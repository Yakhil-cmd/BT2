### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target of a GitHub `status` webhook purely by `Commit.where(sha: params.sha)`, with no check that the reporting repository matches the repository owning that commit's `Stack`. Combined with `Status.replicate_from_github!` persisting `target_url`/`description` verbatim, any webhook whose signature validates for *some* org known to Shipit can write attacker-controlled strings into a `Status` row belonging to a `Commit`/`Stack` from a different repository, as long as the same SHA string exists in both repositories' commit history (a common, non-cryptographic-collision scenario for forks/shared history, or for multiple Stacks tracking the same underlying repo).

### Finding Description
The claimed binding is: `commit.stack.repository.full_name == webhook_payload.repository.full_name` (i.e., the party whose signature was verified is the same party authorized to write into that specific commit's stack). This binding is never checked.

Trace:
- `WebhooksController#verify_signature` only validates that the HMAC signature matches the `webhook_secret` configured for `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates *an organization*, not a specific repository/stack: [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This performs a **global** lookup across every `Commit` row in the database matching the raw `sha` string, with no filter on `commit.stack.repository` or on `params['repository']['full_name']`. [2](#0-1) 
- `Commit#create_status_from_github!` forwards the commit's own (victim) `stack_id` together with attacker-supplied fields into `Status.replicate_from_github!`: [3](#0-2) 
- `Status.replicate_from_github!` persists `state`, `description`, `target_url`, `context`, `created_at` verbatim with no URL/host allow-list or sanitization: [4](#0-3) 

Root cause: the only authorization check performed is "is this signature valid for the org named in `repository.owner.login`", but the actual write target (`commit.stack_id`) is selected solely by matching the free-text `sha` field against the *entire* `Commit` table, irrespective of which repository/org that commit's stack belongs to. Any repository (fork, sibling repo in the same org, or any repo that legitimately shares git history/objects with a tracked repo) that can get GitHub to emit a valid, signed `status` event for a SHA that also exists in a different Stack's commit history will have `target_url`/`description` written into that unrelated Stack's `Status` record and rendered in that stack's UI.

Existing guards do not prevent this:
- `verify_signature` only checks organization-level HMAC, not per-repository ownership of the SHA.
- `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` (`requires :sha`, `accepts :target_url`) validate types/presence only, not content or origin authorization: [5](#0-4) 
- No model validation on `Status#target_url`/`description` exists beyond `state` inclusion: [6](#0-5) 

### Impact Explanation
An attacker who can get GitHub to deliver a validly-signed `status` webhook (e.g., by having write access to a fork or sibling repository whose owning org is configured in Shipit's `secrets.yml`, and where the SHA also exists in a victim Stack's commit history because of shared git history or the same repository being tracked by multiple Stacks/environments) can inject an arbitrary `target_url` (e.g., `javascript:`/phishing URL) and `description` into a `Status` record belonging to a Stack it did not authenticate for. This matches the rules' Critical category: "a payload for one repository mutating another's stack, commit, task or team." The write is repeatable per matching SHA and is not limited to a single victim stack — every `Commit` row sharing that SHA across the whole installation is affected in one request.

### Likelihood Explanation
Requires: (1) a repository/org already configured with a `webhook_secret` in Shipit (i.e., Shipit already trusts that org's GitHub App), and (2) a SHA collision between the attacker-controlled repository's commit history and a victim Stack's tracked commit — realistically achievable via a fork sharing objects with the upstream repo, or multiple Stacks/environments tracking the same repository, rather than a true SHA-1 preimage attack. No Shipit session, API token, or secret is needed by the attacker; GitHub itself signs the webhook for the attacker's own repository/org membership. Feasibility is moderate-to-high in any multi-repo or multi-environment Shipit deployment where an org's GitHub App is shared across several tracked Stacks.

### Recommendation
In `StatusHandler#process` (and `Commit#create_status_from_github!`), scope the `Commit` lookup by the reporting repository, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: params.repository.owner.login, name: params.repository.name })`, so a status is only applied to commits whose Stack actually belongs to the repository that GitHub reported the event for. Additionally consider allow-listing `target_url` hosts before rendering/storing.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not attach a status to a commit belonging to a different repository sharing the same sha" do
  victim_commit = shipit_commits(:first) # belongs to victim stack/repository
  forged_payload = OpenStruct.new(
    sha: victim_commit.sha,
    state: 'success',
    description: 'FORGED description',
    target_url: 'javascript:alert(1)//attacker-controlled',
    context: 'ci/attacker',
    created_at: Time.now.to_s,
    repository: OpenStruct.new(full_name: 'attacker-org/unrelated-repo', owner: OpenStruct.new(login: 'attacker-org'))
  )

  Shipit::Webhooks::Handlers::StatusHandler.new.call(forged_payload.to_h.deep_stringify_keys)

  status = victim_commit.statuses.last
  # Broken binding demonstrated: attacker-controlled string ends up on victim's stack
  assert_equal 'javascript:alert(1)//attacker-controlled', status.target_url
  assert_equal 'FORGED description', status.description
  refute_equal victim_commit.stack.repository.full_name, forged_payload.repository.full_name
end
```
This asserts `@commit.statuses.last.target_url` equals the attacker-forged string while the reporting `repository.full_name` never matches `commit.stack.repository.full_name`, proving the divergence.
