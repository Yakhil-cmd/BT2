This is a very close architectural analog to the ERC20 "transfer not checked" bug, and it exists in `aa_composer.js`'s handling of `fixed_denominations` assets during `sendUnit`.

### Title
AA composer silently drops payment messages for fixed-denomination assets after AA state has already been committed, causing permanent loss of user funds without any transfer or bounce - (File: aa_composer.js)

### Summary
In `sendUnit()`, when a triggered AA response includes a `payment` message paying out an asset that turns out to be a `fixed_denominations` (indivisible) asset, the payment message is silently discarded from the outgoing unit, while any accompanying `state` message that already decremented the AA's internal accounting for that withdrawal is still executed and committed. There is no bounce, no error, and no way for the AA (or the withdrawing user) to detect that the transfer never happened.

### Finding Description
When composing the response unit, the composer resolves each payment message's asset info and explicitly skips completion of `fixed_denominations` payment payloads, marking them for later removal instead of raising an error: [1](#0-0) 

Later, after the state-update formula for the whole unit has been evaluated, the composer filters out exactly those payment messages tied to `fixed_denominations` assets - silently, with only a console log, no `bounce()`: [2](#0-1) 

Because `message.app !== 'payment'` messages (including `state` messages) are left untouched by this filter, any `state` app message in the same response that already deducted an internal balance/ledger entry (a common pattern used throughout the protocol's own bundled AA examples, e.g. withdraw-then-decrement patterns) still gets applied via `executeStateUpdateFormula`, even though the actual payment to the user was dropped: [3](#0-2) 

This is the exact same bug class as the MerkleVesting finding: the code updates internal state as if a transfer succeeded, without verifying that the transfer actually happened, and the failure is swallowed rather than causing a revert/bounce of the whole trigger.

The bundled sample AAs shipped with the codebase follow precisely the vulnerable pattern - a `payment` message paying out `trigger.data.asset`/`$asset` combined with a `state` message that decrements the tracked balance in the same response, for arbitrary caller-specified assets: [4](#0-3) [5](#0-4) 

Any of these AAs (or any AA author's contract following this common, protocol-endorsed pattern) is affected as soon as a user attempts to withdraw a `fixed_denominations` asset that had previously been credited to their internal balance (e.g., via a deposit of that asset, which is accepted and tracked identically to divisible assets in the `state`-based accounting).

### Impact Explanation
A user's internal AA balance for a `fixed_denominations` asset is silently decremented while the corresponding payment output is dropped from the unit before it's ever built/signed. The user loses their tracked funds with no possibility of retrying the withdrawal (the state variable, e.g. `var[$key]`, has already been reduced) and no compensating output was ever produced. This is a direct, permanent AA fund loss reachable by any unprivileged trigger sender who deposits and later withdraws a fixed-denomination asset from an affected AA, matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
The trigger path requires only: (1) an AA that follows the payment+state-decrement withdrawal pattern shown in the protocol's own official examples, and (2) the asset involved happening to be `fixed_denominations` (indivisible). No special privileges, malicious peers, or race conditions are needed - a single ordinary trigger unit from any address suffices to both deposit and later withdraw the asset, hitting this code path deterministically once the balance and asset properties align. Given that the vulnerable pattern is present in ocore's own bundled sample AAs used as reference implementations for third-party AA authors, likelihood of real-world occurrence is high.

### Recommendation
When a payment message targeting a `fixed_denominations` asset cannot be completed/sent, the whole response should be bounced (as with any other unsendable payment), rather than silently filtered out after other messages (in particular `state` messages) have already been evaluated and applied. At minimum, `sendUnit` should validate upfront (before `executeStateUpdateFormula` is run) whether any payment message references a `fixed_denominations` asset, and bounce the trigger with a clear error (e.g., "cannot send fixed-denomination asset from AA") instead of dropping the message post hoc.

### Proof of Concept
1. Deploy an AA using the withdraw pattern from `test/samples/a_bank_without_percent.oscript` (payment + state decrement in the same case), using `trigger.data.asset` as the asset to pay out.
2. Attacker deposits units of a `fixed_denominations` asset to the AA; the AA's silent-accept branch credits `var[$asset_key]` for that asset.
3. Attacker sends a trigger with `trigger.data.withdraw = true`, `trigger.data.asset = <fixed_denominations asset>`, `trigger.data.amount = <credited amount>`.
4. In `sendUnit`, `assetInfos[asset].fixed_denominations` is true, so the payment payload is never completed (`aa_composer.js:1327-1328`) and is subsequently filtered out entirely (`aa_composer.js:1356`) without bouncing.
5. The accompanying `state` message (`var[$key] = var[$key] - trigger.data.amount;`) is still part of `messages` and is applied by `executeStateUpdateFormula` (`aa_composer.js:1405`), permanently reducing the attacker's/user's tracked balance.
6. No payment output for the fixed-denomination asset is ever produced; the user's funds are unrecoverable through this AA.
