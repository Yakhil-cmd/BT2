### Title
`pallet_bridge_messages::MessagesOperatingMode` enum lets an admin unintentionally un-halt inbound message delivery while switching to `RejectingOutboundMessages` - (File: bridges/primitives/messages/src/lib.rs, bridges/modules/messages/src/lib.rs)

### Summary
`pallet-bridge-messages` represents the bridge's operating status with a single enum, `MessagesOperatingMode`, exactly the anti-pattern flagged in the Drift audit: a status type that cannot represent more than one independent restriction at a time, and whose variants don't map cleanly onto the operations they are supposed to gate. Calling `set_operating_mode(RejectingOutboundMessages)` while the pallet was previously `Basic(Halted)` silently clears the halt, re-enabling `receive_messages_proof`/`receive_messages_delivery_proof` (which any signed relayer can call) even though the pallet owner never intended to resume inbound processing.

### Finding Description
`MessagesOperatingMode` is defined as:

```rust
pub enum MessagesOperatingMode {
	Basic(BasicOperatingMode),      // Normal / Halted
	RejectingOutboundMessages,      // only blocks outbound sends
}
``` [1](#0-0) 

and its `is_halted()` implementation only returns `true` for the `Basic(Halted)` variant:

```rust
impl OperatingMode for MessagesOperatingMode {
	fn is_halted(&self) -> bool {
		match self {
			Self::Basic(operating_mode) => operating_mode.is_halted(),
			_ => false,
		}
	}
}
``` [2](#0-1) 

The pallet's only gate on inbound message delivery is this single `is_halted()`/`ensure_not_halted()` check, called from `receive_messages_proof` and `receive_messages_delivery_proof`:

```rust
pub fn receive_messages_proof(...) -> DispatchResultWithPostInfo {
    Self::ensure_not_halted().map_err(Error::<T, I>::BridgeModule)?;
    ...
}
...
pub fn receive_messages_delivery_proof(...) -> DispatchResultWithPostInfo {
    Self::ensure_not_halted().map_err(Error::<T, I>::BridgeModule)?;
    ...
}
``` [3](#0-2) [4](#0-3) 

`ensure_not_halted` simply reads `OperatingModeStorage::get().is_halted()`:

```rust
fn ensure_not_halted() -> Result<(), OwnedBridgeModuleError> {
    match Self::is_halted() {
        true => Err(OwnedBridgeModuleError::Halted),
        false => Ok(()),
    }
}
``` [5](#0-4) 

Because `RejectingOutboundMessages` is a *separate, orthogonal* variant rather than a composable flag alongside `Halted`, if the pallet owner (or root/governance) is currently in `Basic(Halted)` mode — e.g. because they discovered a problem with header-chain finality proofs and wanted to stop **all** bridge traffic — and then calls `set_operating_mode(RejectingOutboundMessages)` (for example, intending to additionally/still stop outbound sends during an upgrade window, or simply mis-remembering the current state), the new mode is written verbatim over the storage:

```rust
fn set_operating_mode(origin: T::RuntimeOrigin, operating_mode: Self::OperatingMode) -> DispatchResult {
    Self::ensure_owner_or_root(origin)?;
    Self::OperatingModeStorage::put(operating_mode);
    ...
}
``` [6](#0-5) 

`is_halted()` now evaluates to `false`, so `ensure_not_halted()` passes, and `receive_messages_proof`/`receive_messages_delivery_proof` become callable again by any signed relayer — even though the admin believed the bridge was still (at least) halted. This is the direct analog of the Drift `ExchangeStatus` enum bug: pausing/adjusting one operation ("reject outbound only") silently unpauses another ("accept inbound proofs/deliveries") that was previously and intentionally disabled.

### Impact Explanation
Once inbound message reception is unintentionally reactivated while the bridge was believed to be fully halted (e.g., during an active incident, compromised bridged-chain finality, or a known-bad proof source), unprivileged relayers can resume submitting `receive_messages_proof` and `receive_messages_delivery_proof`. Since `MessageDispatch` and `DeliveryConfirmationPayments`/`DeliveryPayments` process message dispatch and relayer rewards immediately from these calls, this can lead to dispatch of messages (potentially XCM-borne asset transfers via the bridge) and reward payouts during exactly the window the operator meant to freeze, defeating the purpose of the halt and undermining the bridge's primary incident-response control.

### Likelihood Explanation
The mis-transition itself requires the `PalletOwner`/root to call `set_operating_mode`, but this exactly mirrors the pattern the original report calls out: the design of the status representation is what makes an *administrator's routine or defensive action* (e.g., "stop outbound sends because the far side chain is upgrading") accidentally clear an *unrelated, currently active restriction* (a full halt) — with no warning, no explicit combination logic, and no documentation flagging the interaction between `Basic(Halted)` and `RejectingOutboundMessages`. Given that `set_operating_mode` is the pallet's designated incident-response lever and is exercised via governance/root across multiple bridge-hub runtimes, the likelihood of this footgun being hit during an actual incident is non-trivial, even though the initial state-mutating call itself needs privileged access.

### Recommendation
Represent the operating mode as a set of independent flags (e.g. `halted: bool`, `rejecting_outbound: bool`) rather than a flat enum where one variant silently supersedes another. Ensure `receive_messages_proof`/`receive_messages_delivery_proof` and `validate_message`/`send_message` each check exactly the flag(s) relevant to them, and make `set_operating_mode` (or add a new extrinsic) explicit about which flags it is toggling rather than overwriting the whole mode. Add documentation/tests asserting that transitioning between modes cannot unintentionally clear an orthogonal restriction.

### Proof of Concept
Failed guard: `ensure_not_halted()` in `receive_messages_proof`/`receive_messages_delivery_proof` only inspects `MessagesOperatingMode::is_halted()`, which is `false` for `RejectingOutboundMessages` regardless of the pallet's prior `Basic(Halted)` state [2](#0-1) .

Minimal reproduction outline (using the pallet's existing test harness in `bridges/modules/messages/src/tests/pallet_tests.rs`, which already exercises both modes independently):
1. `PalletOperatingMode::<TestRuntime, ()>::put(MessagesOperatingMode::Basic(BasicOperatingMode::Halted))` — confirmed by the existing test `pallet_rejects_transactions_if_halted` that both `receive_messages_proof` and `receive_messages_delivery_proof` fail with `Error::BridgeModule(OwnedBridgeModuleError::Halted)` [7](#0-6) .
2. Call `Pallet::<TestRuntime>::set_operating_mode(RuntimeOrigin::root(), MessagesOperatingMode::RejectingOutboundMessages)` (owner/root action, simulating an admin who wants to additionally/only block outbound sends).
3. Re-run `receive_messages_proof`/`receive_messages_delivery_proof` as an ordinary signed relayer — per the existing test `pallet_rejects_new_messages_in_rejecting_outbound_messages_operating_mode`, these calls now succeed (`assert_ok!`) even though the pallet was supposed to remain halted [8](#0-7) .

This is not a hypothetical: the test suite itself demonstrates the two states behave completely differently for inbound processing, confirming that transitioning `Halted -> RejectingOutboundMessages` reopens inbound delivery. No test in the harness asserts that inbound processing must remain blocked when moving away from `Halted` into `RejectingOutboundMessages`, indicating the interaction was not considered a security-relevant transition. I did not execute this against a live network; the reproduction is a straightforward composition of the pallet's own existing unit tests (`pallet_rejects_transactions_if_halted` + `pallet_rejects_new_messages_in_rejecting_outbound_messages_operating_mode`) demonstrating the same storage-value transition described above.

#[test]
fn pallet_rejects_transactions_if_halted() {
	run_test(|| {
		// send message first to be able to check that delivery_proof fails later
		send_regular_message(test_lane_id());

		PalletOperatingMode::<TestRuntime, ()>::put(MessagesOperatingMode::Basic(
			BasicOperatingMode::Halted,
		));

		assert_noop!(
			Pallet::<TestRuntime, ()>::validate_message(test_lane_id(), &REGULAR_PAYLOAD),
			Error::<TestRuntime, ()>::NotOperatingNormally,
		);

		let messages_proof = prepare_messages_proof(vec![message(2, REGULAR_PAYLOAD)], None);
		assert_noop!(
			Pallet::<TestRuntime>::receive_messages_proof(
				RuntimeOrigin::signed(1),
				TEST_RELAYER_A,
				messages_proof,
				1,
				REGULAR_PAYLOAD.declared_weight,
			),
			Error::<TestRuntime, ()>::BridgeModule(bp_runtime::OwnedBridgeModuleError::Halted),
		);

		let delivery_proof = prepare_messages_delivery_proof(
			test_lane_id(),
			InboundLaneData {
				state: LaneState::Opened,
				last_confirmed_nonce: 1,
				relayers: vec![unrewarded_relayer(1, 1, TEST_RELAYER_A)].into(),
			},
		);
		assert_noop!(
			Pallet::<TestRuntime>::receive_messages_delivery_proof(
				RuntimeOrigin::signed(1),
				delivery_proof,
				UnrewardedRelayersState {
					unrewarded_relayer_entries: 1,
					messages_in_oldest_entry: 1,
					total_messages: 1,
					last_delivered_nonce: 1,
				},
			),
			Error::<TestRuntime, ()>::BridgeModule(bp_runtime::OwnedBridgeModuleError::Halted),
		);
		assert_ok!(Pallet::<TestRuntime>::do_try_state());
	});
}
