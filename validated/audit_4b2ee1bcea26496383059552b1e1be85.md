### Title
Webhook signature verified against one organization's secret but the acted-upon `repository.full_name` is unbound to that organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` looks up the GitHub App/webhook secret to validate the HMAC using `repository_owner`, a value pulled straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check passes, every `Webhooks::Handlers::Handler` subclass re-reads `repository.full_name` from the same body to look up the `Repository`/`Stack` to mutate — with no code path re-asserting that `full_name`'s owner matches the organization whose secret validated the signature.

### Finding Description
`Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization key configured under `secrets.github` (`TOP_LEVEL_GH_KEYS` vs. per-org sub-hashes). `WebhooksController#verify_signature` derives `organization` from the incoming, unauthenticated JSON payload (`repository_owner`), fetches that organization's app/secret, and HMAC-verifies the raw body against it: [5](#0-4) [6](#0-5) 

Signature verification itself only proves the body was signed by *some org's* configured secret (`GitHubApp#verify_webhook_signature`) — it never checks that the `repository`/`organization` object used to select that secret is the *only* repository object the handlers subsequently act on: [7](#0-6) 

Every handler independently re-parses `payload.dig('repository','full_name')` and loads the `Repository`/`Stack` purely by that string, with `Repository.from_github_repo_name` doing a case-insensitive DB lookup with no scoping to the verifying organization: [3](#0-2) [4](#0-3) [8](#0-7) [9](#0-8) 

This is the exact bug class from the analog report: a value used to derive the security check (`minGasReserve` deducted for the delegatecall / here, the org used to pick the verifying secret) is not the same value that downstream logic actually consumes and trusts (the delegatecall target's semantics / here, the `repository.full_name` that determines which `Stack` is deployed, merged, or archived). The equality that should hold — "organization whose secret verified this webhook" == "organization that owns the repository the handler is about to mutate" — is never enforced.

### Impact Explanation
An operator running a multi-tenant Shipit instance (one deployment, several GitHub orgs each with their own installed GitHub App and `webhook_secret`, which is the documented supported configuration in `lib/shipit.rb`) is exposed: anyone with legitimate webhook delivery rights to **one** onboarded, lower-trust organization (e.g. they administer that org's GitHub App or can trigger its webhook events) can craft a payload whose `organization.login`/`repository.owner.login` names their own org (so the correct, known secret is used and the signature is legitimate) while the `repository.full_name` field names a **different**, higher-privilege repository/stack managed by the same Shipit instance. Handlers such as `PushHandler` (triggers `sync_github`/deploy-affecting sync), the pull-request handlers (archive/unarchive review stacks, capture labels used for provisioning decisions), and the `status`/`check_suite` handlers act on whatever `Stack`/`Repository` that spoofed `full_name` resolves to. This can be used to inject spurious commit statuses, archive/unarchive review stacks, or trigger `sync_github` for a repository/stack the attacker does not control — undermining the integrity guarantees the merge-queue and continuous-deployment logic (`ProcessMergeRequestsJob`, `MergeRequest#all_status_checks_passed?`) rely on, potentially enabling an unauthorized merge or deploy path for a stack the attacker has no legitimate access to.

### Likelihood Explanation
This requires the operator to run more than one GitHub organization/app config in the same Shipit deployment (a supported, documented mode) and requires the attacker to control (or trigger) legitimate webhook deliveries for at least one of the onboarded organizations — e.g., as an admin of a lower-trust org that was allowed to install the Shipit GitHub App. That is a real but non-trivial precondition; it does not require any Shipit session, API token, or the target repository's own secret. Given multi-org support exists specifically to let independent orgs share one Shipit instance, this is a plausible configuration.

### Recommendation
After computing `repository_owner` and verifying the signature, re-derive/require that every field the handler consumes to select `Repository`/`Stack` (`repository.full_name`, `organization.login`) has an owner that case-insensitively matches the `repository_owner` used to select the verifying secret; reject (422) any payload where they diverge, rather than trusting `full_name` independently in each handler.

### Proof of Concept
1. Configure Shipit with two organizations, `trusted-org` and `attacker-org`, each with its own GitHub App and distinct `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. As an admin of `attacker-org`'s GitHub App, craft a `push` webhook JSON body with `"organization": {"login": "attacker-org"}` (or `repository.owner.login = "attacker-org"`) but `"repository": {"full_name": "trusted-org/high-value-repo", ...}` and a valid `ref`/`after`.
3. Sign the raw body with `attacker-org`'s real `webhook_secret` and set `X-Hub-Signature` accordingly; POST to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own known secret.
5. `PushHandler#process` loads stacks via `Repository.from_github_repo_name("trusted-org/high-value-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the `trusted-org` stack — a stack the attacker does not control and for which they have no legitimate webhook delivery relationship.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))

        "unknown_organization=#{e.message}",

      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
