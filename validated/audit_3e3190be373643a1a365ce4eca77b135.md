### Title
Stack-scoped `ApiClient` tokens can read the deploy/build state of *any* stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and every other API endpoint enforces this scope by resolving the requested stack through `BaseController#stack`, which filters through `BaseController#stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`). [1](#0-0)  `Api::CCMenuController` overrides this private `stack` helper with an unscoped lookup, `Stack.from_param!(params[:stack_id])`, which ignores `current_api_client.stack_id` entirely. [2](#0-1)  This breaks the equality that every other controller enforces: `stack the token authorizes == stack the request touches`.

### Finding Description
`ApiClient#check_permissions!`, used by `require_permission!`, only checks that the requested permission string (e.g. `read:stack`) is present in the client's `permissions` array — it never checks `stack_id`. [3](#0-2)  Stack scoping for a token is instead enforced structurally, by every controller resolving the target `Stack` through `BaseController#stack`/`#stacks`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped (e.g. fixture `here_come_the_walrus`, scoped to stack `shipit`, with only `read:stack`). [1](#0-0)  The test fixture confirms this scoping model is a real, in-use permission tier. [4](#0-3) 

`Api::CCMenuController`, however, only declares `require_permission :read, :stack` (permission check, no scope check) and defines its own private `stack` method that bypasses the base's scoped `stacks` relation:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

As a result, any bearer of a stack-scoped, `read:stack`-only token — including the low-privilege CCMenu token minted for a single stack by `CCMenuUrlController#client` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`) [5](#0-4)  or any admin-issued token scoped to one stack — can supply an arbitrary `stack_id` param to `Api::CCMenuController#show` and receive that other stack's build/deploy state, including lock status, running/sleeping activity, last deploy id, last build time, and the stack's web URL. [6](#0-5)  Every other endpoint that trusts the same scoping mechanism (`DeploysController`, `TasksController`, `StacksController`, etc.) correctly restricts `stack` via the inherited scoped helper, confirming `CCMenuController`'s bypass is a deviation from the codebase's own trust model rather than intended design. [7](#0-6) 

### Impact Explanation
This is an authorization-boundary crossing: a credential that is only supposed to authorize reads for stack A is used to read stack state for stack B. It matches the specified High-severity category "unauthenticated/[under-scoped] read of stack state, task streams or deploy output" — the token authenticates, but the authorization scope binding (`stack_id` it was issued for) is not honored, letting the holder enumerate lock reasons, deploy activity/timing, and internal stack URLs for stacks they were never granted access to. In deployments where CCMenu URLs (which embed the token in a query string, see `CCMenuUrlController#fetch`) are shared with third-party CI dashboards or leaked via referrer headers/logs, this converts a narrow, single-stack credential into a full read across every stack in the Shipit instance.

### Likelihood Explanation
No special privileges beyond possessing any valid, stack-scoped, `read:stack` API token are required — this is the minimal-privilege token type in the system (created automatically per user for the CCMenu integration). The attacker only needs to change the `stack_id` request parameter; no signature, no additional secret, and no elevated permission is needed. This is a straightforward parameter substitution against a documented, reachable, unauthenticated-by-scope endpoint.

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` (or reimplement it using the inherited scoped `stacks` relation, i.e. `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot resolve stacks outside `current_api_client.stack_id`, consistent with every other controller under `Shipit::Api::BaseController`.

### Proof of Concept
1. As an authenticated user, create (or let Shipit auto-create) a CCMenu token scoped implicitly to a stack workflow, or have an admin issue an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (mirroring fixture `here_come_the_walrus`).
2. Using that token's `authentication_token`, call:
   `GET /api/stacks/<STACK_B_PARAM>/ccmenu.xml?token=<TOKEN_SCOPED_TO_A>`
   (or via Basic Auth with the token, per `test "can authenticate with query string token"`). [8](#0-7) 
3. Because `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id`, the response returns Stack B's `lastBuildStatus`, `activity`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — data the token was never authorized to access. [6](#0-5)
