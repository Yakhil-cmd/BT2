## Analysis

The reported bug class is a **cap/binding mismatch**: a value that is supposed to constrain behavior to what was "authorized" is not actually enforced everywhere, letting the real distribution exceed the intended cap. In `shipit-engine`, the equivalent binding is: **the stack an `ApiClient` token is scoped to (`ApiClient#stack_id`) must equal the stack a request is allowed to touch.**

### Finding Description

`Shipit::Api::BaseController` is the only place that correctly enforces per-token stack scoping: [1](#0-0) 

`stack` resolves through `stacks`, which restricts the queryable set to `current_api_client.stack_id` when the client is scoped to one. Every controller that inherits this behavior (e.g. `TasksController`, `DeploysController`) is safe: [2](#0-1) [3](#0-2) 

However, `Shipit::Api::CCMenuController` overrides `stack` and bypasses the scoping entirely, resolving the target stack from the raw, unscoped `Stack` relation: [4](#0-3) 

Permission enforcement itself only checks the *static* permission string, never the token's stack binding: [5](#0-4) 

So `require_permission :read, :stack` only guarantees the token has the `read:stack` permission somewhere — not that it's authorized for *this* stack. The stack-level restriction is a convention enforced by the `stack`/`stacks` helper methods, and `CCMenuController` doesn't use them.

This is reachable via a real, already-issued token: `CCMenuUrlController#client` mints (or reuses) a stack-scoped-sounding "CCMenu Client" `ApiClient`, but never actually sets `stack:` on it — only `permissions: %w[read:stack]`: [6](#0-5) 

This token is embedded as a plaintext query parameter in a URL meant for one stack's CI badge (`api_stack_ccmenu_url(stack_id: stack.to_param)`), which is the kind of URL commonly pasted into READMEs, CI dashboards, or shared with third parties (Jenkins/CCTray badge integrations).

### Impact Explanation

Because the token is unscoped and `CCMenuController#stack` ignores `ApiClient#stack_id` entirely, anyone holding one such "CCMenu" token — including a token minted for/shared for a single low-sensitivity stack — can query `GET /api/stacks/:any_other_stack_id/ccmenu.xml?token=...` for **any other stack in the deployment**, retrieving that stack's name, last build status/label/time and web URL. This is an unauthorized cross-stack read of stack state, breaking the equality "stack a token authorizes == stack a token touches" described in scope.

Even for hand-crafted, explicitly stack-scoped `ApiClient` tokens (created via the admin UI with a `stack_id` set and only `read:stack` permission, intended to restrict a low-trust integration to one stack), routing that same token through `CCMenuController` grants it read access to every stack, silently defeating the scoping the operator configured.

### Likelihood Explanation

Exploitation only requires possession of a valid, currently-permitted `read:stack` `ApiClient` token (a normal, low-privilege CI/CCMenu integration credential that is designed to be embedded in URLs and shared outside the trust boundary of the Shipit deployment) and knowledge/enumeration of another stack's `to_param`. No additional secrets, sessions, or elevated roles are required beyond what the report's threshold allows ("an `ApiClient` token" is the credential class this bug is about, not something being additionally required beyond scope).

### Recommendation

Make `CCMenuController#stack` go through the scoped `stacks` relation instead of the raw `Stack` model, matching every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Additionally, `CCMenuUrlController#client` should explicitly bind the minted token to the specific stack (`stack:` attribute), and `find_or_create_by!` should key on `stack` as well as `creator`/`name`, so a single unscoped token isn't silently reused/valid across all stacks.

### Proof of Concept

1. Any user with access to Stack A visits `GET /stacks/:stack_a/ccmenu_url` → `CCMenuUrlController#fetch` returns a URL containing `token=<T>`, where `T` authenticates an `ApiClient` with `permissions: ['read:stack']` and no `stack_id` set. [7](#0-6) 
2. That URL/token is shared externally (as CI badges typically are).
3. An attacker who obtains `T` requests `GET /api/stacks/<stack_b_id>/ccmenu.xml?token=T` for an unrelated Stack B.
4. `CCMenuController#authenticate_api_client` accepts `T`; `require_permission :read, :stack` passes because the permission list contains `read:stack` (scope-agnostic check in `ApiClient#check_permissions!`); `stack` resolves Stack B via unscoped `Stack.from_param!`, returning Stack B's build status/name/URL — data the token was never meant to expose. [8](#0-7)
