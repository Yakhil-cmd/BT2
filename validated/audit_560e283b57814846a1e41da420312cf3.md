## Finding: Stale owner approvals are not invalidated across multisig owner removal/re-addition

### Title
Multisig `MultisigTransaction.votes` entries persist across owner removal and re-addition, allowing a stale approval to silently count toward quorum - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
This is a direct analog of the reported bug class: a status field bound to a participant's identity (`tierWinner`'s `invoiceComplete`/`supportingDocumentsComplete` in the OpenQ report) is not reset when the underlying set membership changes. In `multisig_account.move`, an owner's approval/rejection vote for a pending `MultisigTransaction` is keyed only by `address` in a `SimpleMap<address, bool>` and is never cleared when that same address is removed from, and later re-added to, the owners list.

### Finding Description
Votes on a pending multisig transaction are recorded per-owner-address in the `votes: SimpleMap<address, bool>` field of `MultisigTransaction`, set via `vote_transanction` [1](#0-0) .

Approval counting is done by `num_approvals_and_rejections_internal`, which iterates the account's *current* `owners` vector and simply checks whether that address has an entry in the transaction's `votes` map: [2](#0-1) .

Owner-set mutation is centralized in `update_owner_schema`, used by `add_owner(s)`, `remove_owner(s)`, `swap_owner(s)`, and `update_signatures_required`. This function only mutates `multisig_account_ref_mut.owners` (adding/removing addresses) and `num_signatures_required` - it never touches `multisig_account_ref_mut.transactions` or any transaction's `votes` map: [3](#0-2) .

The existing test suite only verifies the *removal* direction - that a removed owner's vote stops counting because they're no longer in `owners`: [4](#0-3) . There is no equivalent check, and no code path, for the *re-addition* direction: if the same address is swapped/added back into `owners` while the transaction they previously voted on is still pending (unresolved), their old `votes` entry is still present in the map and is immediately counted again by `num_approvals_and_rejections_internal`- with no new approval action performed by that owner after rejoining.

### Impact Explanation
This breaks the "fresh consensus per transaction, per current owner set" invariant that the K-of-N multisig scheme is supposed to provide - the on-chain analog of the approval-set binding failures called out in the admission pivots. A transaction proposed while an owner was still a member can pick up that owner's old vote again after an owner-list churn (remove-then-re-add, or swap-out-then-swap-back-in of the same address) without that owner ever re-affirming their intent for that specific transaction. In a scenario where an owner is removed for cause (e.g., compromised key, departure) and later a *different* physical controller obtains that same address (e.g., account handed to a new signer, or the address is re-added as a placeholder for a different real-world owner), the stale approval is silently reused, potentially pushing a pending transaction over the `num_signatures_required` quorum with fewer genuinely-current approvals than intended.

### Likelihood Explanation
Requires only owner-management operations that are a normal, expected part of multisig lifecycle management (`remove_owner`/`add_owner`/`swap_owner`), not any privileged admin/governance bypass, combined with an unresolved pending transaction, executed via `execute_rejected_transaction`/VM-driven `validate_multisig_transaction`. No cryptographic bypass or external precondition is needed - vote persistence is unconditional.

### Recommendation
When `update_owner_schema` removes an owner, purge that address's vote entry from every pending transaction's `votes` map (or track vote validity by a `(owner_address, owner_epoch)` pair that is bumped on every owner-list change), so re-adding the same address cannot resurrect a stale approval without a fresh vote.

### Proof of Concept
1. Create multisig account with owners `[O1, O2, O3]`, `num_signatures_required = 2`.
2. `O1` calls `create_transaction` (sequence 1) — implicitly approves.
3. `O2` calls `approve_transaction(multisig_account, 1)` — now 2 approvals, `can_be_executed` is true.
4. Multisig calls `remove_owners([O2])` (e.g., O2 is suspected compromised) — `can_be_executed` becomes false since only `O1` remains a current owner with a vote.
5. Multisig calls `add_owner([O2])` again shortly after (e.g., mistake corrected, or address reused for a new key holder) — no re-approval action is performed by `O2`.
6. `num_approvals_and_rejections_internal` again counts `O2`'s stale `votes` entry (still `true` from step 3) because `O2` is back in `owners` and the map was never cleared - `can_be_executed` returns true again and the transaction can be executed with only `O1`'s current, freely-given approval plus a resurrected stale one.     inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
