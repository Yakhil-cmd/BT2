### Title
Webhook signature verification uses `repository.owner.login` while `PushHandler` resolves the target stack from `repository.full_name`, allowing a self-signed webhook to sync an arbitrary victim repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/organization config (and thus the HMAC secret used to authenticate the request) via `repository_owner`, which reads `payload.dig('repository','owner','login')`. `Handlers::Handler#repository_name` (used by `PushHandler#process` via `#stacks`) instead reads `payload.dig('repository','full_name')`. These two fields are never checked for consistency, so an attacker who legitimately owns `attacker-org` and knows its own `webhook_secret` can send a correctly-signed payload where `repository.owner.login = 'attacker-org'` (used only for signature verification) but `repository.full_name = 'victim-org/victim-repo'` (used to resolve stacks and drive `GithubSyncJob`).

### Finding Description
The broken binding: the organization whose secret authenticated the bytes (`repository.owner.login`) is never asserted equal to the organization owning the repository actually acted upon (`repository.full_name`'s owner segment).

Code path:
- `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` [1](#0-0) 
- `verify_signature` selects the app config using `repository_owner`, then verifies the raw body against that org's `webhook_secret`: [2](#0-1) 
- `repository_owner` reads only `repository.owner.login` (or `organization.login`): [3](#0-2) 
- After verification passes, `create` dispatches the parsed JSON to handlers for the event: [4](#0-3) 
- `PushHandler#process` looks up stacks via `stacks`, which calls `Repository.from_github_repo_name(repository_name)`: [5](#0-4) 
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a completely separate field from the one used for signature-org selection: [6](#0-5) 

Because `verify_webhook_signature` only checks the HMAC against the secret configured for whatever organization `repository_owner` names [7](#0-6) , and that organization name is attacker-controlled JSON content (not derived from any GitHub-verified source, TLS client cert, or App installation binding), the attacker can pick `attacker-org` for the owner field (to pass verification with a secret they know) while setting `full_name` to `victim-org/victim-repo` for the actual handler logic. Nothing in `drop_unhandled_event`, `check_if_ping`, `ExplicitParameters` (`PushHandler` only requires `ref`/`after`, it never validates `repository.full_name` against `repository.owner.login`), or `Repository.from_github_repo_name` cross-checks these two payload fields against each other.

Exploit flow:
1. Attacker registers `attacker-org` as a real GitHub App/organization config in Shipit with a known `webhook_secret` (a normal, unprivileged, legitimate use of the product — any org owner can do this).
2. Attacker crafts a JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/master", "after": "<sha>"}`.
3. Attacker computes `sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)` and sends `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=...`.
4. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, verifies successfully (attacker knows the secret), request proceeds.
5. `PushHandler#process` resolves `victim-org/victim-repo`'s stacks and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing a sync/deploy-adjacent job against the victim's repository/stack, entirely outside the victim's control or knowledge.

### Impact Explanation
This is a cross-tenant authentication bypass: a payload "signed" for `attacker-org` mutates state (triggers `GithubSyncJob`/`sync_github`) for `victim-org`'s stack, matching the Critical category "a payload for one repository mutating another's stack." The blast radius extends to any Shipit instance hosting multiple organizations/tenants where an attacker controls at least one legitimately configured org — they can force GitHub sync operations against any other tenant's repository purely by manipulating unauthenticated JSON fields, repeatable on demand for any victim repo name they can guess or know.

### Likelihood Explanation
Preconditions are modest and match the attacker capability described: Shipit must be configured with a GitHub App/org entry for `attacker-org` that the attacker administers (a normal onboarding scenario, not a privileged Shipit role), and the attacker needs no access to the victim's secrets, session, or API tokens at all. The attack requires only computing a standard HMAC-SHA1 over an attacker-composed byte string and sending one HTTP POST — trivially repeatable and scriptable against arbitrary victim `full_name` values.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController#verify_signature`), require that `payload.dig('repository','full_name')`'s owner segment equals `payload.dig('repository','owner','login')` (or `organization.login`) used for signature verification, rejecting the request (422) on mismatch. More robustly, derive the signing organization strictly from `repository.full_name`'s owner segment (single source of truth) instead of a separately-read `owner.login`/`organization.login` field, so there is only one field that both selects the secret and identifies the target repository.

### Proof of Concept
Minitest plan for `test/controllers/webhooks_controller_test.rb`:
1. Configure `Shipit.github_configs` (or stub `Shipit.github`) so `attacker-org` has a real, non-blank `webhook_secret` (e.g., `'attacker-secret'`), and create a victim `Shipit::Stack` for `victim-org/victim-repo` with branch `master`.
2. Build `payload = {"ref" => "refs/heads/master", "after" => "deadbeef", "repository" => {"owner" => {"login" => "attacker-org"}, "full_name" => "victim-org/victim-repo"}}.to_json`.
3. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', payload)`.
4. `post shipit.webhooks_path, params: payload, headers: {'X-Github-Event' => 'push', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json'}`.
5. Assert response is `:ok` (verification passed with attacker-org's secret) — confirming `repository_owner` == `'attacker-org'` was used for auth.
6. Assert `Repository.from_github_repo_name('victim-org/victim-repo')` resolves to the victim stack and that `GithubSyncJob` (or the effect of `stack.sync_github`) was enqueued for the victim stack, i.e., assert on both sides of the equality: the signing org (`attacker-org`) differs from the mutated repository's owner (`victim-org`), yet the sync proceeded — proving the binding is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
