### Title
Cross-Stack Authorization Bypass in CCMenu API Endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the stack-lookup helper inherited from `Api::BaseController` in a way that removes the scoping that ties an `ApiClient`'s token to the single stack it was issued for, allowing any valid API token with `read:stack` permission to read the CI status of *any* stack in the installation, not just the one it is authorized for.

### Finding Description
`Api::BaseController` defines the binding between an `ApiClient`'s authorization scope and the `Stack` a request may touch: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a stack, and `stack` resolves `params[:stack_id]` only within that restricted set via `stacks.from_param!`. Every other stack-scoped API controller (`LocksController`, `OutputsController`, `TasksController`, `DeploysController`, `RollbacksController`, `ReleaseStatusesController`) relies on this inherited `stack` method, so the equality `token.stack_id == stack_being_read` is enforced.

`Api::CCMenuController` breaks this by defining its own `stack` method that bypasses the scoped `stacks` collection entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the string `"read:stack"` is present in `ApiClient#permissions` — it never compares the client's `stack_id` to the requested stack: [3](#0-2) 

Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, any token carrying `read:stack` — including one scoped to an unrelated stack via `ApiClient.stack_id` — resolves and serves data for whatever `stack_id` is placed in the URL.

### Impact Explanation
This breaks the "stack a token authorizes vs. stack it touches" binding: a token minted for Stack A (e.g. via the `CCMenuUrlController`, which explicitly creates a client scoped to one stack: [4](#0-3) ) can be used to read the CI status (last build status/label/time, activity, lock state) of any other stack in the Shipit instance by simply changing the `stack_id` path segment on `GET /api/stacks/:stack_id/ccmenu`. This is an unauthenticated-scope read of stack state across repository/stack boundaries, matching the "High - escalation into authorization... unauthenticated read of stack state" impact class.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `read:stack` API token (e.g. a CCMenu URL shared with a CI dashboard tool, which is designed to be embedded in less-trusted contexts) can trivially exploit this by editing the stack path segment of the request URL — no additional privileges, secrets, or session are required beyond the token they already legitimately hold for their own stack.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-checked `Api::BaseController#stack`/`#stacks` methods (or add an explicit check that `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`) so that a stack-scoped token can never resolve to a different stack.

### Proof of Concept
1. Create a stack `owner/private-repo`, and via `CCMenuUrlController#fetch` (or `ApiClient.create_with(permissions: %w[read:stack], stack: stack_a)`) obtain a token scoped to `stack_a` only.
2. Using that token's Basic-Auth credentials, send `GET /api/stacks/other-owner/other-repo/environment/ccmenu`.
3. Observe that `CCMenuController#stack` resolves `Stack.from_param!('other-owner/other-repo/environment')` successfully (since it does not filter by `current_api_client.stack_id`), and the response renders `other-owner/other-repo`'s last build status/activity/lock state, despite the token never having been granted permission for that stack.
