### Title
AA response payments in fixed-denomination assets are silently dropped without bounce, permanently trapping the sent funds - (File: aa_composer.js)

### Summary
The External Report describes bridging functions that fail to revert when unexpected native value is attached to an ERC20-only call, so the mistakenly-sent value becomes stuck in the contract. The analogous root cause in `ocore` is in `sendUnit()` inside `handleTrigger()` in `aa_composer.js`: when an AA's own response messages try to pay out an asset that turns out to have `fixed_denominations`, the code does not bounce or error — it silently filters the payment message out of the response unit, so the funds stay parked in the AA's balance with no restitution path coded into the AA's own logic, and no signal is given to the AA author/trigger sender that the payout failed.

### Finding Description
In `sendUnit()`, when building an AA response, each non-base payment message is looked up via `storage.loadAssetWithListOfAttestedAuthors`, and if the asset is `fixed_denominations`, the code explicitly comments "will skip it later" and returns `cb()` without adding output addresses or completing the message: [1](#0-0) 

Later, after the eachSeries loop finishes, these messages are filtered out entirely: [2](#0-1) 

If this filtering empties the whole message list, the AA finishes with `handleSuccessfulEmptyResponseUnit(null)` — i.e., the trigger is treated as fully and successfully processed even though the intended payout never happened: [3](#0-2) 

This differs qualitatively from every other payment failure path in `handleTrigger`, which properly calls `bounce(err)` to revert state changes and return leftover funds to the trigger sender (e.g., invalid outputs, unknown asset, private-asset restrictions): [4](#0-3) [5](#0-4) 

Because there is no bounce and no error surfaced, the AA's internal accounting (state vars already updated by `state` messages, balances already debited in `updateFinalAABalances`) proceeds as if the payment succeeded, while the actual on-chain payment message silently disappears. Any assets the AA held or received that are fixed-denomination and intended for payout in that trigger execution are left stranded in the AA's own balance with no code path in the AA definition to retry or recover them (the AA author is unaware the payment app silently no-ops for this asset class), directly mirroring the reported bug class: a fund-moving instruction is silently accepted/ignored rather than rejected, so the funds become frozen.

### Impact Explanation
This causes **AA fund freezing**: any developer-authored AA that is designed to forward or pay out a fixed-denomination asset (e.g., an indivisible/coin-denominated asset issued via an `asset` message inside the AA, or received as trigger input) will have that payout silently dropped whenever exercised, with the unit still validated and saved as a "successful" response. Users interacting with such an AA (e.g., swap/vault/marketplace AAs handling NFT-like fixed-denomination coins) would see their expected payout never arrive, and the AA has no internal awareness that the transfer failed, so it cannot bounce or retry. Funds effectively become stuck in the AA's balance under normal usage, not merely as an edge-case user error, since AA authors have no straightforward validation-time signal that fixed-denomination assets are unsupported for `payment` messages in this way.

### Likelihood Explanation
The condition is trivially reachable by any unprivileged AA author who authors an AA definition that pays out a `fixed_denominations` asset (a normal, documented ojson feature — `payment` messages support arbitrary assets per `aa_validation.js`), and any trigger sender who causes that code path to execute. No special privileges, malicious peers, or node collusion are required — a single posted trigger unit against a publicly deployed AA is sufficient.

### Recommendation
When a `payment` message inside an AA response targets a `fixed_denominations` asset, `sendUnit()` should `bounce()` with a clear error (e.g., "AA cannot send fixed-denomination asset payments") instead of silently filtering the message out of the response and continuing as a successful empty response. This surfaces the failure to the trigger sender/bounce mechanism and prevents state changes and balance debits from being finalized as if the payment had succeeded.

### Proof of Concept
1. Deploy an AA whose response `messages` include a `payment` message paying out an asset `X` where `X` is later defined (or already exists) with `fixed_denominations: true`.
2. Send a trigger to the AA that causes this payment message to execute along with a `state` message that marks the payout as done (a common oscript pattern, as seen in `test/aa_composer.test.js` "issue recently defined asset" pattern where AAs track state after issuing/sending assets).
3. Observe in `aa_composer.js` `sendUnit()`: the payment message is skipped at [6](#0-5) 
 and filtered out at [7](#0-6) 
, yet `state` message effects and balance bookkeeping proceed, and if no other message remains, `handleSuccessfulEmptyResponseUnit(null)` is invoked, marking the trigger as fully handled with no bounce and no recovery of the intended payout.
