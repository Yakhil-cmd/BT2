### Title
Private/Indivisible Asset Sent to an AA Address Is Permanently Locked Because AAs Can Neither Trigger On Nor Spend It - (File: aa_composer.js, main_chain.js)

### Summary
Obyte's Autonomous Agents (AAs) are smart-contract-like addresses that react to "triggers" — payments sent to them. However, the DAG-stabilization logic that detects AA triggers explicitly filters out private-asset outputs, and the AA response-composition logic explicitly refuses to spend private or fixed-denomination (indivisible) assets. Consequently, if a user sends a private or indivisible asset "coin" to an AA address, the AA can never process it as a trigger, and even if the balance is nominally credited, the AA has no code path to spend or return it. The asset becomes permanently unspendable, mirroring the ERC721 "lost NFT" bug class where a plain `_transfer` to a contract without `onERC721Received` support permanently locks the token.

### Finding Description
Two independent mechanisms compound to create the lock:

1. **Trigger detection excludes private assets.** `handleAATriggers` (inside `markMcIndexStable` in `main_chain.js`) is the only code path that inserts rows into `aa_triggers`, which in turn is the only source feeding `handleTrigger`/`getTrigger` execution. Its SQL query explicitly requires `outputs.asset IS NULL OR is_private=0`: [4](#0-3) 
This means a unit whose only payment output to an AA address is denominated in a *private* asset never creates a trigger row for that AA at all — the AA never "wakes up" to process it, regardless of any bounce-fee or balance bookkeeping.

2. **AAs cannot spend private or fixed-denomination (indivisible) assets even if they somehow held a balance.** In `sendUnit`, when composing a response, any asset marked `is_private` is explicitly rejected with an error ("sending private asset from AA"): [5](#0-4) 
And payment messages referencing `fixed_denominations` (indivisible, NFT-like coin) assets are unconditionally stripped out of the response before the unit is built: [6](#0-5) 

Because outputs for private assets are only spendable via the private-payment protocol (`indivisible_asset.js` / `private_payment.js`, which requires address+blinding secrets exchanged out-of-band), and AAs have no oscript primitive or code path to construct such spend proofs or hidden outputs, any private/indivisible coin sent to an AA is functionally unrecoverable by the AA. There is no equivalent of ERC721's `onERC721Received` hook concept here, but the net effect is the same: the receiving "contract" (AA) has no implemented mechanism to accept, acknowledge, or forward the asset back out.

### Impact Explanation
Funds (a unique/private asset unit) sent to any AA address are permanently and unrecoverably lost from the sender's perspective — the AA cannot bounce it back (no trigger fires, so no bounce logic runs), cannot spend it in a response (explicit rejection), and cannot expose it via any getter/state mechanism to allow the AA definer to reroute it manually, since the AA address's private key is unknown (it is derived from the AA definition, not held by any party). This satisfies the "AA fund loss or freezing" acceptance criterion: a legitimate class of asset value becomes permanently stuck at a valid, reachable address with no path to retrieval.

### Likelihood Explanation
Any wallet user or asset issuer who is not fully aware that AAs cannot handle private or indivisible ("NFT-like") assets can trigger this by simply sending such an asset to an AA address — a straightforward user error that is common wherever asset senders script bulk transfers or misinterpret AA addresses as ordinary wallet addresses. No malicious actor, privileged role, or protocol vulnerability is required to reach this state; it is directly reachable by an ordinary, unprivileged user issuing or holding an indivisible/private asset and choosing (or being tricked into choosing) an AA as the recipient.

### Recommendation
- Extend the bounce-fee/trigger detection logic in `main_chain.js`'s `handleAATriggers` query, or the wallet-side `checkAAOutputs` pre-send check in `aa_addresses.js`, to detect and warn/reject sends of private or `fixed_denominations` assets to known AA addresses before the unit is even composed, analogous to the existing bounce-fee check [7](#0-6) .
- Alternatively, make private/indivisible-asset outputs sent to an AA still generate a trigger purely for bounce purposes (auto-refund), so the AA at least attempts to return the asset via the standard private-payment chain mechanics, rather than silently ignoring it.

### Proof of Concept
1. Issue a private, fixed-denomination ("indivisible"/NFT-like) asset via `composer`/`indivisible_asset.js`.
2. Send an output of this asset to a valid AA address (any deployed AA), using the private-payment flow (`buildPrivateElementsChain` / `validateAndSavePrivatePaymentChain`).
3. Observe that `handleAATriggers` in `main_chain.js` never inserts a row into `aa_triggers` for this unit/address because of the `outputs.asset IS NULL OR is_private=0` filter [8](#0-7)  — the AA never executes `handleTrigger`, so no bounce, no acknowledgment, and no state change occurs.
4. Confirm that even if a base-asset bounce-fee trigger for the *same* unit executes for other outputs, any attempt by the AA to spend the private asset out in a `payment` message is rejected at composition time ("sending private asset from AA") [2](#0-1) , and indivisible-asset messages are filtered out entirely before the response unit is built [3](#0-2) .
5. The private/indivisible asset output remains permanently `is_spent=0` at the AA address with no code path in the codebase capable of spending it.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
