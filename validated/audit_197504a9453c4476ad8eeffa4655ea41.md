### Title
API client scoped to one stack can read CCMenu deploy state of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` scopes stack lookups to the calling `ApiClient`'s authorized stack via `stacks`/`stack`, but `Api::CCMenuController` overrides `#stack` to bypass that scoping and query any stack directly by id, breaking the binding "stack a token authorises == stack a token touches."

### Finding Description
`Api::BaseController` defines the authorization-scoped resolution used by every other API controller: [1](#0-0) 

`stacks` restricts the resolvable set to only the client's authorized stack when the `ApiClient` has a `stack_id` set, otherwise falls back to all stacks (unscoped clients). `stack` then must call through `stacks.from_param!` to enforce that restriction.

`Api::CCMenuController`, however, defines its own private `stack` method that does not go through this scoping mechanism at all: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model class rather than on the scoped `stacks` relation. The class-level permission check declared with `require_permission :read, :stack` only verifies that the `ApiClient`'s `permissions` array contains `"read:stack"` — it has no notion of *which* stack, that job is delegated entirely to `#stack`/`#stacks`: [3](#0-2) [4](#0-3) 

Because `CCMenuController#stack` re-implements the lookup without the scoping relation, an `ApiClient` record that legitimately has `stack_id` set (a client explicitly authorized only for one stack, as exercised by the fixture-backed test `"an api client scoped to a stack will only see that one stack"`) still authorizes reads of *any* `stack_id` param, not just its own: [5](#0-4) 

### Impact Explanation
This breaks the equality "stack a token authorises == stack a token touches" for CCMenu status queries: an attacker holding any valid `read:stack`-scoped API client token — even one deliberately limited by an operator to a single, low-sensitivity stack — can enumerate/read the CCMenu XML status (last build status/label, running state, lock state) of every other stack in the installation via `Api::CCMenuController#show`: [6](#0-5) 

This is an authenticated read of stack state that the credential was never authorized to see, which maps to the "unauthorized read of stack state" High-impact category (authorization-scope escalation from a single stack to all stacks), not merely a cosmetic bug.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `read:stack` API clients (the intended least-privilege pattern demonstrated by the `here_come_the_walrus` fixture/tests). Any holder of such a token — which by design is meant to be restricted — can trivially probe other `stack_id` values in the URL; no additional privilege, secret, or session is required beyond the already-issued scoped token, satisfying the "unprivileged attacker" bar (the attacker only has the narrow token they were given, not the excluded categories of session/webhook/private-key access).

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped relation, consistent with `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the direct `Stack.from_param!` bypass so `read:stack` permission enforcement stays consistent for stack-scoped API clients.

### Proof of Concept
1. Operator creates a stack-scoped API client `A` with `permissions: ["read:stack"]` and `stack_id` = Stack#1 (as supported by the `ApiClient` model and exercised by existing fixtures/tests).
2. Attacker in possession of client `A`'s token issues:
   `GET /api/2/<Stack#2 owner>/<Stack#2 repo>/<env>/ccmenu.xml` (any other `stack_id`) with Basic auth using `A`'s `authentication_token`.
3. `Api::CCMenuController#authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (`A` has `read:stack`), and `#stack` calls `Stack.from_param!(params[:stack_id])` on Stack#2 directly, bypassing the `stacks` scope that would have restricted it to Stack#1 only — returning Stack#2's build/deploy status even though `A` was never authorized for Stack#2.
