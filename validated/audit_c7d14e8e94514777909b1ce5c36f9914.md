### Title
Webhook signature bypass via an org with a blank `webhook_secret` allows forging a `status` event that mutates *any* stack's commit by SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`GithubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization's `webhook_secret` is blank, and the organization used for verification is chosen entirely from attacker-controlled payload (`repository.owner.login`). `StatusHandler#process` then looks up `Commit.where(sha: params.sha)` globally, with no scoping to the repository/organization that was actually verified, so a forged `status` webhook "authenticated" via a low-security org can create a GitHub status on a commit belonging to a completely different, high-value stack.

### Finding Description
The binding that must hold is: **the organization whose `webhook_secret` verifies the signature == the organization/repository whose commit gets mutated**. This binding is broken by two independent facts in the code:

1. `WebhooksController#verify_signature` resolves the GitHub App purely from the payload's `repository.owner.login` (or `organization.login`), with no cross-check against the commit/stack being targeted: [1](#0-0) [2](#0-1) 

2. `GithubApp#verify_webhook_signature` bails out with `true` (verified) when `webhook_secret` is blank/unset for that org: [3](#0-2) 

3. Crucially, `StatusHandler#process` does not require or check any `repository` field at all — it resolves target commits purely by `sha`, globally across the entire `commits` table, regardless of which stack/repo they belong to: [4](#0-3) 

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: status`, body `{"repository": {"owner": {"login": "low-security-org"}}, "sha": "<victim commit sha>", "state": "success", ...}`. Since `low-security-org` is configured in `Shipit.githubs` with a blank `webhook_secret` (a real, supported and documented configuration — see `docs/setup.md` "Webhook secret (optional)" and the example secrets files showing `webhook_secret: # nil`), `verify_signature` resolves `Shipit.github(organization: 'low-security-org')` and its `verify_webhook_signature` returns `true` with *no signature header required at all*. The request then reaches `StatusHandler`, which finds and mutates the commit matching `sha` in *any* stack in the database — including one belonging to `flagship-org`, an org that does enforce webhook secrets.

Existing guards do not stop this: `verify_signature` only ever verifies against the org named in the payload, never against the org owning the targeted commit; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`, with no `repository` requirement (unlike other handlers, e.g. `PushHandler`, which use `payload.dig('repository', 'full_name')` to scope via `stacks`). `Commit.create_status_from_github!` performs no repository/stack ownership check against the payload owner either.

### Impact Explanation
A forged `status` event with `state: success` creates a `Shipit::Status` row on the targeted commit via `Commit#create_status_from_github!` → `add_status`, which recomputes `status` and can flip `Commit#deployable?` (`success? && !blocked?`) to true, and triggers `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` / continuous delivery scheduling (`schedule_continuous_delivery`): [5](#0-4) [6](#0-5) 

This is a payload for one repository (the low-secret org) mutating another repository's commit/stack state, which can enable an unauthorized deploy or merge of a commit that never actually passed CI — matching the **Critical** category ("a payload for one repository mutating another's stack, commit, task or team... an unauthorized deploy, rollback or merge"). The attack is repeatable against any commit SHA present in the database, for any stack, as long as at least one org in `Shipit.githubs` has a blank `webhook_secret`.

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one organization configured in `Shipit.githubs`/`secrets.yml` with a blank `webhook_secret` — this is an explicitly documented and supported configuration (marked "optional" in `docs/setup.md`, and shown as `webhook_secret: # nil` in multiple example config files), so it's a realistic misconfiguration for low-traffic/onboarding orgs. The attacker needs no credentials — just knowledge of that org's login name (which is public, e.g., visible via GitHub) and the target commit's SHA (also public if the victim repo is public, or discoverable via the Shipit UI/API for private ones the attacker doesn't need to access). Cost is a single unauthenticated HTTP POST.

### Recommendation
- Require every webhook handler that mutates commit/stack state (`StatusHandler`, `CheckRunHandler`, etc.) to include and validate the `repository.full_name` in its params, and scope the mutation strictly to `Commit.where(sha: params.sha, stack: stacks)` (using the `stacks` helper already available on `Handler`), rather than a global `Commit.where(sha: ...)`.
- Do not treat a blank `webhook_secret` as "always verified" — either require a webhook secret to be configured for every org, or at minimum ensure the org resolved for signature verification matches the org that owns the repository referenced by the mutated resource, so a blank-secret org can never affect another org's data.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "status webhook from an org with blank webhook_secret can forge status on another org's commit" do
  # victim: default 'shopify' org configured with webhook_secret in test/dummy secrets
  victim_commit = shipit_commits(:first)
  refute victim_commit.deployable?, "precondition: commit must not already be deployable"

  # attacker-controlled org with NO webhook_secret configured
  Shipit.githubs['low-secret-org'] = Shipit::GithubApp.new('low-secret-org', { webhook_secret: nil })

  request.headers['X-Github-Event'] = 'status'
  # no X-Hub-Signature header sent at all

  forged_body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'low-secret-org' } }
  }.to_json

  post :create, body: forged_body, as: :json
  assert_response :ok

  victim_commit.reload
  assert victim_commit.deployable?, "forged status from unrelated org made victim's commit deployable"
end
```
This demonstrates the binding `organization used for verification (low-secret-org) == organization owning the mutated commit (shopify/victim stack)` is violated: verification succeeds for `low-secret-org` (blank secret), yet the write lands on a commit belonging to a different, unrelated stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
