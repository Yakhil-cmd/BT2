### Title
Webhook signature/organization-verification failure does not halt the request, letting `PushHandler` mutate an arbitrary victim stack — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` calls `head(422)` on both a failed signature check and a rescued `Shipit::GithubOrganizationUnknown`, but never calls `throw(:abort)`. Since Rails 5+ only halts a `before_action` chain via explicit `throw(:abort)` (a bare `render`/`head` call no longer implicitly stops the chain), execution falls through to `create`, which parses the raw, unauthenticated payload and dispatches it to `PushHandler`. `PushHandler` resolves the target repository from `payload.dig('repository', 'full_name')` — a value the attacker fully controls and which is independent from the `repository.owner.login` used to pick/validate the GitHub App/secret — so an attacker can trigger `sync_github` on any victim stack without ever presenting a valid signature.

### Finding Description
The broken binding: the intended invariant is
`request_processed? == (verify_webhook_signature(secret_of(repository_owner), raw_body) == true)`.

In practice, after this change the code produces:
`request_processed? == true` regardless of the right-hand side, whenever `verify_signature` merely calls `head(422)` without `throw(:abort)`.

Trace:
1. `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` [1](#0-0) .
2. `verify_signature` computes `repository_owner` from attacker-controlled JSON (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and calls `Shipit.github(organization: repository_owner)` [2](#0-1) . If that organization isn't configured, `Shipit.github` raises `Shipit::GithubOrganizationUnknown`, which is rescued and answered with `head(422)` — but the method just returns normally afterward instead of `throw(:abort)` [3](#0-2) . The same is true of the `head(422) unless verified` line for a plain bad-signature case — no `throw(:abort)` there either [4](#0-3) .
3. Because the `before_action` did not `throw(:abort)`, Rails' callback chain is not halted, and `create` still executes: `params = JSON.parse(request.raw_post); Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .
4. `PushHandler#process` resolves the target stacks purely from the payload's `repository.full_name` via `Repository.from_github_repo_name`, and pushes `expected_head_sha: params.after` into `sync_github` for every non-archived stack on the matching branch [6](#0-5) [7](#0-6) . This lookup is completely decoupled from `repository_owner`, which is the only value used for the (bypassed) signature check.
5. Only at the very end of `create` does `head(:ok)` run, which — because `head(422)` already ran earlier in the same request — raises `AbstractController::DoubleRenderError`. The exception fires only after `handler.call(params)` (and its DB side effects) has already completed, so the attacker's mutation persists even though the HTTP response ultimately surfaces as a 500.

Existing guards fail to stop this: `drop_unhandled_event` only screens by event *type* ("push" is a registered handler, so it passes) [8](#0-7) ; `verify_signature`'s rescue/failure branches produce a response but never abort the filter chain; `ExplicitParameters` only validates presence of `ref`/`after`, not authenticity of the sender [9](#0-8) .

### Impact Explanation
An attacker who never possesses any `webhook_secret` can force `PushHandler` to run against any victim stack, calling `sync_github(expected_head_sha: params.after)` on every non-archived stack matching the attacker-chosen `ref`/branch. On a stack configured with `blocking_statuses`, `sync_github` pulling in attacker-influenced commit/status state can flip `blocked?`, gating or ungating deploys for a repository the attacker does not own or control. This is a cross-tenant state write: a payload that authenticated to nothing (an unrecognized/bogus GitHub organization) causes writes against a completely different, victim-owned `Repository`/`Stack`. This matches the Critical category: "a payload for one repository mutating another's stack ... or an unauthorized deploy/rollback."

### Likelihood Explanation
No privileges are required: the attacker only needs to `POST /webhooks` with `X-Github-Event: push`, a `repository.owner.login`/`organization.login` value not present in `Shipit.github_apps` config (trivial to pick a bogus org name), and a `repository.full_name`/`ref`/`after` pointing at any real, targeted stack. No valid HMAC signature is ever required because the check never halts request processing. This is fully repeatable against arbitrary configured repositories/stacks as long as their `full_name` is known (which is public information for any GitHub repo).

### Recommendation
In `Shipit::WebhooksController#verify_signature`, replace bare `head(422)` calls with an explicit halt, e.g. `head(422) and throw(:abort)` (or refactor to `render(...)` plus `throw(:abort)`) in both the `unless verified` branch and the `rescue Shipit::GithubOrganizationUnknown` branch, ensuring `create` never executes when signature verification fails or the organization is unknown.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb`, add a minitest:
1. Configure/stub a victim `Repository` (`owner: 'acme', name: 'victim-repo'`) with a `Stack` on branch `master`, `blocking_statuses` configured, not archived.
2. POST `/webhooks` with header `X-Github-Event: push` and a JSON body where:
   - `repository.owner.login` = `'unknown-org-does-not-exist'` (not present in Shipit's configured GitHub orgs, forcing `GithubOrganizationUnknown`)
   - `repository.full_name` = `'acme/victim-repo'`
   - `ref` = `'refs/heads/master'`, `after` = attacker-chosen SHA
   - No valid `X-Hub-Signature` header (or omit it).
3. Assert on both sides of the binding:
   - Before: `Shipit::Stack.find(victim_stack.id).sync_github` was never invoked (e.g. stub/mock `sync_github` and assert `assert_not_called`).
   - After the request: assert the mock/stub for `sync_github` **was** called with `expected_head_sha:` equal to the attacker's `after` value, proving `PushHandler` executed despite `verify_signature` never validating any secret for `acme`'s configured GitHub App.
   - Also assert the response is a `DoubleRenderError`/500 (not a clean 422), confirming the security check's `head(422)` did not stop the pipeline, only crashed it after the mutation already occurred.
