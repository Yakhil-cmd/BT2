## Analysis

The external report describes a coupled-withdrawal bug: a user's principal is trapped because reward payment (from a possibly-insufficient external source) is bundled atomically with principal withdrawal, and a revert of the reward transfer reverts the whole withdrawal.

Sui's native staking module (`sui_system::staking_pool`) has the equivalent split logic for `StakedSui` vs. `FungibleStakedSui`, and only one of the two code paths defends against the reward-side running out of balance.

### Title
Permanent lock of `FungibleStakedSui` principal when reward split exceeds `rewards_pool` balance - (File: `crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

### Summary
`redeem_fungible_staked_sui` computes a `rewards_amount` from a notional pool-wide exchange rate and then unconditionally calls `pool.rewards_pool.split(rewards_amount)`. Unlike the sibling function `withdraw_rewards` (used by the `StakedSui` withdrawal path), which explicitly clamps the reward amount with `.min(pool.rewards_pool.value())` to avoid aborting, the fungible-stake redemption path has no such clamp. If the computed `rewards_amount` ever exceeds the actual `rewards_pool` balance, `Balance::split` aborts (`ENotEnough`), reverting the entire transaction — including the principal portion that had already been split out of `fungible_staked_sui_data.principal` in the same call. Because `FungibleStakedSuiData` (and its `principal` balance) is a shared/embedded object rather than something the user holds independently, the user has no alternate path to withdraw just the principal; if the underfunding condition persists, the redemption is permanently blocked.

### Impact Explanation
If `rewards_amount` (computed off the pool-level exchange rate/proportional accounting) ever diverges upward from the true available `pool.rewards_pool.value()` — the same rounding/underflow scenario already documented by the `TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN` comment for the direct-stake path — every `redeem_fungible_staked_sui` call for that pool will deterministically abort until more rewards are deposited (if ever). Since holders of `FungibleStakedSui` have no separate function to withdraw only their principal share (there is no fungible equivalent of the direct/pre-active-pool early-return branch in `request_withdraw_stake`), affected principal becomes durably inaccessible — a permanent fund lock, which is an allowed High-severity impact class.

### Likelihood Explanation
The triggering condition (computed reward exceeding actual `rewards_pool` balance) is exactly the scenario the Sui developers already anticipated and patched for the `StakedSui` withdrawal path via `.min()`, but apparently forgot to apply to the `FungibleStakedSui` path, and left the corresponding error constant unused. This is a genuine code-path asymmetry rather than a purely theoretical claim, though pinning down the precise numeric trigger (rounding accumulation across many stake/unstake/reward-deposit cycles) requires further empirical/fuzzing work to fully confirm reachability in a live validator staking pool.

### Recommendation
Apply the same defensive clamp used in `withdraw_rewards` to `redeem_fungible_staked_sui`:
```move
let rewards_amount = rewards_amount.min(pool.rewards_pool.value());
```
before calling `pool.rewards_pool.split(rewards_amount)`, so that a reward-side shortfall degrades gracefully (returns less reward) instead of aborting and blocking principal withdrawal. Alternatively, split principal and rewards into two independently-callable operations so a reward-side failure never blocks principal recovery.

public(package) fun redeem_fungible_staked_sui(
    pool: &mut StakingPool,
    fungible_staked_sui: FungibleStakedSui,
    ctx: &TxContext,
): Balance<SUI> {
    let FungibleStakedSui { id, pool_id, value } = fungible_staked_sui;
    assert!(pool_id == object::id(pool), EWrongPool);

    id.delete();

    let latest_exchange_rate = pool.pool_token_exchange_rate_at_epoch(ctx.epoch());
    let fungible_staked_sui_data: &mut FungibleStakedSuiData =
        &mut pool.extra_fields[FungibleStakedSuiDataKey {}];

    let (
        principal_amount,
        rewards_amount,
    ) = latest_exchange_rate.calculate_fungible_staked_sui_withdraw_amount(
        value,
        fungible_staked_sui_data.principal.value(),
        fungible_staked_sui_data.total_supply,
    );

    fungible_staked_sui_data.total_supply = fungible_staked_sui_data.total_supply - value;

    let mut sui_out = fungible_staked_sui_data.principal.split(principal_amount);
    sui_out.join(pool.rewards_pool.split(rewards_amount));

    pool.pending_total_sui_withdraw = pool.pending_total_sui_withdraw + sui_out.value();
    pool.pending_pool_token_withdraw = pool.pending_pool_token_withdraw + value;

    sui_out
}

/// Split a `Balance` and take a sub balance from it.
public fun split<T>(self: &mut Balance<T>, value: u64): Balance<T> {
    assert!(self.value >= value, ENotEnough);
    self.value = self.value - value;
    Balance { value }
}
