### Title
Cross-tenant commit-status forgery via unscoped SHA lookup in `StatusHandler#process` unblocks victim stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with a bare `Commit.where(sha: params.sha)`, with no scoping to the repository that emitted the webhook [1](#0-0) . Any commit sharing the same SHA in any other stack (which happens whenever two repositories share git history, e.g. a fork) receives the forged status, and `Commit#blocked?`/`Stack#trigger_continuous_delivery` will treat the victim's stack as unblocked from that single, attacker-controlled webhook.

### Finding Description
The claimed-broken binding, made explicit:
`status_signed_by(attacker_org) == status_authorized_for(victim_stack.commit(sha))` — this should be false (an attacker's own repo's CI signal must never satisfy a different tenant's commit's CI requirement), but the code makes it true.

Path traced:
- `WebhooksController#create` dispatches payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates only that the payload's signature matches the secret of `repository_owner = params.dig('repository','owner','login')` [2](#0-1) . This proves the request came from *some* org the attacker controls (their own fork/org) — it says nothing about which commits that signal is allowed to affect.
- Other handlers (`push_handler`, `check_suite_handler`, all `pull_request/*` handlers) correctly restrict their effect to `stacks`, computed from `Repository.from_github_repo_name(repository_name)` i.e., the payload's own `repository.full_name` [3](#0-2) .
- `StatusHandler#process` does not use `stacks`/`repository_name` at all; it looks up commits purely by `sha` across the entire commits table and calls `commit.create_status_from_github!(params)` for every match [1](#0-0) .
- `Commit#blocked?` recomputes over `stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?)`, and `blocking?` is purely a function of the commit's own `statuses` state/context [4](#0-3) [5](#0-4) . Once the forged status flips a blocking commit's state to success, every newer commit in the same stack whose `deployable?` depends on that computation flips too [6](#0-5) , which feeds directly into `Stack#next_commit_to_deploy` and `Stack#trigger_continuous_delivery` [7](#0-6) .

Attack: the attacker owns/forks a repository that shares git history with the victim's tracked repository (a common real-world scenario — public projects, mirrors, or any two repos whose tracked branch diverged from a common base). Because Git commit SHAs are content-addressed, any commit that exists unmodified in both repositories has the identical SHA in both. The attacker:
1. Identifies (from Shipit's public/observable stack UI, or simply by having a fork) a shared-SHA commit that is the oldest blocking commit in the victim's `undeployed_commits` window.
2. Sets a passing commit status for that SHA in **their own** repository (via GitHub's normal status API, on a repo they fully control) so GitHub emits a `status` webhook, signed with **their own** org's webhook secret.
3. `verify_signature` passes — genuinely, because it is being verified against the attacker's own org, which they legitimately control.
4. `StatusHandler#process` runs `Commit.where(sha: <shared sha>)`, which returns rows from both the attacker's own stack and the victim's completely unrelated stack, and writes a `Status` record onto the victim's `Commit` too.
5. The victim's blocking commit's `blocking?` now evaluates false, `Commit#blocked?` for every newer undeployed commit in that stack recomputes false, and `trigger_continuous_delivery`/`next_commit_to_deploy` may deploy commits the victim never validated for that repository.

None of the existing guards catch this: `verify_signature` authenticates the org, not the target commit; `ExplicitParameters` schema on `StatusHandler` only validates field types/presence, not ownership [8](#0-7) ; there is no `stacks`/repository check in this handler at all.

### Impact Explanation
A single forged (but validly-signed-for-the-attacker's-own-org) status webhook writes a `Status` record against a commit belonging to a repository/stack the attacker does not own or control, which is exactly the "payload for one repository mutating another's stack, commit ... an unauthorized deploy" category (Critical). Because `Commit#blocked?` is recomputed transitively over the whole undeployed window, a single forged status can flip `deployable?` for every newer commit stacked behind the blocking one, enabling `trigger_continuous_delivery` to fire an unauthorized deploy for the victim's stack. This is repeatable against any victim repository/stack that happens to share commit history with a repository the attacker controls (forks are the common case), and the attacker can repeat this for as many shared SHAs as they can find.

### Likelihood Explanation
Preconditions: victim stack has `ci.blocking` statuses configured (per README) [9](#0-8) , multiple undeployed commits stacked behind a blocking one, and a shared-history commit exists between the attacker-controlled repo and the victim repo (trivially true for any fork relationship, which is extremely common on GitHub). Attacker cost is low: fork or otherwise control a repo sharing history with the target, then set a commit status via the standard GitHub API on their own repo/SHA — no Shipit credentials, GitHub App keys, or webhook secrets needed for the victim org.

### Recommendation
Scope `StatusHandler#process` to the repository that emitted the webhook, mirroring the other handlers' `stacks`/`repository_name` pattern, e.g. only update commits belonging to `stacks` derived from `payload.dig('repository','full_name')` instead of a bare cross-tenant `Commit.where(sha: ...)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual location may need adjustment to match existing handler test conventions):
```ruby
test "#process does not update commits belonging to a different repository sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:some_other_repo_stack)

  shared_sha = "abc123..." # same sha value on both commits, simulating shared git history
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'soc/compliance',
    'repository' => { 'full_name' => attacker_stack.github_repo_name }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal 'success', attacker_commit.reload.status.state   # expected: attacker's own commit updated
  refute_equal 'success', victim_commit.reload.status.state     # currently FAILS: victim_commit also becomes success
end
```
Both sides of the equality to assert: `status_applied_to(attacker_commit) == true` and `status_applied_to(victim_commit) == false` — the current implementation makes the second assertion fail, proving the cross-tenant write.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
