### Title
Cross-stack commit status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA only, with no filter on repository or stack, and updates the status of every matching row. Because `Commit` rows are unique per `(sha, stack_id)` rather than globally unique per SHA, an authenticated webhook for one repository can flip CI state for the exact same SHA recorded under a different stack (e.g. a review stack) if that stack happens to contain a commit with that SHA.

### Finding Description
The broken invariant is: `status_webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` row mutated by the handler. In `StatusHandler#process`, the code is: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no `stack_id`, `repository_id`, or repo-name filter. `params.context`, `params.sha`, and `params.state` are fully attacker-controlled fields of the JSON body of the `status` webhook.

`verify_signature` in `WebhooksController` only proves that the payload was signed by the GitHub App secret for `repository_owner` (derived from `payload['repository']['owner']['login']`) — [2](#0-1) . It authenticates *who sent the payload*, but does nothing to constrain *which `Commit` rows in the database* get written. It never checks that `params.dig('repository','full_name')` matches the repository owning the commit(s) being updated.

The DB schema confirms the SHA is not globally unique — it is only unique per `(sha, stack_id)`: [3](#0-2) . This means the same SHA string can legitimately exist as separate `Commit` rows across multiple stacks (main stack and any of its review stacks, or any other stack that happens to import a commit with that hash), and `StatusHandler` will flip all of them in a single call, regardless of which repository actually authenticated the webhook.

Combined with review stacks (`review_stacks_enabled: true`, `provisioning_behavior: allow_all`), an external contributor can open a PR that auto-provisions a review stack executing `shipit.yml` [4](#0-3) . If that review stack's `Commit` row shares a SHA with a commit tracked by the main "deploy/production"-gated stack (e.g. because the PR branch is not rebased/re-committed and shares an ancestor commit that both stacks have ingested, or because the SHA was deliberately crafted to collide with a known upstream commit already present in the target stack's commit history), a `status` webhook signed for the attacker's own repository — setting `context: deploy/production` and `state: success` (or `failure`) for that SHA — is applied by `Commit.where(sha: ...)` to *every* `Commit` row with that SHA across all stacks, including the victim's, without the victim repository ever authenticating that state.

Existing guards do not close this: `verify_signature` checks provenance of the sender, not scope of the mutation; `ExplicitParameters` (the `params do ... end` schema) only validates types/presence of `sha`/`state`/`context`, not ownership; there is no `stack.repository`/`stack_id` filter anywhere in `process`.

### Impact Explanation
A payload authenticated for repository A can flip the `deploy/production` (or any) status of a commit belonging to a completely different stack/repository B, as long as B has a `Commit` row with the same SHA. This is a cross-tenant "payload for one repository mutating another repository's stack/commit" scenario. Depending on how `deployable?`/`blocked?`/`required_statuses` are configured on the victim stack, this can unblock a merge, unblock/allow a deploy, or force a block on an otherwise green commit — i.e., it can trigger an unauthorized deploy or improperly gate/ungate a release on the victim's stack. Severity matches "Critical: a payload for one repository mutating another's stack/commit" per the given impact classes.

### Likelihood Explanation
Exploitability is gated by a nontrivial precondition: the attacker must get a `Commit` row with an *identical SHA* to exist in the victim's stack — this generally requires the victim stack to actually contain the exact same commit (a shared ancestor/history, e.g. a fork of the target repo, or a PR against the same repo where a review stack is auto-provisioned per `review_stacks_enabled: true` + `allow_all`). This is realistic specifically for the review-stacks case described in the question, since review stacks are commonly provisioned from PR branches of the same repository, meaning many commits are shared verbatim between the main stack and the review stacks. In that in-repo scenario, `repository_owner` will match (same repo), so `verify_signature` passes normally, and the attacker (any external contributor who can open a PR and thus cause GitHub to emit `status` events, or who can directly call `POST /webhooks` with a validly-signed status for their own accessible repo/org) can trivially target any commit SHA shared between their review stack and the tracked stack, including intentionally citing an existing upstream `deploy/production`-relevant SHA. This is repeatable per request and is not rate-limited by the handler itself.

### Recommendation
Scope the status update to only the commits belonging to the repository that authenticated the webhook. In `StatusHandler#process`, join through `stack`/`repository` and filter by the repository name derived from the verified payload (e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })`), or otherwise pass the authenticated repository context from the controller into the handler and require `commit.stack.repository.full_name == payload_repository_full_name` before applying `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — not present in current test/ tree):
1. Create `repository_a` (attacker-controlled, e.g. `owner/repo-a`) and `repository_b` (victim, e.g. `owner/repo-b`) with `repository_b.review_stacks_enabled = true`, `provisioning_behavior = allow_all`.
2. Create `stack_b` under `repository_b` requiring status context `deploy/production`; create `commit_b = stack_b.commits.create!(sha: "deadbeef"*5, ...)`.
3. Create `stack_a` under `repository_a`; create `commit_a = stack_a.commits.create!(sha: commit_b.sha, ...)` (same SHA, different stack — allowed since uniqueness is `(sha, stack_id)`, not global).
4. Assert baseline: `commit_b.status.state == "pending"` (or whatever default), i.e. `commit_a.stack.repository.full_name != commit_b.stack.repository.full_name` while both share `sha`.
5. Build a `status` webhook payload with `sha: commit_b.sha`, `context: "deploy/production"`, `state: "success"`, `repository: { owner: { login: "owner" }, full_name: "owner/repo-a" }`, signed with repository_a's/organization's webhook secret.
6. `StatusHandler.new(payload).call` (or POST to `/webhooks` with proper `X-Hub-Signature`).
7. Assert `commit_b.reload.status.state == "success"` even though the webhook only authenticated for `repository_a`, proving the equality `status_webhook.repository.full_name == commit.stack.repository.full_name` is violated for `commit_b`.
