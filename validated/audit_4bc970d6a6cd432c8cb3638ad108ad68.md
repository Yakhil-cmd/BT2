### Title
AA authors can permanently block exercise of escrow/option-style logic by referencing a formula-computed asset that never resolves, causing buyers to lose premiums already paid - (File: aa_composer.js)

### Summary
The Putty finding shows that a counterparty in an escrow-like contract can encode payment conditions (zero amounts or non-existent tokens) that make the counterparty's future claim permanently unfulfillable, while premiums already paid are unrecoverable. The same class of bug is reachable in ocore's Autonomous Agents: `aa_validation.js` allows the `asset` field of a `payment` message to be an arbitrary formula that is never checked against a real, existing asset at definition time, and `aa_composer.js` resolves that formula only at trigger-execution time via `storage.loadAssetWithListOfAttestedAuthors`. If the formula can be made to always resolve to an asset that never exists (e.g., a typo'd/never-issued asset id, or one conditioned on a state variable that the AA design never actually sets), every trigger that reaches that payment message bounces forever, permanently denying the counterparty's ability to complete the exchange, after they may have already paid an irrecoverable premium/fee in an earlier interaction with the same AA.

### Finding Description
In `aa_validation.js`, the `payment` message case validates the shape of `asset` only loosely — it must be `'base'`, a valid base64 hash, or a formula; the validator never checks that the formula, when evaluated, will resolve to an asset that actually exists: [1](#0-0) 

At trigger-execution time, `aa_composer.js`'s `sendUnit()` resolves each payment message's asset and, if it is non-base, looks it up via `storage.loadAssetWithListOfAttestedAuthors`. If that lookup errors (asset not found / not valid), the error is propagated straight into `cb(err)` for the whole `async.eachSeries` over messages: [2](#0-1) 

That error terminates message processing and forces the entire trigger to bounce: [3](#0-2) 

`bounce()` discards any pending state update (`objStateUpdate = null`) and only refunds what was received in *this* trigger, minus the bounce fee; it has no knowledge of, and cannot recover, coins the counterparty sent in *earlier*, separate triggers to the same AA (e.g., an option premium, a subscription fee, a locked deposit): [4](#0-3) 

Because AA definitions are immutable once posted, and the formula for `asset` can reference a state variable, a data-feed value, or a hard-coded asset unit-hash that will never correspond to a real, existing asset (either because it's malformed or because the branch of logic that would define/issue it is never reachable), an AA author acting as the "seller"/counterparty in an escrow, lending, or option-like AA can:
1. Accept a payment (premium/fee/collateral) from a counterparty in an early trigger.
2. Guarantee that the later "exercise"/"claim"/"redeem" trigger's payout message always references a non-existent asset (or, similarly, a formula whose amount will always compute to zero across all downstream messages, causing `handleSuccessfulEmptyResponseUnit` to occur only when *all* messages are cleared — otherwise the invalid-asset path bounces).
3. Cause every subsequent legitimate claim/exercise attempt from the counterparty to bounce permanently, since the malformed asset reference is baked into the AA's immutable code and is evaluated identically on every attempt.

This mirrors the external report exactly at the semantic level: a counterparty encodes an unfulfillable claim condition (invalid/non-existent asset reference), and the victim who already transferred value (premium/fee/deposit) in good faith has no way to ever complete the exchange, permanently losing that value.

### Impact Explanation
Funds already sent to the AA in a prior trigger (premium, subscription fee, deposit, collateral top-up, etc.) become permanently unrecoverable because the AA's payout logic can never execute — it will always bounce due to the invalid asset reference. This is a concrete AA fund loss/freezing scenario for any AA whose author intentionally or accidentally encodes such a payment message, and it is fully reachable by posting a normal trigger unit; no privileged access, node compromise, or network attack is required.

### Likelihood Explanation
Any AA author can define this pattern deliberately (malicious/adversarial "seller" AA, as in the original finding) or introduce it accidentally (a plausible engineering mistake, given that `aa_validation.js` performs no semantic check that a formula-based `asset` field will ever resolve to a real asset). Since AA source code is public before counterparties interact with it, a careful counterparty could in principle detect an obviously-wrong hard-coded asset id, but formula-based/state-dependent asset references make the flaw much harder to spot by inspection, and it is undetectable at the protocol/validation layer.

### Recommendation
- In `aa_validation.js`, when the `asset` field of a `payment` message is a formula, consider requiring it to be validated/testable against a known-good set of assets referenced elsewhere in the AA definition (e.g., assets the AA itself defines via `app: 'asset'` messages, or `'base'`), rather than accepting arbitrary formulas with no correctness guarantee.
- In `aa_composer.js`, distinguish "asset genuinely does not exist" bounces from other bounce causes, and consider whether AAs should be able to catch this condition via formula (e.g., exposing `asset[...][[exists]]`, which already exists in `formula/evaluation.js`, more prominently in AA authoring guidance) so that well-written AAs can guard against paying out in an asset that doesn't exist and instead fail gracefully or select a fallback, rather than relying solely on the AA author to write correct code.
- Document this footgun clearly for AA authors and provide static/linting checks (outside of chain consensus) that flag `payment` messages whose `asset` formula cannot be proven to correspond to an existing or self-issued asset.

### Proof of Concept
1. Author an AA whose first-stage message accepts a "premium" payment from a counterparty and records this in state (e.g., `var['paid'] = true`).
2. Author a second-stage ("exercise") message, reachable once `var['paid']` is true, whose `payment` message payload has `asset: "{var['nonexistent_asset']}"` — a state variable that the AA's logic never actually sets to a real asset unit-hash (or hard-code a plausible-looking but never-issued asset hash).
3. A counterparty triggers stage 1, paying the premium; `var['paid']` becomes true, the AA's collected premium is spent/kept as intended.
4. The counterparty triggers stage 2 to exercise/claim. In `aa_composer.js`, `storage.loadAssetWithListOfAttestedAuthors` fails to find the asset, the error propagates to `cb(err)` in the `async.eachSeries` over messages, and `bounce(err)` is invoked, discarding the state update and refunding only the bytes from the exercise trigger (minus bounce fee) — the previously paid premium is not returned.
5. Every future exercise attempt bounces identically, since the AA definition is immutable, permanently denying the counterparty's claim while the premium remains lost. [4](#0-3) [5](#0-4) [1](#0-0)
