### Title
Vault-level `repay` pause blocks liquidations with no grace period, unlike the dedicated `pause-liquidation` mechanism - ([File: mainnet/contracts/market/v0-4-market.clar], [File: mainnet/contracts/vault/v0-vault-stx.clar] and sibling vaults)

### Summary
The market contract's own liquidation-specific pause (`pause-liquidation`) was hardened to address exactly the bug class in the external report: unpausing sets a grace period during which liquidations remain blocked, giving borrowers time to fix their positions [1](#0-0) . However, `liquidate()` also depends on a second, independent pause switch at the vault level — the `repay` flag in each vault's `pause-states` — which has no grace-period logic and is checked unconditionally inside `system-repay`, a function `liquidate()` must call to settle the borrower's debt.

### Finding Description
`liquidate()` in `v0-4-market.clar` computes liquidation amounts and then calls `vault-system-repay`, which routes to the underlying vault's `system-repay` function to actually settle the seized debt [2](#0-1) [3](#0-2) .

Each vault's `system-repay` unconditionally asserts that the vault's own `repay` pause flag is not set: [4](#0-3) 

This flag is distinct from the market's `pause-liquidation` variable, and is intended to let the DAO independently pause ordinary user loan repayments per-vault (e.g. during a vault-specific incident) without necessarily pausing liquidations market-wide. But because `liquidate()` internally must call `system-repay` to move funds, setting the vault's `repay` pause flag silently blocks all liquidations for that asset's debt, with `ERR-PAUSED` propagating out of the `liquidate` call — even if `pause-liquidation` in the market contract is `false` and no liquidation grace period is active.

Crucially, unlike `pause-liquidation`/`is-liquidation-paused`, which the protocol deliberately fixed by adding grace periods on unpause specifically to avoid the reported bug class [5](#0-4) , the vault's `repay` pause is a bare toggle with no grace-period safety net. During any period the DAO pauses vault-level `repay` (for a legitimate, unrelated reason — e.g. temporarily halting user-initiated repayments to investigate an oracle or accrual issue), no unhealthy position on that debt asset can be liquidated, regardless of how adverse the market move is.

### Impact Explanation
While liquidations are blocked, an unhealthy borrower's debt continues to accrue/lose collateral value; when the position ultimately can no longer be liquidated to fully cover the debt, the shortfall is socialized across all suppliers via `socialize-debt`, which mutually reduces the liquidity index (`lindex`) for every depositor in that vault [6](#0-5) . This is a shared-pool socialization of losses caused by a stranger's (the borrower's) unliquidatable position, harming all other unprivileged suppliers of that vault — this is the "socialization charged to all suppliers" pattern explicitly named as in-scope. This lands in the Critical impact class (protocol insolvency / theft of at-rest funds from all pool suppliers via forced write-down of the liquidity index).

### Likelihood Explanation
Likelihood is moderate: it requires the DAO to pause `repay` on a vault (a normal, foreseeable operational action, e.g. during maintenance or an incident response unrelated to liquidations) while a position on that debt asset simultaneously becomes unhealthy due to market movement. Given multi-vault, multi-asset design, and that pausing `repay` is a plausible standalone maintenance action (as opposed to a coordinated full-protocol pause), the interaction is realistic and was evidently not accounted for when the liquidation-specific grace-period mitigation was added.

### Recommendation
Either (a) have `liquidate()`/`vault-system-repay` bypass the vault's `repay` pause flag when invoked from the liquidation path (e.g. add a dedicated `liquidation-repay` entry point in each vault that does not check `get repay states`), or (b) extend the same grace-period mechanism used for `pause-liquidation` to the vault's `repay` pause flag so that unpausing `repay` also cannot trigger an immediate liquidation cascade, while pausing `repay` never blocks liquidations outright.

### Proof of Concept
1. DAO calls each vault's pause-setting function to set `repay: true` in `pause-states` for, say, `v0-vault-usdc` (a legitimate action to pause user-initiated USDC loan repayments during a maintenance window), while leaving market's `pause-liquidation` at `false`.
2. Concurrently, the price of a borrower's collateral drops, pushing their USDC-debt position's LTV above `ltv-liq-partial`.
3. A liquidator calls `liquidate(borrower, collateral-ft, usdc-ft, debt-amount, ...)`. Execution proceeds through health checks and liquidation-parameter math, then calls `vault-system-repay` → `.v0-vault-usdc system-repay` [2](#0-1) .
4. `system-repay` hits `(asserts! (not (get repay states)) ERR-PAUSED)` and the entire `liquidate` transaction reverts [7](#0-6) .
5. The unhealthy position remains open and continues to deteriorate for the duration of the `repay` pause (unbounded, no grace period), risking full bad-debt socialization onto all USDC vault suppliers once liquidation eventually occurs.
