## Analog Analysis: CVE-2018-3170 (MySQL DDL causing hang/crash)

The MySQL bug lets a network-reachable, authenticated (but not admin) attacker send a request that hits an unhandled internal server condition, crashing/hanging the whole DB server (availability-only impact). The closest structural analog in `ocore--004` is that `validation.js` embeds several `throw Error(...)` "invariant" assertions inside the unit-validation code path that is reachable directly from a **posted/received unit** (an unprivileged unit poster), and any uncaught exception anywhere in the node process is turned into a hard process crash by the top-level handler.

### Title
Unhandled invariant-violation `throw` in double-spend/witness validation crashes the whole node process - (File: `validation.js`, `network.js`)

### Summary
`checkForDoublespends()` in `validation.js` and related invariant checks (e.g. `validateParents`, `buildListOfMcUnitsWithPotentiallyDifferentWitnesslists`) use `throw Error(...)` for conditions the developers believed "can't happen," rather than routing them through the normal `callback(err)` error path used everywhere else in validation. Because `validate()` is invoked synchronously inside the `async.series` control flow, any of these `throw` statements propagate out of the `db.query` callback and become an **uncaught exception** at the top of the event loop. `network.js` installs a global handler that deliberately re-throws to crash the process: [1](#0-0) . This means any code path in validation, AA execution, or DAG bookkeeping that can be driven into one of these "unreachable" `throw`s by attacker-controlled unit content results in denial of service for the whole node, not just rejection of the bad unit — directly mirroring the “hang or frequently repeatable crash (complete DOS)” impact of CVE-2018-3170.

### Finding Description
Unit validation is entered directly from a posted/received joint via `handleJoint()` → `validation.validate()` [2](#0-1) . Inside validation, several helper functions assert data-shape invariants using `throw Error(...)` instead of returning an error to the callback chain:

- `checkForDoublespends()`, used for both `spend_proofs` and payment-input double-spend detection, throws if a conflicting DB record's address is not among the authors of the unit being validated, or if a "should be unreachable" combination of stability/sequence is found: [3](#0-2) .
- `validateParents()` throws on parent/last-ball inconsistencies it assumes cannot occur (`objValidationState.bAA && objUnit.parent_units.length > 2`, "last ball unit just became stable but ball not found", etc.): [4](#0-3) [5](#0-4) .
- `validateAuthor()`/`validateAuthors()` throw on “AA-only” invariants (`throw Error("AA definition not found ...")`, `throw Error("AA unit with multiple authors")`) that assume `objValidationState.bAA` unit shapes are always well-formed: [6](#0-5) [7](#0-6) .
- `storage.js`'s witness-list-mutation walk throws `"no best parent of unit ...?"` if a cached unit's `best_parent_unit` is unexpectedly null while walking the DAG: [8](#0-7) .

Any of these represent a class of bug directly analogous to the MySQL DDL crash: a server-side "should never happen" assumption that is reachable from unprivileged, network-supplied input (a posted unit, an AA trigger unit composed via `aa_composer.js`'s `validateAndSaveUnit`, or a private-payment double-spend check) and, when violated, is not handled gracefully but instead throws all the way out of the validation pipeline. Because the process installs `process.on('uncaughtException', ...) { ... throw err; }`, that throw is not merely a local validation failure — it terminates the entire ocore process [1](#0-0) .

### Impact Explanation
If an attacker can construct a unit (via `network.js`'s `handleJoint` unit posting path, or an AA trigger that flows through `aa_composer.js`'s `validateAndSaveUnit` which reuses the same `validation.validate()`, see `aa_composer.js` lines around `throw Error("AA validation joint error: " + err)`) that reaches one of these "unreachable" throw sites, the effect is a full node crash (denial of service), matching the CVSS Availability-only impact of CVE-2018-3170. Because this is triggered by processing a single posted unit or a wallet-composed transaction, and the crash-on-uncaughtException policy is global (`network.js:4530-4543`), a witness/hub/full node repeatedly fed such a unit would repeatedly crash, preventing the network from confirming new units through that node.

### Likelihood Explanation
These invariant throws are guarded by preceding checks meant to make them logically unreachable in the sanctioned code paths (e.g., the double-spend SQL query filters by escaped address before the throw at `validation.js:1672`), so triggering them requires finding a specific edge case where the precondition assumption is violated — for example, a mismatch between how `arrAuthorAddresses` is computed versus how the SQL address-matching is done (case sensitivity, whitespace, or author-list ordering edge cases), or a race between AA sub-trigger validation and the assumption that AA-generated units are always well-formed. I was not able to fully verify a concrete unit/trigger payload that violates one of these specific invariants within the scope of this review — this would require deeper tracing of `arrAuthorAddresses` construction versus the SQL matching logic, and of AA trigger composition in `aa_composer.js`, which is only partially covered by the indexed context.

### Recommendation
Replace all `throw Error(...)` invariant assertions inside the unit-validation call graph (`validation.js`, `storage.js`'s DAG-walking helpers reachable from validation, and `aa_composer.js`'s trigger validation) with calls to the existing `callback(err)` / `ifUnitError` error-reporting convention, so that any violated invariant results in unit rejection rather than an uncaught exception that crashes the whole process. At minimum, wrap the top-level `validate()` invocation (and the AA `validateAndSaveUnit` path) in a try/catch that converts unexpected exceptions into a `ifUnitError`/`ifTransientError` callback instead of letting them propagate to `process.on('uncaughtException')`.

### Proof of Concept
Not established. Exploiting this would require crafting a unit or AA trigger whose author/address/sequence data violates one of the invariants asserted in `checkForDoublespends()` (`validation.js:1672`, `1688`, `1692`), `validateParents()` (`validation.js:678`, `817`), or the AA definition/author invariants (`validation.js:1130`, `1171`) while still passing all preceding checks in `validate()`. Confirming a concrete PoC would require constructing and locally validating a crafted joint against the exact SQL/address-matching logic in `checkForDoublespends`, which was not verified in this analysis.
