### Title
Division-by-Zero in `consolidatedNode.Split` Panics `FinalizeState` When Proposer Has Zero Total Staking — (`kaiax/staking/staking_info.go`)

### Summary

`consolidatedNode.Split` divides by `totalAmount = StakingAmount + CLStakingAmount`. When a block proposer is registered in both the AddressBook and CLRegistry but both staking amounts round down to zero (< 1 KAIA each), `totalAmount = 0` and `big.Int.Div` panics. This panic propagates through `specWithProposerAndFunds` / `specWithProposerAndFundsFlex` → `getDeferredRewardFullKore` / `getDeferredRewardFullFlex` → `FinalizeState`, crashing block finalization on every honest node that processes the block.

### Finding Description

`consolidatedNode.Split` in `kaiax/staking/staking_info.go` computes the CN/CL reward split:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)   // ← panics if totalAmount == 0
    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [1](#0-0) 

Both `StakingAmount` and `CLStakingAmount` are stored in whole KAIA (rounded down from wei). If a validator's CNStaking contract holds < 1 KAIA and their CL pool also holds < 1 KAIA, both fields are 0 after the integer division in `parseCallResult` / `parsePermissionlessCallResult`:

```go
CLStakingAmount: big.NewInt(0).Div(clRes.StakingAmounts[i], big.NewInt(params.KAIA)).Uint64(),
``` [2](#0-1) 

`Split` is called unconditionally (no guard on `totalAmount`) from `specWithProposerAndFunds` and `specWithProposerAndFundsFlex` for the block proposer whenever `cn.CLStakingInfo != nil`:

```go
// Handle CLStakingInfo for proposer after Prague
cns := si.ConsolidatedNodes()
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase { continue }
    if cn.CLStakingInfo == nil { break }
    cnAmount, clAmount := cn.Split(proposer)   // ← no zero-total guard
    ...
}
``` [3](#0-2) 

The same pattern exists in `specWithProposerAndFundsFlex`: [4](#0-3) 

By contrast, `assignStakingRewards` and `assignStakingRewardsFlex` are safe because they only call `Split` when `cnTotalStakingAmount > minStake`, guaranteeing `totalAmount > 0`: [5](#0-4) 

The full call chain from block finalization to the panic:

`FinalizeState` → `GetDeferredReward` → `getDeferredRewardFull` → `getDeferredRewardFullKore` (or `Flex`) → `specWithProposerAndFunds` → `cn.Split` → **panic: integer divide by zero** [6](#0-5) 

### Impact Explanation

`FinalizeState` is called at the end of every block. A Go runtime panic in `big.Int.Div` is unrecovered in this path and crashes the node process. Every honest node that imports the block containing this proposer will crash during finalization, causing a complete halt of block processing and consensus divergence. All KAIA block rewards for that block are lost (never credited), and the chain cannot advance until the node is restarted and the block is re-processed — which will panic again on the same block, creating a permanent chain halt for affected nodes.

### Likelihood Explanation

Post-Prague hardfork, any validator registered in both the AddressBook and CLRegistry with sub-1-KAIA balances in both contracts satisfies the trigger. In the permissioned era (Prague active, permissionless not yet active), AddressBook entries are admin-controlled, but CLRegistry registration may be self-service. Even in the permissioned path, a validator whose staking contract was drained to dust (< 1 KAIA) while a CL pool entry with < 1 KAIA exists is sufficient. The rounding-down conversion (`/ params.KAIA`) makes this easy to reach accidentally or deliberately.

### Recommendation

Add a zero-total guard in `consolidatedNode.Split` before dividing:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    cnAmountBig := big.NewInt(int64(c.StakingAmount))
    clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)
    if totalAmount.Sign() == 0 {
        // Both staking amounts rounded to zero; give everything to CN.
        return amount, big.NewInt(0)
    }
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)
    cnAmount := new(big.Int).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

Alternatively, filter out consolidated nodes with `totalAmount == 0` before calling `Split` in `specWithProposerAndFunds` and `specWithProposerAndFundsFlex`.

### Proof of Concept

1. Deploy a Prague-enabled chain.
2. Register validator `V` in AddressBook with staking contract `S` holding 0.9 KAIA (rounds to `StakingAmount = 0`).
3. Register `V` in CLRegistry with CL pool `P` holding 0.9 KAIA (rounds to `CLStakingAmount = 0`).
4. Wait for `V` to be selected as block proposer.
5. `FinalizeState` calls `getDeferredRewardFullKore` → `specWithProposerAndFunds`.
6. The loop finds `cn` where `cn.RewardAddr == V.rewardbase` and `cn.CLStakingInfo != nil`.
7. `cn.Split(proposer)` is called with `totalAmount = 0 + 0 = 0`.
8. `clAmount.Div(clAmount, big.NewInt(0))` → **runtime panic: integer divide by zero**.
9. Node crashes; all honest nodes processing this block crash identically; chain halts. [7](#0-6)
