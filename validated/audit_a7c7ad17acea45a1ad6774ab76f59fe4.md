### Title
Aquarius LP collateral forfeits external venue rewards to the pool - (File: contracts/controller/src/positions/supply.rs)

### Summary
A user can deposit reward-bearing Aquarius LP tokens through `supply(caller, account_id, spoke_id, assets)`, which transfers the underlying LP token from the user to the shared pool before crediting pool shares. [1](#0-0) [2](#0-1)   
The pool then becomes the LP-token holder, so venue rewards attributable to that collateral accrue to the pool rather than to the depositor. [3](#0-2)   
The pool has no external-reward claim or forwarding path, and rewards requiring the holder's authorization cannot be claimed at all. [3](#0-2) 

### Finding Description
`Controller::supply` accepts arbitrary listed hub assets and routes each payment into `process_deposit`. [1](#0-0)   
`process_deposit` resolves the physical pool address and calls `transfer_amount_measured` from the caller to that pool for every supplied `hub_asset.asset`. [4](#0-3)   
It then invokes `pool_supply_call`, while `LiquidityPool::supply` only accrues the market, mints scaled supply shares, and credits cash. [5](#0-4) [6](#0-5)   
No position field or accounting leg associates subsequently accrued venue rewards with the original LP supplier. [7](#0-6)   
The only outbound claim path is `claim_revenue`, which burns internally tracked market revenue shares and pays the pool owner; it does not claim third-party Aquarius rewards or allocate them to suppliers. [8](#0-7) [9](#0-8) 

### Impact Explanation
All external yield generated by deposited Aquarius LP collateral is permanently unavailable to the depositor. [3](#0-2)   
Rewards that can be permissionlessly pushed become unbooked donations to the shared pool balance, while authorization-gated gauge rewards remain unclaimable. [3](#0-2)   
This is theft or permanent freezing of unclaimed yield rather than loss of collateral principal, so the appropriate severity is Medium. [3](#0-2) 

### Likelihood Explanation
The path is reachable by any unprivileged holder of a listed Aquarius LP token by calling `supply` with that token's `HubAssetKey` and a positive amount. [1](#0-0) [10](#0-9)   
Exploitation does not require another attacker because the normal deposit itself changes the reward-bearing token's holder to the pool. [11](#0-10) [3](#0-2)   
Materiality depends on the listed LP token continuing to accrue external venue rewards. [3](#0-2) 

### Recommendation
Either do not list reward-bearing LP tokens as collateral, or add an explicit owner-governed reward-claim path that the pool can authorize and that forwards rewards to an accumulator for accounting and distribution. [12](#0-11) [3](#0-2)   
The implementation should distinguish external reward tokens from market cash and collateral balances, and should define how accrued rewards are allocated across the suppliers whose LP custody generated them. [2](#0-1) [13](#0-12) 

### Proof of Concept
1. Governance lists an Aquarius LP token under a `HubAssetKey`, and Alice calls `Controller::supply(alice, 0, spoke_id, vec![(lp_key, lp_amount)])`. [1](#0-0) 
2. The controller transfers `lp_amount` of the LP token from Alice to the physical pool and credits Alice only scaled supply shares. [2](#0-1) 
3. Aquarius treats the pool address as the LP holder, so subsequent venue rewards accrue to the pool rather than Alice. [3](#0-2) 
4. Permissionlessly pushable rewards can only become an unbooked pool donation, while gauge rewards requiring pool authorization cannot be claimed because the pool exposes no corresponding claim method. [3](#0-2) 
5. Alice's later `withdraw` can recover her collateral through the normal pool withdrawal path, but no operation returns the forgone venue rewards to her. [14](#0-13) [15](#0-14)

/// Withdraws for an authorized owner/delegate and checks post-pool solvency.
/// Zero requests withdraw all; returns the pool's actual payouts per asset.
pub(crate) fn process_withdraw(
    env: &Env,
    caller: &Address,
    account_id: u64,
    withdrawals: &Vec<HubPayment>,
    to: Option<Address>,
) -> Vec<HubPayment> {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_payments(env, withdrawals, payments::ZeroLeg::MeansAll);

    let paid = settle_withdraw(env, &mut account, &recipient, &aggregated, &mut cache);
    let _ = enforce_post_pool_solvency(env, &mut cache, &mut account);

    finalize_position_flow(
        env,
        account_id,
        &account,
        &mut cache,
        PositionSides::Supply,
        true,
    );
    paid

**File:** docs/explanation/threat-model.md (L129-140)
```markdown
One token listed in several hubs shares physical pool custody even though
market books are separate. Direct donations do not rewrite those books.
Cash flash loans impose exact balance transitions and allowance repayment;
receipt-tax compatibility elsewhere does not establish flash-loan compatibility.

Aquarius LP collateral earns venue rewards for its holder, which is the pool.
The pool has no entrypoint to claim or forward them. The venue's reward claim
did not require the holder's authorization when reviewed (mainnet simulation,
2026-09), so any caller can push accrued rewards into the pool address as an
unbooked donation. Gauge rewards need the pool's authorization and therefore
cannot be claimed at all. Suppliers of LP collateral should expect no venue
rewards; this is forgone yield, not a loss of principal.
```
