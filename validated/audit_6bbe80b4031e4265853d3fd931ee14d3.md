### Title
Unbounded native call-stack recursion in address/asset definition evaluation causes stack overflow (DoS) - ([File: definition.js])

### Summary
`definition.js`'s `evaluate()` functions inside `validateDefinition()` and `validateAuthentifiers()` recursively evaluate nested `and`/`or`/`not`/`r of set`/`weighted and`/`address` boolean-expression trees using synchronous callback chains (`async.eachSeries` with immediately-invoked callbacks). Unlike the formula engine (`formula/validation.js`, `formula/evaluation.js`) and the AA-definition validator (`aa_validation.js`), which explicitly interrupt recursion every 100 calls via `setImmediate` and/or track an explicit `depth` counter capped at a maximum, `definition.js`'s `evaluate()` has **no such call-stack-interruption or depth cap** — it only tracks a `complexity`/`count_ops` budget, which limits the total number of nodes visited but not the *depth* of a purely linear (e.g., chained `not`) nesting. A single unprivileged unit poster (defining a new address), an asset issuer (defining `issue_condition`/`transfer_condition`), or an AA author embedding a nested address/asset definition can submit a deeply and narrowly nested definition (e.g., `['not', ['not', ['not', ... ]]]`) that stays under the complexity/ops budget while driving the recursive `evaluate()` call chain to a depth that exhausts the V8 call stack (`RangeError: Maximum call stack size exceeded`), crashing or hanging the validating node process for every full node (and every light wallet verifying signatures via `validateAuthentifiers`) that processes the unit.

### Finding Description
`definition.js` defines two structurally similar recursive evaluators over the address/asset-condition AST:
- `validateDefinition()`'s inner `evaluate()` [1](#0-0) , which recurses through `and`/`or`/`r of set`/`weighted and`/`not`/`address` cases using `async.eachSeries` [2](#0-1)  and `not` [3](#0-2) .
- `validateAuthentifiers()`'s inner `evaluate()` [4](#0-3) , with an equivalent `not` case [5](#0-4) .

Both only guard against runaway *complexity* (total node count) via `complexity`/`count_ops` counters bounded by `constants.MAX_COMPLEXITY`/`constants.MAX_OPS` [6](#0-5) , but neither guards against runaway *depth*. A chain of `not` nodes (or a minimally-branching `and`/`or` chain) increases `complexity` by exactly 1 per nesting level, so an attacker can build a definition whose nesting depth is as large as `MAX_COMPLEXITY` (and similarly bounded by `MAX_OPS`) while each level adds a full JavaScript stack frame (plus the `async.eachSeries` wrapper frames) to the native call stack — because each `cb`/`cb2` in the chain is invoked synchronously, not deferred.

Contrast this with the two other recursive validators in the same codebase that were explicitly hardened against exactly this bug class:
- `formula/validation.js`'s `evaluate()` interrupts every 100 calls with `setImmediate` and additionally enforces `depth > 100` → `"maximum depth exceeded"` [7](#0-6) .
- `aa_validation.js`'s `validate()` similarly checks `depth > MAX_DEPTH` and interrupts every 100 calls with `setImmediate` [8](#0-7) .
- `formula/evaluation.js`'s `evaluate()` interrupts every 100 calls with `setImmediate` to avoid "extra long call stacks" [9](#0-8) .

`definition.js`'s two `evaluate()` functions have no equivalent protection, making them the outlier.

This evaluator is reached from ordinary, unprivileged unit posting via `validateAuthor()` in `validation.js`, which calls `Definition.validateAuthentifiers()` on the address's definition when validating a unit's signatures [10](#0-9) , and from asset issuance/transfer condition validation via `validateAssetDefinition()`, which calls `Definition.validateDefinition()` directly on attacker-supplied `issue_condition`/`transfer_condition` [11](#0-10) . It is also reachable via private/signed-message validation (`signed_message.js`) which calls `Definition.validateAuthentifiers()` on a definition supplied inline by the message's author [12](#0-11) .

### Impact Explanation
Every node (and light client) that validates a unit containing such a deeply/narrowly-nested address definition, or an asset with such an `issue_condition`/`transfer_condition`, will attempt to run the vulnerable recursive `evaluate()` and can crash with an uncaught `RangeError: Maximum call stack size exceeded`. Because address/asset/definition validation happens uniformly across all full nodes as part of standard unit/DAG validation, a single maliciously crafted unit can be broadcast and processed by the entire network, causing repeated node crashes/denial of service and preventing the network from confirming new units — matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
An unprivileged actor can trigger this purely by posting a new unit that defines an address (or asset issue/transfer condition) with a deeply nested chain of cheap ops (`not`, or minimally-branching `and`/`or`), staying within the `MAX_COMPLEXITY`/`MAX_OPS` limits enforced at the top of `evaluate()`. No special privileges, existing balances, or cooperation from other parties are required — only the ability to post a unit, which is the baseline capability of any user of the network.

### Recommendation
Add the same defenses already used elsewhere in the codebase to `definition.js`'s two `evaluate()` functions:
1. Track an explicit recursion `depth` parameter, incremented on each recursive `evaluate()` call, and reject with an error once it exceeds a safe maximum (mirroring `aa_validation.js`'s `MAX_DEPTH` check and `formula/validation.js`'s `depth > 100` check).
2. Periodically yield the call stack (e.g., every N evaluations) via `setImmediate`, as already done in `formula/evaluation.js`, `formula/validation.js`, and `aa_validation.js`'s `validate()`.
3. Apply the fix consistently to both `validateDefinition()`'s and `validateAuthentifiers()`'s `evaluate()` implementations, since both are reachable from unit/asset/signed-message validation paths.

### Proof of Concept
Construct an address definition (or asset `issue_condition`/`transfer_condition`) consisting of a long chain of nested `not` operators wrapping a single `sig` leaf, e.g. programmatically:
```
def = ['sig', {pubkey: <valid pubkey>}]
for i in range(DEPTH):        # DEPTH chosen close to constants.MAX_COMPLEXITY / MAX_OPS
    def = ['not', def]
```
Post a unit whose author uses this address (chash160 of `def`) as its `definition`, or an asset definition using this as `issue_condition`. When any node calls `validateAuthor()` → `Definition.validateAuthentifiers()` (or `validateAssetDefinition()` → `Definition.validateDefinition()`) on this structure, the synchronous recursive `evaluate()` calls will build up native call-stack frames proportional to `DEPTH`; with `DEPTH` chosen large enough (bounded only by the complexity/ops budget, not by any depth cap), this results in `RangeError: Maximum call stack size exceeded` during validation of the unit — verifiable by comparing to the existing hardened `not` handling in `aa_validation.js`/`formula/validation.js`, whose explicit depth checks were added precisely to prevent this failure mode in sibling recursive evaluators.
