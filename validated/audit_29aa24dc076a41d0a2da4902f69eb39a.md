### Title
Webhook signature verification is keyed on `repository.owner.login`, but event handlers act on `repository.full_name` - a valid signature from one configured GitHub organization can be replayed against another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the JSON body itself. Once the signature is accepted, `Shipit::Webhooks::Handlers::Handler#stacks` (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack` using a *different* field from the same body: `repository.full_name`. Nothing ties these two fields together, so a payload can be crafted where the "owner" used to pick the verifying secret differs from the "repository" that is actually acted upon.

### Finding Description
`verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The signature is checked against the secret for whichever organization `repository.owner.login` claims to be. Handlers, however, resolve the affected repository/stack independently:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler` then directly mutates state for whatever stack it resolves:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

Shipit supports multiple configured GitHub organizations, each with its own `webhook_secret` (`TOP_LEVEL_GH_KEYS` includes `webhook_secret` per org) [4](#0-3) , and each organization's admin obtains their own app's `webhook_secret` from their GitHub App settings (per `docs/setup.md`) [5](#0-4) .

Binding that should hold: `organization authenticated by HMAC == organization/repository whose Stack is written`. Before the attack: an org "attacker-org" only has authority to sign/deliver webhooks whose `repository.owner.login` is `attacker-org`, and Shipit is trusted to only mutate `attacker-org`'s own stacks in response. After the attack: because `verify_signature` derives the secret from `repository.owner.login` while `Handler#repository_name` reads `repository.full_name`, the org that authenticated (`attacker-org`, whose secret validates the HMAC) is decoupled from the repository actually written to (`victim-org/victim-repo`, taken from `full_name`). An administrator (or anyone with access to that org's app webhook secret) of any organization configured in the same Shipit instance can forge a payload with `repository.owner.login = "attacker-org"` (so the signature check passes with the attacker's own secret) and `repository.full_name = "victim-org/victim-repo"` (so the handler acts on a completely different tenant's stack), since nothing cross-validates that `full_name`'s owner segment matches `owner.login`.

### Impact Explanation
This is a cross-repository/cross-tenant write: an org that legitimately authenticated (proved knowledge of its own webhook secret) can cause Shipit to execute handler logic — e.g. `PushHandler#process` calling `stack.sync_github(expected_head_sha: ...)` on `victim-org`'s stack, or the `status`/`check_suite` handlers writing check/status records for `victim-org`'s commits — none of which the attacker's organization owns or has any GitHub-side authorization over. In deployments where `continuous_deployment` is enabled on the victim stack, syncing/forging head SHAs and injected commit metadata can influence what gets considered "deployable" and trigger `ContinuousDeliveryJob` against the victim's stack, which maps to "an unauthorized deploy" as covered by the rules. This satisfies the required High-tier impact: escalation across a repository/authentication boundary leading to unauthorized state changes / potential unauthorized deploy on a stack the caller does not own.

### Likelihood Explanation
Requires only that Shipit is configured to serve more than one GitHub organization (a documented, supported feature: `config/secrets.development.example.yml` shows the multi-org config block) [6](#0-5)  and that the attacker controls (as an admin) any one of those organizations' GitHub Apps, which is enough to obtain that org's own `webhook_secret` and sign arbitrary payloads. No repository write access, GitHub App private key, or Shipit-side credentials for the victim organization are required — only knowledge of the attacker's own org's webhook secret, which is not privileged with respect to any *other* tenant's data.

### Recommendation
After signature verification succeeds, cross-check that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` (and any other org-identifying field used later, e.g. in `Team`/`User` webhook handlers) before dispatching to handlers; reject the webhook (422) if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret`, both tracked as stacks in the same Shipit instance (supported per `config/secrets.development.example.yml` multi-org block).
2. As an admin of `attacker-org`, obtain `attacker-org`'s `webhook_secret` from the GitHub App settings.
3. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw_post)>` and POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature using `attacker-org`'s secret [7](#0-6) .
6. `PushHandler` resolves `stacks` via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on `victim-org`'s stack [3](#0-2) [2](#0-1) , even though only `attacker-org`'s credential was ever proven.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
