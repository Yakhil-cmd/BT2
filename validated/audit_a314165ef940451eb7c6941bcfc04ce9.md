## Analysis

The Cooler bug class is: an asset is returned to an address via a path that is *supposed to be terminal/destroyed*, but the higher-level accounting that governs later logic doesn't know it's unusable, so downstream code (built on that stale accounting) misbehaves — in Cooler's case, silently not burning collateral that a "trusted" path would have burned.

`ocore` has an exact structural analog in the `auto_destroy` asset feature used by Autonomous Agents (AAs).

**Root cause chain:**

1. Protocol-level rule: once an `auto_destroy` asset output is sent to `definer_address`, it can never be spent again — any attempt to use it as a `transfer` input from that address is rejected: [1](#0-0) [2](#0-1) 

2. When an AA *is* the `definer_address` of such an asset, `aa_composer.js` explicitly recognizes that none of the asset's holdings at that address are spendable and returns an empty set of candidate inputs entirely for that asset: [3](#0-2) [4](#0-3) 

3. However, nothing prevents the *accounting* (`aa_balances` / the `balance[asset]` value read by oscript formulas) from including these permanently-frozen holdings. Any payment of the `auto_destroy` asset sent back to the AA (analogous to gOHM being sent back to the ClearingHouse) increases the AA's tracked balance the same way any other incoming payment does — the balance-update logic in `handleTrigger`/`updateFinalAABalances` makes no distinction for `auto_destroy` funds returned to the definer: [5](#0-4) 

4. If the AA's oscript logic pays out `balance[asset]` (a very common pattern, e.g. "send all"), the composer cannot find the reported balance as spendable inputs (step 2 zeroes them out), so it falls back to `issueAsset()`. For assets without a `cap`, this function will silently mint (`type: "issue"`) whatever amount is needed to make up the shortfall, since the AA is the definer: [6](#0-5) 

**Impact:** an AA that is the definer of an uncapped, `auto_destroy` asset — and that uses `balance[asset]` in its payment logic (a standard, idiomatic oscript pattern, seen throughout the sample contracts, e.g. `uniswap_like_market_maker.oscript` and `option_contract.oscript`) — will silently over-issue (inflate) the asset supply whenever users send that asset back to the AA's own address, because the accounting layer counts the destroyed funds as part of `balance[asset]` while the composer cannot actually spend them and compensates by minting fresh supply instead of bouncing or excluding the phantom balance. This is a genuine, unbounded supply-inflation bug reachable by any unprivileged user simply sending an `auto_destroy` asset payment to an AA that happens to be its definer.

### Title
Uncapped `auto_destroy` Asset Balance Wrongly Counted as Spendable Leads to Unbounded Re-Issuance by the Defining AA - (File: aa_composer.js)

### Summary
When an Autonomous Agent is the `definer_address` of an `auto_destroy` asset, any units of that asset sent back to the AA become permanently unspendable by protocol rule, yet they remain part of the AA's reported `balance[asset]`. If the AA's oscript relies on `balance[asset]` to decide payout amounts, the payment composer cannot source the reported balance from spendable inputs and instead falls back to auto-issuing (minting) new supply to cover the difference for uncapped assets.

### Finding Description
`validation.js` enforces that an `auto_destroy` asset's output, once sent to the definer's address, can never again be used as a spend input [1](#0-0) . `aa_composer.js` correctly recognizes this and excludes all such holdings from the candidate-input pool when composing an AA response, returning an empty result for the whole asset at that address [3](#0-2) . However, the AA's balance bookkeeping (`aa_balances`, and the `balance[asset]` value exposed to oscript formulas) treats every output ever received at the AA's address the same way, without excluding these permanently-frozen `auto_destroy` funds [5](#0-4) . When the AA's logic subsequently tries to pay out `balance[asset]` and the composer can't find spendable inputs matching the reported balance, `issueAsset()` mints new supply on the fly to close the gap for assets without a `cap` [6](#0-5) .

### Impact Explanation
This produces genuine, unbounded supply inflation of an asset defined by an AA: an unprivileged sender can trigger inflation simply by paying an `auto_destroy` asset back to the AA that defines it, inflating `balance[asset]` and thereby causing the AA to auto-mint replacement supply whenever a `balance[asset]`-based payout logic executes. This directly parallels the Cooler finding where collateral sent through an alternate path is not burned as the primary accounting path assumes, corrupting supply/accounting invariants.

### Likelihood Explanation
Any user can post a normal `payment` message sending the `auto_destroy` asset to the AA's own address — no privileged role is required. `balance[asset]`-based payout patterns ("send-all" style) are common and idiomatic in oscript (seen in sample contracts such as `uniswap_like_market_maker.oscript`), making the vulnerable pattern realistic for AA authors relying on documented `balance[]` semantics without being aware `auto_destroy` breaks the spendable/accounted-balance equivalence.

### Recommendation
Exclude `auto_destroy` holdings at the definer's own address from `aa_balances`/`balance[asset]` reporting (mirroring the exclusion already implemented in `readStableOutputs`/`readUnstableOutputsSentByAAs`), so oscript formulas never see a balance that is not actually payable, and remove the implicit fallback to `issueAsset()` when a `balance[asset]`-driven payout cannot be satisfied from genuinely spendable coins.

### Proof of Concept
1. Deploy AA `A` that defines asset `X` with `is_transferrable: true, auto_destroy: true, issued_by_definer_only: true` and **no `cap`**.
2. `A`'s trigger logic includes a message paying out `{address: trigger.address, amount: balance[X]}` for `asset: X`.
3. User `U` sends a normal payment of `X` (amount `N`) directly to `A`'s address (not through any special AA function) — this is equivalent to "gOHM sent to ClearingHouse" — the funds land at `A` (the asset's definer), making them permanently unspendable per `validation.js` (`auto_destroy` + `definer_address` rule).
4. `A`'s `aa_balances` for asset `X` increases by `N` (per `aa_composer.js:543-587`), so `balance[X]` in any subsequent trigger execution reports the inflated (but unspendable) figure.
5. Any subsequent trigger causes `A` to attempt to pay `balance[X]`; `readStableOutputs`/`readUnstableOutputsSentByAAs` return no spendable inputs for `X` (`aa_composer.js:1140-1173`), so `issueAsset()` mints `N` additional units of `X` to satisfy the payout (`aa_composer.js:1175-1212`) — inflating the total circulating supply of `X` by `N` beyond what was ever legitimately backed.

					var input = {

						amount: issue_amount,

					payload.inputs.unshift(input);
					total_amount += issue_amount;
					var change_amount = total_amount - target_amount;
