### Title
Uncontrolled memory allocation when decrypting device messages before size/nesting validation - ([File: device.js])

### Summary
`device.js`'s `decryptPackage()` performs base64-decoding and AES-GCM decryption of an attacker-supplied `encrypted_message` field before any bound is placed on its size, allowing an unpaired or paired correspondent to force a node/wallet to allocate arbitrarily large buffers, mirroring the Mattermost CWE-789 pattern of unbounded memory allocation while processing an untrusted payload.

### Finding Description
When a device message arrives via the hub (`hub/message` justsaying), `device.js` validates only structural presence of fields, not size: [1](#0-0) 
It then calls `decryptPackage(objDeviceMessage.encrypted_package)`: [2](#0-1) 

Inside `decryptPackage`, the `encrypted_message` string (fully attacker-controlled, base64-encoded) is converted straight into a `Buffer` with no length cap, and then walked in fixed-size chunks through the decipher, meaning the total allocation (`enc_buf`, the array of decrypted chunks, and the final `Buffer.concat`) scales linearly and unboundedly with whatever size the sender chooses to send: [3](#0-2) 

The only guard applied before this point is a shape/nesting check, `isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000)` — but this is applied only in `wallet.js`'s `handleMessageFromHub` *after* `decryptPackage` has already succeeded and produced the parsed JSON, i.e., after the unbounded allocation has already happened: [4](#0-3) 

On the hub side (`network.js`, `hub/deliver`), there is likewise no bound on `encrypted_package.encrypted_message` length before it is hashed, JSON-stringified, and stored/broadcast; `isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)` bounds node *count*/*depth*, not the raw string length of `encrypted_message`: [5](#0-4) 

Crucially, delivery to a *non-correspondent* device is explicitly allowed for certain subjects (e.g., `pairing`, `my_xpubkey`, `wallet_fully_approved`), so this path is reachable by any unpaired remote peer, not just an already-trusted correspondent: [6](#0-5) 

There is no equivalent to `constants.MAX_UNIT_LENGTH` (used for on-chain units) applied to device messages' `encrypted_message` payload size anywhere in this pipeline.

### Impact Explanation
An attacker (any device that can reach the hub, or any correspondent) can repeatedly send oversized `encrypted_package.encrypted_message` payloads to a victim's paired/hub-connected wallet or hub node. Each such message forces allocation of buffers proportional to the attacker-chosen size (limited only by the underlying WebSocket/HTTP framework's own frame/message limits, which are not enforced in application logic here) before any application-level size check occurs. Repeated or concurrent delivery can exhaust process memory, causing the wallet/hub process to crash or become unresponsive — a denial-of-service against the node's ability to process device/contract messages (in scope per the "wallet and contract message handling" category).

### Likelihood Explanation
Reachability is straightforward: the `hub/deliver` command is accepted from any WebSocket peer that presents a syntactically valid `objDeviceMessage`, and specific subjects (`pairing`, `my_xpubkey`, `wallet_fully_approved`) are explicitly processed even from unknown/non-correspondent senders. No authentication beyond signature-verification-after-parsing/allocation is required, and no length limit gates the vulnerable code path. This makes exploitation low-effort for any network participant.

### Recommendation
Enforce a maximum length on `objDeviceMessage.encrypted_package.encrypted_message` (and `iv`/`authtag`) both at the hub ingress (`network.js` `hub/deliver`) and at the client's `decryptPackage()` entry point in `device.js`, rejecting oversized messages before any base64 decoding, buffer allocation, or decryption occurs — analogous to `constants.MAX_UNIT_LENGTH` used for units.

### Proof of Concept
1. Attacker crafts an `objDeviceMessage` with a valid signature/pubkey/`to` address but with `encrypted_package.encrypted_message` set to a very large base64 string (e.g., hundreds of MB), and `dh`/`iv`/`authtag` fields populated with plausible dummy values.
2. Attacker sends this via `hub/deliver` to a hub, or directly as `hub/message` justsaying to a victim client.
3. On the recipient side, `device.js`'s `handleJustsaying` → `decryptPackage()` executes `Buffer.from(objEncryptedPackage.encrypted_message, "base64")`, allocating a buffer sized to the attacker's input before signature/decryption failure is even reached in some code paths, and regardless of ultimate decryption failure, the allocation has already occurred.
4. Repeating this rapidly from one or multiple connections exhausts memory on the victim node/wallet process.
