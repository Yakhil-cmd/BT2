### Title
Cross-Organization Team Membership Forgery via `membership` Webhook Grants Unauthorized Access to `Shipit.github_teams` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The bug class in the report is a mismatch between the entity a signature/authorization check is bound to and the entity actually mutated by the operation it authorizes. In `shipit-engine`, `WebhooksController#verify_signature` selects and validates the webhook HMAC using the **organization identified in the payload itself**, but the `membership` webhook handler then writes to a `Team` record looked up purely by a GitHub-supplied numeric `github_id`, with no check that this `Team` actually belongs to the organization that produced the verified signature. An attacker who controls *any* GitHub organization with the Shipit GitHub App installed (a normal, unprivileged, self-service action) can forge a `membership` "added" webhook, signed with their own organization's known `webhook_secret`, that targets the `github_id` of a privileged `Team` belonging to a *different* organization — the one backing `Shipit.github_teams` — and add an arbitrary GitHub login as a member of that team inside Shipit's database.

### Finding Description
`WebhooksController#verify_signature` derives the app/secret to check the signature against from the payload's own organization field, with a fallback specifically used by `membership` events: [1](#0-0) [2](#0-1) 

Because `Shipit.github(organization: ...)` supports multiple independently configured GitHub Apps/organizations (each with its own `webhook_secret`), signature verification only proves "this request was sent by whoever administers the GitHub App on `organization.login`" — it says nothing about which `Team`/repository the payload subsequently references.

`MembershipHandler` then processes the event by looking up (or creating) a `Team` solely by the numeric `github_id` supplied in the payload: [3](#0-2) 

`find_or_create_by!(github_id: params.team.id)` will **find** any pre-existing `Team` row that matches that `github_id`, regardless of its `organization` column — the `organization.login` from the payload is only applied inside the `do |team|` block, which ActiveRecord only runs on **creation**, not when an existing record is found. If the `github_id` in the forged payload coincides with the `github_id` of a `Team` already present in Shipit's database (e.g., a team backing `Shipit.github_teams`, created via `Team.find_or_create_by_handle`/`fetch_and_create_from_github`), the handler resolves to that existing, privileged `Team` object: [4](#0-3) 

The handler then does `team.add_member(member)` where `member` is a `User` created purely from an attacker-supplied `login` string: [5](#0-4) [6](#0-5) 

This `Team` membership is exactly what gates application access: `Shipit::Authentication#force_github_authentication` calls `current_user.authorized?`, which is `true` if the user belongs to any team in `Shipit.github_teams`: [7](#0-6) [8](#0-7) 

**Equality broken:** the organization that authenticated the webhook request (`organization.login` used to select `webhook_secret` in `verify_signature`) must equal the organization owning the `Team` actually mutated by the handler (`Team#organization`, used only on `Team` creation, never checked on lookup). Because `MembershipHandler#find_or_create_team!` keys exclusively off `github_id` for lookup, this equality is not enforced, letting an attacker's own (unprivileged, self-administered) organization authenticate a mutation against a `Team` that belongs to and gates a completely different organization's Shipit deployment.

### Impact Explanation
Once an attacker-chosen GitHub login is added as a member of a `Team` present in `Shipit.github_teams`, any real GitHub user with that login who authenticates via `GithubAuthenticationController#callback` (standard OAuth login, no special privileges required) becomes `authorized?` in the target Shipit instance: [9](#0-8) 

This is an authorization-boundary bypass — escalation into `Shipit.github_teams` authorization — which per the scoring rubric is a **High** severity finding (unauthenticated/unauthorized escalation into the app's team-based access control), and downstream could enable the attacker to trigger deploys, rollbacks, or custom tasks (via `TasksController`/`DeploysController`, which are gated by the same `Shipit.github_teams` check) — an unauthorized deploy/rollback path.

### Likelihood Explanation
The attacker only needs: (1) to control any GitHub organization with the Shipit GitHub App installed and know that org's own `webhook_secret` (trivially true — they set it up themselves as a normal, self-service app installation, exactly as documented in `docs/setup.md`), and (2) to know or guess the numeric `github_id` of the target `Team`. GitHub team IDs are small sequential integers and can be discovered in various ways (via GitHub's API for teams the attacker has any visibility into, via other webhook deliveries, or by brute-forcing a modest ID space), making this feasible without any credential belonging to the victim Shipit deployment or its organization.

### Recommendation
In `Team.find_or_create_by!`, scope the lookup by both `github_id` **and** `organization` (i.e., `find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally have `MembershipHandler` verify that `params.organization.login` matches the `organization` already associated with the found `Team` before performing `add_member`/`members.delete`. More generally, `WebhooksController#verify_signature` should ensure that every entity referenced later by a given event's handler (team, organization, repository) is consistent with the organization whose secret validated the signature, rather than allowing handlers to trust unrelated payload fields.

### Proof of Concept
1. Attacker creates/administers `attacker-org` on GitHub and installs the Shipit GitHub App there, configuring Shipit (multi-org config) with a known `webhook_secret` for `attacker-org` (a normal, self-service setup step, e.g. as shown in `test/dummy/config/secrets_double_github_app.yml`-style configuration referenced in `Shipit.github(organization:)`).
2. Attacker discovers the numeric GitHub `github_id` of the `Team` backing the target Shipit instance's `Shipit.github_teams` (e.g., `shopify/developers`).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": { "id": <target_team_github_id>, "name": "developers", "slug": "developers", "url": "https://api.github.com/teams/..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-github-login" }
}
```
   signed with `X-Hub-Signature: sha1=<hmac(attacker-org webhook_secret, body)>`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"attacker-org"` (no `repository` key on membership events), calls `Shipit.github(organization: "attacker-org")`, and the signature validates successfully because the attacker knows this secret.
5. `MembershipHandler#process` executes `Team.find_or_create_by!(github_id: target_team_github_id)`, matching the pre-existing privileged team, and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
6. Attacker logs into the target Shipit instance via GitHub OAuth as `attacker-github-login`; `current_user.authorized?` now returns `true` due to the forged team membership, granting full authenticated access to stacks, deploys, and tasks.

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
