### Title
Cross-organization/cross-repository Status forgery leading to unauthorized deploy scheduling - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check in `Shipit::WebhooksController` selects *which* organization's secret to verify against using an attacker-supplied field of the payload itself, and silently accepts unsigned payloads for any organization that has no `webhook_secret` configured (an explicitly documented, supported setting). Once verified against that (possibly secret-less) organization, `Shipit::Webhooks::Handlers::StatusHandler` applies the `status` event to **any** `Commit` in the whole Shipit instance that matches the raw `sha` field, with no check that the commit belongs to the repository/organization that actually authenticated the webhook. This breaks the equality "organization authenticated == repository/commit written," letting an attacker who controls (or who is handed) any org configured on the Shipit instance with no `webhook_secret` inject a fabricated `success` CI status onto a commit belonging to a completely different, unrelated stack, triggering `Commit#add_status` → `stack.schedule_merges`, i.e. an unauthorized deploy/merge trigger.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration to validate the HMAC signature against using `repository_owner`, computed purely from the JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret` is documented as optional per-organization configuration, e.g. in setup docs and default templates: [4](#0-3) [5](#0-4) 

Once the request passes this check for *any* configured organization (including one the attacker controls or one with a blank secret), `WebhooksController#create` dispatches the raw JSON to the matching handler based solely on `X-Github-Event`, with no re-validation that the payload's target repository matches the organization that authenticated it: [6](#0-5) 

`StatusHandler#process` then looks up commits **globally by `sha` only** — it never scopes to a repository, stack, or the authenticating organization: [7](#0-6) 

Applying a status update flows into `Commit#add_status`, which can schedule merges/deploys when the new status is `pending` or `success`: [8](#0-7) 

The broken binding, stated as an equality that should hold but doesn't:
`organization authenticated by verify_signature` == `repository/stack whose Commit is mutated by StatusHandler`.
Before the attack: these are always equal in a legitimate GitHub-originated webhook, because GitHub always signs the payload it sends about the org/repo it targets. After the attack: an attacker can present a payload validated for organization X (no secret, or one they legitimately administer) while the `sha` in the body belongs to a Commit under an entirely unrelated organization Y's stack — `StatusHandler` will still mutate Y's commit.

### Impact Explanation
This allows an unprivileged network attacker (no Shipit session, no `ApiClient` token, no GitHub write access to the victim repository) to forge a `success` (or `pending`) CI status on an arbitrary commit belonging to any stack tracked by the Shipit instance, as long as they can get a webhook signature to validate for *some* organization on that instance (trivial for any org configured without a `webhook_secret`, which is a documented, supported configuration). This can flip a stack's `merge_status` and trigger `stack.schedule_merges`, i.e. an **unauthorized deploy/merge trigger** on a repository the attacker has no legitimate relationship to — matching the "Critical: unauthorized deploy, rollback or merge" impact bucket.

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (it's the GitHub webhook intake) and requires no session, API token, or repository access — only knowledge of a target commit `sha` (visible on GitHub) and the ability to have one organization on the multi-tenant Shipit instance configured without a `webhook_secret`, which the project's own docs treat as a normal, optional setting. No race condition, no privileged access, and no reliance on undocumented deployment behavior are required.

### Recommendation
- Scope `StatusHandler` (and any other handler using cross-cutting lookups such as `Commit.where(sha: ...)`) to the repository/organization that authenticated the current webhook request, not just the raw payload's `repository`/`sha` fields.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations lacking a configured secret; require a secret or reject with 422/501 if verification cannot be performed, and consider requiring `X-Hub-Signature-256` with the SHA-256 algorithm.
- Bind the organization used to select the verification secret to an actual trusted GitHub App identity (e.g. installation ID from the request), not to an attacker-controlled JSON field, and cross-check that the target repository's owner matches that organization before executing side effects.

### Proof of Concept
1. Set up (or be handed) a Shipit instance configured with two GitHub orgs, one of which (`attacker-org`) has `webhook_secret` unset, per the documented optional configuration:
```yaml
github:
  attacker-org:
    app_id: ...
    installation_id: ...
    webhook_secret: # nil
  victim-org:
    webhook_secret: some-secret
```
2. Find the `sha` of a commit belonging to a stack under `victim-org/some-repo` (visible via public GitHub history or the Shipit UI).
3. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any garbage), and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"attacker-org"`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit purely by `sha`, calling `create_status_from_github!`, which can set state `success` and trigger `stack.schedule_merges` for `victim-org/some-repo`, entirely bypassing the intended per-organization signature isolation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
