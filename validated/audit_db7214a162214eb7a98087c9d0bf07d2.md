### Title
CCMenu API endpoint bypasses stack-scoped ApiClient authorization, allowing cross-stack disclosure of deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used to render deploy status XML, resolving the target stack directly from the unscoped `Stack` relation instead of from the `ApiClient`-scoped relation that every other API controller uses. This breaks the binding "the stack a token authorizes" == "the stack the request touches", letting a caller holding a token scoped to one stack read the CCMenu status of any stack in the installation.

### Finding Description
`ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . `Shipit::Api::BaseController` enforces this scope centrally: `stacks` restricts the queryable relation to `current_api_client.stack_id` when the client is scoped, and the shared `stack` helper resolves the requested id through that scoped relation: [2](#0-1) 

`StacksController#stack` and `HooksController` (through `stack`) both call `stacks.from_param!`, correctly inheriting this scoping [3](#0-2) .

`CCMenuController`, however, defines its own `stack` method that bypasses `stacks` entirely and resolves the id against the global `Stack` table: [4](#0-3) 

The only authorization check performed before `show` runs is `require_permission :read, :stack`, which only verifies that the string `read:stack` is present in `current_api_client.permissions` — it does not check which stack the permission applies to [5](#0-4) . Since `stack` in `CCMenuController` never consults `current_api_client.stack_id`, any client carrying `read:stack` — including a token deliberately scoped to a single stack via `stack:` on the `ApiClient` record (as in the `here_come_the_walrus` fixture, scoped to `shipit`) [6](#0-5)  — can pass an arbitrary `stack_id` and receive that other stack's CCMenu XML (name, `lastBuildStatus`, `lastBuildLabel`, lock status, etc.).

Binding broken (before → after intended scope enforcement):
`current_api_client.stack_id == requested stack_id` (enforced everywhere else through `BaseController#stacks`) is replaced in `CCMenuController` by `requested stack_id ∈ Stack.all`, i.e. any stack.

### Impact Explanation
This is an authorization-scope escalation: a token intentionally minted and distributed for read access to a single stack (e.g. the CCMenu URL feature, `CCMenuUrlController#client`, which is designed around a single stack's CCMenu URL) [7](#0-6)  can be replayed against `api/:stack_id/cc_menu.xml` for any other stack in the deployment, disclosing deploy/build status, lock state, and stack existence across the whole Shipit instance. This matches the High-severity category "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state" analog called out in scope, since it crosses an authorization boundary that every sibling controller enforces.

### Likelihood Explanation
Exploitation requires only possession of any valid, stack-scoped API token with `read:stack` permission and knowledge/guessing of another stack's numeric id or slug — no signature, secret, or elevated privilege is needed beyond what a legitimately-scoped, low-privilege client already holds. This is a straightforward parameter-substitution attack against a documented, unauthenticated-by-design (basic-auth-token) endpoint.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation defined in `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, so the client's `stack_id` scope is always enforced, consistent with `StacksController` and `HooksController`.

### Proof of Concept
1. An administrator creates (or the CCMenu URL flow creates) an `ApiClient` scoped to `stack: A` with permission `read:stack` (see `here_come_the_walrus` fixture pattern) [6](#0-5) , and shares its token for stack A's CCMenu integration.
2. Using that token, request `GET /api/:stack_id/cc_menu.xml` with `stack_id` set to stack B (a different, e.g. private, stack) instead of stack A.
3. `authenticate_api_client` accepts the token (`ApiClient.authenticate`) and `require_permission :read, :stack` passes because the token has `read:stack` [8](#0-7) .
4. `stack` resolves stack B directly from `Stack.from_param!`, ignoring the client's `stack_id` scope, and the controller renders stack B's deploy/build status XML to the caller [9](#0-8) , confirmed by the existing test only asserting behavior for the client's own stack and never exercising cross-stack denial [10](#0-9) .
