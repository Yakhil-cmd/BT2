## Analysis

This confirms the multi-tenant configuration model: `Shipit.github(organization:)` looks up a **per-organization** config block (`app_id`, `installation_id`, `webhook_secret`, etc.) keyed by GitHub organization login, via `Shipit.github_app_config` [1](#0-0) . Each configured organization has its own independent `webhook_secret`.

The binding that is supposed to hold is:
**`organization whose webhook_secret authenticated the request` == `organization/repository the payload's contents are applied to`.**

- Signature verification selects the secret using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback), and verifies the **raw POST body** HMAC against that org's secret [2](#0-1) .
- The actual repository that GitHub-sync/push processing writes to is resolved independently, from `payload.dig('repository', 'full_name')` inside `Handler#repository_name` / `Handler#stacks`, e.g. in `PushHandler#process` [3](#0-2) [4](#0-3) .

Both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside the same JSON body (whoever owns *any* configured organization's GitHub App can craft an arbitrary JSON payload and sign it with their own legitimate `webhook_secret`). Nothing ties `repository.owner.login` to `repository.full_name`; they are two independent fields that just happen to agree in a genuine GitHub-generated payload. `verify_signature` only proves "this body was HMAC-signed with organization X's secret" — it says nothing about which repository the body's `full_name` field claims to describe.

This is exactly the analog class called out in the rules ("an organization that authenticated versus the repository that is written"), directly paralleling the smart-contract bug where the check (elapsed time) covered less than what the action actually did (spend all incentives) — here the check (HMAC of org X's secret) covers less than what the payload actually claims (an arbitrary `repository.full_name`, `ref`, `after` sha, etc. for any repo Shipit tracks).

## Root cause confirmation

- `WebhooksController#verify_signature` binds trust to `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`), which selects the `GitHubApp` instance/secret used only for HMAC validation.
- `Handler#stacks`/`Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:30-38`) and every handler (`PushHandler`, `StatusHandler`, PR handlers, etc.) resolve the target `Stack`/`Repository` from the unauthenticated `repository.full_name` field of the same payload, with no cross-check that this repository belongs to the organization whose secret validated the signature.
- Because Shipit supports many organizations each with independent App credentials (`github_app_config`, `TOP_LEVEL_GH_KEYS`), a party controlling a legitimately-configured but different organization/GitHub App can produce a validly-signed webhook body whose `repository.full_name` claims to be *any other* repository/stack tracked by the same Shipit instance.

### Title
Webhook Signature Verification Is Scoped to `repository.owner.login` But Not To The `repository.full_name` The Payload Actually Targets - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate an inbound webhook using `repository.owner.login` (or the fallback `organization.login`) from the JSON body, then hands the *entire* raw payload to `Shipit::Webhooks` handlers, which resolve the `Stack`/`Repository` to mutate using the independent `repository.full_name` field of the same payload. Because these two fields are never cross-validated, and Shipit supports multiple organizations each configured with their own valid `webhook_secret`, an attacker who legitimately controls the GitHub App/webhook secret for organization A can forge a webhook payload whose `repository.full_name` names a repository belonging to organization B, and have it processed as authentic against B's tracked stacks.

### Finding Description
`Shipit.github(organization:)` looks up per-organization webhook secrets via `github_app_config`, keyed by organization login [1](#0-0) . `WebhooksController#verify_signature` derives `organization` purely from `repository_owner`, i.e., `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and calls `github_app.verify_webhook_signature` with the raw request body [5](#0-4) [6](#0-5) . This only proves the HMAC matches organization A's secret — a fact entirely under organization A's control since organization A itself possesses that secret.

Once verified, `WebhooksController#create` dispatches the *whole* parsed body to every registered handler for the event type [7](#0-6) . All handlers derive their operating scope from `payload.dig('repository', 'full_name')` via the shared `Handler#repository_name`/`Handler#stacks` methods [3](#0-2) , e.g. `PushHandler#process` looks up `stacks.not_archived.where(branch:)` and calls `stack.sync_github(expected_head_sha: params.after)` [4](#0-3) . Nothing checks that the `full_name`'s owner equals the `repository.owner.login`/`organization.login` used for signature verification.

This breaks the equality: `organization whose secret authenticated the payload == repository the payload's contents actually mutate`.

### Impact Explanation
An attacker who is a legitimate maintainer/admin of organization A's GitHub App installation (i.e., controls A's `webhook_secret`, which is routine and not a privileged Shipit credential) can forge a `push` webhook body claiming `repository.full_name = "OrgB/private-repo"`, `ref = "refs/heads/<branch>"`, and an arbitrary `after` SHA, sign it with A's own secret, and POST it to the shared `/webhooks` endpoint. Shipit will validate the signature against A and then process the payload as an update to OrgB's stack, triggering `GithubSyncJob` and `stack.sync_github(expected_head_sha:)` for a repository/stack the attacker does not own. Depending on subsequent job behavior (fetching from `stack.repo_git_url` using Shipit's own installation credentials for the *real* target repository, appending commits, and eventually invoking `CacheDeploySpecJob`), this can inject attacker-influenced expected SHAs / trigger spurious syncs and deploy-spec cache refreshes against a repository the attacker is not authorized to interact with — a cross-repository/cross-organization state-mutation using the app's own GitHub credentials, matching the "cross-repository writes" / "unauthorized deploy" impact class, since it can influence which commit becomes eligible for deploy tracking on a stack the attacker does not control.

### Likelihood Explanation
Requires the attacker to control a legitimately configured GitHub organization's App/webhook secret within the same multi-tenant Shipit instance — plausible in any deployment supporting more than one organization (this is the documented multi-org config schema in `lib/shipit.rb`). No Shipit session, `ApiClient` token, or private key is needed; only the ability to construct and POST an arbitrary JSON body signed with one's own valid webhook secret to the shared, unauthenticated `/webhooks` endpoint.

### Recommendation
After signature verification, re-derive the repository/organization the payload claims to target and assert it matches (or is a repository actually owned by) the organization whose secret validated the signature, before dispatching to handlers. Concretely, validate `repository.full_name`'s owner segment equals `repository_owner` (and that a `Repository` record for that owner is actually configured under that organization) prior to invoking `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `github_app_config`).
2. As an admin/owner of `OrgA`'s GitHub App, construct a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
   }
   ```
3. Compute `X-Hub-Signature` using `OrgA`'s legitimate `webhook_secret` over the raw body.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the HMAC — the request passes.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for OrgB's stack with the attacker-supplied `expected_head_sha`, despite the request never being signed by OrgB.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
