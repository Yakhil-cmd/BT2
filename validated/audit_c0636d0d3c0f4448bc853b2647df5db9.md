### Title
`Handler#stacks` trusts `payload['repository']['full_name']` independently of the org verified via `X-Hub-Signature`, enabling cross-repository stack triggering — (File: `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature against the GitHub App configured for `repository_owner = params.dig('repository','owner','login')`, but `Handler#stacks` (used by `PushHandler#process`) independently reads `payload.dig('repository','full_name')` to resolve target stacks. These are two separate, attacker-controlled JSON fields in the same POST body that are never cross-checked, and in a multi-org Shipit deployment an org can be configured with no `webhook_secret`, making its signature check a no-op — letting an attacker "verify" against their own unsecured org while pointing `repository.full_name` at a victim org's repo.

### Finding Description
The claimed binding, stated as an equality: `repository_owner_used_for_signature (params.dig('repository','owner','login')) == owner_segment_of(repository_name_used_for_stacks (payload.dig('repository','full_name')))`. Tracing the code shows this equality is never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`: [1](#0-0) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: [2](#0-1) 
- Shipit explicitly supports multi-org configs where each org has its own (optionally blank) `webhook_secret`, as shown in the test fixture `secrets_double_github_app.yml` where both `OrgOne` and `OrgTwo` have `webhook_secret: # nil`: [3](#0-2) 
- Once `verify_signature` passes (trivially, for the attacker's own org with no secret), `WebhooksController#create` forwards the **entire parsed JSON body** — not just the verified org's data — to the handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) 
- `Handler#stacks` and `Handler#repository_name` then read `payload.dig('repository', 'full_name')` — a completely independent JSON key from `repository.owner.login` used above — to resolve the `Repository` and its `stacks`: [5](#0-4) 
- `PushHandler#process` uses that unverified `stacks` scope directly to enqueue `GithubSyncJob` for every matching stack: [6](#0-5) 

Exploit flow: attacker controls (or is granted) an org `attacker-org` configured in Shipit with no `webhook_secret` (a legitimate, supported multi-tenant configuration per `github_app_config`/`github_organizations`: [7](#0-6) ). Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a JSON body where `repository.owner.login = "attacker-org"` (so `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank) but `repository.full_name = "victim-org/repo"` and `ref` matching a real stack's branch under `victim-org/repo`. `PushHandler` resolves `stacks` from `full_name`, matches by branch, and enqueues `GithubSyncJob` for every non-archived matching stack — for a repository/org the attacker never proved control of.

Existing guards do not close this: `drop_unhandled_event` and `check_if_ping` only gate on event type; `ExplicitParameters` (`PushHandler.params`) only validates presence/type of `ref`/`after`, not organizational ownership; there is no code anywhere that compares `repository_owner` (verified) against the owner segment of `repository_name`/`full_name` (used for lookups).

### Impact Explanation
A single forged/unsecured-org webhook request causes `GithubSyncJob` to be enqueued for every non-archived stack of an arbitrary victim repository whose branch happens to match the attacker-supplied `ref` — i.e., a payload/webhook authenticated (trivially) for one repository mutates state tied to another repository's stacks, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." This is repeatable per-request against any victim `owner/repo` and any of its branches, as long as the attacker's own org has a webhook_secret-less (or otherwise attacker-satisfiable) config in the same Shipit installation, and it does not require any Shipit session, API token, or GitHub secret.

### Likelihood Explanation
Requires: (1) a multi-org Shipit installation, (2) at least one org configured with a blank/missing `webhook_secret` (explicitly supported, as evidenced by the test fixture) that the attacker controls or can otherwise trigger a webhook delivery for, and (3) knowledge of the victim's `full_name` and a branch name (both public information for any public repo, or guessable). No GitHub App private key, `secret_key_base`, or other Shipit/GitHub secret is needed. Given these preconditions this is directly executable with a plain unauthenticated POST to `/webhooks`.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController`), require that the owner segment parsed from `payload.dig('repository', 'full_name')` matches the `repository_owner` used to select and verify the webhook signature, and reject/`head(422)` the request otherwise. Alternatively, pass the already-verified `repository_owner` into handlers and have `Handler#stacks` scope lookups by that verified owner rather than re-deriving it from an independent, unverified payload field.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (multi-org secrets fixture, e.g. `secrets_double_github_app.yml`):
```ruby
test "push webhook 'verified' for attacker's unsecured org can trigger sync for a victim repo's stacks" do
  # attacker-org has no webhook_secret configured (see secrets_double_github_app.yml)
  victim_repo   = shipit_repositories(:shipit) # owner/name != "attacker-org"
  victim_stack  = shipit_stacks(:shipit)       # belongs to victim_repo, branch "master"

  request.headers['X-Github-Event'] = 'push'
  body = JSON.parse(payload(:push_master))
  body["repository"]["owner"]["login"] = "attacker-org"       # signature check org
  body["repository"]["full_name"] = victim_repo.github_repo_name # stacks lookup uses this instead

  # No X-Hub-Signature header set / attacker-org has no secret => verify_webhook_signature returns true

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: body["after"]]) do
    post :create, body: body.to_json, as: :json
  end
  assert_response :ok
end
```
Assert on both sides of the equality: `repository_owner` resolved during `verify_signature` (`"attacker-org"`) is not equal to the owner segment of `repository_name` used by `Handler#stacks` (`victim_repo.owner`), yet the job still enqueues for `victim_stack`, proving the org boundary is unenforced.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
