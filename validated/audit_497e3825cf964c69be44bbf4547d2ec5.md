### Title
Reusable L1 BTC lockup proof lets a staker double-count a single Bitcoin lock across multiple non-overlapping bond registrations - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond`'s L1 path credits a staker with `sats-total` (used to compute STX floor, signer weight, and reward share) purely by proving that a Bitcoin output *once* existed with the expected time-lock script, amount, and sufficient `unlock-burn-height`. Neither `validate-l1-lockup` nor `verify-l1-lockups` records that a given (txid, output-index) has already been used to fund a bond membership. The de-duplication list (`seen-outpoints`) is created fresh inside a single call and discarded afterward, so the same immutable, already-mined Bitcoin transaction can be re-submitted as proof in a later, separate `register-for-bond` call once the staker's prior bond position ends.

### Finding Description
`verify-l1-lockups` ( [1](#0-0) ) folds over the caller-supplied `outputs` list with a fresh `seen-outpoints: (list)` accumulator on every invocation. `validate-l1-lockup` checks that `unlock-burn-height` is high enough, that the script/amount match, that the Merkle proof and block header are valid, and that the outpoint hasn't appeared twice **within this same call** ( [2](#0-1) ). There is no persistent, contract-wide map recording which (txid, output-index) pairs have already been consumed by a prior `register-for-bond` call.

The only two guards against reuse are:
- `ERR_ALREADY_REGISTERED` via `bond-overlaps-new-position?` — but this only blocks a *second, temporally overlapping* membership for the same principal ( [3](#0-2) ).
- `verify-bond-rollover-window` — gates a non-overlapping re-registration to the last half-cycle of the ending bond's L1 unlock window.

Neither check verifies that the *underlying Bitcoin UTXO is still time-locked* at the moment of reuse. Because `construct-lockup-output-script` commits the P2WSH to a fixed `unlock-burn-height` baked into the real Bitcoin output ( [4](#0-3) ), a staker who sets that `unlock-burn-height` sufficiently far in the future can satisfy the `>= minimum-unlock-height` requirement of many, or arbitrarily many, subsequent (non-overlapping) bond periods ( [5](#0-4) ). Once the current bond term ends (or the staker explicitly unstakes), they can re-present the exact same historical Merkle-proof/header/txid tuple to a fresh, later `register-for-bond` call. This is accepted because the Merkle proof and header verification only prove that the transaction was mined at some past height — they say nothing about whether the BTC lockup is still active/unspent versus already withdrawn on the Bitcoin chain after its (single, real) `unlock-burn-height` passed.

The result: `sats-total` — and the reward shares, signer weight, and STX-lock floor derived from it via `min-ustx-for-sats-amount` and the per-cycle share bookkeeping — can be credited more than once for a single real Bitcoin lock, without any new BTC ever being locked for the second (or Nth) registration.

### Impact Explanation
This breaks the equality that bond/reward accounting is supposed to preserve: the sats recorded as backing a bond membership (and the resulting signer/reward weight) must correspond to sats that are actually locked on Bitcoin for that membership's term. Reusing a stale proof lets a staker's genuine, one-time BTC lock generate multiple discrete `amount-sats` credits over the contract's lifetime, inflating that staker's share of the reward pool relative to the actual BTC collateral securing the system. This is a double-counting of a commitment (Critical per the rules: "double-counting a commitment or reward"), since other real bond holders' proportional rewards/signer weight are diluted by unbacked sats credited from a Bitcoin lock that no longer secures anything for the new term (and may already have been spent by the owner once the original timelock matured).

### Likelihood Explanation
The attacker needs no special privilege: any allow-listed L1 staker can choose the `unlock-burn-height` embedded in their own P2WSH lockup script when they create it, and nothing in the contract forces that value to correspond only to one specific bond term. Reuse only requires waiting for the staker's own existing membership to end (or roll over) and calling `register-for-bond` again with identical Merkle-proof/header/txid data. All checks that gate the call (`bond-overlaps-new-position?`, `verify-bond-rollover-window`, `verify-not-prepare-phase`) are about *scheduling* non-overlap, not about *outpoint uniqueness*, so a determined staker can plan for this at lockup-creation time.

### Recommendation
Persist consumed L1 outpoints in a contract-wide map (e.g., `l1-lockup-outpoints-used: {txid, output-index} -> bool`) and check/insert into it inside `validate-l1-lockup`, rejecting any outpoint that has already funded a prior bond/stake registration for the life of the contract (not just within the current call). Consider additionally requiring that `unlock-burn-height` fall within a bounded window tied to the specific `bond-index` being registered for, rather than allowing `>=` to be satisfied by an arbitrarily distant timelock.

### Proof of Concept
1. Staker Alice creates one real Bitcoin timelock output using `construct-lockup-output-script(alice, U, staker-unlock-bytes, early-unlock-bytes)`, choosing `U` (the unlock height) far enough in the future to exceed `get-bond-l1-unlock-height` for both bond period `N` and a later bond period `N+6`.
2. Alice calls `register-for-bond(bond-index=N, ..., btc-lockup=ok({outputs:[proof for U], ...}))`. `verify-l1-lockups`/`validate-l1-lockup` accept the proof (script, amount, Merkle proof, header all check out, `U >= get-bond-l1-unlock-height(N)`), crediting `sats-total` sats and opening a bond membership with real STX locked from Alice's own balance ( [6](#0-5) ).
3. Bond `N`'s term ends (or Alice unstakes). No global bookkeeping ever recorded the txid/output-index as consumed.
4. During bond `N+6`'s L1-unlock rollover window, Alice calls `register-for-bond(bond-index=N+6, ..., btc-lockup=ok({outputs:[the SAME proof for U], ...}))`. Because `U >= get-bond-l1-unlock-height(N+6)` still holds and the outpoint dedup list is freshly empty for this call, `validate-l1-lockup` accepts it again, crediting the same `sats-total` a second time and opening a second bond membership/reward-share allocation — even if Alice has since spent the original BTC output on the Bitcoin chain.

(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
