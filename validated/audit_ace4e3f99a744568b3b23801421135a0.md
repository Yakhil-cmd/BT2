### Title
Missing Authorization Check Allows Any Paired Correspondent Device to Trigger Unauthorized Use of a Locally-Hosted Multisig/Shared-Address Signing Key - (File: wallet.js)

### Summary
The Jenkins SSH plugin CVE-2022-30959 root cause is a missing permission check that lets an actor use credentials/keys they were never authorized to invoke. The analog in this repository is in the `"sign"` message handler of `handleMessageFromHub` in `wallet.js`, where the `ifLocal` branch of `findAddress` accepts a remote device's signing request for a locally-held signing path without verifying that the requesting device (`from_address`) is actually a registered cosigner/party for that address, unlike the parallel `ifRemote` branch which does perform this check.

### Finding Description
When a paired device sends a `"sign"` message asking this node to sign a unit at a given `address`/`signing_path`, the handler resolves the address via `findAddress` [1](#0-0) . In the `ifRemote` callback, the code explicitly enforces that the requester is a legitimate cosigner before proxying/forwarding the request: [2](#0-1) 

In contrast, the `ifLocal` callback — invoked when the signing path resolves to a key hosted on this very device — has its equivalent authorization check commented out, with a note that enabling it "would make multilateral signing impossible": [3](#0-2) 

The only checks performed before reaching this point are format/structure validations (valid address, valid signing path, address present among unit authors, valid payload hashes) [4](#0-3)  — none of which verify that `from_address` (the device that actually sent this `"sign"` request) is a device registered against this address's signing paths in `wallet_signing_paths` or `shared_address_signing_paths`. As a result, `findAddress` proceeds straight to `callbacks.ifOk()` and unconditionally emits a `signing_request` event with the fully-formed unsigned unit for local signing [5](#0-4) , relying solely on a UI confirmation dialog on the signer's device rather than a code-enforced authorization check tying the request to a legitimate cosigner identity.

### Impact Explanation
Any correspondent device paired with this wallet (not necessarily a cosigner of the target shared/multisig address) can send a spoofed but well-formed `"sign"` request referencing one of the wallet's own shared/multisig addresses and an arbitrary unsigned unit (including malicious payment outputs). Because there is no server-side authorization check binding the request to a legitimate cosigner for that signing path, the request is accepted and surfaced to the user purely through a UI prompt for confirmation, rather than through a protocol-level check that the request even originates from an authorized party. This is a direct parallel to the missing-permission-check pattern in the reported advisory: the credential (local signing key) can be invoked by an unauthorized party's request. If a user is socially engineered into confirming (e.g., a hostile correspondent, hub, or previously legitimate cosigner that lost their role, disguises a rogue payment as a routine cosigning request), it results in unauthorized spending from a multisig/shared address, i.e., real fund loss.

### Likelihood Explanation
Reachable by any unprivileged paired device (a normal correspondent added via chat/pairing) without needing to be a cosigner of the targeted address — satisfying the "paired device" reachable-actor requirement. Exploitation still requires the victim to click through a confirmation dialog, which limits full automation, but the underlying authorization gap (absence of a cosigner check, deliberately disabled per the code comment) is a genuine violation of the intended access-control model that the parallel `ifRemote` path enforces.

### Recommendation
Re-enable and correctly scope a cosigner authorization check in the `ifLocal` branch of the `"sign"` handler: verify that `from_address` is among the registered device addresses for the specific `wallet`/`shared_address` and `signing_path` being requested (via `wallet_signing_paths` / `shared_address_signing_paths`) before emitting `signing_request`, mirroring the check already present in `ifRemote`. If multilateral signing (different addresses in different messages) legitimately requires broader device sets, restrict the check to "sender is a party to at least one address referenced within `objUnit.authors` or `objUnit.messages`" rather than omitting the check entirely.

### Proof of Concept
1. Attacker pairs their device with the victim's wallet as an ordinary correspondent (no special role).
2. Attacker learns (or guesses) one of the victim's shared/multisig addresses and its `signing_path` (these can leak via prior interactions such as textcoin/contract flows or address sharing).
3. Attacker crafts an `unsigned_unit` with `authors` containing that address and malicious `payment` outputs redirecting shared funds to attacker's address, computing correct payload hashes to pass the structural checks in lines 253–330.
4. Attacker sends a `"sign"` justsaying/message with `subject: "sign"`, `body: {address, signing_path, unsigned_unit}` to the victim's device via the hub.
5. `findAddress` resolves to `ifLocal` (since the key is hosted on the victim's device); no check verifies attacker is a legitimate cosigner; `signing_request` is emitted and displayed to the user.
6. If the user is tricked (e.g., request appears alongside legitimate messages, disguised amounts, or presented in an automated/scripted client without careful UI review) into approving, the malicious unit gets signed and broadcast, resulting in unauthorized spend from the shared address.
