### Title
Hookify `_extract_field` fails to resolve `new_text`/`content` for the `Write` tool, silently bypassing block/warn rules that fire correctly for `Edit` - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` resolves the generic field name `new_text` only to the `Edit`-specific key `new_string`, never falling back to the `Write`-specific key `content`. Because `config_loader.Rule.from_dict` infers `field = 'new_text'` for any legacy `event: file` rule (which is documented to cover `Edit`, `Write`, and `MultiEdit`), a dangerous-content rule that reliably blocks a malicious `Edit` silently returns an empty string — and therefore never matches — when the identical payload is written via `Write`.

### Finding Description
`pretooluse.py` classifies `Edit`, `Write`, and `MultiEdit` uniformly under the `file` event and hands the raw hook JSON (`tool_name`, `tool_input`) to `RuleEngine.evaluate_rules` [1](#0-0) .

For legacy-format rules (the documented "Basic Structure" using a bare `pattern:` field), `config_loader.Rule.from_dict` infers the condition field as `new_text` whenever `event == 'file'`, without distinguishing which of `Edit`/`Write`/`MultiEdit` will actually fire the rule [2](#0-1) . The SKILL.md documentation confirms this is intended to apply uniformly across "Edit/Write/MultiEdit operations" [3](#0-2) .

However, in `_extract_field`, the tool-specific handling for `new_text` only reads the `Edit`-specific key: [4](#0-3) 

- `if field == 'new_text' or field == 'new_string': return tool_input.get('new_string', '')` — for the `Write` tool, `tool_input` contains a `content` key, not `new_string`, so this returns `''`.
- The earlier direct-key fast path (`if field in tool_input`) also fails for `Write`, since the key `new_text` is never literally present in `tool_input` (`content` is the real key) [5](#0-4) .

Back in `_check_condition`, the extracted value is `''` (not `None`), so it is not short-circuited by the `field_value is None` guard, and is passed straight into the operator logic (`regex_match`, `contains`, etc.) [6](#0-5) . Matching a non-empty dangerous pattern against `''` always fails, so `_rule_matches` returns `False` and the rule silently never triggers for `Write` calls, even though the exact same payload written via `Edit` (which correctly resolves to `new_string`) is blocked as intended.

An attacker who can influence Claude's choice of tool (e.g., through prompt injection in repository content, issue/PR text, or normal conversational steering causing Claude to prefer `Write` for a new file instead of `Edit`) can cause identical malicious content to bypass a `block`-action hookify rule that the project relies on, purely by using `Write` instead of `Edit` — both of which are ordinary, unprivileged tool invocations reachable in normal Claude Code operation.

### Impact Explanation
This breaks the safety invariant that a hookify `action: block` rule targeting the `file` event reliably denies the protected operation regardless of which underlying file-editing tool is used. Since hookify is a repo-configured guardrail plugin meant to prevent dangerous writes (e.g., secrets, `eval(`, `dangerouslySetInnerHTML`, sensitive file patterns per its own documentation), the bypass allows the exact operation the rule was written to stop to proceed unblocked when routed through `Write` — a logic-level bypass of a required guard, matching "Logic-level service disruption caused by bypassing a required guard or misbinding security state."

### Likelihood Explanation
- No special privilege is required: any normal Claude session that ends up calling the `Write` tool with content that a `file`-event block rule was meant to catch will trigger this.
- The legacy `pattern:` frontmatter format is the primary documented "Basic Structure" example in `SKILL.md`, making this the common/default rule-authoring path, not an edge case.
- The bug is deterministic and 100% reproducible given a rule and a `Write` invocation with the offending content — no race conditions or timing dependency.

### Recommendation
In `RuleEngine._extract_field`, make the `Write`/`Edit` branch resolve `new_text`/`content` consistently regardless of exact tool, e.g.:
```python
elif tool_name in ['Write', 'Edit']:
    if field in ('content', 'new_text', 'new_string'):
        return tool_input.get('content') or tool_input.get('new_string', '')
```
so `new_text` (the generic name used by legacy `pattern:` rules) falls back to `content` for `Write` just as `content` already falls back to `new_string` for `Edit`. Add a regression test asserting that a `block` rule with `event: file` and a `new_text`/`pattern` condition denies both an `Edit` call and a `Write` call carrying the same dangerous payload.

### Proof of Concept
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-eval",
    enabled=True,
    event="file",
    action="block",
    conditions=[Condition(field="new_text", operator="contains", pattern="eval(")],
    message="Dangerous eval() detected!"
)
engine = RuleEngine()

edit_input = {
    "tool_name": "Edit",
    "tool_input": {"file_path": "a.js", "old_string": "x", "new_string": "eval('x')"}
}
write_input = {
    "tool_name": "Write",
    "tool_input": {"file_path": "b.js", "content": "eval('x')"}
}

edit_result = engine.evaluate_rules([rule], edit_input)
write_result = engine.evaluate_rules([rule], write_input)

# Expected (invariant): both denied
assert edit_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
assert write_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"  # FAILS: write_result == {}
```
The `write_result` assertion fails because `_extract_field` returns `''` for the `Write` case, demonstrating the bypass.
