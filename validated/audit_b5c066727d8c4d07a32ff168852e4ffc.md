## Analysis Result

The claimed binding is: `repository_owner` used by `verify_signature` (org whose secret validates the HMAC) must equal the org that owns the `Shipit::Repository`/`Stack`/`PullRequest` mutated by `AssignedHandler#process`.

Tracing the code:

- `WebhooksController#verify_signature` derives the signing org from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and verifies the raw body against `Shipit.github(organization: repository_owner)`'s `webhook_secret`. [1](#0-0) [2](#0-1) 

- `AssignedHandler#pull_request` and `#repository` independently derive the target repository from `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which parses `"owner/name"` and looks up by that literal string — with no cross-check against `repository.owner.login`. [3](#0-2) [4](#0-3) 

Both `repository.owner.login` (used for signature org resolution) and `repository.full_name` (used for the DB lookup target) come from the **same attacker-controlled `repository` object** in the unsigned-until-verified JSON body. Nothing in `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema in `AssignedHandler` cross-validates that `repository.full_name`'s owner segment matches `repository.owner.login`. An attacker who owns/controls an org (and therefore knows their own `webhook_secret`) can send `repository.owner.login = "attacker-org"` (so the signature check passes against the attacker's own secret) while setting `repository.full_name = "victim-org/victim-repo"` (so the handler's lookup resolves to the victim's tracked `Repository`/`Stack`/`PullRequest`).

However, I could not fully verify within tool budget whether `full_name` is used anywhere else for consistency checks, and whether `github_app.verify_webhook_signature` behavior when `webhook_secret` is blank (`return true unless webhook_secret`) changes exploitability further — that path is orthogonal and would apply regardless of org-binding. The core mismatch between the org used for signature verification and the org whose data is mutated is real and unguarded in the code reviewed.

Given the file/method match (`AssignedHandler#pull_request`, `WebhooksController#repository_owner`) and the demonstrated absence of any check that `repository.owner.login` corresponds to `repository.full_name`'s owner, this is a valid cross-tenant write vulnerability.

### Title
Webhook signature verified against `repository.owner.login` while data mutated is selected by unrelated `repository.full_name`, allowing cross-org PR data forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`WebhooksController#verify_signature` resolves the signing organization from `params['repository']['owner']['login']`, while `AssignedHandler#pull_request`/`#repository` resolve the target `Repository`/`Stack`/`PullRequest` from `params['repository']['full_name']`. Both values are read from the same unauthenticated JSON body with no cross-check that they refer to the same organization, letting an attacker sign a request with their own org's webhook secret but target a victim org's tracked pull request.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `org(repository.owner.login used in verify_signature) == org(repository.full_name used in AssignedHandler#pull_request lookup)`.

`WebhooksController#verify_signature` builds `Shipit.github(organization: repository_owner)` and verifies the HMAC signature using that org's `webhook_secret`, where `repository_owner` is `params.dig('repository', 'owner', 'login')` [5](#0-4) [2](#0-1) . This only proves the attacker controls (or is) `repository.owner.login`'s org — it says nothing about `repository.full_name`.

`AssignedHandler#process` calls `pull_request.update(github_pull_request: params.pull_request)` when the action is `assigned`/`unassigned` and a matching `PullRequest` is found [6](#0-5) . The `pull_request` lookup joins `stack: :repository` and filters by `repositories: { id: repository.id }`, where `repository` is `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) . `from_github_repo_name` simply splits `"owner/name"` and does a DB lookup, with no comparison to `repository.owner.login` [4](#0-3) .

Attack: attacker owns/administers an org (e.g. `attacker-org`) registered in `Shipit.github_teams`/app config, so they know its `webhook_secret`. They POST to `/webhooks` with header `X-Github-Event: pull_request` and a body where `repository.owner.login = "attacker-org"` (making `verify_signature` succeed against the attacker's own secret) but `repository.full_name = "victim-org/victim-repo"`, `action = "assigned"`, `number` equal to an existing victim `PullRequest`'s number, and a crafted `pull_request` sub-object (arbitrary `title`, `head.sha`, `head.ref`, `labels`, `assignees`). `AssignedHandler` verifies none of this against the org that signed the request, resolves `repository` via `full_name` to the victim's `Repository`, finds the victim's `PullRequest` by `number`, and persists the attacker-supplied `github_pull_request` payload onto it — including `head.sha`/`ref`, which is later trusted by merge-queue/build logic.

No existing guard (`drop_unhandled_event`, `check_if_ping`, the `ExplicitParameters` schema in `AssignedHandler`, or `Repository`/`Stack` validations) checks that the signing organization and the org embedded in `full_name` match.

### Impact Explanation
A successful request causes the victim's `Shipit::PullRequest` record (title, `head` commit sha/ref, labels, assignees) to be overwritten with attacker-chosen data, without the attacker ever authenticating against the victim org's webhook secret. Because `head.sha` is trusted by downstream merge-queue/status logic, this can influence which commit is treated as the PR's head for merge/build decisions — a payload for one repository (attacker's) mutating another's stack/PR data, matching the Critical category of "a payload for one repository mutating another's stack, commit, task or team." This is repeatable against any victim `PullRequest` number the attacker guesses/knows (numbers are small sequential integers, easily enumerable), for any org whose full_name the attacker chooses to spoof, as long as the attacker can sign with any registered org's secret (their own).

### Likelihood Explanation
Preconditions: the attacker must control (or register) at least one GitHub organization configured in Shipit (`Shipit.github(organization: ...)` config) so they possess a valid `webhook_secret` to sign with — a low bar since any user/org that onboards a repository to this Shipit instance obtains this. The victim org must have an existing tracked `Shipit::PullRequest` with a known `number` (PR numbers are sequential and easily guessed/observed publicly on GitHub). No Shipit session, API token, or GitHub App key is needed. The attacker only needs to send one crafted, unsigned-but-locally-signed HTTP POST to the public `/webhooks` endpoint. This is low cost and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler), require that `params.dig('repository','full_name')`'s owner segment matches `params.dig('repository','owner','login')` before verification, and/or verify the signature using the org derived from `full_name` consistently everywhere it's used to select the target repository. More robustly, resolve the target `Repository` first from `full_name`, then verify the webhook signature using that repository's owner's secret (single source of truth), rejecting any payload where `owner.login` disagrees with the parsed `full_name` owner.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "assigned handler cannot be used to write into a repository whose org didn't sign the request" do
  victim_pr = shipit_pull_requests(:review_stack_review) # existing PullRequest tracked under 'shipit' org/repo
  attacker_org = "attacker-org" # configured with a known webhook_secret in test config

  payload = payload_parsed(:pull_request_assigned)
  payload["number"] = victim_pr.number
  payload["pull_request"]["number"] = victim_pr.number
  payload["pull_request"]["title"] = "PWNED"
  payload["pull_request"]["head"]["sha"] = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
  payload["repository"]["full_name"] = victim_pr.stack.repository.full_name # victim-org/victim-repo
  payload["repository"]["owner"]["login"] = attacker_org # signed org != victim org

  @request.headers['X-Github-Event'] = 'pull_request'
  # sign body with attacker_org's webhook_secret, not victim org's
  sign_request_as(attacker_org, payload)

  assert_no_changes -> { victim_pr.reload.title } do
    post :create, body: payload.to_json, as: :json
  end
  # currently FAILS: victim_pr.title becomes "PWNED" and head sha changes,
  # proving cross-org write despite signature only binding to attacker_org.
end
```
Assertion targets: before request, `victim_pr.title != "PWNED"` and `victim_pr.head.sha != crafted_sha`; after the request, with a fix, both must remain unchanged (request should be rejected with 422) since the signing org (`attacker-org`) does not match the org owning `repository.full_name` (`victim-org`). Without the fix, both values change, proving the vulnerability.
