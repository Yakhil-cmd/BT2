## Analysis

The report's bug class is a **verified/authorized value vs. actually-used value mismatch**: the oracle checks one thing (2-day low) while the effect it authorizes (liquidation size/reward) is computed from a different, attacker-influenced value. The closest analog in this engine that breaks a deployment-trust binding is the mismatch between **the stack a token's scope authorizes vs. the stack the controller actually touches**.

`Shipit::Api::BaseController` establishes the authorization invariant: when an `ApiClient` is scoped to a specific stack (`stack_id` set), lookups must go through `stacks`, which restricts the queryable set to that one stack: [1](#0-0) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving `params[:stack_id]` against the **global** `Stack` relation instead of the client-scoped `stacks` relation: [2](#0-1) 

Its permission check only verifies the client holds the `read:stack` permission string — it never verifies the permission applies to *this* stack: [3](#0-2) [4](#0-3) 

So the binding `token.stack_id == requested_stack.id` (enforced everywhere else via `stacks.from_param!`) is silently dropped for this one controller: any `ApiClient` with `read:stack` permission — even one explicitly scoped to a single stack via the admin UI (e.g. `stack: shipit` in `test/fixtures/shipit/api_clients.yml`) — can read the CCMenu status (deploy activity, `lastBuildStatus`, running state, lock state) of **any** stack in the installation by supplying a different `stack_id` in the URL, since routes accept an arbitrary `*stack_id`: [5](#0-4) 

This is the same class of defect as the oracle report: a value that is supposed to gate/scope an action (the 2-day-low price gating liquidation eligibility, vs. the stack-scoped token gating which stack's data can be read) is not actually the value enforced at the point of use.

### Title
Stack-scoped API token bypasses its own stack authorization in CCMenu controller - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController#stack` resolves the target stack from the global `Stack` relation instead of the caller's client-scoped `stacks` relation used by every other API controller, allowing a token that is restricted to one stack to read the deploy/build status of any stack.

### Finding Description
`Api::BaseController#stacks` (app/controllers/shipit/api/base_controller.rb:74-76) is the sole mechanism that enforces `ApiClient.stack_id` scoping; `Api::BaseController#stack` (lines 78-80) composes on top of it. `Api::CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly (app/controllers/shipit/api/ccmenu_controller.rb:29-31), which never consults `current_api_client.stack_id`. `require_permission :read, :stack` (line 6) only checks that `"read:stack"` is present in `ApiClient#permissions` (app/models/shipit/api_client.rb:38-45); it performs no per-instance/stack check. Consequently the equality the system is meant to enforce, `current_api_client.stack_id == stack.id` (when `stack_id` is set), is never checked in this controller.

### Impact Explanation
An attacker holding any valid API token scoped to a single stack (a normal, intentionally-restricted credential per the admin UI, e.g. `app/views/shipit/api_clients/show.html.erb`) can enumerate `owner/repo/environment` stack paths and read the CI/deploy status, lock state, and last build result of stacks they were never authorized to see. This is an unauthenticated-for-that-resource read of stack state, matching the engine's defined High-impact class ("unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
The only prerequisite is possession of any existing stack-scoped `read:stack` token (a routine, low-privilege credential meant to be handed to CI dashboards/build monitors) plus knowledge of another stack's identifier, which is derivable from `owner/repo/environment` and is not itself secret. No signature, session, or elevated permission is required beyond what the token already legitimately has for its own stack.

### Recommendation
Change `Api::CCMenuController#stack` to use the inherited, client-scoped `stacks` relation (i.e. `stacks.from_param!(params[:stack_id])`) exactly as `Api::BaseController#stack` does, so a stack-scoped token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack: shipit-org/app-a` with permission `read:stack` (as in `test/fixtures/shipit/api_clients.yml`'s `here_come_the_walrus`).
2. Using that client's `authentication_token`, request `GET /api/stacks/shipit-org/app-b/production/ccmenu` (a stack the client was never scoped to).
3. `CCMenuController#stack` resolves `app-b` via `Stack.from_param!` against the global `Stack` table (bypassing the `stacks` scoping), and `require_permission :read, :stack` passes because the client possesses `read:stack` in general.
4. The response renders `app-b`'s CCMenu XML (build status, activity, lock state), disclosing state of a stack outside the token's authorized scope.
