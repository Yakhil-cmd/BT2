## Analysis

The reachable ocore analog to CVE‑2021‑42008 (insufficient bounds/structure checking during decoding of untrusted binary input, causing corrupted data to be trusted) is the ASN.1/DER parsing performed in `signature.js` to extract a secp256k1 public key from an oscript-supplied PEM string, reachable from any AA trigger via the `is_valid_sig` / `vrf_verify` formula ops.### Title
DER BIT-STRING scan via `indexOf` allows public-key substitution/forgery in `is_valid_sig`/`vrf_verify` — ([File: signature.js])

### Summary
`verifyMessageWithSecp256k1PemPubKey` extracts the 65-byte uncompressed public key from an oscript-supplied PEM/DER blob by searching for the first occurrence of the 3-byte marker `03 42 00` anywhere in the buffer with `Buffer.indexOf`, instead of parsing the ASN.1 structure length-by-length. [1](#0-0)  This is the same bug class as CVE‑2021‑42008: a decoder trusts attacker-controlled byte content to locate a field boundary instead of validating structural bounds/length fields, so crafted input can make the decoder pick up the wrong bytes as the "real" data.

### Finding Description
`verifyMessageWithPemPubKey` first checks that the DER `AlgorithmIdentifier` at the structurally-computed offset (`algIdStart`) matches the secp256k1 OID, then hands the whole DER buffer to `verifyMessageWithSecp256k1PemPubKey`. [2](#0-1)  That function does NOT re-derive the BIT STRING offset structurally (e.g., from the outer SEQUENCE/BIT-STRING length bytes); it instead scans the entire DER buffer for the literal 3-byte pattern `03 42 00` and slices 65 bytes after it as the public key. [3](#0-2) 

Because the AlgorithmIdentifier bytes preceding the BIT STRING are attacker-supplied (an oscript AA can pass an arbitrary `pem_key` string into `is_valid_sig(message, pem_key, sig)` / `vrf_verify(seed, proof, pem_key)`), an attacker can embed the marker `03 42 00 04 <32 bytes> <32 bytes>` earlier in the buffer than the legitimate structural BIT STRING, or embed it in padding/garbage appended after a syntactically valid key. `Buffer.indexOf` returns the *first* match, so a maliciously constructed DER blob with two candidate `03 42 00` sequences can cause the parser to extract a public key that differs from the one a naive/legitimate DER parser (or a human/auditor reading the PEM) would consider canonical — i.e., two different byte-for-byte-distinct PEM strings can resolve to two different accepted keys, or the same "visually identical" trusted PEM literal string comparison elsewhere in an AA can be defeated by structurally ambiguous encodings that still parse successfully here. This is directly analogous to `decode_data` in the KISS driver trusting embedded escape/marker bytes without checking they occur at the position dictated by the declared frame length.

`validateAndFormatPemPubKey` (used by the generic, non-secp256k1 path) does perform position-derived length parsing (`identifiersStart`/`identifiersLength` computed from the DER length octets rather than pattern search), [4](#0-3)  which shows the secp256k1 fast-path in `verifyMessageWithSecp256k1PemPubKey` is the outlier that skips structural validation of where the BIT STRING legitimately starts.

This code is reachable by any unprivileged AA author/trigger sender through the oscript ops `is_valid_sig` and `vrf_verify`, which pass caller-controlled `pem_key`, `message`, and `signature`/`proof` values straight into this verification chain. [5](#0-4) 

### Impact Explanation
`is_valid_sig`/`vrf_verify` are commonly used inside AA bounce/response conditions to gate fund release based on signatures from a trusted oracle/counterparty key embedded in the AA's `params` or `getters`. If an AA's security logic relies on comparing a caller-supplied `pem_key` (or portions of it) against an expected value, or assumes the extracted public key uniquely corresponds to a specific PEM encoding, a structurally ambiguous DER blob that still satisfies `pubkey.length===65 && pubkey[0]===0x04` can let an attacker slip a different key past checks than an auditor/DER-strict verifier would expect, potentially allowing forged "valid" signature checks to pass under conditions the AA author did not intend, leading to unauthorized fund release from an AA (fund loss).

### Likelihood Explanation
Requires an AA that consumes attacker-influenced `pem_key` material (directly from trigger data or via some transformation) and whose security model depends on exact/canonical DER encoding — a real but not universal pattern in AA-based oracle/signature-gated contracts. The bug is trivially triggerable at the parsing layer (any trigger sender can supply arbitrary base64/PEM bytes to `is_valid_sig`), but full exploitation additionally requires an AA design that reuses/compares the raw PEM string or otherwise depends on non-ambiguous key extraction, which narrows real-world likelihood to Medium/High depending on AA usage patterns.

### Recommendation
Replace the marker-scan approach in `verifyMessageWithSecp256k1PemPubKey` with fully structural ASN.1 parsing that derives the BIT STRING offset the same way `validateAndFormatPemPubKey` derives `identifiersStart`/`identifiersLength` (i.e., walk the outer SEQUENCE, algorithm SEQUENCE, and BIT STRING length octets), rejecting the key if the byte at the computed offset is not `03`/expected tag, rather than using `Buffer.indexOf` to search for the tag pattern anywhere in the buffer. Additionally reject DER blobs containing trailing/extra bytes beyond the parsed structure to eliminate any ambiguity between different byte sequences resolving to the "same" accepted key.

### Proof of Concept
1. Craft a DER buffer where the required `SECP256K1_ALG_ID` bytes appear at the structurally correct `algIdStart` offset (satisfying the first check in `verifyMessageWithPemPubKey`), but additionally embed a spurious/crafted `03 42 00 04 <32B> <32B>` byte sequence earlier in the buffer (e.g., inside padding, comment-like filler, or a bogus preceding element) before the position where a strict DER parser would place the real BIT STRING.
2. Base64-encode this buffer and wrap it as a PEM `-----BEGIN PUBLIC KEY-----...-----END PUBLIC KEY-----` string; pass it as `pem_key` to an AA's `is_valid_sig(message, pem_key, sig)` call (via `trigger.data.pem_key` or similar) where the AA logic assumes deterministic/canonical key extraction from the PEM.
3. Because `der.indexOf(Buffer.from([0x03,0x42,0x00]))` returns the first match, `verifyMessageWithSecp256k1PemPubKey` extracts the attacker's earlier, spurious 65-byte sequence as `pubkey` instead of the structurally legitimate one, and verifies `sig` against this attacker-chosen key — demonstrating the decoder trusts embedded marker bytes over the declared/structural boundaries, mirroring the unchecked decode boundary flaw of CVE-2021-42008.

Note: I was unable to fully confirm within this session whether any shipped AA template or `getters`/`params` pattern in this repo actually compares raw PEM strings or otherwise depends on canonical/unique key extraction (which would upgrade this from a parsing-robustness defect to a directly weaponizable fund-loss exploit); a Devin session with full repo/test access would be needed to search all `.oscript`/`.ojson` templates for such usage patterns before final severity confirmation.

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;
```
