### Title
L1 BTC-lockup outpoints are only deduplicated within a single call, allowing the same Bitcoin UTXO to be re-credited as sats collateral across separate `register-for-bond` calls - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1-lockup path computes the sats a staker is credited with (`sats-total`) by summing verified Bitcoin outputs via `verify-l1-lockups` / `validate-l1-lockup`. Duplicate-outpoint protection (`seen-outpoints`) is scoped to a single call's `fold` accumulator, initialized fresh to `(list)` on every invocation. There is no contract-wide, persistent map that marks an L1 outpoint as already consumed once it has been used to credit a prior registration. A staker can therefore present the same already-verified Bitcoin lockup output in a second, later `register-for-bond` call (e.g. rolling from an ended L1 bond into a new bond in its L1-unlock window) and have `sats-total` credited again into a different bond's `protocol-bonds-total-staked` / staker and signer share maps, without any additional BTC ever being locked.

### Finding Description
`verify-l1-lockups` (stackslib/src/chainstate/stacks/boot/pox-5.clar:1984-2019) starts the fold with `seen-outpoints: (list)` and `validate-l1-lockup` (lines 2031-2113) only rejects an outpoint that repeats *within that same fold* via `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` (lines 2086-2088). This in-call check is exactly what the regression test at stacks-node/src/tests/pox_5_integrations.rs:1919-2002 exercises (triplicate outpoints in one call → `ERR_DUPLICATE_LOCKUP_OUTPOINT`), confirming the protection is per-call only. [1](#0-0) [2](#0-1) 

Crucially, `register-for-bond` re-derives `sats-total` fresh from `btc-lockup` on every call (line 673-676), and for the L1 path `old-sbtc`/custody accounting is skipped entirely because `get-staker-custodied-sbtc` returns `u0` for an existing L1 lock (`is-l1-lock` true), so `roll-sbtc` performs no sBTC transfer for that leg: [3](#0-2) [4](#0-3) 

The only gate that limits when a second registration can occur is `bond-overlaps-new-position?` / `verify-bond-rollover-window`, which only checks reward-cycle timing (that the prior bond's term has ended or is in its L1-unlock window) — not whether the specific Bitcoin outpoint being presented has already been counted toward a prior bond's `amount-sats`/`protocol-bonds-total-staked`: [5](#0-4) 

As a result, once a staker's first L1-backed bond membership rolls into its unlock window, the *same* previously-verified Bitcoin output (same txid/output-index, same script) can be resubmitted as the `btc-lockup` proof for a new `register-for-bond` call. If that output's encoded unlock height and the bond's configured `early-unlock-bytes` still satisfy the new bond's script/height checks (a plausible admin configuration, since `early-unlock-bytes` and unlock-window conventions are typically shared/templated across sequential bond periods by the same bond-admin), `validate-l1-lockup` will pass and `sats-total` will be credited into the new bond's `amount-sats`, `protocol-bonds-total-staked` (line 793-795), and `signer-shares-staked-for-cycle`/`staker-shares-staked-for-cycle` via `add-staker-to-bond-cycles`/`add-staker-to-signer-cycles` (lines 799-805) — inflating staked weight and reward eligibility for a second (and, in principle, subsequent) bond term while only one Bitcoin lock has ever actually occurred. [6](#0-5) 

This is the pox-5 structural analog of the Morpheus stETH finding: in both cases, an accounting value used to grant rewards/entitlements (`depositPool.deposited`/`lastUnderlyingBalance` there, `sats-total`/`amount-sats`/`protocol-bonds-total-staked` here) is derived and persisted without a durable, cross-call check that it corresponds 1:1 to a real, previously-uncounted external asset event (an actual stETH transfer delta there, an actual not-yet-credited Bitcoin UTXO here).

### Impact Explanation
If exploitable, this breaks the equality that `protocol-bonds-total-staked` / a staker's `amount-sats` should equal the Bitcoin actually locked for that staker's current bond. A staker could inflate their and their signer's counted stake and reward share for a bond term without providing additional real BTC collateral — a double-counting of a commitment. Depending on the reward formula this can dilute other stakers' `sBTC` rewards for that bond and cycle, and inflate the staker's own signer/reward eligibility, matching the "double-counting a commitment or reward" and "sats credited by an L1 proof that were never locked on Bitcoin" categories.

### Likelihood Explanation
Exploitation requires: (1) a staker with an ended/rolling-window L1 bond, (2) being allowlisted for a second bond, and (3) that second bond's admin-chosen `early-unlock-bytes`/unlock-height gate happening to still validate against the staker's already-used UTXO's fixed script/locktime. This is plausible but not guaranteed by default — it depends on bond-admin configuration choices (e.g., reusing the same `early-unlock-bytes` template across sequential bonds, which is a natural operational pattern for a protocol that issues sequential 6-cycle bonds), rather than a purely staker-controlled path. This conditional dependency lowers confidence relative to a pure code-only proof; I could not find (within the indexed content) a persistent/global outpoint registry anywhere else in `pox-5.clar` or `pox-locking` that would close this gap, but I also could not fully confirm from the available index whether `early-unlock-bytes` is deliberately randomized per-bond by the admin tooling (which would mitigate this in practice) — this would need verification against the full bond-admin/off-chain tooling, which is outside the indexed contract code.

### Recommendation
Persist a durable, contract-wide set (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`) and check/insert into it inside `validate-l1-lockup` (or `verify-l1-lockups`) so that once an outpoint has been credited toward any registration, it cannot be presented again in a later, separate `register-for-bond` call — mirroring how `DepositPool::_stake()` in the referenced report is fixed by only ever crediting a real, not-yet-recorded balance delta rather than trusting an amount that can be replayed.

### Proof of Concept
Conceptual reproduction sequence (Clarity-level, on top of the existing `pox_5_integrations.rs` test harness which already builds valid L1 lockup proofs):
1. `setup-bond(bond-index=0, early-unlock-bytes=E, allowlist=[staker])`, staker calls `register-for-bond(0, signer, amount-ustx, ok {outputs:[X], staker-unlock-bytes}, none)` with a real Bitcoin lockup output `X` — succeeds, `protocol-bonds-total-staked[0] += sats(X)`.
2. Mine to bond 0's L1 unlock window (`getBondL1UnlockHeight(0)`), as the existing rollover tests do (stacks-node/src/tests/pox_5_integrations.rs:1165-1204).
3. `setup-bond(bond-index=6, early-unlock-bytes=E, allowlist=[staker])` — admin reuses the same `early-unlock-bytes` and a compatible minimum-unlock-height.
4. Staker calls `register-for-bond(6, signer, amount-ustx, ok {outputs:[X], staker-unlock-bytes}, none)` presenting the *same* output `X` again. `validate-l1-lockup`'s `seen-outpoints` check only guards against `X` appearing twice in the same `outputs` list, not against `X` having already been used in step 1 — so this passes and `protocol-bonds-total-staked[6] += sats(X)` a second time, while only one real BTC lock exists on-chain.

;; Verify l1 lockup information for a staker. This asserts that each lockup
;; corresponds to the right timelock script for this staker, and that the lockup
;; occurred on-chain. If everything is valid, this returns the sum of all lockups in sats.
(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)

;; The sBTC the staker currently has custodied in pox-5, derived from their
;; bond membership. Returns u0 when the staker has no bond membership, or
;; when their existing bond is an L1 lock (no sBTC is custodied for L1
;; bonds). Used by `register-for-bond` and `stake` to compute the source
;; side of a `roll-sbtc` net transfer.
(define-read-only (get-staker-custodied-sbtc (staker principal))
    (match (map-get? protocol-bond-memberships staker)
        m (if (get is-l1-lock m)
            u0
            (get amount-sats m)
        )
        u0
    )
)
