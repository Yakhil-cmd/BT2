### Title
Cross-repository `Status` forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook by a bare SHA lookup across the entire `commits` table, with no constraint tying the matched commit's stack/repository back to the repository that authenticated the webhook. Any actor who can get a validly-signed `status` webhook delivered to `POST /webhooks` for *some* onboarded organization can flip the state of a `Status` (e.g. `context: sonarqube`, `state: failure`) for any commit in the system whose SHA they know, including commits belonging to a completely unrelated stack.

### Finding Description
The invariant that should hold is: for every `Status` write triggered by a webhook, `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` (the commit being mutated must belong to the repository that produced/authenticated the event). This is never checked.

`Shipit::WebhooksController#verify_signature` only validates the HMAC signature against the secret registered for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied payload (`params.dig('repository','owner','login')`): [1](#0-0) 
This only proves the payload was signed by *some* org's registered webhook secret — it says nothing about the `sha` field being legitimately owned by that org.

`StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha: params.sha)` is a global, cross-stack, cross-repository query — there is no `stack_id`/`repository` filter derived from the payload's `repository` object. `commit.create_status_from_github!` then calls `add_status`, which creates a `Status` row, fires `commit_status`/`deployable_status` hooks, and can trigger `stack.schedule_merges` or block deploys: [3](#0-2) [4](#0-3) 

**Attack path:** An attacker who legitimately controls (or is onboarded as a contributor/owner of) any repository/org that Shipit already trusts can send `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, and a payload body:
```json
{"sha":"<victim-commit-sha>","state":"failure","context":"sonarqube","branches":[...],"repository":{"owner":{"login":"attacker-org"}}}
```
Because signature verification only checks that the payload was signed by `attacker-org`'s secret, and `StatusHandler` never cross-checks `sha` ownership against `attacker-org`, this writes a `Status(context: sonarqube, state: failure)` onto every `Commit` row in the database sharing that SHA — including commits that belong to a victim stack/repository the attacker has no access to. Commit SHAs are not secret (they are publicly visible on GitHub commit pages, PR diffs, and CI status pages), so obtaining a target SHA for a chosen victim stack is trivial.

Existing guards do not stop this: `verify_signature` validates *who signed*, not *what repository the payload's data belongs to*; there is no `ExplicitParameters` check binding `sha` to `repository`; `Commit#stack` is not compared to the requesting `repository_owner` anywhere in `StatusHandler` or `Commit#create_status_from_github!`.

### Impact Explanation
This is a payload authenticated by one repository/organization mutating the commit-state, and downstream deploy/merge/block behavior, of an unrelated repository's stack — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. Concretely, an attacker can:
- Force a `failure` status for a `sonarqube`-type required context onto a victim commit, blocking deploys (`Commit#blocked?`/`#deployable?` depend on `status.state`) — see [5](#0-4)  — or flip it to `success`/`pending` to trigger `stack.schedule_merges` and continuous delivery via `add_status`/`schedule_continuous_delivery` [6](#0-5) .
- The blast radius is any stack in the Shipit instance sharing a commit SHA with a repo the attacker can get signed events from (e.g., forks of a common upstream, or duplicated tree histories), and is repeatable per request with no rate limiting on `POST /webhooks`.

### Likelihood Explanation
Preconditions: the attacker needs a validly-signed `status` webhook for *any* org already registered with Shipit (their own repo/org is sufficient — this does not require compromising the victim's secret), and knowledge of a target commit SHA in the victim stack (public information). No Shipit session, API token, or team membership is required. This is a low-cost, highly repeatable attack once the attacker controls or is trusted for any single onboarded repository.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository that authenticated the webhook, e.g. resolve the `Repository` from `payload.dig('repository','full_name')`/`repository_owner`, and restrict to `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: repository.id })` (or equivalent `stack.repository_id` filter) before calling `create_status_from_github!`. Apply the same repository-scoping fix pattern to any other webhook handler that resolves commits/stacks by bare SHA without a repository constraint.

### Proof of Concept
minitest plan (added under `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status webhook from repo A cannot mutate a commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to repository A
  attacker_repo_owner = "attacker-org"  # distinct, already-onboarded org in fixtures/secrets
  victim_commit = shipit_commits(:first)
  assert_equal victim_stack.id, victim_commit.stack_id

  # Binding under test (should hold, currently does not):
  # commit.stack.repository.full_name == payload["repository"]["full_name"]
  assert_not_equal victim_commit.stack.repository.full_name, "attacker-org/attacker-repo"

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature validated for attacker-org only

  body = {
    "sha" => victim_commit.sha,
    "state" => "failure",
    "context" => "sonarqube",
    "branches" => [{ "name" => victim_stack.branch }],
    "repository" => { "full_name" => "attacker-org/attacker-repo", "owner" => { "login" => attacker_repo_owner } }
  }.to_json

  request.headers['X-Github-Event'] = 'status'

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end
  # Currently FAILS: StatusHandler creates the Status on victim_commit despite
  # the webhook being authenticated for "attacker-org", proving the cross-repository write.
end
```
This demonstrates the equality `commit.stack.repository.full_name == payload["repository"]["full_name"]` is false both before and after processing, yet the write still occurs — confirming the vulnerability.
