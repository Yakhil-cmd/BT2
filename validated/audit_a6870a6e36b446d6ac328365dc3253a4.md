### Title
Webhook signature is verified against an organization derived from `repository.owner.login`, but event handlers dispatch on the unrelated `repository.full_name` field, letting one authenticated GitHub organization forge sync events for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which pre-configured GitHub App/organization secret to HMAC-verify against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  Once the signature checks out, the raw payload is handed unmodified to the registered event handlers. [3](#0-2)  Those handlers, however, do not reuse `repository.owner.login` to scope their effect — they instead resolve the target repository via a completely different field, `repository.full_name`. [4](#0-3) 

### Finding Description
The binding that should hold is: `organization that authenticated the request == organization whose repositories/stacks are acted upon`. Instead, the verified field (`repository.owner.login`/`organization.login`) and the acted-upon field (`repository.full_name`) are two independent keys inside the same attacker-controlled JSON body, with no cross-check between them.

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and validates the raw POST body's HMAC against that specific organization's `webhook_secret`. [1](#0-0) 
- `repository_owner` is read from `repository.owner.login`, a JSON field fully controlled by whoever crafts the payload. [2](#0-1) 
- `Handler#stacks` (the base class used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target stacks via `Repository.from_github_repo_name(repository_name)`, where `repository_name = payload.dig('repository', 'full_name')` — a *different* JSON field, never checked against `repository_owner`. [4](#0-3) 
- `PushHandler#process` then directly triggers `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch of that repository. [5](#0-4) 

Concretely: if organization `OrgA` has a legitimate Shipit GitHub App installation (and thus its administrator legitimately knows/derives `OrgA`'s configured `webhook_secret`), that administrator can send a POST to `/webhooks` with a payload where `repository.owner.login = "OrgA"` (so the signature validates against `OrgA`'s secret) but `repository.full_name = "OrgB/victim-repo"` (an entirely unrelated organization/repository they have no legitimate relationship with). The signature check passes because it only validates the sender is *some* known organization, not that the acted-upon repository belongs to that organization. The push handler then finds `OrgB`'s stacks by `full_name` and unconditionally calls `sync_github`, which — for a stack with `continuous_deployment: true` — can trigger `schedule_continuous_delivery`/deploy-triggering logic against the victim stack, using Shipit's own GitHub credentials for `OrgB` to fetch commits, entirely outside `OrgB`'s control. [6](#0-5) [7](#0-6) 

This exactly matches the "organization that authenticated versus the repository that is written" binding the scan targets: the HMAC only proves "a message came from a party who knows organization X's secret," not "the repository referenced in this message belongs to organization X."

### Impact Explanation
This crosses an authentication boundary between tenants: an attacker who legitimately administers/controls one onboarded GitHub organization's webhook secret can force sync/continuous-deployment triggers against stacks belonging to a completely different, unrelated organization onboarded to the same Shipit instance. Where `continuous_deployment` is enabled, this can result in an out-of-schedule, attacker-triggered deploy cycle on a victim's stack — matching the "unauthorized deploy" Critical impact category, achieved purely by exploiting the disconnect between the field used for authentication and the field used to select the write target.

### Likelihood Explanation
Requires the attacker to control (or have signed access to) at least one legitimately onboarded GitHub organization's webhook secret in the same Shipit deployment — a realistic scenario in any multi-tenant Shipit instance serving multiple GitHub organizations, since the webhook secret is per-organization configuration, not a session-bound, per-repository, or per-installation-verified value tied to `full_name`.

### Recommendation
After signature verification, re-derive the trusted organization solely from the verified `repository_owner`/`organization` field, and require that `repository.full_name`'s owner segment match `repository_owner` before dispatching to handlers (or better, look up the target `Repository`/`Stack` by both owner and name and reject if they disagree). Alternately, bind webhook secrets to the specific repository (not just the organization) and validate that binding in `Handler#stacks`.

### Proof of Concept
1. Assume `OrgA` and `OrgB` are both onboarded to a shared Shipit instance, each with a stack (`OrgB` stack has `continuous_deployment: true`).
2. Attacker administers `OrgA`'s GitHub App and knows `OrgA`'s configured `webhook_secret` (legitimate for `OrgA`'s own webhooks).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, must exist on OrgB/victim-repo>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s secret over this exact body (`Hook::DeliverySigner`/`OpenSSL::HMAC` logic mirrors `verify_webhook_signature`). [8](#0-7) 
5. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` computes `repository_owner = "OrgA"`, fetches `OrgA`'s app, and the signature validates successfully. [1](#0-0) 
6. `PushHandler#process` resolves stacks via `repository.full_name = "OrgB/victim-repo"`, unrelated to the verified `OrgA`, and calls `stack.sync_github`, forcing a sync/continuous-deployment cycle on `OrgB`'s stack. [5](#0-4)

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
