## Confirmed vulnerability: webhook signature is verified against a different repository field than the one used to select the target Stack

### Title
Webhook HMAC signature is verified against `repository.owner.login`/`organization.login` but the affected records are selected using `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration (and its `webhook_secret`) used to validate the `X-Hub-Signature` HMAC by reading `repository.owner.login` (falling back to `organization.login`) from the JSON body itself. [1](#0-0)  But every event handler that consumes the same payload to find the `Repository`/`Stack` to act on reads a *different* field, `repository.full_name`. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The engine explicitly supports multi-organization GitHub App configuration, where each organization key under `secrets.github` has its own `webhook_secret` (independently nil-able). [5](#0-4)  `Shipit::GitHubApp#verify_webhook_signature` short-circuits and returns `true` unconditionally whenever the configuration for the selected organization has no `webhook_secret` set: `return true unless webhook_secret`. [6](#0-5) 

`WebhooksController#verify_signature` picks *which* organization's app/secret to use for verification purely from attacker-controlled JSON fields (`repository.owner.login` or `organization.login`), not from any authenticated context: [7](#0-6) 

Meanwhile, the handler base class — used by `PushHandler`, `StatusHandler` and others via `stacks`/`repository_name` — resolves the actual `Repository`/`Stack` records to mutate using the completely independent `repository.full_name` field of the same payload: [2](#0-1) 

This breaks the binding: **organization authenticated (via `repository.owner.login` + its `webhook_secret`) ≠ repository written (via `repository.full_name`)**. An operator running a multi-org Shipit instance (a configuration the engine documents and ships fixtures/tests for, e.g. `test/dummy/config/secrets_double_github_app.yml`, where `OrgTwo` has `webhook_secret: # nil`) is exposed: an unauthenticated internet attacker who knows that *any one* configured organization has no webhook secret can:
1. Set `repository.owner.login` (or `organization.login`) to that unsecured organization, so `verify_webhook_signature` returns `true` with no real signature required.
2. Set `repository.full_name` to any tracked repository under a completely different, "secured" organization.
3. Send arbitrary `push`, `status`, `check_suite`, `pull_request`, or `membership` events, causing handlers to enqueue `GithubSyncJob`, mutate commit `Status`, archive/unarchive review stacks, or add/remove `Membership`/`Team` records against the target org's stacks — all without ever knowing that org's real `webhook_secret`.

Even in the single-org case, if the operator leaves `webhook_secret` unset (the documented default, "optional" per `docs/setup.md`), verification is a no-op for every event and any external caller can forge webhooks for any tracked repository.

### Impact Explanation
This crosses the "organization authenticated versus the repository written" trust boundary named in the rules. Concretely reachable, unauthenticated impacts include:
- Forged `push` events triggering `GithubSyncJob`/`stack.sync_github` against arbitrary tracked stacks. [8](#0-7) 
- Forged `membership` events creating/removing `Team`/`Membership` rows, which feed directly into `Shipit.github_teams` authorization checks used by `Authentication#force_github_authentication` to gate application access. [9](#0-8) 
- Forged `pull_request` events provisioning/archiving review stacks for arbitrary repositories. [10](#0-9) 

This satisfies the "High" bar: escalation into `Shipit.github_teams` authorization, and unauthorized state changes on stacks the attacker does not control on GitHub.

### Likelihood Explanation
Requires the operator to run Shipit with multiple GitHub organizations configured (a documented, supported feature) where at least one configured org lacks a `webhook_secret` — or, more broadly, any deployment that leaves `webhook_secret` empty (documented as optional). No Shipit account, `ApiClient` token, or GitHub write access is needed; only the ability to POST to the public `/webhooks` endpoint with a crafted JSON body and event header.

### Recommendation
Verify the HMAC signature using the same field(s) that will subsequently be used to resolve the affected repository, or bind them together explicitly: after selecting the GitHub App config, re-derive/validate that the `repository.full_name`'s owner matches the organization whose secret validated the signature, and reject if they diverge. Additionally, consider failing closed (rejecting the webhook) rather than accepting unsigned payloads when `webhook_secret` is blank, at least when more than one organization is configured.

### Proof of Concept
Assume Shipit is configured with two orgs: `OrgOne` (has `webhook_secret` set, owns `OrgOne/secured-repo` tracked by Shipit) and `OrgTwo` (no `webhook_secret` configured), per `test/dummy/config/secrets_double_github_app.yml`.

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, verification is bypassed for OrgTwo

{
  "ref": "refs/heads/master",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "OrgTwo" },      # used ONLY for signature-verification org lookup
    "full_name": "OrgOne/secured-repo"    # used to select the Stack that gets mutated
  }
}
```

`verify_signature` calls `Shipit.github(organization: 'OrgTwo')`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (fake) `X-Hub-Signature`. [6](#0-5)  The request proceeds to `PushHandler#process`, which resolves stacks via `Repository.from_github_repo_name('OrgOne/secured-repo')` and calls `stack.sync_github(expected_head_sha: 'deadbeef...')` on stacks the attacker never authenticated against. [2](#0-1) [8](#0-7)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
