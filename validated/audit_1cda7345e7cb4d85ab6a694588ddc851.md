### Title

Flash-position callbacks can execute matured oracle governance while the controller finalizes with stale prices - (File: `contracts/controller/src/strategies/flash_position.rs`)

### Summary

`flash_position` loads oracle prices before invoking an arbitrary WASM receiver and reuses those invocation-local prices during final risk validation. The receiver can execute a matured `ConfigureAssetOracle` governance operation against the price aggregator during the callback, replacing an asset's oracle after the controller has already cached the old valuation. This lets an attacker atomically open a leveraged position under pre-transition prices that would fail under the newly activated oracle configuration.

### Finding Description

`ControllerContract::flash_position` delegates to `process_flash_position` with caller-selected debt, receiver, collateral declarations, and callback data. [1](#0-0) 

The controller prefetches the debt and collateral prices before entering the guarded callback window. [2](#0-1) 

Inside that window, it mints and forwards debt before invoking `execute_flash_position` on the attacker-controlled receiver. [3](#0-2) 

The pool borrow is committed and the borrowed asset is transferred to the controller, then measured and forwarded to the receiver. [4](#0-3) 

`Context::fetch_prices` retains values already stored in `token_prices`, so an oracle change performed during the callback cannot invalidate the earlier read. [5](#0-4) 

After the callback returns, the controller deposits measured collateral and runs `strategy_finalize` without refreshing the prefetched prices or checking that oracle configuration remained unchanged. [6](#0-5) 

Governance `execute` accepts a matured external operation and invokes its target contract. [7](#0-6) 

A scheduled `ConfigureAssetOracle` operation resolves to `price_aggregator.set_oracle`, while `EditOracleTolerance` resolves to `price_aggregator.set_tolerance`; both targets remain callable while the controller is on the call stack. [8](#0-7) 

The flash guard only prevents reentry into controller operations, and the Soroban same-contract restriction does not prevent the receiver from calling the separate governance and price-aggregator contracts. [9](#0-8) 

### Impact Explanation

An attacker can borrow the maximum amount supported by the collateral's old valuation, activate a matured oracle transition during the callback, and leave an account that is undercollateralized under the new valuation. If the resulting shortfall exceeds liquidation recovery, the market accumulates bad debt and suppliers bear the loss.

### Likelihood Explanation

The attack requires a publicly scheduled and matured oracle or tolerance operation whose activation materially changes collateral valuation, plus enough pool liquidity for a meaningful flash-position borrow. This is plausible during governance-approved oracle migrations or emergency feed replacements and can be performed by an unprivileged contract receiver once the operation is executable.

### Recommendation

Revalidate risk-critical pricing state after the flash-position callback and before collateral deposit/finalization. Prefer clearing and reloading `Context::token_prices` for all debt and collateral assets after `invoke_receiver`, or store a price-aggregator configuration epoch before the callback and require it to remain unchanged before `strategy_finalize`. A reloaded-price path is safer because it permits legitimate oracle activation while ensuring the position is evaluated under the final oracle configuration.

### Proof of Concept

1. Wait for a governance-approved `ConfigureAssetOracle` operation to mature, where the collateral's new oracle produces a materially lower valuation than the currently cached oracle.
2. Deploy a WASM receiver that both supplies collateral and calls governance during `execute_flash_position`.
3. Invoke:

```rust
controller.flash_position(
    receiver,                         // caller and account owner
    0,                                // create a new account
    spoke_id,
    PositionMode::Multiply,
    HubAssetKey {
        hub_id,
        asset: debt_token,
    },
    borrow_amount,
    receiver,
    data,
    vec![
        (
            HubAssetKey {
                hub_id,
                asset: collateral_token,
            },
            minimum_collateral,
        )
    ],
    Vec::new(),
)
```

4. Inside `execute_flash_position`, transfer `minimum_collateral` to the controller and execute the matured operation:

```rust
governance.execute(
    None,
    price_aggregator,
    Symbol::new(&env, "set_oracle"),
    vec![
        collateral_price_key.into_val(&env),
        replacement_oracle.into_val(&env),
    ],
    predecessor,
    salt,
);
```

5. Governance invokes `price_aggregator.set_oracle`, after which the callback returns normally.
6. The controller measures and deposits the delivered collateral, but final solvency still uses the collateral price cached before the callback.
7. The transaction commits a solvent position under the old valuation; subsequent reads use the replacement oracle, leaving `health_factor < 1` and potentially creating bad debt after liquidation.

/// Runs `f` with the flash-loan flag set; preserves an already-active outer guard.
pub(crate) fn with_flash_guard<T>(env: &Env, f: impl FnOnce() -> T) -> T {
    let prev = is_flash_loan_ongoing(env);
    set_flash_loan_ongoing(env, true);
    let out = f();
    if !prev {
        set_flash_loan_ongoing(env, false);
    }
    out
