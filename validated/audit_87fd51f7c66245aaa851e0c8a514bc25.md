### Title
Webhook signature verification is scoped to the payload's organization, but `StatusHandler` writes CI statuses to any commit in the database matching an attacker-chosen SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) from the *unverified* JSON body, then verifies the signature against that one field. Once verification passes, `StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` — a global, repository‑agnostic query — and calls `commit.create_status_from_github!(params)`, writing the fully attacker‑supplied `state`, `context`, `description`, and `target_url` onto whatever commit matches, regardless of which repository/organization it actually belongs to.

### Finding Description
The trust binding that should hold is: *"the organization whose webhook secret authenticated this request" == "the organization/repository whose data is written."* This binding is broken:

- `verify_signature` derives `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to verify the signature: [1](#0-0)  with `repository_owner` computed from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .
- Every registered GitHub App/organization has its own independent `webhook_secret` in `config/secrets.yml` (multiple orgs are explicitly supported, e.g. `somegithuborg` / `someothergithuborg`) [3](#0-2) , and the secret used to check the signature is looked up per-organization via `GitHubApp#verify_webhook_signature` and `@webhook_secret` [4](#0-3) .
- Once the request is authenticated as belonging to *some* known organization, the event params (the full JSON body) are dispatched unmodified to the handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .
- `StatusHandler#process` never re-derives or checks the repository/organization at all — it looks up commits purely by SHA across the whole instance: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) . Unlike `Handler#stacks`, which at least scopes lookups through `Repository.from_github_repo_name(repository_name)` [7](#0-6) , `StatusHandler` bypasses that scoping entirely and queries `Commit` directly.

Concretely: an operator of any organization `B` that is legitimately registered in this Shipit instance (and therefore possesses/derives a valid signature for `B`'s webhook secret) can send a `status` event whose `repository.owner.login` is `B` (so the signature check passes) but whose `sha`, `state`, `context`, `target_url`, and `description` are entirely attacker-chosen and target a commit SHA that actually belongs to organization `A`'s stack. The signature check authenticates "this request came from org B," but the write ("set this commit's CI status") is applied to org A's commit with no cross-check that the commit's repository belongs to org B.

### Impact Explanation
`Commit` statuses feed directly into CI‑gating logic used to decide whether a deploy is allowed (`ci.require` / `ci.blocking` in `shipit.yml`, backed by `Shipit::Status::Group` / `Commit#state`, evidenced by `app/models/shipit/status/group.rb` and `app/models/shipit/commit_checks.rb`). By forging a `success` status for a required CI context on a victim organization's commit, an attacker who only controls a different, legitimately-registered organization can make an otherwise CI-blocked commit appear deployable, enabling an unauthorized deploy for a stack/repository they have no legitimate access to. This matches the "unauthorized deploy" high-severity impact category.

### Likelihood Explanation
This requires the attacker to control (or be an authorized user/admin of) at least one organization that is already onboarded into the same multi-tenant Shipit instance — a realistic scenario given the documented support for multiple `github:` entries per Shipit deployment. No GitHub App private key, `webhook_secret` of the victim org, Shipit session, or `ApiClient` token is needed for the victim org; only a valid signature for the attacker's *own* org, which they can legitimately produce (they configured/received that webhook secret when their org's GitHub App was installed).

### Recommendation
Scope `StatusHandler` (and any other handler) to only mutate commits/repositories that belong to the same organization/repository that produced the verified signature, e.g., by requiring `Repository.from_github_repo_name(payload.dig('repository','full_name'))` to resolve to a repository under the verified `repository_owner`, and rejecting the event otherwise. More generally, `verify_signature` should bind the entire payload's `repository.full_name` (not just the owner login used to pick a secret) to the organization whose secret validated it, and every handler should reuse that verified repository/organization identity instead of independently trusting `repository.full_name` or unscoped SHA lookups from the same unverified JSON body.

### Proof of Concept
1. Attacker is a legitimate admin of GitHub organization `B`, registered in Shipit with its own `webhook_secret_B`.
2. Attacker crafts a `status` event body:
```json
{
  "repository": {"owner": {"login": "B"}},
  "sha": "<sha-of-a-commit-belonging-to-org-A-stack>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "description": "forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_B, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"B"`, fetches `Shipit.github(organization: "B")`, and the HMAC checks out against `webhook_secret_B` — request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds org A's commit (no ownership check), and calls `create_status_from_github!(params)`, writing the forged `success` status onto it (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
6. If org A's `shipit.yml` requires that context (`ci.require`), the commit now satisfies CI requirements it never actually passed, and can be deployed.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
