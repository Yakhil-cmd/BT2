### Title
Asset definer can arbitrarily and repeatedly change the `spender_attested` attestor list at any time, freezing transfers of an already-issued asset - (File: `validation.js`)

### Summary
An asset's issuer (`definer_address`) can publish unlimited `asset_attestors` messages after the asset has been issued and distributed, changing which addresses are considered "attested" for that asset. There is no restriction on how often, or under what conditions, this list may change, and no protection for holders whose funds were valid and transferable under a previous attestor list.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment involving that asset — issuance, transfer, and output — is checked against the *current* attestor list at validation time, not the list in effect when the asset units were created or received: [1](#0-0) 
For transfers, the owner address of every spent input must be attested at validation time or the payment is rejected: [2](#0-1) 
For outputs, every recipient address must currently be attested or the payment fails: [3](#0-2) 

The attestor list itself is fully mutable by the sole discretion of the asset definer, with the only check being that the sender is the definer address; there is no limit on frequency, no immutability window, and no protection of previously-attested holders: [4](#0-3) 
The list is looked up as "the latest attestor-list unit before last ball," meaning any new `asset_attestors` unit immediately supersedes all prior lists for validation purposes, network-wide: [5](#0-4) 

This mirrors the reported bug class precisely: just as the NFT contract owner could change `setPlotsAvailablePerSize` or vesting parameters at any time to unexpectedly devalue or lock users' already-acquired assets, the ocore asset definer can change the attestor list at any time to retroactively lock (freeze) previously valid, freely transferable holdings of unprivileged asset holders, or to grant a new address the ability to receive/spend the asset when it previously could not.

### Impact Explanation
A user who received an attested asset as payment, believing (based on the attestor list at receipt time) that they could freely transfer or hold it, can find their balance permanently frozen after the definer publishes a new `asset_attestors` list that removes their address from the attested set — no different addresses, no recourse, output becomes unspendable via the asset's built-in rules. This is direct "AA/user fund … freezing" impact reachable purely by an ordinary asset issuer (not an "operator" of the whole system) issuing a single well-formed unit, well within the unprivileged-actor threat model (asset issuance and transfer conditions is explicitly an in-scope category).

### Likelihood Explanation
Any account that defines a `spender_attested` asset already holds the definer role for that asset and can post `asset_attestors` updates freely and cheaply (just another unit) at any point after issuance and distribution, so likelihood of a rug/mistake is high whenever this asset feature is used, and no protocol-level safeguard (e.g., grandfathering old attestors, cooldown, or immutability) exists to prevent it.

### Recommendation
Consider one or more of: (1) grandfathering addresses attested under the attestor list in effect at the time an output was created, so retroactive attestor-list changes cannot freeze already-existing balances; (2) enforcing a minimum delay/cooldown between `asset_attestors` updates and/or a maximum number of updates, documented and validated on-chain; (3) allowing holders to escape frozen state (e.g., transfer back to definer even when not currently attested) so funds are not permanently stuck.

### Proof of Concept
1. Address `D` defines an asset `A` with `spender_attested: true`, `attestors: [X]` (`validateAssetDefinition` in `validation.js:2725`).
2. `X` attests address `H`; `D` issues asset `A` to `H` via a payment (`validatePayment`, `validation.js:2060`), which passes since `H` is attested.
3. `H` holds/uses the asset normally, expecting it to remain transferable.
4. `D` posts a new `asset_attestors` message removing `X`/`H`'s attestation from the effective list — validated only against `objUnit.authors[0].address !== objAsset.definer_address` (`validation.js:2829-2848`), with no other restriction.
5. Any subsequent attempt by `H` to spend or transfer their existing output of asset `A` now fails validation at `validation.js:2504-2507`/`2630-2641` ("owner address is not attested" / "some output addresses are not attested"), permanently freezing `H`'s previously valid balance with no recourse.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
