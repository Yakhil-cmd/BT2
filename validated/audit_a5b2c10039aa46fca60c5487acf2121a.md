## Analysis

The Asset Hub Polkadot `Barrier` at `system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs:374-409` wraps the deny-filter with plain `DenyReserveTransferToRelayChain`, not `DenyRecursively<DenyReserveTransferToRelayChain>` [1](#0-0) .

By contrast, `bridge-hub-polkadot` and `bulletin-polkadot` both wrap the same deny-filter with `DenyRecursively<...>` [2](#0-1) [3](#0-2) .

This confirms the upstream `xcm-builder` crate provides a dedicated `DenyRecursively` combinator specifically to make deny-barriers inspect nested XCM programs (e.g. those embedded inside `SetAppendix`, `SetErrorHandler`, `InitiateReserveWithdraw{ xcm, .. }`, `DepositReserveAsset{ xcm, .. }`), because the base `ShouldExecute` implementations (like `DenyReserveTransferToRelayChain`) only walk the **top-level** instruction list of the program passed to `prepare_and_execute`. Asset Hub Polkadot, Asset Hub Kusama, Coretime (Polkadot/Kusama), People (Polkadot/Kusama), and Collectives Polkadot all still use the bare (non-recursive) form [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) .

The XCM executor evaluates `Barrier`/`ShouldExecute` exactly once, against the top-level program handed to it via `pallet_xcm::execute` (reachable by any signed account, since `ExecuteXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>` accepts any signed origin) [8](#0-7) . Continuation programs set via `SetAppendix`/`SetErrorHandler` (or nested `xcm` fields of instructions such as `InitiateReserveWithdraw`/`DepositReserveAsset` once forwarded) are executed by the executor's internal recursion without a second `ShouldExecute` pass — this is precisely the gap `DenyRecursively` was built to close in the other chains' configs.

This means a signed AH user can submit (via `pallet_xcm::execute`, or via the `custom_xcm_on_dest`/`xcm` continuation parameter of `transfer_assets_using_type_and_then`) a top-level program that is superficially benign (e.g. `WithdrawAsset`, `BuyExecution`, satisfying `AllowTopLevelPaidExecutionFrom<Everything>`) but carries a `SetAppendix`/`SetErrorHandler` (or nested-instruction) payload containing `InitiateReserveWithdraw { reserve: RelayChainLocation, .. }`. The outer `DenyReserveTransferToRelayChain` scan never inspects that nested instruction, so it is not denied at the barrier stage, and it later executes locally as an appendix/error-handler continuation, forwarding a `ReserveAssetDeposited`/withdrawal message to the Relay chain — which structurally should never accept such a message since AH (not the Relay) is now the DOT reserve/issuance location.

### Title
Non-recursive `DenyReserveTransferToRelayChain` barrier on Asset Hub Polkadot allows deny-list bypass via nested `SetAppendix`/`SetErrorHandler`/embedded XCM programs - (File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs)

### Summary
Asset Hub Polkadot's `Barrier` uses the bare `DenyReserveTransferToRelayChain` filter instead of the `DenyRecursively<DenyReserveTransferToRelayChain>` combinator that bridge-hub-polkadot and bulletin-polkadot already use for the identical deny rule. Because `ShouldExecute` is evaluated only once against the top-level instruction list, a signed user can hide a `InitiateReserveWithdraw{ reserve: RelayChainLocation, .. }` (or `DepositReserveAsset`/`TransferReserveAsset` targeting the Relay) inside a `SetAppendix`/`SetErrorHandler` continuation of an otherwise-allowed top-level program, bypassing the deny-list.

### Finding Description
The `Barrier` type at `system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs:374-409` is `TrailingSetTopicAsId<DenyThenTry<DenyReserveTransferToRelayChain, (...)>>`. `DenyReserveTransferToRelayChain::should_execute` scans only the top-level instruction slice supplied to `XcmExecutor::prepare_and_execute`, looking for `InitiateReserveWithdraw`/`DepositReserveAsset`/`TransferReserveAsset` instructions whose destination/reserve is the Relay chain. It does not recurse into instructions that themselves carry a nested `Xcm` program, such as `SetAppendix(Xcm)`, `SetErrorHandler(Xcm)`, or the `xcm` continuation field of reserve/teleport instructions.

The `Barrier` is invoked exactly once per top-level message/program. Appendix and error-handler programs are executed later by the executor's own internal recursive `process`/`execute` logic on the same chain and holding register, without a second barrier check. Consequently, an attacker can submit a top-level program that satisfies `AllowTopLevelPaidExecutionFrom<Everything>` (e.g. `WithdrawAsset` + `BuyExecution`) and attach a `SetAppendix` containing the denied `InitiateReserveWithdraw{ reserve: RelayChainLocation, .. }`. The outer scan sees only `WithdrawAsset`, `BuyExecution`, `SetAppendix` — none of which match the deny patterns — so the message passes, and the nested reserve-withdraw executes as a local continuation, forwarding a message to the Relay chain claiming Relay-backed reserve of DOT.

Entry points reachable by any signed AH account:
- `pallet_xcm::execute` — `ExecuteXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>` accepts any signed origin (`system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs:612-622`), letting the attacker submit an arbitrary `VersionedXcm` program directly for local execution under this same `Barrier`.
- `transfer_assets_using_type_and_then`'s custom continuation program, which is likewise subject to this `Barrier` when forwarded/executed.

Other chains in this repo (bridge-hub-polkadot, bulletin-polkadot) already close this exact gap using `DenyRecursively<DenyReserveTransferToRelayChain>`, confirming the gap is a known class of issue that the maintainers have already patched elsewhere but left unaddressed on Asset Hub (and also on Asset Hub Kusama, Coretime, People, and Collectives).

### Impact Explanation
If the Relay chain still processes an unauthorized reserve-withdraw/deposit message for DOT under the (structurally incorrect, post-migration) assumption that it holds reserve backing, this creates a cross-chain balance mismatch: AH's local DOT accounting is decremented (withdrawal executed locally) while the Relay is tricked into crediting/releasing DOT it does not actually back, i.e., an unauthorized reserve release / asset duplication vector between AH and the Relay chain.

### Likelihood Explanation
Preconditions are minimal: any signed AH account, no special privileges. The attack requires only constructing and submitting a `VersionedXcm` via `pallet_xcm::execute` containing a `SetAppendix`/`SetErrorHandler` wrapper — a standard, publicly documented XCM instruction, not requiring any exploit of memory-safety or unusual runtime state. It is fully repeatable by any account with enough balance to pay execution fees.

### Recommendation
Wrap the reserve-to-relay deny rule (and any other deny-list barrier) in `DenyRecursively`, mirroring the pattern already used in `bridge-hub-polkadot`/`bulletin-polkadot`:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```
Apply the same fix consistently to Asset Hub Kusama, Coretime Polkadot/Kusama, People Polkadot/Kusama, and Collectives Polkadot, which have the same non-recursive gap.

### Proof of Concept
xcm-emulator integration test:
1. On Asset Hub Polkadot, as a signed test account with sufficient DOT, call `PolkadotXcm::execute` with a program:
   ```
   Xcm(vec![
       WithdrawAsset((Here, fee_amount).into()),
       BuyExecution { fees: (Here, fee_amount).into(), weight_limit: Unlimited },
       SetAppendix(Xcm(vec![
           InitiateReserveWithdraw {
               assets: All.into(),
               reserve: RelayChainLocation::get(),
               xcm: Xcm(vec![DepositAsset { assets: All.into(), beneficiary: attacker_on_relay }]),
           },
       ])),
   ]))
   ```
2. Assert that `PolkadotXcm::execute` currently succeeds (`Outcome::Complete`) and that an outbound UMP message containing `ReserveAssetDeposited`/withdrawal is queued toward the Relay chain — demonstrating the barrier did not trap the nested `InitiateReserveWithdraw{reserve: Parent}`.
3. After applying the `DenyRecursively` fix, re-run the same test and assert the call is now barred (`Outcome::Incomplete`/`Error::Barrier` or `ProcessMessageError::Unsupported`), with no outbound reserve-withdraw message generated.
