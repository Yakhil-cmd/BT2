### Title
Webhook signature verified against one payload field while handlers act on a different, unvalidated field — cross-organization stack/repository confusion in `WebhooksController` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but every event handler (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`) resolves the target `Repository`/`Stack` from a *different* field of the same untrusted JSON body: `payload.dig('repository', 'full_name')`. Because the raw JSON body is fully attacker-controlled (only its HMAC must match), a party who legitimately controls one GitHub organization configured in this Shipit instance (and therefore knows that organization's own `webhook_secret`, which they set themselves when installing their GitHub App) can forge a webhook whose `repository.owner.login` is their own org (so the signature check passes) while `repository.full_name` names a repository belonging to a completely different organization/tenant tracked by the same Shipit instance. This breaks the binding "organization that authenticated == repository that is written."

For example `PushHandler`: [6](#0-5) 

and the pull-request handlers resolve `repository` the same way: [7](#0-6) 

Nothing cross-checks that `repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/target selection) refer to the same repository. Shipit explicitly supports multiple independent GitHub organizations/apps in one instance, each with its own `webhook_secret`: [8](#0-7) [9](#0-8) 

An attacker who legitimately administers/installed the GitHub App for **their own** organization (`org-attacker`) knows `org-attacker`'s `webhook_secret` (they configured it themselves in the GitHub App settings) and can freely send arbitrary raw HTTP requests to `/webhooks` (there is no IP allow-listing or GitHub-only transport restriction visible in the engine). They can set:
- `repository.owner.login = "org-attacker"` → signature check passes using their own secret.
- `repository.full_name = "org-victim/some-repo"` → handler resolves and acts on the victim organization's `Repository`/`Stack`.

This is architecturally the same class of bug as the reported CVE: a security decision (which trust domain/credential authorizes the action) is made from attacker-supplied structured data (the JSON payload) without validating internal consistency, and a *different* field of that same untrusted structure is then used to determine what gets acted upon — i.e., "deserializing" (accepting as trusted) one field for authentication and a different, unchecked field for the privileged action.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out in scope. Concretely:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on any non-archived stack matching the forged `full_name`/branch — this can force GitHub synchronization / trigger continuous-delivery pipelines for a stack belonging to a completely unrelated organization the attacker has no legitimate access to, without ever needing that victim organization's `webhook_secret`.
- `PullRequest::LabeledHandler`/`UnlabeledHandler`/`OpenedHandler` can archive/unarchive or provision review stacks for the victim's repository.
- `StatusHandler`/`CheckSuiteHandler` can inject forged commit statuses/check-run results for the victim's commits, which (per `MergeRequest::StatusChecker` and `required_statuses`/CI gating logic) can be used to make an otherwise-blocked commit appear to pass CI checks required for merges or deploys.

This is an unauthorized cross-repository/cross-tenant action triggered with credentials that were never authorized for the target tenant — matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Likelihood is limited to deployments where the host application configures **multiple independent GitHub organizations** under one Shipit instance (the documented multi-org `secrets.yml` format). In that configuration, any of those organizations' administrators is an "unprivileged attacker" with respect to the other organizations' stacks, and the exploit requires only crafting one raw HTTP POST with a valid HMAC computed from their own, legitimately-known secret — no privileged Shipit session, no victim secret, and no GitHub App private key are needed. In single-organization deployments (the common case, `github_default_organization` returning `nil`), the same secret is used everywhere, so this class of confusion is not exploitable across tenants.

### Recommendation
- In `WebhooksController`, after determining `repository_owner` for signature verification, also validate (before dispatching to handlers) that `repository.full_name`'s owner segment matches the same organization used to select the `webhook_secret` (or, better, resolve the target `Repository` via a lookup scoped to the authenticated organization only).
- In `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`, restrict resolution to repositories belonging to the organization that was cryptographically authenticated for this request, rejecting the event (422) if `repository.full_name`'s owner does not match `repository.owner.login`/`organization.login`.

### Proof of Concept
Preconditions: Shipit configured with the multi-org `github` secrets format (`OrgAttacker`, `OrgVictim` both installed, per `docs/setup.md` "Using Multiple GitHub Applications"). Attacker legitimately owns `OrgAttacker`'s GitHub App and therefore knows `OrgAttacker`'s `webhook_secret`.

1. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/production",
  "after": "<attacker-chosen-sha-that-exists-in-victim-repo>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgAttacker_webhook_secret, raw_body)`.
3. POST to `https://<shipit-host>/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner => "OrgAttacker"`, fetches `OrgAttacker`'s `GitHubApp`, and the signature validates (attacker used the correct, legitimately-known secret).
5. `PushHandler#process` resolves the target stacks via `Repository.from_github_repo_name("orgvictim/victim-repo")`, i.e., a stack owned by `OrgVictim`, and calls `stack.sync_github(expected_head_sha: ...)`, triggering GitHub sync/continuous-delivery behavior on a repository/organization the attacker never authenticated for.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
