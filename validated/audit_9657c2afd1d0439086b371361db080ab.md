### Title
Address definitions using `['address', 'BASE32']` re-evaluate the referenced address's *current* definition, letting the referenced party brick or freeze the outer (composite/shared) address - ([File: definition.js])

### Summary
`definition.js` supports an `['address', other_address]` operator that lets one address's spending condition depend on the *current on-chain definition* of another address, which is looked up live via `storage.readDefinitionByAddress` every time the outer address's authentifiers are validated. Because the referenced address's owner can redefine their own address at any time (via `address_definition_change`), they become an implicit "governance" party for every outer address that references them, exactly like the `AddressProvider`/`TransactionValidator` in the audited report: a party who is supposed to only provide auxiliary logic can unilaterally change the effective spending policy of a shared or dependent address, up to permanently bricking it.

### Finding Description
In `definition.js`, the `address` op is evaluated both at definition-validation time and authentifier-validation time by re-reading the referenced address's definition from storage rather than caching/binding it at address-creation time: [1](#0-0) [2](#0-1) 

The code explicitly documents that re-validating on every use is necessary because a referenced address can be redefined between spends, and calls out that this can make the outer address unusable: [3](#0-2) 

This is the same architectural flaw as the Brahma/Spearbit report: the "authorization" logic (the referenced address's definition) is not fixed/immutable relative to the entity that composed the outer policy (the shared/multisig address); it is fetched from a mutable source of truth (`storage.readDefinitionByAddress`, driven by whatever `address_definition_change` the referenced address last posted) that a single party — the owner of the referenced address — fully controls. If address `A`'s spending policy is `['and', [['sig',...], ['address', 'B']]]` (or similar composite/oracle-style condition depending on `B`), then `B`'s owner can:
1. Post an `address_definition_change` redefining `B` to a definition that can never produce a valid signature/authentifier for the paths under `['address','B']` in `A` (e.g., an unsatisfiable `sig` pubkey, or a condition with `'not'`/complex ops that always evaluates false for the required path) — permanently freezing `A`.
2. Redefine `B` to a much deeper/heavier definition, pushing complexity above `constants.MAX_COMPLEXITY`, causing `A`'s authentifier validation to always fail with `"complexity exceeded at "+path` (line 106-107) — again permanently freezing `A`.
3. Redefine `B` in a way that introduces recursive references back into `A` (or another address that itself references `A`), driving complexity/loop detection to fail deterministically (comment item 2 explicitly warns of this).

None of `A`'s own co-signers can prevent this: the redefinition happens entirely on `B`'s account, and `A`'s definition itself is immutable (per Obyte's definition-by-hash model) — there is no override mechanism analogous to `setGuard(address(0))` that `A`'s owners can invoke to detach from `B`. `A` is fully hostage to whatever `B` decides to become.

### Impact Explanation
Any composite address (shared wallet, escrow, conditional payment address, etc.) that includes an `['address', other_address]` reference to a *third-party-controlled* address can be permanently frozen by that third party redefining themselves, with no recourse for the outer address's legitimate owners. This is a fund-freezing / bricking vulnerability matching the "Governance can brick Safes" bug class: an ostensibly auxiliary, delegatable component (the referenced address's definition) is actually a live, mutable dependency that a single, potentially adversarial or compromised party controls, and there is no way for the dependent party to detach or override it once locked in.

### Likelihood Explanation
Medium likelihood: exploitation requires that some outer address was actually composed referencing an address controlled by a different, potentially adversarial party (e.g., an oracle-style or contractual co-signer relationship using `'address'` rather than `'sig'`/`'r of set'`), which is a supported and documented feature (`wallet_defined_by_addresses.js` / `wallet_defined_by_keys.js` construct definitions that may use this op). Any legitimate user relying on `'address'` references to a party they don't fully trust (or whose keys are later compromised) is exposed. The bug requires no special privilege beyond posting a normal `address_definition_change` for one's own address — a fully unprivileged, standard user action.

### Recommendation
- When an address definition references another address via `['address', other_address]`, capture/pin the referenced definition (or its chash) at the time the outer definition is created/finalized, rather than re-resolving it dynamically at every authentifier validation. Any future redefinition of `other_address` should not retroactively alter the effective spending policy of addresses that already reference it.
- Alternatively/additionally, provide an explicit, immutable escape/override mechanism in the outer definition (analogous to moving the override logic into the immutable guard itself in the Brahma fix) so composite addresses can detach from a redefined inner address without needing that inner address's cooperation.
- At minimum, document and strongly discourage using `'address'` to reference addresses controlled by parties whose incentives may diverge from the outer address's owners, since the current semantics make the outer address's usability entirely dependent on the referenced party's future behavior.

### Proof of Concept
1. Party B creates address `B0` with definition `D0 = ['sig', {pubkey: PK_B}]`.
2. Party A (in cooperation/agreement with B) creates a composite address `A0` with definition `['and', [['sig', {pubkey: PK_A}], ['address', 'B0']]]`, intending B to be a co-approver.
3. `A0` receives funds.
4. B posts `address_definition_change` for `B0`, changing its definition to something unsatisfiable in the context of the `['address','B0']` sub-path within `A0` — e.g. an `['sig', {pubkey: SOME_OTHER_UNKNOWN_KEY}]` that nobody (including B) can produce a valid signature for at that specific nested authentifier path, or a definition whose complexity exceeds `constants.MAX_COMPLEXITY` when evaluated inline (per `definition.js:106-107`).
5. Any subsequent attempt by A (and B) to spend from `A0` fails `validateAuthentifiers` (`definition.js:774-800`, `1454-1465`), returning `"complexity exceeded at "+path` or authentifier failure indefinitely, since the check is re-performed against B's *current* definition on every attempt.
6. `A0`'s funds are permanently frozen; A has no on-chain mechanism to detach from `B0`'s definition since `A0`'s own definition is immutable and contains no override path.
