### Title
KLAY Bridge Transfer Permanently Locks Funds When Recipient Contract Reverts — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge uses a bare low-level call to push KLAY to the recipient address and hard-reverts the entire transaction if that call fails. Because all nonce-accounting state updates happen before the transfer attempt, a revert rolls them back completely. If the recipient is a contract that cannot accept KLAY, the nonce is permanently unresolvable: the KLAY stays locked in the bridge forever and `lowerHandleNonce` can never advance past the stuck nonce.

---

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` executes in this order:

1. Nonce guard (`_lowerHandleNonceCheck`) — line 75
2. Vote accumulation (`_voteValueTransfer`) — line 77
3. Mark request tx hash (`_setHandledRequestTxHash`) — line 81
4. **Write** `handleNoncesToBlockNums[_requestedNonce]` — line 83
5. **Advance** `lowerHandleNonce` / `upperHandleNonce` via `_updateHandleNonce` — line 84
6. Emit `HandleValueTransfer` event — lines 86–96
7. **Transfer KLAY** to `_to` — line 98
8. `require(ok, "handleKLAYTransfer: transfer failed")` — line 99 [1](#0-0) 

If step 7 fails (recipient contract has no payable fallback, deliberately reverts, or runs out of gas), step 8 reverts the entire transaction. Because Solidity reverts unwind all state changes, steps 3–5 are also rolled back:

- `handledRequestTx[_requestTxHash]` is **not** set → operators can retry, but will always fail
- `handleNoncesToBlockNums[_requestedNonce]` is **never** written → `_updateHandleNonce`'s loop condition `handleNoncesToBlockNums[i] > 0` is never satisfied for this nonce
- `lowerHandleNonce` is **permanently stuck** at this nonce [2](#0-1) 

The `_to` address originates from the user's `RequestValueTransfer` event on the source chain. Bridge operators are obligated to relay it faithfully to `handleKLAYTransfer`. [3](#0-2) 

---

### Impact Explanation

**Permanent KLAY lock**: The KLAY deposited on the source chain is held in the destination bridge contract indefinitely. There is no pull-pattern fallback, no alternative recipient, and no admin escape hatch to recover it. The user's bridged assets are lost.

**`lowerHandleNonce` permanently frozen**: Because `handleNoncesToBlockNums[N]` is never written for the stuck nonce N, the `_updateHandleNonce` loop can never advance `lowerHandleNonce` past N. The `recoveryBlockNumber` is also frozen at the last successfully handled nonce. The off-chain recovery module (`ValueTransferRecovery`) will perpetually re-attempt the stuck nonce, consuming operator resources without progress. [4](#0-3) 

---

### Likelihood Explanation

Any user on the source chain can trigger this by specifying a `_to` address that is a contract without a payable fallback (e.g., a multisig, a DAO treasury, a proxy with no receive function, or a contract that deliberately reverts). This is a normal, valid user action. No privileged access is required. The bridge operators have no way to override the `_to` address without acting maliciously.

---

### Recommendation

Apply the pull pattern: instead of pushing KLAY directly to `_to`, record the pending balance in a mapping and provide a `claim()` function. At minimum, wrap the transfer in a `try/catch`-equivalent (using a success-check without `require`) and store unclaimed KLAY for later withdrawal:

```solidity
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;
}
```

Add a `withdraw()` function allowing `_to` to pull their balance. This matches the remediation pattern recommended in the referenced external report and eliminates the revert-blocking risk entirely.

---

### Proof of Concept

1. Deploy a contract `Rejecter` on the destination chain with no payable fallback (or one that explicitly `revert()`s).
2. On the source chain, call `requestKLAYTransfer(rejecter_address, 1 ether, "")` sending `1 ether + fee`.
3. Bridge operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer(txHash, from, rejecter_address, 1 ether, nonce, blockNum, "")` on the destination bridge.
4. The low-level call at line 98 returns `ok = false`; `require` at line 99 reverts the transaction.
5. All state updates (lines 81–84) are rolled back. The nonce is unresolved.
6. Operators retry — same result every time.
7. `lowerHandleNonce` never advances past `nonce`. The 1 KLAY remains locked in the bridge contract permanently. [5](#0-4) [6](#0-5)
