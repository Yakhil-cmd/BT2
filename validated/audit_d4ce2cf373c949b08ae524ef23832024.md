### Title
Malicious route venue can execute arbitrary token transfers under the caller’s authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
A user-supplied swap route can name an attacker-controlled pool address, and the router invokes that address without a venue or pool allowlist. [1](#0-0)  During that nested call, the malicious contract can request an unrelated `token.transfer(victim, attacker, amount)`; Soroban simulation records the transfer as a child of the caller’s authorization entry, and signing that tree authorizes the theft. [2](#0-1) 

### Finding Description
`execute_strategy` decodes pool, token, and output addresses directly from the caller-controlled `assets` registry. [3](#0-2)  Each swap instruction constructs `hop.pool` from `assets[idx_a]` and dispatches it to a venue adapter without checking that the pool is a legitimate or previously allowlisted venue contract. [4](#0-3)  The Aquarius adapter invokes the payload-selected pool’s `swap` function, while the Soroswap adapter invokes payload-selected `get_reserves` and `swap` functions. [5](#0-4) [6](#0-5) 

The controller protects only its own routed input: it authorizes one exact transfer from the controller to the router and then measures controller input/output balances. [7](#0-6)  Those checks do not prevent route-selected code from invoking a separate token contract that calls `victim.require_auth()`. [8](#0-7) 

The in-repository PoC demonstrates that a rogue pool’s transfer appears as a child invocation under `swap_collateral`; if the caller signs that simulated tree, the caller’s unrelated wallet token is transferred to the attacker while the swap still succeeds. [9](#0-8) [10](#0-9) 

### Impact Explanation
An attacker can steal arbitrary tokens held by a user who signs a malicious route’s authorization tree, including tokens unrelated to the listed lending assets. [11](#0-10)  This is theft of user funds rather than merely poor execution quality: the protocol’s measured-output check can still pass because the rogue venue additionally performs or arranges a valid output transfer. [12](#0-11) 

Affected caller-supplied routes include the controller strategy paths that reach `swap_tokens`, such as `swap_collateral`, and direct `execute_strategy` calls have the same authorization-tree exposure. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
Exploitation requires convincing a user to submit an attacker-crafted route and sign the resulting authorization tree. [15](#0-14)  The route is opaque packed XDR to a wallet user, and an honest simulation records the malicious token transfer beneath the top-level lending or router invocation rather than presenting it as an independent operation. [16](#0-15)  The likelihood is therefore moderated by the signature requirement, but the economic consequence can exceed the routed amount because any wallet token can be named by the rogue contract. [17](#0-16) 

### Recommendation
Restrict route-selected code and authorization scope rather than relying on clients to decode packed routes. [4](#0-3)  Prefer an owner-maintained venue/pool allowlist, route manifests that commit to every contract invoked, and wallet/API warnings that reject authorization trees containing token calls other than the expected input transfer. [15](#0-14)  At minimum, expose decoded route contracts in simulation and fail routes whose expected authorization tree contains unrelated token transfers. [18](#0-17) 

### Proof of Concept
1. The attacker deploys a contract whose `swap` method calls `token.transfer(victim, attacker, WALLET_BALANCE)`. [8](#0-7) 
2. The attacker constructs a route whose `assets` registry names that contract as the hop pool, while preserving a valid input token, output token, and minimum output. [11](#0-10) 
3. The victim calls `swap_collateral(caller, account_id, usdc_hub_asset, amount_in, eth_hub_asset, route)`. [19](#0-18) 
4. Simulation records a root `swap_collateral` authorization containing the malicious wallet-token transfer as a child. [16](#0-15) 
5. If the victim signs that tree, the swap succeeds, the victim receives the expected collateral output, and the attacker receives the victim’s entire unrelated token balance. [12](#0-11) [10](#0-9)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
