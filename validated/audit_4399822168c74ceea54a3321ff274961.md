This confirms the vulnerability. The binding that's broken is: **the organization used to select the webhook signing secret** (`repository.owner.login`, used in `WebhooksController#repository_owner`) versus **the repository actually written to** (`repository.full_name`, used in `Handler#repository_name` and `StatusHandler#process`). These two fields live in the same attacker-controlled JSON body and are never cross-validated against each other.

### Title
Cross-organization webhook forgery via mismatched signature-org and repository-full_name fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository.owner.login` (or `organization.login`) from the untrusted JSON body, while every webhook handler (`Handler#repository_name`, used e.g. by `StatusHandler`) resolves the target `Stack`/`Repository` using the independent `repository.full_name` field from the same body. Because Shipit supports multi-organization deployments (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`) with a distinct `webhook_secret` per organization, an attacker who legitimately knows/controls one organization's webhook secret (e.g. because they administer their own org's GitHub App installed on the same shared Shipit instance) can sign a payload whose `repository.owner.login` matches their own org (to pass signature verification) while setting `repository.full_name` to an arbitrary different organization/repo that they do not control.

### Finding Description
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `Shipit.github(organization: repository_owner)` to obtain that organization's `webhook_secret`, then verifies the raw POST body's HMAC signature against it. [1](#0-0) 
- `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), used by every concrete handler (`PushHandler`, `StatusHandler`, PR handlers, etc.), instead reads `payload.dig('repository', 'full_name')` to find the `Repository`/`Stack` that will be mutated. [2](#0-1) 
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) writes attacker-supplied `state`, `description`, `target_url`, `context`, `created_at` directly into a `Status` record for any commit matching `sha`, with no call back to the GitHub API to confirm the status is genuine. [3](#0-2) 
- Because the HMAC signature covers the entire raw request body, and the body's `repository.owner.login` and `repository.full_name` are independent JSON fields controlled entirely by whoever crafts the payload, nothing enforces that they refer to the same repository. GitHub itself would never produce an inconsistent payload, but the engine never checks this invariant itself.
- Multi-org support is an explicitly documented and tested configuration (`docs/setup.md:182-209`, `test/dummy/config/secrets_double_github_app.yml`), so a single Shipit instance frequently manages multiple, mutually untrusted organizations, each with its own webhook secret. [4](#0-3) 

The broken equality is: `organization authenticated (repository.owner.login, secret-checked)` ≠ `repository actually written to (repository.full_name, used by handlers)`.

### Impact Explanation
An attacker who is only privileged to know the webhook secret for one organization hosted on the shared Shipit instance (e.g., an admin of their own org's installed GitHub App — not privileged for the victim org) can forge webhook events that write directly into the victim organization's commit statuses (`Status` records), archive/unarchive review stacks (`ClosedHandler`, `ReopenedHandler`, `LabeledHandler`/`UnlabeledHandler`), or add/remove team memberships across arbitrary teams (`MembershipHandler`), all scoped to whatever `repository.full_name`/`sha`/`team` values they choose in the forged payload — none of which are re-validated against the signing organization. Forged commit statuses can flip a commit to `success`, unblocking CI gating and enabling an unauthorized deploy through the merge queue, which crosses the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitability requires (a) the target instance to be configured for multiple GitHub organizations (a documented, supported feature) and (b) the attacker to know a valid webhook secret for any one of those organizations — which is plausible for a deployment shared across a company with several loosely-trusted GitHub orgs/teams, or if a webhook secret for a lower-trust org ever leaks. No Shipit session, `ApiClient` token, or privileged access to the *victim* org is required.

### Recommendation
In `WebhooksController#verify_signature`, or in `Handler`, validate that the organization portion of `repository.full_name` (and/or `organization.login`) matches the `repository_owner`/organization whose secret validated the signature, rejecting the webhook (422) on mismatch. Alternatively, always derive both the signing-secret organization and the acted-upon repository from the same trusted field, and have handlers reject events whose `repository.full_name` organization differs from the authenticated organization.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, has a Shipit `Stack`/`Repository` tracking commit `abc123` with pending CI).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` using the known secret for `orgA`.
4. POST to `/github/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `GitHubApp`, and the signature validates successfully.
5. `StatusHandler#process` runs, looks up commits by `sha` (matching the victim's tracked commit) via `Commit.where(sha: params.sha)` — independent of any organization — and creates a `Status(state: "success", ...)` on the victim commit, potentially satisfying CI-required checks and enabling a merge/deploy the attacker does not otherwise have permission to trigger.
