### Title
Recalculated per-stake block-reward numerator can double-count already-distributed inflation rewards, causing the sum of `block_reward` fractions for a vote account to exceed its funded `pending_delegator_rewards`/sysvar balance and panic the validator - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`calculate_block_reward` splits a vote account's `pending_delegator_rewards` pool among its delegators using the fraction `stake / total_active_stake`, exactly mirroring the PoolTogether pattern of splitting a fixed reward pool via per-participant fractions. The function's own comment acknowledges that `stake` can end up larger than `total_active_stake`, and clamps only the *individual* reward to `pending_delegator_rewards`, not the *sum* across all delegators. When this happens during a stake-reward recalculation after a snapshot restore, the aggregate block rewards computed for a vote account's delegators can exceed what was actually escrowed for distribution, and the debit of that escrow uses an `.expect()` that panics rather than gracefully failing.

### Finding Description
`calculate_block_reward` computes, for each delegation to a vote account:
```
(pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
    .try_into().unwrap_or(u64::MAX)
    .min(pending_delegator_rewards)
``` [1](#0-0) 

The `total_active_stake` denominator comes from a fixed, per-epoch snapshot (`reward_epoch_delegated_stakes`), but the `stake` numerator is derived from the *current* `Delegation` in `StakesCache` at call time via `delegation_effective_stake` [2](#0-1) . The function's own comment states the risk explicitly:

> "During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`... individual rewards look greater than the pending rewards. This is harmless in practice, but we clamp it just to be safe." [3](#0-2) 

This clamp is only applied per-delegation (`.min(pending_delegator_rewards)`), never across the whole set of delegators for that vote account — exactly the "sum of fractions can exceed 1.0" defect from the reference report. `recalculate_stake_rewards` (invoked after snapshot restore via `recalculate_partitioned_rewards_if_active`) re-runs `calculate_stake_rewards_and_commissions`, which re-invokes `calculate_block_reward` against the *current* (post-partial-distribution) `StakesCache` entries [4](#0-3) , while the `total_active_stake` snapshot used for the denominator is not refreshed to reflect prior distributions [5](#0-4) . A delegation whose `Delegation::stake` field was already bumped by a previously-distributed inflation reward will therefore compute an inflated `stake` numerator relative to the original (rewarded-epoch) `total_active_stake` denominator, producing a larger-than-intended share of `pending_delegator_rewards` for that delegator on top of whatever was already correctly paid out for the earlier partitions.

Whatever is computed as `block_reward_lamports_distributed` is subsequently debited from the `epoch_rewards` sysvar account:
```
account.checked_sub_lamports(debit_block_reward_lamports)
    .expect("epoch reward sysvar has enough lamports for distribution");
``` [6](#0-5) 

If the recalculated per-partition block rewards sum to more than what remains escrowed in the sysvar (because an earlier partition already consumed part of the pool and the later, recalculated partition over-counts due to the numerator/denominator mismatch above), this `.expect()` panics.

The codebase already contains a regression test guarding the analogous *inflation* `stake_reward` computation against exactly this kind of denominator drift (`test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`), which asserts the recalculated reward matches the original using "the same AG delegated stake denominator as the original epoch-boundary calculation" [7](#0-6) . No equivalent test or guard exists for `block_reward`/`calculate_block_reward`, and the existing property test for `calculate_block_reward` only checks that an *individual* reward never exceeds `pending_delegator_rewards`, not that the sum across all delegators of a vote account stays within budget [8](#0-7) .

### Impact Explanation
Because reward calculation/recalculation is deterministic and runs identically on every validator, an over-counted `block_reward` sum in a distribution partition would cause the `.expect()` panic in `update_epoch_rewards_sysvar` to fire on all validators simultaneously at the same block height during epoch-boundary reward distribution. This constitutes a network-wide, deterministic halt at an epoch boundary — one of the concrete, in-scope impact categories (cross-node/consensus halt caused by a shared deterministic bug, not a single node's fault). It is not a validator-operator misconfiguration issue; it is a protocol-level accounting flaw in the reward-splitting logic reachable purely through the normal reward-distribution/recalculation code path (e.g., triggered by a snapshot-restore recalculation mid-distribution, which is a standard, expected code path via `initialize_after_snapshot_restore`) [9](#0-8) .

### Likelihood Explanation
The condition requires: (1) block revenue sharing / Alpenglow reward distribution active, (2) a partial distribution of rewards to some delegators of a vote account already completed, and (3) a recalculation of remaining rewards being triggered (e.g., snapshot restart) before all partitions for that epoch's rewards are fully distributed, such that a delegation's on-chain `stake` value already reflects an earlier partition's reward while the fixed `total_active_stake` snapshot does not. This is a state that can occur with routine node restarts/snapshot loads during an active multi-block reward distribution window, and requires no adversarial input — only ordinary validator restart timing relative to reward-distribution progress. The magnitude of the discrepancy is bounded by how much of a single delegation's stake was already rewarded relative to `total_active_stake`, so it may often be small, but the resulting panic path has no graceful degradation — even a 1-lamport shortfall triggers the `.expect()`.

### Recommendation
- In `calculate_block_reward`/`calculate_stake_rewards_and_commissions`, ensure the `stake` numerator used for `pending_delegator_rewards` splitting reflects the stake as of the **rewarded epoch** (pre-reward) rather than the current, possibly-already-rewarded `Delegation::stake`, mirroring the guard already used for the inflation `stake_reward` path.
- Track and cap the running total of block rewards already distributed for a vote account across partitions/recalculations so the sum can never exceed `pending_delegator_rewards` (or the funded sysvar block-reward escrow), rather than clamping only per-delegation.
- Replace the `.expect()` in `update_epoch_rewards_sysvar`'s `checked_sub_lamports` with a saturating operation or an explicit, tested invariant proof that ties the funded escrow amount to the exact sum that will ever be debited across all recalculations, eliminating the panic path entirely.

### Proof of Concept
A full deterministic repro requires orchestrating: (1) a stake account receiving an inflation-only reward in an early distribution partition (bumping `Delegation::stake`), (2) a bank/snapshot restart before the epoch's reward distribution completes, forcing `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards` → `calculate_stake_rewards_and_commissions` → `calculate_block_reward` to re-derive block rewards for the remaining partitions using the now-inflated `Delegation::stake`, and (3) verifying that the summed `block_reward_lamports_distributed` across partitions exceeds the escrowed sysvar balance, triggering the `.expect()` panic in `update_epoch_rewards_sysvar`. I was not able to fully trace, within the available index, the exact code path that computes the total `block_rewards` amount used to fund `create_epoch_rewards_sysvar`, so I cannot confirm from source alone whether existing safety margins (e.g., over-funding of the escrow) already absorb this discrepancy in practice — this should be verified with a live/dynamic proof-of-concept test analogous to `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` but targeting `block_reward` instead of `stake_reward`, and asserting on the sysvar debit instead of on reward equality.
