### Title
Cross-organization webhook forgery: signature is verified against the org owning `repository.owner.login`, but handlers act on the unrelated `repository.full_name` in the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to HMAC-verify the request against based on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body, then, once verification passes, hands the exact same body to event handlers that instead key off `repository.full_name` to decide which `Stack`/`Repository` to mutate. In a multi-organization Shipit deployment (the documented "Using Multiple Github Applications" mode), these two fields are never checked to belong to the same organization, so a payload can carry one org in `repository.owner.login` (to pick a known webhook secret) and a completely different org/repo in `repository.full_name` (to pick the target of the action).

### Finding Description
`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization when the multi-app config schema is used (`lib/shipit.rb:170-200`, `docs/setup.md` "Using Multiple Github Applications"). The webhook signature check derives that organization purely from the request body: [1](#0-0) [2](#0-1) 

Once `verify_signature` succeeds, `create` parses the whole raw body and dispatches to handlers for the event type: [3](#0-2) 

Every handler, however, resolves its target `Repository`/`Stack` from a *different* field of the same body, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

For example `PushHandler` uses that repository's stacks and triggers a GitHub sync job carrying an attacker-supplied `after` SHA: [5](#0-4) 

`Stack#github_app`/`Repository#github_app` then fetch the API token for whichever organization actually owns the *targeted* repository (i.e. the org named in `full_name`), independent of which org's secret was used to authenticate the request: [6](#0-5) [7](#0-6) 

This is exactly the "analog" of the reported bug class: an attribute is used to authenticate the request (the organization/secret binding, analogous to the EOA `sender` recovered from the tx signer) while a *different* attribute inside the same signed blob (`repository.full_name`, analogous to the ERC20 `Recipient`/`origin`) is what the downstream logic actually trusts and acts on. The signature guarantees the body wasn't tampered with by a third party, but it does not guarantee that `repository.owner.login` and `repository.full_name` refer to the same tenant — the engine never cross-checks the two.

### Impact Explanation
In a Shipit instance configured with multiple GitHub organizations (each with its own GitHub App and `webhook_secret`, as `docs/setup.md` explicitly documents), an entity that legitimately controls Org A's GitHub App settings (and thus knows Org A's `webhook_secret`, which they are entitled to as the admin of their own App/organization) can craft an arbitrary JSON body, set `repository.owner.login` to `"OrgA"` (so `verify_signature` selects and validates against Org A's secret) while setting `repository.full_name` to `"OrgB/some-repo"` and `after` to an SHA of their choosing. This request passes signature verification (it is validly HMAC-signed with a secret the requester legitimately possesses) yet is routed to handlers that operate on Org B's `Stack`, using Org B's own GitHub App credentials to fetch/sync commits (`GithubSyncJob`, `PushHandler`). This lets a tenant that is only supposed to control Org A's repositories force GitHub sync activity, mark stacks accessible/inaccessible, or otherwise drive cross-tenant state changes on Org B's stacks that they have no authorization over — a cross-repository/cross-organization write triggered purely by an authentication check that binds the wrong field.

### Likelihood Explanation
This requires a Shipit deployment using the multi-organization GitHub App configuration (a supported, documented feature), and requires the attacker to control at least one of the configured organizations/apps (i.e., know that org's `webhook_secret`, which they legitimately possess as the app owner of their own tenant). Given that condition, exploitation is trivial: it is a single crafted POST to the shared `/webhooks` endpoint with mismatched `repository.owner.login`/`repository.full_name` fields, no other secrets or elevated access needed.

### Recommendation
After `verify_signature` succeeds, re-derive the organization from the same field the handlers use (`repository.full_name`'s owner, or `organization.login`) and reject the request if it does not match the organization whose secret validated the signature. Alternatively, verify the signature using every configured organization's secret and only proceed if the organization that validates the signature is the same one that owns the targeted repository/stack.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section), and a `Stack` tracking `OrgB/target-repo`.
2. As the party controlling `OrgA`'s GitHub App (who legitimately knows `OrgA`'s `webhook_secret`), build a push-event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies successfully against `OrgA`'s secret.
5. `PushHandler#process` resolves the target via `repository.full_name` = `"OrgB/target-repo"`, finds `OrgB`'s stacks, and enqueues `GithubSyncJob` with `expected_head_sha` set to the attacker-chosen SHA — actions performed against `OrgB`'s stack using `OrgB`'s own GitHub App credentials, despite the request only having been authenticated as `OrgA`.
