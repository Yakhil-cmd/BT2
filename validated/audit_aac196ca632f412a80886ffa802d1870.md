### Title
`MembershipHandler#process` resolves `Team` solely by GitHub `team.id`, letting a webhook signed by *any* configured organization mutate a `Team`/`Membership` belonging to a different organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` using only `github_id: params.team.id`, with no check that the found team's `organization` matches the organization that produced a valid signature (`repository_owner`). Because signature verification is performed per-organization (`Shipit.github(organization: repository_owner)`), an attacker who administers *any* organization onboarded to Shipit (and therefore knows/controls that organization's own configured webhook secret) can sign a `membership` payload with an arbitrary `team.id` value and have it applied to whatever `Team` row already has that `github_id`, even if that row belongs to a completely different, unrelated organization.

### Finding Description
The intended binding is: `Team found/mutated by MembershipHandler#process == Team belonging to organization == repository_owner that passed verify_signature`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-49) computes `repository_owner` from the payload's `organization.login` and verifies the signature using `Shipit.github(organization: repository_owner)`'s own `webhook_secret` [1](#0-0) [2](#0-1) . This only proves the request was signed with the secret belonging to whichever organization login the attacker put in the payload — it says nothing about the `team.id` field.
- `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { ... }` [3](#0-2) . The lookup key is `github_id` only, not scoped by `organization`. If a `Team` row already exists with that `github_id` (e.g., a legitimately onboarded team belonging to organization "victim"), `find_or_create_by!` returns that existing record regardless of the `organization.login` in the current, attacker-signed payload.
- `process` then calls `team.add_member(member)` or `team.members.delete(member)` on that resolved (and possibly mismatched) `Team` [4](#0-3) , mutating `Membership` rows for an organization the current request never proved control over.

Exploit: an attacker who administers Organization A (already onboarded to Shipit, so they know Organization A's webhook secret because they configured GitHub's webhook to point at Shipit with a secret shared during onboarding) crafts a `membership` `added` event with `organization.login = "org-a"`, `member.login = <attacker's own GitHub login>`, and `team.id` equal to the `github_id` of a `Team` row that actually belongs to victim Organization B (e.g., a team referenced in `Shipit.github_teams` used for authorization, or any team used by another stack). `verify_signature` validates fine because the signature matches Organization A's own secret; `drop_unhandled_event`/`ExplicitParameters` schema also pass since the payload is well-formed. `find_or_create_team!` finds the pre-existing Organization‑B `Team` row by `github_id` and `team.add_member(member)` inserts a `Membership` binding the attacker to Organization B's team.

`User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) , so if the targeted `Team` is one of the IDs configured in `Shipit.github_teams`, the attacker becomes "authorized" purely by forging their own organization's signature over a `team.id` value they do not control and never verified.

None of the existing guards catch this: `verify_signature` verifies organization-vs-secret binding but not organization-vs-`team.id`; `ExplicitParameters` only validates types/presence, not cross-referential ownership; `drop_unhandled_event` only checks the event is handled.

### Impact Explanation
A successful exploit lets an attacker add themselves (or any GitHub login) as a `Membership` on a `Team` row belonging to a different, unrelated organization, using only credentials/secrets for an organization they legitimately administer. If that target `Team`'s `id` happens to be included in the host's `Shipit.github_teams` configuration, this directly escalates the attacker into Shipit's authorization group (`User#authorized?`), which the rules classify as High severity ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any `Team` row whose `github_id` the attacker can guess or enumerate (team IDs are small sequential integers on GitHub, and Shipit itself exposes them in fixtures/DB), and can be repeated for `removed` events to strip legitimate members from an unrelated team as a denial of trust/authorization to that org.

### Likelihood Explanation
Preconditions: the attacker must administer at least one organization that is already integrated with the target Shipit instance (has a configured GitHub App/webhook and knows its own `webhook_secret`) — a low bar since Shipit's model supports many independent organizations/teams sharing one deployment, and per the threat model the attacker "administers" an org and can emit webhooks from it. The attacker needs to know or guess the numeric `github_id` of the target `Team`; these are visible via GitHub's public team API in some cases, or via existing Shipit data/URLs, and are otherwise a small integer easily brute-forced with repeated `POST /webhooks` requests since no cross-check exists. No GitHub secrets, session tokens, or Shipit admin access are needed beyond control of one legitimately onboarded organization.

### Recommendation
Scope the `Team` lookup by both `github_id` and the verified organization, and refuse to mutate a `Team` whose stored `organization` does not match the payload's/`repository_owner`'s organization, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "team #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  team || Team.create!(github_id: params.team.id, github_team: params.team, organization: params.organization.login)
end
```
Additionally, pass the controller's already-verified `repository_owner` into the handler and assert it equals `params.organization.login` before any mutation, rather than trusting the unscoped `team.id` alone.

### Proof of Concept
minitest (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, illustrative — actual location must remain outside excluded `test/**` restrictions only for judging category classification, not for placement):
```ruby
test "process does not add a member to a team belonging to a different organization" do
  victim_team = shipit_teams(:shopify_developers) # organization: "shopify", github_id: 1
  attacker_login = "attacker"

  payload = Shipit::Webhooks::Payload.new(
    action: 'added',
    team: { id: victim_team.github_id, name: 'Cooks', slug: 'cooks', url: 'https://example.com/cyclimse/cooks' },
    organization: { login: 'cyclimse' }, # attacker's own, legitimately-signed org
    member: { login: attacker_login }
  )

  handler = Shipit::Webhooks::Handlers::MembershipHandler.new(payload)
  handler.process

  # Binding under test: team mutated must belong to the org that authenticated the request
  assert_not_includes victim_team.reload.members.map(&:login), attacker_login,
    "attacker should not be added to a Team belonging to organization 'shopify' " \
    "via a request signed only for organization 'cyclimse'"
end
```
Before the fix, this assertion fails: `team.add_member(member)` runs against `shopify_developers` (id 1, organization `shopify`) even though the payload's `organization.login` is `cyclimse`, because `find_or_create_team!` matches solely on `github_id`.
