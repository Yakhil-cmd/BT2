### Title
Stale liquidation payment leg reverts the entire liquidation, delaying repayment of remaining unhealthy debt - (File: contracts/controller/src/positions/liquidation/math.rs)

### Summary
`liquidate` accepts multiple debt-payment legs, but every requested `HubAssetKey` must still have a stored borrow position at execution. If a competing repayment or liquidation removes one selected debt leg after the keeper prepared the transaction, `calculate_repayment_amounts` panics with `DebtPositionNotFound`, aborting repayment of the account's remaining debt legs and seizure of collateral. [1](#0-0) 

### Finding Description
The permissionless `liquidate(liquidator, account_id, debt_payments, seize_mode)` path authenticates the liquidator and builds one atomic liquidation plan from the caller's full `debt_payments` vector. [2](#0-1) 

After the global `health_factor < 1 WAD` check, `normalize_repayment_plan` calls `calculate_repayment_amounts`. [3](#0-2) [4](#0-3) 

That function panics when any payment key is absent from `account.borrow_positions`:

```rust
let position: DebtPosition = (&account
    .borrow_positions
    .get(hub_asset.clone())
    .unwrap_or_else(|| panic_with_error!(env, CollateralError::DebtPositionNotFound)))
    .into();
``` [5](#0-4) 

Because Soroban contract failure aborts the whole invocation, no subsequent valid payment leg is processed. The existing regression test confirms that a supported asset without a debt position causes `DEBT_POSITION_NOT_FOUND`. [6](#0-5) 

A typical race is:

1. A keeper observes that account `X` owes `A`, `B`, and `C` and calls `liquidate(X, [(A,a),(B,b),(C,c)], Transfer)`.
2. Before execution, an unprivileged third party repays or liquidates the entire `A` debt through `repay` or another `liquidate` call.
3. `X` still owes `B` and `C` and remains `HF < 1`, but `A` no longer exists in `borrow_positions`.
4. The keeper's transaction reaches `calculate_repayment_amounts` and reverts on `A`, so `B` and `C` remain unpaid and no collateral is seized.

### Impact Explanation
This creates a denial-of-service window for multi-market liquidations: one stale debt leg invalidates repayment of all other still-valid debt legs. Repeated races can leave an account undercollateralized for longer, increasing the probability that it becomes insolvent and that its eventual `clean_bad_debt` socializes losses into supplier indexes. [7](#0-6) 

The consequence is not merely wasted gas. Delayed liquidation can convert a solvent-but-liquidatable position into bad debt, causing protocol insolvency borne by suppliers.

### Likelihood Explanation
Liquidation is permissionless and only requires liquidator authorization, so competing liquidators and borrowers can change the debt book between simulation and inclusion. [8](#0-7) 

Any account with debt in multiple `(hub_id, asset)` books exposes this failure whenever a keeper submits a multi-leg repayment plan. The stale leg need not become healthy individually; it only has to be fully removed before execution.

### Recommendation
Skip payment legs whose borrow position disappeared instead of panicking, then require that at least one valid repayment leg remains. For example, treat a missing `borrow_positions` entry as a refund/skip case during normalization:

```rust
let Some(raw_position) = account.borrow_positions.get(hub_asset.clone()) else {
    refunds.push_back(PaymentTuple {
        asset: hub_asset.asset.clone(),
        amount,
    });
    continue;
};
let position: DebtPosition = (&raw_position).into();
```

The existing final `require_non_empty_payments(&result.repaid)` still rejects a transaction in which every requested debt leg disappeared. [9](#0-8) 

### Proof of Concept
Conceptual reproduction:

```rust
// Account has debt in A and B and HF < 1.
let payments = vec![
    &env,
    (hub_asset_a.clone(), 100),
    (hub_asset_b.clone(), 100),
];

// Another caller fully repays A first.
controller.repay(&anyone, &account_id, &vec![&env, (hub_asset_a.clone(), 0 /* full A */)]);

// The planned liquidation still has B debt and remains profitable/healthy to close,
// but it reverts before B is processed.
let result = controller.try_liquidate(
    &liquidator,
    &account_id,
    &payments,
    &SeizeMode::Transfer,
);

// Reverts with DebtPositionNotFound; B debt and collateral seizure are not executed.
```

The vulnerable ordering is direct: `build_liquidation_plan` performs the health check first, while `calculate_repayment_amounts` later requires every caller-selected key to remain in `borrow_positions`. [10](#0-9) [11](#0-10)
