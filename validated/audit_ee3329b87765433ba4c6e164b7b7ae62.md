### Title
Webhook signature validated against `repository.owner.login` while all handlers act on the independent, unverified `repository.full_name` field, allowing cross-organization stack forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` looks up the GitHub App/webhook secret to check using `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` (or `organization.login`) [2](#0-1) . Every webhook handler, however, resolves the target `Repository`/`Stack` using a completely different JSON path, `payload.dig('repository', 'full_name')` [4](#0-3) . Because both values live in the same unauthenticated request body and are read out independently, there is no guarantee that `owner.login` and the owner segment of `full_name` refer to the same organization.

### Finding Description
`Shipit.github(organization: repository_owner)` fetches the `GithubApp`/secret configured for whatever organization name the attacker places at `repository.owner.login` [3](#0-2) . `GithubApp#verify_webhook_signature` HMACs the raw body against that org's `webhook_secret`, and critically, `return true unless webhook_secret` — verification is a no-op if that particular organization has no `webhook_secret` configured (which is the documented default: `webhook_secret: # nil` in `config/secrets.development.example.yml`) [5](#0-4) .

Meanwhile, the actual write target — which `Repository`/`Stack` records get updated by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. — is resolved solely from `repository.full_name` via `Handler#repository_name`/`#stacks` [1](#0-0) , a field that is never compared against `repository.owner.login`.

The equality that should hold but does not:
`organization whose secret authenticated the request` == `organization owning the repository/stack that handlers mutate`

Because both are independently attacker-supplied strings inside the same JSON body that is only checked for a valid signature *after* being parsed for `repository_owner`, an attacker who can produce a payload that passes signature verification for organization A (e.g., an org configured with no `webhook_secret`, or one whose secret leaked) can set `repository.full_name` to `victim-org/victim-repo` while keeping `repository.owner.login` = `org-with-no-secret`, thereby passing `verify_signature` yet having the handler operate on `victim-org`'s stacks — updating commit statuses, triggering `GithubSyncJob` for pushes, refreshing check runs, or fabricating team `membership` events for an org the attacker never authenticated against.

### Impact Explanation
This breaks the binding between "the organization whose credentials verified this webhook" and "the repository being written to," which the rules classify as High: unauthenticated write of stack state (commit statuses, sync triggers, check-run refresh, or team membership creation) for organizations/repositories the attacker has no legitimate relationship with, as long as any one configured organization has a missing/weak `webhook_secret`.

### Likelihood Explanation
Requires that at least one GitHub organization configured in `Shipit.github` (a multi-org Shipit deployment) has `webhook_secret` unset — the documented default — or that its secret is otherwise known to the attacker (no other credential needed). Given the `Shipit.github(organization: ...)` multi-tenant configuration pattern is explicitly supported and documented, this is a realistic deployment shape.

### Recommendation
Verify the webhook signature using a secret that cannot itself be chosen by the attacker-controlled payload, and cross-check that `repository.owner.login` matches the owner portion of `repository.full_name` before dispatching to handlers. Do not treat `webhook_secret` absence as automatic pass; require it configured, or bind signature verification to a fixed installation identity rather than a field read out of the same unauthenticated body.

### Proof of Concept
1. Deploy Shipit configured with two orgs: `org-a` (no `webhook_secret` set) and `org-b` (has stacks/repositories tracked, secret unknown to attacker).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
   ```json
   { "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }, "after": "<attacker-controlled sha>" }
   ```
3. `verify_signature` calls `Shipit.github(organization: "org-a")`, whose `verify_webhook_signature` returns `true` unconditionally because `org-a` has no `webhook_secret` [5](#0-4) .
4. `PushHandler`/`Handler#stacks` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `GithubSyncJob` against `org-b`'s real stack [1](#0-0) , even though the request was never signed by `org-b`'s GitHub App.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
