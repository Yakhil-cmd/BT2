### Title
SSRF via peer-controlled arbiter contract leads to outbound HTTP requests to attacker-influenced ArbStore URLs, leaking private dispute data - (File: arbiter_contract.js)

### Summary
The GLPI advisory describes an SSRF where an authenticated actor can make the server issue outbound HTTP requests to attacker-chosen targets via the Webhook feature. In `ocore`, `arbiter_contract.js` has an analogous pattern: a wallet automatically issues outbound HTTP requests (`httpRequest`) to a URL that is resolved from an `arbiter_address` field that is fully supplied by an untrusted counterparty in a P2P "arbiter contract" offer, without any validation of the URL's destination.

### Finding Description
When a peer sends an `arbiter_contract_offer` device message, the receiving wallet stores the contract via `store()` [1](#0-0) , including the `arbiter_address` field, which is chosen entirely by the remote peer and is not validated against any allow-list of trusted arbiters.

Later, when the local user interacts with this contract (`openDispute`, `appeal`, `getAppealFee`), the code resolves an ArbStore URL for that `arbiter_address` via `device.requestFromHub("hub/get_arbstore_url", objContract.arbiter_address, ...)` and then immediately performs an outbound HTTP POST containing sensitive contract data to that URL using `httpRequest`: [2](#0-1) [3](#0-2) [4](#0-3) 

`httpRequest` performs a raw `http.request`/`https` call to whatever host/path is resolved, with no restriction on scheme, host, or IP range (no blocking of loopback/link-local/internal addresses): [5](#0-4) 

The URL is not chosen by the local user — it is looked up per `arbiter_address`, a value taken directly from the untrusted contract offer. Since any device can act as an "arbiter" and register itself with a hub-served `arbstore_url` for its own address (see `arbiters.js`, which performs the equivalent lookup/fetch pattern via `device.requestFromHub` and `requestInfoFromArbStore`) [6](#0-5) , a malicious counterparty can name themselves (or a colluding device) as the `arbiter_address` in a contract offer sent to a victim, causing the victim's wallet to later send POST requests containing the dispute payload — including `encrypted_contract`, `my_pairing_code`, `peer_pairing_code`, `contact_info`, and potentially private asset amount/asset id — to a URL under attacker control at `openDispute()` time [7](#0-6) .

This is not a "malicious-hub" scenario: the victim queries their own configured/trusted hub, but the hub is only acting as a directory that maps an arbiter address (attacker-chosen, since the attacker can be the arbiter) to a URL that the attacker itself registered for their own address. The attacker fully controls the destination even though the request path passes through the victim's trusted hub.

### Impact Explanation
The outbound request from `openDispute`/`appeal`/`getAppealFee` carries sensitive data: an `encrypted_contract` package, both parties' pairing codes (`my_pairing_code`, `peer_pairing_code` used for device pairing), contact info, and — when the asset is private — the private `asset` and `amount` fields of the underlying trade: [8](#0-7) 
An SSRF here can be used to (a) probe/exfiltrate data toward internal network endpoints reachable from the victim's node/wallet process, and (b) leak pairing codes and private contract/payment metadata to an attacker-controlled server, since `httpRequest` has no destination restrictions (arbitrary host/port/scheme reachable from the process).

### Likelihood Explanation
Any counterparty in a peer-to-peer arbiter-mediated payment can trigger this by simply proposing a contract naming themselves (or a colluding device) as `arbiter_address`; no special privilege is required beyond normal device pairing/chat capability used for contract offers. The victim only needs to proceed with the normal dispute/appeal workflow, which is the expected UX for this feature, making exploitation straightforward once a counterparty accepts and later disputes/appeals such a contract, or the victim initiates the dispute themselves believing the arbiter to be legitimate.

### Recommendation
- Validate/allow-list the resolved `arbstore_url` before making outbound requests in `httpRequest` (`arbiter_contract.js`) and in `requestInfoFromArbStore` (`arbiters.js`): enforce HTTPS, reject loopback/link-local/private IP ranges and non-standard ports, and resolve DNS to confirm the target is not an internal address.
- Consider requiring arbiter addresses to be selected from a signed/known registry rather than trusting whatever `arbiter_address` a remote party supplies in a contract offer.
- Avoid sending sensitive fields (`encrypted_contract`, pairing codes, private asset/amount) to a URL that is derived from attacker-influenced data without the local user explicitly confirming/trusting that specific arbiter/ArbStore endpoint.

### Proof of Concept
1. Attacker device registers itself as an "arbiter" with its own hub-served `arbstore_url` pointing to an attacker-controlled server (or an internal address such as `http://127.0.0.1:<port>` / a cloud metadata endpoint reachable from the victim's environment).
2. Attacker sends the victim an `arbiter_contract_offer` with `arbiter_address` set to the attacker's own address, using normal contract fields (title/text/amount/asset) [9](#0-8) .
3. Victim accepts and later opens a dispute (or requests the appeal fee) on this contract, which triggers `openDispute()`/`getAppealFee()`: [2](#0-1) [4](#0-3) 
4. The victim's node resolves the `arbstore_url` for the attacker's `arbiter_address` via `hub/get_arbstore_url` and issues an HTTP POST directly to that URL/host with the dispute payload (including pairing codes and, when applicable, private-asset amount/asset), demonstrating outbound SSRF to an attacker-influenced destination with data exfiltration.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

"use strict";
var db = require('./db.js');
var device = require('./device.js');
var http = require('https');
var validationUtils = require('./validation_utils.js');

var arbStoreInfos = {}; // map arbiter_address => arbstoreInfo {address: ..., cut: ...}

function getInfo(address, cb) {
	cb = cb || function() {};
	db.query("SELECT device_pub_key, real_name FROM wallet_arbiters WHERE arbiter_address=?", [address], function(rows){
		if (rows.length && rows[0].real_name) { // request again if no real name
			cb(null, rows[0]);
		} else {
			device.requestFromHub("hub/get_arbstore_url", address, function(err, url){
				if (err) {
					return cb(err);
				}
				if (!validationUtils.isNonemptyString(url))
					return cb("invalid url received from hub");
				requestInfoFromArbStore(url+'/api/arbiter/'+address, function(err, info){
					if (err) {
						return cb(err);
					}
					if (!validationUtils.isNonemptyObject(info))
						return cb("invalid arbiter info received from arbstore");
					db.query("REPLACE INTO wallet_arbiters (arbiter_address, device_pub_key, real_name) VALUES (?, ?, ?)", [address, info.device_pub_key, info.real_name], function() {cb(null, info);});
				});
			});
		}
	});
}

function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}
