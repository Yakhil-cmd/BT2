### Title
Api::CCMenuController allows a stack-scoped CCMenu token to read the build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The external report's bug class is: a resource identifier acted upon (the NFT `tokenId`) is never checked against the identifier the caller was actually authorized for. In Shipit's API layer, the equivalent trust binding is: **the `Stack` a `token` authorises == the `Stack` a request touches**. `Shipit::Api::BaseController` enforces this by scoping lookups through `stacks` (filtered by `current_api_client.stack_id`), but `Shipit::Api::CCMenuController` overrides `stack` and bypasses that scope entirely, breaking the binding.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id` [1](#0-0) . `CCMenuUrlController` creates exactly such a scoped, `read:stack`-only client for a specific stack and hands out its `authentication_token` to be embedded in a CCMenu feed URL [2](#0-1) .

`Shipit::Api::BaseController` is supposed to enforce that a scoped client can only ever resolve stacks it is authorized for:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

However, `Shipit::Api::CCMenuController` redefines `stack` to load directly from the global `Stack` relation, ignoring the `stacks` scoping helper and the `current_api_client.stack_id` binding entirely:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string on the `ApiClient` record — it never checks which `stack_id` the token is bound to [5](#0-4) [6](#0-5) . Any `params[:stack_id]` value is accepted, so a token minted for stack A can be replayed with `stack_id` set to stack B, and `show` will render stack B's build status, last deploy id, and stack `to_param` (used as the CCMenu project name) [7](#0-6) [8](#0-7) .

Before vs. after the equality that should hold:
- Before (intended): `token.stack_id == requested_stack.id` (enforced identically in every other API controller through `BaseController#stack`).
- After (actual, in CCMenuController): `requested_stack` is chosen independently of `token.stack_id`; the equality is never checked.

### Impact Explanation
This is an unauthenticated-scope escalation: possession of any valid stack-scoped CCMenu token (which is routinely embedded in plaintext CCMenu/CCTray feed URLs, often stored in CI dashboards or shared build-radiator tools) grants read access to the build/deploy status of every stack in the Shipit instance, not just the one it was issued for. This matches the "High — unauthenticated read of stack state ... deploy output" impact category, since the attacker did not authenticate as the owning user or obtain a client scoped to the target stack; they only needed *some* valid token.

### Likelihood Explanation
Likelihood is high for anyone who already holds one legitimate CCMenu token (these tokens are designed to be shared/embedded in CI dashboards, precisely the scenario the `stack_id` scoping was meant to contain). No privileged credentials, GitHub App keys, or session are required — only a previously issued CCMenu token for any stack and knowledge/guessing of another stack's `to_param`/slug.

### Recommendation
Make `Api::CCMenuController#stack` go through the same `stacks` scoping helper as `BaseController`, e.g. remove the controller-local override and rely on `stacks.from_param!(params[:stack_id])`, or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
1. Visit stack A's settings page (or call `CCMenuUrlController#fetch`) to obtain a CCMenu URL such as `GET /api/1/stacks/org/repo/staging/cctray.xml?token=<token_A>`, where `token_A` decodes to an `ApiClient` with `stack_id = A.id` and `permissions = ['read:stack']` [9](#0-8) .
2. As an attacker holding only `token_A` (e.g., scraped from a shared CI dashboard), request stack B's feed instead: `GET /api/1/stacks/other-org/other-repo/production/cctray.xml?token=<token_A>`.
3. `authenticate_api_client` accepts `token_A` (it is a valid token) [10](#0-9) ; `require_permission :read, :stack` passes because `token_A`'s `ApiClient` has `read:stack` [11](#0-10) ; `stack` resolves stack B directly from `Stack.from_param!` with no `stack_id` check [12](#0-11) .
4. The response renders stack B's `lastBuildStatus`, `lastBuildLabel` (deploy id), and `activity`, none of which the `token_A` holder should be entitled to see [8](#0-7) .

Note: I was unable to find a test in the indexed portion of `test/controllers/ccmenu_controller_test.rb` that exercises a mismatched `stack_id`, and the full contents of `test/controllers/api/ccmenu_controller_test.rb` were not returned by search — it is possible tests for this specific cross-stack scenario exist and are worth checking directly in a full checkout before filing.

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
```
