### Title
Stack-scoped API token can read any stack's CI/build status via `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` lookup used by every other API controller and resolves the target stack from the raw `Stack` model instead of the request-scoped `stacks` relation, breaking the binding between the stack an `ApiClient` token is authorized for and the stack the endpoint actually touches.

### Finding Description
`Shipit::Api::BaseController` establishes the trust boundary for all API endpoints: a token can be created scoped to a single stack (`ApiClient#stack_id`), and every controller is expected to resolve stacks only from the `stacks` helper, which filters by that scope: [1](#0-0) 

`Api::StacksController` and other nested resource controllers correctly go through this scoped relation (`stacks.from_param!(...)`), so a token restricted to `stack_id: X` can never resolve, read, or act on a different stack ID.

`Api::CCMenuController`, however, defines its own `stack` method that bypasses `stacks` entirely and queries the global `Stack` model directly: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, which only checks that the token's `permissions` array contains `read:stack` — it does not check whether the token is scoped to the requested stack: [3](#0-2) 

The equality that should hold is: `stack requested by params[:stack_id]` == `stack the token's scope (stack_id) authorizes`. For every other API resource this holds because they resolve via `stacks.from_param!`. For `CCMenuController` it does not, because `stack` resolves via `Stack.from_param!(params[:stack_id])` directly, so any stack in the installation can be supplied, regardless of the token's `stack_id`.

### Impact Explanation
This is a stack-scoping bypass: unprivileged-attacker analog of "a stack a token authorizes versus a stack it touches." A token deliberately scoped to a single, low-sensitivity stack (e.g. issued to a third-party CI-status widget, per the `here_come_the_walrus` fixture pattern seen in tests) can be used to read the build/deploy status, activity, last build time/label, and web URL of *any* stack in the Shipit instance, including stacks the token holder was never granted access to. This is an unauthorized cross-stack read of deploy/task state, matching the "High" impact category (unauthenticated/unauthorized read of stack state or deploy output) defined in scope.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token with `read:stack` permission can exploit this trivially by simply supplying a different `stack_id` in the request path — no additional privilege, secret, or race condition is required. The `token` param variant (`Api::CCMenuController#authenticate_api_client`) makes exploitation even easier since it doesn't require crafting Basic Auth headers.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`), consistent with `Api::BaseController#stack` and all sibling controllers, so that a stack-scoped token cannot resolve stacks outside its authorized scope.

### Proof of Concept
1. Create an `ApiClient` scoped to stack `A` (`stack_id: A.id`) with permission `read:stack` (as in fixture `here_come_the_walrus`).
2. Authenticate as that client against `GET /api/ccmenu/:stack_id` (or with `?token=...`) using `stack_id` = the `to_param` of stack `B` (a different stack the client was never granted access to).
3. Observe the request succeeds (`200 OK`) and returns stack `B`'s CI/build XML (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`, etc.), even though the token is scoped only to stack `A`. [4](#0-3) [5](#0-4)
