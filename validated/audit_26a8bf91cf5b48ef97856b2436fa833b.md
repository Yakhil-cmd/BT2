### Title
Stale unlocked read of `hasUnstableOpVoteCount()` used to decide OP-list re-verification during stability advancement - ([File: main_chain.js])

### Summary
`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` snapshots a shared, mutable flag (`bOpListCanChange = hasUnstableOpVoteCount()`) *before* acquiring the `handleJoint` mutex, then uses that stale snapshot *inside* the lock to decide whether each MCI must be re-verified against a possibly-changed OP list before being marked stable. Concurrent unit processing (via `writer.js` `saveJoint`, which mutates `storage.assocUnstableMessages`/`assocUnstableUnits` under the separate `write` lock) can change the true OP-vote state between the unlocked read and the locked use, exactly the same "read shared mutable state before acquiring the lock that's supposed to serialize it" defect pattern as CVE-2025-39905's `pl->phydev` race.

### Finding Description
`hasUnstableOpVoteCount()` scans `storage.assocUnstableMessages` for any unstable `system_vote_count` message with `payload === 'op_list'`: [1](#0-0) 

In `determineIfStableInLaterUnitsAndUpdateStableMcFlag()`, this value is captured *before* the `mutex.lock(["handleJoint"], ...)` call that is supposed to serialize all state affecting stability advancement: [2](#0-1) 

The stale `bOpListCanChange` is then used inside the loop that walks forward from `last_stable_mci + 1` to `new_last_stable_mci`, deciding per-MCI whether to re-run `determineIfStableInLaterUnits` against the best parent's OP list before calling `stabilizeMci(mci)`: [3](#0-2) 

`storage.assocUnstableMessages` (the source of truth for `hasUnstableOpVoteCount()`) is mutated by `writer.js` while units are validated/saved, under the `write` mutex — a different lock than `handleJoint`: [4](#0-3) 

Because the flag is read *before* the `handleJoint` lock is taken, a concurrently-processed unit carrying a `system_vote_count`/`op_list` message can be committed (updating `assocUnstableMessages`) in the window between the unlocked read and the locked stability-advancement loop. If the read happened to occur before that commit, `bOpListCanChange` will be `false` even though the true condition is now `true`, so the code skips the additional per-MCI OP-list stability re-check (`determineIfStableInLaterUnits`) and stabilizes the MCI directly via `stabilizeMci(mci)` without verifying against the newly-changed OP list. This is the same class of bug as the phylink advisory: a boolean/pointer derived from shared mutable state is read outside the lock meant to serialize writers, then trusted inside the lock for a security/consensus-relevant branch decision, instead of being re-checked after the lock is held.

### Impact Explanation
If two nodes race this window differently (one observes the OP-list vote before entering the loop, another observes it after), they can diverge on whether the extra witness-list/stability re-verification is performed for the same MCI, which is one of the paths that determines whether stability advances "as normal" versus using the updated OP list. This is a **node disagreement on validity/stability** condition — nodes can end up disagreeing about which MCI is the last stable MCI and which units are considered final, which is explicitly one of the accepted high-severity outcomes (stability/consensus divergence), and stability determines what units and outputs are considered final for payments/AA execution.

### Likelihood Explanation
The race window is narrow (between reading `bOpListCanChange` and completing `mutex.lock(["handleJoint"], ...)` plus the subsequent `storage.readLastStableMcIndex`/`readUnitProps` calls) but is reachable purely through normal unit posting: any account can post a unit carrying `system_vote_count` for `op_list`, and unrelated concurrent unit posting drives `determineIfStableInLaterUnitsAndUpdateStableMcFlag` to be invoked frequently during normal catch-up/validation. No privileged access is required — an ordinary unit poster triggering OP-list voting activity around the time other units are being validated is sufficient to hit the window, though exact timing to cause divergent behavior across two different nodes is probabilistic rather than deterministic.

### Recommendation
Move the read of `hasUnstableOpVoteCount()` to *after* the `handleJoint` lock is acquired (mirroring the phylink fix's approach of not trusting a pre-lock snapshot for a decision made under the lock), so that the OP-list-change decision is made atomically with respect to the same lock that serializes writes to `assocUnstableMessages`/`assocUnstableUnits`. Alternatively, re-evaluate `hasUnstableOpVoteCount()` on every iteration of the `mci` loop rather than caching a single boolean captured before the lock.

### Proof of Concept
1. Node observes `earlier_unit` stable in `arrLaterUnits`; calls `determineIfStableInLaterUnitsAndUpdateStableMcFlag`.
2. At `main_chain.js:1206`, `bOpListCanChange = hasUnstableOpVoteCount()` returns `false` (no unstable `op_list` vote-count message yet).
3. Before `mutex.lock(["handleJoint"], ...)` resolves, a concurrently validated unit (via `writer.js saveJoint`, holding the separate `write` lock) commits a `system_vote_count`/`op_list` message, updating `storage.assocUnstableMessages`.
4. The `handleJoint` lock is granted; the loop at lines 1224–1234 runs with the stale `bOpListCanChange = false`, so it skips the `determineIfStableInLaterUnits` re-check against the updated OP list and stabilizes the MCI directly via `stabilizeMci(mci)`.
5. A second node, where the read of `hasUnstableOpVoteCount()` happens to occur after the same message is committed, takes the re-check branch and may reach a different stability conclusion for the same MCI — producing a stability/validity disagreement between the two nodes.
