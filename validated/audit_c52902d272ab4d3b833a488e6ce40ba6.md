### Title
Arbiter contract hash does not commit to all contract fields, allowing hash collisions between contracts with different terms - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js` identifies an arbiter contract solely by `hash = getHash(objContract)`, which is the sole primary key of `wallet_arbiter_contracts` and the sole reference used throughout the whole contract lifecycle (storage, `setField`, `getByHash`, dispute matching, shared-address/unit verification). Exactly like the reported `OVM_FraudVerifier`/`OVM_BondManager` bug — where a fraud proof is keyed only by pre-state root + tx hash and can therefore apply to any transition sharing that pair — the arbiter-contract hash is computed from only a subset of the contract's fields, so two materially different contracts (differing in fields excluded from the hash) collide on the same identifier and get treated as "the same" contract everywhere in the code.

### Finding Description
`getHashSrc()` builds the hash preimage from only:
`title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset` [1](#0-0) 

It deliberately omits other fields that are stored and acted upon under the same `hash` key, in particular `ttl`, `cosigners`, `my_contact_info`/`peer_contact_info`, `peer_pairing_code`/`my_pairing_code`, and `peer_device_address`: [2](#0-1) 

The hash is the primary key of `wallet_arbiter_contracts` (`hash CHAR(44) NOT NULL PRIMARY KEY`), and every lookup/update/dispute operation resolves the record purely by this non-unique identifier: [3](#0-2) [4](#0-3) [5](#0-4) 

`store()` inserts a new contract row with `INSERT IGNORE ... VALUES ...`, keyed on `hash`, meaning that once a row with a given hash exists, any subsequent contract (from a device message) that happens to hash to the same value — because it agrees on the hashed fields but differs in `ttl`, `cosigners`, contact info, or pairing codes — is silently dropped, and the wallet keeps operating on the first-stored (possibly stale/attacker-controlled) row: [2](#0-1) 

The offer-handling path in `wallet.js` accepts `arbiter_contract_offer` messages from a paired device (an unprivileged counterparty), validates the hash by recomputing it from the same restricted field set, and stores it via `arbiter_contract.store`: [6](#0-5) 

Later, dispute handling (`arbiter_dispute_request`) again recomputes `expectedContractHash` from only the hashed subset of fields and matches it against `body.contract_hash`, and the signed on-chain data message only commits to `contract_text_hash` (the same restricted hash) plus a separate `contacts_hash`: [7](#0-6) [8](#0-7) 

Because `ttl` and `cosigners` are never bound into `hash` (or into the on-chain `contract_text_hash`/`contacts_hash`), nothing in the protocol proves that both parties (and their cosigners) agree on the same expiration time or the same set of trusted cosigning devices for the shared multisig escrow address that later receives real funds (`createSharedAddressAndPostUnit`, `exports.CHARGE_AMOUNT`): [9](#0-8) 

### Impact Explanation
This directly mirrors the M02 bug class: the identifier meant to uniquely pin a specific contractual "transition" does not capture all the state that determines its behavior, so:
- A counterparty (unprivileged peer/paired device) can grief the negotiation: after a legitimate contract is stored under a hash, any corrected re-offer (e.g., fixing `ttl` or `cosigners`) that hashes to the same value is silently ignored by `INSERT IGNORE`, permanently keeping the wallet on stale/incorrect terms for that hash — analogous to the report's "prevents the first invalid state from being removed."
- Since `cosigners` and `ttl` are outside the committed hash, one party's local record of "who must co-sign the shared address" or "when the contract expires" can diverge from what's cryptographically proven to the counterparty/arbiter, undermining the security of the multisig escrow address into which real funds (`CHARGE_AMOUNT`, the disputed `amount`/`asset`) are sent, and undermining the dispute-resolution flow that references contracts solely by this ambiguous hash.
- This can lead to funds sent to a shared address whose governance (cosigner set) is not what all parties believe was agreed, i.e., fund freezing/loss of control over escrowed funds, or a stalled/incorrect dispute process, which the report class permits ("AA fund loss or freezing" / "unauthorized spending" analog for wallet/contract escrow).

### Likelihood Explanation
The `arbiter_contract_offer`/`arbiter_contract_shared`/`arbiter_dispute_request` device messages are handled directly from a paired-device counterparty with no privileged role required — this is one of the explicitly in-scope actor classes ("private-payment counterparty ... paired device", "wallet and contract message handling"). Triggering a hash collision only requires crafting two contract payloads that agree on the ten hashed fields but differ in the fields excluded from the hash (`ttl`, `cosigners`, contact/pairing info) — well within reach of any party engaging in contract negotiation, so likelihood is Medium.

### Recommendation
Include all contract fields that affect protocol behavior or fund custody (`ttl`, `cosigners`, and ideally the pairing/contact data or a hash thereof) in `getHashSrc()`/`getHash()`, so that the `hash` uniquely and completely identifies one contract instance, matching the report's recommendation to use a fully qualifying identifier (e.g., adding the missing state, analogous to using `stateTransitionIndex`) rather than a partial one. Additionally, consider using a strictly unique key (e.g., including a nonce/random id) rather than relying purely on content hashing of a field subset, and reject/overwrite (rather than silently ignore) conflicting inserts so the wallet does not silently retain stale contract state.

### Proof of Concept
1. Party A sends `arbiter_contract_offer` to Party B with `title="T", text="X", creation_date=D, arbiter_address=Arb, amount=100, asset=null, ttl=24, cosigners=[]`. Its `hash = getHash(...)` covers only the fields in `getHashSrc()`, not `ttl`/`cosigners`.
2. Party B's wallet stores this via `store()`, keyed by `hash` (`INSERT IGNORE`) — [2](#0-1) .
3. Party A later sends a second `arbiter_contract_offer` with identical `title/text/creation_date/addresses/names/amount/asset` (same `hash`) but `ttl=1000` and a different `cosigners` list (e.g., adding an extra device it controls as a would-be co-signer of the eventual shared multisig address).
4. Because `hash` is identical, `store()`'s `INSERT IGNORE` on the primary key silently drops the second offer; Party B's UI/logic continues to reference the original `ttl`/`cosigners`, while Party A can use its own locally-stored (differing) copy in later flows (`deriveSharedAddress`, `createSharedAddressAndPostUnit`) that are not fully re-verified against the "hash" for these excluded fields, since only `contract_text_hash` and `contacts_hash` are checked on-chain — [10](#0-9) , [11](#0-10) .
5. This produces divergent, unverifiable state for `ttl`/`cosigners` under one shared identifier, matching the reported bug class of an identifier that does not uniquely determine the full transition it is meant to represent.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
