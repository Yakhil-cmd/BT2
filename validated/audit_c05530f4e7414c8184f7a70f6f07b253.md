### Title
`DefaultCombineData` returns a stale previous oracle value with no expiry check when fresh submissions fall below the minimum count - ([File: substrate/frame/honzon/oracle/src/default_combine_data.rs])

### Summary
`pallet-oracle`'s `DefaultCombineData::combine_data` filters out stale raw submissions using an `ExpiresIn` window, but when the number of remaining fresh submissions is below `MinimumCount`, it falls back to `prev_value` — the last stored aggregated value — without ever checking whether `prev_value` itself is still within the freshness window. Consumers reading the aggregated value via `Pallet::get`/`DataProvider::get` receive this stale value with no staleness signal, mirroring the reported class of bug: "no fresh source available -> silently return stale data instead of rejecting it."

### Finding Description
`combine_data` filters incoming raw values by `expires_in`: [1](#0-0) 

If `count < minimum_count`, the function returns `prev_value` unconditionally — this is the exact same "fallback path accepts unvetted/stale data" pattern as the QuantAMM `getData` bug, where the backup path was supposed to guard freshness but instead let the previously-rejected stale value through. Here, `prev_value` comes from the pallet's own storage: [2](#0-1) 

and once stored, `Pallet::get`/`DataProvider::get` return it with no staleness re-check at read time: [3](#0-2) [4](#0-3) 

So if oracle operators (a permissioned but not root-controlled set, managed via `SortedMembers`/`pallet-membership`) stop submitting within the `expires_in` window, or the membership set shrinks such that fewer than `MinimumCount` accounts submit fresh values in a block, `Values<T,I>` simply keeps returning the last aggregated value forever — with no bound on how old it can become. Unlike the QuantAMM contract, there is no revert path at all in this pallet; the design intentionally treats "not enough fresh data" as "keep serving old data," identical in spirit to the reported flaw of silently accepting stale data instead of reverting.

The node runtime wires this pallet with `ConstU32<5>` (`MinimumCount`) and `ConstU64<3600>` (`ExpiresIn`, in ms — i.e., 3.6 seconds given `Moment` in ms, or whatever the runtime's `Time` unit is) via: [5](#0-4) 

### Impact Explanation
Any downstream consumer relying on `DataProvider::get`/`DataProviderExtended::get_all_values` (e.g. a PSM-like pallet or price-based logic) can be fed indefinitely-stale price/data values whenever fresh submissions temporarily fall below the configured `MinimumCount` — this is a data-integrity issue analogous to the reported Medium/Low-severity "stale oracle price accepted" finding, not a theft/unauthorized-dispatch primitive. In this repository I could not find a concrete consumer pallet (e.g. PSM) that reads `pallet_oracle`'s price via `DataProvider` to quantify a fund-loss path — searches for `DataProvider`/`Oracle::get` usage in the PSM pallet returned no matches, so the downstream blast radius is unconfirmed and would need further investigation in a live session.

### Likelihood Explanation
This does not require a privileged actor: it happens naturally whenever oracle operators (already-authorized signed accounts) fail to submit fresh data within `ExpiresIn`, which is a normal operational/liveness condition rather than an attack requiring stolen keys or governance control. However, oracle operators are a permissioned, trusted set (`SortedMembers`), so the "attacker" here is really just benign inactivity, not an adversarial input — this weakens the case as a security bug versus an accepted design tradeoff (similar to QuantAMM's own "acknowledged" response to the original report).

### Recommendation
In `combine_data`, when `count < minimum_count`, additionally check `prev_value`'s own timestamp against `expires_in`/`now` and return `None` (or otherwise signal staleness) if `prev_value` has itself expired, rather than unconditionally returning it. Alternatively, enforce a staleness check at the `get`/`DataProvider::get` call site so stale aggregated values are never returned to consumers.

### Proof of Concept
Not executed. Existing tests in `substrate/frame/honzon/oracle/src/tests.rs` (`should_combined_data`) already demonstrate the mechanism: after `Timestamp::set_timestamp(23456)` the previously aggregated value is still returned unchanged with no expiry enforcement: [6](#0-5) 
This confirms the read-path never re-validates freshness, but I did not run a new integration reproduction demonstrating a measurable downstream loss, since no concrete price-consuming pallet reachable through a real extrinsic was found wired to this oracle instance within the indexed code. This should be treated as an unconfirmed/Low-confidence analog pending further investigation of real consumers, rather than a fully proven Critical/High finding.

	fn combine_data(
		_key: &<T as Config<I>>::OracleKey,
		mut values: Vec<TimestampedValueOf<T, I>>,
		prev_value: Option<TimestampedValueOf<T, I>>,
	) -> Option<TimestampedValueOf<T, I>> {
		let expires_in = ExpiresIn::get();
		let now = T::Time::now();

		values.retain(|x| x.timestamp.saturating_add(expires_in) > now);

		let count = values.len() as u32;
		let minimum_count = MinimumCount::get();
		if count < minimum_count || count == 0 {
			return prev_value;
		}
