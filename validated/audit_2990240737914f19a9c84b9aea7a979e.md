### Title
Unauthenticated main-chain stability advancement before author/signature validation - (File: validation.js / main_chain.js)

### Summary
`validate()` calls `validateParents()` (async.series step 6) **before** `validateAuthors()` (step 10, where signatures are actually checked). Inside `validateParents()`, when the unit's claimed `last_ball_unit` is not yet stable in our local view, the code calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()` using the untrusted, not-yet-authenticated `objUnit.parent_units`/`last_ball_unit` fields from the posted unit. If that check finds the ball to be stable in view of the posted (still-unauthenticated) parents, it immediately commits real, permanent state changes to the database — marking MCIs stable, inserting balls, executing AA triggers, and updating TPS fees — via `stabilizeMci()`, which opens and commits its own independent DB transaction, before the unit's own signatures have even been checked.

### Finding Description
This is analogous to CVE-2018-7184: ntpd updated the "received" timestamp / reset association state using data from a packet before that packet had been fully validated, letting an attacker cause a state change using not-yet-authenticated content. In ocore, the equivalent asymmetry is in the unit validation pipeline: [1](#0-0) 

`validateParents` runs before `validateAuthors`. Within `validateParents`, an unstable `last_ball_unit` triggers: [2](#0-1) 

`determineIfStableInLaterUnitsAndUpdateStableMcFlag` acquires the `"handleJoint"` mutex and, if it determines the referenced ball is now stable relative to the *posted, unauthenticated* `parent_units`, walks forward from `last_stable_mci+1` to `new_last_stable_mci` calling `stabilizeMci` for each MCI: [3](#0-2) 

`stabilizeMci` opens its own connection, `BEGIN`s, calls `markMcIndexStable` (which flips `is_stable=1` on units, inserts into `balls`, sets `assocStableUnits`), writes to the kv-store batch, `COMMIT`s, and — separately — runs any newly-stabilized AA triggers via `aa_composer.handleAATriggers()`: [4](#0-3) 

This commit happens on its own connection/transaction, independent of the `conn`/`commit_fn` rollback logic in `validate()` that would otherwise discard all effects if the unit is later rejected in `validateAuthors` or `validateMessages`.

### Impact Explanation
An unprivileged unit poster can craft a syntactically well-formed unit (correct hashes, payload commissions, parent ordering, well-known parent units) with an invalid or missing author signature, causing the validation pipeline to reach `validateParents` and trigger a real, committed advancement of the main-chain stability point, ball insertion, AA trigger execution, and TPS fee updates — all before the poster's own authorization to speak for the referenced addresses is confirmed. Because `validateAuthors` (signature checking) happens strictly after this point in the `async.series` chain, the state-changing side effect occurs regardless of whether the triggering unit itself is ultimately accepted or rejected. This can cause premature/incorrect stabilization decisions (nodes disagreeing on validity/stability if the attacker can influence timing/racing of MC advancement), and it triggers AA execution and TPS fee bookkeping based on state advanced by content that was never actually cryptographically authenticated by its claimed author.

### Likelihood Explanation
Reaching `validateParents` only requires a small set of preconditions (correct unit/payload hashes, correctly-ordered known parents, valid headers/payload commissions) that are all self-computable by an attacker without needing a valid signature; only `validateAuthors`, invoked later, checks signatures. Any peer able to post units (including light clients via `handlePostedJoint`) can reach this code path.

### Recommendation
Move signature/author validation (`validateAuthors`) ahead of `validateParents`/`determineIfStableInLaterUnitsAndUpdateStableMcFlag` in the `async.series` pipeline in `validate()`, or otherwise ensure that irreversible state changes such as `stabilizeMci`'s `markMcIndexStable`/ball insertion/AA-trigger execution are deferred until the full validity (including author signatures) of the triggering unit is confirmed and can be rolled back atomically with the rest of validation.

### Proof of Concept
1. Construct a unit `U` whose `parent_units`/`last_ball_unit` reference real, existing (but not-yet-locally-stable) units such that `determineIfStableInLaterUnits` would resolve to stable given `U`'s parents as `arrLaterUnits`.
2. Set `U.authors[0].authentifiers` to an invalid/garbage signature (still passing all earlier joint/format checks: correct unit hash, payload hashes, headers/payload commission).
3. Post `U` via `handlePostedJoint`/`handleOnlineJoint`.
4. Observe in logs/DB that `validateParents` → `determineIfStableInLaterUnitsAndUpdateStableMcFlag` → `stabilizeMci` executes and commits (`balls` table gets new rows, `units.is_stable` flips, AA triggers fire) even though `U` is subsequently rejected in `validateAuthors` for bad signature.

async function stabilizeMci(mci) {
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const batch = kvstore.batch();
	const count_aa_triggers = await markMcIndexStable(conn, batch, mci);
	await util.promisify(batch.write.bind(batch))({ sync: true });
	await conn.query("COMMIT");
	conn.release();
	if (count_aa_triggers > 0) {
		console.log(`executing ${count_aa_triggers} AA triggers after stabilizing MCI ${mci}`);
		// every trigger takes its own db connection
		const aa_composer = require("./aa_composer.js");
		await aa_composer.handleAATriggers();
	}
	if (mci >= constants.v4UpgradeMci) {
		console.log(`updating tps fees after stabilizing MCI ${mci}`);
		// get a new connection to write tps fees
		const conn = await db.takeConnectionFromPool();
		await conn.query("BEGIN");
		await storage.updateTpsFees(conn, [mci]);
		await conn.query("COMMIT");
		conn.release();
	}
}
