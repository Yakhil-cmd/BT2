This confirms the exploit path. `StatusHandler#process` at [1](#0-0)  looks up commits purely by `sha` (a global, cross-repository lookup with no repository/organization scoping at all) and creates a real `Status` record directly from attacker-supplied `state`/`context`/`description`/`target_url` fields, which feeds Shipit's CI-gating and continuous-deployment logic.

### Title
Webhook signature is verified against an attacker-controlled organization while the payload writes to an unrelated repository/commit - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on an untrusted field taken from the request body itself, while the event handlers that actually mutate state use a *different* untrusted field from the same body to select the target repository/commit. Because these two fields are never cross-checked, an attacker who legitimately controls (or administers) any one GitHub organization configured on a shared, multi-tenant Shipit instance can forge a validly-signed webhook whose "owner" is their own organization but whose "target" (`repository.full_name`, or an unscoped commit `sha`) belongs to a different tenant's repository.

### Finding Description
`verify_signature` computes the organization used for signature verification like this: [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is derived entirely from the JSON body: [3](#0-2) 

The signature is validated with `GitHubApp#verify_webhook_signature`, which HMACs the *whole* raw body against the secret configured for whatever organization `repository_owner` names [4](#0-3) . This is correct only if `repository_owner`'s organization is also the one whose data the payload is allowed to mutate — but nothing enforces that.

Once signature verification passes, the actual event handlers pick the object to act on using a *different* field:
- `Handler#repository_name` uses `payload.dig('repository', 'full_name')` to resolve the `Repository`/`Stack` [5](#0-4) , used by `PushHandler` (triggers `stack.sync_github`) [6](#0-5)  and all the `PullRequest::*` handlers (archive/unarchive review stacks, capture labels, etc.) [7](#0-6) .
- `StatusHandler#process` is even less scoped: it looks up `Commit.where(sha: params.sha)` globally, with no repository/organization filter at all, and writes an attacker-controlled `state`/`context`/`target_url` as a real CI status [1](#0-0) .

Since `repository.owner.login` (used to pick the signing secret) and `repository.full_name` / commit `sha` (used to pick the target) are independent, unrelated fields inside the same attacker-supplied JSON body, an attacker who owns/administers GitHub org **A** (one tenant on a shared Shipit deployment serving multiple orgs, as shown by the multi-org `secrets.yml` layout in `config/secrets.development.shopify.yml`) can:
1. Set `repository.owner.login` = `"A"` so `Shipit.github(organization: "A")`'s webhook secret (which the attacker legitimately possesses, since they can trigger real webhooks from their own org/repo) is used to compute a signature the attacker can produce.
2. Set `repository.full_name` (or a known commit `sha`) to point at organization **B**'s repository/commit, which is a completely separate tenant they do not administer.
3. Submit this forged, correctly-signed request to `POST /github/webhooks`.

The request passes `verify_signature` (signature matches org A's secret) but is then processed by handlers that act on org B's `Stack`/`Commit` records — breaking the intended binding: *organization that authenticated == organization whose repository is written*.

### Impact Explanation
This directly maps to the required Critical impact of "an unauthorized deploy, rollback or merge": by forging `status` webhooks, the attacker can inject a fabricated `success` CI status onto any commit (by SHA) belonging to another tenant's stack, without any organization scoping in `StatusHandler`. If that stack has `continuous_deployment` enabled or the commit's PR is in the merge queue, this fabricated status can satisfy `required_statuses`/`merge_request_required_statuses` checks used by `MergeRequest#reject_unless_mergeable!` and continuous delivery scheduling [8](#0-7) , potentially causing an unauthorized merge or an unauthorized deploy of a commit that never actually passed real CI on GitHub. It can also archive/unarchive victim review stacks and drive `sync_github` on victim stacks via `PushHandler`.

### Likelihood Explanation
This requires the attacker to be an administrator of at least one GitHub organization already onboarded to the same shared Shipit instance (a realistic scenario for any multi-tenant/self-service Shipit deployment, as evidenced by the multi-org config format), but requires no Shipit account, no `ApiClient` token, and no access to the victim organization at all — only the ability to receive/replay a webhook signed with their own org's `webhook_secret`, which they possess by design. This is squarely an "unprivileged attacker" with respect to the victim org.

### Recommendation
Cross-validate the organization used to select the signing secret against the organization actually targeted by the payload before processing any handler: derive `repository_owner` and the acting repository/commit from the same trusted field, and reject the webhook if the resolved `Repository`'s `owner` does not match the organization whose secret validated the signature. Additionally, scope `StatusHandler`'s commit lookup by repository (not global `sha`), and scope other handlers' repository resolution to repositories confirmed to belong to the verified organization.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org`, which is configured in this Shipit instance's `secrets.yml` alongside an unrelated victim org `victim-org` (multi-tenant deployment).
2. Attacker obtains their own org's real webhook secret behavior (e.g. by installing their GitHub App and observing/replaying a legitimately signed delivery, or since they administer `attacker-org`'s GitHub App settings in supported flows).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha known from GitHub, e.g. a PR head>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" },
  "organization": { "login": "attacker-org" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds since the attacker signed with the correct secret for that org.
6. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, finds the victim's commit (owned by `victim-org`, unrelated to the signing organization), and creates a forged `success` status on it, independent of GitHub's real state — potentially unblocking a merge or deploy on `victim-org`'s stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
