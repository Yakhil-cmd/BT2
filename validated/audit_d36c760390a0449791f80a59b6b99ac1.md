Webhook authenticity is bound to `repository.owner.login`/`organization.login` while every event handler acts on unrelated, unverified payload fields (`repository.full_name`, `sha`) — allowing cross-organization/cross-repository webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using only `params.dig('repository','owner','login')` (or `organization.login` as fallback), a field taken directly from the untrusted, attacker-suppliable JSON body.<cite repo="hirayap/shipit-engine--023" path="app/controllers/shipit/webhooks_controller.rb" start="24,30" end="30,30" /> [1](#0-0)  None of the downstream `Shipit::Webhooks::Handlers` re-check that this "authenticated" field matches the field they actually act on. `PushHandler`, all `PullRequest::*Handler`s and the generic `Handler#stacks` helper key off `repository.full_name` instead, [2](#0-1)  and `StatusHandler` keys off a bare `sha` with **no repository/organization scoping at all**, matching `Commit.where(sha: params.sha)` across the entire installation. [3](#0-2) 

Because Shipit explicitly supports multi-organization configurations where each org has its own independent `webhook_secret`, [4](#0-3)  and `GitHubApp#verify_webhook_signature` **bypasses verification entirely when that org's `webhook_secret` is blank** (`return true unless webhook_secret`), [5](#0-4)  an attacker only needs knowledge that at least one configured organization has no webhook secret (a state the project's own example/dev/test secrets templates repeatedly show as the default/optional value). [6](#0-5) [7](#0-6) 

### Finding Description
The equality the code implicitly (but incorrectly) assumes is:

`organization authenticated via HMAC (repository.owner.login / organization.login)` == `repository/commit actually written by the handler (repository.full_name / sha)`

This equality is never enforced. Concretely:

1. `verify_signature` derives `repository_owner` purely from the JSON body (not from any GitHub-signed header or TLS-bound source) and uses it to pick the `GitHubApp` instance/secret: `Shipit.github(organization: repository_owner)`. [8](#0-7) 
2. If that organization's `webhook_secret` is not set, `verify_webhook_signature` returns `true` unconditionally, regardless of the actual signature header supplied. [5](#0-4) 
3. Once "verified", `WebhooksController#create` dispatches the entire raw JSON body to every registered handler for the given `X-Github-Event`, with no further checks tying the payload's `repository`/`organization` back to the one used in step 1. [9](#0-8) 
4. Handlers resolve their target `Stack`/`Repository`/`Commit` from completely different, attacker-controlled fields:
   - `PushHandler`/`Handler#stacks` use `repository.full_name`. [2](#0-1) [10](#0-9) 
   - `StatusHandler` uses only `sha`, globally, with no repository scoping whatsoever. [3](#0-2) 
   - PR handlers (`LabeledHandler`, `ClosedHandler`, `ReopenedHandler`, `LabelCapturingHandler`) likewise resolve via `params.repository.full_name`. [11](#0-10) [12](#0-11) 

So the org whose secret is used to pass verification and the repository/stack/commit actually mutated need not have anything in common. An attacker who identifies (from the multi-org config templates, docs, or trial-and-error) any organization slug with an empty `webhook_secret` can send `repository.owner.login` (or, for events without a `repository` key, `organization.login`) equal to that unsecured org, satisfying `verify_signature`, while setting `repository.full_name` (or `sha`) to point at a completely unrelated, secured victim stack/commit.

### Impact Explanation
This breaks the authentication boundary the webhook signature is supposed to provide and results in unauthorized writes against a victim organization's Shipit resources without ever knowing that organization's real `webhook_secret`:
- `push` events force `stack.sync_github(expected_head_sha: ...)` on victim stacks for an attacker-chosen `expected_head_sha`. [10](#0-9) 
- `status` events create `Status` records on arbitrary commits system-wide (matched purely by `sha`), which feed into `Commit#deployable?` (`success? && !blocked?`) and CI gating used before deploys. [13](#0-12) [14](#0-13)  Forging a fake "success" status on a victim commit can make an otherwise CI-blocked/unreviewed commit appear deployable, enabling an unauthorized deploy path through the normal deploy UI/API once `deployable?` is satisfied.
- `pull_request` events (label/close/reopen) can archive/unarchive/deprovision review stacks belonging to any tracked repository. [15](#0-14) 

This matches the "unauthorized deploy" / cross-repository writes tier of impact, since it lets an unprivileged network attacker manipulate deploy-gating state and stack lifecycle for repositories/organizations they have no legitimate relationship to, using only knowledge of an unrelated, weakly-configured organization slug.

### Likelihood Explanation
Likelihood depends on operational configuration: the vulnerability is only exploitable when (a) the deployment uses the multi-organization `github:` config format, and (b) at least one configured organization has a blank/unset `webhook_secret`. This is explicitly documented as an "optional" setting and shown as the default/example value across the project's own templates (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`), suggesting this is plausible in real deployments, especially since the multi-org feature is newer and less scrutinized than the single-org path. [16](#0-15)  Even without a blank secret, the structural flaw remains: the field checked (`repository.owner.login`) is never required to equal the field acted upon (`repository.full_name`/`sha`), which is a latent design defect independent of any specific misconfiguration.

### Recommendation
- After signature verification succeeds, re-derive the acting organization strictly from the same field validated by `verify_signature`, and require every handler to scope lookups (`Repository.from_github_repo_name`, `Commit.where(sha:)`, etc.) to that verified organization — reject payloads where `repository.full_name`'s owner segment (or `organization.login`) differs from `repository_owner`.
- Do not silently bypass signature verification when `webhook_secret` is blank in multi-organization mode; either require a secret for every configured organization or fail closed.
- For `StatusHandler`, additionally scope the `Commit` lookup by the repository/organization implied by the verified webhook source, not solely by `sha`.

### Proof of Concept
Preconditions: Shipit configured with multi-org `github:` block containing at least two orgs, e.g. `VictimOrg` (has `webhook_secret: s3cr3t`, owns tracked `Stack` `VictimOrg/app`) and `UnsecuredOrg` (`webhook_secret:` blank), per the supported config format. [17](#0-16) 

1. Attacker (no credentials, no GitHub App access to `VictimOrg`) sends:
```
POST /webhooks
X-Github-Event: push
(no valid X-Hub-Signature needed)

{
  "repository": { "owner": { "login": "UnsecuredOrg" }, "full_name": "VictimOrg/app" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
2. `verify_signature` computes `repository_owner = "UnsecuredOrg"`, loads that org's `GitHubApp`, and `verify_webhook_signature` returns `true` because `webhook_secret` is blank. [5](#0-4) 
3. `PushHandler` resolves `stacks` via `repository.full_name == "VictimOrg/app"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's real stack, with no verification ever performed against `VictimOrg`'s secret. [10](#0-9) [2](#0-1) 

Analogous forgery works for `X-Github-Event: status` by supplying an arbitrary `sha`/`state: success`, injecting a fake passing status onto any commit in the entire installation, since `StatusHandler` performs no organization scoping at all. [3](#0-2)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
