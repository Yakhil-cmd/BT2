### Title
Webhook signature verification key is selected using an unverified field from the same request it is meant to authenticate - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the `X-Hub-Signature` against by reading `repository_owner`, which is derived from the *same unauthenticated JSON body* it is about to verify. In a multi-organization deployment (`docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), some organizations may be configured without a `webhook_secret` (documented as optional). `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, so any request that self-reports an owner/organization lacking a configured secret bypasses signature verification entirely, regardless of the "real" target repository processed by the downstream handlers.

### Finding Description
The binding that should hold is: *the organization whose credential authenticated the request* == *the organization whose repository is written to by the handler*. In practice:

1. `repository_owner` reads directly from the untrusted, unauthenticated JSON payload: [1](#0-0) 
2. This value is used to pick the `GitHubApp` (and thus the `webhook_secret`) used to verify the signature, before any verification has occurred: [2](#0-1) 
3. `GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for the selected org: [3](#0-2) 
4. The `github` config schema explicitly allows per-organization `webhook_secret` to be `nil`/unset, and this is documented as optional rather than mandatory: [4](#0-3) [5](#0-4) 

Because the org used to select the verification secret is attacker-controlled input, and the secret-presence check is per-org, an unauthenticated attacker can submit any payload with `repository.owner.login`/`organization.login` set to an org that has no `webhook_secret` configured, and the controller will accept it as a genuine GitHub webhook and dispatch it to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [6](#0-5) 

This breaks the equality **organization authenticated == organization/repository written**, because "authenticated" here degrades to "no secret configured for the self-declared org," which the request itself controls.

### Impact Explanation
Handlers dispatched from unauthenticated webhook payloads can mutate application state tied to real stacks/repositories - e.g. `push` triggers `GithubSyncJob` (enqueued with attacker-chosen `stack_id`/`expected_head_sha` derived from payload matching), `status` creates commit `Status` rows, `membership` creates/removes `Team`/`Membership` records, and `check_suite` triggers `RefreshCheckRunsJob`, all visible in the controller's own test suite: [7](#0-6) [8](#0-7) . For any organization in a multi-org deployment that omits `webhook_secret` (an explicitly supported, documented configuration), this allows spoofed GitHub events to influence sync/merge/status/membership state without possessing any secret - i.e., unauthenticated write access to stack-related state driven entirely by attacker-controlled input, which is one step short of triggering deploy/merge actions gated elsewhere by these records (e.g. status-driven merge queue progression).

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: it requires at least one configured GitHub organization/app to have `webhook_secret` unset. Since the docs explicitly mark `webhook_secret` as "(optional)" for both single-org and multi-org setups, and no code path enforces it must be present, this is a realistic, easy-to-hit misconfiguration rather than a purely theoretical one, especially in multi-org setups where an operator might set a secret for the primary org and forget/omit it for a secondary one.

### Recommendation
- Make `webhook_secret` mandatory at boot/config-validation time for every configured GitHub organization (fail fast if missing), rather than silently treating an absent secret as "verification passed."
- Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank; instead reject (422) or require operators to explicitly opt into "no verification" per organization with a clear, loud warning.
- Ensure the organization used to select the verification key is never trusted before signature verification succeeds - e.g. verify against all configured secrets/orgs and only accept if at least one match is found, rather than trusting the self-reported `repository_owner` to pick the single secret to check against.

### Proof of Concept
1. Deploy Shipit with the multi-org config shown in `docs/setup.md` ("Using Multiple Github Applications"), e.g. `OrgOne` with a real `webhook_secret`, and `OrgTwo` with `webhook_secret` left blank (a supported, documented configuration): [5](#0-4) 
2. As an unauthenticated attacker, POST to `/webhooks` with `X-Github-Event: push` and a JSON body whose `repository.owner.login` is `"OrgTwo"` and `repository.full_name` matching a stack Shipit tracks under `OrgTwo`, with any/garbage `X-Hub-Signature` header.
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` per [3](#0-2)  without ever checking the supplied signature.
4. The request proceeds to `create`, and `Shipit::Webhooks.for_event('push')` handlers run against the attacker-supplied payload, enqueuing `GithubSyncJob` for the targeted stack as shown in the existing test expectations: [9](#0-8) 

**Uncertainty**: I was unable to open `app/models/shipit/webhooks/handlers/push_handler.rb` and `status_handler.rb` directly (tool access issue in the final iteration), so the exact repository-matching logic inside those handlers (e.g., whether they re-validate `full_name` against a `Repository` scoped to the verified org) could not be fully confirmed from source; the analysis above relies on the controller-level test behavior in `test/controllers/webhooks_controller_test.rb` and the `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatch in `app/controllers/shipit/webhooks_controller.rb:12`. A Devin session with full repo access should confirm whether handlers add any additional binding of `repository_owner` to the specific org before mutating state.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

      request.headers['X-Github-Event'] = 'push'
      unknown_repo_payload = JSON.parse(payload(:push_master))
      unknown_repo_payload["repository"]["full_name"] = "owner/unknown-repository"
      unknown_repo_payload = unknown_repo_payload.to_json

      assert_nothing_raised do
        post :create, body: unknown_repo_payload, as: :json
      end
    end

    test ":push with the target branch queues a GithubSyncJob" do
      request.headers['X-Github-Event'] = 'push'

      parsed_body = JSON.parse(payload(:push_master))
      expected_head_sha = parsed_body["after"]

      assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @stack.id, expected_head_sha:]) do
        post :create, body: parsed_body.to_json, as: :json
      end
    end

    test ":push does not enqueue a job if not the target branch" do
      request.headers['X-Github-Event'] = 'push'
      params = JSON.parse(payload(:push_not_master)).to_json
      assert_no_enqueued_jobs do
        post :create, body: params, as: :json
      end
    end

    test ":state create a Status for the specific commit" do
      request.headers['X-Github-Event'] = 'status'

      commit = shipit_commits(:first)

      body = JSON.parse(payload(:status_master)).merge(repository_params).to_json
      assert_difference 'commit.statuses.count', 1 do
        post :create, body:, as: :json
      end

      status = commit.statuses.last
      status_payload = JSON.parse(payload(:status_master))
      assert_equal status_payload['target_url'], status.target_url
      assert_equal status_payload['state'], status.state
      assert_equal status_payload['description'], status.description
      assert_equal status_payload['context'], status.context
      assert_equal status_payload['created_at'], status.created_at.iso8601
    end
