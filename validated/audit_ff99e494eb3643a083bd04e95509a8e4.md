### Title
`StatusHandler` applies GitHub commit-status webhooks to any commit by SHA, breaking the organization-authenticated-vs-repository-written binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The webhook signature check in `WebhooksController#verify_signature` only authenticates that the payload was signed by the GitHub App belonging to the organization named in `repository.owner.login` (or `organization.login`). It does not, and cannot, bind the payload to a specific *repository*. `StatusHandler#process`, unlike every other handler in the codebase, never re-checks that binding: it looks up commits with a completely unscoped, global `Commit.where(sha: params.sha)` query and mutates whichever commit rows match, regardless of which stack/repository they belong to.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/organization from the payload and verifies the HMAC signature against that org's `webhook_secret`: [1](#0-0) 

That check establishes only one equality: *signing organization == payload's declared organization*. It says nothing about which repository within that organization (or installation) the event pertains to. Every other webhook handler re-derives and scopes to the specific repository via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, as implemented in the shared base class: [2](#0-1) 

For example `CheckSuiteHandler` scopes to `stacks.where(branch: ...)` before touching commits, and the `pull_request` handlers all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` first.

`StatusHandler`, however, ignores `repository`/`full_name` entirely and queries the `Commit` table globally: [3](#0-2) 

`Commit#create_status_from_github!` then calls `add_status`, which schedules continuous delivery / merges and fires `deployable_status` hooks whenever the simple state changes, and `stack.schedule_merges` is invoked when the new status is `pending` or `success`: [4](#0-3) 

Because commit SHAs are unique identifiers of git content, not per-stack, per-repository, or per-organization identifiers, `Commit.where(sha: ...)` can match a commit belonging to a *different* stack/repository/organization than the one that produced and signed the webhook — e.g., two stacks tracking mirrored/forked/templated repositories, or repos that share history/cherry-picked commits, will contain identical commit rows with identical SHAs, each tied to its own `stack_id`. A `status` webhook that is validly signed for organization/repo A will be applied to *every* `Commit` row across the database that happens to share that SHA, including ones owned by stack/repo B, even though the signature only ever authenticated A.

This is exactly the "an organization that authenticated versus the repository that is written" binding break: the equality the code should enforce is `signed_organization/repository == repository_the_status_is_written_to`, but the actual code enforces only `signed_organization == payload.organization`, and then writes to `Commit` rows keyed purely by SHA with no repository/stack filter at all.

### Impact Explanation
Setting a status to `success` on a commit that also exists in another stack causes `Commit#deployable?` to become true for that commit in the *other* stack, and triggers `stack.schedule_merges` (`ProcessMergeRequestsJob`) and `deployable_status`/`commit_status` hooks for that stack. If continuous deployment is enabled on the victim stack, or if the victim stack's merge queue is waiting on a required status matching the context supplied in the forged payload, this can cause an unauthorized deploy or an unauthorized pull-request merge on a stack the attacker's own organization/app has no legitimate relationship to — meeting the "unauthorized deploy, rollback or merge" bar for High/Critical impact defined in scope.

### Likelihood Explanation
Exploitation requires the attacker to be able to send a validly-signed `status` webhook (i.e., control or trigger a CI/status update on some repository within an organization that Shipit trusts) whose commit SHA collides with a commit tracked under a *different* stack. This is most practically achieved when Shipit tracks multiple stacks that share commit history (forks, mirrors, templated/scaffolded repos, or repositories that were renamed/migrated while old stacks remain), which is a common operational pattern, and does not require any Shipit credential, API token, or webhook secret belonging to the victim stack — only a legitimate webhook delivery from any repository in a trusted org. The complete absence of any repository/stack filter in `StatusHandler`, in clear contrast to the pattern used by every sibling handler, indicates this is a genuine oversight rather than intentional behavior.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the repository via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` (or use the inherited `stacks` helper) and only update `Commit` rows belonging to that repository's stacks, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, mirroring `CheckSuiteHandler`'s pattern.

### Proof of Concept
1. Shipit tracks two stacks, Stack A (`org/repo-a`) and Stack B (`org/repo-b`), where `repo-b` was forked/mirrored from `repo-a` and both still contain a shared historical commit `abc123...` (identical SHA) — each stored as separate `Commit` rows with different `stack_id`.
2. Stack B currently requires a CI status context `ci/required` to be `success` on commit `abc123...` before it is deployable/mergeable, and it is currently `pending`/`failure` in Stack B's own CI.
3. An attacker who can trigger (or replay) a `status` event from `repo-a`'s CI on commit `abc123...` with `state: success`, `context: ci/required` sends this payload to `/webhooks`. It is signed with the org's real `webhook_secret`, so `verify_signature` passes (org matches).
4. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which returns **both** the Stack A commit row and the Stack B commit row, and calls `create_status_from_github!` on both.
5. Stack B's commit `abc123...` is now marked `success` for `ci/required`, becoming `deployable?` (or unblocking its merge queue) even though nothing in Stack B's own CI ever reported success — an unauthorized deploy/merge condition for Stack B triggered entirely by activity on Stack A's repository.

      reload # to get the statuses into the right order (since sorted :desc)
