### Title
RAY-scaled market totals can overflow the `i128` value ceiling during interest accrual, permanently freezing the market - (File: `common/src/rates/simulate.rs`)

### Summary
`accrue_step` converts scaled debt and supply shares back to RAY-denominated value before calculating utilization. This conversion uses non-saturating `Ray::mul`, which panics with `MathOverflow` when `scaled_amount * index / RAY` exceeds `i128::MAX`. Because pool mutations synchronize the market before processing user actions, a sufficiently large market whose indexes grow past the representable value ceiling can enter a state where `update_indexes`, `withdraw`, `repay`, `liquidate`, and related operations always revert.

### Finding Description
The pool stores totals and positions as RAY-scaled shares and derives current value by multiplying those shares by an index. [1](#0-0)  Every accrual step first calls `scaled_to_original` for both total borrowed and total supplied shares before calculating utilization and the next indexes. [2](#0-1)  `scaled_to_original` is implemented as `scaled.mul(env, index)`. [3](#0-2)  `Ray::mul` delegates to `mul_div_half_up`, which returns `MathOverflow` when the quotient cannot fit in `i128`; widening to `I256` protects the intermediate product but not the final result. [4](#0-3) [5](#0-4) 

This creates a RAY-value ceiling lower than the configured borrow-index ceiling. The documented borrow-index ceiling is `10^36`, while a RAY-scaled market total remains bounded by `i128::MAX` after multiplication by the index. [6](#0-5)  Therefore, a market can overflow its total-value calculation before `update_borrow_index` reaches its cap. [7](#0-6) 

Once this happens, normal recovery paths do not avoid the panic. `synced_market` loads the market and calls `interest::global_sync`. [8](#0-7)  `global_sync` invokes `accrue_chunk`, which invokes the same `accrue_step` arithmetic. [9](#0-8)  The permissionless controller `update_indexes` entrypoint forwards directly to market accrual. [10](#0-9) [11](#0-10) 

### Impact Explanation
The affected market can become permanently unable to accrue or process value-bearing actions. The repository’s own regression test demonstrates that after the overflow is reached, both withdrawal and repayment revert with `MATH_OVERFLOW`, and comments identify the same failure for liquidation. [12](#0-11)  Since `withdraw`, `repay`, `liquidate`, `claim_revenue`, and other pool mutations synchronize the market first, the overflow can freeze supplied collateral, block debt repayment, and prevent liquidation or revenue processing for that market. [13](#0-12) [14](#0-13) 

This meets the permanent-freezing impact class: user funds remain recorded in the pool, but exits and debt settlement cannot proceed because each transaction re-enters the same overflowing accrual calculation.

### Likelihood Explanation
Likelihood is low to moderate rather than high. The overflow requires a very large listed asset position and sustained index growth; the test setup uses a billion whole 18-decimal tokens, elevated caps, and approximately 98% utilization. [15](#0-14)  An unprivileged user can submit `update_indexes(caller, assets)` once the state approaches the ceiling, but creating the prerequisite market size depends on token supply, configured caps, collateral backing, and the deployed interest-rate model. [10](#0-9) [16](#0-15)  The issue is nevertheless deterministic once `scaled_amount * index / RAY` exceeds `i128::MAX`, and the repository explicitly documents that accrued totals can reach the RAY domain limit before the index ceiling. [17](#0-16) 

### Recommendation
Do not let the market enter a permanently unrecoverable arithmetic state. Practical mitigations include:

- Detect when scaled market totals or the next index update would exceed the RAY-value domain and clamp or stop accrual before that boundary.
- Apply the borrow-index ceiling before value multiplication can overflow, while preserving a consistent accounting interpretation.
- Add a bounded recovery path that permits repayment and withdrawal using the last stored indexes after the representable accrual ceiling is reached.
- Enforce stricter market caps so that `supplied * MAX_SUPPLY_INDEX / RAY` and `borrowed * MAX_BORROW_INDEX / RAY` remain below `i128::MAX` for every listed asset.
- Add explicit regression coverage around the largest admitted market totals, not only individual position conversions. [18](#0-17) 

### Proof of Concept
The repository already contains a directed proof in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. The test creates an 18-decimal market, supplies `1_000_000_000 * 10^18` base units, and borrows 98% of that amount. [19](#0-18)  It then advances time and repeatedly calls the permissionless `update_indexes` flow until accrual fails with `MATH_OVERFLOW`. [20](#0-19)  The stored borrow index remains below `MAX_BORROW_INDEX_RAY`, proving the value multiplication overflows before the configured index ceiling can protect the market. [21](#0-20)  Subsequent `withdraw` and `repay` calls also fail with `MATH_OVERFLOW`, demonstrating that the market is frozen rather than merely rejecting one oversized input. [22](#0-21)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

**File:** docs/reference/formulas.md (L407-417)
```markdown
A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion
saturates at `i128::MAX` (`calculate_scaled_cap`), so the entry check fails
open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
