### Title
Webhook signature verification is keyed to `repository.owner.login`/`organization.login` while every handler acts on the independent `repository.full_name` field, and verification is silently skipped for any configured organization with no `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) is used to validate an inbound webhook based on `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, determines which `Repository`/`Stack` to mutate using an entirely separate field, `payload.dig('repository','full_name')`. Nothing ties these two fields together, and `GithubApp#verify_webhook_signature` explicitly returns `true` (i.e., skips verification) whenever the resolved organization has no `webhook_secret` configured. This mirrors the Synapse finding's root cause: a field that drives the trusted/authenticated context (`callData`'s target/organization) is disconnected from the field that is actually acted upon.

### Finding Description
The signature check in the controller is: [1](#0-0) 

`repository_owner` is computed purely from attacker-supplied JSON: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app config for that org, and `verify_webhook_signature` is: [3](#0-2) 

Note `return true unless webhook_secret` — if the organization resolved from `repository.owner.login`/`organization.login` has no secret configured (a state explicitly supported by the sample configs, e.g. `webhook_secret: # nil`), the signature check is bypassed entirely and the request is accepted with `verified = true`.

Once accepted, `create` re-parses the same raw body and dispatches to handlers: [4](#0-3) 

But every handler resolves the target repository independently, via `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

and the pull-request/review-stack handlers likewise trust `params.repository.full_name` directly: [6](#0-5) [7](#0-6) 

The `membership` handler goes further: it trusts `params.organization.login` to attach GitHub team membership records used for authorization, independent of any cryptographic binding to that specific org's key: [8](#0-7) 

and `Team#add_member` unconditionally appends the member: [9](#0-8) 

**The broken binding, as an equality that should hold but doesn't:**
`organization authenticated by verify_webhook_signature (repository.owner.login / organization.login)` == `repository/organization actually mutated by the handler (repository.full_name / params.organization.login used for Team creation)`.

Before the attacker's request: only genuine GitHub-signed events for org X can affect stacks/teams under org X, because signature and target are (in real GitHub traffic) always the same org. After: an attacker who knows (or controls, if it is theirs) any single Shipit-configured GitHub organization with **no `webhook_secret` set** can send a POST to `/webhooks` with `X-Github-Event: push`/`membership`/`pull_request`, setting `repository.owner.login`/`organization.login` to that unsecured org (so `verify_signature` short-circuits to `true`), while setting `repository.full_name` (or, for `membership`, `team.id`/`organization.login`) to reference a **different** repository or team that Shipit tracks under a different, secured organization. `verify_signature` never inspects `repository.full_name`, so the mismatch is invisible to the check, and the handler blindly acts on the attacker-chosen target.

### Impact Explanation
This crosses two of the accepted High/Critical impacts:
- **Escalation into `Shipit.github_teams` authorization**: via `MembershipHandler`, an attacker can add an arbitrary `User` to a `Team` record tied to the target organization's slug/id, without ever authenticating to that organization's GitHub App, potentially granting deploy/merge permissions gated on team membership.
- **Cross-repository writes / unauthorized deploy path**: via `push`/`check_suite`/`status` handlers, an attacker can inject synthetic commits (`GithubSyncJob#append_commit`) or forge commit statuses for a stack belonging to a repository/org the attacker does not control, poisoning the deploy pipeline (fake "green" CI status, spoofed HEAD, etc.) purely by picking a differently-named organization for the signature-selection field.

### Likelihood Explanation
Requires only that at least one Shipit-configured GitHub organization has `webhook_secret` unset — a state the shipped sample configs treat as a normal/default value (`webhook_secret: # nil`, `"webhook_secret": null`), and which the code explicitly tolerates rather than rejecting (`return true unless webhook_secret`). No token, session, or GitHub credential is needed by the attacker; they only need to know the login of one such unsecured organization and the `full_name`/team id of the real target they want to spoof into. This is a purely unprivileged, unauthenticated HTTP POST to the public `/webhooks` endpoint.

### Recommendation
- Cross-validate that `repository.full_name`'s owner segment matches the `repository_owner` (or `organization.login`) used to select the signing key before dispatching to any handler; reject on mismatch.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in non-test environments; require an explicit, logged "unverified" opt-in per organization, and never let an unverified organization's events reference resources belonging to a different, verified organization.
- In `MembershipHandler`, `Handler#stacks`, and all PR/review-stack handlers, resolve the acting organization solely from the value that was authenticated in `verify_signature`, not from an independently-controlled `full_name`/`organization.login` field in the same JSON body.

### Proof of Concept
1. Shipit is configured with two organizations: `secure-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, e.g. left as `nil` per the sample config).
2. Attacker sends: `POST /webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "secure-org/protected-repo" },
  "after": "<attacker-chosen sha>",
  ...
}
```
3. `repository_owner` resolves to `open-org` (`app/controllers/shipit/webhooks_controller.rb:59-62`); `Shipit.github(organization: 'open-org').verify_webhook_signature(...)` returns `true` immediately since `open-org` has no `webhook_secret` (`lib/shipit/github_app.rb:76-77`).
4. `create` dispatches the push handler, which uses `payload.dig('repository','full_name')` == `"secure-org/protected-repo"` to locate and mutate the real, secured stack, entirely bypassing `secure-org`'s configured secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
