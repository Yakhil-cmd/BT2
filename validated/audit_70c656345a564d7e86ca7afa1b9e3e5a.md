### Title
Pool repay/recapitalize refund derived from declared amount pays unbacked refunds out of custody - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `repay` and `recapitalize` legs assume the declared `amount` was already transferred into the pool ("The controller transfers `amount` into the pool before this call") but never measure the actual inbound token balance. The excess-over-debt (repay) or excess-over-shortfall (recapitalize) refund is computed purely from the declared amount and paid out via `transfer_out`, while only the *applied* portion is credited to `cash`. An unprivileged caller can invoke `pool.repay` directly on a market with no debt, declare an arbitrary amount, transfer nothing in, and receive the full declared amount as a "refund" drawn from real pool custody — the exact analog of `validateOrder` trusting `zoneParameters.consideration[0].amount` without a `balanceOf` check.

### Finding Description
In `ops::repay::accounting` (contracts/pool/src/ops/repay.rs:40-67), `resolve_repay(amount, position)` splits the declared `action.amount` into burned debt shares and `overpayment`; `net_repay = amount - overpayment` is credited to cash, and `apply` (lines 25-34) then calls `cache.transfer_out(payer, outcome.overpayment)`. The same shape exists in `ops::recapitalize::accounting` (contracts/pool/src/ops/recapitalize.rs:44-67): `applied = min(amount, backing_shortfall)`, `refund = amount - applied`, then `apply` (lines 26-38) transfers the refund to `payer`. Neither path snapshots `token.balance(pool)` before/after, nor compares the received amount against the declared amount, nor debits `cash`/`require_reserves` for the outbound refund leg — the refund is paid out of unrelated custody while the book stays unchanged. This is exactly the reported bug class: a settlement endpoint derives a payment/refund from a caller-supplied amount field without validating it against actual token balance.

### Impact Explanation
Theft of user funds / protocol insolvency. The in-repo regression test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3590-3611) demonstrates the drain: a fresh `payer` calls `repay` with `amount = custody_before` on a market with zero debt, transfers nothing, `credited == 0`, and `assert_unfunded_refund_drained_custody` (lines 3376-3406) shows the payer receives the full `declared` amount, the pool's entire token custody leaves the contract, and `cash` still reports the funds as present — so subsequent withdrawals that `require_reserves` admits will fail inside the SAC transfer (permanent insolvency of the book). The same path exists via `recapitalize` on any market where `backing_shortfall < amount`, including `shortfall == 0`.

### Likelihood Explanation
Reachable by any unprivileged address: `pool.repay` accepts a `PoolAction` batch with a caller-chosen `amount` and `payer`, with no check that tokens were pushed beforehand (the production flows always route through the controller, which does pull first, but the pool entrypoint itself does not enforce it). Preconditions are trivial: a listed market with nonzero custody and zero/low debt, or any market whose backing shortfall is below the declared amount. No oracle manipulation, timing, or privileged role is needed.

### Recommendation
Measure, don't trust. Snapshot `token::Client::balance(pool)` at entry and require the inbound delta to cover `amount` before computing `net_repay`/`applied` and the refund — the same `transfer_amount_measured`/`balance_delta_since` discipline already used in `controller/src/payments.rs` and `ops/flash.rs` (`INV-FLASH-01`). Alternatively, replace the push-then-refund design with a pull (`transfer_from`) of exactly `net_repay`/`applied`, so no refund leg ever pays out of custody. Either way, the refund must be bounded by measured received funds, mirroring the report's `balanceOf >= payment` fix.

### Proof of Concept
From the in-repo test (contracts/pool/tests/flows.rs:3590-3611), restated as an attack:

```rust
// pool has `custody_before` tokens of real custody, `borrowed == 0`.
let payer = Address::generate(&env);           // unprivileged, holds nothing
let action = PoolAction {                      // t.ract(0, custody_before)
    hub_asset, kind: Repay,
    amount: custody_before,                    // declared, never transferred
    ...
};
pool_client.repay(&payer, &vec![action]);
// resolve_repay: current_debt_ceil == 0 => overpayment == amount, net_repay == 0
// RepayRoundsToZeroShares assert passes on `net_repay == 0`
// transfer_out(payer, custody_before) drains pool custody; cash unchanged
```

Result: `token.balance(payer) == custody_before`, `token.balance(pool) == 0`, `cash` still reports the paid-out funds, and later supplier withdrawals revert — the pool is insolvent. The identical sequence via `recapitalize(hub_asset, payer, amount)` on a market with `backing_shortfall == 0` yields `applied == 0`, `refund == amount`, and the same unbacked payout.
