### Title
Unfunded `recapitalize` refunds the declared amount out of pool custody without verifying an inbound payment - (File: contracts/pool/src/lib.rs)

### Summary
The pool's `recapitalize` path pays a "refund" to the declared `payer` for a payment that was never measured as received. The bug class mirrors the hinic CMDQ leak: a failure/cleanup path releases a resource (pool token custody) that was never actually committed. An unprivileged caller can drain the pool's real token balance by declaring a recapitalize amount while transferring nothing in, leaving the `cash` book overstating custody and the market unable to honor withdrawals.

### Finding Description
`Pool::recapitalize(hub_asset, payer, amount)` is exercised directly in `contracts/pool/tests/flows.rs`. The dedicated tests document the defect precisely:

- `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` calls `recapitalize(&hub(asset), &payer, &custody)` where `payer` never funded the pool, and asserts the payer "is refunded in full for a payment that never happened", the pool's entire custody leaves the contract, and the cash book is untouched.
- `test_unfunded_recapitalize_is_bounded_by_custody_not_by_the_declared_amount` confirms the payout is bounded only by live custody — i.e., a claim up to the full pool balance succeeds.

The controller-side `recapitalize` uses `transfer_amount_measured` (balance-delta receipt measurement), but the pool-level settlement honors the declared amount with no proof of receipt — the payment leg is optional while the refund leg is unconditional.

### Impact Explanation
An attacker calls `recapitalize` with `payer = attacker` and `amount = pool_balance(token)`. The pool transfers its entire custody of that token to the attacker while the `cash` book still records the funds as present. Result: direct theft of all supplied liquidity in that market (theft of user funds), followed by protocol insolvency — `Cache::require_reserves` reads the book, so legitimate withdrawals pass the liquidity guard and then revert inside the SAC transfer, permanently freezing remaining suppliers' accounting claims.

### Likelihood Explanation
Reachable by any unprivileged address in a single transaction: no privileged role, timing, price movement, or pre-existing position is required. The only bound is live pool custody, so the maximum theft equals the market's full balance.

### Recommendation
Make the pool settlement measured: snapshot the pool's token balance, pull `amount` from `payer` (or require the controller to have already transferred in), and only then pay the refund — or restructure so the refund is `min(declared, measured_inflow)` and revert when the measured inflow is zero. The cash book and custody must stay consistent on every settlement path.

### Proof of Concept
Documented by the repo's own tests in `contracts/pool/tests/flows.rs` (lines 3404–3516): seed the pool with a supplier deposit via `supply`, then call `recapitalize(hub_asset, payer, custody)` from an unfunded `payer`. Assertions confirm `token.balance(&pool) == 0`, `payer` received the full amount, `cash` still claims the deposit, and the supplier's subsequent `withdraw` reverts inside the SAC transfer (`BalanceError = 10`) rather than at a pool guard.
