### Title
Cross-repository forgery of commit CI status via webhook signature bypass for unconfigured-secret organizations — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The webhook signature check in `WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate against using a value taken from the attacker-controlled payload itself (`repository.owner.login` or `organization.login`), and `GithubApp#verify_webhook_signature` trivially returns `true` whenever that organization has no `webhook_secret` configured. `StatusHandler#process`, which is dispatched after that check, then writes a commit CI status using nothing but a bare, unscoped `sha` lookup across the entire database — with no check that the commit belongs to the repository/organization whose credentials were actually verified. The binding "organization that authenticated == repository that is written" is broken.

### Finding Description
`WebhooksController#verify_signature` picks the `github_app` (and therefore the secret used to validate `X-Hub-Signature`) purely from data inside the untrusted JSON payload: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` bypasses validation entirely for any organization that has no secret configured — which is the documented/example default in the multi-organization setup (`webhook_secret: # nil` in `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`, and `docs/setup.md`): [3](#0-2) 

Once the request passes this check, `Shipit::Webhooks.for_event(event)` dispatches to handlers with the raw, still-untrusted `params`: [4](#0-3) 

`StatusHandler#process` never uses `Handler#stacks`/`repository_name` scoping at all — it looks up commits **globally by `sha`** and writes a status to whatever commit(s) match, regardless of which repository/stack they belong to: [5](#0-4) 

Compare this with `Handler#stacks`, which is how other handlers correctly scope writes to the repository named in the payload: [6](#0-5) 

So the equality that should hold — *the organization whose credential was verified == the repository/stack whose state is mutated* — does not hold for `status` events: the verified side is `repository.owner.login`/`organization.login` (attacker-chosen, can be any org with a blank `webhook_secret`), while the mutated side is any commit anywhere in the instance that happens to share the forged `sha`.

### Impact Explanation
This is an unprivileged-attacker escalation with no session, `ApiClient` token, or `webhook_secret` knowledge required for the *target* organization: the attacker only needs to know (or guess) the name of *any* organization configured in Shipit's multi-org `github:` block that has not set a `webhook_secret` (a state explicitly shown as a valid/default configuration in this repo's own example secrets files and docs). By forging a `status` webhook citing that unconfigured organization, they can set an arbitrary CI state (`success`) on any commit SHA tracked by any stack in the instance — including stacks belonging to other, fully-secured organizations. Since commit deployability in Shipit is gated on CI status (`deployable?`/`required_statuses` checks referenced throughout `test/models/commits_test.rb`), this can be used to force a commit to appear CI-green and trigger an unauthorized deploy of a protected repository's stack — meeting the Critical bar ("an unauthorized deploy").

### Likelihood Explanation
High: exploitation requires only a single unauthenticated HTTP POST to the public `WebhooksController#create` endpoint with attacker-chosen JSON. No secrets, tokens, or prior repository access are needed for the target repository — only knowledge that some other organization in the same Shipit instance's config has no `webhook_secret` set, which is the documented default/example configuration shape in this codebase.

### Recommendation
- Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank in a multi-organization deployment; require every configured organization to have a non-blank secret, or reject webhooks for organizations without one.
- Scope `StatusHandler#process` (and any other handler that doesn't use `Handler#stacks`) to the repository actually named in the payload (`repository.full_name`), consistent with the other handlers, rather than doing a global, unscoped `Commit.where(sha:)` lookup.
- Ensure the organization used for signature verification and the repository/organization whose records are mutated are always the same value taken from a signature-verified payload, never independently re-derived from different, unauthenticated payload fields.

### Proof of Concept
1. Configure (or observe) a multi-org Shipit instance where organization `unsecured-org` has `webhook_secret` unset (per the documented example configs), while organization `secured-org` (with a real webhook secret) owns a tracked stack containing commit `abcdef1234...` that is currently failing CI.
2. POST to `/github/webhooks` (no `X-Hub-Signature` header needed):
```
X-Github-Event: status

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "unsecured-org/whatever" },
  "sha": "abcdef1234...",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)`, which returns `true` unconditionally because that org has no `webhook_secret`.
4. `StatusHandler#process` runs `Commit.where(sha: "abcdef1234...")`, finds the commit belonging to `secured-org`'s stack (unrelated to `unsecured-org`), and calls `create_status_from_github!`, marking it as passing CI — enabling a deploy of `secured-org`'s protected stack without ever presenting a valid signature for that organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
