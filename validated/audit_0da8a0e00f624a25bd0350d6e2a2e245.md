## Title
Header-Commission Percentage-Share Rounding Enables Byte Supply Inflation - (File: `headers_commission.js`)

## Summary
`calcHeadersCommissions()` in `headers_commission.js` splits a payer unit's fixed `headers_commission` budget among multiple recipients by rounding each recipient's percentage share independently, exactly the same "per-entity percentage rounding" anti-pattern described in the referenced report. Because each recipient's amount is computed with an independent `Math.round(full_amount * share / 100.0)` instead of allocating a remainder-aware split, the sum of rounded per-recipient amounts can exceed the actual `full_amount` that was ever deducted from the payer, creating bytes that were never backed by any real balance reduction — a concrete supply-inflation bug, reachable by any unprivileged unit author who defines `earned_headers_commission_recipients` on their own unit.

## Finding Description
When headers-commission winners are computed, the amount owed to each recipient address is calculated independently from the payer's `headers_commission` and that recipient's percentage `earned_headers_commission_share`: [1](#0-0) 

and again in the SQL/RAM cross-check path: [2](#0-1) 

The MySQL variant performs the identical unsafe operation directly in SQL: [3](#0-2) 

`earned_headers_commission_share` is a plain integer percentage field, freely set by the unit's author(s) when they define multiple authors/recipients on a unit, and is persisted without any remainder-normalization: [4](#0-3) [5](#0-4) 

Because each recipient's share is rounded to the nearest integer *independently*, symmetric splits (e.g. two recipients at 50%/50%) round in the *same direction* whenever `full_amount` is odd: `Math.round(full_amount/2)` computed twice yields `2 * round(full_amount/2)`, which is `full_amount + 1` whenever `full_amount` is odd. This is not a random, self-canceling rounding error — it is a deterministic, direction-biased error for any split where the fractional remainders coincide across recipients, guaranteeing the sum distributed exceeds the amount actually earned.

The distributed (possibly inflated) amounts are inserted into `headers_commission_contributions`, aggregated into `headers_commission_outputs`, and later become fully spendable "headers_commission" type inputs validated elsewhere in the codebase: [6](#0-5) [7](#0-6) 

Nothing in this path re-checks that `SUM(recipient_amounts) <= full_amount`; the per-recipient rounded amounts are trusted as-is and become real spendable UTXOs.

## Impact Explanation
Each occurrence creates new spendable bytes that were never deducted from any payer's balance, directly inflating the circulating byte supply beyond the fixed genesis total (`constants.TOTAL_WHITEBYTES`), which is only enforced at genesis issuance and nowhere else at commission-distribution time: [8](#0-7) 

Because the exploit is deterministic (not merely probabilistic rounding noise) and can be triggered repeatedly by an attacker who fully controls both recipient addresses of their own unit, it constitutes a systematic, repeatable supply-inflation primitive rather than a one-off rounding quirk.

## Likelihood Explanation
Any unprivileged user can:
1. Author a unit with `earned_headers_commission_recipients` split 50/50 (or any symmetric split with the same rounding-remainder) between two addresses they control.
2. Ensure that unit becomes the deterministic "winner" of headers commission from some parent unit (the winner is picked from candidate children via a public SHA1-lowest-hash tie-break, so multiple candidate children can be posted to increase win probability) whose `headers_commission` happens to be odd — an extremely common, unconstrained value determined purely by unit byte size.
3. Repeat at will across the DAG at low cost (only the cost of posting units), each time skimming +1 byte of unbacked commission.

This requires no special privileges, no witness/hub/OP role, and no network-level manipulation — only ordinary unit posting capability, matching the reachable-actor requirement (unprivileged unit poster).

## Recommendation
Replace independent per-recipient rounding with a remainder-safe distribution algorithm, e.g.:
- Compute each recipient's amount with `Math.floor(full_amount * share / 100)`, then distribute the leftover remainder deterministically (e.g., to the largest-remainder recipient, or entirely to a designated primary recipient), guaranteeing `SUM(recipient_amounts) === full_amount` exactly.
- Enforce this invariant in both the SQL (mysql) and JS (sqlite/RAM) code paths identically, and add a consistency assertion (`SUM(amount) === headers_commission`) similar to the existing debug-mode cross-checks already present in the function, but always enforced (not only under `!conf.bFaster`).

## Proof of Concept
1. Let a payer unit `A` be included such that its `headers_commission` field equals an odd number, e.g. `3` (trivially achievable — header commission is proportional to header/unit byte size and is odd roughly half the time).
2. Author a winning child unit `B` (the unit selected by the existing SHA1 tie-break as the earner of `A`'s header commission) as multi-authored with:
```
earned_headers_commission_recipients: [
  { address: X, earned_headers_commission_share: 50 },
  { address: Y, earned_headers_commission_share: 50 }
]
```
where `X` and `Y` are both addresses controlled by the attacker.
3. When `calcHeadersCommissions()` runs for the stabilizing MCI, for each recipient:
```
amount = Math.round(3 * 50 / 100.0) = Math.round(1.5) = 2
```
Both `X` and `Y` receive `2`, for a total of `4`, one more byte than the `3` bytes that `A` actually paid — confirmed directly by the code at: [9](#0-8) 
4. The extra byte is inserted into `headers_commission_contributions` and later aggregated into `headers_commission_outputs`, becoming a spendable `headers_commission`-type input for `X` and `Y`, permanently inflating the circulating byte supply by 1 unit per occurrence — repeatable indefinitely.
