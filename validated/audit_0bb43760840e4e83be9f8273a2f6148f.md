### Title
AA-generated units are exempt from the `MAX_UNIT_LENGTH` size cap after `pemCurvesFixMci`, allowing unbounded response-unit size/fees - (File: validation.js)

### Summary
`validate()` and `validateParents()` in `validation.js` enforce the anti-spam invariant that a unit's `headers_commission + payload_commission` must not exceed `constants.MAX_UNIT_LENGTH`. This is exactly the same class of bug described in the external report: a size/overhead value computed from transaction/message data (`_encodingLength`/`overheadForPublicData` in zkSync) can exceed its intended maximum because the check is missing or incomplete for certain code paths. Here, the equivalent invariant is silently skipped for Autonomous Agent (AA)-generated units once the chain has passed `pemCurvesFixMci`.

### Finding Description
In `validate()`, the size cap is only checked for non-AA units: [1](#0-0) 
```
if (objUnit.headers_commission + objUnit.payload_commission > constants.MAX_UNIT_LENGTH && !bGenesis && !bAA)
    return callbacks.ifUnitError("unit too large");
```
For AA units (`bAA === true`), `validateParents()` only re-applies the cap while `last_ball_mci < constants.pemCurvesFixMci`: [2](#0-1) 
```
if (objUnit.headers_commission + objUnit.payload_commission > constants.MAX_UNIT_LENGTH && objValidationState.bAA && objValidationState.last_ball_mci < constants.pemCurvesFixMci)
    return callback("unit too large");
```
Once `last_ball_mci >= constants.pemCurvesFixMci`, neither check applies to AA units, so an AA response unit's total size (`headers_commission + payload_commission`, computed by `objectLength.getHeadersSize`/`objectLength.getTotalPayloadSize`, see [3](#0-2) ) is never bounded by `MAX_UNIT_LENGTH`.

Per-field limits still exist (`MAX_MESSAGES_PER_UNIT=128`, `MAX_AA_STRING_LENGTH=4096`, `MAX_DATA_FEEDS_PER_MESSAGE=1024`, `MAX_DATA_FEED_VALUE_LENGTH=64`, `MAX_STATE_VAR_VALUE_LENGTH=1024`, etc. — [4](#0-3) ), but these per-message limits multiplied across the maximum number of messages can exceed `MAX_UNIT_LENGTH` (5,000,000 bytes, [5](#0-4) ) — e.g. a single `data_feed` message alone can reach `1024 * 64 = 65536` bytes, and with up to 128 messages the theoretical total dwarfs the 5 MB cap. So the global invariant that a regular unit relies on is not actually redundant with the per-field limits for AA units.

Because `aa_composer.js` computes `headers_commission`/`payload_commission`/`oversize_fee` from the same unbounded size and charges it to the AA's own balance before saving the unit (`storage.getOversizeFee` grows exponentially past `threshold_size`, see [6](#0-5)  and its use in `aa_composer.js`): [7](#0-6) 
an AA whose trigger-controlled output content (e.g., echoing large data-feed or state-derived data back in a `data`/`data_feed` message) can grow past what `MAX_UNIT_LENGTH` was designed to allow, without validation ever rejecting the resulting unit for size.

### Impact Explanation
This breaks the intended invariant that bounds unit size (and, by extension, the size-derived `oversize_fee`) for every unit type. For AA-generated units, an unprivileged trigger sender can craft trigger data (subject only to the per-field byte limits, not to any aggregate cap) that forces the AA to emit an oversized response unit. Because `oversize_fee` and `headers_commission`/`payload_commission` scale with size — and the exponential `getOversizeFee` formula grows steeply once `size` exceeds `threshold_size` — the AA's balance can be charged fees far larger than the protocol's `MAX_UNIT_LENGTH`-based fee model anticipates, draining AA funds that the AA's own logic did not intend to spend. This is an unintended AA fund loss caused by bypassing the size-cap invariant, analogous to the zkSync issue where unchecked overhead values could exceed maximum bounds and violate gas-metering invariants.

### Likelihood Explanation
Any address can define and trigger an AA (an "AA trigger sender" is explicitly in scope). Exploitation only requires designing (or interacting with) an AA whose oscript echoes attacker-influenced data (e.g., trigger data, data feed values, or state variables) into outgoing `data`/`data_feed` messages up to the per-field limits, repeated across the maximum number of messages. No special privileges, malicious nodes, or network conditions are needed — only ordinary unit posting/trigger sending, which is squarely in the unprivileged AA trigger sender's capability.

### Recommendation
Restore the unconditional `MAX_UNIT_LENGTH` check for AA units in both `validate()` (currently skipped via `&& !bAA`) and `validateParents()` (currently gated to `last_ball_mci < constants.pemCurvesFixMci`), i.e., re-enable the cap for all mci ranges rather than only pre-`pemCurvesFixMci`. Additionally, have `aa_composer.js` proactively enforce the same cap while composing the AA response unit (bouncing the trigger instead of silently building/charging for an oversized unit) so the invariant is checked at the point of construction as well as at validation.

### Proof of Concept
1. Post an AA whose response includes a `data_feed` (or `data`) message whose fields are populated from trigger data/state, each field near the `MAX_DATA_FEED_VALUE_LENGTH`/`MAX_AA_STRING_LENGTH` per-field limits, and which the AA repeats across many response messages (up to `MAX_MESSAGES_PER_UNIT`).
2. Trigger the AA repeatedly (or once, with maximal trigger payload) at an mci `>= constants.pemCurvesFixMci`, so that the resulting response unit's `headers_commission + payload_commission` exceeds `constants.MAX_UNIT_LENGTH`.
3. Observe in `aa_composer.js`'s `sendUnit()`/`completePaymentPayload()` flow ( [8](#0-7) ) that `validateAndSaveUnit` succeeds despite the oversized unit, because neither `validate()` (`bAA` excluded) nor `validateParents()` (mci past `pemCurvesFixMci`) rejects it — confirming the size cap is not enforced and the AA is charged fees proportional to the unbounded size.

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
}
