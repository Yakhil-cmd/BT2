### Title
Unbounded Concurrent Validation of Private Payment Chains Causes CPU/Memory Exhaustion - (File: network.js)

### Summary
`network.js`'s `handleSavedPrivatePayments()` pulls **all** rows from the `unhandled_private_payments` table and validates each one with `async.each` — i.e. fully in parallel, with no concurrency cap and no serialization queue — mirroring the CVE-2019-18214 pattern where many expensive jobs (there: FFmpeg conversions; here: private-chain cryptographic/DB validation) run concurrently instead of being queued for serial execution. [1](#0-0) 

### Finding Description
A device-paired counterparty (or anyone able to reach a wallet through the "private_payments" hub-relayed message, handled in `wallet.js`'s `handlePrivatePaymentChains`) can send private-payment chains to a wallet node. Each chain that isn't immediately resolvable (e.g. light client with an unknown/unstable ancestor unit) is persisted to the `unhandled_private_payments` table via `savePrivatePayment` inside `handleOnlinePrivatePayment`, and the caller is told `ifQueued()` without blocking: [2](#0-1) 

The outer loop in `wallet.js` that receives these chains from the hub uses `async.eachSeries`, so an attacker can cheaply enqueue an arbitrary number of chains in a single "private_payments" message (or many messages) without the wallet doing expensive work at enqueue time: [3](#0-2) 

Later, `handleSavedPrivatePayments()` is invoked (e.g. on new unit/joint arrival) and reads back every pending row from `unhandled_private_payments`, then validates **all of them concurrently** using `async.each` ("handle different chains in parallel"): [4](#0-3) 

Each parallel job performs non-trivial work per chain: a DB transaction (`BEGIN`), asset lookup, spend-proof and hash verification, and for indivisible chains a full `parsePrivatePaymentChain` walk of the private-element list with per-element crypto hashing (`objectHash.getBase64Hash`) and a `graph.determineIfIncluded` DAG traversal query: [5](#0-4) [6](#0-5) 

None of these code paths impose a cap on the number of chains queued in `unhandled_private_payments`, nor do they limit the concurrency of `async.each` in `handleSavedPrivatePayments`. This is directly analogous to the reported CVE: many concurrent expensive jobs are triggered by unprivileged input and are not queued for serial execution, so they all run at once.

### Impact Explanation
An attacker who is a paired device or private-payment counterparty (or anyone able to relay "private_payments" messages via a hub to a victim wallet) can flood the victim with a large number of distinct private-payment chains. Because `handleSavedPrivatePayments` fires all queued validations in parallel via `async.each`, the wallet node can be driven to open many simultaneous DB transactions and perform many simultaneous cryptographic hash/graph-traversal operations, exhausting CPU and memory/connection-pool resources on the victim's node — a denial of service preventing legitimate transaction processing, matching the "network unable to confirm new units" / node resource-exhaustion impact class allowed by the rules.

### Likelihood Explanation
Reaching this path requires only the ability to send "private_payments"-subject device messages to a wallet (a paired device, or a private-payment counterparty relaying through a hub) — no special privileges. Enqueuing chains is cheap (`INSERT ... IGNORE` per chain), so an attacker can cheaply build up a large backlog in `unhandled_private_payments` before the parallel-validation trigger fires, making the attack easy to mount repeatedly.

### Recommendation
Serialize processing of `unhandled_private_payments` (e.g. replace `async.each` with `async.eachLimit`/`eachSeries` in `handleSavedPrivatePayments`, or reuse `mutex`-based per-key queuing already present elsewhere in the codebase), and impose a hard cap on the number of pending unhandled private payment chains a single counterparty/device can queue.

### Proof of Concept
1. As a paired device (or relay through a hub), send a `"private_payments"` message with `body.chains` containing N distinct chains (large N), each referencing an unknown/unstable ancestor unit so it gets queued rather than validated immediately (`ifQueued` branch in `handleOnlinePrivatePayment`, `network.js:2404-2410`).
2. `wallet.js`'s `handlePrivatePaymentChains` (`wallet.js:1020-1064`) inserts all N chains into `unhandled_private_payments` cheaply via `async.eachSeries`, each iteration doing only a lightweight INSERT.
3. Trigger (or wait for) `handleSavedPrivatePayments()` — it reads all N pending rows and validates them with `async.each` (`network.js:2459-2518`), spawning N concurrent DB transactions and cryptographic/graph-traversal validations at once, consuming CPU/memory disproportionately to legitimate load.

Note: Confirming the exact runtime trigger frequency of `handleSavedPrivatePayments()` (I found 3 references in `network.js` but could not fully trace all call sites due to index truncation) and quantifying the practical N achievable per message would benefit from a full-repo Devin session to verify call graph and any implicit rate limits not visible in the indexed snippets.
