[1](#0-0) 

### Title
Silent failure of `INSERT IGNORE` in `validateAndSavePrivatePaymentChain` is never checked, letting a colliding private-asset chain be accepted as valid without being persisted - (File: indivisible_asset.js)

### Summary
`validateAndSavePrivatePaymentChain` builds a batch of `INSERT ` + `db.getIgnore()` `INTO inputs` / `INTO outputs` queries and runs them with `async.series(arrQueries, function(){ ... callbacks.ifOk(); })`, unconditionally reporting success regardless of whether the rows were actually written.

### Finding Description
`db.getIgnore()` returns the dialect-specific "ignore duplicate key" clause (`OR IGNORE` for SQLite, `IGNORE` for MySQL). This is used intentionally for idempotency when the exact same private-payment chain is re-received. However, the row-level uniqueness constraint on `inputs` (`bySrcOutput`/`byAssetDenominationSerialAddress`) and `outputs` (`unit, message_index, output_index`) can also collide when a *different* conflicting/malformed private element happens to reuse an already-occupied primary/unique key for that unit+message_index+output_index (for private chains the unit hash is attacker/counterparty supplied content that has already passed `parsePrivatePaymentChain`'s `ifOk` callback, but the actual persistence step's success is never verified). Because the code never checks `affectedRows`/`changes` returned by `conn.addQuery`, a row that silently fails to insert (e.g., because a prior row already occupies that primary key with different, unexpected data) is treated exactly the same as a full, correct persistence, and `callbacks.ifOk()` fires unconditionally.

This mirrors the `CompoundToNotionalV2.enableToken` class of bug: an operation that can silently return "did nothing" instead of throwing is treated as unconditional success because the return/affected-row value is discarded. [2](#0-1) 

### Impact Explanation
If the `outputs` or `inputs` rows for a spend-marking update (`is_spent=1`, `address`, `blinding` for the currently-owned output) are silently skipped because of an ignored insert conflict, the wallet's local state can diverge from the actual chain-of-custody recorded by the sender/previous owners, while the code still reports the chain as accepted (`ifOk`). This can lead to private-asset ownership/spendability bookkeeping being wrong for the recipient (e.g., the coin recorded as not spent/owned when it should be, or vice versa), which is a fund-loss/inconsistency class of issue limited to private (indivisible) asset chains reachable directly from any private-payment counterparty message.

### Likelihood Explanation
Likelihood is limited by the fact that `parsePrivatePaymentChain`'s prior validation must already accept the chain, and the primary-key collision has to line up with pre-existing rows for the same `unit/message_index/output_index` (which normally would only happen through resending of an identical valid chain, the intended IGNORE case). It requires a specifically crafted private element sequence from a payment counterparty to trigger a divergent, non-verified persistence path, so likelihood is moderate rather than trivial.

### Recommendation
After executing the batch of `INSERT ... IGNORE` and `UPDATE` queries in `validateAndSavePrivatePaymentChain`, verify the actual number of affected/changed rows for each insert/update matches the expected count (one row per input/output) before invoking `callbacks.ifOk()`. If any expected row was not written (i.e., ignored due to a genuine conflict rather than an exact idempotent resend), the batch should be treated as an error and surfaced via `callbacks.ifError` instead of silently succeeding.

### Proof of Concept
1. A counterparty sends a first private payment chain element for `unit U`, `message_index m`, `output_index o` that gets inserted into `outputs` via `validateAndSavePrivatePaymentChain`.
2. The counterparty (or an attacker controlling private-chain messages to the wallet) later sends a second, different private element that legitimately validates through `parsePrivatePaymentChain` but targets the same `(unit, message_index, output_index)` primary key with different `amount`/`address`/`blinding` values (e.g., due to a bug or race in upstream validation allowing the same coordinates to be reused across chains).
3. The `INSERT` + `db.getIgnore()` silently no-ops because the primary key already exists; the stale/incorrect prior row remains.
4. `async.series` still completes without error and `callbacks.ifOk()` is invoked, so the receiving wallet considers the new chain fully and correctly persisted even though the on-disk state does not reflect it, causing bookkeeping/spendability inconsistency for the private asset.

function validateAndSavePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	parsePrivatePaymentChain(conn, arrPrivateElements, {
		ifError: callbacks.ifError,
		ifOk: function(bAllStable){
			console.log("saving private chain "+JSON.stringify(arrPrivateElements));
			profiler.start();
			var arrQueries = [];
			for (var i=0; i<arrPrivateElements.length; i++){
				var objPrivateElement = arrPrivateElements[i];
				var payload = objPrivateElement.payload;
				var input_address = objPrivateElement.input_address;
				var input = payload.inputs[0];
				var is_unique = objPrivateElement.bStable ? 1 : null; // unstable still have chances to become nonserial therefore nonunique
				if (!input.type) // transfer
					conn.addQuery(arrQueries, 
						"INSERT "+db.getIgnore()+" INTO inputs \n\
						(unit, message_index, input_index, src_unit, src_message_index, src_output_index, asset, denomination, address, type, is_unique) \n\
						VALUES (?,?,?,?,?,?,?,?,?,'transfer',?)", 
						[objPrivateElement.unit, objPrivateElement.message_index, 0, input.unit, input.message_index, input.output_index, 
						payload.asset, payload.denomination, input_address, is_unique]);
				else if (input.type === 'issue')
					conn.addQuery(arrQueries, 
						"INSERT "+db.getIgnore()+" INTO inputs \n\
						(unit, message_index, input_index, serial_number, amount, asset, denomination, address, type, is_unique) \n\
						VALUES (?,?,?,?,?,?,?,?,'issue',?)", 
						[objPrivateElement.unit, objPrivateElement.message_index, 0, input.serial_number, input.amount, 
						payload.asset, payload.denomination, input_address, is_unique]);
				else
					throw Error("neither transfer nor issue after validation");
				var is_serial = objPrivateElement.bStable ? 1 : null; // initPrivatePaymentValidationState already checks for non-serial
				var outputs = payload.outputs;
				for (var output_index=0; output_index<outputs.length; output_index++){
					var output = outputs[output_index];
					console.log("inserting output "+JSON.stringify(output));
					conn.addQuery(arrQueries, 
						"INSERT "+db.getIgnore()+" INTO outputs \n\
						(unit, message_index, output_index, amount, output_hash, asset, denomination) \n\
						VALUES (?,?,?,?,?,?,?)",
						[objPrivateElement.unit, objPrivateElement.message_index, output_index, 
						output.amount, output.output_hash, payload.asset, payload.denomination]);
					var fields = "is_serial=?";
					var params = [is_serial];
					if (output_index === objPrivateElement.output_index){
						var is_spent = (i===0) ? 0 : 1;
						fields += ", is_spent=?, address=?, blinding=?";
						params.push(is_spent, objPrivateElement.output.address, objPrivateElement.output.blinding);
					}
					params.push(objPrivateElement.unit, objPrivateElement.message_index, output_index);
					conn.addQuery(arrQueries, "UPDATE outputs SET "+fields+" WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0", params);
				}
			}
		//	console.log("queries: "+JSON.stringify(arrQueries));
			async.series(arrQueries, function(){
				profiler.stop('save');
				callbacks.ifOk();
			});
		}
	});
}
