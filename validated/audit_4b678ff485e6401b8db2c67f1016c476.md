### Title
Fee-on-transfer/deflationary ERC20 contracts break `ERC20Transactor` amount accounting, trapping XCM-transferred value - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` treat the XCM-requested `amount` as the actual amount moved by an arbitrary, attacker-deployed Solidity ERC20 contract, without ever comparing the contract's real balance delta to `amount`. Any contract that charges a transfer fee (deflationary/fee-on-transfer token, trivially written and deployed by any user via `pallet-revive`) causes the XCM holding register to be credited with more than what the checking account actually received, and later the fixed-`amount` withdrawal-side `transfer` call to the beneficiary can fail or under-deliver, trapping the difference.

### Finding Description
`withdraw_asset_with_surplus` calls the target contract's `IERC20::transfer(to: checking_account, value: amount)` via `pallet_revive::Pallet::<T>::bare_call`, and on a boolean `true` return, unconditionally credits `AssetsInHolding::new_from_fungible_credit(what.id, Erc20Credit(amount))` with the full requested `amount` [3](#0-2) . There is no read of `balanceOf(checking_account)` before/after the call to determine the *actual* amount received — exactly the missing check the report describes for `DonationVotingMerkleDistributionVaultStrategy._afterAllocate`.

Symmetrically, `deposit_asset_with_surplus` transfers the same fixed `amount` out of the checking account to the beneficiary via another `IERC20::transfer` call and only checks the boolean return / revert flag, again never verifying that the beneficiary actually received `amount` [4](#0-3) .

The transactor is generic over `Matcher: MatchesFungibles<H160, u128>`, and the configured `ERC20Matcher` accepts *any* local `AccountKey20` location — there is no allow-list, ownership check, or governance gate [1](#0-0) . This is the real, unprivileged user entry point: any signed account can (1) deploy a fee-on-transfer ERC20 contract through `pallet-revive`, and (2) use `pallet-xcm`'s public reserve-transfer/execute extrinsics with an `Asset` whose `id` is that contract's `AccountKey20` location, causing the executor to invoke `ERC20Transactor` for this asset via the configured `AssetTransactors` tuple [5](#0-4) .

Because `Erc20Credit`'s imbalance amount is exactly the requested `amount` regardless of what the ERC20 contract actually moved [6](#0-5) , a fee-deducting contract causes:
1. `withdraw_asset_with_surplus`: sender's real ERC20 balance decreases by `amount`, but checking account only receives `amount - fee`. Holding register nonetheless records `amount`.
2. On deposit to the beneficiary (locally, or after a hop through another chain that echoes back the recorded `amount`), `deposit_asset_with_surplus` attempts to `transfer(amount)` out of the checking account — which now holds strictly less than `amount` — causing the underlying `transfer` call to revert/return `false` for a spec-compliant ERC20 (`ERC20InsufficientBalance`), which is exactly the `_update`/`_transfer` balance check seen in the OpenZeppelin fixture bundled in this repo [7](#0-6) .
3. `deposit_asset_with_surplus` then returns `Err((what, XcmError::FailedToTransactAsset(...)))`, which causes the XCM executor to trap the assets (`AssetsInHolding` `what` is returned back but the underlying real tokens are stuck in the checking account, an account nobody except the pallet's own logic can move funds out of via ordinary transfers, since it is a `PalletId`-derived account with no user-facing withdrawal path for the shortfall).

The sender's real, on-chain ERC20 balance was permanently reduced by `amount` (the fee-on-transfer contract enforces this on the withdraw leg), while the amount actually recoverable through the checking account/beneficiary path is capped at `amount - fee`, and even that recovery fails outright because the deposit leg tries to move the full, un-adjusted `amount`.

### Impact Explanation
Funds withdrawn from the user during the XCM `WithdrawAsset`/reserve-transfer leg are permanently unrecoverable once the deposit-side fixed-`amount` transfer fails: the checking account cannot release its actual (reduced) balance to the beneficiary through the transactor's logic, since it always attempts `amount`, not the checking account's real ERC20 balance. This is a fund-freezing bug reachable by any signed user with a wallet capable of deploying a trivial contract, no privileged role required. It matches the report's core defect class: "amount recorded/credited does not reflect actual balance movement of an externally-controlled token contract," applied to `ERC20Transactor` instead of the Solidity vault contract in the original report.

### Likelihood Explanation
High for the trigger condition (deploying and using a fee-on-transfer contract as the `ERC20Transactor`'s asset requires only standard, unprivileged `pallet-revive` contract deployment plus a normal `pallet-xcm` transfer/execute call using that contract's location as the `AssetId`). Whether it manifests as "value permanently stuck" versus "transaction cleanly fails and rolls back" depends on `pallet-revive`/XCM executor's transactional semantics around `bare_call` and instruction failure handling, and on whether the checking-account's ERC20 balance from the withdraw leg is rolled back together with the deposit-leg failure in the same XCM message (it is not, since withdraw and deposit are executed as separate, already-committed `bare_call`s inside distinct XCM instructions of possibly different messages/hops).

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus`, read the checking account's `balanceOf` before and after the `transfer` call (or decode/verify a `Transfer` event amount) and credit `Erc20Credit` with the *actual* delta rather than the requested `amount`. In `deposit_asset_with_surplus`, similarly measure the actual amount delivered to the beneficiary and reconcile any shortfall back into the returned `AssetsInHolding` (as the report recommends: "use balance before and after check"), so no held/recorded balance ever exceeds what is truly transactable through the underlying contract.

### Proof of Concept

A concrete PoC would: (1) deploy a minimal fee-on-transfer ERC20 via `pallet_revive::Pallet::<T>::bare_instantiate`/`bare_call` in a `substrate/frame`-style test harness mirroring `substrate/frame/assets/precompiles/src/tests.rs`'s `bare_call` pattern [8](#0-7) ; (2) drive `ERC20Transactor::withdraw_asset_with_surplus` then `deposit_asset_with_surplus` directly (as the `xcm_executor::traits::TransactAsset` trait) with that contract's `H160` as asset id; (3) assert the checking account's real `balanceOf` after step (2) is less than the credited `Erc20Credit(amount)`, and that the deposit leg's second `transfer(amount)` reverts, per the `ERC20InsufficientBalance` guard in the reference `ERC20.sol._update` [7](#0-6) . ///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}
