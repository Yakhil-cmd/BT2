### Title
Cross-repository commit-status forgery via SHA-only lookup breaks the "organization authenticated" vs "repository written" binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook handler updates commit CI state by looking up commits purely by `sha`, with no verification that the `sha` actually belongs to the repository named (and authenticated) in the webhook payload. Because webhook signature verification is scoped only to the *organization* declared in the payload, and never re-validated against the repository the target `Commit` record actually belongs to, an attacker who can produce a validly-signed webhook for *any* Shipit-tracked organization/repository can inject a fabricated CI status for a commit belonging to a completely different, unrelated stack — as long as the SHA values collide (which happens routinely for forked/mirrored repositories sharing history).

### Finding Description
`WebhooksController#verify_signature` selects which organization's secret to validate the HMAC against using an attacker-controlled field from the JSON body itself: [1](#0-0) [2](#0-1) 

The signature check only proves that the request was signed with the webhook secret configured for *some organization named in the payload* — it says nothing about which `Commit`/`Stack`/`Repository` the event should be allowed to affect.

`Shipit::Webhooks::Handlers::StatusHandler#process` then updates **every** commit in the database matching the given `sha`, with no repository/stack scoping at all: [3](#0-2) 

Compare this to `PushHandler`, which correctly scopes to `stacks` derived from `repository.full_name`: [4](#0-3) [5](#0-4) 

`StatusHandler` never calls `stacks`/`repository_name` — it operates directly on `Commit.where(sha: params.sha)`, so the binding that should hold — *"the organization/repository authenticated by the signature" == "the repository whose commit gets written"* — is broken. The only fields covered by the HMAC are the raw JSON bytes; nothing in the application logic re-derives and compares the target commit's owning repository against the authenticated organization.

`Commit#create_status_from_github!` then feeds directly into deploy-safety logic: statuses determine `deployable?` and trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`: [6](#0-5) [7](#0-6) [8](#0-7) 

Since Git commit SHAs are content-addressed and preserved across forks/mirrors, two different repositories tracked by Shipit (or one tracked repository plus an attacker-created fork of it registered under the attacker's own GitHub org with its own configured webhook secret) can legitimately share identical commit SHAs for shared ancestor commits. An attacker who controls a repository whose organization is configured in Shipit (i.e., has a valid, signable webhook) can send a `status` event naming their own repository (satisfying signature verification) but carrying a `sha` that also exists in a victim stack's history, with `state: success` for a `context` matching a `required_status` check. This flips the `Status::Group` state for that commit in the *victim* stack, satisfying `deployable?` gating for that commit in the victim's continuous-delivery/merge pipeline.

### Impact Explanation
This breaks a repository-authorization boundary: a party authenticated only for repository/organization A is able to write CI-status state for a commit belonging to stack/repository B, influencing whether that commit is treated as `deployable?` and can trigger `schedule_merges`/continuous deployment in `Commit#add_status`/`#deployable?`. This can contribute to an unauthorized deploy of a shared/historical commit in a victim stack — matching the "unauthorized deploy" criterion.

### Likelihood Explanation
Exploitation requires: (1) the attacker controls (or has push access to) a repository/organization already configured in Shipit with a webhook secret they can compute a valid signature for, and (2) a target commit SHA that is shared between the attacker's repository and the victim stack's repository history (common for forks or repositories that share ancestor commits/mirrors). This is a realistic but not universal scenario — it does not work against arbitrary, unrelated, never-forked commits, since SHA1 collision on attacker-chosen content is infeasible. Likelihood is therefore moderate: it requires a specific but plausible repository relationship (fork/mirror sharing history) between attacker-controlled and victim repositories, both onboarded to the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` (and any other sha-only lookups) to commits belonging to stacks derived from `repository_name`/`repository.full_name` in the payload, analogous to `PushHandler`'s use of `stacks`, e.g. `Commit.where(sha: params.sha).where(stack_id: stacks.flat_map(&:id))` or by joining through `Stack -> Repository` and filtering on the authenticated repository's owner/name, so a status update can never cross repository boundaries regardless of SHA collisions.

### Proof of Concept
1. Attacker controls repository `attacker/fork` (a fork of victim `victim/app`), configured in Shipit under an organization `attacker-org` with its own valid `webhook_secret`.
2. `attacker/fork` and `victim/app` share ancestor commit `abc123...` (identical SHA due to fork history).
3. Attacker computes a valid `X-Hub-Signature` HMAC using `attacker-org`'s webhook secret over a crafted JSON body:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker/fork" }
}
```
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (it is legitimately signed by that org's secret).
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, which matches the commit record belonging to `victim/app`'s stack, and calls `commit.create_status_from_github!`, setting that commit's status to `success` for `victim/app`'s stack — despite the attacker never having any credential, permission, or webhook binding for `victim/app`.
