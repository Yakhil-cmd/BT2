## Title
ECDSA Signature Malleability in secp256k1 PEM Verification Enables Bypass of AA Signature-Reuse Protection - (File: signature.js)

## Summary
`signature.js`'s `verifyMessageWithSecp256k1PemPubKey()`, which backs the oscript `is_valid_sig()` function reachable from any AA trigger, explicitly normalizes the ECDSA signature (forces low-`s`) before verification. This means that for one secp256k1 key/message pair, two distinct byte-string signatures — the original `(r, s)` and its mathematically-equivalent malleable twin `(r, n-s)` re-encoded in DER — both verify successfully. Any AA that implements signature-reuse/replay protection by treating the raw signature bytes themselves as the "used" key (a natural pattern in oscript, since `r`/`s` cannot easily be extracted) can be bypassed by an attacker who re-serializes a previously-consumed signature into its malleable-but-still-valid alternate form.

The call `ecdsa.signatureNormalize(rawCompact)` explicitly forces the signature into canonical low-`s` form *before* calling `ecdsaVerify`. This is exactly the class of bug flagged in the external report: the verification path accepts more than one *byte encoding* of what is cryptographically "the same" signature. Given any valid signature `(r, s)`, `(r, n-s mod n)` is also a mathematically valid ECDSA signature for the same message and public key; DER-encoding both produces two different byte strings that this function will both accept, because it normalizes prior to the actual verify call.

This is reachable by any unprivileged AA trigger sender through the oscript formula `is_valid_sig(message, pem_key, signature)`: [3](#0-2)

By contrast, the address-definition `['sig', {...}]` authentifier path and device-login path call `ecdsaSig.verify()` directly with a raw 64-byte compact signature and no normalization step: [5](#0-4) [6](#0-5) 
There, the underlying `secp256k1` library's `ecdsaVerify` rejects non-canonical (high-`s`) signatures outright, so only one byte-encoding of the signature is ever valid — this path is not malleable. The malleability is isolated to the PEM/`is_valid_sig` secp256k1 code path introduced for AA formula evaluation.

Because AA authors commonly use signed off-chain messages (vouchers, oracle attestations, payment-channel counter-signatures, etc.) and must implement their own anti-replay logic in oscript state vars (there is no unit-level nonce concept for arbitrary `is_valid_sig` payloads), a frequent and natural implementation is to key the "already used" state var off the signature string itself, e.g. `var['used_' || signature]`. This is precisely the vulnerable pattern called out in the external report ("marking the signature itself as used, rather than the signed message or a nonce included in it").

## Impact Explanation
An attacker who has already used one encoding of a valid secp256k1 signature can re-derive and resubmit the malleable twin encoding to any AA that checks/stores raw signature bytes for reuse protection, bypassing that protection. Depending on what the guarded action releases (funds, vouchers, state transitions), this enables double-execution of AA logic intended to run only once per signature — i.e. concrete AA fund loss/double-spend of AA-held funds. The severity depends on the specific AA's use of `is_valid_sig`, but the underlying primitive (verification accepting two distinct byte-encodings of one logical signature) is a real, exploitable defect in the shared library that every such AA relies on.

## Likelihood Explanation
Likelihood is Medium: exploitation requires (a) an AA using `is_valid_sig()` with a secp256k1 PEM key and (b) that AA implementing reuse-protection keyed on raw signature bytes rather than on the signed message content/nonce — a plausible but not universal pattern. No special privilege is needed by the attacker: computing the malleable twin `(n-s)` and re-encoding as DER is trivial arithmetic, and the trigger can be posted by any wallet.

## Recommendation
In `verifyMessageWithSecp256k1PemPubKey` (and more generally in `verifyMessageWithPemPubKey`), reject non-canonical signatures instead of silently normalizing them: check that the imported signature's `s` value is already ≤ n/2 (i.e., compare `rawCompact` against `ecdsa.signatureNormalize(rawCompact)` and reject if they differ) before calling `ecdsaVerify`, mirroring the strict behavior already enforced by the plain `ecdsaSig.verify()` path used for unit authentifiers.

## Proof of Concept
1. AA defines: `if (var['used_' || trigger.data.signature]) bounce('replay'); var['used_' || trigger.data.signature] = true;` followed by `is_valid_sig(trigger.data.message, PEM_KEY, trigger.data.signature)` gating a fund release.
2. Signer produces a valid secp256k1 DER signature `sig1 = DER(r, s)` over `message`; attacker submits trigger #1 with `signature = sig1`; AA marks `used_sig1 = true` and releases funds.
3. Attacker computes `s' = n - s mod n` and re-encodes `sig2 = DER(r, s')` — a different byte string.
4. Attacker submits trigger #2 with `signature = sig2`. `var['used_' || sig2]` is unset (different key), so the reuse guard passes. `is_valid_sig(message, PEM_KEY, sig2)` still returns `true` because `verifyMessageWithSecp256k1PemPubKey` normalizes `sig2` to the same canonical form as `sig1` before calling `ecdsaVerify`.
5. The AA releases funds a second time for the same underlying signed message/authorization.

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
```
