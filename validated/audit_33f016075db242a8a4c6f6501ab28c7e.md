Based on my investigation, I found a genuine issue, though it differs from what the question describes — the actual root cause isn't a partial/unconfigured worktree, but rather that the pre-publish hook doesn't actually gate the publish in the way the docs imply.

### Title
Pre-publish hook is fire-and-forget and does not gate `publishSymlink`, allowing publish to proceed before hook completion or on hook failure - (File: main.go, pkg/hook/hook.go)

### Summary
`syncHooks.beforePublish` (main.go) enqueues the hash to the pre-publish `HookRunner` via a non-blocking `Send` and unconditionally returns `nil`, regardless of whether the hook actually ran or succeeded. `SyncRepo` then immediately calls `git.publishSymlink(newWorktree)`, so the symlink flip is not actually blocked on the hook's completion or success/failure result.

### Finding Description
In `main.go`, `syncHooks.beforePublish` is defined as: [1](#0-0) 
It calls `prePubExechookRunner.Send(hash)`, which is a non-blocking channel write [2](#0-1) , and then hardcodes `return nil` regardless of whether the hook has even started executing, let alone completed. The consuming goroutine, `HookRunner.Run`, only picks up the hash asynchronously from a separate goroutine's event loop and calls `hook.Do(ctx, hash)` there [3](#0-2) .

In `SyncRepo`, the code treats `beforePublish`'s return value as if it reflects the hook's outcome: [4](#0-3) 
Because `beforePublish` always returns `nil` immediately after enqueueing, `git.publishSymlink(newWorktree)` executes right after, without waiting for the actual `Exechook.Do` call in the separate goroutine to run or finish. The only mechanism that reflects the hook's actual result is `HookRunner.WaitForCompletion`, gated by `oneTimeResult`, but that is invoked as a separate, later step (near program exit in one-time mode), by which point `publishSymlink` has already atomically flipped the link to the new worktree.

This means the comment above the call — "If the previous run crashed before publishing the link, then we must call the pre-publish hook... The post-publish hooks are called in both cases" — describes an intent to gate publishing on the pre-publish hook, but the implementation does not actually block on hook success. In `--one-time` mode, `WaitForCompletion`'s result only affects the process's final exit status; it does not prevent the symlink from already pointing at the new (potentially hook-rejected) worktree by the time the process exits with failure.

Regarding the specific "partial worktree" framing in the question: `configureWorktree` completes fully before `beforePublish`/`Send` is invoked [5](#0-4) , so the hook (once it runs) does operate on a fully-configured worktree at the correct hash — that specific race is not present. The actual defect is the non-blocking gate, not tree partiality.

### Impact Explanation
An attacker who controls repo content that the pre-publish hook is meant to validate (e.g., a scanning/policy hook) can have their content published to the symlink even though the hook subsequently fails, because publishing is not actually conditioned on the hook's real completion/result — only the final process exit code is. This is "unverified content published despite a gating hook," matching the described impact class, but the mechanism is a synchronization/blocking defect in `beforePublish`, not a partial-tree race.

### Likelihood Explanation
This triggers on every sync where `--pre-publish-exechook-command` is configured (a documented, standard flag) and a new hash is fetched; it requires no non-default or unusual flags beyond the existing pre-publish hook feature, and is deterministic rather than timing-dependent, since `Send` always returns immediately without waiting on the runner goroutine.

### Recommendation
Make `beforePublish` synchronous with respect to the hook's actual outcome for the specific hash being published — e.g., have it invoke the hook directly (or wait on a per-invocation completion channel) and propagate a real error before `publishSymlink` runs, rather than only recording success/failure for later exit-code reporting via `oneTimeResult`.

func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}
}
