### Title
`remote_proxy` extrinsic weight is not scaled to attacker-supplied `proof` size, allowing under-charged trie-traversal DoS - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`Pallet::do_remote_proxy` calls `sp_trie::read_trie_value` over an attacker-supplied `proof: Vec<Vec<u8>>` of arbitrary (bounded only by extrinsic length limits) size and node count, but the declared `#[pallet::weight]` for `remote_proxy` charges a fixed benchmarked constant (`WeightInfoOf::<T,I>::remote_proxy()`) plus only the inner call's weight — it does not add any component that scales with `proof` size. This allows an attacker to submit maximally large, invalid proofs that cause disproportionate trie-traversal/hashing cost relative to the weight charged.

### Finding Description
The `remote_proxy` extrinsic's weight annotation is: [1](#0-0) 
which only includes `WeightInfoOf::<T,I>::remote_proxy()` (a fixed constant from the benchmark), a DB read/write weight, and the inner call's `call_weight` — no term dependent on `proof.len()` or the number/size of trie nodes supplied.

Inside `do_remote_proxy`, the proof is converted into an in-memory trie DB and passed to `sp_trie::read_trie_value`, which will traverse/hash all supplied nodes attempting to resolve the path before it can conclude the proof is invalid: [2](#0-1) 

The benchmark that produced the constant weight (`pallets/remote-proxy/src/benchmarking.rs`) always constructs a single, minimal, *valid* proof via `T::RemoteProxy::create_remote_proxy_proof`, with no parameterization over proof size/depth/width: [3](#0-2) 

The resulting generated weight in production, e.g. for asset-hub-kusama, is a small fixed constant with `Estimated: 1846` bytes of PoV and ~18.2M picoseconds of ref-time — clearly measured against a tiny realistic proof, not a maximal/adversarial one: [4](#0-3) 

No other check in the pallet limits proof size/shape before the trie call — the only preceding check is a binary search in `BlockToRoot` for the claimed `block`, which is trivially satisfied by using any historically valid block number that's still retained by `MaxStorageRootsToKeep`: [5](#0-4) 

The only bound on the total size of `proof` is the runtime's generic extrinsic length limit (`BlockLength`/`max_extrinsic_size`), which is unrelated to and much larger than what is priced into the fixed weight. Thus an attacker can submit an extrinsic near that length limit filled with junk `Vec<Vec<u8>>` entries; `sp_trie::read_trie_value` will attempt to traverse them (following/hashing nodes) before ultimately failing to resolve the key and returning `Ok(None)`/`Err`, translated to `InvalidProof`, but only after doing traversal work proportional to the attacker-controlled proof size — while only the small fixed constant weight is deducted from the block's weight budget.

### Impact Explanation
Since actual per-call execution time can scale with attacker-controlled proof size while charged weight stays roughly constant, an attacker can submit repeated `remote_proxy` calls with maximal bogus proofs in a block, consuming more wall-clock/ref-time than what is accounted for in the block's declared weight limit. This can crowd out honest extrinsics in the same block and — if severe/repeated enough across blocks — degrade block production timing (soft DoS on block execution time), which matches the scoped "block-level DoS / stuck extrinsic queue" impact category. Note this is a *resource-accounting* issue, not an asset-theft or origin-forgery issue — no funds are stolen or proxies forged, since `InvalidProof`/`DidNotFindMatchingProxyDefinition` still ultimately reject the fabricated proxy definition.

### Likelihood Explanation
Preconditions are trivial for any signed account: submit a `remote_proxy(real, force_proxy_type, call, proof)` extrinsic where `block` matches any entry currently in `BlockToRoot` (a public/derivable value, since it mirrors relay-chain state, and typically only requires the block number of a recent relay block, not any specific storage knowledge) and `proof` is filled with large/junk byte vectors up to the extrinsic size limit. This is repeatable every block by any signed account with enough balance to pay transaction fees (fees are charged per weight, and if weight under-charges true cost, fees also under-charge). The only cost to the attacker is transaction fees computed from the (under-priced) weight, making the attack economically favorable relative to the resource cost imposed.

### Recommendation
Add a weight component to `remote_proxy`/`remote_proxy_with_registered_proof` that scales with `proof` size (e.g., total encoded length of `Vec<Vec<u8>>`, or a `WeightInfo::remote_proxy_proof_size(proof_len)` linear/quadratic component derived from a size-parameterized benchmark), and/or enforce an explicit, tightly-bounded `MaxProofSize`/`MaxProofNodeCount` on `RemoteProxyProof::RelayChain { proof, .. }` decoding (rejecting oversized proofs pre-dispatch, ideally as a `SignedExtension`/`TransactionExtension` check before the full weight is spent) so PoV/time cost is proportionate to charged weight in the worst case.

### Proof of Concept
Benchmark-based invariant test:
1. In `pallets/remote-proxy/src/benchmarking.rs`, add a new benchmark variant `remote_proxy_worst_case` parameterized by a component `p` (number of proof nodes) or `s` (bytes per node), constructing a `proof: Vec<Vec<u8>>` of maximal size within `BlockLength`/`MaxEncodedLen` bounds, filled with structurally-valid-looking but semantically bogus trie node bytes (or reuse a real large trie's unrelated nodes) targeting a valid `block` in `BlockToRoot`, and assert the call returns `Err(Error::InvalidProof)`.
2. Measure actual weight/time consumed by this call using `frame_benchmarking`'s built-in timing and compare it against `WeightInfoOf::<T,I>::remote_proxy()` (the currently charged constant weight): assert `measured_ref_time > charged_ref_time * tolerance` and/or `measured_proof_size > charged_proof_size * tolerance` to demonstrate under-charging.
3. As a runtime integration test, submit N such `remote_proxy` extrinsics with maximal `proof` payloads in a single block via `frame_system::Pallet::note_extrinsic`/executive block-building test harness, and assert total actual execution time exceeds the block's declared `Weight::MAX`/`max_block` budget computed from summed charged weights — demonstrating a discrepancy between accounted and real cost.
