### Title
Unvalidated swap-route addresses can invoke attacker-controlled contracts that add wallet-draining token transfers to the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept `swap` as opaque `Bytes`, forward it to the configured router, and do not validate the contract addresses encoded inside the route. [1](#0-0) [2](#0-1)  A route can therefore place attacker-controlled code below the caller’s authorization and make it request an unrelated token transfer from that caller. [3](#0-2) 

### Finding Description
`StrategySwap` is only an encoded byte blob, so the controller performs no destination, venue, or hop-address validation before passing it to `router.execute_strategy`. [1](#0-0) [2](#0-1)  `swap_collateral` accepts that caller-supplied route after checking authorization and account ownership, then reaches the router through `withdraw_and_swap_from_supply`. [4](#0-3)  The controller only authorizes the exact router input transfer and checks input/output balance deltas; it does not constrain which addresses the route causes the router to invoke. [5](#0-4)  XOXNO’s threat model confirms that payload-named pool and token addresses are not allowlisted and can put third-party code beneath the caller’s authorization. [6](#0-5) 

The strongest reachable path is `swap_collateral(caller, account_id, current, from_amount, new, swap)`, with `swap` containing a route whose hop contract is attacker-controlled; the same opaque-route sink is also reachable from `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
A malicious route can execute a contract that calls `token.transfer(victim, attacker, amount)` for a wallet token unrelated to the lending position. [10](#0-9)  Simulation records that transfer as a child of the victim’s `swap_collateral` authorization, and enforcement executes it if the victim signs the returned tree. [11](#0-10)  The included test demonstrates complete loss of an unlisted wallet-token balance while the malicious route still returns fair swap output and preserves the expected collateral deposit. [12](#0-11) 

### Likelihood Explanation
The issue requires a user to submit or sign a poisoned route and its expanded authorization tree; an attacker cannot directly force the extra transfer without that signature. [13](#0-12)  It is nevertheless practical where routes are produced off-chain or by an untrusted service, because a client that trusts simulation output without rejecting unexpected child authorizations will expose wallet balances beyond the swap input. [14](#0-13) 

### Recommendation
Validate route destinations before execution instead of treating `swap` as opaque controller input. [15](#0-14)  Restrict route-called contracts to governance-registered venue implementations or pools derived from a trusted venue registry, and reject routes that can introduce additional caller-authorization children beyond the documented input transfer. [16](#0-15)  Until contract-level validation exists, clients must decode every route and refuse any simulated authorization tree containing anything other than the expected swap input transfer. [17](#0-16) 

### Proof of Concept
The repository’s `rogue_hop_pool_transfer_joins_caller_auth_tree` test supplies `swap_collateral` with a route naming `RogueHopPool`; the pool’s `swap` function transfers Alice’s unrelated wallet token to the attacker. [18](#0-17) [19](#0-18)  In recording mode, the unauthorized wallet transfer appears under Alice’s controller authorization, Alice’s balance becomes zero, and the attacker receives the full balance. [20](#0-19)  In enforcing mode, the same route fails when Alice signs only the honest root invocation but succeeds once the simulated child transfer is included in the signed tree. [13](#0-12)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
