## Analysis

The Code4rena finding (H-12) concerns a permissionless swap/rebalance function (`distributeMochi`) that computes an output amount from a manipulable on-chain price with no minimum-return / slippage check, letting anyone sandwich it with front-run/back-run trades.

Ocore's Autonomous Agent (AA) layer has a directly analogous class of contracts, exemplified in the project's own reference pattern for building an on-chain AMM/exchange, `test/samples/uniswap_like_market_maker.oscript`. The "exchange bytes to asset" and "exchange asset to bytes" branches compute the swap output purely from the AA's current `balance[...]` and the constant-product formula, with **no slippage/minimum-output parameter at all**: [1](#0-0) 

Contrast this with the "invest" branch a few lines above, which does check an expected ratio and bounces on mismatch — showing the exchange branches were deliberately left unprotected (documented as "we can deduct exchange fees here", not slippage bounds). Similarly, `sell_asset_for_bytes.oscript` and the order-book sample compute swap amounts straight from mutable state/rate with no caller-supplied minimum.

The reason this is exploitable specifically in Obyte's model (not just "bad contract code") is that AA-trigger execution order is **fully deterministic and externally predictable/steerable** rather than protected by transaction atomicity or private mempools. Multiple trigger units addressed to the same AA that become stable within the same MCI are queued and executed in a fixed order: [2](#0-1) [3](#0-2) 

Ordering key is `(mci, level, unit, address)` — i.e., primarily by DAG `level`. Since any unprivileged unit poster freely chooses their unit's parents (and thus its `level`, which is `max(parent levels)+1`), an attacker who observes a victim's not-yet-stable swap-trigger unit can:
1. author a "front-run" trigger unit built on parents that keep its `level` below the victim's, swapping into the AA first, and
2. author a "back-run" trigger unit that includes the victim's unit (or a descendant) as a parent, giving it a higher `level`, swapping back out after,
so that once the batch stabilizes together, the deterministic ordering guarantees front-run → victim → back-run execution — a classic sandwich, with no flashbots/private-mempool protection needed because ocore has no notion of transaction-order auction or MEV protection at all.

Because the swap formula uses only `balance[asset]` at execution time and `trigger.output[[...]]` of the currently-processed unit (nothing tied to a prior, harder-to-move average price), the front-run trade shifts the AMM's price before the victim's swap executes, and the back-run trade extracts the resulting slippage — exactly the fund-loss mechanism described in the H-12 report, but reachable purely by an unprivileged AA trigger sender against a standard/permissionless Obyte AMM-style AA, using only DAG-parent selection, with no oracle/hub compromise required.

### Title
Sandwich attack on permissionless AMM-style Autonomous Agents due to deterministic, attacker-influenceable trigger ordering and missing slippage checks - (File: `aa_composer.js`, `main_chain.js`, `test/samples/uniswap_like_market_maker.oscript`)

### Summary
Ocore executes AA triggers that stabilize within the same MCI in a fully deterministic order keyed by `(mci, level, unit, address)`. Because any unprivileged unit author controls their own unit's `level` via parent selection, an attacker can arrange a front-run trigger unit to execute immediately before, and a back-run trigger unit to execute immediately after, a victim's swap trigger against a permissionless exchange-style AA (the pattern documented in `uniswap_like_market_maker.oscript`) that computes output purely from current `balance[...]` with no minimum-return/slippage parameter, enabling classic sandwich extraction of victim funds.

### Finding Description
- The reference "exchange bytes to asset" / "exchange asset to bytes" cases compute swap output solely from live AA balances and the trigger's own output, with no caller-specified minimum acceptable amount: [4](#0-3) 
- AA trigger execution order for units stabilizing in the same MCI is deterministic and computed from `level`, `unit`, `address`: [2](#0-1)  and re-confirmed at dequeue time: [5](#0-4) 
- `level` is derived from the unit's chosen parents, which any unprivileged poster controls, letting an attacker position their trigger unit's `level` immediately below or above a known victim unit before stabilization completes.
- Unlike EVM sandwich mitigations that rely on private mempools/flashbots, Obyte has no mechanism preventing an attacker from observing an unstable victim trigger and crafting bracketing units, since the DAG and pending units are public before stabilization.

### Impact Explanation
Any permissionless AMM/exchange-pattern AA — a design pattern ocore itself documents and encourages via `uniswap_like_market_maker.oscript` and `sell_asset_for_bytes.oscript` — can have its liquidity pool drained via sandwich attacks: the attacker profits by trading against the artificially-moved price, and the victim/pool absorbs the loss. This is a direct fund-loss vulnerability of the same class and severity as the referenced H-12 (High).

### Likelihood Explanation
Any user can post an AA trigger unit and choose parents to control DAG `level`; no operator/hub/witness privilege is required. The attack requires only observing a pending (unstable) victim trigger and composing two additional units before the batch stabilizes — well within reach of an unprivileged actor using standard node/wallet tooling, especially for high-value swaps against low-liquidity AAs.

### Recommendation
- Provide/require a documented convention (and encourage core `oscript` validators/checks) for slippage protection in exchange-style AAs, e.g., requiring callers to supply `min_amount`/`max_slippage` fields validated against the computed swap output, and bouncing otherwise.
- Consider making AA execution order for batched triggers depend on something less attacker-steerable than raw `level`/`unit` (e.g., commit-reveal or randomized tie-breaking across independent trigger chains within an MCI), or provide primitives (like a TWAP-style rolling price stored in AA state, updated across separate MCIs) that AA authors can reference instead of instantaneous `balance[...]`.
- Update the shipped reference AMM sample (`uniswap_like_market_maker.oscript`) to include slippage checks so it is not copied insecurely into production AAs.

### Proof of Concept
1. AA `X` implements the swap formula shown in `uniswap_like_market_maker.oscript` lines 102–145 (constant-product, no min-output check).
2. Victim posts unit `V` with a payment output to `X` swapping `base` for `asset`.
3. Before `V`'s MCI stabilizes, attacker crafts unit `F` (front-run swap of `asset`→`base` or `base`→`asset`, whichever worsens price for `V`) choosing parents so `level(F) < level(V)`.
4. Attacker crafts unit `B` (reverse swap) using `V` (or a descendant) as a parent so `level(B) > level(V)`.
5. When the MCI containing `F`, `V`, `B` stabilizes, `handleAATriggers`/`markMcIndexStable` order execution as `F → V → B` per the `ORDER BY ... level, unit, address` clause: [6](#0-5) .
6. `X`'s balance-dependent formula gives `V` a worse rate than expected, and `B` reverses the attacker's position at the now-favorable price, extracting the difference from `V`/the pool.
