### Title
Cross-Organization Webhook Forgery via Optional `webhook_secret` and Mismatched Owner-vs-Repository Trust Binding - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate a request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). The actual work performed by event handlers (e.g. `PushHandler`) is instead keyed off `payload.dig('repository', 'full_name')`. These two fields are never required to agree, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured. This breaks the binding "organization that authenticated == repository that is written": an attacker who can get a request accepted under an org with no configured secret can point `repository.full_name` at a completely different, tracked repository/stack and trigger real state changes (e.g. `GithubSyncJob`) on it.

### Finding Description
- `WebhooksController#verify_signature` resolves the signing app via `repository_owner`: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` short-circuits to `true` when the resolved org has no secret configured: [3](#0-2) 

- Once verification passes, the entire raw JSON `params` (not scoped to the verified organization) is dispatched to handlers: [4](#0-3) 

- Handlers determine which `Repository`/`Stack` to act on purely from `payload.dig('repository', 'full_name')`, a field that was never checked against `repository_owner`: [5](#0-4) [6](#0-5) 

Because `verify_signature` computes the trust decision from `repository.owner.login`/`organization.login`, while `PushHandler` (and other handlers) act on `repository.full_name`, the "authenticated identity" and "acted-upon resource" are two independently attacker-influenced fields in the same JSON body. If Shipit has *any* configured GitHub organization without a `webhook_secret` (the documented default/dev configuration explicitly ships with `webhook_secret: # nil`, and multi-org deployments can have inconsistent secret configuration across `Shipit.github` entries), an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to that secret-less org, so `verify_webhook_signature` trivially returns `true` regardless of the `X-Hub-Signature` header content.
2. Set `repository.full_name` to `owner/repo` of any *other*, secret-protected repository/stack already tracked by the Shipit instance.
3. Set the event type (e.g. `push`) and required handler params (`ref`, `after`).

`PushHandler#process` will then locate the real stacks for that spoofed `repository.full_name` via `Repository.from_github_repo_name` and invoke `stack.sync_github(expected_head_sha: params.after)` on them — an action that is supposed to only be reachable by a signed, authentic webhook from GitHub for that exact repository.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary explicitly called out as in-scope: the org whose credential (webhook secret, or lack thereof) is checked is not the org/repo the mutating action is actually performed against. Consequences include unauthorized `GithubSyncJob` triggering with an attacker-chosen `expected_head_sha` (an unauthorized sync/deploy-adjacent state change) against arbitrary stacks tracked by the instance, and this pattern extends to other handlers (`status`, `check_suite`, `pull_request`, `membership`) which use the same unauthenticated `repository.full_name` / actor fields once the outer signature gate is bypassed by picking a secret-less organization. This matches the "unauthorized deploy/rollback" class of impact once an attacker can drive commit/branch state used by deploy triggers.

### Likelihood Explanation
Exploitability depends entirely on the operator's configuration: it requires at least one configured `Shipit.github` organization entry with no `webhook_secret` set. This is a realistic and even documented condition — the shipped example secrets files (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets.yml`) show `webhook_secret: # nil` as a valid/expected value, and multi-tenant instances supporting several GitHub orgs may reasonably have inconsistent secret rollout across orgs. Given that condition, the attack requires no authentication, no repository access, and no token — a single unauthenticated POST to `/webhooks` is sufficient, making likelihood high once the precondition holds.

### Recommendation
Bind the authentication decision to the same resource the handler will act on: verify the webhook signature using the secret associated with the repository/org encoded in `repository.full_name` (not a separately-derived `repository.owner.login`/`organization.login`), and reject requests where these fields are inconsistent. Additionally, do not treat a missing `webhook_secret` as an implicit "allow all" — either require a `webhook_secret` for every configured organization or reject requests when no secret is configured rather than silently returning `true` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Assume Shipit is configured with two orgs: `unsecured-org` (no `webhook_secret`) and `victim-org` (has a stack tracking `victim-org/app`, protected by a `webhook_secret`).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-in-victim-org/app>",
  "repository": {
    "full_name": "victim-org/app",
    "owner": { "login": "unsecured-org" }
  }
}
```

- `repository_owner` resolves to `"unsecured-org"` [2](#0-1) .
- `Shipit.github(organization: "unsecured-org")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally [7](#0-6) , and `head(422)` is never called.
- `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs, and `PushHandler` resolves the target stacks from `payload.dig('repository', 'full_name')` = `"victim-org/app"` [8](#0-7) , triggering `stack.sync_github(expected_head_sha: params.after)` on the victim's tracked stack [9](#0-8)  — despite the request never being authenticated against `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
