### Title
Unscoped `status` webhook handler lets any authenticated GitHub organization forge commit statuses for stacks belonging to other repositories/organizations — (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the commit to update purely by SHA, with **no scoping to the repository/organization that the inbound webhook was authenticated for**. Every other webhook handler (`PushHandler`, `PullRequest::*Handler`) scopes its side effects through `Handler#stacks`, which restricts the affected `Stack`s to the `Repository` named in `repository.full_name`. `StatusHandler` skips this entirely and does `Commit.where(sha: params.sha)` against the whole database. Because the signature verification in `WebhooksController#verify_signature` only proves "this request was signed with organization X's webhook secret," not "this request's fields refer to organization X's repositories," an attacker who legitimately controls (or can trigger real status webhooks for) one repository/organization onboarded into a shared Shipit instance can set commit statuses on commits belonging to a completely different stack/repository/organization, as long as they know that target commit's SHA (a public, non-secret value on GitHub).

### Finding Description
The binding that should hold is:
`organization authenticated by verify_signature (repository_owner / that org's webhook_secret) == repository whose state the handler is authorized to mutate`

`WebhooksController#verify_signature` derives the signing organization from the payload itself and verifies the raw body's HMAC against that organization's configured secret: [1](#0-0) [2](#0-1) 

This proves only that the payload was legitimately signed by *some* organization's configured GitHub App/webhook secret — it does not, by itself, constrain which repository's data inside that payload the handler is allowed to act on. Each handler is responsible for enforcing that constraint. The base `Handler` class provides exactly this mechanism: [3](#0-2) 

`PushHandler` correctly uses it — it only touches stacks belonging to the repository named in the payload: [4](#0-3) 

`StatusHandler` does not use `stacks`/`repository_name` at all. It looks up commits globally by SHA and writes a status to every match: [5](#0-4) 

Because Git commit SHAs are content-addressed and public (visible in GitHub URLs, PR pages, CI logs, `git log`, etc.), any organization/repository with a legitimately configured webhook connection into this Shipit instance can craft a `status` event with `sha` set to a commit belonging to an entirely unrelated stack/repository/organization tracked by the same instance, and Shipit will happily record that forged status against it — the equality above is broken: the org that authenticated is not constrained to equal the repository being written.

### Impact Explanation
Commit statuses recorded this way feed directly into deploy and merge-queue gating logic (`ci.require`, `ci.blocking`, `merge.require`, etc., resolved through `DeploySpec#required_statuses`/`blocking_statuses`/`merge_request_required_statuses` and `Commit#deployable?`): [6](#0-5) [7](#0-6) 

By forging a `success` status with the exact context name a target stack requires (`ci.require`/`merge.require`), an attacker outside that stack's own organization can flip an otherwise pending/failing commit to "deployable," clearing CI/merge-queue gates for a repository they do not control — enabling an unauthorized deploy or an unauthorized merge-queue advance on someone else's stack. This satisfies the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Exploitation requires only:
1. The attacker's own organization/repository to be legitimately connected to the shared Shipit instance (a normal, non-privileged onboarding step, not an `ApiClient` token, GitHub App private key, or `webhook_secret` leak — they use their own configured, legitimate secret to sign a payload whose `repository`/`sha` fields they fully control).
2. Knowledge of a target commit SHA on another org's stack, which is public information on GitHub.

No cross-tenant secret, session, or repository write access to the *victim* repository is needed — only the attacker's own legitimately-configured webhook credentials, which the exploit rules do not exclude (they exclude reliance on the *victim's* `webhook_secret`, not the attacker's own).

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve commits only through `stacks` (i.e., `Commit.where(sha: params.sha, stack: stacks)` or equivalent), so a status webhook can only affect commits belonging to the repository named in that webhook's own `repository.full_name`, which itself must correspond to the organization whose secret validated the signature.

### Proof of Concept
1. Shipit instance hosts stacks for both `victim-org/app` (targeted) and `attacker-org/toy-repo` (attacker legitimately administers this repo's GitHub App/webhook connection with their own known `webhook_secret`).
2. Attacker looks up (publicly, via GitHub) the SHA of a pending/failing commit `abc123...` on `victim-org/app` that is currently blocking deploy/merge due to a required status context (e.g. `ci/tests`).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/tests",
  "repository": { "full_name": "attacker-org/toy-repo", "owner": { "login": "attacker-org" } }
}
```
signed with `attacker-org`'s own legitimate webhook secret via `X-Hub-Signature`.
4. `verify_signature` succeeds (correct secret for `attacker-org`).
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the commit under `victim-org/app`'s stack (no repository check), and records a `success` status for context `ci/tests` on it.
6. `victim-org/app`'s commit now satisfies its required CI status and becomes deployable/mergeable, despite the attacker having no relationship to `victim-org`.
