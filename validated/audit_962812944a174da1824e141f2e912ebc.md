### Title
Webhook signature verified against one organization while payload writes to a different repository's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using `repository_owner`, a value read from the same untrusted JSON body it is about to verify. The handlers that actually act on the payload (e.g. `PushHandler`, `StatusHandler`) select the target `Stack`/`Repository` using a *different* field from that same body, `repository.full_name`. Nothing binds these two fields together, so a signature computed with organization A's webhook secret can be replayed with a body whose `repository.full_name` points at organization B's repository, letting the signature-holder for A drive writes (deploy syncs, commit statuses) against B's stacks.

### Finding Description
`verify_signature` computes the org used for signature verification from the request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` is used to look up which configured GitHub App/`webhook_secret` should validate `X-Hub-Signature` for the raw body: [3](#0-2) 

Once the signature is accepted, the raw JSON is dispatched unchanged to event handlers: [4](#0-3) 

But the base `Handler` class resolves which stacks/repository to mutate using a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack for that (attacker-supplied) `repository.full_name`: [6](#0-5) 

Because `Shipit` is explicitly designed to host multiple organizations, each with its own GitHub App and its own `webhook_secret` (see `config/secrets.development.shopify.yml`'s `somegithuborg`/`someothergithuborg` structure): [7](#0-6) 

the equality the engine implicitly (and incorrectly) assumes is:
`organization whose secret signed the delivery == organization owning the repository the handler acts on`

That equality is never enforced. `repository.owner.login` (verification input) and `repository.full_name` (action input) are two independent, attacker-controlled fields inside the same signed JSON body, and the controller/handler pipeline never cross-checks that the repository being written to actually belongs to the organization whose secret validated the signature.

### Impact Explanation
An entity that legitimately holds (or has compromised) the webhook secret for *one* onboarded organization/GitHub App instance (org A) can forge a webhook whose `repository.owner.login`/`organization.login` is set to "A" (so the correct, known secret validates it) but whose `repository.full_name` is set to `"B/some-repo"`. This lets them:
- Trigger `GithubSyncJob`/`stack.sync_github` for stacks under organization B, forcing a fetch/sync to an attacker-chosen `expected_head_sha`, which is used elsewhere to gate/trigger deploys — an unauthorized cross-repository/cross-organization action.
- Inject fabricated commit statuses (`StatusHandler`) or pull_request/membership state for repositories in an org the attacker's secret was never issued for.

This crosses an explicit trust boundary the rules call out ("an organization that authenticated versus the repository that is written") and can result in unauthorized cross-repository writes and, transitively, unauthorized deploys — matching the Critical impact bucket.

### Likelihood Explanation
Exploitation requires only knowledge of a valid `webhook_secret` for *any one* organization configured in the multi-tenant Shipit instance — not privileged access to the target organization/repository being attacked. Because Shipit is architected to host many orgs behind a single `/webhooks` endpoint with per-org secrets, and the verification/action fields are decoupled as shown, this is a straightforward payload-crafting exercise for anyone who already has legitimate/compromised access to one tenant's secret, with no additional session, token, or GitHub write access to the victim org required.

### Recommendation
After computing `repository_owner` for secret selection, re-validate that `repository.owner.login` used for action resolution (`repository_name` / `Repository.from_github_repo_name`) matches the same organization used for signature verification; reject the webhook if they diverge. Equivalently, bind the verified organization explicitly through the handler pipeline (pass it alongside `payload`) and have `Handler#stacks` scope lookups to repositories owned by that verified organization rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Configure Shipit (as in `config/secrets.development.shopify.yml`) with two orgs, `orgA` and `orgB`, each with distinct `webhook_secret`s and each hosting `Stack`s tied to their own repositories.
2. As a holder of `orgA`'s `webhook_secret` (legitimately provisioned for `orgA`), craft a push-event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `webhook_secret`, and the signature validates successfully (per `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves `repository_name` = `"orgB/victim-repo"` (per `app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `orgB`'s stack — an action never authorized by `orgB`'s own webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
