### Title
Forged `pull_request`/`unlabeled` webhook can archive/unarchive a review stack in a different org than the one whose secret verified the signature - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/repository.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a request using only `params.dig('repository', 'owner', 'login')` [1](#0-0) , while `Shipit::Webhooks::Handlers::PullRequest::UnlabeledHandler#repository` resolves the actual `Shipit::Repository` to mutate using the independent field `params.repository.full_name`, split on `/` [2](#0-1) [3](#0-2) . Nothing enforces that these two fields agree, so an attacker who controls a repository in an organization with no configured `webhook_secret` (or whose secret they can compute) can forge a payload naming that org in `repository.owner.login` while pointing `repository.full_name` at a victim org/repository, causing the handler to archive/unarchive (and potentially create/deprovision) that victim's review stack.

### Finding Description
The invariant that should hold is:
`repository_owner` (used to pick the org whose `webhook_secret` verifies the HMAC signature) == the owner of the `Repository` record the handler subsequently mutates.

Trace:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`) [4](#0-3) . `Shipit.github(organization:)` looks up per-org config and raises `GithubOrganizationUnknown` only if the org is entirely absent from configuration [5](#0-4) . If that org has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` short-circuits and returns `true` unconditionally: `return true unless webhook_secret` [6](#0-5) . So any known-but-secretless org name in `repository.owner.login` bypasses signature verification entirely.
2. After passing this check, `WebhooksController#create` dispatches the whole raw `params` hash — including the untouched `repository.full_name` — to every `pull_request` handler via `Shipit::Webhooks.for_event('pull_request')` [7](#0-6) [8](#0-7) .
3. `UnlabeledHandler#repository` resolves the mutated `Shipit::Repository` purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, which just splits on `/` and does a `find_by(owner:, name:)` — with no cross-check against `params.repository.owner.login` [2](#0-1) [3](#0-2) .
4. If `respond_to_label_change?` is satisfied (`action == "unlabeled"`, PR `state == "open"`, target repository has `review_stacks_enabled`, and archive/unarchive conditions computed from attacker-controlled `pull_request.labels`) the handler calls `stack.archive!` or `stack.unarchive!` on the victim repository's `ReviewStackAdapter`-resolved stack [9](#0-8) .

Exploit: attacker registers/controls a GitHub org `attacker-org` that is either (a) configured in Shipit with no `webhook_secret`, or (b) entirely unconfigured is rejected (raises `GithubOrganizationUnknown`) — so the attacker needs an org name that IS present in Shipit's `secrets.github` config but lacks a `webhook_secret` value. They send `POST /webhooks` with header `X-Github-Event: pull_request`, a `pull_request` JSON body where `action: "unlabeled"`, `repository.owner.login: "attacker-org"`, and `repository.full_name: "victim-org/victim-repo"` (a repo that exists in Shipit and has review stacks enabled), with labels crafted to satisfy `archive?`/`unarchive?`. Because `attacker-org` has no secret, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header, and the handler subsequently archives/unarchives `victim-org/victim-repo`'s review stack.

This is a real cross-tenant path: none of `verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema (which only requires `full_name` be a `String`, not that it match `owner.login`), or `Repository#owner`/`#name` format validators check consistency between `repository.owner.login` and `repository.full_name`.

Note: this specific exploitability path depends on Shipit's deployment configuration actually including an organization with a missing/blank `webhook_secret` in `secrets.github` (a config precondition, not a Shipit-code guarantee), since organizations absent from config raise `GithubOrganizationUnknown` and are rejected with 422. If every configured org in the deployment has a non-blank `webhook_secret`, this specific bypass path does not apply, though the underlying missing cross-check (owner vs. full_name) is still present in the code and would be exploitable the moment any org's secret is blank/misconfigured, or in the legacy single-org config mode where `github_default_organization` is `nil` and `repository_owner` is not even used to select the secret (`Shipit.github` ignores `organization:` entirely) [5](#0-4)  — in that legacy mode the same secret verifies for all orgs, and the handler still trusts `full_name` alone to pick the mutated repository, meaning any repo whose org shares the single configured secret (e.g., any public webhook payload signed with a leaked/short secret, or in multi-tenant single-secret setups) can target another repo's stack.

### Impact Explanation
An attacker can archive or unarchive review stacks (and, per the handler logic, drive creation/deprovisioning of review stacks) belonging to a repository/org they do not control and never authenticated a webhook signature for, purely by naming a different, secretless (or same-secret) org in `repository.owner.login`. This matches the Critical category "a payload for one repository mutating another's stack" — cross-tenant state manipulation without a valid `webhook_secret` for the target org. Blast radius is bounded to `pull_request`/`unlabeled` handler side effects (archive/unarchive review stacks, which per `handle` also affects `provision_status`), but is repeatable against any repository configured for review stacks in the Shipit instance, for as long as at least one org in the multi-org config has a blank `webhook_secret` (or the instance runs in legacy single-secret mode).

### Likelihood Explanation
Requires: (1) the target Shipit deployment to use multi-org GitHub App config (`github_default_organization` not nil) with at least one configured org lacking a `webhook_secret`, or to run in legacy single-org mode where the same secret validates all payloads regardless of `repository.owner.login`; (2) the attacker to know/guess a valid org name recognized by Shipit's config and the victim's `owner/name` full_name (both are typically public GitHub information, not secret); (3) review stacks enabled on the target repository. No GitHub, session, or API credentials are needed from the attacker. Given that org names and repo full names are public, and a misconfigured/incomplete `webhook_secret` for even one org in a multi-tenant Shipit instance is plausible, this is feasible and fully repeatable per request.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (or in each handler's `repository` resolution), enforce that the organization used to verify the signature (`repository_owner`) matches the owner embedded in `repository.full_name` before dispatching to handlers — reject the request (422) if they diverge. Additionally, require that every organization referenced in `Shipit` config have a non-blank `webhook_secret` (fail closed rather than `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`), and ensure `Repository.from_github_repo_name` cross-validates against the verified owner rather than trusting `full_name` alone.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
```ruby
test "forged pull_request unlabeled from secretless org mutates a different org's review stack" do
  victim_repo = shipit_repositories(:shipit) # owner/name != attacker-org
  configure_provisioning_behavior(repository: victim_repo, behavior: :allow_with_label, label: "pull-requests-label")
  stack = create_stack_for(victim_repo) # existing, non-archived review stack

  # simulate an org configured in Shipit but with a blank webhook_secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', {}) # no webhook_secret key => verify_webhook_signature always true
  )

  payload = payload_parsed(:pull_request_unlabeled)
  payload["repository"]["owner"]["login"] = "attacker-org"
  payload["repository"]["full_name"] = victim_repo.full_name
  payload["pull_request"]["labels"] = [] # no provisioning label => archive?

  @request.headers['X-Github-Event'] = 'pull_request'
  # no valid X-Hub-Signature needed because attacker-org has no secret
  post :create, body: payload.to_json, as: :json

  assert_response :ok
  assert stack.reload.archived?, "victim stack was archived by a payload never signed for its own org"
end
```
Both sides of the invariant to assert explicitly: `payload["repository"]["owner"]["login"]` (`"attacker-org"`, used by `verify_signature`) vs. `Shipit::Repository.from_github_repo_name(payload["repository"]["full_name"]).owner` (`victim_repo.owner`, used by the handler) — they differ, and the test shows the mutation still lands.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

        "unknown_organization=#{e.message}",

      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
