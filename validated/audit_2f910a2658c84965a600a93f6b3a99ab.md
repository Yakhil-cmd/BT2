### Title
Webhook signature verification org and payload-processing org are decoupled, allowing cross-organization repository spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the signing key using `repository.owner.login`/`organization.login` from the raw JSON body [1](#0-0) , but every downstream handler resolves the target repository from a completely different field, `params.repository.full_name` [2](#0-1) . Nothing binds these two fields to each other, so a payload can be "verified" against one organization's key while acting on a repository belonging to a different, unrelated organization.

### Finding Description
Broken binding: `repository_owner used to pick the verifying GitHubApp` should equal `owner(params.repository.full_name) used to resolve Shipit::Repository`, but the code never enforces this.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature` against that org's configured secret [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org has no `webhook_secret` configured: `return true unless webhook_secret` [4](#0-3) .
- `OpenedHandler#repository` (and every other pull_request handler) instead resolves the acted-upon repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) , and `provision?`/`pull_request_has_provisioning_label?` trust `pull_request.labels` verbatim from the same JSON body [5](#0-4) .
- `Shipit.github(organization:)` only accepts organizations pre-registered by the operator in `secrets.github`; an unknown org raises `GithubOrganizationUnknown`, which halts the request with 422 [6](#0-5) .

Exploit precondition and flow: this only works if the Shipit operator has configured **at least one legitimate organization with no `webhook_secret`** (a real, supported configuration branch per `verify_webhook_signature`), and the attacker knows that org's login. The attacker crafts an "opened" pull_request payload where:
- `repository.owner.login` (and/or `organization.login`) = the secret-less org's name (so `verify_signature` picks that org's `GitHubApp`, whose `verify_webhook_signature` returns `true` for any/no signature),
- `repository.full_name` = `"victim-org/victim-repo"` (a real Shipit-tracked repository under a *different*, properly secured organization),
- `pull_request.labels` = `[{ "name" => repository.provisioning_label_name }]` (fully attacker-fabricated, never applied on GitHub),
- `pull_request.head.sha`/`ref` = attacker-controlled.

`verify_signature` passes (secret-less org, any signature accepted), `drop_unhandled_event`/`check_if_ping` don't interfere, and `OpenedHandler` resolves `repository` to the victim repo via `full_name`, evaluates `provision?` using the fabricated labels, and calls `ReviewStackAdapter#find_or_create!`, creating a `ReviewStack` (and queuing provisioning/deploy of the attacker's `head.sha`/`ref`) against the victim repository — despite the victim's `provisioning_behavior_allow_with_label` gate and despite no genuine GitHub label event ever occurring [7](#0-6) .

Why existing guards fail: `verify_signature` only proves the payload was signed (or exempted) *for the organization named in the payload's owner field* — it never checks that this organization is the same one that owns the repository the handler will subsequently mutate. `ExplicitParameters` schemas only validate types/presence of `repository.full_name`, `pull_request.labels`, etc.; they impose no cross-field consistency constraint [8](#0-7) . `Repository.from_github_repo_name` performs a plain lookup by `owner/name` split of `full_name`, with no relation to the verified org [9](#0-8) .

### Impact Explanation
An attacker can force creation (and provisioning/deploy queuing) of a `ReviewStack` for an arbitrary victim repository, bypassing the `provisioning_behavior_allow_with_label` gate entirely, without ever touching the victim's GitHub organization's real webhook secret. This is a payload for one organization's webhook mutating another organization's repository/stack state — matching the Critical category "a payload for one repository mutating another's stack" and effectively an authentication-bypass on the intended per-repository/per-org provisioning gate. It is repeatable against any victim repository whose `owner/name` the attacker knows, as long as one secret-less (or attacker-known-secret) organization exists in the deployment's `secrets.github` configuration.

### Likelihood Explanation
This requires a specific, non-default operator configuration: at least one organization entry in `secrets.github` with a blank/absent `webhook_secret` (a supported code path, but a security-relevant misconfiguration many operators would avoid once aware), or one whose secret the attacker independently knows. Without such an organization existing, `Shipit.github(organization: attacker_named_org)` either raises `GithubOrganizationUnknown` (422, request halted) or requires the correct HMAC secret, which the attacker does not have. Given this precondition, exploitation cost is a single crafted HTTP POST to `/webhooks` with a fabricated JSON body — no GitHub interaction required, fully repeatable.

### Recommendation
Bind signature-verification identity to the repository actually being acted upon: after selecting `repository_owner` for verification, require that it match the owner segment of `params.repository.full_name` (and reject if they differ) before dispatching to handlers. Alternatively, always verify against the `GitHubApp` config associated with the *resolved* `Shipit::Repository`'s stored `owner`, not a client-supplied field, and disallow (or explicitly flag) organizations configured with an empty `webhook_secret` from being usable as a bypass source for any other org's repositories.

### Proof of Concept
Minitest plan (webhooks_controller_test.rb style, no live GitHub):
1. Fixture setup: configure `Shipit.stubs(:github).with(organization: 'secretless-org')` to return a real `GitHubApp` instance built with `webhook_secret: nil`; ensure a `victim-org/victim-repo` `Shipit::Repository` exists with `provisioning_behavior: 'allow_with_label'` and `provisioning_label_name: 'ship-it'`, `review_stacks_enabled: true`.
2. Build payload: `{ action: 'opened', number: 99, repository: { owner: { login: 'secretless-org' }, full_name: 'victim-org/victim-repo' }, pull_request: { id: 1, number: 99, url: '...', title: 'x', state: 'open', additions: 1, deletions: 0, head: { sha: 'attackersha', ref: 'attacker-branch' }, user: { login: 'attacker' }, assignees: [], labels: [{ name: 'ship-it' }] }, sender: { login: 'attacker' } }`.
3. `request.headers['X-Github-Event'] = 'pull_request'`; no/garbage `X-Hub-Signature`.
4. `assert_difference('Shipit::ReviewStack.count', 1) { post :create, body: payload.to_json, as: :json }` — assert equality violated: `repository_owner` used for verification (`'secretless-org'`) != owner of `params.repository.full_name` (`'victim-org'`), yet a `ReviewStack` is created for `victim-org/victim-repo`.
5. Assert `assert_response :ok` and that the created `ReviewStack`'s `branch == 'attacker-branch'`, proving unauthorized provisioning despite the label never having been applied via a genuine GitHub event.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "status=#{status}"
      ].join(' '))
    end

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
