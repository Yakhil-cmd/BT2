Found a valid analog. The vulnerability class maps directly onto nearcore's `PromiseYield` timeout queue processing, which relies on the same "ordered/monotonic" assumption that the WithdrawProxy bug violates.

### Title
PromiseYield timeout queue processing assumes `expires_at` is monotonically non-decreasing across queue entries, but a reduction of `yield_timeout_length_in_blocks` between entries can violate this, indefinitely stalling later-created yields behind older, longer-lived ones - (File: `runtime/runtime/src/lib.rs`)

### Summary
`resolve_promise_yield_timeouts` walks the `PromiseYieldTimeout` trie queue strictly in insertion order (`first_index` → `next_available_index`) and stops as soon as it finds an entry whose `expires_at` is still in the future, based on the comment "Queue entries are ordered by expires_at". This assumption only holds if `yield_timeout_length_in_blocks` is constant (or only increases) over the lifetime of the queue. If this runtime parameter is decreased by a protocol/config upgrade, a `PromiseYield` receipt created (enqueued) later can have a smaller `expires_at` than an older, still-unresolved entry earlier in the queue - exactly mirroring the WithdrawProxy bug where reducing the Router's auction time lets a newer auction end before an older one.

### Finding Description
When a contract creates a yielded promise, the runtime enqueues a `PromiseYieldTimeout { account_id, data_id, expires_at }` at the back of a FIFO trie-backed queue, where `expires_at` is computed as `apply_state.block_height + config.wasm_config.limit_config.yield_timeout_length_in_blocks`: [1](#0-0) 

The timeout-processing routine iterates the queue starting from `first_index`, and explicitly relies on strict ordering by `expires_at` to decide when to stop: [2](#0-1) 

This is a FIFO queue ordered by insertion (block height at creation), not by `expires_at` value directly. The correctness of the `break` on the first non-expired entry depends entirely on `yield_timeout_length_in_blocks` never decreasing. `RuntimeConfig` parameters, including this one, are explicitly designed to be changed at future protocol versions via differential YAML overlays, as documented in the parameter system: [3](#0-2) 

If a future protocol upgrade decreases `yield_timeout_length_in_blocks` (analogous to the Router reducing auction time in the original report), then:
- Entry A, enqueued at height H1 under the old (larger) timeout length, has `expires_at = H1 + old_length` (large).
- Entry B, enqueued later at height H2 > H1 under the new (smaller) timeout length, has `expires_at = H2 + new_length`, which can be smaller than A's `expires_at`.

Since B is queued behind A (`first_index` still points at A), the loop in `resolve_promise_yield_timeouts` checks A first: `A.expires_at > block_height` is true, so it `break`s immediately - never even inspecting B, even though B has already "expired" and should be resolved.

### Impact Explanation
This causes a chain-stall-like resource lock at the application layer: legitimate `yield_create`/`yield_resume` promises that are already past their timeout cannot be resolved by the protocol until every older, still-unexpired entry ahead of them in the queue is drained (which requires waiting until *their* larger `expires_at` height is reached, or until they are otherwise resolved and walked over). This can indefinitely delay execution of dependent receipts/callbacks for affected contracts and accounts, is triggered purely by ordinary contract calls (`yield_create`), and requires no validator or attacker privilege - only a routine future protocol/config parameter change plus normal contract usage. It matches the "state divergence / stuck state / no-recourse lock" impact category analogous to the original WithdrawProxy funds lock.

### Likelihood Explanation
This is latent and configuration-dependent: currently `yield_timeout_length_in_blocks` has never been changed across protocol versions in this codebase's parameter snapshots, so the bug is not presently triggerable on mainnet. However, because the runtime config framework explicitly supports changing any parameter (including this one) per protocol version, a future governance-approved reduction of this parameter would silently reintroduce this exact class of bug, with no code-level defense against it today.

### Recommendation
Do not rely on an implicit invariant that `expires_at` values are non-decreasing across the FIFO queue. Either:
- Track/store the maximum `expires_at` value ever enqueued and only compute new timeouts as `max(current_max, block_height + yield_timeout_length_in_blocks)`, and forbid processing from stopping until that stored max is reached; or
- Change `resolve_promise_yield_timeouts` to not `break` on the first non-expired entry but instead scan/skip past not-yet-expired entries in a bounded way, or maintain a separate explicit min-heap/ordering by `expires_at` rather than assuming insertion order implies expiry order; or
- Explicitly disallow future decreases to `yield_timeout_length_in_blocks` and add a protocol-level invariant check/test enforcing monotonic non-decrease of this parameter across versions.

### Proof of Concept
1. Suppose at protocol version N, `yield_timeout_length_in_blocks = 1000`. A contract calls `yield_create` at block height 100, enqueuing timeout entry A with `expires_at = 1100`.
2. A protocol upgrade to version N+1 reduces `yield_timeout_length_in_blocks` to 10.
3. At block height 200 (under version N+1), another contract calls `yield_create`, enqueuing timeout entry B with `expires_at = 210`.
4. At block height 210, B has "expired" and should produce a `PromiseResume` timeout receipt, but `resolve_promise_yield_timeouts` first inspects A (`first_index`), finds `A.expires_at (1100) > block_height (210)`, and `break`s before ever looking at B: [4](#0-3) 
5. B's timeout resume is not produced until block height 1100 is reached (when A is finally walked over and removed), an ~890-block (or arbitrarily large, depending on parameter delta) unwarranted delay/lock on B's execution.
