### Title
CCMenu API client token scoped to one stack can read CI build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The `Api::CCMenuController` authenticates callers using an `ApiClient` token but never restricts the returned data to the stack that token was scoped to when it was issued, breaking the binding "stack a token authorizes == stack it touches."

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack` association, and `Shipit::Api::BaseController#stacks`/`#stack` enforce this scope by filtering `Stack.where(id: current_api_client.stack_id)` before resolving `params[:stack_id]`. [1](#0-0) 

However, `Api::CCMenuController` overrides both the authentication method and the `stack` resolver: it authenticates any token supplied via the `token` query parameter (bypassing Basic Auth) and resolves the target stack directly from `params[:stack_id]` with `Stack.from_param!`, without ever checking it against `current_api_client.stack_id`. [2](#0-1) 

The `ApiClient.authenticate` class method itself performs no stack-scoping check — it simply looks up any `ApiClient` by verifying the signed token and returns it. [3](#0-2) 

The `check_permissions!` call enforced via `require_permission :read, :stack` only validates the permission string list (e.g. `read:stack`); it never validates that the `stack` in scope equals `current_api_client.stack_id`. [4](#0-3) [5](#0-4) 

This mirrors the GammaProtocol bug class: the `Controller._redeem` function trusted an unverified `oToken` argument address instead of checking it against the platform's real registered token; here, `CCMenuController#stack` trusts the unverified `params[:stack_id]` argument instead of checking it against the stack the presented token was actually issued/scoped for.

In normal usage, a stack-scoped CCMenu token is generated automatically and handed out via `CCMenuUrlController#fetch`, which creates a token scoped to exactly one stack (`stack_id: @stack.to_param`, permission `read:stack`). [6](#0-5) 

Any holder of such a token (e.g. a CI dashboard tool, or anyone who observed the token in a CCMenu URL/status monitor config) can instead call `/api/stacks/<other-owner>/<other-repo>/<other-env>/ccmenu?token=<their-token>` and receive that other stack's build/deploy status, activity and last build label — data the token was never authorized to access.

### Impact Explanation
This provides unauthorized cross-stack read access: `token` authorizes stack A, but the endpoint returns state (name, activity, lastBuildStatus, lastBuildLabel, webUrl) for any stack B chosen by the caller. This matches the "High" category of "escalation into... unauthenticated/unauthorized read of stack state" defined by the scan rules, since the broken binding is exactly "a stack a token authorises versus a stack it touches."

### Likelihood Explanation
Any party who legitimately possesses (or leaks) a single stack-scoped CCMenu token — a low-privilege artifact commonly embedded in third-party CI-status monitors/URLs — can trivially exploit this by changing the `stack_id` path segment of the request; no additional secrets, session, or GitHub credentials are required.

### Recommendation
In `Api::CCMenuController#stack`, resolve the stack the same way `BaseController#stack` does — restrict the lookup to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a stack, e.g. reuse `stacks.from_param!(params[:stack_id])` instead of the unscoped `Stack.from_param!(params[:stack_id])`.

### Proof of Concept
1. Obtain (or be issued) a legitimate CCMenu token scoped to Stack A via `CCMenuUrlController#fetch` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`), which creates an `ApiClient` with `stack: stack_a, permissions: ['read:stack']`.
2. Send `GET /api/stacks/other-owner/other-repo/other-env/ccmenu?token=<token>`.
3. `Api::CCMenuController#authenticate_api_client` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) successfully authenticates the token via `ApiClient.authenticate`.
4. `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) resolves Stack B (`other-owner/other-repo/other-env`) directly from the URL, ignoring `current_api_client.stack_id`.
5. `require_permission :read, :stack` passes because the client does have the `read:stack` permission string, regardless of which stack it applies to.
6. The response discloses Stack B's build status, activity, and last build info, even though the token was only ever authorized for Stack A.
