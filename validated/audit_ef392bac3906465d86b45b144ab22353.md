### Title
Atomic bundling of `token_0`/`token_1` transfers in `withdraw`/`collect_creator_fee(_permissionless)` lets one frozen/blocked token lock users out of the other, unaffected token — (File: `programs/cp-swap/src/instructions/withdraw.rs`, `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`withdraw`, `collect_creator_fee` and `collect_creator_fee_permissionless` each perform two token transfers (`token_0` then `token_1`) inside a single atomic instruction with no way to request only one of the two tokens. If either the vault's own token account, or the recipient's token account, becomes non-transferable (e.g. the account is frozen by the mint's freeze authority — a standard, universally-supported SPL Token feature the program never screens for on legacy mints), the whole instruction reverts, permanently blocking access to the *unaffected* token as well. This mirrors the referenced `VE3DRewardPool` finding: bundling multiple independent token payouts into one all-or-nothing call turns an isolated, external token problem into a freeze of otherwise-healthy funds.

### Finding Description
`withdraw` burns the user's LP tokens and then unconditionally calls `transfer_from_pool_vault_to_user` twice, once per token, inside the same instruction: [1](#0-0) 

`collect_creator_fee` and `collect_creator_fee_permissionless` follow the identical pattern for the accrued creator fees of both tokens: [2](#0-1) [3](#0-2) 

Each `transfer_from_pool_vault_to_user` is a `token_2022::transfer_checked` CPI that will fail (and thus abort the entire transaction, rolling back the LP burn and both transfers) if the source vault or the destination token account cannot be debited/credited, e.g. because it is frozen: [4](#0-3) 

Crucially, mint safety validation is only performed once, at pool creation, via `is_supported_mint`. For legacy SPL Token mints (`owner == Token::id()`), the function unconditionally approves the mint with **no check whatsoever of the mint's freeze authority**: [5](#0-4) 

`is_supported_mint` is only invoked in `initialize`/`initialize_with_permission`, and never re-checked afterward: [6](#0-5) 

Freeze authority is a standard, common feature of SPL Token mints (e.g. many stablecoins), so pools are routinely created pairing an unrestricted token with a freezable one. Once the pool's own `token_0_vault`/`token_1_vault` (or a recipient's ATA) associated with the freezable mint is frozen by that mint's freeze authority, every instruction that bundles a transfer of that token together with the other token becomes permanently unusable — even though the second token has nothing wrong with it.

### Impact Explanation
If the freeze authority of one pooled token freezes the pool's vault account (or a user's/creator's recipient token account) for any reason — compliance action, key compromise, or malicious behavior by that token's issuer — LPs can no longer call `withdraw` at all, and pool creators can no longer call `collect_creator_fee`/`collect_creator_fee_permissionless` at all, because both instructions require both transfers to succeed atomically. This freezes user LP principal and creator fees denominated in the *unaffected* token as well, with no on-chain recovery path (no partial/single-token withdraw or fee-collect exists). This is a permanent freezing of user and LP funds for as long as the freeze condition persists, matching Medium severity as judged in the original report.

### Likelihood Explanation
The program explicitly supports pairing any legacy SPL Token mint without validating the absence of a freeze authority (`is_supported_mint` returns `true` unconditionally for `Token::id()`-owned mints), so pools with freezable tokens (common, e.g. regulated stablecoins) are a normal, expected configuration, not an edge case requiring special exploitation. The trigger is external (the mint's freeze authority acting on the pool's vault or a user's ATA), so likelihood is moderate and contingent on a legitimate real-world token behavior rather than an on-chain exploit, consistent with the "Medium" rating given to the analogous finding.

### Recommendation
- Add a selective/partial withdrawal path (e.g., allow specifying which of `token_0`/`token_1` to redeem) so a freeze on one token cannot block redemption of the other, mirroring the recommended `getReward(tokens[])` fix in the original report.
- Similarly split `collect_creator_fee`/`collect_creator_fee_permissionless` into per-token variants, or make each transfer failure independently recoverable instead of atomically coupled.
- Consider rejecting legacy SPL Token mints with a non-null freeze authority in `is_supported_mint`, or document/mitigate the risk explicitly since it is currently unchecked.

### Proof of Concept
1. Pool `P` is created via `initialize` with `token_0` = a standard legacy SPL Token mint that has an active freeze authority (e.g. a regulated stablecoin), `token_1` = an ordinary token; `is_supported_mint` passes unconditionally for `token_0` since it is owned by the legacy `Token` program.
2. LP deposits liquidity into `P` via `deposit`.
3. The `token_0` mint's freeze authority freezes `P`'s `token_0_vault` token account (a routine, permissible SPL Token Program action outside of `P`'s or the LP's control).
4. LP calls `withdraw`; the LP burn succeeds, the `token_1` transfer would succeed, but the `token_0` `transfer_checked` CPI fails because the vault is frozen, reverting the entire transaction including the `token_1` payout. [1](#0-0) 
5. The LP has no alternative instruction to redeem only `token_1`; their entire LP position, including the unaffected `token_1` portion, is frozen indefinitely.
6. Identically, if the pool creator's `creator_token_0` ATA (or the vault) is frozen, `collect_creator_fee`/`collect_creator_fee_permissionless` can never succeed, blocking collection of accrued `token_1` fees as well. [2](#0-1)

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}

    mint_associated_is_initialized: bool,

    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
