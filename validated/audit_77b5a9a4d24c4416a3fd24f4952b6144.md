## Analysis

The report's bug class is: a cross-chain **message-receiving handler** calls into logic that can legitimately `revert`/throw under conditions that hold only sometimes (state mismatch, insufficient limits, etc.), and this unhandled failure blocks the message pipeline until manual intervention — a DoS of the messaging channel.

In `ocore`, the closest reachable analog for an **unprivileged unit poster** is the Autonomous-Agent trigger/response pipeline in `aa_composer.js`. When an AA responds to a trigger, its response unit is built and then run back through full `validation.validate()` inside `validateAndSaveUnit()`. Unlike the primary trigger path — which properly catches formula/logic failures and safely `bounce()`s — the *validation* of the AA-generated response unit treats every non-`ifOk` outcome as "impossible" and reacts with a raw, synchronous `throw Error(...)`: [1](#0-0) 

In particular `ifTransientError` unconditionally throws:
```
ifTransientError: function (err) {
    throw Error("AA validation transient error: " + err);
},
```
Transient errors are exactly the class of error that `validation.js` uses for conditions that are *timing/context dependent, not permanently invalid* — e.g. tps-fee-related conditions that are handled elsewhere in the network layer by scheduling a retry rather than crashing: [2](#0-1) 
```
ifTransientError: function(error) {
    sendErrorResult(ws, unit, error);
    onDone();
    if (error.includes("tps fee"))
        setTimeout(handleOnlineJoint, 10 * 1000, ws, objJoint);
},
```

That is, the exact same class of error (`createTransientError`, tps-fee related) that the P2P unit-handling path treats as retryable is treated as a fatal, unrecoverable `throw` when it occurs for an AA-generated response unit inside `aa_composer.js`'s `validateAndSaveUnit`. Because AA trigger execution is deterministic and runs on *every* full node processing that MCI (via `handleAATriggers()` invoked from `markMcIndexStable()`/`writer.js`), an uncaught `throw` here does not fail gracefully for one message — it propagates up through the DB-callback chain with no `try/catch`, and per `network.js`'s global handler: [3](#0-2) 
```
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
```

the process crashes. Since the same trigger/response unit is processed identically by every full node reaching that MCI, this becomes a synchronized, network-wide crash rather than a localized failure — the analog of the CCIP report's "permanent DoS of the pathway until the blocked message can pass," except here the "message" is AA trigger execution required for **all future MCI stabilization**, so the impact escalates to "network unable to confirm new units" until the code is patched, since every node retrying the same MCI hits the identical fatal condition.

### Title
Unhandled `throw` on transient/edge-case validation errors for AA response units can crash every full node deterministically, halting MC stabilization - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `validateAndSaveUnit()`, used to validate every AA-generated response unit before it is written, converts several validation outcomes (`ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`) that `validation.js` treats as recoverable/retryable elsewhere in the codebase into unconditional `throw Error(...)` calls. Because AA trigger execution is fully deterministic and executed by every full node when an MCI stabilizes, any input (an attacker-crafted trigger, asset, or data payload reaching an AA) that drives the AA's generated response unit into one of these "unexpected" validation branches will crash every full node identically and permanently at that MCI, rather than causing a graceful bounce as designed for ordinary AA logic errors.

### Finding Description
`handleTrigger()` in `aa_composer.js` builds the AA's response unit and passes it back into `validation.validate()` via `validateAndSaveUnit()`: [1](#0-0) 

All non-`ifOk` callbacks assume "this can never happen" and `throw`. However, `validation.js` demonstrably produces `ifTransientError` for conditions that *do* legitimately occur depending on runtime/db state (e.g. tps-fee timing issues used elsewhere as retry triggers): [2](#0-1) 

Unlike `handleOnlineJoint`/`handlePostedJoint` in `network.js`, which treat `ifTransientError` as retryable and reschedule, or the `bounce()`/`revert()` machinery elsewhere in `handleTrigger()` which safely absorbs formula-evaluation failures: [4](#0-3) 

`validateAndSaveUnit()` has no such recovery path. A synchronous `throw` inside a nested DB-callback chain (no surrounding `try/catch`) is uncaught, and `network.js`'s global handler intentionally crashes the process on any uncaught exception: [3](#0-2) 

Because AA triggers are scheduled and executed deterministically from the `aa_triggers` table by `handleAATriggers()`, which is invoked from `markMcIndexStable()`/`writer.js` on every full node when the relevant MCI becomes stable: [5](#0-4) [6](#0-5) 

any full node that reaches this MCI will independently re-derive the same AA response unit and hit the same fatal branch. This is exactly analogous to the CCIP report's core issue — a downstream message-processing call that can revert under conditions the outer handler does not gracefully account for — except in `ocore` the blast radius is the entire set of full nodes rather than a single bridge lane, and the "message queue" that gets blocked is main-chain stabilization itself, since `handleAATriggers()` must complete before subsequent MCIs can be marked stable and their own triggers processed.

### Impact Explanation
If any AA response unit (triggered by data an unprivileged unit poster can supply — the trigger payload, asset outputs, or oscript logic of the AA) causes its own validation to return a `ifTransientError`/`ifNeedHashTree`/`ifNeedParentUnits`/`ifOkUnsigned`/`ifJointError` outcome instead of `ifOk`, every full node executing that trigger will throw an uncaught exception and crash. Since this happens deterministically inside `stabilizeMci()`/`markMcIndexStable()`, restarting the node does not help — on restart, the pending trigger in the `aa_triggers` table is retried and the crash recurs, halting all further MC stabilization and unit confirmation network-wide until the software itself is patched. This matches the required "network unable to confirm new units" impact class, and is strictly worse than the source report because it is a synchronized, self-inflicted crash on every honest full node rather than a localized message-execution failure.

### Likelihood Explanation
Reaching one of the "impossible" branches requires crafting a trigger/AA-definition combination whose deterministic response unit trips a condition validation treats as transient/unexpected rather than a plain logic bounce (e.g., a tps-fee edge case, or a race between AA-definition freshness and `last_ball_mci` at trigger-execution time vs. trigger-composition time). This is a narrower trigger surface than a straightforward formula bounce, but it is fully reachable by posting ordinary units/AA definitions and payments — no special privilege is required, matching the report's "unprivileged AA trigger sender" reachability. The report explicitly frames the underlying bug class (unhandled exception in message-processing that can legitimately occur) as low-probability-but-high-impact, which the LucidLabs team risk-accepted; the `ocore` analog carries the same likelihood profile but a strictly higher impact ceiling (total network halt vs. a single blocked cross-chain lane).

### Recommendation
Convert `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, and `ifOkUnsigned` handling in `aa_composer.js`'s `validateAndSaveUnit()` (and the equivalent block in `network.js`'s `ifOk` dry-run path) from unconditional `throw` to safe failure handling that `bounce()`s the AA trigger (treating it like any other AA execution failure) instead of crashing the node process. At minimum, any error class that is demonstrably retryable elsewhere in the codebase (tps-fee transient errors) must not be treated as a fatal invariant violation when it occurs for an internally generated AA response unit.

### Proof of Concept
Conceptual PoC (requires live network/testnet access to confirm concretely, which is outside the scope of this analysis):
1. Deploy an AA whose `messages` section, when it fires in response to an attacker-supplied trigger, produces a response unit whose fee/timing characteristics are crafted to fall into the same category of condition that `validateTpsFee`/`validateAATrigger` in `validation.js` reports via `createTransientError` (or similar) rather than a plain validation failure.
2. Post the triggering unit as an ordinary unprivileged user once it is included and its MCI becomes stable, `main_chain.stabilizeMci()` → `aa_composer.handleAATriggers()` → `handleTrigger()` → `validateAndSaveUnit()` runs.
3. `validation.validate()` returns via the `ifTransientError` callback for the generated response unit; `aa_composer.js` throws, which is uncaught and crashes the process per `network.js`'s `process.on('uncaughtException')` handler.
4. Every other full node reaches the same MCI, deterministically derives the identical response unit, and crashes identically — halting stabilization for the whole network until a patch is deployed.
