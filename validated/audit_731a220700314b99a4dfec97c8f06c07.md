### Title
Webhook target resolution is decoupled from webhook signature-verification identity, allowing unauthenticated cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The engine verifies an inbound GitHub webhook's HMAC signature using a `GitHubApp` config selected from `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload resolve their target `Stack` from a completely different, unchecked field: `repository.full_name`. These two fields are never cross-validated, so the identity used to pick the verification secret is not the identity that is written to. Combined with `verify_webhook_signature` short-circuiting to `true` when no `webhook_secret` is configured for the selected organization, this reproduces the M-05 bug class: a value the code trusts (owner/organization used to authorize) diverges from the value it acts on (repository written to), exactly mirroring the contract's "first calculation vs. second calculation" mismatch that lets untrusted deltas slip through.

### Finding Description
`WebhooksController#verify_signature` picks a `GitHubApp` by the payload's own `repository.owner.login` (falling back to `organization.login`), then verifies the raw body's signature against that app's secret: [1](#0-0) 

`GitHubApp#verify_webhook_signature` trivially passes verification whenever no secret is configured for that organization: [2](#0-1) 

Once the request passes this org-scoped check, the actual event handlers ignore `repository.owner.login` entirely and instead resolve the target repository/stack from `repository.full_name`, a sibling field in the same untrusted JSON body: [3](#0-2) 

`PushHandler` then uses that resolved stack set together with attacker-supplied `ref`/`after` to enqueue a sync to an arbitrary commit SHA: [4](#0-3) 

The equality that should hold is:
`organization used to select/verify the signing secret == organization that owns the repository being written to`

Because `repository_owner` (verification key) and `repository.full_name` (action key) are independently attacker-controlled fields of the same JSON body and are never compared to each other, this equality is not enforced. An attacker who can get `verify_signature` to pass for *any* organization (trivially true for an organization that has no `webhook_secret` configured, since `verify_webhook_signature` returns `true` unconditionally in that case) can set `repository.full_name` to point at a *different* organization's/repository's stack and have `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. act on it.

### Impact Explanation
This breaks the binding between "the organization whose credentials authorized this webhook" and "the repository being mutated," which is precisely the class of binding the rules flag as in-scope (organization authenticated vs. repository written). Exploiting it lets an unauthenticated actor force `GithubSyncJob` to advance a victim stack's `expected_head_sha` to an attacker-chosen value, or forge `status`/`check_suite` events that get recorded against a victim repository's commits, potentially enabling unauthorized deploys/rollbacks or bypassing CI gating that Shipit relies on for deploy decisions — matching the "unauthorized deploy" High/Critical impact bucket.

### Likelihood Explanation
Likelihood is Medium: it requires an instance where at least one configured `GitHubApp`/organization has no `webhook_secret` set (an explicitly supported configuration state per `verify_webhook_signature`'s `return true unless webhook_secret` branch), which is a realistic deployment posture rather than a contrived one, and requires no privileged token, session, or knowledge of any secret.

### Recommendation
Cross-validate that the organization used to select/verify the signature (`repository.owner.login` / `organization.login`) matches the organization embedded in `repository.full_name` before any handler resolves stacks from the payload. Additionally, treat a missing `webhook_secret` for an organization as "reject all webhooks for that organization" rather than "skip verification," so the absence of a secret cannot be leveraged to bypass authentication entirely.

### Proof of Concept
1. Ensure (or find) a configured Shipit organization `orgA` with no `webhook_secret` set.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request is accepted without any valid HMAC.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, mutating state for `victim-org/victim-repo` despite the "verified" identity being unrelated `orgA`.     def verify_signature
```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
