### Title
Inconsistent use of `DenyRecursively` around `DenyReserveTransferToRelayChain` allows nested-instruction bypass of the relay-chain reserve-transfer deny policy - (File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs, asset-hub-kusama/src/xcm_config.rs, collectives-polkadot/src/xcm_config.rs, coretime-kusama/src/xcm_config.rs, coretime-polkadot/src/xcm_config.rs, encointer/src/xcm_config.rs, people-kusama/src/xcm_config.rs, people-polkadot/src/xcm_config.rs, bridge-hub-kusama/src/xcm_config.rs)

### Summary
`DenyReserveTransferToRelayChain` (from `xcm_builder`, external to this repo) matches specific reserve-transfer instructions (`InitiateReserveWithdraw`, `InitiateTeleport`, `DepositReserveAsset`, `TransferReserveAsset`) only against the flat top-level instruction slice supplied to `ShouldExecute::should_execute`. If such an instruction is nested inside `SetAppendix`/`SetErrorHandler` (which carry their own `Xcm<Instruction>` payload as an opaque instruction argument), the deny-matcher's flat scan does not descend into it and treats the wrapper as an unrelated instruction, letting it pass the deny stage. This repo already recognizes and fixes this class of bypass in two chains by wrapping the check with `DenyRecursively<DenyReserveTransferToRelayChain>` [2](#0-1) [3](#0-2) , but every other system parachain in the same repo still uses the plain, non-recursive `DenyReserveTransferToRelayChain`.

### Finding Description
The `Barrier` for Asset Hub Polkadot/Kusama, Collectives Polkadot, Coretime Polkadot/Kusama, Encointer, People Polkadot/Kusama, and Bridge Hub Kusama is built as:
```
DenyThenTry<DenyReserveTransferToRelayChain, (TakeWeightCredit, ..., WithComputedOrigin<(AllowTopLevelPaidExecutionFrom<Everything>, ...)>)>
```
as seen for example at [4](#0-3)  and [5](#0-4) .

`DenyReserveTransferToRelayChain` is defined externally in `xcm_builder` and is imported unmodified, e.g. [6](#0-5) . Its matcher walks the flat top-level instruction list to look for the deny-listed instructions targeting `Location::parent()`. `SetAppendix(Xcm)` and `SetErrorHandler(Xcm)` carry a *nested* `Xcm` program as their instruction argument, which is opaque to a flat top-level scan; the nested `DepositReserveAsset`/`InitiateReserveWithdraw`/etc. inside that nested program is not inspected by the deny stage. Once the message clears the deny stage, it proceeds to `WithComputedOrigin<(AllowTopLevelPaidExecutionFrom<Everything>, ...)>`, which only validates structural/fee properties of the top-level program (first instruction is a funding instruction followed by `BuyExecution`) and does not re-apply the deny policy to nested appendix/error-handler programs. During actual execution, the executor later runs the appendix/error-handler program and would execute the reserve-transfer instruction targeting the Relay Chain normally, since no further deny check occurs at that point.

This repo's own code demonstrates the fix is known: `bridge-hub-polkadot` and `bulletin-polkadot` wrap the check as `DenyRecursively<DenyReserveTransferToRelayChain>`, which (per its name/purpose) inspects nested `Xcm` programs recursively. All other chains listed above lack this wrapper, leaving them exposed to the exact bypass pattern described in the audit prompt (hiding `ReserveAssetDeposited`/reserve-transfer instructions inside `SetAppendix`/`SetErrorHandler`).

### Impact Explanation
An unprivileged parachain (or any XCM sender reachable via XCMP/UMP) could craft a message that structurally satisfies `AllowTopLevelPaidExecutionFrom<Everything>` (fund + `BuyExecution` at the top) while embedding a `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting `Location::parent()` inside a `SetAppendix` or `SetErrorHandler` instruction. On the affected chains (Asset Hub Polkadot/Kusama, Collectives Polkadot, Coretime Polkadot/Kusama, Encointer, People Polkadot/Kusama, Bridge Hub Kusama), the deny barrier would not catch this, and the appendix/error-handler program would later execute the reserve transfer to the Relay Chain, violating the intended "reserve transfers to the Relay Chain must always be denied" invariant.

### Likelihood Explanation
Preconditions are minimal: any account able to send an XCM message through XCMP or as a sovereign-derived origin on these chains (no privileged origin needed) can construct the nested instruction sequence. Feasibility depends on whether the underlying `xcm_builder::DenyReserveTransferToRelayChain` matcher genuinely fails to recurse into `SetAppendix`/`SetErrorHandler` payloads — that logic lives in the external `xcm_builder` crate, not in this repository, so it cannot be fully confirmed or disproven purely from this repo's code. What is concretely verifiable in-repo is the inconsistency: two chains (`bridge-hub-polkadot`, `bulletin-polkadot`) apply `DenyRecursively` specifically for this reason, while the rest do not, which is itself evidence that the underlying non-recursive matcher has this gap and that the fix was only partially rolled out.

### Recommendation
Apply `DenyRecursively<DenyReserveTransferToRelayChain>` consistently across all system parachain `Barrier` definitions that currently use the plain `DenyReserveTransferToRelayChain`, matching the pattern already used in `bridge-hub-polkadot` and `bulletin-polkadot`: `system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs`, `system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs`, `system-parachains/collectives/collectives-polkadot/src/xcm_config.rs`, `system-parachains/coretime/coretime-polkadot/src/xcm_config.rs`, `system-parachains/coretime/coretime-kusama/src/xcm_config.rs`, `system-parachains/encointer/src/xcm_config.rs`, `system-parachains/people/people-polkadot/src/xcm_config.rs`, `system-parachains/people/people-kusama/src/xcm_config.rs`, and `system-parachains/bridge-hubs/bridge-hub-kusama/src/xcm_config.rs`.

### Proof of Concept
xcm-emulator test plan (per affected chain): construct an `Xcm` where the top-level instructions are `WithdrawAsset`/`BuyExecution` (to satisfy `AllowTopLevelPaidExecutionFrom`) followed by `SetAppendix(Xcm(vec![DepositReserveAsset { dest: Location::parent(), .. }]))` and a benign trailing instruction; send it from a non-privileged sibling parachain via XCMP into the target chain. Assert:
1. `Barrier::should_execute` on the raw message returns `Err` (expected/required) — currently would need verification against the actual `xcm_builder` behavior.
2. If execution is not blocked, assert that after processing, no assets were forwarded/deposited to the Relay Chain sovereign/UMP outbound queue, and that `PolkadotXcm`'s asset trap / accounting does not show a completed relay-bound reserve deposit.
3. Repeat with `SetErrorHandler` wrapping instead of `SetAppendix`, and with multiple nesting depths, to confirm the deny policy holds uniformly once `DenyRecursively` is applied on all chains.
