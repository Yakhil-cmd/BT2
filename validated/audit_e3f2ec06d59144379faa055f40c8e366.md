### Title
Webhook signature verified against attacker-chosen organization while payload is dispatched by a different `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the HMAC signature against based on an **unverified** field of the incoming JSON body (`repository.owner.login` / `organization.login`). The event handlers that actually act on the payload, however, key off a **different** unverified field, `repository.full_name`, to resolve the target `Repository`/`Stack`. Because these two fields are never cross-checked against each other, and neither is bound by the signature computed with the *selected* secret, the "organization that authenticated" and "repository that is written" are not the same binding.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick which configured GitHub App/organization's `webhook_secret` verifies the signature:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

Shipit supports multiple GitHub App configs keyed by organization (`config/secrets.development.example.yml` shows the multi-org schema) [3](#0-2) , and `Shipit.github` resolves the app/secret purely from this organization key.

After verification passes, `create` hands the **entire raw, unvalidated `params`** (not just the verified `repository_owner`) to every registered handler:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler (e.g. `PushHandler`) resolves the target `Stack`/`Repository` using a **separate** field, `repository.full_name`, via the base `Handler#stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` then triggers `stack.sync_github(expected_head_sha: params.after)` for every matching stack [6](#0-5) .

The binding that should hold is: `repository_owner (used to select the secret that authenticates the request)` == `repository.full_name owner (used to pick the Repository/Stack that gets synced)`. Nothing in the controller or in `Handler` enforces this equality. `repository.owner.login` and `repository.full_name` are two independently attacker-controlled JSON keys inside the same signed raw body — the signature only proves *that org's* secret was used to sign the bytes, not that the two fields are internally consistent.

**Attack path:** An attacker who operates their own GitHub organization/repo and has installed the same Shipit-connected GitHub App on it (a routine, unprivileged action any GitHub user can do for an app that supports multi-tenant installs, or simply an attacker who is a legitimate, low-privilege installer for one org configured in Shipit) knows/can obtain the `webhook_secret` delivery for their own org's events, since GitHub signs webhooks per-installation and delivers them to the app's single configured URL (`/webhooks`) — the attacker can locally craft an arbitrary JSON body, sign it with the secret associated with the org they own/control, and set `repository.owner.login` to their own org (so `verify_signature` picks their org's secret and it validates), while setting `repository.full_name` to `victim-org/some-repo` (a Stack unrelated to the attacker's org that already exists in Shipit). Because the handler dispatch keys strictly off `full_name`, the forged, self-signed payload is processed as if it originated from the victim repository.

### Impact Explanation
For the `push` event this results in an attacker being able to forge a `GithubSyncJob`/`sync_github` trigger against a victim's `Stack`, using an arbitrary crafted commit SHA (`expected_head_sha`) and forcing state sync outside actual GitHub state for that repository — cross-organization/cross-repository interference within the same Shipit deployment. This crosses the "cross-repository writes" boundary called out in scope, since the write/trigger target (victim repo's stack sync/state) is decoupled from the credential (webhook secret) that authenticated the request.

### Likelihood Explanation
Requires the attacker to control at least one organization/installation configured in the same multi-tenant Shipit deployment (a documented, supported configuration per `config/secrets.development.example.yml`). No repository write access, `ApiClient` token, or GitHub App private key is needed — only knowledge of a webhook secret for an org the attacker legitimately controls, which is inherent to owning that org's GitHub App installation. This is a moderate-likelihood scenario limited to multi-org Shipit deployments; for single-organization deployments (the common case) the attack is not exploitable because there is only one secret/org to select in the first place.

### Recommendation
Bind the field used to select the verifying secret to the field used for target resolution: derive both `repository_owner` (for secret selection) and the target repository from the same trusted source, or explicitly assert `repository.full_name.split('/').first == repository_owner` (case-insensitively) before dispatching to handlers, rejecting the request with 422 otherwise.

### Proof of Concept
```ruby
# Attacker controls "attacker-org" (has an app installation + knows its webhook_secret).
# Victim stack exists at "victim-org/prod-app" in the same Shipit instance.

payload = {
  "ref" => "refs/heads/main",
  "after" => "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository" => {
    "owner" => { "login" => "attacker-org" },   # used only for verify_signature
    "full_name" => "victim-org/prod-app"        # used by PushHandler#stacks to pick target
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_orgs_known_webhook_secret, payload)

post "/webhooks",
  body: payload,
  headers: { "X-Github-Event" => "push", "X-Hub-Signature" => signature }

# verify_signature resolves Shipit.github(organization: "attacker-org") -> succeeds with attacker's own secret
# PushHandler resolves Repository.from_github_repo_name("victim-org/prod-app") -> triggers sync on victim's stack
```
