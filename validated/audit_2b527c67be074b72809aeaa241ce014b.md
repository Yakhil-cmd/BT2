### Title
Webhook signature verification is bypassed for orgs with no `webhook_secret`, while the forged event's target repository is taken from an unrelated, unverified payload field — ([File: lib/shipit/github_app.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the GitHub organization resolved from the payload. Shipit supports multiple GitHub Apps/organizations simultaneously, each selected purely from the *sender-supplied* `repository.owner.login` (or `organization.login`) field in the webhook body. The event handlers, however, resolve the repository/stack to act on from a completely different, equally attacker-controlled field: `payload.dig('repository', 'full_name')`. These two fields are never cross-checked. This breaks the binding "organization that authenticated == repository that is written": an attacker can pick an org with a blank `webhook_secret` to trivially pass signature verification, while pointing `repository.full_name` at a stack belonging to a different, properly-secured organization.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` used to verify the request purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

That `GitHubApp` instance's verification method is: [3](#0-2) 

Note the `return true unless webhook_secret` short-circuit: if the selected organization's config has no `webhook_secret` set (a state explicitly supported/documented, e.g. `webhook_secret: # nil` in `docs/setup.md` and `config/secrets.development.example.yml`, and reachable per-organization in the multi-app scheme), **any** signature (or none) is accepted for that organization.

Meanwhile, the actual entity the event is applied to — the repository/stack whose commits, statuses, checks, etc. get mutated — is derived independently: [4](#0-3) 

Both `repository.owner.login` (used only to pick the verifying `GitHubApp`/secret) and `repository.full_name` (used to pick the stack that is actually written to) live in the same attacker-supplied JSON body and are never checked for consistency. Multi-organization support is a first-class, documented engine feature: [5](#0-4) 

So an attacker who knows (or guesses) that any one configured organization on the instance has a blank `webhook_secret` can craft a POST to `/webhooks` with `repository.owner.login` = that unsecured org, but `repository.full_name` = a repository/stack belonging to a *different*, secured organization. `verify_signature` passes trivially (no HMAC needed), and the handler dispatch (`Shipit::Webhooks.for_event`) then processes the event against the targeted stack as if GitHub itself had sent it. [6](#0-5) [7](#0-6) 

### Impact Explanation
Downstream handlers persist payload content directly with no independent confirmation against GitHub's API for the target repository. For example, the `status` handler persists commit status fields (`state`, `context`, `description`, `target_url`) verbatim from the forged payload for an arbitrary existing commit sha in the targeted stack: [8](#0-7) 

Shipit's deploy-safety logic gates deploys on commit statuses/checks. By injecting a fabricated `success` status for a required CI context on a commit in a stack the attacker does not otherwise control, the attacker can make an unsafe/malicious commit appear deployable, leading to an **unauthorized deploy** — one of the explicitly accepted impacts. The `push` event path similarly lets an attacker trigger `GithubSyncJob` for an arbitrary stack at an attacker-chosen `expected_head_sha`, and `membership`/`check_suite` events let the attacker inject team/user/check-run state for a repository it never authenticated for. This is a Critical/High-tier engine flaw: an unprivileged, unauthenticated network attacker (no session, no `ApiClient` token, no `webhook_secret` knowledge) can write state into stacks belonging to an organization it never authenticated against.

### Likelihood Explanation
Likelihood depends on at least one configured GitHub organization having a blank/unset `webhook_secret` while at least one other stack exists under a different organization/app config — a state the engine itself documents and permits (`webhook_secret` is commented as optional/nil in the shipped example configs and setup docs), rather than a hard requirement violation of how the engine must be mounted. Any installation running the documented multi-organization configuration without setting every org's `webhook_secret` (e.g. during rollout, staging orgs, or orgs onboarded without configuring the GitHub App webhook secret yet) is exposed. No credentials, sessions, or GitHub App keys are required by the attacker.

### Recommendation
- Remove the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`; treat a missing `webhook_secret` as verification failure (or refuse to boot/route webhooks for orgs without a configured secret), not as an implicit pass.
- Cross-validate that the organization used to select the verifying app config (`repository.owner.login` / `organization.login`) matches the organization implied by `repository.full_name` before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
1. Configure Shipit with two organizations: `SecureOrg` (valid `webhook_secret`) and `LegacyOrg` (`webhook_secret` left blank, as shown supported in `docs/setup.md` / `config/secrets.development.example.yml`). `SecureOrg/target-repo` has an existing tracked stack and commit `abcd123`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {
    "owner": { "login": "LegacyOrg" },
    "full_name": "SecureOrg/target-repo"
  },
  "sha": "abcd123",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
Omit or send any garbage `X-Hub-Signature`.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "LegacyOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `Handlers::StatusHandler` (dispatched via `Shipit::Webhooks.for_event('status')`) resolves the target stack via `payload.dig('repository', 'full_name')` = `"SecureOrg/target-repo"`, and creates a fabricated `success` status on commit `abcd123`, satisfying the `ci/required-check` gate used by deploy safety checks for `SecureOrg`'s stack — despite the attacker never possessing `SecureOrg`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
