### Title
`StatusHandler#process` writes commit statuses via a bare `Commit.where(sha:)` scan with no ownership check on `repository_owner`/`repository.full_name` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::Handler` exposes a `stacks` helper that scopes lookups to the repository named in the webhook payload, but `StatusHandler#process` never calls it, instead running `Commit.where(sha: params.sha)` unscoped by repository. Since `WebhooksController#verify_signature` only uses `repository_owner` to pick which GitHub App secret verifies the HMAC signature and never uses it to constrain which rows get mutated, an attacker who owns any GitHub repository configured in Shipit can send a validly-signed `status` webhook for their own repo and have it mutate `Commit`/`Status` rows belonging to any other stack, as long as the `sha` in the payload matches an existing commit row (e.g., a real upstream sha, submodule sha, or otherwise duplicated hash across repos).

### Finding Description
The broken binding, stated as an equality that should hold but does not: `repository_owner` (used by `WebhooksController#verify_signature` in `app/controllers/shipit/webhooks_controller.rb` at `Shipit.github(organization: repository_owner)` and to select the signing secret) must equal `Commit#stack.repository.owner`/`full_name` for every `Commit` row mutated by the handler that was authenticated under that owner. It does not.

Trace:
- `WebhooksController#create` parses JSON and dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0)  after `before_action :verify_signature`, which derives `repository_owner` purely from `params.dig('repository', 'owner', 'login')` to select `Shipit.github(organization: repository_owner)` for HMAC verification, and logs it, but never uses it again [2](#0-1) .
- The base `Handler` class defines a `stacks` helper that scopes to the payload's repository: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [3](#0-2) .
- `StatusHandler#process` ignores this helper entirely and queries commits globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .
- `Commit` has no unique/scoped constraint tying `sha` to a specific repository at the database query level in this handler - `sha` lookups elsewhere (e.g. `by_sha`) are also unscoped, but those are used with an authenticated stack context, not from an unauthenticated webhook boundary.

Attacker request: attacker owns (or controls) a GitHub org/repo that is registered in `Shipit.github_teams`/configured with a valid webhook secret (this is a normal, unprivileged self-service GitHub App/webhook installation on their own repo - no Shipit secret needed). They send `POST /webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with their own repo's legitimately-provisioned secret, and body `{"repository": {"full_name": "attacker/repo", "owner": {"login": "attacker"}}, "sha": "<victim commit sha>", "state": "success", ...}`. `verify_signature` succeeds because it only checks the signature against the attacker-owned org's secret. `StatusHandler.call` then finds and mutates any `Commit` row anywhere in the database with a matching `sha`, regardless of which stack/repository it belongs to.

Why this matters as cross-tenant: `create_status_from_github!` creates a `Status` record and can flip `Commit#deployable?`/`blocked?` semantics via `add_status`, which schedules merges (`stack.schedule_merges`) and continuous deployment (`ContinuousDeliveryJob.perform_later`) for the **victim's stack** based on attacker-forged status state [5](#0-4) [6](#0-5) .

Existing guards do not prevent this: `verify_signature` authenticates *who* sent the webhook (by org secret) but that value is never used to scope the mutation; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` only validates `sha`/`state`/etc. are present and typed, not that they belong to the claimed repository; there is no `Stack`/`Repository` filter applied at all in this handler.

### Impact Explanation
A payload authenticated as belonging to Attacker's repository can inject/forge a commit status (success/failure/pending, with arbitrary `description`/`target_url`) onto a `Commit` belonging to any other stack in the Shipit instance whose `sha` happens to coincide (real-world sha collisions occur naturally via shared upstream history, submodules, cherry-picks, or vendored/monorepo mirrors, and the attacker can also directly reference well-known public shas that a victim stack has already ingested). This can flip a victim commit from blocked to `deployable?`, trigger `stack.schedule_merges`/`ContinuousDeliveryJob`, or conversely mark a legitimate deploy candidate as failing to block deploys - i.e., "a payload for one repository mutating another's stack, commit, task or team," matching the **Critical** category explicitly listed in the rules. The attacker can repeat this against any stack/commit for which they can find or predict a matching sha.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only a GitHub repository they control that is onboarded to the Shipit instance's GitHub App/webhook configuration (a normal, self-service, unprivileged action available to any GitHub user who can add a webhook to their own repo), and knowledge of a target `sha` that exists in a victim's `Commit` table. No Shipit session, API token, or GitHub org secret for the victim is required. The main constraint is sha discovery/collision, but this is feasible in practice (shared commits across forks/mirrors, public shas, monorepo submodule shas) and costs the attacker nothing beyond sending one signed HTTP request per attempt, fully repeatable.

### Recommendation
In `app/models/shipit/webhooks/handlers/status_handler.rb`, scope the lookup through the base class's `stacks` helper instead of a bare `Commit.where`, e.g. `Commit.where(sha: params.sha, stack: stacks)` (or `Commit.joins(:stack).merge(stacks)`), so a status webhook can only mutate commits belonging to the repository named in `payload['repository']['full_name']` — the same repository that was authenticated via `verify_signature`. Apply the same scoping check to any other `Handler` subclass that queries by identifiers (`sha`, PR number, etc.) without going through `stacks`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (minitest, no live GitHub)
test "status webhook does not mutate commits belonging to a different repository" do
  victim_repo = shipit_repositories(:shipit) # or create Repository owned by "victim-org"
  attacker_repo_full_name = "attacker-org/attacker-repo"

  victim_stack = victim_repo.stacks.first
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  payload = {
    "repository" => { "full_name" => attacker_repo_full_name, "owner" => { "login" => "attacker-org" } },
    "sha" => victim_commit.sha,
    "state" => "success"
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  # Equality check: repository_owner used for signature ("attacker-org")
  # must equal victim_commit.stack.repository owner for the mutation to be authorized.
  refute_equal payload.dig("repository", "owner", "login"),
               victim_commit.stack.repository.owner
  # Current code fails this test because create_status_from_github! is still called,
  # i.e. victim_commit.statuses.count changes despite the mismatched owner.
end
```
This demonstrates the equality `repository_owner (attacker-org) == victim_commit.stack.repository.owner (victim-org)` is false, yet `StatusHandler#process` still mutates `victim_commit`, confirming the missing repository scope.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
