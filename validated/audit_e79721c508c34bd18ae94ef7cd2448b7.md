## Title
Cross-organization webhook signature confusion allows unauthorized escalation into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The TRST-M-5 bug class is a mismatch between the value that is *verified* and the value that is later *acted upon*. Shipit-engine has the same class of bug in its webhook pipeline: the GitHub organization used to select which `webhook_secret` verifies the inbound HMAC signature is read from a different, independently-controlled JSON field than the organization the event handler actually uses to mutate authorization state (`Team` membership, which feeds `Shipit.github_teams`).

### Finding Description
`WebhooksController#verify_signature` selects the signing secret to check against using `repository_owner`, which prefers `repository.owner.login` and only falls back to `organization.login` if `repository` is absent: [1](#0-0) [2](#0-1) 

That organization name is passed into `Shipit.github(organization:)`, which in multi-org deployments (a documented, supported configuration) looks up a per-organization config, including a per-organization `webhook_secret`: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank — and `webhook_secret` is explicitly documented/scaffolded as optional (`template.rb`, `docs/setup.md`, `config/secrets.development.example.yml`): [4](#0-3) 

Meanwhile, `MembershipHandler#process` (which mutates `Team` membership) trusts `params.organization.login` verbatim — a field that is completely independent of `repository.owner.login`: [5](#0-4) 

Because GitHub's `membership` event payload has no `repository` key, `repository_owner` normally falls back to `organization.login`, coupling verification and action for legitimate GitHub-issued events. But an attacker POSTing directly and unauthenticated to `/webhooks` (the endpoint has no session/token/API-key requirement — only `verify_signature`) can add an *extra* `repository.owner.login` field naming any organization configured in Shipit's multi-org `github:` section that happens to have no `webhook_secret` set. This makes `verify_signature` pick that organization's (secret-less) `GitHubApp` and pass verification unconditionally, while the `organization.login` field consumed by `MembershipHandler` can independently name the *victim* organization whose `Team` is used for authorization (`Shipit.github_teams`).

`Team.find_or_create_by!(github_id: params.team.id)` matches purely on GitHub's numeric team id, so if the attacker supplies the real `github_id`/`slug`/`organization` of an existing authorized team (discoverable via GitHub's own team APIs for any team they can see), the existing `Team` record used by `Shipit.github_teams` is updated, and `team.add_member(User.find_or_create_by_login!(params.member.login))` adds an attacker-chosen login to it: [6](#0-5) 

That membership directly satisfies `User#authorized?`, which is the sole gate protecting the entire Shipit UI/session flow: [7](#0-6) [8](#0-7) 

The equality that should hold is:
`organization used to select the verifying webhook_secret == organization whose Team/authorization state the handler mutates`

The attack breaks this equality by supplying two different organization-bearing fields in one unauthenticated request.

### Impact Explanation
This lets an unprivileged, unauthenticated internet attacker forge a `membership` webhook that adds an arbitrary GitHub login (their own account) to a `Team` gating access via `Shipit.oauth_teams`/`Shipit.github_teams`, bypassing the intended GitHub-team-based authorization entirely — an escalation into `Shipit.github_teams` authorization, matching the defined High-impact category. Once that login can complete OAuth and pass `authorized?`, they gain full access to the Shipit UI for every stack/repository the instance manages (potential path to unauthorized deploys/rollbacks).

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (documented, supported feature) where at least one configured organization has no `webhook_secret` — the default/example configuration in `template.rb` and `config/secrets.development.example.yml` ships with `webhook_secret:` blank, so this is a very plausible real-world state, not a misconfiguration outside the documented setup; and (2) knowledge of the target team's real GitHub `github_id`/`slug`/`organization`, obtainable from GitHub's own (often publicly visible) team APIs. No Shipit session, API token, or webhook secret for the *victim* org is required.

### Recommendation
Bind webhook signature verification and payload processing to the *same* organization value. Concretely: derive `repository_owner` consistently for the event type actually being processed (do not allow a `repository.owner.login` fallback to leak into events, like `membership`, that are organization-scoped by GitHub's own schema), reject payloads containing unexpected/extra top-level keys not defined for that event, and/or verify that `MembershipHandler`'s `params.organization.login` matches the organization whose secret validated the signature before mutating any `Team`.

### Proof of Concept
1. Deployment configures multi-org GitHub apps: `OrgA` (attacker aware, `webhook_secret` blank) and `shopify` (victim org, `oauth.teams` includes `shopify/developers`, real `webhook_secret` set).
2. Attacker sends, unauthenticated, with no valid `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: membership

{
  "action": "added",
  "team": {"id": <real github id of shopify/developers>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/..."},
  "organization": {"login": "shopify"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "OrgA"}}
}
```
3. `verify_signature` computes `repository_owner` = `"OrgA"` (present via `repository.owner.login`), calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` with no valid signature required (`lib/shipit/github_app.rb:76-83`).
4. `MembershipHandler#process` runs using `params.organization.login == "shopify"`, finds the existing authorized `Team` by `github_id`, and adds `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`, `app/models/shipit/team.rb:41-43`).
5. Attacker completes GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns `true` via the forged team membership (`app/models/shipit/user.rb:80-82`), granting full access to the Shipit application (`app/controllers/concerns/shipit/authentication.rb:20-34`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
