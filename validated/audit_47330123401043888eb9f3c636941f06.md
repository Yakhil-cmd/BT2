### Title
Stack-scoped API token authorizes cross-stack read of deploy/build state via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` authenticates a token with `ApiClient.authenticate(params[:token])` and checks only the `read:stack` permission flag, but resolves the target `Stack` straight from the `stack_id` URL param instead of through the scoped `stacks`/`stack` helpers used everywhere else in the API. Any `ApiClient` token that is scoped to one stack (`ApiClient#stack_id`) can be replayed against any other stack's `/api/*stack_id/ccmenu` URL to read that stack's build/deploy status.

### Finding Description
`Api::BaseController` defines the scoping contract used by every other API controller: [1](#0-0)  — `stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` loads the record through that scoped relation.

`Api::CCMenuController` overrides `stack` to skip this scoping entirely: [2](#0-1)  — it calls `Stack.from_param!(params[:stack_id])` directly, and its `authenticate_api_client` override authenticates via the plain `token` query parameter instead of the Basic-Auth flow used in `BaseController#authenticate_api_client` (app/controllers/shipit/api/base_controller.rb:48-56).

The only authorization check performed is `require_permission :read, :stack`, which resolves to `ApiClient#check_permissions!` [3](#0-2)  — a permission-name check independent of which specific stack is being requested.

The binding that should hold is: `current_api_client.stack_id (the stack the token authorises) == stack (the stack the request touches)`. `CCMenuController#stack` breaks this equality by resolving the stack purely from the attacker-supplied `stack_id` path/query segment, never consulting `current_api_client.stack_id`. This is the same class of bug as the reported voucher issue: a credential (the token/voucher) is verified for authenticity/permission, but the object it is applied to (the recipient address / the target stack) is taken from unverified, attacker-controlled request data instead of being bound into what was authorized.

### Impact Explanation
Any holder of a stack-scoped, `read:stack`-permission API token (e.g., a CCMenu integration token generated by `CCMenuUrlController` for one specific stack, or any `ApiClient` created with a `stack` association) can query the CCMenu XML endpoint for arbitrary other stacks by changing the `stack_id` in the URL, obtaining that stack's deploy/build history, lock status, and last build status/label — data the token was never scoped to access. This matches the in-scope "High" impact category of unauthenticated/unauthorized read of stack state.

### Likelihood Explanation
The `token` is passed as a URL query string parameter by design (`CCMenuUrlController#fetch` embeds it in a generated URL meant to be pasted into third-party CI-monitoring tools), so it is likely to leak into browser history, logs, referrer headers, or shared dashboards — making token possession by an unintended party plausible. Exploitation requires no further privilege: only changing one URL parameter (`stack_id`) once a valid token for any stack is obtained.

### Recommendation
In `Api::CCMenuController`, remove the `stack` override (or reimplement it via the inherited `stacks` scoped relation) so the stack the request touches is always intersected with `current_api_client.stack_id` when the client is stack-scoped, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, consistent with `Api::BaseController`. If unscoped/global CCMenu tokens are an intentional feature, explicitly document and enforce it only for clients with `stack_id.nil?`, and reject stack-scoped tokens whose `stack_id` does not match the requested `stack_id`.

### Proof of Concept
1. Create two stacks, A and B.
2. Generate a CCMenu URL/token for stack A via `CCMenuUrlController#fetch` (or create an `ApiClient` with `stack: A, permissions: ['read:stack']`).
3. Call `GET /api/<owner>/<repoB>/<env>/ccmenu?token=<A's token>` (i.e., substitute stack B's `stack_id` while keeping A's token).
4. Observe the response returns stack B's deploy/lock/build status, even though the token was only ever intended/scoped for stack A — confirmed by `Api::CCMenuController#stack` at [4](#0-3)  never checking `current_api_client.stack_id`.
