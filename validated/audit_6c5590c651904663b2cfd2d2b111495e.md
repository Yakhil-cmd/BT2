## Title
Malicious secondary AA recipient can force revert of the entire parent AA response, blocking payments to all other co-recipients - (File: `aa_composer.js`)

### Summary
The external report flags `send()`-based multi-payee payouts where one malicious/reverting destination can block funds meant for all other payees in the same transaction. Ocore's Autonomous Agent (AA) execution engine has a structurally identical trust assumption: when a primary AA's response sends payments to multiple addresses and one of those addresses happens to be another AA, that secondary AA is invoked as a "secondary trigger" in the same atomic execution. If that single secondary AA bounces, the entire primary AA response — including all payments to every *other* co-recipient in that response — is rolled back and replaced with a bounce.

### Finding Description
When a primary AA sends a payment message with multiple outputs, `sendUnit()` builds the response unit and then calls `handleSecondaryTriggers()` for every output address that is itself an AA [1](#0-0) .

`handleSecondaryTriggers` processes each recipient AA sequentially with `async.eachSeries`. If *any single* secondary AA in that list bounces with an error, the iteration's error callback is triggered for the whole batch, not just for the failing recipient [2](#0-1) .

That error handler calls `revert()`, which rolls the connection back to `SAVEPOINT initial_balances`, clears the batch, discards `arrResponses` for the entire chain, and finally calls `bounce()` on the *primary* trigger [3](#0-2) . `bounce()` then discards the state update and returns only the bounce-fee-deducted change to the original trigger sender, sending no payments to any of the originally intended recipients [4](#0-3) .

Because this failure propagation is all-or-nothing across the *entire set of outputs* in the payment message, a single malicious or intentionally-reverting AA address included as one of several payment destinations can unconditionally veto delivery of funds to every other (unrelated, honest) destination in that same trigger execution — exactly the "one payee blocks all payees" pattern described in the source report, just realized through AA secondary-trigger semantics instead of Solidity `send()`.

### Impact Explanation
Any AA design that pays out to multiple recipients where recipient addresses can be attacker-influenced (e.g., a splitter/distributor AA, a marketplace AA paying seller + referrer + fee-AA, a DAO payout AA) is exposed: an attacker who can get their own AA registered as one of the payees (or who deploys/controls an AA address that legitimate protocols route funds to) can make that AA always bounce. Every trigger to the parent AA that would route funds through the attacker's AA is then repeatedly reverted, meaning:
- No co-recipient (including honest, unrelated users) ever receives their share.
- The parent AA's state changes for that call are lost (bounced), so recorded logic (e.g., marking an order paid, releasing an asset) never completes.
- This is a persistent, unpriviledged, self-service denial/griefing vector that "freezes" fund flow through the AA indefinitely.

This matches the "AA fund loss or freezing" acceptance criterion: an unprivileged actor (whoever deploys the malicious secondary AA and gets it referenced as an output address) can indefinitely block distribution of funds intended for other parties.

### Likelihood Explanation
Reaching this requires only that (a) a target AA sends payments to multiple recipients in a single response and (b) at least one recipient address is (or can be made to be) an AA under attacker control — both of which are common, unprivileged design patterns (e.g., "send fee to AA X, remainder to user"), since AA definitions are permissionless to deploy and any base32 address can subsequently become an AA address before being used as an output. No special privileges, race conditions, or network assumptions are needed; the attacker only needs to write a trivial AA that always fails/bounces and ensure it is used as one of the payees.

### Recommendation
- Document/enforce that failures of *secondary* AA triggers should not automatically revert the *entire* primary response; consider isolating per-output failure handling (e.g., skip/void just the failed secondary trigger's effects, or route its share to a fallback/bounce path) rather than a global `revert()` of the whole batch.
- Where full-batch atomicity is intentional and required by AA semantics, clearly document this to AA authors so that multi-recipient AAs avoid delegating any output address to autonomous/AA-controlled destinations without allow-listing, and provide primitives (e.g., a "try/catch"-style directive) for AA authors to isolate a single payout's failure from the rest of the batch.

### Proof of Concept
1. Deploy `MaliciousAA` whose `messages` always evaluate to `bounce('always fail')` regardless of trigger contents.
2. Deploy `SplitterAA` whose response, for any trigger, sends payments in a single message with two outputs: one to a normal user address `UserA`, and one to `MaliciousAA`'s address.
3. Send a trigger unit to `SplitterAA`.
4. Observe: `SplitterAA`'s `sendUnit()` completes and calls `handleSecondaryTriggers()`, which invokes `MaliciousAA` as a secondary trigger [5](#0-4) ; `MaliciousAA` bounces, `async.eachSeries`'s final callback receives an error and calls `revert()` [6](#0-5) , which rolls back and bounces the entire trigger [3](#0-2) .
5. Result: `UserA` never receives the payment that `SplitterAA` intended for them, even though `UserA` and the trigger sender did nothing wrong — solely because `MaliciousAA` was included as a co-recipient.
