### Title
Cross-organization forged commit status via webhook binds the wrong Github organization's signature to any other organization's commits - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the `webhook_secret` of the organization named in `repository.owner.login` (or `organization.login`), but `Shipit::Webhooks::Handlers::StatusHandler#process` writes the resulting CI status onto **any** `Commit` row in the whole database that matches the raw `sha` field, with no scoping back to the organization/repository that was actually authenticated. In a multi-tenant Shipit install (the documented "Using Multiple Github Applications" mode, `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls one onboarded, low-trust GitHub organization (and therefore knows/controls that organization's `webhook_secret`) can forge a `status` webhook that is validly signed for their own org, but whose `sha` collides with a commit that belongs to a completely different, unrelated organization's stack on the same Shipit instance. This breaks the binding "organization that authenticated == repository/commit that is written."

### Finding Description
- `WebhooksController#verify_signature` selects which `GitHubApp`/secret to use for HMAC validation purely from attacker-supplied payload fields: `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` looks up per-organization app config (multi-org support is a supported deployment mode, see `docs/setup.md` and `lib/shipit.rb`). [3](#0-2) 
- Once the HMAC check passes (using the secret belonging to the org named in the payload), `WebhooksController#create` dispatches the entire, attacker-controlled JSON body to the registered handler for the event, with no re-validation that the rest of the payload actually belongs to that organization: [4](#0-3) 
- Most handlers (`Handler#stacks`/`#repository_name`) at least scope by `payload.dig('repository','full_name')`: [5](#0-4) 
- But `StatusHandler`, which handles the GitHub `status` event, does **not** inherit that scoping. It looks up commits solely by `sha`, globally, across every stack/repository configured in the Shipit instance, and writes a CI status to each match: [6](#0-5) 

Because the signature check only proves "this body was signed with organization X's webhook secret," and `StatusHandler` never checks that the target commit's repository/organization is X, an attacker who is a legitimate admin of a low-trust GitHub organization onboarded to the same Shipit instance can:
1. Discover or guess a commit `sha` belonging to a different, higher-trust stack (SHAs are visible via Shipit's own UI/API, PR pages, etc., which is normal, non-privileged information for a stack the attacker may not have deploy rights to).
2. Craft a `status` webhook payload with `repository.owner.login` set to their own org (so `verify_signature` picks their own known secret) and `sha`/`state`/`context`/`target_url` referencing the target commit and a forged "success" status.
3. Sign the raw body with their own org's webhook secret and POST it to `/webhooks`.
4. `Commit.where(sha: params.sha)` matches the target commit (regardless of stack/repository) and `create_status_from_github!` records the forged status for it.

### Impact Explanation
Commit statuses gate deploy eligibility: `Commit#deployable?` requires `success?` and no blocking status, and `ci.require`/`ci.blocking` in `shipit.yml` are enforced via `required_statuses`/`blocking_statuses`, which are computed from these same `Status` rows. [7](#0-6) [8](#0-7) 
By forging a "success" status context that a target stack's `shipit.yml` marks as `ci.require`, an attacker with credentials scoped to an unrelated, low-trust organization can make an unreviewed/failing commit in a foreign organization's stack appear `deployable?`, enabling an unauthorized deploy of that commit through Shipit's normal deploy flow (`api/deploys` or the UI), and/or unblock/advance the merge queue for that unrelated repository. This is a cross-repository/cross-organization write of trusted CI state and directly undermines Shipit's authorization boundary between tenants sharing one instance — matching the Critical "cross-repository writes"/"unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, non-privileged (with respect to the *victim* organization) administrator/owner of any *other* GitHub organization/app that is configured in the same multi-tenant Shipit deployment — a scenario the project explicitly documents and supports ("Using Multiple Github Applications"). No access to the victim's repository, Shipit session, `ApiClient` token, or GitHub App private key is required; the attacker only needs the webhook secret they themselves control for their own org and a target commit SHA, which is ordinary, non-secret information (visible on GitHub or in Shipit itself). This is a realistic, low-effort attack path for any Shipit instance hosting multiple organizations with different trust levels.

### Recommendation
In `StatusHandler#process`, scope the query to commits whose stack's repository matches the authenticated `repository_owner`/`repository.full_name`, mirroring the base `Handler#stacks`/`#repository_name` scoping used by other handlers, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` instead of `Commit.where(sha: params.sha)`. More generally, `WebhooksController` should pass the verified organization down to every handler and each handler should assert that the repository referenced in the payload belongs to that verified organization before mutating any state, rather than trusting `repository.full_name`/`sha` independently of the signature-selected organization.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, unrelated), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Identify a commit `sha` in a stack belonging to `OrgB`'s repository that Shipit already tracks (e.g., an open, unreviewed PR head commit) and note a status `context` that `OrgB`'s `shipit.yml` lists under `ci.require` (e.g. `ci/circleci`).
3. Build a JSON body:
```json
{
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>` using the secret the attacker legitimately knows for `OrgA`.
5. `POST /webhooks` with header `X-Github-Event: status` and the signed body.
6. `verify_signature` passes because it authenticates against `OrgA`'s secret; `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `success` status on the `OrgB` commit via `create_status_from_github!`, satisfying `ci.require` for a repository the attacker has no rights to, regardless of the org used to sign the request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
