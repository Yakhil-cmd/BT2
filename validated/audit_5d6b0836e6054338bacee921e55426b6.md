### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets an attacker-signed webhook from an unrelated repository forge `security/scan` status on a victim stack's commit, triggering bot-identity auto-deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, with no filter on `repository`/`stack`, so any signed webhook payload can write a `Status` onto every commit in the entire installation sharing that literal SHA string. Signature verification in `Shipit::WebhooksController#verify_signature` only proves the payload's declared `repository.owner.login` owns a registered webhook secret — it does not bind that identity to which commit/stack rows get mutated.

### Finding Description
The broken binding: the code implicitly assumes
`verify_signature(payload.repository_owner) == true` implies `commit.stack.repository.owns(payload.sha)`,
but these are two unrelated checks. `WebhooksController#verify_signature` computes the HMAC only against `repository_owner` derived from the JSON body [1](#0-0) [2](#0-1) , while `StatusHandler#process` performs a completely unscoped write:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

There is no join/filter against `repository_owner`/`repository.full_name` from the same payload. Because git SHAs are 40-hex strings and the target commit's SHA is public information (visible on the victim's Shipit stack page or on GitHub itself), an attacker who legitimately owns any repository registered in Shipit (and therefore knows/controls its webhook secret, as required for a real GitHub-configured webhook) can craft an arbitrary JSON body — `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim-commit-sha>", "context": "security/scan", "state": "success"}` — sign it with their own secret, and POST it to `/webhooks` with `X-Github-Event: status`. `verify_signature` succeeds because the HMAC matches the attacker's own org secret; `drop_unhandled_event` passes because `status` is a handled event; the `ExplicitParameters` schema in `StatusHandler` only validates types, not repository ownership. `Commit.where(sha: ...)` then finds and updates the victim's commit row regardless of which repository the signature verification was performed for.

On the victim's `Commit`, `add_status` recomputes `Status::Group` and, if the state transitions to non-pending/success, calls `stack.schedule_merges` and evaluates `deployable?` / `schedule_continuous_delivery` [4](#0-3) [5](#0-4) [6](#0-5) . If the victim stack has `bot_login` configured (`Shipit.user` used for auto-triggered deploys), a flipped `security/scan` status can make an already-blocked commit `deployable?` (or vice-versa block a good commit), causing `ContinuousDeliveryJob` to ship or withhold a deploy under the bot's identity — with no action from a maintainer of that stack's actual repository.

None of the listed guards prevent this: `verify_signature` authenticates the sender's org, not the row being mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `status_handler.rb` [7](#0-6)  has no repository field requirement at all.

### Impact Explanation
An attacker who owns/controls any repository with a Shipit-registered webhook secret can write forged CI status onto a **different, unrelated victim stack's commit** purely by reusing a known SHA string. Combined with `bot_login`/continuous-deployment configuration, this can force an unauthorized deploy or block a legitimate deploy — a cross-tenant write with real deploy/rollback consequences, matching the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable against any commit whose SHA is discoverable (which is essentially all commits, since they're visible via the Shipit UI/API or GitHub) and any stack in the same Shipit deployment sharing the `commits` table.

### Likelihood Explanation
Preconditions: attacker needs one legitimately Shipit-registered repository (own repo, own webhook secret — attainable by any GitHub user who can add a repo to the target Shipit instance's configured GitHub App/organization scope, or by owning a repo under an org Shipit already trusts). They need to know the victim's target commit SHA, which is generally public. No Shipit session, API token, or team membership is required — only the ability to sign an HTTP POST with a secret they legitimately possess for their own repository. This is straightforward and repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and similarly in check-run/other SHA-keyed handlers) by the repository asserted in the payload, e.g. join through `Stack`/`Repository` using `params.repository.full_name` (already available on the webhook payload and already used by `verify_signature`) before matching by `sha`, so a status can only affect commits belonging to stacks whose repository matches the authenticated `repository_owner`/`full_name`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` for repository `attacker/repo` and `stack_b` for repository `victim/repo`, with `stack_b` configured with `bot_login` set (continuous deployment enabled) and a `required_status: "security/scan"`.
2. Create `commit = create_commit(stack: stack_b, sha: "abc123...")` and assert `commit.deployable?` is `false` (equality #1: `commit.reload.deployable? == false`).
3. Build a `status` webhook payload with `repository: {full_name: "attacker/repo", owner: {login: "attacker"}}`, `sha: commit.sha`, `context: "security/scan"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (bypassing HTTP layer, simulating a signature that validated for `attacker/repo`).
5. Reload `commit` and assert `commit.deployable? == true` and/or that `ContinuousDeliveryJob` was enqueued for `stack_b` — proving the equality from step 2 flipped even though the authenticated repository (`attacker/repo`) never matches `commit.stack.repository.full_name` (`victim/repo`), demonstrating the invariant "a status affects only the repository that authenticated it" is violated.

        payload = { commit: self, stack:, status: new_status.state }

      end
