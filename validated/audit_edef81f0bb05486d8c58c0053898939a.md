### Title
Webhook signature-selection key is not bound to the payload's target repository, allowing cross-organization commit-status/push/PR forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository_owner`, a value read from the JSON body itself (`repository.owner.login`, falling back to `organization.login`). The event handlers that actually act on the payload, however, look up the target `Stack`/`Repository` using a *different* field of the same body — `repository.full_name` (`Handler#repository_name`). Nothing ties these two fields together, so a party that legitimately controls a GitHub App/organization configured in Shipit (and thus knows that organization's `webhook_secret`) can sign an arbitrary payload with their own secret while setting `repository.full_name` to point at a repository belonging to a *different* organization also configured in the same Shipit instance. This is the same class of bug as the reported one: a value used to select/derive the verification context (destination chain ID / here, the signing organization) is decoupled from the value the instruction/handler actually operates on (the account seeds / here, the acted-upon repository).

### Finding Description
- `verify_signature` computes `repository_owner` purely from attacker-controlled JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then does `Shipit.github(organization: repository_owner)` to fetch that organization's `webhook_secret`, and verifies `X-Hub-Signature` against `request.raw_post` using that secret. [1](#0-0) 
- `Shipit.github` / `github_app_config` look up per-organization secrets from a keyed config (as shown by the multi-org fixture `secrets_double_github_app.yml` with distinct `OrgOne`/`OrgTwo` webhook secrets), confirming multiple independent trust domains can be configured in one Shipit instance. [2](#0-1) 
- After signature verification succeeds, `WebhooksController#create` dispatches the full parsed payload to handlers registered for the event, with no re-check that `repository_owner` matches the repository the handler will act on. [3](#0-2) 
- All handlers derive their target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a completely separate field from `repository.owner.login` used for signature-key selection. [4](#0-3) [5](#0-4) 

Because HMAC verification only proves "this body was signed with Org A's secret," and the body content is entirely attacker-defined JSON, an attacker who owns/administers Org A's GitHub App (and therefore its webhook secret) can set `repository.owner.login = "OrgA"` (so signature-key selection picks Org A's secret and passes) while setting `repository.full_name = "OrgB/victim-repo"` (an unrelated organization/repository also configured as a Shipit stack). The equality that should hold — *organization whose secret authenticated the request == organization owning the repository being acted upon* — is broken.

### Impact Explanation
With this mismatch, an attacker can drive several handlers against a victim repository they do not control:
- `StatusHandler#process` writes arbitrary commit statuses (`state`, `context`, `target_url`, `description`) onto any commit SHA that exists in the datastore, regardless of which org it belongs to. [6](#0-5) 
- `PushHandler#process` and `CheckSuiteHandler#process` trigger `stack.sync_github`/`schedule_refresh_check_runs!` against any stack matched by `repository.full_name`, i.e., cross-organization triggering of GitHub sync/refresh jobs. [7](#0-6) [8](#0-7) 
- `PullRequest::OpenedHandler`/`ClosedHandler` can provision or archive review stacks for a repository belonging to another organization. [9](#0-8) 

Since Shipit stacks commonly gate deploys on commit-status/CI checks, forging commit statuses for a victim repository's commit can be used to satisfy deploy-safety checks, contributing to an unauthorized deploy — this falls in the Critical/High bucket described by the rules (cross-repository writes / unauthorized deploy path). This requires the attacker to legitimately control a GitHub App/org that is itself configured in the same Shipit instance (a real but limited precondition — many Shipit deployments host multiple orgs, as evidenced by the `secrets_double_github_app.yml` multi-org fixture), not a fully unauthenticated attacker, but no repository write access to the victim repo is needed.

### Likelihood Explanation
Exploitability is directly tied to how many independent organizations/secrets are configured on one Shipit instance (`github_organizations` returning more than one entry). In that common multi-tenant configuration, any org's own webhook admin can trivially forge cross-org events, since nothing in the code cross-checks `repository.owner.login` against `repository.full_name`'s owner, nor confirms the resolved `Repository` belongs to the organization used for `Shipit.github(organization: repository_owner)`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require and enforce that the organization portion of `repository.full_name` matches `repository_owner` (or, more robustly, always derive the signing key from the same field used to resolve the target repository) before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` (attacker-controlled GitHub App, secret known to attacker) and `OrgB` (victim org, with a repository `OrgB/victim-repo` tracked as a Shipit stack).
2. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac using OrgA's real webhook_secret over the raw body>`.
4. `verify_signature` reads `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check passes (attacker legitimately has this secret). [10](#0-9) 
5. `create` dispatches to `StatusHandler`, which resolves `Commit.where(sha: ...)` — matching the victim commit regardless of organization — and writes a forged `success` status onto it. [6](#0-5)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
