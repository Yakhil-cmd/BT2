### Title
Cross-repository Status webhook applies to Commits of unrelated stacks due to missing repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, without ever checking that `payload.dig('repository','full_name')` matches `commit.stack.repository.full_name`. Since GitHub commit SHAs are only guaranteed unique within a single repository's object graph (they are a deterministic hash of tree/parents/author/committer/timestamp/message, not a cross-repo namespace), a webhook that is legitimately and correctly signed for repo B can write a `Status` onto a `Commit` that actually belongs to stack A.

### Finding Description
The broken binding is:
`payload.dig('repository', 'full_name')` ("attacker/B") ≠ `commit.stack.repository.full_name` ("victim-org/A"), yet the same status is written to the Commit belonging to A.

Code path:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)`, invoking `handler.call(params)`.
- `before_action :verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) resolves `Shipit.github(organization: repository_owner)` using `repository_owner` taken from `payload.dig('repository','owner','login')` — i.e., **the attacker's own organization**, not the victim's. Because repo B is itself a legitimately registered Shipit stack, GitHub signs this webhook with repo B's own valid app/webhook secret. The signature check therefore only proves "this payload is really about repo B", never "this payload's SHA belongs to repo B".
- `Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38) does define a `stacks`/`repository_name` helper meant to scope queries to the repository named in the payload, but `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) never calls it:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally across every stack in the Shipit instance, keyed only on `sha`.

Exploit flow: attacker registers repo B as a Shipit stack (or it's already registered), crafts/produces a commit in repo B whose object content (tree, parents, author, committer, timestamps, message) is byte-identical to a commit already tracked as a `Commit` row under victim stack A — a straightforward outcome for low-entropy commits (e.g., an initial empty-tree commit, or copying a public commit's exact metadata via `git commit-tree`/rebase), no SHA-1 cryptographic collision needed. Attacker then triggers any real CI integration on repo B to POST a `status` event referencing that SHA. GitHub signs it validly for repo B. `verify_signature` passes. `drop_unhandled_event`/`ExplicitParameters` schema pass (state/sha are present and well-formed). `StatusHandler#process` finds the pre-existing `Commit` row for stack A with the same sha and writes the attacker-controlled status/state/description/target_url onto it via `create_status_from_github!`.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) check repository ownership of the matched `Commit` rows; they only authenticate that the payload really originates from the named organization, not that the named organization owns the SHA being mutated.

### Impact Explanation
A payload authenticated only for the attacker's own repo B can write a `Status` row on a `Commit` belonging to victim stack A. Depending on how downstream stack logic consumes `Commit#state`/statuses (e.g., CI gating for merges/deploys), this can influence deploy-readiness or merge-readiness decisions for a repository the attacker never authenticated against — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any known SHA collision the attacker can engineer, and is not limited to one victim stack — any Commit row anywhere in the Shipit instance sharing that literal SHA is affected. This is limited to Commit/Status rows (not RCE or credential leakage), scoped to cross-tenant Commit mutation.

### Likelihood Explanation
Preconditions: repo A and B both registered as Shipit stacks, a `Commit` row for sha=SHA already exists under stack A, and the attacker can produce a commit with byte-identical Git object content in repo B (achievable without breaking SHA-1, by reproducing tree/parents/author/committer/timestamps of a known low-entropy or public commit) and can trigger a real `status` webhook from GitHub for repo B (trivial via any CI hook they control). No Shipit secrets are needed by the attacker — the webhook is genuinely and correctly signed by GitHub for repo B. Feasibility is moderate: engineering an exact SHA match with a specific target commit requires knowing/reproducing that commit's exact metadata, which is realistic for low-entropy commits (e.g., empty initial commits, generated boilerplate) but not for arbitrary high-entropy commits.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks belonging to the payload's repository, e.g. use the existing `stacks` helper from `Handler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the binding `commit.stack.repository.full_name == payload.dig('repository','full_name')` before any status write is applied.

### Proof of Concept
Minitest integration test outline (test/controllers/webhooks_controller_test.rb or test/models pattern):
1. Create `stack_a` for repo `victim-org/A` and `stack_b` for repo `attacker/B`.
2. Seed `commit = shipit_commits(:...)` or `Commit.create!(stack: stack_a, sha: SAME_SHA, ...)`.
3. Build a `status` payload: `{ 'repository' => { 'full_name' => 'attacker/B', 'owner' => {'login' => 'attacker'} }, 'sha' => SAME_SHA, 'state' => 'success' }`.
4. Sign it with `attacker` org's webhook secret (as GitHub legitimately would for repo B) and POST to `/webhooks` with `X-Github-Event: status`.
5. Assert before: `commit.reload.state != 'success'` and `payload['repository']['full_name'] != commit.stack.repository.full_name`.
6. Assert after: response is `200`/`204`, but `commit.reload.state == 'success'` — demonstrating stack A's commit was mutated by a payload authenticated only for repo B, i.e. `commit.stack.repository.full_name` ("victim-org/A") still differs from `payload['repository']['full_name']` ("attacker/B"), proving the binding was violated.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
