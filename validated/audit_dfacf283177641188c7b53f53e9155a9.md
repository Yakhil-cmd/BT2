### Title
`StatusHandler#process` writes Status rows to commits in unrelated repositories by matching on SHA only, letting `MergeRequest::StatusChecker` treat a forged cross-repo status as genuine - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)` and never restricts the query to commits belonging to the stack(s) of the repository named in the webhook payload. Any signed webhook event (verified only against the *sending* organization/app's secret) that names a SHA which also exists in another stack's commit history will write a `Status` onto that other stack's commit, and `MergeRequest::StatusChecker`, built from `head.statuses_and_check_runs`, has no way to distinguish it from a legitimately-scoped status.

### Finding Description
The claimed binding is: for every `status` in `head.statuses_and_check_runs` passed to `StatusChecker.new`, `status.stack_id == head.stack_id` and that status was created by a webhook whose payload's `repository.full_name` matched `head.stack.repository`. This binding is **not enforced**.

- `MergeRequest::StatusChecker` (`app/models/shipit/merge_request.rb:15-40`) is instantiated in `any_status_checks_failed?`/`any_status_checks_missing?`/`all_status_checks_passed?` using `head.statuses_and_check_runs` [1](#0-0) , and `Commit#statuses_and_check_runs` is simply `statuses + check_runs` [2](#0-1)  - i.e. every row ever attached to that `Commit` record, with no repository re-validation at read time.
- The webhook controller verifies the HMAC signature only against the GitHub App/org derived from the payload's own `repository.owner.login` (or `organization.login`) [3](#0-2) . This authenticates "this event was really sent by GitHub for *some* app installation," not "this event concerns *this specific* repository/stack."
- The base `Handler` class provides a `stacks` helper specifically to scope any handler's side effects to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) .
- `StatusHandler#process` bypasses that helper entirely and queries the global `Commit` table by SHA alone: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Since `sha` is not globally unique per stack (git objects/SHAs are shared across forks/mirrors of the same upstream history, and Shipit stores one `Commit` row per (`stack_id`, `sha`)), a payload naming a completely different `repository.full_name` than the target stack can still match and mutate the target stack's `Commit` row.
- `create_status_from_github!` -> `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [6](#0-5)  writes the `Status` using the *victim* commit's own `stack_id` (taken from the matched `Commit`, not from the payload's repository), so the resulting `Status` row looks completely legitimate to any later reader, including `StatusChecker`.

Exploit flow: attacker controls (or can push to) a repository that shares git history/SHAs with a Shipit-tracked repository (e.g., a fork, or any repo within the same GitHub App installation whose branch happens to point at a commit that is also present in the victim stack, which is routine for PR-based workflows). GitHub delivers a genuinely-signed `status` event for the attacker's repository/commit. `verify_signature` passes because it only checks the org/app-level secret, not repo identity. `StatusHandler#process` then matches by SHA and writes a `success` (or any state) `Status` onto the victim stack's `Commit` row. `MergeRequest::StatusChecker.success?` on that commit now returns `true` even though nothing genuine ran CI against the victim repository's commit.

None of the existing guards prevent this: `verify_signature` checks org/app secret only; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` validates `sha`/`state` types, not which repository they belong to; there is no `require_permission!`/`stacks` scoping applied in `StatusHandler#process` unlike other handlers that call the base class's `stacks` helper.

### Impact Explanation
A payload authenticated for one repository writes a `Status` (and, if `CheckRunHandler` has the analogous pattern, a `CheckRun`) row against a commit belonging to a completely different stack. This directly satisfies the "payload for one repository mutating another's stack/commit" Critical category: `MergeRequest#any_status_checks_failed?` / `#any_status_checks_missing?` / `#all_status_checks_passed?` (used to gate `reject_unless_mergeable!` and continuous delivery via `Commit#deployable?`/`#schedule_continuous_delivery`) can be flipped to "green" for a commit that never actually passed CI in the target repository, enabling an unauthorized merge or deploy of that commit. The blast radius spans every stack whose commit history happens to share a SHA with a repository under the same (or any) GitHub App installation that Shipit trusts.

### Likelihood Explanation
The attacker needs: (1) a repository under a GitHub App/org installation that Shipit is configured to accept webhooks for (so a real signature is produced by GitHub, not forged by the attacker), and (2) a commit SHA collision with the victim stack's commit history - trivially achievable via forks/PR branches which share commit objects and therefore SHAs with the upstream repository. Both preconditions are realistic in typical Shipit deployments (Shipit is usually deployed against org-wide GitHub App installations, and PR-based development guarantees SHA sharing between fork and upstream). No secrets, sessions, or privileged roles are required; the attacker only needs the ability GitHub already grants any contributor: push to a branch/fork and let GitHub emit the status webhook.

### Recommendation
In `StatusHandler#process` (and the equivalent `CheckRunHandler`), scope the commit lookup to the stacks resolved from the payload's own `repository.full_name` (using the existing `stacks` helper from `Handler`), e.g. `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }`, instead of querying the global `Commit` table by SHA alone. This restores the binding that every `Status`/`CheckRun` attached to a commit was created by a webhook whose payload named that commit's own repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
    test "a status webhook for repo B must not flip StatusChecker.success? for a commit in repo A" do
      shared_sha = 'a' * 40

      stack_a = shipit_stacks(:shipit)                 # victim stack, repository e.g. "shopify/shipit-engine"
      commit_a = stack_a.commits.create!(sha: shared_sha, message: 'victim commit')

      stack_b = create_stack(repository: create_repository(owner: 'attacker', name: 'evil-fork'))
      stack_b.commits.create!(sha: shared_sha, message: 'attacker commit, same sha (fork)')

      payload = {
        'sha' => shared_sha,
        'state' => 'success',
        'context' => 'ci/attacker',
        'repository' => { 'full_name' => 'attacker/evil-fork', 'owner' => { 'login' => 'attacker' } },
      }

      Shipit::Webhooks::Handlers::StatusHandler.call(payload) # signature already verified upstream by controller

      merge_request = commit_a.stack.merge_requests.create!(number: 1, head: commit_a)
      checker = MergeRequest::StatusChecker.new(commit_a, commit_a.statuses_and_check_runs, nil)

      # Binding under test: commit_a.stack.repository != payload['repository']['full_name']
      assert_not_equal commit_a.stack.repository.full_name, payload.dig('repository', 'full_name')

      # Bug: despite the mismatch above, the forged status is attached and treated as genuine
      assert checker.success?, "forged cross-repo status should not make StatusChecker.success? true"
    end
  end
end
```
This test constructs two stacks whose commits share a SHA (as forks routinely do), delivers a `status` webhook payload naming the *attacker's* repository, and asserts that `commit_a` (belonging to the victim stack) ends up with a `Status` causing `StatusChecker#success?` to return `true` - demonstrating the broken repository binding purely through this engine's code, with no live GitHub interaction required.
