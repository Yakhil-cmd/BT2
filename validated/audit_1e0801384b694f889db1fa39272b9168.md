This confirms the vulnerability. `ApiClient#check_permissions!` only checks whether the `read:stack` string is in the permissions array — it never validates which `stack_id` the token is scoped to [1](#0-0) . The `belongs_to :stack, optional: true` association and `stack_id` column exist precisely to scope a token to one stack [2](#0-1) , and `BaseController#stacks`/`BaseController#stack` correctly enforce that scoping by intersecting with `current_api_client.stack_id` [3](#0-2) . However, `CCMenuController` overrides `stack` to bypass this scoping entirely, calling `Stack.from_param!(params[:stack_id])` directly against the full `Stack` table [4](#0-3) , so `#show` renders `stack.deploys_and_rollbacks.last` for any stack id supplied, regardless of which stack the token is bound to [5](#0-4) .

### Title
CCMenuController#show bypasses per-token stack scoping, allowing cross-tenant deploy state enumeration - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` accessor to resolve `params[:stack_id]` against the unscoped `Stack` model instead of the `stacks` relation that `BaseController` uses to intersect with `current_api_client.stack_id`. As a result, any valid API token with `read:stack` permission — even one issued for a single specific stack — can read the CCMenu XML (branch, last deploy sha/status, running state) of every other stack in the instance by simply varying the numeric `stack_id` in the URL.

### Finding Description
The binding that should hold is: `Stack.from_param!(params[:stack_id]) ∈ Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true. `BaseController#stacks` and `BaseController#stack` implement exactly this binding [3](#0-2) . But `CCMenuController` redefines `stack` as `@stack ||= Stack.from_param!(params[:stack_id])`, dropping the `stacks` scoping entirely [4](#0-3) . The `require_permission :read, :stack` before_action only checks `ApiClient#check_permissions!`, which is a flat permission-string membership check independent of `stack_id` [1](#0-0) . So a token scoped to stack 1 (`api_client.stack_id == 1`, permissions including `read:stack`) passes the before_action for any requested `stack_id`, and `#show` happily renders `stack.deploys_and_rollbacks.last` for stack 2, 3, etc. [5](#0-4) . No other guard in the request path (authentication, `require_permission!`, model validations) checks stack ownership for this action.

Attacker flow: obtain (or be issued) one legitimate CCMenu-capable token bound to their own stack; issue `GET /api/stacks/2/cc_menu.xml?token=<token>`, `/api/stacks/3/cc_menu.xml?token=<token>`, ... incrementing `stack_id`; each request returns 200 with the target stack's branch, last deploy commit sha, and running/success status rendered from `shipit/ccmenu/project`.

### Impact Explanation
This grants unauthenticated-for-that-resource read access to deploy state (branch name, latest deploy/rollback sha, build status) for every stack on the Shipit instance, using only a token scoped to one stack. This matches "High - ... unauthenticated read of stack state, task streams or deploy output" since the token was never authorized for those other stacks. It is fully repeatable across all sequential/enumerable stack ids and affects every tenant stack in the instance, not just the attacker's own.

### Likelihood Explanation
Preconditions are minimal and realistic: the attacker only needs one legitimately issued CCMenu token with `read:stack` permission for their own stack (a routine, low-privilege credential meant for CI dashboard integration), and stack ids are small sequential integers that are trivially enumerable. No secrets, sessions, or elevated roles are required — this is directly exploitable by any holder of a standard CCMenu token.

### Recommendation
Remove the overriding `stack` method in `Shipit::Api::CCMenuController` (or reimplement it to use the inherited `stacks` scope) so that `stack` resolves via `stacks.from_param!(params[:stack_id])`, consistent with `BaseController`, ensuring the lookup is always intersected with `current_api_client.stack_id` when the token is stack-scoped.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` style (minitest):
1. Create two stacks, `stack_a` and `stack_b`, each with a deploy.
2. Create an `ApiClient` with `stack_id: stack_a.id`, `permissions: ['read:stack']`.
3. `get "/api/stacks/#{stack_b.id}/cc_menu.xml", params: { token: api_client.authentication_token }`.
4. Assert broken binding directly: before the fix, `response.status == 200` and the XML body contains `stack_b`'s deploy sha — i.e., `Stack.from_param!(stack_b.id.to_s)` is reachable even though `stack_b.id` is not in `Stack.where(id: api_client.stack_id)` (`stack_a.id`).
5. After the fix, assert `response.status == 404` (or forbidden), confirming `stack ∈ Stack.where(id: current_api_client.stack_id)` now holds for the CCMenu action too.
