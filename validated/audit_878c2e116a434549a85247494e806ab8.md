### Title
Uncapped, single-issuer assets allow unlimited, unbounded supply inflation by the asset definer with no protocol-enforced ceiling - (File: validation.js)

### Summary
`validateAssetDefinition()` in `validation.js` makes the `cap` field of a custom asset entirely optional, and when it is omitted, neither unit validation nor the AA engine impose any protocol-level ceiling on how much of that asset its definer can create. This mirrors the reported bug class: a single privileged party (the asset "owner"/definer) retains an unbounded, repeatable minting capability that is not enforced on-chain, so any documented/expected supply limit is purely a social contract.

### Finding Description
When an unprivileged unit poster (or AA author) defines a new asset, `validateAssetDefinition()` only validates `cap` *if present*: [1](#0-0) 
There is no requirement that a cap be set at all, and `payload.cap && !payload.issued_by_definer_only` is the only cross-check performed [2](#0-1) . The same optionality exists for AA-defined assets in `aa_validation.js` [3](#0-2) .

For a capped asset, issuance is restricted to exactly one lifetime issue of `cap` units, enforced by `serial_number` uniqueness and the "already issued" check [4](#0-3) . For an **uncapped** asset, this ceiling disappears entirely: the only per-message limit is `input.amount > constants.MAX_CAP` (i.e. the total whitebyte supply, effectively unbounded) [5](#0-4) , and the definer (or, if `issued_by_definer_only:false`, any address) can post a fresh `issue` input in as many separate units as desired, each incrementing `serial_number` with no cumulative-supply check [6](#0-5) .

This same pattern is reproduced in the composer/wallet code paths that build issue inputs: `inputs.js#issueAsset` computes `issue_amount = objAsset.cap || (required_amount - total_amount) || 1`, i.e. whatever amount the issuer needs, with no cap enforcement when `objAsset.cap` is falsy [7](#0-6) ; `indivisible_asset.js#issueNextCoin` similarly issues `count_coins_to_issue * denomination` freely for uncapped denominations [8](#0-7) ; and the AA composer's `issueAsset()` does the same for AA-controlled assets [9](#0-8) . `wallet.js#readFundedAddresses` explicitly documents this as by-design: "uncapped asset: can be issued from definer_address ... total = Infinity" [10](#0-9) .

### Impact Explanation
Any asset advertised off-chain (or via UI/documentation) as having a fixed/limited supply, but whose on-chain definition omits `cap`, allows its definer to mint unlimited additional units at will, at any point after the initial definition, across as many separate units as they like. This is a direct analog of the reported `teamSummon()` issue: no enforced ceiling exists at the protocol layer, only a "social"/documentation-based expectation, and the party controlling issuance (the definer address or, for AA-issued tokens, whoever controls or triggers the AA when `issued_by_definer_only:false`) can inflate supply arbitrarily, destroying the economic value of all existing holders' balances of that asset. This is a genuine supply-inflation vector for any token built on ocore's custom-asset primitive, consistent with the "supply inflation" impact category called out as acceptable.

### Likelihood Explanation
This requires no attack beyond normal, permitted use of the protocol's asset-issuance primitive: an asset issuer who chooses (or is compromised into choosing/using) a definition without `cap` need only submit additional `payment` messages with `type:"issue"` inputs to mint more, exactly as legitimate issuance is done. No consensus break, cryptographic bypass, or malicious peer/hub involvement is needed — it is reachable purely by a legitimate but under-constrained asset issuer or AA author, matching the same acknowledged-but-real risk profile as the original report.

### Recommendation
- Since this is fundamentally the same category of finding as the original (owner/definer holding effectively unlimited mint rights when no cap is set), the practical mitigation is social/documentation-level for ocore itself (as in the original C4 report): asset creators and AA authors should always set an explicit `cap` when a fixed supply is promised.
- Optionally, ocore/oscript tooling (wallet UIs, asset explorers) could warn users when an asset lacks a `cap`, and AA authors can be encouraged/required by linting tools to always specify `cap` (numeric or formula-bound) for assets meant to have finite supply, and to track cumulative issued amounts in AA state vars to self-enforce a cap when the built-in `cap` field cannot capture dynamic minting logic.

### Proof of Concept
1. An asset definer posts an `asset` message via `validateAssetDefinition` without a `cap` field, e.g. `{is_private:false, is_transferrable:true, auto_destroy:false, fixed_denominations:false, issued_by_definer_only:true, cosigned_by_definer:false, spender_attested:false}` — this passes validation because `cap` checks are skipped entirely when absent [1](#0-0) .
2. The definer subsequently posts any number of `payment` messages for that asset with `inputs:[{type:"issue", amount:<any value up to MAX_CAP>, serial_number:<n>}]`; each is independently valid since only the double-spend/serial-number uniqueness check applies, not a cumulative supply cap [6](#0-5) .
3. Repeating step 2 indefinitely lets the definer mint an unbounded total supply of the asset, exactly analogous to the unrestricted `teamSummon()` minting in the original report.
