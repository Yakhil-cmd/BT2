### Title
Cross-repository `status` webhook forges `Commit` state, corrupting `Deploy#ignored_safeties` audit flag - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, matching purely on SHA with no check that the webhook's authenticated repository is the one that owns that commit. Because `WebhooksController#verify_signature` only authenticates that the webhook came from *some* repository/organization known to Shipit (via `Shipit.github(organization: repository_owner)`), not that it is authorized for the specific `Stack`/`Commit` being mutated, an attacker who controls any repository registered as a Shipit stack can forge a `success` status for a commit belonging to a completely different (victim) stack, as long as that commit's SHA also exists as a row in the attacker's own stack (which happens naturally for shared/forked history).

### Finding Description
Binding claimed: `deploy.ignored_safeties? == !victim_repository_real_ci_state(until_commit).deployable?`, i.e. the safety flag persisted on a `Deploy` must reflect the true CI state of the deploy's own stack/repository.

Code path:
1. `WebhooksController#verify_signature` authenticates the webhook only against the organization owning the repository named in the payload: `Shipit.github(organization: repository_owner)` [1](#0-0) . It never checks that the payload's `sha`/commit actually belongs to that repository.
2. `Shipit::Webhooks::Handlers::StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This query is **not scoped to the stack/repository that authenticated the webhook** — it matches every `Commit` row across every `Stack` that happens to share that SHA.
3. `Commit#create_status_from_github!` unconditionally records the forged status against whatever commit row is found: `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [3](#0-2) .
4. `Commit#deployable?` (derived from `status.state`) is now `true` for the victim commit, even though the victim repository's real CI never reported success.
5. `Stack#build_deploy` computes `ignored_safeties: force || !until_commit.deployable?` [4](#0-3) , which now evaluates to `false` and is persisted via `Stack#trigger_deploy` [5](#0-4) .

Root cause: SHA is not a repository-scoped or globally unique identifier of authorization — `Commit` rows are keyed by `(stack_id, sha)`, and identical SHAs legitimately occur across different stacks that share commit history (forks, mirrors, staging/production stacks tracking the same repo). `StatusHandler` treats `sha` as if it uniquely and safely identified the commit that the authenticated webhook is allowed to update, which is false whenever another stack shares that SHA. None of the existing guards catch this: `verify_signature` validates organization-level HMAC, not per-commit repository ownership; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema on `StatusHandler` only validates the payload shape, not the target commit's repository binding.

Attacker request: An attacker who controls (or has push access to) any repository registered in Shipit as a `Stack` (e.g., their own fork/mirror sharing history with a victim's tracked repository, or a second stack over the same upstream) calls the real GitHub Statuses API — `POST /repos/{attacker_repo}/statuses/{victim_commit_sha}` — with `state: success`. GitHub allows creating a status for any SHA string on a repo the caller has push access to, without requiring that SHA to be reachable in that repo's own history. GitHub then delivers a correctly-signed `status` webhook to Shipit for the attacker's repository, containing the victim's SHA. This webhook passes `verify_signature` (it's genuinely signed by the org owning the attacker's repo) and is processed by `StatusHandler`, which finds and mutates the victim's `Commit` row in a different `Stack`.

### Impact Explanation
This is "a payload for one repository mutating another's stack, commit, task or team," matching the Critical impact category. Concretely: a forged `Status::success` record is written onto a victim stack's `Commit`, flipping `Commit#deployable?` to `true`; a subsequent operator or scheduled `trigger_deploy`/continuous-delivery run on the victim stack then persists `Deploy#ignored_safeties = false` even though the victim repository's real, unforged CI state (as reported by its own CI provider) is failing/pending. This falsifies the deploy audit trail — the record claims safety checks were honored when they were bypassed via a forged status — and can also unlock continuous delivery (`Stack#trigger_continuous_delivery`) to actually deploy an unsafe commit, since `Commit#deployable?` gates `next_commit_to_deploy`/`deployable_commits`. The attack is repeatable against any victim stack whose commit history overlaps with a stack the attacker controls, and is not limited to one victim — any shared-history stack is exposed.

### Likelihood Explanation
Preconditions: (1) the attacker must control/own at least one repository that is registered as a Shipit `Stack` with a working GitHub webhook (a realistic scenario in self-service Shipit deployments, or simply a second environment/mirror stack for the same codebase); (2) that repository must share at least one commit SHA with the victim stack's repository, which is the normal case for forks, mirrors, and multi-stack setups tracking the same codebase. No Shipit secrets, sessions, or API tokens are required — only ordinary GitHub push/API access to a repo the attacker already controls, which is explicitly within the "unprivileged attacker" model. The forgery is a single API call and is fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to the repository that authenticated the webhook, not merely to SHA. Either join through `Stack` to filter `Commit.where(sha: params.sha)` by `stack.repository == webhook_repository` (compare `repository.owner`/`repository.name` against the payload's `repository` object, not just the organization), or pass the authenticated repository identity from `WebhooksController` into each handler and require an exact match before creating/updating a `Status` on a `Commit`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from a different repository cannot forge a status on a victim commit" do
  victim_stack  = shipit_stacks(:shipit)          # repo: shopify/shipit-engine
  attacker_stack = shipit_stacks(:other_repo)     # repo attacker controls, shares SHA history
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_stack.commits.create!(sha: shared_sha, ...)

  # Simulate victim repo's real (unforged) CI: failing
  victim_commit.statuses.create!(stack_id: victim_stack.id, state: 'failure', context: 'ci/travis')
  refute_predicate victim_commit.reload, :deployable?

  # Attacker forges a signed webhook for THEIR OWN repo, referencing the victim's SHA
  payload = { sha: shared_sha, state: 'success', context: 'ci/travis', repository: attacker_stack.repository.to_github_payload }
  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload) # passes verify_signature for attacker's org

  # Binding check
  assert_predicate victim_commit.reload, :deployable? # BROKEN: forged true, should remain false

  deploy = victim_stack.trigger_deploy(victim_commit, AnonymousUser.new)
  refute_predicate deploy, :ignored_safeties? # BROKEN: should be true (real CI failing), asserts false
end
```
This demonstrates the binding `deploy.ignored_safeties? == !victim's_real_CI.deployable?` no longer holds once a same-SHA, different-repository status is injected.
