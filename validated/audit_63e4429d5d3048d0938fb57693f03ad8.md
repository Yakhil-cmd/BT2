### Title
Cross-organization webhook forgery lets an org's `membership` webhook grant `Shipit.github_teams` authorization for a *different* organization's team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub organization named in the payload, using that organization's configured `webhook_secret`. `MembershipHandler`, however, resolves the `Team` to modify purely by the attacker-suppliable `team.id` (GitHub's numeric team id), never checking that this team actually belongs to the organization whose secret produced the valid signature. This breaks the binding: "organization that authenticated" ≠ "team whose membership is written," letting anyone who controls webhook delivery for *any* configured organization escalate arbitrary GitHub logins into a *different*, privileged organization's team that gates `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the signature purely from `repository_owner` (`repository.owner.login` or fallback `organization.login`) taken from the payload itself: [1](#0-0) 

So the only thing the signature proves is "this request was signed with organization X's configured `webhook_secret`" — it does not, by itself, constrain *which* records the handler is allowed to touch afterwards.

`MembershipHandler#process` then resolves the target `Team` using only the numeric `params.team.id` supplied in the (now-verified-for-org-X) payload, and adds `params.member.login` to it: [2](#0-1) 

Crucially, `Team.find_or_create_by!(github_id: params.team.id)` only sets `team.organization = params.organization.login` inside the creation block — if a `Team` row with that `github_id` **already exists** (e.g. it was pre-populated because it's one of `Shipit.github_teams`, the teams configured in `github.oauth.teams` that gate application authorization), the existing row is returned unchanged and the organization is never re-validated: [3](#0-2) 

Authorization to use Shipit at all is driven directly by membership in these teams: [4](#0-3) 

Put together: signature verification is scoped to "organization X authenticated," but the write ("add this GitHub login to Team with this `github_id`") is scoped to "any team id the payload names," with no re-check that the team belongs to organization X. An admin of organization X (who legitimately knows/controls X's webhook secret, since org admins configure org webhooks on GitHub's side) can forge a `membership` event whose `team.id` is the public GitHub team id of a *different*, privileged organization's team (team ids and slugs are discoverable via `GET /orgs/:org/teams`), granting an arbitrary GitHub login membership in that privileged `Shipit::Team` row and thus `authorized?` on the whole Shipit instance.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization (explicitly listed as High impact): an attacker who only controls one (possibly low-trust) configured GitHub organization can grant any GitHub account access to a Shipit instance that is supposed to be gated to a completely different, privileged organization's team, without ever being a real member of that team or organization.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (supported — see `Shipit.github(organization:)` and the multi-app secrets fixture) where the attacker controls webhook configuration for at least one configured organization, and knowledge of the target team's public GitHub `id`/slug (retrievable via the GitHub API for teams visible to the attacker, or by prior reconnaissance). This is a realistic scenario for any Shipit instance shared across multiple GitHub orgs of differing trust levels.

### Recommendation
In `MembershipHandler`, verify that the resolved `Team#organization` matches `params.organization.login` before mutating membership (reject/no-op otherwise), and/or update `Team.find_or_create_by!` to always enforce/validate `organization` against the authenticating org rather than only on first creation.

### Proof of Concept
1. Shipit is configured with `Shipit.github_teams` containing `PrivilegedOrg/admins` (its `Team` row already exists with `github_id = 1000`, `organization = "PrivilegedOrg"`).
2. Attacker administers `AttackerOrg`, which is also configured in Shipit (`github.<AttackerOrg>.webhook_secret` known to the attacker via GitHub org webhook settings).
3. Attacker sends a `membership` webhook to Shipit, signed with `AttackerOrg`'s `webhook_secret`, with body:
```json
{
  "action": "added",
  "team": {"id": 1000, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/1000"},
  "organization": {"login": "AttackerOrg"},
  "member": {"login": "attacker-controlled-login"}
}
```
4. `verify_signature` succeeds (signed correctly for `AttackerOrg`).
5. `MembershipHandler#find_or_create_team!` finds the existing `Team` with `github_id: 1000` (the real `PrivilegedOrg/admins`) and adds `attacker-controlled-login` as a member.
6. That GitHub login is now `authorized?` for Shipit via `PrivilegedOrg/admins` membership, despite never joining `PrivilegedOrg`.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
