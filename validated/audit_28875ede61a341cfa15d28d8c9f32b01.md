### Title
Signature verification keyed on `repository.owner.login` while stack resolution keyed on `repository.full_name` allows cross-tenant webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret used to validate the raw request body) using `repository_owner` (`repository.owner.login`), but the actual write performed in `#create`/`PushHandler` resolves the target stack using `repository.full_name` — a completely separate, attacker-controlled field in the same JSON body. Nothing ties these two values together, so a payload can be signed/verified against one organization's app while mutating another organization's stack.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`organization_whose_secret_verified_the_bytes (derived from params.dig('repository','owner','login'))` == `organization_owning_the_stack_that_gets_mutated (derived from params.dig('repository','full_name').split('/').first)`.

Trace:
- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner)` to obtain a `GitHubApp`, then calls `github_app.verify_webhook_signature(signature, request.raw_post)`. [1](#0-0) 
- `Shipit.github` looks up that organization's config via `github_app_config(organization)` and raises `GithubOrganizationUnknown` only if the org key is absent from `secrets.github`; if the org exists but has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`). [2](#0-1) [3](#0-2) 
- Once verification passes, `#create` re-parses the raw body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, e.g. `PushHandler`. [4](#0-3) 
- `PushHandler` (via base `Handler#stacks`) resolves the target stacks purely from `payload.dig('repository', 'full_name')`, with no reference at all to `repository.owner.login` or to which org's secret verified the request. [5](#0-4) [6](#0-5) 

Attacker request: a multi-org Shipit deployment (as shown in `config/secrets.development.shopify.yml`, which configures multiple independent `github:` orgs each with their own `webhook_secret`) where the attacker legitimately owns/administers `attacker-org`'s GitHub App entry registered on this Shipit instance (and therefore knows `attacker-org`'s `webhook_secret`, or that org's secret is unset). The attacker POSTs to `/webhooks` with `X-Github-Event: push`, a valid (or, if unset, no) `X-Hub-Signature` computed for `attacker-org`, and a JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`. `verify_signature` authenticates the byte stream against `attacker-org`'s app/secret and passes; `PushHandler` then looks up `victim-org/victim-repo`'s stack purely by `full_name` and calls `stack.sync_github(expected_head_sha: ...)`, enqueuing a `GithubSyncJob` for a stack the attacker never authenticated against.

Why existing guards fail: `drop_unhandled_event` only checks the event type exists; `verify_signature` never cross-checks that the verifying org matches the prefix of `repository.full_name`; `ExplicitParameters` schemas in handlers (e.g. `PushHandler`) only validate `ref`/`after` types, not repository ownership consistency; there is no model-level validation tying incoming payload owner to the `Repository`/`Stack` being written.

### Impact Explanation
A payload that only proves authenticity for one tenant (`attacker-org`) is used to trigger a real write — `GithubSyncJob` enqueued for `victim-org/victim-repo`'s stack via `stack.sync_github` — for a different tenant that never authenticated the request. This is a cross-repository/cross-tenant mutation triggered by a payload not authenticated by the victim's own secret, matching the "payload for one repository mutating another's stack" Critical category. The attack is repeatable against any stack/repository known to the attacker (by full_name) as long as the attacker controls one configured-but-weak org (missing/known secret) on the shared Shipit instance; blast radius extends across every tenant sharing that Shipit installation.

### Likelihood Explanation
This requires a specific but realistic deployment shape: a multi-organization Shipit instance (supported and documented via the `github:` multi-key config format, as seen in `config/secrets.development.shopify.yml`) where at least one onboarded organization either has no `webhook_secret` set or whose secret is known to its own (attacker) org administrators — plausible in self-service/onboarding flows where each org supplies its own webhook secret. Given that precondition, the attacker's cost is a single crafted HTTP POST with no other privilege, secret, or session required, and the attack is trivially repeatable against arbitrary victim repositories they can name.

### Recommendation
After successful signature verification, `verify_signature` (or `#create`) must derive the organization from `repository.full_name`'s owner segment (or the handler's actual repository resolution) and confirm it equals — or itself independently verify against — the organization used to compute the signature, rejecting the request if they diverge. Concretely, compute `expected_owner = params.dig('repository','full_name')&.split('/', 2)&.first` and require it to equal `repository_owner` before proceeding, or better, always verify using the org derived from `full_name` rather than `owner.login`.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (minitest, `ActionController::TestCase`):
```ruby
test "push payload with mismatched owner.login and full_name should not sync a different org's stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to victim-org/victim-repo per fixtures
  request.headers['X-Github-Event'] = 'push'

  payload = JSON.parse(payload(:push_master))
  payload['repository']['owner']['login'] = 'attacker-org'
  payload['repository']['full_name'] = victim_stack.github_repo_name # 'victim-org/victim-repo'
  body = payload.to_json

  # attacker-org configured with no webhook_secret -> verify_webhook_signature returns true unconditionally
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', {}) # no webhook_secret
  )

  assert_no_enqueued_jobs do
    post :create, body: body, as: :json
  end
  # Equality that should hold but currently doesn't without the fix:
  # organization_that_verified_signature ('attacker-org') == organization_owning_mutated_stack ('victim-org')
end
```
Before the fix, this enqueues `GithubSyncJob` for `victim_stack.id`; after the fix (adding the owner/full_name consistency check), the request is rejected with 422 and no job is enqueued.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
