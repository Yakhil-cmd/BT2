### Title
AA definer/admin front-running of mutable state (exchange rate / fee) enables total value theft from trigger senders due to missing slippage protection - (File: `test/samples/sell_asset_for_bytes.oscript`, `test/samples/uniswap_like_market_maker.oscript`, `aa_composer.js`)

### Summary
Autonomous Agents (AAs) in ocore can expose a privileged "admin" address that is allowed to update a mutable state variable (an exchange rate, price, or fee) via a normal trigger, while ordinary users interact with the very same AA to swap value based on that state variable with **no enforced minimum-output / slippage check**. Because AA trigger execution order is decided deterministically per stabilized MCI batch (not by real-time submission order), the admin address can post a rate/fee-changing trigger that gets processed in an earlier or the same MCI batch as a victim's pending swap trigger, changing the payout formula before the victim's funds are consumed. This mirrors the CatalystVault finding: a privileged, trusted role (fee/definer address) can front-run an ordinary user's swap to drain the value they send to the contract, and the language/reference templates do not build in a minOut safeguard to prevent it.

### Finding Description
Reference AA templates shipped with ocore illustrate this exact class of bug:

In `test/samples/sell_asset_for_bytes.oscript`, an admin address (`$my_address`) can update `var['rate']` at will: [1](#0-0) 

and any user exchanging bytes for the asset computes the payout purely from the current `var['rate']`, with **no minimum-output parameter supplied by the trigger sender and no check against it**: [2](#0-1) 

The same pattern appears in the Uniswap-like market-maker template, where the exchange formulas explicitly note "we can deduct exchange fees here" but never validate any caller-supplied minimum acceptable amount: [3](#0-2) 

The reason this is exploitable via front-running (not just "the owner can always do this") is that AA trigger processing order is not first-come-first-served in real time; it's decided in deterministic batches once an MCI stabilizes, ordered by `level`, `unit`, `address`, and AAs execute strictly in the order the units become part of a stabilized MCI: [4](#0-3) [5](#0-4) 

This means an admin who observes a victim's still-unstable swap trigger unit propagate through the network can immediately broadcast a rate-change trigger and, by controlling its DAG placement (parents/witness selections), get it included and stabilized in an MCI batch that runs at or before the victim's trigger — effectively "front-running" the victim within the deterministic execution window, exactly as described in the CatalystVault report's front-running scenario. Once the victim's trigger executes against the manipulated `var['rate']`, the AA keeps 100% of the bytes/asset sent (since Oscript's `payment` messages don't revert on zero-amount outputs and there's no protocol-level requirement for AAs to bounce when output is unexpectedly low), so the admin (or the AA's balance under admin control) captures the full value the victim intended to swap.

### Impact Explanation
This causes an unprivileged AA trigger sender to lose the entire value of funds sent to the AA for a swap, transferred instead to (or retained under the control of) the privileged AA admin/definer address — a concrete AA fund loss for the counterparty, matching the accepted impact category "AA fund loss." Because the templates shown are the officially distributed reference designs for building exchange/market-maker AAs on Obyte, any AA built following this pattern (mutable price/fee state variable settable by an admin address, and swap logic that trusts the trigger's `trigger.output` without a caller-specified minimum) inherits this exact class of vulnerability.

### Likelihood Explanation
Likelihood is Medium: it requires a privileged/trusted address (the AA's own definer, analogous to CatalystVault's fee administrator) to act maliciously or be compromised, and it requires reasonably fast reaction to see the victim's pending (unstable) swap trigger before it stabilizes — feasible for the admin since they can watch the network like anyone else and quickly issue a low-cost state-update trigger to their own AA.

### Recommendation
- Oscript reference templates and any production AA implementing exchange/market-maker logic should require and validate a caller-specified minimum-acceptable-output field in `trigger.data` (e.g., `trigger.data.min_out`) and `bounce()` when the computed payout is below it, so a rate/fee change cannot silently zero out a user's expected proceeds.
- Documentation/templates should discourage unconstrained admin-controlled parameters (unbounded fee or rate changes) without a timelock or a maximum bound, and should show the safe pattern (minOut + bounce) as the default in all shipped examples (`sell_asset_for_bytes.oscript`, `uniswap_like_market_maker.oscript`, `futures_contract.oscript`, `order_book_exchange.oscript`).

### Proof of Concept
1. An AA is deployed from `sell_asset_for_bytes.oscript` (or a similarly-patterned production AA) with `$my_address` acting as rate-setter.
2. A user broadcasts a unit sending >100000 bytes to the AA to buy the asset, omitting any minimum-acceptable-amount data field (the template provides none).
3. Before the user's unit stabilizes, `$my_address` broadcasts a trigger with `trigger.data.exchange_rate = 0`ish value, engineering its DAG placement so it stabilizes in the same or an earlier MCI batch (per the deterministic ordering in `main_chain.js`'s `handleAATriggers`/`aa_composer.js`'s `handleAATriggers`).
4. When the victim's trigger executes, `var['rate']` is already near zero, so `$asset_amount = round($bytes_amount * var['rate'])` computes to (near) zero.
5. The AA's `payment` message with `amount: 0` (or negligible) is simply skipped/emits no meaningful transfer per Obyte's payment message semantics, while the victim's bytes remain in the AA's balance.
6. `$my_address` restores `var['rate']` to the original value and can withdraw the retained bytes at will since it also controls the AA in similar templates (e.g., `create_an_asset.oscript`'s withdraw case) or via subsequent legitimate swaps at the correct rate.

function handleAATriggers(onDone) {
	if (!onDone)
		return new Promise(resolve => handleAATriggers(resolve));
	mutex.lock(['aa_triggers'], function (unlock) {
		db.query(
			"SELECT aa_triggers.mci, aa_triggers.unit, address, definition \n\
			FROM aa_triggers \n\
			CROSS JOIN units USING(unit) \n\
			CROSS JOIN aa_addresses USING(address) \n\
			ORDER BY aa_triggers.mci, level, aa_triggers.unit, address",
			function (rows) {
				var arrPostedUnits = [];
				async.eachSeries(
					rows,
					function (row, cb) {
						console.log('handleAATriggers', row.unit, row.mci, row.address);
						var arrDefinition = JSON.parse(row.definition);
						handlePrimaryAATrigger(row.mci, row.unit, row.address, arrDefinition, arrPostedUnits, cb);
					},
					function () {
						arrPostedUnits.forEach(function (objUnit) {
							eventBus.emit('new_aa_unit', objUnit);
						});
						unlock();
						onDone();
					}
				);
			}
		);
	});
}
