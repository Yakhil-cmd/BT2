### Title
Webhook signing organization is derived from an attacker-controlled field that is decoupled from the repository field actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization whose `webhook_secret` is used to validate the signature based on `repository.owner.login` (or `organization.login`) taken straight out of the *unverified* JSON body. [1](#0-0) [2](#0-1)  Every downstream handler, however, resolves the actual `Repository`/`Stack` to act on using a *different* field of the same unverified body: `repository.full_name`. [3](#0-2) 

### Finding Description
The binding that should hold is: `organization whose secret verified the signature == organization that owns the repository being written to`. In this engine those are computed from two independently attacker-settable JSON keys inside the same unauthenticated payload:

- Verification organization: `params.dig('repository','owner','login') || params.dig('organization','login')`, used to select `Shipit.github(organization: repository_owner)` and thus the `webhook_secret` checked against `X-Hub-Signature`. [1](#0-0) 
- Acted-upon repository: `payload.dig('repository','full_name')`, used by `Handler#stacks` / `Handler#repository_name` to look up the `Repository` (and its `Stack`s) that `PushHandler`, `StatusHandler`, etc. will mutate. [3](#0-2) [4](#0-3) [5](#0-4) 

`GithubApp#verify_webhook_signature` additionally has: `return true unless webhook_secret` — i.e. if the organization resolved for signing has no `webhook_secret` configured, the signature check is unconditionally bypassed. [6](#0-5) 

Because `repository.owner.login` and `repository.full_name` are two independent strings inside the same request body, an attacker who knows (or guesses) that *any* configured GitHub organization on the install has no `webhook_secret` set (a legitimate, documented configuration — see `docs/setup.md` / `config/secrets.development.shopify.yml` showing `webhook_secret: nil`) can craft a body where:
- `repository.owner.login` = that no-secret organization (so `verify_webhook_signature` returns `true` unconditionally, no valid signature required), while
- `repository.full_name` = `"victim-org/victim-repo"`, a completely different, properly-secured organization's repository that has a real Shipit `Stack`.

The `push`/`status`/`check_suite` handlers then resolve the stack via `full_name` and act on it — e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for the victim's stack, using attacker-chosen `ref`/`after` values. [7](#0-6) 

This is the direct structural analog of the reported bug class: two values that are supposed to be tied together by an integrity/authorization check (asset amount vs. shares; here, signing organization vs. acted-upon repository) are instead computed from independent, unauthenticated inputs, so the "rounding"/binding gap can be steered by the attacker to their advantage.

### Impact Explanation
If exploitable, this allows an unauthenticated attacker to forge webhook events (`push`, `status`, `check_suite`, `membership`, etc.) against any repository/stack configured under an organization that *does* have a webhook secret configured, as long as any other configured organization on the same Shipit install lacks a `webhook_secret`. Consequences include forcing `sync_github` calls with attacker-chosen `expected_head_sha`, injecting forged commit statuses (`StatusHandler`), or triggering `membership`/team-mutation handlers — i.e., unauthorized state changes to stacks the attacker does not control, without holding any Shipit session, `ApiClient` token, or real GitHub webhook secret.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment, and (2) at least one configured organization with `webhook_secret` left blank. Both conditions are explicitly supported/documented (`docs/setup.md` describes `webhook_secret` as optional; sample secrets files ship with it `nil`). [8](#0-7)  I could not verify from the available code whether `Shipit.github(organization:)` requires the organization key to literally match a configured key in `Shipit.secrets.github` (raising `GithubOrganizationUnknown` otherwise) or whether it falls back to a default single-org config — this determines whether the attacker must merely name an existing no-secret org or can use an arbitrary string. I was unable to fully inspect `Shipit.github` and `Shipit.secrets` resolution logic to confirm this precisely; a background agent with full repository access should verify `lib/shipit.rb`'s `github`/`secrets` methods and `config/secrets*.yml` structure end-to-end before treating this as confirmed rather than a probable analog.

### Recommendation
Bind the signature-verification organization to the same repository field used by handlers (`repository.full_name`'s owner segment), or better, verify the signature once against the payload without depending on attacker-controlled routing, then re-derive `repository_owner` from the verified payload only after a valid signature is established for that specific webhook secret. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-organization installs — require an explicit secret per organization, or fail closed to `422` when no secret is configured but other organizations in the same install do have secrets.

### Proof of Concept
Given a Shipit install with two configured GitHub orgs: `no-secret-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`), and a `Stack` for `victim-org/victim-repo`:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

`verify_signature` resolves `repository_owner` = `"no-secret-org"` → `Shipit.github(organization: "no-secret-org")` → `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank. [9](#0-8)  The request passes to `PushHandler`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's real stack. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
