### Title
Webhook signature is verified against an organization derived from an attacker-controlled field, but the stack/repository acted upon is looked up from a different, independently-forgeable field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to use for verifying `X-Hub-Signature` based on `repository.owner.login` (falling back to `organization.login`), both taken straight from the unauthenticated JSON body. Once the signature validates against that organization's secret, the actual event handler (`Shipit::Webhooks::Handlers::Handler#stacks`, and `PushHandler`, `StatusHandler`, etc.) looks up the repository/stack to act on using a *different* field, `repository.full_name`, and even in some handlers, a bare `sha` (`StatusHandler`) with no owner scoping at all. Nothing ties `full_name` (or `sha`) to the organization whose secret produced the signature. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
This is the same "overwrite/substitution" bug class as H-2: a value is used for one purpose (here, authorization — selecting the signing secret) and then a *different, unchecked* value is used for the operative action (here, selecting the stack that gets written to), while the code implicitly (and incorrectly) assumes the two are the same value.

Concretely:
- `repository_owner` (used to pick the webhook secret / tenant in `Shipit.github(organization: repository_owner)`) is read from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. [2](#0-1) 
- The event handlers never reuse `repository_owner`. Instead they derive the acted-upon repository from `payload.dig('repository','full_name')` via `Repository.from_github_repo_name`, which just splits the string on `/` and does a DB lookup — with no cross-check that the owner segment matches the organization whose secret validated the signature. [3](#0-2) [6](#0-5) 
- `Shipit` supports genuine multi-tenant configuration: each organization has its own independently configured `webhook_secret` in `secrets.github[org]`, resolved via `github_app_config`. [7](#0-6) 

Because the person who configures a GitHub App/webhook for their own organization on a shared Shipit instance necessarily knows that organization's `webhook_secret` (they set it when wiring up the GitHub webhook), an attacker who legitimately administers **Org A** on a multi-org Shipit deployment can:
1. Compute a valid `X-Hub-Signature` using Org A's own `webhook_secret`.
2. Set `repository.owner.login` = `"org-a"` (so `verify_signature` picks Org A's secret and passes) while setting `repository.full_name` = `"org-b/victim-repo"` (or, for `StatusHandler`, an arbitrary `sha` known to belong to a commit in Org B's stack).
3. POST this forged payload to `/webhooks`.

The signature check passes (it only proves the sender knows Org A's secret), but the handler acts on Org B's `Stack`/`Commit` records because it never re-derives or checks the owner from the same trust boundary that produced the signature.

The binding that is broken:

`organization authenticated by verify_signature == organization whose repository is written by the handler`

Before the attack this equality naturally holds because legitimate GitHub webhook deliveries always keep `repository.owner.login` consistent with `repository.full_name`. After the attacker's forged POST, the left side is Org A (attacker-controlled, self-signed) while the right side is Org B (victim) — the equality is broken.

### Impact Explanation
This is a cross-tenant/cross-repository write on a shared Shipit installation:
- `PushHandler` enqueues `GithubSyncJob` for the victim's stack with an attacker-chosen `expected_head_sha`, forcing Shipit to re-sync a victim stack against GitHub state the attacker does not control but can influence the timing/frequency of. [8](#0-7) 
- `StatusHandler` writes arbitrary CI/status records onto any `Commit` matching a guessed/known `sha` across the whole instance, with **no repository/owner scoping check at all** in that handler — it queries `Commit.where(sha: params.sha)` globally. [5](#0-4) 
Since Shipit deploy safety checks (CI "required"/"blocking" statuses per `shipit.yml`) can gate whether a stack is deployable, an attacker who can inject fabricated success statuses for commits in a victim stack can push that victim stack toward becoming deployable, i.e. contribute to an **unauthorized deploy**. This satisfies the required Critical/High impact bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires the attacker to legitimately administer at least one organization on a shared, multi-tenant Shipit instance (so they know their own `webhook_secret`) — a plausible scenario for any Shipit deployment onboarding multiple independent GitHub orgs/teams, which is exactly the multi-org config path supported by `Shipit.github_app_config`. No GitHub compromise, no `ApiClient` token, and no privileged Shipit account is needed — only knowledge of one's own already-configured webhook secret and the target repository's `full_name`/commit SHAs, which are public GitHub metadata.

### Recommendation
Bind the authenticated organization to the repository actually acted upon:
- In `Handler#repository_name` (and any handler using it), derive the repository from the *same* field used by `verify_signature`, i.e. require `repository.owner.login` (or `organization.login`) to equal the owner segment of `repository.full_name` before doing the `Repository.from_github_repo_name` lookup, rejecting the payload otherwise.
- Alternatively, pass the verified organization down from `WebhooksController` into each handler and have handlers scope the `Stack`/`Commit` lookup to `Repository` records belonging to that verified organization, rather than trusting `full_name`/`sha` alone.
- For `StatusHandler` specifically, scope the `Commit` lookup by the verified repository owner, not just `sha`, to prevent cross-tenant status injection.

### Proof of Concept
1. Attacker legitimately administers `org-a`, which is configured in Shipit with `webhook_secret: "s3cr3t-a"`.
2. Attacker computes `sig = HMAC-SHA1("s3cr3t-a", raw_body)` for a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=sig`.
4. `verify_signature` resolves `repository_owner == "org-a"`, fetches Org A's `webhook_secret`, verifies successfully. [9](#0-8) 
5. `PushHandler#process` resolves `stacks` via `repository_name = "org-b/victim-repo"`, matching Org B's real `Stack`, and enqueues `GithubSyncJob` for it with the attacker-supplied `expected_head_sha`, despite the request never being validated against Org B's secret. [8](#0-7) 
6. Similarly, a forged `status` event signed with Org A's secret but carrying a `sha` belonging to Org B's commit lets the attacker write arbitrary CI status onto Org B's commit via `StatusHandler`, with zero owner-based filtering. [5](#0-4)

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
