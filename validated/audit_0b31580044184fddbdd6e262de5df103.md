Confirmed — `config/routes.rb` mounts a global `resources :hooks` at the top level (`namespace :api`, line 46), separate from the stack-nested `resources :hooks` (line 43). Both are handled by the same `Shipit::Api::HooksController`, whose scoping logic depends entirely on whether `params[:stack_id]` happens to be present, not on the URL actually hit or the `ApiClient`'s authorized scope.

### Title
Stack-scoped API token can create/manage global webhook `Hook`s outside its authorized stack - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
An `ApiClient` token that is scoped to a single stack (`stack_id` set, e.g. `here_come_the_walrus` fixture) and merely holds the generic `write:hook` permission can call the top-level, non-stack-nested `POST /api/hooks` endpoint. Because `HooksController#stack_id` returns `nil` whenever `params[:stack_id]` is absent, the created `Hook` record has `stack_id: nil`, which `Hook.for_stack`/`Hook.global` treat as a **global** hook that receives events for every stack in the Shipit instance — not just the one stack the token is authorized for.

### Finding Description
`ApiClient#check_permissions!` in [1](#0-0)  only checks that the string `"write:hook"` is present in `permissions`; it never checks `stack_id`. The actual stack-scoping is supposed to happen via `BaseController#stacks`: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` in [2](#0-1) .

`HooksController` binds to that scoping only through the `stack_id` helper: [3](#0-2) 

If `params[:stack_id]` is absent, `stack_id` is `nil`, `hooks` becomes `Hook.where(stack_id: nil)`, and `stack` (from `BaseController`) is never invoked — so the `current_api_client.stack_id?` scoping check in `stacks`/`stack` is bypassed entirely for this action, because it's simply never called.

`config/routes.rb` exposes exactly this unscoped path: a global `resources :hooks, only: %i[index create show update destroy]` at line 46, distinct from the stack-nested one at line 43: [4](#0-3) .

`Hook.for_stack(stack_id)` explicitly includes stack_id `nil` hooks for every stack's event delivery: [5](#0-4) . This is the binding being broken: **the stack a token is authorized for (`ApiClient.stack_id`) ≠ the stack(s) whose events the created `Hook` actually touches (all stacks, via `stack_id: nil`)**.

### Impact Explanation
A hook's `delivery_url` and `secret` are attacker-controlled input (`create` params in [6](#0-5) ). By registering a global hook, a token scoped to one low-value stack can cause `Hook.deliver!`/`DeliverHookJob` to POST event payloads (`deploy`, `rollback`, `commit_status`, `merge`, etc., see `EVENTS` in [7](#0-6) ) for **every stack in the installation** to an attacker-controlled URL — an unauthorized cross-stack read of task/deploy state that the token was never granted. It can also `update`/`destroy` any pre-existing global hook (`hooks.find(params[:id])` against `Hook.where(stack_id: nil)`), disrupting other stacks' integrations. This matches the "unauthenticated/unauthorized read of stack state" High-severity class, via a scope-authorization bypass rather than pure authentication bypass.

### Likelihood Explanation
Any `ApiClient` with the common `write:hook` permission and a restricted `stack_id` (a normal, lower-privilege token configuration intended to limit that client to one stack) can trigger this by simply calling the un-nested route instead of the nested one — no additional secret, session, or privilege is required beyond the token itself, which is the expected credential for using the API in the first place.

### Recommendation
`HooksController` should not derive scoping from the mere presence of a URL param. It should always intersect with the `ApiClient`'s authorized scope: if `current_api_client.stack_id?`, force `stack_id` to that client's stack (rejecting/`404`ing global-hook actions) regardless of whether `params[:stack_id]` was supplied, mirroring the pattern already used in `BaseController#stacks`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack: shipit` (e.g., fixture `here_come_the_walrus`) but grant it `write:hook`.
2. Authenticate with that token and `POST /api/hooks` (the **top-level** route from `config/routes.rb` line 46, not `/api/stacks/:stack_id/hooks`) with `delivery_url` and `events`.
3. Inspect the created record: `Hook.last.stack_id == nil`.
4. Trigger any event (e.g. a deploy) on an unrelated stack the client was never authorized for; observe `Hook.for_stack(other_stack.id)` includes the newly created hook (per `scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }`), so `DeliverHookJob` sends that unrelated stack's event payload to the attacker's `delivery_url`.
