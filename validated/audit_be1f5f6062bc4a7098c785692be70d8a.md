### Title
Cross-Repository Commit Status Forgery via Unscoped `StatusHandler` Breaks Organization-to-Repository Binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook by selecting a GitHub App configuration (and its `webhook_secret`) using a `repository_owner`/`organization.login` value taken from the payload itself, and verifies the payload's HMAC against that org's secret. `Shipit::Webhooks::Handlers::StatusHandler`, however, applies the resulting `commit_status` action globally, by commit SHA only, with no re-check that the commit's repository actually belongs to the organization/app that was authenticated. This breaks the equality that should hold: `organization_authenticated_by_signature == organization_owning_the_written_repository`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` derives the signing organization purely from the untrusted body: [1](#0-0) [2](#0-1) 

The secret used for that organization is optional and, when unset (the documented default, e.g. `webhook_secret: # nil` in the setup docs and secrets templates), signature verification is bypassed entirely: [3](#0-2) 

Every other event handler scopes its side effects to the repository named in the payload via `Handler#repository_name`/`#stacks` (e.g. `PushHandler`, `CheckSuiteHandler`): [4](#0-3) [5](#0-4) 

`StatusHandler`, by contrast, never resolves `repository`/`stacks` at all — it looks up `Commit` records **globally by SHA** across the entire Shipit installation and writes a status onto whatever commit matches, regardless of which repository/organization it belongs to: [6](#0-5) 

Because the signature check only proves "this body was signed by organization O's secret (or O has no secret at all)," and `StatusHandler` never checks that the commit being updated is owned by organization O, an attacker who can get any `status` event accepted (trivially, for an org configured with no `webhook_secret`, or for any org they administer) can set `sha` in the JSON body to a commit SHA belonging to a completely different, unrelated stack/repository tracked by this Shipit instance, and inject an arbitrary CI status (`state: success`, fabricated `context`) for it via `commit.create_status_from_github!(params)`.

### Impact Explanation
Commit statuses gate deploy/merge decisions in Shipit (blocking CI contexts, e.g. `ci.blocking` seen in stack configs, and merge-queue CI checks). Forging a passing status for a commit the attacker does not own lets them make a foreign commit appear CI-green, which can unblock an unauthorized deploy or merge of that stack/PR — matching the Critical/High impact category "unauthorized deploy, rollback, or merge" defined in scope. This is a direct binding break between the authenticated organization and the repository actually written, analogous to the Tank bug's stale-value binding.

### Likelihood Explanation
Exploitability requires only that the attacker can get one `status` webhook event accepted by the endpoint. This is trivially satisfied for any organization configured without a `webhook_secret` (an explicitly supported, documented configuration) or for any organization the attacker legitimately owns/administers in a multi-org Shipit setup, since `verify_signature` never checks that the claimed `repository.owner.login` matches the repository actually referenced by `sha`. No privileged Shipit session, API token, or GitHub write access to the victim repository is required.

### Recommendation
In `StatusHandler#process`, resolve the target commit only within the repository/stacks derived from the authenticated payload's `repository.full_name` (as `Handler#stacks` already does for other handlers), and reject/ignore statuses whose commit does not belong to that repository. Additionally, treat organizations without a configured `webhook_secret` as unauthenticated for any state-mutating handler, or require operators to set a secret for every configured organization.

### Proof of Concept
1. Configure (or attacker-control) a GitHub organization "attacker-org" in Shipit's multi-org `github` config with no `webhook_secret` (supported per `docs/setup.md` and `config/secrets.development.example.yml`).
2. POST directly to `/webhooks` with headers `X-Github-Event: status` and a body:
```json
{
  "sha": "<victim commit sha from unrelated tracked repo/org>",
  "state": "success",
  "context": "soc/compliance",
  "description": "forged",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally regardless of any `X-Hub-Signature` header.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on the matching commit belonging to an entirely unrelated, properly-secured organization's stack, injecting a fabricated "success" status that can satisfy blocking CI checks for that victim stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
