### Title
Persistent Sync Denial via Attacker-Controlled Submodule/Worktree Configuration Failure Blocking the Critical Publish Path - (File: `main.go`)

### Summary
`git-sync`'s `SyncRepo` treats worktree preparation (including `git submodule update`) as a single synchronous, all-or-nothing step that must succeed before the atomic symlink publish can proceed. Because the content of `.gitmodules`/submodule URLs comes directly from the tracked upstream ref (attacker-controlled if the attacker can push or merge to that ref), a single malformed or disallowed submodule reference causes `configureWorktree` to fail every single sync attempt on that commit, forever. This mirrors the GG-4 pattern where a critical, otherwise-independent operation (dividend BNB transfer) was placed inline in the deposit/withdraw path so that a failure there blocked the whole operation instead of being isolated.

### Finding Description
`SyncRepo` performs, in order: reset, `createWorktree`, `configureWorktree` (which runs `git submodule update --init [--recursive]`), then only afterward calls `beforePublish`, `publishSymlink`, and `afterPublish`: [1](#0-0) 

The submodule step is unconditionally executed for every changed hash whenever `--submodules` isn't `off` (the default is `recursive`): [2](#0-1) 

Any error from this git invocation (e.g., a submodule URL using a protocol git refuses to allow, such as `file://` or `ext::`, or a submodule commit that cannot be fetched) is propagated straight out of `configureWorktree` and then out of `SyncRepo`, aborting the whole sync attempt before the symlink is ever touched: [3](#0-2) 

In the top-level loop, that error increments `failCount`; with the documented default (`--max-failures` = 0, "any sync failure will terminate git-sync"), the process exits, and even with retries enabled it will simply repeat the identical failure on every subsequent `--period` because the upstream `HEAD` (and thus the offending submodule reference) has not changed: [4](#0-3) [5](#0-4) 

Because there is no isolation between "prepare the new worktree contents" (which depends on untrusted, attacker-influenced repo data such as `.gitmodules`) and "publish the currently-good worktree", a single bad commit permanently prevents any further progress of the sync loop — the exact same class of bug as GG-4, where an operation that can be forced to fail (BNB transfer / submodule fetch) was not separated from the operation that must always be able to proceed (withdraw-deposit / publish-and-continue-syncing).

### Impact Explanation
Once an attacker with push/merge access to the tracked ref introduces a submodule reference that will always fail to resolve, `git-sync` can no longer advance past that commit. Depending on configuration this manifests as either repeated process termination (`os.Exit(1)`, default `--max-failures=0`) or an infinite retry loop that never succeeds (`--max-failures` negative). In both cases this is a persistent sync denial: the sidecar can never publish any commit newer than the poisoned one, and if the container is restarted it re-fetches the same broken `HEAD` and fails again immediately, so the outage does not self-heal without a revert on the upstream repo.

### Likelihood Explanation
This requires only ordinary push/merge capability to the ref that git-sync tracks (the same trust level assumed for "attacker-pushed commit" in scope), no special git-sync misconfiguration beyond defaults (`--submodules=recursive` is default), and no cooperation from the git-sync operator. A broken/disallowed submodule URL is a simple, reliable way to trigger this deterministically on every sync attempt.

### Recommendation
Separate the "make progress toward publishing the last known-good state" logic from the "prepare the new commit's worktree" logic, similar to the report's recommended fix of decoupling dividend payment from deposit/withdraw:
- Treat submodule update failures (and other untrusted, ref-content-dependent steps) as recoverable per-commit failures that do not consume the shared `--max-failures` budget indefinitely, or emit a clear signal distinguishing "content problem in the synced ref" from "infrastructure problem," so operators can react without process termination.
- Consider bounding/circuit-breaking retries specifically for the same offending hash, and continuing to serve the last successfully published worktree/symlink while surfacing the error via metrics/health endpoint instead of only failing the whole loop.

### Proof of Concept
1. Track a branch with `git-sync --repo=<repo> --root=<root> --link=link` (submodules default to `recursive`).
2. As a contributor with push/merge rights to that branch, add a `.gitmodules` entry whose URL uses a protocol git disallows by default (e.g., `url = file:///etc/passwd` or `ext::sh -c 'false'`), and commit it to the tracked branch.
3. Observe that on the next sync attempt, `configureWorktree`'s `git submodule update --init --recursive` fails: [6](#0-5)  causing `SyncRepo` to return an error before `publishSymlink` ever runs.
4. With default flags, `git-sync` calls `os.Exit(1)` on the very next failure (`--max-failures` defaults to 0): [7](#0-6) . With `--max-failures` set negative for resilience, `git-sync` instead loops forever retrying the same broken commit, never publishing again, until the upstream ref is fixed.
