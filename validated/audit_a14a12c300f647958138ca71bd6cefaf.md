### Title
No minimum debt/position size enforced in `liquidate` — tiny positions create liquidator-unprofitable debt that is socialized to all suppliers - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar`'s `borrow` path has no minimum debt-size check, and `liquidate` only asserts non-zero amounts (`> debt-amount u0`, `> debt-to-repay u0`, `> coll-final u0`), never a minimum notional. Because the liquidator's reward is `liq-penalty` applied proportionally to the (potentially tiny) debt/collateral being liquidated, a borrower (or coordinated Sybil of many borrowers) can open many small positions whose liquidation reward is smaller than the on-chain transaction cost of calling `liquidate`, so rational liquidators never bother liquidating them. Left unliquidated as prices move further underwater, these positions accumulate bad debt that is ultimately socialized across all suppliers of the debt asset via `socialize-debt-asset`, harming lenders who never interacted with the attacker.

### Finding Description
`liquidate` computes the liquidator's collateral bonus proportionally to the debt actually repaid: [1](#0-0) 
and the guard rails before executing only check the amounts are non-zero, with no floor on notional size: [2](#0-1) 

There is no `MIN-BORROW`/`MIN-DEBT`/minimum-position constant anywhere in the production contracts (confirmed via search of `mainnet/contracts/**`), so a borrower can open a position with an arbitrarily small debt (e.g. equal to a handful of base units of the debt token). When such a position becomes unhealthy, the liquidator's `liq-penalty`-based reward, scaled down to the tiny debt size, can be smaller than the Stacks transaction fee required to call `liquidate`, so no rational liquidator will act on it.

When a position with no collateral left is finally (or never) liquidated, any remaining unpaid debt is written off via bad-debt socialization, which mutates shared vault state (`fresh-debt-list`, `socialize-debt-asset`) affecting the debt-asset's supply-side accounting for all depositors of that vault, not just the borrower who created the tiny position: [3](#0-2) 

The victim here is every other supplier/lender in the same debt vault: the shared state is the vault's aggregate debt/supply index consumed by `socialize-debt-asset`, primed into an unliquidatable, loss-making state by the attacker's many small borrow positions, and consumed (i.e., paid for) by all lenders of that asset when the socialization fold executes.

### Impact Explanation
This lands on **protocol insolvency / permanent freezing of funds**: an attacker (or a set of attacker-controlled accounts) can open a large number of tiny borrow positions across one or more debt assets, none of which are worth liquidating once undercollateralized. As prices drift, these positions accumulate losses that are never recovered by liquidators, and when finally processed, the loss is socialized to all suppliers of that debt vault, reducing the amount they can withdraw — the same "exchange must cover bad debt to allow others to withdraw" impact identified in the referenced report.

### Likelihood Explanation
Likelihood is comparable to (or higher than) the referenced Sherlock finding: it requires no privileged access, and can occur either through a deliberate Sybil-style attack (many cheap borrow calls, each below the liquidator-profitability threshold) or organically, since Zest, unlike the audited perpetual protocol, has no admin-adjustable per-position liquidation-fee floor documented in the reviewed contracts and no minimum position size at all. The severity depends on Stacks transaction fee levels versus `LIQ-PENALTY-MIN`/`LIQ-PENALTY-MAX` values, which was flagged as Medium in the analogous audit even under L2 conditions with cheaper gas; Stacks transaction costs are not obviously lower, making the attack at least as practical here.

### Recommendation
Introduce a minimum total debt/notional value (enforced in `borrow` and re-checked in `liquidate`/partial-liquidation math) below which positions cannot be opened, and/or round the liquidator's fee up rather than down so that any liquidatable position always yields a liquidator reward that exceeds a configurable minimum absolute value, ensuring liquidation always remains economically rational regardless of position size.

### Proof of Concept
1. Attacker calls `borrow` (or the deposit+borrow flow) many times, each time depositing minimal collateral and borrowing a debt amount just large enough to pass `> debt-amount u0` type checks (`mainnet/contracts/market/v0-4-market.clar:1490`), but small enough that `liq-penalty` on that debt (`calc-liq-collateral-repay`, lines 726-729) yields a liquidator profit smaller than the network fee for calling `liquidate`.
2. Repeat across thousands of positions/accounts; each position individually falls below LTV-LIQ-FULL over time (oracle price drift), becoming eligible for liquidation but unprofitable to liquidate.
3. No liquidator calls `liquidate` on these positions because gas/fees exceed the reward.
4. Positions continue to accrue interest debt with no offsetting seizable collateral; once collateral is fully eroded, any eventual liquidation attempt (or protocol-triggered cleanup) hits the `no-collateral-left` branch and calls `socialize-debt-asset` across the fold at lines 1534-1560, socializing the loss to all suppliers of that debt vault.
5. Aggregate losses across the many tiny positions accumulate into a material insolvency for the debt vault's suppliers, exactly mirroring the "lots of small losses equivalent to one large loss" impact from the referenced report.
