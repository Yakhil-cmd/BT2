### Title
Race window between `handleResult(bStable, true)` and the deferred, separately-locked stability commit lets the main chain stability point advance inconsistently across concurrent validations - ([File: main_chain.js])

### Summary
The CVE describes a race between a state transition (grant-table version change) and a concurrent operation (page mapping) that consumes the pre-transition state, leaving freed pages mapped and usable after the free — a classic "decide based on stale/in-flight state, then let the real state change land later" TOCTOU. `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()` has the same shape: it computes a stability verdict, immediately hands that verdict back to the caller via `handleResult(bStable, true)`, and *only afterward* performs the actual DB mutation that makes the unit stable — under a different lock and a different connection than the one the caller is using.

### Finding Description
In [1](#0-0)  `determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, earlier_unit, arrLaterUnits, bStableInDb, handleResult)`:

1. It runs `determineIfStableInLaterUnits(conn, earlier_unit, arrLaterUnits, ...)` on the caller's own connection/transaction to decide if `earlier_unit` is stable "in view of" `arrLaterUnits`.
2. If it decides the unit *is* stable but wasn't marked stable yet (`bStable && !bStableInDb`), it calls `handleResult(bStable, true)` **immediately**, at [2](#0-1)  — returning control (and the "stable" verdict) to the caller before any persistent state change has happened.
3. Only *after* returning that verdict does the function go on to actually advance the stability point: it acquires a completely different lock, `mutex.lock(["handleJoint"], ...)`, and re-reads state from the shared connection pool (`db`, not the caller's `conn`) to perform `stabilizeMci()` for each newly-stable mci, as seen at [3](#0-2) .

The one caller that is aware of this hazard, `network.js`'s `tryToAdvanceStabilityPointForCatchupAATrigger`, explicitly works around it by using "a dedicated connection so that interleaving writes from other tasks don't interfere with this check", per the comment at [4](#0-3) . This shows the ocore authors are aware that concurrent invocations of this stability-advancement logic can interleave and corrupt each other's view, but the workaround is applied only to that one call site.

The primary, unprivileged-reachable call site is inside unit validation itself, at [5](#0-4) , where `validateParents()` calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, last_ball_unit, objUnit.parent_units, objLastBallUnitProps.is_stable, function(bStable, bAdvancedLastStableMci){ ... })`. This is driven directly by any unit an attacker posts (an unprivileged unit poster fully controls `last_ball_unit`/`parent_units` via the joint they submit), and it happens inside `validation.validate()`'s per-author-address mutex (`mutex.lock(arrAuthorAddresses, ...)` at [6](#0-5) ), which is *not* the same lock (`["handleJoint"]`/`["write"]`) used for the actual stability commit.

Because two units from *different* authors can be validated concurrently (each with its own author-address mutex and its own DB connection), two overlapping calls into `determineIfStableInLaterUnitsAndUpdateStableMcFlag`/`stabilizeMci` for overlapping or adjacent mci ranges are possible: each call reads `last_stable_mci` from the shared `db` pool independently, computes `new_last_stable_mci`, and then loops calling `stabilizeMci(mci)` for `mci` in `[last_stable_mci+1 .. new_last_stable_mci]` — all while only holding the `["handleJoint"]` mutex for *its own* invocation, taken *after* the verdict was already handed back to its own caller. Depending on how `stabilizeMci`/`markMcIndexStable` update the in-memory caches (`storage.assocStableUnits`, `storage.assocStableUnitsByMci`, etc. — the same caches manipulated in `storage.js` around [7](#0-6) ) versus the DB rows, two racing stabilizations can double-process or skip an mci, or leave the in-memory cache and DB relationally inconsistent between concurrently-running validations, i.e. exactly the "freed page still mapped" pattern: one code path treats a unit/mci as already stabilized (and lets a dependent unit validate/commit against that assumption) while the actual persistent stabilization for that mci is still in flight or applied out of order on a different connection.

### Impact Explanation
If two concurrent unit submissions can trigger overlapping, non-mutually-excluded stability advancement, the risk is that different in-process views of "which mci/unit is stable" diverge from what is durably committed to the database, which is precisely the class of impact this analysis is permitted to accept: **node disagreement on validity or stability**. In the worst case this could let a node accept as final/stable an output that a concurrently-running stabilization pass has not actually committed as stable yet (or vice-versa), enabling a payment referencing that output to be treated as spending a stable input when it should still be conditional — a precursor to accepting a **double-spend of an output that is not actually final** once two racing "stable" verdicts land inconsistently across the cache/DB boundary.

### Likelihood Explanation
Likelihood is moderate-to-low in the strict sense of "always reachable," because:
- The window requires precise timing of two units from different authors arriving and being validated concurrently, each needing their own `last_ball_unit`/parents to trigger the "not yet stable but should be" advancement branch.
- Part of the theoretical race is defended: when the *same* caller learns `bAdvancedLastStableMci===true` synchronously, `validation.js` returns a transient error and retries rather than committing (`validation.js:811-812`), reducing self-interference.
- However, the codebase's own defensive comment in `network.js` around `tryToAdvanceStabilityPointForCatchupAATrigger` confirms that interleaving of separate stabilization attempts on different connections is a real, previously-identified concern that was only patched for that one path, not universally serialized behind a single lock guarding the entire "compute stability -> commit stability" sequence.

### Recommendation
Serialize the entire "compute-then-commit" stability sequence in `determineIfStableInLaterUnitsAndUpdateStableMcFlag` under a single lock acquired *before* the stability verdict is computed (not just before the DB commit), or make the verdict provisional until the same lock that performs `stabilizeMci` has confirmed it, mirroring the dedicated-connection workaround already applied in `tryToAdvanceStabilityPointForCatchupAATrigger` so that all callers — including the one inside `validation.js`'s per-unit validation path — are protected consistently.

### Proof of Concept
Not independently reproducible from static analysis alone: this requires two concurrently validated units from different authors, each referencing different `last_ball_unit`s whose parents make them individually appear "stable" at read time, timed so that both invoke `determineIfStableInLaterUnitsAndUpdateStableMcFlag`'s deferred commit phase before either completes. Full confirmation would require dynamic/concurrency testing of `main_chain.js`'s `stabilizeMci`/`markMcIndexStable` (whose bodies were not retrieved in this investigation — grep found them declared in `main_chain.js` but their implementations were not inspected here) to verify whether they are individually idempotent/safe against concurrent overlapping invocation, or whether they mutate `storage.assocStableUnits`/`assocStableUnitsByMci` non-atomically relative to the DB commit. This is a genuine gap in the analysis: I could not confirm the internals of `stabilizeMci`/`markMcIndexStable` within the available tool budget, so the exact mechanics of any resulting inconsistency (versus the possibility that lower-level locking elsewhere fully serializes them) remain unverified.

async function shrinkCache(){
	if (Object.keys(assocCachedAssetInfos).length > MAX_ITEMS_IN_CACHE)
		assocCachedAssetInfos = {};
	console.log(Object.keys(assocUnstableUnits).length+" unstable units");

	var arrAuthorsUnits = Object.keys(assocCachedUnitAuthors);
	var arrWitnessesUnits = Object.keys(assocCachedUnitWitnesses);
	if (arrPropsUnits.length < MAX_ITEMS_IN_CACHE && arrAuthorsUnits.length < MAX_ITEMS_IN_CACHE && arrWitnessesUnits.length < MAX_ITEMS_IN_CACHE && arrKnownUnits.length < MAX_ITEMS_IN_CACHE && arrStableUnits.length < MAX_ITEMS_IN_CACHE)

	if (min_retrievable_mci === null)

	readLastStableMcIndex(db, function(last_stable_mci){
		const top_mci = Math.min(min_retrievable_mci, last_stable_mci - constants.COUNT_MC_BALLS_FOR_PAID_WITNESSING - 10);

					});

	});
