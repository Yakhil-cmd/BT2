### Title
API token stack-scope bypass in CCMenu controller allows reading state of stacks the token was never authorized for - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`) can only ever operate on that single stack, by having every subclass resolve the target stack through the scoped `stacks` relation. `Shipit::Api::CCMenuController` overrides the `stack` accessor to bypass that relation entirely and resolve the stack directly from the unscoped `Stack` model, so the permission check (`read:stack`) is satisfied while the actual object acted upon is not the one the token was bound to — the same "authorization decision computed over one thing, action performed on another" pattern as the referenced NFTX `_sendForReceiver` bug, where the completion signal (success) didn't cover the actual branch taken.

### Finding Description
`Shipit::Api::BaseController#stacks` restricts the queryable set of stacks to the one the API client was scoped to when it has a `stack_id`: [1](#0-0) 

Every controller that inherits `stack` from `BaseController` (e.g. `DeploysController`, `LocksController`) therefore has its `stack` resolved via this scoped relation, and `Stack.from_param!` will raise/404 if the requested `stack_id` isn't the one the client is bound to.

`CCMenuController`, however, defines its own `stack` method that talks to `Stack` directly, not through `stacks`: [2](#0-1) 

`require_permission :read, :stack` only checks that the permission string `"read:stack"` is present in `current_api_client.permissions` via `ApiClient#check_permissions!`: [3](#0-2) 

It never checks *which* stack is being read against `current_api_client.stack_id`. Because `CCMenuController#stack` resolves `params[:stack_id]` against the global `Stack` table instead of the scoped `stacks` relation, an `ApiClient` created with a `stack_id` restriction (as in the `here_come_the_walrus` fixture) — whose token is only supposed to authorize `read:stack` for its own stack — can pass an *arbitrary* `stack_id` in the request and successfully read another stack's latest deploy/rollback status: [4](#0-3) 

This mirrors the report's root cause exactly: the check that is supposed to gate the action (`_receiver.isContract` branch signalling success / the token's `stack_id` scope) doesn't cover the actual branch taken (the else/non-contract transfer / the direct `Stack.from_param!` lookup), so the binding "stack a token authorizes == stack it touches" is broken.

The equality that should hold is:
`stack the token authorizes (current_api_client.stack_id)` == `stack the controller action touches (params[:stack_id] resolved via Stack.from_param!)`

Before the bug: for every other stack-scoped controller, both sides are the same because `stack` is resolved through `stacks.from_param!`.
After: in `CCMenuController`, the left side is still the client's bound `stack_id`, but the right side becomes any stack ID supplied in the URL, since resolution bypasses the `stacks` scoping relation.

### Impact Explanation
A holder of a stack-scoped API token (e.g. one issued for CI status widgets, since `CCMenuUrlController` mints exactly this kind of restricted, `read:stack`-only token bound to a single stack) can enumerate and read the deploy/rollback status (`stack.deploys_and_rollbacks.last`, including stack name, last build label/status/time) of any stack in the Shipit instance, not just the one the token was scoped to. This is an unauthorized read of stack state that the token issuer never intended to grant, i.e., an authorization-scope escalation across stacks reachable by any valid, even narrowly-scoped, API credential.

### Likelihood Explanation
Any valid API client credential (including deliberately narrow, stack-scoped tokens meant only to expose CI-status badges) is sufficient; no additional privilege is required. Stack IDs (`owner/repo/env`) are predictable/enumerable (they mirror GitHub repo names and environment strings), making exploitation straightforward once any single stack-scoped token is obtained.

### Recommendation
Have `CCMenuController#stack` resolve through the scoped `stacks` relation from `BaseController`, exactly as the other stack-scoped controllers do, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override so it inherits the scoped behavior, or explicitly re-checking `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id: <stack A>` with only `read:stack` permission (as fixture `here_come_the_walrus` does): [4](#0-3) 
2. Authenticate with that client's token and call `GET /api/stacks/<stack B>/ccmenu`, where `<stack B>` is a different stack the token was never scoped to.
3. Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` directly rather than the scoped `stacks.from_param!`, and `require_permission :read, :stack` only checks the permission string and not the target stack, the request succeeds and returns stack B's build status/name, which the token holder was never authorized to see: [5](#0-4)
