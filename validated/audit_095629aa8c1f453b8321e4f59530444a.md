## Title
Authentication/Integrity Bypass via Loose Comparison of Signed Contract Text - (File: wallet.js)

### Summary
In `wallet.js`, the `arbiter_contract_response` handler verifies that a peer's cryptographically signed acceptance message actually matches the contract's agreed-upon `title` text. The comparison uses JavaScript's loose `!=` operator instead of a strict `!==`/type-checked comparison, mirroring the CVE-2024-34340 root cause (a loose `==` comparison of attacker-influenced, type-flexible values used as a security gate).

### Finding Description
When a peer responds to an arbiter contract offer with `status: "accepted"`, the node validates the signed message and then checks that the signed content matches the expected contract title: [1](#0-0) 

The attacker (the peer/paired device) fully controls `body.signed_message`, which is base64-decoded and `JSON.parse`d into `objSignedMessage`: [2](#0-1) 

`signed_message.validateSignedMessage()` does not constrain the type of the `signed_message` field — it only checks that the key `'signed_message'` exists in the object, never that it is a string: [3](#0-2) 

Because `objSignedMessage.signed_message` can be any JSON type (array, number, boolean, object) while `objContract.title` is a plain string, the check `objSignedMessage.signed_message != objContract.title` is subject to JavaScript type coercion. For example, a single-element array whose element stringifies to the title (`[title]`) is loosely equal to the string `title` (`[title] == title` evaluates `true`), even though the actual value that was hashed and signed via `objectHash.getSignedPackageHashToSign()` is structurally different from the plain title string. This lets a malicious peer produce a validly-signed package whose real signed payload differs from the displayed/expected `title`, yet still pass the equality gate meant to bind the signature to that exact title text.

This is the same bug class as CVE-2024-34340: a security-relevant equality check on attacker-influenced data uses loose (`!=`) instead of strict (`!==`) comparison, allowing type-juggling to defeat the intended content-binding guarantee.

### Impact Explanation
The arbiter contract flow relies on the peer's signature over the exact `title` text as the auditable proof of agreement, later used for dispute resolution with the arbiter (`openDispute`, which reuses `objContract.title`). By exploiting the loose comparison, a malicious counterparty can have their acceptance recorded as valid ("accepted" status, contract funds flow proceeds) while their actual signed payload does not match the title that was agreed to and displayed to the other party. This undermines the integrity of the acceptance record used in fund-affecting dispute resolution, which can be leveraged to contest or manipulate arbitration outcomes — a concrete node-disagreement/fund-related integrity issue reachable purely by a paired device sending a crafted `arbiter_contract_response` message.

### Likelihood Explanation
The attack requires only that the victim node has an outstanding arbiter contract offer to a peer device (`is_incoming=false`) and that the peer sends a specially-crafted `arbiter_contract_response` message with a JSON `signed_message` value engineered to loosely equal the title. No special privileges beyond being a paired correspondent are needed, and the message path (`device.js` → `wallet.js handleMessageFromHub`) is directly reachable by any paired device.

### Recommendation
Replace the loose comparison with a strict, type-checked comparison:
```js
if (err || objSignedMessage.authors[0].address !== objContract.peer_address
    || typeof objSignedMessage.signed_message !== 'string'
    || objSignedMessage.signed_message !== objContract.title)
    return callbacks.ifError("wrong contract signature");
```
Additionally, `signed_message.validateSignedMessage()` should validate that `objSignedMessage.signed_message` is of an expected type (e.g., string) whenever the caller expects string semantics, to prevent similar type-confusion issues in other callers.

### Proof of Concept
1. Alice sends an arbiter contract offer to Bob with `title = "Pay 100 for goods"`.
2. Bob (malicious) crafts a signed message where `signed_message` is the array `["Pay 100 for goods"]` instead of the string, signs it with his address's key (he owns the key, so `validateSignedMessage` succeeds), and base64-encodes it as `body.signed_message`.
3. Bob sends `arbiter_contract_response` with `status: "accepted"` and this payload.
4. On Alice's node, `objSignedMessage.signed_message != objContract.title` evaluates to `false` (`["Pay 100 for goods"] == "Pay 100 for goods"` is `true` in JS), so the check passes.
5. The contract is marked `"accepted"` even though the cryptographically signed payload is not the plain title string, breaking the integrity guarantee relied upon for later dispute arbitration.
