### Title
API clients can forge the acting user identity on privileged stack operations via the `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Api::BaseController#identify_user` binds `current_user` to any existing `Shipit::User` by a case-insensitive `login` match taken directly from the client-supplied `X-Shipit-User` header, with no verification that the authenticated `ApiClient` (or the caller behind it) actually corresponds to that GitHub identity. This mirrors the reported `setClientOwner` flaw: a "name" (here, a GitHub login) can be bound to a privileged identity by an actor whose own credential carries no such privilege, and the binding is trusted downstream for privileged actions (deploy, rollback, abort, lock) without re-validating the caller against the identity being claimed.

### Finding Description
Authentication in the API layer is a two-part scheme:
1. `authenticate_api_client` verifies the bearer token against `ApiClient.authenticate`, establishing `current_api_client` and its `permissions`/`stack_id` scope [1](#0-0) .
2. `current_user`/`identify_user` separately determines *who* is credited/recorded as the human actor for the operation, purely from an unauthenticated header:
```ruby
def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
``` [2](#0-1) 

There is no cross-check that the login supplied in `X-Shipit-User` corresponds to the entity that owns the `ApiClient` token (`ApiClient#creator`), nor any check of `User#authorized?`/team membership at the point of binding. Any caller holding a valid `ApiClient` token — even one scoped to a single stack with minimal permissions (e.g. only `deploy:stack`) — can set this header to the `login` of any other `Shipit::User` record (including privileged human operators who are members of `Shipit.github_teams`) and have that identity bound to `current_user` for the request.

This binding is equality-critical: `identity claimed via X-Shipit-User == User recorded as actor for privileged Task/Deploy/Rollback/Lock state`, but the left side is never validated against the right side's actual authentication (session, OAuth `github_id`) the way `Authentication#find_current_user` does via `session[:user_id]` [3](#0-2) . The forged `current_user` then flows into state-changing, permission-gated operations:
- `stack.trigger_deploy(commit, current_user, ...)` in `Api::DeploysController#create` [4](#0-3) 
- `stack.trigger_task(...)`/`task.abort!(aborted_by: current_user)` in `Api::TasksController` [5](#0-4) 
- `stack.lock(params.reason, current_user)` in `Api::LocksController` [6](#0-5) 
- `active_task.abort!(aborted_by: current_user, ...)` / `deploy.trigger_rollback(current_user, ...)` in `Api::RollbacksController` [7](#0-6) 

### Impact Explanation
This lets a holder of a narrowly-scoped `ApiClient` token permanently and falsely attribute deploys, rollbacks, aborts, and stack locks to any other Shipit user of the operator's choosing — including forging attribution to privileged human operators for actions the forger actually performed. It corrupts the audit trail used to reconstruct who authorized a deploy/rollback/lock (the exact binding — GitHub identity vs. the `User` recorded as responsible for the action — that this scan's rules call out), which undermines accountability for "an unauthorized deploy, rollback" review after the fact. It does not, on its own, bypass the `ApiClient#check_permissions!` scope check (the caller still needs `deploy:stack`/`lock:stack` etc.), so it does not independently escalate into the `Critical` tier, but it directly breaks the actor-identity guarantee assumed by every `current_user` consumer in the API layer.

### Likelihood Explanation
Any party in possession of a legitimate but narrowly-scoped `ApiClient` token (e.g., a CI system granted only `deploy:stack` for one stack) can trivially add an `X-Shipit-User` header to every request; the endpoint requires no additional secret to do so, since `identify_user` performs no ownership check between the token and the claimed login.

### Recommendation
- Validate that the login supplied via `X-Shipit-User` corresponds to the `ApiClient#creator`, or remove the header-based identity override entirely in favor of deriving the acting user solely from the authenticated principal.
- If third-party attribution is a required feature, restrict it to `ApiClient`s explicitly granted a dedicated permission (e.g. `impersonate:user`), and log/audit any such impersonation.
- Add regression tests asserting that `current_user` cannot be set to a `User` unrelated to the authenticated `ApiClient`.

### Proof of Concept
1. Provision a low-privilege `ApiClient` scoped to a single stack with only `deploy:stack` permission (as in `here_come_the_walrus` fixture) [8](#0-7) .
2. Using this token's Basic-Auth credentials, send:
```
POST /api/stacks/<owner>/<repo>/<env>/deploys
Authorization: Basic <token>
X-Shipit-User: walrus
Content-Type: application/json

{ "sha": "<commit-sha>" }
```
3. `identify_user` resolves `current_user` to the `walrus` `User` record purely from the header [9](#0-8) , and `Api::DeploysController#create` records the deploy as triggered by `walrus`, even though the actual caller only possesses the scoped `here_come_the_walrus` token and no session/OAuth credential belonging to `walrus` [4](#0-3) .

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil

          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

      end
