### Title
Unbounded In-Memory Buffering of Git Subprocess Output Enables Return-Bomb Style Memory-Exhaustion DoS - (File: pkg/cmd/cmd.go)

### Summary
`git-sync` executes every `git` subcommand (fetch, ls-remote, log, worktree, config, etc.) through `pkg/cmd.Runner.Run`/`RunWithStdin`, which captures the entire stdout and stderr of the subprocess into unbounded, in-memory `bytes.Buffer`s before any length check is performed [1](#0-0) . This is directly analogous to the OmniPortal "return bomb" bug class: data returned from an external, potentially attacker-influenced source (there, an XCall's return data; here, a git remote's protocol responses/output) is unconditionally loaded fully into memory before the caller has a chance to bound or reject it.

### Finding Description
`runWithStdin` allocates `outbuf`/`errbuf` as unbounded `bytes.Buffer`s and assigns them directly as `cmd.Stdout`/`cmd.Stderr` for every invocation of the `git` binary [2](#0-1) . There is no `io.LimitReader`, size cap, or streaming/discard mechanism anywhere in this path — the full output is buffered, converted to a string, and only afterward is it inspected or logged [3](#0-2) .

Because `git.Run`/`git.RunWithStdin` is the sole mechanism `main.go` uses to invoke `git fetch`, `git worktree`, `git log`, `git config`, etc. against the configured `--repo`, any content or protocol behavior controlled by that remote (e.g., unusually large ref advertisements, verbose/large error output on stderr, or huge blob/commit data surfaced through `git log`/`git show` style commands) is buffered in full in the git-sync process's own memory before git-sync's logic ever gets to decide the data is "too large" — mirroring the OmniPortal pattern where `result` was loaded into memory in `_exec(address,uint64,bytes)` before the `xreceiptMaxErrorBytes` truncation was applied in `_exec(XTypes.Msg)`.

### Impact Explanation
If the configured git remote is malicious or compromised (the realistic "untrusted content source" for `git-sync`, analogous to an attacker submitting oversized XCall return data), it can cause `git` subcommands invoked by `git-sync` to emit very large stdout/stderr (e.g., via crafted refs, error messages, or verbose output), which is fully buffered into the parent Go process's heap. Repeated or large enough responses can drive git-sync's memory usage far beyond expectations, leading to OOM termination of the sidecar and a **persistent sync denial** — the same "unprofitable/DoS" outcome the original report describes for relayers, but manifesting as resource exhaustion of the git-sync sidecar instead of gas cost to a relayer.

### Likelihood Explanation
This requires the git remote itself to be malicious/compromised or reachable via a MITM able to inject large responses into the git protocol/transport; it does not require any special git-sync flags beyond normal operation, since every code path funnels through `Runner.Run`/`RunWithStdin` [4](#0-3) . Likelihood is moderate: it depends on the operator syncing from a repository whose upstream trust boundary is imperfect (e.g., third-party or user-contributed repos, or an attacker who briefly gains push/control of the configured remote), which is a scenario `git-sync`'s threat model already contemplates (untrusted repo content).

### Recommendation
Wrap `cmd.Stdout`/`cmd.Stderr` with size-bounded readers (e.g., `io.LimitReader` combined with a bounded buffer, similar to `excessivelySafeCall`'s bounded-copy approach) in `pkg/cmd/cmd.go`'s `runWithStdin`, truncating and flagging output once it exceeds a configurable maximum before the full data is retained in memory, rather than buffering everything up front and only then trimming/logging it.

### Proof of Concept
Not independently executable in this read-only review; the root cause is structural and evidenced by the unbounded `bytes.NewBuffer(nil)` allocations wired directly as `cmd.Stdout`/`cmd.Stderr` for all `git` invocations [2](#0-1) , with no downstream size limiting in `main.go`'s call sites (23 call sites of `git.Run`/`git.RunWithStdin`) before the values are used. A full exploit chain (crafting a git server response large enough to reliably OOM the sidecar) was not verified against a live git-sync instance in this review; confirming exact memory-exhaustion thresholds would require running git-sync against a controlled malicious git remote in a Devin session with file/terminal access.

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
