### Title
Session fixation on GitHub OAuth login due to missing session reset in `GithubAuthenticationController#callback` - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
The reported bug class is "an approval action re-binds/executes state without re-validating a trust boundary that should be re-established on completion" (replaying an already-approved deposit against the same investor binding). The closest reachable analog in Shipit is the GitHub OAuth login callback, which writes the authenticated identity into the *current* session without first invalidating/regenerating it. This breaks the equality that should hold at an authentication boundary: `session_id issued to attacker (pre-login)` == `session_id session[:user_id] is bound to (post-login)` should never hold, but in this code path it does.

### Finding Description
`GithubAuthenticationController#callback` completes the OmniAuth GitHub flow and writes the resulting `User#id` straight into `session[:user_id]` without ever calling `reset_session` (or otherwise rotating the session identifier): [1](#0-0) 

Compare this with `Shipit::Authentication#force_github_authentication`, where the engine authors explicitly call `reset_session` when a stale/legacy credential is detected, showing the engine's own code recognizes the need to rotate the session at trust-boundary transitions: [2](#0-1) 

`current_user` is resolved purely from `session[:user_id]`: [3](#0-2) 

Because the identifier that binds a browser session to a `User` record is never rotated at the moment of authentication, if an attacker can get a victim's browser to carry a session identifier the attacker already knows (a fixation), completion of the GitHub OAuth dance by the victim will cause `sign_in_github` to bind the victim's `User` (and therefore their `github_access_token`) to that already-known session, without the application ever re-issuing a fresh session key. The route is unauthenticated and reachable by anyone (`GithubAuthenticationController` does not include `Shipit::Authentication`), so no ApiClient token, webhook secret, or privileged account is needed to reach the vulnerable code: [4](#0-3) 

### Impact Explanation
If exploited, an attacker who fixates a session and later hijacks it after the victim authenticates gains a fully authenticated Shipit session bound to the victim's `User`, including the victim's decrypted `github_access_token` usage via `github_api`/`current_user`, and any privileges the victim's GitHub team membership grants (deploy, lock, rollback, merge-queue actions). This matches the explicitly listed High-severity impact category "session fixation / forced OAuth completion."

### Likelihood Explanation
Exploitability is fully dependent on the session store the host application configures for this Rails engine (e.g. cookie store vs. a server-side/shared store such as `ActiveRecord::SessionStore` or a Redis-backed store). Since Shipit already requires Redis for other subsystems (Pubsubstub), a server-side session store is a plausible deployment choice, which is the classical precondition for session-ID fixation attacks. I could not confirm from the indexed engine code which store the shipped/documented deployment uses (session store selection is host-app configuration, outside `app/**`/`lib/shipit/**`), so likelihood should be treated as **configuration-dependent, not certain** — the root-cause code defect (missing session reset at login) is present and verifiable in-engine regardless.

### Recommendation
Call `reset_session` (or `session.regenerate_id` if only the identifier needs rotating while preserving `omniauth.origin`) in `GithubAuthenticationController#callback` immediately before assigning `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `Shipit::Authentication#force_github_authentication`.

### Proof of Concept
1. Attacker visits the Shipit instance (unauthenticated) and captures the session cookie value issued by the app for their own browser (or, on a shared-store deployment, otherwise causes a known session identifier to be set in the victim's browser — the classic fixation delivery vector, e.g. via a subdomain able to set cookies for the shared parent domain, or a value accepted via URL/cookie injection depending on host session-store configuration).
2. Attacker gets the victim to browse the site using that fixed session identifier and to click "Sign in with GitHub".
3. Victim completes the real GitHub OAuth consent flow; GitHub redirects back to `/github/auth/github/callback`.
4. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on the *existing* (attacker-known) session, without rotating the session key: [5](#0-4) 
5. Attacker reuses the known session identifier and is now recognized as the victim by `current_user`/`find_current_user`, gaining the victim's authenticated Shipit privileges.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
