### Title
`or` in oscript/AA formula evaluation aborts entirely on a single sub-expression error instead of trying remaining branches - ([File: formula/evaluation.js])

### Summary
In `formula/evaluation.js`, the `or` operator evaluates its operands sequentially with `async.eachSeries` and treats any `fatal_error` raised by one operand (e.g. a missing `data_feed`/`attestation`/`in_data_feed` lookup) as a hard abort for the whole `or` expression, even when a subsequent, independent operand could legitimately evaluate to `true`. This mirrors the reported bug class: one failing/broken "adapter" (here, one oracle/data source) causes an operation that should tolerate partial failure (a redundancy `or` across independent sources) to fail entirely.

### Finding Description
The `or` handler is: [1](#0-0) 

For each operand it calls `evaluate(param, ...)`. If that operand internally triggers `setFatalError` (for example a `data_feed` lookup that doesn't find a value and has no `ifnone`, as seen in the `data_feed` case), the global `fatal_error` flag is set and the callback returns `false`: [2](#0-1) 

Back in the `or` loop, after each operand's evaluation the code checks `if (fatal_error) return cb2(fatal_error);` which stops `async.eachSeries` immediately with that error, and the final callback computes `cb(!err ? prevV : false)` — i.e. the whole `or` resolves to `false` (and the enclosing computation is aborted as a fatal error) regardless of whether a later, unevaluated operand would have returned `true`. [1](#0-0) 

This is different from a normal boolean `or` semantics where independent conditions should be tried on their own merits; a temporary/permanent problem with one oracle source (analogous to a "broken/paused adapter") short-circuits evaluation and prevents the other, functioning branch from being considered — the same "one bad dependency reverts everything" pattern described in the report for `AssetManager`'s money-market adapter loop.

Once `fatal_error` is set, `evaluate` on any nested call immediately short-circuits with `false` (`if (fatal_error) return cb(false);`), so no other part of the formula (nor any sibling `or`/`and` at any nesting level above it) can recover from this failure: [3](#0-2) 

This formula evaluator is shared by both AA trigger/response formulas and non-AA `['formula', ...]` address-definition conditions (`validateAuthentifiers`/`evaluateAssetCondition` path in `definition.js`), so it is reachable by any unprivileged address owner who defines a spending condition, or any AA author/trigger sender whose formula combines redundant, independent oracle checks with `or`.

### Impact Explanation
- For an address whose spending condition is `['formula', "data_feed[[oracles=A,...]]==X or data_feed[[oracles=B,...]]==X"]` (a common redundancy pattern using two independent oracles so that funds remain spendable if either oracle posts the expected value), a temporary outage or delay from oracle A (feed not yet posted) makes the whole `or` fail even though oracle B has already posted the matching value. This can freeze legitimate spending of funds that should be authorized.
- For an AA whose bounce/response logic uses `or` combining a `data_feed`/`attestation`/`in_data_feed` check with another independent check, a single missing data feed forces the whole trigger to bounce (losing the bounce fee for the sender) even when the AA logic should otherwise proceed via the alternative branch. Repeated triggers can be perpetually and unnecessarily bounced as long as one of the referenced oracles is stale/unavailable, causing sustained inability to interact with the AA (fund freezing / DoS on otherwise valid operations) — the direct analog of "deposit/withdraw/rebalance reverted because one adapter is broken."

### Likelihood Explanation
This requires only an ordinary user to define a definition/AA formula containing an `or` of two data-source-dependent sub-expressions (a documented, encouraged pattern for oracle redundancy) and one of the referenced oracles to be late, stale, or to never publish the specific feed/attestation queried. No malicious peer, node, or privileged actor is needed — it's a self-inflicted DoS/freeze triggered purely by normal, expected oracle availability variance, making it plausible in production usage of formulas with redundant oracle conditions.

### Recommendation
In the `or` (and similarly `and`, where appropriate) evaluation loop in `formula/evaluation.js`, distinguish between a data/lookup failure local to one operand (e.g., "data feed not found") and a truly fatal parsing/type error. For `or`, if an operand's failure is of the "value not found" class, treat it as `false` for that operand and continue evaluating remaining operands instead of immediately calling `setFatalError`/aborting via the global `fatal_error` flag, so that redundancy conditions (`or` over independent oracle checks) behave as intended.

### Proof of Concept
1. Define an address (or AA trigger condition) with:
   `['formula', "data_feed[[oracles='ORACLE_A', feed_name='price']]==100 or data_feed[[oracles='ORACLE_B', feed_name='price']]==100"]`
2. Have `ORACLE_B` post a data feed unit with `price=100` (stable), but `ORACLE_A` never posts a `price` feed.
3. Attempt to spend from the address (or trigger the AA) — evaluation reaches the `data_feed` case for `ORACLE_A` first (order per formula text), which fails with `"data feed price not found"`, calling `setFatalError` and setting `fatal_error=true`.
4. In `formula/evaluation.js:400-425`, the `or` loop's `if (fatal_error) return cb2(fatal_error);` fires before the second operand (`ORACLE_B`, which would satisfy the condition) is ever evaluated, and the whole `or` resolves to `false`/the formula evaluation aborts, denying the spend/bouncing the trigger despite `ORACLE_B`'s valid, matching feed.
