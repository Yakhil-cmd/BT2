### Title
API clients can impersonate arbitrary Shipit users via the unauthenticated `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController#current_user` trusts a client-supplied `X-Shipit-User` header to determine which `User` record initiated an API action, with no verification that the authenticated `ApiClient` (or the human behind it) is actually that user. This breaks the binding between "the credential that was authenticated" (the `ApiClient` Basic-Auth token) and "the `User` identity that gets attributed/used for the action," which is analogous to the ERC777-callback report's pattern of an unprivileged party manipulating a value that downstream trust decisions rely on without it being covered by the actual authentication check.

### Finding Description
`authenticate_api_client` verifies only the `ApiClient` bearer token via `BasicAuth`/`ApiClient.authenticate` [1](#0-0) . Separately, `current_user` is derived from an arbitrary request header instead of anything cryptographically tied to the authenticated client: [2](#0-1) 

Any caller holding a valid `ApiClient` token (which only proves permission on operations like `deploy:stack`, `lock:stack`, etc. per `ApiClient#check_permissions!` [3](#0-2) ) can set `X-Shipit-User` to the login of any existing `Shipit::User` and have that identity bound to the resulting action, e.g. `stack.trigger_deploy(commit, current_user, ...)` [4](#0-3) , `stack.lock(params.reason, current_user)` [5](#0-4) , or `MergeRequest.request_merge!(stack, params[:id], current_user)` [6](#0-5) . Tests confirm the header is trusted as the deploy author with no additional check: [7](#0-6) .

The equality that should hold is: `authenticated credential == identity attributed to the action`. Instead, the engine enforces only `authenticated credential -> permission scope`, while `identity attributed to action = attacker-chosen header value`, with no relationship between the two.

### Impact Explanation
This allows an unprivileged holder of a low-trust API token (one that only needs `deploy:stack`/`lock:stack`/`write:stack` permission on a given stack, not any relationship to the impersonated human) to attribute deploys, rollbacks, locks, and merge requests to any other Shipit user by login. Because `SHIPIT_USER`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` env vars used for the deploy commands are derived from this attacker-chosen user (`lib/shipit/task_commands.rb`), and audit trails (`aborted_by`, `deploy.user`, `lock` author) are populated from it, this is a genuine authentication/identity-binding break that corrupts audit trail integrity and can be used to frame or hide behind another user for an unauthorized deploy/rollback/merge/lock action — matching the "unauthorized deploy/rollback/merge" impact criterion.

### Likelihood Explanation
Requires only possession of a valid `ApiClient` token with the relevant scope for the target endpoint — the same precondition already needed to legitimately call these endpoints. No secret guessing, no privileged account, and no session is required beyond the API token itself, so any party issued an API client (even one scoped to a single stack via `ApiClient#stack_id`) can perform this identity spoof for free.

### Recommendation
Do not trust a raw client-supplied header for identity attribution. Bind the acting user to the `ApiClient` record itself (e.g., require an `ApiClient` to be created/scoped to exactly one `User` and use that association), or require a signed/verified token (e.g., a per-user JWT or the `ApiClient#creator`) instead of `request.headers['X-Shipit-User']`, and audit all call sites (`DeploysController`, `RollbacksController`, `LocksController`, `TasksController`, `MergeRequestsController`) that currently pass `current_user` straight into state-changing/audited operations.

### Proof of Concept
1. Obtain any valid `ApiClient` authentication token scoped only to `deploy:stack` for a given stack (e.g. via an internal integration that legitimately has such a token).
2. Send `POST /api/stacks/:id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: <victim-login>`.
3. Observe (per `test/controllers/api/deploys_controller_test.rb:49-60`) that the resulting `Deploy#user` is the victim, not any identity tied to the token itself — the deploy, its audit trail, and its `SHIPIT_USER`/committer env vars are now attributed to a user who never made the request.
