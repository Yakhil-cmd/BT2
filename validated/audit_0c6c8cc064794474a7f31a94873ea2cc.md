`GIT_TEMPLATE_DIR` injection via unfiltered pull-request label names in `ReviewStack#env` enables RCE on next `git clone` - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack's environment hash with no allowlist, and `LabelCapturingHandler` persists label names verbatim from the webhook payload with no character/name filtering. Because `StackCommands#env` and `Command#unbundled_env` pass this hash unfiltered into `PTY.spawn`, an attacker-controlled label named `git_template_dir` becomes `GIT_TEMPLATE_DIR=true` in the environment of every git subprocess for that stack, including `git clone` invocations reachable from `StackCommands#fetch_deployed_revision`.

### Finding Description
The broken binding: `Shipit.env.merge(deploy_variables_permitted_only)` is expected to hold for all environment reaching `Command`/`PTY.spawn` (i.e., `env_reaching_git == whitelisted_keys_only`), but for review stacks this becomes `env_reaching_git == whitelisted_keys ∪ {LABEL_NAME.upcase => "true" for every PR label}` — an unbounded, attacker-chosen key set.

Path:
1. An unprivileged fork PR author adds a label to their own PR whose name, when uppercased, is `GIT_TEMPLATE_DIR` (e.g. label `git_template_dir`). GitHub emits a `pull_request` `labeled` webhook to `POST /webhooks`.
2. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` stores the raw label names on the `PullRequest` model with no allowlist or character restriction: [1](#0-0) 
3. `Shipit::ReviewStack#env` merges these label names uppercased into the stack's env hash, unconditionally, with no key allowlist: [2](#0-1) 
4. `StackCommands#env` merges the stack env on top of the base env: [3](#0-2) 
5. `StackCommands#fetch_deployed_revision` (and `fetch`, `fetch_commit`, `with_temporary_working_directory`'s internal `git clone`) pass this `env` straight to `Command.new`: [4](#0-3) [5](#0-4) 
6. `Command#unbundled_env` merges `@env` (attacker-controlled) last, so it can override/introduce arbitrary variables including `GIT_TEMPLATE_DIR`, then spawns the process with it: [6](#0-5) [7](#0-6) 

Existing guards that fail to stop this: `EnvironmentVariables#permit` exists and is the correct sanitization mechanism, but it is only invoked for deploy/task/rollback variables via `filter_deploy_envs`/`filter_envs` (`Stack#trigger_task`, `Stack#build_deploy`, `TaskDefinition#filter_envs`) — [8](#0-7) . `StackCommands#env` and `ReviewStack#env` never call `EnvironmentVariables#permit`, so the label-derived keys bypass sanitization entirely. `LabelCapturingHandler`'s param schema only requires `labels` to contain a `name` String — no validation on content: [9](#0-8) , and the test suite even documents that arbitrary/emoji label names are accepted verbatim: [10](#0-9) . This is confirmed as intended (if dangerous) behavior by existing tests: [11](#0-10) [12](#0-11) .

Once `GIT_TEMPLATE_DIR` points at an attacker-writable directory (e.g., under the git cache path that the attacker can also influence through other repo content, or any world-writable path known to the attacker on the deploy host), the next `git clone` invoked by `StackCommands#fetch` / `with_temporary_working_directory` will copy files from that template directory into `.git/hooks` of the newly cloned repo, and those hooks execute on subsequent git operations (`post-checkout`, etc.), giving code execution as the Shipit worker user.

### Impact Explanation
This allows a Critical class of impact — remote code execution on the Shipit deploy host via `Command`/`PTY.spawn`, since git hooks placed via a poisoned template directory execute native code as the same OS user (and same shell environment, including `GITHUB_TOKEN`) that git and later deploy/task commands run. This is exploitable by an unprivileged fork contributor who never needs a Shipit session, API token, or GitHub org membership — merely the ability to open a PR and label it, provided the target repository's `provisioning_behavior` is `allow_with_label` (or `allow_all`) and review stacks are enabled. The blast radius is scoped to the review stack for that repository/PR, but given the shared worker host and shared secrets (`GITHUB_TOKEN` in the same process environment), the code execution achieved is on the same host that serves other stacks, so credential exfiltration and lateral effects on other tenants sharing the host are plausible.

### Likelihood Explanation
Preconditions: the target `Repository` must have review stacks enabled with `provisioning_behavior` of `allow_with_label` (attacker must also apply/know the specific opt-in provisioning label) or `allow_all` (no extra requirement). Attacker cost is trivial: open a PR from a fork and add one label named `git_template_dir` (case-insensitive, since it's uppercased by the code). No secrets, no privileged role, and no interaction with GitHub webhook signing is needed beyond normal GitHub webhook delivery for actions the attacker already legitimately performs on their own PR. This is fully repeatable and requires only standard GitHub permissions on a repository the attacker forked.

### Recommendation
Do not merge unrestricted pull-request label names into the process environment. Either (a) prefix label-derived environment keys (e.g., `LABEL_<NAME>`) so they can never collide with meaningful variable names like `GIT_TEMPLATE_DIR`, `GIT_ASKPASS`, `LD_PRELOAD`, etc., and/or (b) run label-derived env through `EnvironmentVariables#permit` against an explicit allowlist before merging in `ReviewStack#env`, and/or (c) strip any label name matching `GIT_*`, `LD_*`, or other known-dangerous environment variable name patterns before merging.

### Proof of Concept
Add a minitest to `test/lib/shipit/stack_commands_test.rb` (or an equivalent test file) that:
1. Loads `shipit_stacks(:review_stack)` and sets `stack.pull_request.labels = ["git_template_dir"]`.
2. Calls `Shipit::StackCommands.new(stack).env` and asserts `env["GIT_TEMPLATE_DIR"] == "true"`.
3. Additionally, stub/inspect the `Command` object returned by `StackCommands#fetch_deployed_revision`'s internal `Command.new(command_line, env:, chdir: dir)` (e.g., via `Command.expects(:new).with(anything, has_entry('GIT_TEMPLATE_DIR', 'true'), anything)` or by capturing `command.env` before `.run`) to prove the value reaches the `Command` that will ultimately be passed to `PTY.spawn`.

Both assertions succeed against current code, demonstrating the binding is broken: `env_reaching_git` should equal only the documented/whitelisted keys but instead includes attacker-chosen keys derived from PR label names.

    def with_temporary_working_directory(commit: nil, recursive: true)
      commit ||= @stack.last_deployed_commit.presence || @stack.commits.reachable.last

      if !commit || !fetched?(commit).tap(&:run).success?
        @stack.acquire_git_cache_lock do
          fetch.run! unless fetched?(commit).tap(&:run).success?
        end
      end

      git_args = []
      git_args << '--recursive' if recursive
      Dir.mktmpdir do |dir|
        git(
          'clone', @stack.git_path, @stack.repo_name,
          *git_args, '--origin', 'cache',
          chdir: dir
        ).run!

        git_dir = File.join(dir, @stack.repo_name)
        if commit
          git(
            '-c',
            'advice.detachedHead=false',
            'checkout',
            *quiet_git_arg,
            commit.sha,
            chdir: git_dir
          ).run!
        end
        yield Pathname.new(git_dir)
      end
    end
