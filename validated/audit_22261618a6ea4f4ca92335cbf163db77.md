## Analog Found

### Title
Balance-Based Exchange Rate Manipulation via Direct Donation to AA Address - (File: aa_composer.js)

### Summary
The Compound `sweepToken` bug allowed anyone to manipulate a market's exchange rate by altering the real token balance of a contract that another function relied on for its rate calculation. ocore's Autonomous Agent (AA) engine has an analogous exposure: the `balance[asset]` formula operator reflects the AA address's *real, unconditional* on-chain balance, which any unprivileged unit poster can inflate simply by sending a payment to the AA's address — independent of whether any `if` case of the AA is triggered and independent of any accounting variable (e.g. `var['mm_asset_outstanding']`) the AA author uses to track "legitimate" deposits.

### Finding Description
When a trigger unit is processed, `updateInitialAABalances()` unconditionally credits every asset amount sent in `trigger.outputs` to `trigger_opts.assocBalances[address][asset]` (or the persisted `aa_balances` table) before any `if`/case matching happens: [1](#0-0) . This means a plain payment to an AA's address always increases its balance, whether or not it matches a case that updates the AA's own bookkeeping variables.

The formula engine's `balance[...]` operator (`readBalance`) simply returns this real balance figure from `objValidationState.assocBalances`, with no distinction between "balance accounted for by the AA's own state" and "balance donated directly by an outside party": [2](#0-1) .

The official ocore sample `uniswap_like_market_maker.oscript` demonstrates the vulnerable pattern that any AA author following this reference design would replicate: it computes swap/investment ratios directly from `balance[$asset]` and `balance[base]` (e.g. `$current_ratio = $asset_balance / $bytes_balance`, `$p = $asset_balance * $bytes_balance`) rather than from internally tracked reserve variables: [3](#0-2) [4](#0-3) . Because the underlying `balance[]` primitive can be inflated by any unprivileged sender posting a plain payment to the AA's address (a "donation"), the invariant the AA author assumes — that `balance[asset]` only changes through the AA's own invest/divest/swap cases — does not hold at the protocol level.

This is the direct structural analog of the TUSD/Compound issue: there, `cUSDT.balanceOf(address(this))` (real balance) was used to compute the exchange rate, and anyone could manipulate that real balance out-of-band (via `sweepToken`) to distort the rate. In ocore, `balance[asset]` (real balance) is exposed to oscript formulas and can likewise be manipulated out-of-band by any unprivileged unit poster sending assets/bytes directly to the AA address, without going through the AA's normal deposit logic.

### Impact Explanation
An attacker can:
- Donate assets/bytes directly to a balance-based AMM-style AA to shift `$current_ratio`/`$p` before calling the "exchange" or "divest" case, extracting more value than deposited (classic donation/first-deposit style attack), or diluting other investors' share calculations that also read `balance[...]` (e.g. `round($investor_share * balance[$asset])`).
- Cause other legitimate users' trigger units (which are queued and executed at specific MCIs) to execute against a balance that was manipulated by an intervening donation, front-running fair pricing.
- Freeze or distort accounting for any real-world AA that follows the documented `balance[]`-based design pattern, leading to fund loss for depositors/investors of that AA — matching the "AA fund loss or freezing" impact criterion.

### Likelihood Explanation
Sending a payment message to any address, including an AA address, requires no special privilege — any wallet/unit poster can do it and it is a first-class supported ocore operation. Any deployed AA that follows the sample "uniswap-like market maker" pattern (using `balance[asset]`/`balance[base]` directly in its pricing formulas, a pattern actively documented as an example in the ocore repo) is exposed. The attack requires only crafting one additional payment unit timed before the target's trigger unit stabilizes.

### Recommendation
- Document explicitly (and warn AA authors) that `balance[asset]` includes any unaccounted external donations and must not be used directly as a price/rate oracle without maintaining and using AA-internal reserve variables (`var[...]`) that are only updated through the AA's own case logic.
- Consider providing/encouraging a "tracked reserve" formula idiom or built-in primitive that AA authors can rely on instead of raw `balance[...]`, so pricing formulas are immune to direct donations.
- For any first-party/reference AAs (like `uniswap_like_market_maker.oscript`) shipped as examples, update them to track reserves via state variables rather than raw `balance[...]`, since developers are likely to copy this pattern verbatim.

### Proof of Concept
1. Deploy an AA using the `uniswap_like_market_maker.oscript` pattern; assume it holds `balance[base]=B` and `balance[$asset]=A` with `var['mm_asset_outstanding']=S`.
2. Attacker sends a plain payment of asset `$asset` (or bytes) directly to the AA's address with an amount that does not match any `if` condition amounts required for the "invest" case (e.g., sends bytes but does not exceed thresholds paired correctly, or sends the asset alone below the trigger threshold used elsewhere), so no case executes but `updateInitialAABalances()` still credits the AA's balance (`aa_composer.js:474-490`).
3. `balance[$asset]` (or `balance[base]`) is now inflated relative to `var['mm_asset_outstanding']`.
4. Attacker (or a colluding second unit) immediately triggers the "exchange bytes to asset" or "divest MM shares" case; because `$asset_balance`/`$bytes_balance` are computed straight from the manipulated `balance[...]`, the computed `$amount`/`$issue_amount` deviates from the fair value, letting the attacker extract more value than they deposited or force other investors' share redemptions to be miscalculated.
