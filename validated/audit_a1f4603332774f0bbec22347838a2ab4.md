### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach an incoming GitHub `status` webhook to purely `Commit.where(sha: params.sha)`, with no check that the webhook's `repository.full_name` matches the repository owning the stack the commit belongs to. Any GitHub repository that can deliver a legitimately-signed `status` event to Shipit (i.e. one already registered/onboarded on the Shipit instance) can therefore write a `Status` row for any commit in any tenant's stack whose SHA happens to match, corrupting `Commit#status`/`Commit#deployable?` for that unrelated stack.

### Finding Description
The broken binding is: **the repository that authenticated a `status` webhook == the repository of the stack/commit the status is applied to**. In `StatusHandler`: [1](#0-0) 

this handler queries `Commit.where(sha: params.sha)` **globally across the entire `commits` table**, and calls `commit.create_status_from_github!(params)` on every match, regardless of which stack/repository that commit belongs to.

Contrast this with the base `Handler` class, which provides a `stacks` helper specifically to scope lookups to the repository that sent the webhook: [2](#0-1) 

`StatusHandler` does not use this helper at all, so the repository identity carried in the webhook payload (`payload.dig('repository','full_name')`) is never checked against the commit being updated.

`Commit#create_status_from_github!` / `#add_status` then recompute `Commit#status` and can flip `Commit#deployable?` for whatever stack owns that `Commit` row: [3](#0-2) [4](#0-3) [5](#0-4) 

Since a git commit's SHA-1 is a hash of its content (tree, parents, author/committer, timestamps, message) and not of the repository name, an unprivileged attacker can trivially obtain a commit object with the exact same SHA as one already imported into victim-org's stack A — e.g. by forking the (public) victim repository. Any commit that exists in the fork has byte-identical SHAs to the upstream repository. The attacker then triggers a genuine, correctly-signed GitHub `status` webhook from their own repository B (their fork, or any other repo/org they control that is already onboarded to the Shipit instance) for that shared SHA, with `state: "success"`.

`WebhooksController#verify_signature` only validates that the HMAC signature matches the secret configured for `repository_owner` taken from the payload — it does **not** verify that the reported `repository.full_name` is entitled to write statuses for the specific commit/stack being updated: [6](#0-5) 

So the signature check legitimately passes (it's a real webhook from a real, registered repository — just not the one that owns the target commit), and `StatusHandler` then blindly applies the status to every `Commit` row sharing that SHA, including the one in victim-org's stack A. This flips `Commit#status` to `success`, making `Commit#deployable?` true and `UndeployedCommit#deploy_state` show `"allowed"` in the UI/API, independent of `continuous_deployment` and independent of any check on the real CI state GitHub has for repo A.

None of the listed guards catch this: `verify_signature` only authenticates *a* registered repository, not the *correct* one for the target commit; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema in `StatusHandler.params` only validates shape (`sha`, `state`, etc.), not repository ownership; `force_github_authentication`, `User#authorized?`, `require_permission!` and the `stacks` scope are irrelevant here because this is an unauthenticated webhook path, and `stacks`/`Repository.from_github_repo_name` is simply never invoked by `StatusHandler`.

### Impact Explanation
A maintainer of victim-org/A, trusting the green status shown by the Shipit UI (driven by `Commit#deployable?`), manually triggers a deploy via the authenticated `Deploy` flow. `Stack#build_deploy` sets `ignored_safeties: force || !until_commit.deployable?`, so with the forged `deployable?` = true this proceeds as a "safe" deploy and ultimately runs `Command#start`/`PTY.spawn` with victim-org/A's `GITHUB_TOKEN` and deploy credentials, deploying a commit whose real CI state on GitHub for repo A was never actually green. This is a payload from one repository (attacker's repo B) mutating a record (`Status`) belonging to another repository's stack (victim-org/A), directly leading to an unauthorized deploy — matching the Critical impact category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any stack/commit combination sharing a SHA the attacker can reproduce (trivial for any public upstream repository via forking), and scales across every tenant/stack hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) the target repository A is public (or its commits are otherwise obtainable) so the attacker can reproduce an identical SHA via forking or replaying the same commit content; (2) the attacker controls at least one GitHub repository/organization (repo B) that is already onboarded to the same Shipit instance so that `Shipit.github(organization: repository_owner)` resolves and `verify_webhook_signature` succeeds for a real webhook GitHub sends on their behalf — this is exactly the situation described in the threat model ("emit webhooks from a repository they own"), which is plausible in any Shipit instance serving multiple tenants/orgs where onboarding a new repo/org is self-service. Given those preconditions, the attack costs the attacker nothing beyond forking a repo and setting a commit status on their own repo (a normal, unprivileged GitHub Statuses API call), and is fully repeatable and scriptable against any known target SHA.

### Recommendation
In `StatusHandler#process` (and any other handler doing global `sha`-only lookups), scope the commit lookup to the repository asserted in the webhook payload, e.g. use the existing `stacks` helper from `Handler` to constrain the query: `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Repository.from_github_repo_name(repository_name)` before matching by `sha`, so a status can only ever be applied to commits belonging to stacks of the repository that actually sent the webhook.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/status_handler_test.rb`) asserting the binding:

```ruby
test "a status webhook from repository B does not update a commit belonging to stack A's repository" do
  stack_a = shipit_stacks(:shipit) # repository "shopify/shipit-engine" e.g.
  commit  = shipit_commits(:first) # belongs to stack_a, currently pending
  assert_not commit.deployable?

  # Forge a status webhook whose payload repository is NOT stack_a's repository,
  # but whose sha collides with commit.sha (as would happen via a fork).
  forged_payload = {
    "sha" => commit.sha,
    "state" => "success",
    "context" => "ci/travis",
    "repository" => { "full_name" => "attacker/unrelated-repo", "owner" => { "login" => "attacker" } }
  }

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'
  post :create, body: forged_payload.to_json, as: :json

  commit.reload
  # Binding under test: repository that authenticated the webhook == repository owning the updated commit.
  # Left side (actual webhook repo) != right side (commit's stack repo) -> update MUST be rejected.
  refute_equal "attacker/unrelated-repo", stack_a.github_repo_name
  refute commit.deployable?, "commit in stack A must not become deployable from a status forged via an unrelated repository"
end
```

This test currently fails against `StatusHandler#process`'s unscoped `Commit.where(sha: params.sha)`, confirming the cross-tenant status forgery.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
