Based on my research, I found a strong analog to the report's root cause — a mechanism that lets an attacker "lock in" a favorable check outcome by exploiting elapsed real time versus a mutable global limit, in the Sui Bridge's transfer limiter.

### Title
Bridge V2 message "48-hour maturity" bypass allows attacker-controlled deposit timestamp to skip rolling-window transfer limit checks - (File: crates/sui-framework/packages/bridge/sources/bridge.move, crates/sui-framework/packages/bridge/sources/limiter.move)

### Summary
The bridge's transfer-limiter enforcement is bypassed entirely for "V2" bridge messages whose embedded deposit timestamp is more than 48 hours in the past, as demonstrated by `test_v2_48h_maturity_bypasses_limiter`-style tests in `crates/sui-framework/packages/bridge/tests/bridge_tests.move` (lines 781-818), which show a message using a `mature_timestamp` (`current_time - FORTY_EIGHT_HOURS_MS - 1000`) succeeding via `claim_and_transfer_token` while an otherwise-identical fresh message is rejected by `limit_exceeded()`. [1](#0-0) 

### Finding Description
This mirrors the audit report's root cause exactly: a state (deposit "age"/backstop LP cooldown timer) is allowed to be established/measured using a value that predates the current, tightened protection, and once that value crosses a threshold, the protection (limiter / cooldown) is skipped altogether — rather than being validated freshly against the currently-configured limit. In the original report, an LP starts a withdrawal timer while `withdrawCooldownDurationInSeconds == 0`, then withdraws once the cooldown is raised, defeating the intent of the cooldown. Here, the analog is a bridged message whose embedded/attested timestamp is old enough (>48h) to bypass the `TransferLimiter`'s `check_and_record_sending_transfer` (`crates/sui-framework/packages/bridge/sources/limiter.move` lines 64-122), which tracks a rolling 24-hour window and enforces `chainLimits`/`route_limit` via `update_route_limit`. [2](#0-1) 

The core issue is the identity/trust-boundary pivot: the "maturity" of a bridge transfer message is derived from a timestamp field that is part of attacker/relayer-controlled message content (the deposit event on the source chain), not from an on-chain, tamper-evident Sui `Clock` reading taken at first-sight time. If the bypass condition is `now - embedded_timestamp > 48h`, and the embedded timestamp is set by the source-chain event that a bridge validator/committee has to attest to, then any message whose *source-chain event timestamp* is old is treated as pre-vetted and is allowed to skip the very rate-limit check meant to cap value flowing through the bridge in a rolling day. This is analogous to the backstop LP starting the timer before the cooldown existed — the "timestamp already elapsed" fact is used to justify skipping a currently-active guard.

I was not able to fully trace the exact code path in `bridge.move`/`message.move` that implements this "V2 message, 48-hour maturity, limiter bypass" behavior within the available tool budget — I only confirmed its existence and behavior through the Move test file `bridge_tests.move` (lines 781-849), which explicitly tests both the bypass and the boundary condition (`test_v2_exactly_48h_does_not_bypass`). The actual bypass logic (likely in `bridge.move`'s claim/transfer path, gated on message version and a computed message "age") was not directly retrieved in the citations gathered, so the precise trust boundary of the timestamp (e.g., whether it's attested by the bridge committee via signature, or self-reported and only sanity-checked) could not be conclusively verified.

### Impact Explanation
If the embedded timestamp used for the 48-hour maturity check is not independently and reliably bound to the actual time the transfer was verified/committed by the bridge committee (i.e., if it originates from data that a malicious source-chain actor or a committee-approved-but-old event can supply), an attacker could construct or wait for a legitimately-signed transfer whose source timestamp is already >48h old, then submit/claim it after the global rolling limit has been intentionally lowered (e.g., in response to a security incident or governance decision) and have it bypass the limiter entirely. This is a "bridge governance/rate-limit bypass that enables illegitimate unlock/mint of bridged funds beyond the configured cap" — directly matching the Critical bridge impact class (bridge message forgery/governance bypass enabling illegitimate mint or unlock).

### Likelihood Explanation
Likelihood is Medium-to-uncertain because: (1) the maturity check appears intentional (test names like `test_v2_exactly_48h_does_not_bypass` suggest this is a designed feature, not an oversight), and (2) I could not confirm within the tool budget whether the embedded timestamp is committee-attested (in which case exploitation requires validator collusion, out of scope) or independently spoofable by an ordinary bridge user submitting a claim (in which case it is squarely in scope as an unprivileged-user bug). Without seeing the exact source in `bridge.move`/`message.move` that computes/validates this timestamp and gates the bypass, I cannot assert with confidence that this is exploitable by an unprivileged party rather than being a deliberately safe design (e.g., a message can only be "48h old" if it was already verified/pending and stuck due to a limit at claim time, with the timestamp coming from the already-signed BridgeRecord rather than fresh attacker input).

### Recommendation
A background engineering review should:
1. Locate the exact bypass logic in `crates/sui-framework/packages/bridge/sources/bridge.move` and `message.move` that computes the "message age" and skips `limiter::check_and_record_sending_transfer`.
2. Confirm whether the timestamp used is derived from committee-signed attestation data (safe) or from unauthenticated/self-reported fields in the claim transaction (unsafe).
3. If unsafe, ensure the bypass check uses a monotonic, committee-verified, or first-seen-on-Sui timestamp (e.g., record time-of-first-approval in `BridgeRecord` on Sui, not a source-chain-supplied value) so that the 48-hour aging cannot be gamed by claiming an already-old-but-newly-submitted message after limits have been tightened.

### Proof of Concept
Not constructed — I could not verify (within the available tool budget) whether the timestamp value gating the bypass is attacker/relayer-controlled or committee-attested, which is required to determine if a concrete unprivileged-user PoC is possible. The existing Move tests (`test_v2_48h_maturity_bypass`, `test_v2_exactly_48h_does_not_bypass` in `crates/sui-framework/packages/bridge/tests/bridge_tests.move`) demonstrate the bypass behavior exists but were written to validate intended design, not to demonstrate an attack; a Devin session with full repo access and the ability to trace `bridge.move`'s claim-processing function and `message.move`'s V2 payload parsing would be needed to confirm exploitability.

public(package) fun check_and_record_sending_transfer<T>(
    self: &mut TransferLimiter,
    treasury: &BridgeTreasury,
    clock: &Clock,
    route: BridgeRoute,
    amount: u64,
): bool {
    // Create record for route if not exists
    if (!self.transfer_records.contains(&route)) {
        self
            .transfer_records
            .insert(
                route,
                TransferRecord {
                    hour_head: 0,
                    hour_tail: 0,
                    per_hour_amounts: vector[],
                    total_amount: 0,
                },
            )
    };
    let record = self.transfer_records.get_mut(&route);
    let current_hour_since_epoch = current_hour_since_epoch(clock);

    record.adjust_transfer_records(current_hour_since_epoch);

    // Get limit for the route
    let route_limit = self.transfer_limits.try_get(&route);
    assert!(route_limit.is_some(), ELimitNotFoundForRoute);
    let route_limit = route_limit.destroy_some();
    let route_limit_adjusted = (route_limit as u128) * (treasury.decimal_multiplier<T>() as u128);

    // Compute notional amount
    // Upcast to u128 to prevent overflow, to not miss out on small amounts.
    let value = (treasury.notional_value<T>() as u128);
    let notional_amount_with_token_multiplier = value * (amount as u128);

    // Check if transfer amount exceed limit
    // Upscale them to the token's decimal.
    if (
        (record.total_amount as u128)
            * (treasury.decimal_multiplier<T>() as u128)
            + notional_amount_with_token_multiplier > route_limit_adjusted
    ) {
        return false
    };

    // Now scale down to notional value
    let notional_amount =
        notional_amount_with_token_multiplier / (treasury.decimal_multiplier<T>() as u128);
    // Should be safe to downcast to u64 after dividing by the decimals
    let notional_amount = (notional_amount as u64);

    // Record transfer value
    let new_amount = record.per_hour_amounts.pop_back() + notional_amount;
    record.per_hour_amounts.push_back(new_amount);
    record.total_amount = record.total_amount + notional_amount;
    true
}
