### Title
Webhook signature scoped to `repository.owner.login` but processing keyed on `repository.full_name` allows cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to validate the incoming request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . That single field is used to pick `Shipit.github(organization: repository_owner)` and verify the HMAC signature against that organization's configured `webhook_secret` [2](#0-1) . However, once the signature check passes, event handlers act on a *different* field, `repository.full_name`, to resolve the actual `Stack`/`Repository`/`Commit` being mutated [3](#0-2) . Because the engine supports multi-organization GitHub App configuration where each organization has its own independent `webhook_secret` [4](#0-3) , an attacker who legitimately administers one organization's webhook secret in a shared Shipit instance can sign a payload as their own org while setting `repository.full_name` to point at a completely unrelated organization's repository, and the mismatch is never checked.

### Finding Description
The verified binding should be: `organization whose secret signed the request == organization/repository being mutated by the handler`. Instead:
- **Signature-authenticated field**: `repository.owner.login` (or `organization.login`) is used only to select which org's `webhook_secret` verifies the HMAC [1](#0-0) , then `verify_webhook_signature` performs a constant-time HMAC compare against that org's secret [5](#0-4) .
- **Action-executed field**: every handler resolves the target repository purely from `payload.dig('repository', 'full_name')`, with no cross-check against `repository.owner.login` used during signature validation [3](#0-2) .

Since these are two independent JSON fields in the same attacker-supplied payload, a party who has been given webhook secret A (because they legitimately administer organization A's GitHub App connection to this shared Shipit instance) can submit a payload where `repository.owner.login = "A"` (so the signature check against secret A passes) but `repository.full_name = "victim-org/victim-repo"`. The controller never verifies that the owner used for authentication matches the owner embedded in `full_name`.

This is a genuine binding break: the identity authenticated by the signature (`organization A`) is not the same as the entity written to (`victim-org/victim-repo`), exactly analogous to the referenced report's pattern where a value used to compute an authorization/rate check diverges from the value actually acted upon.

### Impact Explanation
Handlers reachable through this bypass allow real state mutation on stacks/repositories the attacker does not own:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: ...)`, forcing a git resync of a foreign stack's branch to an attacker-chosen SHA [6](#0-5) .
- `StatusHandler#process` creates a fabricated commit `Status` (`create_status_from_github!`) for any commit matching the given `sha`, on any stack, which can be used to spoof passing/failing CI status for commits the attacker doesn't control [7](#0-6) .
- `PullRequest::ClosedHandler#process` can archive review stacks belonging to a repository resolved independently via `params.repository.full_name` [8](#0-7) .
- `MembershipHandler#process` creates/removes team memberships and creates users tied to an `organization.login` that is likewise taken straight from payload with no relation enforced to the signing organization [9](#0-8) .

If deploy/merge automation in the host application (or `Shipit::CommitChecks`/status-gated merges) relies on GitHub `status`/`check_suite` events being trustworthy per-repository signals, an attacker able to forge these for a foreign repository can influence deploy/merge gating decisions on that repository — a cross-organization write achieved purely by exploiting the signature-vs-processing field mismatch. This satisfies the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
This requires the attacker to control a `webhook_secret` for *some* organization configured on the shared Shipit instance — a low, but non-zero, privilege level distinct from `ApiClient`, session, or admin GitHub-App-key access (which are explicitly excluded). Any environment running Shipit as a multi-tenant/multi-organization deployment (as documented and supported by `Shipit.github(organization:)` and `github_app_config`) is exposed. Likelihood is Medium: it requires the attacker to be a legitimate low-trust participant of one organization, but no session, App private key, or high-privilege token is needed.

### Recommendation
After parsing the payload, re-derive the organization from `repository.full_name`'s owner (or from `organization.login`) and require it to match the `repository_owner` field used to select the signing secret in `verify_signature`. Reject the request (422) on mismatch. Alternatively, once the correct organization/secret is confirmed, only allow handlers to resolve stacks scoped to that same organization rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit is configured with multi-organization GitHub Apps: `secrets.github` contains keys `attacker-org` (webhook_secret `S_A`, known to the attacker as its administrator) and `victim-org` (unrelated, containing stack `victim-org/victim-repo`) — supported per `Shipit.github_app_config` [10](#0-9) .
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/build",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, raw_body)` using their own known secret `S_A`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check succeeds because it was signed with `S_A` [2](#0-1) .
5. `create` then dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — commits belonging to `victim-org/victim-repo` — and writes a forged `Status` record for them, with no re-check that `victim-org` matches `attacker-org` [7](#0-6) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
