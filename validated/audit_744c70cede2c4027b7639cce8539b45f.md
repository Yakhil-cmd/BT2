## Title
API client scoped to one stack can read CCMenu status of any other stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

## Summary
### Finding Description

`Shipit::Api::BaseController` restricts every API endpoint to the set of stacks a token is authorized for via the `stacks`/`stack` helper methods: [1](#0-0) 

`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the `ApiClient` is scoped to a single stack (`stack_id` present), otherwise `Stack.all`. `stack` then calls `stacks.from_param!(...)`, so a stack-scoped token can only ever resolve its own stack. `ApiClient` itself only checks *permission scopes* (e.g. `read:stack`), not *which* stack, in `check_permissions!`: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` and bypasses the `stacks` scoping helper entirely, resolving directly against the global `Stack` relation: [3](#0-2) 

The `require_permission :read, :stack` before_action only calls `current_api_client.check_permissions!(:read, :stack)`, which is a scope-name check, not a per-stack ownership check: [4](#0-3) 

So the binding that should hold is: **stack a token authorizes == stack the token can touch**. Before the request, `BaseController#stack`/`#stacks` enforces this equality for every other API endpoint (`StacksController`, `RollbacksController`, `TasksController`, etc.). In `CCMenuController`, this equality is broken: the token only proves "has `read:stack` permission" (true for any stack-scoped client, since scoped clients are created with that permission, e.g. the `here_come_the_walrus` fixture), while the actual `stack` resolved for the response can be **any** stack in the system, chosen purely from `params[:stack_id]` supplied by the caller.

### Impact Explanation

An attacker who obtains (or is issued) a stack-scoped API token — e.g. via `CCMenuUrlController`, which mints an `ApiClient` with `read:stack` permission and hands out its `authentication_token` in a URL — can use that token against `GET /api/stacks/:stack_id/ccmenu` for a `stack_id` belonging to a completely different, unauthorized stack, and receive that stack's deploy/build status (`latest_deploy`, running state, last build label, etc.). This is an unauthenticated-for-that-resource read of another stack's state/deploy output, matching the High-impact class: "unauthenticated read of stack state, task streams or deploy output" via a broken token-to-stack binding.

### Likelihood Explanation

No special privilege beyond possessing any valid `ApiClient` token with `read:stack` (a very commonly granted, low-sensitivity permission — it's the default permission handed out by `CCMenuUrlController` for CI status badges) is required. The only additional requirement is knowing/guessing another stack's `to_param` (typically `owner/repo/environment`, often predictable or discoverable), which is far below the "requires privileged account" exclusion threshold in the rules.

### Recommendation
Make `CCMenuController#stack` use the same `stacks` scoping helper as `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot resolve a stack outside its `stack_id`.

### Proof of Concept
1. As an admin, call `CCMenuUrlController#fetch` for `stack_a` (or use any existing stack-scoped `ApiClient`, e.g. fixture `here_come_the_walrus`, scoped to stack `shipit` with `read:stack`).
2. Take the returned `token`.
3. Issue `GET /api/stacks/<stack_b_id_or_param>/ccmenu?token=<token>` where `stack_b` is a different stack the client was never granted access to.
4. Observe `CCMenuController#stack` resolves `stack_b` via `Stack.from_param!` (bypassing `current_api_client.stack_id` scoping), and the XML response in `show` (`app/controllers/shipit/api/ccmenu_controller.rb:22-25`) discloses `stack_b`'s latest deploy/build status — despite the token only being authorized for `stack_a`.

*Note: I was unable to run this against a live instance to confirm end-to-end behavior (no execution environment available); the finding is based on static analysis of the controller/model code and the documented behavior of `BaseController#stacks`/`#stack` versus `CCMenuController#stack`. The `find_or_create_by!` scope in `CCMenuUrlController#client` (not matching on `stack:`) also raises a secondary question of whether the minted CCMenu token is even meant to be single-stack-scoped, but the core vulnerability — `CCMenuController` bypassing the token's `stack_id` restriction for any stack-scoped `ApiClient` — holds independently of that.*
