## Finding [1](#0-0) [2](#0-1) 

### Title
Stale `is_valid_signed_package` authorization remains valid after the signer rotates/revokes their address definition (key) - (File: signed_message.js)

### Summary
An AA (or any oscript condition) that authorizes an action using `is_valid_signed_package()`/`validateSignedMessage()` accepts a signed message whose authenticity is checked against the **address definition that was current at the arbitrary, attacker-chosen `last_ball_unit`** embedded in the package, not against the address's *current* definition. If the address owner changes their definition (e.g. rotates/revokes a compromised key, functionally the on-chain analog of "changing a password"), any signed package that was produced under the old definition — and which references any historical, already-stable `last_ball_unit` — continues to validate successfully forever. This mirrors GHSA-3458-r943-hmx4: a credential ("reset token"/authorization proof) that should have been invalidated by the owner's remedial action keeps working.

### Finding Description
`is_valid_signed_package` in `formula/evaluation.js` calls `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)` [3](#0-2) . That function only checks that the package's `last_ball_unit` is itself stable and that its MCI is `<= mci` (the current evaluation point) — it never requires that `last_ball_unit` be recent relative to the moment of validation:

```
signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, function (err, last_ball_mci) {
    if (err) return cb(false);
    if (last_ball_mci === null || last_ball_mci > mci) return cb(false);
    cb(true);
});
```

Inside `validateSignedMessage`, the definition used to verify the authentifiers is looked up **at the historical `last_ball_mci` taken from the package itself**, via `storage.readDefinitionByAddress(conn, objAuthor.address, last_ball_mci, ...)` [4](#0-3) . Because `last_ball_unit` is a field chosen freely by whoever assembled the signed package (any already-stable unit qualifies), an attacker who is in possession of a signed package produced under an address's *old* definition can keep presenting it — the check will always resolve the definition that was active at that old point in history, i.e. the same (now-revoked) definition that produced the valid signature, and accept it.

This is the structural equivalent of the Fleet bug: the "credential" (signed package + old key) is not invalidated when the underlying credential store (`address_definition_changes`, checked via `readDefinitionByAddress`, see `storage.js` lines 754-788) is updated to a new definition. `address_definition_change` is precisely the primitive designed to let a compromised/former key be revoked [5](#0-4) , but `is_valid_signed_package` bypasses that revocation by pinning validation to attacker-selected history instead of the address's current definition.

### Impact Explanation
Any AA that uses `is_valid_signed_package` as an authorization gate for spending funds, releasing escrow, granting a role, or any other privileged action treats "signed by owner" as equivalent to "signed by owner *now*". Because old signed packages remain perpetually valid after a definition/key rotation, an attacker who once obtained (leaked, phished, or previously authorized) a signed package/private key can continue to authorize AA actions — even after the legitimate owner explicitly rotates keys specifically to shut the attacker out. Depending on how the AA is written, this can directly cause AA fund loss (unauthorized withdrawal/authorization) triggered by a single posted unit carrying the stale signed package, matching the "AA fund loss or freezing" impact criterion.

### Likelihood Explanation
Exploitation requires only that the attacker already possess one previously valid signed package (or the corresponding private key material used before rotation) referencing some historical stable `last_ball_unit` — no p2p, hub, or node compromise is needed. The trigger is a single unposted unit sent to an AA by any unprivileged AA trigger sender containing the stale `signed_message` object in its trigger data. This directly parallels the CVSS4 vector of the source advisory (network, low complexity, requires prior possession of the credential, no privileges/UI needed from the victim).

### Recommendation
Require `is_valid_signed_package` (and `validateSignedMessage`) to validate authentifiers against the address's *current* definition (at `mci`, the point of evaluation) rather than the definition frozen at the caller-supplied `last_ball_unit`, or additionally require that `last_ball_unit` be no older than the address's latest stable `address_definition_change` for that address. At minimum, document and/or enforce that AAs relying on `is_valid_signed_package` for revocable authorization must independently check `has definition change`/`seen definition change` to ensure no newer definition supersedes the one used to sign.

### Proof of Concept
1. Address `A` is defined with definition `D1` (single key `K1`).
2. Owner signs a `signed_message` package `P` authorizing a privileged AA action, referencing a currently-stable `last_ball_unit=U0` (mci `m0`). AA logic: `if (is_valid_signed_package(P, A)) { pay funds }`.
3. `K1` is later suspected compromised; owner posts `address_definition_change` to `D2` (new key `K2`), which stabilizes at mci `m1 > m0`.
4. Attacker who has `P` (or `K1`) posts a trigger unit at current mci `m2 >> m1` still containing package `P` with `last_ball_unit=U0`.
5. `is_valid_signed_package(P, A)` calls `validateSignedMessage`, which resolves `A`'s definition at `last_ball_mci = m0` — i.e., `D1`/`K1` — and the old signature verifies successfully, even though `A`'s current (post-revocation) definition is `D2`.
6. The AA executes the privileged action, even though the owner believed rotating the key had revoked `K1`'s authority.
