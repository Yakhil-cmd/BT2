### Title
Integer overflow in asset denomination cap calculation bypasses cap consistency check - ([File: validation.js])

### Summary
`validateAssetDefinition` in `validation.js` computes `total_cap_from_denominations` by multiplying two attacker-controlled positive integers (`count_coins` and `denomination`) without any bound on the product, then compares this sum against the declared `payload.cap`. Like the Linux kernel's `ring_buffer_resize` bug (CVE-2016-9754), where an unprivileged user could write attacker-controlled values that overflowed an internal size calculation, an unprivileged asset issuer can supply `denomination`/`count_coins` pairs whose product exceeds `Number.MAX_SAFE_INTEGER`, causing floating-point precision loss in the running sum used to validate the asset's cap invariant.

### Finding Description
In the denomination loop of `validateAssetDefinition`: [1](#0-0) 

- `denomInfo.denomination` is bounded to `<= constants.MAX_CAP` only after `pemCurvesFixMci` [2](#0-1) .
- `denomInfo.count_coins` is validated only with `isPositiveInteger`, which merely checks `typeof value === 'number' && isFinite(value) && Math.floor(value) === value && value > 0` — there is **no upper bound** on `count_coins` [3](#0-2) .
- The accumulation `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;` is plain JS double-precision arithmetic [4](#0-3) .

Because `count_coins` can be an arbitrarily large positive integer (limited only by JS's `isFinite`, so values well beyond 2^53 are accepted), the product `count_coins * denomination` can exceed `Number.MAX_SAFE_INTEGER` (2^53−1). Beyond this threshold, JS doubles silently lose integer precision, so the computed `total_cap_from_denominations` no longer represents the true mathematical sum, and multiple different denomination sets can be crafted to collide on the same (imprecise) value. Since the only checks against this variable are `total_cap_from_denominations === payload.cap` for consistency and `> constants.MAX_CAP` is never re-verified for the *sum* (only per-denomination), an attacker-crafted asset definition can pass validation with a `cap` field that does not truthfully reflect the sum of `count_coins * denomination` across all denominations.

### Impact Explanation
`cap` and per-denomination `count_coins` are downstream invariants relied upon by asset issuance and divisibility logic to bound total token supply for a fixed-denomination asset. If the recorded cap can be desynchronized from the true product sum through float-overflow collisions, the asset's supply-limiting invariant becomes unreliable at definition time, undermining any code path (issuance accounting, wallet/exchange trust assumptions) that treats `cap` as an accurate upper bound on issuable value for the asset — a data integrity issue affecting supply guarantees, in the same bug class as the referenced CVE (mishandled integer arithmetic in a size/quantity calculation reachable from an unprivileged actor).

### Likelihood Explanation
Any single-authored unit poster can define a new asset (`validateAssetDefinition` runs for any user-submitted `asset` message, not just privileged actors) and fully controls the `denominations` array's `count_coins` and `denomination` fields, requiring no more than crafting one asset-definition message. Note: `MAX_DENOMINATIONS_PER_ASSET_DEFINITION` and the per-`denomination <= MAX_CAP` check limit the exact combinations, and I was not able to fully trace how `payload.cap` is subsequently consumed during actual coin issuance/spending validation within the remaining investigation budget — this would need further confirmation to establish end-to-end unauthorized-spending or inflation impact beyond the definition-time invariant break.

### Recommendation
Bound `count_coins` (e.g., `count_coins <= constants.MAX_CAP`) and perform the running-sum check using safe-integer arithmetic (e.g., reject if `total_cap_from_denominations > Number.MAX_SAFE_INTEGER` at each step, or use `BigInt` for the accumulation) before comparing to `payload.cap`.

### Proof of Concept
Submit an asset-definition message with `fixed_denominations: true` and denominations such as:
```
denominations: [
  { denomination: 100000000, count_coins: 90071992547410 }, // product ~9.007e21, far beyond 2^53
  { denomination: 200000000, count_coins: 1 }
]
```
choosing `count_coins`/`denomination` pairs so that the double-precision sum collides with an attacker-chosen `cap` value that does not equal the true mathematical sum, then confirm `validateAssetDefinition` accepts it because the JS float comparison `total_cap_from_denominations !== payload.cap` passes due to precision loss.
