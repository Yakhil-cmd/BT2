### Title
AA-generated units may reserve an oversize fee that excludes payment-message size, causing the final (actual) oversize fee to exceed the amount collected, making the AA response unit fail validation and bounce - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `sendUnit()` mirrors the Gnosis-auction bug class: it computes and reserves an amount for a fee (`oversize_fee`) using an approximation that deliberately excludes part of the final billable size, then later recomputes the "real" fee on the fully assembled unit. If the real fee ends up higher than the reserved amount (analogous to `sellAmount` vs `sellAmount * (1+feeNumerator)`), the resulting balance check fails and the AA response unit is rejected, forcing the AA to bounce.

### Finding Description
When an AA response unit is being built, `completePaymentPayload()` picks inputs to cover `net_target_amount + getOversizeFee(size)`, where the oversize fee used during input selection is a value computed **once**, deliberately excluding the sizes of all `payment` messages:

```
const oversize_fee_excluding_payments = (bChargeOversizeFee && mci >= constants.pemCurvesFixMci)
    ? storage.getOversizeFee(objUnit.headers_commission + objectLength.getTotalPayloadSize({ ...objUnit, messages: messages.filter(message => message.app !== 'payment') }) - paid_temp_data_fee, last_ball_mci)
    : null;
...
function getOversizeFee(s) {
    if (!bChargeOversizeFee) return 0;
    if (mci < constants.pemCurvesFixMci) return storage.getOversizeFee(s - paid_temp_data_fee, last_ball_mci);
    return oversize_fee_excluding_payments;    // constant, ignores growing payment-message size
}
``` [1](#0-0) 

The comment explicitly states the rationale: "AA-generated units pay the oversize fee based on the unit size excluding its payment messages; this doesn't change as we add more inputs to the payment message, so calculate it only once." [2](#0-1) 

However, after the payment payload is fully assembled (inputs picked, outputs finalized, `payload_commission` recomputed to its real, final value), the code computes the **actual** `oversize_fee` on the complete unit, which now does include the fully-sized payment message(s):

```
objUnit.payload_commission = objectLength.getTotalPayloadSize(objUnit);
const oversize_fee = (mci >= constants.v4UpgradeMci) ? storage.getOversizeFee(objUnit, last_ball_mci, true) : 0;

    objUnit.oversize_fee = oversize_fee;
objUnit.unit = objectHash.getUnitHash(objUnit);
...
executeStateUpdateFormula(objUnit, ...);
validateAndSaveUnit(objUnit, ...);
``` [3](#0-2) 

`validateAndSaveUnit()` runs the unit through the normal `validation.js` pipeline, which enforces the strict payment balance for the base asset:
```
if (total_input !== total_output + objUnit.headers_commission + objUnit.payload_commission + oversize_fee + tps_fee + burn_fee + vote_count_fee)
    return callback("inputs and outputs do not balance: ...");
``` [4](#0-3) 

Because `total_input` was picked earlier to satisfy `net_target_amount + oversize_fee_excluding_payments` (a value that ignores the payment message's own size), while the balance check now requires `total_output + ... + oversize_fee` computed on the complete unit (which can be strictly larger once the payment message itself pushes the unit over the size threshold that computes a nonzero/larger oversize fee), the two amounts can diverge — exactly like `sellAmount` (approved) vs. `sellAmount*(1+fee)` (required) in the reported Gnosis bug. If `oversize_fee (final) > oversize_fee_excluding_payments (reserved)`, `total_input` is insufficient and validation fails.

This means the AA fails to execute its intended payment: its response bounces, state changes are rolled back, and the trigger's funds (minus `bounce_fees`) are returned instead of the intended transfer taking place. For AAs whose deterministic logic depends on this payment succeeding (e.g., exchanges, escrows, auctions implemented as AAs), this is a functional/financial denial-of-service: any legitimate trigger that produces a response unit whose payment message tips the unit over the oversize threshold will systematically and deterministically fail, freezing intended fund movement inside the AA (the AA never completes the operation the trigger paid for), analogous to "all auction initiation attempts may fail" in the original report.

### Likelihood Explanation
This is triggerable by any ordinary (unprivileged) unit poster who sends a trigger to an AA whose response includes a payment message large enough (multiple outputs, multiple assets, private-asset spend proofs, base-asset payment with several inputs) to push the *complete* unit size over an oversize-fee bracket that the *header+non-payment* size alone did not reach. Since AA definitions are commonly public/complex (multiple outputs, data messages, several payment messages), this condition is plausible in existing AAs whenever payment payload size is a meaningful fraction of total unit size — it does not require witness/hub/network‑level privilege, only a normal trigger unit.

### Recommendation
**Short term:** When computing the input-selection target during `completePaymentPayload`, do not use a payment-size-excluding fee estimate as a stand-in for the final fee. Either (a) recompute a (possibly slightly pessimistic) upper bound of the oversize fee that also accounts for the *anticipated* payment message size before selecting inputs, or (b) after computing the final `oversize_fee` on the complete unit, if it differs from the fee that inputs were selected to cover, loop back and pick additional inputs (or reduce outputs / raise a fresh change output) to cover the shortfall before calling `validateAndSaveUnit`, instead of only surfacing a bounce.

**Long term:** Make the oversize-fee formula used during input-picking and the one used for final validation provably consistent (a single authoritative function/parameterization), and add regression tests that specifically exercise AA responses whose payment-message size crosses an oversize-fee threshold, to guarantee `total_input` always covers the final `oversize_fee`.

### Proof of Concept
1. Deploy an AA whose response, for a given trigger, emits a `payment` message with many outputs/assets and a base-asset payment requiring several inputs (i.e., pushing `objUnit`'s total size, once completed, past the oversize threshold), while its `headers_commission + (non-payment payload size)` alone stays below that threshold.
2. Send a trigger causing this AA to build such a response. During `completePaymentPayload`, inputs are selected against `net_target_amount + oversize_fee_excluding_payments` (which is 0 or small, since it excludes the payment message).
3. After completion, `objUnit.oversize_fee = storage.getOversizeFee(objUnit, last_ball_mci, true)` is computed on the full unit and is now nonzero/larger because the payment message's own size is included.
4. `validateAndSaveUnit` runs `validatePaymentInputsAndOutputs`, which requires `total_input === total_output + headers_commission + payload_commission + oversize_fee + ...`; since `total_input` was picked using the smaller estimate, the check fails with "inputs and outputs do not balance", and the AA response `bounce()`s instead of completing the intended payment.
