### Title
CCMenu API endpoint ignores `ApiClient#stack_id` scoping, allowing a stack-scoped token to read any stack's state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The bug-class analog here is the same trust-binding break described in the external report: a credential is authorized for one specific resource (an L2 forwarder scoped to a particular chain/asset), but the code path that consumes it acts on a different, unchecked resource (raw ETH it was never designed to route). In Shipit, the equivalent binding is **the stack an `ApiClient` token authorizes == the stack the controller action actually touches**. `Shipit::Api::CCMenuController` breaks this equality.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping centrally: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is stack-scoped, and the generic `stack` helper resolves the `:stack_id` param only within that restricted set (`stacks.from_param!`). Every other API controller (e.g. `Api::StacksController#stack`) relies on this same scoped helper: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` relation, bypassing the scoping entirely, while still relying only on the generic permission check (`require_permission :read, :stack`) which merely verifies the token has the `read:stack` string in its permission list — it does not verify which stack that permission applies to: [3](#0-2) 

The `stack_id`-scoping feature is a real, supported part of the model (`belongs_to :stack, optional: true`) and is exercised in fixtures/tests (`here_come_the_walrus` is a token scoped to the `:shipit` stack only) and confirmed as an enforced boundary in `Api::StacksController` tests ("an api client scoped to a stack will only see that one stack"). `Api::CCMenuController` is the one endpoint that fails to apply this boundary.

### Impact Explanation
Any holder of a valid, narrowly-scoped `ApiClient` token (e.g. one issued only for stack A) can call `GET /api/stacks/:stack_id/ccmenu.xml` with an arbitrary `:stack_id` for stack B and successfully read stack B's build/deploy status, lock state, and last-build metadata, even though their token was never authorized for stack B. This is an unauthorized read of stack state across a credential/repository boundary the token was explicitly restricted to — the same class of "authorized-for-X, touches-Y" violation as the ETH/WETH binding break in the report, and matches the High-impact category ("unauthenticated/unauthorized read of stack state").

### Likelihood Explanation
Exploitation requires only possession of any legitimately scoped, low-privilege `read:stack` `ApiClient` token (such tokens are routinely handed out for CI status widgets/CCTray integrations) and knowledge or guessing of another stack's `to_param`/id — no additional privilege escalation, no signature forgery, and no session is needed. The overridden `stack` method makes this trivially and deterministically reachable.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the inherited `stacks.from_param!` scoping from `BaseController`) so that stack-scoped tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A with permission `read:stack` (as done via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(..., stack: stack_a)`, the same mechanism used for `here_come_the_walrus` fixture / CCMenu URL flow).
2. Using that token's `authentication_token` (Basic auth), request:
   `GET /api/stacks/<stack_b_id_or_slug>/ccmenu.xml?token=<token>`
   where `stack_b` is a different, non-authorized stack.
3. Observe the response returns HTTP 200 with `stack_b`'s CCTray project XML (name, lastBuildStatus, lastBuildLabel, webUrl), despite the token being scoped only to stack A — confirmed by contrast with `Api::StacksController`, where the same token against `/api/stacks/<stack_b_id>` correctly returns 404/empty due to the enforced `stacks` scoping.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
```
