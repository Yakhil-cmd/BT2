### Title
Tokens sent directly to the pool or controller are permanently frozen — internal cash/share bookkeeping never sees them and no recovery path exists - (File: contracts/pool/src/cache/cash.rs)

### Summary

The pool tracks liquidity in an internal `cash` ledger that is only credited through controller-mediated entrypoints (`supply`, `repay`, `recapitalize`) using measured balance deltas. A direct `token.transfer` to the pool or controller address raises the real balance without touching `cash`, and no entrypoint — privileged or unprivileged — lets anyone withdraw the excess over the books. This is the same bug class as the referenced Allo report: funds that arrive outside the tracked path are locked forever.

### Finding Description

The pool's reserve guard and all outbound paths are gated on the internal `cash` book, not `token.balance(pool)`:

- `Cache::require_reserves` / `debit_cash` only authorize payouts up to tracked `cash` (`contracts/pool/src/cache/cash.rs:15-41`). `withdraw`, `borrow`, `claim_revenue`, and `create_strategy` all debit cash before `transfer_out`, so they can never pay out more than the book.
- `transfer_out` moves tokens but "does not adjust accounting cash" (`contracts/pool/src/cache/cash.rs:43-53`); there is no skim/sweep entrypoint in the pool surface.
- `recapitalize` credits only `min(amount, backing_shortfall)` and refunds the remainder to `payer` (`contracts/pool/src/ops/recapitalize.rs:52-57`), so it cannot be driven to release a donation to an arbitrary caller — the refund equals the caller's own measured input.
- The design docs confirm donations are invisible: "Reserve checks use tracked market cash; token donations alone do not increase it" (`docs/reference/invariants.md`, INV-ACCT-02) and "Direct donations do not rewrite those books" (`docs/explanation/threat-model.md:130`).

On the controller side it is worse: refunds are snapshot-scoped, e.g. `repay_debt_from_controller` snapshots the controller balance *after* funding and refunds only the post-snapshot delta (`contracts/controller/src/strategies/legs.rs:59-80`), and the test `test_migrate_refund_ignores_preexisting_controller_balance` explicitly asserts a pre-existing controller balance "must remain (not used as refund or swept)". The controller has no sweep/recovery entrypoint at all.

Because pool books are per `(hub, token)` over one physical balance, a donation also can't leak out through a sibling market: each market's `cash` cap binds independently.

### Impact Explanation

Permanent freezing of funds. Any user who transfers tokens directly to the pool or controller address — a natural mistake on Stellar where funding a "pool address" feels intuitive, or via a non-obvious frontend — loses them irrecoverably. Unlike the Allo case where the manager's `withdraw` underflows only relative to `poolAmount`, here *no* code path can emit tokens beyond tracked `cash`/`scaled` claims, and the controller offers no recovery at all. Accrued Aquarius venue rewards pushed into the pool (documented as claimable without holder auth) are likewise trapped — acknowledged as "forgone yield" in the threat model, but the same mechanism traps user principal.

### Likelihood Explanation

Medium-low. It requires an off-protocol direct transfer, but the report's premise holds: SAC `transfer` to a contract address is trivially easy, mistakes happen, and reward pushes / stuck callback dust (e.g. flash or swap residual legs left in controller custody) create the same trapped-balance state without user error. Once present, the freeze is unconditional.

### Recommendation

- Add an owner-gated skim on the pool, e.g. `skim(hub_asset, recipient)` that transfers `token.balance(pool) - sum-of-market-cash-backing` (or simply `balance - cash` per market when custody is segregated), emitting an event. This preserves the `cash` invariant while making excess recoverable.
- Add an owner-gated `sweep(token, recipient)` on the controller for balances not owed to in-flight operations (mirroring `sweep_balance` already present in `contracts/swap-aggregator/src/lib.rs:188-203`, which correctly protects reserved fee buckets before sweeping).
- Alternatively/additionally, document and enforce a canonical "fund the pool via controller.supply" frontend path, and consider having `recapitalize`'s refund leg credit against a pre-existing unbooked balance rather than only the current call's input.
