### Title
Webhook signature verification is bound to a different organization than the repository/stack the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification from the payload's `organization.login`/`repository.owner.login`, but the event handlers that subsequently mutate state (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target `Stack`/`Commit` using a *different* payload field — `repository.full_name` or a bare `sha` — with no cross-check that it belongs to the organization whose secret authenticated the request. This breaks the binding `verified_organization == organization_of_repository_written`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config used to verify the HMAC signature purely from payload data: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `organization.login` when `repository.owner.login` is absent, and this determines which `Shipit.github(organization: ...)`/`webhook_secret` is used: [3](#0-2) 

Once signature verification succeeds, the actual event handlers do not re-check that the payload's target repository belongs to the same organization that was used for verification. `Handler#stacks` resolves the affected stacks purely from `repository.full_name`: [4](#0-3) 

`PushHandler#process` then calls `stack.sync_github` for every matching stack based solely on branch name: [5](#0-4) 

`StatusHandler#process` is even weaker: it matches purely by commit `sha` across the entire database, with no repository/organization scoping at all: [6](#0-5) 

`CheckSuiteHandler` similarly resolves `stacks` via `repository.full_name` and schedules check-run refreshes without validating that this repository belongs to the organization whose secret verified the request: [7](#0-6) 

Concretely: if organization A is onboarded to this Shipit instance (has its own `webhook_secret` configured), anyone who controls that organization's webhook configuration on GitHub's side (an org owner/admin of A — not a Shipit user, not holding any Shipit credential) knows or can set the exact `webhook_secret` value shared with Shipit. That party can then send an arbitrary, hand-crafted JSON body directly to Shipit's `/webhooks` endpoint, set `organization.login` (or `repository.owner.login`) to `A` so verification succeeds against A's real secret, while setting `repository.full_name` (for push/check_suite) or `sha` (for status) to reference a completely different, unrelated repository/stack `B` that is also tracked by the same Shipit instance. `verify_signature` only checks that the bytes are signed by A's secret — it never confirms that `A == owner_of(repository.full_name)`. The handler code then acts on stack `B` using data claimed to originate from `A`.

### Impact Explanation
This lets an org-admin of any one onboarded GitHub organization (a credential/authority far short of anything Shipit itself grants) forge push/check-suite/status events for any *other* organization's stacks tracked by the same Shipit instance:
- Forged `push`/`check_suite` events trigger `stack.sync_github`/`schedule_refresh_check_runs!` for stacks that do not belong to the attacker's organization, letting them force sync operations against arbitrary tracked repositories.
- Forged `status` events (`StatusHandler`) let the attacker inject a fabricated `Status` (state, description, context, target_url) onto any commit sha that happens to exist in the database, regardless of which stack/organization it belongs to, because the sha lookup is entirely unscoped by repository/owner. Since commit deployability (blocking statuses, CI status) gates automatic/continuous deployment and merge-queue processing, an attacker who can flip a commit's status to "success" for a repository they do not own can influence the deploy/merge readiness of a stack belonging to a different organization — a cross-repository/cross-organization authorization break using only their own org's legitimate webhook credential.

This matches the "cross-repository writes"/"unauthorized deploy" class of impact, since the deployability and sync state of another organization's stack can be manipulated by a party who is only authorized for their own organization.

### Likelihood Explanation
Exploitation requires only that the attacker administers (or has ever configured) the webhook secret for at least one organization already onboarded onto the target Shipit instance — a bar far below "repository write access" or possession of a Shipit `ApiClient`/session token. Multi-tenant Shipit deployments that onboard several organizations are the primary risk scenario. The attack is a single crafted HTTP POST with a correctly computed HMAC using a secret the attacker legitimately knows.

### Recommendation
After `verify_signature` succeeds, every handler must additionally confirm that the repository/organization referenced by the payload's data used for state mutation (`repository.full_name`, or the owner of the commit's stack in `StatusHandler`) matches the `repository_owner`/organization that was used to select the verifying secret. Concretely:
- In `Handler#stacks`/`PushHandler`/`CheckSuiteHandler`, reject or scope the resolved `Repository` to `repository.owner.login == verified_organization`.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup to commits belonging to stacks whose repository owner equals the verified organization, not a bare, global `sha` search.

### Proof of Concept
1. Attacker is an admin of GitHub organization `attacker-org`, which is legitimately onboarded to the target Shipit instance with its own configured `webhook_secret` (known to the attacker because they configured it on GitHub's side).
2. Victim organization `victim-org` is also onboarded to the same Shipit instance and has stack `victim-org/app` tracked, with pending commits gated by blocking statuses.
3. Attacker crafts a raw JSON body for a `status` event:
```json
{
  "sha": "<victim commit sha, e.g. discovered via public Shipit UI>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}
}
```
4. Attacker computes `sha1=HMAC-SHA1(attacker-org's known webhook_secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=...`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies the HMAC against `attacker-org`'s secret — succeeds.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and creates a forged success status on it, potentially unblocking deploy/merge readiness for `victim-org/app`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
