### Title
RAY-scaled debt value overflows `i128` during accrual, permanently freezing a whale market - (File: common/src/rates/index.rs)

### Summary
The bug class is an integer overflow in size/length arithmetic (ALPINE-CVE-2016-10164). In XOXNO Lending the analogous overflow is in the fixed-point accrual path: `calculate_supplier_rewards` multiplies the total scaled debt (`borrowed`, a RAY value) by the new borrow index (`new_borrow_index`, also RAY) via `Ray::mul`. When a market carries a very large scaled debt and the borrow index has grown by a large factor, the product `borrowed * new_borrow_index` exceeds `i128::MAX`, `try_mul_div_half_up` widens to `I256`, and the final `.to_i128()` returns `None`, which panics with `GenericError::MathOverflow`. Because `global_sync` runs before every pool verb, the panic permanently bricks the market.

### Finding Description
`global_sync` (`contracts/pool/src/interest.rs:20`) is invoked at the top of every cache-mutating pool operation (supply, withdraw, borrow, repay, seize/liquidation, flash). Each chunk calls `accrue_step`, which calls `calculate_supplier_rewards` (`common/src/rates/index.rs:73`):

```rust
let new_total_debt = borrowed.mul(env, new_borrow_index);   // index.rs:81
let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);
```

`Ray::mul` is `mul_div_half_up(x, y, RAY)`; when `x * y + RAY/2` overflows `i128` it falls back to `I256` and returns `None` from `.to_i128()` if the quotient itself exceeds `i128::MAX`, panicking with `MathOverflow` (`common/src/math/fp_core.rs:122-143`). `borrowed` is the sum of all scaled debt shares; for a high-decimal token (e.g., 18 decimals) supplied in whale quantities, `borrowed` is already a large RAY value, so a borrow index of ~170x is enough to push `borrowed * new_borrow_index` past the ceiling.

The borrow-index cap does not save this: `update_borrow_index` (`index.rs:13-19`) clamps the *index* at `MAX_BORROW_INDEX_RAY`, but the overflow is in `borrowed * index`, which blows up at an index far below the cap. The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`) demonstrates exactly this: after sustained ~98% utilization on the XLM rate curve, `update_indexes` panics with `MATH_OVERFLOW`, and subsequent `withdraw` and `repay` calls panic identically because they accrue first.

Reachability for a single unprivileged address: the attacker supplies a very large amount of a high-decimal listed asset via `controller.supply`, supplies collateral in a second market, and calls `controller.borrow` to drive utilization to the steep segment of the rate curve. From then on, accrual happens on every interaction; once `borrowed * borrow_index` crosses `i128::MAX`, every subsequent `update_indexes`, `withdraw`, `repay`, `liquidate`, `flash_loan`, `claim_revenue`, or `recapitalize` on that market reverts inside `global_sync`. Since indexes are monotonic (`update_supply_index`/`update_borrow_index` never decrease, and `apply_bad_debt_to_supply_index` floors at `SUPPLY_INDEX_FLOOR_RAW` rather than fixing the debt side), there is no recovery path — even `clean_bad_debt`/`recapitalize` accrue first.

### Impact Explanation
Permanent freezing of funds and a contract unable to operate: all suppliers' deposits and all borrowers' collateral backing this market become unreachable, and liquidations cannot execute, so any underwater debt is also uncollectible (protocol insolvency exposure). The freeze is permanent because the overflow depends only on state (scaled debt × index) that cannot be reduced without first completing an accrual that itself panics.

### Likelihood Explanation
Medium. It requires a market with very large aggregate scaled debt — practically a high-decimal token with supply caps set high by governance and utilization sustained near the steep part of the rate curve for the index to multiply enough (the harness uses ~98% utilization over multiple years of compounding). No privileged call is needed beyond the existence of such a market configuration; the attacker only uses `supply` and `borrow`. Capital requirements are large but the attacked asset can be a cheap high-decimal token.

### Recommendation
Compute `accrued_interest` without materializing `borrowed * new_index` when the product cannot fit `i128`: e.g., compute `borrowed * (new_index - old_index)` (the delta is much smaller), or perform the multiplication in `I256` throughout and keep totals in a wider type / saturate with a graceful market-pause flag instead of panicking. Additionally, enforce a protocol-level bound on `supplied`/`borrowed` scaled totals (in `Cache::calculate_scaled_supply`/`calculate_scaled_borrow` or the spoke `apply_entry` path) so that `scaled * MAX_*_INDEX_RAY` is guaranteed to fit `i128`, aligning the supply/debt cap domain with the arithmetic domain rather than only with the asset domain.

### Proof of Concept
The repo already contains a working PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`. It builds a market `BIG18` (18 decimals) with the XLM rate curve, supplies `BILLION * 10^18` units, borrows ~98% of it, advances time in one-year steps, and observes `update_indexes` failing with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. It then asserts both `withdraw` and `repay` revert with the same error, demonstrating the permanent freeze. An attacker replicates this with:

1. `controller.supply(BIG18, huge_amount)` — mints scaled shares (floor at supply index).
2. `controller.supply(COL, collateral)` + `controller.borrow(BIG18, ~0.98 * huge_amount)` — drives utilization onto the steep rate segment.
3. Wait / let time pass; any subsequent call (`update_indexes`, or any user's `withdraw`/`repay`/`liquidate`) enters `global_sync` → `accrue_step` → `calculate_supplier_rewards` → `borrowed.mul(new_borrow_index)` → `MathOverflow` panic, freezing the market.
