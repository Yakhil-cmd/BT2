### Title
Third-party `supply` restamps a foreign account's liquidation risk parameters without the health-factor floor that `update_account_threshold` enforces - (File: contracts/controller/src/positions/supply.rs)

### Summary
`update_account_threshold` — the permissionless keeper path for restamping cached risk parameters — is deliberately split in two: without `has_risks` it only restamps LTV (which the health factor never reads), and with `has_risks` it reverts unless the account ends above a 1.05 WAD health-factor floor, precisely so that nobody can push a foreign account into liquidation by restamping its cached liquidation parameters to newly-tightened listed values. The `supply` entrypoint bypasses that guard: any address may top up an asset the victim already holds, and the merge path unconditionally calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, restamping the position's full risk tuple as a side effect with no solvency floor check.

### Finding Description
The only authorization gate for a third-party supply is `require_third_party_existing_supply`, which merely asserts each supplied hub asset is already a supply position of the target account (contracts/controller/src/positions/supply.rs:78-97). It does not require owner or delegate authority, by design (INV-AUTH-03).

However, every supplied leg then flows through `process_deposit` → `merge_supply_leg`, which calls `refresh_supply_risk_params(env, cache, account, hub_asset, &mut position, &asset_config, RiskRefreshScope::FullTuple)` (contracts/controller/src/positions/supply.rs:288-296) before crediting the shares. `FullTuple` restamps the position's cached risk tuple — including the liquidation-side parameters that the health factor reads — to the currently listed `AssetConfig` values.

The contrast with the sanctioned restamp path is explicit in the protocol's own invariant documentation: `update_account_threshold(caller, has_risks, account_ids)` "reverts unless the account clears the update health-factor floor, so it cannot be used to push an account into liquidation" (scripts/permissionless_entrypoints.txt:76). The supply path applies the same class of restamp to a foreign account with no equivalent floor: `process_supply` runs `finalize_position_flow` with `PositionSides::Supply`, which performs no post-action solvency check on the target (ordinary `supply` skips risk checks entirely per docs/reference/endpoints.md:55).

Attack sequence after governance tightens a listed asset's liquidation parameters (a legitimate, ratcheted `EditAssetInSpoke`/`RelaxSpokeAssetFlags` action):

1. Victim account holds a supply position in asset X, cached with the old (looser) liquidation threshold; HF > 1 under cached params, HF < 1 under the new listed params.
2. Attacker calls `update_account_threshold(true, [victim])` — reverts, because the post-restamp HF floor is not met.
3. Attacker instead calls `supply(attacker, victim_id, spoke_id, [(X_key, dust)])`. X is already a supply position, so `require_third_party_existing_supply` passes.
4. `merge_supply_leg` restamps the victim's X position to the tightened tuple.
5. The victim's HF is now < 1; the attacker immediately calls `liquidate` and seizes collateral at the bonus.

The attacker needs only dust of an asset the victim already supplies, plus the liquidation repayment capital — fully within reach of a single unprivileged address.

### Impact Explanation
Theft of user funds via forced liquidation. A solvent-under-cached-params account is pushed below HF 1 by an unauthorized risk restamp, then liquidated at the HF-based bonus. The attacker captures the liquidation bonus and the victim loses collateral it would not have lost through the guarded `update_account_threshold` path. This mirrors the CVE class exactly: an entrypoint authenticates the caller (`require_authorized_caller`) but fails to enforce the permission check appropriate to the privileged side effect it performs.

### Likelihood Explanation
Requires a governance tightening of risk parameters on a listed asset while some accounts still carry stale cached tuples — a normal and recurring event, since cached params are deliberately sticky and restamped lazily. After such a change, every account whose cached params are looser than the new listing is exposed; the attacker needs only a dust amount of an asset the victim already holds. No privileged role, leaked key, or victim cooperation is needed. Confidence caveat: the precise scope of `RiskRefreshScope::FullTuple` versus the LTV-only restamp in `update_account_threshold` was inferred from the variant name and the documented LTV/liquidation-parameter split; if `FullTuple` provably excludes liquidation parameters, the restamp cannot move HF and this reduces to a no-impact inconsistency.

### Recommendation
In `process_supply`, when `is_owner_or_delegate` is false (i.e., the third-party top-up branch already isolated by `require_third_party_existing_supply`), either:
- skip the `refresh_supply_risk_params` call in `merge_supply_leg` and reuse the position's existing cached tuple, or
- restamp with the same LTV-only scope that `update_account_threshold` uses without `has_risks`, or
- enforce the same post-restamp health-factor floor (≥ 1.05 WAD) that the `has_risks` keeper path requires, reverting the supply if the restamp would leave the account below it.

### Proof of Concept
```rust
// Precondition: governance executed EditAssetInSpoke lowering X's
// liquidation threshold. Victim's cached tuple is the old, looser one:
// HF_cached > 1, HF_new < 1.
//
// update_account_threshold refuses:
//   update_account_threshold(attacker, true, [victim_id])  // reverts, HF floor
//
// supply does not:
let dust = 1i128; // X base units; victim already holds a supply position in X
let key = HubAssetKey { hub_id, asset: x_token };
client.supply(&attacker, &victim_id, &spoke_id, &vec![&env, (key.clone(), dust)]);
// merge_supply_leg -> refresh_supply_risk_params(.., RiskRefreshScope::FullTuple)
// victim's X position now carries the tightened liquidation params.
assert!(client.get_health_factor(&victim_id) < WAD);
// Attacker liquidates at the bonus.
client.liquidate(&attacker, &victim_id, &debt_payments, &SeizeMode::Transfer);
```

Relevant code: `require_third_party_existing_supply` (contracts/controller/src/positions/supply.rs:78-97), unconditional `refresh_supply_risk_params(..., FullTuple)` (contracts/controller/src/positions/supply.rs:288-296), and the guarded counterpart `update_account_threshold` semantics (scripts/permissionless_entrypoints.txt:76).
