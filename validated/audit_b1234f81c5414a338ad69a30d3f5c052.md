Unauthenticated/wrongly-scoped read of stack build status via `CCMenuController#stack` bypassing token stack-scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController` overrides the inherited `stack` helper to call `Stack.from_param!(params[:stack_id])` directly instead of using the base class's scoped `stacks` method. As a result, an `ApiClient` token that is narrowly scoped to one stack (via `stack_id`) can be used to read deploy/build status (`show` action) for any other stack, because the scope check is never applied on this controller.

### Finding Description
The intended binding is: **token.stack_id == requested stack.id** whenever `current_api_client.stack_id?` is true. This is implemented once, in `BaseController#stacks`: [1](#0-0) 
`BaseController#stack` correctly calls `stacks.from_param!(...)`, so the scope is enforced for controllers that don't override it.

However, `CCMenuController` defines its own `stack` method that ignores `stacks` entirely: [2](#0-1) 

`authenticate_api_client` in this controller also only accepts `params[:token]` and falls back to the parent's basic-auth flow, but does not restore the scoping: [3](#0-2) 

The only permission check applied is `require_permission :read, :stack`, which calls `check_permissions!`: [4](#0-3) 
This method only checks the string-array `permissions` (e.g. `"read:stack"`) and never compares `stack_id` to the requested stack — so it cannot catch cross-stack use.

Exploit flow: an attacker who has obtained *any* valid `ApiClient` token (e.g., leaked in a referrer/log, or created for a legitimately different, narrowly-scoped purpose — token itself, not secrets, is the credential here) that is scoped to stack A via `stack_id`, can call `GET /stacks/:owner/:repo/:branch/ccmenu.xml?token=<TOKEN>` for stack B's `stack_id` route parameters. `ApiClient.authenticate` only verifies the signed token and looks up the `ApiClient` row by id — it does not know or care which stack was requested. Then `stack` resolves via unscoped `Stack.from_param!`, returning stack B, and `show` renders stack B's latest deploy/build status.

### Impact Explanation
The attacker obtains stack build/deploy status (`shipit/ccmenu/project.xml`: latest deploy id, timestamp, success/failure/running state) for a stack they were never authorized to access, using a token intentionally scoped away from that stack by its issuer. This is a read-only information disclosure of CI/CD state, repeatable for any stack in the Shipit instance as long as any valid token exists, matching the "unauthenticated/wrongly-scoped read of stack state" High-severity category. Blast radius spans all stacks/tenants hosted on the same Shipit instance, since one narrowly-scoped token can enumerate all stacks' CCMenu status.

### Likelihood Explanation
Requires possession of at least one valid `ApiClient` token (any token, even one deliberately scoped to a single, unrelated stack) — no `api_clients_secret` or other server secret is needed since the token is the bearer credential by design. Given the scenario's assumption that some token has leaked or been obtained through a non-privileged channel (as described in the question), exploitation is a single unauthenticated GET request with no rate limiting or additional barriers, making it trivially repeatable against every stack in the deployment.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` helper instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id?` restriction from `BaseController#stacks` is enforced consistently across all API controllers.

### Proof of Concept

2. Create `api_client = Shipit::ApiClient.create!(creator: user, name: 'scoped', stack: stack_a, permissions: ['read:stack'])`.
3. `token = api_client.authentication_token`.
4. `get shipit.api_ccmenu_path(stack_b.to_param, token: token)` (or whatever route helper matches `stack_id` for stack B).
5. (== stack_a.id) != requested stack.id (== stack_b.id)` yet access is granted.
