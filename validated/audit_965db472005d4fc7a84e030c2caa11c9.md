### Title
`MembershipHandler#find_or_create_team!` matches Teams solely by `github_id`, letting a webhook verified with any organization's secret add members to a `Team` belonging to a different organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id) { ... team.organization = params.organization.login }` [1](#0-0) . The block that sets/checks `organization` only runs on record creation; if a `Team` with that `github_id` already exists (e.g., belonging to Org A), the existing record is returned unchanged and `params.organization.login` is never compared against `team.organization` before `team.add_member(member)` is called at [2](#0-1) . Signature verification in `verify_signature` only proves the payload was signed by the organization named in `repository_owner` (falling back to `params.organization.login`) [3](#0-2) [4](#0-3) ; it does not bind the signer's organization to the `team.id` referenced inside the same payload.

### Finding Description
The broken binding: the code should enforce `params.organization.login == team.organization` for the `Team` row matched by `params.team.id` before mutating its `memberships`. It does not — `find_or_create_by!` looks up purely by `github_id`, an attacker-suppliable integer that is not scoped to the signing organization, and skips the block (where `organization` is assigned) entirely when a matching row already exists.

Exploit flow:
1. Org A previously triggered a legitimate `membership` webhook, creating `Shipit::Team` with `github_id = X`, `organization = "org-a"`.
2. Attacker owns/controls Org B on GitHub (any org they can create, no privilege in Shipit needed) and has configured a webhook to `POST /webhooks` with Org B's own webhook secret, satisfying `Shipit.github(organization: "org-b").verify_webhook_signature`.
3. Attacker sends (or crafts, via any org they control, a `membership` event) a payload where `organization.login = "org-b"` (so `repository_owner` and the HMAC check pass using Org B's real secret) but `team.id = X` (Org A's team's `github_id`) and `member.login` = attacker's own GitHub login, `action: "added"`.
4. `verify_signature` passes because the signature is valid for Org B's own webhook secret over this exact payload — no cross-organization secret is required.
5. `MembershipHandler#process` runs `find_or_create_team!`, which finds the existing Org A `Team` by `github_id: X`, skipping the creation block (and thus never re-checking or comparing `organization`).
6. `team.add_member(member)` is called on Org A's `Team`, inserting a `Shipit::Membership` row linking the attacker's `User` to Org A's `Team` [5](#0-4) .

Existing guards do not stop this: `verify_signature`/`GithubApp#verify_webhook_signature` only authenticates that *some* organization named in the payload's `repository`/`organization` field signed it — it never checks that this organization matches the one owning the referenced `team.github_id`. The `ExplicitParameters` schema only validates types/presence, not cross-field authorization [6](#0-5) .

### Impact Explanation
This is a cross-tenant write: a webhook authenticated for Org B causes a `Membership` row to be created for a `Team` that belongs to Org A, without any comparison of `team.organization` against the verified `organization.login`. If that `Team` is referenced in `Shipit.github_teams` (used by `User#authorized?` to gate access to the Shipit UI/deploys: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [7](#0-6) , an attacker can grant themselves membership in a privileged team and thereby gain authorization within Shipit — matching the High-severity category "escalation into `Shipit.github_teams` authorization." The attack is repeatable against any `Team#github_id` the attacker can learn (team IDs are not treated as secrets and are frequently discoverable via GitHub's API/UI), and works against arbitrary existing teams once their `github_id` is known.

### Likelihood Explanation
Preconditions: the target `Team` row must already exist in Shipit's database (created by a prior legitimate webhook from its real organization), and the attacker needs to know its `github_id`. The attacker needs their own GitHub organization/repository with a webhook they control (trivial to create, no Shipit privileges needed) and the ability to send an HTTP POST to `/webhooks` with a payload whose `organization.login` matches that org and `team.id` matches the target's `github_id`. This is inexpensive and fully within the described unprivileged attacker capability (any internet user sending POST /webhooks). Team GitHub IDs are sequential/discoverable, making enumeration plausible.

### Recommendation
In `find_or_create_team!`, look up the `Team` by both `github_id` and `organization`, and explicitly raise/reject when a `Team` exists with the same `github_id` but a different `organization` than `params.organization.login`, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "Team #{team.id} organization mismatch"
  end
  team || Team.create!(github_id: params.team.id, organization: params.organization.login, github_team: params.team)
end
```

### Proof of Concept
Minitest plan (non-network, using existing fixtures/hook signing helpers):
1. Create two `GithubHook::Organization` fixtures, `org_a` and `org_b`, with distinct secrets (fixtures already used for webhook signature tests).
2. Create a `Shipit::Team` fixture belonging to `org_a` with `github_id: 999`.
3. Build a `membership` payload: `{ action: 'added', team: { id: 999, name: 'X', slug: 'x', url: '...' }, organization: { login: 'org_b' }, member: { login: 'attacker' }, repository: { owner: { login: 'org_b' } } }`.
4. Sign the payload with `org_b`'s real webhook secret (as `verify_webhook_signature` expects).
5. `assert_difference -> { Shipit::Team.find_by(organization: 'org_a').memberships.count }, 1 do post :create, headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature }, body: payload.to_json end`
6. Assert response is `:ok` and that the new `Shipit::Membership` links the attacker's user to the `org_a` team, proving the equality `params.organization.login (org_b) != team.organization (org_a)` was never checked.
