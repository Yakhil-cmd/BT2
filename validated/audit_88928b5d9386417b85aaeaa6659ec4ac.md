### Title
Unbounded-length private-payment chains cause unbounded allocation/DB growth in wallet/network private-payment handling - (File: wallet.js)

### Summary
The Go `archive/tar` bug is about a reader that trusts an attacker-controlled *count* of sparse-map regions and allocates memory proportional to that count without any upper bound. The analogous pattern in ocore is `handlePrivatePaymentChains()` in [1](#0-0) , which accepts `body.chains` — an attacker/counterparty-controlled array of private-payment chains, each itself an array of chain elements — and validates only the *shape* of each element (non-empty object/array checks), never an upper bound on `arrChains.length` or on the length of any individual chain `c`.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` is reachable from a private-payment counterparty (a correspondent device sending a `private_payment_chains`-style justsaying) and from files opened in `handlePrivatePaymentFile`. It does: [1](#0-0) 

Unlike every other externally-supplied collection in the codebase — `objUnit.messages` (`MAX_MESSAGES_PER_UNIT`), payment `inputs`/`outputs` (`MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`), `spend_proofs` (`MAX_SPEND_PROOFS_PER_MESSAGE`), data feeds (`MAX_DATA_FEEDS_PER_MESSAGE`), asset denominations/attestors (`MAX_DENOMINATIONS_PER_ASSET_DEFINITION`/`MAX_ATTESTORS_PER_ASSET`) — all enumerated as anti-spam limits in [2](#0-1) , there is **no** `MAX_...` constant bounding the number of chains in `body.chains` or the number of elements in a single private-payment chain.

Each chain is subsequently hashed in full (`objectHash.getBase64Hash(arrChains)`), and for light clients each element is JSON-stringified and persisted verbatim into `unhandled_private_payments` before any per-element cryptographic/DB validation occurs, via `savePrivatePayment()` in [3](#0-2)  and [4](#0-3) . For light wallets with `arrPrivateElements.length > 1`, the code stores the payload directly to the DB and calls `updateLinkProofsOfPrivateChain`/`rerequestLostJointsOfPrivatePayments` without ever checking the chain length against any bound. Full-node processing goes through `parsePrivatePaymentChain` in [5](#0-4) , which iterates the entire attacker-supplied chain (`async.forEachOfSeries(arrPrivateElements, ...)`) performing a DB query and cryptographic hash computation per element, again with no cap on `arrPrivateElements.length`.

This mirrors the CVE precisely: a small, cheaply-constructed message (`body.chains` with a very large `c` array or many large `c` arrays) forces the receiving node to allocate memory (JSON buffers, hash-computation intermediate objects, DB inserts) and perform CPU/DB work proportional to an attacker-chosen, unbounded count — exactly the "large number of sparse regions cause unbounded read/allocate from a small compressed input" pattern.

### Impact Explanation
A malicious correspondent/private-payment counterparty (or a crafted `.textcoin`/private-payment file opened via `handlePrivatePaymentFile`, [6](#0-5) ) can send one `private_payment_chains` message whose `chains` array contains an extremely deep or extremely wide (many chains) structure. This causes the victim wallet to:
- allocate large in-memory JSON/array structures and compute `objectHash.getBase64Hash` over the whole structure,
- for light wallets, persist the entire uncapped payload into `unhandled_private_payments` (permanently, with no size ceiling, until handled/deleted),
- iterate every chain element synchronously performing DB round-trips and hashing.

This can exhaust memory/CPU/disk on the victim's node, degrading or halting its ability to process and confirm its own private and possibly non-private transactions — i.e., "a network (node) unable to confirm new units" for the targeted wallet. It does not directly cause double-spend or supply inflation, but it is a concrete resource-exhaustion vector triggerable by a single crafted message from an already-authorized correspondent (private-payment counterparty), which is one of the explicitly in-scope actors.

### Likelihood Explanation
Likelihood is high for any wallet that accepts private payments from arbitrary correspondents/hubs (which is the default use case of private/blackbytes-style assets). No signature or proof-of-work is required on `body.chains` before the size-unbounded processing occurs; the only checks are structural (`isNonemptyArray`/`isNonemptyObject`), which a single-line crafted array easily satisfies. Triggering requires only sending one `private_payment_chains` justsaying to the victim (or getting them to open a crafted private-payment file), no special network position, no privileged role.

### Recommendation
- Introduce explicit anti-spam constants analogous to the existing `MAX_*_PER_*` family, e.g. `MAX_CHAINS_PER_PRIVATE_PAYMENT_MESSAGE` and `MAX_ELEMENTS_PER_PRIVATE_PAYMENT_CHAIN`, and enforce them at the very start of `handlePrivatePaymentChains()` in [1](#0-0)  before any hashing or iteration.
- Enforce the same bound in `handleOnlinePrivatePayment()` ( [7](#0-6) ) prior to `savePrivatePayment()`/DB insertion, and in `parsePrivatePaymentChain()` ( [8](#0-7) ) prior to `async.forEachOfSeries`.
- Cap the total serialized size of `unhandled_private_payments.json` per row and per peer, and add periodic purge/eviction for stale/oversized unhandled entries.

### Proof of Concept
1. As a correspondent device (already paired, i.e. a legitimate "private-payment counterparty"), construct:
```json
{
  "chains": [
    [ /* N synthetic but structurally-valid chain elements, each: */
      { "unit": "<44-char base64 unit>", "payload": { "asset": "<44-char base64>", "inputs":[{}], "outputs":[{}] } },
      /* ... repeat N times, e.g. N = 1,000,000 ... */
    ]
  ]
}
```
2. Send this as a `private_payment_chains` message (via `handlePrivatePaymentChains`) to the victim wallet, through the hub or directly.
3. Observe that `wallet.js` computes `objectHash.getBase64Hash(arrChains)` over the full N-element structure and, for light wallets, immediately serializes and stores the entire chain in `unhandled_private_payments` via `network.handleOnlinePrivatePayment` → `savePrivatePayment`, before any cryptographic/chain validation rejects the malformed elements — consuming memory/CPU/disk proportional to N with no configured ceiling.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&

			e.payload.inputs.every(isNonemptyObject) &&

		)
	))

function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
}
