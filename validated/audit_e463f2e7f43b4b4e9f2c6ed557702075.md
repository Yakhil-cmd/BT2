## Title
Unauthenticated Device Message with Unrecognized Ephemeral Key Causes Deferred Uncaught Exception That Crashes the Node - (File: device.js)

### Summary
`decryptPackage()` in `device.js` throws an `Error` from inside a `setTimeout` callback when a received device message's `encrypted_package.dh.recipient_ephemeral_pubkey` doesn't match the node's current temp, previous temp, or permanent device key. Because the throw happens asynchronously (100ms later, outside the calling stack), it is not caught by the `try { … } catch(e) { … }` block that wraps the `decryptPackage()` call in `handleJustsaying()`. The resulting uncaught exception is caught by the global `process.on('uncaughtException', …)` handler in `network.js`, which deliberately re-throws to crash the process. This lets any party able to route a device message to the node's device address (via a hub, exactly the "paired device / AA trigger sender"-class unprivileged actor category) crash the full node with a single malformed message, mirroring the Teku UDP-packet DoS bug class (malformed, easily-crafted input causing an unhandled fault that kills the process).

### Finding Description
`device.js` handles incoming device messages relayed through a hub: [1](#0-0) 

The signature/hash checks (lines 163-172) are synchronous and wrapped in `try/catch`, but the actual decryption call at line 177 (`decryptPackage(objDeviceMessage.encrypted_package)`) is only guarded against *synchronous* exceptions.

Inside `decryptPackage`, if the `recipient_ephemeral_pubkey` doesn't match any of the three known keys (current temp key, previous temp key, or permanent key), the function logs a message and schedules a deferred throw: [2](#0-1) 

Since this `throw` executes inside a `setTimeout` callback, it runs on a new stack frame, completely bypassing the `try/catch` in `handleJustsaying` (device.js lines 176-181) that was meant to catch decrypt failures. The resulting exception becomes an uncaught exception at the process level.

`network.js` installs a global handler for this scenario that intentionally kills the whole node process: [3](#0-2) 

Critically, this decrypt attempt happens *before* the node checks whether the sender is even a known correspondent: [4](#0-3) 

So an attacker does not need to be a paired correspondent — they only need to be able to send a structurally valid `hub/message` (self-signed with an arbitrary keypair, which the sender fully controls) addressed to the target's device address, containing an `encrypted_package` whose `dh.recipient_ephemeral_pubkey` is any value that doesn't happen to equal the target's live/prev-temp/permanent public key (trivially satisfiable — just use a random 33/65-byte base64 string of the right shape).

### Impact Explanation
This directly causes a node crash (denial of service) for any node that runs the device/wallet layer (e.g., full nodes with paired devices, headless wallets, hub-connected nodes), analogous to the Teku 46-byte UDP packet crash. A crashed full node stops relaying/validating units and stops confirming new units until manually restarted, satisfying the "network unable to confirm new units" impact bar. Because the trigger condition is on the open/unencrypted metadata of the message (only `dh.recipient_ephemeral_pubkey` needs to mismatch), the attacker doesn't even need to break encryption or know any secret — an essentially garbage but well-formed packet suffices.

### Likelihood Explanation
High. No special privileges, correspondent relationship, or correct cryptographic material is needed — only the ability to route one `hub/message` justsaying (or a `hub/deliver` request forwarded by a hub) to the victim's device address with a syntactically valid `encrypted_package`. The check that filters unrecognized correspondents happens only after decryption is attempted, so the crash path is reached unconditionally for any inbound message not encrypted to a currently valid key.

### Recommendation
Wrap the deferred throw with proper non-fatal error reporting instead of `throw` inside `setTimeout`, e.g., emit `eventBus.emit('nonfatal_error', …)` (the already-commented-out line at device.js:434) instead of scheduling a fatal throw, and make sure `decryptPackage` failures always resolve via `respondWithError`/return codes rather than an unhandled asynchronous exception. At minimum, do not let unrecognized-key messages result in an uncaught exception that reaches the process-level `uncaughtException` handler that re-throws and kills the process.

### Proof of Concept
1. Attacker generates an arbitrary EC keypair and crafts a `objDeviceMessage`:
   - `to`: victim's device address
   - `pubkey`/`signature`: self-signed and internally consistent (attacker signs with their own key — no correspondent relationship required)
   - `encrypted_package`: valid `iv`, `authtag`, `encrypted_message` (any base64 garbage of plausible length), `dh.sender_ephemeral_pubkey` (any valid-looking pubkey), `dh.recipient_ephemeral_pubkey` set to a random value that does NOT match victim's current/prev temp key or permanent key.
2. Attacker sends this as `['justsaying', {subject: 'hub/message', body: {message_hash, message: objDeviceMessage}}]` to a hub connected to the victim device (or via `hub/deliver` if attacker is the hub).
3. `handleJustsaying` in `device.js` passes signature checks (self-signed, so they pass), calls `decryptPackage`, which hits the `else` branch at device.js:429-436, logs "message encrypted to unknown key", and schedules `setTimeout(() => { throw Error(...) }, 100)`.
4. 100ms later, the throw fires with no surrounding try/catch on that stack, `process.on('uncaughtException', …)` fires in `network.js`, and the handler executes `throw err;` at network.js:4542, terminating the node process.
