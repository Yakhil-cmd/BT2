### Title
Cross-repository forgery of `github_status.context` allows overwriting a victim stack's required CI check via any authenticated-but-unscoped `status` webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` selects commits to update by `sha` alone, with no repository scoping, and `Shipit::Status.replicate_from_github!` persists whatever `(context, state, sha)` tuple it is given without verifying it originated from the target stack's own `github_repo_name`. Because git commit SHAs are content-derived and not repository-bound, any repository configured in the same multi-tenant Shipit instance can emit a validly-signed `status` webhook naming a SHA that also exists in a victim stack, forging a specific required context (e.g. `ci/required`) as `success`.

### Finding Description
Binding claimed by the question: `github_status.context` authenticity (must originate from `stack.github_repo_name`'s own CI) == accepted for any verified webhook regardless of originating repository. Tracing the code shows this binding is **broken** (i.e., the insecure equality holds true).

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature against the webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`). This proves the payload came from *some* GitHub organization/repo registered in this Shipit instance — it proves nothing about which stack's commits the `sha` in the body is allowed to affect.
- `Shipit::Webhooks::Handlers::Handler` (the base class) exposes `stacks` / `repository_name` helpers that scope processing to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and every `PullRequest::*Handler` (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) uses exactly this pattern to resolve `repository` before doing anything.
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:7-24`) does **not** declare or use `repository` in its `params` schema at all, and its `process` method is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries **every** `Commit` row across **all stacks** that matches the given `sha`, with no join/filter on repository.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (`app/models/shipit/status.rb:23-33`) does `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)` — it blindly persists the tuple, with no check that `context`/`state` were produced by `stack.github_repo_name`'s own CI.
- Once persisted, `Status::Common#required?` (`app/models/shipit/status/common.rb:50-52`) checks `commit.required_statuses.include?(context)`, and `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) depends on the aggregated status state — so a forged `success` status for a required `context` directly satisfies the CI gate used for deploys and merge-queue processing (`deploy_spec.rb:194-196`, `merge_request_required_statuses`).

Exploit flow: Attacker owns/controls Repo B, which is registered in the same Shipit instance (its own organization/webhook secret is legitimately configured — the attacker never needs to know any secret; GitHub itself signs the webhook when Repo B's own CI posts a status). Victim's Stack A tracks Repo A on some branch, and has synced a `Commit` row for SHA `S` (a normal, often public, commit — SHAs are visible via git/GitHub UI). Because git SHAs are pure content hashes independent of the hosting repository, the attacker reproduces a commit with the exact same tree/parents/author/committer/message/timestamps inside their own Repo B (e.g., by pushing an identical copy/mirror or opening a PR from a fork that contains the same commit) — this commit shares SHA `S` with the tracked commit in Stack A. The attacker then triggers (or crafts, in test) a `status` event from Repo B with `sha: S`, `context: 'ci/required'`, `state: 'success'`. GitHub signs this with Repo B's/organization B's webhook secret, so `verify_signature` passes. `StatusHandler#process` finds **all** `Commit` rows with `sha: S`, including Stack A's, and writes `success` for `ci/required` onto it — completely unrelated to Repo A's CI.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`) do not close this gap: signature verification is per-organization, not per-repository/per-stack, and the `StatusHandler` schema never requires or checks `repository.full_name` before writing.

### Impact Explanation
An attacker with no privileges on the victim's stack/repo can write a fabricated CI status (any state, on any context, including a specifically-named required check like `ci/required`) directly onto a commit belonging to a stack they do not control, as long as they can get a commit with the same SHA hosted (even transiently) under a repository they own that is also wired into the same Shipit deployment. This is a cross-tenant record forgery: a payload authenticated for repository B mutates repository A's commit/stack state. Since `required_statuses`/`deployable?` gate both deploys (`Commit#deployable?`) and the merge-queue (`merge_request_required_statuses`), this can lead to an unauthorized deploy or merge being unblocked by a forged "success" — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge"). The attack is repeatable against any stack/commit whose SHA the attacker can reproduce in a repo they control, and scales across all stacks hosted by the same multi-tenant Shipit instance.

### Likelihood Explanation
Preconditions: the Shipit instance must host more than one organization/repository (a common multi-tenant deployment) so the attacker can register/own a repo with a legitimately-signed webhook path into the same install. The attacker needs to know a target SHA already tracked by the victim stack (trivially obtainable for public repos, or via any read access to the victim repo's commit history) and must be able to get a byte-identical commit into their own repo, which is a normal git operation (mirroring, forking, cherry-picking with `--allow-empty`/preserved metadata, or `git commit-tree` reproduction) — no cryptographic break, no secret required, and no privileged Shipit role needed. Cost is low and the exploit is repeatable per request.

### Recommendation
Scope `StatusHandler#process` (and `Status.replicate_from_github!`) by repository, not just by SHA: require `repository.full_name` in the handler's `params` schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit.where(sha: ...)` lookup to `commit.stack.repository_id == repository.id` (i.e., only update commits belonging to stacks whose `github_repo_name` matches the webhook's originating repository). Reject/ignore the event otherwise.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoForgeryTest < ActiveSupport::TestCase
        test "status event from repo B forges a required context on stack A's commit" do
          stack_a = shipit_stacks(:shipit) # tracks repo "shopify/shipit-engine"
          stack_a.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'require' => ['ci/required'] }))

          commit = stack_a.commits.create!(
            sha: 'deadbeef00000000000000000000000000000000',
            author: shipit_users(:walrus),
            committer: shipit_users(:walrus),
            authored_at: Time.now,
            committed_at: Time.now,
            message: 'shared content commit'
          )

          # Binding before: stack A's commit has no required status recorded, not deployable.
          refute commit.required_statuses.empty?
          refute commit.reload.deployable?

          # Attacker crafts a `status` payload as if delivered from "attacker/repo-b",
          # reusing the identical sha, naming the victim's required context.
          forged_payload = {
            'sha' => commit.sha,
            'state' => 'success',
            'context' => 'ci/required',
            'description' => 'forged',
            'target_url' => 'http://attacker.example.com',
            'created_at' => Time.now.iso8601,
            'branches' => [{ 'name' => 'main' }],
            'repository' => { 'full_name' => 'attacker/repo-b', 'owner' => { 'login' => 'attacker' } }
          }

          params = StatusHandler.param_parser.parse!(forged_payload)
          StatusHandler.new(forged_payload).process

          commit.reload
          status = commit.statuses.find_by(context: 'ci/required')

          # Binding after: repo B's payload has written a status onto stack A's commit,
          # satisfying the required check even though repo B never owns stack A.
          assert_equal 'success', status.state
          assert commit.deployable?, "stack A's commit became deployable via a status forged from an unrelated repository"
        end
      end
    end
  end
end
```
This demonstrates the equality `github_status.context authenticity == accepted regardless of originating repository` holds true in the current code (no repository check exists before `replicate_from_github!` persists the tuple), confirming the vulnerability.
