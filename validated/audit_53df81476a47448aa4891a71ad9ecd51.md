## Title
Time-of-Check-to-Time-of-Use Race Condition in Private Payment Chain Validation Allows Double-Spend of Private Outputs - (File: private_payment.js, indivisible_asset.js, divisible_asset.js)

### Summary
The reported PasswordPusher bug is a TOCTOU race where a limit (`expire_after_views`) is checked and only later incremented, letting concurrent requests slip through before the limit is enforced. Ocore has a structurally identical race in the **private-payment chain validation path**: the double-spend check on a private (hidden) output is performed via a plain `SELECT` inside a per-call DB transaction, and the corresponding `INSERT` that "consumes" the output happens later in the same call — but unlike public units (which serialize validation with `mutex.lock(arrAuthorAddresses, …)` in `validation.js`), private chains are explicitly processed **in parallel with no address/output-level lock**.

### Finding Description
For public units, `validation.validate()` wraps the entire validation+double-spend check in `mutex.lock(arrAuthorAddresses, …)` before any DB reads/writes occur [1](#0-0) , so two conflicting spends from the same author can never be validated concurrently.

Private payment chains bypass this. `handleSavedPrivatePayments()` in `network.js` explicitly processes multiple queued private chains **in parallel** (`async.each`, commented "handle different chains in parallel") [2](#0-1) , and `handleOnlinePrivatePayment()` invokes `privatePayment.validateAndSavePrivatePaymentChain()` directly with no mutex at all [3](#0-2) .

Inside `private_payment.js`, each call takes its **own** DB connection and transaction, does a duplicate-output `SELECT`, and only afterward calls the asset module to validate and insert [4](#0-3) . The actual double-spend guard is `checkForDoublespends`/`checkInputDoubleSpend` in `validation.js`, which is also a `SELECT`-then-defer pattern: it queries the `inputs` table for a conflicting record and only decides afterward whether to accept it [5](#0-4) . The row that would prevent the double-spend is written only later, inside `validateAndSavePrivatePaymentChain` in `indivisible_asset.js`, via an `INSERT … db.getIgnore() … INTO inputs` [6](#0-5)  (same pattern in `divisible_asset.js` [7](#0-6) ).

Because each private-chain validation runs in its own separate connection/transaction and there is no lock keyed on the spent output (`src_unit`/`src_message_index`/`src_output_index`) or the spender's address, two concurrent private payment chains spending the **same hidden private output** to two different recipients can both pass the `SELECT`-based double-spend check before either transaction commits its `INSERT`. This is precisely the TOCTOU pattern in the external report — a limit ("this output can be spent only once") checked via a read that is not exclusive, followed by a write that finalizes consumption, with no lock spanning the check-and-write.

### Impact Explanation
A successful race lets an attacker spend the same private (hidden, blackbyte-style) output twice to two different addresses. Because private outputs and their spend proofs are only known to the parties in the payment chain (recipient, cosigners, and the payer, who is the attacker here), the attacker — as the payment counterparty/sender of the private chain — fully controls the timing and content of both conflicting chains and can broadcast them to two peers/devices simultaneously (e.g., "direct" `private_payment` justsaying plus hub-relayed `private_payments`, both eventually calling `validateAndSavePrivatePaymentChain`). This results in double-spend of value that should have been spendable only once — a concrete unauthorized-spending / double-spend outcome affecting node disagreement on validity for private assets.

### Likelihood Explanation
Exploitability requires only the ability to send two private-payment messages referencing the same source output through independent code paths (direct network message and hub/device forwarding, or two peers) before either finishes its own `BEGIN…COMMIT` cycle — well within reach of an unprivileged private-payment counterparty, no special network position or privileged access needed. The explicit "handle different chains in parallel" behavior in `handleSavedPrivatePayments` further increases the race window under normal operation, not just adversarial timing.

### Recommendation
Serialize private-chain validation the same way public units are serialized: acquire a `mutex.lock` keyed by the source output identity (`src_unit`+`src_message_index`+`src_output_index`) or by the spender's address before performing the double-spend `SELECT` in `checkForDoublespends`/`checkInputDoubleSpend`, and hold it until the corresponding `INSERT` into `inputs` commits, mirroring the `mutex.lock(arrAuthorAddresses, …)` pattern already used in `validation.js`. Alternatively, enforce the uniqueness check purely via the database's `UNIQUE` constraint on `inputs(src_unit, src_message_index, src_output_index, is_unique)` and treat an `INSERT` collision (not `INSERT IGNORE`) as an authoritative double-spend rejection rather than relying on a preceding `SELECT`.

### Proof of Concept
1. Attacker owns a private asset output `O` (from a completed private chain) known only to themself.
2. Attacker crafts two private payment chains, `ChainA` (spends `O` to address `X`) and `ChainB` (spends `O` to address `Y`), both referencing `O` as `src_unit/src_message_index/src_output_index`.
3. Attacker sends `ChainA` directly to peer/device 1 and, near-simultaneously, sends `ChainB` via a different path (e.g., through the hub as a `private_payments` message, or to a second device) so both invoke `privatePayment.validateAndSavePrivatePaymentChain` on separate DB connections before either commits.
4. Each connection independently runs the duplicate-check `SELECT` and `checkForDoublespends` `SELECT`, sees no conflicting row (because neither `INSERT` has committed yet), and proceeds to `INSERT` its own spend of `O`.
5. Both `ChainA` and `ChainB` are accepted as valid, resulting in `O` being spent twice to different recipients.
