### Title
Cross-organization signature verification bypass allows forging GitHub webhooks to trigger unauthorized syncs and deploys on another tenant's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, while every downstream `Webhooks::Handlers::Handler` resolves the target `Stack`/`Repository`/`Commit` to act on using **other, independent fields** of that same unverified body (`repository.full_name`, or a bare `sha`/`stack_id`). Because the field used to pick the verification key is never checked for consistency with the field used to select what gets written, a webhook signed with one organization's secret can be crafted to act on a different organization's stack.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it to pick the app whose secret verifies the signature: [4](#0-3) 

This supports Shipit's documented multi-tenant configuration, where each GitHub organization has its own `app_id`/`webhook_secret` entry under `secrets.github.<org>` [5](#0-4) , and `Shipit.github(organization:)` looks the app up by that key [6](#0-5) .

Once `verify_webhook_signature` succeeds, the controller unconditionally dispatches the full, unfiltered JSON body to every registered handler for the event: [7](#0-6) 

Handlers resolve their target using unrelated fields of the payload:
- The base `Handler#stacks` helper resolves via `repository.full_name`, not `repository.owner.login`: [8](#0-7) 
- `StatusHandler#process` resolves target `Commit`s globally by `sha` alone, with **no repository/organization scoping whatsoever**: [1](#0-0) 
- `PushHandler#process` similarly relies on `Handler#stacks` (i.e., `repository.full_name`) to select which stacks to sync: [9](#0-8) 

Because the verifying key is selected from `repository.owner.login`/`organization.login` while the acted-upon object is selected from `repository.full_name` (push, check_suite, pull_request handlers) or from a bare `sha` with no owner check at all (status handler), an attacker who legitimately controls one tenant organization's webhook secret (e.g., because they are the GitHub App admin for their own org, which Shipit is configured to host alongside other orgs/customers) can produce a validly-signed request whose signature matches their own organization but whose payload content (`repository.full_name`, or `sha`) targets a completely different organization's `Stack`/`Commit`. The binding broken is: **organization that authenticated (verified via HMAC) ≠ repository/commit that gets written**.

For `StatusHandler`, the mismatch is total: no organization or repository field is checked at all, only the raw commit `sha` — trivially exploitable to inject a forged `success` status on any commit that happens to exist in the shared Shipit instance, from any tenant with a valid webhook secret for any organization.

### Impact Explanation
This is a cross-tenant/cross-repository write: a webhook validly signed for org A can create a `Status` record on org B's commit via `StatusHandler`, and `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `Stack#trigger_continuous_delivery` → `Stack#trigger_deploy` can be reached automatically if the targeted stack has `continuous_deployment` enabled [2](#0-1) [3](#0-2) . This can trigger an **unauthorized deploy** of another organization's stack, satisfying the Critical bar ("unauthorized deploy"). It can equally be used to forge `push`/`check_suite` events against arbitrary stacks belonging to other organizations hosted on the same Shipit instance, causing cross-repository writes (spurious `GithubSyncJob`, fake commit/status records, check-run refreshes) outside the attacker's own tenant boundary.

### Likelihood Explanation
Requires only a valid webhook secret for *any one* organization configured on the multi-tenant Shipit install — which the report describes as a supported, documented deployment mode (`docs/setup.md`, "Using Multiple GitHub Applications"). No GitHub App private key, Shipit session, or `ApiClient` token is needed; the attacker directly POSTs to `/webhooks` with a body they control and a signature they can legitimately compute for their own org.

### Recommendation
Cross-validate that the organization/owner used to pick the verification key is identical to the owner embedded in the fields handlers use to resolve their target (e.g., derive `repository_owner` and `repository_name` from the same `repository.full_name` value, and have every handler verify `payload.dig('repository','full_name').split('/').first == verified_organization` before touching any `Stack`/`Commit`/`Repository`). For `StatusHandler` specifically, scope the `Commit` lookup by the repository resolved from the verified organization rather than a bare, globally-unscoped `sha`.

### Proof of Concept
1. Shipit is configured with two tenants, `orgA` (attacker-controlled webhook secret, legitimately obtained as that org's GitHub App admin) and `orgB` (victim, `continuous_deployment: true` on some stack), per the multi-org `secrets.yml` schema.
2. Attacker computes `X-Hub-Signature` using `orgA`'s known `webhook_secret` over a crafted JSON body:
```json
{
  "repository": {"full_name": "orgB/victim-repo", "owner": {"login": "orgA"}},
  "sha": "<sha of a real orgB commit that is pending CI>",
  "state": "success",
  "context": "ci/travis"
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and the computed signature.
4. `verify_signature` resolves `repository_owner` → `"orgA"`, loads `orgA`'s `GitHubApp`, and the HMAC matches → request passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (no owner check) and calls `create_status_from_github!`, injecting a forged `success` status on `orgB`'s commit, which can trigger `orgB`'s continuous deployment pipeline.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
