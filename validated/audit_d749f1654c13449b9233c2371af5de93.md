### Title
Asymmetric TTL renewal breaks the account/NFT both-or-live invariant and freezes the position — (File: contracts/controller/src/storage/account.rs)

### Summary
The kernel bug class is "both or neither must be initialized": partial availability of a paired resource causes failures when the missing half is dereferenced. In XOXNO Lending, every account is a pair of resources — the controller-side `AccountMeta`/`SupplyPositions`/`BorrowPositions` entries and the token entry in the external `position-nft` contract. `renew_user_account` renews only the four controller keys and explicitly does not renew the NFT, and `get_account`/`account_owner` require the NFT `owner_of` lookup to succeed (`try_account_owner` fails closed to `None` → `AccountNotFound`). When the NFT-side entry expires while the controller-side entries remain live, the paired invariant breaks: the account provably exists (`account_exists` only checks `AccountMeta`) yet every owner-dependent operation reverts, freezing the user's collateral and debt until the NFT entry is restored.

### Finding Description
- `renew_user_account` renews `AccountMeta`, `SupplyPositions`, `BorrowPositions`, and `Delegates` for the account but deliberately excludes the NFT (`contracts/controller/src/storage/account.rs:258-272`, comment "does not renew the NFT"). `renew_account` is the documented keeper path for keeping a user's account live.
- `get_account` → `try_get_account` requires both `try_get_account_meta` and `try_account_owner`; `try_account_owner` returns `None` on "unmintable ID, missing token, or failed lookup" and `account_owner` converts that to `AccountNotFound` (`account.rs:35-44, 146-162`).
- Meanwhile position maps default to an empty map when absent (`get_supply_positions`/`get_debt_positions`, lines 63-73), and `account_exists` checks only `AccountMeta` per `abi.md` — so "the account exists" and "the account is operable" are separately tracked facts that can diverge.
- Writes to the position maps via `write_side_map` perform no TTL renewal (lines 94-105), so controller-side liveness depends solely on reads and `renew_account`, neither of which touches the NFT contract's storage.

### Impact Explanation
Temporary freezing of user funds: a holder who supplies collateral through `supply` (or opens a leveraged position via `multiply`/`flash_position`) and later leaves the account inactive — renewing only through `renew_account`, which skips the NFT — ends up with live `AccountMeta` plus live positions but an expired NFT token entry. Every entrypoint that resolves the owner (`withdraw`, `repay`, `supply` top-up on the same account, `borrow`, delegate management, and the NFT's own `transfer`) panics with `AccountNotFound`. The collateral and any claimable yield are locked until the archived NFT entry is restored by a restore transaction. Because `update_account_threshold`-style keeper maintenance also goes through these paths, liquidations on the account may be blocked in the window as well, delaying bad-debt resolution. Impact magnitude depends on archival cadence, so Medium.

### Likelihood Explanation
An unprivileged user reaches this with no special call: call `supply(caller, payments, ...)` to open a position, then interact only via `renew_account` (or not at all) until the position-nft token entry's TTL lapses earlier than the controller's user-window TTL (`TTL_BUMP_USER`, renewed on every `get_user`/`set_user`, `storage/protocol.rs:190-202`). The asymmetry is structural — the two halves live in different contracts with different renewal triggers — so desynchronization requires only ordinary TTL drift, not a race. Any third party can also grief by keeping a victim's controller keys renewed via `renew_account` while the NFT entry is left to expire, forcibly freezing the victim's position.

### Recommendation
Make liveness all-or-nothing for the account pair. Either (a) extend `renew_user_account` to also renew the NFT token entry TTL via a cross-contract bump call to `position-nft`, or (b) treat an unresolvable NFT lookup for an existing `AccountMeta` as a distinct recoverable path (e.g., allow owner-independent `repay`/`liquidate`/restore flow) rather than collapsing it into `AccountNotFound`. At minimum, document that `renew_account` alone is insufficient to keep an account operable and that an NFT restore may be required.

### Proof of Concept
1. `supply(alice, [(hub1, USDC, 10_000e6)])` → controller writes `AccountMeta(id)` + `SupplyPositions(id)` with `TTL_BUMP_USER`; position-nft mints token `id` with its own TTL.
2. Keep the controller keys alive by periodically calling `renew_account(anyone, [id])` — this renews only the four controller keys (`account.rs:259-272`) and never touches the NFT contract.
3. Wait until the NFT token entry archives while `AccountMeta` is still live. `account_exists(id)` returns `true` (checks only `AccountMeta`), but `withdraw(alice, id, ...)` → `get_account` → `try_account_owner` → `nft_try_owner_of_call` fails → `AccountNotFound` panic.
4. Alice's collateral is frozen: withdraw, repay, supply, NFT transfer, and delegate ops all revert until the NFT entry is restored via an archival restore transaction.
