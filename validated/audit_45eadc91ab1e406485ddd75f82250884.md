### Title
Webhook signature verification keys off `repository.owner.login` while every event handler acts on the independently-attacker-supplied `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the request against using `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the **entire raw payload**, and every handler (`Handler#repository_name`) independently reads `payload.dig('repository', 'full_name')` to resolve the `Repository`/`Stack` to act on via `Repository.from_github_repo_name`. Nothing ties the value used for signature selection to the value used for the actual write/action, so a payload can validly authenticate as org A while acting on a repository belonging to org B.

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the webhook == the organization/repository the handler is permitted to act on*. Here that binding is broken because two different JSON fields from the same attacker-controlled payload are used for two different purposes:

- Signature/organization resolution: `app/controllers/shipit/webhooks_controller.rb` [1](#0-0) [2](#0-1) 

  `verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, request.raw_post)` — it only proves that *some* configured GitHub App's `webhook_secret` (keyed by `repository_owner`) matches the HMAC over the raw body. It does not otherwise constrain the content of the body.

- Action resolution: `app/models/shipit/webhooks/handlers/handler.rb` [3](#0-2) 

  Every handler independently computes `stacks`/`repository_name` from `payload.dig('repository', 'full_name')`, completely independent of the `repository.owner.login` value used earlier to pick the verifying secret.

Shipit explicitly supports hosting multiple GitHub organizations behind one instance (see the multi-org `secrets.yml` schema in `docs/setup.md` / `config/secrets.development.example.yml`), each with its own `webhook_secret`. A party who legitimately knows the `webhook_secret` for one configured organization (e.g. they administer the Shipit GitHub App installation for their own, less-trusted org on a shared instance) can craft an arbitrary JSON body where:
- `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` resolves to the secret they know, and `verify_webhook_signature` succeeds), and
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated repository/stack tracked by the same Shipit instance).

Because `repository_owner` and `repository_name` are read from independent, unvalidated JSON paths of the same attacker-supplied body, there is no requirement that they agree, and the code never re-derives `full_name` from `owner.login` + a `name` field or cross-checks them.

### Impact Explanation
Depending on which event/handler is targeted, this crosses a genuine trust boundary between organizations sharing one Shipit instance:
- `push` → `PushHandler` looks up stacks for `repository_name` and can enqueue `GithubSyncJob`/trigger continuous-delivery syncing for a victim org's stack the attacker does not control.
- `status`/`check_suite` → can inject fabricated CI statuses/check-runs against a victim stack's commits, which Shipit's merge queue and continuous-deployment logic treat as authoritative CI signal, potentially unblocking merges or deploys.
- `membership` → creates/updates `Team`/`User` records tied to the (misattributed) organization context.
- `pull_request/*` handlers similarly act on the victim repository's pull requests/merge queue.

This is a cross-organization/cross-repository write achievable by an attacker who only needs valid knowledge of a webhook secret for *any one* org configured on the shared instance — not the victim org's secret, and not any Shipit session, API token, or GitHub write access to the victim repository. This satisfies the "cross-repository writes" / "unauthorized deploy/merge" impact bar.

### Likelihood Explanation
The precondition — a Shipit instance configured with multiple GitHub organizations, each with its own webhook secret — is an explicitly documented and supported configuration (`docs/setup.md`, `config/secrets.development.example.yml`). Any tenant/org owner in that setup already legitimately possesses their own org's `webhook_secret` and can freely craft and POST arbitrary JSON to `/webhooks` with a correctly computed HMAC. No privileged access to the victim org, no session, and no additional secrets are required, making this readily reachable in the documented multi-org deployment model.

### Recommendation
After selecting the GitHub App/secret via `repository_owner`, validate that `repository.full_name` (and any other repository identifiers consumed by handlers) is actually owned by that same `repository_owner`/organization before dispatching to handlers — e.g. assert `payload.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` (and similarly for the `organization` sub-object fallback), rejecting mismatches with `422`.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (secret `S_attacker`) and `victim-org` (secret unknown to attacker), both tracked by the same instance (per the multi-org `secrets.yml` schema).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, body)>` using the secret they legitimately hold for `attacker-org`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and `verify_webhook_signature` succeeds because the signature was computed with that org's secret.
5. `Shipit::Webhooks.for_event('push').each { |h| h.call(params) }` runs `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` via `Handler#repository_name` [3](#0-2)  and acts on `victim-org`'s stacks/commits, despite the request never being authenticated by `victim-org`'s secret.
