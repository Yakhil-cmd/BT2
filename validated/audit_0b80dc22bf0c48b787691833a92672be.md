## Title
Multi-organization webhook signature check does not bind to the repository/commit acted on, allowing cross-organization status forgery and unauthorized deploy - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

## Summary
When Shipit is configured with multiple GitHub App organizations (multi-org `github:` config, e.g. `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using a payload field (`repository.owner.login` / `organization.login`), but the actual event handler that mutates data (`StatusHandler#process`) never checks that field again, and does not scope its write by repository at all. This breaks the equality: `organization that authenticated == repository/commit that is written`.

## Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to validate the signature with, based on attacker-controlled JSON fields in the very payload being verified: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a *per-organization* `webhook_secret` from the multi-org config: [3](#0-2) 

Once `verify_webhook_signature` succeeds against that organization's secret, `create` dispatches the parsed JSON body to the matching event handler: [4](#0-3) 

For the `status` event, `StatusHandler#process` looks up commits purely `by sha`, with **no scoping to the repository or organization at all**: [5](#0-4) 

The base `Handler` class does derive a `repository_name` from `payload.dig('repository', 'full_name')` for handlers that use it (e.g. `push`), but this is a *separate field* from `repository.owner.login`/`organization.login` used for signature-org selection, and `StatusHandler` doesn't use it at all: [6](#0-5) 

Consequently, the binding the system relies on is: `organization whose secret authenticated the request == organization/repository the write applies to`. Concretely, before/after an attacker's request:
- Before: signature valid only implies "sender knows OrgA's `webhook_secret`."
- After: a `Status` row is created/updated for *any* `Commit` in the entire Shipit install matching an attacker-chosen `sha`, regardless of which org/repo that commit belongs to.

An attacker who legitimately administers a GitHub organization/App that Shipit is configured to track (and therefore knows that organization's `webhook_secret` — not a Shipit credential, not `api_clients_secret`, not a GitHub App private key) can locally compute a valid `X-Hub-Signature` for an arbitrary JSON body and POST it directly to `/webhooks` with `X-Github-Event: status`, setting:
- `repository.owner.login` = "OrgA" (their own org, so the signature check passes against OrgA's secret)
- `sha` = the SHA of a commit belonging to a **different** tracked stack/organization ("OrgB"), obtainable from Shipit's own public commit/stack UI or API
- `state` = `"success"`, `context` = one of OrgB's stack's `ci.require` contexts

This creates a forged passing `Status` for OrgB's commit, satisfying `Stack#cached_deploy_spec.required_statuses` checks used by `Commit#deployable?`/`StatusChecker`, which is exactly the mechanism required-CI-status gating and continuous deployment rely on to decide whether a commit may be deployed.

## Impact Explanation
This lets an attacker who only controls one tracked GitHub organization (and its own webhook secret) forge required CI status for commits belonging to an entirely different tracked organization/repository, bypassing `ci.require` checks and enabling an unauthorized deploy on that other stack (via manual deploy trigger by any authorized human, or via `continuous_deployment`, which only checks the release/CI status, not who posted it). This matches the Critical impact category: "an unauthorized deploy." It also demonstrates the exact deployment-trust binding break called out in scope: "an organization that authenticated versus the repository that is written."

## Likelihood Explanation
Requires the attacker to control (and know the secret for) at least one GitHub organization that this specific Shipit instance is configured to track under the multi-org `github:` secrets schema, and to know a target commit SHA belonging to another tracked org (visible via Shipit's own UI). No Shipit session, API token, or GitHub App private key is needed — only the webhook secret of an org they legitimately administer, which is a comparatively low bar for an "unprivileged w.r.t. Shipit" attacker in a multi-tenant Shipit deployment.

## Recommendation
Bind the signature-validating organization to the object being mutated:
- In `StatusHandler#process` (and any other handler that doesn't already scope through `Handler#stacks`/`repository_name`), scope the `Commit` lookup by the stack/repository derived from `payload.dig('repository','full_name')`, and verify that repository's owning organization matches the organization whose `webhook_secret` validated the signature.
- More generally, `WebhooksController#verify_signature` should re-derive/re-check the organization from the same `repository.full_name`/`repository.owner.login` value that handlers use to select which record to write, ensuring the two never diverge.

## Proof of Concept
1. Configure Shipit with the multi-org schema (as in `test/dummy/config/secrets_double_github_app.yml`), tracking `OrgA/repoA` and `OrgB/repoB` as separate stacks, each with distinct `webhook_secret`s.
2. As the attacker, who administers `OrgA` and therefore knows `OrgA`'s `webhook_secret`, obtain a commit SHA for `OrgB/repoB` that is currently failing/missing a required CI status (visible on Shipit's public stack page).
3. Compute `sha256=`/`sha1=` HMAC (per `verify_webhook_signature` in `lib/shipit/github_app.rb`) over a crafted JSON body using `OrgA`'s known `webhook_secret`:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "<OrgB's required ci context>"
}
```
4. POST this body to `/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
5. `verify_signature` succeeds (uses `OrgA`'s secret, matching `repository.owner.login`). `StatusHandler#process` then finds the `Commit` in `OrgB/repoB` purely by SHA (no repository scoping) and creates a passing `Status` for it.
6. The forged status now satisfies `OrgB`'s required CI checks, enabling deploy/continuous-deployment eligibility for a commit the attacker never had access to.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
