This confirms it: `ERC20Matcher` matches **any** local `AccountKey20` location — i.e., any contract address deployed via `pallet-revive` is automatically treated as a valid fungible asset for XCM, with no allowlist/registration required [1](#0-0) . Combined with `ERC20Transactor`'s blind trust of the requested `amount` (rather than the actual balance delta) after a successful `transfer()` return, this is a demonstrable analog of the fee-on-transfer bug class.

### Title
Fee-on-transfer/deflationary ERC20 tokens break `ERC20Transactor` accounting and drain the shared checking account - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the standard `IERC20::transfer` interface on an arbitrary user-deployed `pallet-revive` contract and, upon a `true` return value, unconditionally credit/debit the **requested** `amount` into/out of the XCM `AssetsInHolding` register, without checking the actual balance delta of the `TransfersCheckingAccount` [2](#0-1) [3](#0-2) . Any local `AccountKey20` location is automatically matched as a valid fungible XCM asset with no governance/registration gate [1](#0-0) , so an attacker can permissionlessly deploy a fee-on-transfer/deflationary ERC20 contract via `pallet_revive::Pallet::instantiate` and reference it in `pallet-xcm`'s `execute`/`transfer_assets` extrinsics.

### Finding Description
`Erc20Credit` is an "unsafe" imbalance type explicitly documented as not enforcing runtime-level balance constraints, "where the actual balance constraints are enforced by the ERC20 smart contract itself" [4](#0-3) . This assumption is violated for a fee-on-transfer token: on `withdraw_asset_with_surplus`, the code calls `transfer(checking_account, amount)` from the user's mapped account and, if the call succeeds, credits `amount` (not the actual received delta) into holding [5](#0-4) . If the contract's `transfer` burns/deducts a fee internally while still returning `true`, `TransfersCheckingAccount`'s real on-chain token balance increases by less than `amount`, yet the XCM program proceeds as if the full `amount` is now backed.

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from `TransfersCheckingAccount` to the beneficiary, again trusting the boolean return without verifying the checking account's balance actually decreased by `amount` (or that it had enough of a real balance) [6](#0-5) . Since `TransfersCheckingAccount` is a single shared account (`ERC20TransfersCheckingAccount`) used for all ERC20 assets processed by this transactor, per-token accounting drift accumulates across independent users' XCM executions [7](#0-6) .

The entry point requires no privilege: any signed account can deploy an arbitrary Solidity contract through `pallet-revive` and then invoke `pallet_xcm::execute` / `transfer_assets` referencing that contract address as an `AccountKey20` asset — `ERC20Matcher` accepts it unconditionally [1](#0-0) .

### Impact Explanation
Because the shared checking account's real token balance for a given fee-on-transfer contract can be under-collateralized relative to what the XCM holding register believes it credited, later `deposit_asset_with_surplus` calls for that same token (potentially benefiting other honest users' legitimately-deposited full-value tokens accumulated in the same account) can succeed by drawing down real balance that does not correspond to the depositor's own contribution — a token-supply/accounting mismatch analogous to the Union Finance report's core issue (protocol treats nominal `amount` as if it were the actually-transferred amount). Once the checking account balance for that token is exhausted below outstanding credited amount, legitimate withdraw/deposit operations for that asset begin reverting (`FailedToTransactAsset`), a form of accounting corruption/fund-availability failure for a specific asset class.

This is inherent to any ERC20 whose `transfer` diverges from moving exactly `value`, and the code explicitly acknowledges it delegates balance enforcement to "the ERC20 smart contract itself," which is not true here since the transactor's own `amount` bookkeeping (not a query of the contract's `balanceOf`) is what's used.

### Likelihood Explanation
High feasibility for triggering the divergence (any user can deploy such a contract, no governance action required, and `pallet-revive` is production code guarded only by normal fees/weight limits used in tests such as `smart_contract_does_not_return_bool_fails`/`expensive_erc20_runs_out_of_gas` in `asset-hub-westend/tests/tests.rs`) [8](#0-7) . However, this is a newly introduced feature (`ERC20Transactor`, per `prdoc/stable2506/pr_7762.prdoc`) currently wired only into Asset Hub Westend's `AssetTransactors` tuple, and the practical value-extraction impact depends on other users also using that same fee-on-transfer contract through XCM to build up exploitable balance in the shared checking account, which the attacker does not fully control.

### Recommendation
Do not trust the boolean return of `transfer()` for `amount` bookkeeping. Query `balanceOf(checking_account)` before and after the internal `bare_call`, and use the observed delta as the actual credited/debited amount (mirroring the reported recommendation in the analog report), or reject deposit/withdraw when actual balance change != requested `amount`.

### Proof of Concept

This requires: (1) compiling and deploying a Solidity fee-on-transfer ERC20 fixture via `pallet_revive::Pallet::bare_instantiate` (test infrastructure exists, e.g. `compile_module_with_type` used in `asset-hub-westend/tests/tests.rs`), (2) executing a `pallet-xcm` XCM referencing that contract's `AccountKey20` location through `ERC20Transactor`, and (3) asserting the `TransfersCheckingAccount`'s real ERC20 `balanceOf` diverges from the amount recorded in `AssetsInHolding`/subsequent deposit accounting.
