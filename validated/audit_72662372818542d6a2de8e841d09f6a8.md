## Title
Permanent freezing of pool-creator fees if creator's token account becomes non-transferable (e.g. blacklisted) - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
Creator fees accrued in `PoolState.creator_fees_token_0`/`creator_fees_token_1` can only ever be paid out to the pool creator's own associated token account, which is derived and hard-coded via Anchor's `associated_token::authority = creator` constraint. There is no pull-based alternative or admin override. If the underlying mint enforces a transfer restriction on that destination address (e.g. a `Mint`-level freeze, or — for tokens like USDC — an issuer blacklist enforced by the token program/extension), every call to collect the fee will revert forever, permanently locking the accrued creator fees inside the pool vault.

### Finding Description
`collect_creator_fee` and `collect_creator_fee_permissionless` both push accumulated fees directly to `creator_token_0`/`creator_token_1`, which are ATAs whose owner is fixed to `pool_state.load()?.pool_creator`: [1](#0-0) 

The actual transfer is unconditionally attempted via `transfer_from_pool_vault_to_user`, and only after a successful transfer are the ledger fields zeroed: [2](#0-1) 

Because the recipient account is fixed to the creator's own authority (not attacker- or admin-controlled and not swappable to any other destination), if the token program rejects the transfer to that account — for example because a token like USDC has frozen/blacklisted that address, or the destination token account itself has been frozen (`TokenAccount.is_frozen`) — the CPI in `transfer_from_pool_vault_to_user` fails and the whole instruction reverts: [3](#0-2) 

Since both the creator-signed path (`collect_creator_fee`) and the permissionless path (`collect_creator_fee_permissionless`, callable by any `payer`) route to the exact same fixed destination, there is no way for anyone — including the pool creator — to redirect or otherwise retrieve the accrued fees. This differs from `withdraw`, where the LP token holder supplies their own arbitrary destination token account and can therefore always choose a working one; the creator-fee flow offers no such flexibility.

### Impact Explanation
This constitutes permanent freezing of pool-creator fee funds held in the vaults (`token_0_vault`/`token_1_vault`). The fee accounting (`creator_fees_token_0`/`creator_fees_token_1`) can never be reduced to zero and the corresponding tokens are stuck in the vault indefinitely once the creator's designated ATA becomes unable to receive transfers, with no admin recovery instruction to redirect these specific fees.

### Likelihood Explanation
Likelihood is realistic for any pool built on a mint whose issuer maintains an address blacklist (e.g. USDC-like tokens) or that supports the Token-2022 default-account-state/freeze functionality, since a creator's account can become frozen/blacklisted after pool creation for reasons unrelated to this protocol, and there is no mechanism in this codebase to work around it.

### Recommendation
Adopt a pull-based accounting model for creator fees: keep the fee balance in `PoolState` and let the creator specify (or later change) the destination token account at withdrawal time, or allow the pool owner/admin to redirect creator fees to an alternate address if the creator's account is unusable, analogous to how `withdraw.rs` lets the caller supply an arbitrary destination token account.

### Proof of Concept
1. Create a pool where `token_0`/`token_1` is a mint with issuer-controlled blacklisting (e.g. Token-2022 `default account state` set to frozen, or simulate USDC blacklist by freezing the creator's ATA).
2. Perform swaps so that `creator_fees_token_0`/`creator_fees_token_1` accrue non-zero balances (see accrual logic referenced in `swap_base_output.rs`/`swap_base_input.rs`).
3. Freeze/blacklist the pool creator's associated token account for that mint.
4. Call `collect_creator_fee` (signed by creator) or `collect_creator_fee_permissionless` (any payer) — the CPI in `transfer_from_pool_vault_to_user` fails because the destination account cannot receive tokens, so the instruction reverts and `creator_fees_token_0/1` remain stuck and unrecoverable, since no alternate destination can ever be supplied.

```rust
pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```
