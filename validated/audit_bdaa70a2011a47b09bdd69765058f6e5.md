### Title
Stale `is_spent=1` flag not cleared when a spending unit is propagated to `final-bad` without archiving, causing permanent fund freezing / balance miscalculation - (File: `main_chain.js`, `archiving.js`, `writer.js`)

### Summary
Analogous to CVE-2017-10920 (Xen grant-table mishandling a mapping when only a partial/asymmetric unmapping is performed, causing count mismanagement), `ocore` sets `outputs.is_spent=1` ("map") whenever any unit references an output as a `transfer` input [1](#0-0) , but only ever resets it back to `0` ("unmap") through one narrow path: full archiving/pruning of the spending unit's content [2](#0-1) . If a spending unit is instead invalidated in place (its `sequence` becomes `final-bad` while it remains fully in the DB, e.g. via non-serial resolution or emergency/hard-fork corrections) without being archived, there is no code path that clears `is_spent` back to `0`.

### Finding Description
`writer.js`'s `addInlinePaymentQueries` unconditionally does `UPDATE outputs SET is_spent=1 ...` for every unit that spends an output as an input, at initial acceptance time, before final sequence/stability is known [1](#0-0) . The only mechanism that reverses this flag is `generateQueriesToUnspendTransferOutputsSpentInArchivedUnit`, which runs solely when a specific unit is archived (its content is removed from local storage) and no other unit still references that output [2](#0-1) . There is no equivalent "unmap" step tied to a unit's sequence flipping to `final-bad` while the unit stays in the database.

The project's own code documents this exact class of bug: `main_chain.js`'s `countVotes` contains a comment explicitly describing "outputs whose only spending unit was propagated to final-bad (leaving `is_spent=1` in the DB while no good unit claims the output), which the previous two-query approach... silently undercounted" [3](#0-2) . The fix applied there switches to a `NOT EXISTS`-based good/stable spender check instead of trusting `is_spent` [4](#0-3) . The companion diagnostic tool `tools/compare_vote_balances.js` confirms and quantifies the discrepancy between the old `is_spent=0`-based balance calculation and the corrected `NOT EXISTS` approach, labeling the affected outputs "zombie-spent outputs" [5](#0-4) [6](#0-5) .

Critically, the fix was applied only to the vote-counting balance query. Every other consumer of `is_spent=0` as "is this output spendable" still uses the naive, vulnerable check, including coin-selection/composition code (`composer.js`), wallet balance code (`wallet.js`), AA fund/balance handling (`aa_composer.js`), and private indivisible-asset spend tracking (`indivisible_asset.js`), all of which query `is_spent=0` directly.

### Impact Explanation
Once an output's only spender unit becomes `final-bad` without being archived, the output is permanently stuck as `is_spent=1` even though no valid unit actually consumes it. Any code path that treats `is_spent=0` as the source of truth for "spendable output" (payment composition in `composer.js`, wallet balance display/spending in `wallet.js`, AA balance/fund accounting in `aa_composer.js`, private asset transfer tracking in `indivisible_asset.js`) will incorrectly treat the funds as spent, permanently freezing them from their legitimate owner — a fund-freezing/fund-loss condition. Conversely, code relying on the flag for stability/vote or balance bookkeeping (as fixed in `main_chain.js`) previously undercounted balances, i.e., nodes could disagree on the true balance/vote weight of an address depending on whether they use the corrected query or the legacy `is_spent`-based one, which is a node-disagreement-on-validity/stability class impact.

### Likelihood Explanation
Final-bad outcomes for previously-accepted units are a normal part of DAG consensus (double-spend races, non-serial resolution, and periodic emergency/hard-fork corrections referenced in `main_chain.js`'s `is_emergency` handling) [7](#0-6) , so the underlying condition (a unit's sequence changing to `final-bad` while it is not archived) is not a rare or attacker-exclusive event — it can arise from ordinary network activity, and the codebase's own diagnostic tooling was built specifically because this discrepancy was observed in practice.

### Recommendation
Add a general-purpose reconciliation step, independent of unit archiving, that clears `outputs.is_spent` whenever the last remaining spender of that output transitions to `sequence='final-bad'` (mirroring the logic already implemented for archived units in `archiving.js`). Alternatively, replace all `is_spent=0`-based spendability checks (`composer.js`, `wallet.js`, `aa_composer.js`, `indivisible_asset.js`) with the `NOT EXISTS`-based good/stable-spender check already adopted in `main_chain.js`'s `countVotes`.

### Proof of Concept
1. Two units, A and B, both include a `transfer` input referencing the same source output O (accepted as competing non-serial claims per `checkForDoublespends`/`validatePaymentInputsAndOutputs`) [8](#0-7) .
2. On acceptance, `writer.js` sets `outputs.is_spent=1` for O when either A or B is written [1](#0-0) .
3. Through normal DAG stabilization (or an emergency vote-count correction path), both spending claims for O end up with `sequence='final-bad'`, but neither unit is archived/pruned.
4. `outputs.is_spent` remains `1` for O indefinitely — confirmed by the exact scenario described and reproduced by `tools/compare_vote_balances.js`'s `balancesOldWay` vs `balancesNewWay` comparison, which flags such "zombie-spent" outputs [9](#0-8) .
5. Any component still trusting `is_spent=0` (wallet balance, AA fund calc, coin composer) will now permanently omit O as spendable, freezing the legitimate owner's funds.

function generateQueriesToUnspendTransferOutputsSpentInArchivedUnit(conn, unit, arrQueries, cb){
	conn.query(
		"SELECT src_unit, src_message_index, src_output_index \n\
		FROM inputs \n\
		WHERE inputs.unit=? \n\
			AND inputs.type='transfer' \n\
			AND NOT EXISTS ( \n\
				SELECT 1 FROM inputs AS alt_inputs \n\
				WHERE inputs.src_unit=alt_inputs.src_unit \n\
					AND inputs.src_message_index=alt_inputs.src_message_index \n\
					AND inputs.src_output_index=alt_inputs.src_output_index \n\
					AND alt_inputs.type='transfer' \n\
					AND inputs.unit!=alt_inputs.unit \n\
			)",
		[unit],
		function(rows){
			rows.forEach(function(row){

					[row.src_unit, row.src_message_index, row.src_output_index]

			});

async function balancesOldWay(addresses) {
	const strAddresses = addresses.map(db.escape).join(', ');

	const bal_rows = await db.query(`
		SELECT address, SUM(amount) AS balance
		FROM outputs
		LEFT JOIN units USING(unit)
		WHERE address IN(${strAddresses}) AND is_spent=0 AND asset IS NULL AND is_stable=1 AND sequence='good'
		GROUP BY address`);

	const balances = {};
	for (const { address, balance } of bal_rows)
		balances[address] = balance || 0;

	const spent_rows = await db.query(`
		SELECT inputs.address, SUM(outputs.amount) AS spent_balance
		FROM units
		CROSS JOIN inputs USING(unit)
		CROSS JOIN outputs ON src_unit=outputs.unit AND src_message_index=outputs.message_index AND src_output_index=outputs.output_index
		CROSS JOIN units AS output_units ON outputs.unit=output_units.unit
		WHERE units.is_stable=0 AND +units.sequence='good'
			AND +output_units.is_stable=1 AND +output_units.sequence='good'
			AND inputs.address IN(${strAddresses}) AND type='transfer' AND inputs.asset IS NULL
		GROUP BY inputs.address`);

	for (const { address, spent_balance } of spent_rows) {
		if (balances[address])
			balances[address] += spent_balance;
		else
			balances[address] = spent_balance;
	}

	return balances;
}

async function balancesNewWay(addresses) {
	const strAddresses = addresses.map(db.escape).join(', ');

	const rows = await db.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);

	const balances = {};
	for (const { address, balance } of rows)
		balances[address] = balance || 0;

	return balances;
}
