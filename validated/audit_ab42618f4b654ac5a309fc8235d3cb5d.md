### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits globally by `sha` with no repository/stack scoping, while the only authorization performed anywhere in the webhook pipeline is `WebhooksController#verify_signature`'s per-organization HMAC check on the payload's declared `repository.owner.login`. Because HMAC-valid-for-org-A is treated as authorization to write a `Status` for any commit row matching a given SHA regardless of which org/stack owns it, an attacker who controls a legitimate (but unrelated) GitHub org/repo already configured in the shared Shipit instance can forge status events for another tenant's commits.

### Finding Description
The claimed binding is: `HMAC valid for org X's webhook_secret` (checked in `WebhooksController#verify_signature`) `== authorized to write status rows for org X's own repositories only`.

Code path:
1. `WebhooksController#create` parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
2. `verify_signature` computes `Shipit.github(organization: repository_owner)` from the payload's own `repository.owner.login`/`organization.login` field and checks the HMAC against that org's `webhook_secret` [2](#0-1) , [3](#0-2) . This proves only "the sender knows org X's secret"; it never re-checks that the `sha`/commit referenced in the body actually belongs to a repository owned by org X.
3. `Handler.call` simply does `new(params).process` [4](#0-3) . `Handler` defines a `stacks`/`repository_name` helper scoped from `payload.dig('repository', 'full_name')` [5](#0-4) , proving the framework has the *means* to scope by repository — but `StatusHandler` never calls it.
4. `StatusHandler#process` instead runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5)  — a global, cross-stack, cross-org lookup with no `repository_name`/`stacks` filter anywhere in the call chain.
5. `create_status_from_github!` writes a `Status` row, fires `Hook.emit(:commit_status/:deployable_status, ...)`, and can schedule merges/continuous delivery [7](#0-6) , [8](#0-7) .

Exploit flow: an attacker who owns/controls a GitHub org/repo that is legitimately configured in the multi-tenant Shipit instance (has its own valid `webhook_secret`) uses GitHub's Statuses API (which does not verify the SHA exists in the calling repo) to set a commit status on an arbitrary 40-hex SHA that they know belongs to a different tenant's tracked commit. GitHub delivers a genuinely signed `status` webhook (signed with the attacker's own org secret) to Shipit. `verify_signature` passes because the signature matches the attacker's own org config. `StatusHandler#process` then matches that SHA against `Commit.where(sha: ...)` across the entire installation and writes a status to the victim org's commit/stack, potentially flipping it to `success` and triggering `stack.schedule_merges`/continuous delivery for a stack the attacker's org has no relationship to.

None of the mitigations listed in the Validate section apply here: `verify_signature` checks org-level HMAC only, not repository ownership of the target row; there is no `require_permission!`, `current_user`, `session[:user_id]`, or `ApiClient` scope anywhere in `Handler#initialize`/`Handler.call`/`StatusHandler#process`; and the `stacks`/`repository_name` scoping helper that exists on `Handler` is simply unused by `StatusHandler`.

### Impact Explanation
An attacker with a legitimately-configured (but otherwise unprivileged/unrelated) org in a shared/multi-tenant Shipit installation can write arbitrary `Status` rows against any other tenant's commits by SHA, without ever being a maintainer, team member, or Shipit user of the victim's repository. This can flip a victim commit to `success`, unblock CI gating, and trigger `stack.schedule_merges!`/continuous deployment — an unauthorized deploy path — for a stack the attacker does not own. This is repeatable for any known commit SHA and matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge".

### Likelihood Explanation
Preconditions: the Shipit installation must be configured with per-organization GitHub App configs (multiple `github.<org>` entries in secrets, each with its own `webhook_secret`), and the attacker must control at least one such configured org (a realistic scenario for shared Shipit deployments hosting multiple tenants). The attacker needs to know a target commit SHA belonging to another tenant's tracked stack (often knowable via public GitHub activity, PR pages, etc.). No Shipit session, API token, or GitHub credentials of the victim are required — only a legitimate GitHub Statuses API call against the attacker's own repo, which GitHub does not validate against actual commit ancestry. This is a low-cost, fully repeatable attack against arbitrary SHAs.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the webhook's own repository, e.g. filter `Commit.where(sha: params.sha)` by `stacks` (using the existing `Handler#stacks`/`repository_name` helper) before creating a status, so a status payload can only affect commits belonging to stacks whose repository matches the payload's `repository.full_name`.

```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "StatusHandler#process has no repository/stacks scoping in its call chain" do
          # Binding under test: HMAC-verified-org == HMAC-verified-org's-own-repositories-only
          source_methods = Handler.instance_methods(false) + StatusHandler.instance_methods(false)
          refute_includes source_methods, :stacks # StatusHandler never calls Handler#stacks
          method_source = StatusHandler.instance_method(:process).source_location
          body = File.read(method_source[0])
          refute_match(/stacks|repository_name/, body.split("def process").last.split("end").first)
        end

        test "a status payload from org A writes a status onto org B's commit matching the sha" do
          victim_commit = shipit_commits(:first) # belongs to stack owned by org "shopify"
          attacker_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'attacker/ci',
            'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.call(attacker_payload)
          end

          assert_equal 'success', victim_commit.reload.state
        end
      end
    end
  end
end
```
