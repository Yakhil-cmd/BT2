### Title
Independent per-recipient rounding in headers-commission distribution can inflate or destroy bytes supply - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a parent unit's `headers_commission` among multiple `earned_headers_commission_recipients` by independently rounding each recipient's share with `Math.round(full_amount * share / 100.0)` (both in the MySQL `ROUND(...)` SQL expression and in the JS/SQLite in-memory path), instead of computing shares so they sum exactly back to `full_amount`.

### Finding Description
When a unit has multiple authors (or explicitly redistributes its earned commission via `earned_headers_commission_recipients`), `validateHeadersCommissionRecipients` only enforces that the recipients' `earned_headers_commission_share` percentages sum to exactly 100 [1](#0-0) . It never constrains how the actual byte amount is later split.

The split itself happens deterministically for all full nodes in `headers_commission.js`. For the MySQL path, each recipient's row is computed as `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)` [2](#0-1) . For the SQLite/in-memory path, the same computation is done per recipient as `Math.round(full_amount * share / 100.0)` [3](#0-2)  and again in the "profit_distribution_rows" reconciliation path [4](#0-3) , with the code even acknowledging "note that we round _before_ summing up header commissions won from several parent units" [5](#0-4) .

Because each recipient's share is rounded independently (standard round-half-up, not round-down truncation with remainder distribution), the sum `Σ round(full_amount * share_i / 100)` over all recipients is not guaranteed to equal `full_amount`. For example, with `full_amount = 100` split three ways with shares `{34, 33, 33}` all giving 34/33/33 = 100 (fine), but asymmetric splits or larger recipient counts with fractional halves (e.g. shares that produce `x.5` amounts for multiple addresses) can push the total either above or below `full_amount`, since `Math.round` always rounds `.5` up regardless of sign of the accumulated error, and there is no complementary "give the remainder to the largest share" or "round down and assign leftover to one recipient" logic anywhere in this pipeline.

The distributed amounts are then summed into `headers_commission_outputs` (`SUM(amount) ... GROUP BY main_chain_index, address`) [6](#0-5) , and these output rows are exactly what `mc_outputs.calcEarnings`/`readNextSpendableMcIndex` allow addresses to later claim as `headers_commission`-type inputs in a payment message, checked byte-for-byte in `validatePaymentInputsAndOutputs` [7](#0-6) . Because all full nodes run the identical deterministic rounding algorithm, they will all agree on the (potentially inflated or deflated) total — so this does not cause a fork/consensus disagreement, but it does mean the sum of headers-commission outputs credited to recipients is not strictly bounded by the commission actually collected from the paying parent unit.

### Impact Explanation
An attacker who controls the split of `earned_headers_commission_recipients` (e.g. a multi-authored unit, or explicitly setting the recipient list via `params.earned_headers_commission_recipients` in the composer [8](#0-7) ) can choose the number of recipients and share percentages to make the sum of independently-rounded amounts exceed the actual `full_amount` by up to `~0.5 * (number_of_recipients - 1)` bytes per distribution event. Repeated systematically (many units, many recipients, many stabilized main-chain indices) this creates new bytes credited to the attacker's own addresses that were never actually paid as commission by the payer unit — a low-magnitude but real, repeatable supply-inflation vector. It could also work in the deflationary direction, silently burning small amounts of commission that should have gone to legitimate recipients.

### Likelihood Explanation
Exploitability requires only posting a payment unit with multiple authors and a crafted `earned_headers_commission_recipients` list, which is a completely permissionless, unprivileged action available to any unit poster. The per-event gain is tiny (fractions of a byte, bounded by `0.5*(n-1)`), so this is a low-magnitude griefing/inflation bug rather than a large fund-theft bug, but it is a genuine, provable supply-accounting defect reachable from ordinary unit posting.

### Recommendation
Do not round each recipient's share independently. Compute amounts so they sum exactly to `full_amount`: e.g., round down (`Math.floor`) for all-but-the-last recipient and assign the remainder (`full_amount - sum_of_prior_amounts`) to the last recipient (in a canonical, deterministic order such as sorted by address, which is already enforced), or use a largest-remainder method. Apply this consistently to both the MySQL SQL query and the SQLite/in-memory JS computation in `headers_commission.js`.

### Proof of Concept
1. Compose and post a 2-author unit `U` (address `A1 < A2`) with `earned_headers_commission_recipients = [{address: A1, earned_headers_commission_share: 1}, {address: A2, earned_headers_commission_share: 99}]` — validated fine since shares sum to 100 [9](#0-8) .
2. Suppose `U` wins a parent's `headers_commission` of `full_amount = 150` bytes (choosable/observable by controlling unit size and the DAG structure that makes `U` the hc winner via `getWinnerInfo`) [10](#0-9) .
3. `calcHeadersCommissions` computes `amount_A1 = Math.round(150*1/100) = Math.round(1.5) = 2` and `amount_A2 = Math.round(150*99/100) = Math.round(148.5) = 149`, for a total of `151` credited bytes versus `150` actually paid by the parent unit [3](#0-2) .
4. Both `A1` and `A2` (controlled by the same attacker) can later spend these amounts as `headers_commission`-type inputs, which are validated only against the stored `headers_commission_outputs`/`calcEarnings` totals [11](#0-10) , realizing 1 extra byte of unbacked supply from this single distribution event. Repeating this with more recipients and units at scale accumulates unbacked byte issuance over time.
