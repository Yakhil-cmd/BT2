### Title
Deterministic `CreateAccountWithSeed` Addresses Can Be Pre-Funded by Unprivileged Users to Permanently Block Account Creation - (File: `programs/system/src/system_processor.rs`)

### Summary
The System program derives account addresses deterministically via `Pubkey::create_with_seed(base, seed, owner)` for `CreateAccount`/`CreateAccountWithSeed`, and any unprivileged actor can pre-fund that publicly-computable address with as little as 1 lamport before the legitimate creator's transaction lands, permanently blocking that specific address from ever being initialized as the intended account (stake account, nonce account, etc.), mirroring the front-run risk described in the external report where a deterministic, off-chain-computable `objectId` can be squatted by any actor before the legitimate owner registers it.

### Finding Description
`create_account()` in `programs/system/src/system_processor.rs` bails with `SystemError::AccountAlreadyInUse` whenever the target `to` account already has `lamports > 0`, regardless of who funded it: [1](#0-0) 

This check applies to both `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed`, both of which route through the same `create_account()` function: [2](#0-1) 

For `CreateAccountWithSeed`, the target address is fully deterministic and publicly computable from `(base, seed, owner)` via `Address::create`, which just re-derives and compares the address: [3](#0-2) 

Since the System program's plain `Transfer` instruction allows *anyone* to send lamports to *any* pubkey without any signature from the receiver, an attacker who can predict `(base, seed, owner)` can pre-transfer 1 lamport to the derived address before the rightful owner's `CreateAccountWithSeed` transaction is confirmed. Once that lamport balance is non-zero, the legitimate `create_account()` call permanently fails with `AccountAlreadyInUse`, and the address can never be initialized as the intended account type because the address itself is immutably tied to `(base, seed, owner)` — exactly the "cannot be removed once added" permanence issue the external report describes for `objectId`.

This is a realistic threat because `base` and `seed` are frequently predictable/public in practice: e.g., `stake-accounts/src/stake_accounts.rs::derive_stake_account_address` derives addresses from a known `base_pubkey` and a simple sequential index string: [4](#0-3) 

and CLI stake-account creation with `--seed` follows the identical pattern using a known base keypair pubkey and a caller-supplied seed string: [5](#0-4) 

An observer watching mempool/RPC or simply knowing the stake-pool/validator's base pubkey and its sequential seed convention can front-run the next expected index before it's created.

### Impact Explanation
A successful front-run permanently denies use of that specific derived address for its intended purpose (a "permanently frozen"/unusable account address), forcing the legitimate operator to detect the failure and either retry with a different seed/index or abandon that slot in a sequence. For automated tooling that assumes deterministic, sequential seed derivation (e.g., stake-account batch creation), this can disrupt account provisioning workflows and requires off-chain remediation, aligning with the "permanently frozen accounts" impact bucket.

### Likelihood Explanation
Likelihood is bounded by how predictable `(base, seed, owner)` is to an external observer before the `CreateAccount(WithSeed)` transaction confirms. For any workflow using well-known base pubkeys and simple/sequential seeds (as in the stake-accounts tooling shown above), this is straightforward to front-run with a single low-cost `Transfer` instruction, requiring no special privileges — any unprivileged network participant can do this.

### Recommendation
This is inherent to the System program's `create_with_seed` design (funding accounts before creation is a standard Solana pattern such as rent pre-funding), and is a known, largely unavoidable trade-off; mitigation is primarily off-chain: operators using `CreateAccountWithSeed` for provisioning should avoid predictable `base`/`seed` combinations for security-sensitive or high-value account slots, or use fresh unpredictable base keypairs/seeds rather than deterministic/sequential ones, and add retry/detection logic to fall back to a new seed on `AccountAlreadyInUse`.

### Proof of Concept
1. Attacker learns/observes a target's intended `base` pubkey and `seed` (e.g., a stake-pool's known base key and next sequential index, per `derive_stake_account_address`).
2. Attacker computes `to = Pubkey::create_with_seed(&base, &seed, &stake::program::id())` and submits a plain `SystemInstruction::Transfer` of 1 lamport to `to`.
3. When the legitimate operator submits `CreateAccountWithSeed` targeting the same `to`, `create_account()` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, permanently preventing that derived address from being initialized as intended. [1](#0-0)

    fn create(
        address: &Pubkey,
        with_seed: Option<(&Pubkey, &str, &Pubkey)>,
        invoke_context: &InvokeContext,
    ) -> Result<Self, InstructionError> {
        let base = if let Some((base, seed, owner)) = with_seed {
            // The conversion from `PubkeyError` to `InstructionError` through
            // num-traits is incorrect, but it's the existing behavior.
            let address_with_seed =
                Pubkey::create_with_seed(base, seed, owner).map_err(|e| e as u64)?;
            // re-derive the address, must match the supplied address
            if *address != address_with_seed {
                ic_msg!(
                    invoke_context,
                    "Create: address {} does not match derived address {}",
                    address,
                    address_with_seed
                );
                return Err(SystemError::AddressWithSeedMismatch.into());
            }
            Some(*base)
        } else {
            None
        };

        Ok(Self {
            address: *address,
            base,
        })
    }
