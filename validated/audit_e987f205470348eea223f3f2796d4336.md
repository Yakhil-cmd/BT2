### Title
Webhook signature verification is keyed off an unverified `repository.owner.login` field that can diverge from the `repository.full_name` acted upon by event handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), a field taken from the *unauthenticated* request body itself. The actual event handlers, however, resolve the target `Stack`/`Repository` from a different field of the same untrusted body: `payload.dig('repository', 'full_name')`. Because `webhook_secret` is documented and implemented as optional per organization, and because nothing enforces that the `repository.owner.login` used for signature-selection matches the owner encoded in `repository.full_name`, these two fields are never bound together by the signature check.

### Finding Description [1](#0-0) 

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . `verify_webhook_signature` in `GitHubApp` short-circuits to `true` whenever the organization's `webhook_secret` is unset: `return true unless webhook_secret` [3](#0-2) . This is a first-class, documented configuration option ("Webhook secret (optional)") [4](#0-3) , and multi-organization Shipit deployments (see the `secrets_double_github_app.yml` fixture with `OrgOne`/`OrgTwo`) are an explicitly supported topology [5](#0-4) .

Once `create` proceeds, it dispatches the *entire unverified JSON body* to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) . `Handler#repository_name` (used by every repository-scoped handler, e.g. `PushHandler`) reads `payload.dig('repository', 'full_name')` — a *different* field than the one used to pick the verification secret: [7](#0-6) . `PushHandler#process` then loads stacks for that repository and calls `stack.sync_github(expected_head_sha: params.after)` on any matching, non-archived stack [8](#0-7) , which enqueues `GithubSyncJob` to fetch and append GitHub commits and eventually re-cache the deploy spec [9](#0-8) .

Because signature selection (`repository.owner.login`) and target resolution (`repository.full_name`) are two independently-controlled fields inside the same forged JSON body, an attacker can set `repository.owner.login` to any organization configured in Shipit **without** a `webhook_secret` (bypassing the HMAC check entirely, since it returns `true` unconditionally for that org) while setting `repository.full_name` to point at a Stack belonging to a **different**, secured organization. The equality the code implicitly (and incorrectly) assumes is:
```
verified_organization(repository.owner.login) == acted_upon_repository_owner(repository.full_name)
```
This equality is never checked, and it is exactly the "organization that authenticated versus the repository that is written" binding named in scope.

### Impact Explanation
This lets an unauthenticated network attacker forge `push`, `status`, `check_suite`, or `pull_request` webhook events for a completely arbitrary tracked repository/stack, as long as the Shipit instance has at least one configured organization without a `webhook_secret` (an explicitly supported/optional configuration). Concretely for `push`: the attacker can force `GithubSyncJob` to run for a victim stack with an attacker-chosen `expected_head_sha`, causing Shipit to fetch and append arbitrary upstream commits into the stack's commit history and re-cache its deploy spec ahead of schedule — undermining the integrity of the deployment pipeline's view of the repository state, which can influence subsequent CI-status handling, merge-queue behavior, and deploy candidate selection. `status` events (`StatusHandler`) allow forging arbitrary CI status records against real commits, which can be used to make otherwise-failing/pending commits appear to pass required checks (`Commit#create_status_from_github!`), directly enabling an unauthorized ship of a bad commit through Shipit's status-gated deploy/merge flow.

### Likelihood Explanation
Requires no credentials, no `ApiClient` token, and no legitimate GitHub webhook secret — only that the target Shipit instance manages at least one organization configured without `webhook_secret` (a documented, optional field) alongside the organization/repository the attacker wants to target. This is a realistic and common deployment shape for organizations onboarding a new team or running a small internal org without bothering to set a webhook secret, while sharing the same Shipit instance with production-critical stacks.

### Recommendation
Bind the verified organization to the acted-upon repository as part of the trust boundary, not as two independently-read fields of the unauthenticated payload:
- After choosing `github_app` via `repository_owner`, require that `payload.dig('repository', 'full_name')` (when present) starts with `"#{repository_owner}/"`; reject (422) on mismatch.
- Do not allow `verify_webhook_signature` to return `true` implicitly whenever `webhook_secret` is blank for events that carry a `repository`/`organization` payload capable of referencing other tenants; instead resolve the repository's actual owner org from the datastore (`Repository.from_github_repo_name`) and verify against that organization's key, or enforce that every organization must configure a webhook secret before webhooks are accepted.

### Proof of Concept
Given a Shipit deployment with two configured orgs, `attacker-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`, tracks stack `victim-org/victim-repo`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `repository_owner` resolves to `"attacker-org"` [2](#0-1) .
- `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)` returns `true` because `attacker-org` has no `webhook_secret` [3](#0-2) .
- `PushHandler` resolves the target repository from `full_name` = `"victim-org/victim-repo"` [7](#0-6)  and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [8](#0-7) , without ever possessing `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
