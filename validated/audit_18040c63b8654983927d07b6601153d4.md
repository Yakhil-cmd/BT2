## Finding

### Title
Asset issuer can unilaterally change `spender_attested` attestors post-issuance, freezing existing holders' funds - (File: `writer.js`, `divisible_asset.js`, `aa_validation.js`)

### Summary
Ocore lets an asset definer create a `spender_attested` asset whose spendability by any wallet is conditioned on that wallet being in the current attestors' attested list, and separately lets the definer post an `asset_attestors` message at any later time to change that list, with no timelock, no notice period, and no opt-out for existing holders.

### Finding Description
When an asset is defined with `spender_attested: true`, spending its outputs requires the payer to be attested by one of the asset's attestors, as recorded via the `attestors` field at issuance [1](#0-0) . The set of attestors is not fixed for the lifetime of the asset — it can be changed later through a separate `asset_attestors` message, validated in the codebase as its own message type: [2](#0-1) . This message only requires a valid `asset` reference and a new `attestors` array; it carries no cooldown, no grace period, and no mechanism for existing coin/share holders to react before the change takes effect.

Once the attestors are updated, wallets attempting to spend previously-issued, previously-spendable outputs are re-evaluated against the *current* attestor list, not the list that existed when they acquired the asset: [3](#0-2)  shows that any transfer composition for a `spender_attested` asset checks `objAsset.arrAttestedAddresses.length === 0` and fails with `"none of the authors is attested"` if the payer isn't attested under the currently active set.

This is structurally identical to the reported "cred creator" bug class: a single privileged party (here, the asset issuer/definer, analogous to the cred creator) can unilaterally rewrite a critical parameter (the attestor whitelist, analogous to the fee percentage) that governs whether existing token/share holders can access their own funds, with the change taking effect immediately and without any mechanism (timelock, withdrawal window) that lets holders exit first.

### Impact Explanation
A malicious or compromised asset definer can:
1. Issue a `spender_attested` asset with an attestor set that looks reasonable (e.g., a KYC provider), inducing users to acquire and hold the asset.
2. After users have accumulated meaningful balances, post an `asset_attestors` message that swaps in an attestor who will never attest anyone (or removes all attestors), or keep the definer address itself as sole "attestor" who then refuses to attest holders.
3. Immediately, and for all future transfers, existing holders find their previously-liquid balances non-transferable — `"none of the authors is attested"` — because attestation status is checked against the up-to-date attestor list, not a snapshot taken at issuance/acquisition time.

This constitutes a permanent freeze of user funds under the exact control of a single unprivileged-relative-to-users party who only needs to author a single, cheap, always-permitted message type. It is not a resource-exhaustion or purely theoretical issue: it results in concrete, unauthorized freezing of already-issued asset balances belonging to third parties, matching the "AA/asset fund loss or freezing" impact category.

### Likelihood Explanation
Likelihood is directly comparable to the original report's rating (Medium): the attack requires only actions the issuer is explicitly authorized to perform (defining the asset, later posting `asset_attestors`), no special network position, no cryptographic break, and no cooperation from other parties. The barrier is entirely social/reputational — a malicious issuer choosing to exploit trusting holders — which is the same mitigating/aggravating factor discussed in the source report for the cred fee-update bug.

### Recommendation
- Snapshot the attestor set (or at least grandfather already-acquired balances) at the time an output was created/acquired, rather than re-checking against the live attestor list at spend time; or
- Require a timelock/delay (e.g., N main-chain indices) between posting `asset_attestors` and the change taking effect, during which existing holders can exit/transfer under the old attestor rules; or
- Emit a clear, queryable "pending attestor change" state so wallets can detect and react to upcoming changes before they become effective.

### Proof of Concept
1. Definer D issues asset A with `spender_attested: true`, `attestors: [X]`, where X is a reputable attestor. [1](#0-0) 
2. Users acquire units of A and get attested by X, so `arrAttestedAddresses` is non-empty and they can freely transfer A.
3. D posts an `asset_attestors` message for asset A with `attestors: [D]` (or any attestor who will not attest holders). This message passes validation solely by referencing the correct `asset` and providing a valid attestors array. [2](#0-1) 
4. Any holder attempting to compose a transfer of A now fails composition/validation with `"none of the authors is attested"` because the live attestor set no longer attests them. [3](#0-2) 
5. Holders' balances of A remain permanently stuck until/unless D chooses to attest them (which D, as the attacker, will not do).

**Note on verification limits:** I was unable to fully trace, within the available exploration budget, whether `validation.js` restricts posting of `asset_attestors` messages strictly to the original asset definer's address (this is the expected/likely design based on the schema and naming, and is consistent with all sample scripts/tests referencing this feature), so I could not 100% confirm that no other address could also trigger this state. This does not change the core finding — that the definer, at minimum, has this unilateral freezing capability with no timelock — but a full code review of the `asset_attestors` authorization check in `validation.js` would be needed to fully characterize the exploitable actor set.
