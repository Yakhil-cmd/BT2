### Title
Untrusted swap-route contracts can execute arbitrary token transfers under the caller's authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` accept an opaque route payload and invoke the configured router, while route-selected code can place additional token transfers beneath the caller's `require_auth` tree. This mirrors Zip Slip's unbounded attacker-controlled path: a malicious route can escape the intended swap boundary and authorize unrelated transfers from the caller's wallet. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` authorizes only the controller's exact input transfer to the configured router, but then passes the caller-supplied `StrategySwap` bytes into `router.execute_strategy` without restricting which contracts the router invokes. [3](#0-2) 

`process_swap_collateral` is reachable by an account owner or delegate through the public `swap_collateral` entrypoint and forwards the raw `swap` bytes to `withdraw_and_swap_from_supply`; `process_swap_debt` does the same through `swap_debt`. [4](#0-3) [5](#0-4) [6](#0-5) 

The production threat model confirms that route-named pool and token addresses are not allowlisted, and that third-party code below the caller's authorization can add a token transfer from that caller to the recorded authorization tree. [7](#0-6) 

The regression test demonstrates the boundary escape: a router decodes an attacker-selected `hop_pool`, invokes it, and the pool calls `token.transfer(victim, attacker, amount)`. [8](#0-7) [2](#0-1) 

### Impact Explanation
A malicious swap route can steal unrelated wallet tokens from a user who signs the authorization tree produced by simulation, including tokens that were never listed or supplied to the lending protocol. The test records the rogue transfer as a child of `swap_collateral`, moves the victim's entire unrelated-token balance to the attacker, and shows that signed execution succeeds. [9](#0-8) [10](#0-9) 

The routed amount, router output check, and final account-risk check do not bound this additional transfer because it targets arbitrary wallet balances rather than the controller's swap input or output. [7](#0-6) 

### Likelihood Explanation
The attacker only needs to convince a swap user to submit a crafted route or sign the authorization tree generated for it; no protocol privilege, leaked key, oracle manipulation, or contract upgrade is required. A simulation-first wallet flow is particularly exposed because the malicious child transfer can be discovered only by decoding and inspecting the complete signed authorization tree. [11](#0-10) [12](#0-11) 

### Recommendation
Enforce a strict authorization boundary for strategy routes rather than treating the opaque payload as safe. Prefer constraining router-visible venues and pool/token addresses to a governance-approved allowlist, or redesign the router interface so the controller supplies a decoded route containing only authorized venues. Clients should additionally reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or flash-position authorization tree containing children beyond the expected input transfer. [1](#0-0) [7](#0-6) 

### Proof of Concept
1. Alice owns lending account `account_id` and holds `WALLET_BALANCE` of a token unrelated to the lending markets.
2. The attacker deploys `RogueHopPool` initialized with `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)`.
3. The attacker supplies a route whose `hop_pool` is that contract through `swap_collateral(caller=Alice, account_id, current=USDC, amount, new=ETH, swap=route)`.
4. `UnlistedPoolRouter.execute_strategy` decodes `hop_pool` and invokes its `swap` function while processing the caller-authorized swap. [8](#0-7) 
5. `RogueHopPool.swap` calls `token::Client::transfer(&Alice, &attacker, WALLET_BALANCE)`. [2](#0-1) 
6. Simulation records that transfer as a child invocation under Alice's `swap_collateral` authorization; if Alice signs that tree, the host executes it and her unrelated token balance becomes zero while the attacker receives `WALLET_BALANCE`. [9](#0-8) [10](#0-9)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
