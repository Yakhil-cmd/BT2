### Title
Stake and Vote program `Authorize`/`AuthorizeChecked` instructions perform irreversible single-step authority transfer, permanently bricking accounts on misdirected pubkeys - (Files: `cli/src/stake.rs`, `programs/vote/src/vote_state/mod.rs`)

### Summary
The `Authorize` family of instructions for both the stake program and the vote program change the `staker`/`withdrawer` (stake) or `voter`/`withdrawer` (vote) authority in a single atomic step, with no "pending authority must claim" intermediate state. If the current authority signs an `authorize` transaction naming the wrong `new_authority_pubkey` (e.g., a typo, wrong keypair, or a burn/invalid address), the change takes effect immediately and irrevocably — there is no on-chain mechanism to recover or roll back, unlike a two-step (`Ownable2Step`-style) pattern.

### Finding Description
The stake program's `authorize` instruction (`stake_instruction::authorize`, consumed in `cli/src/stake.rs` and dispatched to the on-chain stake processor via `StakeInstruction::Authorize`) directly overwrites `Meta.authorized.staker` or `Meta.authorized.withdrawer` upon verification that the *current* authority signed — see the CLI-side authority check flow at [1](#0-0) . There is no concept of a "pending" new authority that must separately accept the role; the instruction is unconditionally single-step, mirroring exactly the `OwnableUpgradeable` bug class in the report (single-step `transferOwnership`).

The vote program exhibits the identical pattern: `authorize()` in `programs/vote/src/vote_state/mod.rs` immediately calls `vote_state.set_authorized_withdrawer(*authorized)` (for `VoteAuthorize::Withdrawer`) or `vote_state.set_new_authorized_voter(...)` (for `VoteAuthorize::Voter`) as soon as the existing withdrawer (or voter, depending on type) signature is verified — see [2](#0-1) . Again, no acceptance step by the new authority exists for `VoteAuthorize::Withdrawer`.

The "checked" variants (`authorize_checked` / `AuthorizeChecked`) mitigate this only partially: they require the *new* authority to co-sign the same transaction, which prevents pure typos in an offline-constructed transaction, but they still perform the change atomically in one instruction with no ability to reject/replace before finalization once broadcast, and the plain (`unchecked`) `authorize` instructions remain fully supported and widely used (e.g., by `stake-accounts`, `solana-tokens` distribution tooling — see [3](#0-2)  and [4](#0-3) ), so the unsafe single-step path remains the default and commonly used mechanism protocol-wide.

### Impact Explanation
If a stake account's withdrawer/staker authority (or a vote account's withdrawer authority) is set to an incorrect or inaccessible pubkey via the unchecked `authorize` instruction, control over that stake or vote account's lamports and delegation is permanently and irrecoverably lost — no other instruction path exists to reassign authority without the (now unreachable) current authority's signature. This satisfies the "permanently frozen accounts" acceptance criterion: the account continues to exist and its lamports remain locked/staked, but no key can ever again authorize a `Withdraw`, `Deactivate`, `Split`, `Authorize`, or `SetLockup` on it. For stake accounts this can permanently freeze arbitrarily large amounts of staked SOL; for vote account withdrawer authority it permanently locks the ability to withdraw the vote account's rent-exempt balance/commission proceeds or update the withdrawer key.

### Likelihood Explanation
Low-to-moderate: this requires an unprivileged, ordinary stake/vote account holder to make an operational error (wrong address, corrupted config, or lost/regenerated keypair) when calling the unchecked `authorize` instruction, exactly analogous to the "Low, because it requires an error on the admin side" rating in the original report. This is a routine, frequently-executed operation (delegating/redelegating stake, rotating hot/cold authority keys, custodial withdrawer rotation) performed by ordinary stakers, not validator operators, making accidental misuse plausible at scale across the network.

### Recommendation
Introduce a two-step "pending authority" pattern for both the stake and vote program `Authorize` instructions: `Authorize` should set a `pending_new_authority` field rather than immediately overwriting the current authority, and a new `AcceptAuthority` instruction (signed by the pending new authority) should finalize the transfer. Alternatively, strongly deprecate/restrict the unchecked `authorize`/`Authorize` variants in favor of mandatory use of the "checked" variants (`authorize_checked`/`AuthorizeChecked`) that already require the new authority's co-signature, closing the gap where the unchecked path remains available and commonly used by tooling.

### Proof of Concept
1. Create a stake account and delegate it, with `withdrawer` authority set to keypair `A`.
2. `A` runs `solana stake-authorize <stake_account> --new-withdraw-authority <mistyped_or_wrong_pubkey>` (unchecked `stake_instruction::authorize`, per `parse_stake_authorize`/`process_stake_authorize` in `cli/src/stake.rs`).
3. Transaction succeeds immediately (only `A`'s signature is required, verified via `check_current_authority`), and `Meta.authorized.withdrawer` is now the incorrect/unreachable pubkey.
4. No instruction exists to reassign withdrawer authority without a signature from the (now unreachable) new authority — the stake account's SOL is permanently frozen. The same applies to `programs/vote/src/vote_state/mod.rs::authorize` for `VoteAuthorize::Withdrawer` on a vote account.
