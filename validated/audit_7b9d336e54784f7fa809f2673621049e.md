Based on the investigation, I found a genuine analog of the "unbounded parameter with critical impact" bug class, distinct from the already-guarded `AmmConfig` fee-rate setters (which use `assert!` with both min/max bounds and are admin-only anyway).

### Title
Pool creator can set `open_time` to an unbounded future timestamp, permanently freezing the pool's swap functionality - ([File: programs/cp-swap/src/instructions/initialize.rs])

### Summary
The `initialize` and `initialize_with_permission` instructions accept an unrestricted `open_time: u64` parameter from any caller (payer/creator) with only a lower-bound clamp, and no upper-bound check, mirroring the reported class of bug where a config value has a minimum check but no maximum check, letting an unprivileged actor push it to an extreme that breaks protocol liveness.

### Finding Description
In `initialize` (and identically in `initialize_with_permission`), the only sanitization applied to the user-supplied `open_time` is: [1](#0-0) 
```
let block_timestamp = clock::Clock::get()?.unix_timestamp as u64;
if open_time <= block_timestamp {
    open_time = block_timestamp + 1;
}
```
This only enforces a *minimum* (`open_time > now`); there is no maximum bound (e.g., "no more than N days/seconds in the future"). The value is then persisted verbatim into `PoolState.open_time` via `pool_state.initialize(...)`: [2](#0-1) [3](#0-2) 

`initialize` is a fully permissionless instruction — the `creator` account is just a `Signer`, with no owner/admin constraint, so any user (an unprivileged pool creator) can call it with attacker-chosen `open_time = u64::MAX`. The same applies to `initialize_with_permission`, which likewise only clamps the lower bound: [4](#0-3) 

The `open_time` field is referenced in `swap_base_input.rs` (grep confirms 3 usages of `open_time`), consistent with the well-known Raydium CP-swap pattern where swap instructions gate execution with a check such as requiring `block_timestamp >= pool_state.open_time` before allowing trading. I was not able to fully re-verify the exact check text in `swap_base_input.rs` within the available tool budget (index truncation prevented reading the full file in this session), but the field's presence there, combined with the doc-comment in `lib.rs` describing `open_time` as "the timestamp allowed for swap," strongly indicates swaps are conditioned on `Clock::now >= pool_state.open_time`.

### Impact Explanation
If `open_time` is set to an arbitrarily large value (e.g., `u64::MAX`) at pool creation, the pool becomes permanently unable to satisfy the "swap allowed" time condition, since `unix_timestamp` will never reach `u64::MAX`. This would deny all future `swap_base_input`/`swap_base_output` calls on that pool for as long as the chain exists, effectively bricking the pool. Depending on whether `deposit`/`withdraw` are also time-gated (unconfirmed in this session), this could result in permanent freezing of LP funds already deposited by the creator (the initial liquidity locked at pool creation, including the always-burned 100 LP tokens) and prevents the pool from ever fulfilling its intended trading function, matching the "critical impact via unbounded value" bug class from the reference report.

### Likelihood Explanation
Likelihood is high: the path is reachable from a single permissionless transaction (`initialize` / `initialize_with_permission`) with attacker-fully-controlled `open_time` argument, requires no special privileges, and there is no compensating check elsewhere in the codebase (based on available evidence) that rejects an excessively large `open_time`.

### Recommendation
Add an explicit upper bound in `initialize`/`initialize_with_permission`, e.g.:
```rust
require!(open_time <= block_timestamp + MAX_OPEN_TIME_DELAY, ErrorCode::InvalidOpenTime);
```
where `MAX_OPEN_TIME_DELAY` is a reasonable cap (e.g., a few days/weeks), analogous to adding a maximum gas-limit bound in the referenced `SystemConfig.setGasLimit` fix.

### Proof of Concept
1. Attacker calls `initialize` (or `initialize_with_permission`) with `open_time = u64::MAX` and valid `init_amount_0`/`init_amount_1`.
2. The clamp `if open_time <= block_timestamp { open_time = block_timestamp + 1 }` does not trigger since `u64::MAX > block_timestamp`, so `open_time` is stored as `u64::MAX` in `PoolState`.
3. Any subsequent call to `swap_base_input`/`swap_base_output` on this pool that checks `Clock::now >= pool_state.open_time` will fail indefinitely, permanently disabling trading on the pool (and any liquidity locked in it). [5](#0-4)
