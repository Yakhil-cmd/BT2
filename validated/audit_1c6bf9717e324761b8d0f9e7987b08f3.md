### Title
Cross-repository status forgery via SHA-only commit lookup in `StatusHandler` breaks the organization-authenticated-vs-repository-written binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The GitHub `status` webhook is authenticated per-organization (the HMAC is verified against the webhook secret configured for the organization named in `repository.owner.login`), but the actual write performed by the handler is not scoped to that organization or repository at all — it looks up commits purely by `sha` across the entire Shipit installation.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/organization secret to use for HMAC verification strictly from the payload's `repository.owner.login` (or `organization.login`) field: [1](#0-0) 

Once verification passes, `WebhooksController#create` dispatches the raw, still-untrusted-for-repository-binding JSON payload to the registered handlers: [2](#0-1) 

`StatusHandler#process`, however, never consults `repository.full_name` (the field the base `Handler` class uses elsewhere to scope lookups to a `Repository`/`Stack`, via `Handler#repository_name`/`#stacks`). Instead it resolves target records solely via `Commit.where(sha: params.sha)` — a global, repository-agnostic lookup — and then mutates each matching commit's status: [3](#0-2) 

Compare this to the base `Handler`, which does scope lookups by `repository.full_name` when handlers choose to use it: [4](#0-3) 

This creates exactly the "verified field vs. acted-upon field" mismatch called out in scope: the signature binds trust to `repository.owner.login` (an organization Shipit's GitHub App is installed on), but the write (`commit.create_status_from_github!`) is applied to any `Commit` row in the database whose `sha` matches, regardless of which organization/repository that commit actually belongs to.

Git commit SHAs are content-addressed and are not repository-bound: an identical commit (same tree, parents, author/committer, timestamp, message) produces an identical SHA regardless of which repository it lives in. If a target stack's repository is public (or otherwise readable by the attacker, e.g. a fork), the attacker can reproduce (or already possesses, via a fork) a commit with the exact same SHA that already exists in the target Shipit stack. The attacker then needs only to trigger a legitimate `status` webhook from an organization/repository that they administer and that is *also* onboarded into the same Shipit instance (satisfying `verify_webhook_signature` with that organization's own secret) with `sha` set to the colliding SHA, and `state`, `context`, `target_url`, `description` set arbitrarily.

This lets an attacker who fully controls one org/repo boarded onto a Shipit instance forge a commit status (e.g. `state: "success"`, matching a `ci.require`/`ci.blocking` context) on a commit belonging to a completely different repository/stack that they have no GitHub or Shipit permissions on.

### Impact Explanation
Commit statuses directly gate `Commit#deployable?` and `Stack#branch_status`/blocking-status logic used to allow or block deploys: [5](#0-4) 

By forging a passing status for a required/blocking CI context on a target commit the attacker doesn't control, the attacker can unblock deploy safety gates (`ci.require`/`ci.blocking`) on a stack belonging to another organization/repository — an unauthorized-deploy-enabling cross-repository write, which is explicitly in the Critical/High impact list ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
Requires the attacker to (a) control at least one repository/organization that is itself onboarded to the same multi-tenant Shipit instance (so they can generate a legitimately signed webhook), and (b) be able to produce a commit with an identical SHA to one in the victim stack (trivial if the target repository is public/forkable, since git SHAs are content-derived and not repo-scoped). No Shipit credentials, `ApiClient` token, or webhook secret theft is required — the attacker uses their own legitimately-issued webhook signature. This is a realistic scenario for any Shipit deployment managing more than one organization/repository.

### Recommendation
`StatusHandler` (and any other handler resolving records purely from payload sub-fields such as `sha`) must scope its lookup by the verified repository, e.g. restrict `Commit.where(sha: params.sha)` to `stacks` (as derived from `repository.full_name`, per the base `Handler#stacks`) rather than a global, cross-tenant query. More generally, every handler must bind the payload's `repository.full_name`/`repository.owner.login` to the same scope that was cryptographically verified, so no field acted upon escapes the trust boundary established by signature verification.

### Proof of Concept
1. Shipit instance hosts stacks for both `victim-org/app` and `attacker-org/decoy`, each with its own GitHub App webhook secret.
2. Attacker forks/reconstructs a commit in `attacker-org/decoy` whose SHA is identical to a real commit SHA present in `victim-org/app` (e.g., by forking the public victim repo and reproducing the exact commit, or via a coincidental/crafted shared history).
3. Attacker triggers (or crafts, using their own valid webhook secret for `attacker-org`) a `status` event payload:
   ```json
   {
     "sha": "<victim-commit-sha>",
     "state": "success",
     "context": "ci/required-context",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" }
   }
   ```
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"` and verifies successfully using `attacker-org`'s legitimate secret: `app/controllers/shipit/webhooks_controller.rb:24-31`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the commit in `victim-org/app`, and calls `create_status_from_github!`, creating a forged "success" status on that commit: `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`.
6. `victim-org/app`'s `ci.require`/`ci.blocking` gate is now satisfied for that commit, even though `attacker-org` has no legitimate relationship to `victim-org/app`.
