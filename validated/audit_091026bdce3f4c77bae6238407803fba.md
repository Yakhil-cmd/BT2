Confirmed: `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` acts on `payload.dig('repository', 'full_name')` [1](#0-0) , an entirely different field than the one used to select which GitHub App/organization's `webhook_secret` verifies the signature, which is `params.dig('repository', 'owner', 'login')` or the `organization.login` fallback [2](#0-1) .

### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while every handler acts on the unverified `repository.full_name` field, permitting cross-organization webhook forgery when any configured GitHub App has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check based on `repository.owner.login` (or `organization.login`) taken from the unauthenticated JSON body, then hands the *entire* raw payload to the event handlers, which independently re-read `repository.full_name` to decide which `Repository`/`Stack` to mutate. The equality the engine relies on — "the organization whose secret authenticated this delivery" == "the repository the delivery is allowed to write to" — is never enforced.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 
with `repository_owner` read straight from the untrusted body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` is a no-op when that organization's `webhook_secret` is blank:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

In a multi-organization deployment (`config/secrets*.yml` supports a `github: {OrgOne: {...}, OrgTwo: {...}}` map, see `test/dummy/config/secrets_double_github_app.yml`) [5](#0-4) , if **any one** configured organization has `webhook_secret: nil`, an attacker can set `repository.owner.login`/`organization.login` in the payload to that organization's name (which is public — it's whatever org is mounted on this Shipit instance) to force `verify_webhook_signature` to short-circuit to `true`, while setting `repository.full_name` to a **different** organization/repository entirely. `Shipit::Webhooks::Handlers::Handler` then resolves the target purely from that second, unverified field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

The binding broken: *organization that authenticated the delivery* (`repository_owner`, checked against a possibly-secretless app config) ≠ *repository that is actually written to* (`repository.full_name`, used unconditionally by every handler, including `PullRequest::OpenedHandler#repository`) [6](#0-5) .

### Impact Explanation
Depending on which webhook handler is targeted, an attacker who knows (or can guess) that at least one org on the instance has no `webhook_secret` set can inject forged `push`, `pull_request`, `status`, `check_suite`, or `membership` events for **any repository/stack tracked by the engine**, without any credential. This can trigger unwanted `GithubSyncJob`s, spoof commit CI statuses (`status` handler updates `Commit#statuses` from unverified payload fields), spawn review-stack provisioning for arbitrary pull requests, or manipulate team membership (`membership` event creates/deletes `Membership` records) — all of which feed into deploy eligibility (`required_statuses`, `deployable?`) and thus can influence which commit is considered safe to ship. This lines up with the "unauthorized deploy" / "authentication bypass" impact tier, since it defeats the entire purpose of the webhook signature check for a subset of the fleet's repositories.

### Likelihood Explanation
This requires the operator to have configured at least one organization without a `webhook_secret` in a multi-org Shipit deployment — a realistic and common oversight since the official example config ships with `webhook_secret: # nil` as the default placeholder [7](#0-6) , and nothing in `verify_signature` warns or refuses the request when the secret is unset for a mapped organization — it silently treats it as "verified." No credentials, session, or repository write access are required by the attacker; the endpoint is unauthenticated by design (it's meant to be called by GitHub).

### Recommendation
Do not select the verification secret from unauthenticated payload fields that differ from the field the handlers use to identify the write target. At minimum: (1) require `Shipit.github(organization:)` to refuse verification (`head 422`) rather than return `true` when `webhook_secret` is blank in a multi-org config; (2) re-verify that `repository.owner.login`/`organization.login` matches `repository.full_name`'s owner before processing, or have `verify_webhook_signature` be computed per-repository rather than per-payload-claimed-organization.

### Proof of Concept
1. Instance mounts two GitHub Apps: `OrgOne` (has a `webhook_secret`) and `OrgTwo` (misconfigured, `webhook_secret: nil`), both public information (visible in `Shipit.github_organizations` / app landing pages).
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: push`, an arbitrary/garbage `X-Hub-Signature`, and body:
```json
{
  "organization": { "login": "OrgTwo" },
  "repository": { "full_name": "OrgOne/victim-repo", "owner": {"login": "OrgOne"} },
  "after": "<attacker-chosen-sha>"
}
```
Wait — `repository_owner` prefers `repository.owner.login` over `organization.login`; so the attacker must omit `repository.owner.login` or set it to `OrgTwo` while keeping `repository.full_name` pointed at `OrgOne/victim-repo`:
```json
{
  "repository": { "full_name": "OrgOne/victim-repo", "owner": {"login": "OrgTwo"} },
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` computes `repository_owner == "OrgTwo"`, calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the bogus `X-Hub-Signature`.
4. `Shipit::Webhooks.for_event('push')` handlers run and resolve the target stack via `repository.full_name == "OrgOne/victim-repo"`, acting on the victim organization's repository even though verification was performed (vacuously) under `OrgTwo`'s identity.

      return true unless webhook_secret
