### Title
On-chain "randomness" in AA `number_from_seed()` can be predicted and rerolled by the trigger sender before broadcast - ([File: formula/evaluation.js])

### Summary
The oscript formula function `number_from_seed()` is the platform-provided primitive for AAs to obtain pseudo-random numbers on-chain. Like the reported bug, the only entropy sources available to feed this function inside an AA (`trigger.unit`, `trigger.data`, `timestamp`, `response_unit`, `mc_unit`, etc.) are fully deterministic values that the trigger sender computes and controls *before* ever broadcasting the triggering unit. Because AA execution is fully deterministic given the trigger, a user can locally simulate the AA's response for many different unit compositions (varying `parent_units`/`timestamp`, which they freely choose when composing their own unit) and only broadcast the one unit whose resulting "random" outcome is favorable to them — an even cheaper and more effective version of the "Reroll" attack described in the report, since unfavorable trials never cost anything (they are simply never sent to the network).

### Finding Description
`number_from_seed` derives a "random" number purely from a `sha256` hash of caller-supplied inputs: [1](#0-0) 

There is no protocol-level unpredictable entropy source (no VRF, no post-hoc reveal, no witness-contributed randomness) — any "randomness" an AA author builds with this function must be seeded from data that is knowable/controllable by the very party who benefits from the outcome: the trigger sender.

The trigger object passed into AA/oscript evaluation is built directly from the *sender's own outgoing unit*: [2](#0-1) 

`trigger.unit` is simply `objUnit.unit`, i.e. the hash of the very unit the sender is about to broadcast, which is computed locally with `objectHash.getUnitHash()` before the unit ever leaves the sender's wallet: [3](#0-2) 

When composing a unit, the sender's own client chooses the `timestamp` and, from a candidate set, the `parent_units` (see `composer.js`/`parent_composer.js`), so the sender has many degrees of freedom to alter the resulting unit hash without changing the "meaningful" content (payment amount, address, data): [4](#0-3) [5](#0-4) 

Because the entire AA response is a deterministic function of the trigger content, an attacker can, entirely offline (using the exposed AA estimation/dry-run path such as `estimatePrimaryAATrigger`, or their own local re-implementation of the formula engine), enumerate several candidate units (differing only in parent selection/timestamp) and locally evaluate what `number_from_seed(trigger.unit, ...)` (or any AA that keys randomness off `trigger.unit`, `timestamp`, or `trigger.data` values the sender freely picks) would produce for each candidate, then discard all unfavorable candidates and broadcast only the one unit that gives a favorable outcome. This is exactly the "predict, and reroll for free" pattern from the report's `Reroll` contract, except stronger: since nothing is broadcast for the rejected trials, there isn't even a bounce fee cost, unlike the EVM case where a revert still costs gas.

### Impact Explanation
Any AA that implements a lottery/raffle/random-reward/random-selection mechanism using `number_from_seed()` seeded (directly or indirectly, e.g. via `sha256`/`chash160` of) trigger-controlled values such as `trigger.unit`, `trigger.data`, or `timestamp` can have its randomness completely defeated. An attacker can guarantee winning outcomes (rewards, NFT-like asset draws, favorable game results, etc.) at will, resulting in unauthorized extraction of AA funds/assets that were meant to be distributed fairly/randomly among participants. This maps to concrete "AA fund loss" impact per the validation criteria.

### Likelihood Explanation
Likelihood is Medium: exploitation requires an AA author to have built a randomness-dependent payout mechanism using these primitives (a common and encouraged pattern for lotteries/games on the platform, since `number_from_seed` is the documented tool for this purpose), and an attacker capable of running the formula engine or the dry-run/estimation functions locally to search for a favorable trigger unit before broadcasting. No special privileges are needed — any ordinary unit poster/trigger sender can perform this attack.

### Recommendation
- Do not allow AA-level randomness to be derived solely from values fully known/controllable by the trigger sender before broadcast (`trigger.unit`, `trigger.data`, `timestamp`, `response_unit` of the same trigger).
- Provide/encourage a randomness pattern that includes entropy unknown to the trigger sender at compose time, e.g. combine the seed with `mc_unit`/main-chain data determined *after* the trigger unit is already stable and irreversibly committed (so the sender cannot pre-compute and selectively withhold unfavorable outcomes), or split reveal into two phases (commit unit now, reveal/settle in a later unit keyed off a future MC unit hash unknown at commit time).
- Document explicitly in `number_from_seed` reference material that seeding on any trigger-controlled or pre-broadcast-computable value is unsafe for use cases with financial stakes.

### Proof of Concept
1. Deploy an AA using, e.g.:
   `messages: [{ app: 'state', state: "{ $r = number_from_seed(trigger.unit, 0, 1); if ($r == 1) { ... pay reward ... } }" }]`
2. An attacker composes a candidate trigger unit locally with `composeJoint`, choosing among several valid `parent_units`/`timestamp` combinations returned by `parent_composer.pickParentUnitsAndLastBall` (multiple free-unit candidates commonly exist).
3. For each candidate, attacker computes `objectHash.getUnitHash(objUnit)` locally, exactly reproducing `trigger.unit`, and evaluates the AA's `number_from_seed` formula offline (using the same `formula/evaluation.js` logic, e.g. via `aa_composer.estimatePrimaryAATrigger`/dry run) to predict `$r`.
4. Attacker discards all candidates giving `$r == 0` (no cost incurred — nothing was broadcast) and only signs+broadcasts the one candidate giving `$r == 1`.
5. Result: the reward is paid out to the attacker deterministically, defeating the intended randomness with no need to ever "revert" like in the EVM example.

		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
