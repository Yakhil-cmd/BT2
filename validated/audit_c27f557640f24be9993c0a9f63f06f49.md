### Title
Global `handleJoint` mutex can be permanently starved by an unhandled exception during AA dry-run, freezing acceptance of all new units - ([File: network.js])

### Summary
`network.js`'s `handleJoint()` serializes **all** unit validation/save through a single global lock, `mutex.lock(['handleJoint'], ...)` [1](#0-0) . Inside the `ifOk` callback, when `conf.bDryRunNewTriggers` is enabled, the code `await`s `aa_composer.dryRunPrimaryAATrigger(...)` with no `try/catch` before the lock is released [2](#0-1) . An attacker who posts a unit paying to an AA address can control the trigger content that flows into this dry run. If the dry run throws (synchronously, or the returned promise rejects) the `async` `ifOk` function never reaches `writer.saveJoint(...)`, so `unlock()` is never called [3](#0-2) . Because ocore's mutex implementation is a simple FIFO queue keyed on string locks with no timeout enforcement (the deadlock-checker `checkForDeadlocks` is explicitly disabled: `//setInterval(checkForDeadlocks, 1000);`) [4](#0-3) , once `handleJoint` is stuck locked, every subsequent call to `mutex.lock(['handleJoint'], ...)` queues forever [5](#0-4) . This is functionally analogous to CVE‑2020‑14812: a reachable, unprivileged-triggerable locking flaw that causes the affected service (here, the node's unit-processing pipeline) to hang, denying availability to legitimate operations (accepting/confirming new units) without requiring any special privilege from the attacker.

### Finding Description
`handleJoint(ws, objJoint, bSaved, bPosted, callbacks)` acquires the single global key `'handleJoint'` via `mutex.lock` before calling `validation.validate()` [6](#0-5) . This lock guards the *entire* node's unit intake — it is the same lock used by the composer/wallet code paths (`composer.js`, `divisible_asset.js`, `indivisible_asset.js`) when saving locally composed units [7](#0-6) .

In the `ifOk` handler, when `conf.bDryRunNewTriggers` is on (used to preemptively crash-test AA triggers before committing them for real, per the comment "if it would crash, let it crash now, not when we execute the trigger for real"):
```
if (conf.bDryRunNewTriggers && !conf.bLight && !objJoint.ball && objValidationState.count_primary_aa_triggers) {
    ...
    for (let { address, definition } of rows) {
        const trigger = aa_composer.getTrigger(objJoint.unit, address);
        await aa_composer.dryRunPrimaryAATrigger(trigger, address, JSON.parse(definition));
    }
}
writer.saveJoint(objJoint, objValidationState, null, function(){
    validation_unlock();
    callbacks.ifOk();
    unlock();
    ...
});
``` [8](#0-7) 

`dryRunPrimaryAATrigger` executes `handleTrigger`, the full AA response engine, against attacker-controlled trigger data and definition (`aa_composer.js:272-306`) [9](#0-8) . `handleTrigger` is a very large state machine touching formula evaluation, balances, and state variables; any code path in it (or in the formula engine it invokes) that throws a JS exception instead of routing the error through its callback chain will propagate synchronously up through the `await`, causing the enclosing `async function ifOk(...)` promise to reject. Since this call site does not `await`/attach a `.catch()` to the result of `handleJoint`'s internal callback invocation from `network.js`'s caller (`validation.validate` invokes `callbacks.ifOk` as a plain function, not awaited), an unhandled promise rejection occurs and execution never reaches `unlock()`. The `handleJoint` mutex is therefore held forever.

Because `mutex.js` has no enforcement of lock timeouts in production (`checkForDeadlocks` is commented out) [4](#0-3) , all future `handleJoint('handleJoint')` acquisitions — for every future incoming unit from any peer or from the node's own wallet/AA-response pipeline — queue indefinitely via `arrQueuedJobs` [5](#0-4) . The node stops processing/accepting any new unit until manually restarted.

This mirrors CVE‑2020‑14812's bug class: a locking primitive reachable via ordinary (here, "high privileged" translates to merely "capable of posting a valid unit paying an AA," which any wallet user can do) operations causes the server to hang and become unable to service further requests — in ocore terms, the node becomes unable to confirm new units.

### Impact Explanation
If exploitable, this results in "a network unable to confirm new units" on any full node with `conf.bDryRunNewTriggers` enabled: the global validation/write lock is held forever, so the affected node stops accepting and forwarding any new joint, effectively taking it offline for consensus purposes without a crash or restart trigger, and requiring an operator to notice and manually restart the process. If enough hub/relay nodes run with this configuration, this can stall confirmation of transactions network-wide until operators intervene.

### Likelihood Explanation
Exploitability is conditional and I could not fully verify all preconditions with the available read-only tooling:
- It requires `conf.bDryRunNewTriggers` to be truthy on the target node; I was unable to determine its default value from `conf.js` in the indexed content (only two references in `network.js` were found by grep, none in `conf.js`), so I cannot confirm whether this is enabled by default or only optionally by operators.
- It further requires finding a genuine unhandled-exception path inside `handleTrigger`/formula evaluation reachable by attacker-controlled `trigger`/`definition` data that is not caught internally. `aa_composer.js`, `formula/validation.js`, and `formula/evaluation.js` show extensive internal guards (complexity/op limits, depth limits, decimal-finiteness checks, string-length checks) which suggests many obvious throw sites are already defended, so a concrete crashing input was not identified in this investigation — this is a structural/code-path risk (missing `try/catch` around `await dryRunPrimaryAATrigger`) rather than a proven end-to-end PoC.

### Recommendation
Wrap the `await aa_composer.dryRunPrimaryAATrigger(...)` call in `network.js`'s `ifOk` handler in a `try/catch`, ensuring `unlock()` (and `validation_unlock()`) are always invoked even if the dry run throws or rejects, and route any dry-run failure through `callbacks.ifUnitError`/`ifJointError` instead of allowing an unhandled promise rejection to leak the lock. Additionally, consider re-enabling a bounded, production-safe deadlock/stuck-lock watchdog for the `handleJoint` and `write` mutex keys so a stuck job is force-released or at minimum logged/alerted rather than silently hanging forever.

### Proof of Concept
Not fully reproducible from static analysis alone. Conceptually:
1. Deploy/target a full node running with `conf.bDryRunNewTriggers = true`.
2. Define (or use an already-deployed) AA whose trigger-handling logic can be driven, via attacker-supplied `trigger.data`/outputs, into a state where `handleTrigger`'s internal formula/state-var machinery throws a raw JS exception instead of resolving via its `bounce`/`onDone` callback paths (e.g., a case in `formula/evaluation.js` or `aa_composer.js` not defensively guarded against a particular malformed input).
3. Post a unit paying to that AA address with the crafted trigger payload via `handlePostedJoint`/`handleOnlineJoint`, entering `handleJoint`'s `ifOk` → dry-run branch [2](#0-1) .
4. If the dry run throws, `unlock()` for `'handleJoint'` is never called; observe that subsequent unit submissions to the node stall indefinitely (verifiable via `mutex.getCountOfQueuedJobs()`/`isIdle()` diagnostics in `network.js` showing growing queued jobs with `locks: 1`) [10](#0-9) .
