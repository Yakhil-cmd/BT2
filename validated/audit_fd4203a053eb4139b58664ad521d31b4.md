## Title
Webhook signature is scoped to `repository.owner.login`, but handlers act on `repository.full_name` — cross-repository status/CI forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` will validate the HMAC by reading `params.dig('repository','owner','login')` (or `organization.login`). All webhook handlers, however, resolve the `Repository`/`Stack` to act on from a *different* JSON field: `payload.dig('repository', 'full_name')`, used in `Handler#stacks` / `Handler#repository_name`. Nothing binds these two fields together, so the organization whose secret is proven does not have to equal the repository the handler actually mutates.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-30` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (lines 59-62) is `params.dig('repository','owner','login') || params.dig('organization','login')`.

`verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) is a pure HMAC check of the raw body against the `webhook_secret` configured for that one organization — it says nothing about which repository the payload actually targets.

Once the signature passes, `WebhooksController#create` dispatches the **entire raw payload** to handlers (`app/controllers/shipit/webhooks_controller.rb:10-15`). Every handler inherits `Handler#stacks`/`Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), which look up the target repository from `payload.dig('repository', 'full_name')` — a field completely independent from `repository.owner.login` used for signature selection.

Shipit explicitly supports multiple independently-configured GitHub organizations, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, both listing multiple orgs under `github:`). An attacker who legitimately controls a repository in `OrgA` (and therefore possesses valid signed deliveries / knows `OrgA`'s `webhook_secret` the same way any GitHub-side webhook sender would, i.e., they can trigger genuine events from their own repo) fully controls the raw JSON body of that delivery. They can set:
- `repository.owner.login = "OrgA"` (drives secret selection and passes `verify_signature`)
- `repository.full_name = "OrgB/other-repo"` (drives the handler's lookup and target)

Because the signature is computed over the whole raw body chosen by the attacker (their own webhook trigger for their own repo), the HMAC will validate successfully under `OrgA`'s secret regardless of the `full_name` field's contents. The handler then executes against `OrgB/other-repo`, a repository the attacker never controls.

### Impact Explanation
This breaks the equality the engine relies on: `organization that authenticated == repository that is written`. Concretely:
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) writes CI `Status` records for any `Commit` matching `params.sha`, independent of `stacks`/repository binding entirely (it does not even filter by repository), letting an attacker forge a passing/failing CI status for a commit sha belonging to a completely different tracked repository/stack. If that stack has continuous delivery enabled, a forged successful status can be a contributing trigger toward an unauthorized deploy — landing in the "unauthorized deploy" Critical-impact category.
- `PushHandler` and `CheckSuiteHandler` use `Handler#stacks`, resolved from the attacker-controlled `full_name`, to enqueue `stack.sync_github` / `schedule_refresh_check_runs!` against a cross-tenant stack the attacker does not own — a cross-repository interaction triggered purely by payload content that the signature never covered for that field.

### Likelihood Explanation
Any external actor able to generate a genuinely-signed webhook delivery for one repository configured in Shipit (i.e., anyone with push/admin access to any single repo/org already onboarded, which is the normal unprivileged "attacker with a GitHub account and access to some tracked repo" threat model used in this scan) can craft the JSON body themselves before GitHub signs it, or simply replay/modify a delivery through the standard endpoint since `verify_signature` never re-derives `repository_owner` from a value bound to the signature computation itself — the field used for secret selection is attacker-suppliable and independent of the field used for target resolution.

### Recommendation
Bind the repository acted upon to the same identity that was authenticated: derive `repository_name`/`stacks` from the *same* field used to select the webhook secret (or verify that `repository.owner.login`/`organization.login` is a case-insensitive prefix match of `repository.full_name`'s owner segment) before dispatching to handlers. Reject the payload if `repository.full_name`'s owner does not match the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`), and onboard a `Stack` for `OrgB/target-repo`.
2. As an attacker who owns `OrgA/attacker-repo` (webhook already registered), send/replay a `status` (or `push`/`check_suite`) event body:
```json
{
  "sha": "<sha-of-a-commit-in-OrgB/target-repo>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
signed with `OrgA`'s `webhook_secret` (`X-Hub-Signature: sha1=<hmac using OrgA secret>`), and `X-Github-Event: status`.
3. `WebhooksController#verify_signature` resolves `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully.
4. `StatusHandler#process` creates a `Status` on the commit belonging to `OrgB/target-repo`'s stack, even though the signature only proved knowledge of `OrgA`'s secret, not any credential related to `OrgB`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
