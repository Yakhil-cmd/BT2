### Title
`GIT_EXEC_PATH` injection via PR label name reaches `rollback.override` `Command#start` (`PTY.spawn`) unfiltered - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no key allowlist, and `LabelCapturingHandler#capture_labels` persists those raw label names straight from the unauthenticated webhook body. That merged hash flows unchanged through `TaskCommands#env` / `RollbackCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn`, so an attacker-chosen label such as `git_exec_path` becomes the literal environment key `GIT_EXEC_PATH` for every command the deploy host executes for that stack, including the `rollback.override` step.

### Finding Description
The broken binding: the set of environment keys reaching `PTY.spawn` for a review stack's `rollback.override` step should equal `Shipit.env ∪ {fixed task keys} ∪ deploy_spec.machine_env ∪ task.env` — i.e., keys under Shipit/repo-maintainer control only. In fact it equals that set unioned with `{ label_name.upcase => "true" for every pull_request label }`, an attacker-controlled set with no allowlist.

Path:
1. Any user who can open a PR against the repo (fork PR) or send a `pull_request` webhook can add a label named e.g. `git_exec_path` to their own PR (labeling requires only write access to labels on PRs you control in many workflows, but regardless the webhook itself is unauthenticated at the Shipit HTTP layer — signature verification only proves it came from GitHub for *some* repo, not that the sender is authorized against Shipit's model).
2. `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) writes `params.pull_request.labels.map(&:name)` straight into `pull_request.labels` with no validation or allowlist.
3. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```ruby
def env
  return super unless pull_request.present?
  super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
end
```
No key is excluded — `GIT_EXEC_PATH`, `LD_PRELOAD`, `RUBYOPT`, `PATH`, etc. can all be injected this way.
4. `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) merges `@stack.env` (i.e. `ReviewStack#env`) into the task environment; `RollbackCommands#env` (`lib/shipit/rollback_commands.rb:9-13`) inherits this chain via `DeployCommands < TaskCommands`.
5. `Command#initialize` stores `@env`; `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — the attacker-controlled hash is merged **last**, so it wins over `BASE_ENV`.
6. `Command#start` (`lib/shipit/command.rb:85-101`) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` — the poisoned env, including `GIT_EXEC_PATH`, is what the spawned process (and any `git` subcommand it shells out to, e.g. in a `rollback.override` step) inherits.

`GIT_EXEC_PATH` controls where git looks up its subcommand binaries (e.g. `git-remote-https`, `git-checkout`); an attacker who controls this variable and can get the deploy host to invoke `git` (which every deploy/rollback of a git-backed stack does) can redirect git to execute an attacker-supplied binary placed under a path they also control (e.g. via files committed in their fork, if the working directory or a repo-relative path is used) — this is arbitrary code execution on the deploy host.

Existing guards do not stop this: `verify_signature` / `GitHubApp#verify_webhook_signature` only prove the webhook came from GitHub for *a* repository, not that label names are safe; `ExplicitParameters` schemas (seen in `LabelCapturingHandler`, `LabeledHandler`, `UnlabeledHandler`) only validate label `name` is a `String`, placing no restriction on content; there is no `EnvironmentVariables#permit`-style allowlist applied to `ReviewStack#env`'s label-derived keys before they reach `Command`.

### Impact Explanation
Once a label such as `git_exec_path` is attached to the attacker's own PR against a repository configured with `review_stacks_enabled` (any `provisioning_behavior`, including `prevent_with_label`, since a PR without the block-label still creates/keeps an active review stack under `prevent_with_label`), every subsequent task (deploy, rollback, CI status recheck commands, etc.) run for that stack executes with `GIT_EXEC_PATH` (or any other env var name derivable from a label string) set to the attacker's chosen value. This is executed on the shared Shipit deploy host, not sandboxed per-repository, so it is Critical: Remote Code Execution on the deploy host (`Command`/`PTY.spawn`), matching the stated Immunefi RCE class. The blast radius extends to the whole Shipit host and any other stacks/tasks running on it, since the RCE occurs as the Shipit worker process/user.

### Likelihood Explanation
Preconditions: the repository must have `review_stacks_enabled` and use PR-based review stacks (the standard Shipit review-stack feature); the attacker needs to be able to open/label a PR against the repo (fork PRs qualify) and does not need any Shipit credentials, GitHub team membership, or maintainer status. Cost is trivial — creating/labeling a PR with a chosen label string via the GitHub UI or API. This is fully repeatable: the label can be re-applied, and the injected variable persists in `pull_request.labels` until removed, affecting every task run against that stack. The only remaining uncertainty is the exact downstream exploitation detail (getting `GIT_EXEC_PATH` to point at a directory the attacker also controls on the deploy host filesystem, e.g. via the checked-out fork content) — the finding as validated in this audit is that the unsanitized env key reaches `PTY.spawn`; full exploitation to code execution depends on the deploy host's filesystem layout, which is outside static analysis but is the documented risk class for `GIT_EXEC_PATH`.

### Recommendation
Sanitize `ReviewStack#env` (and any other label-to-env conversion) with an explicit allowlist of permitted label-derived key names (e.g. reject keys matching known dangerous variables like `GIT_EXEC_PATH`, `LD_PRELOAD`, `PATH`, `RUBYOPT`, `BUNDLE_*`, or better, prefix all label-derived keys with a fixed namespace such as `SHIPIT_LABEL_` so they can never collide with security-sensitive environment variable names). Apply this filtering before the hash is merged in `app/models/shipit/review_stack.rb`, and add a regression test asserting `GIT_EXEC_PATH` (or any non-namespaced key) is never present in the resulting env hash regardless of PR label content.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
