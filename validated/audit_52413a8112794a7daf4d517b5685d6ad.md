Based on the analysis, `tps_fee` is real bytes actually paid out of a unit's own base outputs (confirmed in `validation.js:2666`: `total_input !== total_output + objUnit.headers_commission + objUnit.payload_commission + oversize_fee + tps_fee + burn_fee + vote_count_fee`), and `tps_fees_balance` tracks a credit/debit ledger of over/under-payment that directly offsets how much real bytes a future unit from that address must pay (`validation.js:1088-1090`, `composer.js:387`). ### Title
Truncating division in `updateTpsFees()` causes minority-share TPS fee recipients to lose fee credits/debits - (File: storage.js)

### Summary
`updateTpsFees()` in `storage.js` distributes the difference between a unit's paid `tps_fee` and its final, correctly-computed `tps_fee` (`total_tps_fees_delta`) among the unit's `earned_headers_commission_recipients` using `Math.floor(total_tps_fees_delta * share / 100)`. This mirrors exactly the reported bug class: an integer/truncating percentage split that rounds toward zero, so any recipient whose `share` is small relative to 100 (i.e., `total_tps_fees_delta * share < 100`) gets a `tps_fees_delta` of `0` even though they should have received a small positive or negative correction.

### Finding Description [1](#0-0) 

For each stable unit at each MCI, the node computes the true required fee (`getFinalTpsFee`) and compares it to what was actually paid (`objUnitProps.tps_fee`), producing `total_tps_fees_delta` which "can be negative" (over-payment, owed refund) or positive (under-payment, still owed). This delta is supposed to be distributed among `earned_headers_commission_recipients` proportional to their `share` (0-100, validated to sum to exactly 100 in `validateHeadersCommissionRecipients()`, [2](#0-1) ). The per-recipient delta is computed as:
```js
const tps_fees_delta = Math.floor(total_tps_fees_delta * share / 100);
``` [3](#0-2) 

Because `Math.floor` truncates toward negative infinity rather than rounding to nearest, whenever `|total_tps_fees_delta| * share < 100`, the per-recipient delta computes to `0`, silently dropping the correction that recipient should have received. Since each recipient's split is computed *independently* against the fixed `100` denominator rather than proportionally re-normalized, the sum of all distributed deltas systematically diverges from `total_tps_fees_delta` whenever any recipient has a small share — the discarded remainder is neither credited to anyone nor tracked, unlike `headers_commission.js` which explicitly acknowledges (in a comment) that rounding drift across multiple payers is tolerated for a *different, unrelated* reason (summing header commissions "won from several parent units").

This code path is directly reachable by any unprivileged unit author: `earned_headers_commission_recipients` (and thus the `share` values used here) is a field fully controlled by the unit's author when composing a unit with more than one author (or optionally with one author), validated only for summing to 100 and being a positive integer ( [4](#0-3) ). An author can freely choose to add extra low-share recipients.

### Impact Explanation
`tps_fees_balance` is not a cosmetic statistic — it is consumed as a real discount/surcharge against the *actual bytes* a future unit from that address must pay as `tps_fee`, which is itself validated to balance against real base-asset inputs and outputs:
```js
if (total_input !== total_output + objUnit.headers_commission + objUnit.payload_commission + oversize_fee + tps_fee + burn_fee + vote_count_fee)
``` [5](#0-4) 
and is read back via `tps_fees_balance / share` when composing (`composer.js:384-390`) and when validating a submitted unit's `tps_fee` (`validation.js:1086-1090`). A recipient whose earned refund silently rounds to `0` never gets that credit applied to `tps_fees_balances`, so they will be forced to pay real bytes for tps fee that they had already effectively overpaid — a genuine loss of funds for that address across many units over time, all because of the attacker/author's chosen (or naturally small) `earned_headers_commission_share`. This is a deterministic, network-wide computation (every full node performs the identical floor operation), so it does not itself cause consensus disagreement, but it does cause a systematic, silent loss of legitimately earned fee credit for minority-share addresses, which accumulates over time as more units are processed under the v4.0 TPS-fee mechanism.

### Likelihood Explanation
This triggers automatically and deterministically any time a unit's actual final TPS fee differs from what was paid at composition time (routine, since final fee depends on network-wide finality data unknown at compose time) and the unit specifies (or defaults to) any `earned_headers_commission_recipients` with a small percentage share. No attacker action beyond normal, permitted unit composition (setting a small `earned_headers_commission_share` for a co-author) is required; it can also occur unintentionally whenever legitimate multi-author units use very unequal shares.

### Recommendation
Use higher-precision proportional distribution (e.g., accumulate remainders using the largest-remainder method, or track/carry forward the fractional remainder into subsequent MCIs) instead of independently flooring `total_tps_fees_delta * share / 100` per recipient, so that the sum of distributed deltas always equals `total_tps_fees_delta` and no recipient's small-but-nonzero entitlement is discarded.

### Proof of Concept
1. Compose a unit with 2 authors, `earned_headers_commission_recipients` = `[{address: A, earned_headers_commission_share: 99}, {address: B, earned_headers_commission_share: 1}]`.
2. Let the unit's paid `tps_fee` end up being `50` more than the final computed fee (`total_tps_fees_delta = -50`, i.e., both authors together overpaid by 50 bytes and are owed a refund credit).
3. In `updateTpsFees()`: for address B, `Math.floor(-50 * 1 / 100) = Math.floor(-0.5) = -1` — actually check smaller deltas: with `total_tps_fees_delta = -10`, `Math.floor(-10*1/100) = Math.floor(-0.1) = -1`? No — `Math.floor(-0.1) = -1` too — the important truncation-to-zero case is where the magnitude is `< 100/share`. E.g. `total_tps_fees_delta = -50`, share=1: `Math.floor(-50/100)=Math.floor(-0.5)=-1` (not 0, floor rounds down for negatives). Use a positive delta instead: `total_tps_fees_delta = 50` (owed additional fee), share=1: `Math.floor(50*1/100) = Math.floor(0.5) = 0`. Address B's `tps_fees_balance` is never debited despite owing a fractional share of the shortfall, while address A (99% share) is debited `Math.floor(50*99/100) = 49`, leaving `1` unaccounted unit of the true `50` total delta permanently lost from the ledger.
4. Repeat over many units; address B accumulates never-applied credits, causing it to be systematically undercharged/undercredited relative to its true entitlement, verifiable by comparing `SUM(tps_fees_balance changes)` against `SUM(total_tps_fees_delta * share / 100)` computed with full precision.
