### Title
Attacker-controlled PR label names, upcased, are merged into deploy-time env before hardcoded/system keys - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges every label name on the associated PR (upcased) into the environment hash as `LABEL => "true"`, and `TaskCommands#env` merges `@stack.env` immediately after the base env produced by `Commands#base_env` (which contains `GITHUB_TOKEN` and, conditionally, `GIT_ASKPASS`), before the block of hardcoded keys is merged. Since none of the later merges (`SHIPIT_USER`, `EMAIL`, ... , `deploy_spec.machine_env`, `@task.env`) re-assert `GITHUB_TOKEN` or `GIT_ASKPASS`, a PR labeled e.g. `github_token` overwrites `GITHUB_TOKEN` with the literal string `"true"` for the lifetime of that review stack's tasks.

### Finding Description
The claimed binding: `TaskCommands.new(task).env['GITHUB_TOKEN']` should equal `Shipit.github(organization: stack.repository.owner).token` (the real credential set by `Commands#base_env`), but with attacker-controlled labels it instead equals `"true"`.

Code path:
- `Commands#env` (`lib/shipit/commands.rb:24-26`) returns `base_env`, which sets `GITHUB_TOKEN` and conditionally `GIT_ASKPASS` [1](#0-0) .
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) starts with `super` (i.e. `Commands#env`), then `.merge(@stack.env)`, then merges hardcoded keys that never include `GITHUB_TOKEN`/`GIT_ASKPASS`, then `deploy_spec.machine_env`, then `@task.env` [2](#0-1) .
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) calls `super` (`Stack#env`) and merges in `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` — i.e. every label name, upcased, becomes an env key set to the string `"true"` [3](#0-2) .
- Labels originate from the GitHub webhook payload and are stored verbatim (only upcased later) via `PullRequest#github_pull_request=` (`self.labels = github_pull_request.labels.map(&:name)`) and `LabelCapturingHandler#capture_labels` (`pull_request.update!(labels: params.pull_request.labels.map(&:name))`), with no allow-list or character filtering [4](#0-3) [5](#0-4) .

No existing guard filters label content against environment-sensitive key names. `ExplicitParameters` schema only validates that `labels` is `Array` of `{name: String}` — no format restriction [6](#0-5) . `Stack#env` itself doesn't include `GITHUB_TOKEN`, so the model-level `environment` validation (`Stack` format regex on the `environment` column) is irrelevant here — it does not constrain PR labels. `EnvironmentVariables#permit` (used for task/deploy-supplied envs, `Stack#filter_task_envs`/`filter_deploy_envs`) is never invoked on `ReviewStack#env`'s label-derived hash, so it provides no protection.

Attack requires only the capability to attach a label to a PR that already has an active Shipit review stack (PR must already be `opened`/tracked by Shipit for a review-stack-enabled repository). GitHub label mutation typically requires write/triage permission on the repo, which is a repo-side GitHub permission, not a Shipit permission — Shipit does not verify who is authorized to label PRs beyond trusting the webhook payload once signature verification passes.

### Impact Explanation
If the label collides with `GITHUB_TOKEN`, subsequent deploy/rollback tasks on that review stack run with `GITHUB_TOKEN=true` in their environment instead of the real OAuth/App token, breaking git push/fetch operations that rely on that token (denial of correct behavior, not secret exfiltration — the real secret is simply replaced, not leaked). If the label collides with `GIT_ASKPASS` (only set when `Shipit.use_git_askpass?` is enabled), the attacker overwrites the path to the git-askpass helper script with the literal string `"true"`; when git invokes `GIT_ASKPASS` as a program (via `PTY.spawn`/`Command#start`), this could cause command execution failures or, depending on shell/git invocation semantics, unexpected behavior feeding attacker-influenced strings into places git expects executable paths. This is a credential/behavior integrity bug on the review stack the attacker's own PR belongs to — it does not extend to other tenants' stacks because labels are scoped to the PR's own `PullRequest`/`ReviewStack` record, and `GITHUB_TOKEN` here is the app-level token used for git operations for that stack's repository (not another repository's stack). No path exists to have this env corruption applied to a repository the attacker doesn't have write/label access to.

### Likelihood Explanation
Precondition: a Shipit-configured repository must have review stacks enabled, and the PR must already have created a review stack (i.e., `opened` with `stack.present?`). The attacker must be able to attach a label named (case-insensitively) `GITHUB_TOKEN` or `GIT_ASKPASS` to their PR — on GitHub this typically requires write/triage collaborator permission, not merely being an unprivileged forker who can only open a PR. This materially limits the "unprivileged forker" framing from the prompt: pure PR-opening/forking capability, without label-write permission, cannot trigger this. Where label-write is available (e.g., internal repos with liberal collaborator permissions, or bots auto-labeling from PR titles), the attack is trivial and repeatable per deploy.

### Recommendation
In `Shipit::ReviewStack#env`, do not let label-derived keys overwrite security-relevant/reserved environment keys. Either: (1) merge label-derived env before `super`/base credential env rather than after, so hardcoded/system keys always win; (2) maintain an explicit deny-list/allow-list (e.g., reject label names matching `GITHUB_.*`, `GIT_.*`, `PATH`, `BUNDLE_.*`) before upcasing into the env hash; or (3) prefix label-derived keys (e.g., `LABEL_<NAME>`) so they can never collide with system/credential variable names. Additionally, ensure `TaskCommands#env`'s hardcoded/system keys (`GITHUB_TOKEN`, `GIT_ASKPASS`) are merged last (or reasserted) so no upstream merge (`@stack.env`, `@task.env`, `deploy_spec.machine_env`) can clobber them.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual addition)
test "labels cannot clobber GITHUB_TOKEN in task env" do
  stack = shipit_review_stacks(:review_stack) # existing fixture review stack
  stack.pull_request.update!(labels: ['github_token'])

  task = stack.tasks.create!(...) # build a task associated with stack
  commands = Shipit::TaskCommands.new(task)

  real_token = Shipit.github(organization: stack.repository.owner).token
  assert_equal 'true', commands.env['GITHUB_TOKEN']
  refute_equal real_token, commands.env['GITHUB_TOKEN']
end
```
This demonstrates the divergence: `TaskCommands.new(task).env['GITHUB_TOKEN']` becomes `"true"` instead of the real token sourced from `Commands#base_env`.
