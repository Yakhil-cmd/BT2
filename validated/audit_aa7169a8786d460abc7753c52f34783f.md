## Title
Asset definer can instantly freeze already-held spender-attested asset balances by shrinking the attestor list, with no grace period for holders to withdraw — (File: `validation.js`, `storage.js`)

### Summary
For `spender_attested` assets, the asset definer (issuer) can publish an `asset_attestors` message at any time, replacing the entire trusted-attestor list for the asset. This change becomes effective immediately once the message is stable, and it is applied retroactively to every existing holder of the asset: if a holder's previous attestation was granted by an attestor that is no longer on the current list, that holder instantly loses the ability to spend units they already hold — with no delay, migration path, or chance to move funds beforehand. This mirrors the reported JUSD issue where a privileged de-listing action instantly zeroes/locks a user's existing holdings without any protective grace period.

### Finding Description
`spender_attested` is a per-asset flag set at asset definition time; if set, only addresses attested by one of the asset's current trusted attestors are allowed to issue, receive, or spend that asset [1](#0-0) . The trusted attestor list can be changed at will by the asset's definer via an `asset_attestors` message, validated in `validateAttestorListUpdate`, which only requires the message be single-authored by the definer and contain a valid, sorted attestor list — there is no cooldown, delay, or restriction on how often or how drastically the list can change: [2](#0-1) 

When the asset is subsequently loaded (`readAsset` in `storage.js`), only the **single latest** attestor-list unit is used to determine the current trusted attestors — older attestor lists are discarded entirely: [3](#0-2) 

`filterAttestedAddresses` then checks whether a holder's address was attested by one of the *current* attestors (not the attestors that were valid when the holder received the funds): [4](#0-3) 

This "current attestors only" check is enforced both for issuing/receiving (`validatePayment`, `objAsset.arrAttestedAddresses`) and — critically — for **spending previously-received outputs**: [5](#0-4) 

Because the check is done against the live/current attestor list at validation time rather than at the time the holder originally received or was attested for the asset, a definer can:
1. Publish an `asset_attestors` update that drops an existing attestor (e.g., the one who attested address A) from the trusted list.
2. As soon as that message stabilizes, address A's units of this asset — even if A has held them for a long time and did nothing wrong — become permanently unspendable, because `arrAttestedAddresses.indexOf(owner_address) === -1` now fails for both public and private payments.

There is no on-chain mechanism analogous to a "grace period" that would let holder A see the change coming and move/withdraw funds first, nor a fallback mechanism to re-attest and unlock the funds if the removed attestor is unwilling or unable to attest again under the new list. This is architecturally identical to the reported JUSD bug class: a privileged party's single action ("delisting"/removing an attestor) instantly and unconditionally zeroes out an unprivileged party's ability to control assets they already legitimately hold, with no window to react.

### Impact Explanation
If an AA (autonomous agent), used e.g. as a DeFi/exchange/vault contract, holds balances of a `spender_attested` asset contributed by users, and the asset's definer narrows the attestor list (removing the attestor that had attested the AA's address or a depositor's address), the AA's balance of that asset — and any user's already-deposited or already-held balance — becomes permanently frozen/unspendable. This is a concrete "AA fund loss or freezing" outcome: funds already locked inside an AA (or in ordinary addresses) can become stuck forever, with no way for the AA logic or the user to react before the freeze takes effect, since the freeze is enforced retroactively by validators at spend time based on the *current* attestor list, not the list in force when the funds were received.

### Likelihood Explanation
Any asset issuer who defines a `spender_attested` asset already has the unilateral, unchecked ability to send `asset_attestors` messages at any time — this requires no special network privilege beyond being the asset's `definer_address`, which is a role reachable by any ordinary asset issuer as covered by the analog scope. No collusion, timing race, or unusual conditions are needed: a definer wanting to "delist" a particular attestor (or replace a compromised/uncooperative attestor) will trigger this freeze as an unavoidable side effect of an otherwise legitimate administrative action, exactly as in the original report's delisting scenario.

### Recommendation
Do not retroactively invalidate a holder's spend rights based solely on the current attestor list. Options include:
- Track, per output/holder, which attestor list (or attestation) was valid at the time the output was created/received, and honor that snapshot for spending purposes, or
- Introduce an explicit grace period after an `asset_attestors` update during which holders attested under the old list may still spend (e.g., transfer to a compliant address or withdraw), or
- Require that spend-time attestor validation accept an attestation valid at any point up to the last-ball MCI in which the funds were received, not merely the currently active list.

### Proof of Concept
1. Definer `D` creates asset `X` with `spender_attested: true` and `attestors: [Attestor1]` (`app: "asset"`), per `validateAssetDefinition` [6](#0-5) .
2. `Attestor1` posts an `attestation` message attesting address `A`.
3. `A` receives a payment of asset `X` (validated per `validatePayment`, passes because `A` is currently attested) [7](#0-6) .
4. Definer `D` posts `asset_attestors` for asset `X` with a new list `[Attestor2]`, dropping `Attestor1` — accepted by `validateAttestorListUpdate` with no restriction [2](#0-1) .
5. Once this unit stabilizes, `readAsset` now returns only `[Attestor2]` as the asset's attestor list [3](#0-2) ; `A` was never attested by `Attestor2`.
6. `A` attempts to spend the asset `X` units received in step 3. Validation now fails with `"owner address is not attested"` [5](#0-4) , even though `A`'s deposit/holding was fully valid and compliant at the time it was received — `A`'s funds are now permanently stuck with no prior warning or grace period.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
