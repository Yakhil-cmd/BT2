### Title
`StatusHandler#process` writes commit statuses without repository scoping, unlike `Commit#refresh_statuses!` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Commit#refresh_statuses!` always fetches statuses scoped to the owning stack via `stack.github_api.statuses(github_repo_name, sha, ...)`, guaranteeing that the GitHub App credentials and repository context match the commit's own stack before calling `create_status_from_github!`. `StatusHandler#process`, however, looks up commits purely `Commit.where(sha: params.sha)` — with no repository/stack filter — and calls `commit.create_status_from_github!(params)` on every match, breaking the repository-scoping invariant every pull-based status path upholds.

### Finding Description
The claimed binding is: `stack.github_repo_name` (context used by `refresh_statuses!`) `==` `repository_name of the incoming webhook payload` (context that should gate `StatusHandler#process`). Tracing the code shows this equality is never enforced on the webhook path.

- `Commit#refresh_statuses!` (`app/models/shipit/commit.rb:156-163`) calls `stack.github_api.statuses(github_repo_name, sha, per_page: 100)`, i.e. it is bound to the calling commit's own stack/repo before any status is written via `create_status_from_github!`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. There is no use of `repository_name`/`stacks` at all.
- The base `Handler` class (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) *does* expose a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, and other handlers (pull_request, push, check_suite, membership) rely on repository-scoped lookups. `StatusHandler` is the outlier that bypasses this and matches on raw `sha` across the entire `commits` table, i.e. across every tenant/stack.
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the payload's signature matches the GitHub App belonging to `repository_owner` extracted from the payload. It does **not** verify that the `sha` in the payload actually belongs to that repository. So a legitimately signed `status` event from an attacker-owned repository (or org) can carry any `sha` value along with attacker-chosen `state`, `description`, `context`, `target_url`.
- Exploit flow: attacker owns/controls a repository R (with the Shipit GitHub App installed, as any GitHub user integrating a public app can do) that shares a commit `sha` with a victim's stack (e.g., common upstream commit, cherry-pick, or fork history — the stated precondition "shared-sha commit in victim stack"). Attacker posts a commit status (e.g., via GitHub's status API, or their CI) on that shared `sha` in their own repo R. GitHub emits a `status` webhook, correctly signed for R's app/org (attacker did not need to know any Shipit secret — GitHub computed the signature itself). `StatusHandler#process` receives this payload and updates **every** `Commit` row across **every stack** whose `sha` matches, including the victim's, via `create_status_from_github!(params)` → `add_status` → `statuses.replicate_from_github!`.
- None of the existing guards catch this: `verify_signature` validates only that request came from a legitimate GitHub App for the attacker's own org, `drop_unhandled_event` only checks event type is registered, `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), and there is no `require_permission!`/stack-membership check anywhere in this path.

### Impact Explanation
An attacker can inject a fabricated commit status (`success`/`failure`/`pending`, arbitrary `context`, `description`, `target_url`) onto a victim stack's commit that happens to share a `sha` with a commit in a repository the attacker controls. Because `Commit#deployable?` and CI-gating logic depend on aggregated status state, this can make an otherwise-unreviewed/failing commit appear to pass CI (`status.success?`) in the victim's stack, potentially unblocking or triggering downstream continuous-delivery logic (`schedule_continuous_delivery`) or misleading operators into deploying/merging. This is a cross-tenant write: a payload authenticated for repository R mutates commit/status state belonging to a stack for a different repository, matching the "Critical" impact category (payload for one repository mutating another's commit/stack, potentially leading to an unauthorized deploy).

### Likelihood Explanation
Preconditions are modest: the attacker needs (a) a repository where the Shipit GitHub App/webhook is installed (attacker-owned, as with any public GitHub App integration) and (b) a commit `sha` shared with a victim stack (common in monorepo forks, cherry-picks, or shared upstream history — explicitly stated as a given precondition). No Shipit secrets, sessions, or API tokens are required; GitHub itself signs the webhook using the app's legitimate webhook secret for the attacker's own repo/org, which `verify_signature` will accept. The action (creating/updating a commit status on their own repository) is entirely within an unprivileged GitHub user's normal capability. This is repeatable against any victim stack sharing a `sha` with any repository the attacker can install/trigger the webhook from.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks for the webhook's own repository, mirroring the `stacks` helper already provided by the base `Handler` class, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the same repository-context binding that `refresh_statuses!` already enforces via `stack.github_api.statuses(github_repo_name, sha, ...)`.

### Proof of Concept
Minitest plan (no live GitHub calls, using Mocha/fixtures):
```ruby
test "refresh_statuses! is scoped to the commit's own stack/repo" do
  stack = shipit_stacks(:shipit)
  commit = stack.commits.last
  stack.github_api.expects(:statuses).with(stack.github_repo_name, commit.sha, per_page: 100).returns([])
  commit.refresh_statuses!
end

test "StatusHandler#process mutates a commit belonging to a different stack (cross-tenant)" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "victim commit")

  attacker_repo_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "attacker-context",
    "repository" => { "full_name" => "attacker/unrelated-repo", "owner" => { "login" => "attacker" } }
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_repo_payload)
  end
  # Demonstrates create_status_from_github! executed on victim_commit
  # with no check that "attacker/unrelated-repo" == victim_stack.github_repo_name
end
```
This shows both sides of the equality: `refresh_statuses!` always requires `stack.github_repo_name == <api call target>`, while `StatusHandler#process` performs no such comparison, allowing an attacker-signed payload for an unrelated repository to mutate the victim's commit status.
