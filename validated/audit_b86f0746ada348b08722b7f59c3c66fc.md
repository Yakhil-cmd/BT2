### Title
Caller-supplied `spoke_id` lets an unprivileged account resolve risk config from a foreign spoke (cross-"namespace" config resolution) - (File: contracts/controller/src/strategies/multiply.rs)

### Summary
The bug class in the reference advisory is a namespace-scoped resource resolved cluster-wide through a caller-controlled `{NAMESPACE}/{NAME}` reference: the operator trusts the annotation's namespace and materializes that resource's spec into the referencing workload. XOXNO Lending has the same shape: a **spoke** is an account's lifetime-bound risk namespace ("Account creation binds the spoke for the account's lifetime" — `docs/reference/architecture.md`), yet strategy entrypoints such as `multiply` take `spoke_id` as a **caller-supplied argument** rather than loading it from the account record, and the Context resolves listing parameters via `get_spoke_asset(spoke_id, hub_asset)` for whichever spoke the caller names.

### Finding Description
- `HubAssetKey { hub_id, asset }` identifies a market (`common/src/types/pool.rs:471-476`); a **spoke** defines which markets an account may use and their LTV / liquidation threshold / bonus. Spoke listings are per-`(spoke_id, hub_asset)` config rows read through `get_spoke_asset` (`contracts/controller/src/storage/spoke.rs`, `contracts/controller/src/config/asset.rs`).
- The test harness calls `ctrl.multiply(&alice, &account, &HARNESS_SPOKE, &collateral, &amount, &debt, &PositionMode::Multiply, …)` (`tests/test-harness/tests/strategy/cross_hub_same_asset_loop.rs:50-61`), confirming `spoke_id` is an argument the caller chooses, analogous to the `{NAMESPACE}/{NAME}` annotation.
- `Context` caches `spoke_usage` / `spoke_config` per invocation (`contracts/controller/src/context.rs:54-56`), and risk parameters for new legs are stamped from the resolved spoke asset (`contracts/controller/src/risk/params.rs`).
- If the controller does not enforce that the supplied `spoke_id` equals the spoke bound at account creation, any user can reference **any** spoke that lists the desired `hub_asset` and have that foreign spoke's `loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` materialized into their own position legs — exactly the cross-namespace disclosure/use pattern: an unprivileged principal causes the system to resolve and apply a resource belonging to a different trust boundary.
- **Uncertainty**: I could not confirm within the available iterations whether `multiply`/`flash_position`/`swap_collateral` validate `spoke_id` against the account's bound spoke before `Context` resolves `get_spoke_asset`. If such an equality check exists (e.g., in `account.rs` or `spoke_usage.rs`), the finding reduces to intended behavior and should be rejected.

### Impact Explanation
An account opened under a restrictive spoke (low LTV, low liquidation threshold) could open `multiply` / `flash_position` / `swap_debt` legs quoting a permissive spoke's parameters, borrowing more than its risk profile allows and stamping weaker liquidation parameters onto its positions. That produces undercollateralized debt — protocol insolvency / theft of supplier funds — if the bound-spoke check is absent.

### Likelihood Explanation
Reachable by any unprivileged address that can create an account and call `multiply` (no privileged role needed — the same prerequisite-free posture as the advisory's "deploy a workload in your own namespace"). Exploitability hinges entirely on whether `spoke_id` is validated against the account's bound spoke, which I could not verify.

### Recommendation
At every entrypoint accepting `spoke_id` (`multiply`, `flash_position`, `swap_collateral`, `swap_debt`, `migrate_from_blend`), load the account's bound spoke from account storage and assert `spoke_id == account.spoke_id` before any `get_spoke_asset` resolution; do not let callers reference foreign spoke config.

### Proof of Concept
Call `controller.multiply(attacker, account_id, foreign_spoke_id, collateral_hub_asset, amount, debt_hub_asset, PositionMode::Multiply, …)` where `foreign_spoke_id` lists the same `hub_asset` with a higher LTV than the account's bound spoke. Observe whether the minted debt leg is stamped with the foreign spoke's risk parameters (per `tests/test-harness/tests/strategy/cross_hub_same_asset_loop.rs:50-65`, the spoke is purely an input argument). If the transaction succeeds with foreign parameters applied, the cross-boundary resolution is confirmed; if it reverts on a bound-spoke check, no vulnerability exists.
