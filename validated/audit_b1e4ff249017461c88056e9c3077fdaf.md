### Title
Webhook signature verification selects the trusted organization's secret from an unverified payload field, letting an attacker impersonate any repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/organization secret to verify a webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the *unverified* JSON body, before the signature has been checked [1](#0-0) . Once the signature is accepted (proving only that *some* known secret was used to sign *this exact byte string*), every registered handler is invoked with the same raw `params`, and those handlers pick the repository to act on from a *different* field of the same untrusted payload: `repository.full_name`, via `Handler#repository_name`/`Handler#stacks` [2](#0-1) . Nothing ties the organization whose secret validated the request to the repository the handler subsequently mutates.

### Finding Description
The binding that should hold is:

`organization_whose_secret_verified(signature) == organization_that_owns(repository_acted_on)`

Before the pull request/request sequence: for a legitimate GitHub-originated webhook, `repository.owner.login` and `repository.full_name` are always consistent (GitHub itself populates both from the same repository object), so the binding trivially holds.

After an attacker-crafted request: an attacker who legitimately administers (or has otherwise learned the `webhook_secret` of) **their own** organization/GitHub App configuration in this multi-tenant Shipit instance can:
1. Build an arbitrary JSON body whose `repository.owner.login` (or `organization.login`) is set to *their own* organization "A" — this makes `WebhooksController#repository_owner` return "A" [3](#0-2) , causing `Shipit.github(organization: 'A')` to select org A's `GitHubApp`, whose `webhook_secret` the attacker knows.
2. Set `repository.full_name` inside that same JSON body to `"OrgB/target-repo"` — a repository belonging to a completely different, unrelated organization "B" configured on the same Shipit instance.
3. Compute a valid `X-Hub-Signature`/`X-Hub-Signature-256` HMAC over the full raw body using org A's secret. `verify_webhook_signature` only checks that the HMAC matches the body using the secret it looked up — it has no way to know the body internally "lies" about which org it belongs to [4](#0-3) .
4. `WebhooksController#create` then dispatches this fully-attacker-controlled `params` to every handler for the event, e.g. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) . Handlers resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` [2](#0-1) , `params.repository.full_name` (pull request handlers) [6](#0-5) , etc. — never re-checking it against the organization whose secret authorized the request.

This lets the attacker drive side effects against Org B's stacks while only ever proving knowledge of Org A's secret: e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the forged branch [7](#0-6) , and pull-request handlers can archive/unarchive review stacks or trigger provisioning for repositories the attacker does not own [8](#0-7) [9](#0-8) .

### Impact Explanation
This crosses a repository/organization trust boundary using credentials the attacker legitimately possesses only for their own tenant. It maps to the "cross-repository writes" / "unauthorized deploy" Critical bucket: an attacker can force sync/archival/unarchival/provisioning actions and downstream state changes (which can cascade into deploys via `stack.sync_github`) on a stack belonging to an organization they were never authorized to touch, without ever learning that organization's real webhook secret, `GITHUB_TOKEN`, or having any GitHub permissions there.

### Likelihood Explanation
Exploitability depends entirely on the deployment being multi-tenant (multiple organizations configured with distinct `webhook_secret`s on one Shipit instance) — this is an explicitly supported, documented configuration (`Shipit.github(organization:)`, per-org config in `github_app.rb`), not a hypothetical misuse. Any tenant admin of one organization is, by design, an "unprivileged attacker" with respect to every other tenant's repositories, and only needs to craft one raw HTTP POST with a self-computed HMAC — no GitHub access, no `ApiClient` token, no session required.

### Recommendation
After verifying the signature, re-derive the organization from the *same* field that was cryptographically bound (or, better, always verify using the app configured for the concrete repository the payload claims to affect) and require that `repository.owner.login`/`organization.login` and `repository.full_name`'s owner segment refer to the same organization that produced a valid signature, rejecting the webhook otherwise. Ideally, resolve the target `Repository`/`Stack` first, look up the `GitHubApp`/secret tied to that specific repository's registered organization, and verify the signature against that, rather than trusting an attacker-supplied field to pick which secret to check against.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` (attacker-controlled, secret `S_A` known to attacker) and `orgb` (victim, secret `S_B` unknown to attacker), each with a `Stack` registered (`orgb/victim-repo` exists in Shipit).
2. Attacker builds a raw JSON body for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefcafefeed0000000000000000000000",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push` and this signature.
5. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `Shipit.github(organization: 'orga')`, verifies successfully using `S_A` (since the attacker signed with `S_A`) [10](#0-9) .
6. `PushHandler#process` resolves `repository_name` = `"orgb/victim-repo"` from `payload.dig('repository', 'full_name')` and calls `stack.sync_github(expected_head_sha: ...)` on `orgb`'s stack [7](#0-6)  — a write against a repository the attacker never had signing authority over.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
