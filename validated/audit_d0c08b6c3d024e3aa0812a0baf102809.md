### Title
`Api::CCMenuController#show` discloses stack build status outside a scoped `ApiClient`'s authorized stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` scopes stack lookups to `current_api_client.stack_id` via its private `stacks`/`stack` helpers, but `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` model, bypassing that authorization boundary entirely. As a result, an `ApiClient` restricted to one stack can fetch CCMenu status (deploy/rollback state) for any other stack in the system.

### Finding Description
The intended binding is `stack.id ∈ {current_api_client.stack_id}` whenever `current_api_client.stack_id?` is true, enforced in the base controller: [1](#0-0) 

`CCMenuController` redefines `stack` and drops the scoping entirely, resolving directly against all stacks: [2](#0-1) 

`show` then renders whatever stack was resolved: [3](#0-2) 

The only guard applied before `show` is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!('read', 'stack')` — a permission-name check against the client's `permissions` array, entirely independent of which stack ID is being requested: [4](#0-3) [5](#0-4) 

So for a scoped client (`stack_id?` true, `stack_id == A`), a request `GET /api/stacks/:owner/:repo-B/branch-B/cc_status.xml?token=<A's token>` (or via Basic Auth) resolves `stack.id == B ≠ A`, `check_permissions!` still passes because it only checks the permission string `read:stack`, and `show` renders `stack.deploys_and_rollbacks.last` for stack B. The binding `stack.id ∈ {current_api_client.stack_id}` is violated: left side is `B`, right side is `{A}`.

Existing guards do not close this gap: `require_permission!` is permission-only, not stack-scoped; the `stacks` scoping mechanism exists but is bypassed by this controller's own `stack` override; and `authenticate_api_client` here is only relaxed to also accept `params[:token]` (in addition to Basic Auth) but still resolves to a real `ApiClient` — the vulnerability is not in authentication but in the missing scope check afterward.

### Impact Explanation
Any request against `Api::CCMenuController#show` with a valid but stack-scoped API token/client discloses build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status) for **any** stack on the instance, not just the one the client was provisioned for. This is a cross-tenant read of stack state that the `stack_id` scoping mechanism was specifically designed to prevent, matching the "unauthenticated/unauthorized read of stack state" High severity category. It is fully repeatable against every stack ID on the instance by iterating `owner/repo/branch` combinations in the URL.

### Likelihood Explanation
Preconditions are minimal and match realistic operation: at least one `ApiClient` scoped to a single stack (a common configuration for CCMenu-style status badges handed out to individual teams), and at least one other stack existing on the same Shipit instance. The attacker only needs a previously-issued CCMenu URL/token for their own scoped stack (which is routinely embedded in public build badges, READMEs, or CI chat notifications) and knowledge/guessing of another stack's `owner/repo/branch`. No secrets, sessions, or GitHub privileges are required — this is directly reachable via `params[:token]` on the query string, as the controller's own `authenticate_api_client` override supports.

### Recommendation
Have `Api::CCMenuController` reuse the base controller's scoped `stacks`/`stack` resolution instead of calling `Stack.from_param!` directly — i.e., remove the private `stack` override in `CCMenuController` (or reimplement it as `stacks.from_param!(params[:stack_id])`) so that `current_api_client.stack_id` scoping from `Api::BaseController#stacks` is honored.

### Proof of Concept
Add to `test/controllers/api/ccmenu_controller_test.rb`:

```ruby
test "a client scoped to one stack cannot fetch CCMenu status for another stack" do
  other_stack = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: "main")
  @client.update!(stack_id: @stack.id) # scope client to @stack only

  get :show, params: { stack_id: other_stack.to_param }

  assert_response :ok # currently passes -- should be :forbidden/:not_found
  assert_equal other_stack.id, assigns(:stack).id
  refute_equal @client.stack_id, assigns(:stack).id
end
```

This asserts the exact binding violation: `assigns(:stack).id == other_stack.id` while `current_api_client.stack_id == @stack.id`, and the response is `200 OK` rather than `403`/`404`.
