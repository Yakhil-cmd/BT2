### Title
PR label can pre-set/shadow a declared deploy `VariableDefinition`'s value before the operator supplies one - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges PR label names (attacker-controlled) into the stack env as `LABEL => "true"` with no check against the deploy spec's declared `VariableDefinition` names. Because `TaskCommands#env` merges `@stack.env` (labels) before `@task.env` (the operator-supplied, `EnvironmentVariables#permit`-filtered value), an attacker's label wins whenever the operator does not explicitly pass a value for that same variable name in the deploy request.

### Finding Description
The claimed binding, expressed as an equality: for a key `K` declared as a `VariableDefinition` in the target branch's `shipit.yml`, the final task env value should satisfy `env[K] == operator_supplied_value_or_default(K)`, never `env[K] == "true"` set unilaterally by a PR label.

Trace:
1. `ReviewStack#env` merges `pull_request.labels` into the env hash as `{LABEL_NAME.upcase => "true"}` with no filtering against any `VariableDefinition` list: [1](#0-0) 
2. `TaskCommands#env` builds the final env in this order: `super` → `.merge(@stack.env)` (labels) → static keys → `.merge(deploy_spec.machine_env)` → `.merge(@task.env)` (last, wins): [2](#0-1) 
3. `@task.env` is set at deploy-creation time via `Stack#build_deploy`, which only stores `filter_deploy_envs(env.to_h)` — i.e., whatever keys the operator/API actually submitted, filtered through `EnvironmentVariables#permit` (which only enforces that no *extra* disallowed keys are present, not that all declared keys are present): [3](#0-2) [4](#0-3) 
4. `DeploysController#deploy_params` only permits the declared variable names as possible keys under `params[:deploy][:env]`; it does not force their presence — if the operator leaves a variable field blank/unsent (or a caller hits the API without including it), the key is simply absent from `@task.env`: [5](#0-4) 
5. `Stack#trigger_task` (task-definition flow) applies `variable.default` only when `variables_with_defaults` (i.e. variables with an explicit `default:` in `shipit.yml`) — for variables without a configured default, and for regular deploys via `build_deploy` (no default application at all), nothing ever overwrites the label-seeded value: [6](#0-5) 

Because of this ordering and the absence of presence-enforcement, an attacker who labels their own PR `safety_disabled` (which upcases to `SAFETY_DISABLED`) sets that key to `"true"` in `@stack.env` at every task/command invocation for that review stack. If the target branch's `shipit.yml` happens to declare a deploy variable named `SAFETY_DISABLED` (an operator-controlled fact, not attacker-controlled) and the operator does not explicitly supply a value for it when triggering the deploy, the attacker's `"true"` value survives into the final `Command`/`PTY.spawn` environment untouched. `EnvironmentVariables#permit` only checks that submitted keys are on the whitelist — it never checks that the whitelist's keys are *not already colonized* by `ReviewStack#env`'s label loop, so this guard does not close the gap.

### Impact Explanation
The attack lets an unprivileged PR author (no Shipit session, no API token) influence the value of an operator-declared deploy variable on their own review-stack deploy, potentially causing steps in `shipit.yml` to branch on `SAFETY_DISABLED`, `SKIP_TESTS`, or similarly named flags and execute commands that would not otherwise run — i.e., "a command running that should not," scoped to the attacker's own review-stack task execution. This is confined to review stacks the attacker's own PR provisions; it does not cross repository or stack boundaries, does not bypass authentication, and does not leak credentials, so it does not rise to the Critical categories (no RCE via forged webhook/auth bypass, no cross-tenant mutation, no secret exfiltration) — it matches the question's own framing of High severity (undermining `deploy_spec.deploy_variables` intent), borderline Critical only if a specific `shipit.yml` step wires that variable to a safety-critical branch.

### Likelihood Explanation
Preconditions: the target repository's `shipit.yml` (trusted, merged branch) must declare a `VariableDefinition` whose `name` collides with an uppercased PR label the attacker can apply to their own PR, review-stacks must be enabled, and the operator must trigger a deploy without explicitly supplying that variable. Attacker cost is trivial (open a PR, add a label they control on their own fork/PR) and fully repeatable across any deploy of that review stack. Likelihood depends heavily on operator/repo config choosing overlapping names, which is plausible for common conventions (e.g., `SKIP_LINT`, `FORCE`, `DEBUG`) but not guaranteed by default.

### Recommendation
In `ReviewStack#env`, exclude label-derived keys that collide with any `VariableDefinition` name declared for the stack's deploy/task/rollback variables (via `cached_deploy_spec.deploy_variables`/`task_definitions`), or namespace label-derived env vars (e.g. prefix with `LABEL_`) so they can never shadow operator-declared variables. Additionally, consider having `EnvironmentVariables#permit`/`filter_deploy_envs` reject or warn when an env key that will later be merged with lower-priority label data isn't explicitly present, to remove ambiguity about override precedence.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/task_commands_test.rb`, out-of-scope path noted only for illustration since this section only requires a test *plan*):
1. Build a `Stack`/`ReviewStack` with a `cached_deploy_spec` whose deploy `variables` includes `{'name' => 'SAFETY_DISABLED'}` (no default).
2. Create/stub a `PullRequest` associated with the stack with `labels` including `"safety_disabled"`.
3. Assert `stack.env['SAFETY_DISABLED'] == 'true'` (label shadowing occurs at the `Stack#env`/`ReviewStack#env` layer) — this is the pre-condition demonstrating the collision.
4. Build a `Task`/`Deploy` via `stack.build_deploy(commit, user, env: {})` (operator supplies no value for `SAFETY_DISABLED`), save it, and construct `TaskCommands.new(task)`.
5. Assert `TaskCommands.new(task).env['SAFETY_DISABLED'] == 'true'` — proving the label value survives to the final task environment despite the operator never having supplied it, i.e. `env['SAFETY_DISABLED'] != operator_supplied_value` (there was none) and instead equals the attacker's label-derived value.
6. Contrast: build a second deploy with `env: {'SAFETY_DISABLED' => 'false'}` explicitly supplied, and assert `TaskCommands.new(task2).env['SAFETY_DISABLED'] == 'false'`, confirming operator-supplied values do override, and isolating the gap to the "operator did not supply a value" case.

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
