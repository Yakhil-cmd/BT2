### Title
Cross-repo status forgery bypasses `MergeRequest#any_status_checks_missing?` via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit(s) to attach a GitHub `status` webhook event to purely by matching `sha` across the entire `commits` table, without scoping to the repository named in the webhook payload. Because `Status::Group`/`StatusChecker` treats any status record attached to a `MergeRequest`'s `head` commit as authoritative regardless of which stack/repository actually produced it, an attacker who owns a repository that shares a commit SHA with a victim stack (e.g., a fork with unmodified upstream history) can post a real, correctly-signed CI status for their own repo and have it attached to the victim's commit, satisfying `any_status_checks_missing?` and unblocking `reject_unless_mergeable!`.

### Finding Description
The broken binding: the repository whose GitHub App signature authenticated the webhook (`repository_owner` from `payload.dig('repository','owner','login')`, verified in `Shipit::WebhooksController#verify_signature`) must equal the repository that owns the `MergeRequest`/`Commit` the status is attached to. In `StatusHandler`, these are **not** the same thing.

`app/controllers/shipit/webhooks_controller.rb:24-30` verifies the webhook signature only against the organization derived from `repository_owner` in the payload — this proves the payload genuinely came from GitHub for *that* org's app installation, but proves nothing about which repository's commits the `sha` field should be attached to.

The base `Webhooks::Handlers::Handler` class provides a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, i.e., the repository actually named in the payload. Other handlers (`push_handler.rb`, `pull_request/*_handler.rb`, `check_suite_handler.rb`) use this scoping.

`StatusHandler#process` does not:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This queries `Commit.where(sha: params.sha)` globally, with no `stacks`/repository filter, then calls `commit.create_status_from_github!(params)` on every matching commit in the whole install — including commits belonging to stacks other than the one that produced the webhook. `create_status_from_github!` creates the `Status` using `commit.stack_id` (the victim's stack), not the originating repo [2](#0-1) , and `Status.replicate_from_github!` blindly persists the attacker-controlled `state`/`context`/`description` [3](#0-2) .

`MergeRequest::StatusChecker < Status::Group` computes `missing?` from `required_statuses - visible_statuses.map(&:context)` [4](#0-3) , and `reject_unless_mergeable!` rejects with `ci_missing` only if `any_status_checks_missing?` is true [5](#0-4) , `any_status_checks_missing?` delegates directly to `StatusChecker#missing?` on `head.statuses_and_check_runs` [6](#0-5) . Once a `Status` record with the exact missing required `context` and `state: 'success'` exists on the victim's `head` commit — regardless of which repository actually created it — `missing?` becomes false and, on the next `ProcessMergeRequestsJob` run, `all_status_checks_passed?` can become true, allowing `merge!` to fire.

**Exploit flow:**
1. Attacker forks (or otherwise controls a repository sharing commit history/SHAs with) the victim repository, and has that attacker-owned repository connected to the same Shipit instance (or any repository for which a `Shipit.github(organization:)` GitHub App is configured) so genuine, correctly signed `status` webhooks can be produced for it.
2. Attacker's own CI (or a manual call to GitHub's Statuses API on their fork) posts a status for a commit SHA that is shared with the victim stack (e.g., an unmodified base/merge-base commit, or a PR from a fork whose head commit SHA is identical in both repos), using the exact `context` string the victim stack requires (e.g., `ci/circle`) and `state: success`.
3. GitHub sends a genuinely signed webhook to Shipit's `POST /webhooks` with `X-Github-Event: status`. `verify_signature` passes because it is validated against the attacker's own organization, not the victim's.
4. `StatusHandler#process` finds `Commit.where(sha: <shared sha>)`, which now includes the victim stack's `Commit`, and calls `create_status_from_github!(params)` on it — creating a `Status` row scoped to the victim's `stack_id` (`commit.stack.enable_ci_on_stack`, `stack_id` on the record) with the attacker-supplied context/state.
5. The victim `MergeRequest`'s `any_status_checks_missing?` now returns `false` for that context; `reject_unless_mergeable!` no longer rejects for `ci_missing`.
6. On the next `ProcessMergeRequestsJob` cycle, if no other rejection reason applies, `all_status_checks_passed?` becomes true and `merge!` executes `stack.github_api.merge_pull_request` [7](#0-6) , merging the victim's pull request without the required CI having actually run/passed on the victim's own commit content.

**Why existing guards don't catch this:** `verify_signature` authenticates the sender org, not the sha-to-repository binding; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape (`sha`, `state`, `context`, etc. are present and typed) [8](#0-7) , not ownership; the `stacks`/`Repository.from_github_repo_name` scoping mechanism exists in the codebase precisely for this purpose but `StatusHandler` never calls it.

### Impact Explanation
An unauthorized merge of a pull request is enabled for a repository the attacker does not own, by forging (via a benign, correctly-signed event on the attacker's own repository) a *missing* required CI status onto the victim's commit. This is a cross-repository payload mutating another repository's merge-eligibility state, matching the "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized merge" category. It is repeatable against any victim stack sharing a commit SHA with any repository the attacker controls (most naturally, any fork of the victim repo where the shared base/PR-head commits haven't diverged), and does not require any Shipit credentials, session, or GitHub App secret — only ordinary control of one's own GitHub repository/fork and its CI reporting.

### Likelihood Explanation
Feasibility is moderate-to-high in the specific but common scenario of shared commit SHAs across repositories (forks, mirrors, or PR branches where the head commit is byte-identical and thus SHA-identical across the fork and any tracked stack). The attacker needs: (a) a repository connected via GitHub App to Shipit's webhook pipeline for signature verification to succeed for their own org, and (b) a commit SHA that exists in both their own repo and the victim's tracked stack with a matching `sha` value — which occurs naturally whenever a PR's head commit is unmodified between fork and origin, or when both repos share ancestor commits. No secrets are needed; the attacker only needs the ability to trigger a real GitHub `status` event on their own repository (pushing a commit and letting their CI report a status, or directly using the GitHub Statuses API on their own repo) with an attacker-chosen `context`/`state`.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring the `stacks` helper used by other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a `status` event can only create/update `Status` records for commits belonging to stacks whose tracked repository matches `payload.dig('repository', 'full_name')`, closing the cross-repo SHA-collision path.

### Proof of Concept
Add a minitest (e.g., in `test/models/shipit/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`) with:
1. Two stacks/repositories, `victim_stack` (`acme/victim`) and `attacker_stack` (`attacker/evil`), each with a `Commit` sharing the identical `sha` value (simulating a forked/shared commit).
2. `victim_stack.cached_deploy_spec` stubbed so `merge_request_required_statuses` returns `['ci/circle']`, and the victim's `MergeRequest` `head` commit has no `ci/circle` status — assert `merge_request.any_status_checks_missing?` is `true` and `merge_request.reject_unless_mergeable!` rejects with `'ci_missing'`.
3. POST a `status` webhook payload to `WebhooksController#create` with `X-Github-Event: status`, `repository.full_name` = `attacker/evil`, `sha` = the shared sha, `context` = `ci/circle`, `state` = `success`, with `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (or stubbing `verify_webhook_signature`) to simulate a genuinely signed webhook from the attacker's own org.
4. Reload `victim_stack`'s commit/`merge_request` and assert `victim_commit.statuses.where(context: 'ci/circle').exists?` is now `true` even though the request's `repository.full_name` was `attacker/evil`, not `acme/victim` — demonstrating the binding `payload.repository.full_name == commit.stack.repository.full_name` does not hold.
5. Assert `merge_request.any_status_checks_missing?` is now `false` and `merge_request.reject_unless_mergeable!` returns `false` (no `ci_missing` rejection), confirming the merge path is unblocked purely by the attacker's own webhook.
