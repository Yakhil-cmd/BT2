This confirms the reported vulnerability. The existing test suite in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (lines 159-172, "create stacks for repos what prevent_with_label when label is absent") only sets `provisioning_behavior` and `provisioning_label_name` via `configure_provisioning_behavior` (which defaults `provisioning_enabled: true`), so it never exercises the `review_stacks_enabled: false` case — meaning this exact bypass is untested.

### Title
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` ignores `review_stacks_enabled` for `prevent_with_label` repositories, provisioning stacks despite explicit opt-out - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines three clauses with `&&`/`||` such that only the `allow_all` clause is gated by `repository.review_stacks_enabled` due to Ruby operator precedence; the `prevent_with_label` clause is evaluated independently of that flag. Consequently, an unprivileged attacker who opens a PR with zero labels against a repository configured with `provisioning_behavior: 'prevent_with_label'` and `review_stacks_enabled: false` triggers automatic review-stack provisioning, bypassing the operator's explicit opt-out.

### Finding Description
The broken binding: the intended invariant is `provision? == (review_stacks_enabled && provisioning_behavior_matches?)`, but the actual code at [1](#0-0) 
is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` binds tighter than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Only the first disjunct is gated by `review_stacks_enabled`; the third disjunct (`prevent_with_label`) is fully independent of that flag.

Call path: webhook `pull_request` "opened" event → `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` → true (because `provisioning_behavior_prevent_with_label?` is true and PR has no labels, so `!pull_request_has_provisioning_label?` is true) → `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` creates and enqueues a review stack, per [2](#0-1) .

Attacker request: open a plain pull request (no labels) against a repository whose owner has explicitly disabled review stacks (`review_stacks_enabled = false`) but left `provisioning_behavior = 'prevent_with_label'`. No signature bypass or privilege is needed — this is a normal webhook delivered for an ordinary PR-open action, and the divergence occurs entirely in application logic after the webhook is authenticated as genuinely originating from that repository.

Existing guards (signature verification, `ExplicitParameters` schema, etc.) do not protect against this because they only validate the webhook's authenticity/shape, not the business logic; the flaw is purely in `provision?`'s precedence. This is confirmed by comparison: sibling handlers `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` at the top level as a separate top-level condition before evaluating `archive?`/`unarchive?`, per [3](#0-2) 
— but `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` (same bug pattern) do not, per [4](#0-3) .

### Impact Explanation
An attacker (any PR opener) can force creation and provisioning of a `Shipit::ReviewStack` — including whatever provisioning side effects (`ReviewStackProvisioningQueue`, `ProvisioningHandler` hooks) that entails — on a repository where the operator explicitly turned `review_stacks_enabled` off. This is a record/resource being created for a repository under settings that were meant to prevent it, i.e., an unauthorized state mutation triggered purely by webhook content the attacker controls (label absence). It is repeatable against any repository misconfigured this way (any repo with `prevent_with_label` + `review_stacks_enabled: false`), simply by opening new PRs. This matches "unauthorized deploy/mutation" territory but is scoped to provisioning a review stack rather than a deploy — the question specifies Critical impact, but per the provided severity taxonomy this is best characterized as unauthorized creation of a stack resource for a repository whose operator opted out, which is a logic/authorization-flag bypass at the provisioning layer.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior: 'prevent_with_label'` and `review_stacks_enabled: false` set by its operator — a plausible but non-default configuration combination that isn't rejected by any model validation (no validation ties `provisioning_behavior` to `review_stacks_enabled`). Attacker cost is trivial: open a normal PR with no labels. Fully repeatable, no rate limiting relevant, deterministic based on the code path traced above.

### Recommendation
Fix operator precedence in `provision?` (and the identical bug in `ReopenedHandler#unarchive?`) by parenthesizing the `review_stacks_enabled` check across all clauses, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix this assertion fails (a stack is created); after applying the recommended fix, it passes, demonstrating `review_stacks_enabled == false` is honored for the `prevent_with_label` branch.
