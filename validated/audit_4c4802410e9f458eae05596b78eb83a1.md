### Title
Unauthenticated `X-Shipit-User` header lets any API token holder attribute deploys/tasks to an arbitrary user - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The Gearbox report's root cause is a **trust binding broken by a stale/unverified field being trusted after the fact**: `takeOut()` hands out a credit account without clearing the pointer that was established under a *previous* trust context, so a later consumer (`returnCreditAccount`) inherits state it never validated. The generalizable pattern for this scan is: *"a value acted upon by privileged logic was never actually verified/covered by the mechanism that is supposed to establish trust for it."*

In this engine, `Api::BaseController#identify_user` implements exactly this pattern: the `current_user` used to attribute deploys, task triggers, and aborts is derived from a client-supplied HTTP header (`X-Shipit-User`) that is **never covered by the `ApiClient` authentication token's signature**, unlike the GitHub App webhook signature which cryptographically covers the whole payload it acts on.

### Finding Description
`ApiClient` authentication is a bearer token verified with `Shipit::SimpleMessageVerifier` — it authenticates *the client*, nothing else: [1](#0-0) 

`Api::BaseController#authenticate_api_client` validates that token and sets `@current_api_client`: [2](#0-1) 

However, `current_user` — the identity attributed to the action (deploy author, task trigger user, task-abort actor) — is derived from a completely separate, unauthenticated field: the `X-Shipit-User` request header, which is simply looked up by `login` with no cryptographic binding to the presented `ApiClient` token: [3](#0-2) 

This `current_user` is then passed directly into privileged, mutating operations: [4](#0-3) [5](#0-4) 

The equality that should hold is: `identity that authorized the request == identity attributed to the resulting record`. Instead, the engine binds only `token → ApiClient (creator)` and then separately, unauthenticated, binds `header → User`. Any holder of a valid `deploy:stack` `ApiClient` token (which is a fixed shared bearer secret per client, e.g., stored in CI config) can set `X-Shipit-User` to the login of any existing Shipit `User` (including privileged approvers, team leads, etc.) and every `Deploy`, `Task`, `abort!` will record that arbitrary user as the actor — this can also cause deploys/tasks to bypass concurrency/user-based safety checks (e.g. `Task::ConcurrentTaskRunning` per-user gating, `SHIPIT_USER`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` env vars used in `lib/shipit/task_commands.rb`, and audit trails used to decide "who did this").

This is directly analogous to the reported bug class: a downstream consumer (`Deploy`/`Task` creation, git commit attribution, audit log) trusts a field (`current_user`/attributed login) that was never actually covered by the verification step (the `ApiClient` token check) that is supposed to establish who is allowed to act.

### Impact Explanation
Any actor holding a valid `deploy:stack` (or `read:stack`/task-trigger) `ApiClient` token — which is a long-lived, often widely shared CI secret rather than a personal credential — can forge the identity attributed to deploys, task triggers, and task aborts to any existing `Shipit::User` login by simply setting the `X-Shipit-User` header. This falsifies the audit trail of who triggered a production deploy or rollback, and the forged identity is propagated into `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`/`SHIPIT_USER` used by deploy scripts (`lib/shipit/task_commands.rb`), enabling an unauthorized deploy/rollback to be falsely attributed to a legitimate, possibly higher-trust user. This matches the "unauthorized deploy or rollback" / audit-integrity impact category for a credential/authentication boundary crossing.

### Likelihood Explanation
Any party in possession of a valid `ApiClient` token with `deploy:stack`/`read:stack`/`write:stack` permission — which is expected to exist in CI pipelines, integrations, and other semi-trusted automation, i.e., not a single highly privileged secret — can exploit this with a single crafted HTTP header on an otherwise legitimate, properly authenticated API call. No additional access, session, or GitHub credentials are required beyond the token that is already needed to call the endpoint.

### Recommendation
Do not derive `current_user` for attribution purposes from an unauthenticated, client-controlled header. Bind the attributed user to the authenticated `ApiClient` (e.g., always attribute the action to `current_api_client.creator`), or require an additional signed/authenticated assertion (e.g., verify the `X-Shipit-User` claim via a scoped, per-user signed token, or restrict use of the header to `ApiClient`s explicitly marked as "impersonation-capable" with `check_permissions!` covering that specific login). At minimum, the accepted logins should be scoped to `current_api_client.creator` or an explicit allow-list stored on the `ApiClient` record, verified server-side rather than trusted from request headers.

### Proof of Concept
1. Obtain any valid `ApiClient` token with `deploy:stack` permission (e.g., a CI system's shared Shipit token).
2. Send:
```
POST /api/stacks/<owner>/<repo>/<env>/deploys
Authorization: Basic <base64(--:<token>)>
X-Shipit-User: victim-privileged-login
Content-Type: application/json

{ "sha": "<commit-sha>" }
```
3. Observe (via `Api::DeploysController#create` → `Stack#trigger_deploy`) that the resulting `Deploy` record's `user` is `victim-privileged-login`'s `User`, and that `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`/`SHIPIT_USER` env vars set for the deploy scripts (`lib/shipit/task_commands.rb#env`) reflect the impersonated identity — with no verification that the token owner is or is authorized to act as that user.
