### Title
CCMenu API token scope bypass allows reading any stack's build status regardless of `ApiClient.stack_id` binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-resolution method used by `Shipit::Api::BaseController` in a way that discards the per-token stack scoping (`ApiClient#stack_id`). An `ApiClient` token that is only supposed to authorize `read:stack` for one specific stack can be replayed against `Api::CCMenuController#show` with a different `stack_id` parameter and will successfully return that other stack's deploy/build status, in violation of the stack-scoping binding the rest of the API enforces.

### Finding Description
`Shipit::Api::BaseController` is designed so that an `ApiClient` scoped to a specific stack can only see that stack: [1](#0-0) 

`current_api_client.stack_id?` gates the `stacks` relation, and `stack` is derived from that scoped relation (`stacks.from_param!`). This is the mechanism that lets a limited-privilege token created for stack A only ever resolve stack A. This scoping is exercised and relied upon elsewhere in the codebase (`test/controllers/api/stacks_controller_test.rb: "an api client scoped to a stack will only see that one stack"`).

`Api::CCMenuController`, however, overrides both `stack` and `authenticate_api_client`: [2](#0-1) 

Instead of using `stacks.from_param!(params[:stack_id])` (which enforces `current_api_client.stack_id`), it calls `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table. `require_permission :read, :stack` (declared at the top of the controller) only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` — it never checks *which* stack the permission applies to: [3](#0-2) 

So the invariant that should hold is:
`stack authorized by ApiClient.stack_id == stack touched by the request`

For every other API endpoint under `Api::BaseController` this equality holds because `stack`/`stacks` is scoped. For `CCMenuController#show`, the equality is broken: the token authorizes stack A (`stack_id == A`), but the request can make it touch any stack B by simply passing `params[:stack_id] = B`.

### Impact Explanation
This is an authorization boundary break scoped to an `ApiClient` token with `read:stack` permission for a single stack. Such a token can be legitimately handed to lower-trust integrations (e.g., a CI dashboard, a CCMenu client, as generated by `CCMenuUrlController#fetch`, or a scoped token created via the stack settings page/`ApiClientsController`) that are meant to see build status of only one stack. Using the CCMenu endpoint, the holder of that limited token can read the deploy/task/build status of any other stack in the Shipit installation, including private, unrelated repositories' stacks — an unauthenticated-relative-to-scope disclosure of stack/task state, matching the "High: unauthenticated read of stack state" impact category, since it grants read access to state the token was never authorized to see.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack`-scoped `ApiClient` token (these tokens are routinely distributed to third parties/CI systems for CCMenu integration, and the token itself is visible in the CCMenu URL per `CCMenuUrlController#fetch`), plus knowledge or guessing of another stack's `to_param` (owner/repo/environment), which is often discoverable (public repo names, predictable environment names). No repository write access or privileged account is needed — only a legitimately-issued, narrowly-scoped read token, satisfying the "unprivileged attacker" and "no elevated credential" requirements.

### Recommendation
Make `Api::CCMenuController#stack` honor the same scoping as the base controller, e.g. reuse `stacks.from_param!(params[:stack_id])` (the `stacks` method from `Api::BaseController`, which already filters by `current_api_client.stack_id`) instead of querying `Stack` directly. Alternatively, explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id` before rendering the CCMenu XML.

### Proof of Concept
1. As an authorized Shipit user, create (or have created for you) a stack-scoped `ApiClient` for Stack A with permission `read:stack` (e.g., via `CCMenuUrlController#fetch` for Stack A, or via the stack settings API-client UI), yielding a token `T` bound to `stack_id = A`.
2. Confirm normal API scoping: `GET /api/stacks` with Basic Auth token `T` only returns Stack A (per `test/controllers/api/stacks_controller_test.rb` behavior "an api client scoped to a stack will only see that one stack").
3. Call the CCMenu endpoint for a different stack B that `T` is not scoped to:
   `GET /api/:B_owner/:B_repo/:B_env/ccmenu.xml?token=T`
4. Observe that `Api::CCMenuController#show` returns Stack B's project/build status XML successfully, because `stack` resolves via `Stack.from_param!` (unscoped) rather than the token-scoped `stacks` relation — demonstrating the scope bypass.
