## Title
Arbiter/Prosaic contract acceptance signature is not bound to the contract hash, allowing signature replay across multiple contracts with the same peer — ([File: arbiter_contract.js](arbiter_contract.js))

### Summary
The `Gateway.sol` bug is a signed meta-transaction whose hash excludes the target `account`, so a signature made for one account can be replayed against another account owned by the same signer. The exact same class of flaw exists in ocore's arbiter/prosaic contract flow: when a peer "accepts" a contract, they produce a `signed_message` package whose payload is just the human-readable contract **title** string, not the contract's unique hash. On the receiving side, the offerer validates this signature only by comparing it against `objContract.title`, never against `objContract.hash`. Because the same peer can be a counterparty on multiple distinct contracts (different amounts, assets, dates, arbiter) that happen to share the same title text, a single signature produced for one contract's acceptance is valid input for `validateSignedMessage()` against any other contract with an identical title from that same peer.

### Finding Description
`respond()` in [1](#0-0)  sends an `arbiter_contract_response` message containing `signed_message` (a base64-encoded signed package produced by `signed_message.signMessage`) whose plaintext is presumably the contract's title, and this is verified on the offerer's device in `wallet.js`: [2](#0-1) 

The check is:
```
signed_message.validateSignedMessage(db, objSignedMessage, objContract.peer_address, function(err) {
    if (err || objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != objContract.title)
        return callbacks.ifError("wrong contract signature");
    processResponse(objSignedMessage);
});
```
`validateSignedMessage` (in `signed_message.js`) proves only that `objSignedMessage.authors[0].address` correctly signed `objSignedMessage.signed_message` — it has no notion of "which contract" this applies to; that binding is entirely the caller's responsibility [3](#0-2) . The caller binds it only via a **string equality check against the contract title**, not the contract hash. The actual unique identifier of a contract, `getHash()`/`getHashSrc()`, incorporates title, text, creation_date, addresses, arbiter, amount, and asset [4](#0-3)  — but this hash is never included in what the peer signs, nor checked during acceptance validation. Only `objContract.hash` (used to look up the contract row via `getByHash`) ties the response to a specific contract; the actual authenticity check ignores it.

The exact same pattern (comparing `signed_message` to `objContract.title`, no hash binding) is used for `prosaic_contract_response` [5](#0-4) .

This mirrors the reported `Gateway.sol` flaw precisely: the signed payload lacks a field that uniquely scopes it to one "account" (here, one contract instance), so a signature obtained for account/contract A is valid for account/contract B as long as both share the field that *is* checked (title).

### Impact Explanation
An offerer (a malicious or compromised counterparty device — reachable as an ordinary paired device sending crafted `arbiter_contract_offer`/`arbiter_contract_response` messages, no special privilege required) can create multiple contract offers to the same victim peer using identical `title` text but different `text`, `amount`, `asset`, or `arbiter_address`. If the victim ever validly signs an acceptance for one such contract (an ordinary, expected user action), the offerer can replay that same `signed_message` to force-accept any other pending contract with the same title against that peer — moving that contract's status to `accepted`, which triggers creation of the shared address and locking of funds (`CHARGE_AMOUNT`, and later the actual contract sum) per `createSharedAddressAndPostUnit()` [6](#0-5) , without the peer's actual consent to the terms of that specific contract. This can lead to funds being locked into or paid out under terms the victim never agreed to (fund loss / spending under an attacker-chosen contract), which the AA/DAG then honors as a validly-signed contract acceptance.

### Likelihood Explanation
The attacker only needs to be a paired device correspondent capable of sending contract offers to the victim (a normal capability of any peer in this feature) and to get the victim to accept at least one contract offer with a chosen, reused title. Titles are user/attacker-supplied free text with no uniqueness requirement, so the attacker fully controls the collision. This does not require compromising any node, hub, or private key — it is purely a client-message-handling logic flaw, matching allowed scope ("wallet and contract message handling").

### Recommendation
Bind the signed acceptance message to the specific contract instance instead of (or in addition to) the human-readable title — e.g., sign `objContract.hash` (the value returned by `getHash()`, which already incorporates title, text, amount, asset, dates, and addresses) rather than `objContract.title`, and change the verification in `wallet.js` to compare `objSignedMessage.signed_message` against `objContract.hash`. Apply the same fix to both the `arbiter_contract_response` and `prosaic_contract_response` handlers.

### Proof of Concept
1. Attacker (offerer) sends victim two `arbiter_contract_offer` messages with `title: "Service Agreement"` but different `amount`/`text`/`asset` — Contract A (amount=100) and Contract B (amount=100000), each getting distinct `hash` via `getHash()`.
2. Victim inspects and accepts Contract A only; their wallet calls `respond(hashA, "accepted", signedMessageBase64, signer, cb)`, producing a `signed_message` package whose `signed_message` field equals `"Service Agreement"`, signed by the victim's `peer_address` key [1](#0-0) .
3. Attacker intercepts/reuses this `signed_message` payload and sends an `arbiter_contract_response` with `hash: hashB, status: "accepted", signed_message: <same payload>` to the victim's own device (or simply already has it, since it was addressed to the offerer/attacker in the first place).
4. Victim's device processes the response for Contract B: `arbiter_contract.getByHash(hashB, ...)` loads Contract B, and validation only checks `objSignedMessage.signed_message != objContract.title` — which passes because both A and B share `title: "Service Agreement"` — and `objSignedMessage.authors[0].address !== objContract.peer_address`, which also passes (same peer) [7](#0-6) .
5. Contract B is marked `accepted` without the victim ever consenting to its (much larger) `amount`, and proceeds to shared-address creation and fund-locking under Contract B's terms.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
