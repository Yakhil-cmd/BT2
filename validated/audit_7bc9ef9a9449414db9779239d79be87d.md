## Title
Cross-Organization Webhook Forgery via Unbound `repository.owner.login` (Signature Selection) vs. Global `sha`-Based Commit Lookup — Unauthorized Status Injection / Deploy Trigger - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The reported bug class is a rounding error that lets an attacker manipulate an exchange-rate state that a later, security-relevant calculation trusts without re-validating consistency with the original deposit. The structural analog in Shipit is that `WebhooksController#verify_signature` selects **which organization's secret to check** using one payload field (`repository.owner.login` / `organization.login`), while downstream handlers (notably `StatusHandler`) act on a **completely different, unbound field** (`sha`, matched globally across all stacks) without re-validating that the acting organization actually owns the resource being mutated.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against purely from attacker-supplied JSON, before the signature has been verified: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when the selected organization has no configured `webhook_secret` (documented as *optional* in `docs/setup.md`): [3](#0-2) 

Shipit explicitly supports hosting **multiple GitHub organizations** from one instance, each with its own independent `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`). If any one configured organization is left without a `webhook_secret` (allowed by design), `verify_signature` will accept **any** payload claiming that org as `repository.owner.login`/`organization.login`, with **zero** authentication.

Once past `verify_signature`, event handlers use *other, independently-controlled* payload fields to decide what to mutate. `StatusHandler` is the sharpest example — it resolves the target purely by commit SHA, with **no repository/organization scoping at all**: [4](#0-3) 

Compare this to the generic `Handler#stacks` used by other handlers, which at least scopes by `repository.full_name`: [5](#0-4) 

`StatusHandler` does not use this scoping at all — `Commit.where(sha: params.sha)` matches commits belonging to **any stack**, tracked under **any repository/organization** known to this Shipit instance, and unconditionally writes attacker-controlled `state`/`context`/`description` via `create_status_from_github!`.

**The broken binding, stated as an equality that should hold but doesn't:**
`organization authenticated by verify_signature (repository.owner.login)` == `organization owning the Commit/stack mutated by the handler (sha's actual stack.repository)`

Before the attack: a victim organization "SecureOrg" has `webhook_secret` configured; its stacks and commits are only mutable via correctly-signed SecureOrg webhooks.
After the attack: an attacker who knows of any other organization on the same instance configured *without* a webhook secret ("WeakOrg") can submit `X-Github-Event: status` with `repository.owner.login = "WeakOrg"` (satisfying `verify_signature` unconditionally) but `sha` equal to a real, publicly-known commit SHA belonging to SecureOrg's tracked stack — and `StatusHandler` will happily create/overwrite a `Status` for that commit, because it never checks that the commit's owning repository matches the authenticated organization.

### Impact Explanation
Forged/faked commit statuses feed directly into `required_statuses`/`blocking_statuses` deploy-gating logic (`Shipit::DeploySpec#required_statuses`, `#blocking_statuses`) and into `ci.require`d checks that `Stack#schedule_continuous_delivery`/`ContinuousDeliveryJob` rely on before auto-deploying. An attacker who can inject a fabricated "success" status for a commit in a stack they do not control can cause an **unauthorized deploy** to be triggered for that stack (continuous delivery) or unblock a human-triggered deploy that should have been blocked by real CI — a cross-organization/cross-repository write of state that controls production deployments, without ever possessing that organization's webhook secret, an `ApiClient` token, or a Shipit session.

### Likelihood Explanation
Exploitability requires only: (1) the shared Shipit instance to host at least one organization without a configured `webhook_secret` — explicitly documented and supported as an optional configuration (`docs/setup.md`), and (2) knowledge of a target commit SHA, which is not secret (visible via GitHub, or via Shipit's own public commit/API endpoints). No privileged credentials, session, or webhook secret for the target organization are needed — the entire premise of the bug is an *unprivileged, unauthenticated* HTTP POST to `/webhooks`.

### Recommendation
- In `StatusHandler` (and any other handler resolving records without going through `Handler#stacks`), require and validate `payload.dig('repository', 'full_name')` and confirm its owning organization matches the organization used in `verify_signature`, scoping the `Commit` lookup to stacks whose repository belongs to that verified organization.
- In `WebhooksController#verify_signature`, treat a missing `webhook_secret` as a hard misconfiguration to warn/reject on, rather than silently returning `true` (bypassing verification) — at minimum, never let payload-declared organization selection with a blank secret validate events referencing resources under a *different*, secret-protected organization.

### Proof of Concept
1. Shipit instance configured for two orgs, per `docs/setup.md`'s multi-org example: `SecureOrg` (with `webhook_secret`) and `WeakOrg` (no `webhook_secret` set).
2. Attacker identifies a commit SHA `S` currently tracked by a stack under `SecureOrg/some-repo` (e.g., from the public GitHub repo or Shipit's own commit list).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "WeakOrg" }, "full_name": "WeakOrg/unrelated-repo" }
}
```
No `X-Hub-Signature` needed, since `Shipit.github(organization: "WeakOrg").verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb#76-83`).
4. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which runs `Commit.where(sha: "S")` — matching the commit in `SecureOrg`'s stack — and creates a `Status` with `state: "success"` for it, regardless of the fact the request was "authenticated" only for `WeakOrg`.
5. If that `SecureOrg` stack has `continuous_deployment: true` and this was the last required blocking status, `ContinuousDeliveryJob`/`Stack#schedule_continuous_delivery` can now deploy the commit, an unauthorized deploy triggered purely by an unauthenticated forged webhook event.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
