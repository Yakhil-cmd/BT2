### Title
Webhook signature verification selects the GitHub App/secret by an unauthenticated `organization`/`repository.owner.login` field, while handlers act on a different, independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, the `WebhooksController#verify_signature` chooses which GitHub App (and therefore which HMAC `webhook_secret`) to validate an incoming webhook against based on `repository.owner.login` (or `organization.login`) pulled straight out of the *unauthenticated* JSON body. Once the signature check passes for that org, the actual webhook handler (`Shipit::Webhooks::Handlers::Handler#stacks` / `PushHandler#process`) locates the target repository/stack using a completely different field, `repository.full_name`, taken from the same attacker-supplied body. Because the field used to select the verification secret and the field used to select the write target are independent and both attacker-controlled, an org boundary that authenticates a request is never actually bound to the org/repo whose stack gets mutated.

### Finding Description
`Shipit.github(organization: repository_owner)` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-30, 59-62) resolves the `GitHubApp` (and its `webhook_secret`) using: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value comes straight from the raw JSON body (`params = JSON.parse(request.raw_post)`), before any cryptographic authentication has occurred — it is *used to select* which secret performs the authentication, not something the authentication protects.

Once `verify_signature` passes (HMAC-SHA1 over the raw body using the secret associated with whatever org name is in `repository.owner.login`), `create` dispatches the same raw `params` to the registered handler: [3](#0-2) 

The handler base class then determines which `Stack`/`Repository` to mutate using a *different* field, `repository.full_name`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

And `PushHandler#process` uses this to run `stack.sync_github(expected_head_sha: params.after)` for every matching stack: [5](#0-4) 

Because `Shipit.github_app_config`/`github` config in multi-org mode (`lib/shipit.rb`, `github_app_config`) keys secrets by organization login, and each org owner independently knows/controls their own app's `webhook_secret` (they created the GitHub App), the equality that should hold is:

`organization whose secret authenticated the request == organization that owns the repository being written to`

In the current code this equality is never enforced — `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the write target) are two independent, attacker-supplied strings in the same JSON body, and nothing ties them together.

### Impact Explanation
Any party who legitimately controls one configured GitHub organization's webhook secret (i.e., is an admin of any org that has installed the Shipit GitHub App, which is a normal, low-privilege position relative to *other* orgs on the same Shipit instance) can compute a valid HMAC signature for a forged POST body. They can set `repository.owner.login` to their own org (so `verify_signature` succeeds using their known secret) while setting `repository.full_name`, `ref`, and `after` to point at a *different* organization's/repository's stack. This directly drives `stack.sync_github(expected_head_sha: ...)` on a stack that belongs to a repository the attacker does not control, i.e. a cross-repository / cross-organization write triggered without the target org's secret ever being checked. This satisfies the "Critical: cross-repository writes" impact bar defined for this engagement.

### Likelihood Explanation
Exploitation requires the attacker to legitimately hold a valid `webhook_secret` for *any* one organization configured in the same multi-tenant Shipit instance — a realistic scenario for shared/hosted Shipit deployments serving multiple organizations, as explicitly documented in `docs/setup.md` under "Using Multiple Github Applications." No GitHub session, `ApiClient` token, or repository write access on the *victim* org is needed; only knowledge of one's own org's webhook secret and the ability to POST directly to `/webhooks` (bypassing GitHub's delivery infrastructure entirely, since Shipit performs no other origin check).

### Recommendation
Bind the field used to select the verification secret to the same field used to determine the write target: verify the webhook against the secret for the organization derived from `repository.full_name`'s owner (or explicitly cross-check that `repository.owner.login` matches the owner segment of `repository.full_name`) before dispatching to handlers, and reject the request if they disagree.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations, `attacker-org` and `victim-org`, each with their own GitHub App and `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications").
2. As an admin of `attacker-org`, retrieve `attacker-org`'s `webhook_secret` from the GitHub App settings page (legitimate access to your own org's app).
3. Craft a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>`.
5. POST directly to `/webhooks` with header `X-Github-Event: push` and the crafted body/signature.
6. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against `attacker-org`'s secret [1](#0-0) .
7. `PushHandler#process` uses `repository.full_name` (`victim-org/victim-repo`) to look up stacks and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [5](#0-4) [4](#0-3) , without `victim-org`'s webhook secret ever being validated.
