### Title
Non-transferrable/auto-destroy asset "either side must include definer" check omits the change address of the AA/other side, mismatching who actually holds funds vs. who is authorized to receive them - (File: divisible_asset.js)

### Summary
The EigenLayer report describes a class of bug where the entity authorized to perform an action (the `staker`) is checked against the entity that actually receives the funds (the `withdrawer`), and a mismatch between these two roles causes the operation to be blocked, leaving funds effectively stuck. The closest reachable analog in ocore is the enforcement of the `is_transferrable`/`definer_address`/`auto_destroy` asset restrictions, where the code checks that the **definer address** is present on "either side of the deal" using only the intended `to_address`/`arrOutputAddresses`, but does not always correctly account for the **change address**, which is where left-over funds actually end up.

### Finding Description
For assets marked `is_transferrable: false` (which also applies to issuance), the protocol requires that the asset definer be one of the addresses in the transaction, either as sender or receiver, so that the asset can only move to/from its issuer. This is implemented in two places with different levels of correctness:

1. In `divisible_asset.js`'s `composeDivisibleAssetPaymentJoint`, the composer-side check is: [1](#0-0) 
This explicitly has a `// fix: also check change address when not transferrable` comment, indicating it was previously buggy and only partially patched — it checks `params.to_address` but the change output, added later in the same function, is not verified against this condition at compose time: [2](#0-1) 

2. The authoritative consensus check in `validation.js` (`validatePaymentInputsAndOutputs`) evaluates `arrInputAddresses`/`arrOutputAddresses` sets as a whole: [3](#0-2) 

The bug-class analogy: just like EigenLayer checks `staker == withdrawer` using the wrong "identity" (operator delegator, not the actual final destination pool), ocore's transferability guarantee is evaluated using address-set membership checks that were historically incomplete (the composer's own comment admits a prior omission of the change address). If any compose-time path constructs asset payments without properly reconciling the *actual* set of output addresses (including change) against `objAsset.definer_address` before validation, a legitimately-composed transaction for a non-transferrable/auto-destroy asset can pass the composer's optimistic check yet be rejected by network validation, or conversely — more critically — an output that the composer/AA author believes will return to a spendable, spend-authorized address can instead be constructed with an address that resolves to the `definer_address`, invoking the auto-destroy path in validation and node-consensus (`this output was destroyed by sending it to definer address`) irreversibly burning the funds: [4](#0-3) 

This mirrors the underlying mismatch pattern from the report: two different code paths (compose-time optimistic check vs. consensus validation) reason about "is this recipient authorized/expected" using different address sets, and a legitimate payer/AA can lose funds permanently when the two disagree, since `auto_destroy` sends are unrecoverable by design.

### Impact Explanation
If the compose-time restriction check in `divisible_asset.js` diverges from the definitive consensus rule in `validation.js` (as its own inline comment concedes it once did), a wallet, AA-composed payment, or private-payment chain builder could produce a transaction whose change output silently lands on `definer_address` for an `auto_destroy` asset. Consensus nodes will accept this unit as valid (per `validation.js` logic, sending to the definer is explicitly "good"), but the sender's coins are irrecoverably destroyed rather than returned as change — a direct, permanent fund loss for the unprivileged asset holder/poster, analogous to the "withdrawal that can never complete" impact in the original report.

### Likelihood Explanation
Likelihood depends on exactly how change-address selection interacts with `params.to_address`/`arrAssetPayingAddresses` in various callers of `composeDivisibleAssetPaymentJoint` (e.g., AA-driven asset transfers, wallet-composed transfers to non-transferrable/auto-destroy assets) — since I could not fully trace every caller and confirm whether the "fix" comment reflects a complete or still-partial patch, I cannot assert with certainty that an exploitable divergence currently exists in this exact code version. This uncertainty should be resolved with a live/dynamic trace of `params.change_address` selection paths for `is_transferrable:false && auto_destroy:true` assets before treating this as confirmed exploitable.

### Recommendation
Ensure the compose-time restriction check in `divisible_asset.js` (and the indivisible equivalent in `indivisible_asset.js`) validates the **complete final output set** (including all change outputs) against `objAsset.definer_address`/`is_transferrable`/`auto_destroy` exactly as `validation.js` does, rather than checking only `params.to_address`. Add an explicit guard that refuses to route change to the definer address unless the sender genuinely intends to burn the change, and add regression tests covering divisible non-transferrable auto-destroy assets with a change output.

### Proof of Concept
Not independently reproducible from static review alone. The concrete trigger would be: define a divisible asset with `is_transferrable:false, auto_destroy:true`; compose a payment via `composeDivisibleAssetPaymentJoint` where `paying_addresses` does not include `objAsset.definer_address` and the picked coins produce a `change` amount; verify whether the resulting change output address can end up equal to `definer_address` (destroying it) while the compose-time check at `divisible_asset.js:245-246` only inspected `params.to_address`, not the final change output.
