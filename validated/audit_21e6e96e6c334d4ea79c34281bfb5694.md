### Title
Attacker-controlled route programs can inject unauthorized token transfers into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept caller-supplied `swap` bytes and forward them uninterpreted to the configured swap aggregator. [1](#0-0) [2](#0-1)  The route can place attacker-controlled pool or token contracts on the call stack, and those contracts can append a token transfer from the caller as a child of the caller’s authorization entry. [3](#0-2) 

### Finding Description
The controller validates only the routed token input, measured output, and final account state; it does not constrain which contracts the opaque route program invokes. [4](#0-3)  `authorize_transfer_as_current` grants only the controller’s exact input transfer and no sub-invocations, but that protection does not prevent route-selected third-party code from requesting additional authorization from the original caller deeper in the call tree. [5](#0-4) [6](#0-5)  During simulation, the injected `token.transfer(victim, attacker, amount)` is recorded beneath the caller’s strategy authorization, and it executes if the victim signs that poisoned tree. [7](#0-6) 

### Impact Explanation
A malicious route can steal arbitrary wallet-token balances from the victim in addition to consuming the routed collateral. [8](#0-7)  The protocol’s measured-output, overspend, and post-strategy solvency checks do not bound the extra transfer because it is paid directly from the caller rather than from controller balances. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
Any unprivileged caller-facing strategy can carry the malicious route, but exploitation requires the victim to sign the authorization tree containing the unexpected child transfer. [1](#0-0) [7](#0-6)  The exposure is still material because an honest route produces no extra child entry while a malicious quote or compromised route-generation path can make the unauthorized transfer appear as part of the requested swap. [11](#0-10) 

### Recommendation
Restrict route-invoked venue, pool, and token addresses to a governed allowlist, or require routes to carry a caller-verifiable manifest covering every contract and authorization child they may create. [2](#0-1) [12](#0-11)  Until the contract boundary enforces this restriction, clients must decode the route and reject any simulated authorization tree containing children beyond the expected input transfer. [11](#0-10) 

### Proof of Concept
1. The victim owns a liquid account and an unrelated token balance that the lending market does not list. [1](#0-0) 
2. The attacker supplies `swap` bytes whose program names an attacker-deployed pool or token contract as a hop. [2](#0-1) [13](#0-12) 
3. The victim submits `swap_collateral(caller=victim, account_id, current, amount, new, swap)`. [1](#0-0) 
4. During router execution, the attacker contract calls `unrelated_token.transfer(victim, attacker, wallet_balance)`. [14](#0-13) 
5. Simulation records that token transfer as a child under the victim’s `swap_collateral` authorization; signing that tree authorizes the theft while the swap itself can still produce positive measured output and pass final risk checks. [9](#0-8) [7](#0-6)

entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
