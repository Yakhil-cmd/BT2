### Title
Caller-selected flash receivers can execute arbitrary code inside the caller's authorization tree to steal unrelated wallet tokens - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` lets an unprivileged caller supply an arbitrary contract `receiver` and invokes it before settling the flash position. [1](#0-0) [2](#0-1)  Because the callback executes beneath the caller-authorized controller invocation, code in the receiver can add a token transfer from the caller to the simulated authorization tree and steal assets unrelated to the flash position if that tree is signed. [3](#0-2) 

### Finding Description
The entrypoint authenticates `caller`, rejects only the controller and pool as receivers, and otherwise accepts any WASM contract supplied in `receiver`. [4](#0-3) [5](#0-4)  The controller then mints and forwards debt, snapshots declared balances, and calls `invoke_receiver` on that attacker-chosen contract. [6](#0-5)  After the callback returns, the controller accepts the position when the declared collateral deltas and solvency checks pass; it does not constrain what other calls the receiver attempted during the callback. [7](#0-6) 

A nested token transfer can be recorded as a child of the caller's controller authorization and succeeds under enforcing authorization when the caller signs that expanded tree. [8](#0-7) [9](#0-8)  The harness demonstrates the host behavior with a malicious contract invoked below a controller strategy: the malicious contract calls `token.transfer(victim, attacker, amount)`, simulation places that transfer beneath the user's `swap_collateral` authorization, and signing it transfers the entire unrelated wallet balance while the strategy still settles. [10](#0-9) [3](#0-2)  The same authorization-tree exposure applies to `flash_position`'s arbitrary callback because the receiver is likewise untrusted code invoked below the caller-authorized entrypoint. [2](#0-1) 

### Impact Explanation
A successful attack steals arbitrary tokens held by the caller's wallet, beyond the borrowed asset and declared collateral. [11](#0-10) [12](#0-11)  The attacker can pre-fund or operate the receiver so it returns the required collateral, allowing the account checks to pass and the wallet-draining child transfer to remain committed. [7](#0-6) 

### Likelihood Explanation
The attacker must persuade a victim to initiate `flash_position` with the malicious receiver and sign the authorization tree containing the extra token transfer. [1](#0-0) [9](#0-8)  This requires a malicious receiver address or transaction-construction path rather than a protocol secret, oracle manipulation, privileged role, or contract upgrade. [13](#0-12)  Wallets or clients that clearly display and reject unexpected child calls prevent the exploit, while clients that present an opaque simulation-produced authorization tree expose users to full-wallet token theft. [3](#0-2) 

### Recommendation
Do not invoke caller-selected arbitrary receiver contracts while the caller's monetary authorization context is active. [6](#0-5)  Restrict `receiver` to a governed allowlist of audited receiver implementations, or redesign `flash_position` so the flash proceeds are delivered without executing attacker-selected code beneath the caller-authorized entrypoint. [13](#0-12) [2](#0-1)  At the integration layer, simulate the call, decode the complete authorization tree, and reject any child invocation other than the expected protocol calls before presenting it for signature. [14](#0-13) 

### Proof of Concept
1. Deploy a malicious WASM receiver whose callback calls `token::Client::new(env, victim_token).transfer(victim, attacker, victim_balance)` and then returns enough listed collateral to satisfy the declared flash-position minimum; the harness's `RogueHopPool` shows the same nested `transfer` primitive. [10](#0-9) 
2. Have the victim call `flash_position` with `receiver` set to that contract, a positive debt `amount`, and a declared collateral minimum that the receiver can satisfy. [15](#0-14) 
3. During simulation, the receiver's transfer is recorded beneath the victim's controller authorization rather than beneath controller or receiver authority. [16](#0-15) 
4. If the victim signs that generated tree, the host accepts the receiver's wallet transfer, moves the victim's unrelated token balance to the attacker, and the controller can still pass the measured collateral and final risk checks. [9](#0-8) [7](#0-6)
