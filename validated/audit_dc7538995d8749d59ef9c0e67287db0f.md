### Title
Missing write-lock around AA dry-run trigger cache mutation/rollback causes use-after-free-like corruption of the in-memory unit graph - (File: aa_composer.js, writer.js, storage.js)

### Summary
`aa_composer.dryRunPrimaryAATrigger()` executes an AA trigger against a real, unlocked database connection and, through `handleTrigger()` → the same write path used by `writer.js`, mutates the node's shared in-process caches (`storage.assocUnstableUnits`, `storage.assocBestChildren`, `storage.assocUnstableMessages`) with synthetic objects, then rolls back the DB transaction and calls `revertResponsesInCaches()` → `storage.forgetUnit()` to rip those objects back out of the shared caches. None of this path takes the global `"write"` mutex that guards these caches during real unit validation/writing, and the writer explicitly documents that the lock was removed ("without this locking, we get frequent deadlocks from mysql").

### Finding Description
`dryRunPrimaryAATrigger()` takes a plain pooled DB connection and begins a transaction without acquiring `mutex.lock(["write"], …)`: [1](#0-0) 

`handleTrigger()` ultimately drives unit creation through the same code that `writer.js` uses for real units, which writes directly into the shared, global caches `storage.assocUnstableUnits` and `storage.assocBestChildren` (and `assocUnstableMessages`) — and the surrounding comment shows the write-lock was intentionally disabled for this exact code region: [2](#0-1) 

When the dry run finishes, `revertResponsesInCaches()` deletes the synthetic response units from these same shared caches via `storage.forgetUnit()`, including splicing entries out of `assocBestChildren[parent_unit]` by reference and deleting keys from `assocUnstableUnits`: [3](#0-2) [4](#0-3) 

Meanwhile, real unit validation and main-chain computation (`main_chain.js`) reads and walks these exact same caches by direct object reference, not by re-querying the DB each time, and throws hard, unhandled errors when the expected shape/object is missing: [5](#0-4) 

Because `dryRunPrimaryAATrigger`'s mutation/rollback of `assocUnstableUnits`/`assocBestChildren` is not serialized against the `"write"` mutex used by real validation, a legitimate, concurrently-running unit-validation/main-chain-update pass can hold or traverse a reference to an object that the dry run subsequently deletes from the map or splices out of `assocBestChildren` mid-flight. This is the JS/in-memory analog of a use-after-free: the object is still reachable in memory, but the bookkeeping structures that tie it into the consensus graph (parent's best-children list, the `assocUnstableUnits` key) are silently invalidated by an unrelated concurrent request while another code path is still using it, corrupting the shared, process-wide validation state (`storage.assocUnstableUnits`, `storage.assocBestChildren`, `is_free` flags) that all subsequent unit validation depends on.

### Impact Explanation
Corruption of `assocUnstableUnits`/`assocBestChildren` (which `main_chain.js` uses to compute the best parent, level, main-chain index, and stability) can cause the node to throw uncaught errors (e.g. `"unstable unit not found"`, `"trying to forget stable unit"`) which crash the process, or silently produce a wrong main-chain/stability view. Either outcome maps to the accepted impact classes: node disagreement on validity/stability, or a node/network unable to confirm new units, triggered purely by processing normal, unprivileged AA-trigger dry-run/estimate requests that any unit poster or AA trigger sender can cause the node to perform (via `dryRunPrimaryAATrigger`/`estimatePrimaryAATrigger`, referenced from `network.js`).

### Likelihood Explanation
Triggering an AA dry-run/estimation is a routine, unprivileged operation (posting a payment/data message to an AA address, or a wallet/light client requesting an estimate). The race window exists any time such an estimation request executes concurrently with genuine unit validation/writing on the same node — a very common condition on an active hub/full node — and the developers' own comment confirms the write-lock was deliberately dropped from this write path, indicating the race is a known, accepted trade-off rather than a theoretical one.

### Recommendation
Wrap `dryRunPrimaryAATrigger()`/`estimatePrimaryAATrigger()`'s cache-mutating trigger execution and `revertResponsesInCaches()`/`forgetUnit()` rollback in the same `"write"` mutex used by `writer.js` and `main_chain.js`, so that dry-run cache pollution/cleanup cannot interleave with real unit validation and main-chain updates. Alternatively, make dry-run execution operate on a private, deep-cloned snapshot of the relevant caches rather than mutating the shared global `storage.assocUnstableUnits`/`assocBestChildren` structures in place.

### Proof of Concept
Not independently reproducible from static analysis alone (requires a running two-thread/two-request race on a live node): (1) send a unit that is being validated and is about to update the main chain (calls `main_chain.updateMainChain`, which reads `storage.assocUnstableUnits`/`assocBestChildren` by reference); (2) concurrently, from another connection, submit an AA trigger causing `dryRunPrimaryAATrigger` to run, inserting/removing synthetic entries in the same `assocUnstableUnits`/`assocBestChildren` maps via `handleTrigger` → `revertResponsesInCaches` → `forgetUnit`; (3) if the real validation's `goUpFromUnit`/`calcLIMCIs` traversal captured a reference to an object or array slot that the dry run's `forgetUnit` deletes/splices in between, the node throws (`throw Error("unstable unit not found: "+best_parent_unit)` in `main_chain.js:104`, or `throw Error("trying to forget stable unit "+unit)` in `storage.js:2227-2228`) or computes an incorrect main-chain/stability state.
