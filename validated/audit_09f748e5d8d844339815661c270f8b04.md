## Title
Stale-vs-current stake delegation mismatch can panic bank processing during partitioned epoch reward distribution, causing an epoch-boundary halt - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
This is an analog of the Smilee `PositionManager::mint()` bug class: a value computed at one point in time (via one code path) is later checked/consumed as if it must match a value computed independently at a different point in time, and the mismatch is not tolerated — it triggers a hard failure instead of graceful reconciliation. In Smilee, `obtainedPremium` (computed from oracle price) diverged from the DVP's actual required premium (computed from `max(oraclePrice, swapPrice)`), causing a revert. In Agave's stake-reward distribution path, `Bank::build_updated_stake_reward` asserts that a stake delegation amount recomputed from the *current* `StakesCache` snapshot equals a delegation amount that was pre-computed during the epoch-boundary *calculation* phase, when `adjust_delegations_for_rent` is `false` (i.e., the `relax_post_exec_min_balance_check` feature is not active).

### Finding Description
Partitioned epoch rewards are computed in two temporally separated phases:
1. **Calculation phase** (epoch boundary block): `redeem_delegation_rewards` snapshots each stake account's delegation and lamports and computes the post-reward delegation/stake amount, storing it in `PartitionedStakeReward.inflation.stake` [1](#0-0) .
2. **Distribution phase** (subsequent blocks, spread across `num_partitions`): `store_stake_accounts_in_partition` reads the account fresh from the **live** `stakes_cache` at the current block and calls `build_updated_stake_reward`, which — when `adjust_delegations_for_rent` is false — asserts that the *live* delegation plus the pre-computed reward exactly equals the delegation value computed during the calculation phase:

This is structurally identical to the Smilee bug: one component (`stake.delegation.stake`, read live at distribution time from `stakes_cache_accounts`) can diverge from the other (`new_stake.delegation.stake`, computed at the earlier calculation-time snapshot), because ordinary stake-program instructions (e.g. `Split`, `Merge`, `Withdraw`, `Deactivate`, `Redelegate`) issued by the unprivileged stake authority in the blocks between calculation and this partition's distribution block can change the on-chain `delegation.stake` for that account. The reward distribution window spans multiple blocks (`REWARD_CALCULATION_NUM_BLOCKS` delay plus up to `num_partitions` blocks, clamped to 10% of `slots_per_epoch`) [3](#0-2) , during which reward distribution runs concurrently with normal transaction processing rather than the ledger being frozen for that account.

The code comment for `store_stake_accounts_in_partition` explicitly assumes this can never diverge ("Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned") [4](#0-3) , but I was unable to confirm within the available index whether the stake program actually rejects all stake-mutating instructions while `EpochRewardStatus::Active` is set for a given stake account (the `get_reward_interval`/`InsideInterval` check exists only in `runtime/src/bank/partitioned_epoch_rewards/mod.rs`, and I could not locate an analogous check inside the stake program's instruction processor in the indexed portion of `programs/stake/`). If such an instruction-level lockout does not exist (or has any gap, e.g. `MergeCoolingDown` returning a different final stake, or accounts loaded/created in the same slot via `SlotLeader`), the `assert_eq!` becomes reachable with mismatched values, causing a Rust panic inside `Bank::store_stake_accounts_in_partition`, which is called unconditionally from `distribute_partitioned_epoch_rewards` on every block within the distribution window [5](#0-4) .

### Impact Explanation
An `assert_eq!` panic inside bank block processing is not a benign error path — it aborts transaction/block processing on every validator that reaches that slot deterministically (since state transition is deterministic across the cluster), which manifests as a **cluster-wide halt at an epoch boundary** during the reward-distribution window. This matches the accepted "epoch-boundary halt" impact category.

### Likelihood Explanation
Likelihood is **uncertain/low-to-unconfirmed** from the available index: the assert only fires on the `adjust_delegations_for_rent == false` branch (i.e., before/without the `relax_post_exec_min_balance_check` feature), and I could not verify from the indexed code whether the stake program processor actually blocks or serializes stake-mutating instructions for accounts pending distribution. Without confirming a genuine gap that lets a user's `Split`/`Merge`/`Withdraw` land on a stake account between its calculation snapshot and its distribution block while that account is *still selected for and paid* a reward, this remains a plausible-but-unconfirmed structural analog rather than a proven exploit path.

### Recommendation
- Verify whether the stake program (or reward-distribution machinery) enforces exclusivity over stake accounts pending distribution; if not, add such a guard, or
- Change the equality check in `build_updated_stake_reward`'s `else` branch from a hard `assert_eq!` (panic) to a reconciliation path — analogous to the Smilee fix of using `max`/recomputing rather than reverting — e.g., recompute the delegation from the live account state instead of asserting it matches a stale calculation-time value, mirroring what the `adjust_delegations_for_rent == true` branch already does via `adjust_delegation_for_rent` [6](#0-5) .

### Proof of Concept
Could not be concretely demonstrated with the available read-only index access — reproducing this would require confirming (a) the exact stake-program instruction-processing behavior for accounts with pending/active epoch rewards, and (b) constructing a sequence of `Split`/`Merge`/`Withdraw` instructions timed against `REWARD_CALCULATION_NUM_BLOCKS` and partition-hash assignment (`hash_rewards_into_partitions`) to land a stake-mutating instruction on a targeted account before its assigned distribution block. This would need to be validated in a live/simulated cluster (e.g., via a Devin session with test-validator access) rather than through static code search alone.

fn adjust_delegation_for_rent(
    delegation: &mut Delegation,
    rewarded_epoch: Epoch,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
) {
    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    if new_delegation != delegation.stake {
        delegation.stake = new_delegation;
        // Deactivate stake if needed. This deactivation is immediate,
        // unlike a requested deactivation which happens at the next epoch
        // boundary
        if new_delegation == 0 {
            delegation.deactivation_epoch = rewarded_epoch;
        }
    }
}

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
