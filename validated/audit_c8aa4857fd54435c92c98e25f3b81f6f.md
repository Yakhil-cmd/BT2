### Title
Caller-controlled route bytes can attach an unrelated wallet token transfer to an authorized controller strategy call - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept opaque caller-supplied route bytes and forward them to the configured router after authorizing only the strategy input transfer. [1](#0-0) [2](#0-1) 

The route can name an arbitrary pool address because the payload carries an unvalidated address registry and hop instructions invoke that address. [3](#0-2) [4](#0-3) 

### Finding Description
The controller checks the routed asset spend and positive output, but it does not decode or constrain the route's external pool identities. [5](#0-4) 

A malicious venue invoked below the strategy call can issue an unrelated `token.transfer(caller, attacker, amount)`, which Soroban simulation records beneath the caller's `swap_collateral` authorization. [6](#0-5) 

If the caller signs the simulated tree, the unrelated child transfer executes even though the strategy itself only intended to authorize collateral movement. [7](#0-6) 

### Impact Explanation
This can steal arbitrary signer-held tokens unrelated to the lending collateral and outside the measured `amount_in` bound. [8](#0-7) 

The controller's `RouterOverspend` and `NoSwapOutput` checks bound only the declared input and output tokens, not other token transfers added to the caller's signed authorization tree. [5](#0-4) 

### Likelihood Explanation
Execution requires the victim to submit and sign a crafted route whose authorization tree contains the extra transfer. [9](#0-8) 

The condition is plausible when routes are obtained from an untrusted service or copied from another party because the controller treats the bytes as opaque and relies on external routing behavior. [10](#0-9) 

### Recommendation
Reject routes containing unallowlisted pool or token addresses, or require a governance-managed venue registry before invoking route-provided addresses. [3](#0-2) 

At minimum, controller integrations and signing clients should decode every route and reject any authorization tree whose children differ from the single expected strategy input transfer. [11](#0-10) 

### Proof of Concept
1. Configure a route whose instruction uses a supported venue opcode but points its `pool` index to an attacker-deployed contract. [12](#0-11) 
2. The malicious pool returns or arranges a positive output so the controller's measured-output check passes. [13](#0-12) 
3. During the venue call, the malicious pool invokes `token.transfer(victim, attacker, victim_balance)` for an unrelated token held by the victim. [14](#0-13) 
4. Simulation records that unrelated token transfer as a child of the victim's `swap_collateral` authorization. [6](#0-5) 
5. Signing that tree drains the victim's unrelated wallet-token balance while still crediting the expected swapped collateral. [15](#0-14)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
