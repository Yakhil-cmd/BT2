### Title
Webhook signature verified against the payload's claimed organization, but the event is routed and applied to the repository/stack named in an unverified payload field - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC secret used to authenticate the webhook) based on `repository_owner`, a value read out of the JSON body itself. `Webhooks::Handlers::Handler#stacks` then routes the event to a `Stack` using `repository.full_name`, a different field of that same attacker-controlled JSON body. Because HMAC verification only proves "this raw body was signed by *some* app whose secret matches," and the app is chosen by a field inside that same body, an attacker who owns any GitHub App installation (fully self-service, e.g. on their own free GitHub org) can forge a webhook whose `repository.owner.login` names their own org (so it authenticates with their own known secret) while `repository.full_name` names a victim repository/stack actually configured in the target Shipit instance.

### Finding Description
`repository_owner` used to pick the verifying app: [1](#0-0) 

Signature check, performed against that app's secret over the raw JSON body: [2](#0-1) [3](#0-2) 

Once verification passes, every handler resolves the target `Stack`(s) using `repository.full_name`, a separate field of the same body, unrelated to the `repository_owner` field used for authentication: [4](#0-3) 

`PushHandler` then acts on whatever `Repository.from_github_repo_name(repository.full_name)` resolves to: [5](#0-4) 

Equality that should hold but doesn't: `organization that authenticated the request == organization owning the repository the handler writes to`. `verify_signature` proves the body was signed with the secret belonging to `repository_owner` = attacker's own org. Nothing then constrains `repository.full_name` to be a repository belonging to that same org — that field is free-form attacker input inside the very body that was just verified, and it is what every handler (`push_handler.rb`, and by the same `Handler#stacks` mechanism, the status/check_suite/pull_request/membership handlers referenced in `test/controllers/webhooks_controller_test.rb`) uses to pick which `Stack`/`Repository`/`Commit` record to mutate.

Concretely, an attacker who:
1. Creates their own GitHub App (or uses any GitHub App they administer) with a webhook secret they know, installed on a repo/org they own.
2. Sends a POST to Shipit's `/webhooks` endpoint with `X-Github-Event: status` (or `push`, `check_suite`, etc.), a valid `X-Hub-Signature` computed with their own known secret, `repository.owner.login = "attacker-org"`, but `repository.full_name = "victim-org/victim-repo"` (a repository/stack that already exists in the target Shipit instance and is unrelated to the attacker).

This passes `verify_signature` (secret matches attacker-org's app) and is then processed against the victim's `Stack`.

### Impact Explanation
The `status` event handler creates a `Status` for a specific commit purely from payload fields (`sha`, `state`, `context`, etc.), as shown by the existing test coverage: [6](#0-5) 

Because deploy gating in Shipit relies on required CI statuses (`ci.require` in `shipit.yml`), an attacker who can forge a `success` status for an arbitrary commit SHA on a stack they don't own and have never had access to can unblock that stack's required-CI check, i.e. contribute to an **unauthorized deploy** being possible for a commit that never actually passed CI. The same root cause lets an attacker forge `push` events to force `GithubSyncJob`/`sync_github` runs, or `check_suite`/`membership`/`pull_request` events, on any stack in the instance whose repository full name they can guess (often public knowledge). This crosses a credential/authentication boundary (an app the attacker legitimately owns) into control over state (`Status`, sync triggers, membership/team records) belonging to repositories/orgs the attacker has no relationship with — matching the "unauthorized deploy" / cross-repository-write impact bucket.

### Likelihood Explanation
Requires no privileged access to Shipit, no `ApiClient` token, and no access to the victim's actual `webhook_secret`. The attacker only needs a GitHub App they administer (trivial, self-service, free) and knowledge of a target repository's `owner/name` (public information for public repos). Crafting the JSON body and computing HMAC-SHA1 over it with their own known secret is straightforward. The only requirement Shipit itself imposes — that the raw body is properly signed — is satisfied because the signing key is selected from inside the attacker's own forged body.

### Recommendation
Do not select the verifying app from a payload field. Instead:
- Resolve the target `Repository`/`Stack` from `repository.full_name` first, look up the organization that repository actually belongs to in Shipit's configuration, and verify the signature using **that** organization's secret — rejecting the webhook if the claimed `repository.owner.login` does not match the owner recorded for the resolved repository.
- Alternatively, verify signatures using a per-installation/per-app secret bound to the GitHub App installation ID (obtained via `X-GitHub-Hook-Installation-Target-ID` or similar), not a value taken from the JSON body.
- Add a defense-in-depth check in `Webhooks::Handlers::Handler#stacks` (or a shared `before_action`) asserting that `payload.dig('repository','owner','login')` matches the resolved `Repository`'s known owner before dispatching to any handler.

### Proof of Concept
1. Attacker registers/uses a GitHub App on `attacker-org` with webhook secret `S` (known to them since they configured it).
2. Attacker crafts:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<any commit sha that exists in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{ "name": "master" }]
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>`.
4. `POST /webhooks` with `X-Github-Event: status` and this body/signature.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `S`, per [2](#0-1) .
6. The status handler resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (per [4](#0-3) ) and records a forged passing `Status` for that commit, potentially satisfying `victim-org/victim-repo`'s deploy CI gate.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
