### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit for an incoming GitHub `status` webhook purely by `sha`, with no check that the commit's owning stack/repository matches the repository that the signed webhook payload claims to be from. `WebhooksController#verify_signature` only uses the payload's `repository.owner.login` to select which org's HMAC secret to verify against; it never re-checks that the resolved `Commit` actually belongs to that same repository. This lets an attacker who controls a webhook-emitting repository containing a commit with the same SHA as a victim's queued `MergeRequest` head commit inject a `success` status onto the victim's commit, which can drive `ProcessMergeRequestsJob` to call `merge_request.merge!` on the victim's stack.

### Finding Description
The broken binding: the question assumes `repository/org named in the status payload == repository/org owning the MergeRequest whose head commit's status is consulted`. Tracing the code shows this equality is **not enforced anywhere**:

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only uses `repository_owner` (`params.dig('repository','owner','login')`) to pick which `Shipit.github(organization: ...)` app/secret to verify the HMAC signature against. This only proves "this payload's signature matches the claimed org's secret" — an attacker who owns a repo under their own org can produce a validly signed webhook for that org.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does: [1](#0-0) 
  `Commit.where(sha: params.sha)` is a **global, unscoped lookup across all stacks/repositories** in the Shipit instance — it never filters by `stack.repository` or by the payload's `repository_owner`/`repository.full_name`.
- For every `Commit` row matching that SHA (regardless of which stack/org it belongs to), `commit.create_status_from_github!(params)` is called, which creates a `Status` scoped to that commit's own `stack_id`: [2](#0-1) 
- That status creation schedules `ProcessMergeRequestsJob` for the *victim's* stack, and if the victim has a pending `MergeRequest` whose `head` is that commit, `all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`) will evaluate to true from the forged `success` status, and `ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb:21-26`) calls `merge_request.merge!`, which merges the victim's real PR via `stack.github_api.merge_pull_request(stack.github_repo_name, number, ...)`.

Attacker's exact request/PR: attacker creates a commit whose raw git object (tree, parent, author/committer, message, timestamps) byte-for-byte matches the victim's public PR head commit — since git SHA-1 is content-addressed, this is achievable by reconstructing the object from public data (the victim PR's diff/tree and parent commit are visible via GitHub's API/UI) and pushing it as a loose object into the attacker's own repository/PR. The attacker's repo then legitimately fires a GitHub `status` webhook for `state: success` on that SHA, signed with the attacker's own org's webhook secret (a secret the attacker's org rightfully possesses, since GitHub — not Shipit — computes and sends this signature for events on the attacker's own repository).

Why existing guards fail: `verify_signature` validates the signature belongs to the claimed org, which it does — the attacker is the legitimate owner of that org/repo and GitHub genuinely signs the webhook for them. The vulnerability is that the *content* of the payload (the `sha`) is trusted to resolve a `Commit` record without any secondary check that the commit's `stack.repository` matches `repository_owner`/`repository.full_name` from the payload. No other guard (`drop_unhandled_event`, `ExplicitParameters` schema, model validations) checks this cross-repository binding either — `ExplicitParameters` only validates `sha`/`state` types are present, not their relationship to `repository`.

### Impact Explanation
A payload authenticated for repository/org **A** (attacker's own) can mutate `Status` records tied to a totally unrelated stack/repository **B** (victim's), and if the coincidental/engineered SHA belongs to a pending `MergeRequest`'s head commit in stack B with `merge_queue_enabled`, this can trigger `merge_request.merge!` — an unauthorized merge of the victim's real GitHub pull request, executed with Shipit's own GitHub App credentials for stack B. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." It is repeatable against any stack with `merge_queue_enabled` for any SHA the attacker can reproduce.

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled: true`, has a pending `MergeRequest`, and its head commit SHA must be reproducible by the attacker (requires an identical git object — feasible when the victim's PR is public, since tree/parent/commit metadata are all visible via GitHub's API, and git SHA-1 is deterministic over that content). The attacker needs no Shipit credentials, no session, no API token, and no privileged GitHub role — only control of their own repository and the ability to construct a matching commit object and push it. This is a moderate-cost but realistic exploitation path when the target PR/commit content is public, and is fully repeatable across any stack the attacker can reproduce a head SHA for.

### Recommendation
In `StatusHandler#process` (and analogously in any other webhook handler resolving commits solely by `sha`, e.g. check-run/check-suite handlers), scope the `Commit` lookup by the stack's repository derived from the webhook payload's `repository.full_name`/`owner`, e.g. join through `Stack` and filter `Commit.joins(:stack).merge(Stack.where(repository: repository_from_payload))`, rejecting or ignoring commits whose owning stack's repository does not match the payload's repository.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `stack_victim` (`shipit_stacks(:shipit)` or a new factory) with `merge_queue_enabled: true`, repository `victim-org/victim-repo`.
2. Create a `Commit` under `stack_victim` with `sha: SHARED_SHA`.
3. Create a `MergeRequest` on `stack_victim` in `pending` state with `head: that commit`.
4. Build a signed `status` webhook payload with `repository.owner.login = "attacker-org"`, `repository.full_name = "attacker-org/attacker-repo"`, `sha: SHARED_SHA`, `state: "success"`.
5. Stub/allow `GithubApp#verify_webhook_signature` for `attacker-org` to return true (simulating a genuinely signed webhook from the attacker's own org).
6. Expect: `MergeRequest#merge!` on `merge_request` (Mocha `.expects(:merge!)`) is invoked after `ProcessMergeRequestsJob.perform_now(stack_victim)` runs post-webhook — i.e., assert this call chain executes even though the payload's `repository.owner.login` (`"attacker-org"`) never equals `stack_victim.repository.owner` (`"victim-org"`), demonstrating the equality claimed by the question does not hold in the code and the merge is triggered by a payload for a foreign repository.
