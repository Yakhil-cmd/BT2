Based on my research, I found a valid analog in `Shipit::Api::CCMenuController`.

### Title
CCMenu endpoint lets a stack-scoped `ApiClient` token read the state of any other stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The Velodrome bug is a "trusted caller, unchecked destination" pattern: `ALLOWED_CALLER` is authorized to trigger swaps, but the specific factory/route it is allowed to touch is never checked against the registry, so an authorized-but-limited actor can redirect the privileged action to an unauthorized target. The same pattern exists in Shipit's `CCMenuController`, where an `ApiClient` token that is scoped (bound) to one specific `Stack` can be used to read CI/deploy status output for a *different* `Stack` it was never authorized for, because the scope binding is dropped for this one action.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` and the `stack_id` column [1](#0-0) . The generic API scoping mechanism in `Api::BaseController` enforces this binding: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` against that restricted set [2](#0-1) . This is exactly what protects endpoints like `Api::StacksController`, as verified by the test "an api client scoped to a stack will only see that one stack" [3](#0-2) .

`Api::CCMenuController` declares `require_permission :read, :stack`, which only calls `current_api_client.check_permissions!(:read, :stack)` — i.e. it verifies the client *has* the `read:stack` permission string, not that the specific stack being accessed matches the client's bound `stack_id` [4](#0-3) [5](#0-4) . Critically, `CCMenuController` overrides the private `stack` helper to bypass the scoped `stacks` collection entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 

This resolves `params[:stack_id]` directly against `Stack.from_param!`, ignoring `current_api_client.stack_id`. The equality that should hold is:

`stack the ApiClient token is authorized for == stack the request actually touches`

For every other API action this equality is enforced through `Api::BaseController#stacks`/`#stack`. For `CCMenuController#show`, the right-hand side is fully attacker-controlled via the `stack_id` route segment, breaking the binding.

### Impact Explanation
An `ApiClient` created with `read:stack` permission and bound to `Stack A` (e.g. an integration token intentionally scoped narrowly by an admin, matching the pattern in `here_come_the_walrus` fixture: `permissions: ['read:stack']`, `stack: shipit`) [7](#0-6)  can call `GET /api/stacks/*stack_id/ccmenu` with an arbitrary `stack_id` for a stack it was never granted access to, and receive that other stack's latest deploy/rollback status (via `stack.deploys_and_rollbacks.last`) [8](#0-7) . This is an unauthorized cross-repository/cross-stack read of deploy state, matching the "High" impact category ("unauthenticated read of stack state, task streams or deploy output" — here read by a caller unauthenticated *for that stack*, since the token's authorization is bound to a different stack entirely).

### Likelihood Explanation
The only requirement is possession of any valid `ApiClient` token that has the `read:stack` permission and a `stack_id` set (a common, low-privilege, deliberately narrow-scoped credential type meant to be handed out to third parties/CI tools for a single stack's status). No GitHub credentials, session, or elevated privileges are needed beyond that one token, and the route is public within the mounted engine's API namespace [9](#0-8) .

### Recommendation
In `Api::CCMenuController`, remove the override of `stack` (or reimplement it to resolve through the scoped `stacks` collection, i.e. `stacks.from_param!(params[:stack_id])`) so that a stack-bound `ApiClient` cannot query stacks outside its `stack_id` binding, mirroring the enforcement already present in `Api::BaseController`.

### Proof of Concept
1. Admin creates an `ApiClient` with `permissions: ['read:stack']` and `stack: <stack_a>` (a legitimately narrow-scoped token, per the `here_come_the_walrus` fixture pattern).
2. Attacker (or the party holding that token) obtains the token value.
3. Attacker sends `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu?token=<token>` for `stack_b`, a stack the token was never bound to.
4. `authenticate_api_client` succeeds (token is valid) [10](#0-9) ; `require_permission :read, :stack` passes because the client does have `read:stack` in its permission list; `stack` resolves `stack_b` directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` check, and the response leaks `stack_b`'s deploy status [11](#0-10) .
