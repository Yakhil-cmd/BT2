### Title
Unbounded Merkle-proof sibling count in address "in merkle" authentifier evaluation causes CPU-exhaustion validation — (File: definition.js)

### Summary
`validateAuthentifiers`'s `'in merkle'` branch deserializes an attacker-supplied authentifier string into a Merkle proof and calls `verifyMerkleProof` without capping `proof.siblings.length`, unlike the parallel `oscript` `is_valid_merkle_proof()` path which explicitly limits siblings to 50 and proof string to 1024 chars.

### Finding Description
When an address (or asset issue/transfer condition) definition contains an `['in merkle', [...]]` clause, spending from that address requires supplying an authentifier at the corresponding signing path. That authentifier is directly deserialized with `merkle.deserializeMerkleProof` and passed to `merkle.verifyMerkleProof`, which loops once per element in `proof.siblings` doing a SHA-256 hash each time [4](#0-3) . Neither `deserializeMerkleProof` (a plain `split("-")`) nor the calling code in `definition.js` bounds the number of `-`-delimited segments, so the loop trip count is proportional to the authentifier string length supplied by the unit's author — an untrusted, single unit-poster-controlled input. This mirrors the CVE-2017-6467 bug class: a parser loop whose iteration count is governed by an attacker-controlled size field with no upper limit, enabling denial-of-service style resource exhaustion during validation rather than true non-termination.

### Impact Explanation
Every full node and light client that validates a unit spending from such an address must run this unbounded loop as part of consensus-critical unit validation. An attacker can craft an oversized authentifier (large but still within general message-size limits) to make validation of a single unit consume disproportionate CPU relative to normal units, degrading node throughput/availability and potentially causing nodes to disagree on validation completion timing under load — a network-availability concern (nodes struggling to confirm/validate new units in a timely fashion). It's a validation-time DoS surface, not itself a proof-forgery bug, since `verifyMerkleProof` will still return false for an incorrect chain — the loop still runs to completion for each fake sibling supplied.

### Likelihood Explanation
Likelihood is limited by the fact that both the address definition (containing `in merkle`) and the crafted authentifier are entirely under the control of a single unit poster/author, so no cross-party or hub trust is required — moderate likelihood, gated by needing a spendable address with an `in merkle` clause and general unit size constraints (`MAX_UNIT_LENGTH`) which cap how large the authentifier field, and thus the sibling count, can grow.

### Recommendation
Apply the same defensive bound used in `formula/evaluation.js` (`objProof.siblings.length > 50`, and/or cap serialized_proof string length, e.g. 1024 chars) inside `definition.js`'s `'in merkle'` branch before calling `merkle.verifyMerkleProof`, rejecting authentifiers with an excessive number of siblings early.

### Proof of Concept
1. Register an address whose definition includes `['in merkle', [[oracleAddr], 'feed', 'element']]`.
2. When spending from that address, supply as the authentifier at the corresponding signing path a serialized proof string with an artificially large number of `-`-separated sibling segments (e.g., tens of thousands), while keeping the overall unit within `MAX_UNIT_LENGTH`.
3. Submit the unit; every validating node/light client executing `validateAuthentifiers` → `case 'in merkle'` will run `verifyMerkleProof` over the full attacker-chosen sibling count, performing a SHA-256 hash per sibling with no early rejection based on sibling count, consuming disproportionate CPU compared to a well-formed proof of the same address.

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
