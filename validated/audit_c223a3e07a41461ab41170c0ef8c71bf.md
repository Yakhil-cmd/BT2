This is precisely the field naming that `_extract_field` fails to support consistently for `MultiEdit`.

### Title
Hookify block rules for `new_text`/`content`/`old_text` silently fail to match `MultiEdit` operations, allowing dangerous edits to bypass block rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` implements per-tool field aliasing for `Write`/`Edit`/`MultiEdit`, but the `MultiEdit` branch only recognizes `file_path` and `new_text`/`content` — it never handles `old_text`/`old_string`, and (unlike the `Edit` branch) never satisfies a rule authored with the field name that user-facing docs recommend for "file" events uniformly. Any block rule written against `old_text`/`old_string` (a documented, valid field per `SKILL.md` "Field options: File: file_path, new_text, old_text, content") will silently evaluate to `None` for `MultiEdit` calls, causing `_check_condition` to return `False` and the rule to never trigger, even though the identical dangerous string would have been blocked on a plain `Edit` call.

### Finding Description
`RuleEngine._rule_matches` (`plugins/hookify/core/rule_engine.py:96-125`) first checks `rule.tool_matcher` (e.g. `"Edit|Write|MultiEdit"` or unset, in which case all tools are candidates), then requires every `Condition` to match via `_check_condition`, which calls `_extract_field` [1](#0-0) .

`_extract_field` special-cases tool types starting at line 230:
- For `Write`/`Edit`, fields `content`, `new_text`/`new_string`, `old_text`/`old_string`, and `file_path` are all supported [2](#0-1) .
- For `MultiEdit`, only `file_path` and `new_text`/`content` are supported; there is no handling for `old_text`/`old_string` at all, and no handling for `new_string` (only `new_text`) [3](#0-2) .

When the requested `field` isn't found via the generic `if field in tool_input` check (line 196) nor the tool-specific branches, `_extract_field` returns `None` (line 254), and `_check_condition` treats `None` as non-matching (`return False`, line 159-160) regardless of the operator or pattern. This means:
- A rule author following the plugin's own documentation (`plugins/hookify/skills/writing-rules/SKILL.md` lines 88 and 370: "File: `file_path`, `new_text`, `old_text`, `content`") that writes a condition on `old_text` to catch dangerous content being removed/replaced, or that reuses an `Edit`-style `new_string`-named condition, will have that condition never match for `MultiEdit` tool calls.
- Since `Rule` frontmatter typically sets `event: file` (matching Edit/Write/MultiEdit collectively per `pretooluse.py` lines 46-49) or `tool_matcher: "Edit|Write|MultiEdit"`, the operator naturally intends the rule to protect all three tools uniformly, but the engine's inconsistent field-name support per tool silently narrows protection to only `Edit`/`Write`.
- An attacker capable of influencing what tool Claude Code invokes for a given edit (e.g., via prompt-injected instructions in repository content that steer the agent to prefer `MultiEdit` for multi-hunk changes, which is a normal and common tool choice) can cause the identical dangerous payload (e.g. secrets, malicious code, sensitive file content) that would be blocked via `Edit` to pass silently via `MultiEdit`, because the block condition's field extraction returns `None` and the rule never fires.

This is exactly the "tool matching accepts only one representation" bypass: the block rule matches the *tool_matcher* (MultiEdit is included), but the underlying field-extraction representation-specific mismatch causes the intended block to be skipped.

### Impact Explanation
This breaks the core hookify invariant that "a matching block rule must reliably deny the protected operation." A security/compliance block rule (e.g., "block edits injecting API keys," "block edits removing security checks," "block edits to `.env`/secrets files with certain old/new content") intended to cover all file-editing tools can be silently bypassed by using `MultiEdit` instead of `Edit`, resulting in unauthorized file writes (or retained dangerous content) that the operator explicitly configured hookify to prevent. This matches the "Unauthorized file read or write outside the user-approved workspace or target scope" impact category, since the write proceeds despite an active blocking policy meant to constrain it.

### Likelihood Explanation
No privileged access or leaked credentials are required. The condition triggers whenever: (1) the project has a hookify block rule targeting file edits using `old_text`/`old_string`, or reusing `new_string` field naming, and applying it broadly to `Edit|Write|MultiEdit` or `event: file`/no `tool_matcher`; and (2) the actual edit is performed via `MultiEdit` rather than `Edit`. Since `MultiEdit` is a normal, frequently-used Claude Code tool for multi-hunk edits, and its use is influenced by ordinary repository content/structure (e.g., the shape and size of the diff Claude decides to apply), this is a highly feasible and repeatable condition, not a contrived edge case. It requires no attacker interaction with the hookify config file itself — only that the rule's field naming (which the plugin's own documentation presents as tool-agnostic) doesn't match the tool actually invoked.

### Recommendation
Make `_extract_field`'s per-tool handling symmetric and field-agnostic across `Edit`/`Write`/`MultiEdit`:
- For `MultiEdit`, add support for `old_text`/`old_string` by concatenating `old_string` across all `edits`, mirroring the `new_text`/`content` handling.
- For `MultiEdit`, also accept `new_string` as an alias for `new_text` (and vice versa for `Edit`, accept `content` uniformly), so the same condition field name works regardless of which file-editing tool triggered the hook.
- Add a unit test matrix that runs every documented condition field (`file_path`, `new_text`, `old_text`, `content`, `new_string`, `old_string`) against `Edit`, `Write`, and `MultiEdit` tool_input shapes and asserts identical block/allow outcomes for equivalent content.

### Proof of Concept
```python
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

engine = RuleEngine()

rule = Rule(
    name="block-secret-removal",
    enabled=True,
    event="file",
    tool_matcher="Edit|Write|MultiEdit",
    action="block",
    conditions=[
        Condition(field="old_text", operator="contains", pattern="SECURITY_CHECK")
    ],
    message="Removing SECURITY_CHECK marker is not allowed!"
)

# Case 1: Edit tool - rule correctly blocks
edit_input = {
    "tool_name": "Edit",
    "tool_input": {
        "file_path": "app.py",
        "old_string": "if not SECURITY_CHECK(): raise",
        "new_string": "pass"
    }
}
assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Case 2: MultiEdit tool with identical dangerous removal - rule silently fails to block
multiedit_input = {
    "tool_name": "MultiEdit",
    "tool_input": {
        "file_path": "app.py",
        "edits": [
            {"old_string": "if not SECURITY_CHECK(): raise", "new_string": "pass"}
        ]
    }
}
result = engine.evaluate_rules([rule], multiedit_input)
assert result == {}, "BUG: MultiEdit bypasses the block rule that protects Edit for identical content"
```
Expected (correct) behavior: both cases should return a `deny` decision. Actual behavior: the `MultiEdit` case returns `{}` (allowed) because `_extract_field` has no `old_text`/`old_string` handling for `MultiEdit`, confirming the bypass.
