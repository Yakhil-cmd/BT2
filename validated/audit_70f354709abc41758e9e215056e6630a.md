### Title
`deregisterOperator()` Does Not Enforce `operatorThresholds ≤ operatorList.length` Invariant, Freezing Bridge Value Transfers — (File: `contracts/service_chain/bridge/BridgeOperator.sol`)

### Summary

`BridgeOperator.deregisterOperator()` removes an operator from `operatorList` without checking whether the remaining operator count still satisfies the configured `operatorThresholds`. This is the exact analog of the reported MultiSig bug: `setOperatorThreshold()` enforces `operatorList.length >= _threshold`, but `deregisterOperator()` does not, allowing the invariant to be silently violated. When violated, the threshold in `_voteCommon()` can never be reached, permanently freezing all bridge value-transfer and configuration votes until manual recovery.

### Finding Description

`setOperatorThreshold()` correctly guards the invariant:

```solidity
require(operatorList.length >= _threshold, "bigger than num of operators");
``` [1](#0-0) 

But `deregisterOperator()` performs no such check before shrinking `operatorList`:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    for (uint i = 0; i < operatorList.length; i++) {
       if (operatorList[i] == _operator) {
           operatorList[i] = operatorList[operatorList.length-1];
           operatorList.length--;
           break;
       }
    }
    emit OperatorDeregistered(_operator);
}
``` [2](#0-1) 

The vote execution gate in `_voteCommon()` is:

```solidity
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
``` [3](#0-2) 

If `operatorList.length` drops below `operatorThresholds[voteType]`, the condition can never be satisfied regardless of how many operators vote, because `voteCounts` is bounded by the number of active operators.

### Impact Explanation

All three handle functions — `handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer` — gate their actual asset transfer on `_voteValueTransfer()` returning `true`:

```solidity
if (!_voteValueTransfer(_requestNonce)) {
    return;
}
// ... mint or safeTransfer executes here
``` [4](#0-3) [5](#0-4) 

When the threshold invariant is violated, `_voteValueTransfer()` can never return `true`, so:
- KLAY, ERC20, and ERC721 bridged assets are frozen on the destination bridge — no `mint` or `safeTransfer` executes.
- Configuration votes (`setKLAYFee`, `setERC20Fee`, etc.) are also frozen via `_voteConfiguration()`.

The owner can recover by calling `setOperatorThreshold` to lower the threshold (since `setOperatorThreshold` is `onlyOwner`, not vote-gated), or by registering a new operator. However, until recovery, all in-flight cross-chain transfers are stuck and users who have already locked assets on the source chain cannot receive them on the destination chain.

### Likelihood Explanation

The scenario is straightforward: a bridge with 3 operators and `operatorThresholds[ValueTransfer] = 3` (a common 3-of-3 multisig setup). The owner deregisters one operator (e.g., due to key rotation or operator exit). After the call, `operatorList.length = 2` but `operatorThresholds[ValueTransfer] = 3`. The bridge is immediately frozen for all value transfers. The owner may not notice until users report stuck transfers.

### Recommendation

Add a threshold enforcement check inside `deregisterOperator()`, mirroring the guard in `setOperatorThreshold()`:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    for (uint i = 0; i < operatorList.length; i++) {
       if (operatorList[i] == _operator) {
           operatorList[i] = operatorList[operatorList.length-1];
           operatorList.length--;
           break;
       }
    }
    // Enforce invariant: thresholds must not exceed remaining operator count
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        if (operatorThresholds[i] > operatorList.length) {
            operatorThresholds[i] = uint8(operatorList.length);
        }
    }
    emit OperatorDeregistered(_operator);
}
```

Alternatively, revert if any threshold would be violated, forcing the owner to lower the threshold first.

### Proof of Concept

1. Deploy `Bridge` (which inherits `BridgeOperator`). Owner is `A`, automatically added as operator. `operatorThresholds[ValueTransfer] = 1`.
2. Owner registers operators `B` and `C`. `operatorList = [A, B, C]`, length = 3.
3. Owner calls `setOperatorThreshold(VoteType.ValueTransfer, 3)`. Succeeds: `3 >= 3`. Now threshold = 3.
4. Owner calls `deregisterOperator(C)`. Succeeds with no threshold check. Now `operatorList = [A, B]`, length = 2, but `operatorThresholds[ValueTransfer] = 3`.
5. Operators `A` and `B` both call `handleKLAYTransfer(...)` for a pending cross-chain request. Each call enters `_voteCommon()`, increments `voteCounts` to at most 2, but `2 >= 3` is false. `_voteValueTransfer()` returns `false`. The KLAY transfer never executes. The user's funds are stuck.         private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }
