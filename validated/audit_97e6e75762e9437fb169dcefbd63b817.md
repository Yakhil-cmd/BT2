## Analysis: Rounding-down dust permanently locked in `pox-5.clar` reward distribution

The Sherlock CrabNetting bug class (funds locked forever due to floor-division "amount to send" calculations that never reconcile the remainder) maps directly onto `calculate-rewards` / `compute-earned-rewards` in `pox-5.clar`.

### Title
Permanent locking of sBTC reward dust due to double floor-division in reward-per-token accounting - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`calculate-rewards` computes a per-uSTX reward rate using integer (floor) division, and then marks the *entire* `stx-staker-rewards` amount as "accounted for" in `last-accounted-rewards-only`, even though the sum of individually claimable amounts (computed later via `compute-earned-rewards`, which floor-divides again) is strictly less than that amount whenever `cycle-staked-ustx` doesn't evenly divide the reward pool. The un-distributable remainder (sBTC "dust") stays in the contract's token balance forever: it is neither reserved, nor redistributed in a future cycle, nor claimable by any staker.

### Finding Description
In `calculate-rewards`:
```
(accrued-rewards-per-ustx (if no-stx-stakers
    u0
    (/ (* stx-staker-rewards PRECISION) cycle-staked-ustx)   ;; floor division #1
))
...
(var-set last-accounted-rewards-only
    (+ prev-accounted-rewards
        (- gross-accrued-rewards reserve-deposit)))          ;; full stx-staker-rewards is marked as "given away"
``` [1](#0-0) 

Individual earning amounts are then computed with a second floor division per staker:
```
(define-read-only (compute-earned-rewards
        (shares uint) (rpt-current uint) (rpt-paid uint) (pending uint))
    (+ pending (/ (* shares (- rpt-current rpt-paid)) PRECISION)))   ;; floor division #2
``` [2](#0-1) 

Because `accrued-rewards-per-ustx` is itself already the floor of `stx-staker-rewards * PRECISION / cycle-staked-ustx`, multiplying it back by each staker's `shares` and summing across all stakers under-counts the true `stx-staker-rewards` by up to `cycle-staked-ustx - 1` (in `PRECISION`-scaled units, then further truncated by the second division). The same pattern repeats for bond rewards via `accrued-rewards-per-sat`:
```
(accrued-rewards-per-sat (if (is-eq total-sats u0)
    u0
    (/ (* earned PRECISION) total-sats)
))
``` [3](#0-2) 

`get-rewards` / `get-new-rewards` determine future distributable amounts purely from `current-balance - total-staked-sbtc - cur-reserve` minus `last-accounted-rewards-only`:
```
(define-read-only (get-rewards) ...
    (- current-balance total-staked-sbtc cur-reserve))
(define-read-only (get-new-rewards) ...
    (- rewards-balance last-accounted-rewards))
``` [4](#0-3) 

Since `last-accounted-rewards-only` is incremented by the *full* (pre-truncation) `stx-staker-rewards`/bond-yield amount rather than the sum of what stakers can actually claim, the truncation remainder is subtracted out of "new rewards" accounting on every future cycle as well — it is never re-surfaced as claimable, and it is never swept into `reserve-balance`. The sBTC sits in the contract's token balance indefinitely with no code path to withdraw it.

### Impact Explanation
This is a permanent freezing of sBTC reward funds inside `pox-5`, analogous to the CrabNetting dust-lock: value that legitimately belongs to the protocol/stakers becomes stranded because rounding-down accounting is treated as "fully distributed" bookkeeping. Per cycle the loss is bounded (at most `cycle-staked-ustx - 1` scaled units, plus similar bond-level dust), but it accumulates every reward cycle across the contract's lifetime with no recovery mechanism — this matches the rubric's High-severity class ("permanent freezing of reserve or fees").

### Likelihood Explanation
This triggers on essentially every `calculate-rewards` call where `stx-staker-rewards` is not an exact multiple of `cycle-staked-ustx` (and likewise for bond `target-yield`/`total-sats`), which is the common case for arbitrary sBTC reward amounts and uSTX stake totals. No privileged role or attacker action is required — it's a systemic accounting defect triggered by normal operation.

### Recommendation
Track the actual truncation remainder at each step (e.g., compute `distributed = (accrued-rewards-per-ustx * cycle-staked-ustx) / PRECISION` and route `stx-staker-rewards - distributed` into `reserve-balance` instead of implicitly writing it off in `last-accounted-rewards-only`). Apply the same remainder-capture pattern to the bond-reward per-sat calculation in `calculate-bond-rewards`.

### Proof of Concept
1. Two signers stake unequal, non-round uSTX amounts summing to `cycle-staked-ustx` such that `stx-staker-rewards * PRECISION` does not divide evenly by `cycle-staked-ustx`.
2. Call `calculate-rewards`; `accrued-rewards-per-ustx` floors the division, and `last-accounted-rewards-only` is bumped by the *full* `stx-staker-rewards`.
3. Both signers `claim-rewards`; each amount is computed via `compute-earned-rewards`, again floor-dividing `shares * (rpt-current - rpt-paid) / PRECISION`.
4. Sum of both signers' claimed sBTC < `stx-staker-rewards` that was marked as accounted. The difference remains in the contract's sBTC balance, is excluded from all future `get-new-rewards` computations (already counted in `last-accounted-rewards-only`), and is excluded from `reserve-balance` — permanently unclaimable.
