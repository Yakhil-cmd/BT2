### Title
Webhook signature verification binds to `repository.owner.login` while write targets are selected by the independent `repository.full_name`/`sha` fields, enabling cross-organization forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature is accepted, `Shipit::Webhooks::Handlers::Handler` and its subclasses (e.g. `PushHandler`, the `PullRequest::*` handlers, `StatusHandler`) determine *which* database records to mutate using a completely different, independently-controlled field of the same JSON body: `repository.full_name` (via `Repository.from_github_repo_name`) or, in `StatusHandler`, an unscoped `Commit.where(sha: params.sha)` lookup with no repository/owner constraint at all.

### Finding Description
This mirrors the `OracleUniSolo.read()` bug class: two values that are supposed to be tied together (the value that was verified/scaled, and the value actually used) diverge because the code reads one field for authorization and a different field for the operation.

- `verify_signature` ( [1](#0-0) ) picks the HMAC secret keyed on `repository_owner` ( [2](#0-1) ).
- The signature covers the *entire raw JSON body*, so it does not independently pin `repository.full_name` to `repository.owner.login` — a valid signature for owner "A" is equally valid for a payload whose `repository.full_name` says "B/some-repo", as long as the byte content plus secret hash out correctly. Nothing in `verify_webhook_signature` (`lib/shipit/github_app.rb`, `verify_webhook_signature`) checks that `full_name`'s owner segment matches `repository_owner`.
- Handlers then trust `full_name` (or, worse, an unscoped `sha`) to select the target: `Handler#stacks`/`#repository_name` ( [3](#0-2) ), `PushHandler#process` ( [4](#0-3) ), each `PullRequest::*Handler#repository` (e.g. [5](#0-4) ), and `StatusHandler#process`, which queries commits with **no repository scoping whatsoever** ( [6](#0-5) ).

In Shipit's documented multi-tenant configuration ("Using Multiple GitHub Applications", `docs/setup.md`), several independent GitHub organizations can be registered on one Shipit instance, each with its own `webhook_secret` that its own org administrators legitimately possess (this is not a Shipit-privileged credential — it is a secret an org admin configures on their own GitHub App and is entitled to know). The binding this endpoint should enforce is:

`organization authenticated by webhook_secret == organization that owns the repository being written to`

That equality is never checked. An administrator of organization A's own GitHub App (attacker, with respect to Shipit) can:
1. Craft an arbitrary JSON payload where `repository.owner.login = "org-a"` (so `verify_signature` looks up and validates against org A's own known secret) and `repository.full_name = "org-b/victim-repo"` (or, for `status` events, simply any `sha` value with no owner field needed).
2. Compute a valid `X-Hub-Signature` over that raw body using org A's own `webhook_secret`, which they legitimately possess.
3. POST it directly to Shipit's public `/webhooks` endpoint (this endpoint is designed to be internet-reachable so GitHub can call it — nothing else authenticates the caller besides this signature check).
4. `verify_signature` passes because it only checks org A's secret against org A's declared owner login. The handler layer then acts on org B's stack/commit.

### Impact Explanation
This breaks the cross-repository/cross-organization write boundary explicitly called out in scope: an attacker who legitimately controls only their own organization's GitHub App/webhook_secret can force actions against a completely unrelated organization's tracked repository on the same Shipit instance:
- `push` events trigger `stack.sync_github(expected_head_sha: params.after)` on any stack, forcing Shipit's view of another org's branch HEAD to an attacker-chosen SHA.
- `status` events create/forge commit statuses for **any** commit SHA in the entire Shipit database (`Commit.where(sha: params.sha)` has no owner/repo filter at all), which can manipulate deploy-gating checks.
- `pull_request` events can archive/unarchive/provision review stacks belonging to another organization's repository.

This is a cross-repository write and can be leveraged to influence or trigger unauthorized deploy-adjacent state changes on repositories the attacker has no legitimate access to — matching the "cross-repository writes" / "unauthorized deploy" high-impact criteria.

### Likelihood Explanation
High. It requires nothing more than administering (or having previously been granted) a GitHub App / webhook secret for any single organization already configured on the shared Shipit instance — a routine, low-privilege credential relative to Shipit itself — plus the ability to POST directly to the public webhook endpoint, which is a documented, internet-facing endpoint by design.

### Recommendation
Bind the verified identity to the acted-upon resource instead of trusting two independent fields:
- After computing `repository_owner` for secret selection, re-derive the owning organization from the *same* field the handlers use (`repository.full_name`'s owner segment, or the resolved `Repository#owner`) and reject the request (`head 422`) if they don't match.
- In `StatusHandler`, scope the `Commit` lookup by the repository resolved from the verified payload rather than a bare `sha`, e.g. `stacks.commits.where(sha: params.sha)` via `Handler#stacks`.
- More generally, ensure every handler resolves its target strictly through the same repository/owner value that was authenticated by the signature check, never through a sibling field of the same untrusted JSON body.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`, "Using Multiple GitHub Applications") with two orgs, `org-a` and `org-b`, each with its own `webhook_secret`. `org-b/victim-repo` has a tracked `Stack`.
2. As an admin of `org-a`'s own GitHub App, take the known `org-a` `webhook_secret` and build a JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a-webhook_secret, body)>`.
4. `POST /webhooks` with header `X-Github-Event: push`, the above signature and body.
5. `WebhooksController#verify_signature` resolves `repository_owner => "org-a"`, fetches org A's `GitHubApp`, and `verify_webhook_signature` succeeds ( [7](#0-6) ).
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` ( [3](#0-2) ) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `org-b`'s stack — a cross-organization write triggered using only `org-a`'s own credentials.
