### Title
Private assets sent to an Autonomous Agent become permanently frozen because AAs can never spend them out - ([File: aa_composer.js])

### Summary
Similar to the reported `Subaccount` issue where a contract can be sent ETH but has no mechanism to make use of it, an Obyte Autonomous Agent (AA) address can receive a private-asset payment, but the AA's oscript logic can never construct a valid outgoing payment for that asset. Any private-asset funds sent to an AA address are consensus-level permanently stuck.

### Finding Description
When an AA composes its response unit, every `payment` message for a non-base asset is checked against the asset's properties, and if the asset `is_private`, the message is unconditionally rejected with `"sending private asset from AA"`: [1](#0-0) 

The comment on this line explains the root cause: private payments require `spend_proofs` (hash commitments over the previous owner, blinding factor, and amount) that are generated and validated only for real private-payment chains with hidden outputs; an AA's deterministically-composed unit cannot produce these, so any private-asset payment message an AA definition tries to send would fail unit validation anyway. Because of this, `sendUnit` bounces before even attempting to build such a unit.

On the receiving side there is no equivalent restriction: nothing in `validatePayment` / `validatePaymentInputsAndOutputs` (used for both public and private payments) prevents the final open output address of a private-asset payment chain from being an AA address: [2](#0-1) [3](#0-2) 

The only client-side guard against risky payments to AAs, `checkAAOutputs` in `aa_addresses.js`, checks only that `bounce_fees` are met — it has no notion of asset privacy and does not block private-asset outputs to AA addresses: [4](#0-3) 

Furthermore, private outputs are explicitly excluded from `aa_balances` accounting (`AND (is_private=0 OR is_private IS NULL)`), meaning the AA's own state/balance tracking never even reflects the receipt, reinforcing that the AA has no programmatic path to ever move this value again: [5](#0-4) 

So the full picture: a user (or an attacker griefing another user, e.g. tricking a wallet UI, a textcoin flow, or a private-asset marketplace integration into treating an AA address as a normal recipient) can send a private-asset payment to any AA address. The transfer validates and finalizes normally (private payment chain semantics don't check the recipient type), but the AA can never re-emit that asset in a response, since `aa_composer.js` bounces any attempt to do so.

### Impact Explanation
Any private asset sent to an AA address is permanently and irrecoverably locked — there is no way, through the AA's own logic or otherwise, for the funds to be spent, returned to the sender, or otherwise recovered, because the AA authoring key/mechanism cannot produce valid spend proofs. This matches the "AA fund loss or freezing" impact category: value is provably and permanently destroyed/inaccessible, which is a direct financial loss for whoever sent the private asset (by mistake, by a buggy wallet/integration, or via an attacker-crafted request that lures a victim into paying a private asset to what looks like a normal address).

### Likelihood Explanation
Likelihood is real but not trivial to trigger by pure accident, since most AA-interacting tooling defaults to base-asset payments. However:
- Nothing in consensus validation or in `checkAAOutputs` blocks it, so it can be reached by any user or any wallet/service that supports arbitrary private-asset transfers and lets the address be entered/selected freely (e.g., private-asset textcoins, marketplace payouts, custom integrations).
- No warning is surfaced anywhere in the referenced validation path — the loss is silent from the sender's perspective until they realize the AA never reacts to (or forwards) the private funds.

### Recommendation
- Add a consensus-level (or at minimum a wallet/`checkAAOutputs`-level) check that rejects/blocks private-asset payments whose final open output address resolves to a known AA (`aa_addresses` table), analogous to how `checkNotAAs` is already used elsewhere in `validation.js` to prevent AAs from being used as operators/oracles in certain contexts.
- Alternatively, extend AA definition/oscript capabilities so private-asset spend proofs can legitimately be produced for AA-authored payments (a larger protocol change), or explicitly document/enforce that AA addresses must never be used as recipients of private assets, with client-side enforcement in all wallet payment flows (`sendMultiPayment`/`checkAAOutputs`).

### Proof of Concept
1. Define/deploy any AA (e.g. the sample AA at `test/samples/simple_aa.oscript`) which only handles base-asset payments in its `messages`.
2. Issue or acquire a private asset (`is_private: true`) via `indivisible_asset.js` / `divisible_asset.js` private-payment chain mechanics.
3. Using `wallet.js`'s `sendMultiPayment` with `asset` set to the private asset and `to_address` set to the AA's address, send a private-asset payment. Validation succeeds because `validatePaymentInputsAndOutputs` never checks whether the recipient is an AA [3](#0-2) , and `checkAAOutputs` only validates `bounce_fees` for the base asset [6](#0-5) .
4. The private-asset chain finalizes; the AA balance table never even records it (`is_private=0 OR is_private IS NULL` filter) [7](#0-6) .
5. Any attempt to have the AA formula respond with that private asset in a `payment` message bounces with `"sending private asset from AA"` [8](#0-7) , confirming the funds can never be moved out by the AA. The private asset is permanently stranded at the AA address.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
