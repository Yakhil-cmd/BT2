### Title
Webhook org used for signature verification (`repository.owner.login`) is decoupled from the org used to mutate state (`repository.full_name`), allowing cross-tenant stack writes when any configured org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App used to verify the HMAC signature by reading `repository.owner.login` from the *unverified* raw body, while `LabelCapturingHandler` (via `Repository.from_github_repo_name`) resolves and mutates the target stack using `repository.full_name` from the same unverified body. These two fields are never cross-checked, so if any org in the multi-org `github:` config has `webhook_secret` unset (`nil`), an attacker can pick that org for `owner.login` (to make `verify_webhook_signature` unconditionally return `true`) while pointing `repository.full_name` at a completely different, properly-secured org's repository, causing that other org's `PullRequest#labels` to be mutated with no valid signature ever checked against it.

### Finding Description
The claimed binding is: `verified_org` (the org whose `webhook_secret` was used to validate `request.raw_post`) `==` `mutated_org` (the org owning the `Repository`/`Stack` actually written to). Tracing the code shows this equality is never enforced:

- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')`, and calls `github_app.verify_webhook_signature(header, request.raw_post)`. [1](#0-0) , [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is `nil`/blank, regardless of the body content or signature header: `return true unless webhook_secret`. [3](#0-2) 
- `WebhooksController#create` re-parses `params = JSON.parse(request.raw_post)` and dispatches unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
- `LabelCapturingHandler#repository` resolves the target `Repository` using `params.repository.full_name` — a completely separate field from the one used for signature-org selection — via `Repository.from_github_repo_name`. [5](#0-4) 
- The resolved stack's associated `pull_request` is then mutated: `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. [6](#0-5) 
- `ReviewStackAdapter` also reads `params.repository["full_name"]` and `params.sender["login"]` independently for stack lookup/creation, again decoupled from `repository_owner`. [7](#0-6) 

Root cause: nothing in `WebhooksController`, `Shipit::Webhooks::Handlers::Handler`, or `LabelCapturingHandler` asserts that `params.dig('repository','owner','login')` is a prefix of / consistent with `params.repository.full_name`. In a genuine GitHub-originated webhook this is never an issue because GitHub itself generates a truthful, internally-consistent payload and signs the exact bytes with the correct org's secret — any tampering invalidates the signature. The divergence only becomes exploitable when signature verification is bypassed entirely for the org named in `owner.login`, i.e., when that org's `webhook_secret` is `nil`. The engine's own config format explicitly supports per-org `webhook_secret` values that can be blank (see the multi-org shape documented in `docs/setup.md` and mirrored in `test/dummy/config/secrets_double_github_app.yml`, where both `OrgOne` and `OrgTwo` have `webhook_secret: # nil`).

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary one), and body:
```json
{
  "action": "labeled",
  "number": 1,
  "pull_request": { ... "labels": [{"name": "attacker-label"}], "head": {"ref": "...", "sha": "..."} },
  "repository": { "owner": { "login": "OrgWithoutSecret" }, "full_name": "OrgTwo/victim-repo" },
  "sender": { "login": "attacker" }
}
```
`repository_owner` resolves to `OrgWithoutSecret`, whose `webhook_secret` is `nil`, so `verify_signature` passes unconditionally. `LabelCapturingHandler` then resolves the repository/stack via `full_name: "OrgTwo/victim-repo"` and writes attacker-controlled labels into that PR's `PullRequest#labels`, even though `OrgTwo`'s own webhook secret (if any) was never checked.

### Impact Explanation
Any attacker who can reach `POST /webhooks` (no authentication required) can mutate `PullRequest#labels` for an arbitrary repository/stack tracked by Shipit, as long as **any** org configured in the deployment's multi-org `github:` section has a blank `webhook_secret` — regardless of whether the *targeted* org has a properly configured secret. This is a cross-tenant write ("a payload for one repository mutating another's stack") since the org that "authenticated" the request and the org whose data is mutated are unrelated, matching the Critical category. The attack is repeatable against arbitrary stacks/PRs by simply changing `repository.full_name` in the forged body, and other handlers sharing the same `Handler#stacks`/`repository_name` pattern (e.g., `AssignedHandler`, `ClosedHandler`, `OpenedHandler`, `EditedHandler`, `ReopenedHandler`, `UnlabeledHandler`) are similarly reachable through the same decoupled fields, widening the blast radius to archiving/unarchiving review stacks and mutating pull request metadata across tenants. [8](#0-7) 

### Likelihood Explanation
Preconditions: the deployment must use the multi-org `github:` config (documented and supported feature) and at least one configured org must have `webhook_secret` unset/blank — a state the code explicitly anticipates (`return true unless webhook_secret`) rather than rejecting. No attacker secret, session, or privileged role is required; the attacker only needs network access to `POST /webhooks` and knowledge of one org name lacking a secret (which may be discoverable, e.g., a staging/onboarding org) plus the target `full_name`. This makes the attack cheap and fully repeatable once such a configuration exists.

### Recommendation
Bind signature verification and stack resolution to the same trusted identity. Concretely: after computing `repository_owner` for the app selection, validate that `params.repository.full_name` starts with `"#{repository_owner}/"` (reject/422 otherwise) before dispatching to handlers; and/or refuse to treat a webhook as verified when the selected org's `webhook_secret` is blank (fail closed instead of `return true unless webhook_secret`), requiring operators to explicitly opt into unsigned webhooks per-org rather than defaulting to always-valid.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` style, using two orgs both configured with nil `webhook_secret` as in `test/dummy/config/secrets_double_github_app.yml`):

```ruby
test "cross-org label mutation via owner/full_name divergence when signing org has no secret" do
  # Arrange: OrgOne and OrgTwo both configured, OrgOne.webhook_secret is nil
  stack = shipit_stacks(:review_stack_under_org_two) # full_name "OrgTwo/victim-repo"
  pr = stack.pull_request
  assert_not_equal ["attacker-label"], pr.labels

  request.headers['X-Github-Event'] = 'pull_request'
  # No X-Hub-Signature header set / arbitrary value - unsigned

  body = {
    action: "labeled",
    number: pr.number,
    pull_request: {
      id: 1, number: pr.number, url: "https://api.github.com/...", title: "t",
      state: "open", additions: 0, deletions: 0,
      head: { sha: "abc", ref: "feature" },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: "attacker-label" }]
    },
    repository: { owner: { login: "OrgOne" }, full_name: "OrgTwo/victim-repo" },
    sender: { login: "attacker" }
  }.to_json

  assert_changes -> { pr.reload.labels }, to: ["attacker-label"] do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```

Assertion of the binding on both sides: before the request, `verified_org == "OrgOne"` (nil secret, always-true) while `mutated_org == "OrgTwo"` (derived from `full_name`); after the request, `pr.reload.labels == ["attacker-label"]` proves `OrgTwo`'s data was mutated despite `OrgTwo`'s webhook secret never being evaluated — demonstrating `verified_org != mutated_org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
