### Title
`StatusHandler#process` mutates commits by SHA alone, allowing Repo A's signed webhook to overwrite Repo B's commit status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository scoping, and never calls `Handler#stacks` or checks `params.repository`/`repository_name`. `WebhooksController#verify_signature` only proves the payload was signed by the app configured for the `repository.owner.login` named in the payload, but that identity is never cross-checked against the repository that owns the matched `Commit`/`Stack`. Any GitHub org that has installed a Shipit-connected app can trigger writes on any other tenant's commit that happens to share a SHA.

### Finding Description
Binding claimed to hold: `repository_owner_of(commit_matched_by_sha) == repository_owner_that_signed(payload)`. Tracing the code shows this is false.

- `WebhooksController#create` parses the JSON body and dispatches to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_body)` [2](#0-1) . This only proves the *body* was signed with the secret belonging to the org named inside that same body (Repo A) — it says nothing about which `Commit`/`Stack` the handler will end up mutating.
- `StatusHandler#process` is: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . It never calls the base `Handler#stacks` helper (which does scope by `Repository.from_github_repo_name(repository_name)`) and never filters by `params.repository`/`repository_name` at all [4](#0-3) . Compare with other handlers such as `OpenedHandler`/`ClosedHandler`, which correctly resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack-scoped record [5](#0-4) .
- `create_status_from_github!` writes directly into `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) , and `Commit#by_sha`/`Commit.where(sha:)` has no uniqueness constraint scoping SHAs to one repository — the `sha` column is not globally unique across `Stack`s in this schema, so identical commits (e.g., a shared base commit, a cherry-pick, or a rebase producing an identical tree/parents/timestamps) can coexist as separate `Commit` rows in different stacks.

Attacker request: an unprivileged owner of Repo A (which has its own legitimate `webhook_secret` configured in Shipit for Repo A's org) sends `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` for Repo A's secret, and a body where `repository.full_name == "attacker/repoA"` but `sha` equals a SHA that also exists as a `Commit` row under Repo B's `Stack`. `verify_signature` succeeds because the signature is valid for Repo A. `StatusHandler#process` then updates every `Commit` row across the whole database matching that SHA, including Repo B's, regardless of which repository's key signed the request.

None of the listed guards intervene: `verify_signature` validates the signer, not the target being mutated; `drop_unhandled_event` and `ExplicitParameters` only validate payload shape/presence of fields (`sha`, `state`, etc.), not repository ownership of the matched record; `force_github_authentication`/`User#authorized?`/`require_permission!` are session/API-token controls irrelevant to unauthenticated webhook delivery; the `stacks` scope exists on `Handler` but `StatusHandler` simply doesn't use it.

### Impact Explanation
A write happens on Repo B's `Commit#status` (and cascading effects: `deployable_status`/`commit_status` hooks fire, `ProcessMergeRequestsJob` may enqueue, and since the precondition states Repo B's stack has `continuous_deployment?` true with `ignore_ci?` true and its head commit locked to the shared SHA, flipping that commit's state to `success` can make it `deployable?` per `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and potentially trigger downstream deploy scheduling for Repo B — a payload from one repository mutating another's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). This is repeatable against any repository pair as long as the attacker can produce or predict a shared SHA value, and requires no privilege beyond controlling a repository with its own configured webhook app.

### Likelihood Explanation
Requires: (1) the attacker's own repository (Repo A) is a configured Shipit tenant with a legitimate `webhook_secret`, which is a normal, low-cost setup any organization onboarding to Shipit can have; (2) a SHA collision/reuse between Repo A's payload and an existing `Commit` row belonging to Repo B — trivial to arrange deliberately (attacker copies a known public SHA from Repo B, e.g. via a shared open-source dependency, a fork relationship, or a previously observed commit) since `sha` is attacker-controlled plaintext in the JSON body and not verified against Repo A's actual git history by this handler. No GitHub App private key, no `api_clients_secret`, no session is needed — only a normal HTTP POST with a valid HMAC computed from a secret the attacker already legitimately possesses for their own repo.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository that signed the payload: use `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Handler#stacks` (which resolves `Repository.from_github_repo_name(repository_name)`) before calling `create_status_from_github!`, so a webhook can never mutate a `Commit` outside the stacks belonging to the repository named in, and cryptographically bound to, the payload that was verified.

### Proof of Concept
Minitest integration test (`test/controllers/webhooks_controller_test.rb`) plan:
1. Create `repo_a` (`Shipit::Repository`, owner `attacker`) with its own `Stack` and a configured `webhook_secret` for org `attacker` (stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true`, simulating a correctly signed request for Repo A).
2. Use fixture `shipit_stacks(:shipit)` (Repo B, unrelated tenant) with `continuous_deployment: true`, `ignore_ci: true`, and take `commit = shipit_commits(:first)` belonging to Repo B's stack; record `commit.state` before (e.g. `'pending'`/`'unknown'`).
3. Build a status payload: `{ "sha" => commit.sha, "state" => "success", "context" => "ci/attacker", "repository" => { "full_name" => "attacker/repoA", "owner" => { "login" => "attacker" } } }`.
4. `assert_difference('commit.statuses.count', 1)` around `post :create, body: payload.to_json, as: :json` with `X-Github-Event: status`.
5. Assert `commit.reload.state == 'success'` — i.e. Repo B's `Commit#status` changed as a direct result of a payload whose `repository.full_name` was `attacker/repoA`, proving the binding `repository_owner_that_signed(payload) == repository_owner_of(mutated_commit)` does not hold.
