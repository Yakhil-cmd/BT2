### Title
AA balance updates after the initial trigger credit are never re-checked against `MAX_BALANCE`, allowing the tracked balance to exceed the safe accounting cap - (File: aa_composer.js)

### Summary
`GPToke.sol` enforces `points + totalSupply() <= type(uint192).max` only when a stake is first created, but omits the same check when an existing stake is *extended*, letting the tracked total exceed its intended cap. `ocore`'s AA balance accounting has the analogous pattern: the overflow guard against `MAX_BALANCE` is applied only once, when the trigger's own outputs are credited to the AA (`updateInitialAABalances`), but is never re-applied when the AA's balance is subsequently mutated by consumed inputs and outgoing/incoming payment messages processed during the same response (`updateFinalAABalances`).

### Finding Description
`aa_composer.js` defines a safety ceiling for AA balances: [1](#0-0) 

This ceiling is checked in `updateInitialAABalances`, both for the fast in-memory path and the DB-backed path, when the trigger's outputs are added to `objValidationState.assocBalances[address][asset]`: [2](#0-1) [3](#0-2) 

However, `updateFinalAABalances`, which applies the net deltas from `arrConsumedOutputs` (bounced/spent unspent outputs) and from `payment` messages targeting `address` inside the same handler chain (e.g., secondary AA responses, self-payments, or chains of AA-to-AA calls), updates `objValidationState.assocBalances[address][asset]` with no corresponding `MAX_BALANCE` check at all: [4](#0-3) 

Because a single trigger can fan out into a chain of secondary AA invocations (bounces, chained payments) that repeatedly add to the same AA's balance for the same asset, the balance accumulated through `updateFinalAABalances` is never bounded by the same `MAX_BALANCE` guard that protects the initial credit path. This is structurally the same class of bug as the GPToke report: a cap check that exists on the "create/initial" path but is missing on the "update/extend" path that mutates the same tracked total.

### Impact Explanation
`MAX_BALANCE` is deliberately set below `2**63 - 1` to stay within safe integer precision for JS number arithmetic used throughout the AA balance/accounting code (`2 ** 63 - 1 - constants.MAX_MESSAGES_PER_UNIT * constants.MAX_CAP`). If an AA's tracked balance for an asset can be pushed past this via the unchecked `updateFinalAABalances` path (through chained AA responses or repeated self-payments within one trigger's execution), the balance value can silently lose precision or wrap in ways not anticipated by the code that later uses it for payment composition, bounce refunds, and consensus-critical balance bookkeping in `aa_balances`. This can lead to AA balance state that diverges from the true sum of on-chain UTXOs backing the asset, i.e., an accounting-level supply/balance inflation for the affected AA, which downstream can enable the AA to spend or report more of an asset than it legitimately holds.

### Likelihood Explanation
Reaching `updateFinalAABalances` repeatedly for the same AA/asset requires an AA author to design an AA definition (or a trigger sender to invoke an already-deployed self-referential/bouncer-style AA — a common oscript pattern, as demonstrated in the repo's own test suite) that chains payments back into itself many times within the trigger cascade limits (`MAX_MESSAGES_PER_UNIT`, secondary AA depth limits). An attacker fully controls the AA definition and can also control the number/size of payments routed through it over many separate triggers over time, since `updateFinalAABalances` deltas accumulate into the persisted `aa_balances` table across triggers, not just within one trigger execution. This makes gradual accumulation past `MAX_BALANCE` plausible over an extended period without requiring any privileged access — only posting ordinary triggers to an existing or self-deployed AA.

### Recommendation
Apply the same `MAX_BALANCE` overflow check used in `updateInitialAABalances` to the balance mutations performed in `updateFinalAABalances`, e.g.:
```js
for (var asset in assocDeltas) {
    if (assocDeltas[asset]) {
        ...
        objValidationState.assocBalances[address][asset] += assocDeltas[asset];
        if (objValidationState.assocBalances[address][asset] > MAX_BALANCE)
            return cb("balance overflow");
    }
}
```
and propagate the resulting error through the `cb` chain so the response bounces instead of silently persisting an out-of-range balance.

### Proof of Concept
Conceptual sequence (no live execution available in this environment):
1. Deploy an AA `A` whose message logic, upon receiving a trigger, sends a `payment` message back to itself (or to a chain of secondary "bouncer" AAs that eventually pay back into `A`), similar to the `bouncer_aa` pattern used in `test/aa_composer.test.js` (lines 450-526) which chains payments between two AAs within one trigger.
2. Repeatedly send triggers to `A` over many units, each time crediting `A`'s balance through `updateFinalAABalances` deltas that are never checked against `MAX_BALANCE` (only the initial trigger-output credit in `updateInitialAABalances` is checked).
3. Over enough triggers, `objValidationState.assocBalances[A][asset]` (persisted to `aa_balances.balance`) can be pushed past `MAX_BALANCE`, entering the region where `2**63-1` precision-loss issues the constant's own comment (`aa_composer.js:48`) acknowledges are "entirely beyond MAX_SAFE_INTEGER."
4. Because no guard exists on this path, the unit and response continue to validate and apply successfully, unlike a comparable credit through `updateInitialAABalances`, which would bounce with `"balance overflow"`.
