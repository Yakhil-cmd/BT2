### Title
Server-Side Request Forgery in Arbiter Contract HTTP Client Leaks Private Contract Data to Attacker-Controlled URL - (File: `arbiter_contract.js`)

### Summary
When a wallet enters an arbiter contract negotiation with a paired peer, the peer freely chooses the `arbiter_address` that names who will resolve disputes. This address is only format-validated, never checked against a trusted/whitelisted arbiter list, in `wallet.js`. Later, the victim's own wallet resolves a URL for that arbiter (via the arbiter's own hub) and issues unrestricted outbound HTTP(S) requests carrying private contract data (title, text, contact info, party names, and — for private assets — amount/asset) to that URL, with no host allow-listing, no protocol/IP restriction, and no confirmation that the destination is a legitimate ArbStore.

### Finding Description
In `wallet.js`, the `arbiter_contract_offer` message handler accepts an `arbiter_address` supplied entirely by the remote peer device, validating only that it is a syntactically-valid Obyte address: [1](#0-0) 

The offer (including the attacker-chosen `arbiter_address`) is persisted unmodified via `arbiter_contract.store`: [2](#0-1) 

Once the victim later interacts with this contract (`openDispute`, `appeal`, `getAppealFee`, or the internal helper `fillArbstoreAddresses`), the wallet resolves a URL for the attacker-chosen `arbiter_address` and blindly performs an HTTP POST to it, sending the contract's private data: [3](#0-2) [4](#0-3) [5](#0-4) 

The low-level request function performs the request with no scheme, host, or destination restriction — any URL string returned for the arbiter is used verbatim as `http.request` target: [6](#0-5) 

`arbiters.js` exhibits the same unrestricted-fetch pattern for `hub/get_arbstore_url`-resolved endpoints: [7](#0-6) [8](#0-7) 

Because the arbiter identity itself is attacker-chosen (an attacker can act as, or collude with, the named "arbiter" and thus control what URL their own hub reports for `hub/get_arbstore_url`), the victim's own wallet becomes an SSRF/exfiltration client that will fetch or post to whatever host the attacker specifies — the exact bug class described in the Jenkins ECU-TEST advisory (`ATXPublisher.java` sending requests to attacker-specified hosts).

*Uncertainty:* the `hub/get_arbstore_url` request/response protocol itself is implemented on the hub side, which is outside this repository (`ocore--022`), so I could not directly inspect how the hub maps `arbiter_address → url`. The analysis assumes (consistent with the file/table naming, e.g. `arbiter_locations`, `wallet_arbiters`) that this mapping reflects data the arbiter/ArbStore itself publishes, which an attacker acting as their own arbiter fully controls — not a compromise of a third-party hub used by the victim.

### Impact Explanation
An attacker who proposes (or is named in) an arbiter contract can cause the victim wallet to make unrestricted outbound HTTP requests carrying sensitive contract data (contact info, party names, contract text, and for private assets the transaction amount) to any URL of the attacker's choosing. This is a data-exfiltration / SSRF vector reachable purely through the paired-device chat/contract-negotiation channel, without needing a malicious hub or network position — satisfying CWE-918 impact criteria (server sends requests to attacker-specified host, potentially probing internal services or exfiltrating private data).

### Likelihood Explanation
Likelihood is moderate: it requires the victim to accept/interact with an arbiter contract (open a dispute or appeal) where the named arbiter is attacker-controlled, which is a normal user flow for wallets that use the arbiter-contract feature, and the attacker only needs to act as (or register as) an arbiter — no privileged access to hubs or nodes is required.

### Recommendation
- Validate that the resolved arbstore URL uses `https://` and disallow private/loopback/link-local/metadata IP ranges before issuing `httpRequest`/`http.get` in `arbiter_contract.js` and `arbiters.js`.
- Cross-check the arbiter/arbstore mapping against a known/whitelisted registry rather than trusting whatever URL is returned for an arbitrary attacker-chosen `arbiter_address`.
- Warn/prompt the user before any outbound network request is made using contract data tied to a peer-supplied arbiter address, especially prior to first interaction with an unknown arbiter.

### Proof of Concept
1. Attacker device sends the victim an `arbiter_contract_offer` message naming an `arbiter_address` that the attacker controls (a valid-format Obyte address the attacker can also present themselves as arbiter for) — accepted by `wallet.js` after only address-format validation. [9](#0-8) 
2. Victim accepts and later disputes or appeals the contract; the wallet calls `device.requestFromHub("hub/get_arbstore_url", arbiter_address, ...)`, which resolves to a URL the attacker registered for their own arbiter identity. [10](#0-9) 
3. The wallet then issues `httpRequest(url, "/api/dispute/new", dataJSON, cb)`, POSTing contract title/text, contact info, party names, and (for private assets) amount/asset directly to the attacker's server/internal target. [11](#0-10)

function appeal(hash, cb) {
	getByHash(hash, function(objContract){
		if (objContract.status !== "dispute_resolved")
			return cb("contract can't be appealed");
		var command = "hub/get_arbstore_url";
		var address = objContract.arbiter_address;
		if (objContract.arbstore_address) {
			command = "hub/get_arbstore_url_by_address";
			address = objContract.arbstore_address;
		}
		device.requestFromHub(command, address, async function(err, url){
			if (err)
				return cb("can't get arbstore url:", err);
			err = await fillArbstoreAddresses(objContract);
			if (err)
				return cb(err);
			device.getOrGeneratePermanentPairingInfo(function(pairingInfo){
				var my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
				var data = JSON.stringify({
					contract_hash: hash,
					my_pairing_code: objContract.my_pairing_code,
					my_address: objContract.my_address,
					contract: {title: objContract.title, text: objContract.text, creation_date: objContract.creation_date, me_is_payer: objContract.me_is_payer, my_address: objContract.my_address, peer_address: objContract.peer_address, my_party_name: objContract.my_party_name, peer_party_name: objContract.peer_party_name, arbiter_address: objContract.arbiter_address, amount: objContract.amount, asset: objContract.asset},

					setField(hash, "status", "in_appeal", function(objContract) {
						cb(null, resp, objContract);
					});

		});
	});

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
