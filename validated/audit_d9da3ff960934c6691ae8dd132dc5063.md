### Title
Membership webhook processed without valid signature verification allows unauthenticated escalation into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
The bug class from the report — insufficient verification of state before an authorization-relevant recomputation is performed, allowing a low-trust actor to repeatedly manipulate a value that gates output — maps here to Shipit's webhook signature check: `GitHubApp#verify_webhook_signature` unconditionally passes when no `webhook_secret` is configured for an organization, and the `membership` webhook handler blindly trusts attacker-suppliable payload fields (`team.id`, `member.login`, `action`) to mutate the local `Team`/`Membership` tables that `User#authorized?` relies on. This breaks the binding: **GitHub-asserted team membership == Shipit's locally recorded `Membership`/`Team` state used for authorization**.

### Finding Description
`WebhooksController#verify_signature` resolves the org-specific `GitHubApp` from the payload and calls `verify_webhook_signature`: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Per the setup documentation, the webhook secret is explicitly presented as **optional**: [3](#0-2) 

When an organization is configured without a `webhook_secret` (a documented, valid deployment configuration, not a misconfiguration outside the documented mounting), `verify_webhook_signature` always returns `true`, so `POST /webhooks` is processed with **no cryptographic verification at all** — any unauthenticated internet client can submit an arbitrary event.

The `membership` event handler trusts the payload fully to mutate the authorization-relevant `Team`/`Membership` records: [4](#0-3) 

`find_or_create_team!` locates (or creates) a `Team` by the attacker-supplied `github_id`, and `team.add_member(member)` adds an attacker-chosen GitHub `login` (created on the fly via `User.find_or_create_by_login!`) to that team, all without any signature guaranteeing the request actually originated from GitHub.

`User#authorized?` — the gate for the entire application — trusts this same local state: [5](#0-4) 

```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
```

Combined with `force_github_authentication`, which only requires the requester to complete GitHub OAuth (any real GitHub account) and then checks `authorized?`: [6](#0-5) 

### Impact Explanation
An attacker who knows (or guesses) the numeric GitHub `team.id` of one of the org's authorization-gating teams (`Shipit.github_teams`) can forge a `membership` webhook with `action: "added"` and `member.login` set to a GitHub account they control. If the target organization has not configured a `webhook_secret` — a supported, documented configuration — the forged event is processed with no verification, adding the attacker's real GitHub identity to the local `Team` that grants Shipit access. The attacker then simply logs in through the real (unmodified) GitHub OAuth flow with that same account, passes `authorized?`, and gains full authenticated access to Shipit: triggering deploys, rollbacks, merges, and reading task output/streams for every stack. This matches the report's High-severity accepted category "escalation into `Shipit.github_teams` authorization," and in practice enables unauthorized deploys/rollbacks — a Critical outcome — once inside.

### Likelihood Explanation
Requires no Shipit session, `ApiClient` token, GitHub App private key, or repository write access — only (a) an org that has left `webhook_secret` unset (documented as optional, plausible for many installations), (b) knowledge of a numeric GitHub team ID (discoverable via GitHub's API/UI in many contexts), and (c) a normal, unprivileged GitHub account for the attacker. This is a realistic path for any installation that follows the documented "optional" webhook secret guidance.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than optional; refuse to process webhooks for any organization without a configured secret instead of returning `true`.
- In `MembershipHandler`, cross-check that the asserted `organization.login`/`team` actually correspond to a `Shipit.github_teams`-configured team via a live GitHub API call before mutating membership, rather than trusting the webhook payload as sole source of truth for authorization-relevant state.
- Periodically reconcile/re-verify local `Team`/`Membership` records against GitHub's real team membership (already partially done via `refresh_shard`) and prefer live GitHub API checks for `authorized?` on sensitive operations.

### Proof of Concept
1. Target Shipit instance configured with `Shipit.github_teams` containing a team with GitHub `team.id = 1111` (used to gate authorization), and that org's `github.webhook_secret` left unset per the documented "optional" setup.
2. Attacker (no Shipit account, no API token) sends:
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 1111, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/1111"},
  "organization": {"login": "target-org"},
  "member": {"login": "attacker-gh-login"}
}
```
No `X-Hub-Signature` needed — `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `target-org`.
3. `MembershipHandler#process` finds the existing `Team` (github_id 1111), creates a `User` for `attacker-gh-login`, and adds the membership: `team.add_member(member)`.
4. Attacker completes the standard GitHub OAuth login as `attacker-gh-login` (a normal GitHub account they control), hits `force_github_authentication`, and `authorized?` now returns `true` because of the forged `Membership` row.
5. Attacker now has full authenticated access to trigger deploys/rollbacks/merges on Shipit stacks.

Note: I could not verify from the index alone whether `Shipit.github_teams` team IDs are trivially discoverable in a given deployment (this depends on org configuration/visibility settings), so the practical likelihood of step (2)'s prerequisite (`team.id` knowledge) may vary; a Devin session with full repo/API access would be needed to confirm exact discoverability assumptions and any additional guardrails in `lib/shipit.rb`'s `github_teams` loader that I was unable to fully inspect within the available context.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

          team = find_or_create_team!

          case params.action

            team.add_member(member)
