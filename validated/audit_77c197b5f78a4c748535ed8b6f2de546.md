### Title
Cross-organization webhook forgery via mismatch between the field used to select the signing secret and the field used to select the target repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-tenant Shipit deployment (multiple GitHub organizations configured under `secrets.github`), the webhook signature is verified against the GitHub App secret of the organization named in `repository.owner.login` (or `organization.login`), but every downstream event handler resolves the *actual* target repository/stack from the unverified `repository.full_name` field of the same JSON body. These two fields are never cross-checked, so a valid signature computed with organization A's secret can be replayed with a payload whose `repository.full_name` points at organization B's repository.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App (and therefore which HMAC secret) to verify against using `repository_owner`, itself read straight out of the untrusted, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization config (and hence `webhook_secret`) from `secrets.github` keyed by that same attacker-controlled string: [3](#0-2) 

Once `verify_webhook_signature` returns true (HMAC-SHA1 of the raw body matches organization A's `webhook_secret`), the controller dispatches the parsed body to the registered handlers, unmodified: [4](#0-3) 

Every handler, however, resolves the repository/stack to act on using a *different* JSON field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`: [5](#0-4) 

This is used identically by `PushHandler`, the pull-request handlers, and others: [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handlers act on`

Because `repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/action) are independent, attacker-supplied fields inside the same signed body, an attacker who legitimately controls one onboarded organization (and therefore possesses that organization's real `webhook_secret`, e.g. by configuring their own GitHub App/webhook delivery, which is a normal, unprivileged administrative action for their own org) can craft and correctly sign a payload where:
- `repository.owner.login` / `organization.login` = "org-they-control" (selects their own valid secret for verification)
- `repository.full_name` = "victim-org/victim-repo" (the actual repo acted upon by the handler)

Since the signature only proves the payload came from someone possessing org-they-control's secret, not that the referenced repository belongs to that organization, the check passes and the forged event is processed against the victim org's stack.

### Impact Explanation
This breaks the deployment-trust binding between the authenticated GitHub organization and the repository whose stacks are mutated. Concretely, an attacker who controls one tenant's GitHub App/webhook secret in a multi-org Shipit instance can:
- Force `PushHandler` to trigger `GithubSyncJob` / `stack.sync_github` on a victim organization's stack with an attacker-chosen `after` SHA, influencing which commit is considered "head" for sync and downstream deploy eligibility.
- Trigger pull-request handlers (`opened`, `labeled`, `closed`, etc.) against the victim's `Repository`/`ReviewStack`, manipulating merge-queue/review-stack state for a repository the attacker does not own.

This constitutes cross-repository/cross-organization writes performed without holding any credential tied to the victim organization, matching the "cross-repository writes" Critical impact class in scope.

### Likelihood Explanation
Requires only that the target Shipit instance is configured for more than one GitHub organization (`secrets.github` keyed by multiple org names) and that the attacker is a legitimate admin of at least one of those onboarded organizations able to see/configure that org's webhook secret — no Shipit session, API token, or victim-org credential is needed. This is a realistic configuration for shared/multi-tenant Shipit deployments, though single-org deployments (the common case) are not affected since `github_default_organization` would be `nil` and there is only one secret.

### Recommendation
After verifying the HMAC signature, cross-check that the organization used to select the verification secret (`repository.owner.login`/`organization.login`) matches the organization portion of `repository.full_name` used by the handlers, and reject the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same authenticated organization identity rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Deploy Shipit configured with two GitHub organizations, `org-attacker` and `org-victim`, each with its own `webhook_secret` under `secrets.github`.
2. Attacker (legitimate admin of `org-attacker`) builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker's webhook_secret, raw_body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-attacker")` and validates the signature successfully (it was computed with the correct secret for that org).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-victim/victim-repo")`, finds the victim's stack (unrelated to `org-attacker`), and enqueues `GithubSyncJob`/`stack.sync_github` for it — despite the request never being authenticated by anything belonging to `org-victim`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
