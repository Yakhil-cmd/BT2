## Analysis

CVE-2017-7551 describes an authentication oracle: 389-ds-base returned different, distinguishable return codes for "account locked" vs "wrong password," letting an attacker efficiently brute-force credentials. The closest reachable analog in `ocore` is the **hash-lock authentifier check** in `definition.js`, which is a password-like spending condition (`['hash', {hash: 'base64'}]`) that any unit poster can trigger by submitting authentifiers for evaluation, and whose secret-comparison and error-reporting logic behave differently depending on how close/valid a guess is — creating a usable oracle for brute-forcing the locking secret.

### Title
Non-constant-time hash-secret comparison and differentiated error branch leak information enabling brute-force of hash-locked address secrets - (File: definition.js)

### Summary
Address/asset conditions in oscript support a `['hash', {algo:'sha256', hash:'base64'}]` authentifier, which locks spending behind knowledge of a secret preimage (a password-like mechanism, frequently combined in `or`/`and` branches with `sig` for recovery/backup paths). The preimage comparison in `validateAuthentifiers` uses plain JavaScript `===` string comparison rather than a constant-time comparison, and on mismatch sets a specific `fatal_error` string ("bad hash at path ...") that is propagated all the way to the unit submitter as the validation error, distinct from the generic "authentifier verification failed" / "some authentifiers are not used" errors returned for structurally different failures.

### Finding Description
In `definition.js`, the `hash` authentifier branch is: [1](#0-0) 

The equality check `args.hash === crypto.createHash("sha256")...digest("base64")` is a short-circuiting, non-constant-time string comparison. When it fails, `fatal_error` is set to `"bad hash at path "+path`, which is distinct from the case where the authentifier is simply missing (`cb2(false)` with no `fatal_error` set), and distinct from the generic terminal errors: [2](#0-1) 

This `fatal_error` (when set) is returned as the hard `err` to the outer caller instead of a plain `res=false`, and that `err` is forwarded verbatim as the unit's validation-failure message to whoever submitted the unit: [3](#0-2) 

The combination of (a) a non-constant-time comparison of a secret value supplied entirely by the attacker in a network-visible authentifier field, and (b) a distinguishable, path-specific error message returned only when the guess reaches the comparison step (versus a generic failure when it does not), mirrors the CVE-2017-7551 bug class: different, information-leaking response behavior for different classes of failed authentication attempts, which assists an attacker in narrowing down and eventually recovering the secret that guards spending rights.

### Impact Explanation
Any unprivileged party who knows of a `hash`-locked address (e.g., a shared/multi-branch address using `["or", [["hash", {...}], ["sig", {...}]]]` for password-based recovery or a private/textcoin-style redemption path) can repeatedly submit crafted authentifier attempts and observe (1) whether the response is the generic "authentifier verification failed" versus the specific "bad hash at path X" message, confirming the guess was evaluated against the real secret at a known path, and (2) exploit non-constant-time comparison timing differences across repeated attempts. A successful recovery of the preimage secret grants the attacker the authorization needed to spend funds through that branch — i.e., concrete unauthorized spending of funds locked behind that condition.

### Likelihood Explanation
Exploitation requires the attacker to know an address uses a `hash` condition and to be able to send many authentifier guesses cheaply. In `ocore`, authentifier verification for `is_valid_signed_package`/signed messages (`signed_message.js`, reachable via AA triggers/oscript formulas) can be invoked without broadcasting a full paid unit each time, using `Definition.validateAuthentifiers`, which lowers the cost of each probing attempt considerably compared to submitting full DAG units. This makes systematic guessing/timing measurement plausible, though it still requires many round-trips and a realistic secret space (this is a preimage/password design, not a full 256-bit key), so exploitation is more feasible against weak/human-chosen secrets than against random ones.

### Recommendation
Use a constant-time comparison (e.g., `crypto.timingSafeEqual` on fixed-length buffers, after decoding both sides from base64) instead of `===` for the `hash` authentifier check in `definition.js`. Also normalize the `fatal_error` message for hash/signature mismatches to a single generic error text (or suppress path-specific detail) so failed-guess responses are indistinguishable from other authentifier failures, removing the oracle that reveals whether an attacker's guess was evaluated against the real secret.

### Proof of Concept
1. Define an address/asset condition such as `["or", [["hash", {hash: H}], ["sig", {pubkey: P}]]]` where `H` is `sha256(secret)` in base64.
2. Craft a signed message / AA trigger / unit whose `authentifiers["r.0"]` contains a candidate guess string.
3. Submit repeatedly via `Definition.validateAuthentifiers` (e.g., through `is_valid_signed_package` formula evaluation or `signed_message.validateSignedMessage`), observing:
   - "authentifier verification failed" when the authentifier is absent/malformed, vs.
   - a distinguishable `"bad hash at path r.0"` error when the guess reaches the SHA-256 comparison — confirming the guess format is correct and pinpointing the exact branch/path holding the secret.
4. Combine this oracle with timing measurements of the `===` comparison across repeated guesses to iteratively narrow down the preimage, eventually reconstructing `secret` and gaining spending authorization on the address.
