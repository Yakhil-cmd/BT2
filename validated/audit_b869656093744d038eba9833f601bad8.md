### Title
`Stack#deployable?`/`Commit#deployable?` trust org-blind `Status` rows, letting a cross-org forged status trigger an unauthorized continuous deploy - (File: `app/models/shipit/commit.rb`, `app/models/shipit/stack.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit purely by `sha` (`Commit.where(sha: params.sha)`) with no check that the webhook's `repository.full_name`/owner matches the commit's own stack/repository. `Commit#deployable?` and `Stack#next_expected_commit_to_deploy` then treat any `Status` row attached to a commit as equally authoritative regardless of which org's webhook wrote it, so a forged status from an attacker-controlled, Shipit-known org can make a victim stack's commit "deployable" and get it auto-deployed by `ContinuousDeliveryJob`.

### Finding Description
Binding that should hold: `status.created_by_org == commit.stack.repository.owner` (WEBHOOK PROVENANCE) for every `Status` row that `Commit#deployable?` counts as evidence. In the actual code this binding is never checked:

- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
It never filters by `repository_name`/`stacks` the way every other handler does (`Handler#stacks` in `app/models/shipit/webhooks/handlers/handler.rb:32-38` scopes via `Repository.from_github_repo_name(repository_name)`, but `StatusHandler` bypasses `stacks` entirely and matches purely on `sha`).
- The only gate before this handler runs is `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`), which validates the HMAC against `Shipit.github(organization: repository_owner)` — i.e., it proves the request came from *some* GitHub org already configured in this Shipit instance, not that it came from the org that owns the target commit's stack.
- `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is purely `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `success?`/`status` are derived from `statuses_and_check_runs` (`app/models/shipit/commit.rb:144-146`, `304-306`) with no re-check of which org's webhook produced each `Status`.
- `Stack#next_expected_commit_to_deploy` (`app/models/shipit/stack.rb:332-342`) does `commits_to_deploy.find(&:deployable?)`, inheriting the same blind trust.
- `Stack#deployable?` (`app/models/shipit/stack.rb:376-378`) only checks lock/active-task/provisioning state — nothing about status provenance.
- `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) and the periodic scheduling in `lib/tasks/cron.rake` enqueue `ContinuousDeliveryJob`, which calls `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:211-229`), which calls `next_commit_to_deploy`/`trigger_deploy(commit, Shipit.user, ...)`, launching a real `Deploy` task.

Attacker exploit flow: attacker owns (or administers) a repository under a GitHub organization already onboarded to the target Shipit instance (so `verify_signature` passes with a legitimate signature for *their own* org). They send `POST /webhooks` with `X-Github-Event: status`, `repository.full_name` set to their own repo, but `sha` set to the sha of a commit that exists in the victim stack (git SHAs of tracked branches/commits are not secret — visible via GitHub or the Shipit stack page itself) and `state: success` matching the victim stack's `required_statuses`/context. `StatusHandler` looks up `Commit.where(sha: ...)` globally, finds the victim's `Commit` row, and calls `create_status_from_github!`, writing a `Status` owned by the attacker's org onto the victim's commit. On the next `ContinuousDeliveryJob` run (or when the commit gets rescheduled through `cron.rake`'s `schedule_continuous_delivery`), `Commit#deployable?` sees `success?` true and `blocked?` false, `Stack#next_expected_commit_to_deploy` selects that commit, and `trigger_continuous_delivery` fires a real `Deploy` against the victim's production stack.

None of the listed guards close this gap: `verify_signature`/`GitHubApp#verify_webhook_signature` only prove "some onboarded org sent this," not "the owning org of this commit sent this"; `ExplicitParameters` only validates payload shape; `force_github_authentication`/`User#authorized?`/`require_permission!`/`stacks` scope are irrelevant because this is an unauthenticated webhook path, not a session/API path; model validations don't constrain `Status#stack_id`/commit association to the webhook's declared repository.

### Impact Explanation
An attacker with control of a single GitHub org/repo already recognized by the target Shipit instance can write arbitrary `Status` rows on any commit (identified only by `sha`) belonging to any other stack/org managed by the same Shipit instance, and thereby cause `Commit#deployable?`/`Stack#next_expected_commit_to_deploy` to select and auto-deploy that commit through `ContinuousDeliveryJob` → `Stack#trigger_deploy` → real `Task`/`Command` execution of the victim's `shipit.yml` deploy steps. This is an unauthorized deploy of one tenant's code triggered by another tenant's forged webhook — Critical impact ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the victim stack must have `continuous_deployment` enabled and satisfiable `required_statuses`/`soft_failing_statuses`; the attacker must control/administer a repo under an org already configured in this Shipit instance (so their own webhook signature verifies) and must know a target commit sha (feasible for public repos or repos the attacker has any visibility into, e.g., through a shared upstream or fork). Given those, the exploit is cheap and repeatable per commit/target stack, requiring only one crafted HTTP POST with a valid signature for the attacker's own org.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the stacks reachable from the webhook's own `repository.full_name` (mirroring `Handler#stacks`) instead of a global `Commit.where(sha:)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`. Additionally, consider recording/validating the originating repository on `Status` and having `Commit#deployable?`/`Status::Group` reject statuses whose recorded repository does not match `commit.stack.repository`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/stack_test.rb` style, no live GitHub, using `GithubHook.any_instance.stubs(:verify_signature).returns(true)` per existing test pattern):
```ruby
test "cross-org status webhook makes a foreign commit deployable and triggers a deploy" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, required_statuses: ['ci/travis']
  victim_commit = shipit_commits(:undeployed_no_status) # belongs to victim_stack, no statuses yet

  refute_predicate victim_commit, :deployable?

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates a valid signature for attacker-org

  assert_difference -> { victim_commit.statuses.count }, 1 do
    @request.headers['X-Github-Event'] = 'status'
    post :create, body: attacker_payload, as: :json
  end

  victim_commit.reload
  assert_predicate victim_commit, :deployable?
  assert_equal victim_commit, victim_stack.next_expected_commit_to_deploy

  assert_difference -> { victim_stack.deploys.count }, 1 do
    victim_stack.trigger_continuous_delivery
  end
end
```
Assertions on both sides of the equality: before the forged status, `victim_commit.deployable?` is `false` and no `Status` exists tying provenance to `victim_stack.repository`; after the forged cross-org webhook, `victim_commit.deployable?` is `true` and a `Deploy` is created — demonstrating the broken `status.created_by_org == commit.stack.repository.owner` binding.
