### Title
`StatusHandler#process` resolves commits by SHA globally, letting a status webhook from one repository flip `ci_enabled` on another repository's `Stack` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` without scoping to the repository named in the verified webhook payload, unlike other handlers (`push_handler.rb`, `check_suite_handler.rb`, `pull_request/*`) which all resolve targets through the `stacks` helper that filters by `Repository.from_github_repo_name(repository_name)`. Because git commit SHAs are content-addressed and can be identical across unrelated repositories (e.g. forks or repos sharing an initial commit), a legitimately signed status webhook for an attacker-owned/controlled repository can match a `Commit` row belonging to a victim `Stack`, triggering `Status#after_create :enable_ci_on_stack` → `commit.stack.enable_ci!`, mutating the victim's persistent `ci_enabled` flag.

### Finding Description
The broken binding: `payload.dig('repository','full_name')` (the repository the webhook signature at `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) actually authenticates) should equal the repository owning the `Stack` whose `enable_ci!` is invoked, but it does not.

Path:
- `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) verifies the HMAC signature against `Shipit.github(organization: repository_owner)`'s webhook secret, where `repository_owner` is derived purely from `params.dig('repository','owner','login')` of the *attacker's own payload*. This proves only "this payload was signed for organization X," not "this payload's `sha` actually belongs to organization X's history."
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` across the *entire database*, with no `stacks`/`repository_name` filter, unlike the base class helper `stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) that other handlers use to scope by `Repository.from_github_repo_name(repository_name)`.
- `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` (app/models/shipit/commit.rb:165-169) creates a `Status` with `stack_id` set to the *matched commit's own stack* (the victim's), not the attacker's repository.
- `Status#after_create :enable_ci_on_stack` (app/models/shipit/status.rb:18,38-40) calls `commit.stack.enable_ci!`, a persistent write on the victim `Stack` row, regardless of the status `state` value (no state check gates this callback).

Exploit flow: an attacker who owns/administers any repository that is a tracked Shipit stack (so a real, validly-signed GitHub status webhook can be delivered for it) crafts a commit whose SHA collides with a commit SHA that already exists in a victim's stack (trivially achievable by forking/cloning a public repo and reusing shared history, or by constructing byte-identical commit objects). GitHub sends a `status` event for the attacker's repository/organization; the signature check passes because it is a genuine webhook for that org. `StatusHandler#process` then matches the *victim's* `Commit` row (same SHA, different stack) and creates a `Status` bound to `stack_id` of the victim stack, firing `enable_ci_on_stack` on the victim's `Stack`.

None of the existing guards prevent this: `verify_signature` only authenticates the organization tied to the payload's own `repository`, not the SHA's ownership; `drop_unhandled_event` and `ExplicitParameters` schema only validate presence/type of `sha`/`state`, not repository binding; there is no `force_github_authentication`, `require_permission!`, or model validation between `Status`, `Commit`, and the repository named in the payload.

### Impact Explanation
A payload authenticated for repository/organization A causes a persistent state mutation (`ci_enabled` flip via `enable_ci!`) on a `Stack` belonging to unrelated repository/organization B, with no permission check — this matches the "Critical: a payload for one repository mutating another's stack" category. `ci_enabled?` gates whether `Commit#deployable?` requires CI success (`stack.ignore_ci? || (success? && !blocked?)`, app/models/shipit/commit.rb:227-229) and other CI-gating logic; forcing it on can make previously CI-gated commits deployable without ever running CI, enabling downstream unauthorized deploys. This is repeatable against any stack whose commits share a discoverable/colliding SHA with an attacker-influenced repository, and the write is not reversible from the attacker's side but is a real cross-tenant record mutation.

### Likelihood Explanation
Preconditions: victim `Stack#ci_enabled?` is `false` (either `ignore_ci: true` or CI never enabled); the attacker needs a repository that is itself a Shipit-tracked stack capable of generating a validly signed `status` webhook (i.e., the attacker's own onboarded repo, or any repo under an org whose webhook_secret they can trigger legitimately via GitHub itself — no Shipit secrets needed); and a commit SHA collision with the victim's commit, which is realistic for forks/mirrors of the same source history (shared ancestor commits) but requires deliberate content-identical commit construction otherwise. Cost to the attacker is a normal GitHub push/status action on a repo they control; feasibility depends on how easy it is to get a SHA that coincides with a targeted victim commit, which is high for forked/cloned repositories sharing history, lower for arbitrary unrelated targets.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring the `stacks` helper pattern used by other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so a status can only ever be attached to, and mutate, a `Commit`/`Stack` that belongs to the repository the webhook signature actually authenticated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or similar, no live GitHub required):
```ruby
test "a status webhook for repository A must not enable CI on a colliding-SHA commit belonging to stack B" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine" e.g.
  attacker_repo_name = "attacker/unrelated-repo"
  victim_stack.update!(ignore_ci: true) # simulate ci_enabled? == false precondition
  refute victim_stack.reload.ci_enabled?

  colliding_sha = shipit_commits(:first).sha
  # commit belongs to victim_stack; attacker's payload names a different repository
  payload = {
    'sha' => colliding_sha,
    'state' => 'pending',
    'context' => 'attacker/ci',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => attacker_repo_name, 'owner' => { 'login' => 'attacker' } }
  }

  # binding under test: payload['repository']['full_name'] (attacker_repo_name)
  #                      != victim_stack.repository.full_name
  assert_not_equal attacker_repo_name, victim_stack.repository.full_name

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert victim_stack.reload.ci_enabled?, "victim stack's ci_enabled flipped due to an attacker-signed payload for an unrelated repository"
end
```
This demonstrates `victim_stack.reload.ci_enabled?` becomes `true` purely as a side effect of processing a webhook whose `repository.full_name` does not match the victim stack's repository, confirming the broken binding.
