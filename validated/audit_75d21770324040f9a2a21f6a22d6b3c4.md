### Title
Cross-organization webhook signature confusion allows forged commit statuses on any stack, enabling unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The bug class in the report is a mismatch between the value used to authorize/validate an operation and the value actually acted upon (LP tokens minted using unchecked, attacker-influenced inputs instead of a value tied to the real contribution). The analogous binding break in `shipit-engine` is: **the GitHub organization whose secret validates the webhook signature ≠ the repository whose data the webhook handlers actually mutate**. `WebhooksController#verify_signature` selects the signing key from a payload field, but `Webhooks::Handlers::StatusHandler` (and other handlers) act on a *different, unchecked* payload field to determine target scope.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App / webhook secret to validate the HMAC signature with, based on payload content, not a fixed per-org endpoint: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) straight from the attacker-supplied JSON body. Because the signature is an HMAC over the raw body computed with the secret configured for *that same org* (`Shipit.github(organization: repository_owner)` → `GitHubApp#verify_webhook_signature`), an attacker who knows/controls the webhook secret for **any one** GitHub organization integrated with this Shipit instance can self-sign an arbitrary JSON payload with that org's secret: [3](#0-2) 

Once the signature check passes, the handler dispatch is decoupled from `repository_owner` entirely. For the `status` event, `StatusHandler#process` does not scope by repository/organization at all — it looks up **any** commit in the entire database by `sha`: [4](#0-3) 

`Commit#create_status_from_github!` then records the forged status unconditionally: [5](#0-4) 

This breaks the equality: `organization that authenticated the request` == `organization/repository whose data is written`. The signature only proves "the sender knows org A's secret"; it proves nothing about which repository or commit the payload content refers to, and the handler layer never re-checks that binding for status updates.

### Impact Explanation
`Commit#deployable?` and `Commit#schedule_continuous_delivery` gate deploys on the commit's `status` (built from `statuses`/`check_runs`), which is exactly what `StatusHandler` writes: [6](#0-5) [7](#0-6) 

An attacker who has legitimate access to configure/own one GitHub organization onboarded to this shared Shipit instance (and thus knows that org's `webhook_secret`) can forge a `status` webhook with `state: "success"` for an arbitrary commit SHA belonging to a **completely different, victim** stack/repository. If that SHA matches an undeployed commit on a continuous-deployment-enabled stack, this fabricates a passing CI status and can trigger an automatic, unauthorized deploy (`schedule_continuous_delivery` → `ContinuousDeliveryJob`), or unblock a manual deploy button that was gated on CI success — without ever touching the victim repository's real CI or its actual webhook secret. This satisfies the "unauthorized deploy" Critical-impact criterion, achieved purely by exploiting the payload/signature binding, with no `ApiClient` token, session, or GitHub App private key required for the victim stack.

### Likelihood Explanation
Requires the attacker to be integrated into the same multi-tenant Shipit instance as another (victim) organization/stack, and to know their own org's `webhook_secret` (which they legitimately possess, since it's their own webhook configuration). No other credentials for the victim repository are needed, and the `sha` lookup in `StatusHandler` has zero repository scoping, so any commit SHA present anywhere in the instance's database is reachable. This is straightforward to exploit for anyone administering an org already connected to a shared Shipit deployment (a realistic and commonly-deployed configuration, since `Shipit.github_organizations` / `github_app_config` explicitly support multiple orgs sharing one instance).

### Recommendation
- Do not select the verification secret from unauthenticated payload content; verify against every configured org's secret and require the org that verified to match the org derived from `repository.full_name` before dispatching.
- In `Handler#stacks`/`StatusHandler#process`, scope commit/status lookups to the repository identified in the payload (and confirm that repository's owning organization equals the organization whose secret verified the signature) rather than doing a global, unscoped `Commit.where(sha: ...)`.
- Reject webhooks where `repository.owner.login` does not match the actual repository record's known owner for the resolved stack.

### Proof of Concept
1. Attacker owns/administers GitHub org `attacker-org`, which has a stack registered in the shared Shipit instance, and thus knows `attacker-org`'s configured `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" },
  "sha": "<victim-stack-undeployed-commit-sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `attacker-org`, verifies successfully against `attacker-org`'s secret. [1](#0-0) 
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim's commit, unrelated to `attacker-org` — and writes a forged "success" status. [4](#0-3) 
6. If the victim stack has continuous deployment enabled or gates manual deploy on CI status, this forged status can trigger or unlock an unauthorized deploy via `Commit#schedule_continuous_delivery`. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
