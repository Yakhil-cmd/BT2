I found a concrete confused-deputy analog in the webhook signature-verification path, where the field used to select the verifying credential differs from the field used to determine which repository/stack is actually written.

### Title
Webhook organization used for signature verification is not bound to the repository the payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, derived from `params.dig('repository','owner','login')` (or `params.dig('organization','login')` as a fallback). However, every downstream `Webhooks::Handlers::Handler` resolves the affected `Repository`/`Stack` independently, from `payload.dig('repository','full_name')`. In a multi-organization Shipit deployment (as documented in `config/secrets.development.shopify.yml`, which supports multiple `github:` orgs each with their own `webhook_secret`), these two fields are never cross-checked against each other.

### Finding Description
The equality that should hold is: `organization whose secret authenticated the request == organization that owns the repository being mutated`. The code breaks this binding:

- `verify_signature` picks the credential purely from `repository.owner.login` (or `organization.login`) in the unauthenticated JSON body: [1](#0-0) , using `repository_owner` computed at [2](#0-1) .
- Handlers, however, resolve the actual repository/stack to act on from `payload.dig('repository', 'full_name')`, completely independent of `repository.owner.login`: [3](#0-2) . The same pattern repeats in every pull-request handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, etc.), each of which independently does `Repository.from_github_repo_name(params.repository.full_name)`, e.g. [4](#0-3) .
- `Repository.from_github_repo_name` simply splits the `owner/name` string with no validation against any other field: [5](#0-4) .
- `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically verified (`return true unless webhook_secret`): [6](#0-5) .

In a multi-tenant Shipit instance (the engine explicitly supports this, see the multiple `github:` org keys in `config/secrets.development.shopify.yml:5-23`), a legitimate GitHub App owner for organization A can send a POST directly to `/webhooks` with `repository.owner.login` = `"org-a"` (so `verify_signature` selects org A's app config, whose `webhook_secret` they legitimately know because they administer that GitHub App) but with `repository.full_name` = `"org-b/victim-repo"`. The HMAC signature is computed correctly against org A's secret and raw body, so `verify_signature` passes, yet the handler dispatch resolves and mutates `org-b/victim-repo`'s `Stack`/`PullRequest`/`ReviewStack` records — a repository the sender was never authorized to control the GitHub App for.

### Impact Explanation
This breaks the authorization boundary between tenants of a multi-organization Shipit deployment: the org whose credentials the signature check "trusts" is not the org whose repository/stack is actually mutated. Depending on webhook type, an attacker controlling one onboarded organization can, for another organization's repository:
- Create/archive/unarchive Review Stacks (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), triggering provisioning/deprovisioning of environments they don't own.
- Force `PushHandler` to trigger `sync_github` against a target stack (queuing `GithubSyncJob`) for a branch/sha of the attacker's choosing.

This does not directly grant `GITHUB_TOKEN` exfiltration or RCE by itself, but it is a cross-repository write / unauthorized state-mutation primitive driven entirely by attacker-controlled, signature-uncorrelated payload fields — matching the "organization that authenticated versus the repository that is written" binding called out in scope.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment with more than one `github:` entry in secrets, and (2) the attacker legitimately controlling the GitHub App/webhook secret for at least one of those configured organizations (which the engine's own setup docs and secrets templates show as a supported configuration). Given that, no further privilege is needed — the attacker crafts and sends the HTTP request directly to the public `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` and/or `Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization used to select the verifying `GitHubApp`/secret matches the owner embedded in `repository.full_name` used for resolving the target `Repository`. Reject (422) whenever `repository.owner.login` does not match the owner segment of `repository.full_name`, and make every handler derive both from the same already-validated field rather than independently re-parsing `payload.dig('repository', 'full_name')`.

### Proof of Concept
Given a Shipit instance configured with two organizations, `org-a` (attacker-controlled GitHub App, known `webhook_secret_a`) and `org-b` (victim, hosting stack `org-b/victim-repo`):

1. Attacker computes `sha1=HMAC(webhook_secret_a, raw_body)` for a crafted `pull_request` "opened" payload where:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
2. POST to `/webhooks` with header `X-Hub-Signature: sha1=<computed>` and `X-Github-Event: pull_request`.
3. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `webhook_secret_a` (`app/controllers/shipit/webhooks_controller.rb:24-30`).
4. `OpenedHandler#process` resolves `repository` via `Repository.from_github_repo_name(params.repository.full_name)` → `org-b/victim-repo`, and provisions/creates a Review Stack for the victim's repository (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:41-54`), despite the request being authenticated only for `org-a`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
