### Title
`WebhooksController#verify_signature` authenticates the payload against the organization derived from `repository.owner.login`, but every event handler acts on the independently-attacker-controlled `repository.full_name` field, allowing cross-repository writes on multi-tenant installs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit installation (the `github: {org1: {...}, org2: {...}}` schema supported by `Shipit.github_app_config`), each configured organization has its own `webhook_secret`. `WebhooksController#verify_signature` picks which secret to check the HMAC against using a field read straight out of the untrusted, not-yet-verified JSON body, then every handler independently re-reads a *different* field of that same body (`repository.full_name`) to decide which `Repository`/`Stack` to act on. Nothing ties these two fields together, so a party who legitimately controls the GitHub App/webhook secret for organization A can forge a signed payload whose `repository.owner.login` is `A` (so it authenticates) but whose `repository.full_name` is `B/some-repo` (so it is *processed* against organization B's stacks).

### Finding Description
`verify_signature` computes the authenticating organization purely from the payload: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [2](#0-1) 

`repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` - itself attacker-supplied JSON, chosen before any signature check. `Shipit.github(organization:)`/`github_app_config` look up the secret configured for that organization name (case-insensitively): [3](#0-2) 

Once `verify_webhook_signature` succeeds, the controller dispatches to handlers using `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and every handler resolves the *actual* repository/stack from a **different** field of the same payload: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, for example, syncs every matching stack of that repository directly from this field: [5](#0-4) 

The equality the code implicitly (and incorrectly) assumes is:

`organization used to select/verify the webhook secret (repository.owner.login) == organization that owns the repository the handlers act on (repository.full_name's owner segment)`

This equality is never enforced. `repository.owner.login` and `repository.full_name` are two independent strings in the same JSON body that GitHub always keeps consistent, but which the attacker is free to make inconsistent since **both** live inside the raw body that gets signed - signing only proves the body was produced by *someone who knows organization A's secret*, not that the repository referenced in that body belongs to organization A.

### Impact Explanation
On any installation using the multi-org `Shipit.github` config schema (documented in `docs/setup.md` and `config/secrets.development.shopify.yml`), an entity that is a legitimate GitHub App owner/administrator for organization A (and thus knows or can obtain org A's `webhook_secret`) can forge webhook deliveries that are authenticated as "from org A" yet target stacks/repositories that belong to org B, C, etc. Depending on the event handler exercised, this can drive `GithubSyncJob` syncs, pull-request/merge-status state changes, or label-driven review-stack provisioning against a repository the attacker was never granted access to - a cross-repository, cross-tenant write triggered purely by crafting a webhook body plus a secret they legitimately hold for an unrelated org. This matches the required "cross-repository writes" / "unauthorized deploy" impact class, since `stack.sync_github` and downstream deploy/merge automation are reachable via `PushHandler` and other handlers without any additional credential belonging to the victim organization.

### Likelihood Explanation
Requires: (1) the installation is configured with the multi-organization `github:` schema (multiple orgs behind one Shipit instance - an explicitly supported and documented configuration), and (2) the attacker has legitimate control of the webhook secret for at least one configured organization (e.g., they administer their own GitHub App/organization that is onboarded to the shared Shipit instance). Given that, forging the payload is trivial (compute HMAC-SHA1 over an arbitrary JSON body with a known secret) and requires no additional access to the victim organization, victim's GitHub App, or Shipit session/API token.

### Recommendation
After `verify_signature` succeeds, re-derive and compare the organization actually used for authentication against the organization segment of `repository.full_name` (and `organization.login`) for every field the handlers subsequently trust; reject the webhook if they diverge. Alternatively, pass the authenticated organization through to `Handler#stacks`/`Repository.from_github_repo_name` and scope the repository lookup to that organization instead of re-deriving it independently from `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org schema).
2. As someone who controls `orga`'s GitHub App/webhook secret, build a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefcafebabe",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, body)>` and POST it to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `orga`'s `GitHubApp`, and the signature validates successfully.
5. `PushHandler#process` is invoked with the same `params`; `repository_name` resolves to `"orgb/victim-repo"`, and `Repository.from_github_repo_name("orgb/victim-repo")` returns the real `orgb` repository, whose stacks get `sync_github` triggered - despite the request only being authenticated as originating from `orga`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
