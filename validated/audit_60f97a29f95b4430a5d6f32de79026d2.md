### Title
No-secret organization webhook auth bypass lets a forged `pull_request` payload write `PullRequest#labels` onto an arbitrary victim repository's stack via `repository.full_name` spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to verify against using `repository.owner.login` from the attacker-controlled JSON body, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's configured `webhook_secret` is blank. The handler that actually applies the payload (`LabelCapturingHandler`, via `ReviewStackAdapter`) resolves the *target* repository/stack independently from `params.repository.full_name` and `params.number`, with no check that this matches the organization used for authentication - so an attacker who owns/controls a "no-secret" GitHub organization can forge a `pull_request` `opened` payload whose `repository.full_name` names a completely different (victim) repository and get `Shipit::PullRequest#labels` overwritten on that victim's review stack.

### Finding Description
The invariant that should hold is:
`organization_used_to_authenticate(request) == organization_owning_the_repository_whose_state_is_mutated(request)`

Tracing the code:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` returns `true` immediately (`return true unless webhook_secret`) when the resolved organization's config has no `webhook_secret`, with **no HMAC check at all** in that case. [2](#0-1) 
- Once past this gate, `LabelCapturingHandler#repository` resolves the target repository independently, from `params.repository.full_name` (not from `repository.owner.login` used above), via `Shipit::Repository.from_github_repo_name`. [3](#0-2) 
- The stack itself is looked up by `environment: "pr#{params.number}"` scoped to that repository's `review_stacks` - a pure string key fully attacker-controlled (`params.number`), not tied to any commit SHA at all. [4](#0-3) [5](#0-4) 
- `capture_labels` then persists attacker-supplied label names onto that stack's `PullRequest`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. [6](#0-5) 

Note: contrary to the question's premise, `LabelCapturingHandler`/`ReviewStackAdapter` does **not** perform any lookup by commit SHA - the stack is resolved purely by `environment` string (`pr<number>`) scoped to the repository derived from `params.repository.full_name`. So "shared commit SHA with attacker repo" is not the actual amplifying mechanism in this code path; the real and directly exploitable divergence is that `repository.owner.login` (used for auth) and `repository.full_name` (used to pick the mutated repository/stack) are two independent, attacker-controlled fields in the same JSON body with no cross-check between them.

Exploit flow: attacker registers/owns a GitHub organization `attacker-org` that happens to be configured in Shipit (e.g., because Shipit auto-discovers or an operator added it) with a blank `webhook_secret`. Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature` set to anything, and body:
```json
{ "action": "opened", "number": 42,
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "pull_request": { ... "labels": [{"name":"MALICIOUS_ENV_KEY"}] }, "sender": {"login":"attacker"} }
```
`verify_signature` authenticates against `attacker-org`'s (secret-less) config and passes trivially. The handler then resolves `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and, if a review stack `pr42` exists there, overwrites its `PullRequest#labels`. Since label names surface as uppercased environment variables in `ReviewStack#env`, this is a cross-tenant write into a victim's deploy-time environment.

No existing guard catches this: `drop_unhandled_event` only checks the event type exists a handler for it; the `ExplicitParameters` schema only validates shape/types, not owner consistency; there is no check anywhere that `params.repository.owner.login == params.repository.full_name.split('/').first`.

### Impact Explanation
An unauthenticated attacker can cause `Shipit::PullRequest#update!` to execute for a victim repository's review stack that the attacker does not own or control, injecting arbitrary label strings that become uppercased environment variables consumed at deploy/task time (`ReviewStack#env`). This is a cross-repository state-mutation primitive triggered entirely by a forged, unauthenticated webhook, matching the "Critical - a payload for one repository mutating another's stack" category. It is repeatable against any victim repository/stack pair whose PR number the attacker guesses or observes, as long as any single Shipit-configured organization anywhere has a blank `webhook_secret`.

### Likelihood Explanation
Requires: (1) at least one GitHub organization configured in Shipit's `github` config without a `webhook_secret` (a real-world misconfiguration, not attacker-controlled, but plausible and the premise explicitly granted by the question), and (2) a victim repository/review-stack with a guessable `environment` (`pr<number>`) key present in Shipit's DB. No GitHub credentials, Shipit session, or API token are needed - only the ability to send an HTTP POST to `/webhooks`. Cost is a single crafted HTTP request; fully repeatable and scriptable.

### Recommendation
In `Shipit::WebhooksController#verify_signature` and in each `pull_request`/`push`/`status` handler, require that the organization used to authenticate the webhook (`repository.owner.login`) matches the owner segment of `repository.full_name` used to select the target repository/stack, rejecting (422) any payload where these diverge. Additionally, treat organizations with a blank `webhook_secret` as unverifiable and reject their webhooks by default (fail closed) rather than treating a missing secret as "always verified."

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.github_config` (via `Shipit.stub(:github, ...)` or fixture config) so organization `"no-secret-org"` maps to a `GitHubApp` with `webhook_secret` blank, while `"victim-org"` has a real secret.
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")` and a `Shipit::ReviewStack` with `environment: "pr42"` under it, plus its associated `pull_request` with `labels: []`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, an arbitrary/garbage `X-Hub-Signature`, and JSON body: `repository.owner.login = "no-secret-org"`, `repository.full_name = "victim-org/victim-repo"`, `number: 42`, `action: "opened"`, `pull_request.labels: [{"name": "INJECTED"}]`.
4. Assert response is `200 OK` (not `422`), establishing the auth bypass: `assert_response :ok`.
5. Assert cross-tenant mutation: `assert_equal ["INJECTED"], victim_stack.reload.pull_request.labels`.
6. Assert the binding equality before/after: before, `repository_owner ("no-secret-org") != full_name_owner ("victim-org")`; after processing, the victim record was still mutated - proving the invariant "a pull_request event only affects the repository whose secret authenticated it" is violated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
