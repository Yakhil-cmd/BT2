### Title
Cross-organization team ID collision in `MembershipHandler#find_or_create_team!` allows privileged team escalation - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up teams solely by `github_id`, with no binding to the organization that signed the webhook. An attacker who owns a GitHub organization configured in `Shipit.secrets.github` (a legitimate, unprivileged tenant) can sign a `membership` webhook with their own `webhook_secret`, set `team.id` to the numeric `github_id` of a pre-existing `Team` row belonging to a different, privileged organization, and get themselves added as a member of that privileged team.

### Finding Description
The broken binding: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` verifies that the request was signed by `evil-org`'s `webhook_secret` (`repository_owner` == `evil-org`, resolved via `params.dig('organization','login')` since `membership` payloads have no `repository` key) — [1](#0-0) [2](#0-1) . But the mutated record is selected purely by `params.team.id`, independent of which organization signed the request: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The block that sets `team.organization` only runs on **creation**; when a `Team` with that `github_id` already exists (created earlier from a legitimate organization present in `Shipit.github_teams`), `find_or_create_by!` returns the existing row untouched, ignoring the `organization` field entirely. `MembershipHandler#process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , appending the attacker's `User` to that existing privileged `Team`'s membership.

Exploit flow: attacker's org `evil-org` has a legitimate entry under `Shipit.secrets.github` (as documented for multi-org setups) [5](#0-4) . Attacker computes `X-Hub-Signature` with their own `webhook_secret` (verified correctly by `GitHubApp#verify_webhook_signature`, which is fine because verification is scoped per-`organization`) [6](#0-5) . Attacker POSTs `X-Github-Event: membership` with `action=added`, `team.id=<github_id of a Team already in Shipit.github_teams>`, `organization.login=evil-org`, `member.login=<attacker's login>`. Signature check passes because it's scoped to `evil-org`. `find_or_create_team!` finds the pre-existing privileged `Team` by `github_id` alone and returns it. The attacker's user is added as a member.

`User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , and `Shipit.github_teams` is the list of `Team` rows corresponding to `github.oauth_teams` [8](#0-7) . Since the attacker's `User` now has a `Membership` in one of those `Team` rows, `authorized?` becomes true, bypassing `Authentication#force_github_authentication`'s authorization gate.

Existing guards do not prevent this: `verify_signature` only proves *who signed*, not *which team/organization the payload claims to mutate matches the signer*; `ExplicitParameters` schema (`params.team.id: Integer`, `params.organization.login: String`) validates types/presence but not cross-organization consistency [9](#0-8) ; there is no uniqueness/foreign-key constraint tying `github_id` to a specific organization at the DB or model layer that would block a second org's payload from resolving to the same `Team` row.

### Impact Explanation
An attacker with no Shipit privileges and no access to any Shipit or GitHub secret beyond their own organization's webhook secret can grant their own GitHub-authenticated identity membership in a `Team` listed in `Shipit.github_teams`, directly flipping `User#authorized?` to `true`. This bypasses `force_github_authentication`'s authorization check, granting the attacker full authenticated access to the Shipit instance (viewing stacks, potentially triggering deploys/rollbacks depending on downstream authorization checks), an authorization-bypass/escalation into `Shipit.github_teams`. Repeatable per attacker-controlled login and per any team ID they can guess/enumerate (team IDs are small sequential integers per the question's precondition); blast radius spans all tenants sharing the same Shipit deployment/team pool, matching the "escalation into `Shipit.github_teams` authorization" High-severity category.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment where the attacker legitimately controls one configured organization (`evil-org`) with its own `webhook_secret` — a normal, permitted setup per `docs/setup.md`'s "Using Multiple Github Applications" section; (2) a `Team` row already existing with a colliding `github_id` from a genuinely privileged org, which the attacker can enumerate since GitHub team IDs are small sequential integers. No Shipit secret, session, or API token is needed beyond the attacker's own webhook secret for their own org — a capability explicitly available to any GitHub org owner. This is low-cost and fully repeatable.

### Recommendation
Bind the `Team` lookup/creation to the organization that authenticated the webhook, not just `github_id`. Specifically: scope `Team.find_or_create_by!` to `(github_id:, organization: params.organization.login)`, and additionally verify that `params.organization.login` matches the `repository_owner`/organization used to authenticate the request (i.e., pass the verified organization into the handler and reject if it mismatches the payload's `organization.login`). Add a uniqueness constraint/validation ensuring `github_id` cannot be silently reused/reassigned across different `organization` values.

### Proof of Concept
minitest `ActionDispatch::IntegrationTest` (or `WebhooksControllerTest` style) plan:
1. Fixture setup: create a privileged `Team` (e.g. `shipit_teams(:shopify_developers)`, `github_id: 1`, `organization: 'shopify'`), and stub `Shipit.github_teams` to include it.
2. Configure two orgs in `Shipit.secrets.github`: `shopify` (privileged) and `evil-org` (attacker-controlled), each with distinct `webhook_secret`.
3. Compute a valid `X-Hub-Signature` using `evil-org`'s `webhook_secret` over a JSON body: `{action: 'added', team: {id: 1, name: 'x', slug: 'x', url: 'https://x'}, organization: {login: 'evil-org'}, member: {login: 'attacker'}}`.
4. POST to `/webhooks` with `X-Github-Event: membership` and the computed signature.
5. Assert response is `:ok` (signature verified against `evil-org`).
6. Assert `Team.find_by(github_id: 1).organization == 'shopify'` (binding equality before: organization signing == organization of mutated team is expected to hold, but does not).
7. Assert `User.find_by(login: 'attacker').teams.include?(shipit_teams(:shopify_developers))` is `true`.
8. Assert `User.find_by(login: 'attacker').authorized?` is `true` — demonstrating the equality "signing org == mutated team's org" is broken and authorization is bypassed.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
