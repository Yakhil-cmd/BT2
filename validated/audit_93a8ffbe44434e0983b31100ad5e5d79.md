The `authorize` function's `VoteAuthorize::Withdrawer` arm performs a strict, unconditional signer check with no OR-relaxation: [1](#0-0) 

This differs fundamentally from the `VoteAuthorize::Voter` and `VoteAuthorize::VoterWithBLS` arms, where the `authorized_withdrawer_signer` OR-condition inside the `epoch_authorized_voter` closure only ever gates *who may set a new voter* — it never touches `authorized_withdrawer`: [2](#0-1) 

The `set_authorized_withdrawer` mutation is reached only after `verify_authorized_signer(vote_state.authorized_withdrawer(), signers)` succeeds, which requires the actual current withdrawer pubkey to be among the transaction signers — a voter-authority-only signer set fails this check regardless of any chaining of prior `Authorize(Voter)` calls, since changing the voter authority never changes `authorized_withdrawer`. There is no code path in this function where holding Voter authority (current or newly granted) satisfies the Withdrawer check.

This is exactly what the existing regression tests assert. `test_voter_base_key_can_not_authorize_new_withdrawer` drives an `AuthorizeWithSeed(Withdrawer)` instruction signed only by the voter base key and asserts `InstructionError::MissingRequiredSignature`: [3](#0-2) 

And its checked-instruction counterpart `test_voter_base_key_can_not_authorize_new_withdrawer_checked` confirms the same for `AuthorizeCheckedWithSeed`: [4](#0-3) 

`test_authorize_withdrawer` further confirms only the withdrawer can authorize the withdrawer (and a new voter), never the reverse: [5](#0-4) 

Since the `Withdrawer` arm has no dependency on `epoch_authorized_voter` or the `authorized_withdrawer_signer` OR-shortcut, a Voter-authority-only attacker cannot escalate to Withdrawer authority through this function, and the premise of the question does not hold against the actual code.
