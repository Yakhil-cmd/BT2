The strongest analog is the utilization cap gating withdrawals. Let me confirm the exact code paths.### Title
Max-utilization gate on withdrawals permanently freezes supplier funds once accrued interest pushes utilization past the cap - (File: contracts/pool/src/guards.rs)

### Summary

The pool applies `require_utilization_below_max` as an absolute post-state check to every non-liquidation withdrawal. Because burning supply shares lowers `supplied` while `borrowed` is untouched, the check uses post-withdrawal utilization — so once market utilization reaches `max_utilization`, *no* withdrawal of any size can pass. Utilization can cross the cap through interest accrual alone (the borrow index grows faster than the supply index since a reserve factor diverts interest), or be pushed to the cap by a single unprivileged borrower, after which accrual tips it over. While in this state, all suppliers' funds are frozen with `UtilizationAboveMax` (error 127), while borrowers are under no obligation to repay and liquidation withdrawals are the only exit that bypasses the gate.

### Finding Description

`guards::require_utilization_below_max` computes post-action utilization as `ceil(borrowed * borrow_index) / floor(supplied * supply_index)` and reverts when it exceeds `params.max_utilization` [1](#0-0) .

`withdraw::accounting` invokes it via `gate_and_debit` for every non-liquidation withdrawal (`is_liquidation || empty_close` decides whether the gate is skipped) [2](#0-1) . The pool README confirms the consequence: "once utilization reaches the cap no withdrawal of any size passes, and interest accrual alone pushes it there" [3](#0-2) .

This mirrors the Flat Money keeper-fee bug class: a cost/condition that grows on its own (gas-derived keeper fee there; accruing debt vs. slower-growing supply here) ratchets until the user-facing exit path reverts unconditionally. There is no admin-free way for a supplier to lower utilization — only repayment or liquidation of *other* accounts' debt releases the cap, and the borrower(s) holding the debt control when that happens.

A single unprivileged attacker can force the state deterministically: supply collateral, `borrow` an amount sized so post-borrow utilization is exactly at (or one accrual tick below) `max_utilization` — the guard accepts `<=` — then wait one accrual interval. Because `borrowed` accrues at the borrow rate while `supplied` accrues at the lower supply rate, utilization strictly increases and crosses the cap. From that point every `withdraw` and every `repay_debt_with_collateral(close_position = true)` withdrawal leg on that market reverts, until the attacker chooses to repay or becomes liquidatable.

### Impact Explanation

Temporary freezing of user funds: all suppliers of the affected market are unable to withdraw any amount for as long as utilization stays above `max_utilization`. The attacker holding the borrow controls the freeze duration; if the attacker keeps HF ≥ 1 (or the position sits in a liquidation-resistant band), there is no permissionless path to unlock the market — `repay` on someone else's debt is allowed but requires a third party to donate funds. Unlike the Flat Money case where elevated fees hit the exiting trader, here no amount of extra payment unlocks the exit; the gate is a hard post-state revert.

### Likelihood Explanation

Medium. Triggering requires a market configured with `max_utilization < RAY` (the guard early-returns at `>= RAY`, which is a governance choice) and enough borrow demand to reach the cap — a normal market outcome near full utilization, not an exotic state. A deliberate attacker only needs sufficient collateral to borrow to the cap; no price manipulation, privileged role, or oracle failure is required. Once crossed, the freeze is self-sustaining: accrual keeps utilization rising, so it cannot drift back below the cap on its own.

### Recommendation

Exempt withdrawals from `require_utilization_below_max` when the withdrawal does not increase risk — e.g., only apply the check when `net_transfer` draws cash that is backing outstanding borrows beyond a permitted floor, or apply it to the pre-withdrawal utilization instead of the post-state. Alternatively, allow withdrawals while utilization is above the cap up to a bounded amount (e.g., a per-account or per-tx draw that keeps `cash` above the liquidation buffer), so supplier exit can never be fully blocked by a state the supplier did not create and cannot fix.

### Proof of Concept

1. Governance configures a market with `max_utilization = 0.95 * RAY` (any value `< RAY`).
2. Attacker `supply`s collateral on a spoke, then `borrow`s on the target market sized so post-borrow `ceil(borrowed*borrow_index) / floor(supplied*supply_index)` equals `max_utilization`. The call succeeds because the guard accepts `<= max_utilization` [4](#0-3) .
3. One interest-accrual tick elapses. `borrowed * borrow_index` grows at the borrow rate; `supplied * supply_index` grows slower (reserve factor). Utilization is now strictly above `max_utilization`.
4. Any supplier calls controller `withdraw` (or `repay_debt_with_collateral` with `close_position`) for that market. `withdraw::accounting` → `gate_and_debit` → `require_utilization_below_max` sees post-state utilization still above the cap (burning supply shares only raises it) and reverts with `CollateralError::UtilizationAboveMax` (127) [5](#0-4) .
5. The freeze persists until the attacker repays, is liquidated (liquidation withdraws skip the gate via `is_liquidation`), or an altruistic third party repays the attacker's debt. Supplier funds are frozen for the attacker's chosen duration at the cost of ordinary interest on their borrow.

```rust
pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
}
```
