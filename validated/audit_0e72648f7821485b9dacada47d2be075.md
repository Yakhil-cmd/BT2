### Title
Webhook signature check is skipped based on an attacker-chosen `repository.owner.login` while the actually-processed repository is a different, unverified field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects *which* GitHub organization's webhook secret to use for signature verification from an attacker-controlled JSON field, and `GithubApp#verify_webhook_signature` unconditionally returns `true` whenever that organization has no `webhook_secret` configured. The field used to pick the verification key (`repository.owner.login`/`organization.login`) is never checked for consistency against the field(s) actually used afterwards by the event handlers (`repository.full_name`) to decide which `Stack`/`Repository`/commit gets mutated. This breaks the binding "organization authenticated == repository written."

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs `verify_signature`, which does: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read from the same untrusted JSON body and is used only to select the `GithubApp` instance/secret used for the HMAC check. In `lib/shipit/github_app.rb`, `verify_webhook_signature` returns `true` unconditionally when the resolved organization has no configured `webhook_secret`:

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

The repository shows this is a normal, supported configuration state (an organization with no `webhook_secret` set), e.g. `config/secrets.development.shopify.yml` explicitly documents `webhook_secret: # nil` per organization.

After `create` passes the signature gate, the actual event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) look up the target `Repository`/`Stack` using a *different* payload field — `repository.full_name` (e.g. in `PullRequest::OpenedHandler#repository`, and equivalently in the push/status/check_suite handlers) — with no re-verification that this repository belongs to the organization that was used to select the signing secret. Because `verify_signature` bypasses HMAC checking entirely for orgs without a secret, an attacker only needs a Shipit instance that has *any* organization configured without a `webhook_secret` (a supported, even example-documented configuration) to submit a JSON body whose `repository.owner.login`/`organization.login` names that unsecured org while `repository.full_name` (and other repository identifiers acted upon by the handler) names an entirely different, tracked repository/organization. The signature check never covers the mismatch between "the org whose key authenticated the request" and "the repository the handler will mutate."

### Impact Explanation
This lets an unauthenticated actor spoof arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against any Shipit-tracked repository/stack, without ever knowing that repository's real webhook secret, as long as one organization on the instance has no secret configured. Concretely this enables: injecting fabricated commit `status`/`check_suite` records that satisfy `ci.require`/`merge.require` gating and unblock continuous delivery or merge-queue merges (unauthorized deploy/merge), or fabricating `push` events to trigger `GithubSyncJob` against a targeted stack. This matches the High/Critical impact categories of unauthorized deploy/merge and escalation into repository state that should require a verified GitHub-signed webhook.

### Likelihood Explanation
Requires no privileged credential, GitHub App key, `ApiClient` token, or session — only that the Shipit instance has at least one organization configured without a `webhook_secret`, a state the codebase itself treats as valid/expected (`return true unless webhook_secret`, and shown as an example config). No cross-checking is performed anywhere between the org used for authentication and the repository referenced in the payload body that handlers actually act on, so exploitation is a single crafted HTTP POST.

### Recommendation
- Do not allow signature verification to unconditionally succeed when `webhook_secret` is blank for production configurations; at minimum, require handlers to verify that the authenticated organization matches the owner of `repository.full_name`/`organization.login` actually processed.
- Cross-validate that `repository.owner.login` (used to pick the signing key) equals the owner segment of `repository.full_name` before dispatching to handlers.
- Consider making `webhook_secret` mandatory (fail closed) rather than optional per organization.

### Proof of Concept
1. Configure/observe a Shipit instance with an organization `unsecured-org` that has `webhook_secret: nil` (a supported configuration per `config/secrets.development.shopify.yml`).
2. Craft a `push` (or `status`/`check_suite`) webhook JSON body where:
   - `repository.owner.login` = `"unsecured-org"` (drives key selection in `verify_signature`)
   - `repository.full_name` = `"victim-org/victim-repo"` (the actually tracked repository/stack in Shipit)
3. POST to `/webhooks` with `X-Github-Event: status` (or `push`) and any/garbage `X-Hub-Signature` header.
4. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank) regardless of the header — request passes.
5. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` processes the event against `victim-org/victim-repo`, injecting a spoofed commit status / push event for that stack, e.g. flipping `ci.require` contexts to `success` to unblock deploy/merge gating on the targeted stack.
