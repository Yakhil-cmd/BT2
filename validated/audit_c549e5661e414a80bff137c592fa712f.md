### Title
Webhook events are authenticated against `repository.owner.login`'s GitHub App but executed against `repository.full_name` - Cross-Organization Forged Webhook Events ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`config/secrets.yml` with one GitHub App per organization), the webhook signature check selects which organization's `webhook_secret` to verify against using `repository.owner.login` (or `organization.login`), but the event handlers that actually mutate state key off `repository.full_name`, a completely different, unverified field. An org onboarded on the same Shipit instance can therefore forge a valid signature for its own GitHub App while targeting a different organization's stack.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` instance (and thus the HMAC secret) to validate the request using: [1](#0-0) [2](#0-1) 

`repository_owner` resolves to `params.dig('repository', 'owner', 'login')`. This value chooses which per-organization `webhook_secret` (configured via `Shipit.github(organization:)` / `github_app_config`) is used to HMAC-verify the raw payload: [3](#0-2) [4](#0-3) 

Once the signature is accepted, the *entire* raw JSON payload (not just the `repository.owner` sub-object) is dispatched unmodified to the event handlers: [5](#0-4) 

But the handlers resolve which `Stack`/`Repository` to act on using `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

e.g. `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching that repository/branch, and `StatusHandler#process` writes commit statuses for any `Commit` matching `sha`: [7](#0-6) [8](#0-7) 

The equality that should hold is:
`organization whose webhook_secret authenticated the request (repository.owner.login)` == `repository/stack that the handler mutates (repository.full_name)`

This equality is never enforced. This is structurally identical to the report's bug class: an "organization that authenticated" (via `verify_signature`/`repository_owner`) is decoupled from "the repository that is written" (via `Handler#repository_name`/`full_name`).

Before the attacker's request: signature verification and state mutation both implicitly assumed to reference the same repository/org, because in a single-organization deployment there is only one `webhook_secret` and one set of onboarded repositories, so `repository.owner.login` and `repository.full_name`'s owner always coincide.

After the attacker's request: in a multi-organization deployment (documented and supported at `docs/setup.md` "Using Multiple Github Applications", and exercised in `test/dummy/config/secrets_double_github_app.yml`), OrgAttacker legitimately possesses/knows its own `webhook_secret` (they configured or administer that GitHub App). They send a POST to `/github/webhooks` with `X-Hub-Signature` computed with OrgAttacker's `webhook_secret`, while setting the JSON body's `repository.owner.login = "OrgAttacker"` (so verification passes) and `repository.full_name = "OrgVictim/victim-repo"` (so the handler acts on OrgVictim's stack).

### Impact Explanation
This lets a party who controls only one tenant's GitHub App/organization on a shared Shipit instance forge state-changing GitHub webhook events for a completely different tenant's repositories/stacks: forcing `Stack#sync_github` to sync to an attacker-chosen `expected_head_sha`, injecting fake commit `Status` records (`state`, `context`, `target_url`) that can satisfy or block deploy-gating checks, or driving `pull_request`/`check_suite`/`membership` handlers against victim stacks. This is a cross-repository/cross-organization write achieved purely by crafting an HTTP request with an authentic signature for the wrong tenant, matching the "Critical - cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires: (a) a Shipit deployment configured for multiple GitHub organizations (explicitly documented/supported), and (b) the attacker controlling/administering one of those onboarded organizations' GitHub App (thus legitimately knowing that org's own `webhook_secret` — not the victim's). Given that condition, exploitation is a single crafted HTTP POST with no other privilege needed; no session, no `ApiClient` token, and no victim secret is required. Likelihood is realistic for any Shipit instance shared across multiple organizations/teams that don't fully trust each other.

### Recommendation
Bind the field used for authentication to the field used for authorization: after `verify_webhook_signature` succeeds, re-derive the acting organization from the same `repository.owner.login`/`organization.login` used for verification, and require that `repository.full_name`'s owner segment matches it before dispatching to handlers (or, better, pass the verified organization explicitly into `Handler.call` and have `Handler#stacks` scope lookups to `Repository` rows belonging to that organization only).

### Proof of Concept
1. Configure Shipit with two organizations, `OrgAttacker` and `OrgVictim`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md` multi-org setup).
2. Attacker (who administers `OrgAttacker`'s GitHub App) computes `X-Hub-Signature: sha1=<hmac>` using `OrgAttacker`'s `webhook_secret` over a crafted JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/victim-repo"
  }
}
```
3. POST to `/github/webhooks` with `X-Github-Event: push` and the above signature/body.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgAttacker"`, fetches `OrgAttacker`'s `GitHubApp`, and validates successfully because the signature was computed with `OrgAttacker`'s secret.
5. `PushHandler#process` resolves `repository_name` = `"OrgVictim/victim-repo"` via `Handler#repository_name` and calls `stack.sync_github(expected_head_sha: "<attacker_chosen_sha>")` on `OrgVictim`'s stacks — a state change on a repository the attacker was never authenticated for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
