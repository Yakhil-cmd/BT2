## Analog Found: Block-Count-as-Time-Proxy in Polkadot Inflation Curve

The Compound `WhitePaperInterestRateModel` bug (assuming 15s/block to convert block counts into a rate) has a direct structural analog in this repo's DOT issuance curve, which uses relay-chain **block counts** as a proxy for **calendar time**, assuming a fixed 6s block time that the codebase's own comments acknowledge is inaccurate.

### Title
Inflation curve step boundaries computed from relay block count assuming fixed 6s block time, causing proportional issuance drift - (File: `system-parachains/asset-hubs/asset-hub-polkadot/src/staking/mod.rs`)

### Summary
`EraPayout::yearly_after_hard_cap` determines which "two-year emission step" Asset Hub Polkadot is currently in by comparing the **relay chain block number** directly against a duration expressed in blocks (`2 * RC_YEARS`), where `RC_YEARS` is a constant computed from an assumed, fixed `MILLISECS_PER_BLOCK = 6000`. Actual relay-chain block production time is not fixed, as evidenced by the code's own comment describing an empirically observed ~6.04875s block time (an 11.7 minute/day drift from the 6s assumption). This causes the stepped issuance curve to advance/retreat relative to true calendar time, producing a systematic, non-self-correcting error in DOT emission proportional to the deviation between assumed and actual block time — the same root cause class as the reported Compound bug.

### Finding Description
`RC_YEARS` is defined purely in terms of blocks, assuming exactly 6000ms/block: [1](#0-0) 

`yearly_after_hard_cap` treats the live `relay_block_num` as if it were a timestamp, feeding it into a `SteppedCurve` whose `start`, `step_duration = 2 * RC_YEARS`, and step comparisons are all expressed in block units: [2](#0-1) 

Meanwhile, the *amount* emitted within a step is scaled by the **actual elapsed milliseconds** (`era_duration_millis`/`elapsed_millis`, sourced from `Timestamp`), not blocks: [3](#0-2) 

This mixes two different clocks: the *rate* per step is anchored to real time, but *which step* (and thus which `yearly_emission` target/slope) is active is anchored to block count under a fixed 6s/block assumption. The codebase's own inline documentation already confirms this assumption is empirically false: [4](#0-3) 

If the relay chain's true average block time diverges from 6s (as it already has, and as could occur further from network conditions, client changes, or future consensus changes), the block-count threshold `2 * RC_YEARS` will be crossed earlier or later than the intended two-year calendar mark. Every era's emission computed via `issue()` during the affected step is proportionally wrong until the next step boundary is crossed (again, at the wrong wall-clock time) — mirroring the cumulative, non-self-correcting nature of the original Compound blocktime bug.

### Impact Explanation
This affects DOT's protocol-level token issuance schedule enforced by `pallet-dap`/`pallet-staking-async` via `IssuanceCurve::issue`, which is exercised on every era transition and directly determines new token minting: [5](#0-4) 
Because the step boundary and post-hard-cap target/rate depend on comparing a live block number to a blocks-denominated threshold, a sustained block-time drift causes the runtime to apply the wrong two-year rate/target for a period of real time proportional to the drift, over- or under-issuing DOT relative to the referendum-approved (Ref 1710) hard-cap emission schedule. Unlike a simple rounding error, this is systematic for the duration of the mismatch and is enforced automatically without any admin/governance intervention correcting it in real time.

### Likelihood Explanation
No attacker action or trusted-role compromise is required — this triggers purely from natural relay-chain block-time variance, which the code's own comments show has already occurred historically (6.04875s vs. assumed 6s). It requires no crafted transaction, XCM message, or privileged origin; it is a passive consequence of the existing `yearly_after_hard_cap`/`RC_YEARS` design being exercised every era under real-world (non-ideal) block production.

### Recommendation
Avoid using relay block numbers as a substitute for calendar time when deciding which step of the emission curve is active. Instead, track step boundaries using the same `elapsed_millis`/timestamp-based clock already used to scale the emission amount (e.g., accumulate real elapsed time since `HARD_CAP_START`, or persist a timestamp-anchored curve start), so that a drift between actual and assumed average block time cannot desynchronize the "which step" decision from the "how much to emit" calculation.

### Proof of Concept
1. Assume actual relay block production averages 6.05s instead of the assumed 6s baked into `RC_YEARS` (`MILLISECS_PER_BLOCK = 6000` at `relay/polkadot/constants/src/lib.rs:47`) — this is the exact drift documented at `system-parachains/asset-hubs/asset-hub-polkadot/src/staking/mod.rs:327-329`.
2. Over a two-year period, this ~0.83% slower block time means `relay_block_num` reaches the `2 * RC_YEARS` threshold in `yearly_after_hard_cap` roughly 0.83% of a year later in real time than intended.
3. During that trailing window, `EraPayout::issue` (called every era in `impl_experimental_inflation_info`/staking issuance flow) continues to apply the *previous* two-year period's `yearly_emission` (computed from the older, generally larger `target_ti - current_ti` before the step's compounding), scaled against real elapsed milliseconds — producing a persistent, proportional overissuance (or underissuance, depending on drift direction) versus the Referendum-1710-approved schedule until the block-count threshold finally catches up, exactly analogous to the Compound `WhitePaperInterestRateModel` blocktime assumption bug.

```rust
	fn yearly_after_hard_cap(relay_block_num: BlockNumber) -> Balance {
		let march_14_2026_ti = FixedU128::saturating_from_integer(Self::MARCH_2026_TI);
		let target_ti = FixedU128::saturating_from_integer(Self::HARD_CAP_TARGET);

		// Start date of the curve is set two years prior, thus ensuring first step in March,
		// 2026.
		let two_years_before_march =
			FixedU128::saturating_from_integer(Self::HARD_CAP_START - (2 * RC_YEARS));
		let relay_block_fp = FixedU128::saturating_from_integer(relay_block_num);
		let step_duration = FixedU128::saturating_from_integer(2 * RC_YEARS);

		let two_year_rate = Self::BI_ANNUAL_RATE;

		let Ok(ti_curve) = SteppedCurve::try_new(
			// The start date of the curve.
			two_years_before_march,
			// The initial value of the curve.
			march_14_2026_ti,
			// Target TI.
			RemainingPct { target: target_ti, pct: two_year_rate },
			// Step every two years.
			step_duration,
		) else {
			return 0
		};

		// The last step size tells us the expected TI increase over the current two year
		// period.
		let two_year_emission_fp = ti_curve.last_step_size(relay_block_fp);
		let two_year_emission: u128 = two_year_emission_fp.into_inner() / FixedU128::DIV;
		FixedU128::from_rational(1, 2).saturating_mul_int(two_year_emission)
	}
```

```rust
impl sp_staking::budget::IssuanceCurve<Balance> for EraPayout {
	fn issue(_total_issuance: Balance, elapsed_millis: u64) -> Balance {
		let relative_period =
			FixedU128::from_rational(elapsed_millis.into(), Self::MILLISECONDS_PER_YEAR.into());

		let relay_block_num =
			<RelaychainDataProvider<Runtime> as BlockNumberProvider>::current_block_number();
		let yearly_emission = Self::yearly_after_hard_cap(relay_block_num);

		let emission =
			relative_period.saturating_mul_int(yearly_emission).min(Self::MAX_ERA_EMISSION);
		emission.saturated_into()
	}
}
```
