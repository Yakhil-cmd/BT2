## Analysis

The reported class of bug is: computing several percentage-weighted terms that are meant to sum to a whole, but rounding/dividing each term **independently** rather than rounding once after combining them, so the rounding error is not corrected and can drift away from the true total.

This exact class of flaw exists in `headers_commission.js`, where a payer unit's `headers_commission` (`full_amount`) is split among multiple recipients defined by percentage shares (`earned_headers_commission_share`) that are validated only to *sum to 100*, with each recipient amount independently rounded: [1](#0-0) [2](#0-1) 

The share list is validated in `validateHeadersCommissionRecipients`, which only enforces that each `earned_headers_commission_share` is a positive integer and that the shares sum to exactly 100 — it does not constrain how the individual roundings interact with the total: [3](#0-2) 

Because each recipient's payout is `Math.round(full_amount * share / 100.0)` computed **per recipient**, and the individual roundings are never reconciled against `full_amount`, an attacker who controls the recipient list (any unit author is free to set arbitrary `earned_headers_commission_recipients`, an entirely unprivileged, permissionless action) can pick many small integer shares (e.g. 100 recipients with `share = 1` each) such that each of the independent roundings rounds *up*. The distributed total can then exceed the original `full_amount` that was actually reserved from the payer unit, minting extra bytes-equivalent commission that were never backed by any input. This is inserted directly into `headers_commission_outputs`/spendable balances via: [4](#0-3) [5](#0-4) 

Since a single "winning" child unit can be the best child for multiple different parent (payer) units simultaneously (the same `earned_headers_commission_recipients` list is reused for every payer whose commission that child wins), the attacker only pays the one-time cost of a slightly larger unit (to include the recipient list) while collecting the rounding-up gain from every parent unit that names it as best child.

### Title
Supply inflation via rounding-up of `earned_headers_commission_recipients` shares in headers-commission distribution - (File: headers_commission.js)

### Summary
`calcHeadersCommissions` splits a payer unit's fixed `headers_commission` among the recipients an unprivileged unit author lists in `earned_headers_commission_recipients`. Each recipient's share of the commission is rounded independently with `Math.round(full_amount * share / 100.0)` instead of first summing the unrounded shares and rounding once. Because `validateHeadersCommissionRecipients` only requires the integer shares to sum to 100 (not that the rounded amounts sum to `full_amount`), a carefully chosen list of many small shares can cause the sum of the rounded, distributed amounts to exceed the original `full_amount`, creating bytes that were never actually paid in.

### Finding Description
- `validateHeadersCommissionRecipients` (validation.js:1101-1126) only checks `isPositiveInteger(recipient.earned_headers_commission_share)` and that `total_earned_headers_commission_share === 100`. It places no bound on the number of recipients (up to 100, since minimum share is 1) nor on how their individual roundings interact.
- `calcHeadersCommissions` (headers_commission.js:178-187 in-memory path, 193-205 SQL-comparison path) computes, for each recipient of a winning child unit, `amount = Math.round(full_amount * share / 100.0)`. This is done per-recipient, and the comment at line 199 even acknowledges "we round _before_ summing up header commissions" — but only across multiple parent units, not that individual recipient shares of one parent's commission can round the total upward past `full_amount`.
- The resulting `amount`s are inserted as-is into `headers_commission_contributions` and later summed into `headers_commission_outputs` (headers_commission.js:222-227), becoming real spendable balances.
- An attacker fully controls the shares/recipients of their own unit (an entirely permissionless action available to any unit poster), and can choose e.g. 100 recipients (self-controlled addresses) each with `share = 1`. For a `full_amount` whose value modulo 100 is ≥ 50, `Math.round(full_amount/100)` rounds up, and summing that rounded value across all 100 recipients yields a total strictly greater than `full_amount`.
- Because the same crafted unit can be selected as "best child" (winner of headers commission) for multiple different parent units at once, the attacker pays the size/commission cost of the larger recipient list only once while harvesting the rounding surplus from every parent unit whose commission it wins.

### Impact Explanation
This allows an unprivileged actor to mint bytes-equivalent value beyond what was actually collected as commission from parent units — a direct supply-inflation bug, matching the required "supply inflation" impact category. It is deterministic and reproducible by anyone posting ordinary units; no special role, key, or node compromise is required.

### Likelihood Explanation
High: the only requirement is authoring a unit with a crafted `earned_headers_commission_recipients` array (already fully user-controlled and already validated to accept up to 100 integer-share entries) and arranging for that unit to be the "best child" of one or more parent units — both are normal, permissionless behaviors that occur constantly in the DAG.

### Recommendation
Compute all recipient amounts for a given `full_amount` together and correct for rounding drift, e.g., round every recipient's raw fractional share down (`Math.floor`) and assign the remainder (`full_amount - sum(floored amounts)`) to a single recipient (or distribute the leftover units deterministically, e.g., to the largest-share recipient), so that `sum(amount_i) === full_amount` is enforced as an invariant rather than only `sum(share_i) === 100`.

### Proof of Concept
1. Attacker creates address list `A1...A100`, all under their control.
2. Attacker composes a unit whose `earned_headers_commission_recipients` is `[{address: A1, earned_headers_commission_share: 1}, ..., {address: A100, earned_headers_commission_share: 1}]` (sums to 100, passes `validateHeadersCommissionRecipients`).
3. Attacker arranges (via normal unit composition/parent selection) for this unit to become the sole "best child" winning headers commission from a parent unit whose `headers_commission` value `full_amount` satisfies `full_amount % 100 >= 50` (attacker can pick/produce parent units with a convenient headers_commission size, or simply repeat the attack over many naturally occurring parent units until a favorable value occurs).
4. `calcHeadersCommissions` computes, for each of the 100 recipients, `amount = Math.round(full_amount / 100)`, rounding up; summing 100 of these values yields `100 * Math.round(full_amount/100) > full_amount`.
5. The surplus is written into `headers_commission_contributions` → `headers_commission_outputs`, becoming spendable balances for the attacker's addresses that were never backed by an equivalent deduction anywhere else in the system.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
