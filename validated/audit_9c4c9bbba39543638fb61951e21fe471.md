### Title
Cross-organization / cross-repository webhook confusion — authenticated organization (`repository.owner.login`) is never checked against the repository actually acted on (`repository.full_name`) - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
When Shipit is configured for multiple GitHub organizations, each organization has its own `webhook_secret` [1](#0-0) . The controller selects which secret to verify a webhook payload against using the `repository.owner.login` (or `organization.login`) field read from the *same, attacker-suppliable* JSON body [2](#0-1) . Every downstream handler, however, determines which `Stack`/`Repository` records to mutate using an entirely different field, `repository.full_name` [3](#0-2) . Nothing enforces that the organization prefix of `full_name` matches the `owner.login`/`organization.login` used to pick the verifying secret. This breaks the intended binding: *the organization that authenticated the request == the organization whose repository is written*.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to verify against like this:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config/secret keyed by that organization string [4](#0-3) , and `GitHubApp#verify_webhook_signature` is a standard `HMAC-SHA1(secret, raw_body)` compare [5](#0-4) .

Handlers, by contrast, resolve the target repository from a *different* JSON key:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`PushHandler`, `StatusHandler`, and the `PullRequest::*Handler` classes all use `stacks`/`params.repository.full_name` to find the `Stack`/`Repository` to mutate: `sync_github`, create commit statuses, archive/unarchive review stacks, update PR metadata, etc. [7](#0-6) [8](#0-7) 

Because the signature is computed over the *entire raw body*, an attacker cannot tamper with a genuine GitHub-delivered payload without invalidating the signature. But the attack does not require tampering with a real GitHub delivery — it requires only that the attacker be an administrator of *one* organization that is configured in Shipit's multi-org `github:` secrets block (a legitimate, unprivileged-with-respect-to-other-orgs actor, e.g., an org owner who set up their own GitHub App and obtained their own `webhook_secret`, exactly as documented in `docs/setup.md`) [1](#0-0) . Such an attacker can construct an arbitrary JSON payload themselves, sign it with their own known `webhook_secret`, and POST it directly to `/webhooks` (bypassing GitHub entirely) with:
- `repository.owner.login` (or `organization.login`) = their own org (so the correct secret/App is selected and verification succeeds), and
- `repository.full_name` = `"victim-org/victim-repo"` — any other organization/repository tracked by the same Shipit instance.

`verify_signature` succeeds (it is checking only "was this payload signed by *some* configured org's secret", using an org identifier the attacker themselves controls), and the handler then acts on the victim's `full_name`, entirely decoupled from the organization that was actually authenticated.

### Impact Explanation
This is a cross-repository/cross-organization write vulnerability. An administrator of Org A (who never had any access, permission, or webhook installed against Org B's repositories) can, purely through their own legitimate `webhook_secret`:
- Force `GithubSyncJob`/`sync_github` on Org B's stacks via `PushHandler` [9](#0-8) .
- Inject fabricated commit statuses via `StatusHandler#process` (`Commit.where(sha: params.sha)` is not even scoped by repository, compounding the issue) [10](#0-9) , which can flip CI gating used to authorize deploys on Org B's stacks.
- Archive/unarchive Org B's review stacks and mutate Org B's pull-request metadata via the `PullRequest::*Handler` classes [8](#0-7) [11](#0-10) .

This satisfies the "cross-repository writes" Critical impact category, and by poisoning commit statuses that gate deploys, it can contribute to an unauthorized deploy on a repository/organization the attacker never had legitimate access to.

### Likelihood Explanation
Requires Shipit to be configured with the multi-organization `github:` secrets schema (explicitly documented and supported) and requires the attacker to control (as an unprivileged party with respect to *other* tenants) at least one organization's own `webhook_secret` — something they legitimately possess as an org admin of their own tenant. No GitHub session, `ApiClient` token, or Shipit account is needed; only an HTTP POST to the public `/webhooks` endpoint with a self-computed HMAC signature. This is realistic in any Shipit-as-a-service / multi-tenant deployment.

### Recommendation
In `WebhooksController#verify_signature` and/or `Shipit::Webhooks::Handlers::Handler`, derive the organization used to select the verifying secret and the organization used to resolve the target repository from the *same* trusted source, and assert they match — e.g., verify that `repository.full_name.split('/').first.casecmp(repository_owner) == 0` before dispatching to handlers, rejecting the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `orga` (attacker-controlled) and `orgb` (victim), each with distinct `webhook_secret`s, per the documented multi-org schema [1](#0-0) .
2. Attacker (legitimate admin of `orga`, knows `orga`'s `webhook_secret`) builds a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha>",
  "repository": { "full_name": "orgb/victim-repo", "owner": { "login": "orga" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orga_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` resolves to `"orga"`, `Shipit.github(organization: "orga")` picks `orga`'s secret, `verify_signature` succeeds [12](#0-11) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgb/victim-repo")` and calls `stack.sync_github` on `orgb`'s stack [9](#0-8) , even though the attacker was authenticated only as `orga`.

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers

        params do

          stacks

          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
