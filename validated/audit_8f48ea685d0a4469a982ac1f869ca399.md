### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the acted-upon repository comes from an unchecked `repository.full_name` field, allowing cross-tenant stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC against using `repository_owner`, a value read straight out of the attacker-controlled JSON body (`repository.owner.login`, or `organization.login`). Once the signature checks out, the full untrusted payload is dispatched to handlers, and `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` selects the target `Repository`/`Stack` using a *different* field from the very same body: `repository.full_name`. Nothing ties these two fields together, so an authenticated organization (in Shipit's documented multi-GitHub-App mode) can sign a payload with its own known `webhook_secret` while pointing `repository.full_name` at a stack belonging to a different, unrelated organization hosted on the same Shipit instance.

Each organization creates and owns its own GitHub App (and therefore its own webhook secret) per the setup instructions (`https://github.com/organizations/<your-org>/settings/apps/new`), so a tenant organization legitimately knows only its own secret, not other tenants'.

Once `verify_signature` passes, `create` forwards the entire (still merely HMAC-authentic-for-*a*-secret) payload to handlers: [4](#0-3)

using `repository.full_name`, a JSON key entirely independent of the `repository.owner.login` used for signature-key selection. `PushHandler` then directly acts on those stacks: [6](#0-5) 

Because both `repository.owner.login` and `repository.full_name` are simply keys inside the same attacker-composed JSON body, and the code only verifies the whole body's HMAC against the secret picked via `repository.owner.login`, an organization that legitimately owns its own webhook secret can freely set `repository.full_name` to reference a repository/stack belonging to a completely different organization also hosted on the same Shipit deployment. The equality that should hold — "organization whose secret authenticated the request" == "organization owning the repository being written to" — is never enforced.

### Impact Explanation
An organization tenant on a shared, multi-organization Shipit instance can forge webhook events (e.g. `push`, `status`) that are valid HMAC-wise (signed with its own known secret) but target another tenant's `Stack`/`Repository`. This lets it:
- Trigger `stack.sync_github(expected_head_sha:)` for a foreign stack via `PushHandler`, forcing GitHub sync activity against another org's repository state.
- Because every handler shares the same `Handler#stacks`/`repository_name` resolution, the same confusion extends to any handler acting on `repository.full_name` (e.g. commit status creation), which can inject forged commit statuses onto another tenant's commits — commit statuses are used by Shipit to gate deployability, so this can enable an unauthorized deploy of a stack the attacker does not own.

This crosses a repository/tenant boundary using only a credential the attacker legitimately possesses for their own tenant, meeting the High severity bar ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
Requires: (1) a Shipit deployment configured in the documented multi-organization mode with more than one tenant organization sharing the instance, and (2) the attacker being an administrator of one of those tenant GitHub Apps (i.e., possessing their own org's `webhook_secret`, which is a normal, expected credential for a legitimate tenant, not an elevated Shipit-side privilege). Given multi-tenant Shipit setups are explicitly documented and supported, this is a realistic configuration, though single-org deployments (the common case) are unaffected since there is only one secret and thus no organization to "confuse."

### Recommendation
When resolving the target `Repository`/`Stack` in `Shipit::Webhooks::Handlers::Handler#repository_name`, verify that the owner segment of `repository.full_name` matches the `repository_owner`/organization whose secret was actually used to authenticate the request in `WebhooksController#verify_signature`, rejecting (422) any payload where they diverge. Alternatively, thread the authenticated organization through to handler construction and have `Repository.from_github_repo_name` scope its lookup to that organization rather than trusting the raw `repository.full_name` field unconditionally.

### Proof of Concept
1. Configure Shipit in multi-org mode with `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md`), both hosting stacks on the same Shipit instance.
2. As an administrator of `orgA`'s GitHub App, craft a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/production-app" }
}
```
3. Sign the raw body with `orgA`'s known `webhook_secret` using the same `sha1=HMAC` scheme as `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature`, and send it to `/webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s app, and the signature validates successfully (it was signed with `orgA`'s real secret).
5. `PushHandler` resolves `stacks` via `repository.full_name` = `"orgB/production-app"`, and calls `stack.sync_github(expected_head_sha: "deadbeef")` on `orgB`'s stack — despite the request never being authenticated by `orgB`. [7](#0-6) [5](#0-4)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    def event

    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
