### Title
Unbounded `main_chain_index` range in headers-commission/witnessing input validation causes full-range table scans on every posted unit - (File: validation.js, mc_outputs.js, paid_witnessing.js)

### Summary
Any unprivileged unit poster can include a `headers_commission` or `witnessing` input whose `from_main_chain_index`/`to_main_chain_index` span the *entire* history of the chain (0 up to `last_ball_mci`). Validation of that unit unconditionally executes a `SUM(amount)`/`COUNT(1)` aggregate query over `headers_commission_outputs`/`witnessing_outputs`/`units` for that whole range **before** it ever checks whether the resulting commission amount is correct, so the expensive scan runs even for units that are ultimately rejected as invalid.

### Finding Description
In `validation.js` the only range checks performed on a `headers_commission`/`witnessing` input are: [1](#0-0) 

Neither of these checks bounds the *size* of the range (`to_main_chain_index - from_main_chain_index`) — only that `from <= to` and both are `<= last_ball_mci`. Any address that has never spent a `headers_commission`/`witnessing` output (`next_spendable_mc_index == 0`, from `mc_outputs.readNextSpendableMcIndex`) can therefore set `from_main_chain_index=0` and `to_main_chain_index=last_ball_mci`, covering the whole main chain.

This range is fed straight into `paid_witnessing.calcWitnessEarnings` / `mc_outputs.calcEarnings`: [2](#0-1) [3](#0-2) 

Both queries — the `SELECT COUNT(1) ... FROM units WHERE is_on_main_chain=1 AND is_stable=1 AND main_chain_index>=? AND main_chain_index<=?` and the `SELECT SUM(amount) FROM headers_commission_outputs/witnessing_outputs WHERE main_chain_index>=? AND main_chain_index<=? AND address=?` — must scan (or aggregate over) every row in the requested MCI range. As the ledger grows, this range can cover millions of rows.

Crucially, the correctness of the input (i.e., whether `commission === 0` or matches the claimed amount) is only checked **after** these expensive queries return: [4](#0-3) 

This means an attacker does not need a valid unit at all — they only need a syntactically well-formed `headers_commission`/`witnessing` input with a huge MCI range on an address that has not consumed any commissions yet. Each such (ultimately rejected) unit still forces the node to execute one or two full-range aggregation queries. Because units are cheap to author (bytes fee is tiny and validation happens before the unit is even written/committed), an attacker can flood the network with many such units in parallel/sequence, each triggering a full-range scan, exhausting DB/CPU resources on every node that validates them — directly analogous to CVE-2021-32053, where an unauthenticated `_history` request forced a `SELECT COUNT` requiring a full index scan, and many concurrent requests caused resource exhaustion.

### Impact Explanation
Repeatedly submitting such crafted units forces every full node (and every node that must independently validate incoming units) to perform large aggregate scans over `units`, `headers_commission_outputs`, and `witnessing_outputs`. With enough concurrent/successive malicious units, this can saturate database I/O/CPU on validating nodes, slowing or stalling validation of legitimate units network-wide — a denial-of-service on the network's ability to confirm new units, matching the "Uncontrolled Resource Consumption" (CWE-400) class of the reference advisory. This is reachable purely from unprivileged unit posting (no special role required), and does not require the unit to become valid or stable.

### Likelihood Explanation
Likelihood is moderate-to-high on a long-lived chain: the attack requires only posting well-formed but ultimately-rejected units with a wide MCI range from an address with no prior commission spends (trivial to arrange with a fresh address). No privileged role, protocol trust, or valid signatures beyond normal authoring are needed. Any full node performing standard validation is exposed. The cost to the attacker is limited to unit composition/authoring overhead (which is smaller than the server-side scan cost, especially on large, mature ledgers), matching the CVSS `AC:L/PR:N/UI:N` profile of the reference advisory.

### Recommendation
Bound the allowed MCI range for `headers_commission`/`witnessing` inputs during syntactic validation, before running any aggregate queries — e.g., reject inputs whose `to_main_chain_index - from_main_chain_index` exceeds the maximum plausible payout window (`constants.COUNT_MC_BALLS_FOR_PAID_WITNESSING`/`COUNT_MC_BALLS_FOR_HEADERS_COMMISSION`, mirroring the check already used to bound `readMaxSpendableMcIndex`/`max_mci` in `paid_witnessing.js`). Additionally, ensure the `commission === 0` / correctness checks happen before or reject clearly-oversized ranges early, so no full aggregate scan is executed for MCI windows larger than plausible commission-accrual periods. Consider also adding/verifying supporting indexes (`(address, main_chain_index)`) on `headers_commission_outputs`/`witnessing_outputs` to keep worst-case cost bounded even within the allowed window.

### Proof of Concept
1. Generate a fresh address `A` that has never posted a `headers_commission`/`witnessing` input (so `readNextSpendableMcIndex` returns `0`).
2. Compose and broadcast a unit authored by `A` containing a `payment` message with an input:
   ```json
   { "type": "witnessing", "from_main_chain_index": 0, "to_main_chain_index": <last_ball_mci> }
   ```
   (or `headers_commission`), with any output amount (the unit will ultimately be rejected because the claimed commission won't match, but this happens only after the expensive query executes).
3. Broadcast many such units concurrently, each from a fresh unused address, to many/most peers.
4. Observe DB CPU/IO on validating nodes spike proportionally to `to_main_chain_index - from_main_chain_index`, i.e., to the size of the chain history, repeated per malicious unit — analogous to the HAPI FHIR history-request resource exhaustion described in the referenced advisory.

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
