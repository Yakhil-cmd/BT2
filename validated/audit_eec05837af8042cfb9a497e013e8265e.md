### Title
Borrow/withdraw recipient denylist is incomplete — funds sent to the position-NFT or governance contracts are permanently frozen - ([File: contracts/controller/src/positions/mod.rs](contracts/controller/src/positions/mod.rs))

### Summary
The ingress-nginx class — a sanitization/validation rule that is bypassable because it only covers part of the dangerous input space — maps onto `require_external_recipient`. The controller validates the `to` recipient of `borrow` and `withdraw` against a denylist that contains only the pool and the controller itself. Other protocol contracts that can receive tokens but can never release them (position-NFT, governance, price-aggregator, accumulator) are not blocked, so a borrower can permanently trap pool liquidity in an unrecoverable address.

### Finding Description
`require_external_recipient` rejects only `env.current_contract_address()` and the pool:

```rust
// contracts/controller/src/positions/mod.rs:36-43
pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
}
```

This check is invoked from `process_borrow` (`contracts/controller/src/positions/debt.rs:47`) and the withdraw path before the pool executes the outbound `token.transfer` to `recipient`. The denylist exists because protocol-owned destinations strand funds: a pool self-transfer debits `cash` without moving tokens, and controller receipts are never claimed by balance-delta accounting (GH-17 test, `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs`). But the same stranding applies to every other protocol contract:

- The position-NFT contract exposes only NFT `transfer`/`transfer_from`/`approve` and mint/burn gated to the controller — it has no function to move an arbitrary SAC/custom token out (`contracts/position-nft`, per its documented surface in `docs/reference/endpoints.md:236-257`).
- Governance exposes only `execute` of hash-matched scheduled ops and role-gated admin calls — no token sweep (`contracts/governance/src/timelock/lifecycle.rs:85-110`).
- The price-aggregator and accumulator have no token-rescue entrypoint either.

The downstream transfer in the pool does not re-check the destination — the pool "does not re-validate what is already guaranteed upstream" (`contracts/pool/README.md`). So a validated-but-dangerous recipient slips through exactly like the newline bypassing the `path` sanitizer: the check enumerates two forbidden values instead of enforcing an allowlist or a "not a protocol contract" invariant.

### Impact Explanation
An attacker opens an account, supplies minimum collateral, and calls `borrow` with `to` set to the position-NFT (or governance) contract address. The pool transfers real tokens to an address that can never move them — the tokens are permanently frozen. The attacker's debt stays on the books; once the position goes bad, `clean_bad_debt` socializes the loss into the supply index, so suppliers bear a permanent, unrecoverable loss of pool liquidity. This is permanent freezing of user funds and contributes directly to protocol insolvency: the borrowed tokens are gone forever while the corresponding debt is written down against suppliers. Done across markets, an attacker can permanently destroy an arbitrary amount of TVL at the cost of their own collateral, which may be far smaller (e.g., borrow-to-value near LTV on low-liquidity collaterals, or maximally leveraged via `multiply`/`flash_position` loops before the final borrow).

### Likelihood Explanation
Reachable by any unprivileged address through `borrow(caller, account_id, borrows, to)` and `withdraw(...)` — both are standard user entrypoints requiring only owner/delegate authorization on their own account. No timing, oracle, or governance preconditions are needed. The only cost is the collateral posted and the debt the attacker abandons; the freeze itself is guaranteed once the transfer executes. The cost/benefit depends on how much can be borrowed per unit of collateral, so damage is bounded by achievable leverage rather than being free — consistent with Medium.

### Recommendation
Replace the two-entry denylist with a comprehensive protocol-address check: reject `to`/`receiver`/`refund` recipients equal to the pool, the controller, the position-NFT contract, the governance contract, the price-aggregator, and the accumulator (all resolvable from `Context`/storage), or invert the policy to require the recipient to be an account address or an explicitly allowlisted external contract. Apply the same check wherever a user-supplied destination receives pool tokens (`withdraw`, `borrow`, `flash_position` receiver handling, refund legs).

Existing precedent proving the stranding mechanism: `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs` shows pool/controller recipients are rejected precisely because "the pool debits cash without its balance moving" and "the controller holds funds no balance-delta measurement can ever claim" — the identical failure mode applies to position-NFT/governance recipients, which the check does not cover.
