### Title
Confirmation-dialog classification can be spoofed by a shared-address counterparty to suppress the "confirm on other devices" security attention prompt when signing a remote multisig payment - ([File: wallet.js])

### Summary
When the wallet needs a remotely-hosted key to co-sign a unit (multisig / shared address), `getSigner().sign()` decides which confirmation dialog to show to the local user before the remote co-signer actually returns a signature. The decision is made purely by matching the payment output `amount` against fixed constants `prosaic_contract.CHARGE_AMOUNT` / `arbiter_contract.CHARGE_AMOUNT` and by looking up rows in `prosaic_contracts` / `wallet_arbiter_contracts` keyed by `shared_address`/`peer_address`. Because both the "contract" classification and the fallback "confirm_on_other_devices" generic warning are mutually exclusive (`bRequestedConfirmation` short-circuits any subsequent alert), a co-signer/contract counterparty who controls the amounts and shared-address setup can make an arbitrary spend look like an innocuous "contract deposit/claim/sign" event, or suppress the generic alert entirely, weakening the "attention mechanism" that is supposed to make the user pay attention before authorizing a multisig spend from a shared/co-owned address. This mirrors the CVE-2024-37408 class of bug: an authorization decision is made available without a reliable mechanism ensuring the user's attention is properly drawn to what is actually being approved.

### Finding Description
`getSigner` (`wallet.js:1976`) returns a `sign` implementation used by `signed_message.signMessage`/composer flows whenever a signing path resolves to a remote device (`ifRemote`) — i.e. any multisig or shared address that includes a cosigner living on another paired device. [1](#0-0) 

Inside `ifRemote`, before actually alerting the local operator, the code runs two heuristic checks in series to decide whether the UI should show a *reduced-alarm* "contract" dialog instead of the generic warning:

1. **Step 1 — prosaic/arbiter contract deposit**: it looks for a payment output whose amount equals `prosaic_contract.CHARGE_AMOUNT` or `arbiter_contract.CHARGE_AMOUNT`, then queries `prosaic_contracts`/`wallet_arbiter_contracts` by `shared_address` to see whether the peer is already a known contract counterparty. If found, it emits `confirm_contract_deposit` and sets `bRequestedConfirmation = true`. [2](#0-1) 

2. **Step 2 — contract claim/sign**: it checks `prosaic_contracts`/`wallet_arbiter_contracts` by `shared_address OR peer_address`; if the remote device is the known `peer_device_address`, no alert at all is shown (`cb(true)` short-circuits); otherwise it classifies the transaction as either a "claim" (`confirm_contract_claim`) or a generic "sign" (`confirm_contract_sign`) event, again using `CHARGE_AMOUNT`/asset/address matching heuristics rather than a strong cryptographic binding to an actual agreed contract terms. [3](#0-2) 

3. Only if **neither** heuristic fires does the generic `confirm_on_other_devices` warning get shown: [4](#0-3) 

Because `bRequestedConfirmation` is a single boolean gate shared across steps, and because the classification is driven by attacker-observable/attacker-influenced data (exact output amount matching a public constant, and the `shared_address`/`peer_address` rows that a paired contract counterparty itself caused to be created during contract setup, see `prosaic_contract.js`/`arbiter_contract.js`), a malicious cosigner who is already paired with the victim through a prosaic/arbiter contract shared address can:
- Ensure that any output amount they need signed equals `CHARGE_AMOUNT`, causing the wallet to treat a spend as a routine "contract deposit/claim" rather than surfacing the neutral, high-attention `confirm_on_other_devices` alert.
- Rely on the `rows[0].peer_device_address === device_address` branch to suppress alerting altogether when the attacker's own device is recorded as `peer_device_address` for that shared address (step 2, line 2068-2069).

The wallet still requires the correct signature from the local key holder to actually spend, so this alone is not spendable without the user's local device applying its own signature — but the “security attention” safeguard that the front-end relies on to make the human notice what they are approving can be bypassed/downgraded by the counterparty they've already contracted with, exactly analogous to `pam_fprintd.so` "sufficient" authorizing sudo without a real attention check: the underlying primitive (asking for a click/approval) exists, but the mechanism intended to make sure the user actually looks at what they approve can be routed around by the remote party.

### Impact Explanation
If the local user relies on the differentiated dialogs (`confirm_contract_deposit`/`confirm_contract_claim`/`confirm_contract_sign` vs. the generic `confirm_on_other_devices`) to gauge risk, a malicious prosaic/arbiter-contract counterparty can craft a multisig spend request whose output amount matches `CHARGE_AMOUNT` and route it through a shared address they are recorded as a peer of, making the wallet suppress the stronger, neutral "confirm signing initiated by another device" warning or replace it with a comparatively benign "claim/deposit" prompt. A user who is trained to trust the differentiated (weaker) messaging may approve a transaction they would otherwise have scrutinized, resulting in unauthorized spending from the shared/co-owned funds. This is a High severity concern because it can lead to concrete unauthorized spending from a multisig/shared address, matching the "unauthorized spending" acceptance criterion.

### Likelihood Explanation
Exploitation requires: (1) the victim to have set up a prosaic or arbiter contract (creating a `shared_address` and a `prosaic_contracts`/`wallet_arbiter_contracts` row) with the attacker's device — a normal, unprivileged, reachable action any paired device can initiate; and (2) the attacker to subsequently request signing of an output whose amount coincides with the well-known `CHARGE_AMOUNT` constant (public in source, trivial to replicate) via the standard `sign`/`walletGeneral.sendOfferToSign` device-message flow (`wallet.js:251` `case "sign"`). No privileged access, hub cooperation, or network-level manipulation is needed beyond the attacker's own paired-device messages, which are otherwise part of normal contract usage.

### Recommendation
- Do not use a fixed, publicly-known constant amount (`CHARGE_AMOUNT`) as the sole discriminator for classifying a signing request as a benign "contract deposit/claim"; instead bind the classification to a cryptographically verifiable reference to the specific pre-agreed contract (e.g. hash of the contract text/terms) stored at pairing time, and verify the full set of outputs/inputs match the previously agreed contract structure exactly, not just one output’s amount.
- Ensure that any output-amount/asset heuristic used to relax UI warnings can never fully suppress a baseline "a remote device is asking you to sign a transaction" notice — always surface at least a lightweight, mandatory indicator of the party and full amount/recipients being signed, regardless of which classification path is taken.
- Avoid setting a single shared `bRequestedConfirmation` gate across unrelated messages in the same unit; each output/message that moves funds outside of the exact previously agreed contract terms should independently require attention.

### Proof of Concept
1. Attacker device pairs with victim and establishes a prosaic (or arbiter) contract, causing a `shared_address` and a row in `prosaic_contracts` (or `wallet_arbiter_contracts`) with `peer_device_address` = attacker's device address (`prosaic_contract.js`, `arbiter_contract.js`).
2. Attacker (or a party colluding with attacker who also has a signing path on the shared address) triggers the victim's wallet to compose a multisig payment where one of the outputs targeting the shared address (or from it) has `amount === prosaic_contract.CHARGE_AMOUNT` (or `arbiter_contract.CHARGE_AMOUNT`), and additional outputs that actually siphon funds elsewhere.
3. When `wallet.js`'s `getSigner().sign()` (`ifRemote`) runs locally to request the remote co-signer's signature, step 1/2 of the `async.series` (`wallet.js:2044-2088`) matches the crafted output against `CHARGE_AMOUNT` and the known `prosaic_contracts`/`wallet_arbiter_contracts` row, so it emits `confirm_contract_deposit`/`confirm_contract_claim` (or nothing, if `rows[0].peer_device_address === device_address`) instead of the neutral `confirm_on_other_devices` alert.
4. The victim's UI shows the softer/absent prompt, increasing the chance they approve the spend without realizing additional, unrelated outputs are being signed away.
