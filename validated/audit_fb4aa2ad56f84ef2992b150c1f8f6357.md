### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login`, letting an org with no `webhook_secret` be used to forge events for other orgs' repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org config (and therefore which `webhook_secret`) to validate the HMAC signature against using a value taken straight out of the *unverified* JSON body, before the signature has been checked. In a multi-organization Shipit deployment, if any configured organization has no `webhook_secret` set (which the app explicitly supports, e.g. `webhook_secret: # nil` in `config/secrets.development.shopify.yml`), verification for that organization is a no-op, and the org selector is fully attacker-controlled.

### Finding Description
The equality that should hold is: `organization that authenticates the request == organization whose repository the payload actually mutates`. This binding is broken because:

1. `repository_owner` is read directly from the raw, unauthenticated JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), before any signature check occurs: [1](#0-0) 

2. That attacker-controlled value is used to pick which `GitHubApp` (and hence which `webhook_secret`) will be used to verify the signature: [2](#0-1) 

3. `verify_webhook_signature` is a pass-through (`return true unless webhook_secret`) when the selected organization has no secret configured: [3](#0-2) 

4. Once `create` runs, the actual target repository/stack acted upon by handlers is derived from a *separate* field of the same untrusted payload — `repository.full_name` — completely decoupled from the `repository.owner.login` used for signature selection: [4](#0-3) [5](#0-4) 

Because Shipit supports configuring multiple GitHub organizations, each with its own optional `webhook_secret`, an attacker only needs to know (or guess) that one configured org in `secrets.yml` has no `webhook_secret` set. They then send a webhook request with `repository.owner.login` set to that unprotected org (satisfying step 1–3 with no HMAC needed at all) while setting `repository.full_name` in the same JSON body to point at a stack that actually belongs to a *different*, protected organization. `verify_signature` will pick the unprotected org's `GitHubApp`, silently pass verification, and the handler will then process events (e.g. `push`, `status`, `check_suite`, `pull_request`) against the protected repository's stacks, because the code that resolves the affected repository never re-checks that it belongs to the organization that was actually authenticated.

### Impact Explanation
This is a case where the request is treated as authenticated (a "GitHub webhook") for one organization, but the payload used to act on a repository belongs to a different organization whose real webhook_secret is never checked. This lets an unauthenticated attacker inject forged `push`/`status`/`check_suite`/`pull_request` events for stacks under a fully protected organization by exploiting the presence of a single unprotected org entry in `secrets.yml`. Depending on which handler fires, this can trigger `GithubSyncJob` (forcing head SHA changes / triggering deploy eligibility recalculation), fabricate commit `status` records that influence CI gating for deploys, or manipulate review-stack lifecycle (archive/unarchive) — i.e., it can influence the "ref approved" state that governs whether a deploy is allowed to proceed, without possessing the real webhook secret for the targeted org.

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: it requires a multi-organization `secrets.yml` where at least one configured org has a blank/nil `webhook_secret` while another has repositories the attacker wants to target. The engine's own documentation and example secrets file show this as a supported and even documented configuration pattern (`webhook_secret: # nil`), so it is not a purely theoretical operator misconfiguration — it's an explicitly supported state that this code fails to isolate per-organization.

### Recommendation
- Bind signature verification to the actual repository being mutated, not merely the organization named at the top of the payload: after parsing, verify that `repository.full_name`'s organization matches `repository_owner`, and/or resolve the `GitHubApp` from the repository/stack that is ultimately looked up rather than from a raw payload field.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with no secret if other organizations in the same deployment do have secrets configured; either require all orgs to define a secret, or refuse to process events whose `repository.full_name` doesn't belong to the organization that was used for verification.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs, e.g. `org-a` (no `webhook_secret`) and `org-b` (`webhook_secret` set), each owning at least one Stack.
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/protected-repo"
  }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `repository_owner` resolves to `org-a`; `Shipit.github(organization: 'org-a')` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
4. `Shipit::Webhooks::Handlers::PushHandler` then resolves the affected stacks via `Repository.from_github_repo_name('org-b/protected-repo')` and calls `stack.sync_github(expected_head_sha: params.after)` against the `org-b` protected stack — despite `org-b`'s real webhook secret never being validated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
