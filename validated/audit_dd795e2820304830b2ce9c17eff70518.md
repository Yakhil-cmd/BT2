### Title
Fee-on-Transfer ERC20 Tokens Cause Bridge Liquidity Drain via Inflated `RequestValueTransfer` Amount — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` emit `RequestValueTransfer` with the caller-supplied `_value` rather than the amount actually received by the bridge. When a registered ERC20 token silently deducts a transfer fee, the source bridge locks fewer tokens than `_value`, but the counterpart bridge unconditionally releases `_value` tokens to the recipient. In lock/unlock mode this permanently drains the destination bridge's liquidity pool.

---

### Finding Description

**Two entry points share the same flaw:**

**2-step path** — `requestERC20Transfer`:

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

If the token deducts a fee on transfer, the bridge receives `(_value + _feeLimit) × (1 − fee_rate)` instead of `_value + _feeLimit`. The original `_value` is passed unchanged into `_requestERC20Transfer`.

**1-step path** — `onERC20Received` (called by `ERC20ServiceChain.requestValueTransfer`):

```solidity
// ERC20ServiceChain.sol L45-46
require(transfer(bridge, _amount.add(_feeLimit)), "...");
IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
```

The token transfers `_amount + _feeLimit` to the bridge (bridge receives less due to fee), then calls `onERC20Received` with the original `_amount`.

**Inside `_requestERC20Transfer`**, no balance check is performed; the inflated `_value` is emitted directly:

```solidity
// BridgeTransferERC20.sol L97-106
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← user-supplied, not actual received amount
    requestNonce, fee, _extraData
);
```

The off-chain bridge relayer (`node/sc/bridge_manager.go` L338-343) reads `valueOrTokenId` from this event and calls `handleERC20Transfer` on the counterpart bridge with the same inflated value. The counterpart bridge then executes:

```solidity
// BridgeTransferERC20.sol L71
IERC20(_tokenAddress).safeTransfer(_to, _value);   // lock/unlock mode
```

releasing `_value` tokens — more than were ever locked on the source side.

---

### Impact Explanation

**Lock/unlock mode (modeMintBurn = false):**

- Source bridge locks `_value × (1 − fee_rate)` tokens (less than `_value`).
- Destination bridge releases exactly `_value` tokens.
- Per transfer, the destination bridge loses `_value × fee_rate` tokens from its liquidity pool.
- Repeated transfers drain the pool until `handleERC20Transfer` reverts due to insufficient balance, halting all withdrawals for that token.

**Mint/burn mode (modeMintBurn = true):**

- `burn(_value)` is called after `_payERC20FeeAndRefundChange` has already spent part of the bridge's balance on fee/refund transfers.
- If `_value > actual_balance_remaining`, the burn reverts and the entire transaction fails — no silent accounting error, but the bridge becomes unusable for that token until the imbalance is resolved.

The lock/unlock path is the critical one: it silently corrupts the bridge's asset accounting, leading to insolvency of the destination bridge's token reserve.

---

### Likelihood Explanation

**Precondition:** A fee-on-transfer ERC20 must be registered with the bridge. `registerToken` is `onlyOwner`:

```solidity
// BridgeTokens.sol L57-59
function registerToken(address _token, address _cToken)
    external
    onlyOwner
```

This is not a fully unprivileged trigger. However, the realistic scenario is a token that is registered without fees and later has fees activated (e.g., via an upgradeable proxy or an owner-controlled fee switch). Once the token is registered and fees are enabled, **any user** calling `requestERC20Transfer` or `requestValueTransfer` triggers the accounting error — no further privilege is needed. This matches the "valid semi-trusted trigger" criterion.

---

### Recommendation

Measure the actual received amount by comparing the bridge's token balance before and after the `safeTransferFrom` call, and use that delta as the canonical transfer value:

```solidity
function requestERC20Transfer(...) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - balanceBefore;
    // derive actual _value and _feeLimit from actualReceived, then call _requestERC20Transfer
}
```

Apply the same pattern in `onERC20Received` by comparing balance before and after the token's internal transfer.

---

### Proof of Concept

**Setup:** Deploy a fee-on-transfer ERC20 (1% fee on every transfer). Register it with the source bridge (lock/unlock mode). Pre-fund the destination bridge with 1000 tokens.

**Attack loop (any user):**

1. User approves source bridge for 101 tokens (`_value=100`, `_feeLimit=1`, bridge fee=0).
2. User calls `requestERC20Transfer(token, to, 100, 1, "")`.
3. `safeTransferFrom` moves 101 tokens; bridge receives `101 × 0.99 = 99.99` tokens.
4. `_payERC20FeeAndRefundChange` refunds `_feeLimit=1` → bridge holds `99.99 − 1 = 98.99` tokens.
5. `RequestValueTransfer` emits `valueOrTokenId = 100`.
6. Relayer calls `handleERC20Transfer(..., 100, ...)` on destination bridge.
7. Destination bridge executes `safeTransfer(to, 100)` → releases 100 tokens.
8. **Net loss per transfer: 100 − 98.99 = 1.01 tokens from destination bridge pool.**

After ~990 such transfers the destination bridge's 1000-token pool is exhausted. All subsequent `handleERC20Transfer` calls revert, permanently blocking withdrawals for all users who legitimately locked tokens on the source chain. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
