### Title
Cross-repository Status write via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, across the entire `commits` table, and calls `create_status_from_github!` on every match regardless of which repository owns the row. Because `sha` is not unique across repositories/stacks, an attacker who owns a repository with a webhook configured (and thus can produce a validly-signed status webhook) can cause a `Status` to be written onto a commit belonging to a completely different, victim-owned stack whenever the two share a commit SHA.

### Finding Description
Broken binding: `payload.dig('repository','full_name')` (verified as `attacker/repoA`) != the repository owning `commit.stack` for every `Commit` row mutated by `Commit.where(sha: params.sha)`. The `Handler` base class exposes a `stacks` helper ( [1](#0-0) ) that scopes lookups to `Repository.from_github_repo_name(repository_name)`, and this is what `PushHandler` correctly uses ( [2](#0-1) ). `StatusHandler#process`, however, does not use `stacks` or `repository_name` at all — it queries `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` ( [3](#0-2) ), which is a global, unscoped lookup by `sha` across all stacks/repositories in the Shipit instance.

Signature verification in `WebhooksController#verify_signature` only proves the payload came from a GitHub App/webhook belonging to the `repository_owner` named in the payload ( [4](#0-3) ); it says nothing about which `Commit` rows the payload is authorized to mutate. Since `Commit#sha` is not enforced unique per SHA globally (only implicitly unique per stack via GitHub's git object model, but two different stacks/repos can each have a `Commit` row with an identical `sha`, e.g. via cherry-pick, rebase, or an empty-tree/no-op commit), an attacker controlling their own repository/webhook can craft a `status` event naming their own `repository.full_name` with `sha` equal to a SHA that also exists as a `Commit` row in a victim's stack. `create_status_from_github!` calls `add_status`, which persists a new `Status` record via `statuses.replicate_from_github!(stack_id, github_status)` ( [5](#0-4) ) and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` on the victim stack ( [6](#0-5) ), potentially unblocking a deploy or merge on `victim/repoB` — a stack the attacker never authenticated for.

None of the existing guards prevent this: `verify_signature` validates only the signing key/org of the named repository, not commit ownership; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not scoping; there is no `require_permission!`/`stacks` filter in this handler, unlike sibling handlers.

### Impact Explanation
A payload authenticated for `attacker/repoA` mutates `Commit`/`Status` state belonging to `victim/repoB`'s stack — exactly the "payload for one repository mutating another's stack/commit" category, rated Critical. Depending on the victim stack's CI/merge/deployment configuration (`ignore_ci?`, required statuses, continuous deployment, merge queue), this status write can make a blocked commit "deployable" or trigger `schedule_merges`/`ContinuousDeliveryJob`, leading to an unauthorized deploy or merge. The attack is repeatable against any stack that happens to share a commit SHA with an attacker-controlled repository, and is not limited to a single victim — any tenant on the Shipit instance sharing a SHA is affected.

### Likelihood Explanation
Preconditions: the attacker must own/control a GitHub repository already configured with a Shipit stack and valid webhook secret (a normal, low-privilege onboarding step, not a Shipit secret), and must find/construct a SHA that coincides with a `Commit` row in the victim's stack (achievable via cherry-picks, rebases with identical trees, or crafting empty-tree commits, which have deterministic well-known SHAs, e.g. `4b825dc642cb6eb9a060e54bf8d69288fbee491`, likely already present across many stacks). No Shipit session, API token, or team membership is needed. Cost is low and the exploit is fully repeatable by simply re-sending status webhooks.

### Recommendation
Scope the commit lookup by the requesting repository, mirroring `PushHandler`: resolve `stacks` from `repository_name` and restrict the query to commits belonging to those stacks, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each { |c| c.create_status_from_github!(params) }`, or explicitly join through `Stack`/`Repository` before updating statuses.

### Proof of Concept
minitest plan:
1. Create `Repository`/`Stack` `victim_stack` for `victim/repoB` and `Repository`/`Stack` `attacker_stack` for `attacker/repoA`.
2. Create a `Commit` with `sha: 'deadbeef...'` on `victim_stack` and a separate `Commit` with the same `sha` on `attacker_stack`.
3. Build a status payload: `{'sha' => 'deadbeef...', 'state' => 'success', 'repository' => {'full_name' => 'attacker/repoA'}}`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert that the victim commit's `statuses` collection gained a new `Status` (`victim_commit.reload.statuses.count` increased / `victim_commit.status.state == 'success'`), proving a payload naming only `attacker/repoA` mutated `victim/repoB`'s commit — confirming the binding `repository_name from payload == repository owning mutated Commit` does NOT hold.
