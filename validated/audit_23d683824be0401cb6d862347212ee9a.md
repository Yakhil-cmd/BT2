### Title
Headers-commission share can be permanently frozen when assigned to an AA address - (File: `validation.js`)

### Summary
Any unprivileged unit poster can name an arbitrary valid address — including the address of an Autonomous Agent — as a recipient of `earned_headers_commission_recipients` on a multi-authored unit. If that unit later wins the headers-commission race, the commission is credited to the named address in `headers_commission_outputs`/`headers_commission_contributions`. However, the only way to redeem such a credit is by posting a unit with an input of `type: "headers_commission"`, and this input type is unconditionally forbidden inside AA-authored units. Since AAs can only author units through their own deterministic bytecode (which never emits `headers_commission`/`witnessing` inputs), any commission credited to an AA address becomes permanently unspendable — the exact "credited but unwithdrawable" pattern described in the external Dahlia report, where fee shares were assigned to a recipient that had no code path to actually withdraw them.

### Finding Description
`validateHeadersCommissionRecipients` only checks that each recipient's address is syntactically valid, that shares are sorted/positive, and that shares sum to 100 — it never verifies that the recipient is not an AA: [1](#0-0) 

Once a unit with such a recipient list wins the "best child" competition for a parent unit, `calcHeadersCommissions` credits the named address (which may be an AA) directly, based on `earned_headers_commission_recipients`, without any AA-exclusion check: [2](#0-1) 

The credited amount is recorded per-address in `headers_commission_contributions`/`headers_commission_outputs`: [3](#0-2) 

The only way to actually spend such a credit is to include a payment input of `type: "headers_commission"` (or `witnessing`) referencing that address. Validation explicitly forbids this input type from ever appearing in an AA-authored unit: [4](#0-3) 

AAs can only send payments by having their bytecode emit `payment` messages, which are turned into `transfer`/`issue` inputs by the AA composer (e.g. `issueAsset`) — there is no code path in `aa_composer.js` that constructs a `headers_commission` or `witnessing` input for an AA response: [5](#0-4) 

Because an AA address can never author a unit outside of its own deterministic trigger-response mechanism, and that mechanism cannot produce `headers_commission`/`witnessing` inputs, any bytes credited to an AA via `earned_headers_commission_recipients` are permanently stuck in `headers_commission_outputs` with no possible spend path — mirroring the Dahlia case where fee-recipient shares were credited internally but the only withdrawal function required a caller/ownership condition the recipient could never satisfy.

### Impact Explanation
This results in a permanent, unrecoverable freezing of network bytes. Any ordinary user can trigger this unintentionally (by mistakenly or maliciously naming a well-known AA address as a headers-commission recipient in a multi-authored unit they control) or an attacker can deliberately grief a specific AA by never letting it collect commissions it is entitled to as an author — since these bytes are irrecoverably lost from circulation and from the affected AA's usable balance, this constitutes a fund-freezing bug (Medium severity, consistent with the analog report's classification), not merely a minor inconvenience.

### Likelihood Explanation
Triggering this requires only posting a normal multi-authored unit with `earned_headers_commission_recipients` pointing to an AA's address and getting that unit selected as the "winning child" for headers commission — both of which are natural, unprivileged actions available to any unit poster, requiring no special witnessing power, hub cooperation, or protocol upgrade. No malicious peer, node, or network-level behavior is needed.

### Recommendation
In `validateHeadersCommissionRecipients` (and analogously wherever headers-commission/witnessing recipients are validated), reject recipient addresses that are registered AA addresses (using the existing `aa_addresses` lookup pattern already used elsewhere, e.g. `checkNotAAs`), so that headers-commission shares can never be assigned to an address that has no way to redeem them.

### Proof of Concept
1. Alice controls address `A1` and also is one of two co-authors, together with Bob (`B1`), of unit `U` (multi-authored).
2. `U` sets `earned_headers_commission_recipients` to `[{address: "<AA_ADDRESS>", earned_headers_commission_share: 100}]`, where `AA_ADDRESS` is a live, already-defined Autonomous Agent.
3. `U` becomes stable and wins the "best child" race relative to one of its parents (headers-commission payer). `calcHeadersCommissions` credits the full headers commission to `AA_ADDRESS` in `headers_commission_outputs`.
4. Attempt to have the AA at `AA_ADDRESS` spend these bytes: any spend of a `headers_commission`-type credit requires a unit authored with an input `{type: "headers_commission", from_main_chain_index, to_main_chain_index}`. `validatePaymentInputsAndOutputs` rejects such an input whenever `objValidationState.bAA` is true (`validation.js:2531-2532`), and the AA composer never generates such an input for AA responses (`aa_composer.js` only builds `transfer`/`issue` inputs). Therefore the commission credited to `AA_ADDRESS` can never be spent by any unit, by the AA itself, or by anyone else (since only the credited address may claim it) — the funds are permanently frozen.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}

CREATE TABLE headers_commission_contributions (
	unit CHAR(44) CHARACTER SET latin1 COLLATE latin1_bin NOT NULL, -- parent unit that pays commission

	amount BIGINT NOT NULL,
	creation_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

	KEY byAddress(address),
	FOREIGN KEY (unit) REFERENCES units(unit)

	main_chain_index INT NOT NULL,

	is_spent TINYINT NOT NULL DEFAULT 0,
	creation_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
	PRIMARY KEY (main_chain_index, address),
	UNIQUE (address, main_chain_index),

) ENGINE=InnoDB  DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_520_ci;
