### Title
Reachable `throw Error` crash in `validatePaymentInputsAndOutputs` when validating a transfer input for a private fixed-denomination asset - (File: `validation.js`)

### Summary
`tf.raw_ops.TensorListResize`'s bug class is a reachable `CHECK_EQ` (hard assertion) that aborts the whole process when fed attacker-controlled, unexpected input shape — a classic CWE-617 "Reachable Assertion" DoS. `ocore`'s unit-validation pipeline contains an analogous unconditional `throw Error(...)` guard inside `validatePaymentInputsAndOutputs` in [1](#0-0)  that assumes an internal precondition (`objValidationState.src_coin` populated) that is only true when the function is invoked from the *internal* private-chain validation helper, but is false when the same function is reached through the *normal* public-unit validation path that any peer can trigger simply by posting a unit.

### Finding Description
`validatePaymentInputsAndOutputs` is the generic payment-message validator invoked from `validatePayment`/`validateMessage`, which is itself invoked for every message of every unit that passes through `validation.validate()` [2](#0-1) . For private, fixed-denomination assets, the payment message is *not* fully hidden on the DAG — the code explicitly expects such messages inline, with `output_hash`/`amount` visible while `address`/`blinding` are hidden, and validates them in this exact function: [3](#0-2) 

When such a message contains a `"transfer"`-type input, the code reaches: [4](#0-3) 

```
// for private fixed denominations assets, we can't look up src output in the database
// because we validate the entire chain before saving anything.
// Instead we prepopulate objValidationState with denomination and src_output
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    ...
```

`objValidationState.src_coin` is only ever set by `indivisible_asset.js`'s own private-payment-chain validator (`validatePrivatePayment`), which builds its own private `objValidationState` object and calls `validation.validatePayment` directly, bypassing `validation.validate()` [5](#0-4) . That is the *only* place in the codebase that populates `src_coin` before calling into payment validation.

However, `validatePaymentInputsAndOutputs` is also reached through the **normal public unit validation** entry point `validation.validate()` → `validateMessages` → `validateMessage` → `validatePayment`, whose `objValidationState` is built fresh in `validate()` and never contains `src_coin` [6](#0-5) . Any peer can compose and broadcast (or an attacker's node can forward) a unit whose payment message references an existing private, fixed-denomination asset with a `type: "transfer"` input. Because the message is inline (as required for private fixed-denomination assets), it goes through this exact public code path, `objValidationState.src_coin` is `undefined`, and the `throw Error("no src_coin")` fires.

This throw occurs deep inside an `async.forEachOfSeries` callback chain with no surrounding `try/catch` in the call stack (`validate()`'s `async.series` wraps errors returned via callback, not exceptions thrown asynchronously). An uncaught exception thrown from inside a Node.js callback crashes the entire process, exactly analogous to a `CHECK_EQ` fail aborting the TensorFlow process.

### Impact Explanation
Any node (full node, hub, or light-serving node) that validates a broadcast unit containing a transfer input for a private fixed-denomination asset will crash with an uncaught exception. Since unit validation happens automatically whenever a node receives a new joint from any peer, a single malicious unit — reachable by any unprivileged unit poster — can be propagated across the network and crash every full node/hub that processes it, preventing the network from confirming new units. This matches the accepted impact category "a network unable to confirm new units" and is a direct CWE-617 analog of the reported TensorFlow CVE (both are reachable hard-assertion/`throw`-based crashes triggered by attacker-supplied, structurally-valid-but-unexpected input).

### Likelihood Explanation
No special privileges, keys, or existing wallet relationship are required. An attacker only needs to know the address of one already-existing private, fixed-denomination asset (asset definitions are visible/discoverable on the public DAG) and craft a normal-looking unit with a payment message for that asset containing a `"transfer"` input pointing at any output (the input details are checked only after the crash-inducing branch, so even a bogus `unit`/`message_index`/`output_index` triggers the throw before those checks run). This is trivially reproducible and requires no timing tricks, race conditions, or peer compromise.

### Recommendation
Replace the unconditional `throw Error("no src_coin")`/`"no src_output"`/`"no denomination in src coin"`/`"no src coin amount"` guards in `validatePaymentInputsAndOutputs` (validation.js:2416-2424) with a returned validation error (`return cb(...)`) instead of a thrown exception, since this code path is provably reachable from untrusted, attacker-controlled input via the normal unit-validation entry point, not just from the internal, pre-vetted private-chain validator. If the intent is to keep this codepath exclusive to the internal private-chain validator, add an explicit guard earlier in `validatePaymentInputsAndOutputs` (or in the caller) rejecting `transfer` inputs for `objAsset.is_private && objAsset.fixed_denominations` when reached from the public `validate()` entry point, before `src_coin` is dereferenced.

### Proof of Concept
1. Identify (or issue, as an attacker-controlled address is fine since only the asset needs to already be private+fixed-denomination) an existing asset `A` with `is_private: true, fixed_denominations: true` on the target network.
2. Compose a normal unit whose `messages` array includes a `payment` message with `asset: A`, `denomination: <valid>`, one output with a valid `output_hash`/`amount` (per the private-asset inline format required by [3](#0-2) ), and one input `{ "type": undefined (i.e. transfer), "unit": "<any 44-char base64 string>", "message_index": 0, "output_index": 0 }`.
3. Sign and broadcast this unit as a normal joint via the P2P `network.js`/`handleJoint` path (no special access required — any wallet/light client can post units).
4. Any node that validates this unit calls `validation.validate()` → ... → `validatePaymentInputsAndOutputs`, reaches the `transfer` case for a private fixed-denomination asset, finds `objValidationState.src_coin` undefined, and executes `throw Error("no src_coin")` inside an async callback, crashing the node process.
