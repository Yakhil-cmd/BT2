### Title
Missing cosigner authorization check on local "sign" requests allows any paired device to trigger unauthorized signing/spending prompts for shared/multisig addresses - (File: wallet.js)

### Summary
In `handleMessageFromHub`'s `"sign"` case, when `findAddress` resolves the requested address to a locally-hosted key (`ifLocal`), the handler proceeds directly to emit a `"signing_request"` event without verifying that the sending device (`from_address`) is actually an authorized cosigner of the target multisig/shared address. The check that would perform this verification is present in the code but explicitly commented out.

### Finding Description
This is directly analogous to GHSA-48mj-p7x2-5jfm (esphome web_server allowing OTA update while skipping the basic-auth check that gates other operations): a security check exists elsewhere in the same logical flow but is bypassed for one specific code path.

In `wallet.js`, the `"sign"` message case handles signing requests for both remote (`ifRemote`) and local (`ifLocal`) key holders, via `findAddress`: [1](#0-0) 
For the `ifRemote` branch (i.e., when a member key of a multisig/shared address lives on another device and *this* device is a proxy relaying the request), the code correctly validates that the sender is a legitimate cosigner: `other_device_addresses.includes(from_address)`. If the check fails, it rejects with `"you are not listed as a cosigner for this address"`.

However, for the `ifLocal` branch — used when the requested signing key/address actually lives on *this* device (the common multisig case: "same address hosted on several devices") — the analogous check is commented out: [2](#0-1) 

The commented lines would have queried `extended_pubkeys` to confirm the sending device (`from_address`) is a registered cosigner of the wallet/shared address before proceeding. Without it, any device that is merely paired with this wallet node (a `correspondent_device`, not necessarily a genuine cosigner of the target address) can send a `"sign"` message referencing *any* address hosted locally by that node, and the handler will validate/parse the attacker-supplied `unsigned_unit` and fire the `signing_request` event which triggers the UI signing-confirmation dialog (`eventBus.emit("signing_request", ...)`), see `wallet.js:340-371`.

### Impact Explanation
This bypass removes the intended authorization gate that restricts who may originate a signing request against a shared/multisig address hosted on this wallet instance. While actual key material is still protected by the confirmation UI/dialog and by the address definition's own signature scheme (an attacker cannot forge a valid unit without eventually getting real cosigner signatures), the missing check:
- Allows any correspondent (paired) device — not just legitimate cosigners of a specific shared address — to spam/spoof signing requests for accounts they are not a party to, misleading the user's wallet UI into displaying spend confirmation dialogs for units they did not initiate.
- Undermines the multisig authorization model in which only registered `extended_pubkeys`/`wallet_signing_paths` cosigners should be able to solicit a specific device's signature, directly matching the CWE-306 "missing authentication for critical function" pattern of the reference advisory.
- If the local user is habituated to approving such prompts (e.g., automated wallet flows, or where UI confirmation is weak/absent), a non-cosigner correspondent could induce the wallet to co-sign an attacker-crafted unit for a shared address, resulting in unauthorized spending/fund loss when combined with other cosigners' signatures collected by other means.

### Likelihood Explanation
Reachable by any device already paired (correspondent) with the target wallet node — no additional privilege beyond an existing device pairing relationship is required to send a `"sign"` message, since the `ifLocal` branch performs no cosigner-membership check before proceeding (unlike `ifRemote`, which does). The asymmetry between the two branches strongly suggests the `ifLocal` check was intentionally disabled (per the comment) without adding an equivalent scoped verification, making this readily triggerable.

### Recommendation
Reinstate an authorization check in the `ifLocal` branch analogous to the `ifRemote` branch: confirm that `from_address` is registered as a legitimate cosigning device for the specific `body.address`/wallet (e.g., via `wallet_signing_paths`/`extended_pubkeys` or `shared_address_signing_paths`) before emitting `signing_request` or invoking `network.handleOnlineJoint`. If multilateral signing (different addresses signing the same message) must remain supported without this check, scope the exception narrowly (e.g., only for `signed_message` multilateral flows) rather than removing cosigner verification for all local signing requests, including standard multisig share spending.

### Proof of Concept
1. Attacker device pairs with the victim wallet node (a normal, unprivileged pairing — `device.handlePairingMessage`, `wallet.js:97-98`) and thereby becomes a `correspondent_device`, without being added as a cosigner of any of the victim's shared/multisig addresses.
2. Attacker sends a `"sign"` message to the victim node: `{address: "<victim's shared address hosted locally>", signing_path: "r.0", unsigned_unit: {...attacker-crafted unit spending from that address...}}`.
3. `findAddress` resolves the address/path to a local key (`ifLocal`) since the key lives on the victim's device.
4. Because the cosigner check is commented out, the handler proceeds without validating that the attacker's device is an authorized cosigner, validates the unit's structural fields, and emits `signing_request`, causing the victim's wallet UI to prompt for approval of a unit the attacker was not authorized to request signing for — an authorization bypass, matching the missing-auth-check pattern of GHSA-48mj-p7x2-5jfm.
