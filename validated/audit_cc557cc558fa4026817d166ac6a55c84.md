### Title
`Api::CCMenuController#stack` bypasses the `stacks` scope and calls `Stack.from_param!` directly - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` enforces per-token stack scoping via a `stacks` scope method (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) combined with `stacks.from_param!` in its `stack` method. `Api::CCMenuController` overrides `stack` and resolves it with `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` model, completely bypassing the `current_api_client.stack_id` restriction.

### Finding Description
The binding that must hold is: `resolved_stack.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` is true (i.e., the token is scoped to a specific stack).

In `Api::BaseController`:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::CCMenuController` overrides `stack` to bypass this scope:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

The permission check `require_permission :read, :stack` only validates that the token has the string permission `"read:stack"` in its `permissions` array — it never checks the target stack's id against `current_api_client.stack_id`:
```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

So the only place stack-id scoping is enforced is the `stacks` method in the base controller, and `CCMenuController` skips it entirely. An `ApiClient` created with `stack_id` set to stack A and `permissions: ["read:stack"]` can call `GET /api/stacks/:other_stack_id/ccmenu.xml?token=<token>` for any stack B and successfully resolve `stack` to B, because `Stack.from_param!` is unscoped.

The controller also overrides `authenticate_api_client` to accept the token via `params[:token]` instead of HTTP Basic Auth, which is how the attacker can trivially supply the token in a plain `GET` URL:
```
def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [4](#0-3) 

Existing guards do not prevent this: `require_permission!`/`check_permissions!` only checks the operation:scope string, not the specific stack id; there is no model-level validation tying an `ApiClient`'s allowed stacks to the resolved `Stack` record other than the bypassed `stacks` method.

### Impact Explanation
A token scoped to one stack (tenant/repository) can read another stack's CCMenu status data (`deploys_and_rollbacks.last`, deploy status/ended_at, running state) via `GET /api/stacks/:other_stack_id/ccmenu.xml`. This is a cross-tenant unauthorized read of stack/deploy state, repeatable against any stack id in the system with just a single valid scoped `ApiClient` token. This matches "High - unauthorized read of stack state ... task streams or deploy output" (it does not achieve write/RCE, so Critical categories like mutating another stack or forged auth are not reached — the token itself is legitimate but its scope restriction is bypassed).

### Likelihood Explanation
Preconditions: `Shipit.disable_api_authentication` is false (default), and an `ApiClient` scoped to a specific stack (`stack_id` set) with `read:stack` permission exists — this is a normal, common Shipit API client configuration for scoped integrations. The attacker needs only a valid token issued for their own stack (which they legitimately hold as an authorized user of stack A), and can then enumerate/target any other stack id. Cost is a single unauthenticated-style GET request; fully repeatable across every stack in the installation.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped `stacks` method inherited from `BaseController` instead of calling `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Remove the private override entirely if it adds no other behavior, and audit other controllers (e.g. `Api::HooksController`) for the same anti-pattern to ensure all stack resolution goes through the scoped `stacks` method.

### Proof of Concept
```ruby
# test/controllers/shipit/api/ccmenu_controller_test.rb
test "CCMenuController#stack does not honor api client stack scoping" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack

  scoped_client = ApiClient.create!(
    creator: shipit_users(:codertocat),
    name: 'scoped-client',
    stack_id: stack_a.id,
    permissions: ['read:stack']
  )

  get "/api/stacks/#{stack_b.id}/ccmenu.xml", params: { token: scoped_client.authentication_token }

  # BROKEN BINDING: resolved stack id should equal current_api_client.stack_id when scoped
  assert_response :success
  # response body corresponds to stack_b, not stack_a -- cross-tenant read
  assert_includes @response.body, stack_b.to_param
  refute_includes @response.body, stack_a.to_param
end
```
This demonstrates that `resolved_stack.id (stack_b.id) != current_api_client.stack_id (stack_a.id)` yet the request succeeds, confirming the scope bypass via `Stack.from_param!` instead of `stacks.from_param!`.
