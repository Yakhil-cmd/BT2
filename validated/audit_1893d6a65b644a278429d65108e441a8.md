### Title
Accidental token transfers to a lending pool become permanently unclaimable surplus - ([File: contracts/pool/src/cache/cash.rs](contracts/pool/src/cache/cash.rs))

### Summary
A user who directly transfers a supported token to its XOXNO Lending pool permanently loses the transferred amount because the donation increases the pool contract's token balance without increasing accounting `cash`, and no unprivileged recovery path can withdraw the excess. The strongest path is a direct Soroban token `transfer(sender, pool, amount)` to a deployed pool.

### Finding Description
Pool liquidity accounting distinguishes the token contract's physical balance from the market's internal `cash` balance. Only accounting mutations such as supply and net repayment call `credit_cash`; a direct token transfer bypasses the pool and therefore cannot update `cash`. [1](#0-0)  Withdrawals check `cash >= amount` before debiting and sending tokens, so the donated surplus cannot be paid out as liquidity beyond the recorded reserves. [2](#0-1)  Outbound transfers only move a caller-specified accounted amount and do not scan for or reclaim excess token balance. [3](#0-2)  Revenue withdrawal similarly pays only the amount represented by claimable revenue shares rather than arbitrary excess token balance. [4](#0-3)  The public pool interface exposes market operations but no rescue or sweep entrypoint for uncredited token surplus. [5](#0-4) 

### Impact Explanation
The sender's accidentally transferred tokens remain at the pool address while no market share, debt position, revenue share, or `cash` credit is created for them. They are permanently frozen for the sender and cannot be recovered through any user-reachable lending operation.

### Likelihood Explanation
Any unprivileged token holder can reach this state with one ordinary token transfer to the pool address. The issue does not depend on oracle behavior, token issuer cooperation, administrator action, or a protocol malfunction; it requires only the mistaken direct transfer.

### Recommendation
Add an explicit owner- or governance-controlled surplus recovery entrypoint that computes `token.balance(pool) - required_accounting_backing` for the asset and transfers only the uncredited surplus to a designated recipient. The function must reject listed-market principal and revenue by using the accounting `cash`/market backing amount rather than the entire token balance.

### Proof of Concept
1. Let `P` be a deployed pool address and `T` its configured token.
2. An unprivileged user calls `T.transfer(user, P, 1_000)`.
3. `P`'s token balance increases by `1_000`, while the market's `cash` remains unchanged because no pool entrypoint credited the transfer.
4. A supplier can withdraw only against recorded `cash`; `withdraw` calls `require_reserves(net_transfer)` before `debit_cash(net_transfer)`.
5. `claim_revenue` can withdraw only `burn_claimable_revenue()` and therefore cannot select the donated `1_000`.
6. Since no pool entrypoint transfers an unbooked surplus, the `1_000` remains permanently locked at `P`.

    /// Increases accounting cash by `amount`. Rejects negative amounts and overflow.
    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

/// Enforces reserve, utilization, and solvency guards, then debits cash for
/// the net transfer. Liquidations and footprint-only closes skip utilization.
fn gate_and_debit(env: &Env, cache: &mut Cache, net_transfer: i128, skip_utilization_check: bool) {
    cache.require_reserves(net_transfer);

    if !skip_utilization_check {
        guards::require_utilization_below_max(env, cache);
    }
    guards::require_supply_for_debt(env, cache);
    cache.debit_cash(net_transfer);
}
