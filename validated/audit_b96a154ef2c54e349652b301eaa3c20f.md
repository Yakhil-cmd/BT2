### Title
Webhook signature verification authenticates against `repository.owner.login`/`organization.login` while every event handler dispatches against the independently-supplied `repository.full_name`, letting a valid signer from one configured GitHub organization forge writes against a repository owned by a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration where each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to check against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [2](#0-1) [3](#0-2) . However, once the signature check passes, every handler resolves the target repository/stack from a completely different, independently-controlled field of the same JSON body: `payload.dig('repository', 'full_name')` [4](#0-3) , which is used directly by `Repository.from_github_repo_name` in handlers such as `PullRequest::ClosedHandler#repository` [5](#0-4) . Nothing ties `repository.owner.login` (used to pick the signing secret) to `repository.full_name` (used to pick the acted-upon repository) beyond application-level convention.

### Finding Description
The equality that should hold is: `organization whose webhook_secret authenticated the request == organization that owns the repository the handler writes to`. Concretely, for a request body B:
- Verification org = `B.repository.owner.login` (or `B.organization.login`) [3](#0-2) 
- Acted-upon repo = `Repository.from_github_repo_name(B.repository.full_name)` [6](#0-5) 

`verify_signature` only proves that whoever crafted the raw JSON body knew the HMAC secret for the organization named in `repository.owner.login`/`organization.login` [2](#0-1) ; it never checks that this is the same organization that owns `repository.full_name`, and no handler re-validates that binding either [4](#0-3) .

Under the deployment's documented multi-org model, each GitHub organization has its own app/webhook_secret entry in `config/secrets.yml` [7](#0-6) , and `Shipit.github(organization:)` looks up per-organization config keyed by that organization name [8](#0-7) . An operator/administrator of one tenant organization ("org-A") that is configured in a shared Shipit instance controls their own org's `webhook_secret` value (they configured the GitHub App and can read/rotate it, or can simply send events that GitHub itself signs for org-A). That operator has zero privilege on "org-B" (another tenant sharing the same Shipit instance) - no GitHub repo access, no Shipit session, no API token. They can nonetheless build an arbitrary JSON payload, set `repository.owner.login`/`organization.login` to `"org-A"` (their own, satisfying `verify_signature`), sign it with org-A's secret, but set `repository.full_name` to `"org-B/victim-repo"`. `verify_signature` passes because org-A's secret matches, and the dispatched handler then operates on whatever stack/review-stack belongs to `org-B/victim-repo`, entirely bypassing any notion that org-A's credential should only be trusted for org-A's repositories.

### Impact Explanation
Depending on the event type dispatched this becomes a genuine cross-repository write: e.g. `pull_request` `closed` event forges `review_stack.archive!` against a review stack under a repository the attacker's organization does not own [9](#0-8) ; `push` events can similarly be forged to enqueue sync/deploy jobs against another organization's stack. This crosses the "organization that authenticated versus the repository that is written" trust boundary defined by the rules and results in unauthorized cross-organization writes/state changes on stacks the attacker's credential was never meant to authorize.

### Likelihood Explanation
This requires the deployment to actually use the multi-organization GitHub App configuration documented in `docs/setup.md`, and requires the attacker to control (or otherwise obtain the secret for) at least one of the configured tenant organizations while targeting another tenant's repository on the same Shipit instance. This is a realistic scenario for shared/multi-tenant Shipit deployments, which is the exact use case the multi-org configuration feature exists for, but does not apply to single-organization deployments (where `repository_owner` and the acted-upon org are trivially the same).

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), after verifying the HMAC signature, additionally assert that the organization used to select the webhook secret (`repository_owner`) matches the owner segment of `repository.full_name` (and/or the resolved `Repository#owner`) before dispatching to handlers; reject the request with `422` if they diverge.

### Proof of Concept
1. Shipit is configured with two tenant organizations, `org-A` and `org-B`, each with its own `webhook_secret` per the multi-org config format [7](#0-6) .
2. Attacker controls `org-A`'s GitHub App / webhook_secret (e.g. is the admin who set it up) and has no access to `org-B` or any Shipit session/API token.
3. Attacker crafts a `pull_request` `closed` webhook JSON body where `organization.login` / `repository.owner.login` = `"org-A"` but `pull_request.repository.full_name` = `"org-B/victim-repo"`, and computes `X-Hub-Signature` using `org-A`'s `webhook_secret` per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` logic [10](#0-9) .
4. POST to `/webhooks` (the engine's webhook endpoint). `verify_signature` resolves `Shipit.github(organization: "org-A")` and validates the signature successfully [2](#0-1) .
5. `PullRequest::ClosedHandler` is invoked, resolves `repository` via `Repository.from_github_repo_name("org-B/victim-repo")` [5](#0-4)  and calls `review_stack.archive!` on `org-B`'s review stack, even though only `org-A`'s credential was ever proven.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
