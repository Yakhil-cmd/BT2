## Finding

Shipit's webhook ingestion binds the *organization used to select and verify the webhook secret* to a completely different, attacker-controlled field: the *repository/commit that the handler actually mutates*. This mirrors the `staking-ko` bug class ("a field acted on but never covered by the verified authorization") — here the org that authenticates the request is not the same org whose data gets written.

### Title
Webhook Organization-Selection Bypass Allows Unauthenticated Cross-Repository State Mutation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `repository.owner.login` from the untrusted JSON body, then defers verification entirely to `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally whenever that organization's `webhook_secret` is blank — a state explicitly supported as "optional" configuration. The handlers that then act on the payload use unrelated fields (`repository.full_name`, `sha`, `team`, `member.login`, etc.) that are never checked for belonging to the organization that was "verified."

**Broken equality:** `organization_verified(repository.owner.login, secret) == organization_owning(repository/commit mutated by handler)`.
- *Before*: real GitHub deliveries always keep these consistent, and a configured secret makes forgery infeasible.
- *After*: an attacker POSTs directly to the public `/webhooks` endpoint (not through GitHub) naming any Shipit-configured organization that happens to have no `webhook_secret` set for the `owner.login` field (satisfying "verification"), while setting `sha` / `repository.full_name` / `team` / `member.login` to point at a completely different tracked repository, commit, or team.

### Impact Explanation
This crosses a credential/organization boundary with no session, ApiClient token, webhook secret, or GitHub App key required — a purely network-reachable, unauthenticated `/webhooks` POST. Concrete effects:
- `StatusHandler` lets the attacker fabricate a "success" commit status for **any** commit sha tracked by Shipit, independent of which org it belongs to, which is exactly the mechanism Shipit uses to gate deployability of a stack — enabling an **unauthorized deploy** of an unreviewed/unapproved commit.
- `MembershipHandler` lets the attacker add or remove arbitrary GitHub logins from any `Team` record, escalating into `Shipit.github_teams`-based authorization checks used by `force_github_authentication`.
- `PushHandler`/`CheckSuiteHandler` let the attacker trigger sync/check-run jobs against stacks/branches belonging to organizations they don't control.

This satisfies the Critical bucket ("an unauthorized deploy") and the High bucket ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Requires only: (1) the Shipit instance configured for multiple GitHub organizations (a documented, supported feature — see `test/dummy/config/secrets_double_github_app.yml`), and (2) at least one of those organizations left with `webhook_secret` unset (documented as "optional"). No credentials, sessions, or secret knowledge are needed by the attacker; only trial POSTs to the public `/webhooks` endpoint with varying `repository.owner.login` values to find one that returns 200 rather than 422.

### Recommendation
- Do not treat a blank `webhook_secret` as automatic verification success; require every configured organization to have a secret, or fail closed.
- Cryptographically bind the "authenticated organization" to every mutated resource: verify that `repository.full_name`'s owner segment, `sha`'s owning repository, and `team`/`organization.login` all match `repository_owner` before dispatching to a handler.
- Scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks under the verified organization, not a global lookup.

### Proof of Concept
1. Assume a Shipit instance configured with two GitHub Apps: `OrgA` (no `webhook_secret` set) and `OrgB` (has `webhook_secret` set, and owns the stack/commit the attacker wants to affect).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" },
  "sha": "<victim commit sha in OrgB's tracked stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of any (or no) `X-Hub-Signature` header.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a fabricated "success" status on the victim commit belonging to `OrgB`, with no cross-check that `OrgB` was the organization actually verified.

**Note on confidence:** I was not able to inspect `Commit#create_status_from_github!` or `Stack#deployable?` in this session to directly confirm that a forged "success" status alone unlocks the deploy UI, so the "unauthorized deploy" impact is based on the well-established purpose of Shipit's status/CI-gating feature rather than a line-by-line trace of the deploy-gating code. This should be verified directly against `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb` if a maintainer wants full certainty on deploy-gating specifics.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
