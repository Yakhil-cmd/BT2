### Title
Webhook signature verified against attacker's organization while payload's `repository.full_name` selects the victim stack to act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization deployments, `Shipit.github(organization:)` looks up a per-organization `webhook_secret` keyed by `repository_owner`, which is derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . But the handlers that actually execute side effects (triggering `GithubSyncJob`, syncing stacks, creating commit statuses, archiving review stacks, etc.) resolve the target repository/stack from a *different* field in the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')` [2](#0-1) . Because `repository.owner.login` and `repository.full_name` are independent, unauthenticated JSON fields inside the same unsigned-until-verified body, an attacker who controls (or is a collaborator on) any repository under an organization `A` configured in `Shipit.secrets.github` can forge a valid HMAC using organization `A`'s `webhook_secret`, while setting `repository.full_name` to organization `B`'s (victim's) repo/stack. The signature check passes (it's checking org A's secret against the full raw body, which the attacker fully controls and signs correctly), yet the `Handler` subclasses act on organization `B`'s stack.

### Finding Description
The binding that should hold is: **organization that authenticates the webhook == repository that is written/acted upon**. `repository_owner` (used only for HMAC secret selection) is decoupled from `repository_name`/`full_name` (used only for target resolution):
- `verify_signature` selects the app/secret via `repository_owner` [3](#0-2) .
- `Handler#stacks` resolves the acted-upon `Repository` via `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository', 'full_name')` [2](#0-1) .
- Nothing cross-checks that `repository.owner.login` equals the owner segment of `repository.full_name`.

`Shipit.github(organization:)` looks up `secrets.github[organization]`, i.e. a distinct `webhook_secret` per configured GitHub App/organization [4](#0-3) , and `verify_webhook_signature` just HMACs the raw request body with whichever secret was selected [5](#0-4) . Since the attacker fully controls the raw JSON body (this is a webhook endpoint, not something GitHub itself mediates field consistency for), they can put `repository.owner.login = "org-they-control"` and `repository.full_name = "victim-org/victim-repo"` in the same payload, compute the correct HMAC with their own org's known `webhook_secret`, and have the request pass `verify_signature`, after which `PushHandler`, `StatusHandler`, etc. operate on the victim stack using `full_name` [6](#0-5) .

### Impact Explanation
`PushHandler` enqueues `GithubSyncJob` for any stack matching the forged branch/`full_name`, which pulls/syncs the victim repository's commits and can drive downstream automation (statuses, continuous deployment triggers) for a stack the attacker has no legitimate access to — this is an unauthorized cross-repository/cross-organization action reachable purely by knowing one organization's webhook secret (their own, legitimately configured) and guessing/knowing another organization's stack naming. This matches the "cross-repository writes" / "unauthorized deploy" class of Critical impact defined in scope, contingent on the target Shipit instance being configured with multiple GitHub App organizations (the `github_app_config` / multi-org secrets path) [7](#0-6) .

### Likelihood Explanation
This requires the Shipit deployment to be configured with **more than one** organization/app in `secrets.github` (the multi-tenant schema, as opposed to the single top-level schema) so that distinct webhook secrets exist per org and an attacker can legitimately obtain one (e.g., they administer their own org's GitHub App installation pointed at the same Shipit instance). This is a real, supported configuration path (`github_app_config`, `TOP_LEVEL_GH_KEYS`) [7](#0-6) , not a hypothetical misconfiguration, but it does depend on multi-org hosting being in use, which lowers likelihood somewhat relative to a single-org install.

### Recommendation
After computing `repository_owner` for secret selection, verify that it actually matches the owner segment of `payload.dig('repository', 'full_name')` (and of `organization.login`, when present) before dispatching to handlers; reject the webhook (422) on mismatch. Alternatively, have handlers resolve the target repository via the same `repository_owner`-scoped lookup used for signature verification rather than trusting `full_name` independently.

### Proof of Concept
1. Deployment hosts two orgs, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` in `secrets.github` [7](#0-6) .
2. Attacker knows `org-a`'s `webhook_secret` (e.g., they are `org-a`'s legitimate GitHub App admin).
3. Attacker crafts a `push` event JSON body: `repository.owner.login = "org-a"`, `repository.full_name = "org-b/victim-repo"`, `ref = "refs/heads/master"`, `after = <attacker-chosen sha>`.
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org-a's webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and the signature validates [1](#0-0) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` [2](#0-1)  and enqueues `GithubSyncJob` for `org-b`'s stack — an action the attacker has no authorization to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
