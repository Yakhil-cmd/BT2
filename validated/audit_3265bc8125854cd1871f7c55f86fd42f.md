Based on my research, I found a concurrency gap that is structurally analogous to the qrtr bug class (a state-mutating operation proceeding without the synchronization that protects the rest of the same subsystem, opening a race window that a remote/unprivileged party can trigger to corrupt shared state).

### Title
Missing serialization for concurrently-received private-payment chains allows a private-payment counterparty to race duplicate-output checks and double-spend a private output - ([File: private_payment.js])

### Summary
Public/AA units are always validated and written under the global `mutex.lock(['handleJoint'])` before touching the `outputs`/`inputs` tables [1](#0-0) , and even the composer's own private-payment saving path explicitly takes `mutex.lock('handleJoint')` before validating and writing [2](#0-1) [3](#0-2) . However, the path that handles a private payment chain *received from a peer/paired device* (`network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`) does not acquire this (or any) mutex before doing its "check-then-act" duplicate-detection and insert.

### Finding Description
`handleOnlinePrivatePayment` in `network.js` explicitly disables the in-work guard for private payments — the `assocUnitsInWork[unit] = true`/`delete assocUnitsInWork[unit]` calls are commented out [4](#0-3) , so nothing prevents two chains for the same `(unit, message_index, output_index)` from being processed concurrently by two separate calls into `privatePayment.validateAndSavePrivatePaymentChain`.

That function takes a *fresh* connection from the pool, opens its own `BEGIN`, runs a `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` duplicate check, and only after seeing no conflicting row proceeds to call the asset module's save routine and `COMMIT`: [5](#0-4) [6](#0-5) 

This check-then-act sequence spans its own connection/transaction and is not protected by `mutex.lock`, unlike every other place in the codebase that mutates `outputs`/`inputs`. If a malicious private-payment counterparty (or paired device) sends two private-payment chains concurrently that both reveal/claim the same still-hidden output (e.g., two different `blinding`/`address` reveals racing each other, or the same chain resent while the first save is still mid-flight), both connections can pass the duplicate-check `SELECT` before either has committed its `UPDATE ... SET is_spent=1, address=?, blinding=?` on the shared `outputs` row, because the check runs on separate connections/transactions with no exclusive lock analogous to `handleJoint`. This mirrors the qrtr pattern where a state-mutating step (decrementing the refcount / here, deciding "not a duplicate, proceed to spend") happens before the operation that should make the check atomic (erasing from the XArray + RCU sync / here, an exclusive lock across check-and-write) — allowing a second concurrent actor to observe and act on stale state.

### Impact Explanation
If both racing chains complete their inserts/updates, the same private output can be marked spent twice via two different input rows (or two different addresses/blinding reveals can be accepted for the same output), which is exactly the "double-spend of a stable output" class of impact called out for this bug family — private balances and private asset transfer integrity are corrupted for legitimate wallet holders relying on `is_spent`/uniqueness state, and node/wallet state can disagree about which party legitimately owns the coins.

### Likelihood Explanation
Trigger requires only that the attacker is a paired device / private-payment counterparty able to send two (or more) `private_payment` chains for the same output in quick succession — no privileged network position, hub compromise, or protocol violation is needed, matching the "private payment chain" reachable-actor category. The race window is the time between the `SELECT` duplicate-check and the `COMMIT` of the `UPDATE`, which is plausible to win by simply sending both chains back-to-back (network jitter/db latency naturally creates the window); this is analogous in kind (not identical mechanism) to the kernel race that syzkaller reliably triggered between a refcount decrement and the RCU-protected removal.

### Recommendation
Serialize private-payment-chain validation/saving the same way public/AA units and the composer's own private-payment path are serialized: acquire `mutex.lock(['handleJoint'])` (or a dedicated per-output/per-unit lock keyed on `unit:message_index:output_index`) in `privatePayment.validateAndSavePrivatePaymentChain` (or in `network.handleOnlinePrivatePayment` before calling it) so that the duplicate-check `SELECT` and the subsequent `INSERT`/`UPDATE` execute atomically with respect to other concurrent private-payment saves for the same output.

### Proof of Concept
1. Pair with a target wallet as `device_address` A (a normal private-payment counterparty).
2. Craft a valid private-payment head element for asset X, output index N (indivisible or divisible, either works given the shared `outputs` table update pattern).
3. Send this chain to the target twice, essentially simultaneously (e.g., over two separate WS frames issued back-to-back, or via hub relay + direct P2P relay of the same chain), so that `network.handleOnlinePrivatePayment` is invoked twice for the same `(unit, message_index, output_index)` before the first invocation's `COMMIT` lands (no `assocUnitsInWork` guard blocks this — confirmed the guard is commented out).
4. Because `privatePayment.validateAndSavePrivatePaymentChain` opens independent connections/transactions per call and only synchronizes via a plain `SELECT` check (no `mutex.lock`), both calls can pass the duplicate check and each mark the shared output row as spent/finalized, resulting in duplicate crediting/spending records for the same private output in the target's `outputs`/`inputs` tables.

**Note on confidence**: I was not able to fully verify, within the available tool budget, whether a DB-level `UNIQUE`/primary-key constraint on the `inputs` table (keyed on `src_unit, src_message_index, src_output_index`) would cause the second transaction's `INSERT` to fail outright rather than succeed, which would reduce this to a possible crash/unhandled-rejection issue rather than a full double-spend. The schema greps for `inputs`/`is_unique` returned matches in the SQL init files but I could not inspect their exact column definitions before running out of iterations, so this should be validated by a follow-up review of `initial-db/byteball-sqlite.sql`'s `inputs` table definition and the exact failure mode when a duplicate `INSERT` is attempted concurrently.
