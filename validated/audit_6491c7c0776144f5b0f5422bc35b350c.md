### Title
Stack-Scoped API Tokens Bypass Their `stack_id` Restriction in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single `Stack` via its `stack_id` column, and `Api::BaseController#stacks` enforces that scope for every controller that queries stacks through it. `Api::CCMenuController`, however, overrides `#stack` to look up `Stack.from_param!(params[:stack_id])` directly, completely skipping the `stack_id`-scoped `stacks` collection. Any valid `ApiClient` token with the generic `read:stack` permission — including one an administrator deliberately restricted to a single stack — can therefore be used to read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock status, etc.) of every stack in the Shipit instance, not just the one it was authorized for.

### Finding Description
`ApiClient` records can optionally be bound to one `Stack` (`belongs_to :stack, optional: true`) [1](#0-0) . This binding is meant to be the authorization boundary: `Api::BaseController#stacks` returns only the client's own stack when `stack_id` is set, and every stack-scoped lookup goes through it:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::StacksController` and `Api::TasksController` rely on this scoped `stack`/`stacks` accessor, so a token created with `stack: some_stack` is correctly confined to that one stack for those endpoints [3](#0-2) .

`Api::CCMenuController`, however, redefines `stack` independently of the scoped collection, bypassing the `stack_id` binding entirely:

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack

  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
``` [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [5](#0-4)  — it never checks whether the requested `stack_id` matches `current_api_client.stack_id`. Since `stack` calls `Stack.from_param!` on the raw, unscoped `Stack` model, `params[:stack_id]` can be any stack in the instance.

This is exactly the "authorized-scope vs. actually-touched-scope" binding break called out in the prompt: the equality that should hold is `current_api_client.stack_id == stack.id` for every request the token is used on, but in `CCMenuController` the check is skipped, so `stack.id` can be any stack while `current_api_client.stack_id` remains fixed to whatever the token was originally created for.

Tokens minted for exactly this narrow purpose exist in the codebase already: `CCMenuUrlController#client` creates an `ApiClient` with only `read:stack` permission intended to be handed out for CCTray/CI-dashboard integrations [6](#0-5) , and the fixtures show administrators explicitly creating stack-scoped clients, e.g. `here_come_the_walrus`, scoped to the `shipit` stack only [7](#0-6) . The existing test suite for this controller never exercises cross-stack access — it always requests `@stack.to_param`, the client's own stack [8](#0-7) , so this gap is untested.

### Impact Explanation
Any holder of a valid `ApiClient` token that has `read:stack` permission — even one an operator deliberately scoped to a single low-sensitivity stack to limit exposure (e.g. a third-party CI dashboard integration) — can enumerate and read the build/deploy status, lock state, and last build label of every other stack managed by the Shipit instance simply by varying `stack_id` in the request. This is an unauthenticated-scope read of stack state beyond what the credential was authorized for, matching the "High - escalation into authorization... unauthenticated read of stack state" impact category: the token authenticates successfully and is used exactly as designed, but the authorization boundary (`stack_id`) that is supposed to confine it is not enforced on this endpoint.

### Likelihood Explanation
Exploitation requires only possession of any pre-existing, narrowly-scoped `ApiClient` token with `read:stack` permission (routinely distributed for CCMenu/CI dashboard integrations via `CCMenuUrlController`) — no GitHub session, webhook secret, or elevated privilege is needed. The attacker just changes the `stack_id` request parameter. This is a straightforward, always-reachable logic gap rather than a race condition or timing-dependent issue, making it highly likely to be exploitable wherever such scoped tokens are issued.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` collection (as `StacksController`/`TasksController` do), e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a `stack_id`-scoped `ApiClient` can only ever resolve to its own stack, consistent with the enforcement already present in `Api::BaseController`.

### Proof of Concept
1. An operator creates (or the app auto-creates via `CCMenuUrlController`) an `ApiClient` scoped to `stack_id: A` with permission `read:stack` and hands the resulting token to a third-party CI dashboard for stack A only.
2. That token holder sends `GET /api/1/stacks/:B/ccmenu.xml?token=<token>` where `B` is a different stack's identifier.
3. `authenticate_api_client` in `CCMenuController` succeeds via `ApiClient.authenticate(params[:token])` [9](#0-8) ; `require_permission :read, :stack` passes because the token has `read:stack`; `stack` resolves `Stack.from_param!(B)` directly, bypassing the `stack_id == A` restriction, and the response leaks stack B's build/deploy status even though the token was never authorized for stack B.
