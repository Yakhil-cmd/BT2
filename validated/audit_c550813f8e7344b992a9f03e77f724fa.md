### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read the status of any stack, not just the stack it authorizes - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` authenticates a request using an `ApiClient` token but resolves the target `Stack` from the raw `stack_id` path segment instead of from the API client's authorized scope. This breaks the binding: `current_api_client.stack_id` (the stack the token authorizes) != the stack the token can actually touch (any stack in the system).

### Finding Description
`Shipit::Api::BaseController` establishes the trust boundary for scoped API clients: when an `ApiClient` has a `stack_id` set, requests must be limited to that stack via the `stacks` helper, and `stack` is derived from that scoped relation: [1](#0-0) 

Every other stack-scoped API controller (e.g. `Api::StacksController`) resolves the target stack through this scoped `stacks` relation: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass the scoped relation entirely and look the stack up directly from the global `Stack` model using the unscoped `params[:stack_id]`: [3](#0-2) 

It still declares `require_permission :read, :stack`, which only checks that the client's `permissions` array includes `"read:stack"` — it never checks `current_api_client.stack_id`: [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id == stack.id` (or "no restriction" when `stack_id` is nil) — is broken specifically in this controller: any client whose permission set includes `read:stack`, even one explicitly scoped to a single stack at creation time, can supply an arbitrary `stack_id` in the URL and the controller will happily render that other stack's CI/build status.

### Impact Explanation
This is a High-severity issue per the "unauthenticated read of stack state ... or deploy output" impact category: it escalates a token deliberately scoped to a single stack (`ApiClient#stack_id`) into read access over every stack tracked by the Shipit instance. The `/api/stacks/*stack_id/ccmenu` route (and the human-facing `/ccmenu/*stack_id` URL generated by `CCMenuUrlController`) exposes stack name, last build status/label, and lock/failure state: [5](#0-4) [6](#0-5) 

An organization that intentionally issues narrowly-scoped tokens (e.g. a CI dashboard client scoped to one non-sensitive stack, exactly the `here_come_the_walrus` fixture pattern used in tests) loses that isolation guarantee for this one endpoint, letting the token holder enumerate/observe build status across all stacks, including ones they were never granted access to.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token with the `read:stack` permission (a routine, low-privilege credential many integrations receive, e.g. via `CCMenuUrlController#client`) can trigger this by simply changing the `stack_id` segment of the URL — no additional secret, signature, or privilege is required. This matches the confirmed pattern in the underlying report: an authorization check (`read:stack`) passes while the record actually touched is not the one the credential was bound to.

### Recommendation
Make `Api::CCMenuController#stack` use the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot resolve a `stack_id` outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or observe) a stack-scoped `ApiClient` such as the `here_come_the_walrus` fixture: `stack: shipit`, `permissions: ['read:stack']`. [7](#0-6) 
2. Authenticate normally with that client's `authentication_token` (Basic auth), as done in existing tests: [8](#0-7) 
3. Issue `GET /api/stacks/<other-owner>/<other-repo>/<other-environment>/ccmenu` using a `stack_id` that is *not* the client's authorized stack.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (unscoped) rather than `stacks.from_param!` (scoped to `current_api_client.stack_id`), the request succeeds with `200 OK` and returns the other stack's CI status XML, even though the client was only ever authorized for the `shipit` stack.
