This is the critical finding. `EnvironmentVariables#interpolate` at [1](#0-0)  explicitly `Shellwords.escape`s the env value before substituting it into a command argument, and `Command#start` passes `interpolated_arguments` as separate argv elements to `PTY.spawn` (not through a shell string) as shown in [2](#0-1) . This is confirmed by the test `test/unit/command_test.rb` line 23-27, which explicitly asserts that a malicious env value like `$(echo pwnd)` is *not* executed and is instead treated as a literal escaped string: `test '#interpolate_environment_variables escape the variable contents'` [3](#0-2) .

So the equality the question claims is broken — "attacker-controlled label name reaches `Command#start`'s argv/env such that arbitrary code executes" — does not hold: `label_name` becomes only a literal environment-variable **value** ("true") keyed by an uppercased, attacker-chosen **name** via `ReviewStack#env` [4](#0-3) , but:

1. The command **argv** itself comes exclusively from the maintainer-authored `shipit.yml` deploy spec (e.g. `deploy.override`, `tasks.*.steps`), never from PR labels. An attacker can only get a new *value* into the environment hash if the maintainer's own script happens to reference `$THAT_EXACT_UPPERCASED_LABEL_NAME` — an unpredictable, maintainer-authored token, not attacker-controlled.
2. Even if a maintainer script did `$SOME_LABEL`, `EnvironmentVariables#interpolate` shell-escapes the substituted value [5](#0-4) , and the resulting argv element is passed to `PTY.spawn` as a discrete array element rather than through `/bin/sh -c`, so shell metacharacters in the label name can't break out of the argument.

The `opened` PR provisioning gate for `allow_all` is indeed reachable by an unprivileged forked PR without any label check [6](#0-5) , and PR labels do flow unfiltered into `ReviewStack#env` (confirmed by `test/models/shipit/review_stack_test.rb:59-65` and `test/lib/shipit/task_commands_test.rb`). But that only lets an attacker set an arbitrary **environment variable name to "true"** — not inject new argv tokens, alter which script runs, or achieve command injection, because the argv is fixed by the maintainer's spec and env-value interpolation is shell-escaped.

Therefore the claimed RCE path does not exist as stated; at most this is an (out-of-scope, already-documented-as-intended) mechanism for a PR to influence the presence of arbitrary boolean env vars in provisioned review-stack tasks — a feature, not a vulnerability, and not by itself enough to control `Command#args` or bypass the shell-escaping in `EnvironmentVariables#interpolate`.
