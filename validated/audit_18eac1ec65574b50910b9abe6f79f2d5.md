### Title
Attacker-controlled `repository.owner.login` selects the webhook-signature key, letting a spoofed payload masquerade as any other repository's event - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments, `WebhooksController#verify_signature` picks *which* GitHub App/secret to verify a webhook against using `repository_owner`, a value read straight out of the still-unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` / `params.dig('organization', 'login')`). The event handlers that actually act on the request, however, key off a *different* field of the very same payload - `repository.full_name` - to look up the `Stack`/`Repository` to mutate. Nothing ties the two together: the signature only proves "the sender knows the secret configured for `repository_owner`", not "the sender is authorized for the repository named in `repository.full_name`".

### Finding Description
`WebhooksController#verify_signature` resolves the verifying GitHub App using the attacker-supplied `repository_owner`: [1](#0-0) 

`repository_owner` is taken directly from the JSON body before any signature check has occurred: [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization** config/secret in multi-tenant setups: [3](#0-2) 

Crucially, `verify_webhook_signature` treats an organization with no configured `webhook_secret` as automatically verified: [4](#0-3) 

Meanwhile, once the request passes `verify_signature`, handlers dispatch purely on `params` and resolve the target `Repository`/`Stack` from a **different** field of the same JSON body - `repository.full_name` - which is never cross-checked against `repository_owner`: [5](#0-4) [6](#0-5) 

Equality that should hold but is broken: `organization whose secret authenticated the request == owner of the repository the handlers act on`. Because both `repository_owner` (used to pick the verification key) and `repository.full_name` (used to pick the target Stack) are independent, attacker-controlled fields of the same unauthenticated JSON body, an attacker can set them inconsistently. If any organization configured in `secrets.yml` for this Shipit instance has no `webhook_secret` set (a documented, supported configuration per `docs/setup.md`), a request claiming `repository.owner.login` = that no-secret org sails through `verify_signature` unconditionally, while `repository.full_name` can be set to *any other* onboarded repository/organization, e.g. `victim-org/victim-repo`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out as an in-scope analog class. A successful forgery lets an unauthenticated caller drive the `PushHandler` for an arbitrary stack, causing it to enqueue `GithubSyncJob` for that stack with an attacker-chosen `expected_head_sha`: [7](#0-6) 

This can force the stack's git cache to fetch/append the attacker-chosen commit (or repeatedly poll and retry against GitHub for it), and depending on `continuous_deployment` configuration on the affected stack, can move that stack toward deploying/rolling back a commit it wouldn't otherwise have synced, and can also flip the stack's accessible/inaccessible state via `mark_as_inaccessible!`/`mark_as_accessible!`. The `pull_request` handlers (`OpenedHandler`, `LabeledHandler`, etc.) are reachable the same way and can create/archive/unarchive *review stacks* for a repository the attacker does not control, based on the same `repository.full_name` trust gap. This is an unauthenticated cross-repository write/state manipulation against Shipit's own model of stacks, satisfying the High-impact bar ("escalation... unauthorized deploy/rollback", "unauthenticated ... task streams"/state change) without needing any `ApiClient` token, session, or `webhook_secret` knowledge.

### Likelihood Explanation
Likelihood is Medium: the flaw is entirely in engine code and requires no privileged credentials by itself, but it is only reachable when the specific multi-organization deployment has at least one onboarded GitHub organization configured without a `webhook_secret` (an explicitly supported code path in `GitHubApp#verify_webhook_signature`, not a coding error on the operator's part, but not the default/typical secure configuration either). Any Shipit instance managing multiple organizations where even one is left with a blank `webhook_secret` (e.g., during onboarding, staging orgs, or legacy setups) is exposed.

### Recommendation
- Never allow `repository_owner`/`organization` to control verification unless the resulting secret is present and non-empty; treat a missing `webhook_secret` for an organization as "reject the webhook," not "auto-verify."
- After signature verification, re-derive/cross-check that the organization whose secret verified the payload actually owns the repository referenced by `repository.full_name` (i.e., `full_name.split('/').first == repository_owner`) before dispatching to handlers.
- Consider verifying the signature against every configured secret when using a shared multi-tenant webhook endpoint, rather than trusting a payload-supplied org name to select the key.

### Proof of Concept
1. In `secrets.yml` for the multi-org Shipit instance, organization `empty-org` is onboarded with no `webhook_secret` (supported by `GitHubApp#verify_webhook_signature`), while `victim-org` has a proper stack registered and a real, secret-protected webhook.
2. Attacker POSTs directly to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "empty-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
No `X-Hub-Signature` needs to be valid because `verify_webhook_signature` returns `true` unconditionally for `empty-org` (no secret configured).
3. `verify_signature` passes (uses `empty-org`'s config), `Webhooks.for_event('push')` runs `PushHandler`, which resolves the target via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` against `victim-org`'s stack - despite the request never being authenticated for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
