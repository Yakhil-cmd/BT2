### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, allowing a stack-restricted token to read deploy state of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
### Finding Description
`Shipit::Api::BaseController` establishes the binding that an `ApiClient` token authorizes only the stacks it is scoped to: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` is derived from that scoped relation via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` model instead of the scoped `stacks` collection inherited from `BaseController`: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, which only calls `ApiClient#check_permissions!`, a check against the client's permission list (`read:stack`, etc.) that is stack-agnostic: [3](#0-2) 

This means the authorization decision made when a client authenticates ("does this token permit `read:stack`?") is bound to a permission check, but the actual object acted upon ("which `stack_id` this token is restricted to") is never re-verified in `CCMenuController#show`, because it fetches `stack` from the unscoped `Stack.from_param!(params[:stack_id])` rather than from `stacks.from_param!(...)`.

The binding broken is: *stack a token authorizes* (`current_api_client.stack_id`, enforced elsewhere via `stacks`) ≠ *stack the token actually touches* (`Stack.from_param!(params[:stack_id])`, unscoped, in `CCMenuController`).

Test fixtures confirm the intended restriction model: the `here_come_the_walrus` API client is scoped to a single stack (`stack: shipit`) with `read:stack` permission, and the `StacksController` test suite explicitly verifies that such a scoped client "will only see that one stack" via the `index`/`show` actions that go through the scoped `stacks` helper. [4](#0-3) [5](#0-4) 

`CCMenuController` does not have or pass this same test coverage — it uses a wholly different `stack` resolution path that never consults `current_api_client.stack_id`, so a client scoped to stack A can pass any other stack's `stack_id` and receive that other stack's latest deploy/rollback status (CCTray XML with build state, timestamps, and status).

### Impact Explanation
This is an unauthenticated read of stack state across trust boundaries within the API-client model: a caller holding a token deliberately restricted to one stack (e.g., issued for a specific team's CCMenu dashboard) can enumerate and read the deploy status of every other stack in the Shipit instance, including stacks belonging to other teams/repositories that the token was never meant to see. This matches the "High - unauthenticated read of stack state, task streams or deploy output" impact category, because the scoping restriction (the core authorization guarantee of a scoped `ApiClient`) is completely bypassed for this one endpoint.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission (regardless of its `stack_id` scope) — such tokens are routinely created and distributed for tooling like CCMenu/CCTray dashboards, as shown by `CCMenuUrlController`, which mints one automatically for any logged-in user. [6](#0-5) 
Once obtained, hitting `GET /api/stacks/:stack_id/ccmenu` with an arbitrary `stack_id` and the scoped token is trivial — no privilege escalation or additional credentials needed beyond the token itself.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped collection, consistent with the rest of the API namespace:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This reuses `BaseController#stacks`, which already enforces `current_api_client.stack_id` scoping, closing the bypass while preserving the endpoint's existing behavior for globally-scoped tokens.

### Proof of Concept
1. As an admin, create two stacks, `stack_a` (repo `org/private-a`) and `stack_b` (repo `org/private-b`).
2. Create an `ApiClient` scoped to `stack_a` only (`stack_id: stack_a.id`, `permissions: ['read:stack']`) — e.g., via the `here_come_the_walrus`-style fixture pattern shown in `test/fixtures/shipit/api_clients.yml`.
3. Using this token's `authentication_token`, issue:
   `GET /api/stacks/:stack_b_id/ccmenu?token=<token>`
   (basic auth per `BaseController#authenticate_api_client`, or via the `token` param handled by `CCMenuController#authenticate_api_client`).
4. Observe a `200 OK` XML response describing `stack_b`'s latest deploy/rollback status, even though the token's `stack_id` is `stack_a.id` — because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(...)`, never checking `current_api_client.stack_id`.
