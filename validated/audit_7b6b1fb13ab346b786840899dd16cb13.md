### Title
Missing mutex lock in private payment chain validation/save allows concurrent processing of the same private output - ([File: private_payment.js])

### Summary
`privatePayment.validateAndSavePrivatePaymentChain` (called from `network.handleOnlinePrivatePayment` when the containing unit is already known, and from `wallet.js`'s `handlePrivatePaymentChains`) performs a "check duplicate, then insert" sequence for a privately-transferred output without ever acquiring a `mutex.lock(...)` guard, unlike equivalent state-changing flows elsewhere in ocore (e.g. `indivisible_asset.js`'s `getSavingCallbacks` explicitly takes `mutex.lock('handleJoint')`, and `validation.js`'s double-spend "ununique" path explicitly takes `mutex.lock(["private_write"])`) before mutating shared double-spend/asset state.

### Finding Description
`validateAndSavePrivatePaymentChain` in [1](#0-0)  reads the asset, opens its own DB connection (`db.takeConnectionFromPool`), starts a `BEGIN` transaction, runs a `SELECT ... FROM outputs` duplicate check, and if no duplicate is found calls `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)` which performs the `INSERT`s for `outputs`/`inputs` and duplicate-spend bookkeeping (see `divisible_asset.js` [2](#0-1)  and `indivisible_asset.js` [3](#0-2) ). This entire read-check-write sequence is unguarded by any `mutex.lock`.

Every entry point into this function is attacker/counterparty reachable without any coordinating lock:
- `network.handleOnlinePrivatePayment`, invoked directly on receipt of a `private_payment` message from a peer/private-payment counterparty, calls it directly when the unit is already known: [4](#0-3) .
- `handleSavedPrivatePayments` processes multiple queued private chains "in parallel" via `async.each`: [5](#0-4) .

In contrast, the codebase demonstrates elsewhere that this exact class of duplicate/double-spend bookkeeping requires serialization via mutex: `checkForDoublespends`'s `acceptDoublespends` explicitly wraps the "ununique" write for private assets in `mutex.lock(["private_write"], ...)` [6](#0-5) , and normal (non-private-payment-chain) composed private payments go through `getSavingCallbacks`, which explicitly takes `mutex.lock('handleJoint')` before validating/saving [7](#0-6) . `private_payment.js`'s `validateAndSavePrivatePaymentChain` has no analogous lock at all, breaking the pattern the rest of the codebase relies on for this class of operation, precisely analogous to the reported bug class (functions that mutate shared/critical state without the guard that sibling functions consistently use).

Because each call opens an independent connection/transaction rather than serializing through the shared `mutex` module, two private-payment messages referencing the same private output (e.g. the same head element sent twice by a malicious/careless private-payment counterparty, or received simultaneously from hub and directly from peer) can each pass the "duplicate" `SELECT` check before either has committed its `INSERT`, then both proceed to write. This is architecturally the same "missing lock guarding read-then-write critical section" issue the external report calls out as a reentrancy-style hazard.

### Impact Explanation
If two concurrent invocations both pass the duplicate check and proceed to write outputs/inputs for the same private chain element, this can lead to duplicate/conflicting bookkeeping of a private output's spend state (`is_spent`, `is_unique`) or duplicated insertion attempts racing against each other, undermining the invariant that a given private output is recorded and spent exactly once. This maps to the "double-spend of a stable output" / "node disagreement on validity" impact classes: a wallet could end up crediting the same private output twice, or two peers/devices holding the same private chain could reach different conclusions about whether it was already recorded, causing accounting inconsistency for private-asset balances.

### Likelihood Explanation
The DB backend in this codebase (SQLite via `db.takeConnectionFromPool`) does provide some serialization for concurrent writers, but at the JS/application level there is no explicit lock preventing two concurrent JS execution paths from both completing the `SELECT` duplicate check before either commits — the race window exists at the application logic layer regardless of underlying DB locking granularity, and the codebase's own use of `mutex.lock(["private_write"])` in `validation.js` for a related private-asset write path indicates awareness that DB transactional isolation alone was judged insufficient for this class of write. Triggering it only requires a private-payment counterparty (or a peer who received the chain) to deliver the same private element more than once, e.g. via direct P2P delivery plus hub delivery, or by replaying `private_payment` messages, which is within reach of a single unprivileged counterparty/peer as permitted by scope.

### Recommendation
Wrap the duplicate-check-and-save critical section in `private_payment.js`'s `validateAndSavePrivatePaymentChain` with a `mutex.lock` keyed on the private output identity (e.g. `[unit, message_index, output_index]` or the asset), mirroring the pattern already used in `indivisible_asset.js`'s `getSavingCallbacks` (`mutex.lock('handleJoint')`) and `validation.js`'s `mutex.lock(["private_write"])`, so that concurrent deliveries of the same private chain element are serialized rather than racing on independent DB connections.

### Proof of Concept
1. As a private-payment counterparty, send the same head private element (identical `unit`, `message_index`, `output_index`, `payload`) to the target wallet via two channels simultaneously — e.g. directly over P2P and again forwarded through the hub, or by opening two connections and sending the `private_payment` message twice in quick succession.
2. Each delivery, upon `joint_storage.checkIfNewUnit` returning `ifKnown`, invokes `privatePayment.validateAndSavePrivatePaymentChain` independently [4](#0-3) .
3. Both invocations take separate connections and both execute the duplicate-check `SELECT` in `private_payment.js` [8](#0-7)  before either has committed its `INSERT`s in `divisibleAsset`/`indivisibleAsset`'s `validateAndSavePrivatePaymentChain`.
4. Both proceed to insert/update `outputs`/`inputs` for the same private output, resulting in duplicate bookkeeping of the private payment rather than the intended idempotent "duplicate private payment" short-circuit.

function validateAndSavePrivatePaymentChain(arrPrivateElements, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("no priv elements array");
	var headElement = arrPrivateElements[0];
	if (!headElement.payload)
		return callbacks.ifError("no payload in head element");
	var asset = headElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in head element");
	if (!ValidationUtils.isNonnegativeInteger(headElement.message_index))
		return callbacks.ifError("no message index in head private element");
	
	var validateAndSave = function(){
		storage.readAsset(db, asset, null, function(err, objAsset){
			if (err)
				return callbacks.ifError(err);
			if (objAsset.is_private !== 1)
				return callbacks.ifError("asset is not private");
			if (!!objAsset.fixed_denominations !== !!headElement.payload.denomination)
				return callbacks.ifError("presence of denomination field doesn't match the asset type");
			if (!!objAsset.fixed_denominations !== ("output" in headElement))
				return callbacks.ifError("divisible asset must not have output field, indivisible must");
			db.takeConnectionFromPool(function(conn){
				conn.query("BEGIN", function(){
					var transaction_callbacks = {
						ifError: function(err){
							conn.query("ROLLBACK", function(){
								conn.release();
								callbacks.ifError(err);
							});
						},
						ifOk: function(){
							conn.query("COMMIT", function(){
								conn.release();
								callbacks.ifOk();
							});
						}
					};
					// check if duplicate
					var sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?";
					var params = [headElement.unit, asset, headElement.message_index];
					if (objAsset.fixed_denominations){
						if (!ValidationUtils.isNonnegativeInteger(headElement.output_index))
							return transaction_callbacks.ifError("no output index in head private element");
						sql += " AND output_index=?";
						params.push(headElement.output_index);
					}
					conn.query(
						sql, 
						params, 
						function(rows){
							if (rows.length > 1)
								throw Error("more than one output "+sql+' '+params.join(', '));
							if (rows.length > 0 && rows[0].address){ // we could have this output already but the address is still hidden
								const stored = rows[0];
								const payload = headElement.payload;
								let bDuplicate = false;
								if (objAsset.fixed_denominations){ // the row we selected is exactly headElement.output_index, filtered in sql above
									const claimed_output = payload.outputs?.[headElement.output_index];
									const revealed_output = headElement?.output;
									bDuplicate =
										ValidationUtils.isNonemptyObject(claimed_output)
										&& ValidationUtils.isNonemptyObject(revealed_output)
										&& stored.denomination === payload.denomination
										&& stored.amount === claimed_output.amount
										&& stored.address === revealed_output.address
										&& stored.blinding === revealed_output.blinding;
								}
								else // divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them
									bDuplicate = (payload.outputs || []).some(output => {
										return ValidationUtils.isNonemptyObject(output)
											&& stored.denomination === 1
											&& stored.amount === output.amount
											&& stored.address === output.address
											&& stored.blinding === output.blinding;
									});
								if (bDuplicate) {
									console.log("duplicate private payment "+params.join(', '));
									return transaction_callbacks.ifOk();
								}
							}
							var assetModule = objAsset.fixed_denominations ? indivisibleAsset : divisibleAsset;
							assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks);
						}
					);
				});
			});
		});
	};
	
	if (conf.bLight)
		findUnfinishedPastUnitsOfPrivateChains([arrPrivateElements], false, function(arrUnfinishedUnits){
			(arrUnfinishedUnits.length > 0) ? callbacks.ifWaitingForChain() : validateAndSave();
		});
	else
		validateAndSave();
}
