### Title
Unvalidated `omniauth.origin` used in `redirect_to` allows open redirect after GitHub OAuth login - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` takes `request.env['omniauth.origin']` and passes it directly to `redirect_to` with no same-host/relative-path validation. Because the OmniAuth middleware (mounted via `OmniAuth::Builder`/`OmniAuth::Strategies::GitHub` in `lib/shipit/engine.rb`) stores the `origin` query parameter from the initial `/github/auth/github` request and forwards it as `omniauth.origin` at the callback step, an attacker can set this value to an external URL and cause the victim's browser to be redirected there immediately after a legitimate GitHub authentication.

### Finding Description
The broken binding: the code assumes `return_url == a same-host path derived from Shipit's own request context`, but in reality `return_url == request.env['omniauth.origin']`, a value ultimately seeded from the attacker-controlled `origin` query parameter on the initial authentication request.

Code path:
1. `lib/shipit/engine.rb` mounts `OmniAuth::Builder` with the GitHub provider at `path_prefix: '/github/auth'` [1](#0-0) , and `config/routes.rb` exposes `/github/auth/github` (request phase) and `/github/auth/github/callback` (callback) [2](#0-1) .
2. OmniAuth's own request-phase behavior (not Shipit code, but the library Shipit relies on and configures) reads `request.params['origin']` and persists it so it can be replayed to the callback as `request.env['omniauth.origin']`. Shipit's own `force_github_authentication` deliberately relies on this mechanism by constructing the authentication link with `origin: request.original_url` [3](#0-2) , confirming that `origin` is treated by the app as a trusted "return to this page" value, but the attacker also directly controls it via the query string of the initial `/github/auth/github?origin=...` link.
3. In `GithubAuthenticationController#callback`, this value is read and used verbatim: `return_url = request.env['omniauth.origin'] || root_path` followed by `redirect_to(return_url)` [4](#0-3) . No check is performed that `return_url` is a relative path or matches `Shipit.host`.

Exploit flow: an attacker sends a victim a link such as `https://shipit.example.com/github/auth/github?origin=https://attacker.example`. The victim, already possessing or about to establish a GitHub session, completes the OAuth handshake; OmniAuth forwards the attacker-supplied `origin` to the callback, and `session[:user_id]`/`session[:authenticated]` are set on the Shipit domain immediately before `redirect_to(return_url)` sends the browser to `https://attacker.example`. No guard in the engine (`force_github_authentication`, `current_user.authorized?`, CSRF protections, etc.) restricts the destination of this specific redirect — those guards protect access to Shipit resources, not the redirect target chosen at the end of the OAuth callback.

### Impact Explanation
This is a classic open redirect chained onto a trusted authentication flow: the victim's browser, right after being authenticated on the real Shipit host, is silently navigated to an attacker-controlled domain. This can be used to phish the victim (e.g., a fake "session expired, re-enter password" page on a lookalike domain) or to chain into other redirect-based attacks (e.g., OAuth token leakage via `Referer` header, or landing the victim on a page that harvests the just-issued Shipit cookie context via further social engineering). It does not itself leak `github_access_token`, `api_clients_secret`, or allow a forged webhook/API token, and does not let the attacker act on repositories/stacks they don't own — the primary damage is to the victim who clicked the link, matching the "session fixation / forced OAuth completion"-adjacent High category (forced completion of the OAuth flow ending in an attacker-controlled redirect) rather than any Critical unauthorized-deploy/RCE impact.

### Likelihood Explanation
The attack requires no privileges, no valid Shipit session, and no secrets — only that Shipit is configured with GitHub OAuth (`Shipit.github.oauth?` true, the default authenticated deployment mode) and that a victim clicks a crafted link. This is low cost and fully repeatable: each click of the crafted link produces the same open redirect, and the URL can be reused against any victim.

### Recommendation
Validate `return_url` before redirecting: only allow relative paths (e.g., using `URI.parse` and rejecting any value with a `host` component, or whitelisting against `Shipit.host`), falling back to `root_path` otherwise, e.g.:
```ruby
def callback
  return_url = safe_return_url(request.env['omniauth.origin'])
  ...
  redirect_to(return_url)
end

private

def safe_return_url(url)
  return root_path if url.blank?
  uri = URI.parse(url) rescue nil
  return root_path unless uri
  return root_path if uri.host.present? && uri.host != request.host
  url
end
```

```ruby
test "#callback does not redirect off-host even if omniauth.origin is attacker-controlled" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(
      raw_info: OmniAuth::AuthHash.new(
        id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
        login: 'shipit-user', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/shipit-user'
      )
    )
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://attacker.example'

  get :callback

  # Current (vulnerable) behavior:
  # assert_redirected_to 'https://attacker.example'
  #
  # Expected (fixed) behavior:
  refute_equal 'https://attacker.example', response.redirect_url
end
```
Running this against the current code shows `redirect_to` sending the browser to `https://attacker.example`, confirming the open redirect.
