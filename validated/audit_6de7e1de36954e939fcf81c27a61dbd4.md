### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a status webhook from any repository flip CI state on commits belonging to any other stack, including auto-provisioned review stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by bare SHA equality with `Commit.where(sha: params.sha)`, with no repository/stack filter, so a valid webhook from repository A can mutate the CI status of a commit row that actually belongs to repository B's stack whenever both rows share the same SHA (a routine outcome of forking, shared history, or an attacker deliberately pushing/copying the same commit object into their own repo). `verify_signature` in `Shipit::WebhooksController` only authenticates that the payload's declared `repository.owner.login` matches the secret for that org - it never re-checks that the `sha` inside the payload is actually reachable from that same repository - so the forged cross-repo write is not caught anywhere downstream.

### Finding Description
The broken binding is: **for a `status` webhook authenticated for `repository_owner = O`, every `Commit` row updated by that webhook must satisfy `commit.stack.repository.owner == O` (and, more specifically, `commit.stack.repository == payload.repository`)**. In the actual code, this invariant is never enforced.

Path:
1. `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses `params` and dispatches to handlers for the event type. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the attacker-controlled payload (`params.dig('repository','owner','login')`). This proves the request came from a GitHub app/webhook belonging to *some* org the attacker controls (their own repo), not that the `sha` field belongs to that repo.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This is a global, unscoped lookup across the entire `commits` table - not filtered by `stack_id`, `repository_id`, or any relation to the authenticated payload's repository.
3. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes a new `Status` row via `add_status`, which recomputes `status`, emits `Hook.emit(:commit_status, ...)` / `:deployable_status`, and calls `stack.schedule_merges` (`app/models/shipit/commit.rb:379-384`) if the new status is pending or success.
4. If the victim stack has `review_stacks_enabled: true, allow_all: true` (checked in `app/models/shipit/repository.rb` and the PR handlers `opened_handler.rb`/`reopened_handler.rb`/`labeled_handler.rb`), any external PR auto-provisions a review stack that runs `shipit.yml`. Because review-stack commits inherit their SHA from the underlying GitHub commit, an attacker who can produce a commit object with an identical SHA to one tracked in the victim's review stack (trivial: fork or clone the victim repo, or replay the exact same git commit into a repo the attacker owns) can send a `status` webhook signed with their own repo's webhook secret for that shared SHA and context `release/gate`. Because `StatusHandler` performs no repository scoping, the write lands on the victim's `Commit` row and can flip its `blocking?`/`success?` state, unblocking `deployable?` (`app/models/shipit/commit.rb:227-229`) and triggering `schedule_continuous_delivery` → `ContinuousDeliveryJob`, or blocking a required deploy.

None of the listed guards intervene: `verify_signature` authenticates the *sender's own* org, not the SHA-to-repo binding; `drop_unhandled_event` only filters event *type*; the `ExplicitParameters` schema (`params do requires :sha ...`) only validates the shape of `sha`/`state`/`context`, not ownership; there is no `require_permission!`/`User#authorized?` call anywhere in the webhook path since it is intentionally unauthenticated (webhooks are asynchronous GitHub calls, authenticated only via HMAC per-org, not per-repo/per-SHA).

### Impact Explanation
A payload from repository A can flip the CI/deploy-gating status of a commit that belongs to repository B's stack - "a payload for one repository mutating another's stack/commit" - matching the Critical impact category (unauthorized deploy or block on a stack the attacker does not own or administer). Because auto-provisioned review stacks (`review_stacks_enabled: true, allow_all: true`) execute `shipit.yml` on ship, forcing a fake "success" status for `release/gate` can cause the review stack to proceed to deploy/execute arbitrary shipit tasks defined in that repo's `shipit.yml`, which is the RCE-adjacent path referenced by the question. This is repeatable against any repository/stack pair that ever shares a commit SHA with an attacker-controlled repository, and is not limited to a single victim - any tenant configured with `review_stacks_enabled`/`allow_all` and a `release/gate` required status is exposed.

### Likelihood Explanation
Preconditions: the attacker needs (a) some GitHub repository whose webhook is registered with the Shipit instance (any repo Shipit is configured to receive events for, or any org in `Shipit.github(organization:)` config - typically any repo Shipit is deployed against, which is not a high bar for organizations running Shipit for many repos), and (b) a commit SHA shared with the victim stack's tracked commit (achievable by forking the victim repo, since forks preserve commit SHAs, or by cherry-picking/copying the exact commit object). No Shipit session, API token, or GitHub App private key is required - only the ability to make GitHub emit (or the attacker directly POSTs) a `status` webhook, which GitHub will do automatically for any commit pushed to a repo the attacker controls once a third-party CI/status check runs, or the attacker can call `POST /webhooks` directly if they know/derive a valid signature for their own org's secret (which they legitimately have via their own repo's webhook settings). This is a low-cost, repeatable attack limited only by the requirement to align a shared SHA with a targeted stack's tracked commit.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other SHA-keyed handler) to commits whose `stack.repository` matches the authenticated payload's `repository.full_name`/`owner`, e.g. join through `Stack`/`Repository` and filter by `full_name` derived from `params.repository` before updating any `Commit`, rather than relying on bare `sha` uniqueness across the whole table.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, new):
1. Create `repository_a` (`full_name: "attacker/repo"`) and `repository_b` (`full_name: "victim/repo"`), each with its own `Stack` (`stack_b` has `review_stacks_enabled: true`, and repository allow_all true, and `shipit.yml` requiring `release/gate`).
2. Create a `Commit` with `sha: "deadbeef" * 5`, `stack: stack_b` (simulating the victim's review-stack commit).
3. Build a `StatusHandler` payload: `{ sha: "<same sha>", context: "release/gate", state: "success", repository: { owner: { login: "attacker" } } }` and call `StatusHandler.new.process` directly (bypassing controller-level org auth, since that only checks org, not repo/commit ownership).
4. Assert `commit_b.reload.status.success?` is `true` and `commit_b.deployable?` is `true`/blocked? changed, proving repository B's commit state was altered by a payload that only authenticated for owner "attacker", i.e. assert:
   - Before: `commit_b.status.unknown?` (or whatever baseline) == true, `repository_a.full_name != repository_b.full_name`.
   - After: `commit_b.status.state == "success"` even though the authenticated `repository_owner` from the payload (`"attacker"`) does not equal `commit_b.stack.repository.owner` (`"victim"`), demonstrating the broken binding.
