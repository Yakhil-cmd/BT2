### Title
Bridge ERC721 Delivery Uses `_mint`/`transferFrom` Instead of `_safeMint`/`safeTransferFrom`, Permanently Locking Bridged NFTs in Non-Receiver Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` delivers bridged ERC721 tokens to the user-supplied `_to` address without verifying that the recipient can handle ERC721 tokens. In mint-burn mode it calls `mintWithTokenURI` → `_mint`; in lock-unlock mode it calls `transferFrom`. Neither path invokes `_checkOnERC721Received`. If `_to` is a contract that does not implement `IERC721Receiver`, the NFT is minted or transferred into it and is permanently irrecoverable.

---

### Finding Description

`handleERC721Transfer` in `BridgeTransferERC721.sol` has two delivery branches:

**Mint-burn mode** (line 67):
```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```
`mintWithTokenURI` calls `_mint` directly:
```solidity
// ERC721MetadataMintable.sol line 19-23
function mintWithTokenURI(address to, uint256 tokenId, string memory tokenURI) public onlyMinter returns (bool) {
    _mint(to, tokenId);          // ← no safe-check
    _setTokenURI(tokenId, tokenURI);
    return true;
}
```
`_mint` in `ERC721.sol` (lines 210-218) only sets `_tokenOwner` and emits `Transfer`; it never calls `_checkOnERC721Received`.

**Lock-unlock mode** (line 69):
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```
`transferFrom` (ERC721.sol lines 142-147) calls `_transferFrom` with no receiver check. The safe variant `safeTransferFrom` (lines 176-179) is the one that calls `_checkOnERC721Received` and reverts if the recipient contract does not return the magic value.

The `_to` address originates from the user's original `requestERC721Transfer` or `onERC721Received` call on the source chain. Any address — including a contract — can be specified. Bridge operators faithfully relay it to `handleERC721Transfer` on the destination chain with no additional validation.

---

### Impact Explanation

A bridged ERC721 NFT is permanently locked inside a contract that cannot handle it. The token exists on-chain (ownership record is set), but no function on the recipient contract can move it, and the bridge nonce is consumed and marked handled, so the transfer cannot be replayed. The asset is irreversibly lost from the user's perspective. This matches the allowed impact gate: *unauthorized burn / permanent loss of bridged assets*.

---

### Likelihood Explanation

Low-to-medium. The user must specify a contract address as `_to` that does not implement `IERC721Receiver`. This is realistic: multisig wallets (Gnosis Safe without ERC721 module), DAO treasury contracts, and many DeFi contracts do not implement the receiver interface. No privileged access is required; any user initiating a bridge transfer can trigger this.

---

### Recommendation

1. Replace `mintWithTokenURI` (which calls `_mint`) with a `_safeMint`-based variant that calls `_checkOnERC721Received` after minting.
2. Replace `transferFrom(address(this), _to, _tokenId)` with `safeTransferFrom(address(this), _to, _tokenId)`.
3. Add a `nonReentrant` modifier to `handleERC721Transfer` (as already done on `handleKLAYTransfer`) because `_safeMint` and `safeTransferFrom` make an external call to the recipient, opening a reentrancy vector.

---

### Proof of Concept

1. Deploy a contract `NoReceiver` on the destination chain that does **not** implement `IERC721Receiver`.
2. On the source chain, call:
   ```solidity
   bridge.requestERC721Transfer(nftAddress, address(noReceiver), tokenId, "");
   ```
3. Bridge operators observe the `RequestValueTransfer` event and call on the destination bridge:
   ```solidity
   bridge.handleERC721Transfer(txHash, from, address(noReceiver), nftAddress, tokenId, nonce, blockNum, uri, "");
   ```
4. In mint-burn mode: `mintWithTokenURI(address(noReceiver), tokenId, uri)` succeeds silently — `_mint` sets `_tokenOwner[tokenId] = address(noReceiver)` and emits `Transfer`. No revert occurs.
5. In lock-unlock mode: `transferFrom(bridge, address(noReceiver), tokenId)` succeeds silently — `_transferFrom` sets `_tokenOwner[tokenId] = address(noReceiver)` and emits `Transfer`. No revert occurs.
6. `tokenId` is now owned by `NoReceiver`. `NoReceiver` has no function to call `transferFrom` or `safeTransferFrom`, so the NFT is permanently stuck.
7. The bridge's `handleNoncesToBlockNums[nonce]` is written and `_updateHandleNonce` is called — the transfer is marked complete and cannot be retried.

    function _mint(address to, uint256 tokenId) internal {
        require(to != address(0), "ERC721: mint to the zero address");
        require(!_exists(tokenId), "ERC721: token already minted");

        _tokenOwner[tokenId] = to;
        _ownedTokensCount[to].increment();

        emit Transfer(address(0), to, tokenId);
    }
