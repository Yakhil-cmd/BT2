Unsigned webhook accepted when `github.webhook_secret` is unset, allowing forged `membership` payloads to grant Shipit team authorization - ([File: lib/shipit/github_app.rb])

### Summary
`Shipit::GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank, which is the engine's own documented default configuration. `WebhooksController#verify_signature` relies solely on this method to gate acceptance of any webhook claiming a given `repository_owner`/`organization`, so with no secret configured, an unauthenticated internet request can drive `MembershipHandler#process` with an entirely attacker-controlled payload.

### Finding Description
Binding claimed: `Shipit.github(organization: X).verify_webhook_signature(sig, body) == true` should imply the request body was HMAC-signed by GitHub using organization `X`'s `webhook_secret`. This binding is broken when `webhook_secret` is unset for `X`:

```ruby
# lib/shipit/github_app.rb
def verify_webhook_signature(signature, message)
  return true unless webhook_secret   # <-- unconditional bypass
  ...
end
``` [1](#0-0) 

`WebhooksController#verify_signature` uses only this return value to gate the request:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
``` [2](#0-1) 

`repository_owner` is taken straight from the attacker-controlled JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`) [3](#0-2) , so the attacker chooses which configured organization's (secret-less) `GitHubApp` instance is used for verification.

If verification passes, `create` parses the raw body and dispatches to registered handlers for the event, with no other authentication check in between [4](#0-3) . For `X-Github-Event: membership`, this is `MembershipHandler#process`, which creates/finds a `Team` by attacker-supplied `team.id` and adds an attacker-supplied `member.login` to it: 
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
``` [5](#0-4) 

This configuration (`webhook_secret` unset) is the engine's own shipped/documented default, appearing as `webhook_secret: # nil` in `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets.yml`, and `test/dummy/config/secrets_double_github_app.yml` [6](#0-5) , and is explicitly called "optional" in `docs/setup.md`: "Webhook secret (optional): Fill it with some randomly generated string" [7](#0-6) .

No other guard intervenes: `drop_unhandled_event` only checks the event name is registered [8](#0-7) , and `MembershipHandler` has no additional provenance check beyond the `ExplicitParameters` schema, which only validates shape, not origin [9](#0-8) .

### Impact Explanation
An attacker who knows (or guesses) the name of any Shipit-configured GitHub organization that lacks a `webhook_secret` can add themselves (or any GitHub login) to any `Shipit.github_teams`-referenced team by POSTing a forged `membership` webhook naming that organization and an arbitrary `team.id`. Since `Shipit.github_teams` gates OAuth authorization into the app (per `lib/shipit.rb` and `app/models/shipit/user.rb`), this is a direct escalation into privileged Shipit access — an unauthenticated attacker can grant themselves membership in a team that controls deploy/merge authorization, without ever owning a GitHub org or possessing any secret. This is repeatable against every organization configured without a `webhook_secret`, and each request is independent (no rate limiting relevant here). This matches the "escalation into `Shipit.github_teams` authorization" High-severity category, and depending on what the granted team unlocks (e.g., deploy/merge permissions), could rise to Critical (unauthorized deploy/merge via forged authorization).

### Likelihood Explanation
Preconditions: at least one Shipit-configured organization has no `webhook_secret` set — which is the engine's shipped default and requires no operator error beyond following the documented "optional" field. Attacker cost is a single unauthenticated HTTP POST to `/webhooks` with `X-Github-Event: membership`, no `X-Hub-Signature` header, and a JSON body naming the target organization, a team id (attacker can enumerate/guess or use `Team.find_or_create_by!` behavior to create a new team from scratch with any `github_id`), and their own GitHub login. This is highly feasible and fully repeatable.

### Recommendation
Do not treat a missing `webhook_secret` as "trust all requests." Instead: (1) require `webhook_secret` to be present for any organization that has webhook-driven authorization handlers registered (at minimum `membership`), failing closed (reject with 422) when absent, or (2) remove the `return true unless webhook_secret` short-circuit entirely and require an explicit opt-in flag (e.g., `Shipit.insecure_webhooks_allowed?`) with a prominent warning, defaulting to fail-closed. Additionally, consider validating that any `Team` referenced by a `membership` event actually corresponds to a `github_id`/organization pairing already known to Shipit rather than allowing arbitrary team creation from unauthenticated payloads.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "membership webhook accepted without signature when webhook_secret is unset" do
  Shipit.stubs(:github).with(organization: 'shopify').returns(
    Shipit::GitHubApp.new('shopify', { app_id: 42, installation_id: 43, webhook_secret: nil })
  )

  @request.headers['X-Github-Event'] = 'membership'
  # No X-Hub-Signature header set at all

  assert_difference -> { Shipit::Membership.count }, 1 do
    post :create, body: {
      action: 'added',
      team: { id: 999_999, name: 'Evil Team', slug: 'evil-team', url: 'http://example.com' },
      organization: { login: 'shopify' },
      member: { login: 'attacker' },
      repository: { owner: { login: 'shopify' } }
    }.to_json, as: :json
    assert_response :ok
  end
end
```
Both sides of the binding: expected — `verify_webhook_signature(nil, body)` should be `false` (unsigned request), actual — it returns `true` because `webhook_secret` is `nil`; the divergence directly produces an unauthorized `Membership` row and, if the team is in `Shipit.github_teams`, an authorization escalation for `attacker`.
