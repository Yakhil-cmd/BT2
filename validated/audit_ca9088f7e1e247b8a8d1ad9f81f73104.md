### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field — cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on a field taken from the *body itself*: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Shipit supports configuring multiple independent GitHub Apps, each with its own `webhook_secret`, keyed by organization (`config/secrets.development.shopify.yml` shows two separate orgs each with their own `webhook_secret`) [3](#0-2) . Any organization admin that has installed their own Shipit-connected GitHub App legitimately knows their own `webhook_secret` and can therefore produce a validly-signed webhook body for *that* organization.

However, once the signature check passes, the event handlers never re-check that the signing organization matches the repository the payload claims to act on. Every handler resolves its target purely from `repository.full_name` inside the (attacker-fully-controlled) JSON body, with no scoping to `repository_owner`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

The same pattern repeats in `PullRequest::OpenedHandler#repository`, which does `Shipit::Repository.from_github_repo_name(params.repository.full_name)` with no relation whatsoever to `repository_owner`: [5](#0-4) .

Because `Repository.from_github_repo_name` is a global lookup across *all* organizations tracked by the Shipit instance (not scoped to the org whose secret validated the request), an operator who owns/administers organization **A** (and thus legitimately possesses A's `webhook_secret`) can craft a webhook whose `repository.owner.login` = `"org-A"` (used only to pick the verification key) while `repository.full_name` = `"org-B/victim-repo"` (used to pick the actual DB `Repository`/`Stack` that the handler acts on). The HMAC signature will validate because it is computed by the attacker themselves over the entire raw body using A's own secret — the mismatch between the "authenticated organization" and "the repository being written" is never checked.

This is a direct analog of the ERC721Checkpointable bug class: the verified signature covers the *bytes*, but the *authorization decision* (which secret validates, i.e., which org is trusted) is bound to one field (`repository.owner.login`) while the *effect* (which Stack/Repository record is mutated) is driven by an entirely different, attacker-controlled field (`repository.full_name`) that is never checked for consistency with the authenticated identity.

### Impact Explanation
An attacker who administers any one organization configured on a shared multi-tenant Shipit instance (a normal, unprivileged, low-trust position — they only need to know their *own* org's webhook secret, not any credential belonging to the victim organization) can forge webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`) that are processed as if they originated from a completely different organization's repository. Depending on handler, this enables: creating/closing/labeling PRs and provisioning review stacks on a victim's repository (`PullRequest::OpenedHandler`), injecting commit statuses affecting deploy gating (`StatusHandler`), or triggering `RefreshCheckRunsJob`/branch tracking updates (`CheckSuiteHandler`, `PushHandler`) for stacks that belong to a repository the attacker has no legitimate relationship with. This is a cross-repository/cross-organization write performed without ever crossing the intended organization-scoped trust boundary — matching the "cross-repository writes" and "unauthorized deploy" impact classes.

### Likelihood Explanation
Requires only that the Shipit deployment configures more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml`) and that the attacker administers one of them. No access to the victim organization's secret, a Shipit session, or an `ApiClient` token is needed. This is a realistic scenario for any shared/multi-tenant Shipit installation.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`, enforce that the resolved `Repository`'s owner matches the `repository_owner` (or `organization.login`) that was used to select the verification secret, e.g. reject the event if `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner != repository_owner`. This restores the equality between "the organization whose secret authenticated the request" and "the repository being written."

### Proof of Concept
1. Configure Shipit with two organizations, `org-A` and `org-B`, each with their own GitHub App / `webhook_secret` (per `docs/setup.md` multi-org example).
2. `org-B` has a tracked repository `org-B/victim-repo` with an existing Stack.
3. Attacker, who administers `org-A`'s GitHub App and thus knows `org-A`'s `webhook_secret`, crafts a `pull_request` webhook JSON body:
   ```json
   {
     "action": "opened",
     "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" },
     "pull_request": { ... },
     "sender": { "login": "attacker" }
   }
   ```
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC(org-A_webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-A")` and verifies successfully (attacker signed with the correct secret for the org named in the body).
6. `PullRequest::OpenedHandler` resolves `Shipit::Repository.from_github_repo_name("org-B/victim-repo")` and provisions/acts on `org-B`'s stack, entirely bypassing any check that `org-A` is authorized to act on `org-B`'s repository.
