### Title
Webhook signature verification is keyed on attacker-supplied `repository.owner.login` while handlers act on a different attacker-supplied `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App organization's `webhook_secret` to validate the HMAC against using a value read directly from the unauthenticated, unverified JSON body (`repository.owner.login` / `organization.login`). The `X-Hub-Signature` is only checked against that one organization's secret. Once verification "passes", the *entire* raw payload (including a possibly different `repository.full_name`) is dispatched unmodified to event handlers, which look up the target `Stack`/`Repository` purely from `payload.dig('repository', 'full_name')`, with no cross-check that this repository belongs to the organization whose secret validated the signature.

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.*.yml` supports a `github: { orgA: {...}, orgB: {...} }` schema, each with its own `webhook_secret`), the trust binding that must hold is:

`organization whose secret validated X-Hub-Signature == organization that owns the repository the handlers act on`

The controller breaks this equality: [1](#0-0) 

`repository_owner` is derived from the raw, unverified body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization `GitHubApp`/secret via `github_app_config`: [3](#0-2) 

The signature is then verified only against that chosen secret: [4](#0-3) 

If verification passes, `create` blindly forwards the entire raw JSON body — not just the `repository_owner`-scoped part — to all registered handlers for the event: [5](#0-4) 

Handlers resolve the target stack from a completely separate field, `repository.full_name`, with no re-validation against the organization that was authenticated: [6](#0-5) 

`PushHandler`, for example, uses this to sync/enqueue jobs for every non-archived stack of the resolved repository: [7](#0-6) 

Because `repository.owner.login` (used to select the secret) and `repository.full_name` (used to pick the target stack) are two independent fields inside the same unauthenticated JSON body, an attacker who legitimately controls (or knows) the `webhook_secret` for *one* organization configured on the Shipit instance (e.g., their own org's GitHub App, which they set up and installed) can:

1. Set `repository.owner.login` = `their-org` so `verify_signature` picks `their-org`'s `GitHubApp` and validates the HMAC they computed with their known secret.
2. Set `repository.full_name` = `victim-org/some-repo` (or omit `owner.login` and instead supply an `organization.login` matching their org while `repository.full_name` points elsewhere) so the dispatched handler operates on a stack that belongs to an entirely different, victim organization tracked by the same Shipit instance.
3. Craft `push`, `status`, or `check_suite` payloads that get accepted as if it came from GitHub for the victim repository.

### Impact Explanation
This crosses an authentication/authorization boundary: an attacker with only one organization's webhook secret can forge webhook deliveries attributed to a completely different, victim organization's repositories hosted on the same Shipit instance. Concrete effects include:
- `push` events forging `expected_head_sha` and triggering `GithubSyncJob`/`sync_github` against a victim `Stack`, letting an attacker steer which commit Shipit believes is the branch head.
- `status` events injecting fake commit statuses (`Commit#create_status_from_github!`) for arbitrary commit SHAs, which can be used to mark otherwise-undeployable commits as CI-green, enabling an unauthorized deploy to proceed through the normal deploy flow once merged with `require_ci`/deployability checks.
- `check_suite` events triggering `RefreshCheckRunsJob` against the wrong stack.

This maps to the report's "unprivileged-attacker" analog: an organization that authenticated (via HMAC) versus the repository that is actually written to/acted upon differ, with no binding enforced between the two — directly enabling deploy-path manipulation (unauthorized deploy) rather than merely a best-practice nit.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (the per-org `github:` config schema shown in `docs/setup.md` and `config/secrets.development.shopify.yml`), and requires the attacker to legitimately control one org's webhook secret while targeting another org tracked by the same instance — a realistic scenario for shared/multi-tenant Shipit deployments (e.g., a company running one Shipit instance across multiple internal or partner GitHub orgs). No GitHub App private key, `GITHUB_TOKEN`, or Shipit session/API token is needed; the attacker only needs a webhook secret they legitimately possess for their own org.

### Recommendation
After verifying the signature, cross-check that `repository.owner.login` (the org whose secret validated the request) matches the owner embedded in `repository.full_name` before dispatching to handlers, and reject the payload otherwise. Alternatively, scope handler dispatch/repository lookups to only the verified organization rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known to the attacker, who is a legitimate admin of that org's GitHub App) and `victim-org` (tracks a stack the attacker does not control).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefcafebabe0000000000000000000000",
  "repository": {
    "owner": {"login": "attacker-org"},
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac using attacker-org's known webhook_secret over the raw body>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), verifies the HMAC successfully against the attacker's own secret [1](#0-0) , and `create` proceeds.
5. `PushHandler#process` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` [6](#0-5)  and enqueues `sync_github(expected_head_sha: 'deadbeef...')` against `victim-org`'s stack, despite the attacker never holding `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
