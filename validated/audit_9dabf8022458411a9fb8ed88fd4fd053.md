### Title
Webhook signature bypass for organizations without a `webhook_secret` allows cross-organization commit-status and push forgery leading to unauthorized deploys/merges - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config to verify a webhook against using the attacker-controlled `repository.owner.login` (or `organization.login`) field, but the handlers that actually act on the payload use a *different*, independently attacker-controlled field (`repository.full_name`, or bare `sha` for status events) that is never tied back to the organization that "authenticated" the request. Combined with the fact that `GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization, any Shipit deployment that has even one configured organization without a `webhook_secret` (a supported, documented configuration in this codebase) allows a fully unauthenticated attacker to forge webhook events targeting any *other* organization's repositories/stacks.

### Finding Description
The org used to select the verification secret and the resource actually mutated are bound by two independent, unverified fields:

- `repository_owner`, used to pick the `GithubApp` instance whose secret is checked: [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` bypasses verification entirely when the resolved app has a blank secret: [3](#0-2) 

- The engine's own test fixtures demonstrate that a configured organization with `webhook_secret: # nil` is a valid/expected configuration shape (not a misconfiguration the engine rejects): [4](#0-3) 

- Once "verified" (or bypassed), the handler dispatch resolves the *target* repository purely from `repository.full_name`, completely independent of `repository_owner`: [5](#0-4) 

- `StatusHandler`, used to set commit CI statuses, doesn't even scope by repository — it matches commits by bare `sha` across the *entire* Shipit instance: [6](#0-5) 

**Binding broken:** `organization_authenticated (repository.owner.login) == organization_that_owns_the_acted_upon_resource (repository.full_name / commit.sha)`. Before the attack, this equality normally holds because GitHub's HMAC signs the entire raw payload (including `full_name`/`sha`), so a forged mismatch would fail verification. After the attack (targeting an org with a blank `webhook_secret`), `verify_webhook_signature` short-circuits to `true` regardless of the actual signature header, so the equality is never checked at all — the attacker can freely set `repository.owner.login` to the unsecured org while setting `repository.full_name` (push events) or `sha` (status events) to reference any other tracked repository/commit in the instance.

### Impact Explanation
An attacker who knows (or guesses) the login of any org configured in the Shipit instance without a `webhook_secret` can:
- POST a forged `status` webhook event with an arbitrary `sha` belonging to a commit in a completely different organization's stack, setting `state: success` on required/blocking CI statuses (`Commit#create_status_from_github!`), which can unblock the merge queue or deploy safety checks for that unrelated stack — leading to an **unauthorized merge or deploy**.
- POST a forged `push` webhook event with an arbitrary `repository.full_name`, triggering `stack.sync_github` for that repository/stack, influencing deploy state for a repo the attacker has no legitimate relationship to.

This matches the "unauthorized deploy, rollback or merge" impact tier.

### Likelihood Explanation
Exploitability depends entirely on the operator's multi-organization configuration containing at least one org without a `webhook_secret` — which the engine's own fixtures show as a valid, non-error configuration state (`webhook_secret: # nil`), and which the code path (`verify_webhook_signature`) explicitly treats as "always verified" rather than rejecting. No GitHub App private key, `ApiClient` token, or repository write access is required — only knowledge of the unsecured organization's login name, which is often public. The engine does nothing to scope handler side effects to the authenticating organization, so this is a structural flaw in the engine rather than a misconfiguration of the host app.

### Recommendation
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; either require a webhook secret for every configured GitHub App or explicitly restrict what an unsecured org's webhooks are allowed to affect.
- Scope every handler's side effects to the organization that was actually verified: `Handler#stacks` and `StatusHandler#process` should cross-check that `repository.full_name`'s owner (or the commit's stack's repository owner) matches `repository_owner` used during signature verification, rejecting mismatches.
- Avoid resolving commits by bare `sha` alone in `StatusHandler`; scope the lookup to the stack/repository identified in the same payload and verified organization.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgA` (has a `webhook_secret`) and `OrgB` (no `webhook_secret`, as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any garbage value), body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/anything" },
  "sha": "<sha of a commit belonging to OrgA/some-protected-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `verify_webhook_signature` returns `true` unconditionally because `OrgB`'s `webhook_secret` is blank.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the commit belonging to `OrgA`'s stack, creating a fabricated passing status on it — despite the request never being validated against `OrgA`'s secret and despite `OrgA` never authorizing this event.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
