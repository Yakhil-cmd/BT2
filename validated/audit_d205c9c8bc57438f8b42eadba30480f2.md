### Title
Webhook signature verification selects its HMAC secret from an unverified payload field, letting an attacker route forged events through any organization with no `webhook_secret` configured - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp`/`webhook_secret` to validate a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unauthenticated JSON body, and then calls `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally when that organization's `webhook_secret` is blank/nil. The organization value used to *select the verifier* is never bound to, or cross-checked against, the organization/repository the resulting event handlers subsequently act on.

### Finding Description
`verify_signature` resolves the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is computed purely from the raw, unverified request body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`). Whatever organization it resolves to determines which `GitHubApp` instance's `webhook_secret` is used to check `X-Hub-Signature`: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` when the resolved organization has **no configured `webhook_secret`** (`return true unless webhook_secret`). Shipit explicitly supports mixed configurations where some organizations have a `webhook_secret` and others do not, as shown in the shipped multi-org secrets template: [4](#0-3) 

The engine treats "the organization whose key authenticated this HTTP request" and "the organization/repository the event body claims to describe" as the same value, but they are two independently attacker-controlled JSON fields in the same forged POST body — the code never re-derives or compares them after verification. An attacker who knows (or guesses) that at least one configured organization has `webhook_secret` unset can set `repository.owner.login`/`organization.login` to that unprotected org so `verify_signature` trivially passes, while the rest of the JSON body (team id, membership action, push ref/sha, status state, etc.) is fully attacker-supplied and dispatched unchanged to the registered handlers: [5](#0-4) 

For the `membership` event, the handler mutates `Team`/`Membership` records directly from these attacker-controlled fields, as exercised by the controller test which appends/removes memberships and creates teams/users solely from body content: [6](#0-5) 

Because `Shipit.github_teams` membership is exactly what `User#authorized?` checks to grant access to the whole engine, forging a `membership` "added" event lets an attacker splice an arbitrary GitHub login into a team that is trusted for authorization: [7](#0-6) [8](#0-7) 

### Impact Explanation
This breaks the binding "organization that authenticated the webhook request == organization/repository the request is trusted to mutate." A successful forgery can inject arbitrary `Membership` records tying a GitHub identity to a `Team` used by `Shipit.github_teams`, escalating an unprivileged GitHub user into the set authorized to log into and operate the Shipit instance — an explicit High-impact category ("escalation into `Shipit.github_teams` authorization"). The same gap also lets an attacker forge `push`/`status`/`check_suite` events for repositories unrelated to the unprotected organization used purely to pass the signature check, since handlers key off body fields (`repository.full_name`, commit `sha`, etc.) that are never cross-validated against the org used for verification.

### Likelihood Explanation
Requires only that the deployed Shipit installation manage more than one GitHub organization and that at least one of them has no `webhook_secret` set (a state the project's own sample config explicitly shows as valid, `webhook_secret: # nil`) or is easy to identify by an attacker probing multiple orgs. No GitHub App private key, session, or `ApiClient` token is needed — only the ability to POST to the public `/webhooks` endpoint with a crafted `X-Github-Event` header and JSON body.

### Recommendation
Bind signature verification to the organization the event is actually about, not an attacker-suppliable convenience field: require every configured organization used in production to have a mandatory `webhook_secret` (reject requests instead of returning `true` when unset), and re-validate after parsing that all organization/repository references inside the payload used by a handler are consistent with the organization whose secret authenticated the request.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `protected-org` (has `webhook_secret`) and `staging-org` (no `webhook_secret`, matching the shipped `config/secrets.development.shopify.yml` template).
2. POST to `/webhooks` with `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "organization": { "login": "staging-org" },
  "team": { "id": <id-of-a-team-in-Shipit.github_teams>, "slug": "developers", "name": "Developers", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
   No valid `X-Hub-Signature` is required because `verify_webhook_signature` returns `true` for `staging-org` (`lib/shipit/github_app.rb:76-83`).
3. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) passes, `MembershipHandler` runs, and `attacker-github-login` is added to a team counted by `Shipit.github_teams`, satisfying `User#authorized?` (`app/models/shipit/user.rb:80-82`) on next OAuth login.

*Note: I was not able to load the `MembershipHandler` source file itself (only its behavior via `test/controllers/webhooks_controller_test.rb`) or the `PushHandler`/`StatusHandler` internals within this session, so the exact field names consumed by those handlers for cross-org actions are inferred from the tests rather than directly cited; a Devin session with full repository access should confirm those handler internals before remediation.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
