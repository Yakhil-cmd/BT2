### Title
`EnvironmentVariables#interpolate` falls back to the Shipit host's process `ENV` for any `$VAR` not present in `@task.env`/`@stack.env`, leaking host secrets into task output - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate` resolves `$WORD` references in deploy step strings with `@env.fetch(variable) { ENV[variable] }`, so any variable name not present in the task/stack env hash silently falls back to the Shipit server process's own `ENV`. Because deploy step text comes from the target repository's `shipit.yml`/`Shipit::TaskDefinition#steps`, and is never restricted to the `deploy.variables` whitelist before interpolation, a repository contributor can name an arbitrary `$SECRET_ENV_VAR` in a step and have Shipit print its own host-level environment variable (e.g. `GITHUB_TOKEN`) into the PTY output.

### Finding Description
The claimed binding is: for `$WORD` in an interpolated step argument, `value == @task.env['WORD'] || @stack.env['WORD']` (attacker/operator supplied values only). The actual code breaks this: [1](#0-0) 

`interpolate` is called via `Command#interpolate_environment_variables`, which wraps `Command#env` (built from `TaskCommands#env`, i.e. `@stack.env` merged with task metadata, `deploy_spec.machine_env`, and `@task.env`) — it is never filtered through `deploy_variables`/`permit` at this point: [2](#0-1) [3](#0-2) 

`Command#start` feeds the interpolated arguments directly into `PTY.spawn`, and any text produced by the spawned process (including a resolved secret via e.g. `echo $GITHUB_TOKEN`) is streamed and written to the task's persisted output: [4](#0-3) 

Deploy step strings themselves originate from the repository's own `shipit.yml`, loaded per-commit by `DeploySpec::FileSystem#load_config` from the checked-out working directory, and `deploy_steps` come straight from `config('deploy', 'override')`/`discover_deploy_steps` with no whitelist enforcement over the literal text of the step: [5](#0-4) [6](#0-5) 

The `deploy.variables` whitelist (`filter_deploy_envs`/`permit`) only sanitizes environment variables supplied through deploy request parameters (`@task.env`) — it never governs what identifiers may appear as `$WORD` tokens inside the step command strings, and it plays no role in `interpolate`'s resolution at all: [7](#0-6) [8](#0-7) 

**Exploit flow:** An attacker opens a pull request against a repository whose Shipit stack auto-deploys PR branches (a "review stack") or otherwise gets their `shipit.yml` change executed. Their `shipit.yml` deploy step is e.g. `"echo $GITHUB_TOKEN"`. `GITHUB_TOKEN` is not a key in `@task.env` or `@stack.env`, so `@env.fetch('GITHUB_TOKEN') { ... }` executes the block, returning `ENV['GITHUB_TOKEN']` — the Shipit host process's own token — which is then `Shellwords.escape`d into the command line and echoed into task output that the attacker (who owns the PR/review stack) can read.

None of the listed guards intercept this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate webhook delivery, not the *content* of `shipit.yml`; `EnvironmentVariables#permit` is never invoked on the step string, only on request-supplied env hashes; there is no validator constraining which `$WORD` tokens may appear inside a deploy step.

### Impact Explanation
Any secret present in the Shipit host's own process environment (which can include `GITHUB_TOKEN` used for the app's own GitHub API access, or other operator-configured secrets) can be exfiltrated into a task's log output, which is attributable to and readable by the PR author who triggered the review-stack deployment. This is repeatable against any repository/stack that Shipit deploys from PR-controlled content (review stacks), and against any Shipit instance where an attacker-controlled `shipit.yml` step reaches `Command#interpolate_environment_variables`. This matches the Critical category: "exfiltration of `GITHUB_TOKEN` ... or deploy-time secrets."

### Likelihood Explanation
Requires the Shipit instance to run deploys from attacker-influenced `shipit.yml` content — most directly via review stacks (deploying PR branches automatically), which is a documented, common Shipit feature and requires no special privilege beyond opening a PR from a fork. Attacker cost is a single PR; the technique is trivially repeatable across any variable name present in the host's `ENV` (not limited to `GITHUB_TOKEN`).

### Recommendation
In `EnvironmentVariables#interpolate`, remove the `ENV[variable]` fallback and resolve strictly against the provided `@env` hash (returning empty/raising for unknown variables), so that `$WORD` can only ever resolve to a value present in `@task.env`/`@stack.env`, never to the Shipit process's own `ENV`.

### Proof of Concept
Add to `test/unit/environment_variables_test.rb`:
```ruby
test 'interpolate does not fall back to process ENV' do
  ENV['GITHUB_TOKEN'] = 'super-secret-host-token'
  env = { 'SAFE' => 'ok' }
  result = EnvironmentVariables.with(env).interpolate('echo $GITHUB_TOKEN')
  # Binding under test: substituted value must come from env (task/stack), not process ENV.
  assert_not_equal 'echo super-secret-host-token', result
  assert_equal 'echo ', result # or escaped-nil, depending on chosen fix
ensure
  ENV.delete('GITHUB_TOKEN')
end
```
Currently this assertion fails: `result` equals `"echo super-secret-host-token"`, demonstrating the leak of the host process's `ENV['GITHUB_TOKEN']` through `@env.fetch(variable) { ENV[variable] }`.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
