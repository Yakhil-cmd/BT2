### Title
Unresolved Nested Address Definition Silently Treated as "Has Signature" During Definition Validation - (File: definition.js)

### Summary
`validateDefinition()` in `definition.js` structurally validates a new address (or asset-spending) definition, and for every sub-expression it also returns a second boolean indicating whether that branch actually contains a real signature requirement (`sig`, `hash`, weighted `set`, etc. return `cb(null, true/false)` for this purpose) [1](#0-0) . When the definition contains an `['address', other_address]` reference to another address whose definition cannot be found anywhere (not in storage, not among the current unit's co-authors), the code does not fail closed — it unconditionally reports the branch as satisfying the "has signature" property via `bAllowUnresolvedInnerDefinitions ? cb(null, true) : cb(...)`, exactly the "silent success on failed verification" pattern described in the report.

### Finding Description
Inside `evaluate()`'s `'address'` case, the code looks up the referenced address's definition with `storage.readDefinitionByAddress`. If it is not found in storage, it falls back to checking whether the current unit's authors disclose it; if that also fails (`arrDefiningAuthors.length === 0`), instead of returning a validation error, it does:
```
var bAllowUnresolvedInnerDefinitions = true;
...
if (arrDefiningAuthors.length === 0) // no address definition in the current unit
    return bAllowUnresolvedInnerDefinitions ? cb(null, true) : cb("definition of inner address "+other_address+" not found");
``` [2](#0-1) 

This mirrors the libheif bug class precisely: a sub-component of the structure (the nested definition, analogous to a grid tile) fails to be resolved/verified, yet the enclosing computation is not aborted or flagged — it is reported to the caller as `cb(null, true)`, the same "ok" signal used by branches that were genuinely and fully verified (e.g. `'sig'` at line 250, which legitimately returns `cb(null, true)`) [3](#0-2) . The caller of `evaluate()` (definition-structure checks such as weighted-set aggregation at lines 203-232, which sum up `weight_of_options_with_sig` based on this very boolean) cannot distinguish "verified as containing a signature" from "could not be verified, assumed to contain a signature" [4](#0-3) .

By contrast, the actual spend-time authentifier-matching function `validateAuthentifiers()` handles the identical `'address'` case correctly and fails closed (`return cb2(false)`) when the definition cannot be resolved [5](#0-4) . The vulnerable path is confined to `validateDefinition()`, i.e., the structural check performed when a definition is being introduced/validated, not the runtime signature check — but its output (the "has-sig" boolean) is used by higher-level definition-shape rules (visible via the `bHasSig`/weighted-set aggregation logic) to reason about whether a definition genuinely enforces signing.

### Impact Explanation
If the "has signature" property is (as its use in the weighted-set aggregation logic strongly suggests) part of a defense that prevents definitions with no real signing requirement from being accepted as valid address definitions, then an attacker can craft a definition that nests a reference to an address whose definition is deliberately never disclosed (neither in storage nor among co-authors of the defining unit). `validateDefinition()` will credit that branch as containing a signature even though nothing was actually checked. This can let an attacker get a definition accepted as "properly signed" that in reality permits spending without a genuine signature once the "unresolved" address is later defined with a trivially satisfiable (or no-signature) definition, or is simply never required to disclose one. That is a path toward unauthorized spending from an address whose funds should be signature-protected.

### Likelihood Explanation
Any unprivileged unit poster can trigger this by submitting a unit that defines a new address (or an asset condition) containing an `['address', X]` reference to some address `X` for which no definition is ever published, and where `X` is not one of the unit's own authors. The vulnerable branch is reached deterministically via ordinary `validateDefinition()` processing of author/asset definitions, with no special privileges required — the "default" fallback (`bAllowUnresolvedInnerDefinitions = true`) is hard-coded, and a commented-out stricter check right above it (lines 285-286) shows the code path used to fail differently, indicating this is a live design/regression risk area.

### Recommendation
Do not silently mark an unresolved nested address definition as containing a valid signature requirement. When `arrDefiningAuthors.length === 0`, either reject the containing definition outright, or propagate a distinct "unknown"/"unverified" tri-state (rather than reusing the same boolean used for confirmed sig branches) so that composite checks (e.g., weighted-set "at least one branch needs a signature") cannot be satisfied by an unresolved, unverified reference. At minimum, ensure this exact code path cannot be used to satisfy any invariant that assumes real signature enforcement.

### Proof of Concept
1. Attacker composes a unit that defines a new address `A` with definition `['address', 'UNPUBLISHED_ADDRESS']` (or nests it inside a `weighted set`/`or` alongside branches lacking their own signature).
2. `UNPUBLISHED_ADDRESS` has never had its definition published in `definitions`/`address_definition_changes`, and is not a co-author of the defining unit.
3. During `validateDefinition()`, the `'address'` branch hits `ifDefinitionNotFound` with `arrDefiningAuthors.length === 0`, and returns `cb(null, true)` [6](#0-5) , letting the definition pass structural checks that rely on "has signature" as a proxy for real authorization strength (e.g., the weighted-set aggregation at lines 216-231).
4. The definition for `A` is accepted as valid even though the referenced inner definition was never verified to actually contain a signature requirement, opening a path to defining `UNPUBLISHED_ADDRESS` later with weak/no signing conditions and spending from `A` without proper authorization.

Note: I was not able to fully trace every downstream consumer of the "has signature" boolean beyond the weighted-set aggregation shown in `definition.js`; a full confirmation of the invariant this boolean is meant to enforce (and thus the precise blast radius) would benefit from a deeper live-session review of `definition.js` and its callers (`validateAuthentifiers`, asset-issuance condition checks, and any "must have a real sig" invariant enforcement).
