### Title
Webhook signature verification key is selected by an unverified payload field, letting the signing organization diverge from the repository/branch acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App secret to validate the HMAC against using `repository_owner`, a value read straight out of the still‑unverified JSON body [1](#0-0) . The handlers that actually act on the payload (`PushHandler`, `StatusHandler`, the `PullRequest::*` handlers) key their side effects off different fields of the same unverified body — `params.ref`/`stacks` matched by branch, `params.sha`, or `params.repository.full_name` [2](#0-1) [3](#0-2) [4](#0-3) . Nothing binds "the organization whose secret validated this HMAC" to "the repository/stack whose data is mutated by this call" — mirroring the ERC20 pattern of trusting a payload field that is never actually covered by the check that is supposed to guard it.

### Finding Description
`verify_signature` derives the app/secret to check against solely from `repository.owner.login` (or `organization.login`) inside the raw, not-yet-verified body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

The HMAC itself is computed over the entire raw body [6](#0-5) , so a correct signature does prove the body wasn't tampered with by someone who doesn't know `webhook_secret` for that org — but it says nothing about which *other* fields inside that same body (e.g. `repository.full_name`, `ref`, `sha`) are consistent with `repository.owner.login`. Any actor who legitimately possesses a valid `webhook_secret` for **one** configured organization (e.g. because they administer their own GitHub App installation on Shipit, a normal, unprivileged-relative-to-other-tenants capability in a multi-org Shipit deployment as documented in `config/secrets.development.shopify.yml`) can POST directly to `/webhooks` (bypassing GitHub entirely — there is no source-IP or GitHub-only restriction) with:
- `repository.owner.login` = their own org (so `verify_signature` selects and matches their own secret), and
- `repository.full_name`, `ref`, `sha`, etc. pointing at a **different** tenant's repository/stack tracked by the same Shipit instance,

signed with their own known `webhook_secret`. `verify_signature` passes because it only checks the org field they control; the handler that runs afterwards uses the unrelated `full_name`/`ref`/`sha` fields to locate and mutate another tenant's `Stack`/`Commit` records — e.g. `PushHandler#process` matches stacks purely by `branch` (`params.ref`) with no repository/org scoping at all [2](#0-1) , and `StatusHandler#process` matches commits purely by `sha` across the whole `Commit` table [3](#0-2) , again without checking that `sha`'s owning repository matches the org that signed the request.

This is exactly the ERC-20 "unchecked return/mismatched value" bug class translated to this engine's trust model: **the organization actually authenticated by the signature check ≠ the repository whose `Stack`/`Commit` state is written** by the handler that trusts the rest of the same payload.

### Impact Explanation
An attacker who controls a legitimate GitHub App installation for even one organization tracked by a shared, multi-tenant Shipit instance can forge webhook events that mutate the state (commit statuses, sync state, PR/merge-queue records) of *other* organizations' stacks on that same instance, without ever needing their `webhook_secret`, `api_clients_secret`, or a Shipit session. Depending on which handler is hit this can: inject a forged `success` status on another tenant's commit, which schedules `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` and can push that commit toward being **auto-merged or auto-deployed** on a repository the attacker does not own [7](#0-6)  — an unauthorized deploy/merge triggered purely from cross-tenant webhook confusion, satisfying the "Critical: unauthorized deploy, rollback or merge" bar.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (documented, supported configuration — see `config/secrets.development.shopify.yml`), and (2) the attacker to control one of those organizations' installed GitHub App (i.e., know that org's `webhook_secret`, which any org admin who set up their own app installation legitimately has). No access to the target org's secret, no Shipit login, and no `ApiClient` token is required. This is a realistic configuration for shared/SaaS-style Shipit deployments and does not depend on the host failing to mount the engine as documented.

### Recommendation
Bind the verified organization to the acted-upon resource: after signature verification succeeds for `repository_owner`, re-derive the target `Repository`/`Stack` strictly from that same verified organization (e.g., require `Repository.from_github_repo_name(params['repository']['full_name'])` to belong to `repository_owner`, and scope `PushHandler`/`StatusHandler` lookups by repository/organization, not just branch/sha) before any handler mutates state. Reject the webhook if `repository.full_name`'s owner segment doesn't match `repository.owner.login`.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with their own `webhook_secret` (as supported by `config/secrets.development.shopify.yml`).
2. As an attacker who legitimately administers `org-a`'s GitHub App (and thus knows `org-a`'s `webhook_secret`), craft a `status` webhook body:
   ```json
   {
     "repository": {"owner": {"login": "org-a"}},
     "sha": "<sha of a commit belonging to org-b/some-repo tracked by this Shipit instance>",
     "state": "success",
     "context": "ci/forged"
   }
   ```
3. Sign the raw body with `org-a`'s `webhook_secret` and set `X-Hub-Signature`, `X-Github-Event: status`.
4. POST to `/webhooks`. `verify_signature` selects `Shipit.github(organization: 'org-a')` and validates successfully against the attacker-known secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching org-b's commit purely by SHA — and calls `create_status_from_github!`, injecting a forged `success` status that can trigger `ProcessMergeRequestsJob`/continuous delivery on `org-b`'s stack, confirming cross-tenant write via an org/repository trust-binding break.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
