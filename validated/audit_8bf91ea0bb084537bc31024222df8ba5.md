This confirms a genuine binding break: `WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')` [1](#0-0) . All downstream `Handler` subclasses, however, resolve the target `Repository`/`Stack` from a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')` [2](#0-1) , e.g. `PushHandler#process` uses `stacks` (derived from that `full_name`) to call `stack.sync_github` [3](#0-2) .

### Title
Webhook signature is verified against an organization derived from an unauthenticated field, letting an attacker mount actions against an unrelated repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, computed from the raw, unauthenticated JSON payload (`repository.owner.login`, falling back to `organization.login`) [4](#0-3) . The handlers that actually act on the payload (e.g. `PushHandler`, `Handler#stacks`) select the target `Repository`/`Stack` using `repository.full_name` from that same untrusted body [2](#0-1) . Nothing enforces that the org used to pick the signing secret is the same org that owns the repository being acted upon.

### Finding Description
Root cause: `Shipit.github(organization: repository_owner)` returns a `GitHubApp` per-organization config, and `verify_webhook_signature` will `return true unless webhook_secret` (i.e., unconditionally accept unsigned or forged requests) when that organization has no `webhook_secret` configured [5](#0-4) . Multi-org installations are an explicitly supported configuration shape (`config/secrets.development.shopify.yml`, `docs/setup.md` "Using Multiple Github Applications") [6](#0-5) , and the test fixture even shows an org (`OrgTwo`) configured with `webhook_secret: # nil` alongside another org that does have a secret [7](#0-6) .

This breaks the intended binding: *organization authenticated == repository written*. An attacker can craft a raw POST to `/github/webhooks` (no session, no `ApiClient` token needed — this is a public webhook endpoint) with:
- `organization.login` (or `repository.owner.login`) set to an org whose `webhook_secret` is blank/unknown to the attacker's advantage (any org without a secret configured on this Shipit instance satisfies `verify_webhook_signature` unconditionally), and
- `repository.full_name` set to `victim-org/victim-repo`, a stack actually configured in this Shipit instance under a *different*, secured organization.

`verify_signature` passes because the secret-less org's app trivially "verifies" the request, while `PushHandler`/other handlers resolve and act on the victim stack via `repository.full_name` [2](#0-1) [8](#0-7) . This is precisely the read-only-reentrancy-style class of bug in the source report: an intermediate/derived value (`repository_owner`, used only for choosing the verifier) is inconsistent with the value the mutating logic actually operates on (`repository.full_name`), so the signature check does not cover the field being acted upon.

### Impact Explanation
This crosses the "unauthorized action on a repository/stack not covered by the verifying organization's credential" boundary described as High/Critical in scope: an unauthenticated third party can trigger `stack.sync_github` (and other webhook-driven side effects — `check_suite`, `status`, `pull_request`, `membership` handlers, all of which key off `payload.dig('repository', 'full_name')` via the same `Handler` base class) against a victim organization's stack, using only knowledge that some other configured org in the same Shipit deployment has no `webhook_secret` (or by simply omitting the signature for organizations that have never had one configured — the common single-org default `webhook_secret: # nil` shown in `config/secrets.development.example.yml`) [9](#0-8) . Since `sync_github` drives which commits are recorded as deployable and can influence continuous-deployment triggers, this is a genuine authentication-bypass-adjacent boundary break, not merely a DoS/rate-limit issue.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and (b) at least one configured organization without a `webhook_secret` — which is also the documented/default state (`webhook_secret: # nil` in every example secrets file). No credentials, session, or GitHub App key are needed; the webhook endpoint is intentionally public per `app/controllers/shipit/webhooks_controller.rb`. Likelihood is moderate-to-high wherever multi-org or default (no-secret) configurations are in use.

### Recommendation
Verify the webhook signature using the `GitHubApp` that actually owns the repository being acted upon (`repository.full_name`'s owner), not a value that can diverge from it, and reject payloads where `repository.owner.login`/`organization.login` do not match the owner segment of `repository.full_name`. Additionally, consider making an unset `webhook_secret` fail closed (reject) rather than default to `verified = true`, at least for any multi-org deployment.

### Proof of Concept
1. Deploy Shipit configured with two orgs: `SecureOrg` (has `webhook_secret` set) and `EmptyOrg` (no `webhook_secret`, e.g. the shipped default), both onboarded onto the same instance, with a `victim-stack` under `SecureOrg/victim-repo`.
2. POST to `/github/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "organization": {"login": "EmptyOrg"},
  "repository": {"full_name": "SecureOrg/victim-repo", "owner": {}},
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `repository_owner` resolves to `"EmptyOrg"` (fallback path) → `Shipit.github(organization: "EmptyOrg").verify_webhook_signature` returns `true` unconditionally (no secret configured) [5](#0-4) .
4. `PushHandler` resolves `stacks` from `repository.full_name` = `"SecureOrg/victim-repo"`, finds the victim stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — a mutating action on `SecureOrg`'s stack triggered without ever presenting `SecureOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
