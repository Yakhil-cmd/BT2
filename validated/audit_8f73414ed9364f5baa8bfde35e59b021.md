Found the relevant TOCTOU-style binding break, matching the "organization that authenticated versus the repository that is written" analog category.

### Title
Webhook signature is verified against an attacker-controlled organization field that is disjoint from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The handler that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) independently reads `payload.dig('repository','full_name')` to locate the `Stack`/`Repository` to mutate. These two fields are never cross-checked, so a valid signature computed with organization A's secret does not guarantee that the repository being synced/merged/etc. actually belongs to organization A.

### Finding Description [1](#0-0)  resolves the signing organization from `repository_owner`: [2](#0-1)  shows that value comes entirely from the JSON body, with no relation enforced to any other field.

Meanwhile, the actual repository operated on by every webhook handler is derived from a different JSON field: [3](#0-2)  — `repository_name` reads `payload.dig('repository', 'full_name')`, used to find the `Repository`/`Stack` and, e.g. in `PushHandler`, trigger `stack.sync_github` for whatever branch/commit is named in the payload: [4](#0-3) 

In a multi-organization Shipit deployment (the engine explicitly supports configuring several organizations, each with its own `webhook_secret`, as shown in the sample config [5](#0-4) ), the binding that should hold is: *organization whose secret verified the signature == organization that owns the repository being written*. Nothing in `verify_signature` or in `Handler#repository_name`/`#stacks` enforces this equality — `repository.owner.login` (used for verification) and `repository.full_name` (used for action) are two independently attacker-controlled strings inside the same JSON body that Shipit trusts to agree.

### Impact Explanation
Any party capable of producing a validly-signed webhook body for *any one* configured organization (e.g. a normal contributor of an org that has push access to trigger real GitHub webhooks, or anyone who can replay/craft a body signed under one org's secret) can set `repository.owner.login` to that organization while setting `repository.full_name` to `otherorg/other-repo`. The `push` handler will then call `stack.sync_github` for `otherorg/other-repo`, and other handlers (`status`, `check_suite`, `pull_request`, `membership`) will likewise be misdirected — causing Shipit to ingest attacker-controlled commit/status/CI/pull-request data for a repository/organization that never actually produced or authorized this event. Depending on which handler is abused this can pollute CI status used to gate deploys (`status`/`check_suite` handlers) or falsify commit history considered for deploy (`push` handler), for a repository the request's true signer does not own — a cross-repository/cross-organization integrity violation of the deployment pipeline.

### Likelihood Explanation
This requires the engine to be configured with more than one GitHub organization/app (a documented, supported configuration) and requires the attacker to be able to produce a validly-signed webhook payload for at least one of those organizations (e.g., via ordinary GitHub webhook delivery from a repo/org they only need write/webhook-triggering ability on, not on the target org). No Shipit session, API token, or knowledge of the *target* organization's secret is needed — only correspondence with one configured org's own webhook flow, which the attacker can freely shape the JSON body of (GitHub does not constrain arbitrary extra/mismatched fields inside its own delivered payloads, and this path is also reachable by anyone who can get any organization onboarded to a shared/multi-tenant Shipit instance).

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`/`#stacks`, cross-validate that the organization used to select the `webhook_secret` (`repository_owner`) matches the owner segment of `repository.full_name` that handlers actually use to resolve the target `Repository`/`Stack`; reject the webhook (422) if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own GitHub App / `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As a party with the ability to deliver (or replay) a genuinely-signed `push` webhook from `orgA` (i.e., knows/derives `orgA`'s `webhook_secret` through normal, legitimate use of `orgA`'s own GitHub App installation), craft a JSON body where:
   - `repository.owner.login = "orgA"` (so `verify_signature` selects and validates against `orgA`'s secret — [6](#0-5) )
   - `repository.full_name = "orgB/target-repo"` (so `Handler#repository_name` resolves the `orgB` stack — [7](#0-6) )
   - `ref`, `after` set to attacker-chosen values.
3. Sign the raw body with `orgA`'s `webhook_secret` and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` passes (signature matches `orgA`'s secret for `repository_owner == "orgA"`), and `PushHandler#process` runs `stack.sync_github(expected_head_sha: params.after)` against `orgB`'s stack, even though the request was never signed by anything belonging to `orgB`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
