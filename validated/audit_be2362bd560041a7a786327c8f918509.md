### Title
Crafted address-definition reference in a unit causes an unhandled `throw Error` that crashes the node process (DoS) - ([File: definition.js])

### Summary
`ocore` installs a global `process.on('uncaughtException', ...)` handler in `network.js` that deliberately **re-throws** any uncaught exception to crash the whole node process: [1](#0-0) 

Several validation code paths that are reachable from a single, attacker-crafted, unsigned unit use `throw Error(...)` instead of returning an error to the callback chain. If such a `throw` occurs deep inside async validation callbacks (outside of any `try/catch` that funnels back into `validate()`'s own error handling), it becomes an uncaught exception and crashes the node — exactly analogous to the CVE's DoS via crafted input hitting an unguarded cleanup/assertion path in Virtuoso.

### Finding Description
`definition.js`'s `evaluate()` function (used both for validating definitions and for validating authentifiers of a posted unit) resolves nested `['address', other_address]` references. When the referenced address has no on-chain definition yet, it falls back to look for a definition supplied inline by one of the unit's own authors: [2](#0-1) 

The critical line is:
```
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
```
This filter matches on `author.address === other_address && author.definition && objectHash.getChash160(author.definition) === definition_chash`. Because `objUnit.authors` is an attacker-supplied array parsed directly from the posted unit JSON, and `validation.js` does not appear to reject units whose `authors` array contains multiple entries sharing the same `.address` field (the array-of-authors length/shape checks in `validation.js` constrain array size and address validity, but do not enforce address uniqueness across entries) — an attacker can craft a unit with two co-author entries that have the same `address` and the same inline `definition` (whose chash matches the referenced `definition_chash`). This satisfies `arrDefiningAuthors.length > 1`, hitting the `throw Error(...)` inside a nested `storage.readDefinitionByAddress` callback, which is not wrapped by any `try/catch` that would route it back through `validate()`'s `ifUnitError`/`ifJointError` paths.

Because this throw happens inside an asynchronous DB callback (`ifDefinitionNotFound`), it escapes the normal synchronous exception-catching structure of `validate()` and becomes an **uncaught exception**, hitting the global handler in `network.js` that intentionally re-throws to crash the process: [1](#0-0) 

The identical unguarded `throw Error("more than 1 address definition")` pattern also exists in the definition-*validation* path (not just authentifier-checking): [3](#0-2) 

This is reachable any time a unit's spending/definition conditions reference a nested address (`['address', X]`) inside its own or a co-authored address's definition — a standard, unprivileged posting operation available to any wallet.

### Impact Explanation
Any full node (and potentially light vendors serving as hubs) that receives and validates such a unit from the network — via normal gossip/relay, not requiring a malicious peer or privileged access — will crash. Because units propagate broadly, this single crafted unit can be relayed to and crash every full node that processes it, i.e. **a network unable to confirm new units** while nodes are repeatedly restarted/crashing on catch-up of the same poisoned unit (it remains in the DAG and will be revalidated on restart/catch-up, causing a repeatable crash loop). This matches the "network unable to confirm new units" / "node disagreement" acceptance criteria for a Critical/High DoS class analog to CVE-2024-57650.

### Likelihood Explanation
The primitive is reachable by any unprivileged unit poster: it only requires posting a unit whose definition (or a co-author's definition) contains a nested `['address', X]` reference, together with two authors sharing the same address/definition pair matching that referenced chash. No special network position, no hub/peer compromise, and no light-proof serving is needed — it's a standard "just post a unit" attack vector.

### Recommendation
- Replace the unguarded `throw Error("more than 1 address definition")` calls in `definition.js` (both instances) with a call to `cb2(false)` / `cb("...")` so that the condition surfaces as an ordinary unit-validation failure (`ifUnitError`) instead of an uncaught exception.
- Add an explicit validation step in `validation.js` rejecting units whose `authors` array contains duplicate `address` values, closing off this and any similarly-shaped bug class.
- Audit other `throw Error(...)` calls inside asynchronous DB-callback code paths of `definition.js`, `validation.js`, `storage.js`, and `aa_composer.js` that are reachable from untrusted unit/trigger content, since the same crash pattern (`uncaughtException` → re-throw → process crash) generalizes across all of them.

### Proof of Concept
1. Craft an unsigned unit with two authors, `A1` and `A2`, both having `address` equal to some address `X`, and both carrying identical `.definition` fields such that `objectHash.getChash160(definition)` equals the `definition_chash` of a nested `['address', X]` reference used in the spending/definition condition being validated (e.g., as part of another author's multi-sig definition referencing `X`).
2. Post this unit to any full node/relay.
3. During `validateAuthentifiers`/`validateDefinition` processing, `evaluate()` reaches the `'address'` case in `definition.js`, `storage.readDefinitionByAddress` reports `ifDefinitionNotFound` (since `X` has no on-chain definition yet), and the filter over `objUnit.authors` yields `arrDefiningAuthors.length === 2`.
4. The unguarded `throw Error("more than 1 address definition")` fires inside the async callback, escapes to `process.on('uncaughtException', ...)` in `network.js`, which re-throws and crashes the node process — a repeatable Denial of Service triggered purely by unit content, with no attacker privileges beyond normal unit posting.
