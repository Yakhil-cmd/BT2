### Title
Permanent market freeze when scaled debt value overflows before the borrow-index cap - (File: `common/src/rates/simulate.rs`)

### Summary
Interest accrual multiplies `borrowed` by `borrow_index` using checked `Ray` arithmetic before applying `MAX_BORROW_INDEX_RAY`. For a sufficiently large market, the resulting debt value can exceed `i128::MAX` while the index itself remains below its configured cap. Every pool mutation loads an interest-synced market, so the first `MathOverflow` leaves `last_timestamp` unchanged and permanently blocks repayments, withdrawals, liquidations, bad-debt cleanup, and future index updates for that market. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` computes:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
```

`scaled_to_original` is `scaled.mul(env, index)`, which panics on `i128` overflow. [3](#0-2) 

Only after this multiplication does `update_borrow_index` clamp the new index to `MAX_BORROW_INDEX_RAY`; consequently, the value-domain limit is reached before the index cap can engage. [4](#0-3) [5](#0-4) 

An unprivileged actor can establish the vulnerable state through:

1. `Controller::supply(caller, account_id, spoke_id, [(hub_asset, amount)])`
2. `Controller::borrow(caller, account_id, [(hub_asset, debt_amount)], to)`
3. `Controller::update_indexes(caller, [hub_asset])`

The first two calls create a very large, high-utilization market. The third advances interest and eventually triggers the overflow. `Controller::update_indexes` only requires an authorized caller and forwards the assets to `pool_update_indexes_call`. [6](#0-5) [7](#0-6) 

The overflow happens inside `global_sync`, which runs before the mutation and before `mark_accrued`; the panic therefore rolls back the timestamp update and makes subsequent attempts fail at the same point. [8](#0-7) 

### Impact Explanation
The affected market becomes permanently unusable. Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot reduce risk because those entrypoints all reach `ops::load_leg` / `synced_market`, which invokes `global_sync` before processing the action. [9](#0-8) [10](#0-9) 

This causes permanent freezing of user funds and leaves debt and collateral incapable of normal settlement. Because `last_timestamp` is never committed past the failing accrual point, calling `update_indexes` repeatedly does not recover the market. [11](#0-10) 

### Likelihood Explanation
The trigger requires a market large enough for `borrowed * borrow_index` to exceed the raw `i128` domain before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`, plus sustained high utilization and time for the index to grow. Deployed supply, borrow, collateral, and utilization caps can constrain exploitability.

It is nevertheless reachable through only ordinary `supply`, `borrow`, and `update_indexes` calls when configured limits admit the required book size. The repository’s integration test demonstrates the condition with a one-billion-unit 18-decimal market at 98% utilization: yearly index updates eventually return `MATH_OVERFLOW`, while the stored borrow index remains below the cap; subsequent withdraw and repay calls fail identically. [12](#0-11) 

### Recommendation
Bound the debt value before multiplying scaled debt by the index, rather than relying only on the post-multiplication index cap.

At minimum:

- Perform `borrowed * borrow_index` in `I256` or a checked wide fixed-point operation.
- If the unscaled debt value would exceed the supported domain, clamp the index to the largest value that keeps the resulting value representable.
- Commit accrued progress incrementally where safe so one failing chunk cannot leave the market permanently stuck at an old `last_timestamp`.
- Apply the same domain check to `supplied * supply_index`, `calculate_supplier_rewards`, and `supply_index_reward_shortfall`.
- Add a regression test asserting the configured index ceiling engages before the value-domain overflow.

### Proof of Concept
The repository contains a reproducer at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`.

Conceptual transaction sequence:

```rust
let principal = BILLION * 10i128.pow(18);
let debt = principal / 100 * 98;

// Unprivileged market setup.
supply(caller, supplier_account, spoke_id,
       vec![(hub_asset, principal)]);

supply(borrower, borrower_account, spoke_id,
       vec![(collateral_asset, sufficient_collateral)]);

borrow(borrower, borrower_account,
       vec![(hub_asset, debt)], Some(borrower));

// Repeat after sufficiently large ledger-time advances.
update_indexes(caller, vec![hub_asset]);
```

Once `borrowed * borrow_index` exceeds `i128::MAX`, `update_indexes` fails with `GenericError::MathOverflow`. Because the panic occurs before `mark_accrued`, these calls then fail permanently as well:

```rust
repay(caller, borrower_account, vec![(hub_asset, repay_amount)]);
withdraw(caller, supplier_account, vec![(hub_asset, withdraw_amount)], None);
liquidate(liquidator, borrower_account, payments, seize_mode);
```

The existing test explicitly confirms that `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. [13](#0-12)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    env: &Env,
    is_liquidation: bool,
    entry: &PoolWithdrawEntry,
) -> WithdrawOutcome {
    require_nonneg_amount(env, entry.protocol_fee);
    let (mut cache, position) = ops::load_leg(env, &entry.action);

    pub(crate) fn elapsed_ms(&self) -> u64 {

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);

    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);

        "the index cap did not engage before the value overflow"
