### Title
Webhook signing-organization is decoupled from the acted-upon repository, allowing signature-bypass forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to validate `X-Hub-Signature` from an attacker-supplied field (`repository.owner.login`, falling back to `organization.login`) taken from the *unverified* request body, while the payload's actual write target used by every handler is a *different* field (`repository.full_name`). In a multi-organization Shipit deployment, this breaks the binding `organization authenticated == repository written`: `repository.owner.login` picks which org's secret must sign the request, but `repository.full_name` (or `organization.login` for org-scoped events like `membership`) determines which `Repository`/`Stack`/`Team` the payload actually acts on.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is parsed straight out of the raw (unauthenticated) JSON body, and is used only to pick *which* `GitHubApp`/webhook secret must validate the signature: [1](#0-0) 

`Shipit.github(organization:)` resolves a per-organization config (multi-tenant mode) via `github_app_config`: [3](#0-2) 

Crucially, `verify_webhook_signature` treats a missing/`nil` `webhook_secret` for that organization as automatic success, with **no signature check performed**: [4](#0-3) 

Meanwhile, none of the actual event handlers use `repository.owner.login` to decide what to act on. They all key off `repository.full_name` (a different JSON field, independently attacker-controlled in the same unauthenticated body): [5](#0-4) [6](#0-5) 

For organization-scoped events (e.g. `membership`), the handler trusts `organization.login` from the same unauthenticated body to create/attach `Team`/`Membership` records that feed directly into `Shipit.github_teams` authorization: [7](#0-6) 

So the equality that should hold — *the organization whose secret validated this request* == *the organization/repository the payload is allowed to mutate* — is never enforced. `repository_owner` (verification key selector) and `repository.full_name`/`organization.login` (actual mutation target) are two independently-controlled fields inside the same JSON body, exactly analogous to the `SecuritizeSwap` bug where the EIP-712 `TXTYPE_HASH` covered a different set of fields than the ones actually consumed by `doExecuteByInvestor` — the "verified" structure and the "acted-upon" structure diverge.

### Impact Explanation
In a multi-organization Shipit configuration (`docs/setup.md` "Using Multiple GitHub Applications", explicitly documented and supported via `test/dummy/config/secrets_double_github_app.yml`), if any configured organization has `webhook_secret` left blank (documented as "optional" in `docs/setup.md`), `verify_webhook_signature` returns `true` unconditionally for that org. An attacker can then submit a completely unsigned POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) set to the org lacking a secret — satisfies `verify_signature`.
- `repository.full_name` (or `organization.login` for `membership` events) set to a *different*, secured organization's real repository/org that Shipit actually manages.

This forges events for repositories/organizations that are not the one whose (missing) secret was used to "authenticate" the request, i.e. cross-organization/cross-repository control: forcing `PushHandler`/`GithubSyncJob` syncs, archiving/unarchiving review stacks via PR handlers, or — most severely — forging `membership` events to add an attacker-controlled GitHub login to a `Team` that is part of `Shipit.github_teams`, directly escalating into `Shipit.github_teams` authorization and granting the attacker authenticated access to trigger deploys/rollbacks/merges on stacks belonging to a fully-secured organization.

### Likelihood Explanation
Requires only that a Shipit deployment operate in multi-org mode with at least one configured organization lacking `webhook_secret` — a state the codebase and documentation explicitly treat as valid/supported (`webhook_secret: # nil` appears as the shipped default in every multi-org example config, including `test/dummy/config/secrets_double_github_app.yml`). No credentials, tokens, or GitHub App secrets are needed by the attacker; only knowledge/guessing of the unsecured org's name in the Shipit config, which is not treated as a secret.

### Recommendation
- Verify the webhook signature using a secret bound to the organization/repository that the payload will actually mutate, not a separately-attacker-chosen field, and make `repository.full_name`'s owner and `repository_owner`/`organization.login` consistent and cross-checked before trusting either.
- Remove the `return true unless webhook_secret` short-circuit in `GitHubApp#verify_webhook_signature`; require a webhook secret to be configured for every organization able to receive webhooks, or explicitly refuse to process events for organizations without one.
- Reject webhooks whose `repository.full_name` owner does not match the `repository.owner.login`/`organization.login` used to select the signing secret.

### Proof of Concept
Given a multi-org `secrets.yml` where `OrgB` has `webhook_secret: nil` and `OrgA` is fully configured/secured and owns `stack` `OrgA/prod-repo`:

```
POST /webhooks
X-Github-Event: push
Content-Type: application/json
(no X-Hub-Signature header needed)

{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/prod-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```

`verify_signature` resolves `repository_owner => "OrgB"`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` without checking any signature. `WebhooksController#create` then dispatches to `PushHandler`, which resolves the target stack via `payload.dig('repository','full_name')` = `"OrgA/prod-repo"`, and enqueues a `GithubSyncJob`/`sync_github` for the real, secured `OrgA` stack — despite the request never being validated against `OrgA`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'
