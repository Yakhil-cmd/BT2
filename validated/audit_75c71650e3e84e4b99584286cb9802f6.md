## Analog Found

### Title
Authorization Bypass Through User-Controlled Key in wallet signing-request handler allows any paired device to solicit signature over an address/wallet it is not a cosigner of - ([File: wallet.js])

### Summary
The CVE describes an IDOR where a payroll listing/creation endpoint validates a caller-supplied employee identifier for *global existence* instead of checking that the identifier is scoped to (a member of) the caller's own company/tenant. The direct analog in `ocore` is in the device-message `"sign"` handler in `wallet.js`, which lets any correspondent (paired) device request signing over an arbitrary `address` + `signing_path` pair. The local-address branch resolves the request purely by checking that the `(address, signing_path)` pair globally exists in the wallet tables — it never verifies that the requesting device (`from_address`) is actually a registered cosigner/member of that wallet or shared address, i.e. it validates "does this signing path exist at all" rather than "does this signing path belong to *this* correspondent".

### Finding Description
In `handleMessageFromHub`, the `"sign"` case only validates the shape of the request (`address` is a valid address, `signing_path` matches a regex, the unsigned unit has valid authors/messages), then calls `findAddress(body.address, body.signing_path, callbacks, ...)`: [1](#0-0) 

`findAddress` resolves the address purely from global wallet/shared-address tables, with **no filter on `from_address`** (the actual sender of the device message): [2](#0-1) 

When the resolution lands on `ifLocal` (i.e., the address is genuinely one of "my" wallet addresses, held on this device), the handler proceeds to fire a `signing_request` event directly — the authorization check that would have verified the sender is actually a cosigner of this address/wallet is explicitly commented out: [3](#0-2) 

The comment is explicit about *why* it was disabled: `"the commented check would make multilateral signing impossible"`. In other words, the fix for legitimate multilateral signing use cases removed the tenant/membership check altogether, exactly mirroring the CVE's root cause ("validated for global existence rather than company/caller membership").

By contrast, the `ifRemote` branch (used when the target signing key lives on a different device) *does* perform the equivalent membership check: [4](#0-3) 

This asymmetry confirms the missing check is a bug, not an intentional design choice: the remote path checks `other_device_addresses.includes(from_address)`, but the local path has no analogous check that `from_address` is listed among the address's/wallet's authorized cosigner devices (e.g., via `wallet_signing_paths` or `shared_address_signing_paths` joined on `device_address`).

Reachability: any device that is a "correspondent" of the victim's wallet (paired at any point, e.g., a merchant bot, a chat contact, or any device the victim ever exchanged a pairing code with) can send this `"sign"` device message; `"sign"` is not in the whitelist of subjects allowed from indirect/unknown correspondents, but it requires only ordinary correspondent status, not cosigner status of the specific address being targeted — the exact "PR:L" (low-privilege authenticated actor) analog to the CVE.

### Impact Explanation
An attacker who is merely a paired correspondent (not a cosigner of the victim's multisig/shared wallet address) can craft a `"sign"` message naming any address+signing_path the victim controls together with an attacker-chosen unsigned unit (including arbitrary payment outputs). Because the membership check is missing, the wallet will treat this as a legitimate signing request from a plausible cosigner and surface a `signing_request` UI event to the user, who may reasonably believe it originates from an actual, expected cosigner (since the code path bypasses cosigner verification entirely). This can be leveraged to trick a user into approving unauthorized spends from shared/multisig funds, or otherwise pollute signing-request flows with requests that should never have reached the address's true cosigners in the first place. This maps to the "concrete unauthorized spending" / fund-loss category via wallet/device message handling explicitly listed as in-scope.

### Likelihood Explanation
Exploitation requires only that the attacker be an existing correspondent of the victim (a low bar — pairing is a one-time lightweight action, and many wallets/services auto-accept pairing for support/bot purposes), and that the target address be part of a multi-device wallet or shared address (single-key wallets aren't affected the same way since there's only one device to check against, but they also don't need the missing check to protect them). The attack is a straightforward JSON message over the existing hub/device protocol, requiring no cryptographic breaks.

### Recommendation
Reinstate (in un-commented, corrected form) the check removed from the `ifLocal` branch of the `"sign"` handler: before honoring a local signing request, verify that `from_address` is a legitimate cosigner/device for `body.address`'s wallet (for `my_addresses`) or for the shared address (via `shared_address_signing_paths`/`wallet_signing_paths` filtered by `device_address = from_address` and the relevant `signing_path` prefix), instead of relying solely on the address+signing_path's global existence in `findAddress`.

### Proof of Concept
1. Pair device `E` (attacker) with victim device `V` as an ordinary correspondent (no special wallet role).
2. `V` owns a shared/multisig address `A` where `V` is one of several cosigners, held via `my_addresses`/`wallet_signing_paths` for wallet `W`.
3. `E` sends a device message to `V`:
```
{
  "subject": "sign",
  "body": {
    "address": "A",
    "signing_path": "r.0",           // a path known to belong to V's local key
    "unsigned_unit": { ... attacker-crafted payment spending from A ... }
  }
}
```
4. On `V`, `handleMessageFromHub` reaches the `"sign"` case, calls `findAddress("A", "r.0", ...)`, which resolves via `my_addresses`/`wallet_signing_paths` to `ifLocal` (since the signing key genuinely lives on `V`) — with no check that `E` (`from_address`) is a cosigner of wallet `W`/address `A`.
5. `V` fires a `signing_request` event for the attacker-supplied unsigned unit, without ever having validated `E`'s membership in `W`, differing from the `ifRemote` path which explicitly performs this check at [5](#0-4) .
