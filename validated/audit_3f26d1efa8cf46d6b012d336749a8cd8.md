### Title
Cross-organization webhook forgery via attacker-controlled `repository.owner.login` used to select the signature-verification secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, unsigned-at-that-point JSON body, then uses that secret to check the `X-Hub-Signature` HMAC over the raw payload. In a multi-organization Shipit deployment (`config/secrets.yml` with multiple GitHub orgs, each with its own `webhook_secret`), this lets anyone who legitimately knows one organization's webhook secret (e.g., an admin of their own installed GitHub App/org) forge a webhook whose body claims to originate from that organization while its actual payload content (`repository.full_name`, commit SHAs, statuses, etc.) references a stack/repository belonging to a *different* tracked organization.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 

`repository_owner` is derived straight from the JSON body the attacker fully controls: [2](#0-1) 

The secret used for verification (`Shipit.github(organization: repository_owner)`'s `webhook_secret`) is resolved per-organization from `config/secrets.yml`, which explicitly supports multiple independent GitHub Apps/organizations, each with a distinct `webhook_secret`: [3](#0-2) [4](#0-3) 

However, once signature verification passes, the *content* that actually gets acted on (which repository/stack is mutated) is resolved independently from a different field of the same attacker-controlled body — `repository.full_name` — with no cross-check against the organization used to pick the verification secret: [5](#0-4) 

This is the binding break: the organization whose secret authenticates the signature (`repository.owner.login`) is not required to equal the organization/repository the handlers actually operate on (`repository.full_name`). Because `verify_webhook_signature` only checks that the raw body's HMAC matches *some* configured org's secret picked by an attacker-supplied field in that very body, an attacker who legitimately controls one tenant's GitHub App/org (and thus knows its `webhook_secret`, which they can freely obtain since they own that installation) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org "A" so `verify_signature` selects secret A.
2. Set `repository.full_name` (used by `Handler#repository_name`/`Repository.from_github_repo_name`) to a repository belonging to org "B" tracked by the same Shipit instance.
3. Sign the whole raw body with secret A (which they know) — `verify_webhook_signature` passes since it only checks HMAC(secret_for_owner_login, body) == signature.
4. The webhook handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, PR handlers) then execute against org B's stacks based on `repository.full_name`, since none of them re-check that `repository.full_name`'s owner matches the organization whose secret was used. [6](#0-5) 
For example, `PushHandler#process` finds stacks purely via `repository_name` (i.e., attacker-controlled `repository.full_name`) and calls `stack.sync_github(expected_head_sha: params.after)`, regardless of which org's secret authenticated the request.

### Impact Explanation
This breaks the trust boundary between "the organization that cryptographically authenticated the webhook" and "the organization/repository whose Shipit state is mutated." In a shared/multi-tenant Shipit instance (the officially documented multi-org configuration), a party that only administers one tenant's GitHub App can forge webhook events (push resyncs, commit statuses via `StatusHandler`, check-suite results, PR/merge-queue events, team membership changes) for repositories/stacks belonging to a completely different, unrelated organization on the same instance. Injected commit statuses or check-suite results can influence Shipit's deploy/merge-queue gating logic, and forged push events can trigger resyncs/deploy triggers for stacks the attacker has no legitimate authorization over — an unauthorized cross-repository/cross-organization write, matching the "cross-repository writes" / "unauthorized deploy" High-impact criteria.

### Likelihood Explanation
Requires only knowledge of one legitimately-configured organization's `webhook_secret` in a multi-org Shipit deployment — something an org admin of a *different, unrelated* tenant sharing the same Shipit instance would normally have (they configured their own GitHub App and know its secret), without needing a Shipit session, `ApiClient` token, or any GitHub access to the victim org. The HTTP endpoint (`/webhooks`) is public and shared across all configured organizations, and the vulnerable field (`repository.owner.login`/`organization.login`) is directly attacker-controlled JSON with no relation enforced to the payload's actual repository content.

### Recommendation
After selecting the GitHub App/secret via `repository_owner`, verify that `repository.full_name`'s owner segment (and any `organization.login` used by handlers) matches the same organization used for secret selection before dispatching to handlers. Alternatively, resolve the target repository/stack first, derive the organization from the already-known/trusted repository record, and require the payload's declared owner to match it, rejecting mismatches with `422` prior to invoking any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` in `config/secrets.yml` (per `docs/setup.md`'s multi-org example) and each with at least one tracked repository/stack.
2. As an attacker who legitimately owns/administers the GitHub App for `org-a` (and thus knows `org-a`'s `webhook_secret`), craft a push-webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-a')` (from `repository.owner.login`) and validates successfully using `org-a`'s secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('org-b/victim-repo')` [5](#0-4)  and triggers `sync_github` on `org-b`'s stack — despite the attacker having no relationship with `org-b`.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
