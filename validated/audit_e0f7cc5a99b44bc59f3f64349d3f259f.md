### Title
Attacker-controlled secondary AA can force revert of a primary AA's enforcement logic by deliberately bouncing - ([File: aa_composer.js])

### Summary
The AA execution engine treats a chain of AA-to-AA calls (primary trigger → secondary trigger) as fully atomic: if the secondary AA "bounces" (its logic errors out), the entire primary AA's execution — including any punitive/enforcement actions such as slashing, penalty payouts, or blacklisting logic that the primary AA was performing against a malicious account — is unwound via `ROLLBACK TO SAVEPOINT`. This mirrors the reported bug class where a plugin can selectively revert a required call (`requiresNotification()`) to block `slash()` from completing, letting the targeted account evade the consequence and exit through another path (e.g., a pending withdrawal window) before the enforcement actually lands.

### Finding Description
When a primary AA sends outputs to another AA address as part of its logic, `handleSecondaryTriggers` recursively invokes `handleTrigger` for that secondary AA [1](#0-0) . If the secondary AA's execution results in an error (it "bounces"), the callback receives a `bounce_message`, and this propagates up as an error to the outer `async.eachSeries` completion handler: [2](#0-1) 

Here, if the failing secondary AA is not itself secondary to another secondary AA (`!bSecondary`), the primary AA's *entire* execution is unwound by calling `revert()`, not merely the isolated leaf-branch that failed. `revert()` clears all state variable changes, clears the response cache, and issues `ROLLBACK TO SAVEPOINT initial_balances`, undoing every action the primary AA performed in this trigger, before finally bouncing the whole unit back to the trigger's origin: [3](#0-2) 

This means that any address that is both (a) reachable as an output recipient from a primary AA's logic, and (b) itself an AA under attacker control, can act exactly like the malicious "plugin" in the original report: it can behave completely normally most of the time, but the moment it detects (via `trigger.address`, `trigger.data`, or the payment amount it receives, all of which are visible to the secondary AA's Oscript) that it is the target of an unfavorable operation — e.g., a penalty/slashing payout being sent to it, or a payout signaling the account is being expelled/blacklisted by the primary AA — it can deliberately throw/bounce (e.g. by defining a state formula whose only branch either bounces via insufficient `bounce_fees` handling or an explicit condition that fails validation). Because the failure of this single secondary branch reverts the *entire* primary trigger, all enforcement state changes made by the primary AA earlier in the same execution (e.g., marking the account as slashed, decrementing its balance, removing it from an active list) are rolled back together with the failed payment, exactly as `IPlugin.requiresNotification()` reverting undoes `slash()` in the original Solidity report.

### Impact Explanation
A staking/registry/membership AA written in Oscript that attempts to enforce a penalty against a misbehaving account by routing part of the punitive payout (or a notification-style payment) to an address nominated by that account (analogous to a "plugin") can have its entire enforcement transaction voided at will by the account. Because the AA's on-chain state (e.g. "already slashed" flags, exit windows, balance decrements) is rolled back together with the failed payment, the account can repeat this indefinitely while it, in parallel, arranges an ordinary exit/withdrawal through a separate trigger that does not touch the hostile secondary AA. This results in the same category of harm the report is concerned with: an "AA fund loss/freezing" or "unauthorized fund evasion" scenario, where a party that should be penalized retains and withdraws funds because the enforcement transaction can be repeatedly and deliberately bounced by code the party controls, while the AA has no way to isolate the punitive branch from the rest of its atomic execution (there is no "try/catch on secondary trigger" primitive, `revert()` unconditionally throws away the whole primary trigger's results).

### Likelihood Explanation
This requires an AA author to design a contract that sends outputs to an address supplied or influenced by the account being penalized (a very common pattern — allow-lists, plugin registries, referral/notify addresses, or "send to configured recipient" patterns) and for that address to be, or later become, an AA under the attacker's control. Since AA addresses can be redefined/pointed to new logic before being used as a "secondary trigger" recipient (subject to the definition-change activation rules already enforced elsewhere in `aa_composer.js`), and since the attacker fully controls the Oscript in the secondary AA to conditionally bounce based on visible trigger context, the exploit is straightforward to construct once such a design pattern is used. It is not a bug in unit validation/consensus itself but a systemic engine property (the whole-chain atomicity model) that upstream AA authors implementing slashing/penalty semantics must account for; likelihood of exploitation is therefore contract-design-dependent but the mechanism itself in `aa_composer.js` is unconditionally exploitable whenever such a pattern exists.

### Recommendation
Consider providing AA authors an explicit mechanism to isolate a secondary payment/notification branch from the rest of the primary trigger's atomic effects — e.g., an option analogous to a "fire-and-forget" or "catch"-style secondary send where a bounce of the secondary AA does not `revert()` the primary AA's already-applied state changes, only the specific payment branch. At minimum, document prominently (and perhaps warn via `tools/validate_aa_definitions.js`) that sending payments to AA addresses supplied by or influenced by an untrusted account as part of enforcement/penalty logic is unsafe, since the recipient AA can force a full revert of the enforcing trigger by bouncing (`aa_composer.js` `handleSecondaryTriggers` / `revert()`), directly mirroring the try/catch gap identified in the referenced Solidity report.

### Proof of Concept
1. Deploy `PenaltyAA` (primary) which, on receiving a "slash" trigger for `account`, first updates a state var `var['slashed_'||account] = true` and decrements the account's tracked balance, then sends the confiscated amount to `notify_address[account]`, an address previously registered by `account` itself (a common "plugin"/"hook" style pattern).
2. `account` registers `notify_address[account]` pointing to `EvilAA`, an AA whose Oscript logic bounces (fails validation / triggers insufficient `bounce_fees`, or executes a formula that returns an error) whenever it detects (via `trigger.data`, `trigger.address`, or received amount) that it is receiving a "penalty" payout.
3. SLASHER submits the slash trigger to `PenaltyAA`. `PenaltyAA` executes, updates its state vars, and sends the payout as a secondary trigger to `EvilAA`.
4. `EvilAA` bounces. In `handleSecondaryTriggers`, the error propagates and `revert()` is called [2](#0-1) , which rolls back to `SAVEPOINT initial_balances`, discarding the `slashed_` flag and balance decrement made by `PenaltyAA` in the same trigger [4](#0-3) .
5. `account` repeats step 3 whenever SLASHER retries, while separately submitting an ordinary withdrawal trigger (unrelated to `EvilAA`) to fully exit before SLASHER can update `PenaltyAA`'s registered notify address or otherwise work around `EvilAA`.

Note: this analysis is based on the `aa_composer.js` engine logic retrieved via the code index; some surrounding helper functions (e.g. `getTrigger`, full `handleTrigger` signature) were only partially available in the indexed context, so if deeper verification of exact bounce-fee/validation triggers for a minimal `EvilAA` PoC script is needed, a full Devin session with direct repository access would be required to write and run an actual reproduction.
