### Title
Unfunded `repay`/`recapitalize` refunds pay out of real pool custody — the declared amount is refunded even though nothing was transferred in - (File: contracts/pool/src/ops/repay.rs)

### Summary
The ImageMagick CVE is a resource leak on a mishandled error/edge path: memory acquired is never released when a `NoSuchImage` error short-circuits the operator loop. The structural analog in XOXNO Lending is a *custody leak* on a declared-but-unfunded path: `ops::repay::apply` and `ops::recapitalize::apply` compute a refund from the **declared** `action.amount`/`amount`, not from any measured inbound receipt, and then push that refund out of the pool's real token balance via `Cache::transfer_out`. When the caller never funded the leg — or the market has no debt to retire — the entire amount is classified as "excess" and paid out of supplier custody with the cash book untouched.

### Finding Description
`ops::repay::accounting` resolves `action.amount` into `burned` shares and `overpayment` via `cache.resolve_repay` (`contracts/pool/src/ops/repay.rs:40-67`). When the position carries no debt (`current_debt_ceil == 0`), the full-close branch makes the whole amount overpayment and `net_repay = 0`; the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct (`repay.rs:48-52`). `apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` (`repay.rs:32`). `transfer_out` performs a real `token.transfer` from the pool and "does not adjust accounting cash" (`contracts/pool/src/cache/cash.rs:43-53`) — and neither refund path calls `require_reserves` or debits `cash`.

The identical shape exists in `ops::recapitalize::accounting` (`contracts/pool/src/ops/recapitalize.rs:44-67`): `applied = amount.min(backing_shortfall)`, `refund = amount - applied`, then `transfer_out(&payer, refund)` (`recapitalize.rs:34`). Both refunds are derived from a declared amount under the assumption that "the controller transfers `amount` into the pool before this call" (`repay.rs:3`, `recapitalize.rs:4`) — but the pool itself never verifies the inbound transfer happened. The protocol's own test suite pins the flaw: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `client.repay(&payer, &t.ract(0, custody_before))` with **nothing transferred in and no debt**, and asserts the refund "drained custody" (`contracts/pool/tests/flows.rs:3578-3611`).

### Impact Explanation
Theft of user funds / protocol insolvency. Any address that can reach the pool `repay` (or controller `recapitalize`, which is listed as an unprivileged entrypoint) action can declare `amount` up to the pool's token balance on a market with zero outstanding debt (or zero backing shortfall), receive the full declared amount as a "refund" of tokens it never paid, rather than just reclaiming its own transfer. The cash ledger is unchanged, so the book silently desynchronizes from custody — the pool is drained by exactly the refunded amount, and suppliers withdraw against a cash figure that no longer matches reserves. This is the direct analog of the CVE's leak: an edge path (zero debt / zero shortfall) releases a resource (custodied tokens) that was never acquired (no inbound transfer).

### Likelihood Explanation
Reachability depends on whether `pool.repay`/`pool.recapitalize` are gated to the controller. The pool test invokes `client.repay` directly with a fresh `Address::generate` payer and no funding, and there is no `require_auth` or controller check visible in `ops::repay` or `Cache::transfer_out` — indicating the pool entrypoint itself does not enforce pre-funding. Even if direct pool calls are controller-gated, `controller.recapitalize` is an in-scope unprivileged entrypoint and forwards a user-declared amount; the pool-side refund still pays any excess over the shortfall from custody. The trigger conditions are trivial: pick any listed market with `borrowed == 0` (for repay) or no backing shortfall (for recapitalize).

### Recommendation
- Measure the inbound leg instead of trusting the declared amount: snapshot the pool's token balance before/after, or require the caller to pass the measured receipt, so `refund` can never exceed tokens actually received.
- Alternatively, `debit_cash` (or at least `require_reserves`) on the refund and skip the refund entirely when `net_repay == 0` / `applied == 0` and no inbound transfer is proven.
- Tighten the `RepayRoundsToZeroShares` assert so a zero-debt market rejects the leg rather than classifying the whole amount as refundable excess.

### Proof of Concept
```rust
// Pool fixture holds `custody` of `asset` and has zero borrowed debt.
// Attacker calls the pool repay leg directly with no prior transfer in:
let attacker = Address::generate(&env);
let custody = token::Client::new(&env, &asset).balance(&pool);

// resolve_repay: current_debt_ceil == 0 → entire amount is `overpayment`,
// net_repay == 0, so RepayRoundsToZeroShares passes and nothing is burned.
// apply() then executes transfer_out(attacker, custody) — a real token
// transfer paid from supplier custody, with the cash book untouched.
pool_client.repay(&attacker, &PoolAction { /* hub_asset, amount = custody */ });
// token.balance(attacker) == custody; market cash still shows the pre-attack figure.
```
This mirrors the checked-in test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3589-3611`), which asserts `assert_unfunded_refund_drained_custody` after a zero-debt, zero-funding `repay`.

Caveat: I could not fully inspect `contracts/pool/src/lib.rs` entrypoint gating within the iteration budget, so whether the pool restricts `repay`/`recapitalize` callers to the controller is unverified; the reachable variant is `controller.recapitalize`, which forwards a user-declared `amount` to the same unfunded-refund accounting.
