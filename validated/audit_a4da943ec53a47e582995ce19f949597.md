### Title
Text Injection into Prosaic/Arbiter Contract Confirmation Dialogs via Unsanitized `title`/`text` Fields - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` accepts `prosaic_contract_offer`, `prosaic_contract_shared`, `arbiter_contract_offer`/`arbiter_contract_shared`, and `arbiter_dispute_request` messages from any paired correspondent device and stores their `title`/`text` fields with only a presence/type check — no filtering of control characters, bidi override characters, or line-separator characters — before those fields are rendered later in the wallet's contract confirmation/dispute dialogs that gate an irreversible on-chain fund commitment.

### Finding Description
In `wallet.js`, the `prosaic_contract_offer` handler only validates that `title`/`text`/`creation_date` are present and that the contract hash matches, never sanitizing the actual byte content of `title`/`text`: [1](#0-0) 
The same shallow validation pattern (presence + hash check) is used for `prosaic_contract_shared`, `arbiter_contract_shared`, and `arbiter_dispute_request`, which decrypts and reuses `contractContent.title`/`contractContent.text` supplied by a possibly malicious peer without stripping control characters: [2](#0-1) [3](#0-2) 

`prosaic_contract.js`'s `store()`/`createAndSend()` persist `title`/`text` as-is (`title VARCHAR(1000)`, `text TEXT`), with no length trimming of exotic Unicode or removal of RTL/LRO bidi override or line/paragraph separator code points: [4](#0-3) [5](#0-4) 

Contrast this with other message handlers in the same file that at least strip `<>`/enforce length caps (e.g. `wallet_name`, cosigner `name` in `wallet_defined_by_keys.js`), showing the codebase is aware of the need to filter untrusted display strings but doesn't extend that filtering to bidi-override or line-separator characters anywhere, including the contract title/text path: [6](#0-5) 

These `title`/`text` values are subsequently surfaced through the wallet's contract-signing/dispute UI (the confirmation dialog a user reviews before authorizing the shared-address deposit and eventually co-signing a payment unit, per the comments describing "confirm_contract_deposit"/"confirm_contract_sign"/"confirm_contract_claim" flows): [7](#0-6) 

An attacker who is a paired correspondent (or an arbstore acting as arbiter, in the dispute-request path) can embed Unicode bidi override characters (e.g. RLO/LRO) or line/paragraph separator characters in `title`/`text` to visually reorder or reformat the confirmation text — for example making a "You are paying arbiter X 4000 bytes to open contract with attacker" line render as if it referred to a trusted counterparty, or injecting extra fake lines into the dialog — deceiving the user at the moment they approve an on-chain, fund-committing, effectively-irreversible action (funding the shared address and co-signing/paying into the contract).

### Impact Explanation
The forged dialog text is shown immediately before the user authorizes a real value-transfer transaction (posting a unit funding the shared address, or co-signing/claiming through it). A successful spoof can trick the counterparty into signing or funding a payment they would not have otherwise approved, resulting in unauthorized/misdirected spending once the transaction is broadcast and finalized on the DAG — this is analogous to the underlying report's use of text injection to deceive a user into confirming an irreversible action.

### Likelihood Explanation
Any device that a wallet has paired with (a normal, low-privilege trust relationship in Obyte's wallet-pairing model) can trigger this path simply by sending a `prosaic_contract_offer`/`arbiter_contract_offer` or (for arbiters) an `arbiter_dispute_request`. No special network position or privileged role beyond being a paired correspondent/counterparty is required, and the vulnerable fields (`title`, `text`) are exactly the free-form strings a legitimate contract flow requires the peer to supply, making exploitation straightforward.

### Recommendation
Sanitize `title` and `text` (and other free-form peer-supplied display strings such as `my_contact_info`/`peer_contact_info`, party names) before storage and before rendering: strip or reject bidi control characters (U+202A–U+202E, U+2066–U+2069) and line/paragraph separators (U+2028, U+2029, embedded `\r`/`\n` where not expected), similar to the existing `<>` stripping already applied to cosigner/wallet names, and enforce this centrally so the confirmation dialog always renders literal, unambiguous text.

### Proof of Concept
1. Device B pairs with device A (normal wallet pairing).
2. Device B sends `subject: "prosaic_contract_offer"` with `body.title`/`body.text` containing Unicode RLO/PDF bidi-override sequences and a `U+2028` line separator crafted so the rendered dialog text visually reads as an innocuous request (e.g. reordering "Pay attacker 4000 bytes" to appear as "Pay escrow-service 4000 bytes").
3. `wallet.js`'s handler only checks presence/hash of `title`/`text` and forwards to `prosaic_contract.store()`, which persists the string unmodified.
4. When device A's wallet UI later displays the contract for confirmation/signing (via the `confirm_contract_*` events surfaced from `getSigner().sign()`), the spoofed text is rendered as-is, and the user may approve funding/co-signing the shared address believing it matches the intended counterparty/purpose.

function store(objContract, cb) {
	var fields = '(hash, peer_address, peer_device_address, my_address, is_incoming, creation_date, ttl, status, title, text';
	var placeholders = '(?, ?, ?, ?, ?, ?, ?, ?, ?, ?';
	var values = [objContract.hash, objContract.peer_address, objContract.peer_device_address, objContract.my_address, true, objContract.creation_date, objContract.ttl, objContract.status || status_PENDING, objContract.title, objContract.text];
	if (objContract.shared_address) {
		fields += ', shared_address';
		placeholders += ', ?';
		values.push(objContract.shared_address);
	}
	fields += ')';
	placeholders += ')';
	db.query("INSERT "+db.getIgnore()+" INTO prosaic_contracts "+fields+" VALUES "+placeholders, values, function(res) {
		if (cb)
			cb(res);
	});
}
