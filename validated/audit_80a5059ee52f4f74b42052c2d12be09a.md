### Title
Terminal escape-sequence injection via unsanitized device-flow `code` in `DisplayCode` - ([File: internal/authflow/flow.go])

### Summary
`AuthFlow`'s `DisplayCode` closure writes the OAuth device-flow `code` value directly to `IO.ErrOut` via `fmt.Fprintf` with `%s`/`cs.Bold(code)`, with no escape-sequence sanitization, even though `code` originates from the HTTP response of whatever host `gh auth login --hostname` points at. This is the exact untrusted-content class the codebase otherwise guards against consistently (gist view, `pkg/cmd/api`, `pr diff`, `repo read-file`), but this call site was missed.

### Finding Description
`AuthFlow` builds an `oauth.Flow` and registers `DisplayCode` as the device-flow callback: [1](#0-0) 

Inside, `code` is written verbatim to `w` (which is `IO.ErrOut`) both via `cs.Bold(code)` in the success/clipboard-copy path and in the fallback path, with no call to any of the codebase's established sanitization primitives (`iostreams.NewUntrusted`, `iostreams.ContainsEscapeSequence`, or the `asciisanitizer` transform). The `code` value comes from the device authorization response of `flow.DetectFlow()` (from the external `github.com/cli/oauth` package), which is fetched from `oauthHost` — a host the CLI does not control when a user runs `gh auth login --hostname <attacker-host>` pointing at a spoofed/malicious enterprise GitHub instance. Nothing in `flow.go` validates or strips control characters from the returned `user_code` before it reaches `cs.Bold(code)` / `fmt.Fprintf(w, ...)`.

This contrasts with the rest of the codebase, which treats any HTTP-response-derived string as untrusted and routes it through sanitization before it reaches a terminal writer, e.g.:
- `pkg/iostreams/untrusted.go`'s `Untrusted.String()` neutralizes ANSI sequences automatically on any `fmt` verb [2](#0-1) 
- `pkg/cmd/gist/view/view.go` explicitly wraps remote gist content in `iostreams.NewUntrusted` before rendering [3](#0-2) 
- `pkg/cmd/api/api.go` refuses non-JSON bodies containing escape sequences unless `--allow-escape-sequences` is passed [4](#0-3) 

`internal/authflow/flow.go`'s `DisplayCode` has none of these protections, so a crafted `user_code` field (e.g. containing OSC/CSI sequences) from an attacker-controlled `--hostname` endpoint is printed raw to the victim's terminal.

### Impact Explanation
This enables terminal UI spoofing during `gh auth login --hostname <attacker-controlled-enterprise-host>`: a crafted `user_code` containing ANSI/OSC escape sequences can rewrite the terminal title, move the cursor, overwrite prior lines, or otherwise forge what appears to be legitimate `gh` output (e.g., faking a "Press Enter" prompt or obscuring the real verification URL) immediately before the genuine `BrowseURL` prompt is shown. This matches a terminal/output-injection class of impact — it can mislead the victim about which URL to visit or what to approve, but does not itself achieve code execution, credential exfiltration, or file write.

### Likelihood Explanation
Requires the victim to explicitly run `gh auth login --hostname` pointing at an attacker-controlled or spoofed enterprise GitHub endpoint that implements the device-flow handshake and returns a malicious `user_code`. This is a real but narrow precondition (attacker must control the destination host, which the victim must be tricked into using), consistent with the "victim points gh at attacker-controlled endpoint" scenario allowed by the rules.

### Recommendation
Sanitize `code` (and any other server-supplied string surfaced by `DisplayCode`) before printing, mirroring the pattern used elsewhere in the codebase — e.g., wrap it with `iostreams.NewUntrusted(code)` (which sanitizes automatically on `%s`/`%v`/`Sprint`) or run it through the `asciisanitizer` transform / `iostreams.ContainsEscapeSequence` check before formatting into `cs.Bold(code)`.

### Proof of Concept
```go

func TestDisplayCode_SanitizesEscapeSequences(t *testing.T) {
    ios, _, _, errBuf := iostreams.Test()
    maliciousCode := "1234\x1b]0;HIJACKED TITLE\x07-5678"

    // Simulate the DisplayCode closure body from AuthFlow with isCopyToClipboard=false
    cs := ios.ColorScheme()
    fmt.Fprintf(ios.ErrOut, "%s First copy your one-time code: %s\n", cs.Yellow("!"), cs.Bold(maliciousCode))

    assert.NotContains(t, errBuf.String(), "\x1b",
        "escape sequence from server-supplied device code leaked into terminal output")
}
```
Expected today: this assertion **fails**, because `flow.go` line 58 formats `code` with no sanitization, so the raw ESC byte reaches `w`. A fix (wrapping `code` in `iostreams.NewUntrusted` or applying the `asciisanitizer`) should make the assertion pass.
