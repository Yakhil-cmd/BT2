### Title
Cross-organization webhook forgery: signature verified against one organization's secret while the write path acts on a `repository.full_name` from a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate `X-Hub-Signature` against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every downstream `Handler` (e.g. `PushHandler`, `PullRequest::OpenedHandler`) instead resolves the target `Repository`/`Stack` from an entirely separate field, `payload.dig('repository', 'full_name')`. Nothing in the engine enforces that `repository.owner.login` and the owner encoded in `repository.full_name` refer to the same organization/secret used for verification.

### Finding Description
The binding that should hold is:

`organization whose webhook_secret authenticated the request == owner of the repository the handler subsequently creates commits/stacks/syncs for`

Verification path: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Write/dispatch path (independent of `repository_owner`): [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` simply splits `owner/name` from `full_name` and looks up a `Repository` record: [4](#0-3) 

`PushHandler` then syncs commits for whatever stacks belong to that repository: [5](#0-4) 

Because Shipit supports multiple GitHub organizations (`Shipit.github_organizations`, `Shipit.github(organization:)`), each configured with its own `webhook_secret` in secrets, `repository_owner` (used only to pick the verification key) and `repository.full_name` (used to pick the actual target repository) are two independently attacker-controlled fields inside the same JSON body. An attacker who legitimately controls one onboarded organization/repo (and thus can produce a validly-signed webhook payload using that organization's real `webhook_secret`, e.g. via a real push/PR event from their own repo) can craft a payload where `repository.owner.login`/`organization.login` names their own org (so `verify_webhook_signature` succeeds against their own real secret) while `repository.full_name` names a **different** organization's repository that is also managed by this Shipit instance. `verify_signature` only checks the HMAC against the body bytes and the chosen org's secret — it never checks that the two owner fields agree.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding explicitly called out as an in-scope analog. A validly-authenticated webhook belonging to organization A can be used to trigger `PushHandler`/`GithubSyncJob`/`ReviewStackAdapter` (create/close/label PRs, provision review stacks, run continuous delivery sync) writes against organization B's `Stack`/`Repository` records, resulting in cross-repository writes/unauthorized state changes purely from crafting request bodies — satisfying the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Requires that: (1) the Shipit deployment is configured for multiple GitHub organizations (a documented, supported configuration via `secrets.github` per-org keys), and (2) the attacker already controls one legitimately onboarded organization/repository in that same instance (enough to generate a genuinely-signed webhook, e.g. by pushing to their own repo which GitHub signs and delivers). This is a real but non-trivial prerequisite — it is not exploitable by a fully external, uninvolved GitHub user, only by a tenant that is already integrated with the same multi-org Shipit deployment. Likelihood is therefore moderate: plausible in real multi-tenant setups but not universally exploitable.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, and in `Shipit::Webhooks::Handlers::Handler#repository_name`, cross-check that the owner used to select the verification secret is the same owner embedded in `repository.full_name` (and in `organization.login` when present) before dispatching to handlers; reject the webhook otherwise. Alternatively, bind webhook secrets per-repository (not per top-level org config lookup) so the verified secret cannot be reused to sign payloads referencing another organization's repositories.

### Proof of Concept
1. Shipit is configured with two GitHub App orgs, `org-a` and `org-b`, each with its own `webhook_secret` (`Shipit.github_app_config`).
2. Attacker controls a real repository under `org-a` onboarded to this Shipit instance and can trigger a genuine `push` webhook from GitHub (organically signed with `org-a`'s secret) — but crafts/replays a POST to `/webhooks` where:
   - `X-Github-Event: push`
   - body: `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/target-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"}`
   - `X-Hub-Signature`: HMAC-SHA1 computed with `org-a`'s webhook secret over this exact body (attacker can compute this because they legitimately possess `org-a`'s secret via their own valid webhook deliveries/replay, or by controlling `org-a`'s webhook config).
3. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully since the signature matches `org-a`'s secret over the exact bytes sent.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")`, which is unrelated to `org-a`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `org-b`'s stack — a write performed on another organization's repository authenticated only by `org-a`'s credentials.
