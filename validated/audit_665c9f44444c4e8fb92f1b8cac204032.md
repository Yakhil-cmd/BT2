### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized PR merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub `status` event to using only the SHA, with no filter on the repository/organization that the verified webhook came from. An attacker who owns any GitHub repository (and can therefore legitimately sign a `status` webhook for it via GitHub) can push a byte-identical copy of a victim's PR head commit (obtained by simply fetching it, since git commit objects are content-addressed and public) into their own repo, then set a `success` status on that SHA. Shipit will apply that status to *every* `Commit` row across *every* stack sharing that SHA, including the victim's, which can drive `ProcessMergeRequestsJob` to merge a pending PR that never actually passed its own repo's checks.

### Finding Description
The binding that must hold is:

`organization/repository that authenticated the 'status' webhook (verified via Shipit.github(organization: repository_owner).verify_webhook_signature) == organization/repository that owns the Commit record the status is attached to`

This binding is **not enforced**. `StatusHandler#process` is:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike other handlers, `StatusHandler` does not call the base `Handler#stacks` helper that scopes by `Repository.from_github_repo_name(repository_name)`; it queries `Commit` globally by `sha` alone, with the incoming `params.repository` field (used only for signature verification/logging) completely ignored for the write. Every commit row in the `commits` table across every stack in the Shipit installation that happens to share that SHA gets a new `Status` created for it.

Because `Commit.sha` is a git SHA1 of content the attacker fully controls the reproduction of (they can `git fetch` any public commit and `git push` the identical object to their own repository — git object hashes are content-addressed, so pushing the exact byte-identical commit to a different remote yields the identical SHA), the attacker does not need a cryptographic collision, only a copy of a target commit's git object graph.

Exploit flow:
1. Victim stack has `merge_queue_enabled?` true, `merge_status == 'success'`, and a pending `MergeRequest` whose `head` commit has `mergeable` true/non-false but has not yet passed CI (`all_status_checks_passed?` false).
2. Attacker forks/mirrors the victim's public PR branch into a repository they own (`attacker/decoy`), preserving the identical commit SHA.
3. Attacker (or GitHub, on their behalf) creates a `status` event on `attacker/decoy` for that SHA with `state: success`. GitHub signs this webhook with `attacker/decoy`'s own organization's webhook secret — a secret the attacker's own org possesses. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` is read from the payload's `repository.owner.login`, i.e., the attacker's own org, so the signature check passes on the attacker's own credentials. [2](#0-1) 
4. `StatusHandler.call` runs and, via the unscoped `Commit.where(sha:)` query, attaches a `success` `Status` to the victim's commit row too. [3](#0-2) 
5. `Commit#create_status_from_github!` -> `add_status` detects the state transition to `success` and calls `stack.schedule_merges` (on the victim's stack), which enqueues `ProcessMergeRequestsJob`. [4](#0-3) 
6. `ProcessMergeRequestsJob#perform` iterates the victim stack's pending merge requests, calls `merge_request.refresh!`, checks `merge_request.all_status_checks_passed?` — now true because of the forged success status — and calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request` using the victim stack's/organization's own GitHub App credentials. [5](#0-4) [6](#0-5) [7](#0-6) 

Existing guards do not prevent this: `verify_signature` only validates that the sender legitimately owns *some* repository/org — it never checks that the `repository.full_name` in the payload matches the repository that owns the target `Commit`/`Stack`. `all_status_checks_passed?` only inspects `Status`/`CheckRun` rows already present on the `head` commit — it has no way to know those rows were forged by an unrelated repository. `Handler#stacks`/`repository_name` scoping exists in the base class but `StatusHandler` bypasses it entirely by querying `Commit` directly.

### Impact Explanation
An attacker who owns any GitHub repository can force a merge of a pull request on a victim stack of their choosing, using the victim repository's own GitHub API credentials, without that PR ever passing its own required status checks. This is a cross-tenant write: a payload authenticated for one repository ("attacker/decoy") mutates another repository's/stack's data (`Status`, `MergeRequest`) and triggers an unauthorized merge action against GitHub — matching the "Critical: a payload for one repository mutating another's stack... or an unauthorized deploy, rollback or merge" category. Blast radius: any stack in the Shipit instance with the merge queue enabled and a pending mergeable PR is vulnerable; the attack is repeatable against arbitrary victim stacks/organizations as long as the attacker can reproduce the target commit's SHA (trivial for any public commit) and control a `status` event pointing at it.

### Likelihood Explanation
Preconditions on the victim side: `merge_queue_enabled?` true, `merge_status == 'success'`, a pending `MergeRequest` whose `mergeable` is not `false` (i.e., not yet known-conflicting) and that hasn't independently passed CI yet — all realistic configurations for teams using Shipit's merge queue feature. Attacker cost is low: own or control any GitHub repository (free), fetch/push a public commit object, and either wait for GitHub to naturally emit a `status` event for it (e.g., by connecting a CI integration to `attacker/decoy`) or otherwise cause one to be created and delivered to Shipit's webhook endpoint. No Shipit credentials, sessions, or secrets are required. This is straightforwardly repeatable.

### Recommendation
Scope `StatusHandler#process` (and any similar handler) to only update commits belonging to the stack(s) whose repository matches the webhook's authenticated `repository.full_name`, mirroring the `Handler#stacks`/`Repository.from_github_repo_name` pattern used elsewhere, e.g.:

```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

This enforces the binding that a status can only be written for commits that belong to the repository that authenticated the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "does not attach a status to a commit belonging to a different repository" do
          victim_stack = shipit_stacks(:shipit) # merge_queue_enabled, merge_status == success
          merge_request = shipit_merge_requests(:shipit_mergeable_pending_ci) # pending, mergeable, CI not yet passed
          victim_commit = merge_request.head

          decoy_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/forged',
            'repository' => { 'full_name' => 'attacker/decoy', 'owner' => { 'login' => 'attacker' } }
          }

          Shipit.github.api.expects(:merge_pull_request).never

          assert_no_difference -> { victim_commit.statuses.count } do
            StatusHandler.call(decoy_payload)
          end

          refute merge_request.reload.all_status_checks_passed?
        end
      end
    end
  end
end
```
Assertions to make on both sides of the binding: before, `victim_commit.stack.id != Repository.from_github_repo_name('attacker/decoy')&.stacks&.pluck(:id)` (i.e., decoy repo does not own the victim stack); after running `StatusHandler.call(decoy_payload)` on current code, `victim_commit.statuses.count` increases by 1 and `merge_request.all_status_checks_passed?` becomes `true`, and (per `test/models/commits_test.rb` pattern showing `ProcessMergeRequestsJob` is enqueued on success transition) `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack])` fires, followed by `Shipit.github.api.expects(:merge_pull_request)` being satisfied when `ProcessMergeRequestsJob.new.perform(victim_stack)` runs — demonstrating the unauthorized merge.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
