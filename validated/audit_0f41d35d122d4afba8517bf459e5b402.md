### Title
Cross-organization team ID collision in `MembershipHandler#find_or_create_team!` grants authorization escalation into `Shipit.github_teams` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` record solely by `github_id`, with no check that the payload's `organization.login` matches the organization already stored on that `Team`. Because Shipit supports independent GitHub App configurations per organization — including separate GitHub Enterprise domains with their own team-ID counters — an attacker who administers their own org/installation can cause a genuinely GitHub-signed `membership` webhook for their org to resolve to a pre-existing privileged `Team` row belonging to a different organization, and add themselves as a member of it.

### Finding Description
The broken binding: `Team.find_or_create_by!(github_id: params.team.id).organization == params.organization.login` must hold, but the code never checks it.

```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [1](#0-0) 

`find_or_create_by!` first performs `find_by(github_id: …)`; the block (which sets `organization`) only runs on creation, never on an existing match. If a `Team` row with that `github_id` already exists — regardless of which organization it belongs to — that row is returned unmodified, and `process` then calls `team.add_member(member)` on it [2](#0-1) , which appends a `Membership` row [3](#0-2) .

Signature verification is performed per-organization against that organization's own configured `webhook_secret`: `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the HMAC against that org's secret [4](#0-3) . This means a webhook that GitHub genuinely signs for Org B's own installation will pass verification for Org B, entirely independent of Org A's `Team` rows or secrets — there is no cross-org check here either.

`GitHubApp` configuration supports a distinct `domain` per organization (used for GitHub Enterprise installations), documented as "The domain name of your GitHub Enterprise instance" [5](#0-4) [6](#0-5) . Team IDs are only guaranteed globally unique within a single GitHub instance's own ID namespace; when Shipit is configured against multiple independent GitHub instances (e.g. one org on github.com and another on a self-hosted GitHub Enterprise Server, or two separate GHE instances), team IDs are not coordinated across those namespaces and can coincide, and an attacker administering their own GHE instance can deliberately create teams to land on a specific numeric ID.

`Shipit.github_teams` builds the privileged team list from configuration [7](#0-6) , and `User#authorized?` grants Shipit access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) , so the injected `Membership` row is sufficient to grant full application access via `force_github_authentication` [9](#0-8) .

### Impact Explanation
An attacker who controls a genuinely separate GitHub organization/installation (particularly on a separately-scoped GitHub Enterprise instance) can obtain full authenticated access to the entire Shipit application — including deploys, rollbacks, and merges across all repositories — without ever being a member of the actual privileged team in Org A. This is a Critical authentication-bypass class issue: the entire authorization model rests on `Membership` rows keyed off `github_id` collisions that are not validated against the originating organization. Blast radius is application-wide, not scoped to a single stack.

### Likelihood Explanation
Exploitation requires a multi-tenant Shipit deployment where at least one configured organization runs its own independent GitHub instance (a GitHub Enterprise Server) with an ID namespace not coordinated with the target organization's — a configuration this engine explicitly documents and supports via the per-org `domain` setting. On a single shared github.com namespace, GitHub's own globally-unique sequential team IDs make deliberate collision infeasible for an unprivileged attacker, since IDs already assigned to Org A's team can never be reissued. The vulnerability is real code-level negligence (missing organization check) but its exploitability depends entirely on this specific multi-instance deployment topology.

### Recommendation
Scope the lookup by both `github_id` and `organization`: `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and reject/raise if a `Team` with that `github_id` exists under a different organization, rather than silently reusing it.

### Proof of Concept
```ruby
test "membership webhook cannot bind to a team of a different organization with colliding github_id" do
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify'

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: 'Evil Team', slug: 'evil-team', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } }
  }

  assert_no_difference -> { privileged_team.memberships.count } do
    post :create, body: payload.to_json, as: :json
  end

  refute Shipit::Team.find(privileged_team.id).members.exists?(login: 'attacker')
end
```
Binding assertion: before the request, `Team.find_by(github_id: privileged_team.github_id).organization == 'shopify'`; after a webhook genuinely signed and delivered for `attacker-org`, the same query must still equal `'shopify'`, and no `Membership` for `attacker`/privileged_team should exist. With the current unpatched code this assertion fails.
