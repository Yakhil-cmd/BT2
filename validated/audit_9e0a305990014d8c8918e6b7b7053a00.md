### Title
Hardcoded sBTC token literal in mainnet `pox-5.clar` freezes reward/bond funds if sBTC upgrades to a new contract - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar` embeds a fixed `'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token` contract-call literal for its sBTC accounting (balance checks, transfers of earned rewards/bond funds). On mainnet this literal is never rewritten; `make_pox_5_body` only substitutes it for non-mainnet deployments.

### Finding Description
`stackslib/src/chainstate/stacks/boot/mod.rs` shows `make_pox_5_body` returns `POX_5_BODY` unmodified when `is_mainnet` is true, and only performs a string-replace of `SBTC_TOKEN_MAINNET_CONTRACT` for non-mainnet networks: [1](#0-0) 

The corresponding constant is the literal mainnet sBTC contract: [2](#0-1) 

`pox-5.clar` itself contains 34 references to this hardcoded `sbtc-token` contract, used for `get-balance`/`transfer`/`with-ft` calls that gate reward accounting, fee sweeps, and bond/stake balance movement (analogous pattern shown in the test/companion contract `signer-manager.clar`, which performs the same `contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token get-balance ...` / `transfer` pattern): [3](#0-2) 

Separately, the sBTC *registry* contract (used for `get-current-aggregate-pubkey`, which derives the Waterfall reward-set's sBTC deposit recipient key) is configurable per-network via `pox_5_sbtc_registry_contract`, but is fixed to the canonical mainnet address on mainnet: [4](#0-3) [5](#0-4) 

This mirrors exactly the bug class in the referenced report: an on-chain contract (`pox-5`, playing the role of `VoterProxy`/staker-facing contract) has a hardcoded dependency on an external token/registry contract address baked into its Clarity source at consensus/boot-code level, with no upgrade mechanism. Unlike the Angle case, where the underlying LP token/gauge pair could be swapped by governance, here the sBTC ecosystem contract address is fixed for the *entire lifetime of mainnet pox-5*, because boot-code contracts are deployed once at the Epoch 4.0 boundary and are not upgradable — the only way to point pox-5 at a new sBTC contract would be a consensus-breaking hard fork that rewrites `POX_5_BODY`/`SBTC_TOKEN_MAINNET_CONTRACT` and redeploys.

### Impact Explanation
If the sBTC protocol ever migrates its token or registry contract to a new address (contract upgrade, security migration, sBTC v2, etc. — an established real-world pattern for such protocols, as cited in the underlying report for Angle gauges), every pox-5 function that calls the old, now-stale `sbtc-token`/`sbtc-registry` address would either:
- Read a balance of `0` (since real sBTC now lives in the new contract), breaking reward computation and refund sweeps for legitimately earned sBTC.
- Fail all transfers to stakers/signers, since the funds are not held by the hardcoded contract anymore.
- Freeze staking/bond flows that depend on a successful sBTC leg (`register-for-bond`, `stake`, `claim-rewards`) since a failed sBTC call would cause the whole transaction to abort, even though the underlying STX-lock logic in `pox-locking/src/pox_5.rs` is otherwise sound.

This is a **temporary/permanent freezing of staked funds and sBTC rewards** condition: STX locked via `pox-locking`'s `pox_lock_v5`/`pox_rollover_v5` remains locked (per `pox-locking/src/pox_5.rs` handlers), but the sBTC reward/refund/claim legs that are hardwired to the stale contract become permanently unreachable without a hard fork, matching the "permanent freezing of staked STX or sBTC" / "temporary freezing of staked funds" categories.

### Likelihood Explanation
Likelihood is analogous to the original finding: this requires an external event (the sBTC protocol changing its deployed token/registry contract), not an on-chain attacker action, so it is not attacker-triggerable at will. However, it is realistic given that sBTC is itself an actively evolving, externally governed system, and the report explicitly documents this exact class of incident occurring for a comparable veToken protocol. The node-config knob (`pox_5_sbtc_contract`/`pox_5_sbtc_registry_contract`) exists precisely because this was anticipated for non-mainnet — but the mainnet path is intentionally immutable, meaning any real migration requires a coordinated hard fork rather than an in-protocol upgrade path.

### Recommendation
Introduce an indirection layer analogous to the report's recommended "upgradable intermediate contract": rather than hardcoding the sBTC token/registry principal as a literal inside `pox-5.clar`, reference it through a small trait-based or `define-data-var`-backed pointer contract that can be repointed (subject to appropriate governance/consensus rules) if the sBTC deployment migrates, without requiring a full pox-5 boot-code hard fork. At minimum, document and test the hard-fork procedure needed to redeploy pox-5 with an updated `SBTC_TOKEN_MAINNET_CONTRACT`/`SBTC_REGISTRY_MAINNET_CONTRACT`, verifying that in-flight locked funds (per `pox-locking/src/pox_5.rs`) can be migrated/unlocked without loss.

### Proof of Concept
Conceptual sequence (network-level, not an on-chain attacker action):
1. sBTC protocol governance deploys a new `sbtc-token`/`sbtc-registry` contract and migrates real sBTC balances/minting rights to it (as happened to Angle's gauge in the cited report).
2. `pox-5.clar` on Stacks mainnet still calls the old, now-inert `SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token` per `make_pox_5_body`'s mainnet no-op path [6](#0-5) .
3. Any staker call into pox-5 functions that read/transfer sBTC (`claim-rewards`, `register-for-bond`, fee-refund sweeps) either reads a stale zero balance or fails the `transfer`, aborting the whole stacking transaction.
4. STX remains locked (per `pox_lock_v5`/`pox_rollover_v5` in `pox-locking/src/pox_5.rs`), and legitimately earned sBTC rewards become permanently unreachable through pox-5 until a consensus-level hard fork redeploys pox-5 pointing at the new sBTC contract.

/// `(contract-call? <X> ...)` for *literal* contract principals — not for
/// `define-constant`s — and pox-5 has read-only functions that call the
/// sBTC token's `get-balance`.
pub fn make_pox_5_body(is_mainnet: bool) -> String {
    if is_mainnet {
        return POX_5_BODY.to_string();
    }
    let sbtc_contract = pox_5_sbtc_contract(is_mainnet);
    let bond_admin = pox_5_bond_admin(is_mainnet);
    let pause_admin = pox_5_pause_admin(is_mainnet);
    POX_5_BODY
        .replace(SBTC_TOKEN_MAINNET_CONTRACT, &sbtc_contract.to_string())
        .replacen(
            &format!("(define-data-var bond-admin principal '{POX_5_BOND_ADMIN_MAINNET})"),
            &format!("(define-data-var bond-admin principal '{bond_admin})"),
            1,
        )
        .replacen(
            &format!("(define-data-var pause-admin principal '{POX_5_PAUSE_ADMIN_MAINNET})"),
            &format!("(define-data-var pause-admin principal '{pause_admin})"),
            1,
        )
}

pub fn pox_5_sbtc_contract(is_mainnet: bool) -> QualifiedContractIdentifier {
    if is_mainnet {
        return SBTC_TOKEN_MAINNET_CONTRACT_ID.clone();
    }
    let contract_id = POX_5_SBTC_CONTRACT.read().unwrap().clone();
    if let Some(contract_id) = contract_id {
        contract_id
    } else {
        SBTC_TOKEN_TESTNET_CONTRACT_ID.clone()
    }
}

/// Epoch 4.0 / PoX-5 scaffolding: the sBTC registry contract that signer-set

/// per-cycle sBTC waterfall recipient. Not substituted into the pox-5

/// Set once at node startup from `NodeConfig::pox_5_sbtc_registry_contract`.

    RwLock::new(None);

    *POX_5_SBTC_REGISTRY_CONTRACT.write().unwrap() = contract_id;

        contract_id
    } else {
        SBTC_REGISTRY_TESTNET_CONTRACT_ID.clone()
    }
