This confirms the multi-organization GitHub App configuration model: `Shipit.github(organization:)` looks up a per-organization config keyed under `secrets.github`, each with its own independent `webhook_secret` [1](#0-0) . ### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while event processing is bound to `repository.full_name`, allowing cross-tenant/cross-repository forgery in multi-organization GitHub App deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify the `X-Hub-Signature` against based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . Once the signature is accepted, the full raw JSON payload is dispatched unchanged to the registered handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Handlers (e.g. `PushHandler`) determine which `Repository`/`Stack` to act on using a completely different field: `payload.dig('repository', 'full_name')` [4](#0-3) [5](#0-4) .

This is structurally analogous to the reported `pathLengthFromKey` bug: a precondition/binding (`numLeaves` is a power of two — here, "the organization that signed equals the organization whose repository is written to") is silently assumed but never actually enforced by the code, and nothing prevents the two values from diverging.

### Finding Description
Shipit supports hosting multiple independent GitHub Apps/organizations from a single instance, each with its own `webhook_secret`, keyed by organization name in `secrets.github` [6](#0-5) . `Shipit.github(organization:)` fetches the config and raises `GithubOrganizationUnknown` only if the organization key itself is not configured on the instance [7](#0-6) .

An attacker who legitimately administers *any* one organization configured on the shared instance (e.g. they can configure that org's GitHub webhook and thus know/control that org's `webhook_secret`) can craft an arbitrary webhook payload where:
- `repository.owner.login` (or `organization.login`) = their own organization ("A") — used only to select which secret verifies the signature.
- `repository.full_name` = a **different** organization/repository ("B/victim-repo") — used by the handler to look up the target `Stack`.

They sign the payload with organization A's real `webhook_secret` (which is valid and passes `verify_webhook_signature`), then POST it. `verify_signature` passes because it only checks the HMAC against org A's secret and never checks that `repository.owner.login` matches `repository.full_name`'s owner. The handler then acts on organization B's stack using attacker-controlled data (e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack whose branch matches [8](#0-7) ).

### Impact Explanation
This breaks the trust boundary between tenants/organizations sharing one Shipit deployment: an entity that is only authorized to speak for organization A can force webhook-driven side effects (triggering sync jobs, GitHub sync with an attacker-chosen `expected_head_sha`, membership/team changes via the `membership` handler, pull-request state changes, etc.) against organization B's repositories/stacks, which they have no legitimate relationship to. This matches "cross-repository writes" / unauthorized action categories, since GitHub-sourced signed events for org B's stack can be forged using org A's credentials.

### Likelihood Explanation
Requires the deployment to be configured with the multi-organization GitHub App schema (multiple orgs sharing one Shipit instance) and requires the attacker to control a legitimately configured organization's `webhook_secret` on that instance — a real, supported configuration per `docs/setup.md` and `config/secrets.development.example.yml`'s commented multi-org example [9](#0-8) . No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is needed.

### Recommendation
In `verify_signature`, after selecting the GitHub App by `repository_owner`, additionally verify that the owner used for app/secret selection matches the owner embedded in every repository-scoped field the handlers will subsequently trust (or, simpler, have handlers derive their target repository from the same `repository_owner` value already validated, rather than independently re-reading `repository.full_name`).

### Proof of Concept
1. Instance is configured with `secrets.github` containing two orgs: `orgA` (attacker-administered, webhook secret known to attacker) and `orgB` (victim, has a Shipit `Stack`).
2. Attacker builds a `push` webhook JSON payload with `"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}`, `"ref": "refs/heads/main"`, `"after": "<attacker-chosen-sha>"`.
3. Attacker computes `sha1=HMAC(orgA_webhook_secret, payload)` and sets it as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`. `repository_owner` resolves to `orgA`, `Shipit.github(organization: 'orgA')` succeeds, and `verify_webhook_signature` passes because the signature was computed correctly with `orgA`'s secret [10](#0-9) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('orgB/victim-repo')` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on the victim's `main` branch stack, forged entirely with organization A's credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
