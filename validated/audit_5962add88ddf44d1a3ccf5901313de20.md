### Title
Signature verification is scoped to `repository.owner.login`, but the actual repository acted upon is resolved from the independent, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . However, the actual event handlers (e.g. `PushHandler`) resolve the target repository/stack from a *different* JSON field in the same attacker-controlled body: `payload.dig('repository', 'full_name')` [3](#0-2) . These two fields are never cross-checked, so the organization whose secret authenticated the request is not guaranteed to be the organization whose repository is actually mutated.

### Finding Description
This mirrors the report's root cause class: a value is validated/trusted implicitly under one assumption, and a related but distinct value is used for the security-sensitive action, without a check binding the two together. In the original report, `_callERC20Token`/`delegatecall` implicitly trusted `success == true` for a call target that might not exist; here, `verify_signature` implicitly trusts that `repository.owner.login` represents the organization of the repository that will be synced, but the code that actually performs the write (`Handler#repository_name` / `Repository.from_github_repo_name`) reads `repository.full_name` instead [3](#0-2) .

Both `repository.owner.login` and `repository.full_name` are attacker-supplied JSON keys inside the same raw POST body (`request.raw_post`) [4](#0-3) . Nothing in `verify_signature` or in `Handler` enforces that the owner segment of `full_name` matches `repository.owner.login`. Additionally, `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank/not configured for the resolved organization: `return true unless webhook_secret` [5](#0-4) . In a multi-organization Shipit deployment (as documented in `config/secrets.development.example.yml`, which supports per-org `github:` blocks each with its own optional `webhook_secret`) [6](#0-5) , an attacker who knows (or targets) an organization entry with no `webhook_secret` configured can:

1. Send a webhook whose `repository.owner.login` == that unsecured organization → `verify_signature` passes trivially (any/no signature accepted).
2. Set `repository.full_name` == `victim-org/victim-repo`, which is unrelated to `repository.owner.login`.
3. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(repository_name)` using the forged `full_name`, locating the victim's real `Repository`/`Stack` records and calling `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) .

The equality that should hold but does not: `organization_that_authenticated_the_request == organization_owning_the_repository_that_is_written`. Before the attack, these are assumed equal by design (a valid GitHub webhook signed with org A's secret is assumed to only describe org A's repositories); after the attack, `verify_signature` authenticates org A (the unsecured/known-secret org) while the handler acts on org B's repository.

### Impact Explanation
`StatusHandler` similarly trusts `params.sha`/`params.state` without any repository binding at all - it looks up commits globally by `sha` and calls `commit.create_status_from_github!(params)` [8](#0-7) , meaning once signature verification is bypassed via the unsecured-org path, an attacker can inject arbitrary CI status states for any known commit SHA across any stack in the instance, which can be used to satisfy deploy-gating conditions. Combined with `PushHandler`, an attacker can also force out-of-band `sync_github` operations against a victim's stack. This crosses the "escalation into repository state" boundary described in the impact rubric (unauthenticated influence over stack/commit state), though it stops short of directly producing a `GITHUB_TOKEN`/`api_clients_secret` exfiltration or an unauthorized deploy by itself — it requires either a misconfigured (secret-less) org entry or knowledge of another org's `webhook_secret`, and further requires the victim repository to already be registered in the target Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, (2) at least one configured organization with a blank/absent `webhook_secret` (an explicitly supported, documented configuration in `secrets.development.example.yml`) or knowledge of a legitimate `webhook_secret` for some org, and (3) the victim organization's repository being registered as a `Repository`/`Stack` in the same instance. This is a plausible but non-default misconfiguration-dependent scenario, not a zero-precondition exploit.

### Recommendation
Bind the field used for signature-organization selection to the field used for the actual write: verify that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers, or better, derive `repository_owner` from `full_name` directly rather than from an independent field, and remove the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`, instead treating a missing configured secret as "reject" for orgs/repos with any pre-existing `Stack`.

### Proof of Concept
1. Configure Shipit with two orgs in `github:` — `attacker-org` (no `webhook_secret` set) and `victim-org` (has a registered `Stack` for `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<any known sha>"
}
```
with no valid `X-Hub-Signature` (or a garbage one).
3. `verify_signature` resolves `github_app = Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the signature header [9](#0-8) .
4. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"victim-org/victim-repo"`, matching the real victim `Repository`, and triggers `stack.sync_github` on it [7](#0-6) , even though the request was never authenticated by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
