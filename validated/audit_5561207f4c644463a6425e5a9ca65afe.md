### Title
Webhook signature validated against `repository.owner.login`'s org secret, but handlers act on the unvalidated `repository.full_name` field — organization-authenticated ≠ repository-written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify the payload against using `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')`). Once the signature check passes, the *entire* raw payload is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and each handler (e.g. `PushHandler`, `MembershipHandler`) independently re-reads repository/organization identifiers from the same payload (`payload.dig('repository', 'full_name')`, `params.organization.login`) to decide which `Stack`/`Team`/`Repository` record to mutate — without ever re-checking that these values match the organization whose secret validated the signature.

### Finding Description
The equality the system is supposed to enforce is:

```
organization whose webhook_secret authenticated the request == organization/repository the handler writes to
```

In `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`), the org used to choose the HMAC secret is:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

and
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

Once this passes, `create` dispatches the raw parsed body to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

`Handler#stacks`/`#repository_name` then pick the target `Repository`/`Stack` from a *different* JSON field — `repository.full_name` — with no cross-check against `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process` then triggers a resync of any matching, non-archived stacks on the parsed branch:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

`MembershipHandler#process` independently trusts `params.organization.login` (a top-level payload field, not `repository.owner.login`) to create/attach a `Team`, and adds the named `member` to it:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [6](#0-5) 

Because `Shipit.github_teams` (used for the `force_github_authentication` authorization gate) is built directly from these `Team` records via `Shipit.github_teams`/`Team.find_or_create_by_handle`, and `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb` checks `current_user.authorized?` against `Shipit.github_teams`, corrupting or fabricating team membership through a forged-but-signature-valid webhook is a direct path to unauthorized authorization escalation. `github_teams` is computed as:
```ruby
def github_teams
  @github_teams ||= github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }
end
``` [7](#0-6) 

**Attack shape:** an attacker who legitimately controls (or is a maintainer with webhook-triggering rights on) some GitHub organization/repo **A** that is configured in this Shipit instance's `secrets.yml` (i.e., they can get GitHub to sign a webhook with org A's `webhook_secret` — e.g. via a `membership` event on a repo they administer in org A) can shape the JSON body's `organization.login`/`repository.full_name` fields to reference an unrelated, victim organization **B** also configured in the same instance. `repository_owner` (`repository.owner.login`) is used purely to select which secret validates the HMAC; nothing forces `organization.login` or `repository.full_name` used deeper in the handler to equal that same value. The signature only proves "GitHub, on behalf of org A, sent this exact byte stream" — it says nothing about which org/repo identifiers *inside* that stream are authoritative once dispatched to handlers.

This is a direct analog of the reported bug class: a value used to authorize/gate the operation (webhook_secret keyed by `repository_owner`) is disconnected from the value actually acted upon (`repository.full_name` / `organization.login`), just as in Deriverse the seat price used to gate acceptance (calculated at submission time) was disconnected from the price actually applied at execution.

### Impact Explanation
If multiple GitHub organizations are configured on one Shipit instance (a documented, supported configuration — `config/secrets.development.shopify.yml` shows exactly this multi-org schema), an attacker with legitimate/self-controlled webhook delivery in one configured org can forge `membership` payloads that are valid (correctly signed) for their own org but declare `organization.login` of a victim org, letting them fabricate `Team` records or add arbitrary GitHub logins as members of a `Team` object tied to the victim organization's handle. Since `Shipit.github_teams` authorization gates which users may operate the app at all (`app/controllers/concerns/shipit/authentication.rb`), this is escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-severity impacts. Similarly, `PushHandler`/`repository_name` mismatch lets an org-A-signed push event trigger `sync_github` against stacks belonging to org B's repositories.

### Likelihood Explanation
Requires: (1) the deploying organization to configure more than one GitHub org/app in `secrets.yml` (supported and documented), and (2) attacker control over triggering a webhook delivery signed by one of those orgs' secrets (achievable by anyone who can cause GitHub to fire a `membership`/`push` webhook for a repo/org they have access to, without needing any Shipit credentials). This is a realistic, unprivileged-from-Shipit's-perspective attack path, though it depends on the multi-org deployment topology being in use.

### Recommendation
After `verify_signature` succeeds, handlers must re-derive and enforce that every organization/repository identifier used to select records (`repository.full_name`, `organization.login`, `repository.owner.login`) is internally consistent with each other and with the `repository_owner` value that selected the verifying secret, rejecting the webhook (422) if they diverge. Concretely, thread the verified `repository_owner` into `Handler#call`/`#process` and assert `payload.dig('organization','login') == repository_owner` and `repository_name.split('/').first == repository_owner` (case-insensitively) before any lookup/mutation.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` schema).
2. As an admin of a repo in `orgA`, trigger (or replay) a `membership` webhook whose JSON body is crafted so that:
   - `repository.owner.login` (or top-level `organization.login` used for `repository_owner` fallback) = `"orgA"` — this is what `verify_signature` uses to pick `orgA`'s secret, and GitHub will correctly sign it with `orgA`'s secret since it originated from an `orgA` event.
   - The `organization.login` field consumed by `MembershipHandler` (a separate JSON key) = `"orgB"`.
   - `member.login` = attacker's own GitHub login.
3. POST this correctly-signed-for-orgA payload to `/webhooks`. `verify_signature` passes (signed with `orgA`'s secret, matched via `repository_owner == "orgA"`).
4. `MembershipHandler#process` executes `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` using the `orgB` value, then calls `team.add_member(member)`, attaching the attacker's GitHub identity to a `Team` object representing `orgB`.
5. If `orgB`'s handle is included in `Shipit.github_teams`, the attacker's user now satisfies `current_user.authorized?` for `orgB`-gated stacks despite never having been vetted by `orgB`.
