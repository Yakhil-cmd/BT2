### Title
SQL Injection via Unescaped Numeric `value` in System Vote Processing - (File: main_chain.js)

### Summary
`saveSystemVote()` in `main_chain.js`, invoked when a `system_vote` message becomes part of a stable unit, builds an `INSERT INTO numerical_votes ...` statement by directly interpolating the attacker-controlled `value` field into the SQL string instead of passing it as a bound parameter, unlike every other field in the same statement which is safely escaped with `db.escape()`. [1](#0-0) 

### Finding Description
`system_vote` is an application (`app: 'system_vote'`) that any unit author can include in a posted unit. Once the unit stabilizes, `markMcIndexStable()` iterates stable messages and calls `saveSystemVote(payload)` for each `system_vote` message: [2](#0-1) 

Inside `saveSystemVote`, for the numeric subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), the code builds the SQL value list like this:

```js
sqlValues.push(`(${db.escape(unit)}, ${db.escape(address)}, ${db.escape(subject)}, ${value}, ${timestamp})`);
await conn.query("INSERT INTO numerical_votes (unit, address, subject, value, timestamp) VALUES " + sqlValues.join(', '));
``` [3](#0-2) 

`unit`, `address`, and `subject` are escaped with `db.escape()`, but `value` is concatenated raw into the query. This is the same bug class as the Pimcore `CustomReportController` issue: an attacker-supplied field flows unescaped into a SQL string that is executed by the database, while adjacent fields are properly parameterized — an inconsistency that indicates the escaping was simply forgotten for one field.

`value` originates from the unit's message payload (`{ subject, value } = payload`), i.e. it is fully controlled by the unit's author. While earlier validation (in `validation.js`) is expected to enforce that `value` is a JS `number` for these numeric subjects, JSON permits numeric literals such as `1e400`, which `JSON.parse` converts to `Infinity` while `typeof value === 'number'` still holds true. When such a value reaches the template literal, `${value}` renders as the string `Infinity` (or similarly `-Infinity`), which is not valid SQL syntax for a numeric column, causing the `INSERT` statement to fail.

### Impact Explanation
Because `saveSystemVote` runs unconditionally as part of `markMcIndexStable`, which every full node executes to advance main-chain stability, a malformed/invalid SQL statement thrown from this code path breaks the stabilization procedure on any node that processes the unit. Since `saveSystemVote` is `async` and errors are not caught here, this becomes an unhandled rejection/exception during a core consensus operation (advancing MCI stability), which can crash the node process or leave the database transaction in an inconsistent state. If different nodes' SQL engines (SQLite vs MySQL) handle the malformed numeric literal differently (e.g., one throws, another silently coerces), this can also cause **node disagreement on stability**, since some nodes could fail to advance past this MCI while others succeed — directly matching the required impact of "node disagreement on validity or stability" / "network unable to confirm new units", since witness/full nodes that fail to complete stabilization cannot continue validating and confirming subsequent units.

### Likelihood Explanation
Any unit author can trivially include a `system_vote` message with `subject` set to one of the four numeric subjects and `value` set to a JSON numeric literal like `1e400` (parses to `Infinity`) or `-1e400` (`-Infinity`). No special permission (e.g., being a witness) appears required at this layer beyond posting a normally valid unit containing this app-message, making the vector reachable by "an unprivileged unit poster" as required by scope.

### Recommendation
Parameterize `value` the same way the other fields are handled — pass it as a bound query parameter instead of interpolating it directly into the SQL string:
```js
sqlValues.push(`(${db.escape(unit)}, ${db.escape(address)}, ${db.escape(subject)}, ${db.escape(value)}, ${timestamp})`);
```
Additionally, validation for numeric `system_vote` subjects should explicitly reject non-finite numbers (`Infinity`, `-Infinity`, `NaN`) before the message is accepted into a unit, and any DB errors thrown while processing stable messages during `markMcIndexStable` should be handled gracefully (or at minimum, produce consistent behavior across all supported database backends) rather than allowed to propagate as unhandled exceptions.

### Proof of Concept
1. Craft and post a unit containing a message:
```json
{
  "app": "system_vote",
  "payload": { "subject": "threshold_size", "value": 1e400 }
}
```
`JSON.parse` converts `1e400` to `Infinity`, and `typeof Infinity === 'number'` passes a naive numeric-type check.
2. Once the unit stabilizes, `markMcIndexStable` → `saveSystemVote` executes:
```sql
INSERT INTO numerical_votes (unit, address, subject, value, timestamp) VALUES ('UNIT_HASH', 'ADDRESS', 'threshold_size', Infinity, 1690000000)
```
`Infinity` is not valid SQL syntax for a numeric literal in either MySQL or SQLite, causing the `INSERT` to fail/throw during a core stabilization routine that every node must execute, potentially crashing the node process or causing divergent stabilization outcomes across nodes with different DB engines.

**Note on verification confidence:** Due to tool-call budget limits, I was unable to fully inspect `validation.js`'s exact validation logic for `system_vote` payloads (the specific numeric-type/finite check applied before a unit is accepted). The root-cause code path (unescaped `value` concatenation in `main_chain.js`) is confirmed directly from source, but the precise upstream validation constraints on `value` (whether `Infinity`/`-Infinity`/other malformed numeric strings can reach this code) could not be fully confirmed within the available iterations and should be re-verified before treating this as conclusively exploitable end-to-end.
