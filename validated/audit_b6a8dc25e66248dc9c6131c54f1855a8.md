### Title
Cross-organization webhook authentication bypass via mismatched `repository.owner.login` and `repository.full_name` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login`, an attacker-controlled JSON field read straight out of the unverified request body. Downstream, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolve the actual `Repository`/`Stack` to act on using a *different* field of the same payload, `repository.full_name`. Because the signing/authentication decision and the write-target decision are bound to two independent, unvalidated fields of the attacker's own payload, the two can be made to disagree.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where each GitHub organization has its own GitHub App and its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml`, keyed per organization, and `lib/shipit.rb#github_app_config`) [1](#0-0) .

`WebhooksController#verify_signature` picks the verifying app/secret using `repository_owner`, which is read from the *unauthenticated* JSON body (`params.dig('repository', 'owner', 'login')`), before the signature has been checked: [2](#0-1) 

Meanwhile, the actual repository/stack that a handler acts on is resolved from a *different* field of the same body, `repository.full_name`: [3](#0-2) 

`Repository.from_github_repo_name` splits `full_name` on `/` to find the target `Repository` (and its stacks) with no relation back to `owner.login`: [4](#0-3) .

The binding that should hold is:
`organization used to select the verifying webhook_secret == owner of the repository the handler writes to`

An attacker who legitimately owns/administers their own onboarded GitHub organization ("OrgA", with its own GitHub App and known `webhook_secret`, per the supported multi-org config schema) can craft a raw POST body where:
- `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` picks OrgA's own secret, which the attacker knows because they administered that App), and
- `repository.full_name = "OrgB/victim-repo"` (an org/repo they do not control, but which is tracked by the same Shipit instance).

The attacker signs the raw body with OrgA's own secret (which they legitimately know), `verify_signature` succeeds because it only checks OrgA's secret against OrgA-labeled fields, and the request is accepted (`head(:ok)` continues to `create`). The `create` action then dispatches to handlers (e.g. `push`, `pull_request` opened/closed/labeled/reopened/unlabeled, `status`, etc.) that resolve the target repository/stack purely from `repository.full_name`, i.e. OrgB's repository, never re-checking that OrgB's owner matches the organization whose secret verified the signature: [5](#0-4) .

### Impact Explanation
This breaks the deployment-trust binding between "organization that authenticated the request" and "repository that is written," matching the report's bug class (upper bound / signature-scope check narrower than the actually-trusted range, allowing a value outside the intended bound to slip through). Concretely, an attacker who only controls their own onboarded organization's GitHub App can forge webhook events attributed to any other organization's repository tracked by the same Shipit instance, e.g.:
- Triggering `PullRequest::ClosedHandler`/`OpenedHandler`/`ReopenedHandler`/`LabeledHandler` to archive, unarchive, or provision Review Stacks for a victim repository they don't own [6](#0-5) .
- Enqueuing sync/status jobs against a victim stack, influencing which commit is considered deployable.

This is a cross-repository write performed without any legitimate authorization over the victim repository, matching the Critical "cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
Requires only that the Shipit deployment be configured for multiple organizations/GitHub Apps (a documented, supported configuration) and that the attacker legitimately administers one such onboarded organization — no Shipit session, API token, or access to the victim's secret/repo is needed. The mismatch between `owner.login` (used for auth) and `full_name` (used for the write) is a straightforward, unauthenticated field to manipulate in the raw JSON body before signing with the attacker's own known secret.

### Recommendation
Bind authentication and authorization to the same field: after computing `repository_owner` used to select the verifying app, verify that `repository.full_name`'s owner segment matches `repository_owner` (or, better, derive the verifying organization only from `full_name`'s owner segment) before dispatching to handlers. Reject requests where these fields disagree.

### Proof of Concept
1. Attacker legitimately manages GitHub organization `OrgA`, onboarded into the multi-tenant Shipit instance with its own `webhook_secret` (`secrets_double_github_app.yml` pattern).
2. Attacker crafts a `pull_request` payload:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": {"number": 1},
  "repository": {
    "owner": {"login": "OrgA"},
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` using OrgA's known secret.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against OrgA's secret [7](#0-6) .
5. `create` dispatches to `ClosedHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [8](#0-7)  and archives OrgB's stack, despite the request never being authenticated with any OrgB-owned secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
