### Title
Cross-organization webhook confusion allows forged CI status / repository state for a victim stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but every downstream handler resolves the actual `Repository`/`Stack` to mutate using the independent `repository.full_name` field. Because these two payload fields are never checked for consistency, a signature that is valid for organization A can be attached to a payload whose `full_name` names a repository under organization B, letting a party who legitimately owns a GitHub App/webhook secret for org A forge webhook events (fake commit statuses, pull-request label actions, pushes) against any stack configured under org B.

### Finding Description
`verify_signature` computes `repository_owner` purely from the JSON body before the signature is validated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/webhook secret configured for that organization name (as documented for multi-org Shipit deployments) and verifies `X-Hub-Signature` against it.

However, every webhook `Handler` subclass ignores `repository.owner.login` entirely and instead resolves the target repository/stacks from the sibling field `repository.full_name`: [3](#0-2) 

The pull-request handlers repeat the same pattern (`Repository.from_github_repo_name(params.repository.full_name)`): [4](#0-3) [5](#0-4) 

There is no validation anywhere that `repository.owner.login` (the field used to pick the verifying secret) matches the owner segment embedded in `repository.full_name` (the field used to pick which `Repository`/`Stack` records get mutated). This is exactly the "organization authenticated vs. repository written" binding break: the equality `organization_that_signed == organization_that_owns_the_written_repository` is never enforced.

Multi-organization Shipit configurations, as documented, assign a distinct `webhook_secret` per organization: [6](#0-5) 

### Impact Explanation
An org admin who legitimately owns one of the configured GitHub Apps (and therefore knows that org's `webhook_secret`) can sign an arbitrary payload with their own secret while setting `repository.owner.login` to their own org (satisfying signature verification/org selection) and `repository.full_name` to `victim-org/victim-repo` (satisfying handler-side repository resolution). This lets them:
- Forge commit `status` events, injecting arbitrary CI state (`state`, `context`, `target_url`) onto commits of a stack they do not own, which can satisfy `ci.require`/`deployable?` checks and enable an unauthorized deploy of that commit through Shipit — a cross-repository write and potential unauthorized deploy, matching the "High/Critical impact" criteria (unauthorized deploy, cross-repository writes).
- Trigger `push`/`pull_request` handlers (archive/unarchive stacks, enqueue sync jobs, capture labels) against a stack belonging to a different organization than the one whose secret signed the request.

This is the closest structural analog to the reported "instant liquidation after unpause" bug class: a verification decision (which secret authorizes the request) is made on one payload field, while the state-mutating action is carried out based on a different, unguarded payload field — an equivalent "verified field vs. acted-upon field" mismatch.

### Likelihood Explanation
Requires the Shipit instance to be configured with multiple GitHub organizations (a supported, documented configuration) and requires the attacker to control a legitimate GitHub App/webhook installation for at least one of those configured organizations. This is a real but narrower precondition than a fully unauthenticated attacker — it is analogous in spirit to the original report's "requires a long admin pause" precondition: a specific, documented operating mode must be in effect, but no `ApiClient` token, session, or GitHub push access to the victim repo is required.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, re-derive the organization from `repository.full_name`'s owner segment (or `organization.login`) and require it to match the organization whose secret was used for verification, rejecting the request (422) on mismatch. Equivalently, `Handler#repository_name`/`repository` resolution should cross-check that the resolved `Repository#owner` equals the `repository_owner` value used during signature verification before any handler mutates state.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `attacker-org` (webhook_secret known to the attacker, who administers that org's GitHub App) and `victim-org` (hosting the stack to be attacked), per the documented multi-org config.
2. Attacker builds a `status` webhook JSON body:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `sha`, `state = "success"`, `context = "ci/required-check"` matching a real undeployed commit on the victim stack.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, raw_body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GithubApp`, and successfully verifies the attacker's own valid signature.
5. `Shipit::Webhooks.for_event('status')` dispatches to the status handler, which resolves the target commit/stack via `repository.full_name = "victim-org/victim-repo"` (per `Handler#repository_name`) and creates/updates a `Status` record on the victim's commit with attacker-supplied `state`/`context`, potentially satisfying the victim stack's `ci.require` gate and enabling deployment of that commit.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
