### Title
Round Byte Excluded from Committed-Seal Hash Allows Malicious Proposer to Forge `pfReport`, Inflating PFS and Demoting Validators to `ValExiting` — (`consensus/istanbul/sealer.go`, `kaiax/vrank/impl/getter.go`)

---

### Summary

The round byte stored at `header.Extra[IstanbulExtraVanity-1]` is **zeroed out** by `istanbulFilteredHeader` before computing both `SigHash` and `HeaderHash`. Because committed seals sign over `HeaderHash` (with the round byte zeroed), the round byte is **not covered by any signature** in the block. A single malicious proposer can therefore write any round value into the header after collecting 2F+1 committed seals, and honest nodes will accept the block. `pfReport` reads this byte verbatim and emits one failure entry per round, inflating PFS for up to 255 validators per block. When accumulated PFS reaches `PfsThreshold`, `applyViolationTransition` demotes targeted validators to `ValExiting`, stripping them of block rewards.

---

### Finding Description

**Step 1 — Round byte is not signature-protected.**

`istanbulFilteredHeader` is the sole pre-image builder for both `SigHash` (proposer seal) and `HeaderHash` (committed seals):

```go
// consensus/istanbul/sealer.go
func istanbulFilteredHeader(h *types.Header, keepSeal bool) *types.Header {
    ...
    newHeader.Extra[IstanbulExtraVanity-1] = 0          // round byte zeroed
    newHeader.Extra = append(newHeader.Extra[:IstanbulExtraVanity], payload...)
    return newHeader
}
``` [1](#0-0) 

Both hash functions call this helper:

```go
func (m *IstanbulSealer) HeaderHash(header *types.Header) common.Hash {
    if filtered := istanbulFilteredHeader(header, true); filtered != nil {
        return RLPHash(filtered)
    }
    ...
}
func (m *IstanbulSealer) SigHash(header *types.Header) (hash common.Hash) {
    rlp.Encode(hasher, istanbulFilteredHeader(header, false))
    ...
}
``` [2](#0-1) 

Committed seals sign `Keccak256(PrepareCommittedSeal(HeaderHash(header)))`. [3](#0-2) 

Since `HeaderHash` zeros the round byte, the 2F+1 committed seals are valid for **any** round byte value. The `WriteRound` call that writes the actual round is done by the proposer's backend after seals are collected: [4](#0-3) 

A malicious proposer can substitute any byte value (0–255) here without invalidating the committed seals.

**Step 2 — `pfReport` reads the round byte without bounds-checking.**

```go
func (v *VRankModule) pfReport(blockNum uint64) ([]common.Address, error) {
    ...
    roundByte, err := v.RoundReader.Round(header)
    ...
    round := uint64(roundByte)
    if round == 0 {
        return []common.Address{}, nil
    }
    pfReport := make([]common.Address, 0, round)
    for r := uint64(0); r < round; r++ {
        proposer, err := v.Valset.GetProposer(blockNum, r)
        ...
        pfReport = append(pfReport, proposer)
    }
    return pfReport, nil
}
``` [5](#0-4) 

There is no check that `round <= MaxRound` (10). A forged byte of 255 yields 255 failure entries.

**Step 3 — `GetPFS` accumulates these entries.**

```go
func (v *VRankModule) applyBlocksForPFS(...) {
    for blockNum := start; blockNum <= end; blockNum++ {
        report, _ := v.pfReport(blockNum)
        for _, addr := range report {
            pfs[addr]++
        }
    }
}
``` [6](#0-5) 

**Step 4 — `applyViolationTransition` demotes validators whose PFS ≥ `PfsThreshold`.**

```go
if pfs >= ctx.PfsThreshold {
    if canDemoteActive(valset.ValExiting) {
        val.State = valset.ValExiting
    }
}
``` [7](#0-6) 

`ValExiting` validators are excluded from the active committee and lose block rewards.

**Step 5 — The README's security claim is incorrect.**

The README states:

> "It cannot be forged because the round byte is part of the header hash that 2F+1 validators sign with their committed seals." [8](#0-7) 

The code directly contradicts this: `istanbulFilteredHeader` zeros the round byte before hashing. [9](#0-8) 

---

### Impact Explanation

A single malicious proposer, upon winning any proposer slot, can:
- Set the round byte to 255 (or any value up to 255), generating up to 255 `pfReport` entries per block.
- Cause `GetPFS` to accumulate inflated scores for targeted validators.
- Once PFS ≥ `PfsThreshold`, `applyViolationTransition` demotes those validators to `ValExiting`, removing them from the active committee and stripping them of KAIA block rewards.
- The attack is repeatable every time the attacker wins a proposer slot.

This constitutes unauthorized reward loss for honest validators and invalid validator state transitions — both within the allowed impact gate.

---

### Likelihood Explanation

- Requires only a single malicious validator to win one proposer slot (expected regularly in round-robin selection).
- No key compromise, majority collusion, or external service access required.
- The forged block passes all existing header validation because committed seals remain cryptographically valid.
- The attack is silent and accumulates over an epoch before triggering demotion.

---

### Recommendation

1. **Include the round byte in the hash pre-image.** Remove the `newHeader.Extra[IstanbulExtraVanity-1] = 0` line from `istanbulFilteredHeader`, or move the round into the RLP-encoded `IstanbulExtra` struct so it is covered by both `SigHash` and `HeaderHash`. [9](#0-8) 

2. **Add a bounds check in `pfReport`.** Reject or cap the round byte at `MaxRound` (10) before iterating: [10](#0-9) 

3. **Add a block-import validation** that rejects headers whose round byte exceeds `MaxRound`.

---

### Proof of Concept

```
1. Attacker controls validator V, which wins the proposer slot for block N.
2. V proposes a block at actual round 0; 2F+1 honest validators send COMMIT
   messages signing HeaderHash(header) — with round byte zeroed.
3. Before broadcasting, V calls WriteRound(header, 10) to set round byte = 10.
4. V broadcasts the block. Honest nodes verify committed seals against
   HeaderHash (round byte still zeroed in the hash) — verification passes.
5. pfReport(N) iterates r in [0,10): calls GetProposer(N, r) for r=0..9,
   returning 10 (possibly distinct) proposer addresses.
6. applyBlocksForPFS increments pfs[addr]++ for each of those 10 addresses.
7. Repeated over multiple blocks, targeted validators accumulate PFS ≥ PfsThreshold.
8. applyViolationTransition transitions them to ValExiting; they lose block rewards.

Assert: sealer.HeaderHash(header_with_round_10) == sealer.HeaderHash(header_with_round_0)
        (both zero the round byte before hashing — committed seals remain valid).
```
