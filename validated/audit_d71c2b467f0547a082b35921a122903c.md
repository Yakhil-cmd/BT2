### Title
`handleERC721Transfer` Uses `transferFrom`/`_mint` Instead of `safeTransferFrom`/`_safeMint`, Permanently Locking Bridged ERC721 Tokens in Non-Receiver Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` delivers bridged ERC721 tokens to the recipient (`_to`) using `IERC721.transferFrom` (non-mintBurn mode) or `ERC721MetadataMintable.mintWithTokenURI` which internally calls `_mint` (mintBurn mode). Neither path verifies that the recipient contract implements `IERC721Receiver`. If `_to` is a contract that cannot handle ERC721 tokens, the token is permanently locked with no recovery path. By contrast, `handleKLAYTransfer` in `BridgeTransferKLAY` carries a `nonReentrant` guard, demonstrating that the handle path was considered safety-sensitive — yet the analogous ERC721 safety check (`safeTransferFrom`/`_safeMint`) is absent.

---

### Finding Description

In `BridgeTransferERC721.sol`, `handleERC721Transfer` performs the final asset delivery after all nonce and vote checks pass:

**Non-mintBurn mode** (lock/unlock):
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```
`transferFrom` does not invoke `onERC721Received` on `_to`. If `_to` is a contract without ERC721 handling logic, the token is transferred but permanently inaccessible.

**MintBurn mode**:
```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```
`mintWithTokenURI` calls `_mint` internally, which also skips the `onERC721Received` check.

The `_to` address originates from the user's `requestERC721Transfer` call on the source chain:
```solidity
function requestERC721Transfer(
    address _tokenAddress,
    address _to,   // user-controlled
    uint256 _tokenId,
    bytes memory _extraData
) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
}
```

The operator faithfully relays the user-specified `_to` to `handleERC721Transfer` on the destination chain. There is no guard anywhere in the handle path that checks whether `_to` is a contract capable of receiving ERC721 tokens.

The asymmetry with `handleKLAYTransfer` is direct: `handleKLAYTransfer` carries `nonReentrant` (a safety modifier applied because it makes an external call), while `handleERC721Transfer` makes external calls to token contracts and to `_to` without any equivalent safety guard.

---

### Impact Explanation

A user who specifies a contract address as `_to` on the source chain — for example, a multisig wallet, a DeFi protocol, or any contract that does not implement `IERC721Receiver` — will have their ERC721 token bridged to the destination chain and delivered to that contract via `transferFrom` or `_mint`. The token is now owned by `_to`, but `_to` has no mechanism to call `transferFrom` or `safeTransferFrom` on the ERC721 contract to move it. The token is permanently locked. This constitutes an irreversible loss of a bridged asset.

---

### Likelihood Explanation

Medium. The trigger is a valid, unprivileged user action: specifying a contract address as `_to` in `requestERC721Transfer`. Contract addresses as recipients are common in DeFi (e.g., protocol vaults, multisigs, DAO treasuries). No special privilege or collusion is required. The operator simply relays the user's intent faithfully.

---

### Recommendation

1. **Non-mintBurn mode**: Replace `transferFrom` with `safeTransferFrom`:
   ```solidity
   IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
   ```
2. **MintBurn mode**: Use `_safeMint` in `ERC721MetadataMintable.mintWithTokenURI` instead of `_mint`, or add a post-mint `onERC721Received` check on `_to`.
3. **Reentrancy**: Add `nonReentrant` to both `handleERC20Transfer` and `handleERC721Transfer` to match the guard already present on `handleKLAYTransfer`, since `safeTransferFrom` introduces an external callback to `_to`.

---

### Proof of Concept

1. User on source chain calls `requestERC721Transfer(tokenAddr, contractAddr, tokenId, "")` where `contractAddr` is a deployed contract that does not implement `onERC721Received`.
2. The bridge operator observes the `RequestValueTransferEncoded` event and calls `handleERC721Transfer(txHash, user, contractAddr, tokenAddr, tokenId, nonce, blockNum, uri, "")` on the destination bridge.
3. All nonce/vote checks pass. The function reaches:
   ```solidity
   IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
   ```
4. The ERC721 token is now owned by `contractAddr`. Since `contractAddr` has no `transferFrom` or `safeTransferFrom` call capability for this token, the token is permanently locked.
5. The `handledRequestTx[txHash] = true` flag prevents any retry. The token is irrecoverably lost.
