## Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the stack that gets written to is derived from the independent `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

## Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), while the handlers that actually mutate state (e.g. `PushHandler`) resolve the target `Repository`/`Stack` from the separate `repository.full_name` field. These two JSON fields are never cross-checked against each other, breaking the binding "organization that authenticated == repository that is written."

## Finding Description
`before_action :verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

It picks the `GitHubApp` (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`.

Once the signature check passes, `create` dispatches the **raw, attacker-controlled JSON** unmodified to the handlers: [3](#0-2) 

`Handler#stacks` (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target repository from a *different* JSON field, `repository.full_name`: [4](#0-3) [5](#0-4) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the branch matching that resolved repository: [6](#0-5) 

Because `repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/target-selection) are two independent keys inside the same attacker-supplied JSON object, nothing in this engine enforces that `full_name`'s owner segment matches `owner.login`. Shipit explicitly supports multi-organization GitHub App configuration, where each organization has its own distinct `webhook_secret`: [7](#0-6) 

An attacker who legitimately controls one organization's installation (and thus knows/derives that organization's `webhook_secret`, e.g. by installing the Shipit GitHub App on their own org, which any organization admin can do) can compute a valid HMAC-SHA1 signature over a payload whose `repository.owner.login`/`organization.login` is their own org (so `verify_signature` selects their org's secret and it matches), while setting `repository.full_name` to `victim-org/victim-repo`. The signature check passes because it never inspects `full_name`, and the handler then operates on the victim organization's stack.

## Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely, an attacker with a legitimate (but unrelated, low-privilege) GitHub App installation on their own organization can forge webhook events targeting any other tracked repository/stack in the same Shipit instance:
- `push` events can trigger `GithubSyncJob`/`sync_github` against arbitrary stacks, forcing Shipit to fetch and evaluate an attacker-influenced `expected_head_sha` for a victim repository, and can trigger continuous-deployment flows on stacks with `continuous_deployment` enabled — i.e., an **unauthorized deploy** of a repository the attacker does not control.
- `status`/`check_suite` events can forge CI status/check state for a victim's commits, which the merge queue and continuous-deployment gating logic rely on to decide whether to autodeploy — again enabling deploys to proceed against a stack the attacker never had permission to touch.

This satisfies the "unauthorized deploy" criterion under Critical/High impact categories.

## Likelihood Explanation
Exploitability requires the attacker to control a legitimate GitHub App installation for at least one organization configured in Shipit's multi-org `github:` secrets block (a low, but real, privilege — any org admin who installs the app on their own org qualifies), and for the deployment to use the multi-organization secrets schema documented in `docs/setup.md`. Single-organization deployments (the default/common case) are not affected because there is only one `webhook_secret` and it's already trusted for the whole instance. This is a plausible but non-trivial precondition, so likelihood is Medium rather than trivial.

## Recommendation
In `WebhooksController#verify_signature` (or in `Handler#stacks`), cross-validate that the organization used to select the signing secret matches the owner encoded in `repository.full_name` (and `organization.login` where present) before dispatching to handlers. Reject the webhook (422) if they diverge.

## Proof of Concept
Given a multi-org Shipit config with `OrgAttacker` (attacker-controlled installation, known `webhook_secret_A`) and `OrgVictim` (tracks `OrgVictim/secret-repo`):
1. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/secret-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, raw_body)`.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgAttacker"`, fetches `Shipit.github(organization: "OrgAttacker")`, and the signature verifies successfully (attacker legitimately knows this secret).
5. `Shipit::Webhooks.for_event('push').each { |h| h.call(params) }` runs `PushHandler`, which resolves the target repository via `Repository.from_github_repo_name("OrgVictim/secret-repo")` and invokes `stack.sync_github(expected_head_sha: ...)` on the victim's stack — despite the request never being authenticated against `OrgVictim`'s webhook secret.

Note: I could not find any check anywhere in `app/controllers/shipit/webhooks_controller.rb` or `app/models/shipit/webhooks/handlers/**` that cross-validates `repository.owner.login` against `repository.full_name`, confirming the gap exists as described.
