### Title
Cross-org GitHub team-id reuse in `membership` webhook grants unauthorized `Shipit.github_teams` membership - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id` and, when a matching row already exists (e.g. one of `Shipit.github_teams`'s authorization teams belonging to org B), returns it unchanged regardless of which organization's webhook secret validated the request. Because `WebhooksController#verify_signature` selects the verifying secret from the attacker-controlled `organization.login` field in the payload itself, an operator/administrator of a separate onboarded org A can submit a `membership` event, correctly signed with org A's own webhook secret, whose `team.id` equals org B's authorization team's `github_id`, causing `team.add_member(member)` to add an arbitrary GitHub login as a member of org B's privileged Team row.

### Finding Description
The broken binding is: *the org whose secret verified the payload* (`repository_owner` == `params.organization.login`, used in `Shipit.github(organization: repository_owner)`) MUST equal *the org that owns the Team identified by `params.team.id`* (`Team#organization`). This binding is never checked.

Code path:
- `app/controllers/shipit/webhooks_controller.rb` `verify_signature` resolves the app/secret via `repository_owner`, which for events lacking a `repository` key (like `membership`) falls back to `params.dig('organization','login')` [1](#0-0) . This field is fully attacker-supplied JSON content signed only by whichever org's key the attacker used.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; ... }` [2](#0-1) . `find_or_create_by!` only runs the block on creation; if a `Team` with that `github_id` already exists (belonging to a different org), it is returned as-is, and the org check is bypassed entirely.
- `MembershipHandler#process` then calls `team.add_member(member)` for `action == 'added'`, adding the resolved `User` to `team.members` [3](#0-2) .
- `Team#add_member` unconditionally appends the member [4](#0-3) .
- `Shipit.github_teams` (the authorization allow-list) is built from configured `oauth.teams` handles into `Team` rows via `Team.find_or_create_by_handle` [5](#0-4) , and `User#authorized?` checks membership against exactly these `Team` ids [6](#0-5) .

Exploit flow: attacker administers org A, a legitimately onboarded org in a multi-org Shipit deployment (per `docs/setup.md`'s "Using Multiple GitHub Applications"), and therefore knows org A's `webhook_secret`. Attacker crafts a `membership` webhook body: `organization.login = "orgA"`, `action = "added"`, `team = { id: <github_id of org B's authorization Team>, name, slug, url }`, `member.login = <attacker's own GitHub login>`, signs it with org A's HMAC secret, and POSTs to `/webhooks`. `verify_signature` looks up `Shipit.github(organization: "orgA")` and validates successfully against the attacker-forged body. `find_or_create_team!` finds the pre-existing org B Team by `github_id` and returns it untouched; `add_member` inserts a `Membership` row linking the attacker's `User` to org B's privileged `Team`. If that Team is part of `Shipit.github_teams`, `User#authorized?` now returns true for the attacker.

Existing guards do not catch this: `verify_signature` only proves the payload came from *some* org whose secret matches — it never re-derives which org the referenced `team.id` belongs to; the `ExplicitParameters` schema in the handler only checks types/presence, not cross-field consistency; `drop_unhandled_event`/`check_if_ping` are irrelevant; there is no model validation tying `Team#organization` to `Team#github_id`'s true owner on lookup.

### Impact Explanation
A single crafted `membership` webhook from a legitimately onboarded but unprivileged org grants the attacker's GitHub login membership in an arbitrary pre-existing `Team` row, including any team configured in `Shipit.github_teams`. This directly satisfies the "High - escalation into `Shipit.github_teams` authorization" category: it lets an attacker with no Shipit session, no App private key, and no membership in the target org's real GitHub team pass `User#authorized?` and gain full access to the Shipit web UI/app (stacks, deploys, etc.), which is otherwise gated to members of specific GitHub teams. It is repeatable against any org B whose `Team#github_id` is known and any team the attacker wants to join, as long as attacker controls one legitimately-onboarded org's secret.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured for multiple GitHub organizations (`secrets.github` with multiple org keys) — a supported and documented deployment mode; (2) attacker must legitimately control one of the onboarded orgs and thus its `webhook_secret` (consistent with the multi-tenant onboarding model where each org's admin supplies their own GitHub App credentials); (3) attacker must know the numeric `github_id` of the target `Team` in another org — GitHub team IDs are not typically secret and are exposed via the GitHub API/other webhooks the org may have access to, though this does require some reconnaissance. Given these, the attack is a single crafted HTTP POST, fully repeatable, with no rate limiting concerns cited as relevant here.

### Recommendation
In `MembershipHandler#find_or_create_team!`, additionally verify that any existing `Team` matched by `github_id` belongs to `params.organization.login`; reject (or create a distinct record / raise) if `team.organization != params.organization.login`. More robustly, scope the `find_or_create_by!` lookup by both `github_id` and `organization`, and have `WebhooksController#verify_signature` cross-check that the resolved `Team`/`organization` used for secret lookup matches every organization-scoped identifier referenced in the payload before dispatching to handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot use another org's secret to join a foreign Shipit.github_teams team" do
  org_b_team = shipit_teams(:shopify_developers) # existing Team, organization: 'shopify', github_id: known
  attacker_login = 'attacker'

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: org_b_team.github_id, name: org_b_team.name, slug: org_b_team.slug, url: org_b_team.api_url },
    organization: { login: 'org-a' }, # attacker's own onboarded org
    member: { login: attacker_login }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', ORG_A_WEBHOOK_SECRET, payload)
  @request.headers['X-Hub-Signature'] = signature

  post :create, body: payload, as: :json
  assert_response :ok

  attacker = Shipit::User.find_by(login: attacker_login)
  # Binding assertion: attacker.teams should NOT include org_b_team since
  # verifying org ('org-a') != Team#organization ('shopify')
  refute_includes attacker.teams, org_b_team
end
```
This test currently fails against the existing code (membership is created), demonstrating the escalation.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      head(422) unless verified
