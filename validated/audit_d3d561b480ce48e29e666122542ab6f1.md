### Title
`StatusHandler#process` mutates commits across all stacks/organizations, not just the one that signed the payload - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha).each`, with no filter on the repository/organization/stack that produced the webhook. Because signature verification is keyed only by the GitHub organization named in the attacker-controlled payload body, a single validly-signed `status` event for one org can flip CI state (`Status`, `Commit#deployable?`) on commits belonging to a completely different stack/organization if they happen to share a SHA.

### Finding Description
The binding claimed to hold is: `signed_organization(payload) == mutated_repository(commit rows updated)`. Tracing the code shows this equality is not enforced:

- `WebhooksController#verify_signature` reads `repository_owner` straight from the untrusted JSON body (`params.dig('repository','owner','login')`) and picks `Shipit.github(organization: repository_owner)` to validate the HMAC signature: [1](#0-0) [2](#0-1) 
- This only proves the request was signed with the secret configured for *that organization* (`Shipit::GitHubApp#verify_webhook_signature`, an HMAC-SHA1 compare against `@webhook_secret`): [3](#0-2) 
- Once the signature check passes, `StatusHandler#process` is invoked with the whole raw JSON `params` and looks up commits **globally by SHA**, with no scoping to the organization that signed the request, nor to any specific repository or stack: [4](#0-3) 
- `Commit` is `belongs_to :stack`, and the schema only carries a compound index on `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not a uniqueness constraint on `sha` alone, so identical SHAs across unrelated stacks/organizations (common ancestor commits, empty-tree commits, template scaffolds, cherry-picks) are a normal, unprevented occurrence in the data model: [5](#0-4) 
- `commit.create_status_from_github!(params)` then unconditionally creates a `Status` row and recomputes `deployable?`/blocking for every matching commit, regardless of which stack it belongs to: [6](#0-5) [7](#0-6) 

None of the existing guards close this gap: `drop_unhandled_event` only filters by event type, `verify_signature` only authenticates "this payload matches organization X's secret," and there is no `ExplicitParameters` field or downstream check tying the resolved `Commit` rows back to the authenticated organization/repository. An attacker who legitimately controls one repository in one organization (and thus can trigger a validly-signed `status` webhook for that org, e.g. by pushing a commit/PR that GitHub reports status for) can name any SHA in the JSON body; if that SHA coincidentally exists as a `Commit` row under a different stack/organization, that unrelated commit's status is mutated too.

### Impact Explanation
A single validly-authenticated webhook for organization/stack A causes writes (`Status` creation, `deployable?`/`blocked?` recomputation, `Hook.emit(:commit_status/deployable_status, ...)`, potential `schedule_merges`/`ContinuousDeliveryJob` triggering) against `Commit` rows owned by stack B, C, ... that never authenticated that request. This is exactly the "payload for one repository mutating another's stack/commit" case, matching the Critical severity bucket. The blast radius scales with however many stacks share the colliding SHA in the `commits` table, and is repeatable on every replay/POST of the same payload.

### Likelihood Explanation
Requires: (1) attacker has legitimate ability to produce a validly-signed `status` webhook for at least one organization Shipit tracks (achievable by owning/administering a repository under an org that has a configured GitHub App/webhook secret and pushing a commit that triggers a `status` event, or directly crafting the JSON+signature if they know that org's `webhook_secret`); (2) a SHA collision exists between that commit and a commit tracked under a different stack. SHA collisions are realistic for shared initial/empty commits, common template scaffolding commits, or cherry-picked/rebased commits reused across forks and stacks — no cryptographic collision is needed, just identical commit content reused verbatim across repositories. No elevated Shipit role, API token, or secret beyond what the attacker's own legitimately-configured org/repo webhook already grants is needed for the code path itself.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to the repository/organization that authenticated the webhook, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: repository_owner, repository_name: params.dig('repository','name') })`, instead of a bare `Commit.where(sha: ...)`. Pass the authenticated `repository_owner`/`repository_name` from the controller into the handler explicitly rather than trusting only the payload for authorization decisions after the fact.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event mutates commits across unrelated stacks sharing the same SHA" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # unrelated stack/org fixture

  colliding_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: colliding_sha, message: 'shared ancestor')
  commit_b = stack_b.commits.create!(sha: colliding_sha, message: 'shared ancestor')

  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: colliding_sha, state: 'success', context: 'ci/test'
  )

  Shipit::Webhooks::Handlers::StatusHandler.new.process(params)

  commit_a.reload
  commit_b.reload

  assert_equal 1, commit_a.statuses.count
  assert_equal 1, commit_b.statuses.count # fails to be scoped: both stacks mutated by one payload
  assert commit_a.deployable?
  assert commit_b.deployable? # unrelated stack B flipped by a payload that never authenticated it
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
