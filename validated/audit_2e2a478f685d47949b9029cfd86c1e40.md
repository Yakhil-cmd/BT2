## Title
Cross-organization webhook signature confusion allows forging events for a repository belonging to a different, better-secured GitHub App organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a request against using an attacker-controlled field of the *unverified* JSON payload, while the downstream event handlers act on a *different* attacker-controlled field of that same payload to decide which repository/stack to mutate. In a multi-organization Shipit deployment where any configured organization has no `webhook_secret` set (a documented, supported configuration), this binding break lets an unauthenticated attacker forge GitHub webhook events for any repository belonging to any other configured organization.

### Finding Description
`verify_signature` picks the GitHub App/secret to validate against via: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) *before* any signature has been verified. `Shipit.github(organization: repository_owner)` then resolves that organization's configured `GitHubApp`, and: [3](#0-2) 

`verify_webhook_signature` unconditionally returns `true` when that organization's `webhook_secret` is blank/nil — a case explicitly documented and shown as valid multi-org configuration: [4](#0-3) [5](#0-4) 

Once "verified" (or trivially bypassed), the raw payload is handed to every handler for the event: [6](#0-5) 

Handlers, however, resolve the target repository/stack from a *different* field of the same payload — `repository.full_name` — with no cross-check against the field used for signature-org selection: [7](#0-6) 

Nothing in the controller or in `ExplicitParameters` schemas (e.g. `requires :repository { requires :full_name }`, `requires :owner { requires :login }` in `PullRequest` handlers) enforces that `repository.owner.login` (used to pick the verifying secret) is consistent with `repository.full_name` (used to pick the acted-upon repository). Because the attacker crafts the entire JSON body themselves, these two fields can be set independently:

```json
{
  "repository": { "full_name": "orgA/protected-repo", "owner": { "login": "orgB" } },
  ...
}
```

If `orgB` is any configured organization in `Shipit.github` with `webhook_secret: nil` (or simply unconfigured for webhooks), `verify_signature` succeeds for the whole request regardless of the `X-Hub-Signature` header supplied, yet the handler acts on `orgA/protected-repo` — an organization that *does* have a real secret and is not the one that "authenticated" the request.

This is the direct analog of the reported bug class: a value used to authorize/scope an operation (the organization whose secret gates the request) is not the same value the code subsequently acts on (the repository being written to), so the binding "organization that authenticated == organization whose repository is written" is broken.

### Impact Explanation
An unauthenticated attacker who knows (a) that the Shipit instance is configured with multiple GitHub App organizations and (b) that at least one of those organizations has no `webhook_secret` configured can forge arbitrary webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) attributed to a *different, secured* organization's repositories. Depending on the event:
- `status`/`check_suite` handlers feed into `MergeRequest#all_status_checks_passed?` / `reject_unless_mergeable!`, which gate the automatic merge queue (`MergeRequest#merge!`) — forged "success" statuses can push an unauthorized merge for a stack with `merge_queue_enabled`. [8](#0-7) [9](#0-8) 
- `push` triggers `GithubSyncJob`, which can influence continuous delivery/deploy scheduling for a stack the attacker does not control.

This matches the "unauthorized deploy, rollback, or merge" / authorization-bypass impact categories called out as in-scope.

### Likelihood Explanation
This requires the operator to run Shipit in the documented multi-organization mode (`config/secrets*.yml` with a `github:` map keyed by org) and to leave `webhook_secret` unset for at least one org — a state explicitly shown as acceptable in `docs/setup.md` and the Shopify example secrets file (`webhook_secret: # nil`). No credentials, session, `ApiClient` token, or GitHub push access are required; the `/webhooks` endpoint is unauthenticated by design. Likelihood is therefore conditioned entirely on deployment configuration, which the engine itself documents and supports without warning about this cross-org trust implication.

### Recommendation
Bind signature verification to the same field the handlers use to select the target repository/stack (`repository.full_name`, not `repository.owner.login`/`organization.login`), and/or require every configured organization to have a non-blank `webhook_secret` (refuse to boot, or refuse `verify_webhook_signature` success, when `webhook_secret` is blank in a multi-org configuration). Additionally, after verification, re-derive the organization from `repository.full_name` and confirm it matches the organization whose secret validated the signature before invoking any handler.

### Proof of Concept
Given a multi-org config:
```yaml
production:
  github:
    orgA:
      webhook_secret: real-secret-for-orgA
      ...
    orgB:
      webhook_secret:   # nil / unset
      ...
```
Attacker sends (no valid `X-Hub-Signature` needed):
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "full_name": "orgA/protected-repo", "owner": { "login": "orgB" } },
  "sha": "<head sha of an open orgA PR>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "http://x",
  "created_at": "2026-09-02T00:00:00Z"
}
```
`verify_signature` resolves `Shipit.github(organization: "orgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted. `StatusHandler`/downstream code then records this forged status against `orgA/protected-repo` via `repository.full_name`, potentially satisfying `all_status_checks_passed?` for a pending merge request on `orgA`'s stack.

*Note: I was unable to inspect `app/models/shipit/webhooks/handlers/status_handler.rb` and `push_handler.rb` contents directly (only found via grep) to confirm the exact field mapping inside those specific handlers beyond the shared base `Handler#repository_name`/`#stacks` methods cited above; their behavior should be verified in a live session, but the shared vulnerable pattern in `webhooks_controller.rb` and `handler.rb` is confirmed from source.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```
