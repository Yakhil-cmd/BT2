### Title
Kaia Service-Chain Bridge Has No User Escape Hatch: Operator Inaction Permanently Locks Bridged KLAY and ERC-20 Tokens — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge requires a centralized operator to call `handleKLAYTransfer` / `handleERC20Transfer` on the counterpart bridge to complete every cross-chain value transfer. No user-callable escape hatch exists. If the operator stops processing (government order, key loss, software failure, or deliberate censorship), any KLAY or ERC-20 tokens already deposited into the child-chain bridge contract are permanently inaccessible to their owners.

---

### Finding Description

**Deposit path (child → parent):**

1. A user calls `requestKLAYTransfer` (or the ERC-20 equivalent) on the child-chain `BridgeTransferKLAY` contract. The contract takes custody of the user's KLAY and emits `RequestValueTransfer`. [1](#0-0) 

2. The off-chain `SubBridge` / `BridgeManager` watches for that event and calls `handleKLAYTransfer` on the parent-chain bridge to release funds to the user. [2](#0-1) 

**The gate that creates the lock:**

`handleKLAYTransfer` and `handleERC20Transfer` are both guarded by `onlyOperators`. No other address — including the original depositor — can call them. [3](#0-2) [4](#0-3) 

**No escape hatch exists.** The entire bridge contract surface (`BridgeTransferKLAY`, `BridgeTransferERC20`, `BridgeTransferERC721`) contains no function that allows a depositor to reclaim their assets from the child-chain bridge without operator cooperation. The only user-facing write functions are the `request*` deposit functions and the `chargeWithoutEvent` liquidity function. [5](#0-4) 

Additionally, the owner can call `lockKLAY()` / `lockToken()` to block even new deposit requests, and `setRunningStatus(false)` to halt the bridge entirely — both without providing any refund path for already-deposited funds. [6](#0-5) [7](#0-6) 

The `valueTransferRecovery` subsystem (`node/sc/vt_recovery.go`) only retries operator-signed handle transactions; it does not provide users any independent recovery path. [8](#0-7) 

---

### Impact Explanation

Any KLAY or ERC-20 tokens deposited into the child-chain bridge contract are held exclusively by that contract. The only on-chain mechanism to release them on the parent chain is `handleKLAYTransfer` / `handleERC20Transfer`, callable only by registered operators. If the operator set becomes unavailable (key loss, regulatory action, deliberate censorship, software failure), the deposited assets are permanently locked with no on-chain recourse for the depositor.

Affected asset storage: KLAY balance of `BridgeTransferKLAY` contract; ERC-20 token balance of `BridgeTransferERC20` contract (lock-mode) or burned supply (mint-burn mode, where the burn is irreversible on the child chain).

---

### Likelihood Explanation

The default deployment uses a single operator (threshold = 1, one operator registered at construction). [9](#0-8) 

A single point of failure means any disruption to that one operator key or process permanently blocks all pending withdrawals. Even with multiple operators, the owner can raise the threshold above the number of available operators, achieving the same effect. [10](#0-9) 

---

### Recommendation

1. **User-initiated withdrawal**: Add a time-locked escape hatch (e.g., after N blocks without a handle, the depositor can call `claimBack(requestNonce)` to recover their deposited KLAY/tokens from the child-chain bridge).
2. **Permissionless handle**: Allow any address to call `handleKLAYTransfer` / `handleERC20Transfer` if they can supply a valid Merkle proof of the parent-chain state, removing the operator dependency entirely.
3. **Decentralize the operator set**: Require a minimum number of independent operators and enforce that the threshold cannot exceed the operator count minus a safety margin.

---

### Proof of Concept

```
1. Alice calls requestKLAYTransfer on child bridge, sending 100 KLAY.
   → Child bridge holds 100 KLAY; RequestValueTransfer(nonce=5) emitted.

2. Operator goes offline (key lost / regulatory shutdown).

3. Alice attempts to call handleKLAYTransfer(nonce=5) on parent bridge directly.
   → Reverts: "msg.sender is not an operator"
   (confirmed by bridge.test.ts line 770-771)

4. Alice calls lockKLAY() — reverts: "Ownable: caller is not the owner"
   Alice calls setRunningStatus(false) — reverts: "Ownable: caller is not the owner"
   Alice has no other write function available.

5. Alice's 100 KLAY remains permanently locked in the child bridge contract
   with no on-chain recovery path.
``` [11](#0-10) [7](#0-6)

// recoverPendingEvents recovers all pending events by resending them.
func (vtr *valueTransferRecovery) recoverPendingEvents() error {
	defer func() {
		vtr.childEvents = []IRequestValueTransferEvent{}
		vtr.parentEvents = []IRequestValueTransferEvent{}
	}()

	if len(vtr.childEvents) > 0 {
		logger.Warn("VT Recovery : Child -> Parent Chain", "cBridge", vtr.cBridgeInfo.address.String(), "events", len(vtr.childEvents))
	}

	vtRequestEventMeter.Mark(int64(len(vtr.childEvents)))
	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))
	for i, event := range vtr.childEvents {
		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))
	}

	vtHandleEventMeter.Mark(int64(len(vtr.parentEvents)))
	events = make([]IRequestValueTransferEvent, len(vtr.parentEvents))
	for i, event := range vtr.parentEvents {
		events[i] = event
	}
	vtr.cBridgeInfo.AddRequestValueTransferEvents(events)

	return nil
```
