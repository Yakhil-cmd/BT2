Now I have confirmed the full mechanics of this analog. This confirms the bug class: the multi-organization GitHub App configuration (`docs/setup.md:182-209`, `test/dummy/config/secrets_double_github_app.yml`) is a documented, supported deployment mode where different GitHub organizations have independent `webhook_secret` values [1](#0-0) . The `WebhooksController#verify_signature` selects which organization's secret to check the HMAC against using `repository_owner`, derived from `repository.owner.login` (or `organization.login`) in the untrusted, attacker-supplied JSON body [2](#0-1) . Meanwhile, the event handlers that actually act on the payload (e.g. `PushHandler`, and the base `Handler#stacks`) select the target `Stack`/`Repository` using an entirely different field, `repository.full_name` [3](#0-2) [4](#0-3) . GitHub's own real webhooks always keep `repository.owner.login` and `repository.full_name`'s owner segment consistent, but nothing in Shipit's code enforces that binding on inbound payloads.

### Title
Cross-organization webhook forgery via owner/full_name binding gap in `WebhooksController` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-GitHub-App deployment (a documented, supported configuration), `WebhooksController#verify_signature` selects the HMAC secret to validate against based on `repository.owner.login` from the untrusted request body, while the webhook `Handler` subclasses that process the same body select the target stack/repository using the different field `repository.full_name`. An attacker who legitimately controls (or is a member of) one onboarded GitHub organization — and therefore knows or can generate a valid signature with that organization's `webhook_secret` — can self-author (not intercept) a payload whose `repository.owner.login` matches their own organization (so it passes signature verification) but whose `repository.full_name`/`sha`/`branches` fields reference a different, victim organization's stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and looks up `Shipit.github(organization: repository_owner)` to obtain the webhook secret used to validate `X-Hub-Signature`: [5](#0-4) 

Handlers, however, resolve the affected `Stack`/`Repository` using `repository.full_name`, a separate field within the same JSON body: [6](#0-5) 

For `push` events specifically, `PushHandler` uses `stacks` (resolved via `full_name`) combined with attacker-controlled `ref`/`after` to trigger `stack.sync_github(expected_head_sha:)` on any matching stack: [7](#0-6) 

`StatusHandler` similarly trusts `sha`/`state`/`context` fields to create commit statuses on any `Commit` with a matching `sha` across the whole install, independent of which organization the commit belongs to: [8](#0-7) 

Because the signature (`verify_webhook_signature`) is a valid HMAC over the raw body computed with whichever organization's secret matches `repository.owner.login`, and that field is never cross-checked against `repository.full_name`, an attacker with legitimate access to configure or read one org's `webhook_secret` (a normal admin capability for their own org, granted by design in the multi-app setup at `docs/setup.md`) can forge a self-signed payload naming a victim org's repository in `full_name` while keeping `owner.login` set to their own org. Signature verification passes (correct secret for the claimed `repository_owner`), but the handler acts on the victim's stack because it never re-derives or compares the organization from `full_name` against the one that authenticated the request. This breaks the equality that should hold: "organization that authenticated == organization owning the repository being written."

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in the review criteria. Concretely, the `status` handler lets the attacker inject arbitrary CI status entries (`state`, `context`, `description`, `target_url`) for any commit SHA tracked by any stack in the entire Shipit installation — including stacks belonging to organizations the attacker has no access to — by merely knowing one onboarded organization's webhook secret. Since Shipit's merge queue and deploy-gating logic (`Commit#deployable?`, `stack.schedule_merges`) key off these statuses, an attacker can mark a malicious/unreviewed commit in a victim stack as passing CI, enabling deploys or merges to be unlocked without genuine CI having run. This can lead to an unauthorized deploy of attacker-favored code in a repository outside the attacker's authorized organization.

### Likelihood Explanation
Likelihood is moderate: it requires the deployment to use the multi-organization GitHub App configuration (explicitly documented and supported by Shipit) and for the attacker to have legitimate control over one of the onboarded organizations' webhook secret (e.g., as an org admin who set up their own GitHub App entry, or via leaked secret for one tenant). No GitHub App private key, `GITHUB_TOKEN`, Shipit session, or `ApiClient` token is required — only the ability to POST to the public `/webhooks` endpoint with a validly-signed-for-their-own-org body.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler`/`PushHandler`/`StatusHandler`, derive the organization used for stack/repository resolution from the same trusted, verified value used for signature selection (`repository_owner`), and reject any payload where `repository.full_name`'s owner segment does not match the `repository.owner.login`/`organization.login` value that was used to select the verifying secret.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App config (`OrgA`, `OrgB`) as documented in `docs/setup.md`.
2. As an administrator/member of `OrgA`, know `OrgA`'s configured `webhook_secret` (legitimately, since it was configured for your own org's App).
3. Craft a `status` event JSON body: `{"sha": "<victim-commit-sha-in-OrgB-stack>", "state": "success", "context": "ci/travis", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
4. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "OrgA"`, validates successfully against `OrgA`'s secret.
6. `StatusHandler#process` matches `Commit.where(sha: params.sha)` across the whole database — including the `OrgB`/victim commit — and calls `create_status_from_github!`, marking it as `success` without any real CI having run, potentially unlocking merge/deploy for that commit.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
