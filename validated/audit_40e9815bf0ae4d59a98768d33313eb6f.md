This is a strong analog. `device.js`'s `decryptPackage` function schedules a **deferred, asynchronous `throw`** (via `setTimeout`) when it receives an encrypted package addressed to an unrecognized key, and that throw completely escapes every surrounding `try/catch`, reaching `network.js`'s global `uncaughtException` handler which deliberately re-throws to kill the process — exactly the “malformed input → uncaught exception → process exit” pattern in the `nes` advisory.

### Title
Denial of Service via deferred uncaught exception on device message encrypted to an unknown key - (File: device.js)

### Summary
`device.js`'s `decryptPackage()` throws an `Error` inside a `setTimeout` callback whenever an incoming device message's `encrypted_package.dh.recipient_ephemeral_pubkey` does not match any of the node's known keys (current temp key, previous temp key, or permanent key). Because the throw happens asynchronously (100ms later, outside the call stack of the caller), it cannot be caught by the `try { ... } catch(e) { ... }` block that wraps the `decryptPackage()` call in the `hub/message` handler. The exception is caught by the global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws it to crash the whole node process. Any device — even one that has never paired with the target — can trigger this by sending a `hub/message` addressed to the victim's known device address with a bogus `recipient_ephemeral_pubkey`.

### Finding Description
In `device.js`, the `hub/message` justsaying handler validates the outer signature/hash of an incoming device message and then decrypts the payload: [1](#0-0) 

`decryptPackage()` is called synchronously inside a `try/catch`, so any *synchronous* exception is safely converted into an error response. However, when the `recipient_ephemeral_pubkey` doesn't match any of the node's own keys, the function does not throw synchronously — it schedules the throw for later and returns `null` immediately: [2](#0-1) 

Because this `throw` executes inside a `setTimeout` callback, it runs on a new call stack, completely outside the `try { var json = decryptPackage(...) } catch(e) { ... }` block in the caller. It becomes an uncaught exception at the process level. The global handler in `network.js` intentionally converts any uncaught exception into a full process crash: [3](#0-2) 

The only preconditions for the attacker to reach this code path are (1) knowing the target's `device_address` (public information, e.g. shared for pairing or well known for a service/bot), and (2) crafting a device message that passes the outer signature and hash checks — which the attacker can do trivially since those are signed with the attacker's *own* device keypair: [4](#0-3) 

No correspondent relationship is required — the "correspondent not known" whitelist check happens only *after* `decryptPackage()` runs, so even a totally unpaired attacker can hit this.

### Impact Explanation
This causes a full node/wallet process crash (Denial of Service) that can be triggered remotely by any peer/device that knows the victim's device address, with a single malformed message and no authentication or pairing relationship. Repeated crashes (crash looping) can be used to keep a hub, wallet, or headless node offline, preventing it from confirming or relaying units, matching the "network unable to confirm new units" impact bar for this analog category.

### Likelihood Explanation
Likelihood is high: the attack requires only the victim's public device address, a valid attacker keypair (trivial to generate), and one `hub/message` justsaying frame with an `encrypted_package.dh.recipient_ephemeral_pubkey` set to any value not matching the victim's known keys. No cryptographic breaks, no timing races, and no special privileges are needed.

### Recommendation
Do not use a deferred `setTimeout`-wrapped `throw` for the "unknown key" case in `decryptPackage()`. Instead, return an error/null synchronously (as is already done for the other malformed-input branches in this same function, e.g. `wrong params in encrypted package` and the JSON-parse-failure branch) and let the caller's existing `try/catch` in `device.js`'s `hub/message` handler convert it into an error response via `respondWithError`, without crashing the process. If the `setTimeout` was intentionally added to raise developer visibility (e.g., to detect backup-restoration issues), route it through `eventBus.emit('nonfatal_error', ...)` (as already commented out immediately below) instead of a scheduled `throw`.

### Proof of Concept
1. Attacker learns/derives the victim's `device_address` (public info, e.g. from a pairing QR/link the victim has shared, or from any correspondent conversation).
2. Attacker generates their own device keypair and computes a valid `objDeviceMessage`:
   - `to`: victim's `device_address`
   - `pubkey`: attacker's own device pubkey
   - `encrypted_package.dh.recipient_ephemeral_pubkey`: any bogus base64 string (not matching the victim's temp/prev-temp/permanent key)
   - `encrypted_package.{iv,authtag,encrypted_message}`: any well-formed base64 strings (content doesn't matter, decryption never gets that far)
   - `signature`: attacker signs `objectHash.getDeviceMessageHashToSign(objDeviceMessage)` with their own private key
   - `message_hash = objectHash.getBase64Hash(objDeviceMessage)`
3. Attacker sends this as a `['justsaying', {subject:'hub/message', body:{message_hash, message: objDeviceMessage}}]` frame to the victim (directly if connected, or via the victim's hub).
4. Victim's `device.js` `handleJustsaying` passes the hash/signature checks (both computed by the attacker over their own data) and calls `decryptPackage(objDeviceMessage.encrypted_package)`.
5. Since `recipient_ephemeral_pubkey` matches none of the victim's known keys, `decryptPackage` logs "message encrypted to unknown key" and schedules `throw Error(...)` in 100ms, returning `null` immediately (caller sees a harmless `null`/error response).
6. 100ms later, the scheduled `throw` fires outside any try/catch, is caught only by `process.on('uncaughtException', ...)` in `network.js`, which re-throws — terminating the victim's node process.
