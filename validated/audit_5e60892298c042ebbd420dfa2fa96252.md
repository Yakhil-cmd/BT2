### Title
Crash of AA data-feed resolution via unsortable equal-rank unstable candidates causes network-wide inability to confirm new units - ([File: data_feeds.js])

### Summary
`readDataFeedValue()` in `data_feeds.js` resolves an AA's `data_feed[[...]]` read (analogous to Loopscale's price-feed lookup) by collecting all matching unstable `data_feed` messages authored by the referenced oracle address(es) and, when more than one candidate exists and `ifseveral="last"` (the default), sorting them by `latest_included_mc_index` then `level`. If two candidates tie on both, and the call is in AA context (`bIncludeAllUnstable` false), the comparator throws a raw `Error("can't sort candidates ...")` instead of resolving deterministically.

### Finding Description
`readDataFeedValue` builds `arrCandidates` from `storage.assocUnstableMessages` for any unstable, `sequence === 'good'` unit authored by an address in the oracle list [1](#0-0) . When several candidates exist and `ifseveral !== 'abort'`, it sorts them, but the comparator has no tie-break for the AA-context path and throws synchronously: [2](#0-1) 

This code path is reached directly from the `data_feed` opcode of the AA formula evaluator, called synchronously with `bAA=true` (i.e. `unstable_opts` truthy, `bIncludeAllUnstable` false): [3](#0-2) 

Two sibling units authored by the *same* oracle address, both children of the same parent set and carrying only non-conflicting messages (e.g. two `data_feed` messages, no payment), can legitimately have identical `latest_included_mc_index` and `level` while both remaining `sequence === 'good'` during the unstable window — this only requires an ordinary unprivileged address to broadcast two DAG-sibling units, a pattern any wallet/AA-trigger-sender-class actor can construct. If any AA reads that oracle's feed with the default `ifseveral="last"` while both units are still unstable, the comparator throws.

No `try/catch` wraps this synchronous call chain: `formulaParser.evaluate()` invokes the `data_feed` case, which invokes `dataFeeds.readDataFeedValue()` synchronously (the `arrCandidates.length > 1` / sort branch executes without any async boundary), and the throw propagates straight out of `evaluate()` back into `aa_composer.js`'s `replace()`/`evaluateAA()`/state-update logic, none of which catch generic exceptions from `formulaParser.evaluate` [4](#0-3) [5](#0-4) . `handleTrigger` is invoked deterministically by every full node from `main_chain.js` while processing AA triggers during MC stabilization, so an uncaught exception here is a deterministic, network-wide crash trigger rather than a single-node fault.

### Impact Explanation
Because every full/validating node executes the identical AA trigger-processing code at the same point in stabilization, an uncaught exception here is not a localized failure: it is a deterministic crash that hits all nodes evaluating the same AA response at the same time. This matches "network unable to confirm new units" — nodes that crash (or hang, depending on process supervision) can no longer process the main chain forward past the offending trigger, and any AA that reads an oracle feed with the default `ifseveral="last"` (the common, undocumented-danger default, as shown pervasively in the test suite) is exposed. This is directly analogous to the Loopscale root cause: unmanaged conflicting/ambiguous oracle data resolution feeding straight into financially-relevant AA logic, except here the ambiguity manifests as an uncaught exception/DoS on the consensus-critical data-feed resolution path rather than a silently-accepted stale price.

### Likelihood Explanation
Triggering the tie is straightforward for anyone with wallet/API access: post two sibling units (identical parent set) from the same address, each carrying a `data_feed` message for the same `feed_name` with no conflicting payment messages, so both remain `sequence='good'` and unstable simultaneously. As soon as any AA whose logic reads `data_feed[[oracles=<that address>, feed_name=<that name>]]` (default `ifseveral="last"`) is triggered while both sibling units are still unstable, the sort throws. This does not require compromising the oracle's key generally — it only requires the attacker to control (or induce) an address that some deployed AA treats as an oracle, including any AA pattern (documented in the codebase's own test suite) that derives the oracle address dynamically from trigger/input data.

### Recommendation
In `readDataFeedValue`'s sort comparator (`data_feeds.js`), replace the `throw Error("can't sort candidates ...")` branch for the AA path with a deterministic, total-order tie-break (e.g., unit hash comparison) instead of throwing, so that ambiguous same-level/same-mci candidates are resolved consistently across all nodes without raising an exception. Additionally, wrap `formulaParser.evaluate()` invocations in `aa_composer.js` in defensive `try/catch` so that any unexpected internal exception is converted into an AA bounce rather than propagating as an uncaught exception that can halt trigger processing.

### Proof of Concept
1. Deploy an AA whose logic includes `data_feed[[oracles="<ORACLE_ADDR>", feed_name="X"]]` (default `ifseveral="last"`).
2. From `<ORACLE_ADDR>`, construct two sibling units off the same set of parent units (same `parent_units` list), each containing a `data_feed` message with `feed_name="X"` and no conflicting/payment content, so neither is flagged as a double-spend and both remain `sequence='good'`.
3. Broadcast both units so that both remain unstable simultaneously (same `latest_included_mc_index` once included, same `level` since same parents).
4. Trigger the AA while both sibling units are still unstable; `readDataFeedValue` collects two candidates with identical `latest_included_mc_index` and `level`, hits the `arrCandidates.sort` compare function, and throws `Error("can't sort candidates ...")` synchronously out of `formulaParser.evaluate`, propagating uncaught through `aa_composer.js`'s trigger-handling logic executed on every node processing that MC stabilization step.
