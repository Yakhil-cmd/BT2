### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while the actual write target is resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and its `webhook_secret`) used to authenticate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`), a field parsed straight out of the untrusted JSON body before HMAC verification occurs. The event handlers that actually mutate state, however, resolve the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`. Nothing binds these two fields together, so the identity used to authenticate the delivery is not the same identity used to authorize the write.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unverified JSON body and uses it to pick which configured GitHub App's `webhook_secret` will validate `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

Signature verification itself, in `GitHubApp#verify_webhook_signature`, is a no-op if the resolved app has no `webhook_secret` configured — it returns `true` unconditionally in that case: [3](#0-2) 

Once the request passes (or is waved through), `Webhooks.for_event(event)` handlers are invoked with the full unverified `params` hash, unchanged: [4](#0-3) 

Handlers such as `PushHandler`/`StatusHandler` inherit `Handler#stacks`/`#repository_name`, which resolves the affected `Repository` (and its `stacks`) purely from `repository.full_name` — a field completely independent of `repository.owner.login`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a plain DB lookup by `owner`/`name` columns, with no relation back to whichever GitHub App organization authenticated the request: [7](#0-6) 

This is the same class of bug as the reported issue: the contract's `receive()`/authentication path is bound to one field (empty calldata / `bytes4(0)`), while the code that actually dispatches behavior (`fallback` selector resolution) uses a different, unauthenticated interpretation of the same input. Here, the *organization identity that authenticates* the webhook (`repository.owner.login`/`organization.login`) is not equal to the *repository identity that is written* (`repository.full_name`).

### Impact Explanation
If a Shipit deployment is configured with multiple GitHub Apps/organizations (`Shipit.github_organizations`), and any one organization is configured without a `webhook_secret` (or the operator misconfigures the mapping such that `repository_owner` resolves to that org), `verify_webhook_signature` returns `true` for **any** payload, regardless of what `repository.full_name` claims. An attacker who can cause a delivery to be routed to that unsecured app config (by setting `repository.owner.login` accordingly) can forge a `push`/`status`/`check_suite`/`membership` event for a `repository.full_name` belonging to a *different, secured* organization's stack, since the handler layer never re-validates that `full_name`'s owner matches the app that authenticated the request. This can trigger unauthorized `sync_github`/status/deploy-triggering side effects on stacks the attacker does not control — a cross-repository/cross-organization write triggered through a trust binding that was never actually enforced end-to-end.

### Likelihood Explanation
This requires a specific misconfiguration precondition (an organization/app entry with no `webhook_secret`, or an app resolvable without one) to be reachable — it is not exploitable against a single, correctly configured Shipit instance, since every configured org normally has a secret enforced. Given the "reject if it depends on host not mounting the engine as documented" rule and the fact that this needs an actual missing-secret condition rather than a pure logic flaw in signed payloads, the practical likelihood is low-to-moderate and configuration-dependent rather than universally reachable.

### Recommendation
Bind the identity used for signature verification to the identity used for the write: after selecting `repository_owner` for app/secret lookup, re-verify inside each handler that `repository.full_name`'s owner segment matches `repository_owner` (or better, resolve the target `Repository` first, derive its configured GitHub App from the stored `owner`, and verify the signature against *that* app/secret rather than trusting the unverified payload's `owner`/`organization.login`). Additionally, consider disallowing/erroring on GitHub App configs lacking a `webhook_secret` in production, since `verify_webhook_signature` currently treats a missing secret as "always verified."

### Proof of Concept
Preconditions: Shipit configured with `github_organizations` including at least two orgs, `org-a` (has `webhook_secret`) and `org-b` (misconfigured, no `webhook_secret`).

1. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/secured-repo" }
}
```
2. `repository_owner` resolves to `org-b` [2](#0-1) ; `Shipit.github(organization: "org-b")` loads the app with no secret; `verify_webhook_signature` returns `true` without checking any `X-Hub-Signature` [8](#0-7) .
3. `PushHandler#process` runs against `stacks` resolved from `full_name = "org-a/secured-repo"` [6](#0-5) [9](#0-8) , triggering `sync_github` on `org-a`'s stack despite the request never being authenticated against `org-a`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
