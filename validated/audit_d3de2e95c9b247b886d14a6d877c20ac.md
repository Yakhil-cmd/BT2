### Title
Use-after-free-style listener destruction in `handlePrivatePaymentChains` permanently deadlocks the hub-message mutex - ([File: wallet.js])

### Summary
`wallet.js`'s `handlePrivatePaymentChains()` registers per-chain-element completion callbacks on a **global, data-derived** `eventBus` key (`'private_payment_validated-'+unit+'-'+payload_hash+'-'+output_index`) and, on any validation error within one call, wipes out *all* listeners on that key via `eventBus.removeAllListeners(key)`. Because the key is derived only from public/deterministic data (unit, payload hash, output index) rather than being scoped to a single invocation/request, a second concurrent call that legitimately registered a `once` listener on the same key gets its callback silently destroyed before it ever fires — mirroring the CVE-2023-4574 pattern of "multiple of the same callbacks created... eventually all simultaneously destroyed as soon as one of the callbacks finished."

### Finding Description
In `handlePrivatePaymentChains` [1](#0-0) , each private-chain element gets a completion key:
```
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+output_index;
``` [2](#0-1) 

When `network.handleOnlinePrivatePayment` reports `ifQueued` (the normal path for light clients waiting on a not-yet-arrived referencing unit), the function registers a `once` listener on this key [3](#0-2) . This key is **not unique per call/connection** — it is fully reproducible from public chain data, so it is entirely possible for two different `handlePrivatePaymentChains` invocations (e.g., the same private payment forwarded to/received from two different correspondents, which the protocol explicitly does via `forwardPrivateChainsToOtherMembersOfSharedAddresses`/`...OfOutputAddresses`, or a peer resending the identical chain before `handledChainsCache` is populated) to register a listener on the exact same key concurrently.

If any *other* chain element in the same `async.eachSeries` batch fails validation, the overall error path fires:
```
function(err){
    bParsingComplete = true;
    if (err){
        cancelAllKeys();
        return callbacks.ifError(err);
    }
    ...
}
``` [4](#0-3) 
and `cancelAllKeys` does:
```
var cancelAllKeys = function(){
    for (var key in assocValidatedByKey)
        eventBus.removeAllListeners(key);
};
``` [5](#0-4) 

`removeAllListeners(key)` is global — it strips every listener registered on that event name, including the one belonging to the unrelated concurrent call. That other call's `eventBus.once(key, ...)` callback is now destroyed and will never fire, so `cb()` inside its `async.eachSeries` iterator is never invoked, and the outer `callbacks.ifOk()/callbacks.ifError()` for that call is never called.

This directly violates the invariant documented at the top of the dispatcher:
```
// one of callbacks MUST be called, otherwise the mutex will stay locked
function handleMessageFromHub(ws, json, device_pubkey, bIndirectCorrespondent, callbacks){
``` [6](#0-5) 
because `handleMessageFromHub` wraps the caller's callbacks with `mutex.lock(["from_hub"], ...)` and only unlocks when `ifOk`/`ifError` is invoked [7](#0-6) . If the wrapped callback is never called, the `from_hub` mutex is never released.

### Impact Explanation
The `from_hub` mutex serializes **all** subsequent hub messages (pairing, text, signing requests, signatures, private payments, arbiter contract exchanges, etc.) for that wallet/device [8](#0-7) . A single crafted pair of concurrent `private_payments` messages that collide on the completion key — triggerable by an authorized paired device/correspondent, which is one of the explicitly in-scope actors — permanently deadlocks this mutex, freezing the victim's ability to process any further device messages: no further signing requests can complete, no further private payments can be confirmed, and shared/multisig payment flows relying on device messaging are frozen indefinitely. This is a durable denial of ability to confirm/cosign further transactions for the victim wallet, not merely a transient resource exhaustion.

### Likelihood Explanation
Reachable by any paired correspondent device sending two `private_payments` justsaying messages through the hub, one of which is deliberately malformed/invalid in a way that fails validation (e.g., a bad additional chain element) while sharing a head private element/key with a second, otherwise-valid, in-flight chain that is genuinely queued (`ifQueued`) — a state reached whenever the referencing unit hasn't arrived yet, which is routine for light clients. No special privileges beyond being a paired device are required, and the race window exists between message receipt and the `handledChainsCache` write at the very end of processing [9](#0-8) [10](#0-9) .

### Recommendation
Scope the `eventBus` key to the specific `handlePrivatePaymentChains` invocation (e.g., include a per-call nonce/counter in the key, or maintain a per-call map of listener references and remove only the caller's own listener with `eventBus.removeListener(key, thisListenerFn)` instead of `removeAllListeners(key)`). Additionally, ensure `callbacks.ifOk`/`ifError` for `handleMessageFromHub` is always guaranteed to fire (e.g., via a timeout fallback) so a stuck internal listener can never permanently deadlock the `from_hub` mutex.

### Proof of Concept
1. Device B (paired with victim A) sends `private_payments` justsaying message M1 to A via the hub, containing a chain whose head private element hashes to key K, and where A's node responds with `ifQueued` (e.g., references a not-yet-received unit) — A registers `eventBus.once(K, cb1)`.
2. Before M1 finishes, device B (or another correspondent sharing the same address) sends a second `private_payments` message M2 containing two chains: chain 1 has the identical head private element (same unit/payload/output_index → same key K), chain 2 contains a deliberately invalid element that fails validation.
3. M2's chain 1 registers a second `eventBus.once(K, cb2)`; M2's chain 2 fails, causing M2's `async.eachSeries` final callback to invoke `cancelAllKeys()`, which calls `eventBus.removeAllListeners(K)`, destroying both `cb1` (M1's) and `cb2` (M2's own, already redundant) listeners.
4. M1's `cb()` for that chain element is now never invoked; M1's `async.eachSeries` never completes; `callbacks.ifOk()/ifError()` for M1 is never called.
5. Since `handleMessageFromHub`'s `from_hub` mutex was locked for M1 and never unlocked, all subsequent hub messages for A queue indefinitely, freezing A's device-message processing.
