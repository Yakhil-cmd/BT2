### Title
Webhook signature verification binds to `repository.owner.login`, while `CheckSuiteHandler#process` binds to `repository.full_name`, allowing a payload with mismatched owner/full_name to write to an unauthenticated repository's stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate a webhook using `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`), while `Handler#repository_name`/`stacks` (used by `CheckSuiteHandler#process`) resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')`. Nothing in the controller or handler cross-checks that the owner used to pick the signing secret matches the owner encoded in `full_name`, so a single crafted JSON body can be authenticated as belonging to org-A while mutating org-B's stack.

### Finding Description
Binding claimed: `verifying_org` (`params.dig('repository','owner','login') || params.dig('organization','login')`) `== owning_org` (`payload.dig('repository','full_name').split('/').first`).

Trace:
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` itself is read straight from attacker-controlled JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [2](#0-1) 
- After verification succeeds (or is skipped because the resolved org has no `webhook_secret` configured — see `GitHubApp#verify_webhook_signature`, `return true unless webhook_secret`), `create` dispatches the same raw `params` hash to the registered handler. [3](#0-2) [4](#0-3) 
- `CheckSuiteHandler#process` never consults `repository_owner`; it goes through `Handler#stacks`, which resolves the target `Repository` via `Repository.from_github_repo_name(repository_name)`, and `repository_name` is `payload.dig('repository', 'full_name')` — a completely independent key from the one used for signature routing. [5](#0-4) [6](#0-5) 

Attacker request: a `check_suite` POST to `/webhooks` where `repository.owner.login` (or `organization.login`) is set to an org configured in this Shipit instance whose `Shipit.github(organization:)` config has no `webhook_secret` set (an accepted, valid configuration per `GitHubApp#initialize`, `@webhook_secret = @config[:webhook_secret].presence`), while `repository.full_name` is set to `"org-B/private-repo"` and `check_suite.head_branch`/`head_sha` match a real commit/branch on org-B's tracked stack. `verify_signature` resolves org-A's `GitHubApp`, which returns `true` unconditionally (no secret to check), so the request passes verification without the attacker knowing any secret. `CheckSuiteHandler#process` then looks up stacks by `full_name = "org-B/private-repo"` and branch, and calls `stack.commits.where(sha:).each(&:schedule_refresh_check_runs!)`, enqueuing `RefreshCheckRunsJob` against org-B's stack/commit — a write to org-B triggered by a request that only "authenticated" against org-A's (nonexistent) secret. [7](#0-6) 

No existing guard closes this gap: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schema for `CheckSuiteHandler` only validates presence/type of `check_suite.head_sha`/`head_branch`, not the repository owner; there is no code anywhere comparing `repository_owner` to `repository.full_name`'s owner segment. [8](#0-7) [9](#0-8) 

### Impact Explanation
When the resolved verifying organization has no `webhook_secret` configured, the impact is: any internet requester (no session, no token, no secret) can queue `RefreshCheckRunsJob` against an arbitrary stack/commit belonging to a different organization/repository than the one whose (absent) secret was checked, purely by controlling two independently-read JSON fields in one POST body. This matches the "payload for one repository mutating another's stack/commit" critical category. The blast radius spans every organization/repository configured on the Shipit instance whose associated `GitHubApp` config lacks a `webhook_secret`, and the target can be any repository's stack, repeatable per request with no rate limiting on `/webhooks`.

### Likelihood Explanation
Exploitability is conditioned on the operator having configured at least one GitHub organization in Shipit without a `webhook_secret` (an explicitly supported, non-default state in `GitHubApp#initialize`/`verify_webhook_signature`, not a hypothetical). Given that condition, the attacker needs zero secrets, zero privileged role, and only needs to know (a) that such an org exists/its name, and (b) the target org/repo `full_name` and a valid branch/commit sha on the target stack (all discoverable via public GitHub browsing). If every configured org has a `webhook_secret`, an attacker without any secret cannot pass `verify_webhook_signature` for any org, and this specific exploit path is blocked — but the underlying binding flaw (verification target ≠ mutation target) remains latent and would be triggered by any future/alternate bypass of `verify_webhook_signature` (e.g., a misconfigured org).

### Recommendation
Enforce that the organization used to authenticate the webhook matches the actual owner encoded in `repository.full_name` before dispatching to handlers — e.g., in `WebhooksController#create`/`verify_signature`, derive both values and reject (422) if `repository_owner != payload.dig('repository','full_name')&.split('/')&.first`. Additionally, require `webhook_secret` to be present for every configured organization (fail fast at boot if missing) so `verify_webhook_signature` never trivially returns `true`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":check_suite with mismatched owner/full_name enqueues job for a different org's stack" do
  # org-A is configured with no webhook_secret (simulating the accepted config state)
  Shipit.github(organization: 'org-A').stubs(:verify_webhook_signature).returns(true)

  target_stack = shipit_stacks(:shipit) # belongs to org-B
  request.headers['X-Github-Event'] = 'check_suite'
  body = {
    repository: { owner: { login: 'org-A' }, full_name: "#{target_stack.repo_owner}/#{target_stack.repo_name}" },
    check_suite: { head_sha: target_stack.commits.last.sha, head_branch: target_stack.branch }
  }.to_json

  # verifying_org == 'org-A'; owning_org == target_stack.repo_owner ('org-B') -- mismatch
  assert_enqueued_with(job: RefreshCheckRunsJob) do
    post :create, body:, as: :json
    assert_response :ok
  end
end
```
This demonstrates the broken binding without any live GitHub call or knowledge of any real `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
