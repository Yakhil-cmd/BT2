### Title
Convex oversize-fee formula can be gamed by splitting a large unit into multiple smaller units - (File: storage.js)

### Summary
The reported bug class is a fee model that computes a rate/fee based on the *final* (post-change) state and applies that single rate to the *entire* amount, instead of integrating the fee incrementally as the state moves from its starting point to its ending point. Because the fee curve is convex (fee grows faster than linearly with the state), an attacker can pay substantially less total fee by splitting one large operation into several smaller ones, each individually landing at a lower point on the fee curve. In ocore, the analogous mechanism is the **oversize fee** computed by `getOversizeFee()` in `storage.js`, which charges a fee that grows exponentially with the *total size of a single unit*, rather than the size added per operation.

### Finding Description
`getOversizeFee(objUnitOrSize, mci, bAA)` in `storage.js` computes: [1](#0-0) 

```
const threshold_size = getSystemVar('threshold_size', mci);
if (size <= threshold_size)
    return 0;
return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
```

This fee is a convex (exponential) function of the *whole unit's size* (`headers_commission + payload_commission`, minus paid temp-data fee). The fee is computed once per unit and charged as `objUnit.oversize_fee`, validated by the network in `validation.js` to match this exact formula: [2](#0-1) 

Because `size * (exp(size/threshold_size - 1) - 1)` is convex in `size` for `size > threshold_size`, the fee for one unit carrying a total excess of `d` bytes above `threshold_size` is strictly greater than the sum of fees for multiple smaller units whose excess sizes sum to the same `d` (each landing lower on the exponential curve, some possibly even below `threshold_size` and paying zero fee). This mirrors exactly the reported flaw: the fee is calculated “as if the whole amount was applied at a single point on the curve,” rather than integrated incrementally, so a user (or an AA composing multiple response units, or a wallet composing a payment with large data payloads) can reduce total fees paid to the network by splitting one oversized unit into several smaller units instead of a single large one.

This is architecturally identical to the reported `_amountOutBeforeFee`/`_applyFeeSlopes` issue: a nonlinear fee curve evaluated once on the total post-operation size/state and charged against the whole amount, enabling economically motivated splitting to reduce total fee paid.

### Impact Explanation
The oversize fee is the network's primary anti-spam/anti-bloat mechanism for large units (post v4.0 upgrade). If it can be trivially reduced by splitting a large payload into multiple smaller units, the deterrent against posting large/expensive units to the DAG is weakened: an attacker who wants to publish a large amount of data (e.g. large payloads, many messages, big AA responses) pays much less than the fee model intends, while still consuming comparable total header/payload storage and validation work across the network. This does not directly enable double-spends or fund theft, but it undermines a network-wide economic safeguard, allowing cheaper-than-intended DAG bloat, which is the "no confirmable capacity control" analog described in the validation criteria (fee model gaming reduces protection against unbounded storage growth for the same effective payload volume).

### Likelihood Explanation
Any ordinary unit poster (wallet, AA composer producing multiple response units, or a scripted spammer) can trivially split what would otherwise be one large unit into several smaller ones. No special privilege, hub cooperation, or protocol violation is needed — this is purely a consequence of the fee formula being applied per-unit to the full unit size instead of being size-additive/integrated. The exponential shape of `exp(size/threshold_size - 1) - 1` guarantees the splitting benefit grows the larger the original oversize excess is, making it attractive for exactly the "large/expensive" units the mechanism is meant to price.

### Recommendation
Redesign the oversize fee so that it is computed incrementally/additively across a sequence of related units (e.g., tracked cumulative "excess size" state per address/session, similar to how per-unit size is tracked), or make the fee function convex in a way that is invariant to splitting (i.e., integrate the marginal fee over the size range added, rather than evaluating the curve once at the final size and multiplying by the whole size). Alternatively, apply the fee cumulatively across units authored by the same address within a bounded time/MCI window so that splitting a payload across multiple units doesn't escape the higher marginal rate that a single large unit would have incurred.

### Proof of Concept
Given `threshold_size = T` and a target total oversize excess `d` (`size = T + d`):

- Single unit: `fee_single = (T+d) * (exp(d/T) - 1)`
- Split into two units, each with excess `d/2` (assuming both still exceed `T`, or one below `T` paying 0):
  `fee_split = 2 * (T + d/2) * (exp((d/2)/T) - 1)`

Because `exp` is convex, for any `d > 0`, `fee_split < fee_single`. For example, with `T = 10,000` bytes and `d = 10,000` (i.e., one 20,000-byte unit vs. two 15,000-byte units):
- Single: `size=20000`, `fee = 20000 * (exp(1) - 1) ≈ 20000 * 1.718 ≈ 34,366`
- Split (two 15,000-byte units, each `d=5000`): `size=15000` each, `fee_each = 15000 * (exp(0.5) - 1) ≈ 15000 * 0.6487 ≈ 9,731`; total ≈ `19,461`

The split path pays roughly 43% less in oversize fees for delivering the same total payload size, confirming the fee model can be gamed by splitting, exactly analogous to the reported issue's exploit of splitting a burn into multiple smaller transactions to reduce total fee paid.

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
}
