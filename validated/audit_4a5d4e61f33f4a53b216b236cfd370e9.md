### Title
Webhook signature verification keys off an attacker-supplied field, letting the org whose secret is checked diverge from the repository the payload mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) is used to validate the `X-Hub-Signature` header by reading `repository_owner`, which is parsed straight out of the **unauthenticated** request body, before the signature is checked. The webhook handlers that actually perform writes (enqueue syncs, update commit statuses, archive/unarchive review stacks, manage team memberships) key off a *different* attacker-controlled field in the same body (`repository.full_name`, or `organization.login` for membership events). This breaks the intended binding "organization whose secret authenticated the request == repository/organization that gets written to."

### Finding Description
`repository_owner` is computed purely from the JSON body, prior to any cryptographic check: [1](#0-0) 

It's then used to pick the GitHub App/secret that authenticates the whole request: [2](#0-1) 

`verify_webhook_signature` short-circuits to `true` whenever the selected org's `webhook_secret` is blank: [3](#0-2) 

Shipit explicitly documents and supports running with several independently configured GitHub Apps, each with its own (optional) `webhook_secret`, keyed by organization login: [4](#0-3) 

Meanwhile, once verification "passes," handlers dispatch and mutate state using a *different* field taken from the same unauthenticated body — `repository.full_name` (not `repository.owner.login`/`organization.login` that was used to select the secret): [5](#0-4) [6](#0-5) 

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name`/`organization.login` (used to pick the write target) are two independently attacker-controlled JSON fields, an attacker can set them to different values: point `repository.owner.login` (or the fallback `organization.login`) at any organization configured in this Shipit instance that has *no* `webhook_secret` set (satisfying `return true unless webhook_secret`), while pointing `repository.full_name` at the real target stack belonging to a *different*, properly-secured organization. The signature check passes trivially, yet the mutating handler acts on the real target's `Stack`/`Repository`, which never actually validated the forged request.

This is the direct analog of the reported bug class: a value is consumed by security-relevant logic (which entity to trust/authorize) without being covered by the same verification that protects the value actually acted upon — exactly like the unwrapped `ERC20Helper.transfer` acting on `swapAmount_` while only the return-leg `transferFrom` was checked.

### Impact Explanation
Successful exploitation lets an unauthenticated network attacker send a forged `push` webhook that is accepted as "signature verified" and causes `PushHandler` to call `stack.sync_github(...)`, which enqueues `GithubSyncJob` to append attacker-claimed commits and, for stacks with `continuous_deployment: true`, subsequently trigger `ContinuousDeliveryJob`/`trigger_continuous_delivery` → an unauthorized deploy: [7](#0-6) [8](#0-7) 

Other handlers reachable the same way (status updates, PR/review-stack archive/unarchive, team membership changes) can similarly be forced onto a target repository/organization whose actual secret was never checked. This matches the required "Critical: unauthorized deploy" (and potentially "High: escalation into `Shipit.github_teams` authorization" via crafted `membership` events) impact bar.

### Likelihood Explanation
Exploitability requires: (1) this Shipit instance to be configured with multiple GitHub App organizations (a documented, supported configuration) where at least one configured org lacks a `webhook_secret`, and (2) the attacker to know/guess that org's login. Given `webhook_secret` is explicitly optional per the setup docs and organizations may reasonably be onboarded before a secret is set, this is a plausible misconfiguration rather than a purely theoretical one. Likelihood is Medium: it depends on multi-org + partially-secured deployments, which the engine itself documents as a first-class supported mode, but is not universal to every Shipit install (single-org deployments always use the one configured secret regardless of `repository_owner`).

### Recommendation
- Verify the webhook signature using the `webhook_secret` associated with the *same* repository/organization that the handler will actually mutate (i.e., derive both from the same authenticated identity, not two independently-controlled JSON fields), or reject payloads where `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`.
- Do not allow `verify_webhook_signature` to return `true` unconditionally when `webhook_secret` is blank in a multi-org configuration; instead, require an explicit "unsecured org" allow-list or fail closed with a clear configuration error, since silent trust-by-omission recreates the same "missing require" class of bug as the reported issue.
- Add validation that all configured GitHub App organizations have a `webhook_secret` set before serving webhook requests for them, or log/alert when one is missing.

### Proof of Concept
Preconditions: Shipit configured with multiple GitHub orgs (per `docs/setup.md`), e.g. `victim-org` (properly secured, has a `victim-org/target-repo` stack with `continuous_deployment: true`) and `unsecured-org` (configured GitHub App with `webhook_secret` left blank).

```
POST /github_webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   # arbitrary/garbage signature

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-known-to-exist-on-github>",
  "repository": {
    "full_name": "victim-org/target-repo",
    "owner": { "login": "unsecured-org" }
  }
}
```

Flow:
1. `repository_owner` resolves to `"unsecured-org"` from `params.dig('repository','owner','login')`.
2. `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)` returns `true` immediately because that org's `webhook_secret` is blank (`return true unless webhook_secret`), regardless of the bogus `X-Hub-Signature`.
3. `create` proceeds; `PushHandler#stacks` resolves via `payload.dig('repository','full_name')` = `"victim-org/target-repo"`, finds that stack, and calls `stack.sync_github(expected_head_sha: ...)`.
4. `GithubSyncJob` runs, appends commits, and — if the stack has `continuous_deployment: true` — `trigger_continuous_delivery` fires an unauthorized deploy on `victim-org/target-repo`, whose actual signing secret was never validated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end
