### Title
Webhook signature verified against attacker-chosen `repository.owner.login`/`organization.login` while the acted-upon repository is taken from unrelated `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-GitHub-App deployment, `WebhooksController#verify_signature` selects which app config (and therefore which `webhook_secret`) to validate the request against using `repository_owner`, a value read straight out of the unauthenticated JSON body. The handlers that actually mutate state (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a separate field from the same body, `repository.full_name`. Because these are two independent, attacker-controlled fields, and because Shipit's supported multi-org configuration permits some orgs to have `webhook_secret: nil` (which makes `verify_webhook_signature` return `true` unconditionally), an attacker who can trigger delivery of an unsigned/arbitrary-signature webhook to Shipit for a low-security org can spoof `repository.owner.login` to that low-security org while setting `repository.full_name` to a stack belonging to a fully-secured org, bypassing signature enforcement for that stack.

### Finding Description
- `repository_owner` (used only for choosing the signing key to validate against) is derived from the untrusted payload: [1](#0-0) 
- `verify_signature` performs `Shipit.github(organization: repository_owner)` then checks the HMAC using that org's `webhook_secret`; if the secret is blank, verification trivially passes: [2](#0-1) [3](#0-2) 
- The event handler that performs the actual write (queuing a sync of a real `Stack`) resolves the repository from a *different* payload field, `repository.full_name`, entirely independent of `repository_owner`: [4](#0-3) [5](#0-4) 
- `PushHandler#process` then triggers `stack.sync_github` for the resolved stack, based on `full_name`, not on the owner used to authenticate: [6](#0-5) 
- Multi-organization configuration, where each org independently sets (or omits) its own `webhook_secret`, is a first-class supported feature: [7](#0-6) 

This breaks the binding: `organization authenticated == repository written`. The signature is verified against the org named in `repository.owner.login`/`organization.login`, but the record actually acted upon is selected by `repository.full_name`, a field never cross-checked against the authenticated organization.

### Impact Explanation
If any organization configured in Shipit's multi-app setup has no `webhook_secret` (a supported, documented configuration for lower-security or internal GitHub Enterprise orgs, e.g. `webhook_secret: # nil` in `test/dummy/config/secrets_double_github_app.yml:7,46`), an attacker able to reach the `/github/webhooks` endpoint can forge a `push` (or other handled) event whose `repository.owner.login`/`organization.login` claims that unsecured org, while `repository.full_name` names a stack belonging to a different, fully-secured organization. `verify_signature` passes trivially (blank secret ⇒ always verified), and the `PushHandler` will act on the targeted stack (queue `GithubSyncJob`, sync commits, potentially triggering downstream deploy/merge automation) as if it were a legitimate, signed event from the secured org. This effectively lets an attacker with no credentials for the secured org inject events that drive Shipit stack state/automation for that org's repositories — an unauthenticated write/spoofed deployment trigger, i.e. unauthorized manipulation of deploy-relevant state without possessing the correct organization's webhook secret.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with multiple GitHub Apps (a documented, supported feature), and (2) at least one configured organization to have an unset `webhook_secret` (also documented as a valid/optional configuration). Given both conditions, exploitation only requires sending one crafted, unauthenticated HTTP POST to the public webhooks endpoint — no GitHub App private key, no session, no API token is needed. Likelihood is therefore fully dependent on deployment configuration choices that the engine itself permits and documents, rather than on any additional secret-guessing or privileged access.

### Recommendation
Do not derive the signature-verification organization independently from the same untrusted fields used later to resolve the target repository/stack. Instead:
1. Resolve the target `Repository` first from `repository.full_name` (`Repository.from_github_repo_name`), and use that repository's own `owner` to select the GitHub App/`webhook_secret` for verification, ensuring both checks are bound to the same value.
2. Alternatively, after determining `repository_owner` for signature verification, re-validate that `repository.full_name`'s owner segment matches `repository_owner` (case-insensitively) before dispatching to handlers, rejecting mismatches with `422`.
3. Consider disallowing (or warning loudly on) organizations configured with a blank `webhook_secret` when multiple organizations are configured, since a blank secret on any one org effectively disables the anti-spoofing guarantee for the whole install once cross-org field confusion is possible.

### Proof of Concept
Assume `config/secrets.yml` configures two orgs as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (attacker's own installed app, deliberately left with `webhook_secret: nil`) and `OrgTwo` (target, `webhook_secret` set and secret to the attacker).

```
POST /github/webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature needed because OrgOne's webhook_secret is blank)

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/secured-repo"
  }
}
```

- `WebhooksController#repository_owner` returns `"OrgOne"` (`app/controllers/shipit/webhooks_controller.rb:59-62`).
- `Shipit.github(organization: "OrgOne").verify_webhook_signature(...)` returns `true` unconditionally because `OrgOne`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
- `PushHandler#stacks` resolves via `Repository.from_github_repo_name("OrgTwo/secured-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:33-37`, `app/models/shipit/repository.rb:53-56`), locating the real, secured stack and triggering `stack.sync_github(expected_head_sha: "deadbeef...")` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — despite the attacker never possessing `OrgTwo`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
