### Title
Accrual-time i128 overflow in debt-value multiplication permanently freezes a market before the borrow-index cap can engage - (File: common/src/rates/index.rs)

### Summary
CVE-2020-8623 is a remote crash triggered by a crafted query under a specific build configuration. The analog here is a reachable arithmetic panic in the pool's interest-accrual path: once a market's scaled debt and borrow index are large enough that `borrowed * borrow_index` overflows `i128`, `global_sync` panics on every subsequent market operation. Because every entrypoint (`supply`, `withdraw`, `borrow`, `repay`, `liquidate`/`seize`, `update_indexes`, `claim_revenue`) accrues first via `Cache::load` → `interest::global_sync`, the market is permanently bricked: no repayments, withdrawals, liquidations, or bad-debt cleanup can ever execute again.

### Finding Description
`accrue_chunk` in `contracts/pool/src/interest.rs:39-53` calls `accrue_step`, which computes supplier rewards through `calculate_supplier_rewards` in `common/src/rates/index.rs:73-89`. That function multiplies the scaled debt by both the old and new borrow index:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

`Ray::mul` panics on `i128` overflow. Although `update_borrow_index` clamps the *index* at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`), nothing clamps the *product* `borrowed_scaled * index`. On a high-decimals market (e.g., 18 decimals) carrying a whale-scale debt, the RAY-denominated debt value crosses `i128::MAX` while the index itself is still far below the cap. The same panic also fires in `calculate_utilization` via `scaled_to_original` (`contracts/pool/src/cache/scale.rs:23`) and in `calculate_supplier_rewards`' `checked_sub` chain — so every guard and view that re-reads the accrued state trips too.

The panic is not transient: indexes only move forward, and `accrue_chunk` runs inside `global_sync` before any mutation (`contracts/pool/src/interest.rs:20-33`), so there is no sequence of calls that can unwind the overflowed state. `recapitalize` and `clean_bad_debt` also load and sync the cache, so they cannot rescue the market either. The pinned regression test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates the freeze: `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`, and `last.borrow_index < MAX_BORROW_INDEX_RAY` confirms the index cap never engaged.

### Impact Explanation
Permanent freezing of funds. All supplier principal and accrued yield in the affected market become unrecoverable — `withdraw` panics during accrual before any burn or transfer. Borrower collateral locked against the market's debt cannot be released because `repay` and liquidations panic. This satisfies the "permanent freezing of funds" acceptance bar directly, not merely a fail-closed DoS: there is no recovery path since the frozen state is on-chain index/share data, not a parameter an admin can toggle.

### Likelihood Explanation
Reachable by a single unprivileged address through the standard `borrow` entrypoint. The attacker supplies collateral in a separate market (or a different spoke) and borrows as much of the target market's liquidity as caps allow — with lifted/high borrow caps, ~98% utilization is achievable, exactly as the harness test does with `lift_caps` and `borrow_raw`. Reaching the overflow additionally requires (a) a large-supplied, high-decimals market so scaled shares are large, and (b) sustained time at a steep interest-rate segment so the borrow index compounds the product past `i128::MAX`. The preconditions are demanding — a whale-scale market and prolonged high utilization — but none require privileges, leaked keys, or misconfiguration beyond normal listing parameters, and each incremental accrual is permissionlessly triggerable via `update_indexes`. Likelihood is therefore moderate-low; impact is total for that market.

### Recommendation
Saturate instead of panic in the accrual path. In `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`) and in `scaled_to_original`/`calculate_utilization` (`common/src/rates/scaling.rs:14-16`, `contracts/pool/src/cache/scale.rs:23`), use saturating multiplication (e.g., `mul_div_floor_saturating`-style helpers already used by `update_supply_index` at `index.rs:41`) so that an over-the-ceiling debt value clamps rather than traps. Additionally, cap effective scaled debt growth or clamp the index *product* at accrue time so `global_sync` always completes; a market that can no longer compute exact interest is still strictly better than one where every exit panics.

### Proof of Concept
Mirrored by `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`:

1. Build a market with an 18-decimal asset and a steep interest-rate curve (`xlm_curve`); lift spoke caps.
2. `supply_raw(BOB, "BIG18", 1e9 * 10^18)`; attacker supplies collateral in `COL` and `borrow_raw(ALICE, "BIG18", 98% of principal)` — all permissionless calls.
3. Advance ledger time yearly and call `update_indexes` each step.
4. After enough compounding, `update_indexes` fails with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY` — the cap never engages because `borrowed.mul(index)` overflows first.
5. `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", ...)` both fail with `MathOverflow`, confirming permanent freeze of supplier funds.
