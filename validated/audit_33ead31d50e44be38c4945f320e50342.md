### Title
Cross-organization webhook forgery via mismatched signature-owner and target-repository fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the `webhook_secret` configured for the organization found at `params.dig('repository', 'owner', 'login')` (or `organization.login`), but every event `Handler` subsequently resolves the repository/stack to act on using a completely different, unvalidated field: `payload.dig('repository', 'full_name')`. The signature never covers the binding between "which org's secret validated this request" and "which repository will actually be mutated."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` via: [1](#0-0) 
and uses it to fetch the GitHub App config/secret for that org and verify the HMAC over the raw body: [2](#0-1) 

The HMAC (`GitHubApp#verify_webhook_signature`) only proves the payload was signed with *some organization's* `webhook_secret` — it does not prove any relationship between `repository.owner.login` and `repository.full_name`: [3](#0-2) 

Once verification passes, `Handler#stacks` resolves the target repository purely from `payload.dig('repository', 'full_name')`, independent of `repository.owner.login`: [4](#0-3) 
`Repository.from_github_repo_name` just splits this attacker-controlled string on `/`: [5](#0-4) 

Because Shipit supports configuring **multiple GitHub organizations**, each with its own `webhook_secret` (`config/secrets.development.example.yml:18-38`), an attacker who administers their own GitHub App/organization in this Shipit instance knows a valid secret for that org and can compute a valid `X-Hub-Signature` for a payload where `repository.owner.login` is their own org (satisfying `verify_signature`) while `repository.full_name` is set to any other tracked repository, e.g. `"victim-org/victim-repo"`.

`PushHandler#process` then looks up **all matching stacks for that forged `full_name`** and calls `stack.sync_github(expected_head_sha: params.after)` for any `after` SHA the attacker supplies: [6](#0-5) 
`GithubSyncJob#perform` fetches missing commits and, when `commits_changed` and the stack has `continuous_deployment: true`, this ultimately can enqueue `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery` and deploys the newest deployable commit reachable up to that (attacker-influenced) point: [7](#0-6) [8](#0-7) 

This breaks the trust binding: **organization authenticated (via webhook secret) ≠ repository being written/deployed**.

### Impact Explanation
An attacker who controls one organization onboarded to a shared Shipit instance (a legitimate, low-privilege tenant with no Shipit session, API token, or GitHub write access to the victim repo) can forge `push`/`status`/`check_suite`/`membership` webhooks that are accepted as authentic for **any other tracked repository or organization** in the same Shipit deployment. For stacks with `continuous_deployment: true`, this can force an unauthorized deploy/rollback pointer update (`trigger_continuous_delivery`, `sync_github`) on a repository the attacker does not own or have write access to — meeting the "unauthorized deploy" Critical bar. It can also be used to forge `membership` events to add/remove team memberships (`MembershipHandler`), or `status` events to fabricate CI state (`StatusHandler`) that gates deploy eligibility for a repo the attacker doesn't control.

### Likelihood Explanation
Exploitability requires that the Shipit instance is configured with multiple GitHub organizations (a documented, supported configuration — see `config/secrets.development.example.yml` and `docs/setup.md`), and that the attacker is a legitimate but unprivileged user/administrator of one of those organizations (able to obtain their own org's `webhook_secret`). No secret belonging to the victim, no Shipit session, and no `ApiClient` token are required — only knowledge of a signing secret for a *different, unrelated* organization also configured on the same instance. This is a realistic multi-tenant scenario for the engine as documented.

### Recommendation
In `WebhooksController#verify_signature`, after computing the signing organization, additionally assert that every repository-identifying field used later by handlers (`repository.full_name`, and `organization.login` for org-scoped events) is consistent with the same organization that signed the request — e.g., verify `repository.full_name.split('/').first.casecmp(repository_owner) == 0` before dispatching to handlers, and reject (422) on mismatch. More robustly, resolve `Repository`/`Stack` records only through associations validated to belong to the authenticated organization, rather than trusting `full_name` verbatim from the payload body.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` (attacker-controlled, attacker knows its `webhook_secret`) and `victim-org` (has a Shipit stack with `continuous_deployment: true` tracking `victim-org/victim-repo`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<a real, already-existing commit SHA on victim-org/victim-repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker_webhook_secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s webhook secret, and the signature validates successfully.
5. `PushHandler` resolves stacks via `full_name` = `"victim-org/victim-repo"` and enqueues `GithubSyncJob`/`ContinuousDeliveryJob` for the victim's stack, potentially triggering an unauthorized deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
