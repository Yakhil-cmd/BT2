## Title
Race Condition from Premature Lock Release During Async Cache Eviction in `shrinkCache()` — ([File: storage.js])

## Summary
`storage.shrinkCache()` acquires the global `"write"` mutex, then fires off multiple asynchronous `db.query()` calls to identify units to evict from process memory caches (`assocStableUnits`, `assocCachedUnits`, `assocBestChildren`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`), but calls `unlock()` immediately after issuing those queries — **without waiting for their callbacks (the actual cache-deletion work) to complete**. This mirrors the root cause of CVE-2024-44934: a periodic background maintenance task releases a lock/reference before an outstanding asynchronous cleanup operation on the same shared state has finished, letting other code paths that assume exclusivity under that lock run concurrently with the tail of the "GC" cycle and observe/mutate the shared caches inconsistently.

## Finding Description [1](#0-0) 

`shrinkCache()` is scheduled every 5 minutes via `setInterval(shrinkCache, 300*1000)` [2](#0-1) . It:
1. Awaits `mutex.lock("write")` to get exclusive access to the in-memory unit caches.
2. Snapshots `arrUnits` (keys from several caches) synchronously.
3. Asynchronously reads `last_stable_mci` via `readLastStableMcIndex`.
4. Inside that callback, it loops over `arrUnits` in chunks, issuing `db.query(...)` calls whose callbacks perform `delete assocKnownUnits[row.unit]`, `delete assocCachedUnits[row.unit]`, `delete assocBestChildren[row.unit]`, `delete assocStableUnits[row.unit]`, etc. — line 2277-2291.
5. Immediately after the `for` loop that issued these unresolved `db.query` calls, it calls `unlock()` on line 2293, **without any `await`/callback chaining that waits for the queries to actually resolve and finish deleting.**

This is structurally identical to the kernel bug: the "write" lock is treated as sufficient synchronization for a background reclamation pass over the shared unit-props caches (`assocStableUnits`, `assocBestChildren`, `assocUnstableUnits` interactions via `fixIsFreeAfterForgettingUnit`), but the lock is released while part of that reclamation is still pending in flight. Once `unlock()` fires, `handleQueue()` immediately dispatches the next queued `"write"`-locked job — e.g. `writer.saveJoint()` (validating/saving a newly-posted unit) or `main_chain.markMcIndexStable()` (stabilizing units) [3](#0-2) [4](#0-3)  — which can mutate `assocStableUnits`/`assocBestChildren` for the same units that `shrinkCache`'s still-pending query callbacks will delete moments later, or vice versa (deleting an entry that a subsequent writer job just repopulated with fresh state).

`readUnitProps()` [5](#0-4)  explicitly asserts consistency between the in-memory cache and DB (`throw Error("different props of "+unit...)`), so any interleaving that leaves the cache in a state inconsistent with what a concurrent writer just committed will crash the node process the next time that unit's props are consulted.

## Impact Explanation
Because the "write" lock is released before the cache-eviction reads/deletes actually complete, a subsequent write-locked operation (unit validation/save, MC stabilization, `resetMemory`) can run and mutate `assocStableUnits` / `assocBestChildren` for a unit that `shrinkCache`'s in-flight query later deletes (or the reverse ordering), corrupting the authoritative in-memory unit-props cache that `readUnitProps`, `determineIfIncluded`, and MC-stability code rely on. This can:
- Trigger the hard consistency-check `throw Error("different props of ...")` in `readUnitProps`, crashing the node process — a node that crashes stops confirming/relaying new units.
- Silently desynchronize a node's cached view of stable/unstable units from the DB, risking incorrect stability/inclusion determinations (`determineIfIncluded` reads `assocUnstableUnits`/`assocStableUnits` directly) that could cause that node to disagree with peers on unit validity or DAG stability.

Both outcomes map to accepted impact categories (node disagreement on validity/stability; a node unable to confirm new units).

## Likelihood Explanation
`shrinkCache` runs automatically every 5 minutes on any full node whose caches exceed `MAX_ITEMS_IN_CACHE`, which happens naturally under normal network activity — no attacker interaction is strictly required to trigger the race window, though an attacker/normal user simply broadcasting units at a high enough rate to keep the "write" lock contended increases the probability that a writer job is queued and dispatched precisely during the vulnerable window between `unlock()` and the completion of the pending eviction queries. This makes the race plausible in production without any privileged access — merely posting units (something any unit poster can do).

## Recommendation
Make `shrinkCache()` await completion of all issued `db.query` eviction calls (e.g., wrap the chunked loop in `Promise.all`/`async.each` and only call `unlock()` in the final completion callback), so the "write" lock is held for the entire duration of the cache mutation, matching the kernel fix's approach of using `flush_work` to wait for any in-flight GC pass before proceeding with removal/further work on the same shared structures.

## Proof of Concept
1. Run a full node and let its in-memory unit caches grow past `MAX_ITEMS_IN_CACHE` so that `shrinkCache()` proceeds past its early-return check.
2. At the moment `shrinkCache()` calls `unlock()` on line 2293 (right after issuing but not awaiting its chunked `db.query` calls), have another unit posted to the node that requires the `"write"` lock (e.g., via `writer.saveJoint`) or an MC-stabilization pass triggered by that unit.
3. Because `handleQueue()` is invoked synchronously inside `unlock()` [6](#0-5) , the queued write job executes immediately, mutating `assocStableUnits`/`assocBestChildren` for units that `shrinkCache`'s pending `db.query` callbacks (still executing on the event loop) will delete moments later.
4. Subsequent calls to `readUnitProps()` for an affected unit hit the cache/DB mismatch assertion and crash, or `determineIfIncluded`/main-chain logic makes a stability decision based on the now-inconsistent cache.
