### Title
Cross-tenant webhook forgery via divergent `repository_owner` (query-string fallback) vs. body-derived `repository.full_name` in `#create` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret to check) using `repository_owner`, which reads from Rails' merged `params` (query string + parsed JSON body) with a fallback to `params.dig('organization', 'login')`. `#create` independently re-parses `request.raw_post` and hands the result to handlers that resolve the target repository via `payload.dig('repository', 'full_name')` [1](#0-0) . Because Rails performs only a shallow, top-level merge of query-string params into request params, an attacker can craft a JSON body whose `repository` hash omits `owner.login` and add a conflicting `organization[login]=...` query-string parameter, causing the org used for signature verification to diverge from the org that actually owns the repository the handler mutates.

### Finding Description
The binding that must hold is: `org_used_for_signature_check (params.dig('repository','owner','login') || params.dig('organization','login'))` == `org_that_owns_the_mutated_repository (JSON.parse(raw_post).dig('repository','full_name').split('/').first)`.

Code path:
- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` then calls `github_app.verify_webhook_signature(header_sig, request.raw_post)` [2](#0-1) .
- `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) , and `params` in Rails is the shallow merge of query-string parameters and the parsed JSON body, with body keys overwriting query keys only when the same top-level key is present in both.
- `#create` re-parses the raw body independently — `params = JSON.parse(request.raw_post)` — and dispatches it to handlers [4](#0-3) .
- Handlers resolve the target repository purely from the body via `payload.dig('repository', 'full_name')`, independent of whatever org was used to pick the signing secret [5](#0-4) .

Exploit: POST `/webhooks?organization[login]=attacker-org` with `Content-Type: application/json` and body `{"repository": {"full_name": "victim-org/secret-repo"}, ...}` (deliberately omitting `repository.owner.login`). Because the body JSON has no top-level `organization` key, the query-string `organization` survives the merge; because `repository.owner.login` is absent from the body, the first `dig` fails and `repository_owner` falls back to the attacker-chosen `organization` from the query string. `verify_signature` then authenticates against `attacker-org`'s `GitHubApp`. If `attacker-org` is a configured-but-secretless entry, `GitHubApp#verify_webhook_signature` unconditionally returns `true` (`return true unless webhook_secret`) regardless of the signature supplied [6](#0-5) . `#create` then re-parses the same raw body and dispatches to handlers that act on `victim-org/secret-repo`, a repository never checked against its own webhook secret.

Existing guards fail here because `verify_signature`'s org selection and `#create`'s repository resolution consult two different fields (`organization.login` vs `repository.full_name`) via two different parsing paths (merged `params` vs raw re-parsed body), and nothing enforces they resolve to the same tenant.

### Impact Explanation
An attacker who knows (or can reach) any org configured in Shipit without a `webhook_secret`, or any org whose secret they control, can force webhook handlers (pull_request, push, status, check_suite handlers, etc.) to execute against an arbitrary victim repository/stack tracked by Shipit, without ever presenting a valid signature for that victim org. Depending on which event/handler is targeted, this can label/close/reopen pull requests, alter merge-queue state, or affect commit/CI status used to gate deploys for a repository the attacker does not own or control — a cross-tenant write consistent with the Critical category ("a payload for one repository mutating another's stack, commit, task, or team"). This is repeatable against any repository already registered as a Shipit stack.

### Likelihood Explanation
Preconditions: the Shipit deployment must be configured with multiple GitHub orgs (`Shipit.github_apps`), and at least one configured org must have no `webhook_secret` set (or the attacker must control an org's secret) so the forged signature check auto-passes; the victim repository must already exist as a Shipit-tracked repository/stack. No Shipit credentials, session, or GitHub secrets are required — only the ability to send an HTTP POST to `/webhooks` with a crafted query string and JSON body. This is a low-cost, fully attacker-controlled request (no dependence on real GitHub delivery), and is repeatable at will against any victim repository/org combination that satisfies the above configuration.

### Recommendation
Derive the organization used for signature verification and the repository used by handlers from the *same* single parse of `request.raw_post`, and never fall back to `organization.login`/`params` sourced from query-string-mergeable values for signature-critical decisions. Concretely: parse `request.raw_post` once in a `before_action`, memoize it, and have both `repository_owner` and `#create` consume that memoized hash (never `params`). Additionally, treat organizations without a configured `webhook_secret` as unverifiable and reject (422) rather than auto-accepting in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest integration test plan under `test/controllers/webhooks_controller_test.rb`:
1. Configure `Shipit.github_apps` (or stub) with `attacker-org` having no `webhook_secret`, and `victim-org` with a real `webhook_secret`; create a Shipit `Repository`/`Stack` for `victim-org/secret-repo`.
2. POST to `webhooks_path(organization: { login: 'attacker-org' })` with `Content-Type: application/json` and body `{"repository": {"full_name": "victim-org/secret-repo"}, "action": "opened", "number": 1, "pull_request": {...}}`, and an arbitrary/garbage `X-Hub-Signature` header.
3. Assert `response.status == 200` (i.e., signature check passed) even though the header signature does not match `victim-org`'s HMAC secret.
4. Assert side effects occurred against `victim-org/secret-repo` (e.g., a `MergeRequest`/label state changed on that stack), proving the handler mutated the victim's data despite verification never checking `victim-org`'s secret — demonstrating `repository_owner` (`"attacker-org"`) diverged from the handler's resolved repository owner (`"victim-org"`).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
