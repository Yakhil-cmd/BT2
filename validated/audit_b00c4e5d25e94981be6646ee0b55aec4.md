### Title
Forged `push` webhook for an org with blank `webhook_secret` is accepted unconditionally, letting an unauthenticated attacker trigger `PushHandler#process` → `Stack#sync_github` on arbitrary stacks - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` delegates authentication entirely to `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally whenever the resolved org's config has no `webhook_secret` set. [1](#0-0) [2](#0-1)  Because the org that authenticates the request is picked purely from attacker-controlled `repository.owner.login`/`organization.login` in the JSON body, an unauthenticated caller can trivially satisfy the "no-secret org" condition and have any `push` payload accepted, which then unconditionally invokes `PushHandler#process`, calling `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the forged `ref`. [3](#0-2) [4](#0-3) 

### Finding Description
The invariant that should hold is: `verify_webhook_signature(signature, body) == true` **only if** `HMAC-SHA1(webhook_secret_of_org(body.repository.owner.login), body) == signature`. In `lib/shipit/github_app.rb`, the guard `return true unless webhook_secret` breaks this equality whenever the resolved org's config carries no `webhook_secret`: the function short-circuits to `true` for **any** body/signature pair, including a signature header that is absent or garbage. [2](#0-1) 

The org used to resolve `Shipit.github(organization: repository_owner)` is taken straight from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), so the attacker picks which org's (and therefore which secret's) verification path is exercised. [3](#0-2)  If that org happens to be configured in Shipit but without a `webhook_secret` (an operator configuration choice, not itself exploited by the attacker), `verify_signature` never calls `head(422)` and processing proceeds. [5](#0-4) 

`Shipit::Webhooks.for_event('push')` then dispatches to `PushHandler`, whose schema only requires `ref` and `after` — both fully attacker-controlled — and which performs `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` with no re-validation of the request's authenticity against the specific stack/repository being acted on. [6](#0-5) 

No other guard intervenes: `check_if_ping` only special-cases the `ping` event, and `drop_unhandled_event` only filters events with no registered handler — `push` has one — so the request flows straight into `verify_signature` and then `create`. [7](#0-6) 

### Impact Explanation
Because `verify_webhook_signature` returns `true` unconditionally for a no-secret org, an unauthenticated internet caller can force `Stack#sync_github` to run for every non-archived stack matching the forged `ref` within that org's repositories, at a time and `expected_head_sha` of their choosing, without ever knowing any Shipit or GitHub secret. This matches the rules' "Critical — Authentication/authorization bypass (forged webhook ... accepted as trusted)" category: the acceptance decision itself is bypassed, not merely a downstream data-integrity issue. The blast radius is scoped to stacks belonging to the specific org/repository the attacker names in the forged payload (repository is not cross-tenant-spoofable independently of this org selection), but within that scope the attacker can repeatedly and unconditionally trigger the sync/CD-adjacent pipeline entry point for a repository/org they do not administer and have never authenticated against.

### Likelihood Explanation
Preconditions: Shipit must have at least one org configured with an entry in `Shipit.github` config but a blank/absent `webhook_secret` — an operator misconfiguration, but one the code does nothing to prevent or warn about at request time. Given that precondition, exploitation cost is trivial: a single unauthenticated `POST /webhooks` with `X-Github-Event: push` and a JSON body naming that org, requiring no signature, no session, no API token, and no knowledge of any secret. It is fully repeatable and scriptable.

### Recommendation
Do not treat a missing `webhook_secret` as automatic verification success. `GitHubApp#verify_webhook_signature` should fail closed (return `false`/reject) when no secret is configured, or Shipit should refuse to register/route webhooks for orgs lacking a configured `webhook_secret`, surfacing a configuration error instead of silently accepting unauthenticated payloads.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.github` with an org (e.g. `"no-secret-org"`) whose config hash omits `webhook_secret`, matching an existing `Repository`/`Stack` fixture under that org.
2. Create a `Stack` for that org/repo with a known `branch`.
3. `POST /webhooks` with headers `X-Github-Event: push` and no (or garbage) `X-Hub-Signature`, body `{"ref": "refs/heads/<branch>", "after": "<attacker_sha>", "repository": {"owner": {"login": "no-secret-org"}, ...}}`.
4. Assert response is `200 OK` (not `422`), and assert (via mock/stub on `Stack#sync_github`) that `sync_github(expected_head_sha: "<attacker_sha>")` was invoked on the victim stack — proving `verify_signature` accepted the unsigned/forged request and `PushHandler` acted on it.
5. Binding check: before the fix, `verify_webhook_signature(nil_or_garbage_signature, forged_body) == true`; after a fix, it should `== false` and the response should be `422` with no `sync_github` call.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
