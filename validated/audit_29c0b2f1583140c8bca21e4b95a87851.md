### Title
Inconsistent `kip71.lowerboundbasefee` / `kip71.upperboundbasefee` governance votes in the same epoch invert the KIP-71 base-fee mechanism — (`kaiax/gov/headergov/impl/header.go`)

### Summary

`checkConsistency` validates each governance vote for `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` independently against the **current** (pre-epoch) parameter set. In `none` governance mode, two different GC validators can cast one vote each for these coupled parameters in the same epoch. Each vote passes its individual guard, but the combined ratification can produce `LowerBoundBaseFee > UpperBoundBaseFee`. This inverts the KIP-71 base-fee adjustment logic in `NextMagmaBlockBaseFee`, permanently corrupting the fee mechanism for all subsequent blocks.

### Finding Description

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` enforces the invariant `lower ≤ upper` per-vote:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads pre-epoch state
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads pre-epoch state
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
``` [1](#0-0) 

Each check reads `h.GetParamSet(blockNum)` — the parameter set **before** the current epoch's votes take effect. There is no cross-vote check that validates the two new values against each other.

In `none` governance mode (the default, used by all non-mainnet chains), any GC member can vote for any parameter:

> `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified. [2](#0-1) 

Scenario (epoch = E, current state: `lower = 25 gwei`, `upper = 750 gwei`):

| Block | Voter | Vote | Guard check |
|-------|-------|------|-------------|
| E+100 | Validator A | `kip71.lowerboundbasefee = 500 gwei` | `500 ≤ 750` ✓ |
| E+200 | Validator B | `kip71.upperboundbasefee = 100 gwei` | `100 ≥ 25` ✓ |

Both votes are ratified at epoch boundary `(E+1)*epoch`. The resulting state: `LowerBoundBaseFee = 500 gwei`, `UpperBoundBaseFee = 100 gwei` — **inverted**.

### Impact Explanation

`NextMagmaBlockBaseFee` in `params/kip71_config.go` clamps `parentBaseFee` to `[lower, upper]` before computing the next fee:

```go
if parentBaseFee.Cmp(upperBoundBaseFee) >= 0 {
    parentBaseFee = upperBoundBaseFee          // clamps to 100 gwei (the smaller)
} else if parentBaseFee.Cmp(lowerBoundBaseFee) <= 0 {
    parentBaseFee = lowerBoundBaseFee
}
``` [3](#0-2) 

With inverted bounds (`lower=500, upper=100`), any `parentBaseFee` above 100 gwei is clamped to 100 gwei. Then:

- **High gas usage** (`parentGasUsed > gasTarget`): shortcut fires because `parentBaseFee == upperBoundBaseFee`, returns `upperBoundBaseFee = 100 gwei` — fee **decreases** under congestion.
- **Low gas usage** (`parentGasUsed < gasTarget`): computed `nextBaseFee` is below `lowerBoundBaseFee = 500 gwei`, so it is clamped to `500 gwei` — fee **increases** when idle. [4](#0-3) 

This permanently inverts the EIP-1559-style fee adjustment: congestion lowers the base fee and idle periods raise it. Every transaction's `effectiveGasPrice` is computed from this corrupted base fee, directly affecting KAIA fee payments to validators and the burn amount computed in `getBurnAmountKore`. The corruption persists across all subsequent blocks until a corrective governance vote is ratified (another full epoch away).

### Likelihood Explanation

`none` governance mode is the **default** (`DefaultValue: "none"` in `kaiax/gov/param.go`) and is used by all chains that do not explicitly configure `single` mode. Two GC validators acting independently — without coordination or malicious intent — can each vote for one of the two coupled parameters in the same epoch. No single actor needs to intend the inconsistency; it arises from the absence of a cross-vote guard at ratification time. [5](#0-4) 

### Recommendation

Add a cross-vote consistency check at ratification time in `getExpectedGovernance` (or equivalently in `VerifyGov`). After collecting all votes for the epoch, verify that the resulting `(LowerBoundBaseFee, UpperBoundBaseFee)` pair satisfies `lower ≤ upper` before writing the `header.Governance` field. If the invariant is violated, drop the offending vote(s) or reject the epoch's governance update entirely.

Alternatively, extend `checkConsistency` to also inspect pending same-epoch votes for the counterpart parameter, so that a vote for `kip71.lowerboundbasefee` is rejected if a same-epoch vote for `kip71.upperboundbasefee` would produce an inversion, and vice versa.

### Proof of Concept

1. Deploy a chain with `governance.governancemode = "none"`, `kip71.lowerboundbasefee = 25000000000` (25 gwei), `kip71.upperboundbasefee = 750000000000` (750 gwei).
2. In epoch `k`, validator A proposes a block with `header.Vote = ("kip71.lowerboundbasefee", 500000000000)`. `checkConsistency` passes: `500e9 ≤ 750e9`.
3. In the same epoch `k`, validator B proposes a block with `header.Vote = ("kip71.upperboundbasefee", 100000000000)`. `checkConsistency` passes: `100e9 ≥ 25e9`.
4. At epoch block `(k+1)*epoch`, both votes are ratified. `header.Governance = {"kip71.lowerboundbasefee": 500e9, "kip71.upperboundbasefee": 100e9}`.
5. From block `(k+1)*epoch` onward, `NextMagmaBlockBaseFee` is called with `LowerBoundBaseFee=500e9 > UpperBoundBaseFee=100e9`. Under high gas usage the base fee collapses to 100 gwei; under low gas usage it is forced to 500 gwei — the opposite of the intended KIP-71 behavior. All KAIA fee payments and burn amounts are computed from this corrupted value for every subsequent block.
