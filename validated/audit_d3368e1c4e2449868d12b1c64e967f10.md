### Title
Webhook Signature Verification Silently Bypassed When `webhook_secret` Is Unconfigured, Enabling Unauthenticated Forgery of Team-Membership Events — Escalation into `Shipit.github_teams` Authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` treats an unconfigured `webhook_secret` as an automatic pass rather than a fail-closed condition. Because the webhook controller derives the GitHub App configuration (and thus which secret to check) entirely from attacker-controlled payload fields, any organization in a multi-organization Shipit deployment that has not set a `webhook_secret` (explicitly documented as "optional") allows any unauthenticated actor to POST forged webhook events to `/webhooks`, including `membership` events that directly manipulate `Team` membership used for authorization decisions.

### Finding Description
The webhook signature check is: [1](#0-0) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If `webhook_secret` is blank for the app configuration resolved for the request, verification unconditionally succeeds regardless of the `X-Hub-Signature` header content.

The controller determines *which* organization's app config (and therefore secret) to use purely from the untrusted JSON body itself: [2](#0-1) [3](#0-2) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` — a value entirely controlled by the sender. `Shipit.github(organization: repository_owner)` then loads whatever config exists for that organization key (see `Shipit.github_app_config`, `lib/shipit.rb` lines 196-200), and if that org's config has no `webhook_secret`, `verify_signature` passes for *any* payload claiming to be from that organization, without needing to know any secret.

Once verification "succeeds," `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs unauthenticated-attacker-controlled data through real handlers, e.g.: [4](#0-3) 

This handler finds-or-creates a `Team` and adds/removes an arbitrary `member` (a GitHub login of the attacker's choosing) based solely on payload content — no cross-check that the "membership" event genuinely originated from GitHub for that org.

That team membership is exactly what governs application authorization: [5](#0-4) 

```
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
```

and the login-side gate: [6](#0-5) 

This breaks the intended binding: the organization whose signature was supposedly verified vs. the organization/team membership state actually written. When the resolved org has no secret, "verified organization" is a vacuous check — the attacker fully controls both the claimed organization and the mutation performed.

### Impact Explanation
High — escalation into `Shipit.github_teams` authorization. An unauthenticated network attacker who knows (or guesses) that a configured organization lacks a `webhook_secret` can forge a `membership` webhook adding their own GitHub login (once they log in via the normal OAuth flow and a `User` record with that login/`github_id` exists or is created) to a `Team` that is included in `Shipit.github_teams`, making `current_user.authorized?` true and granting access to the whole Shipit UI/API surface that is otherwise gated by team membership. This does not require any Shipit session, API token, webhook secret knowledge, or repository write access — the only precondition is an operator having left `webhook_secret` blank for one organization, an explicitly supported ("optional") configuration per `docs/setup.md`.

### Likelihood Explanation
Moderate. It requires a specific but realistic operational condition: at least one configured GitHub organization in `secrets.github` without a `webhook_secret`. The setup documentation explicitly calls this optional, so this is a plausible (not purely theoretical) deployment state, especially in early setup, staging, or multi-org configurations where the secret was only set for the primary org. The exploit itself requires no privileged access — it is a single unauthenticated HTTP POST.

### Recommendation
Change `verify_webhook_signature` to fail closed when no secret is configured (treat missing `webhook_secret` as a hard misconfiguration error rather than an automatic pass), and/or require `webhook_secret` to be present for every configured organization at boot/validation time. Additionally, consider deriving the "organization" used for authentication from a source that isn't fully attacker-controlled JSON, or independently confirming that the resolved organization actually owns the acted-upon repository/team via an authenticated GitHub API call before mutating authorization-relevant state such as `Team` membership.

### Proof of Concept
1. Deploy Shipit with two organizations configured in `secrets.github`; org `victim-org` intentionally has no `webhook_secret` set (per docs, this is optional).
2. As an unauthenticated attacker, log in via normal GitHub OAuth once so a `User` row exists for your GitHub login/`github_id`.
3. Send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com"},
  "organization": {"login": "victim-org"},
  "member": {"login": "<attacker-github-login>"}
}
```
No valid `X-Hub-Signature` is required, since `Shipit.github(organization: "victim-org").verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
4. `Shipit::Webhooks::Handlers::MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) creates/updates the `Team` and adds the attacker's `User` as a member.
5. If that team's id is included in `Shipit.github_teams`, the attacker's subsequent authenticated session now passes `User#authorized?` (`app/models/shipit/user.rb:80-82`) and gains access previously restricted to that team.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
