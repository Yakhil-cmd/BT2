### Title
`StatusHandler#process` binds forged CI status by SHA alone, letting an attacker-controlled repository's status write into an unrelated stack's commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target `Commit` rows solely via `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every other webhook handler (`push_handler.rb`, `pull_request/*_handler.rb`) which resolve the target stack through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` or the `Handler#stacks` helper. Because git SHAs are content-addressed, an attacker who mirrors a victim's public commit (identical tree/parents/message/timestamps) into their own repository produces a `Commit` row with the same `sha` in a different `Stack`, and a legitimately-signed status webhook from the attacker's own repo will be applied to the victim's commit as well.

### Finding Description
The broken binding: the code must enforce `status.stack_id == Repository.from_github_repo_name(payload.repository.full_name).stack_id` for the commit the status is attached to, but the actual code enforces only `commit.sha == payload.sha`, with `status.stack_id := commit.stack_id` taken from whichever `Commit` rows happen to share that SHA.

Concretely:
- `Shipit::Webhooks::Handlers::StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
- `Commit#create_status_from_github!` creates the `Status` using the found commit's own `stack_id`, not any value derived from the webhook payload's repository:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [2](#0-1) 
- `Status.replicate_from_github!` writes the row keyed on that `stack_id`:
```ruby
def replicate_from_github!(stack_id, github_status)
  find_or_create_by!(
    stack_id:,
    state: github_status.state,
    ...
  )
end
``` [3](#0-2) 
- The `commits` table's uniqueness constraint is scoped to `(sha, stack_id)`, not `sha` alone, confirming the schema explicitly allows the *same SHA to exist under multiple stacks* (e.g., forks tracked as separate stacks):
```ruby
add_index :commits, %i(sha stack_id), unique: true
``` [4](#0-3) 

Other handlers do bind to the reporting repository before touching any stack, e.g. `Handler#stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [5](#0-4) 
and the PR handlers resolve `repository` from `params.repository.full_name` before scoping any action to that repo's stacks. `StatusHandler` skips this entirely and never reads `payload['repository']` at all - the `params` schema for `StatusHandler` doesn't even require a `repository` field, and `process` never consults it. [6](#0-5) 

Exploit flow:
1. Victim owns `victim/repo` with `Stack V` tracking commit `sha=X` (public commit).
2. Attacker forks or independently creates `attacker/repo`, and constructs a commit with identical tree/parents/author/committer/timestamps/message so it hashes to the same `sha=X` (trivial for content-addressed git objects - e.g., cherry-pick/rebase-preserving copy). Attacker's own Shipit stack (`Stack A`, already onboarded/trusted with a valid GitHub App/webhook secret for the attacker's own account/org) ingests this commit, creating a second `Commit` row `(sha: X, stack_id: A)`.
3. Attacker's own CI (which they fully control) posts a `success` status to GitHub for `attacker/repo@X`. GitHub relays a `status` webhook, correctly signed with the attacker's own org's webhook secret. `WebhooksController#verify_signature` passes because it resolves the GitHub App via `repository_owner` from the payload, which legitimately is the attacker's own org - no signature forgery needed. [7](#0-6) 
4. `StatusHandler#process` runs `Commit.where(sha: 'X')`, which returns **both** `(sha:X, stack_id:A)` and `(sha:X, stack_id:V)`. It calls `create_status_from_github!` on each - including the victim's commit - creating a `success` `Status` row with `stack_id: V` attached to the victim's `Stack V`, even though `Stack V` never received any real GitHub status from its own repository. [1](#0-0) 
5. `Shipit::Stack#next_commit_to_deploy` calls `commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)` and `deployable_commits`, which will now see the forged `success` status and select the affected commit as deployable for `Stack V`, even absent any real CI success from the victim's own repository. [8](#0-7) 

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) do not stop this because they validate the webhook's authenticity for the *attacker's own* organization/repository, not whether that repository is the one that owns the target `Commit`/`Stack`. `StatusHandler` simply never checks `payload['repository']` against the found commit's stack repository.

### Impact Explanation
A forged/attacker-controlled CI signal (fully within the attacker's control on their own repository) is written into an unrelated victim `Stack`'s `Status` table and consumed by `Stack#next_commit_to_deploy`/`deployable_commits`, causing the victim's continuous-delivery pipeline to select and deploy a commit that never received real CI success reporting against the victim repository's own GitHub status API. This is a cross-tenant integrity violation ("a payload for one repository mutating another's stack, commit, task or team") and can lead to an unauthorized deploy of attacker-influenced content, matching the Critical impact category. It is repeatable against any victim stack whose undeployed backlog contains a commit whose SHA the attacker can reproduce in a repository they control (any public commit is trivially reproducible in git since SHAs are pure functions of commit content).

### Likelihood Explanation
Preconditions: the attacker must (a) control a repository that is already tracked as a Shipit stack (a self-service, low-privilege action in typical Shipit deployments - onboarding one's own fork/repo), (b) be able to reproduce an identical SHA to a victim's undeployed commit (trivial for public commits: fork + preserve tree/parents/author/committer/message/timestamps), and (c) control CI for their own repository to post a `success` status (trivial - attacker owns the repo). No secrets, tokens, or signature forgery are required; the webhook is genuinely and correctly signed for the attacker's own organization. This is low-cost and fully repeatable against any target stack meeting the SHA-collision precondition.

### Recommendation
Scope `StatusHandler#process` to the repository that emitted the webhook, mirroring `Handler#stacks`/other handlers: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `commit.stack_id` values belonging to that repository's stacks (e.g. `stacks.commits.where(sha: params.sha)` or joining through `Stack` to `Repository`) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (model/handler level, no live GitHub):
```ruby
test "StatusHandler does not attach a status to a commit belonging to an unrelated repository/stack" do
  victim_stack = shipit_stacks(:shipit)          # tracks repository "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse)      # tracks a different repository, e.g. "attacker/repo"

  shared_sha = "deadbeef" * 5 # arbitrary 40-char sha shared by both commits

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                 authored_at: Time.now, committer: shipit_users(:walrus),
                                                 committed_at: Time.now, message: "shared content")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:bob),
                                                     authored_at: Time.now, committer: shipit_users(:bob),
                                                     committed_at: Time.now, message: "shared content")

  payload = ExplicitParameters::Parameters.new(
    sha: shared_sha, state: "success", context: "ci/attacker",
    repository: { full_name: attacker_stack.repository.full_name }
  )

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(
      "sha" => shared_sha, "state" => "success", "context" => "ci/attacker",
      "repository" => { "full_name" => attacker_stack.repository.full_name }
    )
  end

  refute_predicate victim_commit.reload, :deployable? # binding: victim_commit.statuses.stack_id must never equal victim_stack.id via attacker's webhook
end
```
Binding to assert on both sides: before the fix, `victim_commit.statuses.pluck(:stack_id)` includes `victim_stack.id` after the attacker-repo webhook fires (`assert_includes`) - demonstrating the bug; after the fix, it must be empty/excluded (`assert_not_includes`), and `victim_stack.next_commit_to_deploy` must not equal `victim_commit` when only the attacker's repository reported success.
