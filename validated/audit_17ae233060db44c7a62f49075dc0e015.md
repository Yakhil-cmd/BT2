### Title
Webhook signature verification uses attacker-selectable `repository.owner.login` while handlers act on independently-controlled `repository.full_name`, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* per-organization `webhook_secret` to validate a request against based on a field taken from the unauthenticated JSON body itself, while the handlers that actually mutate state key off a *different* field of that same body to decide which repository/stack to act on. In a multi-organization Shipit deployment these two fields are not required to agree, so a party who legitimately owns one configured GitHub App/organization can forge a webhook that is "correctly" signed with their own secret but targets any other organization's repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the organization used to fetch the `GithubApp` (and therefore the `webhook_secret` used for HMAC verification) from the request payload itself: [1](#0-0) [2](#0-1) 

Shipit supports configuring multiple independent organizations, each with its own `webhook_secret`, in the same instance: [3](#0-2) 

Once the signature check passes, `create` dispatches the raw parsed payload to event handlers unmodified: [4](#0-3) 

Handlers, however, resolve the target repository/stack from a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login` (the field used to select the signing secret): [5](#0-4) 

This is the exact class of bug in the external report: a value the code trusts implicitly (there, USDT's non-standard `approve` return; here, the correspondence between `repository.owner.login` and `repository.full_name`) is not actually enforced/covered by the guard that is supposed to bind it. Concretely, the binding "the organization whose secret authenticated this request" == "the repository the handler is about to write to" is never checked — both values are attacker-supplied fields inside the same JSON body, and only the first is covered by the security check.

`StatusHandler` illustrates a directly state-mutating consumer of the unchecked field: it looks up commits purely by `sha` (global, not even scoped by repository) and writes attacker-supplied status fields to them: [6](#0-5) 

`PushHandler` similarly acts on whatever repository/stack `repository.full_name` resolves to: [7](#0-6) 

### Impact Explanation
An attacker who administers even one of the organizations configured in this Shipit instance's `secrets.yml` (i.e., they legitimately know that org's `webhook_secret` because they control that org's GitHub App settings) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org, so `verify_signature` fetches and validates against a secret they know.
2. Set `repository.full_name` to a victim organization's repository that Shipit also tracks.
3. Send this forged, but "validly signed" (from Shipit's perspective) webhook to `/webhooks`.

This lets the attacker inject fabricated GitHub `status` events (`create_status_from_github!`) against commits belonging to a repository they do not own, potentially marking a commit as passing required checks and enabling it to become deployable/ship-eligible under continuous delivery, or force arbitrary resyncs (`stack.sync_github`) of victim stacks via `push` events. Depending on the receiving organization's continuous-delivery configuration, a forged "success" status on an otherwise-unreviewed commit can lead to an unauthorized deploy — matching the Critical impact bar ("an unauthorized deploy").

### Likelihood Explanation
This requires the attacker to control at least one organization/GitHub-App entry already configured in the target Shipit instance's secrets — i.e., it is only exploitable in genuinely multi-tenant Shipit deployments where multiple distinct organizations (with different trust levels) share one instance, as documented by `config/secrets.development.shopify.yml`. Within that documented deployment model, no additional privilege (no Shipit session, no `ApiClient` token, no GitHub repo write access to the victim repo) is required — only knowledge of one's own org's webhook secret, which is a normal, expected credential for a Shipit-onboarded organization administrator.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, re-derive the acting repository/organization strictly from the same field that was authenticated, or explicitly assert `repository.full_name.start_with?("#{repository_owner}/")` before dispatching to handlers. More robustly, scope each handler's repository/commit lookups to the organization whose secret authenticated the request, rather than trusting the independent `repository.full_name` field.

### Proof of Concept
Assume Shipit is configured with two orgs, `attacker-org` (attacker administers it, knows its `webhook_secret`) and `victim-org` (tracked repo `victim-org/app`, unrelated to attacker).

1. Attacker crafts a `status` event payload:
```json
{
  "sha": "<known commit sha in victim-org/app>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)`.
3. `verify_signature` resolves `repository_owner` = `"attacker-org"` [2](#0-1)  , fetches `attacker-org`'s `GithubApp`, and the signature verifies successfully since the attacker legitimately owns that secret.
4. `create` dispatches to `StatusHandler`, which finds the commit by `sha` (global lookup, no owner check) [6](#0-5)  and writes an attacker-controlled "success" status onto a commit in `victim-org/app`, despite the attacker never having been authenticated by `victim-org`'s webhook secret.
