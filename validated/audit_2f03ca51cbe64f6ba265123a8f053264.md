### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on `repository.full_name`, letting an attacker forge cross-organization writes via an unsecured org identity - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using the `repository.owner.login` field parsed from the attacker-controlled JSON body. The event handlers that actually mutate state (create commits, update statuses, process pull requests, trigger syncs/deploys) resolve the target `Repository`/`Stack` using a *different* field from the same body — `repository.full_name` — via `Repository.from_github_repo_name`. These two fields are never cross-validated. In a multi-org Shipit deployment, if any one configured organization has no `webhook_secret` set (the documented/default configuration), an attacker can craft a payload whose `repository.owner.login` names that unsecured org (making signature verification trivially pass) while `repository.full_name` names a repository belonging to a different, secured organization — causing Shipit to process the payload as an authenticated webhook for the secured org's repository/stack.

### Finding Description
`verify_signature` picks the app/secret via the untrusted `repository_owner`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` returns `true` unconditionally whenever the resolved org's `webhook_secret` is blank: [3](#0-2) 

Multi-org configuration is a documented, supported pattern, and `webhook_secret` is explicitly optional/nilable per-org: [4](#0-3) [5](#0-4) 

Meanwhile, the handlers that perform the actual write use a *different* field from the same untrusted body — `repository.full_name` — to resolve the repository being acted upon, completely independent of which org's secret validated the request: [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` looks up any repository by `owner/name`, with no requirement that this `owner` match the `repository.owner.login` used for signature selection: [8](#0-7) 

The equality that is broken is: **organization that authenticated (`repository_owner` used to select the verifying `webhook_secret`) ≠ repository that is written (`repository.full_name` used by handlers to locate the target `Repository`/`Stack`)**. Because a JSON body is fully attacker-controlled and these two fields are independent strings within it, nothing enforces that they refer to the same repository.

### Impact Explanation
An attacker who knows (or engineers) that at least one configured GitHub organization in the Shipit installation has no `webhook_secret` — the literal default in the example configuration — can send a forged webhook whose `repository.owner.login` is that unsecured org (so `verify_signature` passes unconditionally) but whose `repository.full_name` points at a repository under a different, secured organization. Handlers like the push/status/pull_request handlers will then process the payload as if it were a legitimately signed webhook for that other repository, allowing unauthorized commit/status creation, sync job triggering, or pull request state changes for a repository the attacker does not control and could not otherwise forge a valid signature for. This is a cross-repository write / unauthenticated write primitive across organizational trust boundaries, matching the Critical impact category ("cross-repository writes" / effectively an authentication bypass for the write path).

### Likelihood Explanation
Exploitability requires only: (1) a multi-org Shipit configuration (documented, supported), and (2) at least one configured org left with the default `webhook_secret: nil` (explicitly shown as the standard/example value). No credentials, GitHub App private key, or valid signature are needed for the targeted secured org. The attacker only needs to POST a crafted JSON body to the public `/webhooks` endpoint with mismatched `owner.login` / `full_name` fields — a simple, unprivileged HTTP request.

### Recommendation
Bind the signature verification identity to the same field used for repository resolution: derive `repository_owner` from the same `full_name` (or vice versa) that handlers use, or explicitly validate that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers. Additionally, consider rejecting webhooks entirely for any organization not configured with a webhook secret rather than treating a blank secret as an implicit skip, and/or verify the resolved `Repository`'s configured organization matches the organization whose app credentials validated the signature.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `OrgA` (no `webhook_secret` set) and `OrgB` (secured, has `webhook_secret` and a Stack tracking `OrgB/target-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/<tracked-branch>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. The push handler resolves the target stack/repository via `repository.full_name` = `OrgB/target-repo`, and processes the forged commit/sync for `OrgB`'s stack — without ever presenting a signature valid for `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
