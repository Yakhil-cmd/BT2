### Title
Any caller can force-adverse restamp a victim's liquidation parameters to the edge of the health-factor gate via `update_account_threshold` - (File: contracts/controller/src/risk/params.rs)

### Summary
XOXNO Lending stamps each supply position with the spoke listing's LTV, liquidation threshold, liquidation bonus, and liquidation fee at creation (`get_or_create_supply_position`), and afterwards uses the stored values rather than live listing values. Refreshing the adverse tuple (lower LT, higher bonus, lower fee) requires the HF-gated `apply_gated_liquidation_params`, but the refresh is callable by *anyone* through `update_account_threshold(caller, has_risks = true, account_ids)` — the `account_ids` are arbitrary and only `caller` needs auth. As in the Cooler `toggleRoll` report, a user holding favorable stamped terms has no way to opt out: a third party can unilaterally re-stamp the victim's position to the worst terms the 1.05 HF gate permits, at the moment of the attacker's choosing.

### Finding Description
`update_account_threshold` in `contracts/controller/src/risk/params.rs:124` authenticates only `caller` (`require_authorized_caller`) and then iterates over any supplied `account_ids`, calling `sync_account_thresholds` on each — there is no ownership check on the target accounts [1](#0-0) .

For each supply position, `refresh_supply_risk_params` routes through `apply_gated_liquidation_params` (`params.rs:68`), which applies the new `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` whenever the change "favors the liquidator" (`params.rs:96`) provided the account's HF with the new LT is at least 1.05 WAD (`params.rs:78-88`, `params.rs:103-119`). The batch ends with a final HF ≥ 1.05 assertion (`params.rs:221-233`), so the call succeeds while leaving the victim at exactly HF ≈ 1.05 — the minimum margin — instead of the higher HF the victim's originally stamped terms gave them.

The victim cannot prevent this: unlike the Cooler lender who could call `toggleRoll`, there is no opt-out or consent step; the only protection is the protocol-level gate, which caps the damage at HF 1.05 rather than eliminating it.

### Impact Explanation
After a governance `edit_asset_in_spoke` that lowers LT, raises the bonus, or lowers the fee, affected accounts keep their old, safer stamps indefinitely — until someone restamps them. An attacker can pick the moment that maximizes harm: e.g., restamp a victim whose HF would land just above 1.05, stripping the victim's safety buffer so the next minor price drift (or the attacker's own subsequent liquidation setup) makes the account liquidatable, with the newly raised bonus / lowered fee also improving the liquidation terms against the victim. This is an unconsented worsening of a user's position terms that directly enables earlier liquidation of the victim's collateral — theft of user funds via forced liquidation, the same class as rolling a loan against the lender's will.

### Likelihood Explanation
Requires a governance parameter change that produces a liquidator-favoring diff plus a victim whose HF sits in the (1.05, old-terms-HF) band. Both conditions occur naturally during parameter retuning, and the attack transaction is a single permissionless call with negligible cost. Medium likelihood, matching the external report's Medium severity.

### Recommendation
Restrict `update_account_threshold` with `has_risks = true` to the account owner (or an authorized delegate) for each `account_id`, keeping the permissionless path only for `has_risks = false` (LTV-only refresh, which does not affect liquidation terms). Alternatively, allow a permissionless full-tuple refresh only when it strictly improves the account's health factor.

### Proof of Concept
1. Governance executes `AdminOperation::EditAssetInSpoke` lowering USDC's liquidation threshold from 6000 to 5300 (cf. `docs/reference/runbooks/liqvid-listing-params.md` §10, and the scenario exercised in `tests/test-harness/tests/controller/liqvid_listing_params.rs:762` and `tests/integration/flows/admin.sh:84-92`).
2. Victim account, stamped with LT 6000, has HF 1.19 under the old terms — comfortably healthy.
3. Attacker (e.g., `BOB`, an unrelated address) calls `update_account_threshold(caller = BOB, has_risks = true, account_ids = [victim])`. `apply_gated_liquidation_params` computes the hypothetical HF with LT 5300 = 1.051 ≥ 1.05, applies the tuple, and the final HF check passes.
4. The victim's HF is now 1.05 instead of 1.19, without any action or consent by the victim; a small adverse price move makes the account liquidatable, where under its original stamps it would have remained healthy.

```rust
pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
}
```
