### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no constraint tying the matched commit's stack/repository to the organization whose `webhook_secret` authenticated the request. An attacker who controls a repository registered in Shipit can push a commit whose sha collides with (or is copied from) a victim commit's sha and forge a `status` webhook, signed with their own org's secret, that mutates the victim's commit CI state.

### Finding Description
The broken binding is: `organization_that_signed_request` (derived in `WebhooksController#verify_signature` from `params.dig('repository','owner','login')`, verified via `Shipit.github(organization: repository_owner).verify_webhook_signature`) should equal `organization_owning(commit.stack.repository)` for every commit mutated by the handler — but it does not.

Path traced:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the HMAC signature matches `Shipit.github(organization: repository_owner)`'s `webhook_secret`, where `repository_owner` is attacker-controlled JSON (`repository.owner.login`) equal to `'attacker'`. It never inspects or restricts which commits/stacks the payload will be applied to.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, unscoped lookup by `sha` across **all stacks/repositories** in the Shipit instance. There is no `commit.stack.repository.owner == repository_owner` (or any org/stack) check before calling `commit.create_status_from_github!(params)`.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) writes a new `Status` row and, via `add_status`, can flip `deployable?`, trigger `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` if the new status is `success` — i.e., it can unblock continuous delivery / merges for the victim stack.

Exploit: attacker registers `attacker/repo` in Shipit (org `attacker` has its own `webhook_secret`); attacker pushes a commit into their own history whose sha is identical to `shipit_commits(:victim)`'s sha (trivial since Shipit trusts any 40-hex string as a sha, and git shas are not scoped to a repo — an attacker can create an empty/rebased commit reproducing the exact same tree/parent/author/committer/timestamp metadata, or simply reuse a publicly known victim sha string in the JSON payload since the handler never asks GitHub to confirm the sha exists in `attacker/repo`). Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body `{sha: SHARED_SHA, state: 'success', repository: {owner: {login: 'attacker'}}}`, signed with the attacker's own webhook secret. `verify_signature` passes because the signature matches `attacker`'s secret and the check never looks past `repository_owner`. `StatusHandler` then matches the victim's `Commit` row by sha alone and calls `create_status_from_github!`, writing a forged `success` status onto the victim commit, potentially unblocking deploys/merges in `victim-org`.

No existing guard prevents this: `verify_signature` authenticates the *sender org*, not the *target commit's org*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape (`sha`, `state`, etc.), not ownership; there is no `stacks`-scoping, `Repository` format validator, or `subset`/`url` validator applied in this path that ties the matched `Commit` to the signing organization.

### Impact Explanation
A payload for one repository (`attacker/repo`) mutates another tenant's stack/commit (`victim-org/victim-repo`'s `Commit#statuses`), which is explicitly listed as a Critical-severity category ("a payload for one repository mutating another's stack, commit, task or team"). The forged `success` status can make `Commit#deployable?` true and trigger `stack.schedule_merges`, i.e., attacker-influenced automatic merge/deploy behavior for a repository the attacker does not own or control. This is repeatable against any commit sha the attacker can learn (commit shas are frequently public, e.g., visible in PRs, CI logs, git history), and generalizes to any organization onboarded to the same Shipit instance — the blast radius spans all tenants sharing one Shipit deployment.

### Likelihood Explanation
Preconditions are modest and attacker-controlled: attacker needs (a) any Shipit-registered organization/repo of their own with a working `webhook_secret` (a normal, unprivileged Shipit onboarding), and (b) the target commit's sha, which is typically public information. No Shipit session, API token, or victim secrets are required. Producing a sha collision is not "SHA-1 collision" in the cryptographic sense — it is simply copying/reusing a known 40-character sha string in the JSON body, since Shipit's `StatusHandler` never verifies against GitHub that the sha actually belongs to the repository named in the payload. This makes the attack cheap, deterministic, and repeatable per victim commit.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to the repository/organization that authenticated the webhook. Concretely, join through `Commit#stack#repository` and require it to match `repository_owner`/`repository.full_name` from the payload before calling `create_status_from_github!`, e.g.:
```ruby
Commit.joins(stack: :repository)
      .where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })
      .each { |commit| commit.create_status_from_github!(params) }
```
Pass `repository_owner`/`repository_name` (already computed and verified in `WebhooksController`) down to handlers, and apply the same repository-scoping fix to any other handler that resolves records purely by `sha` (e.g. `CheckRunHandler`, `RefreshCheckRunsJob`-adjacent handlers) if they share this pattern.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (add to existing suite)
test "#process does not update commits belonging to a different repository/organization" do
  victim_stack = shipit_stacks(:shipit) # belongs to some victim org/repo
  victim_commit = shipit_commits(:first) # sha belongs to victim_stack
  attacker_repository_owner = 'attacker' # distinct org, registered with its own webhook_secret

  # Binding under test:
  # organization_that_signed_request ('attacker') != organization_owning(victim_commit.stack.repository)
  assert_not_equal attacker_repository_owner, victim_commit.stack.repository.owner

  previous_state = victim_commit.status.state
  refute_equal 'success', previous_state

  params = Webhooks::Handlers::StatusHandler.const_get(:PARAMS_SCHEMA) rescue nil
  handler_params = ExplicitParameters::Parameters.new(
    sha: victim_commit.sha,
    state: 'success',
    repository: { owner: { login: attacker_repository_owner } }
  )

  Shipit::Webhooks::Handlers::StatusHandler.new(handler_params).process

  victim_commit.reload
  assert_equal 'success', victim_commit.status.state, "attacker-signed payload mutated victim commit's status"
end
```
This test bypasses HTTP/signature layers to directly assert the handler-level flaw: even though the acting/signing organization differs from the commit's owning organization, `StatusHandler#process` still updates the victim's commit state, proving the missing binding.
