### Title
Cross-organization commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub *organization* derived from the payload's `repository.owner.login` (or `organization.login`) field, but `Shipit::Webhooks::Handlers::StatusHandler#process` then writes the commit status to **any** `Shipit::Commit` in the entire database whose `sha` matches, with no check that the commit's stack/repository belongs to the organization that was actually authenticated. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
The webhook signature check resolves the GitHub App/secret solely from the org name embedded in the payload and verifies the HMAC against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

Once verified, the controller dispatches to registered handlers without any further binding of the payload's declared repository/org to what gets mutated: [3](#0-2) 

For the `status` event, `StatusHandler` looks up the target commit **purely by SHA**, ignoring `repository.full_name`/owner entirely, unlike sibling handlers (e.g. `PushHandler`, `PullRequest::*Handler`) which scope via `Repository.from_github_repo_name(params.repository.full_name)`: [4](#0-3) 

Compare with the base `Handler#stacks`/`#repository_name` pattern that other handlers use to scope by repo: [5](#0-4) [6](#0-5) 

Shipit explicitly supports one GitHub App/webhook_secret shared across multiple organizations, or per-org secrets configured under distinct top-level keys: [7](#0-6) 

Because Shipit deployments frequently manage stacks for many different organizations/repositories under one installation (or the same shared secret across orgs), a `status` webhook that is validly signed for **organization A** (attacker-controlled or otherwise legitimately onboarded) can carry an arbitrary `sha` that happens to match a commit belonging to a stack owned by **organization B**. `StatusHandler` will apply the forged state/context/description to that commit regardless of which org's secret validated the request: [8](#0-7) 

This directly affects deployability, since commit status gates `deployable?`: [9](#0-8) [10](#0-9) 

### Impact Explanation
This qualifies as **High** ("escalation into `Shipit.github_teams` authorization" analog / unauthorized state mutation across repository boundaries) and can rise to **Critical** ("unauthorized deploy") because forging a `success` status for `ci.require`d contexts on a victim stack's pending commit can flip that commit to `deployable?`, enabling continuous-delivery or manual deploy triggers to proceed on code that never actually passed CI in the victim's own pipeline — all without possessing that victim's webhook secret, ApiClient token, or repository write access; the attacker only needs a valid signature for *some* org already integrated with the same Shipit instance.

### Likelihood Explanation
Requires: (1) knowledge of a target commit SHA present in a Shipit-managed stack (often discoverable via public commits, GitHub UI, or Shipit's own public stack pages), and (2) the ability to produce a webhook validly signed by any organization onboarded to the same Shipit deployment (a very low bar in multi-org configurations, since it is exactly the scenario the "Using Multiple Github Applications" documentation encourages, and the app being installed on the attacker's own org's repos is a normal, low-privilege event GitHub allows). No repository write access, admin token, or `webhook_secret` for the *target* org is needed.

### Recommendation
Scope the `status` handler's commit lookup by the payload's `repository.full_name`/owner, mirroring the pattern used in `PushHandler` and the `PullRequest::*` handlers (`Repository.from_github_repo_name(...).stacks` before matching by SHA), so that the org that authenticated the webhook must actually own the repository/commit being mutated.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with the GitHub App installed on `org-victim` and `org-attacker`, each with its own `webhook_secret`.
2. Attacker installs/owns `org-attacker` and knows (or brute-forces via public GitHub data) that `org-victim`'s stack has a pending commit with `sha = abc123` requiring context `ci/circleci` to be `success` before deploy.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a body `{"sha":"abc123","state":"success","context":"ci/circleci","repository":{"owner":{"login":"org-attacker"}}}`, signed with `org-attacker`'s legitimate `webhook_secret` via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `org-attacker`, fetches `org-attacker`'s `github_app`, and the signature verifies successfully — see `verify_webhook_signature` at `lib/shipit/github_app.rb` lines 76-83.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")` — matching `org-victim`'s commit — and calls `commit.create_status_from_github!(params)`, marking it `success` regardless of the actual CI outcome in `org-victim`.
6. `org-victim`'s stack commit is now `deployable?`, permitting an unauthorized deploy trigger.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
