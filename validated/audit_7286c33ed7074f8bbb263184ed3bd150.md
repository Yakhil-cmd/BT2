### Title
`identify_user` trusts unauthenticated `X-Shipit-User` header to attribute Task/AuditRecord actorship - (`app/controllers/shipit/api/base_controller.rb`)

### Summary
`Shipit::Api::BaseController#identify_user` sets `current_user` from the client-supplied `X-Shipit-User` request header without any verification that the authenticated `ApiClient` (via `current_api_client`) belongs to or is authorized to act as that user. `require_permission!` only calls `current_api_client.check_permissions!(operation, scope)`, which checks the token's permission bitset, never the identity in `current_user`. Any holder of a valid, appropriately-scoped API token can therefore forge the "actor" attributed to a deploy/rollback/task-trigger, spoofing the identity of any existing `User` record (e.g., an admin).

### Finding Description
The intended binding is: `current_user attributed to this action == the GitHub identity that authenticated this request`. The actual code breaks this: [1](#0-0) 

`identify_user` does a case-insensitive lookup of any `User` by the raw `X-Shipit-User` header value with zero authentication of that header. `require_permission!` then only validates the token's own permission scope: [2](#0-1) [3](#0-2) 

There is no comparison between `current_api_client.creator` and `current_user`. Consumers such as `Api::DeploysController#create` and `Api::TasksController#trigger`/`#abort` pass `current_user` straight into `stack.trigger_deploy`, `stack.trigger_task`, and `task.abort!`, which is used for actor/audit attribution: [4](#0-3) [5](#0-4) 

Exploit flow: An attacker who owns a valid API token scoped to `deploy:stack` for stack A (e.g., obtained legitimately for their own automation, or via a shared CCMenu-style token as referenced in the question) sends:
```
GET/POST /api/stacks/A/tasks/:id/... (or /deploys)
Authorization: Basic <attacker's own token>
X-Shipit-User: victim-admin-login
```
`authenticate_api_client` correctly authenticates the attacker's own token. `require_permission!` passes because the attacker's token does have the `deploy:stack` permission. `identify_user` then resolves `current_user` to the victim admin's `User` record purely from the header, and the resulting `Task`/`Deploy` record and any downstream audit trail attribute the action to the victim rather than the attacker.

None of the listed guards (`force_github_authentication`, `User#authorized?`, `require_permission!`, `EnvironmentVariables#permit`, model validators) mitigate this, because they operate on different concerns (session-based UI auth, permission scopes, env var whitelisting) and none of them re-validate the `X-Shipit-User` header against the authenticated `ApiClient`'s `creator`.

### Impact Explanation
The attacker cannot escalate their own permissions (the token's own scope still governs whether the operation is allowed), but they can falsify who is recorded as having performed a legitimate, authorized action (deploy, rollback, task trigger/abort) on any stack their token can already access. This is an audit/attribution integrity break: actions the attacker performs get logged/displayed as performed by an arbitrary existing user (e.g., framing an admin), which undermines any use of `current_user` for authorization decisions or forensic trust elsewhere in the app that assumes `current_user` reflects real GitHub identity. It is repeatable on every request to any endpoint using `current_user` for attribution, for any stack the attacker's token can reach.

### Likelihood Explanation
Preconditions: attacker needs one valid `ApiClient` token with the relevant permission for a stack (something obtainable through normal, low-privilege API client issuance flows such as the CCMenu URL mechanism referenced in the question, or any token they legitimately hold). No secrets, sessions, or GitHub credentials are required. Setting a request header is trivial and requires no special access — cost and feasibility are effectively zero, and the attack is fully repeatable against any stack/user combination the token can already reach.

### Recommendation
Do not trust `X-Shipit-User` as an independent identity source disconnected from the authenticated client. Either remove header-based user identification for API requests entirely and always attribute actions to `current_api_client.creator`, or restrict `identify_user` to only allow overriding to `current_api_client.creator` (i.e., verify the header value matches the token owner) and reject/ignore mismatched values instead of silently trusting them.

### Proof of Concept
```ruby
# test/controllers/api/tasks_controller_test.rb (extension)
test "identify_user does not trust X-Shipit-User beyond the authenticated api client's creator" do
  attacker = shipit_users(:walrus)
  victim   = shipit_users(:bob) # some other existing user, e.g. an admin
  token = create_api_client(creator: attacker, permissions: %w[deploy:stack])

  authorization = "Basic #{Base64.strict_encode64("x:#{token.authentication_token}")}"
  post :trigger, params: { stack_id: @stack.to_param, task_name: 'restart' },
       headers: { 'Authorization' => authorization, 'X-Shipit-User' => victim.login }

  task = Shipit::Task.last
  assert_equal attacker.id, task.user_id, "Task actor must be the authenticated token's creator, not the forged header"
  refute_equal victim.id, task.user_id
end
```
This asserts the created `Task`'s recorded `user` equals the attacker's real identity (`current_api_client.creator`), not the forged `X-Shipit-User` header value, demonstrating the current code fails this assertion because `identify_user` (`app/controllers/shipit/api/base_controller.rb:69-72`) currently sets `current_user` to `victim` regardless of the token owner.
