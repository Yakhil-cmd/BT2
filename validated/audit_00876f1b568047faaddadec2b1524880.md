### Title
Unprivileged `price-feeds` parameter lets any caller prime the global oracle state consumed by other users' health/liquidation checks - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`collateral-add`, `collateral-remove`, `borrow`, and `liquidate` all accept an optional `price-feeds` argument that lets *any* unprivileged caller push signed Pyth price updates into the market's shared oracle state before their own operation is evaluated. Because the resulting price and `last-update` timestamp are stored in maps that are global to the contract (not scoped to the caller or to their specific position), a caller can choose which of several currently-valid (non-stale) Pyth publish times to submit, effectively cherry-picking the most favorable recent price for a feed. That price then becomes "the" oracle price used by every other user's health check and liquidation call against that same asset until a fresher update is submitted — an ordering/priming dependency between two unrelated principals sharing the same cached state.

### Finding Description
`write-feeds`/`write-feed` are invoked at the very start of `collateral-add`, `collateral-remove`, `borrow`, and `liquidate`, before any position-specific logic runs, and unconditionally forward the caller-supplied buffers to `pyth-oracle-v4::verify-and-update-price-feeds`, which writes the decoded price into the shared `pyth-storage-v4` contract: [1](#0-0) 

The price is later read back and validated only against monotonic timestamp progression and a staleness window, not against "is this the newest available price": [2](#0-1) [3](#0-2) 

The `last-update` map that stores this timestamp, and the underlying `pyth-storage-v4` price value, are keyed only by `{type, ident}` — i.e., per asset, globally shared across all users of the market, not per-caller: [4](#0-3) 

Because Pyth continuously emits many valid signed updates per feed, and the freshness check only requires `ts` to be newer than the previously recorded `ts` and within `max-staleness` of the current block time, a caller can hold multiple recently-signed VAAs for the same feed and submit whichever one is most favorable for their own operation. Once written, that price/timestamp pair persists in the shared maps and is what `price-resolve` returns for *every subsequent caller* in the same or later transactions, until someone submits a strictly newer update — exactly the "shared index/cache primed by one caller, consumed by another" pattern: one principal writes into common state during their own unprivileged call, and a different, unrelated principal's health/liquidation evaluation later consumes that same, potentially stale-but-technically-valid, value.

This mirrors the BLS aggregator bug class: two logically-separate validation points (the price used to justify the priming caller's own operation vs. the price consumed later by a liquidator evaluating a *different* borrower) can diverge from what the current true market price is, because the mechanism that keeps them "in sync" (the monotonic freshness check) does not actually guarantee the value is the most recent one available — it only guarantees forward progress from whatever was previously cached.

`liquidate` explicitly demonstrates the consuming side: it accrues, resolves prices, and computes the borrower's LTV entirely from this same shared, potentially attacker-primed cache: [5](#0-4) 

### Impact Explanation
A malicious or opportunistic caller (e.g., a borrower at risk of liquidation, or a colluding third party) can call `collateral-add`/`borrow` with a `price-feeds` payload containing an older-but-still-valid, favorable Pyth VAA for the collateral asset of a *different* borrower who is currently liquidatable. This overwrites the shared `last-update`/price state with a stale-but-fresh-enough value that understates the true drop in collateral value. A liquidator's subsequent `liquidate` call against the at-risk borrower then reads this stale, favorable price, computes an LTV below the liquidation threshold, and reverts with `ERR-HEALTHY`, delaying liquidation of an actually-unhealthy position. This is a temporary freezing of the protocol's ability to liquidate bad debt in a timely manner, which increases the risk that losses are ultimately socialized across all suppliers via `socialize-debt-asset` — a harm to third parties (other suppliers/lenders) distinct from the caller who primed the cache. This falls under the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Exploitability depends on the availability of multiple valid signed VAAs for the same feed within the `max-staleness` window, which is realistic given Pyth's high-frequency publishing cadence and the fact that VAAs remain valid for verification as long as the signing guardian set is still active — no special privilege or DAO action is required, and any of the four price-feed-accepting entry points can be used to prime the cache ahead of a liquidation attempt.

### Recommendation
Do not allow arbitrary global price cache writes as a side effect of an unrelated user's own operation. Options: (1) scope freshness/priming to require the submitted price to be within a small delta of the current block time rather than only monotonically newer than the last cached value; (2) require `liquidate` to itself write the freshest feeds it needs (already supported) and disregard/skip stale caller-primed updates for assets unrelated to the caller's own position; (3) tighten `max-staleness` so cherry-picking a favorable-but-old valid update becomes economically/timing infeasible; (4) add a minimum price update interval or require price submissions to be strictly the latest known publish time by cross-checking against a stored "highest seen" watermark instead of only monotonic progression.

### Proof of Concept
1. Borrower B has an sBTC-collateralized USDC loan that is currently under-collateralized after a real price drop is published on Pyth (LTV above `LTV-LIQ-PARTIAL`).
2. Attacker A (unrelated party, or B colluding with A) holds a still-valid Pyth VAA for the sBTC feed with an earlier, more favorable publish time (within `max-staleness` and newer than the currently recorded `last-update` timestamp for that feed).
3. A calls `collateral-add` (or `borrow`) with `price-feeds` set to that favorable VAA for an unrelated asset/position of their own; `write-feeds` executes at the top of the function and updates the shared `pyth-storage-v4`/`last-update` state for the sBTC feed before A's own health check even runs.
4. Liquidator C then calls `liquidate` against borrower B without supplying `price-feeds` (or supplying none); `price-resolve` reads the now-stale, favorable sBTC price A just wrote, computes B's LTV as below `LTV-LIQ-PARTIAL`, and the call reverts with `ERR-HEALTHY`, blocking the liquidation until a genuinely fresher price is submitted.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
