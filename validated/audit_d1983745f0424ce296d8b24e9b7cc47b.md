No vulnerability found for this question.

**Rationale:** The premise that `keyed_rewards`/`self.rewards` length is unbounded is incorrect. The `RewardType::Voting` entries returned by `Bank::get_rewards_and_num_partitions` come from `reward_commissions`, which is populated per distinct commission collector (`commission_pubkey`) encountered while redeeming stake-delegation rewards [1](#0-0) , and those commission accounts are finally materialized in `load_and_reward_commission_accounts` / `update_reward_commissions` [2](#0-1) .

Critically, the set of vote accounts that can participate in this reward calculation at all is unconditionally capped before calculation begins: `compute_new_epoch_caches_and_rewards` filters `unfiltered_distribution_vote_accounts` through `clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, self.minimum_vote_account_balance_for_vat())` regardless of whether Alpenglow is active [3](#0-2) . `clone_and_filter_for_vat` truncates the vote-account set to at most `max_vote_accounts` entries by stake, discarding the rest (and any tied at the truncation boundary) [4](#0-3) . This is exercised in tests explicitly confirming the bound holds even when more than `MAX_ALPENGLOW_VOTE_ACCOUNTS` validators exist [5](#0-4)  and in the standalone `test_clone_and_filter_for_vat_truncates` test [6](#0-5) .

Consequently, the number of distinct vote accounts (and hence the maximum possible number of `RewardType::Voting` entries in `self.rewards`) is capped at `MAX_ALPENGLOW_VOTE_ACCOUNTS`, independent of how many vote accounts an attacker creates and delegates stake to. Beyond this protocol-level cap, creating additional vote accounts also requires real, per-account economic cost (rent-exempt minimum balance for the vote account plus a minimum stake delegation), so even absent the cap this would be a cost-proportional spam scenario rather than a free-amplification DoS — which falls outside the scope of a genuine unbounded epoch-boundary halt vulnerability.

    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
        }

        let valid_len = entries_to_sort.len();
        if entries_to_sort.len() > max_vote_accounts {
            // Find the cutoff stake using partial sort (more efficient than full sort).
            let (_, cutoff_entry, _) =
                entries_to_sort.select_nth_unstable_by(max_vote_accounts, |a, b| b.2.cmp(&a.2));
            let floor_stake = cutoff_entry.2;

            // Per SIMD 357, we remove all vote accounts with stake smaller or equal to
            // the first truncated one.
            entries_to_sort.retain(|(_, _, stake)| *stake > floor_stake);
        }

        let mut top_entries: HashMap<Pubkey, (u64, VoteAccount)> =
            HashMap::with_capacity(entries_to_sort.len());
        top_entries.extend(
            entries_to_sort
                .into_iter()
                .map(|(pubkey, vote_account, stake)| (*pubkey, (stake, vote_account.clone()))),
        );
