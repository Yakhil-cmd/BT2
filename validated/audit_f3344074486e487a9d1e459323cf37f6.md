### Title
Partial worktree checkout can be published as "complete" via the symlink, because `sanityCheckWorktree` does not verify full checkout — analog of the "partial operation treated as complete" bug class - (File: main.go)

### Summary
The referenced report describes a class of bug where an underlying operation (Aave withdrawal) can complete only partially, but the calling code (`withdrawAll`, `switchStrategy`) commits to the accounting/state transition as if the operation fully succeeded, causing loss of access to the remaining (unaccounted) funds. The closest reachable analog in `git-sync` is the worktree checkout / sanity-check / publish pipeline in `main.go`, where a `git reset --hard` (the actual file-checkout step) can be interrupted (process killed, disk full, container restart) leaving a **partially checked-out worktree**, while the code that decides whether to (re)publish that worktree via the symlink does not actually verify that the checkout fully completed.

### Finding Description
`configureWorktree` performs the actual file materialization via `git reset --hard hash --` [1](#0-0) . If this command is interrupted mid-way (e.g., the container is killed, OOM-killed, or crashes), the on-disk worktree can contain a mix of old and new files — i.e., a "partial checkout".

On the next sync loop, `SyncRepo` determines whether a "current worktree" already matches the desired remote hash. If `currentHash == remoteHash`, the code takes a shortcut path that calls `sanityCheckWorktree` and, if that check passes, **does not re-run `configureWorktree`/`reset --hard` at all** — it treats the existing worktree as already correctly synced [2](#0-1) .

`sanityCheckWorktree` explicitly documents that it cannot detect this exact failure mode:
```
// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
``` [3](#0-2) 

The check only verifies: the directory isn't empty, `rev-parse HEAD` matches the worktree's hash, and `git fsck --connectivity-only` succeeds — none of which validate that the working tree files were actually written out by `reset --hard`. Since `HEAD` and the object database are updated by git as part of the same `reset --hard` invocation, `rev-parse HEAD` can return the correct hash even if the working-tree checkout was interrupted before all blobs were written to disk.

Because this worktree is exactly the one already published via the symlink (`git.link` continues to point at it, since `changed` will be `false` in this scenario per line 1914 [4](#0-3) ), consumers reading through `--link` continue to receive the same, silently-corrupted/partial directory indefinitely, with no re-check, no retry, and no new hook firing (hooks only run when `changed` is true) [5](#0-4) .

This directly mirrors the report's bug class: an operation (`reset --hard` checkout) can partially complete, and the surrounding logic (`sanityCheckWorktree` + the `currentHash == remoteHash` shortcut) treats it as fully complete without verifying the actual result, permanently "freezing" the consumer on an incorrect/partial published state rather than detecting and repairing it.

### Impact Explanation
This maps to "publishing wrong or partial content" and "persistent sync denial" from the accepted-impact list. The `--link` symlink — the entire consumer contract of `git-sync` — can persistently point to a directory with missing or stale files after a crash during checkout, and there is no mechanism to detect or self-heal this beyond the (documented-as-insufficient) `sanityCheckWorktree`. Because the shortcut path skips `configureWorktree` entirely when hashes match, the corruption can persist across arbitrarily many sync cycles, since nothing ever forces a re-checkout as long as `rev-parse HEAD` and `fsck --connectivity-only` succeed.

### Likelihood Explanation
This requires the git process performing `reset --hard` to be interrupted (SIGKILL, OOM, node reboot, `docker pause`/crash) after object database updates but before all worktree files are written — a scenario `git-sync`'s own end-to-end tests explicitly simulate for *worktree directory* corruption via `docker pause`/`docker unpause` around filesystem mutation (see `e2e::worktree_collision`/`e2e::worktree_unexpected_removal` in `test_e2e.sh`) [6](#0-5) , confirming this class of interruption is a recognized and tested failure mode for the surrounding worktree machinery, even though the specific partial-`reset --hard` case is not covered by an e2e test and is explicitly called out as a known gap in the code comment itself.

### Recommendation
- When `currentHash == remoteHash`, do not rely solely on `sanityCheckWorktree`; additionally re-run (or make idempotent) the file-materializing step (`git reset --hard`/`checkout`) or verify working-tree completeness (e.g., `git status --porcelain` / diff against the index) before trusting the existing worktree as fully synced.
- Alternatively, treat a `reset --hard` interruption as detectable by writing a "checkout complete" marker file after `configureWorktree` succeeds, and check for that marker (not just `rev-parse HEAD`) before skipping re-configuration in `SyncRepo`.
- Ensure this repaired/re-verified state, not just the git-internal check, gates whether the existing symlink target is considered trustworthy for continued publication.

### Proof of Concept
1. Start `git-sync` normally, causing a first successful sync (`configureWorktree` runs `git reset --hard <hash> --` at [1](#0-0) , and `publishSymlink` points `--link` at the resulting worktree [7](#0-6) ).
2. Simulate an interruption of a subsequent `reset --hard` for the *same* target hash (e.g., re-run with a large repo and `docker pause`/kill the process mid-checkout, similar to the pattern already used in `test_e2e.sh` at lines 695-729), so that some files are updated on disk and others are not, while `HEAD` and the object DB end up correct.
3. Restart `git-sync`. `SyncRepo` computes `currentHash == remoteHash` and calls `sanityCheckWorktree`, which passes because `rev-parse HEAD` and `fsck --connectivity-only` succeed [2](#0-1) .
4. `configureWorktree` (the actual file writer) is never re-invoked because `changed` is `false`, so the symlink continues to point at the partially-checked-out directory indefinitely, and consumers reading via `--link` silently receive incomplete/stale files with no error surfaced by `git-sync`.

// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}

	// Consistency-check the worktree.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, worktree.Path(), "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "worktree fsck failed", "path", worktree.Path())
		return false
	}

	return true
}
```
