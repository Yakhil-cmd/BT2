### Title
`StatusHandler#process` writes CI status to any commit row matching a bare SHA, with no check that the authenticated repository owns that commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, a global, unscoped lookup across the entire `commits` table, and then writes a status to every match via `commit.create_status_from_github!(params)`. Nothing in the handler, or in the surrounding `WebhooksController`, restricts the update to commits belonging to the repository/stack that the webhook payload (and its verified signature) actually describes.

### Finding Description
The broken binding is: **the repository that cryptographically authenticated a `status` webhook == the repository whose commit gets mutated**. In this code that equality does not hold.

Path:
- `Shipit::WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
- `verify_signature` picks the GitHub App/secret to check *only* by `repository_owner` (the org login in the payload) [2](#0-1) [3](#0-2) . It authenticates that *some* repository under that org/config produced the payload; it says nothing about which specific commit row the `sha` field should be allowed to touch.
- `Shipit.github(organization:)` resolves to a single shared config in the common "backward compatible" single-app setup (`github_default_organization` returns `nil`, so one `secrets.github` config/secret is used for every org and repository configured in this Shipit instance) [4](#0-3) .
- `StatusHandler#process` then does a completely unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . There is no `stack_id`, `repository_id`, or `github_repo_name` filter tying the match back to the repository that the webhook's signature actually vouches for.
- `create_status_from_github!` → `add_status` recomputes the commit's aggregate CI state and, on a meaningful state transition, calls `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [6](#0-5) . This is exactly the mechanism that unblocks/allows a merge or deploy once required statuses (e.g. `ci/build`) turn `success`.

Exploit flow: an attacker who owns/controls a repository that is *also* tracked by the same Shipit instance (any stack, however low-privilege) can post a genuine, GitHub-signed `status` event for context `ci/build` on a SHA value of their choosing. Because `Commit.where(sha: ...)` is a bare string match with no repository scoping, if that SHA string also identifies a commit row belonging to an unrelated stack (including a production stack that requires `ci/build` to be `success` before merging/deploying), the attacker's status write lands on that other stack's commit and can flip it from `pending`/`unknown` to `success`, triggering `stack.schedule_merges` and unblocking a ship. SHA collision across independently-tracked repositories is realistic whenever repos share history (forks, template repos, monorepo splits, or repositories re-imported/renamed), and Shipit provides no additional binding to prevent it once such a collision exists.

Existing guards do not prevent this: `verify_signature` authenticates *an* org/app configuration, not a specific repository-to-commit binding, and in single-app mode all tracked repositories share one webhook secret [7](#0-6) . `drop_unhandled_event` and the `ExplicitParameters` schema on `StatusHandler` only validate the *shape* of the payload (`sha`, `state`, `context` types), not repository ownership of the target commit [8](#0-7) . No model validation in `Commit` or `Stack` enforces sha-to-repository binding at write time.

### Impact Explanation
A successfully signed `status` webhook from a repository the attacker controls can write a CI status onto a commit belonging to a different repository/stack tracked by the same Shipit instance, including a production stack, as long as the two repositories happen to share a commit SHA. This can flip the aggregate commit state to `success` and trigger `stack.schedule_merges`, which is the code path that authorizes automatic merges of pending merge requests once CI is green - i.e., an unauthorized ship on a repository that did not authenticate the write. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
This requires: (1) the attacker to control (own, or have push/status-posting rights to) at least one repository that is itself tracked as a Shipit stack in the same instance/GitHub App configuration as the victim's production stack, and (2) a SHA collision between that attacker-controlled repository and the victim repository (realistic for forks/templates/shared-history repos, not for arbitrary unrelated repositories). Given those preconditions, the attack is cheap and repeatable: the attacker simply posts a commit status via the GitHub API on their own repository for the shared SHA, and GitHub relays a genuinely signed webhook that Shipit will process without any additional scoping check. No Shipit secrets, sessions, or API tokens are needed - only ordinary GitHub write access to a tracked repository.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other handler doing a bare `Commit.where(sha: ...)`/`Commit.by_sha` lookup driven by webhook input) to the repository that authenticated the request, e.g. resolve the `stack`/`repository` from the payload's `repository.full_name` first, then restrict the SHA match to `stack.commits.where(sha: params.sha)` (or equivalent join through `Repository`), so a status can never be applied to a commit outside the repository that produced the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file path may need adjusting to match existing test conventions):
1. Create two stacks, `victim_stack` (environment: `"production"`, with a `deploy_spec`/required status of `ci/build`) and `attacker_stack` (any environment), each with a distinct `Repository`.
2. Create `victim_commit` on `victim_stack` and `attacker_commit` on `attacker_stack`, both with the **same** `sha` value (simulating a shared-history collision) — this is the equality under test: `victim_commit.sha == attacker_commit.sha` while `victim_commit.stack_id != attacker_commit.stack_id`.
3. Build a `status` webhook payload whose `repository.full_name` matches the attacker's repo, `sha` = the shared SHA, `context: "ci/build"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST through `WebhooksController#create` with signature verification stubbed, per existing test patterns in `webhooks_controller_test.rb`).
5. Assert `victim_commit.reload.statuses.count` increased and `victim_commit.reload.state == "success"` (broken binding reproduced: the victim's commit was mutated by a request that only authenticated the attacker's repository), and that `stack.schedule_merges` was invoked/enqueued for `victim_stack` — i.e., before the fix, the two sides of "authenticated repo == mutated repo" diverge; after applying the recommended scoping fix, `victim_commit.reload.statuses.count` must remain unchanged.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
