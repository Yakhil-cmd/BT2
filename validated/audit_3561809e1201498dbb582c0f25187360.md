### Title
Webhook signature is authenticated against the payload's `repository.owner.login`/`organization.login`, but every handler acts on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the incoming signature against by reading it straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a field inside the very payload whose authenticity is what the signature check is supposed to establish.

Once `verify_signature` passes, every event handler determines *which Stack/repository to act on* from a completely different payload field, `repository.full_name`, via `Handler#repository_name` / `#stacks`: [3](#0-2) 

Nothing ties `repository.owner.login` (the value used to pick the HMAC secret) to `repository.full_name` (the value used to look up the target `Repository`/`Stack`). Handlers such as `PushHandler` blindly trigger `stack.sync_github` for whatever stack matches `repository.full_name`: [4](#0-3) 

The equality that should hold is:
`organization whose webhook_secret authenticated the request == owner of the repository the handler mutates`

Because `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON fields inside the same signed body, and the app never cross-checks that `repository.full_name` actually belongs to `repository_owner`, an attacker who controls (or is a maintainer of) *any* GitHub organization/App installation that Shipit trusts — and therefore legitimately knows that org's `webhook_secret` (configured per-organization in `Shipit.github(organization:)`, see `lib/shipit/github_app.rb#verify_webhook_signature`) — can compute a valid HMAC over a forged payload that sets:
- `repository.owner.login` = their own controlled organization (so the secret lookup and HMAC succeed), and
- `repository.full_name` = `victim-org/victim-repo` (an entirely different Stack they have no access to). [5](#0-4) 

The forged, correctly-signed request will pass `verify_signature` (using the attacker's own org secret) and then dispatch into handlers that operate on the victim's stack (`Handler#stacks` → `Repository.from_github_repo_name(repository_name)`), e.g. triggering `GithubSyncJob` via `PushHandler`, injecting fake commit `Status` rows via `StatusHandler`, or manipulating `CheckSuite`/PR state for a repository the attacker never authenticated against.

### Impact Explanation
This breaks the trust binding between "which org's secret authenticated this webhook" and "which repository gets mutated." An attacker who legitimately controls one Shipit-trusted GitHub organization can forge webhook effects (fake pushes triggering sync/deploy pipelines to pick up attacker-influenced commit SHAs, fabricated commit statuses used as merge/deploy gates, PR/check_suite state changes) against a target stack belonging to a *different* organization, without ever having push access, admin rights, or a valid secret for that target. This is a cross-repository/cross-organization write achieved purely by satisfying the app's own signature-verification logic with a different, but valid, secret — squarely matching the "organization that authenticated versus the repository that is written" binding called out in the analog rules.

### Likelihood Explanation
Requires the attacker to be a legitimate, authenticated party for *some* organization/app installation that Shipit already trusts (i.e., they can receive/send webhooks with that org's real `webhook_secret`). This is a lower bar than compromising the victim organization directly, and is realistic in any multi-tenant Shipit deployment serving more than one organization/app installation, which is an explicit configuration Shipit supports (`Shipit.github(organization: ...)`).

### Recommendation
After verifying the signature, re-derive `repository_owner` from the payload used only to select the secret, and require it to equal the owner segment parsed out of `repository.full_name` (or, better, resolve the target `Repository`/`Stack` first and confirm its configured owner/organization matches the organization whose secret validated the signature) before dispatching to any `Handlers`.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org`, which is a legitimate Shipit-integrated organization with webhook secret `S` (known to the attacker, e.g., because they configured the org's webhook or app installation).
2. Attacker crafts a `push` JSON payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeef...",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature with the attacker's own known secret `S`.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler.call(params)`, which computes `repository_name` from `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, looks up that `Stack`, and enqueues `stack.sync_github(expected_head_sha: ...)` — an action on a stack the attacker does not control, using only credentials belonging to an unrelated organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
