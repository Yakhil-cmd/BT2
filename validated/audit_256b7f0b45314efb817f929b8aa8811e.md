## Analog Vulnerability Found

### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `Api::CCMenuController` overrides `stack` to bypass the stack-scoping enforced by `Api::BaseController`, so an `ApiClient` token that is authorized ("authenticated") for only one specific stack can be used to read the build/deploy status of any stack in the Shipit instance.

### Finding Description
In `Api::BaseController`, an `ApiClient` can optionally be scoped to a single stack via `belongs_to :stack` [1](#0-0) . The base controller enforces this scoping through the `stacks` helper, which restricts the visible/actionable set of stacks to `current_api_client.stack_id` when present, and `stack` is derived from that scoped collection: [2](#0-1) .

`Api::CCMenuController`, however, overrides `stack` to look the stack up directly via `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping method: [3](#0-2) . It also overrides `authenticate_api_client` to permit any `ApiClient` authenticated purely by the `token` query parameter, without applying the base controller's stack filter afterward: [4](#0-3) .

This breaks the trust binding: **stack a token authorizes == stack it touches**. The `require_permission :read, :stack` check only verifies the token has the `read:stack` permission string [5](#0-4)  and `ApiClient#check_permissions!` only checks that the permission string is present in the list, it does not check which specific stack the client is scoped to [6](#0-5) . It never compares `current_api_client.stack_id` against the requested `stack_id`. Any client holding a valid, stack-scoped `read:stack` token (e.g. the auto-generated "CCMenu Client" created per-stack by `CCMenuUrlController#client`, which is deliberately scoped to one stack via `create_with(permissions: %w[read:stack])` [7](#0-6) ) can supply a different `stack_id` in the request path/query and read that other stack's information instead.

This is directly analogous to the ERC-6492 report's core flaw: a value that is checked/verified for one purpose (the token's scope binding to stack X) is not the same value that is actually acted upon (an attacker-supplied stack Y), and the code silently trusts the acted-upon value without re-validating it against the authorized value.

### Impact Explanation
An attacker who legitimately possesses (or obtains, e.g. by URL leakage) a `read:stack`-scoped `ApiClient` token intended for a single stack (such as the CCMenu integration token that Shipit auto-provisions and embeds in a URL for CI dashboard tools) can use that token to read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status, etc.) of every other stack managed by the Shipit instance, including private/internal stacks the token holder was never granted access to. This is an authorization-scope escalation: a token meant to be confined to one stack effectively becomes a global "read any stack's build state" token. This matches the "unauthenticated/under-scoped read of stack state" impact class described in the assessment rules.

### Likelihood Explanation
Likelihood is high for anyone already in possession of a valid `ApiClient` authentication token (a normal, unprivileged precondition explicitly permitted by the rules, since it does not require session, webhook_secret, GitHub App keys, or admin access — only a routinely-issued, narrowly-scoped API token). CCMenu tokens are specifically designed to be embedded in third-party CI dashboard tools/URLs, increasing the chance of a token being shared or exposed while the issuer assumes it is limited to a single stack. No signature manipulation or cryptographic bypass is needed — only changing the `stack_id` request parameter.

### Recommendation
`Api::CCMenuController#stack` should use the same scoped lookup as the base controller (i.e., go through `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that a stack-scoped `ApiClient` cannot access stacks outside its `stack_id` binding. Additionally, `ApiClient#check_permissions!` (or the controller layer) should be hardened to explicitly reject requests where `current_api_client.stack_id` is present and does not match the resolved `stack.id`, rather than relying solely on controllers to remember to apply the `stacks` scoping helper.

### Proof of Concept
1. An admin creates Stack A and Stack B in the same Shipit instance.
2. For Stack A, a user visits the CCMenu URL feature, which auto-creates an `ApiClient` scoped to Stack A only, with permission `read:stack`: [7](#0-6) . The resulting token is embedded in a URL such as `/api/stacks/orgA/repoA/ccmenu.xml?token=<TOKEN_A>`.
3. An attacker who obtains `TOKEN_A` (e.g., from the shared CI dashboard config) sends a request to `GET /api/stacks/orgB/repoB/ccmenu.xml?token=<TOKEN_A>` (i.e., swaps `stack_id` in the path to Stack B).
4. `authenticate_api_client` in `CCMenuController` authenticates `TOKEN_A` successfully (it's a valid token) [4](#0-3) .
5. `require_permission :read, :stack` passes because `TOKEN_A`'s permissions include `read:stack`, with no check that `stack_id` matches Stack B [6](#0-5) .
6. `stack` resolves via `Stack.from_param!(params[:stack_id])` to Stack B, unrelated to `TOKEN_A`'s bound stack [8](#0-7) .
7. The response renders Stack B's actual build/deploy status, disclosing information the token was never authorized to access.
