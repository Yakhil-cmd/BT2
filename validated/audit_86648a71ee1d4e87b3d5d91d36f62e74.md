### Title
Front-runnable `InitializeBuffer` instruction lets an adversary steal/DOS a program deployer's buffer account before it is written - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
`cli/src/program.rs`'s `do_process_write_buffer`/`do_process_program_deploy`/`do_process_program_upgrade` build and send the `CreateAccount` and `InitializeBuffer` instructions as **two separate transactions** (`initial_message` sent first, then subsequent `write_messages`), rather than atomically bundling them in one signed transaction. [1](#0-0)  This mirrors exactly the pattern flagged in the external report: an account is created in one step, and a separate, unauthenticated `init`-style call finalizes it in a later step, leaving a window for a third party to front-run the finalization call.

### Finding Description
`UpgradeableLoaderInstruction::InitializeBuffer` is processed in `process_loader_upgradeable_instruction`:

```rust
UpgradeableLoaderInstruction::InitializeBuffer => {
    instruction_context.check_number_of_instruction_accounts(2)?;
    let mut buffer = instruction_context.try_borrow_instruction_account(0)?;
    if UpgradeableLoaderState::Uninitialized != buffer.get_state()? {
        return Err(InstructionError::AccountAlreadyInitialized);
    }
    let authority_key = Some(*instruction_context.get_key_of_instruction_account(1)?);
    buffer.set_state(&UpgradeableLoaderState::Buffer { authority_address: authority_key })?;
}
``` [2](#0-1) 

This handler performs **no signer check** on either the buffer account (index 0) or the supplied authority (index 1) — it only requires the buffer account's current state to be `Uninitialized`. Any transaction sender who knows the (public) buffer address can call `InitializeBuffer` on it and set themselves as `authority_address`, exactly the same class of bug as the reported `IVotingStrategy.init()`, which only checks `roundAddress == address(0)` with no ownership/signature gate.

The CLI's normal buffer-creation flow (`do_process_write_buffer`, `do_process_program_deploy`, `do_process_program_upgrade`) splits `CreateAccount` (which requires the buffer keypair's signature and is submitted as `initial_message`) from the first `Write` instruction batch, sent as separate, subsequently-signed transactions via `send_deploy_messages`. [1](#0-0)  Test/tooling helpers such as `runtime/src/loader_utils.rs::load_upgradeable_buffer` similarly send `create_buffer` (which itself bundles `CreateAccount` + `InitializeBuffer` into one message) as a first transaction, and only afterward send `Write` instructions in following transactions. [3](#0-2)  Once the `CreateAccount` transaction lands on-chain, the buffer account is publicly visible and owned by `bpf_loader_upgradeable` but still `Uninitialized`. Any adversary can observe this state, and if the legitimate `InitializeBuffer` call has not yet landed (e.g., is still propagating, or the deployer's tooling issues it as a separate transaction), the adversary can submit their own `InitializeBuffer` naming themselves as `authority_address`. Because there is no signer requirement, this transaction can even be sent independently of any race with the legitimate transaction's signature — merely knowing the buffer pubkey and its `Uninitialized` state is sufficient.

Once the attacker's `InitializeBuffer` transaction is processed, the account's state moves to `Buffer { authority_address: Some(attacker) }`. Any subsequent legitimate `InitializeBuffer` call for the same address will fail with `InstructionError::AccountAlreadyInitialized` (as validated by `test_bpf_loader_upgradeable_initialize_buffer`) [4](#0-3) , and — worse — subsequent `Write` calls from the legitimate deployer will be rejected because the authority no longer matches (`IncorrectAuthority`), permanently denying the deployer the ability to use this buffer address. The deployer's lamports paid for `CreateAccount` are also stuck (only closable by the attacker, who now controls `authority_address`).

### Impact Explanation
This is a **transaction-triggered denial-of-service and fund-stranding of a specific program deployment/upgrade path**: an adversary can hijack any newly created, not-yet-initialized `bpf_loader_upgradeable` buffer account, blocking the rightful deployer from initializing or writing to it, and taking control of the buffer's authority (and thus the account's lamports, since only the authority can close/withdraw the buffer). This matches the "Medium" severity DOS class in the referenced report — no funds are stolen directly from arbitrary users, but a legitimate operation (program deployment/upgrade) can be griefed by any unprivileged transaction sender who monitors pending/confirmed `CreateAccount` transactions targeting `bpf_loader_upgradeable`.

### Likelihood Explanation
Reachable by any unprivileged transaction sender: they need only observe a `CreateAccount` transaction (public, visible pre-confirmation in the mempool or immediately post-confirmation) creating an account owned by `bpf_loader_upgradeable`, and then submit an `InitializeBuffer` instruction naming that account and any authority of their choosing before the legitimate deployer's `InitializeBuffer`/first `Write` transaction lands. Since CLI code paths (`do_process_write_buffer`, `do_process_program_deploy`, `do_process_program_upgrade`) explicitly send `CreateAccount` and the buffer-initializing instructions in separate transactions/messages [5](#0-4) , this window naturally exists during every normal deploy/upgrade/write-buffer flow, not merely as a theoretical edge case.

### Recommendation
Add an explicit authorization check to `InitializeBuffer` requiring that the buffer account (or the payer/creator who funded it) be a signer on the instruction, so that only the party who created the buffer account can initialize it. Alternatively, require the CLI/SDK helper `solana_loader_v3_interface::instruction::create_buffer` to always be submitted as a single atomic transaction (both `CreateAccount` and `InitializeBuffer` in the same message, as already supported), and update `do_process_write_buffer`/`do_process_program_deploy`/`do_process_program_upgrade` in `cli/src/program.rs` to never split these two instructions across separate transactions.

### Proof of Concept
1. Deployer runs `solana program write-buffer` (or `deploy`), which internally calls `do_process_write_buffer` in `cli/src/program.rs`; this builds `initial_instructions` via `loader_v3_instruction::create_buffer(...)` and sends them as `initial_message` in one transaction, separate from the subsequent `write_messages`. [5](#0-4) 
2. `create_buffer`'s `CreateAccount` instruction lands, creating `buffer_pubkey` owned by `bpf_loader_upgradeable`, state `Uninitialized`, funded with rent-exempt lamports.
3. Before the deployer's own `InitializeBuffer` instruction (bundled with `CreateAccount` inside `create_buffer`, or sent separately) is confirmed, an attacker submits a transaction invoking `UpgradeableLoaderInstruction::InitializeBuffer` on `buffer_pubkey`, naming the attacker's own pubkey as account index 1 (`authority_key`). Per `process_loader_upgradeable_instruction`, this succeeds because no signer check is performed on account 0 or 1, only `UpgradeableLoaderState::Uninitialized != buffer.get_state()?`. [2](#0-1) 
4. The buffer account state becomes `Buffer { authority_address: Some(attacker) }`.
5. The deployer's original `InitializeBuffer` call (if not already included atomically) now fails with `InstructionError::AccountAlreadyInitialized` [4](#0-3) , and any `Write` calls from the deployer fail with `IncorrectAuthority` since `authority_address != authority_key`. [6](#0-5)  The deployer's rent-exempt lamports in the buffer account are now controlled by the attacker.
