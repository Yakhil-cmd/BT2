### Title
Api::CCMenuController lets an ApiClient token read the build status of any stack, not just the stack it is scoped to - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` authenticates an `ApiClient` by token but then resolves the target `Stack` directly from the request params instead of going through the scoped lookup used everywhere else in the API. This breaks the binding "stack a token authorizes == stack it touches": a token created with `stack_id` set (and only `read:stack` permission) can be replayed against the `stack_id` param of any other stack to read its latest deploy/build status.

### Finding Description
Every other API controller resolves the target stack through `BaseController#stack`, which is scoped by `stacks`: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is bound to a single stack (`current_api_client.stack_id?`), which is exactly the mechanism that is supposed to enforce "this token may only touch its own stack".

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 
Here `stack` is resolved via `Stack.from_param!(params[:stack_id])` against the whole `Stack` relation, with no reference to `current_api_client.stack_id`. The only gate is `require_permission :read, :stack`, which is implemented in `ApiClient#check_permissions!` as a pure string-membership check against the client's `permissions` array — it has no notion of *which* stack the permission applies to: [3](#0-2) 

So the equality that should hold — `token.stack_id == params[:stack_id]` (when the token is stack-scoped) — is never checked in this controller. Any `read:stack`-permitted token (including one that was deliberately scoped to a single, low-sensitivity stack, e.g. `here_come_the_walrus` in the fixtures) can be used with an arbitrary `stack_id` to pull CCMenu XML (build status, last deploy id, running state) for a different, unauthorized stack.

### Impact Explanation
This is an unauthenticated (relative to the target stack) read of stack state: a credential legitimately issued for stack A discloses deploy/build status data for stack B. This matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" via a broken authorization scoping boundary (the token's `stack_id` binding).

### Likelihood Explanation
Trivial to exploit for anyone already holding any valid `ApiClient` token with `read:stack` permission (a normal, low-privilege token type meant to be scoped to one project's CI/monitoring integration) — they only need to guess/enumerate another stack's numeric id or slug, which are non-secret, sequential/incrementing values exposed throughout the UI and other API responses.

### Recommendation
In `Api::CCMenuController`, resolve the stack through the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) exactly as `BaseController#stack` does, instead of calling `Stack.from_param!` directly, so that a stack-scoped token cannot be replayed against another stack.

### Proof of Concept
1. Create/obtain an `ApiClient` token `T` with `permissions: ['read:stack']` and `stack_id` set to stack `A` (e.g. fixture `here_come_the_walrus`, scoped to stack `shipit`).
2. Send `GET /api/stacks/<id-or-slug-of-stack-B>/ccmenu.xml?token=T` for a different stack `B` that `T` was never authorized for.
3. `authenticate_api_client` succeeds (token `T` is valid), `require_permission :read, :stack` passes (T has `read:stack`), and `stack` resolves `Stack.from_param!(params[:stack_id])` against stack `B` with no check that `T.stack_id == B.id`.
4. The response renders `shipit/ccmenu/project` with `stack: B`'s latest deploy/rollback status — data the token was never authorized to see. [4](#0-3) [1](#0-0)
