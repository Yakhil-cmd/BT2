This confirms the divergence: `PushHandler#process` at [1](#0-0)  uses `stacks` (scoped via `Repository.from_github_repo_name(repository_name)` in the base `Handler`) before touching any records, while `StatusHandler#process` never calls `stacks` or `repository_name` at all — it queries `Commit.where(sha: params.sha)` globally, across every repository/stack in the installation.

### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets one repository's signed status payload write statuses onto another repository's commit/stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by `sha`, with no constraint tying it to the repository that authenticated the webhook (`payload.dig('repository','full_name')`), unlike every other handler (`PushHandler`, `CheckSuiteHandler`, etc.) which scope via the base `Handler#stacks` helper. If a commit SHA is shared between two Shipit-tracked repositories/stacks (e.g., shared git history, a cherry-picked/rebased commit, a common initial commit, or a repository that was renamed/re-added), a valid, signed `status` webhook from Repository A's organization can create a `Status` row against Repository B's `Commit`, which (when `blocking_statuses` is configured on B's stack) directly flips `Commit#blocked?`/`#deployable?` for B.

### Finding Description
The broken binding is: `commit.stack.repository.full_name == payload.dig('repository','full_name')` — this equality is asserted implicitly by `verify_signature` (which authenticates only that the payload came from GitHub for `repository_owner`'s org, at [2](#0-1) ), but it is never checked when picking which `Commit` record to mutate.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This iterates over *every* `Commit` row across all stacks/repositories sharing that SHA — there is no `repository_name`/`stacks` filter, unlike the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`, [4](#0-3) ) that `PushHandler` correctly uses ( [1](#0-0) ).

`commit.create_status_from_github!` writes a `Status` scoped to `stack_id` ( [5](#0-4) ), and `Status::Common#blocking?` checks `commit.blocking_statuses.include?(context)` ( [6](#0-5) ). `Commit#blocked?` then scans `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)` ( [7](#0-6) ), which feeds `deployable?` ( [8](#0-7) ). Because `blocking_statuses` is per-stack config (`DeploySpec#blocking_statuses`, [9](#0-8) ), a stack B with `ci/build` configured as blocking will have its `blocked?`/`deployable?` state flipped by a status event whose payload authenticated repository A.

Attacker request: A signed `status` event (`context: "ci/build"`, `state: "failure"`, `sha: <shared-sha>`) from a repository the attacker controls/owns, where that repository's organization already has a valid `webhook_secret` configured in Shipit (satisfying `verify_signature`). This requires the same SHA to exist in both the attacker's tracked repo/stack and the victim's stack — a scenario that occurs for repositories with shared git history (splits, forks synced into Shipit, or monorepo extraction) or, more narrowly, any repo whose commits happen to collide on SHA with another tracked repo's commit table.

None of the existing guards prevent this: `verify_signature` only proves the org identity of the sender, not which `Commit`/`Stack` the payload may mutate; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not scope; there is no `require_permission!`/`stacks` filtering inside `StatusHandler` itself.

### Impact Explanation
A payload authenticated for repository A can create/flip a `Status` (and thus `blocked?`/`deployable?`) for a `Commit`/`Stack` belonging to repository B, matching the "Critical — payload for one repository mutating another's stack/commit" category. Depending on continuous-deployment configuration, this can gate or unblock a real deploy on the victim stack, i.e., an unauthorized deploy or forced block. This is repeatable against any pair of repositories/stacks that share a commit SHA.

### Likelihood Explanation
Preconditions: attacker must control (or have webhook delivery from) a repository whose organization is already integrated with the target Shipit instance, and the target victim stack must have `ci.blocking` configured for a status context (e.g., `ci/build`) that is also meaningful/attacker-controllable via a shared SHA. The main constraint is finding/producing a commit SHA collision across the two repositories, which is feasible in shared-history scenarios (fork/split/rename, common ancestor commits still tracked by both stacks) but not a generic SHA-collision attack against arbitrary unrelated repos. Given that constraint, the attack is a single POST/webhook event and fully repeatable.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the target repository via `payload.dig('repository','full_name')`, and constrain the commit lookup to `stacks.flat_map(&:commits)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of a bare, cross-tenant `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, conceptually — actual file is out-of-scope path but illustrates the assertion):
1. Create `repo_a` (`owner_a/repo`) and `repo_b` (`owner_b/repo`), each with a `Stack`; give `stack_b` a `DeploySpec` with `ci: { blocking: ['ci/build'] }`.
2. Create `Commit` rows in both stacks with the **same** `sha` ("deadbeef").
3. Build a `status` webhook payload with `repository.full_name = "owner_a/repo"`, `sha: "deadbeef"`, `context: "ci/build"`, `state: "failure"`.
4. Assert before: `commit_b.reload.blocked?` / `deployable?` matches its pre-webhook state (e.g., `true` deployable, no blocking status).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert after: `commit_b.reload.blocked?` is now `true` (or `deployable?` flipped), even though the payload only authenticated `owner_a/repo`, proving repository A's payload mutated repository B's stack state — the equality `commit.stack.repository.full_name == payload["repository"]["full_name"]` is violated.
