### Title
Recipient-Controlled Revert in `handleKLAYTransfer` Permanently Locks Bridged KAIA and Freezes Bridge Nonce — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` uses a push-based KAIA delivery pattern. If the destination address `_to` is a contract that rejects KAIA (no payable fallback, or an explicitly reverting fallback), the `require(ok, ...)` at line 99 causes the entire transaction to revert. Because all state mutations — nonce recording, `lowerHandleNonce` advancement, and the handled-tx-hash mark — occur before the transfer and are rolled back on revert, the nonce is never marked as handled on-chain. The KAIA is permanently locked inside the bridge contract and `lowerHandleNonce` is frozen at the stuck nonce, corrupting the bridge's nonce accounting.

---

### Finding Description

`handleKLAYTransfer` executes the following sequence:

```solidity
// BridgeTransferKLAY.sol lines 81-99
_setHandledRequestTxHash(_requestTxHash);          // (1) mark tx hash handled
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber; // (2) record nonce
_updateHandleNonce(_requestedNonce);               // (3) advance lowerHandleNonce
emit HandleValueTransfer(...);                     // (4) emit event

(bool ok, ) = _to.call.value(_value)("");          // (5) push KAIA
require(ok, "handleKLAYTransfer: transfer failed"); // (6) revert if rejected
```

Steps (1)–(4) mutate state. Step (6) reverts the entire transaction if `_to` rejects KAIA. Solidity reverts roll back all state changes in the same transaction, so steps (1)–(4) are undone. The nonce is never recorded in `handleNoncesToBlockNums`, so `_updateHandleNonce`'s loop:

```solidity
// BridgeTransfer.sol lines 149-155
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) { ... }
lowerHandleNonce = i;
```

immediately stops at the stuck nonce (because `handleNoncesToBlockNums[N] == 0`) and `lowerHandleNonce` is frozen at `N` permanently.

The `BridgeFee.sol` `_payKLAYFeeAndRefundChange` function contains the same pattern for the `feeReceiver` push (`feeReceiver.call.value(fee)("")` with `require(ok, "transfer fee failed")`), but `feeReceiver` is owner-controlled, so that surface is lower severity.

---

### Impact Explanation

**Corrupted bridge state value:** `lowerHandleNonce` is frozen at nonce `N` forever. `recoveryBlockNumber` never advances past the block preceding nonce `N`, causing the VTRecovery mechanism to re-scan from the same block indefinitely.

**Locked bridged assets:** The KAIA corresponding to nonce `N` is permanently locked inside the bridge contract. The user who initiated the cross-chain transfer on the source chain has already had their KAIA locked or burned there; the destination bridge can never deliver the funds.

**Scope:** Matches the allowed impact gate — unauthorized lock of bridged KAIA assets and persistent corruption of bridge nonce state.

---

### Likelihood Explanation

Any user who initiates a KAIA cross-chain transfer can set `_to` to a contract address that rejects KAIA. This requires no privilege. The attacker only needs to:
1. Deploy a contract on the destination chain with a reverting or absent payable fallback.
2. Call `requestKLAYTransfer(maliciousContract, value, extraData)` on the source bridge.

The bridge operators will faithfully relay the event and call `handleKLAYTransfer` with the malicious address, triggering the permanent lock. The attack is cheap, deterministic, and requires no cooperation from operators or validators.

---

### Recommendation

Replace the push-based delivery with a pull-based pattern. Record the owed KAIA in a mapping and let the recipient withdraw it:

```solidity
// Instead of:
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");

// Use:
pendingWithdrawals[_to] += _value;
// Add a separate withdraw() function callable by _to
```

Alternatively, if push delivery is retained, handle the failure gracefully — mark the nonce as handled regardless of delivery success and store the KAIA for a separate recovery path — so that a single bad recipient cannot freeze the nonce sequence.

---

### Proof of Concept

```
1. Attacker deploys RejectKAIA on the destination chain:
   contract RejectKAIA { fallback() external payable { revert(); } }

2. Attacker calls on source bridge:
   requestKLAYTransfer(address(RejectKAIA), 1 ether, "")
   → source chain locks 1 KAIA, emits RequestValueTransfer(nonce=N)

3. Bridge operators call on destination bridge:
   handleKLAYTransfer(txHash, from, RejectKAIA, 1e18, N, blockNum, "")
   → _setHandledRequestTxHash, handleNoncesToBlockNums[N]=blockNum, _updateHandleNonce(N) execute
   → _to.call.value(1e18)("") returns ok=false (RejectKAIA reverts)
   → require(ok) reverts the entire tx
   → all state changes rolled back; handleNoncesToBlockNums[N] == 0

4. _updateHandleNonce for any future nonce M > N:
   loop: i = lowerHandleNonce = N; handleNoncesToBlockNums[N] == 0 → stop immediately
   lowerHandleNonce stays at N forever

5. Result:
   - 1 KAIA permanently locked in destination bridge
   - lowerHandleNonce frozen at N
   - recoveryBlockNumber never advances past block before N
   - VTRecovery re-scans from the same block indefinitely
```

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

	}
