### Title
Webhook signature verified against `repository.owner.login`'s secret while event handlers act on `repository.full_name` — cross-organization stack forgery (`WebhooksController#verify_signature`)

### Summary
`Shipit::WebhooksController` verifies the inbound webhook HMAC using the GitHub App/organization derived from `repository.owner.login` (falling back to `organization.login`), but every event `Handler` resolves the *target* `Stack`/`Repository` from an entirely different, unrelated field — `repository.full_name`. Because these two fields are never cross-checked, a party who legitimately knows the `webhook_secret` for *any* organization configured in a multi-tenant Shipit instance can forge a payload whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` points at a stack belonging to a completely different, victim organization.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret this way: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

Each org has its own distinct `webhook_secret`, as shown in the multi-org config format: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire raw payload* to the registered handler(s) for the event type: [4](#0-3) 

Every `Handler` subclass, however, resolves which `Stack`/`Repository` to mutate using a **different** field of the same payload — `repository.full_name` — with no relation to `repository.owner.login` used for signing: [5](#0-4) 

Concrete handlers that write state based on this unchecked `full_name` lookup include `PushHandler` (triggers `stack.sync_github`, i.e. re-syncs and can advance deploys against expected head SHAs): [6](#0-5) 

and `StatusHandler`, which writes commit CI statuses purely by matching `sha` globally across `Commit`, independent of which org/repo triggered the request: [7](#0-6) 

Same pattern applies to `CheckSuiteHandler` and the `pull_request` family of handlers, all of which key off `repository.full_name` from the payload rather than the field used for signature/secret selection: [8](#0-7) [9](#0-8) .

This is the exact analog of the reported bug class: a verification gate (signature check tied to `repository.owner.login`/org secret) is treated as if it covers the whole payload, but a materially different field (`repository.full_name`) that drives the actual state mutation is never bound to what was verified — just as `applyRebalForProportions` verified/updated proportions only for `strategy == 1` while the caller assumed the returned array always reflected the current strategy, here the signature only certifies "this org's secret matches," while the code proceeds to act on an independent, unverified `repository.full_name` value.

**Binding broken**: `organization authenticated (repository.owner.login → webhook_secret)` ≠ `repository that is written (repository.full_name → Stack/Repository resolved by handlers)`.

### Impact Explanation
An attacker who is a legitimate admin of *any one* organization/GitHub App onboarded into a shared, multi-tenant Shipit deployment (a low/no-privilege position relative to the victim org) can:
- POST directly to `/webhooks` with a crafted JSON body,
- set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` picks their own known `webhook_secret` and signs successfully,
- set `repository.full_name` to any tracked victim repo/stack.

This can trigger unauthorized `GithubSyncJob`/`sync_github` calls (`PushHandler`), inject/forge commit CI statuses on victim commits (`StatusHandler`) that the merge queue and deploy gating rely on, or manipulate pull-request/review-stack lifecycle (archive/unarchive, label capture) for the victim's repository (`pull_request` handlers). Forged CI statuses can directly influence whether commits are considered deployable/mergeable, which can lead to an unauthorized deploy/merge — matching the Critical impact bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the target deployment to host multiple organizations (a documented, supported configuration — see `config/secrets.development.shopify.yml` and the multi-org `Shipit.github` config). Within such a deployment, any onboarded org's own webhook secret is enough; no access to the victim org, no Shipit session, API token, or GitHub App private key is needed. This is a straightforward unauthenticated-to-the-victim HTTP POST once one (any) org's secret is known.

### Recommendation
Bind the field used to select the signing secret to the field used to resolve the target repository: verify that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` used for the signature check, and reject/short-circuit the request if the derived repository owner does not correspond to the organization whose secret validated the signature. Alternatively, resolve the target `Stack`/`Repository` using only the same `repository_owner` value that was cryptographically verified, rather than trusting `full_name` independently in `Handler#stacks` and each handler's `repository_name`.

### Proof of Concept
1. Attacker administers `org-attacker` in a Shipit instance that also hosts `org-victim/victim-repo` (tracked as a Stack).
2. Attacker knows `webhook_secret` for `org-attacker` (they configured it themselves).
3. Attacker crafts payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist on victim repo>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` HMAC-SHA1 over the raw JSON using `org-attacker`'s `webhook_secret`.
5. POST to `/webhooks` with header `X-Github-Event: push`.
6. `verify_signature` looks up `Shipit.github(organization: "org-attacker")` (from `repository.owner.login`), verifies successfully.
7. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-victim/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — a write the attacker was never authorized to trigger.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
