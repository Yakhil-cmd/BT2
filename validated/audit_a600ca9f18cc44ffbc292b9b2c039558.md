### Title
Cross-organization webhook spoofing via mismatched signature-verification key and repository-lookup key - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and therefore the HMAC `webhook_secret`) used to validate an inbound webhook based on `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, while every `Webhooks::Handlers::Handler` subclass (e.g. `PushHandler`) resolves the actual `Repository`/`Stack` to act on from a *different, independently-attacker-controlled* field: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so an attacker can pick which organization's credentials are used for signature verification while directing the resulting action at a repository belonging to a totally different, unrelated organization.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GithubApp#verify_webhook_signature` also short-circuits to `true` whenever no `webhook_secret` is configured for that org:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Shipit explicitly supports multi-organization configuration where `webhook_secret` can be left blank/nil per org, as shown in the documented sample config: [3](#0-2) 

Meanwhile, every webhook handler resolves the target repository/stack using a *separate* JSON field that is never cross-checked against `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process` uses that lookup to enqueue a sync against arbitrary stacks using an attacker-supplied `after` (expected head sha) and `ref` (branch):
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The trust binding that should hold is: `organization authenticated by verify_signature == owner of the repository/stack actually acted upon`. Before a malicious request: this equality holds implicitly under legitimate GitHub delivery, because GitHub always sets `repository.owner.login` consistent with `repository.full_name` and signs the whole payload with the secret belonging to the app installed on that specific org/repo. After an attacker forges a POST body, the two fields are independent JSON keys with no server-side consistency check, so the equality breaks: `repository_owner` (used to pick the app/secret for verification) can be set to any organization configured in `Shipit.github(...)` — including one whose `webhook_secret` is blank, causing verification to trivially pass — while `repository.full_name` (used by every handler to find the `Repository`/`Stack`) can simultaneously name a repository belonging to a completely different, unrelated, strictly-secured organization.

### Impact Explanation
An unauthenticated, unprivileged internet requester (no Shipit session, no `ApiClient` token, no knowledge of any org's real `webhook_secret`) can:
1. Send `POST /webhooks` with `X-Github-Event: push` and a body like:
   ```json
   {
     "repository": { "owner": { "login": "org-with-no-secret" }, "full_name": "victim-org/victim-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
2. `repository_owner` resolves to `org-with-no-secret`, whose `webhook_secret` is nil/blank, so `verify_webhook_signature` returns `true` unconditionally — no signature at all is required.
3. `PushHandler` then looks up the stack for `victim-org/victim-repo` (via `Repository.from_github_repo_name`/`repository_name`) — a repository whose real GitHub App has a properly configured, secret-protected webhook — and enqueues `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` for the `master` branch of that stack.

This lets an attacker force a spoofed "push" event onto any tracked stack belonging to any other configured (or even unrelated but registered) repository, without ever satisfying that repository's own webhook secret. Depending on stack configuration (continuous deployment triggers, sync-driven deploy candidacy), this can influence which commit is treated as the expected head and feed into deploy/rollback candidate selection — i.e., cross-repository/cross-organization forgery of GitHub events, satisfying the "unauthorized deploy" class of impact if continuous delivery is enabled on the targeted stack. The same mismatch applies to every other handler (`membership`, `status`, `check_suite`, `pull_request` handlers) that all derive the acted-upon repository from `payload.dig('repository','full_name')` independent of `repository_owner`.

### Likelihood Explanation
Requires no credentials at all beyond network access to `/webhooks`, and only requires the Shipit instance to be configured with at least one organization/app entry that has a blank `webhook_secret` (an explicitly documented and supported configuration in this codebase) or an organization the attacker otherwise controls a valid webhook secret for. Given that omitting `webhook_secret` is presented as a normal, optional configuration path in `docs/setup.md` and the sample secrets files, this is a realistic operational configuration, not a contrived edge case.

### Recommendation
Bind the field used to select the verifying GitHub App to the same field used for repository/stack resolution. Concretely:
- Compute `repository_owner` and `repository_name`/`full_name` from the same canonical field (`repository.full_name`), and verify `repository.owner.login`/`organization.login` (if present) matches the owner segment of `full_name`, rejecting the request otherwise.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is unset for an org that owns tracked repositories/stacks; require an explicit secret for any org used to authorize state-changing webhook actions, or fail closed instead of open when no secret is configured.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "org-with-no-secret" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
- `WebhooksController#verify_signature` resolves `repository_owner = "org-with-no-secret"`, whose configured `webhook_secret` is nil, so `GithubApp#verify_webhook_signature` returns `true` regardless of the (absent/invalid) `X-Hub-Signature` header [2](#0-1) .
- `PushHandler.call(params)` is invoked and resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [4](#0-3) , enqueuing `sync_github(expected_head_sha: "deadbeef...")` for that stack's `master` branch [5](#0-4) , even though the attacker never possessed `victim-org`'s real webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
