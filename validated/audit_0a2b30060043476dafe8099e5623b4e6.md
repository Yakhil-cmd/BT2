### Title
CCMenu endpoint ignores API client stack scoping, allowing a stack-scoped token to read the build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
Every other API endpoint restricts a scoped `ApiClient` (one whose `stack_id` is set) to only the stack it was issued for, but `Shipit::Api::CCMenuController` overrides the `stack` lookup and resolves `params[:stack_id]` against the entire `Stack` table, bypassing that restriction.

### Finding Description
`Shipit::Api::BaseController` enforces the binding "a stack a token authorises == the stack it touches" via: [1](#0-0) 

`stacks` narrows the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that narrowed set. This is the mechanism that every other stack-scoped API endpoint (deploys, rollbacks, tasks, hooks, merge_requests, etc.) relies on to keep a stack-restricted token confined to its own stack.

`Shipit::Api::CCMenuController` breaks this binding by redefining `stack` to bypass the scoping entirely: [2](#0-1) 

Here `stack` resolves directly against `Stack.from_param!(params[:stack_id])`, without going through `stacks`/`current_api_client.stack_id`. The controller still calls `require_permission :read, :stack`, but `ApiClient#check_permissions!` only checks that the `permissions` array contains `read:stack` — it never checks which stack the client is scoped to: [3](#0-2) 

So the equality that should hold — `current_api_client.stack_id == stack.id` (when the client is scoped) — is checked everywhere else in the API surface via `stacks`/`stack`, but is never checked in `CCMenuController`.

### Impact Explanation
An `ApiClient` can be created and scoped to a single stack (`ApiClient#stack`, optional belongs_to) specifically so that a token can be distributed externally (e.g., embedded in a CI dashboard/CCTray badge URL, which is exactly what CCMenu tokens are designed for — see `CCMenuUrlController`, which mints a `read:stack` client and embeds its `authentication_token` directly in a query string URL meant to be shared/displayed publicly): [4](#0-3) 

Anyone who obtains that single-stack token (by design, a low-privilege, narrowly-scoped credential meant to only reveal one stack's CI/build status) can instead call `GET /api/stacks/*stack_id/ccmenu?token=...` with an arbitrary `stack_id` and read the deploy/build status, lock state, and name of any stack in the whole Shipit instance — this is unauthorized read of stack state/deploy status that the token was never meant to grant, matching the "stack a token authorises versus a stack it touches" trust binding called out for this class of bug.

### Likelihood Explanation
Any holder of a valid `read:stack`-scoped `ApiClient` token that was issued for one stack (this is precisely the credential model `CCMenuUrlController` produces, intended for embedding in third-party CI status tools) can trivially trigger this by changing the `stack_id` in the URL. No additional privilege, secret, or write access is required beyond possessing one legitimately-scoped, low-privilege CCMenu token.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and use the inherited `stacks`/`stack` scoping from `BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])`) so a stack-scoped `ApiClient` cannot resolve stacks outside its own `stack_id`.

### Proof of Concept
1. Create a stack-scoped `ApiClient` restricted to `Stack A` with `permissions: ['read:stack']` (this mirrors what `CCMenuUrlController#client` produces when scoping is added, or any admin-created scoped client via `/api_clients`).
2. Use that token to call `GET /api/stacks/<owner>/<repo>/<env-of-Stack-B>/ccmenu?token=<TOKEN>` — i.e., substitute a `stack_id` different from the one the client is scoped to.
3. Observe that `CCMenuController#stack` resolves `Stack B` via `Stack.from_param!` (unscoped), and `require_permission :read, :stack` passes because the client's `permissions` array contains `read:stack` regardless of which stack is targeted — the request succeeds and returns Stack B's CCMenu status even though the token was only ever meant to authorize reading Stack A.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
