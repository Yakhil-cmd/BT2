## Analysis

The bug class in the report is a **destructuring/dispatch confusion**: a value used to select the *trust boundary* (the `channel`) is taken from the same untrusted object as the data that gets acted upon, so an attacker can make the two diverge and reach an internal channel they shouldn't be able to reach.

The Shipit `WebhooksController` has the same structural flaw. It picks *which* organization's HMAC secret to verify the signature against using one field of the untrusted JSON body, but the downstream event handlers act on a *different, independently attacker-controlled* field of that same body to decide which repository/commit to mutate. [1](#0-0) [2](#0-1) 

`repository_owner` (`repository.owner.login`) selects the GitHub App/secret used to verify `X-Hub-Signature`. That secret is per-organization on multi-tenant Shipit instances configured with multiple GitHub Apps (documented feature), so any organization that legitimately owns one of the configured GitHub Apps controls a valid secret of its own: [3](#0-2) 

Once the signature check passes, the individual handlers never re-check that `repository.owner.login` matches the object they mutate:

- `StatusHandler#process` looks up commits **globally by SHA, with no repository/organization scoping at all**: [4](#0-3) 

- `PushHandler` and `CheckSuiteHandler` scope to a repository using a *different* payload field, `repository.full_name`, via `Handler#repository_name`: [5](#0-4) [6](#0-5) 

Both `repository.owner.login` (used for signature selection) and `repository.full_name` / `sha` (used to select the record to mutate) are fields inside the same JSON body the attacker controls; there is no cryptographic or logical binding forcing them to refer to the same repository.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on repository/commit data taken from unrelated fields of the same payload, allowing cross-tenant status/sync forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
On a Shipit instance configured with more than one GitHub App/organization (a documented supported configuration), the equality "organization whose secret authenticated the request" == "repository/commit that gets written" is never enforced.

### Finding Description
`WebhooksController#verify_signature` derives the verifying GitHub App purely from `params.dig('repository','owner','login')` in the unauthenticated body, then verifies the HMAC over the whole raw body using that org's `webhook_secret`. [7](#0-6) 

Because an attacker who legitimately administers *any one* of the organizations configured on the shared instance knows/controls that organization's own `webhook_secret`, they can craft an arbitrary JSON body, sign it with their own secret, and set `repository.owner.login` to their own org (so the signature check passes) while setting the fields the handlers actually operate on to values belonging to a *different* tenant:

- `StatusHandler` resolves the target purely via `Commit.where(sha: params.sha)`, with no organization/repository filter whatsoever, so any commit SHA in the entire Shipit database (belonging to any other tenant's stack) can have a status injected. [4](#0-3) 
- `PushHandler`/`CheckSuiteHandler` resolve the target stacks via `repository.full_name` [8](#0-7) , a field independent from `repository.owner.login` used for signing, so an attacker's org secret can be used to sign a payload whose `repository.full_name` names any other tenant's repository, triggering `stack.sync_github` for that foreign stack. [6](#0-5) 

### Impact Explanation
Using only credentials for their own (legitimately owned) organization, an attacker can forge `status`/`push`/`check_suite` events for repositories belonging to unrelated tenants on the same shared Shipit instance. Forged `status` events feed `Commit#create_status_from_github!`, which drives Shipit's deployability gating (the `deployable_status` hook event), so an attacker can mark a foreign commit as CI-green without CI ever running, undermining the deploy gate and potentially enabling an unauthorized deploy of that commit if auto-deploy or human approval relies on that status. Forged `push` events trigger `GithubSyncJob` against a stack the attacker does not control.

### Likelihood Explanation
Requires the attacker to control (own the secret of) at least one GitHub App/organization configured on a multi-tenant Shipit instance — a normal, supported, and documented configuration — with no other privileged Shipit credentials, tokens, or repository write access needed for the *victim* tenant. This is a realistic scenario for any shared/hosted Shipit deployment serving multiple organizations.

### Recommendation
After signature verification succeeds, re-derive the organization/repository actually to be mutated strictly from the same `repository.owner.login`/App context used to select the verifying secret, and reject or scope handler queries (especially `StatusHandler#process`'s unscoped `Commit.where(sha:)`) to only that organization's repositories, rather than trusting unrelated fields (`repository.full_name`, bare `sha`) from the same unauthenticated JSON body.

### Proof of Concept
1. Configure Shipit with two orgs per `docs/setup.md`'s multi-app example: `attacker-org` (attacker administers/owns the GitHub App and knows its `webhook_secret`) and `victim-org` (tracks a commit `abc123` on stack `victim-org/repo`).
2. Attacker crafts:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker signs the raw body with `attacker-org`'s own `webhook_secret` and sends it with `X-Github-Event: status` to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and verifies successfully (it is genuinely signed by that org's secret). [7](#0-6) 
5. `StatusHandler#process` finds commit `abc123` regardless of which org it belongs to and creates a "success" status on it. [4](#0-3)
