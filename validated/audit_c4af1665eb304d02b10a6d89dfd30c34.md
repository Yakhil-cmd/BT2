## Analog Found

### Title
Webhook signature is verified against `repository.owner.login`'s app while the mutating handlers act on unrelated `repository.full_name` / commit `sha` fields, letting an unauthenticated caller forge deploy-gating events for arbitrary stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the GitHub App whose secret should validate the incoming payload using a field pulled straight out of the *unauthenticated* JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` (`repository.owner.login`, falling back to `organization.login`) selects `Shipit.github(organization: repository_owner)`, and only *that* organization's `webhook_secret` is used to validate `X-Hub-Signature`. Critically, `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically valid: [3](#0-2) 

Leaving `webhook_secret` empty for an organization is a documented, supported configuration state (`webhook_secret: # nil`), and Shipit explicitly supports hosting multiple GitHub organizations in one instance: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the parsed body to the event handlers unchanged: [6](#0-5) 

But the handlers never re-check `repository.owner.login` (the field the signature was actually verified against). They instead trust a completely different field, `repository.full_name`, to select the target `Stack`: [7](#0-6) [8](#0-7) 

`StatusHandler` is even less scoped — it looks up commits **by sha alone, across every stack/repository in the installation**, with no repository binding whatsoever: [9](#0-8) 

This is the same bug class as the report: the security check validates one field (`repository.owner.login`, used only to pick the signing key) while the actually-executed action is driven by a different, unverified field (`repository.full_name` or a bare commit `sha`) taken from the same untrusted payload — exactly analogous to a signature covering one encoding of the ABI data while the EVM executes a padded variant of it. The binding that should hold is:

`organization whose secret authenticated the request == repository/stack the request is allowed to mutate`

and it does not, because these are two independent, attacker-controlled JSON fields.

### Impact Explanation
In any Shipit deployment configured for multiple GitHub organizations (a documented, supported feature) where at least one configured organization has no `webhook_secret` set (also a documented default/example value), an unauthenticated attacker can:
1. Set `repository.owner.login` (or `organization.login`) to the no-secret organization — `verify_webhook_signature` returns `true` unconditionally, so no signature is needed at all.
2. Set `repository.full_name` (for `push`/`check_suite`) or `sha` (for `status`) to point at a completely unrelated repository/commit belonging to any other configured stack.

This forges `push` events (triggering `GithubSyncJob`/`stack.sync_github`), `check_suite` events, and — most severely — `status` events that create arbitrary commit statuses on any commit Shipit knows about, regardless of which repository it belongs to. Since commit statuses (`deployable_status`, `merge_status`) are used by Shipit to gate deploys and merge queues, this allows an unauthorized actor to force a stack into a deployable/mergeable state, i.e., an unauthorized deploy or merge — meeting the Critical bar in the rules.

### Likelihood Explanation
No credentials, tokens, or GitHub access are required — only the ability to send a raw HTTP POST to `Shipit::WebhooksController#create` with an `X-Github-Event` header, satisfying the "unprivileged attacker" requirement. The only precondition is an operator having configured multi-organization support with a blank `webhook_secret` for at least one org, which the shipped documentation and example secrets files present as a normal, valid configuration state, not a misconfiguration warning.

### Recommendation
- Require `webhook_secret` to be present for every configured organization; refuse to boot (or refuse all webhooks) if any organization's secret is blank instead of auto-accepting unsigned payloads.
- Bind the field used to select the signing organization to the field used to authorize the mutation: after signature verification, re-derive `repository.owner.login` from the *same* `repository.full_name`/`Repository` record the handler resolves, and reject the event if they don't match.
- Scope `StatusHandler#process` (and any other handler) to commits/stacks belonging to the repository identified in the payload, rather than a global `Commit.where(sha:)` lookup.

### Proof of Concept
Given a Shipit instance configured with two orgs, `trusted-org` (has `webhook_secret` set) and `open-org` (left `webhook_secret: # nil` per the documented example), and a target stack `trusted-org/prod-app`:

```
POST /webhooks
X-Github-Event: status
Content-Type: application/json
(no valid X-Hub-Signature needed)

{
  "organization": { "login": "open-org" },
  "repository": { "owner": { "login": "open-org" }, "full_name": "irrelevant/unused" },
  "sha": "<known head sha of trusted-org/prod-app>",
  "state": "success",
  "context": "ci/required-check"
}
```

`verify_signature` resolves `repository_owner` = `open-org`, calls `Shipit.github(organization: 'open-org').verify_webhook_signature(...)`, which returns `true` unconditionally because `open-org`'s `webhook_secret` is blank [10](#0-9) . The request is accepted, and `StatusHandler#process` creates a success status on the commit belonging to `trusted-org/prod-app` [9](#0-8) , potentially satisfying deploy/merge gating for a stack the attacker has no relationship to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
