### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, letting a webhook secret holder for one organization forge push/status/check-suite events against a stack owned by any other organization on the same Shipit instance - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON payload, then calls `Shipit.github(organization: repository_owner)` to fetch that org's `GithubApp` and verify the signature. [1](#0-0) [2](#0-1) 

Once the signature validates, every event handler determines the target repository/stack from a *different* field in the same body, `repository.full_name`, via `Handler#repository_name`/`#stacks`. [3](#0-2) 

Nothing cross-checks that `repository.owner.login` (the field that selected the verifying secret) matches `repository.full_name` (the field that selects the stack being mutated). Because the HMAC only proves "this body was signed with *some* org's secret", not "this body concerns that org's repository", an attacker who legitimately controls the webhook secret for Organization A (any org configured on the shared Shipit instance) can build a raw JSON body where `repository.owner.login` = "A" (so `Shipit.github(organization: "A")`'s secret is used to compute a valid `X-Hub-Signature`) while `repository.full_name` = "victim-org/victim-repo" (so the handler resolves and mutates a completely different organization's stack).

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the webhook == the organization whose repository is written by the handler*. The engine breaks this equality:

- Signature-selection binding: `repository_owner` (from `repository.owner.login`/`organization.login`) chooses the `GithubApp`/secret. [1](#0-0) 
- Resource-selection binding: `repository_name` (from `repository.full_name`) chooses the `Repository`/`Stack`s that are mutated. [3](#0-2) 

These two lookups read independent, attacker-supplied JSON keys from the same raw POST body that is HMAC-signed as an opaque blob. The HMAC guarantees only that the *whole body* was produced by whoever owns the secret used to compute it — it says nothing about internal consistency between `repository.owner.login` and `repository.full_name`. Since `Shipit.github(organization:)` looks up per-organization configuration (each org has its own `webhook_secret`), the attacker only needs a secret valid for **any** organization hosted by the same Shipit instance, not the victim organization's secret.

`PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` for every stack under the forged repository, `StatusHandler` writes commit statuses (`commit.create_status_from_github!`), and `CheckSuiteHandler` triggers `schedule_refresh_check_runs!` — all scoped by `repository.full_name`, none of which is covered by the signature-selecting field. [4](#0-3) [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who holds a valid webhook secret for one organization configured on a multi-organization Shipit deployment can forge push/status/check-suite webhooks that are accepted as authentic for a victim organization's repository. This lets the attacker:
- Force `sync_github` to run against a victim stack with an attacker-chosen `expected_head_sha`, writing forged commit/state data into the victim's stack.
- Inject forged commit statuses (`StatusHandler`) or check-run refresh triggers (`CheckSuiteHandler`) for the victim's commits, which can influence deploy-gating logic (`shipit.yml` required statuses) that decide whether a deploy/merge/rollback is permitted.

This is a cross-organization confused-deputy write: the "credential" (webhook secret) that authorizes the request belongs to org A, but the write lands on org B's data. This matches the Critical "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the attacker to already possess a valid webhook secret for at least one organization configured on the target Shipit instance (a real but bounded precondition on shared/multi-tenant Shipit deployments hosting several GitHub organizations). No access to the victim's GitHub organization, repository, or any Shipit session/API token is needed — only crafting a raw JSON body with mismatched `repository.owner.login` / `repository.full_name` fields and a correctly computed HMAC using the known secret.

### Recommendation
In `WebhooksController#verify_signature`, and/or in `Handler#repository_name`, cross-validate that the organization used to select the verifying secret is the same organization that owns the `repository.full_name` being acted upon (e.g., derive both from the same trusted field, or explicitly compare `repository.owner.login` against the owner portion of `repository.full_name`, rejecting mismatches with `head(422)`).

### Proof of Concept
1. Shipit instance is configured to host stacks for two organizations, `attacker-org` (attacker knows its `webhook_secret`) and `victim-org` (hosts the target stack).
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, body)`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature. [1](#0-0) 
5. `PushHandler#process` resolves `repository_name` from `repository.full_name` ("victim-org/victim-repo") and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, even though the request was authenticated using `attacker-org`'s secret. [4](#0-3)
