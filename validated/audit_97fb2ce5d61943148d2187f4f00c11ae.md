### Title
Data-feed key injection via unsanitized `feed_name` allows oracle to forge stored MCI/type/value fields in the KV data-feed index - ([File: data_feeds.js])

### Summary
Similar to the AsyncSSH `AuthorizedKeysFile %u` bug — where an attacker-controlled string is concatenated into a delimiter-separated path without stripping the delimiter/traversal characters, letting the attacker "escape" into an unintended file — ocore's data-feed storage builds its RocksDB keys by directly concatenating the attacker-controlled `feed_name` string with `\n` as the field separator, with no evidence that `feed_name` is checked to exclude embedded `\n` characters before being used as a structural key component.

### Finding Description
Data feeds are stored and queried using `\n`-delimited keys such as `'df\n'+address+'\n'+feed_name+'\n'+prefixed_value+'\n'+strMci` and `'dfv\n'+address+'\n'+feed_name+'\n'+strMci`, built in: [1](#0-0) 
and consumed for lookups in: [2](#0-1) [3](#0-2) 

`feed_name` is taken verbatim from the `data_feed` message payload posted by any unit author (the oracle address), and used as a raw key-component, exactly like the SSH advisory's `%u` username being substituted unsanitized into `AuthorizedKeysFile`. Every reader relies on the `\n`-delimited structure to separate `address`, `feed_name`, `type`, `value`, and the reverse-encoded `mci` (`string_utils.encodeMci`) — e.g. `getValueFromDataFeedKey` in [4](#0-3)  asserts exactly 6 `\n`-separated parts and blindly trusts positional fields.

If `feed_name` is allowed to contain a literal `\n` character (I could not confirm from the available index whether `validation.js`'s `data_feed` payload validation rejects embedded newlines in the key name — this needs to be checked directly in the repository, as the file's content was not retrievable through the index for this specific check), a malicious oracle could craft a `feed_name` value that itself contains `\n`-separated `type\nvalue\nmci` segments. This would let the stored key diverge from the value the writer intended to encode (`string_utils.encodeDoubleInLexicograpicOrder(value)` / `string_utils.encodeMci(mci)`), effectively forging the `type`, `value`, or reverse-sorted `mci` suffix that `readDataFeedByAddress`/`dataFeedByAddressExists` parse back out, analogous to how the SSH bug let the attacker use `%u`-expansion to point outside the intended directory.

### Impact Explanation
`readDataFeedValueByParams`/`getDataFeed`/`in_data_feed` in oscript are used by AAs to make trust decisions and payout logic based on data-feed values and their MCI-ordering (`min_mci`/`max_mci` window checks exist specifically to prevent an oracle from retroactively forging feed history for already-triggered AAs, see `min_mci` checks in [5](#0-4) ). If the key-encoding invariant can be broken via `feed_name` injection, a malicious oracle/AA-defined-data-feed source could forge an entry that appears to have been posted at an mci/type/value other than what actually occurred, subverting the min_mci ordering guarantee AAs rely on for correctness. This could cause an AA to release funds or make decisions based on a forged historical data-feed value — leading to AA fund loss or a stability/consensus disagreement between nodes that reconstruct data-feed state differently.

### Likelihood Explanation
Reachable by any unit author who posts a `data_feed` message (no special privilege required beyond being the oracle address an AA is configured to trust) — the same low-privilege bar as the original SSH bug's "attacker-controlled username." Likelihood depends entirely on whether `validation.js`'s data-feed payload validation restricts `feed_name` characters (specifically rejecting embedded `\n`); this could not be confirmed with the tools available in this session due to index limitations, so this should be verified directly against `validation.js`'s `data_feed` case before treating this as confirmed-exploitable.

### Recommendation
In `validation.js`, explicitly reject `feed_name` (and any other value later used as a KV-store key component, e.g. `payload[feed_name]` types) containing `\n`, `\r`, or other structural delimiter bytes used by `data_feeds.js` and `string_utils.js` key encoders, before the message is accepted into the DAG. Alternatively, use a length-prefixed or escaped encoding for `feed_name` in the KV key so that no possible `feed_name` value can inject additional `\n`-delimited segments into the key structure.

### Proof of Concept
Not independently reproduced against the ocore codebase in this session; conceptually:
1. A user posts a unit with a `data_feed` message whose payload key is `feed_name = "X\nn\n<forged-lexicographic-value>\n<forged-reverse-mci>"`.
2. When `main_chain.js`'s `addDataFeeds` writes `'df\n'+address+'\n'+feed_name+'\ns\n'+strValue+'\n'+strMci` to the KV store, the embedded `\n` sequences in `feed_name` create a key indistinguishable in structure from a legitimately-encoded `df` entry for feed name `"X"` with an attacker-chosen type/value/mci suffix.
3. A subsequent AA data-feed lookup for feed name `"X"` via `readDataFeedByAddress`/`dataFeedByAddressExists` (data_feeds.js:110-339) may match the forged suffix, returning attacker-controlled value/mci to the AA logic. [6](#0-5) [1](#0-0)
