## Finding: CCMenu token scope mismatch — token authorized for "any stack" is minted from a per-stack URL

### Title
Insufficiently Scoped CCMenu API Token Allows Reading Deploy/Build Status of Any Stack - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
`CCMenuUrlController#fetch` mints a `read:stack` `ApiClient` token and embeds it in a per-stack CCMenu URL (`/api/stacks/:stack_id/ccmenu.xml?token=...`), intending the token to grant read access to that one stack's build/deploy status only. However, the `ApiClient` created for this purpose is never bound to the target stack, so the resulting token in fact authorizes reading the status of every stack in the Shipit instance, not just the one the URL was generated for.

### Finding Description
`app/controllers/shipit/ccmenu_url_controller.rb` creates (or reuses) an `ApiClient` scoped only by `creator` and `name`, with `permissions: %w[read:stack]`, and **never sets the `stack:` association**: [1](#0-0) 

Because `ApiClient#stack_id` is left `nil`, `Shipit::Api::BaseController#stacks` — the method meant to enforce "this client can only see its own stack" — falls through to the unrestricted branch: [2](#0-1) 

`Shipit::Api::CCMenuController` further authenticates purely via the query-string `token` param (no session, no Basic Auth) and resolves the stack directly by the `stack_id` path segment supplied in the request, with only a permission-name check (`read:stack`), not a per-stack check: [3](#0-2) 

The binding that should hold is: *stack the token was minted for* == *stack the token can be used against*. Before the attack: the URL `GET /api/stacks/<owner>/<name>/<env>/ccmenu.xml?token=T` returns status for stack `<owner>/<name>/<env>` only, as the UI implies. After: because `T` is not bound to any stack (`stack_id` is `nil`), the same `T` also satisfies `GET /api/stacks/<other-owner>/<other-name>/<other-env>/ccmenu.xml?token=T` for **any other stack in the instance**, since `require_permission :read, :stack` only checks the string `"read:stack"` is present in `T`'s permissions list, and `stack` is resolved from attacker-supplied `params[:stack_id]` with no ownership check.

This is the same class of bug as the reported `lock()`/allowance issue: a value that is supposed to represent "the specific, bounded thing the credential should cover" is checked against an unbounded/incorrect proxy (`allowance` vs. actual balance ↔ "any client with `read:stack`" vs. "the specific stack the client was minted for").

### Impact Explanation
Anyone who obtains a CCMenu URL/token generated for one stack (these are designed to be pasted into third-party, lower-trust CI dashboard tools such as CCTray, and are transmitted in a plain query string) can use that same token, unauthenticated (no Shipit session/login), to read deploy/build status for every other stack hosted on that Shipit instance — including stacks/environments/repositories the token holder was never shown or granted access to. This matches the "unauthenticated read of stack state ... or deploy output" High-impact category.

### Likelihood Explanation
Any authenticated Shipit user can trigger `CCMenuUrlController#fetch` for any stack they can see, obtain the resulting token, and then immediately use it against arbitrary `stack_id` path values — no special privileges, no exploitation complexity beyond changing a URL segment. The token is long‑lived (it's a `SimpleMessageVerifier`-signed client id with no expiry) and is explicitly designed to be shared with third-party tooling.

### Recommendation
Bind the token to the intended stack: set `stack:` on the `ApiClient` created in `CCMenuUrlController#client` (e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`), and ensure `CCMenuController#stack` uses the scoped `stacks` helper from `BaseController` (which already respects `current_api_client.stack_id`) instead of querying `Stack.from_param!` directly against attacker-controlled `params[:stack_id]`.

### Proof of Concept
1. As any logged-in Shipit user, visit `GET /stacks/:id/ccmenu` (`CCMenuUrlController#fetch`) for `stack-A`. Receive `ccmenu_url` containing `token=T`.
2. Send `GET /api/stacks/stack-A/ccmenu.xml?token=T` — succeeds, returns stack-A's status (expected).
3. Send `GET /api/stacks/stack-B/ccmenu.xml?token=T` for an unrelated `stack-B` never associated with this token — succeeds and returns stack-B's deploy status, because `ApiClient#stack_id` is `nil` for `T`, so `BaseController#stacks` (and the permission check `read:stack`) impose no per-stack restriction.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
