### Title
Webhook Organization Used for Signature Verification Is Never Bound to the Repository the Payload Acts On - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check the HMAC signature using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')`) inside the *unverified* JSON body [1](#0-0) . That same field is only used to pick *which secret* validates the signature — it is never cross-checked against the repository the event handlers actually operate on, which is derived independently from `payload.dig('repository', 'full_name')` in `Handler#repository_name` [2](#0-1) .

### Finding Description
In a multi-organization Shipit deployment, `Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization via `github_app_config` [3](#0-2) . The controller's `repository_owner` helper reads `repository.owner.login`/`organization.login` straight from the attacker-controlled JSON body *before* any signature check has occurred [4](#0-3) , and uses it solely to select which org's secret validates `X-Hub-Signature` over `request.raw_post` [1](#0-0)  and [5](#0-4) .

Once the HMAC check passes, `WebhooksController#create` dispatches the *entire raw payload* to event handlers [6](#0-5) , and those handlers resolve the target `Repository`/`Stack` using a *different* field, `payload.dig('repository', 'full_name')` [2](#0-1) , which is looked up independent of organization via `Repository.from_github_repo_name` [7](#0-6) .

This is the same class of bug as the AUIPC report: the verification step covers one representation of a value (`repository.owner.login`, used only to pick the signing key) while the code that actually acts on privileged state trusts a second, unconstrained representation (`repository.full_name`) that the signature never binds to the first. Just as the missing byte-range check let a prover submit `pc_limbs` inconsistent with the real PC while still satisfying the "checked" constraints, here an attacker who knows (or controls) organization A's `webhook_secret` can craft a signed envelope that claims to be "from org A" for signature-selection purposes while its `repository.full_name` payload field names a stack belonging to organization B. The signature check never asserts `repository.owner.login == repository.full_name.split('/').first`, so the HMAC over the raw body proves nothing about which repository is actually acted upon.

Concretely: if organization A is any organization configured in `secrets.github` (including one the attacker legitimately administers, e.g. their own GitHub org onboarded to the same Shipit instance) and organization A's `webhook_secret` is known to the attacker (self-configured, leaked, or intentionally blank — `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, see [8](#0-7) ), the attacker can forge a `push`, `status`, `check_suite`, `pull_request`, `deployment_status`, or `membership` webhook whose `repository.owner.login`/`organization.login` is set to org A (to pass signature selection) but whose `repository.full_name` names any other tracked repository/stack in the Shipit install.

### Impact Explanation
Handlers keyed off `repository.full_name` act on arbitrary tracked stacks: e.g. the `push` handler enqueues `GithubSyncJob` to sync commits for the target stack [9](#0-8) , `status`/`check_suite`/`deployment_status` handlers mutate commit/stack CI state that gates deploy eligibility, and `membership`/`pull_request` handlers mutate `Team`/`User`/`Membership` records and review-stack state. By crossing organization A's authentication with organization B's repository, an attacker can inject forged CI status, forged commits-synced state, or forged membership/PR data into a stack they do not otherwise control, potentially unblocking or triggering an unauthorized deploy path — this reaches the "unauthorized deploy/rollback/merge" / cross-repository write impact bar.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with more than one GitHub organization (multi-tenant `secrets.github` keyed by org) and requires the attacker to know/control the `webhook_secret` for at least one of the configured organizations — which is realistic in shared/managed Shipit deployments where multiple teams or orgs each provide their own webhook secret, since a user with legitimate admin rights over org A's GitHub webhook config could reuse that access to attack org B's stacks hosted on the same Shipit instance. No `ApiClient` token, session, or GitHub write access to the victim repository is needed.

### Recommendation
In `WebhooksController#verify_signature` / `#repository_owner`, verify that the organization used to select the signing secret matches the owner embedded in `repository.full_name` (and any other repository identifiers the handlers consume) before dispatching to handlers — i.e., derive a single canonical "authenticated repository owner" from the verified payload and require every downstream `Repository`/`Stack` lookup to be scoped to that same owner, rejecting the event (422) on mismatch, analogous to the fix's approach of consistently constraining every limb of the value used, rather than only a subset.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org-a` (attacker-known `webhook_secret`) and `org-b` (contains stack `org-b/victim-repo`).
2. Attacker computes `sha1=HMAC(org_a_webhook_secret, body)` over a crafted JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  ...
}
```
3. POST to `/github/webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates the signature successfully against `org-a`'s secret [1](#0-0) .
5. `Shipit::Webhooks.for_event('push')` handler resolves the target via `payload.dig('repository','full_name')` = `"org-b/victim-repo"` [2](#0-1) , enqueuing `GithubSyncJob` for `org-b`'s stack despite the request never being authenticated by `org-b`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
