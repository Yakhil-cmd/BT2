## Title
Unhandled Exception Crash via Dry-Run AA Trigger Execution on Untrusted Payment Unit - (File: network.js)

### Summary
CVE-2020-27842 describes a null-pointer dereference in openjpeg's t2 encoder that an attacker triggers by supplying crafted input, crashing the process and denying availability. The reachable analog in `ocore` is an **unhandled exception/unhandled promise rejection** that any unprivileged unit poster can trigger against a full node (hub/witness) simply by sending a normal payment to an existing AA address, causing the entire node process to crash.

### Finding Description
When a new unit is validated successfully and pays to an on-chain AA, `handleJoint`'s `ifOk` callback in [1](#0-0)  performs a **dry run** of the AA trigger before the unit is even committed:

```js
ifOk: async function(objValidationState, validation_unlock){
    ...
    if (conf.bDryRunNewTriggers && !conf.bLight && !objJoint.ball && objValidationState.count_primary_aa_triggers) {
        const outputAddresses = objJoint.unit.messages
            .filter(msg => msg.app === 'payment')
            .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
        const rows = await db.query("SELECT address, definition FROM aa_addresses WHERE address IN (?)", [outputAddresses]);
        for (let { address, definition } of rows) {
            console.log(`dry run trigger for AA address ${address} in submitted unit ${unit}`);
            const trigger = aa_composer.getTrigger(objJoint.unit, address);
            // if it would crash, let it crash now, not when we execute the trigger for real
            await aa_composer.dryRunPrimaryAATrigger(trigger, address, JSON.parse(definition));
        }
    }
    ...
``` [2](#0-1) 

The comment "if it would crash, let it crash now" acknowledges that formula evaluation can throw synchronously. `ifOk` is `async`, and this call is invoked as a bare callback (`callbacks.ifOk(objValidationState, unlock)` at [3](#0-2) ) without any `.catch()` or surrounding `try/catch`. Any exception thrown inside `dryRunPrimaryAATrigger` → `handleTrigger` → `evaluateAA` → formula `evaluate()` therefore becomes an **unhandled promise rejection**, which by default crashes the Node.js process (and even where caught, `process.on('uncaughtException', ...)` in the same file deliberately re-throws to crash the process): [4](#0-3) .

The formula evaluator contains multiple `throw Error(...)` statements for "impossible" type combinations that are reachable only when the runtime value returned by a sub-expression doesn't match the evaluator's assumptions — e.g. in `substring`, `selectSubobject`, and the top-level dispatcher: [5](#0-4) [6](#0-5) [7](#0-6) 

These `throw` sites are outside the `setFatalError`/callback-based error-handling convention used almost everywhere else in the evaluator, meaning any code path that reaches them raises a hard JS exception instead of a graceful "bounce" of the AA response.

### Impact Explanation
Because the dry-run is triggered for **every unit that merely pays to an existing AA** (not requiring the sender to be the AA author, and not requiring any privileged role), an attacker who identifies (or crafts, via a cooperating malicious/edge-case AA) a state/input combination that drives the formula evaluator into one of these unguarded `throw` branches can crash any full node with `conf.bDryRunNewTriggers` enabled by posting a single ordinary-looking payment unit. This is a direct availability attack: the crashed hub/witness stops confirming units for its peers/light clients, i.e. "a network unable to confirm new units," which matches the required Medium/High impact bar.

### Likelihood Explanation
The reachable surface is broad: any already-deployed AA (even one written by a benign author who didn't anticipate every runtime data shape) combined with attacker-chosen trigger/data-feed/asset state can hit these throw sites, since `aa_validation.js`'s static validation only checks formula syntax and use of allowed operations — it cannot statically rule out every runtime type-mismatch the evaluator itself treats as "impossible." The explicit code comment "if it would crash, let it crash now" shows the developers were aware crashes are possible here; the bug is that the crash is not contained/caught, so it takes down the whole process instead of just failing the dry run.

### Recommendation
Wrap the dry-run trigger block in `ifOk` with `try { ... } catch(e) { ... }` (and ensure any awaited rejection is caught) so that a crash during dry-run only aborts the dry run / logs the error, rather than propagating as an unhandled exception that kills the node process. Additionally, replace the unguarded `throw Error(...)` statements in `formula/evaluation.js`'s runtime evaluation paths (`substring`, `selectSubobject`, the main `evaluate` dispatcher) with the same `setFatalError`/callback error convention used elsewhere, so malformed/unexpected runtime states are converted into a normal AA bounce instead of a JS exception.

### Proof of Concept
1. Deploy (or identify) an AA whose formula, under some external condition (e.g. a `data_feed`, `unit[...]`, or asset lookup returning an edge-case value), reaches one of the unguarded `throw Error(...)` branches in `formula/evaluation.js` (e.g., `substring` with a `start`/`length` value type not covered by the boolean/Decimal branches, or `selectSubobject` producing a `value` type not covered by the boolean/number/Decimal/string/object branches).
2. As an unprivileged user, post an ordinary payment unit sending funds to that AA's address with `conf.bDryRunNewTriggers` enabled on the target node (this is the default dry-run safety feature).
3. `handleJoint`'s `ifOk` handler in `network.js` performs `dryRunPrimaryAATrigger`, which throws synchronously inside the `async` callback; the resulting unhandled promise rejection crashes the Node.js process, taking the hub/witness offline.
