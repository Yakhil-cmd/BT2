### Title
CCMenu API token is not stack-scoped, allowing a `read:stack`-scoped ApiClient to read the build status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via `stack_id` (`belongs_to :stack, optional: true`), and `Api::BaseController#stacks`/`#stack` enforce that scope for every other API endpoint by restricting the lookup to `Stack.where(id: current_api_client.stack_id)` before calling `from_param!`. [1](#0-0) [2](#0-1) 

`Api::CCMenuController`, however, overrides `#stack` to bypass that scoping entirely, resolving the stack directly from the global `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` relation: [3](#0-2) 

### Finding Description
The intended binding is: `ApiClient.stack_id (the stack a token authorizes)` == `Stack resolved for the request (the stack the token actually touches)`.

This binding holds in every other `Api::BaseController` subclass, because `#stack` is inherited unmodified and calls `stacks.from_param!(...)`, where `stacks` filters by `current_api_client.stack_id` when present: [2](#0-1) 

`Api::CCMenuController` redefines `#stack` to call `Stack.from_param!(params[:stack_id])` directly, dropping the `current_api_client.stack_id` filter: [3](#0-2) 

The only authorization check that remains is `require_permission :read, :stack`, which simply checks that `"read:stack"` is present in `permissions`, without checking which stack that permission was intended to apply to: [4](#0-3) [5](#0-4) 

This class of token exists specifically to be single-stack scoped: `CCMenuUrlController` (the normal way tokens for this endpoint are minted, e.g. from a stack's page) creates a client scoped only by `permissions: %w[read:stack]`, and the URL for this token is embedded with a `stack_id` in the query path, implying the token is meant to be usable only for that one stack. Combined with the general-purpose `here_come_the_walrus` fixture demonstrating stack-scoped `ApiClient`s (`stack: shipit`) that are enforced everywhere else in the API: [6](#0-5) [7](#0-6) 

Any bearer of a stack-scoped, `read:stack`-only CCMenu token (delivered unauthenticated via query string, per `CCMenuController#authenticate_api_client`) can substitute any other stack's `stack_id` in the URL and read that stack's CI/CD status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) even though the token's `stack_id` binds it to a single stack. [8](#0-7) 

### Impact Explanation
This is a cross-stack read of stack state without authorization for that stack — a token minted for stack A's CCMenu widget is used to read stack B's deploy/build status and lock reason, none of which the token holder was granted access to. This matches "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state" class of impact: the token was designed and distributed as a narrow, single-stack, unauthenticated-bearer capability (embedded in a CI widget URL), and this bug removes the stack boundary entirely, turning it into an any-stack read capability across the whole Shipit instance. It exposes deploy status/labels and lock reasons for stacks the requester should have no visibility into.

### Likelihood Explanation
High. Exploitation requires only possession of any valid `read:stack` CCMenu API token (these are unauthenticated-bearer, distributed as plain URLs meant to be embedded in CI dashboards/tools, per `CCMenuUrlController#fetch`) and knowledge/guessing of another stack's slug (stack IDs are typically `owner/name/branch`-style human-readable slugs, not secret). No privileged account, session, or webhook secret is needed — only the CCMenu token itself, which by design is meant to be narrowly scoped.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` and let it inherit `Api::BaseController#stack`, which resolves through the scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`), so a stack-scoped ApiClient can only ever resolve the stack it is bound to. If unscoped CCMenu tokens are intentionally supported for `UnlimitedApiClient`/non-scoped clients, keep the scoping logic identical to `BaseController#stacks` (i.e., reuse the inherited helper) rather than reimplementing an unscoped lookup.

### Proof of Concept
1. A user visits a stack's page and Shipit generates a CCMenu URL via `CCMenuUrlController#fetch`, creating (or reusing) an `ApiClient` with only `permissions: %w[read:stack]` and embedding `token=<authentication_token>` plus `stack_id=<that stack>` in the returned URL: [9](#0-8) 
2. An attacker who obtains this URL (e.g., from a shared CI dashboard config, a public status page, or a leaked link) takes the same `token` and issues `GET /api/<other_stack_id>/ccmenu?token=<token>`.
3. `Api::CCMenuController#authenticate_api_client` authenticates via `ApiClient.authenticate(params[:token])` (no `stack_id` check at authentication time): [8](#0-7) 
4. `require_permission :read, :stack` passes because the client's `permissions` includes `"read:stack"`, regardless of which stack is being requested.
5. `#stack` resolves `Stack.from_param!(params[:stack_id])` for the *other* stack (not the one the token's `stack_id` points to), and the controller renders that stack's CI status, leaking `lastBuildStatus`/`lastBuildLabel`/`activity`/lock state for a stack the token was never authorized for: [10](#0-9)
