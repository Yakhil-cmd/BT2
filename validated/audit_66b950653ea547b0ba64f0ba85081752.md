### Title
AA state-var name allows embedded `\n`, letting an oscript trigger forge/collide RocksDB `st\n<address>\n<var_name>` storage keys - ([File: formula/evaluation.js])

### Summary
The Dapr advisory's root cause is that an ACL/authorization layer and the actual dispatch layer built a "path" identity independently, one of them (ACL) stripping/decoding reserved delimiter characters (`../`, `#`, `?`) while the other used the raw string, so an attacker could smuggle a reserved delimiter to make the two layers disagree about which resource was being accessed. The analogous pattern in ocore is any place where a user-controlled string is concatenated with a fixed separator to build a storage/lookup key, where the separator character is not stripped/rejected from the untrusted part. `ocore--002` already recognizes this exact risk for data-feed names/values (both are explicitly checked for `\n`, e.g. `validation.js` lines 1933-1943 and `aa_validation.js` lines 92-119, because `data_feeds.js` builds keys as `'df\n'+address+'\n'+feed_name+...`), but the equivalent state-var name path used by `state_var_assignment` in AA oscript is not checked for `\n`.

### Finding Description
AA persistent storage is a key-value store where the key is built by naive string concatenation with `\n` as delimiter:
- write path: `saveStateVars()` in `aa_composer.js` builds `var key = "st\n" + address + "\n" + var_name;` and does `batch.put(key, ...)` / `batch.del(key)`.
- read path: `readAAStateVar()` in `storage.js` does `kvstore.get("st\n" + address + "\n" + var_name, ...)`, and `readAAStateVars()` builds range-scan bounds `options.gte = "st\n" + address + "\n" + var_prefix_from; options.lte = "st\n" + address + "\n" + var_prefix_to + "\uFFFF";` for prefix enumeration. [1](#0-0) [2](#0-1) [3](#0-2) 

Every other identifier that gets embedded into an analogous `\n`-delimited kvstore key in this codebase is explicitly rejected if it contains `\n`:
- data-feed `feed_name`/value, checked both at unit-validation time (`validation.js`) and at AA-definition-validation time (`aa_validation.js`): [4](#0-3) [5](#0-4) 

By contrast, the `state_var_assignment` handler in the formula evaluator - which is the code path that actually determines the `var_name` used to build the `st\n...` key - only enforces a length limit and a lone-surrogate ("well-formed") check; it never rejects `\n`:
```
if (var_name.length > constants.MAX_STATE_VAR_NAME_LENGTH)
    return setFatalError("state var name too long: " + var_name, ...);
if (!var_name.isWellFormed())
    return setFatalError("state var name not well formed: " + var_name, ...);
``` [6](#0-5) 

The `var_name` here is not a compile-time literal - it is the *evaluated result* of an arbitrary oscript expression (`var_name_or_expr`), so it can be built at runtime from trigger data supplied by an unprivileged AA trigger sender: [7](#0-6) 
Likewise the `var`/`balance` read op only checks `isWellFormed()`, not absence of `\n`, for the var name used to build the read key: [8](#0-7) 

Because the storage key is formed by naive concatenation rather than length-prefixing or escaping, this is the same class of bug as the Dapr advisory: one code path in the system (data-feed keys) treats `\n` as a reserved delimiter and strips/rejects it, while a structurally identical code path (AA state-var keys) does not, so the "logical identity" of a stored value (which var, for which address) can be made to disagree with what the developer of the AA intended when they wrote `var['prefix' || untrusted_input]`.

### Impact Explanation
Many AAs on the network implement per-user namespacing by concatenating a fixed prefix with attacker-influenced data to form the state-var name, e.g. `var['balance_' || trigger.data.user]` or `var['order_' || trigger.data.id]`, relying on the concatenated string acting as an unambiguous compound key. If `trigger.data.user`/`id` (attacker-controlled trigger data) is allowed to contain `\n`, an attacker can craft an input whose resulting `var_name` string collides with, or is indistinguishable from, a `var_name` that a different logical prefix/user would produce, because the delimiter the AA author relies on for separation (`_`, `/`, etc.) is not what actually delimits the underlying storage key - the real delimiter is the unescaped `\n` inserted by `storage.js`/`aa_composer.js`. This can let an unprivileged trigger sender manipulate, overwrite, or read a state variable that the AA logic intended to bind to a different address/user, corrupting AA-held balances or asset/permission bookkeeping and leading to fund loss or unauthorized state mutation for AAs whose access-control model depends on string equality/prefix-uniqueness of `var_name`. It also affects any AA that enumerates its own or another address's vars via prefix scans (`readAAStateVars` bounds), since an injected `\n` can shift ordering/boundaries of the lexicographic scan.

### Likelihood Explanation
Exploitability depends on a given AA's code pattern (concatenating attacker-supplied trigger data into a state-var name without validating it), which is a common and encouraged oscript idiom (per-user or per-object storage keys). The unprivileged trigger sender fully controls the string value used in the concatenation and only needs to include a `\n` character - `isWellFormed()` does not filter it (it only rejects unpaired UTF-16 surrogates), and `MAX_STATE_VAR_NAME_LENGTH` (128) still leaves plenty of room for an embedded newline plus target string. No special privileges are required beyond being able to send a trigger unit to a vulnerable AA. The overall network is not weakened, but any deployed AA relying on `\n`-free concatenation is directly exploitable, mirroring the "single reachable path with a missing reserved-character check that a sibling path already enforces" pattern from the Dapr advisory.

### Recommendation
Reject `\n` (and ideally any other bytes reserved by the kvstore key scheme, such as `\uFFFF` used as the upper scan bound) in state-var names at both the point they're used for writes (`state_var_assignment` in `formula/evaluation.js`) and reads (`var`/`balance` ops in `formula/evaluation.js`), exactly as is already done for `feed_name` in `aa_validation.js` and `validation.js`. This should be enforced both in the static `formula/validation.js` complexity/shape checker (so bad AAs are rejected at definition time even for constant var names) and, since the var name can be dynamically computed, in the runtime `formula/evaluation.js` handler before the key is built.

### Proof of Concept
1. Deploy an AA whose oscript does:
```
{
  init: `$user = trigger.data.user;`,
  messages: [{
    app: 'state',
    state: `{
      var['balance_' || $user] += trigger.output[[asset=base]];
    }`
  }]
}
```
2. Send trigger A with `trigger.data.user = "attacker"` to fund `var_name = "balance_attacker"`.
3. Send trigger B with `trigger.data.user = "victim\nballoon"` (embedding a literal `\n`); this produces `var_name = "balance_victim\nballoon"`.
4. Because `state_var_assignment` in `formula/evaluation.js` (lines 1346-1351) only checks length and `isWellFormed()`, this value passes validation and `saveStateVars()` writes key `"st\n" + AA_address + "\nbalance_victim\nballoon"` - a key structurally different from what the AA author assumed a single "victim" bucket key would look like, and colliding lexicographically in unexpected ways with prefix-range scans (`readAAStateVars`) that use `\n`-based bounds, demonstrating that the reserved delimiter is not neutralized on this path even though the parallel data-feed path (`aa_validation.js` lines 100-101, `validation.js` lines 1936-1937) explicitly blocks the same character.

*Note: the exact severity for a given deployment depends on that AA's own key-construction logic; I was not able to enumerate every existing deployed AA that uses this pattern, only confirm that the core protocol code path lacks the same `\n` guard that its sibling data-feed path enforces.*
