### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but write actions (commit sync, status updates, stack lookup) are keyed off the unrelated `repository.full_name` field in the same unauthenticated JSON body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Every webhook handler, however, resolves the actual `Stack`/`Repository` to mutate using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Shipit supports hosting multiple GitHub organizations from one instance, each with its own (optional) `webhook_secret`: [4](#0-3) [5](#0-4) 

Signature validation is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

and `verify_webhook_signature` explicitly *bypasses* verification when no secret is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [6](#0-5) 

Every handler that follows, however, ignores `repository_owner` entirely and instead resolves the target repository from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [2](#0-1) 

`PushHandler#process` uses this `stacks` scope to trigger a resync of the real repository up to an attacker-supplied `after` SHA:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

Because the raw body is a single JSON object, `repository.owner.login` (used only to pick the verification secret) and `repository.full_name` (used to pick which real Stack gets mutated) can be set to **different** organizations by an attacker who crafts the payload themselves. If the attacker controls (or has installed the Shipit GitHub App on) any organization configured on this Shipit instance with no `webhook_secret` set — an explicitly documented, optional setting — `verify_webhook_signature` returns `true` unconditionally for that organization, and the request is accepted with **no HMAC check at all**. The attacker then sets `repository.full_name` to `"VictimOrg/victim-repo"`, an organization/repo they do not control, causing Shipit to act on that victim's real `Stack` (created via `Repository.from_github_repo_name`) as if GitHub had legitimately delivered the event.

This is the same class of bug as the reported `IBCChannelPacketTimeout.sol` issue: a validity/state check (there, "channel open"; here, "signature verified for organization X") is enforced on one binding (the channel/organization), while the action actually performed operates on a *different*, unchecked binding (the packet/repository) that the check was never designed to cover.

### Impact Explanation
An attacker who controls (or can get the Shipit GitHub App installed on) any single organization hosted by a multi-org Shipit deployment — particularly one where an operator left `webhook_secret` blank, which the docs explicitly allow ("Webhook secret (optional)") — can forge webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) that are accepted with a bypassed/attacker-controlled signature check, then have those events act on any other victim organization's `Stack`/`Repository` known to Shipit, purely by setting `repository.full_name` to the victim's repo. Concretely this allows: forcing `GithubSyncJob` to run against a victim stack with an attacker-chosen `expected_head_sha` (`PushHandler`), and — depending on the specific handler — writing fabricated CI/status records used by `MergeRequest#all_status_checks_passed?` to gate the auto-merge queue. Forging a passing status can unblock `ProcessMergeRequestsJob#merge!`, resulting in an **unauthorized merge**, and forcing resyncs on a `continuous_deployment` stack can precipitate an **unauthorized deploy** — both explicitly in-scope Critical/High impacts.

### Likelihood Explanation
Requires no privileged Shipit credentials (no `ApiClient` token, no session, no GitHub team membership) — only the ability to send an HTTP POST to the public `/webhooks` endpoint, and either (a) knowledge that some organization on the Shipit instance has no `webhook_secret` configured (a documented, optional field, so plausible in real deployments), or (b) being able to install the app on one's own org (self-installable GitHub Apps are common) while relying on distinct-org secrets. The victim organization/repo need only be a target already known to the Shipit instance (i.e., an existing `Stack`); the exact `full_name` value is guessable/discoverable since Shipit stacks/repos are visible in the UI to any authenticated user, and organization names are public.

### Recommendation
Bind the signature-verification identity to the same field the handlers act on: derive `repository_owner` (used for `Shipit.github(organization:)`/secret selection) from the same `repository.full_name` (or explicitly cross-check that `repository.owner.login` matches the owner portion of `repository.full_name`) before dispatching to handlers, and reject the request if they diverge. Additionally, avoid silently bypassing signature verification when `webhook_secret` is blank for any *one* organization in a multi-org configuration — either require a secret whenever more than one organization is configured, or otherwise ensure the "no secret configured" organization cannot cause writes to a different organization's repositories.

### Proof of Concept
1. Configure (or observe) a multi-org Shipit instance where `AttackerOrg` has no `webhook_secret` set and `VictimOrg/victim-repo` is a known `Stack` with `continuous_deployment: true`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-40-char-sha-that-exists-in-victim-repo>",
  "repository": {
    "full_name": "VictimOrg/victim-repo",
    "owner": { "login": "AttackerOrg" }
  }
}
```
No `X-Hub-Signature` header (or an arbitrary one) is required because `Shipit.github(organization: 'AttackerOrg').verify_webhook_signature` returns `true` unconditionally (`webhook_secret` is blank for `AttackerOrg`).
3. `WebhooksController#verify_signature` passes; `PushHandler.call` resolves `Repository.from_github_repo_name('VictimOrg/victim-repo')` and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')`, causing Shipit to sync and potentially auto-deploy that commit on the victim's real stack — even though the attacker never had signing authority over `VictimOrg`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
