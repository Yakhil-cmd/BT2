## Duplicated address/key entries silently accepted in multisig address definitions (`r of set`, `weighted and`) - (File: `definition.js`)

### Summary
`definition.js`'s `validateDefinition()` accepts `r of set` and `weighted and` spending-condition sets without checking that the set's elements are distinct. A user (or set of cosigners) can create/approve an M-of-N shared address whose "set" contains the *same* underlying address (or `sig`/`hash` key) more than once. Because each set element is evaluated and signed independently by signing-path, a single private key can satisfy more than one slot of the `required` threshold, silently reducing the real security guarantee (e.g. a nominal "2 of 3" address collapses to effectively "1 of 2 distinct keys"). This mirrors the reported bug class of "duplicated entry accepted without uniqueness check, corrupting the accounting/threshold logic that assumes distinct entries."

### Finding Description
`validateDefinition()` validates `r of set` and `weighted and` purely structurally — it checks `args.set` is an array of length ≥2, checks `required`/`weight` bounds, and recursively validates each element — but never verifies that the elements (or the addresses/pubkeys they resolve to) are unique: [1](#0-0) [2](#0-1) 

Each element gets its own signing path (`path+'.'+index`), and `validateAuthentifiers()` requires a signature at each authentifier path independently — it never cross-checks that two different paths that map to the *same* underlying address/key aren't being double-counted toward the `required` count: [3](#0-2) 

The project is aware of the general risk of duplicated addresses undermining checks elsewhere — e.g. `is_valid_signed_package()` in the formula engine explicitly rejects signed packages containing duplicate author addresses (`test/formula.test.js:6337-6379`), confirming duplicate-address handling is a recognized attack surface — but no equivalent uniqueness check exists in `definition.js` for address-definition sets. Likewise, `wallet_defined_by_addresses.js`'s `handleNewSharedAddress()` only checks that signer addresses match the definition's declared signing paths; it does not reject definitions whose extracted paths point to the same address/device more than once: [4](#0-3) 

### Impact Explanation
A shared/multisig address created via `r of set`/`weighted and` that (accidentally or maliciously, e.g. by a dishonest party proposing the template during co-signer setup) embeds the same address/key twice will validate and accept payments as if a stronger threshold protects it, while in reality one compromised or malicious cosigner can single-handedly satisfy two (or more) of the required slots. This directly undermines the authorization guarantee for spending funds held at that address — i.e., unauthorized/undercollateralized spending relative to the declared M-of-N policy, similar in class to the original report's "duplicated entry breaks the invariant the rest of the system relies on."

### Likelihood Explanation
This requires a user/cosigner to construct or approve such a definition, so it's not exploitable against arbitrary users without their template accepting it; however, in a multi-party shared-address setup, an honest cosigner has no automated protection from a malicious co-proposer sneaking in a duplicated signing slot, since neither `validateDefinition` nor `handleNewSharedAddress` flags it. Given ocore lets any code path construct such definitions and post them as valid addresses (self-posted, no privileged access required), likelihood is moderate.

### Recommendation
In `validateDefinition()`'s `r of set` and `weighted and` handling, track resolved leaf addresses/pubkeys (for `sig`, `hash`, `address` ops) encountered within a set and reject the definition if the same leaf value appears at more than one position of the same set (or globally within a threshold group), similar to how `checkAttestorList()` already enforces uniqueness/sortedness for attestor lists (`validation.js:2850-2864`). Additionally, `handleNewSharedAddress()` should reject definitions whose `extractAddressPathsFromDefinition()` output contains duplicate addresses assigned to the same threshold group.

### Proof of Concept
1. Build an address definition: `["r of set", {required: 2, set: [["sig", {pubkey: A}], ["sig", {pubkey: A}], ["sig", {pubkey: B}]]}]` — nominally "2 of 3", using the same pubkey `A` twice.
2. Compute the chash address and validate it via `Definition.validateDefinition` — validation succeeds (no uniqueness check fires).
3. Sign a unit as author of this address, providing the *same* signature under both authentifier paths corresponding to the two `A` slots (`r.0` and `r.1`), and no signature from key `B`.
4. `validateAuthentifiers()` accepts the unit because both authentifier paths independently verify against key `A`'s signature, satisfying `required=2` with only one distinct private key — defeating the intended 2-distinct-key threshold.
