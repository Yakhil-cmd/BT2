### Title
Cross-stack (and cross-organization) commit status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`), never using `Handler#stacks`/`#repository_name` to constrain the lookup to the repository named in the payload. Any request that passes org-level webhook signature verification can therefore write a `Status` onto a `Commit` belonging to a different stack, and — since the lookup isn't even scoped by organization — potentially to a stack belonging to an entirely different organization, as long as a `Commit` row with a matching `sha` exists anywhere in the database.

### Finding Description
The claimed binding, stated explicitly: a `Status` written from a verified webhook payload should belong to `Repository.from_github_repo_name(payload.repository.full_name).stacks.commits` — i.e. `status.commit.stack.repository.full_name == payload['repository']['full_name']`.

Tracing the code:
- `WebhooksController#verify_signature` only proves the request body was HMAC-signed with the `webhook_secret` of the org named by `repository_owner` (`params.dig('repository','owner','login')` or `organization.login`), taken from the same untrusted payload it's verifying: [1](#0-0) [2](#0-1) 
- `Handler#stacks`/`#repository_name` exist precisely to scope handler logic to the repository named in the payload: [3](#0-2) 
- However, `StatusHandler#process` never calls `stacks` at all. It queries `Commit.where(sha: params.sha)` globally and writes a status to every match: [4](#0-3) 
- Compare with `CheckSuiteHandler#process`, which correctly scopes through `stacks.where(branch: ...)` before touching commits: [5](#0-4) 

So the equality the code should enforce (`status.commit.stack.repository.full_name == payload.repository.full_name`) is never checked. The only actual constraint is that the request's HMAC matches *some* org's `webhook_secret`, and `sha` matches *some* `Commit` row anywhere in the `commits` table (not even scoped to the org that signed the request, let alone the specific repository named in `payload.repository.full_name`). `Commit#sha` is not a global collision risk between the *same* repo's history, but the table itself has no uniqueness constraint across stacks — collisions between unrelated stacks (e.g., attacker pushing an empty/degenerate commit to their own repo, or reusing a well-known sha such as an empty tree/initial commit that other stacks may also record) are structurally possible.

Exploit flow: an attacker who operates any repository under an org with a Shipit webhook configured (or who can guess/brute a `sha` colliding with a commit tracked by a victim stack) sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org's `webhook_secret`, and `sha` set to a commit that exists under a different stack (same org or, since the query is unscoped, potentially a different org entirely). The handler writes a `Status` row (state/description/target_url/context, attacker-controlled) onto that foreign commit, which can flip `Commit#state`, trigger `Hook.emit(:deployable_status, ...)`, and call `stack.schedule_merges`, i.e., influence whether a foreign stack's PR/commit is considered deployable/mergeable.

None of the existing guards prevent this: `verify_signature` only authenticates the org named in the same attacker-supplied payload, not the specific repository/stack; `drop_unhandled_event` and `ExplicitParameters` only validate presence/type of `sha`/`state`, not ownership; there is no `Repository`/`Stack` scoping applied anywhere in `StatusHandler`.

### Impact Explanation
A `Status` record — including `state`, `description`, `target_url`, `context` — can be written onto a `Commit` belonging to a stack the attacker does not control, satisfying "a payload for one repository mutating another's stack, commit ... " (Critical). This can flip a foreign commit's deployability state and trigger `stack.schedule_merges`, affecting merge queue behavior for stacks the attacker has no authorization over. Because the lookup is by bare `sha` with no repository or organization scoping at all, the blast radius is not limited to "same org, different stack" as hypothesized in the question — it is unscoped across the entire `commits` table, so it is potentially exploitable cross-tenant (cross-organization), given any sha collision. The attack is repeatable per request and requires only a valid webhook secret for any one org registered in the instance (which the attacker may legitimately possess for their own repository) plus a matching `sha`.

### Likelihood Explanation
Preconditions: attacker needs a webhook configured (and hence a `webhook_secret`) for at least one repository/org they legitimately control in the Shipit instance — a routine, low-cost setup for any GitHub user who owns a repo tracked by Shipit. The harder part is causing a `sha` collision with a commit tracked in the victim stack; this is trivial within the same org for a monorepo-split scenario (identical commit shas legitimately shared across multiple Shipit stacks that all track the same git history, e.g., mirrors, submodule promotions, or multi-stack setups per repo) and only requires luck/targeting for genuinely unrelated repositories. Given that this is a routinely-occurring configuration (shared git history across several stacks) rather than a purely theoretical SHA-1 collision, likelihood is high in the intra-org/shared-history case and lower but not negligible for cross-org sha collisions.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload before touching any commit, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `status.commit.stack.repository.full_name == payload.repository.full_name` for every write.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Set up two stacks/repositories under the same org (`shipit_stacks(:shipit)` and a second fixture stack, or create one), each with a `Commit` fixture sharing the same `sha` value (simulate the collision).
2. Stub/verify `GithubHook#verify_signature` to return `true` (as existing tests do), and set `X-Github-Event: status`.
3. POST a status payload with `repository.full_name` set to stack B's repo name, but `sha` equal to stack A's commit sha.
4. Assert: `assert_difference 'stack_a_commit.statuses.count', 0` currently fails (status *is* written) because `StatusHandler` doesn't scope by repository — proving the vulnerability. After the fix, the same assertion should pass (no status written to stack A when the payload names stack B), and instead a status should only be created if `stack_b.commits.exists?(sha: ...)`.
