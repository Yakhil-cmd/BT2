## Title
Webhook signature verification uses attacker-controlled `repository.owner.login` while handlers act on a different unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's webhook secret to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the **unauthenticated** JSON request body, before that body has been proven authentic. Once the signature passes, every downstream `Shipit::Webhooks::Handlers::Handler` subclass locates the target repository/stack using a *different* field of the same unauthenticated body: `repository.full_name`. Because the field used to pick the verifying secret is not the field used to select the object being mutated, a caller who legitimately controls one configured GitHub organization (and therefore knows/controls that organization's webhook secret) can forge a correctly-signed payload that claims `repository.owner.login` = their own org, but `repository.full_name` = a stack/repository belonging to a completely different organization also hosted on the same Shipit instance.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp` instance (and thus the `webhook_secret`) to verify against solely based on `repository_owner`: [1](#0-0) [2](#0-1) 

The verification itself is a straightforward HMAC compare scoped to whichever org's secret was selected: [3](#0-2) 

Shipit explicitly supports hosting multiple, independent GitHub organizations from a single instance, each with its own `webhook_secret`, as documented in the setup guide: [4](#0-3) 

Once `verify_signature` passes (using OrgA's secret because `repository.owner.login == "OrgA"`), the raw JSON body is dispatched unchanged to every registered handler: [5](#0-4) 

But handlers never look at `repository.owner.login` again — they resolve the target `Repository`/`Stack` purely from `repository.full_name`, which can point at any repository in the Shipit database, including ones belonging to OrgB: [6](#0-5) 

For example, the push handler enqueues a Github sync job against whatever stacks match that (attacker-chosen) repository name and branch: [7](#0-6) 

Pull-request handlers similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/create review stacks for that repository, again independent of which org's secret authenticated the request: [8](#0-7) [9](#0-8) 

**The broken binding, stated as an equality that the code fails to enforce:**
`organization whose webhook_secret authenticated the request` (derived from `repository.owner.login`) must equal `organization that owns the repository/stack the handler subsequently mutates` (derived from `repository.full_name`). The controller never checks that `repository.owner.login` is a prefix/owner of `repository.full_name`, so these two identities can diverge freely in a single forged payload.

### Impact Explanation
In a multi-organization Shipit deployment (the officially documented configuration), any party who legitimately controls one onboarded GitHub organization — and therefore its own GitHub App's `webhook_secret` — can sign an arbitrary payload with that secret while setting `repository.full_name` to a stack belonging to a different, unrelated organization hosted on the same instance. This allows cross-repository writes: enqueuing sync jobs, archiving/unarchiving/creating review stacks, or other handler-driven mutations against a repository outside the attacker's control, using credentials that were never meant to authorize action on that repository. This matches the "cross-repository writes" Critical impact category.

Additionally, `verify_webhook_signature` returns `true` outright when an organization's `webhook_secret` is unset (`return true unless webhook_secret`) — the setup docs mark the webhook secret as "optional" — so if any onboarded organization is configured without a secret, an attacker can trivially spoof `repository.owner.login` to that organization's name and send an entirely unsigned request that will still pass verification and mutate any other org's repository state.

### Likelihood Explanation
Exploitability requires the attacker to be an admin/controller of at least one GitHub organization already onboarded onto the shared Shipit instance (a realistic scenario for shared/multi-tenant Shipit deployments), or requires any single onboarded organization to have skipped the optional webhook secret. No access to `GITHUB_TOKEN`, session cookies, or the victim organization's secret is needed — only knowledge of the attacker's own organization's webhook secret (which the attacker set themselves during onboarding) or an organization with no secret configured.

### Recommendation
Cross-validate the field used for signature-key selection against the field the handlers act on: e.g., after selecting the `GitHubApp` by `repository.owner.login`, require that `repository.full_name` start with that same `owner/` prefix (or, better, derive the verifying organization directly from `repository.full_name` instead of a separate independently-controlled field) before dispatching to handlers. Reject the request if the two disagree.

### Proof of Concept
1. Onboard/attacker controls GitHub organization `attacker-org` on a multi-org Shipit instance, and knows `attacker-org`'s `webhook_secret` (self-configured during app installation).
2. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, payload)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), and the HMAC matches, so the request passes (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`; `lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`; `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and enqueues a `GithubSyncJob` against the victim's stack — a write triggered on a repository the attacker's organization's credentials never authorized.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
