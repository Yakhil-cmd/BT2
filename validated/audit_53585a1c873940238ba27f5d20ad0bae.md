Based on the code, this claim does not hold up:

1. **`resolve-or-create` is never reached via `collateral-remove-redeem`.** `collateral-remove-redeem` (mainnet/contracts/market/v0-4-market.clar:1211) calls the market-level `collateral-remove` (line 1228), which sets `account` to `contract-caller` (line 1111) — never a third party. That in turn calls `.v0-market-vault collateral-remove` (line 1156), whose vault-level implementation uses `resolve` (mainnet/contracts/market/v0-market-vault.clar:408), *not* `resolve-or-create`. `resolve-or-create` only exists at line 143 and is only invoked from `collateral-add` (line 376). It is unreachable from any collateral-removal path. [1](#0-0) [2](#0-1) [3](#0-2) 

2. **The account is always the caller, never a victim.** Even hypothetically, `collateral-remove` always operates on `contract-caller`'s own position (line 1111), so there is no path by which an attacker can write to a third-party principal's registry/position through this entrypoint. [4](#0-3) 

3. **The "u100 sentinel branch" is guarded and unreachable in practice.** `underlying-id` defaults to `u100` only when `ztoken-id` doesn't match any known zToken, but the very next line asserts `(<= underlying-id stSTXbtc)`, which aborts the transaction with `ERR-UNKNOWN-VAULT` before any state-changing call occurs. [5](#0-4) 

Since the entrypoint never reaches `resolve-or-create`, never writes to any principal other than the caller, and the described sentinel branch is blocked by an assertion, there is no shared state that an attacker A writes that a victim B's transaction later reads through this path. The required two-distinct-principal condition (attacker A vs. victim B) is not met.
