### Title
Webhook signature is verified against the payload's `repository.owner.login` organization while the mutated stack is resolved from the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the raw request body, then verifies the whole raw body against that org's secret. Downstream event handlers, however, resolve the target `Stack`/`Repository` to mutate using a *different* JSON field of the same signed payload: `repository.full_name`. Because both fields live inside the same signed body, an attacker who legitimately controls a GitHub organization/repo registered in Shipit (and therefore knows or can trigger a validly-signed payload for that org) can craft a payload where `repository.owner.login` still points at their own org (so the signature check passes with their own org's secret) while `repository.full_name` names a stack belonging to a completely different, victim organization/repository.

### Finding Description
The binding that should hold is: **organization authenticated (the org whose secret produced a valid HMAC) == organization of the repository actually written**. This binding is broken:

- Signature verification keys off `repository.owner.login`/`organization.login`: [1](#0-0) [2](#0-1) 

- Once signature verification passes (using whatever org's secret matched `repository_owner`), the raw payload is dispatched unchanged to handlers: [3](#0-2) 

- Handlers resolve the actual `Stack`(s) to act on from `repository.full_name`, a field that was never cross-checked against the field used for signature verification: [4](#0-3) 

- `Repository.from_github_repo_name` splits `owner/name` straight out of that string and does a DB lookup with no relation to which org's secret validated the request: [5](#0-4) 

Since Shipit supports multiple GitHub organizations each with independent `webhook_secret`s (per the `# Support multiple GitHub organisations` changelog entry), a payload's `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled strings in the same JSON body — nothing forces them to refer to the same repository. An attacker who administers Org A (and thus can generate a validly-signed webhook delivery from GitHub for Org A) can also directly POST a crafted, validly-signed-for-Org-A JSON body to `/webhooks` where `repository.full_name` is set to `"OrgB/victim-repo"`. The signature check passes (it only ever inspects `repository.owner.login` = "OrgA" to pick the secret, and HMACs the raw body which the attacker fully controls and signs correctly with the OrgA secret they know). The handler then looks up and mutates Org B's stacks.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary explicitly called out as in-scope. Concretely, with `PushHandler`, an attacker can force `Stack#sync_github(expected_head_sha: ...)` to run against a victim stack under a repository/org they do not own: [6](#0-5) 
and with `StatusHandler`, forge commit statuses on victim commits by sha (shas are often public, e.g. via GitHub API), directly influencing whether Shipit considers a victim commit deployable/mergeable: [7](#0-6) 
Manipulating `sync_github`/commit status/check-run state for a stack the attacker doesn't own can trigger unauthorized deploy scheduling (continuous delivery) or corrupt the deployability signal Shipit uses to gate merges/deploys for a repository the attacker has no legitimate access to — this maps to "unauthorized deploy" / cross-repository writes impact.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to legitimately control at least one GitHub organization/repository that is configured in this Shipit instance (so they know or can obtain a validly-signed payload/secret for that org), and requires the victim stack to exist in the same Shipit instance under a different organization. Multi-tenant Shipit deployments serving several organizations are the primary at-risk configuration, matching the "Support multiple GitHub organisations" feature explicitly implemented in this engine.

### Recommendation
Bind the field used to select the signing secret to the field used to resolve the target repository/stack: verify the signature using the secret for the owner parsed from `repository.full_name` (or, conversely, require `repository.owner.login` == the owner segment of `repository.full_name`) before dispatching to handlers, and reject the request if they diverge.

### Proof of Concept
1. Attacker controls `github-org-attacker` in Shipit with a known/derivable `webhook_secret` (e.g. because they configured it, or because GitHub will sign real deliveries for their own repo with it).
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<any_sha>",
  "repository": {
    "owner": { "login": "github-org-attacker" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(webhook_secret_of_attacker_org, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "github-org-attacker")`, computes HMAC with that org's secret, and it matches — request passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on the victim's stack(s), which the attacker has no authorization over.
