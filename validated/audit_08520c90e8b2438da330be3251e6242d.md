### Title
Arbiter contract hash omits the `ttl` (deadline) field, allowing counterparties to disagree on contract expiry - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.getHashSrc()`/`getHash()` compute the integrity hash of an arbiter contract from a fixed set of fields, but deliberately exclude `ttl` (the contract's time-to-live/expiry). This is the same bug class as the reported "weak signature validation": a critical, time/validity-defining parameter is left out of the value that both parties, and later the arbiter/arbstore, use to verify that the contract they are looking at is *the* agreed contract. Just like the option-mispricing report shows that `period`/`maturity`/`deadline` must all be bound into the signed hash to prevent stale or mismatched terms, here the arbiter contract's `ttl` is silently mutable without ever invalidating the hash check, so the two device-paired counterparties (and later the arbiter/arbstore that resolves a dispute over the escrow funds) can end up with a different effective expiration for the "same" hash-committed contract.

### Finding Description
The contract hash is computed as:

```js
function getHashSrc(contract) {
	...
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
``` [1](#0-0) 

`ttl` never appears in `getHashSrc`. This same hash is then used to gate the whole lifecycle of the contract in `wallet.js`:

* At offer time, the receiving device validates `body.hash !== arbiter_contract.getHash(body)` and separately requires `body.ttl > 0`, but the hash never binds the actual `ttl` value received on the wire: [2](#0-1) 

* Expiry enforcement (`objDateCopy.setHours(..., objContract.ttl * 60 * 60)`) later relies purely on the locally-stored, hash-unverified `ttl`: [3](#0-2) 

* Even in the on-chain-anchored dispute flow, where the contract hash is recomputed and matched against `payload.contract_text_hash` in the mutually-signed unit that funded the shared/escrow address, `ttl` is again excluded from `expectedContractHash`: [4](#0-3) [5](#0-4) 

Because `ttl` is not part of the value that is hashed, signed indirectly (via the mutual on-chain unit referencing `contract_text_hash`), and checked, a counterparty can present, store, or later assert a different `ttl` for a contract that hashes identically to what the other party (and the arbiter/arbstore) hold. There is no cryptographic binding forcing all participants to agree on when the contract-governed escrow arrangement actually expires.

### Impact Explanation
The arbiter contract flow culminates in funds being placed into a mutually-defined shared address (`shared_address`) that only the arbiter's/participants' signatures can move, exactly as in a standard escrow. Whether a contract is "still valid" (`ttl` not yet elapsed) directly affects what actions are considered legitimate by each party's wallet (e.g., refusing to act on an "already expired" contract) and by the arbstore/arbiter resolving a dispute over the escrowed funds. Since `ttl` is never cryptographically bound to the hash used to identify/verify the contract, the two counterparties (and the arbiter relying on `getHash`/`expectedContractHash` matching) can be tricked into operating under inconsistent expiry assumptions for what they believe is the same, integrity-checked contract — potentially causing incorrect dispute resolution and loss of escrowed funds, or a party being able to claim a contract has/hasn't expired contrary to what the other party agreed to. This matches the required impact bar of fund loss/freezing tied to the escrow (shared address).

### Likelihood Explanation
Any of the two paired-device counterparties negotiating an arbiter contract can reach this path unprivileged — it only requires normal use of `arbiter_contract_offer`/`arbiter_contract_shared`/`arbiter_dispute_request` device messages, which are handled directly in `wallet.js`. No special privileges, node compromise, or network attack are needed; a counterparty simply needs to send a contract object whose `ttl` differs from what was implied/agreed while keeping all hash-bound fields identical.

### Recommendation
Include `ttl` in `getHashSrc()` (and thus in `getHash()`) so any modification of the contract's expiry invalidates the integrity hash the same way tampering with `title`, `text`, `amount`, or `asset` does:

```diff
function getHashSrc(contract) {
	...
	const src = contract.creation_date > exports.NEW_HASH_DATE
-		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
+		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null', contract.ttl].join(exports.DELIMITER)
		 : ...
}
```
Also include `ttl` in the `expectedContractHash` computed inside the `arbiter_dispute_request` handler in `wallet.js` so that a dispute can never be raised/resolved against a contract whose expiry term wasn't cryptographically fixed at contract-creation time.

### Proof of Concept
1. Device A creates an arbiter contract offer with `title`, `text`, `amount`, `asset`, `arbiter_address`, and `ttl=1` (1 hour) and sends it to Device B via `arbiter_contract_offer` — `objContract.hash = getHash(objContract)` is computed without `ttl`.
2. Device B's handler in `wallet.js` (`case 'arbiter_contract_offer'`) validates `body.hash === arbiter_contract.getHash(body)`, which passes regardless of the `ttl` value carried in `body`.
3. Device A can subsequently present a modified copy of the same contract (e.g., in a later `arbiter_contract_shared`/`arbiter_dispute_request` message, or simply by keeping a different local `ttl` than what B stored) with `ttl` changed to a much larger or smaller value; `getHash`/`expectedContractHash` still match because `ttl` was never part of the hashed content.
4. When a dispute is later opened via `arbiter_dispute_request`, the `expectedContractHash` check (`wallet.js:767-781`) succeeds even though the `ttl` value now used to evaluate "already expired" logic (`wallet.js:550-552`) differs from what the counterparty originally agreed to, letting one party argue the escrow term was longer/shorter than actually committed, affecting the arbiter's fund-release decision on the shared escrow address.
