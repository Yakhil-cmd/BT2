### Title
Pool `repay`/`recapitalize` refund a declared "overpayment" that was never paid in, draining pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The Tor bug class — processing a response/settlement (`CC_RESPONSE`) when the corresponding request (`CC_REQUEST`) was never sent — maps directly onto the pool's refund paths. `ops::repay::apply` computes `overpayment` purely from the caller-declared `action.amount` versus the recorded debt, and `Cache::transfer_out` pays that "excess" back to the `payer` without verifying that the declared amount ever entered custody. `ops::recapitalize::apply` has the identical shape: excess over the shortfall is refunded out of custody with no inbound measurement and no `cash` debit or `require_reserves` check on the refund leg.

### Finding Description
In `contracts/pool/src/ops/repay.rs:25-34`, `apply` runs `accounting` and then unconditionally transfers `outcome.overpayment` to `payer`. `accounting` (lines 40-67) resolves the repay via `cache.resolve_repay(amount, position)`; in `common/src/rates/scaling.rs:171-192`, when `amount >= current_debt_ceil` the function returns the full position plus `amount - current_debt_ceil` as excess. The pool itself never pulls or measures the inbound tokens — the doc comment states "The controller transfers the repay amount into the pool before this call," so the pool trusts the caller-declared `amount` as if it were received.

The killer detail is the zero-debt case: when `pos_scaled` debt unscales to `current_debt_ceil == 0`, `resolve_repay` takes the full-close branch, `net_repay = 0`, and the `RepayRoundsToZeroShares` assert at `repay.rs:48-52` passes on its `net_repay == 0` disjunct. The entire declared `amount` becomes a refundable "overpayment" paid out of the pool's real token balance while the cash book is untouched.

The committed test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs:3589-3611` demonstrates exactly this: a fresh `payer` calls `pool.repay` directly with `amount = custody_before` on a market with zero debt and zero inbound transfer, and the helper asserts custody is drained to the payer. The companion comment at lines 3578-3588 states neither `repay`'s nor `recapitalize`'s refund debits `cash` or passes `require_reserves`. `test_unfunded_recapitalize_is_bounded_by_custody_not_by_the_declared_amount` (`flows.rs:3489-3512`) shows the `recapitalize` refund is bounded only by live custody, not by any measured receipt.

The asset-substitution escape is closed (`flows.rs:3525-3576`: market key asset always equals `params.asset_id`), so the refund is always in the market's real token — the drain is direct theft of supplier funds, not a swap into a worthless asset.

### Impact Explanation
Theft of user funds / protocol insolvency. An attacker calls the pool's `repay` (or `recapitalize`) entrypoint directly as `payer`, declares `amount` up to the pool's token balance on a market with little or no outstanding debt, and receives the "overpayment" refund without transferring anything in. Every token of supplier cash in that market can be extracted. Because the refund does not debit `cash`, the books still claim full backing — the pool is silently emptied, and subsequent withdrawals revert on real SAC transfer failure, permanently freezing remaining supplier funds.

### Likelihood Explanation
The exploit is a single unprivileged transaction: the pool test client invokes `repay(&payer, actions)` with only the payer's authorization and no controller involvement, and no code path in `repay::apply` authenticates a controller caller or measures an inbound transfer. Preconditions are trivial — any initialized market whose recorded debt ceiling is smaller than the pool's token balance (a zero-debt market makes the entire amount refundable). No oracle, timing, or multi-step setup is needed. The cost is only a signature; the gain is the pool's full custody. The only uncertainty is whether production deployment layers an external caller check on the pool that the unit tests bypass — nothing in the inspected pool code shows one.

### Recommendation
- Make settlement measured, not declared: record the pool's token balance before the leg, require `balance_after - balance_before == amount` (or pull `amount` via `transfer_from`), and compute the refund only from measured inbound funds.
- Alternatively, restrict `repay`/`recapitalize`/`seize`/`net_settle` to the controller address via `require_auth` against a stored controller, matching the assumption in the `repay.rs` doc comment.
- Remove the `net_repay == 0` disjunct bypass in `repay.rs:48-52` so a repay that burns zero shares against zero debt always reverts.
- Route refunds through `cash` accounting and `require_reserves` so custody and the book cannot diverge.

### Proof of Concept
The pattern is already pinned by the repo's own tests:

```rust
// contracts/pool/tests/flows.rs:3589-3611
let payer = Address::generate(&t.env);          // attacker, zero balance, zero debt
let custody_before = token.balance(&t.pool);    // e.g. all supplier cash
// no token transfer of any kind happens before this call
let credited = t.client()
    .repay(&payer, &t.ract(0, custody_before))  // declared amount = full custody
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                        // no debt retired
// assert_unfunded_refund_drained_custody: payer now holds custody_before,
// pool book still reports the same cash — insolvent and silent.
```

Live path: attacker calls `Pool::repay(payer, [PoolAction{ hub_asset, position_scaled: 0, amount: pool_balance }])` on a zero-debt market → `resolve_repay` returns `(0, pool_balance)` → `net_repay == 0` passes the zero-shares assert → `cache.transfer_out(payer, pool_balance)` pays the entire market custody to the attacker.
