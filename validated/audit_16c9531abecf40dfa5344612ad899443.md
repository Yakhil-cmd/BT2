### Title
`provision?` operator-precedence bug lets `prevent_with_label`/`allow_with_label` PRs create a `ReviewStack` even when `review_stacks_enabled` is `false`, triggering `sync_github` with app-level GitHub credentials - (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` mixes `&&`/`||` without parentheses so `review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches. If a repository is registered in Shipit with `review_stacks_enabled: false` but `provisioning_behavior: prevent_with_label` (or `allow_with_label`), any PR without (or with) the trigger label causes `ReviewStackAdapter#create!` to persist a `Shipit::ReviewStack`, which fires `after_commit :sync_github, on: :create` on `Stack`, dispatching `GithubSyncJob` that calls GitHub APIs via `Shipit.github(organization: repository.owner).api`.

### Finding Description
Binding claimed by the operator: "a stack is approved for automated GitHub API interaction" == "`repository.review_stacks_enabled == true`". The code that should enforce this equality is: [1](#0-0) 

Ruby's `&&` binds tighter than `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is only ANDed into the first disjunct. If a repository has `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, opening a PR without the provisioning label makes the third disjunct `true`, so `provision?` returns `true` regardless of `review_stacks_enabled`. The same applies to `allow_with_label` combined with a label the attacker controls on their own PR.

`OpenedHandler#process` then unconditionally calls: [2](#0-1) 

which invokes `ReviewStackAdapter#create!`, persisting a `Shipit::ReviewStack` (subclass of `Stack`): [3](#0-2) 

`Stack` registers `after_commit :sync_github, on: :create`: [4](#0-3) 

`sync_github` enqueues `GithubSyncJob`, which uses `stack.github_api` → `Shipit.github(organization: repository.owner).api` (app-level GitHub App/token credential) to fetch commits/CI status and later drive deploy/status API calls: [5](#0-4) [6](#0-5) 

Neither `ExplicitParameters` schema validation, `drop_unhandled_event`, nor any model validation on `Repository`/`Stack` checks `review_stacks_enabled` again before `sync_github` fires — the gating logic lives solely in the broken `provision?` predicate.

### Impact Explanation
The immediate effect is that the app's GitHub credentials (`Shipit.github(organization: repository.owner).api`) are used to call GitHub's API (fetch commits, later status/deployment writes via other job flows) for a repository/stack configuration an operator explicitly did not enable for review-stack automation (`review_stacks_enabled: false`). This is a stack record being created and acted upon for a repository whose review-stack automation was never authorized by the operator — matching "a payload... mutating another's stack" / unauthorized use of app credentials category. It is repeatable for every PR opened/reopened/labeled against any repository configured this way, and the precondition (repository already registered in Shipit with this specific `review_stacks_enabled=false` + `provisioning_behavior` combination) is entirely a server-side/operator configuration state, not something the attacker can create from scratch — this bounds it to repositories operators have onboarded to Shipit but only partially enabled.

### Likelihood Explanation
Requires a `Shipit::Repository` to exist with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (both non-default, explicit admin choices distinct from the "fully off" state, per the enum in `Repository`). Given that combination, any GitHub user able to open a PR (or apply a label they control, via `LabeledHandler`/`UnlabeledHandler`, which share the same `provision?` logic) against that repository triggers the bug with a single webhook-eligible action — no secrets, sessions, or elevated GitHub permissions needed beyond opening a PR on their own fork/branch.

### Recommendation
Fix operator precedence in `provision?` by explicitly gating all branches on `review_stacks_enabled`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same audit/fix to `LabeledHandler` and `UnlabeledHandler`, which reportedly contain the identical `provision?` pattern (per grep matches), before relying on it as an authorization gate.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, in-scope engine test dir):
1. Create a `Shipit::Repository` with `review_stacks_enabled: false`, `provisioning_behavior: 'prevent_with_label'`.
2. Assert precondition equality: `repository.review_stacks_enabled` is `false` (the binding side that should block automation).
3. Build an `opened` PR webhook payload with no labels (attacker-controlled, no provisioning label present).
4. Stub/expect `Shipit::ReviewStackProvisioningQueue.add` and assert a `Shipit::ReviewStack` row is created for the repository despite `review_stacks_enabled == false`.
5. Assert `Stack#sync_github` (via `after_commit :sync_github, on: :create`) enqueues `GithubSyncJob` for the newly created stack — e.g. `assert_enqueued_with(job: Shipit::GithubSyncJob, args: [{ stack_id: stack.id, expected_head_sha: nil }])`.
6. Compare against a control case where `review_stacks_enabled: true` with the same `provisioning_behavior`/label state to show identical `sync_github` behavior occurs in both the "authorized" and "precedence-bug" paths — proving the two sides of the claimed binding do not match (unauthorized stack triggers the same GitHub-credentialed job as an authorized one).
