### Title
EIP-3541 Guard Misplaced After `SetCode` — 0xEF-Prefixed Bytecode Permanently Stored Despite Failed Transaction (`IsKore && !IsPrague`) - (File: `blockchain/vm/evm.go`)

---

### Summary

In `evm.create`, the EIP-3541 check that rejects 0xEF-prefixed runtime code under the `IsKore && !IsPrague` window is placed **after** both `SetCode` and the snapshot-revert block. An attacker can deploy initcode that returns 0xEF-prefixed runtime code; the code is committed to state, the revert window passes with `err == nil`, and only then is `ErrInvalidCode` set. The transaction receipt shows failure, but the code slot at the contract address is permanently non-empty.

---

### Finding Description

The execution order in `evm.create` is:

| Step | Line | Action |
|------|------|--------|
| 1 | 584 | `ret, err = evm.interpreter.Run(...)` — initcode returns `0xEF…` bytes; `err = nil` |
| 2 | 593–595 | 0xEF check **only if `IsPrague`** — skipped in Kaia Cancun window |
| 3 | 601–616 | `err == nil` → `SetCode(address, ret)` called — **0xEF code written to state** |
| 4 | 620–625 | `err == nil` → **revert block does not execute** |
| 5 | 631–633 | `ErrInvalidCode` set — **too late; code already committed** | [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The developers themselves document the defect:

> *"This validation was incorrectly placed after the code was already stored in state DB, which should have been prevented. This is kept for backwards compatibility and will be properly handled after Prague hardfork."* [5](#0-4) 

---

### Impact Explanation

- A **failed transaction** (receipt status = failure, `ErrInvalidCode` returned) permanently writes code to the state trie. This is an **invalid state transition**: the canonical EVM invariant is that a failed contract-creation leaves no code at the target address.
- The deployed 0xEF-prefixed bytecode bypasses EIP-3541 enforcement for the entire Kaia Cancun (`IsKore && !IsPrague`) window.
- Any future logic that gates on `codeSize > 0` or `codeHash != emptyHash` at that address will treat it as a live contract, enabling unexpected call dispatch into attacker-controlled 0xEF-prefixed code.
- The nonce at the contract address is set to 1 (line 571) and the account is created (line 570) before the snapshot; the snapshot revert at line 621 would have undone all of this — but it never fires. [6](#0-5) 

---

### Likelihood Explanation

Exploitability is **high**: any EOA or contract can submit a `CREATE`/`CREATE2` transaction whose initcode returns a single `0xEF` byte followed by arbitrary data. No privileged access, governance key, or validator collusion is required. The only precondition is that the chain is past `IsKore` and before `IsPrague`.

---

### Recommendation

Move the 0xEF check to the same location as the `IsPrague` guard (lines 592–595), so it fires **before** `SetCode` is called and while `err` is still nil:

```go
// Reject code starting with 0xEF (EIP-3541) for all post-Kore forks.
if err == nil && len(ret) >= 1 && ret[0] == 0xEF && evm.chainRules.IsKore {
    err = ErrInvalidCode
}
```

This makes the revert block at lines 620–625 fire correctly, undoing `CreateSmartContractAccountWithKey`, `SetNonce`, `Transfer`, and any storage changes before the code is ever written.

---

### Proof of Concept

1. On a Kaia Cancun fork (`IsKore = true`, `IsPrague = false`), submit a `CREATE` transaction whose initcode is:

   ```
   PUSH1 0x01   // size = 1
   PUSH1 0xEF   // value = 0xEF
   PUSH1 0x00   // mem offset
   MSTORE8
   PUSH1 0x01   // return length
   PUSH1 0x00   // return offset
   RETURN
   ```

2. The transaction receipt will show **status = 0 (failure)** with `ErrInvalidCode`.
3. Query `eth_getCode` at the deterministic `CREATE` address — the result is `0xEF`, not `0x`.
4. The code slot is permanently non-empty in state despite the failed transaction.
