### Title
Webhook signature verification is silently bypassed when an organization's `webhook_secret` is unset, allowing unauthenticated forgery of GitHub events - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever no `webhook_secret` is configured for the GitHub organization the payload claims to belong to. Because the org used to select the verifier is itself derived from the unauthenticated JSON body, an attacker can pick any Shipit-configured organization/repository that has no `webhook_secret` set and POST an arbitrary, completely unsigned payload to `/webhooks`, which Shipit will process as a genuine GitHub event.

### Finding Description
`WebhooksController#verify_signature` looks up the GitHub App configuration keyed by the organization named in the (still-unverified) request body, then asks that app object to verify the signature: [1](#0-0) 

The actual verification is done here: [2](#0-1) 

`verify_webhook_signature` starts with `return true unless webhook_secret` — if the org's `webhook_secret` config key is blank, **every** signature is treated as valid, regardless of the `X-Hub-Signature` header content or absence. The webhook secret is explicitly documented as optional when creating the GitHub App, and the shipped multi-org example configuration ships with `webhook_secret: # nil`: [3](#0-2) [4](#0-3) 

This breaks the equality that should hold: `organization whose secret authenticates the request == organization whose data is trusted and acted upon`. When the secret is unset, the left side of that equality is vacuous (anyone can "authenticate" as that org), yet the right side (the payload's `repository`/`organization`/`sender`/`membership` fields) is fully trusted by every handler in `Shipit::Webhooks::Handlers::*`, including the `membership` handler that creates `Team`/`Membership` records on the fly, as shown by the test suite: [5](#0-4) 

Because `Shipit.oauth_teams`/`Shipit.github_teams` authorization is driven by `Membership` records, an attacker can forge a `membership` "added" event naming an authorized team and their own GitHub login, all without ever knowing any secret, as long as the targeted organization in Shipit's multi-org config has no `webhook_secret` configured.

### Impact Explanation
This is a full authentication bypass for the `/webhooks` endpoint for any organization lacking a configured secret: an unprivileged, unauthenticated internet attacker can inject arbitrary `push`, `status`, `check_suite`, `pull_request`, and `membership` events. Concretely this allows:
- Forging `membership` events to insert `Membership` rows binding the attacker's GitHub login to a team listed in `Shipit.github_teams`, escalating into the OAuth team-based authorization used to grant Shipit access (High impact category: "escalation into `Shipit.github_teams` authorization").
- Forging `push`/`status` events to manipulate commit/status state that feeds into merge-queue and deploy-eligibility decisions, and to enqueue `GithubSyncJob`, influencing which commits are eligible to deploy (contributing toward "an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood is high wherever `webhook_secret` is left blank, which the project's own setup docs and shipped example config present as a normal, supported option ("Webhook secret (optional)"). No credentials, session, or API token are required — the attacker only needs to know (or guess) that Shipit is configured for an organization without a secret and POST directly to the public `/webhooks` route.

### Recommendation
Require `webhook_secret` to be present for every configured GitHub organization and fail closed (reject/`422`) when it is missing, instead of `return true unless webhook_secret`. If an "unsigned" mode must be supported for local development, gate it behind an explicit, non-production-only flag rather than the mere absence of a secret.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`, one (`orgA`) with a `webhook_secret` set and one (`orgB`) with `webhook_secret` left blank (as shown supported in `docs/setup.md` and `config/secrets.development.shopify.yml`).
2. As an anonymous attacker, POST to `/webhooks` with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "orgB"},
  "member": {"login": "attacker-controlled-login"}
}
```
No `X-Hub-Signature` header (or any bogus value) is required.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgB")`, calls `verify_webhook_signature`, which returns `true` immediately because `orgB`'s `webhook_secret` is blank.
4. The `membership` handler processes the forged payload and creates a `Membership` linking `attacker-controlled-login` to team `developers`, exactly as exercised in `test/controllers/webhooks_controller_test.rb` lines 129-165, granting the attacker team-based authorization without ever authenticating with GitHub.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
