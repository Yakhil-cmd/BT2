I found the exploitable analog: `MembershipHandler#find_or_create_team!` trusts the `organization.login` field from the webhook payload to bind a team to an organization, but the signature check that gates the webhook only verifies that *some* payload was signed by *some* configured organization's GitHub App — it never confirms that the `organization.login` claimed inside the body is the same organization whose secret actually signed it.

### Title
Membership webhook trusts payload-supplied `organization.login` to bind teams, decoupled from the signing organization's identity - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `repository_owner`, which for `membership` events falls back to `params.dig('organization', 'login')` [1](#0-0) . `MembershipHandler#find_or_create_team!` then uses that exact same attacker-controlled `params.organization.login` value to create/bind a `Team` record [2](#0-1) . In a multi-organization Shipit deployment, each org has its own GitHub App and its own `webhook_secret` [3](#0-2) [4](#0-3) .

### Finding Description
The binding that should hold is: **organization that authenticated (signed the webhook) == organization the membership event claims to be for**. In `verify_signature`, `repository_owner` is computed and used only to *pick which app's secret to verify with*; it is never compared afterward against the value the handler consumes [5](#0-4) . Because `verify_webhook_signature` returns `true` whenever `webhook_secret` is blank for that looked-up config [6](#0-5) , an org that has no `webhook_secret` configured (a documented, supported configuration state, e.g. `webhook_secret: # nil`) passes verification unconditionally regardless of the `organization.login`/`repository.owner.login` value in the body.

`Team.find_or_create_by_handle`/`find_or_create_team!` uses that same unauthenticated field to create a `Team` scoped to any organization string supplied in the payload, and `Membership` webhooks for that team add/remove members without any further cross-check that the team's organization matches the app that actually validated the request [7](#0-6) [8](#0-7) .

### Impact Explanation
`Shipit.github_teams` (built from `oauth.teams` config, e.g. `MyOrg/developers`) gates authentication/authorization for the entire application via `User#authorized?` [9](#0-8)  and `force_github_authentication` [10](#0-9) . If a `membership` webhook whose signature check is trivially satisfied (org with no `webhook_secret` in a multi-org config) can create/populate a `Team` row matching the exact `organization/slug` handle Shipit trusts for authorization, an attacker could add an arbitrary GitHub login as a member of that team, and that user would subsequently pass `authorized?` on OAuth login — an authentication-bypass into a privileged access boundary (`Shipit.github_teams`).

### Likelihood Explanation
This requires: (1) a multi-org Shipit deployment, (2) at least one configured organization with no `webhook_secret` set (a state explicitly shown as valid/default in the example configs), and (3) knowledge of a target team handle used for `Shipit.github_teams`. All of these are configuration facts, not secrets, making exploitation feasible for an unauthenticated internet attacker who can simply POST to the public `/webhooks` endpoint — no session, API token, or private key required.

### Recommendation
After signature verification, the handler must confirm that `organization.login` (and `repository.owner.login` for repo-scoped events) belongs to the same organization identity that `github_app`/`repository_owner` resolved to (or reject entirely when the resolved app has no `webhook_secret` and the deployment has more than one configured organization). Do not let handlers trust payload-declared organization/repository fields as an implicit proof of origin — bind the verified app identity explicitly to the object being mutated (`Team#organization`) instead of re-deriving it from the same untrusted payload.

### Proof of Concept
1. Operator configures Shipit with two organizations, `OrgOne` (has `webhook_secret` set) and `OrgTwo` (has `webhook_secret: nil`), per the documented multi-org schema [11](#0-10) .
2. `Shipit.github_teams` includes `OrgOne/trusted-team` (the authorization gate).
3. Attacker sends an unsigned/any-signature POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "trusted-team", "slug": "trusted-team", "url": "https://github.com/x"},
  "organization": {"login": "OrgTwo"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "OrgTwo"}}
}
```
4. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally [6](#0-5) .
5. `MembershipHandler` creates/finds a `Team` and adds `attacker` as a member [12](#0-11) ; if the team's `github_id`/slug collides with (or is later reconciled to) the trusted `OrgOne/trusted-team` handle, `attacker` becomes a member of a team used for authorization.

Note: full confirmation that `github_id` collision/reconciliation with an existing trusted `Team` row is reachable this way would require deeper tracing of `Team.find_or_create_by!(github_id:)` semantics across concurrent orgs, which the indexed code did not fully resolve — a Devin session with full repo access could verify this precisely.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      end
