### Title
Cross-organization `Team` confusion in `MembershipHandler#process` allows a signed webhook from an attacker's own org to delete `Membership` rows on a victim org's `Team` — (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id: params.team.id`, ignoring the organization that the request actually authenticated as. Because GitHub team IDs are attacker-observable/guessable and `verify_signature` only proves the request came from *some* organization the attacker controls (not the organization that owns the `Team` being mutated), an attacker who owns any GitHub org with Shipit's app installed can send a genuinely-signed `membership`/`removed` event naming a victim org's `Team.github_id` and a victim member's login, causing `team.members.delete(member)` to run against the victim's `Team`.

### Finding Description
The binding the code needs to hold is:
`authenticating_organization (params.organization.login, verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` **==** `team.organization (the org owning the Team record mutated by team.members.delete(member))`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . Membership payloads carry no `repository` key, so `repository_owner` resolves to `params['organization']['login']` — the attacker's own org, which they legitimately control and can sign for.
2. `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The block (which sets `organization` from the *authenticated* org) only runs when a **new** row is created. If a `Team` with that `github_id` already exists — e.g. the victim org's privileged team — it is returned unchanged, regardless of which org signed the request.
3. `process` then runs `team.members.delete(member)` on that pre-existing (victim) `Team` for `action == 'removed'` [4](#0-3) , deleting the `Membership` row joining the named user to the victim's team.
4. `User#authorized?` derives its truth from `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) , so removing the `Membership` row directly revokes that authorization signal for the victim user, without the victim org's webhook secret ever being involved.

**Attacker request:** `POST /webhooks` with header `X-Github-Event: membership`, signed with the attacker's own org's `webhook_secret`, body:
```json
{
  "action": "removed",
  "team": { "id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "https://example.com" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "victim-privileged-user" }
}
```
`verify_signature` passes because it only checks that `attacker-org`'s secret matches — it never checks that `attacker-org` is the org that actually owns `Team#github_id == victim_team_github_id`. Nothing in `Team`, `find_or_create_team!`, or `verify_signature` cross-checks `team.organization` against the authenticated organization before performing the mutation.

Existing guards checked and found insufficient: `verify_signature` (authenticates the request as belonging to *an* org, not as belonging to the org that owns the target `Team`), the `ExplicitParameters` schema (only validates shape/types, not org ownership), and `Team` model (unique index is on `[organization, slug]`, not `github_id`, so `github_id` alone is not scoped to a single org in a way the handler respects).

### Impact Explanation
A successful request deletes a `Membership` row for a legitimate, privileged user on a `Team` listed in `Shipit.github_teams`, directly flipping `User#authorized?` from true to false for that user without any interaction with the victim org's actual GitHub webhook secret. This is a cross-tenant authorization-state write: an attacker who authenticates only as their own (unrelated) organization can revoke another organization's `github_teams`-based authorization state for an arbitrary named user. This is repeatable at will (each request removes the membership again, and repeated `added`-side confusion could equally be used to falsely add a membership, escalating the impact to authorization granting rather than only revocation). This matches "High - escalation into `Shipit.github_teams` authorization" categorically, since here it is denial (revocation) rather than escalation into privilege, but it is a concrete cross-tenant write on the victim org's access-control model driven purely by data the attacker fully controls (`team.id`, `member.login`) under a signature that only proves attacker-org control.

### Likelihood Explanation
Preconditions: multi-org Shipit deployment where the attacker has (or creates) their own GitHub organization with the Shipit GitHub App/webhook installed (freely available to any GitHub user), and the victim's `Team` row (with a known/guessable `github_id`, e.g. sequential/public via GitHub API) already exists in Shipit's DB (created by a prior legitimate `added` membership event, which is the normal steady state for any org using `Shipit.github_teams`). No Shipit secrets, sessions, or API tokens are needed — only the attacker's own legitimately-issued webhook signature. GitHub team IDs are visible via the public/authenticated GitHub API for teams the attacker can query, and `Shipit::Team` records are also enumerable through app UI/API surfaces in some deployments, making the `github_id` value obtainable without needing insider access. This is a low-cost, single-HTTP-request, repeatable attack.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and the authenticated `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` matches `repository_owner`/the org that `verify_signature` authenticated before performing any mutation. Reject (or no-op) the event if an existing `Team` with that `github_id` belongs to a different `organization` than the authenticated one.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership 'removed' event signed by an unrelated org cannot delete membership on another org's Team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  victim_user = shipit_users(:walrus)
  victim_team.add_member(victim_user)

  attacker_org_login = 'attacker-org' # distinct org, its own webhook secret verifies signature

  assert_no_difference -> { Membership.where(team: victim_team, user: victim_user).count } do
    Shipit::Webhooks::Handlers::MembershipHandler.new.call(
      'action' => 'removed',
      'team' => { 'id' => victim_team.github_id, 'name' => 'x', 'slug' => 'x', 'url' => 'https://example.com' },
      'organization' => { 'login' => attacker_org_login },
      'member' => { 'login' => victim_user.login }
    )
  end
end
```
Binding checked before/after: `params.organization.login` (`attacker-org`, the authenticated org) vs `team.organization` for the `Team` found by `github_id` (`shopify`, the victim org) — these differ both before and after the call, yet `Membership.count` for the victim's team decreases, demonstrating the broken binding. Currently, running this against the unmodified `find_or_create_team!` shows the deletion succeeding (test would need to assert the *no-difference* expectation fails today, confirming the vulnerability, and pass once the recommended organization-scoped lookup is added).
