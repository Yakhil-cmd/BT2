### Title
Attacker-controlled swap routes can inject unauthorized token transfers into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept opaque route bytes and execute them through the configured swap router under the caller’s authorization. Because route-selected venue code is not constrained to only the expected token transfer, a malicious route can add unrelated `transfer` calls from the caller to the signed authorization tree. If the caller signs the simulated tree, the malicious venue can steal unrelated wallet tokens while the controller’s balance checks still pass.

### Finding Description
The controller exposes attacker-influenced `Bytes` route arguments on its public strategy entrypoints, including `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `multiply`. [1](#0-0) 

Each strategy authenticates only the caller and then forwards the supplied route into the shared swap helper without decoding or constraining the route’s external call targets. [2](#0-1) [3](#0-2) [4](#0-3) 

`swap_tokens` reads the configured router, snapshots only the controller’s input and output balances, authorizes one exact controller-to-router transfer, and invokes `execute_strategy` with the caller-provided route. [5](#0-4) 

The granted invoker-contract authorization is deliberately limited to that one token transfer and has no sub-invocations, but it protects only the controller’s contract identity rather than calls that route-selected code requests from the original caller. [6](#0-5) 

After the router returns, the controller verifies only that its own input did not increase or exceed `amount_in` and that its output balance increased, leaving unrelated caller-wallet transfers outside those accounting checks. [7](#0-6) [8](#0-7) 

The documented authorization model confirms that a route-selected third-party contract can place a caller-token transfer beneath the caller’s authorization entry, and that the transfer executes if the caller signs the resulting tree. [9](#0-8) 

### Impact Explanation
A malicious route can steal arbitrary unrelated tokens held by the caller, not merely the collateral or debt amount being routed. The transaction can still deliver sufficient swap output for the account’s risk checks and controller balance checks to succeed, so the caller may receive a valid position update while another token balance is transferred to the attacker. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue contract and supply or publish a route that references it; no protocol privilege, leaked key, compromised router, or invalid market configuration is required. The theft requires the victim to submit a strategy using that route and sign the authorization tree containing the extra token transfer, which can occur when a wallet or interface trusts a route provider and does not inspect every simulated child invocation. [12](#0-11) [9](#0-8) 

### Recommendation
Restrict executable routes to governance-approved venues and pool contracts, rather than allowing route bytes to select arbitrary contract addresses. The router should validate every pool, token, and route target against the allowlist before execution, and callers or integrating clients should reject any authorization tree containing calls other than the expected strategy input transfer. Controller-side minimum-output and balance checks should not be treated as bounds on unrelated caller-authorization effects. [13](#0-12) [9](#0-8) 

### Proof of Concept
1. The attacker deploys a contract exposing the venue call interface expected by the route and configures it to invoke `token.transfer(victim, attacker, victim_balance)` for an unrelated token held by the victim.
2. The attacker constructs a `swap` byte payload that routes a valid swap through that contract while still producing enough legitimate output token to satisfy the controller’s positive-output check.
3. The victim submits `swap_collateral(caller=victim, account_id=victim_account, current=USDC_market, amount=routed_amount, new=ETH_market, swap=malicious_route)`; the same pattern applies to `multiply`, `swap_debt`, or `repay_debt_with_collateral`. [14](#0-13) 
4. The controller authenticates the victim, passes `malicious_route` to the router, and measures only the controller’s input and output balances. [2](#0-1) [5](#0-4) 
5. During route execution, the malicious contract requests the unrelated token transfer from the victim; transaction simulation records that transfer as a child invocation beneath the victim’s `swap_collateral` authorization. [15](#0-14) 
6. If the victim signs the expanded tree, the unrelated wallet tokens move to the attacker while the router returns enough `ETH` for `verify_router_output` and the final strategy checks to succeed. [10](#0-9) [8](#0-7)
