### Title
Cross-User Stale-Index Cache Poisoning via `index-cache-` in `accrue-and-cache` — ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` maintains a single shared cache, `index-cache-`, keyed only by `{ timestamp: stacks-block-time, aid: aid }`, used by every user's transaction that touches a given vault asset in the same block. The first caller to hit a given `aid` in a block calls `vault-accrue` and *primes* the cache; every later caller in the same block — regardless of who they are or what operation they perform — gets a cache **hit** and reuses that primed value without re-deriving it from the vault. This is structurally the same class of bug as the HTTP smuggling report: two different consumers (the priming transaction and the later transaction) are made to agree on a single cached artifact, but nothing guarantees the artifact still reflects the vault's true state by the time the second consumer reads it if state-changing vault operations occur between the two reads in the same block. [1](#0-0) 

### Finding Description
`accrue-and-cache` is the sole gateway market.clar uses to get liquidity/borrow indexes for health checks, notional valuation, and zToken pricing:

```clarity
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)          ;; cache HIT: no vault call
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [1](#0-0) 

This function is invoked from `accrue-user-debts`/`accrue-user-collateral` for *any* user's position that references the asset, and from the collateral-add capacity check that primes the cache for a newly-added zToken asset before evaluating collateral capacity. [2](#0-1) 

The cache key intentionally omits any notion of "who wrote it" or "what vault state it was derived from" beyond `timestamp` — it assumes that within one block, the vault's index is invariant regardless of intervening operations, so any second reader can safely reuse the first reader's value. That assumption fails whenever a vault operation immediately, non-time-gated, alters the index/lindex used for zToken pricing or debt valuation (e.g. `socialize-debt`, which writes off bad debt from a liquidated position and adjusts vault accounting directly rather than through the elapsed-time interest formula) between the transaction that primed the cache and the transaction that consumes it. Because the second, unrelated user's transaction takes a `cache HIT` and never calls `vault-accrue` again, it evaluates its own collateral/debt against a snapshot that another user's actions already made incorrect within the very same block — the market-vault side effect never happens to refresh the shared map entry until the next distinct block timestamp.

This is the same defect shape as the CVE: one component (the cache-priming transaction) commits a normalized value; a second, independent component (a later, unrelated transaction/consumer in the same block) trusts that cached value as-if freshly derived, and the two views of "the current index" diverge without either side detecting it.

### Impact Explanation
If a subsequent, unrelated user's collateral valuation, capacity check, or liquidation health computation is silently backed by a stale/pre-loss index primed earlier in the block by someone else's transaction, that user's position can be evaluated as healthier (or a proposed capacity increase validated as safe) than it truly is once the intervening state-changing event (bad-debt socialization on the same asset) is accounted for. This is not the caller harming themselves — it's a case where victim B's health/borrow-capacity evaluation is determined by unrelated party A's prior transaction and an intervening state mutation neither party controls together, i.e., "a shared index or cache primed by one caller and consumed by another." The result is that debt can be under-collateralized/over-borrowed against stale pricing, ultimately socializing losses to suppliers of the affected vault — a temporary/permanent freezing or shortfall risk to depositors' funds, falling under the in-scope High impact class (temporary freezing of funds / theft of unclaimed yield borne by suppliers).

### Likelihood Explanation
Requires two transactions touching the same `aid` within the same block, where the first primes the cache and an operation such as `socialize-debt` executes on that vault between priming and a later unrelated consumer's read (e.g., liquidation followed immediately by a legitimate borrow/collateral-add in the same block). Given Stacks' block-based execution, sequencing multiple transactions from different accounts into one block is achievable by an attacker via fee-based ordering or self-submission of a follow-up transaction immediately after observing a liquidation event, making this moderately likely to construct, though it requires a state-changing event that alters the index outside the normal time-accrual path within the same block.

### Recommendation
Do not key `index-cache-` purely by `{timestamp, aid}` across all callers. Either (a) invalidate/refresh the cache entry whenever any state-mutating vault operation (deposits, borrows, repays, redeems, socialize-debt) executes on that `aid` within the block, or (b) remove the shared, cross-transaction caching altogether and scope caching to be intra-transaction only (e.g., using a transaction-local variable rather than a persisted map keyed only by block timestamp), so that every transaction's health/pricing computations always call `vault-accrue` fresh rather than trusting another party's earlier snapshot.

### Proof of Concept
1. Block N, Tx1 (Liquidator): Liquidates an unhealthy STX-borrower position, triggering `vault-socialize-debt` on the STX vault, which writes off bad debt and (per protocol accounting) reduces the effective liquidity backing for STX-vault shares/zSTX price — but this call path does not go through `accrue-and-cache`, so the market's `index-cache-` entry for `{timestamp, STX}` (if already primed earlier in the block by any prior call) is not invalidated.
2. Block N, Tx0 (any earlier caller, e.g., a routine borrow) already primed `index-cache-` for `{timestamp, STX}` with the pre-loss index/lindex via `accrue-and-cache`.
3. Block N, Tx2 (Victim/attacker borrower): Calls `collateral-add` with zSTX collateral or performs a health check; `accrue-and-cache` returns a cache HIT with the stale pre-loss lindex from Tx0, letting Tx2's zSTX collateral be valued higher than the vault's true post-write-off backing, permitting borrowing/capacity beyond what the updated vault state would allow.
