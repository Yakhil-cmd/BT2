### Title
Webhook signature verification authenticates the organization named in an unverified payload field while write actions target a different repository named in a sibling payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the request against using `repository_owner`, a value pulled straight out of the still-unauthenticated JSON body. Separately, every webhook handler resolves the repository/stack it will act on using `repository.full_name`, a *different* field from that same unauthenticated body. Nothing ties these two fields together, so the signature check authenticates one organization while the mutation is applied to whatever repository the attacker names in the other field.

### Finding Description
`verify_signature` computes the org used for the HMAC check like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — both are attacker-supplied JSON fields that have not yet been authenticated at this point. `Shipit.github(organization: repository_owner)` then looks up that organization's own `webhook_secret` via `github_app_config`: [3](#0-2) 

Once `verify_webhook_signature` succeeds (which it trivially does if the attacker controls, or knows, the secret for the organization they named), `create` dispatches the same raw params to every registered handler: [4](#0-3) 

Handlers resolve their target stack/repository from a *different* field of the same payload: [5](#0-4) [6](#0-5) 

`repository_name` (`repository.full_name`) is never cross-checked against `repository_owner`, which was the value actually authenticated by the signature check. Consequently, a request whose `repository.owner.login` matches organization A (whose secret the attacker knows) but whose `repository.full_name` names `victim-org/victim-repo` will pass `verify_signature` — because the HMAC was computed and checked against org A's secret — and then be dispatched to handlers that operate on `victim-org/victim-repo`'s real `Stack`/`Repository`/`Commit` records.

This is the exact bug class from the report: the method authenticates against one identity (`msg.sender`==owner in the contract; organization-from-payload here) while its guarded action targets a different, attacker-influenced identity (seller/buyer in the contract; the repository-from-payload here). The check that is supposed to bind "who is allowed to act" to "what is acted upon" is broken because the two are read from independent, equally-unauthenticated fields.

The binding that should hold and is broken:
`verify_signature`'s authenticated organization (`repository_owner`) == the organization component of the repository the dispatched handlers write to (`repository.full_name`'s owner segment).

### Impact Explanation
For the `status` webhook event, the handler creates a `Shipit::Status` for a real commit directly from the (forged-org, but content-controlled) payload fields, as shown by the existing test that asserts the created status mirrors `state`, `description`, `target_url`, and `context` verbatim from the payload: [7](#0-6) 

Shipit stacks gate deploys on aggregated commit statuses. An attacker who is an administrator of any one organization onboarded to a multi-org Shipit instance (and therefore knows or controls that organization's own `webhook_secret`) can forge a `status` (or `check_suite`/`push`) event whose `repository.owner.login` is their own org but whose `repository.full_name` names a victim organization's repository/stack, injecting a fabricated "success" status (or triggering `GithubSyncJob`/`RefreshCheckRunsJob`) against that victim stack. This can make an unreviewed or failing commit appear deployable, enabling an unauthorized deploy/rollback decision on a repository the attacker does not control — a cross-repository write achieved without ever holding a Shipit session, `ApiClient` token, or the victim organization's own webhook secret.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate administrator (or a compromised low-privilege member with access to the GitHub App's own webhook secret) of *any* organization already onboarded to a multi-organization Shipit deployment — this is exactly the "organization that authenticated versus the repository that is written" trust boundary the task explicitly calls out as in-scope, and it needs no repository write access, GitHub App private key, or session on the victim's side. The single missing check (comparing `repository_owner` to the owner segment of `repository.full_name` before dispatch) makes this a low-effort, high-value cross-tenant forgery in any multi-org Shipit installation.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after it, before dispatch in `create`), enforce that the organization used to select the signing secret equals the owner segment of `repository.full_name` (and of any `organization.login` present) before invoking handlers. Reject the request (422) on mismatch, so a signature valid for organization A can never authorize writes against organization B's repositories/stacks.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing multiple organizations, e.g. `org-attacker` (attacker is an admin, knows its `webhook_secret`) and `org-victim` (has an existing `Stack` for `org-victim/victim-repo`), per the multi-org schema in `Shipit.github_app_config`.
2. Attacker crafts a `status` (or `push`/`check_suite`) webhook body:
   ```json
   {
     "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "target_url": "https://ci.example.com/fake"
   }
   ```
3. Attacker signs the raw body with `org-attacker`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, POSTing to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches `org-attacker`'s secret via `Shipit.github(organization: "org-attacker")`, and the HMAC check passes because the attacker signed with the correct (their own) secret — see `app/controllers/shipit/webhooks_controller.rb:24-49`.
5. `create` dispatches to `Shipit::Webhooks.for_event('status')`, whose handler resolves the target via `repository.full_name` = `"org-victim/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and creates a forged passing `Status` on the victim's real commit, with no verification tying the two organizations together.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
