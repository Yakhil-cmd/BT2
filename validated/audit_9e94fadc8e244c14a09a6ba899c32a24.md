Found a strong analog to the OmoAgent bug class: the asset attestor-list update mechanism.

### Title
Asset definer's `asset_attestors` update can freeze previously-received `spender_attested` asset outputs held by addresses dropped from the new attestor list - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, the asset definer can at any time post an `asset_attestors` message that replaces the entire trusted-attestor list. Just as `OmoAgent.setPositionManager()` lets a manager swap a critical reference address with no check on outstanding positions tied to the old value, `validateAttestorListUpdate()` lets the asset definer swap the attestor list with no check on outstanding asset outputs already held by addresses that were attested under the old list. Any holder whose attestation was issued by an attestor removed from the new list becomes permanently unable to spend the asset outputs they already hold.

### Finding Description
`asset_attestors` messages are validated by `validateAttestorListUpdate()`, which only checks that the sender is the asset definer and that the new list is well-formed - it performs no check on funds/outputs currently held by addresses attested under the *old* list: [1](#0-0) 

When spending a `spender_attested` asset, `storage.filterAttestedAddresses()` is always evaluated against the **current** (latest) attestor list for the asset, not the list in effect when the coins were received: [2](#0-1) [3](#0-2) 

The payment-output validation path enforces that every output address of a transfer/issue must be attested under this current list, and the payment-input validation path enforces the same for the address that already owns an output being spent: [4](#0-3) [5](#0-4) 

Sequence of events that reproduces the loss:
1. Definer issues a `spender_attested` asset with attestor set `{A}`.
2. Attestor `A` attests address `X`. `X` legitimately receives asset outputs (satisfies `attested`/output-attestation checks at receipt time).
3. Definer later posts `asset_attestors` naming a new set `{B}` (no attestation of `X` from `B` exists).
4. `X` still holds the previously received, unspent asset outputs, but any future spend from `X` fails at `validatePaymentInputsAndOutputs` (`"owner address is not attested"`) because `filterAttestedAddresses` is evaluated against the *new* current attestor list, not the list active when the coins were credited to `X`.

The result mirrors the report exactly: a privileged party (the asset definer, analogous to the "manager" in OmoAgent) changes a critical reference (attestor list, analogous to `positionManager`) and the protocol keeps no linkage between an already-held balance and the attestor list that was valid at the time it was acquired, orphaning the holder's funds.

### Impact Explanation
This is a concrete freezing of funds for any holder of a `spender_attested` asset whose attestor is dropped from the list: the affected user's outputs become permanently unspendable (until/unless they are re-attested by a currently-valid attestor, which is entirely outside their control and depends on third parties). This matches the "AA fund loss or freezing" / concrete unauthorized-loss-of-access criterion. Impact severity depends on adoption of `spender_attested` assets and value locked in them at the time of an attestor rotation, making it Medium.

### Likelihood Explanation
Any asset definer can trigger this unilaterally and at any time by posting a single `asset_attestors` message - the enabling function requires nothing more than being the asset's definer, which is a normal, expected asset-management action, not a rare or attacker-only capability. Because attestor rotation is a documented, expected asset-management operation, and no safeguard exists for outstanding holders, the likelihood of this occurring (intentionally or accidentally) is Medium-to-High.

### Recommendation
- When validating a spend of a `spender_attested` asset output, check attestation against the attestor list that was current at the time the specific output was created/received (analogous to snapshotting), rather than always against the latest list; or
- Require attestation status to be "sticky" per-output: once an address is validly attested and receives an output, allow it to spend that output regardless of later attestor-list changes, and apply the new list only to freshly issued/received outputs; or
- At minimum, document/enforce that attestor-list updates cannot retroactively invalidate already-attested holders' ability to move existing balances, e.g. by having spend validation accept attestation under *any* attestor list that was valid at output-creation time up to the current one.

### Proof of Concept
1. Definer issues asset `Z` with `{ spender_attested: true, attestors: [A] }` via the `asset` message validated in `validateAssetDefinition` (validation.js:2725-2827), and `attestors` stored via `writer.js` asset_attestors insert on the initial unit.
2. Attestor `A` posts an `attestation` message for address `X` (`writer.js:205-216`), then `X` receives a `payment` of asset `Z`; validation succeeds because `filterAttestedAddresses` finds `X` attested by `A` in the current list (`validation.js:2630-2641`).
3. Definer posts `asset_attestors` with `{ asset: Z, attestors: [B] }`; this passes `validateAttestorListUpdate` (`validation.js:2829-2848`) since only definer-ship and list well-formedness are checked.
4. `readAsset`/`addAttestorsIfNecessary` now returns the latest attestor list `[B]` for asset `Z` for all subsequent lookups (`storage.js:1917-1946`).
5. `X` attempts to spend the previously received output of `Z`; `validatePaymentInputsAndOutputs` calls `filterAttestedAddresses` with the current list `[B]`, `X` is not attested by `B`, and the spend fails with `"owner address is not attested"` (`validation.js:2504-2507`), permanently freezing `X`'s existing balance.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
