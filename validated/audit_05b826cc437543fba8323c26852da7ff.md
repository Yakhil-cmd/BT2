### Title
`pool_state.lp_supply` is never initialized when a pool is created, permanently breaking `deposit()`/`withdraw()` share accounting - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
This is the direct analog of the Surge `debtSharesSupply` bug: a supply-tracking state field that all later share-math relies on is never assigned a value at the point where the first "shares" (here, LP tokens) are minted, so every subsequent operation that reads it operates on a stale/zero value.

### Finding Description
In `initialize_with_permission`, the pool creator's initial liquidity is minted directly: [1](#0-0) 
The function computes `liquidity` from `sqrt(token_0_vault.amount * token_1_vault.amount)` and mints `liquidity - lock_lp_amount` LP tokens to the payer via `token_mint_to`, but nowhere in this instruction is `pool_state.lp_supply` set to reflect the tokens that were just minted. A repo-wide search confirms `lp_supply` is never referenced/assigned in any `initialize*.rs` file [2](#0-1) , in contrast to `deposit.rs` and `withdraw.rs`, which do correctly maintain it with `checked_add`/`checked_sub`: [3](#0-2) [4](#0-3) 

Since `PoolState` is a zero-initialized on-chain account, `lp_supply` defaults to `0` at initialization and is left at `0` after the initial mint. Every subsequent `deposit()`/`withdraw()` call reads `pool_state.lp_supply` and feeds it into `CurveCalculator::lp_tokens_to_trading_tokens` as the divisor: [5](#0-4) [6](#0-5) 
Because `lp_token_supply` is `0`, `checked_div(lp_token_supply)` returns `None`, so `lp_tokens_to_trading_tokens` returns `None` and both `deposit()` and `withdraw()` unconditionally fail with `ErrorCode::ZeroTradingTokens`.

### Impact Explanation
This permanently freezes the pool immediately after creation: no LP can ever deposit additional liquidity, and the pool creator (and any other holder of the initially minted LP tokens) can never redeem their existing LP tokens for the underlying vault tokens, since `withdraw()` hits the same zero-supply division failure. This satisfies the "permanent freezing of user or LP funds" criterion — real tokens are locked in the vaults with no path to reclaim them once minted this way.

### Likelihood Explanation
This triggers deterministically on the very first pool created through `initialize_with_permission`, requiring no attacker action beyond invoking the standard pool-creation instruction with attacker/creator-chosen accounts and amounts — it is not an edge case, it is the default path.

### Recommendation
In `initialize_with_permission` (and any other pool-creation path), explicitly set `pool_state.lp_supply = liquidity` (the full minted amount, including the locked portion) immediately after computing `liquidity` and before/after minting, mirroring the `checked_add`/`checked_sub` maintenance already done in `deposit.rs`/`withdraw.rs`.

### Proof of Concept
1. Call `initialize_with_permission` to create a new pool with token_0/token_1 vault amounts; `liquidity = sqrt(vault0*vault1)` LP tokens are minted to the creator, but `pool_state.lp_supply` remains `0`.
2. Call `deposit()` with any `lp_token_amount > 0`: `CurveCalculator::lp_tokens_to_trading_tokens` divides by `pool_state.lp_supply == 0`, returns `None`, and the instruction reverts with `ErrorCode::ZeroTradingTokens`.
3. Call `withdraw()` with the creator's minted LP tokens: same zero-division failure occurs, so the creator can never redeem the underlying tokens — funds are permanently frozen in the vaults.
