### Title
Webhook organization used for signature verification is not bound to the repository the payload acts on, enabling cross-organization stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but every event handler resolves the `Stack`/`Repository` to write to using the independent `repository.full_name` field, which is never cross-checked against the field used for authentication.

### Finding Description
`WebhooksController` picks the GitHub App/secret used to verify the webhook HMAC from `repository_owner`, computed as: [1](#0-0) 

and verifies the raw body against that organization's secret: [2](#0-1) 

Once verification passes, every handler resolves which `Stack`s to mutate using a *different* field of the same body, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [3](#0-2) 

`repository.owner.login` and `repository.full_name` are two independent JSON fields. The HMAC only proves that the byte string was signed with the secret belonging to the organization named in `repository.owner.login`; it does not enforce any relationship between that value and `repository.full_name`. In Shipit's documented multi-tenant configuration, each GitHub organization has its own `webhook_secret`: [4](#0-3) 

An organization onboarded to the shared Shipit instance legitimately knows its own `webhook_secret` (it was issued to them when they installed their GitHub App) but has no authority over other organizations' repositories. This is directly analogous to the Anchor bug: a normal, unprivileged protocol participant (a validator with no special access) can manipulate a value that is trusted but not properly bound to the entity it is supposed to represent, letting them redirect protocol effects (stake -> another validator's rewards) onto a target they don't own. Here, an onboarded organization ("authenticated organization" = the equality's left side) can redirect handler effects onto a `repository.full_name` it does not own ("repository written" = the equality's right side), breaking the intended equality `authenticated_organization == repository_being_written`.

### Impact Explanation
`PushHandler#process` uses `stacks` (resolved from the attacker-chosen `repository.full_name`) to trigger a GitHub sync on stacks it does not administer: [5](#0-4) 

This enqueues `GithubSyncJob`, which fetches commits via the target stack's own real GitHub credentials and writes them into the stack's commit history / triggers `CacheDeploySpecJob`: [6](#0-5) 

`CheckSuiteHandler` similarly acts on a foreign stack chosen via the unauthenticated `full_name`, scheduling check-run refreshes on its commits: [7](#0-6) 

Because an org with its own valid (but unrelated) `webhook_secret` can force writes/side-effects on any other tracked repository's `Stack`, this is a cross-repository write triggered by an entity that never authenticated for that repository, matching the Critical impact category "cross-repository writes."

### Likelihood Explanation
Exploitation only requires operating a legitimate GitHub App installation on any organization already onboarded to a multi-tenant Shipit deployment (a normal, unprivileged tenant, not a Shipit admin, not requiring `api_clients_secret` or a stolen/leaked secret) and crafting a POST to `/webhooks` with a mismatched `repository.owner.login` vs `repository.full_name`, signed with the tenant's own known secret. This mirrors the original bug's low bar: a validator only needs standard, unprivileged access to the protocol to bias randomness in their favor.

### Recommendation
Bind the field used to select/verify the webhook secret to the field used to resolve the target repository: derive `repository_owner` from the same `repository.full_name` that handlers use (e.g., `full_name.split('/').first`), or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers, rejecting mismatched payloads with `422`.

### Proof of Concept
1. Organization `attacker-org` installs its own GitHub App on the shared Shipit instance (multi-org config), receiving `webhook_secret_A`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` — a signature they can legitimately produce since they know `webhook_secret_A`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes: [2](#0-1) 
5. `PushHandler#process` resolves stacks from `repository.full_name = "victim-org/victim-repo"`, entirely unrelated to `attacker-org`, and calls `stack.sync_github(...)` on the victim's stack: [5](#0-4) 
6. `GithubSyncJob` executes against the victim's stack, writing commits and cache state the attacker never had authorization to touch.

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
