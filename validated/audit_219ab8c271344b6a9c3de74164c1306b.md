### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login`/`organization.login`, decoupling the authenticating organization from the repository the event acts on - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App config (and thus which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, unauthenticated JSON body. Every event handler that actually mutates state, however, resolves the target `Stack`/`Repository`/`Commit` using a *different* field of the same body: `repository.full_name`. Because these two fields are never checked for consistency, an attacker who can produce a signature valid for *any one* configured organization (including one whose `webhook_secret` is blank, which the shipping example configs explicitly allow) can forge webhook payloads that pass verification for org A while `repository.full_name` points at a completely different, unrelated stack/repository tracked under org B.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does: [1](#0-0) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
and `repository_owner` is derived purely from the request body: [2](#0-1) 

`verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) explicitly bypasses HMAC checking entirely when the selected org's `webhook_secret` is blank: [3](#0-2) 
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
Shipit explicitly supports multi-organization deployments where each org has its own `webhook_secret` entry, and the documented/example configs (`config/secrets.development.shopify.yml`, `docs/setup.md`) show `webhook_secret` fields that can legitimately be left blank per org.

Meanwhile, every default handler resolves the affected stack/repository from `repository.full_name` (a distinct field), not from `repository.owner.login`: [4](#0-3) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all inherit this and mutate state (`sync_github`, `Commit#create_status_from_github!`, `schedule_refresh_check_runs!`) purely keyed off `repository.full_name`: [5](#0-4) [6](#0-5) [7](#0-6) 

This is the same bug class as the reported `withdrawForfeit()` issue: a value used for the trust/authorization decision (`rewardTokensClaimed` in the original bug; `repository.owner.login` here) is never kept consistent with the value that the effectful operation is actually performed against (the repaid amount vs. `earned`; `repository.full_name` here). The binding that should hold as an equality — `verified_organization(repository.owner.login) == acted_on_repository_org(repository.full_name)` — is never enforced, because the two are independently attacker-supplied fields inside the same unauthenticated JSON body.

### Impact Explanation
An unprivileged attacker who can obtain (or is simply handed, via a misconfigured/blank `webhook_secret` for any one org in a multi-org Shipit deployment) a valid signature for organization A can submit a webhook whose `repository.full_name` names a stack under an unrelated, properly-secured organization B:
- Via `StatusHandler`, the attacker can create arbitrary commit `Status` rows (`state: 'success'`, forged `context`) for any commit hash tracked by any stack in the instance. If that stack's `shipit.yml` gates deploy eligibility on `ci.require`, this allows an unauthenticated actor to mark an otherwise non-deployable commit as CI-green, directly enabling an **unauthorized deploy** path once combined with continuous delivery or a manual deploy trigger.
- Via `PushHandler`, the attacker can force `stack.sync_github` for stacks under org B, triggering re-sync/queueing jobs (`GithubSyncJob`) which, on stacks with continuous delivery enabled, can trigger deploy attempts out of band.
- Via `CheckSuiteHandler`, the attacker can force `schedule_refresh_check_runs!`, again manipulating deploy-gating status for an unrelated repository.

This satisfies the "High"/"Critical" bar in the rules (unauthorized deploy / unauthenticated write of stack state), because the crossing happens without the attacker needing a Shipit session, an `ApiClient` token, or write access to the target repository at all — they only need the ability to produce a signature (or exploit a blank secret) for *any one* organization configured in the same Shipit instance, then target a *different* org's repository via the `full_name` field.

### Likelihood Explanation
Likelihood is contingent on real-world configuration: it requires either (a) a Shipit instance configured with multiple GitHub App organizations (a documented, supported configuration, `docs/setup.md` "Using Multiple Github Applications") where at least one org has a blank `webhook_secret`, or (b) the attacker legitimately controlling/administering a GitHub App/org that Shipit trusts for one repo, then abusing that trust to target a different tracked org/repo. Given that the example/shipped configuration templates (`config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`) show `webhook_secret` left blank as an accepted default, and multi-org support is a first-class documented feature, this is a realistic misconfiguration path rather than a purely theoretical one.

### Recommendation
Enforce that the organization used to select/verify the webhook signature is the same organization the handlers act upon:
- Verify the signature using the GitHub App config resolved from `repository.full_name`'s owner (the same field handlers use), not a separately-read `repository.owner.login`/`organization.login`.
- Alternatively (or additionally), after successful signature verification, re-check that `repository.owner.login` matches the owner portion of `repository.full_name` before dispatching to handlers, rejecting the payload otherwise.
- Do not silently return `true` from `verify_webhook_signature` when `webhook_secret` is blank; either require a secret for every configured organization or fail closed.

### Proof of Concept
1. Configure Shipit (per documented multi-org support) with two organizations: `orgA` (no `webhook_secret` configured, or one the attacker knows) and `orgB` (properly secured, with a `Stack` tracking `orgB/secure-repo`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a commit on orgB/secure-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/secure-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`; since `orgA`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is even required.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (resolved independent of org) and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto `orgB/secure-repo`'s commit — a stack the attacker has no legitimate relationship to and never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
