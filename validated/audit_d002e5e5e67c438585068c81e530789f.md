### Title
Debt-value `i128` overflow in interest accrual permanently freezes a market — all verbs panic before the borrow-index cap engages - (File: contracts/pool/src/interest.rs)

### Summary
The bug class of CVE-2020-14785 — a crash that takes down the service — maps onto XOXNO Lending's pool as an unrecoverable `MathOverflow` panic inside `global_sync`. Every market verb (`supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `flash_loan`, `recapitalize`, `claim_revenue`, and even the public `update_indexes`) accrues first via `Cache::load → interest::global_sync`. Accrual recomputes debt value with checked multiplication, and once scaled debt shares times the borrow index exceeds `i128::MAX`, accrual panics — before the `MAX_BORROW_INDEX_RAY` index cap can engage. Since `last_timestamp` is never written past the panic, every subsequent call hits the same overflow: no withdrawal, no repayment, no liquidation, no bad-debt cleanup. The market is permanently frozen with all supplier funds locked inside.

### Finding Description
`interest::global_sync` in `contracts/pool/src/interest.rs:20-33` chunks elapsed time into `MAX_COMPOUND_DELTA_MS` windows and calls `accrue_chunk`, which delegates to `common::rates::accrue_step` (`contracts/pool/src/interest.rs:39-48`). The step computes the accrued debt value by unscaling `borrowed` shares at the growing `borrow_index` — the same `scaled_to_original` multiply used in `contracts/pool/src/cache/scale.rs:23`. `docs/reference/invariants.md` (INV-IDX-01) admits the gap directly: "Debt-value overflow can still revert accrual before that ceiling is reached. Bounded indexes do not guarantee representable position or market values."

The end-to-end harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/extreme_amount_inputs.rs:320-360` proves the failure: a market seeded at ~98% utilization on the steep segment of the XLM rate curve accrues for a handful of simulated years, after which `update_indexes` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — the cap never engaged. The test then asserts that `withdraw` and `repay` both fail with the same error, because every verb accrues first. There is no recovery path: `update_indexes` itself panics, `seize_positions`/`clean_bad_debt` accrue first too, and no code path writes `last_timestamp` forward without completing the overflowed multiply.

Reachability by a single unprivileged address: call `controller.supply` with a large amount of a listed asset (or supply collateral and `controller.borrow` a large debt in the target market to drive utilization to the steep part of its interest-rate curve), then let time pass — or keep pushing utilization/borrow volume up with additional borrows. No privileged action, oracle manipulation, or flash mechanics are required; only capital. Because the panic is a revert, not state corruption, the freeze is a clean, permanent denial of service on that `(hub, asset)` market.

### Impact Explanation
**Permanent freezing of funds**, satisfying the accepted-impact list. Once the market crosses the `i128` debt-value boundary:

- Suppliers cannot `withdraw` any amount — accrual panics before the burn.
- Borrowers cannot `repay` — same panic; their collateral stays locked and their positions cannot be liquidated.
- Liquidators cannot `liquidate` — pool `withdraw`/`seize_positions` accrue first.
- Governance cannot recover via `recapitalize` or `claim_revenue` — both accrue first too.
- `clean_bad_debt` cannot socialize the loss, so the bad debt poisons the market forever.

All token funds held by the pool for that market are permanently inaccessible. This mirrors CVE-2020-14785's "hang or frequently repeatable crash (complete DOS)" but with finality: the crash is deterministic and repeated on every call, forever.

### Likelihood Explanation
Likelihood is moderate — Medium severity, consistent with the source advisory. The attack requires no privilege and no timing luck, but it does require capital: the attacker must create a large position (on the order of `i128::MAX / borrow_index` worth of scaled debt at the index multiplier) and the interest curve must be steep enough to compound the debt value to the overflow before the index cap (`MAX_BORROW_INDEX_RAY`, 10³⁶ raw RAY) engages. The harness test demonstrates feasibility on the real XLM curve at 98% utilization in under ~40 simulated years — and an attacker can accelerate this by borrowing more (higher scaled shares raise the value ceiling collision faster) rather than waiting. High-decimal assets (18 decimals in the test) lower the capital barrier because `asset_decimals` shifts the unscaled value up. The freeze is irreversible once triggered, and a whale does not need to be malicious — ordinary large positions at sustained high utilization hit the same cliff.

### Recommendation
Bound the debt *value*, not just the index:

1. In `common::rates::accrue_step`, clamp the effective debt value to `i128::MAX` (or a safe margin below it) before unscaling, or saturate `borrow_index` so that `borrowed * borrow_index` stays representable — i.e., engage a value-aware cap *before* the multiply overflows.
2. Alternatively, make `global_sync` degrade gracefully: on `MathOverflow` during accrual, freeze accrual (write `last_timestamp = now`, cap `borrow_index` at `MAX_BORROW_INDEX_RAY`) instead of panicking, so withdrawals and repayments remain reachable. Suppliers' funds being withdrawable is more important than continued interest accrual.
3. Add a regression test asserting that after the value ceiling is hit, `withdraw`, `repay`, and `seize_positions` still succeed — the current test only asserts they panic.

### Proof of Concept
The repository already contains the executable PoC — `tests/test-harness/tests/controller/extreme_amount_inputs.rs:320-360`. Outline:

```rust
// Supply a whale-sized position in a high-decimal market on the steep
// XLM rate curve, then borrow to ~98% utilization. Both are
// unprivileged controller.supply / controller.borrow calls.
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

// Advance time; each year calls pool.update_indexes (public).
// global_sync -> accrue_step -> scaled_to_original(borrowed, borrow_index)
// overflows i128 -> MathOverflow panic, before MAX_BORROW_INDEX_RAY.
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } // MATH_OVERFLOW
}

// Market is frozen forever: every verb accrues first and panics.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), MATH_OVERFLOW);
```

The test confirms `borrow_index` stays below `MAX_BORROW_INDEX_RAY` at the point of failure — the index ceiling never protects against the value overflow, so no amount of waiting or accrual cadence avoids the freeze once scaled debt is large enough.
