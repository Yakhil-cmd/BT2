### Title
Webhook signature verified against an organization key chosen from the same unauthenticated payload that is later trusted for repository routing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the **unauthenticated** JSON body, before that body's authenticity has been established. The rest of the pipeline (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) then trusts the same untrusted payload fields to resolve the target `Repository`/`Stack`. This breaks the intended binding of "the organization whose secret authenticated this request" == "the organization whose repository/stack the payload is allowed to mutate."

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and uses it to fetch the corresponding `Shipit.github(organization: repository_owner)` app config, then verifies `X-Hub-Signature` against that organization's `webhook_secret`: [1](#0-0) 

Because `repository_owner` is attacker-influenced payload content (it is read before any signature check occurs), an attacker who knows or controls the webhook secret for organization A (e.g., their own onboarded/misconfigured org, or an org configured with no `webhook_secret` at all — in which case `verify_webhook_signature` short-circuits to `true`) can craft a body whose `organization.login`/`repository.owner.login` field points at org A for the *purpose of signature selection*, while the handler-processed fields (`repository.full_name`, commit SHAs, statuses, membership records, etc.) reference org B's actual repository/stack. The handlers (`GithubHook`/`Shipit::Webhooks` handler classes) re-derive the target `Repository`/`Stack` from the same JSON body independently of which organization's key validated the request: [2](#0-1) 

The `verify_webhook_signature` implementation also unconditionally trusts an absent secret as valid: [3](#0-2) 

This is the same trust-binding failure pattern as the analog report: a value used to authorize (organization the signature is checked against) is not the same value that is subsequently acted upon (organization/repository the handler writes to), and the code never re-validates that the two are the same authenticated entity.

### Impact Explanation
If any configured GitHub organization in this Shipit deployment has no `webhook_secret` set (a documented, supported configuration per `config/secrets.development.example.yml`) or if an attacker obtains any single organization's `webhook_secret`, they can forge signed-looking webhook requests whose payload content (`repository.full_name`, `sha`, `state`, `member.login`, `team` objects, etc.) targets an unrelated, higher-value organization/repository that Shipit also manages. This can drive unauthorized state transitions — e.g., forged `status`/`check_suite`/`commit_status` events that unblock CI gating and enable an unauthorized deploy, or forged `membership`/`team` events that add attacker-controlled GitHub identities to `Shipit.github_teams`-authorized teams, escalating into `Shipit.github_teams` authorization (per the report's High-impact criteria).

### Likelihood Explanation
Requires only that the deployment configures more than one GitHub organization (documented multi-org config in `config/secrets.development.example.yml`) or that one organization is configured without a `webhook_secret`; no privileged token, session, or GitHub write access is required — the request is unauthenticated `POST /github/auth/... ` equivalent to the public webhooks endpoint. This is a plausible but configuration-dependent path, since it depends on the specific multi-tenant/webhook_secret setup of the deployment; I could not fully confirm from available files whether the engine enforces additional uniqueness/consistency checks between the selected app config and the eventually resolved repository (the `lib/shipit.rb`/`GithubApp` registry internals were only partially inspectable due to index/tool limits), so this should be verified further in a live session.

### Recommendation
After resolving `repository_owner` and verifying the signature against that organization's app/secret, re-derive the target `Repository`/`Stack` strictly from `repository.full_name` and confirm its owner matches the organization whose key produced a valid signature before dispatching to any handler. Reject events where the signature-selected organization and the payload's target repository owner diverge. Additionally, disallow (or explicitly opt-in with a warning) organizations configured without a `webhook_secret` in multi-org deployments, since a blank secret currently causes `verify_webhook_signature` to always return `true`.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `org-a` (attacker's own, `webhook_secret: nil` or known secret) and `org-b` (victim, `webhook_secret` set and unknown to attacker), per the multi-org config format in `config/secrets.development.example.yml`.
2. Attacker crafts a JSON body for event `membership` (or `status`) whose `organization.login` = `"org-a"` but whose actual acted-upon data (e.g., `member.login`, `team` object, or `repository.full_name`) references a team/repo actually belonging to `org-b`'s Shipit stacks.
3. Send `POST /github/auth/github` webhook endpoint with `X-Github-Event: membership` and (if `org-a` has no secret) any/no valid `X-Hub-Signature`, or a signature computed with `org-a`'s known secret.
4. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` resolves `repository_owner` to `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and passes verification.
5. `Shipit::Webhooks.for_event('membership').each { |handler| handler.call(params) }` processes the payload's `team`/`member` data belonging to `org-b`, creating/removing a `Membership` record for a team associated with `org-b`'s authorization, without ever validating that `org-b`'s webhook secret authorized this event.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
