### Title
Fork PR label names (uppercased) inject arbitrary environment variables (e.g. `GEM_PATH`) into `ReviewStack#env`, poisoning `provision.handler_name` commands - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment variable key with value `"true"`, with no allowlist or blocklist of reserved/dangerous names. Label names are persisted verbatim from the webhook payload by `LabelCapturingHandler#capture_labels`, so an unprivileged fork contributor who can add a label such as `GEM_PATH` (GitHub allows arbitrary label text on their own PR/fork context that triggers `labeled`/`opened`/`reopened` events) causes `GEM_PATH=true` to be merged into the review stack's environment, which then reaches any `Command` spawned for that stack (including the provisioning handler's shell steps) via `Command#unbundled_env`.

### Finding Description
The broken binding: `ReviewStack#env` is claimed to only expose deployment-relevant, sanitized keys, i.e. `ReviewStack#env.keys == Stack#env.keys` (a fixed, known set: `ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`). In reality: [1](#0-0) 

merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" } ` into the base `Stack#env` hash with no key allowlist. `pull_request.labels` is populated directly from GitHub webhook JSON with no filtering: [2](#0-1) 

The `params` schema only requires `labels` entries to have a `name` String — no character/format restriction: [3](#0-2) 

This merged env eventually reaches `Command#start`, which builds the spawned process environment as `BASE_ENV.merge(PATH override).merge(@env.stringify_keys)` — i.e., any key present in `@env` (sourced from the stack/review-stack env, including attacker-controlled uppercase label keys) unconditionally overrides the corresponding key in the base/unbundled environment: [4](#0-3) [5](#0-4) 

**Exploit flow:** An unprivileged fork contributor opens a PR against a repository configured with `provisioning_behavior=allow_with_label`, and adds a label named `GEM_PATH` (or `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc.) to their own PR. GitHub sends a `pull_request` webhook (`labeled`/`opened`/`reopened`) to `POST /webhooks`. `LabelCapturingHandler` persists the raw label name onto the `PullRequest#labels` column with no sanitization. When the `ReviewStack` is provisioned (or any subsequent deploy/task runs for it), `ReviewStack#env` is consulted, producing `GEM_PATH => "true"` (or worse, an attacker-controlled path string if the label itself encodes a path-like value) in the merged environment that is fed into `Command#start` → `PTY.spawn`.

**Why existing guards fail:** There is no `EnvironmentVariables#permit`/allowlist applied to `ReviewStack#env`'s label-derived keys (unlike deploy-time user-supplied envs, which go through `Stack#filter_deploy_envs`/`Task::Definition#filter_envs`). Webhook signature verification (`verify_signature`) only authenticates that GitHub sent the payload — it does not restrict *which* fields of that payload (like arbitrary label text) are safe to project into a process environment. `require_permission!`/`User#authorized?` are not on this code path at all — the webhook path is intentionally unauthenticated-by-user (webhook-signature-authenticated only), and label names are treated as free-form untrusted text.

### Impact Explanation
If the review stack's `provision.handler_name` step (or any deploy/task/rollback command executed for that stack) is a Ruby/Bundler-based script, an attacker-controlled `GEM_PATH` (or `RUBYOPT`, `RUBYLIB`, `BUNDLE_GEMFILE`) causes `require`/`bundle exec` to consult attacker-influenced paths, potentially leading to code execution in the context of the Shipit deploy host process. This is scoped to the specific review-stack's provisioning/deploy commands — but any fork contributor able to open/label a PR on a repo with `provisioning_behavior=allow_with_label` can trigger it repeatedly, and the blast radius depends on what the provisioning script actually requires/loads. Matches the "Critical - RCE on the deploy host via `Command`/`PTY.spawn`" category if a require/bundle-sensitive provisioning script is in use.

### Likelihood Explanation
Preconditions: the repository must have PR-based review stacks enabled with `provisioning_behavior=allow_with_label` (or the label capture flow enabled at all, since `LabelCapturingHandler` runs regardless of the `allow_with_label` policy check on `opened`/`labeled`/`reopened`/`unlabeled` events for any active stack) [6](#0-5) . Cost to the attacker is minimal: they only need permission to open a PR and add a label on their own PR/fork, which GitHub permits for public repos with default settings. The actual severity depends on the operator's `shipit.yml` provisioning script content (whether it is Ruby/Bundler-sensitive) — this is a real environment-injection primitive regardless, and the code contains no defense against it.

### Recommendation
Apply an explicit allowlist (or a denylist of reserved/dangerous names such as `PATH`, `GEM_PATH`, `GEM_HOME`, `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `HOME`) to label-derived keys in `ReviewStack#env`, and/or prefix all label-derived variables with a fixed namespace (e.g., `LABEL_<NAME>`) so they can never collide with or override reserved environment variables consumed by `Command#unbundled_env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual)
test "review stack env does not allow labels to inject reserved env vars like GEM_PATH" do
  stack = shipit_review_stacks(:review_stack)
  pull_request = stack.pull_request
  pull_request.update!(labels: ["GEM_PATH"])

  env = stack.env
  # Binding under test: env must never contain attacker-controlled GEM_PATH
  refute env.key?("GEM_PATH"), "fork PR label should not be able to set GEM_PATH"
end

test "Command#unbundled_env inherits attacker-controlled GEM_PATH from provision env" do
  command = Shipit::Command.new(
    ['echo', {env: {}}],
    chdir: Dir.tmpdir,
    env: { "GEM_PATH" => "/tmp/evil" }
  )
  assert_equal "/tmp/evil", command.unbundled_env["GEM_PATH"]
  # Demonstrates that whatever key reaches Command#env (via ReviewStack#env) is spawned verbatim.
end
```
This demonstrates the equality `ReviewStack#env.keys ⊇ {"GEM_PATH"}` after labeling, contradicting the invariant that the `provision.handler_name` step should inherit no fork-controllable reserved key, and that this value is propagated unchanged into the spawned process's environment.
