### Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) from the *unauthenticated* JSON body, but every event handler subsequently resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`, taken from the same untrusted body. The signature only proves "this payload was signed with organization X's webhook secret" — it never proves that `repository.full_name` actually belongs to organization X. In Shipit's documented multi-organization mode, this lets an entity that legitimately possesses org A's webhook secret forge a payload whose `repository.owner.login` is "A" (so it authenticates) while `repository.full_name` points at a Stack belonging to org B, causing Shipit to act on org B's stack.

### Finding Description
`verify_signature` computes the org used to pick the `GitHubApp`/secret purely from the payload: [1](#0-0) [2](#0-1) 

The HMAC check itself only compares the digest against `request.raw_post` using the secret configured for that derived organization — it says nothing about which repository the payload refers to: [3](#0-2) 

Once "verified", the full raw JSON (`params`) is dispatched unmodified to every registered handler for the event: [4](#0-3) 

Handlers resolve the target `Repository`/`Stack` from a *separate* payload field, `repository.full_name`, with no re-check that its owner matches the organization whose secret validated the request: [5](#0-4) [6](#0-5) 

`PushHandler`, for example, uses that repository resolution to enqueue a real sync job against whatever Stack is returned: [7](#0-6) 

Shipit explicitly supports hosting multiple independent GitHub organizations from one instance, each with its own `webhook_secret`, configured under separate top-level keys: [8](#0-7) [9](#0-8) 

The equality that should hold is:
`organization(secret used to verify signature) == owner(repository.full_name acted upon by the handler)`

but the code never enforces it — it only checks `organization(repository.owner.login) == organization(secret used)`, and separately (and independently) resolves the acted-upon repository from `repository.full_name`. Because both fields live in the same attacker-controllable JSON body, and the signature covers the raw bytes but the controller doesn't cross-validate the two fields against each other, an attacker who can produce a validly-signed payload for org A (i.e., knows org A's `webhook_secret`, e.g. because they administer org A's GitHub App installation in this multi-tenant Shipit deployment) can set `repository.owner.login: "A"` (to pass signature selection) while setting `repository.full_name: "B/some-repo"` (to make the handler act on org B's Stack).

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written," matching the required High-impact class of "escalation into a repository/stack the authenticated org is not authorized for." Concretely, `PushHandler` will enqueue `GithubSyncJob` for an arbitrary Stack chosen by the attacker regardless of which org's secret validated the request, and `StatusHandler`/`CheckSuiteHandler`/pull-request handlers similarly act on `Commit`/`CheckRun`/`ReviewStack` records tied to a Repository the attacker's org has no legitimate relationship to — i.e. cross-organization/cross-repository state manipulation driven entirely by a credential (webhook secret) scoped to a different, unrelated repository owner. This is only a meaningful escalation in deployments that configure multiple GitHub organizations against a single Shipit instance, which the engine explicitly documents and supports.

### Likelihood Explanation
Requires: (1) the deployment to use the multi-organization `github:` config format, and (2) the attacker to already legitimately hold a `webhook_secret` for at least one configured organization (e.g., as that org's GitHub App administrator). Given those preconditions — which are within the documented, intended-multi-tenant use of this engine — no other privilege is required; the attacker sends a single crafted POST to `/webhooks` with a correctly computed `X-Hub-Signature`.

### Recommendation
After `verify_signature` resolves `repository_owner` and validates the HMAC, re-derive the acted-upon repository's owner from `repository.full_name` (or `organization.login`) and assert it equals the same `repository_owner` used to select the signing secret; reject (422) on mismatch before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with multi-org config: `github: { orgA: { webhook_secret: "s_A" }, orgB: { webhook_secret: "s_B" } }`, each with an installed GitHub App, and Stacks configured for repos under both `orgA/*` and `orgB/*`.
2. As an entity that manages orgA's GitHub App (and thus knows `s_A`), craft a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(s_A, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature validates successfully — request proceeds to `create`. [1](#0-0) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgB/target-repo")` and enqueues `stack.sync_github(...)` for orgB's stack, even though the request was only authenticated with orgA's secret. [7](#0-6) [5](#0-4)

```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```
