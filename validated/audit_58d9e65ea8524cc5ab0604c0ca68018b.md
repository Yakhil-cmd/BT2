### Title
Membership-Webhook Authorization Escalation via Cross-Organization Signature Bypass on Nil `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The `WebhooksController` selects which GitHub App configuration (and thus which HMAC secret) to use for signature verification based on an attacker-controlled field of the *unverified* JSON payload (`repository.owner.login` or `organization.login`), not based on any already-authenticated identity. `GitHubApp#verify_webhook_signature` additionally treats a blank/`nil` `webhook_secret` as automatically valid. Because the payload field used to select the verification secret is decoupled from the payload fields the `membership` handler actually acts on (`team`, `organization`, `member`), an attacker who can trigger verification against any organization configured with no `webhook_secret` can submit a forged `membership` event that creates/joins a `Shipit::Team`, thereby escalating into `Shipit.github_teams` authorization for an arbitrary target user — all without any GitHub credentials, `ApiClient` token, or session.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using data taken straight out of the still-unverified request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both are plain fields of the JSON body, readable and settable by anyone crafting the POST, with no relation yet established to a valid signature.

`GitHubApp#verify_webhook_signature` treats an org with no configured `webhook_secret` as unconditionally verified: [3](#0-2) 

The engine explicitly supports multiple GitHub organizations, each with its own independent `webhook_secret`, selected via `Shipit.github_app_config(organization)`: [4](#0-3) 

The repo's own fixtures demonstrate that a legitimately configured organization can have `webhook_secret: # nil`: [5](#0-4) 

Once signature verification "passes" (trivially, because `OrgTwo` has no secret), `WebhooksController#create` dispatches the *entire, attacker-supplied* JSON body to the registered handler for the event type, with no further tie-back to the organization used for verification: [6](#0-5) 

For the `membership` event, `MembershipHandler#process` reads `team`, `organization.login`, and `member.login` directly from that same attacker-controlled payload and uses them to create a `Team` and add an arbitrary GitHub-login `User` to it: [7](#0-6) 

`Shipit.github_teams` (used to authorize dashboard/API access via `User#authorized?`) is derived from `Team` records that this same code path creates/populates: [8](#0-7) [9](#0-8) 

This is the same class of bug as the reported `VirtualToken.cashIn` issue: one field (`msg.value`/`amount`) is checked/used in one place while a *different* field of the same call is trusted for the actual effect (`_mint`). Here, the binding that should hold is:

`organization whose webhook_secret authenticated the request == organization/team the handler is permitted to mutate`

but the engine breaks this equality: the org used to *select the verification secret* (`repository_owner`, checked before verification) is never re-checked against the org (`params.organization.login`) that the `MembershipHandler` actually writes team membership for. Any organization entry configured without a `webhook_secret` — a supported, documented configuration (see `docs/setup.md`'s `webhook_secret: some-secret-value`, optional) — becomes a skeleton key: signing is bypassed entirely for requests claiming that org, while the payload's `team`/`organization`/`member` fields (used for the actual privileged action) are free-form and unrelated to that org.

### Impact Explanation
This is a High-severity finding: it is an unauthenticated (no session, no `ApiClient` token, no GitHub credentials) escalation into `Shipit.github_teams` authorization. An attacker can:
1. POST to `/webhooks` with `X-Github-Event: membership`, `repository`/`organization.login` set to any Shipit-configured org lacking a `webhook_secret` (or, in single-secret installs, any deployment where an operator has left `webhook_secret` empty/nil, which is an explicitly supported "optional" configuration per `docs/setup.md`).
2. Because `verify_webhook_signature` returns `true` for that org unconditionally, no valid HMAC is required.
3. `MembershipHandler` then creates a `Team` matching one of `Shipit.github_teams`' handles (or a pre-existing one) and adds a `member` login of the attacker's choosing, granting that (attacker-controlled) `User` row `authorized?` status and bypassing the team-based access control gate in `Shipit::Authentication#force_github_authentication`.

### Likelihood Explanation
Likelihood is Medium-High for any multi-organization deployment where at least one configured organization omits `webhook_secret` (a state the engine's own configuration schema and fixtures show as valid/expected), or for any deployment that has not set a webhook secret at all. No privileged token, session, or GitHub credential is required — only knowledge of the org's login handle (often public) and the ability to send an HTTP POST to the public `/webhooks` endpoint.

### Recommendation
- Reject requests when `verify_webhook_signature` short-circuits due to a blank `webhook_secret` in a multi-org (or single-org) configuration, or require operators to always configure a non-empty secret before an org's webhooks are accepted.
- Do not select the signature-verification context from unauthenticated payload fields; instead, verify against every currently configured GitHub App/secret (or bind the webhook route per-org) so that a chosen "no-secret" org cannot be used to authorize processing of payload fields belonging to a different org/team.
- After signature verification succeeds, re-validate that the `organization`/`repository.owner.login` used to select the verifying secret matches the `organization.login`/`team`/`member` fields the handler subsequently acts on, rejecting mismatches.

### Proof of Concept
1. Deploy config `test/dummy/config/secrets_double_github_app.yml`-style setup, or any config where an org's `webhook_secret` is nil/absent.
2. Send:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything

{
  "action": "added",
  "team": { "id": 999, "name": "Shipit", "slug": "shipit", "url": "https://x" },
  "organization": { "login": "OrgTwo" },
  "member": { "login": "attacker-github-login" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` → `verify_webhook_signature` returns `true` because `OrgTwo.webhook_secret` is nil (`lib/shipit/github_app.rb:76-77`), independent of the bogus `X-Hub-Signature`.
4. `MembershipHandler#process` runs unmodified, creating/updating `Team` `shipit` and adding `User` `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
5. If `Team` `shipit` corresponds to one of `Shipit.github_teams`, the attacker's `User` record now passes `User#authorized?` (`app/models/shipit/user.rb:80-82`), escalating access without ever authenticating via OAuth/GitHub.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
