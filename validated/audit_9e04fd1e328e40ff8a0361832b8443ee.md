## Confirmed: cross-organization webhook forgery breaks the "organization authenticated == repository written" binding

### Title
Webhook signature verification selects the secret from an attacker-controlled `repository.owner.login`/`organization.login` field, decoupled from the `repository.full_name` the handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read directly out of the *unverified* JSON body, before the signature is checked. The event handlers, however, look up the target `Stack`/`Repository` using a *different* field of the same unverified body: `repository.full_name`. Nothing ties these two fields together, so an attacker who can produce a valid signature for *any* configured organization (e.g. one with no `webhook_secret` set, which is an explicitly supported configuration) can forge a payload whose `repository.full_name` points at a completely different organization/repository and have it processed as if it came from GitHub.

### Finding Description
`verify_signature` derives the signing key from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the app config for that organization and `verify_webhook_signature` is checked against *that* organization's secret: [3](#0-2) [4](#0-3) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured (`return true unless webhook_secret`). Multi-organization deployments with a per-organization secret are an explicitly supported/documented topology, and the fixture/dummy config even demonstrates an organization configured with `webhook_secret: # nil`.

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw JSON to handlers: [5](#0-4) 

Every handler resolves its target `Stack`/`Repository` from `repository.full_name` — a *different* field of the same attacker-supplied body, never cross-checked against `repository_owner`: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

The equality binding that should hold is: `organization whose secret authenticated the request == owner of the repository the handler writes to`. In the current code, `repository_owner` (used only for signature key selection) and `repository.full_name`'s owner (used only for the write) are independent, attacker-controlled fields inside the same unauthenticated JSON body. An attacker who knows (or is not required to know, if the secret is blank) the secret for organization `A` can set `repository.owner.login = "A"` for signature purposes while setting `repository.full_name = "B/private-repo"` for the actual handler logic, forging events for any repository hosted under any other configured organization `B`.

Before the attacker's crafted request: signature verification and target-repository resolution are supposed to reference the same organization/repository, an implicit invariant relied upon by every handler that trusts payload-provided `repository.full_name`. After the crafted request: the two references diverge, and the invariant is violated with no code path enforcing it.

### Impact Explanation
This is a genuine cross-tenant/cross-repository forgery inside the engine's own trust boundary (not merely a third-party/gem issue, not requiring an `ApiClient` token, session, or GitHub write access — the whole premise of the webhook endpoint is that GitHub, not an attacker, submits it). Concrete unauthorized effects reachable through in-scope handlers:

- `StatusHandler#process` writes arbitrary `CommitStatus` records (`state`, `context`, `description`, `target_url`) for any commit sha in the target stack, which feeds directly into CI-gating logic used by the merge queue and continuous-deployment decisions — enabling an unauthorized merge/deploy path for a repository the attacker does not control on GitHub. [10](#0-9) 
- `CheckSuiteHandler#process` triggers `schedule_refresh_check_runs!` for arbitrary commits in a foreign stack. [11](#0-10) 
- `PushHandler#process` triggers `sync_github` for a foreign stack's branch using an attacker-chosen `after` sha context. [12](#0-11) 

Forged commit statuses that satisfy `ci.require` can cause Shipit to treat an otherwise-unreviewed/failing commit as deployable/mergeable — this lands squarely in the "unauthorized deploy, rollback or merge" Critical-impact bucket defined by the rules.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a supported, documented configuration — see `github_organizations`/`github_app_config` and the dummy multi-org secrets fixture) and that at least one configured organization either has no `webhook_secret` set or its secret is otherwise known/guessable by the attacker. No repository write access, no `ApiClient` token, no session, and no TLS interception are needed — the attacker only needs to reach the public `/webhooks` (or equivalent) endpoint with a crafted POST body, which is exactly the deployment-trust binding the audit rules ask to look for (organization authenticated vs. repository written).

### Recommendation
After successfully verifying the signature, re-derive `repository_owner`/target stack strictly from the verified organization context, or explicitly assert that the organization used for signature verification matches the owner segment of `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers. Reject the request if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `OrgA` (no `webhook_secret`, or a known/leaked secret) and `OrgB` (private, unknown secret), each with stacks tracking real repositories.
2. POST to the webhooks endpoint with `X-Github-Event: status` and a body such as:
   ```json
   {
     "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/private-repo" },
     "sha": "<victim-commit-sha-in-OrgB-stack>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
   Omit `X-Hub-Signature` (or send `sha1=` and any value) — since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally.
3. `StatusHandler` resolves the target via `Repository.from_github_repo_name("OrgB/private-repo")` and creates a passing `CommitStatus` for the victim commit, even though the request was never authenticated by `OrgB`'s GitHub App/secret — satisfying CI requirements and enabling an unauthorized merge/deploy for `OrgB`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
