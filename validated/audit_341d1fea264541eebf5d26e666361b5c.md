### Title
Cross-repository Status forgery via globally-unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA across the *entire* database (`Commit.where(sha: params.sha)`) instead of scoping the lookup to the stacks owned by the repository that authenticated the webhook. Any repository whose webhook signature verifies successfully can therefore push a `status` event for a SHA that happens to also exist in another tenant's stack, causing a `Shipit::Status` row to be created with that victim stack's `stack_id`.

### Finding Description
The intended binding is: `Status#stack_id` written == the stack(s) belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, i.e. the repository that signed the webhook. This is exactly the binding enforced by the base `Handler#stacks` helper: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [1](#0-0) .

`StatusHandler#process`, however, never calls `stacks`. It instead does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha: params.sha)` is a global, unscoped query across all stacks/repositories in the installation — it has no `WHERE stack_id IN (...)` filter tied to the payload's own repository at all.

For each matched commit (which may belong to *any* stack), `create_status_from_github!` is invoked:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [3](#0-2) 

Here `stack_id` is `self.stack_id`, i.e. the `stack_id` column of the *matched Commit row*, not anything derived from or validated against the webhook payload's `repository.full_name`. `Status.replicate_from_github!` then persists it verbatim:
```ruby
def replicate_from_github!(stack_id, github_status)
  find_or_create_by!(
    stack_id:,
    state: github_status.state,
    ...
  )
end
``` [4](#0-3) 

**Why existing guards fail:** `verify_signature` in `WebhooksController` only proves that the *sender* possesses the `webhook_secret` for the *organization* named in `params.dig('repository','owner','login')` [5](#0-4) . It authenticates "this request genuinely comes from GitHub for org X," not "this request is entitled to write to stack Y." The repository-to-stack scoping that would normally enforce that entitlement (`Handler#stacks`) is simply not used by `StatusHandler`, unlike the pattern other handlers are expected to follow.

**Attacker's exact path:** an attacker who owns/administers *any* repository tracked as a Shipit stack (Stack B) can:
1. Push a commit to Stack B's repo whose SHA is identical to a SHA already present in a victim Stack A's commit history. This is trivial when both repos share history for a public commit (e.g. a vendored dependency, a shared upstream commit, or simply copying the victim's public commit object — git commits are content-addressed and fully portable between repositories).
2. Use the GitHub Statuses API (or any means) on their own repo/commit to make GitHub emit a legitimately-signed `status` webhook (X-Hub-Signature computed with the real secret for their own org — no secret is ever known/guessed by the attacker, GitHub computes and sends it).
3. `StatusHandler#process` runs `Commit.where(sha: same_sha)`, which returns both the attacker's own Commit row and the victim's Commit row (in Stack A), and writes an attacker-controlled `Status` (`state`, `description`, `target_url`, `context`) into Stack A.

### Impact Explanation
An unprivileged party who merely owns a Shipit-tracked repository can write forged `Shipit::Status` rows into a stack they have no authorization over, as long as they can produce/observe a shared SHA. Because `Status#state` feeds directly into `Commit#deployable?` / CI gating (`stack.ignore_ci? || (success? && !blocked?)`) via `Status::Group`, this can flip a victim commit's CI status to `success`, unblocking or enabling deploys/continuous delivery for a stack the attacker never authenticated against. This is repeatable against any stack for which a shared/predictable SHA can be arranged, and matches the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs (a) control of any repository that is itself onboarded as a Shipit stack (a normal, low-privilege state for anyone integrating their own project with the Shipit instance), and (b) a SHA collision with a target victim commit — achievable deterministically by copying/pushing a known public commit (e.g., a shared open-source dependency commit, or literally reusing a victim's public commit object) into the attacker's own repo. No secrets, sessions, or team memberships are required; GitHub itself signs the webhook for the attacker's own org, which the attacker legitimately possesses. This is fully repeatable and low-cost.

### Recommendation
Scope `StatusHandler#process`'s commit lookup by the payload's own repository, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
Apply the same scoping check to any other handler that queries `Commit`/`CheckRun` by SHA without going through `stacks` (e.g. check-run handling), and add a regression test asserting cross-repository isolation.

### Proof of Concept
```ruby
test "status webhook for repository B cannot create a Status on repository A's stack via shared sha" do
  stack_a = shipit_stacks(:shipit) # victim stack
  stack_b = create_stack!(repository: create_repository!(name: 'attacker-repo')) # attacker-controlled stack

  shared_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'victim commit', author: AnonymousUser.new)
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'attacker commit', author: AnonymousUser.new)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'attacker-context',
    'repository' => { 'full_name' => stack_b.repository.github_repo_name, 'owner' => { 'login' => stack_b.repository.owner } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Broken binding under test: Status#stack_id should equal the *webhook's own* repository's stack (stack_b),
  # never stack_a, since stack_a's repository never authenticated this payload.
  assert_not Shipit::Status.where(stack_id: stack_a.id, context: 'attacker-context').exists?,
    "attacker-signed webhook for repository B must not create a Status row scoped to victim stack A"
  assert Shipit::Status.where(stack_id: stack_b.id, context: 'attacker-context').exists?
end
```
This test currently fails against the code as written, because `Commit.where(sha: shared_sha)` returns `commit_a` too, and `commit_a.create_status_from_github!` writes a `Status` with `stack_id: stack_a.id`.
