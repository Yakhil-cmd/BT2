### Title
Attacker-controlled route bytes can inject a wallet-token transfer into the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts caller-supplied `StrategySwap` bytes in `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, then forwards them verbatim to the configured swap aggregator. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)  The router-call guard only authorizes one exact `token_in.transfer(controller, router, amount_in)` and does not constrain calls made by payload-selected venues. [5](#0-4) [6](#0-5)  A rogue venue can therefore append a victim-authorized token transfer beneath the victim's `swap_*` or `multiply` authorization tree while still returning enough output to satisfy the controller's balance checks. [7](#0-6) [8](#0-7) 

### Finding Description
`process_swap_collateral`, `process_swap_debt`, `process_repay_debt_with_collateral`, and `process_multiply` all authorize the caller and pass attacker-influenced route bytes into the common router path. [9](#0-8) [10](#0-9) [11](#0-10) [12](#0-11) 

`swap_tokens` snapshots only the controller's `token_in` and `token_out` balances, authorizes the router to pull the exact input amount, and invokes `execute_strategy(controller, amount_in, swap)` with the opaque payload unchanged. [13](#0-12) [14](#0-13) 

The explicit contract authorization contains no sub-invocations, but it protects only the controller's input token; it does not prevent a route-selected contract from requesting authorization from the transaction signer elsewhere in the call tree. [6](#0-5) [15](#0-14) 

The post-call checks only reject controller input growth or overspending and require a positive controller output delta, so an unrelated transfer of the caller's wallet token does not make the strategy fail. [7](#0-6) [16](#0-15) 

The authorization-tree test demonstrates the injected command shape: a payload-selected pool calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`, simulation records that transfer as a child of Alice's `swap_collateral` invocation, and execution both drains Alice's wallet token and completes the fair collateral swap. [17](#0-16) [8](#0-7) 

### Impact Explanation
A malicious route provider or phishing frontend can make a victim sign a `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` transaction whose authorization tree includes a hidden child transfer of an unrelated token. [18](#0-17) [19](#0-18) 

If signed, the attacker steals arbitrary wallet tokens held directly by the victim while the requested lending operation remains solvent and completes normally. [20](#0-19)  This is theft of user funds rather than merely a bad fill, because the stolen token need not be the strategy's input, output, collateral, or debt asset. [21](#0-20) 

### Likelihood Explanation
An unprivileged attacker can deploy the rogue venue contract and construct the malicious route; no protocol role, leaked key, upgrade, or oracle manipulation is required. [22](#0-21) 

Execution requires the victim to sign the poisoned authorization tree produced by simulation, so the practical prerequisite is a malicious or compromised route/frontend rather than direct submission by the attacker. [23](#0-22)  The fair returned swap output means the normal slippage-oriented user expectation does not reveal that unrelated wallet funds will also move. [7](#0-6) 

### Recommendation
Do not allow opaque swap programs to reach arbitrary venue contracts under the caller's root authorization; restrict routes to protocol-approved venue contracts or structured venue identifiers instead of attacker-selected addresses. [13](#0-12) 

Until routes are allowlisted, clients must decode the complete payload and reject any signed authorization tree containing children other than the expected controller input transfer; however, this client-side check should not be treated as a substitute for route-venue validation. [6](#0-5) [20](#0-19) 

### Proof of Concept
1. The attacker deploys a venue-shaped contract whose `swap` function invokes `wallet_token.transfer(victim, attacker, victim_balance)`. [17](#0-16) 
2. The attacker returns a route that sends the swap through that venue while arranging enough legitimate `token_out` liquidity for the strategy to produce a positive output delta. [5](#0-4) 
3. The victim calls `swap_collateral(caller=victim, account_id, current, from_amount, new, swap=malicious_route)` or an equivalent routed strategy. [1](#0-0) [24](#0-23) 
4. Simulation places `wallet_token.transfer(victim, attacker, victim_balance)` beneath the victim's root `swap_collateral` authorization. [25](#0-24) 
5. If the victim signs that tree, the transaction drains the unrelated wallet token while leaving the controller's input-spend and positive-output checks satisfied. [26](#0-25) [7](#0-6)
