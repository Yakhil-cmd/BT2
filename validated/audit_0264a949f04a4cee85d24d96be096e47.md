### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but event handlers resolve and mutate the target repository from `repository.full_name` — allowing cross-organization webhook forgery in multi-app Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using the `repository.owner.login` field of the **unverified** JSON body, while every `Webhooks::Handlers::Handler` subclass (via `Handler#stacks`) resolves the `Repository`/`Stack` to act on using the **separate** `repository.full_name` field from that same body. These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that gets written to" are not the same binding.

### Finding Description
`verify_signature` picks the `github_app` (and therefore the `webhook_secret` used for HMAC verification) purely from `repository_owner`, which is read straight out of the JSON payload before any authentication has occurred: [1](#0-0) [2](#0-1) 

Meanwhile, every handler that actually processes the event (push, status, check_suite, etc.) resolves the target `Stack`s using a *different* field of the same payload: [3](#0-2) 

Shipit explicitly supports hosting multiple, independently-configured GitHub Apps/organizations behind a single instance, each with its own `webhook_secret`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated `Stack`) are independent, unauthenticated JSON fields controlled entirely by whoever sends the POST to `/webhooks`, an attacker who legitimately controls one onboarded GitHub App/organization (e.g. their own low-trust org that an operator has also connected to the same Shipit instance) can craft a payload where:
- `repository.owner.login = "attacker-org"` → signature check passes using the attacker's own known `webhook_secret`.
- `repository.full_name = "victim-org/private-repo"` → the handler acts on the victim's `Stack`.

This breaks the binding: `organization that authenticated == repository that is written` is assumed true throughout the webhook pipeline but is never enforced.

### Impact Explanation
Handlers that key off `repository.full_name` include the status handler, whose test confirms that commit CI status fields (`state`, `context`, `target_url`, `description`) are written verbatim from the payload onto the resolved commit: [6](#0-5) 

If `ci.require` in a victim stack's `shipit.yml` gates merges/deploys on a named status context, an attacker who only controls a different, unrelated organization's webhook secret can inject a forged "success" status for a real commit in a repository they have no access to, satisfying CI requirements and enabling an unauthorized deploy or merge-queue advance — this reaches the "unauthorized deploy, rollback or merge" Critical impact bucket. The push handler is similarly reachable and can trigger `GithubSyncJob`/resync activity against a victim stack the attacker does not control.

### Likelihood Explanation
This requires the operator to have configured more than one GitHub App/organization on a single Shipit instance — a supported and documented configuration (`docs/setup.md`, "Using Multiple Github Applications") — and requires the attacker to control (or know the `webhook_secret` of) at least one of those onboarded organizations, which is a materially weaker requirement than requiring access to the victim organization's own secret, `GITHUB_TOKEN`, or an `ApiClient` token. In single-organization deployments this issue is not exploitable, so likelihood depends on deployment topology.

### Recommendation
After parsing the payload, verify that `repository.owner.login` (or the resolved `github_app`'s organization) matches the organization owning the `Repository` resolved via `repository.full_name` before invoking any handler; reject the request (422) on mismatch instead of trusting the two fields independently.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `attacker-org` (attacker is an org owner, knows its `webhook_secret`) and `victim-org` (hosts the tracked `victim-org/private-repo` stack).
2. Attacker computes a valid `X-Hub-Signature` over a JSON body using `attacker-org`'s known `webhook_secret`, but sets the body's `repository` object to:
```json
{
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "sha": "<real sha of a commit in victim-org/private-repo>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/private-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully with the attacker's own secret.
4. `Handler#stacks`/`StatusHandler` resolves `Repository.from_github_repo_name("victim-org/private-repo")` and writes the forged status onto the victim's commit, as shown by the field-mapping demonstrated in `test/controllers/webhooks_controller_test.rb:42-59`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
