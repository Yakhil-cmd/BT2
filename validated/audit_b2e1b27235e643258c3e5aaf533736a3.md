### Title
Missing `return` in error path causes double-processing of a private-payment chain — analogous to the `tipc_buf_append()` UAF's missing-abort pattern - ([File: network.js])

### Summary
In `handleSavedPrivatePayments()`, the inner `validateAndSave()` closure computes a payload hash with `objectHash.getBase64Hash()` inside a `try/catch`. If it throws, the `catch` block deletes the unhandled-payment row and invokes the `async.each` completion callback `cb()` — but execution then falls through to the code after the `try/catch` and calls `privatePayment.validateAndSavePrivatePaymentChain()` a second time on the very same `arrPrivateElements`/`row`, eventually invoking `cb()` (or emitting side effects) a second time for an item whose processing was already finalized. [1](#0-0) 

### Finding Description
`validateAndSave` is defined as:

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
``` [2](#0-1) 

There is no `return` statement inside the `catch` block, so after `deleteHandledPrivateChain(..., cb)` already finalizes the item (removes the DB row and calls the per-item `async.each` callback `cb`), the function continues past the catch and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again on the same, now-stale `row`/`arrPrivateElements`. That call's `ifOk`/`ifError`/`ifWaitingForChain` handlers each eventually call `cb()` again, and `ifOk` re-invokes `deleteHandledPrivateChain` and mutates `assocNewUnits` a second time.

This is the same bug class as the CVE: `tipc_buf_append()`'s error path frees the skb via `kfree_skb()` but omits a `return`, so the caller subsequently treats the already-freed buffer as still owned/live, causing a second free/use. Here, the error path already "releases" the work item (deletes DB row, invokes `cb`) but omits `return`, so the same logical resource (the unhandled-private-payment row / chain, and the `async.each` item-completion token `cb`) is used a second time through `validateAndSavePrivatePaymentChain`.

`getBase64Hash(objHeadPrivateElement.payload, true)` uses `getJsonSourceString()`, which throws on values it considers malformed (`null`, non-finite numbers, empty arrays/objects, etc.) — precisely the kinds of malformed payload fields an attacker fully controls when constructing a private-payment chain sent over `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`. [3](#0-2) [4](#0-3) 

### Impact Explanation
Calling the `async.each` per-item callback `cb` twice for the same item breaks `async`'s internal accounting: the final completion callback for `handleSavedPrivatePayments` (`unlock(); ... eventBus.emit("new_my_transactions", ...)`) can fire prematurely or be invoked in an inconsistent state relative to how many rows were actually still pending, releasing the `["saved_private"]` mutex early while a duplicate validation of the same chain is still in flight. Meanwhile the duplicate call into `privatePayment.validateAndSavePrivatePaymentChain()` re-processes and potentially re-emits `new_direct_private_chains`/`new_my_transactions` events and re-attempts (no-op) row deletion, and can race with the next scheduled `handleSavedPrivatePayments()` invocation operating on the now-prematurely-unlocked mutex — leading to duplicate/overlapping processing of the same private-asset chain. Because private-payment validation writes spend-proofs/outputs and marks issued serial numbers as spent, overlapping/duplicate validation passes on the same chain risk corrupting the deterministic bookkeeping (double insertion attempts, inconsistent `is_spent`/`is_unique` state) used to prevent double-spending of private (indivisible/divisible) asset coins — i.e., node disagreement on validity/stability or asset-accounting corruption for private payments, matching the categories accepted for this scan.

### Likelihood Explanation
The trigger is fully attacker-controlled: any device/private-payment counterparty sending a private-payment chain can include a payload field that makes `getSourceString`/`getJsonSourceString` throw (e.g. an empty array/object, `null`, `NaN`/`Infinity` amount, or a string containing the internal `\x00` join character) as `payload.outputs`/`payload.inputs` elements are attacker-supplied JSON. This is a routine, single-message, unprivileged-peer-reachable path (`handlePrivatePaymentChains` → `unhandled_private_payments` → `handleSavedPrivatePayments`), requiring no race-window luck beyond normal message delivery.

### Recommendation
Add a `return` after `deleteHandledPrivateChain(...)` inside the `catch` block in `validateAndSave()` so the function aborts immediately on hash-computation failure and never falls through to call `privatePayment.validateAndSavePrivatePaymentChain()` a second time for the same item/`cb`. Additionally, consider guarding `cb`/`deleteHandledPrivateChain` with an idempotency flag so a logic error elsewhere cannot cause a double-invocation of the `async.each` iteratee.

### Proof of Concept
1. As a private-payment counterparty (device pairing partner), send a `private_payment_chains` message via `handlePrivatePaymentChains` whose head element's `payload` contains a field that trips `getJsonSourceString`, e.g. an empty `outputs` array element, or a numeric field set to `Infinity`/`NaN` (bypassing earlier structural checks that only validate presence/non-emptiness, not the deep values later hashed). [5](#0-4) 
2. This queues the row into `unhandled_private_payments` and later triggers `handleSavedPrivatePayments()`, which calls `validateAndSave()`. [6](#0-5) 
3. `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws inside the `try`; the `catch` block deletes the row and calls `cb()` — but control falls through to invoke `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again on the same stale data, causing a second invocation of the `async.each` iteratee callback and duplicated side effects (`deleteHandledPrivateChain` no-op, event emissions, premature mutex unlock). [7](#0-6)

function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	return stringify(obj);
}
