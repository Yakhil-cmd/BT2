### Title
Fork-origin pull requests are treated identically to same-repo branches by `provision?`, letting an unreviewed fork's `shipit.yml` drive deploy/task commands - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` decides whether to create a `Shipit::ReviewStack` using only `repository.provisioning_behavior_allow_all?` (or label checks), never inspecting `params.pull_request.head.repo.fork`. `ReviewStackAdapter#create!` then persists `branch: params.pull_request.head.ref` verbatim with no record of fork provenance, so a stack backed by an attacker-controlled branch/fork ref is created from a single unauthenticated webhook.

### Finding Description
The intended binding is: `branch a repository maintainer authored/reviewed == branch whose shipit.yml commands are later executed by Command#start via CacheDeploySpecJob/deploy/task/review.checks`. This binding is broken because:

- `provision?` only checks `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?` (or label conditions) - it never reads `pull_request.head.repo.fork`: [1](#0-0) 

- `ReviewStackAdapter#create!`/`#stack_attributes` writes `branch: params.pull_request.head.ref` and `environment: "pr#{params.number}"` with no fork/owner field, and no other attribute on `Shipit::ReviewStack` records `fork == true`: [2](#0-1) 

- `CacheDeploySpecJob#perform` later checks out the stack's last reachable commit via `Commands.for(stack)` / `StackCommands#with_temporary_working_directory`, which clones/fetches using `@stack.repo_git_url` (the base repository's remote) and `@stack.branch` (the attacker-supplied ref string), then builds `DeploySpec::FileSystem` from whatever `shipit.yml` is found in that checkout: [3](#0-2) [4](#0-3) 

- No guard in `respond_to_pull_request_opened?`, `verify_signature`/webhook handling, or `ExplicitParameters` schema rejects or flags fork PRs; the schema only requires `head.sha`/`head.ref`, never reads/validates `head.repo.fork`: [5](#0-4) 

Attacker flow: attacker forks the tracked repository, pushes a branch with a malicious `shipit.yml` (e.g. `deploy:` or `review: {checks: ...}` steps), opens a PR against the base repo (`provisioning_behavior_allow_all`). GitHub emits `pull_request` `opened` webhook (a webhook the attacker doesn't need to forge - GitHub sends it because they legitimately opened the PR). `OpenedHandler#process` creates a `Shipit::ReviewStack` whose `branch` is the fork's ref. `CacheDeploySpecJob` (queued via `Shipit::ReviewStackProvisioningQueue.add(stack)`) fetches that ref/commit and caches whatever `shipit.yml` it finds, which is later executed by `Command`/`PTY.spawn` during deploy/task/`review.checks` runs on the stack.

### Impact Explanation
This is Critical: RCE on the deploy host via arbitrary `deploy`/`task`/`review.checks` commands defined in a `shipit.yml` the attacker fully controls and that no maintainer has reviewed. The blast radius is scoped to repositories configured "Allow All" (the docs even recommend this as the default: "most likely Allow All"), but any unprivileged GitHub user able to open a PR against such a repository can trigger it, repeatably, once per PR number.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior_allow_all?` (or `allow_with_label`/`prevent_with_label` with attacker-controlled labeling permission, though "Allow All" is the most direct path and is explicitly the documented recommended default). No Shipit session, API token, or GitHub secret is required - only the ability to fork the repo and open a PR, which is available to any GitHub user with read access to a public repository. This makes the attack low-cost and highly feasible for any public repo running Shipit review stacks with default settings.

### Recommendation
Read `params.pull_request.head.repo.fork` in the webhook schema, and either (a) refuse to auto-provision (or auto-run cached deploy specs) for fork-originated PRs unless a maintainer explicitly re-labels/approves them, or (b) record fork provenance on `Shipit::ReviewStack`/`PullRequest` and gate `CacheDeploySpecJob`/deploy execution behind an explicit maintainer approval step (e.g., require a maintainer-applied label or `/ok-to-test`-style comment) before treating the fork's `shipit.yml` as trusted, mirroring the "allow_with_label" opt-in pattern but keyed off fork status rather than just labels.

### Proof of Concept
minitest plan (added under `test/models/shipit/webhooks/handlers/pull_request/`):
1. Configure `shipit_repositories(:shipit)` with `review_stacks_enabled: true, provisioning_behavior: :allow_all`.
2. Take `payload_parsed(:pull_request_opened)` and set `payload["pull_request"]["head"]["repo"]["fork"] = true` and `payload["pull_request"]["head"]["ref"] = "attacker-fork-branch"`.
3. Call `OpenedHandler.new(payload).process`.
4. Assert the binding is broken:
   - `assert_equal "attacker-fork-branch", repository.review_stacks.last.branch` (fork ref accepted identically to a same-repo branch).
   - `assert_not Shipit::ReviewStack.column_names.include?("fork")` and/or `assert_nil repository.review_stacks.last.attributes["fork"]` (no attribute anywhere records fork provenance).
   - `assert_enqueued_with(job: CacheDeploySpecJob, args: [repository.review_stacks.last])` or equivalent, showing the deploy-spec caching pipeline is triggered for the fork branch exactly as it would be for a trusted branch.
