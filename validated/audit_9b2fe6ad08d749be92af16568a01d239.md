### Title
Webhook signature verified against the payload's `repository.owner.login` while the acted-upon repository is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the signature with by reading `repository.owner.login` (falling back to `organization.login`) out of the untrusted, attacker-supplied JSON body itself. Once verification passes, the event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve the actual `Repository`/`Stack` to mutate using a *different* field from the same body, `repository.full_name`. Nothing ties these two fields together, so the identity that authorizes the request and the identity that is acted upon can diverge — the exact "binding broken by acting on a field never covered by verification" pattern described in the report, applied to organization-vs-repository trust instead of contractor/subcontractor identity.

### Finding Description
- `verify_signature` derives the signing organization purely from request body content: [1](#0-0) [2](#0-1) 
- That organization is used only to look up which `GitHubApp`/secret to check the HMAC against: [3](#0-2) 
- `verify_webhook_signature` **passes unconditionally when no webhook secret is configured** for that organization — and the setup docs explicitly mark the webhook secret as optional per-organization: [4](#0-3) [5](#0-4) 
- After verification, handlers ignore `repository.owner.login`/`organization.login` entirely and instead resolve the target repository from `repository.full_name`: [6](#0-5) 
- `PushHandler` uses that repository lookup to trigger `sync_github` on all matching stacks/branches: [7](#0-6) 
- `StatusHandler` uses `params.sha` (also unrelated to `repository.owner.login`) to look up commits across the whole DB and writes CI status that can gate/trigger continuous deployment: [8](#0-7) 

In a multi-organization deployment (`Shipit.github_organizations`/`github_app_config`), if any one configured organization has no `webhook_secret` set, an unauthenticated attacker can send a webhook whose `repository.owner.login`/`organization.login` names that unsecured organization (satisfying `verify_signature`), while `repository.full_name` and `sha` point at a completely different, secured organization's repository/commits. The equality the code implicitly assumes — `repository.owner.login == owner_of(repository.full_name)` — is never checked, so it can be forged. This is a structural analog of the audit finding: a value used to satisfy an authorization check (contractor identity / signing organization) is not the same value the subsequent state-changing logic operates on (subcontractor identity / target repository), and the code never re-validates the binding before acting.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary named in scope, and can produce an unauthorized deploy: `PushHandler` can force `Stack#sync_github` to run for an unrelated stack, and `StatusHandler` can inject/forge commit statuses (`Commit#create_status_from_github!`) for arbitrary commits/repositories tracked by Shipit, which can influence continuous-deployment gating (`continuous_deliver`) — i.e. an unauthorized deploy trigger without any GitHub credentials, `ApiClient` token, or Shipit session, satisfying the Critical "unauthorized deploy" bar.

### Likelihood Explanation
Requires only that the operator's Shipit instance is configured with more than one GitHub organization (the documented multi-tenant `github:` config schema keyed by org) and that at least one of those organizations was set up without a `webhook_secret` (explicitly documented as optional). This is a realistic operational misconfiguration rather than a theoretical one, and the attack itself needs no credentials — just knowledge of a public GitHub org name and the `/webhooks` endpoint.

### Recommendation
Cross-check consistency between the field used for signature-organization selection (`repository.owner.login` / `organization.login`) and the field handlers use to resolve the target repository (`repository.full_name`) before processing; reject the webhook if they disagree. Additionally, do not allow `verify_webhook_signature` to silently return `true` when no secret is configured for an organization that owns tracked repositories — require an explicit secret for every organization that has repositories registered in Shipit, or fail closed instead of open in `lib/shipit/github_app.rb#verify_webhook_signature`.

### Proof of Concept
1. Operator configures `secrets.github` with two orgs: `attacker-org` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`, hosts a tracked `victim-org/app` repository/stack).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" }
}
```
with any/no `X-Hub-Signature` value.
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` → `verify_webhook_signature` returns `true` unconditionally (no secret configured) — see `app/controllers/shipit/webhooks_controller.rb` lines 24-30 and `lib/shipit/github_app.rb` lines 76-83.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/app")` (via `app/models/shipit/webhooks/handlers/handler.rb` lines 32-38) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — see `app/models/shipit/webhooks/handlers/push_handler.rb` lines 12-17 — with no valid signature ever verified for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
