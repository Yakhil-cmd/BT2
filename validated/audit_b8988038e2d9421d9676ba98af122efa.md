### Title
Membership-webhook authorization bypass via mismatched webhook-signature identity and target-team identity - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to use for HMAC verification based on a payload field (`organization.login` for organization-scoped events), but the handler that actually mutates state (`MembershipHandler`) writes to a `Team` record looked up only by an attacker-supplied `team.id`, independent of which organization's secret was used to authenticate the request. Combined with the documented fact that `webhook_secret` is optional and `verify_webhook_signature` returns `true` unconditionally when it is unset, an attacker who can trigger delivery to an organization with no configured secret can forge a `membership` event that adds an arbitrary GitHub login to a `Team` record that is otherwise used to gate access via `Shipit.github_teams`.

### Finding Description
Signature verification derives the authenticating identity from the payload itself, not from any externally trusted channel: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `organization.login` for organization-scoped events such as `membership`, and `Shipit.github(organization: repository_owner)` selects the corresponding app config's `webhook_secret` for HMAC validation.

Verification is a no-op when that organization's `webhook_secret` is not configured, which is an explicitly supported, valid configuration in this engine (not merely documentation): [3](#0-2) [4](#0-3) 

Once the request passes (trivially, for an org with `webhook_secret: nil`), `MembershipHandler#process` uses attacker-controlled fields to locate/create a `Team` and add a member, with no cross-check that the `organization.login` used for authentication matches the `organization` the resulting `Team` object actually belongs to: [5](#0-4) 

`find_or_create_team!` looks the `Team` up solely by `github_id` (the attacker-supplied `team.id`): [6](#0-5) 

If a `Team` with that `github_id` already exists — e.g. a team an administrator legitimately configured via `Shipit.github_teams` for authorization purposes — `find_or_create_by!` simply finds it (the initializer block only runs on creation), and `team.add_member(member)` appends an attacker-chosen `User` (itself resolved via `User.find_or_create_by_login!(params.member.login)`, also attacker-controlled) to that authorized team: [7](#0-6) 

Authorization is subsequently granted purely from local `Team`/`memberships` records: [8](#0-7) [9](#0-8) 

The binding that should hold is: `organization` whose secret authenticated the request == `organization` of the `Team` being mutated by the same request. Before the attacker's request, this equality is trivially true because legitimate GitHub-originated webhooks are internally consistent. After the attacker's forged request (sent to an organization endpoint with no `webhook_secret` configured), the equality is broken: the request is "authenticated" as belonging to an unsecured/attacker-influenced organization, yet the `Team` record it mutates (matched purely by numeric `github_id`) can belong to a completely different, secured organization that is actually used for `Shipit.github_teams` authorization.

### Impact Explanation
This is an unauthenticated escalation into `Shipit.github_teams` authorization: an attacker with no Shipit session, no API token, and no knowledge of any webhook secret for the *target* organization can add themselves (or any known GitHub login) as a member of a `Team` that grants access to the whole Shipit instance, provided any one configured GitHub organization in the deployment has no `webhook_secret` set — an explicitly supported configuration. This matches the accepted High-severity impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires: (1) a multi-org or single-org Shipit deployment where the targeted organization's app config has `webhook_secret` unset (a supported, documented default), and (2) knowledge of the numeric GitHub `team.id` of an authorized team, which is discoverable via GitHub's public team/organization APIs or UI in many setups. No repository write access, GitHub App credentials, or Shipit session are needed — only network access to the public `/webhooks` endpoint.

### Recommendation
Do not select the verification secret from an attacker-controlled payload field alone; additionally, cross-validate that the `organization`/`repository` identity used for verification matches the `organization` value used by handlers when mutating `Team`/`Repository` state (e.g. re-derive and compare `params.organization.login` against the persisted `Team#organization` before mutating an existing record, and refuse organization mismatches). Consider making `webhook_secret` mandatory (fail closed rather than `return true` when absent) as defense in depth.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs: `secured-org` (with `webhook_secret` set, and whose team `Engineering` is listed in `Shipit.github_teams`, already synced locally with `github_id: 555`), and `unsecured-org` (with `webhook_secret` left blank, per the supported config shown in `config/secrets.development.example.yml`).
2. Attacker sends an unsigned `POST /webhooks` with header `X-Github-Event: membership` and body:
   ```json
   {
     "action": "added",
     "team": { "id": 555, "name": "Engineering", "slug": "engineering", "url": "https://api.github.com/teams/555" },
     "organization": { "login": "unsecured-org" },
     "member": { "login": "attacker-github-login" }
   }
   ```
3. `WebhooksController#verify_signature` resolves `repository_owner` to `unsecured-org`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
4. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 555)`, finds the pre-existing `Engineering` team (created for `secured-org`), and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, adding the attacker to the authorized team without ever contacting `secured-org`'s webhook secret.
5. When `attacker-github-login` subsequently authenticates via the real GitHub OAuth flow, `User#authorized?` finds the local membership row and grants full access to the Shipit instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        end
```
