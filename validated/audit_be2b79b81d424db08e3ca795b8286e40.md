### Title
Cross-repository forged `status` webhook writes a blocking `Status` to any commit sharing the same `sha`, falsely triggering `Commit#blocked?` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository scoping, unlike `PushHandler` which scopes lookups through `stacks` (derived from `payload.dig('repository','full_name')`). An attacker who owns any repository that shares a webhook-signing GitHub App installation (e.g., a public fork of the victim repository, which retains identical commit SHAs) can send a legitimately-signed `status` webhook for their own repo, and Shipit will attach that status to **every** `Commit` record across **every** stack whose `sha` matches - including the victim's, falsely tripping `Commit#blocked?`.

### Finding Description
Broken binding: `Status recorded against victim commit == status originating from victim's own repository/CI`. This is false.

Path:
1. `WebhooksController#verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`) [1](#0-0) [2](#0-1) . This check only proves the request came from *some* organization/repo that the configured GitHub App is installed on (e.g., the attacker's own fork) - it says nothing about which commit or repository the `sha`/`context` in the payload actually belongs to.
2. `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
No filtering by `repository_name`/`stacks` is performed here, in contrast to `PushHandler#process`, which correctly scopes to `stacks.not_archived.where(branch:)` derived from `payload.dig('repository','full_name')` [4](#0-3) [5](#0-4) .
3. `Commit#create_status_from_github!` writes the status using the **matched commit's own `stack_id`** (the victim's real stack), not any attacker-supplied stack: `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) , `Status.replicate_from_github!` [7](#0-6) .
4. `Commit#blocked?` then evaluates `stack.commits.reachable...any?(&:blocking?)` for the victim's stack, which is influenced entirely by this attacker-injected `Status` row [8](#0-7) , and `blocking?`/`state` are delegated from `status` [9](#0-8) .

Exploit: attacker forks the victim's public repository (fork commits share identical SHA-1 hashes with upstream until divergence). Attacker's fork has the same GitHub App installed (a public GitHub App can be installed by any GitHub user on their own repositories, no privilege on the victim's org required). Attacker POSTs (or triggers via the GitHub API against their own repo, which GitHub itself will webhook to Shipit) a `status` event with `state: failure`, `context` matching one of the victim's configured `blocking_statuses`/`required_statuses`, and `sha` equal to the shared commit. `verify_signature` passes because it only checks that *a* known organization/app installation signed the request - it never checks that `repository.full_name` in the payload corresponds to the `sha` supplied. `StatusHandler` then attaches this forged `failure` status to the victim's commit, and `blocked?` becomes true for all of the victim's descendant commits, blocking their real deploy pipeline.

`drop_unhandled_event`, `ExplicitParameters` schema (`requires :sha`, `:state`), and model validations on `Status` (`state` enum) do not prevent this, because none of them check that the `sha` belongs to a commit that is actually part of the repository named in the payload.

### Impact Explanation
This is a genuine cross-repository/cross-tenant write: an attacker with no access to the victim's stack, repository, or `webhook_secret` can inject an authoritative-looking CI failure/error status into the victim's commit and stack, causing `Commit#blocked?`/`deployable?` to falsely report blocked/non-deployable state. This can stall or sabotage the victim's release pipeline (denial of legitimate deploys) and, combined with any downstream logic trusting `blocked?`/`status` to decide automated behavior (merges, continuous delivery gating, dashboards), constitutes an unauthorized cross-repository mutation. This matches the "payload for one repository mutating another's stack/commit" Critical category. It is fully repeatable for any repo that shares SHAs with a target - realistically forks of public repositories, which is common.

### Likelihood Explanation
Preconditions are modest: (1) the target commit's SHA must exist identically in some repository the attacker controls (trivially achievable by forking a public repo before it diverges, or by cherry-picking identical trees/parents to reproduce a SHA), (2) the attacker's repo/org must have the same Shipit-integrated GitHub App installed and receive `status` webhooks for it - installable by the attacker on their own fork without any victim cooperation, and (3) the victim stack must list the forged `context` as a blocking/required status, which is normal configuration. Attacker cost is low (fork + one API call to set a commit status on their own repo, or a raw webhook if they can forge a request using GitHub's own signing for their installation). No secrets, sessions, or privileged roles are required.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up records purely by SHA) to only the commits belonging to stacks resolved via the payload's `repository.full_name`, mirroring `PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `Handler#stacks`/`repository_name` helpers, so a status can never be attached to a commit outside the repository that actually emitted the webhook.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`:
```ruby
test ":status webhook from a different repository must not write a status onto a commit belonging to another repository" do
  victim_commit = shipit_commits(:first) # belongs to stack whose repository is "shopify/shipit-engine"
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => victim_commit.stack.blocking_statuses.first || 'ci/travis',
    'repository' => { 'full_name' => 'attacker/forked-shipit-engine', 'owner' => { 'login' => 'attacker' } }
  }

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate a valid signature for attacker's own org/app installation
  request.headers['X-Github-Event'] = 'status'

  assert_no_difference 'victim_commit.statuses.count' do
    post :create, body: attacker_payload.to_json, as: :json
  end

  refute victim_commit.reload.blocked?
end
```
Binding assertion: `victim_commit.statuses.count` unchanged and `victim_commit.blocked? == false` after the attacker's cross-repository webhook, proving the fix. Against current code (`Commit.where(sha: params.sha)` with no repository scoping), this test fails because the forged status is written to `victim_commit` and can flip `blocked?` to `true`.
