### Title
Cross-repository CI-status forgery via SHA-only commit lookup in `StatusHandler` breaks the webhook-org-authenticated vs. stack-written binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The GitHub `status` webhook is authenticated per-organization (`WebhooksController#verify_signature` picks the GitHub App/secret using `repository.owner.login`), but the effect of the event — writing a `Status` to a `Commit` — is dispatched purely by commit SHA with no re-check that the commit actually belongs to the repository/stack that the authenticated organization owns.

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC against using data taken directly from the request body: `repository_owner` (`params.dig('repository', 'owner', 'login')`, falling back to `organization.login`). [1](#0-0) [2](#0-1) 

Once the signature validates for that organization, `StatusHandler#process` is invoked with the full parsed payload. It never re-validates that the target commit belongs to a stack under the *authenticated* organization/repository. Instead it looks up commits **globally, by SHA alone**: [3](#0-2) 

Compare this to `Handler#stacks`/`Handler#repository_name`, which every other handler (e.g. `PushHandler`) uses to scope its side effects to `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [4](#0-3) [5](#0-4) 

`StatusHandler` is the only default handler that bypasses this repository scoping — `Commit.where(sha: params.sha)` matches any commit row in the entire database sharing that 40-character SHA, across every stack/repository ever synced by Shipit, regardless of which organization the signature was verified against.

The equality that should hold is:
```
organization authenticated by HMAC (repository.owner.login)
   ==
organization/repository whose Commit rows are mutated (stack.github_repo_name for the matched Commit)
```
`StatusHandler` breaks this: the left side is checked once at the controller layer, but the right side is determined solely by an attacker-suppliable SHA string that can coincidentally or intentionally collide with a commit already tracked under a completely different organization's stack.

`Commit#create_status_from_github!` → `add_status` writes a new `Status` row, updates `Commit#status` (via `Status::Group.compact`), and — critically — feeds directly into `Commit#deployable?`: [6](#0-5) [7](#0-6) [8](#0-7) 

`deployable?` gates continuous deployment (`schedule_continuous_delivery`) and merge-queue processing (`stack.schedule_merges` inside `add_status`): [9](#0-8) [10](#0-9) 

### Impact Explanation
An entity that legitimately controls a GitHub organization/repository onboarded into this Shipit instance (and therefore knows/can trigger a validly-signed `status` webhook for that org) can forge a `status` event whose `sha` is a commit SHA that happens to also be tracked under a **different** organization's stack (e.g. via a shared upstream commit, a forked repository, or simply a 40-hex-char SHA an attacker chooses that matches a known commit hash disclosed publicly by Shipit's UI/API for another stack). The forged event is authenticated correctly (own org's secret, `422` is never returned) yet it writes a fabricated `success`/`failure` status onto a `Commit` belonging to a stack outside the attacker's authority. If continuous deployment or CI-gated merges/deploys are configured on the victim stack and this is the last blocking status, it can flip `deployable?` to `true` and trigger an unauthorized deploy or merge of the victim's stack — satisfying the "unauthorized deploy" Critical impact criterion, without requiring an API token, session, or the victim's webhook secret at any point.

### Likelihood Explanation
Exploitation requires: (1) the attacker administers at least one organization/repository already connected to the same Shipit instance (a realistic multi-tenant Shipit deployment scenario, and explicitly documented/supported via "Using Multiple GitHub Applications"), and (2) a SHA collision/reuse between the attacker's own tracked commits and a targeted victim stack's commit (trivially achievable if both repos share history via a fork, submodule, or common upstream — a common real-world occurrence). No secret material belonging to the victim org is ever needed. This is a moderate-likelihood, high-impact scenario in any Shipit deployment onboarding multiple untrusted or semi-trusted GitHub organizations.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository derived from the authenticated payload (mirroring `Handler#stacks`/`repository_name`), e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so that a `status` event can only ever mutate commits belonging to the repository named in the same signed payload used to select the organization/verification key, closing the gap between "organization authenticated" and "commit rows written."

### Proof of Concept
1. Attacker owns/administers `attacker-org/repo-x`, which is connected to the shared Shipit instance and has a valid GitHub App installation + webhook secret for `attacker-org`.
2. Attacker identifies (e.g., via Shipit's public stack/commit UI, or via a shared upstream/fork) a commit SHA `S` that is tracked as a `Commit` row under `victim-org/repo-y`'s stack in the same Shipit instance.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/repo-x" }
}
```
4. Attacker signs the raw body with `attacker-org`'s known webhook secret and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org` and validates successfully (this is the attacker's own legitimate secret).
6. `StatusHandler#process` executes `Commit.where(sha: "S")`, which matches the commit belonging to `victim-org/repo-y`, and calls `create_status_from_github!`, writing a fabricated `success` status onto the victim's commit — potentially unblocking `deployable?` and triggering continuous deployment or a merge-queue action on `victim-org/repo-y`'s stack, entirely outside the attacker's authorized organization.
