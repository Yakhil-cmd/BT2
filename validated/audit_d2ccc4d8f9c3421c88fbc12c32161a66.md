### Title
Cross-repository status write via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table (`Commit.where(sha: params.sha)`) instead of scoping to the repository that authenticated the webhook, unlike sibling handlers such as `PushHandler` which scope through the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`). Combined with `Commit#deployable?` short-circuiting on `stack.ignore_ci?`, a `release/gate` status delivered for a SHA that happens to exist in more than one repository/stack can flip deployability/blocking state for a stack that never authenticated that webhook.

### Finding Description
The broken binding: the webhook signature check binds the request to `repository_owner` (`params.dig('repository','owner','login')`) via `Shipit.github(organization: repository_owner).verify_webhook_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-30), but `StatusHandler#process` never re-checks that binding when writing state — it writes to every `Commit` row whose `sha` column matches, regardless of which repository/stack owns that row:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

By contrast, the base `Handler` class exposes a repository-scoped `stacks` accessor (`Repository.from_github_repo_name(repository_name)&.stacks`) [2](#0-1)  that other handlers, e.g. `PushHandler#process`, correctly use to filter by the authenticated repository before mutating any records [3](#0-2) . `StatusHandler` does not use `stacks` at all, so the equality the system is supposed to maintain — "the repository that authenticated the webhook == the repository/stack whose commit rows are mutated" — does not hold for `StatusHandler`.

`create_status_from_github!` appends a new `Status` row and re-evaluates the commit's aggregate `status`/deployability via `add_status` [4](#0-3) . If the victim stack has `ignore_ci` enabled, `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` — CI status is irrelevant to deployability once `ignore_ci?` is true [5](#0-4) , but `blocked?`/merge scheduling still consult `blocking_statuses`/`required_statuses` which are populated from arbitrary written `Status` rows, so injecting a `failure` status for `release/gate` on the shared SHA can still change blocking/merge behavior (`stack.schedule_merges if new_status.pending? || new_status.success?`, `Hook.emit(:deployable_status, ...)`) on the victim stack.

Exploit precondition: two distinct repositories tracked as (possibly different) Shipit stacks must, at some point, contain a `Commit` row with the identical SHA (e.g., a fork/mirror relationship, or a monorepo/submodule scenario, or shared history between a public upstream repo and a downstream import). The attacker only needs the ability to trigger a real, GitHub-signed `status` webhook from a repository they control (or any repository whose GitHub App/webhook secret they can trigger delivery from, per normal repo permissions) with `context: release/gate`, `state: failure`, and a `sha` that also exists in the victim's stack. `verify_signature` only proves the payload came from GitHub for `repository_owner`'s org/app — it does not, and cannot, prove that the specific `sha` inside the payload is not also owned by a different tracked repository, since `StatusHandler` throws that information away by querying `Commit` globally.

### Impact Explanation
An attacker who can generate a legitimately-signed `status` webhook (from any repo/org they have push/CI access to, which is registered with the same Shipit instance) can write `Status` rows onto `Commit` records belonging to a completely different stack whenever a SHA collision exists across repositories. This directly matches the "payload for one repository mutating another's stack/commit" Critical impact category: it can flip a required "release/gate" context to `failure`, potentially blocking deploys/merges on a victim stack, or (in other configurations) marking success and unblocking a deploy the victim never approved — all without any GitHub or Shipit privilege on the victim stack. The blast radius depends on how commonly SHAs are shared across repositories tracked by the same Shipit install (forks/mirrors/monorepo split are common patterns), so it is a plausible, not universal, cross-tenant condition.

### Likelihood Explanation
Exploitability requires: (1) the attacker can get a genuinely GitHub-signed `status` event delivered to the Shipit `/webhooks` endpoint (achievable for any repo they administer/have CI on, no Shipit secrets needed — consistent with the "unprivileged attacker" definition), and (2) a commit SHA collision between the attacker's repository and the victim's tracked stack. Condition (2) is the limiting factor — it is not universal but is realistic in fork/mirror/monorepo topologies, which are common enough in real Shipit deployments (Shipit is designed to track multiple stacks per repo and multiple repos can share commit ancestry). Given (2), the attack is trivially repeatable and costs the attacker nothing beyond normal GitHub repo access.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `PushHandler`/the `stacks` helper, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently, join `Commit` to `Stack`/`Repository` via `stacks` and filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring a status can only ever be written onto commits belonging to stacks whose repository matches `repository_name`/`repository_owner` from the authenticated payload.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repository_a` ("attacker/repo") and `repository_b` ("victim/repo"), each with a `Stack` (`stack_a`, `stack_b`), `stack_b.ignore_ci = true`, `stack_b.required_statuses = ['release/gate']`.
2. Create `Commit.create!(stack: stack_a, sha: 'deadbeef'*5)` and `Commit.create!(stack: stack_b, sha: 'deadbeef'*5)` — same SHA, different stacks (simulating a fork/mirror SHA collision).
3. Build payload: `{ repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } }, sha: 'deadbeef'*5, context: 'release/gate', state: 'failure' }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, as permitted for this scoped model-level PoC).
5. Assert: `stack_b.commits.find_by(sha: 'deadbeef'*5).status.state == 'failure'` and that this status/blocking state changed even though the payload's `repository.full_name` was `attacker/repo`, never `victim/repo` — i.e., `commit_b.status.state` (before: unknown/success) != `commit_b.status.state` (after: failure), proving `repository_that_authenticated == repository_whose_commit_mutated` is false.
6. Contrast with `PushHandler`, which under an equivalent cross-repo payload does **not** touch `stack_b` because it scopes via `stacks`.
