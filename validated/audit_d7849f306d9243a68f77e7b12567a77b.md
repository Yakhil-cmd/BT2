### Title
CCMenu tokens are never bound to their originating stack, allowing cross-repository stack-status reads - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `permissions: %w[read:stack]` but never sets `stack_id`, so the token is stack-agnostic despite being generated from a stack-specific URL. `Api::CCMenuController` compounds this by overriding `#stack` to call `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scoping helper in `BaseController` that would otherwise restrict a client to its bound stack.

### Finding Description
The claimed binding `client.stack_id == stack.id` is false on both sides of the trace, and it stays false — that is exactly the bug.

In `app/controllers/shipit/ccmenu_url_controller.rb:15-18`, the client is created with: [1](#0-0) 
`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` or `stack_id:` attribute is passed, even though `stack` (from `params[:stack_id]`) is computed in the same controller. `ApiClient` does have a `stack` association (`belongs_to :stack, optional: true`, `app/models/shipit/api_client.rb:8`), but it is never populated here, so `client.stack_id` is always `nil` for every CCMenu client any user creates, regardless of which stack's URL page triggered creation.

`Api::CCMenuController#show` (`app/controllers/shipit/api/ccmenu_controller.rb:22-31`) authenticates via `authenticate_api_client`, which sets `@current_api_client` from the token, then enforces only `require_permission :read, :stack` — a check against the client's `permissions` array, not against any stack binding (`app/controllers/shipit/api/base_controller.rb:82-84`). Crucially, `CCMenuController` defines its own `stack` method (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) that calls `Stack.from_param!(params[:stack_id])` directly — it does not go through `BaseController#stacks`, which is the only place that would apply `current_api_client.stack_id` scoping (`app/controllers/shipit/api/base_controller.rb:74-76`). Even if `ApiClient#stack_id` were populated, this override would still ignore it.

Attacker flow: an unprivileged logged-in user visits `/ccmenu/<stack-A-id>`, gets a `CCMenuController::show` URL with `?token=<t>` where `<t>` verifies to their `ApiClient` id. That same token, submitted as `?token=<t>` against `/api/stacks/<stack-B>/ccmenu.xml` for any other stack B, passes `authenticate_api_client` (token verifies to the same client) and `require_permission!(:read, :stack)` (client still has `read:stack` in `permissions`), and `stack` resolves directly to stack B via `Stack.from_param!`. The response renders stack B's deploy status.

No existing guard prevents this: `require_permission` only checks the permissions array, not stack identity; `authenticate_api_client` only verifies the token signature; `stacks`/`from_param!` scoping is bypassed entirely by the controller's own `stack` override.

### Impact Explanation
Any authenticated Shipit user (even with zero team memberships when `Shipit.github_teams` is empty) can mint a `read:stack` CCMenu token from one stack's page and reuse it to read deploy/task status (via `Api::CCMenuController#show`'s XML rendering of `stack.deploys_and_rollbacks.last`) for *any* other stack in the installation, including private/other-team repositories. This is an unauthenticated-scope escalation into cross-repository read of stack state, matching the "High - escalation... unauthenticated read of stack state" category. It is fully repeatable: the token remains valid indefinitely (message-verifier signed, no expiry) and works against every stack, not just the one it was minted from.

### Likelihood Explanation
Preconditions are minimal and match the given precondition: a logged-in Shipit user with no special role, visiting `/ccmenu/*stack_id` for any stack they can view, then replaying the returned token against a different stack's CCMenu endpoint. No secrets, GitHub App keys, or webhook access are needed — just an ordinary authenticated session and the ability to change a URL parameter. This is trivially reproducible and costs a single HTTP GET followed by another HTTP GET.

### Recommendation
Set `stack: stack` (or `stack_id: stack.id`) when creating/finding the `ApiClient` in `CCMenuUrlController#client`, scope `find_or_create_by!` on `stack:` as well so distinct stacks get distinct clients, and change `Api::CCMenuController#stack` to use the inherited `stacks.from_param!(params[:stack_id])` (removing the private override) so `BaseController#stacks`'s `current_api_client.stack_id` scoping is actually applied.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (new/extended test)
test "ccmenu token is not bound to the originating stack and works cross-stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # any other fixture stack
  session[:user_id] = shipit_users(:walrus).id

  get :fetch, params: { stack_id: stack_a.to_param }
  assert_response :ok

  client = Shipit::ApiClient.last
  assert_nil client.stack_id # binding is broken: never set

  token = client.authentication_token

  # Reuse the same token against a different stack's CCMenu endpoint
  get "/api/stacks/#{stack_b.to_param}/ccmenu.xml", params: { token: token }
  assert_response :ok # should be :forbidden/:not_found if properly scoped
end
```
This demonstrates `ApiClient.last.stack_id` is `nil` after `#fetch`, and that the resulting `authentication_token`, minted from stack A's page, successfully authorizes a read against stack B via `Api::CCMenuController#show`.
