### Title
Reversed lock/connection acquisition order in `tryToAdvanceStabilityPointForCatchupAATrigger` can deadlock stability advancement - (File: network.js)

### Summary
Ocore's own code documents a strict lock-acquisition order to avoid deadlocks around stability advancement: "always first obtain a `handleJoint` lock, then a db connection" [1](#0-0) . However, `tryToAdvanceStabilityPointForCatchupAATrigger()` in `network.js`, which is invoked whenever an incoming unit is provisionally rejected during catch-up as a "possible AA" trigger, does the opposite: it takes a database connection from the pool first, and only afterward calls into `determineIfStableInLaterUnitsAndUpdateStableMcFlag()`, which internally tries to acquire the `handleJoint` mutex while that connection is still held.

### Finding Description
When a unit is received while `bCatchingUp` is true and validation fails with `"possible AA"`, `network.js` calls `tryToAdvanceStabilityPointForCatchupAATrigger(objJoint)` from the `ifTransientError` callback [2](#0-1) .

That function immediately takes a pooled DB connection and begins a transaction before calling the stability-advancement routine: [3](#0-2) 

`determineIfStableInLaterUnitsAndUpdateStableMcFlag()`, once it determines the target unit is stable relative to the supplied free units, explicitly acquires the `handleJoint` mutex — and the surrounding comment states the intended safe order is *lock first, then connection*: [4](#0-3) 

This is exactly the inverted ordering the comment warns against: `tryToAdvanceStabilityPointForCatchupAATrigger` holds a pool connection and then blocks on the `handleJoint` mutex, while the normal unit-processing path (`handleJoint` in `network.js`) holds the `handleJoint` mutex first and then needs to acquire a pool connection to validate/write the unit (e.g. via `writer.saveJoint`, which itself waits on `db.takeConnectionFromPool`/write-lock semantics). With a bounded connection pool (`MAX_CONNECTIONS` in `sqlite_pool.js`/`mysql_pool.js`), if the pool is saturated by units still being processed under the `handleJoint` lock and one of those connections happens to be consumed by `tryToAdvanceStabilityPointForCatchupAATrigger` (which is itself blocked waiting for the very same lock that the pending `handleJoint` holder needs to finish and release), the two lock/resource acquisitions can form a classic AB-BA cycle: thread A holds "connection" and waits on "handleJoint lock"; thread B holds "handleJoint lock" and waits on "connection". This is the direct structural analog of the reported "attestation deadlocks" bug class — a circular wait between two resources needed to advance the fork-choice/stability state, causing that part of consensus processing to permanently stall rather than crash.

### Impact Explanation
If this deadlock is triggered, the node stops making progress: the `handleJoint` mutex, which serializes ALL unit acceptance (from network and light clients, `handlePostedJoint`/`handleOnlineJoint`), is permanently blocked, and the connection pool slot is permanently pinned in a `BEGIN`ed transaction. This freezes the node's ability to validate and store new units, i.e. the node becomes "unable to confirm new units," matching the required High-impact class for this analog category. Because catch-up ("possible AA" during `bCatchingUp`) is a state any syncing node naturally passes through when it receives units referencing not-yet-stabilized AA triggers, this is reachable by ordinary unit posting/relay activity, not by a privileged actor.

### Likelihood Explanation
Triggering `tryToAdvanceStabilityPointForCatchupAATrigger` only requires: (1) the local node to be catching up (`bCatchingUp = true`), and (2) receiving a unit whose validation fails with the specific `"possible AA"` transient error, which occurs naturally for units referencing an AA trigger unit that has not yet been executed. Both conditions are reachable during normal network operation/catch-up and do not require a malicious peer, though the deadlock additionally requires connection-pool exhaustion/contention timing (concurrent unit processing saturating `MAX_CONNECTIONS`), which is more likely to manifest under load or on connection-pool-constrained deployments (e.g. small `MAX_CONNECTIONS` configurations). This makes the likelihood moderate rather than trivial to hit on every run, but it is a real, code-provable ordering violation rather than a hypothetical.

### Recommendation
In `tryToAdvanceStabilityPointForCatchupAATrigger`, acquire the `handleJoint` mutex before taking a DB connection from the pool, consistent with the documented invariant in `main_chain.js`. Alternatively, refactor `determineIfStableInLaterUnitsAndUpdateStableMcFlag` so that any connection passed in by a caller that has not already obtained the `handleJoint` lock is released (or the call restructured to not require holding an external connection) prior to attempting `mutex.lock(["handleJoint"], ...)`. Add an assertion or lint rule verifying no code path takes a pool connection before acquiring `handleJoint`, to prevent regressions of this invariant.

### Proof of Concept
1. Configure a node with a small `MAX_CONNECTIONS` pool (or run under concurrent load such that the pool is fully utilized by ongoing `handleJoint` processing).
2. While the node is in `bCatchingUp` state, have units arrive with `sequence` such that validation returns the transient `"possible AA"` error for a unit whose MC parent is unstable — this is a normal occurrence when AA-consuming units are received before their trigger's MCI stabilizes.
3. `ifTransientError` fires and calls `tryToAdvanceStabilityPointForCatchupAATrigger(objJoint)`, which calls `db.takeConnectionFromPool()` and `BEGIN`, consuming one of the last free pool connections [5](#0-4) .
4. Concurrently, other in-flight `handleJoint` calls (holding the `handleJoint` mutex from `network.js`'s main processing path) attempt to obtain a connection to validate/save their joints and block because the pool is exhausted.
5. `tryToAdvanceStabilityPointForCatchupAATrigger`'s call into `determineIfStableInLaterUnitsAndUpdateStableMcFlag` blocks on `mutex.lock(["handleJoint"], ...)` [6](#0-5)  because another handler already holds it (step 4) — producing the circular wait and stalling unit processing network-wide on that node.

Note: I was not able to fully trace every intermediate caller of `writer.saveJoint`/pool acquisition inside the `handleJoint`-locked path within the available search budget to conclusively prove the pool is always exhausted before the mutex is released in production timing; this scenario depends on connection-pool sizing and concurrency, which I could not fully verify against `mysql_pool.js`'s actual `MAX_CONNECTIONS` defaults in this session. A background Devin session with the full repository checked out would be needed to trace the exact concurrency bound and confirm deterministic reproducibility.
