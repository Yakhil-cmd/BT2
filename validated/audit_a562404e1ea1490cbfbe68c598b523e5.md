### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but the stack that gets written to is resolved independently from `repository.full_name` — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification from one payload field, while the handlers that actually mutate stack state (e.g. `PushHandler`) resolve the target `Stack`/`Repository` from a *different* payload field. Because the whole JSON body is attacker-controlled once one is holding any single configured organization's `webhook_secret`, these two fields can be made to disagree, breaking the implicit binding "organization whose secret authenticated the request == organization that owns the repository being written to."

### Finding Description
`verify_signature` picks the GitHub App/secret to check with: [1](#0-0) [2](#0-1) 

`repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, i.e. purely from attacker-supplied JSON, and `Shipit.github(organization: repository_owner)` is used to look up the `webhook_secret` used for the HMAC comparison in `verify_webhook_signature`.

Once the signature check passes, every registered handler (e.g. `PushHandler`) resolves the stack to mutate via `Handler#stacks`, which uses a *separate* field, `repository.full_name`: [3](#0-2) [4](#0-3) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) and the owner encoded in `repository.full_name` (used to pick the acted-upon `Repository`/`Stack`) refer to the same GitHub organization. GitHub itself always sends these consistently, but the webhook body is fully attacker-controlled JSON whose only constraint is matching the HMAC of the *raw body* against one organization's secret — the content of that body, including which repository it claims to describe, is never cross-checked against the organization that authenticated it.

The binding that should hold is:
```
organization_that_authenticated(repository_owner) == organization_owning(repository.full_name)
```
Before the attack (legitimate GitHub traffic) this equality always holds because GitHub itself fills in both fields consistently. An attacker who possesses (e.g. via a leaked/committed `webhook_secret` for organization A — the exact credential-leak bug class in the report) can craft a raw body where `repository.owner.login` = `"orgA"` (so the HMAC validates against orgA's secret) but `repository.full_name` = `"orgB/some-repo"` (so `Handler#stacks` resolves and mutates a stack belonging to a completely different organization, orgB, hosted on the same Shipit instance). This breaks the equality and is a genuine cross-repository/cross-organization write: an attacker credentialed for one tenant can drive webhook-triggered state changes (sync jobs, commit statuses, check-suite refreshes, membership/team changes depending on handler) against any other tenant's stacks.

### Impact Explanation
This crosses the "cross-repository writes" bar explicitly called out as Critical impact: possession of a single organization's `webhook_secret` (a credential class shown to leak in the source-report) is escalated into the ability to forge webhook events against *any other organization's* repositories/stacks managed by the same Shipit deployment, because signature verification and target-resolution are keyed off two independently-controlled JSON fields instead of one verified identity.

### Likelihood Explanation
Requires only that an attacker obtain one organization's `webhook_secret` (out-of-scope items like GitHub App private keys, `api_clients_secret`, or a Shipit session are not needed). Multi-tenant Shipit deployments (multiple `github:` orgs configured in `secrets.yml`, as documented) are the deployment mode most exposed, and no additional privilege beyond one org's webhook secret is required to reach other orgs' stacks.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, after signature verification succeeds, re-derive (or cross-validate) the organization implicated by `repository.full_name` against the organization (`repository_owner`) whose secret validated the signature, and reject the webhook if they diverge.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.*.yml` schema shown in `config/secrets.development.shopify.yml`).
2. Attacker obtains `orgA`'s `webhook_secret` (e.g., it was leaked/checked into source, mirroring the report's finding).
3. Attacker crafts a `push` webhook JSON body with `repository.owner.login = "orgA"` and `repository.full_name = "orgB/some-repo"`, and computes `X-Hub-Signature` using `orgA`'s secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and the HMAC check passes.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/some-repo")` and triggers `stack.sync_github(expected_head_sha: ...)` against `orgB`'s stack — a write triggered by a credential belonging to `orgA`.
