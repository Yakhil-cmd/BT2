### Title
Stack-scoped ApiClient token can read deploy status of any stack via CCMenuController - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` supports being scoped to a single `stack_id`, and `Shipit::Api::BaseController#stacks`/`#stack` is designed to enforce that scope by restricting the queryable `Stack` relation to `current_api_client.stack_id` when it is set. [1](#0-0)  `CCMenuController`, however, overrides `stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, bypassing the scoped `stacks` relation entirely. [2](#0-1)  The only authorization check that remains is `require_permission :read, :stack`, which only checks that `'read:stack'` is present in the client's `permissions` array — it never checks which stack the permission is scoped to. [3](#0-2) [4](#0-3) 

### Finding Description
`ApiClient` is designed to optionally restrict a token to a single stack via `belongs_to :stack, optional: true`, and `BaseController#stacks` enforces this by limiting the visible `Stack` set to that one stack whenever `stack_id` is present. [5](#0-4) [6](#0-5)  Every other API controller (e.g. `Shipit::Api::StacksController`) implicitly relies on this scoped `stacks`/`stack` helper for authorization. [7](#0-6) 

`CCMenuController` breaks this binding by redefining `stack` locally to `Stack.from_param!(params[:stack_id])`, which queries `Stack` unscoped by the authenticated client's `stack_id`. [2](#0-1)  The `require_permission :read, :stack` declaration only calls `current_api_client.check_permissions!('read', 'stack')`, which checks membership in the `permissions` array and never consults `stack_id`. [8](#0-7) [3](#0-2) 

Before: a client scoped to stack A with `read:stack` permission is intended to only ever see stack A's state through the scoped `stacks`/`stack` helper used elsewhere.
After: the same client, hitting `CCMenuController#show` with `params[:stack_id]` set to stack B, passes the permission check (it has `read:stack` globally) and `stack` resolves to stack B directly via `Stack.from_param!`, leaking stack B's deploy status, lock state, and last build info despite the token never being authorized for stack B. [9](#0-8) 

### Impact Explanation
This is an authorization escalation beyond the token's granted scope: a credential deliberately restricted to one stack can read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, activity) for every other stack in the installation, which matches the "escalation into stack authorization" / "unauthenticated read of stack state" High-severity bucket, since the resource-level scoping restriction is completely bypassed by this one controller.

### Likelihood Explanation
Any host application that creates stack-scoped `ApiClient` records (the documented purpose of the `stack_id` association and the `stacks`/`stack` scoping in `BaseController`) is affected as soon as that token is used against the CCMenu endpoint — no additional privilege, secret, or race condition is required; the caller only needs the token they were legitimately issued and a different `stack_id` route param.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (e.g. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the stack-scoping enforced elsewhere in the API also applies here.

### Proof of Concept
1. Create (or have the host app create) `ApiClient` A with `stack_id` set to stack "foo-production" and `permissions: ['read:stack']`.
2. Authenticate as client A and request `GET /api/stacks/bar-staging/cc.xml` (routes to `CCMenuController#show`, params `stack_id: 'bar-staging'`).
3. `require_permission :read, :stack` passes because client A has `'read:stack'` in `permissions`. [4](#0-3) 
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` to `bar-staging`, unscoped by client A's `stack_id`, and the response includes `bar-staging`'s deploy/lock status — data client A was never authorized to see. [10](#0-9)
