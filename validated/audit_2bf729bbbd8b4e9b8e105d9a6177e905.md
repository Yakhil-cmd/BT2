### Title
Operator's `review_stacks_enabled` toggle is not enforced for `allow_with_label`/`prevent_with_label` provisioning behaviors due to an operator-precedence bug in `provision?`/`unarchive?` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`OpenedHandler#provision?` (and the byte-identical `ReopenedHandler#unarchive?`) compute `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`. Because `&&` binds tighter than `||` in Ruby, `review_stacks_enabled` only gates the `allow_all` branch; it does not gate the `allow_with_label` or `prevent_with_label` branches at all. `LabeledHandler#respond_to_label_change?`, by contrast, correctly ANDs `review_stacks_enabled` across the whole condition.

### Finding Description
Intended binding (per the settings UI/docs, `app/views/shipit/repositories/settings.html.erb` and `docs/review_stacks.md`): `provision? == review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))` — i.e. the master toggle must gate every behavior.

Actual code implements: `provision? == (review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)` [1](#0-0) 

These two expressions diverge whenever `review_stacks_enabled == false` and `provisioning_behavior` is `allow_with_label` or `prevent_with_label`: the intended value is always `false`, but the actual value tracks only the label state and ignores the toggle entirely.

The identical flawed predicate is duplicated in `ReopenedHandler#unarchive?` [2](#0-1) , while `LabeledHandler#respond_to_label_change?` correctly chains `repository.review_stacks_enabled && (archive? || unarchive?)` [3](#0-2) , so a bare "labeled" webhook alone does not reach the bug.

Exploit flow for a repository operator-configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`:
1. Attacker (owner of the repo, or a fork with PR rights) opens a PR against the target repo. `opened` webhook fires with no label → `pull_request_has_provisioning_label?` is false → `provision?` false → correctly blocked. [4](#0-3) 
2. Attacker adds the provisioning label to their own PR (a GitHub action they are fully entitled to perform on their own PR). This fires a real `labeled` webhook, which is safely gated by `review_stacks_enabled` and does nothing.
3. Attacker closes and reopens the same PR (again an action any PR author can perform on their own PR). GitHub fires a real `reopened` webhook whose `pull_request.labels` now includes the provisioning label. `ReopenedHandler#unarchive?` evaluates `(allow_with_label? && has_label?) == true`, independent of `review_stacks_enabled`, so `respond_to_pull_request_reopened?` returns true and `stack.unarchive!` → `ReviewStackAdapter#find_or_create!`/`create!` runs, creating a `ReviewStack` and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` with `branch: params.pull_request.head.ref` taken directly from the attacker's fork. [5](#0-4) 

This bypasses the operator's explicit decision to keep review stacks disabled for the repository, and lets the attacker get their own branch provisioned/deployed as a review stack even though the feature was turned off.

Existing guards do not prevent this: webhook signature verification only authenticates that the payload truly came from GitHub for a repository the attacker legitimately controls (opens/labels/closes/reopens on their own PR) — it does not validate that the *effect* of the event respects `review_stacks_enabled`. `ExplicitParameters` schema only validates payload shape, not the business-logic gating. No model validation on `Repository`/`Stack` re-checks `review_stacks_enabled` before stack creation.

### Impact Explanation
A repository whose operator explicitly disabled dynamic review-stack provisioning (`review_stacks_enabled: false`) but left `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` will still have `Shipit::ReviewStack` records created and queued for provisioning/deployment from an attacker-controlled branch (`params.pull_request.head.ref`), whenever the attacker performs the close/label/reopen sequence on their own PR. This is a record written for a repository whose operator did not authorize dynamic provisioning, and — because review stacks are subsequently deployed through the normal task/`Command` pipeline — it effectively grants the attacker an unauthorized deploy of their own fork's code, matching the "unauthorized deploy" / RCE-adjacent Critical category. The blast radius is limited to repositories where an operator set a non-default `provisioning_behavior` while leaving `review_stacks_enabled` off (a plausible but not universal misconfiguration); repositories that never touch `provisioning_behavior` from its default are unaffected.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (not the default `allow_all`). Given that, the attacker cost is trivial — open a PR, add a label to their own PR, close/reopen it — all actions a PR author is normally allowed to perform, requiring no secrets, sessions, or elevated permissions. The bug is deterministic and repeatable per repository meeting these preconditions; it does not require any race or timing luck since the flawed boolean is re-evaluated fresh on the "reopened" webhook, which faithfully reflects the label state at reopen time. The question's proposed proof going through `LabeledHandler` alone does not trigger the bug, because that handler already correctly ANDs `review_stacks_enabled`; the reachable trigger is via `ReopenedHandler` (or, in principle, an "opened" payload that already carries the label at creation time, an edge case not reliably attacker-controllable through normal GitHub UI/API flows).

### Recommendation
Parenthesize the intended precedence explicitly in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the equivalent fix to `unarchive?` in `ReopenedHandler`, and consider extracting this predicate into a single shared method (e.g. on `Repository`) to avoid the duplicated/divergent logic seen between `OpenedHandler`/`ReopenedHandler` and the correctly-gated `LabeledHandler`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`-style, extendable analogously for `opened_handler_test.rb`):
1. Create a `Shipit::Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: "allow_with_label"`, `provisioning_label_name: "deploy-review"`.
2. Build params for action `opened` with `pull_request.labels == []`; call `OpenedHandler.new(...).process` (or `respond_to_pull_request_opened?`); assert no `Shipit::ReviewStack` is created — establishes the "blocked" baseline (LHS of binding: `provision? == false`, matches).
3. Build params for action `reopened` on the same PR number, now with `pull_request.labels == [{ "name" => "deploy-review" }]`; call `ReopenedHandler.new(...).process`.
4. Assert `repository.review_stacks.find_by(environment: "pr<number>")` is **present** and was enqueued via `Shipit::ReviewStackProvisioningQueue`.
5. Assert directly on the boolean divergence: `refute repository.review_stacks_enabled` while `assert ReopenedHandler.new(params, ...).send(:unarchive?)` returns `true` — demonstrating `provision?`/`unarchive? != review_stacks_enabled`-gated value, proving the binding is broken.
