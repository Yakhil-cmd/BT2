### Title
Membership webhook grants team membership on a Team resolved solely by github_id, without checking that the authenticated organization owns that team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::GitHubApp#verify_webhook_signature` only authenticates that a webhook body was signed with the secret configured for the organization named as `repository_owner`/`organization.login` in that same payload [1](#0-0) . It never checks that the `team`/`organization` object inside the payload actually belongs to that authenticated organization, and `MembershipHandler` looks up the target `Team` purely by GitHub's numeric `team.id`, so a legitimate owner of any org can mutate a `Team` record (and its memberships) belonging to a completely different org.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `authenticated_organization (Shipit.github(organization: repository_owner).webhook_secret owner) == team.organization (the Team record being mutated)`.

Path:
1. `Shipit::WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) , then does `github_app = Shipit.github(organization: repository_owner)` and checks the signature against that org's configured secret [3](#0-2) .
2. Because the attacker legitimately controls `attacker-org` and knows its real `webhook_secret`, they set `organization.login = 'attacker-org'` (and omit/match `repository.owner.login` the same way) so `repository_owner` resolves to `attacker-org`. `verify_webhook_signature` (lib/shipit/github_app.rb:76-83) correctly and legitimately validates against `attacker-org`'s own secret - no forgery occurs.
3. The full, attacker-controlled JSON body (including an arbitrary `team.id`, `team.slug`, `team.name`, `organization.login`, `member.login`) is passed unmodified to `MembershipHandler#process` [4](#0-3) .
4. `MembershipHandler#find_or_create_team!` resolves the target `Team` with `Team.find_or_create_by!(github_id: params.team.id)` [5](#0-4) . `find_or_create_by!` only runs the block (which would set `team.organization = params.organization.login`) when creating a *new* record; if a `Team` with that `github_id` already exists (e.g., the victim org's privileged team, previously created legitimately), the existing record is returned untouched and the block is skipped.
5. `process` then unconditionally executes `team.add_member(member)` or `team.members.delete(member)` [6](#0-5)  on that pre-existing team - with zero check that `params.organization.login` matches `team.organization`.

Thus an attacker who owns `attacker-org` and knows its own real webhook secret can add or remove arbitrary users (their own account, or any `login` they name) from any `Team` record whose GitHub numeric team ID they know or guess, even though that team belongs to an entirely different, victim organization. `verify_webhook_signature` never establishes this cross-org binding, and no other layer (`drop_unhandled_event`, the `ExplicitParameters` schema on `MembershipHandler`, or `Team` model validations) checks it either - the `params do ... end` schema only enforces types/presence, not org ownership.

### Impact Explanation
`Team` records resolved this way are the same records consulted by `User#authorized?`: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , where `Shipit.github_teams` is the operator-configured set of privileged teams [8](#0-7) . If the attacker learns/guesses the GitHub numeric `team.id` of one of these privileged teams (team IDs are frequently observable through GitHub's public API or prior webhook deliveries), they can forge a membership-webhook from their own org to insert their own Shipit `User` (or any known `login`) into that privileged `Team`'s membership, thereby satisfying `authorized?` and gaining access reserved for the victim org's team members - all without ever possessing the victim org's webhook secret. This is a cross-tenant authorization escalation matching the "High - escalation into `Shipit.github_teams` authorization" category, and is repeatable against any Team whose `github_id` the attacker can enumerate.

### Likelihood Explanation
Preconditions are modest: the attacker needs (a) a real GitHub org they legitimately own with the Shipit GitHub App installed and a real webhook secret (which they already possess by definition), (b) multi-org Shipit configuration (`Shipit.github(organization:)` support, which is standard), and (c) knowledge of a target privileged team's numeric GitHub `team.id`. No victim secrets, GitHub App private key, or Shipit session/token are required. The attacker only needs to POST a correctly-signed JSON body to `/webhooks` - a single HTTP request, fully repeatable, and requires no interaction from the victim.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after resolving (or before mutating) the `Team`, verify that `params.organization.login.downcase == team.organization.downcase`, and reject/raise (or drop the event) on mismatch instead of silently mutating a record that belongs to a different org. More generally, `WebhooksController#verify_signature` should bind the verified organization identity to every subsequent handler invocation (e.g., pass the authenticated `repository_owner` alongside `params` and have handlers assert consistency against it) rather than trusting organization/team fields taken from the unauthenticated part of the payload.

### Proof of Concept
Minitest plan (webhooks controller/handler level, no live GitHub):
```ruby
test "membership webhook from attacker-org cannot mutate a team belonging to victim-org" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'victim-org', slug: 'admins', name: 'Admins', api_url: 'https://x')

  # Simulate GitHubApp#verify_webhook_signature succeeding legitimately for attacker-org's own secret
  Shipit::GitHubApp.any_instance.stubs(:verify_webhook_signature).returns(true)

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'Admins', slug: 'admins', url: 'https://x' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  assert_difference -> { victim_team.reload.members.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  # Assert the binding: organization claimed in the authenticated request ('attacker-org')
  # does NOT equal the mutated team's actual organization ('victim-org') - yet the mutation succeeded.
  refute_equal 'attacker-org', victim_team.reload.organization
  assert victim_team.members.exists?(login: 'attacker')
end
```
This demonstrates that passing signature verification for `attacker-org` is sufficient to mutate a `Team` scoped to `victim-org`, confirming the missing organization/team ownership check in `MembershipHandler#find_or_create_team!` (app/models/shipit/webhooks/handlers/membership_handler.rb:38-43).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
