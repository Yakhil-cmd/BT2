### Title
Race between `WriteVoteDataBlockNums` (no lock) and `InsertVoteDataBlockNum` (package-level `mu`) silently drops governance votes, causing persistent base-fee mispricing — (`kaiax/gov/headergov/impl/schema.go`)

### Summary
`RemoveVotesAfter` calls `WriteVoteDataBlockNums` without holding the package-level `mu`, while `InsertVoteDataBlockNum` holds that lock for its entire read-modify-write. A concurrent reorg + block-insertion (or background migration) can cause `WriteVoteDataBlockNums` to overwrite the DB after `InsertVoteDataBlockNum` has already appended a new block number, permanently dropping that vote from the persisted index. After a node restart the missing vote is never reloaded, so `getExpectedGovernance` omits it at the next epoch boundary and the wrong governance param (e.g., `LowerBoundBaseFee`/`UpperBoundBaseFee`) is applied to all subsequent blocks.

### Finding Description
`InsertVoteDataBlockNum` (schema.go:59-77) uses the package-level `mu` to atomically read-modify-write the `voteDataBlockNums` DB key. `WriteVoteDataBlockNums` (schema.go:55-57) calls `writeStoredUint64Array` directly with no lock. `RemoveVotesAfter` (rewind.go:36-38) calls `WriteVoteDataBlockNums` after computing the block-num list from the in-memory `h.groupedVotes`. Because these two DB writes are not mutually exclusive, the following interleaving is possible:

1. `InsertVoteDataBlockNum` completes, DB = `[…, N]`
2. `RemoveVotesAfter` (which already deleted N from in-memory state) calls `WriteVoteDataBlockNums([…])`, DB = `[…]` — N is gone

The lost entry is never recovered: `accumulateVotesInEpoch` only scans epochs strictly below `lowestVoteScannedEpochIdx` and will not re-visit an already-scanned epoch.

### Impact Explanation
A governance vote (e.g., for `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee`) is silently dropped from the persisted index. After any subsequent node restart, `readVoteDataFromDB` does not load that vote, `groupedVotes` is incomplete, and the wrong governance parameters are applied to every block from the next epoch boundary onward. This constitutes persistent base-fee mispricing above a material threshold and durable corruption of governance state.

### Likelihood Explanation
The race requires a chain reorg (`RewindDelete` → `RemoveVotesAfter`) to overlap with either `PostInsertBlock` → `HandleVote` → `InsertVoteDataBlockNum` or the background `migrate()` goroutine → `accumulateVotesInEpoch` → `InsertVoteDataBlockNum`. Both scenarios occur during normal node operation; no attacker privilege is required beyond the ability to cause a short reorg via P2P block propagation, which is a standard network-level operation.

### Recommendation
Acquire the package-level `mu` write-lock inside `WriteVoteDataBlockNums` (or at the call site in `RemoveVotesAfter`) so that all reads and writes to the `voteDataBlockNums` DB key are serialized under the same lock. Alternatively, unify the in-memory and DB update into a single locked operation so that `RemoveVotesAfter` cannot overwrite a DB entry that was inserted after it read the in-memory state.

func InsertVoteDataBlockNum(db database.Database, blockNum uint64) {
	mu.Lock()
	defer mu.Unlock()

	blockNums := readStoredUint64Array(db, voteDataBlockNumsKey)
	if blockNums == nil {
		blockNums = StoredUint64Array{}

	// Check if blockNum already exists in the array
	if slices.Contains(blockNums, blockNum) {
		return
	}

	slices.Sort(blockNums)

func (h *headerGovModule) migrate() {
	defer h.wg.Done()

	// Scan all epochs in the background including 0th epoch
	pBorder := ReadLowestVoteScannedEpochIdx(h.ChainKv)
	if pBorder == nil {
		logger.Crit("Unexpected nil: lowest vote scanned epoch index")
		return
	}

	border := *pBorder

	for int64(border) > 0 {
		if h.quit.Load() == 1 {
			return
		}

		time.Sleep(migrationThrottlingDelay)

		border -= 1
		h.accumulateVotesInEpoch(border)
	}

	if border == 0 {
		logger.Info("HeaderGovModule migrate complete")
	}
}
