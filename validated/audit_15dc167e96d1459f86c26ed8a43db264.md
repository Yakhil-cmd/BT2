### Title
Webhook signature-verification key is selected from an unverified payload field, letting a webhook targeting an org with no `webhook_secret` forge CI status/push events for a commit belonging to a different, secret-protected organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to verify the HMAC against using `repository_owner`, a value read straight from the unauthenticated JSON body, before the signature has been checked. If that organization has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` unconditionally returns `true`. Downstream handlers such as `StatusHandler` and `PushHandler` then act on a completely different part of the same payload (`repository.full_name` / a bare commit `sha`) which is not required to match the organization used for verification. This breaks the binding "organization whose credential authenticated the request == organization/repository the payload is allowed to mutate."

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is taken from the raw, unauthenticated request body itself and used to pick *which* per-organization `GitHubApp` (and therefore which secret) will be used to validate the signature of that very body.

In `lib/shipit/github_app.rb`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

If any configured organization has no `webhook_secret` (an explicitly documented, supported configuration - see `docs/setup.md` "Using Multiple Github Applications", and exercised in `test/dummy/config/secrets_double_github_app.yml` where `OrgTwo` has `webhook_secret: # nil`) [3](#0-2) [4](#0-3) , then any request claiming `repository.owner.login` (or `organization.login`) equal to that org's name passes `verify_signature` with **no valid signature at all**.

Once past this gate, the actual event handlers do not re-check that the acted-upon resource belongs to the organization that was used to authenticate the request:

- `StatusHandler#process` looks up commits **globally by SHA**, with no repository/organization scoping whatsoever:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

- `PushHandler#process` and the base `Handler#stacks`/`#repository_name` resolve the target purely from `payload.dig('repository', 'full_name')`, an independent field of the same JSON body that was never itself covered by any secret check for that organization:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) [7](#0-6) 

So the equality that should hold - `organization whose secret authenticated the delivery == organization owning the commit/repository being mutated` - is broken: verification trusts `repository_owner` (attacker-supplied, unauthenticated at check time) to pick a secret, but the mutation targets are chosen from unrelated fields (`sha`, `full_name`) of the same untrusted body, with no cross-check back to the org that "authenticated."

### Impact Explanation
An attacker who can send arbitrary HTTP requests to the `/webhooks` endpoint (unprivileged, no Shipit session or GitHub credential required) can:
- Forge a GitHub `status` webhook with `state: "success"` for the SHA of any commit tracked by Shipit, in any stack, regardless of which organization owns that repository, as long as some other org configured on the instance has a blank `webhook_secret`. Since Shipit stacks gate deploys on commit CI/status state, this can flip a malicious or stale commit to "deployable," leading to an **unauthorized deploy**.
- Forge a `push` event that triggers `stack.sync_github` for a repository belonging to a different, secret-protected organization.

This crosses the "organization that authenticated" vs. "repository that is written" boundary named in the analog rules and can culminate in an unauthorized deploy - a Critical-tier impact per the stated scope.

### Likelihood Explanation
Requires a Shipit instance configured for multiple GitHub organizations (a documented, supported feature) where at least one organization has no `webhook_secret` set. This is not a hypothetical edge case: `docs/setup.md` shows the multi-org config block with blank `webhook_secret:` entries as valid, and the test fixtures exercise exactly this configuration. Given that setup, exploitation requires only crafting an unauthenticated HTTP POST - no token, session, or GitHub credential of any kind.

### Recommendation
- Do not let an unauthenticated field of the payload select which secret is used to authenticate that same payload. Require the caller to prove membership in a specific configured GitHub App (e.g., via a per-org secret path, or App ID conveyed and cross-checked outside the body) before trusting any field from that body.
- Independent of the above, `verify_webhook_signature` should not silently return `true` when `webhook_secret` is unset for an organization that other organizations on the same instance have configured with a real secret; at minimum, cross-validate that `repository.full_name`'s owner matches the `repository_owner` used for signature selection, and that both belong to the same authenticated org.
- `StatusHandler` (and any handler resolving resources purely by SHA) should scope lookups to a repository/stack derived from a value that was actually covered by the verified signature for that specific organization, not resolve `Commit.where(sha:)` globally.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`'s "Using Multiple Github Applications") with two orgs: `OrgSecure` (real `webhook_secret`) and `OrgOpen` (no `webhook_secret`) - a supported configuration shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgOpen" }, "full_name": "OrgSecure/critical-app" },
  "organization": { "login": "OrgOpen" },
  "sha": "<sha of a real, tracked commit in OrgSecure/critical-app>",
  "state": "success"
}
```
No `X-Hub-Signature` header is required, or an arbitrary bogus one may be sent.
3. `verify_signature` computes `repository_owner == "OrgOpen"`, loads `OrgOpen`'s `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally - `head(422)` is never called.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the real commit belonging to `OrgSecure/critical-app`, and calls `create_status_from_github!` with `state: "success"`, marking it as passing CI in an org the attacker never authenticated against. [8](#0-7) [2](#0-1) [9](#0-8)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
