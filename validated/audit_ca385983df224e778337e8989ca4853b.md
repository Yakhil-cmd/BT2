### Title
Recovery pallet's inheritor call filter validates only the top-level call, bypassable by wrapping in `utility::batch` - ([File: substrate/frame/recovery/src/lib.rs])

### Summary
`pallet-recovery`'s `inheritor`/`friend-groups` mechanism (as extended in this fork with `slash_attempt`, `control_inherited_account`, `initiate_attempt`, etc.) restricts what the current controller of an inherited/recovering account can do by matching the wrapped `RuntimeCall`'s outer variant. As with the Parse Server protected-fields check that only inspects top-level query keys, this pallet's authorization check inspects only the outer dispatched call, not calls nested inside `pallet_utility::batch`/`batch_all`. This is the exact structural analog: a security-relevant filter that is not applied recursively to logically/structurally nested sub-calls, letting an attacker who controls only the outer wrapper bypass the restriction that was meant to prevent a privileged action (here, `slash_attempt`, which affects the priority/ordering of competing recovery attempts and their deposits).

### Finding Description
The pallet's own regression test, `inheritor_cannot_bypass_filter_via_utility_batch` in `substrate/frame/recovery/src/tests.rs:1423-1479`, is written specifically to catch this bug class: an account (`FERDIE`) that inherited a lower-priority friend group calls `control_inherited_account` with a `RuntimeCall::Utility(Call::batch { calls: vec![slash_attempt_call] })` instead of dispatching `slash_attempt` directly. [1](#0-0) 

The in-line comment on line 1466 states plainly: *"The batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call."* That is a direct acknowledgment in the codebase that the authorization check performed by `control_inherited_account` matches/filters based on the outer `RuntimeCall` variant (e.g., is it `Call::slash_attempt` at the top level?) rather than using a recursive/origin-level filter (the pattern used correctly by `pallet-proxy`'s `do_proxy`, which installs the restriction via `origin.add_filter(...)`, so it is re-checked for every call `dispatch`ed from that origin, including calls nested inside `utility::batch`). [2](#0-1) 

Compare this to `pallet-utility`'s own dispatch loop, which simply calls `call.dispatch(origin.clone())` for each inner call using the *same* origin used for the outer batch call — so any origin-level filter set for that origin (as proxy does) is naturally re-applied to every nested call, but a callsite-level match on the outer call type (as `control_inherited_account` appears to use, per the test's own comment) is not. [3](#0-2) 

This mirrors the Parse Server vulnerability precisely: Parse Server's protected-field check inspected only the top-level query keys and missed the same constraint expressed inside a `$or`/`$and`/`$nor` sub-query; here the recovery pallet's authorization check inspects only the top-level `RuntimeCall` and misses the same restricted call expressed inside `Utility::batch`.

### Impact Explanation
If `slash_attempt` (or any other call meant to be blocked for a given inheritor/controller) can be executed by wrapping it in `Utility::batch`, an account controlling a lower-priority or otherwise-restricted inherited account can perform an action it should not be authorized to perform — in this scenario, slashing a competing higher-priority friend group's deposit/attempt, which is an integrity/fairness violation of the recovery/inheritance logic and causes direct loss (slashed deposit) to the victim friend group. This would be a High-severity authorization bypass in a live deployment of this pallet, analogous in class (not in exact mechanism) to the CWE-284 (Improper Access Control) issue in the advisory.

### Likelihood Explanation
Likelihood assessment is constrained by tool/iteration limits: I was able to confirm the test's existence and its explicit comment describing the exact bypass, and confirm the structural difference between this filter approach and `pallet-proxy`'s correctly-recursive `add_filter` mechanism, but I could not retrieve and directly read the full implementation of `control_inherited_account`'s authorization/matching logic in `substrate/frame/recovery/src/lib.rs` within the available tool budget to confirm definitively whether the current code already fixes this (i.e., whether the test's `panic!` branch is actually reachable in the present state of the code, or whether it's a dead/passing regression check for an already-patched bypass). The test only `panic!`s if the slash is observed to succeed; it does not use `assert_noop!`/`assert!` to hard-fail otherwise, which is unusual and consistent with this being a demonstrative "if the bug exists, blow up loudly" style test rather than a confirmed-passing unit test guaranteeing the fix.

### Recommendation
Verify with direct code reading (not fully done here due to tool-call budget) whether `control_inherited_account`'s permission check matches against `<T as Config>::RuntimeCall` structurally (top-level match only) or applies an `origin.add_filter(...)`-based recursive restriction like `pallet-proxy::do_proxy`. If it is a top-level match, convert it to the `add_filter` pattern (as `pallet-proxy` and `pallet-utility::batch_all`'s anti-nesting filter do) so the restriction is enforced transitively across `Utility::batch`/`batch_all`, `Multisig`, and any other call-wrapping pallet.

### Proof of Concept
Existing harness: `substrate/frame/recovery/src/tests.rs:1423-1477`, test `inheritor_cannot_bypass_filter_via_utility_batch`, exercises exactly this path — `FERDIE` (holder of the lower-priority `Friends` group's inheritance) calls `Recovery::control_inherited_account(signed(FERDIE), ALICE, Box::new(batch_call))` where `batch_call` wraps `RecoveryCall::slash_attempt { friend_group_index: 0 }` (targeting the higher-priority `Family` group). The test itself documents that the slash succeeds because "our filter only checks the outer call," and will `panic!("BYPASS: recovery call filter was circumvented via utility::batch! ...")` if `BOB`'s (a `Family`-group friend's) balance decreases. I was not able to execute this test directly (no execution tooling available in ask-only mode) or read the full authorization logic in `control_inherited_account` to state with certainty whether the panic branch currently triggers in this repo's present state — this should be confirmed by running `cargo test -p pallet-recovery inheritor_cannot_bypass_filter_via_utility_batch` and reading `substrate/frame/recovery/src/lib.rs`'s `control_inherited_account` implementation in full.
