### Title
Webhook signature verification authenticates a different repository/organization than the one the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Once the signature passes, the raw payload is handed to per-event `Handler` classes that resolve the *actual* target repository/commit using a completely different, unverified field of the same payload (`repository.full_name` for `PushHandler`, or nothing at all for `StatusHandler`, which matches purely on `sha`). Nothing ties the field used to pick the verifying secret to the field used to decide what gets written.

### Finding Description
`verify_signature` picks the app/secret to validate against solely from `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 

The signature check itself is a straightforward HMAC compare of the raw body against the secret configured for that one organization: [3](#0-2) 

Once `head(422)` is *not* triggered, `create` dispatches the entire, attacker-controlled JSON body to the matching handlers regardless of which field was used for the org lookup: [4](#0-3) 

The base `Handler` class resolves the repository to mutate using `payload.dig('repository', 'full_name')` — a field that is never cross-checked against `repository.owner.login` (the field the signature check used): [5](#0-4) 

`PushHandler` uses that `stacks` scope, driven by `full_name`, to trigger a resync of any matching stack, independent of the organization that was actually authenticated by the signature: [6](#0-5) 

`StatusHandler` is worse: it does not use the repository field at all, it matches purely on commit `sha` across the whole `Commit` table, with zero binding to any organization or repository: [7](#0-6) 

Shipit is explicitly designed to be configured with multiple, independently-trusted GitHub organizations, each with its own `webhook_secret`, as documented in `config/secrets.development.shopify.yml`: [8](#0-7) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization whose webhook_secret validated the signature (repository.owner.login / organization.login)` ⧧ `repository/commit actually mutated by the handler (repository.full_name, or bare sha with no repository scope at all)`.

Before the attack: an org admin/maintainer of Org A (who legitimately possesses/controls Org A's GitHub App webhook secret because they administer that GitHub App installation) can only affect Org A's own webhook delivery to this Shipit instance.

After the attack: that same Org A admin can craft an arbitrary JSON payload, set `repository.owner.login` (or `organization.login`) to `"org-a"` so the signature is verified against Org A's secret, but set `repository.full_name` to `"org-b/victim-repo"` (for push events) or simply set `sha` to a commit hash belonging to an entirely different, victim repository under Org B (for status events). The HMAC signature, computed over the full raw body with Org A's secret, is still valid, so `verify_signature` passes, and the handler then acts on Org B's stack/commit.

### Impact Explanation
- **StatusHandler path**: `Commit.where(sha: params.sha)` has no repository or organization scoping at all. An attacker who legitimately controls a webhook secret for any one configured organization can forge a `status` webhook (signed with their own org's secret) claiming an arbitrary `state: "success"` for a commit `sha` belonging to a completely different organization/repository configured on the same Shipit instance. Since Shipit stacks gate deploys on commit/CI status (`Status`/`Status::Group`, `deployable?` checks in `app/models/shipit/stack.rb`), this can be used to spoof passing CI status on a victim's commit and enable an **unauthorized deploy** of a stack the attacker has no legitimate access to — this matches the Critical bar ("unauthorized deploy, rollback or merge").
- **PushHandler path**: the same organization/repository mismatch lets an attacker trigger `GithubSyncJob`/`sync_github` against a victim stack that belongs to a different, unrelated organization, forcing unwanted resyncs of another tenant's stack using a signature that was never actually issued/authorized for that tenant/repo.

This is a direct multi-tenant trust-boundary bypass: the engine authenticates "who signed this", but never checks "is what they signed about actually something they own", exactly mirroring the reported bug class where fee calculation was correctly performed but the funds were never bound to the correct destination (treasury) — here, the signature is correctly verified but never bound to the resource it authorizes.

### Likelihood Explanation
Requires only that the attacker be a legitimate but low-privileged party with respect to the whole Shipit instance: an admin of *some* GitHub App installation/organization that this Shipit deployment is configured to trust (a realistic multi-tenant scenario, as the secrets file structure explicitly supports multiple orgs). No Shipit session, `ApiClient` token, or private key is needed — only the webhook secret for the attacker's own org, which such an org admin legitimately possesses. Crafting a custom JSON payload with mismatched `repository.owner.login`/`organization.login` vs `repository.full_name` (or an arbitrary `sha`) and re-signing it with their own secret is trivial.

### Recommendation
After signature verification succeeds for organization `O`, re-validate that every repository/commit resolved by the handler actually belongs to organization `O` before acting:
- In `Handler#stacks`, ensure the resolved `Repository`'s owner matches the organization whose secret verified the request (pass the verified organization down from the controller into `Webhooks.for_event(event).each { |handler| handler.call(params, organization: repository_owner) }` and check it in `Handler#stacks`).
- In `StatusHandler`, scope `Commit.where(sha: params.sha)` additionally by the commit's repository belonging to the verified organization, not just by `sha`.
- More generally, do not trust any organization/repository identifying field inside the JSON body for authorization purposes unless it was the exact field cryptographically bound to the signature check, or unless it is re-validated against that field after verification.

### Proof of Concept
1. Configure/observe that the target Shipit instance trusts two orgs, `org-a` (attacker-controlled GitHub App/webhook secret) and `org-b` (victim, unrelated to attacker), as shown in `config/secrets.*.yml` structure.
2. Attacker (who legitimately administers `org-a`'s GitHub App and thus knows `org-a`'s `webhook_secret`) crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha belonging to org-b/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/some-repo"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#repository_owner` reads `"org-a"` from `repository.owner.login`, `verify_signature` loads `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret [9](#0-8) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a spoofed successful status on the victim commit belonging to `org-b/victim-repo`, with no check that `org-b` was the organization actually authenticated [7](#0-6) .
6. If `org-b`'s stack requires that status/context to be green before allowing deploy, the victim stack becomes deployable purely off a signature that only ever proved control of `org-a`'s secret — an unauthorized deploy path across organizational boundaries.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
