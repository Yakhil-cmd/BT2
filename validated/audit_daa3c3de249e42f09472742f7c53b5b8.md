### Title
Permanently locked `pending_delegator_rewards` lamports in vote accounts when all delegated stake deactivates before distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs], [File: programs/vote/src/vote_state/mod.rs])

### Summary
`VoteStateV4::pending_delegator_rewards` behaves like the "unvested yield" pool in the reported ERC-4626 bug: lamports are deposited into a vote account via `DepositDelegatorRewards` (SIMD-0123) and held back from delegators until they are distributed proportionally to active stake at the next epoch boundary via `calculate_block_reward`. If the total delegated/active stake behind the vote account drops to zero (all delegators undelegate/withdraw) before that distribution runs, `calculate_block_reward` returns `0` and the "unvested" `pending_delegator_rewards` amount is never paid out — yet `withdraw` explicitly refuses to let the vote account's authorized withdrawer take those lamports out, and refuses to close the account at all while `pending_delegator_rewards > 0`. The lamports become permanently stuck in the vote account with no on-chain mechanism to recover or redistribute them, mirroring the reported vault issue where all stakers withdrawing during the vesting window strands undistributed yield.

### Finding Description
`pending_delegator_rewards` is credited by `deposit_delegator_rewards`, which any signer can call to transfer lamports into a vote account and increment the field: [1](#0-0) 

This pool is meant to be paid out to delegators proportionally to their stake share at each epoch's reward distribution, computed in `calculate_block_reward`: [2](#0-1) 

Critically, the payout is gated on `total_active_stake` (the amount actually delegated to the vote account for the reward epoch): if it is `0`, the function returns `0` unconditionally, i.e. no portion of `pending_delegator_rewards` is distributed for that epoch — and there is no other code path in the epoch-reward calculation/distribution pipeline that reduces `pending_delegator_rewards` independent of a nonzero stake denominator: [3](#0-2) 

Meanwhile, `withdraw` (the only vote-program instruction that can move lamports out of a vote account) explicitly reserves `pending_delegator_rewards`:
- A withdrawal that would zero the account's balance is rejected outright if `pending_delegator_rewards > 0` (SIMD-0123 close-guard).
- A partial withdrawal must leave at least `rent_exempt_minimum + pending_delegator_rewards` in the account. [4](#0-3) 

Putting these together: if every delegator to a vote account deactivates their stake (a fully permissionless, unprivileged action any staker can perform any time — analogous to "all stakers withdraw" in the reported bug) before the epoch boundary at which a pending `DepositDelegatorRewards` deposit would be distributed, `total_active_stake` for that vote account becomes `0` in `reward_epoch_delegated_stakes`, `calculate_block_reward` returns `0` for every remaining/future epoch (since there is no stake left to recompute a share against), and `pending_delegator_rewards` is left at its last nonzero value forever. The authorized withdrawer can never withdraw below that reserved amount, and can never close the account while it is nonzero, so the lamports are permanently locked with no recovery mechanism (no rescue/sunset path exists, unlike the Syntetika fix that added a rescue transfer to the vault owner).

### Impact Explanation
This causes permanent, unrecoverable loss of lamports that were legitimately deposited into a vote account as delegator rewards. Any account (including third parties acting in good faith, e.g. protocol block-revenue-sharing depositors) that deposits via `DepositDelegatorRewards` can have those funds stranded if the validator's remaining delegators later fully undelegate — a scenario entirely reachable by ordinary, permissionless `DeactivateStake` transactions from any staker, with no cooperation from the vote account authority required. This is a concrete, unsigned/undirected fund-lock analogous to the reported vault bug: real value becomes permanently inaccessible, and worse than the reported bug because there is no partial-recovery mechanic (the vault's later depositor could recover *most* funds through share dilution; here the vote account has no equivalent recovery path at all — the funds are simply frozen).

### Likelihood Explanation
Likelihood is moderate: it requires (1) a `DepositDelegatorRewards` deposit into a vote account with nonzero pending rewards, and (2) subsequent complete deactivation of all delegated stake to that vote account before the deposited amount is fully distributed across epochs. Since delegators can deactivate/withdraw their stake at will and validators can lose all their delegators (e.g., during commission changes, slashing events, or simple attrition), this is a realistic, unprivileged, naturally-occurring scenario rather than a contrived edge case, though it depends on the relatively new SIMD-0123 `DepositDelegatorRewards`/block-revenue-sharing feature being active.

### Recommendation
Add a rescue/redistribution path analogous to the Syntetika fix:
- When a vote account's `total_active_stake` (or effective delegated stake) reaches zero while `pending_delegator_rewards > 0`, either (a) redirect the pending amount to the block-revenue/inflation-rewards collector or authorized withdrawer at the next epoch boundary instead of silently discarding the distribution, or (b) allow the authorized withdrawer to reclaim `pending_delegator_rewards` once stake has been at zero for a defined grace period.
- Alternatively, gate future `DepositDelegatorRewards` deposits on the vote account currently having nonzero active/effective stake, and validate at deposit time (and periodically) that a mechanism exists to fully drain `pending_delegator_rewards` even when stake is fully withdrawn.

### Proof of Concept
Conceptual reproduction using existing instructions (cannot be fully driven purely through the indexed test harness here, but the mechanics are directly supported by the cited code paths):
1. Validator creates a v4 vote account and one staker delegates stake to it.
2. A depositor calls `DepositDelegatorRewards` on the vote account, incrementing `pending_delegator_rewards` (see `deposit_delegator_rewards`, `programs/vote/src/vote_state/mod.rs:935-988`).
3. Before the reward epoch in which this deposit would be distributed completes, the staker calls `DeactivateStake` and fully withdraws, reducing the vote account's `total_active_stake` for the relevant `RewardEpochDelegatedStakes` entry to `0`.
4. At the next epoch boundary, `calculate_block_reward` is invoked for any (now nonexistent) delegations to this vote account; since `total_active_stake == 0`, it returns `0` (`calculation.rs:211-213`), so `pending_delegator_rewards` is never decremented.
5. The vote account's authorized withdrawer attempts `Withdraw`; `withdraw()` blocks any withdrawal that would drop the balance below `rent_exempt_minimum + pending_delegator_rewards`, and blocks a full close entirely while `pending_delegator_rewards > 0` (`vote_state/mod.rs:1084-1122`).
6. The deposited lamports remain locked in the vote account indefinitely, with no delegators left to receive them and no way for the withdrawer to reclaim them.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
