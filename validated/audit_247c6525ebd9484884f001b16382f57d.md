### Title
RAY-domain accrual overflow permanently freezes all operations on a large market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

A market whose scaled supply or debt value approaches the `i128` RAY domain limit can reach a state where the next interest-accrual calculation overflows before the borrow-index ceiling can protect it. Because every pool mutation first runs `interest::global_sync`, the resulting `MathOverflow` panic blocks `withdraw`, `repay`, `liquidate`, and other market operations, permanently freezing supplier funds and borrower repayment. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

Each accrual first converts `borrowed` and `supplied` scaled RAY shares back to original values through `scaled_to_original`. [4](#0-3)  Those fixed-point multiplications panic with `GenericError::MathOverflow` when the result exceeds `i128::MAX`. [5](#0-4) 

The borrow index is nominally capped at `MAX_BORROW_INDEX_RAY`, but that cap is applied only to the index value, not to `borrowed * borrow_index` or `supplied * supply_index`. [6](#0-5)  A sufficiently large market can therefore cross the RAY-value ceiling while its indexes remain below their configured caps. [7](#0-6) 

The defect is triggered by the permissionless controller entrypoint `update_indexes(caller, assets)`, where `assets` contains the affected `HubAssetKey`. [8](#0-7)  Internally, `ops::market::accrue` loads the market and calls `interest::global_sync`, which invokes `accrue_step` for each elapsed chunk. [9](#0-8) [10](#0-9) 

All normal pool mutations use the same synchronization path through `synced_market`, so the panic also prevents exits, repayments, liquidations, and recapitalization once the state is reached. [11](#0-10) 

### Impact Explanation

This is a permanent market-level denial of service. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot close unsafe positions, and recapitalization cannot proceed because each path accrues the affected market before applying the requested mutation. [12](#0-11) [13](#0-12) 

The existing regression test demonstrates that `update_indexes` first fails with `MATH_OVERFLOW`, and subsequent `withdraw` and `repay` calls fail with the same error. [14](#0-13)  The market is not merely temporarily congested: without an upgrade or state repair, the trapped accrual remains the required first step for every later operation. [2](#0-1) 

### Likelihood Explanation

The trigger requires an extremely large admitted market and sustained interest accrual, so it is not a low-cost griefing path on an ordinary deployment. [15](#0-14)  The code nevertheless permits the preconditions: caps can be configured up to the asset-domain ceiling, positions near that ceiling are accepted, and an unprivileged caller can advance accrual by submitting `update_indexes`. [16](#0-15) [8](#0-7) 

The protocol documentation explicitly notes that accrued totals can overflow before the index ceiling and can block repayment and withdrawal, confirming that the vulnerable arithmetic boundary is reachable rather than only hypothetical test state. [17](#0-16)  The impact is material and deterministic once crossed, while the market-size prerequisite makes Medium severity more appropriate than High or Critical. [18](#0-17) 

### Recommendation

Make accrual fail safely when the RAY-domain value ceiling is reached:

- Detect impending `scaled * index` overflow using saturating or `I256` calculations before converting totals.
- Clamp the borrow index before the total-debt calculation can exceed `i128::MAX`, and apply the same total-value guard to supplied-value growth.
- Preserve a recovery path that can commit the capped indexes without recomputing an overflowing pre-accrual total.
- Ensure `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, and `recapitalize` can still operate on a saturated market, using conservative capped totals where exact accrual is impossible.
- Add production-level tests asserting that once `MAX_BORROW_INDEX_RAY` is reached, all exit and repayment paths remain callable rather than trapping in accrual.

### Proof of Concept

The repository contains a reproducible scenario in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. It creates an 18-decimal market, supplies one billion whole tokens, borrows 98% of that supply, repeatedly invokes the public index-update path, and observes `MATH_OVERFLOW` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [19](#0-18) 

The same test then proves the market-freezing impact: both a one-unit withdrawal and a repayment fail with `MATH_OVERFLOW` because those operations must first synchronize the market. [13](#0-12)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
