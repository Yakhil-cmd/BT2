### Title
Unchecked `transferFrom` Instead of `safeTransferFrom` in ERC721 Bridge Handle Path Permanently Locks Bridged NFTs — (File: `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer()` uses the bare `IERC721.transferFrom()` to deliver a bridged NFT to the recipient. If the recipient is a contract that does not implement `IERC721Receiver`, the transfer succeeds at the EVM level (ownership changes) but the NFT is permanently locked in that contract. Because the bridge nonce and handled-request state are committed **before** the transfer call, the request is irrevocably consumed and cannot be retried, resulting in permanent loss of the bridged asset.

---

### Finding Description

In `contracts/service_chain/bridge/BridgeTransferERC721.sol`, the non-mint-burn path of `handleERC721Transfer` uses:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

This is called **after** all bridge state has already been committed:

```solidity
_setHandledRequestTxHash(_requestTxHash);          // line 51
handleNoncesToBlockNums[_requestedNonce] = ...;    // line 53
_updateHandleNonce(_requestedNonce);               // line 54
emit HandleValueTransfer(...);                     // lines 54-64
``` [2](#0-1) 

The ERC721 standard's `transferFrom` does **not** call `onERC721Received` on the recipient. Only `safeTransferFrom` performs that check. If `_to` is a contract without `IERC721Receiver` support, `transferFrom` will succeed (ownership is transferred to `_to`), but the NFT is permanently stuck — the contract cannot move it. The bridge has already marked the nonce as handled and emitted `HandleValueTransfer`, so the request cannot be replayed.

By contrast, the ERC20 bridge path correctly uses `safeTransfer` (via `SafeERC20`):

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [3](#0-2) 

The same unsafe pattern also appears in `requestERC721Transfer` (line 129), where `transferFrom` is used to pull the NFT from the user into the bridge:

```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
``` [4](#0-3) 

---

### Impact Explanation

- **Permanent loss of bridged ERC721 assets.** When `_to` is a contract without `onERC721Received`, the NFT is transferred to an address that cannot move it. The bridge nonce is consumed and the request is marked handled, so there is no recovery path.
- The corrupted value is the **NFT token ownership**: the bridge's `lowerHandleNonce` / `handleNoncesToBlockNums` state records the transfer as complete, but the asset is locked forever.
- This satisfies the allowed impact gate: *unauthorized burn / permanent loss of bridged assets* via a valid user-triggered input (`_to` address set to a non-receiver contract on the destination chain).

---

### Likelihood Explanation

- The `_to` address originates from the user's cross-chain transfer request on the source chain. Any user can legitimately specify a contract address (e.g., a multisig, a DeFi vault, a DAO treasury) as the destination.
- Many contract wallets and protocol contracts do not implement `IERC721Receiver`. This is a common real-world scenario.
- No operator collusion is required; the operator faithfully relays the user-supplied `_to`.
- The trigger is a normal, unprivileged user action (initiating a bridge transfer to a contract address).

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in both locations in `BridgeTransferERC721.sol`:

**`handleERC721Transfer` (line 69):**
```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

**`requestERC721Transfer` (line 129):**
```solidity
// Before
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);
```

The bridge contract itself must also implement `IERC721Receiver.onERC721Received` to accept tokens via `safeTransferFrom` in the `requestERC721Transfer` path.

---

### Proof of Concept

1. User on the source chain calls `requestERC721Transfer` (or `onERC721Received`) specifying `_to = 0xDeadContract` — a deployed contract that does **not** implement `IERC721Receiver` (e.g., a plain multisig or any contract without the callback).
2. Bridge operators reach quorum and call `handleERC721Transfer` on the destination bridge with `_to = 0xDeadContract`.
3. The bridge executes:
   - `_setHandledRequestTxHash(...)` — nonce marked handled ✓
   - `_updateHandleNonce(...)` — `lowerHandleNonce` advanced ✓
   - `emit HandleValueTransfer(...)` — event emitted ✓
   - `IERC721(_tokenAddress).transferFrom(address(this), 0xDeadContract, _tokenId)` — **succeeds**, NFT ownership moves to `0xDeadContract`
4. `0xDeadContract` has no `onERC721Received` and no way to call `transferFrom`/`safeTransferFrom` on the NFT. The NFT is permanently locked.
5. The bridge considers the request fully handled. No retry is possible. The user's bridged NFT is permanently lost.
