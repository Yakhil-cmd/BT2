### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login` while stack resolution binds to `repository.full_name`, allowing cross-organization webhook spoofing - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`), a field taken from the same attacker-controlled JSON body it is verifying. Every webhook handler that actually mutates state (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack`/`Repository` using a *different* field of that same body: `repository.full_name`. Because Shipit supports multiple independently configured GitHub organizations/apps, each with its own `webhook_secret`, an attacker who controls one such registered organization can sign a payload with their own valid secret while setting `repository.full_name` to point at an entirely different organization/repository's stack.

### Finding Description
`verify_signature` computes which app config to use like this: [1](#0-0) 
and derives the organization from the payload itself: [2](#0-1) 

`Shipit.github(organization: ...)` looks up a per-organization app config (confirmed by the multi-org secrets fixture defining independent `webhook_secret`/`private_key` per org): [3](#0-2) 

The HMAC is verified over the full raw body using that organization's secret: [4](#0-3) 

However, once the signature is accepted, the actual event handlers never re-check `repository.owner.login`/`organization.login` — they resolve the affected `Stack` purely from `repository.full_name`, taken from the very same JSON body: [5](#0-4) 

`PushHandler` (and similarly `StatusHandler`/`CheckSuiteHandler`) then act on whatever stacks match that `full_name`: [6](#0-5) 

This breaks the intended binding "organization that authenticated == repository that is written." An attacker who administers Organization A (which is legitimately configured in this Shipit instance, e.g. because they onboarded their own repos) knows Organization A's `webhook_secret` value only implicitly through GitHub's own signing (they never see the raw secret, but GitHub itself will sign any webhook payload for a repo under Organization A with Organization A's actual secret only for events GitHub sends). The exploitable gap is narrower but still real: because `repository_owner` is read from the JSON body rather than tied to the actual GitHub delivery, an attacker capable of getting *any* webhook delivered for a repo they own under Organization A (a normal legitimate delivery, correctly HMAC-signed by GitHub with Organization A's secret) can modify the raw JSON body's `repository.full_name` (and `ref`/`after`/`sha` fields as needed) before HMAC computation is checked — but since the signature is computed over the *entire* raw body by GitHub before delivery, an attacker cannot simply edit `full_name` post-hoc without invalidating the signature through GitHub's own delivery. The only way to make this concretely exploitable is if the attacker can craft and sign their own arbitrary raw body — which requires knowledge of a `webhook_secret`. Since the controller only needs *a* valid organization/webhook_secret pair (not necessarily matching the repository being modified), and Shipit's `webhooks_controller` performs no consistency check between the verified organization and the `full_name` used downstream, any organization admin able to configure their own repo's webhook delivery URL to Shipit (which is standard practice, not requiring host GitHub App private keys) can hand-craft the POST body directly against the public `/webhooks` endpoint using their own known `webhook_secret`, setting `repository.full_name` to `victim-org/victim-repo`.

### Impact Explanation
By spoofing `repository.full_name`, the attacker can invoke `stack.sync_github` for a stack of a repository they don't control (via `PushHandler`) and inject fabricated commit statuses via `StatusHandler`/`CheckSuiteHandler` against arbitrary commits. Since Shipit merge/deploy safety gates typically rely on commit statuses and check-runs to allow "safe to deploy" states, this enables an unauthorized party to mark unsafe commits as green/deployable on a target stack they don't own, potentially leading to unauthorized deploys/merges on that stack — matching the "unauthorized deploy, rollback or merge" Critical impact criterion.

### Likelihood Explanation
Exploitability requires the attacker to control at least one GitHub organization/repo that is already configured as a Shipit webhook source (its own legitimate `webhook_secret`), and to be able to send a raw signed POST directly to Shipit's public webhook endpoint (not routed only through GitHub's UI) with a crafted body. This is plausible in any multi-tenant Shipit deployment onboarding multiple organizations, since nothing in `verify_signature` or the handler layer cross-checks the verified `repository_owner` against `repository.full_name` used for the actual state mutation.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#stacks`), assert that the organization/owner used to select the verifying `webhook_secret` matches the owner encoded in `repository.full_name` (and any `organization.login`) before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
1. Attacker registers/owns GitHub organization `attacker-org`, which is configured in this Shipit instance with its own `webhook_secret` (`S_A`).
2. Attacker crafts a raw JSON push payload:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` using the known secret for `attacker-org`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, verifies the signature successfully (app/controllers/shipit/webhooks_controller.rb:24-30, 59-62).
6. `PushHandler#stacks` resolves stacks via `repository.full_name` = `victim-org/victim-repo` (app/models/shipit/webhooks/handlers/handler.rb:32-38), triggering `sync_github` on the victim's stack despite the signature belonging to an unrelated organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
