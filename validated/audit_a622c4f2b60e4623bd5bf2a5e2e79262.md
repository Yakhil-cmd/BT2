Based on my investigation, I found a concrete instance of the bug class described in the report—a hardcoded/misused parameter that breaks a trust binding—in Shipit's webhook signature verification.

### Title
Webhook signature verification is keyed off an attacker-controlled `repository.owner.login` field, decoupling the organization whose secret authenticates the request from the repository that gets written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on `repository_owner`, a value read directly out of the same unauthenticated JSON body it's about to verify. Every webhook handler that actually mutates state (push, status, check_suite, pull_request, membership) instead keys its target `Repository`/`Stack`/`Commit` lookup off `repository.full_name` (or `sha`, which is global and not scoped to a repository at all). Because Shipit supports multiple GitHub organizations, each with its own independent `webhook_secret` [1](#0-0) , an attacker who legitimately controls a webhook secret for *any one* configured organization (e.g., their own org/app installed on this Shipit instance) can craft a raw payload where `repository.owner.login` names their own org (so their known secret verifies it) while `repository.full_name` (or `sha`) names a repository/commit belonging to a completely different organization tracked by the same Shipit instance.

### Finding Description
The verification path is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is used purely to pick *which* organization's secret to check the signature against — it is not itself validated against anything. Once verification passes, the same raw body is dispatched to handlers, none of which re-check that `repository.owner.login` matches the repository they act on:

- `Handler#stacks` resolves the target purely from `repository.full_name`: `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name = payload.dig('repository', 'full_name')` [3](#0-2) .
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every stack matching that repository/branch [4](#0-3) .
- `StatusHandler#process` writes a `Status` for **any** `Commit` in the whole database matching `sha`, with no repository scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) .
- Pull-request handlers similarly resolve their target `Repository`/`ReviewStack` from `params.repository.full_name`, independent of `repository_owner` [6](#0-5) .

`Shipit.github` explicitly supports one `webhook_secret` per organization when configured for multiple GitHub orgs [7](#0-6) , and the multi-org setup is a documented, first-class configuration mode [1](#0-0) . This creates exactly the binding break called out by the rules: **the organization whose secret authenticates the request ≠ the repository the handlers actually write to.** A holder of Organization A's webhook secret can forge a payload with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/target-repo"` (or an arbitrary `sha` for the sha-keyed `status` event); the signature will still validate because the entire raw body — including the mismatched `full_name`/`sha` — is HMAC'd with OrgA's secret, which the attacker legitimately possesses.

### Impact Explanation
This crosses the "unauthorized deploy" threshold via the `status` event path specifically: `StatusHandler` writes CI statuses onto commits matched only by `sha`, globally, with no ownership check. `Commit#deployable?` gates on `success? && !blocked?` [8](#0-7) , and a `success` status transition schedules continuous delivery / enables deploy eligibility for a target stack the attacker does not control [9](#0-8) . An attacker who legitimately controls one organization's webhook secret in a multi-org Shipit deployment can therefore forge a `success` status for a commit sha in a victim organization's stack they have no legitimate access to, making it eligible for an unauthorized deploy/continuous-deployment trigger — without ever needing GitHub push access to the victim repository. The `push` event path additionally lets the same attacker enqueue `sync_github` against an arbitrary tracked stack.

### Likelihood Explanation
This requires a Shipit instance configured with multiple GitHub organizations/apps (a documented, supported configuration) and an attacker who legitimately possesses one organization's `webhook_secret` (e.g., they administer that org's GitHub App or received the secret when it was provisioned) but has no relationship to the victim organization/repository. Given multi-tenant Shipit deployments are an explicit supported use case, this is a realistic configuration, though it does require the attacker to already hold a valid secret for *some* organization on the instance.

### Recommendation
After verifying the signature, re-derive the effective organization strictly from `repository.owner.login` used during verification and reject/ignore the webhook if any handler's resolved `Repository`/`Stack` owner does not match that same organization. Concretely, `Shipit::Webhooks::Handlers::Handler` should accept and check the verified `repository_owner` against `Repository#owner` before acting, and `StatusHandler`/`CheckSuiteHandler` (and any other sha-keyed handler) should scope their `Commit` lookup through `stack.repository.owner == verified_organization` rather than a bare global `sha` match.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret`, both tracked by the same Shipit instance (per the documented multi-org config) [1](#0-0) .
2. As the legitimate holder of `OrgA`'s `webhook_secret`, craft a `status` event payload: `{"sha": "<victim-commit-sha-in-OrgB-repo>", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/decoy"}}`.
3. Compute `X-Hub-Signature` using `OrgA`'s webhook secret over the raw JSON body.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` to `OrgA`, verifies successfully against `OrgA`'s secret [10](#0-9) .
5. `StatusHandler#process` matches the victim commit purely by `sha` regardless of `OrgA`/`OrgB` mismatch and creates a `success` status on it [5](#0-4) , potentially making an `OrgB` commit `deployable?` [8](#0-7)  and eligible for continuous deployment the attacker has no legitimate access to trigger.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
