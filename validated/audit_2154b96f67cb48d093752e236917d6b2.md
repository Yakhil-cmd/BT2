### Title
Permissionless `SafeMode::enter()` blocks emergency governance-cancellation calls (`Democracy::emergency_cancel`, `cancel_referendum`, `veto_external`, `cancel_proposal`, `Referenda::cancel`/`kill`, `Collective::disapprove_proposal`) - ([File: substrate/bin/node/runtime/src/lib.rs])

### Summary
The reported Telcoin bug is that an emergency-veto function (`challengeTransaction()`) is gated by `whenNotPaused`, so pausing the protocol also disables the only mechanism able to stop a malicious pending transaction. The same class of bug exists in the reference Substrate node runtime: entering `pallet-safe-mode` filters out *all* calls except a small whitelist, and that whitelist does not include the governance "emergency brake" extrinsics (`Democracy::emergency_cancel`, `cancel_referendum`, `veto_external`, `cancel_proposal`, `Referenda::cancel`/`kill`, `Collective::disapprove_proposal`). Crucially, entering safe-mode is **permissionless** (deposit-gated), so any unprivileged account can trigger the very state that disables the community's ability to cancel/veto a malicious governance action already in flight.

### Finding Description
`pallet-safe-mode`'s `Contains` implementation blocks every call whose pallet is not in `WhitelistedCalls` while safe-mode is entered: [1](#0-0) 

In the reference node runtime, the whitelist is defined as: [2](#0-1) 

Only `System`, `SafeMode`, and `TxPause` calls bypass the filter. This means once safe-mode is entered, calls like `Democracy::emergency_cancel`, `Democracy::cancel_referendum`, `Democracy::veto_external`, `Democracy::cancel_proposal`, `Referenda::cancel`, `Referenda::kill`, and `Collective::disapprove_proposal` — the exact set of extrinsics designed to stop a malicious or erroneous proposal/referendum before it executes — are also blocked.

Critically, entering safe-mode is not restricted to a privileged origin: it is configured with a non-`None` `EnterDepositAmount`, enabling permissionless entry by depositing funds, and can be repeatedly extended the same way: [3](#0-2) 

The pallet doc explicitly documents deposit-based permissionless entry/extension as a supported "primary feature": [4](#0-3) 

The relevant emergency-brake dispatchables exist and are intended for exactly this "stop a bad proposal before it executes" purpose: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

This reproduces the exact invariant violation from the report: the pause/circuit-breaker mechanism disables the very veto/cancellation mechanism that is supposed to remain available during an emergency.

### Impact Explanation
If a malicious or erroneous referendum/proposal has already been scheduled for enactment (e.g., via `Scheduler`), and any account (attacker or otherwise) enters safe-mode — permissionlessly, by depositing the configured amount — the `CancellationOrigin`/`VetoOrigin`/`CancelOrigin`/`DisapproveOrigin` holders lose the ability to call `emergency_cancel`, `cancel_referendum`, `veto_external`, `cancel_proposal`, `Referenda::cancel`, `Referenda::kill`, or `Collective::disapprove_proposal` for as long as safe-mode remains entered (`EnterDuration`, extendable via repeated `extend()` calls, also permissionless). If the scheduled malicious call executes while these calls remain blocked (or safe-mode is extended past the point of execution), funds could move or state could be corrupted without any way to intervene through the intended governance safety valve — this maps directly to the reported "funds might be stolen ... and/or further measures are required" impact category, at Medium severity.

### Likelihood Explanation
Likelihood depends on: (1) safe-mode being entered while a malicious proposal/referendum is pending cancellation, and (2) the malicious proposal being enacted before safe-mode is exited/`ForceExitOrigin` intervenes. Because entry/extension is permissionless (deposit-only, no privileged role required) per the runtime config shown above, an attacker or even an unrelated party triggering safe-mode during a contentious vote is plausible without requiring any privileged access, satisfying the "no privileged role" constraint from the scan brief. However, this specific whitelist/config combination is only present in the example `substrate/bin/node/runtime` reference runtime; production chains (Polkadot, Kusama, parachains) would need to be checked individually for whether they include `pallet-safe-mode` with a similarly narrow whitelist and permissionless entry, and whether Democracy/Referenda/Collective are wired into `BaseCallFilter` via `SafeMode`. I was not able to fully verify the `BaseCallFilter` wiring line and complete `construct_runtime!` pallet list within the available tool budget — this reference-runtime finding should be treated as an audit lead for the general pallet-safe-mode/pallet-tx-pause whitelist design pattern rather than a confirmed live production vulnerability.

### Recommendation
Add the emergency-cancellation/veto extrinsics of any governance pallets deployed alongside `pallet-safe-mode` (`Democracy::emergency_cancel`, `cancel_referendum`, `veto_external`, `cancel_proposal`; `Referenda::cancel`, `kill`; `Collective::disapprove_proposal`, and equivalents in `pallet-referenda`/`pallet-democracy` successors) to `SafeModeWhitelistedCalls` (and the analogous `TxPauseWhitelistedCalls`) so that emergency brakes remain callable while the protocol is in safe-mode/paused. Alternatively, restrict `EnterDepositAmount`/`ExtendDepositAmount` to `None` (privileged-only entry) so safe-mode cannot be triggered by an unprivileged actor to shield a pending malicious proposal from cancellation.

### Proof of Concept
No executable PoC was run against a live/test node within this session (tool access was limited to static code search/read, no terminal execution available). The finding is derived from static analysis of:
- `pallet_safe_mode::Pallet::is_allowed` filtering logic [1](#0-0) 
- The reference runtime's `SafeModeWhitelistedCalls` whitelist that omits governance-cancellation pallets [2](#0-1) 
- The permissionless (deposit-based) `EnterDepositAmount`/`ExtendDepositAmount` configuration enabling any account to trigger/extend safe-mode [3](#0-2) 
- Existing `pallet-safe-mode` unit tests demonstrating `enter()`/`extend()` via deposit (`can_activate`) and the `Contains` filter behavior, which a Devin agent could extend into an integration test combining `pallet-safe-mode` + `pallet-democracy`/`pallet-referenda` to demonstrate `emergency_cancel`/`cancel` being rejected by the call filter while safe-mode is active.

A concrete integration-test reproduction (constructing a mock runtime with `pallet-safe-mode`, `pallet-democracy` or `pallet-referenda`, wiring `BaseCallFilter = InsideBoth<DefaultFilter, SafeMode>`, entering safe-mode via deposit, and asserting `Democracy::emergency_cancel`/`Referenda::cancel` is rejected with `Error::CallFiltered`) was not executed in this session; this is flagged as unverified and would need to be run by a background agent with terminal access to produce pass/fail evidence.

		/// Schedule an emergency cancellation of a referendum. Cannot happen twice to the same
		/// referendum.
		///
		/// The dispatch origin of this call must be `CancellationOrigin`.
		///
		/// -`ref_index`: The index of the referendum to cancel.
		///
		/// Weight: `O(1)`.
		#[pallet::call_index(3)]
		#[pallet::weight((T::WeightInfo::emergency_cancel(), DispatchClass::Operational))]
		pub fn emergency_cancel(
			origin: OriginFor<T>,
			ref_index: ReferendumIndex,
		) -> DispatchResult {
			T::CancellationOrigin::ensure_origin(origin)?;

			let status = Self::referendum_status(ref_index)?;
			let h = status.proposal.hash();
			ensure!(!Cancellations::<T>::contains_key(h), Error::<T>::AlreadyCanceled);

			Cancellations::<T>::insert(h, true);
			Self::internal_cancel_referendum(ref_index);
			Ok(())
		}

		///
		/// The dispatch origin of this call must be `CancelProposalOrigin`.
		///
		/// - `prop_index`: The index of the proposal to cancel.
		///
		/// Weight: `O(p)` where `p = PublicProps::<T>::decode_len()`
		#[pallet::call_index(17)]
		#[pallet::weight(T::WeightInfo::cancel_proposal())]
		pub fn cancel_proposal(
			origin: OriginFor<T>,
			#[pallet::compact] prop_index: PropIndex,
		) -> DispatchResult {
			T::CancelProposalOrigin::ensure_origin(origin)?;

			PublicProps::<T>::mutate(|props| props.retain(|p| p.0 != prop_index));
			if let Some((whos, amount)) = DepositOf::<T>::take(prop_index) {
				for who in whos.into_iter() {
					T::Slash::on_unbalanced(T::Currency::slash_reserved(&who, amount).0);
				}
			}
			Self::deposit_event(Event::<T>::ProposalCanceled { prop_index });
			Self::clear_metadata(MetadataOwner::Proposal(prop_index));
			Ok(())
		}

		///
		/// - `origin`: must be the `CancelOrigin`.
		/// - `index`: The index of the referendum to be cancelled.

		/// Emits `Cancelled`.
		#[pallet::call_index(3)]
		#[pallet::weight(T::WeightInfo::cancel())]
		pub fn cancel(origin: OriginFor<T>, index: ReferendumIndex) -> DispatchResult {
			T::CancelOrigin::ensure_origin(origin)?;
			let status = Self::ensure_ongoing(index)?;
			if let Some((_, last_alarm)) = status.alarm {
				let _ = T::Scheduler::cancel(last_alarm);
			}
			if status.deciding.is_some() {
				Self::note_one_fewer_deciding(status.track);
			}
			Self::deposit_event(Event::<T, I>::Cancelled { index, tally: status.tally });
			let info = ReferendumInfo::Cancelled(
				T::BlockNumberProvider::current_block_number(),
				Some(status.submission_deposit),
				status.decision_deposit,
			);
			ReferendumInfoFor::<T, I>::insert(index, info);
			Ok(())
		}
