### Title
System-parameter governance can be swayed by transient, un-vested balances counted at vote-tally time - (File: main_chain.js, function: countVotes)

### Summary
The ZeroLend report shows that `VestedZeroNFT::mint` lacked an access-control check, letting an attacker self-mint a fully-unlocked ("no vesting") NFT and instantly obtain governance voting power without any real, time-locked commitment. The reachable analog in `ocore` is Obyte's on-chain system-parameter governance (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), where voting weight is likewise granted without requiring the voter to actually hold/lock the coins for any minimum period — weight is simply "whatever balance the address happens to have" at the moment the vote is tallied.

### Finding Description
Voting weight for system governance is computed in `countVotes()` [1](#0-0) . The function:

1. Selects every address that has *ever* cast a `system_vote` for the subject: `SELECT DISTINCT address FROM system_votes WHERE subject=?` [2](#0-1) .
2. Reads each of those addresses' **current** stable-good base-asset balance at the moment the MCI is being stabilized (i.e., "now", not at the time the vote message was posted) [3](#0-2) .
3. Loads that snapshot into a temporary `voter_balances` table and cross-joins it with the recorded vote choice to compute the winning value [4](#0-3) , [5](#0-4) .

There is no requirement that the balance used to weight a vote be the same balance that was held when the address originally cast that vote, nor any minimum holding/lock period on the coins. An address only needs to have voted once inside the (multi-year) eligibility window; whatever balance it has *right before the counting MCI stabilizes* is what gets counted. This mirrors the root cause of the ZeroLend bug: voting power is minted/acquired on demand right before it is used, with no genuine long-term stake behind it.

### Impact Explanation
`op_list` governance selects the network's Order Providers (witnesses), and the numerical subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) directly control consensus-critical fee/throughput parameters used by every node to validate and order units [6](#0-5) . Because vote weight is based on the balance held at count time rather than at vote time, a well-funded actor can:
1. Cast a minimal-value `system_vote` from a dormant/cheap address to become "eligible" within the vote window.
2. Shortly before the target MCI stabilizes, transfer a large balance into that same address (from an exchange, another wallet, etc.).
3. Have that transient balance counted at full weight in `countVotes`, then move the funds away again once the MCI has stabilized and the parameter/OP-list change has been written to `storage.systemVars`.

This lets an attacker deviate the OP-list or fee-parameter outcome from what genuine, committed stakeholders intended — directly matching "Manipulation of governance voting result deviating from voted outcome" — and because `op_list`/`threshold_size` affect main-chain stability determination network-wide, a skewed outcome can cause nodes to diverge on which units/witnesses are authoritative (node disagreement on validity/stability).

### Likelihood Explanation
Exploiting this requires no protocol bug beyond the missing time-locking/snapshot design: any address holder can perform the described sequence using ordinary payments (no special privilege needed), similar to how the ZeroLend attacker needed only ordinary token balance to self-mint full voting power. The main practical constraint is the `SYSTEM_VOTE_MIN_SHARE` / time-window expansion logic [7](#0-6) , which can force a larger aggregate voted balance to be reached, but does not prevent a single large actor from injecting a big transient balance right before stabilization.

### Recommendation
Snapshot and lock in each voter's balance (or a time-weighted/coin-age-weighted balance) at the time the `system_vote` unit is posted, rather than re-reading the live balance at count time; alternatively require the voting balance to have been held continuously (unspent) since before the vote was cast through to the counting MCI, so that transient/borrowed balances cannot be substituted in just before tallying.

### Proof of Concept
Conceptual (no code needed to prove the logic, per the "unknown" caveat below):
1. Address A casts a `system_vote` for `op_list` (or a numerical subject) with a small balance, satisfying "has voted" and (if needed) the `since_timestamp` recency window in `countVotes` [7](#0-6) .
2. Shortly before the MCI containing A's preferred outcome stabilizes, a large amount of bytes is transferred into A from elsewhere.
3. When `countVotes` runs for that MCI, the `bal_rows` query picks up A's now-large stable-good balance [3](#0-2)  and it is summed into `voter_balances`, giving A's stale vote outsized weight in the `op_list`/numerical-subject tally [5](#0-4) .
4. After the outcome is written to `storage.systemVars`, the funds can be moved out of A again.

Note: I was not able to fully trace every code path that produces/validates a `system_vote` message (e.g., its exact validation in `validation.js`/`writer.js`) within the available search results, so I cannot rule out an unseen minimum-holding-period or snapshot check outside the excerpts reviewed; if such a check exists elsewhere, this finding would need re-scoping. A Devin session with full repository access would be needed to confirm there is no such safeguard in `validation.js`/`writer.js`'s `system_vote` handling.
