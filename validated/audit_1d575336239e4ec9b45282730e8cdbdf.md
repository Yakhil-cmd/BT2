### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler acts on the independently-attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`. All downstream `Webhooks::Handlers` (push, status, check_suite, pull_request, membership) instead resolve the target `Repository`/`Stack` from `payload.dig('repository','full_name')`. These are two independent, attacker-supplied JSON fields inside the same signed body; nothing binds "the org whose secret validated this request" to "the repo the handler will mutate." Anyone who legitimately knows one organization's configured `webhook_secret` (e.g., the person who created that org's GitHub App in Shipit's config, per `test/dummy/config/secrets_double_github_app.yml`, which shows Shipit natively supports multiple orgs with independent secrets) can forge a fully valid, signed webhook whose `repository.owner.login` matches their own org (to pass `verify_webhook_signature`) but whose `repository.full_name` names a completely different organization's/repository's stack.

### Finding Description
- Signature verification: `verify_signature` computes `repository_owner` and fetches `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature(signature, request.raw_post)` [1](#0-0)  using `repository_owner` derived solely from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) .
- After verification passes, the entire raw payload (unmodified) is dispatched to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- Every base handler resolves the actual `Stack`/`Repository` it mutates from a *different* field, `repository.full_name`, not `repository.owner.login`: `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [4](#0-3) . The same pattern repeats in the pull-request handlers, e.g. `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) .
- The signature is a HMAC over the raw request body using the secret keyed to whatever organization the attacker puts in `repository.owner.login`/`organization.login` [6](#0-5) . Because `repository.owner.login` and `repository.full_name` are simply two independent string fields inside the same JSON object that the attacker fully controls before signing, nothing forces `full_name`'s owner segment to equal `owner.login`.

**Binding broken:** `organization authenticated by verify_signature == organization/repository written by the event handler`. Before the attacker's request: verification org == acted-upon repo's org (true for legitimate GitHub-originated payloads, since GitHub itself fills both fields consistently from the real push/PR event). After the attacker's forged request: verification org (their own, whose secret they know) != acted-upon repo's org (an arbitrary other tenant's stack), yet the request is accepted as `head(:ok)`/processed because `verify_webhook_signature` only checks the raw bytes against the secret for the org named in the same forged payload.

### Impact Explanation
Once past `verify_signature`, an attacker can trigger, against any repository/stack registered in the Shipit instance (not just their own org's), any of:
- `PushHandler#process`, which enqueues `stack.sync_github(expected_head_sha: params.after)` for stacks matching the forged branch [7](#0-6) , forcing a github sync against an attacker-chosen `expected_head_sha` for a victim stack.
- `StatusHandler#process`, which looks up commits **globally by sha with no repository scoping at all** and calls `commit.create_status_from_github!(params)` [8](#0-7) . `add_status` can flip a commit's simple state, which in turn calls `stack.schedule_merges` and, through `Commit#schedule_continuous_delivery`, enqueues `ContinuousDeliveryJob` for that stack if `deployable?` [9](#0-8)  and [10](#0-9) . This can result in an unauthorized deploy/merge being scheduled for a stack the attacker has no legitimate relationship with.
- `PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` etc. similarly act on `repository.full_name` to create/archive/unarchive review stacks belonging to other tenants.

This crosses the "cross-repository writes" / "unauthorized deploy, rollback or merge" impact bar (High/Critical) purely by forging a JSON body and computing an HMAC with a secret the attacker legitimately possesses for their own org — no Shipit session, `ApiClient` token, GitHub App private key, or repository write access on the *victim* repo is required.

### Likelihood Explanation
Medium-to-High in any multi-organization Shipit deployment (explicitly supported and documented — see `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo` each having distinct `webhook_secret`). Any org admin who set up their own GitHub App integration (and therefore knows their own `webhook_secret`) can compute a valid signature for a payload whose `repository.full_name`/`organization.login` fields are decoupled and pointed at a different tenant. The webhook endpoint is unauthenticated except for this single signature check, and is publicly reachable.

### Recommendation
Bind the organization used for signature selection to the organization actually acted upon:
- After selecting `repository_owner` and verifying the signature, re-derive/validate that the owner segment of `repository.full_name` (and `organization.login` if present) matches the same `repository_owner` used for verification, rejecting the request (422) on mismatch.
- Alternatively, have handlers resolve the target `Stack`/`Repository` using the same `repository_owner`/organization value that was cryptographically verified, rather than independently trusting `repository.full_name` from the unauthenticated-until-verified body.
- Additionally scope `StatusHandler#process`'s `Commit.where(sha: params.sha)` lookup to the verified repository/stacks rather than searching globally by sha.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker's own org, attacker knows `webhook_secret_A` because they created that GitHub App) and `OrgB` (victim, has a Stack registered for `OrgB/victim-repo`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, raw_body)` since they legitimately possess `webhook_secret_A`.
4. `POST /webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"OrgA"` from `repository.owner.login`, fetches `Shipit.github(organization: "OrgA")`, and the signature checks out against `webhook_secret_A` [1](#0-0) .
5. `PushHandler#process` then resolves the target stacks via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"` [4](#0-3)  and enqueues a sync/deploy pipeline for `OrgB`'s stack using attacker-controlled `after` sha — despite the attacker never having been authenticated for, or granted access to, `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
