## Analysis

The reported bug class — a router/pool instruction that transfers tokens from an attacker‑supplied "source" account using the caller's signature as authority, without verifying that the caller actually owns that source account — has a direct analog in this repository's swap instructions.

### Title
Missing token-account ownership constraint on `input_token_account` allows theft of arbitrary delegated token approvals in `swap_base_input`/`swap_base_output` — (File: `programs/cp-swap/src/instructions/swap_base_input.rs`)

### Summary
`Swap::input_token_account` (shared by both `swap_base_input` and `swap_base_output`, since `swap_base_output.rs` reuses the `Swap` accounts struct) has no Anchor constraint tying it to the `payer` signer. Compare this to `Deposit`/`Withdraw`, which both explicitly enforce `token::authority = owner` on the equivalent accounts. The swap transfer is then executed with `payer` as the SPL `transfer_checked` authority against whatever `input_token_account` the attacker supplies.

### Finding Description
In `Deposit`: [1](#0-0) 
both `token_0_account` and `token_1_account` are constrained with `token::authority = owner`, where `owner` is a `Signer`. This forces the source token account to actually belong to the signer.

In `Swap` (used by both `swap_base_input` and `swap_base_output`), no such constraint exists: [2](#0-1) 

The instruction then performs the transfer using `payer` as the CPI authority against the attacker-supplied `input_token_account`: [3](#0-2) [4](#0-3) 

`transfer_from_user_to_pool_vault` simply issues `token_2022::transfer_checked` with the supplied `authority`/`from` pair and does no additional ownership check itself: [5](#0-4) 

Because SPL Token's `transfer_checked` succeeds if the authority signer is either the account owner **or an approved delegate**, any account for which `payer` (the attacker, who only needs to sign the transaction) has been granted a delegate approval — for any reason, by any other dApp/user interaction — can be passed in as `input_token_account`. The attacker chooses `output_token_account` to be their own wallet, so swap proceeds flow to the attacker while the debited tokens come from the victim's delegated account.

### Impact Explanation
This allows outright theft of tokens for which a victim has granted a delegate/approval to the attacker's address (or, more critically, to a shared/PDA authority that also gets used as `payer` in some higher-level integration), by routing them through a swap instead of a deposit. It results in direct loss of user funds without any privileged access needed — only a token approval that the victim believes is scoped to a different, legitimate purpose. It maps to the same bug class as the source report: an unvalidated "source" address benefiting an attacker with an existing approval, exploited without the actual owner's involvement.

### Likelihood Explanation
Exploitability depends on the existence of a delegate approval from a victim to the attacker-controlled `payer` key. This is a real-world pattern for approvals granted to session keys, aggregator relayers, or other programs/services that later get used to sign a swap transaction on this pool — the attacker only needs one such delegated approval to reach `input_vault`. Given the codebase already recognizes the need for `token::authority = owner`/`payer` in `Deposit`/`Withdraw`, but omits it in `Swap`, this is a straightforward asymmetric-validation flaw reachable by a single unprivileged swap transaction with attacker-chosen accounts.

### Recommendation
Add a `token::authority = payer` constraint on `input_token_account` in the `Swap` accounts struct (mirroring `Deposit`'s `token_0_account`/`token_1_account`), ensuring the swap can only ever debit a token account actually owned by the signing `payer`.

### Proof of Concept
1. Victim approves address `A` (attacker-controlled) as a delegate on their `token_0` account for some unrelated legitimate reason (e.g., interacting with a different protocol that later turns out to be, or is impersonated by, the attacker).
2. Attacker constructs a `swap_base_input` instruction where `payer = A`, `input_token_account = victim_token_0_account`, `output_token_account = attacker_token_1_account`.
3. Anchor account validation for `Swap` passes because no ownership constraint exists on `input_token_account`.
4. `transfer_from_user_to_pool_vault` succeeds because `A` is a valid SPL delegate on `victim_token_0_account`, transferring victim funds into the pool vault.
5. The pool then sends the swapped `token_1` output to the attacker's own `output_token_account`, completing the theft.

```rust
pub fn transfer_from_user_to_pool_vault<'a>(
    authority: AccountInfo<'a>,
    from: AccountInfo<'a>,
    to_vault: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new(
            *token_program.key,
            token_2022::TransferChecked {
                from,
                to: to_vault,
                authority,
                mint,
            },
        ),
        amount,
        mint_decimals,
    )
}
```
