### Title
Webhook signature verification is keyed on `repository.owner.login`, but event processing is keyed on `repository.full_name` — allowing a webhook signed with one organization's `webhook_secret` to act on a different organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (each GitHub org configured with its own `webhook_secret` under `secrets.github`), `WebhooksController#verify_signature` selects the `GitHubApp`/secret to validate the HMAC signature using `repository_owner`, which is read straight from the unauthenticated JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Once the signature check passes, the very same untrusted payload is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and every handler resolves the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')` — a completely different field of the same payload that the "authenticating" field never binds to.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
using `repository_owner`: [2](#0-1) 

`Shipit.github(organization:)` picks the `GitHubApp` (and thus the `webhook_secret` used for `verify_webhook_signature`) strictly based on this `repository_owner` string taken from the request body itself: [3](#0-2) [4](#0-3) 

After the signature is validated against the secret for `repository_owner`, `create` dispatches the raw, attacker-controlled `params` to handlers unchanged: [5](#0-4) 

Every handler resolves which `Repository`/`Stack` to mutate using a *different* field of the payload — `repository.full_name` — via the shared base class: [6](#0-5) 
`Repository.from_github_repo_name` splits this into `owner/name` and looks up the DB row directly, with no cross-check against `repository.owner.login`: [7](#0-6) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon repository) are two independent, unauthenticated fields in the same JSON body, and the HMAC only proves that *some* field of the byte stream is unmodified relative to *a* known secret — not that these two fields agree — an attacker who controls (or has compromised) the webhook secret for **one** organization onboarded onto this Shipit instance can forge a signature that verifies successfully for `repository.owner.login = orgA`, while setting `repository.full_name = "orgB/some-repo"` for any other repository/organization managed by the same Shipit instance. Handlers such as `PushHandler` will then act on `orgB/some-repo`'s stacks: [8](#0-7) 

This breaks the intended binding: "the organization whose secret authenticated the request" == "the repository the request is permitted to act on." Instead the engine enforces: "the organization named in an unauthenticated JSON field" == "the repository the handler mutates," which is a strictly weaker and attacker-influenceable property.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Depending on which handler fires, this enables cross-repository/cross-organization effects using only knowledge of one org's (lower-trust) webhook secret — e.g. triggering `GithubSyncJob`/`sync_github` on a `push` event for an unrelated stack (`PushHandler`), creating/removing `Membership` or `Team` records cross-tenant (`membership` handler), or driving `ReviewStack` archive/unarchive/provisioning flows for another organization's repositories. In a genuinely multi-tenant Shipit installation (the only case where `github_app_config`/per-org secrets are meaningful) this is a cross-repository write achieved by forging a webhook that is valid for one org but is processed as if it targeted another. This matches the report's core defect pattern: a value that is checked/authenticated is not the same value that state-changing logic subsequently acts upon, letting an attacker recombine attacker-controlled fields to escape the intended trust boundary — directly analogous to Tokensoft's `initializeDistributionRecord()` minting for `_beneficiary`/`_amount` values covered by the merkle proof while other invariants (one-time use) were not enforced consistently with what the proof was meant to guarantee.

### Likelihood Explanation
Exploitability requires the attacker to possess a valid `webhook_secret` for *some* organization configured on the Shipit instance (their own onboarded org, or one leaked/compromised) — this is the multi-tenant analogue of "no privileged Shipit session/API token needed," since webhook secrets are configured per-GitHub-org outside of Shipit's own auth model and are commonly less tightly held than `api_clients_secret` or GitHub App private keys. Given that secret, forging the JSON body with mismatched `repository.owner.login` vs `repository.full_name` requires no additional privilege and is a single crafted HTTP POST to the public `/webhooks` endpoint. This is only meaningfully exploitable on installations that configure multiple GitHub organizations via `github_app_config`; single-org installations are not affected since there is only one secret to check against.

### Recommendation
After successful signature verification, re-derive/validate the acted-upon repository against the *same* organization used to select the verifying secret — e.g., in `Shipit::Webhooks::Handlers::Handler`, ensure `Repository.from_github_repo_name(repository_name).owner` matches the `repository_owner`/organization that the controller used for `Shipit.github(organization:)`, and reject (422) if they diverge. Alternatively, pass the verified organization down into each handler and have `stacks`/`Repository.from_github_repo_name` scope lookups to that organization instead of trusting `repository.full_name` alone.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, e.g. `orgA` (secret `SA`) and `orgB` (secret `SB`), each with at least one `Stack` synced from GitHub.
2. As an attacker who knows `SA` (e.g., a compromised or intentionally-provisioned webhook secret for `orgA`), craft a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(SA, raw_body)>` and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, obtains `orgA`'s `GitHubApp`, and successfully verifies the signature against `SA` — the request passes.
5. `PushHandler#process` is invoked with the same payload; it computes `stacks` via `Repository.from_github_repo_name("orgB/target-repo")`, finds `orgB/target-repo`'s stacks, and calls `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s repository — despite the request only being authenticated for `orgA`.

    # Backward compatibility

      config = secrets.github
    else
      config = github_app_config(organization)

  end
