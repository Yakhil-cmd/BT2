### Title
Arbiter contract dispute/appeal flow leaks device pairing secret to attacker-chosen ArbStore URL - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js` lets the counterparty in an arbiter contract offer freely choose the `arbiter_address` used for later dispute/appeal actions. When the victim (payer or payee) subsequently calls `openDispute`, `appeal`, or `getAppealFee`, ocore resolves that `arbiter_address` to a URL via the hub (`hub/get_arbstore_url`) and then POSTs a JSON payload containing `my_pairing_code` — which embeds the plaintext device `pairing_secret` — straight to that URL with `httpRequest`, with no validation that the URL belongs to a trusted/known ArbStore.

### Finding Description
An arbiter contract is created and offered by either party via `createAndSend()` [1](#0-0) , where the offeror freely sets `objContract.arbiter_address` and sends it to the peer as `"arbiter_contract_offer"`. The recipient stores the contract via `store()` trusting whatever `arbiter_address` was supplied [2](#0-1) .

Later, when the victim disputes or appeals the contract, the arbiter address is resolved to a URL purely through the hub lookup `hub/get_arbstore_url` [3](#0-2) [4](#0-3) [5](#0-4) . Since an attacker can name themselves (or an address they control) as `arbiter_address` in the contract they offer, and can register/claim an arbstore URL pointing at their own server for that same address, the hub will legitimately return an attacker-controlled URL for `hub/get_arbstore_url`.

The dispute/appeal payload embeds `my_pairing_code`, built from the device's permanent pairing secret:
```
var my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
``` [6](#0-5) [7](#0-6) 

This data is POSTed in plaintext JSON directly to the resolved (attacker-controlled) URL via `httpRequest`, without any allow-listing, TLS pinning, or user confirmation of the destination: [8](#0-7) 

The `pairing_secret` is the exact secret used by `device.js` to authenticate an inbound pairing request and add the sender as a trusted correspondent device (`handlePairingMessage`), which validates only that the presented `pairing_secret` matches a stored one before establishing a confirmed correspondent relationship [9](#0-8) . Anyone who obtains this secret can pair with the victim's device and be treated as a legitimate correspondent for e2e-encrypted chat/wallet messaging.

This mirrors the reported bug class exactly: a secret placeholder (the pairing secret) is interpolated into a destination that is effectively attacker-controlled (an ArbStore URL keyed off an attacker-chosen `arbiter_address`), and the secret is exfiltrated to that host without confirmation.

### Impact Explanation
Leaking the permanent `pairing_secret` lets the attacker pair with the victim's device as a "confirmed" correspondent (`handlePairingMessage` inserts into `correspondent_devices` and marks `is_confirmed=1`) [10](#0-9) . Once paired, the attacker can impersonate a trusted device to the victim's wallet, injecting messages such as further malicious `arbiter_contract_offer`s, payment/private-payment negotiation messages, or other device-messaging flows (`hub/deliver` path) that the wallet UI treats as coming from a legitimate paired device [11](#0-10) . This creates a foothold for social-engineering-driven fund loss/theft (e.g. tricking the user into signing multisig payments, textcoin sends, or accepting fraudulent arbiter resolutions) — reachable purely from a private-payment counterparty crafting an arbiter contract, with no privileged access required.

### Likelihood Explanation
The attack only requires the attacker to act as a normal arbiter-contract counterparty (already an in-scope reachable actor) and to designate an address they control as `arbiter_address`, then register/claim a corresponding ArbStore URL with the hub for that address. No cryptographic bypass is needed — the code path is a straightforward, always-executed feature (dispute/appeal/get_appeal_fee) whenever the victim uses those legitimate contract functions with an attacker-selected arbiter.

### Recommendation
- Do not include `my_pairing_code` / `pairing_secret` in the dispute/appeal HTTP payload sent to an ArbStore; the ArbStore does not need the raw pairing secret, only a way to contact the party (e.g., send it end-to-end encrypted to the counterparty's device instead, as is already done for `encrypted_contract`).
- If the pairing code must be relayed to the ArbStore, encrypt it for the ArbStore's `device_pub_key` (same pattern used for `encrypted_contract`) rather than sending it in cleartext JSON.
- Validate/allow-list ArbStore URLs (e.g., via a signed registry or well-known list) rather than trusting an arbitrary hub-returned URL tied to a user-chosen `arbiter_address`.

### Proof of Concept
1. Attacker proposes an arbiter contract to victim via `createAndSend()`, setting `arbiter_address` to an address the attacker controls.
2. Attacker registers an ArbStore URL for that `arbiter_address` pointing to `https://attacker.example/`.
3. Victim accepts, pays, and later calls `arbiterContract.openDispute(hash, cb)` or `.appeal(hash, cb)`.
4. ocore resolves `hub/get_arbstore_url` for the attacker's address to `https://attacker.example/`, then POSTs `{ ..., my_pairing_code: "<pubkey>@<hub>#<pairing_secret>", ... }` to `https://attacker.example/api/dispute/new` (or `/api/appeal/new`) — see [12](#0-11)  and [13](#0-12) .
5. Attacker now possesses the victim's `pairing_secret` and can pair with the victim's device via `device.js`'s pairing flow.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)",
