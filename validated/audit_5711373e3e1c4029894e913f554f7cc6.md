## Analysis

**Binding claimed to be broken:** `commit.deployable?` should equal true **iff** `commit.status.state == 'success'` **and** every `Status` row contributing to that state has `provenance_repository == stack.repository.full_name`. In the actual code, `commit.deployable?` (`app/models/shipit/commit.rb:227-229`) equals true whenever `commit.status.state == 'success' && !blocked?`, with `status` built purely from `Status` rows attached to `commit_id`/`stack_id` — **with no field or check recording which webhook-authenticated repository produced the row**. Before vs. after: both sides of the equality collapse to the same thing (any row with matching `commit_id`), so the binding is broken by construction, not by a subtle omission.

**Path:**
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves the GitHub App/secret via `repository_owner`, which is read straight from the attacker-controlled payload: `params.dig('repository','owner','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`). An attacker who owns their own GitHub org/repo gets a **genuinely, correctly signed** `status` webhook from GitHub for that org — signature verification passes legitimately, because it is only proving "this event came from GitHub for org X," not "org X owns this commit/stack."
2. `Shipit::Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is an **unscoped, instance-wide** lookup by `sha` alone — no join/filter against `Repository.from_github_repo_name(repository_name)` or the commit's `stack.repository`, unlike every other handler (`PushHandler`, `PullRequest::*Handler`) which uses the base `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) scoped to `Repository.from_github_repo_name(repository_name)`.
3. `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) writes the `Status` using the **victim commit's own `stack_id`** — i.e. the forged row is indistinguishable from a legitimate status on the victim stack, because it was written scoped to that commit's real, pre-existing stack ownership.
4. `Commit#deployable?` / `Commit#status` (delegated via `commit_checks.rb` / `status/group.rb`) reads all `Status` rows for that `commit_id` with no origin/provenance filter, so the forged `state: 'success', context: <victim's required check>` row satisfies `success?` and (if it also matches the configured required context) clears any `required_statuses` gate too.
5. An operator or `continuous_deployment` job later calls `Api::DeploysController#create` (`app/controllers/shipit/api/deploys_controller.rb:19-27`, which checks `commit.deployable?` only when `require_ci` is set — and continuous delivery paths check it unconditionally) or `Stack#next_expected_commit_to_deploy` → `deployable?`, and the deploy proceeds via `Command#start` on the deploy host, executing code that never received a real "success" from the actual repository's CI.

**Why guards don't catch it:** `verify_signature` only authenticates the org/app named in the attacker's own payload; it says nothing about which `Commit`/`Stack` the payload's `sha` is allowed to touch. `ExplicitParameters` validates types, not repository scoping. No model validation ties `Status#context`/`state` to a repository identity — `Status` (`app/models/shipit/status.rb`) has no repository/provenance column at all.

**Precondition dependency:** This exploit is entirely dependent on the previously-identified `StatusHandler` cross-repo write bug — i.e. the ability for an attacker's own signed webhook to write a `Status` row against a commit belonging to a stack/repository they don't own, via `Commit.where(sha: params.sha)` global lookup. That precondition is itself present in this codebase (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), and I was able to confirm it directly, not just assume it based on the prompt's framing.

Given that the cross-repo write is real, and `deployable?`/`status` provide zero additional provenance check on top of it, the deploy-gating bypass described in the question is a genuine, valid consequence of the same root cause — not a new independent binding violation, but rather this question demonstrates that the fix must be applied at the write site (`StatusHandler`) because there is no compensating control downstream in `Commit#deployable?`/`Stack#deployable?`.

### Title
Deploy gating (`Commit#deployable?`) trusts CI status rows forged cross-repo via unscoped `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with a bare `Commit.where(sha: params.sha)`, with no filter tying the webhook's authenticated repository to the commit's actual owning stack/repository, unlike every sibling handler. Because SHAs are content-addressed and can collide across a public fork lineage, any GitHub user who owns their own repo can emit a genuinely-signed `status` webhook that writes a forged `success` `Status` row onto a victim commit, which `Commit#deployable?` then trusts unconditionally.

### Finding Description
The broken binding: `commit.deployable?` should only be `true` when all contributing `Status` rows originate from a webhook authenticated for `commit.stack.repository.full_name`, i.e. `status.provenance_repo == stack.repository.full_name`. Instead `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is computed purely from `commit.status.state`/`blocked?`, over `Status` rows that carry no repository provenance at all (`app/models/shipit/status.rb`).

Root cause: `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up commits by `sha` across the entire instance instead of scoping to `stacks` (the pattern used by `PushHandler` and the `PullRequest::*` handlers via `Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`, which resolves `Repository.from_github_repo_name(repository_name)`). `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only proves the payload came from GitHub for the org named in the attacker's own payload (`repository_owner`, line 59-61); it makes no claim about which commit/stack that org is allowed to affect.

Attack: attacker owns `attacker/fork` (a public fork of `victim/repo`, sharing history/SHAs). They push/merge so a shared commit SHA exists in both repos, or simply target a still-shared ancestor commit. They trigger (or directly emit) a `status` event from their own repo with `sha=<shared-sha>`, `state=success`, `context=<victim's required CI context>`. GitHub signs this correctly for `attacker`'s org, `verify_signature` passes, `StatusHandler` finds the `Commit` row belonging to `victim`'s `Stack` by SHA alone, and writes a `Status` scoped to `victim`'s `stack_id` via `create_status_from_github!` → `replicate_from_github!` (`app/models/shipit/commit.rb:165-169`).

An operator or continuous-deployment job later calls `commit.deployable?`/`stack.next_expected_commit_to_deploy` and observes `success?` true, deploying a commit that never passed the victim repository's actual CI.

### Impact Explanation
A payload from one (attacker-owned) repository forges deploy-gating state for another (victim) repository's stack, satisfying the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" criteria — Critical severity. The forged status is written for any commit whose SHA the attacker can arrange to match (shared ancestor history via public fork, or engineered content collision), so it is repeatable against any victim stack whose repository has a public/forkable history and whose commits transiently share SHAs with attacker-controlled repos. Ultimately it lets an operator trigger `Command#start` deploying code presented as CI-green when it is not.

### Likelihood Explanation
Preconditions: attacker must own a GitHub org/repo (trivial, free), Shipit must be configured to receive `status` webhooks from that org (only requires the org's own GitHub App/webhook secret, which the attacker controls for their own org), and the target victim commit SHA must exist as a `Commit` record in Shipit's DB (naturally true for any commit reachable in the victim's tracked branch history, including shared ancestors with public forks). No Shipit credentials, session, or victim GitHub credentials are needed. Cost is a single webhook/API call; it is repeatable for every shared SHA.

### Recommendation
Scope `StatusHandler#process` to the webhook's own authenticated repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Additionally, consider recording repository provenance on `Status` and asserting it matches `stack.repository.full_name` before allowing a status to affect `deployable?`, as defense in depth.
