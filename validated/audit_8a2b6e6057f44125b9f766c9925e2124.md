### Title
Cross-repository SHA collision in `StatusHandler` lets one repository's status webhook mutate/merge-schedule an unrelated stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub status to purely `by sha`, with no filter on the webhook payload's `repository.full_name`, unlike every sibling handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest` handlers) which all scope through `stacks`/`Repository.from_github_repo_name`. Because git SHAs are content-addressed and not namespaced per repository, an attacker who controls a repository sharing a SHA with a victim stack's commit (e.g. via a fork or shared history) can trigger a real, validly-signed `status` webhook from their own repository and have it applied to the victim's `Commit`, cascading into `Stack#schedule_merges` on the victim stack.

### Finding Description
The claimed binding is: `stack (passed to Hook.emit/schedule_merges inside Commit#add_status) == stack named by payload.repository.full_name`.

Tracing the code:
- `StatusHandler#process` does: [1](#0-0) 
This runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across **all** stacks/repositories in the Shipit instance.

- Compare to the base `Handler` class, whose `stacks` helper (used by `PushHandler`, `CheckSuiteHandler`, and all `PullRequest` handlers) resolves the payload's repository first via `Repository.from_github_repo_name(repository_name)` before touching any stack: [2](#0-1) 
`StatusHandler` is the only handler that bypasses this scoping entirely and never references `params.repository` at all — the `params` schema for `StatusHandler` doesn't even require a `repository` block: [3](#0-2) 

- Inside `Commit#create_status_from_github!` → `add_status`, the `stack` used for hooks and merge scheduling is `commit.stack` (the commit's own persisted association), determined solely by which `Commit` row matched `sha`: [4](#0-3) [5](#0-4) 

So the two sides of the binding diverge: `stack` is bound to `commit.stack` (derived from `Commit.where(sha:)` across the whole table), while the payload's `repository.full_name` is never consulted to filter that lookup. If any commit on any unrelated stack S2 shares a SHA with the one referenced in a status webhook signed for R1, `S2.schedule_merges` fires as a side effect of R1's own status event.

Exploit flow:
1. Attacker owns and controls repository R1, which has a Shipit stack S1 (with an empty `blocking_statuses`/`required_statuses` deploy_spec — irrelevant to this specific path, but consistent with a low-friction CI setup on R1).
2. Attacker finds/arranges a commit SHA shared between R1 and victim's tracked repository/stack S2 (SHAs are content-addressed; forks, cherry-picks, or shared history make identical SHAs across distinct repositories routine).
3. Attacker (as owner of R1) creates a commit status on that SHA in R1 via the normal GitHub UI/API — a completely ordinary, unprivileged action on a repo they own.
4. GitHub itself computes and sends the `status` webhook to Shipit, signed with the real secret configured for R1's installation. `WebhooksController#verify_signature` validates it successfully because it is a genuine, correctly-signed GitHub webhook — no secret is stolen or forged.
5. `StatusHandler#process` receives this and matches `Commit.where(sha: params.sha)`, which returns **all** commits sharing that SHA, including the one belonging to victim stack S2.
6. `Commit#add_status` is invoked on the S2 commit and, if the status is `pending` or `success`, calls `stack.schedule_merges` — where `stack` is S2 — enqueuing `ProcessMergeRequestsJob.perform_later(S2)`.

Why existing guards fail: `verify_signature` only authenticates *which organization* sent the webhook (matching `repository_owner` to a configured GitHub App/secret); it says nothing about which `Commit`/`Stack` rows the payload is allowed to touch. `ExplicitParameters` schema for `StatusHandler` doesn't require or use `repository` at all, so there is no application-level check tying the status to the repository that owns it. No `stacks`/`Repository.from_github_repo_name` scoping is applied for this handler, unlike all its siblings.

### Impact Explanation
A payload originating from repository R1 (fully controlled by the attacker) can write a `Status` record onto and trigger `Stack#schedule_merges` for an unrelated victim stack S2, purely because of a SHA match with no repository check. This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius is any Shipit-tracked stack whose commit history overlaps by SHA with a repository the attacker controls (forks of open-source projects being the most direct real-world case), and the attack is repeatable at will since the attacker can post as many statuses as desired against SHAs they choose within their own repo.

### Likelihood Explanation
- Preconditions: Shipit must track a webhook `status` handler (default configuration; `REQUIRED_HOOKS = %i[push status]` on `Stack`) and a SHA collision must exist between attacker's controlled repository and a victim's tracked commit history. Forking (or having previously forked) an upstream repository that also has a Shipit stack is a normal, low-cost, entirely legitimate action requiring no privileges beyond GitHub account ownership.
- Attacker cost: none beyond owning a GitHub repository and posting a status via the standard GitHub API on a commit they can reference — no Shipit credentials, secrets, or elevated GitHub permissions are needed.
- Feasibility/repeatability: high — this is triggerable at will and does not depend on any race condition or timing; the only constraint is finding/aligning a shared SHA, which is trivial for forked repositories.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository the same way every other handler does: require `repository.full_name` in the `params` schema, resolve `stacks` via `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `stacks.flat_map(&:commits)` (or a joined query filtered by `stack_id in stacks`) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, out of scope to edit `test/**` per rules but illustrating the binding failure conceptually):
```ruby
test "status webhook for repository R1 must not schedule merges on unrelated stack S2 sharing the same commit sha" do
  s1_stack = shipit_stacks(:shipit)                 # tracks repo R1, attacker-controlled
  s2_stack = shipit_stacks(:cyclimse)               # tracks unrelated repo R2, victim
  shared_sha = "deadbeef" * 5

  s1_stack.commits.create!(sha: shared_sha, ...)
  victim_commit = s2_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    "sha" => shared_sha, "state" => "success",
    "repository" => { "full_name" => s1_stack.github_repo_name, "owner" => { "login" => s1_stack.repository.owner } }
  }

  # Binding under test: stack passed to schedule_merges == stack named by payload.repository.full_name (s1_stack)
  Shipit::Stack.any_instance.expects(:schedule_merges).never  # for s2_stack specifically

  assert_no_enqueued_jobs only: ProcessMergeRequestsJob do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # currently FAILS: ProcessMergeRequestsJob IS enqueued with [s2_stack], proving divergence
end
```
This demonstrates `Stack#schedule_merges` firing on S2 as a side effect of a payload whose `repository.full_name` names S1, confirming the broken binding.
