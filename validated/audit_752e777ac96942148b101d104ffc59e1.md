### Title
Stored `Account.owner` is never synced with the position NFT owner, so `position-nft::transfer` does not transfer spending authority and the seller retains control of all funds — (`File: contracts/controller/src/account.rs`)

### Summary
Each controller account is keyed by a position NFT whose `owner_of` is documented as "the account owner" (`contracts/position-nft/src/contract.rs:1-3`). However, every fund-moving entrypoint (`withdraw`, `borrow`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, `flash_position`) authorizes the caller against `account.owner` — a field written once at `create_account_with` (`contracts/controller/src/account.rs:64-70`) — via `require_owner_or_delegate`, which simply checks `caller == owner` or a delegate recorded under that stored owner (`account.rs:115-140`). Nothing in the codebase updates `account.owner` on an NFT transfer: `position-nft::transfer`/`transfer_from` are stock OpenZeppelin methods (`contract.rs:131-133`) that only call `Base::update` inside the NFT contract and have no callback into the controller, and `burn`/`mint` are controller-only. Meanwhile `require_account_owner` (used by `add_delegate`, `remove_delegate`, `renew_account`) authenticates via `storage::account_owner` — the NFT owner — so the controller deliberately mixes two sources of truth for "owner" (`account.rs:143-148` vs `account.rs:130-140`). The stale stored owner keeps full spending authority forever; the NFT holder gets none of it.

### Impact Explanation
An unprivileged seller can list or transfer a position NFT, receive payment off-chain or in a DEX sale, and then — still being `account.owner` — call `controller::withdraw(account_id, ...)` and `controller::borrow(account_id, ...)` to pull out every unit of the NFT holder's collateral and push the account into bad debt. Conversely, an account owner can `transfer` the NFT to a victim (or sell it), wait for the buyer to `supply` additional collateral into "their" account (supply is permissionless for existing slots per `permissionless_entrypoints.txt:69`), and drain it. Delegates granted by the previous owner also remain active because `get_delegates` is keyed on the stored owner (`account.rs:126`), so the seller's manager-contract delegates can drain as well. This is theft of user funds — the highest-impact broken access control analog: the authorization check consults a stale, attacker-controlled identity instead of the current NFT owner.

### Likelihood Explanation
Any user can reach this with two ordinary calls: `position-nft::transfer(from, to, token_id)` followed by the seller calling `controller::withdraw`/`borrow` on the same `account_id`, which passes `require_owner_or_delegate` because the stored `owner` still equals the seller. No privileged role, leaked key, or timing window is required; the NFT-transfer ordering (payment) is easily arranged via any marketplace or OTC deal, since the protocol's own documentation presents the NFT as the account ownership token (`contract.rs:1-3`, `permissionless_entrypoints.txt:106`). The invariant file itself claims "delegate grants from the previous owner go inactive" (`permissionless_entrypoints.txt:111`), which is false under this code path — delegates are looked up under the stale stored owner — indicating the divergence between the two ownership sources is unintended.

### Recommendation
Make the controller's spending-authority checks read the same ownership source as `require_account_owner`: have `require_owner_or_delegate` resolve the current owner via `storage::account_owner` (NFT `owner_of`) rather than the stored `account.owner`, or drop `Account.owner` from storage entirely and always query the NFT. Key delegate grants by `account_id` alone (or the NFT owner at query time) so a transfer reliably revokes prior delegates. Alternatively, hook NFT `transfer`/`transfer_from` to notify the controller and rewrite `account.owner` and re-key/clear delegate entries atomically — but the read-through approach is simpler and cannot desynchronize.

### Proof of Concept
```text
Preconditions: Attacker owns account_id = 7 (stored Account.owner = Attacker,
NFT 7 owner = Attacker) holding 100k USDC collateral.

1. Attacker sells NFT 7 to Victim (marketplace/OTC): the NFT contract runs
   position-nft::transfer(Attacker, Victim, 7). Base::update sets
   Owner(7) = Victim. Controller storage is untouched: Account{owner: Attacker}.

2. Victim (now NFT owner) calls controller::supply to top up collateral,
   or simply believes they own the 100k. Any withdraw they attempt via
   controller::withdraw(Victim, 7, hub, usdc, ...) reverts in
   require_owner_or_delegate because caller != account.owner (Attacker).

3. Attacker calls:
     controller::withdraw(Attacker, 7, hub_id, USDC, 100_000e7, Attacker)
   → caller.require_auth() passes (Attacker signs)
   → require_owner_or_delegate(env, 7, Attacker, account.owner=Attacker) → ok
   → collateral paid to Attacker.

4. Attacker additionally calls:
     controller::borrow(Attacker, 7, hub_id, XLM, max_ltv_amount, Attacker)
   borrowing the market against the now-doomed account; post-HF check only
   requires solvency at the moment of borrow. The account is left
   over-leveraged; the NFT holder inherits the debt and liquidation while
   Attacker keeps the proceeds.

Result: full expropriation of the NFT buyer's collateral plus protocol debt,
using only the documented transfer and two permissionless caller-auth
entrypoints.
```

Caveat: I could not read `storage::account_owner`'s implementation or every call site passing `&account.owner` within the available iterations; the finding rests on `Account.owner` being set at creation (`account.rs:64-70`) and `require_owner_or_delegate` comparing against it (`account.rs:121`), with no code path updating that field on NFT transfer. If `storage::get_account` itself rewrites `owner` from the NFT on load, this finding is void — but `account.rs:143-146` distinguishing `storage::account_owner` from `storage::get_account_meta`, and the delegate-keying design, indicate it does not.
