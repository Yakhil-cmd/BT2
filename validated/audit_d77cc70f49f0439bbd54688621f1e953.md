### Title
Auto-destroy asset accounting mismatch lets an AA's `balance[asset]`/`aa_balances` be inflated with unspendable "burned" funds - ([File: aa_composer.js])

### Summary
When an AA defines an asset with `auto_destroy: true` and `issued_by_definer_only: true` (the AA itself as definer/redemption sink), any unprivileged user can send that asset back to the AA. The AA's balance bookkeeping (`aa_balances` table and the `balance[asset]` formula) unconditionally credits the received amount, while the coin-selection logic used to actually *spend* that asset explicitly excludes outputs sitting at the definer's own address when the asset is `auto_destroy`. This produces the same root-cause pattern as the CashCowCoin incident: a token-burn/reserve-sync operation that updates one accounting dimension (the AA's internal balance ledger, analogous to the Pair's reserve state) without correctly reflecting that the underlying value has actually been destroyed/is unusable, and this can be repeated by any external unprivileged trigger sender.

### Finding Description
`updateInitialAABalances` and `updateFinalAABalances` in `aa_composer.js` add every payment output sent to the AA's address into `objValidationState.assocBalances[address][asset]` / the `aa_balances` table, with no special-case for `auto_destroy` assets whose definer is the receiving AA itself: [1](#0-0) [2](#0-1) 

This same ledger value is what the `balance[asset]` oscript formula reads (`readBalance()` in the formula engine pulls straight from `objValidationState.assocBalances` / `aa_balances`): [3](#0-2) 

However, when the AA later tries to actually *spend* funds of that same asset (e.g. to pay out a response), the coin-selection routine explicitly refuses to pick up any outputs that were sent to the definer address for an `auto_destroy` asset, treating them as permanently destroyed and unusable: [4](#0-3) [5](#0-4) 

This is consistent with how `validation.js` treats a payment sent to the definer of an `auto_destroy` asset as effectively burnt and unspendable in future transfers: [6](#0-5) [7](#0-6) 

So there are two disjoint views of the same event:
- The ledger (`aa_balances`, and everything `balance[asset]` exposes to AA logic) treats the incoming, self-addressed `auto_destroy` payment as a normal balance increase.
- The spend path treats the very same output as permanently unusable/burned.

This is structurally the same defect class as the CashCowCoin report: a "burn" step (auto_destroy) that is not reflected consistently in the internal accounting used elsewhere by the contract logic (here, the AA's own `balance[]`), so the on-chain "reserve" tracked by the AA can be repeatedly inflated by an unprivileged user with real, unusable value, while the AA logic (which typically relies on `balance[asset]` to decide how much it can safely pay out, mint, or treat as backing — see the built-in AMM/market-maker patterns that key off `balance[$asset]` for constant-product calculations) is misled.

### Impact Explanation
Any AA that issues a redeemable/uncapped `auto_destroy`, `issued_by_definer_only` asset (a documented, supported ocore asset-definition pattern) is affected. Because `balance[asset]` and `aa_balances` do not distinguish "spendable" from "destroyed-but-still-owned-by-definer" outputs, an unprivileged attacker can, with each trigger unit, inflate the AA's apparent balance of that asset without giving the AA any actually usable funds. Downstream AA logic that computes payouts, ratios, or accounting invariants from `balance[asset]` (a pattern explicitly supported and demonstrated by the shipped AMM/order-book sample AAs that key off `balance[$asset]`) can be driven into an inconsistent state: either it believes it holds more backing than it can spend (leading to failed/stuck payouts — fund freezing), or, for uncapped `issued_by_definer_only` assets, the fallback issuance path in `completePaymentPayload`/`issueAsset` can mint fresh supply to make up for the "missing" spendable coins that the ledger claims exist, i.e. uncontrolled new issuance backed by nothing: [8](#0-7) 

This maps to the accepted impact categories of AA fund loss/freezing and, in the uncapped case, unauthorized supply inflation — repeatable over many iterations by a single unprivileged actor, exactly mirroring the "≈80 iterative cycles" draining pattern in the CCC report.

### Likelihood Explanation
Reachable by any address that can post a normal payment unit to an AA — no special privilege, no reliance on a malicious peer/hub/node. The only precondition is that the target AA defines (or accepts trigger-driven definition of) an `auto_destroy` + `issued_by_definer_only` asset with itself as definer, which is a standard, documented, and demonstrated ocore AA capability (see `aa_validation.js` asset-message validation, which explicitly allows AAs to define such assets). Triggering the mismatch requires no unusual timing or race condition — a single self-directed payment of the asset is sufficient per iteration, and repeating it linearly inflates the divergence.

### Recommendation
When crediting `aa_balances`/`assocBalances` in `updateInitialAABalances`/`updateFinalAABalances`, detect the case where the asset is `auto_destroy` and `issued_by_definer_only` and the receiving address equals the asset's `definer_address`; either exclude such amounts from the balance credit or track them in a separate, clearly-labeled "destroyed" counter that AA logic and `balance[asset]` cannot conflate with spendable funds. Ensure `balance[asset]` and the coin-selection logic in `completePaymentPayload`/`readStableOutputs` share one consistent notion of "AA-spendable balance" for `auto_destroy` assets.

### Proof of Concept
1. An AA `X` defines asset `A` with `issued_by_definer_only: true`, `auto_destroy: true`, no `cap` (uncapped), `X` as definer — a pattern explicitly supported per `aa_validation.js`'s asset-message validation.
2. Any unprivileged attacker who holds any amount of `A` (or obtains it via `X`'s normal issuance flow) sends a payment of `A` back to `X`'s own address as a trigger.
3. `updateInitialAABalances`/`updateFinalAABalances` increase `aa_balances`/`assocBalances[X][A]` by the received amount (`aa_composer.js:481-485`, `556-570`), and this becomes visible to `X`'s oscript via `balance[A]`.
4. Because the output was sent to the definer of an `auto_destroy` asset, `completePaymentPayload`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` (`aa_composer.js:1140-1144`, `1157-1160`) will never select it as spendable input.
5. Repeat step 2 across multiple trigger units: `balance[A]` keeps climbing with value that `X` can never actually move, while any AA logic keyed off `balance[A]` (e.g. AMM-style payout/ratio formulas, or a re-issue path in `issueAsset`, `aa_composer.js:1175-1212`, for the uncapped case) computes against a phantom reserve — leading to stuck/failed payouts (fund freezing) or, for the uncapped issuance branch, minting of new supply not backed by real spendable funds.

*Note: full end-to-end confirmation of the downstream `issueAsset` re-mint trigger conditions (exact code path connecting insufficient spendable coins to the issuance fallback for a non-base asset within `completePaymentPayload`) was not fully traced line-by-line due to the reasoning budget; the ledger/spend-path divergence itself (steps 1-4) is directly confirmed against the cited code.*
