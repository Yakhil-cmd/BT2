### Title
`gh release view` writes attacker-controlled release body directly to `IO.Out`, bypassing ANSI sanitization - (File: pkg/cmd/release/view/view.go)

### Summary
`gh release view` renders the release description (`release.Body`, sourced verbatim from the GitHub API `body` field of a release the victim did not author) through `fmt.Fprint`/`fmt.Fprintln` directly on `opts.IO.Out`/`io.Out` in both `renderReleaseTTY` and `renderReleasePlain`, instead of `opts.IO.ContentOut` or `iostreams.Untrusted`. Unlike `gist view` and `pr diff`, which explicitly sanitize or refuse escape sequences before printing, `release view` performs no ANSI-escape check or sanitization anywhere in this path.

### Finding Description
`Release.Body` is decoded directly from JSON as a plain `string`, with no `Untrusted` typing or provenance tracking. [1](#0-0) 
An unprivileged attacker who can create a release (or a repository the victim runs `gh release view` against, e.g. via a fork the victim inspects, or any repo they can publish releases to that the victim later views) fully controls this `body` text, including embedded ANSI escape sequences (0x1B).

In `viewRun`, the body flows to `renderReleaseTTY` (TTY case) or `renderReleasePlain` (non-TTY/machine-readable case). [9](#0-8) 
`renderReleasePlain` prints `release.Body` with a raw `fmt.Fprint(w, release.Body)` where `w` is `opts.IO.Out` — zero sanitization, zero escape-sequence detection. [2](#0-1) 
`renderReleaseTTY` passes `release.Body` into `markdown.Render` and writes the result to `io.Out` (aliased from `opts.IO.Out`), again with no sanitizer in between. [3](#0-2) 
`markdown.Render` is a passthrough to glamour rendering with no ANSI-stripping step of its own. [4](#0-3) 

This is exactly the "forgot to route untrusted content through ContentOut" scenario described in the question: sibling commands (`gist view`, `pr diff`) were updated to use `iostreams.Untrusted`/`ContentOut` and explicit `ContainsEscapeSequence` checks, but `release view` was never updated to use this model, even though it displays remote, attacker-supplied text.

### Impact Explanation
An attacker publishes (or edits) a GitHub release with a body containing ANSI/terminal escape sequences (e.g., cursor movement, terminal title rewrite, OSC 52 clipboard write, or sequences that redraw the screen to spoof a fake prompt). When a victim runs `gh release view` (or `gh release view <tag>`, including the default `--json`-less path or the machine-readable/piped path), the escape sequences are written unmodified to the victim's terminal. This enables terminal/prompt spoofing and, depending on terminal emulator, more severe escape-sequence abuses (e.g., title-bar manipulation, clipboard injection via OSC 52, or crafted output that tricks the user into running attacker-suggested commands). This matches the "terminal escape sequence / output sanitization bypass" impact class referenced in the question (ANSI/escape injection to terminal, prompt forgery).

### Likelihood Explanation
Fully attacker-reachable with no special privileges: any user who can create or has already created a release on any repository (including a public repo the victim inspects) controls the release body. The victim merely needs to run the ordinary command `gh release view` against that repository/tag. Both the TTY-rendered path and the plain/piped path are affected, making this trivially reproducible and 100% repeatable.

### Recommendation
Route `release.Body` through the same untrusted-content model used elsewhere: type `Release.Body` as (or wrap it at render time in) `iostreams.Untrusted`, sanitize before feeding into `markdown.Render` (as `gist view` does via `content.String()`), and write the final output through `opts.IO.ContentOut` instead of `opts.IO.Out` in both `renderReleaseTTY` and `renderReleasePlain`. For the plain/non-TTY path, additionally apply the same `ContainsEscapeSequence` refusal pattern used in `pr diff`/`gist view` (optionally gated by an `--allow-escape-sequences` flag) before writing raw body text.

// SetContentSanitization toggles ANSI escape sanitization on ContentOut.
// Commands should call this with false when an explicit opt-out flag (e.g.
// --allow-escape-sequences) is set, so subsequent writes of external content
// pass through unmodified.
func (s *IOStreams) SetContentSanitization(enabled bool) {
	s.sanitizeContent = enabled
	s.ContentOut = newContentWriter(s.Out, enabled)
}

// newContentWriter returns the writer to wire up as ContentOut. When
// sanitize is true it inserts an asciisanitizer in front of the underlying
// writer; otherwise it returns the underlying writer directly so writes
// reach stdout unchanged.
func newContentWriter(out io.Writer, sanitize bool) io.Writer {
	if !sanitize {
		return out
	}
	return transform.NewWriter(out, &asciisanitizer.Sanitizer{})
}
