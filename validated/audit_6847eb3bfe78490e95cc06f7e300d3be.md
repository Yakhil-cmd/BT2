### Title
Stack-scoped API token can read CCMenu build status of any stack, bypassing its `stack_id` authorization scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be created with a `stack_id`, which is meant to restrict that token's `read:stack` permission to a single stack. `Shipit::Api::BaseController#stacks`/`#stack` correctly enforces this by scoping the query: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `Shipit::Api::CCMenuController`, however, overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, never consulting the client's `stack_id` scope [2](#0-1) . The `require_permission :read, :stack` check only verifies the client's permission list contains the string `read:stack` [3](#0-2) ; it performs no per-stack comparison. This is structurally identical to the referenced Tigris bug: a guard exists, but it is evaluated against the wrong operand (the permission bit rather than the specific stack that the token authorizes), so the intended per-stack binding is bypassed.

### Finding Description
`ApiClient#stack_id` is designed to bind a token to exactly one stack — this is enforced in every other API controller through `BaseController#stacks`/`#stack`, e.g. `StacksController#index` uses `@stacks = stacks` (the scoped relation) [4](#0-3) , and `BaseController#stack` calls `stacks.from_param!(params[:stack_id])` [5](#0-4) .

`CCMenuController` redefines `stack` to bypass this scoped relation and instead resolve any stack directly from `Stack.from_param!(params[:stack_id])` [6](#0-5) . The equality that should hold is:

`stack requested by client == stack authorized for client (current_api_client.stack_id)`

but in `CCMenuController#show`, this becomes:

`stack requested by client (any params[:stack_id]) != stack authorized for client (current_api_client.stack_id)`

Any `ApiClient` token possessing the `read:stack` permission — even one deliberately scoped to a single, non-sensitive stack via `stack_id` — can call `GET /stacks/:stack_id/ccmenu.xml?token=<token>` with any other stack's identifier and receive that stack's build/deploy status, because `CCMenuController#authenticate_api_client` authenticates via the raw token param and `#show` resolves `stack` unscoped [7](#0-6) .

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack state: a token intentionally restricted to one stack (e.g., one issued through `CCMenuUrlController#client`, which is created with `permissions: %w[read:stack]` and scoped to a particular stack [8](#0-7) ) can enumerate and read the build/deploy status (name, activity, last build status/label/time, web URL) of every stack in the Shipit instance, not just the one it was authorized for. This matches the "unauthenticated read of stack state" High-impact category: it escalates a narrowly-scoped, low-trust token into a global read of stack state across the deployment.

### Likelihood Explanation
Any holder of a legitimately-scoped, low-privilege CCMenu/API token (which are routinely generated per-stack for CI status widgets, see `CCMenuUrlController`) can trivially exploit this by substituting `stack_id` in the URL — no additional secrets, session, or write access are required beyond the token they already legitimately possess for their own stack.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation, consistent with the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures the stack being read is validated against `current_api_client.stack_id`, matching the pattern already used in `BaseController` and `StacksController`.

### Proof of Concept
1. Create (or have issued) an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (e.g., via `CCMenuUrlController#fetch` for stack A) [8](#0-7) .
2. Note the issued `authentication_token`.
3. Send `GET /stacks/<owner>/<other-stack-B>/ccmenu.xml?token=<token>` (or the equivalent `stack_id` route param for stack B, a stack unrelated to A).
4. `authenticate_api_client` authenticates successfully because the token is valid [9](#0-8) ; `require_permission :read, :stack` passes because the client has `read:stack` in its permission list [3](#0-2) ; `stack` resolves stack B unscoped [6](#0-5) .
5. The response renders stack B's build status and metadata, even though the token was only ever authorized for stack A.
