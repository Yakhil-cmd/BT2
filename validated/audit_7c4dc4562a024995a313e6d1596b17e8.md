### Title
Webhook signature is verified against the organization in `repository.owner.login`, but handlers act on the repository named in `repository.full_name` with no cross-check, enabling cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` derives the authenticating GitHub organization purely from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and validates the HMAC signature against that organization's `webhook_secret`. `Handler#repository_name`/`#stacks`, used by every webhook handler (e.g. `PushHandler`, `StatusHandler`, pull-request handlers), instead resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`. Nothing ties the two fields together, so a payload can be signed as belonging to organization A while its `repository.full_name` names a repository owned by organization B, and Shipit will still act on B's stack.

### Finding Description
In a multi-organization Shipit configuration (documented in `config/secrets.development.example.yml`), each GitHub org has its own `webhook_secret`. `verify_signature` picks the app/secret to check against using only `repository_owner`: [1](#0-0) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`): [2](#0-1) 

Once the signature is accepted, `create` dispatches the *entire* JSON payload to the registered handlers for the event: [3](#0-2) 

Handlers resolve their target `Stack`/`Repository` from a *different* field, `repository.full_name`, with no comparison to the organization used for signature verification: [4](#0-3) 

For example, `PushHandler` uses this to look up stacks and immediately trigger a GitHub sync job for the matched stack: [5](#0-4) 

Pull-request handlers similarly resolve `Repository.from_github_repo_name(params.repository.full_name)` and mutate pull requests/stacks (e.g. archiving on label changes): [6](#0-5) [7](#0-6) 

**Binding broken:** organization authenticated (`repository.owner.login`, checked against that org's `webhook_secret`) ≠ repository written (`repository.full_name`, used unchecked by every handler). The rules explicitly call out this exact class of binding ("an organization that authenticated versus the repository that is written") as in scope.

### Impact Explanation
An attacker who administers any GitHub organization/app that is legitimately registered with a shared Shipit instance (a normal, unprivileged tenant in a multi-org setup, not requiring access to any *other* org's secrets) knows their own `webhook_secret`. They can send a correctly-signed webhook whose `repository.owner.login` matches their own org (passing `verify_webhook_signature`) but whose `repository.full_name` names a stack belonging to a different organization/repository hosted on the same Shipit instance. Handlers such as `PushHandler`, the pull-request handlers, and `StatusHandler`/`CheckSuiteHandler` will then act on that unrelated stack — enqueuing sync jobs, mutating commit statuses used for deploy gating, archiving/unarchiving stacks, or updating pull request state tracked by Shipit — none of which the attacker's own webhook secret should authorize. This is a cross-repository/cross-organization write achieved purely by crafting the JSON body differently from the signed org, matching the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Requires a multi-org Shipit deployment (explicitly supported and documented as a configuration mode) and requires the attacker to control one legitimately configured organization's webhook secret — a standard, unprivileged tenant capability, not a privileged Shipit account, API token, or leaked secret belonging to the victim organization. No special timing or race condition is needed; a single crafted, correctly-signed POST to `/github-webhooks/create` (routed via `config/routes.rb`) is sufficient.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`#stacks`), assert that the organization used to select the `webhook_secret` (`repository_owner`) matches the owner segment of `repository.full_name` (and `organization.login` for org-level events) before dispatching to handlers. Reject the request (e.g. `head(422)`) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. As the administrator of `attacker-org`, compute a valid `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over a JSON body where:
   - `repository.owner.login` = `"attacker-org"` (used only for signature-org lookup)
   - `repository.full_name` = `"victim-org/victim-repo"` (the stack the attacker does not own)
   - a valid `push` event body (`ref`, `after`, etc.)
3. POST to the webhooks endpoint (`scope '/*id'... 'push' event route` from `config/routes.rb`) with `X-Github-Event: push` and the computed signature.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which succeeds because the signature was computed with `attacker-org`'s secret — see `app/controllers/shipit/webhooks_controller.rb:24-30`.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for `victim-org`'s stack, despite the request never being authenticated by `victim-org`'s webhook secret.
