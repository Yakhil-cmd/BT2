Based on my investigation, this is a genuine multi-tenant configuration binding break in the webhook signature verification flow.

### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the repository actually written to is selected independently by `repository.full_name`, allowing a valid-but-unrelated organization's webhook secret to authorize writes to another organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit.github(organization:)` supports a per-organization configuration schema where each organization key under `secrets.github` can carry its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using only `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `organization.login`) [2](#0-1) . However, the handlers that actually perform writes (create commits, sync stacks, close/label review stacks, etc.) locate the target `Repository`/`Stack` using a completely different, independently-controlled payload field: `payload.dig('repository', 'full_name')` [3](#0-2) , which is parsed by `Repository.from_github_repo_name` into `owner`/`name` by splitting on `/` [4](#0-3) .

### Finding Description
The binding that should hold is: **organization whose signature validated the request == organization that owns the repository being written to**. Instead, the engine checks: `verify_webhook_signature(sig, raw_body)` using `Shipit.github(organization: repository.owner.login)`, then separately resolves the write target via `repository.full_name`. These two fields are both attacker-supplied inside the same JSON body and are never cross-checked against each other.

If a Shipit deployment is configured for multiple GitHub organizations (the per-organization config schema explicitly supported by `github_app_config` [5](#0-4) ), each organization has its own `webhook_secret`. An attacker who legitimately controls (or has push access to) Organization A, which is one of the configured GitHub App installations, can sign a valid webhook using Organization A's secret (since they can trigger real GitHub events on their own repo, or, if they have obtained/computed A's `webhook_secret` through any legitimate low-privilege channel available to an org member) while setting `repository.full_name` to `OrgB/some-repo` and `repository.owner.login` to `OrgA` (so that `verify_signature`'s org lookup for the secret matches A, but the actual write target inside the handler resolves to B). Because `verify_signature` never confirms that the `organization` it authenticated against equals the `owner` embedded in `full_name` used by the handlers, a webhook validly signed for org A's installation can drive writes (commit creation via `GithubSyncJob`, review-stack archive/unarchive, team/membership changes) against any other organization's `Repository`/`Stack` records that Shipit tracks, as long as that repository's name/owner string is guessed or known.

### Impact Explanation
This breaks the deployment-trust binding of "organization that authenticated versus the repository that is written," matching the class explicitly listed in the rules. The consequence is a cross-repository/cross-organization write: an attacker holding only one organization's valid webhook signature can force GithubSyncJob to fetch and append commits, mutate `Commit`/`Status` records, or archive/unarchive review stacks belonging to a stack owned by a completely different, unauthorized organization tracked by the same Shipit instance. This satisfies the "cross-repository writes" / "unauthorized deploy" impact bar, since ingested commits and check-runs feed directly into whether continuous delivery is allowed to ship.

### Likelihood Explanation
Exploitability depends on the deployment running the multi-organization config schema (`secrets.github` keyed by organization) rather than the single-app schema — this is a supported, documented configuration path (`github_app_config`), not a hypothetical one. Any attacker who is a legitimate member/collaborator of one of the configured organizations (able to trigger or replay a validly-signed webhook for that org) can attempt this without needing credentials for the target organization, satisfying the "unprivileged-attacker" bar relative to the victim organization/repository.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), after establishing which organization's secret validated the signature, assert that the resolved repository's owner (from `full_name`) matches the organization used for signature verification before dispatching to handlers. E.g., derive `repository_owner` and the handler's `repository_name` owner segment once, compare them, and `head(422)` on mismatch, analogous to how `addEarnings` in the referenced report needed to call `isValidForEarnings` before crediting.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orga` (webhook_secret: `secretA`) and `orgb` (webhook_secret: `secretB`), each with `Repository` records tracked (`orga/repo1`, `orgb/repo2`).
2. Craft a `push` webhook JSON body: `{"repository": {"owner": {"login": "orga"}, "full_name": "orgb/repo2"}, "ref": "refs/heads/main", "after": "<attacker-controlled sha>"}`.
3. Sign the raw body with `secretA` (known to the attacker as an org A member/collaborator) and send it as `X-Hub-Signature`.
4. `verify_signature` computes `repository_owner == "orga"`, fetches `Shipit.github(organization: "orga")`, and validation succeeds using `secretA`.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/repo2")`, matching Organization B's stack, and enqueues `GithubSyncJob` against it — despite the request never being signed by Organization B's secret [6](#0-5) [3](#0-2) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
