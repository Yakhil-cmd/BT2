### Title
Webhook signature verification is bypassed for any organization with a missing `webhook_secret`, and `WebhooksController#create` never binds the verified organization to `repository.full_name` before dispatching to event handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` resolves the GitHub App config using only `repository.owner.login`, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that config has no `webhook_secret`. Because `#create` never checks that the org used for verification matches the org embedded in `repository.full_name`, an attacker can select any configured org lacking a `webhook_secret`, put it in `repository.owner.login`, and freely set `repository.full_name` to `victim-org/victim-repo`, causing every registered handler for the event to run against an unauthenticated, attacker-chosen victim repository payload.

### Finding Description
The broken binding is: `repository_owner` (`params.dig('repository','owner','login')`, used to select the `GitHubApp` for signature verification) must equal the organization that owns `repository.full_name` (the value handlers actually act on). Nothing in `#create` enforces this equality.

Trace:
- `verify_signature` computes `repository_owner` from `params['repository']['owner']['login']` and calls `Shipit.github(organization: repository_owner)` [1](#0-0)  and [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` if that resolved org's config has no `webhook_secret` set, regardless of the `X-Hub-Signature` header content: [3](#0-2) .
- `#create` re-parses the raw body and dispatches the *entire* JSON payload — including `repository.full_name`, which was never re-validated against `repository_owner` — to every registered handler for the event: [4](#0-3) .

Exploit flow: the attacker crafts a JSON body copied/adapted from a public GitHub pull_request payload for `victim-org/victim-repo`, sets `repository.owner.login` to an org configured in `secrets.github` with a blank/absent `webhook_secret` (multi-tenant github app configs are supported via `github_app_config`/`github_organizations`, see `lib/shipit.rb:170-200`), and sends it with any (even garbage) `X-Hub-Signature`. `verify_signature` passes because `verify_webhook_signature` returns `true` unconditionally for that org. `Shipit::Webhooks.for_event(event)` handlers are then invoked with `params` whose `repository.full_name` still points at `victim-org/victim-repo`.

Existing guards do not stop this: `drop_unhandled_event` only checks whether handlers exist for the event name, not payload authenticity; `verify_signature` authenticates the *sender org* selected from an attacker-controlled field, not the *target repository*; there is no `ExplicitParameters` schema or model validation in `#create` tying `repository_owner` to `repository.full_name`.

### Impact Explanation
Depending on which handler is registered for the event (e.g. `push`, `status`, `pull_request`, `check_suite`, `membership`), this allows writing records (commits, statuses, check runs, team memberships) attributed to `victim-org/victim-repo` without ever knowing that org's real `webhook_secret` — this is a payload for one repository/organization mutating another's stack/commit/task/team data, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any repository whose `full_name` the attacker chooses, as long as at least one organization in the deployment's GitHub App configuration has no `webhook_secret` set.

### Likelihood Explanation
This requires the specific precondition that the Shipit deployment uses the multi-tenant GitHub App config schema (`secrets.github` keyed by organization) **and** at least one configured organization has an empty/missing `webhook_secret`. If the deployment uses the single-app schema (`github_default_organization` is `nil`), `Shipit.github(organization: repository_owner)` ignores `repository_owner` entirely and always resolves the one configured app [5](#0-4) , so the bypass only manifests if that single app itself lacks a `webhook_secret` (a misconfiguration, not attacker-controlled). Thus this finding's applicability is conditional on operator misconfiguration (a no-secret org existing) rather than a universally-reachable bug in the engine's default single-tenant setup. I could not locate the actual pull_request/assigned handler implementation in this index (`app/models/shipit/hooks` was empty in my search) to directly confirm how `full_name` is used downstream to resolve a `Stack`, so I cannot fully confirm the downstream write path for `pull_request` specifically beyond the generic `handler.call(params)` dispatch shown in `#create`.

### Recommendation
- Never let `verify_webhook_signature` return `true` when `webhook_secret` is blank; instead treat a missing configured secret as a hard misconfiguration (raise/log and reject with 500/422), so no organization can silently accept unsigned/forged payloads.
- Bind verification to the mutated resource: after resolving `repository_owner`, verify that `params.dig('repository','full_name')&.split('/')&.first` matches `repository_owner` (case-insensitively) before dispatching to handlers, rejecting mismatches with 422.
- Consider resolving the `GitHubApp` from the persisted `Repository`/`Stack` record's known owner rather than from attacker-supplied payload fields.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "signature bypass via org with no webhook_secret allows cross-repo full_name forgery" do
  # Precondition: configure an org "no-secret-org" in secrets.github with webhook_secret blank
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', { webhook_secret: nil })
  )

  event = 'pull_request'
  mock_handler = mock
  # Handler is invoked with attacker's forged full_name for victim-org/victim-repo
  mock_handler.expects(:call).with do |params|
    params['repository']['full_name'] == 'victim-org/victim-repo'
  end.once
  Shipit::Webhooks.handlers['pull_request'] = [mock_handler]

  payload = {
    action: 'opened',
    number: 2,
    repository: { full_name: 'victim-org/victim-repo', owner: { login: 'no-secret-org' } }
  }

  @request.headers['X-Github-Event'] = event
  @request.headers['X-Hub-Signature'] = 'sha1=garbage-not-a-real-signature'
  post :create, body: payload.to_json, as: :json

  assert_response :ok # verification passed despite bogus signature
end
```
Assertions on both sides of the binding: `repository_owner` resolved during verification is `'no-secret-org'`, while the value handlers receive/act on (`params['repository']['full_name']`) is `'victim-org/victim-repo'` — the two are unequal, yet the request is accepted and dispatched, proving the binding is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end
