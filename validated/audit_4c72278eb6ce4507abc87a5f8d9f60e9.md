### Title
Attacker-selected swap route can inject an authorized token transfer and steal wallet assets - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategies forward caller-supplied opaque route bytes to the configured swap router. A route can invoke attacker-controlled code beneath the caller’s original authorization and cause that code to request an additional `token.transfer` from the caller. Soroban simulation records that transfer as a child authorization; if the caller signs the poisoned tree, the attacker can drain tokens unrelated to the lending position while the swap still returns valid output. [1](#0-0) 

### Finding Description
`process_swap_collateral` accepts a caller-supplied `StrategySwap`, authenticates the caller, verifies account ownership or delegation, withdraws collateral, and passes the route bytes into the strategy swap path. [2](#0-1) 

`swap_tokens` forwards those bytes without validating their destination graph: it loads the configured router, authorizes only the controller’s exact input transfer, and invokes `execute_strategy(controller, amount_in, swap)`. [3](#0-2) 

The narrow invoker authorization protects only the controller’s input transfer. It does not prevent route-selected code deeper in the call stack from making another `require_auth`-protected call against the original caller. [4](#0-3) 

The adversarial fixture demonstrates the primitive: a route-selected contract calls `token.transfer(victim, attacker, amount)` from inside the swap. [5](#0-4) 

Simulation attaches that transfer as a child of the victim’s `swap_collateral` authorization, while the route still pays the expected output and completes successfully. [6](#0-5) 

This is analogous to the report’s attacker-controlled request target: user-controlled routing data causes trusted protocol execution to contact attacker-selected code, but the resulting unauthorized action is a token transfer rather than an HTTP request. [7](#0-6) 

### Impact Explanation
A victim who signs the simulated authorization tree loses arbitrary balances of unrelated wallet tokens in addition to the intended collateral swap. [8](#0-7) 

The attack can steal assets that were never supplied to XOXNO and are not covered by the route’s `amount_in`, output measurement, minimum-output check, or final account risk checks. [9](#0-8) 

The same authorization-tree injection applies to every controller strategy that accepts route bytes and reaches `swap_tokens`, including `multiply`, `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral`. [10](#0-9) 

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the additional child authorization, so it is not a fully unilateral theft. [11](#0-10) 

However, routes are opaque XDR bytes, and an attacker controlling a quote source, interface, or route payload can make the theft appear as a successful swap with the expected collateral output. [12](#0-11) 

The regression test confirms that honest simulation records the malicious child transfer and that signing that poisoned tree executes it. [13](#0-12) 

### Recommendation
Do not treat route bytes as trusted merely because the configured router and measured output are fixed. Restrict executable route destinations to a governance-approved venue registry or otherwise reject route-selected contracts that can introduce caller-authorized operations outside the expected input transfer. [3](#0-2) 

Clients should also decode and validate simulated authorization trees before signing: a legitimate controller swap should contain only the expected controller-root invocation and its expected input-transfer child, and any additional child must abort the transaction. [14](#0-13) 

### Proof of Concept
A minimal route contains an attacker-deployed hop contract whose `swap` function executes `token.transfer(victim, attacker, victim_balance)`. [15](#0-14) 

```text
1. Victim holds supplied USDC and an unrelated wallet token.
2. Attacker supplies route bytes naming the malicious hop contract.
3. Victim calls:
   swap_collateral(
       caller = victim,
       account_id = victim_account,
       current = USDC market,
       from_amount = 5_000 USDC,
       new = ETH market,
       swap = malicious_route_xdr,
   )
4. Controller authorizes only controller -> router input transfer.
5. Route execution reaches malicious hop.
6. Hop calls wallet_token.transfer(victim, attacker, victim_balance).
7. Simulation adds that token transfer as a child of the victim's
   swap_collateral authorization.
8. Victim signs the returned authorization tree.
9. The swap returns a valid ETH amount and final risk checks pass.
10. The unrelated wallet token has been transferred to the attacker.
```

The test records the malicious transfer under the victim’s root authorization and confirms that the victim’s wallet balance becomes zero, the attacker receives the full balance, and the victim still receives the expected swapped collateral. [16](#0-15)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
