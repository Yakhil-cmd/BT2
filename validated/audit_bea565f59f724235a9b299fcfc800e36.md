## Analog Found: Fixed AA `bounce_fees` can become insufficient after protocol fee upgrades, permanently stranding funds sent to an AA

### Title
Hardcoded/fixed AA bounce fee can be exceeded by protocol-upgraded oversize fees, causing funds sent to an AA to become permanently stuck - (File: `aa_composer.js`, `aa_validation.js`, `constants.js`)

### Summary
The Istanbul report describes a class of bug where a **fixed, hardcoded resource allowance** (`transfer()`'s 2300 gas stipend) becomes insufficient after a protocol-level cost change (Istanbul SLOAD repricing), causing the payment to permanently fail and funds to get stuck. The same failure pattern exists in ocore's Autonomous Agent (AA) framework: every AA has a fixed `bounce_fees.base` reserved to pay for sending a bounce response, defaulting to the hardcoded `constants.MIN_BYTES_BOUNCE_FEE` if the AA author doesn't specify a larger one [1](#0-0) . Just like Istanbul added SLOAD costs that broke `transfer()`'s fixed stipend, later ocore protocol upgrades (`v4UpgradeMci`, `pemCurvesFixMci`) introduced a new, size- and content-dependent `oversize_fee` on top of headers/payload commissions [2](#0-1) . If this dynamically-computed fee (which did not exist when many already-deployed AAs were defined with a small fixed `bounce_fees.base`) exceeds the coins available for the bounce response, both the primary response and the bounce fallback fail, and the incoming payment is never returned nor forwarded.

### Finding Description
When a trigger unit sends coins to an AA, `handleTrigger()` first checks that the received amount covers the AA's fixed `bounce_fees.base`/asset requirements before even evaluating the AA logic [3](#0-2) . This check uses only the flat `bounce_fees` value the AA declared at definition time - it has no way to anticipate future fee-formula changes.

If the AA's primary logic fails (bounces) for any reason, `bounce()` tries to send back `trigger.outputs - bounce_fees` to the trigger address by calling `sendUnit()` [4](#0-3) . `sendUnit()` composes the actual response unit and, from `v4UpgradeMci` onward, adds an `oversize_fee` computed from unit size via `storage.getOversizeFee()` [5](#0-4) [6](#0-5) . This fee is not part of the fixed `bounce_fees.base` an AA author configured, and it did not exist for AAs deployed before `v4UpgradeMci`.

Critically, if `sendUnit()` fails while composing the bounce response (e.g. `completePaymentPayload` errors because the leftover amount minus the newly-introduced oversize fee is insufficient), it calls `bounce(err)` again. But `bBouncing` is already `true` at that point, so the second call to `bounce()` short-circuits straight to `finish(null)` [7](#0-6) . `finish(null)` with no response unit simply calls `onDone` - no payment is created, no state changes occur, and the originally-received coins simply remain as an unspent output at the AA's own address forever, since **only the AA's own logic (triggered by a future unit) can ever spend outputs held by an AA address**, and every future trigger against that same broken AA would fail the exact same way.

### Impact Explanation
Coins sent into an AA can become permanently unspendable once the actual cost of producing a response/bounce unit (driven by protocol-wide, non-author-controlled fee formulas like `getOversizeFee()`) exceeds the AA's statically configured `bounce_fees.base`. This is a direct network-wide analog of "Eth may get stuck in contract": legitimate user funds sent to a contract-like AA can never be recovered by any party, not even the AA author, because the AA logic and validation path both depend on a fixed fee constant that a later hard-fork-style upgrade (`v4UpgradeMci`/`pemCurvesFixMci`) can silently invalidate for pre-existing AA definitions.

### Likelihood Explanation
Any already-deployed AA that specifies (or defaults to) a `bounce_fees.base` close to `constants.MIN_BYTES_BOUNCE_FEE`, combined with a trigger payment sized so the reply/bounce unit crosses the `threshold_size` used by `getOversizeFee()`, can trigger this. Since AA definitions are immutable once posted, and the oversize fee formula/thresholds are governed by `getSystemVar()` (which can be voted/changed over time) [8](#0-7) , any future increase to `threshold_size` sensitivity or fee curve steepness re-triggers this class of failure across every already-deployed AA whose author picked a fee margin that was safe under the old fee schedule but not the new one.

### Recommendation
- Require AAs to reserve bounce fees dynamically (e.g., compute worst-case `oversize_fee` at validation time via `aa_validation.js` and enforce `bounce_fees.base` covers it, not just `MIN_BYTES_BOUNCE_FEE`), or
- Make the pre-check in `handleTrigger()` (`(trigger.outputs.base || 0) < bounce_fees.base`) also account for the current `getOversizeFee()` estimate rather than only the AA-declared static fee, and
- On a second bounce failure inside `sendUnit()`, fall back to a minimal response that still returns available principal instead of silently dropping to `finish(null)` and stranding the funds.

### Proof of Concept
1. Deploy (pre-`v4UpgradeMci`) an AA with `bounce_fees: { base: constants.MIN_BYTES_BOUNCE_FEE }` and logic that can legitimately bounce (e.g., a `require`/`bounce` condition) [1](#0-0) .
2. After the network activates `v4UpgradeMci`, send a trigger payment to that AA sized such that, after the primary logic bounces, the reconstructed bounce-response unit's `headers_commission + payload_commission` crosses `threshold_size`, causing `storage.getOversizeFee()` to return a nonzero fee [9](#0-8) .
3. `sendUnit()`'s `completePaymentPayload` fails to find enough input to cover `net_target_amount + getOversizeFee(size)` and calls `bounce(err)` again [10](#0-9) .
4. Because `bBouncing` is already `true`, this second call resolves to `finish(null)` [7](#0-6) , and the trigger's payment output sitting at the AA address is never spent - permanently stuck.

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
}
