### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` breaks the "authenticated organization vs. written repository/commit" binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on an attacker-controlled field of the *same unauthenticated* payload (`repository.owner.login`), and `Handler#stacks` scopes most handlers by `repository.full_name`. `StatusHandler`, however, never re-derives or checks the repository/stack scope at all — it looks up commits globally by `sha` across the entire Shipit instance and writes a `Status` for whichever commit matches, regardless of which organization/repository the verified signature belongs to.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the GitHub App config to verify against using a field taken from the raw, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

This is the multi-org configuration pattern (`config/secrets.development.shopify.yml`), where each org has its own `webhook_secret`: [3](#0-2) 

Once the signature check passes for the org matching `repository.owner.login`, the raw payload is handed unchanged to the event handler for processing: [4](#0-3) 

Most handlers (e.g. `PushHandler`) re-scope their side effects to the specific repository named in the payload via `Handler#stacks`/`Handler#repository_name` (`repository.full_name`): [5](#0-4) [6](#0-5) 

`StatusHandler`, by contrast, does **not** scope by repository/stack at all — it queries `Commit` globally by `sha` and writes a status to whatever commit matches, in whatever stack that commit happens to belong to: [7](#0-6) 

This breaks the trust binding: `repository.owner.login` (used to select the signing secret / "the organization that authenticated") ≠ the stack/commit that is actually written (determined solely by `sha`, with no repository check). Any org onboarded onto the same Shipit instance — i.e., any org whose GitHub App is configured with its own `webhook_secret` in `config/secrets*.yml` — can forge a valid signature for its own org, then send a `status` event with `sha` set to a commit that belongs to a *different* org's stack (e.g., guessed/observed via Shipit's public UI or API) and `state: "success"`.

`Status#after_create` calls `enable_ci_on_stack` and `schedule_continuous_delivery`, meaning the forged status directly participates in CI/deploy gating logic for the victim's stack: [8](#0-7) 

Because Shipit's deploy pipeline treats commit statuses/checks as CI signals that unblock/allow deploys (`Commit#detached_head?`/checks used by `Stack`/`DeploySpec` to gate deploys — confirmed present via `app/models/shipit/commit.rb` matches for checks/statuses, though I was not able to fully trace every deploy-gating branch in the time available), injecting a fabricated `success` status for a target commit can make an otherwise-blocked commit appear CI-green in a victim organization's stack.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope: a tenant that only has legitimate credentials (its own `webhook_secret`) for its own organization can write CI status data into a completely different organization's stack/commit records, without any repository/stack containment. If CI status is part of a stack's deploy-blocking criteria (which is the entire purpose of the `status`/`deployable_status` webhook events and `Status#schedule_continuous_delivery`), this allows an attacker who controls one onboarded org's app credentials to manufacture a false-positive CI signal that can unblock/trigger a deploy in another organization's stack — an unauthorized-deploy class impact, matching the accepted High/Critical impact categories (escalation into cross-tenant deploy state).

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations (documented, supported multi-tenant configuration shown in `config/secrets.development.shopify.yml`), and (2) the attacker controlling a legitimately configured org's `webhook_secret`/GitHub App (i.e., being a legitimate tenant of the same Shipit instance, not a privileged Shipit admin) and (3) knowledge of a target commit `sha` belonging to a different org's stack (commit SHAs and stack pages are visible through Shipit's own UI once authenticated as any user, or guessable/observable from GitHub itself since SHAs are public). No `ApiClient` token, GitHub App private key, or Shipit session is required — only the ability to POST a signed webhook to the shared `/webhooks` endpoint, which is exactly the access model the engine is designed to accept from any onboarded org.

### Recommendation
`StatusHandler#process` (and any other handler that does not currently scope by repository) must verify that the commit's stack/repository matches the `repository.full_name` (and ideally `repository.owner.login`) actually present in — and used to authenticate — the payload, the same way `Handler#stacks` does for `PushHandler`. Concretely, scope the `Commit.where(sha: params.sha)` lookup to `stacks` (i.e., commits belonging to `Repository.from_github_repo_name(repository_name).stacks`) before calling `create_status_from_github!`, so that a status can only be applied to commits within the repository whose credentials produced the verified signature.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml`).
2. As the attacker, obtain/possess `org-a`'s legitimate `webhook_secret` (attacker is a legitimate GitHub App admin for `org-a` only).
3. Identify a commit `sha` belonging to a stack under `org-b` (visible via Shipit's stack/commit pages, or from GitHub directly since commit SHAs are public).
4. Craft a `status` webhook payload:
```json
{
  "sha": "<org-b-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
5. Sign the payload with `org-a`'s `webhook_secret` and POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: "org-a")` and successfully verifies the signature.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `org-b` commit (no repository check), and calls `commit.create_status_from_github!(params)`, creating a `success` `Status` on `org-b`'s stack — triggering `enable_ci_on_stack` and `schedule_continuous_delivery` for a stack the attacker has no legitimate access to.
