### Title
Arbiter Contract Shared Address Accepts Overpayment via `>=` Check, Permanently Locking Excess Funds - (File: `arbiter_contract.js`)

### Summary
The Byteball/Obyte arbiter-contract subsystem funds a 2-of-2/dispute-resolvable shared address whose payout is always for the *fixed* `objContract.amount` recorded when the contract was created. The listener that detects the funding payment and marks the contract "paid" accepts **any payment greater than or equal to** the contract amount, instead of requiring an exact match. Because the later payout logic (`complete()`) only ever spends exactly the fixed contract amount (split between peer/arbstore), any excess sent by the payer stays in the shared address with no code path designed to release it back to the overpayer.

### Finding Description

`opts.change_address` is set to `objContract.shared_address` itself, so any amount picked up as inputs beyond the fixed payout amount is simply returned as "change" back into the same shared address rather than to the original overpaying party. Once the contract transitions to `completed`/`cancelled` (the only states this module drives), there is no remaining code path in `arbiter_contract.js` that ever spends the shared address again — the excess balance is stranded in a wallet-defined shared address whose spending conditions require cooperation/authorization tied to a contract that has already been finalized (see the fixed "has output amount=X" clauses built in `deriveSharedAddress()`): [3](#0-2) 

### Impact Explanation
Any counterparty (payer) in a private arbiter contract who sends more than the exact `contract.amount` to the shared address — whether by mistake, wallet rounding, or a malicious/careless client — has the excess amount permanently, or at minimum indefinitely, trapped: it is neither refunded to them nor delivered to the payee/arbstore, and no further legitimate spend from that shared address is ever composed by this module after the contract concludes. This is a fund-freezing bug reachable by an ordinary private-payment counterparty, matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
Triggering this requires only that the payer send an amount to the shared funding address that is `>=` (rather than exactly equal to) the recorded contract amount — a very plausible and easy user action (e.g., choosing "send all" from a wallet, or fee/rounding differences), so the likelihood of the condition being hit is moderate to high, even absent malicious intent.

### Recommendation
- Change the funding-detection query to require exact equality (`SUM(outputs.amount) = wallet_arbiter_contracts.amount`), or explicitly track/reject overpayments before marking the contract "paid".
- Alternatively, if overpayment is allowed to proceed, extend `complete()`/refund logic to detect and refund any balance in the shared address beyond `objContract.amount` back to the payer as part of the completion/cancellation transaction, instead of routing it to `change_address = shared_address` where it becomes unrecoverable in practice.

### Proof of Concept
1. Two parties negotiate an arbiter contract for `amount = 1_000_000` bytes; a shared address is derived per `deriveSharedAddress()`.
2. The payer funds the shared address with `1_000_500` bytes (500 extra, e.g., due to leftover change being swept in).
3. The `new_my_transactions` listener's query matches `SUM(outputs.amount) >= wallet_arbiter_contracts.amount` (1,000,500 ≥ 1,000,000) and sets contract status to `paid`.
4. Upon `complete()`, the wallet computes `opts.amount = objContract.amount` (1,000,000) to the peer (or splits `peer_amount`/`arbstore_amount` summing to 1,000,000), with `change_address = objContract.shared_address`.
5. The extra 500 bytes are returned as a change output back to the same shared address.
6. Contract status becomes `completed`; no further code in `arbiter_contract.js` ever spends this shared address again — the 500-byte surplus is stuck.
