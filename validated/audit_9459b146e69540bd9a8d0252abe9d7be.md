### Title
Terminal escape sequence injection via unsanitized `Target`/`SubmoduleGitURL` fields in symlink/submodule error messages - (File: pkg/cmd/repo/read-file/http.go)

### Finding Description
`fetchFile` in [1](#0-0)  builds error messages from the Contents API response when `content.Type` is not `"file"`. The comment on lines 135-137 explicitly states that `content.Path` is used "rather than the user input in these messages, so a crafted path cannot smuggle terminal escape sequences into our output" — but this reasoning only covers `content.Path`. The `symlink` and `submodule` branches interpolate `content.Target` and `content.SubmoduleGitURL` directly into `fmt.Errorf`: [2](#0-1) 

These two fields come straight from the JSON body of the Contents API response (`contentsResponse.Target`, `contentsResponse.SubmoduleGitURL`, declared at [3](#0-2) ) and are fully attacker-controlled: a malicious repository can return a symlink entry whose `target` field, or a submodule entry whose `submodule_git_url` field, contains raw ANSI/terminal escape sequences (ESC, OSC, CSI).

Unlike the actual file-content path — which is explicitly and carefully guarded by `iostreams.ContainsEscapeSequence` before being written to `ContentOut` (see [4](#0-3) ) — this error string is returned as a plain `error` from `fetchFile` and propagated unchanged through `readFileRun` ( [5](#0-4) ) up to `cobra`'s error handling, which is ultimately printed via `printError(stderr, err, cmd, hasDebug)` in `internal/ghcmd/cmd.go` [6](#0-5) . That print path does not route through the `Untrusted` type or `asciisanitizer` transform that other parts of the codebase use specifically to neutralize escape sequences in externally-sourced strings (contrast with [7](#0-6) ).

### Impact Explanation
This allows a malicious repository (published by any unprivileged GitHub user) to inject terminal escape sequences into a victim's terminal when they run `gh repo read-file <path>` against a path that resolves to a symlink or submodule with a crafted `target`/`submodule_git_url`. Depending on terminal emulator, this can be used for title-bar spoofing, hidden/obscured output, or (in vulnerable terminal emulators) more serious escape-sequence-driven attacks — matching the "terminal escape sequence injection" impact class the codebase's own tests and comments (e.g. `acceptance/testdata/workflow/run-view-log-escape-sequences.txtar`, `pkg/cmd/gist/view` sanitization) treat as a real, in-scope concern.

### Likelihood Explanation
High feasibility: the attacker only needs to control repository content (a symlink or submodule entry) and have the victim run `gh repo read-file <that-path>` against the attacker's repo/fork. No special privileges, tokens, or MITM are required — this is directly reachable via ordinary use of the documented command against attacker-published content.

### Recommendation
Sanitize `content.Target` and `content.SubmoduleGitURL` the same way file content is sanitized before including them in error messages — e.g., wrap them in `iostreams.NewUntrusted(...)` (whose `String()` strips escape sequences) or run them through `asciisanitizer`/`iostreams.ContainsEscapeSequence` checks, consistent with the stated intent in the existing comment that already protects `content.Path`.

### Proof of Concept
```go
// pkg/cmd/repo/read-file/http_test.go (new test)
func TestFetchFile_SymlinkTargetEscapeSequence(t *testing.T) {
    reg := &httpmock.Registry{}
    defer reg.Verify(t)
    reg.Register(
        httpmock.REST("GET", "repos/OWNER/REPO/contents/evil-link"),
        httpmock.JSONResponse(map[string]interface{}{
            "type":   "symlink",
            "path":   "evil-link",
            "target": "safe\x1b]0;PWNED\x07", // OSC title-set escape sequence
        }),
    )
    httpClient := &http.Client{Transport: reg}
    _, err := fetchFile(httpClient, ghrepo.New("OWNER", "REPO"), "evil-link", "")
    require.Error(t, err)
    // Expect the ESC byte to be stripped/sanitized; currently it is not.
    assert.NotContains(t, err.Error(), "\x1b", "symlink target escape sequence leaked into error message")
}
```
Running this against the current code fails the assertion because `fmt.Errorf("path %q is a symlink to %q which does not exist", content.Path, content.Target)` embeds the raw ESC byte from `content.Target` unmodified. An equivalent test can be written for the `submodule` branch using `submodule_git_url`.

func fetchFile(httpClient *http.Client, repo ghrepo.Interface, filePath, ref string) (*repoFile, error) {
	content, err := fetchContent(httpClient, repo, filePath, ref)
	if err != nil {
		return nil, err
	}

	if content.Type != "file" {
		// The path resolved to something other than a regular file. Use content.Path
		// (the API-sanitized path) rather than the user input in these messages, so a
		// crafted path cannot smuggle terminal escape sequences into our output.
		switch content.Type {
		case "dir":
			return nil, fmt.Errorf("path %q is a directory; use `gh repo read-dir` instead", content.Path)
		case "symlink":
			return nil, fmt.Errorf("path %q is a symlink to %q which does not exist", content.Path, content.Target)
		case "submodule":
			return nil, fmt.Errorf("path %q is a submodule (%s at %s)", content.Path, content.SubmoduleGitURL, content.SHA)
		default:
			return nil, fmt.Errorf("path %q is not a regular file (type: %s)", content.Path, content.Type)
		}
	}

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
