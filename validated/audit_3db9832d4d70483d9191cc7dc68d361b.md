### Title
Signed packages (`is_valid_signed_package`) omit the network `alt` identifier, allowing cross-network replay of signatures - ([File: object_hash.js], [File: signed_message.js])

### Summary
The Linea report's root cause is that the verifier's public inputs did not bind the proof to a specific `chainId`, so a proof/data generated on a forked chain (with its own `chainId` baked into the circuit) could still be finalized on the canonical L1 contract. The ocore analog is `getSignedPackageHashToSign()` in `object_hash.js`, which computes the hash-to-sign for a "signed package" used by `is_valid_signed_package()` in AA oscript. This hash is derived only from the package's own fields (`signed_message`, `authors`, `last_ball_unit`, `version`) and never includes `alt` (ocore's network/chain identifier), unlike regular units whose hash (`getUnitHashToSign`/`getStrippedUnit`) explicitly includes `alt`.

### Finding Description
For real units, `alt` is a mandatory network-distinguishing field checked directly in unit validation: [1](#0-0) 
and it is included when computing a unit's canonical hash via `getStrippedUnit`: [2](#0-1) 

However, "signed packages" — arbitrary off-chain signed messages produced by `signed_message.signMessage()` and verified on-chain by AAs via the `is_valid_signed_package(package, address)` oscript operator — are hashed by a separate function, `getSignedPackageHashToSign`, which strips authentifiers but does **not** include `alt` (or any other network/chain identifier) in the hashed source string: [3](#0-2) 

The allowed/expected fields of a signed package are limited to `signed_message`, `last_ball_unit`, `authors`, `version` — `alt` is not part of the schema at all: [4](#0-3) [5](#0-4) 

`validateSignedMessage()` verifies the authentifier signature against `unit_hash_to_sign = getSignedPackageHashToSign(objSignedMessage)` and the address's definition, but performs no check that the package was created for the same network (mainnet/testnet/devnet) as the AA evaluating it: [6](#0-5) 

`constants.js` shows that `alt`, `version`, and `GENESIS_UNIT` all change between `mainnet`, `testnet`, and `devnet`, meaning each network is a logically distinct chain with the same address-derivation scheme (Chash160) but different `alt`/genesis: [7](#0-6) [8](#0-7) 

Because ocore addresses are derived purely from the address definition (Chash160 of `["sig", {pubkey}]` etc.) independent of `alt`, the *same* private key/address exists on mainnet, testnet, and devnet. A user's signature on a signed package produced for one network (e.g., testnet) is bit-for-bit valid on another network (e.g., mainnet) because the hash-to-sign never encodes `alt`. This mirrors the Linea bug exactly: the verifier (here, `is_valid_signed_package`/`validateSignedMessage`) cannot distinguish which "chain" a package was created for, because the chain identifier is missing from the signed data.

Any AA design that uses `is_valid_signed_package` to authorize state-changing actions — such as the payment-channel and order-book examples shipped in the repo's own oscript samples — is exposed. In these samples, a peer's off-chain signed order/payment-authorization package is checked with `is_valid_signed_package(trigger.data.sentByPeer, address)` and then used directly to move funds: [9](#0-8) [10](#0-9) 

### Impact Explanation
If a user (or counterparty in a payment channel/order book AA) signs a package on one ocore network (e.g., testnet, or a future forked/alt network sharing the same signature scheme), that exact same signed package — with the same signature bytes — passes `is_valid_signed_package` and `validateSignedMessage` on a different network, since neither the hash-to-sign nor the field-validation logic incorporates `alt`. An attacker who obtains (or is given) a testnet-signed package from a counterparty could replay it against a mainnet AA (or vice versa) to move funds in a payment channel, execute a stale/foreign order in an order-book AA, or otherwise cause unauthorized state changes/fund loss — a direct analog to "finalizing data from a forked chain" enabling fund theft.

### Likelihood Explanation
Exploitability requires: (1) an AA design that trusts `is_valid_signed_package` results to authorize value transfer (present in the repo's own reference oscript templates for payment channels and order-book exchanges), and (2) the victim's signing key/address existing, and being reachable, on more than one ocore-compatible network with the same address-derivation scheme (e.g., mainnet vs. testnet vs. a devnet fork). Since `alt`/`version`/`GENESIS_UNIT` differences are the *only* mechanism separating networks and addresses are network-independent, cross-network signature reuse is structurally possible whenever a user or service participates in more than one such network with the same keys — a realistic scenario for testers, bridges, or any future alt-chain sharing the address format.

### Recommendation
Include the network identifier (`constants.alt`, and ideally `constants.version`'s network component or `GENESIS_UNIT`) as part of the data hashed in `getSignedPackageHashToSign()`, and enforce this field during `validateSignedMessage()`/`is_valid_signed_package` validation, analogous to how `alt` is mandatory and checked for regular units in `validation.js`. This ensures a signed package created for one ocore network cannot be replayed as valid on another.

### Proof of Concept
1. On network A (e.g., testnet, `alt = '2'`), an address `ADDR` with definition `["sig", {"pubkey": PK}]` signs a package via `signed_message.signMessage()`:
   - `getSignedPackageHashToSign({signed_message: msg, authors:[{address:ADDR}], last_ball_unit: LBU, version: '4.0t'})` produces hash `H` (no `alt` included).
   - User signs `H` with private key, producing signature `S`.
2. The resulting signed package `{signed_message: msg, authors:[{address:ADDR, authentifiers:{r:S}}], last_ball_unit: LBU, version:'4.0t'}` is submitted as `trigger.data.sentByPeer` (or similar) to an AA on network B (e.g., mainnet or a devnet fork) whose address space and Chash160 derivation are identical, and whose `last_ball_unit`/mci lookup can resolve to some existing unit (or an equivalent package is regenerated for network B's own last_ball_unit while keeping the same `signed_message`/`authors`/signature, since the signed hash never binds to `alt`).
3. `is_valid_signed_package(trigger.data.sentByPeer, ADDR)` calls `signed_message.validateSignedMessage`, which recomputes `unit_hash_to_sign = getSignedPackageHashToSign(objSignedMessage)` — identical to `H` on both networks — and successfully verifies signature `S` against `ADDR`'s definition, returning `true` on network B even though the package was never intended for network B.
4. The AA (e.g., the payment-channel `oscript` sample) accepts the forged/replayed authorization and releases funds based on it, causing unauthorized fund movement.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
