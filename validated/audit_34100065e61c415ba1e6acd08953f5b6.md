### Title
Unlocked Map Iteration and Per-Entry Lock/Unlock in `RemoveVotesAfter`/`RemoveGovAfter` Enables Data Race and Partial Rewind State Observation During Fork Resolution — (`kaiax/gov/headergov/impl/rewind.go`)

### Summary
`RemoveVotesAfter` and `RemoveGovAfter` iterate over `h.groupedVotes` and `h.governances` without holding `h.mu` during the range loops, acquiring and releasing the lock only for each individual `delete` call. This creates two concurrent-safety defects: (1) a Go data race between the unlocked iteration and concurrent writers (`AddVote`, `AddGov`), which the Go runtime detects as a fatal panic; and (2) a window between per-entry deletions where a concurrent `RLock` reader observes a partially-rewound map, causing `getExpectedGovernance` to compute a governance payload inconsistent with the pre-rewind state.

### Finding Description
In `rewind.go`, both `RemoveVotesAfter` (lines 20–33) and `RemoveGovAfter` (lines 43–49) follow this pattern:

```go
for epochIdxIter, votes := range h.groupedVotes {   // no lock held
    for blockNumIter := range votes {                // no lock held
        if blockNumIter > blockNum {
            h.mu.Lock()
            delete(h.groupedVotes[epochIdxIter], blockNumIter)
            h.mu.Unlock()                            // lock released before next iteration
        }
    }
}
```

The outer and inner `range` loops read the maps without any lock. Concurrent goroutines that write to these maps (e.g., `AddVote` via `PostInsertBlock`, or the background `migrate` goroutine calling `accumulateVotesInEpoch`) hold `h.mu.Lock()` during their writes. Go's map implementation is not safe for concurrent read+write; the runtime will panic.

Even if no concurrent write occurs, the per-entry lock/unlock means a concurrent `getVotesInEpoch` fast-path caller can acquire `h.mu.RLock()` between two deletions and observe a partially-rewound `h.groupedVotes[epochIdx]`. This partial snapshot is then used by `getExpectedGovernance` → `VerifyGov`, which performs a strict equality check against the block's `Governance` field.

### Impact Explanation
- **Runtime panic (highest severity):** During any fork resolution that triggers `RewindDelete` concurrently with `PostInsertBlock` (which calls `AddVote`), the Go runtime detects concurrent map access and panics, crashing the node. This is a durable loss of node functionality reachable through normal P2P block propagation.
- **Transient `VerifyGov` failure:** A concurrent reader between two per-entry deletions sees a partial rewind, computes a different expected governance, and `VerifyGov` returns `ErrGovVerification` for a valid epoch block. This can cause an honest node to temporarily reject a valid block during fork resolution.

### Likelihood Explanation
Fork resolution (chain reorganization) is a routine event on any live Kaia network. `RewindDelete` is called by `blockchain.go` during reorg processing. `PostInsertBlock` (which calls `AddVote`) runs on the new canonical chain concurrently. No attacker action is required — the race is triggered by normal network conditions. The Go race detector would flag this immediately.

### Recommendation
Hold `h.mu.Lock()` for the **entire** rewind operation, not per-entry:

```go
func (h *headerGovModule) RemoveVotesAfter(blockNum uint64) {
    h.mu.Lock()
    defer h.mu.Unlock()

    dirty := false
    for epochIdxIter, votes := range h.groupedVotes {
        for blockNumIter := range votes {
            if blockNumIter > blockNum {
                dirty = true
                delete(h.groupedVotes[epochIdxIter], blockNumIter)
                if len(h.groupedVotes[epochIdxIter]) == 0 {
                    delete(h.groupedVotes, epochIdxIter)
                }
            }
        }
    }
    // WriteVoteDataBlockNums must be called outside the lock if it can block
    if dirty {
        WriteVoteDataBlockNums(h.ChainKv, h.VoteBlockNums())
    }
}
```

Apply the same fix to `RemoveGovAfter`. Note that `VoteBlockNums()` and `GovBlockNums()` also acquire `h.mu.RLock()`, so the DB write calls should be moved outside the lock scope to avoid deadlock.
