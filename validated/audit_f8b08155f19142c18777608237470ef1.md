### Title
Node crash / permanent stall of AA-trigger processing via uncaught exception in unstable `data_feed` candidate sorting - ([File: data_feeds.js])

### Summary
`data_feeds.js`'s `readDataFeedValue()` looks up unstable, AA-posted `data_feed` messages when evaluating the `data_feed[[...]]` oscript primitive inside an AA formula. When more than one candidate unit ties on both `latest_included_mc_index` and `level` and the caller did not request `ifseveral="abort"`, the tie-break comparator synchronously `throw`s a JS `Error` instead of returning a deterministic result. Because this code runs deep inside the synchronous callback chain of `handleAATriggers()`/`handleTrigger()`, this uncaught exception is not caught anywhere in the call chain, crashing the node process (or at minimum permanently deadlocking the `aa_triggers` mutex so `stabilizeMci()` never completes) whenever any AA references a `data_feed` oracle whose value is fed by another AA and two candidate postings tie in level.

### Finding Description
`readDataFeedValue()` builds a list of unstable candidate data-feed postings from `storage.assocUnstableMessages` when `unstable_opts` is truthy: [1](#0-0) 

When more than one candidate is found and `ifseveral !== 'abort'`, they are sorted by `latest_included_mc_index` then `level`; if both are equal and `bIncludeAllUnstable` is false, the comparator throws: [2](#0-1) 

The `data_feed` oscript evaluator (invoked while executing any AA's `init`/`if`/`state` formulas) calls this function with `unstable_opts = bAA`, i.e. a plain boolean `true`, never the string `'all_unstable'`: [3](#0-2) 

Because `unstable_opts !== 'all_unstable'`, `bIncludeAllUnstable` is `false` inside `readDataFeedValue()`, so the throwing branch is reachable in the AA-execution path whenever two AA-authored unstable units post the same `feed_name` for one of the referenced oracle addresses, at identical `latest_included_mc_index` and DAG `level` (the filter at line 217 only admits candidate units with `objUnit.bAA === true`, i.e. postings that are themselves AA responses; `min_mci`/`max_mci`/oracle-address filters are attacker-controllable via the `data_feed[[...]]` parameters and via which addresses issue the colliding postings).

This synchronous `throw` happens inside `evaluate()`'s `getDataFeed()` callback, which is invoked from deep inside `handleTrigger()` → `handlePrimaryAATrigger()` → `handleAATriggers()`, none of which wrap the formula-evaluation call chain in `try/catch`: [4](#0-3) [5](#0-4) 

`handleAATriggers()` is invoked from `stabilizeMci()` every time a new MCI is stabilized, under a mutex that is only released in the (unreached) completion callback: [6](#0-5) 

Since this is fired deterministically from stable-unit processing (not from network-timing-dependent p2p code), every full node that stabilizes the same MCI executes the identical AA trigger and evaluates the identical `data_feed[[...]]` lookup against the identical `storage.assocUnstableMessages` state, so the crash/deadlock is reproduced network-wide, not just on one victim node.

### Impact Explanation
An uncaught exception thrown mid-way through `handleAATriggers()` either crashes the Node.js process (default behavior for an uncaught exception outside of a domain/handler) or leaves the `['aa_triggers']` mutex permanently locked because the completion callback that calls `unlock()`/`onDone()` is never reached. In either case, `stabilizeMci()` can never finish for that (and all subsequent) MCIs on affected nodes, which halts main-chain stabilization — i.e., the network becomes unable to confirm/stabilize new units. Since the trigger is fully reproducible from on-chain, network-visible data (not a race condition dependent on peer timing), this affects every full node deterministically, which is a network-wide liveness/availability failure rather than a single-node bug.

### Likelihood Explanation
Reaching the bug requires: (1) an AA whose formula calls `data_feed[[oracles=..., feed_name=...]]` without `ifseveral="abort"` and without `all_unstable`-only oracle addresses (the common/default usage pattern, e.g. as in the `futures_contract.oscript` sample) referencing an oracle address that is itself an AA; and (2) causing that AA-oracle to post two data-feed messages for the same `feed_name` from unstable units that tie on `latest_included_mc_index` and DAG `level`. Both conditions are reachable by an unprivileged actor: anyone can define an AA that reads a `data_feed`, and anyone can trigger an existing "oracle AA" twice with carefully timed/parent-selected triggering units so that its two response units land at the same level within the min/max MCI window used by the reader. No special privileges, hub/peer position, or leaked keys are required — only crafting and posting ordinary units/triggers.

### Recommendation
Replace the `throw Error("can't sort candidates ...")` in the tie-break comparator of `readDataFeedValue()` with a deterministic, non-throwing resolution (e.g., treat as `bAbortedBecauseOfSeveral` or apply a further deterministic tie-breaker such as unit hash) so that AA-triggered `data_feed` evaluation can never raise a synchronous exception. Additionally, wrap the AA-trigger execution pipeline (`handleAATriggers`/`handlePrimaryAATrigger`/`handleTrigger`) in defensive error handling so an unexpected internal exception cannot leave the `aa_triggers` mutex locked or crash the process, degrading gracefully instead (e.g., bouncing the specific trigger) rather than halting stabilization network-wide.

### Proof of Concept
1. Deploy AA `Oracle` that, on any trigger, emits a `data_feed` message with a fixed `feed_name` (e.g. as part of its state-update logic), acting as a price/exchange-rate oracle.
2. Deploy AA `Consumer` whose formula contains `data_feed[[oracles='<Oracle address>', feed_name='rate']]` (default `ifseveral="last"`), mirroring the pattern used in `futures_contract.oscript`'s exchange-rate lookup: [7](#0-6) 
3. Trigger `Oracle` twice with two units chosen/parent-selected so that the resulting AA response units both stabilize as unstable-but-good, with identical `latest_included_mc_index` and DAG `level`, before either is stable.
4. Trigger `Consumer` so that its formula evaluates `data_feed[[...]]` while both `Oracle` response candidates are still in `storage.assocUnstableMessages` — `readDataFeedValue()`'s candidate list will contain two entries tied on `latest_included_mc_index` and `level`, driving the sort comparator to `throw Error("can't sort candidates ...")` synchronously inside `handleAATriggers()`, crashing/deadlocking every full node that processes this stabilized MCI.
