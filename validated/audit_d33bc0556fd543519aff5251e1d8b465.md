### Title
Permanently unclaimable creator fees when `initialize_with_permission` sets `pool_creator` to an unowned/unsignable address - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` accepts `creator` as an `UncheckedAccount` (not a `Signer`), so any unprivileged caller of `initialize_with_permission` can set the pool's permanent `pool_creator` field to an arbitrary attacker-chosen pubkey that no one controls a private key for. `PoolState::initialize` stores this value verbatim with no validation, and it is never changeable afterward.

### Finding Description
In `initialize_with_permission.rs` the `creator` account is declared only as `/// CHECK: creator of pool` `pub creator: UncheckedAccount<'info>` [1](#0-0) , unlike `initialize.rs` where `creator` must be a `Signer` [2](#0-1) . The actual funds are supplied by `payer`, while `creator` is a free-form account reference used purely to populate `pool_state.pool_creator`. `PoolState::initialize` copies whatever pubkey is passed in without any check that it corresponds to a keypair, an ATA owner, or any account capable of proving control later: [3](#0-2) 

This is directly analogous to NFTR-11: a permanent “owner” reference is stored (the coveted asset there being the reserved name; here it is the right to collect the pool's `creator_fees_token_0`/`creator_fees_token_1`), and once that owner reference points to an address nobody can produce a signature for, the associated right becomes permanently unusable, exactly like a burned NFT with no owner.

`collect_creator_fee` requires `creator` to be the transaction `Signer` and to match `pool_state.pool_creator` [4](#0-3) . If `pool_creator` was set to an address with no known private key (e.g., a random pubkey, a foreign program's PDA, or a hash with no discoverable seed), this instruction can never be signed and is permanently unusable for that pool.

`collect_creator_fee_permissionless` avoids the signer requirement, letting anyone route the fee to an ATA owned by `pool_creator` [5](#0-4) [6](#0-5) . However, since ATA creation with `associated_token::authority = creator` works for any pubkey regardless of whether a private key exists for it, the tokens end up sitting in a token account whose owner can never sign a transfer — the funds are moved but remain permanently unspendable, i.e., permanently frozen rather than genuinely returned to a controllable party.

There is no `dereserve`/`update_creator`/`transfer_pool_creator` instruction anywhere in the program to correct a bad `pool_creator` once the pool is created, mirroring the exact recommendation from the NFTR report (allow reassignment/dereservation when the recorded owner cannot act) that was never implemented here.

### Impact Explanation
Accumulated `creator_fees_token_0` / `creator_fees_token_1` for a pool created via `initialize_with_permission` can become permanently locked/frozen if `pool_creator` is set (whether by mistake, third-party pool deployment tooling, or malicious front-running of the `initialize_with_permission` call) to an address without a spendable private key. Because `pool_state` and its `pool_creator` field are immutable after creation and there is no permissionless-fund-rescue-with-new-creator path, this constitutes permanent freezing of protocol/creator fee funds tied to that pool for its entire lifetime.

### Likelihood Explanation
`initialize_with_permission` is reachable by any account holding a valid `PermissionPda` (or whatever gating exists at the call-site) but the `creator` field itself is completely unchecked and attacker-controlled within that single transaction — no signature or account-ownership proof is required for it. Any party constructing this instruction (the payer, a front-end bug, or a malicious integrator) can trivially supply an arbitrary or vanity pubkey they don't control as `creator`, silently bricking future creator-fee collection for that pool. This requires no special privilege beyond being able to call `initialize_with_permission`, which is within the reachable, unprivileged surface described in the scope.

### Recommendation
Require `creator` in `InitializeWithPermission` to either be a `Signer`, or add an explicit acknowledgment/attestation step so the designated `pool_creator` can prove key ownership before the pool is finalized. Alternatively, add a permissionless instruction to change `pool_creator` to a new address in the case the currently stored one cannot sign, similar to what the NFTR report recommended for dereserving names tied to burned/ownerless NFTs.

### Proof of Concept
1. Attacker (or a naive integrator) calls `initialize_with_permission` supplying `payer` as their own signer but `creator` as an arbitrary pubkey `X` with no known private key (e.g., a hash of random bytes, or an address belonging to a program with no way to sign arbitrary instructions).
2. `PoolState::initialize` stores `pool_creator = X` permanently [7](#0-6) .
3. Over time, swaps accrue `creator_fees_token_0`/`creator_fees_token_1` in `pool_state`.
4. `collect_creator_fee` can never succeed because it requires `creator` to be `X`'s signature [4](#0-3) .
5. `collect_creator_fee_permissionless` can be called by anyone, but it only moves the funds into an ATA owned by `X` [6](#0-5) ; since `X` has no private key, those tokens are now permanently unspendable — funds are frozen forever with no recovery path in the program.
