### Title
Indirect (unpaired) correspondents can invoke the full wallet message-handling switch instead of being restricted to a safe subset - (File: wallet.js)

### Summary
`handleMessageFromHub` in `wallet.js` receives every device message routed from the hub and dispatches on `json.subject` through a large switch statement covering wallet creation, multisig `sign` requests, private-payment forwarding, and arbiter-contract handling. The function accepts a `bIndirectCorrespondent` flag indicating the sender is not a directly paired/trusted correspondent, but the authorization check that is supposed to restrict such senders to a narrow safe subset of subjects is commented out.

### Finding Description
`handleMessageFromHub(ws, json, device_pubkey, bIndirectCorrespondent, callbacks)` is meant to gate untrusted, indirectly-known correspondents (devices reached only transitively, e.g. as other cosigners in a shared/multisig wallet, not devices the user explicitly paired with) to only `cancel_new_wallet`, `my_xpubkey`, and `new_wallet_address` subjects. That restriction line is present but disabled: [1](#0-0) 
Because the check never executes, any indirect correspondent can reach every case in the switch, including:
- `sign` — request a device to sign a unit for a shared/multisig address, including one containing private payment payloads [2](#0-1) 
- `object`/`text` — arbitrary emit into wallet UI event handlers [3](#0-2) 
- `arbiter_contract_shared` / `arbiter_contract_update` — contract state manipulation gated only on DB checks tied to `from_address`, not on correspondent trust level [4](#0-3) 

This is directly analogous to the Geode CVE-2017-5649 pattern: an actor holding a lesser permission level (`CLUSTER:READ`, here "indirect correspondent") is able to reach functionality intended only for a higher-trust principal (`DATA:READ`, here "paired/direct correspondent"), because an authorization gate that should separate the two capability tiers was disabled/removed rather than enforced.

### Impact Explanation
An indirect correspondent — a device known to the wallet only transitively (e.g., as another signer on a shared multisig address) and never explicitly paired/approved by the user — can send `sign` requests for arbitrary unsigned units, including ones carrying `private_payloads` describing hidden payment outputs, triggering `findAddress`/`network.handleOnlineJoint` and a `signing_request` UI confirmation event with sensitive payment details. It can also drive `arbiter_contract_shared`/`arbiter_contract_update` state transitions using only address/signing-path matches, without honoring the intended lower trust level for indirect correspondents. This can lead to unwanted disclosure of private-payment structure, spurious signing prompts that pressure a user into approving a malicious unit, or contract-state confusion — capabilities that were explicitly meant to be withheld from non-paired devices.

### Likelihood Explanation
`bIndirectCorrespondent` sources are inherently less trusted (introduced via `device.addIndirectCorrespondents`, reachable simply by being listed as a cosigner in a shared wallet definition someone shares with the victim). Since the guard is fully commented out rather than conditionally bypassed, every message from such a device reaches the full switch with no additional gate — this requires no race condition or edge case, just sending a hub message with the sender's device pubkey/signature which the sender already legitimately controls.

### Recommendation
Re-enable and enforce the commented-out authorization check at `wallet.js:92-93`, restricting `bIndirectCorrespondent` senders to the intended safe subset of subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`), and audit whether additional subjects (e.g., `wallet_fully_approved`) also need to be included in that allow-list rather than left reachable by default.

### Proof of Concept
1. Become an indirect correspondent of a victim wallet by being included as a cosigner address in a shared/multisig wallet definition template that gets forwarded to the victim (`walletDefinedByKeys.handleOfferToCreateNewWallet` path), without ever being explicitly paired by the victim.
2. Send a `hub/message` device message with `subject: "sign"` and a crafted `unsigned_unit` referencing a shared address the victim controls, along with `signing_path` matching a cosigner path.
3. Because the `bIndirectCorrespondent` check at `wallet.js:92-93` is disabled, `doHandle()` proceeds to the `sign` case at `wallet.js:251` and triggers `findAddress` → `signing_request` event, surfacing a signing prompt/private payload details to the victim's wallet UI despite the sender never having been trusted as a direct correspondent.
