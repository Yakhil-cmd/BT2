### Title
Unbounded single-block epoch-reward calculation over all stake delegations can exceed epoch-boundary slot-time budget - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
At every epoch boundary, `Bank::compute_new_epoch_caches_and_rewards` triggers `calculate_rewards_for_partitioning`, which in turn calls `calculate_stake_rewards_and_commissions` and `calculate_reward_points_partitioned`. These functions iterate over *every* stake delegation on the network in a single call within the epoch-boundary block, unlike the reward *distribution* step which is explicitly chunked (`get_reward_distribution_num_blocks`, `MAX_PARTITIONED_REWARDS_PER_BLOCK`) across multiple blocks specifically to bound per-block work. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`calculate_stake_rewards_and_commissions` pre-allocates and processes a `PartitionedStakeRewards` vector sized to `stake_delegations.len()`, running `redeem_delegation_rewards` (and, when block-revenue-sharing is enabled, `calculate_block_reward`) for every single stake delegation via `rayon::par_iter`, entirely within the processing of one bank/slot at the epoch boundary: [4](#0-3) 

Similarly, `calculate_reward_points_partitioned` iterates every stake delegation to sum reward points for the Tower/migration epoch types: [5](#0-4) 

By contrast, the accompanying *distribution* subsystem was explicitly designed to bound per-block work to `MAX_PARTITIONED_REWARDS_PER_BLOCK` (4096) stake-account stores, and further clamps the number of distribution blocks to at most 10% of the epoch's slots: [6](#0-5) [3](#0-2) 

No equivalent per-block cap exists for the *calculation* phase; it always runs to completion for the full stake-delegation set in the single epoch-boundary block, parallelized only by a thread pool with no bound on `stake_delegations.len()`. The code's own comment acknowledges this scaling concern explicitly ("For N stake delegations, where N is >1,000,000, we produce...").

This is directly analogous to the reported `timelockERC721Keys` issue: a loop whose length is proportional to the growth of a permissionless, unprivileged-user-controlled data structure (the total number of delegated stake accounts, which any user can create via the System/Stake programs) is fully processed within a single fixed-time unit (a block/slot), with the growth trigger explicitly being "if project is very successful" — i.e., cluster growth over time, not any privileged/validator action.

### Impact Explanation
If the total number of stake delegations grows large enough that a single-threaded-equivalent pass (bounded by available CPU cores via rayon, not artificially capped) cannot complete within the slot-time budget of the epoch-boundary block, that bank's freeze/replay would take excessively long. Because every validator computing the same epoch-boundary bank must perform this same unbounded computation, this could cause a cluster-wide slowdown or halt at every epoch boundary (an "epoch-boundary halt"), which is an explicitly accepted impact category for this scan.

### Likelihood Explanation
Likelihood is currently low-to-moderate: rayon-based parallelism across many delegations mitigates the practical risk today, and the number of stake accounts required to exceed the epoch-boundary time budget would need to be very large. However, since stake account creation is permissionless and unprivileged (via `system_instruction::create_account` + `stake_instruction::initialize`/`delegate_stake`), the input set that drives this loop is entirely attacker/user-growable over time, matching the acknowledged Visor Finance scenario where the bug "may happen if project is very successful."

### Recommendation
Apply the same chunking/partitioning strategy already used for the distribution phase to the calculation phase: cap the amount of `stake_delegations` processed per epoch-boundary block (e.g., via `MAX_PARTITIONED_REWARDS_PER_BLOCK`-style limits) and spread the calculation itself across multiple blocks, or otherwise bound/parallelize with a hard ceiling independent of stake-delegation count, so the epoch-boundary block's synchronous work is provably bounded regardless of total stake-delegation growth.

### Proof of Concept
1. Grow the total number of unique stake accounts/delegations on a cluster to a very large number (permissionless, since anyone can create a stake account and delegate it via System/Stake program instructions).
2. At the next epoch boundary, `Bank::compute_new_epoch_caches_and_rewards` calls `calculate_rewards_for_partitioning`, which synchronously calls `calculate_stake_rewards_and_commissions` over the entire `stake_delegations` vector [7](#0-6) .
3. Unlike the bounded distribution phase (`get_reward_distribution_num_blocks` clamps to `MAX_PARTITIONED_REWARDS_PER_BLOCK` per block, capped at 10% of slots per epoch) [3](#0-2) , the calculation phase has no such per-block bound, so its wall-clock cost grows linearly (modulo parallelism) with the total stake-delegation count and must complete within a single slot's time budget.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

                1,
