### Title
Unguarded Zero `CLPoolAddr` in CL Staking Reward Distribution Sends KAIA to the Zero Address — (`kaiax/reward/impl/getter.go`)

### Summary

After the Prague hardfork, staking rewards for validators with Consensus Liquidity (CL) are split between the validator's AddressBook reward address (`cn.RewardAddr`) and the CL pool address (`cn.CLStakingInfo.CLPoolAddr`). Neither `assignStakingRewards`, `assignStakingRewardsFlex`, `specWithProposerAndFunds`, nor `specWithProposerAndFundsFlex` checks whether `CLPoolAddr` is the zero address before crediting it. If the CLRegistry returns a zero pool address — which the staking ingestion layer (`parseCallResult`, `parsePermissionlessCallResult`) also never validates — the corresponding KAIA reward share is credited to `address(0)` and permanently lost.

### Finding Description

In `assignStakingRewards` (Prague branch):

```go
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount   // ← no zero-address guard
}
```

The only guard is `cn.CLStakingInfo != nil`. There is no check that `cn.CLStakingInfo.CLPoolAddr != common.Address{}`. The same pattern appears in `assignStakingRewardsFlex` and in both `specWithProposerAndFunds` / `specWithProposerAndFundsFlex` for the proposer's CL split.

The `CLPoolAddr` value originates from the CLRegistry contract, read via `contract.MultiCallDPStakingInfo` and stored verbatim in `parseCallResult` / `parsePermissionlessCallResult` without any zero-address validation:

```go
clStakingInfos[i] = &staking.CLStakingInfo{
    CLNodeId:        clRes.NodeIds[i],
    CLPoolAddr:      clRes.ClPools[i],          // ← stored without zero check
    CLStakingAmount: ...,
}
```

`FinalizeState` then iterates `spec.Rewards` and calls `state.AddBalance(addr, amount)` for every entry, including `address(0)`:

```go
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)   // addr may be common.Address{}
}

### Impact Explanation

Any KAIA allocated as `clAmount` for a validator whose `CLPoolAddr` is `address(0)` is credited to the zero address via `state.AddBalance`. In Kaia's EVM state, `address(0)` is a normal account with no private key; funds sent there are unrecoverable. This constitutes an **unauthorized loss of KAIA from the reward pool** — the minted inflation and collected fees that should reach a legitimate CL pool are instead permanently burned. The `RewardSpec.Rewards` map will contain `address(0) → clAmount`, which also corrupts the reward accounting visible through `kaia_getReward`.

### Likelihood Explanation

The CLRegistry is a system contract populated by validators registering their CL pool addresses. If the CLRegistry contract does not enforce a non-zero pool address at registration time, a validator (or a misconfigured registration transaction) can store `address(0)` as `CLPoolAddr`. The Go staking ingestion layer (`parseCallResult`, `parsePermissionlessCallResult`) performs no zero-address validation on `clRes.ClPools[i]`, so the zero value propagates into `CLStakingInfo` and subsequently into reward distribution every block for that validator. The trigger requires only a valid CLRegistry entry with a zero pool address — no privileged access beyond normal validator registration.

### Recommendation

Add a zero-address guard in all four reward-distribution sites before crediting `CLPoolAddr`:

```go
// In assignStakingRewards, assignStakingRewardsFlex,
// specWithProposerAndFunds, specWithProposerAndFundsFlex:
if isPrague && cn.CLStakingInfo != nil &&
    !common.EmptyAddress(cn.CLStakingInfo.CLPoolAddr) {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
} else {
    alloc[cn.RewardAddr] = reward  // full amount stays with CN
}
```

Additionally, add a zero-address check in `parseCallResult` and `parsePermissionlessCallResult` when constructing `CLStakingInfo`, and consider rejecting or logging a warning when `CLPoolAddr` is zero.

### Proof of Concept

1. A validator registers in the CLRegistry with `CLPoolAddr = address(0)` (either due to a bug in the registry contract or a misconfigured call).
2. `getFromState` calls `contract.MultiCallDPStakingInfo`, which returns `clRes.ClPools[i] = address(0)`.
3. `parseCallResult` / `parsePermissionlessCallResult` stores it verbatim: `CLStakingInfo{CLPoolAddr: common.Address{}, CLStakingAmount: X}`.
4. `consolidateNodes` attaches this `CLStakingInfo` to the consolidated node.
5. At block finalization, `assignStakingRewards` (or `assignStakingRewardsFlex`) enters the `isPrague && cn.CLStakingInfo != nil` branch, calls `cn.Split(reward)`, and writes `alloc[common.Address{}] = clAmount`.
6. `specWithProposerAndFunds` similarly writes `newSpec.IncRecipient(common.Address{}, clAmount)` for the proposer's CL split.
7. `FinalizeState` calls `state.AddBalance(common.Address{}, clAmount)` — KAIA is credited to the zero address and lost permanently every block. [8](#0-7) [9](#0-8) [10](#0-9) [11](#0-10)

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
