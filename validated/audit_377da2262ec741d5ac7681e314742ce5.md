### Title
Double-counting of L1 Bitcoin lockup collateral across separate `register-for-bond` calls — ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond` credits `sats-total` uSTX/sBTC-equivalent staking weight by verifying a staker's Bitcoin L1 timelock outputs in `verify-l1-lockups` / `validate-l1-lockup`. The de-duplication of Bitcoin outpoints (`seen-outpoints`) is only tracked **within a single call's fold accumulator** and is never persisted to contract storage. There is no map recording "this UTXO has already been credited to bond X" across separate transactions/bonds.

### Finding Description
In `register-for-bond` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:642-841`), the L1 path computes:
```
(sats-total (try! (match btc-lockup
    l1-lockups (verify-l1-lockups tx-sender bond-index l1-lockups)
    sbtc-amount (ok sbtc-amount))))
``` [1](#0-0) 

`verify-l1-lockups` initializes a **fresh, empty** `seen-outpoints` list for each call and folds over the supplied outputs, checking script/amount/merkle-proof validity and rejecting only duplicates *within that same list*:
```
(accumulation (try! (fold validate-l1-lockup (get outputs lockups)
    (ok { sum: u0, staker: staker, ... seen-outpoints: (list) }))))
``` [2](#0-1) 

`validate-l1-lockup` asserts `(is-none (index-of? seen-outpoints outpoint))` against that local, per-call list, then credits `sum` with the output's `amount`:
```
(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)
...
(ok { ... sum: (+ (get sum accumulator) (get amount output)),
      seen-outpoints: (unwrap-panic (as-max-len? (append seen-outpoints outpoint) u10)) })
``` [3](#0-2) 

Nowhere in `register-for-bond`, `verify-l1-lockups`, or `validate-l1-lockup` is there a persistent map (e.g. a `used-outpoints` map keyed by `{txid, output-index}`) that survives across transactions or across different `bond-index` values. This means the same on-chain Bitcoin timelock output can be presented again in a later `register-for-bond` call (for the same or a different `bond-index`/allowlist slot, or even a different `staker` value that the L1 script happens to also validate against) to mint additional `sats-total` credit without any additional BTC ever being locked. Since `sats-total` directly feeds `protocol-bonds-total-staked`, `add-staker-to-bond-cycles` (signer/reward-cycle share accounting) and gates the minimum `amount-ustx` requirement, a staker can re-submit the exact same already-proven Bitcoin UTXO in a fresh `register-for-bond` call to claim bond participation (and thus reward-cycle shares / signer weight) a second time while only having locked BTC once.

This breaks the intended equality: `sum(sats credited across all active bonds) == sats actually locked on Bitcoin by verified, unique UTXOs`. The contract only prevents reuse of a UTXO within one call's list of up to 10 outputs; it never checks against the set of UTXOs already consumed by prior successful registrations.

### Impact Explanation
This is a double-counting of a Bitcoin-backed commitment: the same physical BTC lockup can be counted for staking weight in more than one protocol bond, inflating `protocol-bonds-total-staked`, signer reward-cycle shares (`add-staker-to-bond-cycles`, `add-staker-to-signer-cycles`), and consequently sBTC reward distribution weight (`calculate-rewards`) without a corresponding real increase in locked collateral. This matches the Critical impact category "double-counting a commitment or reward" — sBTC rewards would be paid out based on inflated stake that was never actually locked a second time.

### Likelihood Explanation
Any unprivileged allowlisted staker calling `register-for-bond` can reuse the *same* verified L1 lockup transaction/output across multiple registrations (e.g., re-registering into a second bond period, or by any allowlisted principal that is validated by the same timelock script) since there is no persistent cross-call outpoint tracking. This requires no admin/bond/pause privileges and no cooperation from other users — only that the attacker be allowlisted for more than one bond (a normal, expected staker workflow), or that the same script conditions validate under `construct-lockup-output-script` for more than one principal.

### Recommendation
Introduce a persistent map, e.g. `used-l1-lockup-outpoints: {txid: (buff 32), output-index: uint} -> bool`, and have `validate-l1-lockup` (or `verify-l1-lockups`) check-and-insert against this global map rather than (or in addition to) the local per-call `seen-outpoints` list, so that once a Bitcoin outpoint has been credited to any bond, it cannot be credited again in a subsequent `register-for-bond` call.

### Proof of Concept
1. Staker is allowlisted for `bond-index = A` and later for `bond-index = B` (a normal allowlist scenario, or the same allowlist entry re-added after A's bond cycle passes).
2. Staker locks BTC once via a valid L1 timelock output `O` (txid/output-index), and calls `register-for-bond(A, ..., btc-lockup = Ok([O]), ...)`. `verify-l1-lockups` validates `O` and credits `sats-total = amount(O)`; `protocol-bond-memberships` and `protocol-bonds-total-staked` for `A` are updated.
3. Staker calls `register-for-bond(B, ..., btc-lockup = Ok([O]), ...)` presenting the identical, still-unspent-on-L1 output `O` again. `verify-l1-lockups`'s `seen-outpoints` check only rejects duplicates within the *current* call's `outputs` list (which contains just `O` once), so it passes, again crediting `sats-total = amount(O)` for bond `B`.
4. Result: `protocol-bonds-total-staked` for A and B both count `amount(O)`, and reward/signer-share accounting for two separate bonds is backed by a single BTC lockup — double-counted collateral, since no global outpoint-usage table exists in `stackslib/src/chainstate/stacks/boot/pox-5.clar`.

Note: I was unable to fully trace `get-bond-l1-unlock-height`/`bond-period-to-burn-height` definitions (search returned no matches in this file within the remaining budget) to confirm whether cross-bond timing constraints (e.g., requiring the prior bond to have fully ended before `B`'s registration) would incidentally block this reuse in every case. The core defect — absence of persistent global outpoint tracking in `verify-l1-lockups`/`validate-l1-lockup` — is confirmed directly from the code shown above.
