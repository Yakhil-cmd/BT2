### Title
Release asset `Name` containing `../` traversal or absolute path bypasses destination confinement in `destinationWriter.makePath` - ([File: pkg/cmd/release/download/download.go])

### Summary
`destinationWriter.makePath` joins the attacker-controlled release asset `Name` directly with `opts.Destination` via `filepath.Join`, and neither `makePath` nor `check`/`Copy` validate that the resulting path stays within the destination directory. A release asset named e.g. `../../evil.sh` (or an absolute path) will resolve outside `opts.Destination`, and `Copy` will `os.MkdirAll` the parent directories and `os.OpenFile` with `O_CREATE|O_TRUNC` at that location.

### Finding Description
In `downloadRun`, assets are pulled from the release API response (`release.Assets`), and each asset's `Name` field flows unmodified into `downloadTarget.name` [1](#0-0) . That name is passed to `downloadAsset` → `dest.Check(fileName)` → `dest.Copy(fileName, ...)` [2](#0-1) [3](#0-2) .

`makePath` does no sanitization — it simply does `filepath.Join(w.dir, name)`, which normalizes/cleans `..` segments rather than rejecting them, so a name like `../../evil.sh` produces a path outside `w.dir`: [4](#0-3) 

`check` only verifies whether a file already exists at the computed path (for `--clobber`/`--skip-existing` semantics) — it performs no containment/confinement check against `w.dir`: [5](#0-4) 

`Copy` then creates any needed parent directories and opens the file for writing, truncating any existing content: [6](#0-5) 

Notably, the only filename filtering that occurs prior to this is `isWindowsReservedFilename` for Windows reserved device names [7](#0-6)  — there is no equivalent check for path traversal or absolute paths. By contrast, the sibling `pkg/cmd/run/download` feature uses `safepaths.Absolute` and `ghzip.ExtractZip` for confinement when extracting artifact ZIPs [8](#0-7) , showing that this class of protection is a known pattern in the codebase but is absent from `pkg/cmd/release/download/download.go`.

Since a GitHub repository owner (or fork owner) fully controls the `Name` field of assets they upload to their own release, and `gh release download` with `-p/--pattern` (or without any pattern) will iterate `release.Assets` and pass `a.Name` straight through, an attacker who owns/controls a repo/release can name an asset `../../evil.sh` or similar to escape `opts.Destination`.

### Impact Explanation
This allows arbitrary file write/overwrite outside the intended destination directory chosen by the victim (e.g., `~/Downloads` or CWD), on the victim's filesystem, when they run `gh release download` against an attacker-controlled repository/release (including their own public repos or forks visible to the victim). This maps to GitHub's "arbitrary file write" bounty impact class and could be leveraged for further compromise depending on where the write lands (e.g., overwriting startup files, shell profiles, or other automation the victim may execute later).

### Likelihood Explanation
Feasibility is high and repeatable: the attacker only needs the ability to publish a release with a custom asset filename (e.g., via GitHub's upload API/UI when creating a release asset — GitHub does permit slashes and `..` in the metadata `name` field, distinct from the underlying storage blob), and the victim needs to run `gh release download` (with or without `--pattern`) against that release. No elevated privileges, tokens, or MITM are required — only the victim choosing to download from an attacker-owned/attacker-controlled repo.

### Recommendation
In `destinationWriter.makePath` (or before it's used in `Check`/`Copy`), reject or sanitize asset names that are absolute or contain `..` path segments after `filepath.Clean`, and/or verify with `filepath.Rel(w.dir, fp)` that the resulting path does not escape `w.dir` (rejecting if `Rel` returns a path starting with `..` or is absolute) before calling `os.MkdirAll`/`os.OpenFile`. Consider reusing the existing `internal/safepaths` abstraction used by `pkg/cmd/run/download`.

### Proof of Concept
```go
func TestDestinationWriter_PathTraversal(t *testing.T) {
    tmp := t.TempDir()
    w := destinationWriter{dir: tmp}
    fp := w.makePath("../../evil.sh")
    // fp resolves outside tmp
    rel, err := filepath.Rel(tmp, fp)
    require.NoError(t, err)
    require.True(t, strings.HasPrefix(rel, ".."), "path escapes destination: %s", fp)

    err = w.Copy("../../evil.sh", strings.NewReader("malicious"))
    require.NoError(t, err) // currently succeeds - should be rejected
    _, statErr := os.Stat(fp)
    require.NoError(t, statErr, "file was written outside destination")
}
```
An end-to-end variant would use `httpmock` to serve a release JSON with `assets: [{name: "../../evil.sh", url: ...}]`, invoke `downloadRun` with `Destination` set to a temp subdirectory, and assert that a file is created at `<tempdir's parent>/evil.sh` outside `Destination`.
