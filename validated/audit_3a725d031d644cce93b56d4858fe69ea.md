### Title
Cross-tenant webhook forgery: HMAC signature is validated against the organization named in `repository.owner.login`, while event handlers write to the stack named in the untrusted `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary

### Finding Description
Shipit supports hosting multiple GitHub organizations/tenants on a single instance, each with its own independent `webhook_secret`, as documented under "Using Multiple Github Applications" [1](#0-0)  and exercised in `test/dummy/config/secrets_double_github_app.yml` [2](#0-1) . Every tenant posts to the same shared `/github/webhooks` endpoint handled by `WebhooksController`.

`WebhooksController#verify_signature` decides *which tenant's secret* to check the HMAC against purely from an attacker-supplied field inside the raw JSON body itself: [3](#0-2) [4](#0-3) 

`Shipit.github(organization: repository_owner)` resolves to the `GitHubApp`/`webhook_secret` configured for whatever organization name is present at `repository.owner.login` in the body [5](#0-4) .

Once the signature is accepted, `WebhooksController#create` dispatches the *entire, attacker-controlled* JSON body to the registered handlers [6](#0-5) . Those handlers resolve the target `Repository`/`Stack` from a **different** field of the same body — `repository.full_name` — not from `repository.owner.login`: [7](#0-6) 

For example `PushHandler#process` uses that repository/stack lookup to trigger a sync with an attacker-chosen `expected_head_sha`: [8](#0-7) ; `StatusHandler#process` writes commit statuses [9](#0-8) ; several pull-request handlers archive/unarchive review stacks by the same `repository.full_name` field (e.g. `closed_handler.rb`, `reopened_handler.rb`, `labeled_handler.rb`).

Because the request is a bare unauthenticated HTTP POST fabricated by the caller (not literally relayed unmodified by GitHub), an actor who legitimately administers one tenant, "Org A", on the shared instance — and therefore legitimately knows Org A's `webhook_secret` (handed out per-tenant by design in the multi-org feature) — can build a body where:
- `repository.owner.login = "OrgA"` so `verify_signature` selects Org A's `GitHubApp` and the HMAC computed with the known Org A secret validates, and
- `repository.full_name = "OrgB/some-repo"`, naming a repository/stack that belongs to a completely different tenant, "Org B", hosted on the same instance, which the attacker has no access to.

The webhook is accepted, and handlers act on Org B's stack using data the attacker fully controls (forced re-sync to an attacker-chosen commit, forged CI/commit statuses, forged review-stack archive/unarchive events, etc.). This is exactly a break of the "organization that authenticated versus the repository that is written" binding: `verify_signature` authenticates *who signed*, but the handlers act on *whatever repository name is embedded in the same signed body*, and nothing ties those two fields together.

### Impact Explanation
This lets a tenant with zero privileges on Org B force writes against Org B's stacks (triggering syncs/deplo* pipelines with attacker-chosen SHAs, forging GitHub commit statuses that gate deploy eligibility, and archiving/unarchiving Org B's review stacks) purely by knowing a webhook secret that belongs to a different, unrelated tenant they legitimately administer. This matches the "cross-repository writes" Critical-impact category: an org boundary that is supposed to isolate tenants on a shared Shipit install is not enforced past signature verification.

### Likelihood Explanation
Exploitation requires no Shipit session, `ApiClient` token, or GitHub App private key — only knowledge of the webhook secret for any single tenant configured on the shared instance, which the multi-org feature explicitly distributes to each tenant's own administrators. Any instance operator running the documented multi-organization configuration is exposed; this is a design/implementation gap rather than a theoretical edge case, since `repository.owner.login` and `repository.full_name` are never cross-checked anywhere in the request path.

### Recommendation
After determining `repository_owner` and successfully verifying the signature, `WebhooksController` (or `Handlers::Handler`) should also verify that the resolved `Repository`/`Stack` for `repository.full_name` actually belongs to the same organization (`repository.owner.login`) that was used to select the signing secret, rejecting (422) any payload where these fields diverge. Alternatively, resolve the repository/stack once (from `full_name`) and derive the verification organization from that resolved repository's own owner rather than trusting a second untied field in the same body.

### Proof of Concept
Not executed (no sandbox/terminal access in this mode); conceptually:
1. Deploy Shipit with the documented multi-org config (`OrgA`, `OrgB`, distinct `webhook_secret`s), each with stacks configured for their respective repos [2](#0-1) .
2. As an OrgA admin (who legitimately knows OrgA's `webhook_secret`), craft a `push` event JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/target-repo"`, `ref = refs/heads/<OrgB stack branch>`, and an attacker-chosen `after` SHA.
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POST to the shared `/github/webhooks` endpoint with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` picks `Shipit.github(organization: "OrgA")` and the signature validates [3](#0-2) .
5. `PushHandler#process` resolves OrgB's stack via `repository.full_name` and calls `stack.sync_github(expected_head_sha: <attacker sha>)` [8](#0-7) , demonstrating a cross-tenant write despite the signature only proving knowledge of OrgA's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
