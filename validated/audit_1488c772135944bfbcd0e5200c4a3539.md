### Title
Donated (self-issued) asset can push an AA's tracked balance past `MAX_BALANCE`, causing the trigger to bounce and permanently freezing that AA/asset combination - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `updateInitialAABalances` adds the amounts received in a trigger's payment outputs to the AA's tracked per-asset balance and checks the result against a hardcoded ceiling `MAX_BALANCE`. Because any user can issue a custom asset with `cap` up to `constants.MAX_CAP` and "donate" it to an AA address, an attacker can push the AA's stored `aa_balances` row for that asset above `MAX_BALANCE` in a single payment. The overflow check runs only after the `UPDATE ... SET balance=balance+?` query has already been queued/executed, so the corrupted (over-limit) balance is persisted even though the triggering call is bounced. This is directly analogous to the reported Solidity bug: a donated token inflates an internal accounting value past its allowed maximum, which then makes every subsequent legitimate operation (there: `withdraw`; here: any AA trigger involving that asset) revert/bounce.

### Finding Description
`MAX_BALANCE` is defined as `2**63 - 1 - constants.MAX_MESSAGES_PER_UNIT * constants.MAX_CAP` [1](#0-0) . In `updateInitialAABalances`, for every asset that the trigger unit pays to the AA, the code adds the payment amount to the AA's balance and sets `bOverflow` when the resulting value exceeds `MAX_BALANCE`: [2](#0-1) 

Critically, the `UPDATE aa_balances SET balance=balance+?` query for that asset is queued into `arrQueries` in the very same loop iteration that detects the overflow, and all queued queries are executed via `async.series(arrQueries, ...)` before the overflow error is surfaced through `cb(...)`: [3](#0-2) 

So the erroneous "return balance overflow" is only used to bounce the *current* trigger's response - the underlying `aa_balances` row for that address/asset has already been permanently incremented past `MAX_BALANCE` in the database. Any future trigger unit that sends even a tiny additional amount of the same asset to that AA address will again exceed `MAX_BALANCE` and again get flagged with `bOverflow`, because the check is a strict `>` comparison against a value the balance can never go back below (asset balances only increase via trigger payments and are not intentionally decremented back under the cap by any repair mechanism visible in this code path). This mirrors the reported bug class: an externally donated/self-issued asset inflates an internal accounted value beyond a hard-coded bound, causing subsequent legitimate calls that touch that same accounting slot to fail.

The overflow guard itself is only enforced from `constants.pemCurvesFixMci` onward: [4](#0-3) 

An attacker does not need any special privilege: any address can define a custom asset (`payload.cap <= constants.MAX_CAP` is the only cap-related requirement) via a normal `asset` message, issue up to that cap, and send it in a `payment` message to any AA address that is designed to accept arbitrary/attacker-chosen assets (e.g., a DEX/vault-style AA that tracks balances per asset for deposits). Because `MAX_CAP` is itself very close to the `MAX_BALANCE` threshold subtracted only by `MAX_MESSAGES_PER_UNIT` issuances worth of headroom, a single large donation (or a handful of donations under `MAX_MESSAGES_PER_UNIT`) is sufficient to overflow the accounted balance for that one asset.

### Impact Explanation
Once the AA's `aa_balances` entry for the targeted asset exceeds `MAX_BALANCE`, every future trigger unit that sends any positive amount of that asset to the AA will also be flagged as `bOverflow` and bounced. This effectively freezes the AA's ability to correctly process that asset going forward (any trigger whose payment includes an output in the poisoned asset can no longer complete normally), denying legitimate users of the AA the ability to interact with it using that asset - a fund-freezing / denial-of-service condition for the affected AA, reachable purely by posting a normal AA-triggering unit from an unprivileged asset issuer/attacker.

### Likelihood Explanation
Likelihood is moderate to high for any AA that is designed to accept externally-supplied/attacker-choosable assets (multi-asset vaults, DEX-style AAs, bridges), since defining and issuing a custom asset and sending it as a payment to an AA are both ordinary, unprivileged operations available to any user of the network.

### Recommendation
Do not persist the balance update to `aa_balances` (or should roll it back) when `bOverflow` is detected before the trigger is bounced, and/or cap accepted per-trigger/per-asset amounts independently of the cumulative stored balance so a single or repeated donation cannot push the recorded balance permanently past `MAX_BALANCE`. Consider validating/rejecting the donated amount at the point of computing `assocBalances`/`aa_balances` rather than after the DB write has already been queued, mirroring the type of fix referenced in the analog report (validate against overflow before updating persisted state, not after).

### Proof of Concept
1. Attacker defines a custom asset `X` with `cap` close to `constants.MAX_CAP` via an `asset` message unit (allowed for any address, subject only to `payload.cap <= constants.MAX_CAP`) [5](#0-4) .
2. Attacker issues the full cap of asset `X` to themselves (standard `issue` input flow) [6](#0-5) .
3. Attacker sends a `payment` message with asset `X` to a target AA's address that accepts arbitrary assets, in an amount sufficient (combined with `MAX_MESSAGES_PER_UNIT` headroom) to push `assocBalances[address][X]` above `MAX_BALANCE` in `updateInitialAABalances` [7](#0-6) .
4. The trigger bounces with "balance overflow", but the `UPDATE aa_balances SET balance=balance+?` for asset `X` has already been executed, permanently corrupting the AA's tracked balance for `X` [3](#0-2) .
5. Any subsequent legitimate trigger sending asset `X` to that AA will again overflow and bounce, freezing all future interactions involving asset `X` with that AA.
