### Title
Webhook signature verification is keyed to `repository.owner.login` while event handlers act on `repository.full_name` from the same untrusted payload, allowing cross-organization forgery of GitHub events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate an incoming payload's HMAC against by reading `repository.owner.login` (or `organization.login`) out of the same JSON body that the signature is supposed to protect, then all downstream event handlers resolve the `Repository`/`Stack` to write to using a different field of that same body: `repository.full_name`. Nothing binds "the organization whose secret validated this signature" to "the repository the handler will act upon," so in a multi-organization Shipit deployment, an attacker who legitimately controls the GitHub App/webhook secret for *any one* onboarded organization can forge a payload naming a *different* organization/repository in `repository.full_name` and have it processed as if GitHub sent it for that other repository.

### Finding Description
`verify_signature` does: [1](#0-0) 
It looks up the GitHub App config using `repository_owner`, which is itself parsed straight out of the attacker-controlled body: [2](#0-1) 

`Shipit.github(organization:)` resolves the per-organization `webhook_secret` from `config/secrets*.yml`, as shown by the multi-org config shape: [3](#0-2) 
and by `Shipit#github`/`#github_app_config` selecting the secret purely by the `organization` string: [4](#0-3) 

Once `verified` is true, `create` dispatches the entire (still attacker-controlled) JSON body to every handler for the declared `X-Github-Event`: [5](#0-4) 

Every handler, however, determines *which* repository/stack to mutate using `repository.full_name`, a completely independent field from the one used for signature routing: [6](#0-5) 
This pattern repeats identically across `PushHandler` and all `PullRequest::*Handler` classes: [7](#0-6) [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization_whose_secret_signed(payload) == owner_of(repository_the_handler_writes_to(payload))`

Before the attack: for a legitimate GitHub delivery, GitHub itself only ever sends a payload where `repository.owner.login` and `repository.full_name` refer to the same real repository, and it signs it with that repository's/organization's actual secret — so the equality holds by construction of GitHub's delivery mechanism.

After the attack: the attacker is the administrator of their own onboarded organization/App (a legitimate, unprivileged Shipit customer of the multi-tenant instance) and therefore knows that organization's `webhook_secret`. They compute a valid `X-Hub-Signature` for a payload where `repository.owner.login` is their own org (satisfying `verify_signature`) but `repository.full_name` names a stack/repository belonging to an entirely different, victim organization tracked by the same Shipit instance. The signature check only proves "someone who knows org A's secret sent this," never "this event actually originates from the repository named inside it," so the equality is broken and the handler acts on the victim repository using data entirely chosen by the attacker (branch name, head SHA, PR body/labels, sender login, etc.).

### Impact Explanation
This is a cross-organization/cross-repository write achieved without any Shipit session, API token, or the victim organization's webhook secret — only knowledge of a secret the attacker legitimately possesses for their own tenant. Concretely reachable consequences on any repository tracked by the same Shipit instance:
- `PushHandler#process` forces `stack.sync_github(expected_head_sha: params.after)` for any branch/stack the attacker names, using an attacker-chosen `after` SHA [9](#0-8) .
- `PullRequest::OpenedHandler#process` will provision a real `ReviewStack` (checking out and deploying code) for the victim repository if that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all?`, using an attacker-supplied branch/ref: [10](#0-9)  and [11](#0-10) .
- `PullRequest::ClosedHandler`/`ReopenedHandler`/`UnlabeledHandler` can archive or unarchive review stacks belonging to a repository the attacker does not own.

This satisfies the "cross-repository writes" / "unauthorized deploy" tier of impact defined in scope, because it lets an attacker who is authenticated only as a low-privilege tenant of the Shipit instance trigger stack synchronization and review-stack (deploy) provisioning against another organization's repository.

### Likelihood Explanation
Requires only that the attacker be an onboarded, unprivileged organization/App on the same multi-tenant Shipit instance (a normal state of affairs for shared/hosted Shipit deployments using the `github:` multi-org secrets schema) — no privileged account, no GitHub write access to the victim repo, and no interception of TLS or secrets is needed. The forged HTTP POST is trivial to construct once the attacker's own webhook secret is known, which they possess by design since they configured it.

### Recommendation
After computing `verified`, additionally assert that the organization used to select the webhook secret matches the owner encoded in every repository-bearing field the handlers will actually consume (e.g., require `repository.owner.login == repository.full_name.split('/').first`, or better, resolve the `Repository`/`Stack` via `Shipit::Repository.from_github_repo_name(repository.full_name)` first and verify that its configured Shipit "organization" is the same one whose secret validated the signature) before dispatching to handlers. Alternatively, mount organization-scoped webhook endpoints (e.g., `/webhooks/:organization`) so the URL, not payload content, determines which secret is used, then cross-check the payload's `repository.full_name` against that fixed organization.

### Proof of Concept
1. Shipit instance is configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` under `secrets.github` (per `config/secrets.development.shopify.yml` schema).
2. Attacker knows `attacker-org`'s `webhook_secret` (they configured it themselves when onboarding their own repos).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), validates the HMAC successfully against `attacker-org`'s real secret [1](#0-0) .
6. `create` dispatches the body to `PushHandler`, which resolves the target stack via `repository.full_name = "victim-org/victim-repo"` [6](#0-5)  and calls `stack.sync_github(expected_head_sha: 'attacker-chosen-sha')` on the victim's stack [9](#0-8) , despite the request never having been authorized by `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
