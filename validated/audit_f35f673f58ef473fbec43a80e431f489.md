### Title
Webhook signature verified against the wrong organization's secret, allowing cross-repository status/sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature with by reading `repository.owner.login` (or `organization.login`) from the *unverified* JSON body, while the handlers that actually write data (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve the target `Repository`/`Stack` using a *different* field of that same unverified body: `repository.full_name`. Nothing ties the organization used to authenticate the payload to the repository that is actually written to.

### Finding Description
`verify_signature` computes the signing organization purely from body content, before the signature has been validated: [1](#0-0) [2](#0-1) 

The resolved `github_app` for that organization is then used to verify the `X-Hub-Signature` against `Shipit.github(organization: repository_owner)`'s `webhook_secret`: [3](#0-2) 

Note that `verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured (`return true unless webhook_secret`). Shipit explicitly supports multiple GitHub Apps/organizations sharing one instance, each with its own independent secret configuration, as shown by the multi-app fixture: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, `Shipit::Webhooks.for_event(event)` dispatches to handlers that look up the *target* repository from a completely independent field of the same body — `repository.full_name` — not `repository.owner.login`: [6](#0-5) [7](#0-6) 

`PushHandler` uses this to trigger a sync against any stack of the resolved repository: [8](#0-7) 

`StatusHandler` uses `Commit.where(sha: params.sha)` — a purely global lookup with no repository scoping at all — to write CI status onto any commit matching that SHA anywhere in the instance: [9](#0-8) 

`CheckSuiteHandler` similarly resolves stacks via `repository.full_name` and schedules a check-run refresh: [10](#0-9) 

**The broken binding**: `organization_whose_secret_authenticated(request)` is expected to equal `owner_of_repository_written_to(request)`. In this engine, the first is derived from `repository.owner.login` and the second from `repository.full_name`, both attacker-supplied fields inside the same signed body. An attacker who controls (or knows the secret for) organization **B** — e.g., because org **B** has no `webhook_secret` configured (common/default, per `test/dummy/config/secrets_double_github_app.yml`, `webhook_secret: # nil`), or because they are a legitimate webhook sender for org **B** — can send a payload where:
- `repository.owner.login` = `B` (used only to pick which secret verifies the signature — trivially satisfied or unauthenticated),
- `repository.full_name` = `A/some-repo` (an entirely different organization's repository that the attacker does not control).

`verify_signature` authenticates the request as "from org B" (or passes with no secret configured for B), and then `PushHandler`/`StatusHandler`/`CheckSuiteHandler` act on stacks/commits belonging to org **A**'s repository, because those handlers never re-check that `full_name`'s owner matches the org that was actually authenticated.

### Impact Explanation
This lets a party without any credential for organization A's repository:
- Force a `GithubSyncJob`/status refresh cycle against another org's stack (`PushHandler`), and
- Forge arbitrary commit statuses via `StatusHandler#process`, which has no repository scoping whatsoever (`Commit.where(sha: params.sha)` matches by SHA across the entire instance).

Forged commit statuses directly feed Shipit's deploy-gating logic (statuses determine whether a commit is "safe" to deploy). Writing a passing/forced status onto a commit belonging to a stack the attacker does not control, using credentials/authentication belonging to an unrelated organization, is a cross-repository write that can influence an unauthorized deploy decision on that stack — matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (a) the instance to serve more than one GitHub organization/app (an explicitly supported and documented configuration, see `test/dummy/config/secrets_double_github_app.yml`), and (b) at least one org configured without a `webhook_secret` (the default/no-secret case is explicitly handled and treated as "verified"), or possession of a webhook secret for any one org on the instance. Given multi-tenant Shipit deployments and the common practice of omitting `webhook_secret` for internal/low-risk apps, this is realistically reachable without needing org A's own secret.

### Recommendation
Bind the authenticated organization to the repository actually acted upon: after `verify_signature` succeeds, re-derive `repository.owner.login` from the body and assert it equals the owner encoded in `repository.full_name` before dispatching to any handler; reject the request otherwise. Additionally, scope `StatusHandler#process` (and any other handler using a global lookup) by the verified repository/organization rather than a bare `Commit.where(sha:)` lookup, so no accounting/authorization determination is made from unauthenticated or cross-organization data.

### Proof of Concept
1. Configure Shipit with two orgs, `A` (has `webhook_secret: s3cr3t`) and `B` (no `webhook_secret` configured), as in `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "B" },
    "full_name": "A/target-repo"
  }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "B").verify_webhook_signature` returns `true` unconditionally (`webhook_secret` is `nil` for `B`) — see `lib/shipit/github_app.rb:76-83`.
3. `verify_signature` passes (org "B" authenticated), but `PushHandler#stacks` resolves via `repository.full_name`, i.e. `Repository.from_github_repo_name("A/target-repo")` — org A's repository — and triggers `stack.sync_github` on it, per `app/models/shipit/webhooks/handlers/handler.rb:32-38` and `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`.
4. Similarly, a `status` event with an org-B-authenticated body but a `sha` belonging to a commit in org A's stack will write a forged `Status` via `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, with no repository ownership check at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
