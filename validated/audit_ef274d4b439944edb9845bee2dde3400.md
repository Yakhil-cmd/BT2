### Title
Oracle staleness/failure causes hard revert with no fallback, blocking liquidation of under-collateralized positions and forcing bad-debt socialization onto lenders - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-resolve` in `v0-4-market.clar` hard-reverts (via `try!`/`unwrap!`) whenever a Pyth/DIA feed call fails or a price is stale/out-of-confidence, and there is no fallback oracle mechanism at all in Zest. `get-assets`, which is called from `borrow`, `withdraw`, and `liquidate` via `get-notional-evaluation`, wraps `price-multi-resolve` in `unwrap-panic`, so a single failing/stale price for any asset that participates in a position's collateral mask aborts the entire operation, including `liquidate`. This is the same bug class as the ParaSpace report (oracle outage → revert instead of fallback → liquidation fails), but here it is broader because there is no fallback path whatsoever, and a single stale feed can block liquidation for every position that includes that asset.

### Finding Description
`price-resolve` propagates any failure straight into a revert: [1](#0-0) 

`resolve-pyth`/`resolve-dia` themselves `unwrap!` on oracle call failures with `ERR-ORACLE-PYTH`/`ERR-ORACLE-DIA`: [2](#0-1) 

`get-assets`, used to build the notional valuation of a borrower's whole position, calls `unwrap-panic` on `price-multi-resolve`: [3](#0-2) 

`liquidate` calls `get-assets`/`get-notional-evaluation` before it can compute `total-collateral-usd`/`total-debt-usd`, the LTV, and the liquidation parameters: [4](#0-3) 

Additionally, for a disabled-collateral asset being seized during liquidation, `process-collateral-asset` resolves its price with `unwrap-panic (price-resolve oracle-data)`, again a hard panic rather than a recoverable error: [5](#0-4) 

Unlike ParaSpace's `ParaSpaceOracle`, Zest's market contract has no fallback price source at all - there is no try/catch or secondary oracle to fall back to when `resolve-pyth`/`resolve-dia`/the staleness check fails. Any of the following, none of which require attacker privilege, will cause `price-resolve` to revert for the affected asset:
- Pyth/DIA feeder outage or disagreement causing the price to exceed the asset's `max-staleness` (`oracle-timestamp-fresh`, docs/oracle.md:257-269, mirrored at [6](#0-5) ).
- Confidence-interval check failing (`check-confidence`, [7](#0-6) ).
- The underlying storage contract read call itself reverting.

Because `get-assets` evaluates every asset in the *enabled* collateral/debt mask for a position (`mask-to-list-collateral`/`get-status-multi`), a single stale/failing feed for one asset (e.g., USDH via DIA) blocks `liquidate`, `borrow`, and `withdraw` for **every** position whose mask includes that asset - not just the caller who triggers the transaction.

### Impact Explanation
When a feeder outage or disagreement makes one asset's price stale/unavailable, `liquidate()` reverts for all borrowers holding that asset as collateral or debt, even though their positions may be severely under-collateralized. During this window:
- Under-collateralized positions cannot be liquidated by anyone, letting bad debt grow unchecked as the borrower's collateral value continues to fall (e.g., in a volatile market) or interest accrues on debt.
- Once the feed recovers, the position may already have insufficient collateral to fully cover debt, and the shortfall is socialized across all lenders/suppliers via the protocol's bad-debt socialization path (`no-collateral-left`/bad-debt handling seen later in `liquidate`), directly harming depositors who had no part in causing or benefiting from the outage.

This is a harm from one unprivileged party (any borrower whose position happens to include the stale asset, or simply market conditions) onto another (all lenders sharing the pool, via socialized bad debt), satisfying the "socialization charged to all suppliers" and "position made unevaluable by a third party" criteria. The impact falls under **temporary freezing of funds** (liquidation blocked during outage) with a risk of escalating into **protocol insolvency** if bad debt grows large enough before the feed recovers, matching the Critical/High impact classes.

### Likelihood Explanation
Feeder outages and Pyth/DIA disagreement are not hypothetical - the report explicitly cites this as a real operational risk (six-hour default staleness windows in the original protocol; Zest's own asset registration requires `max-staleness > 0` and documents that volatile assets may use windows as short as 60 seconds, docs/oracle.md:271-275). No attacker action or privilege is needed; the trigger is purely an oracle-availability condition external to any single user, and the resulting revert path is deterministic given the code (`unwrap!`/`unwrap-panic` on any oracle failure), making the DoS on liquidation highly likely to occur during real-world oracle disruptions.

### Recommendation
Introduce a fallback oracle path (or graceful degraded-liquidation mode) analogous to what the ParaSpace report recommends: wrap `resolve-pyth`/`resolve-dia` calls in `liquidate`'s and `get-assets`'s price resolution with recoverable error handling (already partially done via `unwrap!`/`ERR-DISABLED-COLLATERAL-PRICE-FAILED` in `collateral-remove`) consistently across all price-resolution call sites, including `process-collateral-asset`, `process-debt-asset`, and `get-assets`. Where a price cannot be resolved, allow liquidation to proceed using only the assets whose prices are resolvable (excluding the unresolvable asset from that liquidation attempt) rather than reverting the entire operation, or provide an emergency fallback price source that the DAO can activate without requiring a full asset registry change.

### Proof of Concept
1. Register asset `USDH` (or any Pyth/DIA-backed asset) with `max-staleness` per current defaults, per `docs/oracle.md:241-275`.
2. Multiple borrowers open positions using `USDH` as collateral or debt within their egroup mask.
3. The DIA feeder for `USDH` stops updating (real-world feeder outage) beyond `max-staleness`, or Pyth price staleness exceeds the configured window for another asset in the same masks.
4. Any of these borrowers' collateral value drops (or debt accrues) such that their position becomes liquidatable.
5. A liquidator calls `liquidate(...)`. Internally this calls `get-liquidation-position` → `get-assets` → `price-multi-resolve` → `price-resolve` for `USDH`, which fails staleness check `oracle-timestamp-fresh` and returns `(err ERR-ORACLE-INVARIANT)`, propagated by `try!` up to `unwrap-panic` in `get-assets` ( [3](#0-2) ), causing the whole `liquidate` call to panic/revert.
6. This happens for every position sharing that asset in its mask, for as long as the feeder outage persists, during which under-collateralized debt continues to accrue - ultimately increasing bad debt socialized to lenders once liquidation finally succeeds.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
