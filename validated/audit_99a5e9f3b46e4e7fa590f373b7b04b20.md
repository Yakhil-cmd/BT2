### Title
Stop-hook security review baseline advances past files dropped by diff prioritization, permanently evading review - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin's `Stop` hook reviews only a git diff against a session `baseline_sha` "checkpoint" that is advanced after each review fire. When a turn produces more changed files than `MAX_DIFF_FILES`, the hook prioritizes and reviews only a subset, silently dropping the rest — yet it still advances `baseline_sha` to the *current* working-tree snapshot. The dropped files' changes are therefore folded into the new baseline without ever being reviewed, permanently escaping detection, exactly like the Dispenser `retain()` bug where `mapLastClaimedStakingEpochs` is advanced past epochs whose incentive weight was never actually checkpointed.

### Finding Description
In `handle_stop_hook` (`plugins/security-guidance/hooks/security_reminder_hook.py`), when the diff contains more files than `MAX_DIFF_FILES`, `_prioritize_diff_files` truncates `diff_files` to the top-risk subset and reports the drop count in `_stop_dropped`: [1](#0-0) 

Only the truncated `diff_files` set is sent to `analyze_code_security`: [2](#0-1) 

If any findings surface from the reviewed subset (`concrete_guidance` non-empty), the hook then calls `capture_git_baseline(cwd)` — which snapshots the *entire current working tree*, not just the reviewed files — and unconditionally writes it as the new `baseline_sha` under lock: [3](#0-2) 

Because `content_base = baseline_sha or diff_base` drives all future diffs (`get_git_diff`), any subsequent Stop-hook fire will diff against this new baseline, meaning the dropped-but-unreviewed files' changes are no longer part of any future diff unless those exact files are touched again — and even then only the *new* delta on top of the now-baked-in unreviewed content is visible. The unreviewed content itself is permanently excluded from review, analogous to the Dispenser `retain()` function writing `mapLastClaimedStakingEpochs[retainerHash] = lastClaimedEpoch` for epochs whose nominee weight was never checkpointed, permanently forfeiting incentives for those epochs.

This mirrors the report's root cause precisely: a "checkpoint" marker (there, `mapLastClaimedStakingEpochs`; here, `baseline_sha`) is advanced to cover a range of items, while the actual per-item processing (there, vote-weight checkpointing; here, LLM security review) was only partially performed over that range, and the un-processed remainder can never be recovered.

### Impact Explanation
An attacker-influenced session (e.g., via prompt injection causing Claude to touch many files in a single turn, or a large automated refactor) can cause `_prioritize_diff_files` to drop the file(s) actually carrying an injected vulnerability (since prioritization is heuristic, based on path risk tokens) while other, higher-priority files still trigger findings. That trigger advances `baseline_sha` past the vulnerable, unreviewed file's changes, permanently removing them from the security-guidance Stop-hook's future diff scope. This is a direct bypass of a security-relevant trust boundary (the automated code-security review gate), allowing vulnerable/malicious code changes to silently evade the tool's own detection mechanism for the remainder of the session.

### Likelihood Explanation
Requires a turn with more changed files than `MAX_DIFF_FILES` where at least one reviewed (higher-priority) file surfaces a finding while a lower-priority dropped file carries the actual injected vulnerability. This is plausible in large refactors, bulk-generated code, or an adversarial prompt deliberately spreading a malicious edit across many low-"risk-token" paths alongside a decoy finding-triggering file, making the likelihood moderate rather than trivial.

### Recommendation
Only advance `baseline_sha` to cover the files that were actually reviewed, not the full working-tree snapshot. Concretely: after review, capture a baseline that reflects "reviewed-files-at-HEAD plus not-yet-reviewed-files-at-old-baseline" (e.g., persist a per-file reviewed-SHA map, or exclude `_stop_dropped` paths from the new baseline capture and keep their pre-review baseline pinned until they are actually reviewed), mirroring the code-423n4 fix pattern of ensuring the checkpoint operation actually covers the state it's about to mark as processed.

### Proof of Concept
1. In one turn, have Claude/a subagent modify > `MAX_DIFF_FILES` files, including `src/vendor/util_helper.py` (low security-risk path score, contains an injected backdoor) and `auth/login.py` (high-risk path score, contains an unrelated benign-but-flaggable pattern).
2. `handle_stop_hook` runs: `_prioritize_diff_files` keeps `auth/login.py` in the reviewed set and drops `src/vendor/util_helper.py` (`_stop_dropped` incremented). [4](#0-3) 
3. `analyze_code_security` flags `auth/login.py`, so `concrete_guidance` is non-empty.
4. `capture_git_baseline(cwd)` snapshots the whole working tree (including the still-uncommitted backdoor in `util_helper.py`) and this becomes the new `baseline_sha`. [3](#0-2) 
5. All future Stop-hook diffs are taken against this new baseline; the backdoor content in `util_helper.py` is now baked into the baseline and never appears in any future diff for review, permanently evading the security-guidance plugin's detection.
