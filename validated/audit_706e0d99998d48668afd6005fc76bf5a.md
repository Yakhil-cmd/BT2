### Title
Cross-organization webhook forgery — signature verified against `repository.owner.login` while handlers act on unchecked `repository.full_name` / arbitrary `sha` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify a payload's HMAC against based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, but the event handlers that subsequently act on the same payload key off a different, independently-controlled field (`repository.full_name`, or nothing at all in the case of commit status). Nothing enforces that the organization used to select/verify the signature actually corresponds to the repository/commit the handler mutates.

### Finding Description
Shipit supports multi-tenant GitHub configuration: `Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization [1](#0-0) . The webhook signature check picks the org purely from payload content:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

After that check passes, `create` re-parses the same raw body and dispatches it, unmodified, to all registered handlers for the event: [3](#0-2) 

Handlers determine the *target* repository from a **different** field, `repository.full_name`, via `Handler#repository_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Nothing enforces `repository.full_name.split('/').first == repository.owner.login`. `PushHandler` uses this `stacks` scope to trigger `stack.sync_github` [5](#0-4) , and the pull-request handlers use `Repository.from_github_repo_name(params.repository.full_name)` the same way [6](#0-5) .

Worse, `StatusHandler` performs **no repository scoping at all** — it looks up commits globally by SHA across the entire Shipit install and writes a GitHub-sourced status onto them:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

Additionally, `GitHubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` for an organization as automatically verified: `return true unless webhook_secret` [8](#0-7) , which is a common configuration state for lightly-configured orgs (see `webhook_secret: # nil` in the sample secrets file) [9](#0-8) .

**Binding broken (equality that should hold but doesn't):**
`organization authenticated via HMAC (repository.owner.login)` ⇏ `repository/commit actually mutated (repository.full_name / commit.sha)`.

### Impact Explanation
In a multi-org Shipit deployment, an attacker who can produce a validly-signed webhook for **any one** configured organization (e.g., an org whose `webhook_secret` is unset/blank, or one where they control the GitHub App/secret) can craft a JSON body whose `repository.owner.login` matches that org (to pass signature verification) while `repository.full_name` (or `sha`, for status events) targets a completely unrelated, victim repository/stack that they have no access to. This allows:
- Forcing `sync_github` on arbitrary tracked stacks (push events) via `PushHandler`.
- Forging/overwriting commit CI statuses for **any** commit tracked by the entire Shipit instance via `StatusHandler`, which has no repository check whatsoever. Since CI-required statuses (`ci.require`) gate whether a commit is deployable, and continuous deployment automatically ships deployable commits, an attacker can mark an arbitrary malicious commit as passing required CI and cause Shipit to autonomously ship it — an **unauthorized deploy**, which is explicitly listed as a Critical-severity outcome.
- Manipulating pull-request-based review-stack lifecycle (archive/unarchive/create) for repositories outside the authenticated org.

This mirrors the referenced Sherlock report's root cause pattern: a value used to satisfy one invariant (signature verification against an org secret) is silently reused/trusted for a distinct, unguarded purpose (selecting the mutated resource), breaking an implicit equality the code never checks.

### Likelihood Explanation
Requires the attacker to obtain a valid signature for at least one configured organization — either because that organization's `webhook_secret` is blank (a documented default/no-op state that `verify_webhook_signature` explicitly permits) or because the attacker controls a legitimately configured, lower-trust org in a multi-tenant Shipit instance. Given Shipit's explicit multi-org support and the sample configs showing organizations with no secret set, this is a realistic operational configuration, not a purely theoretical one. No repository write access, GitHub App private key, or Shipit session/API token is needed — only knowledge (or absence) of one org's webhook secret, which is a materially weaker credential than the ones excluded by scope rules (`GITHUB_TOKEN`, `api_clients_secret`, GitHub App private key, ApiClient token, Shipit session).

### Recommendation
- In `WebhooksController#repository_owner`, derive the verification key strictly from `repository.full_name`'s owner segment (or otherwise ensure it is the same value the handlers use to select the target repository), so signature verification and target-resource resolution are bound to the same field.
- In `Shipit::Webhooks::Handlers::Handler` (and specifically `StatusHandler`), scope lookups by the repository verified during signature checking rather than trusting `full_name`/`sha` alone; reject payloads where the claimed owner does not match the repository actually resolved.
- Reconsider defaulting `verify_webhook_signature` to `true` when `webhook_secret` is blank, or require an explicit opt-in flag for "unsigned webhooks allowed" per organization.

### Proof of Concept
1. Shipit configured with two GitHub orgs: `orgA` (attacker-controlled or with `webhook_secret` blank) and `orgB` (victim, tracked stack `orgB/victim-repo`, with `ci.require: ["ci/tests"]` and `continuous_deployment: true`).
2. Attacker computes/produces a valid `X-Hub-Signature` for `orgA` (trivial if `orgA.webhook_secret` is blank, since `verify_webhook_signature` returns `true` unconditionally in that case).
3. Attacker POSTs to `/github/webhooks` with `X-Github-Event: status`, body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sha": "<sha of malicious/unreviewed commit in orgB/victim-repo>",
  "state": "success",
  "context": "ci/tests"
}
```
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and passes, since the signature matches `orgA`'s (blank) secret.
5. `StatusHandler#process` finds the commit by `sha` alone (no org check) and calls `commit.create_status_from_github!(params)`, marking the required `ci/tests` context as `success` for a commit in `orgB/victim-repo` that the attacker never had CI or repository access to.
6. If `orgB/victim-repo`'s stack has continuous deployment enabled, Shipit's continuous delivery job now considers the commit deployable and ships it — an unauthorized deploy triggered without any Shipit session, ApiClient token, or `orgB` credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
