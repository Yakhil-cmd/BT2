### Title
Webhook signature verification binds to the payload's `repository.owner`/`organization.login` while handlers act on the independently-controlled `repository.full_name`, allowing cross-organization webhook forgery when any configured org omits a `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController` is a public, unauthenticated endpoint (no session, no `ApiClient` token) whose only protection is an HMAC signature check. The signature check selects *which* GitHub App/secret to verify against using one payload field (`repository.owner.login`, falling back to `organization.login`), while every event handler resolves the actual `Stack`/`Repository`/`Team` to mutate using a *different*, independently-controlled payload field (`repository.full_name`, or `organization.login`/`team` for membership events). These two lookups are never cross-checked against each other.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-suppliable payload content: [1](#0-0) [2](#0-1) 

The signature verifier itself bypasses HMAC validation entirely whenever the selected organization's config has no `webhook_secret` set (an optional config field, as shown by tests exercising the blank-secret path): [3](#0-2) [4](#0-3) 

Meanwhile, downstream handlers never re-check which organization was actually authenticated — `Handler#stacks` resolves the target purely from `payload.dig('repository', 'full_name')`: [5](#0-4) 

and `MembershipHandler#process` resolves/creates a `Team` and adds an arbitrary `member.login` based on payload fields with no relation to the verified signature at all: [6](#0-5) 

**Binding broken:** `organization authenticated (repository_owner used to pick the HMAC secret)` ≠ `repository/team actually written (repository.full_name / team.organization used by handlers)`.

Before the attack: signature validity is meant to imply "this event genuinely originated from GitHub for this organization's resources."
After: an attacker crafts a POST whose `repository.owner.login`/`organization.login` names *any* Shipit-configured organization that happens to have no `webhook_secret` set, while placing a *different*, real target (`repository.full_name`, or a `team`/`member` object) belonging to any other organization tracked by this Shipit instance. `verify_signature` passes unconditionally (secret-less org), and the handler then acts on the unrelated, attacker-chosen target.

### Impact Explanation
This crosses directly into the rules' explicit High-impact bucket: "escalation into `Shipit.github_teams` authorization." Via the `membership` event, `MembershipHandler` creates/looks up a `Team` by the attacker-supplied `team.id`/`organization.login` and adds an attacker-supplied `member.login` (which can be the attacker's own GitHub login) to it, with `Membership` created as a side effect: [7](#0-6) 
If that team is one of `Shipit.github_teams` used for authorization checks, this is an unauthenticated escalation into the app's authorization model: [8](#0-7) 

Additionally, `push`/`status` handlers can be forged to trigger `sync_github` or fabricate commit statuses on stacks/commits belonging to organizations other than the one whose (missing) secret was used to pass verification: [9](#0-8) [10](#0-9) 

### Likelihood Explanation
This requires only that at least one GitHub App organization configured in the Shipit instance has no `webhook_secret` set — an allowed, non-error configuration state (`@webhook_secret = @config[:webhook_secret].presence`) — and that the instance tracks more than one organization/repository. Given the endpoint is intentionally public and unauthenticated by design (to receive real GitHub webhooks), and no credential, session, or repository access is required from the attacker, likelihood is realistic wherever such a configuration mismatch exists.

### Recommendation
- After selecting the signing organization, re-derive the target repository/team strictly from a field bound to that same verified organization, and reject the event if `repository.full_name`'s owner (or `team.organization`) does not match the organization whose secret validated the signature.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; instead require an explicit "authentication disabled" configuration flag per organization, mirroring `Shipit.disable_api_authentication`.
- Consider requiring `webhook_secret` to be present for every configured organization, failing fast at boot/config-load time if any organization omits it.

### Proof of Concept
1. Shipit is configured with two organizations, `org-with-secret` (has `webhook_secret`) and `org-no-secret` (omits `webhook_secret`), both tracked by the same Shipit instance.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "org-no-secret" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `verify_signature` calls `Shipit.github(organization: 'org-no-secret')`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank for that org [3](#0-2) .
4. `MembershipHandler#process` runs, creating/finding team id `999` and adding `attacker-github-login` to it [7](#0-6) . If team `999` corresponds to a team listed in `Shipit.github_teams`, the attacker's user is now authorized in the application without ever having a real GitHub session or team membership.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
