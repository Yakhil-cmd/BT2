### Title
Webhook signature verification authenticates the wrong organization relative to the repository the payload writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on one payload field (`repository.owner.login`), while every event handler resolves the `Repository`/`Stack` to mutate based on a *different* payload field (`repository.full_name`). Because these two fields are never cross-checked against each other, a payload can be crafted so that the signature is verified against organization A's secret while the mutating side effects are applied to a stack belonging to organization B's repository.

### Finding Description
The signature check derives the signing organization purely from the payload itself, not from any pre-established binding to the stack being modified: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The verified event is then dispatched to handlers such as `StatusHandler` and `PushHandler`, whose base class resolves the target `Repository`/`Stack` from a *separate* field of the same JSON body: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the repository that gets acted on) are two independent, attacker-controlled JSON fields inside the same raw body. Nothing enforces that `full_name` starts with `owner.login`. If an attacker controls (or has legitimate access to) a GitHub organization/App installation that Shipit is configured for — and therefore knows that org's `webhook_secret` (e.g. because they can see/trigger real deliveries for their own org) — they can HMAC-sign an arbitrary payload with that secret while setting `repository.full_name` to point at a completely different, victim-tracked repository/stack. `verify_webhook_signature` will pass because it only checks that the signature matches the secret for `repository_owner`, and the raw body containing the forged `full_name` is exactly what was signed.

This is the same class of bug as the audit finding: a value is used as if it were validated/bound to the same entity as another value it is compared/paired against, but the code actually inspects the wrong side of the pair (there, `btcAssetAmount == 0` acted on the zero-amount asset instead of the non-zero one; here, the org used for authentication is not required to match the org that owns the repository being mutated).

### Impact Explanation
The `StatusHandler` writes forged commit statuses for any commit sha it is given, regardless of which org authenticated: [4](#0-3) 

Commit statuses drive Shipit's CI-gating and continuous-deployment logic (`required_statuses`/`deployable?` in `app/models/shipit/stack.rb` and `app/models/shipit/commit.rb`). An attacker who only controls a foreign, unrelated GitHub organization/App installation configured in the same Shipit instance can forge a "success" status for a required CI context on a commit belonging to a repository they do not own. If that stack has `continuous_deployment` enabled, this can cause Shipit to consider a commit deployable/ready when it never actually passed CI, resulting in an unauthorized deploy trigger against a repository the attacker does not control — crossing the "unauthorized deploy" and "cross-repository writes" impact bar.

`PushHandler` similarly lets the attacker trigger `stack.sync_github` for the victim's stack using a forged event authenticated under an unrelated org's secret.

### Likelihood Explanation
Requires: (1) Shipit configured with more than one GitHub organization/App (a documented multi-org deployment scenario), and (2) attacker control of the webhook secret for at least one of those configured organizations (e.g., as an admin/member of that org's GitHub App installation) without any privilege over the victim repository/org. This is a plausible deployment topology for a shared Shipit instance serving multiple orgs, and requires no Shipit session, API token, or write access to the victim repository — only knowledge of a webhook secret for a different org registered in the same instance.

### Recommendation
Bind signature verification to the same repository ownership the handlers act on: derive the verifying organization from the same, single field used by the handlers (`repository.full_name`'s owner segment), and additionally, in `Webhooks::Handlers::Handler`, verify that the resolved `Repository`'s configured GitHub owner matches `repository_owner`/`organization.login` from the payload before permitting handlers to run. Reject the webhook if the two do not match.

### Proof of Concept
1. Shipit is configured with `github_apps` for both `org-a` (attacker-controlled installation) and `org-b` (victim, tracks repo `org-b/victim-repo`).
2. Attacker crafts a JSON payload for a `status` event:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_for_org_a, raw_body)` using the secret they know for `org-a`.
4. POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`), verification succeeds because the attacker signed with `org-a`'s secret.
6. `StatusHandler#process` resolves the target commit via `Commit.where(sha: ...)`, which belongs to `org-b/victim-repo`, and writes a forged `success` status for `ci/required-check`, satisfying Shipit's deploy gating for a repository the attacker never had access to.
