### Title
`StatusHandler#process` accepts `params.branches` but never uses it for any scoping - zero repository or branch validation before writing commit statuses - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler` declares an `accepts :branches, Array do requires :name, String end` schema entry via `ExplicitParameters`, but `#process` never references `params.branches` anywhere in its body. `#process` looks up commits purely by `Commit.where(sha: params.sha)` with no branch, repository, or stack-derived filter of any kind, confirming that branch information supplied in the webhook payload has no bearing on which `Commit` rows get mutated.

### Finding Description
The binding under test: `params.branches` (an array of `{name: ...}` hashes accepted by the schema) should be checked against `commit.stack`'s tracked `branch` before `Commit#create_status_from_github!` is invoked. Actual code: [1](#0-0) 

```ruby
class StatusHandler < Handler
  params do
    requires :sha, String
    requires :state, String
    accepts :description, String
    accepts :target_url, String
    accepts :context, String
    accepts :created_at, String

    accepts :branches, Array do
      requires :name, String
    end
  end

  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

`params.branches` is parsed and validated (must be an array of objects with a `name` String) by `ExplicitParameters`, but it is never read inside `#process`. The only inputs actually used are `params.sha` (to find matching `Commit` rows, globally, with no `stack_id`/repository filter) and `params` itself (passed wholesale into `create_status_from_github!`, which internally uses `state`, `target_url`, `description`, `context`, `created_at`).

Contrast with `CheckSuiteHandler`, which does use its equivalent field to scope the write: [2](#0-1) 

and `PushHandler`, which scopes by `branch` derived from `params.ref`: [3](#0-2) 

`StatusHandler` has no analogous scoping. The base `Handler` class exposes a `stacks` helper that scopes by `repository_name` from the payload: [4](#0-3) 

but `StatusHandler#process` never calls `stacks` — it queries `Commit` directly and globally by `sha`.

Guard evaluation:
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies the payload was signed by the GitHub App keyed on `repository_owner`/`organization`. It says nothing about whether the `sha` or `branches` inside the payload correspond to that same organization's repository, and it does not participate in the branch/commit-scoping decision at all.
- `drop_unhandled_event` only checks that a handler exists for the event name; it does not inspect payload contents.
- `ExplicitParameters` only validates shape/types (`branches` must be an array of `{name: String}`); it performs no semantic authorization or scoping and confirms nothing is checked against it downstream.
- There is no `stacks`, `branch`, or `repository`-based `where` clause anywhere in `StatusHandler#process`.

Given the equality claimed by the binding — "`params.branches`'s `name` should equal (or be checked against) `commit.stack.branch` before mutation" — the trace shows this equality is never evaluated: the left side (`params.branches`) is read into `params` and then dropped; the right side (`commit.stack.branch`) is never consulted in `#process`. Both sides remain unconnected before and after, confirming the divergence.

### Impact Explanation
Any `status` webhook whose payload passes signature verification for *some* organization will apply `create_status_from_github!` to every `Commit` row in the entire Shipit instance whose `sha` matches `params.sha`, regardless of `branches`, regardless of the originating repository, and regardless of which stack/branch that commit actually belongs to. This can flip the CI/status state (`success`/`error`/`pending`, `target_url`, `description`, `context`) of an arbitrary commit belonging to a completely different stack or repository than the one attributed by `repository_owner`, which can influence downstream deployability/merge-queue decisions (`Commit#create_status_from_github!` → `add_status` → `stack.schedule_merges`). This matches "a payload for one repository mutating another's stack/commit" (Critical) since `branches`, which could have served as the scoping mechanism, is fully unused, and no other scoping exists in this handler.

### Likelihood Explanation
Precondition is that the attacker can get a validly-signed `status` webhook delivered for *any* organization Shipit tracks (a normal, low-cost precondition for a user with commit/PR access to an org-owned repo with the GitHub App/webhook installed, as assumed by the threat model). Once delivered, the `sha` field is fully attacker-controlled and requires no knowledge of branch names, secrets, or the target repository's configuration — only knowledge of a target `sha` value that exists as a `Commit` row somewhere in the Shipit database (e.g. by observing shared/public commit SHAs, which are guessable/enumerable across forks and repos sharing history). Repeatable indefinitely.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the stack's tracked branch and repository, e.g. resolve `stacks` from the payload's `repository` (as `Handler#stacks` already provides), and require that the matched commit's `stack` be among those stacks, optionally further filtering by `params.branches.map(&:name)` against `stack.branch`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "branches param has no effect on which commits are mutated" do
  commit = shipit_commits(:first) # belongs to some stack/branch, e.g. "master"

  payload_with_wrong_branch = {
    'sha' => commit.sha,
    'state' => 'success',
    'branches' => [{ 'name' => 'totally-unrelated-branch-that-does-not-track-this-commit' }]
  }

  assert_difference '-> { commit.statuses.count }', 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload_with_wrong_branch)
  end

  # Binding under test: params.branches[0].name == commit.stack.branch
  # LHS:
  branches_name = payload_with_wrong_branch['branches'][0]['name']
  # RHS:
  tracked_branch = commit.stack.branch
  refute_equal branches_name, tracked_branch # divergence: mismatched branch, yet status was still written

  status = commit.statuses.last
  assert_equal 'success', status.state # mutation happened regardless of branches mismatch
end
```
