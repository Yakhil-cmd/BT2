### Title
Arbiter contract sharing leaks both parties' permanent pairing secrets to wallet cosigners - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js` stores the full permanent pairing code of both the local user (`my_pairing_code`) and the counterparty (`peer_pairing_code`) as plain columns of the `wallet_arbiter_contracts` row. When a contract becomes `accepted`, `shareContractToCosigners()` fetches this full row via `getByHash()` (a `SELECT *`) and forwards it verbatim to every device that co-signs the local user's address, without stripping the pairing-code fields, even though those cosigner devices are not supposed to be able to pair with the counterparty's device directly. This mirrors CVE-2020-1940: an additional sensitive attribute (there, a changed password; here, the peer's/own permanent pairing secret) is carried inside an object that is passed on to another consumer without ever being removed.

### Finding Description
`respond()` generates a permanent pairing code containing the raw pairing secret and stores it on the contract: [1](#0-0) 

That whole contract row — including `my_pairing_code` and `peer_pairing_code`, both of the form `pubkey@hub#pairing_secret` — is then broadcast unmodified to every cosigner of the local user's address: [2](#0-1) 

`getByHash()` performs a `SELECT *`, so nothing is filtered out of `objContract` before it is handed to `sendMessageToDevice`: [3](#0-2) 

Notably, the code elsewhere shows the developers are aware that certain fields must be stripped before being sent to a different role: when creating the contract, `cosigners` is explicitly deleted from the copy sent to the peer: [4](#0-3) 

but the symmetric redaction (stripping `my_pairing_code`/`peer_pairing_code` before sending to cosigners) is missing in `shareContractToCosigners()` and in the equivalent call from `createSharedAddressAndPostUnit()`: [5](#0-4) 

Once a cosigner device receives the counterparty's permanent pairing secret, it can independently pair with that device (`handlePairingMessage`), because permanent pairing secrets accept multiple peers and are not one-time/invalidated: [6](#0-5) 

Becoming a paired correspondent of the peer's device grants the cosigner privileges that unpaired/unknown devices do not have — e.g. it is no longer restricted to the `arrSubjectsAllowedFromNoncorrespondents` whitelist when receiving hub-relayed messages: [7](#0-6) 

and it becomes eligible to receive privately-forwarded payment chains and shared-address bookkeeping that assume a trusted correspondent relationship (e.g. `forwardPrivateChainsToOtherMembersOfSharedAddresses`, `handleMessageFromHub`'s `private_payments` and `signing_request` handling).

### Impact Explanation
A wallet cosigner is only supposed to co-sign transactions on the shared/multisig address; it is not supposed to be able to unilaterally pair with, and thereby directly message and be treated as a known correspondent of, the counterparty's device. Leaking the counterparty's permanent pairing secret to the cosigner (and, symmetrically, leaking the local user's own permanent pairing secret to any hostile cosigner added to a shared address the user is part of) lets that unintended party:
- pair as a correspondent of the peer without the peer's explicit consent/QR exchange,
- subsequently receive private payment chains or `signing_request`/`private_payments` messages addressed to that identity, and
- leverage the trusted-correspondent status to submit follow-on protocol messages that the peer's wallet processes with fewer checks than it would apply to a stranger,
which can be chained into private-payment/asset disclosure or manipulation of the multi-party arbiter-contract flow (e.g., interfering with `shared_address` derivation acknowledgements or contract-status updates that the local wallet blindly trusts from "cosigners").

### Likelihood Explanation
Any device configured as a cosigner on the local user's wallet address (a normal, low-privilege setup for shared/multisig addresses) automatically receives this leak the moment the local user accepts or shares an arbiter contract — no additional action or exploit is required from the cosigner; they merely have to be included as a wallet cosigner, which is routine.

### Recommendation
Before calling `device.sendMessageToDevice(device_address, "arbiter_contract_shared", objContract)` in `shareContractToCosigners()` (and in `createSharedAddressAndPostUnit()`), clone the contract object and delete `my_pairing_code` and `peer_pairing_code` (and any other pairing-secret-bearing fields) the same way `cosigners` is stripped for the peer-facing message in `createAndSend()`. Cosigners do not need either party's raw pairing secret to perform their signing role.

### Proof of Concept
1. Alice creates an arbiter contract with Bob and adds Carol as a cosigner on her payer address (a normal multisig setup).
2. Bob accepts the contract; `respond()` sets `peer_pairing_code` on Alice's stored contract to `bob_pubkey@bob_hub#bob_pairing_secret`, and `shareContractToCosigners()` is invoked.
3. Alice's wallet sends the full `objContract` — including `peer_pairing_code` — to Carol via `arbiter_contract_shared`.
4. Carol extracts `bob_pairing_secret` from the received message and sends Bob a `pairing` device message using that secret (`sendPairingMessage`).
5. Bob's `handlePairingMessage()` accepts the pairing secret (still valid/permanent) and adds Carol as a confirmed correspondent, even though Bob never intended to pair with Carol.

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
