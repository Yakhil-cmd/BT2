### Title
Webhook signature is verified against the organization named in the (unsigned-at-verification-time) JSON body, while event handlers act on repository/commit data from that same untrusted body with no cross-check to the verifying organization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's GitHub App/webhook secret* to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON payload, before the signature has been checked. `StatusHandler#process` then looks up the target `Commit` purely by `sha` (`Commit.where(sha: params.sha)`) with **no repository/organization scoping at all**. This breaks the binding "organization that authenticated == repository that is written": an attacker who legitimately controls one organization/repo integrated with the Shipit instance (and therefore legitimately knows that org's webhook secret) can sign a payload that verifies for their own org, while the `sha` field references a commit belonging to a completely different stack/repository (trivially true for forks, which share commit SHAs with upstream).

### Finding Description
Signature verification and target-resolution use two different fields of the same untrusted payload, and the field used for verification is never tied to the field used for writes: [1](#0-0) 

`repository_owner` is derived entirely from attacker-controlled JSON (no header, no route-bound value): [2](#0-1) 

Once `verify_signature` passes (because it matched *some* organization the attacker legitimately administers), the raw payload is dispatched to handlers un-modified: [3](#0-2) 

`StatusHandler` resolves the target purely by SHA, globally, with no repository/stack scoping to the `repository` object that was used for signature verification: [4](#0-3) 

By contrast, `Handler#stacks`/`Handler#repository_name` shows the codebase does have a notion of scoping events to a specific repository (`Repository.from_github_repo_name(repository_name)`), but `StatusHandler` does not use it: [5](#0-4) 

Concretely, the binding that should hold is:
`organization-that-signed(payload) == organization-owning(commit written by handler)`

but the code only enforces:
`organization-that-signed(payload) == payload["repository"]["owner"]["login"]` (trivially true, self-referential)

with **no** constraint that the `sha` being written actually belongs to a commit under that same organization/repository. Since Git commit SHAs are content-addressed and identical across a repository and any of its forks, an attacker who forks a public victim repository shares SHAs with the upstream history. If the attacker's fork/organization is also integrated with the same Shipit instance (a normal, permitted, unprivileged setup step - registering one's own repo/org with a self-service Shipit instance, not requiring any Shipit session, API token, or victim credentials), the attacker can send a correctly-signed `status` webhook (signed with their own legitimately-known webhook secret) whose `sha` matches a commit that also exists in the victim's stack history. `StatusHandler` will happily attach that status to the victim's `Commit` record.

### Impact Explanation
Commit CI statuses gate deployability in Shipit (`required_statuses`/`blocking_statuses`/`soft_failing_statuses` are read from `shipit.yml` and used to compute whether a commit is `deployable?`, which the `Deploy`/`Stack` flow relies on to permit a deploy). By forging a `success` status on a shared SHA that also exists in the victim stack (via a fork relationship), the attacker can flip a commit that would otherwise be blocked by CI into a deployable state on the *victim's* stack, without ever touching the victim's GitHub App, webhook secret, or Shipit credentials. This is a cross-organization write (a commit-status write for a repository the attacker's signing organization does not own) that can enable an unauthorized deploy of the victim's stack - matching the report's core defect class (a recalculation/verification step that omits a piece of prior state it should have been bound to, letting an unprivileged actor claim more trust than was granted).

### Likelihood Explanation
Requires only: (1) the target Shipit instance supports multiple GitHub App/organization configurations (documented, supported multi-tenant feature - see `Shipit.github(organization:)`), (2) the attacker owns/administers one such integrated organization or repo (a normal, unprivileged onboarding step, not a Shipit credential), and (3) a shared-SHA commit exists between the attacker's repo and the victim's stack - trivially achievable via forking a public victim repository, which is a routine, unprivileged GitHub action. No webhook secret theft, no Shipit session, and no API token of the victim are needed.

### Recommendation
Scope every webhook handler's lookups (especially `StatusHandler`, and any handler that writes based on `sha` alone) to the `Repository`/`Stack` derived from the *same organization that produced a valid signature*, not merely `Commit.where(sha:)` globally. Concretely: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` first, verify that repository's owner organization is the one whose secret validated the signature, and only then search for/create commits scoped to that repository's stacks - mirroring the `Handler#stacks` pattern that already exists but isn't applied in `StatusHandler`.

### Proof of Concept
1. Shipit instance is configured with multiple orgs in `secrets.github`, e.g. `AttackerOrg` (attacker-administered) and `VictimOrg` (target), each with its own `webhook_secret`.
2. Attacker forks `VictimOrg/app` into `AttackerOrg/app-fork`, inheriting shared commit SHAs with the upstream (e.g., SHA `abc123` exists in both histories, since Shipit only tracked/imported `abc123` into `VictimOrg`'s stack via its own sync).
3. Attacker sends a `status` webhook event to Shipit:
   - Header `X-Github-Event: status`
   - Header `X-Hub-Signature` = `sha1=` HMAC computed with `AttackerOrg`'s webhook secret (known to the attacker) over the exact raw body.
   - Body: `{"sha":"abc123","state":"success","context":"ci/required","repository":{"owner":{"login":"AttackerOrg"},"full_name":"AttackerOrg/app-fork"}}`
4. `WebhooksController#verify_signature` computes `repository_owner == "AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and the signature verifies successfully (attacker used their own valid secret).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: "abc123").each { |c| c.create_status_from_github!(params) }` - this matches the `Commit` row belonging to `VictimOrg`'s stack (because the SHA is shared), writing a forged `success` status onto it despite the signature never having been verified against `VictimOrg`'s secret.
6. If `ci/required` is in `VictimOrg`'s stack's `required_statuses`, the victim commit becomes `deployable?` due to the forged status, enabling an unauthorized deploy trigger by any user with deploy rights on the victim stack (or via continuous deployment), based entirely on attacker-forged CI data.

Note: I was unable to fully trace `Commit#create_status_from_github!` and the exact `deployable?`/CI-gating code path within the remaining tool budget to confirm the precise mechanics of how a forged status flips deployability end-to-end; this should be verified against `app/models/shipit/commit.rb` and `app/models/shipit/commit_checks.rb` (or equivalent) before remediation.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
