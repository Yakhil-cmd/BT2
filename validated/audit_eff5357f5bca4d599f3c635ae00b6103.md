### Title
Cross-organization webhook confusion: `repository_owner` selects the signature secret while `LabeledHandler`/`repository.full_name` selects the acted-upon stack, allowing a forged `pull_request` payload authenticated by one org's secret to archive/unarchive another org's review stack - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret`) to validate a webhook against using `repository_owner`, which falls back from `params.dig('repository','owner','login')` to `params.dig('organization','login')` when `repository` is omitted or lacks an `owner`. `LabeledHandler`, however, independently resolves the target stack purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`. Because these two fields are populated from unrelated, fully attacker-controlled parts of the JSON body, a webhook that is cryptographically valid for organization A's secret can still carry a `repository.full_name` pointing at organization B's stack, letting the handler archive/unarchive B's review stack using A's authentication.

### Finding Description
The broken binding is the implicit assumption:
`repository_owner (used in Shipit.github(organization: repository_owner) for HMAC verification) == owner(repository.full_name) (used by LabeledHandler#repository to select the acted-upon Repository)`

Trace:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to select the `GitHubApp` config: `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `Shipit.github` looks up a distinct per-organization config (with its own `webhook_secret`, `bot_login`, etc.) keyed by the `organization` argument in a multi-tenant credentials layout [3](#0-2) .
- `LabeledHandler` requires `repository.full_name` in its `ExplicitParameters` schema but does not require or cross-check `repository.owner.login` against the signature-selecting field [4](#0-3) .
- `LabeledHandler#repository` resolves the target `Repository` solely from `params.repository.full_name` [5](#0-4) , and `#handle` calls `stack.archive!` / `stack.unarchive!` on the resulting review stack based on the provisioning label [6](#0-5) .

Exploit flow: In a Shipit deployment configured with multiple GitHub organizations (`github_default_organization` non-nil, i.e. `secrets.github` keyed by org login, per `Shipit.github_app_config`) [7](#0-6) , an attacker who controls (or knows the webhook secret of) organization `attacker-org` sends `POST /webhooks` with `X-Github-Event: pull_request`, a body whose top-level `repository` key is omitted (or lacks `owner`), `organization.login = "attacker-org"`, and `pull_request.repository.full_name` (nested `repository.full_name` required by the handler schema) set to `"victim-org/victim-repo"`. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and validates the HMAC the attacker legitimately computed with a secret they know for their own org - the request passes. `LabeledHandler` then resolves `repository.full_name = "victim-org/victim-repo"`, loads `victim-org`'s `Repository`, and calls `archive!`/`unarchive!` on its review stack, all while the bot identity used for any downstream auto-triggered deploy is `victim-org`'s configured `bot_login` (`Shipit.user`), unrelated to the attacker's authenticated org.

Existing guards do not prevent this: `verify_signature` never checks that `repository_owner` equals the owner segment of `repository.full_name`; `drop_unhandled_event` only checks the event is registered; the `ExplicitParameters` schema for `LabeledHandler` validates presence/type of `repository.full_name` but not its relationship to `organization.login`; there is no `User#authorized?`/`require_permission!` check in the webhook path since webhooks are unauthenticated by design and rely solely on signature verification for trust.

### Impact Explanation
An attacker who has legitimate access to configure a webhook secret for one tenant organization onboarded to a shared multi-tenant Shipit instance can forge a `pull_request`/`labeled` webhook that archives or unarchives an arbitrary review stack belonging to a *different* tenant organization, without ever authenticating against that organization's secret. This is a payload for one repository (organization) mutating another organization's stack state - matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). Archiving/unarchiving a review stack can suppress or trigger deploy automation tied to the victim's configured bot identity (`Shipit.user`/`bot_login`), amplifying blast radius toward unauthorized deploy/rollback behavior on the victim stack. This is repeatable against any victim repository/organization onboarded to the same Shipit instance, since the only constraint is knowledge of one (any) organization's webhook secret.

### Likelihood Explanation
This finding only applies to multi-tenant Shipit deployments where `Shipit.github_default_organization` is non-nil (per-organization `github` credentials with distinct secrets, per `Shipit.github_app_config`) [7](#0-6) . In the common single-org/global-config deployment (`github_default_organization` nil), `Shipit.github(organization: repository_owner)` always resolves to the same single config regardless of the attacker-controlled `repository_owner`/`organization.login` value, so the same secret is checked either way and there is no cross-tenant confusion. The attack additionally requires the attacker to know/control the `webhook_secret` for at least one organization configured on the instance (typically their own, if they are the one who set up that org's Shipit integration) - this is a real but non-trivial precondition specific to multi-tenant setups, not a fully "zero-privilege internet attacker" scenario. Given these preconditions, the attack is cheap and fully repeatable once satisfied (a single crafted HTTP POST).

### Recommendation
In `Shipit::WebhooksController`, after signature verification, validate that the owner segment of the actual `repository.full_name`/`repository.owner.login` used by downstream handlers matches the `repository_owner` value that selected the signing secret; reject the request (422) on mismatch. Alternatively, require handlers like `LabeledHandler` to derive the acted-upon repository strictly from the same `repository.owner.login` field used for signature selection, and add an explicit equality assertion between `repository_owner` and the repository owner parsed by the handler before any state-mutating action (`archive!`/`unarchive!`).

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Configure `Shipit.stubs(:github_default_organization).returns('attacker-org')` (or set up `secrets.github` with two org keys `attacker-org` and `victim-org`, each with a distinct `webhook_secret` and `bot_login`).
2. Create `victim_repo = Shipit::Repository.create!(owner: 'victim-org', name: 'victim-repo', review_stacks_enabled: true, provisioning_behavior: 'prevent_with_label')` and a `Shipit::ReviewStack` for a PR under it, initially active (not archived).
3. Build a `pull_request`/`labeled` JSON payload that: omits `repository.owner` (or omits `repository` entirely for the top-level signature-selecting object) and sets `organization.login = 'attacker-org'`, while setting the nested `repository.full_name = 'victim-org/victim-repo'` required by `LabeledHandler`'s schema, and includes the provisioning label to trigger `archive?`.
4. Sign the raw body with `attacker-org`'s known `webhook_secret` and set `X-Hub-Signature` accordingly; POST to `/webhooks` with `X-Github-Event: pull_request`.
5. Assert response is `200`, `victim_repo`'s review stack's `archive!`/`unarchive!` state changed as dictated by the payload, and assert as the broken-binding check: `repository_owner (== 'attacker-org') != owner_of(repository.full_name) (== 'victim-org')`, demonstrating the signature-selection field and the acted-upon-repository field diverged while the action still succeeded against `victim-org`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
