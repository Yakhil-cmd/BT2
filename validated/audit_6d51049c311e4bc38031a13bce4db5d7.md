Based on the investigation, I can identify a genuine structural analog in ocore's asset conditions mechanism.

### Title
Immutable `attested` clause in an asset's `issue_condition`/`transfer_condition` permanently freezes the asset when the referenced attestor migrates its address - (File: definition.js, validation.js, aa_validation.js)

### Summary
The external report describes a `Marketplace` contract that hardcodes a reference to the `OriginToken` contract address; when `OriginToken` is migrated to a new address via `TokenMigration`, the `Marketplace` never updates its reference, permanently stranding deposited/offered funds. The structural root cause is an immutable reference to an external identity that is later migrated, with no update path in the referencing contract.

The equivalent pattern in ocore is an asset's `issue_condition` or `transfer_condition`, which can embed an `['attested', address, [attestor_addresses]]` clause [1](#0-0)  requiring that the holder/issuer be attested by one of a fixed, hardcoded list of attestor addresses. Unlike the built-in `spender_attested`/`attestors` fields (which have a dedicated `asset_attestors` message letting the definer update the trusted attestor list) [2](#0-1) [3](#0-2) , `issue_condition` and `transfer_condition` are part of the asset definition and have no update mechanism at all once the asset unit is posted [4](#0-3) .

### Finding Description
An asset issuer (a normal, unprivileged unit poster) can define `issue_condition`/`transfer_condition` referencing `['attested', 'this address', [attestor1, attestor2, ...]]` [1](#0-0) , and the same fields are exposed identically for assets issued by an AA [5](#0-4) . At spend-time, `attested` is checked by querying the live `attestations` table for a matching `attestor_address`/`address` pair as of `last_ball_mci` [6](#0-5)  (pattern shared with `seen address`/`seen definition change` checks in the same evaluator).

The attestor address embedded in the condition is permanent: the `assets` table and its `issue_condition`/`transfer_condition` columns are written once at asset creation and never updated [7](#0-6) , and `validateAssetDefinition` provides no message type to change these two fields post-issuance [8](#0-7) . If the real-world attestation service tied to that address rotates its signing/posting address (e.g., due to a key compromise, an operational migration, or simply retiring an old attestor address in favor of a new one — directly analogous to `TokenMigration` retiring the old `OriginToken`), all future attestations will be posted from the new address. The `attested` clause, however, still hardcodes the old attestor address, so it can never again be satisfied.

### Impact Explanation
This causes a genuine, protocol-level "AA/asset fund freezing" outcome matching the accepted impact classes: any holder of the asset (analogous to Alice's deposit or Charlie's offer funds) permanently loses the ability to issue further supply or transfer/spend their holdings, because the `transfer_condition`/`issue_condition` predicate can never again evaluate true. There is no governance path to fix it since the condition is baked into the immutable asset definition — no `asset_attestors`-style update exists for these two fields, unlike the dedicated `spender_attested` mechanism.

### Likelihood Explanation
Likelihood is moderate: it requires an asset issuer to have chosen to use a custom `issue_condition`/`transfer_condition` with an `attested` clause instead of the built-in `spender_attested`/`attestors` fields (which do support updates). This is a legitimate, documented feature of oscript definitions, so any dApp issuing a compliance-gated or KYC-gated asset via this pattern is exposed. It does not require any malicious actor — a normal, expected real-world event (attestor key/address rotation) triggers the freeze, exactly like the `TokenMigration` scenario in the report.

### Recommendation
Short term: document prominently that `issue_condition`/`transfer_condition` clauses referencing `attested` are permanent and cannot be updated, and recommend developers use the built-in `spender_attested`/`attestors` + `asset_attestors` update message instead when attestor rotation might ever be needed.

Long term: consider extending the `asset_attestors` update message (or an equivalent) to also support updating attestor addresses referenced inside custom `issue_condition`/`transfer_condition` trees, so an asset is not permanently bricked if a relied-upon attestor migrates its address.

### Proof of Concept
1. An issuer posts an `asset` definition message with `transfer_condition: ['attested', 'this address', ['ATTESTOR_ADDR_V1']]`, `issued_by_definer_only: true`, `is_transferrable: true` (validated per `validateAssetDefinition` / `aa_validation.js` asset case).
2. Users receive/hold this asset; every transfer is validated against `Definition.validateAuthentifiers`'s `attested` case, which queries `attestations` for `attestor_address='ATTESTOR_ADDR_V1'` [6](#0-5) .
3. The attestation service ("migrates") and begins posting all future attestations from `ATTESTOR_ADDR_V2` instead of `ATTESTOR_ADDR_V1` (e.g., after a key rotation).
4. Because the asset's `transfer_condition` is immutable and there is no message to update it [8](#0-7) , no future attestation record will ever again satisfy `attestor_address='ATTESTOR_ADDR_V1'` for new addresses.
5. All holders whose addresses were not already attested under V1 (and any future holder) are permanently unable to pass the `attested` transfer condition — the asset's supply becomes frozen/untransferable, with no on-chain remediation path.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
