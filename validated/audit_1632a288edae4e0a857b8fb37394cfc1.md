### Title
`provision?` ignores `review_stacks_enabled` for `prevent_with_label`/`allow_with_label` due to operator-precedence bug, causing unauthorized review-stack creation - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` and the three provisioning-behavior predicates with `&&`/`||` without parentheses, so `review_stacks_enabled` only gates `provisioning_behavior_allow_all?` and is silently ignored for `allow_with_label` and `prevent_with_label`. Combined with `pull_request_has_provisioning_label?` always returning `false` when `provisioning_label_name` is `nil` (since PR label names are always non-nil `String`s, `Array#include?(nil)` can never match), a repository configured with `provisioning_behavior: :prevent_with_label`, `provisioning_label_name: nil`, and `review_stacks_enabled: false` will still auto-provision a review stack for any opened pull request with no labels.

### Finding Description
The binding that should hold is: `provision? == true` **iff** `repository.review_stacks_enabled == true` **and** ( `allow_all` **or** (`allow_with_label` and PR label == operator-set `provisioning_label_name`) **or** (`prevent_with_label` and PR label != operator-set `provisioning_label_name`) ). The actual code is: [1](#0-0) 

Ruby's operator precedence parses this as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. This means `review_stacks_enabled` is scoped only to the `allow_all?` term and has zero effect on the `allow_with_label`/`prevent_with_label` terms.

Separately, `pull_request_has_provisioning_label?` is `pull_request_label_names.include?(repository.provisioning_label_name)`. The webhook schema requires every label's `name` to be a `String` [2](#0-1) , so `pull_request_label_names` never contains `nil`. When `provisioning_label_name` is `nil` (the schema default column has no default and starts `nil` [3](#0-2) ), `Array#include?(nil)` is always `false`, regardless of which labels the attacker's PR carries.

For a repository set to `prevent_with_label` with `provisioning_label_name: nil` and `review_stacks_enabled: false`:
- `has_label?` is always `false` (as shown above) → `!has_label?` is always `true`.
- `prevent_with_label?` is `true`.
- The third term evaluates to `true` unconditionally, and because of the precedence bug `review_stacks_enabled` never suppresses it.

So `provision?` returns `true` even though the operator explicitly disabled review stacks (`review_stacks_enabled: false`). Any attacker who can open a pull request against the tracked repository (with or without labels — labels don't matter here) triggers `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter#find_or_create!` [4](#0-3) , which provisions a new stack and runs the repository's provisioning scripts.

No existing guard catches this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and delegates entirely to the broken `provision?` [5](#0-4) ; there is no separate validation that `review_stacks_enabled` gates all provisioning modes.

### Impact Explanation
This is a repository-scoped authorization bypass: an operator who sets `review_stacks_enabled: false` (intending to disable automatic review-stack creation/provisioning entirely) unknowingly leaves the door open if they've also configured `provisioning_behavior: prevent_with_label` without setting a `provisioning_label_name`. Any pull request opened against that repository (by any contributor able to open a PR) causes an unauthorized stack to be provisioned and its deploy-spec-driven provisioning commands executed on the deploy host — matching the Critical category ("unauthorized review-stack creation and code execution"). This is repeatable per pull request/per repository misconfigured this way; blast radius is limited to repositories with this specific config combination but is fully repeatable for each.

### Likelihood Explanation
Requires the specific but plausible operator misconfiguration: `provisioning_behavior: :prevent_with_label` and `provisioning_label_name` left unset (nil), while `review_stacks_enabled` is `false` (the actual column default) [3](#0-2) . Given `provisioning_label_name` has no enforced presence validation tying it to `prevent_with_label`/`allow_with_label` in `Repository` [6](#0-5) , this misconfiguration is easy to reach accidentally, and once present, exploitation requires zero special access — only opening a PR.

### Recommendation
Fix the precedence bug in `provision?` to make `review_stacks_enabled` gate all three behaviors explicitly, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Additionally, add a `Repository` validation requiring `provisioning_label_name` to be present when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, so `pull_request_has_provisioning_label?` cannot silently degrade via `Array#include?(nil)`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label and no configured label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # review_stacks_enabled: false
    behavior: :prevent_with_label,
    label: nil                     # provisioning_label_name: nil
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding under test: `repository.review_stacks_enabled == false` should force `provision? == false` regardless of `provisioning_behavior`/label state. Running this test against current code fails (`Shipit::Stack.count` increases by 1), demonstrating `review_stacks_enabled` is ignored for `prevent_with_label`.
