## Title
Cross-organization team membership hijack via `Team.find_or_create_by!(github_id:)` lacking organization equality check - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

## Summary
`MembershipHandler#process` looks up an existing `Team` solely by GitHub's global `github_id`, and `Team#add_member` never re-checks the webhook's verified organization against the team's stored `organization`. An attacker who controls any second organization with a genuinely configured Shipit GitHub App can send a legitimately-signed `membership` webhook naming a victim team's `github_id` and add an arbitrary GitHub login (their own account) to that team, bypassing organization provenance entirely — even on the very first write, independent of idempotency.

## Finding Description
The binding that should hold is: `team.organization == repository_owner (the org whose secret verified this specific request)` for every mutation of a team's membership. This is never enforced.

Trace:
1. `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from the payload's `organization.login`/`repository.owner.login` and verifies the HMAC against that org's own `webhook_secret`. [1](#0-0)  This only proves the request came from *some* org that legitimately controls its own secret (e.g., attacker's own org O2) — it says nothing about O1, the team's actual organization.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. The `organization:` assignment only happens inside the creation block, which is skipped entirely if a `Team` with that `github_id` already exists. [2](#0-1)  No comparison of `params.organization.login` against the found `team.organization` is ever performed.
3. `Team#add_member` then unconditionally appends the member if not already present, with no organization check at all: `members.append(member) unless members.include?(member)`. [3](#0-2) 
4. `Membership` validation only enforces `uniqueness: { scope: :team_id }` — no organization-provenance check. [4](#0-3) 

Exploit flow: attacker administers org `O2` with a genuinely configured Shipit GitHub App/webhook. Attacker knows (or discovers) the numeric `github_id` of a target team belonging to org `O1` (e.g., `shopify/developers`, which may be one of `Shipit.github_teams` used for authorization gating). Attacker sends a `membership`/`added` webhook, signed with O2's real secret, with `organization.login: "O2"`, `team.id: <O1's team github_id>`, `member.login: "attacker"`. `verify_signature` passes (genuinely signed by O2). `find_or_create_team!` finds the pre-existing O1 team by `github_id` alone and returns it unchanged. `team.add_member(attacker_user)` inserts a new `Membership` row for the O1 team — on the very first request, no idempotency needed.

No existing guard catches this: `verify_signature` only authenticates the sender organization, not the target team's owner; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not organization consistency; there is no `require_permission!`/organization equality check anywhere in `MembershipHandler` or `Team`.

## Impact Explanation
`User#authorized?` grants Shipit application access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. [5](#0-4)  If the hijacked team is configured in `Shipit.github_teams`, this is a direct escalation into Shipit's authorization gate for an attacker who controls no more than their own separate GitHub organization and a legitimately configured Shipit app for it — matching "High - escalation into `Shipit.github_teams` authorization" (and arguably an authentication bypass into the tool for a party that was never authorized by O1). This is repeatable against any team whose `github_id` is discoverable, cross-tenant (attacker's org O2 mutates state belonging to org O1's team).

## Likelihood Explanation
Preconditions: attacker needs to own/administer a second GitHub organization with its own genuinely configured Shipit GitHub App/webhook secret (a normal, self-serve setup step, not a Shipit or victim secret), and must know the numeric `github_id` of the victim team (GitHub team IDs are not cryptographically secret and can be discovered via various public/semi-public means). No Shipit session, API token, or victim secret is required. The attack is a single HTTP POST to `/webhooks` with a correctly-signed payload for the attacker's own org — low cost, fully repeatable.

## Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login.downcase == team.organization` for existing teams and reject (raise / drop) the event on mismatch instead of silently reusing the record; scope the lookup by `github_id` **and** `organization`, or re-derive/validate organization on every event, not only at creation time.

## Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual, minitest)
test "membership webhook from a different organization must not add members to another org's team" do
  team = Shipit::Team.create!(github_id: 999, organization: 'shopify', slug: 'developers', name: 'Developers')
  attacker = nil

  payload = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Developers', 'slug' => 'developers', 'url' => 'http://x' },
    'organization' => { 'login' => 'evil-org' }, # attacker's own, genuinely-verified org
    'member' => { 'login' => 'attacker' }
  }

  assert_no_difference -> { Shipit::Membership.count } do
    Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call
  end

  team.reload
  refute team.members.exists?(login: 'attacker')
end
```
Both sides of the binding to assert: `team.organization` (`'shopify'`) vs. the request's verified organization (`'evil-org'`) — they differ, yet with current code the `assert_no_difference`/`refute` fail because `find_or_create_team!` returns the existing `shopify` team and `add_member` inserts the row regardless.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
