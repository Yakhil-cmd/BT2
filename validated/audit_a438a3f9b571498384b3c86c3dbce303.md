### Title
Hardcoded byte-size fee constants for textcoin claims can under-fund private/indivisible-asset claim addresses, permanently freezing funds - ([File: constants.js])

### Summary
The textcoin feature funds an ephemeral claim address with a *statically hardcoded* estimate of the bytes fee the recipient will need to pay when constructing the claim unit. For private, fixed-denomination ("indivisible") asset textcoins, the claim logic uses zero tolerance and explicitly disables the fallback of paying the shortfall from the recipient's own address (to preserve privacy). If the hardcoded fee constants understate the actual commission required by the real claim unit — which can happen whenever the unit serialization format changes in a future protocol upgrade, just as the report describes for EVM gas costs changing across forks — the private asset payment becomes permanently unclaimable.

### Finding Description
`constants.js` hardcodes several fee constants that approximate the exact byte size of a future, not-yet-built unit: [1](#0-0) 

`TEXTCOIN_CLAIM_FEE` only compensates for `version.length` changes; `TEXTCOIN_ASSET_CLAIM_HEADER_FEE`, `TEXTCOIN_ASSET_CLAIM_MESSAGE_FEE`, `TEXTCOIN_ASSET_CLAIM_BASE_MSG_FEE`, and `TEXTCOIN_PRIVATE_ASSET_CLAIM_MESSAGE_FEE` are pure hardcoded integers derived from assumed JSON key/value lengths of the future claim unit's headers and payment message. They are not derived from `object_length.getHeadersSize`/`getTotalPayloadSize` at claim time, nor updated by any versioned/system-var mechanism (unlike `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`, which are voted on-chain via `system_vars`, see `initial_votes.js`).

These constants are added to the textcoin output in `wallet.js` when the sender composes the payment: [2](#0-1) [3](#0-2) 

Only the oversize fee component is computed dynamically via `storage.getOversizeFee`; the header/message-count-based components remain static assumptions about unit byte size.

When the recipient later claims a private, fixed-denomination (indivisible) asset textcoin, the claim composes with zero tolerance: [4](#0-3) 

And crucially, the "not enough funds" fallback that would otherwise let the recipient pay the missing bytes fee from their own wallet address is explicitly disabled for private payments to avoid deanonymizing the recipient: [5](#0-4) 

So the only source of bytes to pay the claim unit's `headers_commission`/`payload_commission` is the amount pre-funded by the sender using the hardcoded constants. The comment `// AA-generated units pay the oversize fee...` and the existence of `pemCurvesFixMci` (a dedicated upgrade MCI that had to fix a previous curve/serialization-size bug affecting fee/size calculations) show that the underlying serialization-size assumptions have already drifted once in this codebase's history — directly mirroring the "EVM gas costs have changed before" risk cited in the original report.

### Impact Explanation
If a future protocol upgrade changes the serialized size of a unit's headers or payment message (new optional fields, key-size changes, signature/format changes — precedents: `includeKeySizesUpgradeMci`, `v4UpgradeMci` adding `oversize_fee`/`tps_fee`/`burn_fee`/`max_aa_responses`, and the historical `pemCurvesFixMci` fix), the hardcoded `TEXTCOIN_ASSET_CLAIM_*` / `TEXTCOIN_PRIVATE_ASSET_CLAIM_MESSAGE_FEE` constants will underestimate the true commission needed by the claim unit. For a private, indivisible-asset textcoin, this results in a claim unit that can never satisfy the exact-denomination, zero-tolerance funding requirement, and the privacy-preserving fallback is disabled, so the recipient can never claim the payment. This is a permanent freeze of already-transferred asset funds — a real fund-loss condition, not just an off-chain accounting inaccuracy.

### Likelihood Explanation
Medium: the assumptions underlying these constants are tied to unit serialization format, which has changed multiple times in ocore's history (key-size inclusion, v4 fee fields, and the `pemCurvesFixMci` fix specifically addressing a size-related bug). Any future upgrade touching unit/message serialization without a corresponding manual update to these four hardcoded constants reproduces the exact same class of bug described in the source report.

### Recommendation
Replace the hardcoded byte-size constants with dynamically computed values derived from `object_length.getHeadersSize`/`getTotalPayloadSize` against the actual (or a template) claim unit at claim-funding time, similar to how `oversize_fee` is already computed dynamically via `storage.getOversizeFee`. Alternatively, version-gate these constants behind the relevant upgrade MCIs (as is already done for other protocol constants such as `includeKeySizesUpgradeMci`) so they can be corrected without silently breaking previously-issued, not-yet-claimed private textcoins.

### Proof of Concept
1. A future protocol upgrade adds a new mandatory field to unit headers or increases a key name's length (as has happened historically, e.g. `includeKeySizesUpgradeMci`, `pemCurvesFixMci`).
2. `TEXTCOIN_ASSET_CLAIM_HEADER_FEE`/`TEXTCOIN_PRIVATE_ASSET_CLAIM_MESSAGE_FEE` in `constants.js` are not updated to reflect the new byte size.
3. A user sends a private, fixed-denomination asset via `sendMultiPayment` with a textcoin output; `wallet.js:2450-2457` funds the claim address using the stale hardcoded constants, under-provisioning bytes.
4. The recipient calls `receiveTextCoin`; `indivisibleAsset.composeAndSaveIndivisibleAssetPaymentJoint` is invoked with `tolerance_plus=0`/`tolerance_minus=0` (`wallet.js:2774-2776`) and fails with "not enough funds."
5. Because `opts._private` is true, the `ifNotEnoughFunds` handler at `wallet.js:2697-2711` refuses to retry with the recipient's own address, and the private asset payment is permanently unclaimable.
