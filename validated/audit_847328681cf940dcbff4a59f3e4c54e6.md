### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login` field that is decoupled from the `repository.full_name` actually acted on by event handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a delivery against using a value pulled out of the very JSON body whose authenticity it is trying to establish, while the code paths that actually mutate Shipit data (creating stacks, syncing commits, updating statuses, adding team memberships) key off a different field (`repository.full_name` / `organization.login`) inside that same body. Because both fields live inside the HMAC-signed payload but are never cross-checked against each other, an actor who legitimately controls one onboarded GitHub organization (and therefore knows that organization's configured `webhook_secret`) can produce a validly-signed payload whose `repository.owner.login` names their own org (to pass `verify_signature`) while other fields consumed later (e.g. `repository.full_name`, `organization.login` used by the `membership`/`push`/`status` handlers) name a different, victim organization/repository.

### Finding Description
`verify_signature` derives the signing organization exclusively from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` is used to fetch the per-organization `webhook_secret` used by `verify_webhook_signature`: [3](#0-2) 

The signature check therefore only proves "this body was signed with the secret belonging to whatever organization the body itself claims to belong to" - it does not prove any binding between that claimed organization and the repository/organization values that the downstream handlers subsequently act on (`GithubSyncJob`, commit `Status` creation, `Team`/`Membership` creation via the `membership` event, as exercised in `test/controllers/webhooks_controller_test.rb`). Handlers dispatched via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` receive the full, unvalidated `params` hash and use whichever sub-fields they need (e.g. `membership_params` in the tests use `organization: { login: 'shopify' }` and separately-provided `repository` fields) without re-deriving/re-checking those fields against the organization whose secret validated the request.

Because a self-service, multi-tenant deployment of Shipit configures one GitHub App entry (`app_id`, `installation_id`, `webhook_secret`, `private_key`) per organization in `secrets.yml` (see `config/secrets.development.shopify.yml`, `docs/setup.md`), any org owner who is legitimately onboarded onto the same Shipit instance knows their own `webhook_secret`, satisfies `verify_webhook_signature`, and can then supply arbitrary `repository.full_name` / `organization.login` values elsewhere in the same signed body.

### Impact Explanation
If a handler creates/updates records (Team, Membership, Commit, Status, Stack) keyed by a `repository.full_name` or `organization.login` value that differs from the organization whose secret validated the delivery, an org owner on a shared Shipit instance could inject webhook-driven writes (e.g. fabricate commit statuses, team memberships, or trigger `GithubSyncJob`) against another tenant's repository/organization - a cross-repository/cross-organization write performed by an actor who only controls their own org's credentials. This matches the High/Critical "cross-repository writes" impact class defined for this analysis.

### Likelihood Explanation
Requires only that the attacker be an authenticated administrator of one org configured on a shared multi-tenant Shipit deployment (a scenario the docs explicitly support: multiple `github:` entries keyed by org in `secrets.yml`). No GitHub App private key, Shipit session, or API token is needed - the attacker crafts and POSTs a raw HTTP payload directly to `/webhooks`, computing the HMAC themselves with their own known secret.

### Recommendation
Bind webhook signature verification to a single canonical identifier and enforce that every downstream handler re-derives its target Stack/Repository/Organization strictly from that same identifier (not from independently-read sub-fields of the payload). Concretely: after signature verification, tag the parsed payload with the verified `repository_owner`, and require handlers (`push`, `status`, `membership`, etc.) to assert that any `repository.full_name`/`organization.login` value they consume belongs to that verified owner before creating or mutating records, rejecting the delivery (422) otherwise.

### Proof of Concept
1. Onboard/administer `org-attacker` on a shared Shipit instance, knowing its `webhook_secret` (`S_a`).
2. Build a JSON body for the `membership` event where `organization.login = "org-attacker"` but `member.login`/`team` reference or otherwise target data intended for `org-victim` (or, for `push`/`status` events, set `repository.owner.login = "org-attacker"` while `repository.full_name = "org-victim/target-repo"`).
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_a, raw_body)>` using the known secret for `org-attacker`.
4. POST to `/webhooks` with `X-Github-Event` set accordingly.
5. `verify_signature` resolves `repository_owner` to `org-attacker`, validates the signature successfully with `S_a`, and the corresponding handler in `Shipit::Webhooks.for_event(event)` processes the full payload, acting on the `org-victim`/`target-repo` fields embedded in the same body.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
