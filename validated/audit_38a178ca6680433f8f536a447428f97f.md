### Title
CCMenu API endpoint bypasses ApiClient's stack scope, letting a stack-scoped token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup to fetch the stack directly by param instead of going through the ApiClient-scoped lookup used everywhere else in the API, breaking the binding "the stack a token authorizes" == "the stack the request actually touches."

### Finding Description
The base API controller establishes a binding between an `ApiClient`'s authorized stack and the stack a request can act on: [1](#0-0) . Here `stacks` is scoped to `current_api_client.stack_id` when the client has one, and `stack` is resolved only from within that scoped relation (`stacks.from_param!`). Every other API controller inherits this and is therefore prevented from touching a stack outside the token's `stack_id` scope, even if the token carries the generic `read:stack` permission.

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) . It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, not through `current_api_client`-scoped `stacks`. Authorization is still enforced only at the coarse permission level via `require_permission :read, :stack` (i.e., `current_api_client.check_permissions!(:read, :stack)`), which merely checks that the string `"read:stack"` is in the token's `permissions` array — it never checks which stack the token is bound to: [3](#0-2) .

Consequently, any `ApiClient` record that has been granted `read:stack` and has a non-nil `stack_id` (i.e., is meant to be scoped to a single stack) can be replayed against `CCMenuController#show` with an arbitrary `stack_id` in the URL/query params and will successfully render that other stack's CI/build status, deploy state, and lock state — data belonging to a stack the token was never authorized for.

### Impact Explanation
This crosses the "a stack a token authorises versus a stack it touches" trust boundary called out in the rules. Concretely, it is an unauthenticated-for-that-stack read of stack state (deploy status, lock status, last build info) via a token that was only meant to be valid for a different stack. This matches the High-severity class: "unauthorized read of stack state ... via API token whose stack scope should have restricted it." The confidentiality impact is limited to state exposed in the CCMenu XML view (deploy id, status, lock reason), not source code or credentials, but it is a clear authorization-boundary violation reachable by anyone holding any single-stack-scoped `read:stack` token (which is by design a low-privilege, widely distributed token type intended for CI dashboard integrations).

### Likelihood Explanation
Exploitation requires possession of any valid ApiClient token scoped to one stack with `read:stack` permission — the type of token that is commonly generated and shared for CCMenu/CI-dashboard integrations (see `CCMenuUrlController`, which mints a `read:stack` `ApiClient`). The rules classify possessing an `ApiClient` token as a normal (non-privileged-account) capability boundary to test against, and the bypass itself requires no special conditions — simply supplying a different `stack_id` in the request. This makes exploitation straightforward once any such token is obtained.

### Recommendation
Change `CCMenuController#stack` to resolve through the ApiClient-scoped lookup (`stacks.from_param!(params[:stack_id])`, inherited from `BaseController`) instead of calling `Stack.from_param!` directly, so a token's `stack_id` scope is enforced consistently across all API endpoints, matching the binding enforced in `BaseController#stack`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A with `permissions: ["read:stack"]` and `stack_id = A.id` (e.g., via the normal CCMenu URL generation flow in `CCMenuUrlController#client`, or via the API client management UI).
2. Note the token's `authentication_token`.
3. Send `GET /api/stacks/:stack_id_of_B/ccmenu.xml?token=<token>` where `B` is a different stack that the token was never granted access to.
4. `authenticate_api_client` succeeds using `params[:token]`; `require_permission :read, :stack` passes because the token has `read:stack` in its permission list; `stack` resolves via `Stack.from_param!(params[:stack_id])` — ignoring `current_api_client.stack_id` — returning Stack B.
5. The response renders Stack B's CI/build/deploy/lock status, even though the token is only authorized for Stack A. [4](#0-3)
