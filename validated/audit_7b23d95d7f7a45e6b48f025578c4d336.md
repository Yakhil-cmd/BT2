### Title
Stack-scoped API token bypasses its stack restriction in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces the binding "stack a token authorises == stack a token touches" by resolving the target stack through `stacks.from_param!`, where `stacks` is filtered to `current_api_client.stack_id` when the client is scoped to a single stack. `Api::CCMenuController` overrides the private `stack` helper to call `Stack.from_param!(params[:stack_id])` directly, discarding that scoping filter, so a token restricted to one stack can read CCMenu/build status for any stack.

### Finding Description
`Api::BaseController` defines the intended scoping mechanism: [3](#0-2) 

`current_api_client.stack_id?` is true when an `ApiClient` (`app/models/shipit/api_client.rb`) `belongs_to :stack, optional: true` and has a `stack_id` set — this is exactly how scoped tokens like the `here_come_the_walrus` fixture are modeled: [4](#0-3) 

Permission checks (`require_permission`) only validate the `operation:scope` string (e.g. `read:stack`) against the client's `permissions` array — they never validate which specific stack is being accessed: [5](#0-4) 

So the only place that enforces "this token may only touch its own stack" is the `stacks`/`stack` helper in `BaseController`. `Api::CCMenuController`, however, redefines `stack` to bypass this filter entirely, resolving directly against the full `Stack` table: [6](#0-5) 

Because `#show` uses this unscoped `stack` to fetch `stack.deploys_and_rollbacks.last` and render the CCMenu status, a client whose token authorizes only stack A can request `GET /api/stacks/:B/ccmenu` for an arbitrary stack B and still receive a valid response, since `require_permission :read, :stack` only checks that `read:stack` is among the client's permissions, not that B matches the client's `stack_id`.

Equality broken: `stack authorised by token (current_api_client.stack_id)` ≠ `stack touched by controller action (Stack.from_param!(params[:stack_id]))`.

### Impact Explanation
This allows a holder of a legitimately-issued, narrowly-scoped API token (e.g. the "CCMenu Client" tokens minted by `CCMenuUrlController#client`, which are explicitly created with `permissions: %w[read:stack]` and bound to a single stack for embedding in CI-monitoring tools) to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, lock state) of any other stack on the Shipit instance, not just the one it was issued for. This matches the "High - unauthenticated read of stack state" class of impact: the token is valid but its authorization boundary (single stack) is not the boundary actually enforced (all stacks), so an attacker escalates read access across stacks/repositories they were not granted visibility into.

### Likelihood Explanation
Exploitation requires only an existing stack-scoped read-only token (which by design is meant to be low-privilege and is even distributed via a shareable URL, per `CCMenuUrlController`) and knowledge/guessing of another stack's `owner/repo/environment` path — stack identifiers are not secret and are enumerable via `Api::StacksController#index` if broader read access exists, or simply known from GitHub. No privileged account or additional secret is required beyond the scoped token itself.

### Recommendation
Fix `Api::CCMenuController#stack` to reuse the scoped `stacks` collection from `BaseController` instead of querying `Stack` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so stack-scoped tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create (or reuse) an `ApiClient` scoped to stack `owner/repo-a/production` with only `read:stack` permission (as done automatically by `Shipit::CCMenuUrlController#client` for any user visiting a stack's CCMenu URL).
2. As the holder of that token, issue: `GET /api/stacks/owner/repo-b/staging/ccmenu?token=<scoped-token>` (or via HTTP Basic auth).
3. Observe that `Api::CCMenuController#stack` resolves `repo-b/staging` via `Stack.from_param!` (unscoped), `require_permission :read, :stack` passes because the token has `read:stack`, and the response renders `repo-b/staging`'s current deploy/build status XML — a stack the token was never authorized for.
