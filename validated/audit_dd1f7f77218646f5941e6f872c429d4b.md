This bug class concerns ERC-20 `approve()` allowances that a contract cannot reset back to zero. The Raydium CP-Swap program does not use any SPL Token `approve`/`delegate` mechanism at all — all token movements go through direct `transfer_checked` CPIs signed by the pool's PDA authority (`AUTH_SEED`), as seen in `transfer_from_user_to_pool_vault` and `transfer_from_pool_vault_to_user` in [1](#0-0)  and their usage in `swap_base_output` [2](#0-1) . The occurrences of "approve" in the codebase (e.g. in `error.rs`'s `NotApproved` error) are unrelated string matches, not an SPL `Approve`/delegate authorization being granted to a persistent spender. Since there is no analog of a vault granting a standing allowance to another program/account that later cannot be revoked, this report's root cause has no reachable counterpart in the constant-product curve, deposit/withdraw, swap, or initialize paths of this program.

pub fn transfer_from_user_to_pool_vault<'a>(
    authority: AccountInfo<'a>,
    from: AccountInfo<'a>,

    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new(
            *token_program.key,
            token_2022::TransferChecked {
                from,
                to: to_vault,
                authority,
                mint,
            },
        ),
        amount,
        mint_decimals,
    )
}
