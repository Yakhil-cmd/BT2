## Analysis

The report's bug class is: a liquidator is allowed to act on a smaller "available" scope (share/collateral) than the actual claim (full debt), and once the bounded resource is exhausted, nothing enforces the leftover claim — creating a permanent trust-binding break between "amount owed" and "amount actually collectible."

The closest analog in this engine is a **scope-vs-enforcement mismatch for `ApiClient#stack_id`**. `Shipit::ApiClient` supports being bound to a single `Stack` via `belongs_to :stack, optional: true` [1](#0-0) , and the base API controller correctly enforces this binding by scoping the visible/actionable stacks to `current_api_client.stack_id` whenever it is set: [2](#0-1) 

This is exercised by the fixture `here_come_the_walrus`, an `ApiClient` scoped to the `shipit` stack with only `read:stack` permission [3](#0-2) , and is verified by the test "an api client scoped to a stack will only see that one stack" [4](#0-3) .

However, `Shipit::Api::CCMenuController` overrides `stack` to bypass this binding entirely, resolving the target stack from the raw, unscoped `Stack` relation instead of from `stacks` (the api-client-scoped relation): [5](#0-4) 

`require_permission :read, :stack` only checks whether the `read:stack` permission string is present in `ApiClient#permissions` via `check_permissions!` [6](#0-5)  — it never checks whether the specific stack being accessed matches `current_api_client.stack_id`. That check only exists in the `stacks`/`stack` helpers of `BaseController`, which `CCMenuController` does not use.

### Title
Stack-scoped ApiClient token can read CI/build status of any stack via CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` created with `stack_id` set (a credential intentionally restricted to a single stack) can be used against `Api::CCMenuController#show` to read the build status of **any** stack in the installation, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` establishes the binding "stack a token authorizes == stack it is allowed to touch" through its `stacks`/`stack` helper methods, which filter by `current_api_client.stack_id` when present [2](#0-1) . `CCMenuController`, however, redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely ignoring `current_api_client.stack_id` [7](#0-6) . The `require_permission :read, :stack` declaration only enforces the coarse `read:stack` permission flag [8](#0-7) , and `ApiClient#check_permissions!` has no notion of which stack is being accessed [6](#0-5) . As a result, the equality "`token.stack_id` == `stack.id` being acted upon" is broken specifically in this controller, even though the rest of the API enforces it correctly.

### Impact Explanation
This is a scope-escalation of an existing, valid credential: a token explicitly restricted by an operator to one stack (e.g., handed to a third-party CI dashboard for a single repository/environment) can be used to enumerate build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for every stack in the Shipit installation, as rendered by `CCMenuController#show` [9](#0-8) . This matches the "unauthenticated read of stack state" bucket in spirit — the credential is valid, but its authorized scope has been silently escalated from one stack to all stacks, crossing the repository/stack authorization boundary the token was explicitly bound to.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a supported, first-class configuration per the `stack` column, `stacks` fixture, and existing test coverage of the scoping behavior [4](#0-3) ) can trigger this simply by calling the CCMenu endpoint with a different `stack_id` param and their own token — no additional privileges, session, or secret is required beyond the token they already legitimately hold.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the inherited `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens are restricted to their assigned stack, consistent with every other controller under `Shipit::Api::BaseController`.

### Proof of Concept
1. An operator creates (or the host application creates programmatically) an `ApiClient` with `stack: stack_a`, `permissions: ['read:stack']` — mirroring the `here_come_the_walrus` fixture [3](#0-2) , and hands its `authentication_token` to a third party expected to only see `stack_a`.
2. The third party issues:
   `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<stack_a-scoped-token>` where `stack_b` is any other stack in the installation.
3. `authenticate_api_client` resolves `current_api_client` to the `stack_a`-scoped `ApiClient` [10](#0-9) .
4. `require_permission :read, :stack` passes because the client has `read:stack` in its permission list, regardless of which stack ID was requested.
5. `stack` resolves via the overridden `Stack.from_param!(params[:stack_id])`, returning `stack_b` instead of failing/scoping to `stack_a` [7](#0-6) .
6. `show` renders `stack_b`'s latest deploy/build status back to the caller [9](#0-8) , despite the token never having been authorized for `stack_b`.
