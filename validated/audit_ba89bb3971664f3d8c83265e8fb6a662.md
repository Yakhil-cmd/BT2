### Title
Webhook signature verification keys off `repository.owner.login` while stack-routing keys off `repository.full_name`, allowing cross-organization webhook forgery in multi-tenant Shipit instances - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
When a single Shipit deployment manages multiple GitHub organizations (the documented "Using Multiple GitHub Applications" configuration), the field used to select which HMAC secret validates an inbound webhook is not the same field later used to determine which `Stack`/repository the webhook payload acts on. This breaks the equality binding: `organization authenticated by HMAC == organization of the repository actually written to`.

### Finding Description
`WebhooksController#verify_signature` resolves which `GitHubApp` (and therefore which `webhook_secret`) to validate the request against using: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`), and `Shipit.github(organization: repository_owner)` looks up the org-specific config/secret in the multi-org schema documented in `docs/setup.md` ("Using Multiple Github Applications") and exercised by `test/dummy/config/secrets_double_github_app.yml`.

Once the HMAC check passes, event handlers determine *which* stack/repository to act on using a **different** field of the same untrusted JSON body: [3](#0-2) 

`PushHandler#process` then uses `stacks` (derived from `repository_name` = `full_name`) to look up stacks and calls `stack.sync_github`, which enqueues `GithubSyncJob`: [4](#0-3) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the target stack) are two independent, attacker-controlled JSON fields with no cross-validation, an actor who legitimately controls a GitHub App/organization already configured on the shared Shipit instance (and therefore knows that organization's `webhook_secret`) can sign a payload where `repository.owner.login` is their own org (satisfying signature verification) while `repository.full_name` names a stack belonging to a *different* organization/repository on the same Shipit instance. In legitimate GitHub-generated payloads these two fields always describe the same repository, so nothing in the current code enforces that this remains true for forged requests.

### Impact Explanation
With a forged payload of this shape, an attacker who is a legitimate (but unprivileged with respect to other tenants) org owner on a shared Shipit install can:
- Force `GithubSyncJob` to run against a foreign stack, causing Shipit to poll/sync commits and, for stacks with `continuous_deployment` enabled, resume/trigger the continuous-delivery pipeline (`continuous_delivery_resumed!` is called from `trigger_deploy`, and sync completion feeds into deploy scheduling) earlier or differently than the foreign org's own maintainers intended.
- More broadly, this demonstrates a violation of the tenant isolation the multi-org GitHub App feature is meant to provide: webhook authenticity is anchored to the wrong identity boundary (claimed owner) rather than the boundary that is actually acted upon (target repository/stack).

This falls into the "escalation into authorization boundary" class described by the rules (organization authenticated vs. repository written), and in installations relying on `continuous_deployment` it can result in an unauthorized/forced deploy trigger on a repository the attacker does not own.

### Likelihood Explanation
Requires: (1) the target Shipit instance to be configured for multiple GitHub organizations (an explicitly documented, supported configuration), and (2) the attacker to control at least one of those organizations' GitHub Apps/webhook secret (i.e., they are a legitimate but low-privilege tenant of the shared instance). Given that, forging the cross-tenant payload requires no further privilege — just crafting a JSON body with mismatched `repository.owner.login` and `repository.full_name` and signing it with the known secret. This is plausible in shared/managed Shipit deployments serving several organizations, though not applicable to single-organization deployments (the default, unversioned `github:` config schema) where there is only one secret and the binding is trivially self-consistent.

### Recommendation
Bind the same identity used for signature verification to the identity used for routing/lookup:
- After verifying the signature for `repository_owner`, additionally check that the organization portion of `repository.full_name` (or `organization.login` for org-scoped events) matches `repository_owner`/the resolved `GitHubApp`'s configured organization before dispatching to handlers.
- Alternatively, have `Handlers::Handler#repository_name` and `stacks` scope lookups to `Repository` records that belong to the same organization that authenticated the webhook, rejecting/logging any payload where the two disagree.

### Proof of Concept
1. Configure Shipit in the multi-org mode (`secrets.yml` `github: { OrgA: {...webhook_secret: SECRET_A}, OrgB: {...} }`), with `OrgA` controlled by the attacker and `OrgB/victim-repo` a stack belonging to a different tenant.
2. Craft a push payload:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. Sign the raw JSON with `SECRET_A` (`sha1=` HMAC) and POST to `/github/webhooks` with `X-Github-Event: push` and `X-Hub-Signature` set to that signature.
4. `verify_signature` resolves `repository_owner == "OrgA"`, verifies successfully against `SECRET_A`.
5. `PushHandler#process` resolves `repository_name == "OrgB/victim-repo"` via `Handler#repository_name`/`stacks`, and calls `stack.sync_github` on the victim's stack — a stack the attacker never authenticated for — despite verification having occurred against `OrgA`'s secret.

Note: I was unable to fully trace, due to the tool-call budget running out, whether `GithubSyncJob`'s commit sync alone (without cron-triggered `schedule_continuous_delivery`) can immediately fire a deploy for `continuous_deployment` stacks; this final link should be confirmed in the codebase (`app/models/shipit/commit.rb#create_from_github!`, `app/jobs/shipit/continuous_delivery_job.rb`) before treating the impact as a guaranteed unauthorized deploy rather than an unauthorized cross-tenant sync/poll trigger.
