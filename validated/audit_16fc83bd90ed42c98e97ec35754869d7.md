### Title
Race-condition consumption of one-time device pairing secrets enables correspondent-identity hijack - ([File: device.js])

### Summary
`handlePairingMessage` in `device.js` processes an incoming `"pairing"` message from *any* device that presents a valid `pairing_secret`. For non-permanent (single-use) secrets, the first caller to present the secret is accepted as the correspondent and the secret row is deleted, exactly mirroring the `validate_and_store_payload` front-running pattern: a public, unauthenticated "validate-and-consume" operation on a single-use token that any party can invoke ahead of the intended recipient.

### Finding Description
`startWaitingForPairing` generates a random, non-permanent `pairing_secret`, stores it in `pairing_secrets`, and returns pairing info that is shared out-of-band (QR code/link) with the intended partner device: [1](#0-0) 

When any device sends a `"pairing"` message containing a `pairing_secret`, `handlePairingMessage` looks it up and, if found, unconditionally accepts the request, inserting the sender as a confirmed correspondent and then deleting the one-time secret so it cannot be used again: [2](#0-1) 

There is no binding between the secret and any expected identity (device pubkey) of the intended recipient beyond whatever the secret itself proves — anyone who obtains the secret bytes (e.g. via the shared QR/link surface, clipboard, screenshot, over-shoulder capture, or any leak in the sharing channel) can race the intended device to the hub. The `INSERT ... IGNORE INTO correspondent_devices` plus `DELETE FROM pairing_secrets WHERE pairing_secret=?` is not atomic with respect to competing message deliveries reaching the wallet at effectively the same time, and — more importantly — there is no re-check that the accepting request is coming from the party who was actually intended to redeem it. The first `"pairing"` message that reaches the device consumes the secret; the legitimate device's later `"pairing"` message will then fail with `"pairing secret not found or expired"`.

### Impact Explanation
This is directly analogous to the reported `validate_and_store_payload` front-run: a public "validate and mark used" primitive lets an unrelated party pre-consume a resource intended for a specific counterpart, causing the legitimate transaction/handshake to fail. Here the effect is worse than simple denial of service: successful consumption of the secret does not just block the legitimate device — it plants the attacker as a *confirmed correspondent* in place of the intended device. Correspondent devices are the trust anchor for:
- Sending/receiving `wallet and contract message handling` (chat, signing requests, arbiter contracts).
- Forwarding private payment chains to correspondents in multi-member/shared addresses (`forwardPrivateChainsToOtherMembersOfSharedAddresses` in `network.js`), meaning an attacker impersonating a legitimate cosigner can receive private payment data intended for that party.
- Multi-signature/shared-address setup flows (`wallet_defined_by_addresses.js`), where correspondent devices are used to assemble cosigners for jointly controlled addresses — an attacker substituted for a legitimate cosigner could end up holding a live signing key over what the victim believes is a address shared only with a trusted party, creating a path to unauthorized spending from that shared address.

Given the rules permit "paired device" as a reachable, unprivileged actor and "wallet and contract message handling" as in-scope, this qualifies as a Medium/High finding: it enables identity confusion of a paired counterparty which can escalate to leakage of private payment chains or participation as an unintended cosigner in shared-address definitions.

### Likelihood Explanation
Exploitability depends on the attacker obtaining the pairing secret before the intended device redeems it. This is plausible in common real-world sharing flows (pairing QR codes/links pasted in chats, shown on screen, sent through less-secure channels, or intercepted during transmission) and requires no privileged key material, hub cooperation, or node compromise — only speed in submitting the `"pairing"` message with the leaked secret, which is inherently a race any unprivileged party observing the secret can win.

### Recommendation
- Bind one-time pairing secrets to the expected counterpart, or require an out-of-band confirmation step (e.g., user confirmation on the redeeming side showing the new correspondent's identity/fingerprint) before finalizing an unconfirmed correspondent as "confirmed" and irreversibly consuming the secret.
- Make the "check secret exists" → "add correspondent" → "delete secret" sequence atomic/exclusive (e.g., `DELETE ... WHERE pairing_secret=? RETURNING`, or a single conditional update) so that only one redemption can ever succeed and losers get a definitive error immediately rather than potentially racing on the same window.
- Surface an explicit UI warning/notification the moment a one-time pairing secret is redeemed, so the sharer can detect and revoke a hijacked pairing before using the (now attacker-controlled) correspondent for shared-address or private-payment flows.

### Proof of Concept
1. Alice (device A) calls `startWaitingForPairing`, generating one-time `pairing_secret` S and shares the resulting pairing code (`pubkey@hub#S`) with Bob out-of-band. [1](#0-0) 
2. Mallory obtains S from the sharing channel (e.g., screenshot, clipboard, shoulder-surfing, logging) before Bob acts on it.
3. Mallory's device sends a `"pairing"` message to Alice's hub/device with `body.pairing_secret = S` and her own `device_pubkey`.
4. Alice's `handlePairingMessage` finds S in `pairing_secrets`, inserts Mallory as a confirmed correspondent, and deletes S: [3](#0-2) 
5. When Bob's device later sends its own `"pairing"` message with the same S, the query returns no rows and Bob's legitimate pairing fails: `"pairing secret not found or expired"`.
6. Alice now unknowingly treats Mallory as the correspondent she intended to be Bob — any subsequent shared-address assembly, private payment chain, or arbiter contract flow directed at "Bob's device address" is actually directed at Mallory.

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
