Based on my investigation, I found a clear analog in `wallet.js`'s `sign` message handler.

### Title
Missing Cosigner Authorization Check Allows Any Paired Device to Trigger Signing Requests for Locally-Held Addresses - (File: wallet.js)

### Summary
The `"sign"` device-message handler in `handleMessageFromHub` verifies that the requesting device is an authorized cosigner only in the `ifRemote` branch (proxying a signing request to another device), but the equivalent check is explicitly commented out in the `ifLocal` branch, which handles signing requests for addresses whose keys are hosted on the current device.

### Finding Description
When a `"sign"` message arrives, `findAddress()` resolves whether the requested address/signing_path is `ifLocal` (private key material lives on this device) or `ifRemote` (must be forwarded to another cosigner's device). In the `ifRemote` path there is an explicit authorization check: [1](#0-0) 
requiring `from_address` to be present in `other_device_addresses`, i.e., a legitimate cosigner of that address.

In the `ifLocal` path, the exact same check exists in the code but is commented out: [2](#0-1) 
The comment states "the commented check would make multilateral signing impossible," indicating the check was deliberately disabled rather than removed as dead code. As a result, `ifLocal` never verifies that `from_address` (the sender of the `"sign"` justsaying, which can be *any* paired/correspondent device, not just cosigners of `body.address`) is actually authorized over the shared address being signed for.

The only remaining gate before the `signing_request` event fires is `authorAddresses.includes(body.address)` (structural validity of the attacker-supplied unit) — this does not verify that the *sender* of the request has any relationship to `body.address`. Any correspondent device that knows one of the local device's addresses (which are often shared during shared-address/contract setup, or simply guessed since address derivation for wallet-defined-by-addresses uses deterministic templates) can trigger a `signing_request` UI event for that address with an attacker-crafted unit, without being an actual party to that address's definition.

### Impact Explanation
This is a permission/authorization bypass analogous to the Craft CMS IDOR: a target-object-specific authorization check ("is this caller actually a cosigner of this address?") is missing on one code path while present on the structurally identical path. A malicious paired device can force `signing_request` prompts (and, for `signed_message`/multilateral-signing flows used by prosaic/arbiter contracts, spending-unit signing prompts) referencing addresses it has no cosigning rights over, potentially tricking the user into approving payments/contract commitments they did not initiate, or spamming/DoS-ing the signing UI with spoofed requests purportedly related to `body.address`.

### Likelihood Explanation
Exploitation requires only an established device pairing (any correspondent), which is a low bar reachable by "paired device" actors explicitly in scope. No cryptographic material needs to be broken — the sender only needs to know a target address string.

### Recommendation
Restore the cosigner-membership check in the `ifLocal` branch of the `"sign"` case (mirroring the `ifRemote` branch), i.e., before emitting `signing_request`, verify `from_address` is a legitimate cosigner/device party for `body.address` and `body.signing_path` (e.g., check `shared_address_signing_paths` / `wallet_signing_paths` / `peer_addresses` for a matching `device_address`), and only allow the multilateral-signing exception for definitions that structurally require an external counterparty address.

### Proof of Concept
1. Device A pairs with Device B (ordinary correspondent, not a cosigner of any shared address held by B).
2. A learns one of B's local addresses `ADDR` (e.g., from a leaked/observed prior interaction, QR code, or brute-forced deterministic shared-address derivation).
3. A sends B a `"sign"` justsaying: `{subject: "sign", body: {address: ADDR, signing_path: "r", unsigned_unit: {authors:[{address: ADDR, authentifiers:{...}}], messages:[...spending outputs attacker controls...]}}}`.
4. B's `handleMessageFromHub` resolves `ADDR` via `findAddress` to `ifLocal` (since B holds the key), and because the cosigner check is commented out, it proceeds straight to firing `signing_request` for the user to approve — with no verification that A had any right to request signing on `ADDR`.
