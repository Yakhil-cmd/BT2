## Finding

This confirms a real cross-tenant vulnerability in `StatusHandler`.

The base `Handler` class scopes lookups to the authenticated repository via `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), as used correctly by `CheckSuiteHandler` (`stacks.where(branch: …)`). [1](#0-0) [2](#0-1) 

`StatusHandler#process`, however, bypasses this scoping entirely and queries the global `Commit` table by bare `sha` with no repository/stack filter: [3](#0-2) 

The database schema confirms `sha` is only unique per `(sha, stack_id)`, not globally — the same SHA value is expected/allowed to exist across multiple stacks (e.g. forks sharing git history with an upstream repo): [4](#0-3) 

`verify_signature` in `WebhooksController` only checks the webhook signature against the organization owning the *sending* repository (`repository_owner` derived from the payload's own `repository.owner.login`), which correctly proves the attacker's own repo emitted the event — but it says nothing about which `Commit` rows the handler is allowed to touch: [5](#0-4) 

So the broken binding is: `Commit.where(sha: params.sha)` should be `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent, scoped to `Repository.from_github_repo_name(payload.repository.full_name)`), but it isn't — the handler writes a `Status` to every `Commit` row in the database matching that SHA, regardless of which stack/repo it belongs to.

Applying this to `add_status` in `commit.rb`: once a matching-SHA `Commit` in a victim stack receives a new `Status` row, `stack.schedule_merges` is invoked and `deployable_status`/`commit_status` hooks fire when state transitions occur, exactly the mechanism that drives auto-merge and continuous-deployment (`Deploy` creation) on the victim stack: [6](#0-5) 

**Exploit path**: An attacker who owns/forks a public repository sharing commit history with a victim's tracked repo (any fork relationship, or simply any two repos that happen to reach the same SHA, e.g., via a shared ancestor commit) can send a legitimately-signed `status` webhook from *their own* GitHub App/organization for a SHA that also exists as a `Commit` row in the victim's Shipit stack, with `context: codecov/project` (or any context the victim stack requires) and `state: success`. `StatusHandler` will apply this status to the victim's `Commit` too, since the query is unscoped by repository. If the victim stack is configured with `bot_login` (i.e., `Shipit.user`) and continuous deployment/merge is enabled and requires that status context, this can trigger `schedule_merges`/deploy scheduling that runs under the bot identity — an unauthorized deploy/merge triggered by a payload the victim repository never authenticated.

**Caveat/uncertainty**: I could not fully verify within this pass whether `Stack#schedule_merges` / auto-deploy machinery unconditionally deploys purely off `Status` presence versus requiring additional PR/merge-request state (i.e., whether a bare `Commit` with a matching status is sufficient to trigger a `Deploy`, or whether a `MergeRequest` must also exist and be attached). This affects whether the "ship" outcome is directly forced or only "unblocks" a pending merge request that also needs the SHA to be a real open PR against the victim repo. Either way, the cross-tenant write of `Status` records (a record written for a repository that did not authenticate it) is a confirmed, code-level bug regardless of the full downstream deploy consequence.

### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up `Commit` records by bare SHA with no repository scoping, unlike sibling handlers (e.g. `CheckSuiteHandler`) which correctly scope via `stacks`. Because `sha` is only unique per `(sha, stack_id)` in the schema, an attacker who controls a webhook-signed event for their own (e.g. forked) repository can inject a `Status` onto a `Commit` belonging to an unrelated victim stack that happens to share the same SHA.

### Finding Description
Broken binding: `Status.created_for(commit) == Status.created_for(commit WHERE commit.stack.repository == authenticated_repository)` should hold but does not. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, with no join/filter on the stack or repository that the request's signature actually authenticated (`verify_signature` only proves the *sender's own* repo/org signed the payload). The unique index `(sha, stack_id)` on `commits` proves the schema anticipates the same SHA existing in multiple stacks. An attacker can therefore send a validly-signed `status` webhook from their own controlled repository for a shared SHA (e.g. shared git history via fork) with `context: "codecov/project"`, and the handler writes a new `Status` to the victim's `Commit` row, feeding into `Commit#add_status`, which invokes `stack.schedule_merges` and emits `deployable_status`/`commit_status` hooks that drive continuous deployment/merge scheduling on the victim stack — potentially executed under the stack's configured `bot_login` identity.

### Impact Explanation
A payload authenticated for one repository is used to mutate `Commit`/`Status` state belonging to a different repository's stack, which can unblock or trigger `schedule_merges`/deploy scheduling on that victim stack. This matches "a payload for one repository mutating another's stack/commit" and potentially "an unauthorized deploy, rollback or merge," repeatable against any stack whose commits share a SHA with a repo the attacker controls (most naturally, forks).

### Likelihood Explanation
Requires: (1) attacker owns/controls a repository capable of emitting a legitimately-signed `status` webhook (trivial — attacker's own GitHub repo/fork), (2) a SHA collision in the literal git sense — i.e., shared commit history (forks trivially satisfy this for ancestor commits), (3) the victim stack requiring the specific status context and having continuous deployment/merge and `bot_login` configured. Preconditions 1–2 are cheap and common (forking is unrestricted); precondition 3 depends on victim configuration.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring `CheckSuiteHandler`: iterate over `stacks.flat_map(&:commits).where(sha: params.sha)` (or join `Commit` through `Stack`/`Repository` matching `payload.dig('repository','full_name')`) instead of the global unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or controller test):
1. Create two `Repository`/`Stack` pairs: `attacker/repo` and `victim/repo` (victim stack has `bot_login` set / `continuous_deployment: true`, and `required_statuses` including `codecov/project`).
2. Create `Commit` rows with the identical `sha` value `"deadbeef..."` in both stacks (simulating shared fork history).
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"` (so `verify_signature`/`repository_owner` succeeds against the attacker's org secret), `sha: "deadbeef..."`, `context: "codecov/project"`, `state: "success"`.
4. POST to `/webhooks` with `X-Github-Event: status` and a valid signature for `attacker/repo`'s org.
5. Assert: `victim_stack.commits.find_by(sha: "deadbeef...").statuses.where(context: "codecov/project").exists?` is `true`, and/or `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack])` fires — proving the victim stack's commit was mutated by a webhook that only authenticated `attacker/repo`.
6. Equality to test: `commit_scoped_to_authenticated_repo? (victim_commit) == false` while `status_written_to(victim_commit) == true`, demonstrating the invariant "a status for `codecov/project` only affects the repository that authenticated it" is violated.

      end
      new_status
