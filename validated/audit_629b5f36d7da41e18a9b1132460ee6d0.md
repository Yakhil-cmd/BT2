### Title
`liquidate-multi` batch DoS via unhandled `unwrap-panic` on missing index cache for uninvolved debt assets - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` documents that "Failed liquidations return error codes but don't revert entire batch" [1](#0-0) . In practice, a single malformed entry in the batch — one whose `debt-ft` does not correspond to an asset the targeted `borrower` actually has debt in — causes an unhandled `unwrap-panic` runtime abort inside `scale-debt-for-liquidation`, which aborts the *entire* atomic transaction rather than returning an isolated error for that position, exactly as the Gloas fix addressed a crash triggered by processing an item that was never populated ("non-custody columns") instead of being skipped/handled gracefully.

### Finding Description
`liquidate` accrues and caches vault indexes only for the assets the borrower currently holds debt/collateral in:
```
(u-debt (accrue-user-debts (get debt pos-full)))
(u-coll (accrue-user-collateral (get collateral pos-full)))
``` [2](#0-1) 

`debt-aid` is derived from the caller-supplied `debt-ft` parameter, independent of what the borrower's `pos-full` actually contains:
```
(debt-address (contract-of debt-ft))
(debt-asset (try! (get-asset debt-address)))
(debt-aid (get id debt-asset))
``` [3](#0-2) 

Later, `scale-debt-for-liquidation` unconditionally does:
```
(borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
``` [4](#0-3) 

`get-cached-indexes` only returns `some` if `accrue-and-cache`/`vault-accrue` was already called for that `(stacks-block-time, aid)` pair in this transaction [5](#0-4) . If `debt-aid` was never part of `(get debt pos-full)`, the cache entry is never written, so `get-cached-indexes` returns `none` and `unwrap-panic` triggers a runtime abort — not a `(err ...)` response — before any of the graceful `asserts!` checks at the end of `liquidate` are even reached (e.g. `ERR-ZERO-LIQUIDATION-AMOUNTS`) [6](#0-5) .

`liquidate-multi` invokes `liquidate` directly (via `call-liquidate`) inside a `map`:
```
(define-public (liquidate-multi (positions ...))
  (ok (map call-liquidate positions)))
``` [7](#0-6) 

Because `call-liquidate` calls `liquidate` as an ordinary function (not wrapped in a mechanism that converts a runtime panic into an `(err ...)` value), a panic in *any single* list element aborts the whole Clarity transaction, unwinding every other position's liquidation in the same batch — even ones that were perfectly valid and would otherwise have succeeded.

### Impact Explanation
- **Attacker**: any account that can influence or supply an entry in a `liquidate-multi` positions list with a `debt-ft` that does not match one of the target borrower's real debts (a trivial, always-available action — no privileged access or race condition needed).
- **Victim**: the other, legitimate liquidation entries batched in the same `liquidate-multi` call — and, transitively, the borrowers whose unhealthy positions should have been liquidated and the suppliers of the affected vaults, since a delayed liquidation lets an unhealthy position deteriorate further, increasing bad-debt/socialization risk to all suppliers of that asset pool.
- **Shared state**: the `index-cache` map keyed by `(stacks-block-time, aid)`, which is populated based on the *borrower's* debt list, not the caller-specified `debt-ft`, and is then blindly trusted via `unwrap-panic` deeper in the call.

Without the bug: each position in `liquidate-multi` is evaluated independently; a bad entry returns an `err` for that slot while the rest of the list still succeeds (as documented). With the bug: a single malformed/malicious entry aborts the whole transaction, so liquidators cannot batch multiple unhealthy positions reliably, and any hostile or accidental inclusion of a mismatched `debt-ft` becomes a griefing vector that blocks liquidation of otherwise-liquidatable positions bundled in the same call — a temporary freezing of the liquidation mechanism for third parties' positions.

### Likelihood Explanation
High reproducibility: no special timing, front-running, or privileged role is required — simply passing a `debt-ft` for an asset the borrower has zero debt in reliably triggers the `unwrap-panic`, because `accrue-user-debts` never touches that asset's cache slot. Any keeper/bot aggregating multiple borrower liquidations into a single `liquidate-multi` call is exposed to one bad/malicious entry poisoning the whole batch.

### Recommendation
Replace the `unwrap-panic (get-cached-indexes asset-id)` in `scale-debt-for-liquidation` (and the equivalent calls at the "remaining debt" and "other debt repayable" computations) with an explicit accrual/cache-population step for `debt-aid` regardless of whether it's already in the borrower's debt list (e.g., call `accrue-and-cache debt-aid` unconditionally before scaling), or return a graceful `(err ERR-...)` instead of panicking when the cache entry is absent, so a single bad batch entry cannot abort the transaction.

### Proof of Concept
1. Borrower B has debt only in `USDC` and collateral in `STX`; B's LTV is above `ltv-liq-partial`.
2. Liquidator constructs `liquidate-multi` with two entries:
   - Entry 1: valid liquidation of B using `debt-ft = USDC` (would succeed).
   - Entry 2 (attacker-supplied or accidental): a call targeting B (or any other liquidatable borrower) but with `debt-ft = USDH`, an asset B holds no debt in.
3. `call-liquidate` on entry 2 calls `liquidate`; `accrue-user-debts` never populates the cache for `USDH` because it isn't in B's `(get debt pos-full)`.
4. `scale-debt-for-liquidation` calls `(unwrap-panic (get-cached-indexes USDH-aid))`, which is `none`, causing a runtime panic.
5. The panic aborts the entire `liquidate-multi` transaction, reverting entry 1's otherwise-valid liquidation along with it, despite the function's documented "don't revert entire batch" guarantee.
