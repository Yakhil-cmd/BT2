### Title
KLAY Bridge Transfer Permanently Blocked by Non-Payable Recipient — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer()` in the service-chain bridge delivers native KAIA to the recipient `_to` via a raw `.call.value()`. If `_to` is a contract that reverts on ETH receipt, the `require(ok, ...)` guard rolls back the entire transaction — including all nonce-accounting state — making the nonce permanently undeliverable and locking the corresponding KAIA in the bridge forever.

---

### Finding Description

`handleKLAYTransfer()` performs all state mutations (nonce bookkeeping, vote closure, tx-hash marking) and then attempts the native transfer at the very end:

```solidity
// BridgeTransferKLAY.sol lines 81-99
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");   // ← reverts everything above
``` [1](#0-0) 

Because Solidity reverts all state changes on a failed `require`, every mutation — `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, `_updateHandleNonce`, and the vote recorded by `_voteValueTransfer` — is rolled back. Operators can retry, but every attempt will revert identically.

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting from `lowerHandleNonce`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) { ... }
lowerHandleNonce = i;
``` [2](#0-1) 

Because `handleNoncesToBlockNums[stuck_nonce]` is never written (always reverted), `lowerHandleNonce` is permanently frozen at the stuck nonce. There is no owner/operator function to skip a nonce or redirect delivery to a different address.

The same pattern exists in `_payKLAYFeeAndRefundChange()` in `BridgeFee.sol`, where a non-payable `feeReceiver` contract would block every KLAY bridge request:

```solidity
(bool ok, ) = feeReceiver.call.value(fee)("");
require(ok, "transfer fee failed");
``` [3](#0-2) 

---

### Impact Explanation

- **Unauthorized asset lock**: KAIA sent from the source chain is consumed (locked in the source bridge or burned in mint/burn mode) but can never be delivered on the destination chain. The funds are permanently stranded with no recovery path.
- **Bridge nonce corruption**: `lowerHandleNonce` is frozen at the stuck nonce. The off-chain bridge manager's `recoveryBlockNumber` never advances past that point, causing the recovery/monitoring subsystem to loop indefinitely over the same failed nonce.
- **Scope**: Matches "Unauthorized transfer … affecting KAIA, bridged assets, or system-managed funds" and "Persistent corruption of … state … that breaks … withdrawals, transfers, or settlement."

---

### Likelihood Explanation

Low-to-medium. Any user who specifies a `_to` address that is a contract without a `payable` fallback (e.g., a multisig, a DAO treasury, or a deliberately crafted griefing contract) triggers this path. The user controls `_to` freely via `requestKLAYTransfer(address _to, ...)` on the source chain. No special privilege is required. [4](#0-3) 

---

### Recommendation

1. **Pull-over-push for `handleKLAYTransfer`**: Instead of pushing KAIA to `_to` inside the operator-called function, record the pending withdrawal in a mapping and let `_to` claim it via a separate `withdraw()` function. This decouples nonce advancement from delivery success.

2. **Soft-fail delivery**: If the push fails, store the amount in a `pendingWithdrawals[_to]` mapping and emit an event, but do not revert. Nonce accounting proceeds normally.

3. **Apply the same fix to `_payKLAYFeeAndRefundChange`**: Both the `feeReceiver` transfer and the `msg.sender` refund transfer should use pull-payment or soft-fail patterns. [5](#0-4) 

---

### Proof of Concept

```
1. Deploy a "GriefRecipient" contract on the destination chain with no payable fallback
   (any receive() that does `revert()`).

2. On the source chain, call:
     bridge.requestKLAYTransfer{value: 1 ether}(griefRecipient, 1 ether, "");
   This emits RequestValueTransfer with requestNonce = N and locks 1 KAIA in the source bridge.

3. On the destination chain, operators call:
     bridge.handleKLAYTransfer(txHash, from, griefRecipient, 1e18, N, blockNum, "");
   - _voteValueTransfer(N) returns true (threshold met).
   - _setHandledRequestTxHash, handleNoncesToBlockNums[N], _updateHandleNonce all execute.
   - griefRecipient.call{value: 1e18}("") → reverts.
   - require(ok, ...) → entire tx reverts; all state rolled back.

4. Every subsequent operator retry for nonce N reverts identically.

5. handleNoncesToBlockNums[N] is never set → lowerHandleNonce stays at N forever.

6. The 1 KAIA is permanently locked in the destination bridge with no admin escape hatch.
```

        uint256 fee = feeOfKLAY;
