### Title
Webhook signature is verified against the attacker-controlled `repository.owner.login` org while handlers act on the (unbound) `repository.full_name` in the same payload, allowing cross-organization spoofed events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login` straight out of the untrusted, attacker-supplied JSON body, then verifies the signature over the *whole* raw body with that org's secret. Nothing binds the org used for signature verification to the `repository.full_name` that the webhook handlers subsequently act on. In a multi-organization Shipit deployment (`Shipit.github_organizations` / per-org `webhook_secret` in `secrets.github`), an attacker who legitimately controls one onboarded organization (and therefore knows/controls that org's webhook secret via their own GitHub App/webhook config) can sign a payload that declares `repository.owner.login` as their own org (so it passes `verify_webhook_signature`) while setting `repository.full_name` to any other onboarded `owner/repo`, causing handlers such as `PushHandler` to act on a stack that belongs to a different organization entirely.

### Finding Description
`verify_signature` computes the verifying app from attacker-controlled data before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp`/`webhook_secret` per organization key in `secrets.github`, and `github_organizations` exposes that multi-tenant list: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only checks the signature against `webhook_secret`, i.e. whichever secret was selected for `repository_owner`: [4](#0-3) 

Once the signature check on the selected org's secret passes, `create` dispatches the *entire raw payload* to handlers, using the payload's own `repository.full_name` (not `repository_owner`) to locate the target stack/repository: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality the engine implicitly assumes is:
`organization authenticated (repository.owner.login, used to pick webhook_secret)` == `organization whose repository is written (repository.full_name, used to pick the Stack/Repository)`.

Nothing in `verify_signature`, `Handler#repository_name`, or `Repository.from_github_repo_name` enforces that equality — `repository.owner.login` and the owner segment of `repository.full_name` are independent JSON fields inside the same signed body, and only the signature-selection field is checked against org identity: [8](#0-7) 

This is analogous to the reported OpenSSL `X509::Name#==` bug in that a verification routine is trusted to bind two values that it never actually compares — here the "verified organization" and the "acted-upon repository" are two different fields, and the code silently assumes they match.

### Impact Explanation
If exploitable, this breaks the trust boundary between tenants of a multi-organization Shipit instance: an attacker who is a legitimate member/admin of Organization A (and thus can configure Organization A's own webhook secret in `secrets.github`) could forge webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) that name Organization B's repository in `repository.full_name`, triggering `GithubSyncJob`, commit `Status` creation, `check_suite` refreshes, or review-stack archive/unarchive actions for a repository/stack they do not own. This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope, and could lead to spoofed CI status or unauthorized sync/state changes on another organization's stack.

### Likelihood Explanation
Exploitability is conditional on the host application being configured with multiple organizations under `secrets.github` (the multi-tenant schema described by `github_default_organization`/`github_organizations`), and on the attacker being a legitimate operator of at least one of those onboarded organizations. I was not able to fully verify from the indexed code whether typical Shipit deployments run in this multi-org mode by default, or whether additional authorization checks exist elsewhere (e.g., at the reverse-proxy/GitHub App installation level) that would prevent an attacker's own org's webhook deliveries from reaching this endpoint with a different org's repository claimed. This should be validated further, ideally with a full Devin session that can inspect deployment/config examples and any additional binding checks not captured by the indexed subset of `app/**` and `lib/shipit/**`.

### Recommendation
In `WebhooksController#verify_signature` (or in each `Handler`), after successfully verifying the signature for `repository_owner`, additionally verify that the owner segment of `repository.full_name` (and/or `organization.login` for org-scoped events) matches the `repository_owner`/org used to select the webhook secret, rejecting the request (422) on mismatch. This closes the gap between "org whose secret verified the signature" and "org whose repository the payload claims to mutate."

### Proof of Concept
Given a multi-org `secrets.github` config with orgs `attacker-org` and `victim-org`, each with distinct `webhook_secret`s:
1. Attacker crafts a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` — a secret they legitimately possess for their own org.
3. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and `verify_webhook_signature` succeeds because the signature really was produced with that org's secret.
4. `create` parses the same body and calls `PushHandler`, which resolves `repository_name` from `repository.full_name == "victim-org/victim-repo"` [6](#0-5)  and triggers `stack.sync_github` for the victim's stack [9](#0-8) , despite the signature only proving authenticity for `attacker-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
