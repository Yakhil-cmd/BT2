### Title
Webhook signature check binds to attacker-chosen `repository.owner.login`, letting an org with no `webhook_secret` forge events for any tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to validate a webhook against using a value taken directly from the unauthenticated request body, while the event handlers that actually act on the payload use a *different* field (`repository.full_name`) from the same unverified body to decide which `Repository`/`Stack` to mutate. If any configured organization has no `webhook_secret` set, signature verification for that organization is a no-op, breaking the intended binding "organization whose secret authenticated this request" == "repository that gets written to."

### Finding Description
`verify_signature` picks the app config using a value read straight out of `params`, which Rails has already parsed from the raw, unauthenticated request body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` is a trivial bypass when that organization's `webhook_secret` is blank/unset: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Multi-org Shipit installations are documented and supported (`secrets.yml` can configure several GitHub Apps, one per org), each with its own optional `webhook_secret`: [4](#0-3) 

The event handlers, however, do not use `repository_owner`/the org that was used to select the verifying secret — they resolve which repository/stack to act on from `payload.dig('repository', 'full_name')`: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because both `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to pick the target repository) come from the same single unauthenticated JSON body, and because the selection of which org's secret guards the request is attacker-influenced, an attacker who knows (or guesses) that one configured organization has no `webhook_secret` set can craft a payload where `repository.owner.login` names that unsecured org while `repository.full_name` names a completely different, secured stack's repository. `verify_signature` will pick the unsecured org's `GitHubApp`, `verify_webhook_signature` returns `true` unconditionally (no secret to check against), and the request proceeds to `create`, which dispatches the (fully attacker-controlled) payload to handlers such as `PushHandler` and `StatusHandler` acting on the victim repository: [6](#0-5) [7](#0-6) 

`PushHandler` triggers `stack.sync_github(expected_head_sha: ...)`, which enqueues `GithubSyncJob` (re-validated against the real GitHub API before appending commits, limiting damage there), but `StatusHandler` directly writes attacker-supplied `state`/`description`/`context` as a `CommitStatus` for any commit whose sha is supplied, without any live GitHub API check — this is a direct forged write into another stack's commit/CI status data, which downstream deploy-safety logic (`release_status?`, CI gating) can consult.

This is the analog of the report's core bug class: a value the verification step is bound to (`repository_owner`, used to pick the secret) is *not* the value that ends up governing what gets mutated (`repository.full_name`), so updating/relying on one field's "trust" does not protect the other field's effect — directly matching the "organization that authenticated versus the repository that is written" binding named in scope.

### Impact Explanation
An attacker who can identify (through misconfiguration, defaults, or leaked secrets.yml templates showing `webhook_secret: nil`) an installation with at least one organization lacking a `webhook_secret` can forge webhook deliveries claiming to originate from that org while acting on any other tracked repository in the same Shipit instance. This allows cross-repository writes of commit statuses (`StatusHandler`) and can trigger `GithubSyncJob` for unrelated stacks (`PushHandler`) without holding any GitHub credentials for the targeted repository, no `ApiClient` token, and no Shipit session — satisfying the required "cross-repository writes" / "unauthorized" impact bar.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, and (2) at least one configured organization with `webhook_secret` unset — a state explicitly shown as valid/example configuration in this repo's own `secrets.development.example.yml` and referenced as optional in `docs/setup.md`. Given that webhook secret configuration is per-org and easy to omit accidentally (especially during incremental onboarding of new orgs), this is a plausible, low-effort misconfiguration for an attacker to exploit once discovered, requiring no privileged access.

### Recommendation
- Verify the webhook signature using the organization/app whose secret must match, and derive the acting scope (`Repository`/`Stack` lookup in handlers) from the *same* verified identity — do not let handlers key off a different, independently-controlled payload field (`repository.full_name`) than the one used to select the verifying secret.
- Cross-check that the resolved `Repository`'s owner matches the `repository_owner` value that was used to select the `GitHubApp`/secret before dispatching to handlers.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; either require a secret for every configured organization or explicitly reject/flag such organizations as unauthenticated instead of implicitly trusting all their traffic.

### Proof of Concept
1. Shipit is configured with two orgs: `secure-org` (has `webhook_secret` set) and `open-org` (webhook_secret left blank, e.g. per the example config).
2. Attacker sends a POST to `/github/webhooks` (or engine-mounted webhook path) with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha in secure-org/some-repo>",
  "state": "success",
  "context": "ci/tests",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/some-repo"
  }
}
```
No `X-Hub-Signature` header, or an arbitrary one, is needed.
3. `verify_signature` computes `repository_owner == "open-org"`, calls `Shipit.github(organization: "open-org")`, and `verify_webhook_signature` returns `true` immediately because `open-org`'s `webhook_secret` is blank.
4. `create` dispatches the payload to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` (a commit belonging to `secure-org/some-repo`) and calls `commit.create_status_from_github!(params)`, writing a forged "success" status for a repository the attacker has no access to and whose org's secret was never checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
