### Title
NULL Pointer Dereference in `handleOnlinePrivatePayment` when a private-payment chain element is missing its `payload` object - (File: network.js)

### Summary
The reported CVE-2022-25867 describes a NULL pointer dereference in `socket.io-client-java` when parsing a packet with an invalid payload format — a client crashes because it dereferences a field of a packet without first checking that the packet payload has the expected structure. Ocore's private-payment handling path has an analogous pattern: `network.handleOnlinePrivatePayment` immediately dereferences `arrPrivateElements[0].payload.denomination` without first verifying that `.payload` is a non-empty object, before any of the structural validation that later functions perform.

### Finding Description
`network.handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` only checks that `arrPrivateElements` is a non-empty array: [1](#0-0) 
It then immediately accesses `arrPrivateElements[0].payload.denomination` to compute `output_index`, without validating that `arrPrivateElements[0].payload` exists or is an object. If `payload` is `undefined`/`null`/a primitive, this throws a `TypeError: Cannot read properties of undefined (reading 'denomination')`.

The safety of this code currently relies entirely on the caller pre-validating the shape of each chain element. The known caller in `wallet.js`, `handlePrivatePaymentChains`, does perform this check before calling into the network layer: [2](#0-1) 
However, `handleOnlinePrivatePayment` is a shared/exported entry point in `network.js` invoked from multiple call sites (`wallet.js` and `network.js` itself, confirmed by the presence of 5 and 3 call sites respectively). It is architecturally a single choke point that different message-handling code paths funnel into, and it does not itself defend against a malformed `payload` field — unlike `parsePrivatePaymentChain` in `indivisible_asset.js`, which explicitly checks `!objPrivateElement.payload` before dereferencing: [3](#0-2) 
and unlike `private_payment.js`'s `validateAndSavePrivatePaymentChain`, which also checks `!headElement.payload` first: [4](#0-3) 

This means `handleOnlinePrivatePayment` is the one place in the private-payment pipeline that assumes payload-shape validation has already happened elsewhere, rather than enforcing it locally — the same root-cause pattern as the CVE (dereferencing fields of an attacker-supplied packet/message before confirming the payload format is valid).

### Impact Explanation
An unhandled `TypeError` thrown synchronously inside a `justsaying`/message-handling callback in a Node.js event-loop application is not caught by any wrapping `try/catch` in `onWebsocketMessage`'s dispatch path for `handleJustsaying`, so it can propagate as an uncaught exception and crash the node process (denial of service for that node/wallet). Because private payments are a core wallet/private-chain feature reachable by any private-payment counterparty (device correspondent) sending malformed chain data, this could be used to repeatedly crash a targeted wallet/hub-connected node, disrupting normal operation and payment processing (availability impact), matching the CVSS profile of the underlying advisory (`C:N/I:N/A:H`).

### Likelihood Explanation
Exploitability depends on whether any live call path actually reaches `handleOnlinePrivatePayment` without first passing through a validator that checks `payload` (like `handlePrivatePaymentChains`'s `.every(...)` guard). Based on available context, I could not fully confirm all 3 call sites within `network.js` itself and whether any of them skip that upstream validation — this requires reading the full call sites in `network.js` (only partial context was retrieved due to tool-call limits, and I did not get to inspect the 3 in-file callers of `handleOnlinePrivatePayment` in `network.js` before running out of iterations). If such a path exists, the likelihood is high given it requires only a single malformed device message from a paired/private-payment counterparty. If all call paths are properly guarded by validators like `handlePrivatePaymentChains`, this is a defense-in-depth gap rather than a directly reachable vulnerability.

### Recommendation
Add an explicit guard at the top of `handleOnlinePrivatePayment` (and in general, at every function that receives untrusted `arrPrivateElements`) verifying `isNonemptyObject(arrPrivateElements[0].payload)` before touching `.denomination` or any other payload field, returning `callbacks.ifError(...)` on failure — mirroring the defensive checks already present in `indivisible_asset.js`'s `parsePrivatePaymentChain` and `private_payment.js`'s `validateAndSavePrivatePaymentChain`.

### Proof of Concept
1. As a paired device/private-payment counterparty, send a `hub/message` (or equivalent private_payments message) whose `body.chains` contains a chain array element with `unit` and other required top-level string fields set, but with `payload` set to `null` or omitted, targeting a code path that reaches `network.handleOnlinePrivatePayment` directly without going through `handlePrivatePaymentChains`'s `.every(e => isNonemptyObject(e.payload) ...)` guard.
2. `handleOnlinePrivatePayment` executes `arrPrivateElements[0].payload.denomination` at network.js:2382, throwing `TypeError: Cannot read properties of null (reading 'denomination')`.
3. If uncaught, this crashes the receiving node process, denying it the ability to process further payments/units until restarted.

**Caveat**: I was unable to fully verify, within the available tool budget, whether every call path to `handleOnlinePrivatePayment` is protected by an upstream shape-validator equivalent to `handlePrivatePaymentChains`. This should be confirmed by reviewing all in-file (`network.js`) callers of `handleOnlinePrivatePayment` before treating this as a confirmed, directly-exploitable vulnerability rather than a defense-in-depth gap.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
