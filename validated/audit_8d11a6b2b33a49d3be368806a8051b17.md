### Title
`repository_owner` (used to select the webhook secret) can diverge from `repository.full_name` (used to select the target stack) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the request with `repository_owner`, which reads `params.dig('repository','owner','login')` and falls back to `params.dig('organization','login')` only when the nested `owner` key is missing. `Handler#repository_name` (used by every event handler, e.g. `PushHandler`) independently re-reads `payload.dig('repository','full_name')` from the same raw body, with no cross-check that the two point at the same GitHub organization/repository.

### Finding Description
Binding claimed: `repository_owner` (org whose secret validated the signature) == owner of `repository.full_name` (the repo the handler acts on). Trace:

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to fetch `Shipit.github(organization: repository_owner)` and call `verify_webhook_signature` [2](#0-1) .
- `verify_webhook_signature` HMACs the raw body against the secret configured for that org, and explicitly returns `true` if no secret is configured for that org (`return true unless webhook_secret`) [3](#0-2) .
- On `#create`, the same raw JSON is dispatched to handlers, and `Handler#repository_name` reads `payload.dig('repository','full_name')` completely independently to select the target `Repository`/`Stack` [4](#0-3) . `PushHandler#process` then calls `stack.sync_github` for every non-archived stack on the matched branch [5](#0-4) .

Nothing enforces `params.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first`, nor that the fallback `organization.login` matches `repository.full_name`'s owner. A crafted body can omit `repository.owner` while still including `repository.full_name` pointing at any tracked repo, and supply a top-level `organization.login` naming a different, weakly-configured org. `verify_signature` then authenticates the request against that other org's secret (or unconditionally, if that org has no `webhook_secret` set at all), while the handler acts on the victim repository named in `repository.full_name`.

Existing tests confirm this is exactly how the code behaves: the "unknown github organization" test sets `repository.owner.login` to derive `repository_owner` for verification purposes only, and the "membership" tests separately supply `organization.login` merged with `repository.owner.login: 'shopify'` via `repository_params` [6](#0-5) , but there is no test (or code) that ever validates the two fields agree with each other when both are attacker-controlled.

None of the listed guards close this gap: `drop_unhandled_event` only checks event-type registration, `ExplicitParameters` (`PushHandler.params`) only validates presence of `ref`/`after`, and `Repository.from_github_repo_name` merely looks up whatever `full_name` string is given [7](#0-6)  — none of them re-derive or compare against `repository_owner`.

### Impact Explanation
If any organization registered in `Shipit.github` config has no `webhook_secret` configured (a real, documented fallback path in `verify_webhook_signature`), or if the attacker otherwise possesses a valid secret for *any* tracked organization, they can submit a `push` (or other) webhook body naming that weak org in `organization.login`, omit `repository.owner`, and set `repository.full_name` to an arbitrary victim repo. `PushHandler` will trigger `stack.sync_github` on the victim stack — a cross-tenant action triggered by a payload that never authenticated against the victim's own secret. This matches "a payload for one repository mutating another's stack" under the Critical category. Blast radius is any stack under any repository tracked by the Shipit instance, repeatable per request, limited only by discoverability/existence of a mis-configured or attacker-controlled org entry in the multi-org Shipit config.

### Likelihood Explanation
Exploitation requires: (1) the Shipit deployment to configure `github_apps` for multiple organizations (multi-tenant setup), and (2) at least one of those orgs to have a blank/no `webhook_secret`, or the attacker to know a valid secret for some tracked org other than the victim's. Without such a misconfiguration or leaked secret, the attacker cannot pass `verify_webhook_signature` for any org and the attack fails. This is a real but conditional weakness — the vulnerable *code path* exists unconditionally, but real-world exploitability depends on operator-side multi-org configuration choices (e.g., a demo/staging org left with no secret, or an org intentionally left "open").

### Recommendation
Do not derive `repository_owner` and the handler's target repository independently from an untrusted body. Verify the signature using a scheme that does not vary by attacker-controlled fields, or enforce that `payload.dig('repository','owner','login')` (or its derivation from `full_name`) exactly matches the org actually used for verification before dispatching to handlers. At minimum, remove the `organization.login` fallback for signature verification, and reject requests where `repository.owner.login` is absent but `repository.full_name` is present, since these two fields should always co-occur in genuine GitHub payloads for repository-scoped events.

### Proof of Concept
```ruby
test "signature verified under org A must not authorize handler to act on org B's repository" do
  request.headers['X-Github-Event'] = 'push'
  # 'weak-org' has no webhook_secret configured in test github_apps config (or is stubbed to return true)
  Shipit.github(organization: 'weak-org').stubs(:verify_webhook_signature).returns(true)

  body = {
    organization: { login: 'weak-org' },     # verified org (repository_owner fallback)
    repository: { full_name: @stack.repository.full_name }, # no owner.login key -> victim stack, mismatched org
    ref: "refs/heads/#{@stack.branch}",
    after: 'deadbeef'
  }.to_json

  # Binding under test:
  #   repository_owner  == 'weak-org'
  #   owner_of(repository.full_name) == @stack.repository.owner (different org)
  assert_not_equal 'weak-org', @stack.repository.owner

  Stack.any_instance.expects(:sync_github).with(expected_head_sha: 'deadbeef')
  post :create, body:, as: :json
  assert_response :ok
end
```
This demonstrates the request is authenticated under `weak-org`'s secret while `PushHandler` acts on a stack belonging to a different, unrelated organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
