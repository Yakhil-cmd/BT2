### Title
Malformed PEM/DER Public Key Parsing in `is_valid_sig`/`vrf_verify` Allows AA-Reachable Crash / Signature-Check Corruption - (File: `signature.js`)

### Summary
CVE-2019-8536 is a WebKit memory-corruption bug triggered by processing maliciously crafted content. The closest reachable analog in ocore is `signature.js`'s hand-rolled ASN.1/DER parser for PEM public keys, invoked by the oscript functions `is_valid_sig` and `vrf_verify` in `formula/evaluation.js`. This code path is reachable by any unprivileged AA trigger sender (or unit author whose address definition embeds an oscript-style check), since `pem_key` is fully attacker-controlled trigger data.

### Finding Description
`validateAndFormatPemPubKey` in `signature.js` manually walks a base64-decoded, attacker-supplied buffer, indexing into it based on length bytes taken from the same untrusted buffer: [1](#0-0) 
It reads `contentAloneBuffer[1]`, `[2]`, `[3]`, `[4]`, `[5]` and computes `identifiersStart`/`identifiersLength` purely from attacker data, with only a handful of allowed length values checked (`13,16,19,20`) — but no check that `identifiersStart + identifiersLength` stays within `contentAloneBuffer.length` before later slicing on `contentAloneHex`.

`verifyMessageWithSecp256k1PemPubKey` performs similar unchecked offset arithmetic, locating a byte pattern via `der.indexOf(...)` and then slicing at fixed offsets relative to that index without validating the found index is not too close to the buffer's end: [2](#0-1) 

This is reachable end-to-end through oscript: [3](#0-2) 
`pem_key`, `message`, and `signature` are all evaluated directly from trigger/message data with only string-type and length checks (`ValidationUtils.isNonemptyString`, `<1024` chars) — no structural validation before being handed to `signature.validateAndFormatPemPubKey`.

Because Node.js `Buffer` indexing/`slice` beyond bounds does not corrupt memory (it returns `undefined`/truncated buffers rather than crashing), the "memory corruption" analog does not manifest as true OOB memory access in this JS codebase. What is concretely reachable is: (a) malformed/truncated PEM content causing `contentAloneBuffer[n]` to be `undefined`, producing `NaN`-driven or incorrect `identifiersLength`/`hex_pub_key_length` comparisons that either throw uncaught exceptions inside AA/formula evaluation, or (b) succeed in slicing garbage bytes that happen to satisfy the loose identifier/length checks, causing `crypto.createVerify`/`ecdsaVerify` to be invoked with attacker-shaped key material. I could not, within the given time, construct or confirm a concrete case where this parsing confusion causes `verifyMessageWithPemPubKey`/`verifyMessageWithSecp256k1PemPubKey` to return `true` for a forged signature — the surrounding `objSupportedPemTypes`/`objSafePemTypes` hex-identifier equality check and the underlying crypto library's own signature verification act as a backstop. Absent a demonstrated verification bypass, this reduces to a best-effort code-quality concern (unchecked buffer indexing) rather than a confirmed exploitable vulnerability.

### Impact Explanation
If a concrete parsing confusion could be shown to make `is_valid_sig`/`vrf_verify` return `true` for an unauthenticated signer, this would let an attacker satisfy an AA's or address definition's authentication condition without possessing the private key, leading to unauthorized fund release from an AA or unauthorized spending. However, I was not able to prove this outcome; the actual cryptographic verification is still delegated to Node's `crypto`/`secp256k1` module, which would independently reject a forged signature over the real message. The more plausible impact is an uncaught exception thrown deep in `validateAndFormatPemPubKey` when indices run out of bounds on malformed input, which — if not caught by the calling `evaluate()`/`validateFormula()` error-handling wrappers — could cause a full node crash while processing an untrusted AA trigger unit (a denial-of-service against MC-wide validation), rather than fund loss or double-spend.

### Likelihood Explanation
`is_valid_sig` and `vrf_verify` are ordinary oscript functions callable by any AA definition and reachable by any unprivileged party who can send a trigger to that AA, or by anyone who posts a unit invoking a formula-based address definition that uses these functions. The `pem_key` string is fully attacker-controlled, and the parsing logic performs several unchecked out-of-range indexing operations before any cryptographic library call. However, no confirmed corruption or authentication bypass was demonstrated in this analysis, and the try/catch wrapping at the top of `validateAndFormatPemPubKey`'s callers (`verify()`, `is_valid_sig` handler) may already absorb thrown errors in most paths, reducing likelihood of the DoS materializing.

### Recommendation
Add explicit bounds checks (`contentAloneBuffer.length >= identifiersStart + identifiersLength + 8`, etc.) before all offset-based reads/slices in `validateAndFormatPemPubKey` and `verifyMessageWithSecp256k1PemPubKey`, and wrap the entire PEM-parsing routine in try/catch that returns a validation error rather than propagating exceptions into AA/unit validation flow, consistent with how `chash.isChashValid` already guards its `Buffer.from`/decode calls.

### Proof of Concept
Not conclusively constructed. A minimal PoC would need to supply `trigger.data.pem_key` as a short/truncated base64 string (e.g., decoding to fewer than 6 bytes, or with `contentAloneBuffer[1] == 0x82` but total length < 6) via `is_valid_sig(message, pem_key, signature)` in an AA formula, then observe whether `validateAndFormatPemPubKey` throws an unhandled exception during `mci`-based AA validation. This was not executed against a live node in this analysis; further dynamic testing (via `test/pem_sig.test.js` harness with intentionally truncated/malformed DER inputs) would be required to confirm concrete unhandled-exception or bypass behavior.
