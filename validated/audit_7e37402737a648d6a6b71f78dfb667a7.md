### Title
Unbounded attestor array in `attested` address-definition op skips complexity accounting, enabling a cheap definition that costs every validating node excessive CPU per use - (File: definition.js)

### Summary
`ERC721Pool.initialize()`'s unbounded `for` loop over attacker-supplied `tokenIds_` shows the general bug class: a user-controlled array is iterated with no size cap, so cost scales linearly with attacker-chosen input and can exceed the resource budget of whoever must process it. In ocore the analogous resource budget is the oscript definition-evaluation "gas meter" — `complexity`/`count_ops`, capped by `constants.MAX_COMPLEXITY`/`constants.MAX_OPS` in `definition.js`. Several ops that loop over user-supplied address arrays (`in data feed`, `in merkle`) explicitly charge extra complexity per array element (`complexity += arrAddresses.length-1`) specifically to prevent unbounded work. The `attested` op does not do this.

### Finding Description
In `validateDefinition`'s `evaluate()` function in `definition.js`, the `attested` case validates an address plus an array of attestor addresses: [1](#0-0) 

Unlike `in data feed` and `in merkle`, which loop over a similarly attacker-controlled `arrAddresses` and then compensate the complexity/gas meter for every extra element evaluated (`complexity += arrAddresses.length-1;`), the `attested` case performs `for (var i=0; i<arrAttestors.length; i++) if (!isValidAddress(arrAttestors[i])) return cb(...)` without any equivalent complexity charge: [2](#0-1) [3](#0-2) 

Because `evaluate()` only increments `complexity`/`count_ops` once per call (at function entry) regardless of how many attestor addresses are validated inside the `attested` branch, the number of `isValidAddress` calls that a single unit of "complexity" buys is effectively unbounded for this op: [4](#0-3) 

The only remaining constraint on `arrAttestors.length` is the raw byte size of the unit/message containing the definition (via `getLength`/payload fee accounting in `object_length.js`), not the complexity/ops gas meter that the rest of oscript relies on to bound CPU work. An attacker can craft an address definition (or any place a definition/asset-condition is evaluated, e.g. via nested `address` references, AA formula-based definitions, shared multisig address definitions posted to peers) containing an `attested` clause with a very large `arrAttestors` array, while keeping `complexity` and `count_ops` far below `MAX_COMPLEXITY`/`MAX_OPS`. Every node that later validates a unit signed by/using that address (`validateAuthentifiers` re-invokes `validateDefinition` on every use, per the comment at `definition.js:1449-1453`) re-runs this unbounded, un-metered loop synchronously. [5](#0-4) 

This is functionally the same class of bug as the reported issue: gas/complexity accounting exists specifically to bound the cost of processing a user-supplied structure, but one branch of the loop-processing logic (`attested`) fails to apply it, letting the attacker-controlled array length drive unbounded work outside the intended budget.

### Impact Explanation
Address definitions are re-validated on every unit that uses that address as an author/definer, and `validateDefinition`/`validateAuthentifiers` run synchronously and single-threaded inside the Node.js validation pipeline. A crafted `attested` clause with a very large attestor array forces every full node (and any node re-validating that address, including hub/witness nodes needed for stabilization) to spend disproportionate, un-metered CPU time on every unit involving that address, while the complexity/ops meter — the mechanism the protocol relies on to keep per-unit validation cost bounded and predictable — reports the definition as cheap. Repeated or concurrent submission of units from such an address can degrade validation throughput network-wide and delay confirmation/stabilization of unrelated units queued behind it, since ocore's validation is largely serialized per connection/queue. This maps to the "network unable to confirm new units in a timely manner" impact category, driven directly by a root-cause gap in the complexity-accounting code (not a generic network/DoS argument).

### Likelihood Explanation
Likelihood is moderate: the `attested` op is a documented, publicly available primitive in ocore's definition language (usable by any address owner or via a `definition` message), enabled since `constants.attestedInDefinitionUpgradeMci`. Creating such a definition costs only the byte-size fee for the array (proportional to bytes, not complexity), which is comparatively cheap relative to the CPU cost imposed on every validating node for every subsequent authenticated unit from that address. No special privileges beyond posting a normal unit/definition are required, satisfying the "unprivileged unit poster" reachability requirement.

### Recommendation
Add the same per-element complexity charge used for `in data feed` / `in merkle` to the `attested` case, e.g. `complexity += arrAttestors.length - 1;` before or after the validation loop, and/or introduce an explicit maximum length constant for `arrAttestors` (analogous to `constants.MAX_ATTESTORS_PER_ASSET` used in `checkAttestorList` for asset attestor lists) enforced in the `attested` branch of `definition.js`.

### Proof of Concept
1. Construct an address definition: `['attested', ['SOME_VALID_ADDRESS', arrAttestors]]` where `arrAttestors` is an array of e.g. 50,000 syntactically valid base32 addresses, sized to stay within the unit/message byte-size limits enforced by `object_length.js`/payload fee rules, but far exceeding what a `complexity`-bounded op of similar shape (`in data feed`/`in merkle`) would allow.
2. Submit this as an author's definition (or as a shared/multisig address definition per `wallet_defined_by_addresses.js`) in a unit; `validateDefinition` in `definition.js` will accept it because `complexity`/`count_ops` are incremented only once for the whole `attested` op, never scaling with `arrAttestors.length` (contrast with `definition.js:418` and `definition.js:465`).
3. Every subsequent unit authored by/referencing that address triggers `validateAuthentifiers` → `validateDefinition` again (per `definition.js:1449-1454`), re-running the 50,000-iteration `isValidAddress` loop synchronously on every full node validating it, imposing repeated, un-metered CPU cost disproportionate to the complexity score charged.
