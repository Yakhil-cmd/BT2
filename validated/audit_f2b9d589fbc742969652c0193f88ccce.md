## Finding

### Title
Worktree sanity check does not verify checkout completeness before trusting it as valid, risking persistent publication of partial content - (File: main.go, `sanityCheckWorktree`)

### Summary
The reported Solmate issue is a class of bug where a "success" signal (`safeTransfer`/`safeTransferFrom` returning true) is trusted without verifying that the underlying operation actually occurred (no codesize check), causing the caller to believe state was correctly updated when it was not. The closest reachable analog in `git-sync` is `repoSync.sanityCheckWorktree`, which is git-sync's "was this operation actually completed" check for a worktree, and it explicitly does not verify that the actual payload (checked-out files) is complete before being trusted as a valid, publishable state.

### Finding Description
`sanityCheckWorktree` is used to decide whether an on-disk worktree can continue to be trusted/served without redoing the checkout. Its own doc comment concedes the gap: [1](#0-0) 

It only checks: (1) the directory isn't empty, (2) `rev-parse HEAD` matches the expected hash, and (3) `git fsck --connectivity-only` succeeds. None of these validate that the working tree actually contains the complete set of files for that commit — a `git reset --hard`/checkout that was interrupted partway (process kill, disk full, OOM) can still leave a directory that is non-empty, has `HEAD` pointing at the right commit, and passes object-connectivity fsck, while the working files are only partially materialized.

This check gates the decision in `SyncRepo` about whether to keep serving the existing worktree as-is: [2](#0-1) 

If `sanityCheckWorktree` returns `true` for a truncated/partial checkout, `git-sync` does **not** nuke and recreate the worktree; `changed` stays `false`, no new worktree is built, `publishSymlink` is not re-invoked, and the pre-existing symlink (set by `currentWorktree()`, which just reads whatever `git.link` currently resolves to) keeps pointing consumers at the same, incomplete directory: [3](#0-2) [4](#0-3) 

This mirrors the reported bug class precisely: a cheap, incomplete check ("it returned success"/"HEAD matches, fsck passes") is treated as proof that the real payload (fund transfer / file checkout) fully happened, when it did not.

### Impact Explanation
If the worktree was left partially checked out by a prior crashed/killed sync (e.g., OOM-killed pod, node eviction, disk pressure — all realistic in the Kubernetes sidecar deployment model this tool targets), git-sync can silently continue serving that same partial worktree indefinitely through the `--link` symlink, satisfying "publishing wrong or partial content" to consumers of the sidecar volume. Because the check is optimistic (it only detects gross corruption, not incompleteness), this can persist across many sync cycles until the next content change forces a full re-checkout.

### Likelihood Explanation
This requires a pre-existing partial checkout, which is a real (not merely theoretical) condition acknowledged in the code's own comment — process interruption during `git reset --hard`/submodule updates is common in container orchestration (OOMKill, node drain, `SIGKILL` during rolling restarts). No attacker-controlled repo content is strictly required to trigger the initial partial checkout, though a large or slow-to-materialize tree (e.g., huge files, submodules) increases the checkout window and thus the likelihood of interruption catching it mid-flight.

### Recommendation
Strengthen `sanityCheckWorktree` to actually validate checkout completeness, e.g. by comparing `git status --porcelain=v1 -uno`/`git diff --name-only HEAD` for unexpected differences from a clean checkout, or by checking `git checkout-index`/`git ls-files` counts against the tree object, rather than relying solely on `HEAD` equality and `fsck --connectivity-only` (which only validates the object graph, not the working tree).

### Proof of Concept
1. Start git-sync with `--link=link --root=/root` and let it complete an initial sync (worktree `wt1` fully checked out, `link -> .worktrees/wt1`).
2. Simulate a crash during a subsequent large checkout (e.g., `SIGKILL` the process mid `configureWorktree` on a new hash) such that some files in the worktree remain from the old tree or are missing/truncated, but `HEAD` already points to the new hash (this can happen because `git reset --hard` updates `HEAD`/index before fully writing all blobs to the working tree for large trees).
3. Restart git-sync with the same target hash (`currentHash == remoteHash`).
4. `sanityCheckWorktree` runs: directory not empty ✓, `rev-parse HEAD` matches ✓, `fsck --connectivity-only` passes (object DB is intact even if working tree files are stale/missing) ✓ → returns `true`.
5. `SyncRepo` treats the worktree as valid; `changed=false`; the symlink is left as-is, continuing to serve the incomplete working tree to consumers with no error surfaced. [2](#0-1)

// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

// currentWorktree reads the repo's link and returns a worktree value for it.
func (git *repoSync) currentWorktree() (worktree, error) {
	target, err := os.Readlink(git.link.String())
	if err != nil && !os.IsNotExist(err) {
		return "", err
	}
	if target == "" {
		return "", nil
	}
	if filepath.IsAbs(target) {
		return worktree(target), nil
	}
	linkDir, _ := git.link.Split()
	return worktree(linkDir.Join(target)), nil
}
