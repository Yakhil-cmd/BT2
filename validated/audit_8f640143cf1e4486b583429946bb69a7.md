## Analog Found

### Title
Data feed oracle can post a new value after a trigger unit is broadcast but before it stabilizes, silently changing the outcome of AA logic that depended on the old value - ([File: formula/evaluation.js])

### Summary
The reported issue is about a privileged party (pool owner) changing a parameter (`scaledOfferFactor`) while a user's transaction sits unconfirmed in the mempool, so the parameter the trader "locked in" mentally when broadcasting is not the one actually used at execution time. The same class of problem exists in ocore's Autonomous Agent (AA) formula engine when an AA reads an oracle `data_feed`: the value used is whatever is the *latest* value at or before the **stabilization** MCI of the trigger unit, not the value that existed when the user composed/broadcast the trigger. An oracle (or anyone who controls the oracle address) can post a new feed value after seeing the user's pending trigger in the DAG but before it stabilizes, and that new value is what gets applied — with no timelock or value-pinning mechanism protecting the trigger sender.

### Finding Description
When an AA formula evaluates `data_feed[[...]]` or `in_data_feed[[...]]`, it calls `dataFeeds.readDataFeedValue`/`dataFeedExists` with `max_mci = mci`, where `mci` is the main-chain index at which the *trigger unit* stabilizes, and by default `min_mci = 0`, `ifseveral = 'last'`: [1](#0-0) 

The lookup selects the newest matching data-feed record whose MCI is `<= max_mci` (the trigger's stabilization MCI), scanning both stable records in the kvstore and unstable/pending oracle posts when `bAA` is set: [2](#0-1) 

Crucially, `mci` for a trigger is not chosen by the sender — it is the MCI the trigger unit ends up on once the network's main chain advances and the unit becomes stable, which happens well after broadcast: [3](#0-2) [4](#0-3) 

Because of this, a user composing a trigger (e.g., a swap/exchange AA that reads an exchange-rate oracle) has no way to bind execution to the oracle value visible at broadcast time. The oracle (or an entity able to post to the oracle address) can publish a fresh value anytime before the trigger's MCI stabilizes — a window that spans from broadcast until final confirmation — and that new value is what the AA will use. AA authors are aware of the general risk (comments referencing "data_feed will abort if the exchange rate not posted yet") but there is no protocol-level mechanism (equivalent to a timelock or price-snapshot) to prevent the value from changing mid-flight: [5](#0-4) 

The only knob available, `min_mci`, only excludes feeds posted *before* a given MCI — it does nothing to prevent a *new* value from being posted and picked up between the time the user's trigger is broadcast and the time it stabilizes: [6](#0-5) 

### Impact Explanation
Any AA whose economic logic depends on an oracle-fed price/exchange rate (issuance/swap/lending/futures-style AAs, as illustrated by the shipped `futures_contract.oscript` sample) is exposed: a party with control over the oracle address can observe an incoming, still-unconfirmed trigger and post a new feed value before the trigger stabilizes, causing the AA to execute with a price unfavorable to the trigger sender. This can directly cause fund loss for the trigger's author (e.g., receiving far fewer converted tokens/bytes than expected), which is the same "surprise value change during pending tx" impact described in the source report, just realized through the data-feed mechanism instead of a Uniswap-pool owner setter.

### Likelihood Explanation
Any AA author building oracle-driven financial logic without explicitly designing around this timing gap (e.g., without requiring the trigger to reference a specific already-stable data-feed unit) is vulnerable by construction — this is the default behavior of `data_feed[[...]]`, not a misconfiguration. The confirmation window (broadcast → stabilization) is on the order of multiple units/witness rounds, giving ample time for a value change to land before the trigger's MCI is finalized.

### Recommendation
- Document/require AA authors to pin the data feed to the exact stable unit visible at trigger-composition time using the `what='unit'` mode plus explicit unit checks, or to require `min_mci` to reflect the last stable feed at the time the trigger was signed, rejecting execution otherwise.
- Consider adding a formula primitive that lets the trigger explicitly reference the specific oracle-posting unit it expects (fail/bounce if that exact unit is not the one used), effectively giving traders a way to "lock in" the value they saw, analogous to a timelock/commit step.
- Provide reference AA patterns/library helpers that snapshot the price into the trigger's own `data` payload and validate the AA's read matches, to close this front-running-style window.

### Proof of Concept
1. An AA reads `$rate = data_feed[[oracles='<oracle_address>', feed_name='RATE']]` and swaps assets using `$rate` (as in `test/samples/futures_contract.oscript`).
2. Alice sees `RATE=50` posted stably and broadcasts a trigger unit expecting to receive assets based on `50`.
3. Before Alice's trigger unit stabilizes (which can take several confirmation rounds), the oracle address posts a new `RATE=25` unit.
4. If the new data-feed unit's MCI ends up `<=` Alice's trigger MCI when the main chain advances, `readDataFeedValue`/`dataFeedExists` (called from `formula/evaluation.js` lines 600-663, backed by `data_feeds.js` lines 205-249) picks the newer value `25` instead of `50`.
5. The AA executes using `25`, giving Alice half of what she expected when she broadcast the trigger — with no timelock or value-pinning mechanism to prevent this.

			FROM units \n\
			CROSS JOIN outputs USING(unit) \n\
			CROSS JOIN aa_addresses USING(address) \n\
			LEFT JOIN assets ON asset=assets.unit \n\
