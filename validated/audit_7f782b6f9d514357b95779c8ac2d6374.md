### Title
Pool `repay` refunds the declared "overpayment" out of real token custody without verifying the inbound transfer — anyone can drain supplier cash - ([File: contracts/pool/src/ops/repay.rs])

### Summary
The Connext bug class is "repay accepts a claim of repayment without validating it against the actual asset/obligation." The XOXNO analog is sharper: `ops::repay::apply` trusts the caller-declared `action.amount`, treats any amount above the position's outstanding debt as overpayment, and transfers that "excess" back to the payer via `cache.transfer_out` — a transfer drawn from the pool's real token custody that is never debited from `cash` and never checked by `require_reserves`. When the repaid leg carries no (or little) debt, the entire declared amount becomes "overpayment," so an unprivileged caller can pull real tokens out of the pool while having transferred nothing in.

### Finding Description
In `contracts/pool/src/ops/repay.rs:25-34`, `apply` runs `accounting` and then executes `outcome.cache.transfer_out(payer, outcome.overpayment)`. In `accounting` (`repay.rs:40-67`), `cache.resolve_repay(amount, position)` splits the declared `action.amount` into burned debt shares and `overpayment`; only `net_repay` is credited to cash (`cache.credit_cash(net_repay)` at line 57). The overpayment leg moves tokens out of custody without touching the cash book.

The in-repo test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` at `contracts/pool/tests/flows.rs:3578-3611` demonstrates the exact primitive: the fixture calls `t.client().repay(&payer, &t.ract(0, custody_before))` with a randomly generated `payer` on a market with `borrowed == 0` and nothing transferred in. `resolve_repay` takes the full-close branch (`current_debt_ceil == 0`), `net_repay` is 0, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the full declared amount is refunded from custody — `assert_unfunded_refund_drained_custody` confirms the drain.

The controller-side `repay` (`contracts/controller/src/positions/debt.rs:126-162`) does perform a measured inbound transfer and requires an existing debt position, but it neither constrains nor authenticates the pool-level leg; the pool's own entrypoint is callable directly (as the test does) and the refund path never reconciles the declared amount against an actual balance increase. The same unfunded-refund shape exists in `ops::recapitalize::apply` (noted in the same test comment), which confirms this is a structural gap in how declared amounts are settled, exactly mirroring the Connext issue where the repayment's claimed backing was never checked.

### Impact Explanation
Theft of user funds / protocol insolvency. Each call transfers up to the pool's full token balance to an arbitrary payer while the `cash` book is left untouched, so suppliers' recorded claims remain but the tokens backing them are gone — withdrawals later fail or leave the book insolvent. The drain is repeatable until custody is empty, with zero cost to the attacker beyond declaring a large `amount`.

### Likelihood Explanation
High. The attacker needs no collateral, no debt position, and no privileged role — the test invokes `repay` with a freshly generated address. The only requirement is a market with little or no outstanding debt relative to the declared amount so the excess equals the desired payout; a market with `borrowed == 0` yields the full amount. (Uncertainty: I could not fully confirm within the available iterations whether `Pool::repay` enforces a controller-only check in `contracts/pool/src/lib.rs`; however, the passing test that calls it directly with a generated `payer` and asserts custody drainage strongly indicates it is reachable by unprivileged addresses, and even if gated, the controller's strategy paths that refund balance deltas rely on the same assumption that the pool only refunds what it received.)

### Recommendation
- Settle the repay leg by measured receipt, not by declared amount: snapshot the pool's token balance before/after, or require the controller to have prefunded the exact amount and cap `overpayment` to the measured excess.
- Debit the refund against `cash` and pass it through `require_reserves` (or route it through the same custody-accounting path as `withdraw`), so an unfunded refund cannot draw on supplier backing.
- Reject `repay` actions where `net_repay == 0 && amount > 0` (a pure-overpayment leg is never legitimate) instead of letting the `RepayRoundsToZeroShares` disjunct pass.

### Proof of Concept
The repository already contains it — `contracts/pool/tests/flows.rs:3590-3611`:

```rust
let payer = Address::generate(&t.env);            // unprivileged, funded with nothing
// custody_before == before.cash, before.borrowed == 0, nothing transferred in
let credited = t.client()
    .repay(&payer, &t.ract(0, custody_before))
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                          // no debt retired
assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
// payer received `custody_before` tokens; cash book unchanged
```

Calling `repay` with `amount = pool_token_balance` on any debt-free market transfers that entire balance to `payer`. Repeating across markets drains every listed asset.
