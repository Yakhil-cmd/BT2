## Analysis Result

### Title
Signed-message packages (`is_valid_signed_package`) omit network/chain domain separation, enabling cross-network signature replay - (File: `signed_message.js`)

### Summary
The reported bug class is EIP-712 message hashing without a chain ID, letting a signature valid on one chain be replayed on another. ocore has a directly analogous primitive: off-DAG "signed messages" (`signed_message.js`, exposed to AAs via `is_valid_signed_package` in `formula/evaluation.js`) are hashed and verified without binding to the network/chain identifier that ocore itself defines (`constants.alt` / `constants.version`, distinguishing livenet, testnet, and devnet). Because address derivation (`getChash160`) is also network-independent, a signed package produced for one network validates identically on another, allowing replay of oracle/attestor-style authorizations across mainnet, testnet, and devnet deployments of the same AA logic.

### Finding Description
Regular DAG units embed the network identifier: `getStrippedUnit`/`getNakedUnit` keep the `alt`/`version` fields, and `constants.alt` is `'1'`/`'2'`/`'3'` for livenet/testnet/devnet respectively, with correspondingly distinct `constants.version` (`'4.0'`, `'4.0t'`, `'4.0dev'`) and `constants.supported_versions` arrays. [1](#0-0) [2](#0-1) 

However, "signed messages" — a separate off-DAG signing construct used for AA authorization checks and device/wallet messaging — do not enforce this domain separation. `getSignedPackageHashToSign` only hashes `signed_message`, `authors`, `last_ball_unit`, `timestamp`, and `version`, with no `alt`/network binding: [3](#0-2) 

Crucially, `version` is **optional** in a signed package. `validateSignedMessage` only checks the version against `constants.supported_versions` *if the field is present*: [4](#0-3) 

The oscript-level consumer, `is_valid_signed_package` (reachable by any AA author via oscript, and triggerable by any unprivileged trigger sender who supplies `trigger.data`), forwards the same permissiveness — it validates `version` only `if (signedPackage.version)` is truthy, otherwise skips the network/version check entirely: [5](#0-4) 

Because address derivation via `getChash160` never incorporates `alt`/network, the same address (and thus the same private key/signer) exists identically across livenet, testnet, and devnet by design. If a version-less signed package is produced (e.g. an oracle/attestor's off-chain signing tool that doesn't set the optional `version` field, or one node's `signMessage` output reused as-is), the resulting signature is valid on every network `is_valid_signed_package`/`validateSignedMessage` runs on, since the hash never encodes which network the authorization was intended for. [6](#0-5) 

### Impact Explanation
AAs commonly gate privileged state transitions — fund release, price/oracle updates, KYC/attestation gating, minting logic — behind `is_valid_signed_package(pkg, oracle_address)` checks trusting a specific signer address. Since that trusted address is identical across livenet/testnet/devnet and the signed package's hash has no chain binding when `version` is omitted, a signature obtained from (or intended for) one network's instance of the oracle/attestor/AA can be replayed against an identically-deployed AA on another network. This can cause an AA to accept a stale or foreign-network authorization it should have rejected, leading to unauthorized fund release/loss from the AA or acceptance of a bogus attestation, i.e., concrete AA fund loss.

### Likelihood Explanation
Exploitability depends on an oracle/attestor/AA operator omitting the optional `version` field or reusing a mainnet-style signer across networks (a realistic and common practice, since Obyte explicitly supports one seed/address across livenet/testnet/devnet). No privileged access is required — any AA trigger sender who obtains a validly-signed package (e.g. from public testnet activity, from another AA's published trigger data, or from an oracle's test tooling) can submit it as trigger data to a live AA that performs the same `is_valid_signed_package` check.

### Recommendation
Include a mandatory, always-hashed domain-separation field (e.g. `constants.alt` or `constants.version`) inside `getSignedPackageHashToSign`, and reject any signed package in `validateSignedMessage`/`is_valid_signed_package` whose version/alt does not exactly match the verifying node's own network constants — removing the current "if present" conditional so that omission cannot bypass the check.

### Proof of Concept
1. An oracle/attestor signs a package via `signMessage()` without relying on network-aware composition (`bNetworkAware=false`), producing `{signed_message, authors}` with no `version` field, using an address whose definition (e.g. `['sig', {pubkey}]`) is identical on livenet and testnet. [7](#0-6) 
2. This package is submitted as `trigger.data.signed_package` to an AA on network A that calls `is_valid_signed_package(trigger.data.signed_package, oracle_address)` to authorize an action (e.g., release funds). [8](#0-7) 
3. `validateSignedMessage` skips the version/network check because `version` is absent, and `getChash160` confirms the address matches on both networks, so the identical package + signature also validates on an equivalent AA deployed on network B. [4](#0-3) 
4. The attacker replays the same signed package + signature against the AA on network B (or vice versa) to trigger the privileged action a second time in a context the signer never intended, resulting in unauthorized fund release from that AA.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
