API token stack-scope bypass in CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup helper used by every other API controller and, in doing so, drops the enforcement that binds an `ApiClient`'s authorization to the single `stack_id` it was issued for. This lets any token holder use a stack-scoped token to read the build/deploy status of any stack in the installation, not just the one the token was authorized for.

### Finding Description
`Shipit::Api::BaseController` supports issuing `ApiClient` tokens that are scoped to a single stack via the `stack_id` column: [1](#0-0) 

`stacks` restricts the visible set of stacks to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` (used generically by all API resources) resolves `params[:stack_id]` only within that restricted scope — i.e., the "stack a token authorizes" (`current_api_client.stack_id`) is checked against the "stack a token touches" (`params[:stack_id]`) on every normal API request.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

`stack` here resolves directly via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id` altogether. The controller only checks a generic `read:stack` permission (`require_permission :read, :stack`) via `require_permission!`, which validates the *type* of permission the client has but never checks *which* stack it is scoped to: [3](#0-2) 

The token is verified with `ApiClient.authenticate`, which is a `SimpleMessageVerifier`-signed digest of the `ApiClient` `id` only — permissions and `stack_id` are not part of the signed token and are looked up fresh from the DB on each request (this is expected/by design, similar to a session token). The break here is not in the token digest itself, but in the fact that one endpoint (`CCMenuController`) fails to re-derive/re-check the `stack_id` binding that the rest of the API enforces. This is exactly the "a stack a token authorizes versus a stack it touches" binding: `current_api_client.stack_id == params[:stack_id]` holds everywhere except this controller.

This is corroborated by the fixture `here_come_the_walrus`, which is explicitly created scoped to a single stack (`stack: shipit`, permission `read:stack` only): [4](#0-3) 

Test coverage elsewhere explicitly documents and enforces this scoping for the JSON `stacks` API (`"an api client scoped to a stack will only see that one stack"`), but the CCMenu test suite never exercises passing a `stack_id` different from the token's authorized stack, meaning this endpoint has no test verifying (or enforcing) the same restriction.

### Impact Explanation
An attacker who holds any valid `ApiClient` token limited to a single stack (e.g. a CCMenu URL generated for a low-trust integration via `CCMenuUrlController`, which itself creates minimally-privileged, stack-agnostic-looking tokens) can pass an arbitrary `stack_id` to `GET /api/:stack_id/ccmenu` and read build status (`lastBuildStatus`, `lastBuildLabel`, activity, webUrl, etc.) for any stack in the Shipit instance — including stacks whose existence, deploy status, or lock/failure state the token holder was never authorized to see. This is an unauthorized cross-stack read of deploy/task state, matching the "High" impact category of "unauthenticated/unauthorized read of stack state, task streams or deploy output" defined in scope.

### Likelihood Explanation
Any party holding a legitimately-issued, narrowly-scoped `ApiClient` token (e.g. a CI dashboard integration token meant only for one stack) can trivially exploit this by changing the `stack_id` URL segment — no privilege escalation, secret cracking, or additional access is required beyond possessing one valid, low-privilege stack-scoped token, which is routinely distributed for CCMenu integrations via `CCMenuUrlController`.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it to reuse `BaseController#stacks`/`#stack`) so that stack lookup is scoped through `current_api_client.stack_id` consistently, matching the behavior of every other API controller.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A (`stack_id` set, e.g. via `CCMenuUrlController#fetch`, which issues a `read:stack`-only client for the requested stack) and note its `authentication_token`.
2. Send `GET /api/<Stack B's param>/ccmenu.xml?token=<Stack A's token>` (or with HTTP Basic auth) where Stack B is a different, unrelated stack.
3. Observe that the response renders Stack B's `lastBuildStatus`, `lastBuildLabel`, `activity`, etc. — despite the token only being authorized (`stack_id`) for Stack A — because `CCMenuController#stack` resolves `params[:stack_id]` via `Stack.from_param!` without checking `current_api_client.stack_id`.
