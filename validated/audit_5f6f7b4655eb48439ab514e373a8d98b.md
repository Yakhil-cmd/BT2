### Title
Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` in multi-org Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-organization Shipit deployments, the HMAC signature verification selects which organization's `webhook_secret` to validate against using `repository.owner.login` (or `organization.login`), but every webhook handler resolves the actual `Repository`/`Stack` to act on using the independent, unchecked `repository.full_name` field from the same payload. An attacker who legitimately controls (and knows the `webhook_secret` of) one low-privilege organization configured in the same Shipit instance can forge a signed webhook whose `repository.owner.login` matches their own org (so it passes signature verification) but whose `repository.full_name` points at a different, victim organization's repository — allowing them to inject data (e.g. forged commit statuses) into stacks they have no authority over.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the app/secret used for HMAC verification from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`params.dig('repository','owner','login')`), and `Shipit.github(organization: repository_owner)` looks up that organization's dedicated `webhook_secret` in the multi-org config schema: [3](#0-2) 

This confirms that when Shipit is configured with multiple orgs (`config/secrets.development.example.yml` documents this schema with a separate `webhook_secret` per organization), each org's operators/admins legitimately possess their own `webhook_secret` and can produce a valid `X-Hub-Signature` for any payload content they choose — GitHub's HMAC only proves "this body was signed with organization X's secret," not "this event actually originates from organization X's repository."

Once signature verification passes, `WebhooksController#create` dispatches the raw, attacker-controlled `params` to handlers: [4](#0-3) 

Every handler resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login` (the field that was actually used to select the trusted secret): [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks the repo up purely by owner/name string, independent of which org's secret verified the request: [6](#0-5) 

Concretely, `StatusHandler` uses only `sha` to find matching commits across the whole database and writes a new `Status` for them — it never checks `repository.full_name` at all, nor the authenticated org: [7](#0-6) 

This means an attacker who owns organization `attacker-org` (configured in Shipit with its own known `webhook_secret`) can sign an arbitrary JSON body containing:
- `repository.owner.login = "attacker-org"` (so `verify_signature` succeeds using `attacker-org`'s secret)
- `sha` = the SHA of a commit belonging to a victim stack in `victim-org`
- `state = "success"`, forged `context`/`description`/`target_url`

and have Shipit accept it as an authentic CI status update for the victim's commit, since `StatusHandler` has no organization binding check at all. Other handlers (`PushHandler`, PR handlers) do resolve via `repository.full_name`, which is likewise disconnected from the verified `repository.owner.login`, letting a low-privilege org trigger `sync_github`/review-stack lifecycle actions (archive/unarchive) on stacks belonging to a completely different organization.

The broken binding, stated as an equality that should hold but doesn't:
`organization whose secret authenticated the request == organization owning the repository/stack being written to`

### Impact Explanation
Forged commit statuses directly affect `Commit#deployable?`, which factors into whether continuous deployment or manual deploys proceed: [8](#0-7) 
An attacker controlling one tenant organization in a shared multi-org Shipit instance can mark a victim organization's commit as CI-`success`, potentially causing that commit to become `deployable?` and get picked up by continuous delivery (`Stack.schedule_continuous_delivery` / `next_expected_commit_to_deploy`), resulting in an **unauthorized deploy** of a commit the victim organization never approved for release. This matches the "unauthorized deploy" Critical-tier impact criterion. It also allows cross-organization writes (forged statuses, forced syncs, forced archive/unarchive of review stacks) — a boundary that should be enforced by the per-org webhook secret but is not, because the org-identifying field used for authentication is never the same field used for authorization of the write target.

### Likelihood Explanation
Exploitability requires that the deployment is configured with the documented multi-organization schema (multiple `webhook_secret`s, one per org) and that the attacker is an administrator of at least one of the lower-privileged organizations onboarded to that shared instance — a realistic scenario for shared/internal Shipit deployments serving multiple teams/orgs, which the engine explicitly supports and documents. No GitHub App private key, `ApiClient` token, or Shipit user session is required — only the ability to craft and correctly sign an HTTP POST to `/webhooks` using a secret the attacker legitimately owns for their own org.

### Recommendation
Bind the authenticated organization to the write target: after `verify_signature` succeeds, pass the authenticated `repository_owner` (or the `GitHubApp` instance/org it resolved) down to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and have `Handler#stacks`/`Handler#repository` (and `StatusHandler`, `PushHandler`, PR handlers, etc.) reject/ignore any payload whose `repository.full_name` owner does not case-insensitively equal the organization whose secret verified the signature. `Repository.from_github_repo_name` (or a new authorization step in `Webhooks::Handlers::Handler`) should enforce `repo_owner == authenticated_organization`.

### Proof of Concept
1. Configure Shipit with the documented multi-org schema, e.g. two orgs `attacker-org` (secret `S1`) and `victim-org` (secret `S2`), each installed as a separate GitHub App on the same Shipit instance, with stacks tracked for both.
2. As the attacker (administrator of `attacker-org`, who legitimately knows `S1`), build a JSON body:
```json
{
  "sha": "<sha-of-a-victim-org-commit>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged by attacker",
  "target_url": "https://attacker.example/fake",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully because it was genuinely signed with `S1`.
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — the victim's commit — with no organization check, and calls `create_status_from_github!`, injecting a forged "success" CI status onto a `victim-org` commit, potentially making it `deployable?` and eligible for continuous deployment.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
