## Analysis

This confirms the exploitable binding mismatch: `WebhooksController#verify_signature` selects the GitHub App / webhook secret used to authenticate the request based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or falls back to `params.dig('organization', 'login')`). [1](#0-0)  However, the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a completely separate, independently attacker-controlled field of the same JSON body. [2](#0-1)  `Repository.from_github_repo_name` then splits that `full_name` on `/` and looks up by `owner`/`name` with no cross-check against `repository.owner.login`. [3](#0-2) 

In a multi-organization Shipit installation, each org has its own `GitHubApp`/webhook secret, selected via `Shipit.github(organization: repository_owner)`. [4](#0-3)  An attacker who legitimately administers their own GitHub App installation ("attacker-org", with a Shipit-configured webhook secret they know) can sign a webhook payload where `repository.owner.login` = `"attacker-org"` (so `verify_signature` picks — and validates against — the attacker's own known secret) but `repository.full_name` = `"victim-org/victim-repo"`. `PushHandler#process` will then locate stacks belonging to `victim-org/victim-repo` and call `stack.sync_github(expected_head_sha: params.after)`, enqueuing a `GithubSyncJob` for the victim's stack — a repository the attacker never authenticated for. [5](#0-4) 

This exactly matches one of the specified binding classes: "an organization that authenticated versus the repository that is written." The vulnerability class from the report (a privilege/permission field that is trusted going forward but never re-validated against the authenticated identity) has a direct analog: the field used for authentication (`repository.owner.login`) is never re-checked against the field used to select the acted-upon resource (`repository.full_name`).

### Title
Webhook signature is verified against `repository.owner.login`, but the affected `Stack`/`Repository` is resolved from the independently-controlled `repository.full_name`, allowing cross-organization sync triggering - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the GitHub App/webhook secret belonging to the organization named in `repository.owner.login` (or `organization.login`), but the handlers dispatched afterward (`PushHandler`, and the `stacks`/`repository_name` helpers shared by all `Handler` subclasses) resolve the target repository/stack from `repository.full_name`, a separate JSON field the same attacker fully controls. These two fields are never checked for consistency.

### Finding Description
- Authentication binding: `repository_owner` (used to pick the `GithubApp` instance and thus the HMAC secret for signature verification) is derived from `params.dig('repository', 'owner', 'login')`. [1](#0-0) 
- Action binding: `Handler#repository_name` (used by every default handler via `Handler#stacks`) is derived from `payload.dig('repository', 'full_name')`, and `Repository.from_github_repo_name` looks up the target repo purely from that string. [2](#0-1) [3](#0-2) 
- Nothing in `verify_signature` or in `Handler` cross-validates that `repository.full_name` starts with `repository.owner.login`. An attacker who controls a legitimately configured GitHub App/organization in the Shipit multi-org config (`Shipit.github_organizations`/per-org `secrets.github`) can produce a validly-signed webhook (signed with their own known secret, `owner.login` = their org) while setting `full_name` to point at a stack belonging to a different, victim organization.

### Impact Explanation
The `push` event handler triggers `stack.sync_github(expected_head_sha: params.after)` on whichever stack it resolves via the spoofed `full_name`, letting the attacker force a `GithubSyncJob` against a victim's stack that they have no authorization over. [5](#0-4)  This is a form of unauthorized action against a repository whose deployment configuration/state the attacker does not own, satisfying the "cross-repository writes" bar because the sync operation is state-changing (advances/refreshes the tracked head commit for the target stack) and is normally reserved for pushes GitHub itself sends for that specific repository.

### Likelihood Explanation
Requires the attacker to control (own) at least one organization/GitHub App that is legitimately registered in the Shipit multi-org configuration (`Shipit.github_app_config`) — i.e., they must know a valid webhook secret for *some* org, but not for the victim org. This is a realistic scenario for any Shipit instance serving multiple organizations/teams (as the multi-org secrets format in `test/dummy/config/secrets_double_github_app.yml` and `lib/shipit.rb#github_organizations` demonstrates is a supported configuration), where one org's admins are not trusted to act on another org's stacks.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`Handler#stacks`), verify that `payload.dig('repository', 'full_name')` is consistent with `payload.dig('repository', 'owner', 'login')` (i.e., `full_name.split('/').first == owner.login`) before dispatching to handlers, or better, have every handler resolve the target strictly by `owner.login` + `repository.name` rather than trusting the combined `full_name` string independently of the authenticated owner.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own webhook secret (multi-org config as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known webhook secret (which they legitimately possess) over this exact body.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GithubApp`, and successfully verifies the signature. [6](#0-5) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` helper resolves `Repository.from_github_repo_name('victim-org/victim-repo')`, finding and acting on the victim's stack, triggering `sync_github` on it despite the attacker never having authenticated as `victim-org`. [5](#0-4)
