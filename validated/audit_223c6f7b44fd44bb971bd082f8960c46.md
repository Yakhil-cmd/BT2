### Title
`register-for-bond` L1 lockup outpoint dedup is scoped to a single call, allowing the same on-chain BTC lockup to be re-presented to inflate a staker's credited `sats-total` across separate transactions - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`verify-l1-lockups` / `validate-l1-lockup` build the "duplicate outpoint" defense (`seen-outpoints`) purely as a local `fold` accumulator that lives only for the duration of a single `register-for-bond` call. There is no persistent, contract-state map (e.g. `used-l1-outpoints`) recording which Bitcoin `(txid, output-index)` pairs have already been credited to a bond in a *previous* transaction.

### Finding Description
`validate-l1-lockup` accumulates `seen-outpoints` in its `response` accumulator and only rejects an outpoint that repeats **within the same fold/call**: [1](#0-0) [2](#0-1) 

`verify-l1-lockups` seeds this accumulator fresh (`seen-outpoints: (list)`) on every invocation: [3](#0-2) 

The only global-state guard against reusing an L1 proof is `bond-overlaps-new-position?`, which is keyed on the *reward cycle term* of the staker's existing bond membership, not on the underlying Bitcoin outpoint: [4](#0-3) 

Because `validate-l1-lockup` derives `expected-script-hash` from the caller-supplied `unlock-burn-height` (only constrained to be `>=` the *current* bond's minimum, not pinned to it): [5](#0-4) 

a staker can construct a single real Bitcoin timelock output whose encoded `unlock-burn-height` satisfies the minimum-unlock-height gate of several *future, non-overlapping* bond periods at once. Since `register-for-bond` recomputes `sats-total` purely from the supplied Bitcoin merkle/txid proof each time (`sats-total (try! (verify-l1-lockups tx-sender bond-index l1-lockups))`) and stores it directly into `protocol-bond-memberships` / `protocol-bonds-total-staked`: [6](#0-5) [7](#0-6) 

the staker can roll from bond N into bond N+6 (a flow the contract explicitly allows via `bond-overlaps-new-position?`) and *re-submit the exact same Bitcoin output/merkle proof* as the L1 lockup evidence for the new bond, since nothing in contract storage ever marks that outpoint as "already spent" toward a bond credit. Each successive `register-for-bond` call is a fresh top-level transaction, so the per-call `seen-outpoints` list offers no protection across calls.

This breaks the equality the whole L1 path is supposed to enforce: "sats credited by an L1 proof == sats actually newly locked on Bitcoin for this specific bond term." A staker can present one BTC lockup transaction as proof of collateral for bond N, then again as proof of collateral for bond N+6, N+12, etc., because reuse across time is structurally identical to reuse within one call and the contract only prevents the latter.

### Impact Explanation
`amount-sats` (from `sats-total`) directly drives `protocol-bonds-total-staked` and each bond's reward computation (`bondTargetYieldPerCalculation`, as exercised in `pox-5.test.ts`). Reusing a single BTC lockup across successive bond registrations lets a staker be credited as having locked sats they did not additionally lock, inflating their share of reward slots/yield relative to genuinely-collateralized stakers — a double-counting of a staking commitment. This matches the "High" impact bucket ("signing weight or reward slots exceeding locked value") — because the STX side is still independently locked and verified by `pox-locking`, the concrete loss is reward-slot/weight inflation rather than unbacked STX minting, but it still lets one Bitcoin lockup back more bond credit than it should.

### Likelihood Explanation
Exploitation requires only: (1) constructing one real (or already-existing) Bitcoin P2WSH timelock output whose baked-in `unlock-burn-height` is far enough in the future to satisfy several bonds' `get-bond-l1-unlock-height` minimums, and (2) calling `register-for-bond` at the start of each subsequent, non-overlapping bond period with the same proof data. No signer, admin, or another user's key is needed — the staker only reuses their own previously-published Bitcoin transaction. This is fully reachable by an ordinary staker and does not depend on race conditions, making it a realistic, low-complexity attack path.

### Recommendation
Persist a global map of consumed L1 outpoints (e.g. `used-l1-lockup-outpoints: {txid, output-index} -> bool`) written to by `validate-l1-lockup`/`verify-l1-lockups` (or by `register-for-bond` after success), and check-and-insert against it instead of (or in addition to) the local `seen-outpoints` fold accumulator, so a given Bitcoin lockup output can only ever be credited toward one bond registration for its lifetime.

### Proof of Concept
1. Staker `alice` builds and broadcasts a single Bitcoin P2WSH lockup output for `sats` STX-collateral, using `unlock-burn-height = H`, where `H` is chosen to be `>= get-bond-l1-unlock-height(bond0)` **and** `>= get-bond-l1-unlock-height(bond6)` (bond indices 6 apart, per `BOND_LENGTH_CYCLES`).
2. Alice calls `register-for-bond(bond-index=0, ..., btc-lockup=ok({outputs: [thatOutput], ...}))`. `validate-l1-lockup` accepts it (unlock height, script hash, merkle proof all check out); `protocol-bond-memberships` records `amount-sats = sats` for bond 0.
3. Bond 0's term ends (`unlock-cycle` passes); `bond-overlaps-new-position?` now returns `false` for bond 6.
4. Alice calls `register-for-bond(bond-index=6, ..., btc-lockup=ok({outputs: [the SAME output/tx/merkle-proof], ...}))`. Because `seen-outpoints` is reset fresh for this new call and no persistent outpoint map exists, `validate-l1-lockup` accepts the identical proof again, crediting `amount-sats = sats` a second time for bond 6 — from the same underlying, never-re-locked Bitcoin funds.
