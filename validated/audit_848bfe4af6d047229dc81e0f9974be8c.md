### Title
Webhook org-selected-for-signature-verification is decoupled from org resolved for stack mutation, enabling cross-tenant stack/label injection - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a payload against using `params.dig('repository','owner','login')`, but every pull-request handler (including `LabelCapturingHandler`) resolves the affected `Repository`/`Stack` using the independent `params.repository.full_name` field via `Repository.from_github_repo_name`. Nothing in the request pipeline enforces that these two attacker-controlled JSON fields refer to the same organization, so a payload validly signed with organization B's `webhook_secret` can carry `repository.full_name` pointing at a repository tracked under organization A, causing organization B's signed request to mutate organization A's stack (e.g. inject attacker-chosen labels via `capture_labels`).

### Finding Description
The binding that should hold is: **organization whose `webhook_secret` verified the payload == organization owning the `Repository` resolved by `Shipit::Repository.from_github_repo_name(params.repository.full_name)`**.

Tracing the code:
- `verify_signature` picks the verifying app via `repository_owner`, which is read straight from the raw JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . This selects `Shipit.github(organization: repository_owner)`, which in the multi-org config schema does `github_app_config(organization)` and uses that org's specific `webhook_secret` for the HMAC check [2](#0-1) .
- Every downstream pull-request handler (e.g. `LabelCapturingHandler`, `OpenedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`) resolves the target repository purely from a *different* JSON field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which just splits the string on `/` and does `find_by(owner:, name:)` [3](#0-2) [4](#0-3) .
- `capture_labels` then unconditionally does `pull_request.update!(labels: params.pull_request.labels.map(&:name))` on the stack resolved that way [5](#0-4) .

`repository.owner.login` and `repository.full_name` are two separate, independently-settable keys inside the same attacker-supplied JSON body — nothing ties them together, and no handler re-verifies that the resolved `Repository`'s `owner` matches `repository_owner`. An attacker who is a legitimate admin/onboarder of some organization B tracked in Shipit's multi-org `github:` config (and therefore knows B's `webhook_secret`, as shown supported by `config/secrets.development.example.yml`) can craft a `pull_request` payload with `repository.owner.login = "orgB"` (so `verify_signature` validates against B's secret) and `repository.full_name = "orgA/some-tracked-repo"` (a repository actually owned by unrelated organization A). The HMAC only covers the raw body against B's known secret, so the forged payload passes `verify_signature`, then `LabelCapturingHandler`/other handlers resolve and mutate organization A's `Repository`/`Stack`/`PullRequest` state, entirely bypassing the intended tenant isolation.

None of the existing guards close this gap: `verify_signature` only proves the sender knows *some* configured org's secret, not that the acted-upon repository belongs to that org; `drop_unhandled_event` only filters unregistered events; the `ExplicitParameters` schema only enforces types/presence of `repository.full_name`, not org consistency; `Repository.from_github_repo_name` performs no ownership cross-check against the verifying organization.

### Impact Explanation
An attacker who legitimately controls (knows the `webhook_secret` for) any one organization onboarded into a multi-tenant Shipit deployment can forge webhook events that mutate a *different* organization's tracked repository state — e.g. injecting arbitrary label strings into another org's `ReviewStack`/`PullRequest.labels` (used elsewhere as env-variable-shaped inputs), or triggering `stack.archive!`/`unarchive!` on someone else's review stack via `LabeledHandler`/`UnlabeledHandler`/`ReopenedHandler`, all of which share the same `repository.full_name`-only resolution pattern. This is a cross-tenant/cross-repository authentication-binding failure: the query text notes "a payload for one repository mutating another's stack," which matches the stated Critical category. It is repeatable against any tracked repository whose owner/name is known or guessable, for every event type handled through the same pattern (`pull_request`, and by extension any other webhook handler using `Handler#stacks`/`repository_name`, since `Handler#stacks` also resolves purely from `payload.dig('repository','full_name')` [6](#0-5) ).

### Likelihood Explanation
This requires Shipit to be deployed in the multi-org `github:` configuration schema (distinct `webhook_secret` per organization key, as documented in `config/secrets.development.example.yml`) and for the attacker to be a legitimately onboarded organization with a known `webhook_secret` for at least one org in that config — a real, supported deployment mode, not a hypothetical misconfiguration. Given that precondition, exploitation cost is trivial: a single crafted HTTP POST to `/webhooks` with a valid HMAC computed from the attacker's own known secret over their own chosen body, no interaction with the victim org required, and repeatable at will against any tracked repository name.

### Recommendation
After resolving the target `Repository` from `params.repository.full_name`, explicitly verify that its `owner` matches the organization whose `webhook_secret` was used to validate the signature (i.e., compare against `repository_owner`/the `organization` parameter passed to `Shipit.github`), and reject the webhook (e.g. `head(422)`) on mismatch. This check should live centrally, e.g. in `Shipit::Webhooks::Handlers::Handler#stacks`/`repository_name` or in `WebhooksController#verify_signature`, so every handler benefits without per-handler duplication.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "a payload signed for org B mutates org A's stack via full_name mismatch" do
  org_a_repo = shipit_repositories(:shipit) # owner "shopify", tracked stack/review stack
  # Configure a second org "org-b" in secrets.github with its own known webhook_secret
  # (multi-org schema), attacker knows org-b's webhook_secret.

  request.headers['X-Github-Event'] = 'pull_request'
  payload = JSON.parse(payload(:pull_request_opened))
  payload['repository']['owner']['login'] = 'org-b'          # selects org-b's secret for verify_signature
  payload['repository']['full_name']      = org_a_repo.github_repo_name # e.g. "shopify/shipit-engine"
  payload['pull_request']['labels']       = [{ 'name' => 'attacker-controlled-label' }]

  raw_body = payload.to_json
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', ORG_B_WEBHOOK_SECRET, raw_body)
  request.headers['X-Hub-Signature'] = signature

  post :create, body: raw_body, as: :json

  assert_response :ok
  # Binding check: verifying org ("org-b") != resolved repository's owner ("shopify")
  refute_equal 'org-b', org_a_repo.owner
  # Yet org A's stack was mutated by a payload verified under org B's secret:
  assert_includes org_a_repo.stacks.last.pull_request.labels, 'attacker-controlled-label'
end
```

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
