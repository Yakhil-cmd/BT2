### Title
Missing protocol-level slippage/minimum-output enforcement for AA "swap" logic combined with attacker-influenceable trigger execution order enables sandwich-style value extraction - (File: aa_composer.js, formula/evaluation.js, main_chain.js)

### Summary
Autonomous Agents (AAs) that implement AMM/exchange-like logic (e.g. computing an output amount from the AA's *current* balance/state at execution time) have no protocol-provided mechanism to enforce a caller-specified minimum acceptable output ("slippage limit"). Combined with the fact that AA triggers accumulated in the same main-chain index are executed in a deterministic order derived from the DAG `level` of the triggering unit — a value the trigger's author controls by freely choosing which parent units to build on — an attacker can compose and post their own state-mutating unit so that it is processed by the AA immediately before (and/or after) a victim's swap-style trigger, exactly mirroring the sandwich-attack primitive described in the referenced Solidity finding.

### Finding Description
The oscript formula language exposes only the raw trigger inputs (`trigger.output[[asset=...]]`, `trigger.data`) to AA authors [1](#0-0) , with no built-in "minimum output" / deadline construct analogous to a DEX router's `amountOutMin`. This means every swap-style AA — such as the reference `uniswap_like_market_maker.oscript` sample, which computes the output purely from the AA's live balances at the moment the trigger executes (`$asset_balance`, `$bytes_balance`, `$p`, `$new_asset_balance`) — has no protocol-enforced protection against the pool ratio changing between when the user creates their trigger unit and when it is actually executed [2](#0-1) .

Execution order for multiple AA triggers landing in the same stabilized MCI is not based on arrival/broadcast time, but on a deterministic SQL ordering by DAG `level`, `unit`, and `address`: `ORDER BY aa_triggers.mci, level, aa_triggers.unit, address` in `handleAATriggers` (`aa_composer.js`) and `ORDER BY units.level, units.unit, address` when triggers are queued during stabilization (`main_chain.js`) [3](#0-2) [4](#0-3) . The `level` of a unit is simply `max(level of chosen parents) + 1`, computed and enforced at `updateLevel`/`determineMaxLevel` time [5](#0-4) , and any composer is free to choose which free/eligible parent units to build on when constructing a new unit via `pickParentUnits`/`pickParentUnitsAndLastBall` [6](#0-5) . Because a user (or bot) constructing a competing unit chooses its own parents, and low-level protocol code imposes no App-level relative-ordering guarantee tied to the *content* of the triggers, a well-resourced actor watching the DAG for a pending (not-yet-stable) swap-trigger unit can compose their own manipulating unit(s) and steer level assignment/parenting so that their trigger is included in the same MCI batch and processed by the AA before the victim's swap (to skew the pool ratio) and, if desired, a second unit processed after (to reverse the skew and capture the difference) — the classic front-run/back-run sandwich pattern, but expressed through DAG-level trigger ordering rather than blockchain miner ordering.

### Impact Explanation
Any AA implementing pooled-liquidity/exchange logic that derives an output amount from mutable AA state at execution time (balances, order books, oracle-fed prices) is exposed. A successful sandwich would let the attacker extract value directly from the victim's trade by manipulating the AA's internal balances/ratio immediately before the victim's trigger executes, and reversing the manipulation afterward, netting a profit while the victim receives a worse-than-expected output — an unauthorized transfer of value out of the victim's swap, matching the "concrete unauthorized spending" / fund-loss category. Because there is no protocol primitive (and no widely-adopted oscript idiom demonstrated even in ocore's own sample AAs) to specify and enforce a minimum acceptable output, this is systemic to any DEX/AMM-style AA built on ocore, not a one-off bug in a single deployed contract.

### Likelihood Explanation
Exploitability depends on an attacker being able to observe a pending swap trigger before it stabilizes and compose a colliding unit that lands in the same MCI batch with favorable level/ordering — feasible for a sophisticated actor monitoring the DAG, similar in spirit to mempool-watching MEV bots, though bounded by ocore's DAG timing/witness constraints (making perfect adjacency harder to guarantee than in a single-block EVM chain). This mirrors the original finding's conclusion: not trivially exploitable by any anonymous actor, but a real risk for AAs holding liquidity, warranting a Medium rating consistent with the original judged severity.

### Recommendation
- Provide (and document) an oscript idiom/best-practice for slippage protection: AA authors should require callers to pass an expected minimum output / maximum input via `trigger.data` and have the AA `bounce()` if the computed amount violates it, e.g. `if ($amount < trigger.data.min_amount) bounce('slippage too high');`.
- Update ocore documentation/samples (including `uniswap_like_market_maker.oscript`) to demonstrate this pattern so it becomes the expected norm for AMM-style AAs, since — as in the original report — the absence of an enforced or even recommended mechanism is the core issue.
- Consider whether trigger ordering guarantees (e.g., FIFO by broadcast/inclusion rather than DAG level for same-MCI triggers to the same AA) could reduce the attacker's ability to insert a trigger immediately before a known pending one.

### Proof of Concept
1. Deploy an AMM-style AA equivalent to `test/samples/uniswap_like_market_maker.oscript`'s "exchange bytes to asset" case, which computes `$amount` solely from `balance[$asset]`/`balance[base]` at execution time with no caller-supplied minimum output check [2](#0-1) .
2. Victim broadcasts a swap trigger unit `U_v` sending `base` to the AA, expecting `$amount` of `asset` based on the currently observed pool ratio.
3. Before `U_v` stabilizes, attacker observes it in the DAG and composes unit `U_a1` (built on parents that keep it at the same/lower `level`) that sends a large swap in the same direction to skew `$asset_balance`/`$bytes_balance` unfavorably for the victim, aiming for `U_a1` to be assigned a lower or equal `level` so it is processed by `handleAATriggers`'s `ORDER BY ... level, unit, address` before `U_v` [3](#0-2) .
4. Once `U_v` executes against the now-skewed pool, victim receives less `asset` than expected, with no `bounce` possible since the AA has no slippage check.
5. Attacker composes `U_a2` (parented after both) to reverse-trade back and realize profit from the temporarily skewed ratio.
