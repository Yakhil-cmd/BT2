### Title
Webhook signature verification authenticates the payload's organization but webhook handlers act on a different, unverified repository field, enabling cross-organization commit-status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks a GitHub App configuration and validates `X-Hub-Signature` using the organization derived from `repository.owner.login`/`organization.login`, but the individual webhook `Handler` subclasses that then execute the event act on a completely different, independently-read payload field (`repository.full_name`, or in the `status` case, no repository scoping at all). Because these two fields are never cross-checked, and because `verify_webhook_signature` intentionally short-circuits to `true` when no `webhook_secret` is configured for the resolved organization, an attacker can satisfy the "authenticated organization" side of the binding cheaply while controlling the "repository/commit actually written to" side arbitrarily.

Note `return true unless webhook_secret` — if the organization resolved by `repository_owner` has no configured `webhook_secret` (a supported, documented configuration, see `config/secrets.development.shopify.yml` where `webhook_secret:` is nil), verification is bypassed entirely for any payload naming that organization.

Once past `verify_signature`, the concrete `Handler` subclasses determine which `Stack`/`Commit` to mutate using a **separate** payload field that is never tied back to the field used for authentication: [4](#0-3) 
`PushHandler` and `CheckSuiteHandler` use this `stacks` helper (keyed off `repository.full_name`), while `StatusHandler` doesn't even scope by repository at all — it matches on commit SHA globally: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization_authenticated_by(verify_signature) == owner_of(repository_acted_on_by(handler))`

This equality is never enforced: `verify_signature` authenticates against `repository.owner.login` / `organization.login`, while the handlers key off `repository.full_name` (or nothing, for `StatusHandler`) read independently from the same untrusted JSON body.

### Impact Explanation
For any organization entry in `Shipit.github` configured without a `webhook_secret` (a state the code explicitly treats as valid, not an error), an unauthenticated caller can POST directly to `/webhooks` with:
- `X-Github-Event: status`
- a body whose `repository.owner.login`/`organization.login` matches the secret-less org (so `verify_signature` passes trivially), and
- `sha`, `state: success`, `context` fields referencing a commit that actually belongs to a **different**, unrelated, properly-secured organization/stack.

`StatusHandler#process` will create a passing CI status for that arbitrary commit with no repository check at all, since `Commit.where(sha: params.sha)` is global. If that stack requires this CI context for continuous deployment/merge queue eligibility (`ci.require` in `shipit.yml`), this can enable an unauthorized deploy or merge — squarely within the "unauthorized deploy, rollback or merge" Critical impact bucket. `PushHandler`/`CheckSuiteHandler` similarly let the secret-less-org caller trigger `GithubSyncJob`/check-run refresh for stacks that belong to other, security-conscious organizations, since `Repository.from_github_repo_name` is resolved from the unauthenticated `full_name` field.

### Likelihood Explanation
Likelihood is bounded by whether any organization in the deployment's `Shipit.github` configuration has `webhook_secret` unset — the code path exists specifically to support that configuration (e.g., internal/test orgs), so it is a realistic operational state rather than a purely theoretical one. Given such an org exists, exploitation requires only a single unauthenticated HTTP POST with attacker-chosen JSON — no session, API token, or secret of any kind.

### Recommendation
Do not decouple the field used to select/validate the webhook secret from the field the handler subsequently acts on. Concretely:
- After signature verification, re-derive the repository/organization solely from the verified payload and pass it explicitly into handlers rather than letting each `Handler` independently re-read `repository.full_name` (or nothing, in `StatusHandler`'s case) from the same untrusted body.
- Require `StatusHandler` to scope `Commit.where(sha:)` by the verified repository/stack, not globally.
- Consider disallowing (or clearly gating behind an explicit opt-in with warnings) the `webhook_secret` blank bypass in `GithubApp#verify_webhook_signature`, since it silently authenticates any payload claiming to be from that organization.

### Proof of Concept
1. Configure two orgs in `Shipit.github`: `secretless-org` (no `webhook_secret`) and `victim-org` (has stacks with `ci.require` gating deploys on a status context, e.g. `ci/tests`).
2. Send:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<real sha of an undeployed commit on a victim-org stack>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "secretless-org" }, "full_name": "secretless-org/whatever" }
}
```
3. `verify_signature` resolves `repository_owner` = `secretless-org`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of headers.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `success` status for the victim-org commit, satisfying its CI-required check without any real CI run, potentially unlocking continuous deployment/merge for that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
