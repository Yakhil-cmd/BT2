Confirmed vulnerability found: the webhook signature verification binds trust to `repository.owner.login`/`organization.login`, but the event handlers that act on the payload key off `repository.full_name` — a different, unauthenticated field — with no cross-check that the two agree.

### Title
Webhook signature verified against payload's claimed organization is never checked against the repository actually acted upon, enabling cross-organization writes in multi-tenant deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify the HMAC signature against based on `repository_owner`, which is read straight from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0)  Once the signature passes for that organization, the raw payload is dispatched unmodified to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [2](#0-1)  The handlers (e.g. `PushHandler`, `StatusHandler`) never re-derive or validate the organization; they instead look up the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` via `Handler#repository_name` / `Handler#stacks`. [3](#0-2) [4](#0-3) 

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where multiple GitHub Apps (and therefore multiple independent `webhook_secret`s) are registered, one per organization, as documented/tested by `secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`). [5](#0-4)  `verify_signature` uses this to look up the correct app/secret: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [6](#0-5) 

The binding that should hold is:
`organization used to select/verify the HMAC secret == organization owning the repository the handler actually writes to`

But the field used for verification (`repository.owner.login` / `organization.login`) and the field used to select the write target (`repository.full_name`, consumed in `Handler#repository_name`) are two independently attacker-controlled JSON fields in the same unsigned-until-verified request body, and nothing after verification confirms they are consistent. [7](#0-6) [8](#0-7) 

An attacker who controls a webhook secret for one tenant (`OrgOne`, e.g. because they administer that GitHub App/organization on a shared Shipit instance) can:
1. Set `repository.owner.login` (or `organization.login`) = `OrgOne` so the signature check passes with `OrgOne`'s secret.
2. Set `repository.full_name` = `OrgTwo/some-repo` (a repository belonging to a different tenant configured on the same Shipit instance).

`verify_signature` succeeds because it only checks the HMAC against `OrgOne`'s secret and the raw body — it does not care that `full_name` points elsewhere. [9](#0-8)  The `push` handler then finds `OrgTwo/some-repo`'s `Stack`s via `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)`, i.e. it triggers a GitHub sync (and downstream deploy-eligible commit ingestion) for a stack the attacker has no legitimate authority over. [4](#0-3) 

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding: an attacker who only controls one tenant's webhook credentials can inject/forge push, status, or check_suite events for another tenant's stacks on the same Shipit installation, causing unauthorized commit ingestion, forged commit statuses (`StatusHandler` creates a `Status` for any `sha` matching `Commit.where(sha:)` regardless of repository) [10](#0-9) , or triggering syncs that can influence what appears deployable. This maps to the "unauthorized deploy/organization-authenticated-vs-repository-written" boundary called out in scope, at High/Critical severity depending on downstream effect (status forgery can gate/unblock deploys).

### Likelihood Explanation
Requires a multi-organization Shipit deployment (documented and tested feature — `secrets_double_github_app.yml`) where the attacker legitimately controls one tenant's GitHub App/webhook secret but targets another tenant's repository configured on the same instance. This is a realistic configuration for shared/self-hosted Shipit instances serving multiple orgs.

### Recommendation
After `verify_signature` succeeds, thread the verified `organization` (the one whose secret validated the signature) through to the handlers, and have `Handler#stacks` (or `PushHandler`/`StatusHandler`/etc.) reject/ignore any event where the repository resolved from `full_name` does not belong to that verified organization, rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows `OrgOne`'s `webhook_secret` (e.g., an admin of `OrgOne`'s GitHub App), craft a `push` event payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgTwo/victim-repo", "owner": { "login": "OrgOne" } }
   }
   ```
3. Sign the raw body with `OrgOne`'s `webhook_secret` and send it as `X-Hub-Signature` to `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the signature validates successfully. [6](#0-5) 
5. `PushHandler#process` resolves the target stacks from `repository.full_name = "OrgTwo/victim-repo"` and calls `stack.sync_github`, acting on `OrgTwo`'s stack despite the request only being authenticated for `OrgOne`. [4](#0-3)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
