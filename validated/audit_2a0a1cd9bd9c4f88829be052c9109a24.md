I have confirmed the vulnerability. `propagateFinalBad` in `main_chain.js` updates `storage.assocStableUnits[unit].sequence` in-memory and the `units` table in the DB when a previously-stable unit is discovered to have spent an input that turns out to belong to a final-bad unit — but it never touches `assocCachedAssetInfos`, the asset-definition cache in `storage.js`. This is the same bug class as the Nova advisory: state that determines authorization (here, an asset definition's validity/`sequence`) is cached at one point in time and never invalidated when the underlying resource is later revoked/changed, so stale "still good" state keeps being served/reused for security decisions.

### Title
Stale `sequence` cached in `assocCachedAssetInfos` lets a voided (final-bad) asset definition keep being treated as valid, enabling continued issuance/transfer of a supply-inflating asset - (File: storage.js)

### Summary
`storage.readAssetInfo()` caches an asset's row (including `sequence` and `is_stable`) in the module-level `assocCachedAssetInfos` map the first time it is read as stable. `readAsset()` then gates all issuance/transfer validation on `objAsset.sequence !== "good"`. However, when a unit that defines an asset is later discovered to have spent an input belonging to a unit that becomes `final-bad` (a double-spend loser resolved after the asset's defining unit was already stable and cached), `main_chain.js`'s `propagateFinalBad()` updates the unit's sequence to `'final-bad'` in the DB and in `storage.assocStableUnits`, but does not delete/update the corresponding entry in `assocCachedAssetInfos`. All subsequent asset lookups keep returning the stale, cached `sequence: 'good'`.

### Finding Description
- `readAssetInfo()` caches the asset row only once, keyed by `asset` (the defining unit hash), with no expiry logic tied to sequence changes: [1](#0-0) 
- `readAsset()` relies entirely on the (possibly cached) `sequence` field to decide whether the asset definition is usable: [2](#0-1) 
- `main_chain.js`'s `propagateFinalBad()` is the mechanism that can flip an already-stable, already-cached unit's sequence from `good` to `final-bad` after the fact, when a descendant spends an input from a newly discovered final-bad unit. It updates `storage.assocStableUnits[unit].sequence` and the DB row, but has no knowledge of, and does not touch, `assocCachedAssetInfos`: [3](#0-2) 
- The comment in `readUnitProps()` explicitly acknowledges this exact class of hazard for the general unit-props cache — "we don't cache final-bads as they can be voided later" — but the asset-info cache in `readAssetInfo()` does not apply the same discipline; it caches `is_stable` rows unconditionally on sequence, and there is no code path that purges a specific `asset` entry from `assocCachedAssetInfos` when its defining unit's sequence changes after caching: [4](#0-3) [5](#0-4) 
- The only cache-eviction routine (`shrinkCache`) clears `assocCachedAssetInfos` wholesale only when it exceeds `MAX_ITEMS_IN_CACHE`, not in response to sequence transitions, so a small deployment/testnet where the cache never hits that size limit could carry the stale entry indefinitely: [6](#0-5) 

This mirrors the Nova bug class precisely: a cached decision about a resource's validity/ownership ("good" sequence, analogous to a device path binding) is not invalidated when the underlying resource's true state changes (unit becomes `final-bad`, analogous to the VM being migrated), so later actions keep trusting stale state.

### Impact Explanation
If exploited, an attacker who controls (or colludes with) the definer of an asset can:
1. Post the asset-defining unit and get it to become stable and read once (e.g., via any `readAsset`/`readAssetInfo` call — this happens naturally as soon as any unit references the asset), populating `assocCachedAssetInfos[asset]` with `sequence: 'good'`.
2. Arrange for that same defining unit to later be discovered as a double-spend loser through `propagateFinalBad` (i.e., its unit is proven to have spent an input from another unit that itself becomes `final-bad`), which flips the unit's true sequence to `final-bad`.
3. Continue issuing/transferring the asset — every node whose `assocCachedAssetInfos` cache holds the stale `good` entry will keep validating issuance and payment messages referencing that asset as if it were legitimately defined, because `readAsset()` only checks the cached `sequence`.

This can result in continued supply inflation of a nominally voided asset, or acceptance of transfers of an asset that should be considered non-existent — a concrete double-spend/inflation condition and a source of node disagreement (nodes that have not cached the entry, or that purged it via `shrinkCache`, will correctly reject the same messages that cache-poisoned nodes accept), i.e., a consensus split on unit validity.

### Likelihood Explanation
Reaching this requires a specific but reachable sequence: getting an asset-defining unit to be both read (to populate the cache) and later provably final-bad via input-propagation from another final-bad unit. This depends on non-deterministic network/DAG timing (double-spend races) rather than a single-shot input the attacker fully controls, so it is not trivially triggerable on demand, but it is within reach of a unit-posting attacker/asset issuer who can construct a double-spend scenario deliberately (issue asset from a unit whose author also submits a conflicting unit elsewhere, engineering the loser scenario). No special privileges beyond normal unit posting are required.

### Recommendation
When `propagateFinalBad` (and the analogous same-mci final-bad transition in `handleNonserialUnits`) flips a unit's `sequence`, also invalidate any corresponding entry in `assocCachedAssetInfos` (i.e., `delete storage.assocCachedAssetInfos[unit]` for every unit whose sequence changes), or update the cached object's `sequence` field in place, the same way `storage.assocStableUnits[unit].sequence` is updated. More generally, `readAssetInfo`'s cache should not be keyed purely on `is_stable` without a mechanism to react to subsequent sequence changes of the same unit.

### Proof of Concept
1. Node A defines asset `X` in unit `U1` (cap-based, `issued_by_definer_only`), signed by address `ADDR`.
2. Some other logic on the network causes `ADDR` (or a colluding co-author path) to also sign a conflicting/double-spending unit `U2` elsewhere in the DAG such that, once resolved, `U1` is determined to have spent an input from a unit that itself becomes `final-bad`, causing `main_chain.js`’s `handleNonserialUnits`/`propagateFinalBad` to set `U1`'s sequence to `final-bad` in the DB and in `assocStableUnits`.
3. Prior to this transition, some node already called `storage.readAssetInfo(conn, 'U1', ...)` (e.g., while validating any earlier payment referencing asset `U1`), so `assocCachedAssetInfos['U1']` holds `{ ..., sequence: 'good', is_stable: 1 }`.
4. After `U1` becomes `final-bad` in the DB, the definer posts a new issuance/payment message for asset `U1`. On the node with the stale cache entry, `readAsset()` calls `readAssetInfo()`, gets the cached object, sees `sequence === 'good'`, and validates/accepts the issuance — even though the DB row for `U1` now says `final-bad`. [2](#0-1) 
5. Other nodes that never cached `U1` (or whose cache was cleared by `shrinkCache`) query the DB directly, see `sequence='final-bad'`, and reject the same issuance — producing divergent validity outcomes across the network for the same unit.
