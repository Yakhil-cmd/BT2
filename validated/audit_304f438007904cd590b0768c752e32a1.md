### Title
Webhook authentication is bound to `repository.owner.login`/`organization.login` but writes are bound to `repository.full_name`, enabling cross-organization forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The reported bug class ("a loop iterates over data that was never validated against the caller's authorization") analogizes to a broken binding in Shipit's webhook pipeline: the field used to select *which organization's secret authenticates* an inbound webhook is not the same field used to decide *which repository/stack the payload is applied to*. An attacker who can produce a signature that validates against **any one** configured GitHub organization (including one that trivially bypasses verification) can direct the resulting write to a **different** organization's repository/stack.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration to verify against using: [1](#0-0) 
```
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
It then verifies the HMAC using that org's config: [2](#0-1) 

The actual signature check, `GithubApp#verify_webhook_signature`, trivially passes when the resolved organization has no secret configured: [3](#0-2) 
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Once past `verify_signature`, every event handler determines *which stacks to mutate* using a completely different field, `repository.full_name`, with no cross-check against `repository_owner`: [4](#0-3) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` (and similarly the `pull_request/*` handlers) then act on those stacks: [5](#0-4) 

Because `repository.owner.login`/`organization.login` (used to pick the authenticating secret) and `repository.full_name` (used to pick the mutated repository) come from the **same attacker-controlled JSON body** and are never cross-validated, the binding "organization that authenticated == repository that is written" does not hold. If the Shipit instance is configured with multiple GitHub organizations and even one of them has no `webhook_secret` set (a supported, non-error configuration per `@webhook_secret = @config[:webhook_secret].presence` in `GithubApp#initialize`), an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to that unsecured organization's login, so `verify_signature` passes with no signature needed.
2. Set `repository.full_name` to `"secured-org/target-repo"`, a repository belonging to a different, properly secured organization that has stacks configured in Shipit.

The handler will look up and act on the `secured-org/target-repo` stacks despite the request never having been authenticated against `secured-org`'s webhook secret.

### Impact Explanation
This allows cross-repository/cross-organization writes without possessing the target organization's webhook secret: forcing `GithubSyncJob` runs (`push` event), or driving `pull_request` handlers (label-based merge/review-stack behavior) against a target stack the attacker doesn't own. This matches the Critical "cross-repository writes" / "unauthorized deploy" category, because it lets an unprivileged sender inject events that are processed as if they came from the authenticated organization owning the target repository.

### Likelihood Explanation
Exploitability depends on the deployment having at least one GitHub organization configured in `Shipit.github_organizations` without a `webhook_secret` (or more generally, on the fact that the org used for authentication and the org whose repo is mutated are never required to match). This is a supported configuration path in the engine itself (secrets are optional per `presence` check), not a deviation from documented mounting, so it is a real analog rather than a purely theoretical one. However, I could not fully verify from the indexed code whether the top-level Shipit application enforces `webhook_secret` presence for every configured organization outside this engine, which would mitigate the issue; this is a boundary condition worth flagging.

### Recommendation
Cross-validate the authenticating organization against the repository being mutated: derive the stack-lookup organization from the same `repository_owner`/`organization.login` value that was HMAC-verified, and reject (422) if `repository.full_name`'s owner segment does not match the verified `repository_owner`. Additionally, consider making `webhook_secret` mandatory for every configured GitHub organization so `verify_webhook_signature` can never silently return `true`.

### Proof of Concept
Assume Shipit is configured with two GitHub orgs: `open-org` (no `webhook_secret` set) and `secured-org` (has stacks and a `webhook_secret`).
```
POST /webhooks
X-Github-Event: push
(no X-Hub-Signature header required)

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "secured-org/target-repo",
    "owner": { "login": "open-org" }
  }
}
```
`repository_owner` resolves to `open-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally per [6](#0-5) . `PushHandler` then resolves stacks via `repository.full_name = "secured-org/target-repo"` per [7](#0-6)  and calls `stack.sync_github(expected_head_sha: params.after)` on `secured-org`'s stacks, even though the request was never authenticated against `secured-org`'s secret.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
