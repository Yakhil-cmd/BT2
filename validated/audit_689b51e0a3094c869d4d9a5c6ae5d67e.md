### Title
Unchecked checkout success allows shipit.yml steps to execute against an unintended commit - ([File: app/models/shipit/task_execution_strategy/default.rb])

### Summary
The reported bug class (ERC-20 `transfer`/`transferFrom` boolean return value silently discarded, so failed token movements are treated as successes) generalizes to: a security/consistency-critical boolean result is computed but never inspected by the caller, so a failure path is silently treated as success. In `Shipit::TaskExecutionStrategy::Default`, the git `checkout` command's success flag is discarded the same way, breaking the equality that should hold between "the commit SHA that was approved/requested for the task" and "the working-tree state whose `shipit.yml` steps actually get executed."

### Finding Description
`Default#run` executes, in order: `checkout_repository`, then `perform_task`, then unconditionally writes `"Completed successfully"` and calls `@task.report_complete!`: [1](#0-0) 

`checkout_repository` performs the checkout via `capture!`, but discards its boolean return value instead of checking it: [2](#0-1) 

`capture!` itself only returns `command.success?` — it does not raise on a non-zero exit status: [3](#0-2) 

Because the return value of `capture!(@commands.checkout(@task.until_commit))` is never inspected (no `unless`, no `raise`, no `Command::Error`), a failed `git checkout <sha>` (for example because the ref is not present in the local cache after a race, gets rewritten, or otherwise cannot be resolved) does not stop task execution. Control flow falls through to `perform_task`, which then runs `@commands.install_dependencies` and `@commands.perform` (the `shipit.yml` steps) against whatever commit happens to already be checked out in the working directory — not `@task.until_commit`. This exactly matches the report’s bug class: the return value of a consequential operation is produced but never processed, so a failure is silently treated as success and downstream trust decisions (deploy the approved SHA) are made on stale/wrong state.

This breaks the binding: `Task.until_commit` (the ref that was approved/requested to deploy) == the ref whose `shipit.yml` steps are executed.

### Impact Explanation
If the checkout of the intended SHA silently fails while a stale checkout of a previous commit remains in the working directory, `perform_task` will run the previous commit's `shipit.yml` steps and `@task.report_complete!` will mark the task/deploy as successful for `until_commit`. This is effectively an unauthorized deploy: the system records and reports a deployment of a commit that was never actually built/deployed, while actually executing code from a different (older) revision that reviewers/CI may not have approved for this specific deploy action. This maps to the "unauthorized deploy" Critical impact category and to the "ref approved versus a ref whose `shipit.yml` steps execute" binding called out in the rules.

### Likelihood Explanation
This does not require any privileged credentials, API tokens, or GitHub write access — it depends purely on internal engine logic reachable any time a deploy/task is executed and a `git checkout` step returns non-zero (network hiccup during a previous `git fetch`, cache corruption, a since-rewritten/force-pushed ref, or an attacker who can force a race on the shared git cache directory `@stack.git_path` for a stack they can trigger tasks/deploys on). No signature, webhook secret, or session compromise is needed — the flaw is a latent unconditional-continue after `checkout_repository`.

### Recommendation
Check the return value of the final `capture!(@commands.checkout(@task.until_commit))` call in `checkout_repository` and abort the task (raising `Command::Error` or an equivalent) if it is `false`, so that `perform_task` and `@task.report_complete!` never run against an unverified checkout state.

### Proof of Concept
Conceptual reproduction (cannot be fully driven end-to-end without live infra/terminal access, which is outside this analysis tool's capability):
1. Trigger a deploy/task for `until_commit = SHA_B` on a stack whose local git cache currently has `SHA_A` checked out.
2. Cause the final `git checkout <SHA_B>` invocation inside `checkout_repository` to fail (e.g., corrupt/prune the object right after `fetched?` succeeded, or force a race on the shared `git_path`), while `SHA_A` remains checked out in the working directory.
3. Observe that `Default#run` proceeds directly to `perform_task`, running `shipit.yml` install/deploy steps against `SHA_A`, and then calls `@task.report_complete!`, marking the task complete for `SHA_B` — an unauthorized/incorrect deploy is recorded as successful. [4](#0-3)

      def checkout_repository
        unless @commands.fetched?(@task.until_commit).tap(&:run).success?
          # acquire_git_cache_lock can take upto 15 seconds
          # to process. Try to make sure that the job isn't
          # marked dead while we attempt to acquire the lock.
          @task.ping
          @task.acquire_git_cache_lock do
            @task.ping
            unless @commands.fetched?(@task.until_commit).tap(&:run).success?
              capture!(@commands.fetch_commit(@task.until_commit))
            end
          end
        end
        capture_all!(@commands.clone)
        capture!(@commands.checkout(@task.until_commit))
      end

      def capture_all!(commands)
        commands.map { |c| capture!(c) }
      end

      def capture!(command)
        started_at = Process.clock_gettime(Process::CLOCK_MONOTONIC)
        command.start do
          @task.ping
          check_for_abort
        end
        @task.write("\n$ #{command}\npid: #{command.pid}\n")
        @task.pid = command.pid
        command.stream! do |line|
          @task.write(line)
        end
        finished_at = Process.clock_gettime(Process::CLOCK_MONOTONIC)
        @task.write("pid: #{command.pid} finished in: #{(finished_at - started_at).round(3)} seconds\n")
        command.success?
      end
