### Title
Unauthenticated `sender` field in `TransferStxOp` allows theft of any victim's STX via PreStxOp output spoofing - (File: stackslib/src/chainstate/burn/operations/transfer_stx.rs)

### Summary
`TransferStxOp::check` only rejects `sender == recipient` and a non-positive amount; it performs no check that the `sender` address is actually controlled by whoever crafted the operation. Because `sender` is derived from the antecedent `PreStxOp`'s `output` field — an arbitrary Bitcoin transaction output address anyone can set to any hash160, including a victim's — an attacker can move a victim's full STX balance to themselves with zero Stacks-signature or Bitcoin-key proof of ownership over the `sender` address.

### Finding Description
Equality broken: **STX debited from `sender`** should equal **STX whose owner (the entity holding the private key of `sender`) authorized this specific transfer**. In this code path, zero authorization from the real owner of `sender` exists.

Trace:
1. `PreStxOp::parse_from_tx` sets `output` directly from `outputs.get(0)` of the raw Bitcoin transaction [1](#0-0) . Anyone constructing a Bitcoin transaction can choose *any* hash160 as this output — no signature over that address, nor proof of key ownership, is required to pay Bitcoin to an address.
2. `TransferStxOp::get_sender_txid` only requires that the `TransferStxOp`'s input 0 spend vout 1 (the second output, i.e. the "change" UTXO) of the referenced `PreStxOp` tx [2](#0-1) .
3. `Burnchain::classify_transaction` looks up the matching `PreStxOp` and passes `pre_stx.output` as `sender` into `TransferStxOp::from_tx` [3](#0-2) , and `parse_from_tx` sets `sender: sender.clone()` unconditionally [4](#0-3) .
4. `TransferStxOp::check` validates only `transfered_ustx != 0` and `sender != recipient` [5](#0-4) . There is no check that the entity submitting the tx controls `sender`.
5. `process_transfer_ops` then calls `run_stx_transfer(&sender.into(), &recipient.into(), transfered_ustx, ...)` unconditionally moving funds [6](#0-5) .
6. `run_stx_transfer` → `stx_transfer` sets `invoke_ctx.sender = from.clone()` before calling `stx_transfer_consolidated`, so the internal `Some(from) != invoke_ctx.sender.as_ref()` check in `stx_transfer_consolidated` is tautologically satisfied and provides no real authentication for burn-chain-originated transfers [7](#0-6) [8](#0-7) . The only real balance safety check is `can_transfer`/sufficient-balance, not identity.

Attacker's exact call: craft a `PreStxOp` Bitcoin transaction with `output[0] = victim_addr` (any address, no key needed) and `output[1]` = a UTXO funded and controlled by the attacker. Then craft a `TransferStxOp` transaction whose input spends that `output[1]` (signed with the attacker's own key) and whose payload sets `transfered_ustx = victim_balance` and whose output (the "recipient") is the attacker's address. `TransferStxOp::check` passes (`sender != recipient`, amount > 0), and `process_transfer_ops` debits the victim and credits the attacker.

Why existing guards fail: the only guard, `sender == recipient` self-send rejection, does not prevent an attacker choosing `sender` to be a *third party* (the victim) distinct from `recipient` (the attacker). No code path verifies that the party who signs/funds the Bitcoin transaction actually owns the `sender` Stacks/Bitcoin address.

### Impact Explanation
Any attacker able to construct raw Bitcoin transactions (their own inputs and fees) can drain the entire unlocked STX balance of any known Stacks address to themselves, with no dependency on a miner, signer, or privileged role. This is direct, permanent theft of victim STX — Critical severity, matching "theft ... of locked/unbacked STX." It is fully repeatable against any address whose balance the attacker wants to steal, limited only by attacker's ability to pay Bitcoin transaction fees for the two-transaction PreStx/TransferStx sequence.

### Likelihood Explanation
Preconditions are minimal: the attacker needs a small amount of their own BTC to fund the PreStxOp's two outputs and to pay for the subsequent TransferStxOp's fee; they need to know the victim's Stacks/legacy-Bitcoin address (public knowledge). No PoX phase, membership, or cycle state is required — `TransferStxOp` is processed unconditionally by `process_transfer_ops` for any epoch supporting these ops (2.1+). No signer/miner privilege is required, as shown by test helpers that submit these ops directly via `BurnchainOpSigner` with arbitrary keys/addresses (e.g., `stacks-node/src/tests/epoch_21.rs`). This makes the attack highly feasible and cheaply repeatable.

### Recommendation
Require that `PreStxOp.output` (and therefore `TransferStxOp.sender`/`StackStxOp.sender`/`DelegateStxOp.sender`) be provably controlled by the transaction submitter — e.g., derive `sender` from the Bitcoin transaction's own signing input's public key (as is done for other burn ops) rather than from an arbitrary transaction output address, or require the address in `output[0]` to match the address recoverable from the input(s) that funded the PreStx transaction.

### Proof of Concept
Rust integration test on booted chainstate (pattern already used in `stacks-node/src/tests/epoch_21.rs`):
1. Fund `victim_addr` with STX (e.g. via genesis allocation or prior transfer) — record `victim_balance`.
2. Attacker (using only their own BTC key/UTXOs) submits `PreStxOp { output: victim_addr }`, funding output[1] from their own UTXO.
3. Attacker submits `TransferStxOp { sender: victim_addr, recipient: attacker_addr, transfered_ustx: victim_balance }`, spending the PreStx tx's output[1] with the attacker's own signer key (no victim key used anywhere).
4. Mine blocks so `process_transfer_ops` runs.
5. Assert `get_balance(victim_addr) == 0` (or reduced by `victim_balance`) and `get_balance(attacker_addr) == victim_balance`, proving debit/credit occurred with no signature from `victim_addr`'s private key at any point in the flow.

impl TransferStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.transfered_ustx == 0 {
            warn!("Invalid TransferStxOp, must have positive ustx");
            return Err(op_error::TransferStxMustBePositive);
        }
        if self.sender == self.recipient {
            warn!("Invalid TransferStxOp, sender is recipient");
            return Err(op_error::TransferStxSelfSend);
        }
        Ok(())
    }
}

pub fn stx_transfer_consolidated(
