I've confirmed the vulnerability. `Shipit::Api::StacksController#stack` correctly uses the token-scoping helper `stacks.from_param!` [1](#0-0)  (where `stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped) [2](#0-1) . But `Shipit::Api::CCMenuController#stack` bypasses this scoping entirely and resolves any stack directly via `Stack.from_param!(params[:stack_id])` [3](#0-2) . `require_permission :read, :stack` only checks that the permission name `read:stack` is present in the token's permission list [4](#0-3)  — it never verifies the token is scoped to the specific stack being accessed, so the only enforcement for stack-scoped tokens is the `stacks` helper, which `CCMenuController` skips.

### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, letting a stack-scoped token read any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to look up the stack directly from `Stack.from_param!(params[:stack_id])` instead of using the scoped `stacks.from_param!` helper that every other API controller (`Api::StacksController`, `Api::RollbacksController`, etc.) relies on to restrict a token to its authorized stack.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id` [5](#0-4) . `Api::BaseController#stacks` enforces this scoping: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [6](#0-5) . All other stack-touching API controllers call `stack` through this `stacks` relation, so a token scoped to stack A cannot resolve stack B, and `from_param!` raises a not-found error for out-of-scope IDs.

`CCMenuController`, however, redefines `stack` to bypass this relation:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks whether `"read:stack"` is present in the `permissions` array — it has no notion of *which* stack the permission applies to [4](#0-3) . The equality that should hold is: `token.authorized_stack == stack_touched_by_action`. For every controller using `stacks.from_param!` this equality is enforced by the DB query itself; for `CCMenuController` it is not enforced at all, because `Stack.from_param!` (as used unscoped in `Stack`) resolves against the full `Stack` table regardless of the token's `stack_id` [7](#0-6) .

### Impact Explanation
An `ApiClient` token deliberately scoped to a single stack (e.g. created for a specific team/environment integration) can be used to read the CCMenu XML status — including the latest deploy/rollback ID and running state — of any other stack in the installation, including stacks the token owner has no authorization for. This is an unauthorized cross-stack read of stack/task state, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" relative to what the token was scoped to authorize.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token (with only `read:stack` permission and a `stack_id` restricting it to one stack) can trivially exploit this by supplying a different `stack_id` in the URL — no additional privilege, secret, or race condition is required.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped relation, consistent with every other stack-scoped API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override so it inherits `Api::BaseController#stack`/`#stacks` behavior.

### Proof of Concept
1. Create two stacks, A and B.
2. Create an `ApiClient` with `permissions: ['read:stack']` and `stack: A` (i.e., `stack_id` set to A's id), matching the `here_come_the_walrus` fixture pattern [8](#0-7) .
3. Authenticate as this token and request `GET /api/stacks/:B_stack_id/ccmenu.xml` (route defined for `Api::CCMenuController#show`).
4. The response returns stack B's deploy status/XML successfully, even though the token is scoped only to stack A — contrast with the existing test that shows stack-scoped tokens are properly restricted when using the scoped `stacks` relation on `Api::StacksController#index` [9](#0-8) .
