### Title
Webhook Signature Verification Silently Disabled When `webhook_secret` Is Unset, Allowing Unauthenticated Forged GitHub Events - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb])

### Summary
The external report's bug class is "any input is accepted because there is no whitelist/validation gate." The direct analog in this engine is the webhook trust boundary: `WebhooksController#verify_signature` is supposed to bind an inbound HTTP POST to a specific GitHub organization's shared secret before any payload-derived write happens, but `GithubApp#verify_webhook_signature` treats the absence of a configured `webhook_secret` as automatic success, which breaks the equality "organization that cryptographically authenticated the request == organization whose repository/stack is written."

### Finding Description
`WebhooksController#verify_signature` selects a `github_app` using the attacker-supplied payload field `repository_owner` (`params.dig('repository','owner','login')`), then asks that app to verify `X-Hub-Signature` against `request.raw_post`: [1](#0-0) 

That verification is implemented as:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
i.e. when the configured GitHub App/org entry has no `webhook_secret`, the method unconditionally returns `true`, treating an unauthenticated request as verified. `webhook_secret` is nil-able configuration that the shipped example configs actively document as the default: [2](#0-1) [3](#0-2) 

Once `verify_signature` passes (trivially, because no secret is configured), the raw JSON body — entirely attacker controlled — is parsed and dispatched to handlers keyed purely by payload content, with no further authentication: [4](#0-3) 

Handlers resolve which `Stack`/`Repository`/`Team`/`User` to act on solely from the same untrusted payload, e.g. `Handler#repository_name` reads `payload.dig('repository','full_name')` to locate stacks to sync/deploy: [5](#0-4) 
and `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the named branch: [6](#0-5) 

The `membership` handler creates `Team` and `User` records on the fly directly from payload content, as shown by the corresponding tests: [7](#0-6) 

Because the "organization" that is treated as authenticated is a payload field read before verification, and verification itself is a no-op whenever `webhook_secret` is blank, there is no cryptographic binding tying the caller to the organization/repository whose stacks, teams, or users are subsequently written. This is structurally the same flaw as the reported `depositToken` issue: the contract (controller) accepts and acts on arbitrary attacker-supplied input (webhook payload) because the "whitelist"/verification gate (`webhook_secret` check) can be trivially absent or bypassed.

### Impact Explanation
An unauthenticated network attacker who can reach the `/webhooks` (or engine-mounted `/github/webhooks`) endpoint can, for any org configured without `webhook_secret` (a state explicitly present in the documented example configs), POST arbitrary JSON claiming to be a `push`, `pull_request`, `membership`, or `status` event. This triggers unauthorized deploy syncs (`stack.sync_github`), creation of `Team`/`User` records used for authorization, and manipulation of review-app lifecycle (archive/unarchive) — all without possessing a Shipit session, API token, or the actual GitHub webhook secret. This satisfies the Critical criterion "an unauthorized deploy" and the High criterion "escalation into `Shipit.github_teams` authorization" (forged `membership` payloads create teams/users that can influence authorization checks in `User#authorized?`).

### Likelihood Explanation
Likelihood is high in any deployment that follows the shipped example secrets templates without explicitly setting `webhook_secret`, since `webhook_secret: # nil` is the literal default shown in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`. No credentials, GitHub App private key, or repository write access are needed — only network reachability of the webhook endpoint, which is documented/mounted as a public GitHub-facing endpoint by design.

### Recommendation
Fail closed instead of failing open: `GithubApp#verify_webhook_signature` should reject (return `false`/422) when `webhook_secret` is blank rather than treating it as automatically verified, and the setup documentation/example configs should require a non-empty `webhook_secret` for any organization before webhooks are accepted.

### Proof of Concept
1. Deploy Shipit using the documented example secrets file, leaving `webhook_secret` unset for organization `victim-org` (as shown in `config/secrets.development.example.yml`).
2. As an unauthenticated attacker, POST to the webhooks endpoint:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{"ref":"refs/heads/master","after":"<attacker-chosen-sha>","repository":{"full_name":"victim-org/victim-repo","owner":{"login":"victim-org"}}}
```
3. `verify_signature` calls `Shipit.github(organization: 'victim-org')`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank (`lib/shipit/github_app.rb`).
4. `PushHandler#process` locates all non-archived stacks for `victim-org/victim-repo` on branch `master` and calls `sync_github(expected_head_sha: '<attacker-chosen-sha>')`, causing an unauthorized sync/deploy trigger without ever supplying a valid GitHub signature.
