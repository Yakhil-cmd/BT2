## Analysis

The Mattermost CVE describes a missing membership/ownership check when **linking** one resource (a Board) to another (a private Channel) — the server accepted the link request without verifying the requester actually belongs to the channel being linked to.

The closest reachable analog in `ocore` is in the **shared-address linking flow**, which is driven entirely by unauthenticated device (wallet) messages from any paired correspondent.

### Root cause

`handleNewSharedAddress` in `wallet_defined_by_addresses.js` accepts a `definition` + `signers` map coming from a peer device and only checks internal structural consistency of the payload — never that the *sender* of the message is actually one of the parties named in the definition: [1](#0-0) 

The membership check that is performed, `determineIfIncludesMeAndRewriteDeviceAddress`, only verifies that *some* address in the payload happens to belong to the receiving wallet (`my_addresses`/`shared_addresses`) — it does not verify that the message's sending device is entitled to represent any of the other addresses/paths in the definition: [2](#0-1) 

Since a target address is public information (learned e.g. from a previous payment), an attacker who is merely a paired correspondent device of the victim can craft a definition such as `["and",[["address","VICTIM_ADDRESS"],["address","ATTACKER_ADDRESS"]]]`, set `signers["r.1"] = {address: "ATTACKER_ADDRESS", device_address: attacker_device}`, and send it as `new_shared_address`. The victim's wallet will pass all the structural checks (`extractAddressPathsFromDefinition` match, `validateAddressDefinition`) and call `addNewSharedAddress`, permanently registering the attacker's device as a legitimate cosigner/member of a "shared address" that includes the victim's key — without ever confirming the attacker actually controls `ATTACKER_ADDRESS` or that the victim agreed to this association: [3](#0-2) 

### Downstream impact — private payment chain leak/misdirection

Once inserted, `shared_address_signing_paths` is used to decide who private payment chains for that address get forwarded to, purely from the DB rows created above (no re-validation of legitimacy): [4](#0-3) 

Any private-asset payment later sent to this now-poisoned "shared address" will be automatically forwarded to the attacker's device via `walletGeneral.forwardPrivateChainsToDevices`, leaking private payment chain data to an unauthorized third party who was never actually invited to be a co-signer, and the victim's wallet UI/interfaces will subsequently treat this address as multi-party co-owned (potentially soliciting/accepting a co-signature from the attacker for spending, or exposing decision-making information about a private payment counterparty relationship the victim never established).

### Title
Unauthenticated linking of arbitrary device as shared-address cosigner via crafted `new_shared_address` message leaks private payment chains - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress`/`addNewSharedAddress` in `wallet_defined_by_addresses.js` accept and persist a peer-supplied address definition and signer map without verifying that the sending device is authorized to represent any address other than the recipient's own — analogous to Mattermost's missing channel-membership check when linking a Board.

### Finding Description
The device-to-device message handler for `new_shared_address` (dispatched to `wallet_defined_by_addresses.handleNewSharedAddress`) validates only that: (1) the definition hashes to the stated address, (2) each signer address structurally matches its path in the definition, and (3) at least one referenced address belongs to the local wallet (`determineIfIncludesMeAndRewriteDeviceAddress`). It never validates that the sending correspondent device is actually the owner/controller of the other address(es) named in the definition, nor that the recipient explicitly consented to be linked into this multi-address group with that particular counterparty device. Any paired correspondent can therefore submit a definition embedding the victim's known address plus an address/device of the attacker's choosing, causing the victim's node to record `shared_addresses` / `shared_address_signing_paths` rows that designate the attacker's device as a legitimate cosigner.

### Impact Explanation
`forwardPrivateChainsToOtherMembersOfAddresses` uses these unauthenticated `shared_address_signing_paths` rows to decide which devices receive forwarded private payment chains for the shared address, meaning private payment data intended for the victim (and any real counterparty) is silently disclosed to a device that was never legitimately part of the group. It also poisons the wallet's model of who is a rightful co-signer for the address, which can be leveraged for social engineering in subsequent co-signing flows.

### Likelihood Explanation
Requires only that the attacker be a paired correspondent device of the victim (a normal, low-privilege relationship established through standard device pairing) and knowledge of one of the victim's addresses — no special access is needed, making this readily reachable.

### Recommendation
When processing `new_shared_address`, require that the message either originates from a device explicitly referenced with a matching address/definition role already known and expected by the recipient (e.g. only accept unsolicited shared-address creation if the sender's device_address matches one of the other addresses' declared device_address AND the recipient has some prior association/invitation), and/or require explicit user confirmation before writing new `shared_address_signing_paths` entries that add a new, previously-unknown device as a cosigner/forwarding recipient for an address the user controls.

### Proof of Concept
1. Attacker pairs with victim's device (normal pairing).
2. Attacker crafts `arrDefinition = ["and",[["address","VICTIM_ADDR"],["address","ATTACKER_ADDR"]]]`, computes `address = chash160(arrDefinition)`, and `signers = {"r.0": {address:"VICTIM_ADDR"}, "r.1": {address:"ATTACKER_ADDR", device_address: attacker_device}}`.
3. Attacker sends this as a `new_shared_address` device message to the victim.
4. `handleNewSharedAddress` passes all structural checks and calls `addNewSharedAddress`, inserting `shared_address_signing_paths` rows including the attacker's device.
5. Any subsequent private payment sent to the resulting shared address gets forwarded to the attacker's device via `forwardPrivateChainsToOtherMembersOfAddresses`, even though the attacker was never legitimately invited into that co-ownership relationship.

**Note on confidence:** I was unable to view the exact `case "new_shared_address":` handler body inside `wallet.js` before running out of tool iterations, so I cannot fully confirm whether any additional guard exists there before calling into `wallet_defined_by_addresses.js`. Based on the confirmed logic in `wallet_defined_by_addresses.js` itself (which contains the actual authorization-relevant checks), no such guard appears to exist, but this residual uncertainty should be verified in a full code review/Devin session.

// Checks if any of my payment addresses is mentioned.
// It is possible that my device address is not mentioned in the definition if I'm a member of multisig address, one of my cosigners is mentioned instead
function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function forwardPrivateChainsToOtherMembersOfAddresses(arrChains, arrAddresses, bForwarded, conn, onSaved){
	conn = conn || db;
	conn.query(
		"SELECT device_address FROM shared_address_signing_paths \n\
		JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?) AND device_address!=?", 
		[arrAddresses, device.getMyDeviceAddress()], 
		function(rows){
			console.log("shared address devices: "+rows.length);
			var arrDeviceAddresses = rows.map(function(row){ return row.device_address; });
			walletGeneral.forwardPrivateChainsToDevices(arrDeviceAddresses, arrChains, bForwarded, conn, onSaved);
		}
	);
}
