### Title
CCMenuController#show bypasses the ApiClient's stack scoping, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` defines a scoped `stack` lookup helper that restricts which stacks an `ApiClient` may touch to the one it is bound to (`current_api_client.stack_id`). `Shipit::Api::CCMenuController` overrides this helper with an unscoped lookup, so the equality "stack a token authorizes == stack a token touches" is broken for this single endpoint.

### Finding Description
`BaseController#stacks` and `#stack` enforce the scoping invariant for a stack-restricted `ApiClient`: [1](#0-0) 

`CCMenuController` requires only the generic `read:stack` permission and never checks *which* stack the client is scoped to, then redefines `stack` to look up any stack by `params[:stack_id]` directly on `Stack`, bypassing the `stacks` scope entirely: [2](#0-1) 

This is structurally the same bug class as the `selfRevokeSigner` report: a binding that is supposed to hold (`ApiClient.stack_id` == the stack that gets acted upon) is silently broken in one code path, because that path re-derives the "current" value (here, the stack) from attacker-controlled input (`params[:stack_id]`) instead of trusting the previously-established/scoped value. The existing test suite documents the intended invariant elsewhere: `stacks_controller_test.rb` confirms "an api client scoped to a stack will only see that one stack" for the `index`/`show` actions that go through the scoped `stack`/`stacks` helpers, but `CCMenuController` was never wired to use them.

### Impact Explanation
Any holder of a legitimately-issued `ApiClient` token that is scoped to a single stack (e.g., a low-privilege integration token meant only to expose that stack's CI status to a CCTray/CCMenu client) can query `/api/<any_other_stack>/cc_status` (or equivalent CCMenu route) for **any stack in the Shipit instance**, not just the one it was authorized for. This discloses stack name, latest deploy/build status, deploy label, and timestamp for repositories/environments the token was never granted access to — an unauthorized cross-stack read of deploy state, matching the "High: unauthenticated/unauthorized read of stack state... task streams or deploy output" impact category (here, "unauthorized" in the sense of exceeding the token's explicit stack scope).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires possession of any valid, even narrowly-scoped, `ApiClient` authentication token (Basic Auth credentials or `?token=`), which is a normal artifact handed out to lower-trust integrations (e.g., a CI status badge or CCMenu widget embedded in a semi-trusted context). Given such a token, exploitation is trivial — a single GET request with a different `stack_id` — and requires no other precondition (no GitHub write access, no webhook secret, no admin session).

### Recommendation
Make `CCMenuController` use the inherited scoped `stack`/`stacks` helpers from `BaseController` instead of overriding `stack` with an unscoped `Stack.from_param!` lookup, so that a stack-restricted `ApiClient` can never resolve a stack outside its `stack_id` scope, consistent with `DeploysController`, `TasksController`, and `StacksController`.

### Proof of Concept
1. Create two stacks, `stack_a` and `stack_b`.
2. Create an `ApiClient` scoped to `stack_a` only (`stack_id` set to `stack_a.id`) with `read:stack` permission — this is the legitimate, narrowly-scoped credential the org intended to hand out (e.g., to a semi-trusted CCTray consumer).
3. Using that client's Basic Auth token, issue `GET /api/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/cc_status.xml` (the CCMenu route resolved by `stack_id` param).
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (not `stacks.from_param!`), so it resolves `stack_b` even though the client is scoped to `stack_a`.
5. The response renders `stack_b`'s name, `lastBuildStatus`, `lastBuildLabel`, and `lastBuildTime` — data the token was never authorized to see, confirmed by the existing test `"#show renders the xml"` in `test/controllers/api/ccmenu_controller_test.rb:20-24`, which shows the endpoint trusts whatever `stack_id` is passed in without cross-checking `current_api_client.stack_id`.

        end

      end
