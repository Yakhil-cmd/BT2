This is a genuine analog: the webhook signature-verification key selection is keyed on one payload field (`repository.owner.login` / `organization.login`), while every downstream `Webhooks::Handlers::Handler` acts on a *different* field (`repository.full_name`) that the signature never specifically binds to the selected key. Since the whole body is HMAC-signed but with a secret chosen *by the attacker's own organization*, nothing forces `repository.full_name` to belong to the same organization whose secret validated the request.

### Title
Webhook signature is keyed by `repository.owner.login` but handlers trust the independent `repository.full_name` field, letting any onboarded organization forge events for other stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check with `Shipit.github(organization: repository_owner)`, where `repository_owner` comes straight from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) [2](#0-1)  Every webhook handler, however, resolves the target repository/stack from a *different* field of the same body, `repository.full_name`. [3](#0-2) 

### Finding Description
Shipit supports multi-organization deployments where each GitHub organization has its own `webhook_secret` in `secrets.github[org]`, looked up via `Shipit.github_app_config` / `Shipit.github`. [4](#0-3) 

The binding the engine implicitly relies on is:
`repository.owner.login (used to pick the HMAC secret) == repository.full_name's owner (used to pick the stack acted upon)`

Nothing enforces this equality. An attacker who legitimately owns/administers *any* GitHub organization onboarded into this Shipit instance (and therefore possesses that org's own `webhook_secret`, e.g. by configuring their own repository's webhook delivery, which is a normal, unprivileged GitHub-side action) can:

1. Set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` fetches *their own* known secret and the HMAC check passes over the raw body they control. [5](#0-4) 
2. Independently set `repository.full_name` inside the same JSON body to `victim-org/victim-repo`.
3. Because `Handler#stacks` and every concrete handler (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolve the target purely from `repository.full_name`, the forged event is dispatched against the victim's stack. [3](#0-2) [6](#0-5) 

Since the HMAC is only checked for internal consistency ("is this body signed by *some* org's secret this attacker controls?") and not for consistency between the two organization-identifying fields, the "organization that authenticated" and "repository that is written to" are decoupled — exactly the kind of trust-binding break described in the rules.

### Impact Explanation
The most damaging concrete handler is the `status` event path, which creates a `Status` record for an arbitrary commit sha of the victim stack based on attacker-controlled fields, without any cross-check against the owner used for signature verification (see `repository_params` test helper showing `repository.owner.login` is the only field checked during verification while status creation keys off `sha`/`repository.full_name`). [7](#0-6)  A stack with `continuous_deployment` enabled and CI status requirements configured via `shipit.yml`'s `ci.require` can be tricked into believing a previously-failing/pending commit now has a passing CI status, which — combined with continuous deployment — leads to an **unauthorized deploy** of a real commit on the victim's stack, satisfying the Critical-impact bar ("an unauthorized deploy"). Lower-severity but still valid abuse includes forcing unnecessary `GithubSyncJob` runs, archiving/unarchiving review stacks, or fabricating `check_suite`/`pull_request` state for repositories the attacker does not own.

### Likelihood Explanation
Requires only that the attacker be a legitimate, unprivileged administrator of *any* GitHub organization/repository already onboarded to this Shipit instance (a routine, self-service action — configuring their own repo's webhook and reading the secret GitHub gives them, or simply knowing the secret they themselves set during onboarding). It does not require a Shipit session, `ApiClient` token, GitHub App private key, or repository write access to the *victim* repository, satisfying the unprivileged-attacker constraint. Multi-tenant Shipit deployments (multiple orgs configured under `secrets.github`) are an intended, documented use case, so this path is realistically reachable.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, after verifying the signature, assert that the organization implied by `repository.full_name` (or `repository.owner.login`) used by the handler matches the organization whose secret validated the signature, and reject the webhook otherwise. Alternatively, bind `repository_owner` and `repository.full_name`'s owner segment together before dispatching to `Shipit::Webhooks.for_event`.

### Proof of Concept
1. Attacker legitimately configures Shipit for organization `attacker-org` (or already has any org onboarded) and knows `secrets.github[:attacker-org][:webhook_secret]`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and the HMAC check succeeds because attacker used their own valid secret. [1](#0-0) 
5. `Handlers::StatusHandler` (subclass of `Handler`) resolves `repository_name` from `repository.full_name` = `victim-org/victim-repo` and updates/creates the CI status on the victim's tracked commit. [3](#0-2) 
6. If `victim-org/victim-repo`'s stack has continuous deployment enabled and gates on that CI context, the forged "success" status can trigger an automatic, unauthorized deploy.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
