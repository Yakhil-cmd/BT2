## Title
Merkle leaves have the same format as parent nodes in `merkle.js`, allowing fraudulent merkle proofs to be validated by the `in merkle` authentifier and `is_valid_merkle_proof` oscript function - (File: `merkle.js`)

### Summary
`ocore`'s custom Merkle tree implementation in `merkle.js` hashes leaves and internal nodes with the exact same hash function and no domain-separation prefix. A leaf is hashed as `hash(element)` and an internal node is hashed as `hash(hash(left)+hash(right))`. Since `hash()` returns a fixed 44-character base64 SHA-256 digest, an attacker can craft an "element" string that is the concatenation of two known child digests (88 characters), causing its leaf hash to collide with the hash of a genuine internal node. This lets an attacker submit a forged (shorter) Merkle proof that validates against a legitimate Merkle root that they did not actually create a matching leaf for.

### Finding Description
The hashing routine is defined as: [1](#0-0) 

Leaves are hashed with `arrHashes = arrElements.map(hash)` (single string input), while internal (parent) nodes are hashed as `hash(arrHashes[i] + arrHashes[hash2_index])` — i.e., the concatenation of two prior 44-character base64 digests. There is no prefix byte (e.g. `0x00` for leaves vs `0x01` for nodes) to separate the two domains, so both leaf and node inputs are just opaque strings fed into the same `sha256` hash.

`verifyMerkleProof` walks up the proof siblings the same way, and the source code itself flags the exact issue this report is about: [2](#0-1) 

Because a leaf and a two-child-hash-concatenation node hash the same way, any attacker who knows (or can derive from previously published/observed proofs) two adjacent digests `h0` and `h1` at any level of the tree can construct a fake "leaf" element equal to `h0 + h1` (an 88-character string). `hash(h0+h1)` computed as a "leaf" is bit-for-bit identical to the internal node hash that the real tree computes for those two children. The attacker then submits a Merkle proof using the sibling path *above* that node (skipping the level that would have included `h0`/`h1` themselves), together with `index` corresponding to the position of that internal node. `verifyMerkleProof` will report success even though `h0+h1` was never intended to be a leaf value.

This flaw is directly reachable through two unprivileged, user-controlled code paths:
1. The `in merkle` address-definition authentifier, which lets any unit/AA author embed a serialized Merkle proof as an authentifier to satisfy an address's spending condition, checked against a previously-published data feed root: [3](#0-2) 
2. The `is_valid_merkle_proof` oscript/AA formula function, callable from any AA trigger or oscript definition to validate arbitrary attacker-supplied `element`/`proof` pairs against a caller-controlled root value: [4](#0-3) 

### Impact Explanation
Both call sites are used to gate spending or authorization logic: `in merkle` is embedded directly in address definitions to authorize spending conditional on membership in an oracle-published set (e.g., whitelists, KYC sets, voting/allowlist membership), and `is_valid_merkle_proof` is used inside AA (Autonomous Agent) oscript logic to authorize state transitions/fund releases based on proof of inclusion in a data-feed-committed Merkle root. Because a fabricated "leaf" (the concatenation of two internal hashes) can be proven as a member of the tree with a shorter, forged proof, an attacker who is not actually part of the committed set can satisfy the definition/authentifier check or the AA condition. This can result in unauthorized spending from an address whose spending condition uses `in merkle`, or unauthorized fund release/state manipulation in an AA that relies on `is_valid_merkle_proof` for access control — both concrete unauthorized-spending / AA-fund-loss outcomes.

### Likelihood Explanation
Exploitability requires the attacker to know at least one pair of sibling hashes from the target tree at some depth. In the `in merkle` and `is_valid_merkle_proof` use cases, the tree structure and intermediate hashes are typically exposed through legitimately issued proofs (siblings are transmitted in cleartext as part of any real proof, per `serializeMerkleProof`/`deserializeMerkleProof`), so an attacker who has observed even one real proof, or who can otherwise learn two adjacent node hashes, can mount the attack without any privileged access. This makes the likelihood realistic wherever such Merkle-gated definitions or AA formulas are deployed.

### Recommendation
Introduce domain separation in `merkle.js`: prefix leaf hashing and internal node hashing with distinct constant bytes/tags before hashing (e.g., `hash("0"+element)` for leaves and `hash("1"+left+right)` for nodes), or otherwise ensure leaf preimages cannot be confused with a two-hash concatenation (e.g., reject elements whose length/format matches the concatenation of two digests). Update `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently, and bump any protocol/format compatibility handling so already-published trees are not silently reinterpreted.

### Proof of Concept
1. Build (or observe from a published proof/data feed) a small Merkle tree with `merkle.getMerkleRoot`; obtain two adjacent leaf hashes `h0 = hash(elements[0])`, `h1 = hash(elements[1])` and the sibling hashes above them up to the root, as done in `test/merkle.test.js`: [5](#0-4) 
2. Construct a fake leaf `fakeElement = h0 + h1`. Compute `hash(fakeElement)`; observe it equals the real internal node hash `hash(h0+h1)` computed by `getMerkleRoot`/`getMerkleProof`.
3. Build a proof object `{ index: <index of the internal node>, siblings: <siblings above that node>, root: <same real root> }` and call `merkle.verifyMerkleProof(fakeElement, proof)` — it returns `true`, even though `fakeElement` was never a genuine leaf.
4. Feed this crafted `element`/`proof` pair into either the `in merkle` authentifier evaluation path or the `is_valid_merkle_proof` oscript function to demonstrate that spending/authorization conditions relying on genuine set membership can be satisfied fraudulently.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
