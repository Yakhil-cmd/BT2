### Title
TPS-fee "current network throughput" estimator can be manipulated by cheap AA triggers to spike required fees for all other unit senders - ([File: storage.js])

### Summary
The external report describes an attacker cycling `submit`/`withdraw` actions to manipulate a shared limit-tracking counter, eventually disabling the affected action for other users. ocore has an analogous shared, global resource: the network-wide "current TPS" estimate that drives the mandatory `tps_fee` every unit must pay. This estimate counts not just real units but a synthetic multiplier (`max_aa_responses`, up to `MAX_RESPONSES_PER_PRIMARY_TRIGGER`) for every unstable unit that merely targets an AA address, regardless of whether the AA actually produces that many responses. An attacker can therefore cheaply post units addressed to an AA, inflate the global unstable-unit TPS counter, and force `getCurrentTpsFee()`/`getMinAcceptableTpsFeeMultiplier()` to soft-reject other users' units for insufficient `tps_fee` — a "submit" that raises a shared limit and locks other users out, analogous to the reported bug class.

### Finding Description
`getCurrentTps()` sums `getCountUnitsPayingTpsFee(objUnitProps)` over every currently unstable unit to estimate live network throughput: [1](#0-0) 

`getCountUnitsPayingTpsFee` adds `count_primary_aa_triggers * max_aa_responses` (the unit's *claimed* max responses, defaulting to `constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER`) to the unit weight, independent of how many responses the AA actually produces: [2](#0-1) 

`count_primary_aa_triggers` is simply the count of output addresses that are AA addresses — reachable by any unprivileged unit poster/AA trigger sender who names an AA as a payment output address: [3](#0-2) 

This inflated per-unit weight is fed straight into the global, mci-independent TPS estimator used for admission control of every other unit on the network: [4](#0-3) 

Because `getCurrentTpsFee` grows exponentially with `tps`(`base_tps_fee * (exp(tps/tps_interval)-1)`), a handful of AA-triggering units sitting unstable can push the required `min_acceptable_tps_fee` for the whole mempool sharply upward: [5](#0-4) 

Once the attacker's units stabilize, `updateTpsFees` recomputes the fee from the AA's *actual* `count_aa_responses` and refunds any pre-paid excess back into the attacker's `tps_fees_balance` bucket: [6](#0-5) 

This refund-after-stabilization is the "withdraw" half of the cycle: the attacker pays the (much smaller) real fee, gets the surplus credited back, and can repeat the "submit" (post a fresh batch of AA-addressed units) to keep the counter inflated — the same submit/withdraw manipulation pattern the external report flags, applied to a shared global rate-limiting counter instead of a per-user balance.

### Impact Explanation
While the attacker's units are unstable (which can be a sustained window if the attacker keeps a steady stream of cheap AA-addressed units flowing), every other unit author on the network faces an artificially high `min_acceptable_tps_fee`. Units that don't pay this inflated fee are soft-rejected via `createTransientError`, i.e., temporarily un-confirmable: [7](#0-6) 
This matches the "network unable to confirm new units" impact class: normal users' transactions are priced out or rejected while the attacker's true cost is only the marginal real `tps_fee`/`actual_tps_fee` difference which is refunded through `tps_fees_balance`. This is a network-wide griefing/DoS vector on unit admission rather than a localized balance bug, but it is the closest concrete, reachable analog to "manipulating submit/withdraw cycles to disable an action for other users."

### Likelihood Explanation
Any address can author a unit and add an output naming an AA address, and any address can set `max_aa_responses` up to `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, so the primitive is trivially reachable without special privileges — only the cost of the base `tps_fee` for the crafted units and standard unit fees. The condition needed (keeping several such units unstable simultaneously) is a normal, expected network state (confirmation is not instantaneous), so the attack window naturally recurs. I was not able to fully verify, within the available tool budget, the exact numeric magnitude of `MAX_RESPONSES_PER_PRIMARY_TRIGGER` and `tps_interval`/`base_tps_fee` defaults, nor whether other mitigations (e.g., `min_parentable_tps_fee`, OP exemptions) sufficiently dampen the effect in practice — this would need to be validated against `constants.js`'s actual default values and a live/simulated fee calculation before treating this as confirmed-exploitable at scale.

### Recommendation
- Weight the TPS estimator for unstable units by a more conservative/backstopped estimate of AA responses (e.g., a small fixed default rather than the attacker-controlled `max_aa_responses` field), or cap the aggregate influence any single unstable unit/author can have on `getCurrentTps()`.
- Consider excluding or discounting `count_primary_aa_triggers * max_aa_responses` contributions from addresses that have not historically triggered that many actual AA responses, or reconcile the estimate against `count_aa_responses` progressively as the AA executes rather than only at stabilization.
- Rate-limit or fee-scale `max_aa_responses` claims per author to prevent cheap, repeated inflation of the shared TPS gauge.

### Proof of Concept
Conceptual PoC (could not be executed in this read-only environment):
1. Attacker composes a unit whose payment output addresses include an AA address, and sets `max_aa_responses` close to `MAX_RESPONSES_PER_PRIMARY_TRIGGER` (per `composer.js:374-393`).
2. Attacker broadcasts several such units back-to-back while keeping them just unstable (e.g., by not waiting for confirmations, or by exploiting normal confirmation latency).
3. `storage.getCurrentTps()` sums the inflated `getCountUnitsPayingTpsFee` weight for these unstable units (`storage.js:1351-1377`), spiking `getCurrentTpsFee()`/`getMinAcceptableTpsFeeMultiplier()`.
4. Concurrently, honest users' units are validated against this inflated `min_acceptable_tps_fee` in `validateTpsFee` (`validation.js:1074-1095`) and are soft-rejected (`createTransientError`) unless they also pay the inflated fee.
5. When the attacker's units stabilize, `updateTpsFees` (`storage.js:1247-1275`) reconciles against the AA's actual response count and refunds the attacker's overpayment into `tps_fees_balance`, letting the attacker repeat the cycle at low net cost.


Repository: Jortegata/ocore--020

Context: The TPS-fee subsystem (files `storage.js`, `validation.js`, `composer.js`, `constants.js`) computes a network-wide "current TPS" estimate used to gate acceptance of every new unit via a `tps_fee` requirement. The estimate is computed in `storage.getCurrentTps()` / `getCountUnitsPayingTpsFee()` (storage.js, around lines 1351-1403) by summing, over all currently unstable units, `1 + count_primary_aa_triggers * max_aa_responses`, where `max_aa_responses` defaults to `constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER` but can be explicitly set by the unit's author up to that constant (see `composer.js` lines 318-399, especially 356-393). `count_primary_aa_triggers` is simply the count of AA addresses among a unit's payment output addresses. This weight is not validated against how many responses the targeted AA actually produces until the unit stabilizes, at which point `storage.updateTpsFees()` (storage.js lines 1247-1275) reconciles and refunds any overpayment into the author's `tps_fees_balance`.

Suspected vulnerability: A normal, unprivileged unit author can post low-cost units naming an AA address as output and claiming a high `max_aa_responses`, inflating the global unstable-unit TPS estimate used in `validateTpsFee()` (validation.js lines 1050-1097) and `storage.getCurrentTpsFee()`/`getMinAcceptableTpsFeeMultiplier()` (storage.js lines 1397-1467). Because `getCurrentTpsFee` grows exponentially with the estimated TPS, this can spike the `min_acceptable_tps_fee` required of all other units currently being composed/validated, causing honest units to be soft-rejected (`createTransientError`) until the attacker's units stabilize — effectively a repeatable, low-net-cost griefing/DoS on the network's ability to confirm new units, since the attacker's overpayment is refunded via `tps_fees_balance` after stabilization.

Tasks for the engineer:
1. Confirm the exact values of `constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER`, `base_tps_fee`, and `tps_interval` defaults, and trace how `max_aa_responses` is validated in `validation.js` (search all ~17 references) to determine the real bounds an attacker can set for this field per unit.
2. Build a local/testnet simulation (using ocore's test harness, e.g. `test/` scaffolding or a devnet) that: (a) posts a burst of units addressed to an existing AA with maximal `max_aa_responses`, keeping them unstable; (b) measures `storage.getCurrentTps()` / `getCurrentTpsFee()` before and during the burst; (c) attempts to post an "honest" unit from a different address during the burst and checks whether it is soft-rejected due to `tps_fee` being below `min_acceptable_tps_fee`.
3. Quantify the attacker's net cost: measure the actual `tps_fee` charged vs. the refund credited to `tps_fees_balance` after the attacker's units stabilize (per `updateTpsFees`), to confirm the cycle is net cheap/repeatable.
4. If confirmed, evaluate and prototype a fix, such as: capping the aggregate TPS-estimator contribution attributable to any single author/AA-target combination within a rolling window, weighting the estimator by a smaller default/discounted response count instead of the user-supplied `max_aa_responses`, or reconciling the estimate against actual `count_aa_responses` progressively rather than only at stabilization. Update `storage.js` (`getCountUnitsPayingTpsFee`, `getCurrentTps`, `getRecentTps`) and any related validation in `validation.js` (`validateTpsFee`) accordingly, with regression tests covering both the exploit scenario and normal AA-trigger throughput accounting.
5. Document findings (confirmed exploitable / mitigated by existing protections / not exploitable) with concrete numbers from the simulation, since this could not be verified through static code reading alone.

function getCountUnitsPayingTpsFee(objUnitProps) {
	let count_units = 1;
	if (objUnitProps.count_primary_aa_triggers) {
		const max_aa_responses = (typeof objUnitProps.max_aa_responses === "number") ? objUnitProps.max_aa_responses : constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER;
		count_units += objUnitProps.count_primary_aa_triggers * max_aa_responses;
	}
	return count_units;

	if (last_stable_mci === null)

	const since_mci = last_stable_mci + shift;
	let count = count_units; // include the current unit and its AA responses
	let since_timestamp = 0;

	for (let unit in assocUnstableUnits) {

		if (objUnitProps.timestamp > now) continue; // skip future-timestamped units
		if (objUnitProps.main_chain_index > since_mci || objUnitProps.main_chain_index === null)
			count += getCountUnitsPayingTpsFee(objUnitProps);
		else if (shift > 0 && objUnitProps.main_chain_index === since_mci) {
			if (objUnitProps.timestamp > since_timestamp)
				since_timestamp = objUnitProps.timestamp;
