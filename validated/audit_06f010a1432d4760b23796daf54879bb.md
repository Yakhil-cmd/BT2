### Title
Unchecked ERC721 `transferFrom` Return in Bridge Deposit Allows Free Cross-Chain NFT Minting — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.sol` calls `IERC721.transferFrom` in both the deposit path (`requestERC721Transfer`) and the withdrawal path (`handleERC721Transfer`) without verifying that the transfer actually succeeded. If a registered ERC721 token does not revert on failure, an attacker can trigger a cross-chain bridge request without depositing the NFT, causing bridge operators to mint or release an NFT on the counterpart chain for free. The bridge nonce is permanently consumed and the `HandleValueTransfer` event is emitted regardless of whether the asset moved.

---

### Finding Description

**Deposit path — `requestERC721Transfer`** [1](#0-0) 

```solidity
function requestERC721Transfer(
    address _tokenAddress,
    address _to,
    uint256 _tokenId,
    bytes memory _extraData
) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
}
```

`IERC721.transferFrom` returns `void`; its success is never verified. If the token does not revert on failure, `_requestERC721Transfer` is still called, which emits `RequestValueTransferEncoded` and increments `requestNonce`. [2](#0-1) 

**Withdrawal path — `handleERC721Transfer` (non-mintBurn mode)**

The bridge updates its nonce and emits `HandleValueTransfer` *before* attempting the asset transfer: [3](#0-2) 

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);          // nonce consumed here
emit HandleValueTransfer(...);                // event emitted here

// transfer happens last — failure is silent
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```

If `transferFrom` silently fails, the nonce slot is permanently consumed and the event is emitted, but the NFT is never delivered to `_to`.

---

### Impact Explanation

**Deposit path (higher severity):** An attacker who calls `requestERC721Transfer` with a registered ERC721 token that does not revert on failure receives a valid bridge request event without depositing the NFT. Bridge operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer` on the counterpart chain, which mints or releases an NFT to the attacker. The attacker obtains a bridged NFT at zero cost — an unauthorized mint of a bridged asset.

**Withdrawal path:** If `transferFrom` silently fails during `handleERC721Transfer`, the bridge nonce is permanently consumed (the request can never be replayed), the `HandleValueTransfer` event is emitted (observers believe the transfer succeeded), but the NFT remains locked in the bridge contract. The user who burned or locked their NFT on the source chain loses it permanently.

Both cases corrupt the bridge's protected accounting state (`lowerHandleNonce`, `handleNoncesToBlockNums`, `closedValueTransferVotes`) relative to actual asset ownership. [4](#0-3) 

---

### Likelihood Explanation

Likelihood is conditional on a registered ERC721 token that does not revert on `transferFrom` failure. Token registration is controlled by bridge operators (`onlyRegisteredToken` / `onlyOwner`), so a malicious or buggy token must first be registered. However, once registered, any unprivileged user can trigger the exploit. Non-reverting ERC721 implementations exist in the wild (custom or upgradeable tokens), and the bridge provides no defense-in-depth check after registration. [5](#0-4) 

---

### Recommendation

1. **Deposit path:** After calling `transferFrom`, verify the bridge actually received the token:
   ```solidity
   IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
   require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "transfer failed");
   ```
   Alternatively, use `safeTransferFrom` which performs the `onERC721Received` callback and reverts if the receiver does not accept.

2. **Withdrawal path:** Move the nonce update and event emission to *after* the successful transfer, or wrap the transfer in a `require`:
   ```solidity
   IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
   require(IERC721(_tokenAddress).ownerOf(_tokenId) == _to, "transfer failed");
   // then update nonce and emit event
   ```

3. Add documentation warning operators to only register ERC721 tokens that revert on failure.

---

### Proof of Concept

1. Deploy a non-reverting ERC721 token `MaliciousNFT` where `transferFrom` is a no-op (does not revert, does not move the token).
2. Bridge operator registers `MaliciousNFT` on the child bridge.
3. Attacker calls `requestERC721Transfer(maliciousNFT, attacker, tokenId, "")`.
4. `transferFrom(attacker, bridge, tokenId)` silently does nothing — the bridge does not receive the NFT.
5. `_requestERC721Transfer` emits `RequestValueTransferEncoded` with `requestNonce = N` and increments `requestNonce`.
6. Bridge operator's off-chain relay (`handleRequestValueTransferEvent` in `node/sc/bridge_manager.go`) observes the event and calls `handleERC721Transfer` on the parent bridge. [6](#0-5) 

7. Parent bridge mints or transfers `tokenId` to the attacker on the parent chain.
8. Attacker holds the NFT on the parent chain; the child chain bridge nonce is consumed; no NFT was ever deposited.
