### Title
Attacker-controlled `.gitmodules` submodule URLs can redirect operator-configured git credentials to unauthorized repositories on the same host - ([File: main.go])

### Summary
The Aave `swapLiquidity` bug allowed an attacker to redirect a trusted resource (an allowance the `LendingPool` held on behalf of others) to an arbitrary attacker-chosen `receiverAddress`. The closest reachable analog in `git-sync` is the `--credential` / submodule-authentication mechanism: git-sync stores operator-supplied, per-URL credentials via `git credential approve` [1](#0-0) , explicitly to support fetching submodules that live at different URLs than the top-level repo [2](#0-1) . Submodule URLs, however, come from the synced repository's `.gitmodules` content, which is attacker-controlled if the attacker has push access to the tracked repo (the same trust position as the "liquidity provider" caller in the Aave report) [3](#0-2) .

### Finding Description
`git-sync` merges all `--credential` entries and feeds them to `git credential approve` keyed only by a URL string supplied at startup by the operator [4](#0-3) [1](#0-0) . Git's default credential matching is scoped by protocol+host (not by full path) unless `credential.useHttpPath` is explicitly configured. This means a credential intended for `https://git.example.com/team-a/repo` is, by git's own default behavior, also handed out for any other path under `https://git.example.com/...`.

The path under that host is not chosen by the operator at fetch time — it is chosen by whatever `.gitmodules` entries exist in the tracked repository, and `configureWorktree` unconditionally runs `git submodule update --init [--recursive]` against whatever submodule URLs are present in the currently synced commit [3](#0-2) . An attacker who can push a commit to the tracked repository (the documented, expected use case per the README's submodule/`--credential` guidance) can add or modify a `.gitmodules` entry pointing to a different, private repository on the same credential-scoped host. On the next sync, git-sync's stored, operator-provisioned credential — intended only for the legitimate submodule/repo — will be silently presented by git to authenticate the fetch of the attacker-chosen path, and the resulting (otherwise-inaccessible) repository content is checked out into the shared `--root`/`--link` output where consumers (potentially including the attacker, if the sidecar output is exposed) can read it.

This mirrors the Aave root cause exactly: a caller who is only supposed to control one parameter of a multi-step flow (here, the `.gitmodules` submodule URL "path" component) can redirect the use of credentials/allowances that were scoped and trusted for a different destination.

### Impact Explanation
Successful exploitation results in unauthorized disclosure of a private repository's contents to an attacker who only had push rights to a separate, less-privileged repository. This is a credential/authorization-scope violation: the git-sync operator's provisioned per-host credential is used, without their intent, to fetch content the attacker was not supposed to reach. This is squarely within the accepted impact class ("credential or token disclosure," "publishing wrong or partial content").

### Likelihood Explanation
This requires: (1) the git-sync deployment to use `--credential` with host-scoped (not `useHttpPath`-restricted) credentials for submodule support — a documented, encouraged configuration [5](#0-4) ; (2) submodules enabled (`--submodules` not `off`); and (3) the attacker having write/push access to the tracked repository (or a repository that becomes a submodule source), which is the same "unprivileged but repo-content-controlling" attacker position used throughout the analog rules and in the original Aave report (any caller of `swapLiquidity`). Likelihood is moderate — it depends on operator configuration choices (using shared/broad credentials plus submodules) that the README's own example actively suggests.

### Recommendation
- Document and, where feasible, enforce that `--credential` entries be scoped as narrowly as possible (recommend/require `credential.useHttpPath=true` semantics or full-URL exact matching) so a stored credential cannot be reused for an unrelated path on the same host.
- Consider validating or allow-listing submodule URLs against the credentials/hosts the operator has explicitly provisioned, rejecting or warning on submodule URLs that resolve to hosts/paths not already known to `--credential`/`--repo`.
- Surface a warning in logs when a newly discovered `.gitmodules` entry causes a previously-configured credential to be used against a new destination.

### Proof of Concept
1. Operator runs `git-sync --repo=https://git.example.com/org/app --credential='{"url":"https://git.example.com","username":"svc","password-file":"/creds/pw"}' --submodules=recursive --root=/mnt/git`. Note the credential URL is host-scoped (`https://git.example.com`), matching the documented example pattern [6](#0-5) .
2. Attacker has push access to `org/app` (the tracked repo) and adds `.gitmodules` pointing a submodule at `https://git.example.com/org/private-secret-repo`, then commits/pushes.
3. On the next poll, git-sync fetches the new commit and runs `git submodule update --init --recursive` [3](#0-2) ; git presents the stored `svc` credential (matched by host) to authenticate the fetch of `private-secret-repo`.
4. The private repo's contents are checked out under `--root`/`--link`, disclosing data the attacker did not otherwise have access to, wherever the git-sync output volume is consumed.

Note: I could not fully verify from the indexed code whether `credential.useHttpPath` is set anywhere by git-sync (no occurrence found in the indexed files), which is the key mitigating/aggravating factor for this analog; a Devin session with full repository/terminal access would be needed to confirm git's exact credential-matching configuration and to run the PoC end-to-end.

```go
// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```
