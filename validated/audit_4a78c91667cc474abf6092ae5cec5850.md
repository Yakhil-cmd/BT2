### Title
Webhook signature is verified against the payload's `repository.owner.login`, but write actions are dispatched using the (unverified-as-consistent) `repository.full_name`, allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a payload against by reading `repository.owner.login` out of the same untrusted JSON body it is trying to authenticate, then all downstream write operations key off a different field of that same body, `repository.full_name`. Because the HMAC check only proves "this body was signed by *some* org's secret", not "the `owner.login` and `full_name` fields are mutually consistent", an attacker who legitimately controls one onboarded GitHub organization's webhook secret can forge a payload whose `owner.login` matches their own org (so their own valid signature passes) while `full_name` points at a completely different organization's repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick the app whose secret must reproduce `X-Hub-Signature`:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

Once verification passes, `create` dispatches the raw parsed JSON to every handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers resolve the target `Stack`/`Repository` not from `owner.login`, but from a separate field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Nothing in the controller or the handler base class enforces that `full_name` is namespaced under `owner.login`. Both fields are attacker-controlled inside the very JSON body being HMAC-signed - the signature only proves "some app's secret signed this exact byte string", it does not bind `owner.login` to `full_name` semantically. An attacker who owns/administers any GitHub organization that is itself onboarded into this same multi-tenant Shipit deployment (and therefore legitimately knows that org's `webhook_secret`, configured per-organization via `Shipit.github(organization:)`) can set `repository.owner.login` to their own org (so `verify_signature` selects a key they can correctly sign with) while setting `repository.full_name` to `"<victim-org>/<victim-repo>"`. The signature check passes, and the handler then acts on the victim's `Stack`.

For example, `PushHandler` will force-sync any not-archived stack of the victim's repo/branch to an attacker-chosen SHA:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

`MembershipHandler` likewise creates/mutates `Team` and `Membership` records keyed by `params.organization.login`/`params.team.id`, both independently attacker-supplied fields of the same signed body, letting an org-A-signed payload manipulate team membership entries associated with org B. [6](#0-5) 

This is the direct analog of the reported bug class: the field that is checked/authenticated (`repository.owner.login`, used to pick the verifying key) is not the field that is actually acted upon (`repository.full_name`, used to select the mutated resource) - i.e. "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker who controls (or compromises) any single GitHub organization/App onboarded onto the shared Shipit instance can forge webhook events that trigger writes against a completely different, unrelated organization's stacks: forcing `sync_github` to an attacker-chosen commit SHA, or manipulating `Team`/`Membership` records tied to another org. Because `sync_github`/downstream continuous-deployment flows can lead to deploy triggers, this crosses the "cross-repository writes" / "unauthorized deploy" bar for Critical severity, without the attacker ever needing the victim organization's own webhook secret, App credentials, or repository access.

### Likelihood Explanation
Exploitation only requires legitimate control of the webhook secret for any one organization already configured in the same Shipit deployment - a realistic condition for any multi-tenant Shipit installation serving several GitHub orgs/teams, and requires no privileged Shipit session, API token, or victim-org credential. Constructing a payload with mismatched `owner.login`/`full_name` fields is trivial since both are plain JSON strings under attacker control.

### Recommendation
Bind the field used for signature-key selection to the field used for the actual write: either (a) verify that `repository.full_name` starts with `#{repository_owner}/`, rejecting mismatches before dispatching to handlers, or (b) always derive the target repository/organization for handler dispatch from the same value that selected the verifying key (`repository_owner`), never from an independently-controlled sibling field of the payload.

### Proof of Concept
1. Shipit hosts stacks for two independent orgs, `org-a` and `org-b`, each with its own GitHub App/`webhook_secret` configured via `Shipit.github(organization:)`.
2. Attacker legitimately administers `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` over this exact raw body using `org-a`'s known `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, loads `org-a`'s `GitHubApp`, and successfully verifies the attacker's correctly-computed HMAC.
6. `create` runs `PushHandler`, which resolves `repository_name` = `"org-b/victim-repo"` via `Handler#repository_name`, finds `org-b`'s real `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` - a write against `org-b`'s stack triggered entirely with `org-a`'s credentials.
