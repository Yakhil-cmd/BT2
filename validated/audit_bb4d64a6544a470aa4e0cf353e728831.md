### Title
Cross-repository `Status` write via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by SHA with no repository/stack scoping, unlike every other webhook handler in the engine which resolves the target stacks via `Repository.from_github_repo_name(repository_name)`. Since git SHAs are content-addressed and identical across forks/mirrors of a repository, a status webhook that is legitimately signed for one repository can be replicated onto `Commit` rows belonging to a completely different `Stack`/`Repository` that happens to share the same commit SHA (e.g. a fork of the victim's repo), letting an attacker who only controls their own fork inject CI state into a victim's stack.

### Finding Description
The broken binding: the code should guarantee `status.stack_id == commit_that_authenticated_the_webhook.stack_id` for every `Status` created from a webhook, i.e. a status event authenticated for repository `R` should only ever create/update `Status` rows on commits belonging to stacks of `R`. In practice:

- `WebhooksController#verify_signature` authenticates the webhook only against `repository_owner` (`params.dig('repository','owner','login')`), calling `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) . This proves the payload came from GitHub for *some* repository owned by that org — it does not bind the SHA to that specific repository at all.
- `WebhooksController#create` then dispatches the whole payload to `StatusHandler.call(params)` [2](#0-1) .
- `StatusHandler#process` resolves target commits solely by `params.sha`, with zero use of `params.repository` or any repository/stack scoping:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

Compare this to the base `Handler` class, which provides a `stacks` helper explicitly scoped to the repository that authenticated the request (`Repository.from_github_repo_name(repository_name)&.stacks`) [4](#0-3)  — a helper `StatusHandler` never calls. `PushHandler` and the `PullRequest` handlers all resolve `repository` from `params.repository.full_name` before acting [5](#0-4) , confirming that `StatusHandler` is the outlier.

`Commit` rows are only unique per `(stack_id, sha)` (indexed via `20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally unique on `sha`. This means multiple `Stack`/`Repository` pairs can legitimately hold `Commit` rows with the identical SHA whenever they track forks/mirrors of the same underlying git history — a routine occurrence in engineering orgs that fork within the same GitHub organization or maintain a public repo and internal forks.

Exploit flow:
1. Victim stack `V` (repository `org/victim`) has `review_stacks_enabled: true`, `provisioning_behavior: allow_all`, and requires status context `buildkite/deploy` to be `success` before merging/deploying.
2. Attacker forks `org/victim` to `org/attacker-fork` (or any repo under an org for which Shipit's GitHub App is installed, satisfying `Shipit.github(organization: repository_owner)`), and pushes/labels/opens a PR containing a commit whose SHA is identical to a commit already tracked by Shipit for `V` (trivial, since forks share history).
3. Attacker (or their CI) posts a `status` webhook for `org/attacker-fork`'s SHA/context `buildkite/deploy`/`state: success` (or `failure`). GitHub signs this webhook correctly because it is a real, legitimately-triggered event for a repo the attacker controls.
4. `verify_signature` passes because it only checks the org's HMAC secret, not which repository's SHA is referenced.
5. `StatusHandler#process` matches `Commit.where(sha: ...)` against **all** commits with that SHA across the Shipit instance, including the commit belonging to `V`, and calls `commit.create_status_from_github!(params)` on it — writing a `Status` row scoped to `V`'s `stack_id` [6](#0-5) .
6. This status transition fires `deployable_status`/`commit_status` hooks and `stack.schedule_merges` [7](#0-6) , which — combined with `V`'s `continuous_deployment` or `review_stack` auto-provisioning/merge behavior — can trigger an unauthorized deploy or unblock a merge on `V`, a stack the attacker never authenticated against.

Existing guards fail to prevent this because: `verify_signature` authenticates the org, not the SHA-to-repository binding; there is no `ExplicitParameters` constraint tying `sha` to `repository`; and `StatusHandler` never consults `repository_name`/`stacks` the way sibling handlers do.

### Impact Explanation
A payload authenticated for one repository (or fork) can write a `Status` (CI result) onto a `Commit`/`Stack` belonging to a different repository that the attacker does not control, matching the "payload for one repository mutating another's stack/commit" Critical impact class. Because `Status` creation drives `deployable?`/`blocked?` logic and can schedule continuous deployment or unblock merge requests on the victim stack [8](#0-7) , this can result in an unauthorized deploy or a wrongful block of the victim's pipeline. This is repeatable against any stack whose commit history overlaps (via fork/mirror) with a repository the attacker can legitimately trigger webhooks for.

### Likelihood Explanation
The precondition is that the attacker's repo owner (org login) must be one for which Shipit already has GitHub App/webhook credentials configured (`Shipit.github(organization: repository_owner)` must resolve, else `GithubOrganizationUnknown` yields a 422) [9](#0-8) . This is realistic in organizations that use GitHub Apps installed org-wide (common setup) and allow forking within the org, or where the victim repo itself is public and forkable and Shipit is configured per-installation rather than per-repo. Once that precondition holds, the attack requires no Shipit session, API token, or secret — only the ability to trigger a normal, legitimately-signed `status` event from a repo/fork the attacker owns, which is well within the stated unprivileged attacker capabilities.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the `Handler#stacks` pattern used elsewhere: resolve `Repository.from_github_repo_name(params.repository.full_name)`, then only update `Commit` rows whose `stack_id` belongs to that repository's stacks (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), rather than an unscoped global SHA lookup.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not update a commit belonging to a different repository sharing the same SHA" do
  victim_repo = shipit_repositories(:shipit) # org/victim
  attacker_repo = Shipit::Repository.create!(owner: 'org', name: 'attacker-fork')

  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  shared_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus),
                                                committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  attacker_stack = attacker_repo.stacks.create!(environment: 'production', branch: 'master')
  attacker_stack.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus),
                                  committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'buildkite/deploy',
    'repository' => { 'full_name' => attacker_repo.github_repo_name, 'owner' => { 'login' => 'org' } }
  }

  # BINDING UNDER TEST: status.stack_id (of any Status created) must equal
  # the stack_id of the repository that authenticated the webhook (attacker_stack.id),
  # never victim_stack.id.
  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
This test currently fails against the present implementation (the victim commit's status count increases), demonstrating that `StatusHandler` writes a `Status` for `victim_stack` even though the webhook only authenticated `attacker_repo`.
