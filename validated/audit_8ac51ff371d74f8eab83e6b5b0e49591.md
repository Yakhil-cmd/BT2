### Title
Unfiltered pull-request-label-derived `PATH` (and other env keys) override the sanitized git PATH in `Command#unbundled_env`, enabling RCE via `StackCommands#fetch`/`#git_clone` - (File: lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no allowlist, and `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` writes those label names straight from the webhook body with no filtering. `StackCommands#env` (`super.merge(@stack.env)`) forwards this attacker-controlled hash into `git(...)`/`git_clone(...)` calls used by `#fetch`, `#fetch_commit`, `#fetched?`, which construct a `Shipit::Command` whose `#unbundled_env` merges `@env` **last**, letting a label literally named `path` (upcased to `PATH`) fully replace the sanitized `PATH` Shipit sets for subprocess execution.

### Finding Description
The broken binding: the invariant claimed by the question is that the env hash passed to `PTY.spawn` should be restricted to `deploy_spec.machine_env` + declared `VariableDefinition` names. In fact:

`env_keys(PTY.spawn) == deploy_spec.machine_env.keys ∪ VariableDefinition.names` is FALSE; it is actually `env_keys(PTY.spawn) ⊇ pull_request.labels.map(&:upcase)` with no allowlist at all.

Path:
1. `LabelCapturingHandler#capture_labels` takes the webhook's `pull_request.labels[].name` and stores them verbatim: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [1](#0-0) . This handler runs on `opened`, `labeled`, `unlabeled`, and `reopened` pull_request webhook events for any repository with review stacks enabled, i.e. reachable by any fork PR author against a repo with review-stacks configured [2](#0-1) .
2. `ReviewStack#env` merges those raw label names, upcased, straight into the env hash with value `"true"` and no key allowlist: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [3](#0-2) .
3. `StackCommands#env` forwards this into git commands: `super.merge(@stack.env)`, and `#fetch`/`#fetch_commit` explicitly pass this `env:` into `git('fetch', ...)` or `git_clone(...)` [4](#0-3) . Because `env:` is explicitly supplied at these call sites, `Commands#git`'s `kwargs[:env] ||= base_env` default never triggers, so the label-derived hash is used verbatim, not `base_env`.
4. `Command#initialize` stores `@env` unchanged aside from stringifying values: `@env = env.transform_values { |v| v&.to_s }` [5](#0-4) , with no key allowlist anywhere in this class.
5. `Command#unbundled_env` builds the final environment for `PTY.spawn` by merging `@env` **last**, after the safe `PATH`: `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` [6](#0-5) . If the attacker's label is named `path`, the upcased key `PATH` in `@env` overwrites Shipit's sanitized `PATH` entirely.
6. `Command#start` invokes `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) . The `git` invocations built by `Commands#git` use the bare executable name `"git"` (no absolute path) [8](#0-7) , so the OS resolves it via `PATH`. An attacker-controlled `PATH` value that points to a directory containing a malicious file named `git` causes that file to execute instead of the real `git` binary, with full permissions of the Shipit deploy host process.

Why existing guards don't stop this: `EnvironmentVariables#permit` is the only env allowlisting mechanism in the codebase, and it is used solely for deploy/rollback plan variables in `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs` [9](#0-8)  — it is never applied to `Stack#env`, `ReviewStack#env`, or `StackCommands#env`. The webhook params schema (`ExplicitParameters`) only validates that `labels[].name` is a `String`, imposing no content or key restriction [10](#0-9) . `verify_signature`/webhook signature checks authenticate that the *payload* came from GitHub for that repo, but do nothing to sanitize the *content* of `labels[].name`, which the PR author (or anyone with label-set permission on their own fork/PR, depending on repo settings) fully controls.

### Impact Explanation
An attacker who can label a PR (which, per the existing test suite, includes emoji and free-form Unicode names, confirming no content restriction [11](#0-10) ) can inject an arbitrary environment variable KEY, including `PATH`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, etc., into every subsequent `git fetch`/`git clone` invocation Shipit performs for that review stack's git cache. Overwriting `PATH` to point at an attacker-supplied directory (which the attacker can pre-populate via files committed to their own fork, then reference relative to the stack's working directory) allows a fake `git` binary to execute instead of the real one, achieving Remote Code Execution on the Shipit deploy host under the Shipit process's privileges. This matches the "Critical – RCE on the deploy host via `Command`/`PTY.spawn`" category. It is repeatable against any repository that has review stacks enabled, by any fork PR author, requiring no privileged role.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (a common, not unusual, Shipit configuration for PR-based deployment). The attacker needs only to open a PR from a fork (or push a label to their own PR) and set a label whose name is `path` (case-insensitive, since it's upcased) or another sensitive env var name. This costs the attacker nothing beyond normal, unprivileged GitHub interaction — no Shipit session, API token, or GitHub App credentials are needed. It is fully repeatable and scriptable against any Shipit-managed repo with review stacks enabled.

### Recommendation
Apply an explicit allowlist to any environment hash before it reaches `Command`/`PTY.spawn`, particularly for values derived from GitHub-controlled input like PR labels. Concretely:
- In `ReviewStack#env`, reject or filter label names against a safe key pattern/allowlist before merging (e.g., disallow overriding of `PATH` and other reserved keys), or namespace label-derived variables with a fixed prefix that cannot collide with reserved names.
- In `Command#unbundled_env`, merge `@env` before setting `PATH` (or explicitly re-apply the sanitized `PATH` last) so that no caller-supplied env hash can ever override the sanitized `PATH`/other reserved keys.
- Consider applying `EnvironmentVariables#permit` (already used for deploy/rollback variables) to `Stack#env`/`ReviewStack#env` derived data as well.

### Proof of Concept
```ruby
# test/unit/command_test.rb (or a new test)
test "#unbundled_env does not allow caller-supplied env to override the sanitized PATH" do
  malicious_path = "/tmp/attacker-controlled-bin"
  command = Command.new('git --version', env: { 'PATH' => malicious_path }, chdir: '.')

  sanitized_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"

  # Broken binding today: command.unbundled_env['PATH'] == malicious_path
  # Expected/fixed binding: command.unbundled_env['PATH'] should remain sanitized_path
  refute_equal malicious_path, command.unbundled_env['PATH']
  assert_equal sanitized_path, command.unbundled_env['PATH']
end

# test/models/shipit/review_stack_test.rb
test "#env should not allow a PR label to inject a PATH override" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]  # upcased to "PATH"

  # Broken binding today: stack.env["PATH"] == "true"
  # Expected/fixed binding: stack.env should not contain a "PATH" key, or it should be rejected
  assert_nil stack.env["PATH"], "PR label should not be able to set the PATH environment key"
end
```
These two assertions demonstrate that (a) `StackCommands#fetch`/`#git_clone`'s merged env, sourced from `ReviewStack#env`, can carry a `PATH` key sourced from an unprivileged PR label, and (b) `Command#unbundled_env` lets that attacker-supplied `PATH` value override the sanitized `PATH` used for `PTY.spawn`, confirming the RCE path end-to-end without any live GitHub interaction.
