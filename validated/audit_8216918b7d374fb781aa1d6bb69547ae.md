### Title
`StatusHandler#process` writes GitHub `status` events into commits of any stack sharing the same SHA, bypassing repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha).each`, matching by bare SHA across the entire `commits` table rather than scoping the lookup to the repository that authenticated the webhook. Unlike other handlers (`push_handler.rb`, `check_suite_handler.rb`, `pull_request/*_handler.rb`) which use the base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) to scope the affected records to the repository named in the payload, `StatusHandler` performs no such scoping.

### Finding Description
The broken binding: for a `status` webhook, the intended invariant is `commit.stack.repository.full_name == payload['repository']['full_name']` — i.e., a status should only be written to commits belonging to the repository that generated the webhook. `StatusHandler#process` violates this: [1](#0-0) 

versus the scoping pattern used elsewhere in the same handler hierarchy: [2](#0-1) 

`verify_signature` in `Shipit::WebhooksController` only proves that the request was signed with the GitHub App/organization secret matching `params.dig('repository','owner','login')` — i.e., that *some* repository under that owner sent the webhook — it does not constrain which commit rows the handler is allowed to touch: [3](#0-2) 

Because `Shipit::Commit` rows are keyed by SHA1 content hash and not namespaced per repository at the handler level, `StatusHandler` will update *every* `Commit` record across *every* stack in the installation whose `sha` column matches the attacker-supplied `params.sha`, regardless of which repository authenticated the webhook. Git SHA1s are content-addressed (over tree, parents, author, committer, timestamps, message), so an attacker who owns/controls a repository registered with Shipit can, for commits with reproducible/deterministic content (e.g., empty commits, well-known initial commits, or a cherry-pick/rebase reproducing identical commit metadata), engineer a commit object in their own repo whose SHA equals a SHA present in a victim stack. The resulting `create_status_from_github!` write goes to the victim's `Commit`, affecting `Commit#status`, `Commit#blocked?` (via `stack.commits.reachable...any?(&:blocking?)` in `app/models/shipit/commit.rb`), and `Commit#deployable?`/`schedule_continuous_delivery`, which can gate or unblock deploys and merges on the victim stack: [4](#0-3) [5](#0-4) 

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) check that the commit being updated actually belongs to a stack whose repository matches the authenticated payload's repository — that scoping exists in `Handler#stacks`/`Handler#repository_name` but `StatusHandler` never calls it.

### Impact Explanation
An attacker who owns any GitHub repository can, by constructing/discovering a commit whose SHA collides with a commit SHA already present in a victim's Shipit stack, send a signed `status` webhook (signed with their own repo's/org's credentials) for `context: ci/build` and an arbitrary `state`. This flips CI status for the victim's commit, and if the victim stack has `blocking_statuses` configured, this can set or clear `blocked?`, gating or forcing deploys/merges on a stack the attacker never authenticated for. This is a cross-repository/cross-tenant state mutation — matching the "Critical: a payload for one repository mutating another's stack/commit" category.

### Likelihood Explanation
Exploitation requires the attacker to control a repository whose webhooks are accepted by the Shipit instance (own GitHub org/repo registered as a stack, or any org for which the operator's GitHub App is installed) and to produce a commit with an identical SHA1 to a targeted commit in the victim stack. Because SHA1 is a 160-bit content hash keyed on tree/parents/author/committer/timestamps/message, deliberately colliding with an arbitrary, unpredictable victim commit is not generally feasible; it becomes practical mainly for degenerate/reproducible commits (e.g., an empty initial commit with fixed committer/author identity and timestamp, which is not attacker-controlled either) or where the same commit is legitimately shared across repositories (forks, subtree/vendor syncs, mirrored branches) — a scenario explicitly called out in the question as "a SHA shared with a victim stack." In that shared-SHA scenario (e.g., a fork or mirrored branch stack), the vulnerability is fully and repeatably exploitable with no engineered SHA collision needed, since the attacker's own webhook for their own fork's commit will still match the victim's `Commit` row by bare SHA.

### Recommendation
Scope `StatusHandler#process` (and audit `check_suite_handler.rb` / any other handler not shown using `stacks`) to only update commits belonging to stacks whose repository matches the authenticated payload's repository, e.g. `stacks.commits.where(sha: params.sha)` instead of `Commit.where(sha: params.sha)`, using the existing `Handler#stacks` helper that resolves `Repository.from_github_repo_name(repository_name)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is out of scope per rules but describes the binding to assert):
1. Create `repo_a` (`Repository`) and `stack_a` with `blocking_statuses` requiring `ci/build`; create `repo_b` and `stack_b` (attacker-controlled, no blocking config needed).
2. Create a `Commit` under `stack_a` with a fixed `sha` (`SHARED_SHA`), and a `Commit` under `stack_b` with the same `SHARED_SHA` (representing a shared/forked commit).
3. Build a `status` payload: `{ sha: SHARED_SHA, state: 'failure', context: 'ci/build', repository: { full_name: repo_b.full_name, owner: { login: repo_b.owner } } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, which is orthogonal — it only authenticates `repo_b`, not which `Commit` rows are touched).
5. Assert equality BEFORE: `stack_a.commits.find_by(sha: SHARED_SHA).blocked? == false` (or whatever the pre-state is) and the binding under test is `commit_a.stack.repository.full_name == payload['repository']['full_name']` — which is `stack_a.repository.full_name != repo_b.full_name`.
6. Assert AFTER: `stack_a.commits.find_by(sha: SHARED_SHA).blocking?` is now `true` (status written despite the payload having authenticated only `repo_b`), and `stack_a.commits.find_by(sha: SHARED_SHA).blocked?`/`deployable?` state has changed as a result — proving the write crossed repository boundaries.
