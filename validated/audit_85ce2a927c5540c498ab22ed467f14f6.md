### Title
Unbounded memory leak of eventBus listeners/closures for queued private payment chains that never complete validation - (File: `wallet.js`)

### Summary
`handlePrivatePaymentChains()` in `wallet.js` registers a one-time `eventBus.once(key, …)` listener (holding a closure over `arrPrivateElements`, `ws`, `assocValidatedByKey`, and the outer callbacks) for every private-chain element that `network.handleOnlinePrivatePayment()` reports as `ifQueued`. The reference to that listener/closure is only ever released when the corresponding `key` event eventually fires (validation completes) or when `cancelAllKeys()` is invoked by a synchronous validation error in the same batch. There is no timeout, TTL, or periodic sweep that removes stale listeners for chains whose validation never resolves, unlike other in-memory caches in the same codebase (e.g. `archiving.js`'s `assocCachedPrunedJoints` with a `PRUNED_JOINT_CACHE_TTL_ms`, or `network.js`'s `assocUnitsWaitingForPrunedContent` with `purgeExpiredUnitsWaitingForPrunedContent`).

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` [1](#0-0)  is reachable directly from any private-payment counterparty (a device sending private chains over the wallet protocol). For each private element it builds a `key = 'private_payment_validated-' + unit + '-' + json_payload_hash + '-' + output_index` and calls `network.handleOnlinePrivatePayment`. If the outcome is `ifQueued` (the most likely outcome for light clients per the code comment), the code does:

```js
ifQueued: function(){
    eventBus.once(key, function(bValid){ ... });
    cb();
}
``` [2](#0-1) 

This listener is released only when `key` is eventually emitted by the network layer, or by `cancelAllKeys()`:
```js
var cancelAllKeys = function(){
    for (var key in assocValidatedByKey)
        eventBus.removeAllListeners(key);
};
``` [3](#0-2) 

`cancelAllKeys()` is only invoked from the `async.eachSeries` final error callback (a *synchronous* error surfaced during the same request's processing) [4](#0-3) , or from inside the listener itself if `bValid` is falsy [5](#0-4) . If the unit the chain depends on never gets validated/emitted (e.g., its parent unit is withheld, the chain references a unit that never arrives, or validation stalls for any reason not covered by an explicit emit of `key`), the `eventBus.once(key, …)` registration — and everything captured in its closure (`arrPrivateElements`, i.e. the full private payment payload, plus references to `ws`, `assocValidatedByKey`) — remains permanently attached to the shared `eventBus` singleton. Each distinct set of `arrChains` produces a new `cache_key` (`objectHash.getBase64Hash(arrChains)`) [6](#0-5) , so a counterparty can trivially generate an unbounded number of never-resolving `key`s (e.g., by sending private chains that reference deliberately-withheld ancestor units), each adding a new permanent listener/closure to `eventBus`.

This mirrors the CVE-2021-47119 bug class: a reference (buffer head / here, an `eventBus` listener + closure) is not released before/independently of the resource life-cycle event it depended on (`kill_bdev` / here, chain validation completion), so under repeated triggering by an unprivileged actor the leak accumulates without bound, exactly as the CVE's systemd mount/unmount loop amplified the kernel-side leak.

### Impact Explanation
This is a per-node memory-exhaustion issue triggerable by any private-payment counterparty (no special privilege required), matching the report's allowed reach ("private-payment counterparty"). Sustained exploitation degrades or crashes the victim node's process (wallet/hub), which can lead to denial of service for legitimate private-payment processing on that node — a node effectively "unable to confirm new units" for its private-payment workflow once memory pressure or crash occurs.

### Likelihood Explanation
High likelihood of triggerability: any device peer can send `handlePrivatePaymentChains` requests with crafted `arrChains` whose head unit can be made to never validate (e.g., referencing a unit that is never delivered), driving the code into the `ifQueued` branch repeatedly with distinct `cache_key`s so the dedup cache (`handledChainsCache`) at line [7](#0-6)  does not suppress new attempts.

### Recommendation
Add an expiry/TTL mechanism for pending `assocValidatedByKey`/`eventBus.once(key, …)` registrations analogous to `purgeExpiredUnitsWaitingForPrunedContent` in `network.js`, so that listeners for chains that never resolve within a bounded time window are removed via `eventBus.removeAllListeners(key)` and the associated closures released. Additionally, consider bounding the total number of concurrently pending queued private-payment validations per peer/device.

### Proof of Concept
1. As a paired device / private-payment counterparty, send `handlePrivatePaymentChains` with an `arrChains` payload whose head private element references a `unit` that the recipient node will never receive/validate (e.g., a bogus but well-formed unit reference, or one whose ancestor is deliberately withheld).
2. `network.handleOnlinePrivatePayment` returns `ifQueued`, causing `wallet.js` to register `eventBus.once(key, …)` [8](#0-7) ; because the referenced unit never arrives/validates, `key` is never emitted and the listener is never removed.
3. Repeat with a new distinct `arrChains` set each time (varying units/payload so `cache_key` differs) to bypass `handledChainsCache` dedup [9](#0-8) .
4. Observe unbounded growth of `eventBus` listeners/closures over time as no cleanup path is ever exercised for these entries.

**Note on confidence**: I was unable to fully trace where exactly `network.js` emits the `key` events (`private_payment_validated-...`) and under what conditions such emission is guaranteed to eventually happen for every queued chain, since the tool budget was exhausted before I could inspect `network.js`'s private-payment handling functions (`handleOnlinePrivatePayment`, `handleSavedPrivatePayments`, and the several matches found by `grep_search` for `private_payment_validated-` in `network.js`) in full. If it turns out `network.js` guarantees emission (success or failure) for every queued chain within a bounded time in all cases (including dropped/witheld dependencies), this analog would not hold. I recommend a follow-up read of those `network.js` sections to confirm whether `key` emission is truly unconditional/bounded before treating this finding as fully validated.
