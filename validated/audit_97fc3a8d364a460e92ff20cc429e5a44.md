### Title
V3→V4 vote account auto-conversion silently resets the "other" commission collector to a stale default - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
When a legacy `VoteStateV3` account is upgraded on-the-fly to `VoteStateV4` (via `try_convert_to_vote_state_v4`), any instruction that touches only one of the two new V4-only fields — `inflation_rewards_commission_bps`/`inflation_rewards_collector` or `block_revenue_commission_bps`/`block_revenue_collector` — causes the *other*, untouched field to be silently (re)written to a V4-conversion default rather than preserving whatever value the withdraw authority had previously configured (or leaving it unset/neutral). This mirrors the SecondSwap bug class: a state-mutating call that is supposed to touch only one setting inadvertently resets a sibling setting to a default that the account's authority did not choose.

### Finding Description
`update_commission_collector` in `programs/vote/src/vote_state/mod.rs` operates on a `VoteStateHandler` obtained via `get_vote_state_handler_checked`, which internally calls `try_convert_to_vote_state_v4` (`programs/vote/src/vote_state/handler.rs`) whenever the underlying account is still serialized as V3. That conversion routine fabricates V4-only fields that don't exist in V3 — in particular it sets `inflation_rewards_collector = vote_pubkey` and `block_revenue_collector = node_pubkey` as fixed defaults [1](#0-0) .

The test at `programs/vote/src/vote_state/mod.rs` lines 4734-4796 documents the exact side effect: calling `update_commission_collector` for `CommissionKind::InflationRewards` on a V3-backed account correctly updates the caller's intended field, but as a byproduct of the implicit V3→V4 conversion, the untouched `block_revenue_collector` field is written to `v3_node_pubkey` (its V4-conversion default) instead of retaining any prior semantic value or a neutral/unset state [2](#0-1) .

The commission update path (`update_commission_bps`, lines 827-859) exhibits the analogous pattern for the numeric commission-in-basis-points fields: it calls `get_vote_state_handler_checked` (which performs the same implicit V3→V4 upgrade) and then updates only the requested `kind`'s field, leaving the sibling field however the conversion routine initialized it [3](#0-2) .

Because this conversion is triggered lazily on *any* instruction touching the account (not a one-time explicit "initialize" step gated by an issuer/authority-controlled flag), a withdraw authority who intentionally sets one collector/commission value cannot prevent a subsequent, unrelated instruction (updating the other kind) from clobbering the sibling field back to the conversion default the first time it flips from V3 to V4 semantics — precisely the "no `initiated` guard" root cause identified in the SecondSwap report, where toggling one setting silently overwrote another that the account owner had already configured.

### Impact Explanation
This does not directly move funds, but it corrupts vote-account commission/collector state — the on-chain mechanism controlling where inflation and block-revenue rewards commission gets paid. A validator operator relying on an already-configured `block_revenue_collector`/commission (set prior to any V4-triggering instruction) could have that value silently reset the first time any instruction interacts with the account under new V4 semantics, redirecting or defaulting commission collection against the authority's actual intent. This is analogous to the original finding's unauthorized change of a fee-relevant parameter (`maxSellPercent`) via an unrelated state-toggle side effect, but scoped to vote-account commission accounting rather than direct token transfers.

### Likelihood Explanation
The trigger requires only that: (1) a V3 vote account still exists (V3 is the pre-V4 legacy format, so any vote account not yet upgraded qualifies), and (2) any instruction is submitted that calls `update_commission_collector` or `update_commission_bps` for only one of the two commission kinds, signed by the authorized withdrawer. No special privilege beyond being the withdraw authority (which is the normal authorized caller for these instructions) is needed, and the withdraw authority itself may trigger this unintentionally on their own account, or a third party could be relied upon/tricked into calling the "other" kind's update to disturb settings — this is a builtin (`programs/vote`) reachable from an ordinary transaction.

### Recommendation
When performing the implicit V3→V4 conversion in `try_convert_to_vote_state_v4` (`programs/vote/src/vote_state/handler.rs`), do not fabricate default values for `inflation_rewards_collector`/`block_revenue_collector` (or their bps counterparts) that overwrite what should be a "never configured" sentinel. Instead, track whether each V4-only field has been explicitly initialized, and only apply defaults on genuine first-initialization (e.g. via `InitializeAccountV2`), never as a side effect of an unrelated single-field update instruction converting the account format. Alternatively, make the V3→V4 conversion set both fields once and persist that state so subsequent single-field updates cannot re-trigger the default-assignment path.

### Proof of Concept
The existing regression test in-tree already demonstrates the behavior end-to-end: [4](#0-3) 
1. Start with a V3-serialized vote account with a chosen `authorized_withdrawer` and `node_pubkey`.
2. Call `update_commission_collector` requesting only `CommissionKind::InflationRewards` with a new collector.
3. Observe: the requested field (`InflationRewards` collector) is updated to the new value as expected — but `CommissionKind::BlockRevenue`'s collector, which was never touched by the caller, gets silently set to `v3_node_pubkey` (the conversion default) rather than remaining in its prior (or a neutral) state, exactly as asserted in the test at lines 4790-4795.

        // V3 -> V4 auto-conversion side-effect: updating one collector against a
        // V3-serialized account causes the "other" collector to be written as
        // its V4 default (inflation_rewards_collector = vote_pubkey,
        // block_revenue_collector = node_pubkey), per try_convert_to_vote_state_v4.
        {
            let v3 = get_max_sized_vote_state_v3();
            let v3_node_pubkey = v3.node_pubkey;
            let v3_withdrawer = v3.authorized_withdrawer;
            let v3_vote_pubkey = solana_pubkey::new_rand();

            let v4_size = VoteStateV4::size_of();
            let mut account_data = vec![0u8; v4_size];
            bincode::serialize_into(&mut account_data[..], &VoteStateVersions::V3(Box::new(v3)))
                .unwrap();
            let mut v3_vote_account =
                AccountSharedData::new(rent.minimum_balance(v4_size), v4_size, &id());
            v3_vote_account.set_data_from_slice(&account_data);

            let v3_signers: HashSet<Pubkey> = vec![v3_withdrawer].into_iter().collect();

            let transaction_context = new_transaction_context(
                vec![
                    (id(), processor_account.clone()),
                    (v3_vote_pubkey, v3_vote_account),
                    (new_collector, collector_account.clone()),
                ],
                vec![
                    InstructionAccount::new(1, false, true),
                    InstructionAccount::new(2, false, true),
                ],
                &rent,
            );
            let instruction_context = transaction_context.get_next_instruction_context().unwrap();
            let mut borrowed_vote_account = instruction_context
                .try_borrow_instruction_account(0)
                .unwrap();

            update_commission_collector(
                &mut borrowed_vote_account,
                target_version,
                NewCommissionCollector::NewAccount(
                    instruction_context
                        .try_borrow_instruction_account(1)
                        .unwrap(),
                ),
                CommissionKind::InflationRewards,
                &v3_signers,
                &rent,
            )
            .unwrap();

            // The updated field reflects the caller's new collector.
            assert_eq!(
                get_commission_collector(&borrowed_vote_account, CommissionKind::InflationRewards),
                new_collector,
            );
            // The *other* field was reset to its V4-conversion default
            // (block_revenue_collector = node_pubkey from the V3 source).
            assert_eq!(
                get_commission_collector(&borrowed_vote_account, CommissionKind::BlockRevenue),
                v3_node_pubkey,
            );
        }
