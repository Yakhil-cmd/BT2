### Title
Fork PR labels (`allow_with_label`) let an attacker inject arbitrary environment variables (e.g. `PROMPT_COMMAND`) into every command spawned for the review stack - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no allowlist, and this hash is merged last (i.e. with highest priority) into the environment handed to `Command#start`/`PTY.spawn`. An unprivileged fork contributor who can label their own PR can therefore set any environment variable name they want — including `PROMPT_COMMAND` — for every command Shipit runs against that review stack.

### Finding Description
The broken binding: the intended invariant is `env_reaching_PTY_spawn.keys ⊆ allowlisted_keys ∪ {stack-defined SHIPIT_* vars}`. In practice, `env_reaching_PTY_spawn.keys ⊇ pull_request.labels.map(&:upcase)` with no filtering at all.

Trace:
1. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim from the webhook payload onto `pull_request.update!(labels: ...)`, with no character/format restriction beyond `requires :name, String` in the params schema. [1](#0-0) 
2. `ReviewStack#env` unconditionally merges those raw label strings, uppercased, into the stack's environment hash: `labels[label_name.upcase] = "true"`, with no key allowlist. [2](#0-1) 
3. `TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for review stacks) early, and only later merges `deploy_spec.machine_env` and `@task.env` — so any label key not explicitly redefined by those later merges survives untouched into the final hash passed to `Command.new(command_line, env:, ...)`. [3](#0-2) 
4. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and `unbundled_env` is computed as `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — the attacker-controlled `@env` (which includes the label-derived keys) is merged **last**, giving it precedence over `BASE_ENV`/`PATH` and any other host-defined defaults. [4](#0-3) 

Because a PR label named `prompt_command` becomes the env key `PROMPT_COMMAND` with value `"true"`, and this reaches the process environment of every command spawned for that review stack via a PTY, an attacker fully controls this and other environment variable names for build/deploy steps run against their own fork's review stack. No existing guard (`verify_signature`, params schema, `EnvironmentVariables#permit`, or a key allowlist) restricts which label names can become environment variable keys — the params schema only validates the `name` is a `String`, not its contents, and no allowlist exists in `ReviewStack#env`.

### Impact Explanation
The attacker can inject arbitrary environment variable names/values (bounded to string value `"true"`, but the key is fully attacker-chosen) into every command executed for their review stack's provisioning/deploy/task pipeline, including the `machine.environment` step. Variables like `PROMPT_COMMAND`, `BASH_ENV`, or other shell-influencing variables that get honored by scripts/tools invoked under a PTY can result in unintended command execution on the Shipit deploy host in the context of the review-stack's task process. This affects only the attacker's own fork/review-stack (blast radius limited to that stack's task execution), but it is fully repeatable per PR/label and requires no privileges beyond opening/labeling a PR on a repo configured with `provisioning_behavior: allow_with_label`. This matches the "Critical — RCE on the deploy host via `Command`/`PTY.spawn`" category since it is a code-path within this engine that lets an untrusted actor control the process environment of a spawned command.

### Likelihood Explanation
Preconditions: the target repository must be configured with `provisioning_behavior: allow_with_label` (or otherwise allow review stacks for fork PRs), which is documented as the exact scenario in the question. The attacker only needs to open a PR from their own fork and add a label with the desired name (e.g. `prompt_command`) — labeling one's own PR requires no elevated GitHub permission on public repos accepting fork PRs, and the webhook path (`LabelCapturingHandler`) requires no Shipit credentials, only a valid GitHub webhook (which GitHub itself sends). This is low-cost and fully repeatable.

### Recommendation
Restrict `ReviewStack#env` to a strict allowlist of safe label-derived variable names (or prefix them, e.g. `SHIPIT_LABEL_<NAME>`, so they can never collide with sensitive environment variable names like `PROMPT_COMMAND`, `BASH_ENV`, `LD_PRELOAD`, `PATH`, etc.). Additionally, in `Command#unbundled_env`, do not allow caller-supplied `@env` to silently override security-sensitive base environment keys — merge `@env` through an explicit denylist/allowlist rather than unconditionally last.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/command_test.rb`):
1. Build a `ReviewStack` with an associated `pull_request` whose `labels` include `"prompt_command"`.
2. Assert `review_stack.env["PROMPT_COMMAND"] == "true"` (demonstrates the injection point).
3. Build a `TaskCommands`/`Command` instance using this stack's `env` for a `machine.environment` step, and call `Command#unbundled_env`.
4. Assert `command.unbundled_env["PROMPT_COMMAND"] == "true"`, proving the attacker-controlled label value reaches the environment hash passed to `PTY.spawn`, with no allowlist filtering it out.
