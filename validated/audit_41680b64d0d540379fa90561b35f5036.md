### Title
CCMenuController ignores ApiClient stack scoping, allowing a stack-scoped token to read any stack's CI/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping through its `stacks`/`stack` helper methods: when an `ApiClient` has a non-nil `stack_id`, `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)`, and every subsequent `stack` lookup goes through that scoped relation. [1](#0-0)  `Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving directly from the global `Stack` relation using only the request's `stack_id` param. [2](#0-1) 

### Finding Description
The equality that should hold is: `token.authorized_stack == stack.touched_by_request`. For a stack-scoped `ApiClient` (`stack_id` present), `BaseController#stack` preserves this by delegating to `stacks.from_param!`, which is pre-filtered to `Stack.where(id: current_api_client.stack_id)`. [1](#0-0) 

`CCMenuController` is mounted under the same `require_permission :read, :stack` gate, which only validates that the `read:stack` string is present in the client's `permissions` array — it never checks which stack the permission applies to. [3](#0-2)  The actual stack-identity restriction is supposed to come exclusively from the `stacks`/`stack` scoping helper, but `CCMenuController#stack` re-implements stack lookup independently of that helper:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

As a result, any valid `ApiClient` token that only has `read:stack` and is scoped to stack A (e.g. an admin-issued client with `stack_id` set, or the per-user "CCMenu Client" created automatically by `CCMenuUrlController`) can be replayed against `GET /api/stacks/:stack_id/ccmenu.xml?token=...` for stack B, C, or any other stack in the installation. `#show` will happily render stack B's latest deploy/rollback status. [4](#0-3) 

### Impact Explanation
This is an unauthenticated (token-holder, not privileged-session) read of stack state for stacks the token was never authorized to access — matching the "High" impact bucket of unauthenticated read of stack state / deploy output. A minimally-scoped, low-trust token (one legitimately obtained only for a single, possibly public/unimportant, stack) can be used to enumerate deploy status, last build label, and CI activity of every other stack in the Shipit instance, defeating the entire purpose of per-stack API client scoping.

### Likelihood Explanation
Likelihood is high: `token` is a normal, low-privilege credential that a user can self-provision (`CCMenuUrlController#client` auto-creates a `read:stack`-only client for any logged-in user), and exploitation is a single unauthenticated GET request with an attacker-controlled `stack_id` route param — no additional privilege, signature bypass, or session is required beyond possessing any valid CCMenu token.

### Recommendation
Route `CCMenuController#stack` through the same scoped `stacks` relation used by `BaseController` (e.g. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so stack-scoped tokens cannot be used against stacks outside their `stack_id`.

### Proof of Concept
1. As any logged-in Shipit user, visit the CCMenu URL endpoint for stack A: `GET /A_owner/A_repo/production/ccmenu_url` → `CCMenuUrlController#fetch` creates/fetches a `read:stack`-only `ApiClient` and returns a signed `token`. [5](#0-4) 
2. Using that same `token`, request `GET /api/stacks/B_owner/B_repo/production/ccmenu.xml?token=<token>` for an unrelated stack B.
3. `CCMenuController#authenticate_api_client` accepts the token (it is valid, just not scoped to B), and `#stack` resolves B directly via `Stack.from_param!`, bypassing any stack-id restriction, returning B's CI/deploy status in the XML response. [6](#0-5)
