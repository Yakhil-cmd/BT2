## Title
Stack-scoped `ApiClient` token can read CCMenu status for any stack, not just the one it is scoped to - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` implements a binding between an `ApiClient`'s `stack_id` scope and the stacks it is allowed to touch: any client created with a `stack_id` is restricted to that one stack via the `stacks` method, and the generic `stack` helper resolves the requested stack only from that restricted relation. [1](#0-0) 
`Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly from the unscoped `Stack` model instead of the scoped `stacks` relation, and its permission check is only the generic `read:stack` capability check, not a check that the token's `stack_id` matches the requested stack. [2](#0-1) 

### Finding Description
`ApiClient` records can be created scoped to a single stack (`stack_id` set), and `#stack_id?` is used by `BaseController#stacks` to build a scope of exactly one stack when the client is scoped: [3](#0-2) 
Controllers that use the inherited `stack` method (e.g. `Api::StacksController`) are correctly bound to `current_api_client.stack_id`.

`CCMenuController` defines its own `stack` method that bypasses this binding entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 
The controller declares `require_permission :read, :stack`, which only calls `current_api_client.check_permissions!(:read, :stack)` — this only verifies the string `"read:stack"` is present in the client's `permissions` array, with no reference to `stack_id` at all: [5](#0-4) [6](#0-5) 

The binding that should hold is: `ApiClient.stack_id` (the stack a token authorizes) `== stack` (the stack the request actually touches). `CCMenuController` breaks this equality: any client holding `read:stack` permission — even one explicitly scoped to Stack A via `stack_id` — can supply an arbitrary `params[:stack_id]` for Stack B and successfully render Stack B's CCMenu status, because the lookup goes through the global `Stack.from_param!` rather than the client-scoped `stacks.from_param!`.

### Impact Explanation
This is an unauthenticated-scope escalation: a token deliberately restricted by an administrator to a single stack (a common pattern, e.g. the auto-generated "CCMenu Client" created per-stack by `CCMenuUrlController#client`) can be used to read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of any other stack in the installation, including private/production stacks the token holder was never meant to see. This matches the "High" impact tier of unauthenticated/unauthorized read of stack state. [7](#0-6) 

### Likelihood Explanation
The attack requires only possession of any valid `ApiClient` token with `read:stack` permission — which is exactly the class of token this feature is designed to hand out widely (embedded in CI dashboards, CCMenu widgets, etc.) and is scoped to a single stack specifically because it is expected to leak/be shared more broadly than a full API token. Exploitation only requires changing the `stack_id` in the URL of an otherwise legitimate CCMenu request; no additional privileges are needed.

### Recommendation
Make `CCMenuController#stack` go through the same scoped lookup as the rest of the API (`stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that a stack-scoped client cannot resolve a stack outside its `stack_id`.

### Proof of Concept
1. Create (or use the existing `here_come_the_walrus` fixture pattern) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id. [8](#0-7) 
2. Obtain its `authentication_token` and call:
   `GET /api/ccmenu/<Stack B id or path>?token=<token for Stack A>`
3. Because `CCMenuController#authenticate_api_client` accepts the token via `params[:token]` and `#stack` resolves through `Stack.from_param!` (unscoped), the response renders Stack B's CCMenu XML (build status/lock state) even though the token is only supposed to authorize Stack A. [9](#0-8)
