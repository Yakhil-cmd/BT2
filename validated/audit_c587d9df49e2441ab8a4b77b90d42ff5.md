The reported CVE-2016-3108 describes a local symlink attack against a CLI script (`pulp-gen-nodes-certificate`) that writes/leaks key material via insecure file operations performed by a local, unprivileged user. This bug class requires a local attacker with filesystem race/symlink capability against a privileged process — it has no meaningful analog in Polkadot SDK's actual attacker-facing entry points (signed extrinsics, XCM execute/send, or contract calls), which is what the scan method requires as the entry point for a valid finding.

I checked the closest structural analogs in the codebase — CLI/tooling code that generates and writes secret key material to disk:

- `substrate/client/cli/src/commands/generate_node_key.rs` uses `fs::write` to persist a generated node key to a user-specified path. [1](#0-0) 
- `substrate/client/keystore/src/local.rs`'s `KeystoreInner::write_to_file` uses `File::create` and sets `0o600` permissions on Unix. [2](#0-1) 
- `substrate/client/network/src/config.rs`'s `open_secret_file`/`write_secret_file` explicitly uses `OpenOptions::new().write(true).create_new(true).mode(0o600)`, which atomically fails if the target already exists (including as a symlink), avoiding the classic TOCTOU/symlink race that CVE-2016-3108 exploited. [3](#0-2) 

None of these are reachable via a signed extrinsic, XCM message, or contract call — they are operator-invoked, local CLI/node-startup tooling requiring local filesystem access to the operator's own machine, which the scan method explicitly excludes ("attacker has no privileged role... local users"/pure local file-race issues are not in-scope for a runtime bounty). There is no cross-pallet, XCM, or contract boundary where an untrusted network-facing input could induce a symlink-style file write. No further investigation path leads to a Critical/High runtime-level analog for this CVE class in this codebase.
