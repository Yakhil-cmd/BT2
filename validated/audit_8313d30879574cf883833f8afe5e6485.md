### Title
Unauthenticated NULL/undefined dereference in `handleOnlinePrivatePayment` crashes the node on malformed `private_payment` message - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment()` dereferences `arrPrivateElements[0].payload.denomination` before validating that `arrPrivateElements[0]` is an object or that it has a `payload` field. A peer or a paired wallet can trigger this by sending a malformed `private_payment` justsaying/handler payload, causing an uncaught `TypeError` (JS analog of a NULL pointer dereference), directly mirroring the ALPINE-CVE-2020-10957 pattern of "malformed parameters to an unauthenticated command → NULL pointer dereference → crash."

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` is the entry point that processes an incoming private-payment chain (sent either directly peer-to-peer or forwarded through the hub via the `'private_payment'` justsaying subject, and also reachable from `wallet.js`'s `handlePrivatePaymentChains`/"sign" flows that ultimately call into it): [1](#0-0) 

The only validation performed before accessing nested fields is:
```js
if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
    return callbacks.ifError("private_payment content must be non-empty array");
```
Immediately after, the code does:
```js
var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```
There is no check that `arrPrivateElements[0]` is a non-null object, nor that it has a `payload` property, before dereferencing `.payload.denomination`. If an attacker sends `arrPrivateElements = [null]`, `[42]`, `["x"]`, or `[{}]` (any element lacking `payload`), this line throws an uncaught `TypeError: Cannot read properties of undefined (reading 'denomination')` (or `of null`, depending on the element type) — the direct analog of the CVE's NULL pointer dereference from malformed command parameters.

By contrast, every other private-payment entry point in the codebase (`wallet.js` `handlePrivatePaymentChains`, `private_payment.js` `validateAndSavePrivatePaymentChain`) rigorously checks `isNonemptyObject(e)`, `isNonemptyObject(e.payload)`, etc., before touching nested fields: [2](#0-1) [3](#0-2) 

This shows the missing check in `handleOnlinePrivatePayment` is an inconsistency/oversight relative to the rest of the codebase's defensive pattern, exactly the class of bug the CVE describes (unauthenticated, malformed-parameter-triggered null dereference).

### Impact Explanation
An uncaught exception thrown inside a `db.query`/event-loop callback chain in Node.js is not something the `try/catch` in `handleMessageFromHub` (wallet.js) can always catch, because `handleOnlinePrivatePayment` is invoked directly from `network.js` message handling paths as well (not only wrapped by wallet.js's `doHandle` try/catch). Where the call is not wrapped in a try/catch, this becomes an uncaught exception that reaches the global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to crash the process: [4](#0-3) 

A crashed full node/hub is unable to process or relay new units, matching the "network unable to confirm new units" impact category. Because the trigger is a single malformed message from any connected peer or paired device (no privileged access, no prior authentication beyond an established connection), this is a low-effort, repeatable remote denial-of-service.

### Likelihood Explanation
Likelihood is high: the attacker only needs to establish a peer connection (or be a paired device/private-payment counterparty) and send one `private_payment` message whose first chain element lacks a `payload` field or is not an object. No cryptographic material, no prior valid unit, and no special privileges are required — this is directly analogous to the "unauthenticated sending of malformed parameters" precondition in the original CVE.

### Recommendation
Add explicit type/shape validation at the top of `handleOnlinePrivatePayment` before any field access, e.g.:
```js
if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
    return callbacks.ifError("private_payment content must be non-empty array");
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0]) || !ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("invalid private payment element");
```
before computing `unit`, `message_index`, and `output_index`. Additionally, wrap all external message-handling entry points (`handleJustsaying`, `handleOnlinePrivatePayment`, etc.) with a defensive try/catch that reports the error via `callbacks.ifError` instead of letting exceptions propagate to `uncaughtException`.

### Proof of Concept
As an established peer or paired device, send a justsaying of subject `'private_payment'` with body:
```json
[ {} ]
```
or
```json
[ null ]
```
This reaches `handleOnlinePrivatePayment(ws, [ {} ], ..., callbacks)`. `ValidationUtils.isNonemptyArray([{}])` passes, then:
```js
var output_index = arrPrivateElements[0].payload.denomination ? ... : -1;
```
throws `TypeError: Cannot read properties of undefined (reading 'denomination')` (for `[{}]`) or `Cannot read properties of null (reading 'payload')` (for `[null]`), which is unhandled at this call site and can crash the process via the global `uncaughtException` handler.
