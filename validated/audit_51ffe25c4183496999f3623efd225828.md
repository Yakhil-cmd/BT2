### Title
Unfiltered `machine.environment` in fork's `shipit.yml` lets a PR injected `BUNDLE_PATH` hijack bundler on `rollback.override` (and all other) steps - ([File: app/models/shipit/deploy_spec.rb])

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim with no whitelist, and `TaskCommands#env` merges this hash *after* it sets its own fixed `BUNDLE_PATH`, so a value from the fork's `shipit.yml` silently overrides Shipit's intended bundler sandbox path for every task type, including rollback. That polluted `env` is passed unchanged through `Command#unbundled_env` into `PTY.spawn`, giving a PR author code-execution control over any command in the deploy host's environment that shells out to `bundle`.

### Finding Description
The broken binding: Shipit intends `BUNDLE_PATH == Rails.root.join('data', 'bundler').to_s` for every task, as hard-coded in `TaskCommands#env`: [1](#0-0) 
but the actual value that reaches the spawned process is `BUNDLE_PATH == deploy_spec.machine_env['BUNDLE_PATH']` whenever that key is present, because `.merge(deploy_spec.machine_env)` is applied *after* the explicit `'BUNDLE_PATH' => Rails.root.join('data','bundler').to_s` assignment in the same call chain.

`deploy_spec.machine_env` is defined as a pass-through with no sanitization: [2](#0-1) 
This is unlike `deploy_variables`/`rollback_variables`, which are explicitly whitelisted via `EnvironmentVariables#permit` in `filter_deploy_envs`/`filter_rollback_envs`: [3](#0-2) 
That whitelist only applies to `@task.env` (the deploy-time variables a user supplies through the UI/API); `machine_env` bypasses it entirely and is merged directly.

`RollbackCommands#env` inherits from `TaskCommands#env` via `DeployCommands`, adding only `'ROLLBACK' => '1'`: [4](#0-3) 
so the corrupted `BUNDLE_PATH` (and any other attacker key) flows straight into the rollback step's `Command`.

Finally, `Command#unbundled_env` takes the `@env` hash (built from `TaskCommands#env`) and merges it on top of `BASE_ENV`, which is derived from `Bundler.unbundled_env`/`Bundler.clean_env` specifically to strip bundler-related variables: [5](#0-4) [6](#0-5) 
The attacker's `@env['BUNDLE_PATH']` overrides the cleaned value and is handed to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`: [7](#0-6) 

The `deploy_spec` for a review-stack task is read from the checked-out fork branch's working tree via `DeploySpec::FileSystem`, driven by `TaskCommands#deploy_spec`: [8](#0-7) 
so the file content is entirely attacker-controlled once a `ReviewStack` exists for that PR branch, regardless of `provisioning_behavior` (that setting only gates whether/how the review stack gets provisioned, not whether its `shipit.yml` content is sanitized — see `Repository#provisioning_behavior_*` methods, which only govern auto-provisioning, not env filtering): [9](#0-8) 
`ReviewStack#env` further only adds PR label flags, it does not filter or remove machine env keys: [10](#0-9) 

Exploit flow: attacker opens a PR from their own fork against a repo with `provisioning_behavior: allow_with_label`, adds the required label (their own PR, their own label — no privilege needed since a repo owner can label their own PR), causing Shipit to provision a review stack tracking their fork branch, whose `shipit.yml` contains:
```yaml
machine:
  environment:
    BUNDLE_PATH: /tmp/attacker_gems
rollback:
  override:
    - bundle exec some_command
```
When a rollback is triggered on that review stack, `RollbackCommands#env` resolves `BUNDLE_PATH=/tmp/attacker_gems`, and any `bundle exec`/`bundle install` invocation in the rollback step (or any step, since this affects all `TaskCommands` subclasses: deploy, rollback, fetch, tasks) loads gems from the attacker-populated directory, executing arbitrary Ruby code that runs on `require`/load, on the Shipit deploy host, with the host's ambient privileges (including `GITHUB_TOKEN` present in `base_env`).

Existing guards do not stop this: `filter_deploy_envs`/`filter_rollback_envs` never touch `machine_env`; `EnvironmentVariables#permit` is not called on it; there is no model validation restricting keys/values in `machine.environment`; `ReviewStack#env` doesn't strip it.

### Impact Explanation
Arbitrary command/code execution on the Shipit deploy host under the deploy runner's OS user, triggerable by any GitHub user who can open a PR/fork and (self-)label it on a repo configured with `allow_with_label` (or `allow_all`, which needs no label at all). This is Critical: RCE on the deploy host via `Command`/`PTY.spawn`, and it also exposes `GITHUB_TOKEN` and other secrets present in the process environment (`base_env` in `lib/shipit/commands.rb`) to the attacker-controlled gem code. The technique generalizes beyond `BUNDLE_PATH` to any environment variable an attacker wants to inject (e.g. `RUBYOPT`, `LD_PRELOAD` if the shell honors it, `PATH` is protected but other tool-specific paths are not), so the blast radius covers every step type (`dependencies`, `deploy`, `rollback`, `fetch`, `tasks`) for any repository that allows review stacks from forks.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior` set to `allow_with_label` (or `allow_all`), which is a supported, documented Shipit feature for fork-based PR review environments. The attacker needs only the ability to open a PR from a fork and label it (label ownership generally allowed on one's own PR, or `allow_all` requires no label). No Shipit credentials, GitHub App keys, or team membership are required. This is low-cost and fully repeatable against any repo with this common configuration.

### Recommendation
Sanitize `DeploySpec#machine_env` the same way `filter_deploy_envs`/`filter_rollback_envs` sanitize task env — require these keys to appear in an explicit, maintainer-approved allowlist (e.g., only variables declared in `machine.variables`, analogous to `deploy_variables`), and unconditionally reject/strip well-known dangerous keys such as `BUNDLE_PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, `GEM_HOME`, `GEM_PATH`, `PATH`, `LD_PRELOAD` regardless of allowlist. Additionally, ensure the explicit `BUNDLE_PATH` set in `TaskCommands#env` is applied last (after `deploy_spec.machine_env`) so it cannot be overridden by repository configuration at all.

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (or rollback_commands_test.rb)
test "machine.environment BUNDLE_PATH from fork shipit.yml overrides the sandboxed bundler path in rollback env" do
  stack = shipit_stacks(:shipit)
  deploy = stack.deploys.new
  task = deploy # or a Rollback task built from stack

  deploy_spec_stub = Shipit::DeploySpec.new(
    'machine' => { 'environment' => { 'BUNDLE_PATH' => '/tmp/attacker_gems' } },
    'rollback' => { 'override' => ['bundle exec malicious'] }
  )
  commands = Shipit::RollbackCommands.new(task)
  commands.stubs(:deploy_spec).returns(deploy_spec_stub)

  resolved_env = commands.env

  # Binding under test: BUNDLE_PATH must equal the fixed sandbox path, not the attacker value
  assert_equal Rails.root.join('data', 'bundler').to_s, resolved_env['BUNDLE_PATH'],
    "attacker-controlled machine.environment must not override BUNDLE_PATH"
  # Demonstrates the actual (broken) behavior:
  assert_equal '/tmp/attacker_gems', resolved_env['BUNDLE_PATH']

  # Confirm the polluted env reaches Command#unbundled_env / PTY.spawn input
  command = Shipit::Command.new('bundle exec malicious', chdir: '/tmp', env: resolved_env)
  assert_equal '/tmp/attacker_gems', command.unbundled_env['BUNDLE_PATH']
end
```
This proves that the value passed to `PTY.spawn` for the `rollback.override` step's `BUNDLE_PATH` is attacker-controlled rather than the intended sandboxed path, confirming the vulnerability end-to-end without needing live GitHub interaction.
