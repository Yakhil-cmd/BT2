### Title
Return-data / output-data-receivers appended after receipt-size validation bypass `max_receipt_size` / `max_length_returned_data` bound - ([File: runtime/runtime/src/verifier.rs], [File: runtime/near-vm-runner/src/logic/logic.rs])

### Summary
The claimed target, a `config` function inside `runtime/near-vm-runner/src/logic/logic.rs`, does not correspond to any host-call/return-data-plumbing logic I could locate in that file — the only `fn config` match there is unrelated to `promise_batch_action_*`/return-data bounding, so the specific file/function pairing in the question is not supported by the codebase. [1](#0-0) 

However, the underlying invariant the question describes — "return data is bounded and charged on every hop" — does have a real, already-acknowledged bypass in this codebase, but it lives in `runtime/runtime/src/verifier.rs` (`validate_receipt`/`validate_action_receipt`) and `runtime/runtime/src/lib.rs` (`apply_action_receipt`), not in `logic::config`. `output_data_receivers` are appended to a receipt **after** the receipt has already passed the `max_receipt_size` size-validation check, allowing the final receipt to exceed the configured size limit. This is a known, already-tracked bug (referenced as nearcore issue #12606 in code comments) with existing regression tests that explicitly document the receipt is "currently not rejected... because of a bug." [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`value_return` in `logic.rs` does correctly charge gas per byte of returned data for every `output_data_receiver` and correctly enforces `max_length_returned_data` on the value itself before it becomes a `ReturnData::Value`. [5](#0-4) 

The actual gap is downstream in the runtime: when a `FunctionCall` action's outcome is applied, if the receipt has `output_data_receivers`, `apply_action_receipt` either (a) extends an already-created new receipt's `output_data_receivers` with the parent's `output_data_receivers` (the `promise_return`/joint-promise case), or (b) constructs new `DataReceipt`s with the returned `data` appended to `output_data_receivers`. In both cases, this mutation happens strictly after `validate_receipt`/`validate_action_receipt`/`validate_data_receipt` have already checked `max_receipt_size` / `max_length_returned_data` on the receipt as constructed at that point in time. [3](#0-2) [6](#0-5) 

This is exactly the scenario documented in `test-loop-tests/src/tests/max_receipt_size.rs`: a receipt is built to be exactly at `max_receipt_size`, passes validation, and then `output_data_receivers` (or a large `value_return` payload turned into a `DataReceipt`) is appended afterward, pushing the receipt above the configured limit — with the test comments explicitly stating "The receipt should be rejected, but currently isn't because of a bug." [4](#0-3) [7](#0-6)  The `ValidateReceiptMode::ExistingReceipt` variant in `verifier.rs` explicitly documents that older/existing receipts must be tolerated above the size limit "because... there is a bug which allows to create receipts that are above the size limit," linking to issue #12606. [2](#0-1) 

An attacker (ordinary contract account) chains `promise_batch_create`/`promise_batch_then`/`promise_return`/`value_return` host calls to construct a DAG where a receipt is built up to just under `max_receipt_size`, then have a callback add `output_data_receivers` or a large returned value so that the appended data receipt exceeds `max_receipt_size` or (in some flows) `max_length_returned_data` after the size check has already passed.

### Impact Explanation
This does not bypass gas charging for the *bytes themselves* (per-byte `new_data_receipt_byte` costs are still paid in `value_return`), so it is not literally "free execution" of unbounded data. The concrete, already-acknowledged impact is that a receipt/data-receipt can be produced above `max_receipt_size`/`max_length_returned_data`, i.e., the size-bound invariant that other subsystems (e.g., bandwidth scheduler, receipt storage/state-witness size assumptions, network message size assumptions) rely on is violated. This matches the "unbounded resource use" bounty class rather than "underpriced execution": oversized receipts stored/transmitted in violation of protocol limits can strain storage, state witnesses, and cross-shard receipt transport, and is the reason the code carries a dedicated backward-compatibility carve-out (`ValidateReceiptMode::ExistingReceipt`) to avoid nodes panicking/rejecting historical chain data. [2](#0-1) 

### Likelihood Explanation
High feasibility and fully reproducible: this is not speculative — it is already exercised by dedicated regression tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) in the repository that assert an oversized receipt is produced on-chain, with code comments explicitly calling this "a bug" and referencing a public tracking issue. [8](#0-7) [9](#0-8)  No special privileges are required beyond deploying and calling a contract, which any unprivileged account can do.

### Recommendation
Re-validate the fully-assembled receipt (including `output_data_receivers` / appended `DataReceipt` payload) against `max_receipt_size` and `max_length_returned_data` after `apply_action_receipt` finishes mutating `output_data_receivers`/constructing the `DataReceipt`, before the receipt is queued for sending/storage, and reject or refund/fail the receipt rather than allowing it to propagate oversized. Alternatively, reserve/account for the maximum possible `output_data_receivers`/data payload size at the point of the initial size check so the post-mutation receipt is guaranteed to stay within bounds.

### Proof of Concept
The existing tests already serve as the PoC:
- `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_promise_return` — builds a receipt at exactly `max_receipt_size`, uses `promise_return` to graft `output_data_receivers` onto it post-validation, and asserts (`assert_oversized_receipt_occurred`) that an oversized receipt is actually produced and accepted by the chain. [10](#0-9) 
- `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_value_return` — calls `return_large_value` with a value of size `max_receipt_size`, producing a `DataReceipt` larger than the limit, and asserts the oversized receipt occurs on-chain. [11](#0-10) 

To validate as a unit test under `runtime/near-vm-runner/src/tests/`, one would need to move validation to the runtime layer (`runtime/runtime/src/verifier.rs` / `lib.rs`), since `logic.rs::value_return` itself already correctly bounds and charges for the value at the point it is set — the gap is entirely in the runtime crate's post-hoc receipt assembly, not in `near-vm-runner`'s `logic.rs`.

**Note on the stated target**: I could not confirm that `runtime/near-vm-runner/src/logic/logic.rs::config` is the function responsible for this behavior — no `fn config` performing return-data plumbing exists there in this codebase snapshot. The real root cause is in `runtime/runtime/src/verifier.rs` and `runtime/runtime/src/lib.rs`, so the file/function attribution in the question is incorrect even though the underlying vulnerability class (unbounded return-data/receipt size) is real and already tracked.

    pub fn value_return(&mut self, value_len: u64, value_ptr: u64) -> Result<()> {
        self.result_state.gas_counter.pay_base(base)?;
        let return_val = get_memory_or_register!(self, value_ptr, value_len)?;
        let mut burn_cost = ParameterCost::ZERO;
        let num_bytes = return_val.len() as u64;
        if num_bytes > self.config.limit_config.max_length_returned_data {
            return Err(HostError::ReturnedValueLengthExceeded {
                length: num_bytes,
                limit: self.config.limit_config.max_length_returned_data,
            }
            .into());
        }
        for data_receiver in &self.context.output_data_receivers {
            let sir = data_receiver == &self.context.current_account_id;
            // We deduct for execution here too, because if we later have an OR combinator
            // for promises then we might have some valid data receipts that arrive too late
            // to be picked up by the execution that waits on them (because it has started
            // after it receives the first data receipt) and then we need to issue a special
            // refund in this situation. Which we avoid by just paying for execution of
            // data receipt that might not be performed.
            // The gas here is considered burnt, cause we'll prepay for it upfront.
            burn_cost = burn_cost
                .checked_add(
                    self.fees_config
                        .fee(ActionCosts::new_data_receipt_byte)
                        .send_fee(sir)
                        .checked_add(
                            self.fees_config.fee(ActionCosts::new_data_receipt_byte).exec_fee(),
                        )
                        .ok_or(HostError::IntegerOverflow)?
                        .checked_mul(num_bytes)
                        .ok_or(HostError::IntegerOverflow)?,
                )
                .ok_or(HostError::IntegerOverflow)?;
        }
        self.result_state.gas_counter.pay_action_accumulated(
            burn_cost,
            burn_cost.gas,
            ActionCosts::new_data_receipt_byte,
        )?;
        self.result_state.return_data = ReturnData::Value(return_val.into_owned());
        Ok(())

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-logic/logic.rs#fn(VMLogic::read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
}

// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
