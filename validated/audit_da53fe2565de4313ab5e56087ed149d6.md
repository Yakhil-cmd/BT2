### Title
ERC20Transactor trusts ERC20 `transfer()` return value instead of verifying actual balance delta, breaking XCM accounting for fee-on-transfer/malicious ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor`, the `TransactAsset` implementation that lets XCM move value backed by arbitrary `pallet-revive` ERC20 contracts, credits/burns the *exact* amount specified in the XCM `Asset` whenever the underlying `IERC20.transfer()` call returns `true`, without ever checking that the sender/receiver/checking-account balances actually changed by that amount. This is the exact "fee-on-transfer breaks accounting" root cause from the source report, applied to Polkadot SDK's own `TransactAsset` boundary between XCM holding registers and arbitrary ERC20 contracts.

### Finding Description
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` both build an `IERC20::transferCall` for `amount` (the XCM-message-specified value, attacker controlled since it comes from the `Asset` fungible amount in the executed XCM program), execute it via `pallet_revive::Pallet::<T>::bare_call`, and treat a decoded `true` return value as proof that exactly `amount` tokens moved: [1](#0-0) [2](#0-1) 

There is no pre/post balance check on either the source, the `TransfersCheckingAccount`, or the beneficiary — the code only inspects the boolean success flag returned by `transfer()`, exactly the anti-pattern flagged in the source report ("There should be pre and post checks on balances to get the real amount of token"). The `amount` used to construct the `Erc20Credit` in holding (`withdraw_asset_with_surplus`, line 200) is the *requested* amount, not the amount that actually reached the `TransfersCheckingAccount`.

This transactor is wired into AssetHub Westend's runtime as one of the `AssetTransactors` used by the XCM executor: [3](#0-2) 

The `Matcher` (`assets_common::ERC20Matcher`) resolves an XCM `Asset` location to an arbitrary `H160` contract address — any account can permissionlessly deploy a `pallet-revive` contract implementing the standard `IERC20` interface (e.g. `transferCall`) and construct an XCM `Location`/`Asset` that the matcher will accept, since asset legitimacy here is determined purely by "does this contract respond to the ERC20 ABI and return `true`," not by any registry/governance allow-list, unlike `ForeignAssets`/`TrustBackedAssets` which are gated by `pallet-assets` issuance.

An attacker (no privileged role required) can therefore:
1. Deploy a `pallet-revive` contract whose `transfer()` implementation takes a fee (or arbitrarily short-changes the transfer) but still returns `true`.
2. Submit a signed `pallet_xcm::execute`/`transfer_assets`/reserve-transfer XCM program referencing that contract as the fungible asset id and an `amount`.
3. During `withdraw_asset_with_surplus`, the contract's `transfer()` moves less than `amount` into `TransfersCheckingAccount`, but `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` still credits the *requested* `amount` into the XCM holding register.
4. That holding can subsequently be `DepositAsset`ed anywhere (including back to the attacker, or forwarded remotely via `DepositReserveAsset`/`InitiateReserveWithdraw`), letting the XCM executor account for and move `amount` of "backed" value when the checking account never actually received it.

### Impact Explanation
This breaks the fungible-asset invariant the whole `TransactAsset`/holding-register model depends on: value recorded in XCM holding must correspond to value actually moved into custody. Because `Erc20Credit` unconditionally reflects the requested `amount` (not the delta observed at the checking account), a fee-on-transfer or adversarial ERC20 contract lets an attacker mint/circulate more XCM-holding value than was actually escrowed at `TransfersCheckingAccount`, i.e., an unbacked-issuance-style break of the checking-account invariant analogous to the `SolverVaults` USDT bug — subsequent legitimate holders of that ERC20-backed asset (via `deposit_asset_with_surplus` from the checking account to real beneficiaries) can end up unable to redeem the full nominal amount because the checking account's real balance is short of what the XCM layer believes it holds.

### Likelihood Explanation
The precondition (an ERC20 contract taking a fee on transfer while still returning `true`) requires only a permissionless contract deployment via `pallet-revive`, which any user can do, and normal signed-extrinsic XCM execution — no governance, no malicious collator/relayer, no stolen keys. The `ERC20Matcher`/`ERC20Transactor` accepts any contract implementing the `IERC20` ABI, so the trust boundary genuinely is "does `transfer()` return `true`," not "was the token audited to be fee-free." This makes the bug class realistically reachable by an ordinary user, matching the report's premise that a currently fee-free token could later add a fee (or be malicious from day one, in the FRAME case).

### Recommendation
In `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the actual `balanceOf` of the relevant account (checking account / beneficiary) before and after the `transfer()` call and use the observed delta — not the requested `amount` — when constructing `Erc20Credit`/reporting success, mirroring the "pre and post balance check" recommendation from the source report.
