### Title
`StatusHandler#process` mutates `Commit` rows across unrelated repositories via unscoped `sha` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a global, unscoped `Commit.where(sha: params.sha)` instead of restricting the query to commits belonging to the stacks of the repository named in the webhook payload. Because `Commit#sha` has no uniqueness constraint tied to `stack_id`/repository, and the webhook signature is only verified against the GitHub organization owning the payload's `repository`/`organization` field, a validly-signed webhook for an attacker-controlled repository X can update `Commit` and derived CI-status/`deployable?` state for any other Shipit-tracked stack Y whose commit history happens to share a SHA with X (e.g., both mirror the same open-source dependency).

### Finding Description
The binding that should hold but does not: `Repository.from_github_repo_name(payload['repository']['full_name']) == commit.stack.repository` for every `commit` the handler mutates.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` [1](#0-0)  only checks the HMAC signature using the `GitHubApp` selected by `repository_owner` (the `organization.login` of the payload). It says nothing about which repository's commits may be modified — any repo/org with a Shipit GitHub App installed and a known `webhook_secret` can produce a validly-signed `status` event naming its own `repository.full_name`.
- `Handler#stacks` correctly scopes to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) , but `StatusHandler` never uses `stacks`.
- `StatusHandler#process` instead runs a completely unscoped query: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
- `Commit` `belongs_to :stack` [4](#0-3)  and nothing in the schema enforces global SHA uniqueness across stacks/repositories — two Shipit-tracked repositories that both mirrored the same OSS dependency will legitimately contain `Commit` rows with identical `sha` values but different `stack_id`.
- `create_status_from_github!` writes a new `Status` for that commit and recomputes `status`, which feeds directly into `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [5](#0-4)  and can trigger `stack.schedule_merges` / continuous deployment via `add_status` [6](#0-5) .

Exploit flow: attacker owns/controls repository X (e.g., a public fork of a shared OSS library) with the Shipit GitHub App installed. Attacker finds (or engineers, by cherry-picking/rebasing so a specific SHA is shared) a commit SHA that also exists in target repository Y's stack (both mirrored the same upstream commit). Attacker triggers a `status` webhook for repo X (by pushing a commit/PR that causes GitHub to emit a `status` event, or, since status events can be sent for any SHA known to X, by using a CI integration on X to post a status for that SHA) — GitHub signs this webhook with X's installation secret, so `verify_signature` passes. `StatusHandler#process` then finds *all* `Commit` rows with that SHA, including the one belonging to Y's stack, and writes a forged status (e.g., `state: success`, fake `context`/`target_url`) onto it.

Existing guards do not close this gap: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the request came from the org owning the named repository, not that the commits touched belong to that repository [7](#0-6) ; `drop_unhandled_event` and `ExplicitParameters` schema only validate shape of `sha`/`state`, not ownership; `Handler#stacks` exists precisely to provide this scoping but `StatusHandler` doesn't call it.

### Impact Explanation
An attacker who controls any repository with the Shipit GitHub App installed can inject fabricated CI status onto commits of an unrelated, private target stack whenever a shared commit SHA exists (a realistic scenario for vendored/mirrored open-source dependencies, monorepo forks, or squash-merge coincidences). This can flip a target commit to `success`, unblocking `Commit#deployable?` and potentially triggering continuous deployment/merge scheduling for repository Y — an unauthorized deploy pathway — or conversely mark it `failure`/`error` to block Y's legitimate deploys (denial of a specific commit, though blanket DoS is out of scope). This is a cross-tenant payload-for-one-repository-mutating-another's-commit/stack scenario, matching the Critical impact category defined in the rules.

### Likelihood Explanation
Preconditions: attacker needs their own repository with the Shipit GitHub App/webhook installed (self-service, no privileged access to Shipit or to repository Y needed) and a commit SHA collision between X and Y's tracked history. SHA collisions are plausible but not universal — they require both stacks to have ingested the exact same commit (common for shared OSS dependencies, vendored code, or forks), which the attacker can often engineer by forking a dependency Y already tracks and pushing an unmodified upstream commit. The attacker's cost is low (own a public repo, enable the app, send a `status` event); the action is repeatable against any commit SHA the attacker can determine or predict exists in Y's stack.

### Recommendation
Scope the lookup to the payload's repository, mirroring what `Handler#stacks` already provides:
```ruby
def process
  stacks.commits.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ensures only commits belonging to stacks of `Repository.from_github_repo_name(repository_name)` are ever mutated.

### Proof of Concept
Minitest plan (no live GitHub calls needed, calling `StatusHandler.call` directly):
```ruby
test "status webhook for repository X does not mutate commits belonging to repository Y" do
  shared_sha = "a" * 40

  repo_x = shipit_repositories(:shipit) # or a factory create
  repo_y = create_repository(github_repo_name: "acme/private-app")
  stack_x = create_stack(repository: repo_x)
  stack_y = create_stack(repository: repo_y)

  commit_x = stack_x.commits.create!(sha: shared_sha, message: "shared dep bump")
  commit_y = stack_y.commits.create!(sha: shared_sha, message: "shared dep bump")

  payload = {
    "repository" => { "full_name" => repo_x.github_repo_name },
    "sha" => shared_sha,
    "state" => "success",
    "context" => "attacker-ci"
  }

  # Binding under test, checked before:
  assert_not_equal Repository.from_github_repo_name(payload["repository"]["full_name"]), commit_y.stack.repository

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_y.reload
  # Should remain unaffected if properly scoped; currently fails because it IS mutated.
  assert_empty commit_y.statuses, "commit belonging to unrelated stack Y was mutated by webhook signed for repository X"

  commit_x.reload
  assert_equal 1, commit_x.statuses.count
end
```
This demonstrates that with the current unscoped `Commit.where(sha: params.sha)`, `commit_y.statuses` is populated (assertion fails), proving the cross-tenant write; after applying the `stacks.commits.where(...)` fix, the assertion passes.
