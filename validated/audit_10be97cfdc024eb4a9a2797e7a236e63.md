# Analysis Complete

## Title
Node-as-Leaf collision in `merkle.verifyMerkleProof` allows forging inclusion for elements never in the original set - (File: `merkle.js`)

## Summary
`ocore`'s Merkle implementation in `merkle.js` treats leaf hashes and internal-node hashes as members of the exact same output domain (`sha256(...).digest("base64")`), and `verifyMerkleProof` accepts an attacker-chosen string as the "element", hashing it once to obtain the initial node value. Because internal nodes are computed as `hash(childHashA + childHashB)`, an attacker who knows any two sibling hash strings from the tree can submit `element = childHashA + childHashB` as a fake leaf. `hash(element)` then equals the real internal node's hash, and the remaining sibling chain up to the root validates normally, letting the attacker "prove" membership of an element that was never part of the original leaf set. This is the classic node-as-leaf / second-preimage collision that the code itself flags but does not fix.

## Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree by first hashing each element (`arrHashes = arrElements.map(hash)`) and then repeatedly combining pairs: `hash(arrHashes[i] + arrHashes[hash2_index])`. [1](#0-0) 

`verifyMerkleProof` starts from `hash(element)` and folds in the supplied `siblings` in order, comparing the final value to `proof.root`. The function's own comment acknowledges the risk without mitigating it: [2](#0-1) 

Because a leaf's committed value is `hash(element)` (an arbitrary-length string) and an internal node's value is `hash(childA + childB)` (concatenation of two 44-character base64 SHA-256 digests), both are produced by the identical hash function with no domain separation between "leaf" and "internal node" inputs. An attacker who can observe (or compute, if the underlying element set is public/derivable) two sibling hash strings `childA` and `childB` at any level of the tree can set `element = childA + childB`. Then `hash(element)` equals the real internal node's hash value, and by supplying the sibling chain that was originally used above that internal node up to the root, the proof verifies successfully — despite `element` never having been part of the original `arrElements` array.

This primitive is directly reachable by an untrusted AA trigger sender through the oscript function `is_valid_merkle_proof`, which evaluates both the `element` and the `proof` object entirely from trigger data with no length/format constraint beyond non-empty string, then calls straight into `merkle.verifyMerkleProof`: [3](#0-2) 

The formula validator imposes only complexity accounting, no additional restriction that would prevent this: [4](#0-3) 

The same primitive is also used for address "in merkle" authentifiers, where the merkle proof (siblings/index) portion is attacker-supplied via `assocAuthentifiers[path]`, although in that call site the `element` itself is fixed by the address definition rather than by the sender: [5](#0-4) 

The most reachable and impactful attack surface is `is_valid_merkle_proof` inside AA oscript logic, which is the exact analog of the FootiumAcademy pattern: an AA author trusts `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` (typically after separately checking `objProof.root` equals a known/trusted committed root) as proof that `trigger.data.element` belongs to a pre-committed allowlist, fee tier, division, etc.

## Impact Explanation
Any AA that uses `is_valid_merkle_proof` to gate privileged behavior (e.g., allowlist-based minting, discounted fees, whitelisted asset transfers, private-sale eligibility) based on a fixed, trusted merkle root can be bypassed. An attacker crafts an `element` string equal to the concatenation of two known internal-node hashes and supplies the sibling chain above that node; `is_valid_merkle_proof` returns `true` for an `element` that was never a genuine member of the committed set. Depending on how the AA uses the verified `element` (e.g., minting rights, fee bypass, fund release conditions), this can lead to unauthorized fund transfer/spending from the AA, bypassing intended commitment restrictions — a direct AA fund loss / unauthorized-action class of impact.

## Likelihood Explanation
Exploitability requires the attacker to know at least one pair of sibling hash values from the committed tree along with valid sibling data further up to the root. In the common intended use case, the full original element set (or a public proof-generation mechanism) is published so legitimate members can build their own inclusion proofs; this same information trivially yields all internal node hash values needed to construct the collision, mirroring exactly the escalation resolved as valid-medium in the referenced Sherlock report (the sponsor there also acknowledged this as a realistic post-audit fix target). No special network position, admin access, or race condition is required — only a normal unit/AA trigger from an ordinary user interacting with an AA that relies on `is_valid_merkle_proof`.

## Recommendation
Domain-separate leaf and internal-node hashing so they can never collide, e.g., prefix leaf inputs with a distinct tag (`hash("\x00" + element)`) and internal node inputs with another (`hash("\x01" + left + right)`), or otherwise ensure the leaf hashing function's output space cannot be produced by valid internal-node concatenations. Apply the fix in `merkle.js`'s `hash`, `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`, and document that AAs consuming `is_valid_merkle_proof` should not treat the raw hashing scheme as collision-safe until fixed.

## Proof of Concept
1. A merkle tree is built over some public/derivable set `arrElements` via `merkle.getMerkleRoot`, and its root is committed as a trusted value inside an AA's state (e.g., `var['allowlist_root']`).
2. During tree construction, at some point two adjacent hashes `h1`, `h2` (`arrHashes[i]`, `arrHashes[i+1]`) are combined into an internal node `N = hash(h1 + h2)`, which itself participates further up the tree via a sibling chain `S = [s1, s2, ...]` to the root (this is exactly the data returned by `merkle.getMerkleProof` if `N`'s position were treated as a "leaf" one level up).
3. Attacker sets `fakeElement = h1 + h2` (string concatenation of the two hash strings) and constructs `fakeProof = { index: N's index at that level, siblings: S, root: allowlist_root }`.
4. Attacker sends a unit triggering the AA with `trigger.data.element = fakeElement`, `trigger.data.proof = fakeProof`.
5. Oscript evaluates `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` → `merkle.verifyMerkleProof(fakeElement, fakeProof)`:
   - `hash(fakeElement) === N` (by construction — same string, same hash function),
   - folding in `S` reproduces `allowlist_root`,
   - function returns `true`.
6. The AA treats `fakeElement` as a proven member of the allowlist/committed set, even though `fakeElement` was never one of the original `arrElements`, enabling the attacker to trigger privileged AA logic (mint, fee bypass, fund release, etc.) tied to that "membership". [6](#0-5) [3](#0-2)

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
