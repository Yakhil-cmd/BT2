### Title
Webhook signature validation authenticates the payload's `repository.owner.login` organization while `StatusHandler` writes commit statuses scoped only by a global, unverified `sha` field, allowing cross-organization status injection - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate the HMAC signature based on `repository.owner.login` (or `organization.login`) taken from the JSON body itself. [1](#0-0) [2](#0-1)  Once the HMAC check passes for *that* organization's secret, the event is dispatched to handlers with the entire raw JSON payload, unmodified. [3](#0-2)  The `status` handler, however, never re-derives or checks the `repository` field at all — it looks up commits globally by `sha` across every stack in the installation and writes a GitHub-reported status onto them. [4](#0-3)  This breaks the binding: *the organization whose secret authenticated the request* ≠ *the repository/stack whose commit actually gets written*.

### Finding Description
Shipit supports hosting multiple GitHub organizations on one instance, each with its own `webhook_secret` configured under `config/secrets.yml`'s `github` section. [5](#0-4)  `Shipit.github(organization: repository_owner)` picks the app/secret to verify against purely from the attacker-controlled JSON body's `repository.owner.login`. [1](#0-0) [2](#0-1) 

Compare this with the base `Handler` class, which every event handler inherits from: it derives `stacks`/target repository from `payload.dig('repository', 'full_name')` — a *different* field of the same JSON body that is not cross-checked against the field used for signature selection. [6](#0-5)  `PushHandler` at least uses this repository-scoped `stacks` accessor, but `StatusHandler` bypasses it entirely and queries `Commit.where(sha: params.sha)` — unscoped by repository or organization — then calls `commit.create_status_from_github!(params)` on every match. [4](#0-3) 

Because the raw body is signed as a whole, an attacker cannot forge an arbitrary body without knowing *some* configured organization's `webhook_secret`. But an admin/maintainer of Organization A (who legitimately knows or can obtain Org A's `webhook_secret` because it is their own GitHub App configuration on the shared Shipit instance) can compute a valid HMAC-SHA1 over a crafted body whose `repository.owner.login` is `"org-a"` (so `verify_signature` succeeds using Org A's secret) while the `sha`, `state`, and `context` fields target a commit that actually belongs to Organization B's repository/stack (a completely different trust domain hosted on the same Shipit instance). Since `StatusHandler` never checks that the commit's stack belongs to the organization that was cryptographically verified, the forged `success` status is accepted and persisted for Org B's commit.

This directly maps to the report's bug class: one code path (`setInterestRate` / `verify_webhook_signature`, i.e. the thing that is "checked") differs from another path (`constructor` / `StatusHandler`'s write) that acts on the same kind of value without re-validating the binding — here, the binding "organization that authenticated" == "repository being written" is broken.

### Impact Explanation
A fabricated `success` (or any) status on an arbitrary commit directly affects deploy-gating logic: `Commit#deployable?` requires `success? && !blocked?`, [7](#0-6)  and `#schedule_continuous_delivery` triggers `ContinuousDeliveryJob` automatically once a commit becomes deployable under continuous deployment. [8](#0-7)  Tests confirm that creating a `success` status on a commit under continuous deployment enqueues a real deploy job. [9](#0-8)  An attacker who only controls one org's webhook secret on a shared Shipit instance can therefore inject a fake passing CI status onto a commit belonging to a different organization's stack and trigger an **unauthorized deploy** of that commit — meeting the "unauthorized deploy" criterion for Critical impact.

### Likelihood Explanation
This requires the attacker to already be a legitimate admin of at least one GitHub organization configured on the shared multi-org Shipit instance (so they know that org's `webhook_secret`), and knowledge of a target commit `sha` in a different org's tracked repository (SHAs are often public/guessable via GitHub itself). No repository write access to the victim org is required, and no privileged Shipit session/API token is required — the request goes straight to the unauthenticated `/webhooks` endpoint. This is realistic specifically for the documented multi-organization deployment mode, which the engine explicitly supports. [5](#0-4) 

### Recommendation
In `StatusHandler` (and any other handler that does not already scope via `Handler#stacks`), restrict the `Commit` lookup to only those commits belonging to stacks under the `repository_name`/organization that was actually authenticated by `verify_signature`, e.g. `stacks.commits.where(sha: params.sha)` using the same `Repository.from_github_repo_name(repository_name)` binding already used by `Handler#stacks`. [6](#0-5)  Additionally, `WebhooksController#verify_signature` should confirm that the organization it used to pick the `webhook_secret` matches the organization embedded in `repository.full_name`, rejecting mismatches.

### Proof of Concept
1. Configure two organizations on one Shipit instance, `org-a` (attacker-controlled webhook secret) and `org-b` (victim, tracked stack with an undeployed commit `<victim-sha>` under continuous deployment). [5](#0-4) 
2. Craft a `status` event JSON body:
   ```json
   {
     "sha": "<victim-sha>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/decoy" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-secret, body)>` and `X-Github-Event: status`, and POST to `/webhooks`.
4. `verify_signature` resolves `repository_owner` → `org-a`, verifies successfully against Org A's secret. [1](#0-0) 
5. `StatusHandler#process` finds `Commit.where(sha: "<victim-sha>")` (Org B's commit) with no ownership check, and calls `create_status_from_github!`. [4](#0-3) 
6. If Org B's stack has continuous deployment enabled, the forged `success` status schedules an unauthorized deploy. [8](#0-7) [9](#0-8)

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
