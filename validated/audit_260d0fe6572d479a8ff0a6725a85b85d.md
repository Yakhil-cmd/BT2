Confirmed: `here_come_the_walrus` fixture demonstrates a real, supported feature — `ApiClient` records can be scoped to a single `Stack` via the `stack` association [1](#0-0) , and `Api::BaseController#stacks`/`#stack` correctly restrict such a client's visible stacks to the one it's bound to [2](#0-1) . `Api::CCMenuController`, however, overrides `#stack` to bypass that scoping entirely, resolving directly against `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` collection [3](#0-2) .

### Title
Stack-scoped API token authorizes reads on any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` deliberately restricted to a single stack (`stack_id` set) can be used to read the CCMenu build-status XML of **any** stack in the Shipit instance, because `Api::CCMenuController#stack` does not honor the client's stack scoping and instead resolves the target stack directly from the request parameter.

### Finding Description
`ApiClient` supports scoping a token to a single stack via its `stack` association [4](#0-3) . The generic API base controller correctly enforces this: `stacks` returns only the client's bound stack when `stack_id?` is true, and `stack` is derived from that scoped relation [2](#0-1) . `Api::CCMenuController` inherits from `BaseController` and reuses `require_permission :read, :stack`, which only checks the client's `permissions` array (`read:stack`) via `ApiClient#check_permissions!`, not which stack it is entitled to [5](#0-4) . Crucially, `CCMenuController` redefines `stack` privately as `Stack.from_param!(params[:stack_id])`, completely discarding the `stacks`/`stack_id?` scoping check from the parent class [3](#0-2) .

This breaks the binding: `token.stack_id == requested_stack.id` is checked everywhere else in the API surface (e.g., `StacksController`, generic `stack` helper) but not in `CCMenuController`. As long as the token carries `read:stack` permission — which is the exact permission automatically granted to every stack-scoped CCMenu client minted by `CCMenuUrlController#client` [6](#0-5)  — the permission check passes for *any* `stack_id` param, not just the one the client/token was minted for.

### Impact Explanation
This is an unauthenticated-read escalation: a token intended by design to expose only one stack's public CI-style status (name, lastBuildStatus, lastBuildLabel, webUrl, activity — see fixture in `ccmenu/project.xml.builder` rendering) instead discloses this data for every stack in the install, including private/internal stacks the token holder should not have visibility into. This satisfies the "High - unauthenticated read of stack state" impact bucket, since any holder of a stack-scoped, low-privilege CCMenu token (which is routinely embedded in third-party CI dashboard tools, e.g. CCMenu clients) can enumerate build status of arbitrary stacks by varying `stack_id` in the URL.

### Likelihood Explanation
High likelihood: exploitation requires only possession of one legitimately-issued, narrowly-scoped `read:stack` CCMenu token (which by design is meant to be shared with low-trust third-party tooling) and knowledge/guessing of another stack's `to_param` (owner/repo/environment, which is often predictable or discoverable). No privileged account, GitHub credentials, or session is required beyond the token itself, which the rules permit as this is the intended, minimally-privileged credential for this exact endpoint.

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` (or reimplement it to call the inherited scoped `stacks.from_param!(params[:stack_id])`) so that stack-scoped clients cannot bypass their `stack_id` restriction.

### Proof of Concept
1. As an authorized Shipit user, mint a CCMenu URL for `stack_id=owner/repo-a/production` via `GET /stack/owner/repo-a/production/ccmenu_url` (`CCMenuUrlController#fetch`), obtaining a token scoped to that stack with `permissions: ['read:stack']`.
2. Using that token, request `GET /api/stacks/owner/OTHER-REPO/production/ccmenu.xml?token=<token>`.
3. Observe `200 OK` with the CCMenu XML project status for `owner/OTHER-REPO/production`, despite the token being scoped only to `owner/repo-a/production` — confirmed by `Api::CCMenuController#stack` bypassing the `stacks` scoping used elsewhere in the API [3](#0-2) .
