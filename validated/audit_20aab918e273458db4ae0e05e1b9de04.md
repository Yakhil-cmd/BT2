## Title
Unscoped `StatusHandler` allows cross-repository forgery of commit CI status via SHA collision from an attacker-controlled, independently-authenticated repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies an incoming GitHub `status` webhook to **every** `Commit` record whose `sha` matches, with no check that the commit belongs to a stack/repository under the organization the webhook signature was verified against. This breaks the same class of binding described in the external report (a value verified/authorized for one scope being applied to a different scope) — here, "the organization whose webhook secret authenticated the request" versus "the repository/stack whose commit status gets written."

### Finding Description
`WebhooksController#verify_signature` selects the HMAC secret to verify the raw payload using `repository_owner`, i.e., the GitHub organization identified in the *current* payload: [1](#0-0) [2](#0-1) 

This only proves the payload was sent by *some* organization's configured GitHub App/webhook secret (Shipit explicitly supports multiple organizations with independent secrets, per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`) — it does not prove the payload should be allowed to mutate state belonging to a *different* repository.

Most handlers correctly scope their side effects through `Handler#stacks`, which filters by `Repository.from_github_repo_name(repository_name)` (i.e., `payload.dig('repository', 'full_name')`): [3](#0-2) 

However, `StatusHandler#process` does **not** use `stacks` at all — it looks up commits globally by SHA across the entire commits table: [4](#0-3) 

Git commit SHA-1s are computed from tree/blob content, parent SHAs, author/committer, and timestamps — not from the hosting repository. Any actor who forks or otherwise reproduces an identical commit (e.g., a public repo, or a repo they were given commits into) will get an *identical* SHA in their own, differently-owned repository. Because `StatusHandler` doesn't check `repository.full_name` against the commit's owning stack, an attacker who:
1. Owns/administers a GitHub organization with its own Shipit-configured GitHub App (its own `webhook_secret`), and
2. Has (or creates) a commit whose SHA matches a commit already tracked by a victim's stack (e.g., by forking the victim's public repo and replaying the exact commit, or via a shared upstream commit that both repos contain),

can send (or trigger CI to send) a `status` event for their own repository/organization. That event will be correctly signature-verified using *their own* organization's secret, but `StatusHandler` will then write a fabricated commit status (e.g., `success`) onto the victim's stack's commit, because the lookup is `Commit.where(sha: params.sha)` with no repository/stack filter: [5](#0-4) 

This is the same "verified-for-A, applied-to-B" bug class as the reported `staking_pool::advance_epoch` issue: the authenticated scope (org that signed the request) is decoupled from the scope the code actually mutates (any commit sharing that SHA in any stack). Compare with `CheckSuiteHandler`, which correctly scopes via `stacks.where(branch: ...)`: [6](#0-5) 

### Impact Explanation
Commit statuses recorded this way feed directly into deploy-blocking/CI-gating logic (`required_statuses`, `blocking_statuses`, `soft_failing_statuses` in `DeploySpec`) and into `Commit#state`/`Commit#status`, which Shipit uses to decide whether a commit is deployable and whether continuous deployment should trigger a deploy. An attacker who can forge a "success" status for a commit under a victim's stack — without ever authenticating to the victim's GitHub organization or repository — can cause Shipit to treat an otherwise CI-failing or CI-pending commit as passing, enabling an **unauthorized deploy** (bypassing required CI checks) on the victim stack. This satisfies the "unauthorized deploy" / "cross-repository writes" criteria for High/Critical impact.

### Likelihood Explanation
The attacker needs: (a) their own Shipit-registered GitHub organization/App configuration (a realistic scenario in any Shipit deployment supporting multiple orgs, as documented), and (b) a commit whose SHA coincides with a commit tracked in the victim's stack — trivially achievable by forking a public/shared repository and replaying the identical commit (git SHAs are content-deterministic, not repo-scoped), then firing a `status` webhook (or triggering CI on their fork, which GitHub relays as a `status` event) referencing that SHA. No secret of the victim organization, no Shipit session, and no repository write access to the victim's repo is required — only control of one's own, separately configured GitHub org/app. This is a realistic, unprivileged-attacker path.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are scoped: resolve the target stacks via `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and only update commits belonging to those stacks, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Also add a `requires :repository { requires :full_name, String }` parameter declaration (consistent with other handlers) so the repository is a required, validated part of the payload used to scope the write.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` and `attacker-org`, each with its own GitHub App/`webhook_secret` (supported multi-org config, see `docs/setup.md` "Using Multiple Github Applications").
2. Victim has a stack tracking `victim-org/app` with a commit `C` (sha `abc123...`) that is currently CI-`pending`/`failure`.
3. Attacker forks `victim-org/app` into `attacker-org/app-fork`, preserving commit `C` unmodified (identical sha `abc123...` since git SHAs are content-derived).
4. Attacker's CI (or attacker directly, since they control the `attacker-org` GitHub App and can produce a validly signed request with `attacker-org`'s webhook secret) sends a `status` webhook event with `repository.full_name = "attacker-org/app-fork"`, `sha = "abc123..."`, `state = "success"`.
5. `WebhooksController#verify_signature` verifies the HMAC using `attacker-org`'s secret (valid) and passes the event to `StatusHandler`.
6. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, finds the victim's commit `C` (unscoped by repository), and calls `commit.create_status_from_github!(params)`, marking the victim's commit as `success` — even though the attacker never authenticated to or had access to `victim-org`.
7. If `victim-org/app`'s stack has continuous deployment enabled and this status satisfies `required_statuses`, an unauthorized deploy of commit `C` can now be triggered.
