### Title
Missing per-unit lock in `handleOnlinePrivatePayment` allows concurrent private-payment validation to race the duplicate/spend checks - (File: network.js)

### Summary
The CVE's root cause is that `hci_conn` lookup and field access happen without holding the lock that protects the object from concurrent modification/deletion, creating a TOCTOU window. The analogous pattern in ocore is `handleOnlinePrivatePayment()` in [1](#0-0) , where the `assocUnitsInWork[unit]` guard that would normally serialize concurrent handling of the same unit has been explicitly commented out for the `ifKnown` branch, so `privatePayment.validateAndSavePrivatePaymentChain()` can be invoked concurrently for the same unit/private chain from multiple sources (direct peer message, hub-relayed message, or `handleSavedPrivatePayments()` re-processing the `unhandled_private_payments` table) without any lock covering the read-modify-write sequence.

### Finding Description
`handleOnlinePrivatePayment()` is reachable directly from an unpaired-payment counterparty sending a `private_payment` justsaying/message (via hub or directly), and also indirectly through `wallet.js`'s `handlePrivatePaymentChains()` at [2](#0-1) , which is invoked upon receipt of a device message containing private payment chains.

Inside `handleOnlinePrivatePayment`, when the referenced unit is already known (`ifKnown`), the code used to set `assocUnitsInWork[unit] = true` before calling `validateAndSavePrivatePaymentChain` and clear it afterward, but both lines are now commented out: [3](#0-2) 

This means nothing prevents the same (unit, message_index, output_index) private element from being validated and saved concurrently by two independent call paths — e.g. one triggered by `handleOnlinePrivatePayment` (a private chain arriving live) and another triggered by `handleSavedPrivatePayments()` re-processing a previously queued row from `unhandled_private_payments` (the deferred path is only serialized by the unrelated `"saved_private"` mutex key, not by unit, and doesn't touch `assocUnitsInWork` either — see the commented-out check at [4](#0-3) ).

Deeper in the call chain, `private_payment.js`'s `validateAndSavePrivatePaymentChain()` performs its own duplicate check by reading `outputs` for a `(unit, asset, message_index[, output_index])` and only afterward begins its own DB transaction to insert/spend rows: [5](#0-4) 

This "read-then-decide-then-write" duplicate check is not protected by any external mutex keyed on the unit or on the addresses involved (unlike the base validation path in `validation.js`, which explicitly does `mutex.lock(arrAuthorAddresses, ...)` around the read/validate/write sequence: [6](#0-5) ). Two concurrent invocations for the same private element can both pass the duplicate check (`rows.length > 0 && rows[0].address` false, or the fields not yet populated) before either one commits its INSERT/UPDATE, then both proceed to independently call `indivisible_asset.validateAndSavePrivatePaymentChain` / `divisible_asset.validateAndSaveDivisiblePrivatePayment`, each of which issues its own `UPDATE outputs SET is_spent=1 ...` for the same `src_output` (see indivisible flow at [7](#0-6)  and divisible flow at [8](#0-7) ). Depending on interleaving with the underlying storage engine's isolation and on how `is_spent`/`is_unique` are (re)written across the two racing transactions, this window allows a maliciously crafted or replayed pair of concurrent private-payment deliveries for the same underlying output to be recorded/accepted twice by the same node's local private-payment bookkeeping, corrupting `outputs`/`inputs` state for a value the node believes it holds (private asset balance) — analogous in effect to the "modified concurrently while still referenced" UAF pattern, but manifesting here as state corruption/inconsistent acceptance rather than memory corruption.

### Impact Explanation
A successful race causes the victim node's private-asset bookkeeping (the `outputs`/`inputs` tables used to track private/hidden-asset balances) to reflect an inconsistent or duplicated state for the same private output — this can lead to acceptance of what is effectively a double-spend of a private asset output from that node's local perspective, or the wallet believing it received/holds a private balance twice. Because private assets rely entirely on each node's local bookkeeping (there is no public ledger check for private outputs beyond what's exchanged directly), this directly threatens fund-accounting correctness for the affected wallet/hub, satisfying the "double-spend of a stable output" / "node disagreement on validity" bar even though the trigger is a local race rather than a consensus fork.

### Likelihood Explanation
The attacking party is any private-payment counterparty (a party who is already permitted to send this wallet a private payment chain) — no privileged key or special network position is required. They control timing of delivery (e.g., sending duplicate/near-simultaneous copies of the same private chain via hub and/or direct peer connection, or forcing a hub-relay retry while a locally-queued copy is being reprocessed by `handleSavedPrivatePayments`), which is a directly attacker-influenceable condition. However, actually winning the race requires hitting a narrow async gap between the duplicate-check SELECT and the transaction-scoped INSERT/UPDATE, and outcomes further depend on the SQL engine's isolation/locking behavior (sqlite vs mysql) for the interleaved transactions, so reliability of exploitation is not guaranteed on every attempt — likelihood is assessed as moderate.

### Recommendation
Restore per-unit serialization in `handleOnlinePrivatePayment`/`handleSavedPrivatePayments` (re-enable the `assocUnitsInWork[unit]` guard, or introduce a `mutex.lock([unit, message_index, output_index_or_asset], ...)` wrapping the full read-check-write sequence in `private_payment.js`'s `validateAndSavePrivatePaymentChain`), so that concurrent deliveries of the same private element cannot both pass the duplicate check before either commits. Ensure the lock scope covers from the duplicate-check SELECT through the final `COMMIT`/`ROLLBACK` of the same private element's transaction.

### Proof of Concept
Conceptual (network access / two live connections needed to demonstrate timing, not verifiable statically from source alone):
1. As a counterparty who has legitimately sent (or can resend) a private payment chain to a wallet, construct two delivery paths for the identical `arrPrivateElements` for the same `(unit, message_index, output_index)`:
   - Path A: send directly to the target's peer WebSocket, invoking `handleOnlinePrivatePayment` → `ifKnown` branch (no `assocUnitsInWork` guard).
   - Path B: cause the same payment to also be queued into `unhandled_private_payments` and picked up by a concurrent `handleSavedPrivatePayments()` cycle (e.g., via the hub-relay route or a light-client re-request), which reprocesses the row independently.
2. Time the two deliveries so both reach `private_payment.js`'s duplicate-check SELECT (`private_payment.js:62-107`) before either has committed its transaction.
3. Observe whether both branches proceed to `indivisible_asset.js`/`divisible_asset.js`'s save logic and independently mark the same source output `is_spent`/insert duplicate `outputs`/`inputs` rows, producing inconsistent bookkeeping for the same private output on the victim node.

Note: because this requires precise network-timing reproduction across two live connections/DB transactions, it could not be executed or confirmed within this static-analysis session; the finding is based on the confirmed absence of the previously-present `assocUnitsInWork` lock (visibly commented out in the current source) and the absence of any equivalent lock in the downstream `private_payment.js` validate-and-save path.

function validateAndSaveDivisiblePrivatePayment(conn, objPrivateElement, callbacks){
	validateDivisiblePrivatePayment(conn, objPrivateElement, {
		ifError: callbacks.ifError,
		ifOk: function(bStable, arrAuthorAddresses){
			console.log("private validation OK "+bStable);
			var unit = objPrivateElement.unit;
			var message_index = objPrivateElement.message_index;
			var payload = objPrivateElement.payload;
			var arrQueries = [];
			for (var j=0; j<payload.outputs.length; j++){
				var output = payload.outputs[j];
				conn.addQuery(arrQueries, 
					"INSERT INTO outputs (unit, message_index, output_index, address, amount, blinding, asset) VALUES (?,?,?,?,?,?,?)",
					[unit, message_index, j, output.address, parseInt(output.amount), output.blinding, payload.asset]
				);
			}
			for (var j=0; j<payload.inputs.length; j++){
				var input = payload.inputs[j];
				var type = input.type || "transfer";
				var src_unit = input.unit;
				var src_message_index = input.message_index;
				var src_output_index = input.output_index;
				var address = null, address_sql = null;
				if (type === "issue")
					address = input.address || arrAuthorAddresses[0];
				else{ // transfer
					if (arrAuthorAddresses.length === 1)
						address = arrAuthorAddresses[0];
					else
						address_sql = "(SELECT address FROM outputs \
						WHERE unit="+conn.escape(src_unit)+" AND message_index="+conn.escape(src_message_index)+" \
							AND output_index="+conn.escape(src_output_index)+" AND address IN("+conn.escape(arrAuthorAddresses)+"))";
				}
				var is_unique = bStable ? 1 : null; // unstable still have chances to become nonserial therefore nonunique
				conn.addQuery(arrQueries, "INSERT INTO inputs \n\
						(unit, message_index, input_index, type, \n\
						src_unit, src_message_index, src_output_index, \
						serial_number, amount, \n\
						asset, is_unique, address) VALUES(?,?,?,?,?,?,?,?,?,?,?,"+(address_sql || conn.escape(address))+")",
					[unit, message_index, j, type, 
					 src_unit, src_message_index, src_output_index, 
					 input.serial_number, input.amount, 
					 payload.asset, is_unique]);
				if (type === "transfer"){
					conn.addQuery(arrQueries, 
						"UPDATE outputs SET is_spent=1 WHERE unit=? AND message_index=? AND output_index=?",
						[src_unit, src_message_index, src_output_index]);
				}
			}
			async.series(arrQueries, callbacks.ifOk);
		}
	});
