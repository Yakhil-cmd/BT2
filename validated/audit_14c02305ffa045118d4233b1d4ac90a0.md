### Title
Unauthenticated webhook spoofing via organization/repository binding mismatch in signature verification - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to use for HMAC verification based on an attacker-controlled field of the *unverified* JSON body (`repository.owner.login`), while the handlers that actually act on the event use a *different* attacker-controlled field of the same body (the target repository/stack identity) to decide what state to mutate. When any configured GitHub organization in a multi-org Shipit deployment has no `webhook_secret` set, `verify_webhook_signature` unconditionally returns `true`, letting an attacker impersonate that organization while pointing the payload at a completely different, properly-secured stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` instance to check the signature against using `repository_owner`, computed purely from the incoming JSON body: [1](#0-0) 

That app instance's `verify_webhook_signature` is then called: [2](#0-1) 

Crucially, `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the organization's `webhook_secret` is blank: [3](#0-2) 

`webhook_secret` is documented and templated as an *optional* per-organization field: [4](#0-3) [5](#0-4) 

After this "verification" step, the actual event dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) hands the *entire* raw payload to handlers such as the push handler, which look up the target `Stack`/`Repository` using the `repository.full_name` field from that same payload — a field the signature-selection step never inspects or binds to the verified organization: [6](#0-5) 

This breaks the intended binding: `organization authenticated by verify_signature == organization owning the repository/stack actually mutated by the handler`. The equality the code assumes is `repository_owner (used to pick verifying secret) == repository.full_name owner (used to find/mutate the Stack)`, but nothing enforces this — both come from the same unauthenticated JSON body, and an attacker fully controls both independently.

### Impact Explanation
In any installation configured with more than one GitHub organization (as explicitly supported and documented via the multi-org `github:` config block) where at least one organization has no `webhook_secret` configured, an unauthenticated attacker can send a POST to `/webhooks` with `X-Github-Event` set to `push`/`status`/`check_suite`/etc., set `repository.owner.login` to the org with no secret (satisfying `verify_signature` unconditionally), while setting the actual `repository.full_name` / commit `sha` fields to reference a stack belonging to a *different*, properly-secured organization. This lets the attacker inject forged `push`, `status`, or `check_suite` events for stacks they have no GitHub access to, causing `GithubSyncJob` enqueuing, fabricated commit statuses, or check-run refreshes on victim stacks without ever presenting a valid signature for that organization. This is an authentication bypass on the webhook trust boundary and an unauthorized state mutation on stacks outside the attacker's control, matching the High/Critical impact classes (unauthenticated write of stack/commit state through a boundary meant to be GitHub-signed).

### Likelihood Explanation
Exploitability depends entirely on operator configuration: a multi-org Shipit deployment where at least one configured organization omits `webhook_secret` (a configuration explicitly presented as optional in the shipped example config and documented multi-org config schema). Any operator following the documented "optional" guidance for even one org building a shared multi-org Shipit instance is exposed. No credentials, session, or GitHub App token are required — only network access to the public `/webhooks` endpoint.

### Recommendation
Bind the signature-verifying organization to the organization actually acted upon:
- Require `webhook_secret` to be present for every configured organization (reject boot/config if blank in multi-org mode), removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.
- After verification, re-derive `repository_owner` from the verified payload and assert it matches the owning organization of the `Repository`/`Stack` that the handler is about to mutate, rejecting the event otherwise.

### Proof of Concept
1. Deploy Shipit with a multi-org `github:` config containing `org-empty` (no `webhook_secret`) and `org-secured` (a real stack, secret set).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "org-empty" }, "full_name": "org-secured/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
No `X-Hub-Signature` header (or any garbage value) is required.
3. `verify_signature` calls `Shipit.github(organization: 'org-empty')`, whose `verify_webhook_signature` returns `true` immediately because `org-empty` has no `webhook_secret`.
4. `create` proceeds and dispatches the push handler against `org-secured/victim-repo`, enqueuing `GithubSyncJob` for that stack despite no valid signature ever being presented for `org-secured`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

    end
