### Title
Missing authorization check on `reject_new_shared_address` allows any paired device to delete another party's pending shared-address proposal - (File: wallet.js / wallet_defined_by_addresses.js)

### Summary
In `wallet.js`, the `handleMessageFromHub` dispatcher processes several device-message subjects that mutate the state of a shared (multisig) address under negotiation: `create_new_shared_address`, `approve_new_shared_address`, and `reject_new_shared_address`. The `approve` path enforces that the update only applies to the row belonging to the sending device (`WHERE definition_template_chash=? AND device_address=?`), effectively authorizing the mutation to the sender's own membership record. The `reject` path, however, calls `walletDefinedByAddresses.deletePendingSharedAddress(address_definition_template_chash)` with **no verification whatsoever that the sending device (`from_address`) is a member of that pending shared-address definition**. Any correspondent device that knows (or can derive/observe) the `definition_template_chash` can unilaterally destroy the whole pending multisig-address negotiation for every other legitimate cosigner. [1](#0-0) [2](#0-1) 

### Finding Description
The device-message handler dispatches on `subject`:

- `approve_new_shared_address` → `approvePendingSharedAddress(chash, from_address, address, ...)`, which performs an `UPDATE ... WHERE definition_template_chash=? AND device_address=?`, scoping the effect strictly to rows owned by the sender (implicit authorization by row ownership). [3](#0-2) 

- `reject_new_shared_address` → only validates that `body.address_definition_template_chash` is a syntactically valid address/chash, then immediately calls `deletePendingSharedAddress(chash)`, which unconditionally deletes both `pending_shared_address_signing_paths` and `pending_shared_addresses` rows for that chash, with no `device_address` predicate and no membership check at all. [4](#0-3) [5](#0-4) 

This is the same bug class described in the mailcow report: a destructive/deletion action lacks the authorization check that is present on the corresponding edit/approve action. Here, the "victim" resource is a pending collaborative address-creation record (used for multisig or shared/contract addresses, which underlie escrow, arbiter contracts, and AA-controlled multisig wallets). Because `handleMessageFromHub` only requires that `from_address` be a *known correspondent* (not a member of this specific pending negotiation) for this subject to be processed, any paired device that is a correspondent of the victim — even one with no relationship to the specific multisig address being negotiated — can send a forged `reject_new_shared_address` message and irreversibly erase the negotiation state for all real cosigners.

### Impact Explanation
Deleting the pending shared address record silently aborts the collaborative creation of a multisig/shared address for every legitimate participant without their consent. Shared addresses created through this flow are frequently used to secure funds in multi-signature wallets, arbiter/prosaic escrow contracts, and other multi-party fund-custody arrangements. An attacker who is merely a paired correspondent of one of the participants (not even a party to the specific address) can indefinitely block or repeatedly grief the setup of such addresses, freezing the ability of legitimate users to establish a shared custody address they rely on for holding/spending funds. This matches the "freezing" impact category, since the participants can never complete a shared address that was already in progress, and the attack can be repeated indefinitely to prevent completion.

### Likelihood Explanation
The attack requires no special privilege beyond being an already-paired correspondent device of one of the negotiating parties — a status trivially achieved through the normal pairing flow that this project also allows from any peer. The `definition_template_chash` is a deterministic hash of the definition template (addresses/pubkeys of intended cosigners), which can be predictable or observable by a correspondent who is aware of the intended participant set (e.g., in a group where the attacker is one of the correspondents but not the specific transaction's cosigner). No signature or extra proof of relevance to the specific shared-address negotiation is required by the handler, so exploitation is straightforward once the chash is known.

### Recommendation
Before deleting a pending shared address, verify that `from_address` is actually a member of the corresponding `pending_shared_address_signing_paths` row(s) for that `definition_template_chash`, mirroring the ownership check already used in `approvePendingSharedAddress`. Reject the message with an error if the sender has no membership row for that pending address chash, e.g.:
```js
db.query("SELECT 1 FROM pending_shared_address_signing_paths WHERE definition_template_chash=? AND device_address=?",
  [address_definition_template_chash, from_address], function(rows){
    if (rows.length === 0) return callbacks.ifError("not a member of this pending shared address");
    walletDefinedByAddresses.deletePendingSharedAddress(address_definition_template_chash);
    callbacks.ifOk();
});
```

### Proof of Concept
1. Device A initiates a shared/multisig address proposal by sending `create_new_shared_address` to devices B and C, which causes a `pending_shared_addresses`/`pending_shared_address_signing_paths` record to be created on A's node with `definition_template_chash = X`. [6](#0-5) 
2. Attacker D, who is merely a paired correspondent of A (unrelated to this specific proposal) but who can compute or has observed `X` (deterministic hash of the known template/participant set), sends A a device message: `{subject: "reject_new_shared_address", body: {address_definition_template_chash: X}}`.
3. `handleMessageFromHub` on A's node only checks that `X` is a syntactically valid chash and that D is a known correspondent (not that D belongs to the negotiation), then calls `deletePendingSharedAddress(X)`. [4](#0-3) 
4. Both `pending_shared_addresses` and `pending_shared_address_signing_paths` rows for `X` are deleted, silently aborting the negotiation for B and C without their knowledge or consent, even though D had no legitimate stake in it. [5](#0-4)
