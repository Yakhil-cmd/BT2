### Title
Unicode bidi/zero-width characters in attestation subject names are rendered unsanitized in `printVerifiedSubjects`, enabling display spoofing - (File: pkg/cmd/release/verify/verify.go)

### Summary
`printVerifiedSubjects` in `pkg/cmd/release/verify/verify.go` writes the `Name` field of each attestation `Subject` directly to the terminal table via `table.AddField(name)` with no filtering of Unicode bidirectional-override, zero-width, or combining characters. Since asset/subject names originate from the release publisher (the repo owner), an attacker who controls a repository and its release process can embed characters like U+202E (RIGHT-TO-LEFT OVERRIDE) in an asset name so the string GitHub's attestation service legitimately signs still renders with a reversed/altered displayed extension or path when a victim runs `gh release verify` against that repo.

### Finding Description
`printVerifiedSubjects` unmarshals the DSSE payload from the verified Sigstore bundle into `v1.Statement` and, for each `Subject`, takes `s.Name` and passes it straight into the table renderer: [1](#0-0) 

No sanitization step exists in this path or in `internal/tableprinter.TablePrinter.AddField`/`NewWithWriter`, which only handles column padding/truncation and color, not Unicode text-direction or zero-width control characters: [2](#0-1) 

The codebase does have an established sanitization pattern for *ANSI escape sequences* (the `asciisanitizer` transform used by `iostreams.Untrusted`, `ContentOut`, and `pkg/cmd/skills/list/list.go`'s `sanitizeForTerminal`), but that mechanism strips C0 control bytes and ANSI escapes — it does not touch bidi-control code points (U+202A–U+202E, U+2066–U+2069), zero-width characters (U+200B, U+FEFF), or combining marks, all of which are ordinary printable Unicode runes: [3](#0-2) 

Because the attacker owns the target repository (the "attacker's own repo/workflow claims" scenario in scope), they can name a release asset with an embedded RTL-override character, e.g. `exe‮txt.` (rendered as `exetxt.exe`-looking-like-`.txt`), commit/tag a release, and let GitHub Actions' attestation flow legitimately sign the subject name as part of the release attestation. `verifyRun` -> `VerifyAttestation` only validates the cryptographic authenticity of the bundle, not the semantic safety of the strings it contains, so the check "is this subject name sane to print" never happens before `printVerifiedSubjects` writes it to the table.

### Impact Explanation
This enables spoofing of the displayed asset name/extension in the `gh release verify` output table. A victim could be shown what appears to be a `.txt` file when the actual attested/downloadable asset is a `.exe`/script, potentially leading them to download and execute it via a follow-up `gh release download`, believing they verified a benign attachment. This matches a terminal output/prompt spoofing class of impact, though it requires the victim to take a further action (download/execute) based on the misleading display; `printVerifiedSubjects` itself only prints metadata and does not perform any file write or execution.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs control of their own repository/release workflow, which is within the stated attacker capability (no privileged access to the victim needed). The victim must run `gh release verify` against the attacker's repo. This is a plausible but narrow social-engineering-adjacent path — the direct impact is limited to the table's visual name field and the digest column is unaffected, so it does not by itself bypass the attestation's cryptographic guarantees (the digest of the real underlying file is still correctly displayed and would need to be relied upon separately, e.g. via `gh release download` behaviors).

### Recommendation
Sanitize `s.Name` in `printVerifiedSubjects` before calling `table.AddField`, e.g. strip or escape Unicode bidi control characters (U+202A-U+202E, U+2066-U+2069), zero-width characters (U+200B, U+200C, U+200D, U+FEFF), and other non-printable/format characters (`unicode.Cf` category), consistent with the existing terminal-sanitization pattern used elsewhere in the codebase (`asciisanitizer`, `sanitizeForTerminal` in `pkg/cmd/skills/list/list.go`).

```go
func TestPrintVerifiedSubjects_StripsBidiControls(t *testing.T) {
    // Build a fake DSSE payload whose subject Name contains U+202E RLO
    // e.g. "safe\u202Etxt.exe" which visually renders as "safeexe.txt"
    maliciousName := "safe\u202Etxt.exe"
    stmt := &v1.Statement{
        Subject: []*v1.ResourceDescriptor{
            {Name: maliciousName, Digest: map[string]string{"sha256": "deadbeef"}},
            {Name: "other-asset", Digest: map[string]string{"sha256": "cafebabe"}},
        },
    }
    payload, _ := protojson.Marshal(stmt)
    att := &verification.AttestationProcessingResult{
        Attestation: &api.Attestation{
            Bundle: &protobundle.Bundle{
                Content: &protobundle.Bundle_DsseEnvelope{
                    DsseEnvelope: &dsse.Envelope{Payload: string(payload)},
                },
            },
        },
    }

    io, _, out, _ := iostreams.Test()
    err := printVerifiedSubjects(io, att)
    require.NoError(t, err)

    // Expected assertion (currently fails): bidi control chars must not
    // reach the rendered table.
    assert.NotContains(t, out.String(), "\u202E")
}
```
Expected current behavior: the assertion fails because `\u202E` passes through unmodified to stdout, confirming the desync between the raw and displayed name.

```go
// NewWithWriter creates a TablePrinter from a Writer, whether the output is a terminal, the terminal width, and more.
func NewWithWriter(w io.Writer, isTTY bool, maxWidth int, cs *iostreams.ColorScheme, headers headerOption) *TablePrinter {
	tp := &TablePrinter{
		TablePrinter: tableprinter.New(w, isTTY, maxWidth),
		isTTY:        isTTY,
		cs:           cs,
	}

	if isTTY && len(headers.columns) > 0 {
		// Make sure all headers are uppercase, taking a copy of the headers to avoid modifying the original slice.
		upperCasedHeaders := make([]string, len(headers.columns))
		for i := range headers.columns {
			upperCasedHeaders[i] = strings.ToUpper(headers.columns[i])
		}

		// Make sure all header columns are padded - even the last one. Previously, the last header column
		// was not padded. In tests cs.Enabled() is false which allows us to avoid having to fix up
		// numerous tests that verify header padding.
		var paddingFunc func(int, string) string
		if cs.Enabled {
			paddingFunc = text.PadRight
		}

		tp.AddHeader(
			upperCasedHeaders,
			WithPadding(paddingFunc),
			WithColor(cs.TableHeader),
		)
	}

	return tp
}
```

```go
// stripControl is a defensive fallback used only if the sanitizing transform
// errors, which the asciisanitizer does not do in practice. It drops C0 control
// bytes other than tab, newline, and carriage return so the result can never
// carry an escape sequence.
func stripControl(s string) string {
	return strings.Map(func(r rune) rune {
		if r < 0x20 && r != '\t' && r != '\n' && r != '\r' {
			return -1
		}
		return r
	}, s)
```
