### Title
Cross-organization webhook confusion: signature validated against `repository.owner.login`/`organization.login`, but write target selected from independent `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. Once the signature is accepted, every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the actual `Stack`/`Repository` to act on using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. In a multi-tenant Shipit deployment configured with the `github: { org_a: {...}, org_b: {...} }` schema, nothing ties the organization whose secret validated the signature to the repository actually written to.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The secret used for verification is chosen purely from a JSON field inside the attacker-supplied (though signed) payload, `repository.owner.login` / `organization.login`.

The event handlers, however, never look at that field. They derive the target repository from a sibling field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler`, for example, uses this to load stacks and immediately trigger a sync:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization config with independent secrets:
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  @github ||= {}
  @github[organization] ||= GitHubApp.new(organization, config)
``` [4](#0-3) 

Because the whole raw POST body is HMAC-signed as a single blob, an attacker cannot tamper with fields after the fact without breaking the signature - but this is not a tamper-after-signing attack. It is a binding-confusion attack: whoever legitimately controls a valid `webhook_secret` for **any one** organization configured in this Shipit instance (e.g. `org_a`) can compose the JSON body themselves (nothing requires it to originate from GitHub's own webhook delivery; the controller accepts any POST to `/webhooks` bearing a valid `X-Hub-Signature` for the secret matching `repository.owner.login`), setting:
- `repository.owner.login` = `"org_a"` (so `Shipit.github(organization: "org_a")`'s secret is used and verification succeeds), and
- `repository.full_name` = `"org_b/victim-repo"` (a completely different, unrelated organization's/tenant's repository already registered as a `Stack` in the same Shipit instance).

The controller only checks that the signature is valid for `org_a`'s secret; it never checks that `full_name`'s owner matches `repository_owner`. The handler then acts on `org_b/victim-repo`'s `Stack` using `org_a`'s "authenticated" webhook.

This breaks exactly the "organization that authenticated versus the repository that is written" binding called out in the analog rules: the equality `authenticated_org == written_repository_org` is never enforced.

### Impact Explanation
Depending on which webhook handler fires, this allows a holder of one tenant's webhook secret to affect another tenant's stack that is hosted on the same Shipit instance:
- `push` events trigger `stack.sync_github` on the victim's stack (state/sync manipulation) [3](#0-2) .
- `status`/`check_suite` handlers can inject/alter commit statuses and check-run state used for merge/deploy gating on the victim stack (`RefreshCheckRunsJob`, commit `Status` creation), potentially manipulating the checks that Shipit treats as green before an unauthorized deploy or merge decision on the victim's stack.
- `membership` handlers create `Team`/`User` records tied to whatever data the forged payload supplies.

The severity depends on which handler is reachable and what state it mutates on the victim stack, but the underlying primitive - the authenticated identity (organization/secret used to pass signature check) is not equal to the entity being written (repository/stack) - matches the class of bug in the report (a validated signer/authority that does not carry forward to the object actually operated on).

### Likelihood Explanation
This is only reachable when a Shipit instance is configured for **multiple GitHub organizations** (`github: {org_a: {...}, org_b: {...}}` schema) and different, mutually-untrusting tenants/orgs have their stacks hosted in the same instance — this is the exact scenario the multi-org configuration in `docs/setup.md` and `lib/shipit.rb#github_organizations` is built for [5](#0-4) . Any org admin who possesses their own org's legitimate `webhook_secret` (which is normal, non-privileged knowledge of their own tenant configuration, not privileged Shipit access) can exploit this without needing any Shipit session, API token, or GitHub write access to the victim repo. In single-organization deployments (the default/most common case) this is not exploitable, since there's only one secret and `repository_owner` is effectively ignored for secret selection (`config = secrets.github` regardless of the field) — the finding is scoped to multi-org deployments.

### Recommendation
After validating the signature, require that the extracted `repository_owner`/`organization.login` matches the owner segment of `repository.full_name` (and record/propagate the verified organization through the handler chain) before allowing any handler to resolve or mutate a `Stack`. Reject the webhook if these fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `org_a` and `org_b`, each with their own GitHub App/`webhook_secret`, and register a `Stack` for `org_b/victim-repo`.
2. As the administrator of `org_a` (an attacker who legitimately controls only `org_a`), compute:
   ```
   body = {
     "repository": { "owner": { "login": "org_a" }, "full_name": "org_b/victim-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha that exists in org_b/victim-repo>"
   }.to_json
   signature = "sha1=" + HMAC_SHA1(org_a_webhook_secret, body)
   ```
3. `POST /webhooks` with `X-Github-Event: push`, `X-Hub-Signature: <signature>`, body as above.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org_a")`, verifies the signature against `org_a`'s secret, and succeeds [6](#0-5) .
5. `PushHandler#process` resolves stacks via `repository_name` = `payload.dig('repository','full_name')` = `"org_b/victim-repo"`, and invokes `stack.sync_github(expected_head_sha: ...)` on the victim's stack [2](#0-1) [3](#0-2)  — a cross-tenant action performed using `org_a`'s webhook authentication.
