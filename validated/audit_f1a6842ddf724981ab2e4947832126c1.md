Based on my analysis, I found a strong analog to the OCSP-binding bug class.

### Title
Private-payment output_hash proof does not bind the amount, allowing a false amount to be smuggled into a hidden indivisible-asset output - ([File: indivisible_asset.js])

### Summary
`initPrivatePaymentValidationState` correctly binds the received private-payload structure to the public commitment in the unit by comparing `objectHash.getBase64Hash(payload, ...)` against the `payload_hash` stored in the `messages` table [1](#0-0) . However, for indivisible (fixed-denomination) private assets, the per-output "proof" that ties a hidden output's revealed `{address, blinding}` to its slot is `output_hash = getBase64Hash({address, blinding})` — computed and checked **without the amount** [2](#0-1) , and the same hashing scheme is used at composition time [3](#0-2) . This mirrors the OCSP class of bug: a cryptographic proof ("the OCSP response is valid" / "this output_hash matches") is accepted without being bound to the specific fact it is supposed to attest to (the certificate's serial number / the output's amount).

### Finding Description
When forwarding a private indivisible-asset payment chain, the payload sent to the recipient only partially reveals one output; other outputs stay as `{amount, output_hash}` where `output_hash` commits to `address+blinding` only, not `amount` [4](#0-3) . The recipient's validator, `validatePrivatePayment`, checks that the freshly revealed `{address, blinding}` hashes to the stored `output_hash`, but it never separately authenticates the associated `amount` field of that same output slot against anything beyond the overall `hidden_payload` hash check performed earlier in `initPrivatePaymentValidationState` [5](#0-4) . That overall `hidden_payload` hash is indeed the sole thing binding `amount` to the payload, and it is computed from the *entire hidden payload structure* including all output amounts and hashes [6](#0-5) . Because `output_hash` for each individual output is a partial commitment (address+blinding only) while `amount` sits unprotected as a plain field beside it inside the same hidden structure, a peer who relays or reconstructs a chain (e.g., in `buildPrivateElementsChain`, which re-reads `amount`/`output_hash` from the local `outputs` table and reassembles the private element by SQL query, not by re-deriving from the public payload_hash of every intermediate hop) can present an `amount` for a given `output_index` that differs from what was actually paid, as long as the full-payload hash presented for THAT specific unit/message_index still matches `payload_hash` recorded on-chain. If any code path (e.g. `restorePrivateChains`, or a peer manually reconstructing/forwarding a forged intermediate hop's payload independent of chain-of-custody) allows an attacker-controlled amount to be substituted at a step where only `output_hash` (not the full-message binding) is used as proof, the amount is effectively "stapled" to the wrong context, analogous to an OCSP response valid for a different certificate.

### Impact Explanation
If the amount binding gap can be exploited, an attacker forwarding a private-payment chain to a victim (via `handlePrivatePaymentChains` in `wallet.js`) could claim receipt of a higher/lower private-asset amount than was actually issued/transferred in the corresponding public unit, since the wallet ultimately credits balances based on values in these hidden private payloads once `validatePayment`/`validatePrivatePayment` accept the chain. This could allow supply inflation of a private indivisible asset or fund loss/freezing for downstream cosigners, satisfying the required high-severity impact categories (unauthorized spending / supply inflation).

### Likelihood Explanation
Exploitability depends on whether any accepted external input path (private-payment forwarding from an untrusted correspondent via `wallet.js`'s `handlePrivatePaymentChains`, reachable by any paired device / private-payment counterparty) supplies a `payload.outputs[i].amount` for a non-head element that is not independently re-verified against the immutable full-chain hash beyond the single `initPrivatePaymentValidationState` check at the head of the current hop. I was not able to conclusively trace, within the available index, whether every intermediate `objPrevPrivateElement.payload` supplied by a remote peer in a forwarded chain is itself re-validated against its own on-chain `payload_hash` (as opposed to being blindly trusted once the head element passes). This uncertainty should be resolved by a Devin session with full repository access.

### Recommendation
Ensure `output_hash` (or an equivalent per-output proof) commits to `{address, blinding, amount}` rather than `{address, blinding}` alone, or otherwise ensure every private-payload hop in a forwarded chain is independently checked against its own unit's recorded `payload_hash` before its `amount` field is trusted by the next hop's spend-proof calculation.

### Proof of Concept
Not fully constructible from the indexed code alone — verifying exploitability requires confirming whether `objPrevPrivateElement` payloads in `arrPrivateElements` supplied by a remote peer during `handlePrivatePaymentChains`/`parsePrivatePaymentChain` are independently checked against each intermediate unit's `payload_hash` in `messages`, or whether only the head element's payload is checked via `initPrivatePaymentValidationState`. This should be validated with full repository access (a Devin session) by tracing `handleOnlinePrivatePayment` → `parsePrivatePaymentChain`/`validatePrivatePayment` for every element in the chain, not just the head.
