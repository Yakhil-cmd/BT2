### Title
Webhook signature verification is bypassable when a configured GitHub organization has no `webhook_secret`, allowing forged `membership` events to grant unauthorized `Shipit.github_teams` access - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check against based on an organization name taken directly from the **unverified** JSON body (`repository.owner.login` / `organization.login`), then delegates to `GitHubApp#verify_webhook_signature`. That method contains an explicit bypass: `return true unless webhook_secret`. If any configured GitHub organization in `secrets.github` has no `webhook_secret` set, every webhook claiming that organization is accepted without any signature check at all, and the payload is dispatched straight to `Shipit::Webhooks.for_event(event)` handlers.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
picks `repository_owner` from the request body itself: [2](#0-1) 
and calls `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp`, then `verify_webhook_signature`. Signature verification is: [3](#0-2) 
`return true unless webhook_secret` — for an organization configured **without** a `webhook_secret` (a state explicitly documented and defaulted to `nil` in every example config, e.g. `webhook_secret: # nil` in `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, and `test/dummy/config/secrets_double_github_app.yml`), any POST to the public `/github_webhooks` endpoint claiming that org is accepted with **no signature at all**.

The equality broken is: *organization authenticated by the HMAC check* ≠ *organization actually used to process the event's side effects*. Before the attacker's request, only GitHub (holding the real webhook secret, when one exists) can produce accepted webhook events. After the request, any unauthenticated party who knows (or guesses) the name of a configured-but-secretless organization key can produce accepted events, because the check for that org is unconditionally `true`.

Once accepted, the event is dispatched to handlers with no further authentication, e.g. `Handlers::MembershipHandler`: [4](#0-3) 
which, for `action: 'added'`, calls `team.add_member(member)` where `member` is `User.find_or_create_by_login!(params.member.login)` — an attacker-supplied GitHub login. `Shipit.github_teams` gating is what `current_user.authorized?` checks: [5](#0-4) 
and `force_github_authentication` enforces it for every controller in the app: [6](#0-5) 

So an attacker who has no Shipit session, no `ApiClient` token, and no GitHub write access can forge a `membership` webhook (`action: 'added'`) naming their own GitHub login and a team matching one of `Shipit.github_teams`, adding themselves to that team and satisfying `authorized?` — full authentication-bypass into the application.

### Impact Explanation
This maps directly to the allowed High-impact class "escalation into `Shipit.github_teams` authorization" and can plausibly be chained into unauthorized deploys once the attacker is treated as an authenticated, authorized `User` (deploy/rollback controllers only check `current_user.authorized?`, not GitHub team membership per request). It requires only that the deployment be running a multi-organization GitHub config (`secrets.github` keyed by org) where at least one configured organization key lacks a `webhook_secret` — which is exactly the state shown as the default/example in every shipped config sample in this repo (`webhook_secret: # nil`).

### Likelihood Explanation
Likelihood is contingent on operator configuration: the vulnerability only manifests if a real deployment leaves `webhook_secret` unset for a configured organization key. The code path and default/example configs strongly suggest this is a plausible, even encouraged, configuration state, but I could not confirm from the code whether Shipit's setup docs treat `webhook_secret` as mandatory in practice (docs say "if you've set a webhook secret ... copy it here", implying it's optional). Because the bypass is triggered purely by an unauthenticated HTTP request to a route mounted by default (no session, token, or GitHub credential needed) once that configuration condition holds, I rate this as a legitimate, code-rooted analog rather than a pure configuration/documentation issue — the root cause (`return true unless webhook_secret`) lives in `lib/shipit/github_app.rb`, not in the host app.

### Recommendation
- In `GitHubApp#verify_webhook_signature`, do not silently accept requests when `webhook_secret` is blank; instead treat a missing secret as a hard misconfiguration (raise/reject) rather than an implicit bypass.
- Ensure `WebhooksController#repository_owner` cannot be used to pick a signature-verification path that has no compensating secret.
- Make `webhook_secret` a required, validated configuration key at boot for any `github` organization entry.

### Proof of Concept
1. Deploy Shipit with a multi-org config (`secrets.github: { orgA: {...}, orgB: { webhook_secret: nil, oauth: { teams: ["orgB/some-team"] } } }`), matching the shipped example configs.
2. As an unauthenticated attacker, `POST /github_webhooks` with headers `X-Github-Event: membership` and no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "some-team", "slug": "some-team", "url": "https://example.com"},
  "organization": {"login": "orgB"},
  "member": {"login": "attacker-github-login"}
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgB")`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `orgB` (`lib/shipit/github_app.rb:76-83`).
4. `MembershipHandler#process` runs, creating/finding `User` with login `attacker-github-login` and adding it to the `orgB/some-team` `Team`.
5. Attacker completes GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns true because the user belongs to a team in `Shipit.github_teams`, granting full application access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
