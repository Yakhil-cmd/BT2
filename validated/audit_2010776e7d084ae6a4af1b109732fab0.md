### Title
Cross-Transaction Shared Interest-Index Cache Lets One Caller's Utilization Manipulation Be Consumed by All Other Users in the Same Block - ([File: local-testing/contracts/market/market.clar], mirrored in [File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` caches each vault's freshly-accrued borrow/liquidity index in `index-cache`, keyed only by `{timestamp: stacks-block-time, aid}` [1](#0-0) . Since `stacks-block-time` is identical for every transaction inside the same block, this cache is not scoped to the calling transaction — it is a block-wide shared value. Whichever unprivileged user's transaction is the first to trigger `accrue-and-cache` for a given asset "locks in" the index for every other user's transaction that touches the same asset later in that block, exactly the "shared index/cache primed by one caller and consumed by another" bug class described in the ZetaChain analog (a hash/index computed once and blindly trusted for subsequent unrelated actors).

### Finding Description
The cached value is not a pure function of elapsed time; it also depends on the *live* utilization rate sampled at the moment of the priming call: [2](#0-1) 

`next-index`/`next-liquidity-index` compute `rate = interest-rate()` from `utilization()` evaluated *at call time*, then apply that single rate over `time-delta = stacks-block-time - last-update`, which can span many minutes/hours since the previous accrual [3](#0-2) .

`market.clar`'s `accrue-and-cache` calls this vault accrual only on a cache miss and then stores the result under the block-wide key, returning the cached tuple to every subsequent caller in the same block without re-deriving it: [1](#0-0) 

This cached `{index, lindex}` is consumed later in the same block by unrelated operations belonging to other users — e.g. liquidation debt scaling reads it directly: [4](#0-3) 

and z-token collateral pricing (`resolve-ztoken`) also reads the same cache: [5](#0-4) 

**Attack path:** Attacker (User A, no privileges) opens a transaction against a vault where they hold sufficient capital/collateral. Inside a single atomic call they (a) borrow a large amount to spike `utilization()` up or repay/deposit to push it down, then (b) immediately perform any action that calls `accrue-and-cache` for that `aid` for the first time in the block (any deposit/borrow/repay/liquidate touches it). The resulting `next-index`/`next-liquidity-index` — computed with the attacker's momentarily engineered utilization applied over the *entire* un-accrued time window since `last-update` — is written into `index-cache` for that block's timestamp.

Any other, unrelated user (Victim, User B) whose transaction lands later in the same block and touches the same asset (borrow, repay, supply, or gets liquidated) will read this manipulated cached index instead of a value derived from the vault's true, unmanipulated utilization. The victim never called `vault-accrue` themselves and has no way to detect or avoid the poisoned cache entry.

### Impact Explanation
Because the entire elapsed-time interest multiplier is collapsed into one utilization sample that the attacker controls at the priming instant, and that single value is then shared with every other user's operation in the same block via `index-cache`, an attacker can systematically depress the liquidity index (`lindex`) applied for that accrual period, reducing the interest that legitimately accrues to all suppliers holding zTokens for that asset during that window (theft/loss of unclaimed yield), or inflate/deflate the borrow index (`index`) used later in the same block by a liquidator's `scale-debt-for-liquidation` against a victim's position, corrupting the amount of debt-repay/collateral-seizure computed for that unrelated liquidation. This lands in the in-scope "theft of unclaimed yield" / "temporary freezing of funds" impact classes, since the effect is limited to the interest/valuation computed for that one block window rather than a permanent, unbounded drain.

### Likelihood Explanation
No privileged role or DAO action is required. The precondition is simply being the first transaction in a block to touch a given `aid`'s accrual (attacker can guarantee this with normal transaction submission/fee bidding) combined with performing a self-funded borrow/repay pair (or deposit/withdraw pair) in the same atomic call to move `utilization()` before the accrual snapshot — no flashloan is needed since the manipulation and the priming call are done with the attacker's own capital in one transaction. The magnitude of impact per exploit is bounded by one block's worth of the elapsed-since-last-accrual interest, so it would need to be repeated to accumulate meaningful value, which is achievable given interest accrual can go long periods between triggers (`time-delta` is unbounded).

### Recommendation
Scope `index-cache` to the individual transaction rather than to `stacks-block-time` (e.g., use a transaction-nonce/tx-sender-independent ephemeral value, or simply remove cross-transaction caching and only cache within a single call's execution using a `let`-bound accumulator passed through the fold), so that one user's engineered utilization at the priming instant can never be inherited by a different user's transaction in the same block.

### Proof of Concept
1. Block N contains no prior transaction touching vault `USDC` (`index-cache` has no entry for `{timestamp: T, aid: USDC}`).
2. Attacker submits a transaction: deposit collateral, `borrow` a large amount of USDC (spiking utilization far above its steady-state level), then within the same call perform a trivial `repay`-adjacent or `supply-collateral-add` action on USDC that triggers `accrue-and-cache` — because the vault's `utilization()`/`interest-rate()` is read live inside `next-liquidity-index`, the resulting `lindex` reflects the attacker's temporarily inflated (or, symmetrically, deflated) utilization applied over the full multi-block `time-delta` since the vault's `last-update`, and this value is written to `index-cache` at key `{timestamp: T, aid: USDC}` [1](#0-0) .
3. Attacker's own borrow is then reversed (repaid) at the end of the same transaction, restoring true utilization, but `index-cache` retains the poisoned index for the remainder of block N.
4. A second, unrelated transaction from Victim in block N (e.g., a `supply-collateral-add` of USDC, or a liquidator's call to `liquidate` against a third party's position) calls `get-cached-indexes`/`accrue-and-cache` for USDC, hits the cache, and receives the attacker-primed index instead of one reflecting genuine market utilization [4](#0-3) .
5. Repeating this pattern across blocks lets the attacker consistently under-accrue supplier yield (or bias liquidation debt-scaling) for USDC at the expense of every other user whose transaction lands in the same block, without ever needing privileged access or a flashloan.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

  (let ((points-data (var-get points-ir))
        (uword (get util points-data))
        (rword (get rate points-data))
        (utils (unpack-u16 uword))
        (rates (unpack-u16 rword)))

(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
