This confirms a critical finding: `StatusHandler#process` matches purely on `Commit.where(sha: params.sha)` [1](#0-0) , with no scoping to the repository/organization at all, and `create_status_from_github!` feeds directly into `add_status`, which fires `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges` whenever the status becomes success/pending [2](#0-1) , and `Commit#schedule_continuous_delivery` triggers `ContinuousDeliveryJob` when `deployable?` and `stack.continuous_deployment?` [3](#0-2) . Combined with the org/secret-selection vs. repository-resolution mismatch in the webhook controller, this is sufficient to build the analog.

### Title
Cross-tenant webhook forgery via organization/repository binding mismatch enables forged CI status and unauthorized deploy triggers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request's HMAC signature against using `repository_owner`, a value read directly from the *unverified* JSON body (`params.dig('repository','owner','login')` or `organization.login`) [4](#0-3) [5](#0-4) . Once the signature is accepted, the actual event handlers resolve the target repository/stack from an entirely different, independently attacker-controlled field, `payload.dig('repository', 'full_name')` [6](#0-5) , or in the case of `StatusHandler`, from `params.sha` with no repository scoping at all [1](#0-0) . Nothing enforces that the organization whose secret validated the signature is the same organization/repository that the handler actually acts on.

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single instance, each configured with its own `app_id`/`installation_id`/`webhook_secret` under `Shipit.github(organization:)` [7](#0-6) . The signature check is:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [8](#0-7) 

This picks the verification secret using one field of the raw, not-yet-verified body. But `create` then dispatches the whole raw body to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [9](#0-8) . Handlers resolve the target stack using `repository.full_name` [6](#0-5) , or, for `status` events, using only the commit SHA across the whole database with zero owner/org check [10](#0-9) .

An attacker who is a legitimate admin of "Org A" (and therefore knows Org A's own `webhook_secret`, since each tenant creates and configures its own GitHub App per `docs/setup.md`) can send a forged webhook request directly to the shared `/github/webhooks` endpoint (not through GitHub) with:
- `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) so `verify_signature` selects Org A's secret and the HMAC computed over the crafted raw body validates,
- `repository.full_name = "orgB/victim-repo"` and/or a `sha` belonging to a commit in Org B's stack, which is never checked against Org A.

Because the HMAC only proves "signed with Org A's secret", not "this event genuinely concerns Org A's repository", the handler happily acts on Org B's stack/commit.

### Impact Explanation
This breaks the trust binding "organization that authenticated == repository that is written". Concretely, an attacker who only controls Org A's webhook secret can:
- Forge a `status` event with `state: "success"` for a specific victim commit SHA in Org B. `StatusHandler` finds the commit purely by `sha` with no owner check and calls `commit.create_status_from_github!`, which can flip the commit's aggregate state to success, fire `Hook.emit(:deployable_status, ...)`, call `stack.schedule_merges`, and — if Org B's victim stack has `continuous_deployment` enabled — trigger `ContinuousDeliveryJob` via `Commit#schedule_continuous_delivery` [3](#0-2) [2](#0-1) .
- Forge `push`, `pull_request` (opened/reopened/labeled/unlabeled/closed), or `membership` events referencing Org B's `repository.full_name`, causing cross-repository writes: creating/archiving/unarchiving review stacks, syncing/merging, and creating users/teams outside Org A's own tenant, all attributable to a request that only proved possession of Org A's secret.

This constitutes cross-repository writes and an unauthorized deploy trigger, matching the Critical impact bar.

### Likelihood Explanation
Any customer/tenant admin who legitimately possesses their own organization's `webhook_secret` (a normal, unprivileged credential scoped only to their own org's GitHub App) can exploit this without any access to Org B, GitHub App private keys, or `GITHUB_TOKEN`. The only requirement is a multi-org Shipit deployment, which is an explicitly documented and supported configuration [11](#0-10) . No race condition, retry abuse, or DoS technique is needed — a single crafted POST suffices.

### Recommendation
After `verify_signature` succeeds for a given organization/app, re-derive `repository_owner` from the same field used for the actual event processing, and reject the request (or scope all handler queries) if the owner of `repository.full_name` (and/or `organization.login`) does not match the organization whose secret validated the signature. Additionally, `StatusHandler` (and any handler working by bare identifiers like `sha`) must scope its lookup to the verified organization/repository rather than searching globally across all stacks.

### Proof of Concept
1. Configure Shipit with two tenant orgs, `orgA` (secret `S_A`) and `orgB` (secret `S_B`), per the documented multi-org config [12](#0-11) .
2. As an Org A admin (who knows `S_A`), craft a JSON body:
```json
{
  "sha": "<victim commit sha in orgB/victim-repo>",
  "state": "success",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and POST to the Shipit webhooks endpoint with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and the signature validates [4](#0-3) .
5. `StatusHandler#process` finds the Org B commit by `sha` alone and marks it `success`, potentially triggering continuous deployment on Org B's stack [1](#0-0) .

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```
