### Title
Cross-org webhook signature confusion allows an attacker-controlled GitHub org (with no `webhook_secret` configured) to forge `pull_request.labeled` events that archive/unarchive a different org's review stack - (File: app/controllers/shipit/webhooks_controller.rb / app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects the GitHub App config to validate the HMAC signature using only the top-level `repository.owner.login` field, while `LabeledHandler` (and its sibling PR handlers) resolve and mutate the target `Repository`/`Stack` using the independent `repository.full_name` field from the same attacker-supplied JSON body. If the org named by `owner.login` has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` unconditionally returns `true`, letting an unauthenticated caller forge a payload whose `full_name` names a completely different (victim) org/repo, and have `LabeledHandler#handle` call `stack.archive!`/`stack.unarchive!` on that victim's review stack.

### Finding Description
The broken binding: **verified-org (the org used to fetch the `GitHubApp`/secret in `verify_signature`) == stack-owning-org (the org encoded in `params.repository.full_name` used by `LabeledHandler`)**. These are two independently attacker-controlled fields within the same unauthenticated JSON body, and no code enforces that they refer to the same organization.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, raw_post)`. [1](#0-0) 
2. `Shipit.github` only branches per-organization when the deployment uses the multi-org secrets schema (`github_default_organization` non-nil); in that case it looks up `github_app_config(organization)` keyed by the org name. [2](#0-1) 
3. `GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that org: `return true unless webhook_secret`. [3](#0-2) 
4. Once signature verification passes, `WebhooksController#create` dispatches the raw parsed JSON to `Shipit::Webhooks.for_event(event)` handlers, including `LabeledHandler`, unmodified. [4](#0-3) 
5. `LabeledHandler` never re-checks `repository.owner.login`; it resolves the target repository purely from `params.repository.full_name`, then evaluates `archive?`/`unarchive?` against that repository's `provisioning_behavior_prevent_with_label?`/`provisioning_label_name`, and calls `stack.archive!`/`stack.unarchive!` via `ReviewStackAdapter` scoped to that repository's `review_stacks`. [5](#0-4) 

Exploit: the attacker sends `POST /webhooks` with header `X-Github-Event: pull_request` and a body where `repository.owner.login` = an org that is configured in `secrets.github` (multi-org schema) but has no `webhook_secret` set, while `repository.full_name` = `"victim-org/victim-repo"` and `pull_request.labels` contains the victim repository's configured `provisioning_label_name` (or omits it, depending on `provisioning_behavior_prevent_with_label?`/`allow_with_label?`). No valid `X-Hub-Signature` is required because verification for the unconfigured org always returns `true`.

Existing guards fail to stop this because: `drop_unhandled_event` only checks the event type is handled, not payload consistency; `verify_signature`'s org lookup and the handler's repository lookup use two different fields of attacker-controlled JSON with no cross-check; `ExplicitParameters` schema in `LabeledHandler` only validates field types/presence, not that `repository.full_name`'s org matches the org verified upstream; and there is no `User#authorized?`/`require_permission!` check on this unauthenticated webhook path at all.

### Impact Explanation
A payload authenticated (trivially, due to no secret) as belonging to one organization can mutate (archive/unarchive) the review-stack deploy state of an entirely unrelated organization's repository/stack, which is exactly the "payload for one repository mutating another's stack" Critical category. Repeated calls let the attacker toggle any victim review stack's archived state at will, disrupting deploys/deprovisioning for that repository, as long as the attacker can supply a `repository.owner.login` that matches a configured-but-secretless org. Blast radius is scoped to Shipit installations using the multi-org secrets schema where at least one configured org lacks a `webhook_secret`; other orgs/stacks on the same instance are affected as victims regardless of their own secret configuration, since the check is keyed off `owner.login`, not `full_name`.

### Likelihood Explanation
Requires: (1) the Shipit instance to use the multi-organization `github:` secrets schema (keyed by org name) rather than the single top-level schema — in the single-org schema, `Shipit.github(organization: ...)` ignores the passed org and always uses the single configured secret, so this attack does not apply there — and (2) at least one configured org entry lacking `webhook_secret`. This is a plausible operator misconfiguration (the shipped example config literally shows `webhook_secret: # nil` as a placeholder), but it is a precondition outside the attacker's control; the attacker does not need any credentials, just knowledge of an org name in that state. Given the precondition, exploitation cost is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, and/or in each PR handler, enforce that the organization used to verify the signature is the same organization that owns the repository being mutated — e.g., derive the repository to mutate from the same `repository.owner.login`/`full_name` pair that was verified, and reject the request if `params.repository.full_name` does not belong to `repository_owner`. Additionally, treat an unconfigured `webhook_secret` as a hard misconfiguration to reject (fail closed) rather than defaulting to trusted, or require all configured orgs to have a non-blank `webhook_secret` at boot.

### Proof of Concept
Minitest plan for `test/controllers/webhooks_controller_test.rb` (multi-org secrets fixture required, e.g. `test/dummy/config/secrets_double_github_app.yml`, with one org's `webhook_secret` left blank):

```ruby
test "labeled webhook verified for org A can archive org B's stack when org A has no webhook_secret" do
  # Precondition equality check (must hold BEFORE exploit):
  # verified_org = "org-a" (webhook_secret: nil)
  # stack_owning_org = "org-b" (victim, has its own webhook_secret configured)
  # verified_org != stack_owning_org

  victim_repo = shipit_repositories(:victim) # full_name "org-b/victim-repo"
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :prevent_with_label,
                       provisioning_label_name: "deploy-me")
  stack = create_review_stack_for(victim_repo) # provisioned, not archived

  payload = JSON.parse(payload(:pull_request_labeled))
  payload["repository"]["full_name"] = "org-b/victim-repo"
  payload["repository"]["owner"]["login"] = "org-a" # unconfigured secret
  payload["pull_request"]["labels"] = [{ "name" => "deploy-me" }]

  @request.headers['X-Github-Event'] = 'pull_request'
  # no X-Hub-Signature header set, or an arbitrary invalid value

  assert_not stack.archived?

  post :create, body: payload.to_json, as: :json

  assert_response :ok
  assert stack.reload.archived?, "victim stack for org-b was archived via a payload verified against org-a's (unconfigured) secret"
end
```

This demonstrates the equality `verified_org (org-a) != stack_owning_org (org-b)` both before request (asserted via fixture setup) and after (the mutation still happens), proving the binding is broken.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

          end

          def respond_to_label_change?
            params.action == "labeled" &&
              pull_request_state == "open" &&
              repository.review_stacks_enabled &&
              (archive? || unarchive?)
          end

          def archive?
            (repository.provisioning_behavior_allow_with_label? && !pull_request_has_provisioning_label?) ||
              (repository.provisioning_behavior_prevent_with_label? && pull_request_has_provisioning_label?)
          end

          def unarchive?
            (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
              (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
          end

          def pull_request_has_provisioning_label?
            pull_request_label_names.include?(repository.provisioning_label_name)
          end
