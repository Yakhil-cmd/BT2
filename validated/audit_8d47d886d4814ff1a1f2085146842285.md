### Title
Unbounded / Unvalidated Nested AA Definitions in `payload.definition` Bypass Complexity, Depth and Op Limits - ([File: aa_validation.js])

### Summary
CVE-2024-4140 describes an excessive-memory-use / DoS issue in Email-MIME caused by unbounded recursive parsing depth and part counts. `ocore` mitigates the equivalent class of bug (unbounded recursive structures reachable from untrusted input) almost everywhere with explicit counters: `MAX_DEPTH` in `aa_validation.js`, `MAX_COMPLEXITY`/`MAX_OPS` in `definition.js` and `formula/validation.js`, the `depth > 100` guard in `formula/evaluation.js`/`formula/validation.js`, and `isTooBigObj`/`isTooDeeplyNestedOrHasTooManyNodes` in `string_utils.js`. However, one recursive nested structure — an AA definition embedded inside another AA definition via a `definition` message — is validated only shallowly, because the recursive call that would apply these same limits is explicitly disabled (commented out).

### Finding Description
In `aa_validation.js`, `validateMessage`→`validatePayload` handles the `'definition'` app case (an AA posting a message that itself defines another autonomous agent): [1](#0-0) 

The code only checks that `payload.definition` is a 2-element array, that the first element is `'autonomous agent'`, and that `payload.definition[1]` is a non-empty object. The line that would recurse into `validateAADefinition(payload.definition, cb2)` — which is exactly the function that enforces `MAX_DEPTH`, `MAX_COMPLEXITY`, and `MAX_OPS` (via `validate()` and `validateFormula()`) — is commented out with the note *"interrupt the call stack to protect against deep nesting"*, meaning the very mechanism meant to bound the recursion was disabled rather than replaced with an alternative bound.

By contrast, every other place in the codebase that walks attacker-supplied nested structures caps depth/complexity explicitly: [2](#0-1) [3](#0-2) [4](#0-3) 

This means an AA author (an unprivileged, in-scope actor per the rules) can craft a top-level AA definition whose `messages` array contains a `'definition'` message with an arbitrarily deep/complex nested AA definition object in `payload.definition[1]` (deep formula strings, deeply nested `if`/`init`/`cases`, oversized objects), and this nested definition will pass `validateAADefinition` without ever having its own complexity, op-count, or depth checked, because the recursive re-entry into `validate()`/`validateFormula()` is skipped entirely.

### Impact Explanation
If the nested, unchecked AA definition is later materialized (e.g., posted as an actual `definition` message defining a new on-chain address when the outer AA fires), the *new* address definition would still pass through the standalone address-definition path in `definition.js` (`evaluate()`), which does enforce `MAX_COMPLEXITY`/`MAX_OPS`. So the strongest concretely provable consequence is at validation time of the *outer* AA definition itself: the validator accepts an AA definition containing a nested structure that was never actually complexity/depth-checked, meaning the guarantee that "every accepted AA definition has bounded formula complexity" no longer holds uniformly for nested `'definition'` payloads. Depending on how deeply nested/oversized `payload.definition[1]` is allowed to be (only `isNonemptyObject` is required — no size or depth cap on the object itself), a malicious AA author could embed megabytes of deeply nested data in this field, which every node must nonetheless traverse with `isNonemptyObject`/`hasFieldsExcept`-style checks recursively performed elsewhere in the codebase (e.g., JSON stringification/storage), causing disproportionate CPU/memory cost per node during AA-definition validation and storage relative to the cost the original, intended `MAX_DEPTH`/`MAX_COMPLEXITY` limits were designed to impose.

### Likelihood Explanation
Any unprivileged AA author can trigger this simply by posting a unit that defines an AA whose `messages` includes a `'definition'` app message with a crafted nested AA definition. No special privileges, hub/peer compromise, or network position is required — it is reachable purely through normal AA-definition posting, matching the "AA definitions and triggers" and "oscript/ojson evaluation" categories in scope.

### Recommendation
Restore recursive validation of the nested AA definition (or equivalently invoke the same depth/complexity/op-count-limited `validate()`/`validateFormula()` machinery) instead of only performing the shallow array/keys check, so that nested `'definition'` payloads are subject to the same `MAX_DEPTH`, `MAX_COMPLEXITY`, and `MAX_OPS` bounds enforced everywhere else in `aa_validation.js` and `definition.js`.

### Proof of Concept
1. Construct an outer AA definition:
```
['autonomous agent', {
  messages: [{
    app: 'definition',
    payload: {
      definition: ['autonomous agent', <deeply nested / oversized object with many `if`/`init` cases and long formula strings>]
    }
  }],
  ...
}]
```
2. Submit this as a normal AA-definition unit via `validateAADefinition` (the path exercised by `aa_validation.js`).
3. Observe that the shallow check at `aa_validation.js:208-223` accepts the definition without ever invoking `validate()`/`validateFormula()` on `payload.definition[1]`, i.e., without the `MAX_DEPTH`/`MAX_COMPLEXITY`/`MAX_OPS` enforcement that would otherwise reject or bound such nested content.

Note: I could not fully trace, within the remaining tool budget, how the resulting nested `definition` message payload is consumed at trigger time (e.g., in `aa_composer.js`) to confirm whether downstream re-validation before actually posting a new address definition fully neutralizes the runtime impact. This should be verified further before treating the impact tier as fully proven; the validation-time gap itself, however, is concretely demonstrated by the disabled recursive call.
