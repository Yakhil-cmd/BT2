### Title
Webhook signature verified against payload's `repository.owner.login` while repository/stack resolution acts on payload's `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App / HMAC secret to validate a webhook against based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Once the signature check passes, `create` dispatches the same raw JSON `params` to handlers (`PushHandler`, `PullRequest::*Handler`, etc.), which resolve the actual repository/stack to act on using a **different** field: `params.dig('repository', 'full_name')` via `Shipit::Repository.from_github_repo_name`. In a multi-organization Shipit deployment (`Shipit.github(organization:)` / `Shipit.github_app_config`, documented in `config/secrets.development.example.yml`), these two fields are never checked for consistency.

### Finding Description
The intended trust binding is: *the organization whose webhook secret signed this payload* == *the organization owning the repository the payload will cause Shipit to act on*.

- Verification side: `app/controllers/shipit/webhooks_controller.rb`
  ```ruby
  def verify_signature
    github_app = Shipit.github(organization: repository_owner)
    verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
    ...
  end

  def repository_owner
    params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
  end
  ```
  This selects the `GitHubApp` (and thus the HMAC `webhook_secret`) purely from `repository.owner.login` (or `organization.login`), per `Shipit.github_app_config` in `lib/shipit.rb`.

- Action side: `app/models/shipit/webhooks/handlers/handler.rb`
  ```ruby
  def stacks
    @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
  end

  def repository_name
    payload.dig('repository', 'full_name')
  end
  ```
  Every default handler (`PushHandler`, `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `AssignedHandler`, `LabelCapturingHandler`, etc.) resolves which `Repository`/`Stack` to mutate from `repository.full_name`, not from `repository.owner.login`.

Because HMAC verification only proves "this request was signed with OrgA's webhook secret" and never proves "the repository named in `full_name` belongs to OrgA," an attacker who legitimately controls OrgA (installs their own Shipit-integrated GitHub App on their own organization, thus legitimately possessing OrgA's `webhook_secret`) can craft a payload where `repository.owner.login = "OrgA"` (satisfying signature verification) but `repository.full_name = "OrgB/some-tracked-repo"` (targeting a repository actually owned/tracked under a different organization in the same Shipit instance). The signature will validate successfully because it's checked against OrgA's own secret, yet the handler will act on OrgB's tracked repository/stack.

This is a genuine binding break of the class called out in the rules: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
Concretely, with a forged `push` event (`GITHUB_TOKEN`/`webhook_secret` from the attacker's own organization, no privileged Shipit or GitHub credentials needed for the victim's org), `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` on any stack belonging to `OrgB/repo` matching the forged branch, forcing an out-of-band sync to an attacker-chosen SHA. Combined with `pull_request` handlers, an attacker can also archive/unarchive review stacks or force provisioning (`ReviewStackAdapter.find_or_create!`) for repositories they do not own, and manipulate pull request state/labels tracked by Shipit for a foreign repository. This crosses a repository trust boundary: actions intended to be scoped to the organization that owns the webhook secret leak into any other tracked organization/repository, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar, contingent on the target Shipit instance being configured with more than one GitHub organization (multi-org `github:` config as documented in `config/secrets.development.example.yml`).

### Likelihood Explanation
This requires the Shipit instance to be configured with the multi-organization `github:` schema (one `GitHubApp`/secret per org) and the attacker to control at least one of the configured organizations (i.e., they can install their own GitHub App/webhook against Shipit and thus legitimately know that organization's `webhook_secret`) while wanting to influence a *different* tracked organization's repository. This is not a config the codebase disallows — `Shipit.github_app_config`/`github_organizations` explicitly document and support many-orgs setups — and no code path cross-checks the two fields, so it is a design-level gap rather than a rare edge case. Single-organization deployments (the default/common case) are not exploitable this way since there is only one webhook secret and one org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook secret matches the owner of the repository actually referenced by `full_name` before dispatching to handlers, e.g. compare `repository_owner` against `params.dig('repository', 'full_name')&.split('/')&.first` and reject (422) on mismatch, or have handlers resolve stacks scoped to `repository_owner` rather than trusting `full_name` alone.

### Proof of Concept
1. Configure Shipit with the multi-org schema in `secrets.yml`:
   ```yaml
   github:
     orga:
       app_id: ...
       webhook_secret: attacker_known_secret
     orgb:
       app_id: ...
       webhook_secret: victim_secret   # unknown to attacker
   ```
2. Attacker owns/administers `orga` (legitimately knows `attacker_known_secret`), while `orgb/victim-repo` is a Shipit-tracked stack belonging to `orgb`.
3. Attacker sends a `push` webhook to `/webhooks` with:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
   }
   ```
   signed with `X-Hub-Signature: sha1=<HMAC using attacker_known_secret>`.
4. `verify_signature` calls `Shipit.github(organization: "orga")`, verifies the HMAC against `attacker_known_secret`, and succeeds.
5. `PushHandler#process` resolves the target via `Repository.from_github_repo_name("orgb/victim-repo")`, finds `orgb`'s stack, and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")`, causing Shipit to act on a repository the attacker does not control and never proved ownership of. ```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
