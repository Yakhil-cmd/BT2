### Title
`EnvironmentVariables#interpolate` falls back to the Shipit host process's own `ENV` for undeclared `$VAR` references in deploy step commands - (File: `lib/shipit/environment_variables.rb`)

### Summary
`Shipit::EnvironmentVariables#interpolate` substitutes `$VAR` tokens found in a deploy/rollback step's command line using `@env.fetch(variable) { ENV[variable] }`, where `@env` is the task's approved/whitelisted environment hash and `ENV` is the Shipit web/worker process's own environment. Any `shipit.yml` step that references a variable not present in `@env` (e.g. not declared in `deploy.variables` or not supplied by the deployer) causes the Shipit host's own process environment value for that name to be silently interpolated into the command argv and then embedded via `Shellwords.escape`.

### Finding Description
The broken binding, stated as an equality that must hold but does not:

`value substituted for "$VAR" in a task command == @env[VAR]` (the task/deploy's approved env)

but the actual code produces:

`value substituted for "$VAR" == @env.fetch(VAR) { ENV[VAR] }`, i.e. when `VAR` is absent from `@env`, the value becomes `ENV[VAR]` — a key from the Shipit host process's own environment (e.g. `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL`, `GITHUB_TOKEN`, `SECRET_KEY_BASE`) — which is a completely different, higher-privilege value not scoped to the task at all.

Code path:
- [1](#0-0) : `interpolate` scans the argument string for `$\w+` tokens and replaces each with `Shellwords.escape(@env.fetch(variable) { ENV[variable] })`.
- [2](#0-1) : `Command#interpolate_environment_variables` calls `EnvironmentVariables.with(env).interpolate(argument)` recursively over `@args`.
- [3](#0-2) : `interpolated_arguments` invokes this for every argument of the command about to run.
- [4](#0-3) : `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so the interpolated string (containing the leaked host secret) becomes literal argv text passed to the spawned shell/process, which typically echoes/logs it into the task's visible output stream.

Root cause: the whitelist mechanism (`DeploySpec#filter_deploy_envs` / `filter_rollback_envs` calling `EnvironmentVariables#permit`, at [5](#0-4)  and [6](#0-5) ) only guards the *env hash construction* step — it raises `NotPermitted` if the deployer supplies env keys outside `deploy.variables`. It does **not** guard `interpolate`, which is a completely separate code path invoked later against the shell command string, and which has an explicit `ENV[variable]` fallback for any name not found in the task's `@env`. An attacker who controls `shipit.yml` (via a PR to their own fork/branch, since `shipit.yml` is read from the repository at the deployed ref) can reference `$AWS_SECRET_ACCESS_KEY` or any other name they guess exists in the Shipit host's process environment, and it will be substituted into the running command, ending up in task output that the attacker (as PR author, if they can trigger/see the deploy, or via any observer of the stack's task page) can read.

Existing guards checked and confirmed insufficient for this path: `EnvironmentVariables#permit`/`filter_deploy_envs` only restrict the *declared* env hash, not `interpolate`'s fallback; there is no `verify_signature`/webhook check relevant here since the exploit is purely in deploy-step command execution, not webhook handling; `ExplicitParameters`, `force_github_authentication`, `require_permission!` are unrelated to this internal interpolation step.

### Impact Explanation
Any deploy/rollback/task step in `shipit.yml` that references an undeclared `$VAR` name matching a key in the Shipit host process's environment causes that host secret's value to be embedded into the spawned command's argv, and typically into the task's log/output stream (e.g. via `echo`, or simply because many shells print the fully substituted command line, or a script that does `env` or fails with a usage message including the arg). This is exfiltration of deploy-time/host secrets (`AWS_SECRET_ACCESS_KEY`, `DATABASE_URL`, `GITHUB_TOKEN`, etc., depending on what's in the Shipit process's `ENV`) to anyone who can view the task output for that stack — matching the Critical category "exfiltration of ... deploy-time secrets." It is repeatable on every deploy/rollback/task run against any stack whose `shipit.yml` an attacker can influence (their own fork/PR branch that gets deployed) and is not limited to a single stack; the blast radius covers whatever secrets happen to be present in the Shipit host's own `ENV`, which is shared across all stacks/tenants served by that Shipit instance.

### Likelihood Explanation
Preconditions: an operator-triggered deploy must run against a `shipit.yml`/deploy step containing a `$VAR` reference where `VAR` is not declared in `deploy.variables` and not part of the task's approved env, and that name must coincidentally (or by educated guess, e.g. common names like `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL`, `SECRET_KEY_BASE`, `GITHUB_TOKEN`) match a key in the Shipit host process's own `ENV`. The attacker needs no privileges beyond being able to modify the `shipit.yml`/step scripts that will be deployed (e.g., a contributor to the repo, or an operator being tricked into merging a malicious PR) — no session, API token, or webhook secret is required, since this is purely an engine-internal command-interpolation bug triggered at deploy time. Guessing common secret-bearing env var names is low-cost and highly feasible given standard deployment infra conventions.

### Recommendation
Remove the `ENV[variable]` fallback in `Shipit::EnvironmentVariables#interpolate`; if `variable` is not present in `@env`, leave the `$VAR` token unexpanded (or raise/replace with an empty string) rather than reading from the Shipit host process's own environment. Interpolation should only ever draw from the already-whitelisted task/deploy env hash, never from the ambient process environment.

### Proof of Concept
In a minitest file (not shown here per scope rules, but conceptually):
```ruby
ENV['SHIPIT_TEST_SECRET'] = 'leaked'
command = Shipit::Command.new('echo $SHIPIT_TEST_SECRET', env: {}, chdir: '.')
output = command.run
assert_not_equal "leaked\n", output
```
Both sides of the binding to check: expected `interpolated value == @env['SHIPIT_TEST_SECRET']` (i.e., `nil`/unset, since `env: {}`), but actual `interpolated value == ENV['SHIPIT_TEST_SECRET']` (`'leaked'`). Running this against current code demonstrates the fallback fires and the host secret is echoed into task output, confirming the vulnerability as filed by the question.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
