## Analysis Summary

I found a valid analog: the webhook signature verification uses a different field to select the signing organization than the field the event handlers use to select the affected repository/stack.

### Title
Webhook signature is verified against an attacker-controllable organization key while handlers act on an independently-controlled repository field, allowing signature/target confusion - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to HMAC-verify the payload with by reading `repository.owner.login`, falling back to `organization.login` if the former is absent. But `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every event handler (`PushHandler`, `StatusHandler`, etc.) to resolve the `Stack`/`Repository` acted upon, reads a completely separate field: `repository.full_name`. Nothing enforces that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` used for signature selection.

### Finding Description
`verify_signature` in [1](#0-0)  computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is defined as: [2](#0-1) 

Meanwhile, every webhook handler resolves the target repository/stack independently via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')`: [3](#0-2) 

This is used, e.g., by `PushHandler#process` (which triggers `stack.sync_github`) and `StatusHandler#process` (which creates a commit status from an arbitrary state/description/target_url): [4](#0-3) [5](#0-4) 

The trust binding that should hold is:
`organization_whose_webhook_secret_signed(payload) == owner_of(repository.full_name acted upon by handler)`

Because the two lookups use different JSON keys (`repository.owner.login`/`organization.login` vs `repository.full_name`), an actor who legitimately controls a GitHub App installation for **their own** organization (and thus knows that organization's `webhook_secret`) can forge an HMAC-valid payload whose `repository.owner.login` is omitted/set to their own org (or where `organization.login` is present and set to their own org while `repository.owner.login` is absent), while `repository.full_name` names a stack belonging to a **different**, victim organization/repository. `Shipit.github(organization: repository_owner)` would resolve to the attacker's own configured app/secret, signature verification succeeds, and the handler then acts on the victim's `Stack` because it trusts `repository.full_name` unconditionally.

Whether this is reachable in a given deployment depends on `Shipit.github` supporting multiple organizations (multi-tenant secrets config), which the engine explicitly supports (`Shipit.github(organization:)`, `TOP_LEVEL_GH_KEYS`, `secrets_double_github_app.yml` fixture referenced in tests) — i.e., this is a documented, in-scope capability of the engine, not a host-app misconfiguration.

### Impact Explanation
This breaks a deployment-trust binding: the organization that authenticated the webhook is not the same as the repository that gets written/acted on. Depending on the handler abused:
- `PushHandler` can force `GithubSyncJob`/`sync_github` on a victim stack with an attacker-chosen `expected_head_sha`, deceiving the sync logic about the state of a repository the attacker does not control.
- `StatusHandler` lets the attacker fabricate arbitrary commit statuses (`state`, `context`, `description`, `target_url`) on a victim stack's commits, which can flip CI-required-status gating (`ci.require`) and enable an **unauthorized deploy or merge-queue merge** on a repository the attacker has no GitHub write access to.

This qualifies as High/Critical impact per scope: escalation into unauthorized deploy/merge, achieved purely by exploiting the organization-vs-repository binding mismatch, in a multi-tenant Shipit configuration.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with more than one GitHub organization/app (a supported, documented configuration), and (2) the attacker controls (or the webhook_secret is known for) at least one of those configured organizations while a victim stack for a different organization exists on the same instance. This is a realistic multi-tenant scenario for shared Shipit deployments serving several orgs, but not exploitable against a single-organization Shipit instance (where `repository_owner` always resolves to the one configured org's secret regardless of the mismatch).

### Recommendation
Verify that `repository.owner.login` (or `organization.login`) actually matches the owner encoded in `repository.full_name` before selecting the signing app/organization, or better: derive the app/organization used to verify the signature from the same authoritative field the handlers use to select the target (`repository.full_name`'s owner segment), so the field bound by the signature check is exactly the field the handlers act upon.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker's own GitHub App/secret) and `orgB` (victim, has a `Stack` for `orgB/victim-repo`).
2. Attacker crafts a `push` (or `status`) webhook JSON body:
```json
{
  "organization": {"login": "orgA"},
  "repository": {"full_name": "orgB/victim-repo"},
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
   Note `repository.owner.login` is omitted so `repository_owner` falls back to `organization.login` = `"orgA"`.
3. Attacker computes `X-Hub-Signature: sha1=<hmac using orgA's own webhook_secret>` over this exact raw body (valid, since they know their own org's secret).
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "orgA")`, which succeeds using the attacker's known secret.
5. `WebhooksController#create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker sha>")` on the victim's stack — despite the attacker having no credentials for `orgB`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
