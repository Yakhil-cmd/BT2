### Title
Webhook secret selection uses `repository.owner.login` while the acted-upon repository comes from `repository.full_name` — cross-organization forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub organizations behind a single instance, each configured with its own `webhook_secret` in `config/secrets.yml` (documented in `docs/setup.md` "Using Multiple Github Applications" and exercised by `Shipit.github_app_config`). `WebhooksController#verify_signature` selects **which** organization's secret to verify the HMAC signature against using a value taken from the very payload being verified: `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')`. Every webhook handler, however, resolves the actual `Repository`/`Stack` to act on from a *different* field of the same payload: `payload.dig('repository', 'full_name')` in `Handler#repository_name`. Nothing binds these two fields together — the code trusts that they always describe the same repository, but an attacker constructing the payload from scratch controls both independently. [3](#0-2) [4](#0-3) 

### Finding Description
`GitHubApp#verify_webhook_signature` computes `SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))` where `webhook_secret` comes from the `GitHubApp` instance chosen for `repository_owner`. This only proves that *someone who knows organization X's `webhook_secret`* produced the signature over the raw body — it says nothing about which repository the JSON body's `repository.full_name` claims to reference. [5](#0-4) 

In a multi-org deployment (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md:182-209`), each GitHub organization that onboards to the shared Shipit instance is handed its own `webhook_secret` value to configure on its own GitHub organization's webhook settings. An admin of organization `OrgOne` legitimately knows `OrgOne`'s `webhook_secret` (they configured it). That admin has no privileged access to Shipit itself, `OrgTwo`'s secret, or `OrgTwo`'s repositories — this is exactly an "unprivileged attacker" relative to `OrgTwo`.

That admin can craft an arbitrary POST body offline (never routed through GitHub) such as:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha belonging to OrgTwo/victim-repo>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
and sign it with `HMAC-SHA1(OrgOne_webhook_secret, raw_body)`. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgOne"`, loads `Shipit.github(organization: "OrgOne")`, and the signature check succeeds because the attacker legitimately possesses that secret. Verification passes even though the payload's `repository.full_name` names a repository under `OrgTwo`, which the attacker never controlled and whose secret was never checked. [6](#0-5) 

`WebhooksController#create` then dispatches to `Shipit::Webhooks.for_event(event)` handlers with the same parsed payload. `PushHandler#process` resolves `stacks` via `Handler#stacks`/`Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — `"OrgTwo/victim-repo"` — and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgTwo`'s stacks, an action never authorized by anything `OrgTwo` controls. [2](#0-1) [1](#0-0) 

This is the equality the code silently assumes but never enforces:
`organization verified via repository.owner.login == organization that owns repository.full_name`
An attacker who legitimately controls one side (their own org's secret + the `owner.login` field) can freely set the other side (`full_name`) to point at any repository configured in the shared Shipit instance.

### Impact Explanation
This lets an org admin who is a legitimate, unprivileged tenant of a shared multi-org Shipit deployment forge webhook events that are attributed to (and acted upon) a completely different organization's repositories. Depending on the event/handler this can drive `GithubSyncJob`/`sync_github` on another organization's stack (`PushHandler`), inject fabricated commit statuses onto another organization's commits (`StatusHandler`, `Commit#create_status_from_github!`), or otherwise pollute another tenant's stack/task state, since `Handler#stacks` performs no cross-check that the verified organization actually owns the acted-upon repository. Falsely injected commit statuses can flip a commit's `deployable?` status, directly influencing whether that commit becomes eligible for deployment on the victim organization's stack — an unauthorized-deploy-adjacent impact across a repository/organization trust boundary the attacker does not own.

### Likelihood Explanation
Requires only that the attacker be a legitimate admin/operator of *any one* organization already onboarded to a shared, multi-org Shipit instance (a configuration explicitly documented and supported: `docs/setup.md:182-209`, `test/dummy/config/secrets_double_github_app.yml`). No Shipit account, `ApiClient` token, or GitHub App credentials for the victim org are needed — only knowledge of the attacker's own org's `webhook_secret`, which by design that org's admins possess in order to configure their GitHub webhook. The forged request bypasses GitHub entirely and is POSTed directly to the Shipit webhooks endpoint.

### Recommendation
Bind the field used to select the verifying secret to the same field used for repository resolution: derive `repository_owner` from `repository.full_name`'s owner segment (or otherwise require `repository.owner.login` to equal the owner segment of `repository.full_name` before dispatching to handlers), and reject the payload if they disagree.

### Proof of Concept
1. Deploy Shipit with the multi-org config shown in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, each with a distinct `webhook_secret`), with a stack configured for `OrgTwo/victim-repo`.
2. As the (unprivileged, relative to `OrgTwo`) admin of `OrgOne`, compute:
```ruby
body = {
  ref: "refs/heads/master",
  after: "<attacker-chosen-sha>",
  repository: { owner: { login: "OrgOne" }, full_name: "OrgTwo/victim-repo" }
}.to_json
sig = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", OrgOne_webhook_secret, body)
```
3. POST to `/github/webhooks` (per `config/routes.rb`) with headers `X-Github-Event: push`, `X-Hub-Signature: <sig>`, body as above.
4. `verify_signature` passes (verified against `OrgOne`'s secret via `repository.owner.login`), while `PushHandler` acts on `OrgTwo`'s stack via `repository.full_name`, calling `sync_github` on a repository the attacker does not own — confirming the cross-organization write.
