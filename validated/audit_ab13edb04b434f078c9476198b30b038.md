### Title
Webhook signature verified against attacker-chosen `repository.owner.login`, not the repository actually written via `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) used to validate an inbound webhook using `repository_owner`, a value read directly out of the untrusted JSON body. The handlers that actually mutate state (create statuses, sync commits, etc.) select the target `Repository`/`Stack` using a *different* field from the same untrusted body: `repository.full_name`. Because these two fields are never cross-checked, an attacker who legitimately controls a Shipit-integrated GitHub organization (and therefore knows that organization's own `webhook_secret`) can sign a payload with their own secret while pointing `repository.full_name` at a completely different, victim-owned repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the organization used for verification purely from body content, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GitHubApp` configured for whatever organization name appears in `repository.owner.login` (or `organization.login`), and `verify_webhook_signature` simply HMACs the raw body with that organization's own `webhook_secret`: [3](#0-2) 

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers such as `PushHandler` and the status handler, which resolve the target repository from a **separate** field of the same JSON body — `repository.full_name` — with no comparison back to `repository_owner`: [4](#0-3) [5](#0-4) 

The binding that should hold is: `organization authenticated by signature == owner(repository written by handler)`. Because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated `Stack`/`Repository`) are independent, attacker-controlled fields of the same unauthenticated payload, this equality is never enforced. A payload can be crafted where `repository.owner.login = "attacker-org"` (an org the attacker legitimately administers and for which they know the real `webhook_secret`) while `repository.full_name = "victim-org/victim-repo"` (a repository tracked by the same Shipit instance under a different, unrelated GitHub App/organization config). The signature is computed correctly with the attacker's own secret, `verify_signature` passes, and the handler then acts on the victim's repository/stack.

This mirrors the report's root cause exactly: a value used for the trust computation (`weth`/`neededWeth`, here `repository_owner`) is decoupled from the value the operation is actually performed against (`rdnt` pool state, here `repository.full_name`), letting the attacker supply a "signed" input that authorizes an action on unrelated state.

### Impact Explanation
The status webhook handler (exercised in `test/controllers/webhooks_controller_test.rb:42-59`) creates a `Status` record directly from `sha`, `state`, `target_url`, `description`, and `context` fields of the payload, keyed only by matching the commit in the target repo resolved via `repository.full_name`. By forging a webhook signed with their own organization's real secret but naming a victim repository's `full_name`, an attacker can inject fabricated `success` CI statuses on a victim's tracked commits, or forge `push`/`check_suite` events causing `GithubSyncJob`/`RefreshCheckRunsJob` to run against the victim stack. Since commit/deployable statuses gate whether a commit is eligible for deploy, this can lead to an unauthorized deploy of a repository the attacker does not own or control — matching the "unauthorized deploy" Critical impact bucket, without requiring any Shipit session, API token, or the victim organization's own `webhook_secret`.

### Likelihood Explanation
The prerequisite is only that the attacker be an admin of *some* GitHub organization/repository that is legitimately connected to the same Shipit instance (a normal, unprivileged multi-tenant scenario for a shared Shipit deployment), which lets them freely retrieve/rotate their own app's `webhook_secret` value and craft arbitrary raw JSON bodies. No access to the victim's secret, session, or API token is required, and the endpoint (`WebhooksController#create`) is unauthenticated by design (webhooks). This is a realistic and directly reachable path in any multi-organization Shipit deployment.

### Recommendation
After signature verification, re-derive the acting organization from `repository.full_name` (or `organization.login` used to look up the `Repository`) and require it to match the organization whose secret validated the signature, rejecting the request (422) on mismatch. Alternatively, verify the signature using the secret belonging to the organization that owns the `Repository`/`Stack` actually resolved by `repository.full_name`, rather than trusting `repository.owner.login` from the payload to select the verifying secret.

### Proof of Concept
1. Attacker administers `attacker-org`, a GitHub organization/App legitimately connected to a shared Shipit instance, and thus knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "sha": "<victim commit sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "description": "forged",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully because the attacker really does know that secret.
5. `Shipit::Webhooks.for_event('status')` handler resolves the commit/stack via `repository.full_name = "victim-org/victim-repo"` and writes a forged `success` status on the victim's commit, independent of which organization's secret verified the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
