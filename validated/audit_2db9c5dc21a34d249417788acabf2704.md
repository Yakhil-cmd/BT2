### Title
GitHub webhook signature verification is keyed on an attacker-controlled organization field that is disjoint from the repository field the handlers actually act on - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) is used to verify the inbound HMAC signature by reading an attacker-supplied field from the raw JSON body (`repository.owner.login`, falling back to `organization.login`). The actual webhook handlers, however, resolve the target repository/stack using a completely different, independently-controlled field of the same body: `repository.full_name`. Because these two fields are never cross-checked, and because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured, an attacker can pick an organization slug that has no secret configured to make signature verification a no-op, while still causing the handler to act on an arbitrary victim `repository.full_name` / commit `sha`.

### Finding Description
`verify_signature` computes the organization used for verification like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')` when the former is absent/`nil`. This value is fed into `Shipit.github(organization: repository_owner)`, which looks up a `GitHubApp` instance per organization in a multi-tenant setup: [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as "always verified": [4](#0-3) 

Meanwhile, every webhook `Handler` resolves the affected repository purely from `payload.dig('repository', 'full_name')`, a field that is never compared against the organization used for signature verification: [5](#0-4) 

`PushHandler` and `StatusHandler` then act on that resolved repository/commit without any further authorization check: [6](#0-5) [7](#0-6) 

The binding that should hold is: **the organization whose secret authenticated the webhook == the organization that owns the repository the handler mutates**. Before a forged request: for a legitimate GitHub-signed webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always the same real organization, and the HMAC (computed over the full raw body by GitHub, using that organization's secret) covers the entire payload including `full_name`. After the attacker's forged request: `organization.login` (used only for GitHub-app/secret selection) is set to an org that Shipit multi-tenant config lists with no `webhook_secret` — a documented, optional configuration state (`webhook_secret: # nil` appears as valid syntax in `docs/setup.md` and in `config/secrets.development.example.yml` / `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml`) — while `repository.full_name` is set to an entirely different, victim organization's repository. Verification trivially returns `true` for the secret-less org (`return true unless webhook_secret`), and the handler then processes the victim's `full_name`/`sha` with no relation whatsoever to the org that "authenticated" the request.

This is exactly the class of bug in the report: a field acted upon (`repository.full_name`, driving which `Stack`/`Commit` gets mutated) is never actually covered by the binding used to gate the request (`repository_owner`/`organization.login`, which only selects a possibly-unprotected secret).

### Impact Explanation
An unauthenticated attacker (no `webhook_secret`, no GitHub App private key, no Shipit session, no `ApiClient` token) can submit forged `push` or `status` webhooks that are accepted as verified for any organization lacking a configured `webhook_secret`, yet cause mutations against Stacks/Commits belonging to an unrelated, fully-secured organization:
- Via `StatusHandler`, the attacker can inject fabricated commit statuses (`create_status_from_github!`) for arbitrary commit SHAs belonging to victim repositories, which can be used to fake "success" CI checks that a stack's merge-queue or deploy gating relies on, potentially enabling an unauthorized merge/deploy.
- Via `PushHandler`, the attacker can force `stack.sync_github` calls with attacker-chosen `expected_head_sha` against victim stacks.

This is an authentication-bypass primitive: the "signature verified" guarantee is defeated by exploiting the fact that the org used to select the verification secret is disjoint from the org whose data is mutated.

### Likelihood Explanation
Requires only that the Shipit deployment uses the documented multi-organization GitHub App configuration (`github: { org: {...} }`) with at least one organization entry that has no `webhook_secret` set — a state explicitly shown as valid/example in the shipped configuration templates and setup docs, not a deviation from documented mounting. No credentials, tokens, or GitHub App secrets are needed by the attacker; only the webhook endpoint's public URL and knowledge of an existing organization slug in that Shipit instance's config (visible via the app's own stacks/repositories UI) and the victim repository's `owner/name`.

### Recommendation
- In `WebhooksController#verify_signature`, require that the organization used to select the `GitHubApp`/secret (`repository_owner`) matches the owner segment of `repository.full_name` that the handlers will subsequently use; reject the request otherwise.
- Do not fall back to `organization.login` when `repository.owner.login` is present but different from `full_name`'s owner.
- Change `GitHubApp#verify_webhook_signature` to fail closed (return `false`, not `true`) when `webhook_secret` is blank, or require `webhook_secret` to be mandatory for every organization entry in a multi-tenant config, with startup validation that highlights missing secrets.
- Have webhook `Handler`s resolve the repository via the same organization value that was cryptographically verified, rather than re-parsing an independent `full_name` field from the same untrusted payload.

### Proof of Concept
Assume a Shipit deployment configured with multiple GitHub orgs, where `SecretOrg` has a real `webhook_secret`, and `NoSecretOrg` is configured with `webhook_secret:` left blank (a documented valid state), and `SecretOrg/victim-repo` exists as a tracked Stack.

1. Attacker sends, with no `X-Hub-Signature` header (or any garbage value):
```
POST /github/hooks   (whatever route mounts Shipit::WebhooksController#create)
X-Github-Event: status

{
  "organization": { "login": "NoSecretOrg" },
  "repository": { "full_name": "SecretOrg/victim-repo" },
  "sha": "<victim commit sha awaiting CI>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
2. `repository_owner` evaluates to `"NoSecretOrg"` (since `repository.owner` is absent, it falls back to `organization.login`).
3. `Shipit.github(organization: "NoSecretOrg").verify_webhook_signature(...)` returns `true` unconditionally because that org has no `webhook_secret` (`return true unless webhook_secret`).
4. `StatusHandler#process` runs against `Commit.where(sha: ...)` resolved solely from the request's `sha`, unrelated to `NoSecretOrg`, and creates a fabricated successful status on the victim commit in `SecretOrg/victim-repo`. [8](#0-7) [4](#0-3) [9](#0-8)

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit

        def process
