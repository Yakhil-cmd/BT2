### Title
Webhook signature check silently passes when `webhook_secret` is unset, letting an unauthenticated caller forge a `membership` event and escalate a `User` into `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects a per-organization `GithubApp` and asks it to verify the `X-Hub-Signature` header against the raw request body [1](#0-0) . That verification is implemented as `return true unless webhook_secret`, i.e. if the organization's `webhook_secret` is blank/unset, **any** payload — signed or not — is accepted [2](#0-1) . `webhook_secret` is explicitly documented as optional (`webhook_secret (optional)`) in setup docs and is shown as `nil` for a legitimately configured org in the test fixtures [3](#0-2) . Once past this check, `Shipit::Webhooks::Handlers::MembershipHandler#process` blindly trusts the attacker-supplied `team` and `member` fields to create/find a `Team` by `github_id` and add a `Membership` for that team [4](#0-3) . `User#authorized?` is computed purely from `teams` membership rows compared against `Shipit.github_teams` [5](#0-4) , so forging a `Membership` row is equivalent to forging real GitHub-org-team membership, which is the entire authorization gate for the application [6](#0-5) .

### Finding Description
The trust binding that should hold is: *"the organization whose webhook signature validated == the organization/team data actually written to the database."* This binding is broken because signature "validation" for an org with an unset secret is not validation at all — it unconditionally returns `true` [2](#0-1) .

The webhook dispatch flow is:
1. `WebhooksController#create` parses the raw JSON and dispatches it to handlers registered for the `X-Github-Event` header, with no additional authorization [7](#0-6) .
2. `verify_signature` picks `Shipit.github(organization: repository_owner)` — for `membership` events, `repository_owner` falls back to `params.dig('organization', 'login')` [8](#0-7) . If that organization is configured with a blank `webhook_secret`, `verify_webhook_signature` returns `true` for literally any body/signature pair.
3. `MembershipHandler#process` then executes with full trust: it creates a `Team` keyed by the attacker-supplied numeric `github_id` (a value that is public and obtainable from GitHub's API without any credentials) and calls `team.add_member(member)` for a `User` resolved by login [4](#0-3) .
4. If the forged/looked-up `Team#github_id` matches (or is made to match) one of the `Team` rows referenced by `Shipit.github_teams`, the targeted `User` immediately becomes `authorized?` per `User#authorized?`'s equality check `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) .

This is the same bug class as the Vyper commit's root cause: a check that is supposed to enforce a strict equivalence (signature ⇒ authentic organization) is effectively skipped/weakened for a valid configuration state (unset secret), producing an unsound trust decision downstream (which org/team is allowed to write authorization-relevant data).

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" boundary explicitly called out as a High-impact outcome. An attacker with no Shipit session, no `ApiClient` token, and no GitHub write access to any repository can grant themselves (or any known GitHub login) membership in a `Team` whose id is one of `Shipit.github_teams`, bypassing the entire `force_github_authentication` gate that otherwise restricts every controller in the engine [6](#0-5) . From there the attacker can reach any authenticated-only action (stacks, deploys, rollbacks, API client management), effectively achieving unauthorized deploy/rollback capability.

### Likelihood Explanation
The precondition — at least one configured GitHub organization/app with no `webhook_secret` — is explicitly supported and documented as optional configuration [3](#0-2) , and appears as a real example in the multi-org secrets fixture used by the test suite [9](#0-8) . No credential, session, or GitHub write access is required to exploit it — the attacker only needs to POST to `/webhooks` with the `X-Github-Event: membership` header and a crafted JSON body. The only "unknown" the attacker needs is the numeric `github_id` of an authorized team, which is retrievable from GitHub's public/team API without any special privilege for teams under orgs the attacker can query, or otherwise guessable/enumerable given `github_id` is a small sequential integer.

### Recommendation
- Do not treat an unset `webhook_secret` as "signature verified"; either require `webhook_secret` for all organizations that have any webhook-driven write path (especially `membership`), or make `verify_webhook_signature` fail closed instead of returning `true` when the secret is blank.
- In `MembershipHandler`, cross-check that `params.organization.login` (the value actually used to select the signing organization) matches the organization already recorded against the `Team` being mutated, and re-validate team membership against the GitHub API rather than trusting webhook payload fields outright for authorization-relevant writes.
- Consider decoupling `User#authorized?` from locally-cached `Membership` rows that can be populated by external webhook input; treat webhook-derived team membership as a cache that must be periodically reconciled with a fresh, authenticated GitHub API call, not as an authoritative source for authorization decisions.

### Proof of Concept
Assume `OrgTwo` (or any organization configured with `webhook_secret: nil`, a supported configuration per `docs/setup.md`) is registered in Shipit, and a `Team` row already exists (or is discoverable) with `github_id` equal to one of the ids in `Shipit.github_teams`.

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {
    "id": <github_id of an authorized Shipit.github_teams entry>,
    "name": "Developers",
    "slug": "developers",
    "url": "https://api.github.com/teams/1234"
  },
  "organization": { "login": "OrgTwo" },
  "member": { "login": "attacker-github-login" }
}
```

Because `OrgTwo`'s `webhook_secret` is unset, `verify_webhook_signature` returns `true` regardless of (or absent) the `X-Hub-Signature` header [2](#0-1) . `MembershipHandler#process` then creates/finds the `Team` and adds `attacker-github-login` as a member [4](#0-3) . On the attacker's next OAuth login (or if their `Shipit::User` row already exists), `authorized?` now returns `true`, granting full access to the Shipit UI/API as an authorized user [5](#0-4) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?

          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')

        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
