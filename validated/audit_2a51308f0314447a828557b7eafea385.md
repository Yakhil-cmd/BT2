### Title
Merkle "Node-as-Leaf" Second-Preimage Forgery Allows Forged `in merkle` / `is_valid_merkle_proof` Membership Proofs - (File: `merkle.js`)

### Summary
`merkle.js` implements a classic (non-domain-separated) Merkle tree, and its `verifyMerkleProof()` function contains the exact bug class described in the report: a verifier can be tricked into accepting a "proof" for content that was never actually committed as a real leaf, by re-using an internal node's pre-image as a forged "leaf element". This is the same root cause as the MerkleDB report — hashing is reused across different structural levels of the tree (leaf vs. internal node) without any domain separation, so a shortened/substituted piece of the tree can still reproduce the expected root and pass verification. The code even contains an unresolved comment acknowledging this: `merkle.js` line 85, `// Node-as-Leaf issue might matter in some cases`. [1](#0-0) 

### Finding Description
The tree is built by hashing leaves and then repeatedly hashing concatenated pairs of hashes to obtain parent nodes, with no leading byte/tag distinguishing "leaf hash" from "internal node hash": [2](#0-1) [3](#0-2) 

Verification simply re-derives the root from a supplied `element` and `siblings` list: [1](#0-0) 

Because `verifyMerkleProof` computes `hash(element)` as the starting leaf and then walks up through the supplied siblings, an attacker who knows the two hash strings that form some internal node `n = hash(h_left + h_right)` can submit `element = h_left + h_right` (the raw concatenation, not an actual original leaf value) together with the *remaining* siblings above that internal node. `hash(element)` will equal `n`, and the rest of the proof will reconstruct the true root exactly as if `n` were a legitimate leaf hash. This lets an attacker "prove" membership of an artificial, self-chosen `element` string that was never part of the original element set — the pruned/forged proof still hashes up to the correct root, mirroring how the MerkleDB bug allowed a shortened path to still match the root ID.

This primitive is exposed to unprivileged users in two places:
1. Address/asset spending conditions via the `in merkle` operator, verified during `validateAuthentifiers`: [4](#0-3) 
2. Autonomous Agent (AA) oscript formula evaluation via `is_valid_merkle_proof`, where **both** the `element` and the `proof` come directly from AA trigger data supplied by an untrusted trigger sender: [5](#0-4) 

In the `is_valid_merkle_proof` path, the `element` argument is fully attacker-controlled (e.g., `trigger.data.claim`), so an AA trigger sender can directly supply a forged concatenation string as `element` plus a truncated sibling list, and pass the check for *any* root the AA is validating against (e.g., a root published via a data feed), without ever knowing a genuine whitelisted/committed leaf value.

### Impact Explanation
Any oscript/AA logic that uses `in merkle` (address definitions) or `is_valid_merkle_proof` (AA formulas) to gate spending, whitelisting, or payouts based on membership in an oracle-published Merkle root can be bypassed by a party who does not possess a genuine leaf value, as long as they can observe (or derive) the two child hashes of some internal node of that tree — which is trivial once any other legitimate participant's proof has been broadcast on-chain (siblings are posted publicly as authentifiers/trigger data). This directly enables:
- Unauthorized spending from addresses defined with `in merkle` spending conditions,
- AA fund loss / incorrect payout logic where an AA trusts `is_valid_merkle_proof` to gate a fund release based on a whitelist/claim root, since an attacker can forge a "membership" proof for an arbitrary self-chosen `element` that was never part of the committed set.

This matches the required "concrete unauthorized spending / AA fund loss" impact category.

### Likelihood Explanation
Exploitation requires no privileged access — only knowledge of two hash strings that are siblings of an internal node in a previously (or concurrently) revealed proof for the same tree, which is realistically available any time more than one leaf's proof has been publicly disclosed (which is inherent to how such proofs are used and broadcast on the DAG). The forgery computation itself is a couple of SHA-256 hashes, no cryptographic breaking required. Likelihood is Medium-to-High for any application (address definition or AA) that relies on `in merkle`/`is_valid_merkle_proof` for security-critical whitelist/claim checks.

### Recommendation
Add domain separation between leaf hashing and internal-node hashing in `merkle.js` (e.g., prefix leaves with `0x00` and internal nodes with `0x01` before hashing, as in RFC 6962 / standard fixes for this well-known "second preimage"/"node-as-leaf" class of Merkle-tree bugs), in both `getMerkleRoot`/`getMerkleProof` (construction) and `verifyMerkleProof` (verification). Additionally, reject `element` values whose length happens to equal exactly two concatenated hash outputs to reduce risk for already-deployed trees, though the primary fix must be domain separation.

### Proof of Concept
1. Oracle builds a 4-leaf tree over elements `e0..e3` and publishes `root = h(h(h(e0)+h(e1)) + h(h(e2)+h(e3)))` via a data feed (`feed_name`), per `merkle.js:9-20` [2](#0-1) .
2. A legitimate user proves membership of `e0`, revealing on-chain (as an authentifier or AA trigger payload) `proof = {index:0, siblings:[h(e1), n2], root}` where `n2 = h(h(e2)+h(e3))`.
3. Attacker now knows `h(e0)` (computable) and `h(e1)` (from the revealed proof), and can compute `n1 = h(h(e0)+h(e1))`.
4. Attacker sets `forged_element = h(e0) + h(e1)` (raw concatenation string) and constructs `forged_proof = {index:0, siblings:[n2], root}`.
5. Calling `verifyMerkleProof(forged_element, forged_proof)` per `merkle.js:84-102` computes `hash(forged_element) = n1`, then `hash(n1 + n2) = root`, returning `true` — even though `forged_element` was never one of the oracle's committed leaves `e0..e3`.
6. If this check gates an `in merkle` spending condition (`definition.js:1004-1020`) or an AA's `is_valid_merkle_proof($trigger.data.claim, $trigger.data.proof)` (`formula/evaluation.js:1768-1807`), the attacker satisfies the membership check with a self-fabricated claim and unlocks funds/authorization intended only for genuine whitelisted leaves. function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
