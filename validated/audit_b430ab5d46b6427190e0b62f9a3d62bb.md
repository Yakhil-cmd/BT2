### Title
Attacker-controlled stake mutation (`Split`) during reward-distribution window triggers `assert_eq!` panic in `build_updated_stake_reward`, halting the validator instead of producing the claimed silent capitalization drift - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The literal claim in the question — that `distribute_epoch_rewards_in_partition`'s `fetch_add(stake_reward_lamports_minted)` / `fetch_sub(block_reward_lamports_burned)` pair can be applied inconsistently by an attacker withdrawing mid-window — does not hold: the only failure path (`AccountNotFound`) correctly avoids crediting `stake_reward_lamports_minted` and correctly debits `block_reward_lamports_burned`, so `pre_cap + minted - burned == post_cap` is preserved even when the stake account disappears from the cache [1](#0-0) . However, the same "attacker mutates own stake account mid-window" scenario does trigger a real, reachable bug: a partial mutation (e.g. `Split`) that leaves the stake account present but with a different delegation causes an `assert_eq!` panic in `build_updated_stake_reward`, because that function reads the *live* `StakesCache` at distribution time rather than the calculation-time snapshot [2](#0-1) .

### Finding Description
`store_stake_accounts_in_partition` looks up each stake account via `stakes_cache_accounts.get(&partitioned_stake_reward.stake_pubkey)`, where `stakes_cache_accounts` is the bank's *current* `StakesCache`, not the calculation-time snapshot used to compute `PartitionedStakeReward.inflation.stake` [3](#0-2) .

Inside `build_updated_stake_reward`, when the `adjust_delegations_for_rent` feature is inactive (the default/legacy path), the code asserts that the *current* delegation plus the (calculation-time) `stake_reward` equals the *precomputed* `new_stake.delegation.stake` value:
```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, ...);
``` [2](#0-1) 

`stake.delegation.stake` comes from the live cache entry (post-attacker-mutation), while `new_stake.delegation.stake` is the value baked into `partitioned_stake_reward` during the calculation phase (pre-mutation delegation + reward). The function's doc comment explicitly (and incorrectly) assumes this can't diverge: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned"* [4](#0-3) . No such restriction was found anywhere in the runtime: the reward-distribution window (`EpochRewardStatus::Active`) is tracked purely as bank-internal state and is not consulted by the stake program or transaction-processing pipeline to reject stake instructions; a test even documents that ordinary account mutations (system transfers to stake accounts) are explicitly allowed during the reward period [5](#0-4) .

Attack flow: attacker delegates stake, reward calculation runs at the epoch boundary and fixes `stake_reward` and `new_stake.delegation.stake` for the attacker's pubkey based on the pre-mutation delegation. Before the block whose `partition_index` covers this account is reached (distribution can span up to 10% of an epoch's slots, per `get_reward_distribution_num_blocks` [6](#0-5) ), the attacker submits an ordinary `Split` instruction (owner-authorized, no privileged access needed) against their own stake account, changing its live delegation in the `StakesCache`. When `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward` later processes this account, the `assert_eq!` fails and panics inside bank/block processing, which — since all validators execute the same partitioned distribution deterministically at the same block height — crashes every validator processing that slot simultaneously, i.e. a consensus/epoch-boundary halt.

### Impact Explanation
This is a validator-crashing consensus halt reachable purely from a normal user's own stake-account instructions (no special privileges, no leader/gossip control). It falls under the "epoch-boundary halt" impact category explicitly listed as in-scope. It is distinct from — and does not support — the literal capitalization-drift claim in the question: the burn/mint accounting itself (`fetch_add`/`fetch_sub`) is internally consistent on the `AccountNotFound` error path.

### Likelihood Explanation
Preconditions: attacker must have a delegated stake account that is scheduled into some reward partition (guaranteed for any staker at an epoch boundary), and must be able to submit a `Split` (or similar) instruction against it before its partition's distribution block executes — a window that can span up to ~10% of an epoch's slots. This requires no validator/operator privileges and is fully reproducible by any staker; the only variable is correctly timing the mutation relative to the (attacker-observable) partition schedule, which is derived deterministically from `hash_rewards_into_partitions` using public information (parent blockhash, pubkey).

### Recommendation
`build_updated_stake_reward` (and `store_stake_accounts_in_partition`) should not assert equality between a live, potentially-mutated cache entry and a value computed at an earlier point in time. Instead, either (a) snapshot/freeze the exact stake account state used for reward calculation and reuse that snapshot (not the live cache) when applying rewards at distribution time, or (b) treat any observed delegation mismatch as a burn case (like `AccountNotFound`) rather than an `assert_eq!` panic, and correspondingly emit metrics/alerts instead of crashing.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
