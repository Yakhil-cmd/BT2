### Title
Signature-verification identity (`repository.owner.login`) is decoupled from the identity actually acted upon (`repository.full_name`), enabling cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `organization.login`). Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the actual `Repository`/`Stack` to mutate using a completely different field: `payload.dig('repository','full_name')`. Nothing ties these two fields together, so a payload that is validly signed for organization A but declares `repository.full_name` pointing at organization B's tracked repository will pass signature verification and then act on B's stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes the authorizing identity like this: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` is used purely to pick which `webhook_secret` HMACs the raw request body, and `verify_webhook_signature` only proves that the entire raw payload was signed with *some org's* secret — it never checks that the org whose secret matched is the same org referenced elsewhere in the payload.

Every handler, however, resolves the actual repository/stack to act on using a different, unrelated field, `repository.full_name`: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits this string on `/` and looks up any repository row by owner/name with no relation back to `repository.owner.login`: [4](#0-3) 

Because both `repository.owner.login` and `repository.full_name` are ordinary fields inside the same JSON body that the attacker fully authors and signs themselves (for their own onboarded organization), nothing prevents the attacker from setting them inconsistently: `repository.owner.login = "attacker-org"` (so `verify_signature` fetches and matches `attacker-org`'s `webhook_secret`, which the attacker legitimately possesses because they administer that org's GitHub App), while `repository.full_name = "victim-org/victim-repo"` (a different repository/stack tracked by the same shared Shipit instance).

This breaks exactly the trust binding: *the organization that authenticated the request* (`repository_owner` / `attacker-org`) *≠ the repository that is actually written* (`repository.full_name` / `victim-org/victim-repo`).

This is directly reachable for every registered handler that keys off `repository.full_name` without re-validating the owner, including:
- `PushHandler` — triggers `stack.sync_github(expected_head_sha: ...)` for an arbitrary victim stack: [5](#0-4) 
- `StatusHandler` — forges a CI status (`state`, `context`, `description`) on an arbitrary victim commit, which can influence `ci.require` / `ci.blocking` deploy-gating checks defined in the victim's `shipit.yml`: [6](#0-5) 
- `CheckSuiteHandler` — schedules a check-run refresh for an arbitrary victim stack/commit: [7](#0-6) 
- Pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`) — archive/unarchive/create review stacks for an arbitrary victim repository, all resolving via `params.repository.full_name`: [8](#0-7) 

This is only exploitable in a multi-tenant Shipit deployment where more than one GitHub organization is configured with its own `webhook_secret` (as documented/scaffolded in `config/secrets.development.shopify.yml`, where multiple orgs each define their own `webhook_secret`), and where the attacker administers/owns one such onboarded organization — i.e., legitimately knows one org's `webhook_secret` — but does not have any privilege over the victim org's repositories in Shipit. No `ApiClient` token, session, or GitHub write access to the victim repository is required.

### Impact Explanation
An attacker who controls (owns) one organization onboarded to a shared Shipit instance can forge signed webhook events acted upon as if issued for any other organization/repository tracked by the same instance. This crosses a repository/organization trust boundary using only credentials the attacker legitimately possesses for their *own* tenant, which is an unauthorized cross-repository action: it can force `GithubSyncJob`s and, most notably, fabricate GitHub commit statuses on victim commits (`StatusHandler`) that can be used to satisfy `ci.require`/unblock `ci.blocking` safety gates defined in the victim's `shipit.yml`, indirectly influencing whether a deploy proceeds. This satisfies the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the deployment to host more than one GitHub organization (a documented, supported configuration per `config/secrets.development.shopify.yml`) and requires the attacker to legitimately administer one of those organizations' GitHub Apps (so they know that org's `webhook_secret`). Given that requirement, exploitation itself is trivial — a single crafted POST to `/webhooks` with a valid HMAC for the attacker's own org and mismatched `repository.full_name`/`owner.login` fields, no rate limiting or additional secrets needed.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that the organization used to select/validate the signing secret is consistent with the organization embedded in `repository.full_name` (and `repository.owner.login`) before dispatching to handlers — e.g., reject the request if `repository_owner` does not case-insensitively match the owner segment of `repository.full_name`.

### Proof of Concept
1. Attacker administers `attacker-org`, onboarded to the shared Shipit instance with its own `webhook_secret` (`S_attacker`), and knows `S_attacker`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, which correctly validates the signature against `S_attacker` and passes.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for the victim's stack — despite the request never being authenticated for `victim-org`.
