### Title
Indivisible ("NFT-like") assets sent to an AA are permanently frozen because AAs can never send them back, including on bounce - (File: aa_composer.js)

### Summary
An Autonomous Agent (AA) trigger sender can transfer any asset, including a capped/indivisible ("fixed_denominations") asset that behaves like an NFT in Obyte, to an AA address. However, the AA response-composition logic in `aa_composer.js` unconditionally strips any outgoing `payment` message whose asset is `fixed_denominations` before the response unit is built - this happens both for regular AA-authored payment messages and, critically, for the automatic `bounce()` refund path that is supposed to return received coins to the sender when the trigger is rejected or doesn't match a bounce_fees threshold.

### Finding Description
When an AA trigger is processed, `handleTrigger()` composes outgoing messages via `sendUnit()`. Inside `sendUnit`, each `payment` message's asset is looked up, and if `objAsset.fixed_denominations` is true, the message is intentionally skipped from `completeMessage()`:
```
if (objAsset.fixed_denominations) // will skip it later
    return cb();
```
and later filtered out entirely:
```
messages = messages.filter(function (message) { return (message.app !== 'payment' || !message.payload.asset || !assetInfos[message.payload.asset].fixed_denominations); });
``` [4](#0-3) 

This filtering is applied uniformly to *all* messages passed into `sendUnit`, including the messages built by the `bounce()` function, which iterates over `trigger.outputs` (every asset the trigger sent to the AA) and builds a refund `payment` message for each asset without any check for `fixed_denominations`:
```
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    ...
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
...
sendUnit(messages);
``` [5](#0-4) 

Because `sendUnit` cannot send a payment for a `fixed_denominations` asset (indivisible-asset payments require picking specific coins/serial numbers with proofs, something the AA formula/payment-composition path never does for outgoing messages), the bounce refund silently drops that asset's payment message. There is no other mechanism for an AA to send an indivisible asset out - any AA-authored `payment` message referencing a `fixed_denominations` asset is likewise dropped by the same filter, regardless of what the AA's oscript logic intends. This mirrors the OpenQ report exactly: a user posts a "transfer" (unit output) of an NFT-like asset to a smart-contract-like address (the AA), and the recipient contract has no code path capable of ever sending that asset back out, so it becomes permanently stuck in the AA's balance.

### Impact Explanation
Any indivisible/capped asset (the closest ocore analog to an NFT, since it is issued with a fixed unit denomination and can represent a unique non-fungible token when capped at 1) sent to any AA is irrecoverably locked: it cannot be refunded automatically via `bounce()`, and no AA-authored logic can ever emit a payment message carrying that asset out again. This is a permanent freezing of AA-held funds for that asset class, affecting every AA on the network that might receive such assets (accidentally or intentionally, e.g., an AA designed as an escrow/marketplace for indivisible assets), not just a single malformed contract.

### Likelihood Explanation
This is trivially triggerable by any unprivileged unit poster: simply send a `fixed_denominations` asset as an output to any AA address as part of a trigger unit. No special privileges, oracle cooperation, or malicious AA definition are required. It reproduces deterministically every time a `fixed_denominations` asset is included in `trigger.outputs`, whether the AA's own case logic tries to refund it, bounces due to insufficient bytes to cover fees, or the AA simply doesn't reference it at all.

### Recommendation
Either (a) disallow sending `fixed_denominations` assets to AA addresses at the validation layer (reject such payments to known AA addresses, analogous to the existing check for private assets), or (b) implement genuine support for AAs to compose outgoing `fixed_denominations` payments (picking specific denominated coins with correct inputs) so that `bounce()` and AA-authored payment messages can actually return/forward such assets instead of silently dropping them.

### Proof of Concept
1. Issue an indivisible asset with `fixed_denominations: true` and `cap: 1` (an NFT-like unique token).
2. Post a unit whose trigger sends this asset as an output to any AA address, alongside enough base bytes to cover `bounce_fees`.
3. If the AA's case logic doesn't match this trigger (or the AA reaches `bounce()` for any other reason, e.g. insufficient balance elsewhere), observe in `aa_composer.js` `bounce()` that a refund `payment` message is queued for the asset, but `sendUnit()` at lines 1327-1361 strips it from the outgoing messages because `assetInfos[asset].fixed_denominations` is true.
4. The asset output remains held by the AA address with `is_spent=0` indefinitely - no unit, bounce, or AA logic can ever move it out, permanently freezing it.
