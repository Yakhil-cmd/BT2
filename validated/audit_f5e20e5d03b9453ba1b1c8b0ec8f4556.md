This confirms the vulnerability path is real and reachable. Review stacks can be auto-provisioned on PR open when `repository.review_stacks_enabled` and `provisioning_behavior_allow_all?` (repo config, not attacker-controlled, but plausible for open-source review-app setups), triggering `ReviewStackProvisioningQueue` which eventually runs deploy/provision tasks against the checked-out PR branch content, including its `shipit.yml`.

### Title
Path traversal in `machine.directory` config allows attacker-controlled `chdir` outside sandboxed working directory - (File: app/models/shipit/deploy_spec/file_system.rb)

### Summary
`DeploySpec::FileSystem#file` and the `directory` accessor build filesystem paths and `chdir` targets directly from the repository-controlled `machine.directory` key in `shipit.yml`/`shipit.<env>.yml`, with no validation that the resulting path stays within `@app_dir`/`working_directory`. An attacker who can get their branch's `shipit.yml` checked out for any task (e.g. an auto-provisioned review stack, or a manually triggered task on the PR commit) can set `machine.directory: ../../../etc` (or similar) to make `Command#start` `mkdir_p` and execute subsequent shell commands outside the intended working directory.

### Finding Description
The broken binding: the value used as `chdir` for `Command#start`, i.e. `TaskCommands#steps_directory`, is claimed to equal a subdirectory of `@task.working_directory` (`File.join(stack.deploys_path, id.to_s)`), but no code enforces that equality/containment.

Code path:
- `DeploySpec#directory` reads straight from `config('machine', 'directory')`, which is `shipit.yml` content from the checked-out commit: `app/models/shipit/deploy_spec.rb:73-75`. [1](#0-0) 
- `DeploySpec::FileSystem#file` joins `@app_dir`, `directory`, and `path` with `File.join`/`Pathname.new`, performing no traversal check: [2](#0-1)  This is exactly what the existing test `"#file is impacted by machine.directory"` demonstrates (it only checks the join behavior, not any sandboxing): [3](#0-2) 
- `TaskCommands#steps_directory` similarly does `File.join(@task.working_directory, sub_directory)` when `deploy_spec.directory` is present, again with no traversal check, and this is used as the `chdir:` for `install_dependencies` and `perform`: [4](#0-3) [5](#0-4) 
- This is already validated by an existing unit test showing `chdir` following an attacker-influenceable `directory` value verbatim: [6](#0-5) 
- `Command#start` then does `FileUtils.mkdir_p(@chdir)` and `PTY.spawn(..., chdir: @chdir)` on whatever path was supplied, with no containment check: [7](#0-6) 

Attacker's exact action: open a pull request (or push to a branch) whose `shipit.yml`/`.shipit/shipit.yml` sets `machine: { directory: '../../../../tmp/evil' }`. If the target repository has `review_stacks_enabled` with `provisioning_behavior_allow_all?` (or `allow_with_label?`/`prevent_with_label?` matched by the attacker's own PR labels, which an unprivileged PR author can set on their own PR), `Webhooks::Handlers::PullRequest::OpenedHandler#process` auto-creates a `ReviewStack` and enqueues provisioning via `ReviewStackProvisioningQueue.add`: [8](#0-7) [9](#0-8)  Task execution then checks out the PR branch's commit, reads its `shipit.yml` via `DeploySpec::FileSystem`, and runs dependency/deploy/provision steps `chdir`'d into the traversal path.

Why guards don't stop it: `verify_signature`/webhook auth only validates that the payload legitimately came from GitHub for that repo — it does not (and cannot) sanitize the *content* of the `shipit.yml` on the attacker's own branch. There is no schema validation, allowlist, or `Pathname#cleanpath`/`realpath`-and-containment check anywhere in `DeploySpec::FileSystem#file`, `#directory`, or `TaskCommands#steps_directory`.

### Impact Explanation
Critical. Once a task executes with a traversal `machine.directory`, `Command#start` creates directories and spawns shell commands (`FileUtils.mkdir_p`, `PTY.spawn`) with `chdir` pointed anywhere writable/reachable on the deploy host's filesystem, not confined to `Stack#deploys_path`/the task's `working_directory`. Combined with `dependencies_steps`/`deploy_steps`/`provision` commands (also attacker-controlled via the same `shipit.yml`), this gives the PR author command execution rooted outside the sandbox, which can affect other stacks' checkouts or host state depending on filesystem layout and permissions — i.e., RCE on the deploy host beyond the intended per-task sandbox.

### Likelihood Explanation
Requires the target repository to have review stacks (or another mechanism) that will run a task against an unmerged PR branch's content — this is a documented, first-class Shipit feature (`review_stacks_enabled`, `provisioning_behavior_allow_all?`/`allow_with_label?`) intended to let PR authors test their own branches, so it is a realistic configuration, not a corner case. No secrets or elevated privileges are needed by the attacker; opening a PR (or applying a label they control on their own PR under `allow_with_label`) is sufficient. This is repeatable against every PR the attacker opens.

### Recommendation
In `DeploySpec::FileSystem#file` (and `TaskCommands#steps_directory`), resolve the joined path (`File.expand_path`/`Pathname#cleanpath`) and assert it is contained within `@app_dir`/`working_directory` before use, rejecting or clamping any `machine.directory` value that escapes the sandbox.

### Proof of Concept
1. In a test for `DeploySpec::FileSystem`, stub `load_config` (or `directory`) to return `'machine' => { 'directory' => '../../../tmp/evil' }`, call `spec.file('baz')`, and assert the result does **not** start with `@app_dir` (currently it does escape, demonstrating the bug):
```ruby
@spec.stubs(:load_config).returns('machine' => { 'directory' => '../../../tmp/evil' })
resolved = @spec.file('baz').cleanpath.to_s
refute resolved.start_with?(@app_dir.to_s)
```
2. In a `TaskCommands`/`DeployCommands` test analogous to the existing `"the working_directory can be overriten in the spec"` test, stub `deploy_spec.directory` to return a traversal string and assert `commands.perform.first.chdir` equals the escaped path outside `@task.working_directory`, mirroring `test/unit/deploy_commands_test.rb:273-279` but with a `../` value instead of `'my_directory'`.
