### Title
Webhook signature is verified against `repository.owner`/`organization` while the handler acts on `repository.full_name` - cross-organization stack takeover in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In a multi-GitHub-App Shipit deployment (documented in `docs/setup.md` under "Using Multiple Github Applications"), each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using the *organization* field of the payload, but the webhook handler that actually mutates state resolves the target repository from an entirely different, unverified field: `repository.full_name`. An attacker who owns/administers *any* organization onboarded to the same Shipit instance (and therefore knows that organization's own `webhook_secret`, which they can read from their own GitHub App settings) can forge a valid signature for a payload whose `repository.full_name` points at a victim repository/stack tracked by a different organization.

### Finding Description
`WebhooksController#verify_signature` computes the authenticating organization solely from the payload: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is used to fetch the correct `GitHubApp` (and thus the correct `webhook_secret`) via `Shipit.github(organization: repository_owner)`, and the HMAC signature is checked only against that secret.

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler with the raw, attacker-supplied `params` [3](#0-2) . Every handler resolves the target stacks not from `repository.owner.login` (the field that was cryptographically bound to the verifying secret) but from `repository.full_name`: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Nothing ties `repository.full_name` to `repository.owner.login`/`organization.login`. GitHub itself would never send such an inconsistent payload, but the signature check does not enforce that `repository.full_name` starts with the authenticated `repository_owner` — it only proves the payload was signed with *some* configured org's secret.

This breaks the binding: `organization authenticated by webhook_secret == organization whose repository is written by the handler`. An attacker who controls their own onboarded GitHub organization/App (knowing their own `webhook_secret`) can sign a payload with `repository.owner.login`/`organization.login` set to their own org, while setting `repository.full_name` to `victim-org/victim-repo`. `verify_signature` succeeds (their own secret matches), then `PushHandler`, `StatusHandler`, or `CheckSuiteHandler` acts on the victim's stacks: [5](#0-4) [6](#0-5) [7](#0-6) 

Concretely:
- `PushHandler#process` invokes `stack.sync_github(expected_head_sha:)` on the victim stack, forcing a resync toward an attacker-chosen `after` SHA/branch on a repository the attacker never had write access to.
- `StatusHandler#process` calls `commit.create_status_from_github!(params)` for any `Commit` matching `params.sha`, forging CI/CD status (`state`, `context`, `target_url`) on victim commits. Since continuous-deployment / merge-queue gating in Shipit relies on commit statuses being "green" to trigger automatic deploys/merges, this lets an attacker manufacture a passing status for a victim repository's commit.
- `CheckSuiteHandler#process` schedules check-run refreshes for victim commits, similarly influenced by attacker-controlled `head_sha`/`head_branch` matched only by `full_name`.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary described by the rules. By forging CI status (`StatusHandler`) for a victim's tracked commit, an attacker can make a stack appear deployable, potentially triggering an unauthorized automatic deploy through Shipit's continuous-deployment feature (a stack configured with `continuous_deployment: true` will deploy the latest commit once required statuses turn green). This satisfies the "unauthorized deploy" criterion under High/Critical impact. It also allows cross-repository state corruption (forcing `sync_github` on unrelated repositories), and reliance on organization boundaries for multi-tenant Shipit installations is defeated.

### Likelihood Explanation
This requires: (1) the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration — see `docs/setup.md`), and (2) the attacker administers at least one onboarded organization's GitHub App, meaning they can read/rotate that org's own `webhook_secret` and send webhooks to Shipit's public `/webhooks` endpoint. Both are attacker-controlled, unprivileged with respect to the *victim* organization — the attacker never needs credentials for the victim org, a Shipit session, or an `ApiClient` token. This matches the "unprivileged-attacker" framing of the rules. Likelihood is moderate: it depends on a multi-org deployment and on the attacker being a legitimate (if malicious) tenant of that Shipit instance, but no interaction with the victim organization is required.

### Recommendation
Bind the field used to select the verifying secret to the field used to resolve the target repository. Concretely:
- In `WebhooksController#verify_signature`, after verifying the HMAC, also assert that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch.
- Alternatively, change `Handler#repository_name` to derive the repository strictly from `repository.owner.login` + `repository.name` rather than the independently-supplied `repository.full_name`, so the same payload field that authorized the request is the one that determines what gets mutated.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `attacker-org` and `victim-org`, each with its own GitHub App / `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As the (legitimate but malicious) admin of `attacker-org`, craft a `status` webhook payload:
```json
{
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Sign the raw body with `attacker-org`'s own `webhook_secret` and send it to `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully using the attacker's own secret.
5. `StatusHandler#process` finds the `Commit` by `sha` (belonging to `victim-org/victim-repo`) and calls `create_status_from_github!`, forging a passing CI status. If `victim-org/victim-repo`'s stack has continuous deployment enabled and this was the last required status, an unauthorized deploy can be triggered.
