Webhook signature verification keys off `repository.owner.login` while every handler acts on the independent `repository.full_name` field, allowing cross-organization webhook forgery in multi-tenant Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is a valid analog of the report's root cause: a value that determines *which trust boundary validated the request* (the GitHub App/secret selected via `repository.owner.login`) is not the same value that is later *acted upon* (`repository.full_name`, used to resolve the `Repository`/`Stack`). Both fields are attacker-controlled, independent siblings inside the same JSON body, so a party who legitimately controls one organization's webhook secret in a multi-org Shipit instance can forge webhooks that make Shipit act on a different organization's repository.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate the HMAC signature from a field taken out of the still-unverified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a value taken directly from the attacker-supplied body, before the signature is checked. It is used only to pick which configured GitHub App's `webhook_secret` verifies the payload: [3](#0-2) 

In the documented multi-organization configuration (`docs/setup.md`, "Using Multiple Github Applications"), each org has its own `webhook_secret`, and `Shipit.github(organization:)` looks the config up by that organization key: [4](#0-3) 

Once the signature is verified (using the secret matching whatever organization the *attacker chose* to put in `repository.owner.login`), every handler resolves the target `Repository`/`Stack` from a **different, sibling field**: `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because HMAC covers the raw JSON body as a whole, and `owner.login`/`full_name` are independent fields inside that body, an attacker who legitimately controls a webhook secret for **any one** organization configured on the shared Shipit instance can craft a payload where:
- `repository.owner.login` = "attacker-org" (used only to pick the verifying secret)
- `repository.full_name` = "victim-org/victim-repo" (used to find the `Repository`/`Stack` acted upon)

sign it with the attacker-org's own valid webhook secret, and `verify_signature` will succeed because it fetches and checks against exactly the secret the attacker used. The handlers then act on the victim's repository/stack, having authenticated nothing about that victim organization at all.

Concrete impacts by handler, all reachable via the same forged payload:
- `PushHandler` enqueues `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`: [7](#0-6) 
- `StatusHandler` creates a commit status on a victim commit: [8](#0-7) 
- `CheckSuiteHandler` schedules check-run refreshes on a victim stack's commits: [9](#0-8) 

This is the exact bug class from the report: a field that is validated/authenticated (`repository.owner.login` → selects the verifying key) is different from the field that is actually acted upon (`repository.full_name` → selects the mutated resource), and the mismatch is never checked.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. An attacker who is an authorized user of *one* organization's GitHub App installation on a shared/multi-tenant Shipit instance can forge webhook events that queue sync jobs, write commit statuses, and trigger check-run refresh scheduling against a *different* organization's repositories/stacks that they have no legitimate relationship to — an unauthenticated cross-repository write from the perspective of the targeted organization. This matches the High-severity criterion "escalation into authorization... unauthorized... deploy" territory for status/sync manipulation of another org's stacks (e.g., `create_status_from_github!` can affect deployability gating, and `sync_github` can alter the commit history Shipit believes exists for a stack that could later gate/trigger deploys).

### Likelihood Explanation
Exploitability requires the Shipit instance to run in the documented multi-organization mode (`docs/setup.md`, "Using Multiple Github Applications") with attacker legitimate access to at least one configured organization's webhook secret (e.g., attacker is an admin of one org's installed GitHub App, or that org's `webhook_secret` has otherwise leaked) — this does not require compromising the target/victim organization at all, only one, arbitrary, unrelated org sharing the same Shipit instance. This is a realistic scenario for any Shipit-as-a-service or shared-instance deployment onboarding multiple orgs, which the engine explicitly documents and supports.

### Recommendation
Bind the field used to select/verify the signing secret to the same field used for resource resolution. Concretely: after selecting `github_app` via `repository_owner`, cross-check that `repository.full_name`'s owner segment equals the `repository_owner` that was actually used to validate the signature (or, better, verify the signature using every configured secret whose owner matches `repository.full_name`'s owner component rather than an independent `owner.login`/`organization.login` field), and reject the webhook if they diverge.

### Proof of Concept
Given a multi-org config with orgs `attacker-org` (secret `S_A`, which the attacker legitimately possesses) and `victim-org` (secret `S_V`, unknown to attacker), and a stack existing for `victim-org/victim-repo`:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>

body = {
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },   // used only to pick verifying secret S_A
    "full_name": "victim-org/victim-repo"   // used by Handler#stacks / #repository_name
  }
}
```

`WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates the HMAC against `S_A` — which the attacker used, so it passes. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, despite the request never being authenticated by `victim-org`'s secret.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
