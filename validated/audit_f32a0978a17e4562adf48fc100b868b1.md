### Title
Accrual panics on `i128` overflow before the borrow-index cap can engage, permanently freezing a large high-utilization market - (File: common/src/rates/scaling.rs)

### Summary
The analog of "library math that silently relied on wrap-around now reverts on overflow" is the RAY-scaled valuation in `accrue_step`. `scaled_to_original` multiplies scaled shares by the index via `Ray::mul`, which panics with `GenericError::MathOverflow` when the RAY value exceeds `i128::MAX`. The protocol has an index cap (`MAX_BORROW_INDEX_RAY = 10^36`) that is supposed to stop runaway index growth, but the cap is applied in `update_borrow_index` *after* interest accrues, while `scaled_to_original(env, borrowed, borrow_index)` runs *before* the cap check on the *old* book state. Once `borrowed * borrow_index` overflows `i128`, every entrypoint panics during accrual, so the cap never gets a chance to engage and the market freezes permanently.

### Finding Description
`contracts/pool/src/interest.rs::global_sync` → `accrue_chunk` calls `common/src/rates/simulate.rs::accrue_step`, whose first statement is `scaled_to_original(env, borrowed, borrow_index)` (`common/src/rates/simulate.rs:60`). `scaled_to_original` is `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`), and `Ray::mul` goes through `mul_div_half_up`, which panics with `MathOverflow` when the product does not fit `i128` (`common/src/math/fp_core.rs`, docs `formulas.md:22-24`). `update_borrow_index` caps the index only on the value it returns (`common/src/rates/index.rs:13-19`), so it cannot prevent the panic that occurs while *reading* the already-too-large product.

The repo's own stress test demonstrates the cliff: with ~1 billion whole tokens supplied on an 18-decimal market at ~98% utilization on the steep XLM rate curve, `borrow_index` grows past ~170x in a few years, `borrowed * borrow_index` exceeds `i128::MAX` (the value ceiling is ~170e36 raw RAY), and `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — "the index cap did not engage before the value overflow" (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-360`).

### Impact Explanation
Permanent freezing of funds: every mutating verb accrues first, so once the book crosses the ceiling no supplier can withdraw, no borrower can repay, and no liquidator can liquidate on that market. All supplied principal and accrued yield on the book are locked forever, and liquidatable bad debt can never be cleaned, pushing the book toward insolvency as debt continues to be recorded. This is the same failure mode as the reference report — a numeric ceiling the original design assumed was unreachable (or handled by a cap) instead traps every downstream call.

### Likelihood Explanation
Reachable by an unprivileged address through `supply`, `borrow`, and `update_indexes`, but it requires whale-scale capital (on the order of 1e9 whole tokens, i.e. `1e36` raw units near the ceiling of `1.7e38`), a steep admin-configured rate curve, and years of unattended accrual at high utilization. `lift_caps` shows supply caps must be near `max_cap_for_decimals`, so it is gated by governance cap configuration rather than blocked outright. This matches a Medium severity: a real, permanent freeze that needs extraordinary market conditions rather than a routine deposit.

### Recommendation
Cap or saturate before the overflowing multiply. Concretely: (a) clamp `borrow_index` in `update_borrow_index` to `min(MAX_BORROW_INDEX_RAY, i128::MAX / max(borrowed, 1))` so `borrowed * borrow_index` can never overflow, making the index cap the binding constraint as intended; or (b) make `scaled_to_original` (or a dedicated accrual variant) saturate via `mul_div_floor_saturating` so accrual completes and stops growing debt instead of trapping every entrypoint. The supply-side path already uses the saturating variant in `update_supply_index`/`protocol_fee_shares` (`common/src/rates/index.rs:41,95`); the borrow side lacks the equivalent guard.

### Proof of Concept
Mirrors `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`:

1. On a hub, list an 18-decimal asset `BIG18` with the steep XLM-style curve (`max_borrow_rate = 1.75 * RAY`, `optimal_utilization = 0.75 * RAY`) and raise supply/borrow caps via `edit_asset_in_spoke_caps` to `max_cap_for_decimals(18)`.
2. Attacker (or any whale) calls controller `supply` of `1e9 * 10^18` units of `BIG18`; a second account supplies collateral in another market and calls `borrow` for ~98% of the book.
3. Advance ledger time in ~1-year steps, calling `update_indexes` each step. After a few years `borrow_index` exceeds ~170x while remaining below `MAX_BORROW_INDEX_RAY`.
4. The next `update_indexes` call reverts with `GenericError::MathOverflow` inside `accrue_step → scaled_to_original` because `borrowed * borrow_index > i128::MAX`.
5. `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, and `flash_*` on that market all invoke `global_sync` first and revert identically. The market — including all supplier principal — is permanently frozen, and the index cap designed to bound growth is unreachable.

Caveat: I could not re-verify within this session whether `docs/reference/formulas.md`/`threat-model.md` explicitly bless this ceiling as an accepted domain bound (the test references a bound in `formulas.md`). If the freeze ordering is documented as intended behavior, this finding may be downgraded; the code and test as written treat the cap-not-engaging outcome as a demonstrated cliff rather than a designed stop.
