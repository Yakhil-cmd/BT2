### Title
Unicode bidi/format-control characters are not stripped from AA-issuer-controlled asset metadata `name`, enabling display spoofing of asset tickers in the wallet - (File: wallet.js)

### Summary
The Thunderbird CVE stripped RTLO/bidi-override Unicode characters from filenames because such characters let an attacker make an executable *display* as a document. `ocore` has an analogous "controlled string is displayed verbatim to the user without stripping bidirectional-control characters" pattern in the asset-metadata / asset-naming path: the `name` (and `suffix`) fields that an asset registry publishes via a `data` message are stored and shown as-is in the wallet UI when a user picks an asset to send or reads their balance.

### Finding Description
Any address can publish asset metadata by posting a `data`-app message referencing an `asset` and a `name`/`suffix`/`decimals` payload. Validation of `data` messages in `validation.js` only performs generic object well-formedness checks (`isObjectWellFormed`, which rejects lone surrogates and null bytes) [1](#0-0)  — it does **not** reject Unicode bidirectional-control characters (U+202A–U+202E, U+2066–U+2069) or other formatting/invisible characters. The registry client picks this payload up in `fetchAssetMetadata` and writes `payload.name` straight into `asset_metadata.name` with only a `!payload.name` (non-empty) and a decimals-type check — no character filtering: [2](#0-1) . The stored/derived name is then combined with a `suffix` and handed to the wallet UI for display (asset picker, balances) in `readAssetMetadata`: [3](#0-2) .

Because a RIGHT-TO-LEFT OVERRIDE or similar bidi-control character embedded in `name`/`suffix` is a perfectly well-formed, non-null-byte string, it passes every check in the pipeline (`isObjectWellFormed`, the `!payload.name` check, `UNIQUE(name, registry_address)` in `asset_metadata`) and is rendered by wallet clients. This is exactly the same bug class as CVE-2023-3417: a control character causes the true content (the actual asset a user is selecting) to be rendered as something else (e.g., visually indistinguishable from GBYTE or a well‑known stablecoin ticker), independent of the registry-address/suffix disambiguation mechanism that only helps when a user actually inspects the registry field.

### Impact Explanation
An unprivileged asset issuer/registry publishes metadata for a scam or worthless asset whose displayed `name`/`suffix` is engineered with bidi-override characters to visually match (or hide the divergence from) a well-known, valuable asset's ticker. A user selecting "the asset that looks right" in the wallet's asset picker can be tricked into sending funds denominated in, or accepting, the wrong asset — resulting in fund loss/misdirected payment (unauthorized spending from the victim's perspective, since the transaction is technically valid but based on a spoofed on-screen representation). This maps to the "asset issuance" and "wallet message handling" reachable surfaces named in the rules.

### Likelihood Explanation
Medium. No special privilege is needed — anyone can be an "asset registry" for their own issued asset and publish `data` metadata; the only precondition is that a wallet/user actually loads and trusts the free-form displayed name field without also comparing the underlying `asset` unit hash. The core disambiguation fields (`registry_address`, `suffix`) mitigate but do not eliminate the risk, since most users judge assets primarily by the rendered ticker text, not by comparing base64 registry addresses.

### Recommendation
Sanitize/normalize the `name` and `suffix` fields (and any other strings destined for unescaped UI display, e.g., chat "text", prosaic/arbiter contract `title`) by stripping or rejecting Unicode bidirectional-control and other invisible/format characters (U+200B–U+200F, U+202A–U+202E, U+2066–U+2069, etc.) at validation time, in addition to the existing lone-surrogate/null-byte checks in `isObjectWellFormed`, and/or restrict `name`/`suffix` to a safe character whitelist (alphanumeric plus a small punctuation set) given they are already length-capped to 20 characters.

### Proof of Concept
1. Attacker issues a new asset `X` and becomes its own metadata registry.
2. Attacker composes and sends a `data` message with `payload = { asset: X, name: "GBYTE\u202Etinu", decimals: 9 }` (embedding U+202E RIGHT-TO-LEFT OVERRIDE so the tail of the string renders reversed, masking or spoofing intent) referencing itself as `registry_address`.
3. Validation accepts the unit: `isObjectWellFormed` passes (well-formed, no null bytes) [1](#0-0) ; the `data` app has no structural/content restriction on arbitrary keys/values beyond the generic message checks.
4. A victim wallet calls `fetchAssetMetadata`, stores `payload.name` verbatim into `asset_metadata.name` [4](#0-3) , and later renders it via `readAssetMetadata` in the asset picker [5](#0-4) , showing a visually deceptive ticker.
5. Victim selects/sends to what appears to be a trusted asset but is actually attacker's asset `X`, resulting in loss/misdirection of funds.

Note: I could not fully verify end-to-end how every downstream wallet-UI client (outside `ocore`, e.g. GUI wallets) renders `name`/`suffix` strings, since that code lives in separate front-end repos not included in this index; the analysis is based on what `ocore` validates and stores, which is the reachable, in-scope portion of this bug class.

function isObjectWellFormed(obj) {
	if (typeof obj !== 'object' || obj === null)
		return typeof obj === 'string' ? obj.isWellFormed() && obj.indexOf('\0') === -1 : true;

	if (Array.isArray(obj)) {
		// for-loop is faster than .every
		for (let i = 0; i < obj.length; i++) {
			if (!isObjectWellFormed(obj[i])) return false;
		}
		return true;
	}

	for (const key in obj) {
		if (Object.hasOwn(obj, key)) {
			if (!key.isWellFormed() || key.indexOf('\0') >= 0) return false;
			if (!isObjectWellFormed(obj[key])) return false;
		}
	}

	return true;
}
