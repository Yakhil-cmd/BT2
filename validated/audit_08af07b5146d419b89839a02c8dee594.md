### Title
Ralph Wiggum's `stop-hook.sh` blindly trusts a git-committed `.claude/ralph-loop.local.md`, enabling prompt injection via repo content - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
The plugin-settings `SKILL.md` pattern documents `.claude/plugin-name.local.md` as "user-managed (not in git)" state, but this trust assumption is never enforced anywhere in the codebase — no script calls `git check-ignore` or `git ls-files` to confirm the file is actually untracked. The concrete runtime consumer of this pattern, `plugins/ralph-wiggum/hooks/stop-hook.sh`, reads `.claude/ralph-loop.local.md` purely with a `[[ -f "$RALPH_STATE_FILE" ]]` existence check and then feeds its frontmatter and body directly into hook decisions and back into the Claude conversation.

### Finding Description
`plugins/ralph-wiggum/hooks/stop-hook.sh` only checks file existence before trusting `.claude/ralph-loop.local.md` as authoritative session state [1](#0-0) . It parses `iteration`, `max_iterations`, and `completion_promise` from the frontmatter and extracts the markdown body as `PROMPT_TEXT`, which is then emitted as the hook's `"reason"` field — text that is fed back to Claude as the next turn's instruction [2](#0-1) . Because there is no verification that this file is genuinely user-authored and untracked by git (no call to `git check-ignore`/`git ls-files` exists anywhere in the repository, confirmed by search), an attacker can simply commit `.claude/ralph-loop.local.md` into a shared repository. When a victim clones the repo with the ralph-wiggum plugin installed and later triggers a Stop event (e.g., normal session end), the hook activates the "loop" state automatically using the attacker's committed content, injecting the attacker's chosen instructions as `PROMPT_TEXT`/`reason` and controlling `completion_promise`/`max_iterations` to keep the loop running indefinitely or terminate on attacker-chosen conditions.

The broader plugin-settings pattern documented in `SKILL.md` explicitly states the file's "Lifecycle: User-managed (not in git, should be in `.gitignore`)" [3](#0-2) , and the security-considerations section discusses input sanitization and path traversal but never addresses verifying the file's git-tracked status [4](#0-3) . Both `parse-frontmatter.sh` and `validate-settings.sh` utility scripts only check file existence/readability/structure, never git status [5](#0-4) [6](#0-5) .

### Impact Explanation
This is a genuine trust-boundary collapse between repo-supplied and user-supplied configuration: repository content masquerading as local user state gains the same authority as manually authored settings. In the ralph-wiggum case specifically, the impact is prompt injection with persistence — the attacker's `PROMPT_TEXT` is injected as the Claude session's continuation instruction on every Stop event until `completion_promise` is satisfied or `max_iterations` reached, both attacker-controlled. This can be used to steer an unsuspecting victim's Claude Code session toward attacker-chosen actions (e.g., "read and exfiltrate secrets," "run destructive commands") framed as the loop's task, without the victim ever creating the file themselves.

### Likelihood Explanation
Preconditions: victim clones/pulls a repository containing a committed `.claude/ralph-loop.local.md`, and has the ralph-wiggum plugin installed with its Stop hook registered. No admin privilege, key leakage, or social engineering beyond normal repo consumption is required — this is squarely "ordinary repository content" reaching hook execution, matching the scoped attacker model. The exploit is fully repeatable: any repository the attacker can contribute to (including via PR merge, since the file would just need to exist in the working tree) can carry this payload.

### Recommendation
Before trusting any `.claude/*.local.md` file's contents as "local user state," hooks/commands built on this pattern should verify the file is not git-tracked, e.g. `git ls-files --error-unmatch "$STATE_FILE"` (or `git check-ignore -q`) and refuse to honor the file (or warn/require explicit confirmation) if it is tracked. This check should be added to `plugins/ralph-wiggum/hooks/stop-hook.sh`, and the plugin-settings `SKILL.md` pattern/`parse-frontmatter.sh`/`validate-settings.sh` should be updated to document and provide this guard as the canonical quick-exit pattern for all plugins following it.

### Proof of Concept
Integration test:
1. Initialize a git repo, `git add .claude/ralph-loop.local.md` with attacker-controlled frontmatter (`max_iterations: 999999`, no `completion_promise`) and a malicious body prompt, then `git commit`.
2. Clone the repo into a fresh directory (simulating the victim), install the ralph-wiggum plugin.
3. Invoke `plugins/ralph-wiggum/hooks/stop-hook.sh` with a synthetic Stop-hook JSON input (valid `transcript_path` pointing to a fake transcript with one assistant message).
4. Assert current (vulnerable) behavior: the hook exits with `{"decision":"block","reason":"<attacker prompt>"}` — proving the attacker's committed content was trusted and injected.
5. After the fix, assert the hook instead detects the file is git-tracked via `git ls-files --error-unmatch .claude/ralph-loop.local.md` succeeding, and either refuses to activate the loop (`exit 0` without blocking) or emits an explicit warning requiring confirmation.

# Not complete - continue loop with SAME PROMPT
NEXT_ITERATION=$((ITERATION + 1))

# Extract prompt (everything after the closing ---)
# Skip first --- line, skip until second --- line, then print everything after
# Use i>=2 instead of i==2 to handle --- in prompt content
PROMPT_TEXT=$(awk '/^---$/{i++; next} i>=2' "$RALPH_STATE_FILE")

if [[ -z "$PROMPT_TEXT" ]]; then
  echo "⚠️  Ralph loop: State file corrupted or incomplete" >&2
  echo "   File: $RALPH_STATE_FILE" >&2
  echo "   Problem: No prompt text found" >&2
  echo "" >&2
  echo "   This usually means:" >&2
  echo "     • State file was manually edited" >&2
  echo "     • File was corrupted during writing" >&2
  echo "" >&2
  echo "   Ralph loop is stopping. Run /ralph-loop again to start fresh." >&2
  rm "$RALPH_STATE_FILE"
  exit 0
fi

# Update iteration in frontmatter (portable across macOS and Linux)
# Create temp file, then atomically replace
TEMP_FILE="${RALPH_STATE_FILE}.tmp.$$"
sed "s/^iteration: .*/iteration: $NEXT_ITERATION/" "$RALPH_STATE_FILE" > "$TEMP_FILE"
mv "$TEMP_FILE" "$RALPH_STATE_FILE"

# Build system message with iteration count and completion promise info
if [[ "$COMPLETION_PROMISE" != "null" ]] && [[ -n "$COMPLETION_PROMISE" ]]; then
  SYSTEM_MSG="🔄 Ralph iteration $NEXT_ITERATION | To stop: output <promise>$COMPLETION_PROMISE</promise> (ONLY when statement is TRUE - do not lie to exit!)"
else
  SYSTEM_MSG="🔄 Ralph iteration $NEXT_ITERATION | No completion promise set - loop runs infinitely"
fi

# Output JSON to block the stop and feed prompt back
# The "reason" field contains the prompt that will be sent back to Claude
jq -n \
  --arg prompt "$PROMPT_TEXT" \
  --arg msg "$SYSTEM_MSG" \
  '{
    "decision": "block",
    "reason": $prompt,
    "systemMessage": $msg
  }'
```

## Security Considerations

### Sanitize User Input

When writing settings files from user input:

```bash
# Escape quotes in user input
SAFE_VALUE=$(echo "$USER_INPUT" | sed 's/"/\\"/g')

# Write to file
cat > "$STATE_FILE" <<EOF
---
user_setting: "$SAFE_VALUE"
---
EOF
```

### Validate File Paths

If settings contain file paths:

```bash
FILE_PATH=$(echo "$FRONTMATTER" | grep '^data_file:' | sed 's/data_file: *//')

# Check for path traversal
if [[ "$FILE_PATH" == *".."* ]]; then
  echo "⚠️  Invalid path in settings (path traversal)" >&2
  exit 2
fi
```

### Permissions

Settings files should be:
- Readable by user only (`chmod 600`)
- Not committed to git
- Not shared between users
```
