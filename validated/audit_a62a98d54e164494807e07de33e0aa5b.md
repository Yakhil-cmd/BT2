Wall-clock TTL on `stop_hook_fire_count` allows the Stop-hook loop-limiting security control to be bypassed after an idle/paused gap - ([File: plugins/security-guidance/hooks/diffstate.py])

### Summary
The Taiko report describes a class of bug where a security-relevant counter/delay is checked against **wall-clock elapsed time**, and any gap in activity (a `pause()`/`unpause()`) is not distinguished from active-processing time, silently resetting or shrinking the intended protection window and letting an unprivileged actor bypass a delay-based safeguard. The `security-guidance` plugin's Stop-hook loop cap (`MAX_STOP_HOOK_FIRINGS`) is protected by an almost identical pattern: a wall-clock TTL (`STOP_LOOP_STATE_TTL_SEC`) that resets the `stop_hook_fire_count` used to cap `asyncRewake` loop iterations, regardless of whether time passed due to genuine idling or an adversarially-induced gap.

### Finding Description
`consume_stop_state()` in [1](#0-0)  computes `expired = (now - fire_ts) > STOP_LOOP_STATE_TTL_SEC` and, if expired, resets `fire_count` to `0` before returning it to the caller. The TTL constant and its justification are defined at [2](#0-1) , which explicitly states the 120-second window is sized to "comfortably contain MAX_STOP_HOOK_FIRINGS" for the normal `asyncRewake` cycle (vuln → exit(2) → fix → Stop again, "~30-60s/cycle").

This mirrors the Taiko bug's root cause exactly: a security counter/delay that is supposed to bound a specific class of repeated action (there: `invocationDelay` bounding who can call `processMessage()`; here: `MAX_STOP_HOOK_FIRINGS` bounding how many times the Stop hook can fire in one `asyncRewake` loop to prevent infinite-loop abuse) is gated purely on `time.time()` deltas without any distinction between "genuine session activity" and "a gap caused by pausing/stalling the session." Just as pausing the Taiko protocol let a non-preferred executor's clock silently "catch up" past the preferred executor's window, here anything that stalls Stop-hook firing for slightly over 120 seconds (a slow/hung command, a long-running tool call, an intentionally delayed step inserted by an adversarial prompt/skill, network stalls, etc.) causes the enforcement counter to silently reset to `0`, giving the loop-abuse protection a fresh budget instead of continuing to enforce the original cap.

### Impact Explanation
`MAX_STOP_HOOK_FIRINGS` exists specifically to stop an `asyncRewake` loop (a Stop hook that keeps blocking with `exit(2)` to force additional turns) from firing unboundedly, which is a resource-abuse/DoS and potential logic-bypass vector referenced directly in the code comments. If an attacker (via prompt injection, a compromised skill, or a slow/blocking sub-tool) can reliably introduce >120 seconds between consecutive Stop-hook firings, they can indefinitely reset the fire-count guardrail and keep the loop alive well past its intended cap, defeating the purpose of the security control (analogous to defeating the preferred-executor exclusivity window in the reference bug). This is a genuine trust-boundary weakening in a hook-abuse-prevention mechanism, though the severity is bounded relative to the on-chain finding (no direct fund loss; impact is unbounded loop/resource consumption and reduced efficacy of the anti-loop safeguard).

### Likelihood Explanation
Likelihood is moderate: triggering a >120s gap between Stop-hook firings is plausible in realistic conditions (slow tool calls, network stalls, deliberately slow commands orchestrated by a malicious prompt/skill) without requiring any special privilege — exactly the "unprivileged-user" trust boundary this analog task requires. It does not require a malicious node/peer/operator, is not mocked-only, and is reachable through normal hook/tool-authorization code paths already present in the shipped plugin.

### Recommendation
Do not reset `stop_hook_fire_count` purely based on elapsed wall-clock time. Instead, tie the TTL/reset condition to genuine session-lifecycle events (e.g., a new `UserPromptSubmit`/turn boundary, explicit `/clear`, or a monotonic count of intervening turns) rather than `time.time()` deltas that can be inflated by stalls, similar to the report's recommendation to track "how much time has already been spent" independent of pause-induced gaps. At minimum, cap how much elapsed time is treated as "expiring" the counter, or increment a turn-based counter alongside the timestamp so both must agree before resetting.

### Proof of Concept
1. A Stop hook enters the `asyncRewake` loop pattern (blocks with `exit(2)`, expecting a fix, then fires Stop again), incrementing `stop_hook_fire_count`/`stop_hook_fire_count_ts` toward `MAX_STOP_HOOK_FIRINGS`.
2. Before the cap is reached, an attacker-influenced step (e.g., a slow tool call, network stall, or deliberately delayed sub-agent action) causes more than `STOP_LOOP_STATE_TTL_SEC` (120s) to elapse before the next Stop-hook firing.
3. On the next call to `consume_stop_state()` [3](#0-2) , `expired` evaluates `True` and `fire_count` is reset to `0`, regardless of how many times the loop had already fired.
4. The loop-limiting check at [4](#0-3)  now sees `fire_count = 0`, allowing `MAX_STOP_HOOK_FIRINGS` more iterations than the control was designed to permit — the anti-loop safeguard is effectively bypassed by simply waiting out the TTL window.

def consume_stop_state(session_id):
    """Atomically snapshot all state the Stop hook needs and clear touched_paths.

    The Stop hook is asyncRewake — it runs in the background after Claude's
    turn ends. The user can submit a new prompt before this hook finishes its
    initial state read. Telemetry showed a meaningful share of would-be reviews lost when
    the next turn's UPS wiped touched_paths before Stop read it.

    Single locked read-then-clear closes that window: PostToolUse appends
    after this clear go into the next snapshot; UPS overwrites of baseline_sha
    after this snapshot are invisible to this Stop fire.
    """
    import time as _time
    now = _time.time()

    def _snap(state):
        fire_ts = state.get("stop_hook_fire_count_ts", 0)
        expired = (now - fire_ts) > STOP_LOOP_STATE_TTL_SEC
        findings_ts = state.get("previous_findings_ts", fire_ts)
        findings_expired = (now - findings_ts) > PREVIOUS_FINDINGS_TTL_SEC
        snap = {
            "touched_paths": list(state.get("touched_paths", [])),
            "baseline_sha": state.get("baseline_sha"),
            "head_at_capture": state.get("head_at_capture"),
            "untracked_at_baseline": (
                dict(state["untracked_at_baseline"])
                if isinstance(state.get("untracked_at_baseline"), dict) else {}
            ),
            "fire_count": 0 if expired else state.get("stop_hook_fire_count", 0),
            "fire_count_expired": expired and state.get("stop_hook_fire_count", 0) > 0,
            "previous_findings": [] if findings_expired else list(state.get("previous_findings", [])),
        }
        state["touched_paths"] = []
        return snap

    return with_locked_state(session_id, _snap) or {
        "touched_paths": [], "baseline_sha": None, "head_at_capture": None,
        "untracked_at_baseline": {},
        "fire_count": 0, "fire_count_expired": False, "previous_findings": [],
    }
