### Title
Unprivileged borrowers can freeze withdrawals by pushing utilization over the cap - (File: `contracts/pool/src/ops/withdraw.rs`)

### Summary
A borrower can borrow up to `max_utilization`; subsequent interest accrual raises utilization above the cap, after which every ordinary withdrawal of that market reverts until debt is repaid or liquidated. [1](#0-0) 

### Finding Description
`controller.borrow` reaches `pool::ops::borrow::mint_debt`, which accepts a borrow while post-borrow utilization is less than or equal to `params.max_utilization`. [2](#0-1) 

Utilization is calculated as accrued debt divided by accrued supplied value, with debt rounded up and supply rounded down. [3](#0-2) 

Each withdrawal accrues the market, burns supply shares, and then calls `require_utilization_below_max` before transferring assets. [4](#0-3) [5](#0-4) 

Because utilization is below 100% for a normally configured capped market, accruing equal aggregate interest to debt and supply claims moves `debt / supply` toward 100%; consequently, a borrow taken near the cap crosses it as time passes. [6](#0-5) 

The attacker can trigger or accelerate this condition through the permissionless `controller.update_indexes(caller, assets)` path. [7](#0-6) 

### Impact Explanation
Once utilization exceeds `max_utilization`, all non-liquidation withdrawals from that market revert with `CollateralError::UtilizationAboveMax`, including withdrawals small enough to be covered by available cash. [5](#0-4) [8](#0-7) 

This temporarily freezes supplier funds for as long as the borrower maintains a solvent position and refuses to repay; repayment or a successful liquidation is required to restore withdrawals. [9](#0-8) 

### Likelihood Explanation
An unprivileged account can reach this state by supplying collateral in one asset and borrowing another asset up to its utilization cap; no privileged call, leaked key, malformed market, or third-party oracle manipulation is required. [10](#0-9) [2](#0-1) 

The attack scales with available liquidity and collateral, and its ongoing cost is ordinary borrow interest; a sufficiently collateralized borrower can maintain the freeze without becoming liquidatable. [1](#0-0) 

### Recommendation
Do not apply the post-state maximum-utilization invariant to ordinary withdrawals; retain `require_reserves` and `require_supply_for_debt`, and use an explicit withdrawal reserve or liquidity-buffer policy if the protocol needs to limit withdrawals independently. [5](#0-4) [11](#0-10) 

Alternatively, permit withdrawals while `utilization > max_utilization` when cash can cover the transfer, since blocking those exits converts a temporary high-utilization state into a denial of withdrawals rather than merely preventing utilization from worsening. [12](#0-11) 

### Proof of Concept
1. Create a market for asset `A` with `max_utilization < RAY`, a positive borrow rate, and supplier liquidity.
2. Attacker calls `controller.supply(caller, 0, spoke_id, [(collateral_key, collateral_amount)])`, receiving `account_id`.
3. Attacker calls `controller.borrow(caller, account_id, [(a_key, borrow_amount)], None)`, choosing `borrow_amount` so post-borrow utilization is immediately below `max_utilization`. [10](#0-9) 
4. After ledger time advances, attacker calls `controller.update_indexes(caller, [a_key])`; accrued debt raises utilization above `max_utilization`. [7](#0-6) 
5. A supplier calls `controller.withdraw(owner, victim_account_id, [(a_key, 1)], None)`.
6. `pool::ops::withdraw::accounting` loads and syncs the market, burns shares, calls `require_utilization_below_max`, and the transaction reverts with `UtilizationAboveMax`. [4](#0-3) [8](#0-7) 
7. Every subsequent ordinary withdrawal of `A` reverts while utilization remains above the cap; only debt repayment or liquidation restores exit liquidity.

```rust
pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
```

```rust
pub(crate) fn mint_debt(env: &Env, cache: &mut Cache, position: &mut Ray, amount: i128) {
    require_positive_amount(env, amount);
    cache.require_reserves(amount);
    guards::require_liquidation_buffer(env, cache, amount);

    let minted = cache.calculate_scaled_borrow(amount);

    assert_with_error!(
        env,
        minted.raw() > 0,
        GenericError::BorrowRoundsToZeroShares
    );

    *position = position.checked_add(env, minted);
    cache.mint_debt(minted);
    guards::require_utilization_below_max(env, cache);
}
```

```rust
fn gate_and_debit(env: &Env, cache: &mut Cache, net_transfer: i128, skip_utilization_check: bool) {
    cache.require_reserves(net_transfer);

    if !skip_utilization_check {
        guards::require_utilization_below_max(env, cache);
    }
    guards::require_supply_for_debt(env, cache);
    cache.debit_cash(net_transfer);
```

```rust
pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
```
