## Title
Webhook signature scoped to `repository.owner.login` while handlers act on `repository.full_name` allows cross-repository webhook forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate `X-Hub-Signature` using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` [1](#0-0) . Once the signature check passes, every downstream `Webhooks::Handlers` processor re-reads the acting repository from the independent `params.dig('repository', 'full_name')` field of the same JSON body (e.g. `ReopenedHandler#repository`) [2](#0-1) . These are two different fields of the attacker-controlled JSON payload, and only one of them (`repository.owner.login`) is used to pick the authenticating secret.

### Finding Description
Shipit supports multiple GitHub Apps, one per organization, via `Shipit.github(organization:)` [3](#0-2) ; each organization can have its own (optional) `webhook_secret`, as documented in `docs/setup.md` "Using Multiple Github Applications" and the example configs (`OrgOne`/`OrgTwo`, `somegithuborg`/`someothergithuborg`) [4](#0-3) . In `GitHubApp#verify_webhook_signature`, if no `webhook_secret` is configured for that organization, verification is a no-op: `return true unless webhook_secret` [5](#0-4) .

`WebhooksController#verify_signature` picks which organization's app/secret to check against using `repository_owner`, sourced from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [6](#0-5) . That value only gates *which secret is used to authenticate the sender*; it is never checked against the `repository.full_name` value that handlers use to identify *which repository/stack the payload should mutate*. Handlers such as `PullRequest::ReopenedHandler` resolve the target purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [2](#0-1) , and other handlers (push/status/check_suite/membership) follow the same "trust body fields for target resolution" pattern, only the signature step differentiates by owner.

Because a multi-org Shipit install can validly have one organization configured **without** a `webhook_secret` (this is documented as optional: "If you've set a webhook secret ... you should copy it here" [7](#0-6) , and both stock templates ship `webhook_secret:` blank/nil [8](#0-7) [9](#0-8) ), an unprivileged external party can:
1. Discover that organization `OrgWeak` (any org with no `webhook_secret`, including a throwaway org the attacker fully controls/owns) is one of the configured GitHub Apps.
2. POST directly to `/github/webhooks` (or wherever `WebhooksController` is mounted) with `repository.owner.login = "OrgWeak"` (so `verify_signature` trivially passes because `webhook_secret` is blank) but `repository.full_name = "OrgStrong/private-repo"` — a completely different, secret-protected organization's repository.
3. Because handlers key off `full_name`, not `owner.login`, the forged event is dispatched as if it legitimately originated from `OrgStrong`'s GitHub App: e.g. a forged `push` event enqueues `GithubSyncJob` for `OrgStrong/private-repo`'s stack [10](#0-9) , a forged `pull_request` `reopened` event de-archives/unarchives that stack and re-triggers provisioning [11](#0-10) , and forged `status`/`check_suite` events can flip CI status used to gate `MergeRequest` auto-merge decisions (`any_status_checks_failed?`, `all_status_checks_passed?`) [12](#0-11) .

This is the same class of bug as CVE-2022-30115: the field actually used to decide "is this trusted" (`repository.owner.login`, used for signature-secret selection) is not the same field that later code treats as authoritative for "what does this event apply to" (`repository.full_name`). Just as curl's HSTS cache matched on a normalized hostname while the request used a different (dotted) one, Shipit authenticates on `owner.login` while acting on `full_name`.

### Impact Explanation
This breaks the equality that should hold: `organization whose secret authenticated the request == organization that owns the repository the handler writes to`. An attacker who controls (or picks) any organization in the multi-org config that lacks a `webhook_secret` can forge webhook events attributed to a different, secret-protected repository, causing unauthorized state changes: forcing re-sync/re-provisioning of another org's stack, unarchiving stacks, injecting bogus commit/check-run statuses that feed into `MergeRequest` merge-gating logic, and creating/removing team memberships (`membership` event) — all without ever presenting a valid signature for the targeted organization. This maps to "escalation into `Shipit.github_teams` authorization" / unauthorized manipulation of deploy/merge state for a repository the attacker does not control, satisfying the High-severity bar.

### Likelihood Explanation
Requires: (a) the Shipit instance be configured with the multi-organization GitHub Apps schema, and (b) at least one configured organization having no `webhook_secret` set — both are supported, undiscouraged, documented configurations (the stock example configs ship with `webhook_secret:` blank). No credentials, tokens, or GitHub App private keys are needed; only knowledge of the target `full_name` and of one weakly-configured organization login, both of which are public GitHub information. This is a plausible, not merely theoretical, misconfiguration given the official docs and shipped templates default the secret to blank.

### Recommendation
After resolving `repository_owner` for secret selection, cross-check it against `repository.full_name`'s owner segment (and `organization.login` when present) and reject the request (422) if they diverge, before dispatching to handlers. Additionally, warn/refuse to boot when any configured GitHub App organization has no `webhook_secret` in a multi-org setup, since a single unauthenticated org effectively downgrades trust for the entire installation.

### Proof of Concept
Given a Shipit deployment configured with two organizations, `OrgWeak` (no `webhook_secret`) and `OrgStrong` (has `webhook_secret`), each installed on their own repos:

```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   # anything, unchecked because OrgWeak has no secret

{
  "repository": { "owner": { "login": "OrgWeak" }, "full_name": "OrgStrong/private-repo" },
  "after": "<attacker-chosen sha claimed to exist upstream>"
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgWeak")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [5](#0-4) . The `push` handler then dispatches based on `repository.full_name`, i.e. `OrgStrong/private-repo`, enqueuing a `GithubSyncJob` for that stack exactly as a legitimate `OrgStrong`-signed webhook would [10](#0-9) , even though the request was never authenticated by `OrgStrong`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
