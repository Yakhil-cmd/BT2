## Analysis Result

Mapping the authentik bug class (an unprivileged actor rebinding an identity-owning foreign key — `user`/`group` — on a source-connection record via an API that never checks the caller actually owns that identity, enabling account takeover) to ocore, the closest reachable analog is the **`new_shared_address` device-message handler**, which lets any paired correspondent (not just an actual member of the multisig definition) bind arbitrary `device_address` values to signing paths of other cosigners in a shared (multisig) address — without ever verifying that the sending device is entitled to claim ownership of those paths.

### Title
Unauthenticated rebinding of cosigner `device_address` in shared-address definitions leaks private payment chains and enables fund freezing - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` accepts a `{address, definition, signers}` payload from any paired device over the `new_shared_address` subject and persists the `signers` map (`signing_path -> {address, device_address}`) into `shared_address_signing_paths` without checking that the message's actual sender (`from_address`) is authorized to assert `device_address` values for signing paths belonging to *other* members of the multisig definition.

### Finding Description
The network entry point in `wallet.js` dispatches the `new_shared_address` message directly to the handler with no ownership check on the sender: [1](#0-0) 

`handleNewSharedAddress` only validates that the definition hashes to `body.address`, that each `signers[path].address` matches the corresponding `["address", ...]` leaf extracted from the definition, and that every definition address has a signer entry — it never checks that `from_address` (the actual sender of the device message) matches any `device_address` referenced in `body.signers`: [2](#0-1) 

`determineIfIncludesMeAndRewriteDeviceAddress` only guarantees that *my own* member address's device is rewritten to my own device — it does nothing to authenticate who is allowed to set the `device_address` for a peer's signing path: [3](#0-2) 

This is a known-incomplete area — the code itself carries a TODO acknowledging missing checks: [4](#0-3) 

Once persisted, `shared_address_signing_paths.device_address` is trusted downstream to route sensitive protocol traffic for that shared (multisig) address, including forwarding of private payment chains to "other members": [5](#0-4) 

and to build the list of cosigner devices returned to the UI/wallet code for requesting signatures: [6](#0-5) 

### Impact Explanation
By sending a crafted `new_shared_address` message that includes the victim's real member address (`address`) but substitutes the attacker's own `device_address` for that member's signing path, an attacker can hijack the routing entry that determines where that member's data/requests are sent for this shared address:
- Private payment chains (spend proofs/blinding data for indivisible/divisible private assets) that should be forwarded only to the legitimate cosigner's device are instead sent to the attacker's device via `forwardPrivateChainsToOtherMembersOfAddresses`. Possession of a full private chain in ocore's private-asset model is sufficient to reconstruct/replay a spend, which can enable double-spending or theft of the underlying private asset value.
- Since the legitimate cosigner's device is never contacted for cosignature requests once its `device_address` binding is overwritten, funds controlled by the shared address can become permanently unspendable (frozen), since the multisig definition still cryptographically requires that member's real signature, which the attacker cannot produce, and the true owner is not asked.

This mirrors the authentik bug class exactly: a foreign-key-like ownership binding (`device_address`/`user`) tied to another party's credential is mutable by an unauthorized actor through an ordinary protocol message, with no verification that the mutator is entitled to control that identity's binding.

### Likelihood Explanation
Any device that is a paired correspondent of the victim wallet (a low bar — pairing is done via a shared secret exchanged out of band, and correspondents can also be indirect via `is_indirect`) can send this crafted device message at any time, referencing any multisig shared-address definition the sender is aware of (e.g., ones it or the target device already knows about via `sendNewSharedAddress`/`sendSharedAddressToPeer` broadcasts). No special privilege beyond an existing pairing is required, and the vulnerable code path is a documented TODO ("check that my address is referenced in the definition"/no sender-authorization equivalent), indicating the check is genuinely absent, not merely obscured.

### Recommendation
In `handleNewSharedAddress`, verify that the sending device (`from_address`) is authorized to assert the `device_address` values in `body.signers` — specifically, only allow a device to set/overwrite its own `device_address` binding for signing paths where it is the actual member (i.e., accept `signers[path].device_address` only when it equals `from_address`, or when the local node already independently trusts that mapping for other members). Reject or ignore signer entries for paths not attributable to the message sender, and require independent confirmation (e.g., from the actual correspondent) before treating a new device as authoritative for an existing member's signing path in `shared_address_signing_paths`.

### Proof of Concept
1. Attacker device `D_attacker` pairs (or is already paired) with victim wallet `W`.
2. `W` knows about a shared (multisig) address `S` with definition `["and", [["address", V], ["address", "..."]]]` where member `V` is normally reachable via `D_victim`.
3. `D_attacker` sends `subject: "new_shared_address"` with `body = {address: S, definition: <same definition JSON>, signers: {"r.0": {address: V, device_address: D_attacker, member_signing_path: "r"}, ...}}`.
4. `wallet.js`'s handler forwards this straight to `walletDefinedByAddresses.handleNewSharedAddress(body, ...)` with no check that `from_address === D_attacker` is entitled to claim `V`'s device_address.
5. `handleNewSharedAddress` validates definition hash and address/path consistency (both satisfied, since `V`'s address is legitimately part of the definition) and calls `addNewSharedAddress`, which `INSERT OR IGNORE`s the row `(S, "r.0", V, ..., D_attacker)` into `shared_address_signing_paths`.
6. Subsequent calls to `forwardPrivateChainsToOtherMembersOfAddresses(chains, [S], ...)` now route private chain data intended for `V` to `D_attacker`, and any cosigner lookups via `readSharedAddressCosigners`/similar treat `D_attacker` as the reachable device for `V`'s signing key, freezing legitimate spend flows or leaking private payment data.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

// returns information about cosigner devices
function readSharedAddressCosigners(shared_address, handleCosigners){
	db.query(
		"SELECT DISTINCT shared_address_signing_paths.device_address, name, "+db.getUnixTimestamp("shared_addresses.creation_date")+" AS creation_ts \n\
		FROM shared_address_signing_paths \n\
		JOIN shared_addresses USING(shared_address) \n\
		LEFT JOIN correspondent_devices USING(device_address) \n\
		WHERE shared_address=? AND device_address!=?",
		[shared_address, device.getMyDeviceAddress()],
		function(rows){
			if (rows.length === 0)
				throw Error("no cosigners found for shared address "+shared_address);
			handleCosigners(rows);
		}
	);
}
