### Title
KLAY Permanently Locked in Service-Chain Bridge When Recipient Contract Lacks Payable Fallback — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` delivers bridged KLAY to the destination address via a bare low-level call. If `_to` is a contract without a payable fallback function, the call returns `ok = false`, the `require` reverts the entire transaction (including all nonce-state updates), and the nonce can never be settled. The user's KLAY deposited on the source chain is permanently locked in the bridge with no on-chain recovery path.

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` performs the following sequence:

1. Validates and records the nonce (`_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, `_updateHandleNonce`) — **state changes happen here**.
2. Emits `HandleValueTransfer`.
3. Attempts the KLAY transfer:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

If `_to` is a contract whose fallback reverts or is absent, `ok` is `false`. The `require` reverts the entire transaction, rolling back every state change made in step 1 — including the nonce record in `handleNoncesToBlockNums` and the vote state in `closedValueTransferVotes`. Because `_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0`, a nonce whose record is always reverted can never be cleared, and `lowerHandleNonce` stalls at that slot permanently. [2](#0-1) 

On the source chain, the user's KLAY was already deducted when `requestKLAYTransfer` (or the fallback) was called:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [3](#0-2) 

There is no withdrawal function, no skip-nonce function, and no wrapped-token fallback in the bridge contract. The KLAY is irrecoverably locked in the source-chain bridge.

The same low-level-call pattern also appears in `_payKLAYFeeAndRefundChange` for the fee receiver and the refund path:

```solidity
(bool ok, ) = feeReceiver.call.value(fee)("");
require(ok, "transfer fee failed");
...
(bool ok, ) = msg.sender.call.value(feeRefund)("");
require(ok, "refund fee failed");
``` [4](#0-3) 

If `feeReceiver` is a non-payable contract, every KLAY bridge request reverts, creating a complete DoS on the request side as well.

### Impact Explanation

- **Bridged KAIA loss**: Any KLAY deposited into the source-chain bridge for a request whose `_to` is a non-payable contract is permanently locked. The user receives nothing on the destination chain and cannot reclaim funds on the source chain.
- **Nonce stall**: `lowerHandleNonce` cannot advance past the stuck nonce, corrupting the bridge's accounting of which requests have been settled.
- **No recovery path**: The bridge contract exposes no owner-callable skip or withdrawal function.

### Likelihood Explanation

Developers building smart-contract wallets, multisigs, or protocol vaults on the service chain may bridge KLAY to their contract address. Solidity contracts do not accept KLAY by default; a `receive()` or `fallback() payable` function must be explicitly declared. The bridge emits no warning and performs no pre-flight check. This is the same developer-facing footgun identified in M-07.

### Recommendation

1. **Pre-flight check**: Before accepting the request on the source chain, or before executing the handle on the destination chain, verify `_to.code.length == 0` (EOA-only) or require the caller to explicitly opt in to contract delivery.
2. **Wrapped-token fallback**: If the bare KLAY call fails, wrap the value in WKLAY and transfer the ERC-20 token to `_to` instead (the direct analog of the M-07 mitigation).
3. **Skip/rescue function**: Add an owner-callable function that can mark a nonce as permanently failed and return the corresponding KLAY to a designated rescue address, preventing permanent lock-up.

### Proof of Concept

1. **Source chain**: User calls `requestKLAYTransfer(contractAddr, value, "0x")` where `contractAddr` is a deployed contract with no `receive()` or `payable fallback`. KLAY is deducted from the user and held in bridge A. `RequestValueTransfer` is emitted with nonce N.

2. **Destination chain**: Operators call `handleKLAYTransfer(..., contractAddr, value, N, ...)` on bridge B. Execution reaches line 98:
   ```solidity
   (bool ok, ) = contractAddr.call.value(value)("");
   // ok == false — contract has no payable fallback
   require(ok, "handleKLAYTransfer: transfer failed"); // REVERT
   ```
   All state changes (nonce record, vote state) are rolled back.

3. **Permanent lock**: Operators retry indefinitely; every attempt reverts. `handleNoncesToBlockNums[N]` remains 0. `_updateHandleNonce` stalls `lowerHandleNonce` at N. The user's KLAY on chain A is permanently locked in bridge A with no on-chain recovery. [5](#0-4) [6](#0-5)
