### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but event handlers act on the independent `repository.full_name` field, letting a tenant with a valid webhook secret for their own GitHub organization forge writes against a stack owned by a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) used to authenticate an incoming webhook based on `repository.owner.login` (falling back to `organization.login`), a plain, unverified field of the JSON body itself. [1](#0-0)  Once the signature check passes, every event handler determines which `Repository`/`Stack` to mutate using a *different* field of the same body, `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name` / `#stacks`. [2](#0-1)  Nothing ties `owner.login` to the owner segment of `full_name`; an attacker who legitimately controls one organization onboarded to a multi-tenant Shipit instance (and therefore knows that organization's own `webhook_secret`, configured via `GitHubApp`) can sign an arbitrary payload with their own valid secret while setting `repository.full_name` to point at a stack belonging to a completely different, victim organization.

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own `GitHubApp` instance holding an independent `webhook_secret`. [3](#0-2)  `GitHubApp#verify_webhook_signature` simply HMACs the raw body with whichever secret was selected. [4](#0-3) 

In `WebhooksController`, the secret is selected purely from body content:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and used as:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

After verification succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. [5](#0-4)  Every one of these inherits `stacks`/`repository_name` from `Handler`, which reads `payload.dig('repository', 'full_name')` — a field that was never inspected during signature verification:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`Repository.from_github_repo_name` does a direct DB lookup by owner/name parsed from that string, with no relation back to which organization's secret authenticated the request. [7](#0-6) 

This is structurally identical to the referenced oracle bug: two values that are supposed to be scaled/tied together (the value checked and the value used downstream) are actually independent fields, so the security check on one does not constrain the other. Here, the binding that should hold is:

`organization whose secret authenticated the request == organization that owns the repository being written to`

but the code only enforces: `repository.owner.login (unverified) → secret used for HMAC`, while the actual mutation target is `repository.full_name (unverified, independent)`. Both fields are supplied by the same untrusted JSON body and can be set independently by anyone who can produce a valid signature for *some* organization's secret.

### Impact Explanation
A tenant/attacker legitimately possessing the webhook secret for their own onboarded organization (`attacker-org`) can forge a `push`, `status`, or `check_suite` webhook whose `repository.full_name` names a stack under an unrelated `victim-org`. Handlers such as `PushHandler` will then call `stack.sync_github(expected_head_sha: params.after)` on the victim's stack using attacker-supplied `after`, [8](#0-7)  and `StatusHandler`/`CheckSuiteHandler` can inject arbitrary CI/check statuses onto victim commits — this can satisfy `ci.require`/`deploy` gating checks and cause continuous-delivery stacks to unlock or auto-deploy. This crosses the "cross-repository writes" / "unauthorized deploy" Critical-impact bar defined by the scan rules, because a credential scoped to one organization is used to mutate state belonging to a different organization's repository.

### Likelihood Explanation
This requires a genuinely multi-tenant Shipit deployment (multiple organizations configured, each with their own `GitHubApp`/`webhook_secret`) — a documented, supported configuration (`lib/shipit/github_app.rb`, `docs/setup.md`). [9](#0-8)  Any organization admin who legitimately owns the webhook secret for their own tenant (a routine, unprivileged credential with respect to other tenants) can exploit this without needing the victim's secret, GitHub App private key, or any Shipit session/API token — only the ability to craft and POST an HTTP request to the shared `/webhooks` endpoint.

### Recommendation
Verify the webhook signature using the same field that handlers rely on to resolve the target repository (`repository.full_name`), or, after selecting the app/secret from `repository_owner`, assert that `repository.full_name` (and `organization.login`, if present) is prefixed with that same verified owner before any handler executes. Reject the webhook if the two fields disagree.

### Proof of Concept
1. Shipit instance configured for at least two organizations, `attacker-org` and `victim-org`, each with independent `webhook_secret`s (multi-tenant setup as documented in `lib/shipit/github_app.rb`).
2. Attacker, who legitimately knows `attacker-org`'s `webhook_secret`, crafts:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs the body to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner => "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and the HMAC validates successfully. [10](#0-9) 
5. `PushHandler#process` resolves `stacks` via `payload.dig('repository','full_name') == "victim-org/victim-repo"`, finds the real victim `Stack`, and calls `stack.sync_github(expected_head_sha: params.after)` — mutating state owned by an organization the attacker never authenticated against. [8](#0-7) [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
