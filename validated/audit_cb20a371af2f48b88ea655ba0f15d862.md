### Title
Organization Authenticated by Webhook Signature Not Bound to Repository Written by Handlers - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The bug class from the external report — a field accepted by the settings-update path but never checked against the value actually used at execution time (`migration_token_allocation` accepted in `GlobalSettingsInput` but not applied in `Global::update_settings`, while `create_pool` later trusts the stale/incorrect stored value) — has a structural analog in Shipit's webhook ingestion pipeline: the organization identity that is cryptographically **verified** via the HMAC signature is not the same value that is used to determine **which repository/stack is written to**.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using `repository_owner`, computed purely from the untrusted JSON body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is used only to pick which org's `webhook_secret` to verify the HMAC against (`Shipit.github(organization: repository_owner)`), via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once the signature check passes, the raw `params` hash (the entire attacker-controlled body) is dispatched unchanged to the event handler: [4](#0-3) 

Handlers determine **which repository/stack to mutate** from a *different* JSON path in the same payload — `repository.full_name` — with no cross-check against `repository.owner.login` (the field that was actually authenticated): [5](#0-4) [6](#0-5) 

The binding that should hold is:

`organization authenticated by signature (repository.owner.login) == organization of the repository actually written to (derived from repository.full_name)`

Nothing enforces this equality. `repository.owner.login` and `repository.full_name` are two independently-controlled fields in the same attacker-supplied JSON body; only one of them feeds the signature-secret lookup, and only the other feeds the data-mutation path. Shipit explicitly supports multiple GitHub organizations sharing one Shipit instance, each with its own `webhook_secret` (documented in `docs/setup.md`'s "Using Multiple Github Applications" section), so this cross-organization boundary is a real, first-class concept in the engine, not a theoretical edge case.

### Impact Explanation
An operator/attacker who legitimately controls one organization ("OrgA") registered in this Shipit instance's multi-org GitHub config knows OrgA's `webhook_secret` for their own org (self-configured, not stolen). They can POST a forged webhook body to the public `/github/webhooks` endpoint with:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` validates against the secret they legitimately hold, and
- `repository.full_name = "OrgB/target-repo"` (a stack belonging to a different, unrelated organization tracked by the same Shipit instance)

signed with an HMAC computed using OrgA's own secret over that exact forged body. `verify_signature` passes because it only checks that the signature matches the secret for the org named by `repository.owner.login`; it never verifies that this org matches the org implied by `repository.full_name`. The forged event is then processed against OrgB's stack — e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on any stack whose repository matches the attacker-chosen `full_name`, and other handlers (`status`, `check_suite`, `membership`, pull-request events) similarly write commit statuses, archive/unarchive review stacks, or create team memberships against OrgB's data, using an OrgB-owned identifier while authenticated only as OrgA.

This breaks the trust boundary between organizations that Shipit's own multi-tenant configuration is designed to preserve, letting one org's webhook credential be used to mutate another org's tracked deployment state — an unauthorized write into a repository/stack the attacker's credentials were never meant to authorize.

### Likelihood Explanation
Exploitability requires:
1. The Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration, not a misconfiguration).
2. The attacker to control (or have push/webhook-admin rights on) at least one of those organizations, which is the normal, expected trust level for an org onboarded to a shared Shipit instance — but that trust should be scoped to only that org's repositories, not to every org sharing the deployment.

Given multi-org sharing of a single Shipit instance is an explicit supported feature, this is a realistic scenario for any organization operating a shared Shipit deployment across teams/business units with differing trust levels, which is a common consolidation motivation.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after), require that the organization used to select/verify the webhook secret is derived from — and equals — the organization component of `repository.full_name` (or `organization.login`) that the dispatched handler will actually act on. Concretely:
- Parse `owner/repo` from `repository.full_name` and compare it against `repository.owner.login` (and against the org whose secret validated the signature) before allowing the event to reach `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.
- Reject (422) any payload where these do not match, closing the gap between the authenticated organization and the organization/repository actually mutated.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret`, both tracking stacks in the same Shipit instance.
2. As an operator who only administers `OrgA`'s GitHub App (and thus knows only `OrgA`'s `webhook_secret`), craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist in OrgB's stack>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully because it was computed with the correct (OrgA) secret over this exact payload.
6. `Shipit::Webhooks::Handlers::PushHandler#process` is invoked with the full payload; it derives the target stacks from `payload.dig('repository', 'full_name')` = `"OrgB/target-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack — an action performed by an identity authenticated only for OrgA.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
