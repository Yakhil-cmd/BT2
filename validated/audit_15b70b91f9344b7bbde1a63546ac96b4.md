## Analog Found: Unbounded, Never-Invalidated Definition Cache Keyed Only by Address in `light/get_definition`

### Title
Permanent cache-poisoning of AA/address definitions via unconfirmed `definition` messages - (File: network.js)

### Summary
CVE-2022-27775 is a class of bug where a cached resource is reused across requests because the cache key omits a distinguishing attribute of the context that produced it (the IPv6 zone id), so a value that was only valid in one context gets served in another. `network.js`'s `light/get_definition` handler exhibits the same root cause: it caches an address definition in the process-wide `definitions` object keyed **only by address**, with no key component or invalidation tied to whether the definition is confirmed/stable, and no expiry. Because an **unconfirmed** definition (taken straight from an in-flight, not-yet-stabilized unit) can populate this cache, and the cache is checked *before* the database on every subsequent request, a definition that never becomes canonical can be served to every future light client asking about that address, permanently.

### Finding Description
In the `light/get_definition` handler: [1](#0-0) 
```
case 'light/get_definition':
    ...
    if (definitions[params])
        return sendResponse(ws, tag, definitions[params]);
    db.query("SELECT definition FROM definitions WHERE definition_chash=? UNION SELECT definition FROM aa_addresses WHERE address=? LIMIT 1", [params, params], function(rows){
        var arrDefinition = rows[0]
            ? JSON.parse(rows[0].definition)
            : storage.getUnconfirmedAADefinition(params);
        if (arrDefinition) // save in cache
            definitions[params] = arrDefinition;
        sendResponse(ws, tag, arrDefinition);
    });
    break;
```
When no confirmed row exists, the code falls back to `storage.getUnconfirmedAADefinition(params)`, which scans `assocUnstableMessages` for any not-yet-stable unit with a `definition` message for that address, sequence `'good'`: [2](#0-1) 

This unconfirmed value is unconditionally written into `definitions[params]` and, critically, is served from the cache on every later request **without ever being re-validated against the DB or invalidated when the unit stabilizes, forks out, or is superseded**. `insertAADefinitions` shows that when two units try to define the same AA address, only the first one to be inserted "wins"; the later/rejected one is silently ignored: [3](#0-2) 

An unprivileged AA author (or anyone composing a `definition` message) can therefore post a unit defining address A right before someone else's competing (and ultimately winning) `definition` unit for the same address propagates. If a light client requests `light/get_definition` for A while only the losing unit is known to the hub/serving node (`getUnconfirmedAADefinition` returns the losing payload), that payload gets cached under `definitions[A]` forever. Once the winning definition later stabilizes into `aa_addresses`, the handler will still short-circuit on `if (definitions[params]) return sendResponse(...)` and keep returning the stale, non-canonical definition — the cache key (`address` alone) does not capture the "unconfirmed vs. confirmed" / "which unit" dimension of the value it holds, exactly the missing-key-component pattern in CVE-2022-27775.

### Impact Explanation
Light clients rely on `light/get_definition` to learn the actual AA/address definition that governs an address: hash-verification of who controls it, its getters, its logic for constructing triggers, and for showing users what an AA does before they send funds/triggers to it. If the served definition permanently diverges from the definition that full nodes actually enforce (the one that stabilized in `aa_addresses`/`definitions`), a light client can:
- Build and sign triggers/payments intended for one AA behavior while the network enforces a different one, leading to unexpected bounces, stuck funds, or funds effectively lost/frozen from the user's perspective.
- Be shown incorrect getters/state semantics, undermining any wallet-side validation of AA behavior before a spend.

This is not a network/DoS or malicious-peer issue; it is triggerable by an ordinary unprivileged unit poster (anyone can define/attempt to define an AA address) reaching a light-serving node's own request handler, and it results in persistent server-side data corruption (the cache never self-heals) affecting every downstream light client — matching the "AA fund loss/freezing" and "node disagreement on validity" categories.

### Likelihood Explanation
Requires only: (1) posting (or knowing of) a losing `definition` unit for an address that is about to be defined by a second, competing unit, and (2) a light client (or an attacker acting as one) querying `light/get_definition` for that address while only the losing unit is in `assocUnstableMessages`. Both are ordinary, unprivileged network activities available to any user; no elevated hub/peer role is needed. Once triggered, corruption persists indefinitely (process lifetime) with no self-correcting invalidation path.

### Recommendation
- Do not permanently cache values sourced from `storage.getUnconfirmedAADefinition`; only cache confirmed rows returned from the DB query (`rows[0]`), as is already done in `storage.readAssetInfo`'s analogous cache, which only caches `is_stable` results.
- If caching unconfirmed values is required for performance, key the cache entry with enough context to detect staleness (e.g., the originating unit hash) and invalidate/refresh it on `aa_definition_saved` / unit stabilization events, or attach a short TTL and re-verify against the DB before serving.
- Alternatively, always re-check the DB for confirmed rows before returning any previously cached unconfirmed value.

### Proof of Concept
1. Attacker composes and broadcasts unit `U1` containing `["definition", {address: A, definition: D1 (malicious/incorrect AA logic)}]`.
2. Before `U1`'s conflict with a legitimate/competing unit `U2` (defining the same address `A` with `D2`) is resolved and before either stabilizes, a light client (or victim) sends `light/get_definition` with `params = A` to the serving node.
3. The DB query in the handler finds no confirmed row yet, falls into `storage.getUnconfirmedAADefinition(A)`, which returns `D1` from `assocUnstableMessages` (since `U1`'s sequence is currently `'good'`), and the handler stores `definitions[A] = D1` and replies with `D1`.
4. Time passes; `U2` (defining `A` as `D2`) is the one that actually gets included in `aa_addresses` via `insertAADefinitions`'s "first inserted wins" logic (`U1` is skipped as `prev_unit !== unit`), so the network-enforced definition of `A` becomes `D2`.
5. Any subsequent `light/get_definition` request for `A` to the same serving node hits `if (definitions[params]) return sendResponse(ws, tag, definitions[params]);` at network.js:3830-3831 and returns the stale, non-canonical `D1` forever, even though the network has settled on `D2`.

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}
