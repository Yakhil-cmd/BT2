## Title
Node-as-Leaf ambiguity in `is_valid_merkle_proof()` allows forging membership of arbitrary values against a whitelist Merkle root - (File: `merkle.js`)

### Summary
The core Merkle-proof verifier `verifyMerkleProof()` in `merkle.js` hashes the caller-supplied `element` as if it were always a tree leaf and iteratively combines it with attacker-supplied `siblings` to reconstruct a root, with no domain separation between "leaf hash" and "internal node hash." This is the classic node-as-leaf Merkle proof forgery (the same bug class as the OpenSea Seaport C4 finding). Any Autonomous Agent (AA) author who uses the `is_valid_merkle_proof(element, proof)` oscript function to check trigger-supplied data against a whitelist root can be tricked by a malicious trigger sender into treating an *intermediate hash* of the tree as if it were a genuine whitelisted leaf, because both `element` and `proof` in this formula op are fully attacker-controlled trigger data.

### Finding Description
`getMerkleRoot`/`getMerkleProof`/`verifyMerkleProof` in [1](#0-0)  build the tree by simply hashing leaves and then hashing concatenations of child hashes, with no leaf/node type-byte or prefix to distinguish a leaf hash from an internal node hash: [2](#0-1) 

The comment directly acknowledges the class of bug: `// Node-as-Leaf issue might matter in some cases` at [3](#0-2) .

`verifyMerkleProof(element, proof)` computes `hash(element)` and then folds in each of `proof.siblings` using the given `index` parity, finally comparing to `proof.root`. Since an internal node value is itself just `hash(left+right)` of two children, an attacker who knows the tree structure/root (e.g. because the whitelist and its Merkle tree are published, or because they can derive candidate internal hashes) can pick any internal node `N` of the tree, use `N` as `element`, and supply only the sibling hashes *above* `N` (the higher portion of a normal proof for one of `N`'s descendant leaves). `verifyMerkleProof` will happily reconstruct the correct root and return `true`, even though `N` was never one of the original whitelisted leaf values.

This primitive is exposed to any unprivileged AA trigger sender through the oscript function `is_valid_merkle_proof`, where both operands are ordinary expressions evaluated from trigger data: [4](#0-3) 

An AA author might reasonably write a bases-like whitelist check such as `is_valid_merkle_proof(trigger.data.entry, trigger.data.proof) and trigger.data.proof.root == var['whitelist_root']` (or hardcode the root) to gate a payout, discount, or allow-list action to values in a pre-committed set (addresses, asset ids, coupon codes, etc.). Because the forged proof lets the trigger sender pass an arbitrary internal-node value as `element` and still satisfy the check against the legitimate root, they can claim membership for a value that is not actually part of the whitelist.

Note: the sibling `in merkle` address-definition authentifier at [5](#0-4)  uses the same vulnerable `verifyMerkleProof`, but there the `element` is a fixed literal baked into the address definition (validated at [6](#0-5) ), not attacker-chosen, so it is not directly exploitable the same way. The exploitable surface is the oscript-level `is_valid_merkle_proof` primitive, which any AA developer can wire up with a fully attacker-controlled `element`.

### Impact Explanation
Any AA that relies on `is_valid_merkle_proof` to gate value-transferring or state-changing logic based on membership in an off-chain-committed set (e.g., "pay bonus only to whitelisted addresses/coupon codes/token ids") can be bypassed by an unprivileged AA trigger sender, who forges membership of an arbitrary, unintended value. Depending on how the AA uses the checked value (as a payout key, discount multiplier index, NFT id, etc.), this can lead to unauthorized fund release from the AA, or logic bypass that lets an attacker claim rewards/assets not actually included in the intended whitelist — a direct AA fund loss / unauthorized spending scenario reachable purely by posting a crafted trigger unit.

### Likelihood Explanation
Exploitability depends entirely on AA-author code: only AAs that use `is_valid_merkle_proof` with an attacker-influenced `element` argument to protect value transfers are at risk. Given `is_valid_merkle_proof` is documented and available specifically for whitelist/membership-style checks (see tests at [7](#0-6) ), and the merkle root itself is often published/known off-chain to let genuine users produce proofs, an attacker only needs public knowledge of the tree's intermediate hashes (obtainable by locally rebuilding the tree from any leaked/known leaf set, or in adversarial designs where leaves are guessable/small in number) to forge a valid "membership" claim for a non-member value. The codebase's own comment flags this exact issue as a known but unresolved concern.

### Recommendation
Add domain separation between leaf hashing and internal-node hashing in `merkle.js`, e.g. prefix leaves with a distinct tag/byte (`hash('0'+element)`) and internal nodes with another (`hash('1'+left+right)`), and update `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently. This must be a backward-incompatible, versioned change (guarded by an upgrade MCI) since existing proofs and `in merkle` definitions rely on the current unprefixed hashing scheme. Until fixed, AA/oscript documentation should explicitly warn that `is_valid_merkle_proof` element inputs must not be trusted as guaranteed original leaves when attacker-supplied.

### Proof of Concept
1. Off-chain, build a Merkle tree over leaves `[L0, L1, L2, L3]` using `merkle.getMerkleRoot`, obtaining `root`.
2. Compute the intermediate node `N = hash(hash(L0) + hash(L1))` (the parent of `L0`/`L1`).
3. Take the normal proof for `L0` from `merkle.getMerkleProof`, e.g. `{root, index: 0, siblings: [hash(L1), hash(hash(L2)+hash(L3))]}`.
4. Truncate this proof to only the sibling(s) above `N`: `{root, index: 0, siblings: [hash(hash(L2)+hash(L3))]}` and submit `element = N` instead of `L0`.
5. Call `is_valid_merkle_proof(N, {root, index:0, siblings:[hash(hash(L2)+hash(L3))]})` inside an AA formula (or directly via `merkle.verifyMerkleProof(N, proof)`); it returns `true`, proving `N` — not any real whitelisted leaf — as "in the set" defined by `root`, exactly mirroring the referenced Seaport C4 finding's attack against Merkle-based whitelist checks.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
