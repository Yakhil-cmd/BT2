### Title
Cross-Organization Commit Status Forgery Enables Unauthorized Deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler`, which processes GitHub `status` webhook events, never scopes its write to the repository/organization that authenticated the request. Every other repository-scoped webhook handler (`PushHandler`, `CheckSuiteHandler`, the `pull_request` handlers) filters through `stacks`/`Repository.from_github_repo_name(payload.dig('repository','full_name'))` before mutating anything. `StatusHandler` does not: it looks up commits globally by SHA across the entire installation and writes a CI status onto them regardless of which organization's webhook secret actually signed the request.

### Finding Description
The webhook pipeline authenticates a request by selecting the signing organization from the untrusted JSON body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` is used to fetch that organization's `webhook_secret` and verify the HMAC. Multiple organizations can each be independently configured with their own `webhook_secret` under `secrets.github`: [3](#0-2) 

So verification only proves "this payload was signed by organization X's secret" — it says nothing about which repository the payload's other fields (e.g. `sha`) actually apply to.

Every handler that mutates state is expected to re-derive its target scope from `payload.dig('repository', 'full_name')` via the base `Handler#stacks`/`#repository_name` helpers: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` correctly do this — they only touch stacks belonging to the repository named in the payload: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, ignores the `repository` object entirely and queries commits globally by SHA, independent of which stack/repository/organization they belong to: [7](#0-6) 

Because commit SHAs are unique identifiers stored on `Commit` records shared across all stacks in the same Shipit instance, any organization "OrgA" that is legitimately onboarded (has its own configured `webhook_secret`/GitHub App installation) can send a `status` webhook signed with OrgA's own secret, but reference the `sha` of a commit belonging to a completely different organization "OrgB"'s repository/stack. `verify_signature` only checks that the request came from OrgA (the login in `repository.owner.login`, which the attacker also controls in the same payload); `StatusHandler#process` then blindly finds and updates the matching `Commit` row regardless of its actual owning stack.

This breaks exactly the trust binding called out in the analog rules: the organization that authenticated (OrgA) is not equal to the repository whose data actually gets written (OrgB's commit).

### Impact Explanation
Commit deployability in this engine is driven by commit statuses reaching a `success` state, as exercised in `stack_test.rb`, where creating a `CommitStatus` with `state: 'success'` makes a previously non-deployable commit deployable: [8](#0-7) 

If continuous delivery is enabled on the victim's stack, forging a passing CI status on an otherwise-unshipped commit in a victim organization's repository can cause that commit to be automatically deployed — an unauthorized deploy triggered purely by a cross-tenant authentication mix-up, which meets the Critical impact bar ("an unauthorized deploy... ").

### Likelihood Explanation
The only prerequisite is administrative/webhook control over any one organization that is already onboarded to the shared Shipit instance (i.e., knowledge of that org's own legitimately configured `webhook_secret`/GitHub App installation) — this does not require a Shipit session, `ApiClient` token, or the victim organization's own credentials. Multi-tenant Shipit deployments that host multiple organizations' stacks behind one instance (as explicitly supported by `Shipit.github_organizations`/`github_app_config`) are the ones exposed. The attacker needs to know or guess a real commit SHA in the victim's repository, which is realistic since commit SHAs from public/private-but-visible commits, PR branches, or CI logs are frequently observable.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the `Commit` lookup to commits belonging to stacks under `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, and additionally assert that `repository.owner.login` (the field used for signature verification) matches the owner segment of `repository.full_name` before trusting either field.

### Proof of Concept
1. Onboard/administer legitimate organization `attacker-org` in the shared Shipit instance (its own real `webhook_secret`).
2. Note a target commit SHA `S` belonging to a stack under organization `victim-org` (e.g., observed from a PR or push notification).
3. Send a GitHub `status` webhook payload signed with `attacker-org`'s real webhook secret:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant-repo" }
}
```
4. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s webhook secret, and the signature validates successfully.
5. `StatusHandler#process` executes `Commit.where(sha: "S").each { |commit| commit.create_status_from_github!(params) }`, which finds and updates the `victim-org` commit `S`'s status to `success`, without ever checking that `S` belongs to `attacker-org`.
6. If `victim-org`'s stack has continuous delivery enabled, the now-"deployable" commit may be auto-deployed.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
