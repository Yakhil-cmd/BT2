### Title
Stack-scoped `ApiClient` can create stacks outside its authorized scope via `Api::StacksController#create` - (File: app/controllers/shipit/api/stacks_controller.rb)

### Summary
`Shipit::ApiClient` can be scoped to a single stack via `stack_id`, and every read/write action on `Api::StacksController` (and other stack-bound API controllers) is expected to resolve the target through the `stacks` collection, which filters by that `stack_id`. The `create` action, however, never consults this scoped collection: it builds a brand-new `Stack` from arbitrary `repo_owner`/`repo_name` parameters and never checks that the resulting repository/stack matches the client's authorized `stack_id`.

### Finding Description
`Shipit::Api::BaseController#stacks` defines the authorization scope for a stack-bound token: [1](#0-0) 
Every other stack-touching action (`show`, `update`, `destroy`, `refresh`) resolves the target stack through this scope via `stack`: [2](#0-1) 

`create`, however, bypasses this binding entirely: [3](#0-2) [4](#0-3) 

`Repository.find_or_create_by(owner:, name:)` accepts any attacker-controlled `repo_owner`/`repo_name`, and the new `Stack` is written directly, with no reference to `current_api_client.stack_id`. The only guard on `create` is the coarse `write:stack` permission check: [5](#0-4) [6](#0-5) 

This is the same class of bug as the reported `AgentFactory::assetToken` issue: a binding that is supposed to hold across all operations on a resource (`assetToken` == the token actually held/used; here, `stack_id` == the stack the token is permitted to touch) is enforced in some code paths (`withdraw`, `executeApplication` / `stack`, `update`, `destroy`) but silently dropped in one specific path (`setAssetToken` misuse / `create`), letting an operation act outside the intended scope. Before the attacker's request: `current_api_client.stack_id` == the only stack the token may read/write. After calling `create`: the token has now written (created) a brand-new `Stack`/`Repository` row for an arbitrary repo, breaking the equality `stack the token authorizes == stack the token touches`.

### Impact Explanation
An `ApiClient` deliberately scoped to one stack (e.g., a CI integration token meant to only interact with its own project) can create arbitrary new stacks bound to arbitrary GitHub repositories it was never authorized for. Because `Stack#repository` is resolved via `find_or_create_by`, the attacker can also attach the newly created stack to an *existing* `Repository` row already used by other legitimate stacks, and `Api::StacksController#create` performs no ownership/authorization check against that repository. Given `write:stack` (a permission that a stack-scoped client can legitimately hold for managing its own stack), this crosses into creating and controlling stack state for repositories/environments the token has no business touching — an authorization escalation beyond the token's declared scope, consistent with "escalation into `Shipit.github_teams` authorization" / cross-scope unauthorized state creation for other repositories.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with `write:stack` permission can trigger this with a single unauthenticated-beyond-the-token API call; no additional privileges, timing, or race conditions are required. The scoping mechanism (`stacks` in `BaseController`) is otherwise consistently applied, making the omission in `create` easy to overlook and straightforward to exploit once discovered.

### Recommendation
In `Api::StacksController#create`, validate that the client is not scoped (`current_api_client.stack_id?` must be false) before permitting stack creation, or otherwise ensure the created stack's repository matches the client's authorized scope. Concretely, reject the request (403) when `current_api_client.stack_id?` is true, mirroring the read-side restriction already applied in `stacks`.

### Proof of Concept
1. Create (via the admin UI) an `ApiClient` scoped to `stack_id: <stack A id>` with permission `write:stack`.
2. Using that client's Basic Auth token, issue:
```
POST /api/stacks
repo_owner=some-other-org
repo_name=some-other-repo
environment=production
```
3. Observe a new `Stack` (and possibly a new/found `Repository`) is created for `some-other-org/some-other-repo`, even though the client's `stack_id` scope only permitted access to stack A — no scope check in `Api::StacksController#create` / `#repository` prevents this.
