### Title
Webhook signature is validated against the organization derived from `repository.owner.login`, but the write target (Stack/Repository) is looked up from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App deployment (a documented, in-scope Shipit configuration, see `docs/setup.md:182-209`), `WebhooksController#verify_signature` selects which org's HMAC secret to check the request against using one payload field (`repository.owner.login` / `organization.login`), while the handlers that actually act on the payload (create commits, statuses, trigger syncs/deploys) resolve the target `Stack`/`Repository` using a *different*, independently-controlled payload field (`repository.full_name`). Because the whole raw body is attacker-authored before signing, these two fields are never required to agree.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the JSON body and uses it purely to pick which configured GitHub App's `webhook_secret` to validate the signature against: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app config (including `webhook_secret`) when multiple GitHub Apps are configured, as documented for multi-tenant setups: [3](#0-2) [4](#0-3) 

Once the signature passes, the entire raw JSON body is dispatched unmodified to event handlers: [5](#0-4) 

However, the handlers resolve which `Repository`/`Stack` to mutate using `repository.full_name`, a field that is completely independent of `repository.owner.login`: [6](#0-5) [7](#0-6) 

`PushHandler` triggers `stack.sync_github` (continuous delivery pipeline) for every non-archived stack of the resolved repository/branch, and `StatusHandler` writes a `Status` for any commit matching the attacker-supplied `sha`, both without re-checking that `repository.owner.login` (the field that determined which secret validated the request) matches `repository.full_name`'s owner (the field that determines which repository is actually written to): [8](#0-7) [9](#0-8) 

This is directly analogous to the M-7 pattern: a check is performed against one value (the "before" borrow snapshot / here, the organization used to select the signing secret) while the actual state mutation is driven by a different, unverified quantity (the post-interest borrow delta / here, `repository.full_name`) — the binding between "what was authenticated" and "what gets written" is broken.

### Impact Explanation
In a Shipit deployment configured with multiple GitHub Apps (one per tenant/org — an explicitly supported and documented configuration), an attacker who legitimately controls **any one** of the configured orgs' GitHub App webhook secret (e.g., their own org, onboarded as a tenant) can craft a webhook payload with:
- `repository.owner.login` = their own org (so `verify_signature` validates it using a secret they legitimately know)
- `repository.full_name` = `"<victim-org>/<victim-repo>"` (so the handler mutates a stack belonging to a different tenant)

This yields cross-repository/cross-tenant writes: forged `push` events can enqueue `GithubSyncJob`/continuous-delivery syncs against a victim stack, and forged `status` events can inject fabricated CI/commit statuses that affect deployability checks — all without ever holding a session, `ApiClient` token, or the victim org's webhook secret. This breaks the "organization that authenticated" vs "repository that is written" trust binding and falls under unauthorized cross-repository writes / unauthorized deploy triggers.

### Likelihood Explanation
Requires the operator to run Shipit with the multi-org GitHub App configuration (a supported, documented feature) and requires the attacker to be an onboarded tenant with a legitimately configured (and thus secret-known) GitHub App — not a privileged Shipit user. Given multi-tenant Shipit installs are an explicit use case, this is plausible wherever tenants are mutually untrusted.

### Recommendation
After signature verification, cross-check that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` before dispatching to handlers, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `attacker-org` and `victim-org`, per `docs/setup.md:182-209`.
2. As the legitimate admin of `attacker-org`'s GitHub App, compute an HMAC-SHA1 signature over an arbitrary crafted JSON body using `attacker-org`'s known `webhook_secret`.
3. Craft the body as a `push` event: `{"ref": "refs/heads/master", "after": "<attacker-chosen sha>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}}`.
4. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s app, and successfully verifies the signature with the attacker's own known secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, triggering a sync/deploy pipeline the attacker never had credentials for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
