Based on my investigation, I have enough to answer.### Title
Webhook signature is verified against `repository.owner.login`, but event handlers act on the unrelated `repository.full_name`/`organization.login` fields, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against based solely on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw JSON payload* to handlers [2](#0-1) , and those handlers resolve the target `Stack`/`Repository`/`Commit`/`Team` using a *different* field of that same payload — `payload.dig('repository', 'full_name')` in the base `Handler` class [3](#0-2) , or `params.organization.login` in `MembershipHandler` [4](#0-3) . Nowhere is `repository.full_name` (or `organization.login` used for resource resolution) cross-checked against `repository.owner.login` (the value used for signature verification).

### Finding Description
This engine supports multi-organization configuration where each GitHub organization has its own independent `webhook_secret` [5](#0-4)  as documented for "Using Multiple GitHub Applications" [6](#0-5) . A party who legitimately administers a GitHub App on **Org A** (and therefore knows Org A's `webhook_secret`) can compute a valid HMAC-SHA1 signature (`X-Hub-Signature`) over an arbitrary, hand-crafted JSON body — they are not restricted to relaying genuine GitHub deliveries, since the controller only checks the raw signature against the raw body it receives, it does not require the request to actually originate from GitHub's servers.

The binding that should hold is:
`organization authenticated by the signature (repository.owner.login) == organization/repository the payload is permitted to act on (repository.full_name / organization.login)`

Before the attack: an org's secret can only be used to affect that org's own stacks, because in genuine GitHub deliveries `repository.owner.login` and `repository.full_name` always refer to the same repository.

After the attack: the attacker sets `repository.owner.login` = `"OrgA"` (so `verify_signature` picks Org A's `webhook_secret` and validates using a signature they can compute themselves), while setting `repository.full_name` = `"OrgB/target-repo"` (a repository belonging to a different, unrelated organization tracked by the same Shipit instance). `WebhooksController#verify_signature` succeeds because Org A's secret matches, but `Handler#stacks`/`Handler#repository_name` resolves `Shipit::Repository.from_github_repo_name("OrgB/target-repo")` [3](#0-2)  and dispatches the event against Org B's stacks — despite the requester never having proven any relationship with Org B.

Concretely exploitable handlers include:
- `PushHandler`, which enqueues `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the spoofed target repository/branch [7](#0-6) .
- `StatusHandler`, which looks up `Commit.where(sha: params.sha)` (no repository scoping at all, purely a global commit SHA lookup) and calls `commit.create_status_from_github!(params)` — letting an attacker inject an arbitrary CI/commit status (e.g., forging a green "success" status) onto commits belonging to completely different repositories, potentially unblocking deploy checks that gate a real deploy [8](#0-7) .
- `MembershipHandler`, which trusts `params.organization.login` to attribute team membership add/remove operations, letting a signature valid for Org A be used to manufacture `Team`/`Membership` records nominally tied to a different `organization.login` value [9](#0-8) .
- Pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` without any tie back to the signing organization [10](#0-9) .

### Impact Explanation
This crosses the exact boundary called out in scope: "an organization that authenticated versus the repository that is written." An attacker who legitimately controls one onboarded GitHub organization's webhook secret can forge events that write to, sync, archive/unarchive, or inject fabricated CI status onto stacks belonging to an entirely different, unrelated organization tracked by the same Shipit instance. Forged CI/commit statuses can influence deploy-readiness checks, and forged `push` events force out-of-band Git syncs on foreign stacks — this is a cross-repository/cross-organization write achieved purely by crafting a payload, satisfying the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
This is only exploitable on a multi-organization Shipit deployment (single-org deployments have only one `webhook_secret`, so the attacker would already need that org's secret, which is the whole app's trust boundary). In a multi-org setup, however, no additional privilege is required beyond having been granted a webhook secret for any one of the onboarded organizations — an unprivileged-relative-to-other-orgs attacker. The `/webhooks` endpoint is unauthenticated by design (session auth is skipped for this controller) and accepts freeform JSON bodies with any header combination, so building the forged payload requires no special access beyond knowledge of one org's secret.

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), after selecting the `GitHubApp`/secret via `repository_owner`, re-validate that every organization/repository-identifying field used later for resource resolution (`repository.full_name`'s owner segment, `organization.login`) is consistent with the authenticated `repository_owner`. Concretely: derive the org used for signature verification and require `payload.dig('repository', 'full_name')&.split('/')&.first&.casecmp?(repository_owner)` (and similarly for `organization.login` in `MembershipHandler`) before dispatching to any handler, rejecting the request (422) on mismatch.

### Proof of Concept
```ruby
# Attacker administers "OrgA" (a real onboarded org) and knows OrgA's webhook_secret.
secret = "orgA_webhook_secret"
payload = {
  ref: "refs/heads/master",
  after: "deadbeefcafefeed",
  repository: {
    owner: { login: "OrgA" },       # used by verify_signature -> passes with OrgA's secret
    full_name: "OrgB/target-repo"   # used by Handler#repository_name -> resolves OrgB's stack
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", secret, payload)

post "/webhooks", body: payload, headers: {
  "X-Github-Event" => "push",
  "X-Hub-Signature" => signature
}
# => 200 OK; Shipit::Webhooks::Handlers::PushHandler resolves Repository "OrgB/target-repo"
#    and enqueues stack.sync_github for OrgB's stack, even though the attacker only
#    ever proved control over OrgA's webhook secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event

    end

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
