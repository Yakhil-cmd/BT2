### Title
Webhook Organization Authentication Does Not Bind to the Repository/Stack Written by `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the `GithubApp` (and its `webhook_secret`) belonging to a specific *organization*, derived from the payload's `repository.owner.login` (or `organization.login`). [1](#0-0) [2](#0-1)  That authentication only proves the sender controls a repository under *that* organization. It does not, and cannot, prove anything about which `Commit`/`Stack` in Shipit's database the event is allowed to mutate. `StatusHandler`, however, applies the status update by SHA lookup across the entire `Commit` table with no repository/stack scoping at all: [3](#0-2) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Every other handler that mutates state scopes itself to the repository named in the payload via `Handler#stacks`/`#repository_name`, e.g. `PushHandler` uses `stacks.not_archived.where(branch:)`. [4](#0-3) [5](#0-4)  `StatusHandler` is the outlier: it never checks `payload['repository']` at all.

### Finding Description
The binding that should hold is:

```
organization authenticated by verify_signature == repository/stack whose Commit rows get written
```

`verify_signature` picks the `GithubApp` config (and therefore the `webhook_secret` used in the HMAC check) purely from `repository_owner`, itself read straight out of the unauthenticated JSON body before the signature is verified: [1](#0-0) . Once the signature validates, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the raw parsed params for every handler registered for the event, with no re-check that the "repository" field in the params matches the organization that just authenticated: [6](#0-5) .

`StatusHandler#process` only reads `params.sha`/`params.state` and matches any `Commit` in the whole instance sharing that SHA, irrespective of which repository/stack it belongs to. [7](#0-6)  Because git commit SHAs are content-addressed and deterministic, any two repositories that share commit history (a public fork, a re-pushed copy of the same tree/parent/author/committer metadata, or a repository seeded from the same upstream) can produce a commit whose SHA collides with one already recorded against a *different* organization's `Stack`.

This is the same bug class as the reported Move issue: two pieces of state that are supposed to be tied together by identity (there: `VaultNAV` snapshot vs. live `Bank` balance, both meant to represent the same position; here: "organization that signed the webhook" vs. "repository whose `Commit` gets mutated") are decoupled, and the write path trusts the wrong one of the pair.

### Impact Explanation
An attacker who legitimately controls *any* organization/repository connected to this Shipit instance (a normal, unprivileged tenant — no `ApiClient` token, no victim's `webhook_secret`, no GitHub App key needed) can send a real, correctly-signed `status` webhook for a commit in their own repository whose SHA matches a commit belonging to a victim organization's `Stack`. Because `StatusHandler` ignores `repository_name` entirely, this forges a `Status` (`state`, `context`, `target_url`, `description`) on the victim's commit. Since commit deployability and continuous-deployment triggering are derived from recorded `Status`/`deployable_status` (used by `Stack#next_commit_to_deploy`/`deployable_commits` and `trigger_continuous_delivery`), an attacker can inject a fabricated "success" CI status onto a victim commit, which can cause an unauthorized deploy on a `continuous_deployment`-enabled stack — matching the "unauthorized deploy" criterion in the impact bar. [8](#0-7) 

### Likelihood Explanation
Requires: (1) the attacker to be a legitimate, unprivileged tenant of a multi-org Shipit deployment (a supported, documented configuration — `config/setup.md` describes per-org `github.webhook_secret`), and (2) the ability to produce a commit whose SHA equals a target commit's SHA. This is trivially satisfiable when the victim repository is public (fork it, re-push identical commits into an attacker-owned repository, generating the identical SHA) or when repositories share upstream history. No credential of the victim organization is needed at any point — the attacker's own, legitimately-signed webhook is sufficient because `StatusHandler` never checks it against the repository.

### Recommendation
Bind the authenticated organization to the write path in `StatusHandler`: scope the `Commit` lookup through the repository named in the payload, exactly like `PushHandler`/`Handler#stacks` do, e.g.:

```ruby
def process
  Repository.from_github_repo_name(repository_name)&.stacks&.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```

More generally, every handler should be audited to ensure it only mutates `Commit`/`Stack` rows that belong to the repository named in the payload that was actually covered by the verified signature, not by unscoped attribute lookups (SHA, team id, etc.) that can collide across tenants.

### Proof of Concept
1. Attacker's own GitHub organization `attacker-org` is configured as a normal tenant of this Shipit instance (has its own `GithubApp`/`webhook_secret`, entirely legitimate).
2. Attacker forks (or otherwise reproduces) the victim's public repository `victim-org/app`, preserving history so a specific commit `C` retains the exact same SHA in both repos (trivial for a straight fork/mirror before any new commits are added).
3. Attacker creates a Shipit `Stack` (or simply has `victim-org/app`'s commit `C` already tracked in the DB via prior sync) and pushes/creates a commit status for `C` under `attacker-org/app-fork` (e.g., via GitHub Actions or the GitHub API using attacker's own token).
4. GitHub sends Shipit a `status` webhook for `attacker-org/app-fork`, signed with `attacker-org`'s `webhook_secret`. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and the signature validates. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: C).each { |commit| commit.create_status_from_github!(params) }`, which matches the victim's `victim-org/app` commit row too, and records a forged `success` status on it — despite the request never being signed by `victim-org`'s secret. [3](#0-2) 
6. If `victim-org/app`'s stack has `continuous_deployment: true`, this forged status can make the commit "deployable," triggering `trigger_continuous_delivery` and an unauthorized deploy. [8](#0-7)
