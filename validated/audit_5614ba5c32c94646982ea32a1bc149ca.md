### Title
Login CSRF via unprotected OmniAuth `/github/auth/github` flow enables forced-OAuth session fixation - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
The engine mounts OmniAuth without the CSRF-protection add-on and exposes both the authorization-request endpoint (`/github/auth/github`) and the callback endpoint via plain `GET`, allowing an unprivileged, unauthenticated attacker to force a victim's browser to complete a GitHub OAuth login as the attacker's own controlled GitHub account, silently binding the victim's existing browser session to the attacker's identity.

### Finding Description
`Shipit::Engine` mounts `OmniAuth::Builder` with the `github` strategy without any CSRF token check on the initiation step: [3](#0-2) 
The engine's `Gemfile.lock` shows only bare `omniauth (1.9.2)` / `omniauth-github (1.4.0)`, with no `omniauth-rails_csrf_protection` dependency present anywhere in the resolved gem set, so OmniAuth's request phase performs no state/CSRF validation.
The routes additionally allow the entire OAuth dance to be driven with simple `GET` navigation, including the callback itself: [1](#0-0) 
`GithubAuthenticationController#callback` then unconditionally trusts whatever `omniauth.auth` the middleware attached to the request and immediately overwrites `session[:user_id]`/`session[:authenticated]` with the identity resolved from that auth hash, with no verification that the browser session that started the flow is the same one completing it: [4](#0-3) 

This breaks the intended binding of "the GitHub identity that completed OAuth" == "the `User` the victim's own action intended to authenticate as." An attacker who owns/controls their own GitHub account can complete the OAuth handshake themselves and then hand the resulting callback URL/authorization code to a victim (e.g. via a same-site redirect, an `<img>`/link, or by pre-establishing OAuth state and getting the victim to click through), causing the victim's browser session to become authenticated as the attacker's GitHub identity without the victim's Shipit-side credentials ever being involved.

### Impact Explanation
This is exactly the "session fixation / forced OAuth completion" category called out as High severity in scope: an attacker can force completion of the OAuth flow into a victim's session. Once forced, the victim's browser is logged in as an account fully controlled by the attacker; if the attacker's account is later added to (or already is a member of) an authorized `Shipit.github_teams` team, or if the victim performs privileged actions while believing they are operating under their normal identity, actions get attributed to/executed under the attacker-controlled account bound into the victim's session — an authentication/session-integrity failure requiring no Shipit session, API token, or webhook secret from the attacker.

### Likelihood Explanation
Exploitability requires only that the attacker control a GitHub account and be able to get a victim to visit/click a link (a lightweight social step consistent with a CSRF-class primitive, not "social engineering" of secrets). No Shipit credential, webhook secret, or `ApiClient` token is needed, and the vulnerable code path (`GithubAuthenticationController`, `lib/shipit/engine.rb` OmniAuth mount, `config/routes.rb`) is core, always-active engine code reached by any deployment that enables `Shipit.github.oauth?`, which is the documented way to enable authentication.

### Recommendation
Add `omniauth-rails_csrf_protection` (or equivalent CSRF/state verification) to the mounted OmniAuth middleware, and restrict `/github/auth/github` (`request` and `callback` actions) to `POST`-only where the OmniAuth request phase is concerned, removing the `get :callback`/`get '/', action: :request` routes or gating them with an explicit anti-forgery token check.

### Proof of Concept
1. Attacker completes GitHub OAuth authorization themselves, obtaining a valid `code`/callback URL for their own GitHub account against Shipit's OAuth app.
2. Attacker sends the victim a link that causes the victim's browser to load `GET /github/auth/github/callback?code=<attacker_code>&state=<...>` (or, absent any CSRF/state binding, simply re-triggers the flow end-to-end via an auto-submitting redirect chain starting at `GET /github/auth/github`).
3. Because no CSRF protection is present on the OmniAuth request/callback and `GithubAuthenticationController#callback` performs no session-origin check, the victim's browser session is stamped with `session[:user_id]` resolved to the attacker's GitHub identity, per [5](#0-4) .
4. The victim is now unknowingly operating under the attacker-controlled account for the remainder of the session.
