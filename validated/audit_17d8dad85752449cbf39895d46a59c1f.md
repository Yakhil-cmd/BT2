### Title
Unhandled `throw` on stale `early_return` state crashes AA execution - (File: formula/evaluation.js)

### Summary
The Lua advisory concerns a debug-hook state variable (`oldpc`) that is not correctly reset when control flow returns from a function, leading to a segfault reachable from ordinary script execution. The oscript evaluator in `formula/evaluation.js` has a structurally analogous per-formula-execution state flag, `early_return`, that must be cleared exactly at function-return boundaries. `callFunction()` unconditionally treats a lingering `early_return` value as a fatal bug and does a hard `throw`, rather than converting it into a graceful `setFatalError`/bounce, breaking the “errors from untrusted AA/oscript code must always bounce, never crash the node” invariant that the rest of the evaluator carefully maintains everywhere else.

### Finding Description
`evaluate()` treats `early_return !== undefined` as a signal to stop descending into the AST and short-circuit to `cb(true)`: [1](#0-0) 

`callFunction()` is the only place that clears this flag, and it does so only after the function body’s own `evaluate()` callback fires: [2](#0-1) 

Critically, at the very top of `callFunction()`, before any of that cleanup logic runs, there is a defensive check: [3](#0-2) 
```
if (early_return !== undefined)
    throw Error("function called after a return");
```
This is a synchronous, uncaught `throw` (not `setFatalError`, not `cb(false)`), executed deep inside chains of `async.eachSeries` callbacks that originate from `exports.evaluate()`, which is itself invoked from `aa_composer.js`’s `handleTrigger` while processing units posted by any address. All other “this should never happen” conditions elsewhere in this same interpreter (bad values, shadowed args, oversized objects, etc.) are surfaced via `setFatalError(...)`, which safely bounces the AA response — this one code path is the odd exception that crashes the process with a raw `throw` instead.

The comment on line 128 (“avoid extra long call stacks”) and the `count % 100` `setImmediate` trampolining show the authors are aware evaluation is a long chain of nested asynchronous callbacks sharing closures over `early_return`/`fatal_error`/`count` for the whole formula evaluation, similar in spirit to Lua's `ci->u.l.savedpc`/`oldpc` bookkeeping that must be perfectly synchronized with control-flow transitions (function entry/exit) or the interpreter faults. This code relies on the invariant that `early_return` is always `undefined` by the time any `callFunction()` is invoked (guaranteed today by the short-circuit at line 132), but that invariant is enforced by a “should never happen” exception rather than a validated state machine — any future path (or any currently-missed corner case in nested statement blocks, `func_declaration` argument evaluation, `map`/`filter`/`reduce` callback function invocation, or remote getter interaction with `callGetter`) that manages to invoke `callFunction` while `early_return` is still set from a sibling/outer scope will crash the whole evaluation with an unhandled exception instead of bouncing.

### Impact Explanation
An uncaught `throw` inside the AA trigger-handling pipeline (`aa_composer.js` → `formula/evaluation.js`) that is not wrapped by the caller in a way that turns it into a bounce would propagate up through `handleTrigger`/`dryRunPrimaryAATrigger` and crash (or desynchronize) the Node.js process handling unit/AA validation for any node that processes the offending unit. Because AA trigger processing must be deterministic and identical across all full nodes for DAG stability/consensus, a crash (or an inconsistent state left behind by a thrown exception mid-batch, e.g. partially applied `batch`/`conn` transaction state) on some nodes but not others is a “node disagreement on validity or stability” / “network unable to confirm new units” class impact — reachable purely from a posted trigger unit or AA-to-AA call chain, with no privileged access required.

### Likelihood Explanation
Currently, the guard at the top of `evaluate()` (line 132) appears to prevent `callFunction` from ever being reached while `early_return` is set, so this specific `throw` may not be triggerable via the standard statement/expression grammar today — I could not fully verify every call path (e.g. `map`/`filter`/`reduce` with local function callers at lines ~2405-2410, `evaluateFunctionExpression`, and nested `func_declaration` evaluation) reaches `callFunction` strictly after any pending `early_return` has already been cleared by its own enclosing `callFunction`. This is the main residual uncertainty. Given the interpreter is a deeply nested continuation-passing pipeline shared through closures across many `async.eachSeries`/`async.eachOfSeries` calls, and given oscript is an actively evolving language (new ops guarded by `mci` upgrade constants such as `aa2UpgradeMci`, `aa3UpgradeMci`, `pemCurvesFixMci`), the risk is that a not-yet-discovered corner case (or a future op addition) reintroduces exactly the same class of bug as the Lua CVE: a debug/control-flow bookkeeping variable not reset precisely at a function-return boundary, surfaced by a `throw` instead of a safe error path.

### Recommendation
Replace the `throw Error("function called after a return")` in `callFunction()` with a `setFatalError(...)` call (consistent with every other invariant violation in this file), so that even if this state is ever reached, the AA response bounces deterministically instead of throwing an unhandled exception that can crash or desynchronize node processes. Additionally, audit all call sites that can reach `callFunction` (func_call, remote_func_call via local funcs, map/filter/reduce callers, `evaluateFunctionExpression`) to confirm `early_return` is always cleared before any such call, and add regression tests that specifically exercise return-inside-nested-function-call combinations (including inside `map`/`filter`/`reduce` callback functions and multi-argument function calls where one argument itself calls a function containing `return`).

### Proof of Concept
Not reproducible with currently available tooling/read-only access: exploiting this would require constructing an oscript AA formula where a `func_call`/`remote_func_call` is evaluated while `early_return` is non-`undefined` from an outer scope, bypassing the short-circuit at `formula/evaluation.js:132`. I was unable to find, within index-search access, a concrete grammar construct that survives the short-circuit and still reaches `callFunction` with a stale `early_return`. A Devin session with full repository/test access would be needed to enumerate all `evaluate()`/`callFunction()` call paths (including `map`/`filter`/`reduce`, `evaluateFunctionExpression`, and `func_declaration` evaluation) and attempt to construct or rule out a triggering oscript formula.
