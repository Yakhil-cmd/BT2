### Title
Cross-repository status forgery triggers unauthorized deploy via `StatusHandler#process` unscoped commit lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with `Commit.where(sha: params.sha)`, never checking that the webhook's `repository` field matches `commit.stack.repository`. Because the `commits` table only enforces uniqueness on `(sha, stack_id)` and not globally, an attacker who controls (or has CI rights on) any repository whose commit history happens to share a SHA with a victim stack's HEAD commit can post a legitimate, correctly-signed `status` webhook from that unrelated repository and have the resulting `Status` row attached to the victim's stack.

### Finding Description
The binding that should hold is: `status.stack_id == commit.stack_id` implies the originating webhook's `payload['repository']['full_name'] == commit.stack.repository.full_name`. This binding is never checked.

- `WebhooksController#verify_signature` only verifies that the payload is authentically signed for the organization derived from `repository_owner = params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . This proves the webhook came from *some* repository in that organization/App installation — not that it came from the specific repository tracked by the target stack.
- `StatusHandler#process` then resolves the target `Commit` purely by SHA, with no repository filter at all:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
Compare this to `PushHandler#process`, which correctly scopes to `stacks` (repository-derived) and `branch` before acting [4](#0-3) . `StatusHandler` has no analogous scoping.
- The `commits` table's uniqueness constraint is `(sha, stack_id)`, not a global unique constraint on `sha` alone [5](#0-4) , confirming the same SHA can legitimately exist as commit rows belonging to different stacks (e.g., forks of the same repo, mirrored repos, or an attacker who copies a public victim commit verbatim into their own repo — git commit hashes are content-addressed and portable across repositories).
- `commit.create_status_from_github!` calls `add_status`, which creates the `Status` row scoped to `commit.stack_id` (the resolved commit's actual stack, i.e. potentially the victim's), and on transition to `success`/`pending` calls `stack.schedule_merges` [6](#0-5) [7](#0-6) .
- `Status` model's `after_commit :schedule_continuous_delivery` calls `commit.schedule_continuous_delivery` on every created status [8](#0-7) , which (per the question's stated call chain) evaluates `Commit#deployable?` and enqueues `ContinuousDeliveryJob` if the victim stack has `continuous_deployment: true` and the commit is otherwise unlocked/unblocked.

Exploit flow: attacker owns/controls a repository under a GitHub organization that has the Shipit GitHub App installed (so `verify_signature` will pass for events sourced from that org). Attacker copies a victim commit verbatim (identical tree, parents, author/committer timestamps) into their own repo/fork — producing an identical SHA1. Attacker's own CI (fully under attacker control) posts a `success` status for that SHA to GitHub, which GitHub relays as a `status` webhook to Shipit, correctly signed for the attacker's org. `StatusHandler#process` matches this SHA against `Commit.where(sha: ...)`, finds the victim's stack's commit row, and writes a `success` `Status` scoped to the victim's `stack_id` — with no check that the webhook's `repository` field is the victim's tracked repository.

Existing guards do not close this gap: `verify_signature` authenticates the *organization*, not the specific repository in the payload; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` accept `sha`/`state`/etc. but never require or use a `repository` field to scope the lookup at all.

### Impact Explanation
A crafted status from a repository the attacker controls (or merely has CI/push access to within an onboarded organization) can write a `Status` row for a completely different stack/repository, satisfying `Commit#deployable?` and triggering `ContinuousDeliveryJob.perform_later(stack)` — an unauthorized deploy of a commit the attacker never had CI or write access to on the victim repository. This is repeatable against any stack whose HEAD (or any pending) commit SHA the attacker can reproduce, and is not limited to a single tenant: any stack tracked by an organization onboarded to the Shipit instance is at risk if an attacker can source a matching commit and a status webhook from any repo in that org (or any org whose events reach the same Shipit deployment). This matches the "Critical: a payload for one repository mutating another's stack/commit/task, or an unauthorized deploy" impact category.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true` and an undeployed commit; attacker needs a repository under a GitHub organization already integrated with this Shipit instance's GitHub App (to pass `verify_signature`), and the ability to reproduce an identical commit SHA (trivial for any commit whose content, including author/committer timestamps, the attacker can read — e.g., any public commit, or one shared across forks in the same org). No Shipit credentials, sessions, or secrets are required. This is highly feasible in typical GitHub App / organization-wide webhook setups where multiple repositories in the same org share one webhook secret, and is fully repeatable per victim commit.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stack(s)/repository derived from the webhook payload (mirroring `PushHandler`'s use of `stacks`), e.g. `Commit.where(sha: params.sha).joins(:stack).merge(stacks)` where `stacks` filters by `repository` matching `params.dig('repository','full_name')`, and reject/ignore statuses whose payload repository does not match `commit.stack.repository`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is out of scope for this engine's own code changes but demonstrates the equality check):
```ruby
test "status from an unrelated repository must not affect another stack's commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  victim_commit = shipit_commits(:first) # belongs to victim_stack, sha: SHARED_SHA

  # Simulate a second, unrelated stack/repo with a commit sharing the same sha
  attacker_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'created_at' => Time.now.iso8601,
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'shopify' } }
  }

  request.headers['X-Github-Event'] = 'status'
  assert_no_enqueued_jobs only: ContinuousDeliveryJob do
    post :create, body: attacker_repo_payload.to_json, as: :json
  end

  # Binding check: status must only attach when payload repository == commit.stack.repository
  assert_not_equal attacker_repo_payload['repository']['full_name'], victim_commit.stack.repository.full_name
  refute victim_commit.reload.statuses.exists?(context: 'ci/attacker')
end
```
This test currently fails against `StatusHandler#process`, since it will create the `Status` row on `victim_commit` and enqueue `ContinuousDeliveryJob`, proving the missing repository-provenance check.
