### Title
Reachable `throw Error` in AA secondary-trigger bounce handling crashes the full node - ([File: aa_composer.js])

### Summary
CVE-2023-50019 crashes open5gs's AMF because a registration response received at a specific point in the state machine is mishandled by an unguarded error path. In `ocore`'s AA (Autonomous Agent) execution engine, `handleTrigger()`/`handleSecondaryTriggers()` similarly contain internal state-machine assumptions enforced with `throw Error(...)` instead of graceful error callbacks. Because these functions execute inside the same synchronous JS process as the node's core write path, and `network.js` installs a global `uncaughtException` handler that re-throws to crash the process (`process.on('uncaughtException', ... ) { ... throw err; }`), any code path that reaches one of these asserts halts the whole node, not just the offending trigger.

### Finding Description
`handleSecondaryTriggers()` unconditionally asserts that a primary/secondary AA cannot still be in "bouncing" state when it discovers further secondary AAs to invoke: [1](#0-0) 
and `finish()` asserts that a bouncing secondary AA can never carry a produced response unit: [2](#0-1) 

Both are defensive invariants about the internal `bBouncing`/`bSecondary` state that is threaded through many asynchronous callback chains (`bounce()`, `revert()`, `sendDummyUnit()`, `executeStateUpdateFormula()`, formula evaluation with async oracle/data-feed lookups, `updateStorageSize()`, etc. — see `aa_composer.js:875-1042`, `1102-1250`). Any AA author can craft a definition whose formulas/messages interleave in a way that has not been exercised by the existing test suite (e.g. combinations of secondary triggers, `payment` messages issuing new assets, state-update formulas, and bounce conditions triggered by insufficient balance or formula errors at specific points of the async chain). Because these are `throw Error(...)` rather than calling `onDone`/`bounce` with an error, any unit poster who triggers such an AA (or an AA author who deploys such a definition and gets any user to send a trigger to it) can force this assertion to fire during processing of a legitimately posted trigger unit.

This mirrors the open5gs bug class exactly: the vulnerable code assumes a certain response/state ordering can never happen ("Registration response can't arrive after we already finished"), and when that assumption is violated by a message arriving at a particular point in the async flow, the service crashes instead of returning an error to the caller.

### Impact Explanation
`process.on('uncaughtException', ...)` in `network.js` explicitly re-throws to crash the node: [3](#0-2) 
A crash during `handlePrimaryAATrigger` (which runs inside a DB transaction and a kvstore batch write, per `aa_composer.js:91-150`) means the full node process dies while holding the `aa_triggers` mutex and an open DB transaction, taking down AA processing for the whole network node — a remotely triggerable denial-of-service reachable by an unprivileged trigger sender to any AA (their own or a third-party AA) whose definition happens to create the specific bouncing/secondary interaction. This satisfies "a network unable to confirm new units" (AA processing halts network-wide on that node until manually restarted and the offending trigger reprocessed, deterministically re-crashing on retry).

### Likelihood Explanation
Reaching this specific combination requires an AA definition (author-controlled, and AA authors are effectively unprivileged — anyone can define and register an AA) that produces secondary triggers while in a bouncing state, or a bouncing secondary AA that still ends up producing a response unit. The multiple async layers (state-var formulas, balance/asset issuance, `readAADefinition`/`readAAStateVars` lookups, oracle data feeds) provide many potential ordering combinations not fully covered by tests, similar to how open5gs's issue only manifested "at a specific time." Exploitability requires crafting a definition/trigger sequence to hit the exact ordering, which is a Medium-likelihood, specialist-level condition, consistent with the CVE's own AC:H rating.

### Recommendation
Replace the `throw Error(...)` assertions in `aa_composer.js` finish() and handleSecondaryTriggers() (lines ~1674 and ~1719) with graceful error propagation via `revert()`/`bounce()`/`onDone()` so that any unreachable-in-theory state is converted into a bounced AA response (charged against the AA's own funds) instead of crashing the entire node process. Additionally, harden the global `uncaughtException` handler path so that AA-trigger-processing failures degrade to marking the specific trigger/unit invalid instead of unconditionally crashing the whole node.

### Proof of Concept
Concrete PoC could not be constructed without executing the formula/AA test harness to find the exact sequence of async callbacks needed to reach `bBouncing===true` at the `handleSecondaryTriggers` check or to produce a non-null `objResponseUnit` while `bBouncing && bSecondary` is true in `finish()`. This would require deploying a crafted AA (or chain of AAs) exercising `sendDummyUnit` → asset issuance failure → `bounce()` interleaved with a secondary trigger dispatch, and posting a trigger unit to it; due to the complexity of the async control flow (`aa_composer.js` lines 463-1799) and the lack of ability to run the test suite in this environment, this PoC path is flagged as **unverified** — the analog is based on static code-path analysis of the same bug class (unhandled/asserted error state on an asynchronously-arriving response) rather than a demonstrated crash trace.
