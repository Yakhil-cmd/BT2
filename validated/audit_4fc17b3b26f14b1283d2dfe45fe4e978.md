### Title
Webhook signature check is keyed to `repository.owner.login`/`organization.login` while every event handler acts on the unrelated `repository.full_name` field, letting a request "authenticated" for one GitHub organization drive writes on any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using only `repository.owner.login` (or `organization.login`) from the JSON body, but the event handlers that subsequently act on the same body key off the independent `repository.full_name` field, which is never checked for consistency with the verified owner.

### Finding Description
`verify_signature` computes the "organization" solely from `params.dig('repository','owner','login') || params.dig('organization','login')` and uses it to look up the `Shipit::GithubApp` instance to check against: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` explicitly treats an unconfigured `webhook_secret` as automatic success: `return true unless webhook_secret`. [3](#0-2) 

`webhook_secret` is documented and shipped as optional in every config template (`# nil`), so it is a realistic, unprivileged deployment state, not an edge case: [4](#0-3) [5](#0-4) 

Once the request clears `verify_signature`, `create` re-parses the same raw body and dispatches it to handlers based on the `X-Github-Event` header, with no re-binding to the verified owner: [6](#0-5) 

Every handler resolves the actual target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a completely separate field from the one used for signature verification: [7](#0-6) [8](#0-7) 

This is the same class of bug as the referenced Market.sol finding: the code validates/authorizes against one value (escrow balance / here, `repository.owner.login`) while acting on a different, unchecked value (liquidation fee amount / here, `repository.full_name`). Concretely: the equality the code should enforce is `verified_owner == full_name.split('/').first`, but this is never checked.

### Impact Explanation
If an attacker can get any organization name accepted by `Shipit.github(organization: ...)` (i.e., any org configured in `config/secrets.yml`, which is normal multi-tenant Shipit setup per `docs/setup.md` "Using Multiple Github Applications"), and that org has no `webhook_secret` configured (the documented default/optional state), the attacker can send an unsigned, unauthenticated POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = the secret-less org (so `verify_signature` trivially passes), and
- `repository.full_name` = `"<other-org>/<other-repo>"` for any real, tracked repository — including one whose own organization *does* have a secret configured.

Because handlers only look at `full_name`, this forges `push`, `status`, `check_suite`, `pull_request`, or `membership` events against a target repository/stack that the attacker never authenticated against. Depending on the handler this can enqueue a `GithubSyncJob` with an attacker-chosen `after` SHA, inject fake commit `Status` records, or trigger review-stack provisioning/PR handling — all cross-repository state changes driven by an unauthenticated actor, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the deployment to have at least one configured GitHub organization without a `webhook_secret` — which the shipped templates set to `nil` by default and the setup docs describe as optional — while another organization/repository is also being tracked. This is a plausible, commonly-encountered multi-org configuration, not a contrived edge case, and requires no credentials, GitHub App key, or repository access from the attacker: only knowledge of the secret-less organization's name (often public) and the target repository's `owner/name`.

### Recommendation
After `verify_signature` succeeds, re-derive the "verified organization" and require that `payload.dig('repository','full_name')&.split('/')&.first` (case-insensitively) equals the organization that was actually verified (or the org whose app's secret validated the signature), rejecting the request (422) otherwise. Alternatively, stop treating an absent `webhook_secret` as automatic pass-through in production configurations, or bind verification directly to the resolved `Repository`'s configured GitHub App rather than to a raw payload-supplied owner field.

### Proof of Concept
1. Configure Shipit with two orgs in `config/secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (has a real, tracked `Repository`/`Stack`, e.g. `orgB/prod-app`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": {"login": "orgA"}, "full_name": "orgB/prod-app" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")` → `verify_webhook_signature` returns `true` unconditionally because `orgA.webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
4. `Webhooks.for_event('push')` handler resolves the target via `payload.dig('repository','full_name')` = `"orgB/prod-app"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, `app/models/shipit/repository.rb:53-56`) and enqueues a `GithubSyncJob` for `orgB`'s real stack with the attacker's SHA, despite no valid signature ever being produced for `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
