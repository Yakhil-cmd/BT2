### Title
Missing Reentrancy Guard on `requestERC20Transfer` / `onERC20Received` Enables Duplicate Bridge Request Nonce Emission — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20` lacks `nonReentrant` on its deposit-side entry points (`requestERC20Transfer`, `onERC20Received`, and the internal `_requestERC20Transfer`). Because `requestNonce` is incremented **after** all external token calls, a registered ERC20 token that invokes `bridge.onERC20Received` during its own `transferFrom` (the 1-step bridge design) causes two sequential `RequestValueTransfer` events to be emitted with distinct nonces for a single user deposit. The destination bridge operators process both events and release tokens twice.

---

### Finding Description

`BridgeTransferKLAY` explicitly inherits `ReentrancyGuard` and marks both `handleKLAYTransfer` and `_requestKLAYTransfer` with `nonReentrant`. The comment in `BridgeFee.sol` even documents this requirement:

> `// Caller of this function must be nonReentrant.`
> `// - BridgeTransferKLAY._requestKLAYTransfer() is nonReentrant` [1](#0-0) 

`BridgeTransferERC20` does **not** inherit `ReentrancyGuard` and none of its deposit-side functions carry `nonReentrant`: [2](#0-1) 

The vulnerable execution path is:

**Step 1 — `requestERC20Transfer` pulls tokens via `safeTransferFrom`:** [3](#0-2) 

**Step 2 — If the registered token calls `bridge.onERC20Received` during `transferFrom` (the 1-step mechanism), `_requestERC20Transfer` is entered re-entrantly:** [4](#0-3) 

**Step 3 — Inside `_requestERC20Transfer`, `requestNonce` is read, the event is emitted, and only then incremented — all external calls (`_payERC20FeeAndRefundChange`, `burn`) happen before the increment:** [5](#0-4) 

Because `requestNonce++` is the last statement, the re-entrant call observes the same `requestNonce` value as the outer call. The re-entrant call emits `RequestValueTransfer` with nonce N and increments to N+1; when control returns to the outer call it emits `RequestValueTransfer` with nonce N+1 and increments to N+2. Two distinct, valid-looking events are produced for one deposit.

The same window exists through `_payERC20FeeAndRefundChange`'s own `safeTransfer` calls (to `feeReceiver` and back to `from`), which are also external calls before `requestNonce++`: [6](#0-5) 

`handleERC20Transfer` also lacks `nonReentrant`, but its nonce-replay is blocked by `closedValueTransferVotes` being set before the external call, so the handle path is not exploitable in the same way: [7](#0-6) 

---

### Impact Explanation

The destination bridge operators observe two `RequestValueTransfer` events with sequential nonces (N and N+1), both requesting `_value` tokens to the same recipient. Each nonce passes `_lowerHandleNonceCheck` and `_voteValueTransfer` independently. The destination bridge releases `_value` tokens twice — once per nonce — while the source bridge only received `_value + _feeLimit` tokens from the attacker. The attacker receives `2 × _value` tokens on the destination chain for the cost of `_value + _feeLimit` on the source chain, draining the destination bridge's liquidity pool (lock-and-release mode) or causing excess minting (mint-and-burn mode).

---

### Likelihood Explanation

The bridge is explicitly designed to support tokens that call `onERC20Received` during transfer (the 1-step deposit path). Any registered ERC20 token that implements this callback — including the reference `sc_erc20` token — triggers the condition when a user calls `requestERC20Transfer` instead of the 1-step path. The attacker is an unprivileged user; the only prerequisite is that the token is registered by the bridge owner, which is the normal operational state of the bridge.

---

### Recommendation

1. Add `nonReentrant` to `requestERC20Transfer`, `onERC20Received`, and `handleERC20Transfer` in `BridgeTransferERC20`, mirroring the pattern already applied in `BridgeTransferKLAY`: [8](#0-7) [9](#0-8) 

2. Apply the same fix to `BridgeTransferERC721` (`requestERC721Transfer`, `onERC721Received`, `handleERC721Transfer`), which has the identical structural problem: [10](#0-9) 

3. Move `requestNonce++` to **before** any external call as a defense-in-depth measure (checks-effects-interactions pattern).

---

### Proof of Concept

```
Preconditions:
  - TokenA is registered in the bridge on the source chain.
  - TokenA's transferFrom calls bridge.onERC20Received(from, to, value, feeLimit, data)
    after updating balances (standard 1-step bridge token design).
  - Destination bridge holds ≥ 10 TokenA as liquidity.
  - Attacker holds 6 TokenA on source chain (value=5, feeLimit=1, fee=0.5).

Attack:
  1. Attacker calls bridge.requestERC20Transfer(TokenA, dest, 5, 1, "0x").
  2. Bridge calls TokenA.safeTransferFrom(attacker, bridge, 6).
     → TokenA updates balances, then calls bridge.onERC20Received(attacker, dest, 5, 1, "0x").
  3. [Re-entrant] onERC20Received → _requestERC20Transfer:
       _payERC20FeeAndRefundChange: bridge sends 0.5 fee, 0.5 refund.
       emit RequestValueTransfer(..., nonce=0, ...);
       requestNonce++ → 1
  4. safeTransferFrom returns; outer _requestERC20Transfer continues:
       _payERC20FeeAndRefundChange: bridge sends 0.5 fee, 0.5 refund again.
       emit RequestValueTransfer(..., nonce=1, ...);
       requestNonce++ → 2

Source chain result:
  - Attacker net cost: 6 - 1 (refund×2) = 5 TokenA (approximately).
  - Two events emitted: nonce 0 and nonce 1, both for value=5 to dest.

Destination chain result:
  - Operators handle nonce 0 → release 5 TokenA to dest.
  - Operators handle nonce 1 → release 5 TokenA to dest.
  - Total released: 10 TokenA.

Net attacker gain: ~5 TokenA extracted from destination bridge liquidity.
```

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
