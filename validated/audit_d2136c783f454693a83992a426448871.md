## Title
Lockless in-memory unit/AA-definition cache reads racing against write-locked cache invalidation causes a crash-inducing "torn cache" read (analogous to CVE-2021-47394 unlink-before-delete UAF) - ([File: storage.js])

### Summary
CVE-2021-47394 is a UAF caused by `nf_tables` deleting a table object while a lockless `GET` handler (`nft_table_lookup`) still dereferenced it, because the `GET` path was never covered by the `commit_mutex` that serialized writers. `ocore` has the same class of defect: unit-validation reads of the in-memory unit/AA-definition caches (`storage.assocUnstableUnits`, `assocStableUnits`, `assocUnstableMessages`) are performed **without** holding the `"write"` mutex, while the writer path that mutates/clears those same caches (`writer.js`, `storage.resetMemory`, `archiving.js`, `joint_storage.js`) does hold it. The two paths use disjoint mutex keys, so they can interleave, and a validation flow can observe the caches mid-mutation and throw, crashing the node process.

### Finding Description
`validation.validate()` serializes only per-author addresses, not global cache writes: [1](#0-0) 

Meanwhile `writer.saveJoint()` (which mutates `storage.assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, `assocUnstableMessages`) is protected by a *different* mutex key, `"write"`: [2](#0-1) 

On any error inside `saveJoint`, still holding the `"write"` lock, the writer wipes and lazily rebuilds the entire unstable/stable unit caches via `storage.resetMemory`: [3](#0-2) [4](#0-3)  which in turn does a synchronous `delete` of every cached key before asynchronously re-querying the DB to repopulate them: [5](#0-4) 

`archiving`/`joint_storage.purgeUncoveredNonserialJoints` similarly runs under the `"write"` lock and calls `storage.forgetUnit()`, deleting `assocUnstableUnits[unit]`, `assocStableUnits[unit]`, `assocUnstableMessages[unit]`, etc.: [6](#0-5) 

None of these writer-side mutations are visible to, or excluded from, a concurrently-running `validate()` call for a *different* unit/author set, because `validate()` never takes the `"write"` lock. During that window, `storage.readUnitProps()` — called throughout parent/witness/author validation for every incoming unit — synchronously indexes into `assocStableUnits`/`assocUnstableUnits` with no lock and `throw`s if the expected entry is missing: [7](#0-6) [8](#0-7) 

The AA-trigger path is even more directly exposed: `storage.getUnconfirmedAADefinition()`/`getUnconfirmedAADefinitionsPostedByAAs()` iterate `assocUnstableMessages` and dereference `assocUnstableUnits[unit] || assocStableUnits[unit]`, throwing `"unstable unit "+unit+" not in assoc"` if the unit was concurrently forgotten/reset: [9](#0-8) 
This function is reachable purely from posting a unit that triggers or references an AA (`validateAATrigger`/AA composition flow), i.e. by any unprivileged AA trigger sender.

Because these are plain synchronous `throw Error(...)` calls buried inside `async.series`/callback chains that are not wrapped by the caller in a way that survives an unhandled exception, hitting this window crashes the Node.js process — a full node outage, matching the accepted "network unable to confirm new units" impact class, and structurally identical to the root cause pattern in the report: a mutation path (delete/unlink) that is not synchronized with a lock-free (or differently-locked) read path that still dereferences the object being torn down.

### Impact Explanation
An uncaught exception thrown from the hot validation/AA-trigger path (`readUnitProps`, `getUnconfirmedAADefinition`) crashes the entire hub/full node process. If this can be triggered reliably by ordinary unit/AA-trigger traffic timed against normal stabilization/archiving/rollback events (which are frequent and often triggered by ordinary, unprivileged unit posting), an attacker can repeatedly crash full nodes, denying the network's ability to validate and confirm new units — a High-severity availability impact.

### Likelihood Explanation
The race requires hitting a narrow interleaving window between (a) a writer-lock-held cache reset/forget operation (rollback on error, archiving of uncovered/bad units, or `shrinkCache`) and (b) a concurrent, differently-locked `validate()` call touching the same cached unit keys. `saveJoint` rollback (`resetMemory`), `purgeUncoveredNonserialJoints`, and `shrinkCache` (`setInterval(shrinkCache, 300*1000)`) all run periodically/opportunistically in normal node operation, and Node's callback-based async I/O (DB queries) naturally interleaves execution of unrelated unit validations. This makes the race plausible under sustained unit/trigger traffic, though it is timing-dependent rather than trivially deterministic — appropriate for Medium/High rather than trivial-always-reproducible.

### Recommendation
Ensure all mutations of `storage.assocUnstableUnits`, `assocStableUnits`, `assocStableUnitsByMci`, `assocUnstableMessages`, and `assocBestChildren` (in `writer.js`, `storage.resetMemory`/`forgetUnit`, `archiving.js`, `joint_storage.js`, `main_chain.js`) are mutually exclusive with respect to all readers of these structures, e.g. by having `validation.validate()` acquire the same `"write"` mutex (or a dedicated cache-rwlock) before doing any lockless cache reads, or by making cache invalidation atomic (rebuild-then-swap instead of delete-then-async-repopulate) so partial/empty states are never observable by concurrent readers.

### Proof of Concept
1. Start a full node processing normal unit traffic so that periodic `shrinkCache` (every 5 minutes) or an AA-trigger `saveJoint` rollback (`resetMemory`) is imminent.
2. Concurrently submit/trigger a unit whose validation path calls `storage.readUnitProps` or `storage.getUnconfirmedAADefinition` for a unit key that is being deleted/reset by the writer at that exact tick (e.g., time submission of a payment referencing a just-posted, not-yet-stable AA definition right as another AA trigger's validation fails and forces `resetMemory`, or right as `purgeUncoveredNonserialJoints`/`shrinkCache` fires).
3. Observe the thrown `Error("no unstable props of ...")` / `Error("unstable unit ... not in assoc")` propagating out of the async callback chain, crashing the node process.

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}
