### Title
`MembershipHandler#find_or_create_team!` finds an existing `Team` by `github_id` alone without verifying `params.organization.login` matches the stored `team.organization`, allowing cross-organization membership injection - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb#find_or_create_team!])

### Summary
`WebhooksController#verify_signature` selects the webhook secret to verify against using `repository_owner`, which for a `membership` event falls back to `params.dig('organization', 'login')` [1](#0-0) . This lets an attacker who legitimately controls org A produce a validly-signed `membership` webhook. `MembershipHandler#find_or_create_team!` then loads the `Team` row purely by `github_id` (`params.team.id`), ignoring that the payload's `organization.login` may differ from the `organization` already persisted on that `Team` [2](#0-1) . If the attacker supplies a `team.id` that collides with an existing `Team` belonging to a different, trusted organization (one listed in `Shipit.github_teams`), `team.add_member(member)` adds an arbitrary user to that trusted team [3](#0-2) [4](#0-3) , and `User#authorized?` checks membership in `Shipit.github_teams` by team `id`, not by organization [5](#0-4) .

### Finding Description
The binding the question asserts should hold is: `repository_owner` (used to pick the `webhook_secret` in `verify_signature`) == `team.organization` (the organization already stored on the `Team` row that gets mutated). Tracing the code shows this binding is never enforced on the "found" branch of `find_or_create_by!`.

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and validates the signature against that org's `webhook_secret` [6](#0-5) . For a `membership` event, `repository_owner` falls back to `params.dig('organization','login')` [1](#0-0) , i.e., whatever organization the attacker names in `payload.organization.login`. If the attacker owns org A and signs the payload with org A's real webhook secret, the signature check passes — this is a self-consistent, legitimate signature, not a forged one.
- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }` [2](#0-1) . The block (which sets `team.organization = params.organization.login`) only executes on **creation**. If a `Team` row with that `github_id` already exists (e.g., a trusted team belonging to org B, previously synced via `Team.find_or_create_by_handle` or a prior legitimate `membership` webhook from org B), `find_or_create_by!` returns the **existing** row unchanged — it does not check or update `organization`, and does not raise if `params.organization.login` (org A) differs from `team.organization` (org B).
- `process` then calls `team.add_member(member)` on that returned team where `member` is `User.find_or_create_by_login!(params.member.login)` [3](#0-2) , appending the attacker-specified `member.login` (which can be the attacker's own GitHub login) to `team.members` [4](#0-3) .
- `Shipit.github_teams` maps configured `oauth_teams` handles to `Team` records and is used purely by numeric `id`/foreign key relationship in `User#authorized?`: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) [7](#0-6) . Nothing in this check re-validates organization; it only checks the `Membership` join row exists for a team `id` in the trusted set.

Root cause: the `Team` lookup key (`github_id`, a GitHub-wide numeric team id, guessable/enumerable) is treated as sufficient proof of organizational identity, but the trust boundary (which webhook secret authenticated the request) is keyed by organization login, not by team id. These two identifiers are conflated only on Team creation and never reconciled afterward.

**Preconditions for exploitation** that must hold for the specific trusted `Team` row to already exist with the target `github_id`:
- A `Team` row for the victim org's trusted team must already exist in the database (created either via `Team.find_or_create_by_handle` from `Shipit.github_teams` configuration/rake task, or via a prior legitimate `membership` webhook from the victim org). This is a normal, expected condition for any Shipit instance actually using `Shipit.github_teams` authorization — such orgs must have their teams synced for the authorization scope to function at all.
- The attacker needs to know/guess the target team's numeric `github_id`, which the question posits is enumerable via GitHub's public API for public/visible teams.

### Impact Explanation
An attacker who owns an unprivileged, legitimately-registered GitHub App/organization (their own org A, configured in `Shipit.github_apps`, not in `Shipit.github_teams`) can add an arbitrary user (including themselves) as a member of a `Team` row belonging to a different, trusted organization B that IS in `Shipit.github_teams` — without ever touching org B's webhook secret. This directly escalates the attacker into `Shipit.github_teams` authorization via `User#authorized?`, satisfying "escalation into `Shipit.github_teams` authorization." Depending on how `require_permission!`/`authorized?` gates deploys, rollbacks, merges, and stack mutations elsewhere in the app, this authorization bypass can cascade into unauthorized deploys/rollbacks by the newly-"authorized" attacker account, making the ultimate blast radius potentially Critical (full Shipit authorization bypass) rather than merely High. The attack is repeatable for any trusted `Team` github_id the attacker can enumerate and is not limited to a single team/organization.

### Likelihood Explanation
Preconditions: (1) attacker must own/register their own GitHub App/org entry in `Shipit.github_apps` config (a barrier controlled by the Shipit operator's app configuration, not by GitHub — this is a nontrivial precondition since `Shipit.github_apps`/`github_app_config` is server-side configuration, not something an arbitrary GitHub user can add themselves to); (2) the target trusted `Team` row must already exist in the DB with a known `github_id`; (3) attacker must know or guess that numeric team id. Given (1) is a real constraint (the attacker needs to already be a legitimately configured tenant/org in this Shipit instance's config, not merely "any GitHub user"), likelihood is lower than a fully anonymous webhook forgery, but still realistic for multi-tenant Shipit deployments where multiple orgs' GitHub Apps are configured side-by-side and one tenant org attacks another tenant's trusted team.

### Recommendation
In `find_or_create_team!`, verify that the found `Team#organization` matches `params.organization.login` and reject/ignore the event (or raise) on mismatch, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "organization mismatch" unless team.organization == params.organization.login
  team
end
```
Additionally, `verify_signature` should not rely solely on `params.organization.login` as the trust anchor for events that mutate cross-organization-scoped records; consider validating that the webhook's asserted organization actually owns the referenced team/repository before processing.

### Proof of Concept
minitest in `test/models/webhooks/handlers/membership_handler_test.rb` (conceptual, per rules test would live under `test/` although out-of-scope per the audit rules list — described here for completeness):
1. Create `team_b = Team.create!(organization: 'org-b', github_id: 555, slug: 'trusted-team', name: 'Trusted Team', api_url: '...')`, and stub `Shipit.github_teams` to include `team_b`.
2. Build a `membership` webhook payload: `{ action: 'added', team: { id: 555, name: 'Trusted Team', slug: 'trusted-team', url: '...' }, organization: { login: 'org-a' }, member: { login: 'attacker' } }`.
3. Assert binding before: `params.dig('organization','login')` ('org-a') != `team_b.organization` ('org-b').
4. Invoke `Shipit::Webhooks::Handlers::MembershipHandler.call(payload)` directly (bypassing signature, since signature would pass legitimately for org-a).
5. Assert `team_b.members.reload.map(&:login)` includes `'attacker'` and `Membership.exists?(team: team_b, user: User.find_by(login: 'attacker'))` is true.
6. Assert `User.find_by(login: 'attacker').authorized?` is `true`, proving cross-org escalation into `Shipit.github_teams` despite the binding mismatch from step 3.
