### Title
`WebhooksController` authenticates a request against the organization derived from `repository.owner.login`, but `Webhooks::Handlers::Handler` (and `StatusHandler`) act on data keyed by a different, unverified field (`repository.full_name`, or no repository scoping at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` is used to validate the HMAC signature via `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once that HMAC check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the *entire, attacker-controlled JSON body* to the handlers. The base `Handler#stacks` / `Handler#repository_name` method resolves the target repository from a **different** field, `payload.dig('repository', 'full_name')` [1](#0-0) , and `StatusHandler#process` doesn't scope by repository at all - it updates `Commit.where(sha: params.sha)` globally [2](#0-1) . Neither of these fields is covered by, or cross-checked against, the field (`repository.owner.login`) that determined which organization's secret validated the signature.

### Finding Description
The signature check binds "organization that authenticated" to `repository.owner.login`: [3](#0-2) [4](#0-3) 

But the code that actually mutates state uses a different, unauthenticated field of the same payload:
- `Handler#repository_name`/`#stacks` uses `payload.dig('repository', 'full_name')` to look up the `Repository`/`Stack` that `PushHandler`, `PullRequest::*Handler`s, etc. operate on [1](#0-0) .
- `StatusHandler` doesn't consult the repository at all - it matches `Commit.where(sha: params.sha)` across the whole installation and calls `commit.create_status_from_github!(params)` [5](#0-4) [6](#0-5) .

In a Shipit deployment where multiple GitHub organizations/apps are configured (each with a distinct `webhook_secret`, selected by `Shipit.github(organization: repository_owner)`), any organization that legitimately possesses a valid webhook secret for its own GitHub App installation can produce a payload where `repository.owner.login` equals its own org (so the HMAC check passes with its own secret) while `repository.full_name` (for repo-scoped handlers) or the commit `sha` (for `StatusHandler`, which is not scoped by repository at all) refers to another organization's stack/commit. `CI` status controls deploy eligibility via `Commit#deployable?` -> `success? && !blocked?`, which is derived purely from `statuses`/`checks` records created by `StatusHandler`/`create_status_from_github!` [7](#0-6) .

This is the same class of bug as the report's core issue: a field that is *acted upon* is never checked against the field/identity that was *actually verified* - here, the "consumer/provider pairing" analog is "organization that authenticated" vs. "commit/repository actually written to."

### Impact Explanation
An attacker who controls (or has valid webhook credentials for) any single organization onboarded to a shared/multi-tenant Shipit instance can forge a `status` webhook that is HMAC-valid for their own org, but whose `sha` matches a commit belonging to a completely different organization's stack. Because `StatusHandler` performs no repository/stack scoping, this lets the attacker inject a fabricated `success` CI status onto another team's commit, satisfying `ci.require`/`deployable?` checks and enabling `Shipit` to proceed with (or allow a human to trigger) an **unauthorized deploy of an unreviewed/failing commit** - matching the "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability depends on the operational fact that Shipit is being run in a mode with more than one configured GitHub organization/app (each with its own `webhook_secret`), so that an attacker legitimately owns valid signing credentials for *an* org without owning the target org's credentials. Whether the reference deployment for this engine is single-tenant (one org, one secret) is not something I could fully confirm from the code alone (`Shipit.github`/`GithubOrganizationUnknown` implementation lives in `lib/shipit.rb`, which I was not able to inspect in full in this pass). If the engine is only ever run with a single organization's secret in practice, the "authenticated org != acted-upon org" split collapses since there is only one org to forge from, reducing this to a same-tenant integrity gap only (which is out of scope per the rules, since it wouldn't cross a credential boundary). This uncertainty should be resolved by reading `lib/shipit.rb`'s `Shipit.github`/organization-config resolution logic in full before treating this as confirmed multi-tenant-exploitable.

### Recommendation
Scope all webhook handlers (especially `StatusHandler`) to the repository/organization whose secret validated the signature, not to a raw field read out of the unauthenticated JSON body. Concretely: pass the verified `repository_owner` (or the whole verified `Shipit.github` context) from the controller into `Handler.call`, and require handlers - including `StatusHandler` - to filter their target `Commit`/`Repository`/`Stack` records by that verified organization before mutating them, rejecting any payload where `repository.full_name`'s owner segment does not match the organization that authenticated the request.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (as documented for multi-org support in `docs/setup.md`).
2. As an attacker who legitimately controls `org-a`'s GitHub App webhook secret, craft a `status` event body:
   ```json
   {
     "sha": "<sha-of-a-commit-belonging-to-org-b's-stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "org-a" } }
   }
   ```
3. Sign the raw body with `org-a`'s `webhook_secret` and POST it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"org-a"`, calls `Shipit.github(organization: "org-a")`, and the HMAC check passes using `org-a`'s legitimately-known secret [8](#0-7) .
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which ignores the `repository` field entirely and updates `Commit.where(sha: params.sha)` - a commit that belongs to `org-b`'s stack - creating a fabricated `success` status [2](#0-1) .
6. That fabricated status can satisfy `Commit#deployable?` for `org-b`'s stack, enabling an unauthorized deploy of that commit.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end

**File:** app/controllers/shipit/webhooks_controller.rb (L24-49)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
