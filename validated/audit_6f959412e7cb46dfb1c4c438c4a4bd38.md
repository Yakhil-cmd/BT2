### Title
Webhook signature is validated against a secret chosen from an attacker-controlled field that differs from the field used to dispatch the event, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` [1](#0-0) . However, every event handler resolves the actual `Stack`/`Repository` to act on using a **different** field of the same payload: `payload.dig('repository', 'full_name')` [2](#0-1) . Because both fields are attacker-controlled JSON body content (not independently bound to the signature choice), an attacker can construct a payload where `repository.owner.login` names an organization whose `webhook_secret` they know, while `repository.full_name` names a completely different repository/organization whose stack they want to manipulate.

### Finding Description
Shipit supports multiple GitHub App configurations, one per organization, each with its own `webhook_secret`, looked up via `Shipit.github(organization:)` → `github_app_config(organization)` [3](#0-2) . The webhook signature check does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) . The HMAC itself is computed over the full raw request body via `OpenSSL::HMAC.hexdigest` in `GithubApp#verify_webhook_signature` [5](#0-4) , so the signature does prove *some* organization's secret produced it — but the organization used to pick that secret is attacker-supplied via `repository.owner.login`, a field that is never cross-checked against `repository.full_name`, which is what all handlers (`PushHandler`, `StatusHandler`, PR handlers, etc.) actually use to look up the target `Repository`/`Stack` via `Repository.from_github_repo_name(repository_name)` [2](#0-1) .

This is the same class of bug as the analog: the check ("does this signature verify for organization X") does not bind to the same value that is acted upon ("which repository/stack does this event apply to"). An attacker who has legitimately configured/onboarded their own organization "attacker-org" in this Shipit instance (with a valid, known-to-them `webhook_secret`) can:
1. Craft an arbitrary webhook JSON body (e.g., a `push` event) with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`.
2. Sign the raw body with `attacker-org`'s webhook secret (which they legitimately possess, since it's their own org's GitHub App secret).
3. POST it to `/webhooks`; `verify_signature` picks `attacker-org`'s `GitHubApp`, validates the HMAC successfully, and the request passes.
4. `PushHandler#process` then looks up stacks for `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , forging a fake push/deploy-trigger event for a stack the attacker does not control at all.

### Impact Explanation
This does not on its own achieve RCE, but it does allow an attacker holding only a legitimate credential for their *own* onboarded organization to inject forged, "verified" webhook events (`push`, `status`, `check_suite`, PR events, `membership`) that are dispatched against **any other repository/stack** hosted by the same Shipit instance, purely by controlling the `repository.owner.login` vs `repository.full_name` mismatch in the payload. Depending on handler, this can trigger `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha` [7](#0-6) , forge commit statuses, or manipulate team membership via the `membership` handler (`MembershipHandler`) which trusts `params.organization.login`/`params.team` [8](#0-7) , potentially escalating into `Shipit.github_teams` authorization if the forged organization/team happens to be one of the configured `oauth.teams`. This crosses the required "cross-repository writes" / "escalation into Shipit.github_teams authorization" impact bar, but only in multi-organization deployments where an attacker legitimately controls at least one configured organization's webhook secret.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured with **multiple** GitHub App organizations (the per-organization `secrets.github` schema), and (b) the attacker to control/own at least one of those onboarded organizations (and thus know its `webhook_secret`, which they could legitimately obtain by being an admin of their own org's GitHub App installation). This is a plausible but non-trivial precondition — it is not a fully unprivileged, credential-free attacker in the strictest sense, but it does not require compromising the victim's credentials, a Shipit session, or an `ApiClient` token, and it does cross an organization-repository trust boundary the app is supposed to enforce. Confidence in exploitability is moderate: I confirmed the code paths precisely but could not execute the multi-org configuration to observe runtime behavior end-to-end.

### Recommendation
After the signature is verified using the organization-derived `GitHubApp`, the webhook payload's `repository.full_name`'s owner segment must be cross-checked against the `repository_owner` value used to select the verifying secret (i.e., reject if `full_name.split('/').first.casecmp(repository_owner) != 0`), or alternatively, the secret-selection should be scoped by looking up the `Repository`/`Stack` for `repository.full_name` first and verifying against *that* repository's associated organization's secret, rather than trusting the separate `repository.owner.login` field.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `attacker-org` (attacker controls the GitHub App and knows its `webhook_secret`) and `victim-org` (hosts a real, unrelated Stack, e.g. `victim-org/victim-repo`).
2. Attacker builds a JSON push-event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw JSON body, per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` semantics [5](#0-4) .
4. POST this to `/webhooks` with header `X-Github-Event: push`. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches that org's `GitHubApp`, and the signature verifies successfully [9](#0-8) .
5. `PushHandler#process` runs, looks up stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [2](#0-1)  and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — an event the attacker had no legitimate credential to send.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
