### Title
Unvalidated swap route pools can escape the intended authorization scope and steal unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy routes can place attacker-controlled pool code inside a transaction that already carries the account owner’s authorization. [1](#0-0)  The controller authorizes only one exact input-token transfer, but Soroban simulation can attach an additional `token.transfer(victim, attacker, amount)` sub-invocation beneath the victim’s signed controller authorization. [2](#0-1)  If the victim signs the simulated authorization tree without detecting that extra child, the route contract can transfer unrelated wallet tokens that were never supplied to XOXNO Lending. [3](#0-2) 

### Finding Description
`swap_tokens` accepts arbitrary opaque `swap` bytes, invokes the configured router, and guards the resulting call only by measuring the controller’s input spend and output receipt. [1](#0-0)  The explicit invoker authorization covers only `token_in.transfer(controller, router, amount_in)` and does not constrain what payload-selected external contracts request from the original human caller. [4](#0-3)  A route can therefore include an attacker-controlled contract whose `swap` method invokes `token.transfer(victim, attacker, amount)` on an unrelated Stellar asset. [5](#0-4)  During simulation, that nested authorization requirement is recorded beneath the victim’s existing `swap_collateral` authorization rather than being represented as a separate, clearly attributable top-level request. [6](#0-5) 

The repository’s own host-level test demonstrates the unsafe boundary: a benign route succeeds with a root-only authorization tree, while the rogue route fails only until the victim signs the additional transfer child. [7](#0-6)  Once that poisoned tree is signed, the unrelated wallet-token balance moves to the attacker while the lending strategy still succeeds. [3](#0-2) 

### Impact Explanation
This permits theft of user funds outside the intended swap amount, because the stolen asset need not be the collateral input, output asset, or an asset listed by the lending market. [8](#0-7)  The measured-output and overspend checks do not bound the loss, since they only inspect the controller’s balances of `token_in` and `token_out`. [9](#0-8)  The practical loss is the victim’s spendable balance of any unrelated token that the malicious route names and the poisoned authorization signs. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy the venue contract and craft a route referencing it, but exploitation requires the victim to submit that route and accept an authorization tree containing the unexpected transfer. [10](#0-9)  This is more constrained than a purely remote theft primitive because an honest signer that inspects the child invocation can reject it. [11](#0-10)  The issue nevertheless fits a Medium-severity authorization-scope escape: normal transaction simulation generates the signing payload, and the protocol boundary does not cryptographically distinguish the intended token pull from additional route-induced pulls. [12](#0-11) 

### Recommendation
Constrain routes to governance-approved venue contracts, or introduce a router-level callback isolation mechanism that prevents payload-selected contracts from resolving the original caller’s authorization for unrelated token transfers. [13](#0-12)  At minimum, expose the route’s venue addresses and require clients to reject any authorization sub-invocation other than the exact expected input-token transfer. [14](#0-13)  Wallets and SDK transaction builders should fail when the simulated controller authorization tree contains any unexpected `token.transfer` child. [15](#0-14) 

### Proof of Concept
1. The victim owns an XOXNO account holding USDC collateral and separately holds an unrelated wallet token. [16](#0-15) 
2. The attacker deploys a contract whose `swap` function calls `wallet_token.transfer(victim, attacker, wallet_balance)`. [5](#0-4) 
3. The attacker supplies a `swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap=malicious_route)` route that invokes that contract as a hop. [17](#0-16) 
4. Simulation records the unexpected wallet-token transfer as a child of the victim’s `swap_collateral` authorization. [6](#0-5) 
5. With a root-only signed tree, host authorization rejects the rogue transfer; after the victim signs the poisoned child, the attacker receives the victim’s entire unrelated wallet-token balance and the collateral swap still completes. [18](#0-17)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
