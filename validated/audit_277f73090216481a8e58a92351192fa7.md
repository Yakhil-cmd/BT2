This is a genuine analog: the multi-organization webhook signature verification binds the wrong entity — it authenticates against the organization named in the untrusted payload rather than the organization that owns the repository the handlers act on.

### Title
Webhook signature verification keys off an attacker-controlled `organization`/`repository.owner.login` field instead of the repository actually acted upon, allowing forged GitHub events for any stack when any configured organization lacks (or has a different) `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `GitHubApp`/`webhook_secret` to verify the inbound `X-Hub-Signature` against based on `repository_owner`, which is read straight out of the unauthenticated JSON body [1](#0-0) . That same body's `repository.full_name` field — a sibling field never itself covered by any secret-organization binding check — is what the actual handlers use to look up the target `Stack`/`Repository` and mutate state [2](#0-1) . Because `repository_owner` and `repository.full_name` are independent, attacker-controlled fields in the same JSON body, an attacker can pick an organization (whose slug they know or that is unconfigured) to authenticate the request while pointing `repository.full_name` at a completely different, victim-owned repository/stack.

### Finding Description
`Shipit.github(organization:)` looks up per-organization config via `github_app_config(organization)` and instantiates a `GitHubApp` keyed by that organization [3](#0-2) . `GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` whenever that organization's config has no `webhook_secret` set: `return true unless webhook_secret` [4](#0-3) .

The controller derives which organization to verify against purely from the untrusted payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

and uses it to select the verifying `GitHubApp`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [6](#0-5) 

If verification passes (or is trivially bypassed because the *claimed* org has no `webhook_secret` configured), `create` dispatches the **entire** raw payload — including whatever `repository.full_name` the attacker put in it — to the matching handlers unmodified:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

Handlers resolve the target stack from a *different* field of that same body — `repository.full_name` — with no re-check that it matches the organization used for signature verification:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

**Binding broken (as an equality):** the engine implicitly assumes `organization used to verify the signature == owner of the repository the handler mutates`. Since both are read from unauthenticated attacker-controlled JSON, an attacker can make them diverge:
- Before the attacker's request: signature verification is meant to prove "GitHub, on behalf of org X, sent this event about org X's repository."
- After the attacker's crafted request: `repository.owner.login = "org-with-no-secret"` (or an org whose secret the attacker already possesses through some unrelated hook) is used to pick the verifying `GitHubApp`, while `repository.full_name = "victim-org/victim-repo"` is what's actually acted on by `PushHandler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, etc.

This is only exploitable in a multi-organization Shipit deployment (`secrets.github` keyed by multiple org slugs, per `github_app_config`/`TOP_LEVEL_GH_KEYS` handling in `lib/shipit.rb`) where at least one configured organization has no `webhook_secret`, or where an attacker who legitimately controls one org's webhook secret (e.g., because they administer their own GitHub org connected to the same Shipit instance) can reuse it to forge events for a different org's repositories that Shipit also tracks.

### Impact Explanation
This crosses the "unauthorized deploy/rollback/merge" and "cross-repository writes" bar. Forged `push` events can queue `GithubSyncJob` for a stack that isn't the attacker's, forged `status`/`check_suite` events can flip CI state used as a merge/deploy gate, and forged `membership`/`pull_request` events can add/remove team membership or drive review-stack provisioning/deprovisioning — all against a stack whose actual owning organization's webhook secret was never checked, because verification was performed against a different, attacker-chosen organization's (absent) secret.

### Likelihood Explanation
Requires only that the Shipit instance is configured with multiple GitHub organizations (a documented, supported configuration per `TOP_LEVEL_GH_KEYS`/`github_app_config`) and that at least one has no `webhook_secret` set, or that the attacker has legitimate knowledge of one organization's secret. No privileged Shipit account, `ApiClient` token, or GitHub App key is needed — only the ability to send an unauthenticated HTTP POST to the public webhooks endpoint.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: verify using the organization owning `repository.full_name` (not a separately-controlled `repository.owner.login`/`organization.login` field), or re-validate after parsing that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers. Additionally, do not treat a missing `webhook_secret` for one organization as a global "verification not required" signal when other organizations in the same deployment do enforce secrets.

### Proof of Concept
1. Deploy Shipit tracking two orgs: `victim-org` (has `webhook_secret` configured, owns a tracked repo `victim-org/app`) and `attacker-org` (configured in the same `secrets.github` multi-org map but with no `webhook_secret`, e.g., left blank during onboarding).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any arbitrary value), body:
```json
{
  "repository": { "full_name": "victim-org/app", "owner": { "login": "attacker-org" } },
  "after": "<attacker-chosen sha>",
  ...
}
```
3. `repository_owner` resolves to `attacker-org` [5](#0-4) ; `Shipit.github(organization: 'attacker-org')` loads `attacker-org`'s `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [4](#0-3) .
4. `create` then dispatches the push handler with `repository.full_name = "victim-org/app"`, and `PushHandler`/`Handler#stacks` resolves `victim-org/app`'s real stack and queues `GithubSyncJob` for it [2](#0-1) , despite the request never being validated against `victim-org`'s actual `webhook_secret`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
