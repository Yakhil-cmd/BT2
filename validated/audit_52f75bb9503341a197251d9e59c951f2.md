### Title
Webhook signature verification is skipped for any GitHub organization configured without a `webhook_secret`, allowing unauthenticated forgery of `membership`/`push`/`status` events - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The external report describes a case where an unverified/attacker-influenced field (the destination address bytes going into `calcDestinationId`) controls a security-relevant derivation (the UUID) with insufficient guarantees. The structural analog in this engine is: the *organization* used to decide whether—and how—a webhook's signature is verified is itself read straight out of the unauthenticated request body, and if that organization's configuration has no `webhook_secret`, verification degenerates into an unconditional pass. The binding broken is **"organization authenticated" ≠ "repository/entity written."**

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config to validate against using a field taken directly from the still-unverified JSON body: [1](#0-0) [2](#0-1) 

That config is then handed to `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Note line 77: `return true unless webhook_secret`. If the organization resolved from the attacker-controlled `repository.owner.login` / `organization.login` field has no `webhook_secret` configured, signature verification is bypassed unconditionally — no HMAC comparison ever happens. This is not a hypothetical misconfiguration: leaving `webhook_secret` blank is an explicitly supported/documented configuration state, shown in the shipped templates and sample secrets files: [4](#0-3) [5](#0-4) 

Because the organization/repository claimed in the payload is never itself covered by a signature check in this branch, any of the built-in webhook handlers execute purely on attacker-supplied JSON. The `membership` handler in particular writes `Team`/`Membership`/`User` records straight from the payload (confirmed via `webhooks_controller_test.rb`, e.g. tests `":membership creates the mentioned team on the fly"`, `":membership can append an user membership"`): [6](#0-5) 

`Membership` records back `Shipit.github_teams`-based OAuth authorization for the whole Shipit instance, so forging a `membership` event for an org lacking `webhook_secret` lets an unauthenticated attacker add an arbitrary GitHub login to an authorized team.

### Impact Explanation
This crosses the authentication boundary the rules call out explicitly: escalation into `Shipit.github_teams` authorization, achieved without any Shipit session, `ApiClient` token, or valid `webhook_secret`. An attacker can also forge `push`/`status`/`check_suite` events for the same unsecured organization to enqueue `GithubSyncJob`, fabricate commit `Status` records, or influence check-run refresh state — all of which feed into deploy/lock decisions. The most severe consequence is silently granting OAuth-team membership to an attacker-chosen GitHub identity, which is a direct authorization escalation (High, per the stated impact bar).

### Likelihood Explanation
Requires only that at least one configured organization in the deployment's `github:` block has a blank/absent `webhook_secret` — a state the project's own templates and sample configs present as normal/expected rather than exceptional. No credentials, tokens, or prior access are needed; the attacker only needs to know (or guess) that organization's login and POST to the public `/webhooks` endpoint with the correct `X-Github-Event` header.

### Recommendation
Do not treat a missing `webhook_secret` as "verification passes." Either require `webhook_secret` to be present for every configured organization (fail closed / raise at boot if absent), or explicitly reject webhooks for organizations that have no secret configured instead of returning `true`. Additionally, resolve the verifying organization from a source that cannot be spoofed by the payload alone (e.g., cross-check against the installation/App context) rather than trusting `repository.owner.login` taken from the unauthenticated body.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `somegithuborg` (has `webhook_secret`) and `someothergithuborg` (blank `webhook_secret`, as shown in `config/secrets.development.shopify.yml`).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "someothergithuborg" },
  "team": { "id": 1, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'someothergithuborg')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. The `membership` handler processes the forged payload and creates a `Membership` for `attacker-github-login` on the `Admins` team, which — if that team is listed in `Shipit.github_teams` — grants the attacker authorized access to the Shipit instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
