### Title
Uncaught exception in chash length validation (`isChashValid`) causes unhandled crash when processing malformed addresses in units - (File: chash.js)

### Summary
`chash.isChashValid()` is the core buffer-resizing/length-computation routine used to validate every 32- and 33-length address string that flows through `ValidationUtils.isValidAddress()` / `isValidChash()` (unit authors, definitions, payment outputs, AA triggers, device addresses, etc.). Analogous to the libav bug — which crashed on a length mismatch during audio buffer resizing — `isChashValid()` decodes an attacker-controlled string into a buffer and then performs several length-dependent buffer transformations (`buffer2bin`, `separateIntoCleanDataAndChecksum`, `bin2buffer`) that `throw Error(...)` if the *decoded* buffer's bit-length isn't exactly 160 or 288, but this throw is **not** inside the function's own `try/catch` (only the initial decode step is guarded). [1](#0-0) 

### Finding Description
`isChashValid(encoded)` first checks that the *encoded string* has length 32 or 48 characters, then decodes it with `base32.decode` or `Buffer.from(encoded,'base64')` inside a `try/catch` that only guards the decode call itself: [2](#0-1) 

After that, it unconditionally calls `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)`. `separateIntoCleanDataAndChecksum` requires the resulting bit-string length to be exactly 160 or 288 or it `throw`s an uncaught `Error("bad length=...")`: [3](#0-2) 

A fixed character-length string (32 or 48 chars) does not guarantee a fixed *decoded byte length* for every valid base32/base64 alphabet input (e.g. base32 padding/case handling, or base64 strings containing padding `=` characters that still satisfy `isValidBase64`/length checks upstream but decode to fewer bytes than expected). Since the length re-check happens only *after* decoding and outside the `try/catch`, a crafted address string of the correct character length but an “off” decoded byte count causes an unhandled exception to propagate out of `isChashValid` → `isValidChash` → `isValidAddress`, functions that are called directly on untrusted, attacker-supplied fields during unit/author/AA validation.

### Impact Explanation
`isValidAddress`/`isValidChash` are invoked deep inside unit validation (author addresses, payment output addresses, AA trigger addresses, definitions) without every call site necessarily wrapping validation in a domain/try-catch boundary. An uncaught exception thrown mid-validation on a widely-reachable code path (any node validating a newly received/posted unit) can crash the Node.js process handling that unit. If the same malformed address is broadcast to all witnesses/hubs, it can cause a synchronized crash across nodes that attempt to validate the unit, i.e. the network becomes unable to confirm new units built on top of it — matching the CVE class of a crash caused by improper buffer-length handling.

### Likelihood Explanation
Exploitability depends on whether the underlying `base32`/`base64` decoding libraries can be coaxed into producing a decoded buffer whose bit-length differs from 160/288 while still satisfying the exact 32/48 character-length precondition checked earlier in `isValidChash`/`isChashValid`. This requires confirming exact decoder behavior (e.g., malformed padding, mixed case, or non-canonical base32 alphabet characters) — this could not be fully verified from the indexed code alone, and it is also uncertain whether every call site of `isValidAddress` in `validation.js` is wrapped by an outer try/catch that would turn this into a graceful `ifUnitError` instead of a process crash. This uncertainty should be resolved via targeted testing/fuzzing of `chash.isChashValid` with malformed but length-matching inputs before treating this as a confirmed high-likelihood issue.

### Recommendation
- Wrap the entire body of `isChashValid` (not just the initial decode) in a single `try/catch` that returns `false` on any exception, so malformed input is rejected rather than throwing.
- Explicitly re-validate the decoded buffer's byte length (20 or 36 bytes) immediately after decoding, before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, and return `false` (not throw) on mismatch.
- Audit all call sites of `ValidationUtils.isValidAddress`/`isValidChash` in `validation.js` to ensure none can leak an uncaught exception out of the validation pipeline.

### Proof of Concept
Conceptual PoC (requires confirming decoder edge case): construct a 48-character base64 string that passes `ValidationUtils.isValidBase64` (round-trips under `Buffer.from(...).toString('base64')`) but, due to padding characters, decodes to a `Buffer` whose bit length is not 288 (e.g. a string ending in extra `=` padding that some decoders truncate). Pass this as an `address` field of a unit's `author` or `payment` output and submit the unit for validation; if the decode still succeeds and the length check inside `separateIntoCleanDataAndChecksum` fails, the resulting `Error` propagates uncaught through `isChashValid → isValidChash → isValidAddress`, crashing the validating node process if no outer handler catches it.
