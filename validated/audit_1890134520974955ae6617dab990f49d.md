### Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / `webhook_secret` to verify a webhook's HMAC based on one JSON field (`repository.owner.login`, falling back to `organization.login`), but every event `Handler` (e.g. `PushHandler`) resolves the repository/stack to act on from a *different* field in the same payload (`repository.full_name`). Because these two fields are never checked for consistency, a valid signature from Organization A only proves "Organization A's secret signed this body" - it does not prove that the repository being mutated actually belongs to Organization A.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
with `repository_owner` derived directly from the untrusted, not-yet-verified JSON body: [2](#0-1) 

Once `verify_signature` passes, `create` dispatches the *entire* raw payload to handlers: [3](#0-2) 

All handlers derive the repository/stack to act on from `payload.dig('repository', 'full_name')`, via `Handler#repository_name`/`#stacks`: [4](#0-3) 

`Repository.from_github_repo_name` then splits `"owner/name"` on `/` to find the target `Repository`: [5](#0-4) 

`PushHandler` uses that repository's stacks to trigger a GitHub sync: [6](#0-5) 

PR handlers (`opened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`, `assigned_handler.rb`) likewise resolve the target repository from `params.repository.full_name`, independent of `repository.owner.login`: [7](#0-6) 

Shipit explicitly supports hosting multiple GitHub Apps/organizations behind one instance, each with its own `webhook_secret`, as shown in the multi-org test fixture: [8](#0-7) 

**The broken equality:** verification binds to `organization authenticated = params.dig('repository','owner','login')`, while the mutation binds to `repository written = params.dig('repository','full_name')`. Nothing in `verify_signature` or in the handlers checks that the owner segment of `full_name` equals `repository_owner`. Since GitHub's HMAC only proves "this body was signed with Org A's secret," and Org A's secret is legitimately known to Org A's own administrators/App owners in a multi-tenant Shipit deployment, an entity that controls Org A's GitHub App (and thus its `webhook_secret`) can sign an arbitrary JSON body - including one whose `repository.owner.login` is "OrgA" (to select and pass verification against OrgA's secret) but whose `repository.full_name` is `"OrgB/victim-repo"` (a repository belonging to a different, unrelated organization also hosted on the same Shipit instance).

### Impact Explanation
This breaks the trust boundary between organizations sharing one Shipit instance: a caller who legitimately controls only Organization A's GitHub App/webhook secret can forge push/pull_request/status events that are processed as if they originated from Organization B's repository, because handlers act on `repository.full_name` rather than the field that was actually cryptographically bound to the verifying secret. Consequences include:
- Triggering `stack.sync_github` (`PushHandler`) for stacks under an org the attacker does not control.
- Archiving/unarchiving/provisioning review stacks and mutating pull-request state (`opened_handler.rb`, `labeled_handler.rb`, etc.) for repositories outside the attacker's organization.

This matches the "cross-repository writes" Critical-impact category: a signature verified for one organization is used to authorize state changes against a repository belonging to a different organization.

### Likelihood Explanation
Exploitability depends entirely on the deployment hosting more than one GitHub organization's App/secret in the same Shipit instance (a configuration explicitly supported and tested, per `secrets_double_github_app.yml`). Given that precondition, no additional privilege beyond controlling one onboarded organization's own webhook secret is required - the attacker does not need any Shipit session, `ApiClient` token, or access to the victim org's GitHub App. This satisfies the rule's threshold of an unprivileged-attacker analog crossing an authentication boundary (organization authenticated vs. repository written).

### Recommendation
After signature verification succeeds, re-derive the "authenticated organization" and assert it matches the owner segment of `payload.dig('repository', 'full_name')` (and `payload.dig('organization', 'login')` where present) before dispatching to any handler. Reject the request (422) on mismatch, so the verified identity and the mutated resource are cryptographically the same entity.

### Proof of Concept
Conceptual sequence (assuming Shipit configured with `OrgA` and `OrgB`, per `secrets_double_github_app.yml`, and attacker legitimately administers `OrgA`'s GitHub App, hence knows `OrgA`'s `webhook_secret`):

1. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)`.
3. POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and verifies successfully because the attacker used `OrgA`'s real secret over the exact raw body.
5. `create` dispatches to `PushHandler`, which reads `repository.full_name = "OrgB/victim-repo"` via `Handler#repository_name`, resolves `OrgB`'s stacks, and calls `stack.sync_github(expected_head_sha: params.after)` - a state change on `OrgB`'s repository triggered using only `OrgA`'s credential.
