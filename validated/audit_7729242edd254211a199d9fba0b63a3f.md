### Title
Asset definer can unilaterally and instantly rewrite an asset's attestor list, causing unpredictable rejection of already-in-flight `spender_attested` payments from unprivileged holders - ([File: validation.js])

### Summary
For assets flagged `spender_attested`, the asset **definer** (a privileged role from the perspective of every holder/spender of the asset) is allowed to replace the entire attestor list at any time, with a single, immediately-effective `asset_attestors` message. There is no time lock, no restriction on how drastically the list may change, and no protection for outputs/payments that are already composed and broadcast but not yet stable. This exactly mirrors the reported `zAuctionAccountant.SetZauction()` pattern: a privileged party can change a critical dependency address list "without warning," and this change takes effect immediately for in-flight, not-yet-final transactions, forcing affected unprivileged users to redo their action.

### Finding Description
`validateAttestorListUpdate()` lets the single-authored `asset_attestors` message be posted by anyone who is the `definer_address` of the asset, with essentially no constraints other than list format/sorting: [1](#0-0) 

`checkAttestorList()` only validates length, address format and lexicographic ordering — it performs no comparison against the previous list, no minimum-notice period, and no restriction preventing the definer from dropping every previously-trusted attestor in one message: [2](#0-1) 

This update is dispatched from the generic message-validation switch with only a "one update per asset per unit" de-dup guard — no cooldown/timelock mechanism exists at all: [3](#0-2) 

Every payment referencing a `spender_attested` asset is validated against whatever the *current* attestor list happens to be (as of the payment's own `last_ball_mci`), via `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses`: [4](#0-3) 

and the actual acceptance check that fails the payment message if the spender/issuer is no longer attested: [5](#0-4) 

Because `asset_attestors` updates are ordinary units that can be composed and broadcast at any moment by the definer, a spender who was correctly attested at the time they composed and broadcast their payment can have that attestor removed by the definer before the payment stabilizes/finalizes on the DAG. When that happens, the payment message fails `spender_attested` validation and the unit becomes bad/rejected, exactly analogous to the reported issue where updating `zauction` "has the potential to fail acceptance of bids ... forces bidders to reissue their bids."

### Impact Explanation
Any unprivileged holder of a `spender_attested` asset who has an in-flight (unstable) payment can have that payment rejected at any time before finality, purely because the definer chose to revoke/replace attestors with no notice. This is not merely a cosmetic inconvenience:
- It forces users to redo their transactions (loss of time, extra fees, potential double-composition/nonce issues), the same concrete harm the original report flagged as material.
- It can be weaponized: a definer can watch the unstable DAG for a specific spender's in-flight transfer and immediately post an attestor-list change that removes that spender's attestor, selectively censoring or front-running specific counterparties' transfers of an asset they otherwise are entitled to move, similar to the "selectively censor... based on changing the active [config]" scenario in the source report.
- Because there is no minimum notice/timelock and no restriction on the scope of the change, legitimate users relying on the currently published attestor set have zero assurance their pending transaction will validate.

### Likelihood Explanation
Likelihood is high for the "unpredictable/negative side effect" case (definer changes attestors for legitimate reasons — compliance, key rotation — without realizing pending payments from currently-attested spenders exist) and moderate for the deliberate front-running case (requires the definer to be actively monitoring the unstable DAG for the target's asset transfers, which is straightforward since all this data is public in the DAG). No special privileges beyond being the asset's own definer are required, and `composeAssetAttestorsJoint` is a first-class composer API with no guard rails preventing rapid, drastic changes.

### Recommendation
- Require a mandatory time delay between broadcasting an `asset_attestors` update and its becoming effective for validation (e.g., only take effect after N mci beyond the unit that discloses it, similar to how `address_definition_change` already requires stability before use), giving in-flight spenders a grace window.
- Alternatively/additionally, snapshot the attestor list that applies to a `payment` message at the payment's own last-ball reference and require that snapshot to remain valid for a minimum window, rather than always re-checking against the most recent update up to `last_ball_mci`.
- Emit/require an explicit two-step "propose new attestors" + "commit new attestors" process (analogous to a 2-step ownership transfer) so wallets/UIs can warn spenders about pending attestor changes before they broadcast a payment.
- Validate that new attestor lists are not gratuitously emptied of previously-included addresses without justification (or at minimum surface the diff prominently to holders via the `asset_definition_saved`/attestor-change event stream so wallets can react before composing new payments).

### Proof of Concept
1. Definer D issues asset A with `spender_attested: true`, `attestors: [X]`.
2. Holder H (attested via X) composes and broadcasts a `payment` message spending asset A; the unit references `last_ball_mci = M` and passes the `spender_attested` check in `validatePayment` (validation.js:2115-2122) because X currently attests H.
3. Before H's unit is included/stabilized, D broadcasts an `asset_attestors` message removing X from the attestor list (validation.js:2829-2848, no timelock enforced).
4. If D's update stabilizes with an mci ≤ M relative to H's payment (a race the definer can win by simply acting quickly, since there is no cooldown), `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` (storage.js:1959-1992) no longer finds H attested, and H's already-broadcast payment fails validation and becomes bad, forcing H to reissue the transfer — with the definer able to repeat this at will against any specific spender with no warning or delay.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
