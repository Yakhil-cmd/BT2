This confirms the vulnerability chain. The key finding is that `Shipit.github(organization:)` selects the `GitHubApp`/`webhook_secret` purely from `repository.owner.login` (or `organization.login`) in the JSON body, while `Handler#stacks` (and thus `PushHandler#process` → `stack.sync_github` → `GithubSyncJob#perform`) resolves the target `Stack` purely from `repository.full_name` in the *same* JSON body. Nothing ties these two fields together.

### Title
Webhook signature verification is keyed on `repository.owner.login` while stack resolution is keyed on `repository.full_name`, allowing cross-tenant stack sync via a blank-secret org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and its `webhook_secret`) using `params.dig('repository','owner','login')`, but `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target repository/stack using `params.dig('repository','full_name')` from the exact same attacker-supplied JSON body. These two fields are never checked for consistency, so a single unauthenticated POST can pass signature verification under one (secret-less) organization while pointing `full_name` at a completely different, victim organization's repository/stack.

### Finding Description
The broken binding, as an equality that the code implicitly (and wrongly) assumes but never enforces: `organization_used_to_verify_signature == organization_of_stack_that_gets_synced`. In reality:
- `repository_owner` (used for verification) = `params.dig('repository','owner','login')` [1](#0-0) 
- `repository_name` (used for stack lookup) = `payload.dig('repository','full_name')` [2](#0-1) 

Both come from the same attacker-controlled JSON `POST /webhooks` body and are independent strings with no cross-validation that `full_name` starts with `owner.login`.

Verification flow: `verify_signature` calls `Shipit.github(organization: repository_owner)` to get a `GitHubApp`, then `github_app.verify_webhook_signature(signature, raw_post)`. `verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank: `return true unless webhook_secret` [3](#0-2) . This is a documented/supported per-organization config; `test/dummy/config/secrets.yml` and `secrets_double_github_app.yml` both configure orgs with `webhook_secret: # nil` [4](#0-3) , and multi-org configuration is an officially documented feature [5](#0-4) .

Exploit request: `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {"owner": {"login": "attacker-org-with-blank-secret"}, "full_name": "victim-org/private-repo"},
  "ref": "refs/heads/main",
  "after": "<sha>"
}
```
`verify_signature` looks up `Shipit.github(organization: "attacker-org-with-blank-secret")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header (attacker can omit/forge it). Verification passes. `WebhooksController#create` dispatches to `PushHandler.call(params)` [6](#0-5) . `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` where `stacks` resolves via `Repository.from_github_repo_name(repository_name)` using `full_name = "victim-org/private-repo"` [7](#0-6) , `Repository.from_github_repo_name` splits owner/name from that string and does a direct DB lookup [8](#0-7) . `stack.sync_github` enqueues `GithubSyncJob.perform_later(stack_id: id, expected_head_sha:)` [9](#0-8) , and `GithubSyncJob#perform` does `@stack = Stack.find(params[:stack_id])` and runs the full sync (fetches commits via `stack.github_api`, appends commits, may lock reverted commits, enqueues `CacheDeploySpecJob`) [10](#0-9) .

Existing guards fail because: `verify_signature` never checks that `full_name`'s owner segment matches `repository_owner`; `drop_unhandled_event` only checks event type presence, not payload consistency; `PushHandler`'s `ExplicitParameters` schema only requires `ref`/`after`, not that `repository.full_name`'s owner matches anything [11](#0-10) ; `Repository.from_github_repo_name` performs no ownership/tenant check, just a DB lookup by owner+name strings parsed from the attacker payload [8](#0-7) .

### Impact Explanation
An unauthenticated attacker who can send arbitrary HTTP to `/webhooks` can trigger `GithubSyncJob` (and, if `force_spec_cache`/other triggers apply, `CacheDeploySpecJob`) against any `Stack` belonging to any other configured GitHub organization, as long as at least one configured organization (any org, even the attacker's own if they can get it registered, or any org whose secret was left blank in `secrets.yml`) has a blank `webhook_secret`. This is a cross-tenant write: the sync job pulls commits via `stack.github_api` (the victim org's/Shipit's own GitHub App credentials, not the attacker's) and mutates the victim stack's commit history state, potentially unlocking/locking reverted commits and triggering cache/spec side effects — a payload sent "as" one repository mutating another repository's stack, matching the Critical category. This is repeatable per request against any known/enumerable `stack_id`/`full_name` and is not limited to a single tenant.

### Likelihood Explanation
Requires at least one `GitHubApp` in `Shipit.github_apps`/`secrets.github` configured with a blank `webhook_secret` — this is an explicitly supported, documented configuration (webhook secret is called "optional" in `docs/setup.md`) and appears in the dummy/test configs by default. No GitHub secrets, session, or API token are needed by the attacker; only knowledge of one org name with no secret configured and the target's `owner/repo` full name (often guessable/public knowledge). Cost is a single unauthenticated HTTP POST.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), require that the organization used to resolve/verify the webhook (`repository_owner`) matches the organization segment of `repository.full_name` before dispatching to handlers; reject the request (422) on mismatch. Additionally, consider requiring a non-blank `webhook_secret` for every configured `GitHubApp` in production, or verifying against the specific `GitHubApp` bound to the resolved `Stack`/`Repository`, not just the one named in the payload's `owner.login`.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
