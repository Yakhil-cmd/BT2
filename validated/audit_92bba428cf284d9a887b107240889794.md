### Title
Duplicate members in `r of set` / `weighted and` address definitions let a single signature satisfy multiple counted signing slots, bypassing the intended multisig threshold - ([File: definition.js])

### Summary
`Definition.validateDefinition` accepts `r of set` and `weighted and` definitions without checking that the `set` members are distinct, and `Definition.validateAuthentifiers`'s `sig` authentifier check verifies a signature only against the pubkey and the single unit-wide hash, not against the signing path. Combining these two facts, one real private key can satisfy two (or more) "independent" slots of a threshold definition by reusing the same signature at two different signing paths, defeating the security assumption that `required` distinct co-signers must approve a spend.

### Finding Description
`validateDefinition`'s handling of `r of set` and `weighted and` only checks structural constraints (`required` is a positive int `<= set.length`/`total_weight`, `set.length >= 2`, weights positive, etc.) — it never checks whether two entries of `args.set` are identical or reference the same underlying key/address: [1](#0-0) [2](#0-1) 

At authentication time, `validateAuthentifiers`'s `r of set`/`weighted and` evaluators simply iterate the set and count how many members independently validate: [3](#0-2) 

The leaf `sig` check does not bind the signature to its signing path at all — it verifies the supplied signature against `objValidationState.unit_hash_to_sign` (the same value for the whole unit) and the member's `pubkey`: [4](#0-3) 

Because ECDSA signature verification here is path-independent, if the same `["sig", {pubkey:P}]` leaf (directly, or indirectly through two `["address", A]` leaves pointing at the same address `A` whose definition is `["sig", {pubkey:P}]`) appears at two different positions of an `r of set` or `weighted and` set, a single signature produced once by the holder of `P` can be copied into the `authentifiers` map at both signing paths. Each occurrence independently returns `true` in the loop above, so both "slots" are counted as satisfied even though only one real, independent approval was actually produced.

This definition-construction path is reachable by any unprivileged address definer:
- When a self-custody user builds any address definition (their own address is just the chash of an arbitrary definition tree), duplication has no external victim.
- The exploitable scenario is a **shared/multisig address**, built cooperatively via `wallet_defined_by_addresses.js`. A malicious co-signer can propose a definition, e.g. `["weighted and", {required: 2, set: [{value:["address",A], weight:1}, {value:["address",A], weight:1}, {value:["address",B], weight:1}]}]`, where `A` is fully controlled by the attacker and `B` is the honest cosigner. `handleNewSharedAddress` only validates that each `signing_path → address` mapping matches the parsed definition and calls `Definition.validateDefinition`, none of which reject the duplicate member: [5](#0-4) [6](#0-5) 

The honest party sees "2-of-{A,A,B}, weight required 2" and reasonably (mis)reads it as "2 independent parties must sign", not realizing `A` occupies two slots. The attacker alone (holding only key `A`) can then produce a single signature, place it at both `A`-paths in `authentifiers`, and reach `weight = 2 >= required`, authorizing a spend from the shared funds without any participation or awareness of the honest cosigner `B`.

The project's own test-suite already demonstrates awareness of this general "duplicate authors/members" hazard for `is_valid_signed_package` (formula authors list), confirming duplicates are a recognized risk class in this codebase, but the fix was applied only to that specific formula op, not to `r of set`/`weighted and` member sets in `validateDefinition`: [7](#0-6) 

### Impact Explanation
This allows a single colluding/malicious co-signer of a jointly-created multisig (`r of set`/`weighted and`) shared address to unilaterally authorize spends that were represented to require multiple independent signers, resulting in unauthorized spending of funds that other legitimate members believed were protected by an N-of-M or weighted threshold. This is a concrete "unauthorized spending" outcome affecting real DAG-validated payments (the forged definition and its unit both pass `validateDefinition`/`validateAuthentifiers` in normal consensus validation), not merely a wallet-UI cosmetic issue.

### Likelihood Explanation
Requires an attacker to be one of the parties proposing/negotiating a shared address definition (a normal, permissionless flow available to any wallet user via `wallet_defined_by_addresses.js`) and to convince co-signers to accept a definition containing a subtly duplicated member (e.g., buried in a larger `weighted and`/`r of set` tree, or via nested `["address", innerAddr]` re-use). Detecting this by casual inspection of a printed definition tree is non-trivial for typical users, especially with deeper nesting, making the likelihood moderate.

### Recommendation
In `validateDefinition` (definition.js), when validating `r of set` and `weighted and` args, compute the canonical hash/serialization of every member (`args.set[i]` resp. `args.set[i].value`) and reject the definition if any two members are identical, or more strictly, reject if two members resolve (after following `address`/`definition template` indirection) to the same effective `sig`/`hash` leaf pubkey/hash. At minimum, reject exact structural duplicates within a single `set`.

### Proof of Concept
1. Attacker holds keypair for address `A` (definition `["sig", {pubkey: Pa}]`).
2. Attacker proposes a shared address with definition:
```
["weighted and", {
  required: 2,
  set: [
    { value: ["address", "A"], weight: 1 },
    { value: ["address", "A"], weight: 1 },
    { value: ["address", "B"], weight: 1 }
  ]
}]
```
   through `handleNewSharedAddress`/`createNewSharedAddress` in `wallet_defined_by_addresses.js`, presenting it to honest cosigner `B` as "requires 2 of 3 weighted shares."
3. `Definition.validateDefinition` accepts it — no duplicate check exists in the `weighted and` branch (definition.js:187-233).
4. To spend, the attacker signs the unit once with key `A`, and inserts that identical signature string at both signing paths corresponding to the two `["address","A"]` slots in `authentifiers`.
5. During validation, `validateAuthentifiers`'s `weighted and` evaluator (definition.js:713-732) calls the `sig` leaf evaluator twice (definition.js:734-754); both calls call `ecdsaSig.verify(unit_hash_to_sign, signature, Pa)`, which succeeds both times because verification does not depend on signing path.
6. Total counted weight = 2 ≥ `required` (2), so the unit is accepted as validly authorizing the spend from the shared address, even though cosigner `B` never signed and the attacker used only one real key.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);

			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
