### Title
Membership webhook handler creates `Membership` for a `Team` owned by a different GitHub organization than the one whose signature was verified - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the target `Team` solely by `params.team.id` (a GitHub team ID, globally unique across GitHub, not scoped to the organization that signed the webhook) and never checks that `params.organization.login` matches the `organization` column of the resolved `Team`. In a Shipit deployment configured with multiple GitHub organizations (each with its own `webhook_secret`), a user who controls one of those organizations can sign a `membership` webhook whose `organization.login` is their own org but whose `team.id` belongs to a `Team` row tied to a completely different (victim) organization already tracked in `Shipit.github_teams`, and get added as a member of that team.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`Shipit.github(organization: repository_owner).webhook_secret`'s owning organization == organization that actually owns `Team.find_by(github_id: params.team.id)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For a `membership` event there is no `repository` key, so `repository_owner` is taken directly from the attacker-controlled `organization.login` field, and the signature is checked against **that org's own configured `webhook_secret`** (`github_app_config(organization)` in `Shipit.github`) [3](#0-2) .
2. Because Shipit supports multiple GitHub organizations sharing one instance (`github_app_config`, `github_organizations`) [4](#0-3) , an attacker who administers *any one* configured organization can produce a validly-signed webhook using that org's own secret.
3. `MembershipHandler#find_or_create_team!` looks the team up **only** by `github_id` — `Team.find_or_create_by!(github_id: params.team.id)` — and only sets `team.organization` on first creation, never verifying it against `params.organization.login` on subsequent lookups [5](#0-4) .
4. `team.add_member(member)` then unconditionally appends the attacker-resolved `member` (`User.find_or_create_by_login!(params.member.login)`, itself just the attacker's own GitHub login) to that team's `members`, with no organization cross-check [6](#0-5) [7](#0-6) .

Existing guards do not catch this: `verify_signature` only proves the request was signed by *some* configured organization's secret, not that it matches the team referenced inside the payload; `drop_unhandled_event` and the `ExplicitParameters` schema only validate structural shape (`team.id`, `organization.login` types), not their mutual consistency.

### Impact Explanation
A successful forged webhook inserts a `Membership` row binding the attacker's GitHub account to a `Team` in `Shipit.github_teams`, which is the authorization set consulted by `User#authorized?`/OAuth team checks for granting access to Shipit stacks. This is a cross-tenant privilege escalation: an attacker who only controls their own (Shipit-registered) GitHub org can grant themselves membership in an authorization team belonging to a different organization served by the same Shipit instance, without any legitimate GitHub membership event ever having been emitted for that team. The exploit is repeatable per target `team.id` and is limited to Shipit deployments that configure more than one GitHub organization (multi-tenant `secrets.github` config).

### Likelihood Explanation
Exploitability requires: (a) the Shipit instance to be configured for multiple GitHub organizations, each with a distinct `webhook_secret` (`github_app_config`), and (b) the attacker to legitimately administer at least one of those configured organizations (so they can register/trigger a real webhook signed with that org's secret), and (c) knowledge of a target `team.id` that is already present or creatable in `Shipit::Team` (via `Shipit.github_teams`/`oauth_teams`) — GitHub team IDs are discoverable via GitHub's REST API for organizations the attacker can query. Given these preconditions this is a low-cost, fully repeatable HTTP POST to `/webhooks`.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and analogous team-membership handling), verify that `params.organization.login` matches the existing `Team#organization` for the resolved `github_id` before permitting `add_member`/`delete`; reject (or log and no-op) the event if they diverge instead of operating on a team owned by a different organization.

### Proof of Concept
Minitest plan (webhook handler test, no live GitHub):
1. Seed `Team.create!(github_id: 123, organization: 'victim-org', slug: 'ops', name: 'Ops', api_url: '...')`.
2. Build a membership payload: `{ action: 'added', team: { id: 123, name: 'Ops', slug: 'ops', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'attacker' } }`.
3. Invoke `Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call` (bypassing controller-level signature verification, as it is orthogonal — the point is that the handler itself has no cross-check).
4. Assert: `Team.find(...).organization == 'victim-org'` while `payload[:organization][:login] == 'attacker-org'` (the two diverge), and yet `Membership.exists?(team: team, user: User.find_by(login: 'attacker'))` is `true` after `process` — proving the handler creates the membership despite the organization mismatch.

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
