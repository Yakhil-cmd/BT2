### Title
Permanent market freeze from `scaled_to_original` i128 overflow during chunked accrual — a permissionless permanent-DoS on all market verbs - (File: common/src/rates/simulate.rs)

### Summary
The MySQL CVE class is an availability loss: a reachable code path crashes/hangs the service. The analog on XOXNO Lending is that every mutating pool verb accrues interest first, and accrual permanently panics with `MathOverflow` once `borrowed * borrow_index` exceeds the RAY value capacity — long before the `MAX_BORROW_INDEX_RAY` index ceiling engages. An unprivileged borrower/supplier pair can put a market on this trajectory by supplying and borrowing a large book at sustained high utilization on a steep rate curve. Once the cliff is reached, `update_indexes`, `supply`, `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, `flash_loan`, `flash_position`, and every router strategy that touches the market revert forever: supplier cash and borrower collateral are permanently frozen. The repo's own harness test reproduces the freeze end-to-end.

### Finding Description
`Pool` state mutators run `Cache::load → interest::global_sync → mutate → guards → commit`, so every entrypoint pays accrual up front [1](#0-0) . `global_sync` loops `accrue_chunk` per `MAX_COMPOUND_DELTA_MS` (1-year) window [2](#0-1) , and each chunk recomputes token-denominated values via `scaled_to_original(env, borrowed, borrow_index)` inside `accrue_step` [3](#0-2) .

`borrow_index` is monotone and only capped at `MAX_BORROW_INDEX_RAY = 10^36` raw [4](#0-3) . The product `borrowed_shares * borrow_index` is an `i128`; for a whale-scale book (`scaled` near the RAY capacity) at high utilization on a steep interest curve, the index growth pushes this product past `i128::MAX` while `borrow_index < MAX_BORROW_INDEX_RAY` — the cap that would have stopped growth never engages. `scaled_to_original` then panics with `MathOverflow` (error 33), which every subsequent accrual repeats because the panic happens before `last_timestamp` is re-stamped.

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: a ~1e9-token, 18-decimal market at 98% utilization on the XLM rate curve reaches the cliff within 40 simulated years, after which `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW` while the index is still below its cap [5](#0-4) . The docs acknowledge the mechanism — "Finite RAY value capacity can be exhausted before the index ceiling. Synchronizing an overlarge book can then fail" [6](#0-5)  — but no on-chain guard prevents the state: the utilization ceiling gate is skip-able/configurable (`with_max_utilization_disabled_all_markets` exists precisely because ceilings are governance parameters, not hard bounds), and even a normal high-utilization market simply takes longer to reach the same cliff. Because the freeze occurs inside accrual, there is no in-scope verb that can rescue the market afterward; `recapitalize`, `clean_bad_debt`, and even owner-routed calls that load the cache hit the same panic.

### Impact Explanation
Permanent freezing of user funds and a market that cannot operate: once the panic state is reached, no supplier can withdraw, no borrower can repay, and no liquidator can liquidate any position touching that market — every path accrues first. This matches the accepted "permanent freezing of funds" / "contract unable to operate" impact classes, and is the direct analog of the CVE's complete-DOS availability loss.

### Likelihood Explanation
Reachable by unprivileged actors: anyone can `supply` and `borrow` up to caps, and caps are the only mitigation. The attack requires either (a) a high-decimal, large-supply market sustained at high utilization for years, or (b) governance listing/configuring a market whose cap×decimals×rate product admits the overflow sooner. No privileged action, leaked key, or oracle dishonesty is needed — only time plus ordinary `supply`/`borrow` calls. The cost is capital lock-up rather than a fee, and the freeze is irreversible once triggered. Rated Medium: real permanent-freeze impact, but requires extreme scale/duration and governance-admitted caps.

### Recommendation
- In `accrue_step`/`update_borrow_index`, clamp the debt-value computation (`scaled_to_original` on `borrowed`) or saturate the borrow index at the largest value that keeps `borrowed * borrow_index` representable, so accrual degrades to zero-rate instead of panicking.
- Alternatively, make `global_sync` cap `borrow_index` at `min(computed, MAX_BORROW_INDEX_RAY, max_representable_index(borrowed))` before writing, preserving monotonicity while avoiding the `i128` product.
- As defense-in-depth, validate at listing/cap-setting time that `cap_scaled * index_growth_headroom` fits `i128` for the configured rate curve, and document the residual in the numeric-limits section.

### Proof of Concept
The repository already contains the executable reproduction at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360` [7](#0-6) :

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);             // unprivileged borrow, 98% util

loop {
    t.advance_time(YEAR_SECS);                  // accrual chunks
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// update_indexes, withdraw, and repay all revert with MATH_OVERFLOW (33)
// while last.borrow_index < MAX_BORROW_INDEX_RAY — the cap never engages.
```

Attack path for a single unprivileged address: `supply` a large balance of a high-decimal listed asset, `borrow` near the cap against supplied collateral in a second market, then let interest accrue (or keep re-borrowing to hold utilization high). After enough `MAX_COMPOUND_DELTA_MS` chunks, `accrue_step` panics in `scaled_to_original`, and every subsequent call touching that market — including third-party liquidations and `clean_bad_debt` — reverts permanently.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```
