### Title
Fee-on-Transfer Token Inflates Cross-Chain Transfer Amount in Bridge Lock Mode — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` calls `safeTransferFrom` with the nominal `_value + _feeLimit` but then passes the original `_value` unchanged into `_requestERC20Transfer`, which emits `RequestValueTransfer` with that nominal amount. If the registered ERC20 token applies a transfer fee, the bridge receives fewer tokens than `_value + _feeLimit`, yet the cross-chain event records the full `_value`. The counterpart bridge then releases the full `_value` to the recipient, draining more from its reserves than was actually deposited.

### Finding Description

In `requestERC20Transfer` (lock mode, zero bridge fee):

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The bridge assumes it received exactly `_value + _feeLimit`. For a fee-on-transfer token with rate `r`, it actually receives `(_value + _feeLimit) * (1 - r)`. No balance-before/after check is performed.

`_requestERC20Transfer` then emits the event with the original `_value`:

```solidity
// BridgeTransferERC20.sol L97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← nominal, not actual received
    requestNonce, fee, _extraData
);
```

The off-chain bridge relay (`node/sc/bridge_manager.go:handleRequestValueTransferEvent`) reads `valueOrTokenId` from this event and submits `handleERC20Transfer` to the counterpart bridge with the same nominal `_value`. The counterpart bridge then either mints or transfers `_value` tokens to the recipient — more than was deposited.

The same flaw exists in the `onERC20Received` (1-step) path: the token contract calls `onERC20Received(_from, _to, _value, ...)` with the nominal amount it attempted to send, but the bridge may have received less.

### Impact Explanation

In **lock mode** (`modeMintBurn = false`) with bridge fee = 0 and `_feeLimit = 0`:

1. Attacker calls `requestERC20Transfer` with a fee-on-transfer token (fee rate `r`).
2. Bridge receives `_value * (1 - r)` tokens.
3. No fee operations execute (no revert path).
4. `RequestValueTransfer` event is emitted with `_value`.
5. Counterpart bridge's `handleERC20Transfer` transfers `_value` tokens to the attacker's `_to` address.
6. Net gain per round-trip: `_value * r` tokens extracted from the counterpart bridge's liquidity reserves.

Repeated calls drain the counterpart bridge's ERC20 reserves proportional to the token's transfer fee rate. This is an unauthorized transfer of bridged assets from the counterpart bridge contract.

### Likelihood Explanation

- Any user can call `requestERC20Transfer` with any registered fee-on-transfer ERC20 token.
- No privileged role is required.
- The only prerequisite is that a fee-on-transfer token is registered on the bridge — a realistic scenario since the bridge is designed to support arbitrary ERC20 tokens.
- The attack is repeatable and scales linearly with the number of calls.

### Recommendation

Measure the actual received amount by comparing balances before and after the `safeTransferFrom`, and use that as the bridged value:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    // Derive actual _value and _feeLimit from actualReceived proportionally, or revert if insufficient
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

Alternatively, disallow registration of fee-on-transfer tokens via an explicit check in `registerToken`.

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token with a 10% transfer fee.
2. Register it on both the child-chain and parent-chain bridge contracts.
3. Ensure the parent-chain bridge holds 1000 tokens as liquidity (lock mode).
4. Call `requestERC20Transfer(token, attackerParent, 100, 0, "0x")` from the child chain.
   - Child bridge receives `90` tokens (10% fee deducted).
   - `RequestValueTransfer` event emits `valueOrTokenId = 100`.
5. Bridge relay submits `handleERC20Transfer(..., 100, ...)` to the parent bridge.
6. Parent bridge transfers `100` tokens to `attackerParent`.
7. Net: attacker deposited 90 tokens, received 100 — 10 tokens extracted from parent bridge reserves per call.
