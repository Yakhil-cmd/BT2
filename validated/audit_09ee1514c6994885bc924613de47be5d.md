### Title
Signature-selecting `repository_owner` and record-mutating `repository.full_name` diverge, letting a webhook signed for one GitHub organization unarchive/create a `ReviewStack` for an arbitrary victim repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using `repository_owner`, which falls back to `params.dig('organization','login')` when `repository.owner.login` is absent [1](#0-0) . `ReopenedHandler`, however, resolves the record to mutate purely from `params.repository.full_name`, a field independent of `repository.owner.login`/`organization.login` [2](#0-1) . In a multi-organization Shipit deployment where organizations carry different (or absent) `webhook_secret` values, an attacker can sign a payload with the secret (or lack thereof) of an organization they control while naming a victim repository in `repository.full_name`, causing `stack.unarchive!` to run against a repo/stack that never authenticated the request.

### Finding Description
The broken binding, stated as an equality that the code assumes but does not enforce:

`repository_owner_used_for_signature == organization_owning(repository.full_name)`

Trace:
1. `WebhooksController#create` first runs `verify_signature` as a `before_action`, which computes `repository_owner` from the *same* request body via Rails' automatic JSON parameter parsing: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
2. This `repository_owner` selects the `GitHubApp` instance via `Shipit.github(organization: repository_owner)` [3](#0-2) . For multi-org deployments, `Shipit.github` looks up a per-organization config via `github_app_config(organization)`, and each organization can have its own (or no) `webhook_secret` [4](#0-3) .
3. `GitHubApp#verify_webhook_signature` trivially returns `true` when that organization's `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) . So an attacker who controls (or targets) an organization entry with no configured `webhook_secret` bypasses signature verification entirely by setting `organization.login` to that org's name.
4. Once verification passes, `create` re-parses the raw body independently (`params = JSON.parse(request.raw_post)`) and dispatches to handlers [6](#0-5) .
5. `ReopenedHandler` resolves the target repository strictly from `params.repository.full_name` — a field the attacker can set to any `owner/repo` string, completely decoupled from whatever value was used to pick the signing secret [2](#0-1) . When `respond_to_pull_request_reopened?` is true (action is `"reopened"` and the repo's provisioning policy allows it), `process` calls `stack.unarchive!` on the `ReviewStackAdapter`-resolved stack for that arbitrary repository [7](#0-6) .

Existing guards do not close this gap: `drop_unhandled_event` only checks the event type, not payload consistency; `ExplicitParameters` (the `params do ... end` schema) enforces that `repository.full_name` is present and of type `String`, but never cross-checks it against `repository.owner.login` or `organization.login` used in `verify_signature` [8](#0-7) . There is no code anywhere that asserts the signing organization actually owns the repository named in the payload.

### Impact Explanation
The concrete demonstrable effect of this gap is that a webhook signed under organization A's secret (or an unsecured organization entry) can trigger `Stack#unarchive!`/`ReviewStack` creation for a repository that belongs to organization B, i.e., a payload for one repository mutating another's stack record — matching the "Critical: a payload for one repository mutating another's stack" category. This is a genuine confused-deputy/cross-tenant flaw rooted in the two independently-attacker-set fields (`repository.owner.login`/`organization.login` vs. `repository.full_name`).

One caveat: the question's framing ties this to `blocking_statuses`/`blocked?` gating deploys, but `ReopenedHandler` itself never touches status or blocking state — it only calls `stack.unarchive!`. That causal chain (forced status setting/clearing `blocked?`) belongs to a different handler (`StatusHandler`), not `ReopenedHandler`. So while the cross-tenant `ReviewStack` mutation via `ReopenedHandler` is real, the specific "forced status gates deploys via blocking_statuses" amplification described in the question is not supported by this handler's code and cannot be validated as part of this finding.

### Likelihood Explanation
Exploitability is conditioned on a **multi-organization** Shipit deployment (using the `github_app_config`/per-org secrets schema rather than the legacy single-org schema), because in the legacy single-org schema `Shipit.github` ignores the passed `organization` argument and always uses the one global `secrets.github` config [9](#0-8) , making `repository_owner` irrelevant to key selection. In multi-org setups, the attacker additionally needs an organization entry whose `webhook_secret` is blank/known to them, or one whose secret they can obtain independently (e.g., their own GitHub org integrated with Shipit). This is a real but non-trivial operational precondition; it is not exploitable against a single-tenant Shipit instance.

### Recommendation
Verify the webhook signature using the same repository/organization identity that handlers subsequently act on. Concretely, derive both the verifier-selecting organization and the handler's target repository from the same canonical field (`repository.owner.login`, requiring it to be present in the schema for all repo-scoped events), and reject any payload where the top-level `organization.login` (used only as a fallback) disagrees with the owner segment of `repository.full_name`.

### Proof of Concept
Not fully validated with a runnable minitest due to the multi-org config precondition needing an explicit Rails credentials fixture with two organizations (one with `webhook_secret` blank/known, one representing the victim); this would need to be set up in `test/controllers/webhooks_controller_test.rb`. Suggested assertions:
- Configure `Shipit.github_app_config` fixture with `attacker_org: { webhook_secret: nil }` and `victim_org: { webhook_secret: "victimsecret" }`.
- POST `/webhooks` with `X-Github-Event: pull_request`, body: `{"action":"reopened","number":1,"pull_request": {...}, "organization": {"login": "attacker_org"}, "repository": {"full_name": "victim_org/victim_repo"}, "sender": {"login": "attacker"}}`, no valid `X-Hub-Signature` (or one computed with no secret).
- Assert response is `200 OK` (signature check passed via attacker_org's blank secret).
- Assert `Shipit::Stack.find_by(repo_name: "victim_repo", repo_owner: "victim_org").review_stacks.find_by(...).archived?` is now `false`, proving the victim's stack was mutated by a request authenticated under `attacker_org`'s (non-)secret.

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
