### Title
Truncating `u16` cast in `EncodedExtensionHeader::from_input` causes undersized arena allocation and OOB/panic in `MemTrieNodeId::new_impl` - ([File: core/store/src/trie/mem/flexible_data/extension.rs])

### Summary
The hypothesized `usize` overflow in `RawEncoder::new`'s size summation inside `MemTrieNodeId::new_impl` does not occur — all header sizes are small compile-time constants and all `flexible_data_length()` values are derived from fields no larger than `u32`, so the sum cannot overflow `usize` on 32-bit or 64-bit builds. However, a closely related and genuinely exploitable defect exists one layer below: `EncodedExtensionHeader::from_input` in `core/store/src/trie/mem/flexible_data/extension.rs` computes the header's stored length via a silently truncating cast, `extension.len() as u16` [1](#0-0)  , with no bounds check comparable to the `debug_assert!` used in the sibling value header [2](#0-1) . Since `max_length_storage_key` is configured up to `4_194_304` bytes [3](#0-2) , an attacker-controlled extension (the shared-prefix nibble path between adjacent trie keys) can vastly exceed `u16::MAX` (65535), causing the encoded header length to wrap and desynchronize from the true data length used for the copy.

### Finding Description
`MemTrieNodeId::new_impl` allocates memory for `Extension`/`Leaf` nodes using `RawEncoder::new(arena, HEADER::SERIALIZED_SIZE + extension_header.flexible_data_length() + ...)` [4](#0-3) . The allocation size and the subsequent write size are both driven by `EncodedExtensionHeader::flexible_data_length()`, which simply returns the stored `length: u16` field [5](#0-4) . That field is populated by `from_input` via `extension.len() as u16`, an unchecked truncating cast [1](#0-0) .

An unprivileged account can reach this via ordinary `FunctionCall` actions invoking `storage_write`, which only enforces `max_length_storage_key`/`max_length_storage_value` (up to 4 MiB each) and charges gas per byte, with no bound tying key length to 65535 [6](#0-5) . By writing two (or more) keys that share a very long common byte prefix (near the 4 MiB maximum) and diverge only near the end, the in-memory trie construction/insertion logic (`generic_insert` / `TrieConstructor::add_leaf`) creates an `Extension` node whose nibble path length equals the shared prefix length, which can be far larger than 65535 bytes [7](#0-6) .

When such an extension is passed to `MemTrieNodeId::new_impl`:
1. `EncodedExtensionHeader::from_input` truncates the true length (e.g. ~4,000,000 bytes) into a much smaller stored `u16` value.
2. `RawEncoder::new` allocates a buffer sized using the truncated (small) `flexible_data_length()`.
3. `data.encode_flexible(&extension_header, extension)` computes `length = header.flexible_data_length()` (the truncated small value) and calls `header.encode_flexible_data(data, &mut self.data.subslice_mut(self.pos, length))` [8](#0-7) .
4. Inside `encode_flexible_data`, `target.raw_slice_mut().copy_from_slice(&extension)` is called with `target` sized to the truncated length but `extension` at its true, much larger length [9](#0-8) . `copy_from_slice` requires equal lengths and panics on mismatch, so in the common case this manifests as a deterministic panic (node crash) during transaction/receipt application rather than a silent out-of-bounds write, because Rust's slice-length assertions intervene before raw memory is touched.

None of the guarding checks in the code path (gas metering, `max_length_storage_key`, `debug_assert` used elsewhere for value headers) prevent an extension's byte length from exceeding `u16::MAX`, so the mismatch is fully attacker-reachable through ordinary `SetKey`/`FunctionCall` storage writes.

### Impact Explanation
This causes a deterministic panic in the runtime processing the transaction/receipt (`MemTrieNodeId::new_impl` → `encode_flexible` → `copy_from_slice` length-mismatch panic), crashing the node applying the chunk. Because this is a deterministic function of chain state and transaction content, every validator processing the same receipt would panic identically, which risks a chain stall on the affected shard — matching the "node panic / chain halt" NEAR bounty impact class. It is not confirmed to cause silent heap corruption (Rust's `copy_from_slice` bounds-checks lengths before writing), but the truncation itself is a distinct, unguarded defect independent of the hypothesized `usize` overflow.

### Likelihood Explanation
Feasible for any unprivileged account: it only requires submitting `FunctionCall` actions that perform two or more `storage_write` calls with keys sharing a very long common byte prefix (tens of thousands of bytes up to the ~4 MiB `max_length_storage_key` limit) that diverge near the end, forcing memtrie construction to produce an `Extension` node whose nibble-path length exceeds `u16::MAX`. The attacker pays gas proportional to key/value bytes written but the attack requires no elevated privileges, special contract permissions, or validator/operator access — fully repeatable by any RPC caller.

### Recommendation
Add explicit validation in `EncodedExtensionHeader::from_input` (and mirror the pattern already used in `EncodedValueHeader::from_input`) to assert/error if `extension.len() > u16::MAX as usize`, rejecting or safely erroring before truncation can occur. More generally, enforce a protocol-level invariant (ideally checked against `max_length_storage_key` at config-validation time) guaranteeing that no extension/leaf path byte length can ever exceed `u16::MAX`, and add a debug assertion in `RawEncoder::encode_flexible`/`encode_flexible_data` that the length used for the allocated slice always matches `data.len()` for the actual input.

### Proof of Concept
Unit test plan (to be added under `core/store/src/trie/mem/node/encoding.rs` or `core/store/src/trie/mem/flexible_data/extension.rs` tests):
1. Construct two keys of length just under `max_length_storage_key` (4,194,304 bytes) sharing a common prefix of length > 65,536 bytes, differing only in the last byte.
2. Insert both via the memtrie insertion path (`generic_insert`/`TrieConstructor`) so that an `Extension` node is created with nibble-path length exceeding `u16::MAX`.
3. Call `MemTrieNodeId::new_impl` (or the higher-level insertion API) with this extension and assert that either:
   - the process panics with a slice-length-mismatch inside `copy_from_slice` (reproducing the crash), or
   - after adding the recommended fix, the call instead returns a controlled error/rejects the operation rather than truncating silently.
4. Add a property/fuzz test sweeping extension lengths from 0 to `max_length_storage_key` to confirm `EncodedExtensionHeader::from_input` never silently truncates and that `flexible_data_length()` always equals the actual byte length passed to `encode_flexible_data`.
