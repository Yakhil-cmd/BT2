### Title
Api::CCMenuController#stack ignores the ApiClient's stack scope, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The `Api::BaseController` enforces that an `ApiClient` bound to a specific `stack_id` can only see that one stack, by scoping all stack lookups through `stacks` before calling `.from_param!`. `Api::CCMenuController` overrides `#stack` and looks the stack up directly with `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping. Any valid `ApiClient` token with `read:stack` permission — even one explicitly created for and restricted to a single stack — can therefore read the CCTray/CCMenu status (build/deploy state) of every stack in the installation, not just the one it was authorized for.

### Finding Description
`Api::BaseController` defines the authorization boundary between "the stack(s) a token authorizes" and "the stack a request touches": [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id`'s single stack when the client is scoped, and only falls back to `Stack.all` for unscoped clients. Every other API controller resolves `stack` (or `stacks`) through this method, so a scoped `ApiClient` (e.g. the `here_come_the_walrus` fixture, which is `belongs_to :stack` and limited to the `shipit` stack) cannot touch other stacks.

`Api::CCMenuController`, however, defines its own `#stack` that reimplements the lookup without going through `stacks`: [2](#0-1) 

This binding break is exactly analogous to the OKX report's pattern: a security-relevant constraint (`commissionRateLimit` checked against the wrong side, or a value validated on one path and consumed on another) is enforced on one code path (`BaseController#stack` via `stacks`) but a divergent, unchecked code path (`CCMenuController#stack`) is what's actually used to serve the request. The equality that should hold — "stack a token authorizes == stack a token touches" — is broken here for this controller only.

`require_permission :read, :stack` only checks that the client has the `read:stack` *permission string*; it says nothing about *which* stack(s) that permission applies to. The actual per-stack restriction is solely implemented via the `stacks`/`stack` scoping in `BaseController`, which `CCMenuController` bypasses.

The custom `authenticate_api_client` in this controller also allows authenticating purely via a `params[:token]` query string (as intended, for use in unauthenticated CI status badge URLs), which makes it more likely that such a token leaks or is shared outside its intended single-stack context: [3](#0-2) 

### Impact Explanation
This is a scope-authorization bypass: a token deliberately restricted by its creator to a single stack (`ApiClient#stack`) can be used to read the CI/build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status, etc.) of any stack in the Shipit instance, including private/internal stacks the token was never meant to see. This matches the in-scope High-impact category "unauthenticated read of stack state" for tokens that should be scoped — the token authenticates but reads state entirely outside its granted authorization boundary, which is a direct escalation of the token's authorized scope.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (the built-in `CCMenuUrlController` explicitly creates such scoped, `read:stack`-only tokens for CCTray/CI-status integrations, meant to be embedded in third-party CI dashboard tools): [4](#0-3) 

Because these URLs/tokens are designed to be handed to external CI monitoring tools (and are visible in plain query strings), the realistic threat model is precisely "holder of one stack's CCMenu token learns about/reads status of other stacks" — a lower-privilege leak scenario that the scoping mechanism was built to prevent.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, matching every other API controller's behavior and restoring the "token stack scope == stack touched" invariant.

### Proof of Concept
1. Create two stacks, `stack_a` and `stack_b`.
2. Create a stack-scoped `ApiClient` bound to `stack_a` with permission `read:stack` only (as `CCMenuUrlController#client` does for CCTray integration): [5](#0-4) 
3. Using that client's `authentication_token`, request `GET /api/stacks/stack_b/ccmenu.xml?token=<token>` (or via Basic Auth).
4. `authenticate_api_client` accepts the token (valid signature via `ApiClient.authenticate`), and `stack` resolves `stack_b` directly via `Stack.from_param!`, bypassing the `stacks` scoping that would have raised `ActiveRecord::RecordNotFound` for a client scoped to `stack_a`.
5. The response renders `stack_b`'s build/deploy status even though the token was only ever authorized for `stack_a` — confirmed by the fixture test that similarly proves the override reaches stacks outside any expectation of scope: [6](#0-5)
