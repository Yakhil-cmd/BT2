## Analysis

The reported CompoundV2 exploit is a classic **share/exchange-rate inflation attack**: the attacker becomes the sole depositor with a minimal share supply, silently donates underlying tokens directly to the vault (bypassing the mint accounting), which inflates the "assets-per-share" ratio, and forces the next depositor's share amount to round down to zero due to integer division — after which the attacker redeems the whole pool, stealing the victim's deposit.

Obyte's Autonomous Agent (AA) execution engine has the exact same primitive available to any unprivileged AA trigger sender: **a payment to an AA that does not match any `if` condition in its `cases` list is silently absorbed with no response and no state update**, per `aa_composer.js`'s "eat the received coins and send no response, state changes are still performed" path. [1](#0-0) 

The documented "Uniswap-like market maker" AA template (part of the repo's Sample Autonomous Agents catalog) implements a share-issuance vault whose share/asset ratio is computed exactly like CompoundV2's `exchangeRate`, and it is directly exposed to this donation gap. [2](#0-1) 

### Title
Share-Ratio Inflation via Silent Donation Absorption in Vault-style AA (CompoundV2-style Attack) - (test/samples/uniswap_like_market_maker.oscript, aa_composer.js)

### Summary
Any unprivileged AA trigger sender can replicate the CompoundV2 "inflation attack" against vault/market-maker style Autonomous Agents that compute share issuance as `investor_share_of_prev_balance * outstanding_shares`. The root cause is that Obyte's AA engine silently absorbs payments that don't match any `case`'s `if` condition, without minting shares or updating accounting state, allowing an attacker to "donate" tokens directly into the AA's balance and manipulate the ratio used for subsequent share calculations.

### Finding Description
In `uniswap_like_market_maker.oscript`, the "invest in MM" case computes issued shares as:
```
$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
``` [3](#0-2) 

`$bytes_balance` is read from the AA's live on-chain `balance[base]` state, which any address can inflate simply by sending it bytes. The trigger conditions for all cases require either `trigger.output[[asset=base]] > 1e5` or a nonzero asset/mm_asset output: [4](#0-3) [5](#0-4) 

so any payment of `base` at or below `1e5` with no other asset attached matches none of the `if` conditions. In that situation, `aa_composer.js` treats the trigger as having "no messages after filtering" and simply keeps the coins in the AA's balance, updating no state and sending no response: [1](#0-0) 

An attacker who is (or becomes) the sole shareholder can therefore repeatedly send sub-`1e5` "silent" donations of `base` directly to the AA address, growing `balance[base]` (the denominator `$bytes_balance`) far beyond what `var['mm_asset_outstanding']` (the numerator scale) reflects, without minting any additional `mm_asset` shares. When a genuine investor subsequently deposits through the normal "invest in MM" case, `$investor_share_of_prev_balance` becomes a very small fraction of the now-inflated `$bytes_balance`, and `round(...)` truncates the newly `$issue_amount` to zero for any deposit smaller than `bytes_balance / mm_asset_outstanding`. Because zero-amount outputs are filtered out by the AA engine, the victim's payment message contains no outputs, and per the "no messages after removing 0-outputs" path the AA again silently keeps the victim's funds with no shares returned to them: [6](#0-5) 

The attacker, still holding all outstanding `mm_asset` shares, then calls the "divest MM shares" case, redeeming 100% of the current `balance[base]`/`balance[$asset]` — which now includes the victim's stolen deposit — via `round($investor_share * balance[...])` with `$investor_share = 1`: [7](#0-6) 

### Impact Explanation
A victim's deposited funds (bytes and/or paired asset) are diluted to zero shares and can be fully drained by the attacker who controls all outstanding shares — a direct, unauthorized loss of AA-held user funds, mirroring the fund-theft impact of the CompoundV2 inflation exploit. This is a Medium/High severity fund-loss vector for any AA author who follows this documented ratio-based share-issuance pattern.

### Likelihood Explanation
The attack requires no special privileges: it only needs (1) being the first/sole depositor of a vault AA using this share formula, and (2) sending ordinary sub-threshold payments that any wallet can construct. Given that this pattern is presented as an official reference template for AA authors, any real-world AA cloned from it inherits the flaw, making exploitation straightforward for an attentive attacker monitoring newly deployed instances.

### Recommendation
- In the AA engine, consider making "no case matched" behavior explicit/rejectable rather than silently pooling funds with no accounting hook, or at minimum document this trap prominently since it is the root enabler of the donation attack (`aa_composer.js` around the "eat the received coins" logic).
- In vault-style AA templates (and the shipped sample), never derive share-issuance ratios from raw `balance[...]` reads that can be inflated by unaccounted-for direct transfers; instead track internal reserve variables (`var['reserve_base']`, `var['reserve_asset']`) that are only updated inside the AA's own state-update logic, immune to bare donations.
- Add a minimum-liquidity/burn-first-shares safeguard (as used in Uniswap V2 and later ERC4626 mitigations) so the first depositor cannot obtain an arbitrarily small share count relative to inflatable balance.

### Proof of Concept
1. Attacker deploys/uses the market-maker AA and calls `trigger.data.define` to create `mm_asset`.
2. Attacker sends the minimum initial investment (`base` slightly above `1e5` plus 1 unit of `$asset`) via the "invest in MM" case, becoming sole holder with `mm_asset_outstanding = issue_amount` (a small number). [8](#0-7) 
3. Attacker repeatedly sends plain payments of `base` with amount `≤ 1e5` and no other asset output to the AA address; each is silently absorbed into `balance[base]` with no case matched and no shares minted. [1](#0-0) 
4. A victim deposits through the normal "invest in MM" flow; `$issue_amount` rounds to 0 because `$bytes_balance` is now huge relative to `mm_asset_outstanding`; the victim's payment message ends up with zero-output and is dropped, so the victim receives no shares but their funds remain in the AA. [3](#0-2) 
5. Attacker calls "divest MM shares" with their full `mm_asset` balance (`$investor_share = 1`), draining 100% of `balance[base]` and `balance[$asset]`, including the victim's stolen deposit. [7](#0-6)
