### Title
Missing `nonReentrant` on `handleERC20Transfer` / `handleERC721Transfer` and `requestNonce` Incremented After External Calls in Bridge Transfer Contracts — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

### Summary

The Kaia service-chain bridge applies `nonReentrant` to `handleKLAYTransfer` and `_requestKLAYTransfer` but omits it entirely from the analogous ERC20 and ERC721 functions. Simultaneously, `_requestERC20Transfer` and `_requestERC721Transfer` increment `requestNonce` **after** external calls to token contracts, violating the checks-effects-interactions pattern for the nonce state variable. A semi-trusted registered token contract can exploit the external-call-before-nonce-increment ordering to emit two `RequestValueTransfer(Encoded)` events carrying the same `requestNonce`, corrupting the bridge's nonce sequence and causing a persistent DoS on the counterpart bridge's nonce-ordered processing.

### Finding Description

**Asymmetric reentrancy protection.** `BridgeTransferKLAY` inherits `ReentrancyGuard` and marks both `handleKLAYTransfer` and `_requestKLAYTransfer` as `nonReentrant`. `BridgeTransferERC20` and `BridgeTransferERC721` do not inherit `ReentrancyGuard` and apply no such modifier to any of their public or internal functions. [1](#0-0) [2](#0-1) [3](#0-2) 

**`handleKLAYTransfer` is `nonReentrant`; `handleERC20Transfer` and `handleERC721Transfer` are not.** [4](#0-3) [5](#0-4) [6](#0-5) 

**`requestNonce` incremented after external calls.** In `_requestERC721Transfer`, a low-level external call to the token contract (`_tokenAddress.call(...)`) is made at line 86 to retrieve the token URI. The `requestNonce++` increment does not occur until line 105, after this external call and after the optional `burn` call: [7](#0-6) 

The same pattern exists in `_requestERC20Transfer`, where `_payERC20FeeAndRefundChange` makes external ERC20 `safeTransfer` calls before `requestNonce++`: [8](#0-7) 

The `BridgeFee.sol` comment explicitly acknowledges that `_payKLAYFeeAndRefundChange` requires its caller to be `nonReentrant`, but no equivalent protection is applied to `_payERC20FeeAndRefundChange` or its callers: [9](#0-8) 

**`onERC721Received` is public with no access control beyond `onlyRegisteredToken(msg.sender)`.** Any registered token contract can call it directly without actually transferring an NFT: [10](#0-9) 

### Impact Explanation

**Reentrancy attack path (non-mintBurn mode):**

1. A registered ERC721 token's `tokenURI` implementation calls `bridge.onERC721Received(from, tokenId, to, extraData)` during the low-level call at line 86 of `_requestERC721Transfer`.
2. `onERC721Received` calls `_requestERC721Transfer` again. At this point `requestNonce` is still N (not yet incremented).
3. The inner call emits `RequestValueTransferEncoded` with nonce N and increments `requestNonce` to N+1.
4. The outer call resumes, emits a second `RequestValueTransferEncoded` also with nonce N (the value it read before the inner call), and increments `requestNonce` to N+2.
5. Result: two events with nonce N are emitted; nonce N+1 is permanently skipped.

The counterpart bridge's `_lowerHandleNonceCheck` and `_updateHandleNonce` advance `lowerHandleNonce` sequentially. A gap at N+1 can stall processing of all subsequent nonces (N+2, N+3, …), causing a persistent DoS on the bridge's value-transfer pipeline and preventing users from withdrawing bridged assets. [11](#0-10) 

### Likelihood Explanation

The trigger is a registered ERC721 (or ERC20) token contract — a semi-trusted actor. The bridge owner registers tokens, but a token contract that is later upgraded, has a delegatecall vulnerability, or is intentionally malicious can exploit this. The `onERC721Received` entry point is `public` with no additional guard, making the reentrant call straightforward once a registered token is the `msg.sender`. The `_requestKLAYTransfer` path is explicitly protected; the ERC20/ERC721 paths are not, making this an oversight rather than a design choice.

### Recommendation

1. Add `ReentrancyGuard` inheritance to `BridgeTransferERC20` and `BridgeTransferERC721` and apply `nonReentrant` to `handleERC20Transfer`, `handleERC721Transfer`, `requestERC20Transfer`, `requestERC721Transfer`, `onERC20Received`, and `onERC721Received`.
2. Move `requestNonce++` to **before** any external call in `_requestERC20Transfer` and `_requestERC721Transfer` (checks-effects-interactions).
3. Add access control to `onERC20Received` and `onERC721Received` so they can only be called by registered, unlocked token contracts (not arbitrary callers).

### Proof of Concept

```solidity
// MaliciousERC721: registered on the bridge by owner
contract MaliciousERC721 is ERC721 {
    Bridge public bridge;

    // Called by bridge during _requestERC721Transfer (line 86)
    function tokenURI(uint256 tokenId) public view returns (string memory) {
        // Re-enter bridge with same tokenId before requestNonce is incremented
        bridge.onERC721Received(
            tx.origin,   // _from
            tokenId,     // _tokenId
            tx.origin,   // _to (attacker receives on counterpart chain)
            ""           // _extraData
        );
        return "";
    }

    function transferFrom(address from, address to, uint256 tokenId) public {
        // Simulate transfer (bridge holds the token)
        _transfer(from, to, tokenId);
    }
}

// Attack:
// 1. Owner registers MaliciousERC721 on bridge
// 2. Attacker calls bridge.requestERC721Transfer(maliciousToken, to, tokenId, "")
// 3. Bridge calls maliciousToken.transferFrom(attacker, bridge, tokenId) — succeeds
// 4. Bridge calls _requestERC721Transfer → calls maliciousToken.tokenURI(tokenId)
// 5. tokenURI re-enters bridge.onERC721Received → emits RequestValueTransferEncoded(nonce=N)
//    requestNonce becomes N+1
// 6. Outer _requestERC721Transfer resumes → emits RequestValueTransferEncoded(nonce=N) again
//    requestNonce becomes N+2
// Result: two events with nonce N; nonce N+1 permanently skipped;
//         counterpart bridge stalls on missing nonce N+1.
