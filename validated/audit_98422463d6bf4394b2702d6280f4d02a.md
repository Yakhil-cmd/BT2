### Title
Webhook signature verification uses `repository.owner.login`/`organization.login` while stack mutation uses `repository.full_name`, allowing signature-bypass via an unconfigured organization to mutate another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify against using `repository_owner`, which reads `params.dig('repository','owner','login')` (falling back to `organization.login`). `Webhooks::Handlers::Handler#repository_name`/`PushHandler#process`, however, resolve the target stack using the independent field `payload.dig('repository','full_name')`. Because both fields live in the same attacker-controlled raw JSON body and are never cross-validated, an attacker can name an unconfigured organization in `repository.owner.login` (or in `organization.login` if `repository` is omitted from the signature-check path) to get `verify_webhook_signature` to return `true` unconditionally, while pointing `repository.full_name` at a real, secret-protected organization's stack.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`organization_that_verified_signature (derived from repository_owner) == organization_that_owns_the_mutated_stack (derived from repository.full_name)`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` via [1](#0-0) , then calls `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(...)` at [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank for that organization: [3](#0-2) . `@webhook_secret` is set from per-organization config in `initialize`: [4](#0-3) .
3. On success, `#create` re-parses the same raw body and dispatches to handlers: [5](#0-4) .
4. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a field completely independent of the one used for signature-org selection: [6](#0-5) .
5. `PushHandler#process` uses that resolved `stacks` relation and calls `stack.sync_github(expected_head_sha: params.after)`: [7](#0-6) .
6. `Repository.from_github_repo_name` looks up by owner/name parsed straight from `full_name`, with no reference back to `repository_owner`/`organization.login` used earlier: [8](#0-7) .

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: push`, any `X-Hub-Signature` value (garbage accepted since B has no secret), and a JSON body containing `{"repository": {"owner": {"login": "B"}, "full_name": "A/some-repo"}, "organization": {"login": "B"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}`. Because `repository.owner.login` is `"B"` (an org with no `webhook_secret` configured in Shipit), `verify_signature` selects B's `GitHubApp`, whose `verify_webhook_signature` short-circuits to `true` for any signature. The handler then ignores `repository.owner.login`/`organization.login` entirely and resolves the target stack solely from `repository.full_name = "A/some-repo"`, invoking `sync_github` on organization A's real stack — an org whose secret was never checked.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is a handled kind, not payload consistency; `ExplicitParameters` schema for `PushHandler` only requires `ref` and `after` are present, not that `repository.owner.login == repository.full_name`'s owner; there is no code anywhere that cross-validates `repository_owner` (used for the security decision) against `repository.full_name` (used for the mutation).

### Impact Explanation
An attacker with no privileges on organization A and no knowledge of A's `webhook_secret` can force organization A's stack to execute `sync_github`, causing Shipit to sync/mutate A's stack state (commits/tasks) based on attacker-supplied `ref`/`after` values, while the signature check was performed vacuously against an unrelated, secret-less organization B. This is a full authentication-bypass class finding: a payload nominally "belonging" to B mutates A's stack. It's repeatable against any repository/stack whose owning organization does not itself need to be configured — the attacker only needs Shipit to have at least one organization entry with no `webhook_secret` (or no entry at all, which also returns `true` unless `Shipit.github` raises `GithubOrganizationUnknown` for genuinely unknown orgs — in which case the attacker can instead use any org that IS configured but happens to have no `webhook_secret` set). Matches the Critical category: "a payload for one repository mutating another's stack ... with no authentication."

### Likelihood Explanation
Preconditions: Shipit must have at least one configured GitHub organization entry with a blank/absent `webhook_secret` (the config explicitly supports this via `@webhook_secret = @config[:webhook_secret].presence`), and the target organization A must have `webhook_secret` set (typical, since the question specifies this). The attacker cost is a single unauthenticated HTTP POST with a crafted JSON body — no GitHub credentials, no Shipit session, no secrets required. This is trivially repeatable against any repository/stack in the Shipit instance since `sync_github` can be invoked repeatedly with arbitrary `ref`/`after` values.

### Recommendation
Cross-validate the organization used for signature verification against the organization that owns the resource being mutated before dispatching to handlers — e.g., require `repository.owner.login` (or `organization.login`) used in `verify_signature` to match the owner parsed from `repository.full_name` in the same payload, rejecting mismatches with a 422. Additionally, `GitHubApp#verify_webhook_signature` should not vacuously return `true` when `webhook_secret` is blank; either require every configured organization to define `webhook_secret`, or treat a missing secret as "reject all webhooks for this org" rather than "accept all."

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.github_app` with two orgs: `A` with a real `webhook_secret` (e.g., `'secretA'`) and `B` with no `webhook_secret` configured.
2. Create `Stack` for repository `A/some-repo`.
3. Stub/spy `Stack#sync_github` (e.g., via `Minitest::Mock` or `expects`) to assert it is called with the attacker's `expected_head_sha`.
4. Build a JSON body: `{"ref": "refs/heads/master", "after": "deadbeef", "repository": {"owner": {"login": "b"}, "full_name": "A/some-repo"}, "organization": {"login": "b"}}`.
5. POST `/webhooks` with headers `X-Github-Event: push` and `X-Hub-Signature: sha1=garbage` (any bogus signature).
6. Assert response is `200 OK` (not `422`), proving signature check passed against B's (secret-less) app while the payload targeted A's stack: `assert_response :ok`.
7. Assert `Stack#sync_github` was invoked on the `A/some-repo` stack with `expected_head_sha: 'deadbeef'` — proving the equality `verifying_org (B) != owning_org (A)` and demonstrating cross-tenant mutation without authenticating A's identity.
