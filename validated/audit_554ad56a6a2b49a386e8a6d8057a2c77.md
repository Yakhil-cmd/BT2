### Title
Webhook Organization/Repository Binding Break — Signature Verifies `repository.owner.login`, Handlers Act on Unverified `repository.full_name` — (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` (`lib/shipit/github_app.rb`). `WebhooksController#verify_signature` selects the correct `GitHubApp` (and therefore the correct HMAC secret) using `repository_owner`, which is computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). However, the field actually used afterwards by every repository-scoped webhook handler (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`'s underlying commit lookup, `CheckSuiteHandler`, pull-request handlers, etc.) is the independent `repository.full_name` field of the same JSON body. Nothing ties `repository.full_name` to `repository.owner.login`/`organization.login` — the signature only proves the request was signed with *an org's* secret, not that the specific repository referenced by `full_name` belongs to that org.

### Finding Description
The binding that should hold is:
`organization authenticated via webhook_secret(repository_owner) == repository (by full_name) actually written to`

In `verify_signature`:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This value picks which `Shipit.github(organization: ...)` config (and thus which `webhook_secret`) is used to validate `X-Hub-Signature`.

But every handler that mutates state (`PushHandler#process`, and `Handler#stacks`/`#repository_name` shared by other repo handlers) resolves the target repository from a *different, independently attacker-controlled* field:
```
def repository_name
  payload.dig('repository', 'full_name')
end
```

Because a JSON payload can freely set `repository.owner.login` to organization A (whose secret the attacker holds/controls, e.g. their own installed GitHub App or a compromised low-privilege org) while setting `repository.full_name` to `"B/other-repo"` belonging to organization B, the signature check passes (it only verifies against A's secret) but the handler acts against B's repository/stacks. `Repository.from_github_repo_name(repository_name)` in `Handler#stacks` does not re-check that the repository's registered owner matches `repository_owner`.

### Impact Explanation
An attacker who legitimately controls (or has obtained, through any means not covered by "GitHub App private key/webhook secret theft") a valid GitHub App webhook signature for *any* organization configured in Shipit (for example, they administer their own GitHub org "A" that is also configured in the same multi-org Shipit instance) can craft a `push` webhook whose `repository.owner.login` is `A` (so it signs/validates against A's secret) but whose `repository.full_name` is `B/production-repo`. `PushHandler` will then call `stack.sync_github(expected_head_sha: ...)` for stacks belonging to `B`'s repository — triggering Shipit to fetch/resync history and potentially cache/execute a `shipit.yml` for a repository the attacker's org does not own, and other repo-scoped webhook handlers (pull_request handlers, check_suite handler) are similarly reachable this way. This lets an org whose webhook secret is only meant to authorize events for its own repositories instead drive Shipit behavior (sync, PR/label/merge-status side effects, deploy-triggering CI writes) for an unrelated, cross-organization repository, i.e., a cross-repository/cross-organization write not authorized by the signature that was actually checked.

### Likelihood Explanation
Exploitability requires the attacker to control at least one organization/app installation that Shipit is configured to trust (a realistic scenario for any Shipit instance backing multiple orgs/GitHub Apps, which is an explicitly documented supported configuration in `config/secrets.development.example.yml`). No repository write access, `ApiClient` token, or GitHub App private key of the *victim* org is needed — only membership in / control of any one of the configured trusting organizations, since that org's own valid signature is used to attack a sibling org's repository referenced purely by an unchecked JSON field.

### Recommendation
In `WebhooksController#verify_signature` and in `Handlers::Handler#repository_name`, use the same authoritative field to determine both the signing organization and the acted-upon repository — derive `repository_owner` from `repository.full_name`'s owner segment (or vice versa), and reject the webhook if `repository.owner.login`/`organization.login` does not match the owner portion of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `config/secrets.development.example.yml` multi-org schema).
2. As an attacker who controls `org-a`'s GitHub App/webhook secret, craft a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Sign the payload body with `org-a`'s `webhook_secret` and send it with header `X-Github-Event: push` to `POST /github/webhooks`.
4. `verify_signature` computes `repository_owner == "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully.
5. `PushHandler#process` resolves `repository_name == "org-b/victim-repo"` via `Handler#repository_name`, looks up `Repository.from_github_repo_name("org-b/victim-repo")`, and calls `stack.sync_github(expected_head_sha: "deadbeef")` on `org-b`'s stacks — despite the signature never having been checked against `org-b`'s secret.
