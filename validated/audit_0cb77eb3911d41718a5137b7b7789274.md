### Title
Unvalidated route pool/token addresses let venue code execute arbitrary `transfer` calls inside the caller's signed auth tree — (File: contracts/controller/src/strategies/swap.rs)

### Summary
The Nextcloud CVE is the class "user-supplied content is handed to a third-party component that was never built to handle untrusted input" (here: SSRF/file access/code execution via a rendering library). The structural analog in XOXNO Lending is the swap-route pipeline: account strategies (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) accept a caller-supplied `swap` payload, and the configured router invokes whatever `pool` and token `Address`es the payload names, keeping no allowlist of them. Any contract address placed in a hop runs on the call stack while the caller's `require_auth` tree is still being satisfied, so a rogue "pool" can emit `token.transfer(victim, attacker, amount)` for any token the victim holds. Simulation records that transfer as a child of the caller's auth entry; once the wallet signs the simulated tree, the drain executes. The project's own threat model documents this exposure, and a harness test reproduces it end-to-end.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes exactly one `token_in.transfer(controller, router, amount_in)` via `authorize_transfer_as_current`, then calls `router.execute_strategy(controller, amount_in, swap)` with the fully caller-controlled `StrategySwap` bytes (lines 34-37). It measures only the controller's `token_in`/`token_out` deltas (`in_after <= in_before`, `actual_spent <= amount_in`, positive output) — it never inspects which contracts the route touches.

Inside the router, `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs:23-58`) dispatches on `hop.venue` and the venue adapters `invoke_contract` on `ctx.hop.pool` — an address taken verbatim from the payload's `assets` registry (e.g., `sushi.rs:20-50` calls `token0`/`token1`/`swap` on `ctx.hop.pool`). There is no registry or allowlist of pools or tokens; `Program::decode` validates only indices, modes, and weights, not that the referenced addresses are honest contracts. The threat model states this plainly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-165`).

When such code calls `token.transfer(caller, attacker, x)` on any token, the token's `require_auth(caller)` is satisfied by attaching the invocation as a child of the caller's root auth entry for the strategy call. `simulateTransaction` produces this tree and the wallet signs it — the harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the full path: Alice calls `swap_collateral` with a route through an attacker-deployed `RogueHopPool`; the recorded auth tree contains `wallet_token.transfer(alice → attacker, 77_770_000_000)` under her `swap_collateral` entry, and her entire balance of a token the protocol never even listed is drained while she still receives a fair swap output (lines 194-226).

Neither INV-STRAT-01's single-transfer controller grant nor INV-STRAT-02's measured settlement bounds this: the loss is the caller's wallet, not the routed amount, and the payload `min_out` and final health-factor gates all still pass because the swap itself is honest.

### Impact Explanation
Theft of user funds. A crafted route handed to a victim (malicious quote server, phishing frontend, compromised route builder) drains arbitrary token balances from the victim's wallet — including tokens unrelated to the position — inside a transaction whose economic outcome (the swap) is completely fair, so none of the protocol's measured-delta or solvency checks detect it. Severity: **High** (theft of arbitrary user funds, bounded by wallet balances and requiring the victim to sign the route's transaction).

### Likelihood Explanation
Requires a victim to execute an attacker-influenced route payload and sign the simulated auth tree — the standard quote→simulate→sign flow, which is precisely why the threat model instructs clients to "decode the route it signs and refuse an authorization tree with any other child." The contracts themselves provide no defense: no venue allowlist, no auth-tree constraint enforced on-chain, and the controller's one-transfer grant does not extend to what the router's callee does with invoker auth below it. This is reachable by any unprivileged address via `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` or a direct `execute_strategy` call.

### Recommendation
- Enforce a governance-managed allowlist of pool/venue contract addresses (and token addresses) that route payloads may reference; reject hops to unlisted addresses in `dispatch_hop`/`Program` validation.
- Alternatively/additionally, have the controller snapshot and enforce an auth-tree policy, or execute router strategies from a dedicated sub-account holding only the routed funds so an injected `transfer` finds nothing to steal.
- Document and enforce client-side auth-tree verification (refuse any child beyond the single input transfer) as a mandatory integration requirement.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a `RogueHopPool` contract whose `swap()` executes `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)`; routing `swap_collateral` through it yields a recorded auth tree of `swap_collateral → [wallet_token.transfer(alice, attacker, WALLET_BALANCE)]`, Alice's wallet is emptied (`balance 0 → 77_770_000_000` moved), and she still receives the fair `FAIR_OUT_ETH` supply credit. The threat model section "Routes, callbacks, and external integrations" (`docs/explanation/threat-model.md:142-165`) describes the identical mechanism for both the controller-mediated and direct `execute_strategy` paths.
