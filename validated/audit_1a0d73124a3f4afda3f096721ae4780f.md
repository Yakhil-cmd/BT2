### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled = false` for `allow_with_label`/`prevent_with_label` repositories - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` computes `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...allow_with_label...) || (...prevent_with_label...)`. Because Ruby's `&&` binds tighter than `||`, `review_stacks_enabled` is only ANDed with the `allow_all?` branch, not the `allow_with_label` or `prevent_with_label` branches. Consequently, a repository configured with `provisioning_behavior: allow_with_label` (label present) or `prevent_with_label` (label absent) will have `provision?` return `true` even when `review_stacks_enabled` is `false`, letting `ReviewStackAdapter#create!` persist a `Stack` and `PullRequest` for that repository.

### Finding Description
The intended binding is: `stack_created_for(repository) == true` implies `repository.review_stacks_enabled == true`. Tracing `provision?` in [1](#0-0) :

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby precedence makes this `(A && B) || C || D`, not `A && (B || C || D)`. So `review_stacks_enabled` (`A`) gates only the `allow_all?` term (`B`); the `allow_with_label` term (`C`) and `prevent_with_label` term (`D`) are evaluated independently of `review_stacks_enabled`. `respond_to_pull_request_opened?` at [2](#0-1)  gates `process` solely on this flawed `provision?`, and `process` immediately calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` at [3](#0-2) .

`find_or_create!` calls `create!`, which runs inside a transaction: `scope.create!(stack_attributes)` then `stack.build_pull_request.update!(github_pull_request: params.pull_request)`, and finally enqueues the stack for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)` — all outside the transaction block per [4](#0-3) . `scope` is `repository.review_stacks`, i.e. `has_many :review_stacks` scoped to the resolved `Repository` row per [5](#0-4) , so the repository binding itself is correctly enforced — the vulnerability is purely that `review_stacks_enabled` fails to gate two of the three provisioning-behavior branches.

Exploit: an attacker opens a PR against (or forks and triggers a webhook for) a repository whose Shipit configuration is `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`, with a label configured (e.g. `provisioning_label_name: "review-me"`). The attacker applies that label to their own PR (labels can be set by the PR author on their own PR in many workflows, and the `labels` array here comes straight from the webhook `pull_request.labels`). `pull_request_has_provisioning_label?` returns `true`, `repository.provisioning_behavior_allow_with_label?` returns `true`, so `provision?` returns `true` regardless of `review_stacks_enabled`. A `Stack` and `PullRequest` row are created for a repository whose operator explicitly disabled review-stack provisioning, and the stack is queued for real infrastructure provisioning via `ReviewStackProvisioningQueue`.

No existing guard catches this: `drop_unhandled_event`/`verify_signature` only authenticate that the webhook came from GitHub for that repo (unrelated to this logic bug), `ExplicitParameters` only validates payload shape (as seen in the `params do ... end` block at [6](#0-5) ), and no model validation on `Repository` or `Stack` re-checks `review_stacks_enabled` at creation time — `ReviewStackAdapter#create!` trusts the caller's decision entirely.

### Impact Explanation
An unprivileged GitHub user who can open/label a PR on a repository they control (or any repo where they can influence labels) can force Shipit to create a `Stack` + `PullRequest` record — and trigger real review-stack provisioning — for a repository whose maintainer has explicitly set `review_stacks_enabled: false`. This is an authorization bypass on a per-repository opt-in control: the operator's decision to disable review-stack automation is silently ignored whenever the misconfigured combination (`allow_with_label` + label present, or `prevent_with_label` + label absent) exists. Because provisioning is enqueued via `ReviewStackProvisioningQueue.add(stack)` immediately after creation, this can lead to unauthorized infrastructure/CI actions being kicked off for that repository, repeatable for every PR the attacker can label. This matches "unauthorized deploy" territory under the Critical bucket to the extent provisioning triggers deployment-adjacent automation.

### Likelihood Explanation
Requires the same misconfiguration precondition already assumed in the question: `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` (label present) or `prevent_with_label` (label absent). Given that precondition, the attacker cost is trivial — open a PR and add/remove a label, both actions available to any contributor with write access to labels on their own PR, or simply by forking and opening a PR with the label already applied where label permissions allow it. No secrets, tokens, or elevated GitHub permissions are needed. The bug is deterministic and repeatable on every PR event for the misconfigured repository.

### Recommendation
Fix operator precedence in `provision?` by explicitly parenthesizing so `review_stacks_enabled` gates the entire expression:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to any sibling handlers with the same expression (`labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb` reportedly use similar logic per the earlier grep results and should be audited/fixed identically).

### Proof of Concept
Minitest plan under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style (no live GitHub):

```ruby
test "does not create a stack when review_stacks_enabled is false, even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit) # or a dedicated fixture
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: "allow_with_label",
    provisioning_label_name: "review-me"
  )

  payload = opened_payload_with_label(repository, label: "review-me")

  assert_equal false, repository.review_stacks_enabled # left side of binding
  Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process

  assert_equal 0, Shipit::Stack.where(repository_id: repository.id).count
  assert_equal 0, Shipit::PullRequest.joins(:stack).where(stack: { repository_id: repository.id }).count
end
```

Before the fix, this test fails: `provision?` returns `true` and a `Stack`/`PullRequest` row is created despite `review_stacks_enabled == false`. After applying the parenthesization fix, `provision?` correctly returns `false` and the assertion of `0` rows passes, restoring the binding `stack_created_for(repository) == true ⟺ repository.review_stacks_enabled == true`.
