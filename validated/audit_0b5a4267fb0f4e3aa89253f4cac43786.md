### Title
Webhook `status` event handler writes commit status without scoping to the authenticated repository/organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects a GitHub App configuration (and its `webhook_secret`) by the `repository.owner.login` present in the payload, then hands the *raw payload* to `Shipit::Webhooks.for_event(event)` handlers. The HMAC signature proves only "this payload was signed by the org named in the payload." `StatusHandler`, however, uses the `sha` field to look up and mutate `Commit` records **globally**, with no filter tying the write back to the repository/organization whose secret validated the request.

### Finding Description
`WebhooksController` resolves the org used for signature verification purely from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

This only asserts "a repository/org owner X, controlling a valid `webhook_secret`, produced this HMAC." It does not bind the *content* of the payload's `sha`/state fields to repository X.

`StatusHandler#process` then performs an unscoped, installation-wide lookup and write: [3](#0-2) 

Unlike every other handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest` handlers), which resolve a `Repository`/`stacks` scope via `Handler#stacks` (backed by `payload.dig('repository','full_name')`) before touching records: [4](#0-3) [5](#0-4) 

`StatusHandler` never applies that scope — it queries `Commit.where(sha: params.sha)` across *every* stack/repository in the Shipit instance and calls `commit.create_status_from_github!(params)` on each match.

**Trust binding broken (as an equality):**
`organization authenticated by webhook_secret(repository.owner.login)` ≠ `repository/commit actually mutated by StatusHandler (any Commit row matching sha, regardless of owning repository)`.

Because git commit SHAs are content-addressed, an attacker who operates their own GitHub org/repo (with a legitimately installed Shipit GitHub App and thus a genuine `webhook_secret`) can produce a commit with **the exact same SHA** as a commit in a victim repository also tracked by the same Shipit instance — for example by forking/cloning the victim's public repository so the object graph (and therefore the SHA) is bit-for-bit identical, or by simply pushing the identical commit into their own repo. GitHub will then legitimately sign a `status` webhook for the attacker's own org for that SHA, which passes `verify_signature` (correct secret for the attacker's org). `StatusHandler` will still update the status of the matching `Commit` row belonging to the **victim's** stack, because the SQL lookup is keyed only on `sha`, with no repository/stack scoping.

### Impact Explanation
Commit statuses drive Shipit's CI gating (`ci.require`) and continuous-delivery decisions (`release_status?`/`release_status_context`, deploy blocking on failing/pending status). By forging a `success` status for a commit in a victim stack from a completely different, attacker-controlled repository/organization, an attacker can bypass required-CI gating and enable/force an unauthorized deploy of that commit on the victim's stack — this is a cross-repository write crossing the authentication boundary of the webhook, matching the "unauthorized deploy" / "cross-repository writes" Critical-impact bucket.

### Likelihood Explanation
Requires the attacker to (a) control/onboard any repository behind the same Shipit instance (multi-tenant deployments are explicitly supported via multiple `github:` org entries with independent `webhook_secret`s) and (b) produce a commit whose SHA collides with one in the target stack — trivially achievable by cloning the victim's public repository history and re-pushing the exact same commit into the attacker's own repo, then triggering (or waiting for) a `status` event from a CI system on that commit in the attacker's repo. No cryptographic collision is needed since the SHA is identical by construction. This makes the attack practical, not merely theoretical, wherever a Shipit deployment hosts more than one tenant/organization.

### Recommendation
Scope `StatusHandler#process` the same way every other handler does: resolve `stacks`/`Repository` from `payload.dig('repository','full_name')` first, and only update `Commit` records that belong to that repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` (or join through `Stack`) instead of the bare `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Onboard `attacker-org/attacker-repo` to the target Shipit instance (or use any already-tracked repo the attacker controls) with its own valid `webhook_secret`.
2. Clone `victim-org/victim-repo`'s public history and push an identical commit (same tree/parent/author/committer metadata ⇒ identical SHA `deadbeef...`) into `attacker-repo`, ensuring Shipit has synced a `Commit` row for `deadbeef...` under the victim's stack (already the case if it was previously deployed/tracked).
3. Have a CI system report a `success` status for `deadbeef...` on `attacker-repo` (or POST the crafted `status` webhook payload directly, signed with `attacker-org`'s `webhook_secret`), with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` and validates successfully against `attacker-org`'s secret. [6](#0-5) 
5. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, matching the victim's `Commit` row, and calls `create_status_from_github!`, flipping the status shown/used by the victim's stack — enabling CI-gated deploy despite the request never being authenticated for `victim-org`.
