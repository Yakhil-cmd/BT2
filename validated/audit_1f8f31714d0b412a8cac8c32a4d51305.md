### Title
Webhook signature verification selects the signing organization from an unauthenticated payload field, decoupling it from the repository the event actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the still-unverified JSON body. The event handlers that actually mutate state (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, via `Handler#repository_name`) instead resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')`. Nothing enforces that `repository.owner.login` and the owner segment of `repository.full_name` refer to the same organization inside one payload, so the field used to choose the trust anchor (signing secret) is not the field used to choose the object being written.

### Finding Description
`verify_signature` computes the org to authenticate against like this: [1](#0-0) [2](#0-1) 

```
repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

`Shipit.github(organization:)` looks up a per-organization config (including a distinct `webhook_secret`) in `secrets.github`, keyed by organization name, when the engine is configured in multi-tenant mode: [3](#0-2) 

Once the signature check passes, `create` dispatches the *entire raw payload* to the registered handlers for the event: [4](#0-3) 

Handlers resolve the repository/stack to act on using a *different* field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks the repository up by `owner`/`name` columns directly, independent of `repository.owner.login`: [6](#0-5) 

`PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all consume this `stacks`/`repository_name` resolution (or `Commit.where(sha:)`, which is not repo-scoped at all) to perform writes: `stack.sync_github`, `commit.create_status_from_github!`, `stack.commits...schedule_refresh_check_runs!`: [7](#0-6) [8](#0-7) [9](#0-8) 

**The broken equality:** the engine implicitly assumes
`organization authenticated (repository.owner.login used to pick webhook_secret) == organization whose repository is written (owner segment of repository.full_name used to resolve the Stack/Repository)`.

Nothing in `WebhooksController` or `Repository.from_github_repo_name` enforces this equality. On a Shipit instance configured with several GitHub organizations (the documented `secrets.github.<org>.webhook_secret` multi-tenant mode), an actor who legitimately controls a GitHub App/organization already onboarded onto that Shipit instance (and therefore knows *that org's own* `webhook_secret` — a credential they are entitled to, not one they had to steal) can send a `POST /github` webhook where:
- `repository.owner.login` = their own org (so the signature validates against their own real secret and `verify_webhook_signature` returns true), and
- `repository.full_name` = `"other-org/other-repo"` (so `PushHandler`/`CheckSuiteHandler` resolve and mutate a *different* org's `Stack`, or `StatusHandler`/`commit.create_status_from_github!` targets any commit sha across the whole instance, since `Commit.where(sha:)` performs no repository scoping at all).

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely, an org onboarded to a shared Shipit instance can, using only its own legitimate webhook secret:
- Forge `push` events for a victim stack, forcing `Stack#sync_github` (via `PushHandler`) to run against a repository it does not own — cross-repository interference from an org that never had write access to that repository.
- Forge `status` events for arbitrary commit shas (since `StatusHandler` does `Commit.where(sha: params.sha)` with no repository scoping at all — any commit in the whole Shipit instance can have a fabricated CI status created), which can feed into merge-queue/deploy-safety checks that gate merges and deploys, i.e. an unauthorized/incorrectly-authorized merge or deploy path.
- Forge `check_suite` events to trigger `RefreshCheckRunsJob` against a victim's stack/commits.

This matches the High-severity bucket ("escalation ... unauthenticated read of stack state ... or an unauthorized deploy/rollback/merge" territory) because it lets an org with no privileges over the victim repository inject fabricated CI/push signals that the victim stack's deploy pipeline consumes as trusted GitHub state.

### Likelihood Explanation
Requires the engine to be run in multi-tenant mode with more than one organization's `webhook_secret` configured under `secrets.github` (a documented, supported configuration, not a misconfiguration) and requires the attacker to already control one such onboarded organization/GitHub App installation — i.e., they know their own `webhook_secret`, which is expected and not a privileged secret belonging to Shipit itself. No `ApiClient` token, session, or GitHub App private key theft is needed; this is a pure confused-deputy issue in field selection during signature verification versus event processing.

### Recommendation
After verifying the HMAC, re-derive `repository_owner`/organization strictly from the same field the handlers use (`repository.full_name`'s owner segment), or better: verify the signature using the organization owning the resolved `Repository` record (looked up first, before dispatch) rather than trusting `repository.owner.login`/`organization.login` from the unauthenticated JSON to select the verification key. Additionally, scope `StatusHandler`'s `Commit.where(sha:)` lookup by the resolved repository, not globally.

### Proof of Concept
1. Shipit is deployed with multi-tenant GitHub config: `secrets.github.attacker-org.webhook_secret = S1` and `secrets.github.victim-org.webhook_secret = S2`, both orgs' GitHub Apps pointed at the same Shipit instance's `/github` webhook endpoint (as documented in `docs/setup.md`).
2. Attacker, who administers `attacker-org`'s GitHub App and therefore knows `S1`, crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(S1, body)>` and POSTs to `WebhooksController#create` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC checks out against `S1` — the request passes.
5. `PushHandler.call(params)` runs, calling `Handler#repository_name` → `payload.dig('repository','full_name')` → `"victim-org/victim-repo"`, resolving `victim-org`'s `Stack`, and invoking `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` — a write triggered by attacker-org's credentials against victim-org's stack.

```ruby
      github_app = Shipit.github(organization: repository_owner)
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
