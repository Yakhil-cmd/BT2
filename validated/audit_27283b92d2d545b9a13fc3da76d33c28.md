The external report describes an EVM/Solidity-specific issue: calling `ERC20(_token).approve()` (which ABI-decodes a `bool` return value) against non-standard tokens like USDT that return no data, causing a revert due to return-data-size mismatch. This is strictly a low-level `call`/ABI-decoding artifact of the EVM.

Checking the Sui repository's own EVM bridge contracts, the actual token transfer path uses `SafeERC20.safeTransferFrom` rather than a raw `ERC20.approve`/`transferFrom` call, and it is the *caller* (via `IERC20(tokenAddress).allowance`) who must have already approved the bridge — the contract itself never calls `approve()` on an arbitrary token, so this exact call site doesn't exist in `bridgeERC20`/`bridgeERC20V2`. [1](#0-0) [2](#0-1) 

On the Move side, there is no low-level external-call/ABI-decoding mechanism analogous to Solidity's return-data-size check — Sui's `Coin`/object model and the `bridge::approve_token_transfer`/`claim_token` flow operate through typed Move calls with explicit `assert!` checks, not raw external calls whose return data is length-checked by compiled bytecode. [3](#0-2) 

Even if a similar "non-conforming token breaks a hot path" issue existed, this bug class is a DoS/revert issue (as the original report's own "Assessed type" states), which does not meet the required Critical/High bar for this scope (direct fund theft, state corruption, cap-exceeding, bridge forgery/governance bypass, or RCE). No reachable root cause matching an allowed Critical/High impact was found in this repository for this bug class.
