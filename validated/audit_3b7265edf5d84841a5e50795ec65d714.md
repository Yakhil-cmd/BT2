### Title
ERC20Transactor credits full nominal amount into the XCM holding register without verifying actual ERC20 balance change, breaking accounting for fee-on-transfer/deflationary ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor`, wired into Asset Hub Westend's `AssetTransactors` tuple (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`), lets arbitrary `pallet-revive`-deployed ERC20 contracts be used as XCM-transactable fungible assets. `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` both assume the `IERC20::transfer` call moves exactly `amount` tokens, and unconditionally credit/attempt-transfer that nominal `amount` — never checking the actual balance delta of the involved account (the shared `ERC20TransfersCheckingAccount`). For any ERC20 contract that charges a transfer fee or otherwise delivers less than the requested `value` (a "fee-on-transfer"/deflationary token, which the matcher/config places no restriction against), this creates a real discrepancy between the XCM holding register's accounting and the checking account's actual on-chain ERC20 balance.

### Finding Description
`withdraw_asset_with_surplus` ( [1](#0-0) ) withdraws assets by calling `IERC20::transferCall` from the user to `TransfersCheckingAccount`, and on `Ok(true)` (success) unconditionally constructs an `AssetsInHolding` credit worth the full nominal `amount`: [2](#0-1) 

It never reads the checking account's ERC20 balance before/after the call to determine the *actual* amount received. If the token contract charges a fee on transfer (deducts a percentage before crediting the recipient), the checking account only receives `amount - fee`, yet the XCM holding register is credited with the full `amount`.

Symmetrically, `deposit_asset_with_surplus` ( [3](#0-2) ) transfers the full holding `amount` out of the shared checking account to the beneficiary: [4](#0-3) 

Because `TransfersCheckingAccount` (`ERC20TransfersCheckingAccount`, `PalletId(*b"py/revch")`) is a single shared pot for *all* XCM users of a given ERC20 asset ( [5](#0-4) ), any fee-on-transfer token causes the account's real ERC20 balance to fall below what the sum of all XCM-credited `AssetsInHolding` amounts implies. This is exactly the invariant violated in the referenced report: internal bookkeeping assumes `amount transferred == amount received`, with no balance-before/after check.

Reachability: this is triggered by any signed user calling `pallet_xcm::transfer_assets`/`limited_reserve_transfer_assets`/`execute` (or an XCM program from a trusted origin) that references an ERC20 asset matched by `assets_common::ERC20Matcher` — a normal, permitted extrinsic path, requiring no privileged role. The attacker (or simply an unaware user) only needs to use/register an ERC20 contract with fee-on-transfer semantics as an XCM asset.

### Impact Explanation
The immediate consequence for the withdrawing user is a self-contained accounting overstatement in their own XCM program's holding register (an amount larger than what was actually collected). More importantly, because `TransfersCheckingAccount` is shared across all users of this transactor, this "phantom" excess in the XCM system as a whole means the checking account's real balance is a fee-token amount short of what other users' subsequent `deposit_asset_with_surplus` calls will try to withdraw. Subsequent unrelated `DepositAsset`/reserve-transfer/bridging operations for the *same ERC20 asset* by other users can then fail with `"ERC20 contract reverted"` or `"contract transfer failed"` once the checking account's balance is insufficient — a cross-user, non-privileged-triggered denial of service and accounting-integrity break for that asset, not merely a revert local to the fee-token's own transfer. This matches a Medium-severity classification: it can break the correctness of the XCM asset-transfer/bridging pipeline for that ERC20 asset class, though it does not directly mint/steal funds cross-chain and requires that specific ERC20-as-XCM-asset registration to exist.

### Likelihood Explanation
Likelihood is moderate: it requires an ERC20 contract with fee-on-transfer/deflationary semantics to be matched/registered as an XCM fungible asset via `assets_common::ERC20Matcher` on a chain configured with `ERC20Transactor` (currently Asset Hub Westend). Nothing in `ERC20Transactor`, `ERC20Matcher`, or the matched-config in `xcm_config.rs` was found to filter out non-standard ERC20 semantics; the matcher only checks that the contract implements the `IERC20` ABI and returns success/failure on `transfer`. Whether/how ERC20 contract registration as an XCM asset is governance-gated (e.g., through the ERC20 matcher's whitelist logic) was not fully explored in the available index; that governance step could reduce likelihood, but the core arithmetic/accounting flaw is present regardless.

### Recommendation
In `withdraw_asset_with_surplus`, read the `TransfersCheckingAccount`'s ERC20 balance immediately before and after the `transferCall`, and credit `AssetsInHolding` with the *actual* balance delta rather than the requested `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the actual balance delta of the beneficiary (or checking account debit) matches expectations, and propagate any shortfall back into the XCM holding/surplus accounting instead of assuming exact-amount transfers. This mirrors the original report's recommendation of "calculating the difference in token balance before and after the token transfer."

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}
