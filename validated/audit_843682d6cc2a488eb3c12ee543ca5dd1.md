### Title
Missing `return` after a caught hashing exception causes duplicate processing / double-callback of a device-supplied private-payment chain in `handleSavedPrivatePayments` - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` re-processes rows from `unhandled_private_payments`, a table populated directly from private-payment-chain payloads sent by a paired device/hub peer (`handleOnlinePrivatePayment` → `savePrivatePayment`, and `wallet.js:handlePrivatePaymentChains`). Inside its `validateAndSave` closure, when `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws, the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` but does **not** `return` afterward, so execution falls through to build `key` (using the now-`undefined` `json_payload_hash`) and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same, already-being-deleted row. [1](#0-0) 

### Finding Description
This is the closest reachable analog to the CVE's "use of a resource concurrently with its release" pattern (a logic-level use-after-free): the private-payment row is scheduled for deletion from `unhandled_private_payments` (`deleteHandledPrivateChain`, an async DB call) while the exact same in-memory `arrPrivateElements` object is simultaneously fed into `privatePayment.validateAndSavePrivatePaymentChain`, which independently opens its own transaction, validates, and (on success) writes rows into `outputs`/`inputs` and calls `deleteHandledPrivateChain` again on `ifOk`/`ifError`.

Consequences of the missing `return`:
- The `async.each` iteratee's `cb` gets invoked twice for the same row (once from the catch-branch `deleteHandledPrivateChain`, and again from whichever of `ifOk`/`ifError`/`ifWaitingForChain` fires inside `validateAndSavePrivatePaymentChain`), which is undefined behavior for the `async` library and can desynchronize the `saved_private` mutex lock lifecycle and the `assocNewUnits` bookkeeping used to fire `"new_my_transactions"`.
- More importantly, the "hash failed" catch path is only supposed to guard against being unable to compute the correlation `key`; it was clearly not intended to also continue on to attempt validation/saving of the payload. Since the reachable payload only needs to satisfy the very shallow checks in `wallet.js:handlePrivatePaymentChains` (`isNonemptyObject(e.payload)`, `isNonemptyString(e.payload.asset)`, arrays of non-empty objects) before being persisted to `unhandled_private_payments`, an attacker-controlled peer can supply a payload whose structure makes `objectHash.getBase64Hash` throw (e.g., unsupported value types nested in `payload`) while still passing `parsePrivatePaymentChain`/`validatePrivatePayment`'s own checks, triggering this fall-through and causing the same chain to be raced through two independent commit paths against the same `unhandled_private_payments` row. [2](#0-1) [3](#0-2) 

### Impact Explanation
At minimum this is a reliability/correctness bug: double invocation of the `async.each` callback can corrupt the iteration state of `handleSavedPrivatePayments`, potentially causing the `saved_private` mutex to be released prematurely or held stuck, and duplicate `deleteHandledPrivateChain` calls against a row that no longer exists. Because private payment persistence (`outputs`/`inputs` inserts, `is_spent` flag updates) happens inside its own DB transaction in `privatePayment.validateAndSavePrivatePaymentChain`/`indivisible_asset.js`/`divisible_asset.js`, racing this against the row's own deletion increases the risk of processing the same private chain twice under different timing, which is the class of bug (concurrent use + release of the same resource) the CVE analog targets. I could not fully verify, given tool/iteration limits, whether `objectHash.getBase64Hash` can actually be made to throw on attacker-supplied JSON that otherwise passes the `wallet.js` payload shape checks (this needs inspection of `object_hash.js`'s `getSourceString`/type-dispatch logic, which I was unable to load before running out of iterations). Without that confirmation, I cannot assert this reaches double-spend/fund-loss severity with certainty.

### Likelihood Explanation
Reachability requires only that a paired device (or hub, since `bViaHub` is accepted from the hub relay path) send a `private_payment` chain whose payload triggers a hashing exception; the pre-checks in `wallet.js:handlePrivatePaymentChains` are shallow (object/array/string-type checks only) and do not constrain the JSON deeply enough to guarantee `getBase64Hash` never throws. This makes the trigger plausibly reachable by an unprivileged private-payment counterparty, though the exact malformed-payload shape needed to throw was not confirmed within the available investigation window.

### Recommendation
Add the missing `return` after the `catch` block in `network.js`'s `validateAndSave` (inside `handleSavedPrivatePayments`) so that a hashing failure short-circuits before falling through to `privatePayment.validateAndSavePrivatePaymentChain`, and ensure `cb` is invoked exactly once per row. Additionally, verify `objectHash.getBase64Hash` cannot throw on validated-shape payloads, or add stricter payload-shape validation before persisting to `unhandled_private_payments`.

### Proof of Concept
1. As a paired device (or via the hub relay), send a `private_payment` message whose `chains[0][0].payload` passes the shallow checks in `wallet.js:handlePrivatePaymentChains` (`isNonemptyObject`, `isNonemptyString(asset)`, non-empty `inputs`/`outputs` arrays of non-empty objects) but contains a nested value that causes `objectHash.getBase64Hash` to throw when computing the correlation hash (needs confirmation against `object_hash.js`'s exact type handling).
2. This payload is queued to `unhandled_private_payments` and later picked up by `handleSavedPrivatePayments`.
3. In `validateAndSave`, the `catch` block calls `deleteHandledPrivateChain(...)` but does not return, so `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` also runs against the same row, causing `cb` to fire twice and the delete/validate paths to race.

*Note: Given the exploratory nature of this analysis and the tool-call budget exhausted before I could inspect `object_hash.js` in full, I cannot conclusively confirm the exact payload needed to trigger the hashing exception, nor definitively prove a concrete double-spend/fund-loss outcome beyond the double-callback/race condition itself. If you need certainty on exploitability, a Devin session with full file access should verify `object_hash.js`'s exception conditions and trace the downstream effect of a doubled `async.each` callback in this exact code path.*

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
