## Title
Cross-repository status webhook forgery triggers unauthorized deploy via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
`Webhooks::Handlers::StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no scoping to the repository that authenticated the webhook, so a `status` event validly signed for an attacker-controlled repository can create a `Status` on a commit belonging to an entirely different (victim) stack whenever the two repositories happen to share a commit SHA (e.g., a fork of the victim repo). That `Status` creation fires `after_commit :schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` for the **victim's** stack, and if the victim stack is `continuous_deployment: true` and not `occupied?`, the job proceeds straight to `stack.trigger_continuous_delivery`.

## Finding Description
Binding claimed and actually broken: `webhook.repository_owner (authenticated by verify_signature)` == `commit.stack.github_repo_name (the stack that gets the Status/CD job)` — this equality is **not enforced** anywhere in the path.

Path:
1. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, which only proves the payload was legitimately sent by GitHub for the org named in `params.dig('repository','owner','login')` [1](#0-0) . It does **not** check that `repository_owner`/`repository.full_name` matches the repo of any commit the handler will subsequently touch.
2. `Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` [2](#0-1) .
3. `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This is a **global, unscoped** query across all stacks/repositories in the Shipit instance — it never filters by `params.dig('repository','full_name')` or `repository_owner`.
4. `Status` creation triggers `after_commit :schedule_continuous_delivery`, which calls `commit.schedule_continuous_delivery` [4](#0-3) .
5. `Commit#schedule_continuous_delivery` checks only pre-existing victim-side state (`deployable?`, `stack.continuous_deployment?`, `stack.deployable?`) and enqueues `ContinuousDeliveryJob.set(wait: 10.seconds).perform_later(stack)` for the **victim's stack** [5](#0-4) .
6. `ContinuousDeliveryJob#perform(stack)` re-checks `stack.continuous_deployment?` and `stack.occupied?` (both victim pre-existing state, attacker supplies neither) and, if satisfied, calls `stack.trigger_continuous_delivery`, which leads into `trigger_deploy` and ultimately `Command#start`/`PTY.spawn` using the victim stack's deploy environment/credentials [6](#0-5) .

Why this happens: SHAs are content-addressed and identical across a fork and its upstream for any commit the attacker has not modified. An attacker who owns a fork of the victim's tracked repository can trigger a `status` webhook for their own repository (e.g., via GitHub Actions/API posting a commit status on their own fork, which they are fully authorized to do as repo owner) referencing a SHA that is also present, unmodified, in the victim's upstream repo/stack. That webhook is correctly signed for the attacker's own org/app installation and passes `verify_signature`. `drop_unhandled_event` does not block `status` events (it's a registered handler). `ExplicitParameters` on `StatusHandler` only validates the *shape* of `sha`/`state`/etc., not the repository ownership — there's no repository/stack scoping parameter checked against the commit's owning stack at all. `force_github_authentication`, `User#authorized?`, `require_permission!`, and the `stacks` scope are irrelevant here since webhooks bypass the API/session-authenticated controllers entirely — `WebhooksController` is a raw `ActionController::Base` endpoint authenticated only by the per-organization webhook signature, and that signature check does not bind the specific `sha`/commit set touched to the org that signed it.

## Impact Explanation
This lets an unprivileged GitHub user who merely owns a fork (or any repo sharing a SHA) of a victim repository cause an unauthorized `Status` record to be written against the victim's stack and commit, and — where the victim stack has `continuous_deployment: true` and is momentarily idle (`occupied?` false, e.g., no deploy is currently running) — cause `ContinuousDeliveryJob` to run `stack.trigger_continuous_delivery` → `trigger_deploy`, executing deploy commands on the victim's deploy host with the victim's `GITHUB_TOKEN`/deploy-time secrets. This is "a payload for one repository mutating another's stack/commit" and results in "an unauthorized deploy" — matching the Critical impact category. It is repeatable against any victim stack whose repository the attacker can fork and for which they can find/produce a shared SHA (trivial: any un-rebased upstream commit already shared by the fork).

## Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true` and is not `occupied?` at the moment the delayed job runs (10s after status creation) — both purely pre-existing state on the victim side, not something the attacker must supply. The attacker needs only: a GitHub account, a fork of the target repo (or any repo sharing an SHA with it), and the ability to post a commit status on their own repository (a standard GitHub feature available to any repo owner/collaborator via the Statuses API or Actions). No Shipit credentials, sessions, or secrets are required. This is a low-cost, repeatable attack limited only by SHA-sharing opportunities, which are common in practice for forks of actively-tracked open source or internal repos.

## Recommendation
Scope the `StatusHandler` (and analogous `CheckSuiteHandler`, which already scopes by `stacks.where(branch:)` but should also scope commits by stack) lookup to commits belonging to stacks whose repository matches the webhook's authenticated `repository.full_name`/`repository_owner`, e.g. `Stack.where(repo_name: params.dig('repository','full_name')).flat_map(&:commits).where(sha: params.sha)` or add a `repository` scope column and filter `Commit.joins(:stack).merge(Stack.where(repo_owner: ..., repo_name: ...)).where(sha: params.sha)`, ensuring a status webhook can only affect commits/stacks tied to the repository that produced and signed it.

## Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), no live GitHub:
```ruby
test ":status from a foreign/attacker repository triggers CD for a victim stack sharing the SHA" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.last # SHA shared with attacker's fork

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => victim_stack.branch }],
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => 'attacker-org/forked-repo' }
  }.to_json

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
    post :create, body: attacker_payload, as: :json
  end
  # Binding check: verify_signature authenticated "attacker-org", but the job/deploy
  # target is victim_stack (repo_owner "shopify"/whatever victim org is) — mismatch proven.
  assert_not_equal 'attacker-org', victim_stack.repo_owner
end
```
This demonstrates `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])` firing from a webhook whose only authenticated identity is the attacker's own repository, confirming the broken binding.
