Confirmed: `Shipit.github(organization:)` is memoized per-organization (`app/models/shipit/webhooks/handlers/handler.rb:33-38` uses `params.dig('repository', 'full_name')` for the actual write target, while `WebhooksController#verify_signature` selects the signing/verification secret using a *different* payload field, `repository_owner` (`repository.owner.login` or `organization.login`) — `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).

### Title
Webhook signature verification is keyed by `repository.owner.login`/`organization.login` while handlers act on `repository.full_name`, letting an attacker with any one organization's leaked/absent secret forge events for a different organization's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the request HMAC against using `repository_owner`, taken from `params.dig('repository','owner','login')` (fallback `organization.login`). [1](#0-0) [2](#0-1) 
The event handlers that actually mutate state (statuses, pull-request stack archiving/unarchiving, review-stack provisioning, etc.) resolve the target `Repository`/`Stack` from a *different* field of the same JSON body, `repository.full_name`. [3](#0-2) [4](#0-3) 

### Finding Description
The trust binding that must hold is: `organization whose secret verified this request == owner of the repository the handlers write to`. Shipit supports per-organization GitHub App configuration, each with its own optional `webhook_secret` (`lib/shipit.rb:170-200`, `config/secrets.development.example.yml:8-16`). `verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured (`lib/shipit/github_app.rb:76-83`).

Because the organization used for signature selection (`repository.owner.login`) and the organization used by the handlers to resolve the repository/stack (`repository.full_name`, i.e. `"<owner>/<name>"`) are two independently-controlled fields of the same attacker-supplied JSON body, an unprivileged, unauthenticated poster to the public `/webhooks` endpoint can set:
- `repository.owner.login` to an organization that is either unconfigured for Shipit or configured with no `webhook_secret` — verification then vacuously passes with `head 422` never being hit (or trivially known secret) — and
- `repository.full_name` to `"other-org/other-repo"`, a completely different, actually-managed org/repo pair.

Since `verify_signature` never checks that these two values agree, the request is treated as verified while the payload processed by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`) drives handlers keyed off `repository.full_name` belonging to a target org the attacker never authenticated against.

### Impact Explanation
Handlers reachable this way can mutate stack state without any valid signature for the actually-targeted repository: e.g. `PullRequest::ClosedHandler#process` calls `review_stack.archive!` and `ReopenedHandler`/`UnlabeledHandler` call `stack.unarchive!`/`archive!` for review stacks resolved from the spoofable `repository.full_name` [5](#0-4) [6](#0-5) , and `StatusHandler#process` writes commit statuses for any `sha` matching a `Commit` record across the whole install, independent of the "verified" owner [7](#0-6) .
This is unauthorized cross-repository state mutation (archive/unarchive of review stacks, forged commit statuses that can gate CI-required deploys) driven by an attacker who never proved control of the actually-affected organization/repository — matching the report's "authenticated entity vs. acted-upon entity" mismatch pattern (High-severity class: escalation past the intended authorization boundary / unauthorized writes).

### Likelihood Explanation
Exploitability requires only that at least one configured (or default/no-secret) organization exists whose `repository_owner` value differs from the org actually targeted by `repository.full_name` — no privileged credentials, sessions, or tokens are needed, since `/webhooks` is unauthenticated by design and reachable by anyone who can send an HTTP POST. The `# Fallback to the organization sub-object` comment shows the field is deliberately payload-derived and attacker-controlled. [2](#0-1) 
In single-organization deployments (`github_default_organization` nil) this is not exploitable because there is only one secret/org; the issue is specific to the documented multi-organization configuration schema (`lib/shipit.rb:170-200`, `config/secrets.development.example.yml:18-38`), which the engine explicitly supports and documents.

### Recommendation
After selecting the `GitHubApp` used for signature verification, require that the resolved `repository_owner` matches the owner segment parsed out of `repository.full_name` (and `organization.login` when used as fallback) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, resolve the `Repository`/`Stack` target using the same verified `repository_owner`, not an independent `full_name` field, so a single field is both authenticated and acted upon.

### Proof of Concept
1. Configure Shipit for two organizations, `victim-org` (with a real `webhook_secret`) and `attacker-org` (installed for testing/POC purposes with no `webhook_secret` set, per the optional secret documented in `docs/setup.md:30`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` matching `victim-org`'s secret is needed: `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then creates a forged "success" status on `victim-org/victim-repo`'s commit, potentially satisfying `ci.require` checks that gate deploys for that stack, despite the attacker never having proven any relationship to `victim-org`.
