### Title
Arbitrary tokens sent to the liquidity pool are permanently unrecoverable - (File: contracts/pool/src/lib.rs)

### Summary
The liquidity pool has no generic token-recovery entrypoint. Any user can directly transfer a listed or unlisted token to the pool, but pool custody is separated from market `cash`; unsolicited tokens do not enter any market book and no public or governance operation can withdraw them.

### Finding Description
The pool exposes only market operations such as `supply`, `borrow`, `withdraw`, `repay`, `recapitalize`, `flash_loan`, and `claim_revenue`; its interface contains no rescue or arbitrary-transfer function. [1](#0-0) 

All state-mutating pool entrypoints are restricted to the controller owner, while token custody is tracked separately through the market’s accounting `cash` field rather than the contract’s actual token balance. [2](#0-1) [3](#0-2) 

Outbound token movement is only performed through `Cache::transfer_out` for the asset configured on a market. [4](#0-3) 

For an unlisted token, no `HubAssetKey` or market params exist, so no pool operation can construct a `Cache` and transfer it. For a listed token, a direct `Token::transfer(sender, pool, amount)` increases `token.balance(pool)` but does not call `supply`, `repay`, or `recapitalize`, so `cash` remains unchanged. Withdrawals, borrows, flash loans, and revenue claims are capped by booked cash or revenue rather than the surplus physical balance. [5](#0-4) 

`recapitalize` cannot recover the donation because it only credits up to `backing_shortfall` and refunds the unused amount to the payer. [6](#0-5) 

Likewise, `claim_revenue` only transfers the amount obtained by burning claimable revenue shares and debiting cash; it cannot address an unbooked surplus or a token with no market. [7](#0-6) 

### Impact Explanation
Any token sent directly to the pool outside a recognized controller flow is permanently frozen. This includes unsupported tokens, tokens for assets whose market is later removed from usable flows, accidental user deposits, and externally delivered rewards. Because the token remains outside `cash`, suppliers cannot withdraw it and the protocol cannot route it through any existing market operation.

### Likelihood Explanation
The pool address is publicly observable and direct token transfers are permissionless. Users or integrations can mistakenly send assets to the custody address rather than invoking `Controller::supply`. Third-party venues can also push reward tokens to the pool without a corresponding market operation. The issue requires an external transfer rather than active attacker exploitation, making accidental occurrence plausible but not guaranteed.

### Recommendation
Add an explicit recovery path for non-booked balances, controlled by lending governance rather than a standalone privileged key. A safe design should:

- accept `(token, recipient, amount)`;
- reject listed assets when `amount` exceeds `token.balance(pool) - total_booked_cash_for_token`, accounting for the same asset shared across hubs;
- allow unrestricted recovery only for tokens with no market;
- route execution through the controller or governance so the pool does not gain an independent owner bypass;
- emit an event identifying the recovered token and amount.

### Proof of Concept
1. Deploy the controller and pool, and create no market for `unsupported_token`.
2. An unprivileged user calls the token contract directly:
   `unsupported_token.transfer(user, pool_address, amount)`.
3. The token balance of `pool_address` increases by `amount`.
4. No pool entrypoint accepts that token address independently of a `HubAssetKey`, and no market exists for it.
5. All pool mutators either require a market or are owner-only controller calls; therefore the transferred balance cannot be withdrawn.
6. For a listed token, repeat the transfer directly to the pool. `token.balance(pool)` increases while market `cash` remains unchanged, so `borrow`, `withdraw`, `flash_loan`, and `claim_revenue` cannot use the donated surplus.

    /// Panics if cash reserves are below `amount`.
    pub(crate) fn require_reserves(&self, amount: i128) {
        assert_with_error!(
            self.env,
            self.cash >= amount,
            CollateralError::InsufficientLiquidity
        );
    }

    /// Increases accounting cash by `amount`. Rejects negative amounts and overflow.
    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Decreases accounting cash by `amount`. Rejects negative amounts or
    /// insufficient reserves.
    pub(crate) fn debit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.require_reserves(amount);
        self.cash = self
            .cash
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));

pub(crate) fn accounting(env: &Env, hub_asset: HubAssetKey) -> RevenueOutcome {
    let mut cache = ops::renewed_market(env, &hub_asset);

    let net_transfer = cache.burn_claimable_revenue();

    guards::require_utilization_below_max(env, &cache);
    guards::require_supply_for_debt(env, &cache);
    cache.debit_cash(net_transfer);

    cache.commit();
    RevenueOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: net_transfer,
        },
    }
