### Title
PR label named "path" overrides `Command#unbundled_env`'s constructed `PATH`, enabling relative-path binary hijack on the deploy host - ([File: lib/shipit/command.rb])

### Summary
`Shipit::ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with the fixed value `"true"`, with no key allow-listing. Because `Command#unbundled_env` merges the caller-supplied `@env` *last*, over its own constructed `PATH`, a PR labeled `path` causes the process `PATH` handed to `PTY.spawn` to become the literal string `"true"` instead of `Shipit.shell_paths + ENV['PATH']`, and since git/bundle/cap steps run with `chdir` set inside the checked-out PR branch content, an attacker-controlled `true/` subdirectory containing binaries named `git`, `bundle`, `cap`, etc. would be resolved and executed instead of the real ones.

### Finding Description
The broken binding is: `Command#unbundled_env`'s final env keys should be `⊆ {allow-listed deploy-spec variables} ∪ Shipit's own reserved keys`, but in practice `ReviewStack#env`'s output is merged in unfiltered, so the attacker-controlled key set `{LABEL_NAME.upcase}` is unconstrained and can collide with the reserved key `PATH`.

Code path:
1. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim via `pull_request.update!(labels: ...)` [1](#0-0) . This handler is reachable from any PR `labeled`/`unlabeled`/`opened` webhook the attacker's own repository emits when they label their own PR.
2. `Shipit::ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` over `super` (Stack#env), with **no allow-list** applied [2](#0-1) .
3. `Shipit::TaskCommands#env` merges `@stack.env` into the final env used to build each step's `Command`, again unfiltered by `EnvironmentVariables.permit` [3](#0-2) . `EnvironmentVariables#permit` (the only allow-list mechanism in the codebase) is invoked solely for `deploy_variables`/`rollback_variables`/task `variables` supplied through the UI/API (`deploy_spec.filter_deploy_envs`, `task_definition.filter_envs`) [4](#0-3) [5](#0-4)  — it is never applied to `@stack.env`/label-derived keys.
4. `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` [6](#0-5) . Because `@env` (which now contains `'PATH' => 'true'`) is merged last, it silently overwrites the constructed `PATH`.
5. `Command#start` passes this hash straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) , and `@chdir`/steps for a review stack task run inside the checked-out PR branch working tree (`TaskCommands#checkout`/`#clone` use `@task.working_directory`, populated from the attacker's own branch content) [8](#0-7) .

Existing guards that fail to stop this: `verify_signature`/webhook auth guards only check that the webhook truly comes from the attacker's own repository (which it does — attacker owns the PR), not the *content* of the label; `EnvironmentVariables#permit` exists but is never invoked on this code path; no model validation restricts `PullRequest#labels` values (they're free-text GitHub label names) [1](#0-0) .

Exploit: attacker opens/owns a PR against a repository with review stacks enabled, adds a label literally named `path` (case-insensitive, since it's `.upcase`d), and also commits a directory named `true/` containing malicious executables named after tools the deploy pipeline invokes (`git`, `bundle`, `cap`, etc.) in their branch. When Shipit runs any task/deploy step for that PR's `ReviewStack` (e.g. via `bundle install`/deploy scripts, executed relative to the checked-out branch as cwd), the shell's `PATH` is the bogus relative value `"true"`, and if an unqualified binary name is looked up, the attacker's planted executable under `./true/<name>` in the checkout is what actually executes.

### Impact Explanation
If achievable, this is RCE on the deploy host under the Shipit worker's privileges (git/bundle/deploy steps), matching the "Critical - RCE on the deploy host via `Command`/`PTY.spawn`" category, scoped to the stack/host running the vulnerable review-stack task and any co-located stack sharing that host. However, this depends on: (a) the actual shell/exec-resolution semantics of `PTY.spawn`+`Shellwords`-parsed commands honoring a single relative `PATH` component against the spawned process's `chdir`, and (b) the specific step commands in `shipit.yml`/`Capfile` invoking unqualified binary names not already found via `BASE_ENV`'s absolute-path fallbacks or shell built-ins. I was not able to fully verify point (a) from the available files (no direct evidence of how `Shellwords.split`+`PTY.spawn` resolves relative `PATH` entries relative to `chdir` versus process cwd at spawn time), so the RCE conclusion is plausible but unconfirmed by tracing further OS-level behavior in this codebase.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` (or the equivalent `provisioning_behavior`) so that a `ReviewStack` gets provisioned for the attacker's PR — a configuration decision made by the repository owner/Shipit operator, not the attacker. Given that, the attacker's cost is trivial: open a PR from their own fork, add a label named `path`, and (for the full RCE variant) commit a `true/` directory with malicious scripts. This is repeatable against any repository configured this way. The label-key-collision behavior itself (breaking/replacing `PATH`) is unconditionally reproducible per the existing test suite pattern (`test/models/shipit/review_stack_test.rb:59-65`, `test/lib/shipit/task_commands_test.rb`), confirming that arbitrary uppercase label names do flow unfiltered into env used for `Command`.

### Recommendation
In `Shipit::ReviewStack#env`, reject or namespace label-derived keys that collide with reserved/sensitive environment variable names (at minimum `PATH`, `BUNDLE_PATH`, `GEM_HOME`, `LD_PRELOAD`, `IFS`, etc.), e.g. prefix all label-derived keys with a fixed namespace (`LABEL_`) instead of the bare uppercased label name. Additionally, `Command#unbundled_env` should compute `PATH` last (i.e., not let arbitrary `@env` override it), or explicitly strip/ignore a `PATH` key coming from stack/task env before merging, so the shell's `PATH` is always Shipit's own constructed value.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (add)
test "#env does not allow a PR label to override PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]

  refute_equal "true", stack.env["PATH"]
  assert_includes stack.env["PATH"], Shipit.shell_paths.first if Shipit.shell_paths.any?
end

# test/lib/shipit/task_commands_test.rb (add)
test "#env does not let a PR label override the deploy PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new("true", env: env, chdir: ".")

  refute_equal "true", command.unbundled_env["PATH"]
end
```
Both assertions currently fail (i.e., `env["PATH"]`/`command.unbundled_env["PATH"]` become the literal string `"true"`), demonstrating the binding violation described above.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
