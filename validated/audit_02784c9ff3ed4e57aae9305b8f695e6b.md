### Title
Cross-organization webhook authentication/write mismatch allows forged writes to unrelated repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against using the attacker-controlled `repository.owner.login` field of the *unverified* JSON body, while every `Webhooks::Handlers::Handler` subclass identifies the record it mutates using the independent `repository.full_name` field from the very same body. Because these two fields are never cross-checked, an actor who legitimately controls a GitHub App/webhook secret for **one** organization configured on a multi-tenant Shipit instance can forge a validly-signed webhook whose `owner.login` matches their own org (so it passes signature verification) but whose `full_name` points at a **different** organization's repository/stack, causing handlers to write to that unrelated repository's data.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration to verify against like this: [1](#0-0) [1](#0-0) 

`repository_owner` is read directly from the untrusted JSON body before the signature has even been checked: [2](#0-1) 

That value is fed into `Shipit.github(organization:)`, which resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when the engine is configured in the documented multi-org mode: [3](#0-2) 

This multi-org mode is an explicitly supported, documented configuration (not a deployment quirk), as shown by the fixture used in tests: [4](#0-3) [5](#0-4) 

The signature check itself only proves the raw body was HMAC-signed with the secret belonging to whichever organization `repository_owner` names: [6](#0-5) 

Once verification passes, `WebhooksController#create` blindly dispatches the entire raw payload to the matching handlers: [7](#0-6) 

Every handler, however, determines the target `Repository`/`Stack` using a *different* field of the same payload — `repository.full_name` — with no relation back to `repository_owner`: [8](#0-7) [9](#0-8) 

The same disjoint pattern (`params.repository.full_name` looked up independently of the org used for signature verification) recurs across pull-request handlers that mutate stack/pull-request state (archiving, unarchiving, updating records): [10](#0-9) [11](#0-10) [12](#0-11) 

**Broken binding (equality that should hold but doesn't):**
`organization_whose_secret_verified_signature(repository.owner.login) == organization_owning(repository.full_name_written_by_handlers)`

Before the attacker's forged request: for any genuine GitHub-originated webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always the same organization, because GitHub itself populates both fields consistently for a single delivered event.

After the attacker's forged request: the attacker — who legitimately administers their own GitHub App/organization ("OrgTwo") registered on the same shared Shipit instance and therefore legitimately possesses OrgTwo's `webhook_secret` — crafts a raw JSON body where `repository.owner.login = "OrgTwo"` (so `verify_signature` selects and successfully validates against OrgTwo's own secret) but `repository.full_name = "OrgOne/victim-repo"` (an unrelated org/repo they do not control). The HMAC signature is computed over this exact crafted body with OrgTwo's real secret, so `verify_webhook_signature` returns `true`, and the handlers then look up and mutate `OrgOne/victim-repo`'s `Stack`/`Repository`/`PullRequest` records.

### Impact Explanation
This crosses the organizational trust boundary the webhook signature is meant to enforce, allowing cross-repository/cross-organization writes on a shared multi-tenant Shipit instance: an actor with no privileges over `OrgOne/victim-repo` can trigger `GithubSyncJob` for its stacks, archive/unarchive its review stacks, mutate its `PullRequest` records (`update`, label capture, close/reopen state), or create arbitrary `Team`/`User` records — all attributable to a supposedly-authenticated organization that is not actually the one being acted upon. This matches the "cross-repository writes" Critical-impact category, since state belonging to one tenant's repository can be altered by another tenant who never had write access to it.

### Likelihood Explanation
Exploitability requires only that the attacker administers/operates one legitimate GitHub App+webhook secret already configured on the shared Shipit instance (a normal, intended, unprivileged-relative-to-other-tenants position in a multi-org deployment) and can send an arbitrary POST with a body they fully control and sign themselves — no stolen secrets, no session, and no special GitHub scopes on the victim organization are needed. The root cause (`repository_owner` used for auth selection vs. `repository.full_name` used for target resolution, never cross-validated) is present in every request path through `WebhooksController` and every subclass of `Webhooks::Handlers::Handler`.

### Recommendation
- In `WebhooksController#verify_signature`, after determining which organization's secret validated the payload, enforce that every downstream-referenced repository (`payload.dig('repository','full_name')`, `payload.dig('organization','login')`, etc.) belongs to that same authenticated organization before dispatching to handlers.
- Alternatively, have `Webhooks::Handlers::Handler#repository_name` (and all direct callers of `params.repository.full_name`) validate that the resolved `Repository#owner` matches the organization that successfully verified the signature (`repository_owner`), rejecting the event otherwise.
- Add regression tests asserting that a validly-signed webhook whose `repository.owner.login` differs from the owner segment of `repository.full_name` is rejected.

### Proof of Concept
1. Attacker configures/administers their own GitHub App "OrgTwo" on the shared Shipit instance (as in `secrets_double_github_app.yml`), giving them OrgTwo's real `webhook_secret`.
2. Attacker crafts a JSON body for a `push` (or `pull_request`) event where:
   - `repository.owner.login = "OrgTwo"`
   - `repository.full_name = "OrgOne/victim-repo"` (a repo/stack they don't control)
3. Attacker computes `X-Hub-Signature` over this exact raw body using OrgTwo's `webhook_secret` and POSTs it to `WebhooksController#create`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")` and successfully verifies the signature against OrgTwo's secret.
5. `Shipit::Webhooks.for_event(event)` handlers run `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, resolving `OrgOne/victim-repo`, and perform writes on it (e.g., `stack.sync_github`, pull-request record updates, review-stack archive/unarchive) despite the request having been authenticated only for OrgTwo.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
