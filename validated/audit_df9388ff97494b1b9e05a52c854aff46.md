### Title
Cross-stack CCMenu status disclosure via stack-scoped API token bypass - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the target stack directly from `Stack.from_param!(params[:stack_id])` instead of using the stack-scoped collection (`stacks`) that every other endpoint in `Api::BaseController` relies on. This breaks the equality that should hold for a stack-scoped `ApiClient`: `stack the token authorizes == stack the request touches`. A `read:stack` token that was deliberately bound to one stack (`ApiClient#stack_id`) can be replayed against the CCMenu endpoint with a different `stack_id` in the URL and will disclose that other stack's deploy/build status.

### Finding Description
`ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . This scoping is enforced centrally in `Api::BaseController#stacks`, which restricts the visible/queryable stacks to `current_api_client.stack_id` when the client is scoped: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . `Api::StacksController#stack` correctly goes through this scoped collection (`stacks.from_param!(params[:id])`) [3](#0-2) , and this scoping is explicitly tested and relied upon: a client scoped to one stack "will only see that one stack" and returns zero results for other repositories [4](#0-3) [5](#0-4) .

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and looks the stack up from the full table:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 

The only permission check performed is `require_permission :read, :stack` [7](#0-6) , which calls `ApiClient#check_permissions!` — a generic capability check against the `permissions` array (`permissions.include?("read:stack")`), with no relation whatsoever to which specific stack the token is bound to: `raise InsufficientPermission, ... unless permissions.include?(required_permission)` [8](#0-7) .

Before/after the equality:
- Before (expected): `stack_id token authorizes` == `stack_id request touches`, enforced by `BaseController#stacks` for every other API resource.
- After (actual, in CCMenu only): the token's `read:stack` permission is checked, but the specific `Stack` row is fetched unscoped, so `stack_id token authorizes` != `stack_id request touches` for any `stack_id` supplied in the URL.

### Impact Explanation
Any holder of a valid, narrowly stack-scoped `read:stack` token (the exact kind of credential the system supports specifically to *limit* exposure to one stack) can escalate to reading the deploy/build status, last commit SHA, last build label, and web URL of every other stack in the instance by changing the `stack_id` path segment of `GET /api/*stack_id/ccmenu`. This is an authorization-scope escalation: a credential meant to authorize one stack ends up disclosing state for stacks it was never granted access to, matching the "High — escalation into authorization ... unauthenticated read of stack state ... deploy output" class of impact.

### Likelihood Explanation
The bypass requires only possession of any `read:stack`-permitted `ApiClient` token (regardless of which stack it was scoped to) and knowledge/guessing of another stack's `stack_id` (which is just `owner/repo/environment`, often predictable or discoverable). No cryptographic material or privileged account is needed beyond a token that is explicitly designed to be limited to a single stack — the entire point of stack scoping is defeated by this one controller.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoped lookup used elsewhere, e.g. `stacks.from_param!(params[:stack_id])` (using `Api::BaseController#stacks`), so a stack-scoped client can never resolve a stack outside its `stack_id`. Add regression tests asserting that a token scoped to Stack A receives 403/404 when requesting CCMenu status for Stack B.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id = A` with `permissions: ["read:stack"]` (the same shape as the `here_come_the_walrus` fixture) [4](#0-3) .
2. Send `GET /api/B_owner/B_repo/B_environment/ccmenu?token=<A-scoped-token>` (or via Basic Auth header).
3. `authenticate_api_client` succeeds because the token itself is valid [9](#0-8) ; `require_permission :read, :stack` succeeds because the token generically has `read:stack` [8](#0-7) ; `stack` resolves Stack B directly, unscoped [6](#0-5) .
4. The response renders Stack B's CCMenu XML (name, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl) even though the token was only ever authorized for Stack A.
