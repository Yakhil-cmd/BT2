### Title
Autonomous Agents that depend on a single hard-coded `data_feed`/`in_data_feed` oracle address can become permanently unable to execute their payout logic if that oracle stops posting, freezing user funds in the AA - (File: `formula/evaluation.js`)

### Summary
The `data_feed` and `in_data_feed` oscript primitives let an AA query a price/value from one or more oracle addresses. Like the Chainlink aggregator referenced by Vader's `TwapOracle.consult()`, the oracle address(es) used by a data-feed lookup are fixed at AA-definition time and cannot be changed later, because AA definitions in ocore are immutable once deployed. If the referenced oracle address stops posting new values (key loss, abandonment, compromise, or simply ceasing operation), any AA logic branch that unconditionally reads that feed (no `ifnone` fallback) will permanently fail to execute, exactly mirroring the reported bug class of "stuck stale oracle -> irrecoverable dependent logic."

### Finding Description
`data_feed[[oracles=..., feed_name=...]]` is evaluated by `getDataFeed()` in `formula/evaluation.js`, which calls `dataFeeds.readDataFeedValue()` and, if no value is found for the given `feed_name`/oracle set, returns `cb("data feed " + feed_name + " not found")` unless an `ifnone` parameter was supplied by the AA author. [1](#0-0) 

This error is escalated via `setFatalError`, which fails the formula evaluation for that `if`/`init` block, causing the AA response to bounce. [2](#0-1) 

`in_data_feed` behaves the same way, delegating to `dataFeeds.dataFeedExists`, which simply returns `false` if the feed condition is never satisfied — the branch guarded by it can never fire. [3](#0-2) 

Both primitives take the oracle address(es) as a plain string parameter with no built-in mechanism to reassign or add fallback oracle addresses once the AA has been deployed. The `test/samples/futures_contract.oscript` sample demonstrates this exact pattern in production-style code: a hard-coded oracle address `X55IWSNMHNDUIYKICDW3EOYAWHRUKANP` is used to gate a "blackswan" state transition and to compute the exchange rate used for the maturity payout, with an explicit comment acknowledging the risk ("data_feed will abort if the exchange rate not posted yet") but no way to swap in a different oracle if that one goes stale: [4](#0-3) 

Since AAs are immutable by design (there is no analog of a "definition change" for AA code, only for regular wallet addresses), once such an AA has collected funds, if its designated oracle permanently stops posting the required `feed_name`, the AA's core payout branch becomes irrecoverably unreachable — every attempt to trigger it bounces at the `data_feed`/`in_data_feed` evaluation step in `formula/evaluation.js`.

### Impact Explanation
Any AA whose exit/payout logic (e.g., maturity payout, liquidation, order execution, price-conversion) depends on a single-oracle `data_feed` lookup without a fallback (`ifnone`) is at risk. If the oracle silently stops posting (whether due to key compromise, key loss, hosting failure, or the operator abandoning the service), user funds already sent to that AA in expectation of processing through the price-dependent branch can become permanently stuck, since:
1. The relevant AA logic path can never evaluate successfully (`data_feed` fatally errors, bouncing the trigger).
2. There is no protocol-level way to redirect the AA to a different oracle address post-deployment.

This is a fund-freezing condition analogous to the reported TwapOracle issue, reachable by any AA author who designs (and by any user who sends funds into) an AA using this common oracle-consumption pattern.

### Likelihood Explanation
Oracle abandonment/compromise is a low-probability but realistic external event (same caveat acknowledged by the original Vader report and judge). The likelihood is increased in ocore's case because: (1) `data_feed`/`in_data_feed` explicitly documented usage pattern in sample AAs shows single, hard-coded oracle addresses with no redundancy, and (2) AA immutability means there is categorically no governance/upgrade path available at the protocol level to remediate a stuck oracle for an already-deployed AA, unlike some other blockchains where proxy patterns permit contract upgrades.

### Recommendation
- Encourage/require AA authors to always specify an `ifnone` fallback value or a multi-oracle quorum (`oracles='ADDR1:ADDR2'`) plus a staleness/liveness check (e.g., using `min_mci` together with a manual "circuit breaker" state variable) so a stalled oracle cannot deadlock the AA's core logic.
- Consider documenting/providing a standard idiom or helper contract pattern for AA authors that allows a governance address to update which oracle address(es) an AA reads from by storing the oracle address in AA state (`var['oracle']`) rather than embedding it as a literal, so a governance-triggered `state` message can repoint `data_feed[[oracles=var['oracle'], ...]]` to a new oracle if the original becomes stale.
- Add prominent documentation/warnings in the oscript reference for `data_feed`/`in_data_feed` about the permanent-DoS risk of embedding a single oracle address directly in AA logic without an `ifnone` fallback or governance-updatable state variable.

### Proof of Concept
1. Deploy an AA using the pattern from `test/samples/futures_contract.oscript`, where a payout branch does:
   `$exchange_rate = data_feed[[oracles='ORACLE_ADDR', feed_name='RATE']];`
   with no `ifnone` clause. [5](#0-4) 
2. Users send USD/GB assets and bytes into the AA in expectation of the maturity-date payout branch executing once `timestamp >= maturity`.
3. The oracle operator for `ORACLE_ADDR` stops posting the `RATE` feed value (key loss/abandonment).
4. Every subsequent trigger reaching the `data_feed[[...]]` call fails validation exactly as unit-tested in `formula.test.js` ("formula - datafeed not found" returns `null`, causing the surrounding `if` to bounce): [6](#0-5) 
5. Because the AA is immutable and there is no protocol mechanism to point `data_feed` at a new oracle address, the maturity-payout branch is permanently unreachable, and any assets held by the AA that depend on this branch for withdrawal remain stuck.
