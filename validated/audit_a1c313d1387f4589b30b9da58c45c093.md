### Title
Cross-repository status forgery via unscoped commit SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook by selecting a `GithubApp`/secret keyed on an attacker-supplied field — `repository.owner.login` (or `organization.login`) taken straight from the unparsed JSON body — and validating the HMAC signature against that org's `webhook_secret`. [1](#0-0)  Once the signature check passes for *that* organization, the raw `params` hash is dispatched unmodified to every registered handler for the event. [2](#0-1) 

`StatusHandler`, unlike every other handler in the codebase, never re-derives or checks the repository the event claims to be about. All other handlers scope their side effects through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (the base `Handler#stacks` helper, or explicit `repository` methods in the PR handlers). [3](#0-2) [4](#0-3)  `StatusHandler#process`, however, looks up commits **globally, by SHA alone**, with no repository/stack scoping whatsoever: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [5](#0-4) 

This breaks the equality the engine is supposed to enforce: *the GitHub organization whose signature was verified* must equal *the repository/stack whose state is written*. Because `Commit.sha` is not scoped per-repository in the lookup, a webhook that is validly signed for **organization A** can create a `Status` (and thus flip CI state) on a commit belonging to a stack owned by **organization B**, as long as the attacker knows/guesses that commit's SHA (SHAs are public information visible on GitHub for any repo the attacker can view).

### Finding Description
1. `verify_signature` picks the signing organization from `params.dig('repository','owner','login') || params.dig('organization','login')` — a value fully controlled by the request body, not cryptographically bound to anything else in the payload. [6](#0-5) 
2. The webhook is authenticated only by verifying that `X-Hub-Signature` matches `HMAC-SHA1(webhook_secret_for(that_organization), raw_body)`. [7](#0-6) 
3. Nothing ties the *authenticated organization* to the *repository/stack that will actually be mutated*: `StatusHandler` ignores `repository.full_name` entirely and matches purely on `sha`, which is a global, cross-stack, cross-organization identifier space in this schema (`Commit.where(sha: params.sha)` has no `stack_id`/`repository_id` filter). [5](#0-4) 
4. `commit.create_status_from_github!` creates a `Status`, which triggers `after_commit :schedule_continuous_delivery` on creation, feeding `Commit#deployable?`/`Commit#schedule_continuous_delivery`, which schedules `ContinuousDeliveryJob` when the stack has `continuous_deployment: true` and the commit becomes `success`. [8](#0-7) [9](#0-8) [10](#0-9) 

So: an attacker who can produce **any** validly-signed webhook (for any organization configured in `secrets.github`, including an organization whose `webhook_secret` is left blank — a supported and documented configuration, `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank [11](#0-10) ) can forge a `status` event whose `repository` block names their own org/repo, but whose `sha` targets a commit belonging to a completely different stack/organization managed by the same Shipit instance. Shipit will happily mark that unrelated commit `success`, satisfying `ci.require` and unblocking/auto-triggering a deploy for a commit that never actually passed CI in its own repository's checks.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary explicitly called out as in-scope: the org whose HMAC secret validated the request has no enforced relationship to the stack whose CI status is forged. The concrete impact is an **unauthorized deploy/rollback trigger**: forging a `success` status on a commit in a `continuous_deployment: true` stack schedules `ContinuousDeliveryJob`, which can deploy a commit that never passed CI in the target repository. In multi-organization Shipit installations (a documented, first-class configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), an entity with legitimate webhook credentials for one tenant organization can affect the deploy pipeline of a completely different tenant organization on the same Shipit instance, without ever needing that other organization's secret, GitHub token, or session.

### Likelihood Explanation
Requires only: (a) knowledge of a target commit SHA (public GitHub information), (b) the ability to produce one validly-signed webhook payload for any organization configured on the instance (trivially true if any configured org has a blank `webhook_secret`, which the shipped example configs treat as an acceptable/default value). No repository write access, session, or `ApiClient` token is needed for the victim stack. This is a straightforward, deterministic bug (missing repository scoping in one handler) rather than a race condition or resource-exhaustion issue.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the payload, mirroring every other handler: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and filter `Commit.where(sha: params.sha, stack: stacks)` (or equivalent), so a webhook can only mutate commits belonging to the stack(s) of the repository it claims to represent — and reject/ignore the event if that repository's organization does not match the organization whose secret authenticated the request.

### Proof of Concept
1. Attacker controls (or is a member of) organization `attacker-org`, which is configured in Shipit's `secrets.github` with a blank/absent `webhook_secret` (a supported configuration per the example secrets files).
2. Attacker identifies the SHA of a commit belonging to `victim-org/victim-repo`, a stack with `continuous_deployment: true` and `ci.require` configured (SHA is public on GitHub).
3. Attacker sends:
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<any value, or omitted; unsigned request accepted when webhook_secret blank>
Content-Type: application/json

{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/scratch-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://example.com"
}
```
4. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies (trivially) against `attacker-org`'s blank secret, and allows the request. [12](#0-11) 
5. `StatusHandler#process` finds the commit purely by SHA (irrespective of the `attacker-org/scratch-repo` claim) and creates a `success` `Status` on it, potentially triggering `ContinuousDeliveryJob` for `victim-org/victim-repo`. [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
