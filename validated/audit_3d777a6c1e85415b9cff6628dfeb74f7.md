## Title
Missing length-parity check between `secondary_signer_addresses` and `secondary_signers` in `TransactionAuthenticator::verify` allows unauthenticated secondary-signer addresses to be admitted - (File: types/src/transaction/authenticator.rs)

### Summary
`TransactionAuthenticator::verify` for the `MultiAgent` (and structurally similar `FeePayer`) variant never asserts that `secondary_signer_addresses.len() == secondary_signers.len()`. It only iterates over the provided `secondary_signers` vector and verifies each entry against the signed message; any address present in `secondary_signer_addresses` that lacks a corresponding entry in `secondary_signers` is never checked at all, yet the address still remains part of the authenticator's declared secondary-signer set returned to callers.

### Finding Description
The relevant code: [1](#0-0) 

```rust
Self::MultiAgent {
    sender,
    secondary_signer_addresses,
    secondary_signers,
} => {
    let message = RawTransactionWithData::new_multi_agent(
        raw_txn_for_signing.into_owned(),
        secondary_signer_addresses.clone(),
    );
    sender.verify(&message)?;
    for signer in secondary_signers {
        signer.verify(&message)?;
    }
    Ok(())
},
```

The loop `for signer in secondary_signers` walks only the `secondary_signers` vector. There is no check that this vector's length matches `secondary_signer_addresses.len()`, nor any zip/positional correspondence enforced here. If an attacker (the legitimate sender, using their own valid key) constructs a `MultiAgent` authenticator with `secondary_signer_addresses = [addrA, addrB, addrC]` but `secondary_signers = []` (or fewer entries), `verify()` still returns `Ok(())` as long as `sender.verify(&message)` succeeds — no error is raised for the unauthenticated addresses.

The `MAX_NUM_OF_SIGS` cap similarly relies on `self.secondary_signers()` (the authenticator vector) and not on `secondary_signer_addresses`, so it does not detect or reject the mismatch either: [2](#0-1) 

The `FeePayer` variant has the analogous pattern, pushing `secondary_signers` (not addresses) into `to_verify`: [3](#0-2) 

### Impact Explanation
`secondary_signer_addresses` is the field that downstream consumers (VM prologue / entry-function signer-argument binding) treat as the authoritative list of accounts participating as signers in a multi-agent transaction. Since `verify()` succeeds without requiring a 1:1 correspondence between declared addresses and verified authenticators, a transaction can be admitted that claims additional secondary-signer addresses without any actual signature over those addresses ever being checked. This breaks the intended invariant that every address in `secondary_signer_addresses` has a cryptographically verified corresponding entry in `secondary_signers`, which is exactly the property the exploit question describes.

### Likelihood Explanation
This requires no privileged access — an ordinary transaction sender controls the serialized `TransactionAuthenticator` bytes they submit (BCS-encoded `SignedTransaction`), and can freely set `secondary_signer_addresses` and `secondary_signers` to vectors of different lengths since nothing in `verify()` rejects this shape.

### Recommendation
Add an explicit length-equality assertion (`ensure!(secondary_signer_addresses.len() == secondary_signers.len(), ...)`) at the start of both the `MultiAgent` and `FeePayer` verification arms in `TransactionAuthenticator::verify`, and/or zip the two vectors together so every address is paired with — and requires — a validated authenticator.

### Proof of Concept
Construct a `RawTransaction`, build `TransactionAuthenticator::MultiAgent { sender, secondary_signer_addresses: vec![addrA, addrB], secondary_signers: vec![] }` (only the sender authenticator is real; secondary vector left empty), and call `verify(&raw_txn)`. Under the current implementation this returns `Ok(())` because the `for signer in secondary_signers` loop is a no-op, whereas the invariant expected by the review question (an error when counts differ) is never enforced.
