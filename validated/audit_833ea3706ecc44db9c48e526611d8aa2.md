### Title
`ReopenedHandler#unarchive?` shares `OpenedHandler#provision?`'s operator-precedence bug, allowing re-provisioning on repos with `review_stacks_enabled: false` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses the same boolean expression as `OpenedHandler#provision?`, where Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to gate only the `allow_all` clause, not the `allow_with_label`/`prevent_with_label` clauses. A repository owner who disables review stacks (`review_stacks_enabled: false`) but still has a `provisioning_behavior` of `allow_with_label` or `prevent_with_label` configured will still have closed/archived PR stacks unarchived and re-queued for provisioning when a PR is reopened.

### Finding Description
The binding that should hold is: `repository.review_stacks_enabled == true` must gate all stack unarchival/re-provisioning paths, i.e. `unarchive?` should be logically equivalent to `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.

Instead, the code at [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `review_stacks_enabled == false` but `provisioning_behavior == :allow_with_label` and the PR carries the configured label, or `provisioning_behavior == :prevent_with_label` and the PR lacks the label, `unarchive?` still evaluates `true`.

This is confirmed as an exact structural copy of the bug in `OpenedHandler#provision?` at [2](#0-1) .

Exploit flow: a repository maintainer previously had review stacks enabled and a stack was created and later closed/archived for a PR (any user's PR that was merged/closed goes through `ClosedHandler` → `ReviewStackAdapter#archive!`). The repository is later reconfigured to `review_stacks_enabled: false` (opting out) while `provisioning_behavior` remains `allow_with_label` or `prevent_with_label` (not reset). Any attacker who can reopen that PR (the PR author, or anyone who can push to that PR's branch and toggle GitHub's reopen action) sends a `pull_request` `reopened` webhook. `ReopenedHandler#process` at [3](#0-2)  calls `respond_to_pull_request_reopened?` → `unarchive?`, which returns `true` due to the precedence bug, and then calls `stack.unarchive!`. `ReviewStackAdapter#unarchive!` at [4](#0-3)  re-adds the stack to `Shipit::ReviewStackProvisioningQueue` and calls `stack.unarchive!`, which re-triggers provisioning of the attacker's branch/`shipit.yml`, bypassing the repository's opt-out of review stacks (`review_stacks_enabled: false`).

None of the existing guards (`ExplicitParameters` schema, `drop_unhandled_event`, webhook signature verification) address this — the payload is well-formed and legitimately signed if the attacker owns/controls the repository/PR that triggers the webhook; the bug is purely in the boolean logic gating `unarchive?`.

### Impact Explanation
This causes re-provisioning (running `TaskCommands#perform` / shell commands from `shipit.yml`) for a repository/PR whose owner explicitly disabled review-stack provisioning (`review_stacks_enabled: false`). Since provisioning runs commands sourced from the PR's branch content, this is a path to RCE on the deploy host via attacker-controlled `shipit.yml`, matching the Critical impact category ("a command running that should not"). It is repeatable for any archived stack under any repository configured with `review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label`, as long as a stack for that PR previously existed and was archived.

### Likelihood Explanation
Preconditions: the target repository must have (1) previously had a review stack created for the PR (i.e., `review_stacks_enabled` was `true` at some point, or the stack was created another way), (2) later set `review_stacks_enabled: false`, while (3) leaving `provisioning_behavior` at `allow_with_label` or `prevent_with_label` rather than resetting it. This is a plausible but non-default misconfiguration during a partial opt-out (an operator disabling stacks going forward without clearing the provisioning behavior). Given these preconditions, the attack cost is trivial: reopening a PR (or having a bot force it via GitHub webhook), no secrets or elevated Shipit permissions required.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression, matching the intended binding, in both `ReopenedHandler#unarchive?` and `OpenedHandler#provision?`:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
minitest test (mirrors `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`'s `configure_provisioning_behavior` helper):

```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with prevent_with_label allowing it" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = [] # no label -> prevent_with_label clause evaluates true

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Binding under test: repository.review_stacks_enabled (false) must equal
  # whether unarchival/provisioning occurs (should be false, but bug makes it true)
  assert stack.reload.archived?, "Expected stack to remain archived since review_stacks_enabled is false"
end
```

With the current code, this test fails: `stack.reload.archived?` is `false` and `assert_pending_provision(stack)` would pass, proving the stack was unarchived and re-queued despite `review_stacks_enabled: false`.
