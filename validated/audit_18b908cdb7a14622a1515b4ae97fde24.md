### Title
Autonomous Agent `balance[asset]` includes the just-received trigger funds, causing share/ratio-based AAs to mint fewer shares to the depositor whose own funds are miscounted as prior pool balance - (File: `aa_composer.js`)

### Summary
In ocore, when a unit triggers an Autonomous Agent (AA), the payment amounts sent to the AA in that same trigger unit are credited to the AA's balance **before** the AA's `init`/`messages` oscript formulas are evaluated. Any AA that issues proportional shares/tokens to a depositor by reading `balance[asset]` directly (instead of subtracting the incoming `trigger.output[[asset=...]]` first) will treat the depositor's own deposit as if it were already part of the pre-existing pool, producing the exact "assets deposited before calculating shares" bug described in the external report for `GovernanceHYBR.sol`.

### Finding Description
`getTrigger()` sums all payment outputs addressed to the AA in the triggering unit into `trigger.outputs[asset]` [1](#0-0) .

Before the AA's formulas run, `handleTrigger()` calls `updateInitialAABalances()`, whose own comment states it is meant to "add the coins received in the trigger" to the AA's balance [2](#0-1) . For the live-execution path (non-`bAir`), the same crediting happens directly against the persisted `aa_balances` table before `evaluateAA` is invoked [3](#0-2) , and `evaluateAA`/`sendUnit` (where `init`/`messages` formulas, including `balance[...]` reads, are evaluated) only run afterward [4](#0-3) .

Because of this ordering, `balance[asset]` as read inside an AA's oscript formulas already **includes** the funds from the current trigger. Any AA that computes a proportional share issuance as `issued_shares = (deposited_amount / balance[asset]) * outstanding_shares` (analogous to `GovernanceHYBR::calculateShares` using post-deposit `totalAssets()`) will inflate the denominator with the depositor's own funds, minting fewer shares than the correct 1:1 ratio - identical to the H-01 root cause.

The ocore repository's own bundled example AA for a Uniswap-like market maker demonstrates that this is a real, easy-to-miss pitfall: it explicitly subtracts the trigger output before computing ratios (`$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]`, `$bytes_balance = balance[base] - trigger.output[[asset=base]]`) precisely to avoid this bug [5](#0-4) . Other bundled sample AAs that accept deposits and later distribute funds proportionally (e.g., the fundraising proxy computing `$missing_amount` from `balance[$destination_aa][base] + $total_raised`) rely on similarly careful subtraction of amounts already accounted for, confirming that `balance[]` semantics require this manual correction everywhere shares/ratios are computed from pooled balances [6](#0-5) .

### Impact Explanation
Any unprivileged unit poster can trigger an AA (an AA author deploys a vault/LP/share-style AA reachable by any user's trigger unit). If that AA computes issued shares/tokens from `balance[asset]` without subtracting the incoming `trigger.output[[asset=asset]]`, every depositor after the first receives fewer shares than the correct 1:1 (or pool-ratio) amount, permanently diluting their own deposit and causing quantifiable fund loss for the depositor and unjust enrichment of existing shareholders - matching the "AA fund loss" impact category. Because this affects share/token minting logic inside AA state, the error is baked into on-chain state (`var['...']`, issued asset balances) and cannot be corrected after the fact.

### Likelihood Explanation
This is a design characteristic of every AA that combines deposits with proportional share issuance, not a validation bug that ocore itself catches or warns about. It is easy to introduce (a naive/first implementation of any pooled-vault, LP-token, dividend, or bonding-curve AA is likely to just read `balance[asset]`), as evidenced by the fact that ocore's own official example AA needed to specifically special-case the subtraction to avoid the bug. Given the number of independent AA authors writing arbitrary oscript, and the total absence of any framework-level protection or lint/validation warning against this pattern in `aa_validation.js`/`formula/validation.js`, likelihood of at least one deployed AA getting this wrong is high.

### Recommendation
- Document explicitly (in AA developer docs and inline near the `balance[]` grammar/evaluation code) that `balance[asset]` inside a triggered AA already includes the current trigger's incoming funds, and that any pool/share-ratio calculation must use `balance[asset] - trigger.output[[asset=asset]]` (pre-deposit balance) when calculating the ratio to mint against.
- Consider exposing a dedicated `pre_trigger_balance[asset]` (or similarly named) formula primitive that returns the AA's balance without the current trigger's incoming outputs, removing the need for authors to manually subtract `trigger.output[[asset=...]]` and eliminating this class of off-by-one/dilution bugs.
- Add this pattern to `aa_validation.js`/oscript linting as a warning when `balance[X]` is used in the same `init`/`if` block alongside a proportional-mint payment output for the same asset without an accompanying subtraction of `trigger.output[[asset=X]]`.

### Proof of Concept
Given the official market-maker sample pattern, an equivalent but *unfixed* AA would compute:
```
// vulnerable pattern possible in any oscript AA
$issue_amount = round(trigger.output[[asset=base]] / balance[base] * var['shares_outstanding']);
```
Sequence:
1. AA has `balance[base] = 100e9` (Bob's earlier 1:1 deposit), `var['shares_outstanding'] = 100e9`.
2. Alice sends `trigger.output[[asset=base]] = 100e9`.
3. By the time Alice's `init` formula runs, `updateInitialAABalances()` has already credited her deposit, so `balance[base] = 200e9` [7](#0-6) .
4. `$issue_amount = round(100e9 / 200e9 * 100e9) = 50e9` instead of the correct `100e9`, exactly mirroring the Bob/Alice 100/50 share example in the external report. [2](#0-1) [5](#0-4)

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
