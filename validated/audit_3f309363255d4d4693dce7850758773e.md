### Title
Cross-repository status forgery triggers unauthorized deploy via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's `repository`/`organization` matches the commit's actual stack/repository. Because `verify_signature` in `WebhooksController` only proves the payload was signed by *some* configured GitHub organization/app (the one named in the payload's own `repository.owner.login`), a webhook correctly signed for organization B can still mutate state belonging to stack A if a commit with the same `sha` exists under A.

### Finding Description
The binding the code implicitly relies on is: **the organization whose `webhook_secret` verified the payload == the organization owning the stack that the payload mutates**. This does not hold.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login')` (the payload's *own* claimed owner) and fetches `Shipit.github(organization: repository_owner)` to verify the HMAC. This only proves "this payload was legitimately signed for the organization named inside the payload itself" — it proves nothing about which stack/commit the handler will subsequently touch.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ```
  This queries **all** `Commit` rows across **all** stacks/repositories matching `sha`, with no `WHERE` clause on repository, org, or stack. `commit.create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using `commit.stack_id`, i.e., whatever stack actually owns that commit row — not the stack tied to the org that signed the request.
- `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` then fire regardless of who created the status, feeding `Stack#next_commit_to_deploy` → `Stack#trigger_continuous_delivery` → `Stack#trigger_deploy` (`app/models/shipit/stack.rb:210-229`), which is unconditioned on any actor/org identity check.
- Git commit SHAs are content-addressed (based on tree, parent, author, committer, message, timestamps) and are not bound to a specific repository. If stack A contains a commit whose object is exactly reproducible (e.g., a deterministic/empty commit), an attacker can create a bit-for-bit identical commit object in repository B that they control, giving it the same `sha`.
- No existing guard closes this gap: `verify_signature` validates provenance of the payload relative to the payload's own named org, not relative to the *commit* being mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `StatusHandler.params` validates shape, not repository ownership; there is no `repository.full_name` / stack lookup anywhere in this handler to bind the mutation back to the authenticating org.

Exploit flow: attacker pushes/creates the colliding commit in repository B (which they own) and triggers (or directly emits, if their org's App installation is capable of generating a signed delivery to the shared endpoint) a `status` webhook with `sha` equal to A's commit and `state: success`. `WebhooksController#verify_signature` succeeds because it only checks the signature against B's own configured secret/org. `StatusHandler#process` finds the pre-existing `Commit` row in stack A with that sha and creates a `success` `Status` scoped to `stack_id` of A. This flips `deployable?` for that commit, `Stack#trigger_continuous_delivery` (running via `ContinuousDeliveryJob` / `schedule_continuous_delivery`) picks it via `Stack#next_commit_to_deploy`, and `Stack#trigger_deploy` runs a real deploy of stack A.

### Impact Explanation
An attacker with no relationship to stack A's repository or organization can cause an unauthorized deploy to fire against stack A by supplying a forged CI status from an unrelated, attacker-controlled repository. This is a record (a `Status`, and downstream a `Deploy`) written for stack A that was never authenticated by A's owning org — matching the Critical category "a payload for one repository mutating another's stack, commit, task, or team, or an unauthorized deploy". The blast radius is any stack with `continuous_deployment: true` that has an otherwise-deployable commit blocked only on a missing/failing CI status, and is repeatable per matching sha collision the attacker can engineer.

### Likelihood Explanation
Preconditions are non-trivial but plausible in practice:
- The attacker must control a repository/org that can produce a validly signed `status` webhook to Shipit's single shared endpoint. In the common single-App configuration (`docs/setup.md` default, one global `webhook_secret`/`app_id` for the whole Shipit install), this reduces to "the GitHub App is installed on the attacker's account," which depends on the App's installation visibility (public apps can often be installed by any account) — this part is a GitHub App configuration concern, not purely code, but it is realistic in the documented single-org setup shown in `docs/setup.md`.
- The attacker must reproduce an existing commit's exact SHA in their own repo. This is feasible only for content-identical, deterministic commits (e.g., an "identical empty commit" with matching tree/parent/author/committer/timestamps/message as stated in the question), not for arbitrary commits — this materially limits real-world applicability but is not impossible, especially against automated/bot-authored empty commits with predictable metadata.
- No Shipit credential, session, or API token is needed at any point; the only requirement is control of a repository able to deliver a signed webhook and knowledge/reproduction of a target commit's exact content.

### Recommendation
In `StatusHandler#process` (and any other handler resolving state purely by `sha`), scope the `Commit` lookup by the repository/organization asserted in the payload and verified by the signature, e.g. resolve `Repository`/`Stack` from `params.dig('repository','full_name')` (or the equivalent verified owner) first, then constrain `Commit.where(sha: params.sha, stack: stack)` (or join through `stacks.repository`) so a status can only be attributed to commits that actually belong to the same repository that was cryptographically verified as the sender. Apply the same repository-scoping check consistently across all webhook handlers that look up records by SHA/ref alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "a status webhook signed for org B cannot deploy stack A via a colliding sha" do
  stack_a = shipit_stacks(:shipit) # continuous_deployment: true, org "shopify"
  commit  = stack_a.commits.last
  commit.statuses.destroy_all
  refute_predicate commit, :deployable? # blocked only for lack of success status

  # Simulate org B's payload: repository.owner.login == "attacker-org"
  # but sha == commit.sha (content-identical commit reproduced in B's repo)
  payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => 'attacker-org/evil-repo' }
  }.to_json

  Shipit.stubs(:github).with(organization: 'attacker-org')
        .returns(stub(verify_webhook_signature: true))

  request.headers['X-Github-Event'] = 'status'
  assert_no_difference -> { Deploy.count } do   # EXPECTED after fix; currently fails (Deploy.count increments)
    post :create, body: payload, as: :json
  end
end
```
Assert on both sides of the binding: `commit.stack_id == stack_a.id` (unchanged, the vulnerable read) vs. the org that verified the signature (`attacker-org`) `!= stack_a.repository.owner` — currently the code never compares these two, which is the root cause; the fix must make the handler reject/skip processing when they differ.
