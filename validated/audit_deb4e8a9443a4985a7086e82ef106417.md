### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets one repository's `status` webhook write CI status onto another repository's commit with the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)`, which is not scoped to the repository that authenticated the webhook, unlike every other handler in the same directory. Because the `commits` table only enforces uniqueness on `[sha, stack_id]` (not a global unique SHA), a `status` webhook signed for repository A will write a `Status` row (and flip `deployable?`/`blocked?`) onto commits belonging to repository B's stacks whenever the SHA happens to collide (e.g., a fork/mirror sharing history with the victim's tracked repo).

### Finding Description
The broken binding is: `webhook.repository.full_name == commit.stack.repository.full_name` must hold before a status write is applied to that commit — this is enforced everywhere else via `Handler#stacks`, `def stacks; Repository.from_github_repo_name(repository_name)&.stacks || Stack.none; end` [1](#0-0)  which is correctly used by `CheckSuiteHandler`, `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...) }` [2](#0-1) .

`StatusHandler#process`, however, never calls `stacks` or filters by repository at all:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This query hits every `Commit` row across every stack/repository in the Shipit instance that has a matching `sha`, regardless of which repository's webhook secret was actually used to authenticate the request. The `commits` table's uniqueness constraint is `[sha, stack_id]`, not `[sha]` alone: `add_index :commits, %i(sha stack_id), unique: true` [4](#0-3) , and the schema confirms the same composite index, `t.index ["sha", "stack_id"], name: "index_commits_on_sha_and_stack_id", unique: true` [5](#0-4) , i.e. the same SHA is explicitly permitted to exist in multiple stacks belonging to different repositories.

`create_status_from_github!` then persists a `Status` scoped to the commit's own `stack_id` and mutates deployability state via `add_status`, which recomputes `status`, emits `deployable_status`/`commit_status` hooks, and calls `stack.schedule_merges` if the new state is `success`/`pending`. [6](#0-5) [7](#0-6)  `Commit#deployable?` and `#blocked?` depend directly on this state. [8](#0-7) 

**Attack flow:**
1. Attacker owns a GitHub repository/org enrolled in the same Shipit instance (a normal, low-privilege action — adding one's own repo as a stack is not restricted to Shipit operators).
2. Attacker's repo shares a commit SHA with the victim's tracked repo — realistic when the victim repo is public/open-source and the attacker maintains a fork/mirror with identical history, or when the same commit is pushed to two repos Shipit tracks.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login` set to the attacker's own org, and body `{sha: <shared_sha>, context: "ci/test", state: "success"}`, signed with the attacker's own known webhook secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` using the attacker's own org and successfully verifies the signature against the attacker's own secret. [9](#0-8)  This guard only proves the request came from *some* repository the attacker controls — it does not prove the payload's SHA belongs to that repository's stacks.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds both the attacker's own commit and the victim's commit sharing that SHA, writing a `success` status to both. [3](#0-2) 
6. If `ci/test` is a required status on the victim's stack, this flips `deployable?` to true and can trigger `stack.schedule_merges`, allowing an unauthorized merge/deploy; conversely, sending `state: "failure"` can block a legitimate victim deploy.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters`) only validate the signature belongs to *some* org and that the payload schema is well-formed — none of them enforce that the SHA in the payload belongs to a commit owned by the repository whose secret signed the request. That check is missing specifically in `StatusHandler`, unlike `CheckSuiteHandler`/other handlers that use `Handler#stacks`.

### Impact Explanation
An attacker who controls any repository enrolled in the Shipit instance can write arbitrary `Status` rows (`context`, `state`) onto commits in a completely different, victim-owned stack whenever a SHA collision (shared history) exists — this is a payload from one repository mutating another repository's commit/stack records, matching the "Critical" impact category (cross-tenant state manipulation resulting in unauthorized deploy/merge or block). The write is repeatable for any SHA the attacker can arrange to share with the victim's history, and blast radius extends to any stack in the instance whose commits table contains that SHA.

### Likelihood Explanation
Preconditions: the attacker must have their own repository/stack registered in the same Shipit deployment (low cost, self-service in most configurations), and must be able to produce/find a commit SHA that appears in both their own repository and the victim's tracked repository (feasible for public/open-source projects with forks/mirrors, or any scenario where identical commits are pushed to multiple tracked repos). No secrets belonging to the victim, Shipit operators, or GitHub App are required — only the attacker's own legitimately-issued webhook secret for their own repo. This is fully repeatable and requires no privileged role.

### Recommendation
Scope `StatusHandler#process` by repository the same way `CheckSuiteHandler` does: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` from the webhook payload, then only update commits within `stack.commits.where(sha: params.sha)` for those stacks, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status webhook only affects commits belonging to the authenticated repository" do
  victim_stack = shipit_stacks(:shipit) # repo: "shopify/shipit-engine"
  attacker_stack = Stack.create!(repository: Repository.create!(owner: 'attacker', name: 'evil-fork'))

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")

  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/test',
    'repository' => { 'full_name' => attacker_stack.github_repo_name }
  }

  # Binding under test: victim_commit.statuses must remain empty because the
  # webhook was authenticated only for attacker_stack's repository.
  assert_equal 0, victim_commit.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # After processing, StatusHandler#process's unscoped `Commit.where(sha:)`
  # writes a status onto BOTH commits, breaking the equality:
  # webhook.repository.full_name == commit.stack.repository.full_name
  assert_equal 1, attacker_commit.reload.statuses.count   # expected (authenticated repo)
  assert_equal 0, victim_commit.reload.statuses.count      # currently FAILS: attacker's payload leaks into victim stack
end
```
This test is expected to fail against current code (victim commit incorrectly receives the status), demonstrating the cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
