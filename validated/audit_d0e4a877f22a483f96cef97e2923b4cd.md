### Title
Missing `return` after error path causes callback to fire twice, leading to double-unlock crash in private-payment handling - (File: network.js)

### Summary
`handleSavedPrivatePayments()` in `network.js` processes private-payment chains that a payment counterparty (or the hub relaying on their behalf) has sent to a node. The bug class mirrors the reported "double free" in `linea` (`Matrix::zip_elements`): an operation that can partially fail (panic/throw) mid-way and then continues to release/consume the same resource a second time, corrupting shared state. Here, a thrown exception inside a `try` block is caught but execution is not stopped, so the same per-item completion callback (`cb`) of an `async.each` iteration ends up being invoked twice, ultimately causing the shared `unlock()` for the `"saved_private"` mutex lock to be called twice and crash the process via `mutex.js`'s explicit `"double unlock?"` guard.

### Finding Description
In `validateAndSave` (inside `handleSavedPrivatePayments`), the code computes a hash of attacker-supplied private-payment payload data: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

`objectHash.getBase64Hash(payload, true)` calls `getJsonSourceString`, which throws on values it cannot serialize deterministically (e.g. `null`, `NaN`/`Infinity`, empty arrays/objects, or unsupported types) as seen in `string_utils.js`: [2](#0-1) 

Because the private-payment `payload` originates from network-supplied JSON (`JSON.parse(row.json)`, ultimately populated from a peer/hub-relayed private payment message), an attacker acting as the private-payment counterparty can craft a payload whose `payload` field triggers one of these throws (e.g. an empty object/array, or a value that fails `getJsonSourceString`).

When the exception is thrown, the `catch` block calls `deleteHandledPrivateChain(..., cb)` (which asynchronously deletes the row and then invokes `cb()`), but there is **no `return` after the catch block**. Execution therefore falls through and:
1. Computes `key` using `json_payload_hash`, which was never assigned (still `undefined`, since the `try` failed before assignment).
2. Calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again on the same array, whose `ifOk`/`ifError`/`ifWaitingForChain` branches each eventually call `cb()` (directly, or via a second `deleteHandledPrivateChain(..., cb)`).

The net effect is that the single `cb` for this `async.each` iteration item is invoked twice (once from the catch branch, once from the fallthrough code). `async.each`'s completion tracking is not idempotent against a doubly-invoked iteratee callback, so its final callback: [3](#0-2) 

```js
function(){
    unlock();
    var arrNewUnits = Object.keys(assocNewUnits);
    if (arrNewUnits.length > 0)
        eventBus.emit("new_my_transactions", arrNewUnits);
}
```

can be invoked more than once for the same lock acquisition. Because `unlock` here is a single closure created once when the `"saved_private"` mutex lock was acquired, calling it a second time hits the explicit double-unlock guard in `mutex.js`: [4](#0-3) 

```js
function exec(arrKeys, proc, next_proc){
	arrLockedKeyArrays.push(arrKeys);
	...
	proc(function unlock(unlock_msg) {
		if (!bLocked)
			throw Error("double unlock?");
		...
	});
}
```

This throws an uncaught `Error("double unlock?")`, which is unhandled inside a nested asynchronous callback chain and will crash the Node.js process (there is no domain/try-catch around this async chain to gracefully recover).

### Impact Explanation
Any private-payment counterparty (or a hub relaying an unsolicited/attacker-controlled private payment) that sends a malformed private-payment payload can trigger an uncaught exception that crashes the receiving node's process. Because `handleSavedPrivatePayments` runs for every node that has `my_device_address` set (i.e., any wallet-capable node, including full nodes with an attached wallet), this is reachable from an unprivileged counterparty in a private-payment flow with no special access needed. A crashed node cannot process, validate, or confirm any further units — satisfying the "network unable to confirm new units" impact bar, and mirrors the root cause of the reported bug class: an error/early-exit path is taken but the routine keeps running and re-consumes/re-releases the same resource (here, the completion callback and the mutex unlock function) a second time, corrupting the invariant that `unlock()` should be called exactly once per lock acquisition.

### Likelihood Explanation
The trigger condition is straightforward to reach: any attacker able to send a private-payment message (a "private-payment counterparty" — an explicitly in-scope reachable actor) can supply a `payload` object for the head private element that fails `getJsonSourceString`/`getBase64Hash` (e.g., an empty object/array embedded somewhere reachable, or invalid numeric value). No cryptographic material or witnessing is required to reach this code path; the payload only needs to be stored into `unhandled_private_payments` and later picked up by `handleSavedPrivatePayments`. This makes the bug highly likely to be reachable and reliably reproducible.

### Recommendation
Add a `return` statement immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave` (network.js, around line 2476) so that execution does not fall through to compute `key` and call `privatePayment.validateAndSavePrivatePaymentChain` a second time. Additionally, consider hardening `mutex.js`'s `unlock` to log-and-return instead of throwing on double-unlock in production, and/or wrap `async.each` iteratee logic with a guard (e.g., call-once wrapper around `cb`) to make callback invocation idempotent and prevent similar re-entrancy issues elsewhere.

### Proof of Concept
1. As a device/wallet peer, send (or have relayed through a hub) a `private_payment` message whose chain's head element `payload` is a value that `getJsonSourceString` cannot serialize — e.g. an object containing an empty array (`{ "outputs": [] }` at a position accessible before other structural validation), or a payload that JSON-parses to contain `NaN`-equivalent/invalid numeric content.
2. The message gets stored to `unhandled_private_payments` and is later picked up by `handleSavedPrivatePayments()`.
3. Inside `validateAndSave`, `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws.
4. The `catch` block deletes the row and calls `cb()` once (asynchronously, after the DB delete completes).
5. Execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)` again; one of its callback branches calls `cb()` a second time.
6. `async.each`'s final callback (`unlock(); ...`) fires more than once for the same lock acquisition, and the second `unlock()` call throws `Error("double unlock?")` inside `mutex.js`, crashing the node process.

Note: I was not able to fully trace `privatePayment.validateAndSavePrivatePaymentChain`'s internal callback timing/ordering guarantees (e.g., exact synchronous vs asynchronous invocation of its `ifOk`/`ifError`) from the indexed context alone, so exact reproduction timing (which of the two `cb()` calls "wins" first) could not be verified end-to-end; a Devin session with full file access and a running test harness would be needed to confirm the precise crash trace.

function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
