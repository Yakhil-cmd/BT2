### Title
Unprivileged dust supply into a victim's account fills its supply-position slots and blocks new collateral/debt positions - (File: contracts/controller/src/account.rs)

### Summary
The SuiteCRM report is a path-traversal-to-DoS: user-controlled input resolves to an unintended resource/module and renders the application unusable. The analog in XOXNO Lending is that `supply` lets any caller write into *another* user's account storage path: `load_or_create_account` with `AccountGuard::Supply` only checks `require_spoke_match`, not ownership or delegation (contracts/controller/src/account.rs:99-100). An attacker can therefore inject up to `PositionLimits.max_supply_positions` (max 5, `POSITION_LIMIT_MAX`) dust positions of junk hub assets into a victim's account. Every subsequent victim `supply`/`multiply`/`migrate_from_blend` that would open a new slot reverts with `CollateralError::PositionLimitExceeded` in `validate_bulk_position_limits` (contracts/controller/src/risk/validation.rs:104-111).

### Finding Description
`supply(env, caller, account_id, spoke_id, assets)` routes through `load_or_create_account` with `AccountGuard::Supply`. Unlike `Migrate` and `Multiply`, the `Supply` guard never calls `require_owner_or_delegate` — it only enforces `spoke_id == account.spoke_id` (account.rs:99-100, 151-155). The caller only needs `require_auth` on its own `caller` argument and to actually transfer the (measured) tokens, which can be 1 unit of the cheapest asset per leg. Because `validate_bulk_position_limits` dedups legs but counts each *new* `HubAssetKey` against `current_count + new_positions_count <= max_allowed`, an attacker can spend 5 dust deposits in a single `supply` call (or a few calls) to occupy all supply slots of any victim account in any spoke. The position-NFT owner never consented and cannot prevent the write: the position map `SupplyPositions(account_id)` is keyed solely by `account_id`, exactly like a traversal that lands in a directory the caller should not reach.

### Impact Explanation
Once all `max_supply_positions` slots are occupied by attacker-chosen dust positions, the victim cannot supply any additional distinct asset, and any `borrow` leg requiring new collateral is capped as well — every such call reverts with `PositionLimitExceeded`. To recover, the victim must `withdraw` each dust position in full so `update_or_remove_supply_position` frees the slot; if any injected asset is `frozen`/`paused` in the victim's spoke (withdrawals gated by spoke-asset flags), the slot cannot be freed on that path and the account is effectively bricked for new collateral until governance unfreezes the asset. This is temporary-to-extended freezing of the victim's account functionality/funds caused purely by an unprivileged third party, matching the Medium DoS impact of the reference advisory. Cost to the attacker is ~5 token stroops.

### Likelihood Explanation
Fully permissionless: `supply` requires only caller auth and the spoke/asset to be listed and unpaused at the moment of injection. No flash loan, no privileged role, no timing condition. The dust-spam vector is already demonstrated in-repo by `poc_single_actor_spams_unbounded_dust_accounts` (tests/test-harness/tests/controller/supply.rs:313-343), which shows 1-unit deposits are accepted with no dust floor. The only limitation is that the victim can usually withdraw the dust, so the freeze lasts until the victim notices and pays gas to unwind — hence Medium, not High.

### Recommendation
Apply `require_owner_or_delegate` to `AccountGuard::Supply` for non-zero `account_id` (account.rs:99-110), so only the NFT owner or an active delegated manager can append positions to an existing account. Third-party top-ups (e.g., donation-style supply) should either create a new account (`account_id == 0`, already ownerless-minted to `caller`) or go through a dedicated entrypoint that tops up an *existing* `HubAssetKey` only and reverts when the asset is not already a position, never opening a new slot on someone else's book.

### Proof of Concept
1. Victim owns `account_id = V` in `spoke_id = 1` holding 2 supply positions; `max_supply_positions = 5`.
2. Attacker (no relation to V) calls `controller.supply(caller=attacker, account_id=V, spoke_id=1, assets=[(hubA,1),(hubB,1),(hubC,1)])` with three listed-but-worthless hub assets. `AccountGuard::Supply` passes on spoke match alone; the three measured 1-unit transfers succeed; V's `supply_positions` now has 5 entries.
3. Victim calls `supply` for a new collateral asset `hubD` — `validate_bulk_position_limits` computes `5 + 1 > 5` and reverts `PositionLimitExceeded` (validation.rs:104-111). Same for `multiply`/`migrate_from_blend` legs that need a new slot.
4. Victim must spend extra transactions `withdraw`-ing each dust asset to zero to reclaim slots; if any dust asset is frozen in spoke 1, that slot stays occupied and the account cannot be restored by the victim alone.
