### Title
Public `light/dry_run_aa` endpoint leaks exact AA outputs and state changes, enabling front-running of AA trades - (File: network.js)

### Summary
The `light/dry_run_aa` websocket request handler lets any connected peer submit an arbitrary trigger object plus an AA address and immediately receive the AA's exact simulated response: resulting payment outputs, state-variable deltas, and bounce/error status, at zero cost and without broadcasting a real unit.

### Finding Description
`handleRequest` processes the `light/dry_run_aa` case by validating the target address, reading the AA's definition, validating the caller-supplied trigger object, and then calling `aa_composer.dryRunPrimaryAATrigger(params.trigger, params.address, arrDefinition, ...)`, which fully executes the AA logic against current chain state inside a transaction that is subsequently rolled back [2](#0-1) . `dryRunPrimaryAATrigger` runs the real `handleTrigger` engine — the exact same code path used for genuine on-chain execution — computing real payment outputs and state-variable updates before rolling back [3](#0-2) . There is no fee, no authentication, and no rate limiting tied to this call, and the caller can supply any `trigger.data`/`trigger.outputs`/`trigger.address` values to probe how an AA (e.g., an AMM-style exchange AA, an auction AA, a lending AA) would react to a hypothetical trade, letting an attacker discover the exact price impact, arbitrage opportunity, or profit that a soon-to-be-posted real trigger unit would realize. Because DAG stability/ordering allows an attacker to still get their own competing trigger unit processed in the same or an adjacent stabilization window (units to the same AA are ordered deterministically only once posted, and an attacker who is watching outgoing/candidate trigger content — including via this dry-run oracle — can react before the victim's real trigger is even broadcast), this creates the same insight advantage described in the reported issue: perfect foreknowledge of a pending, profitable state transition, obtainable for free and repeatedly.

### Impact Explanation
Any AA implementing AMM-like or auction-like economics (e.g., token swap pools, bonding-curve AAs) built on top of ocore's AA framework is directly exposed: an attacker can iterate `light/dry_run_aa` calls with candidate trigger amounts to reconstruct the AA's pricing/state function exactly, then race a competing trigger unit ahead of a victim's real trade to capture the value differential (buying before a large trade pushes price up, then selling into it). This results in economic value being extracted from ordinary AA users (fund loss for legitimate traders/AA counterparties), which is the same value-extraction impact class the original report is concerned with, now generalized to any Obyte AA rather than a single AMM contract.

### Likelihood Explanation
Likelihood is high: `light/dry_run_aa` is reachable by any client that can open a websocket connection to a full node (light-wallet protocol, no special privilege, no AA deployment needed), the call is free and side-effect-free (rolled back), and nothing in `validateAATriggerObject` or the handler restricts which addresses/AAs may be probed or throttles repeated probing [4](#0-3) .

### Recommendation
Treat `dry_run_aa` results as sensitive: rate-limit or fee-gate the endpoint per requester, and/or restrict the granularity of returned information (e.g., strip precise state-var deltas/response payloads for AAs not owned by the caller) so that competitors cannot cheaply reconstruct another user's pending trade outcome before it is confirmed. AA authors building AMM/auction-style logic should also be advised in documentation that dry-run simulation is publicly available and design price-impact/slippage protections (e.g., minimum-output guards) into the AA itself, since the underlying `handleTrigger` engine cannot itself distinguish "probing" triggers from real ones.

### Proof of Concept
1. Attacker connects to any full node via the light-client websocket protocol (no wallet funds or AA ownership required).
2. Attacker repeatedly sends `{"command":"light/dry_run_aa","params":{"address": TARGET_AMM_AA, "trigger": {outputs:{base: X}, data:{...}, address: SOME_ADDRESS}}}` for varying `X`, using `network.js`'s handler at [1](#0-0)  which internally calls `aa_composer.dryRunPrimaryAATrigger` [3](#0-2) .
3. From the returned `arrResponses` (exact simulated payment outputs/state changes), the attacker reconstructs the AA's live pricing curve/state without spending anything.
4. When the attacker observes (via network monitoring or repeated dry-run probing) that a large real trigger is about to be posted, they compose and broadcast their own trigger to the same AA first, capturing the price movement/arbitrage that the victim's trade would have caused, extracting value from the victim/AA pool.
