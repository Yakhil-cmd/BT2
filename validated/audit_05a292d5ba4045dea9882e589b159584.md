### Title
Cross-repo commit-status forgery bypasses repository binding, forging CI status and triggering continuous delivery for a victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by SHA (`Commit.where(sha: params.sha)`) with no check that the webhook's `repository` matches the commit's own stack/repository. Because Git SHAs are content-addressed and identical across repositories that share history (forks, mirrors, monorepo splits), a webhook delivered for repository R2 can create a `Shipit::Status` on a commit that actually belongs to victim stack S1 (tracking R1), which then fires `after_commit :schedule_continuous_delivery` on that `Status`/`Commit` and enqueues `ProcessMergeRequestsJob` for S1.

### Finding Description
The claimed binding is: *the identity that triggered continuous-delivery scheduling for S1 == an authorized event from R1*, i.e. `params.dig('repository','full_name') == commit.stack.repository.full_name` should hold before `Commit#create_status_from_github!` runs.

Tracing the path:
- `Shipit::WebhooksController#create` dispatches the parsed JSON body to registered handlers for the event type [1](#0-0) .
- `verify_signature` only checks that the raw payload's HMAC matches the GitHub App's webhook secret for `repository_owner`, which is read straight out of the attacker-supplied payload (`params.dig('repository','owner','login')`) [2](#0-1) [3](#0-2) . This only proves the request genuinely came from GitHub for *some* repository the sender controls (e.g. R2, owned by the attacker) — it proves nothing about R1/S1.
- `Shipit::Webhooks::Handlers::StatusHandler#process` then resolves the target purely by SHA, with no repository filter at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .
- `Commit#create_status_from_github!` creates a `Status` using the commit's *own* `stack_id` (S1's), not any ID derived from the webhook payload's repository [5](#0-4) [6](#0-5) .
- `Status` then runs `after_commit :schedule_continuous_delivery, :broadcast_update, on: :create`, delegating to `commit.schedule_continuous_delivery`, which (per `commits_test.rb`) enqueues `ProcessMergeRequestsJob` scoped to the commit's real stack (S1) [7](#0-6) [8](#0-7) .

So the two sides of the equality diverge: the request is authenticated as belonging to R2 (attacker-controlled), but the mutation (a new `Status`, and the enqueued `ProcessMergeRequestsJob`) is applied to S1/R1's commit and stack, because nothing in `StatusHandler#process` cross-checks `params['repository']` against `commit.stack`'s repository. `drop_unhandled_event`, `verify_signature`, and the `ExplicitParameters` schema on `StatusHandler` (`requires :sha`, `:state`, etc.) all validate shape/signature but never repository ownership of the target commit [9](#0-8) .

Exploit flow: attacker owns/administers repository R2 and can install/enable Shipit's GitHub webhook/App integration on R2 (a repo they own — within the stated attacker capabilities). They arrange for R2 to share a historical commit SHA with a commit that exists in victim stack S1 (e.g., R2 is a fork of R1 that hasn't diverged past that commit, or shares a common ancestor). They then trigger (or replay) a genuinely GitHub-signed `status` event from R2 with `state: 'success'` and that shared `sha`. The signature check passes (it's legitimately signed for R2), `StatusHandler` matches the commit purely by SHA regardless of repository, creates a `Status` on S1's commit, and the `after_commit` callback enqueues `ProcessMergeRequestsJob` for S1 — advancing/faking CI state and continuous-delivery eligibility for a repository (R1) the attacker never had access to or an authorized CI relationship with.

### Impact Explanation
This lets an attacker who controls an unrelated repository (R2) forge CI status ("success"/"pending") on commits belonging to a victim stack S1 tracking a different repository (R1), and cause `ProcessMergeRequestsJob` (continuous delivery trigger) to run for S1 as if R1's own CI reported success. This is a payload from one repository mutating another repository's commit/stack state and triggering an unauthorized deploy-pipeline action, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any commit SHA the attacker can reproduce or already knows (shared history / forks / cherry-picked commits), across any number of victim stacks that happen to share history with an attacker-controlled repo.

### Likelihood Explanation
Preconditions: attacker needs (a) a GitHub repository they own/administer, (b) Shipit's webhook/App integration enabled/installable on that repo (a normal, low-cost step for any repo owner if the Shipit GitHub App supports installation on arbitrary repos/orgs), and (c) a commit SHA collision with the victim's tracked commit, which is realistic via forks/mirrors/shared history rather than requiring a SHA-1 break. No Shipit secrets, sessions, or API tokens are required — only ability to control a real repository and trigger/replay a real GitHub `status` webhook for it. This is fully within the stated unprivileged attacker model.

### Recommendation
In `Shipit::Webhooks::Handlers::StatusHandler#process`, scope the commit lookup by the reporting repository, not SHA alone — e.g. resolve the target `Stack`/`Repository` from `params['repository']['full_name']` first, then only update commits belonging to stacks tracking that exact repository (`Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: matching_repository.id })` or equivalent), rejecting/no-op if the payload's repository does not match the commit's own stack.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test ":status from an unrelated repository updates a commit sha-colliding with a victim stack's commit and schedules continuous delivery" do
  victim_stack = shipit_stacks(:shipit)              # S1, tracks R1
  victim_commit = shipit_commits(:first)               # belongs to S1
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature for R2 passes legitimately in real life

  request.headers['X-Github-Event'] = 'status'
  forged_payload = {
    'sha' => victim_commit.sha,                        # SHA shared via fork/mirror with attacker's own R2
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => victim_stack.branch }],
    'repository' => { 'full_name' => 'attacker/R2', 'owner' => { 'login' => 'attacker' } }
  }.to_json

  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack]) do
    assert_difference 'victim_commit.statuses.count', 1 do
      post :create, body: forged_payload, as: :json
    end
  end

  # Binding check: the authenticated repository (attacker/R2) does NOT equal
  # the mutated stack's repository (R1) — yet the write and job succeeded.
  refute_equal 'attacker/R2', victim_stack.repository.full_name
end
```
