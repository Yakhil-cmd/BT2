### Title
Webhook signature verification binds to the wrong organization, allowing cross-organization Stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using `repository.owner.login` (falling back to `organization.login`) taken from the untrusted JSON body, while the handlers that actually act on the payload select the target `Stack`/`Repository` using an entirely different field of the same body — `repository.full_name`. Nothing enforces that these two fields describe the same organization, so a party who legitimately controls the webhook secret for *one* GitHub organization configured on a shared, multi-tenant Shipit instance can forge a signed webhook whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` points at a *different* organization's repository/stack, causing Shipit to act on that other tenant's Stack.

### Finding Description
`Shipit.github(organization:)` supports a documented multi-organization configuration where each GitHub org gets its own `app_id`/`webhook_secret` (`docs/setup.md`, `config/secrets.development.shopify.yml`) [1](#0-0) . `WebhooksController#verify_signature` picks which org's `GitHubApp` (and thus which `webhook_secret`) is used to validate the incoming signature purely from a field inside the untrusted payload: [2](#0-1) [3](#0-2) 

Once the signature check passes, `create` forwards the *entire raw payload* to the registered handlers: [4](#0-3) 

Every handler subclasses `Shipit::Webhooks::Handlers::Handler`, which resolves the target `Stack`(s) to mutate using a *different* field of the same payload — `repository.full_name` — with no check that it matches the org that was used to authenticate the request: [5](#0-4) 

Concrete write paths reachable this way include:
- `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack [6](#0-5) 
- `CheckSuiteHandler#process`, which schedules `schedule_refresh_check_runs!` on commits [7](#0-6) 
- `StatusHandler#process`, which writes forged CI statuses onto commits via `commit.create_status_from_github!(params)` [8](#0-7) 

The binding that is broken: **organization authenticated (via `webhook_secret` selected by `repository.owner.login`/`organization.login`) ≠ repository/stack actually written (selected by `repository.full_name`)**. Because HMAC verification only proves "this body was signed with Org A's secret," not "this body legitimately describes Org A's repository," an entity that controls Org A's webhook secret can freely put Org B's `full_name` into the same signed body and have Shipit act on Org B's stack.

### Impact Explanation
This is a cross-repository/cross-tenant write: an attacker who is a legitimate administrator of one GitHub organization/App installation configured on a shared Shipit instance (and therefore knows or controls that org's `webhook_secret`) — but who has no access whatsoever to a different organization's repository — can forge signed webhooks that:
- inject arbitrary commits (via forged `push` triggering `sync_github`) into another org's `Stack`,
- fabricate green CI/check-suite statuses on another org's commits,
- influence merge-readiness signals (`merge_status`, `check_suite`) that downstream code relies on to gate deploys/merges.

This meets the "cross-repository writes" / "unauthorized deploy" bar: the attacker is unprivileged with respect to the victim organization's repository, yet can cause Shipit to write state (commits, statuses, sync jobs) into that repository's Stack.

### Likelihood Explanation
Requires: (1) the host Shipit deployment uses the documented multi-organization GitHub config (more than one org's `webhook_secret` configured), and (2) the attacker possesses a valid `webhook_secret` for at least one of the configured orgs — which is normal, expected knowledge for any org onboarded as a legitimate Shipit tenant (an org's own GitHub App admin sets/knows this value). No access to the victim org, no Shipit session, and no GitHub push access to the victim repo is required, only the ability to POST a crafted, self-signed payload to `/webhooks`.

### Recommendation
- Cross-check that `repository.owner.login` (used to pick the verifying `webhook_secret`) equals the owner segment of `repository.full_name` (used by handlers to select the `Stack`) before dispatching to handlers, rejecting mismatches with `422`.
- Alternatively, have handlers resolve stacks scoped to the same organization/`GitHubApp` instance that successfully verified the signature, rather than re-deriving the target repository independently from the raw payload.
- Log/alert on any request where these two fields disagree, since it indicates either misconfiguration or an active forgery attempt.

### Proof of Concept
1. Shipit is configured with a multi-org GitHub setup, e.g. `orgA` (secret `S_A`) and `orgB` (secret `S_B`), each with Stacks registered for their respective repos, per `config/secrets.development.shopify.yml`.
2. Attacker is a legitimate admin of the GitHub App installed for `orgA` and thus knows `S_A`.
3. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
<body above>
```
5. `WebhooksController#verify_signature` computes `repository_owner` = `"orgA"`, loads `Shipit.github(organization: "orgA")`, and successfully verifies the signature using `S_A`.
6. `create` dispatches to `PushHandler`, whose `stacks` method resolves via `Repository.from_github_repo_name("orgB/victim-repo")` — `orgB`'s Stack — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing Shipit to act on `orgB`'s repository despite the request only ever being authenticated against `orgA`'s secret.

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```
