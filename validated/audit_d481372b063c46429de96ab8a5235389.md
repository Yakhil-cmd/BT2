### Title
Signature verification is scoped to the payload's `repository.owner.login` org while the actual write target (stack lookup) is scoped to the independently-supplied `repository.full_name` field, allowing cross-organization webhook forgery when a multi-org deployment has any org configured without a `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to verify the HMAC signature with based solely on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body, while the handlers that actually mutate state (`Shipit::Webhooks::Handlers::Handler#stacks` / `#repository_name`) resolve the target `Repository`/`Stack` from the independently-supplied `repository.full_name` field of that same unauthenticated body. Because Shipit supports multiple GitHub organizations, each with its own `webhook_secret` (`lib/shipit.rb#github_app_config`, `lib/shipit/github_app.rb`), and because `GitHubApp#verify_webhook_signature` explicitly **returns `true` (skips verification) when `webhook_secret` is blank**, an attacker who can identify (or is even a member of) one configured organization that has no `webhook_secret` set can send a forged webhook body whose `repository.owner.login` matches that unsecured org, but whose `repository.full_name` names a *different, victim* organization/repository that does have real stacks under Shipit. The signature check passes trivially (because the selected org has no secret), yet the actual write (triggering a sync, closing/labeling PRs, archiving/creating review stacks, posting commit statuses, etc.) is performed against the victim repository named in `full_name`.

### Finding Description
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository','owner','login')` and looks up `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(signature, raw_post)`.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83): `return true unless webhook_secret`. If the resolved org's config has no `webhook_secret`, **any** signature (or none) is accepted.
- Multi-org configuration is a supported, documented pattern (`test/dummy/config/secrets_double_github_app.yml` shows two orgs, `OrgOne`/`OrgTwo`, each independently configured, and in that fixture both explicitly have `webhook_secret:` empty). `lib/shipit.rb#github_app_config` looks up per-organization secrets purely by the org name key.
- After `verify_signature` passes (or is bypassed), `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the full raw JSON `params` unchanged.
- Every handler (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, and the push/pull_request/status handlers) derives the actual `Repository`/`Stack` to act on from `payload.dig('repository', 'full_name')` — a completely separate field from `repository.owner.login` used for signature-org selection. Nothing cross-checks that `full_name`'s owner segment matches `repository_owner`.

This breaks the intended binding: *the organization whose credential authenticated the request* should equal *the organization/repository that is written to*. Here, the "authenticating" org (chosen via `owner.login`, and possibly configured with no secret at all) is decoupled from the "acted upon" repository (chosen via `full_name`), so the identity of the credential used for authentication and the entity actually mutated can diverge.

### Impact Explanation
This allows an unprivileged network attacker (no `webhook_secret`, no session, no API token required) to forge GitHub webhook events for **any repository/stack registered in Shipit**, as long as the Shipit deployment has at least one configured organization without a `webhook_secret` (a state that Shipit's own example multi-org secrets file demonstrates as valid/expected). Concretely this enables:
- Triggering `push`/`PushHandler` → `stack.sync_github` for a victim's branch with an attacker-chosen `after` SHA, i.e., forcing Shipit to sync/record arbitrary commit metadata for a repository the attacker doesn't control.
- Forging `pull_request` handler events (`opened`, `closed`, `labeled`, `unlabeled`) to archive/unarchive/create review stacks or to force-merge-queue actions for a victim's repository, since these handlers key strictly off `repository.full_name` in the same unauthenticated body.
- Forging `status`/`check_suite` events to inject fake commit statuses that Shipit's CI-gating and merge-queue logic (`Commit#deployable?`, `MergeRequest#all_status_checks_passed?`) rely on to decide whether a commit is safe to deploy or merge — a path toward an unauthorized deploy or merge on the victim stack.

This matches "cross-repository writes" / "an unauthorized deploy, rollback or merge" impact criteria, because the attacker's forged event, once it passes the (bypassable) signature gate for the org with no secret, drives real state changes (stack sync, PR/review-stack lifecycle, status records) against a repository the attacker does not own and never authenticated against.

### Likelihood Explanation
Likelihood is contingent on operational configuration rather than a pure code defect: the vulnerability is only exploitable when (a) the deployment uses the multi-organization GitHub app configuration (`github_app_config`/`github_organizations`), and (b) at least one configured organization has `webhook_secret` unset/blank. Both conditions are demonstrated as supported, non-error configurations in the codebase's own fixtures (`secrets_double_github_app.yml` shows two orgs both with blank `webhook_secret`), meaning this is not a hypothetical misconfiguration but a state the engine explicitly tolerates without warning. Given that, any attacker who knows (or can guess) the org name with the missing secret can forge webhooks for arbitrary other repositories tracked by the same Shipit instance, requiring no credentials, no repository write access, and no privileged account — only knowledge of a signature-less org name and the target's `full_name`.

### Recommendation
- When resolving which GitHub app/secret to use for verification, cross-validate that `repository.full_name`'s owner segment matches the `organization` used for verification (or resolve the org strictly from `full_name`'s owner rather than trusting `owner.login`/`organization.login` independently).
- Do not silently accept unsigned webhooks when `webhook_secret` is blank for a configured organization; instead, reject (422) or require an explicit opt-in flag, since a missing secret currently disables authentication entirely for that org's namespace.
- Consider verifying the signature using the org actually referenced by `repository.full_name` (the entity that will be written to) rather than the loosely-parsed `owner`/`organization` sub-object, closing the gap between "org that authenticated" and "repository being written."

### Proof of Concept
1. Shipit is configured with two GitHub orgs, e.g. `OrgOne` (attacker-known, `webhook_secret` blank) and `Victim` (has real stacks, has its own `webhook_secret`), matching the pattern in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "OrgOne" },
       "full_name": "Victim/production-app"
     }
   }
   ```
   No `X-Hub-Signature` needs to be valid (or any value at all needs to be sent), because `Shipit.github(organization: "OrgOne")` resolves a `GitHubApp` whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (lib/shipit/github_app.rb:76-77).
3. `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) dispatches to `PushHandler`, whose `stacks` method (app/models/shipit/webhooks/handlers/handler.rb:32-38) resolves `Repository.from_github_repo_name("Victim/production-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the real `Victim` stack — a write performed under an authentication check that only ever validated the (secret-less) `OrgOne` context.       github_app = Shipit.github(organization: repository_owner)
```ruby
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
