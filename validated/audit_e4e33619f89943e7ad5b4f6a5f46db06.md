### Title
Instant, unbounded commission changes via `UpdateCommissionBps` let a validator capture stakers' rewards before they can exit — analogous to the NounsDAO forkPeriod lockout - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The Nouns bug lets a privileged actor (DAO majority) instantly set a governance parameter (`forkPeriod`) to an extreme value with no minimum bound, trapping minority participants who cannot react in time. Agave has a structurally identical pattern in the vote program's commission update path: the legacy `UpdateCommission` instruction enforces a mid-epoch cutoff so commission increases can't be sprung on stakers late in an epoch, but the newer `UpdateCommissionBps` instruction (SIMD-0291/SIMD-0249) explicitly removes that guardrail, and the underlying storage accepts values with no enforced maximum. Because un-delegating stake is not instantaneous (it requires a deactivation/cooldown period spanning at least one epoch boundary), a validator's authorized withdrawer can raise commission to an extreme value at any point in an epoch, capture that epoch's rewards from delegators, and delegators have no way to exit in time — mirroring the "malicious majority sets an unreasonable parameter, minority is held captive" bug class.

### Finding Description
The legacy commission update path enforces a timing rule so that commission increases are only allowed in the first half of an epoch, giving stakers advance notice and time to redelegate before rewards are calculated: [1](#0-0) [2](#0-1) 

The newer basis-points commission path, however, explicitly disables this protection per SIMD-0291/SIMD-0249, allowing commission changes "always... regardless of epoch position": [3](#0-2) 

This is confirmed by the processor and its tests, which note there is no commission-update timing rule for the bps path: [4](#0-3) 

In addition, values above 10,000 bps (100%) are accepted at the storage layer and only "capped ... during reward calculation, not storage," meaning the on-chain state itself carries no upper bound either: [5](#0-4) 

Meanwhile, stake deactivation is not instantaneous — a staker who wants to leave a validator must go through a deactivation/cooldown accounting process governed by `stake_activating_and_deactivating_v2` and `StakeHistory`, which can span epoch boundaries before stake becomes fully inactive/withdrawable: [6](#0-5) [7](#0-6) 

Combining these: a validator's authorized withdrawer (an actor with legitimate but limited authority over just their own vote account — analogous to the DAO majority's legitimate but abusable governance authority) can raise `inflation_rewards_commission_bps` or `block_revenue_commission_bps` to an unreasonably high value with zero notice period and no enforced ceiling, capture the current epoch's staking rewards, and delegated stakers have no mechanism to exit or protect their rewards before the change takes effect, since undelegation takes at least an epoch via the deactivation/cooldown mechanism.

### Impact Explanation
This causes a redistribution of staking rewards away from delegators to the validator operator without delegator consent or ability to react — a form of reward corruption/misappropriation reachable via a single signed transaction (`UpdateCommissionBps`) from the vote account's authorized withdrawer. Unlike the legacy path, there is no minimum delay or bound analogous to Nouns' `MIN_FORK_PERIOD` fix, so delegators who are not actively monitoring commission changes each epoch are effectively "held captive" for at least one reward cycle.

### Likelihood Explanation
Low-to-medium likelihood: it requires control of the vote account's `authorized_withdrawer` key (equivalent to the "malicious majority" precondition in the original report — a legitimate, existing authority position, not an external attacker), and depends on delegators not proactively monitoring/redelegating. This mirrors the report's own "low likelihood + high impact = medium severity" characterization.

### Recommendation
Apply the same class of fix used for the Nouns issue: enforce a minimum notice/cool-down period (e.g., only allow commission-bps decreases at any time, but require increases to be scheduled or restricted to the first half of the epoch, mirroring the legacy `is_commission_update_allowed` rule) and/or enforce a hard maximum (e.g., 10,000 bps) at the storage layer rather than only at reward-calculation time, in `update_commission_bps` in `programs/vote/src/vote_state/mod.rs`.

### Proof of Concept
1. Validator's authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10_000 (or higher), kind: InflationRewards }` at any point in the epoch — no timing check exists, per `update_commission_bps` in `programs/vote/src/vote_state/mod.rs:827-859` and the processor path in `programs/vote/src/vote_processor.rs:186-204`.
2. Because storage does not cap the value (`programs/vote/src/vote_state/handler.rs:1755-1775`), the change is accepted immediately, even late in the epoch.
3. Delegators who staked to this validator cannot instantly exit — stake deactivation requires processing through `calculate_activated_stake`/`stake_activating_and_deactivating_v2` (`runtime/src/stakes.rs:411-464`) and typically spans at least one epoch boundary before the stake is fully deactivated, per the deactivation-epoch semantics shown in `cli-output/src/cli_output.rs:1476-1513`.
4. At the next reward distribution, the validator captures the elevated commission share of the epoch's rewards from all its delegators who did not react in time.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}

    pub(crate) fn calculate_activated_stake(
        &self,
        next_epoch: Epoch,
        thread_pool: &ThreadPool,
        new_rate_activation_epoch: Option<Epoch>,
        stake_delegations: &[(&Pubkey, &StakeAccount)],
    ) -> (
        StakeHistory,
        VoteAccounts,
        DelegatedStakes,
        RewardEpochDelegatedStakes,
    ) {
        // Wrap up the prev epoch by adding new stake history entry for the
        // prev epoch.
        let (stake_history_entry, effective_delegated_stakes) = thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .fold(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(acc, mut delegated_stakes), (_stake_pubkey, stake_account)| {
                        let delegation = stake_account.delegation();
                        let activation_status = delegation.stake_activating_and_deactivating_v2(
                            self.epoch,
                            &self.stake_history,
                            new_rate_activation_epoch,
                        );
                        *delegated_stakes.entry(delegation.voter_pubkey).or_default() +=
                            activation_status.effective;
                        (acc + activation_status, delegated_stakes)
                    },
                )
                .reduce(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(activation_status_a, delegated_stakes_a),
                     (activation_status_b, delegated_stakes_b)| {
                        (
                            activation_status_a + activation_status_b,
                            merge_delegated_stakes(delegated_stakes_a, delegated_stakes_b),
                        )
                    },
                )
        });
        let mut stake_history = self.stake_history.clone();
        stake_history.add(self.epoch, stake_history_entry);
        // Refresh the stake distribution of vote accounts for the next epoch,
        // using new stake history.
        let (vote_accounts, delegated_stakes) = refresh_vote_accounts(
            thread_pool,
            next_epoch,
            &self.vote_accounts,
            stake_delegations,
            &stake_history,
            new_rate_activation_epoch,
        );

fn show_inactive_stake(
    me: &CliStakeState,
    f: &mut fmt::Formatter,
    delegated_stake: u64,
) -> fmt::Result {
    if let Some(deactivation_epoch) = me.deactivation_epoch {
        if me.current_epoch > deactivation_epoch {
            let deactivating_stake = me.deactivating_stake.or(me.active_stake);
            if let Some(deactivating_stake) = deactivating_stake {
                writeln!(
                    f,
                    "Inactive Stake: {}",
                    build_balance_message(
                        delegated_stake - deactivating_stake,
                        me.use_lamports_unit,
                        true
                    ),
                )?;
                writeln!(
                    f,
                    "Deactivating Stake: {}",
                    build_balance_message(deactivating_stake, me.use_lamports_unit, true),
                )?;
            }
        }
        writeln!(
            f,
            "Stake deactivates starting from epoch: {deactivation_epoch}"
        )?;
    }
    if let Some(delegated_vote_account_address) = &me.delegated_vote_account_address {
        writeln!(
            f,
            "Delegated Vote Account Address: {delegated_vote_account_address}"
        )?;
    }
    Ok(())
}
