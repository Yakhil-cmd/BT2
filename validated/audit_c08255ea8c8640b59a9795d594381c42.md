## Title
Missing `chain_id` Binding in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer Capability Offers - ([File: aptos-move/framework/aptos-framework/sources/account/account.move])

### Summary
`SignerCapabilityOfferProofChallengeV2`, the message structure signed by an account owner to authorize `offer_signer_capability`, omits the `chain_id` field that its sibling structure `RotationCapabilityOfferProofChallengeV2` explicitly includes for replay protection.

### Finding Description
The framework defines two "V2" capability-offer challenge structs in `account.move`: [1](#0-0) 

The doc comment on `RotationCapabilityOfferProofChallengeV2` explicitly states its purpose: *"This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message."* [2](#0-1) 

However, `SignerCapabilityOfferProofChallengeV2` — the analogous struct used for delegating `SignerCapability` — only carries `sequence_number`, `source_address`, and `recipient_address`, with no `chain_id` field: [3](#0-2) 

Because Move signature verification for these challenges operates over the BCS serialization of the struct itself (the same pattern used for `RotationProofChallenge`/`RotationCapabilityOfferProofChallengeV2`, e.g. via `ed25519`/`verify_signed_message`-style checks), any field not present in the struct is *not* part of the signed bytes and therefore cannot be cryptographically bound or checked against the current execution context. Since `chain_id` is absent from `SignerCapabilityOfferProofChallengeV2`, a signature produced by an account owner on one chain (e.g. testnet/devnet) over a given `sequence_number`/`source_address`/`recipient_address` tuple is byte-for-byte identical to, and therefore valid for, the same tuple on mainnet — as long as the account's `sequence_number` and address match on both networks (a realistic condition for freshly created or synchronized test/prod key pairs).

### Impact Explanation
An attacker who captures a `SignerCapabilityOfferProofChallengeV2` signature from a non-production chain (testnet/devnet) can replay it against mainnet's `offer_signer_capability` entry function to obtain an unauthorized `SignerCapability` over the victim's mainnet account, provided the sequence number still matches. `SignerCapability` allows creating a signer for the victim account, which is a severe capability (can move funds, call arbitrary entry functions as the victim). This directly breaks the cross-chain replay-resistance invariant that the V2 redesign was explicitly meant to establish (as evidenced by the sibling rotation-capability struct doing it correctly).

### Likelihood Explanation
Exploitability requires the victim to have signed a `SignerCapabilityOfferProofChallengeV2` message on any chain (including testnets, which are commonly used for the exact same key material during development/testing) while their mainnet account has a matching `sequence_number`. This is a plausible real-world scenario (e.g., developers/wallets reusing the same keys and testing flows across environments before mainnet deployment), and requires no privileged access — only an unprivileged actor capturing a previously broadcast or leaked signature.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2`, populate it with `chain_id::get()` when constructing the challenge in `offer_signer_capability`, and treat this as a breaking format change requiring a new version (e.g., `SignerCapabilityOfferProofChallengeV3`) with a corresponding migration path, mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`.

### Proof of Concept
Add a Move/e2e test in `aptos-move/e2e-move-tests/src/tests/offer_signer_capability.rs` that:
1. Constructs a `SignerCapabilityOfferProofChallengeV2 { sequence_number, source_address, recipient_address }` (no chain_id available to include) and signs it with the source account's key under a simulated `chain_id::get() == TESTNET_ID` context.
2. Calls `offer_signer_capability` with the same serialized signature under a mainnet (`chain_id::get() == MAINNET_ID`) execution context, keeping `sequence_number`/`source_address` identical.
3. Assert the call should fail (`assert!(result.is_err())`) but currently succeeds because `chain_id` never enters the signed byte representation, confirming the missing binding described above.
