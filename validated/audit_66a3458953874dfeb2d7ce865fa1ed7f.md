### Title
Cross-repository CI status spoofing via unscoped commit lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit verifies GitHub webhook signatures using the secret belonging to the organization named in the payload's `repository.owner.login`/`organization.login` field [1](#0-0) , but the handler that actually writes the payload's data (`StatusHandler`) resolves the target `Commit` by SHA alone, with no scoping to the repository/organization that was authenticated [2](#0-1) . This breaks the binding "organization that authenticated == repository that is written," analogous to the reported NFT id spoofing where `onERC721Received` acted on an id never actually transferred/verified for the caller.

### Finding Description
`WebhooksController#verify_signature` selects a per-organization `GitHubApp` (and its `webhook_secret`) using `repository_owner`, derived from the JSON body itself: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) . In a multi-organization deployment (`github: { OrgOne: {...}, OrgTwo: {...} }`, as documented for "Using Multiple GitHub Applications" [4](#0-3) ), each organization has its own `webhook_secret`, and `Shipit.github(organization:)` picks the config by that same field [5](#0-4) .

The HMAC signature only proves the request body was signed with *some* organization's secret (whichever one `repository_owner` names) — it proves nothing about which repository/stack the payload's other fields (like `sha`) should affect. `StatusHandler#process`, however, performs a completely global, unscoped lookup:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

There is no join/filter against `repository_owner`, the stack's repository, or the organization whose secret validated the signature. `create_status_from_github!` then persists an actual `CommitStatus`/release status via `add_status`/`statuses.replicate_from_github!` [6](#0-5) , and status transitions drive `deployable_status` webhooks / merge and deploy gating logic [7](#0-6) .

**Equality broken:** `organization authenticated by webhook signature` (org A, whose `webhook_secret` the caller legitimately possesses because they administer a GitHub App installed on their own org/repo) ≠ `repository/stack whose Commit row is mutated` (any org B tracked by the same Shipit instance, as long as the attacker knows/guesses a 40-hex-char SHA that exists in B's tracked history — SHAs are public information visible on GitHub).

### Impact Explanation
An attacker who legitimately controls a GitHub App/webhook secret for one organization tracked by a shared, multi-tenant Shipit instance can forge a `status` event that is correctly signed for their own org, yet write an arbitrary CI status (`state: success`, custom `description`/`target_url`) onto a commit belonging to a completely unrelated organization's stack, as long as that commit's SHA is known (SHAs are public). Because commit CI state feeds directly into deployable/mergeable checks and merge-queue/continuous-deployment gating [8](#0-7) , this can be used to force a victim repository's commit to appear "green," enabling an unauthorized merge or deploy of that commit — meeting the "unauthorized deploy, rollback, or merge" bar for High/Critical impact.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration [4](#0-3) ), (2) attacker control of a legitimate `webhook_secret` for at least one org tracked by the instance (i.e., they run their own GitHub App installation, which is unprivileged relative to other tenants), and (3) knowledge of a target commit SHA in a victim stack (trivially obtainable, since SHAs are public on GitHub). No `ApiClient` token, session, or GitHub write access to the victim repository is required — only the attacker's own, unrelated org's webhook secret.

### Recommendation
Scope the `Commit` lookup in `StatusHandler` (and any other handler using a similarly global query) to the repository actually authenticated by the verified signature, e.g. join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and require that its `owner` matches `repository_owner`, mirroring the pattern already used by `Handler#stacks`/`Handler#repository_name` [9](#0-8) .

### Proof of Concept
1. Operate Shipit with `github: { OrgA: {...}, OrgB: {...} }`, where the attacker administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), while `OrgB/victim-repo` is tracked as a separate, unrelated stack.
2. Attacker finds a public commit SHA `S` belonging to `OrgB/victim-repo` (e.g., a PR HEAD commit awaiting CI, visible on github.com).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{"sha": "S", "state": "success", "repository": {"owner": {"login": "OrgA"}}, ...}`, and `X-Hub-Signature` computed with `OrgA`'s (attacker-known) `webhook_secret`.
4. `verify_signature` selects `Shipit.github(organization: "OrgA")` and validates the HMAC successfully [10](#0-9) .
5. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the commit under `OrgB/victim-repo`'s stack (unrelated to `OrgA`), and writes a forged `success` status onto it [2](#0-1) , potentially unblocking merge/deploy gating for a repository the attacker has no legitimate access to.

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
