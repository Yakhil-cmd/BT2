Found the analog. The verified signature binding breaks at the organization vs. repository boundary.

### Title
Webhook signature verified against the payload's organization while events are applied to a different repository name - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, but the individual event handlers (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using an entirely different field of the same JSON body: `payload.dig('repository', 'full_name')`.

### Finding Description
`verify_signature` computes the signing organization like this: [1](#0-0) 
It then fetches `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that organization's `webhook_secret`: [2](#0-1) 

However, the actual repository that gets written to (stacks synced, commits/statuses recorded) is derived independently in `Handler#repository_name` / `Handler#stacks`: [3](#0-2) 

In a multi-organization Shipit deployment (`Shipit.github_organizations` / `github_app_config`, see `lib/shipit.rb:190-200`), each org has its own `webhook_secret`. The equality the system is supposed to enforce is:

`organization whose webhook_secret authenticated the request == organization owning the repository whose stacks are mutated`

Because the signature check only inspects `repository.owner.login` (or `organization.login`) to *pick the secret*, while the handler independently trusts `repository.full_name` to *pick the target repository*, an attacker who holds a valid `webhook_secret` for **any one** onboarded organization (e.g. because they administer/own a low-trust org integrated with the same Shipit instance) can sign a payload where `repository.owner.login` matches their own org (so it verifies against their own secret) while `repository.full_name` is spoofed to reference a stack under a **different, higher-trust** organization/repository. The signature never covers "this signature authorizes writes only to this specific repository" — it only authorizes "some event from this org", and the handler doesn't re-check that `repository.full_name`'s owner matches `repository_owner`.

This mirrors the reported bug class exactly: `contains` checked membership of an item without excluding the "empty"/mismatched slot from the actual set it was verifying against — here, `verify_signature` verifies against one identity field but the mutation logic acts on an unverified/independent identity field from the same payload.

### Impact Explanation
An attacker who legitimately owns one onboarded GitHub organization (and thus knows/controls that org's webhook flow enough to produce a validly-signed payload, e.g. via their own `webhook_secret` for their org) could forge push/status/commit events that resolve to a `Stack` belonging to a completely different, victim organization's repository, mutating `Commit`/`Status`/`Membership`/`Team` state for that unrelated repository — a cross-repository write. Combined with `sync_github`/`trigger_deploy` pathways this can lead to an unauthorized deploy for a repository the attacker does not control.

### Likelihood Explanation
Requires a Shipit instance configured with multiple GitHub organizations (each with its own `webhook_secret`) and requires the attacker to control the webhook signing secret of one of those organizations (i.e., to be a legitimate but lower-privileged tenant onboarded onto the same Shipit instance). This is plausible in shared/multi-tenant Shipit deployments, which is explicitly supported by `Shipit.github_organizations`/`github_app_config`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after verifying the signature against `repository_owner`'s secret, also assert that every repository/organization referenced elsewhere in the payload (`payload.dig('repository','full_name')`, `payload.dig('repository','owner','login')`) is consistent with the organization whose secret validated the signature, rejecting the event (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (see `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a JSON push payload with `organization.login` / `repository.owner.login` = `attacker-org` (so `repository_owner` resolves to `attacker-org`) but `repository.full_name` = `victim-org/some-repo`.
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret`, producing a valid `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature — the request passes.
5. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` invokes `PushHandler`, whose `stacks` method looks up `Repository.from_github_repo_name('victim-org/some-repo')` and calls `stack.sync_github(...)` on the victim's stacks, mutating state cross-organization despite the signature never having authenticated anything about `victim-org`.
