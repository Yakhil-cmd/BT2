The reported bug class depends on a two-stage liquidity mechanism — a buffer held in the pool contract plus a separate external vault (Curve) that gets pre-emptively drained based on an *unvalidated* user-supplied amount, before the token contract's `burn` function later clamps that amount down to the actual balance. `raydium-cp-swap` has no analogous architecture: there is no external vault, no liquidity buffer, and no two-step amount adjustment.

In `programs/cp-swap/src/instructions/withdraw.rs`, the `lp_token_amount` is validated against the caller's actual balance immediately and synchronously, before any calculation or fund movement occurs: [1](#0-0) 

There is no later mismatch-prone step that recalculates or reduces the amount after funds have already been moved based on an inflated value — `token_0_amount`/`token_1_amount` are derived directly from `lp_tokens_to_trading_tokens` using the already-validated `lp_token_amount`, and both are additionally clamped with `std::cmp::min(total_token_0_amount, token_0_amount)` against actual vault balances before any transfer: [2](#0-1) . The LP burn and vault-to-user transfers only happen after these bounds checks, so there is no scenario in which the program "pre-withdraws" excess funds from a separate reserve based on an unadjusted, inflated amount as in the LendingPool report. Since the transfers in `deposit.rs`/`withdraw.rs` operate directly on pool vaults (not a second external vault with a buffer-rebalancing step), the described bug class of unnecessary/excessive fund movement due to a deferred amount-clamping mismatch does not have a reachable analog here.
