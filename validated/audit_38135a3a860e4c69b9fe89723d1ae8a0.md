I confirmed the vulnerability. Operator precedence in `unarchive?` causes `review_stacks_enabled` to gate only the `allow_all` clause, not the `allow_with_label` or `prevent_with_label` clauses.

**The binding:** The intended equality is `review_stacks_enabled == true` must gate *all* provisioning behaviors before `unarchive!`/`create!` can run. The actual code in [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby's `&&` binds tighter than `||`, so this parses as:
```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```

`review_stacks_enabled` only appears in the first disjunct. The second (`allow_with_label`) and third (`prevent_with_label`) disjuncts are entirely independent of `review_stacks_enabled`. With `review_stacks_enabled == false`, `provisioning_behavior == :allow_with_label`, and the PR carrying `repository.provisioning_label_name`, `unarchive?` returns `true`, `process` calls `stack.unarchive!` [2](#0-1) , which delegates to `ReviewStackAdapter#unarchive!` [3](#0-2) . Since no stack exists for that PR's environment, it falls into the `stack.blank?` branch and calls `create!` [4](#0-3) , unconditionally provisioning a new `Shipit::ReviewStack` and queuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)`.

I checked the existing test suite in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` [5](#0-4) : every test helper `configure_provisioning_behavior` defaults `provisioning_enabled: true` and sets `repository.review_stacks_enabled = provisioning_enabled`. There is no test that exercises `review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label`, so this precedence bug is untested and unguarded.

No other guard intercepts this: `params` schema validation only checks payload shape, `respond_to_pull_request_reopened?` just checks `action == "reopened"` then calls the broken `unarchive?` [6](#0-5) , and `Repository#review_stacks_enabled` is a plain attribute with no model-level enforcement tying it to `provisioning_behavior`. The attacker only needs to own a repository connected to Shipit, set `provisioning_behavior: allow_with_label` (a repo-owner-level Shipit setting) — but per the question's binding, `review_stacks_enabled` is explicitly set `false`, meaning stacks should be entirely disabled for that repo. An attacker who can label their own PR with the configured provisioning label and close/reopen it can trigger unauthorized stack creation despite review stacks being disabled.

### Title
`ReopenedHandler#unarchive?` operator-precedence bug bypasses `review_stacks_enabled` gate for `allow_with_label`/`prevent_with_label` behaviors - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`ReopenedHandler#unarchive?` only applies the `review_stacks_enabled` check to the `allow_all` provisioning behavior due to Ruby `&&`/`||` operator precedence, leaving the `allow_with_label` and `prevent_with_label` branches unguarded. On a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label`, closing and reopening a PR carrying the provisioning label triggers `ReviewStackAdapter#unarchive!` → `create!`, provisioning a new review stack even though review stacks are disabled for that repository.

### Finding Description
The intended binding is `repository.review_stacks_enabled == true` gates all stack (re)creation regardless of `provisioning_behavior`. The actual implementation at [1](#0-0)  is:

```ruby
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```

Due to `&&` having higher precedence than `||`, this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Only the `allow_all` clause is gated by `review_stacks_enabled`; the other two clauses evaluate independently of it.

Exploit: repository owner (attacker, unprivileged w.r.t. Shipit) sets their repo's Shipit configuration to `provisioning_behavior: allow_with_label` while `review_stacks_enabled` remains `false` (this combination is a valid, reachable configuration state — the question's binding stipulates it exists). The attacker opens a PR, applies the configured provisioning label to their own PR (label capture handled by `LabelCapturingHandler`), closes the PR, then reopens it, causing GitHub to emit a `pull_request` webhook with `action: "reopened"`. `ReopenedHandler#process` calls `respond_to_pull_request_reopened?` → `unarchive?`, which returns `true` via the second disjunct despite `review_stacks_enabled == false`. `stack.unarchive!` is invoked, resolving to `ReviewStackAdapter#unarchive!` at [3](#0-2) ; since no `ReviewStack` yet exists for `pr#{params.number}`, the `stack.blank?` branch calls `create!` [4](#0-3) , creating a new `Shipit::ReviewStack` and enqueuing it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`.

No existing guard prevents this: the `ExplicitParameters` schema only validates payload shape, `Repository#review_stacks_enabled` is an independent boolean attribute with no validation coupling it to `provisioning_behavior`, and webhook signature verification only authenticates that the payload came from GitHub for that repository — it does not re-derive or enforce cross-field configuration invariants like this one.

### Impact Explanation
A repository owner can cause Shipit to create and queue provisioning for a `Shipit::ReviewStack` on their own repository even though the repository operator explicitly disabled review stacks (`review_stacks_enabled: false`). This is an authorization/configuration-bypass bug: a control meant to hard-disable a feature is silently ignored for two of three provisioning-behavior modes. Provisioning a review stack can trigger deploy/provisioning tasks that run commands against the deploy host for that stack's environment, so this can be a stepping stone to unauthorized task execution, resource creation, and configuration drift the repository operator believed was impossible. It only affects the attacker's own repository/stack (not cross-tenant), but it fully undermines the `review_stacks_enabled: false` guarantee for that repo.

### Likelihood Explanation
The precondition is a real, reachable repository configuration: `review_stacks_enabled: false` with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) — nothing prevents an operator/owner from setting these independently since there's no validation linking them. Given that configuration, the attacker's cost is trivial and requires only standard GitHub actions on their own PR (apply label, close, reopen) with no Shipit credentials, session, or API token. It is fully repeatable at will against that repository.

### Recommendation
Fix operator precedence in `unarchive?` so `review_stacks_enabled` gates every disjunct, e.g.:
```ruby
def unarchive?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Also audit `LabeledHandler`, `UnlabeledHandler`, and `ClosedHandler` for the identical `unarchive?`/`archive?` precedence pattern, since they share the same structure.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add:
```ruby
test "does NOT unarchive/create stacks when review_stacks_enabled is false, even for allow_with_label with matching label" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails because `Shipit::Stack.count` increases by 1 (a `ReviewStack` is created via `create!`) despite `review_stacks_enabled == false`. After applying the recommended fix, `unarchive?` returns `false` and the count does not change, matching the intended binding.
