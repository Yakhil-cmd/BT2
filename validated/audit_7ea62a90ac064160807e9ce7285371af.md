### Title
Blind SSRF via attacker-controlled arbiter address in arbiter-contract flow - (File: `arbiter_contract.js`, `arbiters.js`)

### Summary
`arbiter_contract.js` and `arbiters.js` fetch an "arbstore URL" that is looked up from the hub by an `arbiter_address` supplied by an untrusted correspondent (the counterparty of an arbiter contract), and then make outbound HTTP(S) requests to that URL with no validation of scheme, host, or IP range. This mirrors the audiobookshelf `podcastUtils.js` SSRF pattern: an unauthenticated/low-privilege actor supplies a URL (indirectly, via a self-registered `arbiter_address`) that the victim's own node then fetches without any allow-listing, enabling blind SSRF against the victim's internal network or cloud metadata endpoints.

### Finding Description
When a wallet receives (or creates) an arbiter contract, the `arbiter_address` field is attacker-controlled: any device correspondent can propose an `arbiter_contract_offer` naming itself (or any address it controls) as the arbiter, since `createAndSend`/`store` persist the peer-supplied contract fields, including `arbiter_address`, without restricting them to a trusted allow-list [1](#0-0) [2](#0-1) .

To derive the shared multisig address for the contract, `deriveSharedAddress` calls `arbiters.getArbstoreInfo(contract.arbiter_address, ...)`, which is executed automatically as part of accepting/offering the contract (`createSharedAddressAndPostUnit`) [3](#0-2) [4](#0-3) .

`getArbstoreInfo` (and `getInfo`) ask the hub for the URL associated with the attacker-chosen `arbiter_address` via `device.requestFromHub("hub/get_arbstore_url", ...)`. The only check performed on the returned value is that it is a non-empty string — there is no scheme restriction, no DNS/IP filtering, and no denial of private/loopback/link-local ranges: [5](#0-4) 

The URL is then fetched directly with `http.get`/`https.get`: [6](#0-5) 

Because the hub associates `arbstore_url` with `arbiter_address` via a self-service registration mechanism (any device can act as an "arbiter" and register its own store URL for its own address), an attacker only needs to (1) register itself as an arbiter with a malicious `arbstore_url` (e.g. `http://169.254.169.254` or an internal service address), and (2) propose (or get accepted into) an arbiter contract naming its own address as `arbiter_address`. When the victim processes the contract (deriving the shared address, opening a dispute, appealing, or checking the appeal fee), the victim's own node issues outbound HTTP requests to the attacker-chosen URL with no validation: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
This is a blind SSRF from the victim's node against arbitrary hosts/ports (including internal-only services, cloud metadata endpoints, or loopback services) reachable from the machine running the wallet. It does not directly cause spending, double-spend, or consensus impact, but it does allow an unprivileged correspondent (any paired device, or anyone who can get a contract offer accepted) to force the victim node to perform network requests to attacker-chosen internal targets — the same bug class and same severity class as the referenced CVE-2023-51697 (Medium, blind SSRF from unauthenticated/low-privileged input).

### Likelihood Explanation
The attack requires no special privilege beyond being a device correspondent capable of proposing/accepting an arbiter contract and being able to self-register as an "arbiter" with a hub — both of which are normal, unprivileged user actions in this feature. The victim needs to perform an otherwise normal action (accept/offer a contract, open dispute, appeal, or check appeal fee) for the SSRF request to fire, and these are common wallet interactions, making the likelihood moderate.

### Recommendation
- Validate `arbstore_url` before use: require `https://` scheme, resolve and reject requests to private/loopback/link-local/multicast IP ranges and to the node's own configured hosts, and enforce an allow-list or user confirmation before making any request to a peer-supplied arbstore URL.
- Apply consistent validation in both `arbiters.js` (`requestInfoFromArbStore`, `getInfo`, `getArbstoreInfo`) and `arbiter_contract.js` (`httpRequest`, `getArbstoreAddresses`, `openDispute`, `appeal`, `getAppealFee`).
- Consider requiring explicit user confirmation before contacting an arbstore URL associated with an arbiter address that is not already known/trusted.

### Proof of Concept
1. Attacker device registers itself as an "arbiter" with the shared hub, setting its `arbstore_url` to an SSRF target (e.g. `http://169.254.169.254` or an internal-only service URL) — this registration is not shown to be restricted (out of scope of this repo's client-side code, but the client trusts whatever the hub returns for `hub/get_arbstore_url`, per `arbiters.js:60-67` and `arbiter_contract.js:229`).
2. Attacker sends an `arbiter_contract_offer` device message to the victim, setting `arbiter_address` to its own attacker-controlled address, via `createAndSend`/`store` [1](#0-0) .
3. Victim accepts the contract; the wallet calls `createSharedAddressAndPostUnit` → `deriveSharedAddress` → `arbiters.getArbstoreInfo(attacker_address, ...)` [4](#0-3) [3](#0-2) .
4. `getArbstoreInfo` fetches `hub/get_arbstore_url` for the attacker's address, gets back the attacker-controlled URL unchecked, and issues an outbound HTTPS GET request to it via `requestInfoFromArbStore` [5](#0-4) , causing the victim's node to blindly probe the attacker-chosen internal/external target.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
