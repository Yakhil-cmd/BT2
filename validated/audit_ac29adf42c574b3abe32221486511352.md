### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the handlers act on the repository named in `repository.full_name` — allowing a valid signer for Org A to trigger GitHub-API writes on Org B's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository_owner`, a value read straight out of the untrusted JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once verification succeeds, the dispatched `Handler` subclasses resolve the target `Repository`/`Stack` using a *different* field of the same payload: `repository.full_name`. Nothing ties these two fields together, so in a multi-organization deployment (the shape explicitly supported by `Shipit.github_app_config`, see `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo`, each with its own `webhook_secret`), a payload can be signed with Org A's secret while pointing at Org B's repository.

### Finding Description
Binding that should hold: `organization that authenticated == organization owning the repository the handler writes to`.

Verification side, `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

This picks the `GitHubApp` (and therefore the `webhook_secret` used for HMAC comparison) using attacker-controlled JSON, not a value bound to the actual connection/installation that delivered the request.

Execution side, `app/models/shipit/webhooks/handlers/handler.rb`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`repository_name` is read from a *different* JSON path than `repository_owner`, and is never checked to belong to the organization whose secret validated the signature.

Once a `Stack`/`Repository` is resolved, all subsequent GitHub API calls use the *repository's own owner* to pick the credentials, not the organization that validated the webhook:
```ruby
def github_app
  Shipit.github(organization: owner)
end
``` [4](#0-3) 

So `GithubSyncJob#fetch_missing_commits` (`stack.github_api`) and other handlers (push/PR/status/merge handlers) will use **Org B's own GitHub App token** to act on Org B's repo — even though the request was authenticated solely with Org A's `webhook_secret`.

Concretely: `PushHandler#process` looks up stacks by `branch` on `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4) , which enqueues `GithubSyncJob`. That job then calls `stack.github_commits` / `stack.github_api`, hitting the GitHub API with the credentials of `Repository#owner` (Org B), fetching commits and creating `Commit` records for Org B's stack — all driven by a payload whose only proof-of-authenticity was Org A's secret.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out in scope. In a multi-org Shipit deployment, any actor who legitimately controls a GitHub App installation (and hence its `webhook_secret`) for one onboarded organization can:
- Forge a `push`, `status`, `check_suite`, `pull_request`, or `merge`/`commit_status` webhook payload,
- Sign it with their own org's `webhook_secret` (passes `verify_signature`),
- Set `repository.full_name` to point at any *other* onboarded organization's repository,
- Cause Shipit to perform genuine cross-organization actions using that victim org's own GitHub App token: syncing commits, updating commit statuses, closing/merging pull requests (via the `pull_request`/`merge` handlers), or affecting deploy-triggering data — i.e., an unauthorized write path into a repository the attacker does not control, executed with the victim organization's own GitHub credentials.

This matches the Critical/High bar in scope ("cross-repository writes ... using the app's own GitHub credentials").

### Likelihood Explanation
Requires only that the attacker be a legitimate admin of one org's GitHub App installation in a multi-org Shipit deployment (not a Shipit session, `ApiClient` token, or the victim's private key) — i.e., an "unprivileged" actor relative to the victim organization. This is a realistic operating model for shared/multi-tenant Shipit instances that use the `secrets.github.<org>` schema (as documented and tested via `secrets_double_github_app.yml`). No social engineering, TLS interception, or privileged victim credentials are needed; only a crafted JSON body and a valid HMAC computed with the attacker's own known secret.

### Recommendation
After `verify_signature` succeeds, bind the identified organization to the repository being acted upon: reject (422) the webhook if `payload.dig('repository','full_name')`'s owner does not case-insensitively match the `repository_owner` used to select the verifying `GitHubApp`. Enforce this check centrally (e.g., in `WebhooksController#verify_signature` or in `Handler#initialize`) rather than trusting `repository.full_name` unchecked in `Handler#repository_name`.

### Proof of Concept
Setup: Shipit configured with two orgs, `OrgOne` (secret `s1`) and `OrgTwo` (secret `s2`), each with a `Repository` (`OrgOne/repoA`, `OrgTwo/repoB`) and corresponding `Stack`s, matching the multi-org schema exercised by `test/dummy/config/secrets_double_github_app.yml`.

1. Attacker administers `OrgOne`'s GitHub App installation and therefore knows `s1` (their own webhook secret).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "full_name": "OrgTwo/repoB",
    "owner": { "login": "OrgOne" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(s1, body)` and sends it to `POST /webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")` (from `repository.owner.login`) and successfully verifies the signature against `s1` [6](#0-5) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgTwo/repoB")` via `repository_name` reading `full_name` [3](#0-2) , and enqueues `GithubSyncJob` for `OrgTwo`'s stack.
6. `GithubSyncJob` runs `stack.github_api`, which resolves via `Repository#github_app` to `Shipit.github(organization: "OrgTwo")` — using OrgTwo's own GitHub App credentials to fetch commits/update state for OrgTwo's repo [4](#0-3) [7](#0-6) .

Result: the attacker, authenticated only as OrgOne, has induced state-changing GitHub API activity against OrgTwo's repository/stack using OrgTwo's own credentials.
