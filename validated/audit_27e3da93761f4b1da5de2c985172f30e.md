### Title
Nil/Undefined Dereference DoS via Missing `payload` in Private Payment Chain Head Element - (File: network.js)

### Summary
`handleOnlinePrivatePayment` in `network.js` dereferences `arrPrivateElements[0].payload.denomination` before validating that `payload` exists on the first private-payment element. A private-payment counterparty (or a paired device forwarding a chain via `wallet.js`'s `handlePrivatePaymentChains`) can send a head element that omits the `payload` field entirely, causing an uncaught `TypeError` when the property `.denomination` is read off `undefined`. This mirrors the CVE-2026-40195 pattern in Incus, where `srcBackup.Config` was assumed to be populated by an externally supplied structure and dereferenced without a nil-check, crashing the daemon.

### Finding Description
`handleOnlinePrivatePayment` only validates that `arrPrivateElements` is a non-empty array before immediately reading nested fields off the first element: [1](#0-0) 

```js
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	...
```

There is no check that `arrPrivateElements[0].payload` is a non-empty object (or exists at all) before accessing `.denomination` on it. If an attacker omits `payload` (or sets it to `null`/a primitive), `arrPrivateElements[0].payload.denomination` throws a `TypeError: Cannot read properties of undefined (reading 'denomination')`.

This is directly analogous to the reported Incus bug: `CreateBucketFromBackup` accessed `srcBackup.Config.Bucket.StorageBucketPut` assuming `Config` was populated from untrusted archive metadata, without a nil-check, producing a nil-pointer panic that crashed the daemon. Here, `payload` is the untrusted, attacker-supplied field (analogous to `Config`), and it is dereferenced without validation before any of the later, proper validation logic (`ValidationUtils.isValidBase64(unit, ...)`, etc.) even runs.

This code path is reachable both:
1. Directly as a peer/hub-sent `justsaying` message of type `private_payment` in `network.js`, and
2. Indirectly via `wallet.js`'s `handlePrivatePaymentChains`, which is invoked when a paired device or private-payment counterparty forwards a private payment chain (`network.handleOnlinePrivatePayment(ws, arrPrivateElements, true, {...})`), matching the in-scope "private-payment counterparty or paired device" actor category. [2](#0-1) 

Since JavaScript's runtime does not automatically recover from an uncaught synchronous exception thrown deep inside an event/message handler, this can crash the node process, rendering it unable to process any further units, confirmations, or private payments until restarted.

### Impact Explanation
An unauthenticated (or minimally trusted — anyone able to send a private payment chain, e.g. via a paired device or a private-payment counterparty relationship) party can send a malformed private-payment chain head element lacking the `payload` field. This throws an uncaught `TypeError` inside the message-handling code path, which can crash the node process (denial of service) — the node becomes unable to confirm new units or process further payments until manually restarted. Repeated exploitation keeps the node persistently offline, matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
Likelihood is high: the check that gates this code path (`ValidationUtils.isNonemptyArray(arrPrivateElements)`) only verifies the array is non-empty, not that its elements are well-formed. No authentication beyond being a private-payment counterparty or paired device is required to trigger the crash, and the vulnerable line executes before any of the subsequent validation (`isValidBase64`, `isNonnegativeInteger`, etc.), so the malformed input is dereferenced unconditionally on every call.

### Recommendation
Add an explicit validation step before dereferencing `arrPrivateElements[0].payload`:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("no payload in head private element");
```
This should be placed immediately after the `isNonemptyArray` check and before any property access on `.payload`. Additionally, consider validating all remaining fields expected by downstream code (`unit`, `message_index`) are wrapped in similarly defensive checks, and audit `handleSavedPrivatePayments` / `parsePrivatePaymentChain` for analogous unguarded `.payload` accesses on attacker-controlled elements.

### Proof of Concept
A malicious paired device or private-payment counterparty sends a `private_payment` message (or forwards one through `handlePrivatePaymentChains`) whose chain is:
```json
[
  { "unit": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=", "message_index": 0 }
]
```
i.e., an array with one element that has `unit` and `message_index` but omits `payload` entirely. When `handleOnlinePrivatePayment` executes:
```js
var output_index = arrPrivateElements[0].payload.denomination ? ... : -1;
```
`arrPrivateElements[0].payload` is `undefined`, and reading `.denomination` off it throws a `TypeError`, crashing the node process if not caught by an enclosing handler — reproducing the same missing-validation-before-dereference bug class described in the Incus advisory.
