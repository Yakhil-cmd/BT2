## Finding

### Title
Multisig transaction execution payload integrity check is feature-gated, allowing execution of an unapproved payload when `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is disabled - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction`, the VM-invoked prologue for multisig transactions, only verifies that the executable actually being run matches the payload that other owners approved when `features::abort_if_multisig_payload_mismatch_enabled()` is turned on. For multisig transactions created via `create_transaction` (full payload stored on-chain, `payload_hash == None`), if this feature is disabled there is no check at all binding the on-chain approved payload to the payload that actually executes.

### Finding Description
`validate_multisig_transaction` in [1](#0-0)  performs two distinct payload-integrity checks:

1. If `transaction.payload_hash.is_some()` (transaction created via `create_transaction_with_hash`), it asserts `sha3_256(payload) == *payload_hash`. This path is unconditional and always enforced.
2. If `transaction.payload.is_some()` (transaction created via `create_transaction`, storing the full payload), the match against the actual executed `payload` is only asserted **inside** an `if (features::abort_if_multisig_payload_mismatch_enabled() && transaction.payload.is_some() && !payload.is_empty())` block [2](#0-1) .

The `payload` parameter itself is derived by the VM from the *actual* `TransactionExecutableRef` of the signed transaction being executed, not from what is stored in the `MultisigAccount` resource — see `run_multisig_prologue` in [3](#0-2) , which builds `provided_payload` from `executable` and passes it as `payload` into `validate_multisig_transaction`.

Consequently, when `abort_if_multisig_payload_mismatch_enabled` is `false`:
- Quorum/approval checks (`can_execute` / `can_be_executed`, and the timelock check) only verify that *some* transaction at the resolved sequence number has enough owner approvals — they never inspect what code the executing owner actually attaches to the signed transaction.
- The hash-based check is skipped because `payload_hash` is `None` for `create_transaction`-created entries.
- The full-payload equality check is skipped because the feature flag gates it.

The executing owner therefore fully controls which `TransactionExecutableRef` (entry function/script) is bundled into the `SignedTransaction`, and the VM will execute whatever they supply as long as the quorum/timelock conditions for the pending sequence number are satisfied — regardless of whether other owners approved that exact payload.

### Impact Explanation
This breaks the core invariant of multisig approval: that a transaction executes only if the specific payload that reached quorum is the one that runs. An owner who obtains sufficient approvals for a benign/expected entry function (e.g. a small transfer) could instead execute an entirely different, unapproved entry function (e.g. draining funds, rotating keys, adding themselves as sole owner) under the multisig account's authority, while the on-chain event/audit trail still reflects the originally-approved payload hash/description. This is a direct "approval validation accepting the wrong approval set" admission-boundary failure with high/critical impact, since multisig accounts are typically used to protect high-value treasury or governance operations.

### Likelihood Explanation
Exploitability is entirely conditioned on whether `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled on a given network. I was unable to confirm from the available index whether this flag currently defaults to enabled or disabled on mainnet/testnet (the feature and its default rollout state are defined in `aptos-move/framework/move-stdlib/sources/configs/features.move`, `types/src/on_chain_config/aptos_features.rs`, and `aptos-move/aptos-release-builder/src/components/feature_flags.rs`, but I could not verify their concrete enabled/disabled state or governance history from the tools available). If the flag is disabled on any deployed network (which is common for newly introduced gated checks before governance activation), the bypass is directly reachable by any account owner with sequence-level execution rights and requires no privileged access beyond being one of the multisig owners.

### Recommendation
Make the full-payload match check unconditional (remove the feature gate), or, if the feature flag exists purely for rollout/versioning safety, ensure it is enabled by governance before this code path can be reached in production, and add a defense-in-depth check so that `create_transaction`-created multisig entries can never execute with a payload that doesn't match the stored payload, independent of feature-flag state.

### Proof of Concept
1. Deploy/select a network where `abort_if_multisig_payload_mismatch_enabled` is `false`.
2. Owner A calls `create_transaction(owner, multisig_account, payload_transfer_small)` to propose a small, benign transfer; this stores `transaction.payload = Some(payload_transfer_small)`, `payload_hash = None`.
3. Owners B, C approve the pending transaction believing it to be `payload_transfer_small`.
4. Owner A (or any owner with implicit approval) submits a `SignedTransaction` with `TransactionExecutableRef::EntryFunction` set to a different, malicious entry function (e.g., transferring all funds to themselves) instead of `payload_transfer_small`.
5. `run_multisig_prologue` computes `provided_payload` from this malicious executable and calls `validate_multisig_transaction`; since `payload_hash` is `None` and the feature flag is off, no comparison against the approved `payload_transfer_small` occurs.
6. Quorum/timelock checks pass (they only look at approval counts for the sequence number, not payload content), and the malicious entry function executes with the multisig account's authority.

**Note on confidence**: I could not conclusively determine the current on-chain/default activation state of the `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` feature flag within the tool budget available, which is the deciding factor for real-world exploitability. This should be verified (e.g., via `aptos-move/framework/move-stdlib/sources/configs/features.move` default flags and any genesis/governance feature-enablement records) before treating this as confirmed-exploitable on a live network.

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
