### Title
Cross-repository commit status forgery via webhook signature/scope mismatch enabling unauthorized deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the secret of whichever GitHub App/organization is named in the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) [2](#0-1) . Once the HMAC check succeeds for that named organization, the `status` event handler is invoked and mutates state (`Commit.where(sha: params.sha)`) **without ever checking which repository/stack owns that commit** [3](#0-2) . This is the same trust-binding break as the analog report: a field that gates the signature check (`repository.owner.login`) is not the field the privileged action is actually scoped to (the commit's real owning stack), so an entity that is authenticated for organization A can act on organization B's data.

### Finding Description
- Signature verification picks the GitHub App config (and thus the HMAC secret to validate against) purely from `repository.owner.login`/`organization.login`, both attacker-controlled JSON fields in the raw POST body [1](#0-0) [2](#0-1) .
- Other handlers (e.g. `PushHandler`, `CheckSuiteHandler`) at least re-derive the target `Stack`/`Repository` from `repository.full_name` via `Handler#stacks` / `Repository.from_github_repo_name` before acting [4](#0-3) [5](#0-4) .
- `StatusHandler`, however, does not use `stacks`/`repository_name` at all: it looks up `Commit.where(sha: params.sha)` globally across the whole Shipit installation and calls `create_status_from_github!` on every match [6](#0-5) .
- Equality that should hold but doesn't: `organization authenticated by verify_signature == organization owning the commit being mutated`. Before the attack, only GitHub (holding the real per-org webhook secret) can produce a valid signature for events about that org's commits. After the forged request, an actor who legitimately controls (or has an installed GitHub App for) organization A — a valid, unprivileged tenant of a multi-org Shipit deployment as documented in `docs/setup.md`/`test/dummy/config/secrets_double_github_app.yml` — can sign an arbitrary payload with `repository.owner.login = "OrgA"` (satisfying `verify_signature`) while setting `sha`/`state` to target a commit that actually belongs to `OrgB`'s stack, since `StatusHandler` never checks repository ownership.

### Impact Explanation
Shipit stacks gate deploys/CI status on commit checks (`create_status_from_github!` feeds the deployability status consulted before allowing a deploy). Forging a `success` status for a target commit on a victim stack the attacker does not administer can flip that commit into a deployable state, enabling an **unauthorized deploy** to proceed on infrastructure the attacker has no legitimate access to — this matches the explicitly in-scope "Critical" impact category (unauthorized deploy).

### Likelihood Explanation
The only prerequisite is being an unprivileged tenant/organization admin on a Shipit instance configured for multiple GitHub organizations (a supported and documented configuration, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), which lets the attacker legitimately obtain one valid `webhook_secret`/HMAC-signing capability. Target commit SHAs are public GitHub data. No repository write access, no `ApiClient` token, and no privileged Shipit account are required, satisfying the "unprivileged-attacker" and "credential/authentication boundary crossed" requirements.

### Recommendation
`StatusHandler#process` (and any other handler that doesn't already do so) must scope its lookup to the repository/stack that was actually authenticated by `verify_signature`, e.g. restrict `Commit.where(sha: params.sha)` to commits whose stack's `Repository` matches `payload.dig('repository', 'full_name')`, and additionally verify that the authenticated organization (`repository_owner` used in `verify_signature`) matches the owner of that resolved repository before any handler runs, closing the gap between the signature-verified identity and the entity being mutated.

### Proof of Concept
1. Attacker administers (or has installed a Shipit GitHub App for) `OrgA`, a legitimate but low-privilege tenant on a shared multi-org Shipit instance, and thus knows/can trigger a validly-signed `status` webhook whose secret belongs to `OrgA`.
2. Attacker crafts a raw JSON body:
   ```json
   {
     "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/decoy"},
     "sha": "<victim commit sha in OrgB/target-repo>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature [1](#0-0) .
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no ownership check, marking the victim commit (belonging to `OrgB/target-repo`, unrelated to `OrgA`) as `success` [3](#0-2) .
6. If this status was gating deploy eligibility on the victim stack, the attacker has just enabled/triggered an unauthorized deploy path on infrastructure they don't control.

          end

        def process
          Commit.where(sha: params.sha).each do |commit|

          end
        end
      end
