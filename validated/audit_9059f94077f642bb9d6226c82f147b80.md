### Title
Stale calc-time delegation snapshot silently overwrites (or panics against) live stake state during partitioned reward distribution - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
This is a direct analog of the reported Buyout bug class: a value derived from a point-in-time "total supply" snapshot (here, a stake account's `delegation.stake`) is cached at epoch-boundary reward *calculation* time and then blindly reused at a later reward *distribution* time, without re-validating it against the live, current on-chain state, which can legitimately change in the interim via an ordinary user instruction (`Merge`).

### Finding Description
Partitioned epoch rewards are computed once at the epoch boundary in `calculate_stake_rewards_and_commissions` / `redeem_delegation_rewards` [1](#0-0) , which snapshots `stake.delegation.stake` at that moment and returns `PartitionedStakeReward { inflation: InflationReward { stake, stake_reward, .. }, .. }`. This calculated reward set is stored and only actually applied to accounts many blocks later, spread across `num_partitions` blocks starting at `distribution_starting_block_height` (`REWARD_CALCULATION_NUM_BLOCKS` blocks after calculation, plus the number of partitions) [2](#0-1) .

Between calculation and the specific block that distributes a given account's partition, the stake account owner can submit an ordinary, unprivileged `Merge` instruction (merging another compatible stake account's lamports/delegation into this one), which increases the live `delegation.stake` recorded in `StakesCache` immediately [3](#0-2) . `Merge` requires no special privilege beyond stake authority and is exactly the kind of "innocent" total-changing operation the original report warns about (the report's hypothetical "split module" is here a real, already-shipped `Merge`/`Split` instruction).

At distribution time, `build_updated_stake_reward` loads the account from the **current** `stakes_cache_accounts` (live state, potentially already merged) but then computes the final delegation using `new_stake = partitioned_stake_reward.inflation.stake`, which is the **stale, calc-time snapshot** value, not derived from the live account read moments earlier [4](#0-3) .

Two divergent, both-flawed code paths result:

1. When `adjust_delegations_for_rent` is enabled, the code unconditionally sets `account.set_state(&StakeStateV2::Stake(meta, new_stake, flags))` using the stale `new_stake.delegation` [5](#0-4) . Any legitimately merged-in stake that occurred after calculation is discarded/overwritten by the older, smaller delegation value, permanently desynchronizing the stake account's `delegation.stake` from its actual lamport balance and merge history — the merged-in stake becomes "lost" from the accounting perspective (it no longer contributes to activated/effective stake, future rewards, or voting power), even though the lamports remain in the account.
2. When `adjust_delegations_for_rent` is disabled, the code instead performs `assert_eq!(expected_delegation, new_stake.delegation.stake, ...)` where `expected_delegation` is derived from the **live** `stake.delegation.stake` fetched from `stakes_cache_accounts` plus the calc-time `stake_reward` [6](#0-5) . If the live delegation has grown via `Merge` since calculation, this assertion is false and the validator **panics**. Because block processing (including reward distribution) is deterministic and executed identically by all validators processing the same block, every validator that has ingested the same `Merge` transaction prior to the corresponding distribution block will hit the same `assert_eq!` and panic simultaneously, producing a cluster-wide halt at the epoch reward-distribution boundary.

### Impact Explanation
- If the code takes the "overwrite" branch, a user's legitimately merged stake silently disappears from `delegation.stake` accounting, corrupting stake-weighted vote power/activation/future reward calculations for that account — an accounting divergence directly analogous to "buyout proposer paying for the whole vault but getting only part of it."
- If the code takes the "assert" branch, any account whose delegation changed via `Merge` between calculation and its distribution block causes a deterministic `assert_eq!` panic in `build_updated_stake_reward`, which is invoked from `distribute_epoch_rewards_in_partition` on every validator processing that block — halting cluster consensus during the reward-distribution period at an epoch boundary.

Both outcomes match required impact categories: cross-node/account state divergence (accounting corruption) or an epoch-boundary halt.

### Likelihood Explanation
`Merge` is a normal, permissionless (subject only to the account's own stake authority) stake-program instruction available to any staker at any time [7](#0-6) [8](#0-7) . The reward-calculation-to-distribution window spans `REWARD_CALCULATION_NUM_BLOCKS` plus `num_partitions` blocks, giving normal stakers ample opportunity to submit a `Merge` transaction targeting one of their own pending-reward stake accounts before its specific distribution block/partition is processed. No malicious module or special access is required — a delegator merely needs to merge stake accounts near the epoch boundary, an action stakers legitimately perform for portfolio management (e.g., after a prior `Split`/new delegation activates, as shown in existing test coverage of `Merge` immediately after activation) [9](#0-8) .

I was not able to fully confirm within the available context whether the `adjust_delegations_for_rent` (`relax_post_exec_min_balance_check`) feature is unconditionally activated on all current clusters (it appears in `feature-set/src/lib.rs`), so I cannot definitively state which of the two branches (silent overwrite vs. panic) is reachable on mainnet today versus only on clusters/forks where that feature is not yet active. Both branches share the same root cause — reuse of the stale `partitioned_stake_reward.inflation.stake` snapshot instead of re-deriving/validating against the live account state — and both are only guarded by the `adjust_delegations_for_rent` feature flag, not by any check that the live delegation is unchanged.

### Recommendation
In `build_updated_stake_reward`, do not use the calc-time `partitioned_stake_reward.inflation.stake.delegation` as the final on-chain delegation value unconditionally. Instead:
- Re-derive the final delegation from the **live** `stake.delegation` read from `stakes_cache_accounts` plus the calculated `stake_reward`/`block_reward` deltas, so that any legitimate change to the account (e.g., via `Merge`) since calculation time is preserved rather than overwritten.
- Replace the `assert_eq!` panic path with a graceful reconciliation: if the live delegation differs from what was assumed at calculation time, add the reward delta on top of the live value instead of aborting.
- Consider detecting and logging/metric-reporting (not panicking) when live delegation state has diverged from the calc-time snapshot at distribution time, mirroring the report's suggested "update supply and notify" mitigation.

### Proof of Concept
Deterministic PoC sketch (would need to be run against a local test validator/bank test harness):
1. Create a stake account `A` delegated to vote account `V`, and let an epoch pass so rewards are calculated for it (`calculate_stake_rewards_and_commissions` snapshots `A.delegation.stake = S`, computing `stake_reward = R`).
2. Before the block that distributes `A`'s partition (i.e., before `distribution_starting_block_height + partition_index_for_A`), submit a `Merge` instruction merging a second compatible stake account `B` (same voter, lockup, authority) into `A`, increasing the live `A.delegation.stake` to `S + B_stake`.
3. When the distribution block for `A`'s partition is processed:
   - If `adjust_delegations_for_rent` is off: `build_updated_stake_reward` computes `expected_delegation = (S + B_stake) + R` from the live cache, but compares it against `new_stake.delegation.stake = S + R` (the stale snapshot) — the `assert_eq!` fails and the validator panics, matching `test_delegation_adjustment_at_distribution`-style test harness but with a `Merge` instead of a plain lamport transfer [10](#0-9) .
   - If `adjust_delegations_for_rent` is on: the account's final `delegation.stake` is silently reset to `S + R`, losing `B_stake` from the delegation accounting even though `B`'s lamports were merged into `A`'s balance.

This mirrors the original Buyout PoC pattern: a "supply-changing" operation (`Merge`, analogous to the report's hypothetical "split module") executed between a cached price/quantity snapshot and its later use, producing an inconsistent or crash-inducing result.

            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),

                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
