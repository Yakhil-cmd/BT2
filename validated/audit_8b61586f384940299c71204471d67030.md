### Title
Integer overflow in Elixir NIF binding's list-length-to-byte-size multiplication causes undersized heap allocation and out-of-bounds write - (File: bindings/elixir/native/src/ckzg_wrap.c)

### Summary
`verify_cell_kzg_proof_batch_nif` (and its sibling cell/recovery NIFs) in the Elixir binding obtain array lengths via `enif_get_list_length`, which fills an `unsigned int` (32-bit) `len` output. These `len` values are then multiplied by a fixed element size (`BYTES_PER_COMMITMENT`, `sizeof(uint64_t)`, `BYTES_PER_CELL`, `BYTES_PER_PROOF`) and passed directly to `enif_alloc()` to size the destination buffer. The multiplication is performed in 32-bit arithmetic and can wrap around before being widened to the `size_t` parameter expected by `enif_alloc`. The subsequent copy loop, however, iterates using `enif_get_list_cell` over the *actual*, non-truncated list length, writing one full element per list entry into the undersized/wrapped buffer.

### Finding Description
In `bindings/elixir/native/src/ckzg_wrap.c`: [1](#0-0) 

`commitments_len`, `cell_indices_len`, `cells_len`, and `proofs_len` are all declared as `unsigned int` and populated from `enif_get_list_length`. The function only checks that the four counts are equal to each other — it never bounds them against a sane maximum.

Buffers are then allocated as: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Each of these expressions (`len * ELEMENT_SIZE`) is evaluated in 32-bit `unsigned int` arithmetic (per C's usual arithmetic conversions, since `len` is `unsigned int` and the size constants fit in `int`/`unsigned int`), so the product wraps modulo 2^32 *before* being passed to `enif_alloc(size_t)`. For example, with `BYTES_PER_CELL` (2048 bytes per `Cell`), a list length of exactly `2^32 / 2048 = 2097152` makes `cells_len * BYTES_PER_CELL` wrap to `0`, causing `enif_alloc(0)` to return a zero/near-zero-sized allocation (or `NULL`, depending on the allocator).

Immediately after, the fill loops copy one element per *actual* list entry: [6](#0-5) 

Since `enif_get_list_cell` walks the real (un-wrapped) list of ~2.1 million entries, `memcpy(&cells[i], current_b.data, BYTES_PER_CELL)` writes far beyond the tiny/zero allocation — a classic heap buffer overflow driven by an integer-overflowed size calculation, structurally identical to the `FillUniColor`/`FillUniGray` pattern in the referenced OpenCV advisory (unchecked length used in a size computation that overflows before allocation).

This breaks the intended invariant that "allocated buffer size == number of elements written × element size"; instead the buffer is undersized while the writer still walks the full, attacker-controlled element count, corrupting adjacent heap memory in the BEAM VM process.

### Impact Explanation
A successful trigger corrupts heap memory inside the process hosting the Elixir NIF, which can crash (abort) the node process handling the RPC/NIF call, or potentially be leveraged for further memory corruption. This matches the "High" bar in scope: an attacker-supplied cell/commitment/proof batch (fed to `verify_cell_kzg_proof_batch`) can abort the node process that loaded this binding.

### Likelihood Explanation
Triggering the wraparound for the `cells` buffer (the smallest-multiplier, i.e., most attacker-favorable overflow target due to `BYTES_PER_CELL` being large) requires supplying an Erlang list with about 2.1 million elements, each a valid 2048-byte binary — i.e., roughly 4+ GB of well-formed cell data in a single call, plus matching-length `commitments`, `cell_indices`, and `proofs` lists as required by the equal-length check. This is a very large payload to construct and transmit, which substantially reduces practical likelihood; it is a genuine 32-bit-arithmetic bug but the attack requires multi-gigabyte, non-trivial input, bordering on the "large allocation" territory the scope rules ask to deprioritize. I flag this uncertainty explicitly: the bug class (unsigned-int overflow feeding an allocation size) is real and reachable from an unprivileged NIF caller, but I could not fully confirm exploitability in practice (actual BEAM VM behavior for `enif_alloc(0)`, and whether the Erlang VM would itself refuse to build/pass such a large list before reaching the NIF) without running the code, which is outside available tooling.

### Recommendation
Compute buffer sizes using widened (`size_t`/`uint64_t`) arithmetic before allocation, e.g. `(size_t)len * BYTES_PER_CELL`, and reject list lengths above a sane protocol-defined maximum (e.g., `CELLS_PER_EXT_BLOB`) before any allocation, consistent with the bounds already enforced in the core C library (`src/eip7594/eip7594.c`) for `num_cells`.

### Proof of Concept
1. From Elixir, call `Ckzg.verify_cell_kzg_proof_batch/4` with `commitments`, `cell_indices`, `cells`, and `proofs` lists each of length `2097152` (`2^32 / BYTES_PER_CELL`), where each `cells` entry is a valid `BYTES_PER_CELL`-byte binary, each `commitments`/`proofs` entry a valid 48-byte binary, and `cell_indices` entries valid `uint64_t`s (duplicated to stay within `CELLS_PER_EXT_BLOB` semantics, since the C-level bound check in `verify_cell_kzg_proof_batch` only checks each index individually, not the total count).
2. In the NIF, `cells_len * BYTES_PER_CELL` wraps to `0` in 32-bit arithmetic; `enif_alloc(0)` returns a degenerate allocation.
3. The fill loop at [6](#0-5)  still executes ~2.1 million `memcpy` calls of `BYTES_PER_CELL` bytes each into the degenerate buffer, corrupting heap memory and crashing the BEAM VM process.
