### Title
Cross-organization commit-status forgery via unscoped `sha` lookup in webhook `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The webhook signature-verification layer authenticates a GitHub webhook against a specific *organization*'s configured `webhook_secret` (selected from the unverified `repository.owner.login` field of the payload), but the `status` event handler that acts on the payload never re-checks that the target commit actually belongs to a stack owned by that authenticated organization. It matches purely by SHA across the entire database. In a multi-organization Shipit deployment, an attacker who controls (or knows the webhook secret of) any one configured GitHub organization can forge a `status` webhook for a commit SHA belonging to a completely different organization's repository and inject an arbitrary CI status for it.

### Finding Description
`WebhooksController#verify_signature` derives the signing key from the *organization*, not the specific repository, by reading `repository.owner.login` straight out of the still-untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to whichever `GitHubApp` config entry matches that organization name, each with its own independent `webhook_secret`, as documented for multi-org deployments: [3](#0-2) 

So the binding being asserted by signature verification is: **"this request was signed by Organization X's webhook secret."** It does **not** assert "this request concerns a repository owned by Organization X." Those are two different things, and the payload's `repository.full_name` / commit `sha` fields used later by handlers are not cross-checked against the organization that was used to select the verification key.

`StatusHandler#process` then acts purely on the raw `sha` field, with no repository/organization scoping at all: [4](#0-3) 

Unlike `PushHandler`, which at least scopes to `Repository.from_github_repo_name(repository_name)` via the base `Handler#stacks` helper: [5](#0-4) 

`StatusHandler` bypasses that helper entirely and does `Commit.where(sha: params.sha)` — a global, unscoped lookup across every stack/repository/organization configured in the Shipit instance.

**Root cause / binding broken:** Equality asserted = "organization that authenticated (via `webhook_secret`)" == "organization whose repository is written to." The webhook controller only proves the former; `StatusHandler` writes based on a bare `sha` match with no proof of the latter.

### Impact Explanation
Once `Commit.where(sha: params.sha)` finds the target commit belonging to another organization's stack, `commit.create_status_from_github!(params)` records a new `Status`, which triggers `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery`. Downstream, `Commit#add_status` calls `stack.schedule_merges` when the new status is `pending` or `success`. This means an attacker who only administers one organization's GitHub App configuration in a multi-org Shipit install (a legitimate, unprivileged position relative to the *other* organization) can forge a "success" status on a victim organization's commit they have no GitHub write access to, and thereby unblock/trigger the merge queue or continuous-delivery gating for that victim repository — i.e., an unauthorized merge/deploy action, which falls under the "unauthorized deploy, rollback, or merge" Critical-impact category.

### Likelihood Explanation
This requires a Shipit instance configured with multiple GitHub organizations (a documented, supported configuration per `docs/setup.md` and `secrets.development.shopify.yml`) where the attacker controls one org's app/webhook secret but not the victim org's. This is a realistic deployment pattern (shared internal Shipit instance serving several teams/orgs). The attacker also needs to know or guess a valid commit SHA belonging to the victim stack, which is generally public/discoverable information (commit SHAs are not secrets, visible via GitHub itself or the Shipit UI).

### Recommendation
`StatusHandler` (and any other handler doing bare `sha`/global lookups) must scope commit lookups to stacks whose `Repository` matches the `repository.full_name` in the payload (as `PushHandler`/`Handler#stacks` already do), and the webhook `verify_signature` step should additionally confirm that the resolved organization for signature verification matches the actual owner of the repository referenced in the payload before processing, rather than only using it to pick a decryption key.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per multi-org config docs), and both have stacks registered.
2. Attacker controls `OrgA`'s GitHub App / webhook secret (e.g., legitimately administers that org's integration) but has no access to `OrgB`.
3. Attacker finds a commit SHA `S` on an `OrgB`-owned stack tracked by Shipit (visible via the public Shipit UI or GitHub).
4. Attacker POSTs to the webhooks endpoint with `X-Github-Event: status`, body `{"repository": {"owner": {"login": "OrgA"}}, "sha": "S", "state": "success", "context": "ci/attacker"}`, signed with `OrgA`'s known `webhook_secret`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the HMAC (using the attacker's own known secret).
6. `StatusHandler#process` executes `Commit.where(sha: "S")`, finds the commit belonging to `OrgB`'s stack, and calls `create_status_from_github!`, recording a forged "success" status and triggering `schedule_merges`/continuous delivery for `OrgB`'s stack — despite the attacker never having been authenticated for `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
