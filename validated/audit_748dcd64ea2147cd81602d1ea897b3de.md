### Title
Organization used for webhook signature verification is decoupled from the repository the webhook actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an inbound webhook based on `repository_owner`, taken from the *unverified* JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), then verifies the signature against that org's `webhook_secret`. All downstream handlers, however, resolve which `Repository`/`Stack` to mutate from a *different* field of the same unverified body: `payload.dig('repository', 'full_name')`. Nothing enforces that the organization used to pick the verifying secret and the owner encoded in `full_name` refer to the same GitHub org. [1](#0-0) [2](#0-1) 

### Finding Description
In the multi-organization secrets schema, each org has its own `webhook_secret`, which is allowed to be blank/`nil` (documented as such in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`). `GitHubApp#verify_webhook_signature` explicitly bypasses HMAC verification when no secret is configured: [3](#0-2) 

The controller resolves which `GitHubApp` (and thus which secret) to verify against purely from attacker-supplied payload content, before any cryptographic check has occurred: [4](#0-3) [5](#0-4) 

If an installation hosts multiple GitHub orgs (`Shipit.github_organizations`) and any one of them has `webhook_secret` unset — a supported, documented configuration — an unauthenticated attacker can set `repository.owner.login` (or `organization.login`) to that unsecured org so `verify_signature` short-circuits to `true` with no valid HMAC required, while simultaneously setting `repository.full_name` to `"<secured-org>/<target-repo>"`. All webhook handlers use only `full_name` to locate the `Repository`/`Stack` to act on: [2](#0-1) [6](#0-5) 

For example, the push handler triggers `stack.sync_github` and membership/status/check_suite handlers create teams, users, memberships, or commit statuses — all keyed off `full_name`/`repository` fields that were never covered by the (bypassed) signature check for the secured org: [7](#0-6) 

This breaks the equality the engine implicitly assumes: `organization authenticated (repository_owner used to pick webhook_secret) == organization that owns the repository actually written (repository.full_name)`. After the attack, `organization_authenticated ("weak-org") != repository_owner_written ("secured-org")`, letting a request that never passed a valid signature for the secured org still drive that org's stacks (sync from arbitrary commit SHA, archive/unarchive review stacks, forge commit statuses, add/remove team memberships).

### Impact Explanation
This qualifies as High: unauthenticated forgery of `push`, `status`, `check_suite`, `pull_request`, and `membership` events lets an outside attacker cause unauthorized `GithubSyncJob` runs, fabricate commit statuses/check runs that gate deploy eligibility, and manipulate `Team`/`Membership`/`User` records used for `Shipit.github_teams` authorization — all without holding any secret for the targeted organization. Depending on downstream trust in commit statuses/check runs for deploy gating, this can escalate into unauthorized deploy triggers.

### Likelihood Explanation
Requires: (1) a multi-organization `secrets.github` configuration (explicitly supported, and shown with `webhook_secret: # nil` in the app's own example/dummy secrets files) and (2) at least one configured org without a webhook secret. This is a plausible/likely real-world deployment state since the docs/examples present blank `webhook_secret` as a normal default, and nothing in `verify_signature` enforces that all configured orgs share equally strong secrets or that `repository.owner.login` matches `repository.full_name`'s owner segment.

### Recommendation
Do not select the verifying `GitHubApp`/secret using attacker-controlled payload fields before signature verification. Alternatively: (a) require a non-blank `webhook_secret` for every configured organization at boot, (b) cross-validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name` before processing, or (c) verify the signature against every configured secret and only trust the resulting organization identity if exactly one HMAC succeeds, using that verified organization (not the payload-declared one) for repository resolution.

### Proof of Concept
1. Deploy Shipit with `secrets.github` containing two orgs: `weakorg` (no `webhook_secret`) and `secureorg` (with a secret), both configured per `config/secrets.development.shopify.yml`.
2. POST to `/webhooks` (or the engine's mounted webhook path) with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "weakorg" }, "full_name": "secureorg/target-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "weakorg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request passes with no valid signature for `secureorg`.
4. `PushHandler` resolves the target via `payload.dig('repository', 'full_name')` = `"secureorg/target-repo"`, looks up the real `Repository`/`Stack` for `secureorg`, and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — an unauthorized action on `secureorg`'s stack triggered without ever presenting a valid signature for that org.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
