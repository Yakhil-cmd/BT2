### Title
Clickjacking of authenticated merge-queue enqueue/dequeue via `X-Frame-Options: ALLOWALL` on `MergeStatusController#show` - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController#show` unconditionally sets `X-Frame-Options: ALLOWALL` [1](#0-0)  and derives the displayed stack/PR entirely from an attacker-supplied `referrer` query parameter [2](#0-1) . Because the page can be framed cross-origin and the resulting enqueue/dequeue actions perform no origin/referer check, a UI-redressing attacker can get a logged-in operator to unknowingly trigger `PUT /merge_status/*stack_id/pull/:number` or `DELETE .../pull/:number` on a stack/PR of the attacker's choosing.

### Finding Description
The broken binding: the operator's authenticated identity `session[:user_id] == operator_github_id` is intended to authorize only actions the operator *deliberately* takes on the Shipit origin, but with framing enabled the click event that fires `enqueue`/`dequeue` can be triggered by an attacker-controlled overlay on `attacker-origin != shipit-origin`, while the browser still attaches the operator's session cookie and the DOM-embedded CSRF token to the request.

Path: attacker crafts `<iframe src="https://shipit-host/merge_status?referrer=https://github.com/{owner}/{repo}/pull/{number}">`. `referrer_parser` parses this and `stack` resolves the exact stack for that owner/repo/branch [3](#0-2) , so the attacker fully controls which repository/stack/PR is targeted, not just the visual layer. If the framed operator is `current_user.logged_in?`, the real enqueue/dequeue controls render inside the iframe [4](#0-3) . The attacker overlays a decoy button aligned with the genuine "Enqueue"/"Dequeue" control and lures the operator into clicking it (classic clickjacking). Because the click happens inside the real Shipit-origin iframe, the resulting request is a normal same-origin request carrying valid session cookie and CSRF token — `protect_from_forgery with: :exception` in `ShipitController` does not stop this, since CSRF protection guards against forged cross-origin requests with a *missing* token, not deceptive UI over a *legitimate* same-origin request [5](#0-4) .

`enqueue`/`dequeue` are not in `skip_authentication`, so authentication is enforced, but neither action performs any additional origin/referer/CSRF-beyond-token check: `enqueue` calls `MergeRequest.request_merge!(stack, params[:number], current_user)` directly [6](#0-5) , and `dequeue` cancels the matching request if `waiting?` [7](#0-6) . Only `session[:user_id]`/CSRF-token validity gates these mutations; there is no check that the request originated from a first-party page rather than a framed, attacker-controlled page. The `ALLOWALL` header is the single control removed here, and it is set unconditionally for every request to `#show`, not scoped to a specific trusted embedder.

### Impact Explanation
A successful clickjack causes an authenticated operator's browser to submit a genuine, cookie- and CSRF-token-valid mutation request that adds (`enqueue`) or removes (`dequeue`) a specific pull request from a stack's merge queue — for a stack and PR number chosen entirely by the attacker via the `referrer` parameter. This is a real, repeatable state mutation on the merge queue of any stack the tricked operator is authorized to act on, performed without the operator's informed consent. It directly enables unauthorized manipulation of the automated merge pipeline, matching the "unauthorized ... merge" mutation category. It is repeatable against arbitrary stacks/PRs (limited only by which stacks the victim operator can act on) each time the attacker can get the operator to click.

### Likelihood Explanation
Preconditions: `merge_queue_enabled` on the target stack, and a logged-in operator who can be lured to open/interact with an attacker page (the standard clickjacking precondition). No GitHub secrets, API tokens, or privileged roles are needed by the attacker — only a webpage and social engineering of a click, which is the accepted attacker capability for clickjacking classes of bugs. Feasibility is high because the header is unconditionally permissive and there is no additional server-side origin check to defeat.

### Recommendation
Do not set `X-Frame-Options: ALLOWALL` unconditionally. If framing is required for the legitimate browser-extension use case, scope the permissive header to that specific integration (e.g., only allow framing for requests carrying a recognized extension marker, or move to a `Content-Security-Policy: frame-ancestors` allow-list of specific trusted origins), and require an explicit re-authentication/confirmation step (or a double-submit interaction that can't be silently proxied through an iframe) before executing `enqueue`/`dequeue`. At minimum, add origin/referer validation on the mutating `enqueue`/`dequeue` endpoints so they reject requests that did not originate from the operator's Shipit UI as a top-level navigation.

### Proof of Concept
```ruby
# test/controllers/shipit/merge_status_controller_test.rb
test "#show sets a permissive X-Frame-Options allowing arbitrary framing" do
  stack = shipit_stacks(:shipit)
  get "/merge_status", params: { referrer: "https://github.com/#{stack.repository.owner}/#{stack.repository.name}/pull/1" }
  assert_equal "ALLOWALL", response.headers["X-Frame-Options"]
end

test "#enqueue performs the mutation without validating request origin/referer" do
  stack = shipit_stacks(:shipit)
  session_login_as(shipit_users(:walrus))

  # Simulate a same-origin request as would be produced by a clickjacked click
  # inside an iframe embedded on an attacker page — no Origin/Referer check exists.
  put enqueue_merge_request_path(stack_id: stack.to_param, number: 42),
      headers: { "Origin" => "https://attacker.example", "Referer" => "https://attacker.example/evil" }

  assert_response :success
  assert MergeRequest.find_by(number: 42, stack: stack).locked_by.present?, "enqueue mutated state despite foreign Origin/Referer"
end
```
Both assertions confirm the binding divergence: `X-Frame-Options` allows arbitrary embedding, and the mutating endpoint accepts the request regardless of `Origin`/`Referer`, which is exactly the missing guard the clickjacking exploit relies on.
