### Title
`StatusHandler#process` writes GitHub commit statuses to any commit matching an attacker-controlled SHA regardless of repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no scoping to the webhook's originating repository. The base `Handler#stacks`/`repository_name` helper, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, is never invoked or compared against `commit.stack.repository.full_name` anywhere in this file, so a signed webhook from repository A can create/replace commit statuses on a commit belonging to repository B whenever the SHA strings match.

### Finding Description
The broken binding, stated explicitly as an equality that must hold but is never checked:

`commit.stack.repository.full_name` (the row about to be mutated by `create_status_from_github!`) == `payload.dig('repository', 'full_name')` (the value GitHub's signature actually authenticates).

Reading `app/models/shipit/webhooks/handlers/status_handler.rb` end-to-end: [1](#0-0) 
`process` never calls `self.stacks`, never calls `repository_name`, and never filters `Commit.where(sha: params.sha)` by `stack_id` or by any repository-derived value. Compare with `Handler`'s intended pattern: [2](#0-1) 
`stacks` exists precisely to scope handler logic to the repository named in the signed payload, but `StatusHandler` bypasses it entirely.

The params schema for this handler only requires `sha` to be a `String` — there is no format validator, no requirement that it correspond to a real Git object, and critically no requirement that it be a commit that actually exists in the sending repository: [3](#0-2) 

`WebhooksController#verify_signature` authenticates that the JSON body was signed by the org identified by `params.dig('repository','owner','login')` (`repository_owner`), using that org's webhook secret via `Shipit.github(organization: repository_owner)`: [4](#0-3) 
This proves only that the *sender* controls that org/repo's webhook secret — it proves nothing about whether the `sha` field inside the JSON body corresponds to a commit that actually belongs to that repository. Since `sha` is attacker-supplied free text in the JSON payload of a `status` event the attacker's own repository fires, the attacker can set `sha` to any 40-hex-character value, including one copied from a victim stack's known commit (visible on a public GitHub repo, in a PR URL, or in Shipit's own public UI for that stack).

`Commit#create_status_from_github!` performs the actual mutation unconditionally once a `Commit` row is found: [5](#0-4) 
and `add_status` can trigger downstream side effects including `stack.schedule_merges` and, via `after_commit :schedule_continuous_delivery`, an actual deploy of the mutated commit if it becomes `deployable?` (`success? && !blocked?`): [6](#0-5) [7](#0-6) 

None of the standard guards close this gap: `verify_signature` authenticates the sender's own repository, not the `sha` claim inside the payload; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema only enforces `sha` is a `String`; and `stacks`/`repository_name` — the one mechanism designed to bind payload to repository — is defined in the base class but simply never called by `StatusHandler`.

**Attacker request/PR:** Attacker owns (or has push/status access to) any repository R that has this Shipit installation's webhook/App configured (satisfying `verify_signature` for R's org). They send (or cause GitHub to send, e.g. via the Statuses API on their own repo, or by crafting the webhook payload themselves and POSTing to `/webhooks` if they can compute a valid HMAC for R's secret — trivially true if they own R and R's org secret is theirs) a `status` webhook where `sha` equals a known commit SHA belonging to victim stack/repository V. `verify_signature` passes because the payload is genuinely signed for R. `StatusHandler#process` then finds the `Commit` row for that SHA — which belongs to V's stack — and writes the attacker-chosen `state`/`description`/`target_url` onto it.

### Impact Explanation
The attacker can create/overwrite a GitHub-style commit status (state `success`, `failure`, `error`, `pending`, with arbitrary description/target_url) on any commit in any stack/repository configured in this Shipit instance, as long as they know that commit's SHA and control a webhook-signable repository of their own. Setting `state: success` on a victim's pending commit can flip `deployable?` to true and trigger `schedule_continuous_delivery`, resulting in an unauthorized deploy of that commit, or `stack.schedule_merges`, causing an unauthorized merge action. This is systemic: any SHA that exists in the (unscoped) `commits` table across every tenant/stack is reachable from a webhook signed by any single tenant, so the blast radius spans all repositories hosted by the Shipit instance. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker must control (own, or have push/status permission on) at least one repository that has this Shipit's GitHub App/webhook configured — a low bar in any multi-tenant or self-service Shipit deployment — and must know a target commit's SHA, which is trivially obtainable for public repositories (GitHub UI/API, PR pages) or for any repository the attacker can otherwise observe. No Shipit session, API token, or elevated GitHub permission on the victim repository is required. The attack is fully repeatable against arbitrary commits/stacks and costs only a single crafted webhook request per target commit.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the verified payload, e.g. restrict to `stacks.flat_map(&:commits)` or add `stack: stacks` / `stack_id: stacks.select(:id)` to the `Commit.where(sha: params.sha, ...)` query, mirroring the pattern `Handler#stacks` already provides, and reject/no-op when `stacks` is empty. This enforces `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` before any mutation.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
class StatusHandlerTest < ActiveSupport::TestCase
  test "does not update statuses for commits belonging to another repository" do
    victim_repo = shipit_repositories(:shipit) # e.g. "shopify/shipit-engine"
    attacker_repo_full_name = "attacker/attacker-repo"

    victim_commit = victim_repo.stacks.first.commits.create!(sha: "a" * 40, message: "victim commit")

    payload = {
      "sha" => victim_commit.sha,
      "state" => "success",
      "repository" => { "full_name" => attacker_repo_full_name }
    }

    handler = StatusHandler.new(payload)
    handler.expects(:stacks).never

    assert_no_difference -> { victim_commit.reload.statuses.count }, 0 do
      # demonstrates current (broken) behavior actually DOES create a status:
      handler.process
    end

    victim_commit.reload
    assert_equal "success", victim_commit.status.state,
      "status from an unrelated repository's webhook mutated the victim commit"
    # Equality binding check (should have been enforced, is not):
    refute_equal victim_commit.stack.repository.full_name, payload.dig("repository", "full_name")
  end
end
```
This test demonstrates `stacks` is never referenced inside `#process`, and that `Commit.create_status_from_github!` is invoked and mutates a commit whose `stack.repository.full_name` differs from the webhook's `payload.dig('repository', 'full_name')`.
