### Title
Unbounded attestor list in the `attested` address-definition opcode allows creating an address whose signature validation cost grows without limit - (File: `definition.js`)

### Summary
The `attested` opcode, usable inside address/asset spending-condition definitions, accepts an attestor address array (`args[1]`) with **no maximum length check**, unlike every other list embedded in unit content (`MAX_ATTESTORS_PER_ASSET`, `MAX_DENOMINATIONS_PER_ASSET_DEFINITION`, `MAX_CHOICES_PER_POLL`, `MAX_AUTHORS_PER_UNIT`, etc., all defined in `constants.js`). An attacker can define an address whose definition contains an `['attested', ['addr', [huge array of thousands of addresses]]]` clause. Once the address is created, every future unit signed under that definition forces every validating node to evaluate the full, unbounded attestor array during signature verification — a cost imposed on the whole network for every future transaction from that address, analogous to `extraRewards` being spammable to make `_processRewards()` iteration arbitrarily expensive.

### Finding Description
`validateDefinition()` in `definition.js` validates the `attested` node when a new definition is introduced: [1](#0-0) 
This loop over `arrAttestors` checks only that each entry is a valid address — there is no cap on `arrAttestors.length` (compare with `checkAttestorList()` in `validation.js`, used for asset attestor lists, which explicitly enforces `constants.MAX_ATTESTORS_PER_ASSET`): [2](#0-1) 

Crucially, the per-node complexity counter (`complexity++`) in `validateDefinition`'s `evaluate()` function is incremented once per AST node, not once per element of `arrAttestors`: [3](#0-2) 
So `MAX_COMPLEXITY` (100) and `MAX_OPS` do **not** bound the size of the attestor array — only the overall unit-size limit (`MAX_UNIT_LENGTH`, 5 MB) does, which still permits tens of thousands of 32-byte addresses inside a single `attested` clause.

Once such a definition is accepted (the address becomes chash160 of that definition), it is reused every time the address signs a unit. `validateAuthentifiers()`'s `evaluate()` function handles the `attested` opcode by calling `storage.filterAttestedAddresses()` with the entire unbounded `arrAttestors` array: [4](#0-3) 
This means every single unit ever signed with that definition — by the attacker or by anyone referencing that address via a nested `['address', ...]` condition — re-triggers a lookup against the full, attacker-chosen attestor list on every full node that validates the unit. Since the list is fixed at address-creation time but reused indefinitely, this is a “define-once, pay-forever” cost multiplier imposed on all nodes that ever validate a unit signed by (or referencing) that address, exactly mirroring the `extraRewards` bug class: an attacker-controlled, effectively unbounded list that gets iterated on every future protocol-critical action, at cost to all participants rather than only the attacker.

### Impact Explanation
Because address chashes are derived from the definition itself, an attacker can craft one address with a maximal-size `attested` attestor array once, then repeatedly issue ordinary payments/units signed by that address (or have other addresses reference it via `['address', ...]`). Each such unit forces every validating node (light and full) to process the oversized array during consensus-critical signature/definition evaluation, inflating validation CPU/DB cost network-wide without a corresponding fee increase (unit-size fee is proportional to unit content, but the definition itself is stored once and amortized over unlimited reuse). This creates asymmetric network-wide validation cost / potential DoS vector for nodes trying to keep up with the DAG, which maps to "a network unable to confirm new units efficiently" — the accepted high-severity impact category for this bug class.

### Likelihood Explanation
Likelihood is High for any single attacker with control over their own address definition: creating an oversized `attested` clause requires only posting one valid new-address definition unit (paid for once, size-bounded only by `MAX_UNIT_LENGTH`), after which the attacker (or anyone nesting that address) can trigger the expensive re-validation on demand for the cost of ordinary transaction fees. No special privilege beyond normal unit posting is needed, matching the "unprivileged unit poster / address definition author" reachability required by scope.

### Recommendation
Add an explicit cap (e.g., a new `MAX_ATTESTORS_IN_DEFINITION` constant, consistent with `MAX_ATTESTORS_PER_ASSET`) on `arrAttestors.length` in the `attested` opcode validation in `definition.js`'s `validateDefinition()`, and reject any address definition whose attestor list exceeds it. Additionally, consider factoring the array length into the complexity/ops accounting so that arbitrarily large embedded lists cannot bypass `MAX_COMPLEXITY`/`MAX_OPS` limits in any current or future opcode.

### Proof of Concept
1. Craft an address definition: `['sig', {pub_k: ...}]` combined via `['and', [['sig', {...}], ['attested', ['this address', arrHugeAttestorList]]]]` where `arrHugeAttestorList` contains, e.g., 50,000 distinct valid Base32 addresses (well within `MAX_UNIT_LENGTH`).
2. Post a unit that defines this address (e.g., first payment from the new address, including the `definition` field) — this passes `validateDefinition()` since no length check exists for `arrAttestors`.
3. From then on, sign and broadcast further ordinary units from this address (or from any address that embeds an `['address', <attacker_address>]` condition referencing it).
4. Each such unit forces every validating node's `validateAuthentifiers()`/`evaluate()` to call `storage.filterAttestedAddresses()` with the full 50,000-entry list, imposing disproportionate validation cost compared to a normal signature check, repeatable indefinitely at ordinary transaction cost.

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
