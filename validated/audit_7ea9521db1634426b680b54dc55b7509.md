### Title
Silent failure of `INSERT OR IGNORE` into `inputs`/`outputs` is treated as success in private payment chain saving - (File: indivisible_asset.js)

### Summary
`validateAndSavePrivatePaymentChain` in `indivisible_asset.js` saves a fully-validated private payment chain by issuing a series of `INSERT "+db.getIgnore()+" INTO inputs ...` / `INSERT "+db.getIgnore()+" INTO outputs ...` / `UPDATE outputs ...` queries and then unconditionally invokes `callbacks.ifOk()` once `async.series(arrQueries, ...)` completes, without inspecting whether each insert actually persisted a row.

### Finding Description
`async.series` in `sqlite_pool.js`/`mysql_pool.js` swallows the row-affecting result of each `INSERT ... IGNORE` unless the caller explicitly checks `result.affectedRows` (as is done correctly elsewhere, e.g. `network.js` `hub/update_correspondent_settings` at [1](#0-0) ). In `validateAndSavePrivatePaymentChain`, the queries that record spend uniqueness (`is_unique`) and outputs are built with `db.getIgnore()` and pushed via `conn.addQuery`, then executed with a bare `async.series(arrQueries, function(){ ...; callbacks.ifOk(); })`, with the callback receiving no result and doing no validation of it: [2](#0-1) 

Because `INSERT OR IGNORE` (SQLite) / `INSERT IGNORE` (MySQL) silently no-ops on any constraint violation instead of raising an error, if the target row already exists with a conflicting value (for example, an `inputs` row for the same `(unit, message_index, input_index)` already recorded with `is_unique=1` from a competing/duplicate chain, or a race in concurrent handling of the same private payment via hub and direct paths, cf. the explicit IGNORE-because-duplicate-delivery comment at [3](#0-2) ), the insert is dropped on the floor and the code still calls `callbacks.ifOk()`, exactly mirroring the `rename_tenant` pattern: a fallible persistence operation whose failure is discarded, with the caller unconditionally told "success."

This is the same "unchecked return value" bug class as the ash_postgres CVE: a DB write that can fail due to a collision with pre-existing state is not checked, and the caller (here, the wallet's private-payment acceptance flow in `private_payment.js` / `network.js handleOnlinePrivatePayment`, cf. [4](#0-3) ) proceeds to treat the chain as durably and correctly saved.

### Impact Explanation
If the uniqueness-marking insert into `inputs` is silently dropped, the private (indivisible-asset) input can fail to be correctly recorded as spent/unique in the local database while the wallet still reports the payment as accepted (`ifAccepted`/`ifOk`), and the corresponding pre-existing conflicting record (potentially belonging to a different chain/spend) is left untouched. This can lead the local node to disagree with the true state of which private coin was spent, enabling a double-spend of the same private output to go unnoticed by the local double-spend bookkeeping, or corrupting the recorded chain of a private asset transfer (funds/ownership confusion analogous to cross-tenant repointing in the original CVE).

### Likelihood Explanation
Reachable by any peer that can send a private payment chain to a wallet (asset issuer/private-payment counterparty path), including through the documented "we may receive the same unit/message_index/output_index twice" duplicate-delivery scenario, and through crafted colliding `(unit, message_index, input_index)`/`(unit, message_index, output_index)` values in a private payment chain sent to a victim wallet. No special privileges beyond normal private-payment protocol participation are required.

### Recommendation
In `validateAndSavePrivatePaymentChain`, check the result (`affectedRows`/insertId) of each `INSERT ... IGNORE` and `UPDATE` query before invoking `callbacks.ifOk()`; if an expected insert did not affect a row (i.e., a conflicting row already existed), route to `callbacks.ifError(...)` instead of silently succeeding, mirroring the affectedRows-check pattern already used in `network.js`'s `hub/update_correspondent_settings` handler.

### Proof of Concept
Not independently verified with a live run (index/tooling limits prevented executing the SQLite/MySQL test harness); the analysis is based on static code inspection. Conceptually: 1) craft two private payment chains whose final `inputs` insert targets the same `(unit, message_index, input_index)` primary key but different `is_unique`/associated output data; 2) deliver the first chain to a wallet so it commits the `inputs`/`outputs` rows; 3) deliver a second, colliding chain — the `INSERT OR IGNORE` no-ops but `validateAndSavePrivatePaymentChain` still calls `ifOk()`, causing the wallet to acknowledge acceptance of a payment whose bookkeeping row was never actually written/updated.

function validateAndSavePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	parsePrivatePaymentChain(conn, arrPrivateElements, {
		ifError: callbacks.ifError,
		ifOk: function(bAllStable){
			console.log("saving private chain "+JSON.stringify(arrPrivateElements));
			profiler.start();
			var arrQueries = [];
			for (var i=0; i<arrPrivateElements.length; i++){
				var objPrivateElement = arrPrivateElements[i];
				var payload = objPrivateElement.payload;
				var input_address = objPrivateElement.input_address;
				var input = payload.inputs[0];
				var is_unique = objPrivateElement.bStable ? 1 : null; // unstable still have chances to become nonserial therefore nonunique
				if (!input.type) // transfer
					conn.addQuery(arrQueries, 
						"INSERT "+db.getIgnore()+" INTO inputs \n\
						(unit, message_index, input_index, src_unit, src_message_index, src_output_index, asset, denomination, address, type, is_unique) \n\
						VALUES (?,?,?,?,?,?,?,?,?,'transfer',?)", 
						[objPrivateElement.unit, objPrivateElement.message_index, 0, input.unit, input.message_index, input.output_index, 
						payload.asset, payload.denomination, input_address, is_unique]);
				else if (input.type === 'issue')
					conn.addQuery(arrQueries, 
						"INSERT "+db.getIgnore()+" INTO inputs \n\
						(unit, message_index, input_index, serial_number, amount, asset, denomination, address, type, is_unique) \n\
						VALUES (?,?,?,?,?,?,?,?,'issue',?)", 
						[objPrivateElement.unit, objPrivateElement.message_index, 0, input.serial_number, input.amount, 
						payload.asset, payload.denomination, input_address, is_unique]);
				else
					throw Error("neither transfer nor issue after validation");
				var is_serial = objPrivateElement.bStable ? 1 : null; // initPrivatePaymentValidationState already checks for non-serial
				var outputs = payload.outputs;
				for (var output_index=0; output_index<outputs.length; output_index++){
					var output = outputs[output_index];
					console.log("inserting output "+JSON.stringify(output));
					conn.addQuery(arrQueries, 
						"INSERT "+db.getIgnore()+" INTO outputs \n\
						(unit, message_index, output_index, amount, output_hash, asset, denomination) \n\
						VALUES (?,?,?,?,?,?,?)",
						[objPrivateElement.unit, objPrivateElement.message_index, output_index, 
						output.amount, output.output_hash, payload.asset, payload.denomination]);
					var fields = "is_serial=?";
					var params = [is_serial];
					if (output_index === objPrivateElement.output_index){
						var is_spent = (i===0) ? 0 : 1;
						fields += ", is_spent=?, address=?, blinding=?";
						params.push(is_spent, objPrivateElement.output.address, objPrivateElement.output.blinding);
					}
					params.push(objPrivateElement.unit, objPrivateElement.message_index, output_index);
					conn.addQuery(arrQueries, "UPDATE outputs SET "+fields+" WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0", params);
				}
			}
		//	console.log("queries: "+JSON.stringify(arrQueries));
			async.series(arrQueries, function(){
				profiler.stop('save');
				callbacks.ifOk();
			});
		}
	});
}
