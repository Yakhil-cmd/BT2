### Title
Vote account `InitializeAccount` lacks authorization tied to account creation, enabling front-running/hijacking of freshly-created vote accounts - (File: programs/vote/src/vote_state/mod.rs)

### Summary
`solana_vote_program`'s `InitializeAccount` instruction (`VoteInstruction::InitializeAccount`) initializes a vote account's state but, like Uniswap's `UniswapV3Pool.initialize`, performs no check that the caller is related to whoever created or funded the account. It only requires that an attacker-supplied `node_pubkey` field sign the transaction — a key fully controlled by the caller. Any account that is `Uninitialized`, owned by the vote program, correctly sized, and rent-exempt can be initialized by anyone, including an attacker who races the legitimate owner's initialization transaction.

### Finding Description
The vote program's initialization logic is: [1](#0-0) 

```
pub fn initialize_account<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    vote_init: &VoteInit,
    signers: &HashSet<Pubkey, S>,
    clock: &Clock,
) -> Result<(), InstructionError> {
    VoteStateHandler::check_vote_account_length(vote_account, target_version)?;
    let versioned = vote_account.get_state::<VoteStateVersions>()?;

    if !versioned.is_uninitialized() {
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    // node must agree to accept this vote account
    verify_authorized_signer(&vote_init.node_pubkey, signers)?;

    VoteStateHandler::init_vote_account_state(vote_account, vote_init, clock, target_version)
}
```

The only authorization gate is `verify_authorized_signer(&vote_init.node_pubkey, signers)`, and `vote_init.node_pubkey`, `vote_init.authorized_voter`, and `vote_init.authorized_withdrawer` are all attacker-supplied instruction data — the attacker can set `node_pubkey` to their own keypair and sign with it trivially. There is no requirement that the vote account itself, the account's creator, or the account's original funder co-sign or otherwise be validated.

Vote account creation and initialization are typically issued as two separate `SystemProgram::CreateAccount` + `VoteInstruction::InitializeAccount` instructions, as seen in the CLI/test helper: [2](#0-1) 

Because `CreateAccount` and `InitializeAccount` are logically separate steps, an attacker monitoring the ledger for a freshly created, uninitialized, vote-program-owned, rent-exempt account (the pubkey and its funded lamports become publicly visible the instant `CreateAccount` lands) can submit their own `InitializeAccount` transaction naming themselves as `node_pubkey`/`authorized_voter`/`authorized_withdrawer` before the legitimate owner's `InitializeAccount` transaction is processed. The dispatch path confirms no additional owner/funder check is performed before calling into `vote_state::initialize_account`: [3](#0-2) 

This mirrors the Uniswap bug exactly: `initialize` is unauthenticated relative to the entity that deployed/funded the account, so whoever lands the initializing transaction first sets the account's controlling authorities.

### Impact Explanation
Once an attacker wins the race, `authorized_withdrawer` is set to a key the attacker controls. The vote account is pre-funded with lamports (for rent exemption and, historically, initial balance/stake wiring) supplied by the legitimate operator during `CreateAccount`. With `authorized_withdrawer` compromised, the attacker can subsequently invoke the vote program's withdraw path to move those lamports out, and can also set `authorized_voter` to their own key, allowing them to impersonate the intended validator's voting identity for that vote account address. This is a concrete "drain the initial depositor's funds" outcome analogous to the LP-draining scenario in the report, and it also creates a griefing/DoS vector since the rightful owner's subsequent `InitializeAccount` call will fail with `AccountAlreadyInitialized`, permanently losing the address and its funding.

### Likelihood Explanation
Exploitation only requires observing public ledger state (the `CreateAccount` transaction and resulting account) and submitting an ordinary signed transaction with attacker-chosen `VoteInit` fields — no elevated privileges, special hardware, or protocol-level access are needed. The primary constraint is winning the race between the `CreateAccount` confirmation and the legitimate `InitializeAccount` transaction; this is realistic whenever the two instructions are not submitted atomically in the same transaction/message (e.g., split across separate RPC calls, scripts, or when compute-budget/nonce instructions are inserted between them).

### Recommendation
- Require that the vote account itself (or a signer chosen at `CreateAccount` time, such as the funder) co-sign `InitializeAccount`, rather than trusting an attacker-supplied `node_pubkey`.
- Alternatively, bind vote account initialization data (authorized voter/withdrawer, node identity) at account-creation time in a single atomic instruction so no unauthenticated window exists between creation and initialization, mirroring the "move price operations into the constructor" recommendation from the original report.
- At minimum, document the requirement that `CreateAccount` and `InitializeAccount` must be submitted as a single atomic transaction, and add client-side/CLI enforcement of this invariant.

### Proof of Concept
1. Legitimate operator broadcasts `SystemInstruction::CreateAccount` funding a new pubkey `V` with lamports, owned by the vote program, sized for `VoteStateV4`, in one transaction.
2. Attacker observes `V` on-chain immediately after confirmation (before the operator's second transaction, `VoteInstruction::InitializeAccount`, lands).
3. Attacker submits `VoteInstruction::InitializeAccount(VoteInit { node_pubkey: attacker_key, authorized_voter: attacker_key, authorized_withdrawer: attacker_key, commission: 0 })` naming account `V`, signed solely by `attacker_key` (which the attacker freshly generates and signs with, satisfying `verify_authorized_signer`) — reference dispatch and check logic at [3](#0-2)  and [1](#0-0) .
4. If this transaction lands first, `V`'s state becomes `Initialized` with attacker-controlled authorities; the legitimate operator's subsequent `InitializeAccount` call fails with `AccountAlreadyInitialized`, and the attacker now controls withdrawal/voting rights over the pre-funded account `V`.

Note: I was unable to retrieve and fully verify the vote program's `Withdraw` instruction implementation within the available tool budget to confirm the exact lamport-draining mechanics once `authorized_withdrawer` is hijacked; this final withdrawal step should be verified directly in `programs/vote/src/vote_processor.rs` (the `Withdraw`/`fn withdraw` handlers) before treating fund drainage as fully proven end-to-end.
