### Title
Webhook signature verification uses an attacker-controlled organization field that is decoupled from the repository the event actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate a payload against using a field read from the *same, unverified* JSON body that is about to be processed. Every webhook handler then resolves the repository/stack to act on using a *different* field (`repository.full_name`) from that same body. Because GitHub's HMAC signature only proves the payload was signed by *some* configured organization's secret — not that the org named in `repository.owner.login` matches the org actually targeted by `repository.full_name` — an attacker who controls (or knows the webhook secret of) any one organization registered in a multi-tenant Shipit instance can forge webhook events that act on stacks belonging to a completely different organization/repository.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to look up the verification secret directly from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` then HMAC-verifies the raw payload against **that** organization's secret only: [3](#0-2) 

Once the signature check passes, every handler (`Handler#stacks`) resolves which `Stack`/`Repository` to operate on using a **different** payload field, `repository.full_name`, with no cross-check against the org used for verification: [4](#0-3) 

Concrete handlers use this to mutate state for whichever repository `full_name` names:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for stacks matched by `full_name`: [5](#0-4) 
- `StatusHandler#process` writes a commit status onto **any** `Commit` in the entire instance matching a `sha`, without any repository/stack scoping at all: [6](#0-5) 
- `CheckSuiteHandler#process` schedules check-run refreshes for stacks matched by `full_name`/branch/sha: [7](#0-6) 

**Binding broken:** `organization that authenticated the request` (`params.dig('repository','owner','login')`, used to select the HMAC secret) `≠` `repository that is written` (`params.dig('repository','full_name')`, used by every handler to select the `Stack`/`Commit` acted upon).

Before the attacker's request: an org's webhook secret only authorizes actions on that org's own repositories, because on genuine GitHub payloads `repository.owner.login` and `repository.full_name` always agree.
After the attacker's request: an attacker who knows/controls the webhook secret for `OrgA` (any organization configured in this Shipit instance's `github:` block) crafts a JSON body with `repository.owner.login = "OrgA"` (so `verify_webhook_signature` succeeds using `OrgA`'s secret) but `repository.full_name = "OrgB/victim-repo"`, `ref`, `after`, or `sha` values of their choosing. The handler layer never re-checks the organization and acts on `OrgB`'s stacks/commits.

### Impact Explanation
This lets a party who is a legitimate, low-privilege webhook sender for one tenant organization forge cross-organization/cross-repository GitHub events for any other tenant hosted on the same Shipit instance:
- Force `sync_github` with an attacker-chosen `expected_head_sha` against another organization's stacks (`PushHandler`).
- Write forged commit statuses onto matching commit SHAs anywhere in the database, since `StatusHandler` scopes only by `sha`, not by repository (`Commit.where(sha: params.sha)`), which can affect status/CI-gated logic downstream of `Commit#create_status_from_github!`.
- Trigger check-run refresh scheduling on other organizations' stacks (`CheckSuiteHandler`).

Because commit status/state feeds into deploy-gating logic elsewhere in the engine, this creates a path toward unauthorized state changes on stacks the attacker has no legitimate access to, satisfying the "cross-repository writes" / "unauthorized deploy" class of High/Critical impact called out by the rules. I was not able to fully trace `Commit#create_status_from_github!` and the CI-gating consumer of commit status within the available context, so I cannot confirm the exact downstream deploy-blocking bypass chain with certainty — this should be verified against `app/models/shipit/commit.rb` and the deploy-safety check code before treating the CI-bypass angle as proven, but the cross-tenant write itself is fully confirmed from the cited code.

### Likelihood Explanation
Requires the attacker to control or know the webhook secret (or exploit an org configured with a blank `webhook_secret`, which `verify_webhook_signature` accepts unconditionally — see `return true unless webhook_secret` at [8](#0-7) ) for **any one** organization registered on the shared Shipit instance — realistic in multi-tenant deployments where multiple GitHub orgs/apps are configured (`config/secrets.development.shopify.yml` shows this exact multi-org shape: `somegithuborg`, `someothergithuborg`). No Shipit session, `ApiClient` token, or repository write access to the victim org is required — only a crafted HTTP POST to `/github/webhooks` with a signature valid for the attacker's own org.

### Recommendation
Cross-validate the organization/owner used for signature verification against the actual repository being mutated inside each handler (e.g., verify `repository.full_name.split('/').first == repository_owner` before processing), or scope every handler lookup (`Handler#stacks`, `StatusHandler#process`) by both the verified organization and `full_name`, not `full_name` alone. Additionally, `StatusHandler` should scope `Commit` lookups by the resolved stack/repository rather than a bare `sha` match.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `github.orgX.webhook_secret` (multi-tenant setup as documented in `docs/setup.md`).
2. Attacker has legitimate access to `orgA`'s webhook secret (e.g., they administer an app installation on `orgA`).
3. Attacker POSTs to the webhooks endpoint with `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
   signed with `X-Hub-Signature` computed using `orgA`'s `webhook_secret`.
4. `verify_signature` resolves `repository_owner` to `"orgA"` [2](#0-1)  and successfully verifies against `orgA`'s secret [3](#0-2) .
5. `PushHandler#process` resolves stacks via `payload.dig('repository','full_name')` = `"orgB/victim-repo"` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack [5](#0-4) , despite the attacker never having proven any relationship to `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
