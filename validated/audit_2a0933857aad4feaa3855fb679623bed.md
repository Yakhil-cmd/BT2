### Title
Block-revenue delegator rewards become permanently stranded in a vote account when it has zero delegated stake in the rewarded epoch - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Under SIMD-0123 block revenue sharing, transaction-fee revenue destined for delegators accumulates in a vote account's `pending_delegator_rewards` field every slot the vote account's identity is leader. This pot is only ever paid out proportionally to stake accounts delegated to that vote account at the end of an epoch, using the vote account's total active delegated stake as the denominator. If that denominator is zero, the entire pot is skipped and, because nothing in the codebase ever decrements `pending_delegator_rewards`, the funds remain stuck inside the vote account indefinitely, unable to be paid to stakers and blocked from withdrawal by the vote account's authorized withdrawer.

### Finding Description
Fees are deposited into a vote account's `pending_delegator_rewards` field via `deposit_delegator_fees`/`deposit_or_burn_fee` whenever `block_revenue_sharing` is active and the vote account's node is the block's leader: [1](#0-0) 

At the epoch boundary, `calculate_block_reward` is the sole mechanism that reads and pays out this pot. It computes each stake delegation's share as `pending_delegator_rewards * stake / total_active_stake`, where `total_active_stake` is looked up from the reward epoch's `delegated_stakes` map for that vote account: [2](#0-1) 

If `total_active_stake == 0` — i.e., the vote account had no delegated stake recorded for the rewarded epoch (all delegations deactivated, none yet activated, or the entry is simply absent from the map) — the function unconditionally returns `0` for every stake delegation, meaning none of the accumulated `pending_delegator_rewards` is distributed that epoch: [3](#0-2) 

Critically, a repo-wide search shows `pending_delegator_rewards` is only ever *read* in the reward-calculation path (`calculation.rs`) and only ever *incremented* via `add_pending_delegator_rewards` when new fees are deposited. There is no code path anywhere in the codebase that decrements or clears `pending_delegator_rewards` after (or in lieu of) a block-reward distribution. This means once the denominator hits zero for an epoch, the previously (and any subsequently) accrued delegator-fee lamports have no route back to stakers: the vote account keeps accumulating `pending_delegator_rewards` from every future leader slot, but it is never redistributed unless/until the vote account regains delegated stake, at which point only the *current* balance is used as the numerator against the *current* stake denominator — there is no retroactive accounting for the period stake was zero, so past periods' rewards are permanently forfeited from stakers' perspective.

Compounding this, the validator itself cannot claim these stranded lamports either: `withdraw()` explicitly disallows closing the vote account or draining its balance below `rent_exempt_minimum + pending_delegator_rewards`: [4](#0-3) 

This is a direct structural analog of the `InfraredVault`/`MultiRewards` bug: a rewards pot accrues over time, distribution is denominated by a "stakers" quantity, and when that denominator is zero, the accrued rewards for that period become permanently unclaimable by anyone, with no governance/administrative fallback to reclaim or redirect them.

### Impact Explanation
Delegator-fee lamports (previously collected by the network from real transaction fees, i.e. real value, not synthetic inflation) become permanently locked lamports that no one — not stakers, not the validator/authorized withdrawer — can ever retrieve. This is a genuine loss/stranding of value for the affected vote account's future delegators and represents an accounting dead-end in the stake/reward system. The magnitude scales with how much block-revenue-sharing fee volume the affected leader processes while its delegated stake is (or drops to) zero, which is directly a function of real transaction fee traffic through that leader.

### Likelihood Explanation
Requires: (1) `block_revenue_sharing` feature active (SIMD-0123), and (2) a vote account acting as leader (per the leader schedule computed from a prior epoch's stake) while having zero currently-effective delegated stake in the `reward_epoch_delegated_stakes` snapshot used for the *current* rewarded epoch — e.g., because all delegators fully deactivated their stake, or the vote account's entry is simply missing from the map. Because the leader schedule for an epoch is fixed one epoch in advance from a stake snapshot, and stake can fully deactivate within that lag window, this scenario is reachable without any privileged or malicious action — it can occur through ordinary, unprivileged stake deactivation transactions from a vote account's delegators.

### Recommendation
- Track any `pending_delegator_rewards` amount that fails to be distributed due to a zero-stake denominator (or partial distribution) and either roll it forward correctly for the next epoch's calculation, or provide an explicit governance/administrative path (e.g. an instruction gated by the vote account's authorized withdrawer) to reclaim/redirect stranded `pending_delegator_rewards` when there is no delegated stake to receive them.
- Alternatively, when `total_active_stake == 0`, redirect the pot to the validator identity/collector rather than silently returning `0` and leaving the lamports permanently locked behind the `withdraw()` guard.

### Proof of Concept
Conceptual reproduction path (bank/runtime-level, not requiring privileged access):
1. Enable `block_revenue_sharing` (SIMD-0123) and `custom_commission_collector` features.
2. Create vote account `V` with delegated stake from stake account `S`; have `V`'s node act as leader for one or more slots so that transaction fees flow through `deposit_or_burn_fee` → `deposit_delegator_fees` → `add_pending_delegator_rewards`, growing `V.pending_delegator_rewards` to a nonzero value (`fee_distribution.rs:142-207`, `vote_state/mod.rs:940-993`).
3. Fully deactivate `S`'s stake from `V` (an ordinary `Deactivate`/`Withdraw` stake-program transaction) such that, by the time the reward epoch's `RewardEpochDelegatedStakes` snapshot is taken, `V` has `total_active_stake == 0` in `delegated_stakes` (`calculation.rs:204-208`).
4. At the epoch boundary, `calculate_block_reward` returns `0` for all (now-nonexistent) delegations to `V`; `V.pending_delegator_rewards` is left untouched (no decrement anywhere in the codebase).
5. Attempt to `withdraw()` the full balance of `V`: it fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0` (`vote_state/mod.rs:1089-1126`).
6. Re-delegate new stake to `V` in a later epoch: `calculate_block_reward` will use `V`'s *current* `pending_delegator_rewards` against the *current* stake, but there is no accounting that recovers or attributes the specific lamports that were stranded during the zero-stake period to the correct historical stakers — those fees are effectively lost to the system's intended distribution semantics, with the validator also permanently unable to claim them via `withdraw()`.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation.stake_v2(
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
