### Title
Cross-org webhook can delete another organization's Team `Membership` because `MembershipHandler` never checks `team.organization == params.organization.login` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves the `Team` purely by `params.team.id` (the numeric GitHub team ID) via `find_or_create_team!`, and then unconditionally applies `add_member`/`team.members.delete(member)` to whatever `Team` row that ID resolves to [1](#0-0) . In a multi-org deployment, the webhook signature is verified against the secret of the org named in the payload's own `organization.login` field [2](#0-1) [3](#0-2) , but nothing thereafter confirms that this authenticating org actually owns the `Team` referenced by `team.id`. An attacker who legitimately controls a second org configured in Shipit (`attacker-org`) can send a validly-signed `membership`/`action:removed` webhook naming a real, privileged `Team`'s `github_id` belonging to a different org, silently deleting a legitimate member's `Membership` row.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`signing_org` (the org whose `webhook_secret` produced a valid HMAC, i.e. `repository_owner` used in `Shipit.github(organization: repository_owner)`) **should equal** `team.organization` (the org that actually owns the `Team` row being mutated by `team.members.delete(member)`).

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from the payload itself: for a `membership` event there is no `repository` key, so it falls back to `params.dig('organization', 'login')` [3](#0-2) . It then fetches the GitHub App/secret for that org and verifies the HMAC against the raw body [2](#0-1) . This correctly proves the body was signed by the org literally named in `organization.login` (e.g. `attacker-org`, which the attacker legitimately administers) — it does **not** and cannot prove anything about `team.id`'s true owning org.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [4](#0-3) . For an **existing** Team row (the victim's privileged team), the block that sets `team.organization = params.organization.login` never runs — `find_or_create_by!` only executes the block on creation — so the lookup is a bare `github_id` match with zero cross-checking against `params.organization.login`.
3. `process` then does `team.members.delete(member)` for `action == 'removed'` [5](#0-4) , deleting the `Membership` row regardless of which org authenticated the request.

Exploit flow: attacker administers `attacker-org`, a second organization already configured in Shipit's multi-org `secrets.yml` (and thus possesses that org's genuine `webhook_secret`, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section). Attacker crafts a JSON body: `{"action":"removed","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"legit-victim-member"}}`, computes the correct `X-Hub-Signature` using `attacker-org`'s own secret, and POSTs it to `/webhooks` with `X-Github-Event: membership`. `verify_signature` succeeds (attacker-org's secret matches attacker-org's own signature) [2](#0-1) , `drop_unhandled_event`/`check_if_ping` pass since `membership` is a handled event, and `MembershipHandler#process` deletes the victim's `Membership` row from the privileged team owned by a completely different organization [1](#0-0) .

None of the existing guards stop this: `verify_signature` only binds the payload to the org named inside the payload, not to the `team.id` field; `drop_unhandled_event` only checks the event type exists a handler; the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not organization ownership [6](#0-5) ; and `find_or_create_team!` has no ownership check at all.

### Impact Explanation
A webhook that genuinely authenticates only for `attacker-org` mutates a `Team`/`Membership` record belonging to a different, unrelated organization — this is explicitly one of the listed Critical categories ("a payload for one repository/organization mutating another's stack, commit, task or team"). Concretely, it revokes a legitimate operator's authorization by deleting their `Membership` row in a privileged `Team`, which is used for Shipit's access-control (`User#authorized?`/`Shipit.github_teams`-style checks depend on team membership). The attack is repeatable against any `github_id` the attacker can learn (team IDs are enumerable via GitHub's team APIs by members of the target org, or observable through prior interactions) and is not limited to a single team — every request can target a different `team.id`, silently deleting arbitrary cross-org memberships.

### Likelihood Explanation
Requires: (a) Shipit configured in multi-org mode with the attacker legitimately controlling at least one of the configured orgs (and thus its real `webhook_secret`) — this is the same precondition as the prior "cross-org signed webhook" finding; (b) the attacker knowing/guessing the victim's privileged `Team`'s numeric GitHub `github_id`, which is discoverable via GitHub's team APIs or UI if the attacker has any visibility into the target org (or via brute-force enumeration since team IDs are small sequential integers). No Shipit session, API token, or secret belonging to the victim org is needed. Given a valid `attacker-org` webhook secret, forging the request is a single signed HTTP POST — trivially repeatable.

### Recommendation
In `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!`, after resolving the `Team` by `github_id`, verify that `team.organization == params.organization.login` (case-insensitively) and raise/drop the event if they don't match, so a webhook can only mutate teams belonging to the org that actually signed it. Additionally, do not allow `team.organization` to be silently reassigned/ignored on lookup; treat an organization mismatch on an existing `github_id` as an error condition to be logged and rejected rather than silently proceeding to mutate membership.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition, multi-org secrets fixture)
test "membership 'removed' from org A cannot delete membership of a team owned by org B" do
  victim_team = shipit_teams(:reviewers) # belongs to org "org-b", github_id: 999
  victim_member = shipit_users(:walrus)
  Membership.create!(team: victim_team, user: victim_member)

  # Binding under test (BEFORE):
  assert Membership.exists?(team: victim_team, user: victim_member)
  assert victim_member.authorized? # true before attack

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'removed',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'x' },
    organization: { login: 'org-a' }, # attacker's own org
    member: { login: victim_member.login }
  }.to_json
  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', org_a_real_secret, payload)}"
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { Membership.count }, -1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  # Binding under test (AFTER) — should have stayed true, is now false:
  refute Membership.exists?(team: victim_team, user: victim_member)
  refute victim_member.reload.authorized?
end
```
This demonstrates that a request cryptographically authenticated only for `org-a` mutates a `Membership` row scoped to `org-b`'s `Team`, violating the `signing_org == team.organization` binding.
