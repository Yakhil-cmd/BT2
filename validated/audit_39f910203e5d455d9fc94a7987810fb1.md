### Title
Cross-stack disclosure via unscoped `stack` override in CCMenu API - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the shared `#stack` helper to resolve `params[:stack_id]` against **all** stacks instead of the token-scoped `stacks` collection used by `Api::BaseController`. As a result, any valid API token (even one minted for a single stack) can be replayed against any other `stack_id` to read that stack's CCMenu build status.

### Finding Description
The intended binding is: `stack ∈ current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, i.e. the resolved `stack` must belong to the set the token is scoped to. This is exactly what `Api::BaseController#stacks`/`#stack` implement: [1](#0-0) .

`Api::CCMenuController` however redefines `#stack` to bypass that scoping and go straight to the global model, and also redefines `#authenticate_api_client` to accept a bare `params[:token]` without applying any stack restriction: [2](#0-1) .

`ApiClient#check_permissions!`, used by `require_permission :read, :stack`, only checks membership in the `permissions` array (e.g. `"read:stack"`); it never checks `stack_id` at all: [3](#0-2) . So for CCMenu, the only enforcement of "this token may see this specific stack" is the `#stack` method's scoping — and that scoping is exactly what's dropped here.

Exploit flow: an operator issues an `ApiClient` scoped to stack A (`stack_id` set, `permissions` includes `read:stack`) and shares the CCMenu URL `GET /api/stacks/owner/repoA/env/ccmenu?token=<T>`. An attacker who observes/guesses another stack's slug (`owner/repoB/env`, which is not secret — it's a URL path) requests `GET /api/stacks/owner/repoB/env/ccmenu?token=<T>` with the same token. `authenticate_api_client` verifies the token and succeeds (token is valid), `#stack` resolves `Stack.from_param!("owner/repoB/env")` with no scoping check, and `#show` renders stack B's `deploys_and_rollbacks.last` (build status, `lastBuildLabel`, `webUrl`) in the CCMenu XML.

None of the existing guards catch this: `require_permission!` only checks the permission string, not `stack_id`; `authenticate_api_client` here only validates the signature of the token, not scope; and the sibling controllers (`commits`, `deploys`, `tasks`) are safe because they inherit `Api::BaseController#stack`, which does apply the `stacks` scoping — CCMenu is the outlier that reimplements both methods and drops the check.

### Impact Explanation
An attacker holding one legitimately-scoped token can read build/deploy status (success/failure, last build label, web URL) for arbitrary other stacks in the same Shipit instance, not just the one the token was issued for. This is an unauthenticated-for-that-resource read of stack state, matching the High category ("escalation ... unauthenticated read of stack state, task streams or deploy output"). It does not directly expose secrets or allow writes, but it breaks per-stack tenant isolation for any stack whose `stack_id` slug can be guessed/observed, and is repeatable against every stack in the instance with a single valid token.

### Likelihood Explanation
Preconditions: attacker must possess any valid `ApiClient` token with `read:stack` permission scoped to some stack (these tokens are often distributed for CI/CCTray-style status badges, so leakage/observation is plausible) and must know or guess another stack's `owner/repo/environment` slug (these are derivable from GitHub repo names and are not treated as secret). No GitHub credentials, session, or webhook secret are needed. This is low-cost and fully repeatable — a single GET request per target stack.

### Recommendation
Remove the `#stack` and `#authenticate_api_client` overrides in `Api::CCMenuController` and rely on `Api::BaseController`'s scoped `stacks`/`stack` (and its standard `authenticate_api_client`), or explicitly enforce `stacks.from_param!(params[:stack_id])` scoping in the override. If a query-string `token` param is required (browsers embedding the URL in CCTray clients can't do Basic Auth), extend `Api::BaseController#authenticate_api_client` to also accept `params[:token]` rather than duplicating and de-scoping the logic in the subclass.

### Proof of Concept
```ruby
# test/controllers/shipit/api/ccmenu_controller_test.rb
test "#show does not leak status of a stack outside the token's scope" do
  stack_a = shipit_stacks(:shipit)
  stack_b = create(:stack, repository: create(:repository, owner: 'other', name: 'other-repo'))

  api_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'ccmenu-a',
    stack_id: stack_a.id,
    permissions: ['read:stack'],
  )
  token = api_client.authentication_token

  get "/api/stacks/#{stack_b.repository.owner}/#{stack_b.repository.name}/#{stack_b.environment}/ccmenu",
      params: { token: token }

  # Binding under test: stack_b must NOT be in
  # (current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all)
  # i.e. stack_b.id != api_client.stack_id, so the request must be rejected.
  assert_response :not_found # or :forbidden, currently returns :ok with stack_b's XML
end
```
