### Title
Staking Reward Overwrite via Map Assignment When `CLPoolAddr` Collides With `RewardAddr` in `assignStakingRewards`/`assignStakingRewardsFlex` — (File: `kaiax/reward/impl/getter.go`)

---

### Summary

In `assignStakingRewards` and `assignStakingRewardsFlex`, the `alloc` map is populated using direct assignment (`=`) rather than accumulation. When a validator's `CLPoolAddr` (from CLRegistry) equals any `RewardAddr` in the AddressBook — either the same validator's own reward address or another validator's — the second assignment silently overwrites the first. The `remaining` counter is still reduced by the full `reward = cnAmount + clAmount`, so the overwritten `cnAmount` is neither distributed to the validator nor returned to the proposer. It is permanently lost from the block reward distribution.

---

### Finding Description

In `assignStakingRewards` (Prague + Kore path):

```go
// kaiax/reward/impl/getter.go lines 521-525
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount                    // assignment, not +=
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount      // assignment, not +=
``` [1](#0-0) 

And identically in `assignStakingRewardsFlex`:

```go
// kaiax/reward/impl/getter.go lines 474-477
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
``` [2](#0-1) 

Both use `=` (overwrite). `ConsolidatedNodes()` guarantees unique `RewardAddr` per entry, so `alloc[cn.RewardAddr] = cnAmount` is safe in isolation. However, `alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount` is **not** guarded against colliding with any existing key in `alloc`.

**Collision scenario A — same CN:** If `cn.CLStakingInfo.CLPoolAddr == cn.RewardAddr`:
1. `alloc[addr] = cnAmount` (first write)
2. `alloc[addr] = clAmount` (second write, overwrites!)
3. `remaining -= reward` (still subtracts `cnAmount + clAmount`)

`cnAmount` is gone from `alloc` and gone from `remaining`. It is permanently lost.

**Collision scenario B — cross-CN:** If `cn1.CLStakingInfo.CLPoolAddr == cn2.RewardAddr`:
1. `alloc[addr] = cn2Amount` (written for CN2)
2. `alloc[addr] = cn1.clAmount` (written for CN1's CL, overwrites CN2's reward!)

CN2's staking reward is silently replaced by CN1's CL split amount.

The `alloc` map is consumed by the caller via `spec.IncRecipient`:

```go
// kaiax/reward/impl/getter.go lines 363-365
for addr, amount := range stakersAlloc {
    spec.IncRecipient(addr, amount)
}
``` [3](#0-2) 

`IncRecipient` correctly accumulates, but it only sees the overwritten value. The lost `cnAmount` never reaches `spec.Rewards` and is never added to any balance in `FinalizeState`:

```go
// kaiax/reward/impl/blockstate.go lines 53-55
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
``` [4](#0-3) 

The `RewardSpec.Validate()` only checks for negative amounts — it does not verify that the sum of `spec.Rewards` equals `Minted + TotalFee - BurntFee`, so the loss passes silently. [5](#0-4) 

The `CLPoolAddr` and `RewardAddr` come from two separate contracts (CLRegistry and AddressBook) with no cross-validation anywhere in the staking info parsing path: [6](#0-5) 

---

### Impact Explanation

- Per-block KAIA reward loss: `cnAmount` kei is permanently destroyed — neither credited to the validator nor returned to the proposer.
- In scenario B, CN2's entire staking reward is replaced by an unrelated CL split amount, causing both incorrect over-payment to CN2's address (CN1's `clAmount`) and loss of CN2's correct reward.
- This is an unauthorized alteration of reward distribution affecting KAIA balances, triggered every block for as long as the collision exists in the staking info.

---

### Likelihood Explanation

- Requires `CLPoolAddr == RewardAddr` for some pair of entries across CLRegistry and AddressBook.
- CLRegistry and AddressBook are separate contracts; no on-chain or off-chain validation cross-checks them.
- A CL pool operator (semi-trusted, not a privileged admin) registers their pool address in CLRegistry. If they set `CLPoolAddr` to equal any validator's `RewardAddr`, the bug fires every block.
- The code comment at line 156 of `staking_info.go` states "One CLStakingInfo per validator is guaranteed by CLRegistry" but makes no claim about `CLPoolAddr` being disjoint from `RewardAddr` values. [7](#0-6) 

---

### Recommendation

Replace direct assignment with accumulation in both `assignStakingRewards` and `assignStakingRewardsFlex`:

```go
// Instead of:
alloc[cn.RewardAddr] = cnAmount
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount

// Use:
if alloc[cn.RewardAddr] == nil {
    alloc[cn.RewardAddr] = new(big.Int)
}
alloc[cn.RewardAddr].Add(alloc[cn.RewardAddr], cnAmount)

if alloc[cn.CLStakingInfo.CLPoolAddr] == nil {
    alloc[cn.CLStakingInfo.CLPoolAddr] = new(big.Int)
}
alloc[cn.CLStakingInfo.CLPoolAddr].Add(alloc[cn.CLStakingInfo.CLPoolAddr], clAmount)
```

Additionally, add a validation step in `consolidateNodes` or `parseCallResult`/`parsePermissionlessCallResult` that rejects any `CLPoolAddr` that matches an existing `RewardAddr`.

---

### Proof of Concept

**Setup (scenario A — self-collision):**
- Validator V: `NodeId = 0xA01`, `RewardAddr = 0xC01`, `StakingAmount = 6_000_000` (above `minStake = 5_000_000`)
- CL pool for V: `CLNodeId = 0xA01`, `CLPoolAddr = 0xC01` (same as `RewardAddr`), `CLStakingAmount = 1_000_000`

**Execution in `assignStakingRewards` (Prague, Kore):**
1. `cn.StakingAmount = 6_000_000 >= minStake` → eligible
2. `cnTotalStakingAmount = 6_000_000 + 1_000_000 = 7_000_000`
3. `excess = 7_000_000 - 5_000_000 = 2_000_000`
4. `reward = 2_000_000 * stakersReward / totalExcess`
5. `cn.Split(reward)` → `cnAmount = reward * 6/7`, `clAmount = reward * 1/7`
6. `alloc[0xC01] = cnAmount` ← first write
7. `alloc[0xC01] = clAmount` ← **overwrites**, `cnAmount` is lost
8. `remaining -= reward` ← full reward subtracted, but only `clAmount` is in `alloc`

**Result:** V receives `clAmount` (≈ `reward/7`) instead of `reward`. The difference `cnAmount` (≈ `6*reward/7`) is permanently lost from the block reward. `FinalizeState` calls `state.AddBalance(0xC01, clAmount)` — the validator is underpaid by `cnAmount` kei every block.
