Based on the investigation, the closest ocore analog to the FreeRDP `TrioParse` bug class ("logging might bypass string length checks due to an integer overflow") is a precision-loss bypass in `string_utils.js`'s numeric string parsing helpers, which is directly reachable from oscript/AA formula evaluation.

### Title
Silent floating-point precision loss bypasses numeric string length/precision validation in `toNumber`/formula string coercion - (File: string_utils.js)

### Summary
`string_utils.toNumber()` enforces a significant-digit/mantissa length check only in the "limited precision" branch (pre-`aa2UpgradeMci`, via `getNumericFeedValue`), which explicitly rejects numeric strings whose mantissa is longer than 15 characters. In the non-limited-precision branch (post-`aa2UpgradeMci`, the code path used by all current oscript/AA evaluation), that same length/precision check is absent, so an over-long numeric string is passed straight to `parseFloat` and silently rounded to the nearest IEEE-754 double instead of being rejected.

### Finding Description
`toNumber` chooses between two code paths based on `bLimitedPrecision`: [1](#0-0) 

The limited-precision path (`getNumericFeedValue`) validates the mantissa length and rejects (`return null`) any numeric string whose significant-digit count exceeds internal limits: [2](#0-1) 

But the modern, unlimited-precision path used from `aa2UpgradeMci` onward performs no such length/precision check — it only verifies the string matches a numeric regex and that `parseFloat` produced a finite value, then returns the (possibly precision-truncated) float directly: [3](#0-2) 

This is confirmed by the existing unit tests, which explicitly document that oversized integer strings are silently rounded rather than rejected in the modern path: [4](#0-3) 

This function is invoked throughout `formula/evaluation.js` whenever oscript coerces an attacker/trigger-controlled string into a number (e.g., in `substring`, `split` limit, and other numeric contexts) for units at or after `aa2UpgradeMci`: [5](#0-4) [6](#0-5) 

Any AA trigger sender can place an arbitrarily long numeric-looking string (e.g. `"12345678901234567"`, `bAA` trigger data or unit payload) into a formula input. Instead of being rejected as an invalid/too-precise number (the behavior guaranteed in the legacy limited-precision branch and implicitly assumed by string length/complexity checks elsewhere in the codebase, e.g. `MAX_DATA_FEED_VALUE_LENGTH`/`MAX_AA_STRING_LENGTH` checks that only bound string *length*, not numeric *precision*), the value is silently rounded to a different, attacker-uncontrolled-but-deterministic double. Any AA logic that treats such a value as exact (thresholds, balances, comparisons, multipliers) will silently compute with a wrong number without any error being raised.

### Impact Explanation
If an Autonomous Agent's oscript logic uses `toNumber`-coerced strings in payout/threshold calculations (a common oscript pattern, since AA definitions frequently parse `trigger.data` fields that may be strings), the silent rounding can cause the AA to compute and pay out an amount different from what the AA author intended, or make branching/comparisons succeed or fail unexpectedly. This can lead to AA fund loss or unintended state transitions, since the discrepancy is silent (no validation error is thrown, unlike the legacy branch which explicitly returns `null` and forces the caller to treat the value as a non-numeric string).

### Likelihood Explanation
Likelihood is moderate: exploitation requires a specific AA design that treats attacker-supplied numeric strings with more than ~15 significant digits as exact numeric values without independent bounds validation. It does not by itself break core consensus validation (data feed length caps such as `MAX_DATA_FEED_VALUE_LENGTH = 64` still limit the string, and `MAX_CAP = 9e15` limits amounts), but any AA relying on `toNumber`/formula numeric coercion of long attacker-controlled numeric strings is exposed without any warning, and the divergent behavior between the two `toNumber` branches (silent rounding vs. explicit rejection) is itself a latent correctness bug that any Devin engineer should be aware could produce inconsistent results across different MCI eras.

### Recommendation
Apply the same significant-digit/precision bound used by `getNumericFeedValue` (or an explicit bound tied to `Number.MAX_SAFE_INTEGER`/double precision, e.g. reject mantissas over 15–17 significant digits) in the non-limited-precision branch of `toNumber`, so that oversized numeric strings are consistently rejected (`return null`) rather than silently rounded, in both branches used across all MCI eras.

### Proof of Concept
```js
const string_utils = require('./string_utils.js');
// Limited precision path (pre-aa2UpgradeMci): correctly rejects
console.log(string_utils.toNumber('12345678901234567', true)); // null

// Unlimited precision path (post-aa2UpgradeMci, used by current formula evaluation):
console.log(string_utils.toNumber('12345678901234567')); // 12345678901234568 (silently rounded, no rejection)
```
Feeding such a string as trigger data / oscript literal into an AA that performs arithmetic with the coerced number (via `substring`'s length argument, or any place in `formula/evaluation.js` that calls `string_utils.toNumber` on a string) yields a silently wrong numeric value instead of a rejected/erroring computation.

```javascript
	if (typeof value === 'number')
```

```javascript
function getNumericFeedValue(value, bBySignificantDigits){
	if (typeof value !== 'string')
		throw Error("getNumericFeedValue of not a string: "+value);
	var m = value.match(/^[+-]?(\d+(\.\d+)?)([eE][+-]?(\d+))?$/);
	if (!m)
		return null;
	var f = parseFloat(value);
	if (!isFinite(f))
		return null;
	var mantissa = m[1];
	var abs_exp = m[4];
	if (f === 0 && mantissa > 0 && abs_exp > 0) // too small number out of range such as 1.23e-700
		return null;
	if (bBySignificantDigits) {
		var significant_digits = mantissa.replace(/^0+/, '');
		if (significant_digits.indexOf('.') >= 0)
			significant_digits = significant_digits.replace(/0+$/, '').replace('.', '');
		if (significant_digits.length > 16)
			return null;
	}
	else {
		// mantissa can also be 123.456, 00.123, 1.2300000000, 123000000000, anyway too long number indicates we want to keep it as a string
		if (mantissa.length > 15) // including the point (if any), including 0. in 0.123
			return null;
	}
	return f === 0 ? 0 : f; // replace -0
}
```
