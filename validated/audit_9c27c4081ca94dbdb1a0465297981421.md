### Title
Fee-on-Transfer Token Accounting Discrepancy Inflates Bridged `_value`, Draining Destination Bridge or Inflating Token Supply — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
`requestERC20Transfer` pulls `_value + _feeLimit` from the sender but does not verify the bridge's actual received balance. For fee-on-transfer tokens, the bridge receives less than requested, yet emits `RequestValueTransfer` with the full user-supplied `_value`. The destination bridge then delivers or mints the full `_value`, creating a permanent token deficit on the source side or unbacked inflation on the destination side.

### Finding Description
In `requestERC20Transfer`, `safeTransferFrom` is called for `_value + _feeLimit`. For a token with an in-transfer tax `t`, the bridge receives `(_value + _feeLimit) × (1 − t)`. Subsequently, `_payERC20FeeAndRefundChange` transfers `feeOfERC20[token]` to `feeReceiver` and any remainder back to `from`, both of which also incur the tax (reducing the bridge balance further). The `RequestValueTransfer` event is then emitted with the original `_value`, which the destination-chain relayer uses verbatim to call `handleERC20Transfer(_value)`. [1](#0-0) [6](#0-5) 

### Impact Explanation
- **Lock/unlock mode:** Destination bridge transfers `_value` tokens to the recipient, draining tokens that belong to other depositors. Repeated calls accumulate a deficit proportional to `_value × tax_rate` per transfer.
- **Mint/burn mode:** Destination bridge mints `_value` tokens against fewer burned on the source, permanently inflating the bridged token supply.
- In both cases, the `RequestValueTransfer` event records an inflated `_value` that does not correspond to actual locked/burned collateral, breaking the 1:1 bridge invariant.

### Likelihood Explanation
Requires the bridge owner to register a fee-on-transfer ERC20 token. This is a realistic scenario (deflationary/tax tokens are common), and the owner has no in-code warning that the bridge is incompatible with such tokens. Once registered, any user can trigger the discrepancy permissionlessly.

### Recommendation
After `safeTransferFrom`, measure the actual received amount by comparing pre/post balances:
```solidity
uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
uint256 received = IERC20(_tokenAddress).balanceOf(address(this)).sub(before);
require(received >= _value.add(_feeLimit), "fee-on-transfer token not supported");
```
Alternatively, explicitly document and enforce that fee-on-transfer tokens must not be registered.

### Proof of Concept
1. Deploy a 2% fee-on-transfer ERC20 token.
2. Register it on the bridge (owner call).
3. Set `feeOfERC20[token] = 0.01e18`, `feeReceiver = nonzero`.
4. Call `requestERC20Transfer(token, to, 100e18, 0.01e18, "")`.
5. Assert `IERC20(token).balanceOf(bridge) < 100e18` after the call — bridge holds `~97.9998e18` but `RequestValueTransfer` records `_value=100e18`.
6. On the destination chain, `handleERC20Transfer` delivers `100e18` tokens, draining `~2e18` from other depositors. [7](#0-6) [8](#0-7)

```text
    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
