### Title
`verifySeals` Pre-Permissionless Quorum Undercount Enables Single-Seal Block Acceptance on Sync Nodes — (`blockchain/block_validator.go`)

### Summary

In the pre-permissionless, pre-Randao path of `verifySeals`, the committed-seal threshold is computed as `2*sealer.F(blockNum, qualifiedLen, committeeSize)+1`. When `CommitteeSize=3` and `qualifiedLen>3`, `sealer.F` returns `0`, making the threshold `1`. The consensus core's `calcQuorumSize` returns `3` for the same parameters (effective size `min(10,3)=3 < 4` → full committee). A single malicious council member who is selected as proposer can craft a block with only their own committed seal, have it accepted by all syncing nodes via `validateHeader`, and cause a durable chain split against honest consensus nodes.

### Finding Description

`IstanbulSealer.F` computes fault tolerance as:

```go
// consensus/istanbul/sealer.go:304-309
func (m *IstanbulSealer) F(_ uint64, qualifiedLen, committeeSize int) int {
    if qualifiedLen > int(committeeSize) {
        return int(math.Ceil(float64(committeeSize)/3)) - 1
    }
    return int(math.Ceil(float64(qualifiedLen)/3)) - 1
}
```

For `committeeSize=3`: `ceil(3/3)-1 = 0`. The pre-permissionless branch of `verifySeals` uses this directly:

```go
// blockchain/block_validator.go:314
if validSeal < 2*v.sealer.F(blockNum, qualifiedLen, committeeSize)+1 {
```

yielding a threshold of `1`. [1](#0-0) 

The consensus core uses a different formula:

```go
// consensus/istanbul/core/core.go:81-87
func calcQuorumSize(qualifiedLen int, committeeSize uint64) int {
    size := min(qualifiedLen, int(committeeSize))
    if size < 4 {
        return size   // returns 3 for committeeSize=3
    }
    return int(math.Ceil(float64(2*size) / 3))
}
``` [2](#0-1) 

For `CommitteeSize=3, qualifiedLen=10`: `calcQuorumSize=3`, `verifySeals` threshold=`1`. The gap is 3×.

Note that `sealer.Quorum` (used in the post-permissionless path) correctly handles this case — it returns `n` for `n<4` — but `sealer.F` does not, and the pre-permissionless path deliberately avoids `sealer.Quorum` to preserve historical header validity. [3](#0-2) 

The sync path that calls `verifySeals` is live. `InsertHeaderChain` calls `hc.validator.ValidateHeader` for every unknown header, and the fetcher calls `blockchain.Validator().ValidateHeader` for propagated blocks. Both reach `verifySeals`. [4](#0-3) 

The pre-permissionless `verifySeals` path counts committed seals against the full **council** set (not just the committee), so the attacker only needs to be a council member — not necessarily a committee member — to provide a valid seal. [5](#0-4) 

### Impact Explanation

A single malicious council member who is selected as proposer for a block can:
1. Craft a block with only their own committed seal (1 seal, cryptographically valid).
2. Broadcast it to syncing nodes via P2P.
3. Syncing nodes call `validateHeader` → `verifySeals` → `1 >= 1` → accepted, written to canonical chain.
4. Honest consensus nodes never produce such a block (they require `calcQuorumSize=3` seals before committing).

Result: durable chain split. Syncing nodes (full-sync, fast-sync, snap-sync, light-sync) diverge from the honest consensus chain. Any state transitions in the malicious block — balance changes, contract deployments, reward distributions — are accepted as canonical on synced nodes but not on live consensus nodes.

### Likelihood Explanation

- `CommitteeSize=3` with `qualifiedLen>3` is a valid, reachable governance configuration (governance parameter `istanbul.committeesize`).
- The attack requires a single malicious council member to be selected as proposer — a probabilistic but achievable condition requiring no collusion.
- The P2P broadcast path is fully public and requires no special access beyond being a council member.

### Recommendation

Replace the `2*sealer.F()+1` formula in the pre-permissionless branch of `verifySeals` with a formula that is consistent with `calcQuorumSize`. Specifically, for effective committee sizes below 4, the quorum must equal the full effective size, not `2f+1`. The simplest fix is to use `sealer.Quorum(blockNum, qualifiedLen, committeeSize)` directly, or to replicate the `min(qualifiedLen, committeeSize) < 4 → return size` guard before applying `2f+1`.
