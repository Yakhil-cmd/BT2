### Title
Unauthenticated Bridge Peer Can Prematurely Evict Value-Transfer Txs from `bridgeTxPool` via Fake `ServiceChainReceiptResponseMsg` — (`node/sc/sub_bridge_handler.go`)

### Summary

`writeServiceChainTxReceipts` calls `bridgeTxPool.RemoveTx(tx)` unconditionally for **every** tx type whose hash appears in a received `ServiceChainReceiptResponseMsg`, not only for anchoring txs. Any connected bridge peer — authenticated only by chainID, a public value — can send a fabricated receipt whose `TxHash` matches a pending value-transfer tx, causing that tx to be silently evicted from the pool before it is confirmed on the parent chain.

### Finding Description

The call path is:

```
HandleMainMsg (ServiceChainReceiptResponseMsg)
  → handleParentChainReceiptResponseMsg
    → writeServiceChainTxReceipts
``` [1](#0-0) 

Inside `writeServiceChainTxReceipts`, the anchoring-specific DB writes are gated on `IsChainDataAnchoring()`, but `RemoveTx` sits **outside** that block and executes for every matched tx: [2](#0-1) 

Specifically, lines 440–453 perform anchoring DB writes only when `tx.Type().IsChainDataAnchoring()` is true, but line 455 (`sbh.subbridge.GetBridgeTxPool().RemoveTx(tx)`) is unconditional. The `// TODO-Kaia-ServiceChain: support other tx types if needed.` comment at line 454 confirms the developer was aware that non-anchoring types reach this point. [3](#0-2) 

**Peer authentication is chainID-only.** `RegisterNewPeer` rejects peers with a mismatched chainID but performs no further identity or role verification: [4](#0-3) 

The parent chainID is a public value. Any node that can reach the bridge P2P port and present the correct chainID in the handshake becomes a registered bridge peer and can send `ServiceChainReceiptResponseMsg` messages.

**Tx hash discovery is automatic.** `broadcastServiceChainReceiptRequest` sends the hashes of all pending pool txs to every connected peer: [5](#0-4) 

So once connected, the attacker immediately learns the hashes of all pending value-transfer txs and can craft a matching fake receipt.

### Impact Explanation

Removing a value-transfer tx from `bridgeTxPool` before it is confirmed on the parent chain means the SubBridge will stop retrying it. If the tx was dropped by the parent chain (e.g., gas price too low, nonce gap), the cross-chain transfer is permanently lost. The bridged KAIA or tokens are locked on the child chain with no corresponding release on the parent chain.

If Value Transfer Recovery (VTR) is enabled, it can re-queue the transfer, but the attacker can repeatedly send fake receipts to evict each re-queued tx, turning the impact into a persistent suppression of all cross-chain value transfers for as long as the attacker remains connected.

### Likelihood Explanation

- The bridge P2P port is a standard network listener. If reachable, any node speaking the `servicechain` protocol with the correct (public) chainID can connect.
- No secret, key, or operator approval is required at the code level.
- The attacker receives pending tx hashes automatically via `broadcastServiceChainReceiptRequest`.
- The fake receipt requires only a valid RLP-encoded `ReceiptForStorage` with the target `TxHash`; no cryptographic proof of execution is checked.

### Recommendation

Move `RemoveTx` inside the `IsChainDataAnchoring()` branch, or add an explicit branch for value-transfer txs that verifies the receipt against the parent chain state before evicting the tx. At minimum, add a tx-type guard so that non-anchoring txs are only removed after independent on-chain confirmation, not on the basis of a peer-supplied receipt alone.

### Proof of Concept

1. Start a SubBridge with a pending value-transfer tx in `bridgeTxPool`.
2. Connect a test node to the SubBridge's P2P port, passing the handshake with the correct parent chainID.
3. Receive the pending tx hash via the `ServiceChainReceiptRequestMsg` broadcast.
4. Send a `ServiceChainReceiptResponseMsg` containing a `ReceiptForStorage` with `TxHash` set to the observed hash.
5. Assert that `bridgeTxPool.Get(txHash)` returns `nil` (tx evicted) while the parent chain has no record of the transfer being executed. [6](#0-5) [2](#0-1)

func (sbh *SubBridgeHandler) writeServiceChainTxReceipts(bc *blockchain.BlockChain, receipts []*types.ReceiptForStorage) {
	for _, receipt := range receipts {
		txHash := receipt.TxHash
		if tx := sbh.subbridge.GetBridgeTxPool().Get(txHash); tx != nil {
			if tx.Type().IsChainDataAnchoring() {
				data, err := tx.AnchoredData()
				if err != nil {
					logger.Error("failed to get anchoring data", "txHash", txHash.String(), "err", err)
					continue
				}
				decodedData, err := types.DecodeAnchoringData(data)
				if err != nil {
					logger.Warn("failed to decode anchoring tx", "txHash", txHash.String(), "err", err)
					continue
				}
				sbh.WriteReceiptFromParentChain(decodedData.GetBlockHash(), (*types.Receipt)(receipt))
				sbh.WriteAnchoredBlockNumber(decodedData.GetBlockNumber().Uint64())
			}
			// TODO-Kaia-ServiceChain: support other tx types if needed.
			sbh.subbridge.GetBridgeTxPool().RemoveTx(tx)
		} else {
			logger.Trace("received service chain transaction receipt does not exist in sentServiceChainTxs", "txHash", txHash.String())
		}
		logger.Trace("received service chain transaction receipt", "anchoring txHash", txHash.String())
	}
}
