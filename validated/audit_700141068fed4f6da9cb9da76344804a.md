## Analysis

The reported bug class is "avoid multiple/independent divisions when splitting a reward among parties, since independent rounding introduces errors." An analogous pattern exists in ocore's headers-commission distribution logic, and there the rounding errors can actually mint extra network currency rather than merely favor one party over another.

### Root cause

When a unit has multiple authors and wins headers commission from a parent unit, the earned amount is split among `earned_headers_commission_recipients` using **independent per-recipient rounding**, once in the SQL (mysql) path and once in the JS (sqlite) path: [1](#0-0) [2](#0-1) 

Each recipient's share is computed as `Math.round(full_amount * share / 100.0)` (or the SQL `ROUND(...)` equivalent) independently, so the sum of the rounded amounts is not guaranteed to equal `full_amount`. Validation only guarantees that the recipients' *percentages* sum to exactly 100, not that the resulting *rounded amounts* sum to the original commission: [3](#0-2) 

The resulting per-address amounts are inserted verbatim into `headers_commission_contributions`, aggregated into `headers_commission_outputs`, and later become spendable through a `headers_commission` input, which is trusted at face value during validation (`calcFunc.ifOk` sets `total_input`) with no cross-check that the total ever equalled the payer unit's original `headers_commission` field: [4](#0-3) 

Because this computation is run identically and deterministically by every full node from the same contributions table, there is no consensus disagreement — but the extra minted amount is real, spendable currency that was never actually paid out by the parent unit.

### Exploitability

An attacker fully controls the `earned_headers_commission_recipients` list on their own multi-author unit (any unprivileged unit poster), subject only to: shares must be positive integers, sorted, and sum to exactly 100 [5](#0-4) . By choosing recipient counts/shares such that each individual `full_amount * share / 100` fraction sits just below `x.5`, every recipient's amount rounds up independently, so the sum of amounts credited can exceed the actual `headers_commission` earned by the winning unit's parent. Whether the crafted unit "wins" the headers commission for a given parent is decided by a SHA1-based lottery among sibling children [6](#0-5) , but an attacker can simply keep posting such crafted units until they win — the technique is repeatable indefinitely at ordinary unit-posting cost.

This produces genuine, unbacked base-currency ("bytes") creation credited to attacker-controlled addresses.

### Title
Independent per-recipient rounding in headers-commission distribution allows supply inflation - (File: headers_commission.js)

### Summary
`calcHeadersCommissions` splits a unit's earned headers commission (`full_amount`) among multiple `earned_headers_commission_recipients` by rounding each recipient's share independently (`Math.round(full_amount * share / 100.0)` / SQL `ROUND(...)`), instead of computing the split with a single division/allocation that preserves the total. This mirrors the audit finding's core issue — "avoid multiple divisions" that each introduce independent rounding error — except here the accumulated rounding error is directly mintable as spendable currency.

### Finding Description
`headers_commission.js` computes, for each winning child unit, the amount owed to each of its `earned_headers_commission_recipients` via an independent `Math.round` of `full_amount * share / 100` [2](#0-1) , and the same pattern exists in the MySQL SQL path [1](#0-0) . Validation of the recipient list only enforces that `earned_headers_commission_share` values are positive integers summing to exactly 100 [5](#0-4)  — it never checks that the resulting rounded token amounts reconstruct `full_amount`. The unchecked, possibly-inflated per-address amounts are written straight into `headers_commission_contributions`/`headers_commission_outputs` and later accepted as the authoritative earned amount when a `headers_commission` input is validated and spent [4](#0-3) .

### Impact Explanation
Because the split is attacker-chosen (recipients and their integer percentage shares are fields the unit author fully controls when composing a multi-authored unit, per `composer.js`'s `earned_headers_commission_recipients`), an attacker can pick shares that make every individual rounding operation round upward, so the total credited across `headers_commission_contributions` exceeds the actual `headers_commission` paid by the parent unit. Since all nodes compute this identically (deterministic, not a source of consensus divergence), the excess is not detected as invalid — it becomes genuinely spendable base-currency credited to attacker-controlled addresses, i.e., unbacked supply inflation of the network currency.

### Likelihood Explanation
Exploitation only requires posting an ordinary multi-authored unit with a hand-crafted `earned_headers_commission_recipients` list (an action any regular, unprivileged unit poster can take) and eventually winning the SHA1-based headers-commission lottery among sibling children [6](#0-5) , which can be retried indefinitely at normal fee cost. The gain per successful win is small (bounded by the number of recipients, capped at 100 since shares are positive integers summing to 100), but it is repeatable without limit over time, making the exploit low-cost and reliably exploitable, though only mildly profitable per instance.

### Recommendation
Replace independent per-recipient rounding with an allocation method that guarantees the sum of distributed amounts equals `full_amount` exactly (e.g., compute cumulative rounded totals and take the remainder as each next amount, or give the last recipient `full_amount` minus the sum already allocated to prior recipients) in both the SQL (`headers_commission.js` lines 49-51) and JS (`headers_commission.js` lines 180-188) code paths, and add a consistency check that the sum of `headers_commission_contributions.amount` per payer unit never exceeds `headers_commission`.

### Proof of Concept
1. Attacker controls two addresses A and B and creates a multi-authored unit with `earned_headers_commission_recipients = [{address:A, earned_headers_commission_share:50}, {address:B, earned_headers_commission_share:50}]`.
2. The attacker keeps posting such units as children of various parent units until one is selected as the SHA1-lottery winner for a parent whose `headers_commission` is an odd value X (e.g., 501).
3. `calcHeadersCommissions` computes `Math.round(501*50/100)=251` for A and `Math.round(501*50/100)=251` for B, totalling 502 instead of 501 — one extra unit created from nothing, credited into `headers_commission_outputs` for A and B.
4. Both A and B later spend their `headers_commission_outputs` via a `headers_commission`-type input, which validation accepts without cross-checking against the true 501-unit source amount [4](#0-3) .
5. Repeating this across many won parent units accumulates unbounded, unbacked inflation of the base currency over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
