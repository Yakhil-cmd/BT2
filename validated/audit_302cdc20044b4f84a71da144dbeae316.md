### Title
`CCMenuController#stack` resolves against unscoped `Stack.all` instead of the token-scoped `stacks` relation, bypassing per-`ApiClient` stack scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to the authenticated `ApiClient`'s `stack_id` via `stacks` (`Stack.where(id: current_api_client.stack_id)` when scoped) and `stack` calls `stacks.from_param!`. `Shipit::Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, and `check_permissions!` in `ApiClient` only checks that the permission string (e.g. `read:stack`) is present in the client's `permissions` array — it never checks `stack_id` — so any valid token can read any stack's CCMenu XML.

### Finding Description
Broken binding (equality claimed by `BaseController#stack`, violated by the override):

- Intended: `stack ∈ stacks` where `stacks = current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) 
- Actual in `CCMenuController`: `stack = Stack.from_param!(params[:stack_id])`, i.e. `stack ∈ Stack.all` regardless of `current_api_client.stack_id`. [2](#0-1) 

`CCMenuController` also overrides authentication to pull the token from `params[:token]` rather than Basic Auth: `@current_api_client = ApiClient.authenticate(params[:token])`. [3](#0-2) 

The only permission check performed is `require_permission :read, :stack`, which delegates to `check_permissions!`: [4](#0-3) [5](#0-4) 

`check_permissions!` only verifies `permissions.include?("read:stack")` — it never compares `stack_id`. Scoping is entirely delegated to the `stacks`/`stack` helpers in `BaseController`, and `CCMenuController` bypasses exactly that helper. There is no other guard (no `before_action` re-validating `params[:stack_id]` against `current_api_client.stack_id`).

Exploit flow:
1. Attacker (or any party who legitimately obtained a low-privilege `read:stack` token scoped to stack A, e.g. via the CCMenu URL feature) sends `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=<token-for-stack-A>`.
2. `authenticate_api_client` resolves `current_api_client` to the stack-A client via `ApiClient.authenticate(params[:token])`.
3. `require_permission :read, :stack` passes because the client has `read:stack` in its `permissions` array — this check is stack-agnostic.
4. `show` calls `stack`, which resolves `Stack.from_param!(params[:stack_id])` against all stacks, returning stack B.
5. Response renders stack B's CCMenu XML (deploy/build status) to the attacker, HTTP 200 instead of 404.

### Impact Explanation
This is an unauthenticated-for-scope read of another stack's build/deploy status (last deploy/rollback id, timestamp, running state) via `app/views/shipit/ccmenu/project` — a cross-tenant information disclosure where a token scoped to one repository/stack can enumerate and read the CI/CD status of every other stack in the installation. This matches the High severity category "unauthorized read of stack state" across tenants; it is fully repeatable for any `stack_id` and does not require the token's own stack to match, since the check is limited to permission name and not stack ownership.

### Likelihood Explanation
Precondition is possession of any valid `ApiClient` token with `read:stack` permission scoped to any single stack (a low-privilege capability, e.g. the one embedded in a stack's own public CCMenu URL as generated by `CcmenuUrlController`). Given that, the attack is a single unauthenticated GET request with an arbitrary `stack_id` — no GitHub credentials, no session, no signature bypass required, and is directly reachable through the documented CCMenu XML endpoint.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to delegate to the scoped `stacks` relation instead of the unscoped `Stack` class, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so lookups honor `current_api_client.stack_id` scoping just like every other API controller inheriting from `BaseController`.

### Proof of Concept
Minitest controller test (`test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "cannot read another stack's ccmenu xml with a token scoped to a different stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse)

  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: "scoped-to-a",
    stack: stack_a,
    permissions: ['read:stack']
  )

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }, format: :xml

  # Binding under test: stack resolved must be ∈ Stack.where(id: client.stack_id)
  # i.e. request must NOT resolve to stack_b since client.stack_id == stack_a.id
  assert_response :not_found
  refute_includes response.body, stack_b.repo_name
end
```
Before the fix this test fails: the response is `200 OK` and contains stack B's project XML, proving the cross-stack read. After changing `stack` to use `stacks.from_param!`, `Stack.where(id: current_api_client.stack_id).from_param!(params[:stack_id])` raises `RecordNotFound` for stack B's id, and `not_found` renders a 404.
