### Title
Webhook Signature Verified Against `repository.owner.login`, But Event Processing Trusts a Separately-Extracted `repository.full_name` — Cross-Organization Stack Injection - (`app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook against using one field of the untrusted, not-yet-verified JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature check for *that org* passes, the raw payload is dispatched to `Shipit::Webhooks::Handlers::Handler`, which independently derives the target `Repository`/`Stack` from a *different* field of the same still-attacker-controlled body: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Nothing ties these two fields together, so a payload can be signed with Org A's secret while acting on Org B's repository/stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
It picks the GitHub App config (and thus the `webhook_secret` used to verify the `X-Hub-Signature` HMAC) by calling `Shipit.github(organization: repository_owner)`, where: [2](#0-1) 
`repository_owner` is read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`) — i.e., it is fully attacker-controlled at the point it is used to pick which secret validates the signature. `GithubApp#verify_webhook_signature` then does a straightforward HMAC comparison against that org's secret: [3](#0-2) 

If the signature check succeeds, the whole raw payload is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`). Every handler resolves the `Stack`/`Repository` it will act on via the shared base class: [4](#0-3) 
Note `repository_name` uses `payload.dig('repository', 'full_name')` — a completely separate JSON path from the `repository.owner.login` used for signature-org selection. `PushHandler`, for example, uses this to locate stacks and force a resync to an attacker-supplied `after` SHA: [5](#0-4) 

**Equality that should hold but doesn't:** `organization whose webhook_secret authenticated the request == owner of the repository the handler mutates`. Because both values are read from the same attacker-supplied JSON blob independently, an attacker who legitimately controls (or has leaked) the `webhook_secret` for *any one* organization configured in this Shipit instance (e.g., their own low-value org "orgA" registered per `config/secrets.yml`'s multi-org github map) can sign an arbitrary payload with `repository.owner.login = "orgA"` (so the org-A secret is selected and validated) while setting `repository.full_name = "orgB/high-value-repo"`. The signature passes, but the fully-processed event acts on orgB's stack.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written." Concretely:
- `push` events let the attacker force `stack.sync_github(expected_head_sha:)` on an arbitrary victim stack/repo they have no legitimate access to.
- `status`/`check_suite`/`deployable_status`-style handlers (which follow the same `Handler#stacks`/`repository_name` pattern) let an attacker inject forged CI/commit-status data for a victim repository's commits.
- Because Shipit's `ci.require` gating and `continuous_deployment` automatic delivery (`Stack.schedule_continuous_delivery`) both act purely on locally-stored CI/status state, forging passing status for a victim stack's commit can make an otherwise-blocked or unreviewed commit deployable automatically, without the attacker ever needing an `ApiClient` token, resulting in an unauthorized deploy of attacker-influenced state — a cross-organization write triggered purely by possessing a *different*, lower-privilege organization's webhook secret. This matches the Critical-tier impact ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
Requires only that Shipit is configured to serve more than one GitHub organization (a documented/supported multi-tenant configuration, see `config/secrets.development.shopify.yml` and `docs/setup.md`), and that the attacker has legitimate access to install/administer a GitHub App (and hence its `webhook_secret`) for at least one of those organizations. No repository write access, ApiClient token, or session to the victim org is needed — only crafting one raw HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses. This is a purely structural, always-reachable code path (no timing, race, or DoS dependency), making it a straightforward analog to the "trailing zeros" bug class: two array/lookup indices that are supposed to be kept in lock-step but are populated/consumed from unrelated sources.

### Recommendation
After the signature is verified against `repository_owner`'s secret, re-validate that `repository.full_name`'s owner component (or `organization.login`) equals the same `repository_owner` value used to select the webhook secret before dispatching to handlers. Alternatively, look up the `Repository`/`Stack` first (scoped to the org whose secret validated the signature) and reject/ignore events whose `repository.full_name` owner does not match.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two orgs, `orgA` and `orgB`, each with its own `github.webhook_secret` in `config/secrets.yml`.
2. As an attacker who is an org admin of `orgA`'s GitHub App (or otherwise knows/leaked `orgA`'s `webhook_secret`), craft:
   ```
   POST /github/webhooks
   X-Github-Event: push
   X-Hub-Signature: sha1=<HMAC-SHA1(body, orgA_webhook_secret)>

   body = {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/high-value-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>"
   }
   ```
3. `WebhooksController#verify_signature` computes `repository_owner = "orgA"`, fetches `orgA`'s `GithubApp`, and successfully verifies the signature (`lib/shipit/github_app.rb:76-83`) because it was genuinely signed with `orgA`'s secret.
4. `PushHandler#process` (via `Handler#stacks`/`#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves `Repository.from_github_repo_name("orgB/high-value-repo")` and forces `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim `orgB` stack — despite the request only ever having been authenticated as belonging to `orgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
