### Title
Spend-cap conditions (`sum`/`amount_at_least`/`amount_at_most`) in address definitions only look at the current unit, letting a limited-authority signer drain funds by splitting into many units - (File: definition.js)

### Summary
Address definitions can restrict a co-signing branch to a maximum spend amount using the `sum` operator (e.g. `['sum', {filter: {what:'output', address:'other address'}, at_most: 100}]`) or a per-input/output `amount_at_most` filter. These checks are evaluated only against the messages contained in the unit currently being validated, not against the address's cumulative spending history. A signer who is authorized under such a "limited" branch (e.g. a hot wallet/device meant to be restricted to small transfers) can trivially bypass the cap by posting multiple separate units, each individually satisfying the `at_most`/`amount_at_most` limit, and move an unlimited total amount over time — the exact same "single-transaction cap, no accumulation" flaw described in the external report.

### Finding Description
The `sum` operator is implemented in `validateAuthentifiers`'s `evaluate()` function in `definition.js`. It sums only the inputs/outputs found in `objUnit.messages` (the unit under validation) via `evaluateFilter`: [1](#0-0) 

The underlying `evaluateFilter` function explicitly iterates `objUnit.messages` (the single unit being validated) and never consults historical spending from the database: [2](#0-1) 

Likewise, the `amount_at_least`/`amount_at_most` filter fields (used directly in `has`/`has one`/`seen`) are checked per input/output within the current unit (or via the `seen` op's single-row `LIMIT 1` query), never as a running total across multiple units authored by the same address: [3](#0-2) [4](#0-3) 

The validation-time schema check for `sum` even confirms these are the only supported constraint types (`equals`, `at_least`, `at_most` against a single unit's filtered sum) with no time-window or historical-accumulation option: [5](#0-4) 

Because Obyte/ocore's design allows address definitions such as `['and', [sig-branch, ['sum', {filter:{what:'output', address:'other address'}, at_most: N}]]]` to be used as a lightweight, non-multisig spending-limit policy for a restricted key or paired device, the natural expectation is that the signer under this branch cannot move more than `N` total. In reality, since the check is scoped to a single unit, that signer can issue any number of units, each transferring up to `N`, and there is no mechanism anywhere in `definition.js` or `validation.js` that aggregates a signer's/address's total output amount across multiple units or over any time window.

### Impact Explanation
This allows unauthorized spending beyond the amount the wallet owner intended to authorize for a restricted signing key/device: a definition meant to cap exposure of a compromised/limited key (e.g. allow only up to N bytes/asset units per authorization) provides no real protection, since the entire balance controlled by that address can be drained through repeated smaller transfers, each individually compliant with the `at_most`/`amount_at_most` constraint. This is a fund-loss/unauthorized-spending impact reachable by any unit author who has partial signing authority under such a definition branch — a normal, unprivileged use case for shared or limited-authority wallets.

### Likelihood Explanation
Likelihood is high for any wallet/definition author who relies on `sum`/`amount_at_most` as a genuine spending cap: no special privileges are needed beyond the authority already granted by the branch condition, and the bypass requires only posting several ordinary payment units instead of one, each independently valid.

### Recommendation
Either document explicitly (and prominently, in `sum`/`has`/`amount_at_most` semantics) that these constraints are scoped to a single unit and cannot serve as an aggregate/time-based spending cap, or implement genuine accumulation-based limiting (e.g., a running total tracked per-address/per-branch across a defined MCI/time window, similar to `age`/`mci` checks that already query historical stable units) so that `sum`-style conditions can be used safely as an actual spending-limit security control.

### Proof of Concept
1. Wallet owner sets an address definition: `['and', [['sig', {pubkey: LIMITED_KEY}], ['sum', {filter: {what:'output', address:'other address'}, at_most: 100}]]]`, intending that `LIMITED_KEY` can move at most 100 units of the asset in total.
2. Holder of `LIMITED_KEY` posts unit #1 with a single output of 100 to an external address — passes validation (`sum` = 100 ≤ at_most 100).
3. Holder posts unit #2 with another output of 100 to the same/another address — again passes validation independently, because `evaluateFilter`/`sum` only inspects the messages of unit #2, with no knowledge of unit #1's prior spend.
4. Repeating this process lets `LIMITED_KEY` transfer an unbounded total amount, defeating the intended spending cap.
