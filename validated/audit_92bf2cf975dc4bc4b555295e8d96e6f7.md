### Title
Webhook signature verification keys off an unauthenticated `repository.owner.login` field while handlers act on a different unauthenticated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which HMAC secret) to verify a webhook against using `repository_owner`, a value pulled straight out of the unauthenticated JSON body. Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the `Repository`/`Stack` to act on using a *different* field from that same unauthenticated body: `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other, and the equality the engine implicitly (and incorrectly) assumes is:

`organization used to select/verify the signing secret == owner segment of the repository actually written to by the handler`

This mirrors the Morpho bug class: a quantity used to gate/compute an operation (`_poolIndex`/`_p2pRate` in the report, here "which secret authorizes this request") is not the same quantity that is actually protected/verified by the check that is supposed to bind them together.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the raw, not-yet-verified request body before any signature check is performed. `Shipit.github(organization:)` looks up a per-organization config (`app_id`, `webhook_secret`, `private_key`, ...) declared in `secrets.yml`, exactly the multi-tenant layout shown in the repo's own sample configs, where a webhook_secret can legitimately be left blank for a given org: [2](#0-1) [3](#0-2) 

Inside `GitHubApp#verify_webhook_signature`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

So if **any** configured organization has no `webhook_secret`, a request claiming `repository.owner.login` equal to that organization's name passes signature verification unconditionally, regardless of the rest of the payload.

Once verification "passes", `create` dispatches the full unauthenticated `params` hash to every registered handler:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Every handler resolves its target repository/stack from a completely different, independently-attacker-controlled field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`Repository.from_github_repo_name` splits this string on `/` and does a plain `find_by(owner:, name:)` lookup, with no relation at all to the organization used above for signature selection: [7](#0-6) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the actual write target) are two independent, sibling JSON fields inside the same unauthenticated body, an attacker who knows (or can trigger) a webhook for any organization whose `webhook_secret` is unset can freely set `repository.full_name` to reference any *other* tenant's repository configured in the same Shipit instance, and the handler will act on that other repository/stack — with the signature check having verified nothing about that field at all.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" trust binding required by the rules. Concretely, with a spoofed webhook body whose `repository.owner.login`/`organization.login` names an org with no `webhook_secret`, but whose `repository.full_name` names a victim tenant's repo:
- `push_handler.rb` / `check_suite_handler.rb` will enqueue sync/refresh jobs (`GithubSyncJob`, `RefreshCheckRunsJob`) against the victim's `Stack`, which drive continuous-deployment sync/status logic for that stack.
- `status_handler.rb` writes attacker-controlled CI `state`/`context`/`target_url` as a `Status` on a commit of the victim's `Stack`, which feeds directly into `ci.require`/CI-gating logic that guards automatic deploys for stacks with `continuous_deployment: true`.
- `membership_handler.rb` can create/attach `User`/`Team`/`Membership` records unrelated to the org whose (missing) secret was used to authorize the request.

Because signature verification never actually binds to the repository being mutated, this is effectively an authentication bypass for cross-repository/cross-tenant webhook writes, matching the "cross-repository writes" / "unauthorized deploy" Critical/High impact classes in scope.

### Likelihood Explanation
Exploitability is conditioned on this Shipit deployment being configured with more than one GitHub organization (the multi-org config schema explicitly supported by `Shipit.github_app_config`/`TOP_LEVEL_GH_KEYS`) and at least one of those organizations having `webhook_secret` unset — a configuration the project's own sample secrets files (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) show as valid/expected. Given that condition, no credentials, tokens, or GitHub access are required — a bare unauthenticated `POST /webhooks` with a crafted body and `X-Github-Event` header is sufficient. This is exactly the "unprivileged attacker" scenario the rules require: no `ApiClient` token, no session, no GitHub App key.

### Recommendation
- Verify the webhook signature using the organization's secret, then re-derive/validate that every field the handler will act on (`repository.full_name`, `repository.owner.login`, `organization.login`) is internally consistent, e.g., require `repository.owner.login == repository_owner` (or reject if they differ) before dispatching to handlers.
- Do not permit any configured GitHub organization to have a blank/`nil` `webhook_secret` in production; fail closed (reject the webhook) rather than `return true unless webhook_secret`.
- Scope handler repository/stack resolution to the same organization that was used to select/verify the signature, rather than trusting `full_name` independently.

### Proof of Concept
1. Deploy Shipit with two organizations configured in `secrets.yml`: `orgA` (attacker-controlled, `webhook_secret:` left blank) and `orgB` (victim tenant, with a real `webhook_secret` and a `Stack` for `orgB/app`).
2. Attacker sends, without any signature or valid `X-Hub-Signature` header:
```
POST /webhooks
X-Github-Event: status
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/app" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example"
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`; because `orgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — the request is accepted with **no valid signature at all**.
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which resolves the target via `Repository.from_github_repo_name("orgB/app")` and writes a forged `success` status on the victim's commit — a write into `orgB`'s stack authorized only by `orgA`'s (non-existent) signature.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
