### Title
`MembershipHandler#process` grants arbitrary Shipit team membership using another organization's `github_id`, verified only against the attacker's own webhook secret - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` looks up the target `Team` record solely by the numeric `params.team.id` (`github_id`), with no check that the organization named in the payload (and whose secret validated the signature) actually owns that team on GitHub. An attacker who controls their own GitHub organization's membership webhook can send a genuinely-signed payload for their own org but set `team.id` to a pre-existing, unrelated team's `github_id`, causing `Team#add_member` to run against that foreign team.

### Finding Description
The broken binding: the code assumes `params.organization.login` (verified by signature) is bijective with `params.team.id`, i.e. it implicitly assumes:
`Shipit.github(organization: params.organization.login).api.team(params.team.id).organization.login == params.organization.login`
but this is never checked anywhere in the path.

Path: `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the same untrusted payload (`params.dig('organization', 'login')`, line 61). This only proves the payload was signed by *some* organization's webhook secret — the attacker's own org, which they legitimately control. It does not prove anything about `params.team.id`.

`MembershipHandler#process` (lines 22-34) then calls `find_or_create_team!` (lines 38-43), which does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```
`find_or_create_by!` first performs a `find_by(github_id: params.team.id)`. If a `Team` row already exists with that `github_id` (created earlier by the legitimate owning organization's own genuine membership webhook, or seeded via `Team.find_or_create_by_handle`/`lib/tasks/teams.rake`), the block is **not** executed — the existing record (with its real, different `organization`) is returned untouched. `process` then unconditionally calls `team.add_member(member)` (`app/models/shipit/team.rb:41-43`), inserting the attacker-chosen `member` (any GitHub login, created via `User.find_or_create_by_login!`) into the membership of that pre-existing, foreign team — with no call to `Shipit.github(organization: ...).api.team(params.team.id)` to confirm the signing organization owns that team id.

Existing guards do not close this gap: `verify_signature` only authenticates the organization named in the payload, not the `team.id` claim; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema (`params do ... end`) only checks types/presence, not cross-org ownership; there is no `require_permission!`/`User#authorized?` check inside the handler itself.

### Impact Explanation
Shipit team membership (`Shipit::Team#members`) is the basis for `Shipit.github_teams` authorization used elsewhere in the app to grant deploy/merge/administrative privileges. An attacker who runs any GitHub organization with a Shipit membership webhook configured can add an arbitrary GitHub login into a target `Team` record that belongs to a completely different, unrelated organization, as long as they learn that team's numeric `github_id` (leakable via GitHub UI/API URLs, prior webhook payloads, etc.). This is an authorization escalation into `Shipit.github_teams`, repeatable for every `github_id` the attacker can enumerate, and requires no privileges within the target Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must own/administer a GitHub organization with a `membership` webhook pointed at the target Shipit instance (a normal, unprivileged setup any org owner can do), and must know the numeric `github_id` of the target team (these ids are visible in GitHub UI/API URLs and not treated as secret). The attack requires zero Shipit credentials, sessions, or GitHub App keys belonging to the target — only the attacker's own legitimately-issued webhook secret. This is cheap and fully repeatable against any team whose id becomes known.

### Recommendation
In `find_or_create_team!` (and generally in `MembershipHandler#process`), verify team ownership against GitHub before creating/reusing a record: query `Shipit.github(organization: params.organization.login).api.team(params.team.id)` (or equivalent) and confirm the returned team's organization/slug matches `params.organization.login` before performing `find_or_create_by!`/`add_member`. Alternatively, scope the `Team` lookup by both `github_id` AND `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`) so a webhook from org A can never touch a `Team` row whose `organization` is org B, and reject if an existing row with that `github_id` belongs to a different organization.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (illustrative)
test "process does not let a foreign organization mutate another org's team by reusing its github_id" do
  # Pre-existing team genuinely owned by "target-org"
  target_team = Shipit::Team.create!(
    github_id: 555,
    organization: 'target-org',
    slug: 'admins',
    name: 'Admins',
    api_url: 'https://api.github.com/teams/555'
  )

  # Attacker's own org, "attacker-org", sends a genuinely-signed membership payload
  # for THEIR org, but sets team.id == target_team.github_id
  payload = {
    'action' => 'added',
    'team' => { 'id' => 555, 'name' => 'Admins', 'slug' => 'admins', 'url' => 'https://api.github.com/teams/555' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker-controlled-user' }
  }

  handler = Shipit::Webhooks::Handlers::MembershipHandler.new(payload)
  handler.call(payload) # signature verification happens upstream in the controller and is assumed valid for attacker-org

  target_team.reload
  assert_equal 'target-org', target_team.organization # binding claims org identity is preserved
  assert_includes target_team.members.map(&:login), 'attacker-controlled-user'
  # Assertion demonstrates: no call to Shipit.github(organization: 'attacker-org').api.team(555)
  # was made to confirm attacker-org owns team 555 before add_member executed.
end

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
    end
