### Title
Cross-tenant blocking-status suppression via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike sibling handlers (e.g. `CheckSuiteHandler`) which use the `stacks` helper that resolves `Repository.from_github_repo_name(repository_name)`. A webhook whose signature validates for repository B can therefore write a `Status` row onto any commit in the database that happens to share that SHA, including a commit belonging to stack A, and that write uses the target commit's own `stack_id`, not the source payload's repository.

### Finding Description
The broken binding, stated explicitly: the intended invariant is `status.stack_id == status.commit.stack_id == the stack that authenticated this webhook's repository`. The actual code produces `status.stack_id == commit.stack_id` (correct) but the *selection* of which commit gets the status is `commit.sha == params.sha` with **no constraint that `commit.stack.repository == payload.repository`**. So the true (broken) equality is:

`{ commit selected for status write } == { any Commit row in the DB with sha == params.sha }`, independent of `payload['repository']['full_name']`.

Path:
1. `WebhooksController#create` runs `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` then dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
2. `verify_signature` only checks that the payload was signed with the secret associated with `Shipit.github(organization: repository_owner)` — it authenticates *that the request came from GitHub for the claimed org*, but performs no check that `params.sha` belongs to any particular repository [2](#0-1) .
3. `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This query is global — it is not scoped via `stacks` (the base `Handler#stacks` helper that resolves `Repository.from_github_repo_name(repository_name)`, used correctly by e.g. `CheckSuiteHandler`) [4](#0-3) [5](#0-4) .
4. `create_status_from_github!` writes the status using the **target commit's own `stack_id`** — `statuses.replicate_from_github!(stack_id, github_status)` — so a forged status lands on stack A with `stack_id = A`, fully "legitimate-looking" from stack A's perspective [6](#0-5) .
5. `statuses` are ordered `-> { order(created_at: :desc) }` [7](#0-6) , and `Status::Group` computes the "current" status per context via `statuses.to_a.uniq(&:context)`, which — given the desc ordering — keeps only the most-recently-created status per context [8](#0-7) . A newly injected `success` status for the same `context` as the existing failing/blocking status therefore supersedes it and removes the failing entry from `visible_statuses` entirely.
6. `Commit#blocked?` walks `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)` [9](#0-8) , and `blocking?` delegates to `status.blocking?`, i.e. `Status::Group#blocking?` which is `statuses.any?(&:blocking?)` over the now-superseded (blocking status masked out) list [10](#0-9) . With the blocking failing status masked, this evaluates false, and the downstream head commit's `blocked?` flips to false.

Attacker request: attacker owns/controls a repository B with a legitimately configured, signature-valid Shipit webhook integration. They reproduce a git commit object with an identical SHA to the target intermediate commit in stack A (git commits are content-addressed; reproducing an existing, known commit's tree/parents/author/committer/message/timestamps in a separate repository yields an identical SHA — this is not a cryptographic collision, just content-addressable duplication, feasible whenever the target commit's exact content is known, e.g. a public upstream repo). The attacker sets a GitHub commit status of `success` on that SHA in repo B via the GitHub Status API; GitHub delivers a genuinely signed `status` webhook to Shipit with `repository.full_name = B`, `sha = <A's intermediate commit sha>`, `context = <the blocking context>`, `state = success`. `verify_signature` passes because the signature is valid for org/repo B. `StatusHandler#process` then finds and status-taints stack A's commit.

Existing guards that fail to prevent this: `verify_signature` authenticates the *source org/repo* of the webhook but is never checked against the *sha's owning repository* — there is no cross-check between `payload['repository']` and the `stack`/`Repository` that owns the matched `Commit`. `ExplicitParameters` schema for `StatusHandler` only validates types (`sha: String`, `state: String`, etc.), not tenancy [11](#0-10) .

### Impact Explanation
A cross-tenant write: a payload authenticated for repository B mutates stack A's commit/status state, satisfying the "payload for one repository mutating another's stack/commit" Critical category. Concretely, it can suppress a blocking CI status on an intermediate commit of stack A, causing `Commit#blocked?`/`#deployable?` on a later commit to evaluate incorrectly, enabling an unauthorized deploy of code whose CI/compliance gate should have blocked it. This is repeatable against arbitrary stacks/commits sharing the same SHA, and the blast radius spans all tenants sharing the Shipit instance (any stack, not just one), since the query is a bare, global `Commit.where(sha:)` with no tenant scoping at all.

### Likelihood Explanation
Preconditions: the attacker needs a Shipit-integrated repository they control that can deliver a validly signed webhook (achievable by installing/configuring the app on their own public repo, a standard unprivileged action), and they need to reproduce a commit with an identical SHA to the target commit in stack A — feasible whenever the target commit's exact content (tree, parents, author/committer identities and timestamps, message) is knowable, e.g. because stack A's repository is public or the commit was disclosed via a PR/patch. No Shipit secrets, sessions, or GitHub App keys are required. This is a straightforward, repeatable path once the commit content is known; the attacker cost is limited to owning a webhook-registered repo and re-creating a known commit object.

### Recommendation
Scope `StatusHandler#process` to the repository declared in the webhook payload, analogous to other handlers' use of `stacks`/`Repository.from_github_repo_name(repository_name)`, e.g. restrict the lookup to `stacks.flat_map { |s| s.commits.where(sha: params.sha) }` (or join through `Stack`/`Repository` in the `Commit.where` query) so a status can only be applied to commits belonging to stacks whose repository matches the webhook's authenticated repository.

### Proof of Concept
Minitest plan (in `test/models/webhooks/handlers/status_handler_test.rb` or similar, no live GitHub required):
1. Create `stack_a` bound to repository `org/repo-a`, and a commit chain: `first` (initial, matches `stack_a.last_deployed_commit`), `intermediate` (with an existing blocking-context status set to `failure`, context in `stack_a.blocking_statuses`), `head` (newer than `intermediate`).
2. Create an unrelated `stack_b` bound to repository `org/repo-b`, with its own commit whose `sha` is *set equal* to `intermediate.sha` (simulating the content-duplicated commit in repo B).
3. Assert precondition: `assert_predicate head_commit, :blocked?` (binding holds: blocking status of stack A's own commit blocks stack A's head).
4. Invoke `StatusHandler.call('sha' => intermediate.sha, 'state' => 'success', 'context' => <same blocking context>, 'repository' => { 'full_name' => 'org/repo-b' })` — simulating the webhook payload authenticated for repo B.
5. Assert violation: `refute_predicate head_commit.reload, :blocked?` — demonstrating the head commit of stack A is no longer blocked because a status attributed to repo B's authenticated webhook mutated stack A's commit's effective status.
6. Additionally assert `Shipit::Status.where(commit_id: intermediate.id, state: 'success').exists?` to show the forged status was persisted onto stack A's commit despite originating from repo B's webhook.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
