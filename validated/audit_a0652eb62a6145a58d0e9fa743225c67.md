Based on my investigation, I found a genuine analog. `pending_delegator_rewards` (SIMD-0123's block-revenue accumulator) is only ever incremented, never decremented, mirroring the exact bug class from the report: a "revenue" total that keeps accumulating (`epochRevenues[currentEpoch][token] += amountReceived`) with no corresponding subtraction after payout, causing rewards for one epoch's worth of deposits to be paid out repeatedly across multiple epochs.

### Title
`pending_delegator_rewards` is never decremented after block-reward distribution, causing duplicated/inflated stake rewards across epochs - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The SIMD-0123 block-revenue-sharing feature adds a `pending_delegator_rewards` field to `VoteStateV4` that accumulates lamports via `add_pending_delegator_rewards` [1](#0-0) , credited through the `DepositDelegatorRewards` instruction [2](#0-1) . Each epoch, `calculate_block_reward` reads this same field as the numerator for a proportional payout to every stake delegation: `pending_delegator_rewards * stake / total_active_stake` [3](#0-2) . Nowhere in the codebase (vote program, `handler.rs`, or the distribution path) is `pending_delegator_rewards` ever decremented, reset, or reduced by the amount that has already been distributed as block rewards.

### Finding Description
This is structurally identical to the reported `RevenueHandler.epochRevenues[currentEpoch][token] += amountReceived` bug: a running/cumulative "available rewards" balance is used directly as the payout numerator without ever subtracting what has already been paid out. In `RevenueHandler`, `thisBalance` (undiminished by claims) was added every `checkpoint()` call. In Agave, `pending_delegator_rewards` is added every `DepositDelegatorRewards` call (via `add_pending_delegator_rewards`, `checked_add` only) and is used unmodified as the reward pool for every subsequent epoch's `calculate_block_reward` computation. Since stake rewards are calculated once per epoch during `calculate_rewards_for_partitioning` → `calculate_validator_rewards` → `calculate_stake_rewards_and_commissions` → `calculate_block_reward` [4](#0-3) , and `pending_delegator_rewards` is never reduced by the block-reward amount actually credited to stake accounts in `build_updated_stake_reward` [5](#0-4) , the *entire* accumulated `pending_delegator_rewards` balance is re-paid out again on every subsequent epoch boundary, for as long as the value remains in vote state — i.e., stakers can be paid the same block-revenue deposit multiple times across consecutive epochs, and any deposit made once continues to be redistributed indefinitely.

The proportional split (`stake / total_active_stake`) itself is fine (unlike the RevenueHandler's raw-balance issue), but the numerator (`pending_delegator_rewards`) is the flawed "outstanding balance" quantity, exactly analogous to `thisBalance`/`epochRevenues[currentEpoch][token]` never being reduced by prior distributions.

### Impact Explanation
This causes misattributed/duplicated stake rewards: capitalization increases every epoch by `stake_reward_lamports_minted` (which includes `block_reward`) via `self.capitalization.fetch_add(stake_reward_lamports_minted, ...)` [6](#0-5) , meaning lamports are effectively minted repeatedly from a single deposited amount, inflating the total supply and stakers' balances beyond what was actually deposited via `DepositDelegatorRewards`. This matches the "concrete theft or minting of lamports, misattributed or duplicated rewards" acceptance criteria.

### Likelihood Explanation
This triggers automatically and deterministically on every epoch boundary once `block_revenue_sharing`, `commission_rate_in_basis_points`, and `custom_commission_collector` features are active and any non-zero `DepositDelegatorRewards` deposit has ever been made to a vote account — no attacker action beyond a single legitimate deposit is required; the bug is purely in the reward-calculation bookkeeping, so it will reproduce identically on every validator (cluster-wide, not fork-dependent), and would be caught by any test that (like PoC 1 in the report) checks totals across two or more epoch boundaries following a single deposit.

### Recommendation
`calculate_block_reward` / `redeem_delegation_rewards` (or the reward-distribution path in `distribution.rs`) must track and subtract the amount of `pending_delegator_rewards` actually distributed each epoch, decrementing the vote account's `pending_delegator_rewards` field by the total `block_reward` paid out across all stake accounts for that vote account in that epoch (analogous to fixing `RevenueHandler` to track deltas instead of raw/cumulative balances). This requires plumbing a per-vote-account "consumed pending_delegator_rewards" total back into vote state during/after `store_stake_accounts_in_partition`, ensuring monotonic decrease of `pending_delegator_rewards` as it is paid out.

### Proof of Concept
Could not be fully constructed/run without repository access to compile and execute a multi-epoch integration test; based on static analysis:
1. Enable `block_revenue_sharing`, `commission_rate_in_basis_points`, `custom_commission_collector` features.
2. Call `DepositDelegatorRewards` once with deposit `D` on a vote account with active stake delegations — `pending_delegator_rewards` becomes `D` [7](#0-6) .
3. Advance through one epoch boundary: `calculate_block_reward` pays out `D` proportionally to all delegators as `block_reward`, and capitalization increases by `D`.
4. Advance through a second epoch boundary without any further `DepositDelegatorRewards` call: `pending_delegator_rewards` is still `D` (never decremented), so `calculate_block_reward` again computes and distributes `D` in full — capitalization increases by `D` a second time for the same deposit, verifiable via `bank.capitalization()` deltas and `bank.rewards` records at each epoch boundary, similar to the assertions used in `test_begin_partitioned_rewards_returns_total_capitalization_increase` [8](#0-7) .

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
