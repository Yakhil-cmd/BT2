### Title
Cross-organization team-membership webhook allows escalation into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id`, and the webhook signature check verifies against the organization named in the *current* payload rather than against the organization already bound to that `Team` row. This lets an org that is one of several tenants configured on a shared Shipit instance send a validly-signed `membership` event that names an arbitrary existing `team.id` belonging to a *different* organization, causing `team.add_member(member)` to run against that foreign `Team` row and, if that team is one of `Shipit.github_teams`, granting the named member unauthorized access to the whole Shipit instance.

### Finding Description
The claimed binding, stated as an equality: `Team#organization == organization_of_every_subsequent_verified_event_for_that_github_id` is **false** after the first write, and this is exactly what makes the exploit possible.

Code path:
- `verify_signature` selects which org's secret to check against using the *payload itself*: `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization', 'login')` [1](#0-0) . For a `membership` event there is no `repository` key (per the handler's own params schema), so `repository_owner` is exactly `params.organization.login` — fully attacker-supplied.
- `MembershipHandler#find_or_create_team!` resolves the `Team` row purely by `github_id`, independent of which organization signed the event: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [2](#0-1) . When the row already exists (created earlier for OrgA), the block is skipped and `organization`/`slug` are never re-synced — confirming the "write-once" binding for `organization`.
- Critically, `team.add_member(member)` (or `team.members.delete(member)`) still executes unconditionally afterwards [3](#0-2) , regardless of whether `params.organization.login` matches the `Team`'s stored `organization`.
- `Team#add_member` blindly appends the resolved `User` to `members` [4](#0-3) .

Exploit flow: an attacker who legitimately administers OrgB (one of several orgs configured under `secrets.github` in a multi-org Shipit deployment, per `docs/setup.md`'s "Using Multiple Github Applications" section) knows OrgB's `webhook_secret`. They POST directly to `/webhooks` with header `X-Github-Event: membership` and a body whose HMAC-SHA1 signature (computed with OrgB's own secret) is valid, but whose JSON content sets `organization.login = "OrgB"` (so `verify_signature` passes using OrgB's secret), `team.id = T` (the `github_id` of an existing `Team` row actually owned by OrgA), `team.slug/name/url` arbitrary, `action = "added"`, and `member.login` = attacker's own GitHub login. Because lookup is by `github_id` alone, this resolves to OrgA's `Team` row and adds the attacker as a member of it.

Why guards fail:
- `verify_signature` correctly authenticates *that OrgB sent this request*, but never checks that the `team.id` in the payload actually belongs to OrgB — there is no cross-check between `repository_owner`/`params.organization.login` and the resolved `Team#organization`.
- `ExplicitParameters` schema only validates types/presence of `team.id`, `organization.login`, etc., not their consistency [5](#0-4) .
- `find_or_create_by!`'s create-block is a one-time write, so once a `Team` exists, no later event—regardless of its verified org—can correct or re-validate `organization`.

### Impact Explanation
If the targeted `Team` (github_id `T`) is one of the teams listed in `Shipit.github_teams` (populated via `Team.find_or_create_by_handle` and used in `User#authorized?`: `teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [6](#0-5)  and enforced by `force_github_authentication` [7](#0-6) , then successfully forging this event grants the named GitHub user (who logs in via OAuth to obtain a `User` row, then can be added to the `Membership` join table) authorization into the entire shared Shipit instance — bypassing the "You must be a member of ..." check. This is repeatable against any tenant/team on the shared instance whose `github_id` is known or guessable, and is a cross-tenant escalation: one onboarded (but otherwise unprivileged) organization's admin can grant themselves access controlled by a different organization's team membership. This matches the explicitly listed High-severity category: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with the multi-organization GitHub App scheme (multiple orgs under `secrets.github`), and (2) the attacker legitimately administering/owning at least one of those configured orgs (and thus knowing its `webhook_secret`) while not otherwise being a Shipit operator or `Shipit.github_teams` member. Given those preconditions, the attack is a single crafted HTTP POST, fully repeatable, and does not require any Shipit or GitHub Enterprise secrets beyond what the attacker's own org already possesses.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team#organization` matches `params.organization.login` before performing any membership mutation (e.g., raise/drop the event if `team.organization != params.organization.login`), and additionally scope the initial lookup by `organization` and `slug`/`github_id` together rather than by `github_id` alone, so a `github_id` collision or reuse across organizations cannot bind actions to the wrong `Team` row.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
```ruby
test "membership event from a different (validly-signed) org does not re-sync organization but still mutates a foreign team" do
  team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  original_organization = team.organization

  @request.headers['X-Github-Event'] = 'membership'
  # Stub signature verification success for 'orgb' (simulating attacker owns orgb and knows its secret)
  Shipit.github(organization: 'orgb').stubs(:verify_webhook_signature).returns(true)

  payload = {
    action: 'added',
    team: { id: team.github_id, name: 'Evil Team', slug: 'evil-team', url: 'https://example.com' },
    organization: { login: 'orgb' },
    member: { login: 'attacker' }
  }

  assert_no_difference -> { Team.count } do
    post :create, body: payload.to_json, as: :json
    assert_response :ok
  end

  team.reload
  # Binding claim: organization stays bound to the FIRST writer (shopify), unaffected by orgb's verified event
  assert_equal original_organization, team.organization

  # But add_member still ran for the org whose signature verified this second event
  assert_includes team.members.map(&:login), 'attacker'
end
```
This demonstrates both halves of the broken equality: `Team#organization` remains fixed to the original org (proving write-once), while `add_member` still executes for a request whose verified organization never owned that specific team — the divergence the question asks about.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
