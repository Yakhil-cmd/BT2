### Title
No refund path for burned tokens when a Sui→EVM bridge transfer is never approved/claimed - (File: crates/sui-framework/packages/bridge/sources/bridge.move)

### Summary
`send_token`/`send_token_v2` in the Sui native bridge module immediately burn the user's `Coin<T>` on Sui via `send_token_internal` and create a pending `BridgeRecord` before any off-chain committee signatures exist [1](#0-0) . There is no `cancel`/`refund`/`reclaim` entry point anywhere in the `bridge` package or the bridge client crate to reverse this burn if the transfer is never approved and executed on the destination chain [2](#0-1) .

### Finding Description
The user-facing `send_token<T>` function creates a `BridgeMessage`, calls `send_token_internal`, which asserts the bridge is not paused and the route is valid, then unconditionally burns the coin from the user's treasury balance and stores a `BridgeRecord{ verified_signatures: none, claimed: false }` in `token_transfer_records` [3](#0-2) . At this point the funds are permanently gone from Sui's supply and the only path to completion is an off-chain committee calling `approve_token_transfer` (to attach signatures) and then some party invoking the EVM-side `transferBridgedTokensWithSignatures`, which performs its own independent checks (`isSupportedChain`, `tokenAddressOf != 0`, transfer-limit checks, vault balance sufficiency) before releasing ERC20/ETH funds [4](#0-3) .

Just as in the ZetaChain report, once the record has been created and the token burned, any legitimate failure on the destination side (EVM-side revert due to vault under-funding, transfer-limit exceed handling that only emits an event and returns without minting, unsupported/removed token mapping, or the committee simply declining to sign an already-burned, no-longer-valid message) leaves the `BridgeRecord` permanently in `Pending`/`Approved`-but-unclaimed state with no way for the depositing user, or anyone, to reclaim the burned value [5](#0-4) . Unlike the incoming (claim) path — where a failed limiter check simply returns `option::none()` without having minted anything, so no funds are lost — the outgoing `send_token` path destroys value *before* any validation of deliverability on the far side occurs, and that destruction is irreversible in Move (there is no unburn/remint entrypoint restoring the sender's balance).

### Impact Explanation
This directly parallels the ZetaChain root cause: value is consumed on the source domain at initiation time, while the correctness/success of downstream completion is only checked later (off-chain committee/EVM execution), and no on-chain refund mechanism exists for the failure case. If a Sui→EVM bridge deposit becomes unfulfillable — e.g., vault liquidity insufficient, token no longer supported/paused on the EVM side, or a malformed/unactionable message that the honest, non-malicious committee correctly refuses to execute — the depositor's tokens are burned on Sui with no reclaim path, resulting in permanent fund lock. This matches the "permanent fund lock" High/Medium allowed-impact category.

### Likelihood Explanation
Reachable by any ordinary Sui holder simply by calling `send_token`/`send_token_v2` with a valid-looking but ultimately non-deliverable destination configuration (e.g., a token whose EVM vault balance later becomes insufficient, or is deregistered/paused on the EVM side after the burn but before execution). No malicious validator, bridge authority, or governance action is required — a legitimate, unresponsive-or-declining committee/EVM state transition is sufficient to trigger the loss, matching the "unprivileged caller" attacker model required by scope. However, I could not fully verify from the indexed code whether any additional off-chain safety net (e.g., automatic manual refund tooling in the bridge-node operator flow) exists outside the on-chain Move/Solidity contracts, since bridge-node retry/cancellation logic beyond `sui_client.rs`'s status polling was not found in the indexed portions of `crates/sui-bridge`.

### Recommendation
Add an on-chain refund/cancellation path for `BridgeRecord`s that: (1) allows the original message to be refunded to the sender if it has not been approved within a defined timeout, or (2) allows the sender (or committee via a signed "refund" message type) to reclaim/remint the burned amount back to the original sender if the destination-chain execution is confirmed to have failed. This mirrors the partial mitigation ZetaChain implemented for its Zeta-gas-refund case, but Sui's bridge currently has no equivalent for any token type.

### Proof of Concept
1. User calls `bridge::send_token<T>(bridge, target_chain, target_address, coin, ctx)` with a valid target chain/address; `token_amount` is burned immediately from the Sui `BridgeTreasury` and a `BridgeRecord{claimed:false, verified_signatures:none}` is stored.
2. Before the committee approves/executes, the vault balance for token `T` on the EVM `SuiBridge`/`BridgeVault` becomes insufficient (e.g., drained by other legitimate withdrawals) or the token is removed from `IBridgeConfig`, causing `_transferTokensFromVault` to always revert (`"SuiBridge: Unsupported token"` or `SafeERC20` transfer failure) whenever anyone attempts `transferBridgedTokensWithSignatures`.
3. The off-chain committee, observing the transfer cannot succeed, declines to call `approve_token_transfer`, or does so but the EVM execution reverts indefinitely.
4. The `BridgeRecord` remains permanently `Pending`/`Approved` and unclaimed; there is no `bridge::` entrypoint to burn/cancel the record and remint tokens back to the sender on Sui — the originally burned `token_amount` is permanently lost to the user.

// Create bridge request to send token to other chain, the request will be in
// pending state until approved
public fun send_token<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    ctx: &mut TxContext,
) {
    let inner = load_inner_mut(bridge);

    let bridge_seq_num = inner.get_current_seq_num_and_increment(message_types::token());
    let token_id = inner.treasury.token_id<T>();
    let token_amount = token.balance().value();
    assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
    assert!(token_amount > 0, ETokenValueIsZero);

    // create bridge message
    let message = message::create_token_bridge_message(
        inner.chain_id,
        bridge_seq_num,
        address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_id,
        token_amount,
    );

    inner.send_token_internal(target_chain, token, message);

    // emit event
    event::emit(TokenDepositedEvent {
        seq_num: bridge_seq_num,
        source_chain: inner.chain_id,
        sender_address: address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_type: token_id,
        amount: token_amount,
    });
}

// Record bridge message approvals in Sui, called by the bridge client
// If already approved, return early instead of aborting.
public fun approve_token_transfer(
    bridge: &mut Bridge,
    message: BridgeMessage,
    signatures: vector<vector<u8>>,
) {
    let inner = load_inner_mut(bridge);
    assert!(!inner.paused, EBridgeUnavailable);
    // verify signatures
    inner.committee.verify_signatures(message, signatures);

    assert!(message.message_type() == message_types::token(), EMustBeTokenMessage);
    assert!(
        message.message_version() <= message::token_transfer_message_version(),
        EUnexpectedMessageVersion,
    );
    let token_payload = if (message.message_version() == 2) {
        message.extract_token_bridge_payload_v2().to_token_payload_v1()
    } else {
        message.extract_token_bridge_payload()
    };
    let target_chain = token_payload.token_target_chain();
    assert!(
        message.source_chain() == inner.chain_id || target_chain == inner.chain_id,
        EUnexpectedChainID,
    );

    let message_key = message.key();
    // retrieve pending message if source chain is Sui, the initial message
    // must exist on chain
    if (message.source_chain() == inner.chain_id) {
        let record = &mut inner.token_transfer_records[message_key];

        assert!(record.message == message, EMalformedMessageError);
        assert!(!record.claimed, EInvariantSuiInitializedTokenTransferShouldNotBeClaimed);

        // If record already has verified signatures, it means the message has been approved
        // Then we exit early.
        if (record.verified_signatures.is_some()) {
            event::emit(TokenTransferAlreadyApproved { message_key });
            return
        };
        // Store approval
        record.verified_signatures = option::some(signatures)
    } else {
        // At this point, if this message is in token_transfer_records, we know
        // it's already approved because we only add a message to token_transfer_records
        // after verifying the signatures
        if (inner.token_transfer_records.contains(message_key)) {
            event::emit(TokenTransferAlreadyApproved { message_key });
            return
        };
        // Store message and approval
        inner
            .token_transfer_records
            .push_back(
                message_key,
                BridgeRecord {
                    message,
                    verified_signatures: option::some(signatures),
                    claimed: false,
                },
            );
    };

    event::emit(TokenTransferApproved { message_key });
}

fun send_token_internal<T>(
    inner: &mut BridgeInner,
    target_chain: u8,
    token: Coin<T>,
    message: BridgeMessage,
) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);

    // burn / escrow token, unsupported coins will fail in this step
    inner.treasury.burn(token);

    // Store pending bridge request
    inner
        .token_transfer_records
        .push_back(
            message.key(),
            BridgeRecord {
                message,
                verified_signatures: option::none(),
                claimed: false,
            },
