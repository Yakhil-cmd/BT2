## Title
Secondary-signer authentication bypass via global `is_derivable_account_abstraction_enabled()` flag in `allow_missing_txn_authentication_key` - (File: `aptos-move/framework/aptos-framework/sources/transaction_validation.move`)

### Summary
`allow_missing_txn_authentication_key` is used to decide whether a missing authentication-key proof for a signer can be tolerated. For the *derivable* account-abstraction branch it checks only the **global** feature flag `features::is_derivable_account_abstraction_enabled()` and never checks that the specific address in question actually went through any derivable-AA (or any) authentication. When this function is invoked for a **secondary signer** in `multi_agent_common_prologue`, a transaction that supplies `NoAccountAuthenticator`/no proof for a secondary signer is admitted purely because the global flag is on — even if that secondary account is an ordinary ed25519 account that never enabled/derived any account-abstraction authenticator and never presented any signature.

### Finding Description
`allow_missing_txn_authentication_key`: [1](#0-0) 

is called from `multi_agent_common_prologue` whenever the per-secondary-signer public key hash is `None`: [2](#0-1) 

On the Rust side, `TransactionMetadata::senders()`/`authentication_proofs()` include **secondary signers**, and `validate_signed_transaction` only performs real AA dispatch (`dispatchable_authenticate`, which re-derives/validates the address) when the proof is `AuthenticationProof::Abstract`. Any other proof kind — including `AuthenticationProof::None`, which is what `NoAccountAuthenticator` produces — falls through to `_ => Ok(serialized_signer(&sender))`, i.e. **no cryptographic or AA check at all** is executed for that signer: [3](#0-2) [4](#0-3) 

So the flow for a crafted `MultiAgent`/`FeePayer` transaction where a secondary signer slot uses `AccountAuthenticator::NoAccountAuthenticator` is:
1. `TransactionAuthenticator::verify` iterates and calls `.verify()` on each `AccountAuthenticator`, including the secondary ones [5](#0-4) .
2. `TransactionMetadata::new` turns that secondary authenticator into `AuthenticationProof::None`.
3. `validate_signed_transaction` never calls `dispatchable_authenticate` for it (proof isn't `Abstract`) — no AA authenticate() function runs, no signature is checked, nothing ties this admission to control of the address.
4. The Move prologue sees `signer_public_key_hash = option::none()` for that secondary address and calls `allow_missing_txn_authentication_key(secondary_address)`, which returns `true` solely because `features::is_derivable_account_abstraction_enabled()` is globally on — a network-wide toggle that has nothing to do with whether *this* address is a derivable-AA account.
5. The transaction is admitted, and the target address's `signer` capability (`serialized_signer`) is handed to Move execution as a secondary signer, with zero proof of control.

This breaks the core invariant of multi-agent transactions that "secondary signer" implies the account holder authorized the transaction.

### Impact Explanation
Any unprivileged attacker who knows (a) an existing account address and (b) that `derivable_account_abstraction` feature is on-chain enabled (a normal network feature, not privileged) can craft a `MultiAgent`/`FeePayer` transaction naming any existing address as a secondary signer with `NoAccountAuthenticator`, and have it admitted by both the VM's authenticator verification (no signature required for `NoAccountAuthenticator`) and the Move prologue (`allow_missing_txn_authentication_key` returns true for unrelated reasons). Any Move entry function that trusts a secondary `&signer` parameter as proof of that account's authorization (escrow acceptance, multi-party swaps, approvals, delegation flows, etc.) can be forged for arbitrary victim accounts — a critical secondary-signer authentication/binding bypass.

### Likelihood Explanation
High. The only precondition is that `is_derivable_account_abstraction_enabled` is enabled network-wide, which is a standard feature (not something requiring privileged access to flip per-attack). No secondary-signer state is required on the victim account, and the attack requires no private key, no prior approval, and no interaction from the victim.

### Recommendation
`allow_missing_txn_authentication_key` must not use the global feature flag alone as authorization proof for a specific signer's missing auth key. It should only permit a missing auth key for a signer whose *authentication proof for that specific transaction* was actually `AuthenticationProof::Abstract` and was actually run through `dispatchable_authenticate`/`authenticate()` (which independently re-validates address derivation/enrollment). Concretely: thread through, per secondary signer, whether AA dispatch was actually invoked and succeeded for that address (instead of re-deriving a boolean from a global feature toggle in the Move prologue), and reject `NoAccountAuthenticator` for any signer that isn't backed by a corresponding `Abstract` authentication proof.

### Proof of Concept
1. Enable `derivable_account_abstraction` feature (or use a network where it's already enabled).
2. Create a standard account `victim` with an ordinary ed25519 auth key — never register any dispatchable/derivable AA authenticator for it.
3. Craft a `MultiAgent` (or `FeePayer`) `SignedTransaction` where `sender` is the attacker's account (properly signed) and `secondary_signer_addresses = [victim]`, `secondary_signers = [AccountAuthenticator::NoAccountAuthenticator]`.
4. Submit via `/transactions` (BCS) or mempool.
5. Expected (per boundary conditions) is rejection with `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY`/`INVALID_SIGNATURE`. Actual observed behavior (per code trace above) is acceptance, because `multi_agent_common_prologue` calls `allow_missing_txn_authentication_key(victim)`, which returns `true` due to the global `is_derivable_account_abstraction_enabled()` flag, regardless of `victim`'s actual key scheme or lack of any signature.
