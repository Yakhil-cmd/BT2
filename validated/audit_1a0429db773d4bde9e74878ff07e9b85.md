### Title
Attacker-controlled swap route executes arbitrary contract code under the victim's authorization tree, draining wallet tokens beyond the swapped amount - (contracts/controller/src/strategies/swap.rs)

### Summary
The XSS report describes attacker-supplied markup being executed in the victim's security context because a validating-but-not-sanitizing gate (`isValidSVG`) admits dangerous content. The analog in XOXNO Lending is the router `swap_xdr` payload accepted by `swap_collateral` / `swap_debt` / `repay_debt_with_collateral` / `multiply`: the payload's `assets`/`ops` registries are well-formedness-checked (opcode ranges, index bounds, same-token) but the pool and token addresses they name are never validated or allowlisted, so arbitrary attacker-deployed contracts execute on the call stack beneath the victim's `require_auth` entry — and any `token.transfer(victim, attacker, x)` they issue is recorded by simulation as a child of the victim's signed authorization tree.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` forwards caller-supplied `swap: StrategySwap` bytes verbatim to the configured router (`router.execute_strategy(&controller, &amount_in, swap)`, lines 36–38). The only protocol-side checks are: positive measured input spend bounded by `amount_in` (`RouterOverspend`, lines 41–48), positive measured `token_out` delta (`NoSwapOutput`, lines 75–83), and the post-swap risk gates. None of these inspect which contracts the route invokes.

The router (`contracts/swap-aggregator`) decodes `swap_xdr` into a `StrategyPayload` and dispatches hops to pool and token addresses taken directly from the caller's `assets` registry — it "keeps no allowlist" of them (docs/explanation/threat-model.md, lines 154–156). Because the controller calls `execute_strategy` inside the same authorized invocation, any nested call a rogue hop contract makes — e.g. `token::Client::new(&unrelated_token).transfer(&victim, &attacker, &balance)` — is attributed to the victim's `swap_collateral` auth entry. An honest simulator records it as a child of the caller's entry, and if the wallet/client signs the simulated tree without decoding it, the transfer executes. This is demonstrated end-to-end in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, where a `RogueHopPool` named by the route steals the victim's entire balance of an unrelated wallet token (lines 194–227, 258–268).

Like the SVG payload that passes `isValidSVG()`, the malicious route passes every on-chain check: it returns a fair `token_out`, spends exactly `amount_in`, and leaves the account solvent. The injection point is the unvalidated address registry inside an otherwise well-formed payload.

### Impact Explanation
Theft of user funds. The stolen amount is the victim's wallet balance in whatever tokens the rogue contract names — unbounded by `amount_in`, by the payload `min_out`, or by the final account risk gates (threat-model.md, lines 157–161). The victim can lose their entire holdings of a token the protocol never listed, as in the test (`WALLET_BALANCE = 77_770_000_000` drained to zero). A malicious quote/route provider can distribute such `swap_xdr` to any user of `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or direct `execute_strategy` calls.

### Likelihood Explanation
Medium: exploitation requires the victim to sign the auth tree that simulation produces (analogous to the UI:R in the XSS advisory). The attack succeeds whenever a wallet or client signs simulated auth without decoding the route — which the codebase itself acknowledges is the realistic default: "A client must decode the route it signs and refuse an authorization tree with any other child" (threat-model.md, lines 162–164), i.e. nothing in-contract prevents it. Any unprivileged attacker can deploy a rogue pool contract and craft the route; no privileged role, oracle manipulation, or leaked keys are needed.

### Recommendation
- Enforce a governance-managed allowlist of hop pool/venue addresses inside the router's `dispatch_hop`, or validate that every `assets` entry is a known listed token/pool before invoking it, so payload code cannot run under the caller's auth.
- Alternatively, have the router execute venue calls via a separate sub-account/invoker that isolates the sender's authorization scope.
- Until then, the documented client-side mitigation (decode `swap_xdr`, reject auth trees with unexpected children — `verifyRouteBytes`/`verifyStandaloneEnvelope` in skills/xoxno-swap-aggregator/payload.md) should be treated as mandatory.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is an executable PoC:

1. Attacker deploys `RogueHopPool` whose `swap()` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` (lines 54–72).
2. A `RoutedSwap` route naming that pool as `hop_pool` is built and passed as `swap_xdr` to `controller.swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)` (lines 111–164).
3. Recording-mode simulation accepts the route and records the rogue `transfer` as a child of Alice's `swap_collateral` auth entry; Alice's wallet token balance goes to 0 and the attacker's to `WALLET_BALANCE` while she still receives the fair ETH output (lines 194–227).
4. In enforcing mode, signing that simulated tree executes the theft (lines 258–268); the benign control passes with a root-only tree (lines 233–237).

Note: this exposure is already documented in `docs/explanation/threat-model.md` (lines 154–165) as a known residual risk delegated to client-side verification; if the program considers that documentation an accepted design decision, this finding should be downgraded accordingly.
