### Title
Signed off-chain orders/messages in oscript AAs are accepted with no expiry enforcement, enabling stale-price execution and sandwich attacks - (File: test/samples/order_book_exchange.oscript)

### Summary
`is_valid_signed_package()` and `signed_message.validateSignedMessage()`, the primitives ocore provides for AAs to accept off-chain-signed intents (orders, trade instructions, payment-channel updates), verify only the signature, author definition, and that `last_ball_unit` is a stable unit known at or before the current MCI. Neither the formula evaluator (`formula/evaluation.js`) nor `signed_message.js` enforces any deadline/expiry on the `signed_message` payload itself, even though the schema permits an optional `timestamp` field. The canonical order-book-exchange AA template shipped with ocore explicitly documents this gap with a `// to do check expiry` comment right before the trade is executed.

### Finding Description
An AA author building an order-matching/exchange AA (the exact pattern shown in ocore's own reference template) accepts two counter-signed orders via `trigger.data.order1`/`order2`, each containing `signed_message` fields such as `sell_asset`, `buy_asset`, `sell_amount`, and `price`, authenticated with `is_valid_signed_package(...)` [1](#0-0) . The code performs asset-pair checks, replay protection via `sha256(...)`/`var['executed_'||id]`, balance checks, and signature validation—but the price staleness check is left as an unimplemented TODO: `// to do check expiry` [2](#0-1) .

The root cause is in the underlying primitive: `is_valid_signed_package` in the formula evaluator validates `last_ball_unit` (that it is a stable unit known before the trigger's MCI) and the signature/definition, but does not compare any timestamp in the signed message against the current network time or `mci` to reject stale orders [3](#0-2) . Likewise, `validateSignedMessage()` in `signed_message.js` accepts an optional `timestamp` field in the schema (`["signed_message", "authors", "last_ball_unit", "timestamp", "version"]`) but never uses it to bound message validity/expiry — it is only used for `last_ball_unit`/definition lookups, not compared to "now" [4](#0-3) [5](#0-4) .

This mirrors the reported bug class exactly: a user signs an order/trade intent off-chain (analogous to `sellAllAmount`/`buyAllAmount` calldata with a `minOutputAmount`), the signed package can sit "in the mempool"-equivalent (held by a counterparty, an off-chain matcher, or leaked) indefinitely, and be posted as `trigger.data` to the AA at any arbitrary future point as long as the referenced `last_ball_unit` is still resolvable and the signature is valid — there is no deadline after which the order becomes unexecutable.

### Impact Explanation
Because signed orders never expire, a counterparty (or a party who intercepts a signed order, e.g. one leg of an order-book match) can hold a favorably-priced signed order and execute it much later when market conditions have shifted, extracting value from the original signer at a stale price. Since the AA state machine unconditionally trusts `$order1.price`/`$order2.price` embedded in the old signed message (only checking self-consistency between the two orders, not real-time price), this results in concrete, unauthorized asset loss for the signer of the stale order — a direct AA fund-loss scenario reachable by any unprivileged holder of a previously signed order.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to already possess a validly signed order/message from a victim (obtained through normal exchange interaction, an abandoned/incomplete trade, or a counterparty in a payment-channel-like protocol) and simply delay submission of the trigger. No cryptographic break or privileged access is needed — only patience and knowledge that the signed message remains perpetually valid. The vulnerability is baked into the reference exchange template distributed with ocore, so any AA author following this pattern (a common and documented design for building exchanges/order books using `is_valid_signed_package`) inherits the flaw unless they manually add expiry logic, which the framework does nothing to prompt or enforce.

### Recommendation
- Add an explicit `expiry_ts` (or reuse the schema's optional `timestamp` field with defined semantics) to the signed-message payload convention, and require AA authors to check `timestamp < expiry_ts` (or `$order.expiry_ts > timestamp`) before honoring the order, replacing the `// to do check expiry` TODO with a real check.
- Consider hardening `signed_message.validateSignedMessage()` / `is_valid_signed_package()` to optionally enforce a caller-supplied max-age (e.g., bound the age of `last_ball_unit`'s timestamp relative to the trigger's `last_ball_timestamp`) so AA authors have a first-class, foolproof way to reject stale signed packages instead of relying on ad hoc application-level logic that is easy to forget (as evidenced by the shipped sample never having implemented it).
- Update ocore's official oscript documentation/samples (`order_book_exchange.oscript`) to include a correct expiry check as the canonical reference, since developers are likely to copy this exact template.

### Proof of Concept
1. Alice signs an order package: `{signed_message: {sell_asset: X, buy_asset: base, sell_amount: 1000, price: 0.001}, last_ball_unit: U, authors: [...]}` and sends it off-chain to a market maker/counterparty Bob for matching against the order-book-exchange AA (`test/samples/order_book_exchange.oscript`).
2. Bob does not immediately submit the matching trigger; he waits.
3. Market price of asset X moves significantly in Bob's favor relative to `price` embedded in Alice's signed order.
4. Bob crafts `order2` at the current (now favorable-to-him) price and submits `trigger.data = {order1: <Alice's old signed package>, order2: <Bob's fresh order>}` to the AA.
5. The AA's `if` condition validates both signatures via `is_valid_signed_package` (both pass — signatures are still valid, `last_ball_unit` is still a stable known unit) [1](#0-0) , and because the "to do check expiry" step was never implemented, the trade executes at Alice's stale price, transferring her assets at a rate she never would have agreed to at execution time [6](#0-5) .
