### Title
Signed order-book offers lack expiry/cancellation, allowing execution of stale orders - ([File: test/samples/order_book_exchange.oscript])

### Summary
The `order_book_exchange.oscript` autonomous-agent (AA) sample lets a user pre-sign an off-chain "order" (an offer to sell one asset for another at a fixed price) that anyone holding it can later post to the AA for execution via `is_valid_signed_package`. The order-matching branch of this AA never checks an expiry timestamp and provides no mechanism for the signer to revoke/cancel an outstanding order, exactly mirroring the "Lack of Loan Offer Management" issue: an offer, once signed, remains eternally executable at the terms it was created with, regardless of price/market changes or the signer's wish to withdraw it.

### Finding Description
In the order execution case of the AA, two signed packages (`trigger.data.order1` / `order2`) are decoded and their `signed_message` fields (`address`, `sell_asset`, `buy_asset`, `sell_amount`, `price`) are trusted as long as `is_valid_signed_package` returns true and the computed order id has not already been marked `executed_`: [1](#0-0) 

Critically, right after checking the compatibility of the two orders' asset pairs, the code contains only a comment acknowledging the missing check: [2](#0-1) 

No `trigger.data.orderN.signed_message.expiry` (or similar) field is ever referenced or compared against `timestamp`, and there is no state variable or trigger case allowing the signer to mark an order id as revoked/cancelled before it is (partially) filled. Order ids are derived purely from the signed content (`sha256($order.address || ... || $order.price || last_ball_unit)`), so the only way to invalidate a previously signed order is to fully consume it — something entirely under the counterparty's control, not the signer's.

This mirrors the reported Kairos issue: a lender-analog (order signer) commits to specific terms (`price`) via an off-chain signature, and the platform (the AA) has no operation for the signer to invalidate that signature once conditions change, while an unprivileged counterparty can present the stale signed order at any future point.

### Impact Explanation
Because deployed AA bytecode is immutable, once an order-signer's message circulates (e.g., leaked, or simply held after the signer no longer wants the trade), any unprivileged AA trigger sender can submit it as `order1`/`order2` to execute a trade at outdated pricing. If market prices for `sell_asset`/`buy_asset` have moved, the counterparty profits by forcing execution against the balance the signer deposited in the AA (`var[$sell_key]`), directly causing AA-held fund loss for the signer with no available recourse — matching the "unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
Likelihood is high in any deployment of this exact sample: signed orders are explicitly designed to be shared/broadcast for matching, so leakage or simple "stale offer" scenarios are the expected mode of operation, not an edge case. The missing expiry check is explicitly flagged by the developers' own `// to do check expiry` comment, confirming the gap was known but never implemented, and there is no compensating cancellation path in the `cases` array.

### Recommendation
- Add a mandatory `expiry`/`valid_until` field to the signed order payload and enforce `timestamp < $orderN.expiry` (or compare against `last_ball_unit`'s mci-derived time) before matching, removing the `// to do check expiry` stub.
- Add an explicit cancellation branch (e.g., `trigger.data.cancel_order` from `trigger.address == $order.address`) that marks the corresponding `executed_<id>` state variable as consumed, so a signer can invalidate an order id without needing a counterparty to fill it.

### Proof of Concept
1. Alice deposits `sell_asset` into the AA and signs an order (`price`, `sell_amount`, no expiry) intending it to be matched quickly.
2. Market price of `sell_asset` moves significantly in Alice's favor; Alice no longer wants to honor the old `price` and has no operation in the AA to cancel it (no `cases` branch, no expiry field checked at [3](#0-2) ).
3. Bob, who received/kept Alice's signed order, submits it months later as `order1` together with his own compatible `order2`.
4. `is_valid_signed_package` still validates the signature (it only checks cryptographic validity and, if present, `last_ball_unit` stability — not economic staleness) at [4](#0-3) , so the trade executes at Alice's stale price, debiting her AA balance (`var[$sell_key1]`) at [5](#0-4) , causing her a loss she had no way to prevent.
