### Title
Cross-repository commit status injection via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by SHA across the entire `commits` table, without restricting to the stacks of the repository named in the webhook payload, unlike `PushHandler#process` which correctly scopes via `stacks.not_archived.where(branch:)`. Because git commit SHAs are content-derived and identical across forks/shared history, and the Shipit webhook signature is validated per organization/App rather than per specific-commit ownership, an attacker who owns any repository whose events reach this Shipit instance can send a genuinely GitHub-signed `status` event referencing a SHA that also exists in an unrelated victim stack, causing Shipit to write a forged `Status` row onto that victim commit.

### Finding Description
The broken binding: `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`, and every handler's writes should equal `stacks-derived-from-payload.repository == mutated Stack/Commit rows`. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) honors this: `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
It never calls `stacks`, never uses `repository_name`/`payload['repository']`, and `params` schema (lines 7-18) doesn't require or validate a repository field at all. `Commit.where(sha:)` matches **any** commit row in the database with that SHA, regardless of which `Stack`/`Repository` it belongs to (`Commit belongs_to :stack`, `app/models/shipit/commit.rb:11`).

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) validates the signature via `Shipit.github(organization: repository_owner)` — i.e., it authenticates that the request came from *some* legitimate GitHub App installation tied to `repository_owner`, not that the referenced commit belongs to that owner's repositories. It provides no cross-repository/tenant isolation for the `sha` field.

Exploit flow: an attacker owns/forks a repository that shares commit history (and therefore SHAs) with a repository tracked as a Shipit stack (a common situation for public forks, or any repo history overlap), or otherwise learns a target commit SHA (SHAs are not secret — visible on GitHub UI, PR pages, CI logs). The attacker triggers or replays a genuine `status` event from GitHub for their own repository/commit (real GitHub-signed webhook, no secret needed), setting `state: "success"` (or `failure`) and an arbitrary `description`/`target_url`. Because `repository_owner` in `verify_signature` matches the attacker's own org (which is legitimately allowed to reach this Shipit instance via its own GitHub App/webhook integration), signature verification passes. `StatusHandler` then matches the SHA against the victim's `Commit` row and writes a forged status via `Commit#create_status_from_github!` → `statuses.replicate_from_github!` (`app/models/shipit/commit.rb:165-169`).

None of the existing guards catch this: `verify_signature` only proves "some legitimate GitHub sender," not repository ownership of the commit; the `ExplicitParameters` schema for `StatusHandler` has no repository/stack constraint; `drop_unhandled_event` only filters unregistered event types; `Repository`/`Stack` validators never run because no `Repository`/`Stack` lookup occurs in this code path at all.

### Impact Explanation
A forged commit status on an unrelated (victim) repository's commit is written by `Commit#create_status_from_github!`, which recomputes `Commit#status`/`deployable?` and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` (`app/models/shipit/commit.rb:379-386`). If the victim stack uses continuous deployment/merge automation gated on required statuses (`deployable?`, `schedule_continuous_delivery` in `app/models/shipit/commit.rb:281-287`), a forged "success" status can cause an unauthorized deploy or merge/rollback decision for a repository the attacker never authenticated against. This is a payload for one repository (attacker's) mutating another repository's `Commit`/`Stack` state, matching the Critical severity category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository whose webhooks are accepted by this Shipit instance (i.e., covered by a configured GitHub App/organization, which is the normal, low-cost situation for any SaaS-style multi-tenant install, or simply owning/forking any repo already connected), and (b) a commit SHA that also exists in the victim's tracked stack (achievable via forking shared history, or simply knowing a public SHA and getting a `status` webhook fired referencing it — status events can be produced by any CI/integration the attacker controls on their own repo/commit history). No Shipit session, API token, or secret is required — only a legitimately GitHub-signed webhook for the attacker's own org. This is repeatable against any commit SHA the attacker can discover or reproduce and is not dependent on privileged Shipit roles.

### Recommendation
Scope `StatusHandler#process` (and `Commit` lookup) to the repository named in the payload, mirroring `PushHandler`, e.g.:
```ruby
def process
  stacks.not_archived.find_each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restricts writes to commits belonging to stacks resolved from `Repository.from_github_repo_name(payload['repository'])`, closing the cross-tenant write.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create two `Shipit::Stack`s for two different repositories: `victim/repo` and `attacker/repo`.
2. Create a `Shipit::Commit` under the victim stack with `sha: "deadbeef..."` and no statuses.
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"` and `sha: "deadbeef..."` (the victim's commit SHA) and `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `victim_commit.reload.statuses.count == 1` and `victim_commit.status.state == "success"` — i.e., the attacker's payload for `attacker/repo` mutated the victim stack's commit, even though `Repository.from_github_repo_name("attacker/repo")` does not resolve to the victim's stack.
6. Contrast: build an analogous `push` payload with `repository.full_name = "attacker/repo"` and `ref`/`after` pointing at data resembling the victim stack's branch/sha; call `PushHandler.call(payload)`; assert no change occurs to the victim stack (since `stacks` resolves to `attacker/repo`'s stacks only, which is empty/unrelated), demonstrating the asymmetry.
