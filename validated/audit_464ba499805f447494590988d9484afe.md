### Title
Unchecked RAY share-value overflow permanently freezes a large accrued market - (File: common/src/rates/simulate.rs)

### Summary
High. Accrual converts scaled borrow and supply shares to their RAY-denominated underlying values before applying the borrow-index ceiling. Once `scaled_shares * index` exceeds `i128::MAX`, every market operation that syncs interest reverts with `MathOverflow`, permanently blocking repayment, withdrawal, liquidation, and later accrual.

### Finding Description
`accrue_step` calls `scaled_to_original` for `borrowed` and `supplied` before it calculates utilization or updates the borrow index. [1](#0-0)  The borrow-index cap is applied only inside `update_borrow_index`, after those pre-scale value calculations have already executed. [2](#0-1)  Consequently, `borrow_index < MAX_BORROW_INDEX_RAY` does not guarantee that `borrowed * borrow_index / RAY` remains representable in `i128`.

All pool mutations load the market through `synced_market`, which unconditionally runs `interest::global_sync` before the requested action. [3](#0-2)  The permissionless controller `update_indexes(caller, assets)` entrypoint also reaches the same accrual path. [4](#0-3)  The protocol's own regression test demonstrates the cliff: a one-billion-whole-token, 18-decimal market at 98% utilization eventually fails accrual while the stored borrow index is still below `MAX_BORROW_INDEX_RAY`. [5](#0-4) [6](#0-5) 

### Impact Explanation
This is permanent freezing of user funds and protocol insolvency risk. After the first `MathOverflow`, suppliers cannot withdraw and borrowers cannot repay because both paths accrue interest first; the test explicitly pins both failures. [7](#0-6)  Liquidation reaches the same accrual dependency, so distressed debt cannot be cleaned up through the normal liquidation path. Since the stored index remains below its intended cap, ordinary future calls repeat the overflowing value computation rather than entering the capped-index state. [6](#0-5) 

### Likelihood Explanation
An unprivileged caller can trigger the final condition through `update_indexes` once the market state is large and sufficiently accrued; no malformed binary payload or privileged trigger is required. [4](#0-3)  The practical precondition is severe: the proof uses one billion whole 18-decimal tokens supplied, 98% of them borrowed, sufficient external collateral, caps lifted to the asset-domain ceiling, and multiple years of high-rate accrual. [8](#0-7)  That makes the issue dependent on a very large listed market and sustained utilization, but the resulting failure is deterministic once the share-value product crosses `i128::MAX`.

### Recommendation
Bound scaled principal against the maximum future index, not merely the current index or token cap. In particular, enforce `scaled <= i128::MAX * RAY / MAX_BORROW_INDEX_RAY` for debt share minting and `scaled <= i128::MAX * RAY / MAX_SUPPLY_INDEX_RAY` for supply share minting, or widen `scaled_to_original` and all consumers to `I256` with explicit, non-panicking bounds. Index capping alone is insufficient because the vulnerable multiplication occurs before the cap check. Add a regression test equivalent to the existing whale-market cliff test and verify that repayment, withdrawal, liquidation, and accrual remain executable at the enforced boundary.

### Proof of Concept
The repository contains a harness PoC at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. Its effective sequence is:

```rust
// Listed 18-decimal market, caps lifted to max_cap_for_decimals(18).
supply(bob, account_id, spoke_id, [(BIG18, 1_000_000_000 * 10^18)]);
supply(alice, account_id, spoke_id, [(COL, 3_000_000_000 * 10^7)]);
borrow(alice, alice_account, [(BIG18, 980_000_000 * 10^18)], None);

// Advance ledger time until the next accrual computes an unrepresentable
// borrowed*borrow_index value.
update_indexes(keeper, [BIG18]); // -> MathOverflow

// All subsequent synced operations hit the same precondition.
withdraw(bob, bob_account, [(BIG18, 1)], None); // -> MathOverflow
repay(alice, alice_account, [(BIG18, 1)]);      // -> MathOverflow
```

The test then asserts that the stored `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, proving that the cap never engaged before the earlier share-value multiplication failed. [9](#0-8)
