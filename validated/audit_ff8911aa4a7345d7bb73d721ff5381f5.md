### Title
Webhook signature verification is bound to the wrong organization, letting one tenant forge commit-status / push events for another tenant's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an incoming webhook against using `repository_owner`, a field taken from the same attacker-controlled JSON body it is trying to authenticate. [1](#0-0)  The value used to authenticate the request (`repository.owner.login` / `organization.login`) is never reconciled with the value used later to decide which repository/stack/commit the event actually acts on (`repository.full_name`, or in the `status` event's case, nothing at all). [2](#0-1)  This breaks the intended binding: `organization that authenticated == repository that is written`.

### Finding Description
`verify_signature` derives the organization used to pick a `webhook_secret` purely from the JSON payload:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

and

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
``` [1](#0-0) 

`Shipit` supports multiple independently configured GitHub Apps/organizations sharing one instance, each with its own `webhook_secret`, as shown by the fixture `test/dummy/config/secrets_double_github_app.yml` (`OrgOne` / `OrgTwo`). An org admin who legitimately owns and configured a GitHub App (and therefore knows) `OrgOne`'s `webhook_secret` can craft an arbitrary raw POST body to `/webhooks` (this endpoint accepts any well-formed JSON, it is not restricted to genuine GitHub-originated traffic), sign it with `OrgOne`'s secret, and set `repository.owner.login = "OrgOne"` so `verify_signature` passes.

The actual event handlers, however, resolve their target independently of `repository_owner`:

- `Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a different, attacker-controlled field in the same body — to look up the `Repository`/`Stack` to operate on. [3](#0-2) 
- `StatusHandler#process` does not scope by repository at all: it queries `Commit.where(sha: params.sha)` globally across the entire Shipit instance and calls `commit.create_status_from_github!(params)`. [4](#0-3) 
- `PushHandler#process` resolves `stacks` via the forged `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA. [5](#0-4) 

Because none of these paths re-verify that the resolved repository/commit actually belongs to `repository_owner` (the organization whose secret validated the signature), an org that only controls its own GitHub App can forge events that mutate state belonging to a completely different, unprivileged-for-them organization/stack hosted on the same Shipit instance.

### Impact Explanation
Using `StatusHandler`, an attacker who only administers `OrgOne`'s GitHub App can forge a `status` webhook, sign it with `OrgOne`'s known `webhook_secret`, and set `sha` to any commit SHA that exists anywhere in Shipit's database — including commits belonging to `OrgTwo`'s stacks. This creates/overwrites a `Status` record (e.g. `state: "success"`) on that commit. [4](#0-3)  Since Shipit uses commit statuses to gate deployability, this can make an otherwise non-deployable commit on a foreign stack appear deployable/mergeable, which can lead to an unauthorized deploy on a stack/organization the attacker has no privileges on. `PushHandler` similarly lets the attacker force a `GithubSyncJob` on a foreign stack with an attacker-chosen `expected_head_sha`. [5](#0-4) 

### Likelihood Explanation
This requires only that the Shipit instance be multi-tenant (multiple orgs configured, as explicitly supported and exercised in the fixture `test/dummy/config/secrets_double_github_app.yml`) and that the attacker be a legitimate administrator/owner of one of those orgs' GitHub Apps — an "unprivileged attacker" with respect to the victim org. No access to the victim's secret, session, or `ApiClient` token is required; only knowledge of the attacker's own `webhook_secret`, which the person who configures a GitHub App for their own org would ordinarily possess.

### Recommendation
After successfully verifying the signature for `repository_owner`, re-derive the repository/organization that each handler operates on and assert it matches `repository_owner` (or the verified installation) before processing. In particular, `Handlers::Handler#repository_name` and `StatusHandler#process` should scope lookups by the authenticated organization, not solely by attacker-supplied `full_name`/`sha` fields.

### Proof of Concept
1. Shipit instance hosts two tenants, `OrgOne` (`webhook_secret_1`, attacker is the GitHub App admin) and `OrgTwo` (`webhook_secret_2`, victim, unrelated to attacker), per the `secrets_double_github_app.yml` multi-org pattern.
2. Attacker builds a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgOne/attacker-repo" },
  "sha": "<victim commit sha in OrgTwo's stack>",
  "state": "success",
  "context": "ci/build"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_1, body)>` using their own known `OrgOne` secret and POSTs it to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `OrgOne`'s `webhook_secret_1`, and the signature validates successfully. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `OrgTwo`, and marks it with a forged `success` status, unconstrained by the fact the signature only proved control of `OrgOne`. [4](#0-3)
