### Title
Unallowlisted route venues can add arbitrary token transfers to a swap caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
High. A user-supplied router payload can place attacker-controlled pool code inside the authorization scope of `swap_collateral`, and simulated authorization can consequently include token transfers unrelated to the collateral swap. If the account owner signs the simulated tree, the route can drain unrelated wallet tokens while still satisfying the controller’s measured-input, measured-output, and final-risk checks. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` authenticates the caller and verifies ownership or delegation, then withdraws collateral into the controller and passes the caller-supplied `swap` bytes into `swap_tokens`. [3](#0-2) [4](#0-3) 

`swap_tokens` only constrains the controller-side grant to one exact `token_in.transfer(controller, router, amount_in)` invocation; it does not constrain which contract addresses the payload causes the router to invoke. [1](#0-0)  The subsequent checks bound only the controller’s input spend and require a positive controller output delta. [5](#0-4) 

The route payload selects venue pool addresses, and venue dispatch calls the selected pool through the venue adapter. [6](#0-5) [7](#0-6)  Because no allowlist binds that address to a known pool implementation, its `swap` function can execute unrelated token calls before returning a commercially valid output. [8](#0-7) [9](#0-8) 

Soroban simulation records that unrelated `token.transfer(victim, attacker, amount)` under the victim’s root `swap_collateral` authorization entry. [10](#0-9)  In enforcing authorization mode, the same transfer succeeds when the simulated child invocation is signed and is rejected only when it is omitted. [11](#0-10) 

### Impact Explanation
An attacker can steal arbitrary tokens held directly by a swap user, including tokens that are not listed by the lending protocol and are outside the routed `amount_in`. [12](#0-11) [13](#0-12) 

The malicious pool can still return enough `token_out` to satisfy the router minimum and the controller’s positive measured-output check, so neither the route minimum nor the final account-risk check bounds the unrelated wallet loss. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
The attacker does not need a privileged role, leaked key, protocol upgrade, oracle manipulation, or control of the lending account. [3](#0-2)  The attacker supplies a route that references an attacker-deployed pool address and returns enough output to pass settlement. [16](#0-15) 

Execution requires the victim to submit and sign the authorization tree produced for that route. [17](#0-16)  The malicious transfer is visible in a correctly inspected authorization tree, so careful manual inspection or a client that rejects unexpected children prevents this variant; the protocol nevertheless permits the dangerous route shape rather than enforcing a venue allowlist on-chain. [11](#0-10) 

### Recommendation
Bind every route hop’s venue and pool address to an on-chain registry or allowlist of reviewed pool contracts before dispatch, rather than trusting an arbitrary address in the caller-supplied `assets` registry. [18](#0-17) 

Until venue addresses are constrained, clients must simulate every strategy transaction, decode the complete authorization tree, and reject any child invocation other than the expected input-token transfer. [17](#0-16) [19](#0-18) 

### Proof of Concept
1. Alice owns a debt-free lending account holding 10,000 USDC and also holds `WALLET_BALANCE` of an unrelated token that the protocol never listed. [20](#0-19) 

2. The attacker deploys a pool contract whose `swap` function calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [21](#0-20) 

3. The attacker constructs route bytes naming that contract as the hop pool, with USDC as input and ETH as output, and a normal positive minimum output. [16](#0-15) 

4. Alice invokes `swap_collateral(alice, account_id, USDC, 5_000 USDC, ETH, route)`. [22](#0-21) 

5. Simulation records the unrelated wallet-token transfer as a child of Alice’s `swap_collateral` authorization. [10](#0-9) 

6. When Alice signs that simulated tree, the unrelated token moves to the attacker and the protocol-side swap still completes: Alice’s wallet balance becomes zero, the attacker receives `WALLET_BALANCE`, and Alice’s account receives the fair ETH output. [23](#0-22) [13](#0-12)
