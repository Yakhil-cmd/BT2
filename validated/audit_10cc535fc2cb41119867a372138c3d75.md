Confirmed: the `provision?` method has a Ruby operator-precedence bug where `&&` binds tighter than `||`, so `review_stacks_enabled` only scopes the `allow_all` branch of the boolean expression.### Title
`provision?` operator-precedence bug lets `allow_with_label`/`prevent_with_label` bypass `review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` uses Ruby's `&&`/`||` precedence such that `repository.review_stacks_enabled` only gates the `allow_all` branch of the expression, not the `allow_with_label` or `prevent_with_label` branches. As a result, a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` will still provision a review stack whenever an opened PR carries the configured label, and `prevent_with_label` repositories will provision unless the label is present, both independent of `review_stacks_enabled`.

### Finding Description
The intended binding is: `review_stacks_enabled == true` is the single authorization gate that must hold for `provision?` to ever return `true`; `provisioning_behavior` only refines *which* PRs get provisioned once stacks are enabled.

The actual code: [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
```
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
`review_stacks_enabled` is only ANDed into the first disjunct (`allow_all`). The second and third disjuncts (`allow_with_label`, `prevent_with_label`) never reference `review_stacks_enabled` at all, so they evaluate purely from `provisioning_behavior` and the PR's labels.

Reachable path: `process` calls `respond_to_pull_request_opened?` which calls `provision?` directly, gating whether a `ReviewStack` gets created via `ReviewStackAdapter#find_or_create!`. [2](#0-1) 

`pull_request_has_provisioning_label?` just checks whether any label name in the webhook payload matches `repository.provisioning_label_name`: [3](#0-2) 

Exploit flow: an operator sets `review_stacks_enabled: false` (explicitly disabling dynamic provisioning) but leaves `provisioning_behavior` at `allow_with_label` (or `prevent_with_label`) with some `provisioning_label_name` configured, e.g. `'deploy-pr'`. A PR author with the ability to attach a label matching that name to their own PR (per the threat model's granted capability) opens a PR carrying that label. GitHub emits a signed `pull_request` `opened` webhook (a genuine, correctly-signed event, since the attacker is a real actor performing real GitHub actions on the repository — `verify_signature`/`GitHubApp#verify_webhook_signature` are satisfied because this is not a forged webhook, just a legitimately triggered one) [4](#0-3) 
. `provision?` evaluates the second disjunct to `true` regardless of `review_stacks_enabled`, and a `ReviewStack` row is created.

None of the existing guards intercept this: `verify_signature` only authenticates that the payload genuinely came from GitHub for that repo/org, it says nothing about the `review_stacks_enabled` policy; the `ExplicitParameters` schema only validates payload shape; there is no additional authorization check tying `provisioning_behavior` evaluation to `review_stacks_enabled`.

### Impact Explanation
This causes unauthorized `Shipit::Stack`/`ReviewStack` record creation, and downstream provisioning-handler invocation (`ReviewStackProvisioningQueue`/`ProvisioningHandler#up`), for a repository whose operator explicitly turned dynamic stack provisioning off. This is repeatable on any repository configured this way and does not require any secret or elevated Shipit/GitHub permission beyond the PR/label action itself. It breaks the operator's intended authorization boundary (`review_stacks_enabled` as the master switch) — matching the "a record written for a repository that did not authenticate it" impact class, i.e. unauthorized stack creation despite the repository owner having disabled the feature.

### Likelihood Explanation
Preconditions: repository must have `review_stacks_enabled: false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible/likely misconfiguration, since these two settings are independent form fields on the repository settings page) [5](#0-4) 
. The attacker only needs to open a PR and (per the given threat model) attach/omit the configured label — no Shipit credentials, no GitHub App secret, no webhook forgery required. This is a pure logic bug, deterministically reproducible.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to the equivalent expressions in `LabeledHandler#archive?`/`unarchive?` and `ReopenedHandler#unarchive?` if they have the same pattern (worth auditing, though `LabeledHandler#respond_to_label_change?` does explicitly AND `repository.review_stacks_enabled` at the top level, which does not have this bug) [6](#0-5) 
, but `ReopenedHandler#unarchive?` has the identical pattern and should be checked/fixed too [7](#0-6) 
.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style):
```ruby
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label and matching label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "deploy-pr"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "deploy-pr" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding to assert: `repository.review_stacks_enabled` (false) should equal the actual gating condition for provisioning (i.e., `provision?` should be `false` whenever `review_stacks_enabled` is `false`, independent of `provisioning_behavior`). Currently `Shipit::Stack.count` changes (a stack IS created), proving `provision?` returns `true` despite `review_stacks_enabled == false`, i.e. the binding fails.
