## Title
AA price-dependent logic can be driven by a single most-recently-posted oracle value instead of a consensus/median across multiple configured oracles - (File: `data_feeds.js`)

### Summary
The external report concerns Compound's Open Oracle, which derives a "safe" price from the *median* of several independently reported values so that no single reporter can move the price and so that sudden, extreme price swings are dampened until a majority of sources agree. In ocore, Autonomous Agents (AAs) can query price data via the `data_feed[[...]]` oscript primitive with a colon-separated list of trusted `oracles`, which superficially resembles a multi-source design. However, the underlying implementation does not compute any median, average, or standard deviation across the listed oracles — it simply selects the single most recently-posted (highest MCI/level) value among all of them, so one oracle can unilaterally determine the feed value used by fund-moving AA logic, exactly the failure mode the report warns about, but without even the "50% of sources" resistance that Open Oracle provides.

### Finding Description
`data_feed[[oracles="addr1:addr2:...", feed_name=...]]` is evaluated in `formula/evaluation.js`'s `getDataFeed()` (`formula/evaluation.js:602-664`), which forwards to `dataFeeds.readDataFeedValue()`: [1](#0-0) 

`readDataFeedValue()` (`data_feeds.js:205-285`) iterates over `arrAddresses` — the list of oracle addresses supplied by the AA author — and for each address calls `readDataFeedByAddress()`, threading a shared `objResult` through the calls: [2](#0-1) 

Inside `readDataFeedByAddress()` (`data_feeds.js:287-339`), the selection logic is purely recency-based: the candidate replaces the previous result whenever no value has been set yet, or (for the default `ifseveral='last'` mode) whenever its MCI is greater than the currently stored one: [3](#0-2) 

The unstable-message fast path exhibits the same behavior: multiple candidate values from different oracle addresses are collected and then sorted purely by `latest_included_mc_index`/`level`, and the single most recent one is returned: [4](#0-3) 

At no point are the individual values from the different oracles compared against each other, averaged, or evaluated for dispersion (median/standard deviation). The only alternative mode, `ifseveral='abort'`, does not resolve this either — it simply causes the AA to bounce entirely if any two oracles disagree (`data_feeds.js:249-254` / `parameter validation in formula/validation.js:64-66`), so contract authors cannot obtain any statistically robust aggregate; they can only pick "trust whichever value is newest" or "abort on any disagreement." Real-world contracts in this codebase's own test corpus rely on exactly this multi-oracle-price pattern for financial decisions (e.g. the `GBYTE_USD_MA` / blackswan example in `test/ojson.test.js:1038-1091`, which uses a `data_feed[[...]]` value directly to size a bytes-for-asset exchange).

### Impact Explanation
An AA author who lists multiple trusted oracle addresses expecting Open-Oracle-style resilience (i.e., that no single source can move the price, and that the reported value reflects a consensus) actually gets none of that protection: whichever configured oracle happens to post the newest value — whether due to being compromised, buggy, unusually fast during network congestion, or simply racing ahead during a volatile market — solely determines the price used by the AA's payment/exchange logic. During the exact "sudden, extreme price variation" scenario the external report describes, this lets a single oracle (malicious or merely fast/erroneous) cause the AA to execute payments, exchanges, or collateral/liquidation logic against a stale or unrepresentative price, resulting in AA fund loss for one counterparty and unwarranted gain for another, i.e., unauthorized value transfer through legitimate-looking contract execution.

### Likelihood Explanation
This is triggered by entirely ordinary, permitted usage: any AA that references `data_feed[[oracles="A:B:C", ...]]` with the default `ifseveral='last'` is affected without any special crafting, and any of the listed oracle operators (or an attacker who compromises just one of them) can win the race merely by posting a data-feed unit with a higher MCI than the others, which requires no protocol violation. No consensus among a majority of oracles is needed, unlike the median-based design the report recommends.

### Recommendation
For AAs relying on multiple oracle addresses via `data_feed[[...]]`, provide (or document the need for AA authors to implement in oscript) an aggregation mode that computes the median (and ideally dispersion, e.g., interquartile range or standard deviation) of the values reported by all listed oracles within the applicable MCI window, rather than defaulting to "most recent value wins." At minimum, update documentation to make clear that `oracles="A:B:C"` does not provide median-based safety and that contract authors must implement their own quorum/median logic in oscript (e.g., by reading each oracle individually and computing `median()`/`avg()` themselves) if resilience to a single misbehaving or lagging oracle is required.

### Proof of Concept
1. Deploy an AA whose `if`/`bounce` payment amount depends on `data_feed[[oracles="ORACLE_A:ORACLE_B", feed_name="PRICE"]]` with default `ifseveral='last'`, as in the pattern from `test/ojson.test.js:1069` (`$exchange_rate = data_feed[[oracles=..., feed_name=...]]`).
2. `ORACLE_A` and `ORACLE_B` both regularly post the same true market price, kept in sync under normal conditions.
3. During a sudden market move, have `ORACLE_B` (compromised, buggy, or merely first to react) post a unit with a stale/incorrect `PRICE` value at a higher MCI than `ORACLE_A`'s latest post.
4. Per `readDataFeedByAddress`'s recency comparison (`data_feeds.js:318`) or the unstable-candidate sort (`data_feeds.js:255-267`), the AA's `data_feed[[...]]` call resolves to `ORACLE_B`'s value even though `ORACLE_A` (equally trusted) never agreed with it — no median or 50%-agreement check is performed — allowing an attacker who triggers the AA at that moment to extract funds at the stale/incorrect exchange rate.
