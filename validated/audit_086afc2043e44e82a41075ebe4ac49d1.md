The premise doesn't hold up as a security issue. `native_scalar_from_u64` and `native_scalar_from_u128` in `aptos-move/framework/natives/src/cryptography/ristretto255_scalar.rs` simply call `Scalar::from(num)` on strongly-typed Move arguments (`u64` or `u128` respectively) and return the canonical 32-byte little-endian encoding via `s.to_bytes()`. [1](#0-0) 

Producing identical byte encodings for the same numeric value (e.g., `5u64` and `5u128`) is the mathematically correct and expected behavior of a canonical scalar field encoding — it is not "type confusion." A `Scalar` in Move is just a wrapper struct around a `vector<u8>` (its `data` field), with no embedded type tag distinguishing "came from u64" vs "came from u128": [2](#0-1) 

The Move-level entry points `new_scalar_from_u64` and `new_scalar_from_u128` are separate, explicitly-typed public functions; the Move type system (not the byte encoding) is what enforces which conversion path a caller invokes, and any caller wanting a `u64`-bound value must explicitly call the `u64` variant — nothing lets an attacker "substitute" a u128-encoded scalar for a u64-encoded one at a type level, since Move's type checker distinguishes `u64` and `u128` arguments at the call site, before any native execution occurs. [3](#0-2)
