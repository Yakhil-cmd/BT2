### Title
Stable LP collateral is priced at the cheaper underlying leg, enabling discounted liquidation seizures - (File: common/src/oracle/lp_stable.rs)

### Summary
`fair_stable_lp_price_wad` prices an Aquarius stable-LP share as `D * min(price_a, price_b) / total_shares`, so every unit of the more valuable reserve is valued at the cheaper token’s price. [1](#0-0)  The controller uses that oracle price both to determine whether an account is liquidatable and to convert a USD seizure allowance back into LP-token quantity. [2](#0-1) [3](#0-2)  As a result, a liquidator can receive LP tokens whose true underlying value exceeds the protocol-priced repayment plus intended bonus. [4](#0-3) 

### Finding Description
The Aquarius provider resolves both underlying oracle prices and then dispatches stable pools to `fair_stable_lp_price_wad`. [5](#0-4)  For stable pools, the code solves the StableSwap invariant `D`, selects `a.price_wad.min(b.price_wad)`, and returns `D * min_price / share_supply`. [1](#0-0) 

This reproduces the vulnerable “all reserves are worth the cheaper asset” valuation pattern. [6](#0-5)  If one underlying token trades even slightly above the other, the LP oracle output is below the LP token’s redemption value. [6](#0-5) 

The affected stable-LP asset is deployed as collateral-only market `xSolvBTCSolvBTC_LP` with `can_be_collateral: true`, `can_be_borrowed: false`, LTV 50%, and liquidation threshold 60%. [7](#0-6)  Its oracle is configured as `AquariusStableLp`, with one leg keyed to `xSolvBTC` and the other to `SolvBTC`. [8](#0-7) 

### Impact Explanation
An unprivileged liquidator can call `liquidate(liquidator, account_id, debt_payments, SeizeMode::Transfer)` and receive LP collateral at the understated oracle valuation. [9](#0-8)  During seizure, `calculate_seized_collateral` computes a USD amount from `repay_usd * (1 + bonus)` and divides it by `feed.price`; a smaller `feed.price` therefore produces a larger LP-token seizure. [4](#0-3) 

The discrepancy is directly redeemable through the underlying pool: seized LP shares represent claims on both reserves, including the reserve priced above the oracle’s selected minimum. [10](#0-9)  This transfers borrower collateral value to the liquidator beyond the configured liquidation bonus and can prematurely push LP-backed accounts below `HF = 1`. [11](#0-10) [2](#0-1) 

### Likelihood Explanation
The trigger is an ordinary price difference between the two LP legs; no oracle manipulation, privileged role, or invalid configuration is required. [1](#0-0)  Stable pairs routinely have small deviations from exact parity, and the deployed `xSolvBTC/SolvBTC` market makes this path reachable on a live collateral asset. [12](#0-11) [7](#0-6) 

The liquidation path is permissionless after `liquidator.require_auth()` and only requires the target account to have `health_factor < Wad::ONE`. [13](#0-12) [2](#0-1)  Because the undervaluation also lowers collateral and health factor, a smaller leg-price spread can create the liquidation opportunity itself for accounts near the threshold. [11](#0-10) 

### Recommendation
Do not multiply the whole StableSwap `D` by the minimum leg price when deriving collateral value for both health and liquidation. [1](#0-0)  Use a valuation that accounts for the expected redemption amounts and each leg’s own oracle price, while retaining conservative invariant-based protection against reserve manipulation. [10](#0-9) 

If the protocol intentionally wants a lower-bound collateral oracle, use a separate explicit lower-bound feed for borrow/LTV decisions while liquidation seizure uses fair redemption value; otherwise liquidators are paid in undervalued LP units and capture the spread. [4](#0-3) 

### Proof of Concept
Consider the deployed-style stable LP pool with `1,000,000` LP shares, `1,000,000` units of token A, `1,000,000` units of token B, oracle prices `A = $0.99` and `B = $1.00`, and a highly amplified stable invariant where `D ≈ 2,000,000`. [1](#0-0) 

`fair_stable_lp_price_wad` returns approximately `D * 0.99 / 1,000,000 = $1.98`, while redemption of one LP share is worth approximately `(0.99 * 1 + 1.00 * 1) = $1.99`. [14](#0-13) 

A borrower supplies `10,000` of those LP shares and has debt with risk value `D_debt = $5,950`; at fair value `C = $19,900`, threshold 60% gives `W = $11,940`, so `HF ≈ 2.006`, while at oracle value `C' = $19,800`, `W' = $11,880`, and `HF' ≈ 1.997`. [11](#0-10)  For an account closer to the boundary—e.g. true weighted collateral `$10,020` against debt `$10,000`—a 1% undervaluation reduces weighted collateral to about `$9,919.8`, making `HF < 1` and opening `liquidate`. [2](#0-1) 

The liquidator then calls `liquidate(attacker, victim_account_id, [(debt_hub_asset, payment)], SeizeMode::Transfer)`. [9](#0-8)  For every `$1.00` of planned seizure value before fees and bonus, the seizure calculation divides by `$1.98` instead of `$1.99`, awarding about `0.50505` LP shares instead of `0.50251`, a roughly `0.505%` excess before liquidation bonus effects. [4](#0-3)  The liquidator redeems or sells the extra LP shares for their underlying value, leaving the borrower with less collateral than intended for the debt repaid. [15](#0-14)
