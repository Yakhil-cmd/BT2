### Title
Post-validation mutation of `output_data_receivers` allows receipts to exceed `max_receipt_size` - ([File: core/primitives/src/receipt.rs, runtime/runtime/src/lib.rs])

### Summary
The runtime validates a newly created action receipt's encoded size against `max_receipt_size` before the receipt is finalized, but `output_data_receivers` (populated in response to `promise_return`/DAG-linking logic in the runtime, e.g. `runtime/runtime/src/lib.rs`) is appended after that validation point, allowing a receipt to grow past `max_receipt_size` post-validation. This is a known, already-tracked bug (referenced directly in the repo).

### Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` checks `borsh::object_length(receipt)` against `limit_config.max_receipt_size` and rejects with `ReceiptValidationError::ReceiptSizeExceeded` only under `ValidateReceiptMode::NewReceipt` [1](#0-0) . However, the codebase itself documents that a function call can produce a receipt whose `output_data_receivers` field is mutated *after* this validation, growing the encoded receipt beyond `max_receipt_size`, and that "runtime has to handle them gracefully until the receipt size limit bug is fixed" per a tracked upstream issue [2](#0-1) .

This is not speculative — there is an existing integration test, `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs`, that explicitly constructs this scenario: a receipt is created at exactly `max_receipt_size`, then a `promise_return` triggers appending to `output_data_receivers`, pushing the receipt over the limit. The test comment states plainly that "the receipt should be rejected, but currently isn't because of a bug" [3](#0-2) . The test asserts (via `assert_oversized_receipt_occurred`) that an oversized receipt does in fact appear on-chain [4](#0-3) [5](#0-4) .

An attacker (unprivileged contract caller) can reach this by:
1. Deploying a contract and calling a method that creates promise A, then promise B depending on A (`.then`), so a receipt for A is created and validated near `max_receipt_size`.
2. Inside promise A's execution, creating promise C and calling `promise_return`, which causes the DAG to rewire (`C ->then-> B`), pushing a `DataReceiver` into `output_data_receivers` of receipt C *after* the initial size check already validated it near the limit.
3. The resulting receipt C exceeds `max_receipt_size` and is still accepted and propagated instead of failing.

The `receipt_size`/`compute_receipt_size` functions in `runtime/runtime/src/congestion_control.rs` are used for congestion accounting elsewhere and rely on the same `borsh::object_length` invariant that receipt sizes are bounded [6](#0-5) , so an oversized receipt slipping past `validate_receipt` breaks size-based invariants used for gas/congestion charging and `ChunkStateWitness` size budgeting documented in `docs/misc/state_witness_size_limits.md` (design assumes ≤4 MiB receipts) [7](#0-6) .

### Impact Explanation
This matches the described "High" impact: an attacker can produce receipts that exceed the enforced `max_receipt_size` bound after passing the size check, undermining the invariant that receipt size is bounded and charged. Oversized receipts inflate chunk/witness size beyond the assumed ~17 MiB budget the protocol relies on (`docs/misc/state_witness_size_limits.md`), and can be used to increase computational/storage/bandwidth cost on chunk producers/validators without correspondingly higher gas charges, since the size-dependent cost/charging model assumes the enforced cap. It does not appear to directly cause fund loss or unauthorized actions, but it is a metering/limit-bypass issue with network-wide resource cost implications.

### Likelihood Explanation
High feasibility and reproducibility: this is not a hypothetical path — the repository ships a dedicated regression test (`test_max_receipt_size_promise_return`) that reproduces exactly this bug and references a tracked GitHub issue (near/nearcore#12606) explicitly acknowledging "there is a bug which allows to create receipts that are above the size limit" [8](#0-7) . Any unprivileged account with the ability to deploy and call a contract using standard `promise_batch_action_*`/`promise_then`/`promise_return` host calls can trigger it; no privileged access is required.

### Recommendation
Re-validate (or re-check `max_receipt_size`) after all post-creation mutations to a receipt's `output_data_receivers` — specifically after the DAG-rewiring/`promise_return` logic in `runtime/runtime/src/lib.rs` appends `DataReceiver`s — before the receipt is committed to the outgoing receipts set. Alternatively, compute the worst-case size contribution of `output_data_receivers` before generating the child receipts so the initial `validate_receipt` call accounts for it, closing the gap between the size check and the final encoded receipt used downstream in congestion/gas accounting and state-witness size budgeting. This is already tracked upstream as near/nearcore#12606 and should be fixed as part of a protocol version change with corresponding size-limit test coverage in `test-loop-tests/src/tests/max_receipt_size.rs`.

### Proof of Concept
The existing test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` is a working PoC: it deploys `near_test_contracts::rs_contract()`, calls `max_receipt_size_promise_return_method1` with `args_size` calculated so the initial receipt template is exactly `max_receipt_size` (4_194_304 bytes), then asserts (`assert_oversized_receipt_occurred`) that a receipt exceeding `max_receipt_size` is found among on-chain incoming receipts [9](#0-8) . Expected/observed result per the test comments: the runtime does not reject the oversized receipt (bug), though it also should not crash — assert balance/gas totals remain consistent via existing sanity checks in `runtime/runtime/src/tests/apply.rs`, and add an assertion there mirroring `receipt_is_oversized` to fail CI once the size-check ordering bug is present.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
