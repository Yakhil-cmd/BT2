### Title
Asset definer can unilaterally rotate the attestor list of a `spender_attested` asset, freezing funds held by previously-attested holders - (File: validation.js, storage.js)

### Summary
For assets defined with `spender_attested: true`, spendability of every coin depends on the *current* (latest) attestor list, not the list that was in effect when the holder was attested. The asset definer can post an `asset_attestors` message at any time, single-handedly replacing the attestor set, with no check on outstanding balances held by addresses that were only attested under the old list. Just like `Vault.blacklistProtocol()` mutates critical accounting state (`currentAllocations`) without confirming that all affected funds remain reachable, `asset_attestors` mutates the attestor list without confirming that holders of the asset are still (or newly) attested — freezing their coins.

### Finding Description
An asset's attestor list can be updated with a single-authored `asset_attestors` message, validated by `validateAttestorListUpdate`, which only checks that the sender is the asset's definer and that the new attestor set is well-formed — it performs no check of who currently holds the asset or whether they remain attested: [1](#0-0) 

When reading an asset, only the *latest* attestor list unit is used to populate `arrAttestorAddresses`, discarding all older lists: [2](#0-1) 

Attested-holder status is likewise computed strictly against this current list via `filterAttestedAddresses`: [3](#0-2) 

Both spending (input owner) and receiving (output owner) validation for such assets require presence in the current attestor-derived list, with no fallback to the list that was active when the address was originally attested: [4](#0-3) [5](#0-4) 

Consequently, if the definer swaps out an attestor (e.g., replaces attestor A with attestor B) after some holders were attested only by A, any output owned by those holders permanently fails `objAsset.spender_attested && arrAttestedAddresses.indexOf(owner_address) === -1` → `"owner address is not attested"`, freezing their balance of the asset until/unless they are re-attested by a currently-listed attestor. There is no mechanism in `blacklistProtocol`-style guardrails (e.g., requiring old attestations to remain valid for a grace period, or requiring the definer to prove all current holders are attested before rotating the list) — mirroring the missing "full withdrawal control" and missing consideration of currently-locked funds in the Derby Vault bug.

### Impact Explanation
Any holder of a `spender_attested` asset whose only qualifying attestation came from an attestor that is later dropped from the list becomes permanently unable to spend (or receive further transfers of) that asset — their funds are frozen at the protocol level with no code path to recover them short of the definer/attestor voluntarily re-attesting the holder off-chain. Because this is driven purely by definer discretion and normal identity/attestor rotation (a legitimate, expected operation for compliance/KYC-style assets), it can happen inadvertently or be used to intentionally lock out specific holders, constituting an AA/asset fund-freezing vulnerability of Medium/High severity depending on asset value at stake.

### Likelihood Explanation
This requires no exploit — it is a normal, single-authored, protocol-supported action (`asset_attestors`) that any asset definer routinely performs to update attestors (e.g., attestor rotation, decommissioning a compromised attestor, compliance updates). Any asset issuer using `spender_attested` and any of its user base are exposed whenever attestors are rotated without pre-verifying/re-issuing attestations for existing holders — a scenario with clear real-world likelihood since attestor rotation is an intended feature, not an edge case.

### Recommendation
When validating or applying an `asset_attestors` update, consider not immediately invalidating attestations issued under superseded attestor lists (e.g., keep prior attestations valid for held/pending balances, or require the definer to bundle re-attestation for known non-zero holders before the rotation is accepted). Alternatively, decouple "attested to receive/spend" from "get the coin", e.g., mark existing outputs as validated by the attestor list they were created under (record the attestor-list unit at output creation time and check spending against that same list-lineage) rather than only the current global list, so that changing attestors going forward cannot retroactively freeze already-held balances.

### Proof of Concept
1. Definer D issues asset X with `spender_attested: true` and posts an initial `asset_attestors` message naming attestor A.
2. Attestor A attests holder H (`attestation` message with `attestor_address = A`, `address = H`).
3. D sends/H receives some units of asset X to H — accepted because H is attested by A, the current attestor.
4. D later posts a new `asset_attestors` message for asset X naming only attestor B (dropping A). This passes `validateAttestorListUpdate` since only definer authorship and attestor-list well-formedness are checked (`validation.js:2829-2848`).
5. `storage.readAsset` now resolves `arrAttestorAddresses = [B]` for asset X (`storage.js:1917-1946`).
6. H, still holding units of X, attempts to spend them. `filterAttestedAddresses` finds no attestation of H by B (`storage.js:1960-1974`), so validation of the payment fails with `"owner address is not attested"` (`validation.js:2504-2507`) — H's funds in asset X are now frozen, with no way to spend them unless B (or a newly listed attestor) independently chooses to attest H.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\

			0)",
