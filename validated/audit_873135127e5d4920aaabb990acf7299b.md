### Title
StatusHandler#process resolves commits by `sha` alone, letting an attacker-controlled repository forge `Commit#state` for another tenant's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filter on the originating `repository.full_name`. Every other handler (`PushHandler`, `CheckSuiteHandler`) scopes its lookups through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` before touching any commit/stack; `StatusHandler` never calls `stacks` or `repository_name` at all.

### Finding Description
The binding that should hold is: `commit.state` for stack `S` == `f(Status rows whose originating payload repository.full_name == S.repository.full_name)`. In `StatusHandler`, that binding is broken because commit resolution is by SHA only: [1](#0-0) 

Compare with `Handler#stacks`, which every other handler uses to scope by the webhook's own `repository.full_name`: [2](#0-1) 

and `PushHandler`/`CheckSuiteHandler`, which both go through `stacks` before touching any commit: [3](#0-2) [4](#0-3) 

`commit.create_status_from_github!` creates a `Status` scoped to `commit.stack_id` (the real owner of the matched `Commit` row), but the *state/description/context* values come straight from the attacker's payload: [5](#0-4) [6](#0-5) 

`Commit#state` is delegated straight to the latest/most severe `Status`: [7](#0-6) 

Guard analysis: `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the *attacker's own* GitHub App/organization signed the payload with the correct HMAC secret for `repository_owner` derived from that same payload — it never ties the signature to the specific commit/repository being mutated. It correctly authenticates "this webhook really came from GitHub for org X," but does nothing to prevent org X's webhook from mutating a `Commit` that belongs to org Y's stack, because `StatusHandler#process` never consults `repository_name`/`stacks`. `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership. No model validation ties `Status#stack_id` back to the payload's repository, since `stack_id` is derived from `commit.stack_id` — a value already looked up from an unscoped `Commit.where(sha:)` query.

Exploit flow: an attacker who controls a public GitHub repository can reproduce the exact SHA-1 of any git commit whose full content (tree, parent, author/committer identities and timestamps, message) is known — trivial if the victim stack's commit is visible on GitHub/Shipit (a precondition already granted). They commit identical content in their own repo, causing GitHub to legitimately deliver a signed `status` webhook to Shipit for the attacker's own repository/organization, with `sha` equal to the victim's commit SHA and an attacker-chosen `state` (`success` or `failure`). This webhook passes `verify_signature` because it is a genuine GitHub webhook for the attacker's own org. `StatusHandler#process` then matches `Commit.where(sha: params.sha)` across **all** stacks in the database — including the victim's row for that SHA — and calls `create_status_from_github!`, which writes a new `Status` under the victim stack's `stack_id` with the attacker-chosen state, description, and context. `Commit#state` for the victim's stack now reflects the forged value.

### Impact Explanation
A record (`Status`) is written for a repository/stack that never authenticated the mutation, directly matching the "Critical" category: "a payload for one repository mutating another's stack, commit ... " `Commit#state` drives `deployable?`/`blocked?` and the publicly displayed CI status on the victim's Shipit dashboard, so this can be used to falsely mark a competitor's commit green (enabling/encouraging an unwarranted deploy decision by the victim's own operators) or to grief them with a forged failure that blocks deploys. This is repeatable against any stack/commit whose SHA the attacker can reproduce, and is not limited to a single victim — any tenant sharing the Shipit instance is exposed.

### Likelihood Explanation
Preconditions: the attacker needs an ordinary GitHub account able to create a public repository and push a commit (no Shipit session, token, or secret required, matching the stated attacker model), and needs to know the exact byte-for-byte content of the victim's target commit (tree, parents, author/committer identity+timestamp, message) — knowable when the victim's commit/repo is publicly visible, which the prompt establishes as an existing precondition. Reproducing an identical git commit hash from known content is a standard, well-documented technique (not a hash preimage attack — it is exact content replication), so attacker cost is low and the action is repeatable at will for any commit SHA the attacker can reconstruct.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the same repository-derived `stacks` relation used by other handlers, e.g. resolve `stacks` (or `Repository.from_github_repo_name(repository_name)`) first and only update commits belonging to those stacks: `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join `Commit` to `Stack`/`Repository` and filter by `repository_name` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (no live GitHub, using existing fixtures/handler classes):
1. Create two stacks `stack_a` (repository `owner/repo-a`) and `stack_b` (repository `owner/repo-b`) with commits sharing the same `sha` value (e.g. `"deadbeef" * 5`).
2. Assert baseline: `assert_not_equal 'success', commit_b.reload.state` (or whatever initial state is set for `stack_b`'s commit).
3. Build a `status` webhook payload naming `repository.full_name = 'owner/repo-a'`, `sha` equal to the shared SHA, `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature checks, since those are irrelevant to this binding).
5. Assert the binding violation: `assert_equal 'success', commit_b.reload.state` even though the payload's `repository.full_name` (`owner/repo-a`) never matches `stack_b`'s repository (`owner/repo-b`) — proving `commit_b`'s state changed as a side effect of a webhook that never named its repository.
