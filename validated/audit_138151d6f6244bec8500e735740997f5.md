### Title
Bridge Owner Can Permanently Block Pending Value Transfers by Deregistering Operators Below the Existing Threshold — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`setOperatorThreshold` enforces `require(operatorList.length >= _threshold)` to guarantee the vote threshold is always reachable. However, `deregisterOperator` carries no symmetric guard. The bridge owner can call `deregisterOperator` one or more times to reduce the live operator count below the already-configured `operatorThresholds[ValueTransfer]`, making the threshold permanently unreachable. Every pending cross-chain value transfer request — for which users have already locked KLAY, ERC20, or ERC721 tokens on the source chain — can then never accumulate enough votes to execute on the destination bridge, permanently locking those bridged assets.

---

### Finding Description

`BridgeOperator.setOperatorThreshold` contains an explicit guard:

```solidity
require(operatorList.length >= _threshold, "bigger than num of operators");
```

This invariant is meant to ensure that the operator set is always large enough to satisfy the threshold. [1](#0-0) 

`deregisterOperator`, however, only checks that the target address is currently registered:

```solidity
require(operators[_operator]);
delete operators[_operator];
// ... removes from operatorList ...
```

There is no check that `operatorList.length - 1 >= operatorThresholds[uint8(VoteType.ValueTransfer)]` (or the Configuration vote type). [2](#0-1) 

After the deregistration reduces the operator count below the threshold, `_voteCommon` can never return `true` for a `ValueTransfer` vote:

```solidity
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
return false;
``` [3](#0-2) 

Consequently, `_voteValueTransfer` always returns `false`, and `handleERC20Transfer` / `handleKLAYTransfer` / `handleERC721Transfer` silently return without minting or transferring tokens to the recipient:

```solidity
if (!_voteValueTransfer(_requestedNonce)) {
    return;
}
``` [4](#0-3) 

Note that `setRunningStatus(false)` only gates the *request* path (`require(isRunning, "stopped bridge")`), not the *handle* path. [5](#0-4) [6](#0-5) 

So the owner already has a legitimate way to stop new requests, but making the threshold unreachable is a distinct side-channel that additionally blocks already-submitted, in-flight handle requests — an effect that no documented owner function is supposed to produce.

---

### Impact Explanation

Users who submitted `RequestValueTransfer` events on the source chain have already irrevocably locked their assets (KLAY burned/held, ERC20 burned/held, ERC721 transferred to the bridge). If the destination bridge's `operatorThresholds[ValueTransfer]` becomes unreachable, the corresponding `handleERC20Transfer` / `handleKLAYTransfer` / `handleERC721Transfer` calls can never reach consensus, and those assets are permanently unrecoverable. This satisfies the allowed impact: *unauthorized lock of bridged assets affecting system-managed funds*. [7](#0-6) 

---

### Likelihood Explanation

The bridge owner is a privileged actor, but the `setOperatorThreshold` guard was explicitly written to prevent the threshold from becoming unreachable. `deregisterOperator` silently bypasses that invariant. The owner may trigger this inadvertently (e.g., rotating operators without checking the threshold) or deliberately. No external attacker capability is required — only the bridge owner's key.

---

### Recommendation

Add a threshold-floor check inside `deregisterOperator` for every vote type before removing the operator:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    require(
        operatorList.length - 1 >= operatorThresholds[uint8(VoteType.ValueTransfer)],
        "deregister would make ValueTransfer threshold unreachable"
    );
    require(
        operatorList.length - 1 >= operatorThresholds[uint8(VoteType.Configuration)],
        "deregister would make Configuration threshold unreachable"
    );
    // ... existing removal logic ...
}
```

This mirrors the symmetric guard already present in `setOperatorThreshold` and closes the bypass. [1](#0-0) 

---

### Proof of Concept

```
State: 2 operators (owner = A, B), operatorThresholds[ValueTransfer] = 2

1. User on source chain calls requestERC20Transfer → tokens locked/burned,
   RequestValueTransfer(nonce=0) emitted.

2. Owner calls deregisterOperator(B).
   → operatorList.length = 1, operatorThresholds[ValueTransfer] = 2 (unchanged).
   No revert — deregisterOperator has no threshold guard.

3. Operator A calls handleERC20Transfer(..., requestedNonce=0, ...).
   → _voteValueTransfer(0) → _voteCommon → voteCounts[key] = 1 < threshold 2 → returns false.
   → handleERC20Transfer returns without minting or transferring tokens.

4. No other operator exists. Threshold can never be reached.
   User's tokens are permanently locked on the source chain.
```

The root cause is in `contracts/service_chain/bridge/BridgeOperator.sol` lines 159–174 (`deregisterOperator`) — the missing guard `operatorList.length - 1 >= operatorThresholds[uint8(VoteType.ValueTransfer)]`. [2](#0-1)
