### Title
Missing rejection of invalid `num-cycles` in `StackStxOp::check()` allows malformed burnchain stack-stx operations to be admitted as consensus-valid — (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
The burnchain `StackStxOp::check()` validator, which gates whether a `stack-stx` burnchain operation is accepted into a Stacks block's operation set, contains a check that logs a warning for an out-of-range `num_cycles` but never returns the corresponding error, unlike the sibling `stacked_ustx == 0` check immediately above it.

### Finding Description
`StackStxOp::check()` is the analog of the external report's "missing minimum enforcement" pattern: a value that is supposed to be validated before being trusted downstream is not actually rejected. [1](#0-0) 

```rust
pub fn check(&self) -> Result<(), op_error> {
    if self.stacked_ustx == 0 {
        warn!("Invalid StackStxOp, must have positive ustx");
        return Err(op_error::StackStxMustBePositive);
    }

    if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
        warn!(
            "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
            self.num_cycles, POX_MAX_NUM_CYCLES
        );
    }
    ...
    Ok(())
}
```

Note that the `stacked_ustx == 0` branch correctly `return`s `Err(op_error::StackStxMustBePositive)`, while the `num_cycles` branch only logs and falls through to `Ok(())`. This function is invoked from `SortitionHandleTx::check_transaction`, which uses its result to decide whether the burnchain operation is included in the block's accepted operation set at all: [2](#0-1) 

The intended invariant is that only operations with `num_cycles` in `(0, POX_MAX_NUM_CYCLES]` are ever recorded as consensus-accepted `StackStxOp`s. Because of the missing `return`, an operation with `num_cycles == 0` or `num_cycles > POX_MAX_NUM_CYCLES` (the field is parsed from a single wire byte, so up to 255) still passes `check()` and is recorded into the burnchain database as a "valid" op, exactly like the external report's pattern where an unvalidated user-supplied parameter (`_dstGasForCall`) is silently accepted and only downstream logic accidentally catches (or fails to catch) the resulting inconsistency.

Downstream, this parameter is fed directly into a Clarity contract call as `lock-period`: [3](#0-2) 

For the currently-active PoX-4 contract, `stack-stx` independently re-validates the lock period via `can-stack-stx` → `minimal-can-stack-stx` → `check-pox-lock-period`, which enforces `MIN_POX_REWARD_CYCLES <= lock-period <= MAX_POX_REWARD_CYCLES`: [4](#0-3) 

so an invalid `num_cycles` value will currently be rejected a second time at the Clarity layer and no STX lock will be applied.

### Impact Explanation
Because the Clarity-side `check-pox-lock-period` assertion currently provides a second, independent gate, this specific defect does not currently appear to allow theft, unbacked minting, or a freeze of another user's funds — the STX lock never actually gets applied when the invalid, unrejected op reaches the contract call, since the contract itself aborts the lock. The only concretely provable effect is that a malformed burnchain operation is incorrectly recorded/propagated as "checked and valid" in the burnchain database layer, which is inconsistent with the documented invariant of `check()` and is real dead-check logic that provides no defense-in-depth if the Clarity-side validation is ever weakened, refactored, or bypassed (e.g., for a future PoX version that does not perform an equivalent Clarity-side bound check on `lock-period`/`num-cycles`). I could not find, within the available time and search scope, a second code path in-scope that consumes `num_cycles` from an unrejected `StackStxOp` without funneling through the Clarity contract's own bound check, so I cannot demonstrate a concrete break of the required equalities (theft, unbacked minting, permanent/temporary freezing, unlocking value never locked, double-counting, or an unsigned stacking action) from this specific defect alone.

### Likelihood Explanation
The malformed input is trivial to construct — any user submitting a burnchain `PreStx`+`StackStx` operation pair controls the `num_cycles` byte directly and can set it to 0 or any value in `[POX_MAX_NUM_CYCLES+1, 255]`. However, exploitation of a concrete fund-safety impact requires an additional gap (a path that trusts `check()`'s pass/fail without a redundant Clarity-side re-check), which I was not able to confirm exists in the current in-scope code within this investigation.

### Recommendation
Add the missing `return Err(op_error::StackStxInvalidCycles);` in the `num_cycles` branch of `StackStxOp::check()`, mirroring the `stacked_ustx` branch immediately above it, so that malformed operations are actually excluded from the accepted burnchain operation set rather than merely logged and passed through.

### Proof of Concept
1. Submit a `PreStxOp` followed by a `StackStxOp` burnchain transaction where the wire-encoded `num_cycles` byte is `0` (or `> POX_MAX_NUM_CYCLES`).
2. `StackStxOp::parse_from_tx` successfully parses the op (parsing does not bound-check `num_cycles`): [5](#0-4) 
3. `SortitionHandleTx::check_transaction` calls `op.check()`, which logs a warning but returns `Ok(())`, so the operation is accepted into the block's checked operation set instead of being dropped as `BurnchainError::OpError`.
4. When the Stacks node later processes the accepted `StackStxOp` via `run_contract_call(..., "stack-stx", ...)`, the PoX-4 contract's own `check-pox-lock-period` assertion currently rejects the call and no lock occurs — meaning the observable consensus effect today is limited to an internally-inconsistent "accepted but functionally void" operation, not a fund-safety violation, based on the code paths I was able to examine in this session.

**Uncertainty note:** I was not able to fully audit every downstream consumer of `StackStxOp.num_cycles` (e.g., any reward-set/burn-distribution bookkeeping that might read the field independent of the Clarity contract call) within the tool-call budget available. A full audit (ideally via a Devin session with broader/deeper code search and cross-referencing) would be needed to conclusively rule out a fund-impacting path, since the missing `return Err` is a genuine, provable defect in the burn stacking ops validation layer that was explicitly called out as in-scope.
