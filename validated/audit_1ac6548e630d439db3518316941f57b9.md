### Title
Unverified upstream-provenance metadata in `gh skill install` allows silent redirection to attacker-controlled repository - (File: pkg/cmd/skills/install/install.go)

### Summary
`gh skill install` reads self-declared `github-repo` frontmatter metadata embedded inside a skill's `SKILL.md` file (originating from the remote repository the user is installing from) and uses it to silently redirect the installation source to a different, "upstream" repository, without an authenticated/attested check that the claimed upstream is legitimate. This mirrors the `_srcChainSender`-style flaw in the external report: a field that is fully attacker-controlled content is trusted as an identity/source signal and used to drive a privileged operation (choosing where to fetch and install files from) on behalf of the user.

### Finding Description
When installing a single skill, `installRun` calls `checkUpstreamProvenance(opts, apiClient, hostname, selectedSkills[0], resolved.SHA)` to detect whether the skill was "re-published from an upstream source." [1](#0-0) 

If an `upstreamRepo` is returned, the code unconditionally reassigns the installation target to that repo and recursively re-invokes `installRun`, without any signature/attestation verification of the claimed upstream ownership: [2](#0-1) 

The only check surrounding this redirect — the `visCh`/`RepoVisibilityPublic` lookup — is used solely to populate telemetry dimensions (`from_owner`, `from_repo`); it does not gate whether the redirect occurs: [3](#0-2) 

Because the `github-repo` value that seeds this decision is metadata embedded by whoever published the skill content (frontmatter parsed from the fetched `SKILL.md`, per `internal/skills/frontmatter/frontmatter.go` and `internal/skills/source/source.go` which handle `github-repo`/`github-tree-sha` fields), a malicious "re-publisher" repository can advertise an arbitrary `github-repo` value and cause `gh skill install` to switch its trust/fetch target to that attacker-chosen destination during a completely normal `gh skill install owner/repo skill-name` invocation — analogous to the Tapioca bug where an unverified sender field let an attacker redirect a privileged action to operate against arbitrary state.

### Impact Explanation
If exploited, this allows an attacker who controls (or gets a victim to reference) a "republisher" skill repository to make `gh skill install` silently switch the effective install source to a repository of the attacker's choosing, bypassing the user's explicit repo selection. Since skill files are subsequently written to disk (agent skill directories) and are explicitly documented as executable/instructable content for AI agents, this can result in installing/executing attacker-supplied instructions under the guise of a different, seemingly-trusted "upstream" origin — a source-trust bypass in the extension/skill install pathway.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to get a user to install from (or discover via search) a repository that carries this "republished" frontmatter, but no privileged access, MITM, or leaked token is needed — an ordinary `gh skill install owner/gh-awesome-copilot skill-name` invocation on attacker-published content is sufficient to trigger the redirect logic (`resolved.SHA`/`selectedSkills[0].BlobSHA` come straight from the fetched repository content).

### Recommendation
Do not silently redirect the install source based on self-declared repository metadata inside skill content. At minimum:
- Require explicit user confirmation before redirecting install source to a different repository than the one requested.
- Validate the claimed upstream repository ownership through an authenticated/attested channel (e.g., cross-check via GitHub API metadata such as fork relationship or a signed provenance attestation) rather than trusting frontmatter text.
- Ensure the visibility/ownership check currently only used for telemetry (`visCh`, `RepoVisibilityPublic`) is actually used as a gating condition for the redirect, not just for logging dimensions.

### Proof of Concept
1. Attacker creates `attacker/republished-skill` containing `skills/foo/SKILL.md` whose frontmatter includes `github-repo: attacker/malicious-skill-source` (this is the same kind of metadata legitimately used to indicate true upstream, per `internal/skills/frontmatter/frontmatter.go`).
2. Victim runs `gh skill install attacker/republished-skill foo`.
3. `installRun` detects the `github-repo` frontmatter via `checkUpstreamProvenance`, sets `opts.repo = upstreamRepo` (`attacker/malicious-skill-source`), and recursively calls `installRun(opts)` — the code at [4](#0-3)  — without any additional trust verification gating the switch.
4. The CLI proceeds to fetch and install skill files from `attacker/malicious-skill-source` instead of the originally-specified repository, and reports the install as coming "from" the redirected source.

Note: I was not able to view the full body of `checkUpstreamProvenance` itself (only its call site and the surrounding redirect logic) due to tool/iteration limits, so the exact validation it may or may not perform internally on the `github-repo` claim (e.g., whether it cross-checks anything beyond parsing frontmatter) could not be fully confirmed from the available index. If it independently validates authenticity beyond metadata parsing, this could reduce or negate the finding — this should be verified directly in the repository (`internal/skills/source/source.go` and `checkUpstreamProvenance`'s definition) before treating this as conclusively exploitable.
