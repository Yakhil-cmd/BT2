### Title
Congestion-control gas/size accounting can diverge between buffer-time and forward-time computation for non-state-stored receipts, causing an underflow panic on `CongestionInfo` bookkeeping - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`CongestionInfo` maintains shard-wide aggregates (`buffered_receipts_gas`, `receipt_bytes`, `delayed_receipts_gas`) that must always equal the sum of the per-receipt congestion gas/size values of everything currently queued or buffered. This is structurally the same "two entangled values must use identical math" invariant as the Sai `sin`/`tab` bug: an aggregate counter (`ice`/`CongestionInfo`) is incremented once with a value computed at insertion time, but is decremented later using a value that can be recomputed differently, risking `aggregate < sum(individual values)` and an underflow when settling the last entry.

### Finding Description
When a receipt is buffered, its congestion gas/size is computed once via `compute_receipt_congestion_gas`/`compute_receipt_size` and added to the aggregate counters (`add_buffered_receipt_gas`, `add_receipt_bytes`) in `buffer_receipt` [1](#0-0) .

When the receipt is later popped from the buffer to be forwarded, the gas/size used to *decrement* the same aggregate is obtained via `receipt_congestion_gas`/`receipt_size`, called on the value read back from the trie [2](#0-1) . Critically, `receipt_congestion_gas` branches on the receipt's storage representation:

```
ReceiptOrStateStoredReceipt::Receipt(receipt) => compute_receipt_congestion_gas(receipt, config)
ReceiptOrStateStoredReceipt::StateStoredReceipt(receipt) => Ok(receipt.metadata().congestion_gas)
``` [3](#0-2) 

Only the `StateStoredReceipt` branch reuses the exact value that was persisted at push time (the value stored in `StateStoredReceiptMetadata.congestion_gas`) [4](#0-3) . The plain `Receipt` branch **recomputes** `compute_receipt_congestion_gas(receipt, config)` using whatever `RuntimeConfig` (`apply_state.config`) is active *at forward time*, not the config that was active when the receipt was originally buffered [5](#0-4) . `compute_receipt_congestion_gas` derives its result from `RuntimeConfig` fee parameters (`ActionCosts::new_action_receipt`, `total_prepaid_exec_fees`, `total_prepaid_send_fees`, `total_prepaid_gas`) which are protocol-version-dependent and change across protocol upgrades [6](#0-5) .

This is documented internally as an explicit protocol-consensus concern: `compute_receipt_congestion_gas`'s doc comment states "The calculation is part of protocol and should only be modified with a protocol upgrade," and `get_receipt_group_sizes_for_buffer_to_shard` separately acknowledges "there is a moment right after the protocol upgrade where the outgoing buffer contains receipts which were buffered in the previous protocol version" [7](#0-6) . If a receipt sits in the buffer/delayed queue across a protocol upgrade that changes the fee parameters feeding `compute_receipt_congestion_gas`, and `use_state_stored_receipt` is false for that receipt (old-format, non-`StateStoredReceipt` entries, or any future path where the metadata isn't persisted), then the value subtracted at forward time will not equal the value that was added at buffer time.

The subtraction paths are unguarded arithmetic that error out rather than saturate:
```
inner.buffered_receipts_gas = inner.buffered_receipts_gas.checked_sub(gas).ok_or_else(...UnexpectedIntegerOverflow...)?
``` [8](#0-7) 

And the resharding path uses a hard `.expect()` on the same invariant:
```
congestion_info.remove_buffered_receipt_gas(gas).expect("Buffered gas must not exceed congestion info buffered gas");
``` [9](#0-8) 

Any `RuntimeError::UnexpectedIntegerOverflow` bubbling out of chunk application is converted into an unconditional `panic!` at the client layer:
```
RuntimeError::UnexpectedIntegerOverflow(reason) => { panic!("RuntimeError::UnexpectedIntegerOverflow {reason}") }
``` [10](#0-9) 

### Impact Explanation
Because the recomputation is deterministic and identical on all validators (everyone uses the same current `RuntimeConfig` for the current protocol version), this would not directly cause silent token theft or state divergence between honest nodes — every node would independently reach the same (wrong) aggregate or the same panic. The primary concrete impact is a **chain stall / node panic**: if a stale, non-state-stored-format receipt sitting in an outgoing buffer or delayed queue is forwarded after a protocol upgrade shifted the fee parameters that feed `compute_receipt_congestion_gas`, `remove_buffered_receipt_gas`/`remove_receipt_bytes` can underflow, `Err(RuntimeError::UnexpectedIntegerOverflow(...))` propagates out of chunk application, and the client layer turns that into `panic!`, crashing all applying nodes simultaneously — a network-wide liveness failure. A secondary, softer impact is congestion-info corruption (aggregate lower/higher than the true sum), which skews `outgoing_congestion`/`incoming_congestion` calculations used to gate transaction/receipt admission, effectively mis-pricing or mis-throttling shard bandwidth (analogous to the Sai report's "affects repayment"/"trapped tokens" symptom, translated here into "trapped/stuck receipts or skewed admission control" rather than direct fund loss).

### Likelihood Explanation
This requires a specific and narrow condition: a receipt must remain buffered/delayed across a protocol upgrade boundary that changes the exact `RuntimeConfig` fee fields consumed by `action_receipt_congestion_gas` (`new_action_receipt` exec fee, per-action send/exec fees, etc.), and the receipt must be represented in the non-`StateStoredReceipt` form (i.e., `use_state_stored_receipt` disabled, or a future/edge code path that reintroduces plain `Receipt` storage). Given that `use_state_stored_receipt` appears to already be the standard path for new protocol versions (mitigating this by persisting the computed value), likelihood on mainnet under current default configuration is low-to-moderate; it is realistically triggerable primarily around protocol upgrades that touch fee parameters while old-format receipts are still draining from queues, which the code's own comments acknowledge as a real transitional edge case.

### Recommendation
Following the Sai report's own remediation guidance — "the same mathematical operations have to be used to prevent a difference from appearing during rounding" and "if two values are entangled, it is preferable to store only one and compute the second from it" — the congestion-gas/size value used at removal time must always be the exact value that was used at insertion time, never a value recomputed against a possibly different `RuntimeConfig`. Concretely: (1) ensure the plain `Receipt` (non-`StateStoredReceipt`) path can never be reached for receipts crossing a protocol upgrade boundary where fee-affecting parameters change, or (2) migrate/backfill legacy queued receipts to the `StateStoredReceipt` format (with congestion metadata computed under the old config) during the upgrade, or (3) replace the panicking `checked_sub`/`.expect()` calls with `saturating_sub` plus a metric/warning, so a discrepancy degrades congestion accounting gracefully instead of halting the chain, while a corresponding validation-mode assertion catches genuine bugs in staging.

### Proof of Concept
A concrete PoC requires simulating a protocol upgrade that changes `RuntimeConfig::fees` (e.g., `action_receipt_creation.exec` fee, or an `ActionCosts` fee affecting `total_prepaid_exec_fees`/`total_prepaid_send_fees`) while a receipt buffered under `use_state_stored_receipt = false` (or the legacy `Receipt` variant) remains queued in `ShardsOutgoingReceiptBuffer`/`DelayedReceiptQueue` across the upgrade boundary, then triggering `forward_from_buffer_to_shard` in the new protocol version and observing the `RuntimeError::UnexpectedIntegerOverflow` from `remove_buffered_receipt_gas`/`remove_receipt_bytes`, which the existing test `test_congestion_delayed_receipts_accounting` in `runtime/runtime/src/tests/apply.rs:2699-2739` demonstrates already asserts an exact equality between `compute_receipt_congestion_gas` at read time and the stored aggregate — this test would need to be extended to change `apply_state.config` between the push and pop calls to reproduce the divergence and resulting panic path in `chain/chain/src/runtime/mod.rs:362-364`. I was not able to fully verify from the index whether `use_state_stored_receipt` is unconditionally `true` for all currently-supported protocol versions, or whether any live migration path exists for pre-existing queued receipts during an upgrade; confirming this would require a live Devin session with full repo/config access to trace `use_state_stored_receipt`'s protocol-version gating and any backfill/migration code for legacy receipt formats.

/// Calculate the gas of a receipt before it is pushed into a state queue or
/// buffer. Please note that this method should only be used when storing
/// receipts into state. It should not be used for retrieving receipts from the
/// state.
///
/// The calculation is part of protocol and should only be modified with a
/// protocol upgrade.
pub(crate) fn compute_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
) -> Result<Gas, IntegerOverflowError> {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt) => {
            // account for gas guaranteed to be used for executing the receipts
            action_receipt_congestion_gas(receipt, config, action_receipt.into())
        }
        VersionedReceiptEnum::Data(_data_receipt) => {
            // Data receipts themselves don't cost gas to execute, their cost is
            // burnt at creation. What we should count, is the gas of the
            // postponed action receipt. But looking that up would require
            // reading the postponed receipt from the trie.
            // Thus, the congestion control MVP does not account for data
            // receipts or postponed receipts.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseYield(_) => {
            // The congestion control MVP does not account for yielding a
            // promise. Yielded promises are confined to a single account, hence
            // they never cross the shard boundaries. This makes it irrelevant
            // for the congestion MVP, which only counts gas in the outgoing
            // buffers and delayed receipts queue.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseResume(_) => {
            // The congestion control MVP does not account for resuming a promise.
            // Unlike `PromiseYield`, it is possible that a promise-resume ends
            // up in the delayed receipts queue.
            // But similar to a data receipt, it would be difficult to find the cost
            // of it without expensive state lookups.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(Gas::ZERO),
    }
}

fn action_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
    action_receipt: VersionedActionReceipt,
) -> Result<Gas, IntegerOverflowError> {
    let prepaid_exec_gas =
        total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
            .gas
            .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee().gas)
            .ok_or(IntegerOverflowError)?;
    // account for gas guaranteed to be used for creating new receipts
    let prepaid_send_cost = total_prepaid_send_fees(config, &action_receipt.actions())?;
    let prepaid_gas = prepaid_exec_gas.checked_add_result(prepaid_send_cost.gas)?;

    // account for gas potentially used for dynamic execution
    let gas_attached_to_fns = total_prepaid_gas(&action_receipt.actions())?;
    let gas = gas_attached_to_fns.checked_add_result(prepaid_gas)?;

    Ok(gas)
}
