### Title
Cross-organization webhook forgery via organization/repository binding mismatch in signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) is used to validate the inbound webhook's HMAC signature based on an attacker-controlled field read straight out of the unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`), *before* the signature has been checked. [1](#0-0) [2](#0-1) 

Once the signature check passes (using whichever organization's secret matches `repository_owner`), the actual event handlers act on a completely different field of the same payload to decide **which repository/commit to mutate** — `repository.full_name` for repository/stack lookups, or a bare `sha` with no repository scoping at all for commit statuses. [3](#0-2) [4](#0-3) 

Nothing enforces that the organization used to authenticate the request (`repository_owner`) is the same organization that owns the repository/commit actually acted upon.

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own GitHub App and its own `webhook_secret`, selected by `Shipit.github(organization:)`. [5](#0-4) 

For every inbound webhook, `WebhooksController#verify_signature` looks up the GitHub App to verify against using `repository_owner`, which is read directly from the untrusted JSON body: [6](#0-5) 

`verify_webhook_signature` then simply HMACs the raw POST body with the secret belonging to whatever organization the attacker claimed in `repository.owner.login`: [7](#0-6) 

This means the check only proves "the sender knows *some* onboarded organization's webhook secret" — not "the sender is authorized for the repository the payload will act on." The dispatched handler, however, is free to reference *other* fields of the same body to pick the target of the mutation:

- `Handler#stacks` resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`, independent of the `owner.login` used for signing. [3](#0-2) 
- `PushHandler#process` uses that repository binding to trigger `stack.sync_github(expected_head_sha: params.after)` — an attacker-supplied SHA — for any stack under any onboarded repository. [8](#0-7) 
- `StatusHandler#process` is worse still: it doesn't even use the repository binding — it looks up `Commit.where(sha: params.sha)` **globally across the entire Shipit instance** and writes a forged CI status (`state`, `context`, `description`, `target_url`) onto whatever commit matches that SHA anywhere in the system. [9](#0-8) 

So the equality that should hold — `organization that authenticated == organization/repository that gets mutated` — is broken: the controller verifies org **A** (`repository_owner` from the payload) while the handler mutates state belonging to repository/commit **B** (from `repository.full_name`/`sha` in the same payload), with no cross-check between the two.

### Impact Explanation
An operator that legitimately controls the webhook secret for one onboarded, low-trust GitHub organization (org A) in a multi-org Shipit deployment can forge webhook deliveries that are authenticated as org A but whose payload fields target a repository/commit belonging to an entirely different, higher-trust organization (org B) also hosted on the same Shipit instance. Concretely:
- Forging `status` events lets the attacker mark arbitrary commits (identified only by SHA, no ownership check) as passing CI (`state: success`), which is the exact signal Shipit's merge/deploy pipeline consumes to decide whether a commit is deployable (`ci.require`/blocking statuses feed off `Commit` status records set via `create_status_from_github!`). This can be used to push an unsafe or unreviewed commit into an "unauthorized deploy" state for org B's stack.
- Forging `push` events lets the attacker trigger `sync_github` with an attacker-chosen `expected_head_sha` against org B's stacks, corrupting the perceived deploy state of a repository the attacker does not control.

This crosses the "organization that authenticated vs. repository that is written" trust boundary explicitly called out as in-scope, and can culminate in an unauthorized deploy — a Critical-tier impact per the program's classification.

### Likelihood Explanation
Requires (a) a multi-organization Shipit deployment (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), and (b) the attacker possessing a legitimate webhook secret for *any one* of the onboarded organizations — not the victim's. In shared/managed Shipit installations where multiple teams or business units onboard their own GitHub Apps to one instance, this is a realistic "unprivileged" cross-tenant scenario, since possessing your own org's webhook secret is not "privileged access" to the target org.

### Recommendation
After verifying the HMAC signature for `repository_owner`, additionally assert that every repository/commit referenced later in the same payload actually belongs to that same, now-authenticated organization (e.g., verify `repository.full_name.split('/').first == repository_owner` and require `StatusHandler` to scope commit lookups by repository, not by bare SHA) before dispatching to handlers.

### Proof of Concept
1. Attacker legitimately administers the GitHub App for org `attacker-org`, which is one of several organizations configured under Shipit's multi-org `github:` secrets block, and thus knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<known sha of a commit in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "attacker-org"`, fetches `attacker-org`'s GitHub App, and the signature validates successfully. [1](#0-0) 
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and records a forged "success" status on it. [4](#0-3) 

Note: The exact downstream logic that consumes `Commit` statuses to gate deploy eligibility (e.g. in `app/models/shipit/stack.rb` / `app/models/shipit/deploy_spec.rb`'s `required_statuses`/`blocking_statuses`) was located but not fully traced line-by-line in this session; confirming the precise deploy-gating code path would benefit from a follow-up read of `app/models/shipit/commit.rb`'s `create_status_from_github!` and `Shipit::Stack#deployable?`-style logic in a full Devin session.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
