### Title
Webhook signature check keys off `repository.owner.login` while every event handler acts on `repository.full_name` - unauthenticated cross-repository webhook injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the request signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). All downstream event handlers, however, resolve the repository to act on from a *different* field of the same attacker-controlled JSON body: `Handler#repository_name` reads `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so the organization whose secret authenticated the request is not necessarily the repository that gets written to.

### Finding Description
`verify_signature` picks the app config to verify against: [1](#0-0) 

`repository_owner` is read straight from the JSON body: [2](#0-1) 

Signature verification is a per-organization no-op when that organization has no `webhook_secret` configured: [3](#0-2) 

Shipit explicitly supports multiple GitHub Apps/organizations behind one instance (confirmed by the multi-org fixture with independent `webhook_secret` per org): [4](#0-3) 

Once verification passes, `Shipit::Webhooks.for_event(event)` dispatches to handlers using the raw parsed body, and every handler independently resolves the target repository via `full_name`, not via the `owner.login` value used for signature verification: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` and `repository.full_name` are two independent, unauthenticated fields inside the same JSON body, an attacker can construct a payload where these fields point to different organizations. If an organization `OrgB` is configured on the Shipit instance without a `webhook_secret` (an explicitly supported, documented configuration — see `docs/setup.md`'s "Webhook secret (optional)"), then `verify_webhook_signature` for `OrgB` returns `true` unconditionally regardless of the `X-Hub-Signature` header. An attacker sends a POST to `/webhooks` with `repository.owner.login = "OrgB"` (so verification is a no-op) but `repository.full_name = "OrgA/victim-repo"` (a repository belonging to a *different*, secret-protected organization). The request passes `verify_signature`, and the dispatched handler (e.g. `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, or the `pull_request/*` handlers) resolves and mutates `victim-repo` under `OrgA` using `Repository.from_github_repo_name(repository_name)` from `full_name`, entirely bypassing the fact that `OrgA` requires signed webhooks.

This breaks the binding: **organization that authenticated == repository that is written**. The equality does not hold — the organization used to select/verify the webhook secret is not the same repository entity subsequently mutated by the handler.

### Impact Explanation
Handlers reachable via this path can enqueue `GithubSyncJob` (pushing forged commits/refs into the sync pipeline for the victim repo), create/forge commit `Status` records via `status_handler.rb` (which feed into deployability checks and merge-queue automation), and drive `pull_request` handlers (label/close/reopen) and `check_suite` refresh for the victim repository — all attributed as legitimate GitHub-originated events for a repo whose organization does enforce webhook signing. Since commit statuses and merge/check-suite state directly gate Shipit's automatic merge and deploy decisions, this can lead to an unauthorized deploy/merge being triggered against `OrgA`'s repository without ever possessing `OrgA`'s webhook secret, satisfying the Critical impact bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability requires only that the Shipit instance host more than one GitHub App/organization and that at least one configured organization does not set a `webhook_secret` (explicitly documented as optional). No credentials, GitHub App private key, ApiClient token, or session are required — the attacker only needs to know the login of an unsecured organization onboarded to the same instance and the `full_name` of the target repository, both of which are non-secret, discoverable values. This is a plausible, realistic multi-tenant deployment pattern for Shipit.

### Recommendation
Bind the two fields together before dispatch: verify the signature using the same organization value that will be used to resolve the target repository (e.g., derive both from `repository.full_name`'s owner segment, and reject the request if `repository.owner.login` does not match the owner in `full_name`). Additionally, do not allow signature verification to silently succeed (`return true unless webhook_secret`) for organizations without a configured secret when other organizations on the same instance do have one configured — either require a secret for all organizations or scope the amnesty strictly.

### Proof of Concept
1. Configure a Shipit instance with two GitHub Apps: `OrgA` (has `webhook_secret` set) and `OrgB` (no `webhook_secret`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends: `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" },
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/master"
}
```
No valid `X-Hub-Signature` header is required.
3. `verify_signature` calls `Shipit.github(organization: 'OrgB')`; since `OrgB.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally [7](#0-6) .
4. `PushHandler`/`Handler#repository_name` resolves `payload.dig('repository', 'full_name')` = `"OrgA/victim-repo"` [8](#0-7)  and enqueues sync/status jobs against `OrgA`'s repository despite `OrgA` requiring signed webhooks.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
