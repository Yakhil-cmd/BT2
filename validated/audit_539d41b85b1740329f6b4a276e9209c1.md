### Title
Webhook signature verification is keyed to an attacker-controlled `repository.owner.login`/`organization.login` field while the repository actually acted upon is a separate, unvalidated field in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook against using `repository_owner`, a value read directly out of the untrusted JSON payload (`repository.owner.login` or `organization.login`). The repository/stack that is actually mutated once the request is accepted is derived from a different payload field, `repository.full_name` [1](#0-0) , with no check that this repository belongs to the organization whose secret gated the request. Additionally, `GitHubApp#verify_webhook_signature` fails open: `return true unless webhook_secret` [2](#0-1) . Shipit's own documented multi-org configuration examples ship with `webhook_secret` left blank per-organization [3](#0-2) [4](#0-3) . Together this breaks the equality `organization_that_authenticated == repository_that_is_written`.

### Finding Description
`verify_signature` computes:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [5](#0-4) 
where
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Both `repository_owner` and the `X-Hub-Signature` header are entirely attacker-supplied on an unauthenticated endpoint (`WebhooksController` has no `before_action` requiring a session or API token). For any organization configured in `Shipit.github(organization:)` whose `webhook_secret` is blank, `GitHubApp#verify_webhook_signature` short-circuits and returns `true` for *any* signature value [7](#0-6) .

Once the request passes `verify_signature`, the raw payload is dispatched to handlers keyed only by event name:
```
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [8](#0-7) 

Handlers resolve the target stack(s) from `repository.full_name`, a field never compared against the org used for signature verification:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [9](#0-8) 

So an attacker who knows (or guesses) that a particular org in a multi-org Shipit deployment has no `webhook_secret` configured can send a forged `push` (or other) webhook with `repository.owner.login` set to that unsecured org, while `repository.full_name` points at a completely different, properly-secured organization's repository/stack. `PushHandler` will then call `stack.sync_github(expected_head_sha: ...)` for that unrelated stack [10](#0-9) , and `GithubSyncJob` will fetch commits and detach/append commits using the app's own `github_api` credentials for the *targeted* repository [11](#0-10) , i.e., data belonging to an org the forged request never authenticated against.

### Impact Explanation
This lets an unprivileged, unauthenticated internet attacker manipulate the commit/stack state of a repository/organization other than the one whose (absent or leaked) webhook secret nominally scoped the request, effectively performing a cross-repository/cross-organization write. Depending on which webhook event and handler is hit (`push`, `status`, `check_suite`, `membership`, `pull_request`, `merge`), the impact ranges from spoofed CI status and injected commit history to spoofed team membership changes, without ever needing a session, ApiClient token, or the target org's actual `webhook_secret`.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: the vulnerability is only exploitable when at least one configured GitHub organization in a multi-org Shipit deployment has `webhook_secret` unset. This is not a hypothetical edge case — it is exactly what Shipit's own shipped documentation and test fixtures demonstrate as valid configuration (`secrets.development.example.yml`, `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml` all show `webhook_secret: # nil` for one or more orgs). The engine's own code chooses to fail open (`return true unless webhook_secret`) rather than reject unsigned requests, and never re-validates that the acted-upon repository belongs to the org whose secret (or lack thereof) authorized the request.

### Recommendation
- In `GitHubApp#verify_webhook_signature`, fail closed instead of returning `true` when `webhook_secret` is blank (require an explicit "signature verification disabled" opt-in rather than an implicit one).
- In `WebhooksController` / `Handler`, after resolving the organization used for signature verification, assert that `repository.full_name`'s owner matches `repository_owner` (or the org used to find the webhook_secret) before dispatching to handlers, closing the gap between the authenticated organization and the repository actually written.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `SecureOrg` (has `webhook_secret` set) and `OpenOrg` (has `webhook_secret` left blank, as shown in `test/dummy/config/secrets_double_github_app.yml`).
2. As an unauthenticated attacker, `POST /github/webhooks` with:
   - Header `X-Github-Event: push`
   - Header `X-Hub-Signature: sha1=anything` (arbitrary/invalid)
   - Body: `{"ref":"refs/heads/main","after":"<attacker-chosen sha>","repository":{"owner":{"login":"OpenOrg"},"full_name":"SecureOrg/target-repo"}}`
3. `verify_signature` calls `Shipit.github(organization: "OpenOrg")`; since `OpenOrg`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the bogus signature.
4. `PushHandler` resolves stacks via `Repository.from_github_repo_name("SecureOrg/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, causing `GithubSyncJob` to run against `SecureOrg`'s repository despite the request never having been validated against `SecureOrg`'s credentials.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
