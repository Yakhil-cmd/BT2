This maps cleanly to the reported bug class ("a setter accepts an update to a trust-critical binding without validating consistency with the old/other binding") and there's a concrete, code-level analog in `WebhooksController`/`MembershipHandler`.

### Title
Webhook organization-binding bypass leads to `Shipit.github_teams` privilege escalation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook against using an attacker-supplied field from the *unverified* JSON body (`repository.owner.login` or `organization.login`), not from any authenticated context. When Shipit is configured with the documented multi-organization GitHub App schema and any one configured organization has no `webhook_secret` set (explicitly supported/"optional" per `docs/setup.md`), `GitHubApp#verify_webhook_signature` unconditionally returns `true` for that organization. Because the "organization used to authenticate the webhook" is never bound to the "team/repository the payload actually mutates", an attacker can pick that unsecured organization purely to pass signature verification, while embedding a `team.id`/`member.login` (or `repository.full_name`) belonging to a totally different, real, secured organization. For the `membership` event this results in an unauthenticated attacker adding themselves to a `Team` that gates `Shipit.github_teams` authorization.

### Finding Description
- `verify_signature` derives the org used for verification purely from payload content: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` (i.e., skips verification entirely) whenever that organization's config has no `webhook_secret`: [3](#0-2) 
- A blank `webhook_secret` per organization is an explicitly documented, supported configuration state, not an error condition: [4](#0-3) 
- Once verification is (trivially) satisfied for the "no-secret" organization, the actual mutation performed by `MembershipHandler#process` is keyed only on `params.team.id` (GitHub team ID) and `params.member.login`, completely independent of which organization was used to authenticate the request: [5](#0-4) 
- `Team.find_or_create_by!(github_id: params.team.id)` will match any existing `Team` row by that numeric ID — including a real, privileged team referenced by `Shipit.github_teams` — regardless of which organization's (secret-less) config was used to pass signature verification. [6](#0-5) 
- Membership in that team is exactly what `User#authorized?` checks to grant access to the whole Shipit application: [7](#0-6) 

This is the same class of bug as the report: a "setter" (here, the webhook handler acting on `team.id`/`member.login`) trusts and mutates state based on a field that was never actually covered/bound by the verification step (the org used to pick — or skip — the signature check).

### Impact Explanation
An unauthenticated network attacker (no Shipit session, no `ApiClient` token, no GitHub credentials) who knows only the numeric GitHub `team.id` of a team listed in `Shipit.github_teams` (discoverable via the public GitHub API for that org's teams, or simply guessable/enumerable small integers) can:
1. Send a forged `membership` webhook to `/webhooks` with `X-Github-Event: membership`.
2. Set `organization.login` to any organization configured in Shipit's multi-org GitHub App config that has no `webhook_secret`.
3. Set `team.id` to the real target team's GitHub ID and `member.login` to an attacker-controlled GitHub login.
4. Have that (attacker-controlled) user added to the privileged `Team`, becoming `authorized?` and gaining full read/write access to Shipit — deploys, rollbacks, task execution, etc.

This satisfies the listed High-severity impact: "escalation into `Shipit.github_teams` authorization," achieved with zero credentials, matching the report's core theme of a setter silently accepting/creating an unverified binding that grants unintended control.

### Likelihood Explanation
Requires the operator to use the documented multi-organization GitHub App configuration (explicitly supported in `docs/setup.md`) and to have at least one configured organization without a `webhook_secret` (also explicitly documented as "optional"). Given that the webhook endpoint is public and unauthenticated by design, and the only "signature" gating relies entirely on secret presence-per-org with no cross-check against the organization that actually owns the affected team/repository, likelihood is high in any such deployment.

### Recommendation
- Bind webhook verification to the organization actually affected by the mutation: reject events where the verifying organization does not match the organization owning the `team`/`repository` acted upon.
- Do not silently pass verification when `webhook_secret` is blank for a given org config entry in multi-org setups; require a secret whenever more than one organization is configured, or clearly scope teams/repos to the org that authenticated the request.
- In `MembershipHandler`, validate that `params.team`'s organization matches `params.organization.login`, and that `params.organization.login` matches the organization actually used to pass `verify_signature`.

### Proof of Concept
Given Shipit configured with:
```yaml
github:
  secured-org:
    app_id: ...
    webhook_secret: real-secret
  unsecured-org:
    app_id: ...
    webhook_secret: # blank, "optional"
```
and `Shipit.github_teams` including a team with GitHub `id: 12345` belonging to `secured-org`, an attacker (no auth) sends:
```
POST /webhooks
X-Github-Event: membership
{
  "action": "added",
  "organization": { "login": "unsecured-org" },
  "team": { "id": 12345, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-user" }
}
```
`verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` unconditionally (blank secret), so the request is accepted with no signature header needed. `MembershipHandler` then adds `attacker-controlled-user` to the real `Team` (`github_id: 12345`), which is checked by `User#authorized?` against `Shipit.github_teams`, granting the attacker full authenticated access after a normal GitHub OAuth login as that user.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
