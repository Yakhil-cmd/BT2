### Title
`EnvironmentVariables#interpolate` falls back to Shipit's process `ENV` for any `$WORD` not present in the task/step env, leaking host secrets into task output - ([File: lib/shipit/environment_variables.rb])

### Summary
`Shipit::EnvironmentVariables#interpolate` resolves `$WORD` tokens in step command lines with `@env.fetch(variable) { ENV[variable] }`, i.e. if the token is not a key of the merged per-task/per-step env hash, it silently falls back to the Shipit server process's own `ENV`. Because shipit.yml steps (and thus which `$WORD` tokens are referenced) are attacker-controlled content on a repository's own branch, an attacker can reference any variable name that happens to be a key in the Shipit host's process environment (e.g. `SECRET_KEY_BASE`, `DATABASE_URL`) and have its value shell-escaped and interpolated directly into a command that is echoed to task output.

### Finding Description
The claimed binding is: for every `$WORD` referenced in a step string reaching `Command#interpolated_arguments`, `WORD` must be a key explicitly present in that `Command`'s `@env`, and must never fall back to top-level `ENV`. Tracing the code shows this binding does not hold:

- `Shipit::EnvironmentVariables#interpolate` [1](#0-0)  replaces every `$WORD` occurrence with `Shellwords.escape(@env.fetch(variable) { ENV[variable] })` — an explicit fallback to the Shipit process's `ENV` whenever `variable` is not a key of `@env`.
- `Command#interpolate_arguments`/`#interpolated_arguments` invoke this on every argument of every step before spawning the process [2](#0-1) [3](#0-2) , and the resulting interpolated string is what is passed to `PTY.spawn` and whose stdout becomes the task/deploy log stream [4](#0-3) .
- `@env` for task/deploy commands is built by `TaskCommands#env`, a merge of a base env, `@stack.env` (operator-set), several fixed Shipit-managed keys, `deploy_spec.machine_env`, and finally `@task.env` [5](#0-4) . None of these merges guarantee that an *arbitrary* variable name referenced inside a step (via `$WORD`) is present as a key — they only guarantee that whatever *is* present is validated/whitelisted.
- `TaskDefinition#filter_envs` uses `EnvironmentVariables#permit` to whitelist which **incoming values** a task/deploy submission may set [6](#0-5) , but this whitelist constrains what can be *set* into `@env`; it does nothing to prevent a step from *referencing* a name that was never set, at which point `interpolate` transparently reads from the real process `ENV` instead of raising or returning empty.

Attack: an attacker with write access to a branch/PR that Shipit checks out (e.g., a ReviewStack driven by `.shipit/shipit.yml` on the PR branch, or any deploy/task step defined in shipit.yml on a branch the attacker controls) adds a step such as `echo $SECRET_KEY_BASE` (or `$DATABASE_URL`, or any other name likely to be set as an OS-level environment variable on the Shipit host, e.g. via Heroku config vars, Docker `-e`, or systemd `Environment=`). Because `SECRET_KEY_BASE` is not a key that `TaskCommands#env` populates, `@env.fetch('SECRET_KEY_BASE')` misses and falls back to `ENV['SECRET_KEY_BASE']`, embedding the real secret into the shell command that gets executed and streamed back as task output.

None of the listed guards (`verify_signature`, `require_permission!`, `EnvironmentVariables#permit`, model validations) address this: `permit` only restricts values submitted via API/params for defined variables, it is never invoked to restrict which tokens a step in shipit.yml is allowed to reference at interpolation time.

### Impact Explanation
Any process-level secret readable via Ruby's `ENV` on the Shipit host (`SECRET_KEY_BASE`, `DATABASE_URL`, `GITHUB_APP_PRIVATE_KEY`, `webhook_secret`, or other deploy-time credentials commonly injected as OS environment variables) can be exfiltrated into a task/deploy's output stream simply by adding an `echo $NAME` step to a shipit.yml the attacker controls. This is repeatable on every task/deploy run, against any stack/repository whose shipit.yml the attacker can push, and the leaked secret is visible to anyone who can read that task's output (typically the PR author and any user with read access to the stack). This matches the Critical category: "exfiltration of ... deploy-time secrets".

### Likelihood Explanation
Precondition: the Shipit host process must actually have the targeted secret as an OS environment variable (very common deployment pattern — Heroku/Docker/systemd-style secret injection) and the attacker must control a shipit.yml that Shipit will execute steps from (fork PR / ReviewStack / task definition on a branch the attacker owns). No Shipit credentials, session, or elevated GitHub role is required — only the ability to push a shipit.yml with a step referencing the target variable name and trigger a task/deploy/review-stack run. Cost is trivial (one commit + one triggered run) and fully repeatable/scriptable against every variable name the attacker wants to probe.

### Recommendation
Remove the implicit fallback to top-level `ENV` in `EnvironmentVariables#interpolate`; unresolved `$WORD` tokens should either raise/fail the step or interpolate to an empty string, never read from the Shipit server process's own environment. If pass-through of specific host env vars (e.g. `PATH`) is required, it should be done through an explicit, reviewed whitelist merged into `@env` before interpolation, not a blanket fallback to `ENV`.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (or command_test.rb)
test "interpolate does not leak process ENV for undeclared variables" do
  ENV['SHIPIT_TEST_SECRET'] = 'leak'
  command = Shipit::Command.new('echo $SHIPIT_TEST_SECRET', env: {}, chdir: '.')
  output = command.run
  # Vulnerable behavior: output contains 'leak' even though 'SHIPIT_TEST_SECRET'
  # was never part of the Command's own @env.
  assert_no_match(/leak/, output) # FAILS on current code, proving the leak
ensure
  ENV.delete('SHIPIT_TEST_SECRET')
end
```
This demonstrates that a name never placed in `@env` by `TaskCommands#env`/`Command#initialize` is still resolvable via `interpolate`'s `ENV[variable]` fallback [7](#0-6) , confirming the equality the question challenges is broken.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
