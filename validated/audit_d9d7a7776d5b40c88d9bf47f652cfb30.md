### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in status webhook handler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only authenticates that the payload's signature matches the secret configured for `repository.owner.login` in the payload, i.e., it proves the payload was sent by whoever controls that GitHub organization's webhook secret [3](#0-2) . It does not prove or check that this organization actually owns the commit `sha` referenced in the payload. `StatusHandler#process` then looks up `Commit.where(sha: params.sha)` with zero scoping to any repository/stack tied to the authenticated organization [2](#0-1) , and calls `commit.create_status_from_github!(params)` on every matching commit regardless of which stack/org it belongs to.

### Finding Description
The broken binding: the question requires `organization_that_authenticated_payload == organization_owning_commit(sha)`, but the code never asserts this equality anywhere in the reachable path.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, proving only that ATTACKER_ORG's secret produced a valid HMAC over the raw POST body [4](#0-3) [5](#0-4) .
- `WebhooksController#create` then dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with the entire raw JSON body, including whatever `repository.full_name`/`sha` the attacker chose [6](#0-5) .
- The base `Handler` class exposes a `stacks` helper that *does* scope by `Repository.from_github_repo_name(repository_name)` [1](#0-0) , showing the engine is aware repository-scoping is required for safety — but `StatusHandler#process` bypasses this helper entirely and instead does a bare `Commit.where(sha: params.sha)` across the whole `commits` table [2](#0-1) .
- `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using the victim commit's own `stack_id` [7](#0-6) , and `Status.replicate_from_github!` writes a new `Shipit::Status` row with attacker-controlled `state`, `description`, `target_url`, and `context` [8](#0-7) .

Exploit flow: the attacker registers their own GitHub organization (`ATTACKER_ORG`) with the Shipit-integrated GitHub App, obtaining a legitimate `webhook_secret` for that org. They observe (via public GitHub) a commit `sha` on `VICTIM_REPO`'s stack. They POST a `status` webhook to `/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with ATTACKER_ORG's own secret, and a JSON body where `repository.owner.login = "ATTACKER_ORG"` (or any name that passes signature check) but `sha` is set to the victim's commit sha, `state: "success"`. `verify_signature` passes because it only checks the org named in the payload against that org's own secret, which matches. `StatusHandler#process` finds the victim `Commit` by raw sha with no ownership check, and creates a forged `success` (or any) status on it, potentially unblocking a deploy/merge on `VICTIM_REPO`'s stack — a different tenant entirely.

### Impact Explanation
This is a cross-repository/cross-tenant write: an attacker authenticated only as their own GitHub organization can write a `Shipit::Status` row onto any commit belonging to any other stack in the same Shipit instance, controlling `state`, `description`, `target_url`, and `context`. Setting `state: "success"` can flip `Commit#deployable?` to true (since `deployable?` depends on `success? && !blocked?` derived from `status`) [9](#0-8) , and `add_status` schedules `stack.schedule_merges` / continuous delivery when transitioning to `pending`/`success` [10](#0-9) , which can trigger an unauthorized deploy or merge. This is repeatable against arbitrary commits/stacks system-wide by anyone who can create/control any single GitHub organization with the App installed — matching the "Critical: a payload for one repository mutating another's stack, commit ... or an unauthorized deploy" category.

### Likelihood Explanation
Preconditions are low-cost: the attacker only needs to install/configure the GitHub App on an organization they control (a normal, self-service action for any GitHub user, not requiring victim cooperation) to obtain a valid `webhook_secret` for `Shipit.github(organization: ATTACKER_ORG)`. The victim's commit sha is public information obtainable from GitHub's API/UI for any public repo, or guessable/observable for private ones via other channels. No Shipit session, API token, or victim secret is required. This is fully repeatable and scriptable against any victim commit sha.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to only commits belonging to stacks under the repository/organization that was authenticated by `verify_signature` (i.e., use the `stacks` helper already defined on `Handler`, filtering `Commit.where(sha: params.sha, stack: stacks)` instead of an unscoped `Commit.where(sha: params.sha)`), so a status payload can only affect commits within the repository that signed it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook cannot mutate commits belonging to a different repository/organization" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to victim_stack, sha known publicly
  attacker_repo_full_name = "attacker-org/attacker-repo"

  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "description" => "forged",
    "context" => "ci/forged",
    "repository" => { "full_name" => attacker_repo_full_name, "owner" => { "login" => "attacker-org" } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(ExplicitParameters::Parameters.new(payload))
  end
end
```
Currently this assertion fails (a `Shipit::Status` row IS created on `victim_commit` because `StatusHandler#process` does an unscoped `Commit.where(sha:)` lookup) [2](#0-1) , demonstrating the vulnerability. After applying the recommended fix (scoping via `stacks`), the test should pass.
