### Title
`StatusHandler` matches commits by bare SHA across all repositories, ignoring the webhook payload's `repository` field, breaking the app→repository binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects a `GitHubApp` and its `webhook_secret` strictly by `repository_owner`/`organization.login` in the payload, then dispatches to `StatusHandler`. Unlike `PushHandler` and `CheckSuiteHandler`, which scope their processing through `stacks` (derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), `StatusHandler#process` queries `Commit.where(sha: params.sha)` globally with no repository/stack filter, so a validly-signed status webhook for App X's repository can mutate a commit that belongs to a completely different repository/organization tracked under App Y, as long as the `sha` values match.

### Finding Description
The claimed binding is: `github_app_that_verified_signature.organization == repository_owner_of(mutated_commit)`. Trace:

1. `WebhooksController#verify_signature` picks `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login')`, and verifies the HMAC signature against that specific app's `webhook_secret` [1](#0-0) . This only proves the *signature* belongs to the app named in the payload's `repository.owner.login` — it says nothing about which commits get mutated afterward.
2. `Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` with the full parsed JSON body [2](#0-1) .
3. `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
It never calls the base `Handler#stacks` helper (which scopes to `Repository.from_github_repo_name(repository_name)`) [4](#0-3) , and it never reads `payload.dig('repository','full_name')` at all. Compare with `PushHandler`, which restricts to `stacks.not_archived.where(branch:)` [5](#0-4) , and `CheckSuiteHandler`, which restricts to `stacks.where(branch: ...)` before touching commits [6](#0-5) . Both siblings deliberately scope by repository; `StatusHandler` does not.

4. `Commit#create_status_from_github!` (via `add_status`) creates a `Status` row, and if the resulting `simple_state` transitions to `success`/`pending`, it calls `stack.schedule_merges` and emits `deployable_status`/`commit_status` hooks [7](#0-6) . This is not a benign read — it's a state mutation that can trigger merge-queue processing on **App Y's stack**, entirely off App X's valid signature.

Exploit flow: attacker controls a repository under App X (their own legitimate GitHub App installation, matching the "attacker owns App X" precondition) and knows (from public GitHub) a SHA that also exists as a `Commit` row on some App Y-owned stack (identical git objects are content-addressed and commonly shared across forks/mirrors, or the attacker can simply push a commit into their own repo/branch that reproduces the exact tree/parent/author/timestamp of a known public commit in App Y's repo, yielding an identical SHA). The attacker triggers (or forges, since they control their own repo/App X webhook delivery/GitHub Apps allow re-delivery and users can trigger `status` events via the Statuses API on repos they administer) a `status` webhook for their own App X repository with that `sha`. `WebhooksController` verifies it correctly against App X's `webhook_secret` (fully legitimate signature), but `StatusHandler` then attaches the forged state to **every** `Commit` row in the database sharing that SHA — including the one under App Y's stack — and can flip App Y's commit into `success`/`pending`, invoking `schedule_merges` on App Y's stack.

None of the listed guards catch this: `verify_signature` only binds signature↔declared-repository-owner, not signature↔mutated-record; `ExplicitParameters` only validates the shape of `sha`/`state`/etc, not repository ownership; `drop_unhandled_event` is unrelated; there is no `Repository`/`Stack` validator invoked in this path since no new record is created, only an existing `Commit` (found by global SHA scan) is updated.

### Impact Explanation
A holder of one legitimate GitHub App installation (App X) can inject `Status` rows and flip commit states (`success`, `pending`, `failure`, `error`) on commits belonging to a stack/repository under a completely different, unrelated GitHub App/organization (App Y), as long as a matching SHA exists in Shipit's `commits` table. Because `Commit#create_status_from_github!`/`add_status` triggers `stack.schedule_merges` on success/pending transitions and fires `deployable_status`/`commit_status` hooks, this is not merely stray data — it can influence App Y's merge queue and downstream automation without ever touching App Y's `webhook_secret`. This is a payload for one repository mutating another tenant's commit/stack state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the attacker must legitimately control at least one configured GitHub App/organization in Shipit's multi-app config (a realistic scenario for any Shipit instance onboarding several orgs), and must be able to get a `Commit` row with a matching SHA created under the victim's stack (via a shared upstream/fork commit, cherry-pick, or reproducing an existing public commit's exact git object). Cost is low: no secrets, sessions, or privileged roles are required beyond ownership of one's own already-configured App/repo. This is repeatable against any known SHA in any tenant's stack, since `StatusHandler` never restricts the record set by app or repository — every "status" webhook processed by a correctly-signed app iterates the full unscoped `Commit` table.

### Recommendation
Scope `StatusHandler#process` to the repository declared in the webhook payload, mirroring `PushHandler`/`CheckSuiteHandler`: use the inherited `stacks` helper (or explicitly join `Commit` through `stack.repository == Repository.from_github_repo_name(payload.dig('repository','full_name'))`) before matching by `sha`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, so a status webhook can only mutate commits belonging to stacks whose repository matches the authenticated payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status payload for repo A does not mutate a commit belonging to repo B" do
          # Named-value equality claimed by the binding, checked BEFORE tracing code:
          # github_app_for(payload_repository_owner) == owner_of(stack_of(commit_matched_by_sha))
          repo_a = shipit_stacks(:shipit)              # owned by org "shopify" (App X)
          repo_b = shipit_stacks(:cyclimse)             # owned by a different org (App Y)

          shared_sha = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
          commit_b = repo_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                             committer: shipit_users(:walrus),
                                             authored_at: Time.now, committed_at: Time.now,
                                             message: "victim commit")

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'branches' => [{ 'name' => repo_a.branch }],
            'repository' => { 'full_name' => repo_a.github_repo_name, 'owner' => { 'login' => 'shopify' } }
          }

          assert_difference -> { commit_b.statuses.count }, 1 do
            Shipit::Webhooks::Handlers::StatusHandler.call(payload)
          end

          # Both sides of the binding evaluated AFTER the call:
          assert_not_equal repo_a.repository.owner, repo_b.repository.owner # different tenants
          assert commit_b.statuses.last.present?                             # yet repo B's commit mutated
        end
      end
    end
  end
end
```
This demonstrates that a correctly signed webhook for repository/App X's organization results in a `Status` write on a commit belonging to a stack under a different, unrelated repository/App Y, confirming the app→repository binding does not hold in `StatusHandler`.
