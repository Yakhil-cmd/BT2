### Title
CCMenuController#stack bypasses api-client stack scoping, allowing a stack-scoped token to read any stack's cc.xml - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces per-client stack scoping via `stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), and `stack` is built from that scoped relation. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely skipping the scoping check, so any valid `ApiClient` token — even one bound to a specific `stack_id` — can fetch `cc.xml` for an arbitrary stack.

### Finding Description
The binding the question describes — `current_api_client.stack_id == params[:stack_id]`'s referenced stack — is never enforced by `Api::CCMenuController`, whether or not the client's `stack_id` was reassigned.

- `Api::BaseController#authenticate_api_client` sets `@current_api_client` via `ApiClient.authenticate(token)`; `ApiClient.authenticate` only verifies the signed id (`find_by(id: message_verifier.verify(token).to_i)`), it never checks any stack binding. [1](#0-0) 
- The stack-scope enforcement that exists in this engine lives in `BaseController#stacks`/`#stack`, which restricts the queryable `Stack` relation to `current_api_client.stack_id` when the client has one set. [2](#0-1) 
- `Api::CCMenuController` overrides `stack` with `@stack ||= Stack.from_param!(params[:stack_id])`, which queries the entire `Stack` table, not the client-scoped relation. [3](#0-2) 
- `require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks the `permissions` array (e.g. `'read:stack'`) but has no notion of `stack_id` at all. [4](#0-3) [5](#0-4) 

Consequently, the token-issued-for-stack-A vs. requested-stack-B binding is never checked in this controller: any `ApiClient` with `read:stack` permission — including one whose `stack_id` was originally scoped to a different (or since-repurposed/deleted) stack — can pass any `params[:stack_id]` and get that stack's `cc.xml`. This is broader than "stale token after reassignment": the scoping check is absent from this controller unconditionally, so even a freshly-issued, never-reassigned, stack-scoped token (e.g. the fixture `here_come_the_walrus`, scoped to stack `shipit`) can read any other stack simply by changing `params[:stack_id]` in the request.

The `authenticate_api_client` override in `CCMenuController` (`@current_api_client = ApiClient.authenticate(params[:token]); super unless @current_api_client`) only affects *how the client authenticates* (query-string token vs Basic Auth); it does not add or remove any stack scoping, and is not itself the root cause — the root cause is the `stack` method override that bypasses `BaseController#stacks`. [6](#0-5) 

### Impact Explanation
An attacker holding *any* valid `ApiClient` API token with `read:stack` permission (e.g. a legitimately obtained CCMenu URL token for one project, created via `CCMenuUrlController#client`, which is scoped `read:stack` to a specific stack) can read the build/deploy status (`cc.xml`: name, activity, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl, lock status) of any other stack in the Shipit instance, across any repository/tenant, by simply substituting `params[:stack_id]`. This is an unauthenticated-scope read of stack state for repositories the token was never authorized against — matching the High severity category "unauthenticated read of stack state." It is fully repeatable against every stack on the instance with a single valid token.

### Likelihood Explanation
Preconditions: attacker needs any valid `ApiClient` token with `read:stack` permission scoped to any stack (trivially obtainable for any repository the attacker has legitimate access to, e.g. via the CCMenu URL feature which creates such a token, or any other 3rd party integration token). No GitHub, session, or Shipit secrets are required beyond that one token they legitimately hold. Cost is a single HTTP GET with a modified `stack_id` route parameter; fully deterministic and repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e. `@stack ||= stacks.from_param!(params[:stack_id])`) instead of querying the unscoped `Stack` model directly, so that a client whose `stack_id` is set can only ever resolve to that stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped api client cannot read another stack's cc.xml" do
  scoped_client = shipit_api_clients(:here_come_the_walrus) # stack_id bound to shipit_stacks(:shipit)
  other_stack = shipit_stacks(:soc) # a different stack the client is NOT scoped to

  assert_equal shipit_stacks(:shipit).id, scoped_client.stack_id # binding as issued

  request.headers['Authorization'] = 'bleh'
  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  # EXPECTED (binding enforced): 404/403, current_api_client.stack_id != other_stack.id
  # ACTUAL: 200 OK, response body reflects other_stack, proving the scope was never checked
  assert_response :not_found # currently fails: actual response is :ok with other_stack's data
end
```
This demonstrates that `params[:stack_id]` is never cross-checked against `current_api_client.stack_id` in `Api::CCMenuController`, regardless of whether the client's `stack_id` was reassigned after token issuance.
