### Title
Webhook signature is verified against `repository.owner.login`, but the handler acts on `repository.full_name` — signature-authenticated organization does not bind to the repository/stack that gets modified (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The engine supports configuring one `GitHubApp` (with its own `webhook_secret`) per GitHub organization (documented in `docs/setup.md` "Using Multiple GitHub Applications"). `verify_signature` picks which app's secret to check the HMAC against using `repository.owner.login` (or `organization.login`) taken from the attacker-controlled JSON body itself, before the signature is validated. Once validated, the full, unconstrained `params` hash — including `repository.full_name` — is forwarded to the event handler, which uses `repository.full_name` (a field never tied to the signing key selection) to find the `Stack`/`Repository` to operate on.

### Finding Description
This breaks the intended binding: *the organization whose secret authenticated the request* == *the repository the request is allowed to affect*. An operator running multiple independently-managed GitHub Apps (one per org, as described in the docs) intends each org's webhook secret to only authorize webhook traffic for that org's own repositories. Because the two lookups use different, independently attacker-controllable JSON fields (`repository.owner.login` for auth, `repository.full_name` for effect), an attacker who legitimately possesses (or can compute HMACs with) one org's registered `webhook_secret` can craft a POST to the shared `/github/webhooks` endpoint where:
- `repository.owner.login` = `"attacker-org"` (their own org → passes `verify_webhook_signature` using the org's own key [6](#0-5) )
- `repository.full_name` = `"victim-org/victim-repo"` (a stack tracked by a different, unrelated organization on the same Shipit instance)

The controller only checks the signature once, globally, and never re-validates that the org selected for signing matches the org embedded in `repository.full_name` used by the handler.

### Impact Explanation
A successful forgery lets an attacker who only controls one configured organization's webhook credentials trigger `Shipit::Webhooks::Handlers::PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4)  against a `Stack` belonging to a different organization the attacker has no legitimate access to. Depending on the target stack's continuous-deployment configuration, this can drive unwanted GitHub syncs and downstream deploy/rollback pipeline actions for a repository/organization the attacker was never authorized to touch — a cross-repository/cross-organization action triggered purely from spoofed webhook payload fields.

### Likelihood Explanation
Requires the Shipit operator to be running the documented multi-organization GitHub App configuration and requires the attacker to control (or know the secret of) one of the configured orgs' GitHub Apps — no Shipit session, `ApiClient` token, or repository write access on the *target* org is needed. This is a real, reachable code path (not merely a stack.yml step) since `verify_signature` and the handler dispatch are both exercised on every webhook POST.

### Recommendation
Bind the signature-authenticating identity to the identity actually acted upon: derive the organization used both for HMAC-secret selection *and* for handler dispatch from the same, single authoritative field (e.g., always use `repository.full_name`'s owner segment, or the organization actually configured for the resolved `Stack`/`Repository`), and reject the webhook if the two disagree, mirroring the report's fix of making `WatcherClient` actually bind the update to the verified value rather than trusting a second, unverified field.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, one for `orga` and one for `orgb` (per `docs/setup.md` multi-org setup), each with its own `webhook_secret`.
2. As the holder of `orga`'s app webhook secret, POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {"owner": {"login": "orga"}, "full_name": "orgb/private-repo"},
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, raw_body)>`.
4. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `Shipit.github(organization: "orga")`, and the signature validates successfully [7](#0-6) .
5. `create` dispatches to `PushHandler`, which resolves stacks via `repository.full_name` = `"orgb/private-repo"` [8](#0-7)  and invokes `stack.sync_github` on a stack belonging to `orgb`, despite the request only ever being authenticated for `orga`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
