### Title
`StatusHandler#process` writes GitHub status updates to commits of **any** repository sharing the reported SHA, bypassing per-repository scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with a bare `Commit.where(sha: params.sha)` query that is not scoped to the repository that authenticated the webhook, unlike every other handler which restricts itself to `stacks` derived from `payload.dig('repository', 'full_name')`. Because the same commit SHA can legitimately exist in multiple stacks (e.g. forks sharing history, mirrored repos, or repos onboarded from the same upstream), a webhook signed for repository A can silently mutate the status of an identical commit tracked under repository B's stack.

### Finding Description
The invariant that should hold is:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated while processing a `status` webhook.

Tracing the code:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only validates that the payload was signed with the secret belonging to `repository_owner` (the GitHub App/organization installation) — it says nothing about which repository's *commits table* may be touched, and does not prevent a legitimately-owned attacker repository under a Shipit-tracked org/app installation from sending a real, correctly-signed `status` event.
- Every other handler in this codebase (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) restricts writes to `stacks`, computed as `Repository.from_github_repo_name(repository_name)&.stacks`, i.e. scoped strictly to the repository named in `payload['repository']['full_name']`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does **not** use `stacks` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`Commit.where(sha: params.sha)` is a bare, global lookup across the entire `commits` table with no `stack_id`/repository filter, and `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then writes a real `Status` row and re-evaluates `status`/`deployable?` for whatever commit(s) matched.

Exploit flow: the attacker owns (or forks) a public repository whose history is shared with a victim's tracked repository — the two therefore contain commits with identical SHAs. The attacker legitimately (via their own repo's GitHub Actions or the Statuses API, using their own repo's own token — no forged signature needed) sets `context: deploy/production`, `state: success` for that shared SHA. GitHub signs and delivers this webhook correctly for the attacker's own repository/organization, passing `verify_signature`. `StatusHandler` then matches the same SHA in the victim's `commits` table and writes the success status there too, via `Commit#create_status_from_github!` → `add_status`, which recomputes `deployable?`/`blocked?` for the victim's commit and calls `stack.schedule_merges` when state becomes `success`/`pending` (`app/models/shipit/commit.rb:374-386`). If the victim stack requires `deploy/production` as part of its `required_statuses`/`blocking_statuses`, this can flip a commit from blocked to deployable (or vice versa with a `failure`/`error` state), independent of what the victim's real CI actually reported.

None of the listed guards prevent this: `verify_signature` authenticates *origin*, not *target commit ownership*; there is no repository/stack scoping equivalent to `Handler#stacks` inside `StatusHandler`; `ExplicitParameters` only validates parameter shape, not authorization; there is no `User#authorized?`/`require_permission!` check on this unauthenticated webhook path by design.

### Impact Explanation
A webhook correctly authenticated for repository A can write a `Status` record — and thereby change `deployable?`/`blocked?` — for a `Commit` belonging to a completely different stack/repository B, as long as the two share a commit SHA. This is exactly the "payload for one repository mutating another's stack/commit" class of Critical finding. Because status changes feed into `stack.schedule_merges` and the general deployability evaluation used by continuous-deployment flows, this can be leveraged to unblock (or block) commits for deployment in a repository the attacker does not control, with the potential to cause deployment of unintended state or denial of legitimate deploys. The blast radius covers every stack that has ever ingested the same commit SHA as one owned/forked by the attacker — this is not limited to a single victim and is repeatable at will (each `status` event is a fresh HTTP webhook).

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository under an organization/installation that Shipit's `Shipit.github(organization:)` config recognizes (so `verify_signature` passes with a real GitHub-issued signature), and (b) a commit SHA shared with a victim stack's `commits` table (achievable via forks of a common upstream, or simply because the same code was pushed to multiple mirrored repos tracked by different stacks). Given those, the attack requires only setting a commit status on the attacker's own commit via the ordinary GitHub Statuses API or Actions — no secrets, no privilege escalation, fully repeatable. The main uncertainty is how commonly SHA collisions across independently-tracked stacks occur in a given deployment of Shipit (fork-heavy or monorepo-mirroring organizations are most exposed); this affects likelihood but not the validity of the underlying missing-scoping bug.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
or otherwise join through `Stack`/`Repository` so only commits belonging to the repository named in `payload['repository']['full_name']` can be updated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, pseudocode):
```ruby
test "status for one repository must not affect a commit of another repository with the same sha" do
  attacker_stack = shipit_stacks(:shipit) # repo: "org/attacker-repo"
  victim_stack   = shipit_stacks(:cyclimse) # repo: "org/victim-repo", continuous_deployment: true, required_statuses: ["deploy/production"]

  shared_sha = "a" * 40
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared commit")
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "shared commit")

  before = victim_commit.reload.deployable?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'deploy/production',
    'repository' => { 'full_name' => 'org/attacker-repo', 'owner' => { 'login' => 'org' } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  after = victim_commit.reload.deployable?

  refute_equal before, after, "victim stack's commit deployability changed due to a webhook that only authenticated for the attacker's repository"
  assert victim_commit.statuses.exists?(context: 'deploy/production', state: 'success'),
         "a Status row was written on a commit belonging to a repository that did not authenticate the webhook"
end
```
This demonstrates the equality `commit.stack.repository.full_name == payload['repository']['full_name']` is violated: the victim commit (repo `org/victim-repo`) receives a status write and a `deployable?` transition despite the webhook being authenticated only for `org/attacker-repo`.     def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
