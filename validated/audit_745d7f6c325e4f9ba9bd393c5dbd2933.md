### Title
Missing Zero-Address Validation on `creator` in `initialize_with_permission` Permanently Freezes Creator Fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` accepts an arbitrary, unvalidated `creator` account and stores it directly into `PoolState.pool_creator` without any zero-address (or sanity) check, mirroring the exact bug class described in the external report (missing zero-address checks on critical addresses in `GSP.sol`). Because `pool_creator` is later required to be a `Signer` in `collect_creator_fee` and is used as the token-account authority in `collect_creator_fee_permissionless`, setting it to the default/zero `Pubkey` permanently locks any creator fees accrued by the pool.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as a plain `UncheckedAccount` with no ownership or non-default constraint: [1](#0-0) 

It is written straight into `pool_state.pool_creator` via `PoolState::initialize`, again with no validation: [2](#0-1) 

`PoolState::initialize` itself performs no zero-address check on `pool_creator` either: [3](#0-2) 

This differs from `initialize` (non-permissioned path), where the `creator` field is a `Signer` tied to the actual transaction signer, so it can never be the default `Pubkey`: [4](#0-3) 

Downstream, `pool_creator` is used as the sole authority for collecting creator fees. `collect_creator_fee` requires a `Signer` whose key equals `pool_creator`: [5](#0-4) 

`collect_creator_fee_permissionless` allows anyone to trigger fee transfer, but the destination ATA authority is still `pool_creator`: [6](#0-5) [7](#0-6) 

If `creator` is set to `Pubkey::default()` (`11111111111111111111111111111111`, the System Program ID), no keypair exists that can ever sign as this address, so `collect_creator_fee` becomes permanently unusable for the pool. The permissionless path still functions and will happily create an associated token account whose authority is the default `Pubkey` and transfer the accumulated `creator_fees_token_0`/`creator_fees_token_1` into it — but since no entity controls that authority, those tokens become permanently unrecoverable once transferred there.

### Impact Explanation
Every pool created via `initialize_with_permission` enables creator fees by default (`enable_creator_fee = true`, per the `pool_state.initialize(...)` call), and creator fees accrue continuously from trading volume via `creator_fee_on`. If `pool_creator` is left/set as the zero address, all accumulated creator fees for that pool are permanently frozen — either stuck in `PoolState` forever (since the only privileged collection path requires an impossible signer) or, if collected permissionlessly, sent into an ATA that no one can ever withdraw from. This is a permanent freezing of pool-derived funds, matching the Medium-severity impact bar (permanent freezing of user/LP-adjacent funds).

### Likelihood Explanation
This is reachable in a single transaction: any account with a valid `Permission` PDA (obtained via the `create_permission_pda` admin instruction — a legitimate, non-privileged pool creator in the trust model of this instruction) can call `initialize_with_permission` and simply pass `Pubkey::default()` (or any account without a corresponding keypair) for the `creator` account, since it is attacker-chosen and completely unconstrained. No additional privilege beyond what `initialize_with_permission` already grants is required, and the bug can also occur accidentally due to a client-side bug supplying an uninitialized/zeroed public key.

### Recommendation
Add an explicit non-default check on `creator` in `InitializeWithPermission`, e.g.:
```rust
require_keys_neq!(creator.key(), Pubkey::default(), ErrorCode::InvalidInput);
```
either as an Anchor `constraint` on the `creator` account or as a runtime check at the start of `initialize_with_permission`, before `pool_state.initialize(...)` is called. The same defensive check should also be applied wherever `pool_creator` could be mutated in the future.

### Proof of Concept
1. Admin runs `create_permission_pda` for an attacker/payer address, granting it the ability to call `initialize_with_permission`.
2. Attacker (as `payer`) calls `initialize_with_permission`, supplying `creator = Pubkey::default()` (System Program ID) instead of their own or any real keypair address.
3. `pool_state.pool_creator` is set to the zero address; `enable_creator_fee` is `true` by default.
4. As trades occur, `creator_fees_token_0`/`creator_fees_token_1` accumulate in `PoolState`.
5. `collect_creator_fee` can never succeed because no signer can match `pool_creator == Pubkey::default()`.
6. `collect_creator_fee_permissionless` can be called by anyone; it creates an ATA with `authority = Pubkey::default()` and transfers the accrued fees into it — funds are now permanently inaccessible since no private key corresponds to the default `Pubkey`.
