### Title
Webhook authentication binds to `repository.owner.login`'s GitHub App secret, but every event handler acts on the independently-attacker-controlled `repository.full_name` field - allowing cross-organization webhook spoofing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to validate a delivery against using `repository_owner` (`params.dig('repository', 'owner', 'login')`), then verifies the HMAC over the whole raw body. However, every downstream `Shipit::Webhooks::Handlers::Handler` subclass (e.g. `PushHandler`, and the `Handler#stacks`/`#repository_name` helpers) resolves the target `Repository`/`Stack` using a *different* JSON field: `payload.dig('repository', 'full_name')`. Because the HMAC only proves "this body was signed with organization X's secret", not "this body's `repository.full_name` belongs to organization X", an attacker who legitimately controls the webhook secret for their own onboarded GitHub organization on a shared, multi-tenant Shipit instance can forge a JSON payload where `repository.owner.login` is their own org (to pick the correct/known secret) while `repository.full_name` names a repository/stack belonging to a completely different organization on the same instance.

### Finding Description
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does: `github_app = Shipit.github(organization: repository_owner)`, then `github_app.verify_webhook_signature(signature, raw_post)`. `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (line 61).
- `verify_webhook_signature` (`lib/shipit/github_app.rb`) just does an HMAC-SHA1 comparison against the secret configured for whichever organization was named in `repository_owner`. This only proves the sender knows *that org's* secret; it says nothing about the rest of the JSON body's content being consistent with that org.
- After signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:12`) dispatches the *entire, attacker-supplied* parsed payload to handlers.
- `Shipit::Webhooks::Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) reads `payload.dig('repository', 'full_name')` — a sibling field of `repository.owner.login`, but never cross-checked against it. `#stacks` then does `Repository.from_github_repo_name(repository_name)&.stacks`.
- Concretely, `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the branch resolved from `repository.full_name`, regardless of which org's secret authenticated the request.
- On a Shipit deployment configured for multiple GitHub organizations (as documented in `config/secrets.development.shopify.yml` and `docs/setup.md`, each org has its own `app_id`/`installation_id`/`webhook_secret`), the equality that should hold is: `organization whose secret signed the request == organization owning the repository the handlers act on`. This binding is never enforced — the signature only authenticates `repository.owner.login`, while every handler trusts `repository.full_name` unconditionally.

### Impact Explanation
An attacker who is a legitimate GitHub App administrator for *any one* organization hosted on a shared Shipit instance can forge webhook deliveries whose `repository.full_name` points at a stack owned by a *different* tenant organization. Since `PushHandler` triggers `stack.sync_github`, and other handlers (`status`, `check_suite`, `merge_status`, `deployable_status` per `Hook::EVENTS`) similarly resolve their target stack purely from `repository.full_name`, this allows an unprivileged-with-respect-to-the-victim attacker to inject synthetic CI/check/commit-status and sync events into a victim organization's stacks. This can corrupt deployability state (fake passing CI status) that Continuous Delivery/manual deploy gates rely on, potentially enabling an unauthorized deploy of unreviewed code on the victim's stack — meeting the "unauthorized deploy" impact bar for cross-tenant installations of this engine.

### Likelihood Explanation
Requires the attacker to control a valid webhook secret for *some* organization configured in the same multi-tenant Shipit instance (a realistic scenario per the engine's own documented multi-org config support), and to be able to POST directly to the shared `/webhooks` endpoint with a self-crafted, self-signed JSON body (not a replay of a genuine GitHub delivery, since GitHub itself would keep `repository.owner.login` and `repository.full_name` consistent). This is plausible in any shared/self-service Shipit deployment onboarding multiple orgs, but not exploitable against a single-tenant deployment where only one org/secret exists.

### Recommendation
After signature verification, re-derive the authorized organization from the signature-selected GitHub App/config and assert that `payload.dig('repository', 'full_name')` (and `organization.login`) is actually owned by that organization (e.g., compare `repository.full_name.split('/').first.casecmp(repository_owner)`) before dispatching to any handler. Alternatively, bind `Shipit.github(organization:)` lookups strictly to a value that is cryptographically tied to the same field handlers use (`repository.full_name`'s owner segment) rather than a loosely-related `repository.owner.login`/`organization.login` fallback pair.

### Proof of Concept
1. Deployment hosts two tenants: `victim-org/app` (with its own `webhook_secret: S_v`) and `attacker-org/whatever` (with its own known `webhook_secret: S_a`, known to the attacker because they administer that org's GitHub App).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, e.g. an unreviewed commit sha on victim-org/app>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/app"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_a, body)` using their own known secret `S_a`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against `S_a` — request passes.
5. `Shipit::Webhooks::Handlers::PushHandler#process` resolves `repository_name` from `payload.dig('repository','full_name')` = `"victim-org/app"`, looks up `victim-org/app`'s stacks, and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — a legitimate victim stack is acted on using only the attacker's own, unrelated organization credentials. module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
