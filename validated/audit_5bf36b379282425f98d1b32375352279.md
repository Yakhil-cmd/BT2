### Title
Cross-repository status forgery flips `Commit#deployable?` via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no scoping to the repository/stack the webhook actually belongs to, then attaches the incoming status to every matching `Commit` record in the database. Since `Commit#deployable?` and `Commit#blocked?` aggregate over `stack.commits`/`statuses` without verifying the status's origin repository matches the commit's own stack repository, a status delivered for a SHA that happens to exist in the attacker's own repository (e.g. a fork sharing history with the victim repo, or two stacks tracking repos with overlapping commit history) can flip an unrelated victim stack's commit to "deployable" and trigger `Shipit::Stack#trigger_continuous_delivery`.

### Finding Description
The binding that should hold is: `status.commit.stack.github_repo_name == webhook_payload.repository.full_name` (the status just ingested must belong to the same repository as the commit it's attached to). This binding is broken.

Path:
1. `Shipit::WebhooksController#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates the HMAC signature scoped only to the `repository_owner` (organization) derived from the payload, using `Shipit.github(organization: repository_owner)` [1](#0-0) 
2. `StatusHandler#process` receives `sha`, `state`, etc., and does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is **not scoped by `repository` or `stack_id`** — any `Commit` record anywhere in the Shipit database sharing that `sha` receives the forged status [2](#0-1) 
3. `Commit#create_status_from_github!` calls `add_status`, which creates a `Status` row tied to `stack_id` (the *victim's* stack, from `commit.stack_id`) and re-evaluates `status` [3](#0-2) 
4. `Commit#deployable?` combines `!locked?` with `(stack.ignore_ci? || (success? && !blocked?))`; `success?` is delegated to `status`, which is `Status::Group.compact(self, statuses_and_check_runs)` — aggregating over ALL `statuses` attached to the commit, regardless of which repository actually produced them [4](#0-3) [5](#0-4) 
5. `add_status` then calls `stack.schedule_merges` and fires `schedule_continuous_delivery`, feeding into `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `deployable_commits` → `commits.to_a.reverse.find(&:deployable?)` → `trigger_deploy`, exactly as described in the question.

Root cause: `Commit.where(sha: params.sha)` has no `stack_id`/repository filter, so a same-SHA collision across two unrelated stacks (trivially achievable when an attacker forks the victim's public repo, since forked commits retain identical SHAs up to the fork point) lets the attacker inject a `success` status into the victim's commit's status aggregate by triggering a real GitHub status webhook against their own repository for that shared SHA. `verify_signature` only confirms the webhook truly originated from GitHub for *some* organization known to this Shipit instance — it does not verify that the `repository` in the payload corresponds to the stack whose commit is being updated, so it does not block this cross-repository write.

### Impact Explanation
An attacker who owns a repository containing a SHA that also exists in a victim's tracked stack (via forking or any repo sharing history with a target) can, by simply setting a commit status via GitHub on their own repo, inject a `Status` record into an unrelated victim's `Commit`. If that status is the last blocker preventing `Commit#deployable?` from being true (and the victim stack is otherwise unlocked, idle, and has no other checks blocking), this results in an **unauthorized deploy being triggered on the victim stack** — a record (`Deploy`) being written and a deployment executed for a stack the attacker never authenticated against. This matches the Critical impact category: "an unauthorized deploy... or a payload for one repository mutating another's stack, commit, task."

### Likelihood Explanation
Preconditions: the victim stack must be unlocked, idle (`active_task?` false), and any `deployment_checks` already passing (or continuous deployment enabled with no other blocking statuses) — plausible default configuration. The attacker needs a repository that shares a commit SHA with the victim's tracked repo — realistically achievable by forking a public victim repo (fork commits are bit-identical, same SHA, until divergence) and has the GitHub App/webhook integration active on their own repo (or org) so a genuine signed webhook is delivered. This is consistent with the explicitly allowed attacker capability "emit webhooks from a repository they own." No secrets, tokens, or privileged roles are required — the attacker only needs to control a fork and set a commit status via the normal GitHub Status API on their own repository.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the equivalent `CheckRunHandler`) to the repository present in the webhook payload, e.g.:
```ruby
def process
  Commit.joins(:stack).merge(Stack.where(repo_owner: params.repository.owner.login, repo_name: params.repository.name))
        .where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
so a status is only ever attached to commits belonging to a stack whose repository matches the webhook's originating repository.

### Proof of Concept
Minitest plan (integration-level, no live GitHub, exercising `StatusHandler` directly to model the forged webhook plus `stack.trigger_continuous_delivery`):
```ruby
test "cross-repo status cannot make an unrelated commit deployable" do
  victim_stack = shipit_stacks(:shipit) # e.g. repo "shopify/shipit-engine"
  attacker_repo_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: attacker_repo_sha, message: "victim commit", author: users(:walrus))
  # seed as non-deployable: required status missing/pending
  assert_not victim_commit.deployable?

  # Forge a status "delivered" for an unrelated repo/app_id but same sha
  payload = Webhooks::Handlers::StatusHandler::Params.new(
    sha: attacker_repo_sha, state: "success", context: "ci/attacker-repo",
    repository: { full_name: "attacker/unrelated-fork" }
  )
  Webhooks::Handlers::StatusHandler.new.process # simulating params.sha match

  victim_commit.reload
  assert victim_commit.deployable?, "commit became deployable from an unrelated repo's status"

  assert_difference -> { victim_stack.deploys.count }, 1 do
    victim_stack.trigger_continuous_delivery
  end
end
```
Assertions on both sides of the binding: before, `victim_commit.stack.github_repo_name` ("shopify/shipit-engine") != forged `payload.repository.full_name` ("attacker/unrelated-fork") — yet after `StatusHandler#process`, `victim_commit.statuses` contains the forged status and `victim_commit.deployable?` flips to `true`, demonstrating the equality is never checked and a `Deploy` is created for a repository that did not authenticate the status.
