### Title
Opaque route bytes can smuggle an unrelated signed token transfer inside `swap_collateral` - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts opaque route bytes and forwards them to the configured router after authorizing only the controller's own input transfer. Because the controller validates only its measured input spend, positive output, and final account risk, a malicious route-selected contract can add a separate token transfer under the caller's signed authorization tree. If a victim signs the simulation-produced tree, the strategy can complete normally while unrelated wallet assets are stolen.

### Finding Description
`Controller::swap_collateral` accepts caller-provided `swap` bytes and forwards them unchanged into `process_swap_collateral`. [1](#0-0)  After account authorization, `process_swap_collateral` withdraws the caller's collateral and reaches `swap_tokens_or_passthrough`. [2](#0-1) [3](#0-2) 

For distinct token addresses, `swap_tokens` authorizes exactly one `token_in.transfer(controller, router, amount_in)` invocation, but then executes the caller-supplied route through `router.execute_strategy`. [4](#0-3)  Its post-call checks bound only changes to the controller's `token_in` and `token_out` balances and require positive measured output. [5](#0-4) [6](#0-5) 

Those checks do not constrain other token contracts reached by route-selected code. The repository's threat model states that route pool/token addresses are not allowlisted and that third-party code under the caller's authorization can add a caller-token transfer as a child authorization. [7](#0-6)  The security test demonstrates that simulation records such a transfer beneath `swap_collateral` and that signing the poisoned tree permits it. [8](#0-7) [9](#0-8) 

### Impact Explanation
This enables theft of user funds beyond the collateral being swapped. A malicious route can pay a valid `token_out` amount so the controller's measured-output and solvency checks pass, while a route-selected contract transfers any unrelated caller-owned token to the attacker. The test demonstrates an unrelated wallet token balance moving from the victim to the attacker while the collateral swap still credits the expected output. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
The attacker can deploy the route-selected contract and construct the malicious `swap` bytes without privileges. The victim must sign the simulation-generated authorization tree containing the additional child transfer, so this requires user interaction and a client or signer that does not reject unexpected child invocations. The tested result shows that the extra transfer is present in the simulated tree and is accepted once signed. [12](#0-11) 

### Recommendation
Constrain route-selected pool and token contracts to a governance-managed allowlist appropriate for each supported venue, rather than accepting arbitrary addresses from route bytes. Reject routes containing undeclared external contracts and enforce canonical route decoding before execution. In addition, controller-facing clients and transaction preparation should fail closed if the simulated caller authorization tree contains any child invocation other than the expected route input transfer.

### Proof of Concept
1. The attacker deploys a malicious contract that implements the selected venue's expected call interface. During execution it calls `token::transfer(victim, attacker, victim_balance)` for an unrelated token and still returns enough route output to satisfy the swap.
2. The attacker constructs opaque `swap` bytes whose route selects that contract.
3. The victim invokes `swap_collateral(caller=victim, account_id, current, amount, new, malicious_swap)`.
4. The controller authorizes only its own `token_in.transfer(controller, router, amount_in)` and invokes the router with the supplied bytes. [13](#0-12) 
5. Simulation records the malicious wallet-token transfer as a child of the victim's `swap_collateral` authorization. The repository's regression test asserts that exact recorded authorization shape. [14](#0-13) 
6. If the victim signs that tree, the unrelated wallet token is transferred to the attacker while the swap returns a positive output and passes the controller's post-swap checks. [10](#0-9)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
