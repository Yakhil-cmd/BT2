**Analysis:** `get_allowed_structs` is a pure function that deterministically returns one of two static, immutable maps (`OLD_ALLOWED_STRUCTS` or `NEW_ALLOWED_STRUCTS`) based on a single `bool` parameter [1](#0-0) . This boolean (`struct_constructors_feature`) originates from the VM's on-chain feature-flag configuration, not from any attacker-controlled transaction/authenticator input — it cannot be toggled per-transaction by an unprivileged caller [2](#0-1) .

Within a single call to `validate_view_function` or `validate_combine_signer_and_txn_args`, `allowed_structs` is resolved once and consistently threaded through `construct_args` → `construct_arg` → `recursively_construct_arg`, so the same map is used for both the "is this struct allowed" check and the actual struct-construction path [3](#0-2) . There is no mutable global state or shared cache keyed independently of the flag that could let a struct disallowed under one flag state leak into acceptance under another — the two static `Lazy` maps are read-only and never merged or corrupted across calls [4](#0-3) .

This has nothing to do with sender/signer/sequence/chain-id/replay/fee-payer binding described in the admission boundary gate — it is purely an internal whitelist selection for BCS argument construction, gated by node configuration, not by unprivileged transaction input.
