### Title
Webhook signature is verified against `repository.owner.login`, but write actions are performed against the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate the inbound signature against using the payload's `repository.owner.login` field, but every event handler that actually mutates state (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) resolves the target `Stack`/`Repository` using a completely different, unrelated payload field: `repository.full_name`. The signature check never ties these two fields together, so a payload that is "authenticated" for one organization can drive writes against a stack belonging to a different organization.

### Finding Description
`verify_signature` computes the organization used to pick the `GitHubApp` config purely from the request body: [1](#0-0) [2](#0-1) 

That organization's `GitHubApp#verify_webhook_signature` is then used to accept or reject the whole request: [3](#0-2) 
Notably, `return true unless webhook_secret` — if the org resolved from `repository.owner.login` has no `webhook_secret` configured (an explicitly documented *optional* setting, shown as `nil` in the setup docs and secrets templates), the signature check passes unconditionally regardless of the actual `X-Hub-Signature` header. [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, `create` dispatches the *entire* raw JSON body to every registered handler for the event: [6](#0-5) 

Every default handler, however, resolves the actual `Repository`/`Stack` to mutate from `repository.full_name`, not from `repository.owner.login`: [7](#0-6) [8](#0-7) [9](#0-8) 

Nothing enforces that `full_name`'s owner segment matches `owner.login`. This is structurally identical to the reported bug class: a value used to gate/compute a security-relevant check (`fundingFeePerUnit` computed once and blindly reused for every subsequent liquidated account) is silently substituted for the value that should actually govern the operation on each individual entity (each position's own size/mark price). Here, the "signed/verified" identity (`owner.login`, tied to a specific `GithubApp`/secret) is decoupled from the identity that is actually acted upon (`full_name`, used to find the target `Repository`/`Stack`), and the controller never re-validates that the two agree.

### Impact Explanation
In a Shipit deployment hosting stacks for multiple GitHub organizations (a supported configuration — see the multi-org example in `config/secrets.development.example.yml`), if any one configured organization has no `webhook_secret` set (the documented default/optional state), an attacker can submit a payload where:
- `repository.owner.login` = the unsecured organization (signature check trivially passes, `return true unless webhook_secret`)
- `repository.full_name` = `victim-org/victim-repo` (any other stack hosted by the same Shipit instance)

The dispatched handlers act on `victim-org/victim-repo` despite the request never being validated against that organization's actual webhook secret. Depending on event type this allows an unprivileged, unauthenticated actor to:
- Force `stack.sync_github(expected_head_sha:)` on arbitrary stacks via `push` (`PushHandler`).
- Inject forged `Status`/`check_suite` results via `StatusHandler`/`CheckSuiteHandler`, which feed directly into Shipit's CI-gating logic used to decide whether a commit is deployable — enabling an unauthorized deploy of unreviewed code.
- Archive/unarchive review stacks and mutate pull request state via the `PullRequest::*` handlers.

This crosses the "organization that authenticated versus the repository that is written" trust boundary and lands squarely in the "unauthorized deploy" / cross-repository-write impact category.

### Likelihood Explanation
Likelihood depends on deployment configuration: it is guaranteed to be exploitable in the common single-org case where `github.webhook_secret` is left unset (the documented default), and is exploitable in multi-org setups whenever at least one configured organization omits its secret. No session, `ApiClient` token, or GitHub App private key is required by the attacker — only network access to the public `/webhooks` endpoint and knowledge of any onboarded org name/repo full_name pairing, both of which are typically public GitHub information.

### Recommendation
Bind signature verification to the exact entity being mutated, not just an org-level string pulled from an unverified field:
- Reject events where `repository.owner.login` (or `organization.login`) does not match the owner segment of `repository.full_name`.
- In `Handler#stacks`/`Handler#repository_name`, cross-check that the resolved `Repository`'s `owner` equals the organization that was used to select and validate the webhook secret in `WebhooksController#verify_signature`, rejecting the event otherwise.
- Treat a missing `webhook_secret` as "reject all events for this org" rather than "always verified", or at minimum warn loudly and disable cross-repository handler dispatch when any configured org has no secret.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `org-a` (no `webhook_secret`, i.e. `webhook_secret: null`) and `org-b` (has a `webhook_secret` and an active `Stack`).
2. Send an unauthenticated `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. `verify_signature` resolves `repository_owner` = `org-a`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no secret configured) — see [10](#0-9) .
4. `PushHandler` then resolves stacks via `Repository.from_github_repo_name("org-b/victim-repo")` (per `Handler#repository_name`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `org-b`'s stack, despite the request never being validated with `org-b`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
