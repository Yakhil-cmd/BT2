### Title
Webhook `status` events are matched globally by commit SHA, breaking the organization-that-authenticated vs. repository-that-is-written binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using a payload field, `repository.owner.login` (falling back to `organization.login`), taken from the attacker-supplied JSON body itself. [1](#0-0) [2](#0-1)  Once that check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` looks up the target `Commit` purely by `sha`, with **no repository or organization scoping at all**, unlike every other handler (e.g. `PushHandler`, the `PullRequest::*` handlers) which resolve the acting repository via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature == organization that owns the repository/commit being mutated`. In this engine that equality is never enforced for the `status` event:

- `verify_signature` derives the org used to pick the webhook secret exclusively from the JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')`. [2](#0-1)  `GitHubApp#verify_webhook_signature` additionally short-circuits to `true` whenever that organization's `webhook_secret` is blank: `return true unless webhook_secret`. [6](#0-5)  `docs/setup.md` explicitly documents the webhook secret as "(optional)", and every fixture/sample secrets file in the repo ships with `webhook_secret: # nil`. [7](#0-6) 
- `StatusHandler#process` never consults `repository.full_name`, `repository.owner.login`, or any `Repository`/`Stack` scope; it simply does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` across the entire Shipit instance's commit table. [3](#0-2) 

Consequently, once a delivery is accepted for *any* configured organization name (including one with no `webhook_secret` set — a fully credential-free path), the attacker's `sha` field can name a commit belonging to a *completely different* repository/organization tracked by the same Shipit instance, and `StatusHandler` will happily create/replace that commit's CI status. Commit SHAs are public GitHub data, not secrets, so an attacker does not need any access to the victim repository to learn them.

### Impact Explanation
`Commit#create_status_from_github!` feeds directly into `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and, on a `success` transition, `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` for stacks with `continuous_deployment` enabled. [8](#0-7) [9](#0-8)  A forged, cross-repository "success" status therefore lets an attacker who controls no more than the name of an unrelated, laxly configured (or unconfigured-secret) organization in the same multi-tenant Shipit deployment (1) bypass CI gating for a commit in a repository they have no relationship to, and (2) trigger an unauthorized automatic deploy on that victim stack — satisfying the "unauthorized deploy" Critical-tier impact.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment (the engine explicitly supports and documents `config/secrets*.yml` with multiple GitHub orgs, e.g. `test/dummy/config/secrets_double_github_app.yml`) where at least one configured org has no `webhook_secret` — a state the setup documentation calls "optional," not a misconfiguration. No `ApiClient` token, session, GitHub App private key, or repository write access is needed; the only requirement is knowledge of a target commit's public SHA and the name of one lax/unsecured org already present in the deployment's config.

### Recommendation
`StatusHandler` (and any other handler that trusts payload-embedded commit identifiers) must resolve and scope to the `Repository`/`Stack` derived from `payload.dig('repository','full_name')` — exactly as `PushHandler` and the `PullRequest::*` handlers already do — before touching `Commit` records, and must reject the event if the repository resolved from the signature-authenticating organization does not match the repository the commit belongs to. Additionally, `GitHubApp#verify_webhook_signature` should not silently accept unsigned deliveries when `webhook_secret` is blank in a multi-organization configuration; at minimum this should be strongly discouraged/blocked when more than one organization is configured.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (no `webhook_secret`, as shown to be a supported/documented configuration) and `OrgB` (has a tracked `Stack`/`Repository` and a pending commit with SHA `deadbeef...` visible publicly on GitHub).
2. As an outside attacker with no Shipit account, no `ApiClient` token, and no relation to `OrgB`, POST to `/webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "sha": "deadbeef...",
     "state": "success",
     "context": "ci/attacker-forged",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/unrelated-repo" }
   }
   ```
   Any `X-Hub-Signature` value (even garbage) is accepted because `verify_webhook_signature` returns `true` unconditionally for `OrgA` (blank secret) per `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
3. `WebhooksController#create` dispatches to `StatusHandler`, which finds the commit purely `Commit.where(sha: "deadbeef...")` — the `OrgB` commit — with zero check that it belongs to `OrgA` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) — and creates a `success` status on it.
4. If `OrgB`'s stack has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` enqueues an unauthorized deploy of that commit (`app/models/shipit/commit.rb:281-287`).

Note: I was unable to further inspect `lib/shipit.rb`'s `Shipit.github`/`GithubOrganizationUnknown` resolution logic in this final pass beyond confirming its match count; behavior for organization names that don't exist at all in config (full rejection) versus organizations present but secret-less (accepted) is inferred from `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` guard and the webhook controller's rescue block, which are both directly cited above.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
