## Title
Cross-organization webhook forgery: signature verified against `repository.owner.login`, but the `Handler` base class dispatches on the unrelated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a webhook against using `repository_owner`, a value pulled straight out of the *unverified* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the HMAC check passes (meaning only that the payload was signed with the secret belonging to that claimed owner), every `Shipit::Webhooks::Handlers::Handler` subclass locates the target `Repository`/`Stack` using a *different, independently-attacker-controlled* field: `payload.dig('repository', 'full_name')`. Nothing ties the verified owner to the repository that is actually written to. In a multi-organization Shipit deployment (a configuration explicitly supported, see `config/secrets.development.example.yml` and `docs/setup.md`), this lets a party who legitimately controls a webhook-signing secret for one configured organization forge events that mutate state belonging to a completely different configured organization/repository.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The key selected for HMAC verification (`Shipit.github(organization: repository_owner)` → `lib/shipit.rb#github`/`#github_app_config`) is chosen from a value inside the same untrusted, not-yet-verified `raw_post`. This is by itself a workable "key id" pattern *if* every downstream consumer trusts only the field that was actually bound to that key. It is not: [2](#0-1) 

`app/models/shipit/webhooks/handlers/handler.rb`, the base class used by every registered webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.), resolves the repository/stack to mutate using an entirely separate field, `repository.full_name`, with no cross-check against `repository_owner`/organization used for signature verification:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` simply looks the repo up by owner/name parsed out of that field, with no relation back to whichever organization's secret validated the request: [4](#0-3) 

Concrete example of impact — `StatusHandler`, which fabricates commit CI statuses that gate `ci.require` deploy eligibility, keys entirely off `Commit.where(sha: params.sha)` after the handler has already scoped nothing to the verified organization: [5](#0-4) 
And `CheckSuiteHandler`/`PushHandler` resolve the target stack purely from `stacks` (i.e., `repository.full_name`): [6](#0-5) [7](#0-6) 

**The equality that should hold, but doesn't:**
`organization that produced a valid signature == owner of the repository whose Stack/Commit/PullRequest state is mutated`

Before the fix, these can diverge because they come from two unrelated JSON keys (`repository.owner.login`/`organization.login` vs `repository.full_name`) that an attacker who controls the raw JSON body (and who is entitled to sign at least one configured org's webhooks) can set independently. After a correct fix, the handler would need to derive the acted-upon repository from the same claim that was cryptographically verified, or verify that the two agree.

### Impact Explanation
This is a High-severity issue: in a multi-org Shipit instance, an attacker who has legitimate write/webhook access to Organization A (which they administer or which has installed the GitHub App/webhook config Shipit trusts) can forge a payload whose `repository.owner.login`/`organization.login` says "OrgA" (so it validates against OrgA's `webhook_secret`) while `repository.full_name` names a repository belonging to OrgB (also configured in the same Shipit instance). This allows:
- Injecting fake `status` events to spoof CI results for OrgB's commits, unblocking `ci.require` gates and enabling an unauthorized deploy of OrgB's stack.
- Triggering `push`/`GithubSyncJob` syncs, `check_suite` refreshes, or PR-state mutations (label/merge bookkeeping) against OrgB's stacks the attacker has no legitimate access to.

This crosses the "cross-repository writes"/"unauthorized deploy" impact bar defined by the rules, without requiring an `ApiClient` token, session, or privileged Shipit account — only the ability to sign a webhook for any one org that the same Shipit instance is configured to serve.

### Likelihood Explanation
Requires: (a) a Shipit deployment configured with more than one GitHub organization (a documented, supported configuration — `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` multi-org schema), and (b) the attacker controlling a legitimate webhook-signing capability for at least one of those organizations (e.g., being an admin of one of the smaller/less-trusted orgs sharing the same Shipit instance, a realistic multi-tenant scenario this engine is explicitly built to support). No GitHub App private key, `api_clients_secret`, or Shipit session is needed — the attacker crafts and POSTs their own signed JSON directly to `/webhooks`.

### Recommendation
In `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, resolve the repository using the same organization value that was authenticated in `WebhooksController#verify_signature` (or pass the verified organization down and assert `repository.full_name`'s owner segment matches it before looking up/mutating anything). Alternatively, scope `Repository.from_github_repo_name` lookups by the verified organization, rejecting payloads whose `repository.owner.login`/`organization.login` do not match the owner segment embedded in `repository.full_name`.

### Proof of Concept
1. Configure Shipit for two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (supported multi-org schema).
2. As an admin/webhook operator for `OrgA` (legitimately holding `OrgA`'s `webhook_secret`), build a JSON body:
```json
{
  "organization": { "login": "OrgA" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<victim commit sha in OrgB>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Sign the raw body with `OrgA`'s webhook secret and set `X-Hub-Signature`/`X-Github-Event: status`, POST to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the HMAC check succeeds because it was actually signed with `OrgA`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — since it never re-checks the organization, it creates a fabricated successful CI status on `OrgB`'s commit, potentially satisfying `ci.require` and enabling an unauthorized deploy of `OrgB`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
