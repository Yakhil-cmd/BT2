### Title
Membership webhook `organization.login`/`team.organization` is independent from the signature-verification org (`repository.owner.login`), letting an attacker forge a `Team` row that collides with an unresolved `Shipit.github_teams` handle - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the signing organization (and thus the webhook secret to check against) from `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')` only if `repository` is absent. `MembershipHandler#find_or_create_team!` instead trusts `params.organization.login` unconditionally to set the new `Team#organization`. Because `repository` is not part of the handler's declared schema, an attacker can include a `repository.owner.login` equal to an org they legitimately control (and whose webhook secret they know) purely to pass signature verification, while setting the separate `organization.login` field to an arbitrary victim org string that ends up written into the `Team` row.

### Finding Description
The claimed binding is: `Team(organization, slug)` backing a `Shipit.github_teams` handle == the real GitHub team fetched from GitHub for that `organization/slug` [1](#0-0) . `Shipit.github_teams` lazily resolves each configured handle via `find_by(organization:, slug:) || fetch_and_create_from_github(...)`, so whichever `Team` row already exists for that `organization+slug` pair wins, with no verification that it was actually created from a real GitHub API lookup [2](#0-1) .

`MembershipHandler` creates/updates a `Team` keyed by `github_id` (attacker-controlled integer from the webhook body) and sets `team.organization = params.organization.login` directly from the JSON body [3](#0-2) .

The signature check, however, derives the org used to pick the webhook secret from a *different* field, preferring `repository.owner.login` over `organization.login`: [4](#0-3) [5](#0-4) 

`MembershipHandler`'s param schema does not declare `repository` at all [6](#0-5) , and the raw JSON body is passed straight through as `payload`/`params` to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) , so an unvalidated extra `repository` key is preserved in the body used by the controller even though the handler's `ExplicitParameters` schema only extracts the declared `team`/`organization`/`member` fields.

Exploit flow: attacker owns `attacker-org`, which is a legitimate tenant registered in Shipit's per-organization GitHub config with a webhook secret they know (self-owned org, no stolen secrets). They send:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<hmac using attacker-org's known secret>
{
  "action": "added",
  "team": {"id": <attacker-chosen>, "name": "x", "slug": "security-team", "url": "https://x"},
  "organization": {"login": "victim-org"},
  "member": {"login": "<attacker-login>"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
`repository_owner` resolves to `attacker-org` (because `repository.owner.login` is present and preferred), so `verify_signature` checks against `attacker-org`'s webhook secret, which the attacker legitimately knows, and the signature passes. `MembershipHandler` then ignores `repository` entirely and creates `Team(organization: 'victim-org', slug: 'security-team', github_id: <attacker-chosen>)`, adding the attacker as a member. When `Shipit.github_teams` later (or first) resolves the `'victim-org/security-team'` handle, `find_by(organization: 'victim-org', slug: 'security-team')` matches this forged row instead of ever calling `fetch_and_create_from_github`, and the attacker's membership is already attached.

None of the listed guards stop this: `verify_signature` is satisfied because it authenticates the wrong field (`repository.owner.login`) relative to the field the handler actually trusts (`organization.login`); `drop_unhandled_event` only checks the event name is registered; the `ExplicitParameters` schema for `MembershipHandler` never touches `repository`, so it neither validates nor strips it; `User#authorized?` simply checks team membership against `Shipit.github_teams.map(&:id)`, which is exactly the poisoned ID set [8](#0-7) .

### Impact Explanation
A successful exploit lets an unprivileged GitHub user who merely owns/administers an unrelated GitHub organization (already onboarded as a Shipit tenant) inject themselves into `Shipit.github_teams`, the group used to gate `User#authorized?` for the entire Shipit instance. This is a direct authorization-bypass into whatever privileged team the operator configured under `oauth_teams` (e.g., a "security-team" or "deploy-approvers" team), letting the attacker perform deploys/rollbacks/merges gated on `authorized?`. Blast radius is instance-wide (any repository/stack gated by the same `Shipit.github_teams` check), matching the Critical "authentication bypass" / High "escalation into `Shipit.github_teams` authorization" categories.

### Likelihood Explanation
Preconditions: the Shipit instance must run in the multi-tenant/per-organization GitHub config mode (so `github_app_config(organization)` differentiates secrets per org) and the attacker must already be onboarded as a legitimate tenant with a working webhook secret for their own org — a realistic scenario in any Shipit deployment serving multiple orgs. The race also requires the target handle in `oauth_teams` not yet be memoized/resolved (first invocation, e.g., right after a deploy or app restart, since `@github_teams` is memoized per process). Attacker cost is a single crafted HTTP POST with a signature they can legitimately compute; no secrets belonging to the victim are required. It is repeatable against any `oauth_teams` handle not yet materialized, and against multiple worker processes if `@github_teams` memoization is per-process.

### Recommendation
Make `MembershipHandler` (and any other handler that trusts `organization.login`/`repository.owner.login`) use the exact same organization value that `WebhooksController#verify_signature` used to authenticate the request, rather than re-reading it from the body independently. Concretely: pass the verified `repository_owner` value into the handler (e.g., via the payload wrapper) and have `find_or_create_team!` assert `params.organization.login == verified_organization` (reject otherwise), or simplify `repository_owner` to only ever read `organization.login` for `organization`/`membership`-family events and `repository.owner.login` for repository events, never allowing a payload to supply both inconsistently. Additionally, harden `Team.find_or_create_by_handle` to re-validate that an existing row's `github_id`/team really corresponds to `organization/slug` on GitHub before trusting it (e.g., verify via API on first resolution rather than trusting whatever local row already exists).

### Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb` style, illustrating the decoupled fields — actual file changes are out of scope per rules, but the plan is):
```ruby
test "membership webhook can spoof team.organization independent of signing org" do
  # attacker-org is a legitimately configured tenant whose secret the attacker knows
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate correct sig for attacker-org

  request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: 999_999, name: 'x', slug: 'security-team', url: 'https://x' },
    organization: { login: 'victim-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } } # drives signature check only
  }.to_json

  assert_difference -> { Team.count }, 1 do
    post :create, body:, as: :json
  end

  forged = Team.find_by(github_id: 999_999)
  assert_equal 'victim-org', forged.organization   # equality claimed broken: matches oauth_teams handle org
  assert_equal 'security-team', forged.slug

  Shipit.stubs(:github).returns(stub(oauth_teams: ['victim-org/security-team']))
  resolved = Team.find_or_create_by_handle('victim-org/security-team')
  assert_equal forged.id, resolved.id  # forged row wins over fetch_and_create_from_github
end
```
This demonstrates both sides of the equality (`forged.organization/slug` vs. `Shipit.github_teams` handle target) collide, and that the collision is reachable purely through attacker-controlled payload fields decoupled from the signature-verified organization.
