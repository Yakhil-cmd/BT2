### Title
Cross-repository CI status forgery via unscoped commit lookup in webhook `status` handler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit.github(organization:)` supports a multi-organization configuration where each GitHub organization has its own independent `webhook_secret` [1](#0-0) . The `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against based on a payload field (`repository.owner.login` / `organization.login`) that is itself part of the signed body, then dispatches the parsed JSON to the matching event handler with no further scoping [2](#0-1) . `Webhooks::Handlers::StatusHandler#process`, however, never checks that the commit's SHA belongs to a stack/repository related to the authenticating organization — it looks up commits engine-wide: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` [3](#0-2) . This breaks the binding "organization that authenticated == repository that is written": a valid signature for organization X's webhook secret authorizes writing a commit status onto any commit tracked by Shipit, in any stack of any organization, as long as the SHA matches.

### Finding Description
1. Shipit can be configured to host multiple GitHub organizations, each with an independent app installation and `webhook_secret`, selected via `Shipit.github(organization: repository_owner)` [4](#0-3) .
2. `WebhooksController#verify_signature` reads `repository_owner` straight from the untrusted JSON body and uses it purely to pick *which* secret to verify the HMAC against: `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [5](#0-4) . Verification only proves "this byte stream was signed with organization X's secret" — it never checks that the rest of the payload (in particular `sha`) actually pertains to organization X's repositories.
3. The `status` event is routed to `Handlers::StatusHandler`, whose params schema requires only `sha`, `state`, and optional descriptive fields — no repository/org binding at all [6](#0-5) .
4. `process` resolves target commits purely by `sha`, globally across the `commits` table, and calls `create_status_from_github!` on each match [3](#0-2) , which persists a `Status` record and can flip a commit's deployability/merge state via `add_status` (`stack.schedule_merges`, `Hook.emit(:deployable_status, ...)`) [7](#0-6) .
5. Downstream, `Commit#deployable?` and `Status::Common#blocking?/#required?` consult these statuses by `context` against the *stack's own* `blocking_statuses`/`required_statuses` config [8](#0-7) [9](#0-8) , and `MergeRequest#all_status_checks_passed?`/`#merge!` gate an automatic GitHub merge on the same status data [10](#0-9) .

Combining these: an operator of *any* organization X that is configured in Shipit (i.e., holds a legitimate, low-privilege GitHub App installation and its own `webhook_secret` for their own unrelated repositories) can compute a valid `X-Hub-Signature` over an arbitrary JSON body using X's own secret, and POST it directly to Shipit's webhook endpoint with `event: status`, `sha: <victim commit sha>` (SHAs are public on GitHub and easily discoverable) and `state: success`. Verification succeeds (it only checks the signature against X's own secret), and `StatusHandler` writes that forged status onto the victim commit in a completely different stack/organization, without ever needing GitHub write access to the victim repository.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary explicitly called out as in-scope. A forged "success" status for a `required_statuses`/`blocking_statuses` context, or a status transition that triggers `stack.schedule_merges` and `ProcessMergeRequestsJob`, can make an otherwise CI-failing or CI-pending commit in a victim's stack appear deployable, and can trigger an automatic merge of a pull request via `MergeRequest#merge!` (which calls `stack.github_api.merge_pull_request`) [11](#0-10) , or unblock/trigger continuous deployment (`Commit#add_status` → `stack.schedule_merges`) in a repository the attacker has no legitimate access to. This matches the "unauthorized deploy, rollback or merge" / "cross-repository writes" Critical/High impact bar.

### Likelihood Explanation
Requires only that: (a) Shipit is configured for more than one GitHub organization (multi-tenant deployment, an explicitly supported configuration path in `lib/shipit.rb`), and (b) the attacker controls one of those organizations' own repos/app installations (their own webhook secret, no special privilege). No session, ApiClient token, or victim-repo write access is needed — this is exactly the "unprivileged attacker crossing an authentication/deployment-trust boundary" class described. The main uncertainty is how commonly Shipit is deployed with multiple independent organizations sharing one Shipit instance versus one org per instance; in a single-organization deployment this specific path collapses since there is only one webhook secret. I could not verify from the indexed code how the host application typically provisions `secrets.github` in production, so likelihood is High in multi-org deployments and not applicable in single-org ones.

### Recommendation
In `Webhooks::Handlers::Handler`/`StatusHandler`, scope commit lookup to `stacks` (already computed from `payload.dig('repository','full_name')` via the `Handler#stacks` helper) instead of a bare `Commit.where(sha: ...)` across the whole table, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`. More generally, verify that the authenticated organization from `verify_signature` actually owns the `repository.full_name`/`stack` referenced by the event body before handlers act on it.

### Proof of Concept
1. Shipit configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` under `secrets.github`.
2. Attacker knows their own `attacker-org` webhook secret (they administer that GitHub App installation) and knows a commit SHA that exists in a `victim-org` stack (public commit history).
3. Attacker crafts JSON:
```json
{
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_attacker_org, body)` and POSTs it to `POST /github/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s app config, and the signature validates (`WebhooksController#verify_signature`, `verify_webhook_signature`) [5](#0-4) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `victim-org`'s stack, and creates a forged `success` status on it [3](#0-2) , potentially unblocking deploy/merge for the victim stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(

        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',

      begin

          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
