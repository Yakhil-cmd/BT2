### Title
PR label named `github_token`/`git_askpass` overrides real `GITHUB_TOKEN`/`GIT_ASKPASS` in task env - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every PR label (upcased) as a literal env-var key/value on top of `Stack#env`, and `TaskCommands#env` merges `@stack.env` directly on top of `Commands#base_env` (which sets the real `GITHUB_TOKEN`/`GIT_ASKPASS`) without ever re-asserting those two keys afterward. An attacker who can label their own PR `github_token` or `git_askpass` can therefore stomp the real credential/script-path value in the final env hash handed to `Command`/`PTY.spawn`.

### Finding Description
The broken binding: the question posits `GITHUB_TOKEN` (or `GIT_ASKPASS`) in the final merged `Command#env` must equal `github.token` (Shipit's authenticated GitHub App token) / the trusted askpass script path, and never a value derived from attacker input.

Trace:
- `Commands#base_env` sets the trusted values: `env['GITHUB_TOKEN'] = github.token` and, if `Shipit.use_git_askpass?`, `env['GIT_ASKPASS'] = .../lib/snippets/git-askpass` [1](#0-0) .
- `ReviewStack#env` takes `Stack#env` and merges in every PR label, upcased, as a key with value `"true"`: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [2](#0-1) . If a PR carries a label literally named `github_token` or `git_askpass`, this hash will contain `"GITHUB_TOKEN" => "true"` or `"GIT_ASKPASS" => "true"`.
- `TaskCommands#env` builds the final env as: `super.merge(@stack.env).merge({SHIPIT_USER:, EMAIL:, ...}).merge(deploy_spec.machine_env).merge(@task.env)` [3](#0-2) . `super` is `Commands#env` → `base_env`, which contains the real `GITHUB_TOKEN`/`GIT_ASKPASS`. The very next `.merge(@stack.env)` overwrites these with the attacker's label-derived value ("true"), because Ruby `Hash#merge` gives priority to the argument on collisions. None of the subsequent merges (`SHIPIT_USER`/`EMAIL`/etc., `deploy_spec.machine_env`, `@task.env`) reintroduce or restore `GITHUB_TOKEN`/`GIT_ASKPASS`, so the corrupted value survives into the `Command` passed to `PTY.spawn`.

Attacker's exact PR: open (or already have) a fork PR against a repo whose review-stack behavior is `allow_all` or `allow_with_label` and is satisfied, then apply a label named `github_token` (any case, since it's upcased) via `LabeledHandler`/`OpenedHandler` → `ReviewStackAdapter`. Once the review-stack's provisioned task next runs (e.g., install_dependencies/deploy steps), its `Command#env['GITHUB_TOKEN']` is `"true"` instead of the real GitHub App token.

Existing guards do not prevent this: `verify_signature`/webhook auth only ensure the webhook is genuinely from GitHub for that repository - they don't restrict label content (any repo collaborator, including PR author with label permissions or in open-source repos anyone with triage access, can set labels), and there is no allow-list/deny-list of reserved env-var names when converting labels into env entries.

### Impact Explanation
This breaks the trusted-credential binding for the review-stack's task execution environment. Two concrete outcomes: (1) `GITHUB_TOKEN` becomes the literal string `"true"` instead of a valid App token — any deploy/task script that relies on it for git/GitHub API auth will fail or behave unpredictably (denial of correct operation, not secret exfiltration by itself); (2) `GIT_ASKPASS` similarly gets replaced with `"true"`, which is not an executable path, again breaking git authentication for that task's git operations, potentially causing git to fall back to interactive/broken auth. This does not exfiltrate the real token to the attacker (the real value is overwritten, not read out to attacker-controlled output) unless a wrapper script trusts the presence of `GITHUB_TOKEN`/`GIT_ASKPASS` and echoes the corrupted value somewhere attacker-observable — that dependency wasn't found in this engine's own code. Within this engine, the concrete, demonstrable effect is credential/env corruption for that stack's task, scoped to the specific review stack whose PR carries the label (no cross-tenant/cross-repository blast radius was found since `pull_request.labels` belongs to that PR's own `ReviewStack`).

### Likelihood Explanation
Preconditions: review stacks must be enabled and the stack's provisioning behavior (`allow_all`/`allow_with_label`) must be satisfied for a fork PR, and the attacker must be able to add a label named `github_token` or `git_askpass` to their own PR. Labeling capability is often available to PR authors on their own PRs or to anyone with triage/write access, depending on the host repo's GitHub permission settings — the exact who-can-label boundary lives on GitHub's side, not in this engine. Assuming label capability, the exploit is trivially repeatable and low-cost (a single GitHub label). This engine's code faithfully converts arbitrary label names into env keys with no reserved-name filtering.

### Recommendation
In `TaskCommands#env` (and generally wherever computed env hashes are merged), re-assert the trusted `GITHUB_TOKEN`/`GIT_ASKPASS` (and any other security-sensitive keys) as the last merge step so they cannot be overridden by `@stack.env`/label-derived values, e.g. `.merge(deploy_spec.machine_env).merge(@task.env).merge(base_env.slice('GITHUB_TOKEN', 'GIT_ASKPASS', 'GITHUB_DOMAIN'))`. Alternatively/additionally, in `ReviewStack#env`, filter out label names that collide with reserved/sensitive env keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, `GITHUB_DOMAIN`, etc.) before merging.

### Proof of Concept
Minitest plan (`test/lib/shipit/task_commands_test.rb`-style, no live GitHub — stub `github.token`):
```ruby
test "PR label named github_token overrides the real GitHub token in task env" do
  stack = shipit_review_stacks(:some_review_stack) # or build a ReviewStack fixture
  pull_request = stack.pull_request
  pull_request.update!(labels: ['github_token'])

  task = shipit_deploys(:some_deploy_on_that_stack) # or build one for stack
  commands = Shipit::TaskCommands.new(task)

  real_token = Shipit.github(organization: stack.repository.owner).token
  final_env = commands.env

  # Binding under test: final_env['GITHUB_TOKEN'] == real_token
  refute_equal 'true', final_env['GITHUB_TOKEN'], "label should not be able to set env values"
  assert_equal real_token, final_env['GITHUB_TOKEN'], "GITHUB_TOKEN must remain the trusted GitHub App token"
end
```
This test currently fails against the code as written (asserting the vulnerability), since `final_env['GITHUB_TOKEN']` ends up `"true"` due to the merge order in `TaskCommands#env` and `ReviewStack#env`.
