### Title
Cross-repository `status` webhook mutates commits in unrelated stacks via unscoped SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` with `Commit.where(sha: params.sha)`, with no repository/stack scoping, and applies the incoming `context`/`state` to every matching commit found in the database. Since webhook signature verification (`WebhooksController#verify_signature`) is only checked against the GitHub organization derived from the payload's `repository.owner.login`, not against the specific stack/repository that owns the commit, any attacker who can get a `status` event delivered for a SHA that also exists in a victim's stack (e.g. via a shared commit history through a fork, or a SHA collision across stacks tracking the same underlying repository/branches) can flip the `shipit/checks` status for the victim's commit.

### Finding Description
The broken binding is: `commit.stack_id == authenticated_repository.stack_id` is assumed to hold for every `commit` mutated by a status webhook, but the code never enforces it.

Trace:
1. `WebhooksController#create` parses `params` and dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
2. `verify_signature` resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and validates the HMAC signature for that organization's configured GitHub App/webhook secret — this only proves the request was signed for *some org*, not that it corresponds to the specific stack whose commit is about to be mutated [2](#0-1) .
3. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query is global across the `commits` table — it is not filtered by `stack_id`, `repository`, or organization [3](#0-2) .
4. `Commit#create_status_from_github!` writes a new `Status` row for the matched commit and calls `add_status`, which recomputes `status`, compares `previous_status` vs `new_status`, emits `Hook.emit(:deployable_status, ...)`, and — critically — calls `stack.schedule_merges` if the new status is `pending?` or `success?`, and `schedule_continuous_delivery` runs and enqueues `ContinuousDeliveryJob` whenever `deployable?` flips true [4](#0-3) [5](#0-4) .
5. `deployable?` and `blocked?` are computed purely from the statuses attached to the commit and the owning stack's configured `required_statuses`/`blocking_statuses` [6](#0-5) .

Exploit flow: an attacker who owns/forks a repository sharing commit history with a victim stack (forks retain identical SHAs for unmodified commits) configures their own GitHub App/webhook (which they legitimately control) and sends a `status` event with `sha` = a SHA that is also present as a `Commit` row in the victim's stack, `context: shipit/checks`, `state: failure`. `verify_signature` passes because the signature is valid for the attacker's own org/repo. `StatusHandler#process` then finds and mutates the victim's `Commit` record too, because the lookup has no repository filter. If the victim stack requires `shipit/checks` and has `bot_login` (i.e. `Shipit.user`) configured for auto-triggered continuous deployment, this failure can flip `deployable?`/`blocked?` for the victim commit, and any auto-triggered deploy/rollback subsequently executes under the configured bot identity rather than any real authorization from the victim's own CI.

None of the listed guards catch this: `verify_signature` authenticates an organization's webhook secret, not a specific stack-to-commit binding; `drop_unhandled_event` only filters unknown event types; there is no `ExplicitParameters` repository field required by `StatusHandler`'s schema (only `sha`, `state`, `context`, etc.) [7](#0-6) ; and `Commit.where(sha: ...)` performs no join back to the repository that signed the request.

### Impact Explanation
A payload authenticated for one repository/org can mutate `Status` records — and downstream deployability/blocking state — for a commit belonging to a completely different stack, provided the two stacks share a commit SHA (realistic via GitHub forks, which is explicitly an attacker capability per the rules: "any GitHub user who can ... push to a fork"). Combined with a victim stack that has `bot_login` configured for continuous delivery, this can suppress or trigger automated deploy/rollback actions performed under the bot's identity — an unauthorized deploy/rollback driven by a forged status for a repository that never authenticated the write. This matches the Critical category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback."

### Likelihood Explanation
Preconditions: (1) a victim stack configured with `required_statuses` including `shipit/checks` and `bot_login` for continuous deployment, and (2) a commit SHA shared between the attacker's own repository (fork) and the victim's stack history. Both conditions are common in real-world GitHub workflows (fork-based contribution, shared upstream history) and require no privileged access — the attacker only needs their own repository and its own legitimately-configured webhook, which they fully control. The attack is repeatable at will against any commit SHA the attacker can align with a fork.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to the repository that authenticated the webhook: resolve the target stack(s)/repository from `params.repository.full_name` (or equivalent), and constrain the `Commit` lookup to `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })` (or similar), rather than a bare `Commit.where(sha: ...)` across the entire table.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` style):
1. Create two `Stack`s, `victim_stack` (with `Shipit.user`/bot_login configured, `required_statuses` including `shipit/checks`) and `attacker_stack`, backed by two different `Repository` records.
2. Create a `Commit` with the same `sha` (e.g. `"c" * 40`) attached to both `victim_stack` and `attacker_stack`.
3. Assert precondition equality: `victim_commit.deployable?` (or `status.success?`) == expected pre-attack state (e.g. `true`, based on an existing passing `shipit/checks` status).
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload).call` (or `process`) with `sha` = shared sha, `context: 'shipit/checks'`, `state: 'failure'`, simulating a webhook that only authenticated for `attacker_stack`'s repository.
5. Reload `victim_commit` and assert the equality now differs: `victim_commit.deployable?` flipped to `false` / `blocked?` flipped to `true`, proving that a request authenticated for `attacker_stack`'s repository mutated `victim_stack`'s commit state despite no scoping check in `StatusHandler#process`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
