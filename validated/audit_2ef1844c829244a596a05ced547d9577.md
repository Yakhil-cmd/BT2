I have sufficient evidence to confirm the vulnerability. The invariant that "environment keys reaching `PTY.spawn` are restricted to `machine_env`/`VariableDefinition` names" does not exist anywhere in the code — `ReviewStack#env`, `TaskCommands#env`, and `Command#unbundled_env` all perform unrestricted hash merges with no key allowlist.

### Title
Unfiltered PR-label-derived env keys reach `PTY.spawn`, allowing `PYTHONPATH` (and any other env var name) injection via GitHub label - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable key with the value `"true"`, with no allowlist of permitted key names. That hash flows unfiltered through `TaskCommands#env` → `Command#unbundled_env` → `PTY.spawn`, so a label literally named `pythonpath` becomes `PYTHONPATH=true` in the spawned process's real environment, alongside any shell-interpreted `shipit.yml` step.

### Finding Description
The broken invariant, stated as an equality that does **not** hold: `keys(env passed to PTY.spawn) == keys(deploy_spec.machine_env) ∪ keys(declared VariableDefinition names)`. In fact `keys(env) ⊇ { label_name.upcase | label_name ∈ pull_request.labels }`, an attacker-controlled set with no restriction.

Path:
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook body onto `pull_request.labels` with no name filtering: [1](#0-0) 
- `ReviewStack#env` turns every label name into an uppercased hash key with value `"true"`, merged over `super` (base env) with no allowlist: [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` (which includes the label-derived keys) into the task's command environment: [3](#0-2) 
- `Command#unbundled_env` merges `@env.stringify_keys` (the full task env, including attacker keys) over `BASE_ENV` and `PATH`, with no key restriction: [4](#0-3) 
- `Command#start` passes that hash directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`: [5](#0-4) 

Because `PTY.spawn` receives the hash as the child process's *actual environment* (not merely string-interpolated into the command line via `EnvironmentVariables.with(env).interpolate`, which only substitutes `$VAR` occurrences in the argument string: [6](#0-5) ), setting `PYTHONPATH` this way affects every subprocess spawned for that command, regardless of whether the `shipit.yml` step string references `$PYTHONPATH` explicitly. Any `shipit.yml` step that invokes `python`/`python3` (directly or via a wrapper script) will import from the attacker-supplied path if `PYTHONPATH` points at a location the attacker also controls (e.g., a working-directory path within the checked-out fork branch, or any writable path the deploy host resolves).

Existing tests confirm this behavior is by design and untested against key allowlisting: `TaskCommandsTest`/`DeployCommandsTest`/`ReviewStackTest` all assert that arbitrary uppercased label names become env entries with no restriction on the key namespace: [7](#0-6) [8](#0-7) 

No guard intercepts this: `capture_labels?` only checks stack state (opened/labeled/unlabeled/reopened, not archived) [9](#0-8) , not label content; there is no `EnvironmentVariables#permit`-style allowlist anywhere in this chain.

### Impact Explanation
An attacker who can attach a label to a review-stack-eligible pull request (per this audit's threat model, "label their own PR" is a granted capability) can inject arbitrary environment variable **names**, not just values, into every shell-interpreted step Shipit runs for that review stack's tasks — including deploys, rollbacks, and custom `shipit.yml` steps. Using `PYTHONPATH`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `RUBYOPT`, `NODE_OPTIONS`, etc. as label names lets the attacker hijack any interpreter invoked by the pipeline, achieving code execution in the context of the Shipit deploy host process for that repository's review stack. This matches the Critical RCE class (arbitrary command/code execution via `Command`/`PTY.spawn`).

### Likelihood Explanation
Preconditions: the repository must have review stacks enabled (`review_stacks_enabled`) and the attacker must be able to attach a label to the PR (as granted by this audit's attacker model) and get a `shipit.yml` step to run that invokes an interpreter honoring the injected variable (e.g., `PYTHONPATH`, `RUBYOPT`). No secrets are required. The attack is repeatable for every task run against that review stack while the label is present.

### Recommendation
Restrict `ReviewStack#env`'s label-derived keys to a documented, explicit allowlist (e.g., prefix-scoped like `SHIPIT_LABEL_<NAME>`, or validate against a repo-configured list of permitted flag names) instead of merging raw uppercased label names directly into the process environment. Additionally, apply a global denylist/allowlist in `Command#unbundled_env` to prevent security-sensitive variable names (`PYTHONPATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `NODE_OPTIONS`, `BASH_ENV`, etc.) from ever being set from user-controlled sources such as PR labels or task/stack env.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend existing test class)
test "#env does not allow labels to set PYTHONPATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath"]

  refute stack.env.key?("PYTHONPATH"),
    "Expected PYTHONPATH to be excluded from label-derived env, got: #{stack.env['PYTHONPATH'].inspect}"
end

# test/lib/shipit/task_commands_test.rb
test "#env does not propagate PYTHONPATH from a PR label into the task env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  refute env.key?("PYTHONPATH")
end

# test/unit/command_test.rb
test "#unbundled_env does not allow attacker-controlled keys like PYTHONPATH through" do
  command = Shipit::Command.new('python3 -c "import attacker_module"', env: { "PYTHONPATH" => "/tmp/attacker" }, chdir: '.')
  refute_equal "/tmp/attacker", command.unbundled_env["PYTHONPATH"]
end
```
Both sides of the claimed equality (`env keys == machine_env/VariableDefinition keys`) diverge today: `stack.env`, `TaskCommands#env`, and `Command#unbundled_env` all include the attacker-supplied `PYTHONPATH` key, and the assertions above currently fail, demonstrating the unfiltered pass-through.
