This is a genuine, reachable vulnerability. Here's the analysis:

### Title
Stack-scoped API token issued for CCMenu bypasses stack authorization, allowing any stack's build state to be read - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The binding that should hold is: `ApiClient#stack_id` (the stack the token authorizes) == the stack whose state the token can read. `Shipit::CCMenuUrlController#client` mints a `read:stack` token without a `stack_id`, and `Shipit::Api::CCMenuController#stack` looks up the target stack directly from the request parameter instead of through the base controller's stack-scoping helper, so neither side of the equality is ever enforced.

### Finding Description
`Shipit::CCMenuUrlController#fetch` is meant to generate a CCMenu URL scoped to one stack: [1](#0-0) 

The `client` method creates the `ApiClient` with `permissions: %w[read:stack]` but never sets `stack: stack` (or `stack_id:`), so `ApiClient#stack_id` is `nil` for this client.

On the consuming side, `Shipit::Api::BaseController` defines the intended scoping mechanism: [2](#0-1) 
`stacks` restricts the queryable set to `current_api_client.stack_id` when present, otherwise falls back to `Stack.all`. Every other API controller (e.g. `Api::StacksController`) relies on this `stacks`/`stack` helper to enforce the token's stack binding.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [3](#0-2) 
It calls `Stack.from_param!(params[:stack_id])` directly on the global `Stack` scope, ignoring `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the token has the `read:stack` permission string — it never checks which stack the token is bound to: [4](#0-3) 

Because the token minted by `CCMenuUrlController` has `stack_id == nil` in the first place, even the base-controller scoping (had it been used) would have granted access to `Stack.all`. Combined with `CCMenuController#stack` overriding that scoping outright, the token embedded in the "ccmenu_url" for stack A can be replayed with an arbitrary `stack_id` in the URL/query string to read the CI status of any stack B in the Shipit instance.

### Impact Explanation
This is an unauthenticated (token-holder-only, no session/team-membership required) read of another stack's state: `lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status, etc., for stacks the token was never intended to access: [5](#0-4) 
Any user who obtains one CCMenu token (e.g., a low-privilege team member fetching their own stack's CCMenu URL) can enumerate `stack_id` values and read build/deploy status for every other stack in the installation, including stacks belonging to teams/repositories they are not authorized to view. This matches the "unauthenticated read of stack state" High-impact category.

### Likelihood Explanation
High likelihood: any authenticated Shipit user can trigger `CCMenuUrlController#fetch` for a stack they can see, obtain a permanent (non-expiring) `ApiClient` token, and then reuse that token against `Api::CCMenuController#show` with a different `stack_id` — no additional privilege, secret, or session is required beyond having used the CCMenu feature once.

### Recommendation
- Set `stack: stack` when creating the `ApiClient` in `CCMenuUrlController#client` so the token is actually bound to the intended stack.
- Remove the `stack` override in `Api::CCMenuController` and use the inherited, scoped `stacks`/`stack` helper from `Api::BaseController` (or otherwise verify `current_api_client.stack_id == stack.id`) so a stack-scoped token cannot be replayed against other stacks.

### Proof of Concept
1. As any Shipit user, `GET /ccmenu/<stack_owner>/<stack_name>/<env>` → `CCMenuUrlController#fetch` creates (or reuses) a `read:stack` `ApiClient` with `stack_id: nil` and returns `{"ccmenu_url": ".../api/<any_stack_owner>/<any_stack>/<any_env>/ccmenu.xml?token=<TOKEN>"}`.
2. Replace `stack_id` in the returned URL's path with a different stack's identifier (owned by a different team/repository), keeping the same `token`.
3. Request `GET /api/<other_stack>/ccmenu.xml?token=<TOKEN>` → `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` for the *other* stack, `require_permission :read, :stack` passes because the token merely carries the `read:stack` permission string, and the XML build status for the unrelated stack is returned.
