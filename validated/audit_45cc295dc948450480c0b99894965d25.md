### Title
Prosaic Contract Hash Uses Un-delimited String Concatenation, Enabling Field-Boundary Collision and Contract-Text Forgery - (File: prosaic_contract.js)

### Summary
`prosaic_contract.js` computes the integrity/commitment hash of a prosaic (prose) contract by directly concatenating three attacker-controlled strings — `title`, `text`, and `creation_date` — with **no delimiter** between them, then hashing the result: [1](#0-0) 

This is the same root-cause bug class as the Netty CRLF injection: user-controlled parameters are concatenated into a single string that is later parsed/interpreted as if it were structurally separated fields, with no validation of boundary/separator characters. Just as CRLF was missing from Netty's SMTP parameter validation, a field delimiter is missing from ocore's contract hash pre-image, allowing content to "leak" across field boundaries while producing an identical hash.

### Finding Description
`getHash(contract)` and `getHashV1(contract)` build the pre-image as `contract.title + contract.text + contract.creation_date` with no separator: [1](#0-0) 

Because `title`, `text`, and `creation_date` are all supplied by the contract-composing peer (via `createAndSend`, which is invoked from wallet UI code with values chosen entirely by the offering party), an attacker who plays the "offeror" role in a prosaic contract fully controls the entire hash pre-image. Any two field splits `(title, text)` and `(title', text')` for which `title + text == title' + text'` (with the same `creation_date`) collide to the **same hash**.

This is functionally identical to the bug class in the external report: a security boundary between structured input fields is only implicit (positional concatenation) rather than explicit (delimited), so a party who controls the raw fields can shift content across the field boundary to produce two different "logical documents" that hash identically. 

Notably, the sibling implementation `arbiter_contract.js::getHashSrc` already had to work around exactly this weakness by introducing `exports.DELIMITER = "[|#|]"` and joining fields with it for contracts created after `NEW_HASH_DATE`, while explicitly preserving the vulnerable, delimiter-less `.join("")` behavior for older ones: [2](#0-1) 

`prosaic_contract.js`, however, was never patched with a delimiter at all — `getHash`/`getHashV1` remain vulnerable unconditionally.

The hash is not merely cosmetic: it is embedded as `contract_text_hash` in an on-chain `data` message that is authenticated by the shared-address definition and later re-validated against unit contents: [3](#0-2) 

For the arbiter-contract variant (which follows the same design and directly gates fund flow), the analogous commitment is posted on-chain via `contract_text_hash` when creating the shared address that will hold and later disburse payment funds, and is later used by the arbitration/dispute flow where the *raw* `title`/`text` fields are sent out-of-band to the arbstore for adjudication: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because the hash only commits to the concatenation of `title`/`text`/`creation_date` and not to their individual boundaries, a malicious contract offeror can:
1. Present one `(title, text)` split to the counterparty for review/acceptance and signing (the version that looks like a fair, legitimate agreement), producing on-chain commitment `hash = H(title||text||date)`.
2. Later present a *different* `(title', text')` split — reading with different terms/obligations — to an arbstore/arbitrator during a dispute (`openDispute`/`appeal`), where `title'+text'+date == title+text+date`, so the recomputed hash still matches the previously committed `contract_text_hash`.

Since dispute resolution directly drives the release of escrowed funds from the shared multisig address (`complete()`/`pay()` flows keyed off arbiter data-feed decisions), this hash-boundary ambiguity can be used to make the arbitrator believe a materially different contract was agreed to than what the counterparty actually reviewed and signed — leading to funds being released to the wrong party or under false pretenses. This satisfies the "AA/contract fund loss" impact bar defined for this scan (funds are moved based on a manipulated but hash-verifying document).

### Likelihood Explanation
The pre-image fields (`title`, `text`, `creation_date`) are fully attacker-controlled free-text/timestamp strings entered by the party proposing the contract, with no length restriction preventing boundary shifting and no canonical delimiter. Constructing a colliding split requires no cryptographic breakage — it is a trivial string-boundary manipulation (e.g., moving characters from the end of `title` to the start of `text`), reachable by any unprivileged wallet user who proposes a prosaic or arbiter contract to a counterparty.

### Recommendation
Include an explicit, unambiguous field separator (or length-prefix each field) before hashing, as was already done for the newer `arbiter_contract.js` path via `exports.DELIMITER`. Apply the same fix unconditionally to `prosaic_contract.js::getHash`/`getHashV1`, and remove the still-present unguarded legacy branch in `arbiter_contract.js::getHashSrc` (the `.join("")` path for `creation_date <= NEW_HASH_DATE`), replacing it with a delimited/length-prefixed scheme for all contracts, e.g. using `string_utils.getSourceString`-style structured hashing instead of raw string concatenation.

### Proof of Concept
```js
const crypto = require('crypto');
function getHash(contract) {
  return crypto.createHash('sha256').update(contract.title + contract.text + contract.creation_date, 'utf8').digest('base64');
}

const date = '2024-01-01 00:00:00';

// Version shown to counterparty for signing
const contractA = { title: 'Pay 100', text: '0 USD for goods', creation_date: date };

// Version shown to arbstore during dispute (different meaning, same concatenation)
const contractB = { title: 'Pay 10',  text: '00 USD for goods', creation_date: date };

console.log(getHash(contractA) === getHash(contractB)); // true - hash collision despite different contract text
```
This demonstrates that `prosaic_contract.js`'s hash function does not uniquely bind the logical `(title, text)` pair, allowing an attacker-controlled contract to be reinterpreted differently by different verifying parties while presenting an identical `contract_text_hash` commitment.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
