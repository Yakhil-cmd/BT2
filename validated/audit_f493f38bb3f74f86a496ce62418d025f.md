### Title
`StatusHandler#process` updates commits across unrelated stacks by SHA alone, ignoring the webhook's `repository` field - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` for every match, with no scoping to the repository named in the verified webhook payload. `Handler#stacks`, which exists precisely to scope handler logic to the repository in the payload, is defined but never invoked in this handler, so a status event for one repository can flip CI state for a `Commit` belonging to a completely different `Stack`.

### Finding Description
The broken binding, stated explicitly: the code must enforce `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` before calling `commit.create_status_from_github!`, but no such check exists anywhere on this path.

Trace:
- `Shipit::WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates the HMAC signature using `Shipit.github(organization: repository_owner)` [1](#0-0) . This only proves the request came from a GitHub App/org registered with Shipit; it does not tie the payload's named repository to any specific `Stack`.
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This query has no `stack_id`/repository filter at all — it operates over every `Commit` row in the database sharing that sha, across every stack and repository.
- `Handler#stacks` is defined exactly to scope lookups to the repository named in the payload (`Repository.from_github_repo_name(repository_name)&.stacks`) [3](#0-2) , but `StatusHandler` never calls it, unlike the intended design pattern.
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using `commit.stack_id` — the stack_id of whatever unrelated commit matched the sha, not anything derived from or checked against the webhook's repository [4](#0-3) .
- `Status.replicate_from_github!` performs `find_or_create_by!(stack_id:, state: github_status.state, ...)`, writing a new `Status` row (e.g. `state: 'success'`) tied to that unrelated commit/stack [5](#0-4) .
- `Commit#add_status`, wrapping the write, reloads and recomputes `status`, potentially unblocking deploys/merges via `stack.schedule_merges` and `ContinuousDeliveryJob` [6](#0-5) .

Exploit flow: an attacker who controls a repository in a GitHub org/installation that has Shipit's GitHub App installed (satisfying `verify_signature`) can produce a real, validly-signed `status` webhook for a commit sha that they legitimately possess (e.g., via a fork sharing ancestor commits with an unrelated, Shipit-tracked repository, so the sha is identical by construction of Git's content-addressed history). Sending `state: 'success'` for that sha causes `StatusHandler#process` to match and mutate the `Commit`/`Status` state of the unrelated stack's commit, regardless of which repository the payload names.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) authenticate that the *request* came from a legitimate GitHub App installation and is well-formed, but none of them verify that the *matched Commit's stack* belongs to the *repository named in the payload*. `Handler#stacks` would provide that check but is unused by `StatusHandler`.

### Impact Explanation
A payload legitimately signed for repository A can flip the CI/deploy-readiness state (`pending`/`failure` → `success`) of a `Commit` belonging to an unrelated `Stack`/repository B, as long as both share a commit sha (trivially true for forks or shared history). This can make `Commit#deployable?` return true for a commit that never actually passed CI in repository B's context, and can trigger `stack.schedule_merges` and continuous delivery scheduling for stack B — i.e., an attacker-controlled webhook from one repository mutates another stack's state, matching the "Critical: payload for one repository mutating another's stack/commit" category. This is repeatable against any two stacks sharing commit history (common with forks, mirrors, or template-derived repos) and requires no privilege beyond owning/controlling a repository under an org where Shipit's GitHub App is installed.

### Likelihood Explanation
Preconditions: (1) Shipit's GitHub App/webhook must be installed/registered for an org the attacker can act within (needed to pass `verify_signature`); (2) a target `Stack` must already have a `Commit` row whose sha coincides with a commit the attacker's repository also contains — realistic via forking, since Git commit shas are identical across clones/forks that share history. No secrets, sessions, or elevated GitHub permissions are required beyond pushing/triggering a status event in the attacker's own repository. This is feasible and repeatable for any attacker with a fork relationship to a monitored repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the payload, e.g. iterate `stacks.flat_map(&:commits)` or filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` using the existing `Handler#stacks` helper, so only commits belonging to stacks tied to the payload's `repository.full_name` can be updated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for repository A must not mutate a commit belonging to repository B's stack" do
  stack_a = shipit_stacks(:shipit)              # tracks "org/repo-a"
  stack_b = create_stack(repository: create_repository(name: "repo-b", owner: "org"))

  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)
  commit_b.statuses.create!(stack: stack_b, state: "failure")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "full_name" => "org/repo-a" }, # names repo A only
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal "failure", commit_b.reload.state, # binding: stack_id must equal stack tied to payload repo
    "Commit in unrelated stack (repo-b) was mutated by a webhook naming repo-a"
end
```
Before the fix, `commit_b.reload.state` becomes `"success"` because `StatusHandler#process` matches by sha alone across all stacks. After enforcing the repository/stack binding via `Handler#stacks`, `commit_b` remains untouched.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
