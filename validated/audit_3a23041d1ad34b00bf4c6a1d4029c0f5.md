### Title
Webhook signature verification selects the HMAC secret by `repository.owner.login`/`organization.login`, but every event handler resolves the target Stack using the unrelated `repository.full_name` field, letting any onboarded GitHub organization forge events for another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate the HMAC signature based on `repository.owner.login` (falling back to `organization.login`) taken directly from the still-unverified JSON body. [1](#0-0)  Once *any* configured organization's secret matches, the controller dispatches the *entire* raw payload to handlers. [2](#0-1)  Every handler, however, resolves which `Stack`/`Repository` to act on using `repository.full_name` — a completely different field of the same payload — via `Handler#stacks` / `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3)  Nothing ties `repository.owner.login` (the field that selected the signing secret) to `repository.full_name` (the field that selects the acted-upon repository). This is the "organization authenticated versus the repository that is written" binding: `Shipit.github(organization: repository_owner)` used to authenticate ≠ `Repository.from_github_repo_name(repository.full_name)` used to act.

### Finding Description
Shipit supports hosting multiple GitHub organizations in one instance, each with its own `webhook_secret` configured under `github.<org>` in `secrets.yml`. [5](#0-4)  The webhook secret for organization "orgA" is known to whoever created/owns the GitHub App installed in "orgA" (an unprivileged, mutually-trusted tenant of the Shipit instance, not a Shipit admin). Any of these tenants can craft an arbitrary POST to `/webhooks` with:

- `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) — used only to pick the secret for HMAC verification,
- a valid `X-Hub-Signature` computed with orgA's own known secret,
- but `repository.full_name = "orgB/private-repo"` — the field every `Handler` actually uses to look up the target `Repository`/`Stack`.

`PushHandler#stacks` (via `Handler#stacks`/`#repository_name`) will resolve to org B's repository/stacks purely from `repository.full_name`, with no cross-check against `repository.owner.login`. [6](#0-5) [3](#0-2)  The same pattern repeats in every other `full_name`-driven handler (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`, `AssignedHandler`), all of which call `Repository.from_github_repo_name(params.repository.full_name)` without validating the owner used for signature verification. [7](#0-6) [8](#0-7) 

The result: a legitimate but unprivileged tenant of org A can forge webhook events that are processed as if they came from org B's repository, purely because both organizations happen to be configured on the same Shipit instance.

### Impact Explanation
Forged `push` events cause `PushHandler` to call `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` for org B's stack with an attacker-chosen `expected_head_sha`. [9](#0-8) [10](#0-9)  `GithubSyncJob` fetches commits using the *real* org B GitHub credentials (`stack.github_api`) and appends any legitimately-existing commits up to that sha; if the stack has continuous deployment / merge-queue configured, syncing new commits into org B's stack can trigger deploy queuing tied to a branch the attacker does not control, and label/PR-event forgeries can archive/unarchive/create review stacks belonging to org B, or capture attacker-controlled pull-request labels that influence provisioning behavior for org B's environments. [11](#0-10)  This crosses a repository-write / unauthorized-deploy trust boundary between two unrelated GitHub organizations sharing one Shipit instance, matching the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Requires a Shipit deployment that hosts more than one GitHub organization (`github.<org>` multi-tenant config, explicitly documented and supported). [5](#0-4)  Any actor able to configure or read the webhook secret of any one of the onboarded organizations (e.g., that org's own GitHub App admin — an unprivileged party from the other tenant's perspective) can exploit this with a single crafted HTTP request; no Shipit session, `ApiClient` token, or GitHub push access is needed for the target org.

### Recommendation
After signature verification succeeds, `WebhooksController`/`Handler` must ensure the repository/organization resolved from `repository.full_name` (and any other repository referenced in the payload) belongs to the same organization identified by `repository_owner`/`organization.login` that was used to select the verifying secret — reject the event otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with distinct `webhook_secret`s per the documented multi-org setup. [5](#0-4) 
2. As the owner of the GitHub App installed in `orgA` (who legitimately knows `orgA`'s webhook secret), craft a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/private-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha-that-exists-in-orgB-repo>"
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` succeeds because it verifies against `orgA`'s secret (chosen via `repository.owner.login`). [12](#0-11) 
5. `PushHandler` resolves and acts on `orgB/private-repo`'s stack via `repository.full_name`, queuing `GithubSyncJob` for a stack the attacker has no legitimate access to. [9](#0-8)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
