### Title
`Repository#review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning due to Ruby operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends to gate all automatic stack provisioning on `repository.review_stacks_enabled`, matching the "Dynamically provision stacks for Pull Requests?" checkbox described in `docs/review_stacks.md`. Because `&&` binds tighter than `||` in Ruby, the `review_stacks_enabled` check is only applied to the `allow_all` branch of the `||` chain, leaving the `allow_with_label` and `prevent_with_label` branches completely unguarded by the flag.

### Finding Description
The broken binding: the operator expects `repository.review_stacks_enabled == false` to imply `provision? == false` for every `provisioning_behavior` value. The code instead evaluates:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

which Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` never gates the last two disjuncts.

`respond_to_pull_request_opened?` only checks `params.action == "opened"` and delegates the rest of the authorization decision to `provision?` [2](#0-1) , and `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` whenever `respond_to_pull_request_opened?` is true [3](#0-2) , which creates a real `ReviewStack`/`Stack` record for the repository.

Both `pull_request['labels']` (attacker-controlled, since it's the PR opener's own labels on their own PR/fork) and `params.action` (attacker-controlled, since it's derived directly from the GitHub webhook payload for a PR they open) feed `pull_request_has_provisioning_label?` [4](#0-3) . The only "trusted" input is `repository.provisioning_behavior`, an operator-set enum with values `allow_all`, `allow_with_label`, `prevent_with_label` [5](#0-4) .

Exploit: for any repository the operator has configured with `provisioning_behavior = allow_with_label` (or `prevent_with_label`), regardless of whether the operator has unchecked "review_stacks_enabled", an attacker opens a PR (with the provisioning label present, or absent, respectively) and the stack is provisioned exactly as if the flag were enabled. `review_stacks_enabled` has zero effect in this configuration, silently defeating the operator's intended kill-switch.

None of the standard guards prevent this: webhook signature verification only authenticates that the payload came from GitHub for that repository — it does not validate the PR's labels or action, both of which are legitimately attacker-controlled data within a webhook the attacker's own PR generates. `ExplicitParameters` schema only validates shape/type, not the security-relevant business logic in `provision?`. There is no code path that checks `review_stacks_enabled` again downstream in `ReviewStackAdapter`.

### Impact Explanation
An unprivileged GitHub user who can open pull requests (and label them) against a Shipit-integrated repository can force Shipit to create a `ReviewStack`/`Stack` record for that repository even though the operator has explicitly disabled dynamic review-stack provisioning. This is a write for a repository whose owner deliberately opted out of automatic provisioning being performed anyway, driven purely by attacker-supplied PR metadata — matching the "operator's explicit opt-out is silently ineffective" authorization-bypass class. It is repeatable against any repository configured with `allow_with_label` or `prevent_with_label`, independent of the `review_stacks_enabled` state, but is bounded to repositories already onboarded with one of these two provisioning behaviors (blast radius limited to those specific repos' review-stack lifecycle, not cross-tenant secrets/RCE).

### Likelihood Explanation
Preconditions: the target repository must already be registered in Shipit and have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (an operator configuration choice, not attacker-controlled). No secrets, tokens, or privileged roles are required by the attacker — they only need to open (and label) a pull request against that repository, which is standard, low-cost GitHub user capability. The bug is deterministic (an operator-precedence logic error), so it triggers on every "opened" webhook event that matches the label condition, making it fully reliable and repeatable.

### Recommendation
Add explicit parentheses (or an early guard) so `review_stacks_enabled` gates the entire disjunction, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, add a matrix test:
```ruby
[:allow_with_label, :prevent_with_label].each do |behavior|
  [true, false].each do |enabled|
    test "provision? for #{behavior} with review_stacks_enabled=#{enabled}" do
      repository = shipit_repositories(:shipit).tap do |r|
        r.update!(provisioning_behavior: behavior, review_stacks_enabled: enabled)
      end
      params = build_opened_params(repository: repository, labels: behavior == :allow_with_label ? [{name: repository.provisioning_label_name}] : [])
      handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params)

      # Binding under test: review_stacks_enabled must equal whether a stack gets created
      if enabled
        assert_difference -> { Shipit::ReviewStack.count }, 1 do
          handler.process
        end
      else
        assert_no_difference -> { Shipit::ReviewStack.count } do
          handler.process
        end
      end
    end
  end
end
```
Currently this fails for `enabled: false` in both `allow_with_label` and `prevent_with_label` cases: a `ReviewStack` is created despite `review_stacks_enabled` being `false`, proving the bypass.
