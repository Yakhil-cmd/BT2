### Title
`PoolState::token_price_x32()` will panic on division-by-zero when a swap drains one side of the pool down to its accrued-fee balance - ([File: programs/cp-swap/src/states/pool.rs])

### Summary
`token_price_x32()` divides by `token_0_amount` and `token_1_amount` derived from `vault_amount_without_fee()` without any zero-check, mirroring the reported PriceOracle bug class where an unguarded division causes a revert (panic) instead of a graceful error, on every call from the swap path.

### Finding Description
`vault_amount_without_fee()` returns the vault balance minus the pool's accumulated protocol/fund/creator fees for that token: [1](#0-0) 

`token_price_x32()` then unconditionally divides by both of these results: [2](#0-1) 

This function is invoked unconditionally on every swap through `get_swap_params()`, using the raw vault balances passed in from the `Swap` account context (attacker-controlled by choosing swap size/direction): [3](#0-2) 

`get_swap_params()` itself is called at the very start of both `swap_base_input` and `swap_base_output`, before the constant-product curve is even evaluated: [4](#0-3) [5](#0-4) 

If a sequence of swaps/withdrawals drives one vault's balance down to exactly the amount owed in accrued protocol/fund/creator fees for that token (i.e., `vault_amount_without_fee` returns `0` for one side), any subsequent swap attempting to read the price via `token_price_x32` will perform `u128 / 0`, which panics in Rust rather than returning a Anchor `Result` error. Unlike the `checked_div`/`checked_mul` idiom used everywhere else in this codebase (see `ConstantProductCurve` and `Fees` helpers, which consistently use `checked_*` combinators returning `Option`), this function uses raw `/` operators with no zero-guard.

### Impact Explanation
A panic caused by unchecked division reverts the transaction, but because this check happens unconditionally on the "hot path" of every swap (before the curve math and before any success/failure decision), once a vault's fee-adjusted balance for one token reaches zero, **that pool becomes permanently unusable for swapping** — every subsequent `swap_base_input`/`swap_base_output` call will panic at this line, since the check is performed before any user-supplied slippage/amount validation can reject the trade gracefully. This results in a denial-of-service / freezing condition on the pool's swap functionality, blocking users and LPs from trading or arbitraging the pool back to a healthy state via the affected instruction. Since fees only accrue and are only reduced by an admin/fund withdrawal instruction (not by ordinary swappers), an attacker who can push the vault down to the fee floor (e.g., via extreme small-liquidity pool combined with fee accrual) can lock the pool's swap path.

### Likelihood Explanation
Likelihood depends on being able to drive a vault balance down to exactly (or below, causing the underflow-guarded `checked_sub` in `vault_amount_without_fee` to error first) the accumulated fee amount for that token. This is a narrow edge case — for a pool with meaningfully sized reserves relative to fees, this is very unlikely to occur through normal trading, since `swap_base_input`/`swap_base_output` reduce, but the constant-product curve (`ConstantProductCurve::swap_base_output_without_fees`) prevents the output vault from ever going below what's needed to satisfy `checked_sub`. Reaching exactly zero fee-adjusted balance would require very specific, contrived vault/fee amounts (e.g., a pool created and swapped into extremely small remaining reserves), so likelihood is low without a very deliberate, multi-step setup, though the underlying missing zero-check is a legitimate code defect analogous to the reported issue.

### Recommendation
Add explicit zero-checks in `token_price_x32()` (and propagate errors via `Result` instead of panicking), e.g.:
```rust
pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
    let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
    require!(token_0_amount > 0 && token_1_amount > 0, ErrorCode::InsufficientVault);
    Ok((
        token_1_amount as u128 * Q32 as u128 / token_0_amount as u128,
        token_0_amount as u128 * Q32 as u128 / token_1_amount as u128,
    ))
}
```
This makes the failure an explicit, well-defined Anchor error rather than an uncontrolled panic, consistent with the `checked_*` style used elsewhere in `curve/constant_product.rs` and `curve/fees.rs`.

### Proof of Concept
Not independently reproduced with a concrete transaction trace due to the narrowness of the precondition (vault balance exactly equal to accrued fees for one token); the vulnerability is demonstrated via code-path analysis:
1. `swap_base_input`/`swap_base_output` call `pool_state.get_swap_params(...)` first. [4](#0-3) 
2. `get_swap_params` calls `self.token_price_x32(...)` unconditionally for both trade directions. [3](#0-2) 
3. `token_price_x32` performs `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` and the symmetric division, with no check that `token_0_amount`/`token_1_amount` (i.e., vault balance minus accrued fees) is nonzero. [2](#0-1) 
If either value is `0`, the division panics, aborting the transaction and blocking further swaps through this code path for that pool state until fees are withdrawn/rebalanced.
