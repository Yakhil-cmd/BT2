## Title
Webhook signature is verified against the organization in `repository.owner.login`, but handlers act on `repository.full_name` (and even a bare `sha`) with no cross-check — allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook HMAC against using `repository_owner`, derived from the payload field `repository.owner.login` (or `organization.login`). Once the signature check passes, the actual event handlers (`Shipit::Webhooks::Handlers::*`) never re-check that binding — they instead look up the target `Stack`/`Repository`/`Commit` using a *different* payload field (`repository.full_name`, or in the case of commit statuses, only the bare `sha`). This is the exact analog of the report's root cause: a value trusted for one purpose (organization/account existence check before acting) is disconnected from the value actually acted upon.

### Finding Description
`verify_signature` computes the org used to pick the webhook secret from the payload itself, before the signature has been checked against anything tied to the target repository: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` config (and thus a distinct `webhook_secret`) per organization when the multi-org configuration schema is used, as documented and tested: [3](#0-2) [4](#0-3) 

Once `verify_webhook_signature` succeeds (HMAC computed with the secret belonging to `repository.owner.login`, over the *entire* raw body), `WebhooksController#create` dispatches to handlers with the full parsed payload — with no re-validation that the organization used for signing matches the repository the handler will act on: [5](#0-4) 

Every handler resolves its target repository from a *different* field, `repository.full_name`: [6](#0-5) [7](#0-6) 

Worse, `StatusHandler` (commit status ingestion) does not scope by repository/organization at all — it matches purely by commit SHA across the entire Shipit instance: [8](#0-7) 

**The broken binding, as an equality:**
`organization used to select webhook_secret for signature verification (repository.owner.login)` ≠ `organization/repository the handler actually mutates (repository.full_name / bare sha lookup)`.

Nothing in the request path enforces `repository.owner.login == split(repository.full_name)[0]`, nor does `StatusHandler` check any organization/repository binding whatsoever.

### Impact Explanation
In a multi-organization Shipit deployment (the documented "Using Multiple Github Applications" configuration), an attacker who legitimately administers their own onboarded GitHub organization (and therefore possesses that org's own `webhook_secret`, which they configured themselves) can:
1. Craft a webhook payload with `repository.owner.login` (or `organization.login`) set to their own organization — so `verify_signature` selects and validates against a secret they control.
2. Set `repository.full_name` (push/pull_request handlers) or `sha` (status handler) to reference a completely different, victim-owned repository/commit tracked in the same Shipit instance.
3. Sign the payload with their own webhook secret and POST it to the shared `/webhooks` endpoint.

The forged event is accepted and dispatched against the victim's stack: `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for the victim's stack/branch, and `StatusHandler` injects arbitrary commit statuses for *any* commit SHA tracked instance-wide via `commit.create_status_from_github!`, which can be used to fabricate green CI/required-status checks that gate deploys or merges. This is a cross-repository write and can enable unauthorized deploy/merge decisions on a repository the attacker was never granted access to — the impact class the rules classify as Critical (cross-repository writes / unauthorized deploy or merge).

### Likelihood Explanation
The prerequisite is only that the attacker administers one legitimately-onboarded (even low-trust) organization on a multi-org Shipit instance — not any Shipit session, `ApiClient` token, or the victim's credentials. Multi-org configuration is a documented, supported deployment mode, and nothing in `WebhooksController` or the handler layer cross-validates the signing organization against the acted-upon repository. This is straightforward to exploit once dual-org onboarding exists.

### Recommendation
Bind the webhook signature verification and the payload used to act to the same trusted value:
- After resolving the signing organization, also resolve the repository via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and assert its `owner` matches `repository_owner` used for signature verification, rejecting the request (422) on mismatch.
- For `StatusHandler`, scope the `Commit` lookup by the repository derived from the webhook's verified organization (join through `stack.repository.owner`), not by bare SHA across the whole instance.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with distinct `github.webhook_secret` values (per `docs/setup.md` multi-org example).
2. As an admin of `attacker-org`'s own GitHub App, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully against the attacker's own secret.
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` (per `app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for the victim's stack, entirely under attacker control despite the signature belonging to a different organization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
