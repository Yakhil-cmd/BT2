### Title
CCMenuController#stack bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's CCTray XML (revision SHA leak) - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` defines its own private `stack` method that resolves the stack via `Stack.from_param!(params[:stack_id])` instead of using the scoped `stacks.from_param!` helper defined in `BaseController`. This override completely bypasses the `current_api_client.stack_id` restriction that limits a token to a single stack, so any valid `read:stack`-permissioned API token — even one created scoped to stack A — can fetch the CCTray XML for any other stack B, exposing `lastBuildLabel` (the last deployed commit SHA), `activity`, and `webUrl` for repositories the token was never authorized to see.

### Finding Description
The intended binding is: `data disclosed in the response == data the token's authorized stack permits`, i.e. if `current_api_client.stack_id` is set to stack A's id, requests must resolve `stack` from `Stack.where(id: current_api_client.stack_id)` only.

`BaseController` implements this correctly: [1](#0-0) 

But `CCMenuController` shadows the private `stack` method with an unscoped lookup: [2](#0-1) 

`require_permission :read, :stack` only checks that the token's `permissions` array contains `"read:stack"` — it never checks the stack identity itself: [3](#0-2) 

So a token created with `stack_id = A.id` and `permissions: ["read:stack"]` passes `require_permission!`, then `stack` resolves `Stack.from_param!(params[:stack_id])` against **any** `stack_id` param, not just A. The `show` action then renders stack B's actual last deploy/rollback into the CCTray XML: [4](#0-3) 

The XML template exposes the commit SHA and status fields directly: [5](#0-4) 

Existing guards that would normally prevent cross-stack leakage — the `stacks` scoping method in `BaseController` — are simply never invoked because `CCMenuController` defines its own `stack` accessor that takes precedence via Ruby method resolution within the subclass.

### Impact Explanation
Any holder of a valid CCMenu-capable API token (even one deliberately scoped to a single, non-sensitive stack) can enumerate `stack_id` params and pull the CCTray XML for every other stack in the Shipit instance, including stacks backed by private GitHub repositories the token holder has no GitHub access to. The exposed `lastBuildLabel` reveals the exact last-deployed commit SHA, `activity`/`lastBuildStatus` reveal deploy/lock state, and `webUrl` reveals the stack's internal URL — all cross-tenant, unauthenticated-relative-to-that-stack disclosure. This matches the "High — unauthenticated read of stack state" impact class, since the token was never authenticated for stack B.

### Likelihood Explanation
Preconditions are minimal: an attacker only needs any legitimately issued `ApiClient` token with `read:stack` permission (which could be scoped to a totally unrelated, low-sensitivity stack) and knowledge or guessing of another stack's `stack_id`/param (e.g., `owner/repo/branch`, which may be discoverable). No GitHub credentials, no Shipit session, and no privileged role are required beyond possessing one legitimate scoped token. The exploit is a single unauthenticated-relative GET request and is fully repeatable against every stack in the instance.

### Recommendation
Remove the private `stack` override in `Shipit::Api::CCMenuController` and rely on the scoped `stacks.from_param!` from `BaseController` (or explicitly call `stacks.from_param!(params[:stack_id])` in the override) so the `current_api_client.stack_id` restriction is enforced consistently with every other API controller.

### Proof of Concept
Minitest under `test/controllers/api/ccmenu_controller_test.rb` (existing file):
1. Create `stack_a` and `stack_b`, each with a `Deploy`/`Task` bearing distinct `sha` values.
2. Create an `ApiClient` (`@client`) with `stack_id: stack_a.id` and `permissions: ["read:stack"]`.
3. `get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }`.
4. Assert:
   - `response.status == 200` (not 403/404), and
   - the XML `lastBuildLabel` equals `stack_b.deploys_and_rollbacks.last.until_commit.sha` (stack B's real SHA), proving the token scoped to stack A retrieved stack B's private data — the binding `disclosed_stack == token.stack_id` is violated (`stack_b.id != @client.stack_id`).
