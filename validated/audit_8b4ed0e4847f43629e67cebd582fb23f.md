## Uncontained Token Errors — Analog Found in `pallet-asset-conversion`

### Title
Atomic two-asset payout in `remove_liquidity` allows one poisoned asset to permanently trap a liquidity provider's *entire* position, including the otherwise-healthy asset - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet-asset-conversion::remove_liquidity` burns a user's LP tokens and then transfers back both underlying assets (`asset1`, `asset2`) inside a single atomic dispatchable. If the transfer of either asset fails for any reason outside the user's control, the whole extrinsic — including the burn and the *other*, perfectly healthy asset's transfer — is rolled back by FRAME's default dispatchable atomicity. This is a direct FRAME analog of the Set Protocol `BasicIssuanceModule` M05 finding: a single uncontained token failure blocks recovery of value that has nothing to do with the failing asset.

### Finding Description
`do_remove_liquidity` performs the payout unconditionally with the `?` operator, with no fallback or partial-redemption path: [1](#0-0) 

```rust
T::PoolAssets::burn_from(pool.lp_token.clone(), who, lp_token_burn, Expendable, Exact, Polite)?;

T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)?;
T::Assets::transfer(asset2, &pool_account, withdraw_to, amount2, Expendable)?;
```

The signed extrinsic entry point is `Pallet::remove_liquidity` (`call_index(2)`), reachable by any signed account with LP tokens: [2](#0-1) 

Because a Substrate dispatchable's storage mutations are only committed if the call returns `Ok`, a failure on the *second* transfer (`asset2`) causes the runtime to roll back the just-executed LP burn and the first transfer of `asset1` as well — even though `asset1`'s transfer had already succeeded logically. The user is left holding the same LP tokens they started with, unable to redeem *any* part of their position, including the healthy `asset1` leg, as long as `asset2`'s transfer keeps failing.

Pool creation via `create_pool` is permissionless (any signed account can pair any two `AssetKind`s), and asset creation via `pallet-assets` is itself typically permissionless with the creator becoming the asset's `Admin`/`Freezer`. This is the "since managers can choose any arbitrary components" element of the original finding, mapped onto FRAME: any user can create asset `X`, retain freezer/admin rights over it, pair `X` with a legitimate asset (e.g. the native token) in a pool, wait for third-party liquidity providers to add liquidity, and later use `pallet-assets::freeze` (an ordinary, asset-admin-scoped operation, not requiring any runtime governance/root privilege) to freeze the victim's account for asset `X`. From that point on, every call to `remove_liquidity` for that pool by the victim fails on the `asset2` transfer and rolls back, permanently trapping the victim's LP tokens and their share of the innocent asset1 as well.

The same pattern also affects the EVM-facing wrapper, which forwards directly into the same atomic function: [3](#0-2) 

There is no independent/partial withdrawal mechanism analogous to what the original report recommends ("handle redemption as internal accounting, allow users to withdraw any subset of components").

### Impact Explanation
A liquidity provider's funds become permanently unreachable through the pallet's public API as long as one leg of the pool remains untransferable to them (frozen account, blacklist-like restriction implemented by a custom `fungibles` asset backend, or any other non-standard/adversarial asset behavior on the "poisoned" side). This is a loss-of-funds / stuck-funds scenario for the victim, driven entirely by an ordinary two-party interaction (pool creation + liquidity provision) with no governance or validator compromise required. Severity is comparable to the original Medium-rated Set Protocol finding: value becomes unrecoverable through the intended mechanism, though the user's assets are not stolen (they're just frozen/inaccessible via `remove_liquidity`), and a runtime operator could in principle intervene via root-level asset "thaw"/force calls if the malicious admin doesn't cooperate — this partially mitigates severity relative to a total, irrecoverable loss.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to (a) create/administer an asset with freeze capability, (b) pair it with a desirable asset in a pool, and (c) wait for a victim to add liquidity before freezing them. This is entirely within reach of an unprivileged user under default `pallet-assets` configuration (asset creation and admin/freezer rights are not root-gated in the reference configuration), and requires no bug in `pallet-assets` itself — freezing a specific account for a specific asset is a documented, intended `pallet-assets` capability of the asset's `Freezer`/`Admin` origin.

### Recommendation
- Decouple the LP-token burn from the two asset payouts, or make the payout independently retryable per asset (e.g., credit failed legs to an internal "claimable" balance that the user can withdraw later once/if the underlying restriction is lifted), instead of an all-or-nothing atomic sequence.
- Alternatively, do not roll back the LP burn and successful `asset1` transfer if `asset2`'s transfer fails; instead, keep the failed leg's value in the pool as a claimable credit for `withdraw_to`, so a permanently-frozen counterpart asset cannot trap the healthy asset.
- Consider not allowing pool creation to grant the creator implicit administrative control (freeze rights) over assets that will subsequently pool with the native/reserve asset without some vetting, or document explicitly that using non-audited/attacker-controlled `AssetKind`s in `pallet-asset-conversion` pools carries this specific fund-lockup risk.

### Proof of Concept
No executable PoC was run against a live test harness in this session (tool access ended before an integration test could be authored and executed); the analysis above is based on direct code inspection of `do_remove_liquidity` (substrate/frame/asset-conversion/src/lib.rs:894-966) and the permissionless `create_pool`/`remove_liquidity` extrinsics. A concrete reproduction would:
1. Create two assets via `pallet-assets::create`/`force_create` under test as attacker; register `attacker` as `Freezer` for `asset2`.
2. `AssetConversion::create_pool(attacker, asset1, asset2)`, `add_liquidity` from a `victim` account.
3. Have `attacker` call `Assets::freeze(asset2, victim)` (a standard, non-privileged asset-admin call).
4. Call `AssetConversion::remove_liquidity(victim, asset1, asset2, lp_token_burn, ...)` and assert it errors, and assert via `assert_storage_noop!`/balance checks that the LP tokens are not burned and `asset1` is not transferred despite that leg being individually valid.

This construction was not executed here; it is offered as the exact scaffold needed to confirm the atomic-rollback trapping behavior demonstrated by the cited code paths.
