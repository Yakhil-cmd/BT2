### Title
Non-context-aware delimiter splitting in hookify frontmatter parser allows silent field-injection/omission that can downgrade a `block` hook rule to a no-op `warn` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter()` in the `hookify` plugin parses `.claude/hookify.*.local.md` rule files by naively splitting the raw file content on the literal `---` delimiter, exactly the anti-pattern described in the external report (splitting untrusted/structured text on a bare token instead of using length-prefixed or escaped boundaries). Because the split has no concept of "inside a quoted value" vs "delimiter," any `---` sequence occurring inside a frontmatter value (e.g. inside a `pattern` regex) truncates the parsed frontmatter dict early, silently dropping subsequent keys such as `action: block`. Downstream, `Rule.from_dict()` defaults `action` to `"warn"` when the key is missing [1](#0-0) , so a rule authored to `block` a dangerous command instead only emits a warning and the operation proceeds.

### Finding Description
`extract_frontmatter` performs the split as: [2](#0-1) 

`content.split('---', 2)` is context-free: it matches the literal substring `---` wherever it appears in the file, including inside a `pattern:` value, a `conditions[].pattern` value, or any other frontmatter string — there is no quoting/escaping awareness. If a value legitimately or maliciously contains `---` (e.g. a bash regex like `rm\s*---rf`, or any pattern text containing a markdown horizontal-rule sequence), the second `---` occurrence is consumed prematurely, and everything after it — including an `action: block` key that was meant to be part of the frontmatter — is pushed into `message` (the free-text body) instead of `frontmatter` dict.

`Rule.from_dict()` then computes the effective action via `frontmatter.get('action', 'warn')`, defaulting to `warn` when the key was lost [3](#0-2) . The `RuleEngine.evaluate_rules()` function branches strictly on `rule.action == 'block'` to decide whether to deny the tool call or merely surface a warning message [4](#0-3) . A rule silently downgraded from `block` to `warn` no longer denies `PreToolUse`/`Stop` events — it just appends a `systemMessage`, and the underlying tool call (e.g. `rm -rf`) proceeds.

This is reachable because rule files are commonly generated by the `/hookify` command itself, which derives `pattern` values from LLM analysis of the conversation transcript [5](#0-4) . Any conversation content that can influence the generated `pattern` string (including content originating from untrusted sources the agent has read, e.g. a fetched file/page) can inject a `---` into that value, causing the resulting rule file to have its `action: block` line silently dropped by the parser.

### Impact Explanation
This is a hook-bypass class issue: a security control the user explicitly configured to `block` a dangerous action (matching the plugin's stated purpose — "prevent unwanted behaviors," "block dangerous rm commands," etc., per `plugins/hookify/README.md`) can be silently downgraded to advisory-only without any error, warning, or indication to the user that the rule stopped enforcing. Because `load_rule_file` swallows parsing anomalies and only warns when frontmatter is entirely empty [6](#0-5) , there is no signal that a `block` rule quietly became a `warn` rule. The practical effect is unauthorized execution of an operation (e.g. a destructive Bash command) that the project's own hookify policy was supposed to deny.

### Likelihood Explanation
Exploitation requires the attacker to influence the *content* that ends up in a hookify rule's frontmatter value (most plausibly the `pattern` field), typically via prompt-injection into content the agent reads before running `/hookify`, or a manually crafted rule file containing a pattern with an embedded `---`. This is a multi-step, somewhat narrow trust boundary (it affects the rule file that the *victim's own* agent writes to enforce their own policy), so likelihood is moderate rather than trivial — but it requires no special privilege beyond the ability to get attacker-influenced text into a `pattern`/value field, matching the "unprivileged-user analog" criteria for hook-bypass and frontmatter-parsing trust boundaries.

### Recommendation
Replace the delimiter-based `content.split('---', 2)` with a parser that treats `---` only when it appears alone on its own line (e.g. `^---\s*$` anchored per-line, as many YAML frontmatter parsers do), and reject/escape any `---`-only lines appearing inside quoted values. More robustly, switch to a real YAML parser (`PyYAML`'s `safe_load`) for the frontmatter block instead of the hand-rolled line-based state machine, and fail closed (treat the whole file as invalid / rule disabled) rather than silently truncating when a parse ambiguity is detected, rather than defaulting missing `action` to the permissive `warn`.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```
---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm\s*---\s*rf
action: block
---

Dangerous rm blocked!
```
2. `extract_frontmatter` calls `content.split('---', 2)`. The literal `---` inside the `pattern` value is the *second* occurrence of `---` in the file (first is the opening delimiter). This truncates `frontmatter_text` to just `\nname: block-dangerous-rm\nenabled: true\nevent: bash\npattern: rm\s*`, and everything after — including `rf\naction: block\n` and the real closing `---` — is shoved into `message`.
3. The resulting `frontmatter` dict has no `action` key, so `Rule.from_dict` sets `action = frontmatter.get('action', 'warn')` → `"warn"` [7](#0-6) .
4. When the agent later runs `rm -rf ...`, `RuleEngine.evaluate_rules` matches the (mangled but still regex-functional) pattern, but since `rule.action != 'block'`, it is added to `warning_rules` and the hook returns only a `systemMessage`, not a `permissionDecision: deny` [8](#0-7) . The destructive command executes despite the rule author's intent to block it.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
