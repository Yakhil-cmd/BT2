### Title
Webhook signature verification key selected from unverified `repository.owner.login`/`organization.login` field allows cross-organization signature confusion - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate a webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the **unauthenticated** JSON body, before the HMAC signature has been checked [1](#0-0) . The organization name used to look up the secret is only self-declared in the payload and is never independently confirmed against the repository record that the rest of the pipeline (`create` → `Shipit::Webhooks.for_event`) will actually act upon [2](#0-1) [3](#0-2) .

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository the handlers act on`. Instead:

- `verify_signature` derives `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [3](#0-2) .
- It fetches `Shipit.github(organization: repository_owner)` and verifies the signature using that organization's `webhook_secret` against the raw body [1](#0-0) , and `GitHubApp#verify_webhook_signature` does a straightforward HMAC compare keyed on whichever org's secret was resolved [4](#0-3) .
- Because Shipit supports multiple organizations each with their own app/secret in `config/secrets.yml` (documented in `docs/setup.md`), an actor who legitimately administers their own tracked organization's GitHub App knows that org's `webhook_secret` and can therefore forge a **valid** signature for any payload body they construct, as long as `repository.owner.login`/`organization.login` in that body names their own organization.
- The `create` action then parses the same raw body and dispatches it to `Shipit::Webhooks.for_event(event)` handlers [2](#0-1) , none of which re-derive or re-check the organization from the now-verified signature; they operate on whatever `repository.full_name` (or other repository-identifying fields) appears in the JSON body.
- Nothing in `verify_signature` cross-checks that `repository.full_name`'s owner segment matches the `repository_owner` used to pick the verification key. The signature only proves "this body was signed by organization X's secret" — it does not prove "the repository referenced inside this body belongs to organization X."

This is the same class of bug as CVE-2024-2466: the verification step trusts a field (hostname / organization name) taken from the payload to select the cryptographic material used to validate that very payload, but does not bind the verified identity to the identity actually acted upon afterward.

### Impact Explanation
If exploitable end-to-end, this would let an attacker who controls one organization tracked by a shared Shipit instance forge signed webhook events (e.g. `push`, `status`, `check_suite`) that name a *different, victim* organization's repository in `repository.full_name`, causing Shipit to sync commits, update commit statuses, or trigger check-run refresh jobs for a repository the attacker does not control — a cross-repository/cross-organization write performed under a security check that is meant to prevent exactly that.

### Likelihood Explanation
I was not able to confirm within the available context (index limits prevented me from opening `push_handler.rb`, `handler.rb`, and `repository.rb` in the final iteration) whether the push/status/check-suite handlers resolve the target `Stack`/`Repository` strictly from `repository.full_name` independent of `repository_owner`, or whether they perform an additional owner-consistency check before writing. The grep results show `full_name` is referenced in `app/models/shipit/repository.rb` and several PR handlers, but I could not verify the exact lookup logic or whether a secondary binding (e.g., `Repository.github_repo_name` scoping) closes this gap. This is also gated on the deployment actually configuring multiple organizations (multi-tenant `github:` config), which the docs explicitly support but is an operational choice.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the signature, re-derive the organization from the same `repository.owner.login`/`organization.login` value and require every handler to confirm that the repository/stack it is about to mutate belongs to that verified organization before making any writes — i.e., bind the verified signer identity to the resource acted upon, not just to "some" resource named in the payload.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
