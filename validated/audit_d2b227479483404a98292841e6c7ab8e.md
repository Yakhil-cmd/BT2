### Title
Front-running `initialize`/`initialize_with_permission` lets an attacker permanently hijack the `pool_creator` role and steal all future creator-fee revenue - ([File: programs/cp-swap/src/instructions/initialize.rs])

### Summary
`initialize` (and `initialize_with_permission`) can be called by **any** signer — the account docs explicitly say "Address paying to create the pool. Can be anyone" [1](#0-0) . The `pool_state` PDA address is deterministic, derived only from `amm_config`, `token_0_mint`, and `token_1_mint`, none of which are secret [2](#0-1) . Because there is no access control tying the call to a specific intended creator, an attacker can observe a pending `initialize` transaction for a desirable token pair in the mempool and front-run it with their own transaction using the same deterministic accounts, becoming the immutable `pool_creator` recorded in `PoolState` [3](#0-2) .

### Finding Description
`create_pool` allocates the PDA at the deterministic address derived from `POOL_SEED`, `amm_config`, `token_0_mint`, `token_1_mint` [4](#0-3) . Since this PDA depends only on public information (config index and mint addresses), any unprivileged party can pre-compute it off-chain (as done in `initialize_pool_instr`) [5](#0-4)  and race a legitimate creator's `initialize` transaction.

Whoever's `initialize` call lands first is permanently recorded as `pool_creator` in `pool_state.initialize(...)` [6](#0-5) . This role is not just cosmetic — `pool_creator` is the sole party entitled to `collect_creator_fee` and the fee-destination for `collect_creator_fee_permissionless`, both enforced via `address = pool_state.load()?.pool_creator` constraints [7](#0-6) [8](#0-7) . There is no admin function to change `pool_creator` after initialization, so this capture is permanent for the lifetime of the pool.

The attacker only needs minimal capital: enough tokens to satisfy `CurveCalculator::validate_supply` and pay the `create_pool_fee`, both of which can be trivially small [9](#0-8) .

### Impact Explanation
Once the attacker's front-run transaction succeeds, the legitimate creator's `initialize` call fails (the PDA already exists, `pool_account_info.owner != &system_program::ID` check triggers `ErrorCode::NotApproved` on their now-redundant call) — wasting the legitimate creator's gas and forcing them to abandon that pool config/mint combination, since the pool address for that exact `(amm_config, token_0_mint, token_1_mint)` triple can never be re-initialized. Worse than pure DoS: the legitimate project is now forced to either use the attacker-controlled pool (permanently diverting all future creator-fee revenue to the attacker) or use a different `amm_config` index, fragmenting liquidity for that token pair. This is an unauthorized privileged effect — permanent hijacking of a fee-collection role and diversion of protocol/creator fee revenue — reachable from a single unprivileged transaction with attacker-chosen accounts.

### Likelihood Explanation
Pool creation transactions for popular/anticipated token pairs are highly visible in the mempool and highly incentivized to front-run (MEV bots monitor `Initialize`/`InitializeWithPermission` instructions routinely on Solana AMMs). The attack requires no special privileges, no leaked keys, and minimal capital, only correct computation of public PDAs, making it straightforward for any bot to execute opportunistically whenever a new/anticipated token pair pool is about to be created.

### Recommendation
Bind the `pool_state` PDA (or a permission gate before allowing the vault/LP-mint creation) to a specific expected creator, e.g., require the pool address seed to include the intended creator's pubkey, or require the `initialize` transaction to be co-signed/authorized by a pre-registered creator identity (similar to `initialize_with_permission`'s "permission" account mechanism) so front-running cannot substitute an unauthorized `pool_creator`. Alternatively, allow a governance/admin path to update `pool_creator` if it can be proven the wrong party initialized the pool.

### Proof of Concept
1. Legitimate creator Alice builds and broadcasts an `Initialize` transaction for mint pair `(X, Y)` under `amm_config` index `0`, computing `pool_state`, `token_0_vault`, `token_1_vault`, `lp_mint`, `observation_state` PDAs exactly as done in `initialize_pool_instr` [10](#0-9) .
2. Attacker Bob observes Alice's pending transaction (or simply predicts pool creation for a popular new token pair), computes the identical deterministic `pool_state` PDA and related accounts, and submits his own `Initialize` transaction with `creator = Bob`, a minimal `init_amount_0/init_amount_1` satisfying `validate_supply`, prioritizing it to land first.
3. Bob's transaction succeeds: `create_pool` allocates the PDA, and `pool_state.initialize(...)` records `ctx.accounts.creator.key()` (Bob) as `pool_creator` [6](#0-5) .
4. Alice's original transaction now fails because `pool_account_info.owner != &system_program::ID` no longer holds true for a fresh account [11](#0-10) .
5. Going forward, every `collect_creator_fee`/`collect_creator_fee_permissionless` call routes accumulated `creator_fees_token_0/1` to Bob's token accounts (enforced by `address = pool_state.load()?.pool_creator`) [7](#0-6) , permanently diverting fee revenue intended for Alice's project.

pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);
    }
