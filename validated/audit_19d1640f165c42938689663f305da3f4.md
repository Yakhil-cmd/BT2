### Title
CCMenu API endpoint bypasses ApiClient stack scoping, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` can be scoped to a single stack via its optional `stack` association [1](#0-0) , and `Api::BaseController` enforces that scoping for every stack-touching action by resolving stacks through the `stacks`/`stack` helpers, which restrict the queryable set to `current_api_client.stack_id` when present [2](#0-1) . `Api::CCMenuController` overrides `stack` to resolve directly against the global `Stack` model using the request parameter, bypassing that scoping entirely [3](#0-2) .

### Finding Description
The intended binding is: `current_api_client.stack_id` (the stack a token is authorized for) MUST equal the `stack_id` param a stack-scoped request actually touches, whenever `current_api_client.stack_id?` is true.

`Api::BaseController#stacks` enforces exactly this equality for every controller that inherits its `stack` helper: if the authenticated `ApiClient` has a `stack_id`, the resolvable set is narrowed to `Stack.where(id: current_api_client.stack_id)` before `from_param!` is applied [2](#0-1) . This is confirmed by the test asserting that "an api client scoped to a stack will only see that one stack" [4](#0-3) .

`Api::CCMenuController`, however, defines its own private `stack` method that ignores `current_api_client` entirely and resolves any stack the caller names in `params[:stack_id]`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

The controller only checks that the token carries the generic `read:stack` permission via `require_permission :read, :stack` [6](#0-5) , which merely calls `ApiClient#check_permissions!` to verify the permission string is present in the token's `permissions` array [7](#0-6) . It never checks whether the token's `stack_id` matches the requested `stack_id`. As a result, a token that was deliberately scoped to Stack A (e.g. created by `CCMenuUrlController#client`, which mints `read:stack`-only `ApiClient`s intended for restricted CI-dashboard use [8](#0-7) ) can be replayed against `/api/:stack_id/cc.xml` for any other Stack B and still succeed, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

Before the attacker's request: token T (`stack_id = A`, `permissions = [read:stack]`) is only supposed to yield build/deploy status for stack A.
After the attacker's request: the same token T, submitted with `params[:stack_id] = B`, yields `stack.deploys_and_rollbacks.last` and renders the CI status XML for stack B [9](#0-8) , i.e. `token.stack_id == A` but the request touches stack `B ≠ A` — the exact binding class described in the rules (a stack a token authorises versus a stack it touches).

### Impact Explanation
This is an authorization scope bypass that grants unauthenticated-for-that-resource read access to stack state (deploy/build status, last build label, web URL) for any stack in the installation, using a token that was only meant to be valid for one specific stack. This matches the specified High-impact class: "unauthenticated read of stack state, task streams or deploy output" — the attacker only needs possession of any single stack-scoped `read:stack` token (which is routinely handed out via `CCMenuUrlController#fetch`'s generated `ccmenu_url` containing the token in a query string [10](#0-9) ) to enumerate/read status for stacks it was never granted.

### Likelihood Explanation
High. No special privilege is required beyond holding one legitimately-scoped CCMenu token (these URLs are meant to be embedded in third-party CI dashboard tools and are not treated as highly sensitive secrets by operators). The bypass is a simple parameter substitution (`stack_id`) in an otherwise normal, documented API call; it requires no signature forgery, no additional credentials, and no interaction with GitHub.

### Recommendation
Remove `CCMenuController`'s private `stack` override, or reimplement it to reuse `BaseController#stack`/`#stacks` so the `current_api_client.stack_id` restriction is enforced consistently, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the invariant that a stack-scoped token can only ever resolve to its own stack.

### Proof of Concept
1. As an operator, visit a Stack A's page and trigger `CCMenuUrlController#fetch` (or otherwise obtain a `read:stack`-scoped `ApiClient` token bound to Stack A) — this returns a URL like `.../api/A/cc.xml?token=<T>` [10](#0-9) .
2. As an attacker who obtains token `T` (e.g. from a leaked/shared dashboard link), send `GET /api/B/cc.xml?token=<T>` where `B` is an arbitrary, unrelated stack.
3. `CCMenuController#authenticate_api_client` accepts `T` via `ApiClient.authenticate(params[:token])` [11](#0-10) ; `require_permission :read, :stack` passes because `T` carries `read:stack` [7](#0-6) ; `stack` resolves `B` directly, ignoring `T.stack_id == A` [5](#0-4) .
4. The response renders Stack B's `deploys_and_rollbacks.last` build status, disclosing deploy state for a stack the token was never authorized to see [9](#0-8) .
