### Title
Webhook signature is verified against the organization named in `repository.owner.login`, while every handler acts on the organization/repository named in `repository.full_name` - allowing cross-organization/cross-repository webhook forgery — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to HMAC-verify the request against using one payload field (`repository.owner.login`), but the event handlers that actually mutate state (`PushHandler`, `MembershipHandler`, `StatusHandler`, the `PullRequest::*` handlers) resolve the target `Repository`/`Stack` from a *different* payload field (`repository.full_name`). Both fields are attacker-controlled in the raw JSON body that is being forged, so nothing in the code enforces that they agree.

### Finding Description
`verify_signature` selects the signing organization purely from the body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` intentionally treats an org with no configured secret as always-valid: [3](#0-2) 

Multi-organization deployments are a documented, first-class configuration where each org has its own (optionally blank) `webhook_secret`: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, the entire raw payload is dispatched to handlers, all of which look up the actual repository via `repository.full_name` — an independent field from the one used to pick the verifying secret: [6](#0-5) [7](#0-6) [8](#0-7) 

The equality this breaks is: `organization used to authenticate the request == organization/repository the handler writes to`. Concretely, an attacker crafts a JSON body where `repository.owner.login` names an organization configured in `Shipit.github` with a blank/unset `webhook_secret` (so `verify_webhook_signature` short-circuits to `true` with no real HMAC needed), while `repository.full_name` names an entirely different, victim organization/repository that has real `Stack`s. `Repository.from_github_repo_name` performs no cross-check against the owner used for authentication: [9](#0-8) 

### Impact Explanation
This is an unauthenticated write into a repository/stack the attacker never proved control of, i.e. a cross-repository write reachable by an unprivileged attacker with no session, no `ApiClient` token and no GitHub App key:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for the victim stack with an attacker-chosen SHA, letting the attacker steer what commit Shipit treats as HEAD for sync/deploy purposes.
- `MembershipHandler` creates/deletes `Team`/`Membership` rows for the victim org, directly influencing `Shipit.github_teams` authorization checked by `User#authorized?`.
- `StatusHandler` forges commit statuses on victim commits, which feed merge-queue safety checks.
- The `PullRequest::*` handlers can archive/unarchive review stacks and rewrite label state on the victim repository.

This matches the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact tiers.

### Likelihood Explanation
Requires the host's multi-org `Shipit.github` configuration to include at least one organization with no `webhook_secret` set — a state the engine's own docs and example config files present as a normal, supported configuration rather than misuse. Given that precondition, exploitation needs only a single unauthenticated HTTP POST to the public webhooks endpoint; no signature computation, no credentials, and no prior access are needed.

### Recommendation
Bind the organization used for signature verification to the same field(s) the handlers actually act on, or reject payloads where `repository.owner.login`/`organization.login` doesn't match the owner portion of `repository.full_name`. Additionally, reconsider `verify_webhook_signature`'s `return true unless webhook_secret` fallback — treat a missing secret for a configured organization as a hard rejection (fail closed) rather than an implicit bypass, and require handlers to validate that the resolved `Repository`'s owner equals the organization that authenticated the request.

### Proof of Concept
1. Assume `Shipit.github` is configured for two organizations: `staging-org` (no `webhook_secret` set, e.g. left `nil` in `secrets.yml` per `docs/setup.md`) and `victim-org` (real production org with a real webhook secret and active `Stack`s).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, and a JSON body:
```json
{
  "repository": { "owner": { "login": "staging-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `repository_owner` = `"staging-org"`, fetches `Shipit.github(organization: "staging-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request passes.
4. `PushHandler` resolves the target via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, finds the real `Repository`/`Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on it — a state-changing action on a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
