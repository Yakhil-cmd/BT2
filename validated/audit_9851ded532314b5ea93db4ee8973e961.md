## Title
Unguarded Exception in `definition template` Authentifier Evaluation Crashes the Node - (File: `definition.js`)

### Summary
`definition.js`'s `validateAuthentifiers()` re-evaluates an address's spending definition every time a unit signed by that address is validated. When the definition contains a `['definition template', [unit, params]]` node, the evaluator looks up the referenced template unit and calls `replaceInTemplate()`. Unlike the parallel code path in `validateDefinition()` (used only once, when the definition is first introduced), this code path is **not wrapped in a try/catch**, so any thrown error propagates as an uncaught exception out of an asynchronous `conn.query()` callback and crashes the whole node process, because ocore installs a global handler that deliberately re-throws to kill the process.

### Finding Description
`definition.js` contains two near-identical implementations of the `'definition template'` opcode:

1. `validateDefinition()` (used only at definition-creation time), which safely wraps the risky call: [1](#0-0) 

```
conn.query(... WHERE unit=? AND app='definition_template' ... , [unit, ...], function(rows){
    if (rows.length !== 1)
        return cb("template not found or too many");
    var template = rows[0].payload;
    var arrTemplate = JSON.parse(template);
    try{
        var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
    }
    catch(e){
        if (e instanceof NoVarException)
            return cb(e.toString());
        else
            throw e;
    }
    evaluate(arrFilledTemplate, path, bInNegation, cb);
});
```

2. `validateAuthentifiers()` (executed on **every** unit signed from this address, i.e. every future spend), which has no such protection: [2](#0-1) 

```
case 'definition template':
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            var template = rows[0].payload;
            var arrTemplate = JSON.parse(template);
            var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
            evaluate(arrFilledTemplate, path, bInNegation, cb2);
        }
    );
    break;
```

Two distinct unguarded throw sites exist here:
- `throw Error("not 1 template")` when the referenced template unit is not found (or not yet stable) at the `last_ball_mci` visible to *this particular spending unit* — which can legitimately differ from the mci that was visible when the address definition was first validated.
- The direct (unguarded) call to `replaceInTemplate(arrTemplate, params)`, which can throw `NoVarException` or other errors when `params` does not satisfy every placeholder required by the template.

Both throws occur inside the callback of an asynchronous `conn.query()`, i.e., outside the call stack of any surrounding `try/catch` in `validateAuthentifiers` or in `validation.js`'s `validate()`. The resulting exception is therefore an uncaught exception at the process level. `network.js` explicitly converts any uncaught exception into a fatal crash: [3](#0-2) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

### Impact Explanation
Any address whose definition uses `['definition template', ...]` is, by design of the definition language, an address that any counterparty can reference in the "used_in_unit's `authors[].address`" field. Once such an address has been established (defined once via `validateDefinition`, which is properly guarded), **every subsequent unit spending from that address** triggers `validateAuthentifiers` on all full nodes that receive/relay/validate the unit (this is standard signature verification during `validation.js`'s `validateAuthor` flow). If the referenced template unit is not resolvable as stable at the specific `last_ball_mci` of the new spending unit (e.g., attacker deliberately picks a `last_ball_mci` earlier than the template's stabilization, or the template row count is otherwise not exactly 1), or if `params` no longer satisfies the template's variable requirements, the throw is uncaught and crashes every node — full nodes, hubs, and witnesses alike — that attempts to validate the unit. Because unit validation/broadcast is core consensus machinery reachable by any unprivileged unit poster, this can be used to repeatedly crash all validating nodes on the network each time the malicious unit propagates, preventing the network from confirming new units (denial of service matching the CWE-476/CVE-2025-8402 bug class: unvalidated data driving a fatal dereference/exception during processing).

### Likelihood Explanation
The attack requires only:
1. Defining (once, cheaply) an address whose spending condition is `['definition template', [tmpl_unit, params]]`, referencing a `definition_template` message the attacker controls.
2. Posting a spending unit from that address with `last_ball_mci` chosen so the template lookup query returns 0 rows (or manipulating `params` so `replaceInTemplate` throws).

No special privileges (admin, witness, hub) are required — this is achievable by any ordinary unit author, matching the report's "unprivileged unit poster" reachability requirement. The asymmetry between the guarded `validateDefinition` path and the unguarded `validateAuthentifiers` path strongly suggests this is an overlooked code path rather than an intentional design decision.

### Recommendation
Wrap the `'definition template'` case body in `validateAuthentifiers()` (definition.js, ~lines 802-819) in a try/catch identical to the one already used in `validateDefinition()`:
- Convert `throw Error("not 1 template")` into `return cb2(false)` (treat as authentication failure, not a fatal error).
- Wrap `replaceInTemplate(arrTemplate, params)` in try/catch, converting `NoVarException` and other exceptions into `cb2(false)` rather than letting them propagate uncaught.

### Proof of Concept
1. Attacker creates and stabilizes a `definition_template` message at unit `T` with a template requiring parameter `$x`.
2. Attacker creates address `A` with definition `['definition template', [T, {x: 'val'}]]` and uses it normally once (so `validateDefinition` succeeds, establishing `A`).
3. Attacker crafts a new unit `U` spending from `A`, choosing `last_ball_unit`/`last_ball_mci` so that, at the mci referenced by `objValidationState.last_ball_mci` for `U`, the query `SELECT payload FROM messages JOIN units USING(unit) WHERE unit=T AND app='definition_template' AND main_chain_index<=? AND sequence='good' AND is_stable=1` returns 0 rows (e.g., by picking an earlier last_ball than when `T` stabilized, exploitable if the address was defined with a later last_ball reference the first time but the attacker can present a different/earlier last_ball with subsequent spends since `last_ball_mci` varies per spending unit).
4. When any node validates `U`'s signature via `validateAuthentifiers`, the query callback executes `throw Error("not 1 template")` with no enclosing try/catch, producing an uncaught exception that is caught by `network.js`'s global handler, which re-throws and crashes the node process.

Note: I could not fully trace every possible avenue by which `last_ball_mci` can diverge between the initial `validateDefinition` check and a later `validateAuthentifiers` check for the same address/template pair within the current context window; a background engineering session with full repository access should confirm the exact mci-divergence scenario (e.g., via reorg, chain of AAs, or asynchronous stabilization) and write a runnable end-to-end reproduction unit before finalizing severity to Critical vs High.
