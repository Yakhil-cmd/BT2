### Title
Repository-unscoped commit status webhook allows cross-repository CI-state poisoning - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with `Commit.where(sha: params.sha)`, then calls `create_status_from_github!` on every match, with no filter tying the operation to the repository that actually emitted the webhook. Every other handler in the same directory (e.g. `PushHandler`) scopes its side effects via the `stacks` helper (repository-derived), but `StatusHandler` does not, so a validly-signed status event for one repository can mutate CI state, `blocked?`, and `deployable?` for commits belonging to unrelated stacks/repositories whenever the same SHA exists in more than one place in the database.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository == webhook.repository` for every row returned by `Commit.where(sha: params.sha)`, but nothing in `StatusHandler#process` enforces that equality.

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`WebhooksController#verify_signature` only checks that the HMAC signature matches the GitHub App/webhook secret associated with `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates *who sent the event*, not which specific `Commit` rows the event is allowed to touch:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [2](#0-1) 

By contrast, `PushHandler#process` scopes mutation to stacks derived from the payload's repository/branch:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

`StatusHandler` receives the same `stacks` helper available to it (via `Handler`) but never uses it — it matches purely on SHA. `Commit#blocked?` and `Commit#deployable?` are driven by `statuses`, which is populated by `create_status_from_github!`:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end

def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end
``` [4](#0-3) 

Exploit flow: whenever the same commit SHA exists as a `Commit` row in more than one stack — which happens legitimately whenever multiple Shipit stacks track the same upstream history (forks, mirrors, shared branches merged into several stacks, monorepo splits) — an attacker who owns/controls one of those repositories (and can therefore produce a genuinely-signed `status` webhook for it, e.g. via their own CI reporting to their own fork) can send `state: failure` for that shared SHA. `verify_signature` passes because the signature is valid for the attacker's own repository/organization. `StatusHandler#process` then finds every `Commit` row with that SHA — including ones belonging to the victim's unrelated stack — and writes the failure status onto them via `create_status_from_github!`, flipping `blocked?`/`deployable?` for the victim's pipeline.

### Impact Explanation
A payload authenticated for repository A ends up mutating `Status` records (and therefore CI blocking/deployability state) for stacks belonging to repository/tenant B, purely because both happen to contain a `Commit` row with the same SHA. This is a cross-tenant record-mutation bug: one repository's authenticated event writes another repository's `Commit`/`Status` data, without any authorization check tying the two together. It is repeatable for every matching SHA and blast radius spans every stack in the Shipit instance, matching the "Critical — payload for one repository mutating another's stack/commit" category.

### Likelihood Explanation
Exploitability requires that the attacker-controlled repository share at least one commit SHA with the victim's tracked repository/stack — a common real-world condition for forks, mirrors, or shared-history repositories tracked by multiple Shipit stacks, and something an attacker can engineer deliberately (e.g., by forking the victim's repo and having their own CI/webhook emit a status for a shared ancestor commit). No Shipit credentials, session, or team membership are required — only the ability to have a `status` event signed for a repository the attacker legitimately controls. The `verify_signature` check does not, and structurally cannot, prevent this, since it authenticates the sender/repository, not the specific `Commit` rows the handler is about to mutate.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks tracking the repository that emitted the webhook (using the `repository`/`sha` from the payload joined against `stacks`/`repository_id`, similar to how `PushHandler` uses the `stacks` helper), instead of matching on bare SHA across the entire `commits` table.

### Proof of Concept
Minitest plan (no live GitHub):
1. Seed two `Stack`s belonging to two different `Repository` records (`repo_a`, `repo_b`).
2. Create a `Commit` with `sha: "deadbeef..."` on `stack_a` (repo A) and another `Commit` with the same `sha` on `stack_b` (repo B), both currently green/success (`deployable?` true, `blocked?` false).
3. Build a `status` payload for repo A only (`repository.full_name = repo_a.full_name`, `sha: "deadbeef..."`, `state: "failure"`, matching signature for repo A's org).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(...).call(payload)` (or POST through the controller with a valid signature for repo A).
5. Assert: `stack_a`'s commit now has a failing status (`commit_a.reload.failure?` true) — expected/legitimate.
6. Assert (bug): `stack_b`'s commit — belonging to repo B, which never emitted this event — also now has a failing status (`commit_b.reload.failure?` true), and `commit_b.blocked?`/`commit_b.deployable?` have changed, proving cross-repository state was mutated by a payload that was only authenticated for repo A.
