### Title
`in_data_feed`/oracle-existence checks trust unconfirmed non-'good' units, letting AAs act on data that will never become final - ([File: data_feeds.js])

### Summary
The Rainbow Bridge incident involved an attacker submitting unconfirmed/fake blocks that the bridge briefly treated as valid before final settlement caught the fraud. The analogous class of bug in `ocore` is trusting not-yet-finalized (unstable, non-`good`-sequence) unit data as if it were settled truth when an AA makes a fund-affecting decision.

### Finding Description
`dataFeeds.dataFeedExists()` is used by the oscript/formula engine to implement the `in_data_feed` boolean-existence check (`formula/evaluation.js:701-748`), which AA authors commonly use as a gate for releasing funds or executing branches based on an oracle posting a value. [1](#0-0) 

When called with `bAA=true` (the AA-execution path), `dataFeedExists` scans `storage.assocUnstableMessages` — i.e., data-feed messages from units that are *not yet stable* — to find a match immediately, without waiting for stabilization: [2](#0-1) 

Critically, unlike the sibling function `readDataFeedValue()` (used for `data_feed[...]` value reads), which explicitly filters out units whose `sequence !== 'good'`: [3](#0-2) 

`dataFeedExists()`'s unstable-scan loop has **no such sequence check** — it only checks `objUnit.bAA`, the MCI range, and author-address intersection before scanning the unit's messages for a match: [4](#0-3) 

A unit can be present in `assocUnstableMessages` with `sequence` set to `'good'` or `'temp-bad'` (a unit later determined to conflict/double-spend, pending final resolution) before stabilization. `'temp-bad'` units are the local, as-yet-unconfirmed view of a conflicting/non-serial unit; if the conflict resolves against it upon stabilization, it becomes `'final-bad'` and its message is deleted: [5](#0-4) 

Because `dataFeedExists` does not check for `sequence==='good'`, an oracle-address-authored unit that is provisionally `'temp-bad'` (i.e., destined to be excluded from final history) can still satisfy an `in_data_feed[...]` condition inside an AA formula while it is unstable. This is a direct parallel to trusting an unconfirmed/soon-to-be-orphaned block: the AA can execute state changes / fund transfers on the strength of data that has a real chance of never becoming part of the final, agreed ledger.

### Impact Explanation
An AA gated by `in_data_feed[[oracles=..., feed_name=..., feed_value=...]]` (a very common oscript idiom for oracle-triggered payouts, e.g. price-feed conditional releases, insurance payouts, prediction markets) can be tricked into paying out or changing irreversible state based on a data-feed message from a unit that is provisionally bad and will be excluded from the DAG upon stabilization. Since AA responses that already executed (e.g., sent funds) are not rolled back merely because the *triggering evidence* (the oracle unit) later turns out to be non-serial, this is a path to unauthorized fund loss/inconsistent AA state — matching "AA fund loss" in the validation criteria.

### Likelihood Explanation
Reaching this requires only unprivileged, permissionless actions available to any unit poster: posting a data-feed message from an address recognized as an oracle by the target AA's condition, in a way that conflicts with another unit from the same author (causing local `'temp-bad'` sequencing), and triggering the AA before stabilization resolves the conflict. AAs are executed reactively on new unstable units, so the race window between "unstable, temp-bad" and "stabilized/final-bad" is exactly the window exploited. No special network position, hub role, or leaked key is needed — only crafting/posting conflicting units, which is a standard capability of any unit poster/AA trigger sender.

### Recommendation
Add the same `sequence !== 'good'` guard used in `readDataFeedValue()`'s unstable-scan loop to the unstable-scan loop inside `dataFeedExists()`, so that `in_data_feed`/`data_feed[[...]]` boolean existence checks used by AAs never consider messages from units whose sequence has not been determined (or has already resolved) to `'good'`.

### Proof of Concept
Note: I was unable to fully trace the exact end-to-end AA trigger timing window (e.g., whether `aa_composer.handleAATriggers()` can run against a trigger unit whose best-parent chain includes a `'temp-bad'` oracle unit before `markMcIndexStable` resolves it) using the available search tools; this would need to be confirmed by exercising the code (or with a Devin session) rather than static reading alone. The conceptual PoC is:
1. Attacker controls (or compromises briefly) an address that an AA's `in_data_feed` condition treats as an oracle.
2. Attacker posts two conflicting units from that oracle address at nearly the same DAG position — one posting `feed_value = X` that will satisfy the AA condition, and another (from the same address, causing non-serial/double-spend conflict) that is expected to "win" and become `'good'`, leaving the `feed_value = X` unit as `'temp-bad'`.
3. Before stabilization resolves which unit is `'good'`, attacker (or an accomplice) posts an AA trigger unit that is processed while both units are still in `assocUnstableMessages`.
4. Formula evaluation calls `dataFeeds.dataFeedExists(..., bAA=true, ...)`, which iterates `assocUnstableMessages` without checking `sequence`, finds the `temp-bad` unit's `feed_value = X` message, and returns `true`, causing the AA to execute the funds-releasing branch.
5. Upon stabilization, the `temp-bad` oracle unit is confirmed `'final-bad'` and deleted from `assocUnstableMessages`, i.e., it never becomes part of finalized history — yet the AA has already irreversibly acted on it. [6](#0-5) [3](#0-2)
