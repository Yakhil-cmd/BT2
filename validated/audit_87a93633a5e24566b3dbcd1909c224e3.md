### Title
Cross-repository forged CI status via unscoped `StatusHandler` breaks the organization-authenticated/repository-written binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check in `WebhooksController#verify_signature` authenticates a **payload-declared organization**, not the repository/stack that ends up being written to. `Shipit::Webhooks::Handlers::StatusHandler` then writes a `Status` to `Commit.where(sha: params.sha)` with no scoping to the repository/organization that was actually verified, unlike `PushHandler`/`Handler#stacks`, which correctly scope by `repository.full_name`. This is the same class of bug as the reported issue: one enforcement point (`whenNotPaused` / signature verification) guards one path, while a second path (`onERC721Received` / `StatusHandler`) reaches the same sensitive state (supplying liquidity / writing a commit status) without being bound to what was actually authenticated.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against, using a field taken directly from the (unverified at that point) request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, i.e. the caller chooses which organization's secret is used to validate its own request. This means the "authenticated" binding is: *organization X's webhook secret authenticated this specific raw payload*. Nothing ties that binding to the specific repository/stack the payload subsequently writes to.

Compare the two handlers that consume the same signed payload:

- `PushHandler`/`Handler#stacks` correctly scope writes to the repository named in the payload, via `Repository.from_github_repo_name(repository_name)`: [3](#0-2) [4](#0-3) 

- `StatusHandler`, however, ignores the `Handler#stacks`/`repository_name` scoping entirely and matches **any** commit in the entire Shipit database by SHA, regardless of which repository/organization it belongs to: [5](#0-4) 

So the equality that should hold is: `organization authenticated by verify_signature == organization owning the commit that create_status_from_github! writes to`. It does not hold — `StatusHandler#process` writes to `Commit.where(sha: params.sha)` with zero reference to `repository_owner` or `repository_name`.

`Status#create` directly influences deploy eligibility and continuous delivery: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who legitimately administers *any* GitHub organization configured on the same multi-tenant Shipit instance (a normal, unprivileged tenant with respect to a victim's stack) knows/controls that organization's own `webhook_secret` (it's the secret they themselves configured for their own GitHub App). They can legitimately sign an arbitrary JSON body with `X-Github-Event: status`, set `repository.owner.login` to their own organization (so `verify_signature` passes using a secret they legitimately possess), but set `sha` to the SHA of a commit belonging to a **completely unrelated victim stack/repository** (SHAs are typically public on GitHub). `StatusHandler#process` will match that commit purely by SHA — with no check that the commit's repository/organization matches the organization whose secret was used to authenticate the request — and create a forged `success` `Status` for any `context`, including a `required` CI check context. Because `Commit#deployable?` and `schedule_continuous_delivery` key off `Status`, this can flip a previously non-deployable victim commit to deployable and trigger an unauthorized deploy on `continuous_deployment`-enabled stacks, or let an operator/human on the victim stack click "Deploy" believing CI passed. This matches the Critical "unauthorized deploy" impact category: it breaks the "organization authenticated vs. repository written" trust binding described in the rules.

### Likelihood Explanation
The attacker needs only: (1) any legitimate tenant organization already configured in the Shipit deployment (no privileged access to the victim's org/repo, no `ApiClient` token, no victim `webhook_secret`), and (2) the target commit's SHA, which is generally public information on GitHub. `/webhooks` is an unauthenticated, publicly reachable endpoint (`ActionController::Base`, no session), so this can be executed by a purely external, unprivileged actor with respect to the victim stack.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository actually verified for the request, exactly as `PushHandler`/`Handler#stacks` does — e.g. restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` or otherwise join through `Repository.from_github_repo_name(repository_name)` before matching by SHA, and additionally assert that `repository_owner` used in signature verification matches the repository/organization the handler is about to mutate.

### Proof of Concept
1. Attacker legitimately controls organization `attacker-org`, which is configured in this Shipit instance with `webhook_secret = S` (their own, real secret).
2. Attacker looks up a public commit SHA `deadbeef...` belonging to victim stack `victim-org/victim-repo`, which requires a status context `ci/required-check` to be `deployable?`.
3. Attacker crafts payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S, raw_body)` using their own known secret `S`, and sends `POST /webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using `S`.
6. `Shipit::Webhooks.for_event("status")` invokes `StatusHandler.call(params)`, which runs `Commit.where(sha: "deadbeef...").each { |commit| commit.create_status_from_github!(params) }` — matching the victim's commit regardless of organization, creating a forged `success` status for `ci/required-check`.
7. The victim commit becomes `deployable?` (or, if `continuous_deployment` is enabled on that stack, `schedule_continuous_delivery` triggers `ContinuousDeliveryJob`), resulting in an unauthorized deploy without any legitimate CI signal from `victim-org`.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
