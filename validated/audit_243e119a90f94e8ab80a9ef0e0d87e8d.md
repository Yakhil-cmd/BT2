## Analysis: Flash-loan-style price manipulation of balance-derived AMM prices via atomic AA-to-AA chaining

### Title
Atomic multi-hop AA invocation allows single-unit flash-loan-style manipulation of balance-derived exchange rates - (File: aa_composer.js, formula/evaluation.js)

### Summary
Obyte's Autonomous Agents (AAs) can reference their own live token reserves with `balance[asset]` and expose it to other AAs synchronously through getters (`remote_func_call`/`callGetter`). A single trigger unit can chain any number of AA invocations (primary trigger → secondary triggers → further secondary triggers, up to `MAX_RESPONSES_PER_PRIMARY_TRIGGER`) that execute atomically and sequentially inside one database transaction before the unit is finalized. This is architecturally identical to a flash loan: an attacker can, within one confirmed unit, deposit funds into a reserve-based AMM AA to skew its `balance[]`-derived exchange rate, have that skewed rate consumed by a second, price-dependent AA in the same chain, and then reverse the deposit — all before any other unit can interpose, and with no cost of capital beyond bounce fees.

### Finding Description
Any AA can hold reserves and price other assets purely from its own current balance, as shown in the officially shipped reference AMM `test/samples/uniswap_like_market_maker.oscript`, which computes swap amounts from `balance[$asset]` and `balance[base]` net of the current trigger's own inputs: [1](#0-0) 

`balance[...]` reflects the AA's real, currently-updated reserves at the moment of evaluation, as exercised in the formula test suite: [2](#0-1) 

That live balance is exportable to *other* AAs via getters, which run synchronously against the same `assocBalances` state and can return `balance[base]` (or any derived price) to a calling AA in the very same trigger-processing chain: [3](#0-2) 

The getter call path (`remote_func_call` → `callGetter`) executes against the caller's live `objValidationState.assocBalances`, so any state changes already applied earlier in the same trigger chain are visible to the getter: [4](#0-3) 

Crucially, `handleTrigger` allows one primary trigger to cascade into arbitrarily many secondary AA triggers (`handleSecondaryTriggers`), all processed synchronously within the same unit and the same outer transaction, up to `constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER`: [5](#0-4) [6](#0-5) 

The existing "chain of AAs" and "calling a chain of remote functions" tests confirm that arbitrarily deep AA-to-AA payment and getter chains are fully supported and execute atomically end-to-end in one unit: [7](#0-6) [8](#0-7) 

Because a single unit can (a) send a large payment into a reserve-priced AMM AA, (b) have a second victim AA in the *same* trigger chain read that now-skewed `balance[]`/getter-derived exchange rate to value collateral, mint a derivative, or settle a payout, and (c) reverse the initial payment — the entire "manipulate reserve → exploit dependent price → unwind" sequence completes inside one atomic, single-block-equivalent operation, exactly mirroring the flash-loan attack pattern used against Hundred Finance's cToken exchange-rate mechanics. Unlike EVM reentrancy guards, there is no cross-AA "price freshness" or TWAP mechanism enforced by the engine; each AA author has to defend against this independently, and the bundled reference AMM sample does not.

### Impact Explanation
Any protocol built on ocore that composes a reserve/AMM-style AA with a second AA that trusts that reserve's `balance[]`-derived price (e.g., for collateral valuation, share pricing, or settlement) is exposed to atomic, single-transaction price manipulation. This can produce unauthorized fund extraction from the dependent AA or AMM (mispriced swap execution, over-issuance of a derived asset, or draining of collateral) — a concrete AA fund-loss scenario, matching the High severity of the reference incident.

### Likelihood Explanation
No special privileges are required — any unprivileged unit poster can construct the payment/trigger chain in a single unit as long as they can afford the bounce fees and bytes to fund the temporary skew. The engine explicitly supports multi-hop AA chaining and live-balance getters as core features, so any AA author who follows the shipped reference AMM pattern (`balance[asset]` pricing without a delay/oracle) is realistically exploitable the moment a second AA composes with it.

### Recommendation
- Document and strongly discourage the pattern of pricing purely off instantaneous `balance[]` in composable AAs; provide/require a TWAP-like or multi-block-confirmed price primitive for AMM-style AAs.
- Consider adding an engine-level safeguard such as a "reentrancy" or "call-depth from foreign trigger" flag exposed to AAs so a dependent AA can detect and reject prices sourced from an AMM that was touched earlier in the same atomic trigger chain.
- Update the bundled `uniswap_like_market_maker.oscript` sample to note the flash-loan-style manipulation risk so downstream AA authors do not treat it as a safe template for composable pricing.

### Proof of Concept
1. Deploy AMM AA `M` per `uniswap_like_market_maker.oscript`, seeded with reserves of `base` and asset `$asset` [9](#0-8) .
2. Deploy victim AA `V` whose logic reads `M`'s live price via `remote_func_call`/getter or via `balance[]` after receiving a forwarded payment from `M` in the same chain, and issues/settles funds based on that price (pattern demonstrated by `test/aa_composer.test.js:1364-1519`, showing a getter chain returning `balance[base]` computed live).
3. Craft one trigger unit that (a) sends a large amount of `$asset` to `M` (skewing `$new_bytes_balance`/`$amount` per the "exchange asset to bytes" case), (b) in the same unit, sends outputs that trigger `V`, which reads `M`'s now-skewed price and mis-prices its payout, (c) triggers `M` again in reverse to restore/withdraw the skewed balance.
4. Because all of these AA invocations are handled sequentially and atomically inside `handleTrigger`/`handleSecondaryTriggers` in one transaction [5](#0-4) , the attacker profits from `V`'s mispriced payout while returning `M` to (approximately) its original reserve state, with no other unit able to intervene mid-chain.
