### Title
Crash via uncaught `throw Error` in `definition template` / `address` authentifier evaluation - ([File: definition.js])

### Summary
`definition.js`'s `validateAuthentifiers()` contains two `evaluate()` branches (`'definition template'` and `'address'`) that forcibly assume a database query returns exactly one row and `throw Error(...)` synchronously from inside an asynchronous `conn.query()` callback when that assumption is violated. This is the same bug class as the TensorFlow `ValueOrDie()` crash: a value/condition that can legitimately be in an "error"/unexpected state is force-extracted/asserted without a recoverable error path, and the resulting exception is not caught anywhere in the call chain, crashing the whole ocore process.

### Finding Description
In `definition.js`, `validateAuthentifiers()` evaluates a posted unit's spending/authentication conditions against an address definition. Two branches unconditionally `throw` instead of returning an error through the callback: [1](#0-0) 

```js

    ...

        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            ...
```

and [2](#0-1) 

```js
ifDefinitionNotFound: function(definition_chash){
    ...
    if (arrDefiningAuthors.length === 0) // no definition in the current unit
        return cb2(false);
    if (arrDefiningAuthors.length > 1)
        throw Error("more than 1 address definition");
    ...
```

The equivalent sibling logic in `validateDefinition()` (which checks the *structure* of a definition, not authentification) handles the exact same "not found or too many" condition gracefully via the callback instead of throwing: [3](#0-2) 

```js

        if (rows.length !== 1)
            return cb("template not found or too many");
```

The `evaluate()` function inside `validateAuthentifiers` is invoked from `validateAuthentifiers()` itself, which runs every time a unit is validated that spends from, or is co-authored by, an address whose definition uses `'definition template'` or a nested `'address'` reference: [4](#0-3) 

This is reachable directly from ordinary unit/author validation: [5](#0-4) 

and from private/offline message signature validation: [6](#0-5) 

Although `validateAuthentifiers()` first calls `validateDefinition()` (which runs the same `SELECT` with the same `[unit, last_ball_mci]` parameters and would normally reject a bad definition before `evaluate()` runs), the check in `validateDefinition()` and the check inside `evaluate()`/`validateAuthentifiers` are two **separate, non-atomic asynchronous database queries** issued back-to-back against a live, continuously-mutating DAG database (units are being added/stabilized by other author/witness/catchup activity concurrently). There is no guarantee that the row set for `unit=?` is identical between the two queries; a change in `is_stable`/`main_chain_index`/`sequence` state for the referenced `unit` between the two lookups (a normal, frequent event as MC advances) can make the count of matching rows differ, causing `evaluate()`'s query callback to see `rows.length !== 1` even though `validateDefinition()` saw exactly 1. When that happens, the code path takes the `throw Error("not 1 template")` (or `throw Error("more than 1 address definition")`) branch instead of returning an error via `cb`.

Because the throw occurs asynchronously inside a database driver's callback (`conn.query(..., function(rows){ throw ... })`), it is **not** caught by any surrounding `try/catch` in `validateAuthentifiers`, `validateAuthor`, or `validateMessage`. No global `process.on('uncaughtException')` handler exists in the validation code path (the only `uncaughtException` handler found in the codebase is in `network.js` and is unrelated to validation logic), so this exception propagates to the top of the event loop and terminates the Node.js process.

### Impact Explanation
An uncaught exception thrown from deep inside asynchronous unit-validation logic crashes the entire ocore node process. Because unit validation of every incoming unit that uses an address definition with a `'definition template'` operator or a nested `'address'` reference must pass through this exact code, any full/light node that is validating such a unit at the moment the underlying rows for the referenced unit change state can crash. This is a network-wide availability issue: a validator/witness/hub node repeatedly crashing on such units cannot confirm new units, matching the "network unable to confirm new units" impact category. It does not directly cause fund loss but is a concrete denial-of-service against consensus-critical validation code, reachable from an ordinary posted unit (no special network/peer privilege required — any account can create an address whose definition contains `'definition template'` or a nested `'address'` reference, which is a completely standard, unprivileged spending-condition feature).

### Likelihood Explanation
The trigger condition (the referenced `unit`'s row set for `app='definition_template'`/matching author definition changing between two back-to-back async DB reads) is a timing-dependent race rather than a deterministically attacker-forced crash. It requires that a node's local DB state for the referenced unit changes (e.g., stabilization state flips) precisely between the `validateDefinition()` call and the `evaluate()` call inside `validateAuthentifiers()`. On a live network processing continuous units, this race window is real but narrow, so likelihood is not "trivial-on-demand" but is realistically triggerable, especially by carefully timing when the referenced `unit` transitions to/away from `is_stable=1`/`sequence='good'` relative to the last-ball advertised by the unit under validation.

### Recommendation
Replace both `throw Error(...)` calls inside the async query callbacks of `evaluate()` in `validateAuthentifiers()` (`definition.js`, lines ~811-812 for `'definition template'`, and line ~795 for `'address'`) with a graceful error return through the existing callback mechanism (e.g., `fatal_error = "..."; return cb2(false);`), mirroring the pattern already used in the sibling `validateDefinition()` function. This removes the unhandled-exception crash path while preserving the intended "authentication fails" semantics.

### Proof of Concept
1. Create address `A` whose definition contains `['definition template', [<hash_of_unit_U>, {params...}]]`, where `unit_U` currently carries exactly one stable, good-sequence `definition_template` message (satisfying `validateDefinition()`'s check at unit-definition time).
2. Post a unit `V` spending from/authored by address `A`, timed so that between the moment `validateAuthentifiers()`'s internal `validateDefinition()` query executes and the moment its `evaluate()` query executes for the same `unit_U`, the underlying row visibility for `unit_U` changes (e.g., `unit_U`'s `is_stable`/`sequence` flips due to concurrent stabilization activity, or a conflicting/duplicate `definition_template` entry for the same unit hash becomes visible/invisible).
3. When `rows.length !== 1` is observed in the second (`evaluate()`) query callback, `throw Error("not 1 template")` executes inside the DB driver's async callback, is not caught anywhere up the call stack, and crashes the ocore node process — reproducible by tracing the code path at [7](#0-6)  versus the properly-guarded equivalent at [3](#0-2) .
