### Title
`InitializeBuffer` writes buffer authority binding without any signer check, allowing permissionless authority hijack - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
`UpgradeableLoaderInstruction::InitializeBuffer` writes the `authority_address` field of a program buffer account from an attacker-supplied instruction account with no requirement that either the buffer account or the named authority account be a signer. Anyone who submits an unprivileged transaction naming an existing-but-`Uninitialized` buffer account can call `InitializeBuffer` first and bind themselves (or any address) as that buffer's authority, exactly mirroring the reported `RootValidator::onInstall` pattern: a security-critical binding is written trusting caller-supplied data with no self-binding/signer verification, guarded only by a "not yet initialized" check.

### Finding Description
`process_loader_upgradeable_instruction` handles `InitializeBuffer` as follows: [1](#0-0) 

The handler:
1. Checks only that the buffer account's current state is `Uninitialized` (analogous to a missing `AlreadyInitialized` guard being *present* but nothing else).
2. Reads `authority_key` directly from whichever pubkey is placed at instruction-account index 1 — with **no check that this account is a signer**.
3. Writes `authority_address: authority_key` into the buffer's own state — with **no check that the buffer account (index 0) is a signer either**.

This is structurally identical to the reported `RootValidator::onInstall` bug: a caller-controlled address is written into a security-relevant binding field (`authority_address`, which gates all future `Write`, `SetAuthority`, and `DeployWithMaxDataLen` calls on this buffer) without verifying that the writer is authorized to make that claim. Compare with the sibling instructions in the same file, which *do* correctly enforce signer/ownership checks before mutating authority state, e.g. `Write`: [2](#0-1) 

and `SetAuthority`: [3](#0-2) 

Both of those require the current authority to sign before any authority-state mutation. `InitializeBuffer`, however, has no such requirement at all — it only checks that the account was previously `Uninitialized`.

Downstream, the authority set here is trusted for the rest of the buffer's lifecycle, including the deploy path: [4](#0-3) 

`DeployWithMaxDataLen` checks that the buffer's `authority_address` matches the authority account passed in and requires that account to sign — but it fully trusts whatever `authority_address` was set during `InitializeBuffer`. If an attacker races the initialization of the buffer, they become the trusted authority for that buffer and gain sole control over `Write`/`SetAuthority`/`Deploy` on it.

### Impact Explanation
Any buffer account that is created (funded, owned by `bpf_loader_upgradeable`, in `Uninitialized` state) but not yet initialized in the *same* atomic transaction is vulnerable to a race: an attacker submits their own `InitializeBuffer` instruction naming that buffer account and themselves as authority. Because there is no signer check on the buffer account or the authority account in this instruction, the attacker's transaction succeeds and permanently binds them as the authority for that buffer (the legitimate owner's own `InitializeBuffer` call then fails with `AccountAlreadyInitialized`). The attacker can subsequently populate the buffer with arbitrary ELF bytes via `Write` (which does check the authority they just set) and drive `DeployWithMaxDataLen`/`Upgrade`, effectively hijacking control of the deploy pipeline for that buffer/program account and potentially causing malicious code to be attributed to the victim's intended program address, or denying the victim service on that buffer. This is a permissionless privilege-hijack of a security binding reachable from a single unprivileged transaction, matching the class of bug described in the external report.

### Likelihood Explanation
Exploitability is bounded by whether `CreateAccount` (funding the buffer / setting its owner) and `InitializeBuffer` are submitted in the same atomic transaction. Tooling such as `solana program deploy` typically bundles them together, closing the race window in that common path. However, nothing in the protocol enforces this atomicity — any workflow, custom tooling, or multi-step buffer setup that creates the buffer account and calls `InitializeBuffer` in separate transactions is exposed to front-running by any unprivileged network participant who observes the pending/confirmed `CreateAccount` and submits a competing `InitializeBuffer` first. Given the on-chain visibility of pending buffer accounts, likelihood is non-trivial but conditional on this less-common two-step deployment pattern.

### Recommendation
Add a self-binding/signer check to `InitializeBuffer`, mirroring the mitigation recommended for `RootValidator::onInstall`:
- Require the buffer account (or its de-facto owner/creator) to be a signer of the `InitializeBuffer` instruction, or
- Require the named authority account to sign, proving consent to be bound as authority, and/or
- Perform `InitializeBuffer` and `CreateAccount` for the buffer atomically as a single enforced sequence (e.g., via a combined instruction or a runtime-level guarantee) so no window exists for a third party to observe and race the initialization.

### Proof of Concept
Conceptual Solana transaction sequence (analogous to the Solidity PoC's hijack timing):
1. Victim submits `CreateAccount` (funded by victim, owner = `bpf_loader_upgradeable`, size = `UpgradeableLoaderState::size_of_buffer(N)`) for buffer account `B`, in a transaction separate from `InitializeBuffer` — `B` is now `Uninitialized`, owned by `bpf_loader_upgradeable`, but observable on-chain/in the mempool before the follow-up transaction lands.
2. Attacker observes `B`'s existence in the `Uninitialized` state and submits their own transaction: `InitializeBuffer` with account 0 = `B`, account 1 = `attacker_pubkey`, no signer requirement on either.
3. Per [1](#0-0) , this succeeds unconditionally (state was `Uninitialized`), setting `B.authority_address = Some(attacker_pubkey)`.
4. Victim's own `InitializeBuffer` transaction now fails with `AccountAlreadyInitialized`.
5. Attacker calls `Write` on `B` with themselves as the (now legitimate) authority, loading arbitrary program bytes, and can drive `DeployWithMaxDataLen`, hijacking the deploy for that buffer.

This mirrors the "no length check / no self-binding / no signer verification, guarded only by an initialization check" pattern of the reported `RootValidator::onInstall` vulnerability, applied to Agave's `bpf_loader_upgradeable::InitializeBuffer` instruction. Note: I was not able to fully trace every caller of `InitializeBuffer` across the CLI/tooling layer to confirm whether *all* current tooling paths bundle `CreateAccount` and `InitializeBuffer` atomically; if any supported workflow issues them as separate transactions, the race window described above is directly exploitable.
