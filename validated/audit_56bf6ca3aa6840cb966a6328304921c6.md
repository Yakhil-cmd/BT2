## Title
Webhook signature verification is scoped to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field — allowing cross-repository forged webhook data - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's HMAC secret to verify the incoming payload against using `repository_owner`, which is read straight out of the JSON body (`params.dig('repository', 'owner', 'login')`). Every webhook `Handler`, however, resolves the target `Repository`/`Stack` to write to using a *different* field of the same body: `params.dig('repository', 'full_name')`. Because both fields live in the same attacker-controlled JSON payload and nothing binds them together, a party who legitimately controls the webhook secret for one onboarded organization can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` names a completely different, victim repository already tracked by this Shipit instance.

## Finding Description
- `WebhooksController#verify_signature` selects the app config purely from `repository_owner`: [1](#0-0) [2](#0-1) 
  ```ruby
  def verify_signature
    github_app = Shipit.github(organization: repository_owner)
    verified = github_app.verify_webhook_signature(...)
    ...
  end
  def repository_owner
    params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
  end
  ```
- `verify_webhook_signature` just HMAC-validates the raw body against the secret configured for that one organization: [3](#0-2) 
- Every handler, however, looks up the repository to act on via `repository.full_name`, a sibling field of `repository.owner.login` inside the very same payload, with no re-check against `repository_owner`: [4](#0-3) 
  ```ruby
  def stacks
    @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
  end
  def repository_name
    payload.dig('repository', 'full_name')
  end
  ```
- `StatusHandler`, for example, blindly matches any `Commit` in the whole database by `sha` and writes a forged CI status onto it, with no scoping to the org that was actually authenticated: [5](#0-4) 
- The pull-request family of handlers (`OpenedHandler`, `ClosedHandler`, `LabelCapturingHandler`, `UnlabeledHandler`, `ReviewStackAdapter`, etc.) resolve their target repository the same way, via `params.repository.full_name`, and then create/archive/unarchive `ReviewStack`s and store attacker-supplied `github_pull_request` JSON (including `head.sha`/`head.ref`, labels, assignees) verbatim: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization used to verify the HMAC signature == organization that owns the repository being mutated`. Before any pull request, this binding was implicitly assumed but never enforced — `repository_owner` (verification key) and `repository.full_name` (mutation target) are independent, attacker-controlled fields of the same JSON body, so an attacker who owns/administers one org already onboarded onto this Shipit instance (and thus knows/derives that org's webhook secret, e.g. because they set it or can trigger the GitHub App to sign payloads for their own org) can produce a validly-signed payload while pointing `full_name` at any other org/repo tracked by the same Shipit instance.

## Impact Explanation
This breaks the "organization that authenticated" vs. "repository that is written" binding named in scope. Concretely, an attacker who controls one legitimate, low-privilege org/repo already registered with the Shipit instance can:
- Forge `status`/`commit_status` events that plant fabricated, passing CI statuses on arbitrary commits (matched purely by SHA, globally, via `Commit.where(sha: params.sha)`) belonging to a victim's stack, which feeds directly into `Commit#deployable?`/CI-gating logic used to allow continuous deployment (`Stack#continuous_delivery_delayed?`, deploy gating) — this is an unauthorized-deploy primitive (Critical impact per the rules: "an unauthorized deploy").
- Forge `pull_request` events for a victim's repository/review-stack: create, archive, or unarchive `ReviewStack`s, and store attacker-chosen `head.sha`/`head.ref`/labels into `PullRequest`/`ReviewStack` records that later drive real deploy machinery for that repository.
- Forge `push` events to trigger `GithubSyncJob` for a victim's stack with an attacker-chosen `expected_head_sha`.

All of this is achievable without any Shipit session, `ApiClient` token, or repository write access on GitHub — only knowledge of the webhook secret belonging to any single organization already onboarded to the instance, which is the class of "unprivileged early user" attacker the report describes (control over one small, low-value tenant used to corrupt state affecting other, higher-value tenants).

## Likelihood Explanation
Requires the attacker to have legitimate access to at least one organization's webhook secret already configured in `Shipit.github_apps`/config (i.e., they are an onboarded org admin on this multi-tenant Shipit instance, not an arbitrary internet attacker). This is a realistic scenario for shared/multi-tenant Shipit deployments where many orgs are provisioned by self-service, matching the "malicious early user" framing of the original finding (an attacker with minimal but real footprint abusing a design gap to affect unrelated future/other users).

## Recommendation
Bind the two identities together: after `verify_webhook_signature` succeeds for `repository_owner`, every handler must re-validate that `payload.dig('repository', 'full_name')` (and any other repository references inside nested objects, e.g. `pull_request.base.repo.full_name`) belongs to that same verified organization before performing any lookup or mutation — e.g., assert `repository_name.split('/').first.casecmp(repository_owner).zero?` in `Handler#stacks`/`Handler#repository_name`, and reject/head(422) otherwise.

## Proof of Concept
1. Attacker registers/administers Organization `A`, which is legitimately onboarded to the shared Shipit instance and has its own GitHub App webhook secret `S_A` known to the attacker.
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha belonging to org B's stack>",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` and POSTs it to `/github/webhooks`.
4. `WebhooksController#verify_signature` computes `repository_owner == "A"`, fetches `Shipit.github(organization: "A")`, and the signature verifies successfully (attacker knows `S_A`).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — writing a forged, passing CI status onto org `B`'s commit with no check that `full_name` starts with `"A/"`.
6. This forged status can flip `commit.deployable?` for the victim stack, potentially unblocking a queued or continuous deploy on org `B`'s stack. This part of the impact chain — how far a forged status alone propagates into an actual triggered `Deploy` under default configuration — could not be fully traced further within the indexed context and would benefit from execution in a live/staging Shipit instance to confirm the end-to-end deploy trigger.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
