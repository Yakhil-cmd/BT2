### Title
CCMenu-minted API token authorizes `read:stack` for every stack, not just the stack it was issued for - ([File: app/controllers/shipit/ccmenu_url_controller.rb] / [File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#client` creates/reuses an `ApiClient` scoped only by `creator` and `name`, never setting `stack_id`, so the minted token is a global `read:stack` credential. Independently, `Api::CCMenuController#show` overrides the base `stack` accessor to call `Stack.from_param!` directly instead of the tenant-scoping `stacks.from_param!`, so even a stack-scoped token would still leak other stacks' build state through this endpoint.

### Finding Description
The claimed binding is: `current_api_client.stack_id == stack_being_queried.id` must hold for the CCMenu token to be stack-scoped. In `CCMenuUrlController#client` (app/controllers/shipit/ccmenu_url_controller.rb:15-18), the `ApiClient` is looked up/created via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `permissions: %w[read:stack]` in `create_with` — `stack:` is never passed, so `stack_id` is `nil` for this client and is not enforced when the user requests a URL for stack A. This means for a given user, every stack's CCMenu URL request reuses (or creates) the *same* global client record (unique by `creator`+`name`), with `stack_id` staying `nil`.

On the consuming side, `Api::BaseController#stacks` (app/controllers/shipit/api/base_controller.rb:74-76) is the mechanism intended to enforce `stack_id` scoping (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), but `Api::CCMenuController` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) overrides `stack` to bypass it entirely: `Stack.from_param!(params[:stack_id])` operates on the full `Stack` relation, not the scoped `stacks` relation. `require_permission :read, :stack` only calls `check_permissions!(operation, scope)` (app/models/shipit/api_client.rb:38-45), which checks the literal string `"read:stack"` against the `permissions` array — it never inspects `stack_id` or compares it to the requested stack.

Attack: an unprivileged but authenticated Shipit user (any GitHub user with a Shipit session for org repo-a/stack A) visits `GET /stacks/:id/ccmenu_url` for stack A, receiving a `token` in the CCMenu URL. That same `token` can then be used as `?token=` against `GET /api/stacks/:other_stack_id/ccmenu.xml` for any other stack B in the installation (a different org/repo), and `Api::CCMenuController#show` renders stack B's `lastBuildStatus`, `activity`, `webUrl`, etc. No existing guard (`require_permission`, `authenticate_api_client`, `stacks`) stops this because (a) the client's permission set is scope-generic (`read:stack`), not stack A-specific, and (b) the controller's own `stack` method bypasses the one place (`stacks`) that would have enforced `stack_id` even if it had been set correctly.

### Impact Explanation
An unprivileged, authenticated user of one tenant/repo can read build/deploy status (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`) of every other stack in the Shipit installation, across unrelated orgs/repos, using a token minted for their own stack. This is a cross-tenant unauthorized read of stack state, matching the "High" impact category (unauthenticated/unauthorized read of stack state). It is fully repeatable: the same token works against arbitrarily many stack IDs, and a new "CCMenu Client" token can trivially be re-minted per user.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs an ordinary Shipit session (already granted to any GitHub user with access to at least one stack/repo covered by the install, per the CCMenu feature's normal use) and knowledge/guessability of another stack's `to_param`/id (stack slugs are often derivable from org/repo/environment names visible in the UI). No secrets, admin role, or GitHub team membership is required. Cost is a single GET request to mint the token followed by one GET per target stack.

### Recommendation
- In `CCMenuUrlController#client`, include `stack: stack` in both the `find_or_create_by!` lookup keys and `create_with` attributes, so each stack gets its own `ApiClient` with `stack_id` set (e.g., `find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack: stack)`).
- Fix `Api::CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` (i.e., remove the override or delegate to `super`) so that `stack_id`-scoped clients are actually enforced.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a CCMenu token minted for stack A must not authorize reading stack B" do
  stack_a = Stack.create!(repository: Repository.create!(owner: 'org-a', name: 'repo-a'), branch: 'main')
  stack_b = Stack.create!(repository: Repository.create!(owner: 'org-b', name: 'repo-b'), branch: 'main')

  user = shipit_users(:walrus)
  session[:user_id] = user.id

  get :fetch, params: { stack_id: stack_a.to_param } # CCMenuUrlController#fetch
  token = ApiClient.last.authentication_token

  assert_equal stack_a.id, ApiClient.last.stack_id, "token should be bound to stack A"
  # currently fails: ApiClient.last.stack_id is nil

  get :show, params: { stack_id: stack_b.to_param, token: token } # Api::CCMenuController#show
  assert_response :forbidden # or :not_found
  # currently: assert_response :ok — leaking stack B's build status
end
```
Both assertions (`stack_id` binding, and cross-stack access rejection) fail against current code, confirming the vulnerability.
