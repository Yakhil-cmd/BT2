Cross-repository status corruption via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes GitHub `status` events to every `Commit` row matching a bare SHA, without restricting to the repository/stack that authenticated the webhook. Since the `commits` table's uniqueness constraint is `(sha, stack_id)` rather than `sha` alone, two different stacks (repositories/tenants) can legitimately hold rows with the identical SHA, and a webhook correctly signed for one organization/repo will be applied to the other stack's commit as well.

### Finding Description
The broken binding: the code implicitly assumes `Commit.where(sha: params.sha)` == "the commit belonging to the repository that emitted this webhook", but the actual invariant enforced by the schema is only `sha` unique **per** `stack_id` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`: `add_index :commits, %i(sha stack_id), unique: true`). These two are not equal whenever a victim stack and an attacker-controlled stack (e.g., a fork or a repo with byte-identical history/commit) share a commit SHA.

Path:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw payload and dispatches to `Shipit::Webhooks.for_event(event)` handlers.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the payload is HMAC-signed by the secret configured for `repository_owner` (the organization named in the payload's own `repository.owner.login`/`organization.login`). It does not verify that the SHA in the payload belongs to that specific repository — it can't, because the check happens before any commit is looked up, and it trusts whatever `repository_owner` the attacker's own payload declares.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by bare `sha`, with no `stack_id`/`repository` filter, then calls `commit.create_status_from_github!` for **every** matching row across all stacks.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) creates a `Status` scoped to `commit.stack_id`, which can flip `deployable?`/`blocked?` (`app/models/shipit/commit.rb:227-237`) and trigger `schedule_continuous_delivery` / `deployable_status` hooks (`app/models/shipit/commit.rb:281-287`, `366-386`).

Exploit flow: An attacker who legitimately owns and operates a repository already connected to Shipit (their own `GithubHook`/organization, with their own webhook secret) forks or otherwise reproduces a commit with the exact same SHA as one in a victim's stack (trivial for public/open-source victims, since git SHAs are content-addressed and can be reproduced by cloning/re-pushing the same commit). The attacker then triggers (or directly POSTs, since `X-Hub-Signature` is computed with their own known secret) a `status` webhook for that SHA with `context: ci/test`, `state: failure`. `verify_signature` passes because the signature matches the attacker's own organization's configured secret. `StatusHandler#process` then finds the commit row in **both** the attacker's stack and the victim's stack (identical SHA), and writes a `failure` status onto the victim's commit — flipping `deployable?`, potentially blocking a pending deploy or breaking `ci/test`-required merges on a stack the attacker never authenticated against.

None of the existing guards prevent this: `verify_signature` validates only the organization tied to the payload the attacker fully controls; `drop_unhandled_event` only checks the event type is registered; there is no `ExplicitParameters` check on `sha`/repository binding; and the DB schema explicitly permits duplicate SHAs across different `stack_id`s.

### Impact Explanation
An attacker with a legitimately-registered (attacker-owned) Shipit-tracked repository can write `Status` records into a victim's stack's commit state without ever authenticating for that stack, by exploiting a shared commit SHA. This can flip `Commit#deployable?`/`#blocked?`, force `Hook.emit(:deployable_status, ...)`, and trigger/prevent continuous-delivery scheduling (`Commit#schedule_continuous_delivery`) for a repository that never issued the webhook — a payload for one repository mutating another's stack/commit state. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any victim stack whose commit history shares a SHA with an attacker-controlled repo. [1](#0-0) [2](#0-1) [3](#0-2) 

### Likelihood Explanation
Requires: (1) the attacker to own/operate at least one repository already onboarded into the target Shipit instance (a `GithubHook`/organization config with its own webhook secret) — this is a normal, low-privilege onboarding step, not a Shipit-secret compromise; (2) a commit SHA collision with the victim's stack, achievable deterministically for public repos by forking/replaying identical commit content (git SHA is a hash of content+metadata, fully reproducible by anyone with the source). No GitHub App private key, `api_clients_secret`, or session is needed. This is fully within the declared "unprivileged attacker" capability (owns a repo, can send webhooks from it). It's repeatable per victim stack that shares any commit SHA.

### Recommendation
Scope the lookup in `StatusHandler#process` to the repository that authenticated the webhook, e.g. resolve the `Stack`/`Repository` from the verified `repository_owner`/`repository.full_name` in the payload and filter `Commit.where(sha: params.sha, stack_id: matching_stack_ids)`, mirroring how the `push` handler binds commits to `GithubSyncJob` with an explicit `stack_id`. Alternatively/also, tighten the `commits` uniqueness constraint or add an application-level check ensuring `commit.stack.repository` matches the webhook's `repository.full_name` before applying `create_status_from_github!`.

### Proof of Concept
Minitest plan (no live GitHub required):
```ruby
test "status webhook does not affect commits with the same sha on a different stack" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # distinct GithubHook/org & secret

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit')

  request.headers['X-Github-Event'] = 'status'
  # signed with attacker_stack's own repository_owner/secret
  body = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/test',
    'repository' => { 'full_name' => attacker_stack.repository.full_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # or stub verify_webhook_signature for attacker org

  assert_no_difference -> { victim_commit.statuses.count }, "victim commit must not receive a status from attacker's webhook" do
    post :create, body:, as: :json
  end

  # demonstrates the actual (vulnerable) behavior: without a fix, the above assertion fails
  # because Commit.where(sha: shared_sha) matches both victim_commit and attacker_commit,
  # and StatusHandler#process writes a status onto both.
end
```
Both sides of the equality to assert: `victim_commit.statuses.count` before == after (expected invariant), versus the actual observed `victim_commit.statuses.count` increasing by 1 due to `StatusHandler#process`'s unscoped `Commit.where(sha:)` query. [1](#0-0)
