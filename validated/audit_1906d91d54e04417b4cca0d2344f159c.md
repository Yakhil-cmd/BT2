## Title
Webhook signature verification uses an attacker-controlled organization field that is decoupled from the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository_owner` straight out of the untrusted, attacker-supplied JSON body, but the event handlers that subsequently act on the same payload use a *different* field (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. Because these two lookups are never checked for consistency, a request that is validly signed for one configured organization can carry a `repository.full_name` pointing at a stack belonging to a completely different, unrelated organization also configured on the same Shipit instance.

## Finding Description
`WebhooksController` first computes `repository_owner` from the JSON body and uses it to pick the `GitHubApp` (and therefore the `webhook_secret`) used to verify `X-Hub-Signature`: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is derived entirely from body content: [2](#0-1) 

Once the signature is confirmed valid *for that organization's secret*, the entire raw payload — including the `repository.full_name` field — is forwarded unmodified to the registered handlers: [3](#0-2) 

Handlers (e.g. `PushHandler`) resolve the target `Stack` using `repository.full_name`, a *different* field of the same payload, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) 

Shipit explicitly supports hosting multiple, independently-configured GitHub organizations in one instance, each with its own `webhook_secret`: [6](#0-5) [7](#0-6) 

Because the signature-selection key (`repository.owner.login`) and the state-mutation key (`repository.full_name`) are two independent, attacker-writable JSON fields inside the same signed body, an attacker who legitimately possesses the `webhook_secret` for *their own* organization (Org A, e.g. because they administer that org's GitHub App integration on the shared Shipit instance) can craft a POST body whose HMAC is valid for Org A but whose `repository.full_name` names a stack belonging to Org B. This breaks the binding: `organization that authenticated == repository that is written`.

## Impact Explanation
A forged, validly-signed-for-Org-A webhook can carry `repository.full_name` for a stack owned by Org B. Depending on the event type dispatched to `Shipit::Webhooks.for_event`, this can:
- Trigger `PushHandler#process` → `stack.sync_github(expected_head_sha: ...)` on Org B's stack, forcing a GitHub sync of a target stack the attacker does not control.
- Affect `status`, `check_suite`, `pull_request`, `membership` and other handlers that similarly resolve state via `repository.full_name`/`organization.login` independent of the org used for signature verification, letting an Org-A-scoped attacker manipulate commit statuses, labels, review-stack provisioning, or team/membership records that belong to Org B.

If continuous deployment is enabled on the targeted stack, a forced sync of new commit state can feed into automatic deploy triggering, resulting in an unauthorized deploy on a repository the attacker was never granted access to — a cross-organization write performed with credentials scoped to a different, unrelated organization. This satisfies the "cross-repository writes / unauthorized deploy" Critical-impact bar in a multi-org Shipit deployment.

## Likelihood Explanation
Exploitability requires:
1. The Shipit instance to be configured with multiple GitHub organizations (a documented, supported configuration), each with its own `webhook_secret`.
2. The attacker to control (or have legitimately been given) the `webhook_secret` for at least one configured organization (e.g., they are the admin who registered their own org's GitHub App on the shared instance) — no privileged Shipit account, session, or API token is required, only a webhook secret belonging to a different, unrelated org.

Given that likelihood, no other authentication step exists to prevent the org/repo mismatch: `verify_signature` and the handler processing both trust unrelated fields of the same attacker-supplied JSON independently.

## Recommendation
- After signature verification, re-derive the acting organization strictly from the same field/value pair validated by the signature and reject the request if `repository.full_name`'s owner segment (or `organization.login` for org-scoped events) does not match `repository_owner` used to select the `webhook_secret`.
- Alternatively, verify the signature using a canonicalized subset of the payload that is guaranteed to match the org actually mutated, or bind each configured organization's webhook endpoint to a distinct URL/path so a secret for Org A can never be used to authenticate a payload targeting Org B.

## Proof of Concept
1. Configure a Shipit instance with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret` values (as documented in `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`).
2. As the attacker who knows `OrgA`'s `webhook_secret` (e.g., the party who configured `OrgA`'s GitHub App), craft a JSON body for the `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Sign the raw body with `OrgA`'s `webhook_secret` using HMAC-SHA1 and set it as `X-Hub-Signature`.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` from `repository.owner.login`, verifies successfully against `OrgA`'s secret, and the request proceeds.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, calling `stack.sync_github(expected_head_sha: ...)` on a stack that belongs to `OrgB`, despite the request only being authenticated for `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
