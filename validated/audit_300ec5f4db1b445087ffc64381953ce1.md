### Title
Webhook signature verification keys off `repository.owner.login` while handlers act on the independent `repository.full_name` field, allowing an unsigned/wrongly-signed payload to be attributed to any repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using `repository_owner`, a value read straight out of the untrusted, attacker-suppliable JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The event handlers, however, resolve the repository/stack to actually mutate using a *different* field from the same body: `payload.dig('repository', 'full_name')`. These two fields are never cross-checked, so the "organization whose secret authenticated the request" and "the repository that is written to" are not the same binding. [1](#0-0) [2](#0-1) 

### Finding Description
`verify_signature` does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` comes from the body itself, not from any authenticated source. `GitHubApp#verify_webhook_signature` contains an intentional bypass for organizations that are configured without a `webhook_secret`:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Shipit explicitly supports (and documents) multi-organization configuration where each org has its own, independently-set `webhook_secret`, including the documented possibility of leaving it blank/`nil` for a given org: [4](#0-3) [5](#0-4) 

Meanwhile, every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the repository/stack to operate on via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, a field that is completely independent of `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

The equality that should hold but does not:
`organization whose signature is verified (repository.owner.login)` == `organization whose repository/stack is mutated (repository.full_name's owner)`

An attacker who knows (or guesses) that any one configured GitHub organization on the instance has no `webhook_secret` set (a state the docs and shipped example configs explicitly allow/demonstrate) can craft a raw POST to `/webhooks` where:
- `repository.owner.login` / `organization.login` = the org with no secret (so `verify_webhook_signature` returns `true` unconditionally, regardless of the `X-Hub-Signature` header sent),
- `repository.full_name` = `"<target-org>/<target-repo>"`, a real repository/stack tracked by Shipit under a *different*, fully-secured organization.

Because `verify_signature` never checks that the two fields agree, and because the handlers use `repository.full_name` exclusively, the forged, unsigned payload is processed as if it legitimately originated from GitHub for the target repository.

### Impact Explanation
This breaks the deployment-trust binding described by the rules ("an organization that authenticated versus the repository that is written"). Concretely reachable, unauthenticated (no Shipit session, no API token, no GitHub credentials for the target org needed) impacts:
- `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for any stack under the target repo/branch, letting an attacker trigger GitHub syncs and, combined with continuous-deployment configuration, an unauthorized deploy pipeline trigger. [9](#0-8) 
- `StatusHandler` lets the attacker forge arbitrary CI `state`/`context`/`description` for any commit sha already known to Shipit, which can be used to spoof required CI statuses that gate continuous deployment. [10](#0-9) 
- Pull-request handlers resolve their target the same way (`params.repository.full_name`), so review-stack provisioning/archiving and PR label-driven behavior can similarly be forged for a target org's repositories.

Combined with continuous deployment, this can lead to an unauthorized/forced deploy, which meets the "Critical - unauthorized deploy" bar defined in scope.

### Likelihood Explanation
Exploitability depends entirely on the operator's multi-org configuration having at least one organization with `webhook_secret` unset/blank — a state that is explicitly documented and shown in shipped example secrets files (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`'s `OrgTwo`), so it is a realistic, foreseeable operational configuration, not a purely theoretical one. No credentials, GitHub App keys, Shipit session, or repository write access are required — only knowledge (or a guess, e.g. via a low-value test org name) of which configured org lacks a secret. I could not fully verify at what frequency real-world Shipit deployments actually leave a secret blank for one org among several, since that is an operational/deployment detail outside the indexed engine code; this introduces some uncertainty into the exact likelihood, though the vulnerable code path itself is concretely confirmed.

### Recommendation
Do not let payload-derived `repository.owner.login`/`organization.login` alone determine which secret validates the signature and then let a *different* payload field (`repository.full_name`) determine what gets mutated. At minimum:
1. Require signature verification to succeed with a real HMAC match; disallow the "no secret configured ⇒ auto-verified" bypass path (`return true unless webhook_secret`) for multi-org configurations, or require every configured organization to have a non-blank `webhook_secret`.
2. After verification, assert that the resolved `repository_owner` used to pick the app/secret matches the owner encoded in `repository.full_name` before dispatching to handlers.

### Proof of Concept
Given a `secrets.yml` configured with two orgs, e.g.:
```yaml
production:
  github:
    trusted-org:
      webhook_secret: real-secret
      ...
    empty-secret-org:
      webhook_secret: # nil
      ...
```
1. Attacker sends (no valid GitHub signature, since they don't know `real-secret`):
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef...
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-already-known-to-shipit>",
  "repository": {
    "owner": { "login": "empty-secret-org" },
    "full_name": "trusted-org/production-app"
  }
}
```
2. `WebhooksController#verify_signature` computes `repository_owner == "empty-secret-org"`, loads that org's `GitHubApp` (no secret), and `verify_webhook_signature` returns `true` unconditionally — the bogus `X-Hub-Signature` is never actually checked. [11](#0-10) [3](#0-2) 
3. `PushHandler` resolves the stack via `Repository.from_github_repo_name("trusted-org/production-app")` (from `repository.full_name`, unrelated to the org used for verification) and calls `stack.sync_github(expected_head_sha: ...)` for that stack. [6](#0-5) [9](#0-8) 

I was unable to fully trace whether `sync_github`/continuous-deployment always results in an immediate deploy without further gating (that logic sits outside what I inspected in this pass), so the exact end-to-end path from forged webhook to an actual unauthorized deploy execution should be validated further, though the signature-bypass/cross-repository-write primitive itself is concretely demonstrated above.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
