### Title
Per-recipient rounding in headers commission distribution causes byte-supply drift when a winning unit has multiple `earned_headers_commission_recipients` - (File: headers_commission.js)

### Summary
This is a valid analog of the Bold "share/debt rounding" bug class: proportional shares that are validated to sum to exactly 100% at the unit level are independently rounded per-recipient when the underlying value is actually distributed, so the sum of the distributed amounts can diverge from the total amount that should be conserved. In `ocore`, headers commission (`headers_commission`) owed by a parent unit is split among the `earned_headers_commission_recipients` of the winning child unit using `Math.round(full_amount * share / 100.0)` computed independently for each address, exactly analogous to Bold's `batchDebtSharesDelta = currentBatchDebtShares * debtIncrease / _batchDebt` truncation.

### Finding Description
`earned_headers_commission_recipients` shares are validated only to be positive integers summing to exactly 100 in `validateHeadersCommissionRecipients`: [1](#0-0) 

However, when the actual byte-denominated headers commission (`full_amount`) is split among recipients, each recipient's `amount` is computed independently via `Math.round(full_amount * share / 100.0)` (or the SQL equivalent `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)`), with no reconciliation against `full_amount`: [2](#0-1) [3](#0-2) [4](#0-3) 

Because rounding is applied per-recipient rather than distributing a remainder, `sum(round(full_amount * share_i / 100))` is not guaranteed to equal `full_amount` when there are 2+ recipients with fractional shares (e.g. shares of 33/33/34 on an odd `full_amount`, or any combination producing non-integer per-recipient amounts). This is the same truncation pattern as Bold's `_updateBatchShares`/`_getLatestTroveDataFromBatch`, where per-entity rounding against a shared total silently creates or destroys value at the margins.

These per-unit contributions are later aggregated without any total-conservation check into `headers_commission_outputs`: [5](#0-4) 

and are ultimately spendable as real byte value via `type: "headers_commission"` inputs: [6](#0-5) [7](#0-6) 

An `earned_headers_commission_recipients` list is entirely attacker/unit-author controlled — any multi-authored unit (or a unit designating a different recipient) can set arbitrary share splits (subject only to summing to 100 and being sorted/positive), and this is reachable by any unprivileged unit poster who authors a unit with multiple authors or who names `earned_headers_commission_recipients` explicitly, as set up in `composer.js`: [8](#0-7) 

By choosing share splits (e.g. many small fractional-percent shares, or shares that individually round up on non-exact divisions) across many recipient addresses (which can all be controlled by the same attacker), an attacker can systematically bias `sum(round(...))` above `full_amount` on units they author, repeatedly, to mint extra bytes into `headers_commission_outputs` beyond what the payer units actually paid — this constitutes a supply-inflation primitive, the exact impact class flagged in the referenced report ("small increases ... result in no minting" / "forgiven debt ... rebase shares" → here, "rounding surplus is repeatedly harvested to inflate spendable outputs").

### Impact Explanation
If the rounding bias can be made consistently positive (by choosing recipient counts/shares such that `Math.round` rounds up more often than down across many split entries), an attacker who repeatedly wins headers commissions (by posting units and having their own units chosen as winning children — a probabilistic but attacker-influenceable event since winner selection is via SHA1 hash tie-break among sequence='good' children) and always uses a favorable multi-recipient split could extract systematically more bytes from `headers_commission_outputs` than were ever paid in as `headers_commission` by parent units. This is unauthorized value creation (supply inflation) in the base-currency accounting layer, which is a Medium/High severity issue under the "supply inflation" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: the rounding bias per split is at most ~0.5 units per recipient and requires the attacker to control (or influence) both which unit wins headers commission and the recipient/share list of that unit; net exploitable drift accumulates slowly (bounded by number of recipients and units authored), similar to how the Bold report notes the impact "worsen[s] over time" as operations accrue. It's a real, silent accounting divergence baked into every multi-recipient headers-commission split, not a hypothetical.

### Recommendation
Do not round each recipient's share independently. Instead:
- Compute all recipients' shares, round all but the last, and assign the last recipient `full_amount - sum(previous rounded amounts)` (remainder-based / "largest remainder" allocation) so the total distributed always exactly equals `full_amount`.
- Alternatively, add a post-distribution assertion (as suggested in the referenced report) in `calcHeadersCommissions` that `sum(amount for all recipients of a given payer_unit) === full_amount`, and throw/fail-safe if it does not match, for both the SQL (mysql) and in-memory (sqlite) code paths in `headers_commission.js`.

### Proof of Concept
Conceptual PoC (mirrors the Bold POC structure):
1. Attacker crafts a multi-authored unit `U` (or one unit with `earned_headers_commission_recipients` explicitly set) with N recipient addresses all controlled by the attacker, with shares chosen (e.g. `[33, 33, 34]` or fractional splits over odd `full_amount` values) so that `sum(Math.round(full_amount * share_i / 100))` computed in `headers_commission.js` lines 176-209 exceeds `full_amount` by 1 (or more, with more recipients) each time `U` wins the headers commission for a parent unit.
2. Repeat by authoring many such units over time (each is a legitimate, independently postable unit — no privileged role required), each time capturing the rounding surplus into `headers_commission_contributions` → `headers_commission_outputs`.
3. Sum of `headers_commission_outputs.amount` across all payer units will exceed the sum of `headers_commission` actually recorded on parent (`punits`) units, demonstrating that spendable byte supply was inflated relative to the commission actually charged — verifiable by comparing `SUM(headers_commission_outputs.amount)` against `SUM(units.headers_commission)` for payer units in the affected `main_chain_index` range.

Note: I was not able to fully verify, within the available index, whether any independent invariant check exists elsewhere in the codebase (outside `headers_commission.js`/`validation.js`/`inputs.js`) that cross-checks total `headers_commission_outputs` against total `headers_commission` charged per payer unit across the whole main chain; if such a global reconciliation exists, it would mitigate (but likely only detect after the fact) rather than prevent this drift.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
