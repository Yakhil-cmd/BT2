### Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to authenticate a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')`) [1](#0-0) [2](#0-1) . However, once the signature is accepted, every `Handler` resolves the target `Repository`/`Stack` from a *different*, independently-controlled field of the same JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties `repository.owner.login` (used to pick the signing organization) to `repository.full_name` (used to pick the mutated repository).

### Finding Description
The binding that should hold is:

`organization authenticated by verify_signature == owner(repository written by Handler#repository_name)`

Both values are read from the same untrusted, attacker-suppliable JSON payload, but from unrelated keys:

- Authentication side: `repository_owner` in `app/controllers/shipit/webhooks_controller.rb:59-62` reads `repository.owner.login` (falling back to `organization.login`), and `verify_signature` (lines 24-30) looks up `Shipit.github(organization: repository_owner)` to obtain that org's `webhook_secret`, then HMAC-verifies `X-Hub-Signature` against the raw body with that secret.
- Execution side: `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) reads `repository.full_name` from the same payload to look up `Repository.from_github_repo_name(...)` and thereby the `stacks` that get acted upon (e.g. `PushHandler#process` in `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, which calls `stack.sync_github(...)` for every non-archived stack on the matching branch).

An actor who legitimately controls a GitHub App installation on their own organization (e.g. by creating and registering a Shipit GitHub App for `attacker-org`, a normal, unprivileged, self-service action, as documented in `docs/setup.md`) knows that organization's `webhook_secret`. They can therefore construct and correctly sign an arbitrary JSON payload where:
- `repository.owner.login` = `"attacker-org"` (satisfies `verify_signature`, since the attacker computed the HMAC with `attacker-org`'s own secret), while
- `repository.full_name` = `"victim-org/victim-repo"` (the actual value consumed by every `Handler` subclass to resolve which `Stack` to mutate).

Because the two fields are never cross-checked, the signature verification "authenticates" the wrong entity relative to what is actually written: it proves the sender knows `attacker-org`'s secret, not that the sender is authorized to act on `victim-org/victim-repo`.

### Impact Explanation
This breaks the trust boundary between "which organization's webhook credential validated this request" and "which repository/stack is mutated by it." Handlers keyed off `repository.full_name` (push → `Stack#sync_github`, status, check_suite, pull_request handlers, etc.) can be driven against a victim's stack using a signature computed with credentials for an organization the attacker legitimately controls. If the target stack has `continuous_deployment` enabled, a forged `push`/`status` sequence can lead into `Stack.schedule_continuous_delivery` → `ContinuousDeliveryJob`, i.e. an unauthorized deploy triggered without ever holding a session, `ApiClient` token, or the victim organization's `webhook_secret` — satisfying the "unauthorized deploy" high-impact criterion.

### Likelihood Explanation
Exploitation only requires the attacker to register/own a GitHub App on any organization known to a shared Shipit deployment (a common multi-tenant setup, as shown by the `Using Multiple Github Applications` documentation and `secrets_double_github_app.yml` fixture, where several orgs' apps are configured against one Shipit instance). No repository write access, GitHub App private key theft, or session/API-client credential of the victim is needed — only crafting a webhook body with mismatched `repository.owner.login` vs `repository.full_name` and posting it with a valid signature for the attacker's own org.

### Recommendation
Cross-validate that the organization derived for signature verification matches the owner segment of `repository.full_name` (and, ideally, verify against the `Repository`/`Stack`'s actually configured GitHub App/organization rather than a value taken from the unauthenticated payload) before dispatching to any `Handler`. Reject the webhook (422) if these do not match.

### Proof of Concept
1. Attacker registers/owns a Shipit-compatible GitHub App on `attacker-org`, obtaining `attacker-org`'s `webhook_secret` (self-service, no privileges over the target).
2. Attacker builds a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` (routed to `Shipit::WebhooksController#create`).
4. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s app via `Shipit.github(organization: "attacker-org")`, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` via `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), and `process` invokes `stack.sync_github(...)` on the victim's stacks — all without any credential belonging to `victim-org`.
