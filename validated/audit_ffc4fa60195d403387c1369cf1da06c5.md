### Title
Cross-organization CI status forgery via unscoped commit lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a signature against using an attacker-supplied field (`repository.owner.login`) rather than binding the verification to the specific commit/repository that the handler subsequently mutates. `StatusHandler`, unlike other handlers, never scopes its side effect to the repository that was authenticated — it looks up `Commit.where(sha: params.sha)` engine-wide. Any organization that has its own legitimately-configured GitHub App/webhook secret in a shared Shipit instance can therefore forge a `status` event that is "authenticated" for its own org but writes a fabricated CI status onto a commit belonging to a completely different organization's stack.

### Finding Description
`WebhooksController#verify_signature` picks the app/secret to check the signature with based on `repository_owner`, computed purely from the untrusted payload: [1](#0-0) [2](#0-1) 

Once the signature check for that *attacker-chosen* organization key succeeds, the payload is dispatched to a handler purely on the basis of the `X-Github-Event` header, with the full raw payload — including whatever `repository.full_name`/`sha` values the attacker put in it.

`StatusHandler#process` never re-derives or re-checks the repository at all; it locates commits by `sha` alone across the entire instance: [3](#0-2) 

Compare this to the base `Handler` class, which does define repository-scoping helpers (`repository_name`, `stacks`) used by most other handlers (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers): [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler` is the outlier: it neither calls `stacks`/`repository_name` nor validates that `params.sha` belongs to a commit under the organization that was actually verified. The engine's multi-tenant design explicitly supports several independent GitHub Apps/organizations sharing one Shipit instance, each with its own `webhook_secret`, as shown in the fixture used for testing this exact scenario: [7](#0-6) 

**The broken binding (as an equality):**
`organization authenticated by verify_signature (repository.owner.login in the forged payload)` is treated as equal to `organization that owns the commit mutated by StatusHandler (via params.sha)` — but nothing in the code enforces this equality. An attacker who administers Org B (with its own legitimate GitHub App configured in the shared instance) knows Org B's own `webhook_secret` (which is not a victim credential — it is their own, legitimately obtained, App secret). They can:
1. Build a `status` webhook payload with `repository.owner.login = "OrgB"` and `sha = <commit sha belonging to a stack owned by Org A>`.
2. Sign it with Org B's `webhook_secret` using the standard `sha1=hmac` scheme (`Hook::DeliverySigner`/GithubApp `verify_webhook_signature` algorithm), which is exactly what `verify_webhook_signature` checks: [8](#0-7) 
3. Post it to `/webhooks`; `verify_signature` looks up `Shipit.github(organization: "OrgB")`, validates the signature against Org B's own secret, and succeeds.
4. `StatusHandler#process` then writes the fabricated status onto Org A's commit, because it never checks that the commit actually belongs to `OrgB`.

### Impact Explanation
Shipit stacks can require specific CI status contexts before allowing a deploy (`ci.require` in `shipit.yml`). By forging a `success` status for a required context on a target commit in a victim organization's stack, an attacker who only controls an unrelated organization's GitHub App in the same Shipit instance can satisfy the CI gate and enable an unauthorized deploy of a stack/repository they have no legitimate access to. This crosses the "unauthorized deploy" impact bar defined for this engine, achieved purely through a webhook signature that is valid for the attacker's own organization but is misapplied to another organization's data.

### Likelihood Explanation
This requires only that: (a) the Shipit instance hosts stacks/repositories for more than one GitHub organization/App (a supported, documented configuration — see `secrets_double_github_app.yml` and `docs/setup.md`), and (b) the attacker controls or administers one of those organizations' GitHub Apps (their own, legitimately-owned credential — no victim secret needed). No GitHub write access to the victim repo, no Shipit session, and no victim credentials are required — only the attacker's own webhook secret and knowledge/enumeration of a target commit SHA (which is generally not secret; SHAs are visible via GitHub's public/API surface for the target repo). This makes exploitation practical for any Shipit deployment shared across multiple orgs.

### Recommendation
`StatusHandler` (and any other handler that does not currently do so) must scope its lookup to the repository actually authenticated during `verify_signature`, e.g. by joining `Commit` through `Stack -> Repository` and filtering on `repository.full_name`/`owner` derived from the same trusted payload field used for signature verification, or by having `verify_signature` pass the verified organization down to handlers and rejecting statuses whose commit's owning repository doesn't match.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations (`OrgA`, `OrgB`) as supported by `test/dummy/config/secrets_double_github_app.yml`. `OrgA` owns stack/repo `OrgA/victim-repo` with a commit `deadbeef...` and a `ci.require` context `ci/tests`.
2. As an attacker controlling `OrgB`'s legitimate webhook secret, build payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "OrgB" } }
}
```
3. Sign it: `sha1=#{OpenSSL::HMAC.hexdigest('sha1', OrgB_webhook_secret, payload_json)}`.
4. `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature` set to that value.
5. `WebhooksController#verify_signature` succeeds using `Shipit.github(organization: "OrgB")` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the commit `deadbeef...` (which belongs to `OrgA`) purely by SHA and writes the forged `success` status via `commit.create_status_from_github!`, satisfying `OrgA`'s CI gate without any credential from `OrgA`.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
