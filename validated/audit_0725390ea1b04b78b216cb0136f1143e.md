### Title
Textcoin mnemonic (bearer private key) disclosed via `console.log` - (File: wallet.js)

### Summary
`wallet.js`'s textcoin subsystem stores the BIP39 mnemonic that *is* the private key controlling a textcoin address, and then prints that mnemonic in plaintext to the process log/stdout whenever an unclaimed textcoin is reclaimed by `claimBackOldTextcoins()`. This mirrors the CVE-2020-1753 bug class: a secret credential is emitted through an insecure channel (stdout/log files) instead of being kept out of logs, allowing anyone with read access to those logs to reconstruct the secret and steal the funds it protects.

### Finding Description
A textcoin is a self-contained "bearer" payment: the 12-word mnemonic is directly turned into the spending key for the coin's address in `expandMnemonic()`: [1](#0-0) 

That mnemonic is persisted in the `sent_mnemonics` table when the textcoin is created in `sendMultiPayment` (`assocMnemonics`), and used later in `receiveTextCoin()` to derive `addrInfo.xPrivKey` and sign the reclaiming transaction with `ecdsaSig.sign(...)`: [2](#0-1) 

Whoever knows the mnemonic can unilaterally spend the coin — knowledge of the mnemonic is equivalent to possession of the private key.

`claimBackOldTextcoins()` selects every unclaimed mnemonic older than N days from `sent_mnemonics` and, for each one, logs the full mnemonic in plaintext on both the failure and success paths: [3](#0-2) 

This is functionally identical to the CVE-2020-1753 root cause: a sensitive secret that should never leave a protected channel (an environment variable / secure store) is instead written to a log/stdout stream (`console.log`), where it can be captured by log aggregation, crash reporting, `journalctl`, shell history redirection, or any third party with read access to the node's logs.

### Impact Explanation
Anyone who can read the wallet process's stdout or log files (a very common exposure surface — log shipping agents, crash reporters, shared hosting, misconfigured log permissions) obtains the raw mnemonic for every reclaimed textcoin. Because the mnemonic is the sole authenticator for that address (`"sig", {"pubkey": ...}` definition derived purely from the mnemonic, see `expandMnemonic`), possession of the logged mnemonic lets an attacker compose and broadcast a spend from that address before or in a race with the legitimate reclaim, resulting in direct, unauthorized theft of funds. This satisfies the "concrete unauthorized spending" bar.

### Likelihood Explanation
`sendMultiPayment` (reachable by any user composing a payment to a `textcoin:` pseudo-address, including one attacker-controlled recipient email/target) creates textcoins whose mnemonics later flow into `claimBackOldTextcoins()`. This function runs as ordinary periodic wallet maintenance (reclaiming stale textcoins) with no special privileges required to trigger the underlying condition — an attacker merely needs to send (or receive) a textcoin and wait for the claim-back window, then obtain the operator's logs through any of the common exposure vectors listed above. No malicious peer, hub, or network compromise is required; the leak occurs purely from normal application logging behavior.

### Recommendation
Remove or redact the mnemonic from all `console.log` statements in `claimBackOldTextcoins()` (and any other logging of `mnemonic`/`row.mnemonic` values throughout `wallet.js`). Log only non-sensitive identifiers (e.g., the derived address or unit hash) instead of the raw mnemonic, and audit `sendTextcoinEmail`/`email_template.html` and other paths for similar plaintext propagation of the secret into logs.

### Proof of Concept
1. Attacker (or any user) sends a textcoin via `sendMultiPayment` to a `textcoin:` output; the mnemonic is stored in `sent_mnemonics`.
2. After the configured claim-back period elapses without the recipient claiming it, the wallet's scheduled job calls `claimBackOldTextcoins(to_address, days)`.
3. For each unclaimed row, `receiveTextCoin(row.mnemonic, ...)` runs and the code unconditionally logs:
   - `"failed claiming back old textcoin "+row.mnemonic+": "+err`
   - `"claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset` [4](#0-3) 
4. Any party with read access to the node's console output/log files (log aggregation, crash dump, shared log storage) extracts the plaintext mnemonic, calls `expandMnemonic()` themselves, and signs/broadcasts a competing spend from `addrInfo.address`, stealing the funds before or instead of the legitimate owner.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}

// if a textcoin was not claimed for 'days' days, claims it back
function claimBackOldTextcoins(to_address, days){
	if (typeof days !== 'number')
		throw Error("bad days: " + days);
	db.query(
		"SELECT mnemonic FROM sent_mnemonics LEFT JOIN unit_authors USING(address) \n\
		WHERE mnemonic!='' AND unit_authors.address IS NULL AND creation_date<"+db.addTime("-"+days+" DAY"),
		function(rows){
			async.eachSeries(
				rows,
				function(row, cb){
					receiveTextCoin(row.mnemonic, to_address, function(err, unit, asset){
						if (err)
							console.log("failed claiming back old textcoin "+row.mnemonic+": "+err);
						else
							console.log("claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset);
						cb();
					});
				}
			);
		}
	);
}
