### Title
StatusHandler#process writes GitHub statuses to commits from any tenant's stack by matching SHA globally instead of scoping to the requesting repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and never calls the inherited `Handler#stacks` helper (which scopes to `Repository.from_github_repo_name(repository_name)`), unlike `PushHandler#process` which does scope through `stacks`. Because commit SHAs are not unique per repository/tenant in Shipit's schema, a `status` webhook signed for an attacker-owned repository can mutate the status history of a commit that belongs to an entirely different tenant's stack.

### Finding Description
The broken binding is: `repository_name_derived_stacks (Repository.from_github_repo_name(payload.repository.full_name).stacks) == commit.stack` for every `commit` mutated by `StatusHandler#process`.

Tracing the code:
- `Shipit::Webhooks::Handlers::Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) scopes to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) correctly uses this scope: `stacks.not_archived.where(branch:).find_each { ... }`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does **not** call `stacks` at all. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, an unscoped, cross-tenant lookup by SHA alone.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `add_status`, which creates a `Status` record tied to `stack_id`, updates `stack.schedule_merges`, and emits `Hook.emit(:commit_status, stack, ...)` / `:deployable_status` hooks — all scoped to whatever `stack` the matched commit actually belongs to, not the attacker's stack.

The only gate before reaching `StatusHandler#process` is `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`), which calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This only proves the payload was signed by GitHub for the organization/repo named in `payload['repository']['owner']['login']` — i.e., it proves the attacker really owns that repository and GitHub really sent this event for it. It does **not** prove any relationship between that repository and the commit SHA in the payload. Nothing else in `StatusHandler`, `ExplicitParameters` schema (`requires :sha, String`), or `Commit` re-validates that `sha` actually belongs to a commit under the signing repository's stacks.

Attacker request: attacker creates any repo (e.g., `attacker/evil-repo`) that is connected to Shipit as a tenant (a Shipit-tracked repo, which the rules require as a precondition), obtains a real `sha` value that belongs to some other tenant's commit (commit SHAs are known/guessable — they show up in Shipit's public-ish UI, API, or GitHub itself), and sends a legitimately-signed `status` event for `attacker/evil-repo` with `sha` set to the victim's commit SHA. `verify_signature` passes because the signature is valid for `attacker/evil-repo`. `StatusHandler#process` then finds `Commit.where(sha: victim_sha)` — which resolves to the victim's commit under the victim's stack — and writes a forged `Status` (`state`, `description`, `target_url`, `context` all attacker-controlled) onto it, which can flip `commit.deployable?` and trigger `stack.schedule_merges` / continuous deployment on the **victim's** stack.

### Impact Explanation
This lets an attacker who owns any Shipit-tracked repository forge GitHub commit statuses on arbitrary commits belonging to unrelated stacks/repositories across the entire Shipit instance, simply by knowing (or guessing) a target SHA. Since `add_status` can trigger `stack.schedule_merges` and `Commit#schedule_continuous_delivery`, this can make an attacker-controlled "success" status unblock or trigger an unauthorized deploy/merge on a victim's stack — matching the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The attack is fully repeatable against any commit SHA known to the attacker and is not limited to a single victim; it is a systemic cross-tenant write primitive.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to own one Shipit-connected GitHub repository (so `verify_signature` passes for their own org) and to know a target commit SHA from any other tenant (commit SHAs are not secret — they are visible in Git history, GitHub, and often in Shipit's own UI/API for stacks the attacker can view). No Shipit session, API token, or GitHub App secret is required. The attacker crafts one HTTP POST to `/webhooks` with a valid signature for their own repo. This is cheap, requires no interaction from the victim, and is repeatable at will.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository that signed the webhook, mirroring `PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
or equivalently join through `Repository.from_github_repo_name(repository_name)` before touching any `Commit`, ensuring `commit.stack.repository == repository_name`-derived repository for every mutated row.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "#process does not mutate commits belonging to a different repository's stack" do
  attacker_stack = shipit_stacks(:shipit)          # stack for repo A (attacker-owned)
  victim_stack   = shipit_stacks(:cyclimse)        # stack for repo B (victim, different repository)
  victim_commit  = victim_stack.commits.create!(sha: '0' * 40, message: 'victim commit')

  payload = {
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker-forged',
  }

  handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)

  # Assert the equality that should hold: repository-derived stacks must include the target commit's stack.
  assert_not_includes handler.send(:stacks), victim_stack

  assert_difference -> { victim_commit.statuses.count }, 0 do
    handler.process
  end
end
```
Currently this test fails: `handler.process` creates a `Status` on `victim_commit` even though `handler.send(:stacks)` does not include `victim_stack`, proving `#process` bypasses the repository scope entirely.
