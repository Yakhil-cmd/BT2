### Title
StatusHandler resolves commits by SHA alone, letting a signed webhook from an attacker's own repo mutate a victim stack's commit status and trigger continuous delivery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filter on the payload's `repository.full_name` (unlike `PushHandler`, which scopes via `stacks.where(branch:)` derived from `Repository.from_github_repo_name(repository_name)`). Because signature verification only proves the payload was signed by the organization named in `repository.owner.login` in the payload - which the attacker legitimately controls for their own repo - an attacker can send a validly-signed status webhook for their own repository that still updates `Status` rows (and therefore `Commit#status`/`deployable?`) for any *other* stack whose `Commit` row happens to share the same `sha` value, since `sha` is not namespaced by repository/stack in the `Commit.where(sha:)` lookup.

### Finding Description
The binding the question implies should hold is: `number of ContinuousDeliveryJob enqueues attributable to attacker's webhook for stack ≠ attacker's own stack == 0`. This is violated because:

- `WebhooksController#verify_signature` derives the signing organization purely from the attacker-controlled payload (`repository_owner` reads `params.dig('repository','owner','login')`), then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) . This only proves the request was signed with *that organization's* webhook secret - which the attacker legitimately owns/controls if it's their own GitHub org/repo. It proves nothing about which `Stack`/`Commit` the payload's `sha` should affect.
- `StatusHandler#process` then dispatches purely by `sha`, with zero use of `repository_name`/`payload['repository']` to scope the lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
- Compare this to `PushHandler`, which correctly scopes through `Handler#stacks`, resolving `Repository.from_github_repo_name(repository_name)` before touching any `Stack` [3](#0-2) [4](#0-3) . `StatusHandler` has no equivalent repository check.
- `create_status_from_github!` -> `statuses.replicate_from_github!` creates a `Status` row keyed to `stack_id` (the *victim's* `stack_id`, taken from the matched `Commit`, not from the payload) [5](#0-4) [6](#0-5) .
- `Status` creation fires `after_commit :schedule_continuous_delivery` -> `commit.schedule_continuous_delivery`, which recomputes `deployable?` via `Status::Group.compact`/`state` and, if the victim stack has `continuous_deployment?` true and is otherwise deployable, enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` for the *victim's* stack [7](#0-6) [8](#0-7) [9](#0-8) .

Exploit flow: the attacker needs a `Commit` row to already exist in the victim's stack with a `sha` equal to one the attacker can also produce a signed status webhook for (i.e., a shared/duplicated sha across two different `Stack`/`Repository` records - a realistic occurrence in fork/mirror setups where the same commit sha is synced into multiple stacks' `Commit` tables). The attacker then:
1. POSTs a `status` event, signed with their own repo/org's webhook secret, naming their own `repository.full_name`, with `sha` = the shared sha and `state: failure`.
2. POSTs a second, similarly signed `status` event with the same `sha` and `state: success`.

Both are accepted by `verify_signature` (the attacker's own valid signature) and processed by `StatusHandler`, which finds and mutates the victim's `Commit` (and any other stack's commit with that sha) purely by sha match, with no check that the payload's `repository.full_name` matches the victim commit's `stack.repository`.

Existing guards fail here because: `verify_signature` validates *who signed*, not *which stack the sha belongs to*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate event type/param shape, not repository ownership; there is no `require_permission!`/`stacks` scope check inside `StatusHandler` as there is in `PushHandler`.

### Impact Explanation
An attacker with no privilege over the victim stack can cause `Status` rows to be written against the victim's `Commit`, changing `Commit#status`/`deployable?`, and - if the victim stack has `continuous_deployment?` enabled - can cause an unauthorized `ContinuousDeliveryJob` enqueue (an unauthorized deploy) for a stack the attacker never authenticated against. This matches the "payload for one repository mutating another's stack/commit... or an unauthorized deploy" Critical category. The blast radius is any stack/repository pair that shares a `sha` value with the attacker-controlled repository (forks, mirrors, monorepo splits, or any setup where identical commits are synced into multiple `Stack`s' `Commit` tables).

### Likelihood Explanation
Preconditions: (1) the victim stack has `continuous_deployment?` true; (2) a `Commit` row with the same `sha` already exists under both the attacker's and the victim's stacks (this requires some shared git history/fork/mirror relationship - it is not exploitable against an arbitrary unrelated victim sha unless such duplication exists). Given those preconditions, the attack is trivial and cheap for the attacker: they only need to control one GitHub repo whose webhook fires to the shared Shipit host, and can repeat the toggle indefinitely. The primary constraint is the sha-sharing precondition, which is plausible in fork/mirror topologies but not universal.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to stacks whose `Repository` matches `payload['repository']['full_name']` (e.g., filter through `stacks`/`Repository.from_github_repo_name(repository_name)` the same way `PushHandler` does), rather than a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, do not add under test/ per scope rules - forward to engineer)
test "status webhook from attacker's own repo mutates a victim stack's commit with the same sha" do
  attacker_stack = shipit_stacks(:attacker_stack) # repository owned/controlled by attacker
  victim_stack = shipit_stacks(:shipit)           # continuous_deployment? == true
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_stack.commits.create!(sha: shared_sha, ...) # attacker's own copy, same sha

  payload_failure = { sha: shared_sha, state: "failure", repository: { full_name: attacker_stack.repository.full_name } }
  payload_success = { sha: shared_sha, state: "success", repository: { full_name: attacker_stack.repository.full_name } }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload_failure)
  assert_equal "failure", victim_commit.reload.status.state # binding already broken: victim mutated by attacker's payload

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload_success)
  end
  assert_equal "success", victim_commit.reload.status.state
end
```
Both sides of the binding differ: expected `0` unauthorized `ContinuousDeliveryJob` enqueues for `victim_stack` from the attacker's own webhook traffic, actual `1` per toggle-to-success call.
