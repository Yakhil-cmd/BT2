## Analysis Summary

I examined `pallet_asset_rewards` (Synthetix-style staking rewards pool with `reward_per_token` accounting and pool expiry), the closest FRAME analog to the BondNFT `accRewardsPerShare`/expiry accounting pattern from the report. While the *direction* of the bug differs from the original theft finding, the same root cause category — improper handling of state after an "expiry" boundary in reward accounting — produces a real, permission-less, deterministic bug: a **permanent freeze of funds** rather than theft.

### Title
Any account can permanently freeze staked funds and rewards in an expired `pallet-asset-rewards` pool via a single extra call - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`Pallet::<T>::reward_per_token` computes `rewardable_blocks_elapsed` as `last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)` [1](#0-0) , capping the "applicable" reward block at `expiry_block`, but `update_pool_rewards` always stores the **real, uncapped** current block number into `last_update_block` [2](#0-1) . Once any state-changing call (`stake`, `unstake`, `harvest_rewards`) is processed for the first time after the pool has expired, `last_update_block` becomes greater than `expiry_block`. On the very next call for that pool, `last_block_reward_applicable(expiry_block)` returns `expiry_block` (since `now > expiry_block`), and `expiry_block.ensure_sub(last_update_block)` underflows and returns an arithmetic error, aborting the extrinsic. Because `last_update_block` only ever increases and is never re-capped to `expiry_block`, **every subsequent operation on that pool fails permanently**.

### Finding Description
`harvest_rewards` explicitly allows any signed account to trigger this update for any staker once the pool has expired: `ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);` [3](#0-2) . This is a normal, permission-less, documented usage path (the doc comment for the parameter even says "Otherwise, any account" [4](#0-3) ), so no privileged role, governance action or stolen key is required.

Sequence:
1. Pool `P` has at least one staker with nonzero `total_tokens_staked` and reaches `now > expiry_block`.
2. Anyone calls `harvest_rewards(pool_id, staker)` (or `stake`/`unstake`) — this is accepted, `update_pool_and_staker_rewards` → `reward_per_token` succeeds because `last_update_block <= expiry_block` still holds, and `update_pool_rewards` sets `last_update_block = now` (which is `> expiry_block`) [2](#0-1) .
3. Anyone calls `harvest_rewards`/`stake`/`unstake` on the same pool again (even in the same block). `last_block_reward_applicable(expiry_block)` returns `expiry_block` (`now > expiry_block`), so the computation is `expiry_block.ensure_sub(last_update_block)` where `last_update_block > expiry_block` — this underflows and `ensure_sub` returns an error, aborting the call [1](#0-0) .
4. From this point on, `last_update_block` never decreases, so **every** future `stake`, `unstake`, or `harvest_rewards` call on pool `P` fails identically, forever.

Since `unstake` is also gated behind `update_pool_and_staker_rewards` [5](#0-4) , stakers can never withdraw their frozen staked assets. `cleanup_pool` additionally requires `PoolStakers::<T>::iter_key_prefix(pool_id).next()` to be `None` [6](#0-5) , which can now never be satisfied because stakers can't unstake — so the pool's reward-asset balance and the depositor's storage `Consideration` are permanently unreachable too.

### Impact Explanation
This is an irreversible freezing of user assets: staked tokens (held via `AssetsFreezer`) become permanently unspendable/unstakeable, and any remaining reward-asset balance in the pool account, plus the pool creator's storage deposit, become permanently stuck since `cleanup_pool` can never succeed. Any account — not just the staker or pool admin — can trigger the second, poison call, so this can be induced by a griefing attacker at zero cost right after natural pool expiry.

### Likelihood Explanation
High likelihood: it requires no special timing race, no privileged role, and is triggered by the pool simply reaching its natural, admin-configured `expiry_block` plus two ordinary, permission-less extrinsics (or even one call by the staker followed by any account's `harvest_rewards`). Every pool created via this pallet that is allowed to expire while it still has stakers is affected.

### Recommendation
`update_pool_rewards` should cap `last_update_block` at `min(now, pool_info.expiry_block)` (mirroring `last_block_reward_applicable`) instead of always storing the raw current block number, so that `reward_per_token`'s subtraction never underflows once the pool has expired. Alternatively, `reward_per_token` should use a saturating/checked comparison that treats `last_update_block > expiry_block` as "zero additional rewardable blocks" rather than propagating an arithmetic error.

### Proof of Concept
Failed guard confirmed by static trace of the checked-arithmetic call chain (no test currently exercises "two operations after expiry" — all existing tests re-extend `expiry_block` before further calls, e.g. `extends_reward_accumulation` and `integration` in `substrate/frame/asset-rewards/src/tests.rs`, which never exercise two raw post-expiry calls without an intervening `set_pool_expiry_block`). This report is a **static/logical analog** derived from reading `reward_per_token`/`update_pool_rewards`; no live network or extra test harness execution was run to produce empirical output — a minimal repro would be: create a pool, stake, advance `System::set_block_number` past `expiry_block`, call `StakingRewards::harvest_rewards` once (succeeds), then call it a second time (or `unstake`) and observe `Error::<T>::BlockNumberConversionError`/arithmetic error from `ensure_sub`, after which all further calls to `stake`/`unstake`/`harvest_rewards` on that pool fail identically.
