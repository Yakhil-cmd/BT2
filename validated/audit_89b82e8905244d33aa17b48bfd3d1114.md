### Title
Unconditional throw on failed kvstore delete during cleanup of purged/archived units causes full node crash (DoS) - ([File: kvstore.js])

### Summary
`kvstore.js`'s `del()` unconditionally throws an uncaught `Error` whenever the underlying RocksDB delete callback returns any error, with no retry, no isolation, and no graceful degradation. This function is invoked as the final cleanup step after a unit has already been archived/removed from SQL storage in several unprivileged-reachable code paths (e.g., cleanup of bad/nonserial units triggered by ordinary unit posting). A failure in this single delete call — analogous to the failed `unlink()` after volume creation in CVE-2015-5247 — propagates as an uncaught exception and crashes the whole node process, matching the same "successful-creation/removal, but failed-cleanup-crashes-daemon" bug class.

### Finding Description
`kvstore.js` wraps every RocksDB operation in a callback that throws on any error: [1](#0-0) 

This `del` function is used as the terminal step of the "purge uncovered nonserial (final-bad/temp-bad) joints" flow. When a unit becomes `final-bad`/`temp-bad` (which happens whenever any node validates and rejects a unit posted by an unprivileged peer/unit-poster) and later becomes eligible for purge, the code first archives it in SQL, then deletes its raw joint entry from the KV store: [2](#0-1) 

The identical unconditional-throw-on-delete-failure pattern is also used in `storage.js`'s `archiveJointAndDescendants`, which is executed on ordinary DAG maintenance/testnet reset paths: [3](#0-2) 

And in `network.js`, expired/replayed "waiting for pruned content" entries are deleted the same way without any error check at all (fire-and-forget), relying on `kvstore.del`'s internal throw for any failure signaling: [4](#0-3) 

If the underlying RocksDB `del` callback ever returns an error for any of these keys (disk I/O error, concurrent compaction issue, corrupted entry, resource exhaustion, or any other backend failure condition), `kvstore.js` throws synchronously inside an asynchronous callback. There is no `try/catch` anywhere in these call chains. The thrown error becomes an uncaught exception, which the top-level handler in `network.js` explicitly re-throws to terminate the process: [5](#0-4) 

This mirrors the CVE-2015-5247 root cause exactly: a normal, unprivileged-triggerable object lifecycle event (unit posting → validation → later archival/cleanup) ends with a filesystem/storage-layer delete operation whose failure is not handled gracefully but instead crashes the whole daemon.

### Impact Explanation
Any condition that makes the KV-store delete fail for a to-be-purged unit (disk pressure, transient RocksDB error, or corrupted/missing key state reachable via a crafted sequence of final-bad units and races with the write-lock/`forgetUnit` bookkeeping) results in an unhandled exception that kills the running full node. Because the code path is reached organically from ordinary "bad unit received → later purged" processing — something any unit poster can cause by broadcasting invalid units — this is a general-purpose remote DoS primitive against any node running this cleanup logic, potentially affecting network-wide availability/confirmation if exploited at scale (the same bug class as the CVSS 6.5 "libvirtd crash" report).

### Likelihood Explanation
Likelihood is Medium: reaching the `kvstore.del` cleanup call is trivial (post an invalid/nonserial unit that becomes `final-bad`/`temp-bad` and is later purged, which is routine node housekeeping), but actually causing the underlying RocksDB `del()` call to return an error requires a specific storage-layer failure condition (I/O error, disk full, or exploitable race with `forgetUnit`/`fixIsFreeAfterForgettingUnit` bookkeeping) that is not fully attacker-controlled from a single posted unit alone — similar to the original CVE requiring a specific NFS root_squash environment.

### Recommendation
Do not unconditionally `throw` on delete/get/put errors in `kvstore.js`. Distinguish between fatal corruption (worth crashing on) and transient/backend errors that should be retried, logged, and surfaced to the caller via the callback's error argument instead of thrown synchronously. At minimum, wrap the archiving/purging call sites (`joint_storage.js` purge flow, `storage.js` `archiveJointAndDescendants`, `network.js` pruned-content cleanup) so that a failed cleanup delete does not crash the entire process — retry, skip-and-log, or isolate the failure to the specific unit instead of terminating the daemon.

### Proof of Concept
1. An unprivileged peer posts a syntactically valid but content-invalid unit; the node validates it and marks it `sequence='final-bad'` or `'temp-bad'` in `units`.
2. Once the unit becomes uncovered (no children, not required by other unhandled joints) and the age/witness conditions in `purgeUncoveredNonserialJoints` are met, the periodic purge task archives it in SQL and then calls `kvstore.del('j\n'+row.unit, ...)` (`joint_storage.js:269`).
3. If the underlying RocksDB `del` callback returns any error (e.g., simulated by forcing an I/O error on the RocksDB directory, filling disk, or a corrupted LSM entry for that key), `kvstore.js:53-55` throws `Error("del ... failed: "+err)` inside the async callback.
4. This uncaught exception is caught by `process.on('uncaughtException', ...)` in `network.js:4530`, which logs it and then re-throws (`network.js:4542`), terminating the node process — a full denial of service triggered indirectly by ordinary unit-posting activity combined with a storage-layer delete failure.

**Note on verification limits:** I could not fully trace every internal RocksDB/`level-rocksdb` failure condition that could cause `del()` to return an error from this codebase index alone (that dependency's internals are outside indexed code), so the exact reliably-attacker-triggerable failure trigger for the underlying delete operation is not fully confirmed — only the unconditional-throw/no-error-handling pattern and its reachability from ordinary unprivileged unit posting are proven from the code shown above.
