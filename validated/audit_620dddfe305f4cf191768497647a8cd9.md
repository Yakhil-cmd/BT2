### Title
Cross-Organization Webhook Forgery via Unbound `repository.owner.login` vs `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to validate an inbound GitHub webhook based on `repository.owner.login` (or `organization.login`) taken from the request body, but the event handlers that subsequently act on the same body (e.g. `PushHandler`, `StatusHandler`, `MembershipHandler`) resolve the target `Stack`/`Team`/`Commit` using a *different* field of the same payload — `repository.full_name` (or `organization.login` for membership events) — with no check that it belongs to the organization whose secret validated the request. This is the same class of bug as the reported `early-purchase` issue: a value that is trusted/verified is not the same value that is subsequently acted upon, and the mismatch is never validated.

### Finding Description
In a multi-organization Shipit deployment (explicitly supported and documented, see `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`), each onboarded GitHub organization has its own `webhook_secret` in `Shipit.github(organization:)`.

`verify_signature` picks which secret to verify with using: [1](#0-0) 

`repository_owner` is read straight from the JSON body: [2](#0-1) 

Once signature verification succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the **entire raw payload** to handlers. Handlers resolve the acted-upon repository from an independent field, `repository.full_name`: [3](#0-2) 

used directly by `PushHandler`: [4](#0-3) 

`StatusHandler` acts on `params.sha` alone (no repo scoping at all, so it will match a commit belonging to *any* stack/org that happens to have that SHA): [5](#0-4) 

`MembershipHandler` derives its target `organization.login` from the payload independently of `repository_owner`: [6](#0-5) 

Nowhere does the code assert `repository.owner.login == repository.full_name.split('/').first` (or `organization.login == repository_owner`). GitHub itself always keeps these consistent when *it* generates the payload, but the code never independently enforces that invariant — exactly the "improper parameter validation" pattern from the reference report: a field that is trusted for one purpose (auth/secret-selection) is not cross-checked against the field that is actually acted upon.

**Binding broken:** *organization that authenticated* (`repository_owner` used to select `webhook_secret`) `≠` *repository that is written* (`repository.full_name` / `organization.login` used by the handler to select the `Stack`/`Team`/`Commit`).

### Impact Explanation
An attacker who legitimately controls one organization onboarded to a shared, multi-tenant Shipit instance (i.e., they hold that organization's own `webhook_secret`, which they are entitled to as an app owner of their own org, not the victim org) can compute a valid `X-Hub-Signature` for `repository_owner = their-org`, while setting `repository.full_name` (or `organization.login`) to a victim organization's repository/org that is also mounted on the same Shipit instance. This lets the forged event:
- Trigger `GithubSyncJob`/`sync_github` for the victim's stacks (`PushHandler`).
- Inject a fabricated commit `Status` (`StatusHandler`) for any SHA across the whole instance, since lookup is `Commit.where(sha:)` with no repository scoping — this can be used to satisfy `ci.require`/blocking status checks that gate deploys, contributing to an unauthorized deploy.
- Create/modify `Team` membership tied to an arbitrary `organization.login` (`MembershipHandler`), which can affect `Shipit.github_teams` authorization.

This crosses the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" / "unauthorized deploy" impact bar defined in scope, without requiring an `ApiClient` token, a Shipit session, or the victim's own webhook secret — only the attacker's own (lesser-privileged, different-org) webhook secret.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker to control at least one of those organizations (e.g., a lower-trust org onboarded for a side project) while a higher-value org shares the same instance. Given this multi-tenant setup is explicitly documented as a first-class feature, this is a realistic deployment shape, though it depends on the specific tenancy model chosen by the operator.

### Recommendation
After successful signature verification, enforce that every subsequent org/repo-identifying field in the same payload is consistent with `repository_owner`:
- Verify `repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers.
- For `membership`/`organization`-scoped events, verify `params.organization.login.casecmp?(repository_owner)`.
- Reject (422) the webhook if any mismatch is found, and add regression tests for the multi-org configuration analogous to `test/dummy/config/secrets_double_github_app.yml`.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the owner of `AttackerOrg`'s GitHub App, craft a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "full_name": "VictimOrg/victim-repo", "owner": { "login": "AttackerOrg" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, body)>` and POST to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and validates successfully against the attacker's own secret.
5. `PushHandler#process` uses `payload.dig('repository','full_name')` → `"VictimOrg/victim-repo"` to find and sync `VictimOrg`'s stacks, even though the signature was never validated by `VictimOrg`'s secret.

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
