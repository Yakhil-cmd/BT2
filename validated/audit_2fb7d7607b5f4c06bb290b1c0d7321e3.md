### Title
CCMenu API token is not stack-scoped, allowing reuse across arbitrary stacks - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#client` mints (or reuses) a single `ApiClient` named `'CCMenu Client'` per user with `permissions: %w[read:stack]` and no `stack_id`, then embeds its `authentication_token` in a URL for the specific stack the caller requested. Because the token itself carries no stack scoping and `Api::CCMenuController#stack` resolves the target stack directly from `params[:stack_id]` without consulting the base controller's stack-scoping helper, the same token can be replayed against any stack's `cc.xml` endpoint.

### Finding Description
The claimed binding is: `stack the token authorizes == stack the URL is used against`. Tracing the code shows this equality is never enforced.

- `CCMenuUrlController#client` creates the client with `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is set, so `stack_id` is `nil`. [1](#0-0) 
- `fetch` builds `api_stack_ccmenu_url(stack_id: stack.to_param)` and appends `client.authentication_token` as the `token` query param, i.e. the URL's stack segment is caller-supplied while the token is stack-agnostic. [2](#0-1) 
- `Api::CCMenuController` authenticates via `ApiClient.authenticate(params[:token])` and enforces only `require_permission :read, :stack`, which just checks `permissions.include?("read:stack")` — a generic, non-scoped permission check. [3](#0-2) [4](#0-3) 
- Critically, `Api::CCMenuController#stack` overrides the base controller's `stacks`/`stack` scoping helper and instead calls `Stack.from_param!(params[:stack_id])` directly — bypassing the `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` scoping that `Api::BaseController#stacks` would otherwise apply. [5](#0-4) [6](#0-5) 

Since the client's `stack_id` is `nil`, even the base scoping (`Stack.all`) would not have restricted access anyway — but the controller doesn't even use it. Either way, the token authorizes `read:stack` against *any* stack, not the one the URL was generated for.

Exploit flow: victim visits stack A's settings page and obtains their CCMenu URL (`GET /stacks/:owner/:repo/:branch/ccmenu_url` -> `fetch`), which is shared/leaked (this is the documented use case — pasting into CI dashboard tools). Attacker captures that URL, extracts the `token` value, then issues `GET /api/1/stacks/:owner_B/:repo_B/:branch_B/cc.xml?token=<same-token>`. `ApiClient.authenticate` succeeds (signature valid, same token), `require_permission :read, :stack` passes (client has `read:stack`), and `stack` resolves stack B directly — the response leaks stack B's build/deploy status.

No existing guard prevents this: `require_permission!` only checks the operation:scope pair, not scope identity; there is no comparison between `current_api_client.stack_id` and the requested `stack_id` in `Api::CCMenuController`.

### Impact Explanation
An attacker who obtains one leaked/shared CCMenu URL for stack A can read the CI/deploy status (`cc.xml`, including latest deploy state) of any other stack in the Shipit instance, without ever authenticating themselves. This is a cross-tenant authorization bypass: unauthorized read of stack state for stacks the attacker was never granted access to, repeatable indefinitely since the token is a durable per-user credential (not per-stack, not expiring). This matches the High severity category: "unauthenticated read of stack state" achieved via privilege/scope escalation across stacks.

### Likelihood Explanation
The only precondition is that the attacker obtains one CCMenu URL that a legitimate user generated and shared (this is the intended workflow — pasting the URL into CI status tools/dashboards, which are often less protected than the Shipit UI itself). No Shipit secrets, GitHub credentials, or privileged roles are required beyond capturing a URL that a user already exposed for one stack. Once captured, exploitation is a single unauthenticated HTTP GET with the `stack_id` path segment changed.

### Recommendation
Bind the minted `ApiClient` to the specific stack (`stack: stack`) when creating/finding the `'CCMenu Client'` record (e.g., scope `find_or_create_by!` by `creator`, `name`, and `stack`), and have `Api::CCMenuController#stack` use the base controller's scoped `stacks` helper (or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`) so a token can only be used against the stack it was issued for.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (existing suite) / `test/controllers/ccmenu_url_controller_test.rb`:
1. As `user`, `GET /stacks/:owner_a/:repo_a/:branch_a/ccmenu_url`; extract `token` from the returned `ccmenu_url` JSON.
2. Assert `ApiClient.find_by(name: 'CCMenu Client', creator: user).stack_id.nil?` (confirms unscoped token).
3. `GET /api/1/stacks/:owner_b/:repo_b/:branch_b/cc.xml?token=<token>` for an unrelated stack B.
4. Assert response status `200` and body contains stack B's project/deploy status — proving the token issued for stack A's URL authorizes reads on stack B.
