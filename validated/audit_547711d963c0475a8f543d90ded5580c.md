### Title
No user-settable cap on TPS fees allows a stake-weighted vote to retroactively inflate the fee already committed in a broadcast unit - (File: storage.js, main_chain.js, validation.js)

### Summary
`ocore` charges a `tps_fee` on every unit to throttle throughput. The fee that a poster locks into a unit at composition time (`objUnit.tps_fee`) is computed from the `base_tps_fee`/`tps_interval` system parameters that are current at that moment [1](#0-0) . Those parameters, however, are themselves mutable via a `system_vote`/`system_vote_count` mechanism that any address can participate in, weighted by its byte balance [2](#0-1) [3](#0-2) . Once a unit finally stabilizes, `getFinalTpsFee()` recomputes the fee that is actually due using the **system-var value in effect at the unit's own final MCI**, explicitly *not* the value the poster locked in against the last-ball MCI at broadcast time (the code comment even flags this: "not at last_ball_mci") [4](#0-3) . The difference between what was pre-paid and this recomputed "actual" fee is then applied as a debit/credit to the address's running `tps_fees_balance` [5](#0-4) . There is no mechanism for a poster to declare a maximum acceptable final fee or opt out if the vote changes the parameters between broadcast and stabilization.

### Finding Description
1. A user (or their wallet) composes a unit and locks in `tps_fee` based on `getLocalTpsFee()`, which reads `base_tps_fee`/`tps_interval`/`tps_fee_multiplier` as of the *last-ball MCI* known at compose time [1](#0-0)  and `parent_composer.js` uses the same call when composing the joint [6](#0-5) .
2. Any address (not just witnesses/order providers) can post a `system_vote` message changing `base_tps_fee`, `tps_interval`, or `tps_fee_multiplier` [2](#0-1) , and these votes are tallied by stake balance and applied once counted [7](#0-6) [3](#0-2) .
3. If such a vote raises `base_tps_fee`/lowers `tps_interval` between the time the victim's unit is broadcast and the time it is finally stabilized, `getFinalTpsFee()` computes a materially higher fee than the one the user actually paid, using parameters at the unit's *own* MCI rather than the MCI the user relied on when signing the unit [4](#0-3) .
4. `updateTpsFees()` then applies `total_tps_fees_delta = objUnitProps.tps_fee - tps_fee` to the address's `tps_fees_balance`, which can go deeply negative without any action or consent from the address owner [8](#0-7) .
5. Once negative, `validateTpsFee()` requires every subsequent unit from that address to pay enough `tps_fee` to close the deficit before it will even be accepted (non-OP addresses get a hard rejection, not merely a transient one, when `tps_fees_balance + objUnit.tps_fee*share < min_tps_fee*share`) [9](#0-8) .

This is the direct analog of the reported bug class: a fee parameter that a party other than the sender controls can be raised after the sender has already committed to (signed and broadcast) a transaction, and the sender has no way to cap the maximum fee they are ultimately willing to pay.

### Impact Explanation
An address (including one used to trigger or fund an AA, or a textcoin/asset-issuing address) can be retroactively charged a higher fee than it agreed to pay, driving its `tps_fees_balance` negative through no fault or action of its own. Because subsequent units from that address are rejected until the deficit is paid off, the address is effectively frozen from posting further units (including AA triggers or spending its own funds) until it pays down a fee it never explicitly authorized. This satisfies the "AA fund loss or freezing" / "network unable to confirm new units" impact bar: legitimate transactions from an affected address can be denied confirmation, and the address may be coerced into paying additional, unbudgeted fees to regain the ability to transact.

### Likelihood Explanation
`system_vote` is open to any address (weighted by stake) rather than restricted to a privileged admin role, so the precondition for the fee parameters to move between a user's broadcast and stabilization is realistically reachable without any special privilege — it only requires the network-wide tps-fee parameters to be voted upward during the (short but non-zero) window between broadcast and final stabilization, which is a normal, expected occurrence of the governance mechanism, not a contrived edge case. The exploitation does not require compromising any key; it only requires ordinary use of the existing on-chain voting feature while a victim unit is in flight.

### Recommendation
- When settling the "final" tps fee for a unit in `getFinalTpsFee()` / `updateTpsFees()` (storage.js:1238-1274), use the same system-var snapshot (i.e., value as of the unit's *last_ball_mci*, the value the poster actually relied on) that was used to compute the fee the poster agreed to pay, instead of the value at the unit's own eventual MCI.
- Alternatively, let the poster declare an explicit maximum acceptable `tps_fee`/multiplier in the unit, and refuse to apply an `actual_tps_fee` debit beyond that ceiling to the address's `tps_fees_balance`.
- If retroactive reconciliation is required for network accounting, cap the negative impact per address per settlement window, or require a governance-vote activation delay (analogous to a notice period) so any address with in-flight units is not penalized for parameter changes that occurred after it broadcast its unit.

### Proof of Concept
1. Address A composes and broadcasts unit U with `tps_fee` computed via `getLocalTpsFee()` against the current `base_tps_fee`/`tps_interval` at U's `last_ball_mci` [1](#0-0) .
2. Before U stabilizes, address B (any holder of bytes) posts and gets counted a `system_vote` raising `base_tps_fee` (or lowering `tps_interval`), which is accepted per the validation rules with no restriction to a privileged role [2](#0-1) .
3. When U's MCI stabilizes, `updateTpsFees()` calls `getFinalTpsFee(U)`, which reads the raised `base_tps_fee` at U's own (now-later) MCI rather than the value A locked in [4](#0-3) , producing `actual_tps_fee` far larger than `U.tps_fee`.
4. `total_tps_fees_delta = U.tps_fee - actual_tps_fee` is strongly negative and is written into A's `tps_fees_balances` [10](#0-9) .
5. Any subsequent unit A tries to post is rejected by `validateTpsFee()` until A pays enough extra `tps_fee` to cover the now-negative balance, even though A never agreed to or was warned about the fee increase [9](#0-8) .

function getFinalTpsFee(objUnitProps) {

async function getLocalTpsFee(conn, objUnitProps, count_units = 1) {
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	const base_tps_fee = getSystemVar('base_tps_fee', last_ball_mci); // unit's mci is not known yet
	const tps_interval = getSystemVar('tps_interval', last_ball_mci);
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_ball_mci);
	const tps = await getLocalTps(conn, objUnitProps, count_units);
	console.log(`local tps at ${objUnitProps.unit} ${tps}`);
	const tps_fee_per_unit = Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1));
	return count_units * tps_fee_per_unit;
}
