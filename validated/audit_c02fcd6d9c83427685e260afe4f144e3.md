### Title
Unvalidated route venues can attach unauthorized wallet-draining transfers to user swap authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts caller-supplied `swap` bytes and forwards them to the configured router without validating the contracts named inside the route. A malicious route can therefore place attacker-controlled pool code on the call stack, and that code can add a token transfer from the caller to the caller’s authorization tree. If the caller signs the simulation-produced tree without inspecting its child invocations, unrelated wallet-token balances can be transferred to the attacker while the requested lending strategy still settles normally.

### Finding Description
`swap_collateral` is an unprivileged strategy entrypoint taking an opaque `swap: Bytes` argument and requiring only owner or delegate authorization for the target account. [1](#0-0)  Its implementation authorizes the caller, withdraws the selected collateral, and passes the unmodified route into the shared swap helper. [2](#0-1)  `swap_tokens` forwards those bytes to `router.execute_strategy` inside the flash guard and afterward validates only the controller’s measured input spend and positive output receipt. [3](#0-2) 

The controller intentionally authorizes only one exact input-token transfer and grants no token allowance. [4](#0-3)  That protects the controller’s input transfer, but it does not constrain third-party code reached through the route from requesting additional authorization from the original caller. The project’s auth-tree regression test demonstrates that a rogue hop pool invoked below `swap_collateral` can call `wallet_token.transfer(alice, attacker, amount)`, causing the unauthorized wallet movement to be recorded as a child of Alice’s `swap_collateral` authorization. [5](#0-4) 

### Impact Explanation
A malicious venue can steal any wallet token held by the strategy caller, including assets unrelated to the lending position and exceeding the routed `amount_in`. The theft succeeds when the caller signs the poisoned authorization tree returned by simulation; the measured router output and post-strategy risk checks do not bound or detect the extra token movement. The same route-forwarding pattern is also reachable through `multiply`, `swap_debt`, and `repay_debt_with_collateral`, all of which accept caller-supplied swap bytes. [6](#0-5) 

### Likelihood Explanation
The attacker must induce the victim to submit or sign a transaction containing a malicious route. Unlike a standing-approval exploit, the rogue transfer does not execute under a benign authorization tree: enforcing-mode testing shows it is rejected unless the victim signs the added token-transfer child. [7](#0-6)  The practical risk remains significant because route bytes and nested authorization trees are opaque to many signing interfaces, while a malicious quote can preserve a plausible positive swap output so the lending operation appears successful.

### Recommendation
Restrict route venue contracts to a governance-approved allowlist rather than allowing arbitrary pool addresses in strategy routes. The allowlist should bind both the venue adapter and pool contract, and authorization-tree validation should additionally reject any unexpected child invocation under the caller’s strategy authorization. At minimum, wallets and transaction builders must decode the route and reject any authorization tree containing token movements other than the expected strategy input flow.

### Proof of Concept
1. Alice owns a lending account with supplied USDC and also holds a separate token `VICTIM_TOKEN` that the protocol never listed.
2. The attacker deploys a contract conforming to the selected venue’s expected pool calls. During its swap callback it executes `VICTIM_TOKEN.transfer(Alice, attacker, victim_balance)` and also returns enough `TOKEN_OUT` for the router’s measured-output checks.
3. The attacker constructs `swap` bytes whose route uses the rogue contract as a hop pool and supplies a plausible minimum output.
4. Alice submits `swap_collateral(caller=Alice, account_id, current=USDC, amount, new=ETH, swap=malicious_route)` after simulation. Simulation records the rogue `VICTIM_TOKEN.transfer(Alice, attacker, victim_balance)` as a child invocation beneath Alice’s controller authorization.
5. Alice signs the generated tree. The malicious pool transfers her entire unrelated wallet-token balance to the attacker, while the router’s output lets the collateral swap and account finalization continue. [8](#0-7)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
