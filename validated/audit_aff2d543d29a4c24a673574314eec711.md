### Title
Deleting or misconfiguring the `protocol_treasury_account` causes a deterministic chain-wide panic during epoch-boundary reward distribution - (File: `runtime/runtime/src/lib.rs`)

### Summary
This is the closest reachable analog to the C4 `RubiconMarket.feeTo` bug class: an account designated as a fee/reward *recipient* that becomes unusable (deleted / non-existent) causes the code path that pays it to hard-fail, and — unlike the ERC20 case where only `buy()` reverts for one caller — in nearcore this failure is deterministic protocol logic executed by every validator, which turns into a network-wide panic/chain stall rather than a mere per-transaction revert.

### Finding Description
At the start of every epoch, `Runtime::apply` invokes `update_validator_accounts` with a `ValidatorAccountsUpdate` that carries `protocol_treasury_account_id` whenever the genesis-configured protocol treasury account belongs to the shard being applied [1](#0-0) . Inside `update_validator_accounts`, if the treasury account did not already receive rewards through the `stake_info` path, the code does:

```rust
let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
    StorageError::StorageInconsistentState(format!(
        "Protocol treasury account {} is not found",
        account_id
    ))
})?;
``` [2](#0-1) 

If the treasury account does not exist in state at that moment — for example because its owner (who holds a full-access key to it, as it is a normal, non-staking named account, see the genesis setup in `add_protocol_account`) submitted a `DeleteAccount` action for it before the epoch boundary — this line returns `Err(StorageError::StorageInconsistentState(...))`, which is propagated as `RuntimeError::StorageError` out of `Runtime::apply` [3](#0-2) .

That error is caught in the caller `NightshadeRuntime::apply_chunk`/`process_state_update`, where the error-handling match distinguishes only two `StorageError` variants (`FlatStorageBlockNotSupported`, `MissingTrieValue`) as recoverable; every other `StorageError`, including `StorageInconsistentState`, falls into the catch-all branch that calls `panic!("{err}")`:

```rust
Err(e) => match e {
    Error::StorageError(err) => match &err {
        StorageError::FlatStorageBlockNotSupported(_)
        | StorageError::MissingTrieValue(..) => Err(err.into()),
        _ => panic!("{err}"),
    },
    _ => Err(e),
},
``` [4](#0-3) 

Because this reward-distribution logic is deterministic protocol code (not a malicious-input/validator-only code path — it's triggered purely by ordinary transaction-level `DeleteAccount` action submitted by whoever controls the treasury account's key), every node applying the epoch-boundary chunk for the shard containing the treasury account hits the identical panic. This mirrors the report's root cause (an owner-configurable fee/reward-recipient address becoming invalid, causing the code that pays it to fail) but is stronger in impact because nearcore state transition is fully deterministic and replicated: the panic isn't confined to one caller's transaction like the Solidity `buy()` revert — it crashes every node validating that shard, which stalls the chain.

### Impact Explanation
This is a chain stall / node panic caused solely by an unprivileged account action (deleting the protocol treasury account, which is not a validator and has an ordinary full-access key). It requires no malicious validator or network-layer behavior — only a signed `DeleteAccount` transaction from the account holder. The resulting `panic!` in `chain/chain/src/runtime/mod.rs` is hit identically by all nodes tracking that shard at the next epoch boundary where the treasury is due a reward, producing a consensus-wide halt rather than a localized failure. This satisfies the "chain stall" / "node panic" acceptance criteria.

### Likelihood Explanation
The likelihood depends on whether:
1. The account currently designated as `protocol_treasury_account` in genesis can, in practice, be deleted via a normal `DeleteAccount` action (i.e., it holds a full access key and has zero locked/staked balance, which is the case for a purely reward-receiving, non-validating account such as `treasury.near`/`near`).
2. No additional protocol-level protection exists elsewhere (not confirmed from available context) preventing deletion of the specific account referenced by genesis's `protocol_treasury_account` field.

I was not able to fully verify the exact preconditions of `action_delete_account` in `runtime/runtime/src/actions.rs` (the grep for `fn action_delete_account` matched the file but the follow-up `read_file` call failed due to a missing parameter, and no further tool calls were available). Based on `docs/RuntimeSpec/Fees/Fees.md`, `DeleteAccount` is a standard action available to any account holder and is only constrained by ordering rules (must be the last action) and possibly a staked/locked-balance check — not by any special-casing for the treasury account. Given the account is a plain named account funded purely with `amount` (no `locked` stake) as seen in `mainnet_genesis.json`'s `treasury.near` record [5](#0-4) , deletion by its key-holder appears technically feasible, making the likelihood non-trivial but unconfirmed without inspecting `action_delete_account`'s exact guard conditions.

### Recommendation
- In `update_validator_accounts` (`runtime/runtime/src/lib.rs`), do not treat a missing protocol treasury account as an unrecoverable `StorageInconsistentState`/panic condition. Handle it gracefully (e.g., skip crediting the reward, log a warning, or otherwise fail the specific validator-accounts-update step without halting the chain).
- Alternatively/additionally, prevent deletion of the account configured as `genesis_config.protocol_treasury_account` (special-case it in `action_delete_account` validation), since it is a protocol-critical recipient.
- Broaden the `apply_chunk` error classification in `chain/chain/src/runtime/mod.rs` so that predictable, input-driven storage inconsistencies (like a missing account expected to receive a reward) do not automatically panic the node, consistent with the "process gracefully" TODOs already present nearby for other `RuntimeError` variants.

### Proof of Concept
1. Deploy/observe a network where `genesis_config.protocol_treasury_account` is a plain named account with a full-access key and no locked stake (e.g., `treasury.near`).
2. The key holder submits a `DeleteAccount` transaction removing that account before the next epoch boundary.
3. At the first chunk of the new epoch, `epoch_manager.compute_stake_return_info`/reward calculation still designates this account as the treasury recipient and constructs a `ValidatorAccountsUpdate` with `protocol_treasury_account_id = Some(treasury_account)` [1](#0-0) .
4. `Runtime::apply` → `update_validator_accounts` calls `get_account(...)?.ok_or_else(...)` for the now-deleted account and returns `Err(StorageError::StorageInconsistentState(...))` [2](#0-1) .
5. `NightshadeRuntime::apply_chunk`'s catch-all branch executes `panic!("{err}")` for this error [4](#0-3) , crashing every node applying that shard's chunk — a deterministic, network-wide chain stall.
