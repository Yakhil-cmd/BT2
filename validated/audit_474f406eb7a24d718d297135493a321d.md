### Title
Non-deterministic oracle price reads for unstable data feeds in AA execution enable manipulation and node disagreement - ([File: data_feeds.js])

### Summary
`data_feed[[...]]` / `in_data_feed[[...]]` formulas evaluated inside Autonomous Agents can read oracle values from data-feed units that are **not yet stable**. The lookup for these unstable candidates is done against the node's local, receive-order-dependent in-memory cache (`storage.assocUnstableMessages`/`storage.assocUnstableUnits`) rather than against a causally-defined, deterministic view of the DAG tied to the trigger unit. This is the Obyte analog of UwuLend's oracle-manipulation bug class: a value that has not been finalized/settled is nevertheless trusted by the financial logic (an AA), letting an attacker post a favorable, still-unstable oracle reading right before/around the AA trigger to influence its outcome, and/or causing different nodes to compute different AA results for the same trigger.

### Finding Description
When an AA formula evaluates `data_feed`/`in_data_feed`, it calls `dataFeeds.readDataFeedValue()` / `dataFeeds.dataFeedExists()` with the AA flag set, which enables the “include unstable AA units” branch: [1](#0-0) 

Inside `readDataFeedValue`, when `bIncludeUnstableAAs` is true, the function scans `storage.assocUnstableMessages` — every unit the *local node happens to have already received* — and accepts any `data_feed` message from an address in `arrAddresses` whose `latest_included_mc_index` falls in `[min_mci, max_mci]`: [2](#0-1) 

Crucially, this check only verifies:
1. the author address matches the requested oracle address(es), and
2. the unit's `latest_included_mc_index` is within the requested mci window,

but it does **not** require the candidate unstable unit to be a causal ancestor of the AA trigger unit, nor does it require the set of unstable units considered to be identical across nodes. The population of `assocUnstableMessages` happens purely as a side effect of unit receipt/validation order: [3](#0-2) 

and is rebuilt from whatever is unstable at process start via a similarly receipt-order-dependent scan: [4](#0-3) 

AA triggers, on the other hand, execute deterministically at the moment their MCI becomes stable, driven by `markMcIndexStable` → `handleAATriggers`: [5](#0-4) [6](#0-5) 

Because "which unstable oracle units are known to me right now" is a function of local network propagation/catch-up timing rather than of the trigger unit's own causal history, two fully-honest, fully-validating nodes can have different `assocUnstableMessages` contents at the exact moment they execute the same AA trigger at the same MCI, and therefore compute different `data_feed[[...]]` results (different price, different `ifseveral`/candidate set, or `bAbortedBecauseOfSeveral` on one node but not another). This mirrors the DeFi bug class in the report: a value that has not gone through the protocol's finality/consensus process (there: on-chain settlement of DEX pool state; here: unit stabilization) is used directly to drive financial logic (borrow/liquidate there; AA responses/state here), and the value can be shaped in the narrow window before it is anchored.

### Impact Explanation
- **AA fund loss / freezing**: an AA that references a price/data feed for critical decisions (loan valuation, liquidation threshold, minting rate, etc.) can be driven by a value from a still-unstable unit that an attacker times to appear (or omits) around trigger processing, analogous to the price-window manipulation in the UwuLend hack.
- **Node disagreement on validity/stability of AA outputs**: since the unstable candidate set is not a deterministic, causally-bounded function of the trigger unit, different honest nodes can legitimately disagree on the AA's computed response (different state var updates, different bounce/non-bounce decisions, different response payment amounts) for the exact same trigger and MCI, undermining the "every node computes the same result" guarantee AAs are built on.

### Likelihood Explanation
Any AA author who uses `data_feed`/`in_data_feed` without pinning `min_mci`/`unstable_opts` tightly to already-stable data is exposed; this is the default, most common usage pattern shown throughout the test suite and documentation examples (see `data_feed[[oracles=..., feed_name=...]]` patterns used pervasively). The unstable-inclusion behavior is unconditionally enabled whenever the formula is evaluated in AA context (`bAA` passed straight into `unstable_opts`), so no special AA configuration is required to be exposed to this behavior — it is baked into the default engine path used by essentially every price-dependent AA.

### Recommendation
- Require unstable data-feed candidates used inside AA evaluation to be causally connected to the trigger unit's DAG view (e.g., only unstable units that are ancestors of the trigger's `last_ball_unit`/known parents) rather than any unit satisfying only an mci-window + author check.
- Alternatively, disable inclusion of unstable oracle units for AA `data_feed` evaluation by default and require an explicit, clearly-scoped opt-in (e.g., only "own address" data feeds, never third-party oracle addresses) to avoid nodes diverging on which unstable units are visible.
- Add regression tests where a data-feed unit is posted "late" (after a node begins processing a trigger versus another node that has already received it) to detect divergent AA results across differently-synced nodes.

### Proof of Concept
1. An AA `X` computes a decision using `data_feed[[oracles=ORACLE, feed_name='price']]` inside its trigger handling logic, with the default `unstable_opts` behavior enabled by `bAA=true`.
2. Oracle address `ORACLE` posts a `data_feed` unit `U1` with a favorable price. `U1` is not yet stable (its MCI hasn't been finalized) but has a `latest_included_mc_index` inside the AA's evaluation window.
3. Node A has already received and processed `U1` (in `storage.assocUnstableMessages`) by the time it executes the AA trigger at MCI `M`; Node B, due to network propagation delay, has not yet received `U1` at the same point in time.
4. Both nodes stabilize MCI `M` and run `handleAATriggers`/the AA formula for the same trigger unit; Node A's `readDataFeedValue` finds `U1` in `assocUnstableMessages` and uses its price, while Node B does not find it (falls back to an older/stable value or `ifnone`).
5. The two nodes produce different AA responses (different payment amounts / state variable updates) for the identical trigger unit and MCI — demonstrating both the price-manipulation surface (attacker times `U1`'s propagation) and the underlying node-disagreement risk. [7](#0-6) [3](#0-2)

async function stabilizeMci(mci) {
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const batch = kvstore.batch();
