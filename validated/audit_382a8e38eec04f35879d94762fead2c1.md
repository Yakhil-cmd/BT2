### Title
Webhook signature verification keys on `repository.owner.login` while event handlers act on `repository.full_name` from the same unauthenticated payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, a value read directly out of the untrusted, unsigned-at-that-point JSON body. Once verification passes, the same untrusted payload is handed to event handlers (e.g. `PushHandler`) which resolve the target `Repository`/`Stack` using a *different* field of the same payload, `repository.full_name`. Nothing ties the organization whose secret validated the signature to the repository that the handler subsequently writes to.

### Finding Description
`verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple, independently configured GitHub Apps/organizations in a single instance, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications"). [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the raw payload to handlers keyed by event type:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler resolves the target repository/stack from `repository.full_name`, not from `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` uses this to trigger `Stack#sync_github` for every matching stack:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

Because `repository.owner.login` (used to pick the signing secret) and `repository.full_name` (used to pick the repository being acted on) are two independent, attacker-controlled fields of the same JSON body, an attacker who legitimately controls (or is a collaborator on) a GitHub organization/App configured in this Shipit instance can compute a valid HMAC using *their own* organization's `webhook_secret`, while setting `repository.full_name` to point at a completely unrelated organization/repository also hosted on the same instance. Nothing cross-checks that the app whose secret validated the request actually owns the repository referenced for processing.

This is structurally the same class of bug as the reported Aave `_getAssetIndex` issue: a value used to gate/authorize an operation (`lastUpdateTimestamp` / here, `repository.owner.login`) is not kept consistent with the value that is actually acted upon (`periodStartTimestamp`-derived period / here, `repository.full_name`), because the code assumes the two are always in lock-step without enforcing it, which only broke down once configurations diverged (multi-org vs single-org).

### Impact Explanation
An attacker with legitimate write access to a GitHub organization/App configured on the Shipit instance can forge webhook events (e.g. `push`) that are correctly signed with their own org's secret but whose `repository.full_name` names a stack belonging to a different organization also hosted on the instance. This lets them trigger `Stack#sync_github(expected_head_sha:)` for a repository/stack they have no legitimate access to, which can enqueue `GithubSyncJob` processing an attacker-chosen `expected_head_sha`. Depending on the victim stack's continuous-deployment configuration, this can cause an unauthorized deploy of a chosen (but pre-existing) commit SHA, i.e. cross-organization interference in the deploy pipeline without ever needing access to the victim's GitHub webhook secret or repository. This maps to the "unauthorized deploy" / "cross-repository writes" high-severity bucket.

### Likelihood Explanation
Requires: (1) the operator to configure Shipit with more than one GitHub organization/App (a documented, supported configuration), and (2) the attacker to have legitimate push/webhook-delivery capability for at least one of the configured organizations (i.e., they can get GitHub to deliver a webhook signed with that org's secret, or know that secret through legitimate collaboration). Given that condition, forging the `repository.full_name` field requires no additional privilege — it's just a value in the JSON body, which is never validated against the signing organization. This is not exploitable in single-organization deployments (the common case), which lowers overall likelihood, but is a real design gap whenever the multi-org feature is used as documented.

### Recommendation
After successfully verifying the signature for `repository_owner`, cross-check that `repository_owner` matches the actual owner of `repository.full_name` (or, more robustly, only accept webhooks whose payload repository owner exactly equals the organization key that produced a valid signature) before dispatching to any handler. Alternatively, bind webhook secrets to installation IDs communicated out-of-band (e.g. via the `X-GitHub-Hook-Installation-Target-ID` header) rather than trusting payload body fields for secret selection, and independently verify that the resolved `Repository`'s configured organization equals the organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two orgs, `OrgA` (attacker-controlled/legit) and `OrgB` (victim), each with distinct `webhook_secret`s, both hosting stacks in the same Shipit instance.
2. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-existing-commit-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over the raw body (which they know, since they legitimately administer `OrgA`'s GitHub App/webhook).
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`) and validates successfully against `OrgA`'s secret.
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name('OrgB/victim-repo')` — a repo unrelated to the signing organization — and calls `stack.sync_github(expected_head_sha: '<victim-existing-commit-sha>')` on `OrgB`'s stack, which can trigger downstream continuous-deployment logic for a repository the attacker never had access to.
