### Title
Merkle Tree Duplicate-Leaf Malleability Enables Forged "in merkle" / `is_valid_merkle_proof` Membership Proofs - (File: merkle.js)

### Summary
`merkle.js` builds and verifies Merkle proofs using the classic "duplicate the last node when the level has an odd length" padding rule [1](#0-0) , the same construction responsible for the well-known Bitcoin CVE-2012-2459 Merkle-tree malleability bug. `verifyMerkleProof` never re-derives or checks the claimed tree height/leaf-count against the `index`/`siblings` supplied by the caller [2](#0-1) , so a proof describing a smaller/duplicated tree shape can validate against a root that was actually produced by a different (larger, distinct) set of elements — analogous to the BIND bug where an RRSIG with fewer labels than the real zone is accepted and used to synthesize a wildcard answer for the wrong (broader) scope.

### Finding Description
`getMerkleRoot`/`getMerkleProof` pad odd-length levels by hashing the last element with itself (`hash2_index = (i+1 < arrHashes.length) ? (i+1) : i`) [3](#0-2) [4](#0-3) . `verifyMerkleProof` walks the sibling array supplied entirely by the untrusted caller, without any check that `siblings.length` matches the real depth of the committed tree, or that `index` is consistent with the true cardinality of the leaf set [5](#0-4) .

Because of the duplicate-padding rule, a root computed over N real (distinct) leaves is identical to the root that would be computed over N+1 leaves where the last leaf is literally duplicated. This lets an attacker who knows (or controls) the published root construct an alternate, differently-shaped proof for an element/index that was never actually part of the original committed set, yet still verifies successfully — the same "shorter/mismatched scope still validates" bug class as the BIND advisory.

This directly reaches two attacker-controlled oscript paths:
- Address definition `'in merkle'`, where an untrusted `signing_path` proof is checked purely by `merkle.verifyMerkleProof(element, proof)` and then matched to a value published via a data feed [6](#0-5) . This lets a unit poster satisfy a shared-address/AA authentication condition by supplying a self-consistent but structurally-ambiguous proof.
- AA formula `is_valid_merkle_proof(element, proof)`, callable from any AA trigger, where `proof` (including `index` and `siblings`) is fully attacker-supplied and only self-consistency (`hash chain -> root`) is checked, with no bound on `index` or verification that it matches the real size of the set the root was built from [7](#0-6) .

Neither call site validates that the number of siblings (tree depth) or the leaf index is consistent with the true, previously-attested element count for the root being checked, so the duplicate-padding malleability is fully exploitable by anyone who can post a unit or AA trigger referencing a known root (e.g., a root previously published in a data feed or computed/stored by an AA).

### Impact Explanation
Where a data feed root or AA-stored root is used as a whitelist/authorization boundary (e.g., "address is a member of set X" via `'in merkle'`, or an AA verifying inclusion of a value/address in a committed batch via `is_valid_merkle_proof`), an attacker can forge membership for an element that was never part of the true committed list, or double-count a single element as if it appeared at another index. This can be used to bypass an `'in merkle'` authentifier condition to unlock AA funds or a shared/multisig address the attacker does not legitimately control, or to make an AA accept a bogus batch item, resulting in unauthorized AA fund loss or acceptance of unintended inputs — matching the "concrete unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
Any unprivileged unit poster can trigger this: `is_valid_merkle_proof` is reachable from any oscript/AA trigger, and `'in merkle'` is a standard authentifier op reachable by anyone who posts a unit against a definition using it. Exploitation only requires knowledge of one legitimately published root and its construction (which is often public, e.g. published via a data feed), not a SHA-256 break — it exploits the deterministic duplicate-padding rule, which is a structural design flaw rather than a cryptographic weakness.

### Recommendation
- Bind the Merkle-proof depth/leaf-count to an explicitly-committed tree size (e.g., include and check `num_leaves` in the serialized proof and reject if `index >= num_leaves` or if the derived depth from `num_leaves` doesn't match `siblings.length`).
- Use a padding scheme that doesn't create structural collisions (e.g., RFC 6962-style domain-separated leaf/node hashing, and refuse duplication of the last node — instead carry the odd node up unhashed, or otherwise fix the tree shape per length).
- Add explicit bounds and shape validation in both `definition.js`'s `'in merkle'` handler and `formula/evaluation.js`'s `is_valid_merkle_proof` before trusting `verifyMerkleProof`'s boolean result.

### Proof of Concept
1. Oracle/AA publishes `root = getMerkleRoot([A, B, C])`. Internally this pads by hashing `C` with itself at the last level, i.e. `root = H(H(hA,hB), H(hC,hC))`.
2. This is bit-for-bit identical to the root that a 4-leaf set `[A, B, C, C]` (containing a real duplicate of `C`) would produce.
3. An attacker who is not authorized as the 4th/duplicate entry constructs a `proof` object with `index=3` and the appropriate sibling hashes (`hC`, `H(hA,hB)`), and calls `is_valid_merkle_proof(C, proof)` (or supplies it as the `'in merkle'` authentifier at `path`).
4. `verifyMerkleProof` walks the supplied siblings and confirms `the_other_sibling === proof.root`, returning `true`, even though the true committed set only ever contained `C` once at index 2 and the attacker's claimed "4th distinct slot" never existed — allowing forged/duplicated inclusion proofs against the legitimately published root [5](#0-4) .

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
