### Title
Cross-repository status injection via unbound `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by SHA, with no check that the commit's owning repository/stack matches the `repository.full_name` carried in the webhook payload. Every `PullRequest::*` handler binds action to a repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new`, so a mismatched repo becomes a safe no-op; `StatusHandler` has no equivalent binding, so a mismatched repo can still mutate a real `Commit` belonging to a stack the attacker does not own, as long as the SHA collides.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`params.repository.full_name == <owning repository of the resolved Commit>` — this is enforced for `PullRequest::OpenedHandler` (and `Closed/Labeled/Reopened/Unlabeled`) via [1](#0-0) 
but is **never checked** in `StatusHandler`: [2](#0-1) 

`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` — a global, unscoped query across the entire `commits` table, not filtered by `Repository`, `Stack`, or `params.repository.full_name` at all. `Handler` (the base class) even defines a `repository_name`/`stacks` helper that scopes to the payload's repository [3](#0-2) , but `StatusHandler` doesn't use it.

Root cause: git commit SHAs are content-addressed and therefore collide across repositories/forks whenever the underlying tree/parent/commit metadata is identical (e.g., an attacker forks a public victim repo, or simply already knows a public commit SHA belonging to the victim's tracked branch). The attacker:
1. Owns/controls a GitHub repo (`attacker/repo`) with a validly-configured Shipit webhook, so `WebhooksController#verify_signature` succeeds using the attacker's own org secret (`Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker's own payload) — this signature check says nothing about which commit/stack the payload can affect.
2. Sends a `status` event whose `repository.full_name` is `attacker/repo` but whose `sha` is a real, victim-owned commit SHA (obtainable if the SHA is public, or by forking the victim repo so an identical commit exists in the attacker's own history).
3. `StatusHandler.process` finds the victim's `Commit` row by SHA alone and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `Status` (state/context/target_url/description) onto the victim's stack's commit [4](#0-3) .

Contrast: `PullRequest::OpenedHandler#process` would, under the identical trick (foreign `repository.full_name`, PR number colliding with nothing in the attacker's non-existent-in-Shipit repo), resolve `repository` to `Shipit::NullRepository.new` and become a no-op because `NullRepository` returns `review_stacks_enabled == false`/empty scopes, so `provision?` is false and nothing is created [5](#0-4) . `StatusHandler` has no such NullRepository/binding guard, so the identical "wrong repo" trick is not neutralized — it actively succeeds against a real row.

Existing guards do not prevent this: `verify_signature` only authenticates that *some* repo owner's secret matches the raw payload bytes — it never restricts which SHA/commit the payload's `sha` field is allowed to reference [6](#0-5) . The `ExplicitParameters` schema for `StatusHandler` only validates types (`sha: String`, `state: String`, etc.) [7](#0-6) , not repository ownership of the referenced commit.

### Impact Explanation
An attacker with no relationship to the victim's stack can write arbitrary `Status` rows (state, context, description, target_url) onto a victim's tracked commit. Since `Commit#deployable?`/`#blocked?` and continuous delivery gating (`schedule_continuous_delivery`, `stack.schedule_merges`) key off status state [8](#0-7) [9](#0-8) , injecting a fabricated "success" status for a required CI context can make a commit `deployable?`/mergeable that should not be, or spoof "failure" to block a legitimate deploy — a payload for one repository mutating another's stack/commit. This is repeatable against any Shipit-tracked commit whose SHA the attacker can predict or reproduce (trivial for public forks), across any number of victim stacks, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy".

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: own any GitHub repo/org with a Shipit-registered webhook (or one already integrated), know or reproduce a target commit SHA (public repos make this trivial via fork), and send one `status` webhook. No Shipit session, API token, or GitHub org membership on the victim's side is required. This is fully repeatable and does not depend on any race condition or timing.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository named in the payload, mirroring the pull_request handlers' `Repository.from_github_repo_name(...) || NullRepository` pattern — e.g. resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)`, return early (no-op) if `nil`, and constrain `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or equivalent join through `stacks`) instead of an unscoped `Commit.where(sha:)`.

### Proof of Concept
minitest plan (no live GitHub, uses fixtures):
1. `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`-style test: build `params` with `repository.full_name = "attacker/unrelated-repo"` and a PR number that does not exist for that (non-existent) repository; call `PullRequest::OpenedHandler.call(params)`; assert `assert_no_difference('Shipit::ReviewStack.count')` — confirms `NullRepository` makes the mismatch inert.
2. New test in `test/models/shipit/webhooks/handlers/status_handler_test.rb`:
   - `victim_commit = shipit_commits(:first)` (belongs to stack `shipit`, some fixed `sha`).
   - Build a `status` payload with `repository.full_name = "attacker/unrelated-repo"` (a repo not present/owned in Shipit) and `sha = victim_commit.sha`, `state: "success"`.
   - `assert_difference('victim_commit.statuses.count', 1) { Shipit::Webhooks::Handlers::StatusHandler.call(payload) }` — demonstrates the mismatched-repo payload still mutates the victim's commit, unlike the pull_request-family no-op in step 1.
