### Title
Accrued RAY-value overflow permanently freezes an oversized lending market - (File: `common/src/rates/simulate.rs`)

### Summary
**Severity: High.** A sufficiently large market can make `borrowed * borrow_index` or `supplied * supply_index` exceed `i128::MAX` during interest accrual, causing every subsequent market operation to revert before users can repay, withdraw, liquidate, or clean bad debt.

### Finding Description
The fixed-point market totals are stored as RAY-scaled shares and multiplied by RAY-scaled indexes during each accrual step. [1](#0-0)  `accrue_step` computes both unscaled totals before applying the borrow-index ceiling or calculating rewards. [2](#0-1)  Those conversions call `Ray::mul`, which raises `MathOverflow` when the resulting RAY value cannot fit in `i128`. [3](#0-2) 

Every pool mutation loads the market through `synced_market`, which executes `interest::global_sync` before the requested action. [4](#0-3)  `global_sync` applies all elapsed accrual chunks before committing the market. [5](#0-4)  Consequently, once the accrued value crosses the representable range, the failing multiplication is encountered even by risk-reducing operations.

An unprivileged user can create the prerequisite state using only public controller calls: `supply` to fund the target market, `supply` collateral on a second owned account, `borrow` the target asset to sustain high utilization, and later `update_indexes` to trigger accrual. [6](#0-5) [7](#0-6) 

### Impact Explanation
This permanently freezes all funds and credit operations in the affected market unless a privileged code migration changes the accounting logic. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot clear distressed debt, and bad-debt cleanup cannot proceed because each path synchronizes the overflowing market first. [8](#0-7) 

The repository’s own harness reproduces the condition: an 18-decimal billion-token market at 98% utilization eventually fails `update_indexes` with `MATH_OVERFLOW` before the borrow-index cap is reached, after which both withdrawal and repayment fail with the same error. [9](#0-8) 

### Likelihood Explanation
Likelihood is configuration- and liquidity-dependent. The attacker must control or borrow an exceptionally large fraction of a listed asset, and the market’s supply cap, borrow cap, collateral pricing, token supply, and utilization settings must permit the required exposure. If those conditions exist, however, no privileged action is needed after establishing the oversized high-utilization book; ordinary `supply`, `borrow`, and `update_indexes` calls suffice. [6](#0-5) [7](#0-6) 

### Recommendation
Bound or safely handle the unscaled RAY value before multiplication rather than allowing accrual to panic. At a minimum:

- Cap admitted scaled supply/debt at `i128::MAX / MAX_*_INDEX_RAY`, accounting for revenue shares added later.
- Detect an impending value overflow in `accrue_step` and clamp accrual at a safe index while preserving an explicit recovery path for repayments and withdrawals.
- Add an emergency settlement path that can burn positions without first computing the overflowing aggregate, or otherwise permit surgical repayment/withdrawal after the cap is reached.
- Enforce caps using the maximum reachable index, not the current index, since `calculate_scaled_cap` can admit a book that later becomes unrepresentable. [10](#0-9) 

### Proof of Concept
The existing regression demonstrates the complete path:

1. Create an 18-decimal market and collateral market.
2. Supply `1_000_000_000 * 10^18` base units of the target asset.
3. Supply sufficient collateral and borrow 98% of the target market.
4. Advance time and invoke public `update_indexes`.
5. Accrual fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
6. Subsequent `withdraw` and `repay` calls also fail with `MATH_OVERFLOW`. [9](#0-8)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
