### Title
Global, unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a genuinely-signed webhook from an attacker's own repository mutate a victim commit's status and unblock deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no `stack_id`/`repository_id`/`repository.full_name` scoping, then calls `commit.create_status_from_github!(params)` on every match across the entire install. Because `WebhooksController#verify_signature` only proves the payload came from GitHub for *some* organization the attacker legitimately controls, and does not bind the payload's `repository.full_name` to the `sha` it carries, an attacker who can make GitHub emit a real `status` event referencing a sha that also exists in a victim's tracked stack (e.g. by forking the victim's public repository, which preserves identical commit SHAs for shared history) can flip a `blocking` status on the victim's commit and clear `Commit#blocked?`, unblocking `Stack#trigger_continuous_delivery`.

### Finding Description
The binding that should hold for every commit `StatusHandler` mutates is:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')`

It does not hold. `StatusHandler#process` is: [1](#0-0) 
which does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack scoping at all - `params` (the `context`, `state`, `description`, `target_url`) is applied verbatim to any row in the `commits` table sharing that sha, regardless of which repository the row's stack belongs to.

`WebhooksController#verify_signature` only checks that the HMAC signature matches the webhook secret configured for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body (`params.dig('repository','owner','login')`): [2](#0-1) [3](#0-2) 
and `GitHubApp#verify_webhook_signature` is a pure org-level HMAC check with no relation to the `sha`/`repository.full_name` pairing inside the payload: [4](#0-3) 

This proves the signature check authenticates "this event genuinely came from GitHub for organization X," not "this sha genuinely belongs to repository X." An attacker who legitimately owns any repository registered with Shipit (their own fork or unrelated project under an org Shipit is configured for) can trigger a real `status` webhook (e.g. via the GitHub Statuses API on a commit they can write to) whose `sha` collides with a commit tracked in a completely different stack/repository - trivially achievable by forking a victim's public repository, since forked commits retain byte-identical SHAs for unmodified history. GitHub will sign this event correctly for the attacker's own org, `verify_signature` passes, and `StatusHandler` then blindly walks every `Commit` row with that sha across the whole Shipit install.

Once `create_status_from_github!` runs on the victim's commit, `Commit#blocked?`'s underlying signal changes: [5](#0-4) 
because `blocking?` is derived from the latest `status`/`check_run` state on that commit row via `Status::Group.compact`: [6](#0-5) 
An attacker sending `state: success` for the same `context` used by the victim's blocking status can override/replace it and drop `blocked?` to `false`, which feeds into `deployable?` and continuous-delivery scheduling.

None of the existing guards catch this: `verify_signature` validates org-level HMAC only (not repo/sha binding); `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema (`params do ... end` in `StatusHandler`) validates shape, not tenancy; there is no `Repository`/`Stack` scoping clause anywhere in the query.

### Impact Explanation
A single unprivileged webhook request from an attacker's own (Shipit-registered) repository can silently mutate a `Status` record belonging to a commit in a victim's stack, altering `Commit#blocked?`/`deployable?` and potentially unblocking `stack.trigger_continuous_delivery`, causing an unauthorized deploy to proceed on a repository the attacker never authenticated against. This is a cross-tenant write: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" - matching the Critical impact category. The attack is repeatable against any commit sha the attacker can reproduce (trivial for forks of public repos, or any repo sharing history/cherry-picked commits with the target), and scales across every stack in the Shipit instance since the lookup has zero tenancy boundary.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository registered with Shipit under an organization for which a webhook secret is configured (a normal, low-privilege prerequisite for any team onboarding a project), and (b) a commit sha that also exists in the victim's tracked stack, which is straightforward to obtain by forking a public target repository (shared history yields identical SHAs) or by cherry-picking/rebasing commits to reproduce identical content+parent+author+timestamp. No Shipit session, API token, or GitHub App secret is required beyond what the attacker already legitimately holds for their own repo. This is fully repeatable and requires no timing race or privileged access.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other webhook handler using bare `sha` lookups) by the repository identified in the payload, e.g. join through `Stack`/`Repository` and filter `commits.joins(stack: :repository).where(sha: params.sha, repositories: { full_name: params.dig('repository','full_name') })`, enforcing the `commit.stack.repository.full_name == payload.dig('repository','full_name')` invariant before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new/extended test)
test "status webhook from an unrelated repository cannot clear another stack's blocking status" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = create_stack(repository: create_repository(full_name: 'attacker/unrelated'))

  shared_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')
  victim_commit.statuses.create!(state: 'pending', context: 'ci/build', stack: victim_stack) # blocking

  assert victim_commit.reload.blocked?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/build',
    'repository' => { 'full_name' => attacker_stack.repository.full_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  # Broken binding demonstrated: victim_commit.stack.repository.full_name != payload['repository']['full_name']
  refute_equal victim_stack.repository.full_name, payload['repository']['full_name']
  refute victim_commit.reload.blocked?, "attacker-controlled repository was able to clear the victim commit's blocking status"
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
