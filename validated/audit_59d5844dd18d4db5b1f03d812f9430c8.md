### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` rows purely by matching the raw `sha` string across the *entire* `commits` table, with no filter on the `repository` the webhook payload claims to originate from. Because `Commit` rows are only unique per `(sha, stack_id)` and not globally unique on `sha`, a status legitimately signed for repository A can be written onto a `Commit`/`Status` row that belongs to a completely different stack/repository B, corrupting `Commit#status`, `#deployed?`, `#deploy_failed?` for stack B.

### Finding Description
The claimed binding is: `Status row consulted by Stack(B)#last_deployed_commit / Commit(B)#status` ⇔ `authorized_by(repository_B.webhook_secret)`.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the request signature matches the secret of `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-influenced JSON body (`params.dig('repository','owner','login')`). This proves the request came from *some* authenticated GitHub org/App installation — it proves nothing about which `Commit`/`Stack` rows the payload is allowed to mutate.
2. `Shipit::Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This performs a bare `sha` lookup with **no scoping to a repository or stack at all**. It never consults `params.dig('repository', 'full_name')` to restrict which commits/stacks may be updated.
3. `Commit` has `belongs_to :stack`, and the schema enforces uniqueness only on the composite index `["sha", "stack_id"]` (`test/dummy/db/schema.rb:85`, `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`) — i.e., the same sha string is explicitly allowed, by design, to exist simultaneously across many different stacks/repositories (this is normal for forks/mirrors sharing git history, or for multiple stacks tracking related repos).
4. `Commit#status` (`app/models/shipit/commit.rb:304-306`) is `Status::Group.compact(self, statuses_and_check_runs)`, and `Commit#deployed?`/`#deploy_failed?` (lines 308-314) as well as `Stack#should_delay_continuous_delivery?`/`#next_commit_to_deploy` all consult these `Status` rows without ever re-verifying which repository authored them.
5. Contrast with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-16`), which correctly scopes to `stacks.not_archived.where(branch:)` — i.e., resolves affected stacks through the controller's already-verified organization context before touching any row. `StatusHandler` has no equivalent scoping.

Exploit flow: an attacker controls (or triggers CI on) some repository A that is legitimately connected to Shipit (a stack they administer, or any repo where the installed GitHub App can emit a validly-signed `status` event for org A). If a commit sha also exists as a `Commit` row for an unrelated stack B (trivially achievable because forked/mirrored repositories share identical commit shas for their common history, and Shipit's schema explicitly permits the same sha across many stacks), the attacker fabricates/controls the status content (`state`, `description`, `target_url`, `context`) for that shared sha on repo A. GitHub delivers a webhook to `/webhooks` with `X-Hub-Signature` valid for org A. `verify_signature` passes (correctly, for org A). `StatusHandler#process` then matches **all** `Commit` rows with that sha, including stack B's row, and calls `commit.create_status_from_github!(params)` on it — writing a `Status` record under `stack_id = B` that was never authorized by repository B's webhook_secret.

Existing guards do not stop this: `verify_signature` validates org A's secret only, `drop_unhandled_event`/`check_if_ping` are irrelevant, `ExplicitParameters` schema only validates payload shape (sha/state/etc.), and there is no model validation tying a `Status`'s `stack_id` to the `repository` named in the webhook payload.

### Impact Explanation
A poisoned `Status` row for stack B changes `Commit#status`/`#deployed?`/`#deploy_failed?`, which are read by `Api::CommitsController#index` (`stack.commits.reachable.includes(:statuses)`) and used by `Stack#deployable?`/`#next_commit_to_deploy`/`#should_delay_continuous_delivery?` to gate continuous delivery and by `Api::DeploysController#create` (`param_error!(:require_ci, ...) unless commit.deployable?`). This can (a) falsely mark a commit as CI-green, enabling an unauthorized deploy of stack B commits that never actually passed CI on repo B, or (b) falsely mark a commit failed, disrupting stack B's legitimate deploys — a payload from one repository mutating another repository's stack/commit state, matching the "Critical" impact category (unauthorized deploy triggered from a forged cross-tenant write). This is repeatable against any pair of stacks that happen to share a commit sha (most reliably via forks/mirrors of the same upstream), and is not limited to a single victim.

### Likelihood Explanation
Preconditions: attacker needs (a) a repository connected to a real, validly-signed GitHub status webhook flow into this Shipit instance (either their own tracked stack, or any repo under an org whose webhook_secret they can trigger legitimate events from), and (b) a commit sha that is also present as a `Commit` row on the victim stack — most realistically achieved by forking/mirroring the victim's repository so that shared ancestor commits carry identical shas in both stacks' `commits` tables. No Shipit secrets, sessions, or API tokens are required; the attacker only needs ordinary control over a GitHub repository/CI they already own. This is inexpensive and repeatable at will (just re-post a status).

### Recommendation
Scope `StatusHandler#process` (and equivalently `CheckSuiteHandler`/`CheckRunHandler` if they share this pattern) to the repository named in the webhook payload, e.g. resolve the stack(s) via `Stack.joins(:repository).where(repository: { owner: ..., name: ... })` (mirroring `PushHandler`'s use of `stacks`) and only update `Commit` rows that belong_to those stacks, instead of a bare `Commit.where(sha:)` across the whole table. Additionally, `Commit#sha` uniqueness/status write logic should require repository/stack context to be passed and checked at write time.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for repo A does not affect a Commit belonging to a different stack/repo B, even with matching sha" do
  stack_a = shipit_stacks(:shipit)          # repo A, attacker-controlled/legit
  stack_b = shipit_stacks(:cyclimse)        # repo B, victim, unrelated repository

  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared", authored_at: Time.now, committed_at: Time.now)
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared", authored_at: Time.now, committed_at: Time.now)

  before_state = commit_b.reload.status.state

  # Webhook validly signed for repo A's org (verify_signature passes for org A only)
  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: "success", context: "ci/forged", description: "forged", created_at: Time.now.iso8601
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.call(params.to_h)

  commit_b.reload
  # BINDING CHECK: commit_b (stack B) status must remain unchanged by a status
  # authorized only by repo A's webhook_secret.
  assert_equal before_state, commit_b.status.state,
    "Status for stack B's commit was mutated by a webhook only authorized for repo A"
end
```
This demonstrates the equality `Status(stack_b.commit).authorized_by == repository_b.webhook_secret` is violated: the status is written despite being authorized only by `repository_a.webhook_secret`.
