### Title
Division-by-Zero Panic in `consolidatedNode.Split` When Proposer Has Zero CN and CL Staking Amounts Halts Block Finalization — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidatedNode.Split` divides by `totalAmount = cnAmountBig + clAmountBig` without a zero-guard. When a proposer's CN staking contract holds 0 KAIA **and** its CLRegistry pool holds 0 WrappedKaia, `totalAmount` is zero and Go's `big.Int.Div` panics. The panic fires inside `specWithProposerAndFunds` / `specWithProposerAndFundsFlex` during block finalization, crashing every node that processes the block and halting the chain.

---

### Finding Description

**Root cause — `kaiax/staking/staking_info.go` lines 169–187:**

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)   // ← panics when totalAmount == 0
    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

`Split` is called from two proposer-reward paths that carry **no guard on the combined staking total**:

**`specWithProposerAndFunds` — `kaiax/reward/impl/getter.go` lines 622–637:**

```go
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase { continue }
    if cn.CLStakingInfo == nil { break }          // only nil-check, no amount check
    cnAmount, clAmount := cn.Split(proposer)      // ← panics if both amounts are 0
    ...
}
```

**`specWithProposerAndFundsFlex` — `kaiax/reward/impl/getter.go` lines 572–587** has the identical pattern.

By contrast, the staker-reward paths (`assignStakingRewards` line 516, `assignStakingRewardsFlex` line 438) are safe: they gate on `cnTotalStakingAmount > minStake` or `amount > threshold` before calling `Split`, so `totalAmount` is always positive there.

**State that triggers the panic:**

1. A validator is registered in AddressBook whose staking contract holds 0 KAIA → `cn.StakingAmount = 0` (after the `/KAIA` division in `parseCallResult` line 287).
2. The same validator is registered in CLRegistry with a pool whose WrappedKaia balance is 0 → `cn.CLStakingInfo.CLStakingAmount = 0` (line 299).
3. `consolidateNodes` attaches the non-nil `CLStakingInfo` to the node (line 157), so `cn.CLStakingInfo != nil` is true.
4. The validator is selected as block proposer → `specWithProposerAndFunds` calls `cn.Split(proposer)` → `totalAmount = 0` → **panic**. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

---

### Impact Explanation

`specWithProposerAndFunds` / `specWithProposerAndFundsFlex` are called during `FinalizeState` for every block under the Prague (KIP-226) and Osaka (Flex) reward rules. A panic there is unrecovered and crashes the node process. Because every honest node executes the same deterministic block, **all nodes crash simultaneously** when they reach the affected block. The chain halts; no further blocks can be produced or imported until the software is patched and nodes are restarted. This is an invalid state transition / consensus divergence on all honest nodes.

---

### Likelihood Explanation

After the Prague hardfork, CLRegistry is active. A validator can legitimately have:
- A staking contract with 0 KAIA balance (e.g., not yet funded, or fully withdrawn — permissioned validators remain in the council regardless of staking amount before the Permissionless hardfork).
- A CLRegistry entry whose pool has 0 WrappedKaia balance (e.g., registered before liquidity is deposited).

Both conditions can arise naturally during validator onboarding or after a full withdrawal. The validator will eventually be selected as proposer (round-robin or weighted-random policy), at which point the panic fires deterministically for every node on the network. No adversarial action is required beyond the normal validator lifecycle. [5](#0-4) [6](#0-5) 

---

### Recommendation

Add a zero-total guard inside `Split` before dividing:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    cnAmountBig := big.NewInt(int64(c.StakingAmount))
    clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)

    // Guard: if both amounts are zero, all reward goes to CN (no CL split).
    if totalAmount.Sign() == 0 {
        return amount, big.NewInt(0)
    }

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)
    cnAmount := new(big.Int).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

Additionally, `specWithProposerAndFunds` and `specWithProposerAndFundsFlex` should defensively skip the CL split when `cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount == 0`, consistent with the staker-reward paths that already require a positive excess before calling `Split`. [7](#0-6)
