### Title
Unpermitted environment variables can be injected via rollback — `Deploy#build_rollback` skips `filter_rollback_envs` (`app/models/shipit/deploy.rb`)

### Summary
Every path that creates a `Task`/`Deploy` in this engine sanitizes user-supplied `env` against the `shipit.yml`-declared variable whitelist (`deploy.variables`, `rollback.variables`, or a task's own `variables`) before it is persisted and later merged into the shell environment used to run deploy/rollback/task steps. `Stack#build_deploy` calls `filter_deploy_envs`, `Stack#trigger_task` calls `definition.filter_envs`. `Deploy#build_rollback`, however, stores `env.to_h` verbatim with no call to `EnvironmentVariables.permit`/`stack.filter_rollback_envs`, breaking the binding "environment key permitted (by `shipit.yml` `rollback.variables`) equals environment key spawned (in the task's shell process)".

### Finding Description
`Deploy#build_rollback` (lines 90-102 of `app/models/shipit/deploy.rb`) constructs a `Rollback` with `env: env.to_h` — no whitelist filtering. This is used both by the API-facing `Deploy#trigger_rollback` (called from `Shipit::Api::RollbacksController#create`, which accepts an arbitrary `env` param the way `DeploysController`/`TasksController` do) and by the internal auto-rollback-on-abort path (`trigger_revert_if_required` → `rollback_once_aborted_to.trigger_rollback(aborted_by, env:, force: true)`). Since `filter_rollback_envs`/`EnvironmentVariables.permit` is never invoked here, any key an attacker sends in the `env` hash of a rollback request is persisted on the `Rollback` task record unfiltered.

That stored, unfiltered `Task#env` is later merged into the actual process environment for the rollback's shell commands in `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) as the *last* merge — so it overrides `@stack.env`, the hardcoded `SHIPIT_*`/`GIT_*` variables, and `deploy_spec.machine_env`. `EnvironmentVariables#interpolate` (`lib/shipit/environment_variables.rb:20-27`) then substitutes `$VAR` occurrences in the rollback command arguments (declared in `rollback.override`/deploy steps in `shipit.yml`) using this same unfiltered hash, and `Command#run`/`Command#start` execute those interpolated argv entries on the deploy host.

### Impact Explanation
Any actor with `deploy:stack` permission (a legitimate, but not necessarily fully-trusted, API client/user permitted only to trigger deploys/rollbacks within the bounds the repository's `shipit.yml` intends) can set environment variable names that were never whitelisted by the repository owner's `shipit.yml` `rollback.variables`/`deploy.variables` list, and have them injected into the rollback shell environment on the deploy host. Because `rollback.override`/inferred rollback steps (and the shared `Command#interpolate_environment_variables`) substitute `$VAR` verbatim via `Shellwords.escape`, an attacker who controls arbitrary environment variable *names and values* not restricted to the declared allowlist can influence command behavior in ways the `shipit.yml` author did not intend to expose (e.g., overriding variables the deploy scripts read positionally, such as credentials paths, feature flags, or shell-interpreted variables consumed by `deploy.override`/`rollback.override` scripts that were assumed to be constrained to the declared whitelist). This breaks the "environment key permitted (`shipit.yml` `rollback.variables`) equals environment key spawned in the task process" binding and gives a deploy-permission holder more control over the executing command's environment than the stack's declared configuration allows — a control-plane escalation on the deploy host, matching the class of "no minimum enforcement on a special-case code path" bug from the reference report (there, `checkMinBorrow` was skipped on the settlement path; here, `filter_rollback_envs` is skipped on the rollback-build path).

### Likelihood Explanation
High reachability: any API client with the standard `deploy:stack` permission can call `POST /rollbacks` (`Shipit::Api::RollbacksController#create`) with an arbitrary `env` hash, and it is stored/used unfiltered. It also fires automatically on `rollback_once_aborted?` deploys, so no special access beyond ordinary deploy permission is required to trigger the sanitization bypass — the only extra step compared to a normal deploy is using the rollback endpoint instead of the deploy endpoint, which is a trivial difference in attacker behavior. This is directly analogous to the "self-liquidate through a code path missing the min-borrow check" exploitation pattern from the source report: the correct/protected path (`build_deploy` / `trigger_task`) enforces the invariant, but a second, less-obviously-equivalent path (`build_rollback`) omits it.

### Recommendation
In `app/models/shipit/deploy.rb`, `build_rollback` should filter `env` through the same whitelist mechanism as the other task-creation code paths, e.g. `env: stack.filter_rollback_envs(env.to_h)` (mirroring `Stack#build_deploy`'s `env: filter_deploy_envs(env.to_h)`), and `Deploy#trigger_revert` should likewise ensure the `env:` it stores (`env || self.env`) has been through `filter_rollback_envs` rather than trusting `self.env` (already filtered at deploy time) or a caller-supplied hash directly.

### Proof of Concept
1. Configure a stack's `shipit.yml` with `rollback.variables` containing only a benign variable, e.g. `RUN_MIGRATIONS`.
2. As a client with `deploy:stack` permission, trigger a deploy so a `Deploy` exists that can be rolled back.
3. Call `POST /api/stacks/:stack_id/rollbacks` (`RollbacksController#create` → `deploy.trigger_rollback`) with `env: { "NOT_WHITELISTED_VAR" => "malicious-value" }`.
4. Unlike the equivalent deploy/task creation request (`DeploysController#create`/`TasksController#trigger`), which raises `EnvironmentVariables::NotPermitted` (`422 Variables NOT_WHITELISTED_VAR have not been whitelisted`) for the same unlisted key, the rollback request succeeds and `Rollback#env` is persisted containing `NOT_WHITELISTED_VAR`.
5. When the rollback task executes, `TaskCommands#env` merges `@task.env` last, so `NOT_WHITELISTED_VAR=malicious-value` is present in the shell environment for the rollback's commands, and any `$NOT_WHITELISTED_VAR` reference in `rollback.override`/inferred steps is interpolated with the attacker-supplied value — demonstrating the whitelist enforced on deploy/task creation is bypassed specifically via the rollback path.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
