### Title
StatusHandler applies incoming commit-status webhooks by raw SHA across the whole instance, not the repository the webhook was authenticated for - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook only against the GitHub App/organization derived from `repository.owner.login` (or `organization.login`) in the payload, then dispatches the entire JSON body to the matching event handler. `Shipit::Webhooks::Handlers::StatusHandler`, which processes the `status` event, never re-checks that the commit it mutates belongs to the repository/organization that was authenticated - it looks up commits globally by `sha` alone and writes a GitHub-supplied status onto every match. This is the same class of flaw as the LiFi bug: the authorization decision is bound to one field (the payload's `repository.owner.login`, used to pick the trusted webhook secret) while the state-changing action is bound to a completely different, unvalidated field (`sha`) that can reference objects outside the authenticated repository/organization.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using only `repository_owner`: [1](#0-0) [2](#0-1) 

Once the HMAC check against that org's `webhook_secret` passes, `create` dispatches the parsed payload to the handler registered for the event with no further binding to the repository named in the payload: [3](#0-2) 

The generic `Handler` base class *does* provide a `repository_name`/`stacks` helper that scopes work to `payload.dig('repository', 'full_name')`: [4](#0-3) 

But `StatusHandler#process` does not use it. It resolves the target purely by `sha`, matching **every** `Commit` row in the database with that SHA, regardless of which stack/repository it belongs to, and writes the attacker-supplied `state`/`context`/`description` onto each: [5](#0-4) 

`Commit#create_status_from_github!` unconditionally persists the status and triggers merge-queue scheduling on success: [6](#0-5) [7](#0-6) 

Those statuses feed directly into merge-queue gating: `MergeRequest#any_status_checks_failed?`/`#any_status_checks_missing?` and `#merge!` rely on `head.statuses_and_check_runs`, computed from exactly the rows `StatusHandler` writes: [8](#0-7) [9](#0-8) 

**Binding that is broken (equality form):**
`authenticated_org(payload.repository.owner.login) == acted_upon_repository(commit.stack.repository)` is assumed but never enforced. The webhook signature only proves "this payload was signed with Org A's webhook secret"; it proves nothing about which `sha` values inside that payload are legitimate to touch, and `StatusHandler` acts on `sha` values that can trivially exist in more than one repository (e.g., a public repository and any fork of it share identical commit SHAs for their common history). An attacker who legitimately controls Org A (their own GitHub org with the Shipit GitHub App/webhook installed, and thus knows/derives a validly-signed `status` payload for Org A) can name a `sha` that also exists in Org B's (victim's) repository - since forked/mirrored repos preserve upstream SHAs - and have Shipit apply a forged `success` status to Org B's commit, satisfying merge-queue required-status checks it does not otherwise pass.

### Impact Explanation
Forged status entries directly feed `MergeRequest#reject_unless_mergeable!` and `#merge!`, which is the exact gate Shipit's merge queue uses to decide whether to call `stack.github_api.merge_pull_request(...)` with the app's GitHub App token. By injecting a `success` status (with the required `context`) for a SHA shared with a victim stack's pull request head commit, an attacker outside the victim's organization can push that PR through Shipit's automated merge queue - an unauthorized merge performed with Shipit's own GitHub credentials. This matches the report's Critical bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only: (1) the attacker controls a GitHub org/repo that already has the Shipit GitHub App installed with its own `webhook_secret` (a normal, unprivileged tenant setup in multi-org Shipit deployments, as shown in `config/secrets.development.shopify.yml`), and (2) a commit SHA collision with the target, which is trivially achievable via a fork of the victim's public repository (shared git history ⇒ identical SHAs) or by knowing/guessing the victim's already-pushed commit SHA (SHAs are often public via GitHub). No GITHUB_TOKEN, `api_clients_secret`, or Shipit session is required - only a legitimate GitHub webhook signature for the attacker's own tenant.

### Recommendation
Scope `StatusHandler#process` (and any other handler that keys off `sha` alone) to the repository declared in the same payload, consistent with the pattern already used by `Handler#stacks`/`#repository_name`: resolve target commits via `stacks.flat_map(&:commits).where(sha: ...)` (or equivalently join through `Stack -> Repository` matched to `payload.dig('repository','full_name')`) instead of a bare `Commit.where(sha: ...)`. Additionally, verify that `repository.owner.login` used to select the webhook secret matches the `repository.full_name` owner actually referenced by the payload before dispatching to handlers, mirroring the additional cross-field consistency checks recommended in the original report.

### Proof of Concept
1. Attacker sets up "Org A" (their own GitHub org) with the Shipit GitHub App and its own `webhook_secret`, per the multi-org config shown in `config/secrets.development.shopify.yml`.
2. Attacker forks the victim's public repository into Org A, inheriting identical commit SHAs for the shared history, including the SHA of the victim's open pull-request head commit (`sha_X`), which fails/lacks the CI check required by the victim's `deploy_spec` (e.g. `context: "ci/build"`).
3. Attacker crafts a GitHub `status` webhook JSON body: `{"sha": "sha_X", "state": "success", "context": "ci/build", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/forked-repo"}}` and signs it with Org A's `webhook_secret` (`sha1=HMAC(secret_A, body)`).
4. POST to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature`. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches Org A's app, and the signature verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: "sha_X").each { |c| c.create_status_from_github!(params) }`, which also matches the victim's `Commit` row (same SHA, different `stack_id`), writing a `success` `Status` for context `"ci/build"` onto it.
6. The victim's `MergeRequest#any_status_checks_missing?`/`#any_status_checks_failed?` now returns false for that context, `stack.schedule_merges` runs, and `MergeRequest#merge!` calls `stack.github_api.merge_pull_request(...)`, merging the victim's PR without a legitimate passing check.

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    end
