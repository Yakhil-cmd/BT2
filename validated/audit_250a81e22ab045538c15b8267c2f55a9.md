The bug class maps onto the controller's delegate grants: they "die" on NFT transfer but stay in storage and re-arm if the token returns to the granter — a stale credential that is never actually invalidated. Let me verify the delegate mechanics and what a delegate can do.### Title
Stale delegate grant silently re-arms when a position NFT returns to the granter, letting a former delegate drain the reacquired account - (File: contracts/controller/src/storage/account.rs)

### Summary
The Directus bug class is a credential that outlives its intended invalidation boundary: a session token stays valid after logout because nothing checks server-side state. XOXNO Lending has the same shape in its delegate grants. A `DelegateGrant` is stamped with `granted_by = <granter address>` rather than a transfer epoch, so a transfer makes the grant dormant but never deletes it. If the position NFT ever returns to `granted_by`, the grant re-arms with no new authorization — a "session" the user believed was closed is still valid.

### Finding Description
`is_owner_or_delegate` in `contracts/controller/src/account.rs:114-127` authorizes a caller when the caller is an active position manager and `storage::get_delegates(env, account_id, owner)` contains it. Because the delegate list is keyed by the *granting* owner's address, a grant written by Alice reads as empty while Bob holds the NFT, but becomes live again the moment Alice is the owner again. The README states this directly: "The stale grant stays in storage and re-arms if the token returns to `granted_by`. The next holder's `add_delegate` overwrites it" — so only an intervening owner's explicit overwrite deletes the credential.

The delegated powers are the account's core mutators: `borrow`, `withdraw`, `multiply`, `migrate_from_blend`, etc., all gated by `require_owner_or_delegate` (`contracts/controller/src/account.rs:130-140`). The threat model confirms "Delegates can borrow/withdraw to their chosen recipient within account gates", so a re-armed delegate can extract collateral to itself, not merely act for the owner.

Attack path a single unprivileged address (an active registered position manager M) can submit:
1. Alice calls `add_delegate(Alice, account_id, M)` — grant stored under `granted_by = Alice`.
2. Alice transfers the position NFT to Bob (`position-nft::transfer`). `get_delegates(account_id, Bob)` is empty; the Alice-stamped grant remains in storage.
3. The NFT returns to Alice by any route — Bob sells it back, an OTC position trade unwinds, a `transfer_from` round-trip. Neither party calls `add_delegate`/`remove_delegate`.
4. M calls `controller::withdraw(caller=M, account_id, withdrawals, to=M)` or `borrow(caller=M, account_id, ..., to=M)`. `is_owner_or_delegate` resolves owner = Alice, finds M in `get_delegates(account_id, Alice)`, and authorizes. M drains Alice's collateral or saddles the account with debt paid out to M — without any fresh consent from Alice, who reasonably believed the delegation died at step 2.

### Impact Explanation
Theft of user funds. A re-armed delegate can withdraw all withdrawable collateral to an arbitrary recipient and/or borrow to the LTV limit with the proceeds paid to itself, leaving the reacquiring owner with a drained or max-leveraged account. This is a direct unauthorized-transfer-of-assets primitive, not a theoretical weakening: no oracle drift, liquidation precondition, or privileged action is needed once the NFT is back with the granter.

### Likelihood Explanation
Medium. Exploitation requires (a) the victim to have granted a delegate at some point, (b) the NFT to leave and return to that same address without an intervening owner overwriting delegates, and (c) the delegate to still be an active position manager. Position NFTs are transferable assets (sales, collateralized position trades, marketplace round-trips), so return-to-sender is realistic — including adversarially induced: a malicious M can sell the NFT back to Alice, or Alice herself may reacquire a position she previously sold. The grant requires no expiry and survives indefinitely in storage, so the window never closes on its own.

### Recommendation
Invalidate delegate grants on ownership change rather than dormancy-by-owner-match. Options: store a transfer epoch/generation counter on the account meta, bump it in the controller's transfer-resolution path (or stamp `granted_by` together with the epoch and require equality); or persist a per-account `owner_generation` that `add_delegate`/`remove_delegate`/`get_delegates` read. Alternatively, have the position NFT invoke a controller callback on `transfer`/`transfer_from` that clears all delegate entries for the account. At minimum, `remove_delegate` semantics should be documented to users as the only reliable revocation and grants should carry an expiry.

### Proof of Concept
1. `supply(caller=Alice, account_id=0, ...)` → mints NFT `id` to Alice.
2. `add_delegate(caller=Alice, account_id=id, delegate=M)` — M is an active position manager.
3. `position_nft::transfer(Alice → Bob, id)`; then `position_nft::transfer(Bob → Alice, id)` (or Bob transfers to Carol, who transfers to Alice — no `add_delegate`/`remove_delegate` occurs in between).
4. `supply(caller=Alice, account_id=id, ...)` — Alice funds the reacquired account.
5. `withdraw(caller=M, account_id=id, withdrawals=[collateral], to=M)` succeeds: `get_delegates(env, id, Alice)` still contains M, so `is_owner_or_delegate` returns true and M receives Alice's collateral.
