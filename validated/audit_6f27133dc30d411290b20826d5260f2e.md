Confirmed: this is a genuine binding break analogous to the Zebra bug. The webhook signature verification selects *which* org's secret to check against based on one field of the payload (`repository.owner.login`), while the actual write action (`Repository.from_github_repo_name`) is driven by a different, independently-attacker-controlled field (`repository.full_name`) in the very same signed body. Because GitHub's org/webhook secrets are per-organization and an attacker who administers their own GitHub organization can install their own Shipit-pointed webhook and thus legitimately knows their own org's `webhook_secret`, they can forge a payload whose `repository.owner.login` matches their own org (so the correct/known secret validates the HMAC) but whose `repository.full_name` names a victim org/repo already tracked by Shipit, achieving unauthorized writes (sync, PR label-driven archive/unarchive, deploy-adjacent state changes) against a repository the attacker does not own.

### Title
Webhook organization used for signature selection is not bound to the repository acted upon, enabling cross-organization spoofed webhook writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`) [1](#0-0) [2](#0-1) . Every downstream `Handler` instead resolves the target repository from a *different* field of the same JSON body, `payload.dig('repository', 'full_name')` [3](#0-2) , and handlers such as `PushHandler` act on stacks belonging to that repository (`stack.sync_github(...)`) [4](#0-3) , while PR handlers look up `Repository.from_github_repo_name(params.repository.full_name)` to archive/unarchive review stacks [5](#0-4) .

### Finding Description
The Zebra bug is a case where consensus validity is decided over a digest that doesn't cover a field that later matters (the missing output), letting an attacker sign something valid for a narrower scope than what actually gets used. The analog here is a "field acted on but never bound to a specific other field, despite both being present in the same signed blob": the HMAC over `request.raw_post` proves the *entire* body came from someone who knows *a* valid `webhook_secret` for *some* configured GitHub organization — but which organization's secret validated is chosen from `repository.owner.login`/`organization.login`, and the *object actually mutated* is chosen from the unrelated `repository.full_name` field, with no code path asserting `repository.owner.login == repository.full_name.split('/').first`.

Because Shipit explicitly supports "Using Multiple Github Applications" where each organization has its own independent `webhook_secret` [6](#0-5) , and `Shipit.github(organization: ...)` looks the config up per-organization, an attacker who legitimately controls (and has installed the Shipit-integrated GitHub App on) their *own* organization "orgA" has a fully valid `webhook_secret` for "orgA". They can craft a webhook body where `repository.owner.login` (or `organization.login`) is `"orgA"` (so `verify_signature` selects and validates against orgA's known secret) but `repository.full_name` is `"victim-org/victim-repo"` (so the handler acts on the victim's tracked stacks). `verify_signature` only checks the HMAC over the raw body against orgA's secret — it never checks that the `full_name` used later belongs to the same organization that authenticated [7](#0-6) .

### Impact Explanation
This lets an attacker who only controls their own GitHub organization forge webhook events (`push`, `pull_request` labeled/unlabeled/reopened/closed, `status`, etc.) that are accepted as authentic for any other organization/repository already onboarded to the same Shipit instance, and drive unauthorized state-changing operations: triggering `GithubSyncJob`/`sync_github` on a victim stack's branch with an attacker-chosen `expected_head_sha`, and archiving/unarchiving review stacks via forged PR label events — all without any GitHub credentials for the victim org. This is a cross-repository write achieved purely by exploiting the organization-selection vs. repository-target binding gap, matching the "unauthorized deploy/write" impact bar.

### Likelihood Explanation
Requires only that (a) the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) or that the attacker's org shares/derives the same webhook secret path, and (b) the attacker knows their own org's `webhook_secret` (trivial, since they configured it themselves when installing their own GitHub App integration). No access to the victim org, no Shipit session, and no GITHUB_TOKEN are needed.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after selecting the GitHub App used to validate the signature by `repository_owner`, enforce that every entity resolved later in the request (via `repository.full_name` in `Handler#repository_name`) belongs to that same, already-authenticated organization — e.g., require `full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Attacker creates/owns GitHub organization `orgA` and installs a Shipit-pointed GitHub App on it, obtaining a valid `webhook_secret` for `orgA` (legitimate, self-service).
2. Attacker crafts a JSON body: `{"ref":"refs/heads/master","after":"<attacker-chosen-sha>","repository":{"owner":{"login":"orgA"},"full_name":"victim-org/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, validates the HMAC successfully against `orgA`'s secret [1](#0-0) .
5. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` via `Handler#repository_name` and calls `stack.sync_github(expected_head_sha: params.after)` on victim-org's stacks [3](#0-2) [4](#0-3)  — an unauthorized state change against a repository the attacker does not control.
