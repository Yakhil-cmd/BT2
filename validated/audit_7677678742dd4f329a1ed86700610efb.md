### Title
Webhook signature verification key-selection field is decoupled from the payload's repository/target field, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to validate the HMAC signature against by reading `repository_owner` from the **same unauthenticated JSON body** being verified: `params.dig('repository','owner','login') || params.dig('organization','login')`. Every downstream `Webhooks::Handlers::Handler` then independently reads a *different* field, `payload.dig('repository', 'full_name')`, to resolve the target `Repository`/`Stack`. Nothing ties these two fields together, so the organization whose secret authenticated the delivery is never checked against the repository that handlers actually act on.

### Finding Description
`verify_signature` in [1](#0-0)  resolves the app config with:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is computed purely from attacker-controlled JSON: [2](#0-1) .

`verify_webhook_signature` only checks that the HMAC of the *entire raw body* matches, using the secret belonging to whichever organization the attacker put in `repository.owner.login`/`organization.login`: [3](#0-2) . It never checks that any other field of the body (e.g. `repository.full_name`) is consistent with that organization.

Once signature verification passes, the `create` action dispatches the full, self-authored payload to all handlers for the event: [4](#0-3) . Every handler resolves its target stacks purely from `repository.full_name`, a field that was never part of the org-selection check: [5](#0-4) .

Concretely, `PushHandler` triggers `stack.sync_github` for whatever `repository.full_name` names: [6](#0-5) , and `StatusHandler` writes a commit status onto any commit matching `params.sha` regardless of which org's secret validated the delivery: [7](#0-6) .

Shipit explicitly supports multiple, independently-configured GitHub App organizations sharing one instance, each with its own `webhook_secret`: [8](#0-7) . An entity that is a legitimate administrator of *one* configured organization's GitHub App (and therefore knows/controls that organization's `webhook_secret` as part of normal, unprivileged setup) can construct an arbitrary JSON body: set `repository.owner.login` (or `organization.login`) to their own org so the signature check passes with a secret they legitimately possess, while setting `repository.full_name` to a completely different, unrelated organization's repository tracked by the same Shipit instance. The binding "organization that authenticated" == "organization/repository written" is broken — before: it is assumed the signature scoping covers the acted-upon repository; after: the two are shown to be independently controlled fields in the same unauthenticated JSON blob.

### Impact Explanation
This allows an attacker who only controls one tenant/organization's webhook configuration on a shared Shipit deployment to forge `push`, `status`, and `check_suite` events against stacks belonging to a different organization: injecting fabricated commit statuses (`StatusHandler`), forcing `GithubSyncJob` re-syncs against arbitrary target shas (`PushHandler`), or manipulating check-run refresh state (`CheckSuiteHandler`). Faked/forced commit statuses can flip a stack's CI/deployability gating used elsewhere in the engine, which can lead to cross-tenant unauthorized deploy triggering. This is a cross-repository/cross-organization write from an unprivileged (relative to the victim org) actor, matching the Critical/High "cross-repository writes"/"unauthorized deploy" criteria.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for *some* organization configured on the target Shipit instance. This is realistic in the documented multi-organization deployment model, where distinct internal/partner GitHub orgs each configure their own GitHub App and secret against one shared Shipit instance — each org's own administrators are, by design, "unprivileged" with respect to other orgs' stacks, yet each legitimately holds their own org's webhook secret. No token, TLS interception, or privileged Shipit account is needed beyond that per-org secret, which is a normal, low-privilege credential in this architecture. The vulnerability is purely a code-level omission (no cross-check between the two fields), not a defect in a third-party gem.

### Recommendation
Bind the two fields together before dispatching to handlers:
- Derive the organization used for handler dispatch (`Repository.from_github_repo_name`) from the same field/value validated during signature verification, or
- After selecting `github_app` via `repository_owner`, additionally verify that `payload.dig('repository', 'full_name')`'s owner segment (and/or `organization.login`) matches `repository_owner` exactly, rejecting the request (422) on mismatch, or
- Look up the `Repository`/`Stack` and confirm its configured organization equals the organization whose secret validated the request before allowing any handler to run.

### Proof of Concept
Given a shared Shipit instance configured with `secrets.github` containing both `orgA` (attacker-administered, secret known to attacker) and `orgB` (victim), an attacker can send:
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(body, orgA_webhook_secret)>

{
  "sha": "<victim_commit_sha_in_orgB_stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
`repository_owner` resolves to `orgA`, so `Shipit.github(organization: 'orgA').verify_webhook_signature` succeeds using the attacker's own known secret [1](#0-0) . `StatusHandler#process` then unconditionally applies the forged `state`/`context` to any commit in the system whose sha matches, regardless that the repo field said `orgB/victim-repo` [7](#0-6) , and `Handler#stacks`/`#repository_name` never re-checks the org that authenticated the request [5](#0-4) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
