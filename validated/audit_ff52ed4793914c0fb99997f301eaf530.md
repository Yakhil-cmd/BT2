Confirmed: `Repository.from_github_repo_name` looks up purely by `owner`/`name` parsed from the payload's `repository.full_name` [1](#0-0) , with no cross-check against the `repository.owner.login` value that `verify_signature` used to pick the signing secret.

### Title
Cross-organization webhook forgery via secret-selection/repository-owner mismatch in multi-tenant GitHub App config - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using a field taken directly from the unauthenticated JSON payload (`repository.owner.login`, falling back to `organization.login`), but the downstream event handlers act on an entirely different, independently attacker-controlled field of the same payload (`repository.full_name`) to decide which repository/stack to mutate. Nothing binds the two together, so a signature that only proves knowledge of one organization's webhook secret is accepted as authorization to act on any other configured organization's repository.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the raw, unverified request body and uses it to pick the `GitHubApp` instance (and therefore the `webhook_secret`) that will validate `X-Hub-Signature`: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` also short-circuits to `true` when no `webhook_secret` is configured for the selected organization, which is an explicitly supported/optional configuration per `docs/setup.md` and the multi-app example config: [4](#0-3) [5](#0-4) 

After this "verification" passes, `create` re-parses the same raw body and dispatches it to handlers such as `PushHandler`, whose `stacks`/`repository_name` are derived from `payload.dig('repository', 'full_name')` — a completely different payload field than the one used to pick the verifying secret: [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` then does a plain lookup by `owner`/`name` parsed out of `full_name`, with no check that this owner matches `repository_owner` used earlier for signature selection: [1](#0-0) 

Equality broken: `organization whose secret authenticated the request` ≠ `organization that owns the repository actually written to`. An attacker who can produce a validly-signed payload for *any one* configured organization (e.g., because that org's `webhook_secret` is unset, or because the attacker is a legitimate webhook sender for that org) can set `repository.owner.login`/`organization.login` to that organization while setting `repository.full_name` to `"<victim-org>/<victim-repo>"`. The controller authenticates against the attacker's org, but the handler executes against the victim org's stack.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary explicitly called out as in-scope. Concretely, `PushHandler` will enqueue `GithubSyncJob`/`stack.sync_github` for the victim's stack based on an attacker-chosen `after` SHA, and other handlers (status, check_suite, pull_request, membership) can similarly be driven against a victim org's stacks/teams/users. In multi-org Shipit installs this enables unauthorized triggering of deploy-related state changes on repositories the attacker does not control, without possessing that organization's webhook secret — an unauthorized/forged deploy trigger.

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub organization (a documented, supported feature — `docs/setup.md` "Using Multiple Github Applications"), and requires the attacker to have (or forge) a valid signature for *any one* of the configured organizations — trivially true if that organization's `webhook_secret` is left blank (also an explicitly optional/documented setting), or otherwise as easy as compromising the weakest-secured org among many onboarded orgs.

### Recommendation
After selecting the GitHub App/secret used for `verify_webhook_signature`, cross-validate that the same organization (`repository_owner`) actually owns the repository referenced by `repository.full_name` before dispatching to handlers — reject the webhook (422) if they diverge. Handlers should also independently verify that the resolved `Repository`'s `owner` matches the authenticated organization for the request.

### Proof of Concept
1. Configure Shipit with two orgs, `AttackerOrg` (webhook secret unset or known to attacker) and `VictimOrg` (properly secured, hosts a real stack for `VictimOrg/app`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/app"
  }
}
```
3. Sign the raw body with `AttackerOrg`'s secret (or omit signing if `AttackerOrg` has no secret configured — `verify_webhook_signature` returns `true` unconditionally).
4. `verify_signature` resolves `repository_owner` = `AttackerOrg`, validates successfully against `AttackerOrg`'s app/secret.
5. `create` dispatches the same payload to `PushHandler`, which resolves the target repository via `full_name` = `VictimOrg/app`, finds the real stack, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, causing Shipit to sync/deploy against `VictimOrg`'s stack despite never validating a signature tied to `VictimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
