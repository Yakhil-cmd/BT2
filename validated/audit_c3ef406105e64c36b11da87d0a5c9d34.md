### Title
Aggregate-value overflow in interest accrual permanently freezes a large market - (File: common/src/rates/simulate.rs)

### Summary
The accrual path converts scaled aggregate debt and supply into `i128`-backed `Ray` values before enforcing the borrow-index ceiling. For a sufficiently large market, a successful accrual can leave the index below `MAX_BORROW_INDEX_RAY` while making the next aggregate-value multiplication exceed `i128::MAX`, after which every accrual panics and market operations that synchronize first cannot execute. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Controller::update_indexes` is permissionless, requiring only the caller's authorization, and forwards the selected `HubAssetKey` list to the pool. [4](#0-3) [5](#0-4) 

For each market, pool accrual invokes `interest::global_sync`, which repeatedly calls `accrue_step`. [6](#0-5) [7](#0-6) 

The vulnerable ordering is in `accrue_step`: it computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` before calculating the next index. [8](#0-7)  `scaled_to_original` delegates to `Ray::mul`, so an aggregate value that no longer fits in `i128` panics rather than clamping or returning an error. [2](#0-1) 

The configured borrow-index ceiling is only applied after multiplying the old index by the interest factor, and reward accounting then multiplies `borrowed` by the new index. [3](#0-2) [9](#0-8)  Therefore the ceiling does not protect the protocol from crossing the smaller representable-value boundary `borrowed * borrow_index <= i128::MAX`.

The repository's own boundary test demonstrates the condition: one billion 18-decimal tokens, a 98%-utilization borrow, and repeated yearly accruals eventually produce `MathOverflow` while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [10](#0-9) [11](#0-10) 

Once the market is in that state, the next `update_indexes` call reverts, and the test shows that `withdraw` and `repay` revert with the same `MathOverflow` because they synchronize the market first. [12](#0-11)  The test also documents that liquidation follows the same accrual-first path. [13](#0-12) 

### Impact Explanation
All supplier funds and outstanding debt in the affected market become inaccessible through the normal user paths: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot process the market, and maintenance calls cannot commit a later index. This is a permanent freezing of user funds absent an out-of-band contract upgrade or state repair, not merely a failed individual transaction. [12](#0-11) [14](#0-13) 

Because the pool stores one aggregate `supplied` and `borrowed` balance per market, the failure is market-wide and freezes other users' funds as well as the triggering position. [15](#0-14) 

### Likelihood Explanation
This is not a one-call denial of service on an ordinary market; it requires aggregate scaled balances close to the representable-value ceiling and enough elapsed time for the index to cross the unsafe boundary. The boundary is nevertheless within the code's valid domain: the test uses `max_cap_for_decimals`, valid market parameters, a billion-token position, and 98% utilization. [16](#0-15) [17](#0-16) 

A real high-decimal, high-cap market can reach the same condition through organic whale balances or an attacker-funded position. Once the market is close to the boundary, any unprivileged caller can submit `update_indexes(caller, vec![hub_asset])` and trigger the panic, while no unprivileged recovery path remains. [5](#0-4) 

### Recommendation
Enforce a market-specific representable-index ceiling before every accrual, rather than relying only on the global `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`. For each aggregate scaled balance, calculate the largest index satisfying `scaled * index / RAY <= i128::MAX` using widened arithmetic, cap index growth at `min(global_index_cap, representable_index_cap)`, and make accrual a committed no-op once that cap is reached.

Apply the same invariant when minting supply or debt shares so aggregate shares cannot enter a state where the current index no longer produces a representable aggregate value. All aggregate conversions in `accrue_step`, `calculate_supplier_rewards`, `update_supply_index`, utilization calculations, and bad-debt socialization should use checked or widened arithmetic and handle the boundary explicitly instead of panicking. [18](#0-17) [19](#0-18) 

### Proof of Concept
The existing regression test is a direct proof of concept. On a market whose valid caps permit the size, it supplies one billion 18-decimal tokens, borrows 98% of that market against separate collateral, advances ledger time year by year, and calls `update_indexes` until accrual fails with `MathOverflow`:

t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);

        .with_market(big("BIG18", 18, xlm_curve()))

        years += 1;
        assert!(
            years <= 40,
