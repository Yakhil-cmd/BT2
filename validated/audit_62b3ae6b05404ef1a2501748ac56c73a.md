### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the GitHub App/secret for the *organization named in the payload* and only proves that the payload originated from that organization's installation. `StatusHandler#process`, however, applies the status update to *any* `Commit` row in the database whose `sha` matches the payload, without ever checking that the commit belongs to a stack/repository owned by the authenticated organization. Because `sha` is not a global-unique key (see the `stack_id`+`sha` composite index), this creates a binding break: `organization that authenticated ≠ repository whose commit status is written`.

### Finding Description
`verify_signature` in [1](#0-0)  resolves `repository_owner` from the payload and verifies the HMAC signature against that specific organization's `webhook_secret` via `Shipit.github(organization: repository_owner)`. This only proves "this payload was signed by organization X's GitHub App installation" — it says nothing about which `Commit`/`Stack` rows in Shipit's database the payload is allowed to mutate.

Most handlers correctly re-derive the acted-upon scope from the same payload field that was implicitly trusted for org resolution, by going through `Repository.from_github_repo_name(repository_name)` and then `repository.stacks`, e.g. `PushHandler` and `CheckSuiteHandler` both operate on `stacks` derived from `Handler#stacks` [2](#0-1) .

`StatusHandler`, however, does not use `stacks`/`repository_name` at all: [3](#0-2) 
It queries `Commit.where(sha: params.sha)` across the *entire* commits table and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository/stack that commit belongs to. The database schema confirms `sha` is only indexed together with `stack_id` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), i.e. it is not globally unique — the same SHA can legitimately exist in multiple stacks (e.g., a public upstream repo and any fork/mirror connected to Shipit, or multiple stacks tracking the same repository on different branches).

This is the structural analog of the "double normalization" bug: the report's root cause was that a value already validated/normalized upstream (storage-normalized deposit/borrow amounts) was blindly reprocessed and applied without re-checking its provenance. Here, the value that was validated upstream (the organization identity behind the signature) is discarded, and the code instead re-derives the effective scope purely from an unscoped, attacker-controlled `sha` field, applying the write to whatever commit rows happen to match — potentially belonging to a different, unrelated repository/organization than the one that was actually authenticated.

### Impact Explanation
Commit status data drives Shipit's CI-gating and deploy-safety logic (`Commit`/`Stack#undeployed_commits`, checks used before allowing a deploy). If an attacker controls (or has legitimate webhook-signing capability for) one Shipit-connected repository/organization, and a target repository elsewhere in the same Shipit installation happens to share a commit SHA (trivially achievable for public repos via forking, since git commit hashes are deterministic and forks/mirrors retain identical SHAs), the attacker can send a forged/legitimate `status` event for their own repo with `sha` equal to a commit that also exists in the victim stack. `StatusHandler` will then write that status onto the victim's `Commit`, potentially marking it as CI-successful and influencing deploy eligibility for a repository the attacker was never authorized to affect — a cross-repository write that can contribute to an unauthorized deploy decision.

### Likelihood Explanation
Requires an attacker to have webhook-signing capability for at least one repository/organization onboarded to the same Shipit installation (i.e., a "low-privilege" tenant), plus a commit SHA collision with the target stack, which is realistically achievable through forking a public target repository (shared history yields identical SHAs). No repository write access to the *victim* repository, no Shipit session, and no possession of the victim's webhook secret is required — only the attacker's own (lower-trust) organization's credentials, satisfying the unprivileged-attacker requirement.

### Recommendation
Scope `StatusHandler`'s commit lookup by the repository named in the payload, consistent with `PushHandler`/`CheckSuiteHandler`: resolve `stacks` (or the owning `Repository`) from `payload.dig('repository', 'full_name')` and restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` (or an equivalent `joins(stack: :repository)` scoped query), so that the authenticated organization/repository binding established by `verify_signature` is actually enforced when writing commit status.

### Proof of Concept
1. Configure two Shipit stacks in the same installation: `stack_low` tracking `attacker-org/forked-repo` (attacker has push/webhook rights) and `stack_high` tracking `victim-org/upstream-repo` (attacker has none), where `forked-repo` is a fork of `upstream-repo` sharing commit history/SHAs.
2. Attacker triggers (or, if they control CI/webhook delivery for their org, directly crafts) a `status` webhook event for `attacker-org/forked-repo` with `sha` set to a commit SHA shared with `victim-org/upstream-repo`, and a passing `state`.
3. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s webhook secret and succeeds — it only proves the event came from `attacker-org`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the commit row in `stack_high` as well as `stack_low`, and calls `create_status_from_github!` on both, writing an attacker-controlled CI status onto the victim stack's commit without any check that the commit belongs to `attacker-org`.
