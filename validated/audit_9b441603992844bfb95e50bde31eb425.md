### Title
Cross-organization webhook forgery — signature is verified against the org derived from `repository.owner.login`, but the write target is derived from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of the Astaria bug: the value that is checked/authenticated (`collateralStateHash` vs. the actual lien-taking action) is not the same value that is used to perform the sensitive action (asset transfer). In `WebhooksController`, the HMAC signature that authenticates a webhook is verified using the GitHub App/organization selected from `repository.owner.login`, while every event handler resolves the `Repository`/`Stack` to mutate using the sibling field `repository.full_name`. These two fields live in the same attacker-supplied JSON object but are never cross-checked against each other.

### Finding Description
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the signature against using: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` then loads that organization's `webhook_secret` from `secrets.github` and verifies `X-Hub-Signature` against the raw body using that secret [3](#0-2) , [4](#0-3) .

Once the signature is accepted, `Handler#stacks`/`#repository_name` (used by nearly every handler, e.g. `PushHandler`) resolves the actual `Repository`/`Stack` records to mutate from a *different* field — `repository.full_name` — with no verification that it is consistent with `repository.owner.login`: [5](#0-4) [6](#0-5) 
`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks the record up by `owner`/`name` [7](#0-6) .

In a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, selected via `github_app_config`) [8](#0-7) , an operator who legitimately controls the GitHub App/webhook secret for Organization A can craft a raw JSON payload where `repository.owner.login = "orgA"` (so the signature verifies against Org A's secret) but `repository.full_name = "orgB/victim-repo"` (an unrelated organization/repository they do not control). The signature check passes because it only inspects `owner.login`; the handler then acts on whatever stack matches `full_name`, which belongs to Org B.

This is exactly the "collateral owner" pattern: the field that is cryptographically bound/checked (`owner.login`) is not the field that gates the sensitive state-changing action (`full_name`), so authenticating as one entity lets you act on another.

### Impact Explanation
Handlers keyed off `repository_name`/`stacks` perform state-changing, cross-repository actions without further re-validating the organization, e.g.:
- `PushHandler#process` enqueues `stack.sync_github` for any stack whose branch matches, regardless of which org actually owns that stack [6](#0-5) .
- Other handlers (status, check_suite, pull_request lifecycle, merge, membership) all resolve their target the same way via `Repository.from_github_repo_name(params.repository.full_name)`.

This lets a valid webhook secret holder for one org drive Shipit state (sync commit history, flip commit/CI status, archive/unarchive review stacks, affect merge-queue state, etc.) for a stack belonging to a different, unrelated repository/organization that the attacker has no access to — i.e. a cross-repository write, which meets the Critical-impact bar defined by the rules.

### Likelihood Explanation
This requires the attacker to already hold a valid `webhook_secret` for at least one organization configured on the Shipit instance (i.e., they are a legitimate customer/tenant of a multi-org deployment) but have no access to the target organization's repositories. This is a realistic setup for shared/multi-tenant Shipit installations, since the only prerequisite is the ability to POST an arbitrary raw JSON body with a correctly computed HMAC — no GitHub-side event forging is needed, and no privileged Shipit account is required.

### Recommendation
Bind the webhook's authenticated organization to the resource it is allowed to mutate: after `verify_signature` succeeds, require that the org derived from `repository.owner.login` (the value used to select the secret) matches the owner encoded in `repository.full_name` before any handler is dispatched, or better, derive both the signing organization and the target repository from the same normalized field so they cannot diverge.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, has a stack tracking `orgB/victim-repo`).
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` using the secret they legitimately hold for `orgA`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")`, matches `orgB`'s stack, and triggers `stack.sync_github` for a repository the attacker never controlled.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
