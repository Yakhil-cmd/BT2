### Title
`StatusHandler` binds CI commit-status writes to a global commit SHA lookup instead of the webhook-authenticated repository, allowing cross-repository status injection - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`), i.e. it proves "this HMAC was signed by the app secret configured for organization X." [1](#0-0)  However, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks the repository the status belongs to — it looks up commits purely by SHA across the entire `commits` table and writes a GitHub status onto whatever stack/repository owns that SHA: [2](#0-1)  This breaks the intended binding "organization that authenticated == repository whose commit is written."

### Finding Description
The base `Handler` class does scope most handlers (e.g. `PushHandler`) to the payload's `repository.full_name` via `Handler#stacks`: [3](#0-2)  but `StatusHandler` deliberately bypasses this and instead resolves target records with `Commit.where(sha: params.sha)`, with no filter on `repository`, `stack`, or organization: [4](#0-3) 

The webhook signature check only proves that the *organization named in the payload* owns a valid `webhook_secret` for the app instance `Shipit.github(organization: repository_owner)` picks; it says nothing about which specific repository/commit the payload is allowed to affect: [5](#0-4)  An attacker who is a legitimate administrator of *any* organization/repository that has the Shipit GitHub App installed (and thus can generate a validly-signed `status` webhook for their own org) fully controls the `sha`, `state`, `context`, `description` and `target_url` fields of that signed payload. Since `StatusHandler` ignores the `repository` field for the purposes of scoping the write, the attacker can set `sha` to any commit SHA belonging to a *different* organization's stack and inject an arbitrary status (e.g. `state: "success"`, matching a `blocking` or CI context) onto that commit via `commit.create_status_from_github!(params)`.

This directly maps to the report's "approval race protection" bug class as an analog: the field that is verified by the signature (the payload's own repository/organization) is not the field that is actually acted upon (an arbitrary commit SHA reachable from any stack in the system) — an equality that the engine assumes holds but does not enforce.

### Impact Explanation
Shipit's deploy safety machinery (CI status checks, blocking statuses, and merge-queue validation) is gated on `Commit#statuses`/`ci_status`, which `create_status_from_github!` populates. If a status controlled entirely by an unrelated, low-privilege organization can be written onto a victim stack's commit, an attacker can forge a passing CI status for a victim's commit and, in combination with continuous deployment or merge-queue configuration, cause an **unauthorized deploy** of that commit — satisfying the report's "Critical: unauthorized deploy" bar. This requires no access to the victim's `webhook_secret`, `ApiClient` token, or any privileged account — only administration of an unrelated org/repo that also uses this Shipit instance (a multi-tenant deployment, which is the documented supported configuration).

### Likelihood Explanation
Any tenant/organization onboarded onto a shared Shipit installation can trigger this without additional privilege escalation — they merely need to send a webhook that GitHub itself would normally deliver only for their own repository, but Shipit does not verify that the SHA referenced actually belongs to the authenticated organization's repositories. This is a straightforward payload-crafting attack, not requiring any race condition or timing, making it reliably reproducible.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks belonging to the repository named in the payload (mirroring `Handler#stacks`), e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))`, and reject/no-op if the resolved commit's repository does not match the authenticated `repository.full_name` from the payload. This restores the invariant that only the organization that produced a validly-signed webhook can write statuses for its own repository's commits.

### Proof of Concept
1. Attacker owns/administers `attacker-org/attacker-repo`, onboarded to the shared Shipit instance, and the Shipit GitHub App is installed there with its own `webhook_secret`.
2. Attacker crafts a `status` event payload:
   ```json
   {
     "sha": "<victim-org/victim-repo commit sha, e.g. head of a PR pending merge>",
     "state": "success",
     "context": "ci/required-check",
     "description": "forged",
     "target_url": "https://attacker.example.com",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
   }
   ```
3. Attacker signs this payload with `attacker-org`'s legitimate `webhook_secret` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature, since it was genuinely signed with that org's secret — [5](#0-4) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit regardless of `attacker-org` being unrelated to it, then calls `commit.create_status_from_github!(params)`, writing the forged "success" status onto the victim's stack — [2](#0-1) .
6. If the victim stack has continuous deployment or a merge queue gated on that context, the forged status can unblock or trigger an unauthorized deploy/merge.

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
```
