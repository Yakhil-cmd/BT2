### Title
Fail-open `sys.exit(0)` in `pretooluse.py` lets a non-string `pattern`/`field` value crash `RuleEngine` and silently disable block rules - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
`RuleEngine._check_condition`/`_regex_match` in `plugins/hookify/core/rule_engine.py` assume `Condition.pattern` is always a `str`, but `Condition.from_dict` stores whatever YAML frontmatter provides with no type coercion. An unquoted numeric/boolean YAML value (e.g. `pattern: 777`) causes `re.compile()`, `str.startswith()`, `in`, etc. to raise `TypeError`, which propagates out of `evaluate_rules`. `pretooluse.py` catches this generically, emits a `systemMessage`-only payload (no `permissionDecision: deny`), and unconditionally calls `sys.exit(0)` in its `finally` block, so the tool call proceeds unblocked.

### Finding Description
`Condition.from_dict` reads `pattern=data.get('pattern', '')` directly from the parsed YAML frontmatter without enforcing that it is a string. [1](#0-0) 

In `RuleEngine._check_condition`, once a field value is successfully extracted (non-`None`), the operator is applied directly to `pattern`: `pattern in field_value`, `field_value.startswith(pattern)`, `field_value.endswith(pattern)`, etc. If `pattern` is not a `str` (e.g., a YAML-parsed `int`/`bool`/`list` from an unquoted value like `777`, `true`, or a bare list), these calls raise `TypeError` instead of returning `False`. [2](#0-1) 

The `regex_match` operator is equally affected: `_regex_match` only catches `re.error`, not `TypeError`, so `compile_regex(pattern)` (i.e., `re.compile(pattern, re.IGNORECASE)`) raises an uncaught `TypeError` when `pattern` is not a string or compiled pattern. [3](#0-2) 

`evaluate_rules` iterates over all rules within a single try/except-free block calling `_rule_matches` -> `_check_condition` for each rule in sequence. [4](#0-3) 
If any single rule's condition triggers this `TypeError` (which happens whenever the relevant tool_input field is present, regardless of whether the pattern would otherwise match), the exception propagates out of `evaluate_rules` entirely - aborting evaluation of *all* subsequent rules for that hook invocation, not just the malformed one.

`pretooluse.py`'s `main()` catches this exception generically and emits only a `systemMessage`, never setting `hookSpecificOutput.permissionDecision = "deny"`, then unconditionally exits `0` in `finally`: [5](#0-4) 

Compare to the deny path, which requires `hookSpecificOutput.permissionDecision: "deny"` to actually block a tool call: [6](#0-5) 

Since exceptions are swallowed as a generic error message with `sys.exit(0)`, the net effect for the current tool call is identical to the "no rules matched" path (`{}` / allow), even though a legitimate `action: block` rule would have fired.

### Impact Explanation
This defeats the entire hookify block-enforcement layer for the affected hook invocation: any dangerous `Bash`/`Write`/`Edit` operation that would otherwise be denied by a properly authored `action: block` rule is instead silently allowed, because one malformed condition (anywhere in the loaded rule set, not necessarily the rule intended to block the dangerous action) crashes the whole evaluation pass. This is a fail-open trust-boundary bypass: "deny means deny" is violated, and hook failures silently degrade to allow, exactly the invariant the plugin's design intends to preserve.

### Likelihood Explanation
Feasibility is high and requires no special privilege: any `.claude/hookify.*.local.md` rule file - written manually, generated via the `/hookify` command/`conversation-analyzer` suggestion flow, or copied from documentation - that uses a non-`regex_match` operator (`contains`, `equals`, `not_contains`, `starts_with`, `ends_with`) with an unquoted YAML scalar that looks like a number or boolean (e.g. `pattern: 777`, `pattern: true`) will deterministically trigger this on every matching tool call, since YAML parses unquoted `777` as an integer, not a string. This is a plausible authoring mistake (e.g., a rule meant to catch `chmod 777` written with `operator: contains` and `pattern: 777` instead of a quoted string or `regex_match`), and it is 100% repeatable once such a rule file exists. I was unable to fully verify how the `/hookify` command or `conversation-analyzer` agent generates the actual `.local.md` file content (only the agent's chat-facing markdown output was available, not the command that writes YAML), so I cannot confirm with certainty that the analyzer-driven flow *always* produces safely-quoted patterns; this is an unverified assumption worth confirming.

### Recommendation
- In `Condition.from_dict`, coerce `pattern` (and `field`/`operator`) to `str` (e.g., `str(data.get('pattern', ''))`) so type confusion from YAML parsing cannot occur.
- In `RuleEngine._check_condition` and `_regex_match`, wrap operator evaluation in a `try/except Exception` that treats any evaluation error as a non-match (`return False`) for that specific condition, rather than letting it propagate and abort the whole `evaluate_rules` pass.
- In `pretooluse.py`'s top-level exception handler, do not treat "hook error" as equivalent to "allow": at minimum, log/surface the error distinctly from a normal "no match" result, and consider failing closed (denying) for `action: block`-intended events when the plugin's rule set cannot be safely evaluated.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py` test suite (or a new test file):
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_non_string_pattern_does_not_fail_open():
    bad_rule = Rule(
        name="block-chmod-777",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="contains", pattern=777)],  # unquoted YAML int
        message="Blocked dangerous chmod",
    )
    dangerous_rule = Rule(
        name="block-rm-rf",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")],
        message="Blocked dangerous rm -rf",
    )
    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /"},
    }
    # Currently this raises TypeError inside evaluate_rules instead of returning a deny decision.
    result = engine.evaluate_rules([bad_rule, dangerous_rule], input_data)
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", (
        "A malformed condition must not prevent other block rules from firing; "
        "evaluate_rules must never raise or silently allow"
    )
```
Integration-level assertion at the `pretooluse.py` main() level: feed the same `input_data` via stdin with the two rules loaded, and assert the printed JSON contains `hookSpecificOutput.permissionDecision == "deny"` (never a bare `systemMessage`-only "Hookify error" payload) and that the process still communicates a deny decision before `sys.exit(0)`.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
