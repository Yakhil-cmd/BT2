Based on the investigation, there is a genuine binding mismatch analogous to the reported bug class ("a field acted upon but not covered by the same trust boundary used to authenticate it").

### Title
Webhook signature/organization binding does not cover the repository field used to route writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')` [1](#0-0) . Once the signature is accepted, every `Webhooks::Handlers::Handler` subclass resolves the target `Stack`/`Repository` using a *different* payload field: `payload.dig('repository', 'full_name')` [2](#0-1) .

### Finding Description
The equality that should hold is: `organization used to select/verify the signing secret == organization that owns the repository whose state is mutated`. These are two independently attacker-controlled JSON fields (`repository.owner.login` vs `repository.full_name`) inside the same unsigned-until-verified payload, and nothing enforces that `repository.full_name` starts with `repository.owner.login`. `verify_webhook_signature` in `lib/shipit/github_app.rb` further weakens this: if the resolved organization's config has no `webhook_secret` set, verification trivially returns `true` with no HMAC check at all [3](#0-2) . In a deployment where any configured GitHub App/organization lacks a `webhook_secret` (or its secret is otherwise obtainable), an attacker who can hit the shared `/webhooks` endpoint can set `repository.owner.login` to that low-security organization to pass `verify_signature`, while setting `repository.full_name` to `victim-org/victim-repo` so that `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. operate on a stack belonging to an entirely different, unrelated organization [4](#0-3) .

### Impact Explanation
This breaks the core trust boundary between "who authenticated this webhook" and "whose repository state gets written," directly mirroring the CometBFT class of bug where the field verified and the field acted upon diverge. Handlers like `PushHandler` trigger `stack.sync_github` (fetching commits from GitHub and appending them to the stack) and `StatusHandler` creates commit statuses on arbitrary target commits — writes into a different organization's stack/commit history than the one whose credentials were checked.

### Likelihood Explanation
Requires (a) at least one organization/GitHub App configured in `Shipit.github(organization: ...)` without a `webhook_secret` (or a leaked/guessable one), and (b) the target stack's repository being registered under a different organization/full_name that the attacker names in the crafted payload. This is plausible in any multi-tenant Shipit deployment mixing internal/low-trust orgs with higher-trust ones, but is configuration-dependent rather than universally exploitable — I could not fully verify from the indexed files whether `config/routes.rb` or deployment conventions guarantee a `webhook_secret` is always mandatory for every configured organization (this constraint lives in host-app secrets configuration, outside `lib/shipit/**`).

### Recommendation
Bind the two lookups to the same field: derive both the signature-verification organization and the target repository from the same authenticated identifier (e.g., verify against `repository.full_name`'s owner segment, or reject/require `repository.owner.login` to equal the prefix of `repository.full_name` before dispatching to handlers). Additionally, make `webhook_secret` mandatory (fail closed) rather than defaulting to `true` when absent, in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure two orgs in Shipit: `low-trust-org` (no `webhook_secret` configured) and `victim-org` (has a stack tracking `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "low-trust-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "low-trust-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) regardless of the actual `X-Hub-Signature` header [5](#0-4) .
4. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("victim-org/victim-repo")` [2](#0-1)  and triggers a sync/`GithubSyncJob` against the victim's stack, despite the request never being authenticated against `victim-org`'s webhook trust.
