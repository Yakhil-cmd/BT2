### Title
Unbounded, unpaginated iteration over all access keys in `EXPERIMENTAL_view_access_key_list` allows attacker-triggered node resource exhaustion - (File: `runtime/runtime/src/state_viewer/mod.rs`)

### Summary
`TrieViewer::view_access_keys` iterates the *entire* access-key trie prefix for an account with no limit, page size, or cap, unlike the sibling `view_state` RPC path which explicitly supports `prefix`/`after_key`/`limit` pagination (`chain/jsonrpc-primitives/src/types/view_state.rs`). Because the number of access keys (and gas keys/nonces) an account can hold is bounded only by how much storage stake the account owner is willing to pay — not by any protocol-enforced maximum — an attacker can grow an account's access-key set arbitrarily large and then repeatedly issue the unpaginated `EXPERIMENTAL_view_access_key_list` RPC query against it, forcing full RPC/view-client nodes to perform unbounded trie iteration and memory allocation per single request. This mirrors the Splitter `claimForAllWindows()` pattern: an ever-growing, attacker-influenced counter (`currentWindow` / access-key count) is iterated in full within a single call with no range/pagination parameter, eventually making that call prohibitively expensive or causing node stalls.

### Finding Description
`view_access_keys` builds the raw trie prefix for an account's access keys and iterates over *all* matching keys, collecting them all into a `Vec` before returning: [1](#0-0) 

This function is invoked directly by the `ViewAccessKeyList` query handler with no `limit`/`after_key` parameters: [2](#0-1) 

The request type itself carries no pagination fields at all: [3](#0-2) 

Compare this to the `ViewState` RPC, which was explicitly designed with `prefix`, `after_key`, and `limit` fields to bound the amount of trie data read per request: [4](#0-3) 

Nothing in the protocol enforces a maximum number of access keys (or gas keys, each of which can itself have multiple nonces stored under separate trie keys) per account — a grep for any "max number of access keys" style constant returns no results. The only bound is storage-staking cost paid by the account owner, i.e., the same economic dynamic that let the Splitter attacker cheaply grow `currentWindow` via `incrementWindow()`.

Notably, nearcore developers *did* address the analogous risk for `DeleteAccountAction`, which iterates the same access-key/gas-key trie range during execution: they cap it via `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` and reject deletion (with `ActionErrorKind::DeleteAccountWithLargeState`) if the account's storage usage exceeds that bound: [5](#0-4) 

This shows the state-changing/gas-metered path was hardened against the Splitter-style DoS, but the *read-only* `view_access_keys` RPC path was not given an equivalent cap or pagination, leaving it as the unmitigated analog.

### Impact Explanation
An attacker can:
1. Create (or control) an account and add a very large number of access keys (and/or gas keys with many nonces), paying only the storage stake for that state — no execution gas cap applies to the *size* of the resulting key set beyond what the attacker is willing to spend.
2. Repeatedly call `EXPERIMENTAL_view_access_key_list` (or the underlying `view_access_key_list` JSON-RPC "query" method) against that account.

Each such call forces the serving RPC/view-client node to iterate the full trie range and materialize a `Vec` of every access key, with no limit. Sent at scale, this can consume disproportionate CPU/IO/memory on public RPC nodes relative to the cost paid by the attacker, degrading service for legitimate users (a "node… unbounded resource use" / availability-DoS impact). This does not require a malicious validator or peer — it is fully reachable via ordinary JSON-RPC requests against any full/view-client node serving that account's shard.

### Likelihood Explanation
Likelihood is moderate: exploitation requires only normal account and RPC access (no privileged role), and growing an access-key set to a size sufficient to cause meaningful per-query cost requires proportional NEAR locked for storage, which raises the cost floor for an attacker but does not prevent the attack — the same tradeoff the original Splitter bug exploited by paying WETH dust per `incrementWindow()` call. Public RPC providers that serve arbitrary accounts to arbitrary callers are the most exposed.

### Recommendation
Add pagination to `ViewAccessKeyList`/`view_access_keys` analogous to `ViewState`'s `after_key`/`limit`, and/or enforce a maximum number of access keys (and gas-key nonces) per account, or a maximum response size analogous to `TooLargeContractState` for `ViewState`. At minimum, cap the number of trie entries iterated/returned per RPC call and require callers to page through results.

### Proof of Concept
1. Using a signer with sufficient NEAR balance, submit many `AddKey` actions (or gas-key equivalents) to a single account until the number of stored access keys is large (bounded only by the account's storage-stake budget).
2. Issue repeated `EXPERIMENTAL_view_access_key_list` (or `query`/`view_access_key_list`) JSON-RPC requests for that account against a target full/RPC node.
3. Observe that each request triggers full, unpaginated iteration in `view_access_keys` (`runtime/runtime/src/state_viewer/mod.rs:150-192`) via the `QueryRequest::ViewAccessKeyList` handler (`chain/chain/src/runtime/mod.rs:1379-1400`), with response size and processing cost scaling linearly with the number of keys and no cap — unlike the `ViewState` path which supports `limit`/`after_key` pagination.

    pub fn view_access_keys(
        &self,
        state_update: &TrieUpdate,
        account_id: &AccountId,
    ) -> Result<Vec<(PublicKeyHandle, AccessKey)>, errors::ViewAccessKeyError> {
        let prefix = trie_key_parsers::get_raw_prefix_for_access_keys(account_id);
        let access_keys =
            state_update
                .iter(&prefix)?
                .map(|key| {
                    let key = key?;
                    let key_handle = parse_key_handle_from_access_key_key(&key, account_id)
                        .map_err(|_| errors::ViewAccessKeyError::InternalError {
                            error_message: "Unexpected invalid access key from iterator"
                                .to_string(),
                        })?;
                    if let Some(_index) =
                        parse_nonce_index_from_gas_key_key(&key, account_id, &key_handle).map_err(
                            |_| errors::ViewAccessKeyError::InternalError {
                                error_message: "could not parse nonce index".to_string(),
                            },
                        )?
                    {
                        // This is a gas key nonce, skip it.
                        return Ok(None);
                    }
                    let access_key = near_store::get_access_key_by_handle(
                        state_update,
                        account_id,
                        &key_handle,
                    )?
                    .ok_or_else(|| {
                        near_primitives::errors::StorageError::StorageInconsistentState(format!(
                            "iterator yielded an access-key trie key with no value: {key_handle}"
                        ))
                    })?;

                    Ok(Some((key_handle, access_key)))
                })
                .filter_map_ok(|x| x)
                .collect::<Result<Vec<_>, errors::ViewAccessKeyError>>();
        access_keys
    }
