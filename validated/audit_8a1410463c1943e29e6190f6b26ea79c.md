### Title
AA trigger attribution to the alphabetically-first author (not the true depositor) causes funds/state to be permanently misattributed and unclaimable in multi-authored triggers - (File: aa_composer.js)

### Summary
`getTrigger()` in `aa_composer.js` unconditionally assigns the AA's notion of "trigger sender" to `objUnit.authors[0].address` — the first author sorted lexicographically — rather than to whichever address(es) actually funded the payment output that reached the AA. Because `validation.js`'s `validateAATrigger()` allows any number of distinct authors to co-sign a unit that pays an AA (it only forbids more than one output per address/asset to the same AA, not multi-author triggers), a genuine second co-author who contributed part of the funds sent to the AA is never recognized as the depositor. Any AA-side accounting keyed by `trigger.address` (state vars, deposit/rewards bookkeeping, bounce/refund logic) is permanently attributed to the first author instead, and the real contributing co-author has no way to reclaim or be credited for their share — mirroring the reported Euler bug where stake/rewards get irreversibly delegated to an assumed identity instead of the true, not-yet-known owner.

`trigger.address` is set to `objUnit.authors[0].address` — the *first author by address sort order* — regardless of which author's input(s) actually funded the output(s) directed to the AA. `validateAuthors()` only requires author addresses to be sorted, it does not tie a specific author to a specific output: [2](#0-1) 

`validateAATrigger()` (invoked during normal unit validation, not just AA-response validation) permits multiple authors to co-sign a triggering unit; it only checks that a given (AA address, asset) pair does not receive more than one output, not that only a single author may fund an AA-directed payment: [3](#0-2) 

Consequently, a unit can be composed with two independent authors — e.g. address `A` (alphabetically first) and address `B` — where the combined payment message sends coins to an AA using inputs contributed by both `A` and `B` (each author signs their own inputs in the same unit, a standard multi-author/atomic-unit pattern already supported by the wallet composer, see `composer.js` `composeAuthorsForAddresses`/`bMultiAuthored` handling of `earned_headers_commission_recipients` for multi-author units): [4](#0-3) 

When such a unit becomes stable and triggers the AA, `handlePrimaryAATrigger()` calls `getTrigger(objUnit, address)`, and the resulting `trigger.address` is always `A`, never `B`, even though `B` genuinely contributed funds to the output received by the AA: [5](#0-4) 

Any AA logic that tracks per-depositor accounting via `trigger.address` (e.g. `var[trigger.address]['balance'] += trigger.output[[asset=base]]`) will silently and irreversibly credit the entire deposit to `A`. This state update, once written via `addResponse`/`aa_responses`/`stateVars`, is part of the AA's committed, stable state and cannot later be corrected to recognize `B` as a rightful depositor — there is no mechanism for the AA (or any subsequent unit) to retroactively split or reassign the already-recorded deposit to `B`.

This is architecturally identical to the reported bug: an irreversible on-chain crediting decision is made using an *assumed* identity (the first/alphabetically-sorted author, analogous to Euler's "the account itself") instead of the identity that will later turn out to be the actual, true contributor/owner of the value, and the mis-credited value becomes permanently unclaimable by the real owner.

### Impact Explanation
Any AA that implements per-address balance, staking, reward, or refund accounting based on `trigger.address` in a design that can be triggered by multi-authored units is exposed to permanent, unrecoverable loss of funds/rewards for the non-first co-author. Because the AA's own bookkeeping (state vars, deposit ledgers) is the source of truth for withdrawal rights, and this bookkeeping is written atomically and irreversibly at trigger time, the second author's contribution is stuck forever inside the AA under the first author's name — a direct AA fund loss/freezing scenario for the mis-attributed party.

### Likelihood Explanation
This requires (a) an AA whose logic keys value tracking off `trigger.address` for the depositor's identity (a common and natural pattern for staking/vault-like AAs), and (b) a unit poster/trigger sender crafting or unintentionally submitting a multi-authored triggering unit where funds directed at the AA were sourced from more than one author's inputs. Both conditions are reachable by any unprivileged AA trigger sender using standard multi-author transaction composition already supported by ocore (`composer.js` multi-author flow), so likelihood is non-trivial for any AA that doesn't explicitly reject multi-author triggers.

### Recommendation
Either (a) have `validateAATrigger()` reject primary AA triggers whose unit has more than one author, closing off the ambiguous-attribution case entirely, or (b) have `getTrigger()` explicitly reject/flag triggers where the payment output(s) directed to the AA cannot be unambiguously attributed to a single author's inputs, so AA developers relying on `trigger.address` for depositor bookkeeping cannot be silently given the wrong identity.

### Proof of Concept
1. Deploy an AA that tracks deposits per depositor, e.g. `var[trigger.address]['deposited'] += trigger.output[[asset=base]];` with a withdrawal message gated by `trigger.address == var['depositor']`.
2. Address `B` composes a unit together with co-author `A` (`A < B` lexicographically) where both `A`'s and `B`'s inputs fund a single payment output to the AA (multi-authored unit, both sign their own inputs, as supported by `composer.js`).
3. The unit stabilizes; `aa_composer.js`'s `getTrigger()` sets `trigger.address = A` (see `aa_composer.js:376`), so the AA credits the entire deposit to `A`, not `B`.
4. `B` has no way to invoke the AA as `trigger.address == B` for this deposit and permanently cannot withdraw the value they contributed — funds are stuck under `A`'s AA-tracked balance.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
