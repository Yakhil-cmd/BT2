This confirms the vulnerability path. Key facts:

- `Shipit.github(organization: repository_owner)` selects the GitHub App config keyed by whatever `repository.owner.login` says in the JSON payload [1](#0-0) , and `repository_owner` is read straight from attacker-controlled `params.dig('repository', 'owner', 'login')` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org's `webhook_secret` is blank [3](#0-2) , and multi-org configs (e.g. `test/dummy/config/secrets_double_github_app.yml`) can legitimately have a per-org `webhook_secret: nil` [4](#0-3) .
- Separately, `AssignedHandler#repository` resolves the target repository from `params.repository.full_name` [5](#0-4) , a JSON key entirely independent of `repository.owner.login` used for signature verification — nothing binds the two together.
- `AssignedHandler#process` then blindly persists the attacker-supplied `pull_request` object, including `assignees`/`labels`/`title`, onto the matched victim `PullRequest` [6](#0-5) , for both `assigned` and `unassigned` actions [7](#0-6) .

This means an attacker can craft one JSON body with `repository.owner.login = "org-with-no-webhook-secret"` (to pass `verify_signature` with no secret at all) and `repository.full_name = "victim-org/victim-repo"` (to target an unrelated, secured stack), and the handler will write fabricated `assignees`/`labels`/`title` onto the real victim `PullRequest` row with no relation to actual GitHub state.

### Title
Webhook signature verification org is decoupled from the target repository, letting a no-secret org forge PR state for any other repository - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using the attacker-controlled `repository.owner.login` field, while `AssignedHandler` (and the other PR handlers) resolve the actually-mutated repository/stack from the independent `repository.full_name` field in the same JSON body. Because nothing binds these two fields together, a webhook payload claiming to originate from an organization that has no `webhook_secret` configured passes signature verification unconditionally, while its `full_name` can point at a completely different, secured victim organization's repository, whose `PullRequest` row then gets overwritten with attacker-chosen `assignees`/`labels`/`title`.

### Finding Description
The broken binding is: `verified_org (params.repository.owner.login used in verify_signature) == mutated_repo_owner (params.repository.full_name owner used in AssignedHandler#repository)`. These must be equal for the signature check to mean anything about the data being processed, but the code never enforces it.

Path:
1. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository', 'owner', 'login')` [1](#0-0) , [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that org's `webhook_secret` is not configured: `return true unless webhook_secret` [3](#0-2) . Multi-org configurations legitimately leave `webhook_secret` blank for some orgs, as shown in the test fixture `secrets_double_github_app.yml` [4](#0-3) .
3. Once `head(422)`/exception paths are avoided, `WebhooksController#create` dispatches the raw, still fully attacker-controlled JSON to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) .
4. `AssignedHandler#repository` resolves the repository from `params.repository.full_name` — a different JSON field than the one used for signature verification — via `Shipit::Repository.from_github_repo_name` [5](#0-4) .
5. `AssignedHandler#pull_request` then looks up the real, existing `Shipit::PullRequest` scoped to that resolved repository [9](#0-8) .
6. `AssignedHandler#process` unconditionally does `pull_request.update(github_pull_request: params.pull_request)` for both `assigned` and `unassigned` actions [10](#0-9) , persisting the entire attacker-supplied `pull_request` object — including `assignees`, `labels`, and `title` — with no cross-check against real GitHub data and no re-verification that this data belongs to the org whose secret (or lack thereof) authorized the request.

Exploit: attacker (owning/controlling a repo under `NoSecretOrg`, an org configured on this Shipit instance without a `webhook_secret`) POSTs to `/webhooks` with header `X-Github-Event: pull_request` and a body where `repository.owner.login = "NoSecretOrg"` but `repository.full_name = "victim-org/victim-repo"`, `action: "unassigned"`, and a `pull_request` object with the real victim PR `number` and fabricated `assignees`/`labels`/`title`. `verify_signature` passes because `NoSecretOrg` has no secret; `AssignedHandler` then finds and overwrites the victim's `PullRequest` row.

None of the mandated guards close this gap: `verify_signature` only checks a signature against a secret selected from attacker data, it does not check org-repository consistency; `drop_unhandled_event` only filters unknown event types [11](#0-10) ; the `ExplicitParameters` schema in `AssignedHandler` only validates types/presence, not cross-field consistency [12](#0-11) ; `Repository` model validations only constrain `owner`/`name` character sets, not the requesting org [13](#0-12) .

### Impact Explanation
An attacker who controls any GitHub organization/app configured on the Shipit instance without a `webhook_secret` can forge fabricated PR metadata (assignees, labels, title, state) into any other, unrelated stack's `PullRequest` record — a payload targeting one repository mutating another's stack/PR data, satisfying the "Critical" category (cross-repository/cross-tenant mutation via a request that did not authenticate for that repository). If a Stack's deploy or merge gating logic consults `github_pull_request.assignees`/`labels`/`state` (e.g., review-stack provisioning or PR-based gating), this can be leveraged toward an unauthorized deploy/merge decision. This is repeatable against arbitrary victim stacks/PR numbers as long as the attacker can guess or observe the victim's open PR number.

### Likelihood Explanation
This requires the specific configuration precondition granted by the question: the Shipit instance must be configured with at least one GitHub org/app entry lacking a `webhook_secret` (a supported, documented configuration — see `docs/setup.md` showing `webhook_secret:` left blank, and the multi-org test fixture) [14](#0-13) . Given that precondition, the attack requires no secrets, no session, and no privileged role — only the ability to send an arbitrary HTTP POST to `/webhooks` with a crafted JSON body, and knowledge of the victim's repository full name and PR number (both public/discoverable). Cost is a single unauthenticated HTTP request per PR, fully repeatable.

### Recommendation
Bind the signature-verification identity to the data being mutated: derive the repository/stack strictly from the same organization used to select and verify the webhook secret, e.g., require `params.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` before dispatching to handlers, or better, have `Repository.from_github_repo_name` reject repositories whose owner does not match the verified `repository_owner`. Additionally, treat a missing per-org `webhook_secret` as a configuration error rather than a silent verification bypass (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure a test app with two orgs: `NoSecretOrg` (`webhook_secret: nil`) and `victim-org` (`webhook_secret` present), using a config fixture equivalent to `secrets_double_github_app.yml`.
2. Create `victim_repo = shipit_repository(owner: "victim-org", name: "victim-repo")`, a `Stack` for it, and a `Shipit::PullRequest` with `number: 2`, `github_pull_request: { "assignees" => [], "labels" => [] }`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no `X-Hub-Signature` header, and body:
   ```json
   {
     "action": "unassigned",
     "number": 2,
     "pull_request": { "...": "...", "number": 2, "assignees": [{"login": "attacker-chosen-user"}], "labels": [{"name": "attacker-chosen-label"}] },
     "repository": { "owner": { "login": "NoSecretOrg" }, "full_name": "victim-org/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
4. Assert `response.status == 200` (not 422), then `assert_equal ["attacker-chosen-user"], victim_pull_request.reload.assignees.map(&:login)` and `assert_equal ["attacker-chosen-label"], victim_pull_request.labels.map(&:name)` — i.e., the assignees/labels persisted verbatim on the victim's `PullRequest` even though the request was verified against, and only authorized for, `NoSecretOrg`, not `victim-org`.
