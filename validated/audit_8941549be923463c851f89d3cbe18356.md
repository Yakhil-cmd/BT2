### Title
StatusHandler ignores repository scope when matching commits by SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler`'s param schema only `requires :sha, String` and `:state, String`, with no `repository` requirement at all, and `#process` looks up commits with `Commit.where(sha: params.sha)` across the *entire* `commits` table rather than scoping to the stack identified by the webhook's `repository.full_name`. This lets any legitimately-signed "status" webhook for one repository update the `Status` of a same-SHA commit belonging to a completely different (victim) stack.

### Finding Description
The claimed binding — "minimum payload to pass Handler param validation == minimum payload to establish repository scope" — is broken. The `StatusHandler` params block is: [1](#0-0) 

Only `sha` and `state` are `requires`; `repository` is not declared at all (unlike `OpenedHandler`/`ClosedHandler`/`AssignedHandler`, which all `requires :repository { requires :full_name, String }`) [2](#0-1) . Consequently `params.repository` is never read in `#process`: [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, unscoped lookup across every stack/repository tracked by the Shipit instance, and `commit.create_status_from_github!(params)` writes the status to whichever stack that `Commit` row actually belongs to (`create_status_from_github!` → `statuses.replicate_from_github!(stack_id, ...)`) [4](#0-3) [5](#0-4) .

The controller-level guard, `verify_signature`, only checks that the payload is HMAC-signed with the webhook secret of the organization named in `repository.owner.login`/`organization.login` — it authenticates *which org's secret was used*, not *which repository's commit may be touched*: [6](#0-5) 

Because git commit SHAs are content-addressed, an attacker who owns/controls any repository that shares commit history with a victim's tracked repository (e.g., a fork within the same GitHub App installation, or any repo sharing an ancestor commit) can cause GitHub to deliver a genuinely-signed `status` event (e.g., via their own CI or a `POST /repos/{owner}/{repo}/statuses/{sha}` call on a commit they control) whose `sha` collides with a commit already tracked in the victim's stack. Nothing in `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema checks that `repository.full_name` in the payload matches the repository owning the `Commit` row being mutated — that binding simply does not exist for this handler.

Exploit payload: `{"sha": "<victim_sha>", "state": "success", "repository": {"full_name": "attacker/fork", "owner": {"login": "attacker-org"}}}` with the `X-Github-Event: status` header and a signature valid for `attacker-org`'s webhook secret (a secret the attacker legitimately possesses because GitHub computed it for their own, real event). This payload satisfies the entire params schema and controller guards while writing a `Status` onto the victim's commit/stack.

### Impact Explanation
A `Status` record written for a commit the attacker does not own can flip a victim stack's CI gate from red/pending to `success`, which is used by `Commit#deployable?` and can trigger `ProcessMergeRequestsJob`/continuous delivery for the victim stack [7](#0-6) . This is a payload for one repository mutating another repository's commit/stack state, which can cascade into an unauthorized deploy for the victim — matching the Critical impact category. This is repeatable against any stack whose tracked commits share a SHA with a repository the attacker can trigger status events from (forks, shared-history repos in the same org, etc.).

### Likelihood Explanation
The attacker needs: (1) a repository capable of emitting a real GitHub `status` webhook (any repo they control, including a fork), which is trivial and unprivileged; (2) a commit SHA shared with the victim's tracked stack, which is common for forks of actively-developed open-source or shared-history repos and does not require guessing since SHAs of shared ancestors are public knowledge. No Shipit secrets, sessions, or maintainer status are required. The attack is fully repeatable and requires no special Shipit-side misconfiguration beyond normal multi-repo/multi-fork usage.

### Recommendation
Add `requires :repository { requires :full_name, String }` to `StatusHandler`'s params (matching the other handlers) and scope the commit lookup to the repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` through `Stack`/`Repository` filtered by `params.repository.full_name`, instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
test ":status webhook for one repository must not update a commit belonging to another stack" do
  request.headers['X-Github-Event'] = 'status'

  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to victim_stack

  attacker_payload = {
    sha: victim_commit.sha,
    state: 'success',
    repository: { full_name: 'attacker/fork', owner: { login: 'attacker-org' } }
  }.to_json

  # signature bypass mirrors existing test setup where verify_signature is stubbed
  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: attacker_payload, as: :json
  end
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of the attacker-declared `repository`, so `victim_commit.statuses.count` increases by 1 — proving the params-validation minimum (`{sha, state}`) is not equal to the repository-scope minimum required to safely mutate `victim_commit`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
