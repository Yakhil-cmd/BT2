### Title
`ERC20Transactor` credits the full nominal ERC20 amount to the XCM holding register without verifying the checking account's actual balance delta, breaking on fee-on-transfer ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` performs an ERC20 `transfer(checking_account, amount)` call and, on a bare `true` return, unconditionally credits `amount` (the nominal, requested amount) into the XCM `AssetsInHolding` register via `Erc20Credit(amount)` — never re-reading the checking account's actual ERC20 balance to see how much was really received. `deposit_asset_with_surplus` then attempts to move that same nominal `amount` out of the checking account to the beneficiary. Any ERC20 contract that implements fee-on-transfer semantics (deducting a fee such that the recipient receives less than `value`, while still returning `true`) will desynchronize the checking account's real token balance from the XCM holding register's belief about it.

### Finding Description
`ERC20Matcher` accepts any `Location` of the shape `(0, [AccountKey20 { .. }])` [1](#0-0) , so a caller can name an arbitrary, self-deployed ERC20 contract address as the "asset" in a `WithdrawAsset`/`DepositAsset` XCM program, exactly as demonstrated by the existing test `withdraw_and_deposit_erc20s` which deploys an arbitrary contract via `bare_instantiate` and references it directly by `AccountKey20` in a locally-executed XCM message [2](#0-1) .

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` from the user's origin, and on success unconditionally does:
```
Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))
``` [3](#0-2) 

`Erc20Credit` is explicitly documented as not enforcing real balance constraints — "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [4](#0-3) . If the target ERC20 contract deducts a fee from the transfer (i.e. the checking account's real balance only increases by `amount - fee`, not `amount`), the holding register still records `amount` as available.

`deposit_asset_with_surplus` subsequently issues `IERC20::transferCall{ to: beneficiary, value: amount }` from the checking account for that same nominal `amount` [5](#0-4) . Because the checking account never actually received the full `amount` (only `amount - fee`), this call reverts for insufficient balance if the checking account had no other pre-existing balance of this specific token, or, if the checking account holds accumulated balance of that token from other users' prior legitimate transfers, the deposit will succeed by silently drawing down real tokens that belong to those other users/transfers — masking the deficit from this specific withdrawal at the expense of the shared checking account's pooled balance.

Locally, `PolkadotXcm::execute` reports `Outcome::Incomplete`/error for a failing instruction but the dispatchable itself still returns `Ok(())`; the state mutation already performed by the successful `withdraw_asset` (the real ERC20 `transfer` moving `amount - fee` out of the user into the checking account) is not rolled back, while the corresponding `deposit_asset` either fails outright (funds trapped/lost for the user) or drains the pooled checking account (loss borne by other participants), matching the class of bug described in the source report: "the contract only supports fee-on-transfer tokens if they reduce the fee from the transfer amount" — here the transactor assumes exactly that, with no verification.

### Impact Explanation
This is a fund-accounting break, not a theoretical mismatch: it produces measurable loss of user funds (trapped/burned tokens on failed deposit) or loss/drain of a shared pooled account's balance (checking account) that other users depend on, without any privileged actor being required. The severity is bounded by the fact that it requires the "asset" to be an ERC20 contract exhibiting fee-on-transfer behavior on the specific `transfer()` selector used, and by the fact that `ERC20Transactor`/ERC20 XCM asset support is a newly introduced feature (not a broadly deployed pre-existing bridge). Given the parallels to the original Medium-severity finding (accounting break on non-standard token behavior, not privileged, deterministic reproduction, real fund loss), this aligns with a Medium classification.

### Likelihood Explanation
Likelihood is moderate: the attacker (or an unaware integrator) needs only to deploy an ordinary Solidity ERC20 contract implementing a common fee-on-transfer pattern (many real-world tokens do this) and reference it by its `AccountKey20` address in an XCM `withdraw_asset`/`deposit_asset` program — no governance, no registry entry, no special permission is required, as shown directly by the existing test harness pattern that deploys and uses arbitrary contract bytecode this way.

### Recommendation
`withdraw_asset_with_surplus` should measure the checking account's actual ERC20 balance before and after the `transfer` call (via `balanceOf`) and credit the holding register with the observed delta rather than the nominal requested `amount`. Symmetrically, `deposit_asset_with_surplus` should verify the beneficiary's actual balance increased by the intended amount (or transfer exactly what was actually held, per delta-checked accounting) before considering the operation complete, and any shortfall should be reflected back into the XCM error/trap path rather than silently drawn from the shared checking account. At minimum, this transactor's documentation and configuration should explicitly disclaim support for non-standard-behaving ERC20 tokens (fee-on-transfer, rebasing, etc.), the same mitigation recommended in the original report.

### Proof of Concept
No executable PoC was run in this session (tool access is read-only/ask-only). Reachability and mechanism were verified statically:
- `ERC20Matcher` accepts arbitrary local `AccountKey20` locations without a permissioned registry [1](#0-0) .
- The existing test `withdraw_and_deposit_erc20s` demonstrates the exact reachable path: a user-deployed arbitrary contract referenced directly in a `withdraw_asset`/`deposit_asset` XCM program executed via `PolkadotXcm::execute` from a signed origin [2](#0-1) .
- `withdraw_asset_with_surplus` credits the nominal `amount`, not an observed balance delta [3](#0-2) .
- `deposit_asset_with_surplus` moves that same nominal amount out of the shared checking account [5](#0-4) .

A concrete reproduction would require deploying a Solidity ERC20 with a `transfer()` override that deducts a fee from the sender's remaining balance beyond `value` (returning `true`), then running the same `withdraw_asset`/`deposit_asset` XCM message as the existing test, and asserting that either the deposit reverts (trapped funds) or that the checking account's real balance for that token goes negative relative to what the holding register believed — this reproduction was not executed in this session and its pass/fail result is unverified.

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}

/// This type implements the necessary imbalance accounting traits but does not perform

	}
