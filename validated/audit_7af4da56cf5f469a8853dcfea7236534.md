### Title
DDOS/fund-freezing risk: no dust-output threshold for AA asset balances lets an attacker force an AA to process unbounded tiny inputs when spending a non-base asset - (File: aa_composer.js)

### Summary
`aa_composer.js`'s unit-composition logic that lets an AA spend its own balance explicitly filters out tiny/dust outputs to protect against spam, but this protection is **only applied to the base asset (bytes)**. Any other asset that an AA deals with (a custom token) has no minimum-output threshold, so an unprivileged attacker can flood the AA address with an unbounded number of minimal-amount outputs of that asset. When the AA later tries to spend its balance of that asset in response to a legitimate trigger, it must pull in every one of these dust outputs as inputs, since the max-inputs check is explicitly skipped for AA-generated units.

### Finding Description
When an AA composes a response payment, `completePaymentPayload()`'s `readStableOutputs()`/`readUnstableOutputsSentByAAs()` helpers select unspent outputs at the AA's address to use as inputs. The code comment makes the intended anti-DDOS design explicit: [1](#0-0) 

```
function readStableOutputs(handleRows) {
    if (asset && assetInfos[asset].auto_destroy ...)
        return handleRows([]);
    // byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond
    conn.query(
        "SELECT unit, message_index, output_index, amount, output_id \n\
        FROM outputs \n\
        CROSS JOIN units USING(unit) \n\
        WHERE address=? AND asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+" AND is_spent=0 \n\
        ...
```

The `amount >= FULL_TRANSFER_INPUT_SIZE` dust filter is only injected into the query **when `asset` is falsy** (i.e., for the base/bytes asset). When `asset` is set (any custom token the AA transacts in), no minimum-amount filter is applied at all, so every dust output ever sent to the AA in that asset is eligible to be pulled in as an input.

`iterateUnspentOutputs()` then loops over every row returned and pushes each into `payload.inputs` with no cap on the number of inputs collected for non-base assets: [2](#0-1) 

Normally the network-wide safeguard `MAX_INPUTS_PER_PAYMENT_MESSAGE` would bound how many inputs a payment message can contain, but this check is explicitly bypassed for AA-authored units: [3](#0-2) 

```
if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA)
    return callback("too many inputs");
```

Contrast this with the wallet-side coin-picking logic in `inputs.js`, which explicitly limits the number of rows fetched to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` to stay within protocol limits: [4](#0-3) 

No analogous cap exists in the AA composer's `iterateUnspentOutputs`/`readStableOutputs` path for non-base assets.

### Impact Explanation
Any unprivileged user can send a normal `payment` message to an AA address containing many outputs of a custom asset with amounts as small as 1 unit (the trigger validation and bounce-fee checks only enforce minimums on the base asset and, for other assets, "ignore silently" if the amount is below `bounce_fees[asset]`, per `aa_composer.js:1855-1859`). Because there is no dust filter for non-base assets, all of these outputs remain spendable and will later be pulled into the AA's own outgoing payment as inputs. This can:
- Cause the AA's generated response unit for that asset to become abnormally large, potentially exceeding size/oversize-fee constraints and causing `sendUnit` to fail (`bounce('not enough funds for ...')`), i.e. denial-of-service on that AA's ability to pay out in that asset.
- Once the AA cannot successfully spend, the dust outputs remain unspent, so every future attempt to spend that asset repeats the same failure — effectively **permanently freezing the AA's funds in that asset** (analogous to the reported bug's "borrowers can produce lots of dust positions" DDOS impact, but here it directly harms the AA and its users/counterparties instead of a lender).
- Because the base-asset case explicitly cost-limits dust (< `FULL_TRANSFER_INPUT_SIZE` outputs are ignored) while the asset case has zero such protection, this is a genuine asymmetry/oversight rather than an intentional design choice, matching the root cause of the original report (a missing per-asset minimum threshold enabling spam by an ordinary, unprivileged actor).

### Likelihood Explanation
Any address (no special privileges) can send a standard `payment` message with many small-amount outputs of a custom asset to any AA that is known to hold or transact in that asset. No admin misconfiguration is even required (unlike the Kairos case) — the missing threshold is unconditional for every non-base asset in every AA, making this reachable in normal operation whenever an AA is known to accept/hold a specific token.

### Recommendation
Apply an equivalent minimum-output/dust threshold (analogous to `FULL_TRANSFER_INPUT_SIZE` for bytes) to the asset branch of `readStableOutputs()`/`readUnstableOutputsSentByAAs()` in `aa_composer.js`, and/or cap the number of asset inputs gathered per payment message (mirroring the `MAX_INPUTS_PER_PAYMENT_MESSAGE-2` limit already used in `inputs.js` for wallet-composed payments) so that AA-generated payment messages for custom assets cannot be forced to include an unbounded number of dust inputs.

### Proof of Concept
1. Deploy/observe an AA that accepts and later re-spends a custom asset `X` (common pattern: exchange/bank AAs as seen in `test/samples/a_bank_without_percent.oscript` and `order_book_exchange.oscript`).
2. As an unprivileged user, send hundreds/thousands of payment messages, each with a 1-unit output of asset `X` to the AA's address (allowed — no minimum enforced for non-base assets in trigger validation, see `aa_composer.js:1855-1859`).
3. Trigger the AA to spend from its `X` balance (e.g., normal user interaction that causes the AA to pay out asset `X`).
4. Observe `completePaymentPayload()` → `readStableOutputs()` selecting all of the dust outputs (no `amount >=` filter applied since `asset` is truthy) and `iterateUnspentOutputs()` including all of them as inputs, unconstrained by `MAX_INPUTS_PER_PAYMENT_MESSAGE` because `objValidationState.bAA` is true (`validation.js:2137`), producing an oversized/failing response unit and leaving the AA unable to spend its `X` balance going forward.
