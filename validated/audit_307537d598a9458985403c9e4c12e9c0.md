### Title
`StatusHandler#process` writes `Status` rows for every stack sharing a commit `sha`, bypassing repository/organization scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and never restricts the query to the repository/organization that authenticated the webhook via `Handler#stacks`/`Repository.from_github_repo_name`. Any organization whose webhook secret is known to the sender can post a `status` event naming its own repository but a commit `sha` value that also exists in unrelated tenants' stacks (e.g., the well-known empty-tree SHA or any duplicated initial commit), causing `Status` rows to be created on stacks belonging to organizations that never authenticated the request.

### Finding Description
The broken binding is:
`authenticated_organization (repository_owner used in verify_signature) == { organizations of Stack rows that get mutated by StatusHandler#process }`

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `payload.dig('repository','owner','login')` (or the `organization` sub-object) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, scoping HMAC verification to a single organization's `webhook_secret`. [1](#0-0) 
- The base `Handler` class exposes a `stacks` helper that correctly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, i.e., only stacks belonging to the repository named in the payload. [2](#0-1) 
- `StatusHandler#process`, however, never calls `stacks`. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, an unscoped, instance-wide lookup across all `Stack`s/`Repository`s that happen to have a `Commit` row with the same `sha`. [3](#0-2) 
- `Commit#create_status_from_github!` -> `add_status` creates a `Status` via `statuses.replicate_from_github!(stack_id, github_status)`, writing directly into whichever `stack` the matched `Commit` belongs to, regardless of which organization authenticated the webhook. [4](#0-3) 

Exploit flow: the attacker (or a legitimate but low-privilege user of tenant org "attacker") owns a repository mirrored into Shipit as `attacker/repo`. They configure their own GitHub webhook secret (which they legitimately know, since they administer their own repo/org's webhook) and send a `status` event with `repository.full_name = "attacker/repo"` and `sha` equal to a commit SHA that is shared across multiple tenants' `Stack`/`Commit` rows (trivially arranged when repositories are freshly initialized and share an initial/empty-tree commit, or via any accidental/engineered SHA collision across tenants). `verify_signature` succeeds because it only checks the attacker's own org's secret against `repository_owner = "attacker"`. `StatusHandler#process` then walks every `Commit` row in the entire database matching that `sha`, creating `Status` records on victim stacks the attacker never authenticated for.

None of the existing guards prevent this: `verify_signature` only proves the sender controls one organization's secret, it does not bind the payload's effect to that organization. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape (`sha`, `state`, etc.), not scope. `stacks`/`Repository.from_github_repo_name` scoping exists in the base class but is simply unused by this handler.

### Impact Explanation
Any org with a valid webhook secret for their own repository can inject `Status` rows (state, description, target_url, context) onto commits belonging to unrelated tenants' stacks, as long as a `sha` collision exists. This is a cross-tenant write of state not authorized by the mutated tenant, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Fabricated/forged CI statuses can affect deployability decisions (`Commit#deployable?`, `blocked?`) and even trigger downstream continuous deployment (`Commit#schedule_continuous_delivery`) on the victim stack, since a spoofed `success` status can flip merge/deploy eligibility for commits the attacker does not own. The attack is repeatable against any number of stacks sharing a colliding SHA, and can be performed by a single low-privilege webhook sender per request.

### Likelihood Explanation
Preconditions: the attacker must control (or know the webhook secret for) at least one Shipit-mirrored repository/org, and there must exist a commit `sha` collision between that repository's stack and one or more victim stacks. SHA collisions are entirely plausible in practice: fresh git repositories, template-based scaffolding, or empty-tree/empty-commit SHAs are commonly shared across many unrelated repositories. No GitHub or Shipit secrets belonging to the victim are required — only the attacker's own webhook secret for their own onboarded repository, which is a normal deployment configuration and not a privileged capability relative to other tenants.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring the base class's `stacks` helper, e.g. restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so only commits belonging to stacks of the repository named in `payload['repository']['full_name']` are updated.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, illustrative — actual file is out of scope per rules but described for validation):
1. Create 3 `Repository`/`Stack` fixtures: `attacker/repo`, `victim1/repo`, `victim2/repo`, each with a `Commit` sharing the same `sha` (e.g., the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`).
2. Stub `verify_signature`/`GithubHook` so the webhook posted for `attacker/repo` passes signature verification (using attacker's own configured secret).
3. POST a `status` webhook with `payload['repository']['full_name'] = 'attacker/repo'` and `sha` set to the shared value, `state: 'success'`.
4. Assert the binding equality before: `authenticated_org = 'attacker'`, `orgs_with_new_status = []`.
5. Assert after: `Shipit::Status.where(state: 'success').count` increased by 3 (one per stack sharing the sha), and `orgs_with_new_status = ['attacker', 'victim1', 'victim2']` ≠ `{authenticated_org}` — proving the cardinality mismatch and that `victim1`/`victim2` stacks were mutated without their organization authenticating the request.
