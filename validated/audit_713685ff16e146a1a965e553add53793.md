Based on my investigation, I've confirmed the vulnerability.

### Title
Webhook signature verification uses an attacker-supplied `repository.owner.login` field to select the verifying secret, allowing cross-organization forged events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a webhook's HMAC signature against based on `repository_owner`, a value taken directly from the unauthenticated JSON body of the very request being verified. `Shipit::Webhooks::Handlers::Handler#stacks`/`repository_name`, used afterwards to determine which `Stack`/`Repository` the event actually acts on, reads a *different* field (`repository.full_name`) from that same untrusted body. Because Shipit supports multi-tenant configuration (multiple GitHub organizations each with their own `webhook_secret`, per `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github_app_config`), the field used to pick the verifying secret and the field used to determine the acted-upon repository are never cross-checked against each other.

### Finding Description [1](#0-0) 

`verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to fetch the corresponding `GitHubApp` via `Shipit.github(organization: repository_owner)`, then verifies the raw HMAC signature against that organization's `webhook_secret`: [2](#0-1) 

Once the signature check for the *claimed* organization succeeds, `WebhooksController#create` dispatches the entire raw JSON payload to handlers: [3](#0-2) 

Handlers such as `PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::LabeledHandler`, etc., independently resolve the target `Stack`/`Repository` using `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because both `repository.owner.login` and `repository.full_name` are attacker-controlled fields of the same unauthenticated JSON body, and neither the controller nor the handlers verify that they are consistent with each other, an operator/administrator of one configured GitHub organization (who legitimately knows their own org's `webhook_secret`) can forge a payload where:
- `repository.owner.login` (or `organization.login`) = "OrgA" (their own org, so `verify_signature` picks OrgA's secret which they know and can correctly HMAC-sign the raw body with), while
- `repository.full_name` = "OrgB/some-repo" (a different, unrelated organization's repository configured on the same shared Shipit instance).

The equality that should hold — *the organization whose secret authenticated the request* == *the repository/organization that the event actually acts on* — is broken. This is a direct structural analog to the M-2 finding: a value trusted by the authorization check (`repository_owner`/claim-selecting-the-secret) is disjoint from the value that drives the actual state change (`repository.full_name` used to resolve `Stack`/`Repository`).

### Impact Explanation
Once past signature verification, handlers act on Shipit's own stored GitHub App credentials for whatever organization `repository.full_name` resolves to (e.g. `Stack#github_app`/`github_api` uses `Shipit.github(organization: repository.owner)` based on the *stored* `Repository` record, not the attacker's claim). This lets an attacker who administers one tenant/organization's GitHub App on a shared Shipit deployment forge webhook events (`push`, `pull_request` opened/labeled/reopened/closed, `check_suite`, `status`, `membership`, etc.) that are processed as if they originated from a different organization's repository. Depending on stack configuration this can trigger unauthorized `GithubSyncJob` runs, review-stack provisioning/archival, continuous-deployment sync, and merge-queue processing (`ProcessMergeRequestsJob` → `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request` using Shipit's own legitimate GitHub credentials for the victim org) — i.e., cross-repository/cross-organization writes and unauthorized merges/deploys performed with the app's own GitHub credentials, satisfying the Critical impact bar ("cross-repository writes... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires the multi-organization deployment configuration documented in `docs/setup.md` ("Using Multiple Github Applications") where a single Shipit instance hosts several organizations with independent GitHub App webhook secrets. It requires only knowledge of one's own legitimately-issued webhook secret (no privileged Shipit account, no `ApiClient` token, no `GITHUB_TOKEN`) — this matches the "unprivileged attacker" bar since the attacker only needs standing as an administrator of any one tenant organization configured on the shared instance, not privileged access to the target organization or to Shipit itself.

### Recommendation
After signature verification succeeds, re-derive/verify that `repository.full_name`'s owner matches the same organization (`repository_owner`) whose secret validated the signature before dispatching to handlers, rejecting (422) any mismatch. Alternatively, bind webhook processing per-organization so that a given `GitHubApp`/secret can only ever process events for repositories belonging to that same organization.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both having stacks configured.
2. As an administrator of `OrgA`'s GitHub App (who legitimately knows `OrgA`'s `webhook_secret`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-or-real-sha>",
  "repository": {
     "owner": {"login": "OrgA"},
     "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(OrgA's `webhook_secret`, raw_body).
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "OrgA")`, verifies successfully using the known `OrgA` secret. `PushHandler` then resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob`/triggers stack processing for `OrgB`'s stack, despite the request never being signed by `OrgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
