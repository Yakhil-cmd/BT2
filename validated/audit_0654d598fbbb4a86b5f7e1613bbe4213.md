### Title
Fee Receiver Can Permanently DoS All KLAY Bridge Transfer Requests by Reverting on Callback — (`contracts/service_chain/bridge/BridgeFee.sol`)

### Summary

`BridgeFee._payKLAYFeeAndRefundChange()` pushes KLAY to the `feeReceiver` address via a raw `.call.value()` and hard-requires the call to succeed. If `feeReceiver` is a contract whose `receive()` or fallback reverts, every `requestKLAYTransfer` and fallback invocation on the bridge will revert, permanently blocking all KLAY cross-chain transfer requests.

### Finding Description

`_payKLAYFeeAndRefundChange()` is the fee-payment hook called inside `_requestKLAYTransfer()`:

```
// BridgeFee.sol lines 49-50
(bool ok, ) = feeReceiver.call.value(fee)("");
require(ok, "transfer fee failed");
``` [1](#0-0) 

`_requestKLAYTransfer()` is the internal function invoked by both the public `requestKLAYTransfer()` and the payable fallback: [2](#0-1) 

`setFeeReceiver()` in `BridgeTransfer.sol` is `onlyOwner`, so the bridge owner sets the receiver address: [3](#0-2) 

The `feeReceiver` is stored as a plain `address payable` with no validation that it is an EOA or a contract that can accept KLAY: [4](#0-3) 

If the `feeReceiver` is a contract whose `receive()` or fallback function reverts (e.g., a multisig that has been paused, a contract whose admin deliberately breaks it, or any contract that conditionally rejects KLAY), the `require(ok, "transfer fee failed")` at line 50 causes the entire `_requestKLAYTransfer` call to revert. Because `_requestKLAYTransfer` is `nonReentrant` and `unlockedKLAY`, there is no alternative code path; every user's bridge request fails.

A second push-payment call exists for the change refund: [5](#0-4) 

If `msg.sender` is a contract that rejects KLAY, the refund path also reverts, blocking that caller's requests.

### Impact Explanation

When `feeReceiver` reverts on receipt:

- **All** `requestKLAYTransfer` and fallback calls revert — no user can initiate a KLAY cross-chain transfer.
- KLAY sent by users is returned (the revert unwinds the call), but the bridge is completely non-functional for KLAY transfers.
- The `requestNonce` is never incremented, so no `RequestValueTransfer` event is emitted and the counterpart bridge never receives a signal to release funds.
- This constitutes a persistent DoS on bridged KAIA asset movement, matching the allowed impact category of "bridge … privilege escalation that changes protected chain state or asset ownership" and "unauthorized … transfer … affecting KAIA, bridged assets."

### Likelihood Explanation

The `feeReceiver` is set by the bridge owner, but it is an arbitrary `address payable` — it can be a multisig, a DAO treasury, or any contract. The feeReceiver contract's own administrator can change its behavior (pause, upgrade, or add a reverting `receive()`) independently of the bridge owner. This is the same semi-trusted-actor threat model as the external report's "secondary fee address." The bridge owner has no on-chain mechanism to detect or prevent this after the fact without calling `setFeeReceiver` again.

### Recommendation

Replace the push-payment pattern with a pull-payment (claim) pattern:

1. Accumulate fees owed to `feeReceiver` in a storage mapping instead of transferring immediately.
2. Expose a `claimFees()` function that `feeReceiver` calls to withdraw accumulated fees.
3. Remove the `require(ok, ...)` on the push call, or at minimum replace it with a non-reverting transfer that silently skips the fee payment if the receiver rejects it (and logs an event).

This mirrors the recommendation in the external report: "forcing the fee recipients to claim their fees in a separate transaction."

### Proof of Concept

1. Deploy a malicious contract `MaliciousFeeReceiver` with a `receive()` that always reverts.
2. Bridge owner calls `bridge.setFeeReceiver(address(maliciousFeeReceiver))`.
3. Any user calls `bridge.requestKLAYTransfer{value: 2 ether}(to, 1 ether, "")`.
4. Execution enters `_requestKLAYTransfer` → `_payKLAYFeeAndRefundChange` → `feeReceiver.call.value(fee)("")` → `MaliciousFeeReceiver.receive()` reverts → `require(ok, "transfer fee failed")` reverts the entire transaction.
5. All subsequent `requestKLAYTransfer` and fallback calls revert identically; the bridge is DoS'd for all KLAY transfers.

```solidity
// Attacker contract
contract MaliciousFeeReceiver {
    receive() external payable {
        revert("no KLAY accepted");
    }
}
``` [6](#0-5) [7](#0-6)

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
```

    function _requestKLAYTransfer(address _to, uint256 _feeLimit,  bytes memory _extraData)
        internal
        unlockedKLAY
        nonReentrant
    {
        require(isRunning, "stopped bridge");
        require(msg.value > _feeLimit, "insufficient amount");

        uint256 fee = _payKLAYFeeAndRefundChange(_feeLimit);

        emit RequestValueTransfer(
            TokenType.KLAY,
            msg.sender,
            _to,
            address(0),
            msg.value.sub(_feeLimit),
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }

    // () requests transfer KLAY to msg.sender address on relative chain.
    function () external payable {
        _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
    }

    function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {

        _requestKLAYTransfer(_to, feeLimit, _extraData);
