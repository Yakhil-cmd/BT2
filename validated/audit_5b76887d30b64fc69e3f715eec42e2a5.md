## Title
Trigger payments to an AA with no matching message case are silently absorbed with no path to reclaim them, causing fund loss for the sender - (File: `aa_composer.js`)

### Summary
The external report flags `requestERC20Service()` as `payable` even though it performs no operation with the received ETH, trapping any accidentally-sent value in the contract. The analogous root cause exists in ocore's Autonomous Agent (AA) trigger-handling logic: any unit sent to an AA address is treated as a "trigger" and its coins are unconditionally credited to the AA's balance the moment the trigger is processed, *before* the AA's own logic decides whether it actually wants to act on it. If the AA's `messages`/`cases` template does not match the trigger (e.g., the trigger doesn't satisfy any `if` condition), the AA silently keeps the coins with no response and no state change, and — depending on the AA's logic — those coins may never be reachable by any message the AA can ever construct.

### Finding Description
`getTrigger()` builds the `trigger.outputs` map from every `payment` message addressed to the AA, regardless of whether the AA's template can do anything meaningful with it. [1](#0-0) 

`updateInitialAABalances()` then unconditionally adds all `trigger.outputs` to the AA's persisted balance (`aa_balances` table) as part of `handleTrigger`, independent of whether any subsequent case in the AA definition actually references or forwards that asset/amount. [2](#0-1) 

After the balance update, the AA's `messages` template is evaluated and filtered. If none of the cases apply, or the filtered result contains no state-changing payment messages, the code path explicitly "eats" the received coins and finishes with no response at all: [3](#0-2) 

This is confirmed by the test suite, where a trigger sends `40000` bytes to an AA whose only case's `if` condition never matches (`trigger.data.nonexistent`); the coins are consumed, the AA sends no payment back to the trigger's sender, and the bounce message literally reads `"no messages after filtering, then no state changes"`: [4](#0-3) 

Because AA addresses have no private key and can only ever emit outputs that its immutable oscript definition is explicitly coded to construct, any asset/amount the definition never references in an output expression becomes permanently unspendable — functionally identical to ETH trapped in a `payable` function that has no logic to move it.

### Impact Explanation
Any unprivileged unit poster who sends a payment (base bytes or a custom asset) to an AA address, expecting a specific `case` in the AA's `messages.cases` to trigger a response, will permanently lose those funds if:
- the AA's `if` conditions don't match the trigger's payload (typo in expected `trigger.data` field, unsupported asset, wrong parameters), or
- the trigger's payment carries an asset/amount that no case in the AA ever forwards.

Since the AA can never later synthesize a message referencing an asset its oscript logic doesn't account for, this results in concrete AA fund loss/freezing for the sender, matching the accepted impact class in the validation rules.

### Likelihood Explanation
This condition is trivially reachable by any user: composing and sending a unit with a `payment` message to any deployed AA address is a normal, unprivileged operation. Many real AA templates in the wild only implement a subset of expected cases (see the "silently accept coins" pattern used deliberately in some templates), and any AA lacking a universal fallback/refund case for unexpected inputs or extra assets exposes senders to this loss on ordinary usage mistakes (wrong `trigger.data`, unsupported asset, or exceeding the range checked by a case's `if`).

### Recommendation
- Encourage/standardize a defensive AA template pattern (and document it prominently) that always includes a fallback case which either bounces (returns funds minus bounce fees, which already exists for insufficient-bounce-fee scenarios) or explicitly forwards/records any received asset that isn't otherwise handled, rather than silently eating it.
- Consider extending `validateAADefinition` to warn/reject AA definitions whose `messages`/`cases` set has no fallback (`no if` / catch-all) branch capable of returning value for every asset the AA can potentially receive, closing the gap between "author forgot a case" and "user funds are gone forever."

### Proof of Concept
Using the existing test harness pattern in `test/aa.test.js`:
1. Deploy an AA whose only case has `if: "{trigger.data.nonexistent}"` (always false) and a payment output of `trigger.output[[asset=base]] - 2000` to the trigger's address. [5](#0-4) 
2. Send a trigger unit with `outputs: { base: 40000 }` to the AA.
3. Observe that `handleTrigger` returns bounce message `"no messages after filtering, then no state changes"`, no payment is returned to the trigger sender, and the 40000 bytes remain permanently credited to the AA's on-chain balance with no case in the definition ever able to reference or forward them back out. [6](#0-5)

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
