### Title
Unprivileged `DepositDelegatorRewards` griefing permanently locks a vote account's withdrawable balance - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote program's `DepositDelegatorRewards` instruction (SIMD-0123) lets **any signer**, without being the vote account's authorized withdrawer/voter or having any prior relationship to the account, deposit lamports into an arbitrary target vote account and unconditionally increase that account's `pending_delegator_rewards` counter. `withdraw` then treats `pending_delegator_rewards` as a reserved balance that must remain in the account (and blocks closing the account entirely while it is non-zero), analogous to how the Aegis Vault's `exit()` assumed the entire staked balance was self-staked and reverted once other parties (via `delegateStake`) inflated a value it did not control.

### Finding Description
`deposit_delegator_rewards` only requires the *source* account (the lamport payer) to sign; it performs no check that the caller controls, is authorized on, or has any relationship with the target vote account: [1](#0-0) 

It then unconditionally increments the vote account's `pending_delegator_rewards` field with the attacker-chosen deposit amount: [2](#0-1) [3](#0-2) 

`withdraw` uses this attacker-influenced value as a mandatory reserve: a full withdrawal (account close) is rejected outright whenever `pending_delegator_rewards > 0`, and partial withdrawals must keep `rent_exempt_minimum + pending_delegator_rewards` in the account: [4](#0-3) 

This mirrors the reported bug class exactly: a value that is supposed to represent "self-owned/self-staked" reserve (`pending_delegator_rewards` intended to represent rewards owed to legitimate delegators of that validator) can instead be inflated by an unrelated, unprivileged third party, after which the account's own authority can no longer withdraw/close the account as before, because the code assumes the reserve amount can only be legitimately attributed to real economic activity on that account.

I was not able to locate any code path that decrements `pending_delegator_rewards` after it is paid out during epoch reward distribution (only `add_pending_delegator_rewards` exists in `handler.rs`); `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` computes a *proportional* payout from `pending_delegator_rewards` based on stake share, but confirming the corresponding state write that reduces the stored `pending_delegator_rewards` field was not possible with the available tools/index. This is a material uncertainty: if the field is only reduced slowly (bounded by proportional epoch-reward redemption) or not reduced at all outside the intended protocol flow, an attacker can grief a validator's vote account by depositing a lamport amount whose "reservation" cannot be cleared for a very long time or indefinitely, effectively freezing the account's balance/close-ability against the wishes of its legitimate authorized withdrawer.

### Impact Explanation
If confirmed, this allows any unprivileged account to force a validator's vote account into a state where the authorized withdrawer can no longer withdraw down to the rent-exempt minimum or close the account, without the withdrawer's consent and using only their own (small) lamports as the deposit — a permanently (or indefinitely) frozen-account condition on a core validator/reward-distribution data structure.

### Likelihood Explanation
The `DepositDelegatorRewards` instruction is unprivileged by design (any signer can be the deposit source) and requires no relationship to the target vote account, so exploitation requires only calling this single instruction with an arbitrary target vote account and a small lamport deposit — likelihood is high assuming the feature is active (gated behind `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` feature flags per the code at `programs/vote/src/vote_processor.rs:409-426`).

### Recommendation
Verify whether `pending_delegator_rewards` is ever decremented outside of the intended, stake-proportional epoch-reward redemption path, and if third parties can call `DepositDelegatorRewards` against a vote account they do not control/administer. If so, consider requiring the vote account's authorized withdrawer (or another privileged party) to consent to/initiate deposits, or cap/rate-limit how much an arbitrary depositor can add to `pending_delegator_rewards` relative to actual owed rewards, so the reserved-balance mechanism cannot be weaponized to lock an unrelated account's funds.

### Proof of Concept
1. Attacker selects any target `VoteStateV4` vote account `V` (does not need to control it).
2. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: N }` with themselves as the signing source account and `V` as the vote account, per `deposit_delegator_rewards` in `programs/vote/src/vote_state/mod.rs:936-988` (only the source signer is checked, at line 951).
3. `V`'s `pending_delegator_rewards` is increased by `N` lamports (`handler.rs:196-209`), and `N` lamports are transferred into `V`.
4. `V`'s authorized withdrawer subsequently attempts `Withdraw`; per `withdraw` (`vote_state/mod.rs:1062-1122`), any attempt to close the account (`remaining_balance == 0`) fails while `pending_delegator_rewards > 0`, and partial withdrawals are capped so at least `rent_exempt_minimum + pending_delegator_rewards` remains — a reserve the withdrawer never agreed to and did not create.

        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }
