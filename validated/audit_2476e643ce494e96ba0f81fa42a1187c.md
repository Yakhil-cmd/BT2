### Title
Organization used for webhook signature verification is decoupled from the repository the handler acts on, enabling cross-repository webhook forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret` used to check `X-Hub-Signature`) based on `repository_owner`, which is read straight from the untrusted request body: [1](#0-0) [2](#0-1) 

However, none of the actual event handlers use `repository_owner`/the organization that was authenticated to decide what to act on. Every handler resolves the target `Repository`/`Stack` from a *different* JSON field, `repository.full_name`, taken from the very same attacker-controlled payload: [3](#0-2) [4](#0-3) 

This is exactly the analog of the `upperLookupRecentCheckpoint` bug class: the value that is checked/verified (`repository.owner.login`, used to pick the org secret) is not the value that is subsequently trusted and acted upon (`repository.full_name`, used to pick the stack). Nothing binds `repository.owner.login` to `repository.full_name` — Shipit does not assert `full_name.start_with?("#{owner}/")`.

The engine explicitly supports a "Using Multiple GitHub Applications" mode where each organization has its own, independently configured `webhook_secret` (`docs/setup.md`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), selected via `Shipit.github(organization:)`: [5](#0-4) 

Additionally, `verify_webhook_signature` treats a blank `webhook_secret` as automatically verified: [6](#0-5) 

Both the example config and the multi-app doc show `webhook_secret` as an optional/nil field per-organization, so it is a documented, supported configuration state for at least one organization to have no secret configured.

### Impact Explanation
In a multi-organization deployment where at least one configured GitHub organization has no `webhook_secret` set (a state the shipped example configs explicitly show as valid), an attacker who can reach the `/webhooks` endpoint can:
1. Craft a JSON payload with `repository.owner.login` (or `organization.login`) set to the org that has no secret — this makes `verify_signature` pass unconditionally (`return true unless webhook_secret`), with no valid `X-Hub-Signature` required.
2. Set `repository.full_name` in the same payload to any other org/repo tracked by the Shipit instance, e.g., a victim stack under a *different*, properly-secured organization.
3. Because handlers exclusively key off `repository.full_name` (via `Handler#repository_name` / `Repository.from_github_repo_name`), the forged event is dispatched against the victim's `Stack`, even though the signature check never validated anything related to that organization or repository.

Concretely this allows an unauthenticated attacker to trigger, for a repository they have no relationship to:
- `PushHandler` → `stack.sync_github(expected_head_sha:)`, which can feed an `expected_head_sha` for `GithubSyncJob` and, on stacks with `continuous_deployment: true`, cause `ContinuousDeliveryJob`/`trigger_continuous_delivery` to fire an unauthorized deploy once new commits are (or appear to be) available.
- `pull_request` handlers (`labeled_handler.rb`, `unlabeled_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, `review_stack_adapter.rb`) → archiving, unarchiving, or provisioning/deprovisioning arbitrary review stacks belonging to a repository/org the attacker never authenticated against.

This crosses the "organization authenticated versus repository written" trust boundary called out in scope and can result in an unauthorized deploy/rollback trigger and cross-repository state changes — a Critical/High impact per the given severity classes.

### Likelihood Explanation
Requires only that one configured GitHub organization in a multi-org Shipit deployment has no `webhook_secret` set — a state the project's own example configuration files present as the default/normal value (`webhook_secret: # nil`). No credentials, tokens, or prior authentication are needed; the attacker only needs network access to the public `/webhooks` endpoint and knowledge of the target stack's `repository.full_name`, which is public GitHub information (owner/repo). This is a realistic misconfiguration given the project's own docs/examples show it as an acceptable value.

### Recommendation
- In `Shipit::WebhooksController`, after determining the `github_app` for `repository_owner`, verify that `repository_owner` matches the owner embedded in `repository.full_name` (or otherwise bind the two fields) before dispatching to handlers.
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank; require an explicit "signature verification disabled" opt-in, or fail closed and log/alert instead.
- In `Shipit::Webhooks::Handlers::Handler#repository_name`, cross-check that the resolved repository actually belongs to the same GitHub organization that was used to verify the webhook signature.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations, `AttackerOrg` (no `webhook_secret` configured) and `VictimOrg` (properly configured, tracks stack `VictimOrg/victim-repo` with `continuous_deployment: true`).
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `github_app = Shipit.github(organization: "AttackerOrg")`; since `AttackerOrg` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature.
4. `PushHandler` resolves the target via `payload.dig('repository', 'full_name')` = `"VictimOrg/victim-repo"`, finds the victim `Stack`, and calls `stack.sync_github(expected_head_sha: ...)`, queuing `GithubSyncJob` for a stack the attacker never had verified access to.

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
```
