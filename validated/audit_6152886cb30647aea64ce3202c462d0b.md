### Title
RAY share overflow in accrual permanently freezes a saturated market — no repay, withdraw, or liquidate - (File: common/src/rates/scaling.rs)

### Summary

CVE-2018-18828 is a heap buffer overflow whose impact is denial of service. The analog in XOXNO Lending is an arithmetic overflow of the same class: `scaled.mul(env, index)` inside `scaled_to_original` computes `scaled * index / RAY` as `i128` fixed-point math and panics with `GenericError::MathOverflow` when the Ray-denominated value exceeds `i128::MAX`. Because every user-facing verb runs `global_sync` accrual first, once `borrowed * borrow_index` (or `supplied * supply_index`) crosses the `i128` value ceiling, all entrypoints on that market revert forever. The `MAX_BORROW_INDEX_RAY` cap does not prevent this: it bounds the index, not the `scaled * index` product.

### Finding Description

Interest accrual in `accrue_step` (called from `contracts/pool/src/interest.rs:40` `accrue_chunk`, driven by `global_sync` at `contracts/pool/src/interest.rs:20`) evaluates `calculate_supplier_rewards` and `update_supply_index`, which both multiply scaled share totals by indexes: `borrowed.mul(env, new_borrow_index)` and `supplied.mul(env, old_index)` in `common/src/rates/index.rs:80-81` and `common/src/rates/index.rs:34`. `Ray::mul` maps to `mul_div_half_up` (`common/src/math/fp.rs:185-187`), which panics with `MathOverflow` when `x * y / RAY` does not fit `i128` (`common/src/math/fp_core.rs:108-118`).

The index cap `update_borrow_index` (`common/src/rates/index.rs:13-19`) only clamps `new_index` to `MAX_BORROW_INDEX_RAY`; it does nothing about the product `borrowed * borrow_index`. With a large enough scaled `borrowed` (a whale-scale market on a high-decimal, high-supply token), the debt value overflows `i128` while the index itself is still far below the cap. The repository's own harness test confirms the end state: after the overflow is reached, `try_withdraw_raw`, `try_repay`, and `try_update_indexes_for` all fail with `MATH_OVERFLOW`, and the comment states "Every verb accrues first, so the market freezes: no repay, no withdraw, no liquidation. The index cap never engages" (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360`).

Attacker path (single unprivileged address):

1. `controller.supply` a very large amount into a high-decimal market (e.g., 18 decimals), up to the market cap.
2. `controller.supply` collateral in a second market and `controller.borrow` ~98% of the first market's liquidity (subject to `min_borrow_collateral_usd` and LTV checks).
3. Wait. Utilization stays pinned at ~98% because the attacker is essentially the whole borrow side; the steep segment of the interest curve compounds `borrow_index` each accrual chunk (`compound_interest`, `common/src/rates/compound.rs:31-51`).
4. Once `borrowed * borrow_index / RAY > i128::MAX`, the next `accrue_chunk` panics in `scaled_to_original`/`Ray::mul`, and every subsequent `supply/borrow/withdraw/repay/liquidate/clean_bad_debt/update_indexes` call on that market reverts at `global_sync` before reaching any logic.

### Impact Explanation

Permanent freezing of funds — an accepted impact class. All suppliers' deposits and all borrowers' collateral/debt in the affected (hub, token) book become immovable forever: withdrawals, repayments, liquidations, and bad-debt cleanup all pass through `global_sync` and hit the same `MathOverflow` panic. Unlike a fail-closed pause, there is no admin recovery path that skips accrual, because accrual is a precondition of every mutating verb. The test demonstrates the freeze is terminal (`large_positions_and_long_horizons.rs:354-356`).

### Likelihood Explanation

Medium-to-low likelihood, medium severity. The attack requires a market whose configuration permits whale-scale positions: a token with very large total supply/decimals and a supply cap high enough to bring `scaled * index` near `i128::MAX` (the harness needed `lift_caps` and ~10^27 native units to hit it within the test horizon). For ordinary 7-decimal markets with conservative caps this is unreachable, but `calculate_scaled_cap` deliberately saturates rather than capping the value domain (`common/src/rates/scaling.rs:26-33`), and listings for high-supply tokens would expose it. No privileged action by the attacker is needed — only capital, patience, and a high-utilization borrow that nobody can displace once the freeze lands.

### Recommendation

Check the ceiling where the index cap is enforced: cap `borrowed`/`supplied` scaled totals (or the product `scaled * index`) rather than only the index, e.g., clamp `new_index` to `min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed.raw())` inside `update_borrow_index`, and apply the equivalent bound to `update_supply_index`. Alternatively, use a saturating mul inside `scaled_to_original` for accrual accounting so accrual degrades gracefully instead of bricking the market, while keeping panicking math on user-position unscaling.

### Proof of Concept

Reproduced by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance years; try_update_indexes_for eventually errors:
assert_contract_error(Err(failure), errors::MATH_OVERFLOW);
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
