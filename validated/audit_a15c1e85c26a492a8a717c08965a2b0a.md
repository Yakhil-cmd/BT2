### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while the actual write target is resolved from `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, a field taken from the *same unauthenticated JSON body* it is about to validate. Every webhook handler, however, resolves the `Repository`/`Stack` it actually mutates using a different field, `repository.full_name` (`Handler#repository_name`). Because these two fields are never checked for consistency, and because signature verification is a no-op whenever the selected organization has no `webhook_secret` configured, an attacker can pick any organization with a blank/known secret for the "authenticating" field while pointing the "acted-on" field at a victim organization's repository.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` yields a `GithubApp`/`GithubOrganization` object whose `verify_webhook_signature` short-circuits to `true` whenever that organization has no configured `webhook_secret`: [3](#0-2) 

Meanwhile, every handler resolves the actual `Stack`/`Repository` to act on from a *different* payload field, `repository.full_name`, with no cross-check against `repository_owner`: [4](#0-3) 

For example, the push handler syncs an arbitrary stack picked purely via `repository.full_name`: [5](#0-4) 

**Broken invariant (equality that must hold):**
`organization_used_for_signature_verification == owner_of(repository.full_name_used_to_locate_stack)`

For a genuine GitHub-issued webhook this equality always holds, because both fields come from the same, GitHub-controlled `repository` object. An attacker forging a raw POST to `/webhooks`, however, fully controls both fields independently:
- Set `repository.owner.login` (or `organization.login`) to an org that has **no `webhook_secret` configured** (or one the attacker knows) → `verify_webhook_signature` returns `true` immediately, so `verify_signature` passes with no valid signature at all.
- Set `repository.full_name` to `"victim-org/victim-repo"` → `Handler#repository_name` / `Handler#stacks` resolve the real, secret-protected victim stack, and the handler (`PushHandler#process`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, etc.) executes against it.

This is the direct analog of the `addPool`/`_massUpdatePools` bug class: the value that is checked (`repository_owner`, used to select the signing secret) is not the value that is acted upon (`repository.full_name`, used to select the mutated stack) — exactly the "organization that authenticated versus the repository that is written" binding called out as in-scope.

### Impact Explanation
An unauthenticated attacker can inject arbitrary webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) for any stack/repository configured in Shipit, as long as any single organization in the multi-tenant `Shipit.github(organization: ...)` configuration lacks a `webhook_secret` (or has one the attacker can produce). This can:
- Force `PushHandler` to call `stack.sync_github`, which — for stacks with continuous delivery/deploy enabled — can trigger an unauthorized deploy pipeline run for a repository the attacker never had write access to or a valid webhook signature for.
- Force `StatusHandler` to inject/alter commit statuses that gate deploy safety checks (`ci.require`/`ci.blocking` in `shipit.yml`), potentially unblocking an otherwise-blocked deploy.
- Force `MembershipHandler` to create/modify `Team`/`Membership` records, which feed directly into `User#authorized?` and `Shipit.github_teams` authorization checks.

These map to the Critical ("unauthorized deploy") and High ("escalation into `Shipit.github_teams` authorization") impact categories.

### Likelihood Explanation
Requires no credentials, no session, and no valid webhook secret for the targeted organization/repository — only that at least one other organization in the deployment's GitHub App configuration has no `webhook_secret` set (a documented, supported configuration per `lib/shipit/github_app.rb`'s `return true unless webhook_secret` fallback). The `/webhooks` endpoint (`resources :webhooks, only: :create` in `config/routes.rb`) is unauthenticated by design and reachable by anyone. Any Shipit deployment mixing organizations with and without configured secrets is directly exploitable.

### Recommendation
Bind signature verification to the same identity used for the write:
1. In `WebhooksController`, derive the signing organization from `repository.full_name`'s owner (or require them to match, rejecting the request with 422 if `repository.owner.login` ≠ the owner segment of `repository.full_name`).
2. Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations that own tracked repositories/stacks; require every organization backing an active `Repository`/`Stack` to have a `webhook_secret` configured, or reject webhooks for repositories whose owning organization has no secret.
3. Add an explicit consistency check in `Handler#stacks`/`Handler#repository_name` (or in the controller) that the resolved repository's owner matches the organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two organizations: `victim-org` (has `webhook_secret: "s3cr3t"`, owns a tracked, continuous-delivery-enabled `Stack` for `victim-org/victim-repo`) and `no-secret-org` (no `webhook_secret` configured).
2. Craft a forged `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "no-secret-org" }
     }
   }
   ```
3. POST it to `/webhooks` with header `X-Github-Event: push` and any (or no) `X-Hub-Signature`.
4. `repository_owner` resolves to `"no-secret-org"`; `Shipit.github(organization: "no-secret-org").verify_webhook_signature` returns `true` unconditionally because that org has no secret.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `stacks`/`repository_name` resolve `"victim-org/victim-repo"` from the payload and call `stack.sync_github(expected_head_sha: ...)` on the victim's real stack — with no valid signature ever presented for `victim-org`'s secret.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
