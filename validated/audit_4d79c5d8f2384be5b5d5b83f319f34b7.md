### Title
Membership webhook team-scoping bypass allows cross-organization escalation into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The reported bug class is a state binding that becomes desynchronized under attacker-influenced input, causing a value that was supposed to be re-derived/re-checked to instead be reused from stale/attacker-controlled state. The equivalent binding in shipit-engine is: **the GitHub organization whose secret cryptographically verifies a webhook (`organization.login`, used by `WebhooksController#verify_signature`) is never re-checked against the organization actually recorded on the target `Team` record that `MembershipHandler` mutates.** An attacker who legitimately controls the webhook secret for *any* configured GitHub organization can therefore add themselves to a `Team` that belongs to a completely different, privileged organization, as long as they know that team's numeric GitHub `id`.

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification purely from the attacker-supplied JSON body: [1](#0-0) [2](#0-1) 

For a `membership` event there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` — i.e. the org value the signature check is keyed on is exactly the same field the attacker writes.

`MembershipHandler#process` then resolves the target `Team` purely by GitHub's globally-unique numeric `team.id`, and only sets `team.organization` on **first creation**: [3](#0-2) 

Because `Team.find_or_create_by!(github_id: params.team.id)` short-circuits to the existing record when one already exists, the `organization.login` value that was actually verified by the signature for *this* request is discarded — it is never compared to the `organization` already stored on the pre-existing `Team` row. `team.add_member(member)` is applied to whatever `Team` object that `github_id` resolves to, regardless of which organization's secret authenticated the current request.

Equality that should hold but doesn't:
`verified_organization (secret used to pass HMAC check) == team.organization (org the mutated Team actually belongs to)`

Before the attack: Team #12345 exists with `organization = "PrivilegedOrg"`, created by a legitimate earlier `membership` webhook from PrivilegedOrg.
After the attack: an attacker who only administers a *different*, low-trust org (`"AttackerOrg"`, for which they legitimately hold the app's `webhook_secret`) sends a payload with `organization.login = "AttackerOrg"` (so the HMAC check passes against AttackerOrg's secret) but `team.id = 12345` and `member.login = <attacker's own GitHub login>`, `action = "added"`. `verify_signature` passes (AttackerOrg's secret matches AttackerOrg's payload field). `MembershipHandler` finds the *existing* Team #12345 (still tagged `organization = "PrivilegedOrg"`) and adds the attacker as a member of it.

### Impact Explanation
`Team` membership backs `Shipit.github_teams` authorization, which `Shipit::Authentication#force_github_authentication` uses to gate all controller access: [4](#0-3) 

By forging membership into a `Team` object belonging to a privileged organization while only holding webhook-signing credentials for an unrelated, unprivileged organization, an attacker escalates into `Shipit.github_teams` authorization without ever needing repository access, a Shipit session, or the privileged organization's own webhook secret. This matches the High-impact category "escalation into `Shipit.github_teams` authorization" explicitly listed in scope.

### Likelihood Explanation
The prerequisite — being the legitimate holder of a `webhook_secret` for *some* GitHub App installation configured in Shipit — is realistic in any multi-organization deployment (Shipit explicitly supports multiple orgs, as shown by `test/dummy/config/secrets_double_github_app.yml`). The target team's numeric GitHub `id` is discoverable via the GitHub API for teams the attacker can see (or via prior webhook traffic), and no additional Shipit privilege is required. The vulnerable code path (`find_or_create_by!` short-circuiting the organization tag, and org-derived secret selection with no cross-check against the resolved `Team`) is a straightforward, deterministic logic flaw rather than a race condition, making exploitation reliable once the secret and team id are known.

### Recommendation
In `MembershipHandler#find_or_create_team!`, always verify (and reject/log if mismatched) that `params.organization.login` equals the `organization` already stored on the resolved `Team`, rather than only setting it on creation. Additionally, `WebhooksController#verify_signature` should not let a single JSON field simultaneously determine both "which secret verifies this request" and "which organization's data this request is allowed to mutate" without an independent, out-of-band binding (e.g., verifying via the GitHub App installation ID tied to the secret, not a value taken from the unauthenticated body).

### Proof of Concept
1. Shipit is configured with two orgs, `PrivilegedOrg` and `AttackerOrg`, each with its own GitHub App and `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml` pattern).
2. A legitimate `membership` webhook previously arrives from `PrivilegedOrg`, causing `MembershipHandler` to create `Team#find_or_create_by!(github_id: 12345)` with `organization = "PrivilegedOrg"` — this team's handle is included in `Shipit.github_teams`.
3. Attacker, who administers `AttackerOrg`'s GitHub App (and thus knows `AttackerOrg`'s `webhook_secret`), POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 12345, "name": "Privileged Team", "slug": "privileged-team", "url": "https://github.com/..." },
  "organization": { "login": "AttackerOrg" },
  "member": { "login": "attacker-github-login" }
}
```
signed with `AttackerOrg`'s HMAC secret via `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` → `"AttackerOrg"`, fetches `AttackerOrg`'s secret, and the signature validates successfully.
5. `MembershipHandler#process` finds the pre-existing Team `#12345` (still tagged `PrivilegedOrg`) via `github_id`, and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
6. The attacker's Shipit account is now a member of a team counted toward `Shipit.github_teams` authorization, despite never having any relationship to `PrivilegedOrg`.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
