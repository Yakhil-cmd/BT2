## Title
API token stack-scope bypass on the CCMenu status endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
An `ApiClient` token that is scoped to a single stack (`ApiClient#stack_id`) is supposed to be limited to that stack per `Api::BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` to look the stack up unscoped (`Stack.from_param!`), so a token that authorizes only `read:stack` on Stack A can be reused to read build/status data for any other Stack B, breaking the binding "the stack a token authorizes" vs "the stack the request actually touches."

### Finding Description
`Api::BaseController` establishes the authorization binding for API tokens: a token may be globally scoped or restricted to one specific stack via `ApiClient#stack_id`. This restriction is enforced in the `stacks`/`stack` helpers: [1](#0-0) 

`require_permission!` only checks that the operation/scope string (e.g. `"read:stack"`) is present in `ApiClient#permissions`; it never checks *which* record the operation is being performed on: [2](#0-1) 

So the only place that actually restricts a stack-scoped token to its own stack is the `stacks`/`stack` lookup in `BaseController`. `Api::CCMenuController`, however, redefines `#stack` and bypasses the scoped `stacks` relation entirely, resolving the stack directly from the global `Stack` model using the attacker-controlled `stack_id` request parameter: [3](#0-2) 

The controller still declares `require_permission :read, :stack`, which only proves the token has *a* `read:stack` permission somewhere — not that it is entitled to *this* stack. Because `authenticate_api_client` in this controller also accepts the token via the `token` query-string parameter (`ApiClient.authenticate(params[:token])`), any holder of a stack-scoped, `read:stack`-only token (e.g. the CCMenu tokens auto-created by `CCMenuUrlController#client`, which are always created with just `read:stack` and bound to one stack) can query `/api/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu` for a stack they were never granted access to. [4](#0-3) 

This breaks exactly the "stack a token authorizes vs. stack it touches" binding: before the request, the token's authorized-stack set is `{Stack A}` (as recorded on `ApiClient#stack_id`); after this request, the code allows it to touch `{Stack A, Stack B, Stack C, ...}` — any stack in the system — despite the equality `token.stack_id == requested_stack.id` never being checked in this controller.

### Impact Explanation
This yields unauthenticated (relative to the intended scope) read access to another stack's state: name, latest deploy/build status, and lock status, all rendered as XML via `show.builder`. Per the engine's own severity classification, an "unauthenticated read of stack state" achieved by escalating a token beyond its authorized scope is a High severity issue (cross-tenant information disclosure of deploy/build state for stacks the token holder has no right to see).

### Likelihood Explanation
Any user who can create an `ApiClient` (which is self-service via `ApiClientsController`/`CCMenuUrlController`, requiring only the normal GitHub-team-authorized Shipit login, not admin rights) can mint a stack-scoped `read:stack` token for a stack they legitimately have access to, then reuse that same token's authentication (which only checks the HMAC-signed client id, not the stack) against the CCMenu endpoint for any other `stack_id` path segment. No special privilege beyond ordinary Shipit login and token creation is required, and the attack is a single unauthenticated-relative-to-scope HTTP GET.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` can only resolve the stack it was created for. Additionally, `check_permissions!` could be hardened to also verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` for any per-stack operation, so the binding is enforced centrally rather than per-controller.

### Proof of Concept
1. As an ordinary logged-in Shipit user, visit `Stack A`'s page and trigger `GET /ccmenu/<owner>/<repo-a>/<env-a>` (`CCMenuUrlController#fetch`), which auto-creates (or reuses) an `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and `stack: Stack A`, returning a signed `token`. [5](#0-4) 
2. Using that same `token`, issue: `GET /api/stacks/<owner>/<repo-b>/<env-b>/ccmenu?token=<token>` for an unrelated `Stack B` that the attacker's `ApiClient` is not scoped to.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!` (unscoped) rather than `stacks.from_param!`, the request succeeds with `200 OK` and returns Stack B's name, last build status, and lock state, despite the token only being authorized for Stack A. [6](#0-5)
