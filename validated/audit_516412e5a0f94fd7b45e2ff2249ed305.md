### Title
Empty-weight PoX-4 signer set can be accepted with zero signatures, bypassing Nakamoto block approval - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures()` only rejects a reward cycle if `reward_set.signers()` is `None`; it does not reject an empty-but-`Some` signer vector or a signer set whose total weight is `0`. Combined with `StacksChainState::make_signer_set()`, which can legitimately return `Some(vec![])` when every stacker's `amount_stacked` floors to a `weight` of `0` under the current threshold, this reproduces the "empty committee" bug class from the external report: a valid-looking committee object exists, but it requires no signatures to pass verification.

### Finding Description
`make_signer_set()` in `stackslib/src/chainstate/stacks/boot/mod.rs` only returns `None` when the *input* `entries` list is empty: [1](#0-0) 
Every entry is otherwise mapped and then filtered by `weight == 0`: [2](#0-1) 
If stackers exist (`entries` non-empty) but each one's `stacked_amt / threshold` floors to `0` (e.g., many small stackers, none individually reaching the reward-slot `threshold`), the function returns `Some(vec![])` — a *present* signer list with zero members, not `None`.

This is wrapped into `RewardSet::V0` with `signers: Some(vec![])` by the PoX-4 reward-set computation, and consumed by `pox_4_compute_and_update_signers`: [3](#0-2) 

`verify_signer_signatures()` then checks only for the `None` case: [4](#0-3) 
With `signers = Some(&[])`, `reward_set.total_signing_weight()` computes to `0`: [5](#0-4) 
and `compute_voting_weight_threshold(0)` also evaluates to `0`: [6](#0-5) 
The final check `total_weight_signed < threshold` becomes `0 < 0`, which is `false`, so the function returns `Ok(0)` — the block is accepted with **zero signer signatures**, regardless of the `signer_signature` vector's contents: [7](#0-6) 

This exactly mirrors the reported Validium pattern: `_requiredAmountOfSignatures = 0` combined with an "empty but present" committee causes `verifySignatures()`/`verify_signer_signatures()` to accept an empty signature set as valid.

Notably, this class of bug was independently identified and *fixed* for the newer PoX-5 path, which explicitly guards against an empty signer set: [8](#0-7) 
No equivalent guard exists in the PoX-4 path (`pox_4_compute_and_update_signers`) or in the general `verify_signer_signatures()` block-verification routine that both PoX-4 and PoX-5 reward sets flow through.

### Impact Explanation
If a reward cycle's committed reward set ends up with `Some(vec![])` signers (zero total weight), any Nakamoto block for that cycle passes `verify_signer_signatures()` unconditionally — an **unsigned stacking/block-approval action**. This is a consensus-safety violation: block approval is supposed to require signer consent proportional to locked STX, but this path allows any block to be treated as fully approved with no signatures at all, which could be leveraged for forks/equivocation without needing any signer key.

### Likelihood Explanation
Reaching `Some(vec![])` requires the aggregate stacking distribution in a cycle to produce zero non-zero-weight entries after `make_signer_set`'s per-entry flooring — plausible under specific PoX-4 participation/threshold conditions (e.g., extremely small stacked amounts relative to the reward threshold, or a network configuration with low participation), rather than through routine operation. It does not require any privileged account, only that stacking participation combined with the computed threshold produces this edge case; likelihood is therefore low-to-moderate and configuration/parameter dependent.

### Recommendation
In `verify_signer_signatures()`, reject the block (or otherwise refuse to consider the reward set valid) when `signers.is_empty()` or when `total_signing_weight() == 0`, in addition to the existing `None` check — mirroring the guard already present in `pox_5_compute_and_update_signers`. Alternatively, make `StacksChainState::make_signer_set()` return `None` (rather than `Some(vec![])`) whenever the filtered result is empty, so downstream consumers uniformly treat "no qualifying signers" as the `None`/error case already handled.

### Proof of Concept
1. Configure a PoX-4 reward cycle where stacking entries exist (`entries` non-empty in `make_signer_set`) but each entry's `amount_stacked / threshold` floors to `0` (e.g., many participants each stacking just under the per-slot threshold).
2. `make_signer_set()` returns `Some(vec![])`, so `RewardSet::V0.signers = Some(vec![])`, and `pox_4_compute_and_update_signers` writes this reward set for the cycle.
3. During the following reward cycle, produce a Nakamoto block header with an **empty** `signer_signature` vector.
4. Call `verify_signer_signatures()`: `total_weight = 0`, `threshold = compute_voting_weight_threshold(0) = 0`, `total_weight_signed = 0`; the check `0 < 0` is false, so the function returns `Ok(0)` and the block is treated as fully signed/approved despite having no signatures.

I could not fully trace every call site that constructs `RewardSet::V0` for PoX-4 within the available indexed content (e.g., the exact `get_reward_threshold_and_participation`/`make_reward_set` wiring), so I cannot rule out an additional upstream guard I did not locate; a Devin session with full repository access would be needed to confirm there is no other filter preventing an all-zero-weight, non-empty signer list from being persisted for a live reward cycle.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
