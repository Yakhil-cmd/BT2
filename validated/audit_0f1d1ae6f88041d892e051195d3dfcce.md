### Title
Stack-scoped ApiClient tokens bypass their stack restriction in the CCMenu API - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` resolution method to look up `Stack.from_param!(params[:stack_id])` directly instead of going through the tenant/scope-aware `stacks` method used by every other API controller. This breaks the binding "the stack an `ApiClient` token authorizes" == "the stack it actually touches," letting a stack-scoped token read the CCMenu status of any stack, not just the one it was created for.

### Finding Description
`Shipit::Api::BaseController` centralizes stack access control: any controller that needs to resolve `params[:stack_id]`/`params[:id]` into a `Stack` is expected to do so through the `stacks` helper, which restricts the queryable set to the client's own stack when the `ApiClient` is stack-scoped: [1](#0-0) 

`require_permission!` only checks the coarse `read:stack` permission string via `ApiClient#check_permissions!`; it never checks which specific stack the token is bound to: [2](#0-1) 

The only place that enforces "this client may only see *its own* stack" is the `stacks` scoping method above (`Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true). `CCMenuController`, however, defines its own private `stack` method that completely bypasses that scoping and queries `Stack.from_param!` against the whole `Stack` table: [3](#0-2) 

Compare this to `LocksController` and `HooksController`, which rely on the inherited `stack`/`stacks` methods and are therefore correctly scoped: [4](#0-3) [5](#0-4) 

The fixtures confirm stack-scoped clients are a real, supported concept (`here_come_the_walrus` is bound to a single stack) and that this scoping is expected to be enforced on `index`/other endpoints: [6](#0-5) [7](#0-6) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, a legitimately-issued, narrowly-scoped token (e.g. one minted by `CCMenuUrlController#client` or created via the admin UI and bound to a single stack) can be replayed with an arbitrary `stack_id` in the URL to read the CCMenu status (build/deploy status, name, activity) of any stack in the installation.

Equality broken: `stack a stack-scoped ApiClient token authorizes` ≠ `stack the CCMenuController actually queries and returns data for`.

### Impact Explanation
This is an unauthenticated-relative-to-scope read of another stack's deploy/build state through an authenticated-but-narrowly-scoped API client — exactly the "unauthorized read of stack state" class described as High impact: a token meant to be limited to one stack can enumerate/read status information (deploy state, activity, last build status) of every other stack in the Shipit instance, an authorization/tenant-isolation bypass within the engine's own controller code, not a misconfiguration by the host app.

### Likelihood Explanation
Likelihood is high: it requires only a stack-scoped `ApiClient` token (a normal, intentionally-restricted credential type that this engine issues, e.g. via `CCMenuUrlController`) and a trivial URL parameter change (`stack_id`) to the `Api::CCMenuController#show` route — no additional privilege, no signature forgery, no code execution needed. The route is reachable via `resources :stacks ... get '/ccmenu' => 'ccmenu#show'` in `config/routes.rb`. [8](#0-7) 

### Recommendation
Make `CCMenuController#stack` reuse the inherited, scope-aware `stacks` relation (e.g. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped `ApiClient` tokens can only ever resolve to the stack they were issued for.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` token bound to `stack A` (permission `read:stack`), e.g. via `CCMenuUrlController#fetch` for stack A, or an admin-created client with `stack_id` set to A (see `here_come_the_walrus` fixture pattern).
2. Send `GET /stacks/<owner>/<repoB>/<env>/ccmenu?token=<tokenForStackA>` where `owner/repoB/env` identifies a *different* stack B that the token was never scoped to.
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully (`ApiClient.authenticate(params[:token])`), `require_permission :read, :stack` passes because the token does carry `read:stack`, and `stack` resolves via `Stack.from_param!(params[:stack_id])` — returning stack B's CCMenu XML (name, last build status, activity) even though the token is scoped to stack A only.

Note: I was not able to independently confirm from the index whether any other code path (e.g. a Rails engine-level `before_action`) additionally restricts `stack_id` lookups outside of `BaseController#stacks`; based on all controller and model code found, no such additional check exists for `CCMenuController`.

      end

        end
      end
