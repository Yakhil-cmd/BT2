### Title
Webhook signature verification binds to `repository.owner.login`, but event handlers act on the unverified `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The reported Uniswap bug is a validation gap where a critical role (`owner`) is set from an unchecked input, and every downstream privileged function trusts that value without re-validating it. The analogous gap in shipit-engine is in `WebhooksController`: the HMAC signature is verified against the GitHub App `webhook_secret` selected by `repository.owner.login`, but the actual repository/stack acted upon by every webhook handler is selected from a *different* payload field, `repository.full_name`, which is never cross-checked against the field used for signature verification.

### Finding Description
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to verify the signature against using: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`. Once the signature check passes, `WebhooksController#create` dispatches the *entire raw JSON payload* to all registered handlers for the event, unmodified: [3](#0-2) 

Every handler, however, resolves the target repository/stack from a *different* field, `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 

For example `PushHandler` (`stack.sync_github`), and the `pull_request` handlers (`labeled_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`) all resolve the acting repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`: [5](#0-4) [6](#0-5) 

Nowhere in the controller or handler pipeline is there a check that `repository.owner.login` (the field used to select the verifying secret) matches the owner encoded in `repository.full_name` (the field the handler actually operates on). The binding the report class hints at — "an organization that authenticated versus the repository that is written" — is broken here as an equality:

`repository_owner_used_for_signature == organization(repository.full_name)` is assumed but never enforced.

`StatusHandler` is even weaker: it does not consult the repository at all, resolving purely by commit SHA across the whole database: [7](#0-6) 

### Impact Explanation
In a Shipit deployment that has installed the GitHub App on multiple organizations (this is an explicitly supported, documented configuration — see `config/secrets.development.shopify.yml` showing multiple orgs each with independent `webhook_secret`/`oauth` blocks), each organization is issued its own webhook secret, and each org admin can trigger deliveries of that secret's HMAC by pushing to or otherwise triggering events on any repository within their own org (this is normal, legitimate GitHub App behavior, not a compromise). An attacker who administers Organization A (and therefore possesses/controls delivery of valid HMAC signatures computed with Organization A's `webhook_secret`) can craft a raw POST body whose `repository.owner.login` is `"org-a"` (so `verify_signature` selects and validates against org A's secret) while `repository.full_name` is set to `"org-b/some-repo"` — a repository belonging to a different, unrelated organization tracked by the same Shipit instance. Since handlers act exclusively on `repository.full_name`, this forged event is processed as if it legitimately originated from org B's repository, letting org A trigger `GithubSyncJob` (`PushHandler`), pull-request/review-stack archive/unarchive actions, or commit-status writes against org B's stacks — all without ever possessing org B's webhook secret. This is a cross-organization/cross-repository authorization break, though the impact is capped by what each handler does (`sync_github`, PR label/archive actions, commit status creation) — it does not by itself yield remote code execution or `GITHUB_TOKEN` exfiltration, since none of the reachable handlers execute arbitrary code with attacker-controlled input directly.

### Likelihood Explanation
This requires the attacker to already control (i.e., be able to generate valid signed deliveries for) at least one organization/app installation registered on the same Shipit instance — a moderate bar, but realistic for any multi-tenant Shipit deployment (as explicitly documented in `secrets.development.shopify.yml` supporting `somegithuborg`/`someothergithuborg`). No `webhook_secret`, `api_clients_secret`, GitHub App private key or Shipit session of the *target* org is needed — only knowledge/possession of one's own org's secret, which the rules permit as an unprivileged-attacker starting point relative to the target org's boundary.

### Recommendation
- After parsing the payload, verify that the organization implied by `repository.full_name` (or `organization.login`) matches the `repository_owner` used to select the `webhook_secret`, rejecting the request (422) on mismatch.
- Alternatively, key `verify_signature` and repository/stack resolution off the exact same field, so the field that authorizes and the field that authorizes-for-what can never diverge.
- Add a regression test that sends a payload signed by Org A's secret but naming Org B's `repository.full_name`/`full_name` and asserts rejection.

### Proof of Concept
1. Shipit is configured with two GitHub App installations, `org-a` and `org-b`, each with its own `webhook_secret` (as supported by `Shipit.github(organization:)`).
2. Attacker controls `org-a` and can trigger (or replay) a `push` webhook delivery from GitHub for a repo under `org-a`, giving them a valid `X-Hub-Signature` computed with `org-a`'s `webhook_secret` over an attacker-chosen raw body (GitHub HMACs the exact raw JSON body sent).
3. Attacker crafts the raw JSON body so that:
   - `repository.owner.login = "org-a"` (used only for signature-secret selection),
   - `repository.full_name = "org-b/target-repo"`, `ref = "refs/heads/main"`, `after = "<sha>"` (used by `PushHandler`/`Handler#repository_name`).
4. POST this body plus the valid `org-a` HMAC to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which succeeds because the signature really was computed with `org-a`'s secret over this exact body.
6. `Shipit::Webhooks.for_event('push')` runs `PushHandler`, which calls `stacks` → `Repository.from_github_repo_name("org-b/target-repo")` and enqueues `GithubSyncJob`/other side effects against `org-b`'s stack, even though the request was never signed with `org-b`'s secret. [8](#0-7) [9](#0-8)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "status=#{status}"
      ].join(' '))
    end
