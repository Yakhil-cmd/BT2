The audit is confirmed: `StatusHandler#process` resolves target commits by SHA alone, globally, with zero repository/stack scoping — unlike its sibling `CheckSuiteHandler`, which explicitly scopes through `stacks.where(branch: ...)` before touching commits.

### Title
Global, unscoped `Commit.where(sha:)` lookup lets a status webhook for one repository mutate Commit/Status rows belonging to any other Stack sharing the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire `commits` table and calls `create_status_from_github!` on every match, with no filter on `stack_id`/`repository`. Any two Stacks (regardless of which GitHub repository they track) that happen to contain a `Commit` row with an identical `sha` — a normal occurrence for forks/mirrors of the same upstream repository, or duplicated fixtures — will both be mutated by a single incoming `status` webhook.

### Finding Description
The broken binding is: `webhook.repository.full_name == commit.stack.repository.full_name` is assumed but never enforced. In practice `StatusHandler.call(params)` only checks `params.sha == commit.sha`, independent of which repository the webhook claims to originate from.

Code path:
- `Shipit::WebhooksController#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `Handler#initialize` parses `payload` into `params` and exposes a `stacks` helper that *does* scope by `Repository.from_github_repo_name(repository_name)` [2](#0-1) .
- `CheckSuiteHandler`, for the analogous `head_sha` lookup, correctly uses this scoping: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) ... }` [3](#0-2) .
- `StatusHandler#process`, however, bypasses `stacks`/repository scoping entirely and queries the global `Commit` table: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .
- `create_status_from_github!` writes a new `Status` row, updates the commit's cached status, and fires `Hook.emit(:commit_status/:deployable_status, stack, ...)` and potentially schedules merges/continuous delivery for **each** matching stack [5](#0-4) [6](#0-5) .

`verify_signature` only proves the webhook was signed for the claimed `repository_owner`'s org secret; it never proves that the `sha` in the payload is unique to that repository, and `StatusHandler` never re-checks the `repository` field from the payload before matching commits. Since git SHAs are content-addressed, two independent Stacks that track a shared commit (mirrors, forks, cherry-picks, squash-merges of the same tree/parents/author/timestamp) will legitimately contain identical SHAs, so no hash collision attack is even required — a normal legitimately-signed `status` webhook from repository A's own CI is sufficient to also mutate repository B's Stack/Commit rows and fire hooks, schedule continuous delivery, and unblock merges on B, if B has a commit with that same SHA.

### Impact Explanation
A `status` webhook, properly signed for repository A, causes `Status` rows to be created and `Hook.emit(:commit_status, :deployable_status, ...)` to fire on any other Stack/repository B whose `Commit` table contains the same `sha` — even though B never authenticated or authorized this webhook. This can flip a commit's aggregate CI status on B, trigger `stack.schedule_merges` and `ContinuousDeliveryJob`, potentially unblocking an unauthorized deploy on B. This is a cross-tenant mutation ("a payload for one repository mutating another's stack, commit ... "), matching the Critical severity bucket. It is repeatable for every status event and for as many repositories as share commit history (fork/mirror setups are common).

### Likelihood Explanation
Requires only that two Stacks in the same Shipit instance contain a `Commit` row with the same `sha` — realistic whenever Shipit tracks both an upstream repository and its fork/mirror, or when a commit is cherry-picked/rebased identically into two tracked repos. No secrets, no privileged role, and no hash-collision attack are needed; the attacker only needs the ability to get a legitimately-signed `status` webhook fired for their own onboarded repository (something any repository owner/CI can trigger), and for the shared SHA condition to hold.

### Recommendation
Scope `StatusHandler#process` through the same repository-aware `stacks` helper used by `CheckSuiteHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring only commits belonging to Stacks of the webhook's own repository are updated.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook for one repository mutates commits belonging to another repository's stack" do
          first = shipit_commits(:first)
          other_stack = shipit_stacks(:shipit) # a different Stack/repository than first.stack
          refute_equal first.stack_id, other_stack.id

          duplicate = other_stack.commits.create!(
            sha: first.sha, author: first.author, committer: first.committer,
            authored_at: Time.now, committed_at: Time.now, message: "duplicate sha commit"
          )

          assert_operator Commit.where(sha: first.sha).count, :>, 1

          params = OpenStruct.new(
            sha: first.sha, state: 'success', context: 'ci/example',
            description: nil, target_url: nil, created_at: Time.now.to_s
          )

          assert_difference -> { first.reload.statuses.count } => 1,
                             -> { duplicate.reload.statuses.count } => 1 do
            Shipit::Webhooks::Handlers::StatusHandler.new(params.to_h.stringify_keys.merge(
              'repository' => { 'full_name' => first.stack.repository.full_name }
            )).process
          end
        end
      end
    end
  end
end
```
This demonstrates that a payload scoped (by its own `repository` field) to `first.stack`'s repository nonetheless mutates `duplicate`, which belongs to an unrelated Stack/repository, confirming the missing repository scope.
