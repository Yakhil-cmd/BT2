### Title
Webhook signature verification key selected from an unverified field, decoupled from the repository field the handler actually writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to validate the incoming webhook signature against using a value taken directly from the still-unauthenticated JSON body. The handlers that subsequently mutate state (e.g. `PushHandler`) resolve the target `Stack`/`Repository` from a *different* field of that same unauthenticated body. Nothing binds "the organization whose secret verified this request" to "the repository the request is allowed to act on," so the equality `verified_organization == repository.full_name.owner` is never enforced.

### Finding Description
`repository_owner`, used to select the verification key, is read straight from the request body before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` dispatches to the `GitHubApp` instance configured for that login and calls `verify_webhook_signature`, which HMACs the *entire* raw body with that organization's `webhook_secret`: [3](#0-2) 

Critically, when an onboarded organization has no `webhook_secret` configured, verification is a no-op (`return true unless webhook_secret`), i.e. any payload claiming to be from that organization is accepted unconditionally.

Once "verified" (or waived), `create` dispatches the raw JSON to every registered handler for the event: [4](#0-3) 

But `Handler#repository_name`, used by every handler (e.g. `PushHandler`) to look up the `Stack`s to mutate, reads `repository.full_name` — a field completely separate from `repository.owner.login`/`organization.login` used for signature-key selection: [5](#0-4) [6](#0-5) 

Shipit is designed to host multiple GitHub organizations/Apps on one instance (`Shipit.github(organization:)` dispatch, and the multi-app fixture `test/dummy/config/secrets_double_github_app.yml`), so a single Shipit deployment commonly tracks repositories belonging to more than one organization, each with its own App/secret. Because the field used to pick the verification key (`repository.owner.login`) is never checked against the field used to pick the mutated resource (`repository.full_name`), a payload can legitimately claim to be "from organization A" for verification purposes while carrying `repository.full_name` pointing at a stack that belongs to organization B tracked by the same Shipit instance. Combined with the fail-open `return true unless webhook_secret` behavior for any organization lacking a configured secret, an attacker only needs one such under-configured (or otherwise secret-known) organization entry to forge a request that is accepted by `verify_signature` yet whose payload targets an arbitrary `full_name` already tracked by the instance.

### Impact Explanation
`PushHandler` resolves stacks purely from the attacker-controlled `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` on all matching, non-archived stacks for the given branch. For stacks with `continuous_deployment` enabled, syncing new commit state is the trigger path toward automatic deploy scheduling. An attacker able to satisfy verification for any one onboarded organization (via a missing/no-op `webhook_secret`, which the engine's own `verify_webhook_signature` accepts by design) can thereby force sync/deploy-triggering behavior against a stack belonging to a completely different repository/organization than the one whose credentials were checked — an unauthorized cross-repository/cross-organization write that breaks the deployment-trust boundary the webhook signature is meant to enforce.

### Likelihood Explanation
Exploitation does not require a Shipit session, `ApiClient` token, or GitHub write access to the *target* repository — only that the verification path resolves to an organization whose secret the attacker can satisfy (unset secret, or a secret from an organization they legitimately administer within the same multi-tenant Shipit instance). The decoupling between `repository.owner.login` and `repository.full_name` is unconditional application logic, not a corner case, so any deployment where more than one organization is onboarded (a documented, tested configuration) is exposed once any single org's verification is satisfiable.

### Recommendation
Bind the two fields explicitly: after `verify_webhook_signature` succeeds for `repository_owner`, reject the payload in `create`/`Handler` unless `payload.dig('repository', 'full_name')`'s owner segment equals the verified `repository_owner`. Additionally, make `verify_webhook_signature` fail closed (reject) rather than pass when `webhook_secret` is blank, or require `webhook_secret` presence at boot for every configured organization.

### Proof of Concept
1. Shipit instance is configured with organizations `org-a` (no `webhook_secret` set, or secret known to the attacker) and `org-b` (owns tracked repo `org-b/prod-app`, a stack with `continuous_deployment: true`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/prod-app" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha that exists in org-b/prod-app>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-a")`; since `org-a` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`) — request passes.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/prod-app")` and calls `stack.sync_github(expected_head_sha: ...)` on the `org-b` stack, triggering sync/CD behavior on a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
