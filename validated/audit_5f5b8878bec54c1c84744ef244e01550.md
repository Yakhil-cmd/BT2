The key vulnerability is in `handleKLAYTransfer` in `BridgeTransferKLAY.sol`: the nonce state is updated before the KLAY transfer, but if the transfer reverts (because `_to` is a contract that rejects KLAY), the entire transaction reverts — rolling back the nonce update — and the bridge is permanently stuck at that nonce with the KLAY locked.

### Title
Recipient-Controlled Revert in `handleKLAYTransfer` Permanently Locks Bridge Nonce and KLAY — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` delivers KLAY to a user-supplied `_to` address via a low-level `.call.value()`. If `_to` is a contract that reverts on receiving KLAY, the `require(ok, ...)` check causes the entire transaction to revert, rolling back all nonce state updates. Because the `_to` address is fixed by the original cross-chain request and cannot be changed by operators, every subsequent retry also reverts. The bridge's `lowerHandleNonce` is permanently stuck, the bridged KLAY is permanently locked, and the value-transfer recovery loop spins indefinitely.

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` executes the following sequence:

1. Validates and votes on the nonce (`_lowerHandleNonceCheck`, `_voteValueTransfer`)
2. Marks the request tx hash as handled (`_setHandledRequestTxHash`)
3. Records the block number and **advances the handle nonce** (`_updateHandleNonce`)
4. Emits `HandleValueTransfer`
5. Sends KLAY: `(bool ok, ) = _to.call.value(_value)("");`
6. `require(ok, "handleKLAYTransfer: transfer failed");`

If step 5 returns `ok = false` (because `_to` is a contract with a reverting `receive()`/`fallback()`), step 6 reverts the entire transaction. All state mutations from steps 2–4 are rolled back. The nonce is never consumed.

The `_to` address is set by the user on the source chain via `requestKLAYTransfer(address _to, ...)`. The bridge operator has no ability to substitute a different recipient — they must relay exactly what was requested. Every operator retry with the same nonce will fail identically.

`_updateHandleNonce` advances `lowerHandleNonce` by scanning consecutive entries in `handleNoncesToBlockNums`. Because the stuck nonce's entry is never written (always rolled back), `lowerHandleNonce` can never advance past it, even if higher nonces are successfully handled.

### Impact Explanation

- **KLAY locked**: The KLAY value for the stuck request is permanently locked in the bridge contract; neither the sender nor the recipient can recover it.
- **`lowerHandleNonce` permanently stuck**: `recoveryBlockNumber` never advances past the stuck nonce's block, breaking the value-transfer recovery mechanism (`vt_recovery.go`).
- **Operator DoS**: The recovery loop (`processingPendingRequestEvents` → `handleRequestValueTransferEvent`) retries the stuck nonce indefinitely, consuming operator gas and resources.
- **Scope**: Affects the Kaia service-chain bridge's KLAY settlement path — a system-managed fund with cross-chain asset impact.

### Likelihood Explanation

Any user who can call `requestKLAYTransfer` on the source chain can trigger this. No special privilege is required. The attacker simply deploys a contract that reverts on receiving KLAY and uses it as `_to`. The cost is only the gas for the source-chain request transaction.

### Recommendation

Replace the hard `require` on the KLAY transfer with a pattern that does not revert the nonce state on delivery failure. Two options:

1. **Pull-payment / escrow**: Record the owed amount in a mapping and let the recipient claim it separately. This is the safest approach.
2. **Suppress delivery failure**: Capture `ok` but do not `require` it; emit a `DeliveryFailed` event so operators can take manual action, while the nonce is still consumed and `lowerHandleNonce` advances.

Do not simply remove the `require` without recording the failure, as that would silently lose funds.

### Proof of Concept

```
// SPDX-License-Identifier: MIT
pragma solidity 0.5.6;

// Deploy on the destination chain
contract KAIARejector {
    // Reverts on any KLAY receive
    function() external payable { revert("no KLAY"); }
}
```

**Attack steps:**

1. Attacker deploys `KAIARejector` on the destination chain at address `R`.
2. Attacker calls `bridge.requestKLAYTransfer{value: V}(R, V, "")` on the source chain.
3. Source-chain bridge emits `RequestValueTransfer(KLAY, attacker, R, 0, V, nonce=N, ...)`.
4. Bridge operators call `handleKLAYTransfer(txHash, attacker, R, V, N, blockNum, "")` on the destination chain.
5. `_updateHandleNonce(N)` runs — `handleNoncesToBlockNums[N]` is set, `lowerHandleNonce` may advance.
6. `R.call.value(V)("")` → `KAIARejector.fallback()` reverts → `ok = false`.
7. `require(ok, ...)` reverts the entire transaction; all state from step 5 is rolled back.
8. `lowerHandleNonce` remains at `N`; `handleNoncesToBlockNums[N]` is never set.
9. Every subsequent operator retry of nonce `N` fails identically.
10. `V` KLAY is permanently locked in the bridge; `lowerHandleNonce` is permanently stuck at `N`.

**Corrupted values:**
- `lowerHandleNonce` (stuck at `N`, never advances)
- `recoveryBlockNumber` (never advances past `N`'s block)
- Bridge KLAY balance (permanently inflated by `V`) [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
