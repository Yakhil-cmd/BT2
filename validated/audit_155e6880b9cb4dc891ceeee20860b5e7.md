### Title
RAY-scaled debt/supply value overflow in `accrue_step` permanently freezes a market — (`common/src/rates/simulate.rs`, `contracts/pool/src/interest.rs`)

### Summary
The pool's interest accrual computes `borrowed_original = scaled_to_original(borrowed, borrow_index)` and `supplied_original = scaled_to_original(supplied, supply_index)`, i.e. `shares * index / RAY` in `i128`/`I256` with a `MathOverflow` panic when the result exceeds `i128::MAX` (`common/src/rates/scaling.rs:14-16`, `common/src/rates/simulate.rs:60-61`, `common/src/math/fp_core.rs:108-118`). Because every pool mutation runs `interest::global_sync` (accrue-first) before touching shares or cash (`contracts/pool/src/interest.rs:20-33`, `contracts/pool/README.md:159-168`), once `borrowed * borrow_index` (or `supplied * supply_index`) can no longer be represented, every entrypoint on that market — `supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `recapitalize`, `claim_revenue`, `update_indexes` — reverts permanently. All supplier principal and unclaimed yield in the market is frozen forever.

### Finding Description
The analog to the GTKWave integer overflow is unchecked-domain `i128` multiplication inside the mandatory accrual path. The protocol's own numeric-limit analysis fixes the ceiling: a RAY-denominated balance cannot exceed `i128::MAX / RAY ≈ 1.7014e11` whole tokens, and `scaled * index` is bounded by the same value (`certora/common/spec/rates_rules.rs:22-30`, `docs/reference/formulas.md`). Two compounding facts make this ceiling reachable:

1. `borrow_index` is monotone and grows with elapsed time; it is only capped at `MAX_BORROW_INDEX_RAY = 10^36` (~1e9 × RAY) inside `update_borrow_index` — but `scaled_to_original(borrowed, borrow_index)` is evaluated *before* and *at every* index value on the way to that cap. For a market holding ~1e9 whole-token scaled shares, the value overflows `i128` once the index passes ~170×RAY — long before the index cap can stop accrual.
2. The value depends on `borrowed`/`supplied` share totals, which any unprivileged user inflates via `controller.supply` / `controller.borrow` against an 18-decimal asset whose caps are set within the validated asset domain (`require_cap_within_asset_domain`).

The protocol's own regression test demonstrates the cliff: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` supplies 1e9 whole tokens at 18 decimals, borrows 98%, and shows that after enough years `try_update_indexes_for` fails with `MATH_OVERFLOW`, that `borrow_index < MAX_BORROW_INDEX_RAY` (the cap never engages), and that subsequent `withdraw` and `repay` calls also fail with `MATH_OVERFLOW` because they accrue first (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`).

### Impact Explanation
Permanent freezing of all user funds in the affected market and theft-equivalent loss of unclaimed yield: suppliers can never `withdraw`, borrowers can never `repay`, liquidators cannot `seize_positions`/`liquidate` through the frozen market, and `recapitalize` cannot restore it because it also accrues first (`contracts/pool/src/ops/*` all pass through `Cache::load` → `global_sync`). Since `last_timestamp` is only stamped by a successful accrual (`cache.mark_accrued`), the panic is self-perpetuating — elapsed time only increases the product. There is no owner path to shrink `borrowed`/`supplied` or roll back the index, so the freeze is irreversible.

### Likelihood Explanation
Reachable by a single unprivileged address: `controller.supply` a large amount of a high-decimals listed asset, `controller.borrow` to high utilization, then wait — or simply let natural accrual run on an already-large market. No oracle manipulation, no privileged role, and no cooperation is needed; time is the only other input, and accrual is driven by the permissionless `update_indexes` keeper path as well as every user verb. The only precondition is a market whose share total is within a few orders of the `i128::MAX / RAY` value bound — explicitly within the domain `require_cap_within_asset_domain` permits for 18-decimal assets — or, asymptotically, any nonzero market as `borrow_index` approaches `MAX_BORROW_INDEX_RAY`. The repository ships a test proving the exact failure sequence.

### Recommendation
Make accrual saturation-safe rather than panicking:
- In `accrue_step`, clamp `borrowed_original`/`supplied_original` via `mul_div_floor_saturating` (already used by `calculate_scaled_cap`) or widen utilization inputs to `I256` so a value above the ceiling saturates utilization at 100% instead of trapping.
- Enforce the bound at ingress: cap `supplied`/`borrowed` scaled share totals (and/or market caps) so `shares * MAX_*_INDEX_RAY / RAY` always fits `i128`, and validate caps accordingly in `require_cap_within_asset_domain`.
- Alternatively, lower `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` so the index cap engages before the value ceiling for any permitted share total.

### Proof of Concept
Existing test — `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`:

```rust
let principal = BILLION * 10i128.pow(18);          // 1e9 whole tokens, 18 decimals
t.supply_raw(BOB, "BIG18", principal);             // unprivileged supply
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization, XLM curve
// advance time year-by-year until:
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
// market now frozen: every verb accrues first and hits the same panic
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `accrue_step` → `scaled_to_original(env, borrowed, borrow_index)` → `Ray::mul` → `fp_core::mul_div_half_up` → `panic_with_error!(env, GenericError::MathOverflow)` when `borrowed * borrow_index / RAY > i128::MAX`.
