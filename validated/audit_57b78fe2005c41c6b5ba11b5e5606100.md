Found the key binding: `verify_signature` authenticates the webhook using the organization derived from `repository.owner.login` (or `organization.login`), but `Handler#stacks` resolves the target repository from a *different* field, `repository.full_name`, which is never covered by that same signature check.

### Title
Webhook signature verified against `repository.owner.login` while handlers act on the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the `X-Hub-Signature` HMAC against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the signature is accepted, the full raw payload (including `repository.full_name`) is handed to `Shipit::Webhooks::Handlers::Handler`, whose `stacks`/`repository_name` methods use `payload.dig('repository', 'full_name')` — a completely different, unauthenticated field — to look up the `Repository` and its `Stack`s that the webhook event will mutate.

### Finding Description
The authentication boundary and the write boundary use two different fields of the same attacker-controlled JSON body:

- Authentication is bound to `repository.owner.login` (falling back to `organization.login`): `Shipit.github(organization: repository_owner)` selects the `webhook_secret` used to validate the HMAC signature. [1](#0-0) [2](#0-1) 

- Write target selection is bound to `repository.full_name`: `Handler#stacks` calls `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')`. [3](#0-2) [4](#0-3) 

The HMAC only proves the payload bytes were signed by *some* organization's configured secret, and the org used to pick the secret is `repository.owner.login`. Nothing in `verify_signature` ties `repository.owner.login` to `repository.full_name`, or ensures they refer to the same repository. If an attacker controls (or has been granted access as) a GitHub organization/app installation "OrgA" registered in this Shipit instance (i.e., knows or can trigger a signed webhook with OrgA's `webhook_secret`), they can craft a webhook payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` picks OrgA's secret and the check passes when signed with OrgA's secret)
- `repository.full_name` = `"OrgB/some-other-repo"` (a completely different, unrelated repository/stack tracked by this Shipit instance)

The equality the engine is implicitly relying on — `repository.owner.login used-for-signing == repository.full_name used-for-mutation` — is never checked, breaking the "organization that authenticated versus the repository that is written" binding described by the bug class. Because handlers such as the `pull_request` handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc.) and `push`/`status` handlers act on `stacks` resolved this way, an attacker who can produce a validly-signed webhook for OrgA can inject events (label captures, merge-queue triggers, commit/status updates, PR open/close transitions) against stacks belonging to a repository they do not control.

### Impact Explanation
This crosses a credential/authentication boundary: the HMAC signature is meant to prove "this event genuinely originates from GitHub for the organization/app installation configured with this secret," but the engine uses it to authorize actions on a repository named by an unverified field. This enables cross-repository writes to `MergeRequest`/`Stack`/`Commit`/label state for a repository outside of the authenticating organization's control, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability requires the attacker to already have a legitimate, correctly-configured GitHub App/webhook secret for at least one organization onboarded to this Shipit instance (a realistic scenario in a multi-tenant/shared Shipit deployment where many orgs each configure their own `webhook_secret`/GitHub App, as supported by `Shipit.github(organization: ...)`). No repository write access or Shipit session/API token is required — only control over one organization's outbound-to-Shipit webhook payload contents (which GitHub apps allow via custom webhook redelivery/test payloads, or a compromised/malicious org owner). Given the mismatch between the two fields is structural (not a data-entry accident), likelihood is credible for any deployment onboarding multiple organizations.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`#stacks`), require that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before resolving/acting on `stacks`. Reject the webhook (422) if they disagree, so the field used to select the signing secret and the field used to select the mutated repository are provably the same identity.

### Proof of Concept
1. Attacker legitimately administers/operates GitHub org `attacker-org`, which is registered in this Shipit instance with its own `webhook_secret` (`S_attacker`).
2. Attacker crafts a JSON body for, e.g., a `pull_request` event:
```json
{
  "action": "opened",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "pull_request": { ... }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, body)>` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because it was signed with `S_attacker`. [5](#0-4) 
5. `create` dispatches to `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.call(params)`, whose base class resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, acting on the victim's stacks despite the request never being signed by `victim-org`'s secret. [6](#0-5) 

Note: I was unable to fully trace, within the available iterations, every downstream handler's exact side effects (e.g., exact mutation paths for `push`/`status`/`membership` handlers) to enumerate the complete blast radius; the finding is demonstrated at the `Handler` base-class level shared by all webhook handlers, which is sufficient to prove the broken binding.
