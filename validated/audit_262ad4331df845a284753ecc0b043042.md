### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the repository actually mutated is looked up from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) pulled straight out of the unauthenticated request body. Once the HMAC check passes, every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, etc.) independently re-reads the payload and resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` (`Handler#repository_name`). Nothing ties `repository.full_name`'s owner to the `repository.owner.login`/`organization.login` value that was actually used to select the signing secret.

### Finding Description
The binding that should hold is:
`organization used to verify the HMAC signature == organization that owns the repository whose stacks get mutated`

In this engine that binding is never enforced:

- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it only to pick the `GitHubApp` (`Shipit.github(organization: repository_owner)`) used to validate `X-Hub-Signature` <cite repo="Ellentat/shipit-engine--007" path="app/controllers/shipit/webhooks_controller.rb" start="24="48" /> [1](#0-0) 
- `Shipit.github` resolves the app config purely by that `organization` key in `secrets.github`, independent of anything else in the payload [2](#0-1) 
- Once `verified` is true, `create` dispatches the *entire* raw JSON body (unfiltered) to every registered handler for the event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) 
- `Handler#stacks`/`Handler#repository_name` then locate the affected `Repository` using a *different* field of the same payload: `payload.dig('repository', 'full_name')` [4](#0-3) 
- `PushHandler#process` uses that repository's stacks to enqueue a `sync_github` for a given ref, and `StatusHandler#process` writes commit statuses for any `Commit` matching the given `sha`, again scoped only by whatever `repository`/`sha` values are in the JSON body [5](#0-4) [6](#0-5) 

Because `repository.owner.login`/`organization.login` and `repository.full_name`'s owner are two independent JSON fields with no cross-check, an attacker who legitimately controls a GitHub App installation on Org A (and therefore its `webhook_secret`) can craft a payload where:
- `repository.owner.login` = `OrgA` (so the signature check passes with OrgA's secret), and
- `repository.full_name` = `OrgB/some-repo` (a repository/stack that Shipit tracks for a *different*, unrelated organization/installation).

The signature only proves "this request came from someone who knows OrgA's webhook secret" — it does not prove anything about which repository the payload claims to describe. This is the same class of bug as the CustomSwap finding: a value used to authorize/scale an operation (`_targetPrice`) diverges from the value actually acted upon, because the code assumes two related fields will always agree without enforcing it.

### Impact Explanation
An attacker holding a valid installation/webhook secret for one organization onboarded to a multi-org Shipit deployment (`config/secrets.yml` `github: <org>: ...`, as documented in `docs/setup.md`) can forge signed webhook deliveries that make Shipit act on stacks belonging to a completely different organization it is unaware of, e.g.:
- Force a `push` event to trigger `GithubSyncJob`/`sync_github` for an arbitrary tracked stack (`PushHandler`), potentially causing Shipit to fetch/sync a ref of the attacker's choosing for that stack.
- Inject arbitrary commit statuses on real commits via `StatusHandler#process`, which is read by continuous-delivery gating logic to decide whether commits are safe to deploy (`ci.require`/`ci.blocking` checks described in the README). Injecting a fabricated "success" status for a required CI context on someone else's stack can bypass the CI gate and let an unrelated, unreviewed commit be merged/deployed.

This crosses the "escalation into authorization" bar defined in scope (unauthenticated actor manipulates state/CI-gating of a stack/repository outside the organization whose credentials were actually used to authenticate the request), which the rules class as High.

### Likelihood Explanation
Requires the attacker to already control a legitimate GitHub App installation (and its webhook secret) for at least one organization configured in `Shipit.github` — this is realistic in any environment supporting multiple orgs (explicitly documented in `docs/setup.md` "Using Multiple GitHub Applications" and `test/dummy/config/secrets_double_github_app.yml`). No repository write access, `ApiClient` token, or `GITHUB_TOKEN`/private key is required — only knowledge of one org's `webhook_secret`, and the ability to POST to `/webhooks`. The attack payload is trivial to construct (standard JSON body, valid HMAC computed with the attacker's own secret).

### Recommendation
- After signature verification, cross-check that the organization used to select the `GitHubApp`/secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers; reject (422) on mismatch.
- Alternatively, have handlers resolve the target repository using the same `repository_owner` value used for signature verification rather than independently re-parsing `full_name`, so a single trusted field drives both authentication and repository resolution.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and webhook secret (as in `test/dummy/config/secrets_double_github_app.yml`), and stacks tracked for repos under both.
2. As an attacker who is the (legitimate) GitHub App/organization admin for `OrgA`, build a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully.
5. `PushHandler#process` is invoked with the same payload; `Handler#repository_name` returns `"OrgB/victim-repo"`, and `Repository.from_github_repo_name("OrgB/victim-repo")` resolves OrgB's stacks, which then get `sync_github(expected_head_sha: "<attacker-chosen sha>")` triggered — even though the request was never signed by anything belonging to OrgB.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
