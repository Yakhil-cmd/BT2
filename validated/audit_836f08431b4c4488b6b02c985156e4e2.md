### Title
Webhook signature verification failure does not halt request processing, allowing forged webhooks to escalate into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` is registered as a `before_action`, but when signature verification fails it only calls `head(422)` — it never calls `return` nor `throw(:abort)`. In Rails (5+), a `before_action` callback chain is **not** halted by rendering/`head`; it is only halted by explicitly throwing `:abort`. As a consequence, after `verify_signature` fails, the callback chain still proceeds into `WebhooksController#create`, which parses the (unverified, attacker-controlled) JSON body and dispatches it to the registered `Shipit::Webhooks` handlers before the response is ever returned to the client.

### Finding Description [1](#0-0) [2](#0-1) 

`head(422)` sets the response body/status but does not halt callback execution — no `throw(:abort)` is issued, and there is no `return` before falling through to the trailing `Rails.logger.info` call and, more importantly, back into the `process_action` flow which continues to `create`. This means the equality that should hold — "webhook payload processed" == "webhook payload whose HMAC signature was verified with `webhook_secret`" — is broken: an attacker who does **not** know the app's `webhook_secret` can still get their forged payload dispatched to `Shipit::Webhooks.for_event(event)` handlers.

One of the built-in handlers, `MembershipHandler`, directly mutates authorization-relevant state from unauthenticated payload fields: [3](#0-2) 

`Team#add_member` simply appends the member with no additional verification: [4](#0-3) 

Team membership is exactly what gates access to the whole engine via `User#authorized?`, consumed by `force_github_authentication`: [5](#0-4) [6](#0-5) 

So an attacker who knows (or guesses) any `Shipit.github_teams` id/slug and a GitHub login (their own, or a colleague's, obtained from public GitHub profile data) can `POST /webhooks` with `X-Github-Event: membership`, `action: added`, and a `team` block matching one of `Shipit.github_teams`, with no valid `X-Hub-Signature`. `verify_signature` fails and calls `head(422)`, but because the chain isn't aborted, `create` still runs and `MembershipHandler#process` adds that GitHub login to the authorized team in Shipit's own database — independent of GitHub's real team membership. On next login, `User#authorized?` now returns true for that login, bypassing the intended GitHub-team-based access control.

### Impact Explanation
This is an authentication/authorization-bypass class issue: an unprivileged network attacker with no GitHub credentials, no `webhook_secret`, and no Shipit session can forge a webhook payload that Shipit still processes as if it came from GitHub, and specifically can escalate an arbitrary GitHub login into `Shipit.github_teams` authorization — matching the explicitly allowed High-severity bucket ("escalation into `Shipit.github_teams` authorization"). The same missing-halt bug also lets other handlers (`push`, `status`, `check_suite`) act on forged data (e.g. enqueuing `GithubSyncJob`, creating commit `Status` rows used for deploy gating), widening the blast radius beyond just membership.

### Likelihood Explanation
The root cause is a simple, deterministic control-flow bug (missing `throw(:abort)`/`return`) with no timing or race dependency — it fires on every single request where `verify_webhook_signature` returns `false`, i.e. every forged, unauthenticated request. No secret material, prior session, or GitHub credentials are required; the attacker only needs a public HTTP endpoint (`/webhooks`) and knowledge of an existing team's GitHub id/slug/org (visible in Shipit's own UI/URLs) and any GitHub login string.

### Recommendation
In `app/controllers/shipit/webhooks_controller.rb#verify_signature`, explicitly halt the callback chain when the signature check fails, e.g.:
```ruby
def verify_signature
  ...
  unless verified
    head(422)
    throw(:abort)
  end
  ...
rescue Shipit::GithubOrganizationUnknown => e
  head(422)
  throw(:abort)
end
```
Apply the same fix to `check_if_ping` and `drop_unhandled_event`, which have the identical missing-halt pattern.

### Proof of Concept
1. Identify an existing authorized team via Shipit's UI/DB (e.g. `github_id`, `slug`, `organization` of a team in `Shipit.github_teams`).
2. Send, without any valid `webhook_secret`:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (invalid)
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <known_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "<org>"},
  "member": {"login": "<attacker-github-login>"}
}
```
3. `verify_signature` fails and calls `head(422)`, but does not `throw(:abort)`, so `create` still runs `MembershipHandler#process`, which calls `team.add_member(User.find_or_create_by_login!("<attacker-github-login>"))`, inserting a `Membership` row.
4. The attacker's GitHub login now satisfies `User#authorized?` for that team, granting access to the full Shipit UI/API on next login, despite never having valid GitHub team membership or a valid webhook signature.
