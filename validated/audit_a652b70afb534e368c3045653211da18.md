### Title
Cross-tenant webhook forgery via organization/repository binding mismatch in signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using one payload field (`repository.owner.login`, falling back to `organization.login`), while the actual event handlers act on a *different* payload field (`repository.full_name`) to decide which `Stack`/`Commit` to mutate. Because the signature only proves "this body was signed by the secret belonging to organization X," but never proves that `repository.full_name` inside that same body actually belongs to organization X, a party who legitimately controls the webhook secret for one tenant/organization configured on a shared Shipit instance can forge webhook payloads that target and mutate stacks belonging to a completely different organization/repository.

### Finding Description
The signature check derives the verification key purely from attacker-controlled JSON content: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`. Shipit then looks up the corresponding GitHub App config with `Shipit.github(organization: repository_owner)` and verifies the raw body's HMAC against that org's `webhook_secret`. Multi-org installations are an explicitly supported and documented configuration, each org having its own independent `webhook_secret` in `secrets.yml`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the entire parsed body to the registered handlers: [4](#0-3) 

Every handler resolves the target `Repository`/`Stack` from a *different* field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality the system is supposed to enforce is: `organization whose secret signed the request == owner(repository.full_name acted on)`. Nothing in `verify_signature` or in any handler enforces `repository.owner.login == owner(repository.full_name)`, so this binding can be broken by simply crafting a JSON body where `repository.owner.login` names the org whose secret you know, while `repository.full_name` names an arbitrary other tenant's `owner/repo` string, then signing the whole raw body with your own known secret.

### Impact Explanation
On a Shipit instance configured for multiple GitHub organizations (a documented, supported configuration), any actor who legitimately possesses one org's `webhook_secret` (e.g., an admin of their own GitHub App/org onboarded onto a shared Shipit instance) can forge signed webhook deliveries that are accepted by the controller and then dispatched against a *different* organization's `Repository`/`Stack` records:
- `push`: forces `Stack#sync_github` with an attacker-chosen `expected_head_sha` on a victim stack the attacker has no authorization over.
- `status`: injects arbitrary `CommitStatus` records (`state`, `context`, `target_url`, `description`) onto a victim's tracked commits via `Commit#create_status_from_github!`, which can influence CI-gating logic used to decide whether a deploy/merge is safe.
- `check_suite`/`membership`/`pull_request` handlers are reachable through the same mismatch for any payload shape they parse.

This crosses a tenant/authorization boundary without any credential belonging to the victim organization, satisfying the "organization authenticated vs. repository written" binding-break class. Depending on how commit-status/check-suite data feeds into deploy safety gating elsewhere in the app, this can degrade to an unauthorized/forced deploy scenario (status forgery enabling merge/deploy gates to pass), which maps to the High/Critical impact bands in scope.

### Likelihood Explanation
Requires the attacker to know a valid `webhook_secret` for *some* organization configured on the same shared Shipit instance — realistic in the documented multi-organization deployment mode where distinct, mutually-untrusting teams/orgs share one Shipit install and each configures its own GitHub App/secret. No GitHub App private key, `GITHUB_TOKEN`, session, or `ApiClient` token is needed; only knowledge of one's own legitimately-provisioned webhook secret plus the ability to send an arbitrary HTTP POST to `/webhooks`, which is an unauthenticated, unauthorized-crossing action against another tenant's data.

### Recommendation
Enforce that `repository.owner.login` (or `organization.login`) used to select the signing key matches the owner segment of `repository.full_name` (and any other repository identifiers used in handlers) before dispatching to handlers. Alternatively, resolve the target `Repository` first, look up its known GitHub owner/org from Shipit's own configuration/DB (not from the untrusted payload), and verify the signature using that authoritative owner rather than a value taken from the request body.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.yml`: `attacker-org` (secret known to the attacker, who legitimately administers that org's GitHub App) and `victim-org` (unrelated tenant with a `Stack` tracking `victim-org/victim-repo`).
2. Attacker crafts:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and sends `POST /webhooks` with header `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC matches — request accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — an action the attacker was never authorized to trigger.
