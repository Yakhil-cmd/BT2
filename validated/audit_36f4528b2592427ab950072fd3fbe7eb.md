Confirmed root cause: this maps to the report's bug class — a value the security check authenticates over differs from the value the business logic actually acts on.

### Title
Webhook signature verification keyed on attacker-controlled `organization`/`repository.owner.login`, while target repository resolved from a different, unverified field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, computed by parsing the *unverified* raw body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . The actual repository acted upon by handlers (e.g. `PushHandler`) is resolved from a *different* field of the same payload, `repository.full_name`, via `Handler#repository_name` [2](#0-1) . Nothing binds `repository.owner.login` to `repository.full_name`'s owner segment, and `GitHubApp#verify_webhook_signature` additionally returns `true` unconditionally when no `webhook_secret` is configured for the selected organization: `return true unless webhook_secret` [3](#0-2) .

### Finding Description
The binding that should hold is: `organization used to pick/verify the HMAC secret == organization that owns the repository the payload's handler will act on`. In a multi-organization Shipit deployment (`docs/setup.md` documents this "Using Multiple Github Applications" mode) [4](#0-3) , each org has its own `webhook_secret` entry, and some orgs may legitimately have no secret configured (shown as `webhook_secret: # nil` in the sample secrets file) [5](#0-4) .

`verify_signature` runs as a `before_action` and computes `repository_owner` straight from the raw, unauthenticated JSON body, then fetches `Shipit.github(organization: repository_owner)` to verify the signature against that org's secret [6](#0-5) . Downstream, `create` re-parses the same raw body and dispatches to handlers using `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) , and those handlers locate the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` [8](#0-7) .

Because the field used to choose/verify the signing secret (`repository.owner.login` / `organization.login`) is independent from the field used to select the acted-upon repository (`repository.full_name`), and because an org with no configured `webhook_secret` causes `verify_webhook_signature` to trivially return `true` for any signature, a payload can pass verification "as org A" while its `repository.full_name` targets a stack belonging to org B. This is directly analogous to the TermMax finding: a downstream computation (there, the APR/pool-fee math; here, which repository the event is applied to) is driven by a value that was never covered by the same check that was supposed to authorize the whole operation.

### Impact Explanation
In a Shipit deployment configured with multiple GitHub organizations where at least one configured org key has no `webhook_secret` set (an explicitly documented, supported configuration per `docs/setup.md`), an attacker can send an unsigned/arbitrarily-signed webhook whose `organization.login`/`repository.owner.login` names that unsecured org (bypassing `verify_webhook_signature`'s `return true unless webhook_secret`), while setting `repository.full_name` to a different, secured organization's tracked repository. The dispatched handler (e.g. `PushHandler`) will then act on that unrelated stack, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` SHA [9](#0-8) , or for `status`/`check_suite`/`pull_request` events, forging commit statuses, check-suite refreshes, or PR label/merge-status changes on a repository the attacker does not control — all without a valid signature over the actually-affected repository. This crosses a repository-write / deploy-trust boundary purely by exploiting the mismatch between the verification key field and the target-repository field, without needing `webhook_secret`, an `ApiClient` token, or repository write access.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, and (2) at least one configured organization lacking a `webhook_secret`. Both are explicitly supported/documented configurations, not hypothetical misuse, and the mismatch between `repository_owner` and `repository_name` fields is exploitable by any unauthenticated network attacker who can reach the `/github/webhooks` endpoint (no session, no token, no prior credential required) — matching an "unprivileged attacker" analog.

### Recommendation
Bind the two fields together before trusting the payload: after selecting `repository_owner`/`organization` for secret lookup, verify that `repository.full_name`'s owner segment matches `repository_owner` (or, better, resolve the GitHub App/secret from the same `repository.full_name` value used later by `Handler#repository_name`, rather than from a separate `owner.login`/`organization.login` field). Reject the webhook if the two disagree, and treat a missing `webhook_secret` for a configured org as "reject" rather than "auto-accept" (`return true unless webhook_secret` should not exist, or should only allow this for explicitly single-tenant/no-multi-org deployments).

### Proof of Concept
1. Deploy Shipit with two orgs configured: `unsecured-org` (no `webhook_secret`) and `secured-org` (tracks a real stack, e.g. `secured-org/prod-app`).
2. POST to `/github/webhooks` with header `X-Github-Event: push`, an arbitrary/garbage `X-Hub-Signature`, and JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "organization": {"login": "unsecured-org"},
  "repository": {"full_name": "secured-org/prod-app", "owner": {"login": "unsecured-org"}}
}
```
3. `verify_signature` computes `repository_owner = "unsecured-org"`, fetches `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77` regardless of the bogus signature.
4. `create` dispatches to `PushHandler`, which resolves the target repository via `payload.dig('repository', 'full_name')` = `"secured-org/prod-app"`, and calls `sync_github(expected_head_sha: "<attacker chosen sha>")` on that stack — acting on `secured-org`'s repository despite verification having been performed against `unsecured-org`'s (non-existent) secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
