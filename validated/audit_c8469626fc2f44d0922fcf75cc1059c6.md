### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the commit to update purely by `sha`, with no repository/stack scoping, even though the base `Handler` class already exposes a `stacks`/`repository_name` helper that other handlers use for exactly this purpose. Any commit sharing that SHA across unrelated repositories (e.g., GitHub's universal empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any accidental SHA collision from squashed/rebased history) will have its status written from a webhook that is only authenticated as belonging to a different repository.

### Finding Description
The broken binding is: `payload['repository']['full_name']` (the repo the webhook and its signature are actually scoped to) == `commit.stack.repository.full_name` (the repo whose commit gets mutated). This does not hold.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Compare this to the base `Handler` class, which defines `stacks` and `repository_name` precisely to scope handler logic to the repository named in the webhook payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`StatusHandler` never calls `stacks` or filters by `repository_name`; it queries `Commit` globally by `sha` alone. `Commit` is uniquely identified by `(stack_id, sha)` in practice but not filtered to a specific stack here, so any row in any stack with a matching SHA is updated.

`WebhooksController#verify_signature` only authenticates that the payload originates from a real GitHub webhook for `repository_owner`'s configured GitHub App/organization secret — it does not, and cannot, prove which specific repository's *commit rows in Shipit's database* should be mutated; that binding is left entirely to each handler's own scoping logic [3](#0-2) . Since `StatusHandler` omits repository scoping, a validly-signed webhook from the attacker's own (legitimately onboarded/authorized) repository can, by SHA collision, write a status onto a `Commit` belonging to a completely different stack/repository that the attacker never authenticated against.

Exploit flow: attacker creates an empty repository under an org where Shipit's GitHub App/webhook is already installed (satisfying `verify_signature` for that org), pushes a commit whose SHA is guaranteed/likely to collide with a real commit already tracked by some other stack (e.g., the canonical empty-tree SHA, or any repo's very first commit which is often near-identical across scaffolded projects), and triggers a `status` event (e.g., via a GitHub Action) with arbitrary `state`/`context`/`target_url`/`description`. GitHub delivers this as a legitimately-signed webhook for the attacker's own repo. `StatusHandler#process` ignores `payload['repository']` and updates every `Commit` row across all stacks matching that SHA, including ones in unrelated repositories.

### Impact Explanation
An attacker who controls only their own onboarded repository can inject arbitrary commit statuses (`success`/`failure`/`pending`, description, target_url) onto commits belonging to other tenants' stacks whenever a SHA collision exists. Since commit statuses can gate merge/deploy decisions elsewhere in Shipit (status checks feeding into deploy readiness), this is a payload for one repository mutating another's commit record — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The practical blast radius depends on SHA collision likelihood: the canonical empty-tree SHA is universal and trivially reproducible without any brute force, satisfying the "trivially reproducible" framing in the question, though it only matters if some tracked stack happens to have recorded a `Commit` row with that exact SHA (which is plausible for empty/initial commits and rebase artifacts).

### Likelihood Explanation
Preconditions: (1) attacker must own or control a repository under an org/account for which Shipit's GitHub App/webhook secret already validates (i.e., they must be able to get a legitimately signed webhook delivered to Shipit's endpoint — this is the same precondition needed for any handler, not specific to this bug), and (2) some Shipit-tracked stack must have a `Commit` row whose `sha` matches a SHA the attacker can produce, such as the empty-tree SHA. Given these, the attack is trivially repeatable and requires no credentials beyond having a repo wired to Shipit's webhook delivery, and no brute force since the empty-tree SHA is deterministic. This matches the question's described attacker capability (owns a repo, can emit webhooks from it).

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving `Commit`/records purely by `sha`) to the repository named in the payload, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks`/`repository_name` helper from `Handler`, so that a commit is only updated if it belongs to a stack whose repository matches `payload['repository']['full_name']`.

### Proof of Concept
```ruby
test "status webhook does not update commits belonging to a different repository" do
  stack_a = shipit_stacks(:shipit)
  commit = stack_a.commits.create!(sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904', message: 'empty', author: shipit_users(:walrus))

  payload = {
    'sha' => commit.sha,
    'state' => 'failure',
    'context' => 'attacker-context',
    'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit.reload
  # Binding check: repository named in payload ('attacker-org/unrelated-repo')
  # != repository owning the matched commit (stack_a's repository).
  assert_not_equal 'attacker-org/unrelated-repo', stack_a.repository.full_name
  # Vulnerable behavior: status was still written onto stack_a's commit.
  assert_equal 'failure', commit.statuses.last.state
end
```
This demonstrates that `StatusHandler#process` writes a status onto `stack_a`'s commit despite the webhook payload naming an unrelated repository, confirming the missing repository-scope check.
