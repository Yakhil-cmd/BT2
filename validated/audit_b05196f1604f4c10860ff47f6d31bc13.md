### Title
Unsalted concatenation of `title`/`text`/`creation_date` in prosaic contract hashing allows hash collisions bypassing signature intent - (File: prosaic_contract.js)

### Summary
`prosaic_contract.js` computes the identifying hash of a prosaic (off-chain, "paper") contract by naively concatenating three attacker/peer-controlled dynamic-length strings without any delimiter, exactly the `abi.encodePacked`-style pitfall described in the external report: `keccak256(encodePacked(a,b))` collisions are possible when two or more dynamic-length values are concatenated without a separator, because bytes can be shifted between fields while producing the same digest.

### Finding Description
Both hashing functions used to identify a prosaic contract concatenate `contract.title`, `contract.text`, and `contract.creation_date` directly, with no delimiter or length-prefixing between the fields: [1](#0-0) 

```js
function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}

function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}
```

Both `title` and `text` are free-form, dynamic-length strings supplied by either contracting party (the "offeror" or "acceptor" device) via `createAndSend`/`store`, so a counterparty fully controls their contents: [2](#0-1) [3](#0-2) 

Because there is no separator between `title` and `text`, an attacker can craft two different `(title, text)` pairs whose concatenation is byte-identical — e.g. `title="ab", text="c"` vs `title="a", text="bc"` — while keeping `creation_date` fixed, producing an identical `hash`. This is the same class of bug as the "abi.encodePacked" issue: hashing of multiple dynamic fields without a delimiter or per-field length/type prefix permits content to be shifted across field boundaries and still collide.

By contrast, the codebase elsewhere is aware of this exact class of bug and defends against it: `arbiter_contract.js`'s `getHashSrc` explicitly introduces a `DELIMITER`-joined format for dates after `NEW_HASH_DATE` (though it still falls back to unsafe `.join("")` for legacy dates) [4](#0-3) , and the canonical unit/definition hashing utility `getSourceString` explicitly type-tags and delimits every field with a reserved `STRING_JOIN_CHAR` byte and rejects strings containing that byte, precisely to prevent this collision class [5](#0-4) . `prosaic_contract.js`'s `getHash`/`getHashV1` do not use `getSourceString` and re-introduce the vulnerable pattern.

### Impact Explanation
`hash` is the sole content-identifying value shared between two devices negotiating a prosaic contract (`createAndSend` sends `hash` to the peer, and `getByHash`/`getBySharedAddress` look up contract records solely by this `hash`) [6](#0-5) [7](#0-6) . If a malicious counterparty can construct two distinct `(title, text)` pairs that hash to the same value, they could present one version of the contract text to the counterparty's wallet UI/display while a colliding but different version is what ends up referenced by `contract_text_hash` in the on-chain "data" message used to prove the signing party agreed to specific contract text: [8](#0-7) . This undermines the non-repudiation guarantee of the prosaic-contract signing flow — a party could later claim (or be shown) different contract wording than what is anchored on-chain by the shared hash, since the hash does not uniquely determine `(title, text, creation_date)`.

### Likelihood Explanation
Exploitation requires only that one of the two negotiating peers be malicious and control the `title`/`text` values sent to `createAndSend`/`store`, which is trivially possible since these are plain user-editable strings passed over the wallet's own device-messaging protocol — no privileged network or node role is required, only being a counterparty in a private prosaic contract negotiation. Crafting a colliding pair requires only shifting a shared substring boundary between `title` and `text` (or across `creation_date`, which is a formatted timestamp string), which is straightforward and does not require breaking SHA-256 itself.

### Recommendation
Rewrite `getHash`/`getHashV1` to use a delimiter-based or type-tagged encoding for all fields the same way `string_utils.getSourceString` already does elsewhere in the codebase (which reserves `STRING_JOIN_CHAR` as a separator and rejects it inside field values), e.g.:
```js
function getHash(contract) {
	return objectHash.getBase64Hash([contract.title, contract.text, contract.creation_date]);
}
```
using `objectHash.getBase64Hash`/`getSourceString`, which safely join dynamic fields with an unambiguous, reserved separator, instead of raw `+` concatenation. The same legacy-format fallback issue also exists in `arbiter_contract.js`'s `getHashSrc` for `contract.creation_date <= NEW_HASH_DATE` and should be reviewed, though it is only reachable for old contracts.

### Proof of Concept
1. Party A initiates a prosaic contract offer with `title = "ab"`, `text = "c"`, fixed `creation_date`.
2. `getHash` computes `sha256("ab" + "c" + creation_date)`.
3. Party A separately (or a colluding/impersonating peer) constructs a contract record with `title = "a"`, `text = "bc"`, same `creation_date`.
4. `getHash` computes `sha256("a" + "bc" + creation_date)` — identical to step 2's digest, since string concatenation is associative and no separator distinguishes the field boundary.
5. Both `(title, text)` pairs map to the same `hash`, so a contract lookup/reference by `hash` (`getByHash`, `contract_text_hash` in the signed on-chain data message) cannot distinguish which text was actually agreed upon.
