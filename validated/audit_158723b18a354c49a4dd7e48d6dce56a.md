### Title
Pull-request label names clobber `PATH` (and any other env key) in review-stack task/deploy env, enabling PATH-hijack RCE - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) straight into the task/deploy environment hash with no key allowlist, unlike the deliberate `EnvironmentVariables.permit` allowlist used for API-supplied env vars. Because `Command#unbundled_env` merges the task's `@env` last, a label whose uppercased form is `PATH` overwrites Shipit's safe, hard-coded `PATH` value with the fixed string `"true"`, and since the PR author fully controls the checked-out working directory of their own review stack, they can plant an executable at `<checkout>/true/npm` that gets resolved instead of the real `npm` binary when a `shipit.yml` step runs `npm ci`.

### Finding Description
The broken binding: the invariant should be `env_reaching_PTY_spawn.keys ⊆ deploy_spec.variable_names ∪ Shipit.env.keys ∪ hardcoded_keys`, i.e. every key that reaches `PTY.spawn` must have passed through an explicit allowlist (as enforced by `EnvironmentVariables#permit` at [1](#0-0) , used by `DeploySpec#filter_deploy_envs`/`filter_envs` for user/API-supplied variables at [2](#0-1)  and `app/models/shipit/task_definition.rb` `filter_envs`). Instead, `ReviewStack#env` bypasses that allowlist entirely: [3](#0-2) 

`pull_request.labels` are populated straight from the webhook body with no name restriction, via `LabelCapturingHandler#capture_labels`: [4](#0-3) 

`TaskCommands#env` (used by both tasks and, via `DeployCommands < TaskCommands`, deploys) merges `@stack.env` — which for a `ReviewStack` includes the unfiltered label-derived keys — directly into the final environment hash with no further sanitization: [5](#0-4) 

That hash is passed unchanged into `Command.new(command_line, env:, chdir:)` in `TaskCommands#perform`/`#install_dependencies` (`lib/shipit/task_commands.rb:17-27`), stored as `@env`, and finally merged **last** — after the safe hard-coded `PATH` — in `Command#unbundled_env`: [6](#0-5) 

Root cause: the label name is used verbatim (only uppercased) as an environment-variable key, and no denylist/allowlist filters out reserved/sensitive names like `PATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, `IFS`, etc. The value stored is always the hard-coded string `"true"` (`app/models/shipit/review_stack.rb:91`), not attacker-chosen content, but this does not defeat the exploit: the value is a *known, fixed* string that any attacker who has read the (open-source) engine code can predict. An attacker who labels their own PR with a label whose uppercased name is `PATH` therefore reliably clobbers `Command#unbundled_env`'s `PATH` with the literal value `"true"` — a single relative path segment. Because the deploy/task `chdir` for a review stack is the checked-out working directory of the attacker's own fork branch (fully attacker-controlled content), they can commit an executable at `true/npm` in that branch. When the deploy spec's `npm ci` step is spawned (`Command#start`, `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` at `lib/shipit/command.rb:92`), the OS/shell PATH search resolves the bare command `npm` relative to `PATH="true"` and the process's `chdir`, executing the attacker's planted binary on the Shipit deploy host instead of the real `npm`.

Existing guards do not catch this: `EnvironmentVariables#permit`/`NotPermitted` is never invoked on `ReviewStack#env` or the label-derived hash — it is only applied to explicit user/API-submitted `env` params (see `test/controllers/api/tasks_controller_test.rb:48-53`, `app/controllers/shipit/rollbacks_controller.rb:29-31`). `LabelCapturingHandler`'s `ExplicitParameters` schema only validates types/shape of the webhook payload (`requires :labels, Array do requires :name, String end`), not label name content. There is no repository/model validation restricting label characters, and `Command` itself performs no denylist of reserved environment variable names before merging `@env` over `BASE_ENV`/safe `PATH`.

### Impact Explanation
Any deploy or task step in a review stack's `shipit.yml` that invokes a bare command name (not an absolute path) — `npm ci`, `bundle install`, `make`, etc. — can be hijacked to execute attacker-supplied code on the Shipit deploy host, matching the Critical "RCE on the deploy host via Command/PTY.spawn" category. Because the deploy host is shared infrastructure (it also runs deploys/tasks for other stacks/repositories), an attacker achieving code execution there can pivot to read `GITHUB_TOKEN`s, other stacks' secrets, or manipulate other tenants' deploys — a full blast-radius compromise, not limited to the attacker's own repository. The technique also generalizes beyond `PATH` to any other environment variable name Shipit or the deploy tooling trusts (e.g. `RUBYOPT`, `NODE_OPTIONS`, `BUNDLE_GEMFILE`), widening the attack surface for injection-style RCE.

### Likelihood Explanation
Preconditions: a repository must have review stacks enabled (`repository.review_stacks_enabled`), and the attacker must be able to add a label named `path` (case-insensitive) to their own PR against that repository — trivial if the attacker owns/administers the repository (as the threat model explicitly grants), or possible on any repo where non-collaborators can apply labels. No Shipit session, API token, or webhook secret is required beyond normal GitHub label/PR actions that legitimately trigger the `pull_request` webhook Shipit already processes. The attacker also needs a `shipit.yml` step that runs a bare (non-absolute) command name — a common, unremarkable pattern (`npm ci`, `bundle install`). This is inexpensive and fully repeatable (re-label/re-trigger deploys at will).

### Recommendation
Do not let arbitrary pull-request label names become raw environment-variable keys. Either:
1. Route `ReviewStack#env`'s label-derived hash through `EnvironmentVariables#permit` against an explicit allowlist (as already done for API/task env), or
2. Prefix/namespace label-derived keys (e.g. `LABEL_<NAME>`) so they can never collide with reserved variable names, and additionally reject/strip any label-derived key matching a denylist of security-sensitive names (`PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `RUBYLIB`, `BUNDLE_GEMFILE`, `IFS`, etc.).
3. In `Command#unbundled_env`, make `PATH` (and other sensitive vars) non-overridable by `@env`, i.e. merge order should ensure the safe `PATH` always wins, or explicitly filter `@env` to remove reserved keys before the final merge.

### Proof of Concept
```ruby
# test/unit/command_test.rb (or a new minitest file)
require "test_helper"

module Shipit
  class ReviewStackPathHijackTest < ActiveSupport::TestCase
    test "a pull request label named 'path' overrides PATH reaching the npm ci subprocess" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["path"]

      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env
      assert_equal "true", env["PATH"], "label-derived PATH key reached TaskCommands#env unfiltered"

      command = Shipit::Command.new("npm ci", env:, chdir: task.working_directory)
      resolved_path = command.unbundled_env["PATH"]

      # Binding under test: safe hard-coded PATH (Shipit.shell_paths + ENV['PATH'])
      # should always be what's used to resolve bare commands like `npm`.
      safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
      assert_not_equal safe_path, resolved_path
      assert_equal "true", resolved_path,
        "attacker-controlled label clobbered PATH; a directory named 'true' in the " \
        "checked-out PR branch would now be searched first for `npm`, enabling RCE"
    end
  end
end
```
This demonstrates both sides of the equality: the expected safe `PATH` (`Shipit.shell_paths.join(':') + ':' + ENV['PATH']`) versus the actual value (`"true"`) that reaches `Command#unbundled_env` once a PR is labeled `path`, confirming the fork-controllable env key reaches the `npm ci` subprocess unfiltered.
