### Title
Unauthenticated cross-organization webhook forgery via unsigned `repository.owner.login` selecting a per-org secret that can be blank - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a request against using a field read directly from the **untrusted, not-yet-verified** JSON body, while the actual repository/stack acted upon is resolved from a **different** field in the same body. Combined with `GitHubApp#verify_webhook_signature` returning `true` whenever the selected organization has no `webhook_secret` configured (a state the project explicitly documents and ships as a valid config), an unprivileged attacker can pick an organization slot with no secret to make the app skip signature verification entirely, then point the payload's `repository.full_name` at any other tracked repository/stack (belonging to an organization that *does* have a properly configured secret) to inject forged GitHub events for it.

### Finding Description
The controller derives the "authenticating organization" from the request body before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`repository_owner` is used only to pick which `GitHubApp` config (and thus which `webhook_secret`) to validate the signature against: [3](#0-2) [4](#0-3) 

Critically, if the resolved org's `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — no header, no HMAC check at all. This is not a hardening gap the codebase silently discourages: it is the documented, supported configuration for multi-org installations, and appears in real fixture/config files with `webhook_secret: # nil` for every org: [5](#0-4) [6](#0-5) 

Meanwhile, the actual repository/stack that a webhook event operates on is resolved from a completely separate field of the same untrusted body — `repository.full_name` — independent of `repository.owner.login`: [7](#0-6) 

Because the controller's `repository_owner` (`repository.owner.login`) and the handler's `repository_name` (`repository.full_name`) are read from two independent, attacker-controlled JSON paths in the same forged body, an attacker can set them to different organizations. If they select an org with no `webhook_secret` for `repository.owner.login`, verification is bypassed, while `repository.full_name` can name a repository belonging to a *different*, properly-secured organization whose stacks then process the forged event, e.g. `PushHandler#process` calling `stack.sync_github(expected_head_sha: params.after)` or `StatusHandler` creating a fabricated commit status: [8](#0-7) [9](#0-8) 

This is a direct analog of the report's bug class: a field acted upon (`repository.full_name`, used to select the real target) is never bound to the field the signature/authorization decision is keyed on (`repository.owner.login`), and the "signature" (here, org-selected secret presence) can silently be a no-op — exactly like an unchecked downcast silently overflowing.

### Impact Explanation
This breaks the trust binding "organization that authenticated == repository that is written." An unauthenticated, unprivileged network attacker who knows (a) that the target Shipit instance uses the multi-org config format and (b) the name of any one configured organization slot lacking a `webhook_secret`, can forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `membership`, etc.) targeting stacks belonging to *any other* organization tracked by the same instance. This can trigger `GithubSyncJob`/`sync_github` with attacker-chosen SHAs, fabricate passing CI `status` events used by continuous deployment gating, or manipulate team/membership records — all without ever holding a real GitHub webhook secret, an `ApiClient` token, or a Shipit session. This maps to the Critical bucket: unauthorized deploy/rollback triggering via forged CI/status/push events against a repository the attacker cannot otherwise write to.

### Likelihood Explanation
Requires only knowledge of one organization name configured in the multi-org `github:` block (these are often not secret — companies, subsidiaries, or non-critical orgs are commonly listed as slugs), and requires that at least one configured org uses no webhook secret — a state that is directly supported, documented, and shipped in the repo's own example/test config (`webhook_secret: # nil`). No authentication, session, or valid signature is needed at all for that org. This is a realistic, low-effort attack once instance operators follow the documented multi-org setup pattern for any org without a signing secret.

### Recommendation
- Bind the org used to select the verification secret to the same field used to resolve the target repository (derive both from `repository.full_name`'s owner segment, verified consistently), or verify that `repository.owner.login`/`organization.login` matches the owner portion of `repository.full_name` before trusting either.
- Do not silently pass verification when `webhook_secret` is blank; either require a secret for every configured organization, or fail closed (reject the webhook) rather than fail open when no secret is configured.
- Consider stopping the request pipeline (`return`/`throw`) immediately after `head(422)` in `verify_signature` rather than continuing to log, to avoid any code path relying on `before_action` chain continuing past an invalid signature.

### Proof of Concept
1. Target Shipit instance uses the documented multi-org config: `OrgA` (has `webhook_secret` set) tracks stack `OrgA/critical-repo`; `OrgB` is configured with `webhook_secret` left blank (as shown supported in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker sends, without any valid `X-Hub-Signature` (or an entirely made-up one):
```
POST /webhooks
X-Github-Event: push

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/critical-repo"
  }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgB"`, calls `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) signature header.
4. `WebhooksController#create` dispatches to `PushHandler`, which resolves `repository_name` = `"OrgA/critical-repo"` via `Handler#repository_name`, finds `OrgA/critical-repo`'s stacks, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a forged push event accepted and processed for an organization the attacker never authenticated against and holds no secret for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
