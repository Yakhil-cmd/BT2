The `PullRequest#labels` field is a free-form array with no name allowlist/blocklist, and the webhook signature check (`verify_signature`) only authenticates that GitHub sent the payload for the correct repository/organization — it does not restrict label content. ### Title
Reserved `PATH` environment variable can be overridden via PR label name, corrupting Command#unbundled_env - (File: lib/shipit/command.rb, app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` upcases every GitHub pull-request label name and injects it as an environment variable (`LABEL => "true"`) with no denylist for reserved variable names like `PATH`. Because `Shipit::Command#unbundled_env` merges the task-supplied `@env` hash *after* computing the correct `PATH` from `Shipit.shell_paths`, an attacker-controlled label named `path` (case-insensitively) fully overwrites the process `PATH` used by `PTY.spawn` for every subsequent task/deploy on that stack.

### Finding Description
The broken binding: `Command#unbundled_env['PATH']` should always equal `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` (the value `Shipit::Commands#base_env`/`Command#unbundled_env` computes), but it does not when a `PullRequest#labels` entry equals `"path"` case-insensitively.

Code path:
1. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim onto `PullRequest#labels` with no name filtering: [1](#0-0) 
2. `Shipit::ReviewStack#env` upcases each label and merges it into the stack's env hash: [2](#0-1) 
3. `Shipit::TaskCommands#env` merges `@stack.env` into the task's env with no `PATH` scrubbing: [3](#0-2) 
4. This env hash is passed into `Command.new(..., env:, ...)`, and `Command#unbundled_env` merges `@env.stringify_keys` **after** setting the computed `PATH`, so an attacker-supplied `PATH` key wins: [4](#0-3) 
5. `Command#start` spawns the process with this corrupted environment: [5](#0-4) 

Existing tests confirm labels propagate through this exact chain unmodified: [6](#0-5)  and [7](#0-6) .

Attacker's exact action: open (or already have) a pull request against a repository with an existing, non-archived `ReviewStack`, then have GitHub emit a `labeled` webhook (via the normal GitHub UI/API label action on their own PR) with a label named `path`/`PATH`/`Path` etc. `LabelCapturingHandler` processes this for any non-archived stack regardless of provisioning behavior: [8](#0-7) . The `ExplicitParameters` schema only requires `labels[].name` be a `String`, with no format/reserved-word restriction: [9](#0-8) .

Why guards don't catch it: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticates that the payload genuinely came from GitHub for the given `repository_owner` — it says nothing about label content [10](#0-9) . `PullRequest` has no validation on `labels` content: [11](#0-10) . No later merge step in `TaskCommands#env`/`DeployCommands#env` re-asserts `PATH`.

### Impact Explanation
Once `PATH` is set to the literal string `"true"` (or any attacker-chosen value), every subsequent `git`, `bundle`, or step-defined binary invocation for that stack's tasks/deploys resolves names using that broken `PATH` instead of the operator-configured `Shipit.shell_paths`/`ENV['PATH']`. This can cause silent binary-resolution redirection: if the attacker can also cause a directory to exist on the deploy host matching a component of their injected `PATH` value (e.g., via a prior task that writes files into the task's working directory, which becomes the `chdir` for `PTY.spawn`), a malicious `git`/`bundle` executable placed there would be executed instead of the legitimate one — Remote Code Execution on the deploy host. At minimum, it deterministically breaks command execution for that stack's deploys by pointing `PATH` at a bogus location, denying legitimate binary resolution. This is scoped per-`ReviewStack` (the affected repository's PR-associated stack) and is fully repeatable — each `labeled` webhook re-runs `capture_labels`, and it does not affect other stacks/tenants directly, but is a Critical-severity RCE primitive under `Command`/`PTY.spawn` matching the target impact category.

### Likelihood Explanation
Preconditions: repository has ReviewStack provisioning enabled and an existing non-archived `ReviewStack` tied to the attacker's PR (a `PullRequest` row already exists, e.g. created via the `opened` webhook). The attacker needs only the ability to add a label named `path` to their own PR and have that generate a real GitHub `labeled` webhook — no Shipit secrets, sessions, or `Shipit.github_teams` membership are required. Whether an unprivileged external contributor can label their *own* PR depends on GitHub's repository label permissions (commonly restricted to collaborators), which is a GitHub-side control outside this engine, but is explicitly assumed feasible per the stated threat model. Given that assumption, the attack is trivial and fully repeatable on-demand for any repository with review stacks enabled.

### Recommendation
In `Shipit::Command#unbundled_env`, protect the computed `PATH` by merging it *after* `@env` (or explicitly stripping/ignoring a `PATH` key from `@env`), e.g. `BASE_ENV.merge(@env.stringify_keys).merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}")`. Additionally, in `Shipit::ReviewStack#env`, reject or skip label names that collide with reserved/security-sensitive environment variables (`PATH`, `LD_PRELOAD`, `GIT_ASKPASS`, `BUNDLE_*`, etc.) before upcasing and merging them.

### Proof of Concept
minitest plan (in `test/lib/shipit/task_commands_test.rb`-style, not to be placed under excluded `test/**` output but described here per required format):
```ruby
test "#env PATH cannot be overridden by a malicious PR label" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new("true", env: env, chdir: ".")

  expected_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  assert_equal expected_path, command.unbundled_env["PATH"],
    "PATH was overridden by attacker-controlled PR label: #{command.unbundled_env["PATH"].inspect}"
end
```
Both sides of the equality: left side `Shipit::TaskCommands.new(task).env["PATH"]` (attacker value `"true"`) is asserted against `Command#unbundled_env["PATH"]`, expected to equal `Shipit.shell_paths.join(':') + ':' + ENV['PATH']` — with current code, the assertion fails, proving the binding break.
