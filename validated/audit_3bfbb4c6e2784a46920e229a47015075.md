### Title
Unbounded loop over globally-shared `storage.assocUnstableMessages` in `data_feed`/`in_data_feed` AA formula evaluation causes DoS scaling with network-wide unconfirmed activity - (File: data_feeds.js)

### Summary
`dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js` scan the entire `storage.assocUnstableMessages` object with an unbounded `for (var unit in storage.assocUnstableMessages)` loop whenever an AA reads a data feed with unstable-data support enabled. This map accumulates a `data_feed`/`definition`/`system_vote`/`system_vote_count` message for **every** currently-unstable unit posted by **any** address on the network, and only shrinks when the corresponding MCI stabilizes. Any unprivileged unit poster can grow this map arbitrarily by posting many cheap `data_feed` messages that remain unstable, and any AA trigger sender can then force expensive per-trigger iteration over that entire accumulated set.

### Finding Description
`assocUnstableMessages[unit]` is populated for every unit containing a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message at write time [1](#0-0) , and is only removed for a specific unit once that unit's MCI is marked stable [2](#0-1) . Because stabilization requires the whole main-chain to advance past that unit (not a fixed amount of work per-unit), the size of this map is proportional to the number of currently-unconfirmed `data_feed`-bearing units across the *entire* DAG, not just units related to the calling AA.

`dataFeedExists()` iterates this whole structure unconditionally when `bAA` is true, before falling back to a bounded per-address DB lookup: [7](#0-6) 

`readDataFeedValue()` performs the same unbounded scan for `data_feed()` value lookups: [4](#0-3) 

Both entry points are reached from ordinary AA formula operators `data_feed` and `in_data_feed`, which any AA definition can use and any user can trigger by sending a payment/trigger to that AA: [8](#0-7) [6](#0-5) 

Unlike the `foreach`/`map`/`filter`/`reduce` formula operators, which are explicitly bounded by an evaluator-supplied `count` argument checked against `arrElements.length` (`formula/validation.js` lines 1005-1041, `formula/evaluation.js` lines 2345-2373), and unlike `evaluate()` in `definition.js`/`aa_validation.js` which increments `complexity`/`count_ops` per recursive call and enforces `MAX_COMPLEXITY`/`MAX_OPS`, the `data_feed`/`in_data_feed` cost model charges only a fixed, constant complexity regardless of how large `storage.assocUnstableMessages` has grown. The cost of the operation is decoupled from any per-transaction size or fee paid by the caller of `data_feed()`, and instead depends on cumulative, unrelated network activity from arbitrary other unprivileged unit posters.

### Impact Explanation
An attacker can post a large number of low-fee units each containing a small `data_feed` message from many addresses, keeping them unconfirmed by continuing to post more units faster than stabilization can catch up, or targeting periods of low witness activity. Any AA that calls `data_feed()`/`in_data_feed()` (a very common oracle-consumption pattern) then pays CPU cost proportional to the total number of unstable `data_feed`-bearing units network-wide on every trigger, not just its own related activity. As this list grows, formula evaluation for that AA (and every other AA using data feeds) slows down, potentially causing trigger processing (`handleTrigger()` in `aa_composer.js`) to take excessively long or effectively stall unit/AA-response processing for the node, which can delay or block the release of funds sent into AAs that depend on `data_feed` results — matching the "unbound loop causing high gas usage, breaking the protocol, and locking funds" pattern from the reference report, adapted to ocore's AA/oscript execution model.

### Likelihood Explanation
Reachable by any unprivileged unit poster: no special permissions are needed to post `data_feed` messages, and any user can send a trigger to any AA using `data_feed()`/`in_data_feed()`. The cost of building up `assocUnstableMessages` scales with network-wide unstable unit count, which an attacker directly influences by repeatedly posting cheap `data_feed` messages, especially effective if timed against slow stabilization (e.g., low witness-list liveness periods).

### Recommendation
Bound the iteration cost of the `bAA`/unstable-message code paths in `dataFeedExists()`/`readDataFeedValue()`, e.g. by indexing `assocUnstableMessages` by feed name/oracle address rather than scanning the full map, or by capping the number of unstable entries scanned and falling back to the DB-backed lookup once a threshold is exceeded. Alternatively, charge formula complexity/ops proportional to the current size of `storage.assocUnstableMessages` (similar to how `foreach`/`map`/`filter`/`reduce` charge `count * complexity`), so that AAs relying on this data cannot be forced into disproportionate CPU cost by unrelated network activity.

### Proof of Concept
1. Attacker repeatedly posts many independent units (from many disposable addresses) each containing a `data_feed` message, faster than main-chain stability can confirm them, so they accumulate in `storage.assocUnstableMessages` (populated per `writer.js` lines 603-613).
2. Victim (or attacker) triggers any deployed AA whose oscript uses `data_feed(...)` or `in_data_feed(...)`.
3. `formula/evaluation.js`'s `data_feed`/`in_data_feed` cases call into `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists` with `bAA=true`.
4. Those functions execute the `for (var unit in storage.assocUnstableMessages)` loop over the entire accumulated map (`data_feeds.js` lines 34-94, 211-241), with per-iteration work (property lookups, `_.intersection`, `forEach` over messages) proportional to the number of unconfirmed `data_feed` units network-wide, none of which were posted by the AA's trigger sender or paid for by this particular trigger.
