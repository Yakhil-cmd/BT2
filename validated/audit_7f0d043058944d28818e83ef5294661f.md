### Title
Cross-organization webhook forgery via organization/repository binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to verify a webhook's HMAC signature against by reading an attacker-controlled field (`repository.owner.login`, or falling back to `organization.login`) out of the same unauthenticated JSON body that the event handlers later use to locate the target `Stack`/`Commit` by `repository.full_name`. Nothing binds the organization whose secret validated the signature to the repository the handlers actually act on, so a party who legitimately administers a webhook for one GitHub organization (and therefore knows that organization's `webhook_secret`) can forge a signed payload that names a *different* organization's repository in `full_name`, and Shipit will accept it as authentic.

### Finding Description
The signature check is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read straight out of the unverified `request.raw_post` JSON, before the signature has been checked. It is then used purely to pick *which* organization's `webhook_secret` to HMAC-verify the raw body against, via `GitHubApp#verify_webhook_signature`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

The subsequent handlers (e.g. the `push`/`status` handlers exercised in `test/controllers/webhooks_controller_test.rb`) locate the `Stack`/`Commit` to mutate using the repository identity embedded in the same payload (`repository.full_name`/owner+name), independently of `repository_owner`: [3](#0-2) 

Because the field used to select the verifying secret (`repository.owner.login`) is never checked for consistency against the field used to select the write target (`repository.full_name`), the binding "organization that authenticated" == "repository that is written" is never enforced. An attacker who legitimately controls the webhook configuration for Organization A (and thus knows Org A's `webhook_secret`, since Shipit's webhook secret is simply the shared secret configured on both the GitHub webhook and in Shipit for that org) can craft a raw JSON body whose `repository.owner.login` is `"OrgA"` (so Shipit selects Org A's secret to verify) but whose `repository.full_name`/commit data references `"OrgB/victim-repo"`. Signing that exact body with Org A's known secret produces a signature that passes `verify_signature`, and the handler then acts on Org B's stack using the (otherwise unauthenticated-for-Org-B) payload contents.

### Impact Explanation
This breaks a credential/organization authorization boundary: knowledge of one organization's webhook secret should only authorize writes about that organization's repositories, not arbitrary others. Exploiting it lets an attacker inject forged GitHub events (commit `status`, `check_suite`, `push`-triggered sync, `pull_request` label/merge state, etc.) against a target stack belonging to an organization the attacker does not control, which can manipulate CI status gating, trigger unintended `GithubSyncJob`/merge processing, or otherwise influence deploy/merge state for a repository they have no legitimate access to — an unauthorized cross-repository write through the engine's own webhook trust boundary.

### Likelihood Explanation
Requires the attacker to legitimately administer at least one GitHub organization/repository already integrated with the same Shipit instance (so they know that org's configured `webhook_secret`), and knowledge that other organizations are also configured on the same instance — a realistic scenario for any multi-tenant/multi-org Shipit deployment, with no need for a Shipit session, API token, or the target org's secret.

### Recommendation
After verifying the HMAC signature, re-derive `repository_owner` (or the full repository identity) strictly from the fields actually used by the event handlers, and reject the request if the organization whose secret validated the signature does not match the organization owning the repository the payload claims to describe. Do not let handlers trust `repository.full_name` from a payload verified only against a secret keyed by a separate, attacker-suppliable `repository.owner.login` field.

### Proof of Concept
1. Attacker administers a repository under `OrgA`, which is configured in this Shipit instance with `webhook_secret = SECRET_A`.
2. Attacker crafts a raw JSON body for, e.g., a `status` event:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Attacker computes `sha1=HMAC-SHA1(SECRET_A, body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature using `SECRET_A` — even though the payload's actual target (`OrgB/victim-repo`) belongs to a different, unrelated organization.
5. The `status` handler processes the payload against `OrgB`'s stack/commit, using data the attacker fully controls, e.g., marking an arbitrary victim commit as `success`/passing CI without ever knowing `OrgB`'s secret.
