### Title
Webhook signature verified against `repository.owner.login`'s secret but handlers act on the independently-supplied `repository.full_name` field, allowing cross-organization stack sync/deploy triggers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook delivery against using only `repository.owner.login` (or `organization.login`) from the payload. Event handlers, however, resolve the `Shipit::Repository`/`Stack` to act on using the independent `repository.full_name` field of the same payload. Because both fields live in the same attacker-controlled JSON body, and the signature check does not bind the `owner.login` used for secret-selection to the `full_name` used for repository resolution beyond "some HMAC validates," anyone who can produce a validly-signed webhook for one organization onboarded on this Shipit instance can set `repository.full_name` to point at a stack belonging to a *different* organization/repository also onboarded on the same instance, causing Shipit to sync and potentially auto-deploy that unrelated stack.

### Finding Description
`repository_owner` is computed purely from the payload, not from any authenticated GitHub App context: [1](#0-0) 

This value is used only to pick which configured GitHub App/org's `webhook_secret` should validate the HMAC signature: [2](#0-1) 

Once the signature is accepted, the raw JSON `params` is dispatched unmodified to the registered handlers for the event: [3](#0-2) 

The base `Handler` class, and concrete handlers like `PushHandler`, resolve the target `Repository`/`Stack` from a *different* payload field — `repository.full_name` — not from `repository.owner.login`: [4](#0-3) [5](#0-4) 

The HMAC only proves "this body was signed with the secret belonging to whatever org I chose in `repository_owner`" — it does not prove that `repository.full_name` (the value actually used to look up the target `Stack`) belongs to that same organization. Any party who legitimately controls a GitHub App installation/webhook secret for *one* organization tracked by this Shipit instance (e.g. `OrgA`, which they administer) can hand-craft a webhook body where `repository.owner.login = "OrgA"` (so the correct secret is selected and the HMAC validates) but `repository.full_name = "OrgB/other-repo"` (a completely different, unrelated stack also tracked by the same Shipit instance). The signature check passes, and `PushHandler#process` (confirmed by `test/controllers/webhooks_controller_test.rb`'s `GithubSyncJob` assertion) enqueues a sync against `OrgB/other-repo` with an attacker-chosen `expected_head_sha`: [6](#0-5) 

If that stack has `continuous_deployment` enabled, this forged sync can drive an unauthorized deploy of an arbitrary attacker-chosen commit SHA on a repository/organization the attacker does not administer and for which they hold no webhook secret.

### Impact Explanation
This breaks the trust binding "organization that authenticated versus the repository that is written": the webhook signature only authenticates the organization used to select the secret, not the repository the payload subsequently causes Shipit to act on. The result is an unauthorized cross-organization sync/deploy trigger — matching the Critical-severity "unauthorized deploy" / "cross-repository writes" category.

### Likelihood Explanation
Any entity that operates or administers a GitHub organization/App installation already onboarded to a given Shipit instance (a normal, unprivileged position relative to *other* repositories tracked by the same instance) can trivially forge the `repository.full_name` field, since it is never cross-checked against the org whose secret validated the signature. No GitHub write access to the victim repository, no Shipit session, and no API token are required.

### Recommendation
After signature verification succeeds, re-derive/validate the organization from the same field that handlers use to resolve the target repository (`repository.full_name`'s owner segment), and reject the webhook if it doesn't match the organization (`repository.owner.login`/`organization.login`) whose secret validated the signature. Concretely, in `WebhooksController#verify_signature`, assert that `params.dig('repository','full_name')&.split('/')&.first` equals `repository_owner` before accepting the payload, instead of relying solely on HMAC success.

### Proof of Concept
1. Onboard/administer `OrgA` on the shared Shipit instance and note its GitHub App `webhook_secret` (available to anyone administering that org's App installation).
2. Craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` using `sha1=HMAC-SHA1(webhook_secret, body)` and set it as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` selects `OrgA`'s secret (via `repository_owner` = `"OrgA"`), the signature validates, and `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` with the attacker-chosen `expected_head_sha`, despite the attacker having no credentials for `OrgB`.
