### Title
Textcoin spending mnemonic (private key material) is written to console/log output in clear text - ([File: wallet.js])

### Summary
`claimBackOldTextcoins()` in `wallet.js` logs the full plaintext mnemonic of a textcoin (a self-contained spendable address whose mnemonic *is* the private key) both on success and on failure, mirroring the FreshRSS bug class where secret credentials are printed to a persisted log file on an authentication/claim failure path.

### Finding Description
Textcoins are created by `sendMultiPayment()`/`generateNewMnemonicIfNoAddress()`, which derives a brand-new address from a randomly generated mnemonic and stores that mnemonic in the `sent_mnemonics` table so the coin can later be claimed by whoever holds the mnemonic string [1](#0-0) . The corresponding private key is deterministically derived straight from the mnemonic in `expandMnemonic()`, and that private key is used to sign spends without any additional secret [2](#0-1) .

`claimBackOldTextcoins()` runs periodically (any unclaimed textcoin older than N days is reclaimed) and for every row it processes it prints the *entire mnemonic in clear text* to `console.log`, once on the error path and once on the success path: [3](#0-2) 

Because `console.log` output in ocore-based wallets/hubs is routinely captured to persistent log files (and, in many deployments, forwarded to system logs or crash-reporting), any actor who can read those logs recovers a mnemonic that is directly convertible into a spending private key via `expandMnemonic()` → `receiveTextCoin()` [4](#0-3) . This is functionally identical to the FreshRSS issue: a value that is treated as a bearer secret (there, the API password; here, the textcoin mnemonic/private key) is unconditionally written into logs on both the success and the failure branches of a claim/authorization function (`unauthorized()`/`badRequest()` there, the `ifError`/`ifOk` callbacks of `receiveTextCoin` here).

### Impact Explanation
Anyone with read access to the wallet/hub's logs (support staff, log-aggregation pipelines, crash reporters, misconfigured log-sharing, backup archives, etc.) obtains the plaintext mnemonic for any textcoin that goes through the reclaim path. That mnemonic is not a low-value token — it is the entire spending credential for the derived address (`objectHash.getChash160(["sig", {"pubkey": pubkey}])`), so its disclosure enables **unauthorized spending** of funds sitting at the textcoin address, exactly the kind of concrete fund-loss impact required. If the reclaim races with the intended recipient, this can also enable draining coins the legitimate recipient has not yet claimed.

### Likelihood Explanation
`claimBackOldTextcoins()` is a built-in wallet maintenance routine (no privileged actor required to trigger the underlying textcoin creation/expiry flow — any user creating textcoin outputs via a normal payment reaches this code path over time), and `console.log` sinks are the default logging mechanism throughout `ocore`, making accidental disclosure via saved stdout/stderr, PM2/systemd journals, or shared debug logs realistic and low-effort to exploit once log access is obtained.

### Recommendation
Never log the mnemonic (or any other secret/private-key-equivalent) in clear text. Replace both `console.log` statements in `claimBackOldTextcoins()` with references to the derived public address (e.g., `addrInfo.address`) or a redacted/hashed identifier, and audit other locations that log `mnemonic`, `priv`, `xPrivKey`, or `privKey` values for the same issue (e.g., other debug-only `console.log` calls in `device.js` handling private key material) to ensure they are removed or gated behind a non-persistent debug flag.

### Proof of Concept
1. Attacker (any wallet user) sends a payment with a `textcoin:` output; `generateNewMnemonicIfNoAddress()` creates and stores a mnemonic-based address in `sent_mnemonics` [5](#0-4) .
2. If the textcoin is not claimed within the configured number of days, the periodic job invokes `claimBackOldTextcoins(to_address, days)`.
3. For each unclaimed row, `receiveTextCoin(row.mnemonic, to_address, cb)` is called and the callback logs `row.mnemonic` in full, regardless of success or failure [6](#0-5) .
4. Any party who later reads the persisted log (support ticket, shared debug log, log aggregation system) extracts the mnemonic and calls `expandMnemonic(mnemonic)` themselves to derive `xPrivKey`/`address`, then constructs and signs a spend from that address using the same derivation logic as `receiveTextCoin` [7](#0-6) , taking any remaining balance before the legitimate recipient does.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}

// if a textcoin was not claimed for 'days' days, claims it back
function claimBackOldTextcoins(to_address, days){
	if (typeof days !== 'number')
		throw Error("bad days: " + days);
	db.query(
		"SELECT mnemonic FROM sent_mnemonics LEFT JOIN unit_authors USING(address) \n\
		WHERE mnemonic!='' AND unit_authors.address IS NULL AND creation_date<"+db.addTime("-"+days+" DAY"),
		function(rows){
			async.eachSeries(
				rows,
				function(row, cb){
					receiveTextCoin(row.mnemonic, to_address, function(err, unit, asset){
						if (err)
							console.log("failed claiming back old textcoin "+row.mnemonic+": "+err);
						else
							console.log("claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset);
						cb();
					});
				}
			);
		}
	);
}
