### Title
Webhook HMAC verifier selection is decoupled from the repository used for handler dispatch, enabling cross-tenant `push` forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#repository_owner` selects which `GitHubApp` (and thus which HMAC secret) verifies a webhook using `repository.owner.login` with a fallback to `organization.login`, while `Handler#stacks`/`#repository_name` independently reads `repository.full_name` to decide which `Repository`/`Stack` the payload affects. Because these two lookups are never cross-checked, an attacker who knows (or can probe for) any org on a multi-org Shipit instance configured without a `webhook_secret` can select that org's always-pass verifier while pointing the actual `repository.full_name` at a completely different, properly-secured victim org/repo.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == owner(repository.full_name)`, but nothing enforces `params.dig('repository','owner','login') || params.dig('organization','login')` to equal the owner segment of `payload.dig('repository','full_name')`.

- `repository_owner` in `app/controllers/shipit/webhooks_controller.rb:59-62` reads `repository.owner.login`, falling back to `organization.login` only when the former is absent from the payload.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) calls `Shipit.github(organization: repository_owner)` and then `verify_webhook_signature`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` — i.e., any org configured without a `webhook_secret` accepts arbitrary/forged signatures.
- `Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) independently derives the affected repository from `payload.dig('repository', 'full_name')`, with no reference back to `repository_owner`.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) then syncs every non-archived stack of that repository matching `branch`, calling `stack.sync_github(expected_head_sha: params.after)`.

Exploit request: a `POST /webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "full_name": "victim-org/victim-repo" },
  "organization": { "login": "attacker-org" }
}
```
Here `repository.owner.login` is deliberately omitted so `repository_owner` falls back to `organization.login` = `"attacker-org"`. If `attacker-org` is configured on this Shipit instance without a `webhook_secret` (multi-org schema, `lib/shipit.rb:170-200`), signature verification trivially passes regardless of the `X-Hub-Signature` header. The handler then dispatches on `repository.full_name = "victim-org/victim-repo"`, which is unrelated to `attacker-org` and may have its own, properly-configured `webhook_secret`. This lets the attacker drive `sync_github` against the victim's stacks without ever presenting a valid signature for the victim's org.

No existing guard prevents this: `drop_unhandled_event` and `ExplicitParameters` only validate presence of `ref`/`after`, not owner consistency; there is no check anywhere that the org used to select the verifier matches the owner of `repository.full_name`.

### Impact Explanation
An attacker can forge `push` webhooks for any repository/stack hosted on a Shipit instance, provided the instance is running the multi-org GitHub App schema and at least one configured org lacks a `webhook_secret`, regardless of whether the victim org's own secret is properly set. This is a cross-tenant authentication bypass: "a payload for one repository mutating another's stack" — matching the Critical impact category. `sync_github` can append commits and, depending on stack configuration (continuous deployment), drive an unauthorized deploy pipeline forward. The blast radius spans every stack/repo hosted on the same Shipit instance, not just the misconfigured org's own repos.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-organization GitHub App schema (`github: {org1: {...}, org2: {...}}`), and (2) at least one configured org lacking `webhook_secret`. Given these preconditions, exploitation costs a single unauthenticated HTTP POST with a crafted JSON body and no valid signature — fully repeatable against any repository hosted on the instance. The preconditions are plausible in real multi-tenant deployments (e.g., a newly onboarded org before its secret is set), and the question's threat model explicitly stipulates "org configured without webhook_secret" as a given condition.

### Recommendation
Bind webhook signature verification to the exact repository the handler will act on, not to an independently-controlled `organization`/`owner` field:
- Compute the org used for HMAC selection strictly from `repository.full_name`'s owner segment (or require `repository.owner.login` and reject payloads missing it for repository-scoped events like `push`), rather than falling back to a separate `organization.login` field for events carrying a `repository`.
- After selecting the verifier, assert that the resolved organization matches the owner of `repository.full_name` before dispatching to handlers; reject (422) on mismatch.
- Consider disallowing `webhook_secret`-less orgs from being usable to authenticate events referencing repositories owned by a different, secret-protected org.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, under an `organization fallback selection` context):
```ruby
test "push forged via org without webhook_secret cannot mutate a different org's stack" do
  # Setup: multi-org secrets with 'attacker-org' (no webhook_secret) and 'shopify' (webhook_secret set)
  # victim stack belongs to shopify/shipit-engine

  payload = {
    ref: 'refs/heads/master',
    after: 'f' * 40,
    repository: { full_name: 'shopify/shipit-engine' }, # no owner.login key
    organization: { login: 'attacker-org' }
  }.to_json

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = 'sha1=bogus'

  # Binding under test:
  # repository_owner == 'attacker-org' (from organization.login fallback)
  # repository.full_name owner == 'shopify' (different value)
  assert_no_enqueued_jobs do
    Shipit::Stack.any_instance.expects(:sync_github).never
    post :create, body: payload, as: :json
  end
  assert_response :unprocessable_entity # expected fix: should be rejected
end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
