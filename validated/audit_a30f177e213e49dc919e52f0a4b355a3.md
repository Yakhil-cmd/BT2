### Title
Pull request labels are merged unfiltered into the git subprocess environment, allowing `GIT_PROXY_COMMAND` injection via `ReviewStack#env` - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` takes every label attached to the associated pull request, upcases it, and merges it directly into the stack's environment hash with no key allowlist or denylist. This environment is merged all the way down into `Command#unbundled_env`, which is passed unmodified to `PTY.spawn` for every git subprocess the engine runs on behalf of that stack, including the `git fetch origin` calls in `StackCommands#fetch`/`#fetch_commit`.

### Finding Description
The broken binding: `stack.env["GIT_PROXY_COMMAND"]` should always equal `nil` (or a Shipit-operator-provided value) for any git subprocess Shipit spawns, but it actually equals whatever string a pull-request label named `git_proxy_command` (case-insensitive) sets it to.

Code path:
1. `Shipit::PullRequest#github_pull_request=` stores `github_pull_request.labels.map(&:name)` verbatim as `pull_request.labels` [1](#0-0)  and `LabelCapturingHandler#capture_labels` re-persists label names straight from the webhook payload on `opened`/`labeled`/`unlabeled`/`reopened` events for non-archived stacks, with no validation of the label content [2](#0-1) .
2. `ReviewStack#env` merges every label name (upcased) as an env key with the string `"true"` as value, with no allowlist of accepted keys: `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` [3](#0-2) .
3. `StackCommands#env` merges `@stack.env` into the base env used for `fetch`/`fetch_commit`, both of which run `git('fetch', 'origin', ..., env:, chdir: @stack.git_path)` [4](#0-3) . `TaskCommands#env` also merges `@stack.env` for every deploy/task step [5](#0-4) .
4. `Command#unbundled_env` merges the caller-supplied `@env` on top of `BASE_ENV`/`PATH` with no filtering of dangerous keys, and `Command#start` passes this hash directly to `PTY.spawn` [6](#0-5) .

The engine's own tests confirm this data flow is unfiltered by design: `test/models/shipit/review_stack_test.rb` asserts `stack.env["WIP"] == "true"` after setting `pull_request.labels = ["wip", "bug"]` [7](#0-6) , and `test/lib/shipit/task_commands_test.rb` shows the same labels reaching `Shipit::TaskCommands#env` [8](#0-7) . No allowlist/denylist mechanism (`EnvironmentVariables#permit`, or similar) filters these label-derived keys before they reach `Command`/`PTY.spawn`; `EnvironmentVariables` (`lib/shipit/environment_variables.rb`) only implements variable interpolation for command-line arguments, not env-key filtering for spawned processes.

### Impact Explanation
If a label named (case-insensitively) `git_proxy_command`, `git_ssh_command`, `git_ssh`, `bundle_gemfile`, `ld_preload`, etc. is attached to a pull request tracked by a Shipit `ReviewStack`, that string becomes an environment variable inherited by every `git` subprocess run for that stack — including the engine-driven `git fetch origin` in `StackCommands#fetch`/`#fetch_commit` — and by every task/deploy step in `TaskCommands#perform`. `GIT_PROXY_COMMAND` in particular is a git-honored variable that names an arbitrary program git executes to establish transport connections, giving Remote Code Execution on the Shipit deploy host under the Shipit process's privileges. This matches the Critical RCE-on-deploy-host impact category.

### Likelihood Explanation
Exploitation requires: (a) a repository with Review Stacks enabled (`repository.review_stacks_enabled`) and a provisioning behavior (e.g. `allow_all`) that creates a stack from an unprivileged pull request, and (b) the attacker being able to attach a label with the target name to that pull request. GitHub's own permission model normally restricts adding labels to users with triage/write access on the target repository, which limits this to attackers who are already collaborators, or to attackers targeting their own repositories/forks where `review_stacks_enabled` is configured. Within scope of the engine's own code, once a label is present, the flow to the spawned git process is deterministic and unconditional — there is no additional application-level gate protecting `GIT_PROXY_COMMAND`-class keys once a label of that name exists on the tracked pull request.

### Recommendation
In `ReviewStack#env`, restrict label-derived environment keys to a safe allowlist (e.g. a configurable prefix such as `SHIPIT_LABEL_*`), or reject/strip label names that collide with known-dangerous environment variables (`GIT_*`, `LD_PRELOAD`, `BUNDLE_*`, `PATH`, etc.) before merging. Additionally, `Command#unbundled_env` should apply a final denylist/allowlist pass over `@env` regardless of caller, so that no caller-supplied environment key can silently override transport- or loader-affecting variables for spawned git/shell processes.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extension)
test "#env allows dangerous git env vars to be set via pull request labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_proxy_command"]

  assert_equal "true", stack.env["GIT_PROXY_COMMAND"]
end

# test/lib/shipit/task_commands_test.rb (extension)
test "#env leaks GIT_PROXY_COMMAND label into git fetch env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_proxy_command"]

  cmd = Shipit::StackCommands.new(stack).fetch
  assert_equal "true", cmd.unbundled_env["GIT_PROXY_COMMAND"]
end
```
Both assertions succeed against current code, proving `GIT_PROXY_COMMAND` (or any other dangerous git/env variable name) reaches the `git fetch origin` subprocess's environment unfiltered, sourced entirely from attacker-controllable pull request label names captured via [2](#0-1)  and merged via [3](#0-2) .
