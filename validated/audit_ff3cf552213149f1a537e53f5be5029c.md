### Title
Unbounded recursive chain-walk in `readAllControlAddresses` allows a malicious cosigner to hang shared-address wallet operations - (File: wallet_defined_by_addresses.js)

### Summary
`readAllControlAddresses` in `wallet_defined_by_addresses.js` recursively expands "control addresses" of a shared address by repeatedly querying `shared_address_signing_paths` and recursing on every newly discovered member address, with no depth limit, no visited-set/cycle check, and no cap on the number of hops. [1](#0-0) 

This mirrors the Routinator bug class (CWE-674/835): a party who controls what gets published into the "chain" (there, RRDP repository redirections; here, nested shared-address definitions accepted via `handleNewSharedAddress`) can make the chain-walk never terminate, because the walking code enforces no limit on chain length.

### Finding Description
A shared (multi-sig) address is defined by an `["and"/"or"/... , [["address", "MEMBER_ADDR"], ...]]`-style definition, and its member addresses are recorded in `shared_address_signing_paths` when a peer sends the wallet a `new_shared_address` (or `create_new_shared_address`) device message, handled by `handleNewSharedAddress`. [2](#0-1) 

Validation of the incoming definition is performed by `validateAddressDefinition`, which calls `Definition.validateDefinition` with `bAllowUnresolvedInnerDefinitions: true` and a fake unit — it does not attempt to walk existing `shared_address_signing_paths` rows, so it cannot detect that the address being created participates in (or completes) a cycle with a previously accepted shared address. [3](#0-2) 

Once two (or more) shared addresses reference each other as member addresses (e.g. shared address A's definition lists member address B, and shared address B's definition lists member address A — each accepted in a separate, individually-valid `new_shared_address` message from a paired malicious device), `readAllControlAddresses(conn, [A], cb)` will:
1. Query `shared_address_signing_paths` for members of A → returns B.
2. Recurse with `[B]`.
3. Query for members of B → returns A.
4. Recurse with `[A]` again — indefinitely. [1](#0-0) 

The callback `handleLists` is never invoked because the recursive DB round-trips never converge, so any caller awaiting the result of `readAllControlAddresses` stalls indefinitely (an asynchronous, DB-query-driven infinite loop, analogous to Routinator's unbounded chain-following that never lets the validation run finish).

### Impact Explanation
`readAllControlAddresses` is exported (`exports.readAllControlAddresses`) and used to resolve which addresses/devices control funds of a shared address for wallet operations such as forwarding of private-payment chains and determining who to notify/query about a shared address's balance. If invoked, the calling routine — and any mutex/lock it holds while waiting — never completes. This can wedge wallet functionality (e.g. private-payment forwarding, balance/cosigner discovery) tied to that shared address, denying the honest user timely wallet operation once they accept the malicious device's shared-address messages. It does not directly cause fund loss but is a legitimate node-freezing/DoS analog reachable purely by a paired device sending crafted (individually valid) shared-address definitions.

### Likelihood Explanation
Reachable by any correspondent/paired device that a user has approved chatting with, by sending two ordinary `new_shared_address` messages that reference each other as members — no privileged network position, no protocol violation in either individual message, and no cycle detection exists anywhere in the acceptance path (`handleNewSharedAddress` → `addNewSharedAddress`) or in the consuming function (`readAllControlAddresses`). The main mitigating factor is that this code lives in the wallet-side device-message handling rather than in core unit/AA/DAG validation, and requires the victim to have paired with the attacker's device and to trigger a code path that calls `readAllControlAddresses` for the affected shared address.

### Recommendation
- Add cycle/visited-set tracking (e.g. a `Set` of already-seen addresses) in `readAllControlAddresses`, skipping addresses already visited instead of unconditionally recursing.
- Add a hard maximum recursion depth (similar to `MAX_DEPTH` used elsewhere in `aa_validation.js`) and fail closed once exceeded.
- Optionally, reject shared-address definitions in `handleNewSharedAddress`/`addNewSharedAddress` whose member addresses would introduce a cycle with already-known shared addresses before persisting them to `shared_address_signing_paths`.

### Proof of Concept
1. Attacker pairs with victim's wallet as a correspondent device.
2. Attacker sends `new_shared_address` message defining shared address `A` with definition `["address", "B"]` (or wrapped in `and`/`or`) where `B` is another to-be-created shared address; this is accepted by `handleNewSharedAddress`/`addNewSharedAddress` since it individually validates fine (`bAllowUnresolvedInnerDefinitions: true`).
3. Attacker sends a second `new_shared_address` message defining shared address `B` with definition `["address", "A"]`, again individually valid.
4. Both rows are stored in `shared_address_signing_paths` — a cycle A→B→A now exists.
5. Any subsequent call to `readAllControlAddresses(conn, ["A"], cb)` (e.g. triggered by wallet logic needing the full list of controlling addresses for A) recurses forever between `[A]` and `[B]`, and `cb`/`handleLists` is never invoked, hanging the calling flow and any associated locks.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
