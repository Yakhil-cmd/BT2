## Analysis

CVE-2019-10222 is a Ceph RGW/Beast **remote denial-of-service**: an unauthenticated client sends syntactically valid data, and an edge case in server-side processing throws an unhandled fault that crashes the whole daemon rather than just failing the one request. The reachable analog in `ocore` is an unguarded `throw Error(...)` deep inside the private-payment double-spend resolution path of `validation.js`, which propagates out of the async callback chain as an uncaught exception and is deliberately turned into a full process crash by the global handler in `network.js`.

### Title
Unhandled exception in private-asset double-spend resolution crashes the node process - (File: `validation.js`)

### Summary
`validatePaymentInputsAndOutputs()` calls `checkInputDoubleSpend()` for every payment input, which in turn calls `checkForDoublespends()`. For private assets, the `onDone` callback unconditionally `throw`s if the double-spend graph check fails to resolve the conflict, instead of passing the error back through the normal callback chain.

### Finding Description
When validating a payment input for a private asset, `checkInputDoubleSpend` runs `checkForDoublespends`, whose `onDone` callback is: [1](#0-0) 

Inside `checkForDoublespends`, once conflicting rows are found, the resolution logic itself can also `throw` for cases it treats as "should not happen": [2](#0-1) 

These calls occur several levels deep inside `conn.query` and `graph.determineIfIncludedOrEqual` callbacks, i.e. inside asynchronous I/O completions, not inside the synchronous call stack of `validate()`. A `throw` at that point cannot be caught by any surrounding `try/catch` or by the `async.series`/`mutex.lock` error-handling machinery in `validate()` (`validation.js:363-493`) — it becomes an uncaught exception on the event loop. `network.js` installs a global handler that intentionally converts this into a hard process crash: [3](#0-2) 

This validation path is exercised for **private payments**, which are processed on behalf of a private-payment counterparty via `divisible_asset.js` / `indivisible_asset.js` calling into `validation.validatePayment` → `validatePaymentInputsAndOutputs`: [4](#0-3) [5](#0-4) 

and via the network-facing handler that ingests private payments received from peers/hub and re-validates them: [6](#0-5) 

A counterparty crafts a private-asset transfer chain that passes the earlier structural/spend-proof checks (so it is accepted as "valid" input by the parser) but whose underlying source output is involved in a double-spend that the graph-inclusion check classifies as unresolved/too-young. That drives `err` into `onDone`, which unconditionally throws for private assets (`objAsset.is_private && !conf.bLight`), crashing every full node (and every light-vendor/hub) that processes this payment.

### Impact Explanation
Any node that validates the crafted private payment (the direct recipient, the hub relaying the message, or a full node used as a validating helper) crashes its Node.js process via the deliberate `throw err` in the `uncaughtException` handler. Because the trigger is a single crafted private-payment chain sent by an ordinary private-payment counterparty, this is a repeatable, low-cost remote DoS against wallets/hubs that process private transfers of a private asset — matching the CVE's "unauthenticated attacker crashes the server" class of bug, high severity (availability impact only, no auth required).

### Likelihood Explanation
Likelihood is high: constructing a private payment chain that references a genuinely conflicting/double-spent source output for a private asset is entirely within reach of any wallet holding (or asset issuer able to mint) a private asset; no special privileges beyond being a normal private-payment counterparty are needed, and the throwing code path is on the standard validation route, not a rarely-hit corner case guarded by additional network-level protections.

### Recommendation
Replace the unconditional `throw Error(...)` calls in `checkForDoublespends` (`validation.js:1673`, `1688`, `1692`) and in the private-asset branch of `onDone` (`validation.js:2298-2299`) with normal error propagation through the `cb`/`cb2`/`cb3` callback chain (e.g. `return cb2(err-message)` / `return cb(err)`), so that an unresolved double-spend on a private asset is rejected as a validation error (`ifUnitError`/`ifError`) instead of crashing the process. Add regression tests that submit a private-asset payment whose input double-spends an output not included in the unit's parents, and assert the node responds with a validation error rather than terminating.

### Proof of Concept
1. Issue a private asset and, as the issuer/counterparty, build two conflicting private-payment chains spending the same source output (same `unit`/`message_index`/`output_index`), each with a technically-correct spend proof for its own chain.
2. Send both chains (directly or through the hub) to a target node/wallet, ordering them so the second one's underlying conflict is *not* included in/equal to the first unit's parents (e.g., via `graph.determineIfIncludedOrEqual` returning `bIncluded=false` and being treated as unresolved rather than accepted).
3. The target's `validatePaymentInputsAndOutputs` → `checkInputDoubleSpend` → `checkForDoublespends` → `onDone` receives a non-null `err` for `objAsset.is_private`, executing `throw Error("spend proof didn't help: "+err)` (`validation.js:2298-2299`).
4. This throw escapes the async callback, is caught only by `process.on('uncaughtException', ...)` in `network.js:4530-4543`, which logs it and re-`throw`s, terminating the Node.js process — a remote, unauthenticated denial of service.
