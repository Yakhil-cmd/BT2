### Title
Webhook signature verification binds to a different organization than the repository whose stacks are mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). The actual repository whose `Stack`s get mutated by the event handlers is resolved from an entirely different, unrelated payload field: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing cross-checks that the org used to authenticate the payload is the org that owns the repository being acted upon, so a webhook secret belonging to organization A can be used to sign a payload that mutates stacks belonging to organization B.

### Finding Description
The verification flow is:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Once `create` accepts the request, handlers resolve the *target* repository/stacks using a completely different field:
```ruby
# app/models/shipit/webhooks/handlers/handler.rb
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler#process` uses `stacks` (derived from `full_name`) to trigger `sync_github` on matching stacks: [3](#0-2) . `StatusHandler#process` doesn't even scope by repository at all — it updates any `Commit` whose `sha` matches, regardless of which repository the signed payload claims to be from: [4](#0-3) .

Shipit explicitly supports configuring **multiple independent GitHub organizations**, each with its own `webhook_secret`, in the same Shipit instance: [5](#0-4)  and [6](#0-5) . `Shipit.github(organization:)` looks up the `GitHubApp`/secret keyed strictly by the `repository_owner` value taken from the payload, per `lib/shipit/github_app.rb`'s `verify_webhook_signature` [7](#0-6) .

**The broken binding is:** `organization authenticated by signature == organization owning the repository whose stacks/commits are mutated`. Before the attack: for a legitimate GitHub-originated webhook, `repository.owner.login` and `repository.full_name`'s owner segment always match (GitHub itself sets both from the same repository object), so the binding holds implicitly, never explicitly enforced by Shipit's code. After the attack: an attacker who legitimately controls (or has been handed webhook delivery for) organization A's repository on GitHub — and thus knows/can trigger valid HMAC signatures using org A's `webhook_secret` — can craft (or replay-and-modify before delivery is impossible since GitHub signs it, but the attacker *is* the org A repository admin who can set the payload content by configuring redirect/mirror webhooks, or by using GitHub's "Redeliver"/custom webhook endpoints they control on their own repo) a payload where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/target-repo"`. Because `Shipit.github(organization: "orgA")` verifies using orgA's own secret, the signature check passes trivially, and `PushHandler`/`StatusHandler` then act on organization B's stacks despite the request never having been authenticated by anything orgB controls.

### Impact Explanation
This breaks the intended trust boundary between separate GitHub organizations hosted on the same Shipit instance, allowing cross-repository/cross-organization writes: an attacker owning webhook credentials for one onboarded org can force `GithubSyncJob` synchronization or forge commit statuses (`Commit#create_status_from_github!`) for stacks belonging to a different org's repositories, potentially unblocking or deceiving that stack's merge queue and deploy pipeline. This matches the "cross-repository writes / unauthorized deploy" Critical-tier impact category.

### Likelihood Explanation
Requires the Shipit deployment to be configured with more than one GitHub organization (a documented, supported configuration in `docs/setup.md`), and requires the attacker to control a legitimate webhook_secret for at least one onboarded organization — a realistic scenario for any multi-tenant Shipit instance where different teams/orgs are onboarded with differing trust levels. No privileged Shipit session, `ApiClient` token, or GitHub App private key is needed — only the ability to sign a payload with an org-scoped `webhook_secret` that Shipit itself considers valid for delivery.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to verify the signature (`repository_owner`) matches the organization segment of `repository.full_name` (and of `organization.login` when present) before dispatching to any handler; reject the webhook with 422 if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org config).
2. As the owner of a GitHub repository under `orgA`, set up a proxy/webhook relay (fully within the attacker's own infrastructure and GitHub App/repo settings) that receives GitHub's genuine `push` webhook for `orgA/some-repo` (correctly signed with `orgA`'s secret) and rewrites the JSON body's `repository.full_name` to `orgB/victim-repo` before forwarding to Shipit's `/github/webhooks` endpoint, recomputing nothing (the signature is computed over the modified raw body using the still-known `orgA` secret since the attacker controls the relay and secret).
3. `WebhooksController#verify_signature` computes `repository_owner` from the (now forged) `repository.owner.login`/`organization.login`... — more precisely, the attacker sets `repository.owner.login = "orgA"` and `repository.full_name = "orgB/victim-repo"` and signs with `orgA`'s secret. `Shipit.github(organization: "orgA")` verifies successfully.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github` on `orgB`'s stack, forcing a sync despite the request never being authenticated by anything `orgB` controls.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
