### Title
Silent CLStakingInfo Overwrite in `consolidateNodes()` Causes Permanent Zero-Reward for a CL Pool Sharing a RewardAddr — (`kaiax/staking/staking_info.go`)

---

### Summary

When two AddressBook NodeIds share the same `RewardAddr` and each has a separate `CLStakingInfo` registered in CLRegistry, the `consolidateNodes()` function silently overwrites the first CL's entry with the second. The dropped CL pool receives **zero KAIA reward every block** while the CN absorbs the reward that should have been split to it. No error is raised; the state is silently corrupted.

---

### Finding Description

`consolidateNodes()` in `kaiax/staking/staking_info.go` aggregates multiple AddressBook entries that share the same `RewardAddr` into a single `consolidatedNode`. The CN staking amounts are correctly summed, but the `CLStakingInfo` field is a single pointer — the last CL entry encountered for that `RewardAddr` overwrites all previous ones:

```go
// kaiax/staking/staking_info.go  lines 150-160
if len(si.CLStakingInfos) > 0 {
    for _, clsi := range si.CLStakingInfos {
        if r, ok := nToR[clsi.CLNodeId]; ok {
            // One CLStakingInfo per validator is guaranteed by CLRegistry.
            cmap[r].CLStakingInfo = clsi   // ← OVERWRITES any previous CL for this RewardAddr
        }
    }
}
```

The comment "One CLStakingInfo per validator is guaranteed by CLRegistry" is correct per-NodeId, but it does **not** prevent two distinct NodeIds that share the same `RewardAddr` from each having their own CL registered. The AddressBook explicitly supports multiple NodeIds per `RewardAddr` (the entire purpose of consolidation), and CLRegistry is indexed by NodeId, not by RewardAddr.

Concrete scenario:

| Entity | NodeId | RewardAddr | CLPool | CLStakingAmount |
|--------|--------|------------|--------|-----------------|
| Entry 1 | N1 | R1 | CL1 | X KAIA |
| Entry 2 | N3 | R1 | CL3 | Y KAIA |

After `consolidateNodes()`:
- `consolidatedNode.StakingAmount` = A1 + A3 ✓ (correctly summed)
- `consolidatedNode.CLStakingInfo` = `{N3, CL3, Y}` ✗ (CL1 silently dropped)

The `Split()` function then computes the reward split using only CL3's amount:

```go
// kaiax/staking/staking_info.go  lines 169-186
cnAmountBig = big.NewInt(int64(c.StakingAmount))              // A1+A3
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount)) // Y only — X is gone
totalAmount = cnAmountBig + clAmountBig                        // A1+A3+Y  (missing X)

clAmount = clAmountBig * amount / totalAmount   // CL3 gets reward * Y/(A1+A3+Y)
cnAmount = amount - clAmount                    // CN gets reward * (A1+A3)/(A1+A3+Y)
// CL1 pool address is never credited — receives 0
```

Correct split should be:
- CN: `reward × (A1+A3) / (A1+A3+X+Y)`
- CL1: `reward × X / (A1+A3+X+Y)`
- CL3: `reward × Y / (A1+A3+X+Y)`

The test case in `kaiax/staking/staking_info_test.go` lines 243–271 explicitly demonstrates this overwrite and labels it "not feasible in real" — but this is an unverified developer assumption, not an on-chain invariant.

The corrupted `consolidatedNode` propagates through both reward paths:
- `assignStakingRewards()` — `kaiax/reward/impl/getter.go` line 490
- `assignStakingRewardsFlex()` — `kaiax/reward/impl/getter.go` line 423

Both call `si.ConsolidatedNodes()` and then `cn.Split(reward)`, so every block's reward distribution is affected.

---

### Impact Explanation

CL1's pool address is never added to the `alloc` map in `assignStakingRewards` / `assignStakingRewardsFlex`. Every block, the KAIA that should flow to CL1's pool instead remains with the CN's reward address. Over time this constitutes a permanent, silent misallocation of KAIA block rewards — an unauthorized reward distribution affecting system-managed funds.

---

### Likelihood Explanation

**Permissioned system (pre-Permissionless hardfork):** Requires governance to register two NodeIds with the same `RewardAddr` in AddressBook. This is a privileged path.

**Permissionless system (post-Permissionless hardfork):** A single operator can self-register multiple NodeIds with the same `RewardAddr` in AddressBookV2 and independently register CLs for each NodeId in CLRegistry. No cross-registry check prevents this. This is a valid semi-trusted trigger requiring no special privilege beyond normal validator registration.

---

### Recommendation

Replace the single-pointer overwrite with accumulation. Either:

1. Change `CLStakingInfo` in `consolidatedNode` to a slice and sum all CL amounts when splitting rewards, or
2. Add an explicit guard in `consolidateNodes()` that detects a second CL for the same `RewardAddr` and either rejects it with an error or sums the amounts into a synthetic entry.

```go
// Proposed fix sketch
if existing := cmap[r].CLStakingInfo; existing != nil {
    // Sum CL amounts instead of overwriting
    existing.CLStakingAmount += clsi.CLStakingAmount
    // CLPoolAddr ambiguity must also be resolved (e.g., keep first, or use a list)
} else {
    cmap[r].CLStakingInfo = clsi
}
```

### Proof of Concept

**State setup:**
- AddressBook: `[N1→R1, N3→R1]`, staking amounts `[A1, A3]`
- CLRegistry: `[N1→CL1 pool, X KAIA]`, `[N3→CL3 pool, Y KAIA]`

**Trace through `consolidateNodes()`:**

1. First loop (NodeIds): `cmap[R1] = {NodeIds:[N1,N3], StakingAmount:A1+A3, CLStakingInfo:nil}` [1](#0-0) 

2. Second loop (CLStakingInfos): `cmap[R1].CLStakingInfo = {N1,CL1,X}` then immediately `cmap[R1].CLStakingInfo = {N3,CL3,Y}` — CL1 is gone. [2](#0-1) 

3. `Split(reward)` uses `totalAmount = A1+A3+Y` (missing X): [3](#0-2) 

4. `assignStakingRewards` credits only `cn.RewardAddr` and `cn.CLStakingInfo.CLPoolAddr` (CL3). CL1's pool address is never written to `alloc`. [4](#0-3) 

5. `FinalizeState` distributes rewards per `alloc` — CL1 pool receives 0 KAIA. CL1 pool operator can verify on-chain that their staked tokens earn nothing despite being registered in CLRegistry.

The test case confirming the overwrite behavior (labeled "not feasible in real") is at: [5](#0-4)

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
```
