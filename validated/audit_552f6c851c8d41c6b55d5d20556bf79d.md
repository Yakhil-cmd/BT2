### Title
RAY-value overflow in `scaled_to_original` during accrual permanently freezes every verb on a large high-utilization market - (File: common/src/rates/scaling.rs)

### Summary
The bug class in the report is an out-of-range value corrupting execution (a buffer overflow → segfault/DoS). On Soroban the analogue is an `i128` overflow panic on a state value an unprivileged caller's action helped create. The pool's accrual step computes `borrowed_scaled × borrow_index` and `supplied_scaled × supply_index` as RAY values inside `accrue_step`, before the `MAX_BORROW_INDEX_RAY` cap can engage. For a very large market the product exceeds `i128::MAX` while the index is still below its cap, so `global_sync` panics with `MathOverflow`. Every user-facing verb accrues first, so the market is permanently frozen: no repay, withdraw, liquidation, or `update_indexes` can ever succeed again. This is confirmed by the production-path test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which also notes the bound documented in `docs/reference/formulas.md` is wrong — i.e. this is not a documented design limit. [1](#0-0) 

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs` calls `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)` at the top of every compounding chunk, before computing the interest factor. [2](#0-1)  These are `Ray::mul` = `mul_div_half_up(x, y, RAY)`: the widened `I256` intermediate is exact, but the *result* must fit `i128`, so `supplied_scaled * index` overflows when the RAY value of the book exceeds ~1.7e38 (i128::MAX ≈ 1.7e38, RAY = 1e27 → roughly 1.7e11 token value at index 1, shrinking as the index grows). [3](#0-2) 

`update_borrow_index` clamps the index at `MAX_BORROW_INDEX_RAY` (1e36), but the multiplication `borrowed_scaled × new_index` happens on the *unclamped* path's inputs each step — the test demonstrates the index sits well below the cap when the value product overflows, so the cap never saves it. [4](#0-3) 

`global_sync` runs `accrue_chunk` unconditionally at the head of every mutating pool operation (`supply`, `borrow`, `withdraw`, `repay`, `seize`, `flash_loan`, `claim_revenue`, `update_indexes`). [5](#0-4)  A panic inside accrual therefore blocks the whole market, not just the accrual call. Because `last_timestamp` is only advanced after all chunks succeed (`cache.mark_accrued()`), the overflow recurs on every retry — there is no way to skip or partial-accrued the offending span. [6](#0-5) 

### Impact Explanation
Permanent freezing of funds. Once the RAY value product crosses `i128::MAX` mid-accrual, every verb on that (hub, token) market reverts with `MathOverflow` forever: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and `recapitalize` — which also accrues first — cannot rescue it. The test explicitly asserts `withdraw` and `repay` both revert after the cliff. [7](#0-6)  All user funds in that market are unrecoverable by contract means; the bad debt on the book can never be socialized or cleaned either, since `clean_bad_debt`/`seize` paths accrue too.

### Likelihood Explanation
Requires a whale-scale book (order ~1e11+ units of token value in scaled terms) sustained at high utilization on a steep rate curve for multiple years — the test uses a 1-billion-unit 18-decimal market at 98% utilization on the XLM curve and reaches the cliff in under 40 years, sooner at steeper rates. [8](#0-7)  An unprivileged attacker cannot trigger it instantly, but can contribute to it: `supply` and `borrow` are permissionless, so a funded attacker can deliberately inflate `borrowed`/`supplied` on a high-rate market to pull the cliff closer, then simply wait — time advances `elapsed_ms` regardless of who calls `update_indexes`. The state is monotone: supplied and indexes only grow (absent bad debt), so there is no way back once approached. Medium likelihood on large markets, certain doom once crossed — consistent with the report's Medium severity.

### Recommendation
Make `scaled_to_original` (or `accrue_step`) saturate rather than panic: clamp the accrued value at the point `supplied_scaled × supply_index` or `borrowed_scaled × borrow_index` would exceed `i128::MAX`, e.g. cap utilization inputs at a saturating division (a `mul_div_half_up_saturating` variant, mirroring the existing `mul_div_floor_saturating` in `common/src/math/fp_core.rs` [9](#0-8) ), so accrual degrades to "max utilization, max rate" instead of reverting. Additionally enforce the borrow/supply index caps *before* the value multiplications, and consider capping total per-market scaled supply/borrow at a level where `scaled × MAX_INDEX_RAY` always fits `i128`, turning the unreachable cliff into a hard supply/borrow cap that fails only the offending verb.

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub fn mul_div_floor_saturating(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    require_nonzero_divisor(env, d);
    if let Some(quotient) = x
        .checked_mul(y)
        .and_then(|product| div_floor_i128(product, d))
    {
        return quotient;
    }
    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    div_floor_i256(
        env,
        &x256.mul(&y256),
        &d256,
        quotient_is_nonnegative(x, y, d),
    )
    .to_i128()
    .unwrap_or(if quotient_is_negative(x, y, d) {
        i128::MIN
    } else {
        i128::MAX
    })
}

fn test_borrow_index_at_the_ceiling_multiplies_without_overflow() {
    let env = Env::default();

    // `update_borrow_index` multiplies before it clamps, so the pre-clamp
    // product at the ceiling times the largest reachable chunk factor is the
    // real overflow site. It must stay inside i128 with room to spare.
    let factor = max_chunk_growth_factor(&env, MAX_BORROW_RATE_RAY);
    let at_ceiling = Ray::from(MAX_BORROW_INDEX_RAY);

    let product = at_ceiling.mul(&env, factor);
    assert!(product.raw() > MAX_BORROW_INDEX_RAY);
    assert!(
        product.raw() < i128::MAX / 20,
        "pre-clamp headroom above the ceiling fell below 20x: {}",
        product.raw()
    );

    assert_eq!(
        update_borrow_index(&env, at_ceiling, factor).raw(),
        MAX_BORROW_INDEX_RAY,
    );

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
