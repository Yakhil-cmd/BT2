### Title
XCM ERC20Transactor credits/moves the stated `amount`, not the amount actually transferred by a fee-on-transfer/non-standard ERC20 - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke the target ERC20 contract's `transfer()` and treat a boolean `true` return value as conclusive proof that exactly `amount` moved. Any account may permissionlessly deploy an ERC20 contract via `pallet-revive` on AssetHub and have it recognized as an XCM-transactable fungible asset through `Matcher::matches_fungibles`. A contract that returns `true` while moving less (or more) than the requested `amount` — the same "fee-on-transfer"/non-standard-ERC20 class described in the referenced Juicebox finding — desynchronizes the XCM executor's internal `AssetsInHolding` accounting (and the shared `TransfersCheckingAccount`'s real on-chain balance) from the token's true balances.

### Finding Description
The transactor never measures the `TransfersCheckingAccount`'s actual balance before/after the `transferCall`; it only decodes the boolean return value [3](#0-2) . On withdraw, `Erc20Credit(amount)` is minted into the XCM holding using the *requested* `amount` regardless of how much the ERC20 contract actually moved into the checking account [4](#0-3) . On deposit, the same pattern repeats: the transactor asks the checking account to `transfer(beneficiary, amount)` for the full credited `amount` and, on `true`, reports full success back to the XCM executor without verifying the beneficiary's balance changed by `amount` [5](#0-4) .

Because any address can deploy such a contract (there is no allow-list visible in this transactor — matching is done purely via `Matcher::matches_fungibles` against the H160 contract address), an attacker fully controls the ERC20 semantics without needing any privileged role, matching the "no privileged role/governance/stolen keys" constraint.

### Impact Explanation
For a deflationary/fee-on-transfer ERC20 asset:
- During withdraw, the checking account's real balance increases by `amount - fee`, but the XCM holding is credited the full `amount`.
- The subsequent deposit step will try to move the full (inflated) `amount` out of the checking account. If the checking account's real balance is insufficient, the ERC20's own balance check causes the call to fail, and the transactor reports `XcmError::FailedToTransactAsset`, deterministically failing the message — mirroring the original report's core failure mode (stated amount not honored at settlement time causing a revert).
- If the checking account happens to hold leftover/residual balance of the same ERC20 from other in-flight or partially-failed operations, the deposit can instead *succeed* while paying out of that residual balance, meaning one user's shortfall is silently covered by another's funds sitting in the shared `TransfersCheckingAccount`, and the XCM program's own accounting (holding amounts, refunds, `Wild(AllCounted(N))` leftover deposits used pervasively in this codebase's reserve-transfer flows) continues to reason about the inflated, incorrect `amount` rather than what was truly moved. This breaks the fungible-asset invariant that the recorded holding amount equals the real balance delta, and can result in beneficiaries receiving less than the XCM program computed, or in stuck/undeliverable balances in the shared checking account.

### Likelihood Explanation
Deploying a non-standard/fee-on-transfer ERC20 via `pallet-revive` requires no privileges and is exactly the kind of externally-callable, attacker-authored contract logic the referenced report targets. Any signed account can deploy such a contract and then either use it themselves via XCM `execute`/`send` (a permitted, publicly reachable entry point) or have others interact with it as an ordinary AssetHub asset, since `ERC20Transactor` performs no verification distinguishing "standard" ERC20s from adversarial ones.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the relevant account's ERC20 balance (via `balanceOf`) immediately before and after the `transferCall`, and use the observed delta — not the requested `amount` — to construct `Erc20Credit`/to report success, mirroring the Juicebox mitigation of measuring actual balance delta rather than trusting the stated transfer amount.

### Proof of Concept
No executable PoC was run against a live network; this is a static-code-level analog derived strictly from reading `erc20_transactor.rs` in the target repository, cited above. A full reproduction would require: (1) deploying a minimal Solidity ERC20 on a AssetHub-with-revive test runtime whose `transfer()` deducts a fee (returns `true`, transfers `amount - fee`), (2) driving an XCM `execute`/reserve-transfer through `ERC20Transactor::withdraw_asset_with_surplus` then `deposit_asset_with_surplus` using the existing `pallet_revive` test harness patterns visible in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` (`withdraw_and_deposit_erc20s`, `smart_contract_does_not_return_bool_fails`), and (3) asserting the beneficiary's actual `balanceOf` is less than the amount the XCM program/holding recorded as deposited. This reproduction was not executed as part of this analysis; only the static code path was verified.
