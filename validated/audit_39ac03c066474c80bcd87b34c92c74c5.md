### Title
Webhook signature verification selects the GitHub App/organization from query-string-overridable `params`, while event processing acts on the raw request body - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate a delivery against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')`. `#create` then re-parses `request.raw_post` independently and dispatches that body to handlers. Because Rails' `params` merges `query_parameters` **over** `request_parameters` (body), an attacker can force `verify_signature` to check the signature against an organization/App config of their choosing (e.g., one with no `webhook_secret` configured) via the query string, while the actually-processed payload (from `raw_post`) still targets a different, legitimately-configured victim organization/repository.

### Finding Description
The check and the effect are bound to two different data sources:

- The "authenticated organization" is computed from `params` (query string can override body): [1](#0-0) [2](#0-1) 

- The "repository/data that gets written" is computed independently from the raw body: [3](#0-2) 

- Signature verification is a no-op when the resolved organization has no `webhook_secret` set (a supported/optional configuration, as shown in the secrets template): [4](#0-3) [5](#0-4) 

Rails' `ActionDispatch::Http::Parameters#parameters` merges `request_parameters` (JSON body) first and then merges `query_parameters` on top, so a same-named key supplied in the query string wins over the value in the signed body when accessed via `params`. `repository_owner` uses exactly that merged `params` object, not `request.raw_post`: [6](#0-5) 

Consequently, an attacker can craft a request such as:
```
POST /github/webhooks?repository[owner][login]=attacker-org
X-Github-Event: status
X-Hub-Signature: sha1=anything
Body: { "repository": {"owner": {"login": "victim-org"}, "full_name": "victim-org/victim-repo"}, "sha": "...", "state": "success", ... }
```
`verify_signature` resolves `repository_owner` to `"attacker-org"` (from the query string) and fetches `Shipit.github(organization: "attacker-org")`. If `attacker-org` has no `webhook_secret` configured on this Shipit instance (a legitimately supported, nil-by-default setting) - or the attacker knows that org's secret because they administer it on the same multi-tenant instance - `verify_webhook_signature` returns `true` unconditionally, and the request passes.

`create` then does `params = JSON.parse(request.raw_post)` (a fresh, query-string-independent parse) and dispatches to handlers such as `StatusHandler` or `PushHandler`, which act on the real body content, i.e., `victim-org/victim-repo`: [7](#0-6) [8](#0-7) 

This is structurally identical to the referenced bug class: the invariant actually enforced ("this org's secret is valid" for whatever org is in `params`) is not the same as the invariant that should hold for the data that is actually acted upon (the org/repository embedded in the verified raw body).

### Impact Explanation
This breaks the equality that should hold: `{organization whose secret validated the signature} == {repository/organization the payload writes to}`. Exploiting it lets an unauthenticated attacker (no GitHub webhook secret for the victim org, no Shipit session, no ApiClient token) forge:
- `status` events, injecting fake CI `success` statuses for arbitrary commits (`StatusHandler`), which feeds directly into `MergeRequest#all_status_checks_passed?` and the merge queue, enabling unauthorized merges/deploys of unreviewed code.
- `push` events, forcing `GithubSyncJob`/stack re-sync for arbitrary tracked stacks.
- `check_suite`, `membership`, `pull_request` events, etc., all handled the same way.

This matches the "High"/"Critical" impact bar in the rules: escalation to unauthorized deploy/merge decisions, achieved purely through an authentication-bypass in signature verification logic — no repository write access, ApiClient token, or Shipit session required.

### Likelihood Explanation
Exploitability depends on the multi-tenant configuration of the Shipit instance: it requires at least one configured GitHub organization on the instance whose `webhook_secret` is unset (a documented, supported "nil" default per `config/secrets.development.shopify.yml`) or whose secret the attacker knows (e.g., their own org hooked to the same instance). Given `webhook_secret` is explicitly optional/nilable in the engine's own configuration and any org present in `Shipit.github` config qualifies, this is readily reachable on any instance that hosts more than one organization or that has any org without a secret configured — a realistic and common deployment shape for Shipit (it's designed to serve many repos/orgs from one instance). No credentials, no signed webhook secret for the victim org, and no application-level authentication are needed by the attacker.

### Recommendation
Verify the signature and derive the acted-upon organization from the *same* parsed body:
- Parse `request.raw_post` once (e.g., into `@payload`) before `verify_signature` runs, and have both `repository_owner` and `create` read from that single, body-derived hash instead of the ActionController `params` object that can be polluted by the query string.
- Alternatively, explicitly strip/ignore query parameters for this endpoint (only permit path segments), and be sure `repository_owner` reads exclusively from `JSON.parse(request.raw_post)`.
- Consider requiring a `webhook_secret` to be present for every configured GitHub App/organization (fail closed instead of returning `true` when blank), removing the "no-secret" bypass path entirely.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations, e.g. `victim-org` (has `webhook_secret: real-secret`) and `attacker-org` (webhook_secret left `nil`, as allowed by the shipped config template).
2. Attacker (no credentials) sends:
```
POST /github/webhooks?repository[owner][login]=attacker-org
Content-Type: application/json
X-Github-Event: status
X-Hub-Signature: sha1=0000000000000000000000000000000000000000

{
  "repository": { "owner": { "login": "victim-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<sha of a real pending commit in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{"name": "master"}]
}
```
3. `verify_signature` resolves `repository_owner` to `"attacker-org"` from the query string, loads its `GitHubApp`, and since its `webhook_secret` is blank, `verify_webhook_signature` short-circuits to `true` regardless of the bogus `X-Hub-Signature`.
4. `create` re-parses `request.raw_post`, finds `victim-org/victim-repo` and dispatches to `StatusHandler`, which creates a forged `success` status for the specified `sha` in `victim-org`'s repository — even though `victim-org`'s real `webhook_secret` was never validated.
5. This forged status can satisfy `MergeRequest#all_status_checks_passed?` for the merge queue on `victim-org`'s stack, leading to an unauthorized merge/deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
