### Title
Unchecked multiplication in indivisible-asset denomination/cap validation can desynchronize declared cap from actual issuable supply - (File: validation.js)

### Summary
`validateAssetDefinition()` and `validateIndivisibleIssue()` in `validation.js`, together with the issuance logic in `indivisible_asset.js`, compute the real token supply for a fixed-denomination (indivisible) asset as `denomination * count_coins` without any overflow/safe-arithmetic protection on the multiplication itself. This mirrors the reported bug class ("math operations involving [issuance amounts] that aren't checked … it's always better to be safe and perform checked operations"), except here the unchecked multiplication sits in the on-chain asset-issuance validation path that any unprivileged asset issuer can trigger.

### Finding Description
When an asset issuer defines a fixed-denomination asset with a `cap`, each denomination bucket declares `denomination` and `count_coins`. The cap-consistency check sums these with a raw JS multiplication with no bound on the product: [1](#0-0) 

Key gaps:
- `denomInfo.count_coins` is only checked with `isPositiveInteger(...)` — it has **no upper bound** (unlike `payload.cap`, which is explicitly capped at `constants.MAX_CAP`).
- `denomInfo.denomination` is only bounded against `MAX_CAP` conditionally, on/after `constants.pemCurvesFixMci` (or when `hasBall`/`getMinRetrievableMci()` conditions hold) — see the surrounding check at line 2771. Before that height/condition, `denomination` is effectively unbounded too.
- The product `denomInfo.count_coins * denomInfo.denomination` is accumulated into `total_cap_from_denominations` and only later compared for strict equality against the already-bounded `payload.cap` — the multiplication itself is never checked against `MAX_CAP` or `Number.MAX_SAFE_INTEGER` before being trusted.

The same unchecked pattern re-appears when an actual "issue" input for that denomination is validated: [2](#0-1) 

Here `input.amount !== denomination * denomInfo.count_coins` is the sole integrity check tying the recorded, balance-affecting `input.amount` (already bounded to `MAX_CAP` and validated as `isPositiveInteger` earlier in the `issue` case) to the denomination metadata. Because JavaScript numbers only preserve exact integer values up to `Number.MAX_SAFE_INTEGER` (2^53−1), a product of two sufficiently large operands silently loses precision (rounds to the nearest representable double) rather than throwing or being rejected. An issuer can therefore choose `denomination` and `count_coins` whose true (BigInt) product differs from their IEEE‑754 double product, letting a crafted `input.amount` pass the equality check even though it does not equal the mathematically correct `denomination * count_coins`.

The wallet-side composer that would normally construct these issuances performs the identical unchecked multiplication when computing how many coins to issue for a target amount: [3](#0-2) 

### Impact Explanation
The asset's declared `cap` (and the corresponding sum derived from `denominations`) is a supply guarantee that other unprivileged participants rely on — e.g., AA oscripts read `asset[$asset].cap` to compute investor shares, exchange ratios, or payout amounts (see the market-maker and exchange sample contracts that reference `asset[...].cap`/balances for pricing). If the recorded cap and the denomination-derived total silently diverge due to unchecked multiplication overflow, an asset issuer can make the network accept an asset definition/issuance whose actual composition of denominations does not truthfully reflect the number advertised as the cap, undermining any AA or wallet logic (including third-party contracts) that trusts the cap value for accounting, pricing, or share calculations — a supply-integrity violation analogous to the original unchecked "bought tokens"/"cost" computation in the report.

### Likelihood Explanation
Exploitation requires the issuer to deliberately select `denomination` and `count_coins` values whose product straddles `Number.MAX_SAFE_INTEGER` (~9.007×10^15) so that floating-point rounding produces a mismatch between the true product and the value used for consensus validation. This is fully within reach of a single, unprivileged asset-issuing unit author (no special privilege needed — asset definition and indivisible-asset issuance are ordinary, permissionless unit operations), and the outcome is deterministic (all full nodes compute the same IEEE‑754 result), so there is no risk of rejection once crafted correctly. The engineering effort to find matching overflow values is the main mitigating factor, keeping likelihood at medium rather than high.

### Recommendation
- Bound `denomInfo.count_coins` explicitly against `constants.MAX_CAP` (unconditionally, not just via the derived `total_cap_from_denominations` comparison), matching how `payload.cap` and `output.amount` are already bounded.
- Remove/eliminate the upgrade-height-conditional exemption on `denomInfo.denomination`'s `MAX_CAP` check so it applies unconditionally going forward.
- Perform the multiplication using either `BigInt` or an explicit pre-condition check (e.g., reject if either operand exceeds `Math.sqrt(Number.MAX_SAFE_INTEGER)` or if `count_coins > Math.floor(Number.MAX_SAFE_INTEGER / denomination)`) before trusting the product, in both `validateAssetDefinition()` and `validateIndivisibleIssue()` in `validation.js`, and in the composer logic in `indivisible_asset.js`.

### Proof of Concept
Conceptual outline (exact overflow-triggering values require offline computation, not verified here due to tool/iteration limits):
1. An asset issuer submits an `asset` definition message with `fixed_denominations: true`, `cap: X` (X ≤ `MAX_CAP`), and a `denominations` array containing an entry `{denomination: D, count_coins: C}` where `D` and `C` are chosen (via off-chain search) such that the true integer product `D*C` differs from `X`, but the IEEE‑754 double computation `D*C` in `validation.js` rounds to exactly `X`, passing the `total_cap_from_denominations` vs `cap` equality check at [4](#0-3) .
2. The issuer later posts an `issue` input for denomination `D` with `amount` set to the same rounded value `X`. `validateIndivisibleIssue()` accepts it because `input.amount !== denomination * denomInfo.count_coins` evaluates to `false` under the same floating-point rounding, per [5](#0-4) .
3. The asset is now considered validly issued/capped by all nodes (deterministically), yet the denomination metadata does not truthfully represent `D*C` in exact arithmetic, creating a mismatch that downstream consumers (AAs reading `asset[...].cap`, wallets summing denominations) cannot detect, since they consume the same (deterministically wrong) values.

This proof of concept could not be executed against a live node within this session; the exact `D, C` overflow pair and end-to-end confirmation of downstream impact on AA-visible `cap` values would need to be validated with a running Devin session that has filesystem/test-execution access.
