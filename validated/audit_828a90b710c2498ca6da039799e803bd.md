### Title
`collect_creator_fee` / `collect_creator_fee_permissionless` hard-code the pool creator's own ATA as fee destination, permanently freezing accrued creator fees if that account is frozen/blacklisted - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
Accrued creator fees (`pool_state.creator_fees_token_0` / `creator_fees_token_1`) can only be withdrawn to an associated-token-account whose authority is hard-constrained to `creator` (the `pool_creator` recorded on `PoolState`). Neither instruction exposes a way to redirect the payout to a different recipient token account.

### Finding Description
In `CollectCreatorFee`, the destination accounts are constrained as: [1](#0-0) 

and the `creator` signer itself is pinned to `pool_state.load()?.pool_creator`: [2](#0-1) 

`transfer_from_pool_vault_to_user` then moves the fees to `creator_token_0`/`creator_token_1` unconditionally: [3](#0-2) 

The permissionless variant is identical in structure — `creator_token_0`/`creator_token_1` are constrained to `associated_token::authority = creator`, where `creator` is fixed to `pool_state.load()?.pool_creator`: [4](#0-3) [5](#0-4) 

If token_0's or token_1's mint carries a freeze authority (or a Token-2022 default-account-state / permanent-delegate style mint) and the freeze authority freezes the creator's associated token account (e.g. compliance blacklisting), every CPI `transfer_checked` into that account will fail, because the underlying token program rejects transfers into a frozen account. Since both entry points route funds exclusively to that one ATA with no `recipient` parameter and no alternative destination account, the accrued `creator_fees_token_0`/`creator_fees_token_1` balances tracked in `PoolState`: [6](#0-5) 
become permanently uncollectable — they remain locked inside `token_0_vault`/`token_1_vault` forever, since `vault_amount_without_fee` also continues to reserve them out of the swappable/withdrawable balance: [7](#0-6) 

This mirrors the referenced Ajna/Beedle report: a user-controlled destination is hard-wired to a specific owner-derived address with no `recipient` argument, so if that owner is later blacklisted by the asset issuer, their otherwise-withdrawable funds are frozen with the pool indefinitely. Unlike `withdraw` (whose `token_0_account`/`token_1_account` are only constrained by `token::mint`, with no authority check, so a user can already redirect funds to any other account they control), `collect_creator_fee`/`collect_creator_fee_permissionless` allow no such flexibility.

### Impact Explanation
If the pool creator's own ATA for token_0 or token_1 becomes frozen by the mint's freeze authority (a realistic scenario for stablecoins like USDC with compliance-driven blacklisting), the full accumulated `creator_fees_token_0`/`creator_fees_token_1` balance becomes permanently stuck in the pool vault — no code path exists to redirect it to an unfrozen address. This is a real, if low-likelihood, permanent freezing of legitimate creator fee funds, matching the Medium-severity classification in the referenced report.

### Likelihood Explanation
This requires the pool creator's associated token account for one of the pool's mints to be frozen by that mint's freeze authority, which is an action available only to the token issuer (not any pool participant) and is uncommon in practice — hence the same "low likelihood, medium severity" characterization as the original report.

### Recommendation
Allow the `pool_creator` to specify an alternate destination token account (not hard-constrained to `associated_token::authority = creator`) when calling `collect_creator_fee`, similar to how `withdraw`'s `token_0_account`/`token_1_account` are unconstrained by authority. At minimum, relax the `associated_token::authority` constraint to accept any token account matching the correct mint that the creator explicitly passes in, so fees can still be swept out if the creator's default ATA becomes frozen.

### Proof of Concept
1. Pool is created with `token_0_mint` = a token whose mint authority also holds freeze authority (e.g., a centralized stablecoin).
2. Swaps accrue `creator_fees_token_0` in `PoolState` over time.
3. The token issuer freezes the pool creator's associated token account for `token_0_mint` (out-of-band compliance action).
4. `pool_creator` calls `collect_creator_fee` (or anyone calls `collect_creator_fee_permissionless`); `creator_token_0` resolves to the frozen ATA (forced by `associated_token::authority = creator`), and the `transfer_checked` CPI in `transfer_from_pool_vault_to_user` fails because the destination account is frozen.
5. There is no instruction parameter or account substitution allowed to redirect the payout elsewhere, so `creator_fees_token_0` remains permanently locked in `token_0_vault`.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
