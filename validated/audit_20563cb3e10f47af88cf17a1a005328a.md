### Title
Path traversal via unsanitized release asset `Name` in `destinationWriter.makePath` - (File: pkg/cmd/release/download/download.go)

### Finding Description
`downloadRun` builds `downloadTarget.name` directly from the release asset's `Name` field returned by the GitHub API (`targets[i] = downloadTarget{... name: a.Name}` at [1](#0-0)  ). That name flows unchanged into `downloadAsset` → `dest.Check(fileName)` / `dest.Copy(fileName, ...)`, which call `destinationWriter.makePath`: [2](#0-1) 

`makePath` performs `filepath.Join(w.dir, name)` with no validation that the joined result stays within `w.dir`. `filepath.Join` cleans `..` segments arithmetically but does not confine the result to the base directory — `filepath.Join("dest", "../../etc/cron.d/x")` resolves to a path outside `dest`. Unlike the archive-derived filename path, which passes the server-supplied name through `filepath.Base(serverFileName)` before use ( [3](#0-2) ), the regular (non-archive) per-asset filename at line 197's `a.Name` never receives an equivalent `filepath.Base`/containment check. `os.MkdirAll(dir, 0755)` at [4](#0-3)  will even create the necessary parent directories to reach the escaped location, and `os.OpenFile(..., O_CREATE|O_TRUNC, 0644)` writes/overwrites the file there.

An attacker who controls a repository (or a fork) can publish a release and set an asset name containing path traversal sequences (e.g. `../../.ssh/authorized_keys` or an absolute path, subject to whatever GitHub's upload API permits in the `name` field) via the REST API. When the victim runs `gh release download` against that repo with no `--pattern` restricting to a safe match, `matchAny` is bypassed entirely (empty pattern list), and the file is written using the attacker-chosen relative path outside `--dir`.

Regarding the `matchAny`/`filepath.Match` half of the question: this is not exploitable. `filepath.Match(pattern, name)` ( [5](#0-4) ) only interprets glob metacharacters (`*`, `?`, `[...]`) that appear in the `pattern` argument; characters in the `name` argument are always compared literally, character-by-character, against the compiled pattern. An attacker cannot make an asset name "inject" glob semantics into the victim's `--pattern`, since the metacharacter scanning happens only over the pattern string. So no fail-open/unexpected-match condition exists there.

### Impact Explanation
This matches GitHub's "arbitrary file write/overwrite outside the intended path" impact class. A successful exploit lets an attacker-controlled release asset name write file content to attacker-chosen paths outside the user-specified `--dir` (e.g., overwriting dotfiles, shell profiles, or cron files reachable by traversal from the destination directory), which can lead to code execution if the victim later executes or sources the overwritten file.

### Likelihood Explanation
Preconditions: (1) the victim must run `gh release download` against a repository/release the attacker controls (their own repo, a fork, or a release the attacker can create), without narrowing via a `--pattern` that would exclude the malicious name; (2) GitHub's release-asset-upload API must accept a `name` value containing `/` or `..` sequences (this repo's code performs no server-side validation and relies entirely on GitHub's API acceptance, which is external to this codebase and not verifiable here). Given no client-side defense exists in `gh` itself, the likelihood is driven solely by whether GitHub's upload endpoint permits such names — a factor outside this repository's control but which this code fails to defend against regardless.

### Recommendation
In `destinationWriter.makePath` (or immediately when building `downloadTarget`/before `dest.Check`/`dest.Copy`), sanitize the asset name the same way the archive path already does: apply `filepath.Base(name)` (or reject names containing `/`, `\`, or resolving outside `w.dir` after `filepath.Clean`/`filepath.Abs` comparison) before joining with `w.dir`, and reject/skip assets whose sanitized name differs from the original in a way that indicates traversal.

### Proof of Concept
```go
func TestMakePath_PathTraversal(t *testing.T) {
    w := destinationWriter{dir: "safe-dest"}
    fp := w.makePath("../../etc/passwd-like-file")
    absDest, _ := filepath.Abs("safe-dest")
    absFp, _ := filepath.Abs(fp)
    if strings.HasPrefix(absFp, absDest) {
        t.Fatalf("expected escape, got confined path: %s", absFp)
    }
    // absFp will be outside absDest, demonstrating the missing containment check
}
```
Fuzz plan: generate asset names with `../`, absolute paths, and mixed separators; for each, compute `w.makePath(name)`, resolve to absolute path, and assert `strings.HasPrefix(abs(fp), abs(w.dir)+string(os.PathSeparator))`. The assertion fails for traversal payloads, confirming the missing confinement in `makePath`. (Separately, fuzzing `matchAny` with metacharacters embedded in `name` while holding `pattern` fixed confirms no anomalous match occurs, since `filepath.Match` only special-cases characters in `pattern`.)
