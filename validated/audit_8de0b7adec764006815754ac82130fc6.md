### Title
Webhook signature verification keys off an attacker-controlled `repository.owner.login` field while handlers act on a different `repository.full_name` field, enabling unauthenticated cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify a webhook against using a value pulled directly out of the unauthenticated request body, not from any trusted/authenticated source. Every webhook handler, however, resolves the actual `Stack`/`Repository` to act on using a *different* field from that same body. Because these two fields are never checked for consistency, and because `GithubApp#verify_webhook_signature` unconditionally passes when the resolved org has no configured `webhook_secret`, an attacker can forge a payload that "authenticates" as an org with a blank secret while writing to a completely different, victim repository's stacks.

### Finding Description
`WebhooksController` derives the organization used for signature verification straight from the JSON body: [1](#0-0) [2](#0-1) 

That `repository_owner` value is then used to look up which `GithubApp`/`webhook_secret` to check the `X-Hub-Signature` against. Critically, `verify_webhook_signature` short-circuits to `true` whenever the resolved app has no `webhook_secret` configured: [3](#0-2) 

This "no secret configured" state is a documented, supported configuration (e.g. `webhook_secret: nil`) for organizations onboarded without HMAC signing: [4](#0-3) 

Meanwhile, every webhook handler resolves which repository/stack to actually operate on using `repository.full_name` — a sibling field in the same JSON body that is never cross-checked against the `repository.owner.login` used for signature selection: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

This breaks the equality: `organization authenticated by verify_signature (repository.owner.login → app/secret lookup)` ≠ `repository actually written to by the handler (repository.full_name)`. An attacker only needs to know of any org configured in `Shipit.github` with a blank `webhook_secret` to set `repository.owner.login` to that org (satisfying signature verification unconditionally), while setting `repository.full_name` to any victim org/repo that has real Shipit stacks — with no signature, credential, or repository access required for the victim org.

### Impact Explanation
Once this bypass is achieved, the attacker can drive any handler against arbitrary victim repositories with no repository write access or webhook secret for that repository:
- `PushHandler` invokes `stack.sync_github(expected_head_sha:)` for every non-archived stack on the victim repo's branch, enqueuing `GithubSyncJob`, which fetches and appends new commits and can indirectly feed into continuous delivery scheduling.
- `PullRequest::OpenedHandler`/`ClosedHandler`/`ReopenedHandler`/`LabeledHandler` and `LabelCapturingHandler` create, archive, unarchive Review Stacks, and mutate pull-request labels for the victim repository purely based on the forged `full_name`.

This is a cross-repository write achieved without any credential belonging to the victim organization, matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
The only prerequisite is that at least one organization configured in the deployment's `Shipit.github` map has no `webhook_secret` set — a state explicitly present in this repo's own reference configs (`config/secrets.development.shopify.yml`) and permitted by `GithubApp#verify_webhook_signature`. No authentication, GitHub App private key, or Shipit session is required; the attacker only needs to send a single crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind signature verification to the same repository being acted upon: derive the signing organization from a value that cannot diverge from `repository.full_name`, or explicitly verify that `repository.owner.login` matches the owner segment of `repository.full_name`, rejecting requests where they differ. Additionally, reconsider allowing `webhook_secret` to be blank/optional — either require a secret for every org or, at minimum, refuse cross-field trust when it is absent.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `orgA` (attacker-known, `webhook_secret: nil`) and `victim-org` (has real stacks, `webhook_secret` set and unknown to attacker).
2. POST to `/webhooks` with header `X-Github-Event: pull_request` and body:
```json
{
  "action": "opened",
  "number": 1,
  "pull_request": { "id": 1, "number": 1, "url": "...", "title": "x", "state": "open",
                     "additions": 1, "deletions": 0,
                     "head": { "sha": "deadbeef", "ref": "feature" },
                     "user": { "login": "attacker" }, "assignees": [], "labels": [] },
  "repository": { "owner": { "login": "orgA" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
No `X-Hub-Signature` header is required, since `repository_owner` resolves to `orgA`, whose `webhook_secret` is blank, causing `verify_webhook_signature` to return `true` unconditionally.
3. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler` resolves `repository` via `params.repository.full_name` ("victim-org/victim-repo") and creates/unarchives a Review Stack for the victim repository, despite the request never being signed by `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
