Confirmed: `Commit#create_status_from_github!` (via `add_status`) writes directly to the commit's stack, with no check that the commit's stack/repository matches the organization whose webhook secret verified the request.### Title
Cross-organization commit status write via globally-scoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature using the GitHub App config keyed by `params.dig('repository','owner','login')` (the org named inside the attacker-supplied JSON body), i.e. it only proves the request bytes were signed with *some* org's webhook secret — the org that the attacker names and controls. `StatusHandler#process` then does `Commit.where(sha: params.sha)` with no scoping to that organization/stack, so if the `sha` happens to collide with a commit belonging to a different organization's stack, that unrelated commit's status gets overwritten.

### Finding Description
The broken binding, stated explicitly: **organization whose secret verified the request bytes (`OrgA`, derived from `repository_owner` in `WebhooksController#verify_signature`, app/controllers/shipit/webhooks_controller.rb:24-30,59-61) must equal the organization owning the `Commit` row selected by `Commit.where(sha: params.sha)` in `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) — but the code never checks this.** [1](#0-0) [2](#0-1) [3](#0-2) 

Path: the controller parses raw JSON, computes `repository_owner` purely from attacker-controlled JSON fields, fetches `Shipit.github(organization: repository_owner)`, and verifies the raw body's HMAC signature against that org's `webhook_secret`. Since HMAC verification only proves possession of `OrgA`'s secret (which the attacker legitimately has, per the threat model), the attacker can freely set every other field in the JSON body, including `sha`, to any value — nothing ties `sha` back to `repository_owner`/`OrgA`. `Commit.where(sha: params.sha)` in `StatusHandler#process` is a completely global, cross-tenant query with no `stack_id`/organization filter, and `commit.create_status_from_github!(params)` (app/models/shipit/commit.rb:165-169, delegating to `add_status`, lines 366-386) writes `state`/`description`/`target_url` and fires `commit_status`/`deployable_status` hooks on the matched commit, whatever stack/org it belongs to. [4](#0-3) 

Existing guards do not prevent this: `verify_signature` only checks the signature matches *a* valid webhook secret for the org named in the payload — it never cross-checks that org against the resolved `Commit`'s stack/repository. The `ExplicitParameters` schema (`requires :sha, String`) only validates type, not ownership. `drop_unhandled_event` and `check_if_ping` are unrelated. There is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

Exploit: attacker owns/administers a legitimate (or throwaway) GitHub App/org `OrgA` registered in Shipit with a known `webhook_secret`. They learn (or guess) the full 40-char SHA of a commit tracked by a private/target stack under `OrgB` (e.g., from a previously observed webhook, a leaked commit hash, GitHub search, etc. — feasibility of SHA discovery is explicitly assumed by the question, not something this analysis needs to prove further). They POST to `/webhooks` with `X-Github-Event: status`, body `{"repository": {"owner": {"login": "OrgA"}}, "sha": "<OrgB's commit sha>", "state": "success", ...}`, correctly HMAC-signed with `OrgA`'s secret. `verify_signature` passes (signature matches `OrgA`'s secret against these exact bytes). `StatusHandler#process` finds `OrgB`'s `Commit` row by global `sha` match and overwrites its status.

### Impact Explanation
This is a payload for one repository (`OrgA`) mutating another repository/organization's `Commit` record (`OrgB`) — matching the "Critical" category explicitly listed ("a payload for one repository mutating another's stack, commit, task or team"). An attacker can flip a victim stack's CI status to `success`, which can satisfy `deployable?`/`blocked?` gating (app/models/shipit/commit.rb:227-237) and trigger `ContinuousDeliveryJob`/merge scheduling (`schedule_continuous_delivery`, `stack.schedule_merges`), potentially causing an unauthorized deploy of `OrgB`'s stack if it uses commit-status-gated continuous deployment. This is repeatable against any commit whose SHA the attacker can learn, across arbitrary organizations/stacks configured in the same Shipit instance, since the query has no tenant boundary.

### Likelihood Explanation
Preconditions: the attacker must operate their own GitHub App/org (`OrgA`) already registered with valid `webhook_secret` in this Shipit instance — a low bar for any user with a Shipit-connected repo. They must know the exact full SHA of a target commit in `OrgB`'s stack — feasible for public repos, or via previously leaked/observed webhook data, GitHub notifications, etc. No privileged Shipit role, session, or API token is required. Attack is cheap (a single signed HTTP POST) and fully repeatable.

### Recommendation
In `StatusHandler#process` (and any other handler doing global `sha`/`repository`-independent lookups), scope the `Commit` query to the stack(s) belonging to the verified `repository_owner`/`repository.full_name`, e.g. join through `Stack`/`Repository` filtered by the organization that signed the request, or better, pass the verified repository context from the controller into the handler and require `commit.stack.repository.owner == verified_owner` (and ideally match `repository.full_name`, not just the owner) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from OrgA's verified webhook can overwrite OrgB's commit status" do
  org_b_stack = shipit_stacks(:cyclimse) # belongs to a different org/repo than :shipit
  victim_commit = org_b_stack.commits.create!(sha: 'f' * 40, message: 'victim commit')
  assert_equal 'unknown', victim_commit.state

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker/ci',
    'repository' => { 'owner' => { 'login' => 'shopify' } } # OrgA, attacker's org, whose secret signs this request
  }.to_json

  # Signature computed with OrgA's ("shopify") webhook_secret over `body`, verified via Shipit.github(organization: 'shopify')
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # or compute real HMAC with shopify's secret in fixtures

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end

  victim_commit.reload
  assert_equal 'success', victim_commit.state # OrgB's commit mutated by an OrgA-signed request
end
```
Assertion on both sides of the equality: before the request, `victim_commit.stack` (`OrgB`) has no relationship to `repository_owner` (`OrgA`) used in `verify_signature`; after the request, `victim_commit.state` has changed to the attacker-supplied `success`, proving the write crossed the tenant boundary despite `repository_owner` (`OrgA`) ≠ `victim_commit.stack`'s owning organization (`OrgB`).
