### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login`/`organization.login` field while all event handlers act on a separate, unchecked `repository.full_name` field, letting an attacker with valid webhook credentials for one configured organization forge events against a completely different repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC against using `repository_owner`, a value taken straight from the untrusted request body (`params.dig('repository','owner','login')` or `organization.login`). Once the signature check passes, `create` re-parses the same raw body and dispatches it to handlers that resolve the target `Stack`/`Repository` using a *different* field of the same payload: `repository.full_name`. Nothing ties these two fields together, so authentication (which org's secret validated the request) and authorization (which repository/stack the request is allowed to mutate) are decoupled.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` picks the verifying `GitHubApp` via `Shipit.github(organization: repository_owner)`, where `repository_owner` comes from the payload itself: [1](#0-0) 
- `GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb:76-83` trivially returns `true` when `webhook_secret` is blank - and per `docs/setup.md`, `webhook_secret` is documented as **optional**: [2](#0-1) [3](#0-2) 
- Every handler resolves the target repository from a *separate* field, `repository.full_name`, with no cross-check against the value used for authentication: [4](#0-3) 
- Downstream, e.g. `PushHandler#process`, uses that repository lookup to trigger a real GitHub sync on matching stacks: [5](#0-4) 

This is the same class of bug as the TrueFi/AlphaBetaSplitter finding: one component assumes a value returned/validated by another component reflects the full/true state (`withdrawAll` return == balance withdrawn), but the two are computed independently and can diverge. Here, "the organization that authenticated" (`repository_owner`) is assumed to equal "the repository being written to" (`repository.full_name`'s owner segment), but the code never enforces that equality - both are read from the same attacker-supplied JSON body independently.

In a multi-org Shipit deployment (`config/secrets.yml` with multiple top-level org keys, as documented in `docs/setup.md:182-209` and exercised by `test/dummy/config/secrets_double_github_app.yml`), each organization can have its own `webhook_secret`, and it is documented as optional per organization. An attacker who can produce a valid signature for **any one** configured organization (e.g., an org with no `webhook_secret` set, or one whose secret has otherwise leaked/is known to them) can set `repository.owner.login` to that organization to pass `verify_signature`, while setting `repository.full_name` to `"other-org/other-repo"` — a completely unrelated, victim repository tracked by the same Shipit instance. The `create` action never re-validates that these two fields agree: [6](#0-5) 

### Impact Explanation
This breaks the equality that should hold: `organization that authenticated == owner of repository that is written`. Successful exploitation lets an unprivileged external attacker forge `push`, `status`, `check_suite`, `pull_request`, or `membership` webhook events against a target stack/repository they do not own or have write access to, as long as any organization on the same Shipit instance has a blank/known webhook secret. Concretely this can:
- Trigger `PushHandler` → `stack.sync_github(expected_head_sha: ...)` for the victim's stack [5](#0-4) 
- Inject forged commit statuses via `StatusHandler` for arbitrary commits [7](#0-6) 
- Interfere with `pull_request`/`check_suite`/merge-related handlers, which can influence the automatic merge queue and deploy triggers.

Because this can lead to unauthorized state changes (forged commit checks, triggered syncs feeding into deploy pipelines) on a repository/stack the attacker doesn't control, it aligns with the "unauthorized deploy" / cross-repository-write class of impact called out in scope.

### Likelihood Explanation
Exploitability depends on the deployment having multiple GitHub Apps configured (a documented, supported configuration) and at least one of them having no `webhook_secret` set (explicitly documented as optional) or a leaked/guessable secret. No privileged Shipit session, `ApiClient` token, or repository write access is required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and (if needed) a valid signature for the weaker org. This is a real, root-caused code defect (independent, unvalidated fields) rather than a theoretical concern, but its blast radius is gated by multi-org setups with an unsecured or compromised secondary secret.

### Recommendation
Do not let the payload itself choose the security boundary used to authenticate it. After parsing and verifying, re-derive the acted-upon `repository.full_name`'s owner and assert it matches the organization whose secret validated the signature (i.e., check `repository.full_name.split('/').first == repository_owner` before dispatching to handlers). Additionally, treat `webhook_secret` as effectively mandatory (or emit hardened warnings / reject requests) for any organization configuration, since a blank secret makes `verify_webhook_signature` unconditionally return `true` (`lib/shipit/github_app.rb:76-77`), which undermines the entire signature-verification mechanism for that org and, transitively, for any other org's repositories that can be referenced in the same payload.

### Proof of Concept
1. Deploy Shipit with the multi-org github config shown in `docs/setup.md:182-209`, where `OrgA` has `webhook_secret:` left blank (documented optional) and `OrgB` (the real target, with stacks configured) has a secret set.
2. Attacker sends:
   ```
   POST /webhooks
   X-Github-Event: push
   X-Hub-Signature: sha1=anything   # ignored, since OrgA has no secret
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha-that-exists-on-OrgB-repo>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`; because `OrgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the actual signature header [8](#0-7) .
4. `create` dispatches the same JSON to `PushHandler`, whose `Handler#repository_name` reads `"OrgB/victim-repo"` from `payload.dig('repository','full_name')`, resolves `OrgB`'s real stacks, and calls `stack.sync_github(expected_head_sha: params.after)` [4](#0-3) [5](#0-4) .
5. The attacker has now forced a GitHub sync (and can similarly forge `status`/`check_suite` events) against `OrgB/victim-repo`, a repository they have no legitimate access to, purely by exploiting the mismatch between the field used to authenticate (`repository.owner.login`) and the field used to select the write target (`repository.full_name`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
