### Title
Cross-organization webhook forgery — `repository.owner.login` used to select the signing secret is never checked against `repository.full_name` used to select the target repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization deployments, `Shipit.github(organization: repository_owner)` picks *which* GitHub App's `webhook_secret` verifies the HMAC signature, using `repository.owner.login` (or `organization.login`) from the payload [1](#0-0) . Once the signature checks out, the whole raw payload (including an independent `repository.full_name` field) is handed unchanged to the event handlers, which resolve the *target* repository/stack purely from `repository.full_name` [2](#0-1) . Nothing ties `repository.owner.login` to `repository.full_name`. An attacker who legitimately controls a webhook delivery for org A (i.e., knows org A's `webhook_secret`) can therefore sign a payload whose `repository.owner.login` is "org A" (so the signature check passes) but whose `repository.full_name` is "orgB/some-repo", causing Shipit to act on a completely unrelated organization's repository.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload itself: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and uses it only to look up which App config's `webhook_secret` to HMAC-verify against [3](#0-2) . `Shipit.github(organization:)` and `Shipit.github_app_config` fetch a distinct config (and thus a distinct `webhook_secret`) per organization key in `secrets.github` [4](#0-3) .

After verification succeeds, `WebhooksController#create` dispatches the *entire, attacker-controlled* JSON body to the registered handlers unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) . The base `Handler` class (used by `PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::EditedHandler`, etc.) resolves the stack/repository purely via `payload.dig('repository', 'full_name')` and `Repository.from_github_repo_name(repository_name)` [2](#0-1) , `Repository.from_github_repo_name` simply splits `"owner/name"` and does a plain DB lookup with no relation to which App/secret validated the request [6](#0-5) .

Binding broken: the organization that authenticated the webhook (`repository.owner.login` used to pick the `webhook_secret`) ≠ the repository that is actually written to (`repository.full_name` used by the handler). Since the signature is only proof of "this body was produced by someone possessing org A's secret," and nothing in the verification step or the handler re-checks that `full_name`'s owner segment equals the org that was used to select the secret, a party with a valid secret for org A can forge events attributed to org B, C, etc., as long as those repositories/stacks are also tracked by the same Shipit install (a realistic scenario for shared multi-tenant Shipit instances, which is the explicit use case documented for the multi-org config schema) [7](#0-6) .

### Impact Explanation
This is a cross-repository write achieved without any credential belonging to the victim organization:
- `StatusHandler` will create arbitrary CI statuses on any commit `sha` matching records across the whole instance, since it doesn't even filter by full_name and just does `Commit.where(sha: params.sha)` [8](#0-7)  — letting an attacker mark someone else's commit "success", which is used by `MergeRequest#all_status_checks_passed?` and `Stack#deployable?` to gate merges/deploys.
- `PushHandler` can trigger `GithubSyncJob` for any stack whose repository matches the forged `full_name`, and `PullRequest::OpenedHandler`/`EditedHandler` can create/modify `PullRequest`/review-stack records tied to org B's repositories [9](#0-8) .

This matches the "cross-repository writes" and "escalation into authorization"-class impacts, because it allows an attacker with only org-A-level webhook access to affect the deployable/merge state of org B's repositories that they have no legitimate access to.

### Likelihood Explanation
Requires the deployment to run in the documented multi-organization mode (`secrets.github` keyed by org, each with its own `webhook_secret`) and requires the attacker to already have legitimate ability to produce a correctly-signed webhook for *some* org served by that Shipit instance (e.g., they administer a repo in org A and can view/replay its webhook secret, or they set up their own low-privilege webhook endpoint using an org they control). Given this is exactly the documented multi-tenant configuration pattern in this engine, likelihood is realistic wherever multiple orgs are hosted on one Shipit instance.

### Recommendation
After verifying the signature, re-derive/validate that `repository.full_name`'s owner segment matches the `repository_owner` that was used to select the verifying secret (or reject payloads where they diverge) before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two orgs, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret` (per the documented multi-org `secrets.yml` schema).
2. Attacker administers a repo under `orgA` (or otherwise knows `orgA`'s `webhook_secret`, e.g., via a webhook they configured themselves for their own repo).
3. Attacker crafts a `status` (or `push`/`pull_request`) event JSON body where `repository.owner.login` = `"orgA"` but `repository.full_name` = `"orgB/victim-repo"`, and a `sha` matching a commit belonging to `orgB/victim-repo`.
4. Attacker signs the raw body with `orgA`'s `webhook_secret` and POSTs it to `/github_webhooks` (or the Shipit webhooks endpoint) with `X-Hub-Signature`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s app/secret, and the signature validates successfully.
6. `StatusHandler#process` (or the relevant handler) then executes against `Commit.where(sha: ...)` / `Repository.from_github_repo_name("orgB/victim-repo")`, mutating state for `orgB`'s stack despite the request only being authenticated for `orgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
