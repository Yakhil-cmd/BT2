### Title
Payload-controlled `repository_owner` + global `Commit.where(sha:)` lookup lets a forged webhook mark an arbitrary victim commit deployable - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` derives the GitHub App/secret used to validate the HMAC solely from the attacker-supplied JSON body (`repository.owner.login`), and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org's `webhook_secret` is unset, and only checks the `sha1=` prefix otherwise. `Webhooks::Handlers::StatusHandler#process` then applies the `status` payload to `Commit.where(sha: params.sha)` with **no scoping to the repository/owner that was actually verified**, so a forged event "verified" against one (secret-less or attacker-chosen) organization can still mutate a commit belonging to a completely different, victim repository.

### Finding Description
The broken binding is: *the organization whose secret verified the signature* should equal *the organization/repository whose commit gets mutated*. In this code that equality does not hold.

1. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes:
   ```ruby
   github_app = Shipit.github(organization: repository_owner)
   verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
   ```
   where `repository_owner` (`webhooks_controller.rb:59-62`) is read straight from the untrusted JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')`. The attacker fully controls which org's secret is used to "verify" their own forged body.

2. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`):
   ```ruby
   def verify_webhook_signature(signature, message)
     return true unless webhook_secret
     algorithm, signature = signature.split("=", 2)
     return false unless algorithm == 'sha1'
     SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
   end
   ```
   If the org resolved in step 1 has no `webhook_secret` configured, verification is skipped entirely (`return true unless webhook_secret`) — any body/signature is accepted. It also only ever validates the legacy `sha1=` prefix, never `sha256=`.

3. `Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
   ```ruby
   def process
     Commit.where(sha: params.sha).each do |commit|
       commit.create_status_from_github!(params)
     end
   end
   ```
   This performs a **global** lookup by `sha` across every tracked repository/stack in the installation — it never filters by the repository/owner that `verify_signature` checked.

Exploit flow: the attacker crafts a `status` webhook body where `repository.owner.login` (or `organization.login`) names any org configured in Shipit that has no `webhook_secret` set (a plausible, unprivileged-observable configuration in any multi-org Shipit deployment, or reachable if the attacker owns/controls that secret-less org's repo and can freely trigger webhooks there), sets `sha` to the victim commit's real SHA (observable via GitHub, e.g. a PR on the real repo), and `state: "success"` with the `context` matching a required status check. Because signature verification passes trivially for the secret-less org, and the handler updates commits purely by `sha` with no cross-check against the org that was verified, the victim's commit — belonging to an entirely different repository/stack — gets a forged successful status, which can make it deployable and shippable.

Existing guards do not stop this: `drop_unhandled_event` only filters unregistered events (status is registered), `ExplicitParameters` only validates shape (`sha`, `state`, etc.) not repository identity, and there is no `Repository`/`Stack` ownership check anywhere in `StatusHandler`.

### Impact Explanation
An unprivileged attacker can inject a fabricated "success" status onto any known commit SHA in any repository/stack tracked by the Shipit instance, without needing that repository's or org's webhook secret. This can satisfy Shipit's deploy-gating status checks and enable an unauthorized deploy of attacker-influenced (or simply attacker-chosen, potentially malicious) code for a repository they do not own — matching the Critical category ("a payload for one repository mutating another's stack, commit, task" / "unauthorized deploy"). The attack is repeatable against any commit SHA and is not limited to a single stack.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one GitHub org/app configured without a `webhook_secret` (config-dependent, but plausible and the code explicitly allows it via `@webhook_secret = @config[:webhook_secret].presence`), and the attacker must know the target commit's SHA and a status `context` used as a required check (both are typically public/observable on GitHub). No Shipit session, token, or GitHub secret is required — only the ability to send an HTTP POST to `/webhooks`. Cost is a single crafted HTTP request; it is fully repeatable.

### Recommendation
- Do not derive the verifying org/secret from attacker-controlled payload fields alone without cross-checking the resulting repository against the one actually mutated.
- Fail closed (reject, don't `return true`) when `webhook_secret` is not configured for an org, or require a secret for every configured org.
- Support/require `X-Hub-Signature-256` (sha256) verification.
- In `StatusHandler#process`, scope the `Commit` lookup to the repository identified in the (verified) payload rather than a global `sha` match across all tracked repositories.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` (or a new test) that:
1. Configures two orgs in `Shipit.github_apps`/`app_configs`: `victim-org` (with a real `webhook_secret`) and `attacker-org` (no `webhook_secret`).
2. Creates a `Stack`/`Repository` under `victim-org` and a `Commit` with a known `sha` that is currently not deployable (no successful status).
3. POSTs to `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature: sha1=deadbeef` (or omitted), and a JSON body:
   ```json
   { "repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim sha>", "state": "success", "context": "required-check" }
   ```
4. Assert the request returns `200`.
5. Reload the victim `Commit` and assert `commit.statuses.where(context: "required-check", state: "success").exists?` is now `true` (or that `commit.deployable?` flips to `true`) — proving a forged, unauthenticated webhook mutated a record belonging to a repository/org (`victim-org`) whose secret never verified it, matching the binding violation identified above (equality of "verifying org" vs. "mutated repository" is false).
