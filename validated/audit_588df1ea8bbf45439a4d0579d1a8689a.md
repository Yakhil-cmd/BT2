### Title
`allowance = 0` on gas key add is silently coerced to unlimited allowance instead of a zero allowance - (File: runtime/near-vm-runner/src/wasmtime_runner/logic.rs)

### Summary
The host function `promise_batch_action_add_gas_key_with_function_call` converts the caller-supplied `allowance` value of `0` into `None`, which for a `FunctionCallPermission` means "no allowance limit" (unlimited spending), not "zero allowance." This mirrors the reported PairInfos.sol bug class: a `> 0` gating check silently discards the caller's intent to set a value to `0`, causing the value to be interpreted completely differently than the caller expects.

### Finding Description
In `promise_batch_action_add_gas_key_with_function_call`:

```rust
let allowance = Balance::from_yoctonear(get_u128(
    &mut ctx.result_state.gas_counter,
    memory,
    allowance_ptr,
)?);
let allowance = if allowance > Balance::ZERO { Some(allowance) } else { None };
``` [1](#0-0) 

This is analogous to the `PairInfos.sol` bug: a check gating on "greater than 0" is used to decide whether to apply a caller-supplied value, and when the caller explicitly passes `0`, the check causes a different value (`None`) to be recorded instead of the literal `0` the caller specified.

For `FunctionCallPermission.allowance`, `None` is documented and treated elsewhere in the codebase as "unlimited allowance" rather than "no allowance" — e.g. the verifier only performs allowance-balance checks when `allowance` is `Some`, and skips balance restriction entirely when `None`: [2](#0-1) 

So a contract that intends to add a gas key with `allowance: 0` (i.e., "this key must not be allowed to spend anything via function-call permission, only used for gas-key-balance-funded calls, or as a deliberate zero-cap key") instead receives an access key with an **unlimited** function-call allowance. This is a semantics inversion caused directly by the `> 0` gate, exactly like the reported issue where `feeIndex`/`groupIndex` could not be set to `0`.

### Impact Explanation
If a contract (e.g. a wallet contract, meta-transaction relayer, or any dApp that programmatically provisions access keys via `promise_batch_action_add_gas_key_with_function_call`) intends to create a heavily restricted or "disabled-until-funded" key by passing `allowance = 0`, the runtime instead silently grants that key an unlimited `FunctionCallPermission` allowance. This is an unintended and unauthorized privilege/balance escalation: the resulting access key can spend without the intended cap, which can lead to unauthorized balance draining of the account through the access key's function-call allowance path, contradicting the contract author's explicit intent. This is a state/permission divergence from what the caller requested and can facilitate unauthorized balance change.

### Likelihood Explanation
Likelihood is moderate: it requires a contract to deliberately (or accidentally) pass `allowance = 0` to this host function, which is a plausible input (zero is the natural "no allowance" sentinel a contract author would choose, not realizing `None`/unlimited is the actual "no restriction" semantic in this API). Any account can trigger this via a function call to a contract that calls this host function; no privileged accounts are needed since this is a standard promise-batch host action available to any WASM contract during a function call execution.

### Recommendation
Do not coerce `allowance == 0` to `None`. Preserve the literal value passed by the caller (`Some(Balance::ZERO)` when zero is passed), or if `0` must map to "unlimited" by design, document this loudly in the host function's doc comment and provide contract-facing guidance/tests to prevent misuse. The safest fix, consistent with removing the incorrect `> 0` gate (as recommended in the referenced report), is:
```rust
let allowance = Some(allowance); // preserve exact value, including 0
```
and adjust downstream verifier/action logic if a distinct "unlimited" sentinel is still needed (e.g., use a separate flag/enum instead of overloading `None`/`Some(0)`).

### Proof of Concept
1. Deploy a contract that, in a function call, executes:
```rust
promise_batch_action_add_gas_key_with_function_call(
    promise_idx,
    public_key,
    num_nonces,
    /* allowance = */ 0u128,
    receiver_id,
    method_names,
);
```
2. Query the resulting access key via view client / RPC (`view_access_key`) for the new public key.
3. Observe the returned `AccessKeyPermissionView::GasKeyFunctionCall { allowance, .. }` field is `None` (unlimited) rather than `Some(0)` (as demonstrated by the existing test `test_gas_key_add_function_call_host_function`, which explicitly asserts `allowance.is_none()` when the contract passes `"allowance": "0"`): [3](#0-2) 
4. This confirms that a contract's explicit request for a zero allowance is silently converted into an unlimited allowance grant, a direct behavioral analog of the reported `feeIndex`/`groupIndex` zero-value bug.
