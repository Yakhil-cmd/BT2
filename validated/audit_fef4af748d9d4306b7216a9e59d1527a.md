### Title
`OpenedHandler#provision?` operator-precedence bug provisions review stacks despite `review_stacks_enabled == false`; combined with unauthenticated forged `pull_request` webhooks, an attacker can create a `ReviewStack` and inject uppercased env keys via labels - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/review_stack.rb`)

### Summary
`OpenedHandler#provision?` uses `a && b || c || d` where Ruby's operator precedence causes `review_stacks_enabled` to gate only the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches, so a stack can be provisioned even when `review_stacks_enabled` is `false`. This is reachable through `POST /webhooks`, and `LabelCapturingHandler` later persists attacker-supplied label names onto the `PullRequest`, which `ReviewStack#env` turns into uppercased environment variables merged into the deploy environment.

### Finding Description
The broken binding: the intended invariant is `provision? == (repository.review_stacks_enabled && provisioning_behavior_matches?)`, i.e. `review_stacks_enabled` must gate *every* provisioning path. The actual code in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||` in Ruby, this parses as:

```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```

so with `review_stacks_enabled == false`, `provisioning_behavior == allow_with_label`, and the PR carrying the configured provisioning label (attacker's own label on their own PR), `provision?` still returns `true` and a brand-new `ReviewStack` is created via `ReviewStackAdapter#find_or_create!`. This same unguarded pattern also exists in `unlabeled_handler.rb`/`reopened_handler.rb`'s `pull_request_has_provisioning_label?`-style checks but those are additionally gated by `repository.review_stacks_enabled` in `respond_to_label_change?`/`unarchive?` at the top level — only `OpenedHandler#provision?` has the mis-precedence directly inline.

The reachable path: `POST /webhooks` → `Shipit::WebhooksController#create` → `Shipit::Webhooks.for_event('pull_request')` → `OpenedHandler.call(params)` for `action == "opened"`. Before reaching the handler, `verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login')` [2](#0-1)  and `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank: [3](#0-2) . Note that `repository.full_name`, used by the handler to resolve the actual `Repository`/`Stack` (`Shipit::Repository.from_github_repo_name(params.repository.full_name)`), is a *separate* attacker-controlled field from `repository.owner.login` used for signature verification, so the org that "authenticates" the request need not be the org that owns the affected repository.

Once a stack is created, `LabelCapturingHandler` persists `params.pull_request.labels.map(&:name)` onto `stack.pull_request`: [4](#0-3) . Those labels are later merged as uppercased environment variables in `ReviewStack#env`: [5](#0-4) .

Existing guards fail because:
- `verify_signature` only checks HMAC against the org named in `repository.owner.login`, not the org actually referenced by `repository.full_name` used downstream.
- `review_stacks_enabled` is intended as the master provisioning switch, but the precedence bug only applies it to the `allow_all` behavior.

### Impact Explanation
An attacker who can name a label on their own PR and knows (or guesses) the repository's `provisioning_label_name` can force creation of a `ReviewStack` for a repository that has explicitly disabled review stacks (`review_stacks_enabled == false`), bypassing the operator's intended control. The created stack's provisioning workflow runs (`stack.provisioner.up`), and attacker-controlled label names become environment variables consumed by that stack's deploy commands, which is a config/command-injection surface once mixed with `Command#args`/`PTY.spawn` executed environment during provisioning. Repeatable against any repository configured with `allow_with_label` or `prevent_with_label` behavior irrespective of `review_stacks_enabled`. This matches "a payload for one repository mutating another's stack" / unauthorized provisioning category if combined with cross-org signature bypass, though the full RCE chain (arbitrary command execution via label-derived env var) was not verifiable from the available files — `Stack#env` merge into `Command#args`/`PTY.spawn` was not confirmed within available context.

### Likelihood Explanation
Preconditions: (1) Shipit configured in multi-org mode with at least one org whose `webhook_secret` is blank — this is an operator misconfiguration, not something the attacker controls; (2) target repository has `provisioning_behavior` of `allow_with_label` or `prevent_with_label` with `review_stacks_enabled == false` (an intentional but incorrectly-enforced setting); (3) attacker can open a PR with a chosen label against that repository, or forge the JSON payload directly to `/webhooks` if the no-secret-org condition holds. Attacker cost is low (one HTTP request or one PR label) but the underlying precondition (an org with no `webhook_secret` configured) is an unusual/misconfigured deployment, which materially lowers real-world likelihood.

### Recommendation
Fix the operator precedence in `OpenedHandler#provision?` (and equivalents) by explicitly parenthesizing so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Additionally, `verify_signature` should validate that `repository.full_name`'s owner matches the org used for HMAC verification (`repository.owner.login`), rejecting payloads where the two diverge, and Shipit should refuse to start (or should treat as globally public) any org config where `webhook_secret` is blank in multi-org mode.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does NOT create/provision a stack when review_stacks_enabled is false, even with matching label (regression for precedence bug)" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [{ "name" => "pull-requests-label" }]

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding under test: `provision? == (review_stacks_enabled && provisioning_behavior_matches?)`. Before the fix, this assertion fails (a stack IS created) because `provision?` evaluates to `true` due to the precedence bug even though `review_stacks_enabled == false`. After applying the parenthesization fix, the assertion passes.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
