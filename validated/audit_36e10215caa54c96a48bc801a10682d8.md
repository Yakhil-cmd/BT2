### Title
Unhandled assertion crash from chained parameterized-AA (`base_aa`) triggers - (File: aa_composer.js)

### Summary
The CVE describes a systemd assert crash triggered when two independently valid unit settings (`Delegate=yes` and `User=<unset>`) are combined in a way the code didn't anticipate. The analogous pattern in `ocore` is an internal invariant enforced via `throw Error(...)` in the AA (Autonomous Agent) trigger-execution engine, which can be violated by a permissionless combination of AA definitions, causing every full node executing the trigger deterministically to crash.

### Finding Description
In `handleTrigger()`, when an invoked AA is a "parameterized AA" (has a `base_aa` field), the code enforces the invariant that params must be empty at that point: [1](#0-0) 
```
	var template = arrDefinition[1];
	if (template.base_aa) { // parameterized AA
		if (params && Object.keys(params).length > 0)
			throw Error("unexpected params");
		storage.readAADefinition(conn, template.base_aa, mci, function (arrBaseDefinition) {
			if (!arrBaseDefinition)
				throw Error("base AA not found: " + template.base_aa);
			console.log("redirecting to base AA " + template.base_aa + " with params " + JSON.stringify(template.params));
			trigger_opts.params = template.params;
			trigger_opts.arrDefinition = arrBaseDefinition;
			handleTrigger(trigger_opts);
		});
		return;
	}
``` [2](#0-1) 

This code assumes a parameterized AA's `base_aa` always points directly to a non-parameterized (base) AA, so that when it redirects with `trigger_opts.params = template.params`, the *next* recursive call to `handleTrigger` will see a non-parameterized definition and never re-enter this branch with a non-empty `params`. However, nothing in the definition/redirect path stops one parameterized AA (`AA1`, with `base_aa: AA2`) from pointing at another parameterized AA (`AA2`, with `base_aa: AA3`). A trigger to `AA1`:
1. Enters `handleTrigger` with `params = {}` (a primary trigger always starts with empty params) — passes the check since `params` is empty.
2. Sets `trigger_opts.params = template.params` (AA1's non-empty params) and `trigger_opts.arrDefinition = AA2's definition`, then recurses.
3. On the recursive call, `template = AA2's definition`, which itself has `base_aa: AA3`. Now `params` is AA1's (non-empty) params, so the guard `throw Error("unexpected params")` fires.

This assertion is purely an internal consistency check with no validation-time equivalent preventing the chained configuration — my search did not find any guard in `aa_validation.js`/`validation.js` blocking a `base_aa` AA from itself being the `base_aa` target of another AA. Because AA definitions and triggers are posted by ordinary, unprivileged users/authors and execution of AA triggers happens deterministically on every full node once the triggering unit is stable, this uncaught `throw Error` propagates out of the async callback chain in `handlePrimaryAATrigger` with no local `try/catch`. Uncaught exceptions in the network layer are explicitly re-thrown to crash the whole process: [3](#0-2) 

### Impact Explanation
Because AA trigger execution is part of consensus (every full node re-executes stable triggers identically), a crafted definition/trigger pair that hits this invariant would crash **every full node** that processes the stable trigger, not merely a single peer. This matches the CVE's impact class of "an assert...when a...unit is running": a deterministic, network-wide denial: nodes repeatedly crash on restart-and-replay of the same stable AA trigger, halting confirmation of new units for the whole network — one of the accepted "node disagreement on validity/stability, or a network unable to confirm new units" outcomes.

### Likelihood Explanation
Reaching this code path requires only unprivileged, permissionless actions available to any user:
1. Post an AA definition `AA3` (base AA).
2. Post an AA definition `AA2` that is `{ base_aa: AA3, params: {...} }`.
3. Post an AA definition `AA1` that is `{ base_aa: AA2, params: {...} }` (a parameterized AA pointing at another parameterized AA).
4. Send any payment/trigger to `AA1`.

No special privileges, hub/peer compromise, or malformed protocol messages are needed — just ordinary AA definition and trigger posting, which is exactly the "unprivileged unit poster / AA author / AA trigger sender" reachability the rules call out.

### Recommendation
- Add explicit validation (in `aa_validation.js`) rejecting an AA definition whose `base_aa` target is itself a parameterized AA (i.e., disallow chains of `base_aa`), so this configuration can never be defined in the first place.
- Additionally, harden `aa_composer.js`'s `handleTrigger` to fail the trigger gracefully (e.g., treat it as a bounce/unit error) instead of `throw Error("unexpected params")`, so that even if such a chain is ever created (e.g., via a pre-existing/legacy AA or future validation regression), it cannot crash the node process.

### Proof of Concept
1. Post AA definition `AA3` — any valid base (non-parameterized) AA definition, e.g. a trivial `{ messages: [...] }` AA.
2. Post AA definition `AA2 = ["autonomous agent", { base_aa: AA3, params: { p: 1 } }]`.
3. Post AA definition `AA1 = ["autonomous agent", { base_aa: AA2, params: { p: 2 } }]`.
4. Send a payment/trigger unit to `AA1`.
5. When the trigger becomes stable and `handleAATriggers()` → `handlePrimaryAATrigger()` → `handleTrigger()` executes it, the first redirect (AA1→AA2) succeeds because the initial trigger `params` is `{}`; the second redirect step (now trying to further redirect AA2→AA3) finds `params` (previously set to AA1's `template.params`) non-empty and executes `throw Error("unexpected params")` at aa_composer.js line 435, an uncaught exception that reaches `process.on('uncaughtException', ...)` in `network.js` (lines 4530–4543), which re-throws to crash the process — reproducibly, on every full node that processes this stable trigger.
