## Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` binding mismatch in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook based on `repository.owner.login` (or `organization.login`), but the handler that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target repository/stack from a *different* JSON field, `repository.full_name`. Nothing binds these two fields together, so a party who legitimately controls the webhook secret for one configured GitHub organization can forge a payload whose signature validates against their own secret while `repository.full_name` points at a `Stack` belonging to a completely different organization configured in the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App/secret purely from `repository_owner`: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature is verified with `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, which fetches per-organization secrets from `secrets.github[organization]` in a multi-tenant configuration: [3](#0-2) 

Once the signature passes, `create` dispatches the *entire raw payload* to handlers: [4](#0-3) 

But every handler (e.g. `PushHandler`) resolves which `Stack`/`Repository` to mutate using a *different* field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` does a bare lookup by `owner/name` split out of `full_name`, with no cross-check against `repository.owner.login`: [7](#0-6) 

The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization implied by repository.full_name used to select the Stack`.

This equality is never enforced anywhere in the request pipeline. An attacker who is an authorized webhook sender for OrgA (i.e., knows/controls OrgA's `webhook_secret`, which is intentionally shared with each tenant organization when Shipit is configured with the multi-org schema shown in `secrets.development.example.yml`) can sign a payload where `repository.owner.login = "orgA"` (to pass signature verification) but `repository.full_name = "orgB/victim-repo"` (to make the handler act on OrgB's stack).

### Impact Explanation
This crosses an authentication boundary between tenants: a webhook sender is only supposed to be trusted for events concerning their own organization's repositories, since that is the entire purpose of assigning a distinct `webhook_secret` per organization. By exploiting the field mismatch, OrgA's trusted sender can trigger `PushHandler#process` against a stack it does not own, which calls `stack.sync_github(expected_head_sha: ...)`, queuing `GithubSyncJob` for the victim's stack. This causes the victim stack to fetch and append attacker-influenced commit metadata (`expected_head_sha`) and, depending on downstream logic (deploy triggers on branch push, review-stack creation via `pull_request` handlers using the same `repository.full_name`-based lookup, `membership`/team sync using `organization.login`), can escalate into unauthorized syncs, spurious deploy triggers, or state corruption for a repository the attacker has no legitimate relationship with — a cross-repository/cross-tenant write performed under someone else's trust boundary. This matches the "Critical: cross-repository writes" impact category.

### Likelihood Explanation
Exploitability requires: (1) Shipit configured with the multi-organization GitHub schema (each org with its own `webhook_secret`, as documented and supported by `Shipit.github_app_config`), and (2) the attacker being a legitimate holder of one tenant org's webhook secret (e.g., an org admin who set up their own GitHub App integration, which is by design an "unprivileged" actor relative to any other tenant org on the same Shipit instance). Given that per-repo/per-org webhook secrets are explicitly a supported deployment model and no additional verification ties `repository.owner.login` to `repository.full_name`, likelihood is realistic in any multi-org deployment. In the common single-organization deployment this specific analog collapses (there is only one secret/org), which reduces but does not eliminate risk, since `check_suite`/`status`/`membership` handlers also trust payload-provided identifiers without cross-checking `repository_owner`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`/`#repository_name`), enforce that the organization portion of `repository.full_name` (and `organization.login` for org-scoped events) matches `repository_owner` used to select the verifying secret; reject the request (HTTP 422) on mismatch. Prefer deriving the authorized organization once and passing it explicitly into handlers instead of re-deriving repository/organization identity from independent, unauthenticated-relative-to-each-other payload fields.

### Proof of Concept
1. Configure Shipit with the multi-org schema: `secrets.github.orgA.webhook_secret = S_A`, `secrets.github.orgB.webhook_secret = S_B`, each org has its own installed GitHub App and Shipit stacks (e.g., `orgB/victim-repo`).
2. Attacker (an OrgA admin, knows `S_A`) crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, which resolves to `S_A`, and the HMAC check passes.
5. `PushHandler#process` is invoked with the full payload; `Handler#repository_name` returns `"orgb/victim-repo"`, `Repository.from_github_repo_name` finds `orgB`'s repository, and `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` is queued for OrgB's stack — despite the request never being authenticated for OrgB.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
