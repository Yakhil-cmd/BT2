### Title
Unlocked concurrent AA dry-runs corrupt shared in-memory unstable-unit/free-list caches (`storage.assocUnstableUnits`/`assocBestChildren`) - (File: aa_composer.js)

### Summary
The Xen CVE is a race condition in the grant-table free-list handling: concurrent maptrack operations without adequate locking corrupt the free list, causing crashes or privilege escalation. ocore has an analogous shared, mutable, node-global "free list"-like structure — `storage.assocUnstableUnits` / `storage.assocBestChildren` (tracking which units are `is_free`, best-parent/best-child relationships used for MC/stability calculations) — that is mutated by `aa_composer.dryRunPrimaryAATrigger()` without holding the `write` mutex that normally serializes all such mutations.

### Finding Description
Any peer (including unprivileged light clients) can trigger `dryRunPrimaryAATrigger()` via the `light/dry_run_aa` network command [1](#0-0) , or it is invoked internally while validating an incoming unit (`conf.bDryRunNewTriggers` path) [2](#0-1) .

`dryRunPrimaryAATrigger()` inserts a fake trigger into a copy of the last-stable-MC-unit, runs `handleTrigger()`, and on completion calls `revertResponsesInCaches()` to undo any changes to the shared caches [3](#0-2) .

Crucially, when `handleTrigger()` internally calls `writer.saveJoint()` for the temporary AA-response unit(s), it does so with `objAAValidationState.bUnderWriteLock = true`, which explicitly **skips acquiring `mutex.lock(["write"])`** inside `writer.saveJoint()` [4](#0-3) [5](#0-4) . This is safe for the two legitimate real callers, which serialize themselves via the `aa_triggers` mutex or the `handleJoint` mutex, but `dryRunPrimaryAATrigger()` (called from `light/dry_run_aa`) acquires **no mutex at all**.

As a result, `writer.saveJoint()` proceeds to unconditionally push temporary unit props directly into the live, shared caches:
```
storage.assocUnstableUnits[objUnit.unit] = objNewUnitProps;
storage.assocBestChildren[my_best_parent_unit].push(objNewUnitProps);
``` [6](#0-5) 

Reversal is done afterward by `revertResponsesInCaches()`, which pulls the temporary props back out via `storage.forgetUnit` and `storage.fixIsFreeAfterForgettingUnit` using object-identity (`_.pull`) matching against `assocBestChildren[parent_unit]` [7](#0-6) [8](#0-7) .

If two `light/dry_run_aa` requests execute concurrently (or one overlaps with the real `bDryRunNewTriggers` dry run performed while another unit is mid-validation, or with `handlePrimaryAATrigger`'s real commit which also directly touches `assocStableUnits`/`assocUnstableUnits`), the interleaving of pushes/pulls on the *same* shared arrays (`assocBestChildren[parent]`), together with `fixIsFreeAfterForgettingUnit`'s `is_free` recomputation (which iterates the *entire* `assocUnstableUnits` looking for children) [9](#0-8) , can corrupt the free-list state: a legitimate unstable unit can be left with a wrong `is_free` flag, have its entry in `assocBestChildren` deleted or duplicated, or have a dangling reference remain after a dry run's own unit was already deleted by a concurrently racing dry run's cleanup (since `_.pull` removes by reference, and simultaneous read/writes to the same non-atomic array during `async` I/O gaps are not synchronized). Because Node.js callbacks/`async.series` steps interleave on I/O (kvstore batch writes, DB queries in `writer.saveJoint`), there is ample opportunity for two overlapping dry runs to interleave their cache mutations.

### Impact Explanation
Corruption of `assocUnstableUnits` / `assocBestChildren` / `is_free` directly feeds `main_chain.js` stability and best-parent/best-child determination logic (used to decide MC advancement and unit stability) [10](#0-9) [11](#0-10) . A corrupted in-memory cache diverging from the DB truth causes the affected node to disagree with the rest of the network on unit validity/stability (the assertion checks in `main_chain.js` that compare cache vs DB throw hard errors — i.e., a crash/DoS — or, if not caught, silently produce wrong stability decisions), matching the "node disagreement on validity/stability" / "network unable to confirm new units" impact bar required for this analog.

### Likelihood Explanation
`light/dry_run_aa` is reachable by any unauthenticated light-client peer without rate limiting tied to this specific code path, and a full node running `bDryRunNewTriggers` performs this same unlocked dry run automatically for every incoming unit that outputs to a known AA address. An attacker only needs to send two or more concurrent `light/dry_run_aa` requests (trivial to fire in parallel) targeting AA addresses to trigger overlapping cache mutations; this requires no special privileges, keys, or race against a legitimate operator action beyond ordinary request timing.

### Recommendation
Serialize all cache-mutating dry runs the same way real trigger execution is serialized: have `dryRunPrimaryAATrigger()` (and `estimatePrimaryAATrigger()`) acquire `mutex.lock(["write"])` (or a dedicated `dry_run` key that is mutually exclusive with `write`/`aa_triggers`) before calling `handleTrigger()`, instead of relying on the `bUnderWriteLock` bypass which assumes an already-held write lock that is not actually present on this call path. Additionally, `revertResponsesInCaches` should validate that the objects it removes are actually the ones it added (e.g., by unique dry-run session tagging) rather than trusting `_.pull` object-identity alone under potential concurrent mutation.

### Proof of Concept
1. Deploy any valid AA definition.
2. As a light-client peer (no special privileges required), send two concurrent `light/dry_run_aa` requests targeting the same or different AA addresses so that both dry runs are executed by `network.js`'s `case 'light/dry_run_aa'` handler back-to-back without any synchronizing lock [1](#0-0) .
3. Because `dryRunPrimaryAATrigger` takes no mutex and `writer.saveJoint` skips the write-lock via `bUnderWriteLock` [3](#0-2) [6](#0-5) , both requests' temporary unit props are pushed into `storage.assocBestChildren[my_best_parent_unit]` concurrently.
4. When both call `revertResponsesInCaches()` [7](#0-6) , the `_.pull` calls race on the shared array and `fixIsFreeAfterForgettingUnit` recomputes `is_free` while the other dry run's temporary unit is still (or no longer) present, leaving `assocUnstableUnits`/`assocBestChildren` in a state inconsistent with the DB — verifiable by comparing `storage.assocBestChildren` state against a DB-driven rebuild (as done by the assertion in `main_chain.js:readBestChildrenProps`) [11](#0-10) , which throws `throwError("different best children...")` in `conf.bFaster=false` builds, or silently misconstrues stability in `bFaster` builds.

*Note: full end-to-end exploitation would require running the interleaving against a live network build (with `constants.bFaster` disabled to trigger the built-in assertions) to confirm the exact corrupted state reproduces deterministically; this was not executed as part of this static analysis, only the code paths and absence of locking were verified via the cited source.*

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
