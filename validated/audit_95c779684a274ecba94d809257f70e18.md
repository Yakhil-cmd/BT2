## Analog Vulnerability Found

### Title
Unauthenticated/Unbound `creator` Account in `initialize_with_permission` Allows Permanent Freezing of Creator Fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The IDOR pattern described in the external report — a caller-controlled identity field that is not cryptographically bound to the authenticated caller, letting an attacker act "on behalf of" an arbitrary account — has a direct analog in `InitializeWithPermission`. There, the `creator` field that becomes the pool's permanent fee beneficiary is an unconstrained, non-signing account supplied by the transaction sender, decoupled from the `payer` who actually authenticates via the `Permission` PDA.

### Finding Description
In `initialize_with_permission.rs`, the accounts struct defines: [1](#0-0) 
`payer` is the `Signer` whose authorization is checked against the `Permission` PDA: [2](#0-1) 

However, `creator` is only an `UncheckedAccount<'info>` with no `address =`, `constraint =`, or signer requirement binding it to `payer` or to any permission record. It is nonetheless persisted as the pool's permanent `pool_creator` field: [3](#0-2) 

This contrasts with the permissionless `Initialize` instruction, where the equivalent field is a signer and the caller and the recorded creator are always the same identity: [4](#0-3) [5](#0-4) 

The `pool_creator` field is exactly the value trusted downstream to receive accrued creator fees — including via the fully permissionless collection path, which anyone can invoke to push fees into whatever ATA `creator` resolves to, without `creator`'s signature: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any account holding a valid `Permission` PDA (i.e., anyone authorized to call `initialize_with_permission`) can set `creator` to an arbitrary pubkey that no one controls the private key for (e.g., a PDA of another program, a mint address, or any address with a provably unspendable key). Because `collect_creator_fee` requires `creator` to sign, and `collect_creator_fee_permissionless` routes fees to `creator`'s ATA regardless of who calls it, all accrued creator fees for that pool become permanently locked in an ATA nobody can ever move — a permanent freezing of pool/LP-derived fee revenue. This is a real accounting/ownership binding failure of the same class as the reported IDOR: the privileged beneficiary identity is supplied by the caller instead of being cryptographically tied to the authenticated/permissioned party.

### Likelihood Explanation
High likelihood: exploitation requires only a single transaction with attacker-chosen accounts (a valid `Permission` account for `payer`, and any `creator` pubkey of the attacker's choosing) and no elevated privileges beyond what is already required to legitimately create a permissioned pool.

### Recommendation
Constrain `creator` in `InitializeWithPermission` to be either the `payer` itself, or require `creator` to be a `Signer`, or bind it via the `Permission` PDA (e.g., derive/require the permission seeds from `creator` rather than `payer`, or add an explicit `constraint = creator.key() == payer.key()` if creator and payer are meant to be identical) so the fee-beneficiary identity cannot be set to an address the initializing party does not control.

### Proof of Concept
1. Attacker obtains/holds a valid `Permission` account for their own `payer` pubkey.
2. Attacker calls `initialize_with_permission` supplying `payer` = their own signer, but `creator` = an arbitrary unclaimable pubkey (e.g., a PDA of another program, or any pubkey with no known keypair).
3. Pool is created; `pool_state.pool_creator` is permanently set to that unclaimable address per `initialize_with_permission.rs:357-372`.
4. As swaps occur, creator fees accrue to `pool_state.creator_fees_token_0/1`.
5. Anyone calls `collect_creator_fee_permissionless`; fees are transferred into an ATA owned by the unclaimable `creator` address per `collect_creator_fee_permissionless.rs:61-79`, permanently locking those funds since no one can sign as `creator` to move them further.
