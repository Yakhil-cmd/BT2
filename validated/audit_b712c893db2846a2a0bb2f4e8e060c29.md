### Title
Unfiltered pull-request label injection into deploy-process environment via `ReviewStack#env` bypasses the deploy-spec variable whitelist - ([File: app/models/shipit/review_stack.rb], [lib/shipit/command.rb])

### Summary
`ReviewStack#env` merges every PR label name (uppercased) directly into the stack's environment hash with a fixed value `"true"`, and that hash flows unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Command#unbundled_env`, which is passed verbatim to `PTY.spawn`. Unlike the deploy-spec's own `deploy.variables`/`rollback.variables`/task `variables` mechanism, which is sanitized by `EnvironmentVariables#permit` (`DeploySpec#filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs`), label-derived keys never pass through any whitelist check.

### Finding Description
The claimed binding is: `Command#unbundled_env` keys == the deploy spec's permitted variable set (`deploy_variables`/`rollback_variables`/task `variables`, enforced by `EnvironmentVariables#permit`). This binding is broken for one specific merge source.

Trace:
- `EnvironmentVariables#permit` enforces the whitelist for explicit user-submitted env params (`app/controllers/.../deploys_controller`, `rollbacks_controller`, `tasks_controller`), verified by `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:174-180`) and `TaskDefinition#filter_envs` (`app/models/shipit/task_definition.rb:63-65`). [1](#0-0) [2](#0-1) 

- However, `ReviewStack#env` overrides `Stack#env` and merges raw, attacker-controlled label names — uppercased — directly into the environment hash with no call to `EnvironmentVariables#permit` or any allowlist check: [3](#0-2) 

- `TaskCommands#env` (used by both deploy and task/rollback command builders) merges `@stack.env` (which, for a `ReviewStack`, includes the unfiltered label keys) directly into the environment used to build each `Command`: [4](#0-3) 

- `Command#initialize` stores this hash as `@env` verbatim (only stringifying values), and `Command#unbundled_env` merges it on top of `BASE_ENV`/`PATH` with no filtering, before being passed straight to `PTY.spawn`: [5](#0-4) [6](#0-5) 

- Existing tests explicitly confirm this behavior is intentional and unguarded: labeling a PR `wip`/`bug` produces `env["WIP"] == "true"` / `env["BUG"] == "true"` for both `DeployCommands` and `TaskCommands`, with no involvement of `EnvironmentVariables#permit`: [7](#0-6) [8](#0-7) 

**Attacker's exact request**: open a pull request against a repository that has review stacks enabled (`allow_all`, `allow_with_label`, or `prevent_with_label` provisioning, all attacker-reachable per `test/models/shipit/webhooks/handlers/pull_request/*_handler_test.rb`) and apply the label `NODE_OPTIONS` or `PYTHONPATH` (any GitHub user with write access to their own fork/PR can add labels to their own PR, or the repository owner's label set may already contain such a name — GitHub allows any repo collaborator with triage permission to label PRs on repos they control). Once the `LabeledHandler` processes the webhook, `stack.pull_request.labels` includes `"NODE_OPTIONS"`, and the next deploy/task command build injects `NODE_OPTIONS=true` (or `PYTHONPATH=true`) into every `Command`'s environment for that stack, including `node`/`python` deploy steps.

**Why existing guards fail**: `verify_signature`/`GitHubApp#verify_webhook_signature` and `drop_unhandled_event` only gate whether the webhook is accepted, not what data it carries. `EnvironmentVariables#permit` only guards the explicit `env` param path (API-triggered deploys/rollbacks/tasks) and `deploy.variables`/`rollback.variables`/task `variables`; it is never invoked in the `ReviewStack#env` → `TaskCommands#env` chain. `Stack` model validations (`environment` format, `branch` presence) do not constrain label content since labels come from GitHub, not stack attributes.

### Impact Explanation
Any interpreter-honored environment variable name that an attacker can get accepted as a GitHub label (letters, numbers, underscores are common; GitHub label names permit a wide character set) is force-set to `"true"` in every subsequent deploy/task/rollback `Command` for that review stack — for the same repository, repeatably, on every deploy while the label remains applied. For `NODE_OPTIONS`, this reliably aborts Node-based deploy steps (denial of the deploy step, not code execution by itself). For `PYTHONPATH`/`PERL5LIB`, the injected value is always the literal string `"true"`, not an attacker-chosen path; achieving code execution via module-search-path hijacking requires the attacker to also arrange a file/directory literally named `true` on the interpreter's working-directory-relative search path containing a module that gets imported by the trusted deploy script — feasible only because the attacker also controls the checked-out PR branch content, but this is an additional non-trivial precondition beyond the label alone. In isolation, the confirmed and repeatable impact is: bypass of the deploy-spec's environment-variable whitelist, allowing unauthorized environment injection into commands run on the deploy host for a stack the attacker does not control (repository maintainers configure `deploy.variables`; this bypass ignores that configuration entirely). This is real and reproducible impact against the review-stack owner's deploy host, scoped to stacks with review-stack provisioning enabled.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (a supported, not uncommon configuration) and be labelable by the attacker (their own PR, or any repo where non-maintainers can add labels). No secrets, tokens, or elevated GitHub/Shipit permissions are required — labeling one's own PR is a standard unprivileged GitHub action. The attacker cost is a single API call/UI action to add a label; the effect persists as long as the label is applied and is reproducible across every deploy/task/rollback triggered for that stack.

### Recommendation
Route `ReviewStack#env`'s label-derived keys through the same `EnvironmentVariables#permit` whitelist mechanism used elsewhere (e.g., only allow labels whose name matches an explicit `review.labels` allowlist declared in `shipit.yml`, or drop the raw-label-to-env-var feature and require repositories to opt in per-name). At minimum, reject any label name that collides with security-sensitive interpreter env vars (`NODE_OPTIONS`, `PYTHONPATH`, `PERL5LIB`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_*`, `PATH`, etc.) before merging into `Command` env.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing style)
test "#env allows PR labels to inject interpreter-honoured env vars, bypassing the whitelist" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["node_options"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  # Binding claimed by DeploySpec/EnvironmentVariables#permit:
  #   Command#unbundled_env keys == deploy_spec.deploy_variables (whitelisted names only)
  # Actual: NODE_OPTIONS is present despite not being declared in deploy.variables
  refute_includes stack.cached_deploy_spec.deploy_variables.map(&:name), "NODE_OPTIONS"
  assert_equal "true", env["NODE_OPTIONS"]
end
```
This demonstrates the binding is broken: `NODE_OPTIONS` is not in `deploy_variables` (the permitted set) yet reaches the `Command` environment that is merged into `Command#unbundled_env` and passed to `PTY.spawn`, exactly mirroring the existing `test/lib/shipit/task_commands_test.rb` and `test/lib/shipit/deploy_commands_test.rb` tests for `WIP`/`BUG` labels.
