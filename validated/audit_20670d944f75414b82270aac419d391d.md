### Title
Contract Content Spoofing via Hash-Excluded Fields in `prosaic_contract.getHash` / `arbiter_contract.getHashSrc` - (File: prosaic_contract.js, arbiter_contract.js)

### Summary
The prosaic and arbiter contract features let a paired device send a contract offer that is displayed to the counterparty and later bound to an on-chain signing unit only through a truncated hash. The commitment hash covers just a subset of the fields that make up the "true" contract as displayed/stored, analogous to the Documenso flaw where the rendered/printed view does not reflect all layers actually present in the document — the hash "flattens" only some of the content while other displayed/relied-upon fields ride along unauthenticated.

### Finding Description
`prosaic_contract.getHash()` computes the contract identity as `sha256(title + text + creation_date)` [1](#0-0) . Other fields of the same `objContract` — `peer_address`, `my_address`, `ttl`, `cosigners` — are stored and displayed (and control money flow via the derived shared address) but are excluded from the hash. In `wallet.js`, the `prosaic_contract_offer` handler validates only `body.hash !== prosaic_contract.getHash(body)`, and then stores `body` (which contains `ttl`, `peer_address`, `my_address`, `cosigners`) verbatim, and also broadcasts the raw `body` as an inline chat message `(prosaic-contract:...)` shown to the user [2](#0-1) .

`arbiter_contract.getHashSrc()` is broader, but the value it protects still is not everything that matters operationally: it includes `title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset` [3](#0-2) , while other fields propagated through the protocol (`ttl`, `my_contact_info`/`peer_contact_info`, `cosigners`) are outside the hash and outside `getContactsHash` too (contact info is only bound via a separate, optional `getContactsHash`, not enforced on the initial offer) [4](#0-3) . On `arbiter_contract_offer`, `wallet.js` validates `body.hash !== arbiter_contract.getHash(body)` and, notably, `ttl` is required to be a positive number but is otherwise never checked against any commitment value before being persisted and acted upon (e.g. contract expiry computations use `objContract.ttl` later) [5](#0-4) , [6](#0-5) .

Because the hash — the only integrity anchor a receiving device/user can check before accepting/signing a contract — omits fields that are nonetheless displayed to the user and later used to compute expiry and dispute logic, a malicious offeror (an unprivileged paired device peer) can send a `prosaic_contract_offer`/`arbiter_contract_offer` in which the hash-covered fields (title/text/parties/amount) match what the human reviews, while hash-excluded fields (`ttl`, `cosigners`, contact info) are set to values advantageous to the attacker. The recipient's UI/hash check will pass ("contract looks authentic") even though part of the actually operative contract metadata was never covered by any cryptographic commitment — directly mirroring the CVE-2024-52271 pattern of "displayed version does not reflect all layers actually committed."

### Impact Explanation
This can be used to manipulate contract lifecycle fields that were never bound by the verified hash. Most concretely, `ttl` controls when a `prosaic_contract`/`arbiter_contract` can no longer be accepted/responded to (`objDateCopy...+ objContract.ttl*60*60 < Date.now()`) [7](#0-6) . An attacker fully controls `ttl` without it being covered by the hash the recipient trusts, letting them present a contract whose hash matches the visually reviewed title/text/amount but silently extend or shrink acceptance windows, or, via `cosigners` in the prosaic-contract case, add unauthorized shared-address co-signers that were never part of the hash-verified agreement. This does not directly forge a unit signature (the eventual shared address and unit signing are separately verified), but it does allow content/metadata spoofing consistent with a Medium content-spoofing class bug, since the values that end up governing contract disposition are not what the hash actually attests to.

### Likelihood Explanation
Any paired device (a normal wallet counterparty) can trigger this by simply crafting a `prosaic_contract_offer` or `arbiter_contract_offer` message with hash-covered fields left intact and hash-excluded fields (`ttl`, `cosigners`, contact info) set arbitrarily; the receiving wallet's validation in `wallet.js` performs no additional binding beyond the incomplete `getHash`/`getHashSrc` check. This requires no special privileges beyond normal device pairing, which is explicitly in-scope.

### Recommendation
Include all fields that are persisted, displayed, or later relied upon operationally (`ttl`, `cosigners`, `peer_address`/`my_address` roles beyond what's already covered, contact info) in the canonical hash computed by `prosaic_contract.getHash` and `arbiter_contract.getHashSrc`, or otherwise cryptographically bind every field that affects contract semantics before it is accepted/stored/acted upon.

### Proof of Concept
1. Attacker (device B) crafts a `prosaic_contract_offer` message to victim device A with legitimate `title`, `text`, `creation_date` (so `getHash` matches) but sets `ttl` to an extreme value and `cosigners` to include an address controlled by the attacker.
2. `wallet.js`'s `prosaic_contract_offer` handler only checks `body.hash !== prosaic_contract.getHash(body)` [8](#0-7) ; since `getHash` excludes `ttl`/`cosigners`, the check passes.
3. The contract is stored with the attacker-controlled `ttl`/`cosigners` and displayed to the user as an authentic, hash-verified offer [9](#0-8) .
4. Later, `ttl` governs whether a response can still be accepted (`objDateCopy...ttl*60*60 < Date.now()`), letting the attacker manipulate the effective deadline without the user's verification catching it [7](#0-6) .

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}

function getContactsHash(contract) {
	const payer_pairing_code = contract.me_is_payer ? contract.my_pairing_code : contract.peer_pairing_code;
	const payee_pairing_code = contract.me_is_payer ? contract.peer_pairing_code : contract.my_pairing_code;

	const src = [payer_contact_info || '', payer_pairing_code || '', payee_contact_info || '', payee_pairing_code || ''].join("|");
