### Title
Arbiter/Prosaic Contract Hash Uses Unbound Field Concatenation Vulnerable to Splicing (CWE-115/CWE-347) - (File: arbiter_contract.js, prosaic_contract.js)

### Summary
`getHashSrc()` in `arbiter_contract.js` and `getHash()`/`getHashV1()` in `prosaic_contract.js` compute the contract-identifying hash by directly concatenating variable-length, attacker/peer-controlled strings (`title`, `text`, `creation_date`, party names) with no unambiguous delimiter between them, exactly the same "semantic binding" flaw described in the ALTCHA advisory (CWE-115/CWE-347): the digest does not unambiguously bind the individual field boundaries, so different `(title, text, ...)` splits can collapse to the identical hash.

### Finding Description
`arbiter_contract.js` computes the contract hash as: [1](#0-0) 

For any `creation_date <= NEW_HASH_DATE` (`'2026-11-01'`), the "old" branch is used:
```
[title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset].join("")
```
i.e. plain string concatenation with **no separator at all**. Because `title` and `text` are free-form strings chosen by the offeror when calling `createAndSend`, an attacker can shift the boundary between `title` and `text` (or between `text` and the fixed-format `creation_date`) while producing byte-for-byte identical concatenated input, and therefore an identical SHA-256 digest, for two semantically different contracts.

Critically, the codebase's own `NEW_HASH_DATE`/`exports.DELIMITER` mechanism proves this is a recognized defect that the developers intended to fix by inserting `exports.DELIMITER = "[|#|]"` between fields — but the fix is date-gated to `2026-11-01`, which is *after* today's date (2026-09-15). Until that date, every newly created arbiter contract still uses the vulnerable, delimiter-free hash. `prosaic_contract.js`'s `getHash`/`getHashV1` have no such gate and remain permanently vulnerable: [2](#0-1) 

This directly contrasts with the safe pattern used elsewhere in the codebase, `getSourceString()`, which explicitly type-tags every field and rejects any embedded join-character to prevent exactly this class of splicing: [3](#0-2) 

The contract hash is not cosmetic — it is embedded as a data-feed key (`"CONTRACT_" + contract.hash`) inside the shared address definition that gates release of the escrowed funds, and it is checked against the on-DAG `data` message posted when the contract is signed: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because `title`/`text` are fully controlled by the contract's initiating peer, that peer can craft two different `(title, text)` splits that produce the same `contract.hash` while keeping `creation_date`, party addresses, `arbiter_address`, `amount`, and `asset` identical. This lets a malicious counterparty present one version of the contract terms to the arbiter/arbstore (via `openDispute`'s `encrypted_contract`) while the shared-address definition, the `CONTRACT_<hash>` data-feed key, and the on-chain `contract_text_hash` check all validate against the same hash regardless of which text variant is used. An attacker can thus decouple the dispute content actually reviewed/resolved by the arbiter from the content nominally committed to by the hash, enabling the shared escrow funds to be released based on manipulated contract terms — i.e., unauthorized diversion of escrowed funds through the arbiter-contract flow, or a permanent freeze if the two parties derive divergent expectations of the `CONTRACT_<hash>` key and neither side's condition can ever be satisfied.

### Likelihood Explanation
The attack requires only that the attacker be one of the two contract counterparties (an unprivileged wallet user creating/offering an arbiter or prosaic contract) — no hub, node, or protocol-level privilege is needed. The vulnerable code path is the default, currently-active path (the delimiter fix is gated to a future date), making exploitation straightforward for anyone using the arbiter-contract or prosaic-contract feature today.

### Recommendation
Remove the date gate and immediately use the delimiter-based `getHashSrc` for all contracts, or better, replace ad-hoc concatenation in both `arbiter_contract.js` (`getHashSrc`, `getContactsHash`) and `prosaic_contract.js` (`getHash`, `getHashV1`) with `object_hash.getBase64Hash`/`string_utils.getSourceString`, which already type-tag and delimiter-check every field to make field boundaries unambiguous.

### Proof of Concept
1. Party A (attacker) offers an arbiter contract via `createAndSend` with `title = "Pay"`, `text = "$100 for goods"`.
2. `getHash` computes `sha256("Pay" + "$100 for goods" + creation_date + ...)`.
3. Attacker later (in a dispute submission or alternate channel) substitutes `title = "Pay$100 "`, `text = "for goods"` — the concatenation `"Pay$100 " + "for goods" + creation_date + ...` is byte-identical to step 2's input given the same trailing fields, so `getHash` returns the identical value even though the split between "title" and "text" (and thus their displayed semantics) differs.
4. Any validation that only checks `getHash(contract) === expected_hash` (e.g. `handleReceivedSigningUnit`'s `payload.contract_text_hash !== contract.hash`, or an arbstore-side re-hash check) cannot distinguish the two variants, allowing the attacker to substitute content post hoc while passing all hash-equality checks.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
