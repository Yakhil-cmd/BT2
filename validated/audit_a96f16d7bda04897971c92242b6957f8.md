### Title
Unbounded recursive submodule processing enables node resource-consumption DOS via attacker-controlled repo content - (File: main.go)

### Summary
`git-sync` defaults to `--submodules=recursive` and, on every sync where the target hash changes, runs `git submodule update --init --recursive` with no limit on submodule count, nesting depth, or per-step time budget beyond the single global `--sync-timeout` for the whole sync [3](#0-2) . A repository whose content is controlled by an untrusted contributor (the same "attacker-pushed commit" trust boundary used throughout this analog set) can add a very large or deeply nested tree of git submodules. Every sync attempt that touches that ref must recursively clone/update all of them inside the same bounded context, exactly mirroring the op-geth report's pattern of unbounded per-transaction resource consumption driven by attacker-authored nested structures.

### Finding Description
The sync loop creates one `context.WithTimeout` per sync attempt using the operator-configured `--sync-timeout` (default 120s) and passes that single context through `SyncRepo` → `configureWorktree` → `git.Run` → `exec.CommandContext` for every git subprocess in that sync, including the submodule step [1](#0-0) [4](#0-3) [5](#0-4) . The submodule handling code applies `--recursive` and an optional `--depth` limit on commit history depth per submodule, but does not cap the number of submodules or the nesting depth of "submodules-of-submodules" [3](#0-2) . The e2e test suite confirms that submodules can nest arbitrarily (`sub` → `nested-sub`) and that recursive mode walks the entire chain [6](#0-5) . Because the content of `.gitmodules` and the number/depth of submodules is entirely determined by whoever can push to the tracked ref/branch of `--repo`, an attacker with write access to that ref (the same threat actor assumed capable of crafting a malicious commit/ref in this analog set) can construct a tree with, e.g., thousands of nested or sibling submodules pointing at reachable remotes. On every subsequent sync that picks up a new commit hash for that ref, `git-sync` must re-run the full recursive `submodule update --init --recursive` walk from scratch inside the shared worktree, consuming CPU, network, and wall-clock time bounded only by the single sync-wide timeout.

### Impact Explanation
If the submodule walk exceeds `--sync-timeout`, `exec.CommandContext` kills the subprocess and `runWithStdin` returns a `context.DeadlineExceeded` error [7](#0-6) , which surfaces as a failed sync in the main loop, incrementing `failCount` and, once `--max-failures` is reached, causing `git-sync` to exit(1) entirely [8](#0-7) . Because the malicious commit remains the tip of the tracked ref, every subsequent sync/restart re-attempts and re-fails the same expensive recursive submodule walk, producing **persistent sync denial**: the sidecar can never publish a newer, legitimate revision, and (depending on `--max-failures`) can crash-loop the container. This matches the accepted impact category of "persistent sync denial" and is a reasonable node/CPU/network resource-consumption analog to the op-geth gas-tracker report, where attacker-authored nested structures forced unbounded per-transaction processing cost on the node.

### Likelihood Explanation
Likelihood is moderate and scoped to environments where `--submodules` is left at its default (`recursive`) and the synced ref is writable by a less-trusted party (e.g., CI pipelines, GitOps configs syncing developer-controlled branches, or multi-tenant setups where `git-sync` tracks a branch that untrusted contributors can push to). No credential leak, node compromise, or mocked-only condition is required — only ordinary push access to the tracked ref and knowledge that `--submodules=recursive` is the default. Operators who set `--submodules=off` or `shallow`, or who set a generous `--sync-timeout`, reduce or eliminate the risk, so real-world exposure depends on deployment configuration.

### Recommendation
- Change the default `--submodules` behavior to non-recursive (`shallow` or `off`) unless explicitly opted in, or document the DOS risk prominently.
- Add an explicit, independently configurable timeout/limit for the submodule-update step (distinct from the overall `--sync-timeout`), and/or a maximum submodule count/recursion-depth flag, so a single malicious commit cannot exhaust the whole sync budget.
- Consider running `git submodule update --init --recursive` with `--jobs`/resource caps and surfacing partial-progress caching so repeated failed attempts don't always restart the walk from scratch.
- Treat repeated submodule-induced timeouts as a distinct failure class in metrics/logging so operators can detect and mitigate this pattern (e.g., pin `--max-failures` conservatively or alert on `context.DeadlineExceeded` submodule failures).

### Proof of Concept
1. Deploy `git-sync` with default flags (`--submodules` unset → `recursive`) tracking a branch that an untrusted collaborator can push to, with a modest `--sync-timeout`.
2. Attacker pushes a commit to that branch whose `.gitmodules` references a very large number of submodules and/or a deep chain of submodules-of-submodules (each a small but real reachable repository), analogous to the "10,000 nested contracts" pattern in the source report.
3. On the next sync, `git-sync` calls `configureWorktree`, which runs `git submodule update --init --recursive` inside the single `--sync-timeout`-bounded context [3](#0-2) .
4. If the recursive walk exceeds `--sync-timeout`, the command is killed via `exec.CommandContext`, the sync attempt fails [5](#0-4) , and because the same malicious commit remains at the ref tip, every subsequent periodic sync attempt repeats and fails identically, eventually tripping `--max-failures` and exiting the process — producing persistent denial of successful synchronization [8](#0-7) .

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())

function e2e::submodule_sync_shallow() {
    # Init submodule repo
    local submodule_repo_name="sub"
    local submodule="$WORK/$submodule_repo_name"
    mkdir "$submodule"

    git -C "$submodule" init -q -b "$MAIN_BRANCH"
    echo "submodule" > "$submodule/submodule.file"
    git -C "$submodule" add submodule.file
    git -C "$submodule" commit -aqm "init submodule file"

    # Init nested submodule repo
    local nested_submodule_repo_name="nested-sub"
    local nested_submodule="$WORK/$nested_submodule_repo_name"
    mkdir "$nested_submodule"

    git -C "$nested_submodule" init -q -b "$MAIN_BRANCH"
    echo "nested-submodule" > "$nested_submodule/nested-submodule.file"
    git -C "$nested_submodule" add nested-submodule.file
    git -C "$nested_submodule" commit -aqm "init nested-submodule file"
    git -C "$submodule" -c protocol.file.allow=always submodule add -q file://$nested_submodule "$nested_submodule_repo_name"
    git -C "$submodule" commit -aqm "add nested submodule"

    # Add submodule
    git -C "$REPO" -c protocol.file.allow=always submodule add -q file://$submodule "$submodule_repo_name"
    git -C "$REPO" commit -aqm "add submodule"

    GIT_SYNC \
        --period=100ms \
        --repo="file://$REPO" \
        --root="$ROOT" \
        --link="link" \
        --submodules=shallow \
        &
    wait_for_sync "${MAXWAIT}"
    assert_link_exists "$ROOT/link"
    assert_file_exists "$ROOT/link/file"
    assert_file_exists "$ROOT/link/$submodule_repo_name/submodule.file"
    assert_file_absent "$ROOT/link/$submodule_repo_name/$nested_submodule_repo_name/nested-submodule.file"
    rm -rf $submodule
    rm -rf $nested_submodule
}
