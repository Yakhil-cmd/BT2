### Title
Push-sweep trusts attacker-controlled trailing stdout as authoritative git range, allowing review-range spoofing - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`_push_section` selects the **last** `\nTo <remote>` block in the combined stdout+stderr of a Bash tool call and `_detect_prev_upstream` blindly trusts the `abc..def` range parsed from it via `_PUSH_RANGE_RE`. If an attacker-controlled script/Makefile target is chained after `git push` in the same Bash compound (`git push -q && custom_script`), that script can print a fabricated `To <remote>` / range block that becomes the "last" one and is treated as the authoritative push range.

### Finding Description
`_push_section` (`plugins/security-guidance/hooks/security_reminder_hook.py:739-774`) locates the push's range lines with `bash_output.rfind("\nTo ")` [1](#0-0) , explicitly choosing the *last* `To ` header on the theory that any earlier `To`/`From` blocks come from a chained `git fetch`/`git pull` in the same compound command [2](#0-1) . `_detect_prev_upstream` then runs `_PUSH_RANGE_RE.search(_push_section(bash_output))` and, on a match, returns `m.group(1)` (the "old" sha) unconditionally as the authoritative pre-push remote position [3](#0-2) . `_PUSH_RANGE_RE` itself is a generic regex (`^\s*\+?\s*([0-9a-f]{7,40})\.\.\.?([0-9a-f]{7,40})\s+(\S+)\s+->\s+\S+`) that matches any text resembling git's range-update line format, with no cryptographic or process-provenance binding to the actual `git push` invocation [4](#0-3) .

Because Bash's `tool_response` stdout/stderr are simple concatenated text streams with no structural separation between commands in a compound (`cmd1 && cmd2`), any command chained after `git push` that emits text of the form `To <remote>\n<oldsha>..<newsha> <local-ref> -> <remote-ref>` will produce a second, later `To ` header. `rfind` picks this attacker-controlled block instead of git's own output, and `_PUSH_RANGE_RE` extracts the attacker-chosen `oldsha`/`newsha`/`local-ref`.

The docstring for `_PUSH_RANGE_RE` claims the handler verifies "the pushed ref == HEAD" using the captured local-ref group, intended to reject mismatched-branch pushes [5](#0-4) . This check does not stop the attack: the attacker's chained script runs in the same unprivileged environment as the legitimate push and can trivially query the real branch name and real `HEAD` sha (`git branch --show-current`, `git rev-parse HEAD`) to make its fabricated `local-ref` and `new-sha` fields pass validation, while supplying an arbitrary `old-sha` (e.g., equal to current `HEAD`). The resulting `prev_upstream` value feeds `_compute_push_sweep_base`, which computes `git rev-list prev_upstream..HEAD` as the range to security-review [6](#0-5) . If `prev_upstream` is spoofed to equal `HEAD` (or any descendant of the real prior remote position), the commit list is empty or truncated, causing the review sweep to conclude "already reviewed" and skip.

### Impact Explanation
This bypasses/narrows the push-sweep security review pipeline that is supposed to LLM-scan newly pushed commits for vulnerabilities. An attacker who can get their code committed and included in a repo's build/deploy tooling (Makefile, npm script, CI wrapper invoked by the agent in the same Bash call as `git push`) can suppress or shrink the diff range sent for review, letting malicious or vulnerable code slip past the automated security check silently — a trust-boundary bypass of the plugin's core review-scoping invariant ("correct binding of diff range to real git state").

### Likelihood Explanation
Requires the attacker to control a script/build-target that runs in the same Bash compound command as `git push` (e.g., via a repo's own `Makefile`/`package.json` scripts that the agent is likely to invoke, such as `git push && npm run notify`). No elevated privilege, credentials, or social engineering beyond ordinary repository content is needed — the attacker's script needs no privileged access to fabricate output matching a known, public text format, and can dynamically query the real branch name/HEAD sha at push time. This is realistic in supply-chain style scenarios where a compromised or malicious dependency/build script is part of the repo's normal push/deploy flow.

### Recommendation
Do not trust free-form text appearing after `git push` in shared stdout/stderr as ground truth. Options:
- Run `git push` in isolation (not chained with other commands) when the security hook needs to parse its output, or use `git push --porcelain`/machine-readable output written to a dedicated fd/temp file that other commands can't write to.
- Cross-validate the parsed `old-sha` against real git state before trusting it: verify `old-sha` is actually reachable/was the value of `<branch>@{u}@{1}` or a merge-base, rather than accepting any regex match unconditionally.
- Only accept the `_PUSH_RANGE_RE` match if it is the *only* range-like match in the buffer, or bound the search strictly to output produced strictly before any subsequent shell command runs (impossible to guarantee from concatenated text alone — prefer the isolation approach above).

Unit test in the spirit of existing tests for `_push_section`/`_detect_prev_upstream`:

```python
def test_push_section_rejects_attacker_appended_range(monkeypatch):
    real_old, real_new = "1111111", "2222222"
    fake_old, fake_new = "aaaaaaa", "bbbbbbb"
    bash_output = (
        f"To origin\n"
        f"   {real_old}..{real_new}  main -> main\n"
        # attacker-controlled script chained via `&&` after git push
        f"To fake-remote\n"
        f"{fake_old}..{fake_new} main -> main\n"
    )
    section = _push_section(bash_output)
    m = _PUSH_RANGE_RE.search(section)
    # Current behavior: picks the attacker-injected block (BUG)
    assert m.group(1) == fake_old  # demonstrates the flaw
    # Expected/fixed behavior should assert m.group(1) == real_old instead.
```
Expected assertion after fix: `_detect_prev_upstream`/`_push_section` should never return `fake_old`/`fake_new` when real git push output is present earlier in the buffer — i.e., the parser must bind to the actual `git push` process's output, not to any later text matching the same shape.

```python
def _compute_push_sweep_base(prev_upstream, push_range, reviewed):
    """Advance the diff base past the contiguous reviewed prefix.

    Spec: review `git diff B..HEAD` where `B` is the newest commit such that
    `prev_upstream..B` is entirely in `reviewed`. Returns (B, unreviewed_tail).
    `B == None` means the whole range is reviewed (caller should skip).
    `push_range` must be oldest→newest.

    Examples (✓=reviewed, ✗=not):
      [✓1, ✗2, ✓3]  → B=1, tail=[2,3]   (cannot trim suffix; Read is at HEAD)
      [✓1, ✓2, ✓3]  → B=None            (all reviewed → skip)
      [✗1, ✓2, ✗3]  → B=prev_upstream, tail=[1,2,3]
      []            → B=None
    """
    i = 0
    while i < len(push_range) and push_range[i] in reviewed:
        i += 1
    if i == len(push_range):
        return None, []
    base = push_range[i - 1] if i > 0 else prev_upstream
    return base, push_range[i:]
```

```python
def _detect_prev_upstream(repo_root, bash_output):
    """Where the remote was BEFORE this push.

    Preference order:
      1. Parse `abc..def` from push stdout — authoritative, exact.
      2. `<branch>@{u}@{1}` — the remote-tracking ref's reflog position before
         this push moved it. PostToolUse runs after `git push` completes, so
         `@{u}` is already updated and `@{u}@{1}` is the prior value.
      3. merge-base with the detected main branch — first push of a new
         branch (`* [new branch]` in output, no upstream reflog yet).
    Returns a resolvable ref/sha or None.
    """
    m = _PUSH_RANGE_RE.search(_push_section(bash_output or ""))
    if m:
        return m.group(1)
```
