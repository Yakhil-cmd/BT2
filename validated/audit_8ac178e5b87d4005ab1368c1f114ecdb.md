### Title
Cross-organization webhook event smuggling via `repository.owner.login` vs `repository.full_name` binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a delivery against based on `repository.owner.login` (or `organization.login`) read straight out of the untrusted request body, while every webhook `Handler` subsequently resolves the target `Repository`/`Stack` to mutate using a completely different, independently-controlled field: `repository.full_name`. Since both fields live inside the same attacker-supplied JSON body that gets signed as a whole, an attacker who legitimately controls a GitHub App/organization already configured in this Shipit instance (and therefore genuinely knows *that org's* `webhook_secret`, which they would as its administrator) can craft and correctly sign a payload where `repository.owner.login` names their own org (so the signature check passes) but `repository.full_name` names a repository belonging to an entirely different, victim org/stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App/secret with: [1](#0-0) 
where `repository_owner` is derived purely from the JSON body: [2](#0-1) 

`verify_webhook_signature` only proves that the raw body was signed with the secret belonging to `Shipit.github(organization: repository_owner)` — it says nothing about which repository the rest of the payload claims to be about: [3](#0-2) 

Once the request passes this check, `create` dispatches to the relevant `Webhooks::Handlers::*` classes with the full, attacker-controlled JSON body: [4](#0-3) 

Every handler resolves the `Repository`/`Stack` to act on using `repository.full_name` from that same body — a field that was never cross-checked against the org whose secret was used to authenticate the request: [5](#0-4) [6](#0-5) [7](#0-6) 

So the equality the engine implicitly (and incorrectly) relies on is:
`organization authenticated by verify_webhook_signature (repository.owner.login)` == `repository actually written to by the Handler (repository.full_name)`

These are two independently attacker-controlled fields inside the same signed body, and nothing enforces that `repository.full_name`'s owner matches `repository.owner.login`. This is structurally the same class of bug as the reference report: a value that is legitimately verified (the "incoming" counterparty pull vs. "outgoing" release in the Solidity contract) is inverted/decoupled from the value actually acted upon.

### Impact Explanation
This is only meaningfully exploitable in the documented multi-organization configuration mode, where a single Shipit instance manages several distinct GitHub Apps/orgs, each with its own `webhook_secret`: [8](#0-7) 

In that setup, an org admin of one tenant org (who legitimately knows only their own org's `webhook_secret` — no Shipit session, API token, or GitHub App private key from the victim org is needed) can forge a `push`, `status`, `check_suite`, `pull_request`, or `membership` webhook body claiming `repository.full_name` of a repository belonging to a different, victim org tracked by the same Shipit instance, sign it with their own org's secret, and have Shipit act on it as if it were a legitimate event for the victim repository — e.g. enqueueing `GithubSyncJob` for the victim stack, creating/deleting commit statuses, closing/archiving/unarchiving review stacks, or adding/removing team memberships (`membership` handler creates/removes `Membership` records with attacker-supplied team/user data). This can influence deploy eligibility (CI status manipulation), lifecycle of review stacks, and team-based authorization records (`Shipit.github_teams` membership), which the engine explicitly calls out as a High-severity impact category ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Requires the Shipit deployment to be configured for multiple GitHub organizations and the attacker to control (or have compromised) one of those organizations' GitHub App/webhook configuration — a scenario the engine explicitly documents and supports. No Shipit credentials, sessions, or API tokens are needed; the webhook endpoint is intentionally unauthenticated apart from the per-org signature check.

### Recommendation
After signature verification, re-derive/require the org from the payload's `repository.full_name` (or `organization.login` used for the actual target repository) and confirm it matches the org whose secret was used (`repository_owner`) before dispatching to handlers, e.g. reject the request if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `attacker-org` (secret known to the attacker, e.g. because they administer that GitHub App) and `victim-org` (tracked stacks the attacker has no access to).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org's webhook_secret, raw_body)>` and POSTs to `/github_webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and successfully verifies the signature against that org's known secret. [9](#0-8) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` and enqueues a sync job for the victim's stack, despite the request never being signed by anyone associated with `victim-org`. [10](#0-9)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
