## Cross-chain replay of `offer_signer_capability` due to missing `chain_id` binding in `SignerCapabilityOfferProofChallengeV2`

### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` allows a signer-capability-delegation authorization signed for one Aptos network to be replayed on another - ([File: aptos-move/framework/aptos-framework/sources/account/account.move])

### Summary
`account::offer_signer_capability` authorizes delegating an account's `SignerCapability` (the ability to fabricate a `signer` for that account) to a `recipient_address`, based on an off-chain-signed `SignerCapabilityOfferProofChallengeV2` message. Unlike its sibling `RotationCapabilityOfferProofChallengeV2` (whose doc comment explicitly states the `chain_id` field "prevents replaying the challenge message"), `SignerCapabilityOfferProofChallengeV2` omits `chain_id` entirely. [1](#0-0) 

### Finding Description
`offer_signer_capability` constructs the proof challenge using only `sequence_number`, `source_address`, and `recipient_address` — no `chain_id`: [2](#0-1) 

Compare this with the rotation-capability equivalent, which was explicitly upgraded to V2 specifically to add domain separation via `chain_id` (and `source_address`) to stop replay: [3](#0-2) 

Because Aptos operates multiple networks that share the same account-derivation scheme (mainnet, testnet, and various devnets/local nets), a user's address and public key can be identical across networks, and a freshly created (or otherwise sequence-aligned) account will have the same `sequence_number` on more than one network. A `SignerCapabilityOfferProofChallengeV2` message signed by a user intending to grant `recipient_address` a signer-capability offer on Network A (e.g., a testnet/devnet, or a to-be-launched chain sharing genesis parameters) is byte-for-byte valid input to `verify_signed_message` on Network B, since `source_address`, `recipient_address`, and `sequence_number` can coincide, and `chain_id` is not part of the signed payload at all. If accepted on Network B, the attacker (or an app collecting the signature under one pretext) can call `offer_signer_capability` there and subsequently `account::create_authorized_signer` to obtain a `signer` for the victim's account on Network B, without any admission-time additional signature check tying the approval to that chain.

This is exactly the "domain-binding failure that lets an attacker … rebind a transaction [approval]" category: the authenticated capability-offer message is not bound to the chain it is submitted on, so signing intent for one execution context is misappropriated for another. The multisig account creation flows in the same file explicitly guard against this via a `chain_id` field in `MultisigAccountCreationMessage`/`MultisigAccountCreationWithAuthKeyRevocationMessage`, and `RotationCapabilityOfferProofChallengeV2` does too — highlighting that `SignerCapabilityOfferProofChallengeV2` is the outlier lacking this protection. [1](#0-0) 

### Impact Explanation
If exploited, an attacker can obtain a valid `SignerCapability` for a victim account on an unintended network, then call `create_authorized_signer` to produce a full `signer` for that account there — i.e., unauthorized execution under the victim's signer/account context on a chain the victim never intended to authorize. This is a direct sender/authorization-confusion impact at the capability-approval admission boundary (unauthorized transaction execution under the wrong signer). Severity depends on what state/assets exist for that address on the other chain (e.g., an account created via the same seed phrase on both mainnet and a testnet, or across independently-launched Aptos-based chains).

### Likelihood Explanation
Exploitability requires: (1) a victim signs a `SignerCapabilityOfferProofChallengeV2` off-chain (a normal wallet flow used for delegating account control, e.g., to a dApp/smart-account helper), and (2) the attacker resubmits that exact signed payload via `offer_signer_capability` on a different chain where `source_address`/`sequence_number` match. Sequence-number matching is trivially satisfied for new/never-transacted accounts (sequence 0), and address matching is guaranteed by construction since Aptos addresses are derived identically across networks from the same key material. This makes the likelihood non-trivial in any multi-network deployment scenario (e.g., mainnet vs. any Aptos-compatible testnet/devnet/L2 sharing the framework), though it does require attacker access to a captured signature and a target chain with a matching account state — hence "moderate to high" rather than trivially always-exploitable.

### Recommendation
Add a `chain_id` field to `SignerCapabilityOfferProofChallengeV2` (bump to a V3 or gate behind a feature flag for backward compatibility), matching the pattern already used for `RotationCapabilityOfferProofChallengeV2`, and include `chain_id::get()` when constructing/verifying the challenge in `offer_signer_capability`.

### Proof of Concept
Conceptual PoC (not executable without a live multi-network aptos-core deployment, since the code doesn't already contain a chain_id check to bypass):
1. On Chain A (e.g. testnet), have victim account `V` (fresh, `sequence_number = 0`) sign a `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: V, recipient_address: attacker_controlled_addr }` as part of a legitimate-looking dApp flow (e.g., "delegate account management").
2. Attacker captures `signer_capability_sig_bytes`, `account_scheme`, `account_public_key_bytes`.
3. On Chain B (e.g. a separate Aptos-based network where account `V` also exists with `sequence_number = 0`, and `attacker_controlled_addr` also exists there), attacker calls `account::offer_signer_capability(V_signer_placeholder_not_needed, signer_capability_sig_bytes, account_scheme, account_public_key_bytes, attacker_controlled_addr)`. Since the message content is identical and `chain_id` isn't checked, `verify_signed_message` succeeds and the signer-capability offer is installed for the attacker on Chain B.
4. Attacker calls `account::create_authorized_signer(attacker_signer, V)` on Chain B to obtain a `signer` for `V`, allowing it to move funds/execute arbitrary entry functions as `V` on Chain B.

Note: I was unable to fully confirm real-world deployment topology (i.e., whether distinct Aptos networks in this codebase's ecosystem genuinely reuse identical address/sequence-number state such that this is practically triggerable today), so likelihood should be validated against actual multi-network account state before treating this as immediately exploitable in production; the code-level absence of `chain_id` binding itself, however, is directly verifiable and inconsistent with the sibling rotation-capability protection in the same module.
