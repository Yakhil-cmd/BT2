### Title
Cross-repository `status` webhook mutates unrelated stack's CI-enabled state via unscoped sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `Commit` table, without scoping to the webhook's verified `repository.full_name`, unlike `CheckSuiteHandler` and `PushHandler` which both use the `stacks` helper (scoped via `Repository.from_github_repo_name(repository_name)`). Because Git SHAs are only unique within a repository and Shipit's signature verification only proves *which* repository the payload came from (not which commits it may reference), an attacker who controls a repository can post a `status` webhook whose `sha` collides with a commit belonging to a different tenant's stack, creating a `Status` record on that unrelated commit and toggling that other stack's CI-enabled flag via `Status#enable_ci_on_stack`.

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every commit a `status` webhook is allowed to affect. Instead, `StatusHandler#process` does: [1](#0-0) 
which is `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query. Compare with `CheckSuiteHandler`, which correctly scopes through `stacks` (repository-derived) before touching commits: [2](#0-1) 
and the `Handler` base class exposes exactly this scoping primitive, which `StatusHandler` ignores: [3](#0-2) 

`create_status_from_github!` calls `add_status`, which creates a `Status` row on `stack_id` derived from the commit found (not the attacker's repository): [4](#0-3) 
`Status` has an `after_create :enable_ci_on_stack` callback that unconditionally flips the *found* commit's stack CI cache flag on, regardless of whether that stack intentionally has CI disabled: [5](#0-4) 
which persists via `Stack#enable_ci!` writing to the cache key backing `ci_enabled?`: [6](#0-5) 

`verify_signature` only validates that the payload was legitimately signed by the organization named in `payload['repository']['owner']['login']` (i.e., proves *sender identity*, not that the `sha` inside the payload belongs to that repository): [7](#0-6) 
This means the attacker only needs to control (or be a maintainer of) their own repository — a low-privilege position under the threat model — and can freely choose the `sha` field, `state`, and other payload fields validated only by shape (`ExplicitParameters`), not by cross-referencing to their own repo's actual commit history. If they name a branch/commit whose SHA object happens to be shared (e.g., both stacks track a common upstream/vendored commit, a shared base branch, or an empty-tree/initial commit, or an attacker deliberately engineers a matching SHA by forking history), the `Commit.where(sha:)` lookup will match rows belonging to entirely different repositories/stacks.

Existing guards fail because: `verify_signature` binds sender-to-org, not sha-to-repo; `drop_unhandled_event` only filters unhandled event types; the `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc., not their relationship to the sending repository; and no model validation constrains `Status#stack_id` to correspond to the sender's repository at write time.

### Impact Explanation
A successful cross-repo `status` webhook write causes `Shipit::Status.replicate_from_github!` to create a real `Status` row against a commit that belongs to a stack the attacker doesn't control, and its `after_create` callback calls `commit.stack.enable_ci!`, which writes `true` to `Rails.cache` for that stack's `ci_enabled_cache_key` — a persistent (until cache eviction) cross-tenant configuration mutation. This directly falls under "a payload for one repository mutating another's stack" per the impact taxonomy (Critical). The blast radius includes any Shipit-hosted stack whose SHA space can collide with an attacker-controlled repo's SHA space; the mutation silently re-enables CI gating on a stack an operator had deliberately turned off, which can influence downstream automated behavior gated on `ci_enabled?`/CI status. This is repeatable per matching SHA and requires no privileged Shipit role.

### Likelihood Explanation
The attacker needs only: (1) a GitHub repository already registered as a Shipit-tracked repository owner (to pass `verify_signature`'s org check — note: this only requires the *sending organization* to be known to Shipit, which is true for any repo Shipit already tracks, not that the attacker owns the *target* stack), and (2) the ability to trigger or fabricate a `status` event referencing an arbitrary `sha` string in the JSON body (status events are freely creatable via the GitHub Statuses API by anyone with push access to their own repo, or can be spoofed with a valid signature if the attacker's own repo's webhook secret is used to sign, which is legitimate for their own repo). Exact SHA collision across independent repositories is the main practical constraint, but SHAs are frequently shared across forks, mirrors, or repos sharing common ancestor commits (vendored history, monorepo splits, shared submodules) — a realistic non-cryptographic-break scenario, and the code path itself is unconditionally unscoped, so the vulnerability is fully feasible whenever any sha overlap exists.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, matching the pattern used by `CheckSuiteHandler`/`PushHandler`: iterate `stacks` (derived from `payload.dig('repository','full_name')`) and only look up commits within `stack.commits.where(sha: params.sha)`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, minitest)
test "status webhook for repo A cannot mutate stack B's CI state via shared sha" do
  repo_a = Shipit::Repository.create!(owner: 'attacker', name: 'evil-repo')
  stack_a = Shipit::Stack.create!(repository: repo_a, environment: 'production', branch: 'master')
  commit_a = stack_a.commits.create!(sha: 'deadbeef' * 5, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'a')

  repo_b = Shipit::Repository.create!(owner: 'victim', name: 'secure-repo')
  stack_b = Shipit::Stack.create!(repository: repo_b, environment: 'production', branch: 'master', ignore_ci: true)
  commit_b = stack_b.commits.create!(sha: 'deadbeef' * 5, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'b')

  Rails.cache.delete(stack_b.send(:ci_enabled_cache_key))
  assert_equal false, stack_b.ci_enabled?  # before

  payload = {
    'sha' => commit_a.sha,
    'state' => 'success',
    'repository' => { 'full_name' => repo_a.full_name },
    'branches' => [{ 'name' => 'master' }]
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  stack_b.reload
  assert_equal true, stack_b.ci_enabled?  # after: mutated despite payload only naming repo_a
end
```
This demonstrates `Status.stack_id == commit_b.stack_id (stack_b)` while `payload['repository']['full_name'] == repo_a.full_name`, violating the required binding.
