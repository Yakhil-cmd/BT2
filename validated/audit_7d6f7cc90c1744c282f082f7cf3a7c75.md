### Title
Interest accrual overflows on large positions before the index cap, permanently freezing a market - (File: common/src/rates/simulate.rs)

### Summary
Every market operation first accrues interest, and accrual multiplies the market’s scaled balances by their current indexes before the borrow-index ceiling is applied. When a sufficiently large scaled debt position compounds to an index where `borrowed * borrow_index` exceeds `i128::MAX`, `scaled_to_original` panics with `MathOverflow`; because the panicking call runs before the index update and cap, the state is not advanced and every later operation hits the same overflow. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`accrue_step` converts scaled debt and supply back to original values before computing utilization, the borrow rate, and the next index. [4](#0-3) 

Those conversions delegate to `Ray::mul`, which panics when the resulting fixed-point value does not fit in `i128`; the code performs no checked preflight against the market’s scaled balances. [5](#0-4) [6](#0-5) 

`update_borrow_index` clamps only after computing the new index, so it does not prevent a book whose scaled balance is too large for the already-stored index from overflowing during the next accrual’s initial unscaling. [2](#0-1) 

`global_sync` invokes `accrue_step` for every elapsed chunk before committing the market, while `load_leg` synchronizes the market before borrow, repay, withdrawal, and other position mutations. [7](#0-6) [8](#0-7) 

The permissionless `Controller::update_indexes` path forwards the same assets to the pool’s accrual operation after ordinary caller authorization, so an unprivileged caller can trigger the panicking accrual. [9](#0-8) [10](#0-9) 

The repository’s own boundary test demonstrates the condition: a billion-token, 18-decimal market at sustained high utilization reaches an index whose value representation exceeds `i128::MAX` before `MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment fail with `MathOverflow`. [11](#0-10) [12](#0-11) 

### Impact Explanation
This permanently freezes the affected market rather than merely reverting one oversized request. Once the stored index and scaled balances enter the unsafe region, each later `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, liquidation, cleanup, or rate-model accrual must first complete `global_sync` and therefore panics at the same unscaling step. [13](#0-12) [14](#0-13) 

Suppliers cannot withdraw their deposits, borrowers cannot repay, liquidators cannot reduce unsafe debt, and even an administrative rate-model update accrues under the old model before writing a replacement. [15](#0-14) [16](#0-15) 

This is permanent freezing of user funds and a protocol-operability failure, not a bounded fail-closed rejection of malformed input: valid deposits and debt become inaccessible solely because accrued fixed-point value crosses the `i128` representation boundary. [11](#0-10) 

### Likelihood Explanation
The trigger is economically expensive and market-configuration dependent: it requires a very large scaled book, sufficiently permissive supply/borrow caps, and sustained utilization at a steep borrow-rate segment until the index reaches the unsafe bound. [17](#0-16) 

No privileged operation is needed to trigger accrual once such a market exists because `update_indexes` is permissionless, but the attacker cannot create the necessary index or book size in one input and must rely on capital, time, and configured market parameters. [9](#0-8) [18](#0-17) 

The configured ceiling is `1e36` raw index units, while the demonstrated value ceiling can be reached around an index multiplier of roughly 170 times for the test book, so the representational boundary precedes the intended index cap by many orders of magnitude. [19](#0-18) [20](#0-19) 

### Recommendation
Represent or bound accrued market value before converting scaled balances back to original values. In particular, derive a market-specific safe index bound from `max(supplied, borrowed)` and `i128::MAX`, apply that bound in addition to `MAX_BORROW_INDEX_RAY`, and make accrual saturate at that bound instead of panicking.

The bound should be enforced both when accepting new scaled supply/debt and during index updates, so a market cannot transition into a state where the very first unscaling operation required by every later verb necessarily overflows.

A safer implementation would:

- calculate `scaled * index` through a checked result before utilization or interest calculations;
- clamp the next index to the greatest value whose resulting supply and debt totals fit in `i128`;
- reject new supply or borrows that would remove all safe index headroom;
- add a regression test showing `update_indexes`, `repay`, and `withdraw` remain executable after the boundary is reached.

### Proof of Concept
The existing regression test constructs a valid unprivileged path: a user supplies `1_000_000_000` whole units of an 18-decimal asset, another account posts sufficient collateral and borrows 98 percent of that market, and any caller subsequently invokes `update_indexes` after time advances. [21](#0-20) 

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break e; // GenericError::MathOverflow
    }
}

assert_contract_error(
    t.try_withdraw_raw(BOB, "BIG18", 1),
    errors::MATH_OVERFLOW,
);
assert_contract_error(
    t.try_repay(ALICE, "BIG18", 1.0),
    errors::MATH_OVERFLOW,
);
```

The test confirms that the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, proving the index cap never had an opportunity to protect the market. [12](#0-11)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```
