### Title
Observable Timing Discrepancy in ECDH Shared-Secret Derivation for Device Messages Enables Private-Key Recovery - (File: `device.js`)

### Summary
`deviceMessage` decryption derives an AES key via ECDH between the recipient's long-lived/temporary device private key and an attacker-supplied ephemeral public key (`dh.sender_ephemeral_pubkey`). This operation is invoked on every inbound encrypted package a paired device or hub-relayed peer sends, and the recipient's private key (temp or permanent) is reused across many such messages before rotation. This mirrors the reported bug class (CWE-385/CWE-733): a secret-key-dependent elliptic-curve operation repeatedly invocable by an unprivileged remote party, where a timing side channel in the underlying point-multiplication/verification path could let an attacker recover the private key through many queries.

### Finding Description
`deriveSharedSecret` performs `ecdsa.ecdh(pubkey, privKey, ...)` where `privKey` is the recipient device's permanent key, active temp key, or previous temp key, and `pubkey` is fully attacker-controlled (`objEncryptedPackage.dh.sender_ephemeral_pubkey`), as seen in `decryptPackage`: [1](#0-0) [2](#0-1) 

Any device that is a correspondent (paired device) — or a hub relaying `hub/deliver` messages on the attacker's behalf — can submit an unlimited number of crafted encrypted packages addressed to a victim device. Each package forces the victim to run ECDH with a new attacker-chosen ephemeral pubkey against its own long-lived secret key (`objMyPermanentDeviceKey.priv`) or its current/previous temp key (`objMyTempDeviceKey.priv` / `objMyPrevTempDeviceKey.priv`). The temp key persists across `TEMP_DEVICE_KEY_ROTATION_PERIOD` and its `use_count` is only incremented, not capped, so an attacker gets effectively unbounded ECDH invocations against the same secret scalar before rotation occurs: [3](#0-2) 

This is architecturally identical to the reported Kyber decapsulation oracle: an attacker who can submit many "decapsulation" (here, ECDH-derivation) requests against a single private key, and who can observe timing (e.g., round-trip latency of `hub/deliver`'s response, or of any observable follow-up such as auth-tag verification failure vs. success timing in `decipher.setAuthTag`/`decipher.final()`), could in principle extract information about the private scalar if the ECDH computation of the underlying `secp256k1` npm binding is not fully constant-time for arbitrary (attacker-chosen, possibly invalid or edge-case) public keys.

### Impact Explanation
If the underlying `ecdsa.ecdh` implementation exhibits secret-dependent timing (analogous to the clang-miscompiled constant-time Kyber code in the advisory), a remote correspondent or a malicious hub relaying messages could recover a victim's permanent device private key or temp device key. Compromise of the permanent device key allows impersonation of the device for all future pairings, tampering with wallet/AA-triggering message exchanges (e.g., shared-address cosigning requests, private payment chain delivery), and forging `hub/login`/`hub/temp_pubkey` signatures, leading to unauthorized fund movement in multisig/shared-address flows and loss of confidentiality/integrity of private payment chains that funnel to on-chain spending.

### Likelihood Explanation
Likelihood depends entirely on whether the specific `secp256k1` npm binding's `ecdh` routine has an exploitable timing side channel for attacker-chosen curve points — this has not been verified in the given code (the vulnerability, if any, lives in the native/JS `secp256k1` dependency, not in ocore's own arithmetic). ocore's `deriveSharedSecret`/`decryptPackage` code path is fully reachable by any paired correspondent or a hub without additional privilege, and offers no rate limiting or key-rotation forcing on ECDH invocation count, which raises likelihood if the underlying primitive is timing-unsafe. However, confirming exploitability requires benchmarking the specific `secp256k1` library build/platform, which is outside what the ocore repository content can prove.

### Recommendation
- Rate-limit or cap the number of ECDH derivations permitted against a single temp/permanent key within a rotation window; force temp-key rotation after a small `use_count` threshold rather than only on a timer.
- Validate `sender_ephemeral_pubkey` structurally before use and consider re-deriving the shared secret using a vetted constant-time ECDH implementation (verify the specific `secp256k1` npm build's `ecdh` guarantees constant-time behavior on all supported platforms/compilers).
- Ensure error paths (`setAuthTag`/`decipher.final()` failures, JSON parse failures) return in constant time relative to success paths to avoid amplifying any timing signal from the ECDH step itself.

### Proof of Concept
Conceptual (not verified against the actual `secp256k1` binding's timing behavior):
1. Attacker becomes a correspondent device of the victim (or controls/colludes with the victim's hub).
2. Attacker repeatedly sends `hub/deliver` messages with `encrypted_package.dh.sender_ephemeral_pubkey` set to many different, adversarially chosen curve points, targeting the victim's known temp or permanent pubkey (`recipient_ephemeral_pubkey`).
3. For each message, the victim's `decryptPackage` → `deriveSharedSecret` runs `ecdsa.ecdh(pubkey, priv_key, ...)` using the victim's secret key; the attacker measures the wall-clock time until the victim's observable response (accept/error over the hub, or timing of subsequent activity).
4. Statistical analysis of timing versus chosen input points, following the methodology in the referenced `clangover`/PQClean issue, would recover secret-key bits if `ecdsa.ecdh` is not constant-time for the given inputs on the deployed platform.

function deriveSharedSecret(peer_b64_pubkey, privKey){
	var pubkey = new Buffer(peer_b64_pubkey, 'base64');
	var shared_secret_src = Buffer.from(ecdsa.ecdh(pubkey, privKey, {hashfn: (x, y) => x}, Buffer.alloc(32)));
	var shared_secret = crypto.createHash("sha256").update(shared_secret_src).digest().slice(0, 16);
	return shared_secret;
}
