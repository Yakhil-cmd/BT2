Based on my investigation, I found a strong analog to the reported bug class in the Alpenglow VAT (Validator Admission Ticket) burn mechanism, where a filtering calculation and the actual deduction calculation are computed at different points/using different logic, creating a scenario where the assumed-sufficient balance check does not match the amount actually deducted — mirroring the "margin calculated one way but actual amount taken differs" bug class from the report.

### Title
Vote-account VAT-burn amount can exceed the filtering threshold used to admit accounts, causing a guaranteed panic (`expect`) and epoch-boundary halt - ([File: runtime/src/bank.rs])

### Summary
`maybe_burn_vat_from_staked_accounts` unconditionally deducts `vat_to_burn_per_epoch()` lamports from every vote account that was admitted by `clone_and_filter_for_vat`, relying on an `.expect()` that the balance is sufficient [1](#0-0) . The admission filter in `clone_and_filter_for_vat` uses `minimum_vote_account_balance` computed by `minimum_vote_account_balance_for_vat` at filtering time [2](#0-1) [3](#0-2) . These two computations — the filter threshold and the actual burn amount — are derived independently from `self.vat_to_burn_per_epoch()`/`current_slot_params()` [4](#0-3) , similar to how the Sherlock report's `margin` was computed independently from the actual `exchange()` output, rather than being derived from the true, executed amount.

### Finding Description
`clone_and_filter_for_vat` in `vote/src/vote_account.rs` filters vote accounts by checking `vote_account.lamports() >= minimum_vote_account_balance` where `minimum_vote_account_balance` is supplied by the caller (`Bank::minimum_vote_account_balance_for_vat`) [5](#0-4) . This threshold is calculated as `rent_exempt_minimum + vat_to_burn_per_epoch()` at the time filtering occurs, using the current bank's `slot_params_at_slot` [6](#0-5) [7](#0-6) .

Later, `maybe_burn_vat_from_staked_accounts` — called against `epoch_stakes` that were captured/filtered earlier — re-derives `vat_to_burn_per_epoch()` from `self` (the *current* bank state, which may correspond to a different slot/epoch than when filtering happened) and unconditionally subtracts it from each vote account's lamports with a hard `.expect()` rather than a checked/saturating operation with graceful handling [8](#0-7) .

Because `vat_to_burn_per_epoch()` is a function of `current_slot_params()`, which changes based on slot-time-reduction feature activations (as seen in `slot_time_reduction_vat_burns` and the epoch-boundary transition logic in `slot_params.rs`), the value used for filtering (in an earlier epoch/slot context) can diverge from the value used at burn time if a feature activates between the two calls, or if the "admitted" set was computed from a stale/cached `epoch_stakes` snapshot while `self.vat_to_burn_per_epoch()` reflects a newer slot. If the burn-time VAT amount is larger than the filter-time VAT amount used to admit the account, the `checked_sub(...).expect(...)` in `maybe_burn_vat_from_staked_accounts` will panic, because the comment explicitly assumes "Vote accounts should have already been filtered to contain enough balance for the VAT" [1](#0-0)  — an assumption that is not actually re-validated at burn time, exactly analogous to the Sherlock finding where the margin was assumed sufficient based on a separately-computed value rather than the actual output/amount used at execution time.

### Impact Explanation
A panic inside bank processing at an epoch boundary (this function is invoked as part of epoch-transition/Alpenglow VAT processing) causes the validator to halt or crash while processing that slot. Since this logic runs deterministically for every validator replaying the same block, a mismatch between the filtering threshold and the burn amount would cause **all** validators to panic identically at the same slot — resulting in a cluster-wide epoch-boundary halt, which is one of the explicitly accepted impact categories.

### Likelihood Explanation
This requires the VAT-per-epoch value to change between the time vote accounts are filtered (`clone_and_filter_for_vat`) and the time the burn is executed (`maybe_burn_vat_from_staked_accounts`), e.g., due to a slot-time-reduction feature activating mid-flow, or the epoch_stakes snapshot used for filtering being computed against different slot params than `self` at burn time. Given the codebase's own comments acknowledge multiple VAT tiers via `slot_time_reduction_vat_burns()`/`current_slot_params()` and epoch transitions, this is a plausible, not merely theoretical, timing dependency, though it depends on precise sequencing that I could not fully trace end-to-end (i.e., confirm whether `epoch_stakes` passed into `maybe_burn_vat_from_staked_accounts` is always guaranteed to be filtered with the exact same `vat_to_burn_per_epoch()` value used inside this function at call time).

### Recommendation
Compute the VAT-to-burn amount once, pass it explicitly into both the filtering step and the burn step (rather than deriving it twice from `self`/`current_slot_params()`), and replace the `.expect()` in `maybe_burn_vat_from_staked_accounts` with a `saturating_sub` (burning at most the available balance) or an explicit, non-panicking error path so that any residual mismatch degrades gracefully rather than halting the bank.

### Proof of Concept
No executable PoC was constructed; this is a static code-path analysis. A concrete PoC would require demonstrating a scenario where `epoch_stakes` admitted via `clone_and_filter_for_vat` with one `minimum_vote_account_balance` is later burned via `maybe_burn_vat_from_staked_accounts` using a larger `vat_to_burn_per_epoch()` value — for example, by activating a slot-time-reduction feature between epoch-stakes snapshot creation and VAT-burn execution within the same epoch-transition flow. I was unable to fully confirm within the available search whether current call sites guarantee same-value derivation in all cases; this should be verified against `runtime/src/slot_params.rs` and the call sites of `maybe_burn_vat_from_staked_accounts` before treating this as a confirmed exploitable path.
