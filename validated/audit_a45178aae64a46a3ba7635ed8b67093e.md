### Title
Duplicate members in `r of set` / `weighted and` definitions allow a single signature to be double-counted toward the required threshold - (File: definition.js)

### Summary
The address/asset condition validator in `definition.js` never checks that the elements of an `r of set` or `weighted and` group are distinct. A member (an `["address", X]` or `["sig", {pubkey}]` leaf) can appear more than once in the same `set`, and each occurrence is validated independently. Since signing/verification is deterministic per-path, one actual signer can satisfy multiple "slots" of the required count with what is effectively a single signing action, defeating the multi-party threshold that the definition is supposed to enforce. This is the same bug class as the FeeSplitter "duplicate shareholder" finding: a collection that must contain unique members is never checked for uniqueness, letting one entry double-count.

### Finding Description
`validateDefinition()` in [1](#0-0)  validates `r of set` by iterating `args.set` and counting how many members provide a signature, but does not verify that the members of `args.set` are distinct from each other (no hashing/dedup/sorted-uniqueness check, unlike the sibling function `checkAttestorList()` which explicitly enforces `arrAttestors[i] <= prev` to guarantee sortedness/uniqueness, see [2](#0-1) ). The same gap exists for `weighted and` at [3](#0-2) .

The actual signature-checking counterpart, `validateAuthentifiers()`, evaluates each set element independently by path and sums up satisfied members: for `r of set` at [4](#0-3)  and for `weighted and` at [5](#0-4) . For an `["address", X]` leaf, evaluation recurses into `X`'s own definition *using the same enclosing path* (see [6](#0-5) ), and eventually resolves to a `sig` leaf that is checked against the authentifier supplied at that exact path. If the same address/pubkey is placed twice in the set (e.g. at paths `r.0` and `r.1`), a single deterministic ECDSA signature over the same unit hash and key is valid at both paths, so the author only needs to submit the same signature bytes under two different authentifier path keys to satisfy both slots.

Because address/wallet definitions of this form (`r of set`, `weighted and`) are proposed and exchanged directly between correspondent devices when creating shared/multisig addresses (e.g. `handleNewSharedAddress()` in [7](#0-6) , which calls `validateAddressDefinition()` → `Definition.validateDefinition()` at [8](#0-7) ), a malicious co-signer can propose (or accept and forward) a definition containing a duplicated member referencing their own address/key, alongside honest co-signers' addresses, while the required threshold looks like it demands multiple independent approvals (e.g. "2 of 3").

### Impact Explanation
This breaks the security assumption behind shared/multisig addresses: honest co-signers believe funds require signatures from `required` distinct parties, but the malicious proposer can unilaterally satisfy the threshold alone by duplicating their own set entry, enabling unauthorized spending from what was intended to be a multi-party-controlled address. This falls squarely in the "concrete unauthorized spending" impact category for wallet/multisig-address message handling reachable by an ordinary paired device (no privileged/node role required).

### Likelihood Explanation
Likelihood is limited to the specific scenario of collaboratively created shared/multisig addresses where at least one participant is malicious and controls definition proposal/exchange; the definition is validated (`validateDefinition`) but this validation never rejects duplicate `set` members, so the malicious construction passes validation cleanly, and the double-counting exploit only requires supplying the same deterministic signature under two authentifier paths — a straightforward manipulation available to anyone who can propose a shared-address definition.

### Recommendation
In `definition.js`, when validating `r of set` and `weighted and` (both in `validateDefinition()` and, defensively, in `validateAuthentifiers()`), compute a canonical hash/serialization of each `args.set[i]` element and reject the definition if any two elements are structurally identical (or, at minimum, reject duplicate `["address", X]` / `["sig", {pubkey}]` leaves within the same set), mirroring the sortedness/uniqueness check already used for `checkAttestorList()` and `earned_headers_commission_recipients`.

### Proof of Concept
1. Device A (attacker) and Device B (victim) agree to create a "2 of 3" shared address, believing the third slot also maps to B's other key or a third party.
2. A proposes (or forwards) an address definition: `["r of set", {required: 2, set: [["address", A_addr], ["address", A_addr], ["address", B_addr]]}]`.
3. `handleNewSharedAddress()` / `validateAddressDefinition()` → `Definition.validateDefinition()` accepts this definition because `r of set` validation never checks that `set` members are distinct.
4. When spending, A signs the unit once with its private key and submits the identical signature string under authentifier paths `r.0` and `r.1`.
5. `validateAuthentifiers()`'s `r of set` handler counts both `r.0` and `r.1` as satisfied (`count += 2`), meeting `required = 2` without B's participation, allowing A to spend from the address alone.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
