### Title
Unbounded scan of `assocUnstableUnits`/`assocUnstableMessages` on the hot path of unit/TPS-fee validation and AA data-feed reads can degrade to the point that new units and AA triggers can no longer be confirmed - (File: `storage.js`)

### Summary
`getCurrentTps()`/`getCurrentTpsFee()`/`getCurrentTpsFeeToPay()` in `storage.js` iterate over the entire in-memory `storage.assocUnstableUnits` map on every call, and `readDataFeedValue()` in `data_feeds.js` (together with `storage.getUnconfirmedAADefinition`/`getUnconfirmedAADefinitionsPostedByAAs`) iterate over the entire `storage.assocUnstableMessages` map. Both maps are populated purely by ordinary, unprivileged actions — any unit poster adding parents/messages that haven't stabilized yet, or any AA trigger sender causing `data_feed`/`definition` messages to remain unstable. There is no hard cap on how large these maps can grow, and these functions are on paths executed for every incoming unit (TPS fee validation) and every AA trigger evaluation that reads a data feed (`data_feed[...]` formula operator) or defines a nested AA.

### Finding Description
`getCurrentTps(shift, count_units)` [1](#0-0)  loops `for (let unit in assocUnstableUnits)` over every unit that has not yet stabilized, without any size limit. This function is used by `getCurrentTpsFee()`/`getCurrentTpsFeeToPay()` [2](#0-1) , which validation.js consults on the fee-validation path for units carrying the `tps_fee` field (mandatory for version-4 unit validation) [3](#0-2) . Because `assocUnstableUnits` accumulates one entry per unstable unit — driven purely by the ordinary DAG-growth pace of unprivileged posters — every subsequently posted unit pays the cost of iterating over that ever-growing set until stabilization catches up.

Similarly, `readDataFeedValue()` with `unstable_opts` set loops `for (var unit in storage.assocUnstableMessages)` over every currently unstable unit that carries tracked message types, before finally filtering by author address [4](#0-3) . This function is invoked whenever an AA formula reads a data feed, which is entirely user/AA-triggerable and has no hard limit on the number of unstable data-feed-bearing units that can exist concurrently. The related helpers `storage.getUnconfirmedAADefinition()` and `storage.getUnconfirmedAADefinitionsPostedByAAs()` — used inside `storage.insertAADefinitions()`, which runs inside the write transaction (`writer.js`) whenever an AA-defined-by-AA unit is written — perform the identical full scan of `assocUnstableMessages` [5](#0-4) .

None of these functions bound the number of unstable units/messages they will scan; the maps are only shrunk when the main chain advances and units stabilize (`markMcIndexStable` removes entries from `assocUnstableUnits`) [6](#0-5) . If unstable-unit growth outpaces stabilization (e.g., a burst of units/witnessing issues, or heavy concurrent AA/data-feed activity from ordinary, non-privileged actors), the size of these maps — and thus the per-call cost of `getCurrentTps`/`readDataFeedValue`/`getUnconfirmedAADefinition*` — grows without bound. Because `getCurrentTpsFee` sits on the mandatory tps-fee validation path for every incoming unit, and `readDataFeedValue`/`insertAADefinitions` sit on the AA-trigger execution path (which itself is serialized under the `aa_triggers` mutex in `aa_composer.js`), a sufficiently large backlog of unstable units can make per-unit validation and AA-trigger processing increasingly expensive, exactly mirroring the referenced bug class: an unprivileged actor's ordinary usage (posting units / triggering AAs / posting data feeds) grows an unbounded collection that a critical, unavoidable core routine must fully scan, with no alternative code path to shrink it other than the normal stabilization process itself.

### Impact Explanation
If the unstable set grows large enough, per-unit tps-fee computation and AA trigger execution (data feed reads, nested-AA-definition inserts) become progressively slower. Since `getCurrentTpsFeeToPay` is required for validating every unit posted after the v4 upgrade and `handleAATriggers` serializes all AA trigger processing under a mutex, a sufficiently degraded scan time can slow down or stall the pipeline that confirms new units and processes AA triggers, which corresponds to "a network unable to confirm new units" and to state (AA-held funds, data-feed-gated logic) becoming effectively frozen because the very mechanism required to advance state (stabilization, trigger execution) becomes the bottleneck itself.

### Likelihood Explanation
Growth of `assocUnstableUnits`/`assocUnstableMessages` is driven entirely by ordinary, unprivileged usage: posting units, posting data feeds, and triggering AAs that define nested AAs. No special privilege or malicious protocol violation is needed — only sustained normal activity outpacing the rate at which units stabilize (which itself can be affected by witnessing/branching dynamics that are also influenced by ordinary posting behavior). This mirrors the original report's likelihood profile: normal, permitted usage (buying protection / posting units) that is not capped anywhere in the affected code paths.

### Recommendation
Introduce hard bounds and/or amortized/indexed lookups instead of full scans of `assocUnstableUnits`/`assocUnstableMessages`:
- Maintain per-address or per-feed indexes for unstable data-feed messages (`storage.assocUnstableMessages`) instead of scanning the entire map in `readDataFeedValue`, `getUnconfirmedAADefinition`, and `getUnconfirmedAADefinitionsPostedByAAs`.
- Cap or incrementally maintain the TPS counters in `getCurrentTps` rather than recomputing them by iterating the full `assocUnstableUnits` map on every call.
- Consider rate-limiting or fee-scaling mechanisms tied directly to the size of the unstable-unit backlog to disincentivize unbounded growth, and ensure these scanning functions have a big-O bound independent of total unstable-unit count.

### Proof of Concept
Not independently reproduced in this review; the finding is based on static analysis of the cited code paths (`storage.js` `getCurrentTps`, `data_feeds.js` `readDataFeedValue`, `storage.js` `getUnconfirmedAADefinition*`) which lack any size cap on the collections they fully iterate, combined with the confirmed call sites showing these functions run on the unit-validation and AA-trigger-processing hot paths. Full dynamic verification (e.g., measuring per-call latency growth as `assocUnstableUnits`/`assocUnstableMessages` size increases) was not performed and would require a running node/test harness, which is outside the scope of this static code review.

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}

// arrAddresses is an array of AA addresses whose definitions are posted by other AAs
function getUnconfirmedAADefinitionsPostedByAAs(arrAddresses) {
	var payloads = [];
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (!objUnit.bAA)
			continue;
		assocUnstableMessages[unit].forEach(function (message) {
			if (message.app !== 'definition')
				return;
			var payload = message.payload;
			if (arrAddresses.indexOf(payload.address) >= 0)
			payloads.push(payload);
		});
	}
	return payloads;
}

function getCurrentTpsFee(shift = 0, count_units = 1) {
	const tps = getCurrentTps(shift, count_units);
	console.log(`current tps with shift ${shift} ${tps}`);
	const base_tps_fee = getSystemVar('base_tps_fee', last_stable_mci);
	const tps_interval = getSystemVar('tps_interval', last_stable_mci);
	return Math.round(base_tps_fee * (exp(tps / tps_interval) - 1));
}

function getCurrentTpsFeeToPay(shift = 0, count_units = 1) {
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_stable_mci);
	return Math.round(tps_fee_multiplier * getCurrentTpsFee(shift, count_units));
}
