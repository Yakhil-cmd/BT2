## Title
Webhook signature verification is bound to an attacker-controlled `repository.owner.login`/`organization.login` field while the resulting handler acts on a different attacker-controlled `repository.full_name` field, letting a forged event authenticated against one GitHub organization write to stacks belonging to any other organization tracked by the same Shipit install - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, taken directly from the unauthenticated request body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

Once the signature check passes, the actual event handlers resolve the `Repository`/`Stack` to mutate using a *different* body field, `repository.full_name`, with no scoping back to the organization that was used for authentication: [3](#0-2) 

This is the same class of bug as the `Subaccount#execute` finding: a value that is acted upon (`repository.full_name`, deciding which repo/stack is written to) is not the value that was actually covered/bound by the trust check (`repository.owner.login`, deciding which secret authorizes the request). The binding that should hold is `organization authenticated == organization of the repository written`, and it does not.

### Finding Description
Shipit supports multiple GitHub organizations sharing one instance, each with its own (optional) `webhook_secret`: [4](#0-3) 

`GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when no `webhook_secret` is configured for the organization that was resolved: [5](#0-4) 

`webhook_secret` is documented as optional (`# nil`) in every secrets template shipped with the engine: [6](#0-5) [7](#0-6) 

So, in a legitimate/documented multi-org configuration where at least one onboarded organization has not set a `webhook_secret`, `POST /webhooks` will accept *any* unauthenticated request as long as the body's `repository.owner.login` (or `organization.login`) names that secret-less organization - `verify_signature` never inspects any other field of the payload.

The event is then dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [8](#0-7) 

Every handler resolves which `Repository`/`Stack` to act on from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`, with no restriction that this repository must belong to the organization that was just verified: [9](#0-8) 

For example, `PushHandler` uses this unscoped lookup to select stacks and force a GitHub resync: [10](#0-9) 

Because `repository_owner` (used to pick the authenticating org/secret) and `repository.full_name` (used to pick the repository actually acted upon) are independent, unrelated fields in the same attacker-supplied JSON body, an attacker can set them to point at two different organizations - satisfying the (weak or absent) verification for org A while driving side effects against any Stack under org B, C, etc., that also happen to be registered in the same Shipit instance.

### Impact Explanation
This breaks the authorization boundary between GitHub organizations sharing one Shipit deployment: `organization authenticated == organization/repository written` is required but not enforced. An external, unauthenticated attacker can:
- Trigger `PullRequest` handlers (`opened`, `closed`, `labeled`, `reopened`, `assigned`, `unlabeled`, `edited`) to create/mutate `MergeRequest`/review-stack state for a repository/organization that never authorized the request.
- Trigger `PushHandler` to force `stack.sync_github` on arbitrary stacks belonging to unrelated organizations, causing the app to act on repositories the forging request had no legitimate authorization for.
- Trigger `MembershipHandler`/`StatusHandler`/`CheckSuiteHandler` similarly cross-organization.

This is a cross-organization/cross-repository write capability achievable by an unprivileged, unauthenticated attacker who only needs one organization in the shared Shipit instance to be configured without a `webhook_secret` (an explicitly supported, documented configuration) or, more narrowly, to know/replay that organization's `webhook_secret` while forging the `repository.full_name` of a target elsewhere. That satisfies the "cross-repository writes" Critical-impact category defined in scope.

### Likelihood Explanation
Likelihood depends on deployment configuration: it requires (a) the multi-org config schema to be in use (`Shipit.github_organizations`), and (b) at least one of the configured organizations to have a blank `webhook_secret` - both of which are first-class, documented, supported states of this engine (not misconfiguration outside its scope), as shown by every shipped secrets template leaving `webhook_secret` empty. No GitHub App private key, session, `ApiClient` token, or repository write access is required to reach `POST /webhooks`; the endpoint is intentionally public for GitHub to call.

### Recommendation
Bind the two values instead of treating them independently:
- After resolving the `Repository`/`Stack` in `Shipit::Webhooks::Handlers::Handler#stacks`, verify that the repository's owner matches the `repository_owner` (or `organization.login`) that was used to select the GitHub App/secret in `WebhooksController#verify_signature`, and reject the event otherwise.
- Alternatively/additionally, require a non-blank `webhook_secret` for every configured organization and refuse to boot (or refuse all webhooks for that organization) if one is missing, removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (no `webhook_secret` set, per the documented default) and `org-b` (any secret), each with repositories onboarded as Shipit stacks.
2. As an unauthenticated attacker, send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/private-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'org-a')`; since `org-a` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally. [5](#0-4) 
4. `PushHandler#stacks` resolves the target using `repository.full_name` ("org-b/private-repo"), completely ignoring `org-a`, and invokes `stack.sync_github` on `org-b`'s stack. [9](#0-8) [10](#0-9) 

I was not able to trace further downstream whether `sync_github`/PR-handler side effects can be escalated all the way to an actual unauthorized GitHub merge or deploy within the tool-call budget available; that would require reading `Stack#sync_github`, `MergeRequest`, and the merge-queue job code, which I did not have remaining iterations to inspect. The cross-organization write/authorization-bypass itself, however, is fully verified against the cited source.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
