### Title
`ReviewStack#env` allows a PR label named "environment" to override the `ENVIRONMENT` variable interpolated into deploy commands - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges the stack's base `env` hash (which sets `'ENVIRONMENT' => environment`) with a hash built from `pull_request.labels`, using `Hash#merge`, whose argument values win on key collision. A pull request label literally named `environment` (any case) is upcased to `ENVIRONMENT` and unconditionally overwrites the true `@stack.environment` value in the resulting env hash, which then flows unfiltered into `Command#interpolate_environment_variables` for deploy steps like `cap $ENVIRONMENT deploy`.

### Finding Description
The claimed binding was: *the value substituted for `$ENVIRONMENT` in `Command#interpolate_environment_variables` == `@stack.environment`, and is not derivable from `pull_request.labels`*. Tracing the code shows this binding does **not** hold.

`Stack#env` builds the base hash with `'ENVIRONMENT' => environment` [1](#0-0) . `ReviewStack#env` overrides this method:

```ruby
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
``` [2](#0-1) 

`Hash#merge` gives precedence to the argument hash on key collisions. Because label names are simply upcased with no denylist for reserved keys (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`), a PR label named `"environment"` produces `{'ENVIRONMENT' => 'true'}`, which overwrites the `'ENVIRONMENT' => @stack.environment` entry set by `super`. This is not a hypothetical: the existing test suite for this exact merge behavior only checks non-colliding labels (`WIP`, `BUG`) [3](#0-2) , and never tests a label colliding with a reserved key.

This env hash reaches `TaskCommands#env`, which merges `@stack.env` directly with no filtering:
```ruby
def env
  super
    .merge(@stack.env)
    .merge('SHIPIT_USER' => ..., ...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
``` [4](#0-3) 

No call to `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` (the only whitelist mechanism, via `EnvironmentVariables#permit`) [5](#0-4)  occurs in this path, so the tampered `ENVIRONMENT` value is not sanitized.

`Commands#perform`/`TaskCommands#perform` builds `Command.new(command_line, env:, chdir:)` for each deploy step [6](#0-5) , and typical deploy steps for Capistrano projects are literally `cap $ENVIRONMENT deploy` [7](#0-6) . `Command#interpolate_environment_variables` substitutes `$ENVIRONMENT` using this same tampered `env` hash [8](#0-7) , and `start` spawns the interpolated command via `PTY.spawn` [9](#0-8) .

**Attack**: the attacker opens a pull request in a repository configured for review stacks, and applies a label named `environment` to that PR (labeling one's own PR is within the stated attacker capabilities). When a deploy/task runs for that review stack, `$ENVIRONMENT` in the generated Capistrano/step commands resolves to `"true"` instead of the operator-assigned `pr<number>` environment value, causing `cap true deploy` (or similar) to execute — an unintended deploy target/stage, not the one the operator configured.

Existing guards do not prevent this: `EnvironmentVariables#permit` is never invoked on this path (only `interpolate` is used, which performs no key whitelisting) [10](#0-9) , and there is no reserved-word denylist in `ReviewStack#env`'s label-merging logic.

### Impact Explanation
An unprivileged PR author (or anyone able to label their own PR on a repo with review stacks enabled) can silently redirect deploy commands away from the operator-intended target/environment string, without any signed webhook forgery or privilege escalation — this is an unauthorized deploy against the wrong target, matching the Critical category ("unauthorized deploy...driven by attacker-controlled label text"). The blast radius is scoped to the affected review stack/repository (not cross-tenant), but is fully repeatable on every deploy/task triggered for that stack as long as the offending label remains applied.

### Likelihood Explanation
Preconditions: the repository must have review stacks enabled (a supported, common Shipit feature) and use a deploy step that interpolates `$ENVIRONMENT` (default for Capistrano-detected specs, and common in custom `deploy.override` steps). Cost to the attacker is trivial: apply a label named `environment` to their own PR, no secrets or elevated roles required.

### Recommendation
In `ReviewStack#env`, filter out label names that collide with reserved/base environment variable keys (e.g., `ENVIRONMENT`, `BRANCH`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `LAST_DEPLOYED_SHA`) before merging, or merge with reversed precedence (`labels_hash.merge(super)`) so base/system values always win over label-derived ones.

# test/models/shipit/review_stack_test.rb
test "#env does not allow a label to override the reserved ENVIRONMENT key" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["environment"]

  assert_equal stack.environment, stack.env["ENVIRONMENT"]  # currently fails: env["ENVIRONMENT"] == "true"
end

# test/unit/command_test.rb
test "#interpolated_arguments is not hijacked by a label named environment" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["environment"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  command = Command.new('cap $ENVIRONMENT deploy', env: Shipit::TaskCommands.new(task).env, chdir: '.')
  assert_equal ["cap #{stack.environment} deploy"], command.interpolated_arguments
  # currently fails: resolves to "cap true deploy"
end
```

      end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
