### Title
`provision?` operator-precedence bug allows PR-label bypass of `review_stacks_enabled: false` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
In `OpenedHandler#provision?`, Ruby's `&&`/`||` precedence causes `repository.review_stacks_enabled` to gate only the first disjunct (`provisioning_behavior_allow_all?`), while the `allow_with_label` and `prevent_with_label` disjuncts are evaluated independently of it. Consequently, a repository with `review_stacks_enabled: false` but `provisioning_behavior: 'allow_with_label'` (or `prevent_with_label`) will still provision a review stack whenever an attacker-controlled pull request satisfies the label condition.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold for any branch of `provision?` to return `true`.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` only participates in the first term. If `review_stacks_enabled == false`, `provisioning_behavior == 'allow_with_label'`, and the pull request carries `repository.provisioning_label_name`, the second disjunct alone evaluates to `true`, so `provision?` returns `true` even though the equality `review_stacks_enabled == true` is false.

This diverges from the codebase's own established (and correct) pattern in `LabeledHandler#respond_to_label_change?`, where `review_stacks_enabled` is explicitly ANDed with the *entire* `(archive? || unarchive?)` expression:
```ruby
def respond_to_label_change?
  params.action == "labeled" &&
    pull_request_state == "open" &&
    repository.review_stacks_enabled &&
    (archive? || unarchive?)
end
``` [2](#0-1) 

confirming the intended semantics of `provision?` were meant to require `review_stacks_enabled` unconditionally, but the missing parentheses broke that intent.

`provision?` gates `respond_to_pull_request_opened?`, which gates `process`:
```ruby
def process
  return unless respond_to_pull_request_opened?
  Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter
    .new(params, scope: repository.review_stacks).find_or_create!
end
``` [3](#0-2) 

`find_or_create!` creates a `ReviewStack` record and enqueues it into `Shipit::ReviewStackProvisioningQueue`:
```ruby
def create!
  ReviewStack.transaction do
    stack = scope.create!(stack_attributes)
    stack.build_pull_request.update!(github_pull_request: params.pull_request)
  end
  Shipit::ReviewStackProvisioningQueue.add(stack)
  @stack = stack
end
``` [4](#0-3) 

An unprivileged external contributor who can open a pull request against the target public repository (a normal fork-PR contribution) and add a label matching `repository.provisioning_label_name` triggers a legitimately GitHub-signed `pull_request.opened` webhook. No forged signature or Shipit credential is needed — the webhook is real, signed by GitHub, and delivered because the attacker performed a permitted GitHub action (opening a PR with a label on a public repo, or any repo where they have PR/label permission). None of `verify_signature`, `ExplicitParameters`, or `force_github_authentication` block this because the request is a legitimate, correctly-signed webhook; the flaw is purely in the boolean logic of `provision?` after the webhook is accepted.

### Impact Explanation
The bypass causes Shipit to create a `ReviewStack` and enqueue it for provisioning (build/deploy infrastructure) for a repository whose owner explicitly disabled review stacks (`review_stacks_enabled: false`). This is an unauthorized creation of deploy-time infrastructure/resources triggered purely by an external contributor's PR label, on a repository configuration the owner believed disabled this feature entirely. The blast radius is scoped to the single misconfigured/target repository (not cross-tenant), but it defeats an explicit safety toggle and results in unintended provisioning/deploy activity for every PR carrying the label, repeatable on every PR opened by any contributor.

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`, which is bypassed in the opposite direction — stacks are skipped when they should be provisioned per `allow_all`, but that's a different-flavored bug of the same root cause). Attacker cost is trivial: open a PR and add a label they can apply to their own PR/branch (assuming they have label-write permission, typical for repo collaborators or via GitHub Actions bots in many workflows). No secrets, sessions, or elevated GitHub permissions are required beyond what's needed to open/label a PR, which is explicitly within the unprivileged attacker's capabilities per the rules.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression, matching `LabeledHandler`'s pattern:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, no live GitHub):
1. Build/stub a `Shipit::Repository` with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-preview'`.
2. Build `params` (via the handler's `ExplicitParameters` schema) representing a `pull_request.opened` payload whose `pull_request.labels` includes `{ name: 'deploy-preview' }`.
3. Instantiate `OpenedHandler.new(params)` and stub `repository` to return the above repository double.
4. Assert `handler.send(:provision?)` returns `true`.
5. Assert the binding is broken: `repository.review_stacks_enabled` is `false` while `provision?` is `true` — i.e. `assert_equal false, repository.review_stacks_enabled; assert handler.send(:provision?)`.
6. Optionally call `handler.process` (with `ReviewStackAdapter#find_or_create!` stubbed/spy) and assert it is invoked/creates a stack, demonstrating the unauthorized provisioning side effect.
