This confirms the analog: the `Handler` base class (and all handlers like `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, and PR handlers) resolve the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/secret to authenticate the request against using a *different* field, `repository.owner.login` (or `organization.login`) [2](#0-1) [3](#0-2) . Combined with `GitHubApp#verify_webhook_signature` returning `true` unconditionally whenever `webhook_secret` is blank for that organization [4](#0-3) , this creates exactly the class of binding break the rules describe: "an organization that authenticated versus the repository that is written."

### Title
Webhook authentication is keyed to `repository.owner.login` while the acted-upon repository comes from `repository.full_name`, allowing cross-repository forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify the HMAC signature against using `repository.owner.login` (falling back to `organization.login`), but every event handler resolves the target `Stack` to act on using the independent `repository.full_name` field. When any configured GitHub organization has no `webhook_secret` set (a supported, documented configuration - see `docs/setup.md` and `template.rb`, where `webhook_secret:` is left blank by default), `verify_webhook_signature` short-circuits to `true` for *any* signature/payload, letting an unauthenticated actor freely choose `repository.owner.login` to satisfy/bypass verification while independently setting `repository.full_name` to any other, unrelated (victim) repository that Shipit manages.

### Finding Description
- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to fetch the corresponding `GitHubApp` and check the signature: `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [5](#0-4) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is not configured for that organization: `return true unless webhook_secret` [4](#0-3) .
- Once the signature check passes (or is bypassed), the controller dispatches the *entire attacker-controlled JSON body* to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .
- Every handler (`Handler#stacks`, used by `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, `membership_handler.rb`, and the `pull_request/*` handlers) resolves the affected repository via `payload.dig('repository', 'full_name')`, a field completely independent from the `owner.login` field used for authentication `Repository.from_github_repo_name(repository_name)` [7](#0-6) .
- Because `owner.login`/`organization.login` and `full_name` are two separate, attacker-supplied JSON fields in the same unauthenticated request, there is no requirement that they be consistent. An attacker crafts a payload where `repository.owner.login` is set to an org configured without a `webhook_secret` (a documented default, e.g. `test/dummy/config/secrets_double_github_app.yml` and `template.rb` both ship `webhook_secret:` blank), thereby forcing `verify_webhook_signature` to short-circuit `true` regardless of the `X-Hub-Signature` header sent, while `repository.full_name` points at a completely different, victim-organization repository/stack that Shipit is meant to protect with its real webhook secret.
- This breaks the deployment-trust binding: "organization authenticated" (`repository.owner.login`, checked against a possibly-absent secret) versus "repository written" (`repository.full_name`, acted on by the handler with no additional authentication).

### Impact Explanation
This is an authentication bypass on the `/webhooks` endpoint (mounted without a `Shipit` session, `ApiClient` token, or any other credential — see the `before_action` chain in `app/controllers/shipit/webhooks_controller.rb`). Forged `push` events trigger `GithubSyncJob` for a victim stack, forged `status`/`check_suite` events alter commit/check state used for merge/deploy gating (`app/models/shipit/webhooks/handlers/status_handler.rb`, `check_suite_handler.rb`), and forged `pull_request` events can drive Shipit's Pull Request/review-stack lifecycle logic for arbitrary tracked repositories (`app/models/shipit/webhooks/handlers/pull_request/*`). Since Shipit uses this event stream to gate/trigger merges and deploys for a repository the attacker never had write access to, this can lead to an unauthorized deploy/merge action on a victim stack, matching the High-severity criterion "escalation into unauthenticated read/trigger of stack state" and can, depending on configured handlers, contribute to an unauthorized deploy or merge.

### Likelihood Explanation
Likelihood is contingent on at least one configured GitHub organization in the multi-org config (`Shipit.github_organizations`) having no `webhook_secret` set — a state the project's own default templates and dummy fixtures ship with (`template.rb` lines 68-111, `test/dummy/config/secrets_double_github_app.yml` lines 6-46, `config/secrets.development.shopify.yml`), and something an unprivileged internet attacker can discover simply by POSTing to `/webhooks` and observing the response, with zero credentials required. No repository write access, no `ApiClient` token, and no GitHub App key are needed to exploit it.

### Recommendation
Do not derive the trust decision (`repository_owner`) from a field that is disjoint from the field the handlers actually act upon (`repository.full_name`). At minimum: (1) never allow `verify_webhook_signature` to return `true` when a secret is absent for an organization that owns repositories tracked by Shipit — fail closed instead; (2) after successful signature verification, re-derive `repository_owner` from `repository.full_name`'s owner segment (or `Repository.from_github_repo_name`) and require it match the organization whose secret validated the request, rejecting the payload otherwise.

### Proof of Concept
1. Configure two GitHub orgs in `secrets.yml` per the documented multi-org format (`docs/setup.md` lines 182-209): `victim-org` (with a real `webhook_secret`) and `attacker-org` (left with `webhook_secret: nil`, the shipped default).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, and JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, looks up that org's `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` for any signature.
4. The request proceeds to `Shipit::Webhooks.for_event('push')`, which resolves the target stack via `full_name` = `"victim-org/victim-repo"` and enqueues `GithubSyncJob` for that victim stack, all without ever presenting a valid signature for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
