### Title
Missing network/chain-fork binding in signed-package hash allows cross-network signature replay - (File: `object_hash.js`)

### Summary
Ocore binds ordinary DAG units to their network via the `alt` field, which is included in the unit's signing hash. However, off-chain "signed packages" — used by AA triggers via `is_valid_signed_package`, by payment-channel oscripts, by device login/signing requests, and by wallet cosigning — are hashed with `getSignedPackageHashToSign`, which does not include any network/fork identifier. This is the exact bug class described in the report: a signature schema that omits chain/fork identification, allowing a signature valid on one network/fork to be replayed on another.

### Finding Description
`getUnitHashToSign` signs a deep clone of the entire unit object (`getNakedUnit`), which necessarily includes the unit's `alt` field — the network/fork identifier that `getStrippedUnit` also explicitly preserves: [1](#0-0) 

By contrast, `getSignedPackageHashToSign` only hashes the "signed package" object itself, which is restricted (by `validateSignedMessage`) to the fields `["signed_message", "authors", "last_ball_unit", "timestamp", "version"]` — there is no `alt`/network field in this schema at all: [2](#0-1) [3](#0-2) 

This signed-package format is the exact mechanism used by `is_valid_signed_package` in the oscript/AA formula evaluator to authorize AA-side actions from an off-chain signature, and by sample AA contracts (e.g. payment channels) to authorize balance/fund transfers based on a peer's off-chain signed message: [4](#0-3) [5](#0-4) 

Because the hash that gets signed (`unit_hash_to_sign = objectHash.getSignedPackageHashToSign(objSignedMessage)`) carries no chain/network identifier, the same signature is valid wherever the address, definition, and message content are reproduced — including on a different `alt`-network fork of ocore (e.g., after a hard fork that changes `alt`, or on testnet vs. mainnet deployments sharing the same key), exactly analogous to a chainID-less EIP-712 domain separator. [6](#0-5) 

The device-login/message signature path (`getDeviceMessageHashToSign`) has the same characteristic: it only strips `signature` and cleans nulls, with no chain/network binding. [7](#0-6) 

### Impact Explanation
`is_valid_signed_package` is a general-purpose primitive AA authors use to gate fund transfers and state changes on off-chain signatures (as shown in the bundled payment-channel sample, where a peer's signed message directly authorizes sending "all" channel funds to the counterparty). Because the signed hash is not bound to the specific network/fork, a signature produced for one network (e.g., a testnet deployment of an AA, or a signature intended for a pre-fork chain) can be replayed verbatim against another network/fork running the same AA code with the same participant addresses, causing unauthorized state transitions and fund movement in the AA. This is a direct AA fund-loss / unauthorized-spending impact, matching the report's exploit scenario (signature reuse across two parallel chains).

### Likelihood Explanation
Exploitation requires two networks/forks that share the same address space and accept the same `is_valid_signed_package`-gated AA logic — this occurs whenever developers reuse the same keys/addresses across mainnet and testnet (a common practice), or in the event of an ocore network fork that changes `alt` without changing the signed-package schema. No privileged access is needed: an unprivileged actor holding a validly-signed package from one network can post it as an AA trigger on the other network to replay the authorization.

### Recommendation
Include the network/fork identifier (`alt`, and ideally protocol `version`) inside the object that `getSignedPackageHashToSign` hashes, and enforce it in `validateSignedMessage`/`is_valid_signed_package` (e.g., reject packages whose declared network does not match the validating node's `constants.alt`). Apply the same fix to `getDeviceMessageHashToSign` for device-level signed messages.

### Proof of Concept
1. Deploy an AA (e.g., the sample `payment_channels.oscript`) with the same participant addresses/keys on two networks that differ only in `alt` (e.g., mainnet and a testnet fork, or pre-/post-fork chains).
2. Party A signs a "close channel"/spend-authorizing package using `signMessage`, producing a signature over `objectHash.getSignedPackageHashToSign(objSignedMessage)`, which contains no network identifier.
3. Party B submits this signed package as an AA trigger (`is_valid_signed_package(pkg, addressA)`) on Network 1, successfully draining the channel.
4. Party B resubmits the identical signed package unmodified as a trigger to the equivalent AA instance on Network 2; `validateSignedMessage`/`is_valid_signed_package` accepts it because nothing in the hashed content or validation logic differentiates the two networks, allowing the same authorization to be replayed and funds to be drained a second time.
