### Title
Creator fees can become permanently unclaimable because both `collect_creator_fee` and `collect_creator_fee_permissionless` hardcode the destination token account to the pool creator's own ATA - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
The reported Surge `removeCollateral` bug shows that hardcoding a token transfer destination to a specific address (with no way to redirect it) permanently freezes funds if that address is later blacklisted/frozen by the token program/issuer. The Raydium CP-Swap program has an analogous pattern for creator fees: the accrued `creator_fees_token_0`/`creator_fees_token_1` balances tracked in `PoolState` can only ever be sent to an ATA whose `authority` is fixed to `pool_creator`, with no field in `PoolState` or any instruction that allows the recorded `pool_creator` to be updated to a different address.

### Finding Description
`pool_creator` is set permanently at pool initialization and is never mutated anywhere else in the program [1](#0-0) . Both fee-collection paths for creator fees enforce the recipient account via Anchor's `associated_token::authority = creator` constraint:

- `collect_creator_fee` requires the `creator` itself to sign, and forces `creator_token_0`/`creator_token_1` to be the creator's own ATA [2](#0-1) .
- `collect_creator_fee_permissionless` lets *anyone* pay to trigger the collection, but the recipient ATA is still forced to `authority = creator`, where `creator` is constrained to equal `pool_state.pool_creator` [3](#0-2) [4](#0-3) .

Both instructions then transfer the entire `creator_fees_token_0`/`creator_fees_token_1` balances to that fixed ATA and zero out the counters [5](#0-4) [6](#0-5) .

If the SPL Token (or Token-2022, e.g. via the `TransferHook`/freeze-authority extension) mint used for `token_0`/`token_1` supports freezing or denylisting individual accounts (Token-2022 supports freezing any account via `FreezeAccount`, and third-party stablecoins commonly implement blacklists at the mint/transfer-hook level), and the `pool_creator`'s wallet or ATA is frozen/blacklisted after the pool starts accruing creator fees, there is no instruction in this program that lets the `pool_creator` redirect fee collection to a different, unfrozen account. Unlike `withdraw` (whose `token_0_account`/`token_1_account` only constrain the mint, not the authority, allowing the LP to redirect withdrawals to any account they control) or `collect_protocol_fee`/`collect_fund_fee` (whose `recipient_token_*_account` have no ownership constraint at all, letting the privileged `protocol_owner`/`fund_owner` redirect to any account), the creator-fee path is uniquely rigid: it always forces the destination back to the exact `pool_creator` address recorded at pool creation.

### Impact Explanation
If the recorded `pool_creator`'s account/ATA becomes frozen or blacklisted by the mint authority (a realistic scenario for Token-2022 pools using the `FreezeAccount` extension or default-frozen accounts, or for tokens whose transfer hook enforces a denylist), `creator_fees_token_0`/`creator_fees_token_1` accrue indefinitely in the pool vaults but can never be collected by any account, and there is no fallback path (no admin override, no ability to change `pool_creator`, no alternate recipient parameter). This constitutes a permanent freezing of legitimate creator-fee funds that belong to the pool creator.

### Likelihood Explanation
This requires an external condition (the creator's token account being frozen/blacklisted) rather than a purely attacker-controlled path, so it is not attacker-triggerable in a single transaction by itself. However, it is fully reachable through normal, unprivileged usage: any pool creator using a Token-2022 mint with freeze/denylist extension enabled is exposed, and swap activity from any unprivileged swapper continuously grows the stuck `creator_fees_token_0/1` balances in the interim, making the impact grow over time without any user action required to trigger it.

### Recommendation
Add an instruction (or extend `collect_creator_fee_permissionless`) that allows the `pool_creator` to specify/authorize an alternate destination token account (not hardcoded via `associated_token::authority = creator`), or add an admin-gated mechanism to update `pool_creator` in `PoolState`, mirroring the flexibility already present in `withdraw` and `collect_protocol_fee`/`collect_fund_fee`.

### Proof of Concept
1. Initialize a pool with a Token-2022 mint (e.g. `token_0`) that supports the `FreezeAccount` instruction, with `pool_creator` set to address `C`.
2. Perform swaps so that `creator_fees_token_0` accrues in `pool_state` [7](#0-6) .
3. The mint's freeze authority freezes `C`'s associated token account for `token_0` (or the token's blacklist logic rejects transfers to `C`).
4. Any attempt to call `collect_creator_fee` (signed by `C`) or `collect_creator_fee_permissionless` (called by anyone) fails at the `transfer_from_pool_vault_to_user` CPI to `creator_token_0` because the constrained recipient ATA is frozen/blacklisted [8](#0-7) .
5. Since `pool_creator` cannot be changed and no instruction allows specifying a different recipient, `creator_fees_token_0` remains permanently locked in `token_0_vault`.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```
