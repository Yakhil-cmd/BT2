### Title
XCM `ERC20Transactor` credits full requested amount to holding while a fee-on-transfer ERC20 delivers less, causing accounting drift and permanently trapped assets - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
The `ERC20Transactor` (a `TransactAsset` implementation used by Asset Hub to let XCM programs move ERC20 tokens deployed via `pallet-revive`) performs a Solidity-style `transfer()` call to move tokens into/out of a shared `TransfersCheckingAccount`, and blindly credits/deducts the XCM holding register with the *requested* amount rather than the amount actually observed to move. Any signed user can deploy an arbitrary `pallet-revive` ERC20 contract (no registration/whitelisting is required for the transactor to accept it — it matches on `AccountKey20` address alone) and use `PolkadotXcm::execute`/`transfer_assets` to interact with it. If that ERC20 implements fee-on-transfer semantics, the checking account never actually accumulates as much balance as the XCM executor believes it withdrew, producing exactly the "insufficient support for fee-on-transfer tokens" bug class described in the source report, mapped onto the FRAME/XCM native-precompile boundary instead of Solidity.

### Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall{ to: checking_address, value: amount }` from the user to the shared `TransfersCheckingAccount`, and on `Ok(true)` unconditionally credits the XCM holding register with the full requested `amount` via `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))`: [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` calls `transferCall{ to: beneficiary, value: amount }` from `TransfersCheckingAccount` and, on success, simply returns — again trusting `amount` (the value tracked in holding) rather than checking any before/after balance delta: [2](#0-1) 

For a standard ERC20 fee-on-transfer token, `transfer(to, amount)` debits the *full* `amount` from the sender but credits the recipient with `amount - fee` (fee routed elsewhere, e.g. back to the token deployer). Since the transactor only inspects the boolean return value of `transfer()` and never re-reads `balanceOf(checking_account)` before/after (the exact anti-pattern flagged in the source report's recommendation), the holding register's `Erc20Credit(amount)` overstates what the checking account actually received. This is architecturally the same root cause as the Buffer Protocol bug (`BufferRouter`/`BufferBinaryPool` trusting the nominal transfer amount instead of measured balance deltas), just relocated to the XCM `TransactAsset` boundary where a permissionless smart-contract call stands in for a native asset transfer.

Any signed account can reach this code path with no privileged role:
- Deploy an ERC20 (fee-on-transfer) contract via `pallet_revive` (`UploadOrigin`/`InstantiateOrigin` are `EnsureSigned`), confirmed for Asset Hub Westend: [3](#0-2) 
- Reference it as an XCM asset by its `AccountKey20` location and drive `WithdrawAsset`/`DepositAsset` through `PolkadotXcm::execute`, exactly as exercised in the existing test for the (non-fee-on-transfer) happy path: [4](#0-3) 
- `ERC20Transactor` is wired into `AssetTransactors` alongside the native/foreign asset transactors, so it is live production configuration, not test-only code: [5](#0-4) 

### Impact Explanation
This is a genuine analog of the source Medium finding: the protocol assumes the transferred amount equals the requested amount for an externally-controlled token contract, exactly the class the report describes ("Insufficient support for fee-on-transfer tokens... consider checking the balance of the contract before and after token transfers"). The concrete consequence is a persistent accounting drift between the XCM holding register (`Erc20Credit`) and the real ERC20 balance of `TransfersCheckingAccount`:
- On withdraw, the executor believes more was moved into the checking account than actually landed there.
- On a subsequent deposit for the same (inflated) amount, the checking account may lack sufficient real balance, causing the ERC20 `transfer()` call to revert; the executor then traps the (phantom) holding value via `AssetsTrapped`, effectively locking the user's own tokens/value permanently, since re-claiming the trap replays the same undersized deposit and will fail identically.
- Because `TransfersCheckingAccount` is shared across all ERC20 assets processed by this transactor (a single global account, not per-asset), repeated withdrawals of a fee-on-transfer token by any user progressively degrade the true balance backing that asset's credited holding, so later legitimate depositors of the same asset can also be denied full value or trapped, not just the token's original deployer.

This does not directly enable theft of unrelated users' native DOT/assets (the checking account balance can only be a real ERC20 balance per contract, and `transfer()` calls will revert rather than under-flow), so the primary demonstrable impact is **loss/permanent freezing of the affected ERC20 value inside the checking account and broken XCM asset accounting**, consistent with a Medium severity classification, matching the original report.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: it requires a user to interact with (or deploy) a fee-on-transfer ERC20 and route it through XCM `WithdrawAsset`/`DepositAsset` via the `ERC20Transactor`. No privileged role, governance action, or malicious validator/collator is needed — a normal signed account can deploy the contract and drive the XCM program themselves, matching the "no privileged prerequisite" requirement. The `ERC20Transactor` feature is recent (`pr_7762.prdoc` "ERC20 Asset Transactor") and is present in production Asset Hub Westend runtime configuration.

### Recommendation
In `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf(checking_account)` (or the recipient) immediately before and after the `IERC20::transfer` call and use the observed delta — not the nominal `amount` — both when constructing `Erc20Credit` in `withdraw_asset_with_surplus` and when deciding success/failure and surplus accounting in `deposit_asset_with_surplus`. Consider also rejecting/flagging assets whose measured delta doesn't match the requested amount, so fee-on-transfer or otherwise non-standard ERC20s cannot silently desynchronize the XCM holding register from the real checking-account balance.

### Proof of Concept
No executable PoC was run against a live/test node in this analysis. Reasoning is based on static code inspection of `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and the existing integration test `withdraw_and_deposit_erc20s` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` (lines 1871-1935), which demonstrates the exact `PolkadotXcm::execute` → `withdraw_asset` → `deposit_asset` flow for an ERC20 deployed via `pallet_revive::Pallet::bare_instantiate`. To turn this into a concrete repro, a background engineer would need to:
1. Compile/deploy a minimal fee-on-transfer ERC20 fixture (e.g. modify the `MyToken` fixture used in that test to deduct a fee on `transfer`).
2. Reuse the same XCM `withdraw_asset`/`deposit_asset` program from that test.
3. Assert that `Erc20Credit`/holding-tracked amount and the checking account's real `balanceOf` diverge after the withdraw step, and that the subsequent deposit either reverts or delivers less than the beneficiary was promised, versus the expected equal amounts asserted in the existing non-fee-on-transfer test (lines 1926-1934).

I was not able to execute this modified reproduction due to lack of terminal/build access in this session; this remains a static-analysis-derived, unverified-by-execution finding that should be confirmed via the steps above before filing formally.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
