### Title
Webhook status/push events are not scoped to the organization whose secret verified the signature, allowing cross-repository commit-status forgery and unauthorized continuous deployment - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify a delivery against using `repository_owner`, taken from `payload.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, the event is dispatched to handlers that resolve the actual data to mutate independently of `repository_owner`. `Webhooks::Handlers::StatusHandler` in particular ignores repository/organization scoping entirely and updates any commit in the whole installation matching the raw `sha` supplied in the payload [3](#0-2) . This breaks the binding: *the organization whose secret authenticated the request* must equal *the repository/commit that is actually written*.

### Finding Description
The verification path is:
1. `repository_owner` is read straight from the JSON payload (`params.dig('repository','owner','login')` or `organization.login`), then used to look up the GitHub App config, including `webhook_secret`, for that org via `Shipit.github(organization: repository_owner)` [1](#0-0) .
2. `verify_webhook_signature` in `GithubApp` returns `true` unconditionally when that organization has no `webhook_secret` configured: `return true unless webhook_secret` [4](#0-3) . Shipit explicitly supports multiple organizations in one instance, and the dummy multi-org config in the repo shows a second organization configured with `webhook_secret: # nil` [5](#0-4) , i.e. per-org secrets are optional and independently configured.
3. After signature verification, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full raw payload to handlers [6](#0-5) .
4. The base `Handler` class resolves the target stacks from `payload.dig('repository', 'full_name')` — a separate field from the `repository.owner.login`/`organization.login` used for signature selection, and never cross-checked against it [7](#0-6) .
5. `StatusHandler#process` goes further and doesn't even use `repository_name`/`stacks` scoping — it queries `Commit.where(sha: params.sha)` across the entire application and calls `create_status_from_github!` on every match, regardless of which repository/organization owns that commit [3](#0-2) .

Consequently, an attacker who can get one valid signature accepted (for example because they know the `repository_owner` is a configured organization with no `webhook_secret`, or is otherwise able to select which org's secret is checked via the payload's `repository.owner.login`/`organization.login` fields) can submit a `status` webhook whose `sha` belongs to a commit tracked under a completely different organization/repository/stack, and have that commit's CI status forged to `success`.

### Impact Explanation
Forging a commit status is not cosmetic: Shipit stacks configured with `continuous_deployment: true` are periodically scanned and enqueue deploys for eligible commits (`Stack.schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)`) [8](#0-7) , and commit deployability is gated by required/blocking statuses cached on the deploy spec. By injecting a forged green status for a targeted commit sha via a webhook that was verified only against an unrelated (or secret-less) organization's key, an attacker can flip a commit into a "deployable" state it would not otherwise reach, causing Shipit to trigger an unauthorized deploy for a stack/repository the attacker never had credentials for. This is a cross-repository/cross-organization write that results in an unauthorized deploy — matching the Critical impact bar (unauthorized deploy).

### Likelihood Explanation
The likelihood depends on operational conditions the report itself calls out as in-scope for the "organization authenticated vs repository written" binding: any Shipit deployment tracking more than one GitHub organization, or any organization configured without `webhook_secret` (the engine explicitly supports this — verification unconditionally passes with `return true unless webhook_secret`), creates the mismatch. No repository write access, GitHub App private key, or Shipit session/API token is required; only the ability to send an HTTP POST to `/webhooks` with a payload whose `repository.owner.login` differs from `repository.full_name`'s owner, and whose `sha` matches a commit tracked elsewhere in the instance.

### Recommendation
- Reject webhook payloads where `repository.owner.login`/`organization.login` does not match the owner encoded in `repository.full_name`.
- Scope `StatusHandler` (and any other handler) strictly to `stacks`/`repository_name` resolved from the same payload field that was authenticated, instead of an unscoped `Commit.where(sha:)` lookup.
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
1. Configure Shipit with two organizations, one of which (`OrgTwo`) has no `webhook_secret` (as in the dummy multi-org fixture) [5](#0-4) .
2. Attacker tracks a public commit `sha` that also exists in a stack under `OrgOne` (a real, secured organization tracked by the instance).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body: `{"repository": {"owner": {"login": "OrgTwo"}, "full_name": "OrgOne/victim-repo"}, "sha": "<victim sha>", "state": "success", ...}`, and any (or no) `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"OrgTwo"`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the signature header [9](#0-8) [4](#0-3) .
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, forging a success status on the `OrgOne/victim-repo` commit despite the request never being authenticated against `OrgOne`'s secret [3](#0-2) .
6. If `OrgOne/victim-repo`'s stack has `continuous_deployment: true` and this status makes the commit deployable, the next `schedule_continuous_delivery` run enqueues an unauthorized deploy [8](#0-7) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
