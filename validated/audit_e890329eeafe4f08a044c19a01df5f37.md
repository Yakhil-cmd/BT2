### Title
Webhook signature verification selects the signing organization from unauthenticated payload fields, letting one installed org forge events for stacks owned by a different org — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/org's `webhook_secret` to check the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unauthenticated JSON body, then verifies the *entire* raw body against that org's secret. The handlers that actually act on the payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target `Stack`/`Commit` using a *different* field of the same body — `repository.full_name` — which is never required to match the organization whose secret validated the signature. This breaks the intended binding "the org whose secret authenticated this delivery" == "the repository this delivery is allowed to write into."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is taken from the attacker-supplied JSON body before any signature is verified, and is only used to pick which configured org's `webhook_secret` will be used to HMAC-verify the raw body (`lib/shipit/github_app.rb#verify_webhook_signature`) [2](#0-1) . This engine explicitly supports multiple GitHub Apps/orgs configured side by side in a single Shipit install (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) [3](#0-2) .

Once the signature check passes (using OrgA's secret because `repository.owner.login == "OrgA"`), the raw JSON is dispatched to handlers keyed only on event type, and each handler resolves its target purely from `repository.full_name` in the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Nothing checks that `repository.full_name`'s owner matches `repository.owner.login` used for signature selection. A holder of a legitimate GitHub App installation for OrgA (i.e., someone who can produce real webhook deliveries signed with OrgA's secret, e.g. by triggering any real event in an OrgA repo, or simply by being an admin/maintainer able to configure OrgA's app) can instead POST a body where `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against OrgA's secret) but `repository.full_name = "OrgB/some-repo"`. Because HMAC covers the whole raw body, the attacker just needs to sign that crafted body with OrgA's own secret — which they can compute themselves since they legitimately possess it. The signature check passes, and `PushHandler`/`StatusHandler`/`CheckSuiteHandler` then act on `OrgB/some-repo`'s `Stack`/`Commit` records, which the attacker's org was never installed on or authorized for.

`StatusHandler` in particular applies attacker-controlled CI status (`state`, `context`, `description`) to any `Commit` row matching the given `sha` across the whole instance, without any repository/organization ownership check at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 
Shipit's merge queue and CI-gating logic rely on these `Status` rows to decide whether a commit is "green" and eligible for the merge queue / deploy (`ci.require` in `shipit.yml`), so a forged status delivered under a foreign, but validly-signed, envelope can flip CI state for a repository the attacker's org has no access to. `PushHandler` similarly triggers `stack.sync_github` (`GithubSyncJob`) for an arbitrary target stack chosen entirely by the attacker via `repository.full_name`. [6](#0-5) 

### Impact Explanation
This crosses the "organization authenticated vs. repository written" boundary named in scope. Concretely, an attacker who controls delivery of valid webhooks for OrgA (their own installed GitHub App) can spoof push/status/check_suite events attributed to a repository belonging to a completely different, unrelated organization (OrgB) hosted on the same Shipit instance, causing:
- Forged CI `Status` records injected onto OrgB's commits (`StatusHandler`), potentially satisfying `ci.require` conditions and enabling an unauthorized merge/deploy for a repository the attacker doesn't own — Critical-adjacent (unauthorized deploy path).
- Forced `GithubSyncJob` triggers and check-run refreshes for OrgB's stacks (`PushHandler`, `CheckSuiteHandler`), interfering with OrgB's deployment pipeline state.

The severity is bounded by the fact that the actual GitHub API calls Shipit performs to fetch OrgB's real commits still use OrgB's own `github_app` (resolved from the `Repository#owner` DB column, not the payload), so the attacker cannot exfiltrate OrgB's GitHub token; the impact is confined to state manipulation (CI status/sync triggers) rather than RCE or credential theft.

### Likelihood Explanation
Requires the attacker to already control at least one legitimately configured GitHub organization/App installation on the same Shipit instance (multi-org deployments are a documented, supported configuration). No Shipit session, API token, or GitHub write access to the *target* repository is needed — only the ability to deliver a webhook signed with an org secret the attacker legitimately possesses, and knowledge of the target repository's `owner/name`. This is a realistic scenario for shared/hosted Shipit deployments serving several orgs or teams.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after selecting `github_app` by `repository_owner`, re-validate that `params.dig('repository','full_name')`'s owner segment matches `repository_owner` (or, more robustly, look up the `Repository`/`Stack` by `full_name` and confirm its persisted `owner` equals the org whose secret validated the signature) before dispatching to handlers. Reject the delivery (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls OrgA's GitHub App webhook secret (legitimately, as OrgA's admin).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-that-exists-in-OrgB-repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner => "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully (attacker legitimately has this secret).
6. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `sync_github` on OrgB's stack — enqueuing `GithubSyncJob` for a repository OrgA never had access to. [1](#0-0) [4](#0-3) [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
