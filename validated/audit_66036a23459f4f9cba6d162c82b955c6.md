### Title
Webhook signature verification keys on `repository.owner.login` while every handler resolves the target repo from the independent `repository.full_name` field, allowing cross-tenant `sync_github` triggering - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to verify against using `params.dig('repository', 'owner', 'login')`, but `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler, including `PushHandler`) resolves the target `Repository`/`Stack` using the separate, attacker-controlled `payload.dig('repository', 'full_name')` field. Because both fields live in the same attacker-crafted JSON body and are never cross-checked, an attacker who legitimately owns `attacker-org` (and thus knows its `webhook_secret`) can sign a payload whose `repository.owner.login` is `attacker-org` (so verification passes) while `repository.full_name` is `victim-org/victim-repo` (so the handler acts on the victim's stack). This lets `PushHandler` call `stack.sync_github(expected_head_sha: params.after)` on a victim's stack with an attacker-chosen SHA.

### Finding Description
The broken binding: the code implicitly assumes
`organization_owning(verified_webhook_secret) == organization_owning(repository.full_name used by handlers)`,
but this equality is never enforced — they are two independently attacker-supplied strings in the same JSON body.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and looks up `Shipit.github(organization: repository_owner)` to verify `X-Hub-Signature` via HMAC-SHA1 over the raw body (`lib/shipit/github_app.rb#verify_webhook_signature`). [1](#0-0) [2](#0-1) 
- On success, `create` dispatches the *entire* parsed body to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a completely different key path than the one used for signature verification. [4](#0-3) 
- `PushHandler#process` uses that repository name to load real stacks and calls `sync_github(expected_head_sha: params.after)`, where `after` is fully attacker-controlled. [5](#0-4) 
- `Repository.from_github_repo_name` simply splits the `full_name` string on `/` and does a DB lookup by `owner`/`name` — no relation to the org whose secret verified the request. [6](#0-5) 

Attacker's exact request: attacker owns `attacker-org` in Shipit (a legitimately configured GitHub org with its own `webhook_secret`). They POST to `/webhooks` with header `X-Github-Event: push`, a valid `X-Hub-Signature` computed as `"sha1=" + HMAC-SHA1(attacker-org's webhook_secret, raw_body)`, and a raw JSON body such as:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
`repository.owner.login` ("attacker-org") is used only for signature verification; `repository.full_name` ("victim-org/victim-repo") is used only for resolving the real target `Repository`/`Stack`. The two are never compared against each other, so the mismatch goes undetected.

Why existing guards fail: `verify_signature` only validates that *some* valid organization's secret was used to sign the raw bytes — it never checks that the org used for verification matches the org implied by `full_name`, which is what every handler (`PushHandler`, `LabeledHandler`, `OpenedHandler`, etc.) actually trusts. `drop_unhandled_event`, `ExplicitParameters` schemas, and model validations on `Repository#owner`/`name` format do not perform any cross-field consistency check either — they only validate that the fields are well-formed strings, not that they refer to the same organization as the signer.

### Impact Explanation
A single crafted, correctly-signed HTTP POST from an attacker who controls only their own GitHub org lets them enqueue/trigger `GithubSyncJob`-driven sync against an arbitrary victim stack with an attacker-chosen `expected_head_sha`, i.e., a payload authenticated for one repository mutates another repository's stack state. This is repeatable against any repository/stack registered in Shipit, regardless of tenant, since the only requirement is knowledge of the target's `full_name` (public information) and control of any org's `webhook_secret` (which the attacker legitimately has for their own org). This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: they must be a legitimate Shipit-registered GitHub organization owner (which is a normal, non-privileged onboarding state for any org using Shipit), enabling them to sign arbitrary payload bytes with their own valid `webhook_secret`. No knowledge of the victim's secret, session, or API token is required — only the victim's public `owner/repo` string. The attack is a single crafted HTTP request, fully repeatable against any repository in the deployment.

### Recommendation
Enforce equality between the organization that owns the verified `webhook_secret` and the organization implied by the resolved `repository.full_name`/target `Repository` for every handler. Concretely, in `WebhooksController#verify_signature`, after verification succeeds, additionally derive the owner from `full_name` (`payload.dig('repository','full_name')&.split('/')&.first`) and reject (422) if it differs from `repository_owner` used for the signature check. Alternatively, refactor handlers to resolve the target repository using the same `repository_owner` value validated at the controller layer, rather than trusting `full_name` independently.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":push with mismatched owner.login vs full_name syncs the wrong stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to victim-org/victim-repo
  attacker_secret = "attacker-secret"
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    "ref" => "refs/heads/#{victim_stack.branch}",
    "after" => "deadbeefattackerchosen",
    "repository" => {
      "owner" => { "login" => "attacker-org" },
      "full_name" => victim_stack.repository.full_name
    }
  }.to_json

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = 'sha1=whatever' # accepted due to stub above

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: "deadbeefattackerchosen")

  post :create, body: payload, as: :json
  # Assert: organization owning verified webhook_secret ("attacker-org")
  #         != organization owning repository.full_name used by handler ("victim-org")
  # yet sync_github was still invoked on victim_stack.
end
```
This demonstrates that `Shipit.github(organization: 'attacker-org')` (the verified signer) is disjoint from the `victim-org` stack that ultimately receives `sync_github`, confirming the broken binding.
