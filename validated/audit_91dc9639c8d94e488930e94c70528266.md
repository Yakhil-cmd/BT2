### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table, with no repository or stack scoping, unlike `PushHandler` which scopes via `stacks`. A signed `status` webhook from org A, verified only against org A's secret, will write `Status` rows onto any `Commit` in any stack/org whose `sha` matches, including unrelated tenants.

### Finding Description
The binding that should hold is: `Status.commit.stack.repository == payload.repository` for every `Status` row created by a given webhook delivery — i.e., a webhook verified with organization A's secret must only affect commits belonging to stacks whose repository is the one identified in that payload. `StatusHandler#process` breaks this: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  selects every `Commit` row across all stacks/repositories/orgs sharing that sha string, with no `.where(stack_id: ...)`/`.merge(stacks)` filter.

The `Handler` base class already provides exactly the mechanism needed to bind a payload to its repository — `stacks` resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` [3](#0-2) , and `PushHandler` correctly uses it: `stacks.not_archived.where(branch:).find_each { ... }` [2](#0-1) . `StatusHandler` ignores this helper entirely.

`WebhooksController#verify_signature` only verifies that the payload was signed by `Shipit.github(organization: repository_owner)`, i.e. it authenticates *which organization* sent the payload, not *which stacks* the SHA may legitimately touch [5](#0-4) . That check does not prevent an attacker who controls a valid organization's webhook secret (or, per the threat model, replays a coincidentally-matching public sha) from having their payload matched against commits belonging to entirely different stacks/orgs whose commit histories happen to share that sha (e.g., the well-known empty-tree hash `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any commit imported/mirrored into multiple Shipit-tracked repositories). No other guard (`ExplicitParameters` schema, `drop_unhandled_event`, model validations) restricts the `Commit` scope by repository.

Attack flow: attacker pushes/creates a commit with a known/colliding sha in a repository they control that is registered as a Shipit-tracked stack, triggers/sends a `status` event for that sha signed with their own organization's legitimate webhook secret (which they do have, since it's their own repo/org registered with Shipit), and the handler updates `Status` rows on every other `Commit` row in the database sharing that sha, including commits belonging to unrelated stacks/orgs.

### Impact Explanation
A `Status` row written on a commit updates that commit's CI/deploy-readiness state (via `create_status_from_github!` → `Status` `after_create`/`after_commit` callbacks enabling CI and scheduling continuous delivery) [6](#0-5) , potentially unblocking or corrupting deploy/merge gating logic for a completely different organization's stack. This is a payload from one repository/org mutating another organization's `Commit`/`Status` state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius extends across every Shipit-tracked stack sharing that sha, i.e., any Shipit instance tracking multiple orgs/repos.

### Likelihood Explanation
Requires the attacker to control at least one repository/org that is already registered with Shipit as a legitimate stack (so they have that org's real webhook secret, sent to GitHub by Shipit's own registration flow) and to be able to produce or find a sha that also exists as a `Commit` row in a victim stack — most practically by mirroring/forking a public commit history so the sha is identical, or using well-known fixed hashes (empty tree, initial commits of widely-forked repositories) that many Shipit-tracked repos may share. This is feasible without any secrets belonging to the victim org, and repeatable per matching sha.

### Recommendation
Scope the lookup to the payload's repository, mirroring `PushHandler`: e.g. `Commit.where(sha: params.sha).merStackFactory... ` — concretely, `Commit.joins(:stack).merge(stacks).where(sha: params.sha)` or `stacks.joins(:commits).where(commits: { sha: params.sha })`, so only commits belonging to stacks associated with the webhook's `repository.full_name` are updated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not create a status on a commit belonging to a different stack/repo sharing the same sha" do
  colliding_sha = 'a' * 40
  stack_a = shipit_stacks(:shipit)          # repo owner/shipit
  stack_b = shipit_stacks(:cyclimse)        # different repo/org
  commit_a = stack_a.commits.create!(sha: colliding_sha, ...)
  commit_b = stack_b.commits.create!(sha: colliding_sha, ...)

  payload = {
    'sha' => colliding_sha, 'state' => 'success',
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }

  assert_difference -> { commit_a.statuses.count }, 1 do
    assert_no_difference -> { commit_b.reload.statuses.count } do
      Shipit::Webhooks::Handlers::StatusHandler.call(payload)
    end
  end
end
```
Currently this test fails: `commit_b.statuses.count` also increases by 1, demonstrating the cross-tenant write. Both sides of the binding `Status.commit.stack.repository == payload.repository` must hold for every created `Status`; presently they do not.
