### Title
Unauthenticated `sender` field in `TransferStxOp` allows theft of arbitrary STX balances via a spoofed `PreStxOp` - ([File: stackslib/src/chainstate/burn/operations/transfer_stx.rs])

### Summary
`TransferStxOp::parse_from_tx` sets `sender` from the caller-supplied `PreStxOp.output` value, and `TransferStxOp::check` never verifies that this `sender` is cryptographically tied to any key that actually signed the referenced Bitcoin inputs. Because `PreStxOp.output` is itself an arbitrary address chosen by whoever creates the `PreStxOp` transaction (with no key-ownership proof), an attacker can declare any victim's Stacks address as `sender`, then spend the `PreStxOp`'s own second output (which they fully control) to submit a `TransferStxOp` moving the victim's STX to themselves.

### Finding Description
The broken equality is: **`TransferStxOp.sender` == the Stacks address whose private key actually authorized this transfer**. The code never enforces this.

- `PreStxOp::parse_from_tx` sets `output` purely from `outputs.get(0)....try_into_stacks_address()` [1](#0-0)  — there is no requirement that this address be derived from, or otherwise tied to, the keys that sign the transaction's own inputs. Paying to an address does not require possession of its private key, so an attacker can put an arbitrary victim's Stacks address here in a `PreStxOp` bitcoin transaction that the attacker fully creates and funds themselves.
- `TransferStxOp::get_sender_txid` only checks that the `TransferStxOp`'s input 0 references `vout == 1` of some prior transaction; it never checks who signed that prior transaction's inputs [2](#0-1) .
- `burnchain.rs::classify_transaction` looks up the referenced `PreStxOp` and blindly takes `sender = &pre_stx.output`, passing it into `TransferStxOp::from_tx` [3](#0-2) .
- `TransferStxOp::check` only rejects `sender == recipient`; it performs no signature-based authorization check at all [4](#0-3) .
- `process_transfer_ops` executes the transfer directly: `tx.run_stx_transfer(&sender.into(), &recipient.into(), transfered_ustx, ...)` [5](#0-4) .
- Deeper in Clarity, `run_stx_transfer` → `ExecutionState::stx_transfer` invokes `execute_in_env(from.clone(), ...)`, which sets `invoke_ctx.sender = from` [6](#0-5) ; the subsequent check in `stx_transfer_consolidated`, `if Some(from) != invoke_ctx.sender.as_ref() { ... SENDER_IS_NOT_TX_SENDER }` [7](#0-6) , is therefore tautologically true — it compares `from` to itself, since the burnchain-op code always sets `invoke_ctx.sender` equal to the value it passes as `from`. It provides no real signature verification for burnchain-origin transfers.

**Exploit flow:** the attacker (1) creates and funds a Bitcoin transaction acting as a `PreStxOp`, whose first output address encodes the victim's Stacks address bytes (no victim key needed to pay to an address) and whose second output pays back to an address the attacker controls; (2) in a later Bitcoin transaction acting as `TransferStxOp`, spends that second output as input 0 (satisfying `get_sender_txid`'s `vout==1` requirement) and sets its own recipient output to the attacker's address; (3) once both ops are mined and processed, `sender = victim_address`, `recipient = attacker_address`, and `run_stx_transfer` debits the victim's unlocked STX and credits the attacker, with no signature from the victim ever checked.

None of the existing guards (`check()`, `get_sender_txid`, `stx_transfer_consolidated`'s tx-sender check) prevent this, because they all operate on values that the attacker fully controls at the Bitcoin-transaction-construction layer.

### Impact Explanation
Any account's unlocked STX balance can be transferred to an attacker-chosen recipient without any authorization from the true balance holder — this is direct theft of victim funds, repeatable against any address with a positive unlocked STX balance and repeatable per Bitcoin-transaction pair (bounded only by Bitcoin tx fees the attacker must pay). This is a complete "unsigned stacking/transfer action" moving value the contract did not validate was authorized, matching the audit's High/Critical theft categories (unauthorized transfer of another party's unlocked STX).

### Likelihood Explanation
No special role or privilege is needed — the attacker only needs to construct two ordinary Bitcoin transactions with the correct opcodes/output layout, referencing a victim's known Stacks address (public information) as the fabricated `PreStxOp.output`. The only cost is Bitcoin transaction fees. It works in any epoch that processes `PreStx`/`TransferStx` burnchain ops and requires no cooperation from the victim or any Stacks-side signature. This makes it highly feasible and trivially repeatable against any address with a nonzero unlocked balance.

### Recommendation
Require that `PreStxOp.output` (and thus the derived `sender` for `TransferStxOp`/`StackStxOp`/`DelegateStxOp`/`VoteForAggregateKeyOp`) be cryptographically tied to the actual signer of the referenced Bitcoin inputs — e.g., derive `sender` from the public key(s) that signed the `PreStxOp`'s (or `TransferStxOp`'s) own input scriptSig/witness (as already done in `VoteForAggregateKeyOp::get_sender_pubkey`), rather than trusting an arbitrary declared output address. Alternatively, require that the `PreStxOp`'s `output` address match the address computable from the same keys used to fund/spend it, and enforce this equality at parse time before accepting the op.

### Proof of Concept
Rust integration test plan (mirroring existing tests in `stacks-node/src/tests/epoch_21.rs`):
1. Create `victim_sk`/`victim_addr` (STX address with a funded unlocked balance) and `attacker_sk`/`attacker_addr`, but do **not** give the attacker `victim_sk`.
2. Using only `attacker_sk`-controlled Bitcoin UTXOs, submit a `PreStxOp` bitcoin transaction where `output = victim_addr` (attacker sets this field directly, bypassing any node tooling that would normally auto-fill it with the signer's own derived address).
3. Using `attacker_sk`, spend `vout=1` of that `PreStxOp` transaction to submit a `TransferStxOp` with `recipient = attacker_addr` and `transfered_ustx = N`.
4. Mine both operations and assert:
   - `TransferStxOp::from_tx(...)` returns `Ok(op)` with `op.sender == victim_addr` even though `victim_sk` never signed anything.
   - After block processing, `get_balance(victim_addr) == original_balance - N` and `get_balance(attacker_addr) == N`, proving STX moved from `victim_addr` without any signature check on both sides of the equality `sender == true key-holder`.
