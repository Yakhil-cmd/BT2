## Analysis

The Symmetrical/Sherlock bug describes a **two-step, time-gated fund-release process** whose second step depends on an external party (a liquidation bot / signer) acting within a bounded window; if that party never acts, both an upper and lower timestamp bound become permanently unsatisfiable and the escrowed funds can never be released.

The closest reachable analog in `ocore` is the same structural flaw in the AA (`oscript`) `data_feed[...]` release pattern: an AA escrows user funds and gates the *only* release path on a **single oracle posting a specific feed value**, with no refund/expiry fallback branch. If the oracle never posts that exact feed (crashes, is decommissioned, or simply never used that `feed_name` after the AA's hardcoded maturity date), the AA permanently bounces every subsequent trigger for that case, and the funds locked in the AA become unrecoverable — exactly the "liveness‑dependent, unprivileged‑trigger‑reachable, no fallback ⇒ permanent freeze" bug class from the report.

### Title
AA funds can be permanently frozen when a release path depends solely on a single oracle's `data_feed` with no expiry/refund fallback - (File: `formula/evaluation.js`)

### Summary
An Autonomous Agent whose only exit/redemption branch is gated by `data_feed[[...]]` (default `ifnone: 'abort'`) has no other path to release escrowed funds if the designated oracle never posts the required value. This mirrors the reported "second-step never arrives → funds stuck forever" bug class, except the untrusted external actor here is the oracle rather than a liquidation bot.

### Finding Description
The `data_feed` formula op is evaluated in `formula/evaluation.js`'s `getDataFeed` function [1](#0-0) . When the requested feed/value has not been posted by the specified oracle(s) and no `ifnone` fallback other than `'abort'` is supplied, evaluation returns a fatal error, causing the triggering unit's AA response to bounce [2](#0-1) .

ocore's own reference AA templates encode exactly this pattern without a timeout/refund branch. In `futures_contract.oscript`, the only path to redeem the `usd_asset`/`gb_asset` for bytes is:
```
if (timestamp < 1556668800)
    bounce('wait for maturity date');
$exchange_rate = data_feed[[oracles='X55IWSNMHNDUIYKICDW3EOYAWHRUKANP', feed_name='GBYTE_USD_MA_2019_04_30']];
``` [3](#0-2) 

Before maturity the case always bounces ("wait for maturity date"); after maturity, redemption strictly requires that exact `feed_name` to have been posted by the single named oracle address. There is no message case in the AA that refunds the `usd_asset`/`gb_asset` holders or the base coins that funded the AA if the oracle never posts this feed (oracle goes offline, is decommissioned, or simply never uses that feed name again). Once the maturity timestamp passes with no matching feed ever posted, every attempt to redeem via `getDataFeed` fails with `"data feed ... not found"`, bouncing the trigger indefinitely [4](#0-3) . The `option_contract.oscript` sample has the same structural pattern [5](#0-4) .

### Impact Explanation
Any user who contributed base coins to receive `usd_asset`/`gb_asset` (or the equivalent option-contract assets) has no way to reclaim value if the oracle stops posting the specific feed after maturity: the funds sitting in the AA's balance become permanently unspendable through the existing message-case set, exactly matching the "AA fund loss/freezing" impact bucket required for this class of finding.

### Likelihood Explanation
This requires only that a single, unprivileged, off-chain oracle operator stop posting one specific feed name after a fixed maturity date — no malicious action, network fault, or privileged access is needed, only an ordinary operational failure (the same likelihood class as "the liquidation bot fails to submit in time" in the original report). Any AA author copying this widely-referenced sample pattern (it ships as an official ocore AA reference template) inherits the same freeze risk, so the reachable surface is broad.

### Recommendation
- Add an explicit timeout/refund branch to AA templates and to the documentation guidance: if the required `data_feed` is not found within some grace period after the expected posting time (checked via `mci`/`timestamp` combined with `otherwise`/`ifnone`), allow depositors to reclaim their original contribution.
- Encourage (or provide a built-in oscript idiom for) multi-oracle or self-service refund fallbacks whenever a release path is gated on a single external data source, so a stalled oracle cannot permanently lock AA-held funds.

### Proof of Concept
1. Deploy `futures_contract.oscript` (or a derivative) as an AA; users contribute bytes and receive `usd_asset`/`gb_asset` before maturity [6](#0-5) .
2. After `timestamp` passes `1556668800`, the only redemption case requires `data_feed[[oracles='X55IWSNMHNDUIYKICDW3EOYAWHRUKANP', feed_name='GBYTE_USD_MA_2019_04_30']]` [7](#0-6) .
3. If the oracle at that address never posts a `data_feed` unit with that `feed_name` (e.g., it is retired), every trigger attempting redemption calls `getDataFeed`, which returns `"data feed ... not found"` and bounces [8](#0-7) .
4. Since no other message case exists to withdraw the escrowed `usd_asset`/`gb_asset` or the AA's base balance, the contributed funds remain locked in the AA indefinitely.
