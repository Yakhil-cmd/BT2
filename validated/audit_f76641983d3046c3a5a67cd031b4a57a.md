### Title
Unbounded recursion depth in oscript formula evaluation causes AA-triggering unit to crash/hang the node - ([File: formula/evaluation.js])

### Summary
`formula/validation.js` enforces a call-stack depth limit (`depth > 100`) when *validating* an oscript formula used in an AA definition or address/asset spending condition, but that guard is gated behind an mci upgrade flag (`pemCurvesFixMci`). The corresponding *evaluation* function in `formula/evaluation.js`, which actually executes the formula when an AA is triggered, has no depth guard at all — only a `count % 100` check that defers to `setImmediate` to avoid an overly long call stack, but this does not bound the recursion *depth* of a single nested expression tree (e.g., deeply nested parentheses/arrays/`if` blocks), only the total number of top-level evaluate calls interleaved via the event loop. [1](#0-0) [2](#0-1) 

### Finding Description
`exports.validate` in `formula/validation.js` tracks `depth++`/`depth--` around each recursive `evaluate` call and rejects a formula with `"maximum depth exceeded"` once `depth > 100`, but only for units after `constants.pemCurvesFixMci` (or when the min-retrievable mci has already passed that point): [3](#0-2) 

`exports.evaluate` in `formula/evaluation.js`, which is the function actually invoked at trigger time by `aa_composer.js` to run the formula and produce state changes/response messages, never applies an equivalent per-node depth check. It only guards against long call-stack chains of *sibling* statements via `count % 100 === 0` deferring to `setImmediate`, which does not help with a single deeply nested expression (e.g. `[[[[...1...]]]]`, `max(max(max(...1...)))`, or nested `if` blocks), since each nested level is a synchronous recursive call within the same tick: [4](#0-3) 

The project's own test suite documents this class of input (`deeply nested array`, `deeply nested dictionary`, `deeply nested max`, `deeply nested if`) at nesting depth 2000, confirming the bug class is understood and exercised, but relying only on the validation-time bound rather than a hard bound in the actual evaluator: [5](#0-4) 

For units at or before `pemCurvesFixMci` (i.e., anywhere the pre-upgrade validation path is still in effect, or for stored/legacy AA definitions and asset conditions validated at an mci prior to that upgrade), a deeply-nested formula can pass validation without the depth check being enforced, and then get executed by `formula/evaluation.js`'s unguarded recursive `evaluate`, causing `"RangeError: Maximum call stack size exceeded"` in the Node.js process handling the AA trigger.

### Impact Explanation
Any unprivileged unit poster can send a payment/trigger to an Autonomous Agent, or an AA author can define an AA, referencing a formula with a deeply nested expression tree. If the network mci gate (`pemCurvesFixMci`) is not yet in effect for that context, the formula bypasses the depth limit during validation but is fully evaluated by every node processing the triggering unit, causing an unhandled `RangeError` (stack overflow) that crashes or hangs the node process during unit/AA processing — a repeatable denial-of-service against nodes attempting to validate/execute that unit, consistent with the CVE-2024-21127 bug class (crash/hang caused by insufficiently checked structural input during a "definition"-like processing step).

### Likelihood Explanation
Exploitability depends on whether the relevant unit/AA/trigger is processed at an mci before `constants.pemCurvesFixMci` becomes effective for that validation path (`objValidationState.last_ball_mci < constants.pemCurvesFixMci` and `storage.getMinRetrievableMci() < constants.pemCurvesFixMci`). On networks where this upgrade mci has already passed for all retrievable history, this specific gap is closed for newly-validated formulas; but the evaluator itself (`formula/evaluation.js`) still has no independent depth guard, so any code path that reaches `exports.evaluate` with an unvalidated or insufficiently-validated deeply nested AST (e.g., via getters composition, remote calls, or older definitions grandfathered in) remains at risk. I was not able to fully confirm within the available index whether every call path into `formula/evaluation.js`'s `evaluate` is strictly preceded by the fixed validation depth check post-upgrade, so likelihood is assessed as present but bounded by the mci gate rather than fully open on up-to-date networks.

### Recommendation
Add the same `depth`-based recursion guard used in `formula/validation.js` (line ~276-288) to the `evaluate` function in `formula/evaluation.js`, unconditionally (not gated by `pemCurvesFixMci`), so that execution-time recursion is hard-capped regardless of when/how the formula was validated. This closes the gap for any legacy or edge-case formula that reaches evaluation without having passed the post-upgrade depth check.

### Proof of Concept
1. Construct an AA definition (or address/asset spending condition) whose oscript formula contains deep nesting, e.g. `${'['.repeat(2000)}1${']'.repeat(2000)}` or `${'if(1){'.repeat(2000)}return;${'}'.repeat(2000)}`, mirroring the existing test cases in `test/formula.test.js` lines 6415-6462.
2. Ensure the unit carrying this definition/trigger is validated in a context where `objValidationState.last_ball_mci < constants.pemCurvesFixMci` (or the equivalent min-retrievable-mci condition), so the depth guard in `formula/validation.js` is not applied.
3. Post the unit as an unprivileged AA trigger sender; when nodes call `formula/evaluation.js`'s `exports.evaluate` to execute the formula, the unguarded recursive `evaluate` calls exhaust the JS call stack, throwing `RangeError: Maximum call stack size exceeded` and crashing/hanging the node's unit-processing worker.

		count++;
		if (count % 100 === 0) // avoid extra long call stacks to prevent Maximum call stack size exceeded
			return (typeof setImmediate === 'function') ? setImmediate(evaluate, arr, cb) : setTimeout(evaluate, 0, arr, cb);
		depth++;
		const orig_cb = cb;
		cb = err => {
			depth--;
			if (err && !errorLocation && arr && typeof arr === 'object' && arr.line !== undefined) {
				errorLocation = arr.source_location
					? Object.assign({}, arr.source_location)
					: { line: arr.line };
			}
			orig_cb(err);
		};
