### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while stack/repository resolution uses the independent `repository.full_name` field, allowing cross-organization/cross-repository forgery of webhook-triggered actions - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . Once the signature check passes, every event handler (`PushHandler`, the `PullRequest::*Handler`s, etc.) independently resolves the target `Repository`/`Stack` using a *different* JSON field: `payload.dig('repository', 'full_name')` [2](#0-1) . Because these are two independently attacker-settable fields in the same JSON body, an actor who knows the webhook secret for *any* organization configured in Shipit can forge a payload whose `repository.owner.login` matches that known organization (satisfying signature verification) while `repository.full_name` points at a completely unrelated repository/stack, causing the handler to act on that unrelated stack.

### Finding Description
This is the direct analog of the audit finding's root cause: a value used for one purpose (the "current price"/authorization check) is substituted for a related-but-not-identical value that the rest of the calculation ("the actual liquidity math"/business action) actually needs, breaking the intended equality `authenticated_context == acted_upon_context`.

- `verify_signature` authenticates the *request origin organization* using `repository_owner` (derived from `repository.owner.login` or, if absent, `organization.login`) and looks up the matching `Shipit.github(organization: repository_owner)` webhook secret [3](#0-2) .
- `Handler#stacks`/`#repository_name`, used by `PushHandler#process` and every `PullRequest::*Handler#repository`, resolve the target repository via `payload.dig('repository', 'full_name')` [2](#0-1) , and `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack of that resolved repository matching the pushed branch [4](#0-3) .

There is no code path that checks `repository.owner.login == repository.full_name`'s owner, or that the verified organization actually owns the resolved repository. The binding broken is: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
An attacker who legitimately knows the webhook secret for Organization A (e.g., because they administer a GitHub App/webhook integration for their own org that is also configured in this Shipit instance) can craft a fully custom JSON payload and compute a valid HMAC signature themselves — no interaction with GitHub is required, since `WebhooksController#create` accepts any raw POST body matching the signature. By setting `repository.owner.login` to `"OrgA"` (satisfying signature verification) and `repository.full_name` to `"OrgB/victim-repo"`, the attacker can:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on stacks belonging to a repository/org they do not control and for which they hold no webhook secret, potentially forcing sync to an arbitrary/stale/malicious commit SHA and interacting with any continuous-deployment behavior tied to branch sync.
- Similarly drive `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc. against review stacks of an unrelated repository (archiving/unarchiving review stacks, injecting fabricated pull-request metadata) since they all key off the same `repository.full_name` field independent of the verified org.

This crosses the "cross-repository writes"/"unauthorized deploy" boundary called out as Critical-impact in scope, without requiring any Shipit session, API token, or the target organization's own webhook secret — only knowledge of *some* configured organization's secret, which is a materially weaker credential than what the target action actually requires.

### Likelihood Explanation
Requires the attacker to already hold a legitimate webhook secret for at least one organization configured in the Shipit deployment (a realistic scenario in multi-tenant/multi-org Shipit installs, as seen in the multiple GitHub App configs in `test/dummy/config/secrets_double_github_app.yml`), plus knowledge/guessing of a target repository's `owner/name` string that is registered in the same Shipit instance. Given both, the forgery is a straightforward signed HTTP POST with no rate limiting or additional secret material needed — likelihood is Medium-High in any multi-org deployment.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to select and verify the webhook signature is the same organization that owns the repository ultimately acted upon. Concretely: derive `repository_owner` strictly from the parsed `repository.full_name`'s owner segment (or cross-check `repository.owner.login` against the owner portion of `repository.full_name`) before verification, and reject (422) any payload where these disagree.

### Proof of Concept
1. Shipit is configured with GitHub App entries for `OrgA` and `OrgB`, each with its own `webhook_secret` (as modeled in `test/dummy/config/secrets_double_github_app.yml`). Attacker legitimately knows `OrgA`'s webhook secret (e.g., they administer OrgA's app).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "OrgA"` from `repository.owner.login`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully [5](#0-4) .
5. `PushHandler#process` resolves `repository_name` from `repository.full_name` = `"OrgB/victim-repo"` [6](#0-5) , and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on every matching stack of `OrgB/victim-repo` [4](#0-3)  — despite the attacker never having proven any relationship to `OrgB` or `victim-repo`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
