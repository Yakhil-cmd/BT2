### Title
Malicious swap route can traverse the caller’s authorization tree and steal unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, and related router strategies accept caller-provided route bytes and invoke the configured router without constraining the contracts reachable through that route. A malicious route can name an attacker-controlled pool, which then invokes a token transfer from the caller during router execution. Soroban authorization treats that transfer as a child of the caller’s signed strategy invocation, so signing the simulated authorization tree approves theft of unrelated wallet assets. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_tokens` authorizes only the exact transfer of `token_in` from the controller to the configured router, then forwards the caller-supplied `swap` bytes to `execute_strategy`. This protects the controller’s own input balance, but it does not constrain what contracts the route reaches. [4](#0-3) 

The router decodes each swap instruction’s pool address directly from the route’s caller-controlled asset registry and dispatches it to a venue adapter. Program validation checks only opcode, mode, and registry-index bounds; it does not check that a pool is trusted or canonical. [2](#0-1) [5](#0-4) 

A pool called by a venue adapter runs inside the strategy invocation. It can call `token.transfer(victim, attacker, amount)` for an unrelated token held by the caller. In recording mode, that transfer is reported as a child of the user’s controller authorization; if the user signs the returned tree, the malicious transfer is authorized and executes. [6](#0-5) [7](#0-6) 

### Impact Explanation
This allows theft of user funds beyond the supplied collateral or borrowed amount being routed. The malicious pool can transfer any unrelated token balance that the victim possesses and place that transfer in the authorization tree required to execute the lending operation. [8](#0-7) [9](#0-8) 

The router’s measured-output checks do not prevent this loss: the malicious pool can return a valid output, allowing the swap and account risk checks to pass while independently stealing wallet assets. The regression test demonstrates a debt-free user receiving the expected `ETH` supply while the attacker receives the user’s full unrelated wallet-token balance. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious pool contract and encode it in a route. No governance role, leaked key, compromised router, or protocol upgrade is needed because route registry indices are bounds-checked but their referenced pool addresses are not restricted to trusted venues. [5](#0-4) [3](#0-2) 

The exploit requires the victim to submit and sign the poisoned route. Standard transaction simulation exposes the malicious transfer as an authorization child rather than rejecting it at construction time; a user who signs the simulated tree completes the theft. [11](#0-10) [12](#0-11) 

### Recommendation
Do not allow route payloads to select arbitrary executable pool contracts. Maintain an on-chain allowlist or registry of approved pools per venue and verify every `hop.pool` against it before dispatch. [2](#0-1) 

Additionally, reject any authorization tree containing child invocations other than the expected `token_in.transfer(sender, router, total_in)` for direct router calls, or the expected controller input transfer for composed lending calls. User-facing verification should fail closed when an unexpected child appears, rather than treating simulation output as safe merely because it was generated by the host. [13](#0-12) 

### Proof of Concept
1. Alice supplies `10_000 USDC` and owns an unrelated `WALLET` token balance.
2. An attacker deploys `RogueHopPool`, storing `(alice, wallet_token, attacker, WALLET_BALANCE)`.
3. The attacker creates a `swap_collateral` route whose pool address is the rogue contract.
4. During execution, the router dispatches the swap to that caller-selected pool.
5. `RogueHopPool::swap` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`.
6. Simulation records that transfer under Alice’s `swap_collateral` authorization.
7. If Alice signs the returned tree, the swap deposits the expected `ETH` output while all `WALLET` tokens move to the attacker. [14](#0-13) [8](#0-7) [6](#0-5)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
