### Title
Webhook signature verification is keyed off an attacker-controlled organization field that is disjoint from the repository the handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/secret to validate the HMAC signature against using a field the attacker fully controls inside the unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`), while the actual `Handler` subclasses that execute side effects (`PushHandler`, `StatusHandler`, `MembershipHandler`, etc.) key their side effects off a *different* field in the same body (`repository.full_name`, or a bare `sha`, with no organization scoping at all). The signature check therefore authenticates "some organization configured in `Shipit.github`", not "the organization/repository the handler is about to touch." [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the analog of the M-23 "denominator the attacker controls diverges from the value actually used to compute a privileged outcome" bug class: in `BaseRewardPool`, `stake()` lets the attacker manipulate `totalSupply()` (the denominator) which then silently inflates `rewardPerTokenStored`, a value used later to authorize reward withdrawal — the check and the acted-upon value are not the same guaranteed-consistent quantity.

Here, the equality that should hold but is never enforced is:
`organization used to select verify_webhook_signature's secret == organization that owns the repository/commit the handler subsequently mutates`

Concretely:
- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and looks up `Shipit.github(organization: repository_owner)` to fetch that org's `webhook_secret` for HMAC verification. [2](#0-1) 
- `GitHubApp#verify_webhook_signature` **returns `true` unconditionally when `webhook_secret` is blank**: `return true unless webhook_secret`. [4](#0-3) 
- The documented setup flow treats `webhook_secret` as optional (`webhook_secret: # nil` in `config/secrets.development.shopify.yml`), so it is realistic for at least one configured organization in a multi-org Shipit install to have no secret set. [5](#0-4) 
- Once `verify_signature` passes (trivially, for the secret-less org named in `repository.owner.login`/`organization.login`), `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload*, not just the authenticated organization, to the handler. [6](#0-5) 
- `Handler#repository_name` (used by `PushHandler`) reads `payload.dig('repository', 'full_name')` — a field independent from, and never cross-checked against, `repository_owner` used for signing. [3](#0-2) 
- `StatusHandler#process` doesn't even look at `repository` — it does a **global** `Commit.where(sha: params.sha)` lookup across all stacks/repositories and calls `commit.create_status_from_github!(params)`, with no organization or repository scoping whatsoever. [7](#0-6) 

Put together: an attacker who knows (a) that one configured GitHub organization in `Shipit.github` has no `webhook_secret` set, and (b) a commit SHA belonging to a *different, secured* organization's stack, can send an unsigned/arbitrarily-signed POST to `/github/webhooks` with `organization.login` (or `repository.owner.login`) set to the secret-less org — passing `verify_signature` trivially — while the `sha`/`repository.full_name` in the body targets the victim's real, secured repository/commit. `StatusHandler` and `PushHandler` process that payload as if it were a legitimately signed event for that target repository.

### Impact Explanation
This crosses the "authenticated read/write scope != acted-upon scope" boundary called out in the rules ("an organization that authenticated versus the repository that is written"). Concretely, `StatusHandler` lets the attacker inject arbitrary commit statuses (`state`, `context`, `target_url`, `description`) for any commit SHA tracked by any stack in the Shipit instance, regardless of which organization's secret was checked. Since `ci.require` gates deploy eligibility on commit statuses (per `README.md`), this can be used to forge a passing CI status for a commit in a repository the attacker does not control, moving that commit into a deployable state and enabling an unauthorized deploy through Shipit's normal deploy flow — this reaches the "unauthorized deploy" Critical-impact criterion. `PushHandler` similarly lets the attacker trigger `stack.sync_github(expected_head_sha:)` for any tracked repository by naming it in `repository.full_name`, independent of which org's webhook secret gated the request.

### Likelihood Explanation
Requires: (1) the operator has configured at least one organization app without a `webhook_secret` (explicitly supported/documented as optional in `docs/setup.md` and shown as `nil` in the shipped `config/secrets.development.shopify.yml` template), and (2) the attacker knows a target commit SHA (visible on GitHub) or target repository full name (also public knowledge). No GitHub credentials, no Shipit session, and no `ApiClient` token are needed — only knowledge of public repository metadata and the fact that some org in the install lacks a webhook secret. This is a real, unauthenticated network path (`WebhooksController` skips CSRF and is only gated by `verify_signature`).

### Recommendation
- Require `repository.owner.login` (or the resolved `repository_owner`) used for signature verification to match the organization actually owning the repository/commit acted upon by every `Handler` subclass; reject mismatches.
- In `StatusHandler`, scope the `Commit` lookup to commits belonging to stacks whose repository owner equals the verified organization, not a bare global `sha` lookup.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank for any configured organization capable of controlling stack state; treat a missing secret as a hard misconfiguration (raise/log and reject) rather than an implicit bypass.

### Proof of Concept
1. Assume `Shipit.github` config has organization `no-secret-org` (webhook app installed, but `webhook_secret` left blank) and organization `victim-org` (properly secured) with a tracked stack/commit `SHA_X`.
2. Attacker sends, without any valid GitHub signature:
```
POST /github/webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "SHA_X",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` computes `repository_owner = "no-secret-org"`, fetches that org's `GitHubApp`, and `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `no-secret-org`. [8](#0-7) 
4. `StatusHandler.call(params)` runs `Commit.where(sha: "SHA_X")...create_status_from_github!(params)`, creating a fabricated "success" status on `victim-org`'s commit, without ever checking that `victim-org` matches the org whose secret was verified. [7](#0-6)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
