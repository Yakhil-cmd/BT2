### Title
Webhook signature verification is unconditionally bypassed when `webhook_secret` is unset, letting an unauthenticated attacker forge GitHub events (`push`, `membership`, `status`, `pull_request`, `check_suite`) - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` treats an absent `webhook_secret` as "signature valid" rather than "signature check inapplicable/deny". Because `webhook_secret` is a documented *optional* configuration key, any Shipit deployment (or any single organization in a multi-org config) that does not set it will accept **arbitrary, unsigned** webhook payloads on `/webhooks`, which are then dispatched to all registered event handlers with full trust.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration for the organization embedded in the untrusted request body, then asks that app to verify the signature: [1](#0-0) 

The verification itself is implemented as: [2](#0-1) 

`return true unless webhook_secret` means: if the operator did not configure a `webhook_secret` for that organization, **every** payload is accepted as "verified", regardless of the `X-Hub-Signature` header content. The setup docs and templates explicitly present `webhook_secret` as optional/blank-by-default: [3](#0-2) [4](#0-3) 

Once "verified", the controller dispatches the raw, attacker-controlled JSON straight into the handler registry with no further authentication: [5](#0-4) [6](#0-5) 

This breaks the intended trust binding: **"GitHub organization that authenticated the request" == "organization whose data/state is mutated by the handler."** With no secret configured, the left side of that equality is always vacuously true for any organization name the attacker chooses to put in the payload, while the right side is fully attacker-controlled.

The most impactful handler reachable this way is `MembershipHandler`, which, on a forged `membership` event, creates/looks up a `Team` and adds an arbitrary `User` (created on the fly from an attacker-supplied login) to that team: [7](#0-6) [8](#0-7) 

`Team` membership is the mechanism backing `github.oauth.teams` restricted-access configuration described in the setup docs (`teams` optional, required only if you want to restrict access to a set of GitHub teams): [9](#0-8) 

Other handlers are similarly reachable unauthenticated, e.g. `PushHandler` triggers a stack sync (`stack.sync_github`) for any repository name found in the forged payload: [10](#0-9) [11](#0-10) 

### Impact Explanation
This is a direct analog of the reported bug class: a configuration value that is allowed to take a value ("unset"/"zero") which silently disables a security-critical check elsewhere in the code, rather than failing safe. Here the consequence is not a revert/DoS but an authentication bypass on the webhook trust boundary: any organization deployed with Shipit's documented default (`webhook_secret` blank) accepts unsigned events. Concretely this lets an unprivileged, unauthenticated network attacker:
- Escalate into `Shipit.github_teams`/OAuth-restricted-access authorization by forging a `membership` webhook that adds an attacker-chosen GitHub login to a `Team` gating access (High-severity impact class per the listed criteria).
- Trigger stack syncs and other side effects on any repository/stack the attacker names in the forged payload, since `Handler#stacks` resolves purely from `payload.dig('repository', 'full_name')` with no relation to any verified identity.

### Likelihood Explanation
The precondition — `webhook_secret` left blank — is the literal default shown in `template.rb` and explicitly called "optional" in `docs/setup.md`, so this is a foreseeable, not exotic, misconfiguration a real deployment could ship with (directly analogous to `auctionDecrement` being settable to zero by design/oversight in the source report). No credentials, tokens, or repository access are required to exploit it; the attacker only needs network access to the `/webhooks` endpoint and knowledge of the target organization's login/name, both of which are public.

### Recommendation
Change `verify_webhook_signature` to fail closed when no secret is configured (e.g., log/alert and reject, or require `webhook_secret` to be present at boot for every configured organization) instead of returning `true`. At minimum, add a startup validation that raises if any configured GitHub organization is missing `webhook_secret`, mirroring the recommended fix pattern from the source report (reject the unsafe "disabled" value rather than silently accepting it).

### Proof of Concept
1. Deploy Shipit with a `github` org config that omits `webhook_secret` (the documented default/optional state).
2. As an unauthenticated attacker, POST to `/webhooks` with headers `X-Github-Event: membership` and any (or absent) `X-Hub-Signature`, and body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Restricted", "slug": "restricted-team", "url": "https://example.com"},
  "organization": {"login": "target-org"},
  "member": {"login": "attacker-github-login"}
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "target-org").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank.
4. `MembershipHandler#process` runs, creating/looking up the `Team` (matching a real, access-restricting team slug/organization from `github.oauth.teams`) and adding `attacker-github-login` as a member via `Team#add_member`.
5. The attacker's GitHub account is now recorded as a member of a team used to gate Shipit access, without any legitimate GitHub App webhook secret, session, or repository permission.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
