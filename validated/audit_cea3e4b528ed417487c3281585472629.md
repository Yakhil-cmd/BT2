### Title
Webhook signature scope selected from unverified `repository.owner.login`/`organization.login` while the acted-upon repository comes from a different, cross-checked-nothing field - Authentication Bypass / Unauthorized Deploy - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read directly out of the *unauthenticated* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every event `Handler` (e.g. `PushHandler`, `MembershipHandler`, pull-request handlers) then independently resolves which `Stack`/`Repository`/`Team` to act on using `payload.dig('repository','full_name')` (or other payload fields), with no check that this matches the organization that was used to select the signing secret. [1](#0-0) [2](#0-1) 

### Finding Description
In a multi-organization deployment (`config.github` keyed by org, as documented/shown in `config/secrets.development.shopify.yml` and `config/secrets.development.example.yml`), each organization can be configured with its own (optional) `webhook_secret`. [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly trusts any request when no secret is configured for the selected organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

`WebhooksController#verify_signature` selects *which* organization's app/secret to check against using `repository_owner`, itself taken straight from the unverified JSON payload:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Meanwhile, every handler that actually performs an authorization-sensitive action resolves the target repository/stack from a *different* payload field, `repository.full_name`, with no cross-check against `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler` uses this to sync a real, tracked stack: [6](#0-5) 

Because `repository.owner.login` (used to choose the secret to check) and `repository.full_name` (used to determine which repo/stack is actually mutated) are two independent, both attacker-controlled fields inside the same unauthenticated JSON body, an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to an organization that is configured in Shipit but whose `webhook_secret` is blank/nil — a supported, documented configuration (see the `# nil` placeholders in the secrets examples).
2. Set `repository.full_name` to any real repository/organization actually tracked by Shipit (with its own, properly-secured `webhook_secret`).

`verify_webhook_signature` will unconditionally return `true` for step 1's organization (no secret configured ⇒ no verification), and the handler will then process the payload against the repository named in step 2 — completely bypassing the HMAC check for an org that does enforce a secret. The equality that should hold — "the organization whose credentials authenticated this webhook" == "the organization owning the repository being written" — is never enforced.

### Impact Explanation
This breaks the authentication boundary between GitHub-verified webhook delivery and the actions the engine performs on tracked repositories/stacks. An unauthenticated network attacker (no Shipit session, no `ApiClient` token, no GitHub App credentials) can:
- Trigger `GithubSyncJob`/deploy pipeline resync for a targeted stack via the forged `push` event (`PushHandler#process`), influencing when/what commits are considered head — an unauthorized action against a stack that is otherwise protected by a properly configured `webhook_secret`.
- Create/delete `Team`/`Membership` records or mutate `PullRequest`/merge-queue state for arbitrary tracked repositories via `MembershipHandler`, pull-request handlers, and `check_suite` handlers, none of which validate that the acting organization matches the repository being mutated.

This matches the Critical/High impact bar for an unauthorized deploy/state mutation via an authentication-bypass path, achieved purely by exploiting the org-selection vs. repository-acted-upon mismatch — no `webhook_secret`, `ApiClient` token, or session is required by the attacker.

### Likelihood Explanation
Exploitability requires:
- The deployment to have (or have ever had) more than one GitHub organization configured, with at least one organization left without a `webhook_secret` (a state explicitly supported and shown as the default/example value `# nil` in the config templates), while another configured/tracked organization does enforce one.

This is a realistic misconfiguration risk in the documented multi-org configuration schema itself (the example files ship with `webhook_secret: # nil` as the default placeholder), making this reachable in real deployments that adopt the multi-org schema incrementally.

### Recommendation
- After parsing the payload, verify that `repository.owner.login`/`organization.login` used to select the signing app is the same organization implied by `repository.full_name` before dispatching to handlers — reject the request otherwise.
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for any organization that is explicitly configured in a multi-org setup; require every configured organization to have a non-blank `webhook_secret`, and fail closed if it is missing.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `config.github`: `victim-org` (has `webhook_secret` set) and `attacker-org` (left with `webhook_secret: nil`, matching the documented default).
2. Shipit tracks `victim-org/critical-repo` as a `Stack`.
3. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/critical-repo"
  }
}
```
No valid `X-Hub-Signature` header is required, since `Shipit.github(organization: "attacker-org")` resolves to a `GitHubApp` with `webhook_secret == nil`, causing `verify_webhook_signature` to return `true` unconditionally.
4. `verify_signature` passes; `PushHandler` resolves `repository.full_name` = `victim-org/critical-repo`, finds the real tracked `Stack`, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, all without ever presenting a valid signature for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
