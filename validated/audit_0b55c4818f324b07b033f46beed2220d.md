### Title
Hookify `tool_matcher` bypass via unsupported regex/glob matching in `_matches_tool` - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._matches_tool` only supports exact-string equality against a `|`-delimited list (or the literal wildcard `*`), while the plugin's own documentation and rule-authoring guidance advertise regex/glob-style matchers (e.g. `mcp__.*__delete.*`, prefix wildcards) as valid `tool_matcher`/`matcher` values. A hookify block rule authored per the documented syntax to deny a dangerous tool (Bash, Edit/Write/MultiEdit, or Stop) will silently never match any real `tool_name`, causing the intended block to fail open.

### Finding Description
`RuleEngine._matches_tool` (`plugins/hookify/core/rule_engine.py:127-142`) implements matching as:
```python
if matcher == '*':
    return True
patterns = matcher.split('|')
return tool_name in patterns
```
This only recognizes two representations of a matcher: the literal wildcard `*` and an exact-match OR-list split on `|`. There is no support for regex, glob prefixes, or case-insensitive matching, even though the plugin's hook-development documentation explicitly instructs rule authors to write matchers such as `"mcp__.*"`, `"mcp__.*__delete.*"`, or other regex-like patterns to catch classes of tools [1](#0-0) .

When a defender writes a `tool_matcher` (via `Rule.tool_matcher`, populated from frontmatter in `Rule.from_dict`, [2](#0-1) ) using such a documented pattern intended to block a dangerous MCP delete/write operation, `_rule_matches` calls `_matches_tool(rule.tool_matcher, tool_name)` at [3](#0-2) . Because the matcher string is not a proper regex/glob in the engine's exact-equality logic, `tool_name in patterns` evaluates to `False` for any real tool name (e.g. `mcp__filesystem__delete_file` never literally equals the string `mcp__.*__delete.*`), so `_rule_matches` returns `False` and the rule is treated as non-matching. `evaluate_rules` (`plugins/hookify/core/rule_engine.py:35-94`) then finds no blocking rule and returns `{}` — the operation is silently allowed with no warning that the rule engine never even attempted to enforce the security control.

The three hook entrypoints (`pretooluse.py`, `posttooluse.py`, `stop.py`) route attacker-influenced `tool_name`/`tool_input` (from a normal Bash/Edit/Write/Stop invocation) straight into `RuleEngine.evaluate_rules` [4](#0-3) [5](#0-4) , so any content that steers the agent toward using a tool the rule author expected to be caught by a documented-but-unsupported matcher pattern will bypass the block undetected. This directly breaks the invariant that "a matching block rule must reliably deny the protected operation," since the rule silently never activates rather than failing loudly.

### Impact Explanation
A hookify block rule (e.g., "deny destructive MCP delete tools" or "deny any `mcp__*` write/exfiltration tool") that is written using the documented regex-like matcher syntax will never actually engage, allowing the underlying dangerous Bash/Edit/Write/MultiEdit/Stop-triggering operation to execute. This can lead to unauthorized command execution, file mutation, or disclosure of sensitive code/prompt/token/diff/local file content to an unintended sink, because the defensive control that was supposed to catch and block the operation is a no-op due to the matcher representation mismatch. This matches the "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" impact class listed in the target Immunefi category.

### Likelihood Explanation
This is highly likely to occur in practice: the plugin's own official skill documentation (`SKILL.md`) recommends exactly the regex-style matcher patterns (`mcp__.*`, `mcp__.*__delete.*`) that the engine cannot handle, so any rule author following the documented guidance produces a silently broken rule. No special privileges are required — an unprivileged attacker only needs to induce (e.g., via prompt injection in repository content) the agent to invoke a tool whose name doesn't match the matcher's literal string, which is straightforward since regex-authored matchers essentially never literal-match real tool names. The failure is silent (no error, exit code 0, `{}` returned), making it hard for operators to detect that their security rule is dead.

### Recommendation
Update `_matches_tool` to properly interpret matcher patterns as regular expressions (reusing the existing `compile_regex` helper) or explicit glob patterns, matching the documented syntax, and validate/reject or warn on malformed matcher patterns at rule-load time rather than silently returning `False`. Add a config-loader-time self-test that at minimum compiles the matcher as a regex and logs an error if it fails to match the tool's own name space, so rule authors get feedback instead of a silently disabled block rule.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py` test suite:
```python
def test_regex_style_matcher_should_block_but_does_not():
    engine = RuleEngine()
    rule = Rule(
        name="block-mcp-delete",
        enabled=True,
        event="all",
        tool_matcher="mcp__.*__delete.*",   # documented regex-style matcher
        conditions=[Condition(field="tool_name", operator="regex_match", pattern=".*")],
        action="block",
        message="Blocked destructive MCP delete tool",
    )
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "mcp__filesystem__delete_file",
        "tool_input": {"path": "/etc/secret"},
    }
    result = engine.evaluate_rules([rule], input_data)
    # EXPECTED (per docs): block
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
    # ACTUAL (bug): result == {} because _matches_tool does literal equality,
    # so the dangerous mcp__filesystem__delete_file call is allowed through.
```
This demonstrates that a rule authored per plugin documentation fails to deny the dangerous MCP delete operation, confirming the tool-matcher representation bypass.
