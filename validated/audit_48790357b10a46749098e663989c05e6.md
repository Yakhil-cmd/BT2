This confirms the vulnerability. The base `Handler#stacks` and `#repository_name` resolve the target repository purely from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate against using a *different* field: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . Since these are independent, attacker-controlled JSON fields in the same unverified request body, nothing enforces that `repository.owner.login` (used to pick the secret) actually corresponds to `repository.full_name` (used to pick the Stack/repository acted upon).

### Title
Webhook signature verification authenticates the wrong field, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret using `repository.owner.login` (or `organization.login`) from the raw JSON body, but every webhook handler (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, and the `pull_request` handlers) resolves the actual target repository/stack using the independent `repository.full_name` field from the same body. Because signature verification and repository resolution key off different, attacker-controlled fields of an unsigned-at-verification-time payload, an attacker who controls a legitimate GitHub App installation for their own organization (and thus a valid webhook secret for it) can forge a webhook whose signature is valid for their own org while `repository.full_name` names a victim organization's repository.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 
and looks up `Shipit.github(organization: repository_owner)` to fetch the per-organization `webhook_secret` used to verify `X-Hub-Signature` [3](#0-2) .

Once verification passes, `create` dispatches the *entire raw params hash* — unchanged — to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

Handlers never re-derive or cross-check the organization; they trust `repository.full_name` directly:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

The `PullRequest::*` handlers (e.g. `ClosedHandler`, `OpenedHandler`, `ReopenedHandler`) similarly resolve the acted-upon repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4)  and then call state-changing operations such as `review_stack.archive!` [6](#0-5) , `stack.unarchive!` [7](#0-6) , or `ReviewStackAdapter#find_or_create!` [8](#0-7) , all scoped to whichever repository `full_name` claims — not the organization whose secret authenticated the request.

This breaks the equality: `organization authenticated by verify_signature == organization of the repository the handler writes to`. The two sides are independently attacker-controlled fields of the same request body evaluated before any HMAC check ties them together — the HMAC only proves the whole raw body was signed by *some* org's secret, not that `repository.owner.login` and `repository.full_name` agree.

### Impact Explanation
Any actor who legitimately owns/administers a GitHub App installation on *any* organization registered in Shipit (i.e., knows that organization's `webhook_secret`) can sign a payload where `repository.owner.login`/`organization.login` names their own org (so verification passes) but `repository.full_name` names a repository belonging to a different, victim organization/stack. This yields cross-repository writes: forging `push` events queues `GithubSyncJob`/`sync_github` against the victim stack [9](#0-8) , and forging `pull_request` events can archive/unarchive/provision review stacks belonging to a repository the attacker does not own. This matches the "cross-repository writes" high/critical-impact criterion, since the trust boundary that should bind a verified organization to the repository it can affect is not enforced.

### Likelihood Explanation
Exploitability requires only that the attacker control a webhook secret for *some* organization onboarded to the same Shipit instance (a low bar in multi-tenant Shipit deployments supporting multiple GitHub orgs/installations) — no Shipit session, `ApiClient` token, or GitHub write access to the victim repo is needed. All fields (`repository.owner.login`, `repository.full_name`, `organization.login`) are freely attacker-controlled JSON body fields, and the signature only covers the raw byte string, not any semantic binding between them.

### Recommendation
After (or as part of) `verify_signature`, enforce that the organization used to select the webhook secret matches the owner/organization implied by `repository.full_name` (e.g., require `repository.full_name.split('/').first == repository_owner`, or resolve `Repository.from_github_repo_name(...)` and check its recorded owner/organization matches `repository_owner`) before dispatching to any handler.

### Proof of Concept
1. Attacker's own org `attacker-org` is registered in Shipit with a known `webhook_secret` (e.g., because attacker administers that GitHub App/organization).
2. Attacker crafts a `push` (or `pull_request`) JSON payload where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret over the raw body, since `verify_signature` looks up the secret via `repository_owner` which resolves to `"attacker-org"`.
4. `POST /webhooks` with `X-Github-Event: push` passes signature verification (`Shipit.github(organization: "attacker-org").verify_webhook_signature(...)` succeeds).
5. `create` calls `PushHandler.call(params)`, whose `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob`/triggers stack changes for the victim's stack — a write the attacker was never authorized to trigger.
