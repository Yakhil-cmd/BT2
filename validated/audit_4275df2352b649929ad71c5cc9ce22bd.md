## Finding: FederatedKeyless public key mismapped to plain Keyless in single-key signature parsing

### Title
API layer parses a `FederatedKeyless` public key into a plain `Keyless` `AnyPublicKey`, dropping the `jwk_addr` binding - (File: `api/types/src/transaction.rs`)

### Summary
The REST API's JSON→native conversion for `SingleKeySignature` mishandles the `FederatedKeyless` public key variant. Instead of constructing `AnyPublicKey::federated_keyless(key)` (which preserves the `jwk_addr` that anchors JWK trust to a specific dapp-controlled account), it constructs `AnyPublicKey::keyless(key)`, silently reclassifying the key as a "canonical" (non-federated) keyless key. This is the same bug class as the external report: an entity that must be tracked/verified against a specific paired binding (here, `(iss, idc, jwk_addr)` for federated keyless) is instead collapsed into the wrong, more generic bucket (plain `(iss, idc)` keyless, trusted against the governance-controlled `0x1::jwks::PatchedJWKs` instead of the account-owned `FederatedJWKs`).

### Finding Description
Compare the three parallel conversions in `api/types/src/transaction.rs`:

- The canonical, correct conversion `TryFrom<&PublicKey> for AnyPublicKey`: [1](#0-0) 

- The `MultiKeySignature` → `AccountAuthenticator` conversion (correct): [2](#0-1) 

- The `SingleKeySignature` → `AccountAuthenticator` conversion (buggy): [3](#0-2) 

In the buggy branch, `PublicKey::FederatedKeyless(ref p)` bytes are parsed via `p.value.inner().try_into()` and then wrapped with `AnyPublicKey::keyless(key)` — the same constructor used for the plain `Keyless` arm just above it — instead of `AnyPublicKey::federated_keyless(key)`. This is a direct copy/paste-style inconsistency: two sibling conversion functions in the same file (`PublicKey → AnyPublicKey` and `MultiKeySignature → AccountAuthenticator`) correctly preserve the `federated_keyless` variant, but the `SingleKeySignature → AccountAuthenticator` path does not.

`FederatedKeylessPublicKey` (`jwk_addr: address, pk: KeylessPublicKey`) and `KeylessPublicKey` (`iss_val: String, idc: IdCommitment`) have different BCS layouts: [4](#0-3) 

Because the downstream keyless verification (`keyless_validation.rs`) branches its JWK trust source based on which enum variant (`AnyKeylessPublicKey::Normal` vs `AnyKeylessPublicKey::Federated`) is present: [5](#0-4) 

mis-tagging a federated key as normal would cause the VM to search for the matching JWK in the framework-level `PatchedJWKs` (`0x1`) instead of the dapp's `FederatedJWKs` account resource — the wrong "oracle"/trust source for that key, exactly mirroring the reported bug class of using a token/key's trust anchor from the wrong bucket.

### Impact Explanation
If reachable and if the malformed byte reinterpretation manages to still deserialize successfully as a `KeylessPublicKey` (an unverified assumption — see Likelihood below), a client-submitted JSON transaction whose `single_key_signature.public_key` is typed `federated_keyless` would have the `jwk_addr` silently dropped, and the authenticator constructed would authenticate against the wrong JWK trust source (canonical `0x1` JWKs instead of the specific dapp-owned federated JWK set, or vice versa depending on interpretation). This could, in principle, allow signature verification to pass against an unintended JWK source, which is a signer/authenticator binding confusion at the admission boundary.

### Likelihood Explanation
Low-to-uncertain. `FederatedKeylessPublicKey` bytes are `address (32 bytes) || KeylessPublicKey`, while `KeylessPublicKey` bytes are `String || IdCommitment`. Reinterpreting the former as the latter via `try_into()`/BCS deserialization will very likely fail outright (the leading address bytes will be misread as a ULEB128 string length/UTF‑8 payload and fail to parse), causing the whole conversion to error out via the `?` operator rather than silently admitting a wrongly-bound transaction. I was not able to fully verify, within the tool budget, whether this JSON conversion path is actually wired into a live transaction-submission/admission flow (mempool/vm-validator) versus being used only for read-side JSON serialization of already-validated on-chain data. This uncertainty about reachability and about whether a byte sequence can be crafted that both looks like a valid `FederatedKeyless` public key to the client and parses successfully as a `KeylessPublicKey` reduces confidence that this is independently exploitable to bypass admission.

### Recommendation
Fix the `SingleKeySignature → AccountAuthenticator` conversion in `api/types/src/transaction.rs` to mirror the correct sibling implementations: use `AnyPublicKey::federated_keyless(key)` for the `PublicKey::FederatedKeyless` arm instead of `AnyPublicKey::keyless(key)`. Add a regression test asserting that round-tripping a `FederatedKeyless` `SingleKeySignature` through `TryFrom` preserves the `jwk_addr` and produces `AnyPublicKey::FederatedKeyless`, not `AnyPublicKey::Keyless`.

### Proof of Concept
1. Construct a JSON `SingleKeySignature` whose `public_key` is tagged `type = "federated_keyless"` with valid `FederatedKeylessPublicKey` BCS bytes (`jwk_addr || KeylessPublicKey`).
2. Submit it through the API code path that calls `TryFrom<&SingleKeySignature> for AccountAuthenticator`.
3. Observe (via unit test / debug) that the resulting `AccountAuthenticator::SingleKey` wraps an `AnyPublicKey::Keyless` rather than `AnyPublicKey::FederatedKeyless`, in contrast to what `TryFrom<&PublicKey> for AnyPublicKey` and `TryFrom<&MultiKeySignature> for AccountAuthenticator` produce for equivalent input in the same file: [6](#0-5) 

Given the unresolved uncertainty about whether the malformed bytes still deserialize and whether this conversion sits directly on the mempool/vm-validator admission path, this should be treated as a confirmed code-level defect requiring a fix, but I cannot fully confirm end-to-end exploitability (wrong-sender admission and commit) without further investigation in a live/dynamic environment — which would require a Devin session with code execution to trace the exact call sites of `TryFrom<&SingleKeySignature>` and to test BCS deserialization behavior on cross-typed byte payloads.
