### Title
`Api::CCMenuController#stack` bypasses the `ApiClient.stack_id` scope binding, letting a single-stack token read any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController#stacks`/`#stack` enforce that scope by filtering `Stack.where(id: current_api_client.stack_id)` before looking up the requested `params[:stack_id]`. [1](#0-0)  `Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving directly against the global `Stack` table. [2](#0-1) 

### Finding Description
The binding that should hold is: `stack a token authorizes == stack a token can touch`. `ApiClient#stack_id` is meant to restrict a client to a single stack, e.g. the `here_come_the_walrus` fixture is scoped to the `shipit` stack and only has the `read:stack` permission. [3](#0-2)  `BaseController#stacks` implements this restriction by intersecting the client's `stack_id` with the queryset before any lookup by param. [4](#0-3)  `BaseController#stack` (used by every other API endpoint, e.g. `Api::StacksController`) calls `stacks.from_param!(params[:stack_id])`, so an out-of-scope stack ID raises a not-found error. [5](#0-4) 

`Api::CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly — the unscoped model class, not the `stacks` scope. [6](#0-5)  The `require_permission :read, :stack` before_action only checks that `'read:stack'` is present in `current_api_client.permissions` via `ApiClient#check_permissions!`; it never compares `operation`/`scope` against the specific stack being accessed. [7](#0-6)  Consequently, any `ApiClient` with `read:stack` permission — even one explicitly scoped to a single stack — can pass `params[:stack_id]` for a *different* stack and successfully resolve it in `CCMenuController#show`, because `stack` never re-applies the `stack_id` scope.

### Impact Explanation
This is an unauthenticated-scope-escalation issue for a legitimate, but supposedly stack-scoped token: it lets a credential holder read stack state (`stack.deploys_and_rollbacks.last`, build name, status, last build label/time) for stacks it was never granted access to. [8](#0-7)  This matches the "unauthenticated read of stack state" bug class called out as a valid High-severity impact for this engine. It breaks the `ApiClient.stack_id` authorization boundary the application relies on when it issues narrowly-scoped tokens (e.g. the CCMenu token auto-created by `CcmenuUrlController#client`, which is explicitly scoped to one stack and given only `read:stack`). [9](#0-8) 

### Likelihood Explanation
Exploitation requires only possessing a valid `ApiClient` authentication token that has the `read:stack` permission (regardless of its `stack_id` scoping) — no elevated privileges, no session, and no other credential. Such tokens are routinely distributed for narrow purposes (e.g., embedding in CI dashboards via the CCMenu URL feature), which is exactly the scenario this scoping mechanism is meant to contain. Because the bypass is a straightforward parameter substitution against a documented, reachable endpoint, likelihood is high once a scoped token is available.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` accessor from `BaseController` instead of the unscoped `Stack` model, i.e. remove the private `stack` override (or reimplement it as `stacks.from_param!(params[:stack_id])`), so the `current_api_client.stack_id` restriction is enforced consistently across all API controllers.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to stack `A` with only `read:stack` permission (mirrors the `here_come_the_walrus` fixture / the client auto-provisioned by `CcmenuUrlController`). [3](#0-2) [9](#0-8) 
2. Using that client's `authentication_token`, request `GET /api/:stack_B_owner/:stack_B_name/ccmenu?token=<token>` for a different, unrelated stack `B`.
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully. [10](#0-9)  `require_permission :read, :stack` passes because the client has `'read:stack'` regardless of which stack is targeted. [7](#0-6)  `stack` resolves stack `B` directly from the unscoped `Stack` table, bypassing the `stack_id` restriction. [6](#0-5) 
4. The response renders stack `B`'s build name/status/last build info even though the token was only ever authorized for stack `A`. [8](#0-7) 

Note: I was unable to find any additional access control layer (e.g., a controller-level `before_action` re-checking `stack_id`) elsewhere in `app/controllers/shipit/api/**` that would mitigate this; `CCMenuController` appears to be the only overriding controller among those I inspected within the given scope.
