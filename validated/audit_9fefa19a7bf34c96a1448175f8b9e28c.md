The Union Finance report describes an admin `pause()` that blocks `unstake()`/`withdraw()` via a `whenNotPaused` modifier, permanently locking user funds until the admin lifts the pause. The analogous privileged-but-reachable actor in ocore is the **asset issuer/definer**, who controls the `spender_attested` gating for a `spender_attested` asset via the `asset_attestors` message. Once an asset requires attestation to spend, the definer can update the attestor list at any time, and the network always validates transfers against the *most recent* attestor list rather than the list in effect when the coins were received — silently freezing balances held by previously-attested (now un-attested) addresses.

### Title
Asset issuer can freeze holders' funds at will by updating the `spender_attested` attestor list - (File: `validation.js`, `storage.js`)

### Summary
An asset defined with `spender_attested: true` requires that both spenders and (for issues) issuers be on the asset's current attestor list. The definer can publish a new `asset_attestors` message at any time to replace this list. Validation always checks against the *latest* attestor list, not the list that applied when coins were received, so addresses that were validly attested and received asset funds can be locked out of spending them the moment the definer swaps the attestor list — with no way for those users to reclaim liquidity except by convincing an attestor on the new list (potentially none, or a hostile definer-controlled attestor) to attest them again.

### Finding Description
When an asset is created with `spender_attested: true`, ocore requires that authors of any payment involving that asset be attested by one of the asset's attestors, checked via `objAsset.arrAttestedAddresses`: [1](#0-0) 

The attestor list itself is not fixed at asset creation — it can be replaced by a single-authored `asset_attestors` message, gated only by a check that the sender is the asset's definer: [2](#0-1) 

When resolving whether an address is currently attested, `readAsset`/`addAttestorsIfNecessary` always looks up the single most recent `asset_attestors` unit for that asset (ordered by level/rowid, `LIMIT 1`), not any attestor list that was active historically: [3](#0-2) 

This latest list is then used to filter which of the *current* payment's addresses are attested, both for issuing: [4](#0-3) 
and for transferring already-owned outputs (spending inputs): [5](#0-4) 
as well as for outputs of a payment (i.e., attestor changes also gate who can even *receive* new spends): [6](#0-5) 

Because attestation is re-checked at spend time against the live/current attestor list rather than pinned at the time the coins were acquired, a definer can:
1. Issue/attest a set of addresses, letting users accumulate the asset.
2. Publish a new `asset_attestors` message that drops those addresses (or the attestors who vouched for them) from the list.
3. Immediately, every previously-attested holder's balance becomes unspendable — `validatePaymentInputsAndOutputs`/`validatePayment` will reject any transfer from (or even to) those addresses with `"owner address is not attested"` / `"none of the authors is attested"` / `"some output addresses are not attested"`.

This is directly analogous to the reported bug class: a privileged, in-scope actor (the asset issuer, explicitly listed as reachable) flips a switch that blocks otherwise-valid withdrawal/transfer operations for regular users, with no cooldown, timelock, or protection for balances acquired before the switch was flipped.

### Impact Explanation
Holders of a `spender_attested` asset can have their funds frozen indefinitely at the sole discretion of the asset definer, who can unilaterally revoke or replace the attestor list at any point after issuance. Users have no recourse within the protocol to unfreeze their own funds — they depend entirely on the definer or a newly designated attestor to re-attest them. This satisfies the "AA fund loss or freezing" / unauthorized freezing criteria: user funds already legitimately acquired become permanently or arbitrarily lockable by a single-party action.

### Likelihood Explanation
Any asset using `spender_attested: true` (a documented, supported asset feature, also usable by AAs issuing assets per `aa_validation.js`) is exposed. The definer needs only to post one more `asset_attestors` unit — a single, cheap, single-authored transaction — to lock out existing holders. No collusion or special network position is required, only the definer role that is created at asset-definition time.

### Recommendation
Consider pinning the attestor list applicable to a given payment input to the list that was in effect when the corresponding output was created (analogous to how other per-output asset properties are captured at issuance), or add an explicit unlock/grace mechanism so that once an address is attested and receives asset funds, subsequent attestor-list changes cannot retroactively strip its ability to spend the coins it already legitimately holds. At minimum, documentation should strongly warn users that `spender_attested` assets carry an issuer-controlled freeze risk equivalent to an admin pause with no escape hatch.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and initial `attestors: [T1]`.
2. `T1` attests address `U`.
3. `U` receives a payment of asset `A` (validated fine, since `U` is attested by `T1`, per `validation.js:2115-2122`).
4. `D` posts an `asset_attestors` message for asset `A` with `attestors: [T2]` (dropping `T1`) — accepted per `validateAttestorListUpdate` (`validation.js:2829-2848`), since `D` is the definer.
5. `U` attempts to spend/transfer their previously received `A` balance. `storage.readAsset` now resolves the attestor list to `[T2]` only (`storage.js:1911-1946`); since `U` was never attested by `T2`, validation now fails with `"owner address is not attested"` (`validation.js:2504-2507`), permanently blocking `U`'s spend unless `T2` separately attests them. function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
