## Title
Missing caller-deposit refund when `address_check_callback` / `nep_141_storage_balance_callback` intermediate promises fail, locking external caller funds — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract`'s `CallerDeposit` mechanism is designed to refund an external caller's attached deposit whenever a cross-contract call spawned by `rlp_execute` fails, but this refund is only implemented in the final callback (`rlp_execute_callback`). The two intermediate callbacks that can also terminate the flow on failure — `address_check_callback` and `nep_141_storage_balance_callback` — drop `caller_deposit` on the `PromiseResult::Failed` branch without issuing any refund.

### Finding Description
`CallerDeposit::new` explicitly documents its purpose: "A data type to keep track of the deposit given by an external caller. This allows us to refund the caller's deposit if the cross-contract call fails." [1](#0-0) 

The success path correctly implements this contract in `rlp_execute_callback`, refunding `caller_deposit` via `env::promise_batch_action_transfer` whenever the final promise result is `PromiseResult::Failed`: [2](#0-1) 

However, `caller_deposit` is threaded through two intermediate, promise-chained callbacks before reaching `rlp_execute_callback`:
- `address_check_callback`, invoked after calling the address registrar `lookup`, on `PromiseResult::Failed` returns an error `ExecuteResponse` directly without ever using `caller_deposit` to refund the caller: [3](#0-2) 
- `nep_141_storage_balance_callback`, invoked after calling `storage_balance_of` on a NEP-141 token, on `PromiseResult::Failed` likewise returns directly without refunding: [4](#0-3) 

In both cases `caller_deposit` is a parameter of the function (passed in from `inner_rlp_execute`) but is silently discarded on the failure branch instead of being used to schedule a refund transfer, unlike the identical pattern in `rlp_execute_callback`.

This is structurally analogous to the reported Solidity bug class: a return/result value from a cross-call is not properly propagated into the compensating logic (refund/revert), so the contract continues down a path that leaves the caller's already-collected deposit stuck in the wallet contract, even though the on-chain state correctly records the outer transaction as "handled" (the promise resolves normally, `has_in_flight_tx` is reset to `false`, and no retry mechanism exists to reclaim the deposit).

### Impact Explanation
Any external, non-owner caller (predecessor != current_account_id) who attaches a NEAR deposit while relaying an Ethereum-emulated transaction through `rlp_execute` — specifically an `EOABaseTokenTransfer` with `address_check: Some(_)` (goes through `address_check_callback`) or an `ERC20Transfer` (goes through `nep_141_storage_balance_callback`) — will have that deposit **not refunded** if the intermediate cross-contract call (`address_registrar.lookup` or `token.storage_balance_of`) fails (e.g., due to insufficient prepaid gas, the target contract panicking, or the target account not existing). The deposit remains held by the wallet contract with no code path issuing a refund for that specific failure, unlike the failure path in `rlp_execute_callback`. This is a concrete unauthorized/irrecoverable loss of caller funds (a value-locking bug), matching the accepted impact class ("unauthorized state or balance change" / fund loss).

### Likelihood Explanation
Likelihood is moderate: it requires (1) an external caller (not the wallet owner) attaching a deposit, and (2) the specific intermediate promise (`lookup` or `storage_balance_of`) failing rather than the main action. Both paths are reachable in normal (non-adversarial) operation — the address registrar or token contract can fail for many benign reasons (insufficient gas, transient errors, non-existent target), so this is not a purely contrived edge case; relayers regularly interact with these flows and any failure of the auxiliary lookup call triggers the bug.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, on the `PromiseResult::Failed` branch (and any other early-return `ExecuteResponse::success = false` branch), mirror the refund logic used in `rlp_execute_callback`: check `caller_deposit` and, if `Some`, create a `promise_batch_create`/`promise_batch_action_transfer` to refund `account_id` the `yocto_near` amount before returning the failure response.

### Proof of Concept
Conceptual trace (no test harness modification needed to see the code gap):
1. External account `caller.near` calls `rlp_execute` on the wallet contract with an attached deposit, encoding an `EOABaseTokenTransfer` whose `to` address requires an address-registrar lookup (`address_check: Some(address)`).
2. `inner_rlp_execute` computes `caller_deposit = CallerDeposit::new(&context)` (`Some` since `predecessor_account_id != current_account_id` and deposit > 0) and schedules `address_registrar.lookup(address).then(ext.address_check_callback(target, action, caller_deposit))`. [5](#0-4) 
3. The `lookup` call fails (e.g. registrar contract panics or runs out of gas).
4. `address_check_callback` matches `PromiseResult::Failed` and returns `ExecuteResponse { success: false, ... }` directly — `caller_deposit` is dropped, no transfer promise is created. [3](#0-2) 
5. The caller's attached NEAR deposit remains in the wallet contract's balance indefinitely; there is no retry/reclaim entry point for it (`has_in_flight_tx` is reset to `false` so the wallet is usable again, but the specific deposit is unrecoverable by the caller).

This matches the same root cause pattern as the referenced report: a failure path that skips the compensating refund/rollback logic that the "happy path"/other callback correctly implements.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
