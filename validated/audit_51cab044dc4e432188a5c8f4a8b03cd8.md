## Finding: Unauthenticated cross-organization webhook forgery via `repository.owner.login`/`repository.full_name` binding mismatch

### Title
Webhook signature is verified against the organization named in `repository.owner.login`, while the actual target repository/stack is resolved from the separate, unchecked `repository.full_name` field, letting an unauthenticated attacker impersonate any organization whose `webhook_secret` is unset to act on stacks belonging to a different, secured organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate the inbound webhook HMAC by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated request body, then calls `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp`. Signature verification is only meaningful if that org's `webhook_secret` is configured; if it is blank, `GitHubApp#verify_webhook_signature` returns `true` unconditionally. Crucially, none of the downstream `Webhooks::Handlers::Handler` subclasses re-derive the target repository from `repository_owner` - they instead look up the acted-upon `Repository`/`Stack` from the sibling, independently-attacker-controlled field `repository.full_name`. Because these two JSON fields are never cross-checked, a request can claim to be "from" an org with no webhook secret while actually targeting a completely different org's repository/stack. ### Finding Description
1. `Shipit` supports multi-organization deployments where each org has its own `github` config block, including an independently optional `webhook_secret` (documented in `docs/setup.md`'s "Using Multiple Github Applications" section).
2. `WebhooksController#verify_signature` selects which org's secret to verify the signature against using a value taken entirely from the untrusted payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

3. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is blank:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

4. Once past `verify_signature`, `WebhooksController#create` dispatches the payload to handlers (`PushHandler`, PR handlers, `MembershipHandler`, `CheckSuiteHandler`, etc.). All of these resolve the target `Repository`/`Stack` from `repository.full_name` (a field never checked against `repository.owner.login`):
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` then acts on those stacks directly:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The binding that should hold is: `organization that authenticated the delivery == organization owning the repository/stack being written to`. Because `repository_owner` (used for authentication) and `repository.full_name` (used for the actual write) are two independent, attacker-suppliable fields in the same unauthenticated POST body, this binding does not actually hold. An attacker who knows (or guesses) that any one configured organization on the instance has no `webhook_secret` set can set `repository.owner.login` to that lax org while setting `repository.full_name` to any other, properly-secured organization's `owner/repo`. The forged request sails through `verify_signature` (secret-less org ⇒ unconditional `true`) and is then processed against the victim org's real stack.

### Impact Explanation
This is an unauthenticated cross-repository write: an anonymous requester hitting the public `/webhooks` endpoint can trigger `GithubSyncJob` for a targeted stack (`push` event), create/delete team memberships and users (`membership` event), or archive/unarchive review stacks and mutate PR-tracked state (`pull_request` events) - for any repository/stack in the Shipit instance - purely by naming a different, secret-less organization in `repository.owner.login`. This matches the "cross-repository writes" / "unauthorized deploy" critical-impact bucket: no session, `ApiClient` token, or GitHub credentials are required, only knowledge that the multi-org Shipit instance has at least one org configured without a `webhook_secret` (an explicitly documented, supported, "optional" configuration).

### Likelihood Explanation
Requires a specific but realistic and explicitly documented deployment shape: a multi-organization Shipit install (per `docs/setup.md`) where at least one configured organization has left `webhook_secret` unset - itself a documented "optional" setting, with no code-level guardrail preventing that laxity from bleeding into other orgs' repositories. Given the feature is officially supported and the secret is explicitly optional per-org, this is a plausible real-world misconfiguration rather than a purely theoretical one.

### Recommendation
- After resolving the target `Repository`/`Stack` from `repository.full_name`, verify that its owning organization matches the organization (`repository_owner`) whose secret was used to authenticate the request; reject the webhook otherwise.
- Alternatively/additionally, require `webhook_secret` to be present for all configured organizations (fail closed instead of `return true unless webhook_secret`), or scope the lax organization's "no-secret" trust only to its own repositories rather than to any `repository.full_name` value found in the payload.

### Proof of Concept
Given a Shipit instance configured with two orgs, `orgA` (has `webhook_secret` set, owns `orgA/secret-repo` tracked by Shipit) and `orgB` (no `webhook_secret` configured):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/secret-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```

- `verify_signature` computes `repository_owner = "orgB"`, fetches `Shipit.github(organization: "orgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` with no signature header required at all.
- `PushHandler` then resolves `Repository.from_github_repo_name("orgA/secret-repo")` and enqueues `GithubSyncJob` for all of its non-archived stacks matching branch `main`, entirely bypassing `orgA`'s configured webhook secret. [6](#0-5)

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
