### Title
`StatusHandler` never checks `repository`, allowing any org's webhook to write CI status onto any other tenant's commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with a bare, global `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no scoping to the repository/stack that the webhook claims to originate from. Unlike every other handler (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabelCapturingHandler`, etc.) which all `requires :repository { requires :full_name, String }` and resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting, `StatusHandler`'s params schema (lines 7-18) has no `repository` field at all, so the binding `params.repository.full_name == payload['repository']['full_name']` used everywhere else to scope handler actions to the authenticated tenant simply does not exist for this handler.

### Finding Description
The broken binding, stated as an equality that should hold but does not: for every other handler, `stacks (queried) == Repository.from_github_repo_name(params.repository.full_name).stacks`, i.e., the handler action is scoped to the repository the webhook signer authenticated as. For `StatusHandler`, no such equality is ever evaluated — `params` doesn't carry a `repository` key at all [1](#0-0) , and `process` does a completely unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This is a global query across the `commits` table with no `stack_id`/`repository_id` filter, whereas the structurally analogous `CheckSuiteHandler` correctly scopes via `stacks.where(branch: ...)` before touching commits [3](#0-2) .

Signature verification does not close this gap. `WebhooksController#verify_signature` derives the org to check against purely from the payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) . An attacker who has legitimately installed the GitHub App for their own org (routine self-service) has a valid `webhook_secret` for *that org*. They can send a `status` event payload containing only `sha`, `state`, and optionally `organization.login = "attacker-org"` (with no `repository` key), sign it with their own org's secret, and `verify_webhook_signature` will pass because it only checks the HMAC against the org named in the payload, not against any specific repository ownership of the target commit.

Once past signature verification, `ExplicitParameters::Parameters.parse!` succeeds because the schema (lines 7-18) never requires `repository`. `StatusHandler#process` then runs, and if the attacker knows (or guesses) the `sha` of a commit belonging to a stack in a completely different, unrelated tenant/repository — commit SHAs are frequently public (visible on public GitHub repos, PRs, CI logs) — `Commit.where(sha: params.sha)` will match it regardless of which org or repository it belongs to, and `create_status_from_github!(params)` will write a `Status` row for that foreign commit using attacker-controlled `state`, `description`, `target_url`, and `context` [5](#0-4) .

### Impact Explanation
This lets an unprivileged attacker (owner of any org onboarded onto Shipit with their own webhook secret) inject arbitrary CI statuses (`success`/`failure`/`pending`/`error`, with attacker-chosen `context`/`description`/`target_url`) onto commits belonging to a completely different tenant's tracked repository, without ever authenticating to or being authorized for that repository. `Commit#create_status_from_github!` feeds directly into `Status#replicate_from_github!`, which per `test/models/commits_test.rb` transitions cause `deployable_status` webhooks to fire and can enqueue `ProcessMergeRequestsJob` on state transitions to `success`/`pending` [6](#0-5) , and `deployable?` is defined in terms of CI success state [7](#0-6) . This can make a foreign commit spuriously "deployable" (attacker sends `success`) or block a deploy of a foreign commit (attacker sends `failure`/`error`), and can trigger auto-merge processing for unrelated pull requests. This is a genuine cross-repository write where the payload for one tenant/org mutates another tenant's commit/stack state — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category.

### Likelihood Explanation
Preconditions are minimal and match the routine, self-service scenario described: attacker's org must exist in `Shipit.github_organizations` with any assigned `webhook_secret` — no special Shipit role, no knowledge of any other org's secret, no repository maintainer status. The only extra requirement is knowing the target commit's SHA, which is often public (GitHub UI, PR pages, CI logs) for the many organizations/repos tracked by a shared Shipit instance. The attack is trivially repeatable against any known SHA and requires only a single signed HTTP POST to `/webhooks` per attempt.

### Recommendation
Add a `requires :repository { requires :full_name, String }` block to `StatusHandler`'s params, mirroring the other handlers, and scope the commit lookup through the resolved repository's stacks (e.g. `stacks.flat_map(&:commits) ... where(sha: params.sha)` or joins through `Repository.from_github_repo_name(params.repository.full_name)`), so a status webhook can only mutate commits that belong to the repository named (and implicitly authenticated) in that payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "does not raise when repository key is absent from payload" do
          payload = {
            'sha' => shipit_commits(:cyclimse_first).sha,
            'state' => 'success',
            'organization' => { 'login' => 'attacker-org' }
          }
          assert_nothing_raised do
            StatusHandler.new(payload).process
          end
        end

        test "writes a status onto a commit belonging to an unrelated stack, with no repository binding" do
          victim_commit = shipit_commits(:cyclimse_first) # belongs to a different stack/repo than 'attacker-org'
          payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'organization' => { 'login' => 'attacker-org' } # attacker's own org, not victim_commit's repo owner
          }

          # Equality that SHOULD hold but is never checked:
          # params.repository.full_name == victim_commit.stack.repository.full_name
          # StatusHandler's schema has no `repository` field at all -> binding cannot exist.

          assert_difference '-> { victim_commit.statuses.count }', 1 do
            StatusHandler.new(payload).process
          end
        end
      end
    end
  end
end
```
Note: the existing `test/controllers/webhooks_controller_test.rb` status tests always merge in `repository_params` for convenience [8](#0-7) , which masks the fact that the schema doesn't actually require it — the PoC above demonstrates the payload works identically, and mutates a foreign commit, without that key present.
