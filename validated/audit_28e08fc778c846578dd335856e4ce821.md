### Title
Webhook signature is verified against the organization derived from attacker-controlled payload fields, decoupled from the repository the event actually mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a delivery against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the untrusted JSON body, before the HMAC has been checked. Every downstream `Webhooks::Handlers::Handler` then resolves the repository to mutate from a *different* field of the same untrusted body: `payload.dig('repository', 'full_name')`. Nothing enforces that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same organization. Shipit explicitly supports hosting multiple, independently-configured GitHub organizations (each with its own `webhook_secret`) in one instance, as shown by `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`'s "Using Multiple Github Applications" section, and resolved via `Shipit.github_app_config`/`Shipit.github` in `lib/shipit.rb`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is read from the raw, unverified JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), and is used only to pick *which* `GitHubApp`/`webhook_secret` config entry to HMAC-verify the whole request body against, via `Shipit.github(organization: repository_owner)` -> `Shipit.github_app_config(organization)` -> `GitHubApp#verify_webhook_signature` [3](#0-2) [4](#0-3) .

Once the signature check passes, `Handler#repository_name` — used by every concrete handler (push, status, check_suite, pull_request/*) to locate the `Stack`s/`Repository` to act on — reads a *different* field from the *same body*: [5](#0-4) 

For a genuine GitHub-generated webhook these two fields are always consistent (the org that owns the repo signs its own deliveries with its own secret, and `repository.full_name`'s prefix always equals `repository.owner.login`). But because Shipit lets an attacker submit an arbitrary raw POST body to a single shared endpoint, and only checks that *some* configured organization's secret matches the raw bytes, there is no requirement that `repository.owner.login` (the value used to select the verifying secret) matches the owner segment of `repository.full_name` (the value used to select the repository actually mutated).

The equality that should hold but doesn't: `organization authenticated by verify_signature (repository.owner.login / organization.login) == organization of repository written by the handler (repository.full_name)`.

### Impact Explanation
On a Shipit instance configured with multiple GitHub organizations (a documented, supported configuration — `docs/setup.md` lines 182-209, `lib/shipit.rb#github_app_config`), an attacker who is able to obtain or is entitled to know the `webhook_secret` for *their own* configured organization (e.g., they administer OrgTwo's GitHub App settings, which is a normal, low-privileged capability for that org's own webhook configuration and requires none of the excluded credentials — no `GITHUB_TOKEN`, no Shipit session, no `api_clients_secret`) can forge a signed request whose `repository.owner.login` is `OrgTwo` (so it authenticates under OrgTwo's secret) but whose `repository.full_name` is `OrgOne/some-repo`. This lets them inject arbitrary, apparently-legitimate GitHub events (push, status, check_suite, pull_request open/close/label) against stacks belonging to an org they have no relationship to, causing unauthorized side effects such as: queuing `GithubSyncJob`/deploy triggers for OrgOne's stacks, forging commit `status`/`check_run` results that can gate or unblock deploys, and opening/closing/archiving `ReviewStack`s for OrgOne's repositories. This crosses the "cross-repository writes" / "unauthorized deploy" boundary called out as Critical/High impact.

### Likelihood Explanation
Requires the instance to be configured with more than one GitHub organization (a documented Shipit feature, not a deviation from expected deployment), and requires the attacker to know/control one organization's `webhook_secret` — which is scoped to that org's own GitHub App and does not require any Shipit credential, `ApiClient` token, or privileged Shipit account. This is a realistic tenant-isolation break for any multi-org Shipit deployment.

### Recommendation
Bind the two identities together: after computing the verifying organization from `repository.owner.login`/`organization.login`, reject the request (422) unless every repository referenced in the payload (`repository.full_name`, and any handler-specific repository fields) belongs to that same organization. Alternatively, verify the signature against the app config chosen from the repository ultimately used by each handler, not a separately-read field, so the org whose secret validated the delivery is provably the org whose data is mutated.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an entity that knows/controls `OrgTwo`'s `webhook_secret` (its own GitHub App config), craft a `push` event JSON body:
   ```json
   { "repository": {"owner": {"login": "OrgTwo"}, "full_name": "OrgOne/target-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>", ... }
   ```
3. Sign the raw body with `OrgTwo`'s `webhook_secret` and send it as `X-Hub-Signature` to `POST /github/webhooks` (path per `config/routes.rb`) with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgTwo"`, fetches OrgTwo's `GitHubApp`, and the HMAC check passes since it was signed with OrgTwo's secret.
5. `PushHandler#process` (via `Handler#repository_name` reading `repository.full_name`) resolves `OrgOne/target-repo`'s stacks and enqueues sync/deploy-related jobs for that repository, even though the request was never authenticated by anything belonging to OrgOne.

```ruby
      config = secrets.github
    else
      config = github_app_config(organization)

    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
