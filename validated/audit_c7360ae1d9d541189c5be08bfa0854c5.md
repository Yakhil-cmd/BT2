### Title
Webhook signature verification binds to `repository.owner.login`, not to the repository actually acted upon by the event handlers - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to verify against using only the `repository_owner` field extracted from the untrusted payload, then dispatches the *entire* raw payload to event handlers that resolve the actual repository/stack from other payload fields (`repository.full_name`, `sha`, `ref`) that are never cross-checked against the organization whose secret validated the signature.

### Finding Description
`verify_signature` picks the `GitHubApp` instance (and thus the HMAC secret) to check with: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is read straight from the JSON body: [2](#0-1) 

Shipit supports multiple GitHub Apps, one per organization, each with an *independently configured* `webhook_secret` (`config/secrets.yml` → `github.<Org>.webhook_secret`), as documented and tested: [3](#0-2) [4](#0-3) 

After the signature check passes, `create` blindly hands the *whole* raw payload to every registered handler for the event type: [5](#0-4) 

Those handlers pull the repository/stack identity from unrelated payload fields, e.g. `PushHandler` resolves stacks via `ref`/`after` (the base `Handler#stacks` resolves the repository, presumably via `repository.full_name`), and `StatusHandler` matches commits purely by `sha`: [6](#0-5) [7](#0-6) 

Nothing in this chain re-derives `repository.owner.login`/`repository.full_name` after signature validation and asserts it equals the organization (`repository_owner`) whose secret validated the signature. The binding the system implicitly relies on — **organization authenticated == repository the handlers act on** — is never enforced as an equality check.

In a multi-organization Shipit deployment, an operator who legitimately controls one onboarded organization (e.g. `OrgTwo`, with its own known `webhook_secret`) can compute a valid `X-Hub-Signature` for an arbitrary JSON body using that secret, then POST directly to `/webhooks` with:
- `repository.owner.login` = `"OrgTwo"` (so `verify_signature` picks OrgTwo's app config and the signature checks out)
- `repository.full_name` / `sha` / `ref` referring to a stack belonging to a *different* organization (`OrgOne`) also hosted on the same Shipit instance.

Because `verify_signature` never re-validates that the owner used for signing matches the repository fields consumed by the handler, this forged event is accepted and processed as if it legitimately originated from `OrgOne`'s repository.

### Impact Explanation
This lets an attacker who only controls one tenant organization's webhook secret in a multi-org Shipit deployment forge GitHub events (`push`, `status`, `check_suite`, `membership`, etc.) targeting a completely different organization's stacks. Depending on the handler, this can trigger `GithubSyncJob` for an arbitrary `expected_head_sha` on a foreign repository/stack, inject fabricated commit statuses (`StatusHandler` → `Commit#create_status_from_github!`) that can unblock CI-gated deploys, or manipulate `check_suite`/PR label state used by the merge queue — a cross-tenant, cross-repository write and a path to an unauthorized deploy on a repository the attacker does not control, satisfying the Critical "cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration: `docs/setup.md` "Using Multiple Github Applications") and that the attacker legitimately controls the webhook secret for at least one of those organizations — no privileged Shipit account, `ApiClient` token, or access to any other org's secrets is needed. This is a realistic scenario for shared/multi-tenant Shipit deployments.

### Recommendation
After `verify_signature` selects `github_app` based on `repository_owner`, re-extract the repository/organization fields consumed by the dispatched handlers (`repository.full_name`, or per-event owner fields) and assert they match `repository_owner`/the selected `github_app`'s organization before calling `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Reject the event (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgOne` and `OrgTwo`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately administers `OrgTwo`'s GitHub App and therefore knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgTwo_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `create` dispatches the payload to `PushHandler`, which resolves stacks tied to `OrgOne/victim-repo` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a stack the attacker's organization (`OrgTwo`) never authenticated for.

Note: I could not directly inspect the base `Shipit::Webhooks::Handlers::Handler#stacks`/repository-resolution method within the tool budget to show the exact field it keys on; this should be confirmed, but the control-flow gap in `verify_signature` (organization-only binding, no cross-check against the fields handlers consume) is directly verified from the cited files.

```ruby
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
