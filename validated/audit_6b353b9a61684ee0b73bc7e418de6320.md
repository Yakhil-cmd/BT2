StatusHandler applies GitHub commit statuses to any commit sharing a SHA, ignoring the payload's own repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` never calls the base `Handler#stacks` scope, unlike every other handler subclass, and instead runs `Commit.where(sha: params.sha)` across the entire commits table. Because git commit SHAs are not unique per-repository (identical trees/history in a fork produce identical SHAs), an attacker who controls any repository tracked as a Shipit stack can trigger a genuine, correctly-signed `status` webhook for their own repository and have Shipit write a `Status` record onto a completely different stack's commit.

### Finding Description
The intended binding for every handler is: `payload['repository']['full_name']` (via `repository_name`) → `Repository.from_github_repo_name(repository_name).stacks` → the only records mutated by `process`. This is enforced in sibling handlers, e.g. `PushHandler#process` calls `stacks.not_archived.where(branch:)...` [1](#0-0) , and the `stacks` helper itself derives strictly from the payload's repository field [2](#0-1) .

`StatusHandler#process`, however, does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This query has no `stack_id`/`Repository` filter at all — it is a global lookup across every stack tracked by the Shipit instance. The `repository` field in the payload is parsed only implicitly for signature-org lookup in the controller, never for scoping the mutation.

The webhook controller's `verify_signature` only proves that the request was validly signed by *some* GitHub organization the Shipit instance trusts — the organization owning the repository named in the payload — it does not prove, and cannot prove, that the `sha` being reported belongs only to that repository:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
``` [4](#0-3) 

**Attacker path**: An attacker who owns/administers *any* repository that is tracked by the target Shipit instance as its own stack (e.g., they are a maintainer of some unrelated project also deployed via the same Shipit installation, or they fork a repository and get it registered as a stack) can:
1. Fork or otherwise reproduce a commit with a specific `sha` that also exists in a victim stack's commit history (trivial if they fork the victim's public repo unchanged, or push identical tree/parent/author/timestamp content).
2. Use the GitHub Statuses API on their own repository (using their own GitHub token, which they legitimately possess) to set a status on that SHA — this triggers a genuine GitHub `status` webhook, signed with the secret configured for their own organization.
3. Shipit's `verify_signature` passes (correctly, for their own org/repo).
4. `StatusHandler#process` runs `Commit.where(sha: ...)`, matches the identical SHA row belonging to the **victim's** stack, and calls `create_status_from_github!`, writing a new `Status` on the victim's commit purely because `Commit.sha` collided — the attacker's `repository` field is never checked.

`create_status_from_github!` → `add_status` can flip the commit's aggregated `status`/`simple_state`, trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` if the injected state is `success`/`pending` [5](#0-4) , which can unblock `deployable?` checks (`success? && !blocked?`) for the victim stack [6](#0-5) .

No existing guard prevents this: `verify_signature` only authenticates the sender's own org, `drop_unhandled_event` only checks the event name is registered, and `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.) — none of them tie `params.sha` to `repository_name`.

### Impact Explanation
**Critical.** A payload from one repository (fully controlled by an unprivileged attacker) mutates another stack's commit record — a `Status` row is created for a commit belonging to a repository the attacker never authenticated against. This can influence `Commit#deployable?`/`blocked?` and trigger `stack.schedule_merges`, i.e., forged CI status signals feeding into deploy/merge gating for a victim's stack. The attack is repeatable against any commit SHA collision the attacker can engineer (trivial via forking public repos unchanged) and is not bound to any specific victim — any Shipit-tracked stack whose commit history the attacker can reproduce is affected.

### Likelihood Explanation
Preconditions: the attacker needs write/admin access to at least one repository that is itself tracked as a Shipit stack on the target instance (so they can send a validly-signed webhook), and the ability to reproduce a commit SHA that also exists in the victim's tracked commit history (straightforward for public repos via an unmodified fork, since SHA is a pure function of tree/parents/author/committer/timestamps/message). No Shipit secrets, sessions, or API tokens are required — only a legitimate GitHub Statuses API call on a repo they own. This is a low-cost, fully repeatable, single-HTTP(S)-webhook attack.

### Recommendation
Scope `StatusHandler#process` through the same `stacks` mechanism as every other handler: resolve the repository from the payload, then restrict the `Commit` lookup to that repository's stacks, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or iterate `stacks.flat_map(&:commits).where(sha: ...)`), so a status webhook can only ever mutate commits belonging to the repository named in its own payload.
