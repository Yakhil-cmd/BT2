### Title
Malicious secondary AA can force the entire multi-AA response chain to revert, causing fund loss/freezing for the triggering user and any other legitimate recipients in the chain - (File: aa_composer.js)

### Summary
This is a valid analog of the reported bug class. In the original PoolTogether finding, a claimer processing multiple prize claims in a single transaction can have the whole batch reverted by a single malicious, always-reverting user hook, causing the claimer to lose gas and other honest winners to have their prizes withheld. In ocore's Autonomous Agent (AA) composer, the equivalent untrusted "hook" is a **secondary AA** that gets triggered when a primary AA's response sends an output to it. If that secondary AA (which can be defined permissionlessly by anyone) always bounces, the entire chain of AA responses stemming from the original trigger is rolled back, undoing all state changes and payments that the primary AA (and any other successfully-processed secondary AAs in the same chain) had already produced.

### Finding Description
When a primary AA trigger is handled in `handleTrigger` (`aa_composer.js`), after the AA sends its response messages, any output address that is itself an AA is treated as a secondary trigger via `handleSecondaryTriggers`: [1](#0-0) 

Each secondary AA is invoked with `bSecondary = true`. If a secondary AA's evaluation bounces (e.g., it calls `bounce()` unconditionally, or its logic is written/state is manipulated to always fail), `handleTrigger`'s `onDone` callback receives a `bounce_message`, which is forwarded as an error to `async.eachSeries`'s completion handler: [2](#0-1) 

Because `bSecondary` is false at the top level (the primary trigger context), this calls `revert(err)`, which rolls back the *entire* database transaction to the savepoint taken before any AA balances were touched, clears the in-progress `batch`, and forces the original primary trigger to bounce: [3](#0-2) 

The test `'chain of AAs'` in `test/aa_composer.test.js` demonstrates the intended "happy path" of this composition mechanism — a primary AA forwards funds to a secondary AA, and the secondary AA's response and state changes are only persisted if it does not bounce: [4](#0-3) 

Any address that a primary AA's business logic forwards funds to can become the target of a secondary trigger. Since AAs are permissionless to define (any user can post a `definition` message defining an "autonomous agent"), an attacker can pre-deploy an AA that always calls `bounce(...)` regardless of input, and get funds routed to it — either because it is a genuinely used integration point (e.g., a DEX/router AA that forwards received assets onward, or an AA whose recipient address is influenced by trigger data/parameters), or because the attacker crafts a trigger that causes the target AA to forward outputs to the attacker's reverting AA as a downstream step.

### Impact Explanation
When the attacker's secondary AA bounces, `revert()` unwinds the *entire* chain of AA responses for that primary trigger, not just the attacker's own leg:
- All state variable changes made by the primary AA (and any other, unrelated secondary AAs that had already succeeded earlier in the same `async.eachSeries` chain) are discarded.
- Any payments the primary AA intended to make to unrelated, honest third parties within the same response (e.g., a payout distributed to multiple addresses in one AA execution) are undone.
- The original trigger sender's payment is bounced back (minus bounce fees), so they lose the bounce fee for a transaction whose failure was entirely controlled by an unrelated third party's AA.

This is a fund-loss/freezing condition triggered by a single uncooperative, attacker-controlled component embedded in a composed AA transaction, mirroring the "malicious hook always reverts, causing legitimate batch participants to lose out" bug class from the referenced report.

### Likelihood Explanation
AA definitions are fully permissionless in ocore, so any user can deploy a "revert always" AA at negligible cost. The likelihood of triggering this depends on whether a legitimate AA's payment logic routes funds to an address that can be influenced by an attacker (directly as a fixed target chosen by protocol design for composability, or indirectly via trigger `data`/`params` controlling an output address) — this is a realistic and common pattern for composable AAs (e.g., AAs designed to interoperate with other AAs, routers, oracles, or user-designated forwarding addresses).

### Recommendation
Consider decoupling the failure of a downstream secondary AA from the finality of the primary AA's own response and other, already-successful secondary triggers in the same chain — e.g., allow the primary/ancestor AA's already-computed state changes and unrelated outputs to persist, and only fail (or refund) the specific leg of the chain that failed, similar to how the referenced fix recommends not reverting an entire batch just because one participant's hook fails. At minimum, this bounce-cascade behavior (that a single downstream secondary AA can undo an entire multi-AA composition) should be clearly documented so AA authors are aware that composing with untrusted or externally-controlled AA addresses can be weaponized to void their own successful side effects.

### Proof of Concept
Based on the existing `'chain of AAs'` test pattern in `test/aa_composer.test.js` (lines 156-252), the following variation demonstrates the issue:
1. Define `secondary_aa` such that its message body always calls `bounce("always fail")` regardless of trigger data.
2. Define `primary_aa` that, as part of a single response, both pays an unrelated third address `X` and forwards remaining funds to `secondary_aa`.
3. Trigger `primary_aa` with a normal payment.
4. Observe via `aa_composer.dryRunPrimaryAATrigger` (or a live trigger) that `arrResponses[0].bounced === true` for the primary AA — i.e., the payment intended for the unrelated address `X` never gets included in any response unit, and the primary AA's state var updates are discarded, even though computing them succeeded before the secondary AA's forced bounce.
