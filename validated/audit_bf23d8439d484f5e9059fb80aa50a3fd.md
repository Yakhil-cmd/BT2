## Analog Found: `nominate()` accepts non‑existent validator targets in `pallet-staking`

### Title
Nominating a non-existent validator silently succeeds in `pallet-staking::nominate()` - (File: `substrate/frame/staking/src/pallet/mod.rs`)

### Summary
The external report's root cause is a missing "is this target actually alive/registered" check before a permissionless action records weight against it, inflating on-chain accounting. The same class of defect exists in `substrate/frame/staking` (the classic, still-deployed `pallet-staking`): its `nominate()` extrinsic validates a nomination target only by checking `blocked`, never by checking that the target is actually a registered validator. This lets any signed nominator record approval stake toward a target account that never called `validate()`.

### Finding Description
In `nominate()`, targets are filtered with: [1](#0-0) 

```rust
let targets: BoundedVec<_, _> = targets
    .into_iter()
    .map(|t| T::Lookup::lookup(t).map_err(DispatchError::from))
    .map(|n| {
        n.and_then(|n| {
            if old.contains(&n) || !Validators::<T>::get(&n).blocked {
                Ok(n)
            } else {
                Err(Error::<T>::BadTarget.into())
            }
        })
    })
    .collect::<Result<Vec<_>, _>>()?
```

`Validators::<T>::get(&n)` on a `StorageMap` returns the type's `Default` when the key is absent. `ValidatorPrefs` derives `Default`, giving `blocked: false`: [2](#0-1) 

So for any account `n` that has **never called `validate()`** (i.e., is not a key in `Validators`), `!Validators::<T>::get(&n).blocked` evaluates to `!false == true`, and the target is accepted as valid — exactly mirroring the reported pattern of missing a "gauge is alive" check (`isGauge[_gauge]`/`isAlive[_gauge]`) before processing weight against an entity that should be excluded.

This is not a hypothetical edge case: the sister pallet `pallet-staking-async` had the identical bug and was explicitly patched, with the prdoc titled "Fix calling nominate on a validator that doesn't exist silently succeeds": [3](#0-2) 

The fixed version in `pallet-staking-async` adds the missing existence check: [4](#0-3) 

```rust
let targets: BoundedVec<_, _> = targets
    .into_iter()
    .map(|n| {
        if old.contains(&n) ||
            (Validators::<T>::contains_key(&n) && !Validators::<T>::get(&n).blocked)
        {
            Ok(n)
        } else {
            Err(Error::<T>::BadTarget.into())
        }
    })
```

`pallet-staking` (the non-async, still-live version used by Polkadot/Kusama/Westend/Rococo relay chains and referenced from `polkadot/runtime/westend/Cargo.toml` and `polkadot/runtime/rococo/Cargo.toml`) never received the equivalent fix — it still only checks `blocked`, not `contains_key`.

### Impact Explanation
A nominator can put a non-existent account into their `Nominations.targets`, which is stored and later iterated by the election data provider (`electing_voters`) and used to build voter/target snapshots for NPoS elections. This pollutes on-chain nomination data with phantom targets, analogous to the report's "incorrect deposit"/"inflated totalWeight" categories: bogus entries are recorded into `Nominators` storage and participate in vote-weight bookkeeping toward an account that is not, and may never become, an actual validator. This is a data-integrity/accounting defect in a core, permissionless staking extrinsic, matching the same bug class (Medium impact) already accepted and remediated in the sibling `pallet-staking-async` crate.

### Likelihood Explanation
Medium/High feasibility: `nominate()` is a normal signed extrinsic, requires no privileged role, and any bonded account meeting `MinNominatorBond` can call it with an arbitrary `AccountIdLookupOf<T>` target that has simply never called `validate()`. No governance, no stolen keys, no malicious peer — a pure, always-reachable user entry point.

### Recommendation
Mirror the fix already applied in `pallet-staking-async`: require `Validators::<T>::contains_key(&n)` in addition to the `blocked` check in `pallet-staking::nominate()`'s target-filtering closure at `substrate/frame/staking/src/pallet/mod.rs:1406-1420`, so that nominating a non-existent validator returns `Error::<T>::BadTarget` instead of silently succeeding.

### Proof of Concept
Using the existing `pallet-staking` mock test harness (`substrate/frame/staking/src/tests.rs`), the following demonstrates the failed guard (this mirrors the `nominating_non_validators_is_not_ok` test that exists for `pallet-staking-async` and correctly rejects the case there):

```rust
ExtBuilder::default().nominate(false).build_and_execute(|| {
    assert_ok!(Staking::bond(RuntimeOrigin::signed(1), 1000, RewardDestination::Stash));
    // 41 has never called `validate()` — it is not a key in `Validators`.
    // Because `Validators::get(41)` returns `ValidatorPrefs::default()` (blocked: false),
    // the check `!Validators::<T>::get(&n).blocked` is `true`, and the call succeeds
    // instead of returning `Error::<T>::BadTarget`.
    assert_ok!(Staking::nominate(RuntimeOrigin::signed(1), vec![41]));
});
```
In `pallet-staking-async`, the analogous call correctly fails with `Error::<T>::BadTarget` per the existing test `nominating_non_validators_is_not_ok`: [5](#0-4) 

I was not able to execute the Rust test suite in this environment (read-only code search tools only), so this PoC is presented as a minimal reproduction path through the real extrinsic boundary using the pre-existing test harness/mock runtime, not as an executed result. The claim rests on direct code comparison between the unpatched `pallet-staking::nominate()` guard and the patched `pallet-staking-async::nominate()` guard, plus the prdoc confirming this exact defect class was previously identified and fixed for the sibling pallet.
