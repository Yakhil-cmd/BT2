### Title
Unhandled exception leaves malformed private-payment chain permanently stuck / double-callback in `handleSavedPrivatePayments` - (File: network.js)

### Summary
CVE-2017-12463 leaks an `envelope_s` allocation in `ccnl_app_RX` because when the packet format is unrecognized, the function returns/branches without freeing the structure it already allocated. The analogous flaw in ocore is in `validateAndSave()` inside `handleSavedPrivatePayments()` in `network.js`: when a queued private-payment chain has a payload whose format causes `objectHash.getBase64Hash()` to throw, the `catch` block does cleanup (delete the row, send an error) but does **not** `return`, so execution falls through and re-enters the normal processing path with a corrupted `json_payload_hash` (`undefined`), invoking `privatePayment.validateAndSavePrivatePaymentChain(...)` a second time for the same queued item.

### Finding Description
`handleSavedPrivatePayments()` periodically (`setInterval(handleSavedPrivatePayments, 5*1000)`, see `network.js:4445`) reads all rows from `unhandled_private_payments` and processes each with `async.each`, i.e. in parallel, one `cb` expected per row: [1](#0-0) 

For each row, `validateAndSave` computes a `json_payload_hash` from the head element's payload and builds an event `key`, then calls `privatePayment.validateAndSavePrivatePaymentChain`: [2](#0-1) 

The bug: if `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (an attacker-controlled `payload` inside a posted private-payment chain can be crafted to make hashing fail, e.g. non-serializable/invalid structures), the `catch` block logs the error, optionally sends a result to the peer, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which issues a DB `DELETE` and invokes `cb()` on completion. Crucially, there is **no `return`** after this call:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
```
Execution continues past the `catch` block and calls `privatePayment.validateAndSavePrivatePaymentChain` on the same (still in-memory) `arrPrivateElements`, whose `ifOk`/`ifError`/`ifWaitingForChain` callbacks each also call `cb()`: [3](#0-2) 

This produces two independent completions for one `async.each` item: one from the `deleteHandledPrivateChain` DB callback and one from `validateAndSavePrivatePaymentChain`. In `async.each`, calling the item's callback more than once corrupts the completion counter, which can cause the wrapping `async.each` final callback (and therefore `unlock()` of the `["saved_private"]` mutex, see `network.js:2450-2521`) to fire prematurely/multiple times relative to outstanding work, or to never fire cleanly if other rows are still in flight when the counter is thrown off. Because `handleSavedPrivatePayments` is re-invoked every 5 seconds and also whenever a new unit-of-interest arrives (`findAndHandleJointsThatAreReady` → `handleSavedPrivatePayments(unit)`), any lingering rows that are not correctly deleted (or a `mutex.lockOrSkip(["saved_private"], ...)` call that repeatedly finds the resource still "locked") accumulate and are retried forever without making progress, mirroring the CVE's pattern of an object that is allocated/tracked but never properly released when the input format is invalid.

The root cause — “exceptional/invalid input format handled inline without returning, causing the normal allocation/processing path to run a second time on the same resource” — is structurally the same bug class as CVE-2017-12463's `envelope_s` leak in `ccnl_app_RX`.

### Impact Explanation
A private-payment counterparty (any peer/wallet that can send a private payment chain to another wallet or via a hub, reachable without special privileges — see `handleOnlinePrivatePayment` in `network.js:2375-2441`, which stores the same kind of malformed payload into `unhandled_private_payments` for reprocessing) can craft a payload whose `getBase64Hash` call throws. Because the periodic sweep (`setInterval(handleSavedPrivatePayments, 5*1000)`) reprocesses all pending rows, repeatedly sending such malformed chains causes: (1) duplicate execution of `validateAndSavePrivatePaymentChain` against DB records that may already be deleted mid-flight (a TOCTOU race on the same unit/message/output key), and (2) mutex/queue bookkeping corruption in the `["saved_private"]` lock via `async.each`'s double-`cb()` semantics, which can leave private-payment processing effectively stalled or continuously retried without completing, consuming server resources (memory/DB rows/timers) per malformed message. This is a resource-exhaustion / stuck-processing denial-of-service specific to the wallet/private-payment handling pipeline, reachable by an unprivileged private-payment counterparty, matching the "no impact / high severity DoS via unbounded resource growth from malformed input" pattern in the reported CVE.

### Likelihood Explanation
High: no special privileges are needed — any device that can send a private payment (`handlePrivatePaymentChains` in `wallet.js:955` or `handleOnlinePrivatePayment`/`handleSavedPrivatePayments` in `network.js`) can supply a payload engineered to make `objectHash.getBase64Hash` throw (e.g. structures known to break canonical JSON hashing, such as those containing invalid UTF-16 surrogates or unsupported types). Triggering the periodic sweep only requires waiting up to 5 seconds after the record lands in `unhandled_private_payments`.

### Recommendation
Add a `return` statement immediately after the error handling in the `catch` block of `validateAndSave` (network.js), so that when `getBase64Hash` fails, the function does not fall through into computing `key` and calling `privatePayment.validateAndSavePrivatePaymentChain` a second time:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
Additionally, audit other `async.each`/`async.eachSeries` callback sites in `network.js` for similar "handle error, but no early return" patterns, and consider making `deleteHandledPrivateChain` idempotent/safe against being invoked concurrently with `validateAndSavePrivatePaymentChain` on the same row key.

### Proof of Concept
1. As a paired device or private-payment counterparty, send a `private_payment` (via `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`) whose head element's `payload` is crafted so that `objectHash.getBase64Hash(payload, true)` throws (e.g., a payload containing a value that fails JSON canonicalization/serialization used internally by `getBase64Hash`).
2. The chain is queued into `unhandled_private_payments` (`savePrivatePayment` in `handleOnlinePrivatePayment`, network.js:2390-2401).
3. Within 5 seconds, `handleSavedPrivatePayments()` (network.js:2444) picks up the row and calls `validateAndSave()`.
4. `getBase64Hash` throws; the `catch` block deletes the row and calls `cb()`, but execution continues to also call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which calls `cb()` again for the same `async.each` item — observable via duplicated log lines / duplicated `sendResult` calls / duplicated event emissions for the same `row.unit`.
5. Repeating this with many malformed chains observably corrupts the completion bookkeeping of the `["saved_private"]` mutex-guarded sweep, stalling legitimate private-payment processing. [4](#0-3)
