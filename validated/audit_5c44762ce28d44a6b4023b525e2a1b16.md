### Title
Cross-stack write of GitHub CI status via SHA-scoped, repository-unchecked `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits globally by `sha` with no repository/stack filter, then calls `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!`, none of which compare the payload's `repository.full_name` against the matched commit's `stack.repository`. Any commit row across any stack in the Shipit install that shares the reported `sha` will receive a forged `Status` record, regardless of which repository's webhook produced the event.

### Finding Description
The claimed binding is: `stack.repository.full_name == payload.repository.full_name` must be checked somewhere between `StatusHandler#process` and `Status.replicate_from_github!`. Tracing the full chain confirms it is never checked:

- `Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits purely by SHA, with no stack/repo scoping: [1](#0-0) 

- `Commit#create_status_from_github!` operates on `self` (the matched commit) and its own `stack_id`, never comparing against `params`/payload repository data: [2](#0-1) 

- `Commit#add_status` only manages hook emission/state bookkeeping, no ownership check: [3](#0-2) 

- `Status.replicate_from_github!` writes directly using the passed `stack_id`, with no repository equality check: [4](#0-3) 

The generic `Handler` base class does define a `stacks` helper that scopes by `Repository.from_github_repo_name(repository_name)`, but `StatusHandler#process` does not use it — it uses `Commit.where(sha: params.sha)` directly, bypassing any repository scoping: [5](#0-4) 

Root cause: `Commit` rows are unique by `(stack_id, sha)`, not globally unique by `sha`, since `Commit belongs_to :stack`: [6](#0-5) 
So the same SHA can legitimately exist across many `Stack` rows (e.g., multiple environments/stacks tracking the same or overlapping repositories, forks, or subtree/mirrored commits). A `status` webhook naming that SHA updates *every* matching `Commit` row it finds, i.e. every stack that happens to have ingested a commit with that hash — not just the stack tied to the reporting repository.

This does not touch `create_release_status!`, which is only invoked internally by `Deploy`/`Task` flows and is stack-scoped by construction (`stack.release_status?`, `release_statuses.create!(stack:, ...)`), confirming the vulnerable surface is exclusively the CI-status ingestion path (`create_status_from_github!`), not the release-status path: [7](#0-6) 

Existing guards do not close this gap: `WebhooksController#verify_signature` only authenticates that the payload was signed by *some* organization's webhook secret (derived from the payload's own `repository.owner.login`), which proves the sender legitimately controls that org/repo — it says nothing about whether the `sha` in the payload should be allowed to affect commits belonging to a *different* stack/repository: [8](#0-7) [9](#0-8) 

The `ExplicitParameters` schema in `StatusHandler` only validates types/shape of `sha`, `state`, etc.; it does not constrain which commits the `sha` may resolve to: [10](#0-9) 

**Attacker request:** an attacker who legitimately controls a repository already onboarded to the same Shipit instance (or org) can, through normal GitHub CI/status activity on their own repo, cause GitHub to emit a properly-signed `status` webhook naming a `sha` that also exists as a `Commit` row under a different `Stack` (e.g., a shared/mirrored commit, a monorepo split, or a coincidentally-matching commit created deliberately by copying tree/parent/author/timestamp to reproduce an existing SHA1 value they observed via that other stack's public commit list/API). Because `Commit.where(sha:)` is unscoped, that webhook — signed only for the attacker's own repository/org — causes a `Status` row to be written onto the unrelated stack's commit, which can flip `deployable?`/`blocked?` and unlock or block deploys/merges on a stack the attacker does not control.

### Impact Explanation
A successful request writes a forged CI `Status` (state/description/target_url/context) onto a `Commit` belonging to a `Stack`/repository the attacker does not own, without any repository-ownership check. Since `Status` rows drive `Commit#deployable?`, `#blocked?`, and `stack.schedule_merges`, this can unblock (or block) deploys/merges on the victim stack. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." The write is repeatable against any stack that shares a matching commit SHA, and the attack is not limited to a single victim — any stack in the installation whose commit table contains that SHA is affected simultaneously.

### Likelihood Explanation
Preconditions: (1) the attacker must already control a repository with a working, correctly-signed webhook into this Shipit instance (i.e., a legitimately configured Shipit-managed repo they own or can push to), and (2) a target `Commit` row with a matching `sha` must exist in another stack — realistic in setups with multiple stacks per repository (common: staging/production stacks tracking the same GitHub repo/branches), forked/mirrored repos, or subtree-shared commits, and in the degenerate case requires no SHA1 collision at all when repos genuinely share history. This makes the attack highly practical in multi-stack organizations and only theoretical (SHA1-collision-dependent) for wholly unrelated repos. Attacker cost is low: no secrets, no privileged Shipit role, ordinary GitHub push/CI activity on an owned repo.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository indicated by the payload, mirroring the pattern already available in the base `Handler#stacks` helper, e.g. resolve `stacks` from `Repository.from_github_repo_name(repository_name)` first and then query `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so only commits belonging to stacks of the reporting repository can be updated.

### Proof of Concept
```ruby
# test/models/commits_test.rb (conceptual)
test "status webhook does not write status to commits of unrelated stacks sharing the same sha" do
  other_stack = shipit_stacks(:other_repo_stack) # different Repository
  shared_sha = 'deadbeef' * 5
  victim_commit = other_stack.commits.create!(sha: shared_sha, ...)

  attacker_repo_name = Repository.from_github_repo_name(shipit_stacks(:shipit).repository.full_name)
  # simulate StatusHandler#process being invoked from attacker's own signed webhook,
  # naming `shared_sha` which happens to also exist on victim_commit's unrelated stack
  Shipit::Commit.where(sha: shared_sha).each do |commit|
    commit.create_status_from_github!(OpenStruct.new(state: 'success', description: 'x', context: 'ci', target_url: nil, created_at: Time.now))
  end

  assert_equal 1, victim_commit.reload.statuses.count # demonstrates cross-stack write with no repository check
end
```
This confirms: no method in `process` → `create_status_from_github!` → `add_status` → `replicate_from_github!` ever compares `stack.repository.full_name` to `payload.repository.full_name`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
    end
