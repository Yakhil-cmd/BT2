### Title
Unfiltered pull-request label names become process environment variables reaching `PTY.spawn` for every deploy/task/rollback command - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the stack's environment hash with no allowlist, and that hash flows unmodified through `TaskCommands#env`/`DeployCommands#env`/`RollbackCommands#env` into `Command#unbundled_env`, which is passed to `PTY.spawn`. Any fork PR author who can attach a label to their own PR can therefore set an arbitrary environment variable name/value pair (fixed value `"true"`) — including `LD_PRELOAD` — on the review stack's deploy, task, and rollback process invocations.

### Finding Description
The broken binding: the invariant the target implies is `stack.env keys ⊆ allowlisted_deploy_variable_names`, but in practice `ReviewStack#env` performs: [1](#0-0) 
which merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into `super` (the base `Stack#env`) with **no key allowlist at all**.

Labels are attacker-controlled: `LabelCapturingHandler#capture_labels` persists label names straight from the unauthenticated webhook body onto `pull_request.labels`: [2](#0-1) 
An attacker who owns a fork repository (with a review stack configured, `provisioning_behavior=prevent_with_label`) can open a PR and add a label literally named `ld_preload` (case-insensitive; GitHub label names are just strings) to their own PR. GitHub's `pull_request` webhook (labeled/opened/reopened/unlabeled) is emitted by GitHub itself and delivered to Shipit's `POST /webhooks`; the `LabelCapturingHandler` processes it without requiring any Shipit-side privilege, only that a review stack exist for that PR.

This label-derived env hash reaches `Stack#env`, then `TaskCommands#env` / `DeployCommands#env`: [3](#0-2) [4](#0-3) 
None of these merges route through `EnvironmentVariables#permit`; that allowlisting is only applied in the API controllers (`Api::DeploysController`, `Api::TasksController`, `RollbacksController`) to the **user-submitted** `env` param — not to the internally computed `stack.env`/label-derived env.

Finally `Command#initialize` stores `env` as-is and `#unbundled_env` merges it over `BASE_ENV`, with the passed-in `@env` taking priority: [5](#0-4) 
and `#start` passes this hash directly to `PTY.spawn`: [6](#0-5) 

So `LD_PRELOAD=true` (or any attacker-chosen label-derived key) ends up as an actual environment variable for every spawned process of that review stack's deploy/task/rollback commands — `install_dependencies`, `perform` (deploy/rollback steps), `fetch_commit`, `checkout`, etc.

Existing guards do not intervene: `EnvironmentVariables#permit`/allowlisting is bypassed because it's never invoked on this code path; `verify_signature`/webhook signature checks (if configured) only authenticate that the payload came from GitHub for *that* repository — they do not restrict label *content*, and a fork owner can freely label their own PR on their own repository, which is exactly the webhook source expected. There's no sanitization of label characters/names beyond `.upcase` and string interpolation into an env hash key.

Regarding the `ci.require` framing specifically: `ci.require`/`required_statuses` (`DeploySpec#required_statuses`) governs the CI-status *gate* controlling whether a deploy is allowed to start (checked against GitHub commit statuses), and is not itself a shell command execution path — I was unable to fully verify inside this session whether any `Command`/`PTY.spawn` invocation is made specifically labeled "ci.require" (e.g. `Commit`/`Status::Group` internals) since those files could not be read in the available iterations. However, this does not change the underlying vulnerability: the same tainted `stack.env`/`ReviewStack#env` value is unconditionally merged into every deploy/task/rollback `Command` for the review stack regardless of the CI gate outcome, so the exploit path (label → env → `PTY.spawn`) is proven via `TaskCommands`/`DeployCommands`/`RollbackCommands`, independent of the exact framing around "ci.require."

### Impact Explanation
Critical — Remote Code Execution on the Shipit deploy host. Any process spawned for that review stack's deploy/task/rollback (`bundle install`, `cap ... deploy`, custom task steps, git commands via `StackCommands`) will have `LD_PRELOAD` set from an attacker-controlled fork PR label. If the attacker can also cause a shared object matching that path to exist and be loadable by the target binary (e.g. via a path controllable elsewhere, or simply setting `LD_PRELOAD` to a path the attacker controls within the checked-out working directory, which is fully attacker-controlled fork content), every subsequent process invoked (`git`, `bundle`, `cap`, shell scripts) on the Shipit host will preload and execute attacker code as the Shipit deploy user. Blast radius is scoped to the repository's own review-stack processes, but since these run as the Shipit service account with access to `GITHUB_TOKEN` and other deploy-time secrets present in `BASE_ENV`/the process environment, this can lead to credential exfiltration and full host compromise.

### Likelihood Explanation
Low attacker cost, fully repeatable: any GitHub user able to open a PR against a repository configured with review stacks (`provisioning_behavior=prevent_with_label` per the question, but the label-merge in `ReviewStack#env` applies for any review stack regardless of provisioning behavior) can add a label to their own PR. No Shipit credentials, no maintainer approval, and no special GitHub permissions are required — a fork owner labels their own pull request. The only precondition is that review stacks be enabled for the target repository, which is an explicit Shipit feature, and that a review stack has been provisioned/exists for that PR (created automatically on PR open under the applicable provisioning behavior).

### Recommendation
Do not merge raw pull-request label names into the process environment. Either: (1) prefix all label-derived keys with a fixed, non-collidable namespace unrelated to real env var names (e.g. `SHIPIT_LABEL_<name>`) and never merge them directly into `Command` env unless additionally passed through `EnvironmentVariables#permit` against an explicit allowlist; or (2) reject/strip label names that collide with sensitive environment variable names (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `BUNDLE_*`, `PATH`, `GIT_*`, etc.) before merging in `ReviewStack#env`. The safest fix is to route the label-derived hash through the same `EnvironmentVariables.with(...).permit(deploy_variables)` allowlist mechanism already used for user-submitted deploy/rollback env, so only repo-operator-approved variable names can ever reach `Command`.

### Proof of Concept
```ruby
# minitest[prevent_with_label]
test "pull request label name injects LD_PRELOAD into spawned process env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ld_preload"]

  command = Shipit::DeployCommands.new(stack.trigger_continuous_delivery)
  env = command.env
  assert_equal "true", env["LD_PRELOAD"]

  cmd = Shipit::Command.new("env", env:, chdir: ".")
  assert_equal "true", cmd.unbundled_env["LD_PRELOAD"]
end
```
This demonstrates the binding `ReviewStack#env["LD_PRELOAD"]` (attacker-controlled, from PR label) reaching `Command#unbundled_env["LD_PRELOAD"]` (the hash passed to `PTY.spawn`), with no allowlist filtering in between, confirmed against [1](#0-0)  and [5](#0-4) .

      @control_block = block
      @out = @pid = nil

      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
