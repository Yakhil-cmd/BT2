### Title
Cross-organization webhook forgery via mismatched signature-selection field vs. repository-write field - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
In multi-organization Shipit deployments (`Shipit.github_organizations` returning multiple orgs, i.e. `secrets.github` keyed by organization), the webhook signature check selects which organization's `webhook_secret` to verify against using `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while the handler that actually mutates data locates the target `Repository`/`Stack` using a *different* payload field, `params.dig('repository', 'full_name')`. These two fields are independent, attacker-controlled JSON values in the same unsigned-until-verified request body, and the code never asserts that the owner portion of `full_name` matches `repository.owner.login`.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to verify the HMAC against solely from `repository_owner`: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` locates the target repository/stacks using a completely different field, `repository.full_name`: [3](#0-2) 

`Repository.from_github_repo_name` then splits that string into owner/name and looks up the DB record directly, with no relation back to `repository.owner.login`: [4](#0-3) 

`Shipit.github(organization:)` supports a per-organization secret map for multi-tenant configuration, exactly the shape needed for this cross-org mismatch: [5](#0-4) 

Binding that should hold: `organization used to select/verify webhook_secret == owner of the repository that is actually written to`. The code instead only enforces `repository.owner.login (or organization.login) == key used to pick webhook_secret`, and separately `repository.full_name == repository/stack acted upon`, with **no cross-check between the two fields**. An attacker who legitimately administers *any* organization/GitHub App configured in the same multi-tenant Shipit instance (and therefore knows/controls that org's `webhook_secret`, e.g. by owning that org's GitHub App settings) can:
1. Craft a JSON body where `repository.owner.login` = `attacker-org` (their own, legitimately configured org) but `repository.full_name` = `victim-org/victim-repo` (a Stack belonging to a different tenant on the same Shipit instance).
2. Sign the raw body with `attacker-org`'s own `webhook_secret` using standard `X-Hub-Signature`.
3. POST to `/webhooks`. `verify_signature` picks `Shipit.github(organization: 'attacker-org')`, verifies successfully (it's the attacker's own valid secret over the exact bytes they crafted), and the request proceeds.
4. `PushHandler`/`CheckSuiteHandler`/`StatusHandler` etc. resolve `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')`, triggering `stack.sync_github(expected_head_sha: ...)`, `schedule_refresh_check_runs!`, or `commit.create_status_from_github!` against the victim's stack — actions the attacker has no authorization to trigger.

### Impact Explanation
This crosses a tenant/repository trust boundary: an actor authorized only for one organization's webhooks can trigger deploy-relevant side effects (forced sync to an attacker-chosen `expected_head_sha`, check-run refresh, commit status injection) on another organization's `Stack` that they do not own or have GitHub write access to. This matches the "cross-repository writes" / unauthorized deploy-adjacent action category, since `PushHandler#process` drives `stack.sync_github(expected_head_sha: params.after)` — an attacker-supplied SHA — against a repository they don't control.

### Likelihood Explanation
Exploitability strictly requires the deployment to run Shipit's multi-organization webhook configuration (`secrets.github` keyed by multiple organizations) and for the attacker to be a legitimate operator/owner of at least one of those configured organizations (i.e., they know or can set that org's `webhook_secret`). This is not the common single-organization default (`github_default_organization` returns `nil` and a single shared secret is used for all repos, in which case there is no cross-org secret to abuse). I was not able to fully verify how common the multi-org configuration is in practice, or whether host applications commonly restrict which organizations may be configured together, since that is deployment-specific and outside the indexed engine code. Given the explicit multi-org support in `lib/shipit.rb` (`github_organizations`, `github_app_config`), this is a real, reachable code path in-repo, but its practical likelihood depends on tenant configuration choices made by the operator, not by this engine's own defaults.

### Recommendation
In `Handler#repository_name`/`#stacks`, cross-validate that the resolved repository's owner matches the organization whose secret was used to verify the webhook signature (thread the verified `repository_owner`/organization through to the handler and assert equality with `Repository#owner` before acting), or scope `Repository.from_github_repo_name` lookups to the verified organization instead of trusting the independent `full_name` field unconditionally.

### Proof of Concept
Given a multi-org Shipit config with orgs `attacker-org` (secret known to attacker) and `victim-org` (has Stack `victim-org/victim-repo`):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of raw body using attacker-org's webhook_secret>

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` picks `Shipit.github(organization: 'attacker-org')` [1](#0-0)  and accepts the signature (attacker's own valid secret over this exact body). `PushHandler#process` then resolves `stacks` via `repository_name = payload.dig('repository','full_name')` = `"victim-org/victim-repo"` [6](#0-5)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack using the attacker's forged `after` SHA [7](#0-6) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
