Based on my investigation, the "already issued" check in `aa_composer.js` for AA-issued capped assets does not filter by `sequence` or `main_chain_index`/stability, unlike essentially every other spend/issue-related query in the codebase (which consistently filter on `sequence='good'` and stability). This is a genuine, concrete deviation from the codebase's own conventions and maps to a freezing/denial-of-issuance class of bug — reachable simply by a trigger sender causing the AA's issuing response to end up in a losing/non-good sequence branch (a normal DAG race, not requiring any special privilege).

### Title
Permanent freezing of AA-issued capped-asset issuance due to unfiltered "already issued" check - (File: aa_composer.js)

### Summary
When an Autonomous Agent (AA) issues a capped asset, `aa_composer.js`'s `issueAsset()` guards against re-issuing the capped supply by checking whether any `issue` input already exists for that asset. Unlike every other double-issue/double-spend check in the codebase, this query does not filter by `sequence='good'` or unit stability, so a single non-good (temp-bad/final-bad) AA response unit that contains the issue input permanently blocks any future legitimate issuance of that asset.

### Finding Description
In `aa_composer.js`, `issueAsset()` handles issuance for AA-defined assets: [1](#0-0) 
```
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
```
This query only filters on `type='issue' AND asset=?`. It does not join on `units` and check `sequence='good'` and stability, unlike the analogous double-spend/double-issue detection paths in `validation.js` used for ordinary payments, e.g. `checkForDoublespends`, which explicitly treats `final-bad`/non-good units as non-existent competitors: [2](#0-1) 
```
else
    doubleSpendWhere += " AND asset IS NULL";
// final-bad units are treated as non-existent competitors (their inputs.is_unique is kept NULL)
var doubleSpendQuery = "SELECT "+doubleSpendFields+" FROM inputs " + doubleSpendIndexMySQL + " JOIN units USING(unit) WHERE "+doubleSpendWhere+" AND sequence!='final-bad'";
```
For a capped asset, only one `issue` input can ever legitimately exist (enforced by `serial_number` uniqueness and cap equality checks in `validation.js`): [3](#0-2) 
```
if (!objAsset || objAsset.cap){
    if (input.serial_number !== 1)
        return cb("for capped asset serial_number must be 1");
}
```
If the AA response unit that carries the `issue` input for the capped asset ever ends up on a losing/non-good sequence (e.g., due to a DAG-level conflict/race unrelated to the asset itself — any of the AA response's other inputs colliding with a competing branch, causing the whole unit including its `issue` input to become `temp-bad`/`final-bad`), the `inputs` row for that issue persists in the DB regardless of the unit's final sequence status. Because the `issueAsset()` check ignores sequence, any subsequent legitimate attempt by the AA to issue the same capped asset (e.g., retried by a new trigger after the AA notices it never got the asset issued because the response bounced/was nonserial from the invoker's perspective) will be rejected with `'already issued'` forever, since the row is never cleaned up and the check has no stability/sequence awareness.

The comment `// only our AA can issue, no unstable consensus-breaking issues possible` reflects an assumption that doesn't cover this case: it is not about a third party issuing the asset, but about the AA's own past attempt leaving a "ghost" issue record from a branch that ultimately lost consensus.

### Impact Explanation
This causes a capped asset defined and meant to be issued by an AA to become permanently un-issuable if the specific response unit carrying the issue attempt ends up nonserial/final-bad. Since capped-asset issuance is a one-time, irreversible action gated by this exact check, the AA (and by extension, any user/business logic relying on that asset, e.g., tokenized shares, market-maker AA pools, fundraising AAs shown in the `test/samples/*.oscript` samples) permanently loses the ability to mint the intended supply. This is a fund/functionality-freezing bug for the AA and any downstream users depending on that asset's issuance — a concrete, permanent freezing condition, not merely a transient error.

### Likelihood Explanation
Reachable by any unprivileged unit poster/trigger sender: causing another unrelated input of the same AA-response unit to lose a double-spend race (a routine occurrence in a DAG ledger under concurrent/competing branches) is sufficient to place the issue-carrying unit into a non-good sequence while its `inputs` row remains present. No special permissions, hub/peer compromise, or protocol-level attack is required — only ordinary conflicting-unit posting behavior that the network already handles for every other spend, just not accounted for in this specific check.

### Recommendation
Update the "already issued" check in `issueAsset()` (`aa_composer.js`) to join `inputs` with `units` and only treat issue rows from `sequence='good'` (and, if applicable, sufficiently stable) units as "already issued," mirroring the pattern used in `checkForDoublespends` in `validation.js`. This prevents a stale/losing issue record from permanently blocking future legitimate issuance of the capped asset.

### Proof of Concept
1. Deploy an AA that, on a triggering condition, defines a capped asset and issues it in the same or a later response (as in `test/aa_composer.test.js`'s "issue recently defined asset" test, lines 450-554, and `divisible_asset.js`/`validation.js` cap semantics).
2. Craft a scenario where the AA response unit that contains the `issue` input also has another input/output that ends up in a losing double-spend branch relative to a competing unit (e.g., by racing two triggers that cause the AA to spend the same underlying base-asset output/change in two candidate response units on parallel DAG branches). One of these AA response units becomes `sequence != 'good'` upon stabilization, while its `inputs` row for `type='issue'` remains in the `inputs` table (rows are not deleted for non-good units, only inputs' `is_unique` flag may be nulled for the spent side).
3. Send a new trigger intended to have the AA (re)issue the capped asset (since, from the invoker's point of view, the asset was never actually delivered because the carrying unit was rejected/nonserial).
4. Observe that `issueAsset()`'s query `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` finds the stale row from the non-good unit and returns `'already issued'`, permanently preventing any future issuance of the capped asset by the AA — even though the asset's supply was never actually put into circulation.
