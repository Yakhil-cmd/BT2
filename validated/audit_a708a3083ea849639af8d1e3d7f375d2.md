### Title
Unvalidated private-payment element structure causes uncaught TypeError (NULL/undefined dereference) and node crash - (File: network.js)

### Summary
The CVE analog (NULL pointer dereference on malformed guest commands causing a crash) maps to `network.handleOnlinePrivatePayment` in `network.js`, which dereferences `arrPrivateElements[0].payload.denomination` without verifying that the first private-payment element actually has a `payload` field. A private-payment counterparty (a wallet peer sending you a `private_payment` message, e.g. as the other side of a payment/exchange) fully controls the JSON content of `arrPrivateElements`.

### Finding Description
`handleOnlinePrivatePayment` only validates that `arrPrivateElements` is a non-empty array before touching its first element's nested fields: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

If the sender supplies `arrPrivateElements[0]` as an object without a `payload` field (e.g. `[{}]` or `[{"unit":"x"}]`), `arrPrivateElements[0].payload` is `undefined`, and `.denomination` on `undefined` throws a synchronous `TypeError`. This happens before any of the deeper structural checks that exist later in `private_payment.js` (`validateAndSavePrivatePaymentChain`), which do check `headElement.payload` — but those checks are never reached because the crash happens earlier, in `network.js`.

This function is invoked synchronously from the private-payment message handling path used both for peer-to-peer forwarding and hub-routed messages (`wallet.js` calls into `network.handleOnlinePrivatePayment` for chains received from a device/counterparty). There is no `try/catch` around this call in the relevant call chain, so the exception propagates as an uncaught exception.

The node process explicitly treats any uncaught exception as fatal and deliberately re-throws to crash the process: [2](#0-1) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

This is the direct behavioral analog of the virglrenderer NULL-pointer-dereference DoS: a single malformed message from an otherwise-unprivileged counterparty causes an unhandled dereference that crashes the whole process.

### Impact Explanation
Any wallet that engages in a private-asset transaction (private/indivisible or divisible asset payment) can act as the "private-payment counterparty" and deliberately send a malformed private-payment element missing the `payload` field. Because the crash happens in the main `network.js` message-handling logic (not in an isolated per-connection sandbox) and the process is intentionally torn down on uncaught exceptions, this crashes the entire node — a full denial of service that prevents the node from confirming new units until manually restarted. Unlike a normal validation rejection (`ifError`), this is a hard crash, matching "network unable to confirm new units" impact criteria.

### Likelihood Explanation
High. No privileged access, no need to be a hub, no cryptographic signatures need to be forged, and no prior relationship beyond being a normal private-payment counterparty is required. The only requirement is sending a `private_payment` (or equivalent direct message) with a first element lacking a `payload` property. This bypasses all of the deeper structural checks in `private_payment.js`/`divisible_asset.js`/`indivisible_asset.js` because the crash occurs earlier in `network.js`, before those safer, better-guarded validators are ever invoked.

### Recommendation
Add an explicit structural check at the top of `handleOnlinePrivatePayment` (and any other private-payment entry points) verifying `ValidationUtils.isNonemptyObject(arrPrivateElements[0])` and `ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload)` before accessing `.payload.denomination`, returning `callbacks.ifError(...)` on failure instead of throwing. More generally, wrap the private-payment message-handling dispatch in a `try/catch` that converts unexpected exceptions into a validation error response rather than letting them propagate to the global uncaught-exception handler.

### Proof of Concept
1. As a wallet acting as counterparty in a private-asset payment (or via a hub relaying such a message), construct a `private_payment` message whose content is:
```json
[ { "unit": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=", "message_index": 0 } ]
```
i.e., omit the `payload` field entirely from the head element.
2. Send this to the target node via the normal private-payment channel used between wallets/hub (the path that invokes `network.handleOnlinePrivatePayment`).
3. `arrPrivateElements[0].payload` is `undefined`; the expression `arrPrivateElements[0].payload.denomination` throws a `TypeError`.
4. The exception is uncaught, triggers the `process.on('uncaughtException')` handler in `network.js`, which logs and re-throws, crashing the node process.

**Note on verification limits:** I was not able to fully trace, within the available search iterations, the exact synchronous call path from the raw incoming WebSocket message dispatcher through `wallet.js` into `network.handleOnlinePrivatePayment` to confirm there is no intermediate `try/catch` wrapper that would convert the exception into a normal error response. This should be verified directly in the full `wallet.js` and `network.js` message-routing code (`onWebsocketMessage`/`handleMessage`-style dispatch) before treating this as fully confirmed.
