### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook only against the GitHub App/organization derived from the payload's `repository.owner.login`, but `Webhooks::Handlers::StatusHandler#process` applies the status update to **every** `Commit` row across the entire Shipit instance whose `sha` matches, with no check that the commit's `stack`/`repository` actually matches the `repository` that was authenticated in the payload.

### Finding Description
The webhook is authenticated per-organization: `WebhooksController#verify_signature` picks the app/secret via `repository_owner`, computed as `params.dig('repository', 'owner', 'login')`, and calls `github_app.verify_webhook_signature`. [1](#0-0) [2](#0-1) 

Once verified, the raw payload is dispatched to handlers registered for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

For `status` events, `Handlers::StatusHandler#process` looks up commits **solely by SHA**, with no scoping to the `repository.full_name` that was present in — and used to select the signing key for — the same payload:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

Contrast this with `PushHandler`, which correctly scopes to `Repository.from_github_repo_name(repository_name)` via the base `Handler#stacks` helper before acting: [5](#0-4) [6](#0-5) 

`Commit` rows are not deduplicated globally by SHA — the `sha` column has no uniqueness constraint tying it to one repository; each `Commit belongs_to :stack`, and `Shipit` can host many `Stack`/`Repository` records across different GitHub organizations/repos, each potentially with the same commit SHA (forks, shared history, cherry-picked/rebased branches, mirrored repos, monorepo shared history, or even coincidental collision in test/staging setups). `Commit.create_status_from_github!` performs the write with no repository-ownership re-check at write time: [7](#0-6) 

**Equality that is broken**: the engine implicitly assumes
`organization authenticated by verify_signature (via repository.owner.login) == repository whose Commit rows are mutated (via Commit.where(sha:))`
but the handler never checks this; it substitutes a global, unscoped SHA lookup for the repository-bound identity that was actually authenticated. An organization/App admin who legitimately controls a configured GitHub App installation for **Org A** (and therefore possesses that Org's real, GitHub-issued webhook secret — a normal artifact of setting up that org's integration, not a stolen credential) can cause GitHub to emit (or self-construct and correctly sign, since they hold Org A's `webhook_secret`) a `status` event whose `sha` field is set to a commit SHA that also exists as a `Commit` row under a stack for a completely different, unrelated **Org B/repository** configured in the same Shipit instance. Because `StatusHandler` never re-validates that the SHA belongs to a commit under the repository that was actually authenticated, the forged status is applied to Org B's commit, affecting Org B's CI/deploy gating (`Commit#deployable?`, `Commit#blocked?`, `stack.schedule_merges`) without Org B's authorization.

### Impact Explanation
Forged commit statuses feed directly into deploy/merge decision logic: `Commit#status`, `Commit#deployable?`, `#blocked?`, and `add_status` trigger `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)`. [8](#0-7) [9](#0-8) 
An attacker able to mark a commit `success` on a repository/stack they do not own can help push through an unauthorized deploy/merge of that commit on Org B's stack (bypassing the CI gate that `shipit.yml`/status checks are meant to enforce), which the scope explicitly recognizes as a critical impact ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment (`config/secrets.yml` with multiple GitHub orgs, as documented in `docs/setup.md`) where the attacker's own organization is one of the configured tenants — this is a supported, first-class configuration pattern (`test/dummy/config/secrets_double_github_app.yml`), not a privilege escalation; and (2) a SHA collision/reuse between the attacker's repository and the victim repository, which is realistic in fork-based workflows, shared submodules/monorepos, or repository migrations that Shipit is commonly used with. The attacker needs no access to Org B's webhook secret, GitHub token, or repository — only legitimate, ordinary control of their own tenant's already-configured GitHub App.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository identified in the same payload (via the `Handler#stacks` helper, consistent with `PushHandler`), e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This re-establishes the equality between the organization/repository that was cryptographically authenticated and the repository whose data is mutated.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `OrgA` and `OrgB`, each with its own GitHub App/`webhook_secret` (supported multi-org config, e.g. mirroring `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately administers `OrgA`'s GitHub App and thus knows `OrgA`'s real `webhook_secret`.
3. `OrgB` has a stack tracking a repository whose history includes commit `SHA_X` (e.g. because `OrgA`'s repository is a fork of, or shares history with, `OrgB`'s repository — `SHA_X` therefore exists as a `Commit` row for the `OrgB` stack as well).
4. Attacker crafts a `status` webhook payload:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" },
  "sha": "SHA_X",
  "state": "success",
  "context": "ci/forged"
}
```
5. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks`.
6. `WebhooksController#verify_signature` resolves `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature verifies successfully (attacker legitimately owns this secret).
7. `StatusHandler#process` executes `Commit.where(sha: "SHA_X")`, which returns the `Commit` row belonging to `OrgB`'s stack (in addition to/instead of any `OrgA` commit), and calls `create_status_from_github!`, writing a forged `success` status onto `OrgB`'s commit — despite the request never being authenticated against `OrgB`'s app/secret and the attacker having no access to `OrgB`'s repository.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end
      new_status
    end
