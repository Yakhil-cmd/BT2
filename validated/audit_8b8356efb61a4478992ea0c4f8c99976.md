### Title
Long-lived unencrypted credential caching via `credential.helper cache --timeout 3600` - (File: main.go, `SetupDefaultGitConfigs`)

### Summary
git-sync configures git's built-in `credential-cache` helper with a 1-hour timeout whenever it stores HTTP credentials (username/password, askpass-url response, or GitHub App token). This causes the plaintext credential/token to be held in memory by a long-running `git-credential-cache--daemon` process for up to an hour after each sync, well beyond the single git invocation that needed it — the same underlying "sensitive secret lingers in process memory" bug class described in the external report, but here it is a designed and reachable cross-process caching mechanism rather than a JS heap artifact.

### Finding Description
`SetupDefaultGitConfigs` sets `credential.helper` to `cache --timeout 3600` globally: [1](#0-0) 

Whenever `StoreCredentials` runs (`git credential approve`), this data is handed to the credential-cache daemon, which listens on a Unix domain socket (default `~/.cache/git/credential/socket` or `$XDG_CACHE_HOME`-derived path) and holds the username/password or token in cleartext, in-memory, for the configured timeout: [2](#0-1) 

This is invoked from every credential-refresh path — static `--username`/`--password(-file)`, `--credential`, `--askpass-url`, and GitHub App token minting: [3](#0-2) [4](#0-3) [5](#0-4) 

Because the daemon is reachable via `git credential fill` by anything with filesystem access to that socket, any process sharing the container's `HOME`/`XDG_CACHE_HOME` path (e.g., a co-located sidecar sharing an `emptyDir`/HOME volume, or a process that gains local access to the git-sync container) can retrieve the cached secret without ever needing the original password or key file — directly analogous to the report's "attacker with access to the machine can exfiltrate the secret from memory while locked," except here the "unlock" state is the entire 3600s cache window, and it applies to GitHub App short-lived tokens and askpass-url dynamic secrets too, not just static passwords.

### Impact Explanation
Exposure of the git credential (password, PAT, or minted GitHub App installation token) grants an attacker sync-equivalent access to the source repository for the life of the credential. Impact is bounded by what the credential authorizes (typically read-only clone/fetch access to the synced repo) and requires local access to the same host/namespace as git-sync, so it does not itself grant remote code execution or file-system writes outside `--root`.

### Likelihood Explanation
Requires an attacker to already have some level of local access (shared volume, shared PID/user namespace, or compromise of a co-located container) — it does not come from an untrusted git ref, submodule, or arbitrary HTTP request to git-sync itself. This narrows applicability versus the fully remote analogs called out in scope, so likelihood is low-to-moderate and tied to deployment topology (e.g., misconfigured shared `HOME`/cache volumes between sidecars).

### Recommendation
- Do not enable a persistent credential cache; use `credential.helper=""` (no-op) or a strictly single-use in-memory approach that clears immediately after each `git` invocation.
- If caching is needed for performance, reduce `--timeout` to the minimum required for a single fetch operation and scope the cache socket to a private, non-shared tmpfs path unique to the git-sync process.
- For GitHub App and askpass-url tokens, avoid routing short-lived, already-time-boxed tokens through the long-lived cache daemon at all — pass credentials directly per invocation instead of persisting them via `git credential approve`.

### Proof of Concept
1. Deploy git-sync with `--username`/`--password-file` (or `--askpass-url`, or GitHub App auth) in a Pod where the container's `HOME` (and thus `~/.cache/git/credential/socket`) is on a volume shared with another container.
2. Trigger a sync so `StoreCredentials` populates the cache daemon (main.go:2055-2067).
3. From the second container (or any process with access to that socket) within the 3600s window, run `printf 'url=<repo-url>\n' | git credential fill` to retrieve the cached `username=`/`password=` cleartext without ever knowing the original secret.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}
