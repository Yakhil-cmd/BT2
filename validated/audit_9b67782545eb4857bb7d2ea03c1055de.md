This confirms the vulnerability exists in a concrete, high-impact form.

`StatusHandler#process` writes commit status data (`state`, `description`, `target_url`, `context`) directly from attacker-supplied webhook payload fields into the database via `commit.create_status_from_github!(params)`, with **no re-verification against GitHub's API** — the trust is placed entirely on the webhook signature. That signature, however, is verified using the app selected by `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`), a field independent from `repository.full_name`, which `Handler#repository_name`/`#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) uses to select which `Repository`/`Stack` the write applies to. In a multi-org configuration (`lib/shipit.rb:170-200`, `Shipit.github(organization:)`), each organization has its own `webhook_secret`. Nothing binds "the org whose secret signed this payload" to "the repository whose data gets written."

### Title
Webhook signature verification is bound to `repository.owner.login`, not to `repository.full_name` acted upon, enabling cross-organization/cross-repository commit-status forgery in multi-tenant configurations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a Shipit instance configured with multiple GitHub organizations (`secrets.github` keyed by org, per `lib/shipit.rb:170-200`), each org has its own `webhook_secret`. `WebhooksController#verify_signature` selects which app/secret to verify with based solely on `repository.owner.login` (falling back to `organization.login`) extracted from the same untrusted JSON body it is about to validate. Every event handler, however, resolves the target `Repository`/`Stack` using the separate `repository.full_name` field. Because these two fields are never cross-checked, an attacker who legitimately controls a GitHub App installation on **their own** organization (and therefore legitimately knows that organization's `webhook_secret`, which they configured themselves as part of onboarding to the shared multi-tenant Shipit instance) can sign a payload whose `repository.owner.login` matches their own org, while setting `repository.full_name` to an entirely different, victim organization's repository.

### Finding Description
- Verification: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, raw_post)` — `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- Action target resolution: `Handler#stacks` / `#repository_name` uses `payload.dig('repository', 'full_name')`, a completely separate JSON field from the one used for signature-app selection. [3](#0-2) 
- `StatusHandler#process` trusts the payload's status fields directly and writes them to the matched `Commit` with no independent verification against GitHub's API. [4](#0-3) 
- Multi-org support: each organization gets its own `GitHubApp` instance/secret via `Shipit.github(organization:)`. [5](#0-4) 

The broken binding as an equality: the engine implicitly assumes `organization that signed the payload == organization owning the repository the handler writes to`, but nothing enforces `repository.owner.login == repository.full_name.split('/').first`. An attacker with a valid webhook secret for org A can forge `repository.full_name = "OrgB/victim-repo"` while keeping `repository.owner.login = "OrgA"`, satisfying `verify_signature` under OrgA's secret yet causing the `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc., to operate on OrgB's `Repository`/`Stack`/`Commit` records.

### Impact Explanation
This is a cross-repository/cross-organization write: an org onboarded to the shared Shipit instance (unprivileged with respect to any other tenant's repos, holding no Shipit session, `ApiClient` token, or victim's secrets) can inject/forge commit statuses (`state`, `target_url`, `description`, `context`) for commits belonging to a different organization's stacks, and can trigger `GithubSyncJob`/`sync_github` against another org's stack via a forged `push` event. Forged commit statuses can influence deploy-readiness checks (`release_status?`/CI gating) on a victim stack, potentially enabling an unauthorized deploy decision downstream — matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the attacker to be a legitimate tenant of a multi-org Shipit deployment (i.e., they administer their own GitHub App installation with their own, self-configured `webhook_secret` — not the victim's secret, and no Shipit session/API token). This is a realistic scenario for shared, multi-tenant Shipit deployments as documented in `docs/setup.md`'s "Using Multiple GitHub Applications" section.

### Recommendation
After signature verification, enforce that the organization used to select the verifying `GitHubApp` matches the organization embedded in every payload field the handlers subsequently trust (in particular `repository.full_name`'s owner component), rejecting the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same `repository_owner` value that was cryptographically verified, rather than re-reading a second, unverified field from the payload.

### Proof of Concept
1. Configure a multi-org Shipit instance with `OrgA` (attacker-controlled, secret `S_A`) and `OrgB` (victim, secret `S_B`) per `lib/shipit.rb`'s `github_app_config`.
2. Craft a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha under OrgB/victim-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(S_A, raw_body)` (attacker legitimately knows `S_A`).
4. POST to `/webhooks` with header `X-Github-Event: status`. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and verifies successfully against `S_A`.
5. `StatusHandler#process` matches `Commit.where(sha: ...)` on OrgB's commit (resolved earlier by `Repository.from_github_repo_name("OrgB/victim-repo")` in other handlers/`Handler#stacks`) and writes the forged status, with no cross-check that `OrgB != OrgA`.

    # Backward compatibility

    if github_default_organization.nil?

    else

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first

  end

  def github_organizations
