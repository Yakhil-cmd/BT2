### Title
Webhook organization‑authentication binding does not match the repository that handlers act on, allowing cross‑organization triggering — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) validates an inbound webhook using `repository_owner`, derived from `params.dig('repository','owner','login')`. However, the event handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a *different* field from the same untrusted JSON body: `payload.dig('repository','full_name')`. Because these two fields are never cross‑checked, a caller who legitimately controls the webhook secret for *one* configured GitHub organization can craft a signed payload whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` names a repository belonging to a *different* configured organization, causing the handler to act on that unrelated stack.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This chooses the `GitHubApp` (and its `webhook_secret`) purely from an attacker‑supplied JSON field, then verifies the HMAC of the whole raw body against that secret via `GitHubApp#verify_webhook_signature`: [2](#0-1) 

Once verification passes, the full, attacker‑controlled `params` is dispatched unmodified to the handlers:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [3](#0-2) 

Each handler resolves the affected repository from a *different* key of the same payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` then forces a resync for every matching stack:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The binding that should hold is:
`organization authenticated (repository.owner.login used to pick webhook_secret)` == `repository actually written/acted on (repository.full_name used to resolve Stack)`

Nothing in the controller or `Handler` base class enforces this equality. In a multi‑organization Shipit deployment (as documented in `config/secrets.development.example.yml`, where each org has its own `webhook_secret`), an attacker who administers one onboarded GitHub organization (and therefore legitimately knows that org's webhook secret because they configured its GitHub App) can sign a payload with `repository.owner.login` set to their own org, but `repository.full_name` set to `victim-org/victim-repo`. The signature check passes (it only depends on their own known secret), yet the handler resolves and mutates the *victim's* `Stack` (via `sync_github`, which pulls commits using the app's own GitHub credentials and writes `Commit` records for a repository the attacker does not own).

### Impact Explanation
This breaks the intended per‑organization isolation of the multi‑tenant webhook trust boundary: possession of one organization's webhook secret is sufficient to force write operations (`Stack#sync_github`, new `Commit` rows) against a stack belonging to an entirely different, unrelated GitHub organization configured on the same Shipit instance. Depending on stack configuration (`continuous_deployment: true`, satisfied `ci.require`/`ci.blocking` statuses already present from real GitHub state), a forced resync can be the trigger that causes the victim stack to pick up and auto‑deploy a commit — i.e., an attacker outside the victim organization's control can influence when/whether a deploy for that stack is kicked off, using only credentials for their own, unrelated organization. This crosses the "cross‑repository writes" / "unauthorized deploy" boundary called out as in‑scope impact.

### Likelihood Explanation
Exploitability requires the attacker to be an administrator of at least one GitHub organization that is configured in this Shipit instance's `secrets.yml` (multi-org config), which is a realistic scenario for shared/internal Shipit deployments serving multiple teams/orgs — no Shipit session, `ApiClient` token, or `GITHUB_TOKEN` is needed, only the attacker's own legitimately-possessed webhook secret and the ability to POST to `/webhooks`. This is a low-privilege, unauthenticated-to-Shipit attacker (they only need control of their own org's webhook config), matching the required "unprivileged attacker breaking a deployment-trust binding" pattern.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` for each handler dispatch from the same field the handlers actually use (`repository.full_name`'s owner segment) and require it to equal the organization whose secret validated the signature; reject (422) any payload where `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Attacker administers `attacker-org`, onboarded to the shared Shipit instance with `webhook_secret: S_attacker` (per `config/secrets.development.example.yml` multi-org schema).
2. Attacker builds a `push` payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<any sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `S_attacker`. [6](#0-5) 
5. `PushHandler.call(params)` resolves `repository_name` as `"victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, despite the attacker having no relationship to `victim-org`. [4](#0-3) [5](#0-4)

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
