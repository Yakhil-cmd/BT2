### Title
Cross-repository CI status forgery via webhook signature/scope mismatch enabling unauthorized deploys and merges - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using the GitHub organization named in the *payload* (`repository.owner.login`), but `StatusHandler`, the handler that actually writes state, never re-checks that binding: it matches purely on commit SHA across the *entire* Shipit installation. In a multi-organization Shipit deployment this breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to verify against straight from the untrusted payload: [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` supports multiple independently configured organizations, each with its own `webhook_secret`, via `github_app_config` [5](#0-4) . Every other default handler scopes its writes to the repository named in the signed payload using the shared `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` before touching any record [6](#0-5) , e.g. `PushHandler` [7](#0-6) .

`StatusHandler`, however, does not use that scoping at all — it looks up commits by SHA globally, with no repository/stack filter: [8](#0-7) 

Because SHA-1 git commit hashes are not namespaced per repository/organization, and because Shipit stores `Commit` rows keyed only by `sha` (with cross-stack lookup via `Commit.where(sha: ...)`), an attacker who legitimately administers *any* one organization onboarded to a shared/multi-tenant Shipit instance — and therefore knows that organization's own `webhook_secret` — can POST directly to `/webhooks` with:
- `X-Hub-Signature` computed with **their own** organization's secret (so `verify_signature` passes, because it looks up the secret using `repository.owner.login` from the same forged payload),
- `sha` equal to a commit that exists in a **different**, victim organization's stack,
- `state: "success"`.

`StatusHandler#process` will locate that commit purely by `sha` regardless of which stack/repository/organization it actually belongs to, and call `commit.create_status_from_github!(params)`, creating a `Status` row scoped to the victim stack.

### Impact Explanation
Creating a `Status` triggers side effects that are used to gate deploys and merges:
- `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` [1](#0-0) 
- `Commit#add_status` calls `stack.schedule_merges if new_status.pending? || new_status.success?` [2](#0-1) 
- Deployability (`Commit#deployable?`) and merge-queue gating (`MergeRequest#all_status_checks_passed?`) are computed purely from these `Status` records.

By forging a `success` status for a commit that has not actually passed CI, an attacker can cause the victim stack's `ContinuousDeliveryJob` to trigger a deploy of an unvetted commit, or unblock a pending `MergeRequest` for merge — i.e., an unauthorized deploy or merge, which matches the Critical/High impact bar in scope (unauthorized deploy/merge). Note the practical constraint: the attacker needs the target SHA to already exist as a `Commit` row in the victim stack (e.g., an open PR or pushed branch commit), which is readily obtainable since Shipit/GitHub commit SHAs and PR contents are typically not secret.

### Likelihood Explanation
This requires the instance to be configured for multiple GitHub organizations (supported by `github_app_config`/`TOP_LEVEL_GH_KEYS`, a documented feature) and requires the attacker to be an authenticated administrator of at least one onboarded organization (i.e., they legitimately know that org's own webhook secret) but have no privileges over the victim's organization or repository. This is a realistic misuse case for any shared/multi-tenant Shipit deployment serving several GitHub orgs, since `verify_signature`'s only check is "does *some* known org's secret match," not "does this org own the repository the payload claims to modify."

### Recommendation
`StatusHandler` (and any other handler that doesn't already do so) must scope its lookup to the repository/organization that authenticated the request, not merely to a global SHA match. Concretely:
- Pass the verified `repository_owner`/organization from `WebhooksController` into handler `call`, and require handlers to filter `Commit`/`Stack` lookups by `stack.repository.owner` (or `full_name`) matching that verified organization, mirroring what `Handler#stacks` already does for `PushHandler`/`PullRequest` handlers.
- Alternatively, join `Commit.where(sha: params.sha)` through `stacks: { repository: { owner: repository_owner } }` before creating a status.

### Proof of Concept
1. Shipit is configured with two organizations, `victim-org` and `attacker-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org setup) [9](#0-8) .
2. Attacker is a legitimate admin of `attacker-org`'s GitHub App and knows `attacker-org`'s `webhook_secret` (their own secret, never the victim's).
3. Attacker finds/observes a commit SHA `S` belonging to an open branch/PR in `victim-org/victim-repo`'s Shipit stack (commit SHAs and PR diffs are not secret).
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker_secret, body)` over a JSON body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
5. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s secret, and the signature verifies successfully [3](#0-2) .
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the victim's commit (unrelated to `attacker-org`), and creates a `success` `Status` on it [8](#0-7) .
7. If `victim-org`'s stack has `continuous_deployment: true`, `Status#schedule_continuous_delivery` and `Commit#add_status`'s `stack.schedule_merges` fire, potentially deploying or merging the attacker-targeted commit without it having genuinely passed CI [2](#0-1) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first

  end

  end
