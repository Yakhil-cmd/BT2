### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while payload processing is keyed on `repository.full_name`, allowing a webhook sender that owns one configured GitHub organization to forge events for a different organization's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against by reading `repository.owner.login` (or `organization.login`) out of the untrusted JSON body itself, and then hands the *entire* raw payload to the event handlers, which resolve the target `Stack`/`Repository` using a *different* field of the same payload: `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`). Nothing binds `repository.owner.login` to `repository.full_name`.

### Finding Description
The verification flow is: [1](#0-0) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The HMAC secret used for verification (`Shipit.github(organization: repository_owner).verify_webhook_signature`) is looked up using `repository.owner.login`, itself taken from the unauthenticated request body. Once verification passes, the raw body is parsed again and dispatched unchanged to handlers: [3](#0-2) 

Handlers resolve the actual `Stack`/`Repository` to act on using a *different* field of the same body, `repository.full_name`: [4](#0-3) 

and `Repository.from_github_repo_name` splits that string into `owner/name` and looks the repository up directly, independent of `repository.owner.login`: [5](#0-4) 

Binding that should hold but doesn't: `organization whose webhook_secret authenticated the request == organization that owns the repository the handler writes to`. An attacker who legitimately controls a GitHub organization/app configured in this Shipit instance (i.e., knows OrgA's `webhook_secret`, which is entirely plausible in a multi-tenant Shipit deployment serving several unrelated GitHub orgs) can:
1. Build a payload where `repository.owner.login = "OrgA"` (so verification succeeds against OrgA's secret) but `repository.full_name = "OrgB/victim-repo"`.
2. Sign the whole payload with OrgA's `webhook_secret` via a normal outgoing webhook delivery from their own repo (or any tool once they know the secret).
3. POST it to the shared `/webhooks` endpoint; `verify_signature` succeeds because it only checks OrgA's secret against OrgA's own claimed ownership field, and the event handler then acts on `OrgB/victim-repo` because that's the field it actually trusts for repository resolution.

Concretely, `StatusHandler` writes a `Status` for **any** commit matching `params.sha` across the whole DB, without checking which repository/org that commit belongs to at all: [6](#0-5) 

and `PushHandler` triggers a GitHub sync for any stack whose `Repository.from_github_repo_name(full_name)` matches, again governed by `full_name`, not by the org that produced a valid signature: [7](#0-6) 

### Impact Explanation
This lets a party who controls credentials for one tenant/organization on a shared Shipit instance forge `status`/`push`/`pull_request` events that are attributed to a different organization's repositories and stacks. Concretely: forging a "success" `status` webhook for a commit sha belonging to another organization's stack can satisfy CI-status-based deploy safety checks and enable an unauthorized deploy of that stack (`Status` rows are consumed by `Stack#deployable?`/deploy-safety logic gated on required statuses). Forged `push` events can also force `sync_github` on stacks the attacker does not own, and forged `pull_request` events can create/archive/unarchive review stacks belonging to unrelated repositories. This maps to "escalation into unauthorized deploy" territory, which is a High/Critical-class impact per the rules (unauthorized deploy).

### Likelihood Explanation
Exploitability requires the attacker to already possess a legitimate `webhook_secret` for *some* GitHub organization configured in the same Shipit instance — a realistic condition in any multi-tenant deployment where Shipit serves multiple unrelated GitHub organizations/customers, since each org's admins configure and know their own webhook secret. No GitHub App private key, `api_clients_secret`, or `ApiClient` token is needed; only crafting a raw HTTP POST with a computed HMAC is required, which is squarely an "unprivileged attacker" scenario relative to the victim organization.

### Recommendation
Bind signature verification to the exact repository that will be acted upon, not to a self-reported "owner" field: resolve `Repository.from_github_repo_name(repository.full_name)` first, obtain that repository's/organization's `github_app`, and verify the signature against that. Alternatively, after establishing the verifying organization, require every entity referenced in the payload (`repository.full_name`, `organization.login`) to belong to that same, already-authenticated organization before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Shipit instance is configured with two GitHub organizations, `OrgA` (attacker-controlled, attacker knows `webhook_secret_A`) and `OrgB` (victim, has a stack tracking `OrgB/victim-repo`).
2. Attacker crafts JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, body)` and sets `X-Github-Event: status`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "OrgA").verify_webhook_signature(sig, raw_post)`, which succeeds (attacker used the correct secret for OrgA).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — it matches the victim's commit regardless of `repository.owner.login`, and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status onto `OrgB`'s commit, which downstream deploy-safety checks (or `push`-event handlers, if used similarly) may treat as an authorization signal for a deploy.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
