### Title
AA triggers from causally-unrelated units are not guaranteed to execute in sender-intended order, leading to failed/incorrect cross-party AA transactions - (File: `main_chain.js`, `aa_composer.js`)

### Summary
Obyte's Autonomous Agent (AA) trigger scheduling orders concurrently-arriving triggers deterministically by DAG `level` and lexicographic `unit` hash rather than by the real-world (wall-clock/intended) order in which they were sent. When two trigger units are causally unrelated in the DAG (i.e., neither is an ancestor of the other), the protocol offers no guarantee that they will be processed in the order the users intended, mirroring the "lack of message ordering" issue described in the ZetaChain report where cross-chain messages can be finalized out of order.

### Finding Description
When an MCI becomes stable, `main_chain.js`'s `handleAATriggers()` selects all units that pay to AA addresses in that MCI and inserts them into `aa_triggers`, ordered only by `units.level, units.unit, address`: [1](#0-0) 

`aa_composer.js`'s `handleAATriggers()` then processes the queued triggers using the same deterministic-but-arbitrary tie-break (`mci, level, unit, address`) and executes them strictly in series via `async.eachSeries`: [2](#0-1) 

`level` is only guaranteed to increase along a causal DAG chain — it is computed as `max(parent levels) + 1` — so it correctly orders a unit *after* its own ancestors: [3](#0-2) 

However, for two units that are **not** ancestor/descendant of each other (e.g., sent by two different addresses, or by devices/wallets that composed their units independently before seeing each other's unit), `level` comparison is undefined/incomparable — `graph.js`'s `compareUnitsByProps` explicitly returns `null` ("incomparable") for such sibling units: [4](#0-3) 

In that case the eventual processing order is decided purely by the lexicographic sort of `units.unit` (the unit hash) — a value that has no relationship to when the units were broadcast or the order intended by the interacting parties. Obyte's serial-address-use validation (`checkNoSameAddressInDifferentParents` / `findConflictingUnits` in `validation.js`) only prevents the *same* address from having two mutually non-descendant "good" units; it does nothing to order units authored by two different, cooperating addresses: [5](#0-4) [6](#0-5) 

Consequently, an AA-based dApp that relies on a specific temporal sequence between triggers from different parties (e.g., "Alice deposits collateral" then "Bob's order-matching trigger consumes it", or "Party A opens a private-payment/escrow state" then "Party B settles it") has no protocol-level guarantee that the units will be executed in that order once both become stable in the same MCI, exactly as in the reported cross-chain analog where "cross-chain transactions … are not guaranteed to be finalized in the order they were sent."

### Impact Explanation
If an AA's oscript logic assumes triggers from independent addresses arrive in a specific temporal order (a common pattern for escrow/matching/marketplace/staking-style AAs), a trigger that is supposed to run second can be executed first. This can cause the second-composed unit to be bounced (loss of bounce fees for the sender, and inability to reach the intended AA responses/state changes), or, worse, can cause the AA to execute unintended state transitions if the bounce/guard checks in the AA logic are incomplete — e.g., consuming/locking funds meant for a specific counterpart transaction, or letting a settlement trigger execute against stale/absent state. This is a fund-loss/fund-freezing risk realized purely through normal usage timing (no malicious behavior required), and is analogous to the confirmed ZetaChain finding.

### Likelihood Explanation
This requires only that two causally-unrelated units targeting the same AA(s) become "free"/composed close enough in time that neither is included as an ancestor of the other before both stabilize in the same (or comparable) MCI — a routine occurrence under normal network conditions when independent users/wallets interact with the same AA without deliberately waiting for/chaining off each other's unit. No attacker privilege is required: an ordinary AA trigger sender (or two cooperating/uncoordinated senders) can trigger this by nature of how they compose their units, making the likelihood Medium given typical multi-party AA usage patterns (escrow, matching, sequential staking-like flows).

### Recommendation
- Document explicitly (in AA developer guidance) that trigger execution order across causally-unrelated units is **not** guaranteed to match real-world send order, and that AAs must not assume cross-address temporal ordering.
- For dApps that require enforced ordering between two dependent actions, require the second unit to be causally chained to the first (e.g., require the dependent trigger to be composed only after the first unit's `unit` hash is known and to include it as an explicit ancestor, or have the second sender's client wait until the first is at least "free"/broadcast and pick it as a parent via `pickParentUnitsAndLastBall`).
- Alternatively, add a first-class oscript/formula primitive (analogous to the "message ordering" option in LayerZero cited by the reporter) that lets an AA verify that a referenced prior trigger unit is an ancestor of the current trigger before proceeding, and bounce/reject otherwise, rather than relying solely on state-variable nonces (which, as the original report notes, are insufficient because the AA has no way to distinguish "not yet arrived" from "will never arrive" without an explicit ancestry check).

### Proof of Concept
1. AA `X` implements an escrow-like flow: trigger type `"deposit"` sets `state.deposited[trigger.address] = trigger.outputs.base`; trigger type `"settle"` requires `state.deposited[params.depositor]` to be set, otherwise it bounces.
2. Address `A` composes and broadcasts a `"deposit"` trigger unit `U1`.
3. Immediately afterward, address `B` (who has been told out-of-band that `A` sent the deposit) composes a `"settle"` trigger unit `U2` referencing `A`. Because `B`'s node has not yet seen/included `U1` in its DAG when picking parents (`parent_composer.js pickParentUnitsAndLastBall` selects from currently known free units), `U2` is not a descendant of `U1`.
4. Both `U1` and `U2` propagate and become stable within the same MCI. Since neither is an ancestor of the other, `graph.compareUnitsByProps` returns `null` for the pair: [4](#0-3) .
5. `handleAATriggers()`'s `ORDER BY units.level, units.unit, address` may place `U2` (settle) before `U1` (deposit) if `U2`'s unit hash sorts lower at the same level: [1](#0-0) .
6. AA `X` processes `U2` first, finds `state.deposited[A]` unset, and bounces the settle trigger — reproducing the "second message processed before the first, causing the transaction to fail" scenario from the original report.
