### Title
Unrecoverable node crash via reachable `throw Error` in AA formula evaluator invariants - (File: formula/evaluation.js)

### Summary
`formula/evaluation.js`'s `evaluate()` function contains numerous invariant checks implemented as hard `throw Error(...)` (e.g. `throw Error("unknown field requested: "+arr[2])` [2](#0-1) , `throw Error("test evaluated to object " + res)` [3](#0-2) , `throw Error('unrecognized op '+op)` [4](#0-3) ) rather than being routed through `setFatalError`/`cb(err)`, the normal error-reporting mechanism used everywhere else in the same function. `formula/validation.js` has an analogous assertion `if (depth !== 0) throw Error("mismatched depth " + depth);` [5](#0-4)  which fires if the internal depth counter (incremented/decremented per node visited in `evaluate`) does not return to zero after the walk completes.

### Finding Description
Unlike the Linux `WARN_ON_ONCE`, which merely logs a warning and continues, ocore installs a global `process.on('uncaughtException')` handler in `network.js` that deliberately re-throws to terminate the process [1](#0-0) . This makes every unguarded `throw Error(...)` inside formula validation/evaluation a potential full node-kill primitive, analogous to (but more severe than) the CVE's reachable assertion.

`aa_composer.js`'s `handleTrigger`/`evaluateAA`/`replace` invoke `formulaParser.evaluate(...)` directly as a plain callback without any surrounding `try { } catch { }` [6](#0-5) [7](#0-6) . These calls occur inside `handlePrimaryAATrigger`, itself invoked from unit/joint validation code reached whenever an AA trigger is posted by any user (`network.js`'s `ifOk`/`handleOnlineJoint` flow calls into `writer.saveJoint` → AA trigger processing). If the attacker-controlled formula (an AA's own definition combined with attacker-controlled `trigger.data`) drives execution into one of these `throw Error` branches instead of the normal `setFatalError`/bounce path, the exception propagates synchronously out of the `evaluate()` call stack, is not caught anywhere, becomes an `uncaughtException`, and the global handler kills the entire daemon.

The most concrete reachable instance is `formula/validation.js:1526-1527`'s "mismatched depth" invariant. `depth` is incremented at function entry and decremented in the wrapped callback `cb` for every node visited during `evaluate()` traversal of the parsed AST [8](#0-7) . This assumes every code path that increments `depth` eventually calls the wrapped `cb` exactly once. Any AST-evaluation branch in the large `switch(op)` in `validate()` that returns without invoking `cb` (e.g., via an unhandled synchronous exception thrown from a nested helper, or an async control-flow bug in one of the many `async.eachSeries`/branch handlers) would leave `depth` non-zero when the top-level completion callback runs, hitting the throw at line 1526–1527 and crashing the node. Because `validate()` is invoked on every AA definition and formula evaluated via `readGetterProps`/`aa_validation.js` and `formulaParser.validate` from AA-trigger processing, an attacker who can post a unit (payment) that triggers an AA, or who can define/deploy an AA (any address can post one), controls the formula content and can attempt to steer parsing/evaluation into these unguarded invariant violations.

### Impact Explanation
If an attacker can craft an oscript/AA formula (as an AA author defining `getters`/`init`/`state` formulas, or as any user sending a trigger whose `trigger.data` feeds into evaluated expressions) that reaches one of these `throw Error` invariants during validation or evaluation, the resulting uncaught exception triggers ocore's `process.on('uncaughtException')` handler, which explicitly re-throws to crash the process [1](#0-0) . A crashed full node/hub stops relaying, validating, and confirming units — a "network unable to confirm new units" condition if this is broadcast widely or targets witness/hub nodes, satisfying the required impact bar.

### Likelihood Explanation
Exploitability depends on finding a concrete AST/formula input that reaches one of the unguarded `throw` statements instead of the guarded `setFatalError`/`cb(err)` paths (most branches are guarded, but a few, like the depth-invariant and "unrecognized op"/"test evaluated to object" checks, are not). I was not able to fully trace every branch of the large `evaluate()`/`validate()` switch statements to construct a definite proof-of-concept formula within the available search budget, so likelihood is assessed as **medium**: the crash-on-uncaught-exception architecture is confirmed and reachable via AA triggers/definitions, but a concrete triggering formula for the "mismatched depth" or other bare `throw` requires deeper live testing (e.g. fuzzing the formula parser/evaluator) that a static index search cannot fully confirm.

### Recommendation
- Convert all bare `throw Error(...)` invariant checks inside `formula/evaluation.js` and `formula/validation.js` (including the `depth !== 0` check at `formula/validation.js:1526-1527` and the `unrecognized op`, `unknown field requested`, `test evaluated to object` cases) into `setFatalError(...)`/`cb(err)` calls consistent with the rest of the evaluator, so malformed/edge-case formulas fail gracefully with a bounce/validation error rather than crashing the process.
- Wrap all `formulaParser.evaluate`/`formulaParser.validate` invocations in `aa_composer.js` (`evaluateAA`, `replace`, and case/if/init formula evaluation) with `try/catch` that converts unexpected exceptions into a bounce, instead of letting them propagate to `process.on('uncaughtException')`.
- Add a regression/fuzz test suite exercising the formula parser/evaluator with adversarial ASTs (deeply nested, malformed control flow, mismatched async completions) to ensure the `depth` counter invariant cannot be desynchronized.

### Proof of Concept
A concrete AST-level proof-of-concept formula that desynchronizes the `depth` counter in `formula/validation.js` (to trigger the "mismatched depth" throw) could not be fully constructed and verified from static code search alone within the available investigation; live fuzzing/testing of the formula validator's `evaluate()` switch branches against the wrapped `cb`/`depth--` bookkeeping in `formula/validation.js:272-288` would be required to confirm a specific triggering formula. The reachability of the `process.on('uncaughtException') → throw err` crash path from any uncaught exception surfaced through AA trigger processing is confirmed at `network.js:4530-4543` and `aa_composer.js:589-615/710-733`.
