## Analog Vulnerability Found

### Title
Premature mutex release in `shrinkCache()` allows in-flight cache mutations to race with the `"write"` lock, corrupting shared unit-props caches - ([File: storage.js])

### Summary
CVE-2020-25668 is a kernel use-after-free caused by unsynchronized access to the global `fg_console` variable in `con_font_op`. The direct analog in `ocore--006` is `storage.js`'s `shrinkCache()`, which acquires the process-wide `"write"` mutex that is supposed to serialize all mutations of the shared in-memory unit caches, but calls `unlock()` **before** the asynchronous `db.query()` callbacks that actually mutate those caches have executed. Other code paths that also take the `"write"` lock (most importantly `writer.saveJoint()`) can then run concurrently with these still-pending cache deletions, exactly like the kernel scenario where a shared global is torn down/mutated while another context is still using it.

### Finding Description
`shrinkCache()` takes the lock, issues several chunked `db.query()` calls whose callbacks delete entries from `assocKnownUnits`, `assocCachedUnits`, `assocBestChildren`, `assocStableUnits`, `assocCachedUnitAuthors`, and `assocCachedUnitWitnesses`, but calls `unlock()` immediately after firing the queries instead of after the callbacks complete: [1](#0-0) 

Every other writer of these caches relies on the `"write"` lock for exclusivity — e.g. `writer.js` explicitly comments that the lock exists to avoid interleaving mutations of this shared state: [2](#0-1) [3](#0-2) 

Because `shrinkCache()`'s `unlock()` fires before its own `db.query` deletions are applied, a subsequent lock holder (e.g. a newly validated unit being written via `writer.saveJoint`) can begin mutating `assocUnstableUnits`/`assocBestChildren` while the stale `shrinkCache` callbacks are still pending and will delete entries out from under it moments later. Code that assumes these cache entries stay present once populated (no re-check, no re-fetch) then dereferences `undefined`: [4](#0-3) 

This mirrors the CVE pattern precisely: a shared global data structure is accessed/mutated without the synchronization its own lock is supposed to guarantee, so a consumer can observe or act on a structure that has just been (or is about to be) deleted/mutated by a concurrent, unsynchronized path.

### Impact Explanation
`assocBestChildren`, `assocUnstableUnits`, and `assocStableUnits` back the in-memory state that `main_chain.js` uses to compute best-parent selection, witnessed level, and stability advancement, and that `writer.js` updates on every new unit write. A race that deletes entries from these structures mid-flight can:
- crash the node process with an uncaught `TypeError` when code such as `forgetUnit()`/`fixIsFreeAfterForgettingUnit()`-style traversal hits an `undefined` cache entry, or
- leave the node's cached view of unstable/best-child relationships inconsistent with what other nodes compute, producing **node disagreement on validity or stability** — one of the accepted high-impact outcomes.

### Likelihood Explanation
`shrinkCache()` runs automatically via `setInterval(shrinkCache, 300*1000)` once any of the tracked cache maps exceeds `MAX_ITEMS_IN_CACHE`: [5](#0-4) 

An unprivileged unit poster can trivially grow these caches past the threshold and sustain high unit-processing throughput by continuously broadcasting valid units, which both triggers frequent shrink passes and widens the concurrency window in which other `"write"`-locked operations (ordinary unit saves) interleave with the still-pending deletion callbacks. No privileged position, malicious peer/hub, or network-level attack is required — only the ability to post units, which is the baseline capability assumed in scope.

### Recommendation
Move the `unlock()` call inside the completion callback of all chunked `db.query()` calls in `shrinkCache()` (e.g. using `async.each`/`Promise.all` over the chunks) so the `"write"` lock is held for the entire duration of the cache mutation, not just until the queries are dispatched.

### Proof of Concept
1. Post/broadcast enough distinct units so that `assocCachedUnits`/`assocKnownUnits`/etc. exceed `MAX_ITEMS_IN_CACHE`, causing `shrinkCache()`'s guard condition to pass.
2. Wait for the 5-minute `shrinkCache` interval to fire; it acquires the `"write"` lock, dispatches chunked `db.query()` calls, then immediately calls `unlock()` before those queries return.
3. While the `db.query` callbacks are still pending, submit another unit whose processing goes through `writer.saveJoint()` (which now can acquire the freed `"write"` lock) and mutates `assocUnstableUnits`/`assocBestChildren` for units overlapping the pending shrink chunk.
4. When the delayed `shrinkCache` callbacks finally execute, they delete cache entries that the concurrent `saveJoint` path just created/relied on, leading to either an uncaught exception on next access (e.g., via `forgetUnit`) or a main-chain/stability computation that diverges from other nodes that did not experience the race at that instant.
