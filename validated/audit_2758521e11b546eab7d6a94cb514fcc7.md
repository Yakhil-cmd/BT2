### Title
Webhook signature verification bypassed for GitHub orgs without a configured `webhook_secret` - (File: lib/shipit/github_app.rb, app/controllers/shipit/webhooks_controller.rb)

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when `@webhook_secret` is blank, and `WebhooksController#verify_signature` calls this method using the organization derived directly from the untrusted request body (`repository.owner.login`). Any org configured in `Shipit.secrets.github` without a `webhook_secret` therefore accepts arbitrary, unsigned webhook payloads as authenticated.

### Finding Description
The claimed binding is: "a body verified by some `webhook_secret`" should equal "a body actually protected by an HMAC comparison." In practice: `verify_webhook_signature(signature, message)` at [1](#0-0)  executes `return true unless webhook_secret` before ever touching `signature` or `message`, so when `@webhook_secret` is `nil`/blank (set from `@config[:webhook_secret].presence` at [2](#0-1) ), zero HMAC bytes are computed and the call still returns `true`.

The controller's `verify_signature` before_action resolves the `GitHubApp` instance strictly from attacker-controlled body content: `repository_owner` is read from `params.dig('repository', 'owner', 'login')` at [3](#0-2) , then passed into `Shipit.github(organization: repository_owner)` at [4](#0-3) . If that org exists in config but has no `webhook_secret`, `verified` is `true` for any signature (or none), and `#create` dispatches the parsed payload straight to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` at [5](#0-4) , running the real `PushHandler`/`StatusHandler`/etc. against that org's live stacks.

This is not merely theoretical in this repo: the shipped test dummy configuration itself sets `webhook_secret: # nil` for its `github` org config [6](#0-5) , demonstrating a supported, realistic configuration shape that triggers the bypass. Existing tests never exercise the real HMAC path either — they stub verification (`GithubHook.any_instance.stubs(:verify_signature).returns(true)` in the setup) or mock `verify_webhook_signature` directly rather than proving actual signature enforcement [7](#0-6) [8](#0-7) . No other guard (`drop_unhandled_event`, `check_if_ping`, model validations) checks HMAC integrity or org-secret presence; `drop_unhandled_event` only filters by event name, and `check_if_ping` only short-circuits ping events, neither preventing this bypass for `push`/`status`/`membership`/`check_suite`.

### Impact Explanation
An unauthenticated internet attacker can forge and POST arbitrary `push`, `status`, `check_suite`, or `membership` webhook payloads for any GitHub org configured in Shipit without a `webhook_secret`, causing Shipit to enqueue real jobs (`GithubSyncJob`, `RefreshCheckRunsJob`), write `Status` records, or mutate `Team`/`Membership` records against that org's actual stacks — with no valid HMAC ever computed. This is a full authentication bypass of the webhook trust boundary for any such org, matching the Critical category (forged webhook accepted, unauthorized mutation of a stack/commit/team belonging to a real GitHub org). The blast radius is scoped to orgs with a blank `webhook_secret`, but is fully repeatable per request and requires no attacker capability beyond crafting an HTTP POST.

### Likelihood Explanation
The precondition is operator/config-driven: at least one org in `Shipit.secrets.github` must have `webhook_secret` unset or empty. This is not a hypothetical edge case — it's the exact shape used in this repo's own `test/dummy/config/secrets.yml` [9](#0-8)  and is explicitly cited in the question as a documented pattern in `secrets.development.shopify.yml`-style configs. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body and an `X-Github-Event` header; no secrets, sessions, or tokens are needed, and the exploit is trivially repeatable against any push/status/membership/check_suite handler.

### Recommendation
Fail closed instead of open: if `webhook_secret` is blank for a configured org, `verify_webhook_signature` should return `false` (reject) rather than `true`, or Shipit should refuse to boot/register a GitHub org config without a non-blank `webhook_secret`. At minimum, log and reject unsigned/no-secret webhooks in production environments, and add a startup-time validation that all configured `Shipit.secrets.github` orgs used for webhook-receiving have a `webhook_secret` present.

### Proof of Concept
Minitest plan (no live GitHub, no new test files needed conceptually but demonstrating the assertions):

1. Unit test on `GitHubApp`:
```ruby
app = Shipit::GitHubApp.new('someorg', { app_id: 1, installation_id: 1, private_key: 'x' }) # no webhook_secret key
assert_equal true, app.verify_webhook_signature(nil, 'arbitrary-attacker-body')
assert_equal true, app.verify_webhook_signature('sha1=deadbeef', 'arbitrary-attacker-body')
```
Both assert the equality "zero secret bytes verified" == "body treated as authenticated," which should not hold but does.

2. Integration test on `WebhooksController`:
```ruby
Shipit.stubs(:github).with(organization: 'someorg').returns(
  Shipit::GitHubApp.new('someorg', { app_id: 1, installation_id: 1, private_key: 'x' })
)
OpenSSL::HMAC.expects(:hexdigest).never

request.headers['X-Github-Event'] = 'push'
payload = JSON.parse(payload(:push_master))
payload['repository']['owner']['login'] = 'someorg'

assert_enqueued_with(job: GithubSyncJob) do
  post :create, body: payload.to_json, as: :json
end
assert_response :ok
```
This proves a job is enqueued against `someorg`'s stack without any HMAC computation occurring, confirming the authentication bypass.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
