### Title
Same-Epoch Dual-Vote Bypasses `LowerBoundBaseFee ≤ UpperBoundBaseFee` Invariant, Corrupting Base-Fee State — (`kaiax/gov/headergov/impl/header.go`)

---

### Summary

`checkConsistency` validates each governance vote individually against the **current** `ParamSet` at vote time. When two votes targeting `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` land in the **same epoch**, each passes its individual cross-parameter check, but the combined effect at the epoch boundary produces `LowerBoundBaseFee > UpperBoundBaseFee`. `NextMagmaBlockBaseFee` then silently clamps the base fee to the (now-lower) `UpperBoundBaseFee`, permanently computing every subsequent block's base fee below the intended minimum — an invalid state transition for the fee market.

---

### Finding Description

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` enforces the ordering invariant per-vote:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)          // current state only
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)          // current state only
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
``` [1](#0-0) 

Both branches call `h.GetParamSet(blockNum)` — the **committed** parameter set at the time of the vote — not the accumulated pending votes for the current epoch. There is no cross-vote consistency check at epoch application time.

At the epoch boundary, `getExpectedGovernance` collects all votes from the previous epoch into a `PartialParamSet` (a plain `map[ParamName]any`) and applies them all:

```go
for _, voteBlock := range sortedVoteBlocks {
    vote := prevEpochVotes[voteBlock]
    govs.Add(string(vote.Name()), vote.Value())   // no cross-param check
}
``` [2](#0-1) 

`PartialParamSet.Add` only runs the per-parameter `FormatChecker` (a `noopFormatChecker` for both KIP-71 bounds), with no cross-parameter ordering check: [3](#0-2) 

**Attack path (governance mode "none", or a single governing node in "single" mode):**

| Step | Action | Check result |
|------|--------|-------------|
| Current state | `lower = 25 gwei`, `upper = 750 gwei` | — |
| Block N, epoch E | Vote `UpperBoundBaseFee = 30 gwei` | `30 >= 25` ✓ passes |
| Block M > N, epoch E | Vote `LowerBoundBaseFee = 50 gwei` | `50 <= 750` ✓ passes (checked against **current** upper=750, not pending upper=30) |
| Epoch E+1 boundary | Both votes applied | `lower=50 gwei`, `upper=30 gwei` — **invariant broken** |

After the epoch boundary, `NextMagmaBlockBaseFee` executes with the broken parameters:

```go
lowerBoundBaseFee := new(big.Int).SetUint64(kc.LowerBoundBaseFee)  // 50 gwei
upperBoundBaseFee := new(big.Int).SetUint64(kc.UpperBoundBaseFee)  // 30 gwei
...
if parentBaseFee.Cmp(upperBoundBaseFee) >= 0 {   // always true: parentBaseFee >= 50 > 30
    parentBaseFee = upperBoundBaseFee             // clamp to 30 gwei
}
``` [4](#0-3) 

Every subsequent block's base fee is computed from a `parentBaseFee` clamped to `upperBoundBaseFee` (30 gwei), permanently below the intended minimum of 50 gwei. Because all nodes apply the same broken parameters, `VerifyMagmaHeader` does not reject these blocks — the invalid state is consensus-consistent but semantically wrong.

---

### Impact Explanation

The `LowerBoundBaseFee ≤ UpperBoundBaseFee` invariant is the foundational constraint of the KIP-71 dynamic fee market. Violating it causes `NextMagmaBlockBaseFee` to compute every block's base fee below the intended minimum floor. This is a persistent, consensus-accepted invalid state transition: the fee market is permanently misconfigured, all transactions pay less than the governance-mandated minimum, and fee burn/distribution is reduced below the intended level for every block until a corrective governance vote takes effect (which itself requires another epoch cycle).

---

### Likelihood Explanation

In governance mode "none" (or pre-Permissionless), any validator who is the block proposer can cast a vote. A single validator who proposes two blocks in the same epoch can cast both votes unilaterally. Alternatively, two independent validators each proposing one block in the same epoch can produce the same outcome without coordination. The epoch length is a fixed parameter (e.g., 604,800 blocks on mainnet), giving ample opportunity for both votes to land in the same epoch. No majority collusion is required.

---

### Recommendation

Add a cross-parameter invariant check at epoch application time in `getExpectedGovernance` (or in the governance module that merges the `PartialParamSet` into the active `ParamSet`). After all epoch votes are merged, verify:

```go
if lower, ok1 := govs[gov.Kip71LowerBoundBaseFee]; ok1 {
    if upper, ok2 := govs[gov.Kip71UpperBoundBaseFee]; ok2 {
        if lower.(uint64) > upper.(uint64) {
            // drop or reject the conflicting pair
        }
    }
}
```

Alternatively, enforce the invariant in `checkConsistency` by also consulting the **pending votes already accumulated in the current epoch** for the counterpart parameter, not just the committed `ParamSet`.

### Proof of Concept

1. Deploy a Kaia node with governance mode `"none"` and default KIP-71 parameters (`lower=25 gwei`, `upper=750 gwei`).
2. In epoch E, have validator A (as block proposer at block N) cast vote: `kip71.upperboundbasefee = 30 gwei`. `checkConsistency` passes: `30 >= 25`.
3. In the same epoch E, have validator B (as block proposer at block M > N) cast vote: `kip71.lowerboundbasefee = 50 gwei`. `checkConsistency` passes: `50 <= 750` (current upper, not pending).
4. At the epoch E+1 boundary block, `getExpectedGovernance` collects both votes and writes `lower=50 gwei`, `upper=30 gwei` into `header.Governance`. All nodes accept this block (governance bytes match the locally computed expected governance).
5. From epoch E+1 onward, `NextMagmaBlockBaseFee` clamps `parentBaseFee` to `upperBoundBaseFee=30 gwei` on every block, producing a base fee permanently below the intended minimum of 50 gwei. `VerifyMagmaHeader` accepts all these blocks because all nodes compute the same (wrong) value.
