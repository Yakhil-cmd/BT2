### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while event handlers act on `repository.full_name`, allowing an authenticated organization to trigger writes on another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an inbound webhook based on `params.dig('repository','owner','login')` (or `params.dig('organization','login')`), but the payload dispatched to handlers is trusted as-is, and every `Handlers::Handler` subclass resolves the target `Repository`/`Stack` from `payload.dig('repository','full_name')`. These two fields are never cross-checked, so in a multi-organization Shipit deployment (the documented `github: { org1: {...}, org2: {...} }` config), a party who possesses a valid `webhook_secret` for one configured organization can craft a signed payload whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` names a repository belonging to a different, victim organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the authenticating organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (including a distinct `webhook_secret`) when the multi-org schema is used: [3](#0-2) 

Once the HMAC check passes for whichever organization `repository.owner.login` names, the *entire* raw payload — including the independently-attacker-controlled `repository.full_name` — is handed to every registered handler: [4](#0-3) 

`Handler#stacks`/`#repository_name` resolve the target `Repository` (and thus `Stack`s) solely from `full_name`, with no re-check that it belongs to the organization whose secret authenticated the request: [5](#0-4) [6](#0-5) 

Concretely, `PushHandler` uses this mismatched resolution to force a repository sync of an arbitrary stack to an attacker-chosen `after` (commit SHA): [7](#0-6) 

`StatusHandler` similarly writes commit statuses by `sha` lookup across all stacks with no repository-boundary check at all, and `MembershipHandler` mutates `Team`/`Membership` records keyed off `params.organization.login` independent of the verifying organization, letting an authenticated org holder add/remove memberships nominally attributed to another org: [8](#0-7) [9](#0-8) 

**Binding broken:** the organization whose `webhook_secret` authenticated the request (`repository.owner.login`) ≠ the repository/stack that handlers actually mutate (`repository.full_name`). The signature only proves knowledge of one organization's secret; it proves nothing about the `full_name` field consumed downstream.

### Impact Explanation
This is a cross-repository write: an entity that legitimately controls (or has been issued the webhook secret for) one organization configured in a shared Shipit instance can force Git sync operations, commit status writes, and team-membership mutations against a completely different organization's stacks/repositories that it has no access to. Depending on the affected stack's `continuous_deployment` configuration, forcing `sync_github` with an attacker-chosen `expected_head_sha` can feed into deploy-triggering logic for a repository outside the attacker's authorization scope — this falls under the "Critical: cross-repository writes / unauthorized deploy" bucket.

### Likelihood Explanation
Exploitation requires the deployment to use the multi-organization `github:` config schema documented in `docs/setup.md`, and requires the attacker to be a legitimate operator/owner of at least one of the configured organizations (i.e., they possess that org's `webhook_secret` the same way GitHub would use it to sign real deliveries, or can otherwise obtain it since it's config they control on their own GitHub App). Given that Shipit is explicitly designed to host many organizations/repositories in one instance and each org's admin only needs GitHub App-level control (not Shipit's platform-level trust) to hold a valid secret, this is a realistic multi-tenant boundary violation rather than a purely theoretical one.

### Recommendation
After signature verification, re-derive the authorized organization from the same GitHub App used for verification (or an authoritative installation identifier) and assert that `payload.dig('repository','full_name')`'s owner segment matches that organization before dispatching to handlers. Reject (422) any webhook where `repository.owner.login`/`organization.login` and the owner portion of `repository.full_name` disagree.

### Proof of Concept
1. Deploy Shipit with multi-org config: `github: { attacker-org: { webhook_secret: S1, ... }, victim-org: { webhook_secret: S2, ... } }`, both tracking real repos/stacks in the same instance.
2. Attacker, who legitimately controls `attacker-org`'s GitHub App and thus knows `S1`, crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S1, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies against `S1`. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: '<attacker-chosen sha>')` on the victim organization's stack, despite the request never having been authenticated against `victim-org`'s secret. [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
