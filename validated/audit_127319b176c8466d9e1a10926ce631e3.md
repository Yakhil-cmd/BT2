Based on my investigation, I found a concrete analog in ocore that mirrors the bug class: **an entity that "controls the execution" (satisfies gate-keeping checks) is not the entity whose funds are actually moved**, allowing a restricted/unattested value source to be laundered through a trusted counterparty's identity.

### Title
AA triggers derive `trigger.address` only from `authors[0]`, letting an unattested co-author's funds pass through an "attested"-gated AA under a verified author's identity - (File: aa_composer.js)

### Summary
`getTrigger()` sets `trigger.address = objUnit.authors[0].address` [1](#0-0)  and aggregates payment `outputs` from the whole unit's payment messages regardless of which author actually funded them [2](#0-1) . AAs that gate access with `attested` on `trigger.address` (using the standard `case 'attested'` oscript primitive, checked via `storage.filterAttestedAddresses`) [3](#0-2)  only validate that `authors[0]` is attested/KYC'd — not that the actual bytes/asset funding the trigger's payment outputs originate from that attested author.

### Finding Description
`validateAuthors`/`validateAuthor` in `validation.js` permit multi-authored units where each author independently signs and where payment inputs can be attributed to any of the authors (see the multi-author `issue`/`transfer` input-address handling requiring `input.address` to simply be one of `arrAuthorAddresses`) [4](#0-3) . This means a unit can be co-signed by:
- Author[0]: a KYC-attested/whitelisted address (analogous to "Alice", the verified executor), contributing no funds.
- Author[1]: an unattested/sanctioned address, whose own inputs actually fund the payment message's outputs sent to the AA.

When this unit triggers an AA, `getTrigger()` builds `trigger.address` strictly from `objUnit.authors[0].address` [1](#0-0) , and the AA's `trigger.outputs` sum up amounts sent to it irrespective of which co-author actually supplied the coins [5](#0-4) . If the AA definition does gate-keeping such as `['attested', ['trigger.address', [attestor]]]`, only `authors[0]` (Alice) is checked, exactly mirroring the reported flaw where `VerifiedPoolsBasicHook` checks the verified party executing the call rather than the party whose funds are actually exchanged.

This is structurally the same root cause as the external report: an access-control check is anchored to "who is executing/signing" rather than "whose value is being moved," and the protocol (here, ocore's multi-author unit + AA trigger model) allows those two identities to diverge within a single, unprivileged unit that any user can post.

### Impact Explanation
Any AA built for KYC-style or attestation-gated financial services (deposit, swap, redemption AAs using `attested` on `trigger.address`) can be used by an unattested/sanctioned address to move value through the AA, with the attested co-author merely lending their identity/signature and receiving no or minimal capital themselves, while the sanctioned party's funds are the ones actually processed and any AA-side outputs (e.g., swap proceeds) can be redirected to the attested author or split back to the sanctioned party via the AA's payment logic (since AA output destinations are typically parameterizable in the trigger `data`/formula, not restricted to `trigger.address`). This allows bypass of the "spender must be attested" intent enforced at the application (AA) layer, similar to how the reported bug bypasses the pool's verified-sanctions gate.

### Likelihood Explanation
Low-to-medium: requires an AA author to have built attestation logic keyed on `trigger.address` (a very common and recommended oscript pattern for KYC gating) combined with willingness of a compliant party to co-sign a multi-author unit for compensation — structurally identical precondition to the original report (an external/incentivized off-chain arrangement between a verified party and a sanctioned party). No core-protocol privilege is needed; any unprivileged unit poster can construct and sign such a multi-author trigger unit.

### Recommendation
- Document and, where feasible, enforce that AA attestation checks referencing `trigger.address` should be paired with verification that the address supplying `trigger.outputs` matches `trigger.address`, or expose to oscript the actual per-author contribution so AA authors can explicitly require `trigger.address` (or all contributing authors) to be attested.
- Consider exposing an oscript primitive/field (e.g. `trigger.output[[address=...]]`) or documentation warning that multi-authored trigger units can decouple "who signs (trigger.address)" from "who funds (payment input owners)," so AA developers relying on `attested trigger.address` for compliance gating are aware of this gap and should additionally validate input ownership within their formulas.

### Proof of Concept
Not independently executed; based on static code-path analysis:
1. Attested address A (KYC'd) and unattested/sanctioned address B jointly author a unit (`objUnit.authors = [A, B]`, sorted by address) with a `payment` message whose outputs go to AA address `X`, funded by input(s) owned by B [4](#0-3) .
2. `handleAATriggers`/`getTrigger` process the stable unit; `trigger.address` becomes `A` (first author) regardless of who funded the outputs [6](#0-5) .
3. AA `X`'s definition contains a gate such as `attested trigger.address by [KYC_ATTESTOR]`, which passes because `A` is attested, even though the value moved originates from sanctioned address `B` [3](#0-2) .
4. The AA processes the trigger and can send response outputs to either `A` or, via formula referencing amounts/`trigger.initial_address`, effectively route value/benefit involving `B`. [7](#0-6) [4](#0-3) [3](#0-2)

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
