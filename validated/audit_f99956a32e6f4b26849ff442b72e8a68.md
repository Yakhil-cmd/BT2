### Title
Stack-scoped `ApiClient` tokens can read CCMenu status for any stack, bypassing the token's stack authorization — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The external report describes `RuniverseLandMinter`'s `plotsAvailablePerSize` check being enforced only on one code path (`_mintTokens`) while a second, equally-privileged path (`RuniverseLand.mintTokenId` via `secondaryMinter`) can write the same shared state without any of those checks — breaking the invariant that the checked value and the acted-upon value are the same. The analogous binding in Shipit is: *the stack an `ApiClient` token is scoped/authorised to* (`ApiClient#stack_id`) versus *the stack a controller action actually operates on* (`params[:stack_id]`). `Shipit::Api::BaseController` enforces this binding everywhere via its `stacks`/`stack` helpers, but `Shipit::Api::CCMenuController` re-defines `stack` in a way that silently drops the scoping check, letting a token scoped to Stack A read CCMenu/build data for any other Stack B.

### Finding Description
`Shipit::Api::BaseController` is the common authorization layer for the JSON API. It scopes visible stacks to the calling `ApiClient`'s bound stack when one is set: [1](#0-0) 

This `stacks`/`stack` pair is what every other controller (`StacksController`, `HooksController`, `TasksController`, etc.) relies on so that a token created with `stack: shipit` (see the `here_come_the_walrus` fixture) can only ever resolve `stack` to that one row, even if a request supplies a different `stack_id` in the URL: [2](#0-1) [3](#0-2) 

`CCMenuController`, however, is a `BaseController` subclass that overrides `stack` to bypass the scoped `stacks` relation entirely and resolve directly from `Stack.from_param!`, which searches the whole `stacks` table regardless of which stack (if any) the authenticated `ApiClient` is bound to: [4](#0-3) 

The only authorization gate on this action is `require_permission :read, :stack`, which merely checks that the token's `permissions` array contains the literal string `read:stack` — it never checks `current_api_client.stack_id` against the requested `params[:stack_id]`: [5](#0-4) 

`Stack.from_param!` performs an unscoped lookup by `repo_owner/repo_name/environment`: [6](#0-5) 

So the equality that should hold — `current_api_client.stack_id == stack.id` (when the token is stack-scoped) — is enforced in `BaseController#stack` but is broken specifically in `CCMenuController#stack`, exactly mirroring how `plotsAvailablePerSize` was enforced in `_mintTokens` but not in the parallel `mintTokenId` path.

### Impact Explanation
A token issued with `read:stack` permission and scoped to a single stack (e.g. via `CCMenuUrlController#client`, which mints an `ApiClient` for a specific user, or any admin-issued stack-scoped API client) can call `GET /api/stacks/*other_stack_id/ccmenu` for a stack it was never granted access to, and receive that stack's deploy/build status (last build status, label, activity, web URL). This is an unauthorized read of stack state for a stack outside the token's authorized scope — the token's authorization boundary (bound stack) is crossed without any additional credential. This matches the High-impact category of "unauthenticated/unauthorized read of stack state... via escalation beyond the token's granted scope."

### Likelihood Explanation
Any party holding a legitimately-issued, narrowly stack-scoped `read:stack` token (a routine, low-privilege credential explicitly designed to be restricted to one stack) can trivially exploit this by changing the `stack_id` path segment of the `ccmenu` route — no other secret, signature, or elevated permission is required. The bypass is a one-line consequence of the local `stack` override and is not covered by any existing test (`test/controllers/api/ccmenu_controller_test.rb` only tests same-stack access).

### Recommendation
Remove the private `stack` override in `Shipit::Api::CCMenuController` (and the routes.rb-driven `Stack.from_param!` shortcut in `Shipit::CCMenuUrlController` if applicable) and instead resolve the requested stack through the inherited `stacks`/`stack` helpers from `BaseController`, so the `current_api_client.stack_id` scoping is applied consistently on every action, the same way it is for `StacksController`, `HooksController`, and other API controllers.

### Proof of Concept
1. Create (or reuse) an `ApiClient` scoped to Stack A with permission `read:stack` (e.g. fixture `here_come_the_walrus`, `stack: shipit`).
2. Authenticate with that token's Basic Auth credentials against `GET /api/stacks/<Stack-B-owner>/<Stack-B-name>/<env>/ccmenu`, where Stack B is a different stack the token is not bound to.
3. `CCMenuController#authenticate_api_client` falls back to `super` (Basic Auth) and succeeds; `require_permission :read, :stack` passes because the token has `read:stack`; `stack` resolves Stack B via unscoped `Stack.from_param!`.
4. The response renders Stack B's CCMenu XML (build status/label/activity), even though the token is only authorised for Stack A — confirming the "stack a token authorises" vs. "stack it touches" binding is broken.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
