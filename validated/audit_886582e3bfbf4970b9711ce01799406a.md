### Title
Cross-organization webhook signature confusion allows forged commit status/push events on repositories outside the authenticating organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate an inbound webhook against solely from the unauthenticated payload field `repository.owner.login` (with fallback to `organization.login`), yet nothing in the signature check or in the event handlers subsequently constrains which repository/commit the payload is allowed to mutate. In a multi-organization Shipit deployment (`config/secrets.development.example.yml` documents this exact `github: { orgA: {...}, orgB: {...} }` layout), an attacker who holds the `webhook_secret` for one configured organization can pass `verify_signature` and then supply arbitrary `repository.full_name` / commit `sha` values that belong to a completely different organization's stacks.

### Finding Description
`verify_signature` derives the org used for HMAC verification purely from the JSON body: [4](#0-3) [2](#0-1) 

That check only proves the request was signed by *some* organization's `webhook_secret` known to Shipit — it never ties the verified organization to the repository the handlers subsequently act on. `Shipit::Webhooks::Handlers::Handler#repository_name` (used by `PushHandler`) reads a separate, unchecked field of the same attacker-controlled payload: [5](#0-4) 

Worse, `StatusHandler#process` doesn't even scope by repository — it looks up commits **instance-wide by SHA alone**: [3](#0-2) 
`Commit.create_status_from_github!` then records the forged state/context, which feeds Shipit's deploy/merge gating logic in `Shipit::Status::Group` and `MergeRequest`.

This is the binding break called out in the rules: *"an organization that authenticated versus the repository that is written."* Equality that should hold but doesn't:
`organization_whose_secret_verified_signature == organization_owning_the_repository/commit_being_mutated`
Before the attack: this equality trivially holds because only the legitimate org can produce a valid signature for its own repositories. After the attacker's forged request: the left side is org A (attacker's known/compromised secret) while the right side can be org B/C/... (any repository or commit hosted in the same Shipit instance), because `repository_owner` (used for verification) and `repository.full_name`/`sha` (used for mutation) are read from independent, unauthenticated JSON fields with no cross-check.

### Impact Explanation
An attacker who legitimately controls (or has compromised) one GitHub organization/App installation registered on a shared Shipit instance can:
- Forge `push` events naming a different org's repository, triggering `stack.sync_github` for stacks they don't own.
- Forge `status` events for an arbitrary commit `sha` across the entire installation (no repository scoping at all), setting `state: "success"` on commits belonging to unrelated stacks, which can satisfy required-status gating used by Shipit's deploy/merge safety checks — leading to an unauthorized deploy or merge decision on a repository the attacker has no legitimate access to.

This matches the Critical/High impact classes: "an unauthorized deploy, rollback or merge" via cross-organization/cross-repository writes reachable without any Shipit session, API token, or repository write access — only knowledge of one tenant's `webhook_secret`, which is exactly the kind of credential-scope confusion the rules ask to analogize from the reported "field acted on but not covered by verification" bug class.

### Likelihood Explanation
Requires the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration per `config/secrets.development.example.yml`) and requires the attacker to possess a valid `webhook_secret` for at least one of those organizations (e.g., as an org owner able to view/rotate their own GitHub App's webhook secret, or via leak of one tenant's secret). Given that is the only barrier — no Shipit account, session, or API token is needed — likelihood is moderate to high specifically in shared/multi-tenant deployments.

### Recommendation
- Cross-check the payload's `repository.full_name` / `organization.login` against the same `repository_owner` value that selected the `webhook_secret` used for verification, rejecting mismatches.
- In `StatusHandler` (and any other handler that queries by `sha` alone), scope commit lookups to repositories belonging to the verified organization, not the entire installation.
- Consider binding each `Repository`/`Stack` record to the specific `GitHubApp`/organization config it was created under, and enforce that binding in every webhook handler, not just at the controller layer.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. As a member/owner of `orgA` (with no relationship to `orgB`), retrieve `orgA`'s webhook secret from the GitHub App settings.
3. Craft a `status` webhook payload: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgA/anything"}, "sha": "<known sha of a commit belonging to orgB's stack>", "state": "success", "context": "ci/required-check"}`.
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(orgA_webhook_secret, raw_body)` and POST to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner` → `orgA`, verifies successfully against `orgA`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the commit in `orgB`'s stack regardless of the verified org — and records the forged `success` status, potentially unblocking `orgB`'s merge/deploy gating despite the attacker having no access to `orgB`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
