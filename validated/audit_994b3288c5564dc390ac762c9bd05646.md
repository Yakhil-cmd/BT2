### Title
Unallowlisted `GEM_HOME`/`BUNDLE_GEMFILE` injection via PR label name (uppercased) reaches `Command#start`/`PTY.spawn` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the deploy/task environment with no key allowlist, and that hash flows unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Command#unbundled_env`, which is merged last (i.e. highest priority) before `PTY.spawn`. An attacker who can label their own PR (granted in this audit's threat model) can therefore inject security-sensitive environment variable keys such as `GEM_HOME` or `BUNDLE_GEMFILE` into every command Shipit executes for that review stack.

### Finding Description
The broken binding: the set of environment variable keys reaching `PTY.spawn` for a review-stack task should equal `{SHIPIT_*, GITHUB_*, ENVIRONMENT, machine.environment keys from shipit.yml, task.env}` — i.e., only host- and repo-config-defined keys. Instead it equals that set **union** `{label_name.upcase for every label on the PR}`, because: [1](#0-0) 

`ReviewStack#env` takes `pull_request.labels` (persisted verbatim from the webhook body by `LabelCapturingHandler#capture_labels`, `pull_request.update!(labels: params.pull_request.labels.map(&:name))`) and merges `{label_name.upcase => "true"}` for each label with no allowlist: [2](#0-1) 

That result becomes part of `@stack.env`, which `TaskCommands#env` merges early, followed by hardcoded keys, `deploy_spec.machine_env` and `@task.env` — none of which reference `GEM_HOME`/`BUNDLE_GEMFILE`, so an injected key survives unless the shipit.yml explicitly redefines the same key: [3](#0-2) 

The merged env hash is passed as `Command.new(command_line, env:, chdir:)` for both `install_dependencies` and `perform` steps: [4](#0-3) 

Inside `Command`, `@env` is stringified and merged last, on top of `BASE_ENV` (derived from `Bundler.unbundled_env`, which typically strips/nils Bundler-related vars), so the attacker-injected key wins and is what actually reaches `PTY.spawn`: [5](#0-4) [6](#0-5) 

Existing guards don't stop this: `EnvironmentVariables#permit` requires an explicit `variable_definitions` allowlist and raises `NotPermitted` for disallowed keys, but it is never invoked on `ReviewStack#env`/`stack.env`; it's only used for `interpolate`-style whitelisting elsewhere, not on this path: [7](#0-6) 
No `params` schema, controller filter, or model validation constrains label *content* against a reserved keyword list — `LabelCapturingHandler` only validates types (`String`), not values: [8](#0-7) 

The value written is always the literal string `"true"`, not an attacker-chosen string — this weakens (but does not eliminate) the impact described in the question, because the attacker cannot set `GEM_HOME` to an arbitrary path directly. However, since the env value `"true"` is a valid *relative* path/filename, and the attacker fully controls the checked-out repository content for their fork/branch (the `chdir` for `Command#start` is the task's working directory, i.e., the checked-out PR code), the attacker can commit a file or directory literally named `true` in their repo (e.g. a malicious `Gemfile`-equivalent for `BUNDLE_GEMFILE=true`, or a fake gem tree for `GEM_HOME=true`) to make the fixed value actionable. This still constitutes an environment-variable injection with no allowlist reaching the spawned process, matching the target invariant ("the `machine.environment` step inherits no fork-controllable key such as `GEM_HOME`") is indeed violated.

### Impact Explanation
An unprivileged fork PR author (per the audit's granted capability to label their own PR and control fork content) can force every subsequent Shipit-executed command for their own review stack (dependency install, deploy steps, task steps) to run with an attacker-chosen environment key set to `"true"`. Combined with attacker-controlled repository content (a file/dir named `true`), this is sufficient to redirect gem/bundler resolution (`BUNDLE_GEMFILE`, `GEM_HOME`) to attacker-supplied code that gets evaluated by Ruby/Bundler as part of routine dependency installation, i.e., Remote Code Execution on the Shipit deploy host via `Command`/`PTY.spawn`. The blast radius is scoped to the attacking repository's review stack (the injected keys only affect that stack's `env`), but it is fully repeatable per-PR and per-label, and any review-stack-enabled repository (regardless of `allow_all` vs. `allow_with_label`) that lets the attacker's fork have a labeled, capturable PR is affected.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and the attacker's PR must reach `LabelCapturingHandler#capture_labels` (any state that creates/tracks a `Shipit::PullRequest` for the stack). Per the audit's stated threat model, the attacker is assumed able to label their own PR and control full fork content — under that assumption the attack cost is minimal (one label + one committed file named `true`) and fully repeatable. In a real, unmodified GitHub deployment, adding a label to one's own PR against an upstream repo typically requires triage/write permission on the base repo, which would substantially reduce real-world likelihood outside this audit's assumptions.

### Recommendation
Restrict `ReviewStack#env`'s label-to-env-var mapping to an explicit allowlist of permitted keys/prefixes (e.g. require a configured prefix such as `LABEL_` or run the resulting hash through `EnvironmentVariables#permit` with a strict, non-security-sensitive allowlist), and additionally block reserved/security-sensitive names (`GEM_HOME`, `BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD`, `PATH`, `RUBYLIB`, etc.) from ever being settable via labels, regardless of allowlist.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (add)
test "#env does not allow labels to inject security-sensitive keys like GEM_HOME/BUNDLE_GEMFILE" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_home", "bundle_gemfile"]

  env = stack.env

  # Binding under test: env keys reaching the process must equal the
  # allowlisted set (ENVIRONMENT, LAST_DEPLOYED_SHA, GITHUB_*, DEPLOY_URL)
  # and must NOT include fork-controllable security-sensitive keys.
  refute env.key?("GEM_HOME"), "label injected GEM_HOME into stack.env"
  refute env.key?("BUNDLE_GEMFILE"), "label injected BUNDLE_GEMFILE into stack.env"
end

# test/lib/shipit/task_commands_test.rb (add)
test "#env propagates label-injected GEM_HOME through to Command#unbundled_env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_home"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["GEM_HOME"]

  command = Shipit::Command.new("echo ok", env: env, chdir: ".")
  assert_equal "true", command.unbundled_env["GEM_HOME"]
end
```
Both assertions demonstrate the equality break: `env["GEM_HOME"]` (attacker-controlled key, from a PR label) reaches `Command#unbundled_env["GEM_HOME"]`, the exact hash passed to `PTY.spawn`, with no allowlist rejecting the key.
