This confirms the exploitable binding mismatch. Now I have sufficient evidence to write the finding.

The key mechanics:

- `WebhooksController#verify_signature` picks the HMAC secret to verify against using `repository_owner`, computed solely from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) .
- In a multi-org Shipit deployment, each GitHub organization has its own distinct `webhook_secret`, looked up via `Shipit.github(organization:)` / `github_app_config` [3](#0-2) , exactly as documented for "Using Multiple Github Applications" [4](#0-3) .
- Once the signature check passes, the *entire raw JSON body* is dispatched to handlers, and those handlers independently resolve which `Repository`/`Stack`/`Team` to act on using a **different** field of the same payload: `payload.dig('repository', 'full_name')` in `Handler#repository_name` [5](#0-4) , or `params.organization.login` in `MembershipHandler#find_or_create_team!` [6](#0-5) .
- Nowhere is `repository.owner.login`/`organization.login` (the field bound to secret selection) cross-checked against `repository.full_name` or the team's `organization` (the fields that determine what gets written). An admin who legitimately controls their own org's GitHub App installation (and thus knows that org's `webhook_secret`) can therefore forge a fully self-signed webhook whose `organization.login`/`repository.owner.login` says "my-org" (used only to pick the verification secret) while `team.organization`/`repository.full_name` names a victim org/repo tracked by the same Shipit instance.

This breaks the binding "organization that authenticated versus the repository/team that is written," matching the requested analog class from the Audius report (a validated field diverging from the field actually acted upon).

### Title
Webhook signature verification organization is not bound to the payload's target repository/team, enabling cross-organization writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which org's `webhook_secret` to verify the HMAC signature against using `repository.owner.login`/`organization.login`, but the handlers that actually act on the payload (`Handler#repository_name`, `MembershipHandler#find_or_create_team!`) use unrelated fields of the same JSON body (`repository.full_name`, `team.organization`) to decide what `Stack`/`Repository`/`Team` to mutate. Because nothing cross-validates these fields, an attacker who legitimately controls a GitHub App installation on their own organization (and therefore knows that org's `webhook_secret`) can self-sign a webhook payload whose "authenticating" org field points to their own org while the "target" field names a different, victim organization's repository or team tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the signing org exclusively from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to fetch the corresponding `GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`, then HMAC-verifies the raw body against that secret [7](#0-6) . This design is intended for the documented multi-org configuration where each org has its own app/secret [4](#0-3) , resolved through `Shipit.github_app_config` [8](#0-7) .

Once verification succeeds, `create` parses the full body and dispatches it to registered handlers unmodified [9](#0-8) . Handlers determine *which* stack/repo/team to modify from separate fields:
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` to look up the `Repository`/`Stack` to sync [5](#0-4) .
- `MembershipHandler#find_or_create_team!` reads `params.team.id` and stamps `team.organization = params.organization.login` to create/find a `Team`, then adds/removes the named `member` from it via `team.add_member`/`team.members.delete` [10](#0-9) .

Because the HMAC signature only proves "this body was signed with organization X's secret," not "the `repository.full_name`/`team.organization` inside this body belongs to organization X," an attacker holding org X's webhook secret (a legitimate, unprivileged capability for anyone administering their own org's installed GitHub App) can set `repository.owner.login` (or `organization.login`) to X while setting `repository.full_name`/`team.id`/`team.organization` to reference a victim org Y's stack or team, then sign the whole payload with X's secret. Verification succeeds because it only checks the signature against X's secret, and the mismatch between "authenticating org" and "target org/repo" is never checked.

### Impact Explanation
Through the `membership` event this allows an attacker to add an arbitrary GitHub login as a member of any `Team` known to the Shipit instance, including teams referenced by `Shipit.github_teams` for the `oauth.teams` authorization gate used in `User#authorized?` and `Authentication#force_github_authentication` — i.e., escalation into `Shipit.github_teams` authorization, letting an otherwise-unauthorized GitHub identity gain access to the Shipit UI/API for stacks belonging to a different organization. Through the `push`/`status`/`check_suite`/`pull_request` events, it lets the attacker trigger `sync_github`, forced status/check-run refreshes, or pull-request-state mutations against an arbitrary tracked stack belonging to another organization on the same multi-tenant Shipit instance, without ever needing that victim organization's real webhook secret.

### Likelihood Explanation
This requires a Shipit deployment configured with the documented multi-organization GitHub App setup, and an attacker who administers at least one of the configured organizations (and thus has legitimate access to that organization's own `webhook_secret`) — a realistic and unprivileged-relative-to-the-victim-org scenario in shared/multi-tenant Shipit installations, since no additional authentication or session is required beyond signing an HTTP POST to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the signature, re-derive the "signed" organization and cross-check it against every organization-identifying field actually consumed by handlers (`repository.full_name`'s owner segment, `team.organization`/`organization.login`), rejecting the request (422) if they diverge. Alternatively, have each handler take the already-verified `repository_owner`/`organization` as an explicit trusted parameter and validate that `repository.full_name` and `team.organization` are consistent with it before performing any lookup/mutation.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per docs/setup.md multi-app section).
2. As an administrator of `attacker-org`'s GitHub App, craft a `membership` webhook payload:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-handle" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
   Note `repository.owner.login` = `attacker-org` (used only for signature-secret selection) while `organization.login` = `victim-org` (used by `MembershipHandler` to create/attribute the `Team`).
3. Sign the raw JSON body with `attacker-org`'s `webhook_secret` (`sha1=` HMAC per `GitHubApp#verify_webhook_signature` [11](#0-10) ) and send it as `X-Hub-Signature` with `X-Github-Event: membership` to `/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and verifies successfully because the signature does match `attacker-org`'s secret [1](#0-0) .
5. `MembershipHandler#find_or_create_team!` creates/updates a `Team` stamped `organization: 'victim-org'` and `team.add_member` adds `attacker-handle` to it [10](#0-9) , without ever needing `victim-org`'s real webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
