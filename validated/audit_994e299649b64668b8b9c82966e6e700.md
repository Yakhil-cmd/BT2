### Title
Front-running window during address definition change lets a removed co-signer drain a shared/multi-authority address before the change stabilizes - (File: `validation.js`, `storage.js`)

### Summary
Obyte's analog to a Gnosis/Allo-style "pool manager list" is a **shared address** whose spending authority is expressed as an `oscript` definition (e.g. `["or", [["address","A"],["address","B"]]]`). Removing a co-signer/manager from such an address is done by posting an `address_definition_change` message that swaps in a new (stricter) definition for that address. Because the new definition is only enforced once the change unit is **stable**, the outgoing co-signer can front-run the owner by broadcasting a payment signed under the still-valid **old** definition and get it included/stabilized first, draining the address before the removal takes effect — the exact bug class described in the Sherlock report (untrusted manager front-runs removal to empty the pool).

### Finding Description
Spending authorization for any address is resolved against its *currently effective, stable* definition, looked up via `storage.readDefinitionChashByAddress`/`readDefinitionByAddress`, which explicitly falls back to the previous definition until a definition-change unit is stable: [1](#0-0) 

The validation code that is supposed to prevent an address from acting on outdated state, `checkNoPendingChangeOfDefinitionChash`, only blocks **that same author** from sending after submitting his own pending keychange (and even then only under specific serial/nonserial conditions) — it does not, and cannot, prevent a *different* co-signer holding a still-valid signing path in the old "or"/"and" definition from spending in parallel while the definition-change unit is unstable: [2](#0-1) 

The comment left in `handleDuplicateAddressDefinition` explicitly acknowledges this exact race pattern is a known, unresolved risk in the codebase: [3](#0-2) 

Shared addresses composed of multiple member addresses (the ocore analog of "pool managers") are built and validated with arbitrary `or`/`and`/`r of set` combinations of member addresses in `wallet_defined_by_addresses.js`: [4](#0-3) 

Because DAG stabilization (main chain index advance + multiple confirming units) takes measurable time, an untrusted co-signer who anticipates or observes the pending `address_definition_change` unit (visible in the DAG before it is stable) can immediately compose and broadcast a payment from the shared address using his own authentifier path in the *old* definition. Since `readDefinitionByAddress` continues to resolve to the old definition until the change is stable, this spend validates successfully and can double-spend/drain the address before the owner's removal becomes effective.

### Impact Explanation
This allows a co-signer who is being removed from a shared/multi-signature address to unilaterally and unauthorizedly withdraw all funds from that address during the stabilization window of the definition-change unit, resulting in concrete unauthorized spending / fund loss — analogous to the pool-draining impact in the original report.

### Likelihood Explanation
Any shared address using an `or`-style definition (common pattern for "any of N managers can spend") where an untrusted party is later demoted is exposed. The attack requires no special access beyond being a legitimate signer under the current (soon-to-be-revoked) definition, and DAG unit propagation/stabilization delay gives a realistic window to front-run.

### Recommendation
- When composing a definition change intended to remove a party's spending rights, do not rely on eventual stabilization alone; require that funds first be moved or spending be paused via a mechanism that takes effect at authorship time (e.g., requiring the being-removed party's cooperation to move funds, or spending down the balance) rather than trusting the old definition's authority window.
- Consider adding a validation rule that flags/rejects payments spending from an address that has a pending (unstable) `address_definition_change` when the payment is signed via a definition path that is being removed, similar in spirit to `checkNoPendingChangeOfDefinitionChash`, but generalized to also restrict conflicting co-signers rather than only the same author.
- Document this risk prominently for multi-sig/shared address users so that definition changes intended to remove authority are treated as untrusted until stable, and balances are proactively minimized beforehand.

### Proof of Concept
1. Owner and Manager B are both authorized signers of shared address `S` with definition `["or", [["address","ManagerA"], ["address","ManagerB"]]]`.
2. Owner decides Manager B is untrusted and composes/broadcasts an `address_definition_change` unit for `S` setting a new definition `["address","ManagerA"]` only (via `composer.composeDefinitionChangeJoint`, see `composer.js:85-87`).
3. Before that change unit becomes stable, Manager B observes it in the DAG and immediately composes and broadcasts a `payment` unit spending all of `S`'s balance to his own address, authenticated via the `["address","ManagerB"]` branch of the *still-current* stable definition.
4. `validation.js`'s `checkNoPendingChangeOfDefinitionChash` does not block Manager B's unit (it only restricts the author of the pending change, i.e. `S` sending under its own authorship), and `storage.readDefinitionByAddress` still resolves `S`'s effective definition to the old `or` definition because the change is not yet stable.
5. Manager B's draining payment stabilizes before or independently of the definition-change unit, and the funds are unrecoverable — reproducing the same "attacker front-runs manager removal to empty funds" scenario as the original report.

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}
