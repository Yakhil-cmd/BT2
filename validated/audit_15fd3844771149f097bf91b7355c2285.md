### Title
Recipient-Is-Vault Self-Transfer in `redeem` Desynchronizes `assets` From Real Balance, Enabling Share-Price Manipulation That Dilutes Other Depositors - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`redeem` accepts an arbitrary `recipient` and never checks that it differs from the vault's own address, unlike `transfer`, which explicitly forbids sending shares to `current-contract`. If a caller redeems shares with `recipient` set to the vault's own principal, `send-underlying` performs a self-transfer of the underlying token (net balance change of zero) while the vault still decrements its internal `assets` accounting variable as if the tokens left the contract. This desynchronizes the accounted `assets` value from the vault's real token balance, corrupting the shared exchange-rate calculation (`convert-to-shares-preview` / `convert-to-assets-preview`) used by every subsequent depositor and redeemer.

### Finding Description
`redeem` burns the caller's shares, calls `send-underlying` to move `inkind` underlying tokens to `recipient`, and unconditionally reduces the `assets` data-var by `inkind`: [1](#0-0) 

`send-underlying` transfers the underlying token from the vault (`tx-sender` under `as-contract?`) to `account`: [2](#0-1) 

If `account` (i.e. `recipient`) equals `current-contract`, this is a self-transfer: the vault's real underlying balance is unchanged (tokens leave and return to the same principal), yet `var-set assets (- current-assets inkind)` still fires, permanently understating `assets` relative to the real balance held. No precondition in `redeem` rejects `recipient == current-contract`. By contrast, the token `transfer` function explicitly guards against sending shares to the vault itself: [3](#0-2) 

This shows the developers were aware self-referencing the vault address is unsafe for share transfers, but the same guard is missing from `redeem`'s `recipient` parameter.

The corrupted `assets` variable feeds directly into `total-assets` / `total-assets-preview`, which is the numerator used by every deposit/redeem to compute the exchange rate between shares and underlying: [4](#0-3) 

Because the redeem operation burns shares and applies the fair-value formula (`inkind = amount * ta / ts`) to decrement `assets`, but the tokens are not actually removed, the ratio of real backing to accounted `assets` increases: remaining outstanding shares are now backed by more real value than the ledger records. Any principal (the attacker or anyone else) that deposits afterward receives shares computed against the deflated `ta`, i.e. more shares per unit of real underlying than is fair, diluting every other existing shareholder's claim on the vault's real assets — this is a shared exchange-rate/accounting state primed by one caller and consumed by all subsequent depositors and redeemers, not just the attacker's own position.

The same pattern (`assets` data-var, `redeem`, `send-underlying`, missing `recipient != current-contract` check) is present identically in the other vault instances: `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`.

### Impact Explanation
Once `assets` is desynchronized below the real balance, an attacker can immediately deposit underlying tokens and mint shares priced against the artificially low `total-assets-preview`, receiving more shares than the fair-value formula intends. This inflates the attacker's claim on the vault's real backing at the expense of all other depositors, who will subsequently redeem for less underlying than they are entitled to relative to their true deposit. This is theft of principal (not merely yield) from other liquidity suppliers via a manipulated shared exchange rate, and can be repeated to progressively drain value from the pool — landing in the Critical impact class (theft of user funds at rest / protocol insolvency risk for the share-pricing invariant).

### Likelihood Explanation
The attack requires no privileged access: any holder of vault shares can call `redeem` with `recipient` set to the vault's own contract principal, since no such check exists. It can be combined in the same transaction with a follow-up `deposit` to immediately mint shares at the manipulated price, making it a straightforward, single-block, permissionless sequence.

### Recommendation
Add an explicit guard in `redeem` (and any other function accepting a `recipient`/`to` address that results in `send-underlying`) rejecting `recipient == current-contract`, mirroring the existing check already present in `transfer`:
```
(asserts! (not (is-eq current-contract recipient)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
```
Apply this fix consistently across all vault contracts (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`).

### Proof of Concept
1. Attacker deposits `D0` underlying into `v0-vault-stx`, receiving `S0` shares at the current fair `ta/ts` ratio.
2. Attacker calls `redeem(amount=X, min-out=0, recipient=current-contract)` (the vault's own principal).
   - `ft-burn?` burns `X` of attacker's shares.
   - `send-underlying` self-transfers `inkind = X * ta/ts` tokens from the vault to the vault — real balance unchanged.
   - `var-set assets (- current-assets inkind)` reduces `assets` by `inkind`, even though no tokens actually left.
   - Result: `ta_accounted` shrinks while `ta_real` stays constant; `ts` shrinks by `X`. Remaining shares are now backed by proportionally more real value than the ledger reflects.
3. In the same or next transaction, attacker (or an accomplice) calls `deposit(amount=D1, ...)`. `convert-to-shares-preview` computes shares against the now-deflated `ta_accounted`, minting more shares than the pre-attack fair ratio would allow for `D1`.
4. Attacker redeems these newly minted shares for underlying; because system-wide accounting never reconciled the earlier self-transfer, other original depositors' shares are now worth less real underlying than before, transferring value to the attacker.
