Based on the investigation, the strongest reachable analog to the Loot.sol vesting-duration TOCTOU pattern in this engine is a trust-binding break in the GitHub OAuth login flow: the session identifier that existed *before* authentication is never invalidated when the GitHub identity is bound to it *after* authentication succeeds.

### Title
Session Fixation via GitHub OAuth Callback Not Rotating Session ID - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
The `GithubAuthenticationController#callback` action authenticates a user via GitHub OAuth and then writes `session[:user_id]` into the *existing* Rack session without ever calling `reset_session` (or otherwise rotating the session identifier). An unprivileged attacker who can plant a known session cookie in a victim's browser (a session fixation setup, e.g. via a subdomain cookie, XSS-adjacent cookie injection, or any means of pre-establishing a session id) can force the victim through the OAuth flow, and afterwards reuse the same, now-authenticated, session id to access the application as the victim.

### Finding Description
The equality that should hold is: `session id used for pre-auth (anonymous) state` == `session id retired once a GitHub identity is bound`. Instead the engine keeps the same session id across the trust boundary: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)

  # We need to set this so that the /events and /sidekiq endpoint
  # which leverage `UserRequiredMiddleware` will recognize the user
  # is authenticated.
  session[:authenticated] = true

  redirect_to(return_url)
end
``` [1](#0-0) 

`sign_in_github` binds the verified GitHub identity to a `User` record and stores its `github_access_token`: [2](#0-1) 

No `reset_session` call is made before or after this assignment — contrast with `logout`, which does call `reset_session`: [3](#0-2) 

Once `session[:user_id]` is set, `Authentication#current_user`/`#find_current_user` treats any request carrying that session id as the logged-in user, with no secondary binding (such as the session id itself) verified against the login event: [4](#0-3) 

This is the same class of bug as the Loot.sol finding: a state transition (vesting duration update / authentication completion) occurs while a pre-existing, attacker-influenced artifact (a queued claim tx / a pre-set session id) is not invalidated, letting the attacker's earlier setup silently carry over the trust granted by the later, legitimate action.

### Impact Explanation
If an attacker can get a known session id into a victim's browser (session fixation) and then lure/force the victim to authenticate through `/github/auth/github` (e.g. via a phishing link that has the victim complete the real Shopify/GitHub OAuth login), the attacker's pre-planted session cookie becomes a fully authenticated Shipit session for the victim's account — including whatever `github_teams` authorization the victim has and access to `github_access_token`-backed actions. This matches the rules' explicitly enumerated High-severity impact: "session fixation / forced OAuth completion."

### Likelihood Explanation
Exploitation requires the attacker to have a mechanism to fixate a session id in the victim's browser before the victim completes OAuth (e.g., cross-subdomain cookie setting, a shared/misconfigured session-store scenario, or session id leakage) and to induce the victim to go through the login flow. This is a real but non-trivial precondition, and Rails' default session cookie is host/domain-scoped, which limits (but does not eliminate, depending on deployment/proxy/subdomain configuration) practical fixation vectors.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` immediately before establishing the new authenticated session (i.e., before `session[:user_id] = sign_in_github(auth)`), mirroring the pattern already used in `logout`. This rotates the session id at the trust boundary so that any pre-existing (potentially attacker-controlled) session id cannot be reused post-authentication.

### Proof of Concept
1. Attacker obtains or sets a specific session cookie value in the victim's browser (session fixation primitive, e.g., via a subdomain that shares the session cookie scope, or a session id disclosed by another channel).
2. Attacker sends the victim a link to `/github/auth/github` to initiate login.
3. Victim completes the real GitHub OAuth flow; `GithubAuthenticationController#callback` executes and sets `session[:user_id] = sign_in_github(auth)` on the *same* session id, without calling `reset_session`.
4. Attacker, already holding that session id/cookie, is now treated as the authenticated victim by `Authentication#current_user`, since `find_current_user` only checks `session[:user_id]` [5](#0-4) , gaining the victim's authorization and access to deploy/rollback actions gated behind `force_github_authentication`.
