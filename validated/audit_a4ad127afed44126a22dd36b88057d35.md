### Title
Webhook signing-organization binding does not match the repository being written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting multiple GitHub App configurations, one per organization, each with its own independent `webhook_secret`. When a webhook is received, `WebhooksController#verify_signature` picks *which* app/secret to verify the signature against using `params.dig('repository','owner','login')`. If that organization has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally — verification is skipped entirely for that org. Every webhook event handler, however, resolves the actual `Stack`/`Repository` to act on using a *different* JSON field from the same payload: `payload.dig('repository','full_name')`. Because these two fields are never cross-validated against each other, an unprivileged attacker can forge a raw HTTP POST to the shared, unauthenticated `/github/webhooks` endpoint that claims `repository.owner.login` = an organization with no webhook secret configured, while setting `repository.full_name` = a properly-secured, unrelated organization's repository.

### Finding Description
`Shipit.github(organization:)` returns a distinct `GitHubApp` instance per configured organization, each carrying its own `@webhook_secret` from `config[:webhook_secret]`. [5](#0-4)  Multi-org setups are an explicitly documented and supported configuration mode, and the shipped example secrets even leave `webhook_secret` blank/nil by default. [6](#0-5) [7](#0-6) 

`verify_webhook_signature` explicitly bypasses HMAC verification when no secret is set for the selected app: `return true unless webhook_secret`. [2](#0-1) 

`WebhooksController#verify_signature` selects which app/secret to validate against solely from `repository_owner`, itself computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a value inside the same unauthenticated request body being verified: [8](#0-7) 

Every event handler that acts on a repository instead uses `payload.dig('repository', 'full_name')` to locate the target `Repository`/`Stack`, e.g. the base `Handler#stacks`/`repository_name`, `PushHandler#process`, and the various pull-request handlers: [3](#0-2) [4](#0-3) [9](#0-8) 

Nothing in the controller or in `Handler` asserts that `full_name`'s owner segment equals `repository.owner.login` (the value used to pick the signing key). The binding that should hold — *the organization whose signature validated the request* == *the repository actually mutated by the request* — is broken: the attacker fully controls both fields independently in the raw POST body, and only one of them is tied to any cryptographic check (and even that check can be a no-op if that org has no secret).

### Impact Explanation
This allows cross-repository writes without any credential: an attacker who knows (or guesses) that one configured GitHub organization in a multi-org Shipit deployment has no `webhook_secret` set can forge webhook events (e.g. `push`, `pull_request`, `check_suite`, `membership`) that claim to originate from that unsecured org, but whose `repository.full_name` points at a *different*, properly-secured organization's stack. Depending on handler, this can trigger `stack.sync_github` (fetching/deploy pipeline state changes) for a foreign, secured repository, open/close/archive review stacks, or otherwise mutate state belonging to a repository the attacker has no access to and whose real GitHub App webhook secret they never possessed. This satisfies the "cross-repository writes" / unauthorized deploy-pipeline mutation impact bar, entirely from an unauthenticated network position (no Shipit session, no ApiClient token, no webhook_secret of the *target* org required).

### Likelihood Explanation
Likely in any Shipit deployment using the documented multi-organization GitHub App configuration where at least one configured organization omits `webhook_secret` (a state the shipped example configs actively demonstrate as valid). The webhook endpoint is public and unauthenticated by design (it exists specifically to receive unauthenticated GitHub callbacks), so the only barrier is guessing/observing which org lacks a secret and crafting a JSON body with mismatched `owner.login` / `full_name` — both directly attacker-controlled fields requiring no special access.

### Recommendation
Cross-validate that the organization used to select the verification key (`repository.owner.login` / `organization.login`) matches the owner segment parsed from `repository.full_name` before dispatching to any handler, and reject the request (422) on mismatch. Additionally, treat a missing `webhook_secret` for a configured organization as a misconfiguration to warn/fail loudly about rather than silently short-circuiting signature verification (`return true unless webhook_secret`).

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `OrgTwo` (no `webhook_secret`) and `OrgOne` (properly secured), as shown in the shipped fixture `test/dummy/config/secrets_double_github_app.yml`, and create a stack for `OrgOne/secured-repo`.
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/secured-repo" }
}
```
No `X-Hub-Signature` header is required to pass verification, because `Shipit.github(organization: 'OrgTwo').verify_webhook_signature` returns `true` unconditionally (no secret configured for `OrgTwo`).
3. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('OrgOne/secured-repo')` — the secured org's stack — and calls `stack.sync_github(expected_head_sha: 'deadbeef')`, mutating state for a repository the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
