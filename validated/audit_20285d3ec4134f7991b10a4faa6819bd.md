### Title
Webhook signature verified against `repository.owner.login` while every event handler acts on the independent `repository.full_name` field, allowing cross-organization forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from the same untrusted JSON body via `params.dig('repository', 'owner', 'login')`. However, every `Shipit::Webhooks::Handlers::Handler` subclass (push, status, check_suite, pull_request, etc.) resolves the target `Repository`/`Stack` using a *different* field of that same payload: `payload.dig('repository', 'full_name')` (see `Handler#repository_name`). Nothing in the codebase enforces that `repository.owner.login` and the owner segment of `repository.full_name` refer to the same organization. This breaks the trust binding: `organization that authenticated (owner.login → webhook_secret used) != repository that is written (full_name → Stack acted upon)`.

### Finding Description
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

- After the signature passes, `create` dispatches the raw JSON body to the matching handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

- Every handler resolves the stack/repository to act on via a **different** field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler`, `StatusHandler`, `check_suite_handler`, and the `pull_request/*` handlers all rely on this same `full_name`-based resolution (either through `Handler#stacks` or `Repository.from_github_repo_name(params.repository.full_name)`), e.g.: [4](#0-3) [5](#0-4) 

Because `verify_signature` only checks `owner.login`, and `full_name` is a free-form string elsewhere in the same JSON body, an attacker who legitimately controls a GitHub App/organization already configured in Shipit's multi-org `github:` config (i.e., they know their own org's real `webhook_secret`, requiring no Shipit credentials, session, or API token) can send a signed webhook where:
- `repository.owner.login = "attacker-org"` — makes `Shipit.github(organization: "attacker-org")` pick the attacker's own valid `webhook_secret`, so the HMAC check passes.
- `repository.full_name = "victim-org/victim-repo"` — an unrelated, already-registered Shipit `Stack`.

The signature check has no relation to `full_name`, so the forged event is accepted and dispatched to the handler that acts on `victim-org/victim-repo`.

### Impact Explanation
This lets an attacker who owns any one organization onboarded into Shipit's multi-org GitHub App config forge webhook events for a completely different, victim organization's stack, without ever needing a Shipit session, `ApiClient` token, or write access to the victim repository:
- Via the `status`/`check_suite` events, an attacker can inject fabricated commit statuses/check runs (`Commit#create_status_from_github!` / `StatusHandler#process`) onto a victim commit, making CI look green (`success`) when it never ran. `Status#enable_ci_on_stack` and `schedule_continuous_delivery` are triggered as a side effect, and `MergeRequest#all_status_checks_passed?` relies on exactly these fabricated `Status` records to decide whether continuous-delivery/merge-queue automation may proceed — i.e. this can enable an unauthorized deploy or merge on the victim's stack.
- Via `push`, the attacker can trigger `GithubSyncJob` against the victim `Stack`, forcing it to resync from GitHub with an `expected_head_sha` under attacker control, influencing which commit is considered "new"/deployable.

This satisfies the "unauthorized deploy/merge" bar in the rules, because the fabricated CI status is exactly the signal Shipit's merge/continuous-deployment automation trusts.

### Likelihood Explanation
Requires the attacker to control a legitimate but distinct organization/App entry already configured under Shipit's `github:` multi-org config (a realistic scenario for any Shipit instance serving multiple orgs/customers) and knowledge of only their own `webhook_secret` — no access to the victim's secret, session, or Shipit credentials is needed. The mismatch between `owner.login` (used for auth) and `full_name` (used for authorization/action) is a straightforward payload-crafting exercise once one legitimate webhook_secret is known.

### Recommendation
In `WebhooksController#verify_signature`, derive the organization used to select the `webhook_secret` from the *same* field the handlers use to resolve the target repository (`repository.full_name`'s owner segment), or, better, after verifying the signature, re-validate that `repository.full_name`'s owner matches `repository.owner.login` (and reject on mismatch) before dispatching to any handler. Alternatively, make all handlers resolve stacks by `owner.login` + repository `name` consistently with whatever field the signature check trusts, instead of `full_name`.

### Proof of Concept
1. Shipit is configured with two organizations in `config/secrets.yml`: `attacker-org` (attacker's own GitHub App, attacker knows its `webhook_secret`) and `victim-org` (already has a `Stack` registered, e.g. `victim-org/victim-repo`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-repo-commit-sha>",
  "state": "success",
  "context": "ci/travis",
  "description": "Forged green build",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using their own `attacker-org` webhook secret over the raw body, and sets `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `owner.login`) and successfully verifies the signature with the attacker's own secret.
5. `create` dispatches the parsed payload to `StatusHandler`, which finds the commit by `sha` (looked up globally by sha, not scoped by the verified organization) and calls `commit.create_status_from_github!(params)`, creating a fabricated `success` `Status` on the victim's commit — triggering `enable_ci_on_stack` / `schedule_continuous_delivery` on `victim-org/victim-repo`.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
