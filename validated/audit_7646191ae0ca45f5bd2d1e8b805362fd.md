### Title
Webhook signature verification is keyed off an attacker-controlled, per-organization "repository owner" field that is never bound to the repository actually mutated by the handler - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization config (and therefore which `webhook_secret`) to validate a webhook against using an unverified, attacker-controlled field taken from the still-unauthenticated JSON body. In a multi-organization Shipit deployment, if any one configured organization has no `webhook_secret` set (documented as optional), signature verification for that organization always succeeds. The organization used to select the verifier is never checked against the organization/repository that the event handlers actually act upon, breaking the binding: `organization that authenticated == repository that is written`.

### Finding Description
`repository_owner` is computed purely from the unauthenticated payload before any cryptographic check occurs: [1](#0-0) 

It is then used to select the `GithubApp` instance whose secret is used to verify the HMAC signature of the *entire* raw body: [2](#0-1) 

Crucially, `verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured: [3](#0-2) 

The webhook secret is explicitly documented as optional per organization, including in multi-org setups: [4](#0-3) 

Once "verified," `WebhooksController#create` dispatches the *entire attacker-controlled payload* to every registered handler for the event type, with no re-check that the payload's actual target repository belongs to the organization that was used to authenticate it: [5](#0-4) 

Handlers resolve the repository/stacks to act on from a *different* field of the same payload — `repository.full_name` — which is completely decoupled from the `repository.owner.login` used for signature-org selection: [6](#0-5) 

Worse, `StatusHandler` does not even scope by repository at all — it looks up commits globally by SHA: [7](#0-6) 

`PushHandler` and `CheckSuiteHandler` do scope through `Repository.from_github_repo_name(repository_name)`, but `repository_name` is read from `repository.full_name`, independent of the `repository.owner.login` field used for the security check: [8](#0-7) [9](#0-8) 

**Exploit path (no Shipit credentials required):**
1. Deployment operates Shipit with multiple GitHub organizations configured per `docs/setup.md`'s "Using Multiple Github Applications" section, and (as the docs mark it optional) organization `A` has no `webhook_secret` set while organization `B` (the real target) does.
2. An unprivileged attacker POSTs directly to `/webhooks` with `X-Github-Event: status` (or `push`/`check_suite`) and a JSON body where `repository.owner.login = "A"` and `repository.full_name = "B/target-repo"` (or, for `status`, any arbitrary `sha`).
3. `Shipit.github(organization: "A")` returns organization A's `GithubApp`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank — no valid signature is ever required.
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which creates a forged commit status on any commit in Shipit's database (`Commit.where(sha: params.sha)`), regardless of which org/repo it belongs to.

### Impact Explanation
Forged, unauthenticated GitHub events (commit statuses, pushes, check-suite completions) can be injected into any stack tracked by the Shipit instance, not just organization A's. Commit statuses gate deploy safety checks (`deployable_status`) and can be used to make an otherwise-blocked commit appear "green" to reviewers/automation, or to fabricate `check_suite` completions that drive `schedule_refresh_check_runs!`. Combined with `PushHandler`, an attacker can also force `GithubSyncJob` to run against an arbitrary `expected_head_sha` for any tracked stack. This crosses a repository/organization trust boundary using only network access to the public `/webhooks` endpoint, and can result in an unauthorized deploy being unblocked based on forged status checks.

### Likelihood Explanation
Requires a specific but documented and supported configuration: multiple organizations configured in `config/secrets.yml`, with at least one having no `webhook_secret` set (the docs list the webhook secret as "(optional)"). This is a realistic operational lapse rather than a theoretical one, since Shipit explicitly supports running with no webhook secret at all (single-org case) and does not enforce that all organizations in a multi-org deployment share a consistently-configured secret.

### Recommendation
- Do not let an unauthenticated field pick the verification key. Verify the signature against *all* configured organizations' secrets (or require a canonical binding, e.g., via a per-organization webhook path/token) rather than trusting `repository.owner.login`/`organization.login` from the body.
- Re-validate, after signature verification, that the authenticated organization matches the owner segment of `repository.full_name` used by handlers before dispatching.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is unset if any other configured organization does have a secret; require every organization to have a webhook secret configured, or fail closed.
- Scope `StatusHandler`'s `Commit.where(sha:)` lookup by the resolved repository, not just by SHA.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (with a `webhook_secret`, tracking stack `orgB/target-repo`).
2. As an unauthenticated attacker, send:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/target-repo"},
  "sha": "<real commit sha in orgB/target-repo>",
  "state": "success",
  "context": "ci/required-check",
  "created_at": "2026-09-01T00:00:00Z"
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `verify_signature` selects `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
4. `StatusHandler#process` creates a forged "success" status on the target commit in `orgB/target-repo`, satisfying deploy-gating checks that were never actually reported by GitHub or CI.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
