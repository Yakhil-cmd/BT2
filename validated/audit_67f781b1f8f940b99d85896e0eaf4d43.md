## Title
Webhook signature verification is bound to the wrong organization, allowing cross-organization webhook forgery — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook's `X-Hub-Signature` against by reading `repository_owner` straight out of the **unverified** JSON payload, while the actual repository/stack that is mutated by the handler is resolved from a **different, unrelated** field of that same unverified payload (`repository.full_name`). These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that gets written to" are not the same binding. This is a direct analog of the Sherlock report's root cause: a binding (there, "gas mechanism assumed" vs "gas mechanism actually used"; here, "org verified" vs "repo acted on") silently diverges, and the code trusts the wrong side of it.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`verify_signature` computes: [2](#0-1) 

`repository_owner` is taken directly from the raw JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`), before the signature has been validated. It is used only to pick which `Shipit.github(organization: ...)` app config (and its `webhook_secret`) to verify the HMAC against, in `lib/shipit/github_app.rb`: [3](#0-2) 

Note line 77: `return true unless webhook_secret` — verification is a no-op if the selected organization has no secret configured. Both shipped sample configs ship with `webhook_secret: null`: [4](#0-3) [5](#0-4) 

After (trivially) passing this check, `create` dispatches the **entire raw payload** to handlers: [6](#0-5) 

Every handler resolves the target `Stack`/`Repository` from a *different* payload field, `repository.full_name`, with no relation to `repository_owner`: [7](#0-6) 

So the equality that should hold — `organization whose webhook_secret authenticated the request == owner of the repository the handler writes to` — is never enforced. An attacker only needs `repository.owner.login` (used for signature selection) to point at any configured organization with a blank/absent `webhook_secret`, while `repository.full_name` (used for the actual write) points at a `Stack` belonging to any other, fully-secured organization.

### Impact Explanation
This lets an unprivileged, unauthenticated attacker forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `deployment_status`, `membership`, etc.) against repositories/stacks belonging to an organization it has no legitimate credentials for, as long as *any* other organization configured in the same Shipit instance has no `webhook_secret` set. Concretely this can:
- Trigger `GithubSyncJob` to sync forged commits/branch state into a protected stack's history (`push` handler resolves via `repository_name`, same `Handler#stacks` helper as above).
- Inject forged commit `status`/`check_suite` results that gate deploy safety checks used before a real deploy is allowed to run.
- Create/close/merge review-stack-triggering `pull_request` events for a repository the attacker has no access to.

This crosses the "cross-repository writes" / "unauthorized deploy" bar from the impact list, since it lets an outsider manipulate deploy-gating state (statuses, check runs, PR lifecycle) for a repository under a different, secured GitHub organization, purely by picking a spoofed `repository.owner.login` from a differently-configured org in the same instance.

### Likelihood Explanation
Requires only:
1. A multi-organization Shipit deployment (explicitly supported and documented — the sample secrets files list multiple orgs keyed by name).
2. At least one configured organization without a `webhook_secret` (the shipped example/test configs literally set `webhook_secret: null`, indicating this is not a rare configuration).
3. No authentication, session, `ApiClient` token, or GitHub write access needed — a single unauthenticated `POST /webhooks` request forges the event.

This is realistic in any Shipit install serving multiple orgs where not every org owner has bothered to register `webhook_secret` (it's optional per the code path, not enforced globally).

### Recommendation
Bind signature verification to the same repository the handlers act on, not a caller-supplied "owner" field decoupled from it:
- Derive the organization used to select `webhook_secret` from `repository.full_name` (the same field `Handler#repository_name` uses), not from a separately-read `owner.login`/`organization.login` field.
- Enforce `webhook_secret` as mandatory for every configured GitHub org (fail closed instead of `return true unless webhook_secret`), so a misconfigured/secret-less org can't be used as a "skeleton key" to authenticate payloads for a different org.
- After signature verification, re-validate that the `repository.full_name`'s owner matches the `repository_owner`/`organization.login` that was used to select the verifying secret, rejecting mismatches.

### Proof of Concept
1. Shipit instance configured with two orgs: `secure-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, e.g. copied from the shipped `secrets.development.shopify.yml` template).
2. `secure-org/protected-repo` has a Shipit stack tracking deploy-gating commit statuses.
3. Attacker sends, without any valid signature:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": {
    "full_name": "secure-org/protected-repo",
    "owner": { "login": "open-org" }
  },
  "sha": "<attacker-chosen sha of protected-repo>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "http://attacker.example"
}
```
4. `verify_signature` computes `repository_owner = "open-org"`, loads `open-org`'s `Shipit.github` app, calls `verify_webhook_signature`, which returns `true` immediately because `open-org`'s `webhook_secret` is blank.
5. `create` proceeds and dispatches the payload to the `status` handler, which resolves the target stack via `repository.full_name = "secure-org/protected-repo"` — a repository belonging to the fully-secured `secure-org` — and records the forged, attacker-controlled commit status against it, with no valid signature ever having been produced for `secure-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
