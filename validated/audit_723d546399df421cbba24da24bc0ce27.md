### Title
Webhook signature verified against attacker-chosen organization while handlers act on an unrelated `repository.full_name` — organization-authenticated ≠ repository-written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to validate an inbound GitHub webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body, then verifies the HMAC signature using that organization's secret. Once verification succeeds, `create` re-parses the same body and dispatches it to event handlers that independently resolve the target `Stack`/`Repository` from a *different* field in the same attacker-controlled body: `repository.full_name`. Because these two fields are never bound together by the signature check, a party who legitimately knows the webhook secret for organization A (i.e., they administer a repository/org that is itself onboarded to this Shipit instance) can forge a signed payload where `repository.owner.login` = "A" (to select and pass verification with A's secret) while `repository.full_name` = "B/victim-repo" (an unrelated organization/repo tracked by the same Shipit instance). The handler layer will act on the victim's stack.

### Finding Description
`verify_signature` computes the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), which is fully attacker-controlled content of the same HTTP request whose signature is being checked. `Shipit.github(organization:)` maps that string to a distinct `GitHubApp` instance carrying its own `webhook_secret`, per the multi-org config schema: [3](#0-2) 

After signature verification passes, `create` dispatches the *same raw body* to registered `Shipit::Webhooks::Handlers` classes: [4](#0-3) 

These handlers resolve the affected repository/stack using an entirely separate field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) 

The same pattern repeats in every pull-request handler (`opened`, `closed`, `reopened`, `labeled`/`unlabeled`, `label_capturing`), all of which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` independently of the organization used to validate the signature: [7](#0-6) [8](#0-7) 

The equality that should hold — "organization whose secret authenticated this signature" == "organization owning the repository the handlers write to" — is never enforced. The signature only proves the raw bytes were HMAC'd with *some* configured org's secret; nothing ties that org identity to `repository.full_name` used downstream. This is directly analogous to the audited bug class: a payload field that drives the trust decision (here, which secret validates the request) is disjoint from the payload field that drives the actual write action (here, which repository/stack is mutated), exactly the "organization that authenticated versus the repository that is written" binding called out in scope.

### Impact Explanation
An attacker who legitimately controls a repository/organization onboarded to the same shared multi-tenant Shipit instance (and therefore knows or can obtain that org's `webhook_secret`, since they configured the GitHub webhook themselves) can forge signed webhook deliveries that are verified under their own org's secret but whose `repository.full_name` targets any other tracked stack. Depending on the event type, this permits, without any Shipit session/API-token privilege on the victim org:
- `push` events: force `GithubSyncJob`/`stack.sync_github(expected_head_sha:)` on a victim stack — [9](#0-8) 
- `pull_request` events: create/archive/unarchive `ReviewStack`s belonging to a victim repository — [10](#0-9) 
- `status`/`check_suite`: inject commit statuses/check-run refreshes for a victim's tracked commits.

This is a cross-repository/cross-organization write triggered purely by controlling one tenant's webhook secret — no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is required.

### Likelihood Explanation
Requires the deployment to be configured with the multi-organization `github:` schema (multiple orgs, each with a distinct `webhook_secret`) sharing one Shipit instance — a documented, supported configuration. Any tenant admin who can register a webhook for their own org already knows that org's secret by design. No further privilege escalation is required beyond crafting a raw HTTP POST with a valid `X-Hub-Signature` for their own secret and a `repository.full_name` pointing at another tracked repository.

### Recommendation
Bind the two fields together before dispatch: after verifying the signature with the secret selected via `repository_owner`, re-derive the acting repository from the same trusted owner value (e.g., require `repository.full_name.split('/').first == repository_owner`, case-insensitively) or select the verifying organization from `repository.full_name`'s owner segment instead of the separate `repository.owner.login`/`organization.login` fields, so the same authenticated field drives both the secret selection and the target repository resolution.

### Proof of Concept
1. Deploy Shipit with multi-org config: org `attacker-org` (secret `S_A`) and org `victim-org` (secret unknown to attacker), both with repos onboarded as `Stack`s.
2. Attacker (owner of `attacker-org`, who set `S_A` when creating their own GitHub webhook) crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist on victim-org/victim-repo, e.g. an old commit>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner` = `"attacker-org"`, looks up `Shipit.github(organization: "attacker-org")`, verifies with `S_A` — succeeds.
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — a cross-organization write the attacker was never authorized to trigger.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
