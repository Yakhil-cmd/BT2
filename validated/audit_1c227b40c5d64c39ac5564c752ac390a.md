### Title
Unbounded HTTP server on `--http-bind` allows slowloris-style resource exhaustion that crashes the process and causes persistent sync denial - ([File: main.go])

### Summary
`git-sync`'s optional HTTP endpoint (`--http-bind`, used for liveness, `--http-metrics`, and `--http-pprof`) is served via a bare `http.Serve(ln, mux)` call with no `http.Server` timeouts configured. Any client able to reach this port can open many slow/idle connections (a classic L4 slowloris-style attack, analogous to the Prysm CL-2020-04 report), exhausting file descriptors or goroutines. When `http.Serve` subsequently fails, `git-sync` calls `os.Exit(1)`, terminating the *entire* process — including the independent sync loop — resulting in persistent denial of sync (analogous to "stops finality" in the original report, here "stops sync").

### Finding Description
The HTTP endpoint setup uses the zero-value `http.Server` semantics (no `ReadTimeout`, `ReadHeaderTimeout`, `WriteTimeout`, or `IdleTimeout`), which is a well-known Go footgun (slowloris exposure): [1](#0-0) 

Specifically:
- `net.Listen("tcp", *flHTTPBind)` creates the listener and `http.Serve(ln, mux)` is run in a goroutine with a default `net/http` `Server` that has no timeout hardening.
- The liveness handler (`/`) and, depending on flags, `/metrics` and `/debug/pprof/*` are all served unauthenticated on that same listener.
- Critically, if `http.Serve` returns an error (e.g., `accept tcp: too many open files` once file descriptors are exhausted by many concurrently-held slow connections), the code logs the error and immediately calls `os.Exit(1)`, killing the whole `git-sync` binary, not just the HTTP subsystem: [2](#0-1) 

Because the sync loop (`git.SyncRepo`) and the HTTP server run in the same process, an attacker who can reach `--http-bind` can force a full-process crash via file-descriptor/goroutine exhaustion, stopping the sync loop until the container/pod is restarted by its supervisor.

### Impact Explanation
This maps to "persistent sync denial," one of the explicitly accepted impacts. An attacker with only network reachability to the git-sync HTTP port (commonly bound for Kubernetes liveness probes and metrics scraping, sometimes exposed beyond localhost depending on deployment) can repeatedly crash the process, stalling git-sync's core function of keeping `--root`/`--link` up to date — directly analogous to the Prysm report where an L4 DDoS against P2P connectivity stalled finality. Depending on how the pod/deployment is configured (e.g., without a `Service` restricting access, or if `--http-bind` is set to `0.0.0.0:<port>` rather than `127.0.0.1`), this could be reachable well beyond the local pod network.

### Likelihood Explanation
Likelihood depends on the actual bind address and network exposure of `--http-bind`, which is operator-configured; the docs and e2e tests show it commonly bound to `:PORT` (all interfaces) for liveness/metrics/pprof purposes. No authentication is required to open connections to the endpoint, and slowloris-class attacks require only unprivileged network access and minimal attacker resources, making this a moderately likely but deployment-dependent DoS path.

### Recommendation
- Configure an explicit `http.Server` with sane `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, and `IdleTimeout` values instead of the bare `http.Serve` call.
- Consider limiting `MaxHeaderBytes` and setting `net.Listener` accept backlog / connection limits.
- Avoid calling `os.Exit(1)` on transient `http.Serve` errors that are unrelated to the sync loop's health; at minimum, distinguish fatal listener setup errors from recoverable runtime accept errors, and avoid crashing the whole process purely due to HTTP subsystem exhaustion.
- Document/encourage binding `--http-bind` to `127.0.0.1` by default when only used for local liveness probes, and require an explicit opt-in for broader exposure.

### Proof of Concept
1. Start `git-sync` with `--http-bind=:9376` (as done in `test_e2e.sh`, e.g. `e2e::expose_http`): [3](#0-2) 
2. From an attacker-reachable network position, open many TCP connections to port 9376 and send data extremely slowly (or not at all), holding connections open (slowloris).
3. Once the process's open file descriptor limit is exhausted, `net.Listener.Accept` inside `http.Serve` begins failing.
4. The goroutine at `main.go:890-894` logs the error and calls `os.Exit(1)`, terminating the entire `git-sync` process, including the independent sync loop, stopping all future syncs until the orchestrator restarts the container.

Note: I was not able to verify the exact default value/behavior of `--http-bind` (e.g., default empty vs. always-on, or whether any deployment guidance restricts it to loopback) from the indexed portions of `main.go`/`docs/`, since the flag's default declaration line wasn't retrieved in full; this should be confirmed by inspecting the complete flag declaration for `flHTTPBind` before treating network exposure as guaranteed in all deployments.

function e2e::expose_http() {
    GIT_SYNC \
        --git="/$SLOW_GIT_FETCH" \
        --period=100ms \
        --repo="file://$REPO" \
        --root="$ROOT" \
        --link="link" \
        &

    # do nothing, just wait for the HTTP to come up
    for i in $(seq 1 5); do
        sleep 1
        if curl --silent --output /dev/null http://localhost:$HTTP_PORT; then
            break
        fi
        if [[ "$i" == 5 ]]; then
            fail "HTTP server failed to start"
        fi
    done
