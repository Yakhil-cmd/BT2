Based on the code I was able to retrieve, there's a concrete analog to the oracle bug: a **verification binding mismatch** in Shipit's webhook signature checking, where the organization whose secret is used to *authenticate* a webhook is a different, attacker-controlled field than the repository/team that is actually *acted upon* by the handler.

### Title
Webhook signature is verified against an attacker-chosen organization while the handler acts on a different `repository`/`team` in the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a field read straight out of the untrusted, unauthenticated JSON body. The signature is checked only against that selected org's secret, but the handlers that actually mutate state (`GithubSyncJob`, `MembershipHandler`, etc.) act on a *different* field in the same payload (`repository.full_name`, `team`, `member.login`). In a multi-org Shipit deployment, if any configured organization has no `webhook_secret` set (an explicitly documented, "optional" configuration), an attacker can pick that unsecured organization for `repository_owner`/`organization.login` so the signature check trivially passes, while pointing `repository.full_name` / `team` / `member.login` at a different, secured organization's stack or authorization team.

### Finding Description
The signature verification binds **"organization that authenticated"** to **"organization named in `repository.owner.login` / `organization.login`"**: [1](#0-0) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `GitHubApp` config, and verification is delegated to it: [2](#0-1) 

Critically, `verify_webhook_signature` **returns `true` unconditionally when `webhook_secret` is blank** for that organization's config — and `webhook_secret` is documented as optional per-organization: [3](#0-2) 

Meanwhile, the actual write path used by handlers (confirmed by the controller's own test suite) keys off a *separate* field, `repository.full_name`, to find the `Stack`/`Repository` to act on, and off `team`/`member.login` to create `Membership` rows that feed directly into Shipit's authorization check: [4](#0-3) [5](#0-4) 

`Membership` records created this way feed `User#authorized?`, which is the sole gate for accessing the whole Shipit application when `Shipit.github_teams` is configured: [6](#0-5) [7](#0-6) 

The equality that should hold is: **organization whose secret validated the request == organization whose repository/team data the handler mutates**. Because `repository_owner` (used only to pick the verification secret) and `repository.full_name`/`team` (used to determine the actual write target) are independent, attacker-controlled fields inside the same unauthenticated JSON body, an attacker can satisfy the check with one organization's (weak/absent) secret while writing effects against another organization's stack or team membership.

### Impact Explanation
If any organization configured on the Shipit instance has no `webhook_secret` (a supported, documented configuration — not a misconfiguration outside the documented setup), an unauthenticated, unprivileged attacker can:
- Set `repository.owner.login` (or `organization.login`) to the unsecured organization to make `verify_signature` pass unconditionally.
- Set `repository.full_name`, `team`, and `member.login` to target a *different*, secured organization's `Stack`/`Team`.

This can be used to forge a `membership` event that adds the attacker's own (legitimately authenticated) GitHub identity to a `Team` referenced in `Shipit.github_teams`, escalating them into the authorization gate that otherwise restricts all engine access — matching the High-impact category "escalation into `Shipit.github_teams` authorization." It could also be used to forge `push`/`status`/`check_suite` events against a foreign stack (e.g., to influence `GithubSyncJob`, or falsify CI status/check-run state used to gate deploys).

### Likelihood Explanation
Requires only: (1) a multi-organization Shipit deployment where at least one configured org has `webhook_secret` unset — a state the docs explicitly allow — and (2) knowledge of that org's login plus the target org's team/repo names, all of which are public GitHub metadata. No GitHub App private key, `ApiClient` token, or Shipit session is needed to reach `/webhooks`, satisfying the "unprivileged attacker" requirement.

### Recommendation
Bind the field used for signature-secret selection to the same field(s) used for locating the affected `Stack`/`Team`/`Repository` — i.e., verify the signature using the secret of the organization that owns the `repository.full_name` / `team` actually being written, not a separately-controlled `repository.owner.login`/`organization.login` value. Additionally, do not silently `return true` when `webhook_secret` is blank for a given org config if any other configured org in the instance requires one; treat "no secret configured" the same for all orgs or fail closed.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.yml`: `SecureOrg` (has `webhook_secret` set) and `OpenOrg` (leaves `webhook_secret` nil, per the documented optional setting).
2. POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature` (or an arbitrary one), body:
```json
{
  "action": "added",
  "organization": { "login": "OpenOrg" },
  "team": { "id": 1, "name": "Shopify Developers", "slug": "developers", "url": "..." },
  "member": { "login": "attacker-login" }
}
```
3. `repository_owner` resolves to `OpenOrg` → `Shipit.github(organization: "OpenOrg")` → `verify_webhook_signature` returns `true` unconditionally (blank secret) per [8](#0-7) .
4. The `membership` handler processes the payload's `team`/`member` (belonging conceptually to `SecureOrg`'s required team), creating a `Membership` for `attacker-login`, as shown by the handler behavior exercised in [9](#0-8) .
5. Attacker logs into Shipit via normal GitHub OAuth as `attacker-login`; `User#authorized?` now returns true because of the forged `Membership`, bypassing the `Shipit.github_teams` gate.

**Caveat:** I could not retrieve the source of `Shipit.github`'s organization-lookup logic or `app/models/shipit/webhooks/handlers/membership_handler.rb` directly (tool calls for those files failed before I ran out of iterations); the membership-creation behavior above is inferred from `test/controllers/webhooks_controller_test.rb` rather than the handler source itself. I recommend a Devin session with full file access to confirm the exact matching logic in `Shipit.github` (organization dispatch) and `MembershipHandler`/`Team.find_or_create_by_handle` before treating this as fully confirmed.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

      ].join(' '))
    end

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
