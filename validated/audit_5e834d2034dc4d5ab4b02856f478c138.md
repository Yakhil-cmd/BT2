### Title
Membership webhooks are authenticated against `repository.owner.login`/`organization.login` while `find_or_create_team!` trusts the same JSON body's `organization.login` for a different tenant, letting a no-secret org's signature authorize cross-org `Team`/`Membership` writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks the signing organization from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  before the payload is validated against any handler schema, and `verify_webhook_signature` trivially returns `true` when the selected org has no `webhook_secret` configured [2](#0-1) . `MembershipHandler` never reads `repository` at all - it derives the mutated `Team`'s `organization` purely from `params.organization.login` in the same raw JSON body [3](#0-2) , so an attacker can supply a synthetic `repository.owner.login` pointing at an org with no secret (satisfying signature checks trivially) while `organization.login` in the same request names the victim org whose `Team`/`Membership` rows get written.

### Finding Description
The broken binding is:
`verified_org (params.dig('repository','owner','login') || params.dig('organization','login'))` should equal `mutated_org (params.organization.login used by MembershipHandler#find_or_create_team!)`.

They are not enforced to be equal. The controller's `repository_owner` helper is evaluated on the raw, attacker-controlled JSON before any `ExplicitParameters` schema validation runs [4](#0-3) [5](#0-4) . Nothing rejects an extraneous `repository` key on a `membership` event, so an attacker can add one purely to steer which org's `Shipit.github_app` config (and therefore which `webhook_secret`) is used to validate the signature, while the actual mutation performed by `MembershipHandler` is driven by the separate `organization.login` field [6](#0-5) .

Exploit request: attacker sends `POST /webhooks` with header `X-Github-Event: membership`, body containing:
- `repository.owner.login = "attacker-controlled-org"` (an org configured in Shipit with no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header) [7](#0-6) 
- `organization.login = "victim-org"`
- `team = {id, name, slug, url}` and `member.login` of the attacker's choosing
- `action = "added"` or `"removed"`

`verify_signature` resolves `repository_owner` to `"attacker-controlled-org"`, loads that org's `GitHubApp`, and short-circuits to `true` because that org has no secret. `MembershipHandler#process` then runs unmodified: `find_or_create_team!` creates/finds a `Team` scoped to `organization: "victim-org"` [3](#0-2) , and either adds (`team.add_member(member)`) or removes (`team.members.delete(member)`) a `Membership` row for a `User` resolved solely by `params.member.login` [8](#0-7) . These rows are exactly what `User#authorized?` consults: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) .

None of the existing guards catch this: `drop_unhandled_event` only checks the event *name*, not payload contents [10](#0-9) ; the `ExplicitParameters` schema for `MembershipHandler` requires `organization.login` but places no constraint tying it to `repository.owner.login`, and does not even declare/forbid a `repository` key [6](#0-5) ; `verify_signature` runs on raw `params` before schema validation and never cross-checks against the field the handler will actually use.

### Impact Explanation
This lets an attacker who controls (or names) any org configured in Shipit without a `webhook_secret` forge a fully "verified" webhook that mutates `Team`/`Membership` records belonging to an unrelated victim organization - a direct instance of "a payload for one repository/organization mutating another's ... team," which the rules classify as Critical. With `action=added` and `params.member.login` set to an account the attacker controls, this can directly satisfy `User#authorized?` for `Shipit.github_teams`-gated repositories, enabling that account to pass `require_permission!` checks and trigger deploys/rollbacks on victim stacks. With `action=removed` (the case asked about), the same divergence lets the attacker strip an arbitrary victim org's legitimate maintainer out of the authorizing team, denying their access - a cross-tenant integrity violation, though this specific action does not by itself grant the attacker deploy rights. The `Commit#deployable?`/`ignore_ci` short-circuit is orthogonal: it affects whether a *commit* clears CI, not whether the attacker becomes `authorized?`; it doesn't amplify a membership-removal event into an "attacker deploys code" outcome. The blast radius of the underlying signature/org divergence, however, is real and repeatable against any org lacking a webhook secret, and it directly forges Team/Membership state for a victim org.

### Likelihood Explanation
Preconditions: at least one org configured in `Shipit.github` without a `webhook_secret` (a config choice the attacker doesn't control but many multi-tenant installs may have for less-sensitive orgs), knowledge of a victim org's login and one existing/guessable `team.id`/`member.login` pair. No Shipit session, API token, or GitHub secret is required — only the ability to POST arbitrary JSON to `/webhooks` with a forged `X-Github-Event: membership` header. Attacker cost is minimal and the request is fully repeatable/scriptable against any victim org as long as some no-secret org exists in the config to anchor signature verification.

### Recommendation
Bind signature verification to the same organization field the handler will act on: after parsing/validating the payload against the handler's `ExplicitParameters` schema, verify the signature using the organization the handler actually consumes (e.g., `params.organization.login` for `membership`/`team`-scoped events, `repository.owner.login` only for repository-scoped events), and reject payloads that include a `repository` key inconsistent with (or irrelevant to) the event's declared schema. Additionally, treat "no `webhook_secret` configured" as a hard failure (log/alert and reject) rather than an automatic pass, or require all onboarded orgs to have a secret.

### Proof of Concept
```ruby
test "membership webhook signed via a no-secret org can mutate a different org's team" do
  Shipit.stub(:github, ->(organization:) { org_without_secret_app_for(organization) }) do
    payload = {
      action: 'removed',
      team: { id: 42, name: 'Ops', slug: 'ops', url: 'https://api.github.com/teams/42' },
      organization: { login: 'victim-org' }, # org actually mutated
      member: { login: 'victim-maintainer' }
    }.to_json

    # repository.owner.login points at an org with no webhook_secret configured
    forged = JSON.parse(payload).merge(
      'repository' => { 'owner' => { 'login' => 'no-secret-org' } }
    ).to_json

    membership = shipit_memberships(:victim_org_ops_membership) # pre-existing row for victim-org/ops/victim-maintainer

    post shipit.webhooks_path, params: forged,
      headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => 'sha1=deadbeef' }

    assert_response :ok
    # equality claimed broken: verified_org ('no-secret-org') != mutated_org ('victim-org')
    refute Shipit::Team.find_by(organization: 'victim-org', github_id: 42)
             .members.exists?(login: 'victim-maintainer'),
           "membership for victim-org team was mutated by a payload signed/authorized under a different org"
  end
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
