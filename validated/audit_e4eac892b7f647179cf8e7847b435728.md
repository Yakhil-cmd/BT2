### Title
Webhook Commit-Status Handler Writes Cross-Repository State Because It Never Checks the Authenticated Repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook by picking a `GitHubApp` (and thus a `webhook_secret`) keyed off an attacker-supplied field in the JSON body (`repository.owner.login` / `organization.login`), then HMAC-verifies the raw payload against that org's secret. [1](#0-0) [2](#0-1)  Once the signature check passes, event handlers process the same JSON body, but `Shipit::Webhooks::Handlers::StatusHandler` — unlike `PushHandler`, which correctly scopes to `Repository.from_github_repo_name(repository_name)` — never re-checks that the `repository` named in the payload matches the commit it mutates. [3](#0-2) [4](#0-3) 

### Finding Description
Shipit natively supports multi-tenant configurations where distinct GitHub organizations each have their own `GitHubApp`, `webhook_secret`, and `installation_id`, all funneled through a single shared `/github/webhooks` endpoint. [5](#0-4)  The `docs/setup.md` explicitly documents this "Using Multiple Github Applications" configuration, and `test/dummy/config/secrets_double_github_app.yml` exercises it in tests.

The equality the system is supposed to enforce is:
`organization authenticated by verify_signature (via repository_owner/webhook_secret) == repository/stack whose data is mutated by the handler`

`verify_signature` selects the verification secret using `repository_owner`, which is read from the *payload body itself*:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This proves only that *some* configured organization's secret produced a valid HMAC over the raw body — it does not bind the verified organization to the specific repository/commit that downstream code will act on. The generic `Handler` base class defines the correct binding pattern, deriving `repository_name` from `repository.full_name` and scoping `stacks` to that repository: `Repository.from_github_repo_name(repository_name)&.stacks`. [4](#0-3)  `PushHandler` uses this scoped `stacks` helper before mutating anything.

`StatusHandler`, however, breaks this binding entirely:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

It looks up `Commit` records **globally by `sha` alone**, with no reference to `repository_name`/`stacks` scoping and no cross-check against `repository_owner` — the very field that was used to select the signing secret. Any organization whose `GitHubApp` is configured in Shipit can produce a validly-signed `status` webhook (signed with its own legitimate `webhook_secret`) naming any `sha` value, and that status will be applied to whatever `Commit` row in the entire Shipit database happens to share that sha — regardless of which repository/stack actually owns it. Because SHA1 commit ids are content-derived and often predictable/public (mirrors, forks, shared base commits, or an attacker deliberately reproducing a target's tree/parent/author/committer metadata in their own controlled repository), an attacker who controls one onboarded organization's repository can trigger `commit.create_status_from_github!` for commits belonging to a stack/repository under a completely different, unrelated organization tracked by the same Shipit instance.

This is the direct structural analog of the reported bridge bug: the "discriminator" used to authorize the action (`repository_owner`, akin to `allowedDiscriminator1`, the "any bridge on this network" open scope) is broader than, and decoupled from, the specific resource (repository/stack, akin to a specific bridge contract) actually mutated by the handler.

### Impact Explanation
This allows an attacker who controls (or has push access to) any one organization/repository configured in a multi-tenant Shipit instance to write forged commit statuses onto commits belonging to a different organization's repository/stack, without ever needing that other organization's webhook secret, GitHub App credentials, or Shipit session. Forged commit statuses can flip a commit from non-deployable to deployable (`ci.require` checks in `shipit.yml` rely on `Status` records), potentially unlocking or triggering deploys for a repository the attacker does not control — a cross-repository, cross-tenant write and a step toward unauthorized deploys, matching the Critical "cross-repository writes"/"unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability requires: (1) a multi-organization Shipit deployment, which is a documented, supported and tested configuration, and (2) the attacker controlling one onboarded organization/repository while guessing or reproducing a target sha. Predicting or reproducing an exact sha for a specific target commit is nontrivial in general but becomes tractable for public repositories, forks, or shared history, and requires no privileged Shipit credentials — only ordinary GitHub push access to the attacker's own onboarded repo. This is a real, unprivileged-attacker-reachable path, though its practical trigger rate depends on sha collision/reproduction opportunities.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't already use the `stacks`/`repository_name` scoping helper), scope the `Commit` lookup to the repository named in the payload and cross-validate that `repository_owner` (used for signature verification) matches the repository actually being mutated, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of an unscoped `Commit.where(sha: params.sha)`. More generally, `verify_signature` should be reworked so the verified organization is explicitly re-checked against `repository.full_name`/`repository.owner.login` consistency before any handler executes, closing the gap between "who signed this" and "what this payload claims to be about."

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` (attacker-controlled repo) and `OrgB` (victim repo/stack), per the documented multi-app schema in `docs/setup.md`.
2. Attacker obtains `OrgA`'s legitimate `webhook_secret` (they administer `OrgA`'s GitHub App installation).
3. Attacker crafts a `status` event body: `{"sha": "<victim_commit_sha>", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/attacker-repo"}}` and computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)`.
4. POST to the shared `/github/webhooks` endpoint. `verify_signature` resolves `repository_owner => "OrgA"`, fetches `OrgA`'s `GitHubApp`, and the HMAC validates successfully (app/controllers/shipit/webhooks_controller.rb:24-30).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `OrgB`'s stack (no repository check performed), and calls `create_status_from_github!`, writing a forged "success" status onto `OrgB`'s commit — despite the request never being authenticated by any credential belonging to `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
