### Title
Webhook signature verification binds only the organization's secret, not the repository acted upon — cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a delivery against using the `repository.owner.login` (or `organization.login`) field taken from the *same unverified JSON body*, but the handlers that actually act on the payload key off a completely different field — `repository.full_name` — without ever checking that this repository belongs to the organization whose secret validated the signature. In a multi-organization Shipit deployment, this decouples "which org authenticated the request" from "which repository/stack gets written to."

### Finding Description
The webhook signature check is: [1](#0-0) 

`repository_owner` is derived straight from the untrusted body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the org-specific `GitHubApp` (and its `webhook_secret`) from `secrets.github`, supporting the documented multi-org schema: [3](#0-2) [4](#0-3) 

Once signature verification passes (using whatever secret matches `repository.owner.login`), the raw JSON is dispatched to handlers via a single shared `/webhooks` route: [5](#0-4) [6](#0-5) 

Every handler, however, resolves the target repository/stack from a *different* field of the same untrusted body — `repository.full_name` — with no cross-check against `repository.owner.login`/the org used for signature selection: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

Because HMAC verification only proves "this body was signed with OrgA's secret," and not "this body's `repository.full_name` belongs to OrgA," anyone who knows/controls OrgA's `webhook_secret` (e.g. a legitimate GitHub App owner/admin of OrgA in a Shipit instance that manages several organizations, per the documented `somegithuborg`/`someothergithuborg` config) can set `repository.owner.login: "OrgA"` (to pass signature selection) while setting `repository.full_name: "OrgB/target-repo"` (an unrelated org's repository Shipit also manages). The forged, correctly-signed request will be routed by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` straight to OrgB's stacks — triggering `PushHandler#process` → `stack.sync_github(expected_head_sha:)`, or creating/archiving/unarchiving review stacks for OrgB's pull requests — none of which the attacker is authorized to touch.

This mirrors the report's root cause exactly: the account/role that is authenticated (`feeCollector`/organization owner) is not the same as the entity whose funds/resources are acted upon (LP fees/another organization's repository); the binding "organization authenticated == repository written" is never enforced.

### Impact Explanation
`sync_github` updates the stack's known commits and can drive continuous-deployment pipelines to pick up and deploy attacker-influenced refs on a repository/organization the attacker does not control, and review-stack handlers can create/archive/unarchive environments for a foreign repository. This is a cross-organization write triggered purely by forging a webhook body against a secret the attacker legitimately possesses for their *own* org — an unauthorized cross-repository/cross-organization action, which falls under the "cross-repository writes" / "unauthorized deploy" Critical impact bucket.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with more than one GitHub organization (an explicitly documented and supported deployment mode), and (2) the attacker being a legitimate owner/admin of one of those organizations' GitHub Apps (so they know that org's `webhook_secret`) while wanting to affect a *different* tenant organization's stacks on the same Shipit instance. This is plausible in any shared/multi-tenant Shipit deployment where different teams/orgs are onboarded with separate GitHub Apps but the same webhook endpoint and secret store.

### Recommendation
In `verify_signature`, after selecting the `GitHubApp` by `repository_owner` and validating the signature, additionally assert that `params.dig('repository', 'full_name')` (and `organization.login` for org-scoped events) actually belongs to the same organization used to select the webhook secret, rejecting (422) any payload where these disagree. Alternatively, bind webhook secrets per-repository rather than solely per-organization-name-from-payload.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config (`config/secrets.yml` with top-level `OrgA` and `OrgB` keys, each with its own `webhook_secret`), managing stacks for repos in both `OrgA` and `OrgB`.
2. As an actor who legitimately owns/administers the GitHub App for `OrgA` (and therefore knows `OrgA`'s `webhook_secret`), craft a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s `webhook_secret` over the raw body.
4. `POST` directly to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature (since it was computed with OrgA's secret), then `PushHandler` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — an action the attacker has no authorization over.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks

            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
