### Title
Membership webhook binds team by global GitHub `github_id` without verifying the signing organization owns the team, allowing cross-org escalation into `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id: params.team.id` [1](#0-0) , while `WebhooksController#verify_signature` only proves the payload was signed with the webhook secret of `params.dig('organization','login')`, not that this organization actually owns the referenced team [2](#0-1) . Because `github_id` is a global GitHub team ID (not scoped per-organization in the lookup), an org that legitimately owns a webhook secret can forge a `membership` "added" event naming a pre-existing `Team` record that actually belongs to a different organization, and add an arbitrary GitHub login as a member of it, which flows directly into `User#authorized?`.

### Finding Description
The broken binding is: `organization_that_signed_the_payload == team.organization_that_owns_github_id`. This must hold for any mutation of `Shipit::Team` membership, but the code never checks it.

- `verify_signature` selects the GitHub App / secret to validate against using `repository_owner`, which for a `membership` event falls back to `params.dig('organization', 'login')` [3](#0-2) . This only proves "whoever sent this request knows the secret for the org named in `organization.login`" — it says nothing about the `team` object embedded in the same payload.
- `MembershipHandler#find_or_create_team!` resolves the target `Team` exclusively by `github_id: params.team.id`: `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end` [1](#0-0) . The block that sets `team.organization` only runs when a **new** record is built; if a `Team` row with that `github_id` already exists (e.g., because it is one of the entries pre-populated via `Shipit.github_teams`, which is built from `Shipit.github(organization:).api` team lookups keyed by `organization/slug` in `Team.find_or_create_by_handle` [4](#0-3)  and cached via `github_teams` in `lib/shipit.rb` [5](#0-4) ), the existing record is returned unchanged, and its true `organization` is never re-validated against `params.organization.login`.
- `process` then does `member = User.find_or_create_by_login!(params.member.login); team.add_member(member)` for `action == 'added'` [6](#0-5) , creating a `Membership` row for the attacker's own GitHub login on the victim-owned `Team`.
- `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , which is satisfied purely by having a `Membership` row on that `Team`'s primary key — exactly what the forged webhook produced.

Attacker's exact request: a POST to `/webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with attacker-org's own webhook secret, and body `{"action":"added","organization":{"login":"attacker-org"},"team":{"id":<victim_team_github_id>,"name":"<victim team name>","slug":"<victim team slug>","url":"..."},"member":{"login":"attacker-login"}}`. Because `verify_signature` resolves the GitHub App by `organization.login` ("attacker-org"), the signature check passes using a secret the attacker legitimately possesses, yet the `team` sub-object references a completely different organization's team.

None of the existing guards catch this: `verify_signature` never inspects `params.team`; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `MembershipHandler` validates shapes/types only, not cross-object ownership [8](#0-7) ; and `Team.find_or_create_by!` performs no re-fetch or cross-check against GitHub to confirm `params.organization.login` actually owns `github_id`.

### Impact Explanation
A successful forgery grants the attacker's own GitHub login a `Shipit::Membership` on any pre-existing `Team` row keyed in `Shipit.github_teams`, which is the exact set gating `User#authorized?` and thus `force_github_authentication` for the whole Shipit application [9](#0-8) . This is an authorization-escalation bypass into `Shipit.github_teams`, matching the explicitly listed High-severity category. It is repeatable against any `Team` github_id that is already present in the database, and blast radius spans every stack/repository gated by that team membership, i.e., cross-tenant in any multi-org Shipit deployment.

### Likelihood Explanation
Exploitation requires: (1) a multi-org Shipit deployment where the attacker's own organization is a legitimately configured GitHub App with a known `webhook_secret` (a stated precondition of the scenario, not a general default), (2) a target `Team` row already existing in Shipit's database with a `github_id` the attacker can name (this happens automatically for every entry in `Shipit.github_teams`, since `github_teams` eagerly resolves and persists those `Team` rows), and (3) knowledge of that team's real GitHub `github_id` (team IDs can leak through GitHub UI/API responses even without org membership in various circumstances). Given those preconditions, the attacker's cost per request is a single signed HTTP POST, fully repeatable and scriptable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team#organization` matches `params.organization.login` (the org that authenticated the payload) before allowing any membership mutation; reject/raise (or re-fetch and reconcile) on mismatch instead of silently reusing the existing row. Additionally, `Team` lookups should not trust the numeric `github_id` alone across organizations without also confirming `organization` equality, and ideally the webhook signature verification step should attach the verified organization to the request context so handlers can assert equality against any organization named in nested payload objects.

### Proof of Concept
Add a test to `test/controllers/webhooks_controller_test.rb`-style setup (or a new `test/models/webhooks/handlers/membership_handler_test.rb`, since none currently exists) with the following minitest plan:

```ruby
test "membership event cannot escalate attacker into a different org's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: "shopify", github_id: e.g. 1
  Shipit.stubs(:github_teams).returns([victim_team])

  # Attacker's own org, distinct webhook secret configured for "attacker-org"
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    action: 'added',
    organization: { login: 'attacker-org' },
    team: {
      id: victim_team.github_id,   # victim's real GitHub team id
      name: victim_team.name,
      slug: victim_team.slug,
      url: victim_team.api_url
    },
    member: { login: 'attacker-login' }
  }.to_json

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = 'sha1=whatever-valid-for-attacker-org'

  assert_no_difference -> { Shipit::Team.count } do
    post :create, body: payload, as: :json
  end
  assert_response :ok

  attacker = Shipit::User.find_by(login: 'attacker-login')

  # BROKEN BINDING: organization that signed ("attacker-org") != victim_team.organization ("shopify")
  refute_equal 'attacker-org', victim_team.reload.organization

  # Yet the attacker is now a member of the victim's team and passes authorized?
  assert victim_team.members.include?(attacker)
  assert_predicate attacker, :authorized?
end
```

This asserts both sides of the equality explicitly (`'attacker-org' != victim_team.organization`) and demonstrates that despite the mismatch, `Membership` creation succeeds and `User#authorized?` returns `true` for the attacker.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end
