This confirms `g1_lincomb_fast` explicitly filters out points at infinity (`blst_p1_is_inf(&p[i])`) before scalar multiplication, so any weight applied to an infinity proof point contributes exactly zero to the sum regardless of the scalar value [1](#0-0) . Combined with the all-zero cell producing a zero interpolation polynomial (hence `interpolation_poly_commit == G1_IDENTITY`), the final pairing check reduces to `e(C, G2) == e(O, power_of_s) == 1`, which is only satisfiable when the commitment `C` itself is the identity element.

### Title
No exploitable soundness break: infinity-proof + zero-cell reduces verification to requiring commitment == identity, which an attacker cannot forge - (`src/eip7594/eip7594.c`)

### Summary
Tracing the equality claimed in the question shows that supplying an infinity proof with an all-zero cell does zero out that index's contributions to both `proof_lincomb` and `weighted_sum_of_proofs`, exactly as the question suspects. However, this collapses the final pairing check to `e(C, G2) == 1`, which is only true when `C` is also the point at infinity — something the attacker cannot produce for a non-trivial polynomial without breaking the discrete-log assumption underlying the trusted setup.

### Finding Description
The claimed broken equality is: "final_g1_sum == 0 constraint can be satisfied while commitment C is non-identity." Tracing `verify_cell_kzg_proof_batch` at [2](#0-1)  for `num_cells = 1`:

- `r_powers[0] = r^0 = 1` from `compute_powers`, regardless of the Fiat-Shamir challenge `r`.
- `proofs_g1[0]` decoded via `bytes_to_kzg_proof` accepts infinity because `validate_kzg_g1` has an explicit infinity carve-out.
- `proof_lincomb = g1_lincomb_fast(proofs_g1, r_powers, 1)`. Inside `g1_lincomb_fast`, points where `blst_p1_is_inf(&p[i])` is true are filtered out entirely before the Pippenger MSM call [3](#0-2) , so `proof_lincomb = G1_IDENTITY` no matter what `r_powers[0]` is.
- `weighted_sum_of_proofs` in `computed_weighted_sum_of_proofs` [4](#0-3)  similarly becomes `G1_IDENTITY` for the same reason.
- The all-zero cell makes `aggregated_interpolation_poly` all `FR_ZERO` [5](#0-4) , so `interpolation_poly_commit = g1_lincomb_fast(..., aggregated_interpolation_poly, ...) = G1_IDENTITY` (all-zero scalars also get filtered by the same infinity/zero-scalar path when multiplied — g1_mul(p, 0) = identity, and the sum of identities is identity).
- `final_g1_sum = C·1 - G1_IDENTITY + G1_IDENTITY = C` [6](#0-5) .
- The final check is `pairings_verify(final_g1_sum, G2, proof_lincomb, power_of_s)` = `e(C, G2) == e(G1_IDENTITY, power_of_s)`. Since `e(O, anything) = 1` (pairing identity property), this reduces to `e(C, G2) == 1`, which holds **iff `C` is itself the point at infinity** (by non-degeneracy of the pairing on a prime-order group).

For `C` to equal `G1_IDENTITY`, the attacker would need a G1 element that is the identity yet still be interpreted as a "commitment to a non-zero-degree-0 polynomial." A commitment `C = [f(τ)]G1` equals the identity only if `f(τ) = 0 mod r` — for a fixed secret `τ` unknown to the attacker (discarded toxic waste from the trusted setup), this is only trivially true for `f ≡ 0`. There is no way to craft a non-zero polynomial `f` whose commitment collapses to the identity without knowing `τ`, which is exactly the discrete-log/knowledge-of-exponent assumption the whole KZG scheme relies on. All existing guards (`validate_kzg_g1`'s infinity carve-out, `g1_lincomb_fast`'s infinity filtering, the `bytes_to_kzg_commitment`/`bytes_to_kzg_proof` decoders) do not need to additionally special-case this because the pairing equation itself already enforces the correct constraint — it just happens to reduce to a trivial/degenerate one when both proof and cell are zero, and that degenerate case only accepts a degenerate (also-identity) commitment, i.e., a correctly-formed proof for the all-zero polynomial.

### Impact Explanation
No divergence occurs. `*ok` will be `true` only when the submitted commitment is itself the identity element — which corresponds exactly to a valid (trivial) all-zero polynomial and its correct (infinity) proof. If the attacker submits a non-identity/real commitment alongside the zero-cell + infinity-proof combination, `final_g1_sum = C ≠ G1_IDENTITY`, `e(C, G2) ≠ 1`, and `*ok = false`. This matches REFERENCE_TRUTH/soundness — there is no forged acceptance of a non-zero-degree-0 polynomial's commitment against an all-zero cell.

### Likelihood Explanation
Not exploitable: producing a non-identity commitment that nonetheless satisfies `e(C,G2)==1` requires finding `f(τ)=0` for secret `τ`, equivalent to breaking the trusted setup's secrecy or the discrete log assumption on BLS12-381 G1. This is infeasible for any attacker.

### Recommendation
No code change required for this specific path. The pairing equation's non-degeneracy already binds `C` correctly even in this edge case.

### Proof of Concept
A C unit test in `src/test/tests.c` calling `verify_cell_kzg_proof_batch` with `num_cells = 1`, `proofs_bytes[0]` = compressed infinity (`0xc0` byte followed by zeros, which `validate_kzg_g1`'s infinity carve-out accepts), `cells_bytes[0]` = all-zero field elements, and:
- `commitments_bytes[0]` = a real, non-identity commitment (e.g., commitment to a random blob) → assert `ret == C_KZG_OK` and `*ok == false`.
- `commitments_bytes[0]` = compressed infinity (0-polynomial commitment) → assert `ret == C_KZG_OK` and `*ok == true`.

Both outcomes match the reference specification's expected behavior; no soundness break is demonstrated.
