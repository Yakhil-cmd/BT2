### Title
Unhandled exception in AA dry-run trigger execution permanently leaks the global `handleJoint` mutex, halting new-unit processing - (File: network.js)

### Summary
When `conf.bDryRunNewTriggers` is enabled, `network.js`'s joint-validation success handler (`ifOk`) awaits `aa_composer.dryRunPrimaryAATrigger()` for every AA address that a newly-submitted unit pays into, before ever calling `unlock()`/`validation_unlock()`. If that dry run throws (the code comment even says "if it would crash, let it crash now"), the exception propagates out of an unawaited/uncaught async callback, and the `handleJoint` mutex — which serializes *all* unit validation on the node — is never released.

### Finding Description
The relevant code path is in the `ifOk` callback passed to `validation.validate()`: [1](#0-0) 

Every other termination branch of this same callback set (`ifUnitError`, `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`) carefully calls `unlock()` before returning, mirroring the "proper deinit flow" that the CVE description calls out as missing in the kernel driver. The `ifOk` branch, however, only unlocks inside the `writer.saveJoint(...)` completion callback: [2](#0-1) 

Between `clearHost()` and that `writer.saveJoint` call, the code executes: [3](#0-2) 

`aa_composer.dryRunPrimaryAATrigger()` evaluates the AA's oscript/ojson definition against attacker-supplied trigger data (`objJoint.unit.messages`, `params`, etc. — anything a normal unit poster puts in a payment to an AA address). Any oscript/ojson evaluation bug, malformed-but-validation-passing trigger data, or JSON.parse edge case in the AA's stored `definition` can cause this call to throw or reject. Because the surrounding code has no `try/catch` around the `await`, and no `.catch()` handler, the exception:
1. Skips `writer.saveJoint`, so `unlock()` and `validation_unlock()` are never invoked.
2. Produces an unhandled promise rejection.

`mutex.js`'s `exec()`/`lock()` implementation has no timeout or exception-safety net — a lock that is never explicitly released via the `unlock` callback stays in `arrLockedKeyArrays` forever: [4](#0-3) [5](#0-4) 

Since `handleJoint` is the single serialization point for validating and saving every incoming unit (used identically by the composer/wallet code paths as well): [6](#0-5) [7](#0-6) 

leaking it means every subsequent `mutex.lock(['handleJoint'], ...)` call is queued forever and never executed, exactly analogous to the kernel bug's "memory leak during early return / improper deinit flow" — except here the leaked resource is the mutual-exclusion lock that gates all unit acceptance.

### Impact Explanation
Once `handleJoint` is permanently locked, the affected node (any full node/hub that has enabled dry-run of new AA triggers, a supported first-class use case for early-crash detection before executing triggers for real) can no longer validate or save *any* new unit — AA-related or otherwise. This is a "network unable to confirm new units" condition on that node: it silently stalls, queuing all future joints in `arrQueuedJobs` without ever draining them. A single crafted AA trigger unit posted by any unprivileged unit author is sufficient to induce this state, which matches the required impact class of "a network unable to confirm new units."

### Likelihood Explanation
Reachability requires only that:
- The target node has AA dry-run enabled (`conf.bDryRunNewTriggers`), a legitimate configuration for hubs/witness nodes that proactively catch trigger-execution bugs.
- An attacker deploys or targets any AA whose definition can be driven, via attacker-controlled trigger data, into a code path in `dryRunPrimaryAATrigger`/formula evaluation that throws rather than gracefully returning a bounce/error (the surrounding oscript evaluator otherwise goes to great lengths to convert bad input into `setFatalError`/bounce rather than JS exceptions, but any single missed case in that very large surface — array/dictionary/state-var/response-var handling, JSON.parse of malformed definitions, etc. — reaches this unguarded path).
- No privileged access, peer trust, or race condition is required beyond posting an ordinary unit.

I was not able to fully verify (due to end of investigation time) whether `dryRunPrimaryAATrigger`/`handleTrigger` in `aa_composer.js` currently has an internal case that throws instead of calling back with an error for some attacker-reachable oscript construct; this would need to be confirmed by tracing all `throw` statements reachable from `handleTrigger`/`evaluate`. The structural bug — missing `unlock()` on the exception path in `network.js`'s `ifOk` — is confirmed directly from the code shown above regardless of which specific formula construct triggers the throw.

### Recommendation
Wrap the dry-run block in `network.js`'s `ifOk` handler with proper exception handling so that `unlock()` and `validation_unlock()` are always invoked, e.g.:
```js
try {
    ...
    await aa_composer.dryRunPrimaryAATrigger(trigger, address, JSON.parse(definition));
} catch (e) {
    validation_unlock();
    unlock();
    // surface/report the error instead of crashing silently later
    return callbacks.ifUnitError("dry run trigger failed: " + e);
}
```
More generally, audit all `mutex.lock(['handleJoint'], ...)` (and similarly `'write'`) call sites to guarantee `unlock()` is called in every exit path, including thrown exceptions, mirroring the CVE's fix of ensuring a proper deinit/unlock flow on all return paths, not just the success path.

### Proof of Concept
1. Run a node with `conf.bDryRunNewTriggers = true` (a supported, documented mode for hubs that want to fail fast on AA triggers).
2. Deploy (or locate) an AA whose `definition` can be parsed successfully but whose formula evaluation, when driven by a specific trigger payload from an unprivileged sender, throws a raw JS exception in `aa_composer.dryRunPrimaryAATrigger` rather than resolving to a validation error.
3. Post a unit with a `payment` message to that AA's address containing the crafted trigger data.
4. Observe in `network.js`'s `ifOk` handler (network.js:1271-1281) that the `await aa_composer.dryRunPrimaryAATrigger(...)` call throws before `writer.saveJoint` (and therefore `unlock()`/`validation_unlock()`) is reached.
5. Confirm via `mutex.js` (`arrLockedKeyArrays`) that the `handleJoint` key remains locked indefinitely and that subsequently submitted units are queued in `arrQueuedJobs` but never processed, halting the node's ability to confirm any new unit.
