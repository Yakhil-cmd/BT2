### Title
`MultiKey`/`MultiKeyAuthenticator` allows k-of-n threshold to be satisfied with fewer than k distinct signing keys when public keys repeat - (File: `types/src/transaction/authenticator.rs`)

### Summary
`MultiKey::new` (the k-of-n authenticator used for `MultiKeyAuthenticator`/`SingleSender` accounts) does not enforce that the `public_keys` vector contains only distinct keys. [1](#0-0) 
If an account's authentication key is derived from a `MultiKey` list containing the same public key at multiple indices, `MultiKeyAuthenticator::verify` will accept one signature reused at two different indices that happen to map to the same underlying public key, satisfying `signatures_required` (the threshold) with fewer distinct private keys than intended.

### Finding Description
`MultiKeyAuthenticator::verify` expands the bitmap-indexed signatures into `SingleKeyAuthenticator`s and checks each one individually against the public key at that bit index: [2](#0-1) 
The only structural checks performed are: index is in range, no duplicate *bitmap index*, and enough signatures are present to meet the numeric threshold: [3](#0-2) 

None of these checks require the public keys referenced by the signature indices to be distinct. If `public_keys` (set at authenticator/authentication-key-derivation time) contains a repeated `AnyPublicKey` at two indices (e.g. index 1 and index 2 both equal `sender1_pub`), then a single signature produced by the one private key behind `sender1_pub` verifies successfully when duplicated across both indices, because each `SingleKeyAuthenticator::verify` call only checks "does this signature verify under this public key," not "is this public key distinct from other satisfied indices."

The repo's own unit test demonstrates and asserts this exact behavior succeeds: [4](#0-3) 
Here `multi_key` was constructed with `threshold = 2` over keys `[sender0_pub, sender1_pub, sender1_pub]`. The `mk_auth_12` authenticator supplies the *same* `signature1` (from `sender1`'s key alone) at both index 1 and index 2, and `signed_txn.verify_signature().unwrap()` succeeds — a "2-of-3" authenticator is satisfied by a single signer holding one private key.

The account's authentication key is a hash over the exact `MultiKey` byte encoding (`public_keys` + `signatures_required`), so nothing downstream (prologue's `account::get_authentication_key` check) revalidates key distinctness — the authentication key comparison only confirms the *encoded* MultiKey struct matches what's on-chain, not that its keys are distinct.

### Impact Explanation
Accounts (or approval groups such as governance-configured multisig-style k-of-n signer sets built via `MultiKey`) are expected to provide "k independent approvals" as their core security property — e.g. a "2-of-3" or "3-of-5" scheme is chosen specifically so that no single compromised/malicious key holder can unilaterally authorize a transaction. This bug breaks that admission-boundary invariant: whoever controls a public key that has been listed more than once in the `MultiKey` set (whether by account-owner misconfiguration, tooling bug, or intentional social-engineering of a co-signer into approving a key list without noticing a duplicate) can single-handedly satisfy the full threshold and authorize/execute the transaction alone, defeating the intended "wrong approval set" protection. This is a direct violation of "Authenticator ... accepting the wrong signing material or wrong approval set," resulting in unauthorized transaction execution by an under-authorized signer set.

### Likelihood Explanation
Exploitation requires that a `MultiKey` account/authenticator be created (or reconstructed by an attacker) with a repeated public key among its `public_keys` list — this is a client-side/account-configuration issue, not a protocol-enforced invariant, since `MultiKey::new` performs no dedup/uniqueness check. Any tooling, wallet, or governance flow that builds a k-of-n `MultiKey` without independently checking for duplicate keys is silently vulnerable, and there is no on-chain or account-creation validation preventing it. Because the threshold-with-duplicates weakness is invisible in the raw byte-level authentication key (a hash of the whole struct) and passes both authenticator parsing (`MultiKeyAuthenticator::new`) and prologue authentication-key matching, it can go undetected until exploited.

### Recommendation
In `MultiKey::new`, reject construction when the `public_keys` vector contains duplicate entries (e.g., using a `HashSet`/sorted comparison over the serialized `AnyPublicKey` bytes), returning an error consistent with the other `ensure!` checks already present. Apply the same uniqueness constraint wherever `MultiKey`/`MultiEd25519PublicKey`-equivalent structures are constructed from client input (including the API conversion path in `api/types/src/convert.rs`/`api/types/src/transaction.rs` `TryFrom<&MultiKeySignature> for AccountAuthenticator`) so that k-of-n approval sets always represent k *distinct* keys.

### Proof of Concept
The existing repository test is itself a proof of concept demonstrating the bypass: [5](#0-4) [4](#0-3) 
Steps:
1. Construct `MultiKey::new(vec![sender0_pub, sender1_pub, sender1_pub], 2)` — a "2-of-3" scheme where index 1 and index 2 are the *same* key (`sender1_pub`).
2. Derive the account address from this `MultiKey` via `AuthenticationKey::multi_key`.
3. Have only `sender1` (one private key) sign the raw transaction once, producing `signature1`.
4. Build `MultiKeyAuthenticator::new(multi_key, vec![(1, signature1.clone()), (2, signature1.clone())])` — reusing the single signature at both indices that map to `sender1_pub`.
5. Call `signed_txn.verify_signature()` — it succeeds, proving that only one distinct private key satisfied a nominal 2-of-N threshold.

<br>

Note: I could not independently verify (given remaining budget) whether the multisig-style `MultiKey` construction path used by real account-creation/rotation flows (e.g., `create_signer`, `rotate_authentication_key` in `account.move`, or wallet-side SDK helpers) performs any additional uniqueness validation before this `MultiKey` struct is committed as an account's authentication key; if such a check exists elsewhere in application/SDK code (outside what was reviewed here), it could mitigate real-world exploitability even though the core `authenticator.rs` type itself permits and correctly verifies the duplicate-key construction as shown above.

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }
