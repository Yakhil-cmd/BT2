### Title
Cross-repository forged commit status triggers victim stack's merge pipeline - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves commits by SHA alone (`Commit.where(sha: params.sha)`) without scoping to the repository named in the incoming webhook payload, unlike the base `Handler#stacks` helper used elsewhere. Since git commit SHAs are content-addressed and not repository-specific, an attacker who owns an unrelated repository can produce a commit with the same SHA as a commit tracked by a victim's stack, then emit a legitimately-signed status webhook from their own repository that gets applied to the victim's `Commit` record, driving `Stack#schedule_merges` / `ProcessMergeRequestsJob` for the victim's stack.

### Finding Description
The claimed binding is: `stack_enqueued_for_schedule_merges == stack_whose_webhook_secret_authenticated_the_request`. Tracing the code shows this binding is **false**.

`WebhooksController#verify_signature` authenticates the request using `Shipit.github(organization: repository_owner)` derived from `params.dig('repository','owner','login')` [1](#0-0)  — this only proves the request came from *some* GitHub org/app the attacker legitimately controls (their own), not from the victim's org.

Dispatch then calls the matching handler with the raw payload: [2](#0-1) .

The base `Handler` class provides a `stacks` helper that correctly scopes lookups to the repository named in the payload: [3](#0-2) .

`StatusHandler#process`, however, ignores that helper entirely and looks up commits globally by SHA: [4](#0-3) 

`Commit#create_status_from_github!` then calls `add_status`, which — if the resulting state transitions to `pending` or `success` — calls `stack.schedule_merges` where `stack` is `commit.stack`, i.e. whichever stack owns the matched `Commit` row, not any stack related to the authenticating organization: [5](#0-4) [6](#0-5) 

Because git SHAs are computed purely from commit content (tree, parents, author/committer, message, timestamps) and are independent of which repository hosts them, an attacker can reproduce a victim's exact commit object (by cloning/forking the victim's public repo and pushing the same commit objects into their own repo) and thereby control a commit with an identical SHA in their own repository. The attacker then creates a status on that SHA via the GitHub API against their own repo — a fully legitimate, self-authorized action — and GitHub delivers the resulting `status` webhook signed with the attacker's own org/app secret. `verify_signature` passes because it only checks that the payload's claimed owner matches the signing secret for that owner; it never cross-checks that the SHA-matched `Commit`/`Stack` actually belongs to that repository. `StatusHandler` then applies the status to every `Commit` row sharing that SHA, including the victim's, and `add_status` schedules the victim's `ProcessMergeRequestsJob`.

### Impact Explanation
A single attacker-controlled, self-authenticated webhook can flip a victim stack's commit status to `pending`/`success` and force-enqueue `ProcessMergeRequestsJob` for the victim's stack via `Stack#schedule_merges`, i.e., **a payload authenticated for one repository mutates another repository's commit/stack state and triggers that stack's merge-processing pipeline** without the victim's webhook secret or app credentials ever being used. This matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team"/"an unauthorized ... merge"). The effect is repeatable against any victim stack whose tracked commit SHA the attacker can reproduce (feasible for any commit visible in the victim's public repo history, since forking/cloning preserves SHAs exactly), and is not limited to a single tenant — any Shipit installation processing webhooks from multiple orgs is affected.

### Likelihood Explanation
Preconditions: the attacker needs (1) an account and repository they control on GitHub (trivial, unprivileged), (2) knowledge of a target commit SHA belonging to a victim's tracked stack (public information for public repos, or leaked/guessable for private ones), and (3) the ability to push that exact commit object into their own repo and set a status on it via the standard GitHub API — both ordinary, self-authorized actions requiring no victim secrets. No Shipit session, API token, or webhook secret of the victim is required. This is low-cost and fully repeatable against any known victim commit SHA.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the webhook payload (using the existing `stacks` helper from `Handler`) instead of matching `Commit` by SHA alone, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent join through `Stack`/`Repository` so a status can only be applied to commits belonging to stacks whose repository matches `payload.dig('repository','full_name')`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from repository B must not schedule merges for stack A's commit sharing the same sha" do
  stack_a = shipit_stacks(:shipit)               # victim stack, repo A
  commit_a = shipit_commits(:second)             # belongs to stack_a, some sha S
  assert_equal stack_a.id, commit_a.stack_id

  # Simulate attacker: payload references repository B, but sha == commit_a.sha (identical commit content reproduced in repo B)
  payload = {
    'sha' => commit_a.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [],
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  stack_a.expects(:schedule_merges).never   # binding under test: stack authenticated (attacker-org's) != stack_a

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
```
Given the current implementation, `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter, matches `commit_a`, calls `commit_a.create_status_from_github!`, transitions its status, and triggers `stack_a.schedule_merges` — the `.never` expectation fails, demonstrating that `stack_enqueued_for_schedule_merges (stack_a) != stack authenticated by the request (attacker-org)`, confirming the vulnerability.
