### Title
Webhook signature verification authenticates a different repository field than the one used to select the target `Stack`, enabling cross-repository/cross-organization webhook spoofing when any configured org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization configuration (and therefore the secret used to HMAC-verify the request) using the field `repository.owner.login` (falling back to `organization.login`), while every webhook handler that actually performs the write (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the `Repository`/`Stack` to mutate using a *different* field of the same payload, `repository.full_name`. Nothing enforces that these two fields describe the same repository, so the entity that is cryptographically authenticated is not the entity that is acted upon — the same class of bug as the Staking report, where the authorization check ran against `owner` but the state mutation ran against `msg.sender`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` selects which GitHub App config to verify against: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from `repository.owner.login` (or `organization.login` as a fallback), and `Shipit.github(organization: repository_owner)` is used to fetch the `GithubApp`/secret used in `verify_webhook_signature`: [3](#0-2) 

Critically, if `webhook_secret` is blank for that organization's configuration — which the setup docs explicitly document as optional — verification always succeeds regardless of the actual signature header: [4](#0-3) 

Once verification passes, `create` dispatches the *entire, unauthenticated-with-respect-to-full_name* payload to handlers: [5](#0-4) 

Every handler's base class resolves the target `Repository`/`Stack` using `repository.full_name`, a field that was never part of the check that selected which org's trust was being relied upon: [6](#0-5) 

`PushHandler` (and similarly `StatusHandler`, `CheckSuiteHandler`) then acts on whatever stacks that `repository.full_name` resolves to: [7](#0-6) 

The broken equality is: `organization whose secret authenticated the request` (`repository.owner.login`) must equal `organization/repository whose Stack is mutated` (`repository.full_name`'s owner segment). The code never checks this, exactly mirroring how `Staking#_unstake` authorized against `owner` but mutated `msg.sender`'s votes.

### Impact Explanation
In a Shipit instance configured with multiple GitHub organizations where at least one organization has no `webhook_secret` set (an explicitly supported, documented configuration), an unauthenticated attacker can send a crafted, arbitrarily-signed POST to `/webhooks` with `repository.owner.login` set to the secret-less organization and `repository.full_name` set to any other repository/stack managed by the instance (including ones belonging to organizations that do have secrets configured). This bypasses the signature check entirely (`verify_webhook_signature` short-circuits to `true`) and then causes handlers to act on the spoofed target repository's stacks — e.g., forcing `Stack#sync_github`, or (via `StatusHandler`) injecting fabricated commit statuses that a `continuous_deployment`-enabled stack relies on to gate deploys, potentially causing an unauthorized deploy. This satisfies the Critical bar of "cross-repository writes" / "unauthorized deploy."

### Likelihood Explanation
Requires no credentials, no repository access, and no GitHub App private key — only that the deployment has configured at least one organization without a `webhook_secret`, which is explicitly presented as an optional setting in `docs/setup.md`. The attacker only needs to know the target repository's `full_name` (public information) and the name of any org configured on the instance without a secret.

### Recommendation
Verify the webhook signature using a key selected independently of attacker-controlled JSON, or require that the derived `repository_owner` used for verification match the owner segment of `repository.full_name` used for dispatch before invoking handlers. Additionally, disallow silently treating a blank `webhook_secret` as "always valid" for organizations that share an instance with other secured organizations.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (has a stack `orgB/critical-app` with `continuous_deployment: true`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/critical-app" },
  "ref": "refs/heads/main",
  "after": "<sha>"
}
```
with any/garbage `X-Hub-Signature` value.
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler` resolves `repository_name` as `orgB/critical-app` and triggers `sync_github` / status-driven actions on `orgB`'s stack despite the request never being authenticated for `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
