## Title
CCMenu API endpoint bypasses `ApiClient` stack scoping, allowing a stack-scoped token to read the status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to look up the stack directly by parameter instead of going through the stack-scoped lookup used by every other API endpoint. This breaks the binding between "the stack a token authorizes" and "the stack the request actually touches," letting a token that was deliberately scoped to a single stack read deploy/build status for arbitrary stacks.

### Finding Description
`Shipit::ApiClient` records can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . This scoping is enforced centrally in `Api::BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every controller that inherits this `stack` helper (e.g. `Api::StacksController`) is implicitly restricted: if the authenticating `ApiClient` has a `stack_id`, only that stack can ever be resolved from `params[:stack_id]`, regardless of what id the caller passes.

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The controller still declares `require_permission :read, :stack` [4](#0-3) , but `ApiClient#check_permissions!` only checks whether the permission string `"read:stack"` is present in the client's `permissions` array — it never compares `stack_id`:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
``` [5](#0-4) 

So the only place stack scoping is actually enforced is the `stacks`/`stack` helper in `BaseController`, and `CCMenuController` opts out of it. Stack-scoped tokens are a first-class, intentionally narrow credential: `CCMenuUrlController` creates exactly this kind of scoped client for end users (e.g. to embed in a CI dashboard widget) with only `read:stack` permission and bound to one stack:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [6](#0-5) 

The binding broken here is: **stack a token authorizes ≠ stack a token touches**. Before the request, `current_api_client.stack_id` equals the single stack the token was minted for. After hitting `CCMenuController#show` with a different `stack_id` param, the controller happily resolves and renders build status for that unrelated stack.

### Impact Explanation
This is an unauthorized read of stack state (build/deploy status, last build label, activity, web URL) for stacks the token holder was never granted access to, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" (here it is authenticated with valid but narrowly-scoped credentials, yet the scope constraint is not honored, which is the essence of the specified bug class: "a stack a token authorises versus a stack it touches").

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token (e.g. a CCMenu URL handed to an external CI dashboard tool, per `CCMenuUrlController`) can trivially exploit this by changing the `stack_id`/`id` request parameter to any other stack's identifier — no additional privilege, secret, or write access is required beyond the token they already legitimately possess for one stack.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it to go through the inherited scoped `stacks` collection from `BaseController`) so that stack-scoped `ApiClient` tokens can only ever resolve the stack they were bound to:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. An admin creates (or a user obtains via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id: A`, with `permissions: ['read:stack']`, and gets its `authentication_token`.
2. The attacker sends: `GET /api/stacks/:stack_B_id/ccmenu.xml?token=<token-scoped-to-A>` (per route wiring for `Api::CCMenuController#show`).
3. `authenticate_api_client` resolves `@current_api_client` successfully via `ApiClient.authenticate(params[:token])` [7](#0-6) .
4. `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, independent of which stack is requested.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` directly against `stack_B_id`, bypassing the `current_api_client.stack_id` restriction, and the controller renders `stack_B`'s deploy/build status in the XML response — data the token was never authorized to see.
