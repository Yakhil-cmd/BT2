### Title
`update_account_threshold` reuses one `Context` across a batch of accounts on different spokes, so per-spoke asset configs cached under `HubAssetKey` bleed between spokes and persistently restamp positions with a foreign spoke's LTV/LT/bonus/fees - (File: contracts/controller/src/risk/params.rs)

### Summary
`update_account_threshold` is a permissionless entrypoint: any authenticated caller passes an arbitrary `account_ids` vector and the function iterates the batch through a single shared `Context`, calling only `cache.reset_spoke_context()` between accounts. The `Context` caches spoke asset listings in `spoke_assets: Map<HubAssetKey, SpokeAssetConfig>` — keyed by `(hub_id, asset)` only — while lookups are made as `cached_spoke_asset(account.spoke_id, &hub_asset)`. Because the cache key omits `spoke_id`, an account on spoke B that follows an account on spoke A in the same batch reads spoke A's `SpokeAssetConfig` for the same `(hub_id, asset)` listing. `sync_account_thresholds` then converts that foreign config to `AssetConfig` and writes it into the victim's stored `AccountPositionRaw` via `update_or_remove_supply_position` + `set_supply_positions`.

### Finding Description
The root cause mirrors the referenced bug class: a private per-subrequest structure (here the `Context`'s `spoke_assets` map, plus `verified_hubs`, `token_prices`, `market_indexes`) is retained across loop iterations while only part of the spoke-scoped state is reset. In `contracts/controller/src/risk/params.rs:140-143` the same `cache` serves every `account_id`; `reset_spoke_context()` is documented to reset the spoke usage/config (`SpokeUsageContext` and `SpokeConfig` `Option`s), while `spoke_assets` is a `Map<HubAssetKey, SpokeAssetConfig>` (`contracts/controller/src/context.rs:33`) — a `Map` keyed without `spoke_id`, so `cached_spoke_asset(spoke_id, hub_asset)` returns the listing loaded for whichever spoke populated that `HubAssetKey` key first in the batch.

Concretely, `sync_account_thresholds` iterates the victim's supply positions, calls `cache.cached_spoke_asset(account.spoke_id, &hub_asset)` (params.rs:183), builds `AssetConfig::from(&spoke_config)`, and on any difference commits `account.supply_positions` to storage (params.rs:205, 218). With `has_risks = false` the LTV stamp is rewritten unconditionally (`refresh_supply_risk_params` always applies `position.loan_to_value = effective_config.loan_to_value`, params.rs:35). With `has_risks = true` a looser foreign tuple (higher LT) is applied without the HF gate because `favors_liquidator` only gates *tightening*; and even for tightening, the `clears_min_hf` check computes HF against the wrong spoke's threshold and can pass a config that should have been rejected.

A caller fully controls `account_ids` ordering, so it can interleave accounts across spokes deliberately: seed the cache with a permissive spoke's config via a first account, then list target accounts on the restrictive spoke.

### Impact Explanation
The restamp is a persistent storage write of risk parameters onto accounts the caller does not own:

- **Higher LTV stamped onto a restrictive-spoke account**: the victim (or attacker-controlled account on the restrictive spoke) can subsequently borrow against LTV it was never listed with — `borrow` limits use the stored LTV stamp, not the live listing (documented in `docs/reference/runbooks/liqvid-listing-params.md`: "the controller uses the stored values, not the live listing"). This enables undercollateralized borrowing → protocol insolvency / bad debt.
- **Higher liquidation_threshold stamped onto a victim's collateral**: the account's computed HF is inflated with a foreign LT, blocking legitimate liquidations and leaving bad debt to socialize via `clean_bad_debt`'s supply-index write-down — theft from all suppliers of that market.
- **Wrong bonus/fees**: a higher `liquidation_bonus` or lower `liquidation_fees` than the spoke's listing enriches liquidators at the account's/market's expense.

This satisfies the impact criteria: theft of user funds and protocol insolvency through permanently corrupted per-position risk parameters, reachable by any unprivileged authenticated caller.

### Likelihood Explanation
Two spokes listing the same `(hub_id, asset)` with different LTV/LT/bonus is a normal configuration (the codebase's own tests and integration flows use `PRIMARY_SPOKE_ID` vs `STABLECOIN_SPOKE`/`spoke 2` with divergent LTVs such as 7500 vs 9700). `update_account_threshold` is explicitly permissionless ("any authenticated caller", params.rs:121-124, docs line 405) and accepts a batch. The caller needs only one existing account on the permissive spoke to prime the cache, plus victim IDs on the restrictive spoke. The attack is a single transaction with no capital requirement beyond auth.

### Recommendation
Include `spoke_id` in the `spoke_assets` cache key (e.g., `Map<(u32, HubAssetKey), SpokeAssetConfig>`) or clear `spoke_assets` inside `reset_spoke_context()` so each batch element loads its own spoke's listing. The same treatment should be audited for every `Context` field that is spoke-scoped but keyed without `spoke_id` (e.g., `verified_hubs` is hub-scoped and safe; `spoke_config`/`spoke_usage` are already reset). Add a regression test batching `account_ids` across two spokes that share a `(hub_id, asset)` with divergent LTV/LT and asserting each position is stamped with its own spoke's values.

### Proof of Concept
1. Governance config: spoke 1 lists `(hub0, USDC)` with `ltv = 9700`; spoke 2 lists `(hub0, USDC)` with `ltv = 5000` (the codebase's `standard` vs `stablecoin` spoke presets provide exactly this shape; `tests/test-harness/tests/controller/spoke.rs:1200` uses spoke 2 with `USDC` LTV 9700).
2. Attacker opens account A on spoke 1 and supplies USDC → A's position is cached/stamped at LTV 9700 and, more importantly, `cache.spoke_assets[(hub0,USDC)] = spoke-1 config` when `sync_account_thresholds` runs on A.
3. Attacker calls `update_account_threshold(caller = attacker, has_risks = false, account_ids = [A, V])` where V is any account on spoke 2 holding a USDC supply position.
4. For V, `cached_spoke_asset(2, (hub0,USDC))` hits the map entry populated in step 3 keyed only by `HubAssetKey` → returns the spoke-1 listing. `refresh_supply_risk_params` unconditionally sets `position.loan_to_value = 9700`; `set_supply_positions` persists it.
5. V's position now carries LTV 9700 despite spoke 2's listing of 5000. If V is attacker-controlled, it borrows up to ~97% of collateral value on a spoke intended to cap at 50%, and any subsequent price move or the thin collateral buffer leaves the pool with bad debt that `clean_bad_debt` socializes across all suppliers of that hub market.

Note on verification limits: the decisive detail is whether `Context::reset_spoke_context` also clears the `spoke_assets` map; its body was not retrievable within the tool budget. The struct field `spoke_assets: Map<HubAssetKey, SpokeAssetConfig>` keyed without `spoke_id`, combined with the `cached_spoke_asset(spoke_id, hub_asset)` signature, is the cross-spoke collision surface described above.
