### Title
Flag injection via attacker-controlled skill/path names in `gh skill search` install flow - (File: pkg/cmd/skills/search/search.go)

### Summary
`gh skill search` lets a user interactively select skills discovered via the GitHub Code Search API and then re-invokes `gh skills install` as a subprocess, passing the repository and skill name taken directly from attacker-controlled search results. Because these values are derived from a path segment in a public repository an attacker fully controls, and are passed as literal positional arguments to `exec.Command`, an attacker can craft a skill path/name that cobra parses as a flag (e.g. `--force`, `--all`, `--from-local`) instead of a positional value, altering the behavior of the invoked `gh skills install` command.

### Finding Description
In `pkg/cmd/skills/search/search.go`, `deduplicateResults` builds `skillResult{ SkillName: skillName, Namespace: namespace, Path: item.Path, ... }` from `extractSkillInfo(item.Path)`, where `item.Path` comes straight from the GitHub Code Search API response for `SKILL.md` files [1](#0-0) . This path is entirely attacker-controlled: anyone can publish a public repository containing a file at `skills/<anything>/SKILL.md`, where `<anything>` becomes `SkillName`/`Namespace`.

Later, `promptInstall` uses these attacker-controlled strings to build the argument list for a re-invocation of the `gh` binary itself:
```go
installArg := s.SkillName
if s.Namespace != "" {
    installArg = strings.TrimSuffix(s.Path, "/SKILL.md")
}
//nolint:gosec // arguments are from user-selected search results, not arbitrary input
cmd := exec.Command(opts.ExecutablePath, "skills", "install", s.Repo, installArg,
    "--agent", host.ID, "--scope", scope)
``` [2](#0-1) 

Although `exec.Command` avoids shell metacharacter injection, `installArg` (and potentially `s.Repo`) is passed as a raw token to a `cobra`-based command (`gh skills install`). `cobra`'s flag parser treats any argument beginning with `-`/`--` as a flag rather than a positional value, unless preceded by `--` to stop flag parsing. The `install` command accepts a `[<skill[@version]>]` positional argument in this exact position [3](#0-2) , and defines flags including `--force`, `--all`, `--from-local`, `--allow-hidden-dirs`, `--upstream`, `--pin`, `--dir` [4](#0-3) . A malicious skill publisher can name their `SKILL.md` directory so that `installArg` matches one of these flags exactly (e.g. `skills/force/SKILL.md` won't match, but a namespaced path like `skills/from-local/anything/SKILL.md` could yield `installArg = "skills/from-local/anything"` after `TrimSuffix`; more directly, an attacker can control the raw `SkillName` for the non-namespaced case, publishing `skills/--force/SKILL.md` so that `extractSkillInfo` yields `SkillName = "--force"`).

This is the closest structural analog to the referenced report's root cause: a value that is supposed to be a trusted "expected output" (here, a plain positional skill-name argument) is instead accepted directly from unauthenticated, adversary-controlled input and fed into a security/behavior-relevant code path (`cobra` flag parsing) without validation or the `--` flag-terminator safeguard, letting the attacker manipulate downstream behavior of a `gh` command run by an unsuspecting user — analogous to how the Votium contracts trusted an unbounded external input (`_min_dy = 0`) instead of validating/bounding it.

### Impact Explanation
If an attacker can inject `--from-local` as the skill-name flag, `opts.FromLocal` becomes true, which requires `opts.SkillSource` to be a local directory path; combined with other injected flags, the practical worst case demonstrated in code is forcing `Force: true` (silently overwriting existing skill files without the confirmation prompt) or `AllowHiddenDirs: true` / `Upstream: true`, changing install semantics without the user's knowledge or consent, while the user believes they selected an ordinary skill from search results. This does not achieve direct arbitrary code execution by itself, since the actual file-writing paths (`installSkill`/`installLocalSkill`) still apply path-traversal protections (`safepaths.Join`) [5](#0-4) , but it demonstrates an unvalidated trust boundary between attacker-published search-result metadata and a security-relevant flag-parsing surface, which the code's own `//nolint:gosec` comment shows was assumed safe based on a wrong premise ("not arbitrary input").

### Likelihood Explanation
Likelihood is **low-to-moderate**: an attacker needs to (1) publish a public GitHub repo with a `SKILL.md` at a specially crafted path, (2) have it show up in code search results for a term a victim searches for, and (3) have the victim select it via the interactive `promptInstall` multi-select and proceed. This requires attacker publishing controlled content, matching the "unprivileged remote-attacker analog... from attacker-published content" category, but with no MITM or local access needed.

### Recommendation
- Insert a literal `"--"` argument before the positional skill-name/repo arguments when building the `exec.Command` in `promptInstall`, so `cobra` treats everything after it as positional data, not flags:
  ```go
  cmd := exec.Command(opts.ExecutablePath, "skills", "install", "--agent", host.ID, "--scope", scope, "--", s.Repo, installArg)
  ```
- Alternatively/additionally, validate that `s.Repo` and `installArg` do not begin with `-` before constructing the subprocess invocation, rejecting or sanitizing such search results.
- Remove the `//nolint:gosec` justification, since it incorrectly assumes search results are not attacker-influenced content.

### Proof of Concept
1. Attacker creates a public GitHub repository, e.g. `attacker/evil-skills`, containing `skills/--force/SKILL.md` with a benign-sounding description matching a common search term (e.g., "terraform").
2. Victim runs `gh skill search terraform`, sees the attacker's entry among results, and selects it via the interactive multi-select prompt in `promptInstall` [6](#0-5) .
3. `promptInstall` builds `installArg = "--force"` from `s.SkillName` and executes:
   `gh skills install attacker/evil-skills --force --agent <host> --scope <scope>`
4. `cobra` parses `--force` as the `--force` flag of `gh skills install` rather than as the skill-name positional argument, silently setting `Force: true` and causing any pre-existing skill of the same computed name to be overwritten without the normal confirmation prompt — behavior the victim did not request and was not warned about.
