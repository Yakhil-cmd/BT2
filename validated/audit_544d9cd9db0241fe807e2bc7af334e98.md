### Title
Webhook signature is validated against `repository.owner.login`'s GitHub App secret while handlers act on unrelated, unauthenticated payload fields (`repository.full_name`, `sha`) — cross-tenant/cross-repository forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of the reported bug: the report shows a check performed on `msg.sender` while the actual privileged action operates on `_receiver` — two different fields that happen to coincide in the common case but diverge under attacker control. In Shipit's webhook pipeline, `WebhooksController#verify_signature` selects *which* GitHub App secret to validate the HMAC against using `repository.owner.login` (or `organization.login`) taken from the untrusted, attacker-supplied JSON body, [1](#0-0) . Once verification passes, the event handlers act on **different fields of that same forged body** — `repository.full_name` in `Handler#stacks` [2](#0-1) , and a bare, repository-unscoped `sha` in `StatusHandler` [3](#0-2) . Because HMAC verification only proves "this body was signed with organization X's secret," not "every field in this body pertains to organization X," an attacker who legitimately controls a webhook secret for **any one** onboarded organization can forge a body that authenticates as their own org while pointing at another tenant's repository or an arbitrary commit SHA anywhere in the Shipit instance.

### Finding Description
Shipit explicitly supports (and documents) a multi-tenant deployment model where multiple GitHub organizations, each with its own `webhook_secret`, `app_id`, and `private_key`, are configured under one Shipit instance [4](#0-3) [5](#0-4) .

For every incoming webhook, `repository_owner` — used solely to pick which org's secret to verify the signature with — is read straight from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

`verify_signature` then does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

`Shipit.github` looks up the org-specific config purely by that string and instantiates the corresponding `GitHubApp`, whose `webhook_secret` is used for the HMAC comparison [7](#0-6) [8](#0-7) .

The verification only proves the *entire raw body* was HMAC-signed with the secret belonging to whatever organization is named in `repository.owner.login`. It does **not** constrain any other field of that same body. Since the attacker who legitimately owns/administers organization `OrgAttacker` (with its own real GitHub App and `webhook_secret` configured in this Shipit instance) can generate a validly-signed request for `OrgAttacker`, they can freely choose every other field in the JSON body, including:

- `repository.full_name`, consumed by `Handler#repository_name`/`#stacks` to select which stacks receive the event [2](#0-1) , letting `PushHandler` trigger `stack.sync_github(expected_head_sha: params.after)` on a **victim** organization's stacks [9](#0-8) , or `CheckSuiteHandler` schedule check-run refreshes on victim commits [10](#0-9) .
- `sha`, consumed by `StatusHandler#process`, which is **not scoped to any repository or organization at all**:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This means an attacker holding a valid webhook secret for *their own* org can inject a fake CI status (e.g. `state: "success"`) for **any commit SHA that exists in any stack managed by this Shipit instance**, regardless of which organization/repository it belongs to.

The equality broken is: `organization whose webhook_secret authenticated the signature == organization/repository the handler writes to`. Before the attack, these coincide because legitimate GitHub webhooks always populate `repository.owner.login`/`full_name`/`sha` consistently with the sending installation. After the attacker's forged request, `verify_signature` authenticates as `OrgAttacker` while `PushHandler`/`CheckSuiteHandler`/`StatusHandler` act on `OrgVictim`'s stacks or an arbitrary global commit SHA.

### Impact Explanation
This directly matches the "organization that authenticated versus the repository that is written" binding break called out in scope, and lands squarely in the accepted High/Critical impact categories:
- Via `StatusHandler`, an attacker can forge a passing CI status for any commit in any repository on the instance, defeating `ci.require`/`ci.blocking` gating documented in the README [11](#0-10) , enabling an **unauthorized deploy** of a commit that never actually passed CI in the victim's repository.
- Via `PushHandler`/`CheckSuiteHandler`, an attacker can force `sync_github` or check-run refresh cycles against a victim organization's stacks they have no access to, i.e. writing to state belonging to a repository they don't control — a **cross-repository write** analogous to the receiver/sender mismatch in the reported finding.

### Likelihood Explanation
Likelihood is high for any Shipit deployment using the documented multi-organization configuration: the only prerequisite is that the attacker legitimately administers/owns one onboarded GitHub organization (with its own GitHub App and `webhook_secret`) — no privileged Shipit session, `ApiClient` token, or access to the victim organization is required. This is not a misconfiguration; multi-org setups with independent `webhook_secret`s per org are the officially documented way to run Shipit for multiple tenants.

### Recommendation
Bind webhook processing to the organization that authenticated the request, not to attacker-controlled fields elsewhere in the same payload:
- After `verify_signature` succeeds for organization `O`, pass `O` through to the handlers and have `Handler#stacks` (and `StatusHandler#process`) filter/require that `repository.owner.login` (or `full_name`'s owner segment) and any commit's owning repository match `O`, rejecting/ignoring events where they don't.
- In particular, scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to the authenticated organization's repositories only.

### Proof of Concept
1. Attacker legitimately owns `OrgAttacker`, which is configured in this Shipit instance's multi-org `github:` secrets with its own `webhook_secret` (as per `docs/setup.md`'s "Using Multiple Github Applications").
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgAttacker/dummy" },
  "sha": "<victim-repo-commit-sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature` using `OrgAttacker`'s real `webhook_secret` over this exact raw body and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and successfully verifies the HMAC — [1](#0-0) .
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matching the victim's commit irrespective of organization, and calls `create_status_from_github!`, marking it as passing CI in a repository the attacker never had access to — [3](#0-2) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

<h3 id="ci">CI</h3>

ci:
  hide:
    - ci/circleci
```

**<code>ci.allow_failures</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to be visible but not to required for deploy.

```yml
ci:
  allow_failures:
    - ci/circleci
```

**<code>ci.blocking</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to disallow deploys if any of them is missing or failing on any of the commits being deployed.

```yml
ci:
  blocking:
    - soc/compliance
