Confirmed: `Repository.from_github_repo_name` looks up the repository purely by `owner/name` parsed from `full_name`, with no reference to whichever organization's secret was used for verification.

### Title
Webhook authentication bypass via organization/repository binding mismatch enables cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects which GitHub App (and thus which `webhook_secret`) to verify a webhook against using `repository_owner`, a value read straight out of the untrusted JSON payload. The event handlers that actually act on the payload (`PushHandler`, PR handlers, etc.) instead resolve the target `Stack`/`Repository` using an entirely separate payload field, `repository.full_name`, with no check that it belongs to the organization that was authenticated. This is the same class of defect as the audited `ZtakingPool.depositETHFor`/`IWETH.deposit` mismatch: a value that is verified/relied upon (the "signature" binding) does not actually cover the value that downstream logic acts on.

### Finding Description
`verify_signature` picks the GitHub App config to check the `X-Hub-Signature` against using `repository_owner`, which is parsed from the same attacker-supplied JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` whenever that particular organization has no configured `webhook_secret` (documented as "optional" during setup): [3](#0-2) [4](#0-3) 

Meanwhile every handler resolves the repository/stack to act on purely from `repository.full_name`, a completely independent field of the same JSON body, never cross-checked against the organization used to authenticate the request: [5](#0-4) [6](#0-5) [7](#0-6) 

Binding that should hold: `repository_owner (authenticated org) == owner(repository.full_name) (repository actually written)`. In a Shipit deployment configured for multiple GitHub organizations (as documented under "Using Multiple Github Applications"), each org has its own `webhook_secret`, and it is explicitly optional per the setup docs. Before the attacker's request: no relationship needs to exist between these two fields for a legitimate GitHub-originated webhook because GitHub always sends a consistent payload where `repository.owner.login` matches `repository.full_name`'s owner segment, signed with that org's own secret. After the attacker's request: an unprivileged sender can set `repository.owner.login`/`organization.login` to any organization configured in this Shipit instance that happens to have no `webhook_secret` set (bypassing verification entirely, since `verify_webhook_signature` returns `true` unconditionally), while setting `repository.full_name` to `victim-org/victim-repo` — a repository belonging to a *different*, properly secured organization tracked by the same Shipit instance. Nothing rejects this combination.

### Impact Explanation
This breaks the trust boundary between "which organization's webhook secret authenticated this request" and "which repository's stack gets acted on." A crafted `push` event lets an attacker enqueue `GithubSyncJob` for an arbitrary victim stack with an attacker-chosen `expected_head_sha`, and PR-related handlers (`opened`, `labeled`, `closed`, etc.) let an attacker create/archive/unarchive review stacks or manipulate `PullRequest` records for repositories they do not control, all without ever knowing the victim organization's real webhook secret. This is a cross-repository/cross-organization write achieved purely by exploiting the unauthenticated-organization case, matching the "High" bar for unauthenticated influence over stack/task state via a binding that is supposed to be enforced by the deployment-trust model (organization authenticated vs. repository written).

### Likelihood Explanation
Requires only that the operator's `secrets.yml` contains at least one configured GitHub organization without a `webhook_secret` (explicitly allowed/"optional" per `docs/setup.md`) while other tracked repositories belong to different, secured organizations in the same instance — a realistic and undocumented-as-dangerous multi-org configuration. No credentials, GitHub App keys, or privileged accounts are needed; only knowledge of a configured-but-unsecured organization's name and the target victim repository's `full_name`, both of which can be enumerated externally (GitHub org/repo names are public).

### Recommendation
Bind the two values together: require that `repository.owner.login` (or `organization.login`) used for signature verification always matches the owner segment of `repository.full_name` before dispatching to handlers, and reject payloads where they diverge. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is unset for a per-organization config in multi-org mode — treat a missing secret as a hard configuration error rather than "skip verification."

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.github`: `orgA` (no `webhook_secret` set) and `orgB` (has a real `webhook_secret`, tracks stack `orgB/victim-repo`).
2. POST to `/webhooks` with `X-Github-Event: push`, no valid `X-Hub-Signature` needed, and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request passes.
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and enqueues `GithubSyncJob` for the victim's stack with the attacker-supplied `expected_head_sha`, despite the request never being authenticated for `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
