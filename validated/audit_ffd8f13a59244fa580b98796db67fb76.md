### Title
Webhook signature verification is scoped by attacker-controlled `repository.owner.login`, while stack mutation is scoped by a different attacker-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (as documented and supported by `config/secrets.development.shopify.yml`), `WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a payload against using `repository_owner`, which is read straight out of the unauthenticated JSON body: `params.dig('repository', 'owner', 'login')` [1](#0-0) . That value is then used only to select the verifier: `github_app = Shipit.github(organization: repository_owner)` followed by `github_app.verify_webhook_signature(...)` [2](#0-1) . But the actual mutation performed by event handlers is scoped to a **different** field of the same unauthenticated body: `payload.dig('repository', 'full_name')`, used by `Handler#stacks`/`#repository_name` to look up the target `Repository`/`Stack` [3](#0-2) , and concretely by `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` [4](#0-3) .

### Finding Description
The binding that should hold is: **organization whose signature was verified == organization whose repository is written to**. Both values are read from the same untrusted JSON body but from independent fields (`repository.owner.login` vs `repository.full_name`), and nothing enforces that `repository.full_name` is prefixed by `repository.owner.login`.

`GithubApp#verify_webhook_signature` explicitly treats an unconfigured secret as automatic success: `return true unless webhook_secret` [5](#0-4) . This is a deliberate accommodation for orgs that don't configure a webhook secret (see `webhook_secret: # nil` in the multi-org sample config) [6](#0-5) .

Because `repository_owner` is attacker-controlled (it comes straight from the raw JSON body before any signature check [7](#0-6) ), an attacker who knows that *any* configured organization on the instance has a blank/nil `webhook_secret` can craft a single POST to `/webhooks` where:
- `repository.owner.login` = the organization with no configured secret (so `verify_webhook_signature` short-circuits to `true` regardless of the `X-Hub-Signature` header), and
- `repository.full_name` = `"<protected-org>/<protected-repo>"`, i.e., an entirely different, properly-secured organization/repository that the operator actually cares about protecting.

`verify_signature` passes (using the unprotected org's app), and `create` then dispatches the full attacker payload to `Shipit::Webhooks.for_event(event)` handlers [7](#0-6) , which resolve the target `Stack` purely from `repository.full_name` — the field never covered by the signature check that was actually performed.

### Impact Explanation
For the `push` event this lets an unauthenticated attacker force `Stack#sync_github` to run with an attacker-chosen `expected_head_sha` against any tracked repository on the instance, as long as one configured organization on the same Shipit deployment has no webhook secret. Since deploy eligibility, commit tracking, CI status resync, and eventual deploy/rollback triggers all flow from `sync_github`, this can lead to an unauthorized deploy pipeline state change for a repository the attacker does not control, satisfying the "unauthorized deploy" bar. Other handlers keyed the same way (`membership`, `pull_request`, `status`, `check_suite`) are similarly reachable for the spoofed org/repo combination, e.g. `MembershipHandler` team/user membership changes, or forged commit `status` records feeding `_validateMaxLTV`-equivalent CI gating in Shipit (blocking/allowing deploys).

This requires a specific multi-org misconfiguration (one org configured without a webhook secret) to be exploitable against a *different, properly secured* org — it is not exploitable in a single-org deployment with a secret configured, since then `repository_owner` always resolves to the one app whose secret protects the same repositories.

### Likelihood Explanation
Requires: (1) the operator running a multi-organization Shipit instance, and (2) at least one configured organization with a blank `webhook_secret` (explicitly supported and shown as a valid config shape in `config/secrets.development.shopify.yml`) while other organizations are properly secured. This is a plausible but non-default operational configuration, not a universal default.

### Recommendation
Verify the webhook signature using the GitHub App associated with the *actual* target repository (derived from `repository.full_name`) rather than `repository.owner.login`, or, at minimum, cross-check that `repository.full_name`'s owner segment matches `repository_owner` before invoking any handler. Alternatively, disallow/require a webhook secret for every configured organization so `verify_webhook_signature` can never short-circuit to `true`.

### Proof of Concept
1. Configure Shipit with two orgs: `secure-org` (webhook secret set, has a tracked stack `secure-org/prod-app`) and `unsafe-org` (no `webhook_secret`, i.e., `nil`), as allowed by `config/secrets.development.shopify.yml` [8](#0-7) .
2. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsafe-org" },
    "full_name": "secure-org/prod-app"
  }
}
```
3. `verify_signature` looks up `Shipit.github(organization: "unsafe-org")` and calls `verify_webhook_signature`, which returns `true` unconditionally because `unsafe-org`'s `webhook_secret` is blank [5](#0-4) .
4. `create` proceeds and `PushHandler` resolves the stack via `Repository.from_github_repo_name("secure-org/prod-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the `secure-org` stack [4](#0-3) [3](#0-2)  — despite never presenting a valid signature for `secure-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
