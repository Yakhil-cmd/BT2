## Finding

### Title
API requests can spoof the acting `User` identity via an unverified `X-Shipit-User` header, decoupling the credential that authenticates the request from the identity attributed to the deploy/rollback it performs - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The bug class in the report is a value that is supposed to be bound at a verified point (per-pool `init`) but is instead taken from an unrelated, earlier, unverified context (the implementation's `constructor`), so every downstream user of that value inherits the wrong binding. The analogous binding in shipit-engine is: **the credential that authenticates an API request (`ApiClient` token) vs. the `User` identity that gets attributed to the action the request triggers.** The API controller derives `current_user` from a client-supplied `X-Shipit-User` header with no signature, session, or ownership check tying that header to the authenticated `ApiClient`.

### Finding Description
`Shipit::Api::BaseController#authenticate_api_client` authenticates the caller strictly by verifying an `ApiClient` token: [1](#0-0) 

Separately, `current_user` — the identity attributed to the action — is derived from a request header the client fully controls, with no cryptographic or session binding to the token that was just verified: [2](#0-1) 

`identify_user` does a case-insensitive lookup of `User` by `login` for whatever value is placed in `X-Shipit-User` — any existing Shipit user, including admins/deployers, can be named this way. There is no check that the `ApiClient`'s `creator` matches this header, nor any signature over the header value.

This resolved `current_user`/`@task.user` is subsequently used to set the git committer identity that Shipit itself uses when executing deploy/rollback steps on the deploy host: [3](#0-2) 

So the equality that should hold — `identity authenticated by the ApiClient token == identity attributed to the deploy/rollback (SHIPIT_USER / GIT_COMMITTER_NAME / GIT_COMMITTER_EMAIL)` — does not hold. Just as the StakingVault bug let a single `constructor`-time value (`start`) silently apply to every clone regardless of when it was actually created, here a single unverified header value silently overrides the actually-authenticated identity for every API-triggered task, regardless of which `ApiClient`/creator really issued the request.

### Impact Explanation
Any holder of a valid `ApiClient` token with `deploy:stack` (or task-creation) permission — which per `ApiClient::PERMISSIONS` is a narrow, delegated capability — can impersonate any other Shipit `User` recorded in the system for the purposes of:
- The `SHIPIT_USER`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` values injected into the deploy/rollback shell environment and used for git commits made by the deploy process, falsifying authorship/audit trail of an actual deploy/rollback.
- Any UI/API surface that attributes the task/deploy `user` to a specific person for accountability.

This breaks the deployment-trust binding between the credential that was actually authenticated and the identity the system records/acts as, enabling an unauthorized deploy/rollback to be misattributed to (or effectively "performed as") a different, potentially more privileged user without their involvement — falling in the same class as the required "unauthorized deploy or rollback" impact bucket.

### Likelihood Explanation
Exploitation requires only possession of any legitimate `ApiClient` token scoped to `deploy:stack`/`write:hook`-style permissions (an ordinary, low-privilege integration credential explicitly intended to be distributed to CI/automation), plus knowledge of a target user's `login` (which is public GitHub information). No secret, GitHub App key, or webhook secret is needed, so this does not fall under the excluded "requires webhook_secret / GitHub App private key / privileged account" categories.

### Recommendation
Do not resolve `current_user` from a client-supplied header. Bind the acting identity to the authenticated credential itself — e.g., derive it strictly from `current_api_client.creator`, or require an additional signed/verified claim (equivalent to moving `start` assignment from the shared `constructor` into the per-instance `init`) rather than trusting `X-Shipit-User` verbatim.

### Proof of Concept
1. Obtain (or be issued) any `ApiClient` token with `deploy:stack` permission, e.g. `spy`/`here_come_the_walrus` fixtures show minimal permission sets are normal: [4](#0-3) 
2. Send a task/deploy-creation request through the API with header `X-Shipit-User: <victim-login>` for an existing privileged user.
3. `identify_user` resolves `current_user` to the victim regardless of which `ApiClient`/creator issued the request: [5](#0-4) 
4. The resulting task/deploy is executed with `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` set to the victim's identity: [6](#0-5) 

**Note:** I could not verify within the available tool budget whether any additional authorization-sensitive logic (e.g., lock-ownership overrides) also keys off this spoofable `current_user`, which would strengthen the impact further; the finding above is based on the confirmed attribution path only.

        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end
        return if @current_api_client

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'
        render(status: :unauthorized, json: { message: 'Bad credentials' })
      end
