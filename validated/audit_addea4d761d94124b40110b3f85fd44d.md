### Title
Unit/authentifier signature malleability enables transaction (unit) ID mutation — ([File: signature.js])

### Summary
`signature.js`'s `verify()` function used for the `sig` authentifier check does not enforce canonical (low-S) ECDSA signatures before calling `ecdsaVerify()`, while the unit's own identity hash (`getUnitHash`/`getUnitContentHash`) is computed over the full `authors` array *including* the `authentifiers` (raw signature bytes). This reproduces the classic ECDSA/transaction-malleability bug referenced in the external report: a signature can be transformed into a second, still-valid signature for the identical message/pubkey, which changes the resulting unit hash without the attacker knowing the private key.

### Finding Description
The signature primitive used for unit authors is: [1](#0-0) 
which calls `ecdsa.ecdsaVerify()` directly on the raw 64-byte compact signature with no low-S/canonical-form normalization or check.

Contrast this with the PEM/secp256k1 verification path elsewhere in the same file, which explicitly calls `ecdsa.signatureNormalize()` before verifying — showing the codebase is aware of the canonicalization concern in one code path but not in the primary unit-authentifier path: [2](#0-1) 

The `sig` authentifier evaluated during unit validation calls this non-normalizing `verify()`: [3](#0-2) 

Because ECDSA signatures are inherently malleable — for any valid `(r, s)` there exists a second valid signature `(r, n-s)` for the same message and public key, computable without the private key — an attacker who observes a broadcast (but not-yet-stable) unit can flip `s` in the `authentifiers` field and produce a second, equally-valid signature blob.

The unit's identity hash then depends on this signature content. `getUnitContentHash()` hashes `getNakedUnit(objUnit)`, and `getNakedUnit()` does **not** strip `authors[i].authentifiers`, only `messages[i].payload`: [4](#0-3) 
This content hash then feeds directly into the externally-visible unit identifier: [5](#0-4) 

By contrast, `getUnitHashToSign()` (the hash that is actually signed) explicitly deletes `authentifiers` before hashing, confirming that the signature bytes are not part of the signed content but *are* part of the final unit-identity hash: [6](#0-5) 

No low-S/canonical enforcement exists anywhere in the validation path for the `sig` authentifier (`definition.js`/`validation.js`); the only place `signatureNormalize` is used is the unrelated PEM key verification helper.

### Impact Explanation
Because the final `unit` hash incorporates the malleable signature bytes, an attacker who intercepts a broadcast, not-yet-stable unit can rebroadcast a bit-flipped variant with a **different unit hash** but identical economic effect (same inputs/outputs/messages). This is the ocore analog of the historical Bitcoin transaction-malleability bug:
- Wallets/services tracking confirmation by the original `unit` hash will never see it confirm, since the network instead confirms the malleated variant — this can cause double-crediting/accounting failures for downstream consumers of unit-hash-based confirmation.
- The two variants form a genuine double-spend at the DAG level (same inputs consumed by two differently-hashed units); this forces the network's non-serial/stability conflict-resolution mechanism into a race the original author did not intend, i.e., node disagreement over which of the two attacker-relayed units is the "real"/stable one — squarely a "node disagreement on validity or stability" outcome.
- Any downstream logic (light wallets, exchanges, AAs, or other agents) that references or waits on a specific `unit` value from a peer-supplied signed payload could be permanently desynchronized from the actually-confirmed unit.

### Likelihood Explanation
Likelihood is High: any observer of network traffic (not necessarily a validator) who sees a unit before it is included in a stable MC can compute the malleated authentifier trivially (`s' = n - s`, adjusted encoding) — no cryptographic secret or privileged network position beyond ordinary p2p relay/observation is required, and the check in `definition.js`/`signature.js` will accept the mutated signature as valid.

### Recommendation
Enforce canonical low-S signatures in `signature.js`'s `verify()` (mirroring the `signatureNormalize()` call already used in `verifyMessageWithSecp256k1PemPubKey`) before calling `ecdsaVerify()`, and/or reject `authentifiers` sig values whose `s` component exceeds `n/2` during `sig` authentifier validation in `definition.js`. Additionally, consider excluding `authentifiers`/signature material from `getUnitContentHash`/`getUnitHash` computation (deriving the unit id purely from the hash-to-sign content plus author addresses) so signature malleability cannot affect the canonical unit identifier at all.

### Proof of Concept
1. Author A signs and broadcasts a valid unit U with `sig` authentifier `(r, s)`, where `verify(unit_hash_to_sign, sig, pubkey)` succeeds via `signature.js:16-25`.
2. Before U becomes stable, an observer computes `s' = n - s` (standard ECDSA malleability transform) and re-encodes the authentifier bytes accordingly, producing signature `sig'`.
3. `signature.verify(unit_hash_to_sign, sig', pubkey)` still returns `true` (no canonical-form check), so `definition.js`'s `sig` case at lines 745-748 accepts unit U' with authentifier `sig'` as fully valid.
4. Because `getUnitContentHash`/`getUnitHash` (`object_hash.js:33-65`) include `authentifiers` in the hashed content, U and U' compute to two different `unit` hash values despite identical semantic content (same parents, inputs, outputs, messages).
5. The observer broadcasts U' to the network before/alongside U, creating two DAG units with the same effective payment but different identifiers, forcing the network to resolve which becomes stable while any tooling watching for confirmation of U's original hash never observes it confirm.

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
