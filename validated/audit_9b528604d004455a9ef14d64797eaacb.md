### Title
Unbounded `in merkle` authentifier lets a single unit author trigger disproportionate CPU cost via oversized/crafted merkle-proof strings - (File: definition.js, merkle.js)

### Summary
`MAX_AUTHENTIFIER_LENGTH` caps a raw authentifier at 4096 bytes [1](#0-0) , but that generic length cap is the *only* check performed before the `'in merkle'` authentifier branch treats the authentifier string as a specially-formatted merkle proof (`index-sibling1-sibling2-...-root`) and feeds it straight into `merkle.deserializeMerkleProof()`/`merkle.verifyMerkleProof()` without validating that the content is actually a well-formed proof for the claimed depth. This mirrors the FFmpeg XBIN issue: data that looks like ordinary bytes (an "authentifier") is demuxed into a structured format (a merkle proof) without validating that the structure is sane, so a small attacker-controlled input can be expanded into disproportionately more hashing work than a legitimate proof of the same byte size would require.

### Finding Description
In `definition.js`, the `'in merkle'` authentifier evaluator does:
```
var serialized_proof = assocAuthentifiers[path];
var proof = merkle.deserializeMerkleProof(serialized_proof);
...
merkle.verifyMerkleProof(element, proof)
``` [2](#0-1) 

`deserializeMerkleProof` blindly splits the string on `"-"` and treats everything between the first and last token as a list of sibling hashes, with no limit on the number of siblings and no check that each token is actually a valid-looking hash:
```
function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
``` [3](#0-2) 

`verifyMerkleProof` then iterates over every sibling and performs a SHA-256 hash per iteration:
```
for (var i = 0; i < proof.siblings.length; i++) {
    if (index % 2 === 0)
        the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
    else
        the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
    index = Math.floor(index / 2);
}
``` [4](#0-3) 

Because the only size gate the authentifier ever passes through is the generic `MAX_AUTHENTIFIER_LENGTH` (4096 bytes) check applied uniformly to *all* authentifier types [5](#0-4) [6](#0-5) , an attacker can pack the 4096-byte budget with the minimum-length separator/sibling tokens (e.g. `"1-2-2-2-...-2-root"`) to maximize the sibling count, producing hundreds of SHA-256 operations from one authentifier field, on every node that validates the unit (and, via `signed_message.js`, in `is_valid_signed_package`/PEM-signed-package verification and other authentifier re-validation paths) — all reachable directly by a single unpermissioned unit poster.

By contrast, the formula-level `is_valid_merkle_proof()` builtin *does* impose meaningful, format-aware limits (proof string ≤ 1024 chars, and after the PEM-curves fix, `siblings.length <= 50` and every sibling must be a non-empty string) before calling the same `verifyMerkleProof`:
```
if (proof.length > 1024) return setFatalError("proof is too large", ...);
objProof = merkle.deserializeMerkleProof(proof);
if (bPostPemCurvesFix) {
    if (!Array.isArray(objProof.siblings) || !objProof.siblings.every(ValidationUtils.isNonemptyString))
        return cb(false);
    if (objProof.siblings.length > 50)
        return cb(false);
}
``` [7](#0-6) 

The `'in merkle'` authentifier path in `definition.js` has no equivalent sibling-count or per-sibling shape check — it simply defers to `objValidationState.complexity`/`MAX_COMPLEXITY`/`MAX_OPS` counters that only track the *definition tree* size, not the size of the runtime-supplied authentifier payload being parsed. The `in merkle` op itself contributes a constant complexity/op cost regardless of how many "siblings" the crafted authentifier string decodes into [2](#0-1) , so the anti-spam complexity accounting does not scale with the actual work performed.

### Impact Explanation
This is a CPU-amplification / degraded-performance issue reachable by any unit poster who defines (or uses) an address whose definition includes an `'in merkle'` clause and who supplies a crafted authentifier at that path. Every full node (and every peer/AA re-evaluating this authentifier, e.g. via `signed_message.validateSignedMessage` for signed packages) pays the amplified hashing cost during unit/authentifier validation, while the attacker's cost is bounded by the 4096-byte authentifier limit. This matches the CVE class (unexpected additional CPU load from unvalidated format assumptions) but is capped by the existing 4096-byte ceiling, keeping the amplification factor small (roughly a few hundred SHA-256 calls per validation, not unbounded) — consistent with a Medium-severity resource/DoS-adjacent finding rather than a High-severity one.

### Likelihood Explanation
Likelihood is moderate: constructing the address definition and crafting a maximal-siblings string within 4096 bytes requires no privileged access — only posting a unit with an address using an `'in merkle'` condition and a matching data feed reference, which is an ordinary DAG operation available to any user. No node collusion or elevated permissions are needed.

### Recommendation
Apply the same defensive checks used in `formula/evaluation.js`'s `is_valid_merkle_proof` to the `'in merkle'` authentifier path in `definition.js`: after `merkle.deserializeMerkleProof()`, validate that `proof.siblings.length` is bounded by a small constant (e.g. ≤ 50) and that every sibling is a well-formed hash-length string, rejecting the authentifier (fatal error) otherwise. Additionally, consider making `MAX_AUTHENTIFIER_LENGTH` op-specific so `'in merkle'` authentifiers cannot use the full 4096-byte budget purely to inflate the sibling count, and account for the decoded proof size in the per-unit complexity/ops counters rather than only the static definition size.

### Proof of Concept
1. Create an address whose definition contains `['in merkle', [[oracleAddress], 'feed_name', '=', 'expected_value']]` at some path `p`.
2. Compute any valid short serialized proof normally, e.g. `"0-abc...-root"`.
3. Instead, craft an authentifier string at path `p` consisting of as many minimal filler "sibling" tokens as fit in 4096 bytes, e.g. `"0-" + "x-".repeat(N) + "root"` where `N` is maximized under the 4096-byte cap (hundreds of tokens).
4. Sign/submit a unit using this address with the crafted authentifier at path `p`.
5. Observe that `merkle.verifyMerkleProof()` performs one SHA-256 call per token in the crafted string during validation — every validating node incurs this hashing cost even though `deserializeMerkleProof` never validates that the tokens are plausible hash values, and the definition-side complexity/ops counters do not reflect the inflated sibling count.
