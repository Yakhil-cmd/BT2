### Title
AA addresses can permanently accumulate un-spendable headers-commission (and witnessing) byte rewards - ([File: validation.js])

### Summary
When an autonomous agent (AA) sends a response unit, that unit is a normal DAG unit authored by the AA's own address (`aa_composer.js` builds `objUnit.authors = [{ address: address }]`). Like any other unit, this response unit can be selected as the "winning" child of a parent unit and thus earn headers-commission bytes (and, in principle, witnessing bytes) that get credited to the AA's address in `headers_commission_outputs`/`witnessing_outputs`. However, `validateAuthor`/`validatePaymentInputsAndOutputs` in `validation.js` explicitly forbids the only interface that can spend this class of reward (`type: "headers_commission" | "witnessing"` payment inputs) whenever the unit is an AA-generated unit. Since an AA's outgoing units are exclusively produced by `aa_composer.js` (never hand-crafted by a user), and `aa_composer.js` never builds these special input types, any bytes earned this way by an AA address become permanently unspendable/locked at that address — the exact "missing interface to claim reward" bug pattern described in the report (BGT reward locked in the Staker contract because it lacked the analogous `getReward()`-style hook).

### Finding Description
- Headers commission is a passive byte reward paid to the address that authored the "winning" child unit of another unit (or to `earned_headers_commission_recipients`), computed and stored in `headers_commission_outputs`/`witnessing_outputs`, and it is only spendable in a payment message through a dedicated input of `type: "headers_commission"` or `type: "witnessing"`: [1](#0-0) [2](#0-1) 

- These special inputs can only be added by the composer logic (`inputs.js`) when building a payment for an ordinary (non-AA) unit: [3](#0-2) 

- Crucially, `validation.js` explicitly disallows this input type whenever the unit being validated belongs to an AA (`objValidationState.bAA`): [4](#0-3) 

- AA response units are, however, regular DAG units authored by the AA's own address, produced entirely by `aa_composer.js`, and they are eligible to win headers commission exactly like any user-authored unit, because the eligibility rule only checks unit authorship/child relationships, not whether the author is an AA: [5](#0-4) [6](#0-5) 

- `aa_composer.js`'s payment-completion logic (`completePaymentPayload`) only ever picks funds from the `outputs` table (stable/unstable payment outputs sent by AAs), never from `headers_commission_outputs`/`witnessing_outputs`: [7](#0-6) 

Because an AA address can never again author a manually-signed, non-AA unit (its behavior is permanently governed by its `['autonomous agent', {...}]` definition, and `validateAuthor` throws if an AA-defined address tries to author a plain unit outside the AA engine), and because the AA engine itself is prohibited from using `headers_commission`/`witnessing` inputs, any bytes earned by the AA as headers/witnessing commission become permanently unrecoverable.

### Impact Explanation
This results in genuine, irreversible freezing of AA-owned funds: any bytes that accumulate in `headers_commission_outputs`/`witnessing_outputs` under an AA's address can never be spent by that AA, effectively burning bytes that were rightfully earned by the AA and reducing the AA's usable balance without any path to recovery. This matches the "AA fund loss or freezing" impact criterion.

### Likelihood Explanation
This occurs deterministically any time an AA's response unit becomes the "best child" (winner) of a parent unit under the existing headers-commission distribution algorithm in `headers_commission.js` — a routine, unprivileged, naturally occurring event in the DAG (it doesn't require any attacker; it happens as part of normal unit posting/inclusion), so the likelihood of the condition being triggered is high for any active AA.

### Recommendation
Either (a) exclude AA-authored units from earning headers-commission/witnessing rewards during the headers-commission distribution calculation (so bytes are instead assigned to a spendable, non-AA address or simply not paid to the AA author), or (b) allow the AA engine to construct `headers_commission`/`witnessing` type payment inputs when composing its response/bounce units, giving the AA an actual "claim" mechanism for these rewards (analogous to adding a `getReward()`-style interface in the referenced report).

### Proof of Concept
1. Define and register an AA (e.g. a simple bounce-back or pass-through AA) so its address becomes an active AA address, per `aa_composer.js` unit construction shown at lines 1369-1386.
2. Ensure the AA responds to triggers frequently enough that at some MC index its response unit is chosen by `headers_commission.js`'s `getWinnerInfo` (see `headers_commission.js:144-187`) as the winning child of a parent unit, crediting `headers_commission_outputs` at the AA's own address.
3. Observe that the byte reward accumulates in `headers_commission_outputs` for the AA address.
4. Attempt to have the AA spend these bytes: any composed payment for the AA will only include ordinary `outputs` (see `aa_composer.js:1223-1244`), and any manual attempt to include a `type:"headers_commission"` input in a unit where `objValidationState.bAA` is true is rejected by `validation.js:2531-2532` with `"headers_commission in AA"`.
5. Because the AA address can never again post a manually-authored non-AA unit, the accumulated headers-commission bytes are permanently stuck and unspendable.
