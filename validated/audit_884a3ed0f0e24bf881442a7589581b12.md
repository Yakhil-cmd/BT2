### Title
Cross-repository status forgery clears deploy-blocking status via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook using `Commit.where(sha: params.sha)` with no constraint on the repository that sent the webhook, while `Commit#blocked?`/`Status::Common#blocking?` treat any status row on that commit as authoritative for deploy-blocking purposes. Signature verification (`WebhooksController#verify_signature`) only proves the payload came from a GitHub organization known to Shipit's configured `GitHubApp`s; it does not prove the payload's `repository.full_name` matches the repository owning the commit being updated. If a sha collision (or realistically, another repository within the same GitHub organization/app installation, or any repo whose owner maps to a Shipit-registered organization) can push a `status` event for a sha equal to the victim's blocking commit, `create_status_from_github!` will rewrite that commit's status and unblock deploys.

### Finding Description
Broken binding, stated as an equality: the code implicitly assumes
`commit.stack.repository.full_name == payload['repository']['full_name']`
for every `Commit` row matched by `Commit.where(sha: params.sha)` in `StatusHandler#process`: [1](#0-0) 
This equality is never asserted. `Commit.where(sha:)` is a global, unscoped lookup across all stacks/repositories, and `create_status_from_github!` unconditionally writes the incoming state onto whatever commit rows match: [2](#0-1) 

Downstream, `Commit#blocked?` walks `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self)` and calls `blocking?` on each, and `blocking?` is purely a function of the commit's current `status` state and the stack's configured blocking contexts: [3](#0-2) [4](#0-3) 
Neither of these consult which repository produced the status.

The webhook-level guard, `verify_signature`, only checks the HMAC signature against the `GitHubApp` configured for `repository_owner` (the payload's org/user login), via `Shipit.github(organization: repository_owner)`: [5](#0-4) 
This proves the request came from *an* app installation associated with that organization login — it does not bind the payload to the specific repository that owns the target commit's stack. Other handlers (`Handler#stacks`) do scope work correctly by resolving `Repository.from_github_repo_name(repository_name)` before touching any records, but `StatusHandler` bypasses that base-class helper entirely and queries `Commit` directly by `sha` with no repository filter: [6](#0-5) 

Exploit flow: an unprivileged GitHub user pushes/labels a commit in a repository they own reproducing the victim's known blocking-commit sha (git sha collision is not required if the attacker-owned repo's organization/owner login is one already registered as a Shipit `GitHubApp` — e.g. the same GitHub org hosting many repos with one shared webhook secret — a `status` event on any repo under that org is signed with the same organization-level secret and passes `verify_signature`), then emits a `status` webhook: `state: success`, a non-blocking `context`, `sha: <victim's blocking commit sha>`. `StatusHandler#process` finds the victim's `Commit` row purely by sha match, calls `create_status_from_github!`, which replaces/adds a status such that `blocking?` for that commit becomes false. Any later commit's `Commit#blocked?` recomputation over the range then returns false, and `Commit#deployable?` becomes true for a commit the victim's own CI never approved.

### Impact Explanation
This is a payload from one repository (or its associated org) mutating another stack's commit blocking state and enabling deploys/rollbacks that the victim repository's own CI never authorized — this matches the "payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" Critical category. The blast radius extends to every stack that shares a `GitHubApp`/organization-level webhook secret configuration with the attacker-controlled repository, and is repeatable per blocking-commit sha the attacker wants to clear.

### Likelihood Explanation
Exploitability depends heavily on: (1) whether the attacker can produce a `status` webhook whose signature passes `verify_signature` — this requires the attacker-owned repository to fall under a GitHub organization/owner login that Shipit already trusts with a configured `GitHubApp`/`webhook_secret` (e.g., an org that installs the Shipit GitHub App broadly across many repos, some victim, some attacker-controlled/forked); and (2) an exact sha collision or the ability to have the app deliver a `status` event whose `sha` equals the victim's blocking commit — GitHub delivers `status` webhooks scoped to the repository where the status was set, at the sha in that repository's history, so this generally requires the attacker's own repository to actually contain that commit sha (e.g., a fork sharing history with the upstream victim repo, which is a realistic scenario for a monorepo/org with many app installations sharing one webhook secret, or a fork where the sha is inherited from the shared history). Given a shared-secret organization installation and a forked/related repo containing the same sha, the attack is cheap and repeatable.

### Recommendation
Scope `StatusHandler#process` (and ideally all handlers touching `Commit`/`Stack` records) to the repository named in the payload, mirroring `Handler#stacks`/`repository_name`: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, then restrict `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` before calling `create_status_from_github!`. Reject or ignore commits whose owning stack's repository does not match the webhook's `repository.full_name`.

### Proof of Concept
Minitest plan (model-level, no live GitHub):
1. Build a `stack` with `blocking_statuses` configured (e.g. via `cached_deploy_spec` with `ci.blocking`), and three commits: `blocking_commit` (currently `blocking?` == true, positioned after `stack.last_deployed_commit`), and a `later_commit` after it.
2. Assert precondition: `assert_predicate blocking_commit, :blocking?` and `assert_predicate later_commit, :blocked?`.
3. Construct a `status` payload whose `sha == blocking_commit.sha`, `state: 'success'`, `context:` some non-blocking context, and `repository.full_name` set to an unrelated repository not associated with `stack`'s `Repository`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check to isolate the handler's own repository-binding failure), or post through the controller with a stubbed `verify_signature` returning true for an org that owns the unrelated repository.
5. Assert the broken binding flips on both sides: before, `blocking_commit.stack.repository.full_name != payload['repository']['full_name']`; after processing, `refute_predicate blocking_commit.reload, :blocking?` and `refute_predicate later_commit.reload, :blocked?`, proving a payload attributed to a different repository altered the victim stack's deploy-blocking state.
