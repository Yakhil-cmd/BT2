### Title
Missing `PalletFeature::Approvals` check in `do_cancel_approval` / `do_clear_all_transfer_approvals` allows approval management even when the Approvals feature is disabled - ([File: substrate/frame/nfts/src/features/approvals.rs])

### Summary
`pallet-nfts` exposes a governance-controlled `PalletFeatures` bitflag (`Config::Features`/`Features` storage, tested in `pallet_level_feature_flags_should_work`) that is meant to switch off entire functional areas of the pallet — `Trading`, `Approvals`, `Attributes`, `Swaps` — returning `Error::MethodDisabled` for any dispatchable in that area. `do_approve_transfer` (the "create" side of the approvals workflow) enforces this check, but the paired "remove/cancel" operations, `do_cancel_approval` and `do_clear_all_transfer_approvals`, do not. This is structurally the same defect class as the reported Shopware issue: a feature toggle gates the "create" action in the UI/one code path, but the corresponding cancel/removal action in the same workflow omits the identical enforcement, letting a normal signed user still exercise part of the disabled feature.

### Finding Description
`do_approve_transfer` explicitly gates itself: [1](#0-0) 

`do_cancel_approval`, which is dispatched from the public, signed `cancel_approval` extrinsic and mutates the very same `Item::approvals` storage, has no equivalent `ensure!(Self::is_pallet_feature_enabled(PalletFeature::Approvals), ...)` guard: [2](#0-1) 

Likewise `do_clear_all_transfer_approvals` (backing the `clear_all_transfer_approvals` extrinsic) is also unguarded: [3](#0-2) 

For comparison, every other feature area in `pallet-nfts` consistently applies the flag check at the start of its `do_*` helper — `do_set_price`/`do_buy_item` for `PalletFeature::Trading`, `do_create_swap`/`do_claim_swap` for `PalletFeature::Swaps`: [4](#0-3) [5](#0-4) 

This shows the `Approvals`-area functions were meant to follow the same enforced-on-every-entrypoint pattern, but `cancel_approval`/`clear_all_transfer_approvals` were left out — exactly analogous to Shopware's `CancelOrderRoute` never checking `core.cart.enableOrderRefunds` even though the button/creation path is gated by it (GHSA-r2vg-hvjm-fg38).

The attacker here is an ordinary signed extrinsic caller (item owner or, past the approval deadline, any account), with no privileged origin, matching the "no privileged role" requirement.

### Impact Explanation
The direct consequence is limited: `do_cancel_approval` and `do_clear_all_transfer_approvals` only remove entries from `Item::approvals`; they do not themselves move any asset or transfer ownership. Compared to `do_set_price`/`do_buy_item`/`do_create_swap`/`do_claim_swap` (which move funds/assets and are properly gated), this omission does not by itself enable unbacked issuance or theft. The measurable impact is an **integrity break of the feature-flag invariant**: if a chain operator disables `PalletFeature::Approvals` (e.g., to shut down the whole delegated-approval subsystem, such as in response to an incident), users can still call `cancel_approval`/`clear_all_transfer_approvals` and mutate delegation state that the flag was supposed to freeze, receiving no `MethodDisabled` error unlike every sibling extrinsic in the same feature group. This mirrors the CVSS profile of the Shopware advisory (no confidentiality/availability impact, low integrity impact) rather than a fund-loss scenario.

I was not able to verify, within the available tool budget, whether the `transfer` extrinsic's delegate-permission check (in `substrate/frame/nfts/src/lib.rs`, the caller-vs-owner-vs-approved-delegate branch feeding into `do_transfer`) also omits the `PalletFeature::Approvals` check. If it does, a delegate that was approved before the feature was disabled could still execute an actual ownership transfer while `Approvals` is supposedly disabled, which would raise the severity to a genuine asset-movement bypass. This part is **unconfirmed** and should be checked before filing, since it changes the severity materially.

### Likelihood Explanation
Likelihood of triggering the *code path* is high — it only requires an existing approval and a normal signed call to `cancel_approval` or `clear_all_transfer_approvals` while `Config::Features`/`Features` has `Approvals` disabled. Likelihood of this mattering in practice depends on whether any live Parity-maintained runtime (Asset Hub, etc.) actually disables `PalletFeature::Approvals` at runtime — this pallet exposes the flag as configurable, but I did not confirm any production runtime currently toggles it off, so real-world exposure is uncertain.

### Recommendation
Add the same `ensure!(Self::is_pallet_feature_enabled(PalletFeature::Approvals), Error::<T, I>::MethodDisabled);` guard at the top of `do_cancel_approval` and `do_clear_all_transfer_approvals` in `substrate/frame/nfts/src/features/approvals.rs`, matching the pattern already used in `do_approve_transfer`, `do_set_price`, `do_buy_item`, `do_create_swap`, and `do_claim_swap`. Additionally, audit `substrate/frame/nfts/src/lib.rs`'s `transfer`/`do_transfer` delegate-permission branch to confirm whether existing approvals remain exercisable (i.e., an actual ownership transfer can still occur) while `PalletFeature::Approvals` is disabled, and add the missing check there if so.

### Proof of Concept
No executable PoC was run. The finding is based on direct source inspection showing the asymmetry between `do_approve_transfer` (guarded) and `do_cancel_approval`/`do_clear_all_transfer_approvals` (unguarded) in `substrate/frame/nfts/src/features/approvals.rs`, contrasted with the consistently-guarded `Trading`/`Swaps` feature functions elsewhere in the same pallet. A minimal repro would be: (1) `Features::set` (or equivalent governance call) to disable `PalletFeature::Approvals`, (2) call `Nfts::cancel_approval` or `Nfts::clear_all_transfer_approvals` as a signed owner on an item with an existing approval — expected result if the flag were enforced is `Error::MethodDisabled`; actual result (per the read code, not executed) is `Ok(())`. This was not executed against a running node/test harness in this session, so execution status is "not run — inferred from source only," and the delegate-transfer-bypass extension of this finding remains unverified.

	pub(crate) fn do_cancel_approval(
		maybe_check_origin: Option<T::AccountId>,
		collection: T::CollectionId,
		item: T::ItemId,
		delegate: T::AccountId,
	) -> DispatchResult {
		let mut details =
			Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;

		let maybe_deadline = details.approvals.get(&delegate).ok_or(Error::<T, I>::NotDelegate)?;

		let is_past_deadline = if let Some(deadline) = maybe_deadline {
			let now = T::BlockNumberProvider::current_block_number();
			now > *deadline
		} else {
			false
		};

		if !is_past_deadline {
			if let Some(check_origin) = maybe_check_origin {
				ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);
			}
		}

		details.approvals.remove(&delegate);
		Item::<T, I>::insert(&collection, &item, &details);

		Self::deposit_event(Event::ApprovalCancelled {
			collection,
			item,
			owner: details.owner,
			delegate,
		});

		Ok(())
	}

	pub(crate) fn do_clear_all_transfer_approvals(
		maybe_check_origin: Option<T::AccountId>,
		collection: T::CollectionId,
		item: T::ItemId,
	) -> DispatchResult {
		let mut details =
			Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownCollection)?;

		if let Some(check_origin) = maybe_check_origin {
			ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);
		}

		details.approvals.clear();
		Item::<T, I>::insert(&collection, &item, &details);

		Self::deposit_event(Event::AllApprovalsCancelled {
			collection,
			item,
			owner: details.owner,
		});

		Ok(())
	}
