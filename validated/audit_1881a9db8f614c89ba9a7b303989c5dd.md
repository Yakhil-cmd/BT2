### Title
Uncharged O(N) trie iteration in `compute_gas_key_balance_sum` allows underpriced compute during DeleteAccount/DeleteKey gas-key burn - (File: `core/store/src/utils/mod.rs`, `core/store/src/trie/ops/iter.rs`)

### Summary
`compute_gas_key_balance_sum` iterates the full access-key prefix of an account (via `TrieIteratorImpl`), visiting every access key **and** every `TrieKey::gas_key_nonce` entry, unconditionally fetching the value of each node (`iter.rs` lines 373-376) before deciding whether to use it. Unlike the parallel iteration performed in `remove_account` (same file), which explicitly tracks `gas_key_nonce_count`/`gas_key_nonce_total_key_bytes` "used to calculate compute cost", `compute_gas_key_balance_sum` returns only a `Balance` and carries no accounting output, so its linear-cost trie walk is not billed as compute at all by its caller.

### Finding Description
`TrieIteratorImpl::next` (`core/store/src/trie/ops/iter.rs:342-379`) walks every node in the requested key range and, for each leaf/branch value found, unconditionally calls `self.trie_interface.get_value(value_ref, ...)` (lines 373-376) to materialize the stored bytes before returning the item to the caller.

`compute_gas_key_balance_sum` (`core/store/src/utils/mod.rs:440-479`) drives this iterator over `trie_key_parsers::get_raw_prefix_for_access_keys(account_id)`, which covers **both** `TrieKey::AccessKey` entries and all `TrieKey::gas_key_nonce` entries belonging to the account: [1](#0-0) 
For every nonce entry the loop only determines `nonce_index.is_some()` and then `continue`s — but by that point the iterator has already performed the full node descent and value fetch for that entry via `iter.rs`'s `IterStep::Value` handling. No compute/gas value is accumulated or returned by this function; it returns only `Result<Balance, StorageError>`.

Contrast this with `remove_account` in the same file, which walks the identical prefix but explicitly accumulates `gas_key_nonce_count` and `gas_key_nonce_total_key_bytes`, annotated "used to calculate compute cost": [2](#0-1) 
That counted data is fed into `storage_removes_compute` at the `runtime/runtime/src/access_keys.rs` call sites (e.g. `delete_gas_key`, lines 114-125) to charge `result.compute_usage` proportionally to the number of nonces removed: [3](#0-2) 

Because gas-key deletion/account deletion typically needs both (a) the balance sum for burning and (b) the key removal, two independent full-prefix trie traversals are performed over the same key range, but only the traversal in `remove_account`/`delete_gas_key` produces a value that is turned into charged compute. The traversal inside `compute_gas_key_balance_sum` — which does real trie node fetches and value deserialization proportional to the number of access keys + gas key nonces (`N`) — has no corresponding charge.

An attacker who creates a gas key with a large `num_nonces` (an `AddKeyAction`-controlled, attacker-chosen value) increases `N` for their own account. When `DeleteKey`/`DeleteAccount` subsequently triggers a call path that invokes `compute_gas_key_balance_sum` (used from `runtime/runtime/src/actions.rs`), the node performs O(N) trie node visits and value reads that are not reflected in the compute cost charged for that action, while the symmetric `remove_account` traversal is billed. This produces a divergence between real storage-read work performed and gas charged, i.e. free/underpriced compute proportional to the number of gas-key nonces created.

### Impact Explanation
This is a gas/storage metering bypass: an attacker can force the validating node to perform trie-node and value reads whose cost scales with attacker-chosen `N` (number of gas-key nonces) without paying compute for that specific traversal. Repeated across many accounts/receipts, this allows an attacker to consume more real per-chunk compute time than they pay for, which can be used to degrade chunk production performance relative to the gas paid (a GAS_OR_STORAGE_METERING class issue). It does not directly cause fund loss or state divergence — the balance-burning arithmetic itself is correctly computed — but it violates the "one unit of gas ≈ one unit of node work" invariant that gas metering exists to guarantee.

### Likelihood Explanation
Feasible for any unprivileged account holder: adding a gas key with a large `num_nonces` and later deleting it (or the whole account) is a normal, permitted transaction sequence requiring no special privilege. The only precondition is that `num_nonces` is attacker-controllable to a value large enough to make the extra uncharged traversal cost material; this needs confirming whether any protocol-level cap on `num_nonces` already limits this (not found in the reviewed files), which affects how severe/repeatable the exploit is at scale.

### Recommendation
Charge compute cost for the traversal performed inside `compute_gas_key_balance_sum` proportional to the number of entries visited (access keys and gas-key-nonce entries), symmetric to the accounting already done in `remove_account`/`delete_gas_key`. Either (a) have `compute_gas_key_balance_sum` also return counts/bytes visited so the caller can charge `storage_removes_compute`-equivalent cost for reads, or (b) merge the two traversals into a single pass that simultaneously sums balances and collects counts for compute charging, eliminating the extra unbilled full-prefix scan.

### Proof of Concept
Integration test in `runtime/runtime/src/access_keys.rs` (or `test-loop-tests/src/tests/gas_keys.rs`) style:
1. Create an account with a gas key configured with `num_nonces = N` for varying `N` (e.g. 10, 100, 1000).
2. Trigger `DeleteAccount` (or `DeleteKey` on the gas key) and record `action_result.compute_usage` and, if instrumented, the actual number of trie node/value reads performed (e.g. via a `TrieRecorder`/storage-read counter around the call to `compute_gas_key_balance_sum`).
3. Assert that the recorded storage reads scale linearly with `N`, but that `compute_usage` attributable specifically to the `compute_gas_key_balance_sum` traversal does not increase with `N` (i.e. only the `remove_account`/`storage_removes_compute` portion scales, while the balance-sum traversal's read cost stays effectively free), demonstrating the sub-linear/uncharged accounting relative to actual trie work performed.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
