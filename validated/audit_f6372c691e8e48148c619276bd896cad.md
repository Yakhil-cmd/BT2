I found a solid match for the analog pattern. Let me quickly confirm the view output and the scoping mechanism used elsewhere for comparison.### Title
Stack-scoped API token bypasses its stack authorization in CCMenu controller - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides both `authenticate_api_client` and `stack` in a way that breaks the binding between the stack(s) an `ApiClient` token is authorized for and the stack it actually reads. This lets the holder of a stack-scoped, read-only CCMenu token (the kind minted and distributed by `CCMenuUrlController#fetch`) read the build/deploy status of **any** stack in the installation by simply changing the `stack_id` in the URL, instead of only the single stack the token was scoped to.

### Finding Description
`Api::BaseController` establishes the trust binding "the stack a token authorizes = the stack it touches" via the `stacks` scope: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Every other API controller relies on this scoped `stack`/`stacks` helper, so a token created with a `stack_id` (e.g. `ApiClient` fixture `here_come_the_walrus`, or any CCMenu token minted for a specific stack) can only resolve `stack` to the one row it is bound to [2](#0-1) .

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving directly against the whole `Stack` table using only the unscoped `params[:stack_id]`: [3](#0-2) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`; it never checks which stack the token is bound to: [4](#0-3) 

The intended CCMenu flow mints exactly this kind of scoped token: `CCMenuUrlController#fetch` creates (or reuses) a global, permanent `ApiClient` with only `read:stack` permission and **no `stack_id`**, then builds a URL containing the current stack's id and the token: [5](#0-4) 

Because that helper-generated token itself carries no `stack_id`, the `stacks` scope in `BaseController` would already return `Stack.all` for it — but the deeper issue is structural: even for `ApiClient` records that *do* have an explicit `stack_id` (the mechanism `BaseController#stacks` exists to enforce, and which is exercised/tested elsewhere, e.g. `here_come_the_walrus`), `CCMenuController#stack` never consults `current_api_client.stack_id`. Any token with `read:stack` permission — whether deliberately scoped to one stack or not — can be pointed at an arbitrary `stack_id` path segment and receive that stack's CCMenu XML (name, last build status/label/time, web URL) rendered from `app/views/shipit/ccmenu/project.xml.builder`, because `show` calls the unscoped `stack` method: [6](#0-5) 

The equality that should hold — `stack_id bound to token == stack_id resource actually served` — is broken by this controller-local override, exactly analogous to the report's core defect: a value checked/derived at one point (the authorization-defining flag/field) is not honored consistently at the point the resource is actually served.

### Impact Explanation
This is an authorization-scope bypass: a token meant to be usable only for one stack (or, in the base app's threat model, meant to only ever expose the CCMenu status of the stack it was minted for) can be used to read the build/deploy status of any stack in the entire Shipit installation, including stacks the holder has no relationship to and no read access via the standard `stacks`-scoped API endpoints. This is an unintended cross-stack read of stack state (last build status, label, timing, web URL), matching the "unauthenticated/unauthorized read of stack state" High-impact category, since it escalates a token's authorized scope beyond what it was issued for.

### Likelihood Explanation
Likelihood is high for anyone already possessing any valid CCMenu/API token with `read:stack` permission (these tokens are long-lived, are embedded directly in CCMenu URLs distributed to CI dashboard tools, and are not stack-scoped when minted by `CCMenuUrlController`). No special privilege is required beyond having obtained one legitimate CCMenu URL/token for any single stack; the attacker then only needs to change the `stack_id` path segment of the request to enumerate/read other stacks.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, scoped `BaseController#stack`/`#stacks` helpers (i.e., `stacks.from_param!(params[:stack_id])`) so that stack resolution always respects `current_api_client.stack_id` scoping, consistent with every other API controller.

### Proof of Concept
1. Obtain a CCMenu URL/token for stack A via the normal flow: `GET /ccmenu/*stack_A` → returns `{ "ccmenu_url": ".../api/stack_A/ccmenu.xml?token=<TOKEN>" }` (per `CCMenuUrlController#fetch`).
2. As an unprivileged holder of `<TOKEN>` (e.g., anyone with access to the dashboard tool configured with this URL), issue: `GET /api/<stack_B_owner>/<stack_B_repo>/<stack_B_env>/ccmenu.xml?token=<TOKEN>` where stack B is a different, unrelated stack.
3. `Api::CCMenuController#authenticate_api_client` authenticates `<TOKEN>` successfully (the token is valid, just not meant for stack B), and `#stack` resolves stack B via the unscoped `Stack.from_param!`, so `#show` renders stack B's CCMenu XML (build status, last build label/time) even though the token was only ever issued/associated with stack A.
