## Analysis

The external report describes social engineering that induced users to approve malicious transactions ("do not click on the link, mint, or approve any transactions"). The closest reachable analog in `ocore` is the confirmation-dialog selection heuristic used when a **paired device** requests a co-signature via the `"sign"` device message. This logic decides which (softer or harsher) confirmation prompt a wallet shows the user before they approve spending, based on unreliable heuristics that a remote/paired peer directly controls.

### Title
Misleading co-signing confirmation dialog can be spoofed by a paired peer device to disguise a malicious payment as a benign contract action - ([File: wallet.js])

### Summary
When a remote peer device requests a co-signature for a shared/multisig address via the `"sign"` device message, `getSigner().sign()` in `wallet.js` decides which UX confirmation event to emit (`confirm_contract_deposit`, `confirm_contract_claim`, `confirm_contract_sign`, or the generic `confirm_on_other_devices`) based only on (a) whether one output amount happens to equal the publicly known constant `prosaic_contract.CHARGE_AMOUNT`/`arbiter_contract.CHARGE_AMOUNT`, and (b) whether the destination/peer address is already known in the local `prosaic_contracts`/`wallet_arbiter_contracts` tables. [1](#0-0) 

### Finding Description
`sendOfferToSign` is invoked whenever a co-signer is remote, sending the full `objUnsignedUnit` (attacker/peer-controlled content, since the request originates from the counterpart device) to be signed. [2](#0-1) 

The signer then tries to classify the transaction only to choose the wording of the confirmation dialog shown to the human signer:
- Step 1 looks for *any* output in *any* base-asset payment message equal to the fixed `CHARGE_AMOUNT`, and if the destination address is a known contract `shared_address`, fires the soft `confirm_contract_deposit` notice instead of a generic warning.
- Step 2 checks if the address or peer_address belongs to a known contract and fires `confirm_contract_claim`/`confirm_contract_sign` instead of the generic `confirm_on_other_devices` warning.
- Only if neither heuristic matches does the code fall back to the generic "confirm on other devices" alert. [3](#0-2) 

Because `objUnsignedUnit` is attacker-supplied (from a peer device that is a legitimate cosigner on a shared address, e.g. a contract counterparty or arbiter-contract peer whose device may be compromised, as described by the external report's "Discord/account compromise" bug class), the attacker fully controls the entire message set of the unit being signed except for the constraint that at least one output must match `CHARGE_AMOUNT` and go to the already-known contract address. Nothing prevents the same unit from also containing additional, unrelated payment outputs draining the shared address to attacker-controlled destinations. The heuristic only inspects the *first* matching output amount/address pair; it does not verify that the transaction consists *solely* of the expected contract deposit/claim, nor that no other outputs exist. This lets a malicious/compromised paired device craft a signing request that displays the softer, contract-flavored dialog (e.g., "confirm contract deposit") while the actual payload sweeps funds from the shared address to arbitrary addresses.

### Impact Explanation
If the human signer trusts the softer contract-specific prompt and approves, `handleSignature`/`sign` returns a valid signature for the full multisig unit, and `composer.js` completes cosigning and broadcasts it, causing unauthorized spending of the shared address's funds to attacker-controlled outputs — directly mirroring the report's "please do not click on the link, mint, or approve any transactions" scenario, translated to on-chain paired-device co-signing. This is a Medium-severity social-engineering enabler bug because it weakens the last line of defense (the human confirmation step) that `ocore`'s multisig/shared-address model relies upon when a peer is remote.

### Likelihood Explanation
Exploitation requires the attacker to already be a legitimate cosigner on a shared address with the victim (e.g., a contract counterparty in `prosaic_contracts`/`wallet_arbiter_contracts`), which is a normal, attacker-reachable relationship in the private-payment / shared-address model — no privileged network position is needed, only that the counterpart's device sends a crafted `"sign"` device message. This matches an "unprivileged... private-payment counterparty or paired device" reachable path per the exercise's scope.

### Recommendation
When classifying the unit for the confirmation dialog, require that the payment message contains *only* the expected contract deposit/claim output (no other outputs/messages), or otherwise always fall back to the generic `confirm_on_other_devices` warning whenever any additional outputs exist beyond the recognized contract-related output. Additionally, display the full list of outputs/amounts to the signer regardless of the heuristic classification so that hidden malicious outputs cannot be concealed behind a softer contract-themed prompt.

### Proof of Concept
1. Attacker Bob is a genuine cosigner with victim Alice on shared address `S` via an existing prosaic contract (`shared_address=S`, `peer_device_address=Bob`).
2. Bob's device sends a `"sign"` device message to Alice with `unsigned_unit` containing:
   - `messages[0]`: payment, asset `base`, `outputs: [{address: S, amount: CHARGE_AMOUNT}, {address: <attacker_address>, amount: <large_amount>}]`
3. In `getSigner().sign`, step 1 finds the `CHARGE_AMOUNT` output to `S`, confirms `S` is a known `prosaic_contracts.shared_address`, and (since `peer_device_address !== device_address` may or may not hold depending on setup) emits `confirm_contract_deposit` rather than the generic warning, even though the unit also drains additional funds to `<attacker_address>`.
4. Alice, seeing the softer "contract deposit" prompt, approves, and her signature completes the multisig unit, which is then broadcast — resulting in unauthorized spending from the shared address. [4](#0-3)

function sendOfferToSign(device_address, address, signing_path, objUnsignedUnit, assocPrivatePayloads){
