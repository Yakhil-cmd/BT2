### Title
Cross-stack authorization bypass in CCMenu API — token-authorized stack ≠ stack actually read ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the stack-scoping logic that `Shipit::Api::BaseController` normally enforces for every other API endpoint. Any valid `ApiClient` token with the `read:stack` permission can be used to fetch the CCMenu deploy-status XML feed for **any** stack in the installation, not just the stack the token was meant to be scoped to. This breaks the binding: the stack a token is authorized for ≠ the stack the endpoint actually returns data for.

### Finding Description
`BaseController` defines the correct, scoped lookup that every other API controller relies on: [1](#0-0) 

This ensures that if `current_api_client.stack_id` is set (i.e. the token was created scoped to one specific stack), `stacks`/`stack` only ever resolves within that scope, and `Stack.from_param!` on an out-of-scope id raises a not-found error.

`CCMenuController`, however, does not use this scoped helper. It defines its own private `stack` method that resolves directly from `params[:stack_id]` with no reference to `current_api_client` at all: [2](#0-1) 

The only authorization check performed is `require_permission :read, :stack`, which only verifies that the token's permission list contains the literal string `"read:stack"` — it never checks whether the token is scoped to *this* stack: [3](#0-2) [4](#0-3) 

`CCMenuController` also overrides `authenticate_api_client` to accept the token strictly from a URL query parameter (rather than the `Authorization` header used elsewhere), which is how these tokens end up embedded in CCMenu/CCTray client configuration URLs and are consequently far more likely to leak or be shared: [5](#0-4) 

The token itself is generated per-stack via `CCMenuUrlController`, whose intent is clearly that the resulting URL/token is meant to be usable for that one stack only: [6](#0-5) 

Because `CCMenuController#stack` bypasses the `current_api_client.stack_id` scoping entirely, any holder of a valid `read:stack`-permissioned token — including one generated for/scoped to a single stack — can simply change the `stack_id` route/query parameter to read the CCMenu deploy-status feed of an arbitrary other stack in the Shipit installation.

### Impact Explanation
This is a cross-stack authorization bypass allowing unauthenticated (relative to the target stack) read of another stack's deploy state — the last deploy/rollback status, timestamps, and running state — which matches the "unauthenticated read of stack state, task streams or deploy output" High-severity category. An attacker who obtains any single `read:stack`-scoped `ApiClient` token (e.g. a leaked CCMenu URL, which by design is embedded in third-party CI-status tooling and is not treated as highly sensitive) gains the ability to enumerate/read deploy status for every stack managed by the Shipit instance, defeating the per-stack scoping (`ApiClient#stack`) that the rest of the API relies on as its core authorization boundary.

### Likelihood Explanation
Likelihood is high for an attacker who already possesses any single scoped token: no additional secret, signature forgery, or privileged access is required — only substituting the `stack_id` parameter in an otherwise normal, authenticated request. CCMenu tokens are specifically designed to be embedded in URLs consumed by external tooling (CCTray/CI dashboards), which increases the realistic chance of such a token being available to someone who should only have visibility into one stack.

### Recommendation
Make `CCMenuController` use the same stack-scoping logic as `BaseController` (i.e., resolve `stack` via `stacks.from_param!(params[:stack_id])`, honoring `current_api_client.stack_id`) instead of the unscoped `Stack.from_param!(params[:stack_id])`. Additionally, ensure `CCMenuUrlController` creates/reuses `ApiClient` records scoped to the specific stack (passing `stack:` into `create_with`/`find_or_create_by!`), and enforce that permission checks also validate the token's `stack_id` matches the requested stack whenever `stack_id?` is true.

### Proof of Concept
1. A legitimate user opens the CCMenu URL for `Stack A` (`GET /stacks/:stack_a/ccmenu_url`), producing a token `T` intended for `Stack A`'s deploy status only.
2. This URL/token `T` gets embedded into an external CI dashboard or CCTray client and is exposed there (its purpose, by construction, is to be placed in third-party tooling).
3. An attacker who obtains `T` sends: `GET /api/stacks/:stack_b/cc_menu.xml?token=T`, substituting the id of `Stack B` (a stack they have no legitimate access to).
4. `authenticate_api_client` (app/controllers/shipit/api/ccmenu_controller.rb:33-36) successfully authenticates `T` via `ApiClient.authenticate`.
5. `require_permission :read, :stack` passes because `T`'s permission list contains `read:stack` (no stack-specific check is performed).
6. `stack` (ccmenu_controller.rb:29-31) resolves `Stack B` directly from `params[:stack_id]`, ignoring any scoping on `T`.
7. The controller renders `Stack B`'s latest deploy/rollback status in the response — data the attacker was never authorized to read with token `T`.
