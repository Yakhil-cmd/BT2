### Title
CCMenu ccmenu#show bypasses ApiClient stack scoping, allowing cross-stack reads - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to resolve the stack directly via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` used by every other API controller through `Shipit::Api::BaseController`. This means the `current_api_client.stack_id` restriction is never applied for this endpoint, so a token scoped to one stack can read CCTray/CCMenu status (including latest deploy state) for any other stack, including production.

### Finding Description
The invariant claimed for the API is: `stack == stacks.from_param!(params[:stack_id])` where `stacks = current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) .

`CCMenuController` redefines `stack` to bypass this scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

The only guard on the action is `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!`, a pure boolean check of whether `"read:stack"` is present in the client's `permissions` array — it has no relation whatsoever to `stack_id` [3](#0-2) . So any `ApiClient` with `read:stack` permission — even one legitimately scoped only to `stack_id = A` — passes `require_permission!` and then, via the unscoped `Stack.from_param!`, resolves an arbitrary stack `B` (e.g. production) named in `params[:stack_id]`.

Additionally, `authenticate_api_client` is overridden to accept the token via `params[:token]` (as needed for the CCTray URL feature) rather than only via HTTP Basic auth [4](#0-3) , which is an intentional design for the CCMenu URL feature, but it compounds the exposure since a leaked/URL-embedded per-stack token becomes usable against any stack, not just the one it was minted for.

Exploit: attacker holds (or obtains, e.g. from a `ccmenu_url` generated for a non-sensitive stack) any `ApiClient` token that includes `read:stack` in its `permissions`, scoped to stack A. They issue `GET /api/stacks/*production_org/production_repo/production_env/ccmenu?token=<token>`. `require_permission!(:read, :stack)` succeeds because the token has `read:stack`. `stack` resolves via `Stack.from_param!` directly against the full `Stack` table, ignoring `current_api_client.stack_id`. The response renders `shipit/ccmenu/project` with the production stack's latest deploy/rollback status.

None of the listed guards prevent this: `verify_signature`/webhook checks are irrelevant to this HTTP GET path; `EnvironmentVariables#permit` is irrelevant; the `stacks` scoping method in `BaseController` is simply never called by this controller because it defines its own `stack` method that shadows the intended scoped one.

### Impact Explanation
An attacker holding any stack-scoped API token with `read:stack` permission can disclose the CI/CD status (latest deploy/rollback outcome, running state) of an arbitrary, unrelated stack — including a production stack they have no authorization for. This is a cross-tenant/cross-stack unauthenticated-scope read of stack state, matching the "High — unauthenticated disclosure of stack state" category. It is fully repeatable against any stack in the installation by varying `stack_id` in the URL, since no additional secret is required beyond one valid token.

### Likelihood Explanation
Preconditions: the attacker needs *some* valid `ApiClient` token that has the `read:stack` permission bit set (even scoped to an unrelated/low-value stack) — no `Shipit.github_teams` membership, session, or admin role is needed. Such tokens are routinely created and distributed as CCTray/CCMenu URLs (`Shipit::CcmenuUrlController#fetch`, which auto-creates a `read:stack` ApiClient for any signed-in user) [5](#0-4) . Given how easily a `read:stack` token is minted for low-sensitivity stacks, the cost to reach production-stack disclosure is low and the exploit is trivially repeatable (just change the URL path segment).

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and use the inherited, scope-respecting `stacks.from_param!(params[:stack_id])` from `BaseController`, i.e. delegate to the base `stack`/`stacks` methods instead of calling `Stack.from_param!` directly. If per-URL token auth via `params[:token]` must be retained for the CCTray feature, keep that override but ensure it still funnels through the scoped `stacks` collection before permission checks.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "ccmenu#show does not leak stacks outside the client's stack_id scope" do
  stack_a = shipit_stacks(:shipit) # attacker's authorized stack
  stack_b = shipit_stacks(:cyclimse) # unrelated/"production" stack

  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack_id: stack_a.id,
    permissions: ['read:stack']
  )

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: stack resolved by ccmenu#show must equal
  # current_api_client.stacks.from_param!(params[:stack_id]),
  # which for stack_id: stack_b.to_param and a client scoped to stack_a
  # should raise ActiveRecord::RecordNotFound / 404, not 200.
  assert_response :not_found # currently fails: returns 200 with stack_b's XML status
end
```
This demonstrates that `GET /api/stacks/*stack_id/ccmenu` resolves stacks outside `current_api_client.stack_id`, violating the stated invariant.
