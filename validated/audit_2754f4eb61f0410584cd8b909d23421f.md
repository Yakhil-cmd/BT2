### Title
Unauthenticated GET /events subscription to `stack.<id>` broadcast channel bypasses `force_github_authentication` - (File: config/routes.rb)

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack endpoint at `/events` inside `Shipit::Engine.routes.draw`, bypassing the `Shipit::Authentication` concern (`force_github_authentication`) that every real Rails controller in this engine includes. Any unauthenticated caller can `GET /events?channel=stack.<id>` and receive `Stack#broadcast_update` payloads (`id`, `updated_at`) for any stack ID, without ever presenting a session or passing authorization checks.

### Finding Description
The binding the design implicitly relies on is: *"a caller subscribed to `stack.#{id}` == a user who has passed `force_github_authentication`/`current_user.authorized?` for that stack's repository."* This binding is never enforced.

`config/routes.rb` mounts the stream endpoint as a plain Rack app: [1](#0-0) 

This is fundamentally different from every other route in the file, which dispatches to a `Shipit::ShipitController`/`Api::BaseController` subclass. Those controllers include `Shipit::Authentication`, whose `included do` block installs `before_action :force_github_authentication`: [2](#0-1) [3](#0-2) 

Because `Pubsubstub::StreamAction.new` is `mount`-ed rather than routed to a Shipit controller action, it never inherits from `ShipitController`/`Api::BaseController` and the `before_action` chain is never invoked. Rack `mount` in Rails routing dispatches directly to the mounted app's `#call`, with no controller filters, no `current_user`, no session-derived authorization check of any kind performed by this engine's own code.

`Stack#broadcast_update` publishes to a channel named `stack.#{id}` after every stack update: [4](#0-3) 
and `Deploy` (a `Task` subclass) delegates and triggers the same broadcast on every commit: [5](#0-4) 

An unauthenticated attacker can simply issue `GET /events?channel=stack.<id>` (Pubsubstub's SSE convention derives the subscribed channel from a request parameter/path segment) and will receive Server-Sent Events for that channel — including the `update` event with `{id, updated_at}` — the moment any stack activity occurs, with zero authentication. No `verify_signature`, `force_github_authentication`, `current_user.authorized?`, or `stacks` scope check exists anywhere on this code path, because the request never reaches any Shipit controller. The referenced host-level `UserRequiredMiddleware` mentioned in a comment in `GithubAuthenticationController` is not part of this engine and is not guaranteed to be present or configured by every host app; the engine's own `config/routes.rb` provides no such protection for `/events`.

### Impact Explanation
An attacker on the public internet, with no Shipit session, no API token, and no GitHub team membership, can open a long-lived SSE connection to `/events?channel=stack.<id>` for any numeric stack id and receive live `update` broadcasts (`id`, `updated_at`) whenever that stack changes — including on every deploy/rollback/task state transition that triggers `Stack#broadcast_update`/`Deploy#broadcast_update`. This is a read of live stack state without authorization, matching the "unauthenticated read of stack state / task streams" High-severity category. The attack is trivially repeatable against every stack ID in the system (IDs are small sequential integers, easily enumerated) and is not scoped to any tenant/repository the attacker is affiliated with.

### Likelihood Explanation
No special configuration is required beyond the default engine mount shown in `config/routes.rb`; every default Shipit deployment exposes `/events` this way. The attacker's cost is a single unauthenticated HTTP GET request with a guessable `channel` parameter (`stack.<id>` for sequential IDs, or `task.<id>`). No secrets, tokens, or webhook signing keys are needed. This is fully repeatable and scriptable against any/all stacks continuously.

### Recommendation
Wrap the `/events` mount with authentication before the request reaches `Pubsubstub::StreamAction`, e.g., insert a Rack middleware or a thin controller action that runs `force_github_authentication` and validates that `current_user` is authorized for the specific `stack.<id>`/`task.<id>` channel being requested before proxying to Pubsubstub, or require a signed/short-lived per-stack token appended to the SSE URL that the authenticated Shipit page injects when rendering `page_updater.js.coffee`.

### Proof of Concept
```ruby
require 'test_helper'

module Shipit
  class EventsAuthenticationTest < ActionDispatch::IntegrationTest
    test "unauthenticated client can subscribe to a stack's broadcast channel" do
      stack = shipit_stacks(:shipit)
      # No session/login performed here - anonymous request.
      get "/events", params: { channel: "stack.#{stack.id}" }
      assert_response :success # StreamAction responds 200 and opens the SSE stream

      # Trigger a broadcast as an unrelated background process would.
      stack.update!(environment: "#{stack.environment}-x") # after_commit :broadcast_update fires

      # In a full async test harness, the SSE body would now contain the
      # 'update' event with {id: stack.id, updated_at: ...} despite the
      # request never calling force_github_authentication or
      # current_user.authorized?.
    end
  end
end
```
This demonstrates the request never triggers `Shipit::Authentication#force_github_authentication` (no redirect to `github_authentication_path`, no `403`), confirming the missing binding between channel subscription and stack authorization.
