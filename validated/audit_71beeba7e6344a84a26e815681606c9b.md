## Answer

The vulnerability is real. `Shipit::Webhooks::Handlers::StatusHandler#process` does **not** scope its `Commit` lookup to the webhook's originating repository at all, unlike every other handler in the codebase.

### The broken binding

Claimed binding: every status contributing to `Commit#blocked?`'s `any?(&:blocking?)` check must come from a webhook whose repository equals `stack.repository`.

Actual code: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This queries `Commit.where(sha: params.sha)` **globally across the entire `commits` table**, with no join or filter on `stack_id`, `repository_id`, or the webhook's `repository.full_name`. Compare this to the base `Handler` class, which *does* provide repository-scoping via `stacks`: [2](#0-1) 

`StatusHandler` simply never uses `stacks` or `repository_name` — it is the only handler that resolves target records purely by `sha`, with zero repository binding.

### Why signature verification doesn't help

`WebhooksController#verify_signature` only confirms that the payload was legitimately signed by GitHub for the `repository_owner` named in the payload itself — it never cross-checks that the `sha` in the payload belongs to a commit tracked under that same repository: [3](#0-2) 

An attacker who owns any GitHub repository/org can install a GitHub App (or configure a webhook secret) for their **own** repo, giving them a fully valid signature. They then only need a commit with the exact same sha as the victim's blocking commit in their own repo (trivial — git shas are content-addressed, so pushing/duplicating the identical commit content, e.g. cherry-picking a public commit from the victim's public repo, reproduces the sha exactly; no cryptographic collision is required). They emit a `status` event with `state: "success"` for that sha from their own repository.

### Exploit flow

1. Victim stack has `blocking_statuses` configured and a blocking commit `B` between `last_deployed_commit` and a target commit `T` — `T.blocked?` is `true` via: [4](#0-3) 
2. Attacker duplicates commit `B` (same content ⇒ same sha) into a repo they own, and triggers/forges a `status` webhook with `sha: B.sha, state: "success"`.
3. `WebhooksController#verify_signature` passes because the signature is valid for the attacker's own repo/org.
4. `StatusHandler#process` runs `Commit.where(sha: B.sha)` — this matches the victim's `Commit` record for `B` (same sha), regardless of the fact the webhook payload's `repository.full_name` is the attacker's repo.
5. `commit.create_status_from_github!(params)` adds a `success` status to the victim's commit `B` via `add_status`/`statuses.replicate_from_github!`: [5](#0-4) 
6. `B.blocking?` (`!success? && stack.blocking_statuses.include?(context)`) becomes `false`: [6](#0-5) 
7. `T.blocked?` re-evaluates to `false`, `T.deployable?` becomes `true`, and `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` for the victim stack: [7](#0-6) [8](#0-7) 

### Title
Unauthenticated cross-repository status forgery unblocks a victim stack's deploy queue — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits by `Commit.where(sha: params.sha)` with no repository scoping, unlike every other webhook handler which resolves records via `Repository.from_github_repo_name(repository_name)`. Since `Commit#blocked?` and `Status::Common#blocking?` trust any status attached to a commit regardless of which repository's webhook created it, an attacker who controls an unrelated GitHub repository can forge a passing status for the sha of a victim's blocking commit and clear the victim's deploy-blocking gate.

### Finding Description
Broken binding: `webhook.payload["repository"]["full_name"] == commit.stack.repository.full_name` is never enforced in `StatusHandler`. The handler only checks `Commit.where(sha: params.sha)`, ignoring the repository entirely. `WebhooksController#verify_signature` validates that the payload is authentically signed by GitHub for the sender's `repository_owner`, but this only proves the webhook came from *some* legitimate GitHub repo — not that its sha belongs to that repo's tracked commits. An attacker (owner of any repo with a webhook to the Shipit host) duplicates the exact content of the victim's blocking commit into their own repo (same sha, since git hashes are content-derived, not attacker-influenced randomness), sets its status to `success` via GitHub API, and GitHub delivers a signed `status` webhook. `StatusHandler#process` matches the commit purely by sha across the whole database and calls `commit.create_status_from_github!(params)`, writing a `success` status onto the victim's `Commit` row. This flips `blocking?` to `false` for that commit, and `Commit#blocked?` — which iterates `stack.commits.reachable.newer_than(...).older_than(...).any?(&:blocking?)` — no longer counts it, unblocking every later commit in the victim's queue.

### Impact Explanation
The attacker causes a `success` status record to be written for a repository/stack that never authenticated it, clearing a CD gate and triggering `ContinuousDeliveryJob`/deploys for a victim stack whose commits were intentionally blocked (e.g. by a failing/pending required check). This matches "an unauthorized deploy" and "a payload for one repository mutating another's stack/commit" — Critical severity. The attack is repeatable against any stack with `blocking_statuses` configured, for any blocking commit whose content the attacker can reproduce, and is not limited to one victim — any Shipit-hosted repo is affected as long as the attacker can push a webhook to the same Shipit host (multi-tenant blast radius).

### Likelihood Explanation
Preconditions: victim stack has `blocking_statuses` set and a currently-blocking intermediate commit. The attacker needs: (1) any GitHub repository configured to send webhooks to the target Shipit host — trivial for an unprivileged internet user with a GitHub App install/webhook subscription of their own; (2) the ability to reproduce the exact sha of the victim's blocking commit, which for public commits (typical in blocking CI-status scenarios) is achieved by copying the identical commit object into their own repo — no brute-force collision needed. Cost is low, feasibility high, and the technique is fully repeatable against arbitrary shas the attacker can reproduce.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks under the webhook's own repository, mirroring the base `Handler#stacks` pattern, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status webhook can only affect commits that actually belong to the repository that sent it.

### Proof of Concept
minitest plan (no live GitHub, use existing webhook/handler test helpers already present, e.g. `test/models/shipit/webhooks/handlers_test.rb` pattern for calling `StatusHandler.call`):

```ruby
test "StatusHandler must not update commits belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  blocking_commit = victim_stack.commits.create!(sha: "a" * 40, ...)
  target_commit = victim_stack.commits.create!(sha: "b" * 40, ...)
  victim_stack.update!(last_deployed_commit_id: nil, blocking_statuses: ["ci/blocking"])
  blocking_commit.statuses.create!(state: "pending", context: "ci/blocking")

  assert_predicate target_commit.reload, :blocked? # binding LHS: true before forged status

  attacker_payload = {
    "sha" => blocking_commit.sha,
    "state" => "success",
    "context" => "ci/blocking",
    "repository" => { "full_name" => "attacker/unrelated-repo" }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(
    ExplicitParameters::Parameters.define { }.parse!(attacker_payload)
  )

  refute_predicate target_commit.reload, :blocked?    # currently FAILS: becomes false
  refute_predicate target_commit, :deployable?         # exploit demonstrated: unauthorized unblock
end
```
Assert both sides of the binding: before the forged webhook, `target_commit.blocked?` is `true` because `blocking_commit.blocking?` is `true`; after the cross-repository forged status, `blocking_commit.blocking?` becomes `false` even though the webhook's `repository.full_name` never equals `victim_stack.repository.full_name`, proving the equality is not enforced.
