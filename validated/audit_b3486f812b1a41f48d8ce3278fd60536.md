### Title
Webhook signature is verified against `repository.owner.login`, but the pull-request handlers resolve and mutate the repository via the independent `repository.full_name` field, letting one org's signed payload create/mutate another org's `ReviewStack` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to HMAC-verify the raw body against using `params.dig('repository','owner','login')`, while every PR handler (e.g. `OpenedHandler#repository`) resolves the `Shipit::Repository` to mutate using the sibling, independently-controlled JSON field `params.repository.full_name`. Because nothing enforces that `repository.owner.login` and `repository.full_name` refer to the same GitHub repository, an attacker who controls one onboarded org's webhook secret can sign a payload as their own org while pointing `repository.full_name` at a different org's repository, causing a `ReviewStack` to be created under that other org.

### Finding Description
Broken binding (before/after):
- Claimed invariant: `org(webhook_secret that verified raw_post) == org(repository record looked up via params.repository.full_name)`
- Before tracing: assumed true because in a genuine GitHub-delivered webhook these two fields always describe the same repository.
- After tracing: **false**, because the two fields are read independently and never cross-checked.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, request.raw_post)`, selecting the `webhook_secret` for `repository_owner`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` only checks the HMAC of `request.raw_post` against that org's `webhook_secret`; it never inspects any other field of the payload, including `repository.full_name`. [3](#0-2) 
3. On success, `WebhooksController#create` dispatches the parsed body to all handlers for the event, e.g. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`. [4](#0-3) 
4. `OpenedHandler#repository` resolves the target `Shipit::Repository` using `params.repository.full_name`, a field that was never used or checked during signature verification. [5](#0-4) 
5. `process` then builds a `ReviewStackAdapter` scoped to `repository.review_stacks` (the repository resolved from `full_name`) and calls `find_or_create!`, which creates a `ReviewStack` (`stack_attributes` including `branch: params.pull_request.head.ref`, `environment: "pr#{params.number}"`) under that resolved repository. [6](#0-5) [7](#0-6) 

Exploit flow: the attacker controls (or has legitimately onboarded) org A on the Shipit instance and therefore possesses org A's `webhook_secret` (the only secret they need — this is exactly the credential every legitimate webhook sender for their own org already has). They send `POST /webhooks` with header `X-Github-Event: pull_request`, a body where `repository.owner.login = "orgA"` (matches the signing org, so `verify_signature` passes) but `repository.full_name = "orgB/repoB"` (a repository belonging to a different, non-consenting org). Because `full_name` alone drives `Repository.from_github_repo_name`, Shipit creates/mutates a `ReviewStack` under org B's repository despite org B's webhook secret never being used to authenticate the request.

None of the existing guards prevent this: `drop_unhandled_event` and `check_if_ping` only gate on the event type header, `ExplicitParameters` schemas for `OpenedHandler` only require `repository.full_name` to be a `String` (no format/consistency check against `owner.login`), and no model validation on `Shipit::Repository` cross-checks the looked-up record's owner against the signature-selecting org.

### Impact Explanation
A `ReviewStack` (a Task/Stack-provisioning record with `branch` and `environment` taken from attacker-controlled PR fields) is created for a repository (org B) whose owner never authenticated the request; org A's credentials, not org B's, were used. This is a cross-tenant write: any org onboarded onto the same multi-tenant Shipit instance can use their own valid webhook secret to spawn stacks against any other onboarded org's repository, repeatable per PR/target repository, matching "Critical — a payload for one repository mutating another's stack."

### Likelihood Explanation
Requires: (a) the Shipit instance to host more than one org/repository (multi-tenant), (b) the attacker to control one legitimately onboarded org (A) and therefore its `webhook_secret` (obtained legitimately when they configured their own GitHub webhook), and (c) the target repository (org B) to have `review_stacks_enabled` and a matching `provisioning_behavior` that would allow stack creation for the crafted PR payload. Given those, the attack costs a single crafted HTTP POST with a valid HMAC computed from a secret the attacker already legitimately possesses, and is fully repeatable against any target repository known to the attacker.

### Recommendation
Cross-check that `params.dig('repository','owner','login')` (the org whose secret verified the signature) matches the owner segment of `params.dig('repository','full_name')` before dispatching to handlers, and reject the webhook (422) on mismatch; alternatively, resolve the target repository in `OpenedHandler` (and sibling handlers) via the same `repository_owner` value trusted during signature verification rather than re-deriving it from `full_name`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.github(organization: 'orgA')` with `webhook_secret: 'secretA'`; create `Shipit::Repository` for `orgB/repoB` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
2. Build a `pull_request` "opened" JSON payload with `repository.owner.login = 'orgA'`, `repository.full_name = 'orgB/repoB'`, valid nested `pull_request` fields.
3. Compute `X-Hub-Signature` as `sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'secretA', body)}`.
4. `POST /webhooks` with that body/signature and `X-Github-Event: pull_request`.
5. Assert response is `200`, and assert `Shipit::ReviewStack.where(repository_id: repo_B.id, environment: "pr#{payload_number}").exists?` is `true` — demonstrating org A's secret produced a stack under org B, i.e. `org(signing secret) = "orgA"` while `org(mutated repository) = "orgB"`, violating the claimed equality.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
