### Title
Multisig transaction execution can run a payload different from the one approved by owners when `abort_if_multisig_payload_mismatch_enabled` is off - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the prologue function invoked by the VM to admit a multisig-account transaction for execution, only checks that the caller-supplied `payload` matches what owners approved in two narrow cases. If neither case applies, an executing owner can supply an arbitrary `payload` argument that differs from the payload the other owners actually voted/approved, and the VM will execute that arbitrary payload while all quorum/approval bookkeeping still reports success against the originally-approved transaction record.

### Finding Description
`validate_multisig_transaction` [1](#0-0)  is documented as being "called by the VM as part of transaction prologue, which is invoked during mempool transaction validation and as the first step of transaction execution" — i.e., this is the admission gate that decides whether the actual on-chain `payload` bytes supplied with the transaction are legitimate for the given multisig `sequence_number`.

The function verifies quorum (`can_execute`/`can_be_executed`, approval counts, timelock), then tries to bind the supplied `payload` to what owners approved:
- If `transaction.payload_hash.is_some()` (used by `create_transaction_with_hash`), it hashes the supplied payload and compares it to the stored hash [2](#0-1) .
- Otherwise, if the transaction's full payload *is* stored on-chain (`create_transaction` path), the match between supplied and stored payload is only enforced **when the feature flag `abort_if_multisig_payload_mismatch_enabled` is enabled** [3](#0-2) .

When that feature flag is disabled (or on any network/epoch where it hasn't been turned on), and the transaction was created via `create_transaction` (full payload on chain, `payload_hash` is `None`), there is **no check at all** binding the supplied `payload` argument to the approved `stored_payload`. The prologue only validates quorum/timelock for the sequence number, not that the bytes about to be executed are the bytes that were approved. Any owner who is entitled to execute (has enough approvals) can pass a completely different, unapproved payload as the transaction argument at execution time, and the VM will execute it — while emitting `TransactionExecutionSucceeded`/`Failed` events that reference the original (unrelated) `sequence_number` and approval count, misrepresenting what was actually approved.

This is a pre-validation mismatch at the admission boundary: the multisig approval set was bound to one payload, but a different, unapproved payload is admitted and executed under the same "approved" sequence number/signer set.

### Impact Explanation
This breaks the core multisig approval invariant ("what owners voted for is what gets executed"). An executing owner (who need not control full quorum's intent on content, only be one of the signers with execute rights once quorum count is met) can substitute a different payload — e.g., a transfer to a different address, a different amount, or a completely different module call — from what was actually reviewed and approved by co-signers, while the on-chain event log falsely reports it as the approved transaction. This is a high-impact confused-approval-set/wrong-payload-admission bug at the transaction admission boundary, matching the "Authenticator/multisig/approval validation accepting the wrong approval set" and "pre-validation mismatch causing execution of a transaction that should fail admission" impact categories.

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active in the deployed environment and whether `create_transaction` (full-payload, non-hash) is the code path in use — both are plausible/common configurations (I was not able to confirm the on-chain default state of this feature flag or its rollout status in this session, since flag defaults live in `move-stdlib`/`features.move` release manifests not reviewed here). If the flag is off, exploitation requires no special privilege beyond being one of the multisig owners who is allowed to execute the queued transaction once quorum count is satisfied.

### Recommendation
Make the stored-payload/supplied-payload equality check for `create_transaction`-style multisig transactions unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate, or invert to "abort unless explicitly allowed to skip for backward compatibility only during a well-scoped migration window"), so that admission of a multisig-executed transaction always binds the executed payload to the payload the owners actually approved.

### Proof of Concept
Conceptual sequence (dependent on `abort_if_multisig_payload_mismatch_enabled` being disabled):
1. Owner A calls `create_transaction(owner, multisig_account, payload_A)` where `payload_A` transfers funds to address X. This stores `payload_A` fully on-chain, with `payload_hash = None` [2](#0-1) .
2. Owners B, C vote to approve based on reading `payload_A` (transfer to X), reaching quorum.
3. Owner A (or any owner permitted to execute) submits the transaction for execution but supplies `payload_B` (transfer to attacker-controlled address Y) as the runtime `payload` argument.
4. `validate_multisig_transaction` checks quorum/timelock (pass) and, since `payload_hash` is `None` and the feature flag is disabled, skips the `payload == stored_payload` check entirely [3](#0-2) .
5. The VM executes `payload_B` (funds go to Y), and `successful_transaction_execution_cleanup` emits `TransactionExecutionSucceeded` referencing the same `sequence_number` and approval count as if `payload_A` had been executed [4](#0-3) .

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }

    /// Post-execution cleanup for a successful multisig transaction execution.
    /// This function is private so no other code can call this beside the VM itself as part of MultisigTransaction.
    fun successful_transaction_execution_cleanup(
        executor: address,
        multisig_account: address,
        transaction_payload: vector<u8>,
    ) {
        let num_approvals = transaction_execution_cleanup_common(executor, multisig_account);
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        emit(
            TransactionExecutionSucceeded {
                multisig_account,
                sequence_number: multisig_account_resource.last_executed_sequence_number,
                transaction_payload,
                num_approvals,
                executor,
            }
        );
    }
