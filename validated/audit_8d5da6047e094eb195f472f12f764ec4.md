This confirms the analysis: `AliasChildLocation` only allows a location to alias into its own descendant (checked via `contains(&origin, &target)` requiring the target to be a suffix-extension of origin with matching prefix count), `AliasAccountId32FromSiblingSystemChain` is scoped only to sibling *system* chains matching `AccountId32` junctions, and `AliasOriginRootUsingFilter<AssetHubLocation, Everything>` only allows the genuine `AssetHubLocation` origin to alias *outward*, not the reverse. None of these tuple members allow an arbitrary sibling parachain to alias *into* `AssetHubLocation` or `RelayChainLocation`.

### Title
No vulnerability found - forged origin cannot satisfy `TrustedAliasers` to reach `LocationAsSuperuser` - (File: system-parachains/encointer/src/xcm_config.rs)

### Summary
The attack requires the XCM executor's `Aliasers` (`TrustedAliasers`) to accept an attacker-controlled sibling parachain aliasing into `Equals<AssetHubLocation>` or `Equals<RelayChainLocation>` before `LocationAsSuperuser` is ever consulted, but the composed `TrustedAliasers` type on Encointer explicitly does not permit that direction of aliasing.

### Finding Description
`XcmOriginToTransactDispatchOrigin` places `LocationAsSuperuser<(Equals<RelayChainLocation>, Equals<AssetHubLocation>), RuntimeOrigin>` after `SovereignSignedViaLocation`, `RelayChainAsNative`, and `SiblingParachainAsNative` in the conversion tuple [1](#0-0) . This converter is only reached with whatever `origin` the xcm-executor has resolved for the current instruction, and that resolution is governed by `type Aliasers = TrustedAliasers` [2](#0-1) .

`TrustedAliasers` is defined as `(AliasChildLocation, AliasAccountId32FromSiblingSystemChain, AliasOriginRootUsingFilter<AssetHubLocation, Everything>, AuthorizedAliasers<Runtime>)` [3](#0-2) .

- `AliasChildLocation` only permits an origin to alias into locations that are literal descendants of itself (verified in the emulator test `aliasing_child_locations`, which asserts `Aliasers::contains(&origin, &target)` is true only when `target` extends `origin`'s junctions, and false for any non-descendant, e.g. `Parachain(8)` cannot alias to a location without `Parachain(8)` as prefix) [4](#0-3) . Since a sibling parachain's origin is `Parachain(id)` (or a location under it), it cannot alias into `AssetHubLocation` or `RelayChainLocation` unless `id` happens to be Asset Hub's own para ID.
- `AliasAccountId32FromSiblingSystemChain` only allows an `AccountId32` under a sibling *system* parachain to alias into the *same* `AccountId32` under another sibling system chain — it does not let a chain-level origin become `AssetHubLocation` or `RelayChainLocation` wholesale.
- `AliasOriginRootUsingFilter<AssetHubLocation, Everything>` is asymmetric: it only allows the genuine `AssetHubLocation` origin to alias *outward* into other locations (`Everything`), not the reverse — an attacker cannot use this rule to become `AssetHubLocation`.
- `AuthorizedAliasers<Runtime>` requires an explicit prior authorization deposit from the real target location's owner, which an unprivileged attacker on an arbitrary sibling chain cannot forge.

Consequently, if an attacker's sibling parachain sends `DescendOrigin(AssetHubPluralityJunctions)` the origin becomes `Parachain(attacker_id)/AssetHubPluralityJunctions` (a narrowing operation, not a takeover of a different chain's identity), which is not equal to `AssetHubLocation`. If instead the attacker uses `AliasOrigin(AssetHubLocation)`, the xcm-executor calls `Aliasers::alias_origin(&current_origin, &AssetHubLocation)` before proceeding, and per the analysis above this returns `false` for the attacker's origin, causing the instruction to fail rather than proceed with a spoofed `AssetHubLocation` origin. The underlying transport-level origin (which sibling chain actually sent the message via XCMP/HRMP) is also bound by the parachain-system message queue and cannot be forged by message content, independent of the Aliasers check.

### Impact Explanation
No unauthorized privileged dispatch occurs. `LocationAsSuperuser` is only ever invoked with an `origin` that has passed the `Barrier`/`Aliasers` checks, and those checks structurally prevent an arbitrary sibling parachain from resolving to `Equals<RelayChainLocation>` or `Equals<AssetHubLocation>`.

### Likelihood Explanation
Not applicable — the described exploit path cannot execute because the `Aliasers` check (a required precondition for `AliasOrigin` to succeed, and a structural constraint on what `DescendOrigin` can produce) rejects the forged target before the origin ever reaches `OriginConverter`/`LocationAsSuperuser`.

### Recommendation
No fix needed for this specific concern; the composition of `TrustedAliasers` already restricts aliasing so that only the genuine `AssetHubLocation` (verified via its actual XCMP/UMP transport origin, not attacker-declared junctions) or `RelayChainLocation` can trigger `LocationAsSuperuser`.

### Proof of Concept
An xcm-emulator test analogous to the existing `aliasing_child_locations` tests [4](#0-3)  would assert: `<XcmConfig as xcm_executor::Config>::Aliasers::contains(&Location::new(1, [Parachain(attacker_id)]), &AssetHubLocation::get())` returns `false`, and that sending `Xcm(vec![DescendOrigin(AssetHubPluralityJunctions), AliasOrigin(AssetHubLocation), Transact{..}])` from an attacker sibling results in an XCM execution error (barrier/alias rejection) rather than a `Root`-origin dispatch, confirmed by checking no `sudo`/root-only event is emitted on Encointer.
