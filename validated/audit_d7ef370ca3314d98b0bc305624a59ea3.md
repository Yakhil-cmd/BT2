### Title
Webhook signature verification is keyed on `repository.owner.login` while the event is processed against the independent, attacker-controlled `repository.full_name` field, allowing cross-organization forgery of GitHub webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The C4 report's root cause is that OpenZeppelin's `_mint` trusts the `to`/`msg.sender` address without validating it actually supports the receiving protocol, breaking the binding "address that is authorized" ≠ "address that is acted on". Shipit's webhook controller has the same class of bug: the field used to select/authenticate the HMAC secret (`repository.owner.login`, i.e. the "organization that authenticated") is not the same field used to determine which repository/stack the event is actually applied to (`repository.full_name`, i.e. "the repository that is written"). Nothing ties these two fields together beyond both being read from the same attacker-supplied JSON body.

### Finding Description
`WebhooksController#verify_signature` resolves which `GitHubApp`/secret to validate the HMAC against using only the organization login embedded in the payload: [1](#0-0) [2](#0-1) 

The signature check itself (`verify_webhook_signature`) is a plain HMAC-SHA1 comparison over the raw body using the secret configured for whatever organization the *attacker's own payload* claims to be: [3](#0-2) 

In a multi-organization Shipit deployment (`github_app_config`/`github_default_organization`), each org has its own `webhook_secret`: [4](#0-3) 

Once the signature is accepted, the actual event handler resolves the *target* repository/stack from a completely separate field of the same payload, `repository.full_name`, with no cross-check against `repository.owner.login` used earlier for authentication: [5](#0-4) 

Because the entire request body is attacker-authored (the attacker builds the whole JSON), nothing prevents `repository.owner.login` from being set to an organization the attacker legitimately controls (and therefore knows the `webhook_secret` for), while `repository.full_name` is set to an entirely different, victim organization/repository that the attacker has no access to. The HMAC only proves "this body was signed with org X's secret" — it says nothing about which repository the body's other fields describe, and the code never enforces that `owner.login` is consistent with `full_name`.

This breaks exactly the binding called out in scope: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
An attacker who operates their own organization/repository tracked by the same shared Shipit instance (and thus legitimately knows their own org's `webhook_secret`) can forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that are processed as if they originated from the victim's organization/repository, because the handlers key off `repository.full_name`/`organization.login` fields taken from the same forged, self-signed body. Concretely:
- Forging a `status` or `check_suite` event with the victim's commit SHA and a "success" state can inject fabricated CI/check-run results into the victim's commit's `Status` records, which are consumed by `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?` and by deploy safety checks — enabling an unauthorized merge or deploy of a repository the attacker does not control.
- Forging a `membership` event with `organization.login` claiming the victim org can create/alter `Membership`/`Team` records, escalating into `Shipit.github_teams` authorization for arbitrary logins.

This matches the in-scope Critical/High impacts: unauthorized merge/deploy and escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Exploitability requires only that the Shipit instance is configured in the multi-organization mode (`secrets.github` keyed by org, each with a distinct `webhook_secret`) and that the attacker controls at least one such organization (a normal, unprivileged tenant of a shared Shipit instance) while the victim organization/repository is tracked by the same instance. No access to the victim's GitHub App, `GITHUB_TOKEN`, TLS interception, or Shipit session is required — only knowledge of the attacker's own legitimately-issued webhook secret and the ability to send an HTTP POST to the shared `/webhooks` endpoint.

### Recommendation
After signature verification succeeds, re-derive `repository_owner`/organization strictly from the same field(s) actually used to resolve the target `Repository`/`Stack` (i.e. tie `repository.full_name`'s owner segment to the organization whose secret validated the signature), and reject the webhook if they disagree. Alternatively, verify the signature against every configured organization's secret only after confirming the claimed `full_name` belongs to that organization, or, for multi-tenant configs, require a unique-per-repository (not per-organization) webhook secret so no attacker-controlled organization's secret can validate a forged payload describing a different repository.

### Proof of Concept
1. Shipit instance configured with two orgs, `attacker-org` (attacker knows `webhook_secret`) and `victim-org` (tracks stack `victim-org/victim-repo`), per `lib/shipit.rb#github_app_config`.
2. Attacker builds a raw JSON body for a `status` event:
   ```json
   {
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "required-ci-check"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw body)>` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. The status handler resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), writing a forged successful `Status` against the victim's commit.
6. This forged status can satisfy `MergeRequest#all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`), leading to an unauthorized merge of the victim's pull request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
