### Title
Non-unique `stacks-block-time` cache key allows stale interest-index reuse across colliding blocks - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`accrue-and-cache` keys the shared `index-cache` map solely by `{ timestamp: stacks-block-time, aid: aid }` and treats a cache hit as proof that the asset has already been accrued for the current period, skipping the call to `vault-accrue` entirely. `stacks-block-time` is a second-granularity block timestamp, not a strictly-unique per-block identifier, so two distinct blocks can legitimately produce the same cache key for the same asset. This mirrors the reported class of bug where a non-unique hash/timestamp is used as the sole cardinality for state, causing later legitimate operations to be silently short-circuited by stale cached data written by an earlier, unrelated caller.

### Finding Description
`accrue-and-cache` is the single choke point through which every collateral/debt operation refreshes an asset's liquidity/borrow indexes before using them: [1](#0-0) 

The cache key is `{ timestamp: stacks-block-time, aid: aid }` — nothing else disambiguates it, in particular it does not include the vault's own monotonically-increasing accrual sequence or block height: [2](#0-1) 

Whichever transaction is first to touch a given asset at a given `stacks-block-time` calls `vault-accrue` (routed per-asset via `vault-accrue`) and writes the resulting `{index, lindex}` into `index-cache`: [3](#0-2) 

Every subsequent caller — in the *same* block or in a *different* block whose `stacks-block-time` happens to collide with a previously-cached one for that asset — gets a cache HIT and receives the indexes computed for the first caller's context, without ever invoking `vault-accrue` again: [4](#0-3) 

This is structurally identical to the reported issue: a value that is not guaranteed unique (compressed-data hash / timestamp in the original report; `stacks-block-time` here) is used as the *sole* cardinality key for stored/validated state, and its collision silently substitutes stale, previously-computed data for what should be freshly computed data for a distinct unit of work (a distinct block). The caller who happens to prime the cache for a given `{timestamp, aid}` pair determines the index every other, unrelated user transacting against that asset in a colliding block will use — a shared cache "primed by one caller and consumed by another."

I was not able to fully verify from the indexed contents whether Stacks/Nakamoto strictly guarantees `stacks-block-time` uniqueness/monotonicity across consecutive blocks (this would require deeper protocol-level confirmation not available in the indexed files), so the exact collision frequency is uncertain; however, the contract's own caching design explicitly treats `stacks-block-time` (not block height, not a vault-internal accrual counter) as sufficient cardinality to skip re-accrual, which is the root-cause pattern the external report warns against.

### Impact Explanation
When a stale cache entry is served instead of a fresh `vault-accrue` call, all users interacting with that asset during the colliding block operate on indexes that do not reflect the interest that should have accrued between the first-priming block and the colliding block. Because `vault-accrue` is also the mechanism that would otherwise advance the vault's own internal accrual bookkeeping, a skipped call means depositors' accrued yield for that period is not reflected/realized in the shared index used for that block's collateral/debt evaluations, borrows, repayments, and liquidations — a socialized miscalculation of yield across all suppliers/borrowers of the affected vault, not something confined to the caller who triggered the cache hit. This lands in the **High** impact category: temporary freezing/misallocation of unclaimed yield shared among all LPs of the affected vault.

### Likelihood Explanation
Likelihood depends on how often two blocks can share the same `stacks-block-time` value for the same asset while genuine accrual-relevant time has still elapsed at the vault level. This is not attacker-controlled (block timestamps are set by block producers, not transaction senders), so exploitation is opportunistic rather than deliberately triggerable by an unprivileged caller, which lowers likelihood relative to a directly attacker-forced collision. It should be treated as a design defect that can occur naturally under normal chain operation, particularly during rapid block production, rather than a rare accident.

### Recommendation
Do not use `stacks-block-time` alone as the cardinality for `index-cache`. Either (a) key the cache by a monotonically unique identifier such as `stacks-block-height` combined with `aid`, or (b) move the "already accrued this period" check into the vault contracts themselves (comparing against their own last-accrual timestamp/height rather than trusting an externally-keyed cache), so a timestamp collision can never cause a legitimate accrual to be skipped.

### Proof of Concept
1. Asset `aid` is accrued once in block `B1` at `stacks-block-time = T`; `accrue-and-cache` calls `vault-accrue` and stores `index-cache[{timestamp: T, aid}] = {index, lindex}`.
2. A later block `B2` (whose real elapsed time since `B1` is nonzero, e.g. produced quickly under fast block production) reports `stacks-block-time = T` again (collision).
3. Any user transacting against `aid` in `B2` (deposit, borrow, repay, liquidate) triggers `accrue-and-cache`, which computes `cache-key = {timestamp: T, aid}`, finds the entry from step 1, and returns the stale `{index, lindex}` without calling `vault-accrue`.
4. The vault's true accrual state for the elapsed interval between `B1` and `B2` is never applied; the shared index used for all users' collateral/debt evaluation in `B2` is stale, misallocating accrued interest for that period across all suppliers and borrowers of the vault.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
