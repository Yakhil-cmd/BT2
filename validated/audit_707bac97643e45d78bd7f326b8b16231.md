### Title
`initialize_with_permission` lets the caller assign an arbitrary, unverified `creator` account that permanently owns all future creator-fee withdrawals - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` accepts a `creator` account that is a plain, unchecked, non-signing `UncheckedAccount`, unrelated to the `payer` who actually authorizes and funds the transaction. Its public key is written directly into `pool_state.pool_creator` during pool creation, and that field is the sole and permanent authority over all future `collect_creator_fee` / `collect_creator_fee_permissionless` withdrawals for that pool. A permission-holding caller can set `creator` to any pubkey they choose, including their own, silently and irrevocably diverting the pool's creator-fee stream from whoever the pool nominally belongs to.

### Finding Description
In `initialize_with_permission.rs`, the account struct declares: [1](#0-0) 
`creator` has no `Signer` constraint, no `address =` constraint, and no relationship to `payer` or to the `permission` PDA that authorizes the call. The only real access-control check in this instruction is the `permission` account, which is derived from and gates on `payer.key()`: [2](#0-1) 

Despite `creator` never being validated, its key is committed as the pool's permanent fee-owner via `pool_state.initialize(...)`: [3](#0-2) 

which stores it in `PoolState.pool_creator`: [4](#0-3) 

This field is later used as the exclusive authorization check in `collect_creator_fee` (must be the signer): [5](#0-4) 

and as the mandatory fee-recipient in the permissionless variant: [6](#0-5) 

There is no instruction anywhere in the program that can later modify `pool_creator`; it is set once at initialization and is final.

This is directly analogous to the Snipe-IT `created_by` bug: a field that is supposed to represent a verified, authoritative identity (the entity entitled to future privileged benefits — here, ongoing creator-fee income) is instead populated from an unauthenticated, caller-supplied account in the instruction. The only gate on the instruction (`permission`, keyed to `payer`) authorizes *who may create a permissioned pool*, but does nothing to constrain *who gets named as the fee-owning creator of that pool* — the two identities are conflated in the exploit but decoupled in the code, exactly the CWE-863 pattern in the original report (authorization check on one identity, sensitive field set from a different, unchecked one).

### Impact Explanation
Any account holding a valid `permission` PDA (an allow-listed `payer`, e.g. a partner/launchpad address approved by the protocol admin to create permissioned pools) can call `initialize_with_permission` and set `creator` to their own wallet (or any colluding address) instead of the legitimate token issuer's address. Because `pool_creator` is immutable and is the sole authority for `collect_creator_fee` and the sole recipient for `collect_creator_fee_permissionless`, this permanently and irrevocably steals the entire ongoing creator-fee revenue stream of the pool from the party it was meant for. Since creator fees accrue from every swap on the pool (`creator_fees_token_0/1`), this is continuous fund theft with no remediation path, satisfying "concrete theft ... of user or LP funds" / "unauthorized privileged effect" under the validation criteria.

### Likelihood Explanation
Exploitation requires only that the attacker's key already has a `permission` PDA (i.e., they are within the set of parties allowed to call `initialize_with_permission`). Given that this set is intended to include third parties creating pools on behalf of others (the very purpose of separating `payer` from `creator`), it is a realistic, low-friction misuse of an intended feature: no special signature, oracle manipulation, or race condition is needed — a single call to `initialize_with_permission` with an attacker-chosen `creator` account suffices.

### Recommendation
Require `creator` to either be a `Signer` (proving the named creator consented) or bind it cryptographically to a value the true creator controls (e.g., require `creator` to match a value embedded in the `Permission` account itself, or require the `payer`'s permission record to specify the exact `creator` it is allowed to designate, verified via `has_one`/`address` constraints). At minimum, add a constraint that ties `creator` to `permission.authority` or another admin-approved value rather than accepting it as free-form instruction data.

### Proof of Concept
1. Protocol admin grants a `Permission` PDA to partner wallet `P` via `create_permission_pda` (intended so `P` can launch pools on behalf of token projects).
2. `P` calls `initialize_with_permission`, supplying `payer = P` and `creator = P`'s own attacker wallet `A` (instead of the real project's treasury wallet), along with legitimate mint/vault/config accounts.
3. `pool_state.pool_creator` is set to `A`; the constraint checks on `creator` never fire because none exist.
4. As swaps occur on the pool, creator fees accumulate in `pool_state.creator_fees_token_0/1`.
5. `A` calls `collect_creator_fee` (passing the `address = pool_state.load()?.pool_creator` check) and withdraws all accrued creator fees indefinitely; the intended project/team can never claim them because `pool_creator` cannot be changed.
