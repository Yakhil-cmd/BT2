### Title
Signature verification keyed off unverified `repository.owner.login`/`organization.login` allows cross-organization forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate the HMAC signature against by reading `repository_owner`, a value taken directly from the **unverified** JSON body. The handler that actually processes the event, however, resolves the target repository/stack from a *different* field of the same unverified body (`repository.full_name`). Because the org used to pick the secret and the repository that gets written to are never cross-checked against each other, an attacker who can produce a valid signature for *any one* configured organization (including an org whose `webhook_secret` is unset/nil, which the code treats as "always verified") can forge a payload whose `repository.full_name` points at a completely different, unrelated repository/stack and have it processed as if it were an authentic GitHub webhook for that repository.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is computed purely from body content, before any verification: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config for that org and calls `verify_webhook_signature`, which HMACs `request.raw_post` with that org's `webhook_secret`: [3](#0-2) 

Critically, `return true unless webhook_secret` — if an organization is configured (as shown in the repo's own default/example secrets files) with `webhook_secret: # nil`, *any* payload claiming that org as `repository_owner` is treated as verified with no HMAC check at all: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `create` dispatches to handlers using the raw parsed params — the *same* body whose `repository.owner.login` was used for org selection: [6](#0-5) 

But the handler base class resolves the actual `Stack`/`Repository` to act on from a wholly independent field, `repository.full_name`, with no re-validation that this repository belongs to the organization whose secret was used to authenticate the request: [7](#0-6) 

This breaks the intended binding: `organization authenticated == organization owning the repository written`. The engine only proves "this payload was signed by *an* org's secret" but then trusts an unrelated, attacker-controlled field (`repository.full_name`) to decide which stack's data gets mutated (e.g. `GithubSyncJob` enqueued for pushes, commit `Status` records created, `RefreshCheckRunsJob` enqueued for check suites, pull request handlers creating/merging data) — for any repository tracked by Shipit, regardless of which org's key/secret signed the request.

### Impact Explanation
This is a High-impact escalation: an attacker who is a legitimate member/admin of one GitHub organization configured in Shipit's multi-org `github:` secrets (or who exploits an org configured with a blank `webhook_secret`, which the codebase's own default templates leave nil) can forge signed webhook events targeting a completely different organization's repositories/stacks tracked by the same Shipit instance. Depending on which event is spoofed this allows unauthenticated write of stack/commit/status state belonging to a repository the attacker does not control — e.g., injecting fake `status` events (`Shipit::Status`) that could affect deploy-safety checks, or triggering sync/check-run jobs for arbitrary tracked repositories — a cross-repository/cross-organization trust violation.

### Likelihood Explanation
Likelihood is elevated in any deployment using the documented multi-org configuration (`docs/setup.md` "Using Multiple Github Applications"), where each org can have its own independent `webhook_secret`, and the setup template ships `webhook_secret:` blank by default. Any organization admin able to sign (or, if `webhook_secret` is nil, simply craft) a webhook body can pick an arbitrary `repository.full_name` value; no additional authentication or repository access on the target repo is required.

### Recommendation
After verifying the signature, re-derive the organization from the same trusted source used for authentication and assert it matches the organization implied by `repository.full_name`/`organization.login` used by the handlers, rejecting the request if they diverge. Additionally, avoid treating a missing/blank `webhook_secret` as automatically verified in multi-org configurations, or require it explicitly per environment.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` (attacker-controlled webhook secret or blank secret) and `OrgB` (victim org whose repositories are tracked).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` computes `Shipit.github(organization: "OrgA")` and validates the HMAC (or trivially passes if `OrgA.webhook_secret` is nil) — see [1](#0-0)  and [3](#0-2) .
4. The push handler resolves the stack via `Repository.from_github_repo_name("OrgB/victim-repo")` — see [7](#0-6)  — and processes the forged event against `OrgB`'s stack, even though the request was never authenticated by `OrgB`'s credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
