### Title
Attacker-controlled `.gitmodules` can cause unbounded/slow submodule fetches that permanently exceed `--sync-timeout`, causing persistent sync denial - (File: main.go)

### Summary
`git-sync` fetches an operator-specified `--repo`/`--ref`, but the *content* of that repo—including its `.gitmodules` file—is effectively untrusted input from whoever can push to the tracked ref. `configureWorktree` unconditionally runs `git submodule update --init --recursive` (or `--recursive` variants) with no cap on the number of submodules, nesting depth, or per-submodule size, bounded only by the global `--sync-timeout` context. Because the default `--max-failures` is `0`, any single sync failure (including a `context.DeadlineExceeded` from a submodule update that runs too long) causes git-sync to `os.Exit(1)` immediately, and every subsequent attempt repeats the same unbounded submodule work and fails again, producing a persistent inability to publish new (or any) content.

### Finding Description
`configureWorktree` builds submodule args from `--submodules` and runs them against the worktree with no independent bound on the number/size/nesting of submodules: [1](#0-0) 

This runs inside `SyncRepo`, which is itself wrapped by a single `context.WithTimeout(context.Background(), *flSyncTimeout)` for the *entire* sync attempt (fetch + worktree creation + submodule update): [2](#0-1) 

If a commit on the tracked branch/tag introduces a `.gitmodules` with a very large number of submodules, deeply nested recursive submodules, or a submodule pointing at a huge/slow remote, the `git submodule update --init --recursive` step can be made to reliably exceed `--sync-timeout` (default 120s) on every single sync attempt, since `configureWorktree` is re-run from scratch each loop iteration (`removeWorktree` + `worktree add` + `configureWorktree`): [3](#0-2) 

Because `--max-failures` defaults to `0` ("any sync failure will terminate git-sync"), the very first such failure aborts the process: [4](#0-3) 

In a Kubernetes sidecar deployment the pod/container will simply restart and retry the identical unbounded submodule operation against the same malicious commit, since `--root` (the persistent volume) retains the git object database and the same ref is fetched again — the failure is deterministic and repeats indefinitely (CrashLoopBackOff / stuck at old published hash), never advancing `--link` to the new hash and, if it happens during the very first sync, never publishing anything at all.

This is directly analogous to the Convex `BaseRewardPool.addExtraReward` issue: a party who can influence "external" state that git-sync must fully process before it can perform its principal function (`pullFromLocker` / publish-symlink) can grow that state without bound, so the required processing step never completes and the consumer is permanently denied service (unable to withdraw funds / unable to receive synced files).

### Impact Explanation
- Persistent sync denial: the symlink (`--link`) never advances past a known-good hash, or — on first deployment — is never created at all, denying the consuming application any (or any updated) data indefinitely.
- No recovery without operator intervention (raising `--sync-timeout`/`--max-failures`, pinning to an older ref, or disabling submodules), even though the underlying cause is attacker-supplied repo content, not an operator misconfiguration.
- This matches the accepted impact class "persistent sync denial" from the validation rules.

### Likelihood Explanation
Requires only the ability to add a commit to the ref that `--repo`/`--ref` tracks (e.g., a compromised/malicious contributor, a malicious PR merged by mistake, or any scenario where the synced repository's write access is broader than the git-sync operator trusts). No git-sync admin privilege or special flags are required beyond the tool's default configuration (`--submodules=recursive` is the default, `--max-failures=0` is the default). The attack is purely data-driven (`.gitmodules` content) and does not require exploiting a memory-safety or logic bug in git-sync itself — it abuses the unbounded nature of `git submodule update --init --recursive` relative to the fixed `--sync-timeout` budget.

### Recommendation
- Enforce a configurable cap on the number of submodules and recursion depth processed per sync, or run submodule initialization with its own independent, shorter timeout/backoff separate from the whole-sync timeout so a single hang doesn't necessarily burn the entire attempt.
- Treat submodule-update timeouts as a distinguishable "slow content" failure mode and avoid tearing down/recreating the entire worktree from scratch every retry (allow incremental resumption) so repeated attempts have a chance to make forward progress instead of always restarting from zero.
- Document (and consider defaulting) `--max-failures` to a small positive/negative-with-backoff value for submodule-heavy repos, and surface clear operator-facing metrics/alerts distinguishing "submodule update exceeded timeout" from generic fetch failures so operators can react before assuming total denial.

### Proof of Concept
1. Attacker with push access to the tracked branch adds a `.gitmodules` file referencing hundreds/thousands of submodules (or a small number of very large/slow ones), and/or nests submodules many levels deep, then commits/pushes.
2. Operator's git-sync (defaults: `--submodules=recursive`, `--sync-timeout=120s`, `--max-failures=0`) fetches the new commit; `configureWorktree` invokes `git submodule update --init --recursive` per [1](#0-0) .
3. The submodule update does not finish within 120s; `ctx` created in the main loop is cancelled, `SyncRepo` returns an error.
4. `failCount` becomes `1`, `getMaxFailures()` returns `0`, so `failCount >= maxFails` is true and the process calls `os.Exit(1)` per [5](#0-4) .
5. In Kubernetes the container restarts, re-fetches the same malicious commit against the persisted `--root` volume, and repeats step 2–4 indefinitely — the symlink is never advanced (or never created, if this is the first sync), producing persistent sync denial.

*Note: I was unable to fully inspect `pkg/cmd/cmd.go`'s exact `exec.CommandContext` wiring before the tool budget ran out, so I cannot cite the precise line showing the submodule subprocess is killed on context cancellation versus merely the outer loop giving up while a subprocess lingers; either way the observable effect (permanent inability to publish across restarts) holds, but this specific mechanical detail should be verified in a full session.*

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}
