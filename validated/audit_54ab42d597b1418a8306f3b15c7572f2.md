### Title
Unvalidated swap-route venues can steal unrelated caller-approved assets - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept caller-supplied opaque `swap` bytes and forward them to the configured router. [1](#0-0) [2](#0-1)  The route’s address registry supplies the venue contract for each hop, and no venue allowlist prevents it from being attacker-deployed code. [3](#0-2) [4](#0-3)  While executing under the caller’s authorized strategy invocation, that code can request additional `caller` token transfers; if simulation and signing include the injected child authorization, the transfer succeeds even though it is unrelated to the lending swap.

### Finding Description
`process_swap_collateral` authenticates `caller` and authorizes account access, then passes the unmodified `swap` payload into `withdraw_and_swap_from_supply`. [5](#0-4)  `swap_tokens` authorizes only the controller’s exact input-token transfer to the router and measures controller balances before and after `execute_strategy`, but it does not decode or constrain the venue addresses embedded in `swap`. [6](#0-5)  The router constructs `SwapHop.pool` directly from the route’s `assets` registry and dispatches the selected venue, so a valid payload can name an attacker contract that implements the expected pool ABI. [3](#0-2)  Because the strategy root used `caller.require_auth`, a nested `token.transfer(caller, attacker, amount)` from that venue can be represented as a child authorization beneath the signed strategy call; the measured controller output and final risk checks do not bound that separate wallet transfer. [7](#0-6) [8](#0-7) 

### Impact Explanation
A malicious route can cause theft of any unrelated tokens held by the caller when the caller signs the poisoned authorization tree. The swap can still spend the expected input, return a positive measured output, redeposit it, and pass final account validation, so the protocol-visible operation appears successful while the attacker receives assets outside the routed amount. [8](#0-7) [9](#0-8)  This is theft of user funds, not merely poor execution quality, because the stolen token and recipient need not participate in the route or lending markets.

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue and construct the route bytes without privileged access, malformed encoding, or leaked keys. Exploitation requires a victim to submit a route containing the attacker venue and sign the resulting authorization tree, so the practical vector is a malicious quote, interface, or manually supplied `swap` payload; the opacity of the route bytes and the controller’s lack of route validation make that precondition realistic.

### Recommendation
Restrict route-selected venue and pool addresses to a governance-approved registry or another allowlist of known-compatible contracts, rather than accepting arbitrary `assets` entries as executable pool addresses. Controller and router integrations should also reject authorization trees containing child invocations other than the exact expected token transfer, and clients should surface and block unexpected `caller` transfers before signing. [2](#0-1) [3](#0-2) 

### Proof of Concept
1. The victim owns a solvent account with supplied USDC and also holds an unrelated token `VICTIM_TOKEN`; the attacker deploys `RoguePool` configured with `(victim, VICTIM_TOKEN, attacker, victim_balance)`.
2. `RoguePool` implements the ABI expected by one supported venue: it accepts the router’s input payment, returns enough ETH to satisfy `min_out`, and additionally calls `VICTIM_TOKEN.transfer(victim, attacker, victim_balance)`.
3. The attacker encodes a route whose `assets` registry contains USDC, ETH, and `RoguePool`, and whose swap instruction uses `RoguePool` as `idx_a`, USDC as `idx_b`, and ETH as `idx_c`; `token_in`, `token_out`, and a positive `min_out` are encoded in the program header. [10](#0-9) [3](#0-2) 
4. The victim is induced to invoke `swap_collateral(caller=victim, account_id, current=(hub_id, USDC), amount, new=(hub_id, ETH), swap=malicious_route)`.
5. `process_swap_collateral` validates the account owner, withdraws the USDC supply, and calls `swap_tokens`, which authorizes only controller→router USDC spending and invokes `execute_strategy`. [11](#0-10) [12](#0-11) 
6. During the venue call, `RoguePool` requests `VICTIM_TOKEN.transfer(victim, attacker, victim_balance)`; simulation records it beneath the victim’s strategy authorization, and signing that tree authorizes it.
7. The router returns enough ETH for `verify_router_output` to pass, the controller redeposits the ETH and finalizes the position, while `victim_balance` of `VICTIM_TOKEN` has been transferred to the attacker. [8](#0-7) [9](#0-8)
