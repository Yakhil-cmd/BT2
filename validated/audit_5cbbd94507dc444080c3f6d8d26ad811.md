### Title
Webhook organization used for signature verification is not bound to the repository/commit the event handler writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / webhook secret to validate a signature against based on an **attacker-controlled** field of the JSON payload (`repository.owner.login`, falling back to `organization.login`), but the handlers that subsequently act on the payload resolve the target **repository and commit independently**, using a different payload field (`repository.full_name`) or no repository scoping at all. There is no requirement that the two agree. If any organization configured in a multi-org Shipit deployment has no `webhook_secret` set (a documented, supported configuration), signature verification for that organization is a no-op, and the attacker can forge webhook payloads that are "verified" under that unsecured organization while writing state (commit statuses, pushes) belonging to a completely different, properly-secured organization/repository.

### Finding Description
`verify_signature` derives the organization used for verification purely from the untrusted payload: [1](#0-0) [2](#0-1) 

It then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. `GitHubApp#verify_webhook_signature` explicitly **bypasses** verification when that organization has no configured secret: [3](#0-2) 

This "no secret configured → trust everything" behavior is documented as normal: the setup docs and example secrets files show `webhook_secret` as optional/nilable per organization in the multi-org schema. [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (for the unsecured org), the controller dispatches the **entire raw payload**, unchanged, to the registered handlers: [6](#0-5) 

Handlers resolve the target repository/stack from a *different* payload field than the one used for signature verification: [7](#0-6) [8](#0-7) 

Worse, `StatusHandler` performs **no repository scoping at all** — it updates any commit in the entire Shipit instance matching the attacker-supplied `sha`, regardless of which repository/organization it belongs to: [9](#0-8) 

This breaks the binding: *the organization whose webhook secret authenticated the request* ≠ *the repository/commit the handler actually writes to*. This is the direct structural analog of the reported bug class — a verification/guard path (there, an error path that should abort startup; here, a signature check that should gate which repository may be mutated) is decoupled from the actual resource being acted upon, letting the "trusted" identity for one context be silently substituted for another.

### Impact Explanation
An unprivileged, unauthenticated attacker (no Shipit session, no API token, no GitHub write access) can:
- Forge arbitrary GitHub commit-status payloads (`state: success`, etc.) for any commit SHA tracked by any stack in the Shipit instance, as long as the deployment has at least one organization without a `webhook_secret` configured. Since `StatusHandler` has zero repository scoping, this works across organizations.
- These forged statuses feed directly into `StatusChecker`, which gates automatic merges (`MergeRequest#any_status_checks_failed?`, `#all_status_checks_passed?`) and continuous deployment triggers: [10](#0-9) 
- This can enable an **unauthorized merge or deploy** — satisfying CI gating with forged "success" statuses without any real CI passing, or forge pushes causing `sync_github` to run against another org's repository.

This meets the report's Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only that the Shipit deployment uses the (documented) multi-organization GitHub configuration and that at least one configured organization has no `webhook_secret` set — an explicitly supported and exemplified configuration in this engine's own docs and fixtures, not a misuse of the engine. No credentials, tokens, or prior access are needed; the attacker only needs network access to the public `/github/webhooks` endpoint and knowledge of one unsecured organization's name (visible from Shipit's own public stack pages) to bypass the check for a completely different, secured target repository.

### Recommendation
- Verify the webhook signature using the GitHub App/secret associated with the **repository being written to** (`payload.dig('repository','full_name')`'s owning organization), not a separately-chosen field.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; treat a missing secret as a hard configuration error for any organization that receives webhooks (fail closed).
- Scope `StatusHandler` (and any other handler lacking repository binding) to the repository resolved during signature verification, rejecting events whose payload repository doesn't match the authenticated organization.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub config shown in `docs/setup.md`, where org `unsecured-org` has `webhook_secret` left blank and org `victim-org` has a real webhook secret and a tracked stack/commit.
2. As an anonymous attacker, POST to `/github/webhooks`:
```
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim-org tracked commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/critical-repo" }
}
```
No valid `X-Hub-Signature` is required — `repository_owner` resolves to `unsecured-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
3. `StatusHandler#process` updates the status of the targeted commit in `victim-org/critical-repo` (or, since it does no repo scoping, any commit with that SHA anywhere in the Shipit instance), potentially satisfying merge/deploy CI gating for a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
