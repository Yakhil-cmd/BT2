## Finding: Uncaught length-assumption exception in `chash.js` `isChashValid()` reachable via any address/definition validation

### Title
Unhandled exception in c-hash length validation causes a full-node crash on a crafted address string - (File: chash.js)

### Summary
`chash.js`’s `isChashValid()` assumes that once a 32- or 48-character encoded string is base32/base64-decoded, the resulting bit-length is *always* exactly 160 or 288 bits. That assumption is not actually guaranteed by Node’s lenient `Buffer.from(str, 'base64')` decoder, and the length-mismatch path throws an **uncaught `Error`** outside of any `try/catch`, unlike the CVE-2017-11704 pattern of trusting an internal offset/length invariant while parsing attacker-supplied structured data without verifying it, causing an out-of-bounds condition deep in a low-level decode routine.

### Finding Description
`isChashValid()` in `chash.js` only wraps the *decode* step (`base32.decode`/`Buffer.from(..., 'base64')`) in a `try/catch`: [1](#0-0) 

but the subsequent calls are **not** protected: [2](#0-1) 

`buffer2bin(chash)` produces a bit-string whose length is `chash.length * 8`, and this is fed into `separateIntoCleanDataAndChecksum(binChash)`: [3](#0-2) 

This function throws `Error("bad length=...")` if the bit-length is anything other than exactly 160 or 288 — an assumption inherited from `getChash()`’s well-formed output, but never re-verified for attacker-supplied (`isChashValid`) input. Because `Buffer.from(str, 'base64')` in Node.js does not strictly validate character content/padding the way strict base64 decoders do, a 48-character string containing certain invalid/edge-case characters can decode to a buffer whose length is not exactly 36 bytes (288 bits), triggering the uncaught throw instead of the intended graceful `false` return.

`isChashValid()` is invoked (indirectly) by `validation_utils.js`’s `isValidAddress()`, which is called throughout the definition-evaluation code on attacker-controlled data, e.g. in the `'address'` operator of address/asset definitions evaluated for every posted unit: [4](#0-3) 

Because this call sits deep inside a chain of continuation-passing (`cb`) style evaluation rather than promise/async-wrapped error handling, an exception thrown here is not caught by the calling code and propagates up the call stack as an uncaught exception.

### Impact Explanation
An uncaught exception during unit/definition validation, if it escapes to the top of the event loop, crashes the Node.js process handling that unit — a full node processing a maliciously crafted address definition (something any unit poster or AA definer can embed, e.g. via the `'address'` op referencing a crafted 48-character string) could be knocked offline. Because full nodes independently validate units, this can lead to node crashes/`network unable to confirm new units` if triggered broadly, or inconsistent validation state between nodes that do/do not crash before finishing validation — matching the accepted “node disagreement on validity” / “network unable to confirm new units” impact categories.

### Likelihood Explanation
Reaching this code path requires only posting a unit containing an address/asset definition that uses the `'address'` op (or any other path that calls `isValidAddress`) with a 48-character string engineered to decode via `Buffer.from(..., 'base64')` into something other than exactly 36 bytes. This requires no special privileges — any unit poster can construct and broadcast such a definition. The exact byte sequences that trigger a mismatched decoded length depend on Node’s base64 decoder leniency, which I was not able to fully verify empirically (no execution environment available), so likelihood is assessed as *plausible but unconfirmed* pending a concrete PoC string.

### Recommendation
Wrap the entire body of `isChashValid()` (not just the decode step) in the existing `try/catch`, and inside `separateIntoCleanDataAndChecksum`/`mixChecksumIntoCleanData`, return an error value instead of throwing when the length invariant is violated, so malformed encoded addresses are rejected gracefully (`return false`) rather than crashing the process. Additionally, harden all call sites of `isValidAddress`/`isChashValid` in `definition.js`/`validation_utils.js` with defensive `try/catch` so any residual parsing exception cannot escape unit validation.

### Proof of Concept
Not fully confirmed. Conceptually:
1. Craft a 48-character string `S` such that `Buffer.from(S, 'base64')` decodes to a buffer whose length is not exactly 36 bytes (relying on Node's lenient base64 parsing of invalid/edge characters).
2. Include `S` as `other_address` in an `'address'` definition operator inside a unit's address definition or AA definition and broadcast the unit.
3. When a full node validates the unit, `isValidAddress(S)` → `isChashValid(S)` decodes `S` successfully (no exception in the `try` block) but produces a `binChash` of unexpected length, causing `separateIntoCleanDataAndChecksum` to throw uncaught, potentially crashing the validating node's process.

I was unable to execute Node.js locally to confirm a concrete byte sequence that reproduces the length mismatch from `Buffer.from(str, 'base64')`; this would need to be verified in a live environment (suggest starting a Devin session with code execution access to construct and test a concrete PoC string).
