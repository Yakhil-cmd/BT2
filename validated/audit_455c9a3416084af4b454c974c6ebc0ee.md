### Title
Missing structural limits in `prepare_v2::prepare_contract` allow super-linear preparation cost relative to charged code size - (File: `runtime/near-vm-runner/src/prepare/prepare_v2.rs`)

### Summary
`prepare_v2::prepare_contract` performs wasm validation, section rewriting, and `finite_wasm` gas/stack analysis on attacker-deployed code, but only enforces limits on function count, local count, table count/elements, and type count. Unlike its successor `prepare_v3`, it has **no** limits on function body size, number of blocks per function/contract, number of params per function/contract, or operand-stack bytes per function, all of which `prepare_v3` explicitly added (`PrepareError::TooManyBlocksPerFunction`, `TooManyBlocksPerContract`, `TooManyParamsPerFunction`, `TooManyParamsPerContract`, `OperandStackTooLarge`).

### Finding Description
`PrepareContext::run` in `prepare_v2.rs` walks the wasm module and enforces only these checks: `type_limit`, `function_limit`, `local_limit`, `table_limit`/`table_element_limit` [1](#0-0) . It then hands the "lightly steamed" module to `finite_wasm::Analysis` for stack-height and gas-cost instrumentation [2](#0-1) .

Because there is no cap on the number of control-flow blocks per function/contract, nor on the number of parameters per function/contract, nor on operand-stack size, nor on function body size, an attacker can craft a wasm module (within the byte-size fee-charged for `DeployContract`) that is deliberately shaped to blow up work done in the validation/instrumentation passes (e.g., very deeply nested or numerous blocks driving the `finite_wasm` stack/gas metering instrumentation into much larger output and much more per-block work than the linear-in-bytes assumption holds for). The project's own `prepare_v3` module was built specifically to close this gap, adding exactly these checks with accompanying regression tests (`too_many_blocks_per_function`, `too_many_blocks_per_contract`, `too_many_function_params`, `operand_stack_too_large` in `runtime/near-vm-runner/src/prepare.rs`) [3](#0-2) [4](#0-3) [5](#0-4) , and the estimator module even contains named "adversarial" cost functions for these exact classes of contracts (`adversarial_compile_max_blocks`, `adversarial_load_many_globals`, etc.) [6](#0-5) , confirming these are known classes of pathological inputs that must be bounded during preparation.

The dispatcher `prepare::prepare_contract` selects `prepare_v3` when `config.reftypes_bulk_memory` is true or `kind == VMKind::Wasmtime`, and falls back to `prepare_v2` otherwise [7](#0-6) . This means `prepare_v2` (with its missing limits) is only reachable for runtimes/configurations where `reftypes_bulk_memory` is disabled and the vm kind is not Wasmtime (e.g. legacy `NearVm`/`Wasmer2` configurations on older protocol versions). I was not able to fully confirm from the available index whether any currently active mainnet/testnet runtime config still sets `reftypes_bulk_memory: false` for a non-Wasmtime `vm_kind` (this would need to be checked against the live `RuntimeConfigStore` for the current `PROTOCOL_VERSION`, and against historical block replay requirements, which is not resolvable purely from the index).

### Impact Explanation
If `prepare_v2` is reachable by the currently active protocol configuration for any VM kind, an attacker can deploy a contract that costs the fee-charged (linear-in-bytes) `deploy_contract_cost_per_byte`/`function_call_cost` amount of gas but consumes disproportionately more CPU time in `prepare_contract`, violating the "1ms = 1 Tgas" invariant documented in `docs/architecture/gas/README.md` (compilation/preparation must be linear or `O(n log n)` in code size) [8](#0-7) [9](#0-8) . This is underpriced/free execution relative to true node CPU cost, which for chunk producers can raise the risk of missed block deadlines / slowed chain progress if exploited broadly — matching the "High: greatly increasing the computational cost of the network" impact class.

### Likelihood Explanation
Exploitability is entirely gated on which `prepare_contract` variant is selected by the active `Config`. This depends on `reftypes_bulk_memory` and `vm_kind` for the specific protocol version/runtime in use, which I could not conclusively verify from the indexed snapshots within the available search budget. If any currently supported runtime path still routes through `prepare_v2`, the attack requires only an ordinary `DeployContract` + `FunctionCall`, i.e., trivially reachable by any unprivileged account — making likelihood high conditional on reachability. If `reftypes_bulk_memory` is unconditionally `true` for all currently active configs/vm kinds, the `prepare_v2` code path is dead for current protocol execution and the practical impact is limited (though the code itself remains a latent risk, e.g. if a future config toggles the feature off, or during historical block replay under old protocol versions).

### Recommendation
- Confirm whether `prepare_v2` is reachable under any currently supported `RuntimeConfigStore` configuration (checked against `PROTOCOL_VERSION`) and, if so, port the `prepare_v3` limits (`max_function_body_size`, `max_blocks_per_function`, `max_blocks_per_contract`, `max_params_per_function`, `max_params_per_contract`, `max_operand_stack_bytes_per_function`) into `prepare_v2::PrepareContext`.
- If `prepare_v2` is confirmed dead for all live/reachable protocol versions, consider removing it entirely (or gate it behind an explicit "legacy replay only" path) to eliminate the latent risk of it becoming reachable again via a config change.
- Add estimator/regression benchmarks in `runtime/runtime-params-estimator` specifically targeting `prepare_v2` with adversarial block/param/operand-stack shapes, mirroring the existing `adversarial_*` functions used for `prepare_v3`/other paths.

### Proof of Concept
Add a case under `runtime/near-vm-runner/src/tests/` that:
1. Forces `config.reftypes_bulk_memory = false` and a non-Wasmtime `vm_kind` (e.g. `NearVm`) so `prepare::prepare_contract` routes to `prepare_v2`.
2. Builds a wasm module reusing the harnesses already present in `runtime/near-vm-runner/src/prepare.rs` tests (`contract_with_many_blocks`, `contract_with_blocks_in_one_function`, and a params-per-function generator) but at large N (e.g. tens of thousands of nested/sequential blocks, or thousands of functions with max params), while keeping raw wasm byte size small/constant.
3. Measure wall-clock time and/or instrumented-output size of `prepare_v2::prepare_contract(...)` versus `prepare_v3::prepare_contract(...)` for the same logical shapes, and assert that `prepare_v2` (a) accepts inputs `prepare_v3` would reject with `TooManyBlocksPerFunction`/`TooManyParamsPerFunction`/`OperandStackTooLarge`, and (b) exhibits preparation cost growth super-linear in raw code size while burnt gas (computed from `deploy_contract_cost_per_byte`/`function_call_cost_per_byte`) grows only linearly — demonstrating the underpriced-execution gap.

pub(crate) fn prepare_contract(
    original_code: &[u8],
    features: crate::features::WasmFeatures,
    config: &Config,
    kind: VMKind,
) -> Result<Vec<u8>, PrepareError> {
    let lightly_steamed = PrepareContext::new(original_code, features, config).run()?;

    let res = finite_wasm::Analysis::new()
        .with_stack(Box::new(SimpleMaxStackCfg))
        .with_gas(Box::new(SimpleGasCostCfg(u64::from(config.regular_op_cost))))
        .analyze(&lightly_steamed)
        .map_err(|err| {
            tracing::error!(?err, ?kind, "analysis failed");
            PrepareError::Deserialization
        })?
        // Make sure contracts can’t call the instrumentation functions via `env`.
        .instrument("internal", &lightly_steamed)
        .map_err(|err| {
            tracing::error!(?err, ?kind, "instrumentation failed");
            PrepareError::Serialization
        })?;

pub fn prepare_contract(
    original_code: &[u8],
    config: &Config,
    kind: VMKind,
) -> Result<Vec<u8>, PrepareError> {
    let features = crate::features::WasmFeatures::new(config);
    if config.reftypes_bulk_memory || config.vm_kind == VMKind::Wasmtime {
        prepare_v3::prepare_contract(original_code, features, config, kind)
    } else {
        prepare_v2::prepare_contract(original_code, features, config, kind)
    }
}

    fn too_many_function_params() {
        // Hard-coding config parameters in this test.
        // If the config changes and you have to update these numbers, it most
        // likely means you are about to make a breaking change to WASM
        // contracts, so be careful if that's why you are reading this.
        let max_per_fn = 64;
        let max_per_contract = 50_000;

        // num_params, num_functions, expected preparation Result
        check(1, 1000, Ok(()));
        check(max_per_fn, max_per_contract / max_per_fn, Ok(()));
        check(
            max_per_fn,
            (max_per_contract + max_per_fn) / max_per_fn,
            Err(PrepareError::TooManyParamsPerContract),
        );

        // check that TooManyParamsPerFunction hits before TooManyParamsPerContract
        check(
            max_per_fn + 1,
            (max_per_contract + max_per_fn) / max_per_fn,
            Err(PrepareError::TooManyParamsPerFunction),
        );

        // check that TooManyFunctions hits before TooManyParamsPerFunction
        check(max_per_fn + 1, 1, Err(PrepareError::TooManyParamsPerFunction));
        check(max_per_fn + 1, 10_001, Err(PrepareError::TooManyFunctions));

        // check that TooManyFunctions hits before TooManyParamsPerContract
        check(
            (max_per_contract + 10_000) / 10_000,
            10_000,
            Err(PrepareError::TooManyParamsPerContract),
        );
        check((max_per_contract + 10_000) / 10_000, 10_001, Err(PrepareError::TooManyFunctions));

        #[track_caller]
        fn check(num_params: usize, num_functions: usize, expect: Result<(), PrepareError>) {
            with_vm_variants(|kind| {
                let config = test_vm_config(Some(kind));
                let params =
                    std::iter::repeat("i32").take(num_params).collect::<Vec<_>>().join(" ");
                // anonymous function with N parameters and no body
                let function_def = format!("(func (param {params}))\n");
                let all_function_defs = function_def.repeat(num_functions);

                    &config,
                    kind,
                    &format!(
                        r#"(module
                            {all_function_defs}
                        )"#
                    ),
                );

                if let Err(expected_err) = &expect {
                    let Err(err) = test_result else {
                        panic!(
                            "got Ok expecting error {expected_err}, vm={kind:?}, num_params={num_params}, num_functions={num_functions}"
                        );
                    };
                    assert_eq!(
                        err, *expected_err,
                        "got the wrong error, got {err} but was expecting {expected_err}, vm={kind:?}, num_params={num_params}, num_functions={num_functions}"
                    );
                } else {

                        test_result.is_ok(),
                        "got error when expecting ok, {test_result:?}, vm={kind:?}, num_params={num_params}, num_functions={num_functions}"

### Compilation

The NEAR protocol charges gas fees to deploy a contract. One part of a deployment involves
preparing the contract Wasm code for execution. This may involve instrumentation, compilation,
serialization of the machine code and other similar operations.

An estimate of the deployment cost will typically involve a function which uses the size of the
input Wasm code as its primary input. Such a function can only exist if we have a good knowledge of
the runtime’s time complexity properties are known. For our purposes a linear or `O(n log n)`
relationship between the input size and execution time is the highest we can accept.
