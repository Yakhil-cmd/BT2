### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` and `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with multiple GitHub organizations (each with its own `webhook_secret`, as documented in `config/secrets.development.shopify.yml`), `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), while the downstream event handlers resolve the target `Stack`/`Repository` using a *different* field in the very same payload, `repository.full_name`. Nothing binds these two fields together, so an org administrator who legitimately controls one onboarded organization (and therefore legitimately knows that organization's `webhook_secret`) can forge a validly-signed webhook whose `repository.full_name` points at a completely different, victim organization's repository.

### Finding Description
`WebhooksController#verify_signature` resolves the `GitHubApp`/secret to check against like this: [1](#0-0) [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [2](#0-1) 

`repository_owner` is derived purely from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` in `lib/shipit/github_app.rb` computes an HMAC over `request.raw_post` using the `webhook_secret` belonging to whichever organization `repository_owner` names: [3](#0-2) 

Crucially, the HMAC only proves that the request body was signed with *some* organization's configured secret — it says nothing about whether the rest of the payload is internally consistent. Once signature verification passes, `create` dispatches the raw parsed `params` to the registered handlers: [4](#0-3) 

The handlers (e.g. `PushHandler`, `StatusHandler`) locate the target `Stack` via `Handler#stacks`/`#repository_name`, which reads a **different** JSON key, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

`Shipit.github_app_config`/`Shipit.github` support hosting several independently-configured GitHub organizations, each with its own `webhook_secret`, exactly as shown in the multi-org secrets template: [8](#0-7) [9](#0-8) 

Because GitHub itself would never emit a payload where `repository.owner.login` differs from the owner embedded in `repository.full_name`, the engine implicitly trusts that these two fields always agree. But an attacker who legitimately administers one onboarded organization (and thus knows that organization's own `webhook_secret`, since they configured/installed the app) can construct an arbitrary JSON body, set `repository.owner.login` to their own org (so the correct/known secret is selected and the HMAC check passes), and set `repository.full_name` to `"victim-org/victim-repo"`. The signature check succeeds (it is being checked against the attacker's own known secret over the attacker's own crafted bytes), yet the handler acts on the victim repository named by `full_name`.

The equality that is broken:
`organization authenticated by verify_signature (repository.owner.login) == repository the handler actually writes to (repository.full_name)` — these are never enforced to be equal, despite always being equal in a genuine GitHub-originated webhook.

### Impact Explanation
This lets a Shipit tenant that legitimately owns one onboarded GitHub organization forge webhooks that are treated as authentic events for **any other organization/repository hosted on the same Shipit instance**, without any Shipit session, API token, or the victim's webhook secret. Depending on registered handlers this enables:
- Forged `push` events → `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for the victim's stack [6](#0-5) , letting the attacker drive synchronization of arbitrary commit SHAs into the victim stack's commit history.
- Forged `status` events → `StatusHandler` creates fabricated CI statuses on the victim's commits [7](#0-6) , which can directly satisfy `required_statuses`/`merge_request_required_statuses` checks used to gate automatic deploys and the merge queue [10](#0-9) , potentially leading to an unauthorized deploy or merge on the victim's repository — this crosses the "Critical: unauthorized deploy/merge" bar defined in scope.

This is a genuine cross-repository/cross-tenant write achieved purely by crafting request bodies against the multi-org webhook endpoint; it requires no Shipit login and no possession of the victim's secret.

### Likelihood Explanation
Exploitability depends entirely on the deployment running in the documented multi-organization mode (`secrets.yml` with per-org `webhook_secret`s, as shown in `config/secrets.development.shopify.yml`) and on the attacker legitimately controlling at least one of the onboarded organizations. Single-org deployments (the default/common setup) are not affected because there is only one possible `webhook_secret` and thus no "wrong" organization to select. In the multi-tenant configuration this is straightforward and fully within reach of an unprivileged (relative to the victim organization) but legitimate co-tenant.

### Recommendation
After signature verification succeeds, verify that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` before dispatching to handlers, rejecting the payload (HTTP 422) on mismatch. Alternatively, resolve the target `Stack`/`Repository` using the same `repository_owner` value that was used for signature selection rather than trusting `full_name` independently, or bind the resolved repository's known owner to the GitHub App/organization that authenticated the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S_A`, known to the attacker because they administer that org's GitHub App installation) and `victim-org` (secret `S_V`, unknown to the attacker), per the multi-org schema in `config/secrets.development.shopify.yml`.
2. Craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using the attacker's own known secret `S_A`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` selects `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), verifies the HMAC against `S_A`, and succeeds.
6. `PushHandler#process` resolves the target stack via `Repository.from_github_repo_name('victim-org/victim-repo')` (from `repository.full_name`) [5](#0-4)  and calls `stack.sync_github(expected_head_sha: 'attacker chosen sha')` against the victim's stack — despite the request never having been signed with `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
