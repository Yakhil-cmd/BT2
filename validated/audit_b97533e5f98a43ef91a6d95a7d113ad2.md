### Title
Webhook status events update commits across unrelated repositories/organizations because signature verification never binds the authenticated organization to the commit being written - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController` authenticates a webhook delivery only by which GitHub *organization*'s secret produced a valid HMAC signature, never by which *repository/stack* the payload's mutable fields (like `sha`) are allowed to affect. `StatusHandler#process` then updates commit statuses using a completely unscoped, global `Commit.where(sha: ...)` lookup. This reproduces the report's core bug class — a privileged operation acting on data that was never actually covered by the trust check that authorized the call — as a cross-repository "organization authenticated vs. repository written" mismatch.

### Finding Description
`WebhooksController#verify_signature` determines which `GithubApp` secret to validate the request against solely from the payload's `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 

This only proves "this payload was signed by the app installed for organization X." It does **not** prove that the other fields in the payload (in particular `sha`) actually belong to a commit/stack owned by organization X.

`StatusHandler#process`, however, uses `params.sha` to look up and mutate commit status **globally**, with no scoping to the repository/stack that the signature check authenticated: [3](#0-2) 

Compare this with `Handler#stacks`, which *is* correctly scoped by `repository_name` from the payload: [4](#0-3) 

`StatusHandler` does not use this `stacks` scoping at all — it queries `Commit` directly by `sha` across the whole installation. Since a git commit SHA is a content hash that is identical no matter which repository/fork the commit object lives in, an attacker who onboards their own (attacker-controlled) organization/repository as a Shipit stack — and thus legitimately receives a validly-signed `status` webhook from GitHub for their own repo — can push/replicate a commit object with an identical tree/parent/author/committer/message (i.e., the exact same SHA) as a commit that exists in a victim stack under a completely different, unrelated GitHub organization. When GitHub sends the (legitimately signed, by the attacker's own org's webhook secret) `status` event for the attacker's repository, `StatusHandler#process` will match `Commit.where(sha: ...)` against **every** stack's commit row sharing that SHA — including the victim's — and call `commit.create_status_from_github!(params)` on it: [5](#0-4) 

This breaks the binding `organization_authenticated == repository/stack_written`: the signature check authenticates "attacker's org," but the actual write lands on the victim's stack/commit.

### Impact Explanation
If the victim stack has CI status requirements (`ci.require`) and/or continuous deployment enabled, forging a passing `status` for a commit it already tracks lets an attacker cause that commit to be treated as CI-green from an unrelated, attacker-controlled organization, which can unblock or trigger an unauthorized deploy — the required "unauthorized deploy" impact class. It also constitutes an unauthenticated write into a repository/stack the attacker has no authorization over (a cross-repository write), since the only authentication performed binds to a different organization than the one being mutated.

### Likelihood Explanation
Exploitation requires the attacker to control/onboard some repository as a Shipit stack (already a normal, low-privilege GitHub Apps/OAuth flow for many self-service Shipit deployments) and to know or reproduce the exact git commit object (tree/parent/author/committer/message) of a target commit — feasible when the target repository is public/open-source, since git commit hashes depend only on content, not on which remote hosts the object. No access to the victim org's webhook secret, GitHub token, or repository is required.

### Recommendation
`StatusHandler` (and any other handler using bare content lookups such as `sha`) must scope its query to `stacks` (i.e., stacks belonging to the repository named in the authenticated payload), exactly as `PushHandler` and `CheckSuiteHandler` already do, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of a global `Commit.where(sha: params.sha)`. More generally, every webhook handler must verify that all payload fields it acts on belong to the same repository whose organization signature was verified, not merely trust the organization-level HMAC check as a stand-in for repository-level authorization.

### Proof of Concept
1. Attacker registers repository `attacker-org/decoy` in Shipit as a stack (self-service onboarding, low privilege).
2. Attacker forks/replicates a public commit from `victim-org/target` into `attacker-org/decoy` such that the resulting commit object (tree, parent, author, committer timestamps, message) is byte-identical, producing the same SHA.
3. Attacker sets a commit status on that commit in `attacker-org/decoy` via the GitHub API (using their own legitimate repo permissions). GitHub sends a `status` webhook to Shipit, signed with `attacker-org`'s configured webhook secret.
4. `WebhooksController#verify_signature` succeeds because it only checks that `attacker-org`'s secret matches.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which also returns the commit row belonging to `victim-org/target`'s stack, and calls `create_status_from_github!` on it — flipping CI status on a commit the attacker never had access to, in a stack tied to a different, unauthenticated organization.
