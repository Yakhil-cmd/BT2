### Title
Webhook signature verification keys off `repository.owner.login` while the write path keys off the repository payload the attacker also controls - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to check the HMAC signature against using `repository_owner`, a value extracted from the same untrusted JSON body being verified. If that organization's app config has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` treats the request as verified unconditionally. The handlers invoked afterwards, however, resolve the target `Stack`/`Repository` from other fields of that same body (e.g. `repository.full_name`, `branch`, `sha`), which are never bound to the organization that was actually "authenticated." This lets a caller who knows (or is allowed to omit) one organization's webhook secret trigger writes against a completely different, unrelated repository/stack that is nominally protected by its own secret.

### Finding Description
`WebhooksController` determines the signing organization purely from attacker-supplied payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly out of the raw JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) *before* any signature has been validated, and it is used to look up `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is then used to verify the HMAC: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured (`return true unless webhook_secret`). The engine explicitly supports multiple organizations with independent configs, and it is a documented/valid configuration for one org to have no secret at all, as shown in the test fixtures: [4](#0-3) 

After `verify_signature` passes (trivially, because the attacker chose `repository.owner.login` to point at the org with no secret), `create` parses the same raw body and dispatches it to event handlers with no further identity check: [5](#0-4) 

Handlers then resolve the actual repository/stack to write to from other fields of the very same payload — e.g. `PushHandler` triggers a sync (`stack.sync_github`) for stacks matching `branch`, and `StatusHandler` looks up commits purely by `sha` and creates a status on them: [6](#0-5) [7](#0-6) 

Repositories are looked up by `owner/name` derived from the payload, independent of which organization's secret (if any) validated the request: [8](#0-7) 

**The broken equality:** the engine implicitly assumes
`organization whose webhook_secret authenticated the request == organization that owns the repository being written to`.
Nothing in `verify_signature` or `create` enforces that `repository_owner` (used to pick the secret) matches the `repository.full_name`/`sha`/`branch` fields the handlers actually act on within the same JSON body. An attacker can set `repository.owner.login` to an org with no configured secret (or one whose secret the attacker knows), while setting `repository.full_name` (for push events, indirectly via `branch` matching within `stacks`) or a commit `sha` belonging to a *different*, victim-owned stack that does have its own configured secret. Because the signature check exits early once the (attacker-chosen) organization resolves to a no-secret config, the request is accepted, and the handler proceeds to sync/mutate the victim's stack using attacker-controlled `after`/`sha`/`state` values.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely:
- `PushHandler` can be made to call `stack.sync_github(expected_head_sha: params.after)` for any stack whose `branch` matches, regardless of which org "authenticated" the webhook, potentially forcing a `GithubSyncJob` with an attacker-chosen `expected_head_sha` against a repository the attacker does not control.
- `StatusHandler` can inject `create_status_from_github!` records on arbitrary commits located purely by `sha`, spoofing CI/CD status for another team's stack, which can influence auto-deploy/merge decisions (`merge_queue_enabled`, `continuous_deployment`) — i.e., an unauthorized effect on deploy/merge behavior for a repository outside the "authenticated" organization's boundary.
This qualifies as cross-repository writes / an unauthorized deploy-adjacent action driven by spoofed webhook events.

### Likelihood Explanation
Exploitability depends entirely on the deployment's `Shipit.github` multi-org configuration: it requires at least one configured organization with `webhook_secret` blank/nil (a supported, documented configuration per the fixtures) while at least one other organization/repository is properly secured. Given that the engine natively supports and tests this "double github app" configuration with one org having `webhook_secret: nil`, this is a realistic, not purely theoretical, misconfiguration risk that the code does nothing to prevent by binding the picked secret's organization to the actual repository being mutated.

### Recommendation
- After determining which repository/stack a handler will act on, verify that the repository's actual `owner` (as stored in Shipit, via `Repository.from_github_repo_name`) matches the `repository_owner`/organization whose secret validated the signature, and reject the event otherwise.
- Do not allow "no `webhook_secret` configured" to implicitly grant trust for repositories belonging to a different, secured organization; consider requiring a secret for every configured organization or explicitly scoping unsigned orgs so they cannot resolve to other orgs' repositories.
- Bind the verified identity (organization) to the repository/stack resolution path uniformly across all handlers (`push`, `status`, `check_suite`, etc.), rather than only using `repository_owner` for signature selection and separately trusting `repository.full_name`/`sha`/`branch` for the write.

### Proof of Concept
1. Deploy Shipit with a multi-org GitHub App config where `OrgTwo` has `webhook_secret: nil` (a supported configuration, see `test/dummy/config/secrets_double_github_app.yml`) and `OrgOne` (owning the real target stack) has a configured secret.
2. POST to `/webhooks` with header `X-Github-Event: push`, body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" }
   }
   ```
   No `X-Hub-Signature` header is required, since `repository_owner` resolves to `OrgTwo`, whose `webhook_secret` is `nil`, making `verify_webhook_signature` return `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:25-30`, `lib/shipit/github_app.rb:76-83`).
3. `WebhooksController#create` dispatches the parsed body to `PushHandler`, which matches stacks by `branch` (`master`) irrespective of `repository.owner`, and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgOne`'s victim stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`).
4. Similarly, a `status` event with a `sha` belonging to a victim commit can be sent under the guise of the unsecured `OrgTwo`, injecting a spoofed CI status via `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), potentially affecting merge/deploy gating for `OrgOne`'s repository.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
