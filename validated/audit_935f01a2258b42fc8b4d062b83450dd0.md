## Title
API token scoped to one stack can read status/deploy data for any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

## Summary
An `ApiClient` can be scoped to a single `Stack` (`belongs_to :stack, optional: true`), and every other API endpoint enforces this binding by resolving the target stack through the scoped `stacks` collection. `Shipit::Api::CCMenuController`, however, overrides the stack lookup to use `Stack.from_param!(params[:stack_id])` directly, bypassing the per-client stack scope while still relying on the same coarse-grained `read:stack` permission check.

## Finding Description
`Shipit::Api::BaseController` defines the intended binding between an authenticated `ApiClient` and the stacks it is allowed to touch: [1](#0-0) 

This means a client created with a `stack_id` (see `ApiClient#stack_id?` used above) is restricted to `Stack.where(id: current_api_client.stack_id)` — an equality that should hold: `authorized_stack == requested_stack`.

`CCMenuController` inherits `require_permission :read, :stack` from the base controller, which only checks the coarse permission string, not the stack-scoping: [2](#0-1) 

But it overrides `stack` to bypass the scoped `stacks` helper entirely: [3](#0-2) 

`ApiClient#check_permissions!` only verifies the permission string is present in the client's `permissions` array; it performs no comparison against `stack_id`: [4](#0-3) 

So the equality the platform is supposed to enforce — *the stack a token authorizes* (`current_api_client.stack_id`) *equals the stack a token touches* (`params[:stack_id]`) — is broken specifically in this controller, the same class of bug as the audited contract failing to reset `proposedMainWallet`, leaving a stale/unenforced binding that lets a supposedly-scoped credential act outside its intended boundary.

The test suite explicitly documents (and thus relies on) the scoping working correctly elsewhere: [5](#0-4) 

but there is no equivalent assertion for `CCMenuController`, consistent with the scoping check being silently absent there.

## Impact Explanation
An operator who issues a stack-scoped `ApiClient` token (e.g. to expose a single stack's build status to a third-party CI dashboard/CCTray client) is granting a credential that is supposed to only ever read that one stack. Because `CCMenuController#stack` ignores the scope, that same token can be used to read `deploys_and_rollbacks` status/output for **any** stack in the Shipit instance by simply changing `params[:stack_id]`, i.e. an unauthenticated-for-that-resource read of stack state and deploy output — matching the "High" impact bucket of "unauthenticated read of stack state, task streams or deploy output" for stacks the token was never authorized to see.

## Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API tokens (a documented, supported feature: `ApiClient#stack_id?`), since exploitation requires only possession of that one legitimate, narrowly-scoped token — no privilege escalation, no additional secret, and no interaction with `webhook_secret`, GitHub App keys, or session cookies. The controller's own alternate authentication path (`authenticate_api_client` via `params[:token]`) makes the token trivially usable from a simple GET request.

## Recommendation
Change `CCMenuController#stack` to resolve the stack through the scoped `stacks` collection (as `CommitsController`, `LocksController`, etc. do), e.g. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot fetch data for stacks outside `current_api_client.stack_id`.

## Proof of Concept
1. Create `ApiClient` A with `permissions: ['read:stack']` and `stack_id` set to Stack 1 (private staging environment).
2. Using A's token as `params[:token]`, `GET /api/stacks/:owner/:repo/:env/ccmenu.xml` (via `CCMenuController#show`) for Stack 1 — succeeds as intended.
3. Repeat the same request with `stack_id` referring to Stack 2 (a different, unrelated stack A was never granted access to).
4. Because `stack` resolves via `Stack.from_param!(params[:stack_id])` rather than the scoped `stacks` collection, and `check_permissions!` only checks the `read:stack` string, the request succeeds and returns Stack 2's latest deploy/rollback status — a stack-boundary violation the token was never authorized to cross.
