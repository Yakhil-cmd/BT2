### Title
`handleERC20Transfer` and `handleERC721Transfer` Do Not Check Token Registration or Lock Status, Allowing Bridged Asset Transfer/Mint After Token Is Deregistered or Locked — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge enforces `onlyRegisteredToken` and `onlyUnlockedToken` guards on the **outgoing** request path (`_requestERC20Transfer`, `_requestERC721Transfer`) but applies **no equivalent guards** on the **incoming** handle path (`handleERC20Transfer`, `handleERC721Transfer`). After a token is locked or deregistered on the destination bridge — the primary mechanism to halt cross-chain transfers for a specific asset — operators can still call the handle functions and cause unauthorized minting (mint/burn mode) or unauthorized transfer from bridge reserves (lock/unlock mode) of the affected bridged asset.

---

### Finding Description

`_requestERC20Transfer` enforces two modifiers before emitting a cross-chain request:

```solidity
// BridgeTransferERC20.sol lines 85-86
internal
onlyRegisteredToken(_tokenAddress)
onlyUnlockedToken(_tokenAddress)
```

`_requestERC721Transfer` enforces the same pair:

```solidity
// BridgeTransferERC721.sol lines 82-83
internal
onlyRegisteredToken(_tokenAddress)
onlyUnlockedToken(_tokenAddress)
```

The corresponding handle functions on the destination bridge carry **only** `onlyOperators`:

```solidity
// BridgeTransferERC20.sol lines 41-43
public
onlyOperators
// — no onlyRegisteredToken, no onlyUnlockedToken
```

```solidity
// BridgeTransferERC721.sol lines 40-41
public
onlyOperators
// — no onlyRegisteredToken, no onlyUnlockedToken
```

After the vote threshold is reached, `handleERC20Transfer` unconditionally executes:

```solidity
// BridgeTransferERC20.sol lines 68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
```

The Go-level bridge manager (`node/sc/bridge_manager.go`, `handleRequestValueTransferEvent`) also performs no lock/registration check before dispatching the on-chain call:

```go
// bridge_manager.go lines 338-343
case ERC20:
    handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to,
        ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
```

The `valueTransferRecovery` subsystem (`node/sc/vt_recovery.go`) additionally re-queues and re-submits any pending `RequestValueTransfer` events that were not yet handled, without checking the current lock/registration state of the token on the destination bridge. This means that even after a token is locked or deregistered, the recovery loop will continue to drive `handleERC20Transfer` calls for all outstanding nonces.

---

### Impact Explanation

**Unauthorized mint of bridged assets (mint/burn mode):** When the bridge owner locks or deregisters a token on the destination bridge to halt transfers (e.g., in response to a security incident on the source chain), operators — or the automated bridge manager — can still call `handleERC20Transfer` for any pending nonce. In mint/burn mode this calls `ERC20Mintable.mint`, inflating the token supply on the destination chain beyond what the source chain has locked, breaking the 1:1 peg invariant.

**Unauthorized transfer from bridge reserves (lock/unlock mode):** In lock/unlock mode the same call executes `IERC20.safeTransfer`, draining the destination bridge's token reserves for an asset that the owner intended to freeze.

Both outcomes constitute unauthorized transfer or mint of bridged assets — a direct match to the Kaia Allowed Impact Gate.

---

### Likelihood Explanation

The trigger requires operators (semi-trusted) to call `handleERC20Transfer`/`handleERC721Transfer`, or the automated `handleRequestValueTransferEvent` path to process a pending event. The automated path runs continuously and will process all pending nonces without any manual intervention. Any `RequestValueTransfer` event emitted before the token was locked/deregistered on the destination bridge will be replayed by the recovery subsystem. The window between a source-chain request and the destination-chain lock/deregistration is operationally realistic (e.g., emergency response to a token exploit).

---

### Recommendation

Add `onlyRegisteredToken` and `onlyUnlockedToken` modifiers to `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guards already present on the outgoing request path:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // add
    onlyUnlockedToken(_tokenAddress)     // add
{
```

Apply the same change to `handleERC721Transfer`. This ensures that locking or deregistering a token on the destination bridge immediately halts both outgoing requests and incoming handle calls for that token.

---

### Proof of Concept

1. Deploy a bridge pair in mint/burn mode with token `T` registered on both sides.
2. User calls `requestERC20Transfer` on the source bridge; a `RequestValueTransfer(T, nonce=5, value=1000)` event is emitted.
3. Before operators process nonce 5, the destination bridge owner calls `lockToken(T)` (or `deregisterToken(T)`) to halt transfers for `T`.
4. Verify: calling `_requestERC20Transfer` for `T` on the destination bridge now reverts with `"locked token"` / `"not allowed token"`.
5. An operator (or the automated bridge manager via `handleRequestValueTransferEvent`) calls `handleERC20Transfer(…, T, 1000, 5, …)` on the destination bridge.
6. The call succeeds — `onlyOperators` passes, no token-status check fires — and `ERC20Mintable(T).mint(recipient, 1000)` executes, minting 1000 tokens for an asset the owner intended to freeze.

The `valueTransferRecovery` loop will repeat step 5 for every unhandled nonce, compounding the unauthorized mint.

func (vtr *valueTransferRecovery) recoverPendingEvents() error {

	}()

	if len(vtr.childEvents) > 0 {
		logger.Warn("VT Recovery : Child -> Parent Chain", "cBridge", vtr.cBridgeInfo.address.String(), "events", len(vtr.childEvents))

	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))

		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))

		events[i] = event
	}

	return nil
}
