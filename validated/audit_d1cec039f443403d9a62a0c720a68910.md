### Title
CCMenu API endpoint lets a stack-scoped token read the CI/deploy status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by `Shipit::Api::BaseController` to bypass the token-scoping check that binds an `ApiClient`'s permission to the single `Stack` it was authorized for. This breaks the equality `stack an ApiClient token authorizes == stack the request touches`, letting an attacker holding *any* valid `read:stack` token (in particular the low-privilege, auto-generated CCMenu token) view deploy/task status for arbitrary stacks in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the intended binding between a token and the stack(s) it may touch: [1](#0-0) 

`stacks` is scoped to `current_api_client.stack_id` when the client is stack-bound, and `stack` is derived from that scoped relation (`stacks.from_param!`). Any controller that uses this `stack` helper is therefore safe: even if `params[:stack_id]` is changed to point at a different stack, `Stack.where(id: current_api_client.stack_id).from_param!(...)` will raise `RecordNotFound` because the requested stack isn't inside the scoped relation.

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely and query the full `Stack` table: [2](#0-1) 

The controller only enforces a coarse-grained permission check (`require_permission :read, :stack`), which merely verifies `current_api_client.permissions.include?('read:stack')`: [3](#0-2) [4](#0-3) 

`ApiClient.check_permissions!` never checks *which* stack the token is bound to - that check is supposed to happen via the `stacks`/`stack` scoping helper, which `CCMenuController` deliberately does not use.

This is the same class of bug as the reported `_quorumReached()` issue: a field that is supposed to gate/authorize an action (`stack_id` binding on the token, analogous to `totalVotes`) is silently substituted for an unconstrained value (`params[:stack_id]` against the full `Stack` table, analogous to summing only `against`+`abstain`), producing authorization logic that doesn't match its intended semantics.

Tokens of this kind are created automatically and distributed widely: `CCMenuUrlController#fetch` mints a `read:stack`-scoped `ApiClient` bound to one stack and returns its `authentication_token` embedded in a plain URL (no further authentication) intended for CI dashboard tools: [5](#0-4) [6](#0-5) 

Because this token is meant to be low-privilege and stack-specific (it's handed out to arbitrary CI aggregator tools, embedded in URLs which routinely leak via referrer headers, logs, bookmarks, etc.), the binding-bypass converts a narrowly-scoped, low-trust credential into a global read credential across every stack in the Shipit installation.

### Impact Explanation
Any holder of a valid `read:stack` API token (most concretely, a CCMenu token minted for one specific stack and handed to third-party tooling) can supply an arbitrary `stack_id` in the request to `Shipit::Api::CCMenuController#show` and receive that other stack's deploy state (`stack.deploys_and_rollbacks.last`, including status, timestamps, and success/failure) rendered as CCMenu XML. This is an unauthenticated (relative to the intended per-stack scope) read of stack/task state across the entire deployment fleet, matching the defined High-impact category: "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation requires only possession of any pre-existing `read:stack`-permissioned `ApiClient` token — no repository write access, GitHub App credentials, or privileged Shipit session is needed. CCMenu tokens are explicitly designed to be shared with third-party CI-status tools via a bare URL, which is a realistic leakage/distribution vector, making a would-be attacker's acquisition of at least one such token plausible in real deployments with multiple stacks.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it using the inherited `stacks` scope), so lookups go through `stacks.from_param!(params[:stack_id])` and are constrained to `current_api_client.stack_id` when the token is stack-bound, exactly as `BaseController` intends.

### Proof of Concept
1. An operator calls `GET /stacks/:stack_id/ccmenu_url` for `stack_A`, which creates (or reuses) a `read:stack`-only `ApiClient` bound to `stack_A` and returns a URL like `https://shipit.example.com/api/stacks/stack_A/ccmenu.xml?token=<token_A>` (see `CCMenuUrlController#fetch`, `app/controllers/shipit/ccmenu_url_controller.rb:7-11`). This URL is pasted into a CI dashboard tool as documented usage.
2. An attacker who obtains `token_A` (e.g. via referrer leakage/log access to the dashboard tool - no Shipit session or repo access required) sends:
   `GET /api/stacks/stack_B/ccmenu.xml?token=<token_A>`
3. `CCMenuController#authenticate_api_client` authenticates `token_A` successfully (`ApiClient.authenticate(params[:token])`, `app/controllers/shipit/api/ccmenu_controller.rb:34`).
4. `require_permission :read, :stack` passes because `token_A` does carry `read:stack`.
5. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (`app/controllers/shipit/api/ccmenu_controller.rb:30`), ignoring that `token_A.stack_id == stack_A.id`, and resolves `stack_B` instead.
6. The response renders `stack_B`'s latest deploy/rollback status, disclosing deploy state for a stack the token was never authorized to see.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
