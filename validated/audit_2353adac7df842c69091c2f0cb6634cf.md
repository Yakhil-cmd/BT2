### Title
`GitHubApp#verify_webhook_signature` returns `true` for orgs with no `webhook_secret`, allowing unsigned webhooks to mutate any repository's review stack via `repository.full_name` - ([File: app/models/shipit/github_app.rb])

### Summary
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` selects the `GitHubApp` using only `repository_owner` (derived from `params['repository']['owner']['login']` or `params['organization']['login']`), while the mutated record is looked up later using the unrelated `repository.full_name` field. Because `GitHubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as automatic success, an attacker who controls (or names) an organization with no configured `webhook_secret` can forge a `pull_request` webhook whose `repository.full_name` points at a completely different, secret-protected organization's repo, and have `PullRequest::OpenedHandler` create a `ReviewStack` for that other org's repo with zero valid signature.

### Finding Description
The broken binding: the organization whose `webhook_secret` authenticated the request bytes should equal the organization owning the repository the handler subsequently writes to. In code:

- `repository_owner` is computed purely from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) .
- `verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`, only calling `head(422)` if `verified` is falsy — it does not `return`/halt further processing when unverified, and the actual signature validity is delegated entirely to `GitHubApp#verify_webhook_signature` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` unconditionally short-circuits to `true` when the resolved app has no configured secret: `return true unless webhook_secret` [3](#0-2) , and `@webhook_secret = @config[:webhook_secret].presence` is `nil` whenever that org's config omits `webhook_secret` [4](#0-3) .
- Downstream, `PullRequest::OpenedHandler#repository` and `ReviewStackAdapter#create!` never consult `repository_owner`; they resolve strictly from `params.repository.full_name` supplied in the same attacker-controlled JSON body [5](#0-4) [6](#0-5) .

Exploit flow: attacker crafts a `pull_request` `opened` webhook body where `repository.owner.login` (or `organization.login`) is set to an org `unsecured-org` that exists in `Shipit.github_apps`/secrets but has no `webhook_secret` key, while `repository.full_name` is set to `secured-org/target-repo` (a real, stack-bearing repository belonging to a different, secret-protected org). POST to `/webhooks` with `X-Github-Event: pull_request` and any/garbage `X-Hub-Signature`. `verify_signature` resolves the `unsecured-org` app, calls `verify_webhook_signature`, which returns `true` regardless of signature content. The handler then creates a `ReviewStack` for `secured-org/target-repo`.

Existing guards fail to prevent this: `drop_unhandled_event` only checks the event type is registered, not signature validity [7](#0-6) ; there is no code anywhere that asserts `repository_owner == repository.full_name.split('/').first`; `ExplicitParameters` schema in `OpenedHandler` only validates types/shapes, not org/owner consistency [8](#0-7) .

### Impact Explanation
An unauthenticated internet requester (no Shipit session, no API token, no `webhook_secret`) can create/mutate `ReviewStack` records — and trigger downstream provisioning (`Shipit::ReviewStackProvisioningQueue.add`) — for any repository whose owning org is secured with a `webhook_secret`, as long as any other configured org has no secret set. This is a cross-tenant write: a payload nominally "from" one (unsecured) org mutates another (secured) org's stack, matching the Critical category "a payload for one repository mutating another's stack" and "authentication bypass (forged webhook ... accepted)." It is fully repeatable against any repository reachable via `Repository.from_github_repo_name(full_name)` and requires no privileged credentials.

### Likelihood Explanation
This requires: (1) the deployment's `Shipit.github_apps`/secrets configuration to include at least one organization entry lacking `webhook_secret` (multi-org GitHub App configs are an explicitly supported code path — see `github_app_config`/`TOP_LEVEL_GH_KEYS` in `lib/shipit.rb`), and (2) a target org/repo secured with a `webhook_secret`. Given that precondition, the attacker's cost is a single crafted HTTP POST with no valid credentials — trivially repeatable. The vulnerability is entirely within this engine's `verify_signature`/`GitHubApp#verify_webhook_signature` logic, not a third-party or configuration-only issue, since the "no secret = always trusted" behavior combined with owner/full_name divergence is the root cause.

### Recommendation
1. In `GitHubApp#verify_webhook_signature`, do not treat a missing secret as automatically valid; instead fail closed (return `false`) unless explicitly running in a mode designed for single-org legacy deployments, and require that mode to also bind by validating that `repository.full_name`'s owner matches the org whose secret was used.
2. In `WebhooksController#verify_signature`, `return`/halt with `head(422)` when `verified` is false instead of merely calling `head` without stopping the filter chain (verify that `head(422)` actually halts the callback chain; if not, add an explicit `return`/`throw(:abort)`).
3. Add an explicit binding check: derive the owner from `params.repository.full_name.split('/').first` and assert it equals `repository_owner` used to select the signing org before invoking handlers.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, hypothetical since `test/**` is out of scope for modification but described here for validation):
```ruby
test "pull_request webhook from org with no webhook_secret cannot create ReviewStack under a different secured org's repo" do
  # Arrange: configure two orgs
  # secured-org: webhook_secret: "supersecret"
  # unsecured-org: (no webhook_secret key)
  stack = shipit_stacks(:shipit) # belongs to secured-org/target-repo, review_stacks_enabled: true, provisioning_behavior_allow_all

  payload = {
    action: "opened",
    number: 42,
    pull_request: { id: 1, number: 42, url: "...", title: "x", state: "open",
                     additions: 1, deletions: 1,
                     head: { sha: "abc", ref: "feature" },
                     user: { login: "attacker" }, assignees: [], labels: [] },
    repository: { full_name: "secured-org/target-repo", owner: { login: "unsecured-org" } },
    sender: { login: "attacker" }
  }.to_json

  # Assert binding before: signing org ("unsecured-org", no secret) != owning org ("secured-org", has secret)
  assert_not_equal "unsecured-org", "secured-org"

  post shipit.webhooks_url,
       params: payload,
       headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => 'sha1=garbage' }

  assert_response :ok # not 422 -- signature check falsely passed

  # Assert binding after: a ReviewStack got created for secured-org/target-repo despite no valid signature
  assert Shipit::ReviewStack.exists?(environment: "pr42"), "attacker created a stack under secured org without valid signature"
end
```
This demonstrates that the equality `signing_org (unsecured-org, unauthenticated) == owning_org (secured-org, secret-protected)` is false both before and after the request, yet the write still occurs — confirming the authentication-bypass / cross-repository write.
