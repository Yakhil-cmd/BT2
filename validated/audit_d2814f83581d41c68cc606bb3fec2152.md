### Title
`StatusHandler#process` resolves commits by SHA only, letting a webhook for repository B trigger `stack.schedule_merges` on an unrelated repository A's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Commit#add_status` itself correctly calls `stack.schedule_merges` on `self.stack`, the association fixed at the `Commit` row's creation, so no confusion happens inside that method. The break is one layer up: `StatusHandler#process` selects *which* `Commit` rows to feed into `add_status` using `Commit.where(sha: params.sha)`, with no filter tying the lookup to the repository that the inbound webhook was authenticated for.

### Finding Description
The claimed binding, stated as an equality, is:

`webhook.authenticated_repository == commit.stack.repository` for every `Commit` row mutated by that webhook.

Trace:
- `WebhooksController#verify_signature` authenticates the payload only at the GitHub *organization/owner-login* granularity: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login')`. [1](#0-0) [2](#0-1) 
- This proves "this event came from the app installation for org X," it does **not** bind the payload to one specific repository/stack.
- `StatusHandler#process` then resolves target commits purely by SHA, with zero repository/stack scoping: [3](#0-2) 
- Each matched `Commit` gets `create_status_from_github!` → `add_status`, and `add_status` runs `stack.schedule_merges if new_status.pending? || new_status.success?` using that commit's own (correct) `stack` association: [4](#0-3) 

Because Git SHAs are content-addressed and preserved verbatim across forks/mirrors/cherry-picks, the same SHA can legitimately exist as separate `Commit` rows under two different `Stack`s (different repositories, potentially different tenants/orgs). An attacker who legitimately controls repository B (its own repo, fork, or a repo they administer, onboarded to this Shipit instance so the org-level signature check for B passes) can post a real, validly-signed `status` event for a SHA that is shared with a commit tracked by a *different* stack A. `Commit.where(sha: params.sha)` will match A's `Commit` row too and run `add_status` → `stack.schedule_merges` against stack A, even though A's owning repository never authenticated this event.

None of the existing guards close this gap: `verify_signature`/`drop_unhandled_event` authenticate the org, not the specific repo/stack; the `ExplicitParameters` schema for `StatusHandler` only validates types (`sha`, `state`, etc.), not repository identity; there is no `subset`/repository-membership check anywhere in `StatusHandler#process` binding the found `Commit` to `params['repository']`.

### Impact Explanation
A webhook that authenticates for repository/organization B can cause a write (`Status` record creation) and a side effect (`stack.schedule_merges`, i.e., forcing merge-queue evaluation) against Stack A, a repository/tenant that never authenticated or authorized the request. This is a "payload for one repository mutating another's stack" - matching the Critical category. It is repeatable against any pair of stacks that happen to share a tracked commit SHA (most realistically forks/mirrors of the same upstream history), and requires no privileged Shipit credentials, only ordinary control of a repository that is itself connected to the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) the attacker's repository B must be a legitimate, onboarded tenant of this Shipit instance so that `verify_signature` for B's organization passes (attacker needs no secret - GitHub computes and sends the valid signature for genuine events on B); (2) a SHA collision must exist between a commit in B and a `Commit` row already present under stack A's `commits` table - realistic when A and B are related via fork/mirror/shared history, less so for wholly unrelated repositories. Given those conditions, the attack is cheap and fully repeatable: any status webhook on repo B naming a shared SHA fires the cross-tenant `schedule_merges` call.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the authenticated repository, not by SHA alone, e.g. join through `stack.repository` and filter by `params.dig('repository','full_name')` (or repository id) before calling `create_status_from_github!`, so only commits whose owning stack's repository matches the webhook's authenticated repository are mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for repository B does not schedule_merges for an unrelated stack A sharing the same commit sha" do
  stack_a = shipit_stacks(:shipit)                       # tenant A
  commit_a = stack_a.commits.create!(sha: "deadbeef" * 5, ...)

  stack_b = shipit_stacks(:cyclimse)                     # tenant B, attacker-controlled
  commit_b = stack_b.commits.create!(sha: commit_a.sha, ...) # shared sha via fork/mirror

  payload = { "sha" => commit_a.sha, "state" => "success", "context" => "ci",
              "repository" => { "full_name" => stack_b.repo_name, "owner" => { "login" => stack_b.repo_owner } } }

  Shipit::Stack.any_instance.expects(:schedule_merges).never  # binding under test: stack_a.schedule_merges should NOT fire
  # exercise the handler exactly as WebhooksController does
  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)
end
```
Currently `Commit.where(sha: params.sha)` matches both `commit_a` and `commit_b`, so `stack_a.schedule_merges` (and `stack_b.schedule_merges`) both fire, violating the binding `webhook.authenticated_repository (B) == commit.stack.repository (A)`. After the fix (filtering commits by the payload's repository), only `stack_b.schedule_merges` should be enqueued.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end

      end
