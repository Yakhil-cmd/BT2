### Title
`review_stacks_enabled` fails to gate `prevent_with_label` provisioning due to operator-precedence bug in `provision?` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` (and the structurally identical `ReopenedHandler#unarchive?`) intends `review_stacks_enabled` to gate all three provisioning behaviors, but Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to only gate the `allow_all` branch. For repositories configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`, any pull request lacking the provisioning label still causes ReviewStack creation and provisioning.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false` implies `provision? == false` for every value of `provisioning_behavior`. The actual code in `provision?` is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||` in Ruby, this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The last two disjuncts have no dependency on `review_stacks_enabled` at all. Thus for a repository with `provisioning_behavior_prevent_with_label? == true` and `review_stacks_enabled == false` (the post-migration default per `db/migrate/20201001125502_add_provision_pr_stacks_flag_to_repositories.rb`, which sets `review_stacks_enabled` default `false`), `provision?` evaluates to `true` whenever the incoming pull request lacks the configured label — which is the default state for any PR since `pull_request_has_provisioning_label?` is false unless the attacker explicitly applies the label.

Path: GitHub sends a legitimate, signature-verified `pull_request` "opened" webhook (no forgery needed) → `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` returns `true` → `ReviewStackAdapter#find_or_create!` creates a `Shipit::ReviewStack` and queues provisioning. [2](#0-1) 

The identical precedence bug exists in `ReopenedHandler#unarchive?`, allowing an attacker to resurrect archived stacks on reopen for the same misconfiguration. [3](#0-2) 

Existing guards do not prevent this: webhook signature verification only authenticates that the payload truly came from GitHub for that repository — it does nothing to enforce the `review_stacks_enabled` business rule, and no model validation ties `provisioning_behavior` to `review_stacks_enabled` (the settings form and `update_params` permit them as independent, uncoupled fields). [4](#0-3) 

### Impact Explanation
An external, unprivileged GitHub user who can open a pull request against a repository misconfigured this way causes Shipit to create a `Shipit::ReviewStack` and enqueue it for provisioning — infrastructure and command execution (via the provisioning task machinery) that the repository owner explicitly opted out of by leaving `review_stacks_enabled` false. This is repeatable per PR/per repository for any Shipit-managed repository whose operator has ever set `provisioning_behavior` to `prevent_with_label` without separately enabling `review_stacks_enabled` (a plausible and easy misconfiguration given the two settings are independent checkboxes/selects on the same form). This matches "unauthorized ReviewStack creation and command execution" / "a record written for a repository that did not authenticate it" — an unauthorized provisioning action performed on behalf of a repository whose owner disabled review-stack provisioning.

### Likelihood Explanation
Preconditions: a repository operator must have set `provisioning_behavior` to `prevent_with_label` while `review_stacks_enabled` remains false/unset (the DB default). No attacker secrets, tokens, or privileged roles are required — the attacker only needs the ability to open a pull request against the target repository (or one that forks/targets it), which is the baseline capability assumed for any public repository accepting PRs. Given the settings UI allows configuring `provisioning_behavior` and `review_stacks_enabled` independently, this misconfiguration is plausible in real deployments, though it does require this specific configuration combination rather than being universally exploitable against every repository regardless of settings.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all branches, e.g.:

```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Apply the same fix to `ReopenedHandler#unarchive?`, and audit `LabeledHandler`/`UnlabeledHandler` (which already explicitly AND `review_stacks_enabled` into `respond_to_label_change?` as a separate top-level condition, so they are not affected by this precedence issue) for consistency.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_precedence_test.rb
require "test_helper"

module Shipit
  module Webhooks
    module Handlers
      module PullRequest
        class OpenedHandlerPrecedenceTest < ActiveSupport::TestCase
          Shipit::Repository::PROVISIONING_BEHAVIORS.each do |behavior|
            test "review_stacks_enabled=false must block provisioning for #{behavior}" do
              repository = shipit_repositories(:shipit)
              repository.update!(
                review_stacks_enabled: false,
                provisioning_behavior: behavior,
                provisioning_label_name: "pull-requests-label",
              )
              payload = payload_parsed(:pull_request_opened)
              payload["pull_request"]["labels"] = [] # no label present

              assert_no_difference -> { Shipit::Stack.count },
                "provisioning_behavior=#{behavior} with review_stacks_enabled=false must not provision" do
                OpenedHandler.new(payload).process
              end
            end
          end
        end
      end
    end
  end
end
```

Expected (correct) behavior: `Stack.count` unchanged for all three behaviors, since `repository.review_stacks_enabled == false`. Actual (buggy) behavior: the `prevent_with_label` case fails the assertion — `Stack.count` increases because `provision?` returns `true` via `(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`, independent of `review_stacks_enabled`.
