## Title
Webhook signature is verified using an attacker-controlled organization field that is disjoint from the repository/commit actually mutated by the handler, enabling cross-repository forged webhook writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a delivery against using a field taken straight from the **unverified** JSON body (`repository.owner.login` or `organization.login`), then hands the same unverified body to handlers that key off a *different* field (`repository.full_name` or, in `StatusHandler`, no repository field at all) to decide what to mutate. Nothing binds "the organization whose secret authenticated this request" to "the repository/commit this request is allowed to touch."

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the raw, not-yet-verified payload and uses it to pick which org's secret authenticates the HMAC: [1](#0-0) [2](#0-1) 

`Shipit.github` resolves a distinct `GitHubApp`/secret per organization in the multi-org config schema: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only checks that the raw body's HMAC matches the secret for the organization named in `repository_owner`: [4](#0-3) 

Once verified, the *same* raw body is parsed and dispatched to handlers, all of which resolve the target `Repository`/`Stack` from a separate, independently attacker-controlled field, `repository.full_name`: [5](#0-4) [6](#0-5) 

Critically, `StatusHandler` doesn't even scope by repository — it queries `Commit.where(sha: params.sha)` across the entire installation and writes a CI status onto whatever commit matches that SHA, anywhere in Shipit: [7](#0-6) 

Nothing in `verify_signature` or in the handlers enforces that `repository.owner.login` (the field that selected the authenticating secret) matches `repository.full_name`'s owner segment or the organization that actually owns the affected commit/stack. An attacker who legitimately administers **any one** organization configured in this multi-org Shipit instance (an "unprivileged attacker" relative to any other tenant's repositories) knows that organization's `webhook_secret` (it is a value the org owner sets when wiring up their GitHub App, per `config/secrets.development.example.yml`'s multi-org schema documenting per-org `webhook_secret`). That attacker can:

1. Set `repository.owner.login` = their own org (`attacker-org`) so `verify_signature` selects `attacker-org`'s secret.
2. Sign the full raw JSON body with that known secret.
3. Populate all other fields (`sha`, `state`, `ref`, `after`, `repository.full_name`, `check_suite.head_sha`, etc.) referencing a victim's commit/stack.

The signature check passes because it never inspects or binds the fields the handlers act on. This breaks the equality the engine implicitly relies on: `organization-that-authenticated == repository/commit-that-is-written`. Before the attack, an organization's secret can only affect that organization's own repositories (assumed invariant); after, `StatusHandler`/`PushHandler`/`CheckSuiteHandler` act on any commit/repository named in the unverified fields, regardless of which org's secret signed the request.

### Impact Explanation
This is a cross-repository/cross-organization write: an operator of one onboarded organization can forge webhook deliveries that mutate CI status, trigger `Stack#sync_github` resyncs, or schedule check-run refreshes for **another organization's stacks**, without ever having credentials, GitHub App access, or write permission to that other repository. Falsifying a commit's CI status (`StatusHandler`) is a direct manipulation of state Shipit uses to gate stack behavior for repositories the attacker has no legitimate access to, satisfying the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Requires the deployment to use Shipit's documented multi-organization GitHub configuration (`github: { org1: {...}, org2: {...} }`, as shown in `config/secrets.development.example.yml`) and for the attacker to control at least one legitimately onboarded organization/repository (something a normal, unprivileged tenant of a shared Shipit instance would have). No repository write access, Shipit session, or `ApiClient` token to the *victim* org is needed — only knowledge of the attacker's own org's webhook secret, which they set themselves.

### Recommendation
Bind signature verification to the actual repository being mutated, not a separately-trusted "owner" field: after selecting a candidate `GitHubApp` and verifying the HMAC, re-derive/validate that `repository.full_name`'s owner segment (and, for `StatusHandler`, the resolved commit's stack's owning organization) matches the organization whose secret validated the signature, rejecting the payload otherwise. Additionally, scope `StatusHandler`'s commit lookup to stacks belonging to the verified organization rather than a global `Commit.where(sha:)` query.

### Proof of Concept
Conceptual (no test harness/tool access available for this exercise — described from code paths):
1. Configure multi-org Shipit with `github: { "attacker-org": {webhook_secret: "s1", ...}, "victim-org": {webhook_secret: "s2", ...} }`.
2. Attacker knows `s1` (their own org's secret).
3. Attacker crafts JSON body:
```json
{
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sha": "<victim-pending-commit-sha>",
  "state": "success"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(s1, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC matches — request is accepted.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged `success` status onto the victim's commit, entirely independent of `repository.full_name` or `repository.owner.login`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
