Confirmed: Shipit supports multi-organization GitHub App configs, each with independent `webhook_secret` values selected at runtime via `Shipit.github(organization:)`, keyed off attacker-controlled payload fields [1](#0-0) .

### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the write target is selected from the independent, unverified `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to check the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body, before the signature itself has been verified [2](#0-1) . Once the signature check passes, `create` dispatches the *same* raw payload to every registered handler [3](#0-2) , and every handler resolves the target `Stack`/`Repository` using a *different* field of the same payload: `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name` [4](#0-3) [5](#0-4) . Nothing enforces that `repository.owner.login` (used for authentication/secret selection) and the owner-prefix embedded in `repository.full_name` (used for the actual write target) refer to the same organization. This is exactly the "organization that authenticated versus the repository that is written" trust-binding class called out in scope.

### Finding Description
Shipit's multi-tenant GitHub App configuration lets each organization have its own `webhook_secret`, looked up per-request by `Shipit.github(organization: repository_owner)` [6](#0-5) . The `repository_owner` used for that lookup is taken verbatim from the JSON body:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

`verify_webhook_signature` then HMACs the *entire raw body* with that organization's secret and compares it to `X-Hub-Signature` [8](#0-7) . Once that check succeeds, `create` re-parses the body and hands it to every handler registered for the event type [3](#0-2) . Handlers never re-check `repository.owner.login`; instead they resolve the target repository/stack from `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`Repository.from_github_repo_name` simply splits that string on `/` and looks up any repository row by `owner`/`name` [5](#0-4) , with no comparison back to `repository.owner.login`. Because `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled strings inside a single JSON body, an attacker who legitimately controls the webhook installation (and therefore knows the `webhook_secret`) for one onboarded organization, `orgA`, can craft a payload where `repository.owner.login = "orgA"` (so the correct `orgA` secret is used and the HMAC verifies) while `repository.full_name = "orgB/target-repo"` for a different, unrelated organization/repository also onboarded to the same Shipit instance. The signature check passes using `orgA`'s secret, but the handler logic (push syncs, status updates, PR label/merge handling, review-stack archiving, etc.) acts on `orgB/target-repo`. Downstream, e.g. `GithubSyncJob` and the various `pull_request` handlers, `stack.archive!`/`unarchive!`, merge/label/pull_request status writers, all operate on the `orgB` stack found via `full_name`, i.e., a cross-organization write driven entirely by `orgA`'s credentials [9](#0-8) [10](#0-9) .

The broken equality is:
`organization authenticated (repository.owner.login, HMAC-checked)` ≠ `repository actually written (repository.full_name, unchecked)`.

Before the attacker's request: `orgA`'s webhook secret authorizes only writes to `orgA`'s own stacks (implicit assumption). After the crafted request: `orgA`'s webhook secret is used to push job enqueues, status writes, label/archive actions, and merge-status updates onto any other organization's stack hosted on the same Shipit instance, as long as that other repository/stack row exists in Shipit's database.

### Impact Explanation
This crosses the "cross-repository writes" bar explicitly listed as Critical impact. A tenant/organization with legitimate but narrow webhook access to Shipit can use its own valid signature to trigger `GithubSyncJob` runs, PR label-driven stack archive/unarchive, merge-status writes, and check-run refreshes against a completely different organization's repository/stack that they have no authorization over, purely by manipulating the `repository.full_name` field independently of `repository.owner.login`.

### Likelihood Explanation
Moderate-to-high in any multi-organization Shipit deployment: any org already onboarded with a webhook and its own `webhook_secret` can exploit this without needing any other org's secret, GitHub App private key, or session — it only needs its own legitimately-configured webhook credentials, which it inherently possesses. No additional privilege escalation is required beyond what the org already has for its own repositories.

### Recommendation
After signature verification succeeds, re-derive the expected repository owner and require it to equal `repository_owner` used for the authentication lookup (or equivalently, verify the signature using the organization implied by `repository.full_name`, not `repository.owner.login`/`organization.login`), rejecting the request (422) on mismatch before dispatching to any handler.

### Proof of Concept
1. Attacker administers `orgA`'s GitHub App installation on this shared Shipit instance and therefore knows `orgA`'s configured `webhook_secret`.
2. Attacker crafts a `pull_request` (or `push`/`status`) JSON payload where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"` (a stack belonging to a different tenant on the same instance).
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_secret, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and the HMAC check passes [11](#0-10) .
5. `create` dispatches to the matching handler(s), which resolve the target stack via `payload.dig('repository','full_name')` = `"orgB/victim-repo"` [12](#0-11) , causing writes (e.g., label-triggered `stack.archive!`) on `orgB`'s stack using only `orgA`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
