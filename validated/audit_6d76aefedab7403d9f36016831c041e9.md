### Title
Webhook signature is verified against the payload's `repository.owner` while the write action targets the payload's `repository.full_name` — allowing cross-tenant event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature with by reading `repository.owner.login` (or `organization.login`) out of the *same untrusted, attacker-controlled JSON body* it is trying to authenticate. Every downstream `Shipit::Webhooks::Handlers::Handler` subclass (e.g. `PushHandler`) then looks up the `Stack`/`Repository` to write to using a **different** field of that same payload: `repository.full_name`. Because the field used to pick the verification key and the field used to pick the target repository are independent and both attacker-supplied, a signature computed with organization A's `webhook_secret` can be replayed with a payload whose `repository.full_name` names organization B's repository, causing Shipit to sync commits/push status into org B's stacks using a signature that was never verified against org B's secret.

### Finding Description
The verification step is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/`webhook_secret` configured for that organization (see the multi-org config shape in `config/secrets.development.shopify.yml`, where each org has its own independent `webhook_secret`). The HMAC is verified only against *that* org's secret: [3](#0-2) 

Once `head(422)` is not triggered, `WebhooksController#create` dispatches the **entire raw payload** — including whichever `repository.full_name` the attacker chose — to every matching handler: [4](#0-3) 

Handlers resolve the repository/stack to act on independently, via `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`PushHandler` then finds every non-archived stack for that repository/branch and calls `sync_github`, i.e. performs a write: [6](#0-5) 

`Repository.from_github_repo_name` performs no cross-check that `owner` in `full_name` equals `repository.owner.login`: [7](#0-6) 

**Binding broken:** `organization authenticated (repository.owner.login, checked against org-specific webhook_secret) == repository written (repository.full_name, used to resolve Stack/Repository for sync_github)`. Nothing in the controller or in `Handler#repository_name` enforces this equality — the two fields are read independently from the same untrusted payload, and only one of them is covered by the signature check's *organization selection logic* (the signature itself covers the raw body bytes, but the choice of *which secret* to check it against is itself attacker-influenced).

### Impact Explanation
In a Shipit deployment onboarding multiple GitHub organizations (each with its own GitHub App / `webhook_secret`, as the config format explicitly supports), a party who legitimately controls the webhook configuration for organization A (i.e., knows/can trigger valid webhook deliveries signed with A's secret — which is normal for anyone who can push commits/set commit statuses on A's own repos) can craft a JSON body where `repository.owner.login = "orgA"` (so verification succeeds against A's secret) but `repository.full_name = "orgB/some-repo"`. This is accepted and dispatched to handlers, causing writes (e.g. `Stack#sync_github`, `Commit`/`Status` creation) against organization B's stacks — a cross-repository/cross-tenant write the attacker was never authorized to perform. This matches the report's root-cause class (a value used for an authorization/trust decision differing from the value the operation actually acts on), applied here as an authentication-organization vs. write-target repository mismatch, and lands in the "cross-repository writes" Critical impact bucket.

### Likelihood Explanation
Likelihood depends entirely on Shipit being configured to serve **multiple** GitHub organizations from one instance (explicitly supported per the `config/secrets.*.yml` format showing a hash of orgs each with independent `webhook_secret`/app credentials). In such a deployment, exploitation requires no privileged Shipit account, no `ApiClient` token, and no compromise of the victim org's secret — only the ability to generate a normal, validly-signed webhook delivery from the attacker's own organization (which any GitHub org admin naturally has for their own org's webhooks) with a forged `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after), assert that the organization used to select the verification key equals the owner encoded in `repository.full_name` before dispatching to handlers, and/or have `Handler#repository_name` cross-check `payload.dig('repository','owner','login')` against `payload.dig('repository','full_name').split('/').first` and reject on mismatch. Ideally, resolve the target repository via a value bound to the verification decision itself, not a second independent field of the same untrusted payload.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As someone who can generate a legitimately GitHub-signed webhook for `orgA` (e.g., an admin of `orgA`'s GitHub App/webhook), build a `push` event payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Sign the raw JSON with `orgA`'s `webhook_secret` and send it to `POST /webhooks` with header `X-Github-Event: push` and the matching `X-Hub-Signature`.
4. `verify_signature` computes `repository_owner = "orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature verifies successfully.
5. `PushHandler#process` resolves `stacks` via `payload.dig('repository','full_name')` = `"orgB/victim-repo"` and calls `sync_github` on `orgB`'s stack — a write performed on organization B using a signature validated solely against organization A's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
