## Analysis

The external report's bug class is: **a value is validated/gated under one condition but the code path that actually matters doesn't enforce that same binding** — i.e., the "checked" scope and the "acted-upon" scope diverge.

The strongest analog in this engine is in the webhook pipeline: signature verification is bound to the **organization** derived from the payload, but the actual event handler for `status` events writes to **any commit** matching a SHA, with **no scoping to the repository or organization that was authenticated**.

### Root cause
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify the signature against using `repository_owner`, which is read straight out of the (as yet unverified) JSON body: [1](#0-0) [2](#0-1) 

Once the signature for that organization checks out, `create` dispatches the full payload to the registered handler for the event type: [3](#0-2) 

For `status` events, `StatusHandler#process` never re-checks `repository`/organization — it looks up commits **globally by SHA only**, across every stack/repository tracked by the Shipit instance: [4](#0-3) 

Compare this to the base `Handler` class, which does define a `repository_name`/`stacks` scoping helper, but `StatusHandler` doesn't use it: [5](#0-4) 

`create_status_from_github!` then creates a `Status` row and, critically, can flip a commit's deployability and trigger the merge queue: [6](#0-5) [7](#0-6) 

### The broken binding
`organization authenticated (via webhook_secret keyed on repository_owner)` ≠ `repository/commit actually mutated (any Commit row with a matching sha, in any Stack, in any org)`.

Because GitHub App `webhook_secret`s are shared across **every repository the app is installed on for that organization**, and because git commit SHAs are content-addressed and identical across forks/mirrors of the same history, a party who can trigger a legitimately-signed `status` webhook for *one* repository under a configured organization (e.g. they only have commit-status-write access on a low-value repo — a very common CI/Action permission, far short of "repository write access" to the victim stack) can forge a `Status` for a commit SHA belonging to a *different*, unrelated stack/repository tracked by the same Shipit instance, as long as that SHA happens to also exist there (forks, mirrored history, template repos, monorepo splits, etc. all commonly share identical SHAs). This can flip a target commit to `success`, and `add_status` will call `stack.schedule_merges`, potentially causing the merge queue to merge/deploy a commit whose real CI status was never actually verified for that stack — an unauthorized merge/deploy.

### Title
Cross-repository/organization commit-status forgery via unscoped SHA lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController` authenticates incoming GitHub webhooks per-organization via `verify_webhook_signature`, using the organization derived from the payload's `repository.owner.login`. However, `Shipit::Webhooks::Handlers::StatusHandler#process` ignores the `repository` field entirely and updates `Commit` records solely by matching `sha` across the whole database, with no scoping to the stack/repository/organization that the signature verification was actually performed against.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to validate against based on `repository_owner`, computed from the unverified JSON body: [1](#0-0)  and [2](#0-1) .

This only proves the request was validly signed *for that organization's app installation* — it says nothing about which specific repository within that organization (or which Stack in the Shipit database) the event should be allowed to affect. `StatusHandler#process`, however, performs no such check:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [8](#0-7) 

This is in contrast to other handlers (e.g. `PullRequest::OpenedHandler`, `PullRequest::ClosedHandler`) which explicitly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting: [9](#0-8) . `StatusHandler` skips this entirely, so any `Commit` row anywhere in the database sharing the given SHA is mutated, regardless of which repository/stack it belongs to.

### Impact Explanation
Creating a forged `Status` can drive `Commit#add_status`, which calls `stack.schedule_merges` when the new status is `pending` or `success`: [10](#0-9) . If the affected commit belongs to a stack with `allows_merges?`/deployability gated on `merge_status`/`deployable?` (which depend on commit statuses), an attacker can cause the merge queue to treat an unrelated stack's commit as CI-green and merge/deploy it — a cross-repository/organization write and an unauthorized merge/deploy, without ever needing write access to the affected stack's actual repository, only the ability to trigger a validly-signed `status` webhook for some other repository sharing the target SHA under the same GitHub App installation.

### Likelihood Explanation
Exploitability depends on: (1) being able to generate a legitimately-signed `status` webhook for *some* repository under an org configured in Shipit — a low bar, since commit-status-write access is commonly granted to CI integrations/Actions on individual repos, far short of admin/write access to the victim repository; and (2) the forged SHA existing in another tracked stack — realistic in fork-based workflows, mirrored/template repositories, or monorepo splits where identical commit objects are shared across multiple tracked repositories. This is a moderate-likelihood, high-impact gap because the code performs zero repository-level authorization check at the point of mutation, relying entirely on an organization-level signature check that doesn't bind to the specific repository being written.

### Recommendation
In `StatusHandler#process` (and any other handler relying purely on cross-cutting identifiers like SHA), scope the lookup to the repository named in the payload, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` using the `Handler#stacks`/`repository_name` helpers already defined in the base class, ensuring the organization verified by the signature check is the same one whose repository/stack is being mutated.

### Proof of Concept
1. Obtain (or have) commit-status-write access to `org/side-repo`, a repository under an organization configured in Shipit with a real `webhook_secret` (e.g. via an installed CI integration/Action — no elevated Shipit privileges needed).
2. Identify a commit SHA `S` that exists both in `org/side-repo` and in `org/victim-repo` (a stack tracked by Shipit) — trivially true if `side-repo` is a fork/mirror/template-derived copy of `victim-repo`.
3. POST a commit status for SHA `S` with `state: "success"` to GitHub's Statuses API on `org/side-repo`. GitHub delivers a `status` webhook to Shipit, signed with `org`'s real `webhook_secret`.
4. `WebhooksController#verify_signature` passes (correct org, correct secret). `StatusHandler#process` runs `Commit.where(sha: S)`, which matches the commit in `org/victim-repo`'s stack too, and creates a forged `success` `Status` there — even though the request never referenced `victim-repo`.
5. If this transitions `victim-repo`'s commit to a passing/deployable state, `stack.schedule_merges` fires and the merge/deploy queue can act on a commit that was never actually validated by `victim-repo`'s own CI.
