Confirmed: `is_blackhole` is never read in any query — it's only written (in `device.js` and `wallet.js`), never checked to gate message acceptance.

### Title
Blackholed/unpaired correspondent device is never rejected when delivering messages - (File: device.js / wallet.js)

### Summary
When `conf.bIgnoreUnpairRequests` is set, an unpair (`removed_paired_device`) request does not delete the correspondent; instead the correspondent row is only flagged `is_blackhole=1` in `correspondent_devices`, intending to silently drop future messages from that device. However, the flag is never queried anywhere in the message-acceptance path, so it has no actual effect: a device that a user believes is "locked out" continues to be treated as a fully trusted correspondent, exactly analogous to CVE-2022-22967 where locked accounts were not actually rejected.

### Finding Description
The unpair handler in `wallet.js` (`case "removed_paired_device"`) checks `determineIfDeviceCanBeRemoved`, and when `conf.bIgnoreUnpairRequests` is true it does: [1](#0-0) 
```
db.query("UPDATE correspondent_devices SET is_blackhole=1 WHERE device_address=?", [from_address]);
return callbacks.ifOk();
```
instead of calling `device.removeCorrespondentDevice`. The intent is clearly to keep the correspondent record but silently blackhole further traffic from it.

However, the inbound message path in `device.js`, `handleJustsaying`, case `'hub/message'`, only checks whether the sender is *known* at all, not whether it has been blackholed: [2](#0-1) 
```
db.query("SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?", [from_address], function(rows){
    if (rows.length > 0){
        ...
        handleMessage(rows[0].is_indirect);
    }
    else{ ... }
});
```
`is_blackhole` is not selected, not checked, and `handleMessage` proceeds unconditionally for any row found — including blackholed ones — routing the message to `handle_message_from_hub` (`wallet.js`'s `handleMessageFromHub`), which processes `sign`, `pairing`, `text`, `object`, `new_wallet_address`, arbiter/prosaic-contract, private-payment, and other messages exactly as if the sender were a normal trusted correspondent.

Additionally, `handlePairingMessage` in `device.js` unconditionally clears the flag on any subsequent pairing attempt from the same device address: [3](#0-2) 
```
db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
```
This further reinforces that the flag was intended as an enforcement gate but is never consulted before message processing — a global grep across the repo confirms `is_blackhole` appears only in the two `UPDATE` statements above and in schema files; it is never present in a `SELECT`/`WHERE` used to gate behavior.

### Impact Explanation
Any peer/correspondent that a user has explicitly revoked (via unpair, with `bIgnoreUnpairRequests` enabled to avoid immediate full deletion/race issues) retains full trusted-correspondent privileges: it can send `sign` requests that get auto-signed/relayed for shared multisig addresses, deliver `payment` notifications, private payment chains, and other wallet/contract messages that are processed as coming from a legitimate paired counterparty. Since `wallet.js`'s `"sign"` handler and related flows trust `from_address` derived from `correspondent_devices` membership to authorize actions like requesting a peer's signature on a shared/multisig unit, an attacker whose device was supposed to be locked out can continue to participate in AA trigger construction, private-payment protocol steps, or shared-address signing flows, potentially leading to unauthorized spending or fund loss from a shared/multisig wallet whose intended correspondent revocation silently failed.

### Likelihood Explanation
This is directly reachable by any device that was previously paired and later "unpaired" while `bIgnoreUnpairRequests` is enabled (a supported, documented configuration option, not requiring any special privilege) — no cryptographic break or privileged access is needed; the blackholed device simply continues sending ordinary `hub/message` traffic it was always capable of sending, and the receiving node has no code path enforcing the intended block.

### Recommendation
In `device.js`, `handleJustsaying`'s `'hub/message'` handler, select `is_blackhole` alongside `hub, is_indirect` and reject (or silently drop, matching the original least-surprise intent) any message from a device where `is_blackhole=1`, before invoking `handleMessage`. Also review whether `handlePairingMessage` should be allowed to silently clear `is_blackhole` without explicit user re-approval.

### Proof of Concept
1. Pair device B with device A; B becomes a row in `correspondent_devices` on A.
2. A sets `conf.bIgnoreUnpairRequests = true`.
3. B sends `removed_paired_device` to A. A's `wallet.js` handler sets `is_blackhole=1` for B's row rather than deleting it, and responds `ifOk`.
4. B is still installed/known on the hub, and continues to send `hub/message` traffic to A (e.g., a `sign` request or `payment`/`text` justsaying).
5. In `device.js`, `handleJustsaying`, case `'hub/message'`, the `SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?` query returns B's row (`rows.length>0`); `is_blackhole` is not checked, so `handleMessage(rows[0].is_indirect)` is invoked, and the message is fully processed by `wallet.js`'s `handleMessageFromHub`, exactly as before the "unpair."
