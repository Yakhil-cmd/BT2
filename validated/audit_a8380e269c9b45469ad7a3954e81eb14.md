### Title
Overly-Broad Vulnerability-Finding Dedup Key Permanently Suppresses New Distinct Findings - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The Sherlock report describes a Solidity bug where a state check (`require(claim.amount == 0)`) is keyed too coarsely — on a global "has this user claimed" flag rather than per-epoch — so a single successful claim permanently blocks the user from claiming any future, legitimately distinct epoch. The `security-guidance` plugin's commit/push review pipeline in this repository has the same class of defect: its "already reported" dedup state is keyed on `(filePath, category)` rather than on the specific vulnerable code/finding, so once one vulnerability of a given category is reported for a file, any subsequent, genuinely different vulnerability of the same category in that same file is silently and permanently treated as "already known" and never surfaces to the user again.

### Finding Description
`handle_commit_review_posttooluse` and `handle_push_sweep_posttooluse` record findings into shared session state via closures that build the DB key from only two fields:

```python
def _record_findings(state):
    existing = [f for f in state.get("previous_findings", []) if isinstance(f, dict)]
    seen = {(f.get("filePath", ""), f.get("category", "")) for f in existing}
    for f in finding_snapshots:
        key = (f["filePath"], f["category"])
        if key not in seen:
            seen.add(key)
            existing.append(f)
    state["previous_findings"] = existing
``` [1](#0-0) 

The same `(filePath, category)` key pattern is used in the push-sweep path: [2](#0-1) 

The comment explaining the dedup rationale states the key was deliberately chosen to be coarser than the vulnerable code itself, because that code text "drifts" between fires: [3](#0-2) 

These `previous_findings` entries are later consumed by `_dedup_against_state`/`_finding_keys` (defined in `plugins/security-guidance/hooks/llm.py`) to filter out "already known" findings before anything is shown to the user or forces a Stop-hook re-prompt. I was not able to fully inspect the body of `_dedup_against_state`/`_finding_keys` within the remaining tool budget, so I cannot confirm with certainty whether it re-derives a finer-grained key elsewhere — but every call site that populates `previous_findings` uses only `(filePath, category)`, and this is the exact same "once marked resolved for a coarse identity, blocked forever" pattern as the Sherlock root cause (`claim.amount == 0` keyed globally per user+token instead of per-epoch).

Practically: this hook is the only automated safety net that reviews `git commit`/`git push` diffs for injected or Claude-introduced vulnerabilities before code leaves the local workspace. If Claude (or an attacker steering Claude via prompt injection) introduces one vulnerability of category `"Injection"` in `foo.py` that gets flagged and recorded, then in a later commit introduces a second, unrelated `"Injection"` vulnerability in the same `foo.py` (different line, different bug), the second one is silently classified as "already known" and dropped — never surfaced via `sys.exit(2)`/stderr guidance, never counted in `vulns_found` for the user-visible summary.

### Impact Explanation
This degrades a security control (the "security-guidance" commit/push reviewer) rather than a financial reward system, but the mechanism and consequence are analogous: legitimate, distinct triggers ("new epoch to claim" vs. "new vulnerability instance") are permanently suppressed by an overbroad "already handled" check. The concrete impact here is that a genuinely new, unrelated vulnerability in a previously-flagged file/category is never shown to the user, allowing insecure code to be committed and pushed without the intended review-and-fix loop firing, which is exactly the kind of "unauthorized action reaches the repo without the approval/review gate" outcome the report's rules are checking for (secret/code disclosure & git-automation trust boundary).

### Likelihood Explanation
Likelihood is moderate: it requires (a) an initial finding of some category in a file that gets recorded, and (b) a later, different vulnerability of the same category appearing in the same file across a subsequent commit/push in the same session — a realistic scenario in iterative Claude Code sessions where the same file is repeatedly touched and where categories are broad buckets (e.g., "Injection", "Secrets", "Auth"). No privilege escalation or malicious node/peer is required — an ordinary user or an indirect-prompt-injection-influenced Claude editing the same file repeatedly is sufficient to reach this path.

### Recommendation
Key `previous_findings` (and the corresponding lookup in `_dedup_against_state`/`_finding_keys`) on a value that identifies the specific finding instance rather than just `(filePath, category)` — e.g., include a normalized/fuzzy hash of the vulnerable code snippet's surrounding context (tolerant to line-shift noise) or a stable finding fingerprint (rule id + normalized code span), so a second, distinct vulnerability of the same category in the same file is not conflated with the first and continues to be reported.

### Proof of Concept
Conceptual reproduction (cannot be executed here, but follows directly from the cited code):
1. In session S, edit `foo.py` introducing vulnerability A (category `"Injection"`) and run `git commit`. `handle_commit_review_posttooluse` flags it; `_record_findings` stores `("foo.py", "Injection")` in `previous_findings`. [1](#0-0) 
2. In the same session, edit `foo.py` again, fixing vulnerability A but introducing an unrelated vulnerability B, also category `"Injection"` (e.g., a different unsanitized input sink), then `git commit` again.
3. `_dedup_against_state` filters `new_vulns` against `previous_findings` keyed by `(filePath, category)`; since `("foo.py", "Injection")` is already `seen`, vulnerability B is dropped as "already known" even though it is a completely different bug, and `emit_metrics` reports `vulns_found: 0` / `skipping`.
