## Analog Found: Unhandled Exception in `chash.js` Address/Definition-Hash Validation from Unvalidated Encoded Length

### Title
Uncaught exception in c-hash validation from malformed base32/base64-encoded address data crashes unit validation - (File: chash.js)

### Summary
The external report describes a bug class where lengths/offsets are derived from attacker-controlled on-disk fields without full validation, and only *some* of the resulting error paths are guarded, letting a malformed length propagate into an unchecked code path that throws/crashes. The ocore analog is in `chash.js`'s `isChashValid()`, which only wraps the *decode* step in `try/catch` but leaves the subsequent length-dependent processing (`buffer2bin`, `separateIntoCleanDataAndChecksum`) unguarded, so a decoded buffer of unexpected bit-length throws an uncaught `Error` instead of returning `false`.

### Finding Description
`isChashValid()` checks only the *encoded string length* (32 or 48 characters) before decoding: [1](#0-0) 

The `try/catch` block covers only `base32.decode(encoded)` / `Buffer.from(encoded, 'base64')`. Everything after — `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` — runs **outside** the try/catch: [2](#0-1) 

`separateIntoCleanDataAndChecksum()` itself throws a plain `Error` if the decoded bit-length isn't exactly 160 or 288: [3](#0-2) 

The encoded-length check (32/48 chars) does not guarantee the *decoded byte length* is exactly 20 or 36 bytes — that depends on the content passed to the `thirty-two` base32 decoder, which can behave leniently on non-canonical input (e.g., dropped/invalid characters) without throwing, producing a buffer whose length doesn't match what `checkLength`/`arrOffsets` expect. Because the guard for that mismatch throws instead of being caught, the exception is not converted to a `false` result the way decode failures are.

This mirrors the CVE pattern precisely: a length is derived from attacker-supplied encoded data (`encoded_len`/decoded buffer length), only one of several downstream consumers of that length validates defensively (the decode step, via try/catch), and a sibling consumer (`separateIntoCleanDataAndChecksum`) assumes the length is "good" and throws when it isn't.

`isChashValid` underlies `isValidChash`, which underlies `isValidAddress`, `isValidAddressAnyCase`, and `isValidDeviceAddress`: [4](#0-3) 

`isValidAddress` is called extensively during unit/definition/authentifier validation (author addresses, `cosigned by`, `attested`, `in data feed` oracle lists, asset attestors, etc.), e.g.: [5](#0-4) [6](#0-5) 

While `isValidAddress` pre-filters with the regex `/^[A-Z2-7]{32}$/` (restricting to valid base32 characters) before calling `isValidChash`, `isValidAddressAnyCase` does **not** apply this regex and calls `isValidChash(address, 32)` directly: [7](#0-6) 

This makes it a plausible entry point for feeding non-canonical base32 content of the "correct" 32-character length into `isChashValid` without prior character-set sanitization.

### Impact Explanation
If a crafted 32/48-character string reaches `isChashValid` through a path lacking the `[A-Z2-7]` pre-filter (e.g., via `isValidAddressAnyCase`) and the underlying base32/base64 decode returns a buffer whose bit-length isn't exactly 160/288, the resulting uncaught `Error` propagates out of validation logic. If this occurs inside deterministic unit/definition/AA validation code executed by every full node processing the same posted unit, it can crash all nodes evaluating that unit identically — a node-crash / denial-of-service that prevents the network from confirming new units, which satisfies the required "network unable to confirm new units" impact class. This matches the external CVE's impact profile (`C:N/I:N/A:H` — availability-only, no confidentiality/integrity impact).

### Likelihood Explanation
Medium: Exploitation requires (a) identifying/confirming a concrete call path that supplies unfiltered attacker-controlled data to `isChashValid` (the clearest candidate, `isValidAddressAnyCase`, was located in `validation_utils.js` but its calling sites were not fully enumerated due to tool-call budget exhaustion), and (b) confirming the exact leniency/behavior of the third-party `thirty-two` base32 decoder on non-canonical input (its source was not present in the indexed codebase, so its exact decode semantics for invalid characters could not be verified directly). These two points are the main residual uncertainties.

### Recommendation
Wrap the entire body of `isChashValid()` (not just the decode call) in a single `try/catch`, and/or explicitly re-check the decoded buffer's length against the expected 20/36 bytes before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, returning `false` on mismatch instead of throwing. Additionally, apply the same base32-alphabet pre-validation used in `isValidAddress`'s regex to `isValidAddressAnyCase` (and any other caller of `isValidChash`) so non-canonical encodings are rejected before reaching the c-hash decode/verify pipeline.

### Proof of Concept
Conceptual (not fully verified against the external `thirty-two` decoder implementation, which is outside the indexed repo):
```js
const chash = require('chash.js');
// 32-character string using characters technically outside/borderline of the
// canonical base32 alphabet or with non-canonical padding, reaching isChashValid
// via isValidAddressAnyCase without the [A-Z2-7]{32} pre-filter.
chash.isChashValid('SOME_NONCANONICAL_32_CHAR_STRING'); 
// If the decoded buffer's bit length != 160, separateIntoCleanDataAndChecksum()
// throws an uncaught Error outside chash.js's try/catch, propagating out of
// isValidAddressAnyCase()/isValidChash() into caller validation code.
```

---
Note on limitations: I was unable to fully enumerate all call sites of `isValidAddressAnyCase` (the primary unguarded entry point) and could not inspect the third-party `thirty-two` base32 decoder's source (not present in this repo's index) to conclusively confirm it can produce a non-canonical-length buffer from a 32-character input without throwing. These are the two facts needed to fully confirm reachability and triggerability; the root-cause defect in `chash.js`'s incomplete try/catch scoping, however, is directly confirmed in the code cited above.
