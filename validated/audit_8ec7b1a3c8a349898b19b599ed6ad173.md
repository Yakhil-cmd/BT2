### Title
Missing validation of the `creator` account in `initialize_with_permission` allows setting `pool_creator` to a non-signable/default address, permanently freezing creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The external report's bug class is an inconsistency between two related setter paths where one validates against the zero address and the other does not, causing a legitimate/expected state to become unreachable. The same class of inconsistency exists between the two pool-creation entrypoints of this program: `initialize` requires `creator` to be a `Signer`, while `initialize_with_permission` accepts `creator` as an unchecked, non-signing account with no address validation. This asymmetry lets the pool creator field (`pool_state.pool_creator`) be set to an address that can never sign, permanently disabling the `collect_creator_fee` path and forcing all accrued creator fees through `collect_creator_fee_permissionless` into an account controlled by nobody.

### Finding Description
In `initialize.rs`, the pool creator is bound to the transaction signer: [1](#0-0) 

In `initialize_with_permission.rs`, however, `creator` is declared as an `UncheckedAccount` with no signer requirement and no constraint preventing it from being `Pubkey::default()` or any other address the payer chooses: [2](#0-1) 

The chosen `creator` key is passed directly into `PoolState::initialize` and stored as `pool_creator` without any zero-address or reachability check: [3](#0-2) [4](#0-3) 

Downstream, `collect_creator_fee` requires the transaction signer to equal `pool_state.pool_creator`: [5](#0-4) 

If `pool_creator` is set to an address with no known private key (e.g. `Pubkey::default()`), this constraint can never be satisfied by anyone, and `collect_creator_fee` becomes permanently unusable for that pool. The only remaining path, `collect_creator_fee_permissionless`, sends fees to an ATA whose authority is the unreachable `creator` address: [6](#0-5) [7](#0-6) 

Because the ATA authority is an address nobody controls, tokens delivered there are permanently inaccessible — mirroring the report's "disabling"/DoS pattern but here resulting in outright freezing of funds rather than just a blocked admin action.

### Impact Explanation
Every swap on such a pool accrues `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` (see `update_fees` in `states/pool.rs`), and once collected via the permissionless path, those tokens land in an ATA whose owner key cannot ever sign a withdrawal or be a legitimate token-account authority a user controls. This is a permanent freezing of protocol/user-facing creator fee funds, satisfying the "permanent freezing of user or LP funds" bar. It only affects pools created through the permissioned `initialize_with_permission` flow (an already gated flow, but the `creator` field itself is attacker-influenced with no validation), so the impact is bounded to pools where the payer with permission chooses (or mistakenly supplies) a degenerate `creator` key.

### Likelihood Explanation
Reaching this requires a single call to `initialize_with_permission` with an attacker/payer-chosen `creator` account equal to `Pubkey::default()` (or any other keypair-less address) — no other privilege beyond already holding a `Permission` PDA is needed, and the instruction performs no check to reject it. This is a straightforward, single-transaction reachable misconfiguration rather than a purely theoretical one, though it depends on the pool creator field being attacker/payer supplied incorrectly rather than being forced by protocol logic.

### Recommendation
Add an explicit constraint in `InitializeWithPermission` (mirroring `initialize.rs`) requiring `creator.key() != Pubkey::default()`, or require `creator` to be a `Signer` as in `initialize`, so the `pool_creator` field can never be set to an unreachable address. This aligns validation between the two initialization entrypoints and prevents creator fees from becoming permanently unclaimable.

### Proof of Concept
1. Caller holds a valid `Permission` PDA for `payer`.
2. Caller invokes `initialize_with_permission` supplying `creator = Pubkey::default()` (or any address with no known private key) as the `creator` account — no Anchor constraint rejects this. [3](#0-2) 
3. `pool_state.pool_creator` is now `Pubkey::default()`.
4. Swaps occur on the pool, accruing `creator_fees_token_0`/`creator_fees_token_1`.
5. `collect_creator_fee` can never succeed because no signer can equal `Pubkey::default()`: [5](#0-4) 
6. `collect_creator_fee_permissionless` can be called by anyone, but funds are transferred into an ATA owned by `Pubkey::default()` — an address nobody can ever access: [7](#0-6) 
Resulting in permanent, irrecoverable loss of the pool's creator fees.
