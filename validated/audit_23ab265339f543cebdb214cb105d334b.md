### Title
Merkle proof verification lacks leaf/internal-node domain separation, allowing forged membership proofs in `is_valid_merkle_proof` / `in merkle` — (File: `merkle.js`)

### Summary
`merkle.js` builds and verifies Merkle trees by hashing leaves and internal nodes with the exact same function and no domain-separation prefix, mirroring the classic CVE-2012-2459 / Footium `clubDivsMerkleTree` bug class. Any consumer that lets an attacker choose the "element" being proven — most notably the oscript `is_valid_merkle_proof()` formula function usable in AA definitions — can be tricked into accepting a forged leaf that is really the concatenation of two internal-node hashes, letting an attacker prove "membership" of arbitrary data that was never included in the committed set.

### Finding Description
`getMerkleRoot`/`getMerkleProof` compute leaf hashes as `hash(element)` and internal nodes as `hash(childHash1 + childHash2)`, using the identical `hash()` (sha256/base64) function for both layers with no distinguishing prefix (e.g. `0x00`/`0x01`): [1](#0-0) 

`verifyMerkleProof(element, proof)` recomputes the same way, starting from `hash(element)` and repeatedly combining with `proof.siblings[i]` using plain concatenation: [2](#0-1) 

Because there is no domain separation, an attacker who knows (or can compute/observe) any two sibling internal-node hashes `h1, h2` from a tree can submit `element = h1 + h2` as the "leaf" together with the remaining upper siblings as `proof.siblings`. Since `hash(element) === hash(h1+h2)`, this equals the legitimate ancestor node, and the proof verifies against the real, previously-committed root — even though `h1+h2` was never one of the original `arrElements` that were supposed to be individually committed.

This primitive is directly exposed to attacker/AA-trigger-sender control via the oscript function `is_valid_merkle_proof(element, proof)`, where both `element` and `proof` (including `siblings` and even `root`) are evaluated from arbitrary formula expressions, typically fed from `trigger.data`: [3](#0-2) 

A typical AA membership-check pattern is: `is_valid_merkle_proof(trigger.data.element, trigger.data.proof) AND trigger.data.proof.root == <root committed earlier via state var or data feed>`. Because the proof's `root` field is only checked for equality against the trusted, previously-published root, and the `element`/`siblings` are fully attacker-supplied, the forged-leaf technique lets an attacker "prove" membership for a synthetic `element` value that was never part of the set the root was built from.

The same weak primitive also backs the `in merkle` address-definition authentifier, which checks a spender-supplied `serialized_proof` against a root fetched from an oracle data feed: [4](#0-3) 
Here the `element` ("expected value") is fixed by the address definition itself rather than attacker-chosen, so this particular call site is not directly exploitable by an unprivileged spender — the primary reachable exploit path is through AA formulas using `is_valid_merkle_proof` where the element is attacker-controlled trigger data.

### Impact Explanation
Any AA that uses `is_valid_merkle_proof` to gate a privileged action (allowlist/airdrop claim, discount, voting weight, role grant, fund release, etc.) based on set membership committed via a Merkle root can be bypassed by an attacker who is able to derive two internal sibling hashes of the committed tree (trivial if the underlying dataset/tree is published, or brute-forceable/discoverable in smaller trees). This results in unauthorized AA state changes and unauthorized fund/asset disbursement from the AA — a genuine "AA fund loss" impact reachable by any ordinary trigger sender with no privileged access.

### Likelihood Explanation
Exploitability depends entirely on how AA authors use `is_valid_merkle_proof`, but the underlying merkle.js primitive itself is broken regardless of usage: it fails to include the standard second-preimage/domain-separation defense that all modern Merkle implementations require (e.g. OpenZeppelin's leaf hashing recommendation). Given that AAs are commonly designed around exactly this "prove membership in a committed set" pattern (whitelists, snapshots, airdrops), and the whole point of using a Merkle proof is to let users self-derive proofs from a public dataset, the internal hashes needed to mount the attack are realistically available to any user with access to the published leaf set.

### Recommendation
Add domain separation to `merkle.js`:
- Hash leaves with a distinct prefix, e.g. `hash('0' + element)`, and internal nodes with `hash('1' + left + right)`, so a leaf hash can never collide with an internal-node hash by construction.
- Update `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently, and bump/guard formula behavior (`bPostPemCurvesFix`-style version gate) so old and new trees are not cross-verifiable.
- Audit/document that `is_valid_merkle_proof` combined with AA-side root pinning is unsafe until this fix ships, since currently no additional check in `merkle.js` prevents the intermediate-node-as-leaf substitution.

### Proof of Concept
1. Build a tree of ≥4 elements with `merkle.getMerkleRoot`/`getMerkleProof`, e.g. `arrElements = [A,B,C,D]`.
2. Compute `h1 = hash(A)`, `h2 = hash(B)` (the two leaf hashes forming the left subtree), and note the real root `R = hash(hash(h1+h2) + hash(hash(C)+hash(D)))`.
3. Construct forged input: `element = h1 + h2`, `proof = { index: 0, siblings: [hash(hash(C)+hash(D))], root: R }`.
4. Call `merkle.verifyMerkleProof(element, proof)` (or in an AA formula, `is_valid_merkle_proof(element, proof)` with `proof.root` checked against the real committed root `R`): it returns `true`, even though `element` (`h1+h2`) was never one of the original committed elements `A, B, C, D`.
5. In an AA that grants a reward/state change when `is_valid_merkle_proof(...)` succeeds and `proof.root` matches the known-good root, the attacker obtains the reward without being part of the actual whitelisted/committed set.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
