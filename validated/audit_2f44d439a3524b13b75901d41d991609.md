### Title
`requestERC20Transfer()` Does Not Verify Actual Received Amount After `safeTransferFrom`, Enabling Bridge Reserve Drain via Fee-on-Transfer Tokens — (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer()` calls `safeTransferFrom` to pull `_value + _feeLimit` tokens from the caller into the bridge, then immediately emits a `RequestValueTransfer` event for the full `_value` without ever verifying that the bridge actually received that amount. If the registered ERC20 token applies a transfer fee (fee-on-transfer), the bridge receives fewer tokens than expected but still instructs the counterpart bridge to release the full `_value` to the recipient, draining the counterpart bridge's reserves.

---

### Finding Description

In `requestERC20Transfer`:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
``` [1](#0-0) 

After `safeTransferFrom` completes, the code immediately calls `_requestERC20Transfer` with the caller-supplied `_value`. There is no balance snapshot before/after the transfer to confirm the bridge actually received `_value + _feeLimit` tokens.

`_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange`, which pays the bridge fee and refunds excess `_feeLimit` from the bridge's balance using the nominal amounts:

```solidity
IERC20(_token).safeTransfer(feeReceiver, fee);
...
IERC20(_token).safeTransfer(from, feeRefund);
``` [2](#0-1) 

Finally, `RequestValueTransfer` is emitted with the full `_value`:

```solidity
emit RequestValueTransfer(TokenType.ERC20, _from, _to, _tokenAddress, _value, requestNonce, fee, _extraData);
``` [3](#0-2) 

The counterpart bridge's `handleERC20Transfer` trusts this event and releases the full `_value` to the recipient:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

Token registration is `onlyOwner`, so only the bridge owner can register tokens:

```solidity
function registerToken(address _token, address _cToken) external onlyOwner onlyNotRegisteredToken(_token) {
``` [5](#0-4) 

However, once a fee-on-transfer token is registered (whether intentionally or because the token dynamically enabled fees after registration), **any unprivileged user** can call `requestERC20Transfer` and trigger the drain.

---

### Impact Explanation

For each call to `requestERC20Transfer` with a fee-on-transfer token (transfer fee rate `r`):

- Source bridge receives: `(_value + _feeLimit) × (1 − r)` tokens
- Source bridge pays out fee + refund: nominal `_feeLimit` tokens from its balance
- Source bridge net hold: `(_value + _feeLimit) × (1 − r) − _feeLimit`
- Counterpart bridge releases: full `_value` tokens to recipient

The shortfall per transaction is `(_value + _feeLimit) × r` tokens, taken from the counterpart bridge's existing liquidity reserves. Repeated calls drain the counterpart bridge's ERC20 reserves, eventually causing legitimate `handleERC20Transfer` calls to fail (insufficient balance) and breaking cross-chain withdrawals for all users of that token pair.

This constitutes an **unauthorized transfer of bridged assets** from the counterpart bridge's reserves to the recipient, beyond what was actually deposited.

---

### Likelihood Explanation

- Token registration is `onlyOwner`, which limits the initial setup to a trusted party.
- However, some ERC20 tokens support dynamic fee toggling (e.g., a token owner enables a transfer fee after the bridge has already registered the token). The bridge has no mechanism to detect or react to this change.
- Once a fee-on-transfer token is registered (even accidentally), **any user** can call `requestERC20Transfer` repeatedly to drain the counterpart bridge's reserves with no special privilege required.
- The 2-step path (`requestERC20Transfer`) is the primary affected path; the 1-step path (`onERC20Received`) is also affected since `_value` is passed by the token contract and may not reflect the actual post-fee amount received.

---

### Recommendation

Record the bridge's token balance before and after `safeTransferFrom` and use the actual received amount for all downstream accounting:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived == _value.add(_feeLimit), "fee-on-transfer token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, document that fee-on-transfer tokens are explicitly unsupported and add a check in `registerToken` to reject tokens whose `transfer` results in a balance change different from the requested amount.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` with a 10% transfer fee.
2. Bridge owner calls `registerToken(FeeToken, cFeeToken)` on both source and counterpart bridges.
3. Counterpart bridge is pre-funded with 1000 `cFeeToken`.
4. Attacker approves source bridge for 1100 `FeeToken` (`_value=1000, _feeLimit=100`).
5. Attacker calls `requestERC20Transfer(FeeToken, attacker, 1000, 100, "0x")`.
   - Source bridge receives `1100 × 0.9 = 990` tokens (10% fee deducted).
   - Source bridge pays fee (e.g., 50) and refund (50) from its balance: net holds `990 − 100 = 890` tokens.
   - `RequestValueTransfer` emitted with `_value = 1000`.
6. Counterpart bridge operators call `handleERC20Transfer` for `_value = 1000`.
   - Counterpart bridge releases 1000 `cFeeToken` to attacker.
7. Net: attacker deposited 990 tokens worth of value, received 1000 tokens on the other side. The counterpart bridge lost 10 tokens per transaction.
8. Repeat to drain the counterpart bridge's reserves.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
