### Title
`StatusHandler#process` applies GitHub `status` webhooks to any `Commit` matching `sha`, with no check that the payload's `repository.full_name` matches the target commit's `stack` — allowing a status from an unrelated repository to satisfy `MergeRequest::StatusChecker#success?` and trigger `merge!` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Webhooks::Handlers::StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` for every match, with no comparison of the payload's `repository`/`organization` to the commit's actual `stack`. `Status.replicate_from_github!` and `Commit#create_status_from_github!` likewise never read or validate a repository field. Since git commit SHAs are content-addressed, an attacker who controls a second repository can push a byte-identical commit object (same tree/parent/author/committer/timestamps/message) to obtain the same SHA as a PR head opened against a victim stack, then get a legitimately signed `status` webhook fired for their own repository naming `state: "success"` — this status is written onto the victim's `Commit` because the lookup is by `sha` alone.

### Finding Description
Broken binding: the code implicitly assumes
`Status counted by MergeRequest::StatusChecker#success? (via Status::Group over commit.statuses_and_check_runs) == Status whose originating webhook payload named commit.stack.repository (i.e. params['repository']['full_name'] == commit.github_repo_name)`
but no code enforces the right-hand side at all.

Path:
- `StatusHandler#process`: [1](#0-0) 
  only ever uses `params.sha`, `params.state`, etc. — it never reads or checks `params['repository']`.
- `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }`: [2](#0-1) 
  the `stack_id` used is the **matched commit's own** `stack_id` — not derived from or validated against the payload's repository.
- `Status.replicate_from_github!`: [3](#0-2) 
  builds the `Status` from `state`, `description`, `target_url`, `context`, `created_at` only; `repository` is never consulted.
- `MergeRequest::StatusChecker` is a plain `Status::Group` subclass with no additional repository check: [4](#0-3) , and `all_status_checks_passed?` / `merge!` consume it directly: [5](#0-4) [6](#0-5) .

`WebhooksController#verify_signature` only authenticates *that the delivering organization actually sent this payload* (HMAC against that organization's configured `webhook_secret`, resolved via `repository_owner`): [7](#0-6) . It never binds the authenticated repository to the specific `Commit`/`stack` that the `sha` in the payload will end up mutating. So a webhook can be 100% authentically signed by GitHub for the attacker's own repository, yet its `status` event is applied to a completely different tenant's commit purely because `sha` collides — which is trivially achievable by pushing an identical commit object (not a SHA-1 break, just re-using the same commit bytes) into a second repository the attacker controls.

Exploit flow:
1. Attacker opens a PR against the victim's tracked stack with head commit `X` (created via normal `pull_request`/push sync, stored as a `Shipit::Commit` belonging to the victim's `stack`).
2. Attacker pushes the identical commit object `X` into a second repository `Y` they own (also onboarded to this Shipit instance, or covered by the same GitHub App/organization-level secret).
3. Attacker triggers (via the GitHub API or a real push) a `status` event on `Y` for `sha: X, state: "success"`. GitHub signs and delivers this webhook genuinely; `verify_signature` passes because it correctly proves "this came from `Y`'s organization," not "this describes the victim's repository."
4. `StatusHandler#process` finds the victim's `Commit` (matching by `sha` only) and writes a `success` `Status` scoped to the **victim's** `stack_id`.
5. `MergeRequest#all_status_checks_passed?` becomes `true`, `reject_unless_mergeable!` no longer fires, and `ProcessMergeRequestsJob` merges the PR via `merge_request.merge! → stack.github_api.merge_pull_request`, even though the victim repository's own CI never validated the code.

### Impact Explanation
A payload authenticated for one repository/organization mutates the CI status — and thus the merge decision — of a completely unrelated stack/commit, culminating in `stack.github_api.merge_pull_request` being called for code whose CI was never run in the victim repository. This is a cross-tenant integrity break in a multi-tenant Shipit deployment (or any deployment where a GitHub App/organization webhook secret is shared across multiple repositories) and is directly repeatable against any stack/commit whose SHA the attacker can reproduce in a repo they control. This matches the "payload for one repository mutating another's stack/commit" and "unauthorized merge" Critical categories.

### Likelihood Explanation
Preconditions: the attacker needs (a) an open PR against the victim stack, and (b) a second repository under their control that is also wired into the same Shipit installation's webhook delivery (same organization-level webhook secret, or their own onboarded org in a multi-tenant deployment). Producing an identical commit SHA across two repositories requires no cryptographic collision — only pushing the same commit object (same tree, parents, author/committer identities and timestamps, message) into a second repo, which is standard git operation available to any repo owner. No Shipit secrets, sessions, or maintainer privileges are required. This is realistic in shared/organization-wide Shipit or GitHub App configurations and is fully repeatable.

### Recommendation
In `Commit#create_status_from_github!` / `StatusHandler#process`, verify that the incoming payload's `repository.full_name` (or `organization.login`) matches `commit.github_repo_name` (i.e., `commit.stack.repository.full_name`) before creating the `Status`; drop/ignore statuses whose declared repository does not match the resolved commit's stack. Scope the `Commit.where(sha: params.sha)` lookup by the payload's repository rather than searching the whole `commits` table unscoped.

### Proof of Concept
```ruby
# test/models/merge_request_test.rb
test "a status from an unrelated repository must not satisfy all_status_checks_passed?" do
  @pr.head.statuses.create!(stack: @pr.stack, state: 'failure', context: 'ci/circle')
  refute_predicate @pr, :all_status_checks_passed?

  spoofed_status = OpenStruct.new(
    state: 'success',
    description: 'forged',
    context: 'ci/circle',
    target_url: 'http://example.com',
    created_at: Time.now,
    repository: OpenStruct.new(full_name: 'attacker/unrelated-repo') # never checked anywhere
  )

  @pr.head.create_status_from_github!(spoofed_status)

  # BUG: this becomes true even though the status never named @pr.stack's repository
  assert_predicate @pr, :all_status_checks_passed?

  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [@pr.stack]) do
    # existing hook already schedules this on state transition; confirm merge! would proceed
  end
end
```
Both sides of the claimed binding can be asserted directly: left side `@pr.reload.all_status_checks_passed?` (true after the forged status), right side `spoofed_status.repository.full_name == @pr.stack.github_repo_name` (false) — proving the equality the code should enforce is never checked.
