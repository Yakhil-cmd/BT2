### Title
Webhook signature is verified against the org named in the payload, but event handlers act on an unrelated repository/commit named in the same payload — cross-organization commit-status forgery enabling unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify a webhook against based on a field taken from the untrusted request body itself (`repository.owner.login`, falling back to `organization.login`). The event handlers that subsequently execute, however, key their side effects off *other* untrusted fields in that same body — for `status` events, purely `sha` with no repository/organization scoping at all. In a multi-tenant Shipit deployment (multiple GitHub orgs configured under `secrets.github`), an attacker who legitimately controls one configured organization can forge a webhook that authenticates as their own org but whose payload content targets a commit belonging to a completely different, victim organization's stack.

### Finding Description
`Shipit.github(organization:)` and `Shipit::GitHubApp#verify_webhook_signature` are org-scoped: each org in `secrets.github` (see `config/secrets.development.shopify.yml`) has its own `webhook_secret`. [1](#0-0) 

`WebhooksController#verify_signature` derives *which* org's webhook secret to check against entirely from the request body: [2](#0-1) [3](#0-2) 

So the equality the app relies on is: `organization that authenticates the signature == organization that owns the affected resources`. This equality is never enforced — an attacker who administers `attacker-org` (a legitimately configured Shipit org with its own known `webhook_secret`) can set `repository.owner.login` (or `organization.login`) to `attacker-org` so the signature check passes with a secret they know, while setting the actually-acted-upon fields to point at a victim resource.

The clearest exploitable divergence is in `StatusHandler`, which processes `status` events without any repository/org scoping at all — it matches purely on `sha`: [4](#0-3) 

Any `Commit` row anywhere in the Shipit instance whose `sha` matches gets a forged status recorded via `create_status_from_github!`, regardless of which org/repo it belongs to: [5](#0-4) 

This forged status feeds directly into deploy-gating logic: `Commit#deployable?` requires `success?` and `!blocked?`, both derived from `status`/`statuses_and_check_runs`, which is exactly what `create_status_from_github!` populates: [6](#0-5) [7](#0-6) 

A success status can also trigger `stack.schedule_merges` and continuous delivery for the victim's stack: [8](#0-7) [9](#0-8) 

Other handlers exhibit the same pattern of trusting `repository.full_name`/`organization.login` inside the body for scoping (e.g. `Handler#repository_name`, `PushHandler`, `MembershipHandler`), but their side effects are constrained to existing `Repository`/`Stack` records looked up by that name and, for push, re-fetch data from GitHub using the *stack's own* configured org, limiting impact. `StatusHandler` is the outlier with zero scoping, making it the strongest concrete path. [10](#0-9) [11](#0-10) 

### Impact Explanation
An attacker who controls (or is an authorized webhook sender for) any one GitHub organization configured in the same Shipit instance can forge a "success" (or "failure"/"pending") CI status for an arbitrary commit SHA in a victim organization's stack that they have no legitimate access to. Because commit deployability (`Commit#deployable?`) and continuous-deployment triggering are driven by these statuses, this can be used to force a stack that is gated on CI status to become "deployable" without the real CI ever passing — a step toward an unauthorized deploy. This matches the Critical impact category of "an unauthorized deploy" via a broken authentication binding (org that signed the request vs. resource actually mutated).

### Likelihood Explanation
This requires Shipit to be configured for multiple GitHub organizations (each with its own registered GitHub App/webhook and `webhook_secret`) sharing the same Shipit instance/database — a supported, documented configuration (`secrets.github` keyed by org, see `config/secrets.development.shopify.yml`). Given that, no privileged Shipit credential (API token, session, or GitHub App private key for the *victim* org) is needed — only the ability to send a signed webhook for the attacker's own configured org, which any such tenant already has via their own GitHub App/webhook trigger. This is a realistic scenario for any Shipit deployment serving more than one organization/tenant.

### Recommendation
Do not derive the org used for signature verification independently from the org whose resources are mutated. Concretely:
1. In `StatusHandler` (and other handlers), scope lookups by the repository identified in the payload (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and verify that repository's `owner` matches the `repository_owner`/org that was used to validate the signature, rejecting the event otherwise.
2. More generally, after `verify_signature` resolves an org, propagate that resolved org identity into the handler and require every handler to confirm the resource it is about to mutate (`Repository`/`Stack`/`Commit`) belongs to that same org before applying any side effect.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.github`: `attacker-org` (attacker's own GitHub org/App, `webhook_secret` known to attacker) and `victim-org` (unrelated victim, has a Stack with an undeployed commit `sha = X` requiring a CI status check to become deployable).
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "X",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` (which they legitimately possess) over this exact body.
4. `WebhooksController#repository_owner` resolves to `attacker-org` from the payload, `Shipit.github(organization: 'attacker-org').verify_webhook_signature` succeeds — signature check passes.
5. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which runs `Commit.where(sha: 'X').each { |c| c.create_status_from_github!(params) }` — this matches the victim's commit purely by SHA, with no check that it belongs to `attacker-org`.
6. The victim's commit now has a forged "success" status for `ci/required-check`, potentially making it `deployable?` and triggering `stack.schedule_merges`/continuous delivery for the victim's stack, without the attacker having any access to `victim-org`.

    if github_default_organization.nil?
