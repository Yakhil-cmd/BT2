### Title
Cross-Organization Team-Membership Forgery Escalates into `Shipit.github_teams` Authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The `membership` webhook handler binds team membership mutations to a `team.id` value from the webhook payload without verifying that this GitHub team ID actually belongs to the organization whose secret authenticated the webhook. This mirrors the reported bug class: a value used to update privileged state (`lpState`'s `lastCumulativeFundingX18`) diverges from the value that was actually validated (`state.cumulativeFundingLongX18`). Here, the organization whose secret is cryptographically verified (`repository_owner`, used to select the webhook secret) is never bound to the `team.id` that is looked up and mutated, allowing a webhook signed with one organization's secret to modify team membership belonging to a completely different, unrelated organization's `Team` record.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC signature against using a value taken straight from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. For `membership` events (the real GitHub payload only contains `organization`, not `repository`), this resolves to the attacker-controlled `organization.login` field. In a multi-org Shipit deployment (`lib/shipit.rb#github_app_config`, documented in `docs/setup.md` under "Using Multiple Github Applications"), each organization has its own independently configured `webhook_secret`, which is typically supplied by whoever registers that organization's GitHub App: [3](#0-2) 

Once the signature check passes (using the secret belonging to the organization named in the payload), `Shipit::Webhooks::Handlers::MembershipHandler#process` mutates team membership using a *different, unvalidated* field — the numeric `team.id` — with no check that this ID actually belongs to the same organization that was cryptographically verified: [4](#0-3) 

`Team.find_or_create_by!(github_id: params.team.id)` looks up teams purely by the global GitHub numeric team ID. The `team.organization = params.organization.login` assignment only executes inside the `find_or_create_by!` block, i.e., only on **creation** of a new record — it is never re-validated or updated when an existing `Team` row (with a matching `github_id`) is found. This means an attacker who controls one organization (and therefore its webhook secret) can craft a `membership` "added" event where:
- `organization.login` = their own organization (so `verify_signature` selects a secret they know and the HMAC check passes)
- `team.id` = the real GitHub numeric ID of a target `Team` row that already exists in Shipit's database and is part of `Shipit.github_teams` (the authorization team list)
- `member.login` = the attacker's own GitHub login

`find_or_create_team!` then finds the *existing* target `Team` record (matched only by `github_id`, ignoring `organization`), and `team.add_member(member)` appends the attacker's user record as a member: [5](#0-4) 

This directly breaks `User#authorized?`, which grants full application access based solely on DB-side team membership, with no live GitHub check at request time: [6](#0-5) [7](#0-6) 

**Broken binding (equality that should hold but doesn't):**
`verified_organization` (the org whose secret authenticated the HMAC, i.e., `repository_owner`) `== team.organization` (the org that actually owns the `github_id` being mutated).
The code never enforces this equality; `find_or_create_by!(github_id: …)` short-circuits organization binding entirely for pre-existing teams.

### Impact Explanation
This matches the "High" impact tier explicitly listed in scope: **escalation into `Shipit.github_teams` authorization**. An attacker who has never been vetted or added by GitHub to a privileged team can grant themselves membership in that team purely inside Shipit's database, bypassing GitHub's actual team membership entirely, and subsequently pass `current_user.authorized?` to gain full deploy/rollback/merge access to every stack gated behind that authorized team.

### Likelihood Explanation
Exploitability requires the attacker to control at least one organization/GitHub App registered in Shipit's multi-org `secrets.yml` configuration (a documented, supported feature — `docs/setup.md`, "Using Multiple Github Applications") and to know the numeric GitHub `team.id` of a target privileged team (discoverable via GitHub's public API/UI in many cases, or via prior interaction with the Shipit instance/team roster). No Shipit session, `ApiClient` token, or privileged Shipit account is required — only a webhook secret the attacker set up for their own onboarded organization, which is a normal, unprivileged-attacker-reachable capability in this multi-tenant configuration.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/mutation to the verified organization, e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, or explicitly reject/raise if an existing team's `organization` does not match `params.organization.login`. Additionally, `WebhooksController#verify_signature` should ensure the organization used to select the signing secret is the same organization value trusted for all downstream mutations, rather than allowing handlers to use unrelated payload fields (`team.id`) as an implicit trust anchor.

### Proof of Concept
1. Shipit is configured with multiple GitHub orgs in `secrets.yml` (per `docs/setup.md`), including `victim-org` (whose `developers` team, github_id `1001`, is listed in `Shipit.github_teams`) and `attacker-org` (set up/onboarded by the attacker, who therefore knows `attacker-org`'s `webhook_secret`).
2. Attacker crafts a `membership` webhook JSON body:
```json
{
  "action": "added",
  "team": { "id": 1001, "name": "developers", "slug": "developers", "url": "https://api.github.com/teams/1001" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-login" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret over this raw JSON body and POSTs it to `/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` resolves `repository_owner` to `attacker-org` and validates the signature successfully (per `app/controllers/shipit/webhooks_controller.rb`).
5. `MembershipHandler#find_or_create_team!` looks up `Team.find_or_create_by!(github_id: 1001)`, finding the pre-existing `victim-org/developers` team (id `1001` belongs to `victim-org`, not `attacker-org`), ignoring the mismatch.
6. `team.add_member(User.find_or_create_by_login!("attacker-login"))` adds the attacker's user to the privileged team.
7. Attacker logs into Shipit via GitHub OAuth; `current_user.authorized?` returns `true` because their user row is now a member of a `Shipit.github_teams` team, granting full deploy/rollback/merge access despite never being a real member of `victim-org/developers` on GitHub.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
