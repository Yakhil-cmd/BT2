### Title
`TransferStxOp` sets `sender` from an unverified, attacker-declared `PreStxOp.output` field, allowing theft of any StacksAddress's STX with zero signature from the victim - ([File: stackslib/src/chainstate/burn/operations/transfer_stx.rs])

### Summary
`TransferStxOp::parse_from_tx` accepts a `sender: &StacksAddress` parameter and copies it verbatim into the resulting op without any cryptographic check that this address is controlled by whoever actually spends the referenced Bitcoin UTXO. `TransferStxOp::check()` only rejects a zero-value transfer and a self-send, so any attacker who can craft a two-output Bitcoin transaction (a `PreStxOp`) and then spend its second output (a `TransferStxOp`) can designate an arbitrary victim's `StacksAddress` as `sender` and their own address as `recipient`.

### Finding Description
The equality that should hold is: *the Stacks address whose balance is debited by a `TransferStxOp` == the Stacks address of the entity that authorized the Bitcoin spend proving ownership of the underlying value*. Here it is broken because:

- `TransferStxOp::parse_from_tx` simply does `sender: sender.clone()` [1](#0-0) , where `sender` is passed in from the caller and is ultimately sourced from the corresponding `PreStxOp`'s declared `output` field — a plain Bitcoin-address-derived `StacksAddress` that requires no signature to set (anyone can pay BTC to any address without the recipient's consent).
- `get_sender_txid` only enforces that the `TransferStxOp`'s first input spends `vout == 1` of the referenced prior transaction [2](#0-1) . It never checks that the public key used to spend that output corresponds in any way to the `sender`/`output` address recorded in the `PreStxOp`.
- `TransferStxOp::check()` validates only `transfered_ustx != 0` and `sender != recipient` [3](#0-2) ; there is no check binding `sender` to any Bitcoin signature produced in the transaction.

Exploit flow: the attacker crafts a `PreStxOp` Bitcoin transaction whose first output ("output" field) encodes the victim's `StacksAddress`, funding both outputs entirely with the attacker's own BTC (paying BTC to an address requires no permission from that address's owner). The attacker then spends `vout=1` of that transaction (which they fully control since they created and funded it) to produce a `TransferStxOp` with `recipient = attacker`, `transfered_ustx = victim's balance`. Because `sender` is copied from the `PreStxOp.output` field with no cryptographic link to the key that spent `vout=1`, the resulting op has `sender = victim`, `recipient = attacker`, and passes `check()` trivially.

### Impact Explanation
If the downstream chain-state application of `TransferStxOp` debits the STX balance of `op.sender` and credits `op.recipient` without any additional signature verification (which is the entire premise of these burnchain-triggered ops — they exist specifically so that a Bitcoin transaction alone authorizes a Stacks-side STX movement), then an attacker can drain any StacksAddress's unlocked STX balance to their own address, for the cost of two minimal-fee Bitcoin transactions. This is repeatable against any victim address with a positive balance and matches the Critical category: theft of a victim's STX with zero signature from that victim.

### Likelihood Explanation
No privileged role is required: the attacker only needs to construct and broadcast two ordinary Bitcoin transactions using funds they already control (a `PreStxOp` and a `TransferStxOp` spending its second output). No membership state, cycle phase, or PoX-specific precondition is needed since this code path is independent of pox-5. The cost is limited to Bitcoin transaction fees, and the attack is repeatable against any target with nonzero unlocked STX.

### Recommendation
Bind `sender` cryptographically to the Bitcoin key that funds/spends the relevant UTXO chain, e.g., require that `PreStxOp.output`'s hash matches the public key hash of the address that funds the `PreStxOp`'s inputs (self-declaration must be provably self-referential), and/or require that the `TransferStxOp`'s spending key for `vout=1` matches the hash160 encoded in `sender`. Absent such a binding, the `sender` field must not be treated as an authorized party for debiting real account balances.

### Proof of Concept
Rust integration test plan (extending `stackslib/src/chainstate/burn/operations/transfer_stx.rs::tests` or the coordinator tests referencing `PreStxOp`/`TransferStxOp`):
1. Boot a test chainstate and fund a `victim` Stacks account with STX via a normal genesis/transfer.
2. Construct a `BitcoinTransaction` for `PreStxOp` whose `outputs[0].address` decodes to `victim`'s `StacksAddress`, funded solely by attacker-controlled inputs; process it through the burnchain op parser.
3. Construct a second `BitcoinTransaction` for `TransferStxOp` whose sole input spends `vout=1` of the prior transaction (signed by the attacker's own key), with `outputs[0].address` = attacker's address and payload `transfered_ustx` = victim's full balance.
4. Call `TransferStxOp::parse_from_tx` (as the burnchain indexer would, supplying `sender = victim` derived from step 2's `output` field) and confirm `op.check()` succeeds.
5. Apply the resulting op through the chainstate's burn-op-application logic and assert: `victim`'s STX balance before == full amount, after == 0; `attacker`'s balance increases by that amount — with no Stacks or Bitcoin signature ever produced by `victim`. Both sides of the equality (debited address vs. authorizing entity) mismatch, confirming the break.

impl TransferStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.transfered_ustx == 0 {
            warn!("Invalid TransferStxOp, must have positive ustx");
            return Err(op_error::TransferStxMustBePositive);
        }
        if self.sender == self.recipient {
            warn!("Invalid TransferStxOp, sender is recipient");
            return Err(op_error::TransferStxSelfSend);
        }
        Ok(())
    }
}
