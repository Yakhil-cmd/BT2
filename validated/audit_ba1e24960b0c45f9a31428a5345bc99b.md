### Title
Cross-organization webhook signature scoping lets a repository "owner" attacker with a valid webhook secret for their own org trigger writes against an unrelated `Repository`'s stacks via `Repository.from_github_repo_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to validate the payload against using `repository_owner`, which is read from the attacker-controlled JSON body (`params.dig('repository','owner','login')`), while `Handler#stacks` (and the sibling `repository` methods in the `pull_request` handlers) looks up the target `Repository` using a *different* attacker-controlled field, `payload.dig('repository','full_name')`. Nothing in the request pipeline enforces that these two independently-controlled fields refer to the same repository/organization, so a payload signed with org A's webhook secret but carrying `repository.full_name = "C/some-repo"` passes signature verification yet resolves and mutates org C's stacks.

### Finding Description
The broken binding: the question posits `Repository.from_github_repo_name(repository_name)` existence-check should be equivalent to an ownership check tying the verified organization to the resolved repository, i.e. it assumes `repository_owner (used for HMAC selection) == full_name.split('/').first (used for the DB lookup)`. This binding is never enforced.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from the raw JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to pick which `GitHubApp`/secret to verify against: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
2. `Shipit.github(organization:)` maps the organization name straight to a per-organization config entry (`github_app_config(organization)`), each with its own independently configured `webhook_secret` [3](#0-2) . If the attacker administers org A themselves (a real, unprivileged GitHub org they own) and has onboarded any repo under A into Shipit, they know/control A's `webhook_secret` because they configured GitHub's webhook delivery for A.
3. Once `verify_signature` passes, `create` calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` using the very same parsed JSON [4](#0-3) .
4. Inside the handler, `repository_name` is taken again from the payload, but from the different key `repository.full_name`: `payload.dig('repository', 'full_name')` [5](#0-4) , and `stacks` resolves it via `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [6](#0-5) . `from_github_repo_name` simply splits `owner/name` and does a `find_by` [7](#0-6) .
5. Since `repository.owner.login` (used for signature routing) and `repository.full_name` (used for the DB lookup) are two separate JSON fields with no cross-validation, the attacker can sign with org A's secret while setting `full_name` to any already-onboarded `owner/repo` string, e.g. victim org C's repo.
6. Concretely: `PushHandler#process` does `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [8](#0-7) , so a signed-by-A payload with `full_name: "C/repo"` and a matching branch enqueues `GithubSyncJob` against C's stack, causing Shipit to sync/deploy state driven by attacker-supplied `after` (head SHA) against org C's stack with none of org C's own credentials involved. The `pull_request` handlers (`opened`, `closed`, `reopened`, `unlabeled`, `labeled`) have the analogous pattern via their own `repository` method, which also only does `Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new` [9](#0-8) , allowing e.g. archiving/unarchiving or provisioning review stacks belonging to org C while only having proven possession of org A's webhook secret.
7. Existing guards do not catch this: `verify_signature` only proves the sender knows *some* org's secret matching whatever `repository.owner.login` the attacker chose to put in the payload — it says nothing about which org owns the `repository.full_name` used later. `drop_unhandled_event` and the `ExplicitParameters` schemas (`requires :repository do requires :full_name, String end`) only validate types/presence, not cross-field consistency. `Repository` model validations only constrain the format of stored owner/name, not the webhook payload. There is no `require_permission!`/ownership check anywhere in this webhook flow.

### Impact Explanation
An attacker who owns/administers any GitHub organization "A" already onboarded into Shipit (i.e., they know A's `webhook_secret`, which they themselves configured on GitHub's webhook settings for their own org) can forge a webhook body whose `repository.owner.login` is "A" (so verification routes to and passes with A's secret) but whose `repository.full_name` is `"C/victim-repo"` for any other onboarded `Repository` C. This lets them:
- Trigger `GithubSyncJob`/`sync_github` on victim stacks via `push` events with attacker-chosen `expected_head_sha`.
- Archive/unarchive or force-provision victim's review stacks via the `pull_request` handlers.
This is a cross-repository write against a repository the attacker did not authenticate as, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). It is fully repeatable against every `Repository` already present in Shipit's database, as long as the attacker has any one legitimately onboarded org.

### Likelihood Explanation
Preconditions: attacker must own/administer at least one GitHub org/repo onboarded to Shipit (so they know that org's real `webhook_secret`), and the target's `owner/name` string must already exist in Shipit's `Repository` table (which is discoverable, e.g. via public Shipit UI/stack listing or brute-forcing well-known org/repo names). No knowledge of the victim's secret is required. This is a low-cost, purely network-based attack (raw HTTP POST to `/webhooks` with a crafted body and a valid `X-Hub-Signature` computed with the attacker's own known secret) and is trivially repeatable/scriptable against many target repositories in rapid succession.

### Recommendation
In `Handler#stacks` (and the `repository` methods in the `pull_request` handlers), verify that the resolved `Repository`'s owner matches the organization that was actually used to validate the webhook signature (e.g. pass `repository_owner` from the controller into the handler and assert `repository.owner == repository_owner` before returning stacks), or alternatively derive `repository_name` for the DB lookup from the same trusted field used for signature routing rather than an independently-controlled JSON key. Reject/no-op (return `Stack.none`) when the two diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "signed webhook for org A cannot mutate a stack owned by org C" do
  stack_c = shipit_stacks(:shipit) # owned by repository with owner "shopify"/whatever fixture uses as C
  victim_full_name = stack_c.repository.full_name # e.g. "shopify/shipit-engine"

  # attacker's own org "acme" is configured in Shipit with a known webhook_secret
  attacker_org = "acme"
  attacker_secret = Shipit.github(organization: attacker_org).instance_variable_get(:@webhook_secret)

  forged_payload = JSON.parse(payload(:push_master))
  forged_payload["repository"]["owner"]["login"] = attacker_org # routes verification to attacker's secret
  forged_payload["repository"]["full_name"] = victim_full_name  # but targets victim's stack
  body = forged_payload.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, body)

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: stack_c.id, expected_head_sha: forged_payload["after"]]) do
    post :create, body: body, as: :json
  end
  assert_response :ok
end
```
Assertion of the broken binding: before the fix, `repository_owner` (`"acme"`, used in `verify_signature`) != `full_name.split('/').first` (`"shopify"`, used in `Repository.from_github_repo_name`) yet the job still enqueues against `stack_c`, proving existence-check ≠ ownership-check. After applying the recommended fix, the same request should yield `Stack.none` / no enqueued job.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
