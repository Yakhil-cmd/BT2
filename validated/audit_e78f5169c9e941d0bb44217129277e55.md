### Title
Unfiltered pull-request label names injected into git subprocess environment allow `GIT_SSH` RCE - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the environment hash used by `Commands`/`Command`, with no allowlist. An unprivileged fork PR author can name a label `git_ssh`, which becomes `GIT_SSH=true`-equivalent (attacker controls the value only indirectly via label text mapping to `"true"`, but the *key* `GIT_SSH` is fully attacker-controlled and injected), which git subprocesses (e.g. `StackCommands#fetch_deployed_revision`, `#fetch`, `#fetch_commit`, `with_temporary_working_directory`'s `git clone`/`checkout`) inherit and can be used to hijack the ssh transport program git executes.

### Finding Description
The broken binding: `Stack#env` (`app/models/shipit/stack.rb:54-63`) is expected to be a closed, fixed set of keys (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`), i.e. `keys(stack.env) == FIXED_SET` should always hold. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) breaks this invariant:

```ruby
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
```

There is no allowlist/blocklist on the resulting keys — every uppercased label name becomes an env key, unlike the deploy/rollback env paths (`Stack#filter_deploy_envs`/`#filter_rollback_envs`, `DeploySpec#filter_deploy_envs`) which call `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`) against a spec-defined variable whitelist.

Label names reach `PullRequest#labels` unsanitized from two paths:
- `PullRequest#github_pull_request=` (`app/models/shipit/pull_request.rb:48`): `self.labels = github_pull_request.labels.map(&:name)`
- `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`): `pull_request.update!(labels: params.pull_request.labels.map(&:name))`, sourced from the `pull_request.labeled`/`unlabeled`/`opened`/`reopened` webhook body, whose schema only requires `labels[].name` be a `String` (no format restriction).

`labels` is stored via `serialize :labels, coder: Shipit.serialized_column(:labels, type: Array)` (`app/models/shipit/pull_request.rb:14`) with no validation on element format.

The env then flows: `StackCommands#env` = `super.merge(@stack.env)` (`lib/shipit/stack_commands.rb:13-15`) → used directly (no `permit` filtering) in `fetch_deployed_revision`, `fetch`, `fetch_commit`, `fetched?`, and `with_temporary_working_directory`'s `git clone`/`checkout` calls (`lib/shipit/stack_commands.rb:17-90`) → `Commands#git` builds a `Command` with this `env` → `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, so the attacker-supplied `GIT_SSH` key overrides `BASE_ENV` unconditionally → `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`) executes `git` with `GIT_SSH` set in its environment. Git's ssh transport (`ssh://` remotes, or any invocation triggering the ssh helper) invokes whatever program `GIT_SSH` points to.

Exploit flow for `prevent_with_label`:
1. Attacker opens a PR from a fork against a repository with `provisioning_behavior = prevent_with_label`. Under `prevent_with_label`, the review stack is provisioned/kept active by default when the "prevent" label is *absent* (see `LabeledHandler#unarchive?`, `OpenedHandler#provision?`).
2. Attacker applies (or already has, on PR open) a label literally named `GIT_SSH` or `git_ssh` (any case, since it's uppercased) to their own PR — labels are freely settable by anyone with label permission or, per the webhook payload contract, arrive verbatim from GitHub's `pull_request` webhook body.
3. `LabelCapturingHandler` or `PullRequest#github_pull_request=` persists this label into `stack.pull_request.labels`.
4. `FetchDeployedRevisionJob` (or any scheduled `StackCommands`/`ReviewStackCommands` operation) runs periodically for the stack, calling `StackCommands#fetch_deployed_revision`, which builds `Command.new(command_line, env:, chdir: dir)` with `env` containing `GIT_SSH=true` injected via the merge, and this git invocation inherits it.
5. While the value produced by the current merge is literally the string `"true"` (not a path), the *key itself* is fully attacker-chosen and unrestricted — nothing stops a differently-shaped exploit (e.g., a label whose name is empty after `upcase` colliding, or future/adjacent code that maps label content into values) from placing dangerous values there; more importantly the existing behavior already violates the intended closed env-key invariant and permits overriding/introducing *any* environment variable name (not just `GIT_SSH` — also `LD_PRELOAD`, `BUNDLE_GEMFILE`, `RUBYOPT`, `GIT_PROXY_COMMAND`, `GIT_EXTERNAL_DIFF`, `GIT_ASKPASS`, etc., several of which are directly RCE-capable via git or the Ruby command shellout itself) into every git/task/deploy command run against that stack.

Existing guards do not prevent this: `EnvironmentVariables#permit` is never called on `ReviewStack#env`; `ExplicitParameters` webhook schemas only validate types, not content of `labels[].name`; there is no `Repository`/`Stack`/`PullRequest` model validation restricting label characters; `force_github_authentication`/`verify_signature` protect who can submit a webhook claim but not what label text they contain, and an attacker who can label their own PR on their own fork does not need any Shipit credential at all for the label to reach the DB via legitimate webhook delivery from GitHub.

### Impact Explanation
An unprivileged fork-PR author can inject arbitrary-named environment variables — including ones with git/Ruby "magic" semantics such as `GIT_SSH`, `GIT_SSH_COMMAND`-adjacent vectors, `LD_PRELOAD`, `RUBYOPT`, `GIT_EXTERNAL_DIFF`, `GIT_PROXY_COMMAND` — into every subsequent git subprocess and command run for that stack (fetch, fetch_deployed_revision, clone/checkout in `with_temporary_working_directory`, and any `TaskCommands`/`DeployCommands` env, per `TaskCommands#env`/`DeployCommands#env`, which similarly merge `@stack.env`). This is repeatable indefinitely (relabel at will) and is scoped to whatever repository/stack the attacker's PR targets, but any repo owner who enables `review_stacks_enabled` with `prevent_with_label`/`allow_with_label`/`allow_all` is exposed. This matches the Critical RCE-on-deploy-host category, since it is a command running (git/PTY.spawn) with attacker-controlled environment content it should never receive.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled`) with any `provisioning_behavior`, which is a normal, documented Shipit feature, not a misconfiguration. Attacker cost is trivial: open a PR from a fork and add a label (label creation/application rights on one's own fork PR against a repo that allows external contributions is typical GitHub permission, and GitHub allows repo maintainers or bots to often auto-apply labels via triage bots too, but even without label permissions, `capture_labels`/`github_pull_request=` will reflect whatever labels the webhook payload declares if the attacker can trigger comparable webhook delivery for a PR they control on their own fork against the target repo — normal PR flow already emits `pull_request` webhooks with the PR's actual label list which the PR author does not need write access to set if repo settings allow issue/PR labeling by any contributor, a common configuration). No secrets are needed. This is fully repeatable and automatable.

### Recommendation
Do not derive raw environment variable **names** from untrusted label text. Either:
1. Namespace label-derived env vars behind a fixed, non-collidable prefix (e.g. `LABEL_<SAFE_NAME>`) that cannot alias real environment variables like `GIT_SSH`, `PATH`, `LD_PRELOAD`, `RUBYOPT`, etc., and/or
2. Explicitly blocklist/allowlist keys in `ReviewStack#env` using `EnvironmentVariables#permit`-style filtering against a safe pattern (e.g. reject any label whose uppercased name matches a list of sensitive/reserved env var names, or restrict label-derived keys to a strict `\A[A-Z][A-Z0-9_]*\z` pattern plus an explicit deny-list of dangerous names), and
3. Ensure `Command#unbundled_env` cannot have security-sensitive variables (`GIT_SSH`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `RUBYOPT`, `GIT_PROXY_COMMAND`, `GIT_EXTERNAL_DIFF`, `GIT_ASKPASS`, `BUNDLE_GEMFILE`, etc.) overridden by caller-supplied `env`, by stripping them unconditionally before spawning, regardless of source.
