### Title
Webhook organization used for signature verification is never bound to the repository the event payload writes to, enabling cross-organization forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In multi-organization mode, `WebhooksController#verify_signature` selects which organization's webhook secret to validate a delivery against using one payload field (`repository.owner.login`, or `organization.login`), while every `Webhooks::Handlers::Handler` subclass resolves which `Stack`/`Repository` to mutate using a *different* payload field (`repository.full_name`). Because these two fields are never cross-checked against each other, an attacker who legitimately knows the webhook secret for their own configured organization can craft a signed payload whose `repository.full_name` points at a completely unrelated organization's repository, causing Shipit to act on that other organization's stack.

### Finding Description
`WebhooksController` picks the GitHub App/secret to verify against like this: [1](#0-0) [2](#0-1) 

`repository_owner` (used only to select `Shipit.github(organization: repository_owner)` and thus which `webhook_secret` validates `X-Hub-Signature`) is read from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`.

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler with the *raw, attacker-controlled* payload. Every handler resolves the target `Stack` via `Handler#stacks`, which uses a **different** field of the same payload: [3](#0-2) 

`repository_name` comes from `payload.dig('repository', 'full_name')`, not from `repository.owner.login`. Nothing in the request pipeline enforces that the organization prefix of `repository.full_name` matches `repository.owner.login`/`organization.login` that was actually used to select and validate the HMAC secret.

In multi-tenant configuration, each organization has its own `webhook_secret` configured under `secrets.github[<org>]` and is looked up via `Shipit.github_app_config`: [4](#0-3) 

This is precisely the scenario where the "organization that authenticated" (whichever org's secret produced a valid HMAC) and "the repository that is written" (`repository.full_name`, used to look up `Repository.from_github_repo_name` and the `Stack`s that get mutated) are two independent, uncorrelated fields inside the same signed JSON body. An attacker who administers/knows the webhook secret for their own onboarded organization ("Org A") can hand-craft the entire JSON payload (since HMAC covers the raw bytes they choose) with `repository.owner.login = "org-a"` (to pass signature verification against Org A's secret) but `repository.full_name = "org-b/private-repo"` (an unrelated tenant's repository already registered in the same Shipit instance). The webhook is accepted, and the handler operates on Org B's `Stack`.

Concrete effects, depending on the event chosen:
- `push` → `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on Org B's stack: [5](#0-4)  — forcing an unauthorized sync/resync of Org B's stack with an attacker-chosen `expected_head_sha`.
- `status` → `StatusHandler#process` creates a `Status` on any commit matching `params.sha` regardless of which stack/org it belongs to: [6](#0-5)  — letting the attacker fabricate a passing CI status (`state`, `context`, `target_url`) on Org B's commit, which can make that commit `deployable?` and enable an unauthorized deploy/merge for Org B.
- `check_suite`/`membership`/`pull_request` handlers follow the same `stacks`/`repository_name` resolution pattern via `Handler#stacks`, all keyed off `repository.full_name` and none of them re-validate it against the organization whose secret authenticated the request.

### Impact Explanation
This breaks the binding: `organization authenticated by HMAC == organization whose repository state is mutated`. In a shared multi-tenant Shipit deployment (the officially supported "multiple GitHub organizations" configuration in `lib/shipit.rb`), a tenant who is a legitimate, unprivileged holder of their own organization's webhook secret can forge webhook deliveries that write to another tenant's stack: forcing resyncs, injecting fabricated commit CI statuses that make an otherwise non-deployable commit `deployable?`, or manipulating merge-queue/team membership state for a repository/organization they have no authorization over. Fabricated passing statuses can directly enable an unauthorized deploy of a foreign stack — this is a cross-repository/cross-tenant write, matching the Critical impact bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured in multi-organization mode with at least two tenant organizations sharing the instance, and (2) the attacker already has legitimate configuration/administrative knowledge of their own organization's `webhook_secret` (a normal, unprivileged capability relative to *other* tenants' data, since Shipit is explicitly designed to host many independent orgs). No access to the victim organization's secret, session, or `ApiClient` token is required — only the ability to send an arbitrary signed HTTP POST to the shared `/github_hooks` (or equivalent) endpoint, exactly like a real GitHub webhook.

### Recommendation
After successfully verifying `X-Hub-Signature` for `repository_owner`, re-derive `repository_name` for authorization purposes strictly from the same organization/owner that was authenticated (e.g., require `payload.dig('repository', 'full_name')` to start with `"#{repository_owner}/"`), or reject the request. In `Handler#stacks`, pass the verified `repository_owner` into handlers and assert equality against the owner segment of `repository_name` before resolving any `Stack`. Never trust `repository.full_name` in isolation to select which tenant's data to mutate when the trust boundary (which secret validated the request) is a separate field.

### Proof of Concept
1. Shipit instance is configured with multi-org secrets: `secrets.github["org-a"]` (webhook_secret known to Org A's admin) and `secrets.github["org-b"]` (unrelated tenant, repo `org-b/private-repo` already registered as a `Stack`).
2. Attacker, who legitimately administers Org A's GitHub App/webhook config, crafts a raw JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/private-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "branches": [{"name": "main"}]
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(secrets.github["org-a"].webhook_secret, raw_body)` and POSTs to the webhooks endpoint with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner = "org-a"`, fetches Org A's app/secret, and the signature validates successfully.
5. `StatusHandler#process` runs on the shared payload, finds `Commit.where(sha: ...)` belonging to `org-b/private-repo`'s stack, and creates a fabricated `success` status on it — without ever touching Org B's actual webhook secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
