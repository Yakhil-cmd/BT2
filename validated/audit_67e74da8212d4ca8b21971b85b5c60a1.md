### Title
Unbounded submodule/recursive processing on `configureWorktree()` enables attacker-pushed-commit content to force permanent sync denial via default `--max-failures=0` - (File: main.go)

### Summary
`Gateway.withBatch()` in the referenced report fails because it accepts an unbounded number of messages into a single batch with no count/size validation on the sending side, letting the resulting payload exceed the receiving chain's gas limit and get permanently stuck. The closest reachable analog in `git-sync` is `configureWorktree()`'s submodule handling, which similarly performs unbounded recursive work driven entirely by attacker-controlled repository content (`.gitmodules`), with no configurable limit on submodule count, nesting depth, or aggregate size, and no way to skip/recover an oversized checkout once it is queued for processing.

### Finding Description
When `git.submodules != submodulesOff`, `configureWorktree()` runs `git submodule update --init` (optionally `--recursive`) against whatever `.gitmodules` content is present at the target commit: [1](#0-0) 

There is no flag or internal check that bounds the number of submodules, the recursion depth, or the total data volume this step can pull in — unlike, e.g., `--depth` which only limits commit history, not submodule fan-out. A confirmed grep for any max-submodule/limit mechanism found none. Because the tracked ref/commit is attacker-controlled content (an attacker who can push a commit to the synced repository, e.g. a compromised or multi-writer upstream), they can add an arbitrarily large or deeply nested submodule graph to force this step to run far longer than intended, exactly mirroring the root cause pattern in the report: no validation on the "batch size" (here, submodule graph) before it is accepted and processed.

Each `git` invocation, including the submodule update, runs under a single `--sync-timeout`-bounded context via `runWithStdin`/`exec.CommandContext`: [2](#0-1) 

If the submodule graph is large enough that `git submodule update --init --recursive` cannot finish within `--sync-timeout` (default 120s), the command is killed and `SyncRepo` returns an error, incrementing `failCount` in the main loop: [3](#0-2) 

Critically, `--max-failures` defaults to `0`, meaning "any sync failure will terminate git-sync": [4](#0-3) [5](#0-4) 

Because `SyncRepo` re-derives `changed` from `currentHash != remoteHash` each loop, and the worktree/checkout never completes successfully, the exact same oversized submodule work is retried on every attempt (bounded only by `--sync-timeout`) — there is no mechanism to detect, skip, or partially process an oversized checkout, just as the reported bug had "no mechanism to skip or split oversized batches."

### Impact Explanation
With default settings, the very first sync against a maliciously crafted commit (excessive/deeply-nested submodules) causes `SyncRepo` to time out, `failCount` to reach `maxFailures` (0), and the process to call `os.Exit(1)`: [5](#0-4) 
This is a persistent sync denial: in the common Kubernetes sidecar/init-container deployment pattern, the container will keep restarting (or block init) against the same poisoned commit, and the application relying on `git-sync`'s atomic `--link` will never receive further updates once this ref becomes current, matching the "persistent sync denial" impact class. Even with `--max-failures` set to retry forever, the sync loop still can never make progress past the poisoned commit, permanently blocking updates — analogous to the reported "batch becomes permanently stuck."

### Likelihood Explanation
This requires an attacker with commit/push access to the tracked repository (or a compromised upstream/MITM able to inject such a commit), which matches the report's own threat model (an attacker constructing message batches accepted by the sending-side function without validation). No credential leakage, malicious-operator, or malicious-node assumption is needed beyond "attacker can push a commit reachable by the configured `--ref`" — this is within the allowed "attacker-pushed commit" analog class.

### Recommendation
Add a configurable limit (e.g., `--max-submodule-depth` / `--max-submodules`) enforced before or during `git submodule update`, and consider running submodule initialization with its own bounded, cancellable step so a single oversized `.gitmodules` graph cannot exhaust the entire `--sync-timeout` budget and drive `failCount` to the default abort threshold. Additionally, consider decoupling "sync attempt failed due to oversized/malicious content" from the generic `--max-failures` counter so operators can detect and quarantine a specific bad commit rather than crash-looping indefinitely.

### Proof of Concept
1. Attacker with push access to the synced repo adds a `.gitmodules` file referencing hundreds of nested submodule repositories (or a deeply chained recursive submodule graph) and commits it to the ref that `git-sync --ref` tracks.
2. `git-sync`, running with default flags (`--submodules=recursive`, `--sync-timeout=120s`, `--max-failures=0`), fetches this commit and calls `configureWorktree()`, which invokes `git submodule update --init --recursive`: [1](#0-0) 
3. The submodule step exceeds `--sync-timeout`; `runWithStdin` returns a `context.DeadlineExceeded` error: [6](#0-5) 
4. `SyncRepo` returns an error, `failCount` becomes 1, `getMaxFailures()` returns 0, so `failCount >= maxFailures` is true and the process exits: [5](#0-4) 
5. Because `--ref` still points to the same poisoned commit, every restart (in a Kubernetes Pod, per its `restartPolicy`) repeats the same timeout-then-exit cycle indefinitely, denying the application container any future synced content.

Note: I could not fully verify runtime behavior (e.g., exact wall-clock time needed to trigger the timeout in practice, or whether `git`'s own internal safeguards mitigate extreme submodule counts) since this requires executing the tool rather than static reading; this assessment is based on the code paths cited above.
