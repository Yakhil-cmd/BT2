### Title
Cross-tenant Status webhook write hits Commits on archived/review-app stacks with no lifecycle filter - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha)` with no scoping by stack lifecycle state (`archived?`) or by the payload's repository, so any commit row sharing the attacker-chosen SHA — including ones belonging to archived stacks or `ReviewStack` fixtures — gets `create_status_from_github!` invoked on it. There is no guard anywhere in the call path (`WebhooksController#create`, `verify_signature`, `drop_unhandled_event`, or `Commit`/`Stack` model validations) that excludes archived/soft-deleted stacks from this write.

### Finding Description
The broken binding: the equality the code implicitly assumes is `commit.stack.archived? == false` for every `commit` mutated by `StatusHandler#process`, but the actual code enforces no such thing — `commit.stack.archived?` can be `true` (or the stack can be a `ReviewStack`) and the write still proceeds.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:10-15` (`create`) only checks `check_if_ping`, `drop_unhandled_event`, and `verify_signature` (which validates the GitHub HMAC signature for the org derived from `repository.owner.login`, not stack state) before dispatching to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.
- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is entirely unscoped by `stack_id`, `repository`, or `stack.archived?` — it matches every `Commit` row across every `Stack` in the database that happens to share the SHA in the payload.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `add_status`, which creates a `Status` row via `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/status.rb:24-33`), and `Status#after_create :enable_ci_on_stack` plus `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:18-19`) fire regardless of whether `commit.stack` is archived or is a `ReviewStack`.
- `add_status` (`app/models/shipit/commit.rb:366-386`) also emits `Hook.emit(:commit_status, ...)` and `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges` on state transitions — again with no archived/lifecycle check.

Attacker request: an unprivileged GitHub user (or any internet client, since `verify_webhook_signature` only checks the HMAC for an org that is often unconfigured/absent — see `verify_webhook_signature` returning `true` when no `webhook_secret` is configured, `lib/shipit/github_app.rb:76-77`) sends `POST /webhooks` with header `X-Github-Event: status` and a JSON body:
```json
{ "sha": "<sha shared with a Commit on an archived/review stack>", "state": "success", "context": "ci/attacker", ... "repository": {"owner": {"login": "<any org configured in Shipit.github_teams/Shipit config>"}} }
```
Because `Commit.where(sha:)` has no repository or stack filter, if any `Commit` in the datastore (belonging to any stack, active or archived, production or review-app) shares that SHA, it receives the injected `Status`.

Why existing guards don't help: `verify_signature` authenticates only that the payload came from a GitHub org configured in Shipit, not that it corresponds to the correct repository/stack; `drop_unhandled_event` only checks the event type is registered; there is no `ExplicitParameters` constraint on `repository.full_name` matching `commit.stack.repository`; and no model-level `default_scope` or association filter on `Stack`/`Commit` excludes archived stacks from lookups by SHA.

### Impact Explanation
An attacker with no Shipit credentials can inject a fabricated CI `Status` (and its downstream `deployable_status`/`commit_status` hooks, `schedule_continuous_delivery`, `schedule_merges`) onto a `Commit` belonging to a stack they do not control and have no relationship to authenticate against — including archived and review-app (`ReviewStack`) stacks, which are typically ephemeral/low-scrutiny environments. This is repeatable against any commit SHA that collides across the datastore (trivially satisfiable if two unrelated repos happen to share a common base/empty-tree commit, or if a low-entropy/test SHA is reused). This matches the "unauthorized deploy" / "payload for one repository mutating another's stack or commit" Critical impact category, and additionally extends the blast radius to stacks the security model might assume are inert (archived) or isolated (review apps), which could re-trigger continuous delivery or merge-scheduling on those stacks unexpectedly.

### Likelihood Explanation
Precondition is a colliding SHA existing between an archived/review stack's `Commit` and the attacker's target SHA — this requires either coincidental SHA collision or an attacker who can observe SHAs used across public repos (e.g., common merge-base/empty commits, or SHAs from public forks that were once synced into a review stack before archival). No Shipit session, API token, or GitHub secret is required; the attacker only needs to know (or guess/observe) a SHA and send an unauthenticated HTTP POST to `/webhooks` with a plausible `repository.owner.login`. The severity of the root cause (`Commit.where(sha:)` unscoped) is identical to the general cross-repository status-write bug; this specific angle only demonstrates it additionally defeats stack lifecycle expectations (archived/review stacks), which is a real but same-root-cause extension rather than a separate vulnerability.

### Recommendation
Scope the lookup to the stack(s) belonging to the repository named in the webhook payload, and exclude archived stacks: e.g. `Repository.find_by(...).stacks.not_archived.joins(:commits).where(commits: { sha: params.sha })`, or filter `Commit.where(sha: params.sha).joins(:stack).where(stack: { repository_id: repository.id }).reject { |c| c.stack.archived? }`. At minimum, add `commit.stack.archived?` and repository-ownership checks inside `StatusHandler#process` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (StatusHandler cross-stack scope)
test ":status webhook mutates Commit on an archived stack sharing colliding sha" do
  archived_stack = shipit_stacks(:shipit) # or a dedicated archived fixture
  archived_stack.update!(archived_since: Time.now) # ensure archived? == true
  colliding_sha = "deadbeef" * 5
  commit = archived_stack.commits.create!(sha: colliding_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  body = { sha: colliding_sha, state: 'success', context: 'ci/attacker' }
         .merge(repository: { owner: { login: 'unrelated-org' } }).to_json

  assert_predicate archived_stack.reload, :archived?
  assert_difference -> { commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  # equality check before/after:
  # BEFORE: commit.stack.archived? == true, commit.statuses.count == 0
  # AFTER:  commit.stack.archived? == true, commit.statuses.count == 1  <-- mutation happened despite archived stack
end
```

      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
