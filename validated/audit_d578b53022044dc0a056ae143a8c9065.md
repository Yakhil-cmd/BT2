I found a concrete instance of the reported bug class — `app/controllers/shipit/api/ccmenu_controller.rb` — where a stack-scoped `ApiClient` authorization is bypassed because the `stack` lookup does not reuse the token's authorized scope, exactly analogous to the "monopoly check" that didn't account for previously-proposed validators (a guard checked against the wrong/incomplete state).

### Title
CCMenu API controller resolves the target stack without enforcing the API token's stack scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController#stack` restricts lookups to `current_api_client.stack_id` when the token is scoped to a specific stack, but `Api::CCMenuController` overrides `#stack` with its own implementation that queries `Stack.from_param!` directly, ignoring the token's `stack_id` scope entirely.

### Finding Description
The base API controller defines the deployment-trust binding "stack a token authorizes == stack a token touches" via: [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves through that filtered relation (`stacks.from_param!`). This is the check that is supposed to hold for every request, the same way `MONOPOLY_THRESHOLD` was supposed to hold for every `proposeStake` call.

`Api::CCMenuController`, however, defines its own `stack` method that bypasses the scoped `stacks` relation: [2](#0-1) 
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```
This directly parallels the original bug: a guard (`stack_id` scoping / `MONOPOLY_THRESHOLD`) exists and is enforced in one code path (`BaseController#stack`, the initial `proposeStake` check) but a second code path (`CCMenuController#stack`, the second `proposeStake` call / `beaconStake` approval) performs the sensitive operation (`stack.deploys_and_rollbacks.last`) using unscoped state (`Stack.from_param!` over *all* stacks), never re-checking the token's authorized `stack_id`.

Because `CCMenuController` only requires `read:stack` permission and authenticates via a query-string `token` (as also demonstrated in the test file), any holder of a stack-scoped CCMenu token (which is deliberately generated with minimal `read:stack` permission and handed out via `CCMenuUrlController` for embedding in outward-facing CI dashboards) can substitute an arbitrary `stack_id` in the URL and read status/build data for any stack in the installation, not just the one the token was scoped to: [3](#0-2) [4](#0-3) 

### Impact Explanation
This breaks the "stack a token authorises versus a stack it touches" binding and yields unauthenticated (relative to the intended scope) read access to task streams / deploy output / stack state for stacks outside the token's authorized scope — matching the High-impact category "escalation into `Shipit.github_teams` authorization ... or unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Likelihood is high: the CCMenu token is specifically designed to be low-privilege and widely distributed (embedded in CI dashboard tools such as CCMenu clients), so an attacker who legitimately obtains one stack's CCMenu token (e.g., from a public CI dashboard config) only needs to change the `stack_id` route segment to read other stacks' data. No signature, private key, or session is required — only the disclosed CCMenu token for one stack.

### Recommendation
Remove the overriding `stack` method in `Api::CCMenuController` (or reimplement it using the inherited `stacks` relation instead of the unscoped `Stack.from_param!`), so that a stack-scoped token can only resolve to the stack it was minted for, consistent with `Api::BaseController#stack`.

### Proof of Concept
1. As an authorized user, request a stack-scoped CCMenu URL for `stack-A` via `GET /ccmenu/stack-A` (`CCMenuUrlController#fetch`), obtaining a token whose `ApiClient` has `stack_id = stack-A.id` and `permissions = ["read:stack"]`. [5](#0-4) 
2. Using that token, issue `GET /api/stacks/*stack-B*/ccmenu?token=<token>` where `stack-B` is a different stack in the same Shipit instance.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing the `stack_id`-scoped `stacks` relation from `BaseController`), the request succeeds and returns `stack-B`'s CI/deploy status XML, even though the token was only authorized for `stack-A`.
