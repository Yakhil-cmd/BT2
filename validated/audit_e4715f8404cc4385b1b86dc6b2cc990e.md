Confirmed: the field used to select the verifying webhook secret (`repository.owner.login`, or `organization.login`) is a different JSON field from the one used by the actual write logic (`repository.full_name`, consumed via `Handler#repository_name` and `Repository.from_github_repo_name`). This is exactly the "organization that authenticated versus the repository that is written" binding break called for in the rules.

### Title
Webhook signature is verified against the org named in `repository.owner.login`/`organization.login`, but writes are keyed off the independent `repository.full_name` field, allowing a valid webhook sender for one organization to forge events against another organization's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which HMAC `webhook_secret`) to validate the inbound payload against using `repository_owner`, which is read from the attacker-controlled JSON body itself (`params.dig('repository', 'owner', 'login')` or the `organization.login` fallback), not from any GitHub-verified, out-of-band identifier. [1](#0-0)  Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` processes the entire raw JSON body, and the base `Handler` resolves the target repository/stack using a *different* field, `repository.full_name`. [2](#0-1)  `Repository.from_github_repo_name` splits that string on `/` to find the `owner`/`name` row to act on. [3](#0-2) 

### Finding Description
In a multi-organization Shipit deployment (documented, supported configuration shape shown in `config/secrets.development.example.yml` and exercised by `test/dummy/config/secrets_double_github_app.yml`), each onboarded GitHub organization gets its own `GitHubApp` instance with its own independent `webhook_secret`, keyed by organization name. [4](#0-3)  `Shipit.github(organization:)` looks up per-organization config and constructs a `GitHubApp` whose `verify_webhook_signature` HMACs the raw body with *that organization's* secret. [5](#0-4) 

The controller selects which organization's secret to use purely from a value inside the same unauthenticated payload it is trying to authenticate:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

This is a legitimate design point (each org should sign with its own secret), but the *equality that must hold* is: `organization whose secret validated the HMAC == organization that owns the repository actually mutated by the handler`. That equality is never enforced. The handler layer resolves the mutated `Repository`/`Stack` from an entirely separate JSON field, `repository.full_name`: [7](#0-6)  and `Repository.from_github_repo_name` blindly splits that attacker-controlled string on `/` to find the owner/name row: [3](#0-2) 

Because `repository.owner.login` (used to pick the signing key) and `repository.full_name` (used to pick the row being written to) are two independent fields inside the same signed byte string, an attacker who legitimately controls a webhook secret for **their own** organization ("OrgA", e.g. because they are the GitHub App admin who configured that org's installation, as documented in `docs/setup.md`) can construct an arbitrary JSON body where:
- `organization.login` / `repository.owner.login` = `"OrgA"` (so `verify_signature` selects OrgA's `GitHubApp` and correctly HMACs against OrgA's secret, which the attacker knows), and
- `repository.full_name` = `"OrgB/some-repo"` (an unrelated, victim organization's repository/stack hosted on the same shared Shipit instance).

The HMAC will validate (it was computed correctly with OrgA's secret over this exact body), the controller accepts the request, and the handler dispatches on `full_name`, acting on OrgB's `Stack` — e.g. triggering `GithubSyncJob`/`sync_github` on a push event [8](#0-7) , capturing/removing PR labels on an unrelated stack via `pull_request` handlers, closing/merging PRs, or manipulating commit statuses/check runs for a repository OrgA has no relationship to.

### Impact Explanation
This breaks the org-isolation model of a shared multi-tenant Shipit instance: possession of a valid webhook secret for organization A becomes sufficient to forge deployment/PR/status/merge-affecting webhook events for organization B's stacks, purely by mismatching two payload fields. Depending on which handler is triggered this ranges from forced `sync_github` (which can advance/trigger deploy eligibility state) to PR close/label/merge handlers acting on a foreign repository — i.e., unauthorized cross-repository writes / triggering deploy-adjacent state changes on a stack the caller does not control, which matches the "cross-repository writes" / "unauthorized deploy" high-impact class defined in scope.

### Likelihood Explanation
Requires only that the attacker be an org admin for *any one* GitHub App organization already onboarded onto a shared Shipit instance (a normal, low-privilege tenant of the platform, not a Shipit server admin, not requiring `GITHUB_TOKEN`/`api_clients_secret`/private key theft). No GitHub Enterprise/organization write access to the victim repo is needed at all — only knowledge of one's own org's webhook secret, which the tenant necessarily possesses/configures.

### Recommendation
After signature verification, re-derive the organization/owner from the same field(s) used for the actual write (`repository.full_name` / `repository.owner.login` should be the *same* field consistently, or the handler must independently verify that the resolved `Repository#owner` matches the organization key that successfully validated the signature) before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
1. Configure a shared Shipit instance with two organizations, `OrgA` and `OrgB`, each with distinct `github.webhook_secret` values (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the admin of OrgA's GitHub App (who legitimately knows OrgA's `webhook_secret`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST it to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against OrgA's secret. [9](#0-8) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `sync_github` on OrgB's stack — a write the attacker had no authorization to trigger. [8](#0-7) [3](#0-2)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
