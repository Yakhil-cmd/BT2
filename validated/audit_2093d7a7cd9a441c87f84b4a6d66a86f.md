### Title
Organization identity used for webhook signature verification is not bound to the repository the payload actually targets - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate a request against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`), but `Webhooks::Handlers::Handler#stacks` (used by every handler, including `PushHandler`) resolves the target `Stack`/`Repository` from a *different* field of the same payload, `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a valid signature computed with organization B's webhook secret can be paired with a `repository.full_name` pointing at a repository belonging to organization A.

### Finding Description
The controller picks the app/secret to verify with based on `repository_owner`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only proves that the raw JSON body was HMAC-signed by the holder of the secret configured for that `repository_owner` organization — it says nothing about which repository's data the body may legitimately contain: [3](#0-2) 

Once signature verification passes, every handler resolves the affected stacks from a completely separate field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) 

`PushHandler`, for example, uses that repository-name-derived `stacks` scope to enqueue a sync with an attacker-chosen `after` SHA: [5](#0-4) 

Because the whole JSON body is HMAC-signed, forging the body's content is not possible without the secret — but the secret only needs to belong to organization B ("owner.login": "org-B"), while `repository.full_name` inside the *same body* can be set to `"org-A/target-repo"`. The controller only checks that the signature matches whatever secret was picked for `repository_owner` ("org-B"); it never asserts that `repository.full_name` starts with `repository_owner`.

This breaks the intended binding: *the organization whose credential authenticated the webhook* vs. *the repository whose stacks are actually written to*.

### Impact Explanation
Shipit is explicitly designed to support multiple GitHub organizations configured independently in `config/secrets.yml`, each with its own app/webhook secret: [6](#0-5) 

An operator who legitimately controls the webhook secret for one configured organization (org B) — a valid, authenticated principal from Shipit's perspective, but only for org B's repositories — can craft an arbitrary JSON body, set `repository.owner.login` to `org-B` and `repository.full_name` to any other repository the same Shipit instance tracks (e.g., `org-A/prod-app`), then sign it with org B's secret. `verify_signature` succeeds (it validates against org B's secret), and the `PushHandler` will then locate stacks for `org-A/prod-app` and enqueue `GithubSyncJob` with an attacker-supplied `expected_head_sha`, causing cross-organization/cross-repository state changes (triggering syncs, and depending on downstream logic in `Stack#sync_github`, potentially influencing what SHA is considered deployable) on a repository the attacker has no legitimate authority over. This is a cross-repository write achieved purely by holding credentials scoped to a different, unrelated repository/organization — squarely a "cross-repository writes" class impact.

### Likelihood Explanation
Requires that the Shipit deployment be configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker controls (or has compromised) the webhook secret for at least one of those organizations — which does not require any privilege over the target organization/repository. Given Shipit's own docs promote and describe this exact multi-org setup, likelihood is realistic wherever it's used, though it is not exploitable against a single-organization deployment (there is only one secret to match).

### Recommendation
In `Handler#stacks` / `Handler#repository_name`, validate that `payload.dig('repository', 'owner', 'login')` (the identity used to select the verifying secret) matches `payload.dig('repository', 'full_name')`'s owner segment before resolving stacks, or better, pass the already-verified `repository_owner` from the controller into the handler and use it (rather than trusting the unrelated `full_name` field) to scope the repository lookup.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.yml`: `org-A` (target, secret unknown to attacker) and `org-B` (attacker knows/controls its webhook secret, e.g. because they administer a GitHub App they installed for their own org, or the secret leaked).
2. Attacker builds JSON body:
```json
{
  "repository": { "full_name": "org-A/target-repo", "owner": { "login": "org-B" } },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(org_B_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-B"`, fetches `Shipit.github(organization: "org-B")`, and successfully verifies the signature against org B's secret.
5. `PushHandler#process` calls `stacks` → `Handler#repository_name` → `payload.dig('repository', 'full_name')` = `"org-A/target-repo"`, resolving stacks belonging to `org-A`, and enqueues `GithubSyncJob` with the attacker-supplied `after` SHA for those stacks — despite the attacker never having any credential tied to `org-A`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
