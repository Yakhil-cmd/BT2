### Title
Cross-repository commit-status injection via SHA-only matching in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves target `Commit` records solely by SHA, without restricting the match to the repository named in the webhook payload. This breaks the binding "organization that authenticated == repository that is written": GitHub's webhook signature only proves the payload originated from a legitimately configured organization/repository, not that the commit being mutated belongs to that same repository.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config (and thus the secret used to validate `X-Hub-Signature`) using `repository_owner`, taken from the payload's `repository.owner.login` field [1](#0-0) [2](#0-1) . This only proves the request came from GitHub for *that* organization's installed app — it says nothing about which repository's data may be written.

The base `Handler` class exposes a `stacks` helper that correctly scopes to the repository named in the payload via `Repository.from_github_repo_name(repository_name)` [3](#0-2) , and `PushHandler` uses this scoping correctly [4](#0-3) .

However, `StatusHandler#process` bypasses this scoping entirely and instead queries commits globally by SHA:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

Because Git SHAs are content-addressed and are shared across forks (and can even coincide for unrelated repositories that share history), any repository whose `status` event validly authenticates (i.e., any org/repo with the Shipit GitHub App installed, or any org configured in `Shipit.github`) can cause a `CommitStatus` to be attached to a `Commit` belonging to a completely different Stack/repository, as long as the SHA values collide. The payload's own `repository` field is never used to filter which `Commit` rows are eligible.

### Impact Explanation
This is a cross-repository write: an attacker who controls (or has push/status-setting rights to) any repository onboarded to the Shipit instance can inject a fabricated `CommitStatus` (arbitrary `state`, `context`, `description`, `target_url`) onto a commit belonging to a victim Stack in a different repository/organization, without ever needing credentials for that victim repository. Commit statuses feed into Shipit's deployability and merge-queue decisions, so this can be used to mark unrelated commits as passing/failing checks, potentially unblocking (or blocking) deploys/merges for a Stack the attacker does not otherwise have any relationship with. This matches the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Exploitability requires the attacker to get GitHub to send a legitimately signed `status` webhook whose `sha` collides with a commit tracked by the victim Stack. The most practical path is forking the victim's public repository (fork commits share the exact same SHA as the upstream repository) and posting a commit status via the GitHub API against a commit in that fork — GitHub will deliver a validly signed webhook for the attacker's own (forked) repository/org. No secrets, no elevated GitHub permissions, and no interaction with the victim repository are required beyond having Shipit's GitHub App installed/reachable and a fork containing the target commit.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository identified in the payload (via the same `stacks`/`Repository.from_github_repo_name(repository_name)` mechanism already used elsewhere), e.g. `stacks.commits.where(sha: params.sha)` or by joining through `Stack#repository` to ensure the payload's `repository` field constrains which commits can be mutated, matching the pattern already used correctly in `PushHandler`.

### Proof of Concept
1. Attacker forks a public repository that backs a Shipit-tracked `Stack` (repository `victim/target`), obtaining an identical commit SHA `abc123...` in their fork `attacker/target`.
2. Attacker (owner of `attacker/target`, with the Shipit GitHub App installed on their own org) sets a commit status via the GitHub Statuses API on `abc123...` in `attacker/target` with `state: success`.
3. GitHub sends a `status` webhook to Shipit signed with `attacker`'s org webhook secret; `WebhooksController#verify_signature` validates it successfully since it correctly matches `attacker`'s org config.
4. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which matches the commit in `victim/target`'s Stack (same SHA, unrelated repository), and calls `create_status_from_github!`, writing an attacker-controlled status onto the victim's commit. [5](#0-4)
