### Title
Cross-organization webhook forgery via organization/repository binding mismatch in webhook signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to validate `X-Hub-Signature` based on `repository.owner.login` (or `organization.login`) extracted from the **unverified** JSON body, while every downstream `Handler` locates the target `Stack`/`Commit` using `repository.full_name` (or, for `StatusHandler`, no repository scoping at all). Nothing ties the *organization whose secret authenticated the request* to the *repository the handler actually mutates*, so a party who legitimately controls the webhook secret for **any one** organization configured in the Shipit instance can forge signed events that are processed against **any other tracked repository**.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#verify_signature` does: [1](#0-0) 

`repository_owner` is read straight from the untrusted body before the signature is checked: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization `GitHubApp` instance with its own `webhook_secret` (Shipit supports multiple GitHub organizations, each with an independently configured secret, as documented in `config/secrets.development.example.yml`). `verify_webhook_signature` only proves the raw body was HMAC-signed with **that particular organization's** secret: [3](#0-2) 

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full, attacker-controlled JSON body to handlers, none of which re-check that the `owner.login` used for authentication matches the repository they act on: [4](#0-3) 

The base `Handler` resolves the target stacks purely from `repository.full_name` in the payload: [5](#0-4) 

`PushHandler` triggers a GitHub sync for any stack matching that (attacker-chosen) `full_name`/branch: [6](#0-5) 

`StatusHandler` is worse: it does not scope by repository at all, it matches on commit SHA globally and writes a `Status` record from the forged payload: [7](#0-6) 

**Binding that is broken (equality that should hold but doesn't):**
`organization authenticated by verify_webhook_signature (repository.owner.login)` ≠ `repository/stack acted upon by the Handler (repository.full_name / bare commit sha)`.

This is the direct analog of the reported bug class: a value the code trusts to authorize an action (the increased allowance / here, the organization whose secret validated the signature) is not the same value the subsequent privileged operation actually targets (the arbitrary external call / here, an arbitrary tracked repository's stack or commit).

### Impact Explanation
Anyone who legitimately administers, or has captured a valid webhook secret for, **one** GitHub organization tracked by this Shipit instance can forge signed webhook deliveries that are accepted and processed against **any other organization/repository** also tracked by the same instance:
- Forge a `status` event with `state: "success"` for an arbitrary commit SHA belonging to a repository they do not control, satisfying `release_status?` safety gates and enabling an **unauthorized deploy** of that stack.
- Forge a `push` event for another org's tracked repository to force `sync_github`/`GithubSyncJob` against arbitrary refs.
- Forge `membership`/`check_suite` events to manipulate `Team`/`Membership` records or CI check state for repositories outside the attacker's own organization, escalating into `Shipit.github_teams` authorization decisions.

This satisfies the "unauthorized deploy" / "escalation into `Shipit.github_teams` authorization" High/Critical impact criteria without requiring a Shipit session, `ApiClient` token, or repository write access on the victim repository — only knowledge of one's own organization's webhook secret, which the engine itself expects organization operators to hold.

### Likelihood Explanation
Any deployment that tracks stacks/repositories across more than one GitHub organization (a supported and documented configuration, per `config/secrets.development.example.yml`'s multi-org `github:` block) is exposed. No collusion or GitHub-side compromise is required beyond what the attacker already legitimately has for their own organization — the request is a plain POST to `/webhooks` with a body they fully control and a signature they can correctly compute themselves.

### Recommendation
After verifying the signature, re-derive and enforce that `repository.owner.login`/`organization.login` used to select the signing secret matches the actual `repository.full_name`'s owner for every payload processed by a `Handler`, or scope `StatusHandler`/other handlers' lookups by the authenticated organization instead of trusting bare `sha`/`full_name` fields from the body.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `AttackerOrg` (attacker-administered, webhook secret known to the attacker) and `VictimOrg` (tracks a stack the attacker has no access to), per the multi-org `github:` config format.
2. Attacker crafts body:
```json
{
  "repository": {"owner": {"login": "AttackerOrg"}, "full_name": "VictimOrg/victim-repo"},
  "sha": "<sha of a real commit on VictimOrg/victim-repo>",
  "state": "success",
  "context": "ci/attacker-forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_secret, body)>` and sends `POST /webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and validates successfully because the attacker signed with their own known secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, creating a forged "success" status on `VictimOrg/victim-repo`'s commit — potentially unblocking an unauthorized deploy for a stack the attacker never had access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
