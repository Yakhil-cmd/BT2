This confirms the finding decisively. The base `Handler` class provides a `stacks` helper method that properly scopes lookups to the repository named in the payload via `Repository.from_github_repo_name(repository_name)&.stacks`, and `PushHandler#process` correctly uses it: [1](#0-0) [2](#0-1) . `StatusHandler#process`, however, bypasses this scoping entirely and queries `Commit` globally by `sha` alone: [3](#0-2) . The database schema confirms `sha` is only unique per `(sha, stack_id)`, not globally, meaning two different stacks/organizations legitimately can hold `Commit` rows with an identical `sha`: [4](#0-3) .

### Title
Cross-organization Status forgery via sha-only commit lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` correctly authenticates that a webhook payload was signed by the GitHub App belonging to the organization named in `payload['repository']['owner']['login']`, but this only proves *who sent the event*, not *which Commit rows may be mutated*. `StatusHandler#process` then updates every `Commit` row across the entire database whose `sha` matches the attacker-controlled `params.sha`, with no repository or organization scoping, so a status event validly signed by org A's `webhook_secret` for `org-a/repo` can create/replicate a `Status` on a `Commit` belonging to org B's `Stack` if the two commits happen to share a sha.

### Finding Description
Binding claimed: `webhook_secret owner (org A)` == `organization owning the Stack/Commit mutated`.

Trace:
1. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from `params.dig('repository', 'owner', 'login')` and verifies `X-Hub-Signature` against that org's `webhook_secret`. [5](#0-4)  This only proves the request came from org A's GitHub App installation for whichever repository name org A puts in the payload — GitHub lets the *sending* org sign any payload body it wants; the `repository.full_name`/`repository.owner.login` fields are attacker-controlled content within the JSON body signed by org A's own secret, not cross-checked against Shipit's stored `Repository`/`Stack` ownership.
2. `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event('status')` → `[Handlers::StatusHandler]`. [6](#0-5) 
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never calls the `stacks` helper (which would properly scope by `Repository.from_github_repo_name(repository_name)`) and never filters by `payload['repository']`. [3](#0-2) 
4. `Commit#create_status_from_github!` unconditionally creates a `Status` for that commit and calls `add_status`, which fires hooks, may schedule merges/CD, and updates the commit's cached state — mutating org B's `Stack` state as a side effect. [7](#0-6) [8](#0-7) 
5. `sha` is only unique per `(sha, stack_id)` in the schema, confirming two `Stack`s (potentially owned by different organizations, e.g. both forked from the same upstream commit) are permitted to legitimately hold identical-sha `Commit` rows. [4](#0-3) 

The attacker's exact request: an org-A-controlled webhook sender (or, more directly, anyone who can trigger a "status" event from a repository installed under org A's GitHub App — e.g., a CI integration on their own `org-a/repo`) POSTs to `/webhooks` with `X-Github-Event: status`, `X-Hub-Signature` computed with org A's `webhook_secret`, and a JSON body `{"repository": {"owner": {"login": "org-a"}}, "sha": "<shared-sha>", "state": "success", ...}`. Because `params.sha` matches org B's commit too, `Commit.where(sha: ...)` returns both rows and both get a new `Status`.

Why existing guards fail: `verify_signature` authenticates the sender org but is never re-checked against which `Commit`/`Stack` rows get touched; `ExplicitParameters` schema (`requires :sha, String`) only validates type/presence, not ownership; there is no `stacks`/`Repository.from_github_repo_name` scoping in `StatusHandler`, unlike the sibling `PushHandler`, `CheckSuiteHandler`, and PR handlers which correctly scope via `stacks`.

### Impact Explanation
Any organization with its own valid Shipit GitHub App installation (attacker fully controls org A, its own repo, and can emit a legitimate signed webhook from GitHub for events on that repo, e.g. by pushing a commit with the desired sha and having a CI system post a status, or via any repository they administer under that org) can write arbitrary `Shipit::Status` rows (state, description, context, target_url, created_at — all attacker-supplied fields per `Status.replicate_from_github!`) onto **any other tenant's** `Commit` that happens to share a sha, without ever possessing org B's secrets. This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or team": forging a `success` status can unlock `stack.schedule_merges`/continuous-delivery hooks (`add_status` triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`), potentially causing an unauthorized deploy/merge on org B's stack. [9](#0-8)  The precondition of a colliding sha is realistic in the stated scenario (shared upstream fork history, unmerged/undiverged commits, or common vendored dependency commits), and is fully repeatable — attacker can pick any sha value it wants for its own repository and simply hope/arrange for a collision, or (more strongly) if any other tenant ever adds a commit whose sha matches one the attacker controls (e.g., an empty/well-known commit, a common merge-base, or a widely shared open-source commit sha) the forged event lands.

### Likelihood Explanation
Preconditions: attacker needs (a) their own repository/org onboarded to the same Shipit instance with a legitimate GitHub App installation (already assumed as "unprivileged GitHub user who can push to a fork and emit webhooks from a repository they own" per the threat model — note: they need Shipit to have a Stack tracking *their* repo too, or simply to control the raw signed payload via GitHub's own webhook delivery for their installed repo), and (b) sha collision with a target commit in another tenant's Stack. No possession of org B's `webhook_secret` or any Shipit credential is required — this is exactly the scenario the question describes. The cost is a single crafted/triggered webhook POST; it is trivially repeatable against any sha the attacker can arrange to share.

### Recommendation
Scope `StatusHandler#process` (and any other handler using bare `Commit.where(sha: ...)`/similar global lookups) to the repository identified in the payload, mirroring `PushHandler`/`CheckSuiteHandler`'s use of the `stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the org authenticated by `verify_signature` can only mutate `Commit`/`Status` rows belonging to `Stack`s under `Repository.from_github_repo_name(repository_name)` for that same organization.

### Proof of Concept

```ruby
test "status event for org A repo does not mutate org B's commit with same sha" do
  repo_a = shipit_repositories(:shipit)   # owner: shopify/org-a equivalent
  repo_b = Shipit::Repository.create!(owner: 'org-b', name: 'other-repo')
  stack_b = Shipit::Stack.create!(repository: repo_b, environment: 'production')

  shared_sha = 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'
  commit_a = shipit_stacks(:shipit).commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => repo_a.github_repo_name, 'owner' => { 'login' => 'org-a' } },
    'branches' => [{ 'name' => 'master' }]
  }

  before_a = commit_a.statuses.count
  before_b = commit_b.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal before_a + 1, commit_a.reload.statuses.count   # expected mutation
  assert_equal before_b, commit_b.reload.statuses.count       # MUST remain unchanged; currently FAILS (also incremented)
end
```
With the current implementation this test fails because `commit_b.statuses.count` also increases, proving org A's signed payload mutated org B's `Commit`/`Stack` state.
