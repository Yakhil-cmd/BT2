### Title
Stale Votes from Deregistered Bridge Operators Enable Threshold Bypass for Value Transfer — (`contracts/service_chain/bridge/BridgeOperator.sol`)

### Summary
`BridgeOperator.deregisterOperator` removes an operator from the active set but does not revoke their outstanding votes. A deregistered operator's vote count persists in `voteCounts`, allowing a value transfer to execute with fewer currently-authorized operators than `operatorThresholds` requires — the exact stale-count-vs-actual-state invariant broken in the HatsSignerGate report.

### Finding Description
`_voteCommon` determines whether a vote threshold is met by reading the live `operatorThresholds` value against the accumulated `voteCounts`:

```solidity
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
``` [1](#0-0) 

When an operator is deregistered, `deregisterOperator` removes them from `operators` and `operatorList` but performs no cleanup of the `votes` mapping:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    // operatorList shrink ...
    // votes[*][*].voteCounts NOT touched
}
``` [2](#0-1) 

The code itself documents the resulting invariant break:

> *"Note that outstanding votes by the deregistered operator are not revoked. This enables a subtle counterintuitive scenario … the request was executed with A's vote after A is deregistered."* [3](#0-2) 

The parallel to HatsSignerGate is direct:

| HatsSignerGate | Kaia BridgeOperator |
|---|---|
| `signerCount` not reconciled before `claimSigner` | `voteCounts` not decremented on `deregisterOperator` |
| Stale count lets `validSignerCount > maxSigners` | Stale count lets threshold be reached with fewer live operators |
| `reconcileSignerCount` reverts → DOS | Transfer executes with sub-threshold live authorization |

The `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` functions all route through `_voteValueTransfer` → `_voteCommon`, so every asset type is affected. [4](#0-3) 

### Impact Explanation
A KAIA, ERC-20, or ERC-721 value transfer is executed on the child bridge with fewer currently-authorized operators than `operatorThresholds[ValueTransfer]` requires. The corrupted value is the bridge's locked asset balance: tokens or native KAIA are released to the recipient address with insufficient live-operator authorization. If the owner deregisters a compromised operator specifically to block a pending transfer, that transfer can still execute the moment any remaining operator votes, defeating the revocation entirely.

### Likelihood Explanation
Medium. The scenario arises whenever an operator is deregistered while a matching open vote exists — a realistic operational event (key compromise, operator rotation). No special chain state is required beyond a bridge with ≥2 operators and threshold ≥2. The remaining operator's vote is a normal, unprivileged bridge operation.

### Recommendation
In `deregisterOperator`, iterate over all open nonces and decrement `voteCounts` for any vote cast by the departing operator, mirroring the re-vote path already present in `_voteCommon`:

```solidity
// pseudocode
bytes32 oldKey = votes[voteType][nonce].voted[_operator];
if (oldKey != bytes32(0)) {
    votes[voteType][nonce].voteCounts[oldKey]--;
    delete votes[voteType][nonce].voted[_operator];
}
```

Alternatively, require that no open votes exist for the operator before allowing deregistration, forcing the owner to wait for in-flight votes to settle.

### Proof of Concept
1. Deploy bridge; operators = {A, B, C}, `operatorThresholds[ValueTransfer] = 2`.
2. Operator A calls `handleKLAYTransfer(nonce=N, to=X, value=1000)` → `voteCounts[voteKey] = 1`. [5](#0-4) 
3. Owner discovers A is compromised; calls `deregisterOperator(A)` → A removed from `operators`/`operatorList`, but `voteCounts[voteKey]` remains **1**. [6](#0-5) .
- Although `deregisterOperator` explicitly notes that "outstanding votes by the deregistered operator are not revoked" [7](#0-6) , this is a documented design choice for grace periods rather than an accounting error.
- The `_voteCommon` function manages per-nonce vote counts by tracking individual voters in a mapping (`vote.voted[msg.sender]`), ensuring that if a voter changes their vote, the previous count is correctly decremented before the new one is incremented [8](#0-7) .
- There is no equivalent to a `reconcileSignerCount` function that performs a "sanity check" revert if the number of voters exceeds the threshold; instead, the threshold acts as a minimum requirement for execution [9](#0-8) .

Other modules, such as the `Valset` module, manage validator transitions through a pure-function pipeline (`ApplyAllTransitions`) that recomputes slot limits and active counts based on the current block's state rather than relying on stale cached counters [10](#0-9) .

    // _voteCommon handles common functionality for voting.
    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }
```
