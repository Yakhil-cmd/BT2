### Title
Missing `return` after `getBase64Hash` failure causes double invocation of `async.each` completion callback in private payment handling - (File: network.js)

### Summary
In `handleSavedPrivatePayments()`, the `validateAndSave` closure catches an exception from `objectHash.getBase64Hash()` but fails to `return` afterward, allowing control to fall through to a second, independent code path that also eventually invokes the same `cb` for the `async.each` iterator — mirroring the kernel bug class where an error path performs a manual decrement/cleanup and then falls through into normal cleanup logic that performs it again.

### Finding Description
`handleSavedPrivatePayments()` iterates unhandled private-payment rows with `async.each`, and for each row calls `validateAndSave()`: [1](#0-0) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g. because the head private element's `payload` is malformed/undefined/circular — content fully controlled by whoever sent the private payment: a paired device or private-payment counterparty), the `catch` block does:
- optionally `sendResult(ws, ...)`
- `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which asynchronously calls `cb()` once the DB delete completes: [2](#0-1) 

But there is no `return` statement ending the `catch` block, so execution continues to compute `key` (using the now-`undefined` `json_payload_hash`) and unconditionally calls: [3](#0-2) 

`privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` will invoke exactly one of `ifOk`, `ifError`, or `ifWaitingForChain`, each of which itself calls `cb()` (directly, or via a second `deleteHandledPrivateChain(...)` call). The net effect is that `cb` — the completion callback for that `async.each` item — is invoked twice for a single iteration, exactly analogous to the kernel patch's root cause: an error-handling branch performs cleanup and then falls through into the normal-path cleanup that repeats it, instead of returning immediately.

### Impact Explanation
`async.each`'s final callback fires once all per-item `cb`s have been called once each; calling one item's `cb` twice causes the group callback (`function(){ unlock(); ... }` at line 2512-2517) to fire prematurely/again while other items may still be mid-flight, and releases the `["saved_private"]` mutex early. This can cause `unlock()` to run out of order relative to still-in-flight `db.query`/`validateAndSavePrivatePaymentChain` operations on `unhandled_private_payments`, and lets a second concurrent invocation of `handleSavedPrivatePayments` (or other users of the `saved_private` lock) proceed while the first pass is still processing rows, racing against the same `unhandled_private_payments` DELETE/SELECT statements. This can result in duplicate or out-of-order handling of a private payment chain (double invocation of `deleteHandledPrivateChain`, out-of-order `eventBus.emit(key, ...)`, or acceptance of a private-payment chain while overlapping processing runs), which is a data-integrity/double-processing hazard in the private-payment acceptance path rather than a clean, single-pass validate-then-commit flow.

### Likelihood Explanation
Triggering this requires only that a peer/paired device send a private payment whose head element's `payload` cannot be hashed by `getJsonSourceString`/`getSourceString` (e.g., a payload containing a value that JSON-stringification or hashing chokes on, such as circular structures, `undefined`, or unsupported types) — reachable by any private-payment counterparty via the normal encrypted device-message flow that populates `unhandled_private_payments`, without needing network-level or hub-level privileges. However, this requires constructing a payload that `getJsonSourceString`/`getSourceString` cannot process while still passing earlier deserialization (`JSON.parse(row.json)`), which narrows likelihood — exact conditions under which `getBase64Hash` throws for a legitimately-shaped private-payment payload were not fully verified within tool budget.

### Recommendation
Add a `return` at the end of the `catch` block in `validateAndSave` (network.js, inside `handleSavedPrivatePayments`) so that after `deleteHandledPrivateChain(...)` is scheduled on hash failure, execution does not fall through to also call `privatePayment.validateAndSavePrivatePaymentChain(...)`, avoiding the double `cb()` invocation for that `async.each` item.

### Proof of Concept
1. As a paired device / private-payment counterparty, send a private payment chain whose head element (`arrPrivateElements[0]`) has a `payload` value that causes `objectHash.getBase64Hash(payload, true)` (via `getJsonSourceString`) to throw (e.g. a payload field that is not JSON-serializable in the expected way).
2. The row lands in `unhandled_private_payments` and `handleSavedPrivatePayments()` is invoked (directly or via periodic re-scan).
3. In `validateAndSave()`, the `try` block throws; the `catch` branch logs the error, optionally sends an error result, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — scheduling `cb()` on DB delete completion.
4. Execution falls through (no `return`) to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which will call `ifError`/`ifOk`/`ifWaitingForChain` — each of which also calls `cb()` — resulting in `cb` for this row being invoked twice. [4](#0-3)
