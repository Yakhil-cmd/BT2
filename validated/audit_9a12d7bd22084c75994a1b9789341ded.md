### Title
CCMenu API endpoint bypasses per-stack ApiClient scoping, letting a stack-scoped token read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack with `Stack.from_param!(params[:stack_id])` directly, instead of using the scoped `stacks` collection that every other API controller relies on. This breaks the binding between "the stack an `ApiClient` is authorized for" and "the stack the request actually reads."

### Finding Description
`ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . `Shipit::Api::BaseController` enforces this scope everywhere by funneling all stack lookups through a `stacks` method that restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and only exposes `stack` as `stacks.from_param!(params[:stack_id])`: [2](#0-1) 

This is the mechanism that makes the test "an api client scoped to a stack will only see that one stack" pass for `StacksController#index` [3](#0-2) .

`Shipit::Api::CCMenuController`, however, overrides `stack` and drops the scoping entirely, querying `Stack` directly by the untrusted `params[:stack_id]`: [4](#0-3) 

The controller still calls `require_permission :read, :stack` [5](#0-4) , but `ApiClient#check_permissions!` only checks that the string `"read:stack"` is present in the `permissions` array — it never checks `stack_id` [6](#0-5) . The scope enforcement lives entirely in `BaseController#stacks`, which `CCMenuController` bypasses.

### Impact Explanation
Equality that should hold: `stack_id authorized for token == stack_id actually served`. Before the request: an `ApiClient` scoped to stack A (`client.stack_id == A`) has `read:stack` permission. After a GET to `/api/{stack_id: B}/ccmenu` using that client's token, the controller serves stack B's latest deploy/rollback status via `Stack.from_param!(params[:stack_id])`, which is completely unscoped. Any holder of a narrowly-scoped, single-stack read token (e.g. a CI badge/CCMenu URL meant for one project) can enumerate `stack_id` and read the deploy/task status of every stack in the Shipit instance, i.e. unauthorized cross-stack disclosure of stack state (last deploy/rollback status, running state, lock state) — matching the "unauthenticated/unauthorized read of stack state" High-impact category, since the authorization boundary the token was supposed to be confined to is not honored by this endpoint.

### Likelihood Explanation
Any code path that creates or hands out a stack-scoped `ApiClient` token (the `ApiClient` model explicitly supports `stack_id` scoping and this scoping is relied upon and tested elsewhere in the codebase) is affected as soon as that token is used against the CCMenu endpoint. No special privilege beyond possessing a valid, narrowly-scoped `read:stack` token is required, and the token is passed as a URL query parameter (`token=`) per `CCMenuController#authenticate_api_client`, making it easy to reuse across arbitrary `stack_id` values in the route.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so it is bound by the same `current_api_client.stack_id` restriction enforced in `BaseController`.

### Proof of Concept
1. Admin creates (or the system auto-creates, e.g. via `CCMenuUrlController`) an `ApiClient` with `permissions: ["read:stack"]` scoped to `stack_id = A` (Stack A) and obtains its `authentication_token`.
2. Attacker in possession of that token (e.g. from a shared CCMenu badge URL for Stack A) issues:
   `GET /api/{repo}/{env-of-stack-B}/ccmenu?token=<A's token>`
3. `authenticate_api_client` in `CCMenuController` accepts the token via `ApiClient.authenticate(params[:token])`, setting `current_api_client` to the Stack-A-scoped client.
4. `require_permission :read, :stack` passes because `check_permissions!` only checks the permission string, not `stack_id`.
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped), returning Stack B, and `show` renders Stack B's latest deploy/rollback XML status — data the token was never authorized to access.

*Note: I was unable to execute this PoC in a live environment (read-only ask mode); the analysis is based on static review of `CCMenuController`, `BaseController`, and `ApiClient`, cross-checked against the existing test suite's scoping tests (`test/controllers/api/stacks_controller_test.rb`, `test/controllers/api/ccmenu_controller_test.rb`).*
