### Title
Light-vendor-supplied AA responses are trusted without cryptographic proof - ([File: light.js])

### Summary
The external report describes a wallet that trusted a server's response body for a "supported token list" without validating it against ground truth, letting an attacker inject arbitrary fields (fake token, weird decimals) that the client happily displayed and let the user "add" to the wallet. The analogous root cause in `ocore` is that a light client's history-processing code explicitly **trusts AA-trigger-response data supplied by its light vendor without any DAG/merkle proof**, only doing shallow type/format checks, and then persists and re-emits this data as if it were consensus-confirmed AA execution results.

### Finding Description
In `light.js`, `processHistory()` handles the `light/get_history` response from the light vendor. Unlike regular joints (which go through `validation.validateLight(objJoint)` and are checked against witness-signed balls/skiplist via `witnessProof.processWitnessProof`), the `aa_responses` array is explicitly called out in the code as unverified: [1](#0-0) 
The code only checks:
- field types/shapes (`mci` positive integer, `trigger_address`/`aa_address` valid addresses, `trigger_unit`/`response_unit` valid base64 hash length, `bounced` is 0/1, `response` parses as JSON)
- that `trigger_unit` corresponds to one of the joints included in the very same (attacker-controlled) response (`"foreign trigger_unit"` check)

None of these checks establish that the AA actually executed with this `bounced` value, this `response` content, or this `response_unit` on the real DAG. There is no merkle/ball proof, no signature, no cross-check against `aa_responses` as recorded by a full node from actual consensus execution.

These records are then persisted verbatim by `processAAResponses()`: [2](#0-1) 
and re-broadcast to any other light clients "watching" the same AA via network relay: [3](#0-2) 

Downstream, the wallet UI directly surfaces this unverified `bounced`/`response`/`response_unit` data as transaction history/trigger outcome: [4](#0-3) 

This is architecturally identical to the reported bug class: a client accepts and acts on business-critical data (token list / AA execution result) supplied by a semi-trusted server (API backend / light vendor) with only superficial shape validation, not real integrity/authenticity verification against the source of truth (the actual gno chain / the actual DAG consensus state).

### Impact Explanation
A malicious or compromised light vendor (the light client's chosen full node, which the client does not otherwise fully trust — this is exactly why proofs exist for joints/balance/witness-proof in the rest of `processHistory`) can:
- Report that an AA trigger **bounced** when it actually succeeded, or vice versa, misleading the user's wallet UI about payment/contract outcomes.
- Fabricate a `response_unit` and JSON `response` body (including fake `responseVars`/errors) for a trigger, which is stored in the local `aa_responses` table and surfaces in transaction history and is used by `aaResponseAffectsAddress`/event routing logic that other light clients (bots, watchers) rely on for automated behavior.
- Because this data is re-broadcast to any other light client watching the same AA (`light/aa_response` justsaying), the false information propagates beyond the directly-connected victim.

This does not by itself let an attacker steal real coins (real balances are still derived from validated `outputs`/`units`), but it breaks integrity/trust of AA execution reporting that wallets, bots, and integrations rely on to decide subsequent actions (e.g., assuming a swap/trigger succeeded and proceeding with a follow-up action, or telling a user funds were received/returned when they were not). This matches the impact class of the original report (business-logic/workflow integrity violation, unintended data states, downstream misbehavior) rather than direct fund loss, so severity is Medium.

### Likelihood Explanation
Any light wallet user who connects to (or is directed/MITM'd to) a malicious/compromised light vendor is exposed — no special privilege is needed beyond controlling or spoofing the light-vendor role, which is a normal, reachable network position for light clients (comparable to the original report's ability to manipulate an API response via a proxy). The comment `"AA responses are trusted without proof"` in the code itself confirms this is a known, accepted gap rather than a hypothetical edge case.

### Recommendation
- Require an actual response-unit joint (with witness/ball proof) before trusting `bounced`/`response` fields, i.e., derive the AA response status from the validated `response_unit` joint content (bounce data message) rather than accepting a vendor-asserted `bounced`/`response` JSON blob directly.
- At minimum, cross-check `response_unit`'s presence/validity via `storage.readJoint`/proof chain (as already partially done for `enrichAAResponses`) before persisting or emitting `aa_response`, and mark/flag any `aa_response` entries that could not be corroborated by a proven unit as "unverified" in the UI.
- Do not re-broadcast unverified `aa_response` records to other light clients without the same corroboration.

### Proof of Concept
1. Run a light wallet configured to use a malicious light vendor (or MITM a legitimate one, analogous to the original report's proxy-based Match & Replace).
2. Have the wallet request AA-related history for an address it watches, triggering `light/get_history`.
3. The vendor, in its response's `aa_responses` array, returns a well-formed but fabricated record: valid-looking `trigger_unit` (matching one of the also-attacker-supplied joints), `aa_address`, `bounced: 0`, and a `response` JSON claiming a favorable outcome (e.g., `{"responseVars":{"status":"success"}}`), while in reality on the real network the AA bounced or never triggered.
4. `processHistory` in `light.js` accepts this because it only validates field shapes/formats, not that the AA actually produced this outcome on-chain.
5. `processAAResponses` inserts it into local `aa_responses` and emits `'aa_response'`, which `wallet.js` surfaces in transaction history as if it were a real, confirmed AA execution result, and which `network.js`'s `aa_response` listener relays to any other light client watching the same AA.
