### Title
System governance vote counting uses current balance instead of balance held when the vote was cast, allowing vote-weight manipulation across `op_list`/`threshold_size`/`base_tps_fee`/`tps_interval`/`tps_fee_multiplier` - ([File: main_chain.js])

### Summary
`countVotes()` in `main_chain.js` tallies on-chain governance votes (witness list and network parameter votes) by taking each voter's **current** stable balance at the moment the MCI stabilizes, then applying that single current-balance snapshot to every vote the address has ever cast for the subject within the counting window, regardless of what balance the address actually held at the time it cast each vote. [1](#0-0) 

### Finding Description
`countVotes` first collects all distinct addresses that have ever voted on `subject`, then builds a temporary `voter_balances` table populated with each address's **current unspent balance** (as of the just-stabilized MCI), not the balance at each address's vote timestamp: [2](#0-1) 

For `op_list` votes it then sums `voter_balances.balance` for every address that has an `op_votes` row with `timestamp>=since_timestamp`, and similarly for numerical votes it sums `voter_balances.balance` joined to `numerical_votes` by `timestamp`: [3](#0-2) [4](#0-3) 

This mirrors the reported bug class exactly: a weight metric (ERC20Votes mint amount there, coin balance here) is derived once from a "current" state and then applied retroactively to actions (minting/voting) that happened under a different state, without reconciling the two. Concretely:
- An address can vote for candidate/value X while holding a small balance, then later acquire a large balance (e.g. receive funds, or simply hold on to funds it never actually committed to any vote at that time) - the newly current balance is applied to the old vote as if it had always backed it.
- Conversely, an address that already spent/moved its balance away after voting still has its vote silently down-weighted or zeroed at counting time, changing outcomes that depended on the balance held when the vote was submitted.
- Because a repeated vote on the same subject simply overwrites the previous one and only one final row exists per (address, subject), a single set of coins can be "reused": the code comment before the snippet even documents a known consensus-breaking anomaly worked around with hardcoded OP lists for three specific MCIs (`3547796, 3548896, 3548898`), consistent with this exact class of balance/timing mismatch having already caused a real network disagreement: [5](#0-4) 

The existence of `tools/compare_vote_balances.js`, a diagnostic script explicitly built to detect "zombie-spent outputs" and balance mismatches feeding into vote weight calculations, further indicates this vote-weight/balance synchronization problem is a recognized, unresolved risk area of the codebase: [6](#0-5) 

### Impact Explanation
Governance votes determine the active order-provider (witness) list (`op_list`) and core network economic parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`). If vote weight can be inflated by acquiring balance after casting a vote (rather than by holding balance while actually voting), an attacker can cheaply cast a vote with dust, then move/borrow/flash-acquire a large balance right before the MCI on which the tally runs, causing the network to elect malicious/faulty order providers or set network fee parameters favorable to the attacker. This directly affects "node disagreement on validity/stability" and "network unable to confirm new units" categories, since a bad `op_list` outcome changes consensus witnesses for the whole DAG. The already-documented hardcoded-OP-list workaround at three specific MCIs is evidence this class of issue previously caused actual consensus divergence. [7](#0-6) 

### Likelihood Explanation
The vote-then-acquire-balance sequence requires no special privilege - any address can submit a `system_vote` message and later receive/hold funds before the stabilization MCI is reached, since `since_timestamp`'s window can span up to multiple years and the balance is read only once at tally time regardless of intra-window balance changes. The bug is deterministically reachable by any user who can time a balance transfer before MCI finalization; it does not depend on a malicious node, hub, or leaked key.

### Recommendation
Weight each vote by the balance the voting address actually held at the time the vote's unit became stable (a historical/checkpointed balance), not by the address's balance at the moment of the subsequent MCI tally. This requires reconstructing balance-at-timestamp (e.g., via an output/spend-history join bounded by the vote's MCI) rather than reading `outputs` state as of "now," analogous to how ERC20Votes checkpoints voting power at each transfer instead of relying on a live balance lookup.

### Proof of Concept
1. Address A holds 1 unit of bytes and casts a `system_vote` for `op_list` value `X` at `timestamp T1` (creates a row in `op_votes`/`system_votes`).
2. Before the relevant MCI stabilizes and `countVotes` runs, address A receives a large payment (e.g., 10,000,000 bytes) unrelated to any new vote.
3. When `markMcIndexStable` reaches the qualifying MCI and calls `countVotes(conn, mci, 'op_list')`, `voter_balances` is populated with A's **current** balance (10,000,000), which is then summed against A's single `op_votes` row cast under `T1` with only 1 byte of backing. [8](#0-7) [3](#0-2) 
4. A's vote for `X` is thus counted with 10,000,000x its actual committed weight at the time of voting, potentially swinging the elected `op_list` or numerical parameter outcome.
