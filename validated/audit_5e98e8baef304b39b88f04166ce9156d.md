### Title
GitHub `status` webhook lets any organization that owns *a* Shipit-connected GitHub App forge CI status on commits belonging to a different organization's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook only against the organization named in the payload (`repository.owner.login` / `organization.login`), then hands the *entire* raw JSON body to `Shipit::Webhooks.for_event(event)` handlers with no further binding of "authenticated organization" to "repository/commit being mutated." [1](#0-0) [2](#0-1) 

`Shipit::Webhooks::Handlers::StatusHandler#process` ignores the repository entirely and looks up commits by `sha` across the **whole database**, then writes attacker-supplied `state`, `description`, `target_url`, and `context` onto every matching commit: [3](#0-2) 

Unlike `PushHandler` and `CheckSuiteHandler`, which scope the query through `stacks` (derived from `payload.dig('repository','full_name')` via `Handler#stacks`/`Handler#repository_name`), `StatusHandler` never calls `stacks` and never checks that the commit belongs to a stack whose repository is owned by the organization that produced a valid HMAC signature. [4](#0-3) [5](#0-4) [6](#0-5) 

This breaks the intended binding: `organization authenticated by HMAC` == `organization owning the repository/commit written`. A Shipit deployment configured for multiple GitHub organizations (as documented) keeps a separate `webhook_secret` per organization key in `config/secrets.yml`. [7](#0-6) [8](#0-7) 

### Finding Description
Any party controls a GitHub App installation on *their own* organization ("Org A") that is one of the multiple organizations configured in this Shipit instance. They know Org A's `webhook_secret` because they configured it when creating the GitHub App per the documented setup flow. They can therefore construct a raw HTTP POST to `/webhooks` with:
- `X-Github-Event: status`
- `repository.owner.login` = `"OrgA"` (so `verify_signature` selects Org A's `GitHubApp` and the attacker-computed `X-Hub-Signature` validates, since they legitimately know Org A's secret)
- `sha`, `state`, `description`, `target_url`, `context` set to target a commit sha they've observed on a completely unrelated repository belonging to "Org B" (a different organization/stack managed by the same Shipit instance)

`StatusHandler.process` performs `Commit.where(sha: params.sha)` with no repository/organization scoping, so if that sha exists in Org B's stack, the attacker's forged status is written to it via `commit.create_status_from_github!(params)`. [9](#0-8) 

### Impact Explanation
`Commit#create_status_from_github!` drives `add_status`, which can trigger `stack.schedule_merges` and fire `deployable_status` hooks when the new status transitions to `pending` or `success`. [10](#0-9) 

`ProcessMergeRequestsJob` consults `merge_request.all_status_checks_passed?`, which is driven by exactly these forged `Status` rows via `StatusChecker`. [11](#0-10) [12](#0-11) 

An attacker who is unprivileged with respect to Org B (no Shipit session, no `ApiClient` token, no access to Org B's repository) can forge a `success` CI status for a commit sha in Org B's tracked branch, causing Shipit to consider required status checks satisfied and proceed to auto-merge/deploy that pull request — an unauthorized deploy/merge triggered purely by a webhook forged under a different, unrelated organization's credentials. This matches the required "Critical: unauthorized deploy, rollback or merge" impact bucket.

### Likelihood Explanation
Requires: (1) the target Shipit instance is configured with multiple GitHub organizations sharing one `/webhooks` endpoint (an explicitly documented, supported configuration), (2) the attacker controls a legitimate GitHub App installation on any one of those organizations, and (3) the attacker knows or can guess a commit sha in the victim's tracked branch (commit shas are often public/observable via GitHub commit history, PR pages, CI logs). Given multi-tenant Shipit setups are common (e.g., large companies with many GitHub orgs feeding one internal Shipit), and sha discovery is trivial for public/semi-public repos, likelihood is realistic though it depends on the multi-org deployment model being in use.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the authenticated repository/stack instead of a global `Commit.where(sha: ...)`, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` (mirroring `PushHandler`/`CheckSuiteHandler`'s use of `Handler#stacks`, which is derived from `payload.dig('repository','full_name')`), and additionally verify that the repository named in the payload actually belongs to the organization used to select the webhook secret in `WebhooksController#verify_signature`.

### Proof of Concept
1. Deploy Shipit configured per `docs/setup.md`'s "Using Multiple Github Applications" with two orgs, `OrgA` and `OrgB`, each with tracked stacks and distinct `webhook_secret`s.
2. As the administrator of `OrgA`'s GitHub App (attacker), compute `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` over a crafted body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/attacker-repo"},
  "sha": "<known head commit sha of OrgB/victim-repo's PR>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged"
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and the signature from step 2.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` from `repository.owner.login`, validates successfully, and dispatches to `StatusHandler`.
5. `StatusHandler#process` executes `Commit.where(sha: <victim sha>)`, finds the commit under `OrgB/victim-repo`'s stack (unrelated to OrgA), and calls `create_status_from_github!`, marking the victim's PR check as `success` even though the attacker has no access to `OrgB`.
6. If this was the last required status, `ProcessMergeRequestsJob` proceeds to merge/deploy the victim's PR.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
