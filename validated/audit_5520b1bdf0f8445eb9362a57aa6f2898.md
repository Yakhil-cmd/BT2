This confirms the analog: `handleAATriggers` (the real, committing trigger executor) is serialized under `mutex.lock(['aa_triggers'], ...)` [1](#0-0) , and `handlePrimaryAATrigger` additionally commits under its own `BEGIN`/`COMMIT` and mutates the process-wide unit caches directly (`storage.assocStableUnits[unit].count_aa_responses`) [2](#0-1) . But `dryRunPrimaryAATrigger`, invoked automatically for every incoming unit that pays an AA address (`conf.bDryRunNewTriggers`) from `network.js`'s `handleJoint`/`ifOk` path [3](#0-2) , takes **neither** the `aa_triggers` lock nor the `write` lock. It runs `handleTrigger` on its own DB connection/transaction and, on completion, calls `revertResponsesInCaches`, which directly mutates the same global, unlocked in-memory structures — `storage.assocUnstableUnits`, `storage.assocBestChildren` — via `storage.forgetUnit` and `storage.fixIsFreeAfterForgettingUnit` [4](#0-3) [5](#0-4) .

### Title
Unlocked AA dry-run corrupts shared unit caches concurrently with the locked writer path - (File: aa_composer.js)

### Summary
`dryRunPrimaryAATrigger()` is invoked for every incoming unit that pays coins to a known AA address, as an optimistic pre-check performed before the real write, but it runs completely outside the synchronization domains (`mutex.lock(["write"])` used by `writer.saveJoint`, and `mutex.lock(['aa_triggers'])` used by `handleAATriggers`/`handlePrimaryAATrigger`) that protect the shared, process-global DAG caches in `storage.js` (`assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`, etc.).

### Finding Description
This is structurally the same class of bug as the reported VCAP issue: two logically distinct call paths — the real committing trigger executor (`handlePrimaryAATrigger`, serialized via the `aa_triggers` mutex key, and `writer.saveJoint`, serialized via the `write` mutex key) — and an "observational"/speculative path (`dryRunPrimaryAATrigger`) both operate on one shared underlying resource: the singleton in-process caches exposed by `storage.js`. The real paths assume that only they mutate these caches while holding their respective locks, exactly as the Super VCAP admin instances assumed only their own `admin->lock` guarded the shared hardware register/cache.

`network.js` calls `aa_composer.dryRunPrimaryAATrigger(trigger, address, JSON.parse(definition))` for every unit with `count_primary_aa_triggers` inside the `ifOk` validation callback, *before* `writer.saveJoint` is invoked and *before* the `write` lock is taken [6](#0-5) . `dryRunPrimaryAATrigger` calls `handleTrigger`, which fabricates and processes response units in the same in-memory data structures used by real unit processing (`storage.assocStableUnits`, `readMcUnit`, output/input evaluation, etc.), then on completion calls `revertResponsesInCaches(arrResponses)` [7](#0-6) .

`revertResponsesInCaches` reads `storage.assocUnstableUnits[first_unit]` to get `parent_units`, calls `storage.forgetUnit` for every fabricated response unit, and then calls `storage.fixIsFreeAfterForgettingUnit(parent_units)` [4](#0-3) . Both of these storage functions directly mutate the shared, unlocked global associative caches (`assocKnownUnits`, `assocCachedUnits`, `assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`) that `writer.saveJoint` (running concurrently for a *different* real unit, holding only the `write` lock, not any lock that dry-run also respects) also reads and writes to compute `is_free`, best-parent/best-child bookkeeping, and unit stability bookkeeping [5](#0-4) .

Because `dryRunPrimaryAATrigger` never acquires the `write` or `aa_triggers` lock, its cache mutations (`forgetUnit`/`fixIsFreeAfterForgettingUnit`) can interleave with a concurrent `writer.saveJoint` call for an unrelated real unit that shares parent units with the dry-run's fabricated response chain, or with `handleAATriggers`' processing which also touches `storage.assocStableUnits[unit].count_aa_responses` without any lock shared with the dry-run path. This mirrors the VCAP root cause precisely: an unlocked "diagnostic" read/computation path (debugfs dump / dry-run) repopulates or clears entries in a resource that a properly-locked writer assumes it exclusively controls, corrupting the writer's committed state.

### Impact Explanation
Corruption of `assocUnstableUnits` / `assocBestChildren` / `is_free` bookkeeping can cause a node to compute the wrong best-parent/best-child relationships or wrongly mark units as free/non-free. This directly affects main-chain and stability determination (`main_chain.js` consumes these caches), which can make a node diverge from peers on which units are stable — i.e., node disagreement on validity or stability, one of the accepted high-impact outcomes. Because the fabricated dry-run units share the exact same in-memory keying scheme (by real unit hash of a to-be-submitted trigger, and derived response units) as genuine processing, a well-timed flood of AA-triggering payments can reliably force races against real writes.

### Likelihood Explanation
`conf.bDryRunNewTriggers` gates this path; when enabled it runs unconditionally for **every** unit with an AA-address output — no privileged access required, any unit poster who sends payment to a public AA address triggers it. An attacker can post many such units concurrently (or via multiple peer connections) while the node is also processing/writing other units, deliberately maximizing the overlap window between the unlocked dry-run cache mutation and the locked real write, since JS's single-threaded event loop still interleaves at the many `await`/callback boundaries present in both paths.

### Recommendation
Route `dryRunPrimaryAATrigger`'s cache-touching lifecycle (specifically the `revertResponsesInCaches` call and any code path that calls `storage.forgetUnit`/`storage.fixIsFreeAfterForgettingUnit`) through the same mutex domain used by `writer.saveJoint` (`mutex.lock(["write"])`) and/or `handleAATriggers` (`mutex.lock(['aa_triggers'])`), analogous to introducing `vcap_lock()`/`vcap_unlock()` helpers that unify all consumers of the shared resource behind one lock. Alternatively, make `dryRunPrimaryAATrigger` operate on cache snapshots/copies rather than mutating the live global `storage.js` associative caches at all.

### Proof of Concept
1. Enable `conf.bDryRunNewTriggers` (default true in full nodes per the code path in `network.js`).
2. Attacker submits unit A that pays to public AA address `X` (any AA that produces at least one response message), triggering `dryRunPrimaryAATrigger` in `network.js` at [3](#0-2) , which fabricates response units sharing parent units with genuinely unstable DAG tips and then calls `revertResponsesInCaches` to mutate `storage.assocUnstableUnits`/`assocBestChildren` via `forgetUnit`/`fixIsFreeAfterForgettingUnit`.
3. Concurrently, the attacker (or normal network traffic) causes a second, unrelated real unit B — sharing one of those same parent units — to reach `writer.saveJoint`, which is executing under the `write` lock and reading/writing the very same `assocUnstableUnits`/`assocBestChildren` entries to update `is_free` and best-parent chains at [8](#0-7) .
4. Because the dry-run path holds no lock overlapping with `write`, the two mutations interleave: `forgetUnit`/`fixIsFreeAfterForgettingUnit` executed by the dry run can incorrectly flip `is_free` on a parent unit that unit B's real commit is simultaneously relying on, corrupting the in-memory DAG state used for subsequent best-parent/main-chain computations, which is exactly the class of corruption the kernel fix addresses for the shared VCAP cache.
