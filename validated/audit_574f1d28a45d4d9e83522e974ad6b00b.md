### Title
Cross-organization webhook forgery via mismatched signature-verification key and repository-authorization field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to verify a payload's HMAC using `repository_owner`, which is read from `payload.dig('repository','owner','login')` (falling back to `payload.dig('organization','login')`). However, the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target repository/stack from a *different* field of the same payload: `payload.dig('repository','full_name')`. Nothing ties these two fields together, so an actor who legitimately controls the webhook secret for one organization in a multi-tenant Shipit deployment can forge a payload whose `repository.owner.login` matches their own org (so their own known secret verifies it) while `repository.full_name` names a repository belonging to a different organization/tenant on the same Shipit instance.

### Finding Description
`verify_signature` computes: [1](#0-0) 
using the org derived from: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/secret configured for that org name: [3](#0-2) 

Once the HMAC is validated against that org's secret, the raw payload is dispatched unmodified to handlers: [4](#0-3) 

Handlers, however, do not use `repository.owner.login` (the field the signature was keyed on) to find the target — they use `repository.full_name`: [5](#0-4) 

`PushHandler` uses this to locate stacks and enqueue a sync with an attacker-controlled `after` (expected head sha): [6](#0-5) 

Because the HMAC covers the entire raw JSON body, this is not forgeable by an outsider who knows no secret at all — but on a Shipit instance configured with multiple GitHub Apps/organizations (as documented and supported by `Shipit.github_organizations`/`github_app_config`), each org owner who manages their own app's webhook secret can craft a raw payload where `repository.owner.login` = their own org (so the correct secret validates the signature) but `repository.full_name` names a repository under a sibling organization/tenant hosted on the same instance. The controller only checks "is this signature valid for *some* org named in the payload," never that the org used for verification actually owns the repository being acted upon.

### Impact Explanation
This breaks the trust binding "an organization that authenticated versus the repository that is written": the signature only proves the payload was authorized by organization A, yet the code lets it manipulate stacks/state belonging to organization B. Via `PushHandler`, this allows an attacker who controls one tenant's webhook secret to enqueue `GithubSyncJob` for another tenant's stack with an attacker-chosen `expected_head_sha`, and potentially interact with other events (`status`, `check_suite`, `pull_request`) that similarly resolve their target repository via `repository.full_name`/`payload.dig('repository', ...)` independent of the field used for signature routing. This can trigger cross-repository state changes/deployable-status manipulation and syncs on a repository the attacker does not own, matching the "cross-repository writes" / unauthorized deploy-adjacent impact class.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (documented, supported configuration via `github_app_config`) where the attacker legitimately administers one tenant's GitHub App/webhook secret but not the victim tenant's repository. This is a realistic operational model for shared/hosted Shipit instances serving multiple orgs, and requires no privileged Shipit account, API token, or session — only knowledge of one's own configured webhook secret, which every onboarded organization admin necessarily has.

### Recommendation
In `WebhooksController#verify_signature`/handlers, cross-check that the repository/organization used to select the verifying secret is the same organization that owns `repository.full_name` (or, more robustly, verify the signature using the secret owned by the actual repository being acted upon, not a value chosen by the payload itself independent of downstream usage). Reject events where `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Assume a Shipit instance configured with two orgs' GitHub Apps: `attacker-org` (secret known to the attacker, who administers that org's install) and `victim-org` (secret unknown to attacker), per `docs/setup.md`'s multi-org config schema.
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-secret, payload)` using the secret they legitimately possess for `attacker-org`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s secret, and the signature validates successfully.
5. `PushHandler#process` resolves the target via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, finds victim stacks, and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on a repository the attacker does not control.

Note: full confirmation that `GithubSyncJob`/`Stack#sync_github` performs writes purely from this attacker-controlled `expected_head_sha` without further server-side revalidation against GitHub could not be completed in this session (file `app/jobs/shipit/github_sync_job.rb` and `Stack#sync_github` were not fully read due to tool errors in the final iteration); this should be verified before treating the downstream impact as fully proven.
