### Title
Unauthenticated bypass of author signature verification via forged `aa`/`aa_mci` joint fields in `validation.validate()` - (File: validation.js)

### Summary
`validation.validate(objJoint, callbacks, external_conn)` derives a privileged "this unit is an internally-generated AA response, skip signature checks" flag (`bAA`) directly from an untrusted, attacker-controllable field (`objJoint.aa` / `objJoint.aa_mci`) on the joint object itself, rather than from a value passed out-of-band by the trusted caller. This is structurally the same bug class as CVE-2014-5245: a privileged/trusted code path (Symfony's ESI fragment sub-request, here the internal `aa_composer.validateAndSaveUnit()` self-call) is distinguished only by a marker that lives inside the data the untrusted party fully controls, so anyone who can reach the same function with that marker set inherits the trust.

### Finding Description
In `validation.js`, near the top of `validate()`: [1](#0-0) 

```
var bAA = false;
if (objJoint.aa) {
    bAA = true;
    var aa_mci = objJoint.aa_mci;
    delete objJoint.aa;
    delete objJoint.aa_mci;
}
else {
    if (isArrayOfLength(objUnit.authors, 1) && !isNonemptyObject(objUnit.authors[0].authentifiers) && !objUnit.content_hash && !conf.bLight)
        return callbacks.ifTransientError("possible AA");
}
```

Setting `bAA = true` fundamentally changes how the rest of validation treats the unit:

- `validateAuthor()` (`validation.js:1149-1175`) completely skips authentifier/signature verification when `objValidationState.bAA` is true — it only checks that the author's `address` corresponds to an existing AA definition, then proceeds to `checkSerialAddressUse()`: [2](#0-1) 

- `validateAATrigger()` (`validation.js:986-996`) also short-circuits most trigger-related checks when `objValidationState.bAA` is set.
- Message app whitelist changes to the reduced `aa_validation.aaApps` set: `validation.js:1620-1629`.

This `aa`/`aa_mci` trust marker is intended to be set *only* by the AA engine itself when it constructs a response unit internally (see `aa_composer.js` `validateAndSaveUnit`): [3](#0-2) 
```
function validateAndSaveUnit(objUnit, cb) {
    var objJoint = { unit: objUnit, aa: true, aa_mci: mci };
    validation.validate(objJoint, { ... }, conn);
```

However, `validate()` itself has no restriction that would prevent *any* caller (or any joint payload reaching `validate()`) from setting these same fields. The field-deletion happens **before** the generic joint-shape whitelist checks: [4](#0-3) 
so by the time `hasFieldsExcept(objJoint, [...])` runs, the `aa`/`aa_mci` keys have already been stripped and will not be flagged as "unknown fields" — the function has no way to tell an internally-constructed AA joint from an externally-supplied one carrying the same marker.

The only reason this is not exploitable through the primary network ingress today is that `network.js`'s `handleJoint()` — the single function that feeds untrusted, wire-received joints (from both P2P gossip and light-client `post_joint`) into `validation.validate()` — has an explicit guard: [5](#0-4) 
```
function handleJoint(ws, objJoint, bSaved, bPosted, callbacks){
	if ('aa' in objJoint)
		return callbacks.ifJointError("AA unit cannot be broadcast");
```
This guard is a manually-maintained allowlist check on a single call path, not a property enforced by `validate()` itself. Any additional or future entry point that constructs an `objJoint` from external input and forwards it to `validation.validate()` without independently re-implementing this exact check would silently reinstate the unauthenticated-signature-bypass condition. `composer.js`, `divisible_asset.js`, and `indivisible_asset.js` also call `validation.validate()` directly; whether any of them ever build `objJoint` from attacker-influenced fields without excluding `aa`/`aa_mci` could not be fully verified within the available index — the index does not show full-file contents of `divisible_asset.js`/`indivisible_asset.js` at the exact call sites, only the file-level match count.

### Impact Explanation
If reachable, the impact is severe: `bAA=true` skips address-authentifier/signature verification entirely, so an attacker would only need to know a public AA address and fabricate a unit "authored" by that AA (e.g., a `transfer` input consuming the AA's own unspent output) to move that AA's entire held balance to an address of the attacker's choosing — direct, unauthorized draining of any AA's funds network-wide, without any private key, i.e., unauthorized spending/asset theft at the protocol level. This matches the required severity bar (concrete unauthorized spending / AA fund loss).

### Likelihood Explanation
Currently mitigated: the only externally-reachable route into `validation.validate()` for untrusted joints (`network.js: handleJoint`, invoked by both P2P `joint` gossip and light-client `post_joint`) explicitly rejects any joint containing an `aa` field before validation runs. This makes the vulnerability **not currently exploitable through the primary network paths that were inspected**. However, the design is fragile: the safety property ("no externally-submitted unit can ever set `aa`/`aa_mci`") is enforced by a single ad-hoc check in one caller rather than inside `validate()` where the trust decision is actually made, and `validate()` is called from at least four other locations (`composer.js`, `divisible_asset.js`, `indivisible_asset.js`, `aa_composer.js`) whose full input provenance could not be completely confirmed with the available context. Any new/other caller that omits the equivalent of the `handleJoint` guard, or any place that merges/forwards attacker-supplied joint objects without first deep-cloning/stripping `aa`/`aa_mci`, reopens the hole.

### Recommendation
- Do not derive `bAA` from a field embedded in the (potentially attacker-supplied) `objJoint`. Instead, pass it as a separate, explicit trusted parameter to `validate(objJoint, callbacks, external_conn, bAA, aaMci)` that only internal AA-engine callers can set, and never accept it from parsed network/light-client payloads.
- As defense in depth, keep (and strengthen) the existing `handleJoint` check, but also add a generic guard directly inside `validate()`/`handlePostedJoint`/every ingestion path that unconditionally strips or rejects `aa`/`aa_mci` on any joint whose origin is not the trusted internal caller, performed as the very first step, before any other logic depends on their absence.
- Audit `composer.js`, `divisible_asset.js`, and `indivisible_asset.js` call sites of `validation.validate()` to confirm none of them construct `objJoint` from external/untrusted data without excluding `aa`/`aa_mci`.

### Proof of Concept
Conceptual PoC (not confirmed exploitable end-to-end due to the `handleJoint` guard, but demonstrates the flawed trust boundary in `validate()` itself):
1. Identify any AA address `A` with a nonzero balance from `aa_balances`/its unspent AA-response outputs (public information).
2. Construct a unit `U` with `authors: [{ address: A }]` (no `authentifiers`), an input spending `A`'s known unspent output, and an output sending funds to attacker's address.
3. Call `validation.validate({ unit: U, aa: true, aa_mci: <any stable mci> }, callbacks)` directly (bypassing `network.js`'s `handleJoint`) — this shows that `validateAuthor` never checks `U`'s authentifiers because `objValidationState.bAA` is true, and validation would proceed to `checkSerialAddressUse` and normal input/output balance checks only, no signature required.
4. This proves the code path exists and is trust-decided purely by an attacker-controllable field on the object passed to `validate()`; the only reason today's P2P/light-client ingestion is safe is the separate `'aa' in objJoint` check in `network.js:handleJoint`, not any protection inside `validate()` itself.
