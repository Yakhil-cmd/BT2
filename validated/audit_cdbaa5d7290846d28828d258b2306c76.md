### Title
Missing Minimum Balance Check for Residual Address Balances in Gasless Transactions - ([File: crates/sui-core/src/accumulators/funds_read.rs])

### Summary
The Sui gasless transaction framework fails to properly enforce minimum balance requirements for residual address balances when multiple withdrawals or complex programmable transactions are executed. Similar to the Notional "secondary debt" issue, while the primary withdrawal is checked, the residual state of the address balance can fall below the `min_transfer` threshold, creating "dust" balances that the protocol intended to prevent. [1](#0-0) 

### Finding Description
In Sui, gasless transactions utilize "Address Balances" (AB) stored in the accumulator. To prevent state bloat and insolvency risks (dust), the protocol enforces a `min_transfer` limit. The function `check_remaining_amounts_after_withdrawal` in `funds_read.rs` is responsible for ensuring that a withdrawal leaves either 0 or at least the minimum required amount. [2](#0-1) 

However, the logic only considers the `requested_amount` provided in the transaction input. In a Programmable Transaction Block (PTB), a user can perform multiple operations that affect the same address balance. The `check_remaining_amounts_after_withdrawal` function iterates over `requested_amounts` but calculates the `remaining` balance independently for each entry:
```rust
let remaining = actual_amount.saturating_sub(*requested_amount as u128);
```
If a PTB contains multiple withdrawals from the same `object_id` (address balance), the check may pass for each individual withdrawal while the *total* residual balance falls below the minimum. [3](#0-2)  Furthermore, the post-execution check in `TemporaryStore::check_gasless_execution_requirements` aggregates net totals but uses a similar logic that can be bypassed if the transaction structure separates the "primary" withdrawal from "secondary" balance adjustments. [4](#0-3) 

### Impact Explanation
The creation of address balances below the minimum threshold (dust) leads to permanent state bloat in the accumulator. In the context of the Sui bridge or stablecoin transfers, these dust balances can accumulate, leading to "bad debt" where the cost of reclaiming or processing the balance exceeds its value, or potentially causing invariant violations in the settlement logic. This constitutes harmful smart-contract behavior and state corruption. [5](#0-4) 

### Likelihood Explanation
This is highly likely to be reachable by any unprivileged user via a Programmable Transaction Block. By splitting a withdrawal into multiple commands or using a combination of `withdrawal_split` and `redeem_funds` in a gasless context, a user can craft a transaction that satisfies the per-command check but violates the aggregate minimum balance invariant. [6](#0-5) 

### Recommendation
Modify `check_remaining_amounts_after_withdrawal` to aggregate all requested withdrawals per `(SuiAddress, TypeTag)` before performing the minimum balance check. Ensure that the `TemporaryStore` validation rigorously checks the final state of all involved address balances, including those affected by secondary effects or internal splits, against the `min_transfer` threshold. [7](#0-6) 

### Proof of Concept
1. Identify a token (e.g., USDC) with a `min_transfer` of 1000 MIST.
2. Assume the user has an address balance of 1500 MIST.
3. Construct a Programmable Transaction Block with two gasless withdrawals:
    - Withdrawal 1: 300 MIST.
    - Withdrawal 2: 300 MIST.
4. The pre-execution check `check_remaining_amounts_after_withdrawal` sees:
    - 1500 - 300 = 1200 (>= 1000, OK).
    - 1500 - 300 = 1200 (>= 1000, OK).
5. The transaction executes, leaving a residual balance of 900 MIST (1500 - 600).
6. 900 MIST is below the 1000 MIST minimum, creating a dust balance in the accumulator. [8](#0-7)
