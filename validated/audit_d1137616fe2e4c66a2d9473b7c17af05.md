### Title
Unverified `X-Shipit-User` header lets an authenticated ApiClient impersonate any Shipit user for deploys, rollbacks, locks and task actions - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The Nouns-Builder finding shows an *action field that is trusted and acted upon without being validated against the properly-authorized state* (a property is added and later minted against without checking that the item data backing it actually exists). The structural analog in shipit-engine is `Shipit::Api::BaseController#identify_user`, which derives `current_user` purely from the client-supplied `X-Shipit-User` request header, with no cryptographic binding to the authenticated `ApiClient`. Any bearer of a valid `ApiClient` token that has `deploy:stack`/`lock:stack` permission can set this header to the login of an arbitrary existing Shipit `User` (including privileged operators) and every downstream write - deploy authorship, rollback, lock ownership, task trigger/abort, release-status reporting - is attributed to and executed "as" that impersonated identity.

### Finding Description
`identify_user` looks the claimed identity up by a plain string comparison, with no signature, token or session check tying it to the credential that authenticated the request: [1](#0-0) 

The binding that should hold is: **the identity used to authorize/attribute an action == the identity of the entity that presented the verified credential** (the `ApiClient`'s `creator`/token). Instead, the engine breaks this into two independent things:
- What is verified: the `ApiClient` bearer token (`authenticate_api_client`) and its coarse `permissions` array (`read:stack`, `write:stack`, `deploy:stack`, `lock:stack`, ...). [2](#0-1) 
- What is acted upon: `current_user`, sourced from the unverified `X-Shipit-User` header, and passed as the actor/author/locker/aborter for the actual mutating operations: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Test fixtures confirm this is intentional, documented behavior of the header, not a coincidental edge case: any caller can set `X-Shipit-User` to an arbitrary existing login and have deploy authorship attributed to that user: [8](#0-7) 

Before the attacker's request: `deploy.user` / `rollback.user` / `lock` creator / `aborted_by` reflect the true actor identified by the token. After the attacker's request: the same fields reflect an arbitrary chosen `User` row (looked up case-insensitively by `login`), while the *actual* authenticated principal remains the low-privilege `ApiClient`. The `ApiClient` token permission model (`read:stack`, `deploy:stack`, etc.) authorizes *operations*, but the `User` identity attached to the resulting audit trail/ownership can be forged independently of that authorization boundary.

### Impact Explanation
This does not grant new operation-level permissions beyond what the `ApiClient`'s `permissions` already allow (deploy, rollback, lock, task-trigger/abort, release status) - so it is not a permission bypass. However, it directly falsifies the `User` bound to every deploy, rollback, lock and task action: any script or integration holding a `deploy:stack`/`lock:stack` scoped `ApiClient` token can attribute unauthorized deploys, rollbacks and stack locks to any other Shipit user (e.g., a senior engineer or team lead), poisoning audit trails, notification/blame logic, and any downstream authorization or alerting that trusts `Task#user`/`Deploy#user`/lock ownership. Given the report's requirement of "an unauthorized deploy, rollback" bound to the wrong identity, and the fact that this crosses the trust boundary between "verified ApiClient token" and "User identity recorded/acted upon," it satisfies the High-severity class of "escalation into recorded/attributed identity for unauthorized deploy/rollback."

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `ApiClient` tokens are distributed to CI systems, chatops bots, or other automation with `deploy:stack`/`lock:stack` permissions (a normal, documented usage pattern in this engine, per `README.md`'s API client docs and the `X-Shipit-User` test coverage). No additional secrets are required beyond a legitimately-issued API token that already has the relevant operation permission; the header is plain and requires no signing.

### Recommendation
- Do not allow `X-Shipit-User` to designate an identity for actions unless the `ApiClient` is explicitly configured to be allowed to impersonate ("act-on-behalf-of") users, and scope that trust per-client (e.g., an explicit `impersonates_users` allowlist tied to the `ApiClient` record) rather than a global header trusted from any authenticated client.
- At minimum, record and surface both the authenticating `ApiClient` and the claimed `X-Shipit-User` in `Task`/`Deploy`/lock records so audit trails can distinguish "who authenticated" from "who was claimed," and gate which permission scopes are allowed to set the header at all.

### Proof of Concept
Using an `ApiClient` fixture with only `deploy:stack` permission (e.g., `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`), authenticate normally, then:
```
POST /api/stacks/:stack_id/deploys
Authorization: Basic <valid ApiClient token>
X-Shipit-User: <login of any other existing Shipit user, e.g. an admin>
{ "sha": "<valid sha>" }
```
The resulting `Deploy#user` (and `report_healthy!`/`report_faulty!`/`lock`/`abort!` actor fields in the analogous endpoints) will be set to the impersonated user rather than any user actually tied to the presented credential, as directly demonstrated by: [9](#0-8)

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
