### Title
Webhook signature check is keyed to an attacker-controlled organization field, allowing forged `membership` events to grant `Shipit.github_teams` access - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to verify a webhook against using an unauthenticated field taken from the very payload it is about to verify. If any organization configured on the installation has no `webhook_secret` set (an explicitly optional setting), `GithubApp#verify_webhook_signature` accepts *any* payload unconditionally for that organization. Because the same request body also carries the `team`/`member`/`repository` data that downstream handlers act on, an attacker can pick an organization name that has no secret to pass verification, while the payload's other fields cause `Shipit::Webhooks::Handlers::MembershipHandler` to create/append `Membership` records for arbitrary GitHub logins into arbitrary teams — the same teams gating `Shipit.github_teams` authorization for the entire app.

### Finding Description
The signature check derives the org used for authentication purely from payload content: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that resolved organization: [3](#0-2) 

`webhook_secret` is documented as optional per organization in a multi-org install: [4](#0-3) 

Once verification passes (trivially, for the secret-less org), `create` dispatches the full, attacker-controlled JSON body to all registered handlers for the event type, with no re-check that the org used to "authenticate" the request matches the entity the payload claims to modify: [5](#0-4) 

For the `membership` event, handlers create `Team`/`Membership`/`User` records straight from the payload's `team`/`member`/`action` fields, as shown by the existing test suite (creates a team "on the fly", appends/removes memberships): [6](#0-5) 

Those `Membership`/`Team` records are exactly what gates access to the whole engine: `current_user.authorized?` is checked against `Shipit.github_teams` in the authentication concern used by every non-API controller: [7](#0-6) 

The broken binding, stated as an equality that should hold but doesn't:
`{organization whose secret validated the webhook signature} == {organization/team that the payload's Membership/Team records claim to represent}`.
Before the attack: only genuine GitHub deliveries (HMAC-signed by the real org's `webhook_secret`) can create/modify `Membership` rows for that org's teams. After the attacker's forged request: any organization present in `config/secrets*.yml` without a configured `webhook_secret` becomes a skeleton key — its (non-existent) signature check always passes — yet the JSON body can name a `team` matching one of the org handles in `Shipit.github_teams` and a `member.login` equal to the attacker's own (or any) GitHub login, both of which are asserted with no cross-check against the "authenticating" organization.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" boundary explicitly called out as in-scope High impact. An attacker who is not a member of any authorized team, and holds no Shipit session, ApiClient token, or webhook secret, can forge a POST to `/webhooks` with `X-Github-Event: membership`, an org name that has no configured secret, and a `team`/`member` payload naming a required team and their own GitHub login. This creates a `Membership` row granting them `current_user.authorized?` for the entire Shipit UI, letting them create `ApiClient`s, trigger deploys, and access repository/stack state without ever authenticating to GitHub.

### Likelihood Explanation
Any Shipit deployment configuring more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml` / `secrets_double_github_app.yml`) is exposed if even one of those organizations was set up without a `webhook_secret` (explicitly marked optional in setup docs and example secrets). The `/webhooks` endpoint is unauthenticated by design (it must accept GitHub deliveries), so the attacker needs no credentials — only knowledge that such a secret-less org handle exists, which is often guessable/discoverable from the app's public GitHub App installation pages.

### Recommendation
- Require `webhook_secret` to be present for every configured organization (fail closed instead of returning `true` when blank) in `GithubApp#verify_webhook_signature`.
- Re-validate, inside each handler (especially `MembershipHandler`), that the `organization`/`team` referenced in the payload actually belongs to the organization that was used to select the verifying `GithubApp`/secret, rather than trusting payload-declared identifiers independently of the authentication step.
- Consider requiring `X-Hub-Signature-256` unconditionally and rejecting webhooks entirely for organizations without a configured secret, rather than accepting them.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `OrgWithSecret` (has `webhook_secret`) and `OrgNoSecret` (no `webhook_secret`, as allowed by `config/secrets.development.example.yml`).
2. `Shipit.github_teams` includes `OrgWithSecret/some-team`.
3. Attacker POSTs to `/webhooks` with headers `X-Github-Event: membership` and no valid signature, body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "some-team", "slug": "some-team" },
  "organization": { "login": "OrgNoSecret" },
  "member": { "login": "attacker-handle" }
}
```
4. `repository_owner` resolves to `OrgNoSecret` (`app/controllers/shipit/webhooks_controller.rb:59-62`), whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
5. `MembershipHandler` creates/updates a `Membership` associating GitHub login `attacker-handle` with team `some-team` (behavior demonstrated by `test/controllers/webhooks_controller_test.rb:129-165`), even though `some-team` is actually an `OrgWithSecret` team, not `OrgNoSecret`'s.
6. Attacker then completes normal GitHub OAuth login as `attacker-handle`; `current_user.authorized?` now passes because of the forged `Membership`, granting full access per `app/controllers/concerns/shipit/authentication.rb:20-34`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
