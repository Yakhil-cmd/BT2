### Title
Webhook signature verification uses an attacker-chosen organization key that can be blank, letting unsigned payloads be processed as trusted GitHub events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using `repository_owner`, a value read straight out of the **unauthenticated** JSON body, before any signature check has occurred. [1](#0-0)  That selection is then used purely to pick a `webhook_secret`; if the selected organization's config has no `webhook_secret` set, `verify_webhook_signature` short-circuits to `true` unconditionally. [2](#0-1)  Downstream handlers then act on a completely different `repository.full_name` field taken from the same untrusted body to locate the real `Stack`/`Repository`. [3](#0-2) 

### Finding Description
This mirrors the report's bug class: a value used to establish trust (the "caller"/signing organization) is attacker-controlled and disconnected from the value that is actually acted upon (the repository being written to).

- Shipit supports multiple configured GitHub organizations, each with its own optional `webhook_secret` (docs: `docs/setup.md` "Using Multiple Github Applications", and fixture `test/dummy/config/secrets_double_github_app.yml`). [4](#0-3) [5](#0-4) 
- `repository_owner`, used to pick `Shipit.github(organization: repository_owner)`, is parsed from `params.dig('repository','owner','login')` — the raw JSON body — *before* `verify_webhook_signature` is called. [1](#0-0) [6](#0-5) 
- `verify_webhook_signature` treats a blank/nil `webhook_secret` as "always verified": `return true unless webhook_secret`. [2](#0-1) 
- After this bypass, the actual event processing (`PushHandler`, `StatusHandler`, etc.) looks up the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — again taken from the same untrusted body, and *not* required to match the `repository_owner` used to choose the (bypassed) secret. [3](#0-2) [7](#0-6) 

The binding that should hold is: `organization whose secret authenticated the request == organization owning the repository/stack being mutated`. In a multi-org deployment where any single configured organization lacks a `webhook_secret` (e.g. a staging/dev org added to the same secrets file, or simply an app that hasn't set one up yet for one org), an attacker can set `repository.owner.login` in the JSON body to that blank-secret organization to make `verify_signature` pass with no valid `X-Hub-Signature` at all, while setting `repository.full_name` to any other tracked repository belonging to a *different*, properly-secured organization. The `PushHandler`/`StatusHandler`/etc. will then process the forged event against that other repository's stacks.

### Impact Explanation
If exploitable, this allows an unauthenticated attacker to inject arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) for stacks they do not control, e.g. triggering `GithubSyncJob` with an attacker-chosen `expected_head_sha`, forging commit statuses via `StatusHandler`/`create_status_from_github!`, or manipulating pull-request label/merge-queue state through the pull-request handlers. Depending on which handler is reached, this can influence which commit gets treated as CI-passing/deployable and, combined with `continuous_deployment`, could lead to an unauthorized deploy — matching the report's "manipulation of data processed by a security-module-gated entry point" pattern.

### Likelihood Explanation
Exploitability is conditional: it requires a Shipit deployment configured with **multiple GitHub organizations** (the documented multi-org schema) where at least one configured organization has no `webhook_secret` set. This is a real, documented, supported configuration shape (not a hypothetical), but I could not confirm from the indexed code/docs how common such partial configuration is in practice, nor whether the host application's `secrets.yml` always sets a secret for every org it lists. This uncertainty affects likelihood but not the existence of the code-level trust-binding gap itself.

### Recommendation
- Do not let attacker-supplied JSON body fields determine which secret is used to authenticate the same JSON body; if multiple organizations are configured, require a secret to be present for every organization, or reject any organization config missing a `webhook_secret` when the app is used in multi-org mode.
- After verifying the signature, cross-check that the `repository.full_name`/owner acted upon by handlers matches the organization whose secret validated the payload, rather than trusting it as an independent unauthenticated field.
- Remove or gate the `return true unless webhook_secret` bypass in `verify_webhook_signature` behind an explicit, opt-in "unsigned webhooks allowed" configuration flag rather than making it the silent default.

### Proof of Concept
Preconditions: Shipit configured with two organizations, e.g. `OrgOne` (has `webhook_secret` set) and `OrgTwo` (no `webhook_secret`), both able to sync repositories tracked by Shipit — matching the schema in `test/dummy/config/secrets_double_github_app.yml`. [8](#0-7) 

1. Attacker crafts a `push` webhook POST to `/webhooks` with:
   - `X-Github-Event: push`
   - No valid `X-Hub-Signature` (or an arbitrary garbage value)
   - Body: `{"repository": {"owner": {"login": "OrgTwo"}, "full_name": "OrgOne/some-tracked-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen-sha>"}`
2. `repository_owner` resolves to `"OrgTwo"`; `Shipit.github(organization: "OrgTwo")` returns the `GitHubApp` for `OrgTwo`, whose `webhook_secret` is blank. [1](#0-0) 
3. `verify_webhook_signature` immediately returns `true` because `webhook_secret` is nil, regardless of the (invalid) `X-Hub-Signature`. [2](#0-1) 
4. `WebhooksController#create` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository','full_name')` = `"OrgOne/some-tracked-repo"`, and calls `stack.sync_github(expected_head_sha: params.after)` on the actual `OrgOne`-owned stack — despite the request never being authenticated by `OrgOne`'s secret. [7](#0-6) 

I was not able to fully trace `sync_github`/`GithubSyncJob` internals or confirm the exact downstream consequence (e.g. whether `expected_head_sha` alone can force a deploy) within the indexed context; a Devin session with full repo access would be needed to validate the complete exploit chain end-to-end and confirm real-world severity.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
