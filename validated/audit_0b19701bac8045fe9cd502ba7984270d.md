### Title
Cross-organization team hijack via unscoped `Team.find_or_create_by!(github_id:)` in `MembershipHandler` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` record solely by the numeric `github_id` supplied in the webhook payload, with no check that the payload's `organization.login` matches the `organization` already stored on that `Team` row. Because `Shipit::WebhooksController#verify_signature` only verifies that the request was validly signed for the organization named in the payload — not that the `team.id` inside the payload actually belongs to that organization — an attacker who controls any GitHub organization already onboarded into this Shipit instance can forge a signed `membership` webhook for their own org that references a `team.id` belonging to a completely different, privileged organization, and add an arbitrary user to that team.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`Team.find_by(github_id: X).organization == params['organization']['login']` for every request that reaches `team.add_member(member)`.

Trace:
- `WebhooksController#verify_signature` selects the HMAC secret via `Shipit.github(organization: repository_owner)`, and for `membership` events `repository_owner` falls back to `params.dig('organization', 'login')` [1](#0-0)  and verifies the signature with that org's own secret [2](#0-1) . This only proves the request was signed by whatever org is named in `organization.login` — it says nothing about the `team.id` value also present in the payload.
- `Shipit.github(organization:)` requires the organization to be configured in `secrets.github`, raising `GithubOrganizationUnknown` otherwise [3](#0-2) , so the attacker must control (be an admin of) one org that is already onboarded to this Shipit instance and knows/sets that org's own webhook secret — a precondition explicitly allowed by the rules ("emit webhooks from a repository/org they own").
- `MembershipHandler` validates only types via `ExplicitParameters` (`team.id` just needs to be an `Integer`) [4](#0-3) , then resolves the team purely by `github_id`:
```
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [5](#0-4) 
If a `Team` row with that `github_id` already exists (created earlier by a legitimate webhook from an unrelated, possibly privileged organization), `find_or_create_by!` returns that existing record and the block (which would set `organization`) never runs. The handler then unconditionally does `team.add_member(member)` [6](#0-5) , where `member` is created from the attacker-controlled `params.member.login` via `User.find_or_create_by_login!` [7](#0-6) , with no verification against GitHub that this user is really a member of that team.
- `Team` has no organization-scoped or org+github_id validation — it defines no `validates` at all [8](#0-7) , so nothing rejects the mismatch.
- These `Team` rows are exactly the ones gating access: `Shipit.github_teams` builds the privileged team list from configured OAuth team handles via `Team.find_or_create_by_handle` [9](#0-8) , and `User#authorized?` checks membership against those team ids [10](#0-9) , enforced in `force_github_authentication` [11](#0-10) .

Attacker's exact request: POST `/webhooks` with `X-Github-Event: membership`, `X-Hub-Signature` computed with attacker's own onboarded org's webhook secret, body:
```
{"action":"added","team":{"id":<privileged_team_github_id>,"name":"x","slug":"x","url":"http://x"},
 "organization":{"login":"attacker-org"},"member":{"login":"<attacker-controlled-login>"}}
```
This passes `verify_signature` (secret matches `attacker-org`), passes `drop_unhandled_event` (handler registered), and passes parameter validation (types only), then silently binds `member` into the pre-existing privileged `Team` row belonging to an unrelated org.

None of the existing guards catch this: `verify_signature` authenticates the *organization name in the payload*, not the *team id*; `ExplicitParameters` only checks types; `Team`/`Membership` models enforce no organization-scoped uniqueness (only `Membership` prevents duplicate rows for the same user/team pair, per `test/models/membership_test.rb`).

### Impact Explanation
An attacker who administers any GitHub organization already configured in this Shipit instance (not necessarily a privileged one) can add an arbitrary, attacker-chosen GitHub login into a `Team` belonging to a different organization, including any team enumerated in `Shipit.github_teams`. Once that login is later associated with a real (or attacker-controlled) Shipit `User` account, `User#authorized?` returns true, granting authenticated, unauthorized access to the Shipit deploy UI and its actions (deploy/rollback/merge) — an authentication/authorization bypass matching the "High – escalation into `Shipit.github_teams` authorization" category. The attack is repeatable against any team whose numeric `github_id` the attacker can obtain or guess (GitHub team ids are sequential integers and are exposed via the GitHub API for teams the attacker can see), and is not limited to a single victim organization.

### Likelihood Explanation
Preconditions: the attacker must control/administer at least one GitHub organization that is already onboarded into this specific Shipit deployment (present in `secrets.github` with a configured webhook secret), and must know a valid `github_id` for a team in the target (privileged) organization. The former is realistic for multi-tenant Shipit deployments (e.g., Shopify's own use case, where many orgs/repos share one instance); the latter requires only a value visible via GitHub's own team-listing API or brute-forcing a small integer range — no Shipit secrets are needed. Cost per attempt is a single signed HTTP POST; the attack is fully repeatable and scriptable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by organization as well as `github_id` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify on every request (not just creation) that an existing `Team`'s `organization` matches `params.organization.login`, rejecting/logging the event otherwise. Add a DB-level uniqueness constraint on `(github_id, organization)` (or `github_id`) so mismatched writes cannot silently succeed.

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerCrossOrgTest < ActiveSupport::TestCase
        test "membership event from unrelated org binds into a privileged team by colliding github_id" do
          privileged_team = Team.create!(github_id: 999_001, organization: 'victim-org', slug: 'admins', name: 'Admins', api_url: 'https://x')

          payload = {
            'action' => 'added',
            'team' => { 'id' => 999_001, 'name' => 'Admins', 'slug' => 'admins', 'url' => 'https://x' },
            'organization' => { 'login' => 'attacker-org' }, # different org signs this
            'member' => { 'login' => 'attacker-controlled-user' }
          }

          # Simulates the binding claimed to be broken:
          # Before: privileged_team.organization == 'victim-org'
          assert_equal 'victim-org', privileged_team.organization

          MembershipHandler.call(payload)

          resolved_team = Team.find_by(github_id: 999_001)
          # Bug: same row is reused, organization field untouched, but membership granted
          assert_equal privileged_team.id, resolved_team.id
          assert_equal 'victim-org', resolved_team.organization # still victim-org, proving no re-binding occurred
          assert resolved_team.members.exists?(login: 'attacker-controlled-user'),
                 "attacker-controlled user was added to victim-org's privileged team via attacker-org's signed webhook"
        end
      end
    end
  end
end
```
This demonstrates `Team.find_or_create_by!(github_id: X)` returning the pre-existing `victim-org` record for a payload whose `organization.login` is `attacker-org`, with `member.login` fully attacker-controlled and no organization-scoped validation preventing the write.

# frozen_string_literal: true

module Shipit
  class Team < Record
    REQUIRED_HOOKS = %i[membership].freeze

    has_many :memberships
    has_many :members, class_name: :User, through: :memberships, source: :user

    has_many :github_hooks,
             -> { where(event: REQUIRED_HOOKS) },
             foreign_key: :organization,
             primary_key: :organization,
             class_name: 'GithubHook::Organization',
             inverse_of: false

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
    end

    def refresh_members!
      github_api = Shipit.github(organization:).api
      github_members = Shipit::OctokitIterator.new(github_api.get(api_url).rels[:members])
      members = github_members.map { |u| User.find_or_create_from_github(u) }
      self.members = members
      save!
    end

    def github_team=(github_team)
      self.name = github_team.name
      self.slug = github_team.slug
      self.api_url = github_team.url
      self.github_id = github_team.id
    end
  end
