## Finding: Valid

### Title
`allow_missing_txn_authentication_key` skips fee-payer key verification for *any* account whenever DAA is globally enabled, not only for accounts actually using it - ([File: aptos-move/framework/aptos-framework/sources/transaction_validation.move])

### Summary
`unified_prologue_fee_payer_v2` allows the fee-payer authentication-key check to be bypassed whenever `fee_payer_public_key_hash` is `Option::none()`, by delegating to `allow_missing_txn_authentication_key(fee_payer_address)`. That helper's derivable-account-abstraction (DAA) branch tests only the **global** feature flag `features::is_derivable_account_abstraction_enabled()` and performs **no per-account check** that `fee_payer_address` is actually a DAA account — unlike its sibling branch for classic account abstraction, which correctly calls `account_abstraction::using_dispatchable_authenticator(transaction_sender)`.

### Finding Description
`unified_prologue_fee_payer_v2` performs the fee-payer binding check like this: [1](#0-0) 

When `fee_payer_public_key_hash` is `None`, it defers entirely to: [2](#0-1) 

Note the asymmetry: the account-abstraction (V1) disjunct is address-scoped (`using_dispatchable_authenticator(transaction_sender)`), but the derivable-account-abstraction disjunct is a bare global feature-flag test with no binding to `transaction_sender`/`fee_payer_address` at all. Once DAA is enabled network-wide (a normal, expected on-chain state), this function returns `true` for **every** address, whether or not that address ever used derivable account abstraction.

On the Rust side, a `None` proof for the fee payer is produced either by a genuine `AuthenticationProof::Abstract` (verified cryptographically via `dispatchable_authenticate`) or by `AuthenticationProof::None`, which comes from `AccountAuthenticator::NoAccountAuthenticator`: [3](#0-2) [4](#0-3) 

Critically, when building the fee-payer signer, only the `AuthenticationProof::Abstract` arm triggers real cryptographic verification (`dispatchable_authenticate`); everything else — including `AuthenticationProof::None` from `NoAccountAuthenticator` — falls into the catch-all arm that fabricates a signer with **no verification performed**: [5](#0-4) 

Combining these two facts: a transaction whose fee-payer authenticator is `NoAccountAuthenticator` produces `fee_payer_public_key_hash = None` with zero cryptographic verification of the named `fee_payer_address`, and the Move-side check then trusts `allow_missing_txn_authentication_key`, which (via the DAA global-flag branch) will assert `true` for that address even though it never used any account-abstraction scheme and never proved control of its authentication key.

The doc comment on the parameter itself states the intended invariant that this code violates:
```
// None means no need to check, i.e. either AA (where it is already checked) or simulation
``` [6](#0-5) 
The invariant "either AA (already checked) or simulation" is not actually enforced for the `NoAccountAuthenticator` case, because the DAA branch of `allow_missing_txn_authentication_key` does not confirm that "AA was already checked" for that specific address — it only checks that the feature is turned on somewhere on the network.

### Impact Explanation
An unprivileged attacker can construct a `TransactionAuthenticator::FeePayer` where `fee_payer_signer = NoAccountAuthenticator` and `fee_payer_address` is an arbitrary victim account that uses a normal (non-AA) authentication scheme. If `is_derivable_account_abstraction_enabled()` is on (as it typically is on live networks), `unified_prologue_fee_payer_v2` will not abort with `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY` even though the victim never signed anything and never proved control of its key. This breaks the fee-payer/gas-binding guarantee that transaction admission is supposed to enforce, letting an attacker name an arbitrary account as gas payer without any proof of authorization from that account.

### Likelihood Explanation
Exploitability requires only that the DAA feature flag be enabled network-wide — a normal production configuration, not a privileged or exotic state — and requires no signature or key material from the named fee-payer account. The remaining open question (which I could not fully verify given tool-call limits) is whether `AccountAuthenticator::NoAccountAuthenticator::verify()` in `types/src/transaction/authenticator.rs`, or an earlier admission-layer gate (e.g., mempool/vm-validator or `crates/aptos-transaction-filters`), rejects a `NoAccountAuthenticator` fee-payer authenticator on non-simulation transactions before it reaches the prologue. This should be confirmed to establish full end-to-end exploitability.

### Recommendation
Make `allow_missing_txn_authentication_key`'s DAA branch address-scoped, e.g., only allow a missing auth key if the account's authentication key was actually derived via the DAA scheme (mirroring the `using_dispatchable_authenticator` check on the classic-AA branch), rather than trusting a global feature toggle alone. Additionally, verify (and if necessary add) an explicit admission-time restriction preventing `AccountAuthenticator::NoAccountAuthenticator` from being accepted as a fee-payer or sender authenticator for any transaction that is not a simulation.

### Proof of Concept
1. Ensure network has `derivable_account_abstraction` feature enabled (typical mainnet/testnet state).
2. Craft a `SignedTransaction` with `TransactionAuthenticator::FeePayer { sender: <attacker's valid Ed25519 authenticator>, fee_payer_address: <victim_address_using_plain_ed25519>, fee_payer_signer: AccountAuthenticator::NoAccountAuthenticator, .. }`.
3. Submit for real execution (`is_simulation = false`).
4. Observe that `run_script_prologue` computes `fee_payer_public_key_hash = None` (from `AuthenticationProof::None::optional_auth_key()`), calls `unified_prologue_fee_payer_v2`, hits the `else` branch, and `allow_missing_txn_authentication_key(victim_address)` returns `true` purely because DAA is globally enabled — the `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY` assert at [7](#0-6)  does not fire, despite the victim never having authenticated.
