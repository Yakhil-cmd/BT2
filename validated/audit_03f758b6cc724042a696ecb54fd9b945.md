### Title
Cross-organization `Team` hijack via `Team.find_or_create_by!(github_id:)` ignoring `organization` — ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, with no check that the webhook's `organization.login` matches the `organization` column already stored on that row. A properly-signed `membership` webhook from an unrelated, legitimately onboarded GitHub organization can therefore attach an arbitrary GitHub login as a `Membership` to a `Team` row that actually belongs to a different organization, including one referenced by `Shipit.github_teams`.

### Finding Description
The broken binding is: `Team#organization == params.organization.login` for any `Team` mutated by a `membership` webhook. This is never enforced.

Code path:
- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that organization's own `webhook_secret` [1](#0-0) . This only proves the request came from *some* configured organization — the one named in the payload — not that it came from the organization that owns the target `Team`.
- `MembershipHandler#process` calls `find_or_create_team!` then unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))` for `action == 'added'` [2](#0-1) .
- `find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [3](#0-2) . When a row with that `github_id` already exists (created for a different organization), the block is skipped entirely — `organization` is never re-validated against the payload's `organization.login`.
- `Shipit.github_teams` builds the authorization gate from configured `oauth.teams` handles via `Team.find_or_create_by_handle` [4](#0-3) , and `User#authorized?` checks membership against exactly those team ids [5](#0-4) .

Exploit flow: an attacker who administers a second GitHub organization that is legitimately configured as a Shipit tenant (its own `webhook_secret` under `secrets.github`) sends a `membership` `added` webhook, signed with their own valid secret, naming `team.id` equal to the `github_id` of a `Team` row that belongs to a *different* tenant organization and is listed in that tenant's `Shipit.github_teams`. `find_or_create_by!` matches the existing row by `github_id` alone, skips re-validation, and `team.add_member(...)` grants the attacker-named user a `Membership` on that team — a team they were never invited to.

No existing guard stops this: `verify_signature` only authenticates the *claimed* organization, not team ownership; `ExplicitParameters` schema only validates types/presence, not cross-object consistency; there is no model-level check comparing `organization` to the pre-existing row before skipping the creation block.

### Impact Explanation
Any user added this way inherits every capability gated by `Shipit.github_teams` — deploy, rollback, merge — through `Authentication#force_github_authentication` -> `User#authorized?` [5](#0-4) . This is a cross-tenant boundary violation: a webhook authenticated for organization B mutates a `Team` record that belongs to and gates authorization for organization A. It is repeatable for any `github_id` the attacker can determine, and works against every deployment where more than one organization is configured under `secrets.github` (the documented multi-org support in `Shipit.github_organizations`/`github_app_config`) [6](#0-5) .

### Likelihood Explanation
Requires: (1) the Shipit instance to have multiple organizations configured (multi-tenant setup, a supported and documented configuration), (2) the attacker to control one of those organizations well enough to trigger/emit a genuine `membership` webhook with a valid signature for their own org, and (3) knowledge of the `github_id` of a target `Team` in another tenant. Condition (3) is the weakest link — GitHub team ids are not trivially discoverable without membership in the target org in most cases, so real-world exploitability depends on operational leakage of that id (e.g., logs, prior webhook payload sniffing, GitHub API access as a member of the target org at some point). Given the multi-org precondition, this is a real, in-repo logic flaw rather than a purely theoretical one.

### Recommendation
Scope the lookup in `find_or_create_team!` by both `github_id` and `organization`, and reject (or update-without-reuse) when an existing row's `organization` differs from `params.organization.login`. For example: `Team.find_by(github_id: params.team.id, organization: params.organization.login) || Team.create!(...)`, raising/logging on `github_id` collision across organizations instead of silently reusing the row.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/team_test.rb` style):
1. Create `team_a = Team.create!(github_id: 999, organization: 'org-a', slug: 'devs', name: 'Devs', api_url: 'http://x')`.
2. Assert precondition: `team_a.organization == 'org-a'` and `params.organization.login` will be `'org-b'` (different).
3. Stub `verify_signature` (as existing tests do via `GithubHook.any_instance.stubs(:verify_signature).returns(true)` or equivalent) to simulate a valid signature from `org-b`.
4. POST a `membership` webhook: `{action: 'added', team: {id: 999, name:'x', slug:'x', url:'x'}, organization: {login: 'org-b'}, member: {login: 'attacker'}, repository: {owner: {login: 'org-b'}}}`.
5. Assert: `Membership.exists?(team_id: team_a.id, user: User.find_by(login: 'attacker'))` is `true`, while `team_a.reload.organization` is still `'org-a'` — proving a webhook authenticated for `org-b` mutated a team belonging to `org-a`, violating the `Team#organization == params.organization.login` binding.
