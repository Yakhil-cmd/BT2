### Title
Unsanitized attestation certificate extension values (BuildConfigURI/BuildSignerURI) reach `Handler.PrintBulletPoints` and are written raw to the terminal - (File: pkg/cmd/attestation/verify/verify.go)

### Summary
`runVerify` extracts `sourceRepoAndOrg`, `sourceWorkflow`, `signerRepoAndOrg`, and `signerWorkflow` from the certificate's `BuildConfigURI`/`BuildSignerURI` extensions via `extractAttestationDetail` and passes them directly to `opts.Logger.PrintBulletPoints`, which writes them with a raw `fmt.Fprintln` to `h.IO.ErrOut`. Unlike other places in this codebase (`pkg/cmd/repo/view/http.go`, `pkg/cmd/run/view/view.go`, `pkg/cmd/pr/diff/diff.go`, `pkg/cmd/workflow/shared/shared.go`, `pkg/cmd/skills/list/list.go`) that explicitly wrap externally-derived content in `iostreams.Untrusted` before printing to sanitize ANSI escapes, `verify.go`/`handler.go` never route this attacker-influenceable data through `asciisanitizer`.

### Finding Description
`extractAttestationDetail` (pkg/cmd/attestation/verify/verify.go:351-386) applies `regexp.MustCompile` with a greedy `.+` capture group over `builderSignerURI` to derive the workflow path segment, then returns it unmodified. In `runVerify` (verify.go:322-345) these values are placed into `rows` and handed to `opts.Logger.PrintBulletPoints(rows)`.

`Handler.PrintBulletPoints` (pkg/cmd/attestation/io/handler.go:71-88) builds a string from the rows and writes it with `fmt.Fprintln(h.IO.ErrOut, info)` — no ANSI-escape stripping, no `iostreams.Untrusted` wrapper, unlike the `Untrusted.String()` sanitization path (pkg/iostreams/untrusted.go:35-44) used elsewhere in the codebase for exactly this class of remote-controlled data.

The `BuildConfigURI`/`BuildSignerURI` X.509 certificate extension values are populated by GitHub's Fulcio/OIDC issuance process from the actual repository name and workflow file path used at Actions runtime. While GitHub's web UI restricts filenames, `git` itself does not require workflow/tree entry path bytes to exclude control characters (only NUL and `/` are disallowed at the git object level) — a repository/workflow file path pushed directly via `git` (bypassing the web UI) could therefore contain raw control bytes such as `\x1b`. Git ref names (branch names, which also appear in the workflow string as `@refs/heads/<branch>`) are more strictly validated by `git-check-ref-format` and disallow control characters, but the repository name and the workflow *path* component are less strictly constrained. An attacker who owns a public repo and workflow could thus craft a path segment/name containing ANSI escape byte sequences that survive into `BuildConfigURI`/`BuildSignerURI`, survive the `.+` regex capture, and end up unsanitized in `PrintBulletPoints`'s output to `ErrOut`.

### Impact Explanation
This is a terminal-escape-sequence injection into the victim's stderr stream when running `gh attestation verify --owner <attacker-owner>` (or `--repo`) against attacker-controlled/attacker-owned artifacts and workflows. Depending on the victim's terminal emulator, this can be used to spoof output, hide/obscure legitimate verification results, move the cursor, set the terminal title, or in vulnerable terminal emulators trigger more serious effects (e.g., OSC-based clipboard/query abuses). This matches GitHub's "terminal escape sequence / output injection" bounty impact class, since the codebase's own existing mitigation pattern (`iostreams.Untrusted`) demonstrates GitHub has already classified untrusted-content-to-terminal as an output-safety concern requiring sanitization.

### Likelihood Explanation
Preconditions: attacker needs only an unprivileged public GitHub account and repo/workflow they fully control (no special permissions), and must be able to push a workflow file whose path contains control-byte sequences via direct git plumbing rather than the GitHub web UI (feasibility of this specific precondition is not fully confirmed from the code alone — it depends on GitHub server-side filename validation, which is outside this repo's code and could not be verified here). The victim must run `gh attestation verify` pointed at that attacker owner/repo, which is a normal, expected usage pattern (verifying artifacts from third-party repos is the primary use case of this command) with a TTY stderr.

### Recommendation
Wrap `sourceRepoAndOrg`, `sourceWorkflow`, `signerRepoAndOrg`, and `signerWorkflow` in `iostreams.Untrusted(...)` before passing them into `rows`/`PrintBulletPoints`, consistent with the sanitization pattern already used in `pkg/cmd/repo/view/http.go`, `pkg/cmd/run/view/view.go`, `pkg/cmd/pr/diff/diff.go`, `pkg/cmd/workflow/shared/shared.go`, and `pkg/cmd/skills/list/list.go`. Alternatively/additionally, harden `Handler.PrintBulletPoints`/`Printf`/`Println` to sanitize all values through `asciisanitizer` before writing to `h.IO.ErrOut`, since these are general-purpose output helpers used with values whose provenance is not always trusted by every caller.

Expected today: the assertion fails because `errOut` contains the raw `0x1B` bytes, since `extractAttestationDetail`'s output flows into `PrintBulletPoints` → `fmt.Fprintln(h.IO.ErrOut, info)` with no `asciisanitizer`/`Untrusted` wrapping.
