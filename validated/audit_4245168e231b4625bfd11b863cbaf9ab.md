### Title
Consistency assert on stake delegation vs. calculated epoch reward is violated by an ordinary stake instruction executed between reward calculation and distribution, crashing the validator - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
The report's bug class is "a snapshot taken for a state transition is not kept consistent with mutations that happen before the snapshot is fully consumed, letting a user action landing in the gap corrupt/double-use accounting." The closest reachable analog in this codebase is in the partitioned epoch-rewards distribution path: `build_updated_stake_reward` asserts that a stake account's *current* delegation (read live from `StakesCache` at distribution time) plus the previously-calculated stake reward equals the delegation value that was snapshotted at the epoch-boundary calculation time. Any ordinary, unprivileged stake-program instruction that changes `Delegation::stake` for that account between the calculation block and its scheduled distribution block (which can be many blocks later, since payouts are spread over `num_partitions` blocks) breaks this invariant and hits a hard `assert_eq!`, panicking the bank-processing thread on every validator that processes that block.

### Finding Description
`Bank::distribute_partitioned_epoch_rewards` -> `distribute_epoch_rewards_in_partition` -> `store_stake_accounts_in_partition` -> `Bank::build_updated_stake_reward` in [1](#0-0)  reads the account's *live* delegation from `stakes_cache_accounts` at the block height when the reward for that stake account is actually paid out (a block that can be many slots after the epoch-boundary calculation, since rewards are hashed into `num_partitions` and paid out one partition per block): [2](#0-1) 

When the `adjust_delegations_for_rent` (i.e. `relax_post_exec_min_balance_check`) feature is not active, the code takes the `else` branch and enforces:
```
expected_delegation = stake.delegation.stake + partitioned_stake_reward.inflation.stake_reward
assert_eq!(expected_delegation, new_stake.delegation.stake)
```
where `stake` is the *current* on-chain delegation (fetched live at distribution time) and `new_stake` (`partitioned_stake_reward.inflation.stake`) is the delegation that was snapshotted and reward-adjusted back at the epoch-boundary calculation time (see `redeem_stake_rewards` in [3](#0-2) , where `stake.delegation.stake += staker_rewards` happens against the calculation-time delegation).

This assertion is silently relying on the invariant "no stake instruction touches `Delegation::stake` for this pubkey between calculation and its distribution block." That invariant is not enforced anywhere: the stake program continues to accept ordinary user-initiated instructions (Split, Merge, Deactivate/Redelegate flows that alter `Delegation::stake`) against the same stake account at any time, including during the multi-block reward-distribution window, because there is no lock/guard tying stake-account mutability to `EpochRewardStatus::Active`.

An unprivileged holder of a stake account's authority can:
1. Observe (or predict, since `hash_rewards_into_partitions` is a deterministic function of the parent blockhash and pubkey/`num_partitions`) which future block height their stake account's reward partition will be processed in.
2. Submit an ordinary `Split` (or other delegation-mutating) instruction for their own stake account in an earlier block, changing `Delegation::stake` for that pubkey.
3. When the block containing their assigned partition index is processed, `build_updated_stake_reward` computes a mismatched `expected_delegation` vs. `new_stake.delegation.stake` and hits the `assert_eq!`, panicking the bank-processing code path.

Because block/bank processing is deterministic and run independently by every validator on the network, this panic occurs identically on every node that processes the offending block, producing a synchronized crash across the cluster rather than a fork — i.e., a transaction-triggered halt.

### Impact Explanation
A single ordinary, permissionless stake-program transaction (no special privileges, no validator-operator access, no leader collusion) can deterministically crash every validator that processes the block, because the crash is a `panic!`/`assert_eq!` inside bank-commit-critical code (`Bank::distribute_partitioned_epoch_rewards`), which runs on every replaying/voting node. This is a cluster-halting availability bug reachable purely by submitting a stake-account-mutating transaction timed to land inside the active `EpochRewardStatus::Distribution` window for that account's assigned partition block.

### Likelihood Explanation
The reward-distribution window and per-account partition assignment are both deterministic and knowable/predictable ahead of time (based on parent blockhash and `num_partitions`), so an attacker who owns any stake account earning a reward can reliably choose the right block to submit a delegation-altering instruction (e.g. `Split`). The only limiting factor is whether the `relax_post_exec_min_balance_check` feature (which switches the code to the non-asserting `adjust_delegation_for_rent` branch) is active on the target cluster; wherever/whenever that feature is not yet activated, this `assert_eq!` path is live and directly reachable by any staker.

### Recommendation
Do not assert equality between the live (current) delegation and the calculation-time snapshot; instead, recompute the reward/delegation update purely relative to the calculation-time snapshot (as is already done in the `adjust_delegations_for_rent` branch), and treat mismatches as either (a) skip/burn the reward gracefully (as the `Err` path already does for missing accounts) or (b) explicitly disallow delegation-mutating stake instructions on accounts with a pending/uncredited partitioned reward until distribution completes for that pubkey. At minimum, replace the `assert_eq!` with a recoverable `DistributionError` variant so that an inconsistency degrades to "burn/skip this reward" instead of a process-wide panic.

### Proof of Concept
1. Enable/confirm `relax_post_exec_min_balance_check` (`adjust_delegations_for_rent`) is inactive for the target epoch (or run a test/localnet with it deactivated, as several existing tests already exercise: see `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` tests such as the ones building `PartitionedStakeReward`s directly, e.g. lines 942-1013).
2. Create/delegate a stake account and let it accrue an epoch-boundary reward so it is included in `PartitionedStakeRewards` (`calculate_stake_rewards_and_commissions`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:779-872`).
3. After the epoch boundary but before the block corresponding to this stake account's assigned partition index (`hash_rewards_into_partitions`), submit a `Split` instruction from the stake account's authority that reduces `Delegation::stake` for that pubkey.
4. Advance to the block that processes that partition; `Bank::distribute_partitioned_epoch_rewards` → `store_stake_accounts_in_partition` → `build_updated_stake_reward` computes `expected_delegation = (reduced) stake.delegation.stake + stake_reward`, which no longer equals `new_stake.delegation.stake` (computed from the pre-Split delegation), and the `assert_eq!` at [4](#0-3)  panics, crashing the bank-processing thread on every validator replaying that block.     pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);

        distribution_epoch: u64,
        stake_history: &StakeHistory,
        new_warmup_cooldown_rate_epoch: Option<Epoch>,
        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
        partitioned_stake_reward: &PartitionedStakeReward,
        rent: &Rent,
        adjust_delegations_for_rent: bool,
    ) -> Result<StakeReward, DistributionError> {
        let stake_account = stakes_cache_accounts
            .get(&partitioned_stake_reward.stake_pubkey)
            .ok_or(DistributionError::AccountNotFound)?
            .clone();

        let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
        let StakeStateV2::Stake(meta, stake, flags) = stake_state else {
            // StakesCache only stores accounts where StakeStateV2::delegation().is_some()
            unreachable!(
                "StakesCache entry {:?} failed StakeStateV2 deserialization",
                partitioned_stake_reward.stake_pubkey
            )
        };
        account
            .checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
        account
            .checked_add_lamports(partitioned_stake_reward.block_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;

        let mut new_stake = partitioned_stake_reward.inflation.stake;
        if adjust_delegations_for_rent {
            let minimum_balance = rent.minimum_balance(account.data().len());
            // The rewarded epoch is right before the distribution epoch
            let rewarded_epoch = distribution_epoch.saturating_sub(1);
            // The entry in `partitioned_stake_reward` contains the rewards,
            // calculated during the calculation phase
            let delegation_with_rewards = new_stake.delegation.stake;
            adjust_delegation_for_rent(
                &mut new_stake.delegation,
                rewarded_epoch,
                delegation_with_rewards,
                account.lamports(),
                minimum_balance,
            );
        } else {
            let expected_delegation = stake
                .delegation
                .stake
                .saturating_add(partitioned_stake_reward.inflation.stake_reward);
            assert_eq!(
                expected_delegation, new_stake.delegation.stake,
                "stake reward delegation must be consistent with the updated stake account \
                 lamport balance"
            );
