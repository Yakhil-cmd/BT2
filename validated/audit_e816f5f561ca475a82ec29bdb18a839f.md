### Title
Unallowlisted PR-label env keys (e.g. `BASH_ENV`) merged into `Stack#env` reach `git`/step subprocess environment - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges every pull-request label name (uppercased) as a new environment-variable key with no allowlist, and `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload. Those keys flow unfiltered through `StackCommands#env`/`TaskCommands#env` into `Command#unbundled_env`, which is passed to `PTY.spawn`, so a PR author fully controls arbitrary environment-variable keys (not just values) for every `git` and `shipit.yml` step invocation on that stack.

### Finding Description
The broken binding: the invariant claimed by the question is that the set of keys reaching `PTY.spawn` should be restricted to `deploy_spec.machine_env` and declared `VariableDefinition` names, i.e. `keys(PTY.spawn env) ⊆ declared_variable_names`. That equality does **not** hold.

Trace:
- `LabelCapturingHandler#capture_labels` takes the label names straight from the webhook body with no sanitization or allowlist: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [1](#0-0) . The only schema constraint is `requires :name, String` [2](#0-1)  — any string is accepted as a label name, including `bash_env` or `BASH_ENV`.
- `ReviewStack#env` merges these label names (uppercased) as **environment-variable keys**, each set to `"true"`, with no allowlist filtering the resulting key set: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [3](#0-2) .
- `StackCommands#env` (`super.merge(@stack.env)`) and `TaskCommands#env` (`super.merge(@stack.env).merge(...)`) both incorporate this unfiltered hash: [4](#0-3) [5](#0-4) . Note the order: `.merge(deploy_spec.machine_env).merge(@task.env)` come *after* `@stack.env`, so `machine_env`/task env can override the same key, but they do **not** remove or filter out any extraneous keys introduced by `@stack.env`; the label-derived key remains in the final hash unless a later merge happens to use the identical key name.
- `StackCommands#fetch`/`#git_clone` pass this hash straight to the `git` command: `git('fetch', 'origin', ..., env:, chdir: @stack.git_path)` and `git_clone(@stack.repo_git_url, @stack.git_path, branch: @stack.branch, env:, chdir: @stack.deploys_path)` [6](#0-5) [7](#0-6) .
- `Command#unbundled_env` merges `@env.stringify_keys` (the attacker-influenced hash) directly over `BASE_ENV` with **no key allowlist at all**: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [8](#0-7) , and `#start` passes that hash straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [9](#0-8) .

Exploit flow: an attacker who owns a fork and opens a pull request against a repository that already has a Shipit `ReviewStack` configured, adds a label whose name (case-insensitive) becomes `BASH_ENV` after uppercasing (e.g. label `"bash_env"`), pointing to a file path they also control or can write via their branch checked into the working directory (e.g. a file inside the repo's `.git`/working tree written by an earlier step, or a path they can influence). GitHub's `labeled` webhook is signature-verified by `verify_signature`/`GitHubApp#verify_webhook_signature` before reaching `LabelCapturingHandler`, but signature verification only proves the payload came from GitHub for that configured repository — it does not validate or restrict the *label name string itself*. Once the label is captured, every subsequent `fetch`/`git_clone`/task step for that review stack carries `BASH_ENV=<attacker string>` in the process environment.

Whether this actually yields code execution depends on whether any subprocess spawned in that environment ends up invoking a **bash** shell in non-interactive mode (e.g., a git hook, a `sh -c` step in `shipit.yml` on a system where `/bin/sh` is bash, or an explicit `bash -c` step) — `PTY.spawn`'s multi-argument form (`git`, `clone`, ...) executes via `execve` directly and does not by itself consult `BASH_ENV`; risk is highest for `shipit.yml` step commands that are single shell-metacharacter strings, which Ruby/`Process.spawn` will route through a shell. I was not able to fully verify from this index whether the deployment's shell steps are guaranteed to invoke `bash` versus `dash`/`sh`, so the precise reachability to arbitrary code execution via `BASH_ENV` specifically is plausible but not conclusively demonstrated purely from this repo's code; the underlying vulnerability — arbitrary, unallowlisted environment KEY injection reaching every `git`/step subprocess for a review stack — is confirmed and is a serious issue independent of the specific `BASH_ENV` vector, since other dangerous keys (`GIT_SSH_COMMAND`, `GIT_ASKPASS`, `LD_PRELOAD`, `PATH`, `IFS`, etc.) are equally unfiltered and some (`GIT_SSH_COMMAND`) are directly consulted by `git` itself without requiring a bash shell at all.

No existing guard closes this gap: `verify_signature` only authenticates payload origin, not label content; there is no `EnvironmentVariables#permit`-style allowlist applied to `ReviewStack#env` or to `Command#unbundled_env`; `Stack#environment` format validation (`/\A[a-z0-9\-_:]+\z/`) applies to the stack's deploy environment name, not to PR label strings; `DeploySpec`'s `VariableDefinition`/`machine_env` mechanism is never consulted to filter or restrict `@stack.env`'s key set before it reaches `Command`.

### Impact Explanation
An unprivileged fork PR author can inject arbitrary environment variable **keys** (not just interpolated values) into every `git fetch`/`git clone` and `shipit.yml` step subprocess executed for their own review stack, on the Shipit deploy host. Because `git` itself honours several dangerous env vars regardless of shell involvement (e.g., `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_PROXY_COMMAND`), and step commands may be shell-invoked, this can escalate to Remote Code Execution on the deploy host, matching the Critical RCE class. The blast radius is scoped to the review stack backing the attacker's own PR/repo (since `@stack.env` is per-stack), but the deploy host and any credentials in `BASE_ENV` (e.g. `GITHUB_TOKEN`) shared by the process are exposed to that execution context.

### Likelihood Explanation
Preconditions: the target repository must have GitHub review-stack provisioning enabled in Shipit, and the attacker must be able to open a PR (fork PR) and label it — both are standard, low-cost, unprivileged actions requiring no Shipit credentials, session, or GitHub App secrets. The webhook signature check only gates that GitHub sent the event for a real repo/PR, which any repository contributor can trigger by labeling their own PR. This is fully repeatable by any user against any repository with review stacks enabled.

### Recommendation
Restrict the keys merged from PR labels (and from `@stack.env` in general) to an explicit allowlist of environment variable names — e.g., only allow keys declared in `DeploySpec#machine_env`/`VariableDefinition` names, or route them through a dedicated namespaced label context (e.g. `LABEL_<name>`) instead of raw environment keys. Apply the same allowlist inside `Command#unbundled_env` before merging `@env` over `BASE_ENV`, rejecting/dropping any key not in the permitted set (particularly blocking known dangerous names such as `BASH_ENV`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `LD_PRELOAD`, `IFS`, `PATH`).

### Proof of Concept
Minitest plan (no live GitHub required):
1. Build a `Shipit::ReviewStack` with an associated `Shipit::PullRequest` whose `labels` include `"bash_env"`.
2. Assert `review_stack.env["BASH_ENV"] == "true"` to prove the unallowlisted key reaches `Stack#env`.
3. Build `Shipit::StackCommands.new(review_stack).env` and assert it also contains `"BASH_ENV" => "true"`.
4. Instantiate `Shipit::Command.new("git", "fetch", env: stack_commands.env, chdir: tmp_dir)` and assert `command.unbundled_env["BASH_ENV"] == "true"`, demonstrating the key survives into the hash passed to `PTY.spawn` with no allowlist filtering.
5. (Optional, for full confirmation) stub `PTY.spawn` to capture the env argument and assert the `BASH_ENV` key is present in the captured hash when `Command#start` is invoked.
