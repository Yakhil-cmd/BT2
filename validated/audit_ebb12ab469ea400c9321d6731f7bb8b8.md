### Title
Cross-tenant `Status` forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` only proves that a webhook payload was signed with the secret configured for the organization named in the payload's `repository.owner.login`/`organization.login` field, not that the payload's `sha` belongs to a commit owned by that organization. `StatusHandler#process` then resolves the target `Commit` purely by `Commit.where(sha: params.sha)` with no join/filter on repository or stack, so a signature that authenticates organization A is used to authorize a `Status` write against any `Commit` row in the database whose `sha` matches, including rows belonging to organization B's stack.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`organization_verified_by(verify_webhook_signature) == organization_owning(Commit.find_by(sha: params.sha).stack)`

Trace:
1. `verify_signature` computes `repository_owner` from the payload's own `repository.owner.login` (or `organization.login`) and fetches `Shipit.github(organization: repository_owner)`, then checks the HMAC signature against that org's `webhook_secret`. [1](#0-0) [2](#0-1) 
2. This only proves the request body was signed by attacker's own org's configured secret — it says nothing about which `sha` values are legitimately theirs to report status for.
3. `Shipit::Webhooks::Handlers::StatusHandler#process` calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no `Repository`/`Stack` scoping tying the lookup back to `repository_owner`. [3](#0-2) 
4. `Commit#create_status_from_github!` → `add_status` creates a `Status` row, reloads the commit's aggregate `status`, and if the state transitions, fires `stack.schedule_merges` (when new status is pending or success) or emits `deployable_status`/`commit_status` hooks. [4](#0-3) [5](#0-4) 

Exploit flow: an attacker registers/owns their own GitHub organization tracked by this Shipit instance (satisfying `webhook_secret` for that org only). Any Shipit-tracked commit `sha` from a *different* organization's stack is knowable (git commits are content-addressed and public; a fork of the victim's public repo reproduces byte-identical SHAs for shared commits, or an attacker can simply observe a public commit's sha). The attacker sends `POST /webhooks` with header `X-Github-Event: status`, a body signed with their own org's secret, `repository.owner.login` set to their own org (so `verify_signature` passes), and `sha` set to the victim's commit sha. `verify_signature` succeeds because it only checks the attacker's own secret. `StatusHandler#process` then finds and mutates the victim's `Commit` row (in the victim's stack) purely because `sha` matches, with no check that the commit's `stack.repository` is owned by the org that authenticated the request.

Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler.params`, `check_if_ping`) validate payload shape/event type only — none of them tie the authenticated organization to the target commit's stack/repository. `force_github_authentication`, `User#authorized?`, and `require_permission!` are irrelevant here since this is an unauthenticated webhook endpoint by design; the intended trust boundary is supposed to be enforced by the signature-to-repository binding, and it is not.

### Impact Explanation
An attacker can inject arbitrary forged CI `Status` records (state: success/failure/pending, arbitrary `description`/`target_url`/`context`) onto any commit tracked anywhere on the Shipit instance, as long as they can guess or observe that commit's sha (trivial for public repos, e.g. via fork). This can flip `Commit#deployable?`/`blocked?` for the victim's stack (`success? && !blocked?`), and can trigger `stack.schedule_merges` or continuous-deployment scheduling (`schedule_continuous_delivery`) for a stack the attacker has no relationship to. This is a payload authenticated for one organization mutating another organization's stack/commit data and potentially triggering an unauthorized merge/deploy — matching the "Critical" category (payload for one repository mutating another's stack/commit, or unauthorized deploy/merge).

### Likelihood Explanation
Preconditions are modest: the attacker needs any Shipit-tracked GitHub organization they control (to obtain a valid `webhook_secret` binding for `verify_signature`) and knowledge of a target sha from a different, victim-owned stack tracked by the same Shipit instance (obtainable via public commit history or by forking the victim's public repo, which preserves identical SHAs for shared commits). No access to the victim's repo, Shipit session, API token, or the victim's webhook secret is required. The request is a single unauthenticated `POST /webhooks` and is fully repeatable against any known sha across any tenant on the instance.

### Recommendation
In `StatusHandler#process` (and any other handler resolving commits by `sha` alone, e.g. `push_handler.rb`, `check_suite_handler.rb`), scope the `Commit` lookup by the repository/stack derived from the authenticated `repository_owner`/`repository.full_name` in the payload, e.g. `Stack.where(repository: repo).commits.where(sha: params.sha)`, so a signature verified for organization A can never resolve or mutate a `Commit` belonging to a stack outside organization A.

### Proof of Concept
Minitest plan (no live GitHub, stub `GithubHook#verify_signature`/`GitHubApp#verify_webhook_signature` to return `true` unconditionally):
1. Create `victim_stack` under `Repository` owned by `"victim-org/victim-repo"`, and a `Commit` `victim_commit` on `victim_stack` with a known `sha` (e.g. `"deadbeef" * 5`).
2. Create an attacker-configured Shipit github app entry for org `"attacker-org"` (any/no shared secret, since `verify_webhook_signature` is stubbed to `true`).
3. Assert setup binding before request: `victim_commit.stack.repository.owner != "attacker-org"` (the two organizations are distinct — establishes the equality that should block the write).
4. POST to `/webhooks` with headers `X-Github-Event: status`, `X-Hub-Signature: sha1=whatever`, and JSON body: `{"repository": {"owner": {"login": "attacker-org"}}, "sha": victim_commit.sha, "state": "success", "context": "ci/forged"}`.
5. Assert response is `200`/`:ok`.
6. Assert `victim_commit.statuses.reload.last.state == "success"` and `victim_commit.statuses.last.context == "ci/forged"` — i.e., a `Status` row was created under `victim_stack`'s commit despite the request only ever having been authenticated against `attacker-org`'s secret, proving `organization_verified_by(verify_signature) != organization_owning(target_commit.stack)` yet the write succeeded.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
