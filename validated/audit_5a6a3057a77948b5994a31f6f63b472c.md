### Title
Cross-tenant status write via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the organization named in `repository.owner.login`, while `StatusHandler#process` never reads or validates `repository.full_name` (or any repository field) at all — it looks up commits globally by `sha` across the entire installation. Unlike `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers, which all scope writes through the `Handler#stacks`/`repository` helper keyed on `payload.dig('repository', 'full_name')`, `StatusHandler` has no repository binding whatsoever, so a signature valid for one organization can write a `Status` onto any commit belonging to any other tenant's stack that happens to share the same SHA.

### Finding Description
The broken binding, stated as an equality that must hold but does not:

`organization_that_signed_the_request` (derived from `repository_owner` = `params.dig('repository','owner','login')`, used in `Shipit.github(organization: repository_owner)` at [1](#0-0)  and `repository_owner` helper at [2](#0-1) )

should equal

`organization_owning_the_repository_whose_stack_gets_mutated` (which for `StatusHandler` is never even computed, since the class omits `repository` from its `ExplicitParameters` schema entirely, unlike sibling handlers).

Tracing the code:
- `WebhooksController#create` parses the raw body and dispatches to `Shipit::Webhooks.for_event(event)` handlers without any further repo check [3](#0-2) .
- Signature verification only checks the body against the webhook secret of the org named by `repository.owner.login` [1](#0-0) .
- The base `Handler` class exposes a `stacks`/`repository_name` helper that other handlers use to scope operations to the repository named by `payload.dig('repository', 'full_name')` [4](#0-3) . `PushHandler` uses `stacks.not_archived.where(branch:)` [5](#0-4) , `CheckSuiteHandler` uses `stacks.where(branch:)` [6](#0-5) , and the `PullRequest::*` handlers resolve `Repository.from_github_repo_name(params.repository.full_name)` explicitly, e.g. [7](#0-6) .
- `StatusHandler`'s param schema requires only `sha`/`state` and never declares or reads `repository` at all, and `process` queries commits with a completely global, unscoped `Commit.where(sha: params.sha)`, then writes a `Status` to every matching commit regardless of which stack/repository it belongs to [8](#0-7) .
- The write cascades: `Commit#create_status_from_github!` → `Status.replicate_from_github!` [9](#0-8) , and `Status` has `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery, :broadcast_update` [10](#0-9) , meaning a forged status can enable CI and trigger continuous-delivery/merge processing on a completely unrelated tenant's stack.

**Attacker's exact request:** the attacker owns GitHub org `attacker-org` and has a legitimate, self-controlled webhook secret for it. They send a `status` event to `POST /webhooks` with:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
signed with `attacker-org`'s own webhook secret. `verify_signature` passes (it only checks `attacker-org`'s secret against `attacker-org`'s own payload — a fully legitimate self-signed request). `StatusHandler#process` then does `Commit.where(sha: "<victim commit sha>")`, finds the victim's commit if it exists in any stack in the database, and writes a `success`/`failure` status onto it — with zero reference to `attacker-org` anywhere in the write path.

**Getting a matching SHA without any secret:** Git commit SHAs are content-addressed hashes of tree + parents + author/committer + message + timestamps. If the victim repository is public (as is typical for open-source projects using Shipit), the attacker can fork it and obtain byte-identical commits with identical SHAs with zero access to victim secrets, satisfying the "self-controlled, no secret leak" precondition.

**Why existing guards fail:** `verify_signature` (and `GitHubApp#verify_webhook_signature`, [11](#0-10) ) only proves the body was signed by *some* organization's secret — it never cross-checks that org against the repository actually mutated. `ExplicitParameters` schema for `StatusHandler` doesn't even declare a `repository` field, so there's nothing for it to validate. No model validation on `Status`/`Commit` restricts which stack a `sha` may belong to; `Commit.where(sha:)` is a bare, unscoped lookup across every stack in the installation.

### Impact Explanation
Any GitHub org onboarded to this Shipit instance can forge a `status` webhook that writes a `Shipit::Status` record onto a commit belonging to an entirely different tenant's stack, without ever proving control of that tenant's organization or repository. Because `Status` creation cascades into `enable_ci_on_stack` and `schedule_continuous_delivery`, this can influence CI-gating and continuous-delivery/merge logic on the victim stack — a cross-tenant write triggered by an unrelated party's authenticated request, matching the "Critical: a payload for one repository mutating another's stack/commit" category. The attack is repeatable against any commit SHA the attacker can reproduce (trivial for any public fork) and is not limited to a single victim repository.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's reach: register/own any GitHub organization and repository onboarded (or onboardable) to the target Shipit instance, receive that org's own legitimate webhook secret from GitHub (standard onboarding, no leak needed), and fork a public victim repository to obtain colliding commit SHAs. No Shipit session, API token, or victim secret is required. The attack is a single crafted HTTP POST and is fully repeatable.

### Recommendation
In `StatusHandler`, require and validate `repository.full_name` in the `ExplicitParameters` schema, and scope the commit lookup through the same `stacks`/`repository_name` binding used by `PushHandler`/`CheckSuiteHandler` (e.g., `stacks.joins(:commits).where(commits: { sha: params.sha })`) instead of a global `Commit.where(sha:)`. Additionally, harden `WebhooksController#verify_signature` to cross-check that `repository.owner.login` matches the owner implied by `repository.full_name` before dispatching to any handler, closing the general class of "signed-by-org-A, targets-repo-of-org-B" payload forgeries across all handlers.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "process must not write a status onto a commit belonging to an unrelated organization's stack" do
  victim_stack   = shipit_stacks(:shipit) # repository owned by "shopify"
  victim_commit  = shipit_commits(:first) # sha X, belongs to victim_stack
  # simulate attacker's own org signing its own payload; verify_signature is out of scope for
  # this unit test since it's a controller-level concern -- the point is StatusHandler alone
  # has no repository binding to defend against this even if verify_signature is correct.
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'attacker-org' } } # no relation to victim_stack
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # Equality check that should have held but didn't:
  # organization_that_signed ("attacker-org") != organization_owning(victim_stack) ("shopify")
  # yet the write against victim_stack's commit still succeeded.
end
```
A controller-level variant should stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true` (attacker's own valid secret), POST the payload above with `X-Github-Event: status`, and assert `victim_commit.statuses.count` increased — demonstrating the write succeeds despite the signing organization never matching the victim's stack/repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
