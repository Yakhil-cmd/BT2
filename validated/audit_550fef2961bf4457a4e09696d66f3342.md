### Title
Zalo-style dedupe key collision: `handledChainsCache` in private-payment chain forwarding is scoped only by chain content, not by sender — cross-sender private payment chains are silently dropped ([File: wallet.js])

### Summary
`handlePrivatePaymentChains()` in `wallet.js` deduplicates incoming `private_payment_chains` device messages using a cache keyed **only** by the hash of the chain payload content (`objectHash.getBase64Hash(arrChains)`), with no scoping by sender (`from_address`) or session. This mirrors the reported bug class exactly: a replay/dedupe key that is not scoped across all the dimensions that make an event unique (chat/sender), causing legitimate events from different senders to collide and be silently suppressed.

### Finding Description [1](#0-0) 

```js
var handledChainsCache = {};
...
function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	...
	var cache_key = objectHash.getBase64Hash(arrChains);
	...
	if (handledChainsCache[cache_key]) {
		eventBus.emit('all_private_payments_handled', from_address);
		eventBus.emit('all_private_payments_handled-' + arrChains[0][0].unit);
		return callbacks.ifOk();
	}
	...
```

`cache_key` is derived purely from the byte content of `arrChains` (unit, message_index, payload, outputs, inputs) and does **not** incorporate `from_address` (the sending device/counterparty) at all. When the cache hit fires, the function returns immediately at the very top, **before** ever calling `network.handleOnlinePrivatePayment`, before running `checkIfAllValidated`, and before calling `forwardPrivateChainsToOtherMembersOfSharedAddresses` / `forwardPrivateChainsToOtherMembersOfOutputAddresses` (only reached via the non-cached path, at lines 1007-1017 and 1074-1076).

This is architecturally identical to the reported bug: dedupe keys must be scoped by the full identity of the event (chat + sender in the advisory; here, chain-content + sender-device). Because `ocore` intentionally allows the *same* private-payment chain content to legitimately arrive from multiple distinct correspondents — the code even documents this scenario at [2](#0-1) , "we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device" — a second, legitimate delivery of the identical `arrChains` payload from a different device/cosigner within the 1-hour cache TTL ( [3](#0-2) ) is treated as an exact duplicate and dropped without validation or forwarding.

### Impact Explanation
Private payments for private/indivisible assets are unusable by the recipient unless the full private chain is delivered and locally validated/stored (`handleOnlinePrivatePayment` / `privatePayment.validateAndSavePrivatePaymentChain`). The cross-sender collision means:
- A cosigner/counterparty on a shared/multisig address who independently forwards the same private chain (e.g., because the sender relays it to multiple members, or after a wallet reconnect/retry) can have their delivery silently swallowed by the cache from an earlier, unrelated sender's delivery.
- Since `forwardPrivateChainsToOtherMembersOfSharedAddresses`/`OfOutputAddresses` never runs on the cache-hit path, other legitimate members of a shared address may never receive the private chain needed to spend or co-sign the corresponding output, effectively freezing those funds for up to the 1-hour cache window (and beyond, if the sender does not retry after the fake `ifOk`/`all_private_payments_handled` success signal is emitted).
- The dedup logic reports false success (`callbacks.ifOk()` and `all_private_payments_handled`) to the second sender/recipient chain, masking the failure and preventing any retry logic from firing.

This matches the "AA/wallet fund loss or freezing" impact category: legitimate private-payment recipients/cosigners can be denied the data required to spend funds they are entitled to, within the deduplication window.

### Likelihood Explanation
Any paired device / private-payment counterparty that is a normal, non-malicious participant in a shared or multi-recipient private payment can trigger this by design of the protocol (the same chain content is expected to be forwarded to multiple cosigners/recipients). No malicious peer, hub, or network manipulation is required — the collision occurs purely from the insufficiently-scoped in-memory cache key on the receiving wallet.

### Recommendation
Include `from_address` (or an equivalent per-sender/session identifier) in `cache_key`, e.g. `objectHash.getBase64Hash(arrChains) + '-' + from_address`, so that identical chain content received from distinct legitimate senders is processed and forwarded independently, matching the scoping fix pattern used in the referenced advisory (scope dedupe keys across the missing dimensions — here, sender identity).

### Proof of Concept
1. Wallet W is a cosigner on a shared address along with correspondent devices A and B.
2. Device A sends a `private_payment_chains` message to W containing chain `C` (this populates `handledChainsCache[hash(C)]` after successful validation).
3. Within the 1-hour cache window, device B independently sends the same content `C` (identical unit/payload — plausible when the same private chain is relayed by multiple parties for a shared output) to W.
4. W's `handlePrivatePaymentChains` computes the same `cache_key`, hits `handledChainsCache[cache_key]`, and returns `callbacks.ifOk()` immediately — never calling `network.handleOnlinePrivatePayment` or forwarding the chain associated with B's delivery.
5. If B's delivery represented information W's wallet only received from B (e.g., a race/retry, or forwarding meant to reach further cosigners downstream of B), that path is lost silently, leaving affected cosigners unable to spend/co-sign against the associated shared-address output until it is redelivered outside the cache window.
