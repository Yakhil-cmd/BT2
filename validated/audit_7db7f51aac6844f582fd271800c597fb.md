This confirms the review stack provisioning pipeline (`ReviewStackProvisioningQueue` → `PerformTaskJob` → `TaskExecutionStrategy` → `Command`/`PTY.spawn`) is the same infrastructure used for regular provisioning tasks, so a stack created through this bypass gets fed into normal task execution just like any other legitimately-authorized stack.

The analysis confirms the vulnerability exactly as described in the question.

### Title
`provision?` operator-precedence bug lets `allow_with_label`/`prevent_with_label` bypass `review_stacks_enabled: false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
Ruby's `&&`/`||` precedence causes `provision?` to only gate the `allow_all` behavior on `repository.review_stacks_enabled`; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of that flag. An attacker who can open a pull request against, or push a label to, a repository configured with review stacks disabled but `provisioning_behavior` set to a label-based mode can still trigger dynamic stack creation.

### Finding Description
The claimed binding is: for all three `provisioning_behavior` values `V`, `provision?` should equal `repository.review_stacks_enabled && behavior_matches?(V)`. Tracing the code shows this only holds for `V = allow_all`. [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, the expression parses as:
```
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
`review_stacks_enabled` appears only in the first disjunct. If a repository has `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`), the second/third disjunct can still evaluate to `true` purely based on label presence, which the attacker (the PR author, who can attach labels to their own PR, or via the `labeled`/`unlabeled` webhooks) fully controls.

`respond_to_pull_request_opened?` gates only on `params.action == "opened" && provision?` [2](#0-1) , so once `provision?` is true, `process` calls `ReviewStackAdapter#find_or_create!`, which creates a `Stack` record and enqueues it for provisioning [3](#0-2) . No other guard (`verify_signature`, `ExplicitParameters` schema, model validations) checks `review_stacks_enabled` for the label-based branches — the check simply doesn't exist for those two paths. The identical bug pattern repeats in `unarchive?` in `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:70-75` [4](#0-3) . Notably `labeled_handler.rb` and `unlabeled_handler.rb` correctly AND `review_stacks_enabled` outside the archive/unarchive predicates [5](#0-4) , confirming `opened_handler.rb` and `reopened_handler.rb` diverge from the intended (and elsewhere correctly implemented) semantics.

The existing test suite does not catch this: `configure_provisioning_behavior` defaults `provisioning_enabled: true` and no test exercises `allow_with_label`/`prevent_with_label` combined with `provisioning_enabled: false` [6](#0-5) ; the only disabled-flag test uses `behavior: :allow_all` [7](#0-6) .

### Impact Explanation
An attacker who opens (or labels) a pull request on a repository whose operator explicitly disabled dynamic review-stack provisioning (`review_stacks_enabled: false`) but left `provisioning_behavior` at `allow_with_label`/`prevent_with_label` can force creation of a `Stack`/`ReviewStack` record and enqueue it into `Shipit::ReviewStackProvisioningQueue`, feeding the same provisioning/task pipeline (`PerformTaskJob` → `TaskExecutionStrategy` → `Command`) used for legitimate deploy/provision tasks. This is an unauthorized record write and task trigger for a repository whose operator disabled that exact feature, matching the "unauthorized deploy/provision" Critical category. The bug is repeatable per pull request/label event and against any repository configured this way.

### Likelihood Explanation
Requires the repository owner to have set `review_stacks_enabled: false` while still selecting `allow_with_label` or `prevent_with_label` in `provisioning_behavior` — a plausible misconfiguration state (e.g., temporarily disabling review stacks without resetting behavior back to `allow_all`). Given that state, the attack costs the attacker nothing beyond opening a PR and/or adding a label they control, no secrets required, fully repeatable.

### Recommendation
Fix operator grouping in `provision?` (and the identical pattern in `reopened_handler.rb`'s `unarchive?`) so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
minitest matrix in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
%i[allow_all allow_with_label prevent_with_label].each do |behavior|
  test "does not create stacks when review_stacks_enabled is false (#{behavior})" do
    repository = shipit_repositories(:shipit)
    configure_provisioning_behavior(
      repository:, provisioning_enabled: false, behavior:, label: "pull-requests-label"
    )
    payload = payload_parsed(:pull_request_opened)
    payload["pull_request"]["labels"] << { "name" => "pull-requests-label" } if behavior == :allow_with_label

    assert_no_difference -> { Shipit::Stack.count } do
      OpenedHandler.new(payload).process
    end

```
Before the fix, the `allow_with_label` and `prevent_with_label` iterations fail (a stack IS created despite `review_stacks_enabled: false`), while `allow_all` passes — demonstrating the asymmetry is confined to the last two disjuncts exactly as claimed.
