Good, `GithubSyncJob#perform` fetches commits via `stack.github_commits` which calls `stack.github_api` (i.e. `Shipit.github(organization: repository.owner).api`), so the actual GitHub data fetched is fully controlled by the real `stack.repository.owner`/GitHub App — the forged `expected_head_sha` only affects retry timing, not which commits get appended. Impact is therefore limited to triggering a resync/mark-as-accessible check and cache invalidation for an arbitrary stack, not arbitrary data injection or a deploy. This narrows the exploitable impact from the `push` handler alone, but the core binding break (authenticating with org A's secret while acting on an arbitrary `repository.full_name`) still stands as the root cause. ### Title
Webhook signature is verified against the GitHub App selected by `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb](app/controllers/shipit/webhooks_controller.rb))

### Summary
In a multi-organization Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), each onboarded GitHub organization gets its own `GitHubApp` config with its own `webhook_secret`, keyed by organization login. `WebhooksController#verify_signature` selects which app/secret to use for HMAC verification based on `repository_owner`, which is read from the payload's `repository.owner.login`, falling back to `organization.login` if absent. However, once the signature check passes, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by all handlers, e.g. `PushHandler`) resolves the actual target `Repository`/`Stack` from a completely different, unchecked field: `payload.dig('repository', 'full_name')`. Nothing ties the organization whose secret authenticated the request to the repository that the handler subsequently reads/writes.

### Finding Description
- `Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when the multi-org config schema is used: [4](#0-3) 
- `WebhooksController#verify_signature` derives that organization purely from attacker-controlled JSON fields (`repository.owner.login` or `organization.login`) and never cross-checks it against `repository.full_name`: [5](#0-4) 
- Every webhook handler instead derives the acted-upon repository from `payload.dig('repository', 'full_name')`: [2](#0-1) 

The binding the system implicitly promises is: "the organization whose secret signed this request == the organization whose repository is being acted on." Nothing in the code enforces `repository.owner.login == repository.full_name.split('/').first`, and the two fields used for authentication vs. authorization are independently attacker-supplied in the raw POST body. Any actor who legitimately knows one onboarded organization's `webhook_secret` (which, per `docs/setup.md`, is chosen and known by whoever configures that organization's GitHub App, i.e. a per-org admin rather than the Shipit host) can sign an arbitrary payload with `repository.owner.login` set to their own org (to select their known secret) while setting `repository.full_name` to any other organization's repository already tracked by Shipit, and directly `POST` it to `/webhooks`, bypassing GitHub entirely.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated" and "the repository that is written," matching the analog class called out in the rules. Concretely, an attacker who only controls organization A's webhook secret can:
- Forge a `push` event that causes `PushHandler#process` to invoke `stack.sync_github` for an unrelated stack belonging to organization B, forcing a resync/`mark_as_accessible!`/cache-recompute cycle on a stack they have no legitimate relationship with: [6](#0-5) 
- Forge `pull_request`, `status`, `check_suite`, or `membership` events targeted at any tracked repository/stack, since every handler trusts `repository.full_name` without validating it against the authenticating organization.

Note the actual commit data fetched by the resulting `GithubSyncJob` still comes from `stack.github_api`, which uses the real target stack's own configured GitHub App/repo owner — so this specific `push` path does not let the attacker inject arbitrary commit SHAs, capping the concrete impact of that one handler. The severity therefore depends on which handler is reached; handlers that mutate state purely from payload content (e.g., PR label/status updates, review-stack provisioning/archival) are more directly impactful since they act on victim-org repositories using only the forged payload.

### Likelihood Explanation
Requires knowledge of at least one legitimately-onboarded organization's `webhook_secret` in a multi-org Shipit deployment — an "unprivileged" actor with respect to other organizations sharing the instance, but who is a trusted admin of their own onboarded org (a realistic and documented deployment topology). No GitHub write access, Shipit session, or `ApiClient` token is required; the request goes directly to the public `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), require that the organization used to select the verifying `GitHubApp`/secret matches the owner segment of `repository.full_name` (or `repository.owner.login`) that handlers subsequently act on; reject the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit with the multi-org `github` secrets schema (`docs/setup.md` "Using Multiple Github Applications"), onboarding `org-a` (attacker-known secret) and `org-b` (victim, already has a Stack tracked in Shipit).
2. Attacker crafts a JSON body: `{"ref": "refs/heads/master", "after": "<any sha>", "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, raw body)>` and sets `X-Github-Event: push`.
4. `POST /webhooks` — `verify_signature` resolves `repository_owner` to `org-a`, verifies successfully against `org-a`'s secret. `PushHandler` then resolves the target stack via `full_name = "org-b/victim-repo"` and calls `stack.sync_github`, acting on organization B's stack despite the request only having been authenticated for organization A.
