### Title
`pull_request` webhook signature verified against `repository.owner.login`'s org while `LabeledHandler` mutates the stack resolved from `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates the entire request using the GitHub App/org selected by `repository_owner` (`params.dig('repository','owner','login')`), but `LabeledHandler` (and its siblings) resolve the repository/stack to mutate strictly from `params.repository.full_name` via `Repository.from_github_repo_name`. These two fields are never checked against each other, so an attacker who controls a payload can pick which org's secret authenticates the request while pointing the mutation at a repository belonging to a completely different, victim org.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`repository_owner` (used to select the signing org/secret in `verify_signature`) **should equal** `owner(params.repository.full_name)` (used by the handler to resolve the mutated `Repository`/`Stack`) — but nothing in the code path checks this.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then does `github_app = Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(...)` [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is present for that organization's config [3](#0-2) . So any org configured in `Shipit.github_organizations` without a `webhook_secret` value trivially "authenticates" any payload whose `repository.owner.login` matches that org — regardless of the actual HMAC signature.
3. Once `verify_signature` passes, `WebhooksController#create` dispatches the raw parsed JSON to `LabeledHandler.call(params)` with no further binding of `repository_owner` to anything [4](#0-3) .
4. `LabeledHandler#repository` resolves the repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , completely independent of `repository_owner`/`repository.owner.login` used in step 1.
5. `LabeledHandler#handle` then calls `stack.archive!` or `stack.unarchive!` on the resolved review stack based on the provisioning label logic [6](#0-5) , and the target repository's review stacks (any environment, including production if `review_stacks_enabled`) are affected.

Attacker request: forge a `pull_request`/`action=labeled` JSON body where `repository.owner.login` = `attacker-org` (an org present in `Shipit.github_organizations` with no `webhook_secret` configured, so signature check short-circuits to `true`), but `repository.full_name` = `victim-org/victim-repo` (a real, unrelated repository with a production-environment review stack managed by this Shipit instance). Send it to `POST /webhooks` with header `X-Github-Event: pull_request`; the signature header content is irrelevant because `verify_webhook_signature` returns `true` without checking it when `webhook_secret` is blank for `attacker-org`.

Existing guards that fail to close this: `verify_signature` only checks HMAC against the org keyed by `repository_owner`, never cross-checks it against `repository.full_name`'s owner; `drop_unhandled_event` only checks the event type is registered, not payload consistency; the `ExplicitParameters` schema in `LabeledHandler` only requires `repository.full_name` to be a `String`, with no relationship constraint back to `repository.owner.login`; there is no model validation anywhere connecting the two owner fields within a single webhook payload.

### Impact Explanation
A payload authenticated by one organization's webhook secret (or by an org with no secret configured at all) can archive or unarchive a review stack belonging to an entirely different organization's repository, including a stack flagged as the production environment. This is a cross-tenant mutation: a party who controls (or merely names) a low-value/no-secret org can force state changes (archive/unarchive, which per `ReviewStackAdapter#unarchive!` requeues provisioning and can trigger deploy/rollback side effects) on a victim org's production stack that never authenticated the request. This matches "a payload for one repository mutating another's stack" — Critical, per the stated impact categories.

### Likelihood Explanation
Preconditions: the Shipit instance must be multi-org (i.e., `Shipit.github_organizations` configured with more than one org), and at least one configured org must have no `webhook_secret` set (or the attacker must otherwise be able to produce a valid signature for whichever org they name — which is trivial if that org has no secret). The victim repository must have `review_stacks_enabled` and an open PR whose label state can trip `archive?`/`unarchive?`. This is a repeatable, zero-privilege, single-HTTP-request attack against `POST /webhooks`, requiring no authentication, no GitHub App private key, and no knowledge of the victim's webhook secret — only knowledge of the victim's `owner/name` string and PR/label state, both public information on GitHub.

### Recommendation
Bind signature-selection identity to the mutation target: before dispatching to handlers, verify that `params.dig('repository','owner','login')` (or `organization.login`) equals the owner segment parsed from `params.dig('repository','full_name')`, and reject (422) on mismatch. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank — an org without a configured webhook secret should not be usable to authenticate incoming webhooks (fail closed, not open, e.g. return `false` or raise a configuration error).

### Proof of Concept
Minitest plan (webhook controller test level):
1. Configure `Shipit.github_organizations` with two orgs: `"attacker-org"` (no `webhook_secret` key) and `"victim-org"` (with a `webhook_secret`).
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_all")` and a `Shipit::ReviewStack`/`Stack` for it with `environment: "production"`, unarchived, plus an open `PullRequest`.
3. Build a `pull_request`/`labeled` payload with `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victit-repo"`, `action = "labeled"`, `pull_request.state = "open"`, labels chosen to satisfy `archive?` (e.g. omit provisioning label under `allow_all` — adapt per real behavior) so `stack.archive!` is invoked.
4. POST to `/webhooks` with `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature` header (or none).
5. Assert the response is `200 OK` (not `422`), proving `verify_signature` passed for `attacker-org`.
6. Assert the equality invariant is violated: before request, `stack.reload.archived? == false`; after request, `stack.reload.archived? == true`, even though the authenticating org (`attacker-org`) is not `owner(params.repository.full_name)` (`victim-org`) — i.e. `repository_owner != full_name.split('/').first` yet the mutation on `victim-org`'s production stack still occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
