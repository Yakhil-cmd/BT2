## Finding

### Title
Nested AA definitions embedded in a `definition` message are never recursively re-validated - ([File: aa_validation.js])

### Summary
`aa_validation.validateAADefinition()` performs full structural/complexity/formula validation of an Autonomous Agent (AA) definition (messages, formulas, ops, complexity budget, allowed fields, etc.). When an AA's own template contains a `definition` message (used to let an AA spawn/publish a *nested* AA definition at execution time), the validator only performs a handful of superficial checks and explicitly skips the deep, recursive call into `validateAADefinition` for the nested definition — the call is left commented out in the code.

### Finding Description
In `aa_validation.js`, the `case 'definition':` branch inside `validatePayload()` handles the `definition` app, which is the only way an AA definition template can itself embed another AA definition: [1](#0-0) 

The checks performed are only:
- `payload.definition` is a 2-element array
- no foreign fields in the payload
- `payload.definition[0] === 'autonomous agent'`
- `payload.definition[1]` is a non-empty object

None of these checks recurse into the nested definition to validate its `messages`, formulas, `getters`, `bounce_fees`, complexity (`constants.MAX_COMPLEXITY`), operation count (`constants.MAX_OPS`), or field whitelists, the way the top-level call to `validateAADefinition` does for the outer AA (see the full recursive checks performed elsewhere in the same file, e.g. for `payment`, `data_feed`, `asset` messages at [2](#0-1) ). The line that would have performed this recursive re-validation is present in the source but disabled:

```
//	(typeof setImmediate === 'function') ? setImmediate(validateAADefinition, payload.definition, cb2) : setTimeout(validateAADefinition, 0, payload.definition, cb2);
```

This is structurally identical to the CVE's root cause: a nested/inherited definition (there: the parent directory's Owner/Group SID inside the security descriptor; here: a nested AA definition embedded inside a parent AA's `definition` message) is copied/accepted into a new object graph without validating its internal structure, because the validator wrongly assumes the substructure is well-formed or will be "validated later." Here that "later" validation never happens through this path — this nested definition is exactly what gets written to `aa_addresses.definition` in storage when the `definition` message is actually executed by `aa_composer.js`, and it is subsequently loaded by `storage.readAADefinition()`/`handleTrigger()` and executed as a first-class AA without ever having passed `validateAADefinition`'s formula/complexity/schema checks.

This is reachable purely by posting/triggering an AA (in-scope surface: "AA definitions and triggers, oscript/ojson evaluation"), since any account can trigger any AA, including ones that are pre-configured (by their author) to emit a `definition` message defining a new nested AA.

### Impact Explanation
Because the nested AA definition bypasses `MAX_COMPLEXITY`/`MAX_OPS` checks and the field/format whitelists enforced by `validateAADefinition`, it can contain malformed formulas, disallowed message fields, or unbounded expression trees. When that nested AA is later triggered, `aa_composer.js`'s `handleTrigger`/formula evaluation path must process a definition that was never guaranteed to satisfy the invariants the rest of the AA execution engine assumes (bounded complexity, well-formed payment/output shapes, valid asset/address fields, etc.). This can cause:
- Uncaught exceptions/hangs during AA execution when nodes independently process the same trigger unit while stabilizing the DAG, risking inconsistent handling (bounce vs. crash vs. differing responses) between full nodes — i.e., node disagreement on validity/response of a unit.
- A denial-of-service vector where a trigger to such a malformed nested AA causes excessive computation (since op/complexity limits designed to bound AA execution cost were never enforced on the nested definition), potentially stalling processing of subsequent units that depend on stabilization of this trigger.

### Likelihood Explanation
Any account can craft and post a normal AA definition whose template includes a `definition` app message with an arbitrary "nested" AA body; this passes unit/AA definition validation today because the deep check is disabled. No special privilege beyond being able to post an AA definition and later trigger it is required. However, exploiting this into full consensus-halting or fund-loss impact (rather than a single AA misbehaving) requires further confirmation of how `aa_composer.js` writes/executes the resulting nested AA, which could not be fully traced within the available context.

### Recommendation
Re-enable full recursive validation of nested AA definitions in the `definition` message case of `aa_validation.js` (i.e., actually invoke `validateAADefinition` on `payload.definition`, including its own complexity/ops accounting merged into the parent budget) before accepting the outer AA definition, mirroring the recursive validation already used for other nested constructs (data feeds, payment outputs, asset fields).

### Proof of Concept
Not independently reproduced against a running node in this session; the analysis is based on static review of `aa_validation.js` lines 208–223, where the recursive validation call for nested AA definitions is present in the source but commented out, leaving only shallow structural checks. A concrete PoC would require constructing an AA whose `messages` template includes a `definition` app message with an oversized/malformed nested `messages`/formula, triggering it, and observing that `aa_composer.js` executes/stores the nested AA despite it violating `constants.MAX_COMPLEXITY`/`MAX_OPS` — this step was not verified against `aa_composer.js`'s definition-message handling in this session and should be confirmed by a background agent with full repo/test access.
