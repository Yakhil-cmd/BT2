### Title
Attacker-controlled swap route can execute arbitrary token transfers under the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept caller-supplied route bytes and execute them through the configured router under the caller’s broad authorization for the strategy call. A malicious route can place attacker-controlled contract code beneath that authorization; that code can call an unrelated token’s `transfer(caller, attacker, amount)`. Simulation reports the theft transfer as a child authorization of the controller call, and execution succeeds if the caller signs the simulated tree. This is analogous to CVE-2023-37154: attacker-controlled route data reaches an execution primitive that can perform actions beyond the nominally requested operation.

### Finding Description
`swap_collateral` accepts arbitrary `swap: Bytes` from the caller and forwards it to `process_swap_collateral` [1](#0-0) . The strategy first authenticates only `caller.require_auth()` [2](#0-1)  and then sends the route to `swap_tokens_or_passthrough` [3](#0-2) .

`swap_tokens` invokes the configured router with the uninterpreted route bytes [4](#0-3) . Its checks only bound the controller’s input-token balance and require positive output [5](#0-4) ; they do not prevent route-selected third-party code from requesting the original caller’s authorization for unrelated token transfers.

The harness demonstrates the resulting authorization-tree injection: a route-selected contract calls `token.transfer(victim, attacker, amount)` [6](#0-5) . During simulation, that unrelated transfer is recorded as a child of the caller’s `swap_collateral` authorization, and the simulated call empties the victim’s wallet token [7](#0-6) . In enforcing mode, the same route succeeds when the returned child transfer is signed [8](#0-7) .

The same reachable pattern applies to every strategy path that passes caller-controlled route bytes into `swap_tokens` or `swap_tokens_or_passthrough`: `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. The route payload itself supplies the external contract addresses, so an unprivileged attacker can construct the malicious route and a quote/signature flow can induce the victim to sign the complete authorization tree.

### Impact Explanation
A malicious route can steal arbitrary SEP-41/token-contract assets held by the caller, including assets that are not listed by the lending protocol and were never supplied as collateral. The demonstrated test steals the victim’s entire unrelated wallet-token balance while still producing a valid swap output [9](#0-8) . This is theft of user funds, not merely poor swap execution: the transferred token, amount, and recipient are selected by the malicious hop rather than bounded by the strategy’s `amount_in`.

### Likelihood Explanation
Exploitation requires the victim to submit or approve a malicious route and to sign the exact authorization tree returned by simulation. This is realistic when route bytes are produced by an off-chain quote provider, aggregator UI, or malicious counterparties, because the authorization tree can contain an additional token-transfer child that is easy to overlook. An unprivileged attacker needs no protocol role, leaked key, compromised router, or upgraded contract: the threat model explicitly notes that route pool and token addresses are not allowlisted and that third-party code can appear below the caller’s authorization [10](#0-9) . Severity is High due to direct arbitrary-wallet-token theft, with the user-signature requirement limiting likelihood relative to a fully unauthenticated drain.

### Recommendation
Do not treat opaque route bytes as safe merely because controller input/output deltas and final account risk are correct. Enforce a protocol-controlled venue/pool allowlist for route hop contracts, or change the router interface/execution model so route-selected contracts cannot request authorization from the original strategy caller. At minimum, simulation and signing infrastructure must decode every submitted route and reject any authorization tree containing children other than the single expected controller input transfer or explicitly expected token pulls. The defense should be enforced where routes are admitted rather than relying solely on wallet UX warnings.

### Proof of Concept
The repository already contains a focused executable proof:

```rust
token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
```

From `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-70`, this call is made by a route-selected `RogueHopPool`, with `victim`, `wallet_token`, `to`, and `amount` all controlled by the route constructor.

The test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` builds a `swap_collateral` call whose route invokes that pool. Simulation records:

```text
root: Controller.swap_collateral(...)
  child: wallet_token.transfer(alice, attacker, WALLET_BALANCE)
```

and then observes `alice == 0`, `attacker == WALLET_BALANCE`, while the account receives the expected swap output [7](#0-6) . The enforcing-mode test then signs the simulated poisoned tree and successfully performs the same wallet theft [8](#0-7) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
