### Title
AA `timestamp` value is derived from the trigger's self-chosen `last_ball`, letting a poster backdate time-sensitive AA logic - (File: formula/evaluation.js)

### Summary
The external report flags smart-contract logic that relies on `block.timestamp` for time-sensitive decisions (e.g., swap deadlines), which lets whoever controls ordering/inclusion of the transaction manipulate the effective "current time" the contract sees. In `ocore`, the oscript `timestamp` built-in used inside AA formulas is **not** derived from any externally-verified wall-clock value at execution time; it is taken directly from `objValidationState.last_ball_timestamp`, i.e. the timestamp of the `last_ball` that the *trigger unit's author chose to reference* when composing their unit.

### Finding Description
In `formula/evaluation.js`, the `timestamp` opcode resolves to:
```
case 'timestamp':
    cb(new Decimal(objValidationState.last_ball_timestamp));
    break;
``` [1](#0-0) 

`objValidationState.last_ball_timestamp` is populated during unit validation from the `last_ball_unit` that the unit itself references:
```
objValidationState.last_ball_mci = objLastBallUnitProps.main_chain_index;
objValidationState.last_ball_timestamp = objLastBallUnitProps.timestamp;
``` [2](#0-1) 

The `last_ball`/`last_ball_unit` pair is a field the unit's author supplies when composing the unit (an unprivileged operation available to any poster of an AA trigger); the validator only checks that it is on the main chain, is stable, and is consistent with the unit's parents (i.e. not older than what the parents already commit to) — see the surrounding parent-consistency checks in `validateParents` [3](#0-2) . There is no requirement that the author reference the *most recent* stable ball available to them; any older still-valid stable ball that satisfies the monotonic parent constraint is acceptable.

Multiple production AA samples in this codebase use `timestamp` for maturity/expiry/staleness gating in exactly the pattern the external report warns about, e.g. an ICO expiry check `trigger.address == $control_address OR timestamp > $expiry_ts` [4](#0-3) , and a maturity/blackswan gate `if (timestamp < 1556668800) bounce('wait for maturity date');` [5](#0-4) . This shows `timestamp` is the idiomatic, documented way AA authors are expected to implement deadline/expiry logic in oscript.

Because the value is author-selectable (by choosing which stable ball to reference as `last_ball_unit`), a trigger poster can deliberately reference an older-than-current stable ball to make `timestamp` appear earlier than real time. This is the direct analog of the reported issue: instead of a block builder holding back and replaying a swap to pick a favorable `block.timestamp`, an ocore AA trigger's poster can pick an older `last_ball` to make the AA's internal `timestamp` earlier than actual wall-clock time, bypassing "not yet matured / not yet expired / rate not yet stale" checks that assume `timestamp` tracks real elapsed time.

### Impact Explanation
Any AA that gates fund release, price computation, or state transitions on `timestamp` (maturity dates, ICO/expiry deadlines, price/rate staleness windows, blackswan/oracle-freshness checks) can be manipulated by a trigger poster choosing an artificially old `last_ball`. This can let an attacker prematurely trigger logic that should be blocked until a real deadline passes, or conversely stall a favorable state transition by keeping their own reference point old — resulting in AA fund loss, unauthorized early payouts, or incorrect settlement pricing, matching the "Medium/High" severity class of the swap-deadline analog (fund loss/mispriced settlement due to manipulable time reference), not merely a low-severity issue.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged role is needed — any address posting a trigger to an AA composes its own `last_ball`/`last_ball_unit`, and the validator's constraint is only "not older than what parents already imply", not "must be the latest known stable ball" [6](#0-5) . Any AA author who used `timestamp` per the documented pattern (as multiple in-repo AA samples do) is exposed. The practical window of manipulation is bounded by how far behind the author's own chain of `last_ball` references is permitted to lag, which limits but does not eliminate the exploitable skew.

### Recommendation
- Avoid using `timestamp` (last-ball-derived, author-influenced) as the sole time reference for security-critical expiry/maturity checks in AA templates; where possible, cross-check against `mci` progress or require a minimum number of confirmations/stability advances since a reference event, rather than trusting the referenced ball's timestamp directly.
- Consider tightening the last_ball selection constraint in `validation.js` so that an AA trigger cannot reference an arbitrarily old (but still valid) stable ball relative to the current known main chain tip, reducing the backdating window.
- Document for AA authors that `timestamp` reflects the trigger-unit-selected `last_ball`'s timestamp, not real "now", and is therefore attacker-influenceable within the allowed lag window.

### Proof of Concept
1. An AA `X` implements a maturity gate: `if (timestamp < MATURITY_TS) bounce('wait for maturity');` (pattern taken from `test/samples/futures_contract.oscript` lines 86-87).
2. Attacker composes a trigger unit to `X` but sets `last_ball_unit`/`last_ball` to an older stable ball (satisfying the parent-consistency checks in `validateParents`) whose `last_ball_timestamp` is `< MATURITY_TS`, even though real wall-clock time has passed `MATURITY_TS`.
3. During AA execution, `objValidationState.last_ball_timestamp` is set from that chosen ball [2](#0-1) , and the `timestamp` opcode returns this stale value [1](#0-0) .
4. The maturity/staleness check based on `timestamp` behaves as if less time has passed than in reality, allowing the attacker to bypass the intended temporal gate (or conversely delay a check that should fire), leading to premature or mispriced fund release from the AA.
