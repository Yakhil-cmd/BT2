### Title
Attacker-controlled PR label name becomes `GIT_CONFIG_GLOBAL` in git subprocess env for `StackCommands#fetch_deployed_revision` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges the pull request's label names (uppercased) directly into the stack's environment hash with no key allowlist, and `LabelCapturingHandler#capture_labels` persists whatever label names GitHub sends in the webhook body. `StackCommands#fetch_deployed_revision` and other `StackCommands`/`TaskCommands` methods pass `env:` straight into `Command.new`, whose `unbundled_env` merges it on top of the process environment before `PTY.spawn`, so any label an unprivileged fork PR author applies becomes a real environment variable name (with the fixed value `"true"`) inherited by the spawned git process.

### Finding Description
The broken binding: `Command#unbundled_env` should only ever expose environment variable names from a fixed, reviewed allowlist to `PTY.spawn`, i.e. `keys(@env) ⊆ allowlist`. Instead `keys(@env)` includes `pull_request.labels.map(&:upcase)` with no restriction, so `keys(@env) ⊆ allowlist` does not hold.

Path: an attacker opens a PR from a fork and adds a label whose name, once uppercased, matches a git-recognized environment variable such as `GIT_CONFIG_GLOBAL` (webhook `pull_request.labeled` event, `action: "labeled"`). `LabelCapturingHandler#capture_labels` (app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102) writes `params.pull_request.labels.map(&:name)` straight onto `pull_request.labels` with no validation of the label text. `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) then does: [1](#0-0) 
producing e.g. `{"GIT_CONFIG_GLOBAL" => "true"}` merged on top of the base stack env. `StackCommands#env` (lib/shipit/stack_commands.rb:13-15) merges this into the commands' base env, and `fetch_deployed_revision` (lib/shipit/stack_commands.rb:51-59) builds `Command.new(command_line, env:, chdir: dir)` where `dir` is the checked-out working copy of the PR's own head commit. `Command#unbundled_env` (lib/shipit/command.rb:103-105) merges `@env.stringify_keys` last, so `GIT_CONFIG_GLOBAL=true` reaches `PTY.spawn` for the git subprocess.

The exploit's stated value is fixed to the literal string `"true"` (not attacker-chosen content) — `label_name.upcase => "true"` — so for `GIT_CONFIG_GLOBAL=true` to actually load an attacker-controlled config, git must resolve the relative path `true` against the current working directory, which for `fetch_deployed_revision` is the checked-out working tree of the PR's own head commit (`with_temporary_working_directory`, lib/shipit/stack_commands.rb:52,67-98). Since the PR author fully controls the content of that commit, they can also commit a file literally named `true` in the repo root containing a malicious git config (e.g., `[core] fsmonitor = "/bin/sh -c ...`) so that when the git subprocess reads `GIT_CONFIG_GLOBAL` it executes the attacker's command.

No existing guard prevents this: `EnvironmentVariables#permit` (lib/shipit/environment_variables.rb) is an allowlist mechanism that exists elsewhere (`Stack#trigger_task`/`build_deploy` filter user-supplied task/deploy env via `filter_task_envs`/`filter_deploy_envs`) but is never applied to `ReviewStack#env`'s label-derived keys or to `StackCommands#env`/`TaskCommands#env`. `LabelCapturingHandler` only validates the webhook payload shape (`ExplicitParameters` schema requires `labels` to be an array of `{name: String}`) but not the label string content. Webhook signature verification (`verify_signature`) only proves the payload comes from GitHub for a repo already connected to Shipit — a fork PR author fully controls the label text they attach to their own PR, so signature verification does not stop this.

### Impact Explanation
An attacker who can create a label on their own pull request (any GitHub user able to open a PR against a repository that has review stacks enabled, and who can also label it — note: on many repos only maintainers/collaborators can attach labels, which affects likelihood but not the code-level vulnerability) can inject arbitrary environment variable *names* into every git subprocess spawned for that review stack, including `fetch_deployed_revision`, `fetch`, `fetch_commit`, and (via `TaskCommands`) deploy/rollback steps. Combined with attacker-controlled repository content, this is Remote Code Execution on the Shipit deploy host under the git subprocess's privileges — matching the "Critical — RCE on the deploy host via `Command`/`PTY.spawn`" category. Every review stack for a repository with review stacks enabled is affected, and the attack is repeatable for any PR the attacker controls.

### Likelihood Explanation
Preconditions: the target repository must have Shipit review stacks enabled, and the attacker must be able to attach a label to a PR against it (either because label creation/attachment is unrestricted on that repo, or because the attacker already has enough access to label their own PR). Assuming label attachment is possible, the rest of the chain (opening a PR, committing a file named `true` with a malicious git config, and having Shipit's `fetch_deployed_revision`/deploy machinery run against that commit) requires no Shipit credentials, secrets, or maintainer approval — it is fully reachable by the webhook flow already described. This makes the attack low-cost and repeatable per PR/label event once label-attachment is achievable.

### Recommendation
In `ReviewStack#env`, do not project raw label names into arbitrary environment variable keys. Either (a) prefix all label-derived keys with a fixed, safe namespace that cannot collide with real environment variables Shipit or git recognizes (e.g. `SHIPIT_LABEL_<name>`), or (b) run the resulting hash through `EnvironmentVariables#permit` against an explicit allowlist before merging it into the stack env, and reject/drop any label name matching dangerous patterns (`GIT_*`, `LD_*`, `BUNDLE_*`, etc.). Additionally, `Command#unbundled_env` should scrub any inherited/merged `GIT_*`-family variables not present in a hardcoded allowlist before calling `PTY.spawn`, as defense-in-depth against any other environment-merging code path introducing similar injections.

### Proof of Concept
Add a minitest (e.g. `test/unit/stack_commands_test.rb` or `test/models/shipit/review_stack_test.rb`):
```ruby
test "PR label name can inject GIT_CONFIG_GLOBAL into stack env" do
  stack = shipit_stacks(:shipit) # or a ReviewStack fixture with a pull_request
  pull_request = stack.pull_request # or build one
  pull_request.update!(labels: ["GIT_CONFIG_GLOBAL"])

  env = stack.env
  assert_equal "true", env["GIT_CONFIG_GLOBAL"], "label name should not become an environment variable key"
end

test "fetch_deployed_revision Command inherits attacker-controlled GIT_CONFIG_GLOBAL" do
  stack_commands = StackCommands.new(review_stack_with_label("GIT_CONFIG_GLOBAL"))
  command = Command.new("git status", env: stack_commands.env, chdir: Dir.mktmpdir)
  assert command.unbundled_env.key?("GIT_CONFIG_GLOBAL"),
    "Command#unbundled_env must never pass fork-controllable GIT_* variables to the git subprocess"
end
```
Both assertions should FAIL after a fix that either namespaces label-derived keys or filters them through an allowlist (i.e., `env["GIT_CONFIG_GLOBAL"]` should be `nil`/absent).
