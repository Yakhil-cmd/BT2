## Title
Forged `check_suite` webhook via owner/full_name split lets an unauthenticated attacker mutate another repository's commits - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/check_suite_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App / HMAC secret to verify the payload using `repository.owner.login` from the untrusted JSON body, while `Shipit::Webhooks::Handlers::Handler#stacks` (used by `CheckSuiteHandler`) resolves the target `Repository` using `repository.full_name` from the same body. These two fields are never checked for consistency, so an attacker can name a "no-secret" org as the owner (which trivially passes verification) while pointing `full_name` at a repository belonging to a different, secret-protected org.

### Finding Description
The broken binding: the invariant the app implicitly relies on is
`org_that_verified_signature == org_that_owns(repository.full_name)`.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` via `params.dig('repository', 'owner', 'login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` is: `return true unless webhook_secret` [2](#0-1) . This means if the org named in `repository.owner.login` happens to have **no** `webhook_secret` configured, verification passes for *any* payload/signature, with no cryptographic check at all.
- After verification passes, `WebhooksController#create` dispatches the same raw `params` to `Shipit::Webhooks.for_event(event)` handlers, including `CheckSuiteHandler` [3](#0-2) .
- `CheckSuiteHandler#process` calls `stacks`, which is defined on the base `Handler` class as `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name` is `payload.dig('repository', 'full_name')` — a **completely separate field** from the one used for signature verification [4](#0-3) .
- `CheckSuiteHandler#process` then mutates commits under that resolved repository's stacks by `head_branch`/`head_sha`, calling `schedule_refresh_check_runs!` [5](#0-4) .

Exploit flow: attacker crafts a JSON body with `repository.owner.login = "org-with-no-secret"` and `repository.full_name = "victim-org/victim-repo"`, sets `X-Github-Event: check_suite`, and sends any (or no) valid `X-Hub-Signature` (irrelevant since the no-secret org's `verify_webhook_signature` returns `true` unconditionally). The controller accepts it, then `CheckSuiteHandler` resolves `victim-org/victim-repo`'s stacks (via `Repository.from_github_repo_name`) and schedules check-run refresh jobs against real commits in the victim repository/stack — data belonging to an org that never validated this request.

Why existing guards fail: there is no code anywhere that compares `repository.owner.login` to `repository.full_name`'s owner segment, nor does `verify_signature` re-derive the owner from `full_name`. `drop_unhandled_event` only filters unhandled event types, not payload consistency. `ExplicitParameters` schema in `CheckSuiteHandler` only validates presence/types of `head_sha`/`head_branch`, not repository identity.

### Impact Explanation
This lets an unauthenticated attacker who controls no webhook secret for any org cause `Shipit` to execute repository-scoped side effects (`Commit#schedule_refresh_check_runs!`) against an arbitrary victim repository/stack, as long as: (a) that victim repository is registered in Shipit, and (b) at least one other org configured in `Shipit.github_teams`/`github_configs` has no `webhook_secret` set (a plausible, common misconfiguration — e.g., open-source orgs or orgs onboarded before secrets were enforced). This is a cross-tenant/cross-repository payload confusion: one org's (absent) trust boundary is used to write state belonging to another org's repository, matching the "payload for one repository mutating another's stack/commit" Critical category. The blast radius is bounded to what `CheckSuiteHandler` does (scheduling check-run refresh jobs) for this specific handler, but the same owner/full_name divergence pattern applies to every handler in `app/models/shipit/webhooks/handlers/` that uses the base `Handler#stacks`/`repository_name` helper, since none of them re-validate `repository.owner.login` against `full_name`.

### Likelihood Explanation
Preconditions: (1) at least one org in the Shipit deployment's GitHub config has no `webhook_secret` set — feasible in many real deployments (e.g., default/staging config, or an org onboarded without configuring the secret), and (2) the victim repository is already registered as a `Shipit::Repository`. No Shipit session, API token, or GitHub credentials are required — this is a plain unauthenticated `POST /webhooks`. The attack is a single HTTP request, fully repeatable against any registered repository/stack/branch/sha combination, at essentially zero cost.

### Recommendation
In `WebhooksController#verify_signature`, derive `repository_owner` from `repository.full_name`'s owner segment (or require `repository.owner.login` to match the owner segment of `repository.full_name` before verifying), and reject the request if they diverge. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when no secret is configured — either require a secret for any org that owns registered repositories, or fail closed instead of open when `webhook_secret` is blank.

### Proof of Concept
Minitest plan (ActionDispatch::IntegrationTest, no live GitHub):
1. Configure two orgs in `Shipit.github(...)`/config: `no-secret-org` with `webhook_secret: nil`, and `victim-org` with a real `webhook_secret`.
2. Create `Shipit::Repository.create!(owner: 'victim-org', name: 'victim-repo')` with a `Stack` (`branch: 'main'`) and a `Commit` (`sha: 'deadbeef...'`).
3. Assert precondition: `victim_stack.commits.find_by(sha: 'deadbeef...').checks_refreshed_at` (or equivalent last-refresh marker) is unset/old — i.e., `no-secret-org != victim-org` as verifying vs. owning org.
4. POST to `/webhooks` with header `X-Github-Event: check_suite`, body:
   ```json
   { "repository": { "owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo" },
     "check_suite": {"head_branch": "main", "head_sha": "deadbeef..."} }
   ```
   with any `X-Hub-Signature` value (e.g., garbage).
5. Assert response is `200 OK` (not `422`), and assert `Commit#schedule_refresh_check_runs!` was invoked / a refresh job was enqueued for the `victim-org/victim-repo` commit — proving the org that "verified" (`no-secret-org`) differs from the org whose record was mutated (`victim-org`), confirming the equality `verifying_org == owning_org` is violated.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
