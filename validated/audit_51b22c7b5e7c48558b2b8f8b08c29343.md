### Title
AA "bAir" simulated response path (`sendDummyUnit`) skips `spender_attested`/`cosigned_by_definer`/`transfer_condition` checks that are otherwise enforced on every payment - (File: aa_composer.js)

### Summary
The Brix-money bug is a class of "restriction bypass through an alternate execution/composition path": a regulatory check (`SOFT_RESTRICTED_STAKER_ROLE`) is fully enforced on the direct staking function, but the cross-chain composer path performs an equivalent state-changing operation (`VAULT.deposit()`) through a different code path that never re-runs the restriction check, because it deposits/sends on behalf of `address(this)` and never authenticates the real beneficiary. [1](#0-0) 

### Finding Description
In ocore, asset-level regulatory restrictions (attestor allow-lists, definer co-signing, and issue/transfer conditions) are supposed to be enforced uniformly whenever an asset moves. The canonical enforcement point is `validatePaymentInputsAndOutputs()`, which, for every payment message (human-authored or AA-authored) checks:
- `spender_attested` — every output address must be on the attestor's attested list [2](#0-1) 
- `issue_condition` / `transfer_condition` via `Definition.evaluateAssetCondition` [3](#0-2) 
- input-side attestation of the spending address [4](#0-3) 

This is the path taken by the normal AA-response unit construction (`sendUnit` → `validateAndSaveUnit` → `validation.validate` → `validatePayment`/`validatePaymentInputsAndOutputs`), so it is fully checked. [5](#0-4) 

However, `aa_composer.js` also has an alternate branch, `sendDummyUnit()`, used when the trigger is processed with `trigger_opts.bAir` (an in-memory/"air" execution mode that maintains balances directly in `trigger_opts.assocBalances` rather than persisting/validating a real signed unit). In this branch, the AA constructs its own payment `messages`, mutates `assocBalances` for the output addresses directly, and the **only** restriction check performed before treating the transfer as successful is that assets with a negative resulting balance must satisfy `issued_by_definer_only`:

```
storage.loadAssetWithListOfAttestedAuthors(conn, asset, mci, [address], true, function (err, objAsset) {
    if (err) return cb(err);
    if (objAsset.issued_by_definer_only && address !== objAsset.definer_address)
        return cb("not enough balance in " + asset);
    cb();
});
``` [6](#0-5) 

There is no call anywhere in `sendDummyUnit()` to `storage.filterAttestedAddresses`, no evaluation of `objAsset.spender_attested`, `objAsset.cosigned_by_definer`, `objAsset.is_transferrable`, or `objAsset.transfer_condition`/`issue_condition` against the output addresses being credited. Because the dummy unit is never passed to `validation.validate()` (unlike the `sendUnit` real-unit path), none of the restriction logic in `validatePaymentInputsAndOutputs` (lines 2616-2658) ever executes for these transfers. [7](#0-6) 

This is structurally identical to the reported bug class: one execution path (`StakediTry.deposit()` / real-unit AA path) enforces the restriction, while a second, functionally-equivalent path (`wiTryVaultComposer._depositAndSend()` / AA `bAir` simulated-balance path) performs the same economic transfer of a restricted asset but omits the restriction check because it operates on an internal/self-referential state (composer's `address(this)`, AA's `assocBalances`) instead of running the standard validated flow.

### Impact Explanation
If an attacker can get a trigger processed through the `bAir` branch (`sendDummyUnit`) while holding or being credited a `spender_attested` (attestor-restricted), `cosigned_by_definer`, or condition-restricted asset, they could receive/move that restricted asset to an address that is not attested and would otherwise never pass `validatePaymentInputsAndOutputs`. This breaks the intended KYC/attestor-gating and definer co-signing guarantees for that asset class, which is a Medium/High severity issue since restricted assets are explicitly designed to prevent unauthorized transfer/receipt.

### Likelihood Explanation
Reachability depends entirely on how/when `trigger_opts.bAir` is actually set for real (non-dry-run) execution versus only for local read-only estimation (e.g., `dryRunPrimaryAATrigger`, or getters). The evidence gathered strongly shows the code path exists and is structurally missing the checks, but I was not able to fully trace, within the remaining iterations, every caller that sets `bAir` for a real state-mutating trigger execution (as opposed to purely local/light-client simulation that never gets committed to the DAG). This affects confidence in exploitability under the "single posted unit/trigger" reachability requirement — if `bAir` mode is only ever used for local previews that never actually move real balances, the practical impact would be reduced to a preview-only inconsistency rather than an actual double-processing or fund-freezing/inflation bug.

### Recommendation
In `sendDummyUnit()` (and any other AA execution branch that credits/debits `assocBalances` without running the messages through `validation.validate`), add the same restriction checks that `validatePaymentInputsAndOutputs` performs for real units: verify `spender_attested` against `arrOutputAddresses` (and the AA's own spending address), verify `cosigned_by_definer`/`is_transferrable`, and evaluate `issue_condition`/`transfer_condition` via `Definition.evaluateAssetCondition` before crediting balances or emitting a successful response.

### Proof of Concept
I was unable to construct and confirm a runnable proof-of-concept within the tool-call budget available (locating and exercising every caller path that sets `trigger_opts.bAir=true` for a real, committed AA trigger would require additional tracing of `handleTrigger`'s callers, e.g. in `network.js`/`headless.js` or oscript "AA-to-AA on other chains/air" execution flows, which was not completed). The concrete code-level gap — `sendDummyUnit()` omitting the `spender_attested`/`cosigned_by_definer`/`transfer_condition` checks that `validatePaymentInputsAndOutputs` enforces — is verified directly from source at the cited line ranges.
