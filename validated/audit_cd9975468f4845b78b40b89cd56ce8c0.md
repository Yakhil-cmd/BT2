### Title
Missing `return` after catch block causes double-invocation of the async.each completion callback in `handleSavedPrivatePayments` - ([File: network.js])

### Summary
In `network.js`'s `handleSavedPrivatePayments()`, the inner `validateAndSave` function computes a hash of the private element's payload inside a `try/catch`. When the hash computation throws, the `catch` block calls `deleteHandledPrivateChain(..., cb)` (which itself eventually invokes the `async.each` iteratee callback `cb`) but does **not** `return` afterward. Execution falls through to the rest of the function, which then calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers *also* call `cb` (directly, or via a second `deleteHandledPrivateChain` call). This results in `cb` being invoked twice for the same `async.each` item — the same double-completion bug class as the btrfs report, where a single I/O/callback completion path is invoked twice because an error branch doesn't stop propagation into the "normal" completion path.

### Finding Description
`handleSavedPrivatePayments()` iterates unhandled private payments with `async.each`, and for each row defines: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
``` [2](#0-1) 

The `catch` branch lacks a `return` statement. `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` passes `cb` — the `async.each` per-item completion callback — as its own completion callback (an asynchronous DB delete). Because there's no `return`, control flow continues past the `catch` block regardless of whether an exception was thrown, computing `key` (with `json_payload_hash` now `undefined`) and unconditionally calling `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`. Every branch of that call (`ifOk`, `ifError`, `ifWaitingForChain`) itself calls `cb()` — either directly or via a second `deleteHandledPrivateChain(...)` call: [3](#0-2) 

So on the exception path, `cb` gets scheduled to be called twice: once from the `catch` block's `deleteHandledPrivateChain`, and again from whichever branch `validateAndSavePrivatePaymentChain`'s callbacks take. This directly parallels the btrfs bug class: an early error-completion path (`bio_endio`/`cb`) is invoked, but the caller does not know this happened and invokes the same completion callback again through the normal path.

`async.each`'s completion behavior when the same `cb` is invoked more than once for one item is not idempotent-safe: it decrements/tracks completion count per call, so calling it twice for one item causes the overall `async.each` final callback (which calls `unlock()` releasing the `["saved_private"]` mutex) to fire prematurely — before all rows have actually finished processing — or to fire additional times, depending on `async`'s internal bookkeeping. This corrupts the mutex/lock lifecycle guarding this section (`lock(["saved_private"], ...)`), and can also cause `deleteHandledPrivateChain` to run twice concurrently against the same row, along with duplicate `sendResult`/event emissions (`eventBus.emit(key, ...)`) for the same private payment chain.

### Impact Explanation
`objHeadPrivateElement.payload` is attacker/peer-controlled content taken from `unhandled_private_payments` (populated from private payment chains received from peers/hub as part of normal wallet flows for private assets). If `objectHash.getBase64Hash` throws on a malformed payload (e.g., containing values that make hashing fail, similar to other `catch (e) { return callbacks.ifError(...) }` guards seen elsewhere in the codebase for the exact same call), the double-callback path triggers. This can:
- prematurely release the `["saved_private"]` mutex while a chain's validation/save is still in flight, allowing concurrent re-entrant processing of the private-payment save path,
- cause `unlock()` and the "new_my_transactions" emission from `async.each`'s completion callback to run out of sync with actual completion of DB writes for private payment chains,
- result in double invocation of `deleteHandledPrivateChain` (double DB delete on the same row) and, depending on `async`'s internal state handling for double-callback per item, corrupt the count of remaining tasks, potentially causing the wallet to falsely believe processing finished, or to process the same private payment record twice.

This affects the local wallet's bookkeeping of privately-transferred asset ownership, which underpins spend authorization for private assets. Corruption/races here can lead to incorrect crediting/handling of private payment chains, i.e., an integrity issue in fund tracking for private assets — a Medium-severity node-disagreement/fund-tracking corruption class issue, reachable simply by sending a private payment chain with a payload crafted to make `objectHash.getBase64Hash` throw.

### Likelihood Explanation
Reachable by any device/peer that can deliver a private payment chain to a wallet (normal p2p/hub private-payment flow feeding `unhandled_private_payments`), which is an unprivileged posting path per the analog rules (private-payment counterparty). The trigger condition requires `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` to throw — this is plausible for a payload with degenerate/circular or type-mismatched fields, mirroring the exact defensive `try/catch` pattern used elsewhere in the codebase for the identical call (e.g., in `wallet.js` and `network.js`'s `handlePrivatePaymentChains`), which shows the maintainers are aware this call can throw on attacker-supplied payloads.

### Recommendation
Add a `return` statement at the end of the `catch` block in `validateAndSave` (network.js, around line 2476) so execution does not continue into computing `key`/calling `privatePayment.validateAndSavePrivatePaymentChain` after the exception path has already completed via `deleteHandledPrivateChain(..., cb)`. This mirrors the pattern already used for the same hashing call in `handlePrivatePaymentFile`/`handlePrivatePaymentChains` where errors return immediately.

### Proof of Concept
1. A malicious device/peer sends a private payment chain to the wallet where the head element's `payload` (or nested structure within `payload`) is crafted so that `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g., an object with a non-serializable/self-referential structure that JSON hashing chokes on, or a type-mismatched field matching other known-throwing shapes handled elsewhere via `catch(e){ return callbacks.ifError(...) }`).
2. This causes the record to be persisted into `unhandled_private_payments`, and later processed by `handleSavedPrivatePayments()`.
3. `validateAndSave()` executes: `objectHash.getBase64Hash` throws → `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` (async completion #1) → falls through (no `return`) → calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifError`/`ifOk`/`ifWaitingForChain` handler invokes `cb` a second time (completion #2), because `key` now includes `undefined` and validation of the malformed payload proceeds/fails independently.
4. `async.each`'s single item now completes twice, corrupting the pending-task bookkeeping for the batch and causing `unlock()` on `["saved_private"]` and the `"new_my_transactions"` event to fire out of sync with the true completion state of all rows, alongside a duplicate DB delete for the same row.
