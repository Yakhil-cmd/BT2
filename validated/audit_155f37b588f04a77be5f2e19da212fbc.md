Based on my investigation, I found a genuine gap between what the signature actually covers and what gets executed for encrypted transactions. I was not able to fully confirm (due to running out of tool budget) whether the API ingress layer (`api/types/src/convert.rs`, `api/src/transactions.rs`) explicitly rejects a client-submitted transaction whose payload is already in the `EncryptedPayload::Decrypted`/`FailedDecryption` state at submission time, so that residual uncertainty should be resolved by further review of those files (and of the mempool submission entrypoint) before treating this as fully confirmed in production.

### Title
Encrypted-transaction signature verification ignores the `decrypted` field, allowing decrypted-content/`payload_hash` binding to be bypassed outside the consensus decryption pipeline - (File: `types/src/transaction/authenticator.rs`, `types/src/transaction/mod.rs`, `types/src/transaction/encrypted_payload.rs`)

### Summary
`TransactionAuthenticator::verify` reconstructs the signing message via `RawTransaction::as_encrypted_variant()`, which discards the `decrypted`/`eval_proof`/`reason` fields of an `EncryptedPayload` and replaces the payload with `EncryptedPayload::Encrypted(original.clone())` before checking the signature. [1](#0-0) [2](#0-1) 
This means the cryptographic signature on an encrypted transaction never covers the actual `decrypted` executable content that the VM ultimately runs — it only covers the ciphertext/`payload_hash`/config bundle (`EncryptedInner`). The only mechanism that binds the `decrypted` executable to the signed `original.payload_hash` is `EncryptedPayload::try_into_decrypted`, which checks `original.payload_hash != CryptoHash::hash(&plaintext)` before transitioning the state to `Decrypted`. [3](#0-2) 

### Finding Description
`try_into_decrypted` is only invoked from the consensus decryption pipeline (`decrypt_validator_path` / `decrypt_encrypted_txns_inner`), where it is called after the real threshold decryption of the ciphertext produces a candidate plaintext. [4](#0-3) 
I found no equivalent hash-binding check performed inside `mempool/**` (a search for `payload_hash`, `try_into_decrypted`, `EncryptedPayload::Decrypted`, `is_encrypted_variant` under `mempool/**` returned zero matches), and `TransactionAuthenticator::verify`/`check_signature` — the check that mempool and the VM validator do run — is provably blind to the `decrypted` field because it operates on `as_encrypted_variant()`. [5](#0-4) 

Once a payload is in `EncryptedPayload::Decrypted { original, eval_proof, decrypted }` state, `executable()`/`executable_ref()` return the (unverified-by-signature) `decrypted.executable()` content directly for VM execution: [6](#0-5) 
Nothing in `TransactionAuthenticator::verify`, `check_signature`, or the AptosVM validator path (`aptos_vm.rs`'s `VMValidator::validate_transaction`, which only calls `check_authenticator_features`, an encrypted-feature-flag gate, and `transaction.check_signature()`) re-derives or re-checks `original.payload_hash` against `decrypted` outside the consensus decryption pipeline. [7](#0-6) 

Consequently, if a `SignedTransaction` is presented to mempool/vm-validator already in the `Decrypted` (or `FailedDecryption`) state — i.e., not freshly produced by the trusted consensus decryption pipeline — with `decrypted` content that does not match `original.payload_hash` (or was never actually the plaintext of `original.ciphertext`), signature verification still succeeds (because it only checks `original`), and nothing else in the admission path re-validates the `payload_hash`/`decrypted` binding before the VM treats `decrypted.executable()` as ground truth for execution. This breaks the invariant asserted in `RawTransaction::as_encrypted_variant`'s own doc comment ("signatures are verified over the encrypted form … not the decrypted payload") as a *general* execution-binding guarantee — the guarantee only holds for the specific code path (the honest consensus decryption pipeline) that calls `try_into_decrypted`; any other path that can inject a `Decrypted`-state payload bypasses it.

### Impact Explanation
Because the `decrypted` executable is not covered by the signature and the `payload_hash` binding check lives only in the consensus decryption pipeline, any component in the admission path other than that specific pipeline stage (mempool ingestion/gossip, VM validator, or a directly crafted client submission that already carries a `Decrypted` payload) can cause a transaction to execute content that was never actually verified against what the signer committed to. This matches the required admission-impact category "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit," since a transaction whose `decrypted` field mismatches `original.payload_hash` should fail decryption/admission but nothing forces that check outside the one pipeline stage.

### Likelihood Explanation
Exploitability hinges on whether any unprivileged, non-consensus path (mempool submission, API `/transactions` ingestion, or gossip relay before block decryption) can hand the VM validator a `SignedTransaction` whose payload is already `EncryptedPayload::Decrypted`/`FailedDecryption` rather than `Encrypted`. I could not fully confirm from the code I reviewed whether the API/mempool ingestion layer (`api/types/src/convert.rs`, `api/src/transactions.rs`) explicitly rejects such payloads at submission time — this needs to be checked directly before concluding the issue is remotely triggerable by an unprivileged submitter versus only reachable internally within the trusted consensus pipeline.

### Recommendation
- Add an explicit, unconditional check at mempool ingestion and/or `VMValidator::validate_transaction` that rejects any `SignedTransaction` whose `EncryptedPayload` is not in the `Encrypted` state (i.e., reject `Decrypted`/`FailedDecryption` payloads at the network/API boundary), so that only the consensus decryption pipeline is ever allowed to produce a `Decrypted` state.
- Alternatively/additionally, make the VM's actual execution path re-verify `original.payload_hash == CryptoHash::hash(&decrypted)` (and the `claimed_entry_fun` constraint) immediately before running `decrypted.executable()`, rather than relying solely on the decryption pipeline having performed that check earlier.
- Consider including a binding of the `decrypted` content itself (or its hash) into the value being signature-checked, so that `TransactionAuthenticator::verify` is not entirely blind to what will actually execute.

### Proof of Concept
Conceptual PoC (needs to be validated against the exact mempool/API ingestion code, which I could not fully inspect):
1. Construct a normal `RawTransaction` with `TransactionPayload::EncryptedPayload(EncryptedPayload::Encrypted(original))` and sign it normally — the signature covers `original` via `as_encrypted_variant()`. [2](#0-1) 
2. Before submission (or via a relaying component that is not the trusted decryption pipeline), replace the payload with `EncryptedPayload::Decrypted { original: original.clone(), eval_proof: <any>, decrypted: <attacker-chosen executable not matching original.payload_hash> }`.
3. Submit to mempool/vm-validator. `TransactionAuthenticator::verify` still succeeds because it recomputes the signing message from `original` only. [1](#0-0) 
4. If the ingestion layer does not independently re-run `try_into_decrypted`'s `payload_hash` check, the VM executes `decrypted.executable()` — content the signer never approved via the ciphertext — as a valid, committed transaction. [6](#0-5)

    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }
