## Finding

### Title
`DenyReserveTransferToRelayChain` Barrier does not recurse into `SetAppendix`/`SetErrorHandler`, allowing relay-chain reserve-transfer denial to be bypassed - (File: system-parachains/encointer/src/xcm_config.rs)

### Summary
Encointer's `Barrier` type wraps the bare `DenyReserveTransferToRelayChain` filter, which only scans the top-level instruction slice of an XCM program for `InitiateReserveWithdraw`/`DepositReserveAsset`/`TransferReserveAsset` targeting the Relay Chain. It does not descend into nested `Xcm<Call>` programs carried by `SetAppendix`/`SetErrorHandler`, so a malicious/negligently-crafted local `pallet_xcm::execute` (or `send`) call can smuggle a relay-targeted reserve-withdraw instruction inside a `SetAppendix`, evading the deny rule that the runtime intends to enforce for all messages on this chain. [1](#0-0) 

### Finding Description
`Barrier` is composed as `TrailingSetTopicAsId<DenyThenTry<DenyReserveTransferToRelayChain, (...)>>`, and is used both for incoming XCMP/UMP messages and for local `pallet_xcm::execute` calls (`ExecuteXcmOrigin = EnsureXcmOrigin<..., LocalSignedOriginToLocation>`, so any signed local account can drive the `XcmExecutor` directly). [2](#0-1) 

`DenyReserveTransferToRelayChain` (from `xcm-builder`) performs a flat `message.iter().any(...)` match over the top-level instruction slice looking for reserve-related instructions with `dest`/`reserve` equal to `Parent`. It does not recurse into instructions that themselves embed a nested `Xcm<Call>` program to be executed locally later — namely `SetAppendix(Xcm<Call>)` and `SetErrorHandler(Xcm<Call>)`. The XCM executor runs the appendix/error-handler program after the main program completes, without re-invoking the top-level `Barrier` on that nested program.

This exact gap is already acknowledged and fixed elsewhere in this same repository: `bridge-hub-polkadot` and `bulletin-polkadot` wrap the filter as `DenyRecursively<DenyReserveTransferToRelayChain>` specifically to walk into nested instruction sequences at any depth, while `encointer` (like `asset-hub-kusama`, `bridge-hub-kusama`, `collectives-polkadot`, `coretime-*`, `people-*`) still uses the un-wrapped, non-recursive version. [3](#0-2) [4](#0-3) 

Attacker flow on Encointer:
1. Attacker is any signed account with a KSM balance on Encointer, and calls `pallet_xcm::execute` (permitted via `EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>`), or crafts an outbound `send`.
2. The top-level program is e.g. `[WithdrawAsset(...), BuyExecution(...), SetAppendix(Xcm(vec![InitiateReserveWithdraw { assets, reserve: Parent, xcm: vec![DepositAsset{...}] }])), ...]` — satisfying `AllowTopLevelPaidExecutionFrom<Everything>` so the outer barrier passes.
3. `DenyReserveTransferToRelayChain::should_execute` only inspects the outer slice; it sees `SetAppendix(...)` as a single opaque instruction and never inspects its inner `InitiateReserveWithdraw{ reserve: Parent, ... }`, so the deny check does not trigger.
4. After the main program finishes, the executor runs the appendix, executing `InitiateReserveWithdraw` — which is not gated by `IsReserve` on the *sending* side — withdrawing the attacker's own KSM from holding and dispatching a `ReserveAssetDeposited` XCM to the Relay Chain, in violation of the chain's intended KSM routing (teleport-only, as reflected by `IsTeleporter = TrustedTeleporters` / `IsReserve = ()`).

### Impact Explanation
This is a genuine logic gap in the Barrier composition: the deny rule can be bypassed for messages nesting the denied instruction inside `SetAppendix`/`SetErrorHandler`. However, the concrete blast radius is narrower than direct fund theft from other users: `InitiateReserveWithdraw` only lets the attacker move assets that are already in their own holding register (their own KSM). The resulting `ReserveAssetDeposited` message sent to the Relay Chain would still have to pass the Relay's own `IsReserve`/barrier configuration; relay chains typically do not recognize parachains as reserves for their own native token (KSM is teleport-only between Encointer and the Relay), so the message would most likely be trapped (`AssetTrap`) on arrival rather than credited. The concrete impact is therefore self-inflicted loss/trapping of the attacker's own KSM and a violation of the "messages must only execute through intended routes" invariant, rather than theft of other users' funds.

### Likelihood Explanation
Reachable by any unprivileged signed account able to call `pallet_xcm::execute`/`send` on Encointer — no special privileges or governance action required. The construction (`SetAppendix` wrapping a reserve-withdraw instruction) is a normal, spec-legal XCM program, so this is straightforward to reproduce, not a hypothetical.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively` in `system-parachains/encointer/src/xcm_config.rs`'s `Barrier` definition (matching the pattern already used in `bridge-hub-polkadot`/`bulletin-polkadot`), so the deny rule is checked recursively against instructions nested inside `SetAppendix`/`SetErrorHandler` at all depths. Apply the same fix to the other affected chains (`asset-hub-kusama`, `asset-hub-polkadot`, `bridge-hub-kusama`, `collectives-polkadot`, `coretime-kusama`, `coretime-polkadot`, `people-kusama`, `people-polkadot`) that still use the bare filter.

### Proof of Concept
xcm-emulator / Rust unit test plan for `pallet_xcm::execute`-driven barrier check on Encointer:
```rust
#[test]
fn deny_reserve_transfer_to_relay_bypassed_via_set_appendix() {
    // Build a program where InitiateReserveWithdraw{reserve: Parent} is nested inside SetAppendix
    let mut msg: Xcm<RuntimeCall> = Xcm(vec![
        WithdrawAsset((Parent, 1_000_000_000u128).into()),
        BuyExecution { fees: (Parent, 1_000_000_000u128).into(), weight_limit: Unlimited },
        SetAppendix(Xcm(vec![
            InitiateReserveWithdraw {
                assets: All.into(),
                reserve: Location::parent(),
                xcm: Xcm(vec![DepositAsset { assets: All.into(), beneficiary: Location::parent() }]),
            },
        ])),
    ]);

    // Assert: top-level Barrier::should_execute currently returns Ok(()) (bug) - should return Err
    let result = <encointer_kusama_runtime::xcm_config::Barrier as ShouldExecute>::should_execute(
        &Location::new(0, [AccountId32 { network: None, id: ATTACKER.into() }]),
        &mut msg.0,
        Weight::from_parts(1_000_000_000, 0),
        &mut Properties { weight_credit: Weight::zero(), message_id: None },
    );
    assert!(result.is_err(), "Barrier must deny relay-chain reserve transfer even when nested in SetAppendix");
}
```
Expected (fixed) behavior: after wrapping with `DenyRecursively`, `should_execute` returns `Err(ProcessMessageError::Unsupported)` for any nesting depth of the relay-chain reserve-withdraw instruction, matching behavior already verified for `bridge-hub-polkadot`.
