### Title
Cross-Organization Forged Commit Status via Webhook Signature/Payload Binding Mismatch - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature is verified against the GitHub App configuration selected by `repository.owner.login` (or `organization.login`) in the JSON payload [1](#0-0) , but the `status` event handler resolves the target `Commit` to mutate purely by the attacker-controlled `sha` field, with **no check that the commit belongs to the organization/repository whose secret authenticated the request** [2](#0-1) . The binding that should hold — "organization whose secret verified the signature" == "repository/commit being written to" — is broken.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` to validate the HMAC using `repository_owner`, itself read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [3](#0-2) . This is only used to select the key for `verify_webhook_signature` [4](#0-3) ; nothing ties this login to what the handler actually mutates.

Most handlers (push, pull_request) additionally scope their side effects by `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks` [5](#0-4) , which is itself a second, independently-attacker-controlled field that need not match `repository.owner.login` used for signature selection — but that is a secondary concern.

`StatusHandler`, however, does not scope by repository at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
It looks up commits **globally by SHA across every stack/repository tracked by the Shipit instance**, and writes an attacker-supplied `state`, `description`, `context`, and `target_url` onto whatever `Commit` record matches, regardless of which organization or repository that commit actually belongs to.

An attacker who controls (or has onboarded) any organization known to this Shipit instance — obtaining a legitimate `webhook_secret` for their own org — can craft a `status` event payload where `repository.owner.login` is their own organization (satisfying `verify_signature`) while `sha` is set to a commit SHA belonging to a completely different, victim organization's stack. Since git SHAs of a target commit are frequently public/known (from GitHub UI, PRs, CI logs, etc.), this is a directly reachable cross-organization write.

### Impact Explanation
Commit statuses gate Shipit's deploy pipeline via `shipit.yml`'s `ci.require` / `ci.blocking` configuration on `Stack`/`DeploySpec` [6](#0-5) . By forging a passing status (`state: success`) for a required CI context on a victim commit that has not actually passed CI, an attacker with only their own organization's webhook credentials can unblock deploy gating and enable an unauthorized deploy of a commit that should have been blocked — satisfying the "unauthorized deploy" high/critical impact criterion. Conversely, forging failing statuses would let an attacker deny CI to arbitrary unrelated stacks, but that overlaps with out-of-scope DoS and is not the primary claim here.

### Likelihood Explanation
Exploitability requires: (1) the attacker legitimately controls one organization onboarded to the same Shipit instance (multi-tenant github config, `Shipit.github(organization:)`) with a real `webhook_secret` they know because it's their own integration, and (2) knowledge of a target commit SHA in a victim stack, which is commonly public. No `ApiClient` token, `github_access_token`, or session is required — only the attacker's own webhook secret, which they are entitled to as an onboarded org owner but not entitled to use against other orgs' data. This is a realistic multi-tenant trust-boundary violation.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository identified by the verified organization/`repository.full_name`, mirroring what `Handler#stacks` already does for the push/pull_request handlers, e.g. `stacks.commits.where(sha: params.sha)` instead of a global `Commit.where(sha: params.sha)`. More generally, `WebhooksController#verify_signature` should assert equality between the organization whose secret validated the signature and the `repository.full_name`'s owner used by every handler, rejecting mismatched payloads before dispatch.

### Proof of Concept
1. Attacker owns/administers `attacker-org`, onboarded to this Shipit instance with its own valid `webhook_secret`.
2. Attacker learns SHA `abcd123...` of a commit tracked under `victim-org/victim-repo`'s stack (e.g., from a public PR).
3. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC over body using attacker-org's webhook_secret>

{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"},
  "sha": "abcd123...",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://evil.example"
}
```
4. `verify_signature` selects `attacker-org`'s app config and validates successfully [1](#0-0) .
5. `StatusHandler#process` finds the victim's `Commit` by SHA alone and writes the forged status onto it [2](#0-1) , potentially satisfying `ci.require`/`ci.blocking` gating for `victim-org/victim-repo`'s deploy pipeline.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
