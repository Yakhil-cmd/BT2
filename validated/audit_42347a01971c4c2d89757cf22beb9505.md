### Title
Unauthenticated webhook signature bypass allows forging cross-organization events (commit statuses, pushes, team membership) via attacker-controlled org selection - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using a field taken directly from the **unauthenticated, attacker-supplied request body** itself, before any verification has occurred. If any organization configured in a multi-tenant Shipit install has a blank/`nil` `webhook_secret`, an attacker can pick that organization to make signature verification unconditionally succeed, then rely on completely different (and never re-validated) fields of the same forged payload to mutate state belonging to an unrelated, unverified repository/commit/organization.

### Finding Description
`verify_signature` computes the organization used to fetch the verification secret purely from the raw JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up per-organization config, and `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "always verified": [3](#0-2) 

This is not a hypothetical misconfiguration — the shipped example multi-org secrets template explicitly documents organizations with commented-out/nil `webhook_secret`: [4](#0-3) 

Once the signature check is satisfied (because the attacker chose an org key with a blank secret), the same `create` action dispatches the *entire, still-unverified-for-consistency* payload to event handlers, which read completely different fields to decide what to mutate: [5](#0-4) [6](#0-5) 

For example, `StatusHandler` looks up commits **globally by SHA, with no repository/organization scoping at all**, and writes a CI status directly from attacker-supplied `state`/`context`: [7](#0-6) 

`PushHandler` and `MembershipHandler` similarly key off `repository.full_name` or `organization.login` inside the payload, independent of whichever `repository.owner.login`/`organization.login` value was used to pick the (possibly secret-less) verification org: [8](#0-7) [9](#0-8) 

**The broken binding (equality that should hold but doesn't):**
`organization used to select/pass HMAC verification` == `organization/repository/commit whose state the handler mutates`.

Before the attack: an attacker with no Shipit session, no `ApiClient` token, and no knowledge of any *victim* org's `webhook_secret` cannot forge events for that victim org, because `verify_signature` would use the victim's real (non-blank) secret and reject a wrong/missing HMAC.

After the attack: the attacker sets `repository.owner.login` (or `organization.login`) in the JSON body to the name of *any* organization configured in the same Shipit instance whose `webhook_secret` is blank/unset — trivially satisfying `verify_webhook_signature`'s early-return — while setting `repository.full_name`, `sha`, `ref`/`after`, or `organization.login` elsewhere in the same body to reference a totally different, victim repository/commit/team. The handler acts on the victim data with signature verification effectively disabled.

### Impact Explanation
This crosses a credential/authentication boundary an unprivileged, unauthenticated network attacker should never be able to cross: forging GitHub webhook events for a repository/commit they were never issued a valid signature for. Concretely reachable primitives:
- `StatusHandler` lets an attacker inject an arbitrary CI `state`/`context` onto **any commit in the entire install** by SHA alone, with zero repository scoping — this can satisfy `ci.require`/`required_statuses` gating used by continuous delivery and merge-queue logic (documented in README `ci.require`), leading to an **unauthorized deploy** of a commit that never actually passed CI.
- `PushHandler` forces `stack.sync_github` for any stack whose branch matches the forged `ref`, which can also feed into continuous delivery triggers.
- `MembershipHandler` can add/remove arbitrary GitHub users to/from `Team` records tied to any `organization.login`, affecting `Shipit.github_teams` authorization used elsewhere in the app.

This satisfies the "unauthorized deploy" / "escalation into `Shipit.github_teams` authorization" High/Critical impact categories, and requires no repository write access, session, API token, or secret from the victim organization — only that *some* org in the shared install has a misconfigured (blank) `webhook_secret`, which the README/setup docs and shipped example config show is a normal transient state during onboarding.

### Likelihood Explanation
Requires: (1) the Shipit instance is configured for multiple GitHub organizations (`Shipit.github(organization:)` multi-org schema), and (2) at least one configured organization currently has a blank/unset `webhook_secret` (explicitly shown as a valid/expected interim state in the shipped example config and setup docs). Given this is a documented supported configuration state rather than an edge case, likelihood is non-trivial in any real multi-tenant deployment during onboarding of a new org, or any org that intentionally/accidentally leaves the field blank. The webhook endpoint itself is unauthenticated and public by design, so no other precondition is needed.

### Recommendation
Never derive the HMAC-verification key from unauthenticated request content. Either: (a) key the incoming webhook route by organization/installation ID from the URL path (validated against Shipit's known configured orgs) rather than the JSON body, and additionally verify that all organization-identifying fields inside the payload (`repository.owner.login`, `organization.login`, `repository.full_name`'s owner segment) are mutually consistent before dispatch; or (b) require every configured organization to have a non-blank `webhook_secret` (fail closed instead of `return true unless webhook_secret`); and scope handlers like `StatusHandler` to the repository resolved during verification instead of a global, repo-agnostic `Commit.where(sha:)` lookup.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.yml`: `victim-org` (real `webhook_secret`) and `staging-org` (`webhook_secret: nil`, e.g. mid-onboarding, matching `config/secrets.development.shopify.yml`).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "staging-org" }, "full_name": "victim-org/victim-repo" },
  "organization": { "login": "staging-org" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` computes `repository_owner = "staging-org"`, fetches `staging-org`'s `GitHubApp` (blank secret) → `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (matches the real victim commit regardless of repo) and calls `create_status_from_github!` with attacker-chosen `state: "success"`, satisfying CI gating for `victim-org/victim-repo` without ever possessing `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
