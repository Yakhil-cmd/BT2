### Title
Webhook signature verification keyed by `repository.owner.login` while target repository is resolved from `repository.full_name`, letting an org's own webhook secret sign payloads for a different org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (each org configured with its own `webhook_secret` under `secrets.github[<org>]`), the `WebhooksController#verify_signature` method selects which organization's secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the JSON body. But every webhook `Handler` subclass (`PushHandler`, `PullRequest::OpenedHandler`, etc.) determines which `Repository`/`Stack` to act on using the separate `repository.full_name` field, resolved via `Repository.from_github_repo_name`.

### Finding Description
`verify_signature` computes:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and fetches `Shipit.github(organization: repository_owner)` to obtain the matching `webhook_secret` for HMAC verification [2](#0-1) .

Handlers instead resolve which stack to mutate using `payload.dig('repository', 'full_name')` [3](#0-2) , and `Repository.from_github_repo_name` simply splits that string on `/` to look up owner/name [4](#0-3) .

Since a valid attacker holds the legitimate `webhook_secret` for their own onboarded organization "A" (or, more realistically, has observed/received real webhook deliveries for org A and can compute a valid signature for arbitrary org-A-attributed bodies because the secret is org-scoped, not repo-scoped), and the signature only binds "which secret was used to sign this exact byte string," nothing ties the signing key selection (`repository.owner.login` == "A") to the value actually consumed by the handler for authorization (`repository.full_name`). An attacker who controls org A's webhook secret (e.g., a compromised/malicious GitHub App installation under org A, or knowledge of org A's `webhook_secret`) can construct a payload where `repository.owner.login = "A"` (so the correct, weaker-trust secret is selected and verification passes) but `repository.full_name = "B/victim-repo"` — a completely different organization's repository that has stacks configured in the same Shipit instance. The equality the code implicitly assumes but never enforces is:
`repository.owner.login == repository.full_name.split('/').first`

Nothing in `WebhooksController` or `Handler` enforces this equality, so the organization that authenticated (via secret selection) is not the same as the organization/repository the handler actually writes to.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly listed as in-scope. Depending on handler, an attacker holding one organization's `webhook_secret` could trigger `GithubSyncJob`, archive/unarchive/provision review stacks, or otherwise mutate a totally different (victim) organization's `Stack`/`PullRequest`/`Repository` state despite never having any credential tied to the victim organization. This is a cross-repository/cross-organization write achieved purely from valid authentication under an unrelated org.

### Likelihood Explanation
Requires the attacker to already possess a legitimate `webhook_secret` for at least one organization onboarded to the shared Shipit instance (e.g., their own org's GitHub App installation) — a real precondition for any multi-tenant Shipit deployment. Given that, forging the JSON body's `full_name` field is trivial since it is just a string field consumed for lookup, not independently validated against `repository.owner.login`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that `repository.owner.login` (used to select the signing organization/secret) equals the owner segment of `repository.full_name` (used by handlers to resolve the target `Repository`/`Stack`). Reject the webhook (422) if they diverge, ensuring the same field drives both key selection and authorization target.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `orgA` (attacker-controlled webhook secret) and `orgB` (victim, has stacks for `orgB/victim-repo`).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)`.
4. `verify_signature` looks up `Shipit.github(organization: "orgA")`, verifies successfully using the attacker-known `orgA` secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")`, finds and syncs `orgB`'s stack, enqueueing `GithubSyncJob` against the victim's repository — despite the request never being authenticated with any `orgB` credential.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
