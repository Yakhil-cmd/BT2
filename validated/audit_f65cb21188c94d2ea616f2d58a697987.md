Based on the investigation, the strongest local analog to the `UniProxy._router` caller-controlled-trust issue is in Aptos's **multisig transaction admission path**: `validate_multisig_transaction` in `multisig_account.move`, invoked by the VM prologue (`run_multisig_prologue`) before every multisig transaction executes.

### Title
Multisig execution payload is not bound to the quorum-approved payload when only a full payload (not a hash) is stored and `abort_if_multisig_payload_mismatch` is disabled - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction` is the on-chain admission check the VM runs (via `run_multisig_prologue`) to decide whether a submitted multisig execution is allowed to run. The function only cross-checks the caller-supplied `payload` (which is exactly the executable bytes taken from the *current* transaction being submitted, not the stored approved transaction) against the on-chain record in two disjoint cases: (1) a `payload_hash` was stored, or (2) the full `payload` was stored **and** the `abort_if_multisig_payload_mismatch` feature is enabled. If the multisig transaction was created via `create_transaction` (full payload stored, no hash) and that feature flag is off, neither branch fires, and the caller's `payload` argument is accepted with **no comparison whatsoever** to the payload the owners actually voted on.

### Finding Description
`validate_multisig_transaction` checks quorum and then optionally binds the executing payload to what was approved: [1](#0-0) 

The two guard branches are:
- `transaction.payload_hash.is_some()` → verify `sha3_256(payload) == payload_hash`.
- `features::abort_if_multisig_payload_mismatch_enabled() && transaction.payload.is_some() && !payload.is_empty()` → verify `payload == stored_payload`.

If a transaction was created with `create_transaction` (which stores the full `payload`, not a hash) [2](#0-1) , and the feature `abort_if_multisig_payload_mismatch_enabled` is not turned on, **both** branches are skipped: `payload_hash` is `None` so branch 1 doesn't run, and branch 2 is gated by the feature flag. No assertion ties the caller's `payload` argument to `transaction.payload`.

Critically, the `payload` passed into this admission function is derived directly from the `TransactionExecutableRef` of the transaction currently being submitted for execution — not fetched from the on-chain approved record: [3](#0-2) 

And the same executable bytes are what actually get executed as the multisig account after the prologue passes: [4](#0-3) [5](#0-4) 

So the admission boundary (`validate_multisig_transaction`) can be satisfied by quorum on payload A, while the caller supplies and executes an entirely different payload B as the multisig account, when the gating feature is off — the approval set is validated, but the thing it approved is not bound to what runs. This is the direct analog of the `_router` problem: a value the caller fully controls (`payload`/`executable`) is trusted without verifying it matches the object that legitimate parties (owners) actually authorized.

### Impact Explanation
Any account owner able to reach quorum (or the last approving owner who triggers `can_execute`) can execute an arbitrary entry function or script as the multisig account, bypassing what the other owners actually reviewed and voted for. Because multisig accounts frequently hold treasury funds or admin capabilities, this allows fund theft or unauthorized privileged calls under the multisig's authority — a critical break of the multisig approval-binding invariant (approval validation accepting the wrong approved payload), which is explicitly in-scope per the Admission Pivots ("multisig approval sets ... must bind to the intended account set/content").

### Likelihood Explanation
The exploit path only requires: (1) a multisig transaction created with `create_transaction` (full payload, no hash — a documented, first-class code path, not a misuse) [6](#0-5) , and (2) `abort_if_multisig_payload_mismatch_enabled` being false at the time of execution. I was **not able to confirm within available tool calls whether this feature flag is enabled by default on current networks** (mainnet/testnet) or whether it is still mid-rollout; the naming convention (`abort_if_X_enabled` as an added safety gate) is consistent with Aptos's standard pattern of shipping new invariant checks behind a feature flag before making them mandatory, which would mean the check is off until explicitly activated via governance. This flag-dependency is the single open uncertainty in this finding — if the flag is already permanently enabled/hardcoded on all live networks, this path is not exploitable today.

### Recommendation
Make the full-payload check unconditional (not feature-gated) whenever `transaction.payload_hash` is `None` and `transaction.payload.is_some()`, i.e., always assert `payload == *stored_payload` in that branch regardless of `abort_if_multisig_payload_mismatch_enabled`. Alternatively, deprecate the caller-supplied `payload`/`executable` parameter for multisig prologue/execution entirely and always execute the transaction using the on-chain stored `transaction.payload` (falling back to hash-verified caller payload only when no full payload was stored), removing caller control over what is actually executed.

### Proof of Concept
1. Owner A calls `create_transaction(owner_A, multisig_addr, payload_A_bytes)` where `payload_A_bytes` is a benign, harmless entry-function call. This stores `transaction.payload = Some(payload_A_bytes)` and `payload_hash = None`. [6](#0-5) 
2. Other owners review `payload_A_bytes` off-chain/on-chain and vote to approve, reaching quorum via `approve_transaction`.
3. A malicious owner (or the same owner A) submits the actual on-chain execution transaction with `TransactionExecutableRef::EntryFunction(payload_B)`, where `payload_B` is an arbitrary malicious call (e.g., transfer of multisig-held funds to attacker).
4. `run_multisig_prologue` serializes `payload_B` as `provided_payload` and calls `validate_multisig_transaction(owner, multisig_addr, payload_B_bytes)`.
5. Inside `validate_multisig_transaction`: `transaction.payload_hash.is_some()` is `false` → branch 1 skipped. If `abort_if_multisig_payload_mismatch_enabled()` is `false`, branch 2 is skipped too. No assertion fails.
6. Execution proceeds using `payload_B` (the attacker's payload), not `payload_A` (what owners approved), as confirmed by `execute_multisig_transaction`/`execute_multisig_payload` operating on the same `executable` bytes from the submitted transaction. [7](#0-6) [8](#0-7)

    fn execute_multisig_payload(
        &self,
        resolver: &impl AptosMoveResolver,
        code_storage: &impl AptosCodeStorage,
        mut session: UserSession,
        gas_meter: &mut impl AptosGasMeter,
        traversal_context: &mut TraversalContext,
        multisig_address: AccountAddress,
        payload: &MultisigTransactionPayload,
        change_set_configs: &ChangeSetConfigs,
        trace_recorder: &mut impl TraceRecorder,
    ) -> Result<UserSessionChangeSet, VMStatus> {
        let serialized_signers =
            SerializedSigners::new(vec![serialized_signer(&multisig_address)], None);

        // If txn args are not valid, we'd still consider the transaction as executed but
        // failed. This is primarily because it's unrecoverable at this point.
        session.execute(|session| match payload {
            MultisigTransactionPayload::EntryFunction(entry_function) => self
                .validate_and_execute_entry_function(
                    code_storage,
                    session,
                    &serialized_signers,
                    gas_meter,
                    traversal_context,
                    entry_function,
                    trace_recorder,
                ),
            MultisigTransactionPayload::Script(script) => self.validate_and_execute_script(
                session,
                &serialized_signers,
                code_storage,
                gas_meter,
                traversal_context,
                script,
                trace_recorder,
            ),
        })?;
