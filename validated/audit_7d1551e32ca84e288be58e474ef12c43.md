## Title
CCMenu API token stack-scope bypass — token authorized for one stack grants read access to any stack (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The Kashi report's bug class is a **verification/action binding mismatch**: the value checked is not the value ultimately used. The analogous binding in Shipit is *"the stack a token authorises versus the stack it touches"*. `Shipit::Api::CCMenuController` breaks exactly this binding: it authenticates an `ApiClient` and checks that it holds the generic `read:stack` permission, but then loads the target `Stack` directly from the unscoped `Stack.from_param!(params[:stack_id])` instead of the stack-scoped `stacks.from_param!` helper used by every other API controller. Any `ApiClient` token that was minted with `read:stack` for one specific stack can therefore be replayed with a different `stack_id` to read CI/deploy status of any other stack in the installation.

### Finding Description
`BaseController` defines the correct, scoped lookup: [1](#0-0) 

This ensures that if an `ApiClient` has a `stack_id` set (i.e. it was issued for a specific stack), it can only resolve that stack — `stacks` returns `Stack.where(id: current_api_client.stack_id)` rather than `Stack.all`.

`Api::StacksController` and other in-scope controllers rely on this scoped `stack`/`stacks` method. `CCMenuController`, however, overrides it: [2](#0-1) 

`stack` is resolved via the bare `Stack.from_param!(params[:stack_id])`, completely bypassing `current_api_client.stack_id` scoping. The controller's only authorization gate is the generic permission check: [3](#0-2) 

which only verifies `permissions.include?('read:stack')` — it never verifies that the authenticated token's `stack_id` matches the requested `params[:stack_id]`: [4](#0-3) 

Compounding this, the normal way a "read-only, single stack" CCMenu token is minted is `CCMenuUrlController#client`, which creates/finds an `ApiClient` scoped by `creator`+`name` only — `stack:` is never part of the create attributes, so the resulting token has `stack_id == nil` from creation: [5](#0-4) 

Even if that separate defect were fixed and a `stack_id` were set on creation, `CCMenuController#stack` would still ignore it, so the core vulnerability is the scoping bypass in `CCMenuController`.

**Binding broken:** `stack an ApiClient token authorises (current_api_client.stack_id) == stack the request touches (params[:stack_id])` — this equality is enforced in `BaseController#stacks`/`#stack` but explicitly not enforced in `CCMenuController#stack`.

### Impact Explanation
This is an unauthenticated (query-string token, no session) cross-stack read of stack/deploy state — matches the "High: unauthenticated read of stack state, task streams or deploy output" impact category. An attacker who obtains any valid `read:stack`-scoped API token/CCMenu URL (e.g. one legitimately issued to them for a public/low-sensitivity stack, or leaked from an unauthenticated CI dashboard/build-status widget where CCMenu URLs are commonly embedded) can enumerate `stack_id` values and read deploy/build status, deploy times, and lock state of stacks they were never authorized to see — including private/internal stacks, since `Stack.from_param!` has no ownership check on its own.

### Likelihood Explanation
High. `CCMenuUrlController#fetch` deliberately generates a URL with the token embedded in the query string, intended for use by unauthenticated CI status-badge tools; such URLs frequently end up in dashboards, README badges, or logs. Exploitation requires no privileges beyond possessing one such URL/token and simply substituting a different `stack_id` — `Stack.from_param!` resolves by slug/param and stack ids/slugs are often guessable or discoverable (e.g., via the stacks index).

### Recommendation
In `app/controllers/shipit/api/ccmenu_controller.rb`, change `stack` to use the scoped lookup consistent with `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Additionally, fix `CCMenuUrlController#client` to bind the created `ApiClient` to the specific stack (`stack:` must be part of `create_with`/lookup attributes), so a CCMenu token minted for stack A can never be valid for stack B even before reaching the controller layer.

### Proof of Concept
1. As a user with access to Stack A, visit the CCMenu URL feature; Shipit creates/reuses an `ApiClient` named `"CCMenu Client"` and returns a URL like `.../api/stacks/org/repo-a/env/ccmenu.xml?token=<token>`.
2. Take `<token>` and request `.../api/stacks/org/repo-b-private/env/ccmenu.xml?token=<token>` for a different, unrelated stack B.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` succeeds (client has `read:stack`), and `stack` resolves `Stack.from_param!('repo-b-private/env')` directly — bypassing any `stack_id` scoping — returning build/deploy status for stack B despite the token never having been authorized for it.
