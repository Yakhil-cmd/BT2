### Title
Webhook signature verified per-organization but `StatusHandler` writes commit status cross-tenant by SHA alone, enabling unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit selects the `GitHubApp`/`webhook_secret` used to HMAC-verify an inbound webhook based on the `repository.owner.login` (or `organization.login`) field of the *same* payload the attacker fully controls [1](#0-0) , resolved via `Shipit.github(organization: repository_owner)` [2](#0-1)  and per-organization app config [3](#0-2) . This is Shipit's documented multi-tenant setup where several unrelated GitHub organizations each get their own `webhook_secret` on one shared Shipit instance [4](#0-3) . However, the `status` event handler that actually mutates data never re-checks that the payload's target belongs to the organization whose secret authenticated the request: it looks up commits purely by `sha` across the entire instance and writes a `Status` row for whatever it finds. [5](#0-4) 

### Finding Description
The equality that should hold is:

`organization whose webhook_secret authenticated the request == organization owning the commit/stack that gets written`

`WebhooksController#verify_signature` picks the verifying `GitHubApp` using `repository_owner`, itself read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) [6](#0-5) . The HMAC only proves "whoever crafted this exact byte stream knows organization X's `webhook_secret`" — it says nothing about which records get mutated downstream, because that byte stream is entirely attacker-authored (this is a forged JSON body, not a real GitHub-generated one).

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [7](#0-6) 

This query has no `stack_id`, `repository_id`, or organization scoping whatsoever — `sha` is looked up globally across every `Stack`/`Repository` hosted on the Shipit instance. Compare this with the base `Handler` class, which does provide a `repository_name`/`stacks` scoping helper based on `payload.dig('repository','full_name')` [8](#0-7) , but `StatusHandler` does not use it at all.

Writing a `Status` triggers `enable_ci_on_stack` and `schedule_continuous_delivery` [9](#0-8) , and status transitions gate both manual "deployable" checks and continuous deployment (`stack.schedule_merges`, CD job scheduling) as shown by the transition/CD tests [10](#0-9) [11](#0-10) .

So an attacker who legitimately administers **any one** organization configured on the shared Shipit instance (and therefore can obtain/register a valid `webhook_secret` for that org via GitHub's normal App/webhook settings) can forge a `status` webhook whose `repository.owner.login` matches *their own* org (so it passes `verify_webhook_signature`), while setting `sha` to a commit SHA belonging to an entirely different tenant's repository/stack on the same Shipit instance. The handler will happily create a `success`/`failure` `Status` for that foreign commit.

### Impact Explanation
If the target stack has `continuous_deployment` enabled, a forged `success` status can cause an unauthorized deploy to be scheduled for a commit the attacker doesn't control and doesn't have write access to [11](#0-10) . Even without CD, forging `success` for required/blocking CI contexts defeats `Commit#deployable?` checks that gate manual deploys via the API/UI (`required_statuses`, `blocking_statuses`) [12](#0-11) , letting an attacker (or someone colluding with them) get an unsafe commit deployed by another authorized user who trusts the green CI status. This matches the "unauthorized deploy" Critical impact category. The only prerequisite is that the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) [4](#0-3) , and that the attacker knows a target commit SHA in the victim stack — SHAs are frequently public (visible in PRs, commit URLs, CI logs) even when the attacker has no push/write access to that repository.

### Likelihood Explanation
Exploitability requires only: (1) the shared Shipit instance hosts more than one GitHub organization (explicitly supported/documented), (2) attacker has legitimate admin rights over their own (unrelated) organization's GitHub App/webhook config — not the victim org, and (3) knowledge of a target commit's SHA. No access to the Shipit application itself, no session, and no victim-org credentials are required — only the attacker's own org's `webhook_secret`, which they legitimately possess for their own organization.

### Recommendation
In `StatusHandler` (and any other handler that trusts `sha`/commit lookups without repository scoping), constrain the query to commits belonging to stacks under the repository identified by `repository.full_name`/`repository.owner.login` — the same repository whose organization key was used to select the verifying `GitHubApp` — e.g. `stacks.commits.where(sha: params.sha)` using the `Handler#stacks` helper that already exists but is unused here. More generally, add an invariant check (analogous to the requested `assert!` consistency check in the reported bug class) asserting that the organization used to verify the webhook signature equals the organization owning every record the handler is about to mutate, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgVictim`, each with their own GitHub App/`webhook_secret`, both hosting stacks on the same Shipit instance (per documented multi-org setup) [4](#0-3) .
2. Attacker legitimately controls `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker learns the SHA of a commit `deadbeef...` in `OrgVictim`'s stack (e.g., from a public PR link or CI log), and knows that stack has `continuous_deployment: true` or a required CI context.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<deadbeef...OrgVictim commit>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
signed with `OrgA`'s `webhook_secret` in `X-Hub-Signature`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the HMAC succeeds [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgVictim` commit (global lookup, no org check), and calls `create_status_from_github!`, creating a `success` `Status` on `OrgVictim`'s stack [7](#0-6) .
7. If `OrgVictim`'s stack has continuous deployment enabled, this triggers an unauthorized deploy of that commit; otherwise it unblocks manual deploys that were gated on that CI context.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
