## Title
API client stack-scope bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug class in the M-22 report is a check that validates one quantity (`MINIMUM_LIQUIDITY`) but the actual state-changing action (`removeLiquidity`) is not bound to that check, so the invariant that should hold between "authorized withdrawal amount" and "actual balance removed" is silently broken by a specific caller path. The analogous binding in this Rails engine is: **the set of stacks an `ApiClient` token is authorized to read (`ApiClient#stack_id`) must equal the stack the request actually reads**. In `Shipit::Api::CCMenuController` that equality is broken.

### Finding Description
`Shipit::Api::BaseController` is the shared authorization gate for every scoped API endpoint. It restricts a token's visible stacks to the one it was issued for: [1](#0-0) 

`require_permission :read, :stack` only checks that the client possesses the `read:stack` permission string; it never checks *which* stack is being accessed — that binding is supposed to be enforced entirely by routing all stack lookups through `stacks.from_param!`, which is pre-filtered by `current_api_client.stack_id`: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides the private `stack` method and bypasses the scoped `stacks` collection entirely, loading the stack directly from the global `Stack` table using only the client-supplied `params[:stack_id]`: [3](#0-2) 

Because `require_permission :read, :stack` (declared via `BaseController.require_permission`) only calls `current_api_client.check_permissions!('read', 'stack')` — a string-permission check with no stack argument — and the `stack` method used by `show` no longer goes through `stacks.from_param!`, a token that was minted scoped to Stack A (`ApiClient#stack_id == A.id`) can supply any other stack's `stack_id` in the URL and successfully read that other stack's CCMenu XML (name, activity, last build status/label, web URL).

### Impact Explanation
This is an unauthenticated (relative to the target stack) read of stack/deploy state: it satisfies the "unauthenticated read of stack state" High-impact category from the rules, because it lets a token whose GitHub-side authorization was scoped narrowly (one stack, `read:stack` only) read arbitrary other stacks' deploy/build status. This is a real credential-scope vs. resource-accessed binding violation, not a rate-limiting/DoS/best-practice issue, and does not require GitHub App keys, `webhook_secret`, or repository write access — only possession of any valid `ApiClient` token (e.g. a CCMenu token that end users routinely embed in CI dashboards, generated by `CCMenuUrlController#client` and exposed as a URL query parameter).

### Likelihood Explanation
Every stack's "Settings" page exposes a CCMenu URL containing the token in plaintext in the query string (`app/views/shipit/stacks/settings.html.erb`, `CCMenuUrlController#fetch`), so tokens of this class are widely distributed to third-party CI dashboard tools by design. Any holder of one such legitimately-issued, narrowly-scoped token can trivially enumerate other stacks by varying the `stack_id` path segment — no additional secret or privilege is required.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or `app/controllers/shipit/api/ccmenu_controller.rb`) and have it resolve the stack through the inherited, permission-scoped `stacks` collection (`stacks.from_param!(params[:stack_id])`) exactly as `BaseController` and every other scoped API controller do, so a token's `stack_id` binding is enforced consistently for every endpoint.

### Proof of Concept
1. Admin issues a CCMenu token scoped to Stack A via `CCMenuUrlController#fetch` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, ...)`), producing a URL like `/api/A/ccmenu.xml?token=<T>`.
2. An attacker who obtains `<T>` (e.g., pasted into an external CI aggregator, per the intended CCMenu use case) requests `/api/B/ccmenu.xml?token=<T>` for an unrelated Stack B they were never granted access to.
3. `Api::BaseController#authenticate_api_client` succeeds because `<T>` is a valid token (only checks token validity, not target stack).
4. `require_permission :read, :stack` passes because it only checks the permission string `read:stack` on the client, not the specific stack id.
5. `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly against the global `Stack` table, ignoring `current_api_client.stack_id`, returning Stack B's data despite the token being scoped to Stack A only.

**Uncertainty note**: I was unable to execute file reads for `test/controllers/api/ccmenu_controller_test.rb` and `test/fixtures/shipit/api_clients.yml` in the final iteration (tool call parameters were rejected), so I could not directly confirm from the fixture/test suite whether a stack-scoped `ApiClient` (`stack_id` set) is exercised specifically against `Api::CCMenuController` in the existing test suite, or whether some other layer (e.g. routing constraint) re-adds the missing scoping check that I did not locate in the code I did read. The core code paths cited above (`base_controller.rb` and `api/ccmenu_controller.rb`) were fully retrieved and directly support the described divergence.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
