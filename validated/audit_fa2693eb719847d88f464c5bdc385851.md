### Title
Webhook signature is verified against an attacker-chosen organization while the handler acts on an unrelated `repository.full_name` field, allowing cross-tenant stack sync forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp`/`webhook_secret` to validate the HMAC against based on an attacker-supplied field of the JSON body (`repository.owner.login`, falling back to `organization.login`), but the event handlers that subsequently run act on a *different* field of the same body (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. Nothing re-checks that the `full_name`'s owner matches the organization whose secret validated the signature.

### Finding Description
`verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config (and thus the `webhook_secret`) keyed by whatever login string appears in the untrusted payload. Any tenant who legitimately owns one configured GitHub organization in `Shipit.github` (and therefore genuinely knows that org's `webhook_secret`) can craft an arbitrary JSON body, sign it with their own valid secret, set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` passes), and simultaneously set `repository.full_name` to `victim-org/victim-repo`.

The base `Handler` class and `PushHandler` resolve the target purely from `repository.full_name`, with no cross-check against the organization used to authenticate the request: [3](#0-2) [4](#0-3) 

The `push` handler enqueues `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack in `victim-org/victim-repo`, using an attacker-controlled `after` (SHA) value. This is a binding break of the type: *organization authenticated by the signature* ≠ *repository whose stack is written to by the handler*.

### Impact Explanation
An attacker with legitimate access to their own tenant's webhook secret (a normal, unprivileged capability in a multi-organization Shipit deployment — configuring their own GitHub App/organization does not grant any privilege over other orgs) can forge webhook deliveries that are accepted as authentic and dispatched against stacks belonging to a completely different, victim organization. This lets them trigger `GithubSyncJob` (and other handlers keyed similarly, e.g. `check_suite`, `status`, `pull_request` handlers, all of which resolve the target repository from the same untrusted `repository.full_name`/`organization` payload fields) against arbitrary victim repositories, at minimum causing an unauthorized sync toward an attacker-chosen commit SHA, and depending on downstream sync/status logic, potentially enabling commits to become marked deployable or reflected in commit status data for a repository the attacker does not own.

### Likelihood Explanation
Requires the attacker to control at least one organization/app entry configured in Shipit's multi-tenant `Shipit.github` map (i.e., they know a legitimate `webhook_secret` for their own org) — no repository write access, `ApiClient` token, or Shipit session is needed, only the ability to POST directly to the public `/github/hooks` webhook endpoint, which is unauthenticated at the transport layer and only distinguishes callers via the HMAC-and-org lookup shown above.

### Recommendation
After signature verification, bind the verified organization to the payload's repository owner: reject the request if `repository.owner.login` (or `organization.login`) used for signature selection does not match `repository.full_name`'s owner segment (or the `Repository` record's known owner) before dispatching to handlers, rather than trusting both independently.

### Proof of Concept
1. Attacker's org `attacker-org` is configured in Shipit with `webhook_secret = S` (the attacker legitimately administers this GitHub org and knows `S`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` and POSTs to the webhooks endpoint with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, verifies successfully with secret `S`. [5](#0-4) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack. [6](#0-5)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
