### Title
Cross-Organization Status Forgery Enables Unauthorized Deploy via Unscoped `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook using the `webhook_secret` belonging to the organization named in the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) [2](#0-1) . In Shipit's supported multi-organization configuration, each organization has its own distinct GitHub App and `webhook_secret` [3](#0-2) [4](#0-3) . However, once signature verification succeeds for *some* organization, `Shipit::Webhooks::Handlers::StatusHandler#process` acts on the payload's `sha` field with **no scoping to the authenticated organization or its repositories at all**:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

Unlike `PushHandler`, which restricts affected stacks via `Handler#stacks`/`Repository.from_github_repo_name` derived from `repository.full_name` [6](#0-5) [7](#0-6) , `StatusHandler` never invokes `stacks` or filters by repository/org — it queries `Commit` globally by `sha` across every stack in the Shipit instance.

### Finding Description
The trust binding that should hold is: **the organization whose webhook secret authenticated the request == the repository/commit the resulting write targets.** This binding is broken for the `status` event:

1. `verify_signature` picks the GitHub App/secret to check purely from `repository_owner` (or `organization.login`), values read directly out of the unauthenticated request body before the signature has been verified [1](#0-0) [2](#0-1) .
2. Any tenant that legitimately administers *its own* GitHub App installation (and therefore legitimately knows its own `webhook_secret`, exactly as intended by the "Using Multiple Github Applications" feature [4](#0-3) ) can compute a valid `X-Hub-Signature` HMAC for **any payload body it wants**, as long as `repository.owner.login` names its own org.
3. That attacker crafts a `status` event payload with `repository.owner.login = "attacker-org"` (so `verify_signature` uses the attacker's own secret and passes) but with `sha` set to a commit SHA belonging to a totally different, victim stack/organization, and `state = "success"`.
4. `StatusHandler#process` does `Commit.where(sha: params.sha)` — this is a global, unscoped lookup, so it matches the victim's commit regardless of which organization's secret validated the signature [5](#0-4) .
5. `commit.create_status_from_github!(params)` → `Commit#add_status` creates a forged `Status` record for the victim's commit [8](#0-7) [9](#0-8) .
6. `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` fire on the victim stack [10](#0-9) , and `add_status` also calls `stack.schedule_merges if new_status.pending? || new_status.success?` [11](#0-10) .
7. Because `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [12](#0-11) , injecting a forged `success` status flips the victim's commit to deployable, which — combined with continuous delivery/merge-queue scheduling — can trigger an unauthorized deploy of the victim's stack, entirely from an attacker who only controls their own, unrelated organization's webhook credentials.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out as in-scope. A tenant/organization admin with no privileges on the victim's repository or stack can forge CI status data for the victim's commits, defeating CI gating and enabling an unauthorized deploy — matching the Critical impact category ("unauthorized deploy").

### Likelihood Explanation
Requires only that the attacker operate a legitimately configured GitHub App/organization within the same multi-tenant Shipit instance (a documented, supported configuration) and know their own `webhook_secret` — no compromise of the victim's credentials, GitHub account, or Shipit session is needed. The `sha` value is a public piece of information (commit hashes are visible in git history/PRs), making target selection straightforward.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository derived from the verified payload, mirroring `Handler#stacks`/`repository_name`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner })`. More fundamentally, `verify_signature` should bind the authenticated organization into request-scoped state that all handlers are required to check against the repository/commit they act on, rather than allowing handlers to trust payload fields independently of which secret validated them.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per docs' multi-org setup).
2. Identify a commit `sha` belonging to a stack under `victim-org` that is currently not deployable (e.g., pending/no CI).
3. Build a `status` webhook payload:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Sign it with `attacker-org`'s own `webhook_secret` (`sha1=` HMAC as computed by `DeliverySigner`/`verify_webhook_signature`) [13](#0-12) .
5. POST to `/github/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
6. `verify_signature` succeeds (valid signature for `attacker-org`) [1](#0-0) ; `StatusHandler` then creates a `success` `Status` on the victim's commit regardless of `attacker-org` having no relationship to `victim-org` [5](#0-4) .
7. Observe the victim commit becomes `deployable?` and continuous delivery/merge scheduling is triggered on the victim's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
