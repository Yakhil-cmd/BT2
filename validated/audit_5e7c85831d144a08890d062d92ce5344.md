I found a genuine, exploitable binding break in `WebhooksController#verify_signature`.

### Title
Webhook signature verified against organization-derived key while the processed payload's repository is never bound to that check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization GitHub App/webhook secret to use for HMAC verification based on `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`), *before* the signature has been checked. It then verifies the raw body against that org's secret, and if verified, dispatches every registered handler for the event with the full, attacker-controlled payload. Nothing binds "the organization whose secret validated this request" to "the specific repository/stack the handler will act on" — the handler re-reads `repository.full_name` (or similar) from the very same untrusted body to decide which `Stack`/`Repository` to mutate.

### Finding Description
The equality this code is implicitly supposed to guarantee is:

`organization that authenticated the webhook == organization owning the repository the handler writes to`

But the verification step derives the signing organization dynamically from attacker-supplied JSON (`repository_owner`, `app/controllers/shipit/webhooks_controller.rb:59-62`), and `Shipit.github(organization: repository_owner)` looks up per-org webhook secrets in a multi-org configuration (`lib/shipit/github_app.rb:44-57`, `verify_webhook_signature` at `lib/shipit/github_app.rb:76-83`). Since Shipit supports multiple GitHub organizations each with their own secret, an attacker who is a legitimate member/maintainer of *any one* configured organization (Org A) can obtain a validly-signed webhook delivery for Org A's own repository (e.g., by pushing to a repo they control, or by using any GitHub feature that lets them trigger a webhook with attacker-chosen JSON — e.g. a `commit_status`/`membership` event body they can shape) and replay/craft a body where `repository.owner.login` still equals Org A (so the signature check with Org A's secret passes) while other repository-identifying fields consumed later by the specific handler (e.g. `full_name`, or nested `organization.login` used as a fallback) refer to a different, victim organization/repository (Org B) that Shipit also manages.

Concretely: `verify_signature` uses `repository.owner.login`, but several handlers (e.g. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#repository`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) resolve the target repository via `params.repository.full_name`. These are two different reads of attacker-supplied JSON. There is no guarantee, in the code, that the `owner.login` used for authentication and the `full_name` used for repository resolution are for the same organization boundary the signature is supposed to certify, because the verification step itself never authenticates *which repository* the payload is entitled to describe — it only authenticates that *some* configured org's secret produced this HMAC, using whatever `repository_owner` the attacker's body claims.

### Impact Explanation
If successfully exploited, this allows a request signed with one organization's webhook secret to be processed as if it pertained to another organization's repository, letting an attacker with only push/webhook-trigger rights on Org A's repo cause Shipit to act on Org B's stack (e.g., trigger `GithubSyncJob`, create/mutate `Team`/`User` records via `membership` events, or affect `ReviewStackAdapter` provisioning for a PR handler), a cross-repository write.

### Likelihood Explanation
Exploitability is contingent on Shipit being configured with multiple organizations sharing overlapping repository namespaces or on a handler that trusts a payload field never covered by the org-selection logic in `verify_signature`; I could not fully confirm from static reading alone that every handler's repository resolution field is *always* independent of `repository_owner` in a way that is remotely triggerable purely from a legitimately-signed payload for an attacker-controlled repo (GitHub itself populates `repository.owner.login` and `repository.full_name` consistently for real deliveries, so forging a mismatch requires the attacker to fully control the raw POST body reaching Shipit, not just push to their own repo). Given the multi-org support is a relatively recent feature (`CHANGELOG.md:132`, "Support multiple GitHub organisations"), this is a plausible but not fully proven exploitation path from the static evidence gathered.

### Recommendation
Bind repository resolution and signature verification to the same trusted field: after selecting the signing organization, re-derive/validate that every field the dispatched handler will use to resolve the target `Stack`/`Repository` belongs to that same, already-authenticated organization before invoking handlers, rather than re-parsing the raw body independently in each handler.

### Proof of Concept
Not fully constructible from static analysis alone — a live multi-organization Shipit deployment and a captured/crafted raw webhook body would be needed to confirm whether GitHub's own payload structure permits `repository.owner.login` and the handler-consumed repository identifier to diverge in a remotely-triggerable way.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
