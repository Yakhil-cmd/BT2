### Title
`data_feed[[...]]` in oscript formula evaluation exposes unstable oracle updates to AA triggers, enabling sandwich attacks against price-based AAs - (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
The `data_feed[[...]]` and `in_data_feed[[...]]` oscript primitives, used by any AA author to read oracle prices inside a trigger response, are resolved through `dataFeeds.readDataFeedValue()`/`dataFeedExists()` with the `bAA` flag set to `true`. When `bAA` is true, these functions scan `storage.assocUnstableMessages` — i.e., data-feed messages from oracle units that have been broadcast on the network but have **not yet reached DAG stability** — in addition to already-stable feed values. This lets a trigger sender's AA response consume a price the instant it is broadcast, before it is final, exactly like reading a pending mempool transaction in the Unitas/XOracle report.

### Finding Description
`formula/evaluation.js` handles the `data_feed` opcode by calling: [1](#0-0) 
which passes `bAA` (true when the formula is evaluated as part of an AA response) into `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)`.

Inside `data_feeds.js`, when `unstable_opts` (here `bAA`) is truthy, `readDataFeedValue` iterates `storage.assocUnstableMessages` — units that are known to the node but not yet stabilized on the main chain — and picks the data-feed value from the candidate with the highest `latest_included_mc_index`/`level`: [2](#0-1) 

The same unstable-message scan is used for the boolean `in_data_feed[[...]]` primitive via `dataFeedExists`: [3](#0-2) 

Any AA author can (and the official sample templates in this codebase do) build price-dependent exchange logic on top of `data_feed[[...]]`, e.g. the futures contract sample computing a byte/asset conversion rate directly from an oracle feed: [4](#0-3) 
and the option contract sample gating asset redemption on a live oracle comparison: [5](#0-4) 

Because unstable oracle units propagate over the P2P network before they are stable, any unprivileged AA trigger sender who observes the oracle's price-update unit as soon as it is gossiped can:
1. Immediately post a trigger unit that (via `bAA=true` unstable lookup) sees the *new* price before it is final, executing a trade that is favorable relative to the AA's other assets/balances still priced at the old level, or conversely
2. Choose *not* to build on the oracle's unit (keeping their own trigger's DAG position such that the oracle update is outside `[min_mci, max_mci]` or absent from `assocUnstableMessages` relative to their unit's ancestry), thereby forcing the AA to use the stale price for one leg of a two-sided trade and the fresh price for the other leg — the same "buy cheap before, sell dear after" structure described in the reported issue.

This differs from a normal user simply reacting to a stable price: the vulnerability specifically stems from ocore's core protocol choice to let AA responses consult **not-yet-stable** data-feed messages (`bIncludeUnstableAAs`/`unstable_opts` path), which removes the natural "commit" delay that stabilization would otherwise provide and creates a race window identical in kind to the mempool-visibility window exploited in the XOracle report.

### Impact Explanation
Any AA that uses `data_feed[[...]]`/`in_data_feed[[...]]` to price a swap, redemption, or settlement (as in the shipped `futures_contract.oscript` and `option_contract.oscript` templates, and any production AA following this well-documented pattern) can have its bytes/asset reserves drained by a trigger sender who races the propagation of an oracle price update, executing a buy immediately before the update is effectively "seen" and a sell immediately after, extracting the price delta from the AA's reserves — mirroring the "Unitas reserves are drained" impact in the original report, but here against any Obyte AA-based exchange/derivative contract.

### Likelihood Explanation
Any address can trigger an AA (no privilege required), oracle price updates are necessarily broadcast publicly before they stabilize, and the unstable-data-feed lookup path (`bIncludeUnstableAAs`) is exercised on every AA evaluation that uses `data_feed`/`in_data_feed`, so the precondition (observing an oracle unit in-flight and racing a trigger) is always available whenever a price-sensitive AA is deployed using this standard, documented pattern.

### Recommendation
- For AA authors: avoid pricing large one-shot trades purely off the latest unstable `data_feed` value; require the referenced data-feed unit to be at least a few MCI old (`min_mci`), average over a time window, or apply a time/fee buffer as in `futures_contract.oscript`'s `GBYTE_USD_MA_2019_04_30` fixed-date feed.
- For ocore: consider adding an oscript option to force `data_feed[[...]]` to consult only *stable* messages (bypass `bIncludeUnstableAAs`) so AA authors can opt out of the unstable/pending-price race window when building price-sensitive contracts.

### Proof of Concept
1. Deploy an AA following the `uniswap_like_market_maker.oscript` / `futures_contract.oscript` pattern that prices a swap/redemption via `data_feed[[oracles=..., feed_name=...]]`. [6](#0-5) 
2. Oracle broadcasts a unit updating the feed to a new value (e.g., price increases). This unit is visible on the network immediately but not yet part of the stable main chain.
3. Attacker immediately posts trigger unit A that buys the AA's underlying asset; because `readDataFeedValue` is called with `bAA=true`, it scans `storage.assocUnstableMessages` and can pick up the fresh oracle value for this trigger while the AA's balance still reflects pre-update state (`data_feeds.js:211-273`).
4. Once the price update and the attacker's first trade both stabilize, attacker posts trigger unit B that sells back, again reading the (now different visibility window of) the data feed, capturing the spread from the AA's reserves.
