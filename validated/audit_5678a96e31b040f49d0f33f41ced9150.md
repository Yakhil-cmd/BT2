### Title
Stale `bOpListCanChange` snapshot taken before re-acquiring the `handleJoint` lock lets nodes disagree on MC stability - ([File: main_chain.js])

### Summary
`determineIfStableInLaterUnitsAndUpdateStableMcFlag` releases the DAG-state context, evaluates `hasUnstableOpVoteCount()` *outside* any lock, and only afterwards asynchronously acquires the `handleJoint` mutex before advancing the stability point over a range of MCIs. Any unit posted by an ordinary user between the snapshot and the lock acquisition can change whether an OP-list vote count is pending, but the code keeps using the stale snapshot for the whole multi-MCI stabilization loop. This is structurally the same bug class as ALPINE-CVE-2026-62435: code drops/reacquires a lock and assumes a property (there: v1/v2 grant table shape; here: "OP list is/ins't mutable during this stabilization pass") stays constant across the window when the lock isn't held.

`bOpListCanChange` is computed by `hasUnstableOpVoteCount()`, which just scans `storage.assocUnstableMessages` for a pending `system_vote_count`/`op_list` message: [2](#0-1) 

The code already recognizes that state can move while waiting for the `handleJoint` lock — it explicitly re-reads `last_stable_mci` and `objEarlierUnitProps` after acquiring the lock and bails out if the stability point already advanced (line 1222-1223). However, it does **not** re-evaluate `bOpListCanChange` after acquiring the lock; the boolean captured before the lock request is used unconditionally for the entire multi-MCI loop that follows.

Any unpriviledged unit author can post a unit carrying a `system_vote`/`system_vote_count` message once `last_ball_mci >= constants.v4UpgradeMci` — validated only by ordinary structural checks in `validation.js`: [3](#0-2) 

Because `handleJoint` is a single global mutex shared by joint validation/writing (`network.js:handleJoint`, `writer.js:saveJoint`) and by this stabilization path, and because `mutex.lock` queues callers when the key is already held (`mutex.js:75-86`), there is a realistic window between `hasUnstableOpVoteCount()` being read and the "handleJoint" lock actually being granted during which another unit with a `system_vote_count` for `op_list` is processed and stored into `storage.assocUnstableMessages` (or, conversely, an existing pending vote-count unit gets stabilized and cleared from `assocUnstableMessages` by `saveUnstablePayloads`, `main_chain.js:1550-1585`, decided by `voteCountSubjects`).

* If `bOpListCanChange` was captured as `false` but a `system_vote_count` for `op_list` becomes pending during the wait, the node will stabilize the whole `[last_stable_mci+1 .. new_last_stable_mci]` range via straight `stabilizeMci()` calls **without** re-checking stability per-MCI against the (possibly changing) best-parent OP list, even though `stabilizeMci` itself can trigger `countVotes()` mid-loop and change `storage.systemVars.op_list` between iterations.
* A different node that happened to grab the lock a moment earlier/later (or that received the vote-count unit slightly before/after computing its own snapshot) would take the opposite branch, performing the extra `determineIfStableInLaterUnits` check with the current OP list and potentially reaching a different verdict on which MCIs are stable/should even be advanced (`break` at line 1231).

This directly mirrors the Xen advisory’s pattern: "code holding, but intermediately dropping and then re-acquiring the grant table lock, sometimes wrongly assumes that said properties wouldn't change across the window in time where the lock is not being held." Here the analogous "property" is whether the OP list vote count is mutable/pending, and the "lock" is the `handleJoint` mutex.

### Impact Explanation
Divergent handling of the OP-list-mutability flag across nodes can cause them to disagree about which main-chain indices are stable and about the resulting OP list used for stability determination going forward. This is a stability/consensus divergence: different nodes may stabilize a different set of MCIs (or the same MCIs using a different effective OP list), which can propagate into different `is_stable` flags, different AA trigger executions at those MCIs, and different downstream vote counts — i.e., node disagreement on validity/stability of the DAG, potentially fragmenting the network's shared view of finality.

### Likelihood Explanation
The trigger requires only an ordinary unit carrying a `system_vote`/`system_vote_count op_list` message, postable by any unprivileged unit author once past `v4UpgradeMci` — no special privileges are needed. The race window is real because `handleJoint` is a heavily contended global lock (used for essentially all joint validation and writer commits), so queuing delays before this stabilization job's lock request is fulfilled are common, especially under load or during batches of new-unit processing. The other required condition is that the actual OP-list-vote-count pending state changes exactly within that window, which is not attacker-fully-controlled but plausible given normal periodic OP re-election activity or an attacker deliberately timing their `system_vote_count` post to coincide with observed main-chain progress. Overall likelihood is moderate rather than trivial to reliably trigger, matching the report's Medium severity.

### Recommendation
Re-evaluate `hasUnstableOpVoteCount()` (or equivalent up-to-date state) immediately after the `handleJoint` lock is acquired, rather than relying on the snapshot taken before the lock request, so that the per-MCI stability check (`bOpListCanChange && mci >= v4UpgradeMci`) is based on state guaranteed consistent with the state used to compute `new_last_stable_mci`/`last_stable_mci`. Alternatively, re-check the flag on every loop iteration, since `stabilizeMci` itself can alter it mid-loop by processing `system_vote_count` messages.

### Proof of Concept
Conceptual scenario (cannot be executed without live multi-node infra/DB, but derivable purely from the code paths cited):
1. Node A's `handleJoint` mutex is currently held processing an unrelated joint.
2. `determineIfStableInLaterUnits` finds `earlier_unit` newly stable in later units; `bStable && !bStableInDb`, so `handleResult` fires and the code proceeds to move the stability point.
3. At this instant `hasUnstableOpVoteCount()` returns `false` (no pending `op_list` vote count) — `bOpListCanChange = false` is captured.
4. Before Node A's queued `mutex.lock(["handleJoint"], ...)` callback fires, an ordinary user unit containing `{app:'system_vote_count', payload:'op_list'}` is validated and saved by the currently-running joint-handling job, adding an entry to `storage.assocUnstableMessages`.
5. Node A's callback finally runs with `bOpListCanChange` still `false`; the loop over `[last_stable_mci+1 .. new_last_stable_mci]` calls `stabilizeMci(mci)` directly for every MCI, skipping the "check stability before every step using the best parent's OP list" branch that a node which captured `bOpListCanChange = true` (because it read the flag a moment later, after step 4) would have executed.
6. The two nodes can end up stabilizing a different range of MCIs (one may `break` early due to the extra check failing, the other advances fully), producing disagreement on stability between nodes.

function hasUnstableOpVoteCount() {
	for (let unit in storage.assocUnstableMessages) {
		for (let message of storage.assocUnstableMessages[unit]) {
			if (message.app === 'system_vote_count' && message.payload === 'op_list')
				return true;
		}
	}
	return false;
}
