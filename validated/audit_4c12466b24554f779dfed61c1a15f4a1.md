### Title
CCMenu API endpoint uses `Stack.from_param!` instead of scoped `stacks`, letting a stack-scoped `ApiClient` token read the CI status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` restricts which stacks an `ApiClient` may act on: when a token is scoped to a stack (`current_api_client.stack_id?`), `stacks` is limited to `Stack.where(id: current_api_client.stack_id)`, and controllers are expected to resolve the target stack through this scoped relation (`stacks.from_param!(params[:stack_id])`). `Shipit::Api::CCMenuController` overrides `stack` to instead call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing the `stack_id` binding entirely.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id` [1](#0-0) . `Api::BaseController#stacks` enforces that scope for controllers that use it: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and the base `#stack` helper resolves through it: `stacks.from_param!(params[:stack_id])` [2](#0-1) .

`CCMenuController` requires only `:read, :stack` permission and then defines its own `stack` method that ignores the scoped `stacks` relation entirely, resolving directly against the global `Stack` model:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

This breaks the binding "a stack a token authorizes == a stack a token can act on/read." Before the flaw: a token with `stack_id` set to stack A and `read:stack` permission should only be able to fetch CI status for stack A. After: the `require_permission :read, :stack` check at [4](#0-3)  only verifies the `read:stack` permission string is present on the token — it never checks the token's `stack_id` scope against the actual `stack_id` route parameter, because `#stack` never goes through `stacks`. Any valid, unrevoked `ApiClient` token that has `read:stack` permission — even one deliberately scoped to a completely unrelated stack — can call `GET /api/stacks/:stack_id/ccmenu` for **any** other stack in the Shipit instance and read its latest deploy/rollback status, id, and success/failure state, rendered as CCMenu XML [5](#0-4) .

The route confirms `:stack_id` is fully attacker-controlled per request: `scope '/stacks/*stack_id', ... get '/ccmenu' => 'ccmenu#show'` [6](#0-5) .

### Impact Explanation
This is an authorization-scope escalation: a credential legitimately issued and scoped to stack A ends up authorizing read access to CI/deploy state of any stack B in the instance, directly matching the in-scope High-impact category "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state, task streams or deploy output" (the token effectively becomes an unscoped-read credential for all stacks' deploy status, despite being provisioned as scoped-only). It requires nothing beyond possessing one legitimately-scoped, low-privilege token (e.g. a CCMenu client created via `CCMenuUrlController`, which creates tokens scoped to a single stack: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, ...)` [7](#0-6) ), which by design is meant to be narrowly scoped and often shared/embedded in external CI dashboards.

### Likelihood Explanation
High likelihood: any holder of a stack-scoped CCMenu-style token (these are designed to be embedded in third-party CI-status tools, so exposure risk is real) can trivially enumerate/guess other `stack_id` path segments (owner/repo/environment triples are often predictable/public GitHub repo names) and read their deploy status without any additional authentication.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation, consistent with the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that the `current_api_client.stack_id` binding is enforced the same way it is in `Api::BaseController` and `Api::StacksController`.

### Proof of Concept
1. As a legitimate user, create a CCMenu client scoped to Stack A via `GET /ccmenu/*stack_id`, which internally calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` with `stack: nil` unless explicitly scoped — but any token created with `stack_id` set (e.g., via `Api::ApiClientsController#create` with a `stack_id`) and permission `read:stack` reproduces the issue.
2. Obtain the token's `authentication_token` (Basic Auth credential) for the stack-A-scoped client.
3. Call `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu` using that token's Basic Auth credentials.
4. Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(...)`, the request succeeds and returns the CCMenu XML (deploy status) for the unrelated stack, despite the token being scoped only to Stack A.
