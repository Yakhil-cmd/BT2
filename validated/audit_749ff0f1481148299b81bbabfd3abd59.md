### Title
Unhandled NULL/undefined pointer dereference in `handleOnlinePrivatePayment` crashes the node on a malformed `private_payment` message - ([File: network.js])

### Summary
`handleOnlinePrivatePayment()` in `network.js` dereferences `arrPrivateElements[0].payload.denomination` before verifying that `arrPrivateElements[0].payload` is even an object. A peer or private-payment counterparty can send a `private_payment` justsaying message whose head element has no `payload` field (or a non-object `payload`), causing a synchronous `TypeError: Cannot read properties of undefined (reading 'denomination')`. This is the same bug class as CVE-2021-45773 (NULL pointer dereference from unchecked attacker-controlled input in a network-facing message handler causing a crash/DoS), just expressed as a JS `TypeError` instead of a C NULL pointer dereference.

### Finding Description
`handleOnlinePrivatePayment` is reached from the `private_payment` justsaying handler in `network.js` and from `wallet.js`'s `handlePrivatePaymentChains` (hub relaying), both of which forward attacker/peer-controlled JSON directly into this function: [1](#0-0) 

The function validates that `arrPrivateElements` is a non-empty array, but does not validate the shape of `arrPrivateElements[0]` before accessing nested fields:
```js
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");

	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	...
```
If `arrPrivateElements[0].payload` is `undefined`, `null`, a string, or any non-object, `.denomination` throws a `TypeError`. This throw happens synchronously inside the WebSocket `'message'`/justsaying dispatcher, outside of any `try/catch`, so it propagates as an uncaught exception in the event loop and crashes the Node.js process (or triggers the global uncaught-exception handler that most ocore deployments configure to exit/restart).

Contrast this with the proper defensive pattern used elsewhere in the same private-payment code paths, e.g. `private_payment.js`, which explicitly checks `headElement.payload` before touching it: [2](#0-1) 

and `wallet.js`'s caller, which reads `objHeadPrivateElement.payload.denomination` under the same unguarded pattern before calling into `network.handleOnlinePrivatePayment`: [3](#0-2) 

Both call sites are reachable by an unprivileged actor: any WebSocket peer can send a `justsaying` with subject `private_payment` directly (network.js), and any paired device/hub correspondent can trigger the `wallet.js` path via `handlePrivatePaymentChains`.

### Impact Explanation
A remote, unauthenticated peer connection (or any paired correspondent) can crash a full node or light node by sending a single malformed `private_payment` message with a head element that has no (or a malformed) `payload`. Because this code executes early, before any database/mutex work and before validation of the payload's actual content, the crash is cheap and repeatable. If deployed nodes auto-restart, this becomes a rolling, low-cost DoS against relays/hubs that process such messages from many peers, degrading network availability to confirm/relay private and public transactions. This satisfies the requested impact class of "a network unable to confirm new units" via resource-cheap, repeatable crashes of core relaying/validation processes — the direct analog of the lib60870 NULL-pointer crash-on-malformed-field.

### Likelihood Explanation
High. No authentication or pairing beyond an accepted WebSocket connection is required to reach the `network.js` code path; the message is a `justsaying`, requiring no round-trip request/response and no rate limiting beyond normal connection handling. The only requirement is that `arrPrivateElements` be a non-empty array (trivially satisfiable) with an object that either omits `payload` or sets it to a primitive value.

### Recommendation
Add explicit type/shape validation of `arrPrivateElements[0]` and its `payload` field before any property access, mirroring the guard already present in `private_payment.js`:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("no payload in private_payment head element");
```
Apply the same defensive check in `wallet.js`'s `handlePrivatePaymentChains` before dereferencing `objHeadPrivateElement.payload.denomination`. More generally, wrap message-handling entry points (`onWebsocketMessage`/justsaying dispatch) in a top-level `try/catch` that reports and drops the offending message instead of allowing an uncaught exception to terminate the process.

### Proof of Concept
An attacker connects to a full/light node (or a hub relays on their behalf) and sends:
```json
["justsaying", {
  "subject": "private_payment",
  "body": [
    { "unit": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=" }
    // no "payload" field at all
  ]
}]
```
This message reaches `handleOnlinePrivatePayment(ws, arrPrivateElements, false, callbacks)`. At `arrPrivateElements[0].payload.denomination`, `payload` is `undefined`, so the property access throws `TypeError: Cannot read properties of undefined (reading 'denomination')`, uncaught, crashing the node process.

Note: I was not able to trace the exact top-level dispatcher/try-catch wrapping for the `private_payment` justsaying subject inside `network.js` (the switch-case body for `handleJustsaying`'s `'private_payment'` branch) within the indexed snippets, so I cannot state with 100% certainty whether a surrounding `try/catch` exists at that exact call site that would convert the crash into a caught error instead. Confirming this would require inspecting the full `handleJustsaying` switch statement in `network.js` around the `private_payment` case, which was not fully retrieved in this session — a live Devin session with full file access could verify this quickly.
