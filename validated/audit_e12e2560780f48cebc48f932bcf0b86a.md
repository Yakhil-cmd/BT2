### Title
Flash-loan receiver can inject unauthorized wallet transfers into the caller's signed authorization tree - (File: contracts/pool/src/ops/flash.rs)

### Summary
`flash_loan` permits the caller to choose any deployed Wasm receiver, and the pool invokes its `execute_flash_loan` callback before collecting repayment. [1](#0-0)  A malicious receiver can use that callback to request the victim's authorization for unrelated token transfers; simulation records the transfer as a child of the victim's `flash_loan` authorization, and it executes if the victim signs that poisoned tree. [2](#0-1) 

### Finding Description
`Controller::flash_loan(caller, asset, amount, receiver, data)` is permissionless but requires caller authorization, while `receiver` is supplied as an argument. [3](#0-2)  The pool only checks that `receiver` is a Wasm contract, transfers the principal to it, and invokes `execute_flash_loan`; it does not restrict the receiver to an allowlist or constrain what other authorization requests the receiver makes during the callback. [4](#0-3)  The callback can therefore call `token.transfer(victim, attacker, victim_balance)` on any token held by the victim, and the host will reject it only when that transfer is absent from the signed authorization tree. [5](#0-4)  A compliant malicious receiver can still approve `amount + fee` to the pool, so the protocol's exact repayment checks pass after the unrelated transfer has executed. [6](#0-5) 

### Impact Explanation
The attacker can steal unrelated tokens directly from the victim's wallet, not merely the flash-loaned asset or funds already committed to the protocol. [7](#0-6)  Because token balances are public, the receiver can be configured or instructed through `data` to request the victim's full balance of a chosen token. [8](#0-7)  The protocol's own balance and repayment invariants remain intact, making the damage an unauthorized theft of user funds rather than pool insolvency. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker can deploy a conforming `execute_flash_loan` receiver and induce a victim to submit `flash_loan` with that receiver, such as through a malicious interface or bundled transaction. [3](#0-2)  Exploitation requires the victim to sign the authorization tree containing the extra token transfer, so it is not unilateral and depends on inadequate wallet or client-side authorization inspection. [10](#0-9)  The attacker must also arrange repayment approval for `amount + fee`, but the receiver has just received the principal and can supply the fee itself. [6](#0-5) 

### Recommendation
Restrict `receiver` to a governance-managed allowlist or to protocol-reviewed receiver implementations if unrestricted flash-loan callbacks are not required. [4](#0-3)  If arbitrary receivers are retained, clients must treat the authorization tree as part of the security boundary: decode it before signing and reject any child invocation other than the expected flash-loan flow. [11](#0-10) 

### Proof of Concept
1. The attacker deploys `MaliciousReceiver` implementing `execute_flash_loan`.
2. The attacker causes the victim to submit `Controller::flash_loan(victim, asset, amount, malicious_receiver, data)`.
3. The pool transfers `amount` to `MaliciousReceiver` and invokes its callback. [12](#0-11) 
4. Inside the callback, `MaliciousReceiver` calls `TOKEN.transfer(victim, attacker, balance_of_victim)` and then approves `amount + fee` for the pool. [13](#0-12) 
5. Transaction simulation adds the victim-token transfer as a child under the victim's `flash_loan` authorization. [14](#0-13) 
6. If the victim signs that tree, the callback moves the unrelated wallet tokens to the attacker and the pool successfully collects `amount + fee`. [10](#0-9)

```rust
fn collect_repayment(
    env: &Env,
    asset: &token::Client,
    pool: &Address,
    receiver: &Address,
    terms: &FlashTerms,
) {
    assert_with_error!(
        env,
        asset.allowance(receiver, pool) >= terms.total_repayment,
        FlashLoanError::InvalidFlashloanRepay
    );
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
    require_balance(env, asset, pool, terms.balance_after_repayment);
}
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
