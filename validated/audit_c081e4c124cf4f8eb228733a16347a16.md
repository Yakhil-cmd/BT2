### Title
Webhook signature verification uses an attacker-controlled organization key that is decoupled from the repository the event actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to authenticate a webhook with, using an organization login taken directly from the unverified request body. Every downstream event handler, however, decides which `Stack`/`Repository` the event applies to using a *different* field (`repository.full_name`) from that same unverified body. Because `GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for the selected organization, an attacker can pick a "authenticating organization" whose config has no secret, while pointing the actual mutation at a repository belonging to a different, secret-protected organization.

### Finding Description
`verify_signature` reads the authenticating organization from the raw JSON payload before any cryptographic check has been performed: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the GitHub App configuration keyed by that attacker-supplied login, and constructs a `GitHubApp` scoped to whatever `webhook_secret` (or absence thereof) is configured for it: [3](#0-2) 

The signature check itself short-circuits to `true` whenever the selected organization has no `webhook_secret` configured: [4](#0-3) 

Once the request passes `verify_signature`, the actual event handlers never re-check which organization "authenticated" the request. Instead they derive the target `Stack`/`Repository` from a *different* JSON field in the same attacker-controlled body, `repository.full_name`: [5](#0-4) [6](#0-5) 

This breaks the required binding: `organization used to authenticate the request == organization owning the repository the handler acts on`. In this engine's multi-organization configuration schema (documented and tested), each organization can have its own `webhook_secret`: [7](#0-6) 

An attacker who knows (or guesses) that any one configured organization has no `webhook_secret` set can craft a single POST to `/github_webhooks` with:
- `repository.owner.login` = the unprotected organization (drives `verify_signature`, which passes unconditionally), and
- `repository.full_name` = `"<protected-org>/<victim-repo>"` (drives the handler's `Repository.from_github_repo_name` lookup and thus which `Stack` is acted on).

Because these two fields are never cross-checked against each other, the request is treated as fully authenticated for the protected organization's repository even though no valid HMAC was ever produced for that organization's secret.

### Impact Explanation
This is an authentication-bypass primitive on the public, unauthenticated `/github_webhooks` endpoint (no session, no `ApiClient` token, no GitHub App key needed by the attacker). Depending on which event type is spoofed, this can drive an unauthorized action against a stack that the attacker was never supposed to control:
- `push` → forces `stack.sync_github` on an arbitrary matched stack/branch [8](#0-7) .
- `pull_request` (opened/closed/labeled/reopened) → provisions, archives, or unarchives review stacks for a targeted repository [9](#0-8) .
- `membership` → creates/deletes `Team`/`Membership` records, which feed directly into `Shipit.github_teams` authorization used to gate access to the whole app [10](#0-9) .

Because `Shipit.github_teams` membership/authorization state can be manipulated and stack-affecting events can be forged for repositories the attacker does not administer, this reaches the report's High/Critical bar ("escalation into `Shipit.github_teams` authorization" and "unauthorized deploy" surface via forced sync/provisioning).

### Likelihood Explanation
Exploitability requires only that the multi-organization GitHub config schema be in use and that at least one configured organization omit `webhook_secret` (a supported, documented configuration, not a misuse of the engine) while another configured organization does set one. No credentials or network position beyond sending an HTTP POST to the public webhook endpoint are required, and the fields involved (`repository.owner.login`, `repository.full_name`) are both plain, attacker-supplied JSON in the same payload, so likelihood is high whenever this multi-org configuration pattern is deployed.

### Recommendation
Bind the signature-verification organization to the same repository identity the handlers act on: derive the authenticating organization from `repository.full_name`'s owner segment (or otherwise ensure the two fields are the same value) before selecting the `GitHubApp`/`webhook_secret`, and require a configured `webhook_secret` for every organization (reject with 422 rather than default-allow when the selected config has none), so that an unprotected organization's absence of a secret can never be leveraged to short-circuit verification for a different organization's payload.

### Proof of Concept
1. Configure Shipit with the multi-org schema: `org-a` (no `webhook_secret`) and `org-b` (`webhook_secret: "s3cr3t"`), with a `Stack` for `org-b/victim-repo`.
2. Send `POST /github_webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or an arbitrary value), and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`), regardless of the header value.
4. `Shipit::Webhooks::Handlers::PushHandler#process` resolves the stack via `Repository.from_github_repo_name("org-b/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues `stack.sync_github`, an action that should only be triggerable by a validly-signed webhook from `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
