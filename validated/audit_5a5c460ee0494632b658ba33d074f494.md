### Title
Webhook signature verification is scoped to the wrong organization, letting one onboarded GitHub org forge push/status events for another org's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) used to validate an inbound webhook using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  However, the handlers that actually act on the payload (`PushHandler`, `StatusHandler`, etc.) determine the target `Repository`/`Stack` from a *different* field of the same attacker-suppliable JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing ties these two fields together, so the organization whose secret authenticated the request is not verified to be the owner of the repository that is actually written to.

### Finding Description
Shipit supports hosting multiple GitHub organizations in one instance, each with its own `webhook_secret`, selected via `Shipit.github(organization:)`. [4](#0-3) [5](#0-4)  `WebhooksController#verify_signature` picks the app/secret to validate against solely from `repository_owner` (`repository.owner.login`, or `organization.login` as fallback), extracted from the raw, attacker-controlled JSON body itself: [6](#0-5) 

Once the signature check passes, the entire `params` hash is handed unmodified to the registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [7](#0-6)  The base `Handler` class resolves which `Repository`/`Stack` to act on using a completely separate JSON path, `repository.full_name`: [3](#0-2) 

`PushHandler` uses this to look up stacks and trigger `stack.sync_github(expected_head_sha: params.after)` on every matching stack, [8](#0-7)  and `StatusHandler` uses `Commit.where(sha: params.sha)` (a global, cross-repository lookup) to attach an attacker-controlled CI status (`state`, `context`, `description`, `target_url`) to any matching commit. [9](#0-8) 

Because `repository.owner.login` (used only for picking the HMAC secret) and `repository.full_name` (used to pick the actual write target) are independent fields inside the same JSON body, an attacker who legitimately administers one Shipit-onboarded GitHub organization ("OrgA") — and therefore knows OrgA's own `webhook_secret`, which they themselves configured when wiring up their org's webhook to this Shipit instance — can forge a POST to `/github/webhooks` where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` selects OrgA's `GitHubApp` and the attacker-computed HMAC using OrgA's own secret validates), while
- `repository.full_name` = `"OrgB/victim-repo"` (a completely different, unrelated organization/repository also hosted by the same Shipit instance).

The signature check only proves "this body was signed by *some* known org's secret"; it never proves that the repository named inside the body belongs to that org. This is exactly the "organization that authenticated versus the repository that is written" binding break: `verified_org(payload) != owner(repository_full_name(payload))`, and the engine never checks that equality.

### Impact Explanation
This qualifies as High impact per the listed criteria: it is an authentication-boundary bypass that lets a request authenticated for one repository/org act on another repository's state without any legitimate relationship to it — effectively unauthenticated read/write of another organization's stack and commit state:
- Via `PushHandler`, an attacker can force `GithubSyncJob` on OrgB's stacks with an attacker-chosen `expected_head_sha`, spoofing what Shipit considers the current head of a victim branch. [8](#0-7) 
- Via `StatusHandler`, an attacker can inject arbitrary, forged CI/status entries (`state`, `context`, etc.) onto any commit across any onboarded repository, since `Commit.where(sha: ...)` is not scoped by the authenticating organization at all. [9](#0-8)  Because `shipit.yml`'s `ci.require` gating and merge-queue/continuous-delivery logic consume these `Status` records to decide whether commits are deployable/mergeable, forged statuses from an unrelated org can influence deploy/merge gating for a victim repository.

This directly maps to the High-impact bucket "unauthenticated read of stack state, task streams or deploy output" (and arguably contributes toward "unauthorized deploy" if forged green CI statuses are consumed downstream by continuous deployment).

### Likelihood Explanation
Requires only that the Shipit instance host more than one GitHub organization (an explicitly documented and supported configuration, see `docs/setup.md`'s "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), and that the attacker is a legitimate admin of one of those organizations (able to know/configure that org's own `webhook_secret` — no privileged Shipit credentials, no `ApiClient` token, and no access to the victim org are required). Crafting the HMAC and POSTing to the public `/github/webhooks` endpoint requires only standard HTTP tooling.

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, cross-check that the organization used to select/verify the signing secret matches the owner of `repository.full_name` (and `organization.login` where relevant) before dispatching to handlers — e.g. reject the webhook if `payload.dig('repository', 'owner', 'login')` (or its fallback) does not case-insensitively match the owner segment of `payload.dig('repository', 'full_name')`. More robustly, resolve the target `Repository`/`Stack` first, derive its owning organization from Shipit's own configuration/db records (not from attacker-supplied fields), and verify the signature against that resolved organization's secret.

### Proof of Concept
1. Deploy Shipit with the multi-org schema, e.g. `OrgA` and `OrgB` both configured with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an admin of `OrgA` (which the attacker legitimately controls, including its Shipit webhook secret), build a push-event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and set `X-Github-Event: push`.
4. POST to `/github/webhooks`. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's `GitHubApp`, and the signature validates successfully using the attacker-known OrgA secret. [1](#0-0) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves the repository via `payload.dig('repository', 'full_name')` = `"OrgB/victim-repo"`, entirely independent of the org used for authentication. [3](#0-2)  `sync_github(expected_head_sha: "deadbeef...")` is invoked on OrgB's stacks despite the request never being authenticated by OrgB's secret. [8](#0-7)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
```
