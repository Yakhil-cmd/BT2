### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits by matching `sha` globally across the entire `commits` table, without ever checking that the `sha` belongs to a commit under the `repository` (and therefore the GitHub organization) whose webhook signature was actually verified. This breaks the intended binding: *the organization/repository that authenticated the webhook* must equal *the repository whose commit record is written*.

### Finding Description
Webhook signature verification is performed by `WebhooksController#verify_signature`, which selects the GitHub App config to check against based on `repository_owner`, itself read from the still-unverified JSON body (`params.dig('repository', 'owner', 'login')`), and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

This means the signature is verified against the `webhook_secret` configured for **whatever organization the attacker names in the payload** — which, in a multi-org Shipit deployment (`Shipit.github(organization:)` supports per-org secrets, see `docs/setup.md` and `lib/shipit/github_app.rb`), can be an organization the attacker legitimately administers and for which they know/control the `webhook_secret`. [3](#0-2) [4](#0-3) 

Once the signature check passes (using the attacker's own org's secret), `WebhooksController#create` dispatches the parsed payload to the relevant `Handler` for the event type. [5](#0-4) 

For the `status` event, `Shipit::Webhooks::Handlers::StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [6](#0-5) 

This lookup is **not scoped to the repository named in the payload** at all — unlike the base `Handler` class, which does provide a `repository_name`/`stacks` scoping helper (`payload.dig('repository', 'full_name')` → `Repository.from_github_repo_name(...).stacks`), `StatusHandler` never calls into that helper; it queries `Commit` directly by `sha` across the whole installation. [7](#0-6) 

Because git SHAs from other tracked repositories/stacks are commonly observable (via public GitHub commit history, prior deploy pages, hooks, etc.), an attacker who administers one organization/repo connected to this same Shipit instance can:
1. Set up a legitimate webhook for their own org/repo with a `webhook_secret` they control.
2. Craft and correctly HMAC-sign a `status` event payload where `sha` is a known commit SHA belonging to a **different, victim** repository/stack tracked by the same Shipit instance, and `state` is `success`.
3. Send it to the shared `WebhooksController#create` endpoint. Signature verification succeeds because it is keyed off the attacker-controlled org.
4. `StatusHandler` finds the victim's `Commit` record purely by SHA match and writes a forged "success" status to it via `create_status_from_github!`.

### Impact Explanation
Writing a forged "success" status onto a victim's commit can flip deployability/CI-gating logic and, for stacks with `continuous_deployment` enabled, can influence automatic deploy triggering pathways in `Commit`/`Stack`/`Deploy` (status transitions are consumed by `ProcessMergeRequestsJob` and CD checks, per test coverage such as `test/models/commits_test.rb`). This is a cross-repository write into another tenant's data (an unauthorized modification of build/deploy state for a repository the attacker was never granted access to), satisfying the "cross-repository writes" / "unauthorized deploy" criteria for High/Critical impact, since a single Shipit instance can host stacks for many unrelated GitHub orgs/repos and the attacker only needs write access (as an org admin configuring their own webhook) to one of them.

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit deployment tracking multiple orgs/repos (the documented and supported "multiple Github applications for different Github organizations" configuration), (b) attacker control over one org's webhook configuration/secret (an ordinary, unprivileged-with-respect-to-Shipit GitHub org admin capability, not a Shipit credential), and (c) knowledge of a target commit SHA in another tracked repository (generally discoverable). No Shipit session, API token, or GitHub App private key is needed — only the ability to fire a correctly-signed webhook for one's own org.

### Recommendation
`StatusHandler#process` (and any other handler that queries records without going through the `Handler#stacks`/`repository_name` scoping) must filter commits by the repository named in the payload before acting on `sha`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, ensuring the repository that authenticated the webhook is the same repository whose data is mutated. More generally, `WebhooksController#verify_signature` should not let an attacker pick an arbitrary organization's key by supplying an unverified `repository.owner.login`/`organization.login`; associate/verify that the authenticated org actually owns the repository referenced by the event payload before any handler runs.

### Proof of Concept
1. Attacker administers `attacker-org/attacker-repo`, connected to the shared Shipit instance, and configures (or already knows) its `webhook_secret`.
2. Attacker learns a commit SHA `S` that Shipit tracks for `victim-org/victim-repo` (e.g., a public commit SHA visible on GitHub).
3. Attacker builds a `status` webhook JSON body: `{"sha": "S", "state": "success", "context": "ci/forced", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}}` and computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker_webhook_secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the victim's commit (unscoped by repository), and calls `create_status_from_github!`, writing a forged success status onto the victim stack's commit — despite the attacker never having any access to `victim-org/victim-repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
