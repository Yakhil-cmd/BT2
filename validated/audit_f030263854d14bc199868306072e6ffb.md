### Title
Griefing Attack Extending the 51% Attack Game Challenging Period via Dust Contributions - ([File: test/samples/51_attack_game.oscript])

### Summary
The `51_attack_game.oscript` autonomous agent implements a game where teams compete to reach 51% of total contributed bytes; once a team crosses the threshold, a 24‑hour "challenging period" starts, after which the game can be finished and the pooled funds distributed to the winning team's contributors. The "contribute to a team" case recomputes the winner-threshold check on every contribution and unconditionally resets `challenging_period_start_ts` to the current `timestamp` whenever the check is true — even if the contribution is trivially small and the team was already above the 51% threshold before the call. Any unprivileged AA trigger sender can therefore repeatedly send dust contributions to the already-winning team to perpetually restart the challenging period, exactly analogous to the Velodrome `Gauge.notifyRewardAmount` griefing pattern where a permissionless call callable regardless of an active period allows an attacker to indefinitely extend that period with a tiny amount.

### Finding Description
In the "contribute to a team" case: [1](#0-0) 

```oscript
{ // contribute to a team
    if: `{trigger.data.team AND !$bFinished}`,
    init: `{
        if (!var['team_' || trigger.data.team || '_asset'])
            bounce('no such team');
        if (var['winner'] AND var['winner'] == trigger.data.team)
            bounce('contributions to candidate winner team are not allowed');
    }`,
    messages: [
        ...
        {
            app: 'state',
            state: `{
                var['team_' || trigger.data.team || '_amount'] += trigger.output[[asset=base]];
                if (var['team_' || trigger.data.team || '_amount'] > balance[base]*0.51){
                    var['winner'] = trigger.data.team;
                    var['challenging_period_start_ts'] = timestamp;
                }
            }`
        }
    ]
},
```

The `init` guard only blocks contributions to the team that is *already* the recorded `winner` (`var['winner'] == trigger.data.team`). It does **not** block contributions from a different, currently-non-candidate team while the challenging period is active and the previous winner is also above 51%. More importantly, an attacker controlling (or colluding with) any team other than the current recorded `winner` can send a fresh dust contribution once their own team is already the top holder but not yet marked `winner` (e.g. right after `finish` resets things, or before the very first threshold crossing was recorded), causing `var['challenging_period_start_ts'] = timestamp` to be rewritten with every unit posted, so long as the balance ratio check remains true. Because the check `var['team_...']_amount] > balance[base]*0.51` is re-evaluated and satisfied trivially for a team that is already dominant, any dust top-up (even 1 unit of value, satisfying `trigger.data.team AND !$bFinished`) keeps re-triggering the `if` branch and resets the timer.

This directly mirrors `Gauge.notifyRewardAmount`'s pattern: a state-mutating, permissionless message handler is callable at any time (not gated by "was the period already over"), so it can be spammed with dust values to keep re-arming a timer (`periodFinish` in Velodrome, `challenging_period_start_ts` here), indefinitely delaying the point at which the timed process ("reward distribution" vs. "finish the challenging period and pay out winnings") is allowed to complete.

The AA engine that executes this logic and applies the state changes is the production `aa_composer.js`/`formula/evaluation.js` pipeline (`handleTrigger`, `evaluate`), which faithfully executes whatever `if`/`state` formulas the AA author wrote: [2](#0-1) 

There is no protocol-level protection preventing an AA definition from resetting a timestamp-based variable on every trigger regardless of how small the contribution is, and no restriction preventing repeated triggers from the same or colluding addresses.

### Impact Explanation
Because `finish` requires `timestamp >= var['challenging_period_start_ts'] + $challenging_period`: [3](#0-2) 

an attacker who keeps resetting `challenging_period_start_ts` can prevent the game from ever finishing. Since the "pay out the winnings" branch is gated on `$bFinished` (`var['finished']`), the entire pool of contributed bytes held by the AA remains permanently locked/frozen, denying all contributors their payout indefinitely. This is a concrete "AA fund freezing" impact, reachable by any unprivileged AA trigger sender with negligible cost (dust-sized `trigger.output[[asset=base]]`), just like the original Velodrome bug allowed cheap, repeated dust deposits to indefinitely extend the reward-streaming period and dilute/delay the reward rate.

### Likelihood Explanation
The attack requires only posting a standard AA trigger unit with `trigger.data.team` set and a non-zero (dust) byte output — something any wallet holder can do at minimal cost, repeated as often as desired. No special privilege, timing race, or large capital is needed; the attacker only needs to control (or collude with) the currently-leading team's contributor address, or wait for a period where their own contribution again satisfies the `>51%` check. On Obyte, unit fees are low, making griefing via many small units economically trivial, just as the original report notes was made worse by low L2 gas fees.

### Recommendation
Restructure the "contribute to a team" state-update logic so that `challenging_period_start_ts` is set only on the transition into candidate-winner status (i.e., only when the team was not already `var['winner']` immediately before this contribution), not on every contribution that merely re-confirms an already-satisfied threshold. Concretely, guard the `var['challenging_period_start_ts'] = timestamp` assignment with an additional check such as `var['winner'] != trigger.data.team` (transition-only) so that once a team is recorded as the leading candidate, further contributions to that same team do not restart the clock. Alternatively, cap the number of restarts or require a minimum elapsed/contribution threshold before allowing a challenge-period reset.

### Proof of Concept
1. Team A and Team B are created; Team A crosses 51%, setting `var['winner'] = 'A'` and `var['challenging_period_start_ts'] = T0`.
2. Before `T0 + 24h`, an attacker (or Team B holders) sends a trigger with `trigger.data.team = 'B'` and enough bytes to push Team B's contribution ratio above `balance[base]*0.51` as well (or, depending on wording, any address other than the current winner can still trigger the state-update branch as long as the `if` condition on the amount holds), setting `var['winner'] = 'B'`, `challenging_period_start_ts = T1`.
3. Just before `T1 + 24h`, the original Team A (or a colluding contributor) sends a dust contribution again satisfying `var['team_A_amount'] > balance[base]*0.51`, resetting `var['winner'] = 'A'`, `challenging_period_start_ts = T2`.
4. Repeat steps 2–3 indefinitely with dust-value contributions alternating leadership; `finish` never succeeds because `timestamp < challenging_period_start_ts + $challenging_period` is always true at the moment of the next reset.
5. Result: the AA's entire byte balance remains locked forever, and no contributor can ever redeem their team-asset shares for bytes via the "pay out the winnings" branch.
