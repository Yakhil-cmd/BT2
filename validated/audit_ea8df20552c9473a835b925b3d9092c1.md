### Title
Asset Definer Can Unilaterally Freeze Attested-Asset Holders' Funds by Replacing the Attestor List Without Timelock, Multi-Sig, or Event Transparency - ([File: validation.js])

### Summary
For assets created with `spender_attested: true`, the asset `definer_address` has sole, unrestricted, and un-timelocked control over who is a valid "attestor" for that asset via the `asset_attestors` message. `validateAttestorListUpdate` only checks that the author is the current definer — there is no multi-signature requirement, no timelock, and no separate transparency mechanism, mirroring the `whitelistGuardian`/`vetoGuardian` design flaw described in the reference report (single privileged role can change access-control state unilaterally and opaquely).

### Finding Description
When an asset has `spender_attested: true`, every payment that spends or receives that asset must involve addresses that are currently "attested" according to the *latest* attestor list for that asset: [1](#0-0) [2](#0-1) 

The only check performed when the definer publishes a new `asset_attestors` list is that the message is single-authored and comes from the current `definer_address`: [3](#0-2) [4](#0-3) 

There is no requirement for the definer's replacement list to include the previously-trusted attestors, no cool-down/timelock before the new list becomes effective, and no protection for holders who already hold coins of the asset based on attestations issued under the old list. Once the `asset_attestors` unit is stable, payment validation immediately switches to using only the new list:
- input-owner attestation check: [5](#0-4) 
- issuer attestation check: [6](#0-5) 
- output-address attestation check: [7](#0-6) 

Because attestation status is derived from `attestations` messages issued by whichever addresses are in the *current* attestor list (`filterAttestedAddresses` cross-references `attestor_address IN(?)` against the live `arrAttestorAddresses`), a definer can:
1. Publish a new `asset_attestors` list dropping all previously-trusted attestors and/or naming attestors who will never re-attest existing legitimate holders.
2. This instantly and permanently prevents every existing holder whose attestation came from the removed attestors from spending, issuing to, or receiving the asset — even though their attestation was valid when they acquired the funds.

This is a direct analog of the audited issue: a privileged "guardian" address (`definer_address` acting as an attestor-list guardian) has unchecked, un-timelocked, non-multisig, non-event-logged power over spending eligibility for an entire asset class.

### Impact Explanation
This causes freezing of already-issued asset balances: legitimate holders lose the ability to move or use funds they legitimately acquired, with no on-chain recourse, once the definer swaps the attestor list. Since `spender_attested` assets are explicitly designed to gate transfer eligibility on attestation, and the mechanism to update that eligibility is entirely centralized in one address with no delay or oversight, a compromised or malicious definer key can freeze arbitrary amounts of value across all holders of the asset. This matches the "AA fund loss or freezing" impact class.

### Likelihood Explanation
Any asset issuer choosing `spender_attested: true` (a documented, standard oscript/asset feature, also usable from AAs per `aa_validation.js`) already holds the `definer_address` key needed to trigger this at will — no additional compromise, coordination, or special access is required beyond normal key custody of the definer. The action is a single valid `asset_attestors` unit.

### Recommendation
- Require a timelock/grace period between publishing a new attestor list and its taking effect, so holders attested under the old list have a chance to act.
- Optionally require attestor-list changes to be co-signed (e.g., via `cosigned_by_definer`-style additional authorization) or allow holders/attestors themselves to contest a removal.
- Emit clearer, queryable state (already partially done via the `asset_attestors` table) but add validation-layer warnings/limits, e.g., disallow completely emptying the attestor set or disallow near-immediate full replacement without a minimum list overlap.

### Proof of Concept
1. Issuer creates asset `A` with `spender_attested: true` and attestor list `[X]`.
2. Attestor `X` attests holder `H`; `H` receives/holds asset `A` based on that attestation (`validation.js:2506-2507`, `2630-2642`).
3. Definer publishes `asset_attestors` message for asset `A` with new list `[Y]`, where `Y` will never attest `H` (validated only by `validateAttestorListUpdate`, `validation.js:2829-2848`).
4. Once stable, `storage.readAsset`/`addAttestorsIfNecessary` (`storage.js:1917-1946`) resolves `arrAttestorAddresses = [Y]`; `filterAttestedAddresses` (`storage.js:1960-1974`) no longer returns `H` as attested.
5. `H`'s subsequent payment attempting to spend previously-held coins of asset `A` fails validation ("owner address is not attested", `validation.js:2506-2507`), permanently freezing `H`'s funds with no path to recovery other than the definer's discretion.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
