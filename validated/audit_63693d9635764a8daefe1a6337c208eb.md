### Title
Permanent market freeze via RAY value overflow in `scaled_to_original` during interest accrual - (File: contracts/pool/src/cache/scale.rs)

### Summary
The analog of CVE-2017-9752 (crafted input → buffer overflow → crash) in this codebase is an `i128` value overflow during accrual: multiplying total scaled debt/supply by the interest index exceeds `i128::MAX` before the `MAX_BORROW_INDEX_RAY` cap can engage. Because every controller/pool verb accrues the market first, once the market crosses this threshold it is permanently bricked — supply, withdraw, borrow, repay, liquidate, and `update_indexes` all revert with `MathOverflow`. The repository's own regression test proves the freeze.

### Finding Description
`Cache::calculate_utilization` and the accrual path unscale `borrowed`/`supplied` RAY shares by multiplying them with the index via `scaled_to_original` (`contracts/pool/src/cache/scale.rs:23-26`), which delegates to `Ray::mul` → `mul_div_*` in `common/src/math/fp_core.rs`. These helpers panic with `GenericError::MathOverflow` when the product/quotient does not fit `i128` (fp_core.rs:108-118, 148-159).

The borrow index is capped at `MAX_BORROW_INDEX_RAY` in `update_borrow_index` (`common/src/rates/index.rs:13-19`), but the cap applies to the *index*, not to the *value* `borrowed * index`. A market with a sufficiently large scaled principal hits the `i128` value ceiling while the index is still well below its cap. `update_supply_index` uses `mul_div_floor_saturating` and headroom clamping (index.rs:40-44, 94-99), but `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` unconditionally (index.rs:80-83), which panics.

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`) demonstrates exactly this: after sustained ~98% utilization on the steep end of the interest curve, `update_indexes` fails with `MATH_OVERFLOW`, `borrow_index < MAX_BORROW_INDEX_RAY` (the cap never engages), and subsequently `withdraw` and `repay` both fail with `MATH_OVERFLOW` because every verb accrues first — "the market is frozen: no repay, no withdraw, no liquidation".

### Impact Explanation
Permanent freezing of funds. Once `borrowed * borrow_index` (or `supplied * supply_index`) crosses `i128::MAX`, accrual panics on every subsequent invocation for that market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and keepers cannot even call `update_indexes`. All assets in that market book are locked forever; downstream this also blocks `clean_bad_debt`/`recapitalize`, so bad debt in that market cannot be resolved — protocol insolvency on top of the freeze.

### Likelihood Explanation
Medium-low probability, high impact. The trigger is reachable entirely by unprivileged addresses using `supply`/`borrow` on the controller — no governance action is needed beyond the initial listing. However, it requires (a) a listed asset with enough decimals and notional supply to make the RAY-scaled value near the `i128` ceiling (the test uses `BILLION * 10^18` base units, which is realistic for high-decimal or low-unit-price tokens), and (b) sustained high utilization so the index grows the remaining distance — the test reaches the cliff within ~40 simulated years at 98% utilization on the XLM curve, faster for larger principals. An attacker with whale-scale capital can deliberately accelerate accrual by borrowing to the steep utilization segment, and supply-side donations ("direct token transfers to the pool") are in scope for inflating the denominator/numerator. The decay of the condition is one-directional: once crossed, there is no remediation short of a contract upgrade, so the expected value of the attack grows over the protocol's lifetime.

### Recommendation
Make accrual saturate instead of panic at the value ceiling:

- In `update_borrow_index`, cap the index such that `borrowed * index` cannot overflow — e.g., clamp `new_index ≤ MAX_BORROW_INDEX_RAY.min(i128::MAX-scaled bound for current borrowed)` — or use `mul_div_floor_saturating`/`I256`-widened computation in `scaled_to_original` and `calculate_supplier_rewards`, clamping accrued value at `i128::MAX`.
- Ensure `calculate_supplier_rewards` (index.rs:80-83) and `Cache::calculate_utilization` (scale.rs:23-26) degrade gracefully (saturate accrued interest / utilization at bounds) rather than trapping, so repay/withdraw/liquidate keep functioning even in the degenerate index regime.
- Add an explicit invariant: `borrowed * MAX_BORROW_INDEX_RAY` and `supplied * MAX_SUPPLY_INDEX_RAY` must fit `i128` at market listing time (reject or cap listings whose scaled principal would violate this), since index caps alone do not prevent the value overflow.

### Proof of Concept
Already encoded in the repository's own test suite — `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`:

```rust
let principal = BILLION * 10i128.pow(18);          // unprivileged supply
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                   // 98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance time; update_indexes eventually fails with MATH_OVERFLOW
// while borrow_index < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `controller.supply`/`borrow` grow `borrowed`/`supplied` scaled shares → `pool` accrual calls `scaled_to_original` (`contracts/pool/src/cache/scale.rs:23`) → `Ray::mul` → `mul_div_floor`/`mul_div_half_up` (`common/src/math/fp_core.rs:148-159`, `108-118`) → `MathOverflow` panic on every subsequent touch of the market, permanently.
