### Title
Unauthenticated P2P Staking Info Injection via Missing Validation in `DeliverStakingInfos` Allows Reward/Treasury Address Poisoning During Fast/Snap Sync — (`datasync/downloader/queue.go`)

### Summary

During FastSync or SnapSync with `WeightedRandom` proposer policy (pre-Kaia-fork), a malicious P2P peer can deliver a `P2PStakingInfo` with attacker-controlled `CouncilRewardAddrs`, `KEFAddr`, and `KIFAddr` for any staking-interval boundary block whose header has an empty body and empty receipts. Because the body and receipt pending bits are never set for such a header, clearing only the `stakingInfoType` bit via `SetStakingInfoDone()` immediately satisfies `AllDone()`. The result is committed to the DB with no content validation, poisoning the staking info used for reward and treasury distribution.

### Finding Description

In `newFetchResult`, the `pending` bitmask is initialized as follows:

- `bodyType` bit: set only if `!header.EmptyBody()`
- `receiptType` bit: set only if `(fastSync||snapSync) && !header.EmptyReceipts()`
- `stakingInfoType` bit: set if `(fastSync||snapSync) && WeightedRandom && num%stakingUpdateInterval==0 && !isKaiaFork`

For a header where `EmptyBody()=true` and `EmptyReceipts()=true` at a staking-interval boundary, `pending` starts with only the `stakingInfoType` bit set. After `SetStakingInfoDone()` is called, `pending` becomes 0 and `AllDone()` returns `true`.

The critical gap is in `DeliverStakingInfos`:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
```

No validation is performed — the peer-supplied `P2PStakingInfo` is accepted unconditionally and stored into `fetchResult.StakingInfo`. The `reconstruct` closure then calls `SetStakingInfoDone()`, making the result immediately complete. The downstream `commitFastSyncData` path then writes this to the DB under the staking info key.

### Impact Explanation

The staking info stored at interval boundaries is used by the node for:
- **Validator reward routing** (`CouncilRewardAddrs`): block rewards are sent to these addresses
- **Treasury fund routing** (`KEFAddr`, `KIFAddr`): KEF and KIF treasury distributions go to these addresses

An attacker who poisons these addresses during fast sync causes the synced node to route block rewards and treasury funds to attacker-controlled addresses for the affected staking interval. This is a direct unauthorized redirection of KAIA token value — block rewards and treasury distributions — satisfying the required impact gate.

### Likelihood Explanation

- Requires FastSync or SnapSync mode (common for new nodes joining the network)
- Requires `WeightedRandom` proposer policy (the default Kaia mainnet configuration)
- Requires pre-Kaia-fork blocks (limits the window, but historical sync of pre-fork blocks is common)
- Attacker only needs to be a connected P2P peer — a permissionless, public network entrypoint
- Empty-body, empty-receipt blocks at staking interval boundaries are normal (e.g., blocks with no transactions)

### Recommendation

Replace the TODO stub in `DeliverStakingInfos` with actual validation. The delivered `P2PStakingInfo` should be verified against the state root committed in the header: re-derive the staking info from the synced state trie and compare it against the peer-supplied data, or at minimum verify that `BlockNum` matches the expected source block number for the interval. Until this is implemented, staking info should not be accepted from untrusted peers without cryptographic proof of correctness.

### Proof of Concept

1. Construct a `types.Header` with `TxHash = types.EmptyTxsHash`, `ReceiptHash = types.EmptyReceiptsHash`, and `Number` set to a multiple of `stakingUpdateInterval` (e.g., 86400).
2. Call `newFetchResult(header, FastSync, uint64(istanbul.WeightedRandom), 86400, false)` — only `stakingInfoType` bit is set in `pending`.
3. Construct a `P2PStakingInfo` with attacker-controlled `CouncilRewardAddrs = [attackerAddr]`, `KEFAddr = attackerAddr`, `KIFAddr = attackerAddr`.
4. Call `DeliverStakingInfos` with this info — `validate` returns nil, `reconstruct` stores the info and calls `SetStakingInfoDone()`.
5. Assert `fetchResult.AllDone() == true` — passes immediately.
6. Assert `fetchResult.StakingInfo.CouncilRewardAddrs[0] == attackerAddr` — passes.
7. The result is eligible for `commitFastSyncData`, which writes the poisoned staking info to DB.

func newFetchResult(header *types.Header, mode SyncMode, proposerPolicy uint64, stakingUpdateInterval uint64, isKaiaFork bool) *fetchResult {
	var (
		fastSync = mode == FastSync
		snapSync = mode == SnapSync
	)
	item := &fetchResult{
		Header: header,
	}
	if !header.EmptyBody() {
		item.pending |= (1 << bodyType)
	}
	if (fastSync || snapSync) && !header.EmptyReceipts() {
		item.pending |= (1 << receiptType)
	}
	if (fastSync || snapSync) && proposerPolicy == uint64(istanbul.WeightedRandom) &&
		(header.Number.Uint64()%stakingUpdateInterval == 0 && !isKaiaFork) {
		item.pending |= (1 << stakingInfoType)
	}
	return item
