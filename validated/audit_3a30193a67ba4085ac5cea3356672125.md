### Title
`StatusHandler#process` mutates commits/stacks across repositories by matching commit `sha` globally, without the repository-scoping guard used by `CheckSuiteHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The base `Handler` class provides a `stacks` helper that scopes any webhook to the stack(s) belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and `CheckSuiteHandler#process` uses exactly this helper before touching any commit. `StatusHandler#process`, however, bypasses this helper entirely and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, matching commits purely by SHA across every stack/repository in the installation, so a status webhook whose signature is validly signed for the attacker's own repository can create a `Status` on a commit belonging to a completely different (victim) stack.

### Finding Description
Binding claimed broken: `stacks` (i.e. `Repository.from_github_repo_name(payload.dig('repository','full_name')).stacks`) used by `CheckSuiteHandler#process` at [1](#0-0)  == the scoping that `StatusHandler#process` applies before mutating a commit.

Tracing confirms this is broken:
- Base `Handler#stacks` derives the scope strictly from the payload's own repository: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, where `repository_name` is `payload.dig('repository', 'full_name')`. [2](#0-1) 
- `CheckSuiteHandler#process` correctly uses this scoped `stacks` relation, then further filters by `commits.where(sha: ...)` within that stack, so a check-suite payload can never touch a commit outside the stack tied to the payload's own repository. [1](#0-0) 
- `StatusHandler#process` does not call `stacks` (or `Repository.from_github_repo_name`) at all. It queries `Commit.where(sha: params.sha)` unscoped by repository/stack and immediately calls `commit.create_status_from_github!(params)` on every match. [3](#0-2) 
- `create_status_from_github!` unconditionally creates a `Status` row tied to `commit.stack_id`, and `Status` creation has side effects: it enables CI on the stack and schedules continuous delivery. [4](#0-3) [5](#0-4) 

Attack path: signature verification (`WebhooksController#verify_signature`) only checks that the payload is signed by the GitHub App/webhook secret associated with `repository_owner` derived from the payload itself (`params.dig('repository','owner','login')`), i.e. it proves the sender controls *some* repo/owner, not that the sender controls the repo whose commit is being mutated. [6](#0-5)  Once past that check, `Shipit::Webhooks.for_event('status')` dispatches straight to `StatusHandler`, which has no repository check of its own. [7](#0-6) 

Because git commit SHAs are content-addressed, any fork of a public victim repository contains commits with identical SHAs to the upstream repository. An attacker who forks the victim's repository (or otherwise controls a GitHub repo whose commit history overlaps with the victim's, e.g., via a shared commit) can register/trigger a `status` webhook on their own fork/repo (signed correctly for that repo's owner) carrying `sha` equal to a real victim commit and `state: success`. Because `Commit.where(sha:)` matches globally by SHA and `stack_id` is derived from the pre-existing `Commit` row (belonging to the victim's stack), this creates a legitimate-looking successful `Status` on the victim's commit, in the victim's stack, potentially satisfying required-CI gating and enabling merges or deploys the attacker does not control.

### Impact Explanation
An attacker with no relationship to the victim's Shipit stack, repository, or team can write a `Status` (CI check result) onto an arbitrary victim commit in an arbitrary stack merely by owning a repo that shares a commit SHA with the victim (trivially achieved via a public fork). This is a cross-tenant write: a payload authenticated for repository A mutates stack/commit state for repository B, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It can flip a commit's CI state to `success`, unblocking downstream automation (e.g., auto-merge, deploy gating) tied to `Commit#state`/`deployable_status`. This is repeatable against any commit SHA that exists in a repository the attacker controls or can otherwise learn/replicate (i.e., any public repo Shipit tracks and that has been forked).

### Likelihood Explanation
Preconditions are low-cost for the attacker: they need (1) a GitHub repository/org they control that Shipit's `verify_signature` accepts (i.e., a repository under a GitHub owner for which `Shipit.github(organization: repository_owner)` resolves — typically requires the app to be installed/known for that owner) and (2) knowledge of a target commit SHA in a victim stack, easily obtained by forking the victim's public repository (identical SHAs) or observing PR/commit metadata. No Shipit session, API token, or team membership is required — only the ability to send a correctly-signed webhook for a repo the attacker legitimately owns. This is fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks resolved from the payload's own repository, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a `status` webhook can only mutate commits belonging to the stack(s) tied to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, closing the cross-repository mutation path.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, or extending `test/controllers/webhooks_controller_test.rb`):

1. Setup: create `stack_a` (repo `owner-a/repo`) and `stack_b` (repo `owner-b/repo`), each with a `Commit` sharing the same `sha` value (simulating a fork with identical commit history).
2. Send a `check_suite` webhook whose `repository.full_name` is `owner-b/repo` and `head_sha` equal to that shared sha, with `head_branch` matching only `stack_a`'s branch (i.e., cross-repo). Assert **no** `RefreshCheckRunsJob` is enqueued for `stack_a`'s commit — proving `CheckSuiteHandler` correctly rejects/ignores cross-repository payloads via `stacks`.
3. Send a `status` webhook with `repository.full_name` set to `owner-b/repo` (attacker-owned, correctly signed) but `sha` equal to `stack_a`'s (victim) commit sha, `state: 'success'`.
   ```ruby
   assert_difference -> { stack_a_commit.statuses.count }, 1 do
     post :create, body: status_payload_for_owner_b_repo_with_victim_sha, as: :json
   end
   assert_equal 'success', stack_a_commit.reload.state
   ```
4. The assertion in step 3 succeeding (a `Status` created on `stack_a`'s commit from a payload signed for `owner-b/repo`) while step 2's equivalent check-suite payload is correctly ignored demonstrates the divergence: `CheckSuiteHandler` enforces repository scoping via `stacks`, `StatusHandler` does not, allowing cross-repository mutation of victim commit/stack state.
