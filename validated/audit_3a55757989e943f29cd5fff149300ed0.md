## Title
`countVotes()` System Variable Vote Counting Can Permanently Fail (DoS on Consensus) Once the Distinct Voter-Address Set Grows Too Large - (File: `main_chain.js`)

### Summary
`countVotes()` in `main_chain.js` builds an unbounded, ever-growing list of voter addresses from the `system_votes` table and inlines it directly into a raw SQL string. Because any unprivileged unit poster can permanently add a brand-new address to `system_votes` simply by casting a `system_vote`, the address set only grows over time and is never pruned. Once it is large enough to exceed the underlying database's maximum SQL statement/packet length, the query throws, and — because `countVotes()` is executed deterministically by every full node as a mandatory step of `markMcIndexStable()` — the failure reproduces on every node forever, blocking `system_vote_count` processing (and, transitively, MC stabilization for that MCI) network-wide. This mirrors the reported `getUsers()` pattern: an attacker-growable array is later consumed in a way that reverts once it becomes "too big," and the failure is permanent.

### Finding Description
Any address can cast a `system_vote` message; validation only checks payload shape/values, not the size of the historical voter set: [1](#0-0) 

When a `system_vote` unit becomes stable, `saveSystemVote()` unconditionally `INSERT`s a new row into `system_votes` for every author address of the unit, for every subject voted on — with no deletion of old rows and no cap on distinct addresses: [2](#0-1) 

`countVotes()` — invoked as a required step whenever a `system_vote_count` message stabilizes — reads *all* distinct addresses that have ever voted for the subject and joins them into a raw, unparameterized SQL string: [3](#0-2) [4](#0-3) 

This string is then embedded directly into the `outputs.address IN(${strAddresses})` clause of a raw SQL query, with no chunking or pagination: [5](#0-4) 

`countVotes()` is called synchronously as part of the mandatory stabilization pipeline for every stable MCI containing a `system_vote_count`: [6](#0-5) 

Since posting a `system_vote` from a fresh address is cheap (any newly-created address can vote; balance is irrelevant to being counted in `system_votes`, only to being weighted later), an attacker can continually create new addresses and cast votes from them (subject to `MAX_AUTHORS_PER_UNIT` per unit, but repeatable across many units) to make the `system_votes` distinct-address set grow without bound over time. Because this table is never pruned, the size only increases monotonically. Once the generated SQL statement exceeds the database engine's maximum statement/packet length (e.g., SQLite's `SQLITE_MAX_SQL_LENGTH`, or MySQL's `max_allowed_packet`), the query throws inside `countVotes()`, which has no surrounding error handling in this code path.

### Impact Explanation
`countVotes()` executes deterministically and identically on every full node as part of `markMcIndexStable()` (via `saveUnstablePayloads` -> the `voteCountSubjects` loop). Once the SQL statement becomes too large to execute, the failure is not specific to one attacker or peer — it reproduces on every honest node processing the same MCI. Because `system_votes` rows are never deleted, this condition, once reached, is permanent: any future `system_vote_count` message (including ones the network may issue to change `op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) will deterministically fail on all nodes, and (depending on how the surrounding transaction/exception propagates) can prevent that MCI's stabilization pipeline from completing, i.e., the network becomes unable to confirm/stabilize new units past that point — a severe network-wide availability failure, matching "a network unable to confirm new units" / "node disagreement on validity or stability."

### Likelihood Explanation
Reaching the point of failure requires accumulating a very large number of distinct addresses in `system_votes` for a subject, which requires posting many low-value units over time (bounded only by transaction fees, which are cheap on ocore). This is not instantaneous but is achievable by a patient, moderately-resourced attacker since there is no protocol-level limit on the number of distinct voter addresses tracked, and no cleanup mechanism exists. The bug class (an ever-growing on-chain-triggered array used unbounded in a size-sensitive operation) is directly analogous to the reported `getUsers()` issue.

### Recommendation
- Do not inline the full distinct-address list into a single raw SQL string; instead join/query `system_votes` directly against `outputs`/`voter_balances` (e.g., `outputs.address IN (SELECT DISTINCT address FROM system_votes WHERE subject=?)`) rather than materializing the JS array into a query string.
- Alternatively, chunk the address list into fixed-size batches for the balance lookup and aggregate results, so no single SQL statement grows unbounded.
- Consider capping/pruning the number of distinct addresses retained per subject in `system_votes` (e.g., only retain addresses observed within the current voting timeframe window) instead of retaining every address that has ever voted.

### Proof of Concept
1. Over an extended period, an attacker repeatedly creates new addresses and, for each, posts a unit containing a valid `system_vote` message (e.g., subject `threshold_size`) — validated and accepted per `validation.js` lines 1844-1859, each insert adding a new distinct row to `system_votes` per `main_chain.js` lines 1619-1636.
2. No mechanism removes old entries from `system_votes`, so the distinct-address count for that subject grows unbounded over time.
3. When a `system_vote_count` message for that subject next stabilizes, `countVotes()` (main_chain.js lines 1737-1773) builds `strAddresses` from the full accumulated address list and embeds it directly in the SQL query.
4. Once the resulting SQL statement exceeds the database's maximum statement length, the query throws on every node executing `markMcIndexStable()`/`saveUnstablePayloads()` for that MCI, deterministically and permanently blocking that vote count (and potentially MCI stabilization) across the network.
