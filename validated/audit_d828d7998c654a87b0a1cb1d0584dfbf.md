### Title
Webhook signature verification is scoped to `repository.owner.login`, but the write target is resolved from the independent `repository.full_name` field, allowing cross-organization forgery in multi-org Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. All downstream webhook handlers, however, resolve the repository to actually mutate using a *different*, independently-controlled JSON field: `payload.dig('repository', 'full_name')`. Because these are two separate keys inside the same attacker-supplied JSON body, an attacker who controls (or is not required to sign for) one organization's webhook secret can point `owner.login` at that organization while pointing `full_name` at a victim repository belonging to a different organization hosted on the same Shipit instance.

### Finding Description
The verification step: [1](#0-0) 

picks the GitHub App/secret purely from `repository_owner`: [2](#0-1) 

This value is entirely attacker-controlled JSON (`repository.owner.login`, with a fallback to `organization.login`). Once `verified` is true, `create` dispatches the raw params to every registered handler for the event: [3](#0-2) 

Every base `Handler` resolves the repository/stacks to operate on from a *different* JSON key, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler`, for example, uses that repository resolution to call `stack.sync_github` on whatever stack matches `full_name`: [5](#0-4) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up any matching repository row, with no cross-check against `owner.login`: [6](#0-5) 

The signature check itself is per-organization and can be a no-op if that organization has no `webhook_secret` configured (documented as optional in `docs/setup.md`): [7](#0-6) 

The engine explicitly supports multiple GitHub Apps/organizations in one instance (evidenced by the dedicated fixture `test/dummy/config/secrets_double_github_app.yml`), so in a multi-tenant deployment, the "organization whose secret authenticated the request" and "the repository whose stacks get written" are not the same binding — breaking the equality `organization authenticated == repository written`.

### Impact Explanation
In a multi-organization Shipit instance, an attacker who is a legitimate, unprivileged administrator of Organization A's own GitHub App integration (or whose organization simply has no `webhook_secret` configured, which `verify_webhook_signature` treats as automatically verified) can forge a webhook body where `repository.owner.login` = "org-a" (satisfies signature check) but `repository.full_name` = "org-b/victim-repo" (used by every handler to select the stacks/repository to mutate). This lets the attacker:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha: ...)` on a victim repository's stack, injecting an attacker-chosen commit SHA into Shipit's view of the victim's git history.
- Similarly abuse `StatusHandler`/`CheckSuiteHandler` to plant fake CI/check statuses on victim commits, which can make otherwise-blocked commits appear deployable, or `PullRequest` handlers to manipulate victim merge-queue state.

This is a cross-organization write into a repository/stack the attacker does not own or have any Shipit permission on, matching the Critical impact category "cross-repository writes."

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly supported per the dedicated `secrets_double_github_app.yml` test fixture) where the attacker administers, or is otherwise able to sign for, at least one of the configured organizations (including trivially any organization configured with no `webhook_secret`, which is documented as an "optional" setting). No Shipit session, `ApiClient` token, or victim-org secret is ever required — only knowledge/control of one organization's own webhook secret (or an unsecured org), which is a normal unprivileged capability of any org onboarded onto the shared instance.

### Recommendation
Bind the organization used to select/verify the webhook signature to the organization used to resolve the target repository. Concretely, `Handler#repository_name`/`stacks` should derive the owner from the same `repository.owner.login` (or otherwise verified) field used in `verify_signature`, and reject events where `repository.full_name`'s owner segment does not match the organization that successfully verified the signature. Alternatively, verify the signature using a global/shared secret comparison enforced against the specific `Repository` record ultimately resolved, rather than against an attacker-suppliable `owner.login` value.

### Proof of Concept
1. Attacker controls (or is the legitimate administrator of) Organization A's own GitHub App installation onboarded onto the shared Shipit instance and knows its `webhook_secret` "secretA" (or Organization A has no `webhook_secret` configured at all).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches Org A's `GitHubApp`, and successfully verifies the signature against secretA (`app/controllers/shipit/webhooks_controller.rb:24-30`, `app/controllers/shipit/webhooks_controller.rb:59-62`).
5. `create` dispatches to `PushHandler`, which resolves `repository_name` from `full_name` = `"org-b/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and invokes `stack.sync_github(expected_head_sha: "deadbeef...")` on Organization B's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), despite the request only ever being authenticated for Organization A.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
