### Title
Cross-repository status write via `StatusHandler#process` allows attackers to force a false-negative CI state and block victim deploys/merges - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by matching `sha` across the entire `commits` table with no repository/stack scoping, then writes a `Status` (state can be `failure`/`error`) onto every matching commit. An attacker who owns a repository containing a commit with the same SHA as one in the victim's stack can send a signed webhook for their own repo (which passes `verify_signature`) with `state: failure`, causing the victim's identical-SHA commit to receive a failing status, which flips `Commit#deployable?` to `false` and suppresses `Stack#schedule_continuous_delivery`/`ContinuousDeliveryJob` enqueue, blocking the victim's legitimate deploy.

### Finding Description
The binding that must hold is: **repository authorizing the status webhook write == repository owning the target `Commit` row**. In code this should mean the commit selection is scoped to the stack tied to the webhook's `repository.full_name`/owner, matching the same repository that `verify_signature` authenticated against.

Instead: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit.where(sha: params.sha)` queries across **all stacks/repositories** in the Shipit installation — `sha` is not a unique key scoped by stack, and no `stack_id`/`repository` filter is applied. `params.state` is attacker-controlled and validated only against `Status::STATES` (`pending`, `success`, `failure`, `error`), not against any repository ownership check.

`WebhooksController#verify_signature` only confirms that the payload was signed for the organization identified by `repository_owner` (from the attacker's own payload) — it authenticates *that the webhook came from a GitHub org the attacker controls/owns*, not that the `sha` inside the payload belongs to a commit in that same org's repositories: [2](#0-1) 

Once `create_status_from_github!` runs on the victim's commit: [3](#0-2) 

it calls `add_status`, which recomputes `status` and — for the failure/error case — flips `deployable?`: [4](#0-3) 

and `schedule_continuous_delivery` becomes a no-op because `deployable?` is now `false`: [5](#0-4) 

Attack flow:
1. Attacker creates/owns a GitHub repository and connects it as a Shipit stack (or any Shipit-tracked repo they own), obtaining a legitimate `webhook_secret`/signature for that org via normal repo webhook setup.
2. Attacker crafts a commit (or simply chooses a colliding SHA — SHA-1 prefix collisions are practically producible with existing published SHA-1 collision techniques, or if same commit content ever coincides, e.g. cherry-picks/mirrors) so `Commit.where(sha: ...)` matches a real victim commit row.
3. Attacker POSTs `X-Github-Event: status` to `/webhooks` with `repository` pointing to their own repo (so `verify_signature` passes using their own org's app/secret) and `state: failure`, `sha: <victim's commit sha>`.
4. `StatusHandler#process` finds the victim's `Commit` row purely by `sha`, ignoring which stack/repo it belongs to, and writes a `failure`/`error` `Status` owned by the attacker's `stack_id` context onto the victim commit's status list.
5. `Commit#deployable?` becomes `false` for the victim commit; `Stack#schedule_merges`/continuous delivery scheduling for that commit is blocked, sabotaging the victim's deploy or merge pipeline.

No existing guard prevents this: `verify_signature` validates the webhook's source org, not the target commit's owning repo; the `ExplicitParameters` schema on `StatusHandler` only validates types/presence of `sha`/`state`/etc., not repository scope; there is no `Repository`/`Stack` equality check anywhere in `process`.

### Impact Explanation
An unprivileged attacker who controls any repository connected to the same Shipit instance can inject a `failure`/`error` `Status` row onto an arbitrary victim commit sharing the attacker-chosen SHA, mutating a record that belongs to a repository/stack the attacker never authenticated against. This directly blocks `deployable?`, preventing `ContinuousDeliveryJob` enqueue and merge-request auto-merge (`schedule_merges` is gated on `success`/`pending`), i.e., an unauthorized denial of deploy/merge on another tenant's stack — matching the Critical category "a payload for one repository mutating another repository's stack, commit... or an unauthorized deploy, rollback or merge" (here, blocking one). This is repeatable against any repository/stack sharing an exploitable SHA and is not limited to a single victim.

### Likelihood Explanation
The attacker needs only: (1) a Shipit-connected repository they control (to obtain a valid signature under `verify_signature`), and (2) a commit SHA that collides with a victim's tracked commit. Exact SHA collision on arbitrary content is currently infeasible without SHA-1 attack tooling, but this bug is exploitable trivially whenever any commit is naturally shared across repositories tracked by the same Shipit install — e.g., forks, mirrors, vendored/subtree commits, or cherry-picked commits with identical content/metadata (SHA-1 is a function of tree+parents+message+timestamps, so identical content on the same date reproduces identically). This is a materially easier bar than a signature/session bypass and requires zero Shipit credentials.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to stacks associated with the webhook's authenticated repository (`params.dig('repository','full_name')`), e.g. resolve the `Repository`/`Stack` from the payload and filter `Commit.where(sha: params.sha, stack_id: matching_stack_ids)`, mirroring the fix needed for the related success-case escalation finding.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "cross-repo failure status must not block a victim commit sharing the same sha" do
  victim_stack  = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # attacker-owned/controlled stack

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                committer: shipit_users(:walrus),
                                                authored_at: Time.now, committed_at: Time.now,
                                                message: "victim commit")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                    committer: shipit_users(:walrus),
                                                    authored_at: Time.now, committed_at: Time.now,
                                                    message: "attacker commit")
  victim_commit.statuses.create!(stack_id: victim_stack.id, state: 'success')
  assert victim_commit.reload.deployable?, "sanity: victim commit deployable before attack"

  params = ExplicitParameters::Parameters.new(
    sha: shared_sha, state: 'failure', description: 'attacker-forced failure',
    context: 'ci/attacker', target_url: nil, created_at: Time.now.to_s, branches: []
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.call(params) # simulates attacker's signed webhook for their own repo

  refute victim_commit.reload.deployable?,
    "BUG: attacker-controlled webhook for their own repo mutated the victim commit's status and blocked deploy"

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    victim_commit.schedule_continuous_delivery
  end
end
```

This demonstrates: before the attack, `victim_commit.deployable?` is `true`; after the cross-repo webhook call, it flips to `false` and `ContinuousDeliveryJob` is not enqueued, confirming the same missing repository-scoping in `StatusHandler#process` enables denial-of-deploy sabotage across tenants.
