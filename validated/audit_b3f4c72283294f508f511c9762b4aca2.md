### Title
Webhook signature verification keys off `repository.owner.login` while all event handlers act on `repository.full_name` - unauthenticated cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization installations, `WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate the HMAC signature using `repository_owner`, an attacker-controlled field taken from the unauthenticated JSON body itself. Every webhook handler, however, resolves the target `Repository`/`Stack` using a *different* field from the very same body: `repository.full_name`. These two fields are never cross-checked, so an attacker can pick any configured GitHub organization that has no `webhook_secret` set (a supported, documented configuration — see `config/secrets.development.example.yml` and `docs/setup.md`'s "Using Multiple Github Applications" section) to trivially pass verification, while pointing `repository.full_name` at a completely different, real, victim stack.

### Finding Description
`verify_signature` computes the app used for verification like this: [1](#0-0) 

`repository_owner` is read directly from the untrusted JSON payload before any signature check: [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly treats an app/org with no configured secret as always-valid: [3](#0-2) 

Meanwhile, every concrete handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, etc.) resolves the actual `Repository`/`Stack` to mutate using `repository.full_name`, taken from `Handler#stacks`/`#repository_name`, not from `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

The equality that should hold, and is broken, is:
`organization used to select webhook_secret (repository.owner.login / organization.login)` == `organization implied by repository.full_name that handlers act on`.

Because both values come from the same unauthenticated JSON body and are never compared, an attacker only needs to craft:
```json
{
  "repository": {
    "owner": {"login": "OrgWithoutSecret"},
    "full_name": "victim-org/victim-repo"
  },
  ...
}
```
`Shipit.github(organization: "OrgWithoutSecret")` returns a `GitHubApp` configured with `webhook_secret: nil` (a documented, valid configuration shown in `config/secrets.development.example.yml:11` and `test/dummy/config/secrets_double_github_app.yml`), so `verify_webhook_signature` returns `true` unconditionally, regardless of the actual `X-Hub-Signature` header. `create` then dispatches the full, forged body to handlers, which operate on `victim-org/victim-repo` — a stack that may belong to a fully protected organization with a real `webhook_secret`.

This is not merely a theoretical inconsistency: the multi-org support was explicitly added to let one Shipit installation serve several orgs with independently configured secrets, meaning it is realistic for one org to be misconfigured/legacy/testing with no secret while others carry production stacks, and the code lets that weak org's "authentication" be reused to spoof events for the strong org's repositories.

### Impact Explanation
Depending on the spoofed event type, an unauthenticated attacker (no Shipit session, no `ApiClient` token, no GitHub webhook secret for the target org) can:
- Spoof a `push` event (`PushHandler`) to force `Stack#sync_github` for arbitrary stacks.
- Spoof a `status` event (`StatusHandler`) to mark arbitrary, already-existing commits on a protected stack as passing required CI/status checks.
- Combined with `continuous_deployment` on the target stack (`Stack.schedule_continuous_delivery` / `ContinuousDeliveryJob`), forging enough green-status webhooks for a commit can make that stack deploy that commit automatically, without ever touching the real org's webhook secret — this is an **unauthorized deploy**, matching the Critical impact bucket in this program's rules.
- Spoof `pull_request`/`check_suite` events to manipulate the merge queue state of a victim repo's stacks.

### Likelihood Explanation
This requires: (1) the Shipit deployment is configured with the multi-org `github:` schema (documented, supported), and (2) at least one configured organization has no `webhook_secret` (also documented as a valid, common setup, e.g. shown with a comment `# nil` in the example and dummy config files). Given the setup instructions do not warn that leaving one org's `webhook_secret` blank compromises every *other* org's webhook authenticity, this misconfiguration is plausible and the exploit itself requires nothing beyond an unauthenticated POST to `/webhooks`.

### Recommendation
- Do not select the verification secret from the same untrusted field(s) used to determine which repository/stack a handler will act on. Verify the signature independently, or, at minimum, derive the org used for signature verification identically to how each handler resolves ownership of `repository.full_name`, and reject events where `repository.owner.login` doesn't match the owner segment of `repository.full_name`.
- Consider disallowing/discouraging `webhook_secret: nil` when running in the multi-organization mode, or fail closed (422) instead of `true` when no secret is configured and other organizations do have one.
- Cross check the resolved `Repository`'s configured GitHub organization against the app/organization that validated the signature before processing the event.

### Proof of Concept
Setup: Shipit configured with two orgs, e.g. `test/dummy/config/secrets_double_github_app.yml` style config, where `OrgOne` and/or `OrgTwo` have `webhook_secret: nil`, and a victim stack exists for `real-org/real-repo` protected by a properly configured `webhook_secret` under `real-org`.

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=deadbeef   # arbitrary/incorrect value

{
  "repository": {
    "owner": {"login": "OrgOne"},        <- org with no webhook_secret configured
    "full_name": "real-org/real-repo"    <- victim org's real stack
  },
  "sha": "<existing commit sha on real-org/real-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
`verify_signature` calls `Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally and the forged event is accepted and dispatched to `StatusHandler`, which updates the status of the commit belonging to `real-org/real-repo` — all without ever knowing `real-org`'s actual webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
