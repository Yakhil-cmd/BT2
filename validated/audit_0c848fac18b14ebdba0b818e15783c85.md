### Title
Cross-repository Status injection via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the `Commit` records to update purely by `sha`, with no check that the webhook's `repository.full_name` matches the commit's own stack/repository. Any legitimately-signed `status` webhook — including one triggered from a repository the attacker owns/controls — can write a `Status` (e.g. `success`) onto any other stack's `Commit` row that happens to share the same SHA (a routine occurrence for forks, mirrors, or shared ancestor commits), immediately flipping `Commit#deployable?` for a repository the attacker never authenticated against.

### Finding Description
The broken binding, stated explicitly:
`Status written for Commit X == Status produced by the CI provider of Commit X's own stack/repository`
is false in this codebase. The actual code enforces only:
`Status written for Commit X == Status from ANY webhook whose payload.sha == X.sha`, regardless of `payload.dig('repository','full_name')`.

Code path:
- `WebhooksController#create` dispatches by event type only, then calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` verifies the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON payload (`params.dig('repository','owner','login')`) [2](#0-1) [3](#0-2) . This only confirms the request was signed by the GitHub App as installed on *some* repository (which can legitimately be the attacker's own repository, e.g. their own fork, if the app is installed there) — it does **not** confirm the sha belongs to that repository.
- The base `Handler` class provides a `stacks`/`repository_name` helper explicitly meant to scope lookups to the repository that sent the webhook [4](#0-3) , and other handlers (e.g. pull_request handlers) rely on this scoping.
- `StatusHandler#process`, however, ignores this helper entirely and looks up commits globally by sha only: [5](#0-4) 
- `Commit#create_status_from_github!` then calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [6](#0-5) , using the *victim* commit's own `stack_id` for the new `Status` row (so the record is correctly attributed to the victim's stack), but the **state, description, context** all come straight from the attacker's forged payload.
- `Commit#deployable?` is computed live from the (now attacker-influenced) status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [7](#0-6) , and `status` itself is `Status::Group.compact(self, statuses_and_check_runs)` [8](#0-7) , whose significant-status selection prefers success once no pending/failing statuses remain [9](#0-8) .

Exploit flow: the attacker installs/owns a repository (any public/unprivileged GitHub repository they control, potentially with the same GitHub App that Shipit uses installed on it, which is a normal unprivileged action for the attacker on their own resources) and force-pushes or cherry-picks a commit that is byte-identical (and thus SHA-identical) to a commit that also exists in the victim's tracked stack — trivially achievable for a fork of the victim's repository sharing history, or for any commit copied verbatim into another repo. The attacker (or their own real CI, which they fully control) posts a `success` status via GitHub's status API against their own repository/sha. GitHub genuinely and correctly signs and delivers this `status` webhook to Shipit's `/webhooks` endpoint. `verify_signature` passes because the signature is valid for whichever organization/app installation actually sent it. `StatusHandler#process` then matches `Commit.where(sha: params.sha)`, finds the victim's own `Commit` row (under an entirely different stack/repository the attacker never touched), and writes the forged `success` state onto it, making `deployable?` true before the victim's real CI ever reports.

None of the listed guards close this gap: `verify_signature` only proves *a* valid GitHub App delivery occurred, not that it originated from the *target* commit's repository; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
This is a cross-repository/cross-tenant mutation: a webhook genuinely originating from repository A (attacker-controlled) can write a `Status` record and flip `deployable?`, trigger `deployable_status` hooks, and enqueue `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` for a `Commit` belonging to repository B (victim, unrelated tenant) purely because of a SHA collision that is trivial to engineer via forking or history-sharing. This matches the explicitly in-scope Critical category "a payload for one repository mutating another's stack, commit, task or team" and can result in an unauthorized deploy being triggered (`stack.continuous_deployment?` path in `schedule_continuous_delivery`, `app/models/shipit/commit.rb:281-287`). It is repeatable against any stack whose tracked repository has (or once had) a shared commit history with an attacker-controlled repository.

### Likelihood Explanation
No secrets are required from the attacker: they only need (a) a repository they control where the shared GitHub App is installed (an ordinary, unprivileged action available to any GitHub user for public apps) and (b) a commit sha collision with the victim's tracked repo, which is the normal case for any forked repository sharing git history. Preconditions match the question's scenario exactly: victim commit has no/incomplete statuses yet. This requires no Shipit session, API token, or GitHub secret — only an unprivileged GitHub account.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to commits belonging to the repository that actually sent the webhook, using the existing `stacks`/`repository_name` helper from `Handler`, e.g. iterate `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative):
```ruby
test "status webhook from repository A must not update a commit belonging to repository B with the same sha" do
  victim_stack = shipit_stacks(:shipit)          # tracks 'shopify/shipit-engine'
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...) # no statuses yet
  attacker_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker-ci',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  refute victim_commit.deployable?

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_repo_payload)

  victim_commit.reload
  # Binding under test: Status written for victim_commit == Status from victim_commit's own repository's CI
  # LHS (actual): victim_commit.statuses.last.context => 'attacker-ci' (came from unrelated repo)
  # RHS (expected): should be nil / no status written since 'attacker/unrelated-repo' does not own this commit
  assert_nil victim_commit.statuses.find_by(context: 'attacker-ci'), "status from unrelated repository must not attach to victim commit"
  refute victim_commit.deployable?, "deployable? must not flip due to a cross-repository forged status"
end
```
This demonstrates the pre-fix behavior (status gets written, `deployable?` becomes true) versus the expected post-fix behavior (status rejected because the sending repository doesn't own the commit's stack).
