### Title
StatusHandler#process resolves `Commit` rows by bare sha with no repository/stack scoping, allowing cross-tenant Status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up every `Commit` row matching the webhook's `sha` across the *entire* database and calls `create_status_from_github!` on each one, without checking that the commit's stack corresponds to the repository that sent the webhook. Since `sha` is not unique across stacks (shared history, common ancestors, or attacker-mintable shas such as the empty-tree sha), a genuinely-signed `status` webhook from an attacker-owned repository can write a `Status` onto a `Commit` belonging to an unrelated victim stack.

### Finding Description
The broken binding: the code implicitly assumes `Commit.sha == params.sha` implies `commit.stack.repository == payload.repository`, i.e. sha equality across two `Commit` rows in different stacks is treated as repository equality. This is false — `sha` has no uniqueness constraint across stacks in this schema.

Code path:
- `WebhooksController#verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` only verifies that the payload is legitimately signed by GitHub for `repository_owner` (the org named in the payload's own `repository.owner.login`). It does not verify the sha belongs to that repository.
- `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `StatusHandler.call`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha` with **no** `stack_id`/`repository` filter, unlike `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which correctly scopes via `stacks.not_archived.where(branch:)` where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` in `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`). `StatusHandler` never calls `stacks`/`repository_name` at all.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` is the **victim commit's own** `stack_id` — the Status is written against the victim's stack, not the attacker's.

Exploit flow:
1. Attacker owns/administers repository A, onboarded as a Shipit stack (any user can self-onboard a repo they own).
2. Attacker crafts/pushes a commit or otherwise causes GitHub to have a commit/status target with the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904` (or any sha they can freely mint, e.g., via a shared merge-base/common ancestor with victim stack B — likely if A was ever forked from or shares history with B).
3. Attacker triggers a real GitHub `status` event on repo A for that sha with `state: success` (e.g. via GitHub's Statuses API on their own repo, or by causing a CI integration to post one). GitHub signs this payload with the legitimate webhook secret for repo A's org — `verify_signature` passes since the signature is valid for that org/repo, which is all it checks.
4. `StatusHandler#process` finds **every** `Commit` row across all stacks with that sha, including victim stack B's row (e.g., a common ancestor commit that was synced into B's commit history), and calls `create_status_from_github!` on it — writing a forged `Status(state: success)` into B.

Why guards fail: `verify_signature` authenticates *who signed the payload* (the org owning repo A), not *which commit/stack the sha belongs to*. `ExplicitParameters` only validates the shape of `sha`/`state`, not ownership. There is no `require_permission!`/`stacks` scoping in `StatusHandler`, unlike every other stack-scoped handler.

### Impact Explanation
A forged `success` (or any) `Status` is written on a `Commit` in a victim stack B that the attacker does not control and has no push access to. If that commit is otherwise pending deploy criteria (branch head, required status) and the stack has continuous deployment or manual deploy gated on CI status, this forged status can unblock/trigger a deploy of unreviewed/unintended code, matching "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". This is repeatable against any pair of stacks that share a commit sha, and is trivially repeatable using the universal empty-tree sha if it ever ends up recorded as a `Commit` row in any victim stack (e.g., via merge-base computations, initial empty-repo commits, or history sync). Blast radius: cross-tenant, one attacker's own onboarded repo can inject statuses into arbitrary other repositories' commit histories synced by Shipit.

### Likelihood Explanation
Preconditions: attacker needs (a) an onboarded repo A they control (self-service, no special privilege) and (b) a sha collision with a `Commit` row belonging to victim stack B (guaranteed for the empty-tree sha if such a row exists in B, or achievable via shared history/common ancestors — common in monorepo forks, template repos, or repos with a shared root commit). Attacker cost is low: create/own a small repo, sync it into Shipit, and send a normal signed `status` event via GitHub's own mechanisms. No secrets are required since GitHub itself computes the legitimate signature for the attacker's own repo. Feasibility depends on the existence of an actual sha collision between the two stacks' commit tables, which is plausible for the specific empty-tree sha or shared ancestors, but not guaranteed in all deployments.

### Recommendation
Scope `StatusHandler#process` by repository/stack, mirroring `PushHandler`: use `stacks` (derived from `Repository.from_github_repo_name(repository_name)`) to constrain the `Commit` lookup, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status webhook can only affect commits belonging to stacks whose repository actually sent the signed payload.

### Proof of Concept
Minitest plan (models/controller test, no live GitHub):
```ruby
test "cross-tenant status forgery via shared sha" do
  attacker_stack = shipit_stacks(:cyclimse) # onboarded by attacker, has its own github_hook/secret
  victim_stack   = shipit_stacks(:shipit)

  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim ancestor', author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate genuine signature for attacker's own repo/org

  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.repository.full_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  assert_difference -> { victim_commit.reload.statuses.count }, 1 do
    post :create, body:, as: :json
  end

  assert_equal 'success', victim_commit.reload.status.state
end
```
Assertion of the broken binding before/after: before the request, `victim_commit.stack_id == victim_stack.id` and `attacker_stack.id != victim_stack.id` (repositories differ) yet `Commit.where(sha: shared_sha)` returns rows from both stacks — after the request, `victim_commit.statuses.last.stack_id == victim_stack.id` even though the webhook was signed only for `attacker_stack`'s repository, proving sha equality was treated as repository equality.
