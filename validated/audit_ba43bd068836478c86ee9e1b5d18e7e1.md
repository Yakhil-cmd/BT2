### Title
Uncaught length-assertion exception in `chash.isChashValid` on malformed 288-bit chash input causes Denial of Service - (File: chash.js)

### Summary
`chash.js` decodes an attacker-supplied encoded hash string and then unpacks it under a strict, hard-coded bit-length assumption (`160` or `288`). When the decode step (`Buffer.from(encoded, 'base64')`) is fed a malformed value, Node's lenient base64 decoder can silently return a buffer of unexpected length instead of throwing, and the subsequent length assertion in `separateIntoCleanDataAndChecksum` throws an uncaught error outside of the surrounding `try/catch`, crashing the validating process — the same class of bug as the reported CVE, where `DCTStream::transformDataUnit` performed an out-of-bounds/invalid read because it assumed a fixed data-unit size that untrusted input did not actually satisfy.

### Finding Description
`isChashValid` first checks only the string length (32 or 48 chars) before decoding: [1](#0-0) 

For the 48-character (288-bit) branch, decoding uses `Buffer.from(encoded, 'base64')`, which is lenient: unlike `base32.decode` (used for the 32-char case), it does not throw on invalid base64 characters/padding — it simply stops decoding early or drops invalid characters, producing a `Buffer` whose length can be shorter than the expected 36 bytes. That decode call is wrapped in a `try/catch`, but the code that follows is not: [2](#0-1) 

`buffer2bin` converts the (possibly short) buffer to a bit string of unexpected length, and `separateIntoCleanDataAndChecksum` then hard-asserts the length must be exactly `160` or `288` bits, throwing an uncaught `Error("bad length=...")` otherwise: [3](#0-2) 

This function is reached through `validation_utils.isValidChash`, which is the generic chash-validation entry point used across the codebase (addresses, device addresses, definitions): [4](#0-3) 

While the most common 32-character address path additionally enforces a strict base32 charset via regex (`/^[A-Z2-7]{32}$/`) before calling `isChashValid`, that hardening is specific to `isValidAddress` and is not part of `isChashValid`/`isValidChash` itself. Any code path that calls `isValidChash`/`chash.isChashValid` directly with a 48-character value (the 288-bit/base64 chash format used for definitions and asset-related hashes) without first constraining the character set is exposed to this uncaught-exception crash, exactly mirroring the CVE's root cause: a parser trusting a fixed-size assumption on attacker-controlled, variable/malformed input, resulting in an unhandled fault instead of a controlled rejection.

### Impact Explanation
An uncaught exception thrown deep inside address/definition-hash validation logic during unit or definition processing can crash the Node.js process handling validation, since it is not caught by the local `try/catch` and can escape further up the call stack depending on the caller's own error handling. If reachable from a network-visible validation path (e.g., a posted unit containing a hash field validated via the 288-bit branch), this allows any unprivileged unit poster to cause a Denial of Service against nodes processing the unit, potentially halting their ability to validate/confirm new units — matching the CVSS 3.1 vector of the CVE (Availability: High, no confidentiality/integrity impact).

### Likelihood Explanation
Likelihood depends on whether any reachable, attacker-controlled field is validated through the 48-character (`chash288`) branch of `isChashValid` without prior charset sanitization equivalent to the regex guard present for the 32-character address case. The 32-character address path itself is not exploitable this way because of the pre-decode regex constraint. This makes the finding a real defect in `chash.js`'s error handling (missing exception guarding around the length-assertion logic), but its remote triggerability is contingent on an unguarded 48-character call site, which was not confirmed with certainty within the available index.

### Recommendation
Wrap the entire body of `isChashValid` (not just the decode call) in the `try/catch`, and treat any thrown length-mismatch or malformed-data error as `return false` rather than letting it propagate. Additionally, validate that base64 input strictly matches the expected charset/padding before calling `Buffer.from(encoded, 'base64')`, since Node's base64 decoder does not reject malformed input by default.

### Proof of Concept
Calling `chash.isChashValid()` directly with a 48-character string containing invalid base64 characters (so that `Buffer.from(str, 'base64')` returns a buffer shorter than 36 bytes) reproduces the crash:
```js
const chash = require('./chash.js');
// 48 chars, but not valid base64 padding/charset -> Buffer.from decodes to < 36 bytes
chash.isChashValid('!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!');
// throws uncaught Error("bad length=...") from separateIntoCleanDataAndChecksum,
// escaping the local try/catch in isChashValid
``` [5](#0-4)
