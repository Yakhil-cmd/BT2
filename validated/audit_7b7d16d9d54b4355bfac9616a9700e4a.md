### Title
Wallet approval-state persistence (`extended_pubkeys`/`wallets`) is reachable and forgeable by unpaired, non-correspondent devices via `my_xpubkey`/`wallet_fully_approved` messages - ([File: wallet_defined_by_keys.js])

### Summary
The `my_xpubkey` and `wallet_fully_approved` device-message subjects are explicitly whitelisted to be processed even from devices that are **not** paired correspondents [1](#0-0) , and the handlers they invoke persist rows into the `extended_pubkeys`/`wallets` config tables without ever checking that the sending device is actually one of the wallet's designated cosigners.

### Finding Description
`handleMessageFromHub` routes the `my_xpubkey` and `wallet_fully_approved` subjects straight to `walletDefinedByKeys.addDeviceXPubKey` and `walletDefinedByKeys.handleNotificationThatWalletFullyApproved`, and both are annotated "allowed from non-correspondents": [2](#0-1) 

`device.js` enforces this by whitelisting exactly these subjects (plus `pairing`) for senders who are not in `correspondent_devices` at all: [3](#0-2) 

The handlers themselves take `wallet` (an attacker-controlled, arbitrary base64 string) and `from_address` (the sender's own device address, cryptographically bound to their signature) and unconditionally `INSERT ... IGNORE`/`UPDATE` into `extended_pubkeys`, then attempt to advance the wallet's persistent approval state — with no check that `from_address` is a member of `wallet_signing_paths` for that `wallet`: [4](#0-3) 

The persisted rows feed directly into the wallet completion state machine: [5](#0-4) 

`checkAndFullyApproveWallet`/`checkAndFinalizeWallet` mark a wallet "fully approved"/"ready" only if **every** row returned by `extended_pubkeys` joined on `wallet` has `approval_date`/`member_ready_date` set. Since any outside device can inject an extra `extended_pubkeys` row for a guessed/known `wallet` id via `wallet_fully_approved` (which sets `member_ready_date` but leaves `approval_date` NULL, because that code path never supplies an `extended_pubkey`), the `.some(row => !row.approval_date)` check permanently evaluates true, and the real wallet can never reach `full_approval_date`/`ready_date` — regardless of how many legitimate cosigners actually approve.

This mirrors the reported bug class precisely: a persistence path intended to require a specific authorized role (a device that is genuinely one of the wallet's cosigners, analogous to "owner"/admin authority in the advisory) is reachable through a lower-privilege message-handling path (explicitly opened to non-correspondents) that performs config persistence without an authorization check (CWE-862/CWE-863).

### Impact Explanation
Any device that learns or guesses a pending multisig `wallet` id (a base64 SHA-256 hash transmitted during wallet setup) can poison that wallet's persistent `extended_pubkeys` state before or during the legitimate cosigners' approval flow, permanently preventing `wallets.full_approval_date`/`ready_date` from ever being set. This effectively freezes the shared/multisig address's usability from the affected node's perspective — a wallet-level denial-of-service/funds-availability freeze caused entirely by an unauthorized, unpaired sender writing to persistent wallet configuration it has no legitimate role in.

### Likelihood Explanation
The precondition — knowledge of a `wallet` id — is realistic for participants who were ever proposed as cosigners (e.g., `other_cosigners` entries, or previously-removed/rejected members reusing the id), and no pairing, correspondence, or membership verification is required to send `my_xpubkey`/`wallet_fully_approved`; the code path is deliberately open to non-correspondents.

### Recommendation
Before persisting into `extended_pubkeys`/advancing `wallets` approval state in `addDeviceXPubKey`/`handleNotificationThatWalletFullyApproved`, verify that `device_address` is actually listed in `wallet_signing_paths` for the given `wallet` (i.e., is a genuine, expected cosigner per the wallet's own definition template) before accepting the write, rather than trusting any sender whitelisted merely by message subject.

### Proof of Concept
1. Attacker device (unpaired, not a correspondent) obtains/guesses a target `wallet` id (base64 sha256 digest) of a multisig wallet currently being set up between real cosigners.
2. Attacker sends a `wallet_fully_approved` device message with `{wallet: "<guessed_id>"}` to the victim node. Per the whitelist in `device.js`, this is processed despite the attacker not being a correspondent.
3. `handleNotificationThatWalletFullyApproved` inserts a row `(wallet, attacker_device_address)` into `extended_pubkeys` and sets its `member_ready_date`, leaving `approval_date` NULL.
4. When the real cosigners later complete their genuine approvals, `checkAndFullyApproveWallet`'s query still returns the attacker's row with `approval_date IS NULL`, so `full_approval_date`/`ready_date` are never set for the wallet on the victim's node. [6](#0-5)

function checkAndFinalizeWallet(wallet, onDone){
	db.query("SELECT member_ready_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0){ // wallet not created yet or already deleted
		//	throw Error("no wallet in checkAndFinalizeWallet");
			console.log("no wallet in checkAndFinalizeWallet");
			return onDone ? onDone() : null;
		}
		if (rows.some(function(row){ return !row.member_ready_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET ready_date="+db.getNow()+" WHERE wallet=? AND ready_date IS NULL", [wallet], function(){
			if (onDone)
				onDone();
			eventBus.emit('wallet_completed', wallet);
		});
	});
}

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}

// called from network, without user interaction
function addDeviceXPubKey(wallet, device_address, xPubKey, onDone){
	db.query(
		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",
		[wallet, device_address],
		function(){
			db.query(
				"UPDATE extended_pubkeys SET extended_pubkey=?, approval_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[xPubKey, wallet, device_address],
				function(){
					eventBus.emit('wallet_approved', wallet, device_address);
					checkAndFullyApproveWallet(wallet, onDone);
				}
			);
		}
	);
}

// called from network, without user interaction
function handleNotificationThatWalletFullyApproved(wallet, device_address, onDone){
	db.query( // just in case it was not inserted yet
		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",
		[wallet, device_address],
		function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device_address],
				function(){
					checkAndFinalizeWallet(wallet, onDone);
				}
			);
		}
	);
}
