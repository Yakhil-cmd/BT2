This confirms the vulnerability. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [1](#0-0)  which is a completely different field from the one used by `WebhooksController#verify_signature` / `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (with an `organization.login` fallback) to select which per-organization `GitHubApp` config (and thus which `webhook_secret`) authenticates the request [2](#0-1) .

### Title
Cross-organization webhook forgery via mismatched authentication field and repository-lookup field - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook against the `webhook_secret` of the organization named in `repository.owner.login` (or `organization.login`), but `Shipit::Webhooks::Handlers::Handler#repository_name` — used by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) to resolve the target `Stack`/`Repository`/`Commit` — reads a *different* JSON field, `repository.full_name`. Both fields live in the same attacker-controlled, unsigned-until-verified JSON body, and nothing ties them together.

### Finding Description
In a multi-organization Shipit deployment (`Shipit.github(organization:)`/`github_app_config`, documented in `docs/setup.md`), each configured GitHub organization has its own `webhook_secret` [3](#0-2) . If `verify_webhook_signature` finds no `webhook_secret` configured for the selected organization, it returns `true` unconditionally: `return true unless webhook_secret` [4](#0-3) .

The organization used to pick which secret governs the request is derived purely from the untrusted request body, before the signature is checked: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [5](#0-4) . Once `verify_signature` passes, `Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *same raw JSON* to handlers [6](#0-5) , and every handler resolves its target repository via `payload.dig('repository', 'full_name')` — an entirely separate field [1](#0-0) .

This breaks the binding: `organization authenticated == repository written`. An attacker can craft a body where `repository.owner.login` names an organization configured with a blank/missing `webhook_secret` (or one the attacker otherwise controls/knows), passing signature verification trivially or with a leaked/guessable secret for that org, while setting `repository.full_name` to the full name of a stack belonging to an entirely different, properly-secured organization tracked by the same Shipit instance. `PushHandler` would then trigger `stack.sync_github(expected_head_sha: ...)` [7](#0-6) , `StatusHandler` would inject fabricated commit statuses via `commit.create_status_from_github!` [8](#0-7)  for commits under the victim org, and similarly for `CheckSuiteHandler`/PR handlers — all without ever knowing the victim organization's real `webhook_secret`.

### Impact Explanation
This is a High-impact authentication-binding break: an unauthenticated/cross-tenant attacker (in a multi-org Shipit install) can inject GitHub-originated events (fake CI statuses, fake pushes triggering sync jobs, fake check-suite completions, fake PR state changes) attributed to a repository/stack they do not control and were never issued credentials for. Since CI status gating (`ci.require`) and merge/deploy eligibility for a stack rely on `Commit#statuses` populated from these webhooks, this can be leveraged toward triggering an unauthorized deploy path (satisfying CI checks that never really passed) for the victim's stack. It does not itself grant `GITHUB_TOKEN` exfiltration or direct RCE, but it forges the trust signal (organization-authenticated webhook) that downstream deploy-eligibility logic depends on.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set (a state explicitly shown as a valid/blank configuration in `docs/setup.md` and `config/secrets.development.shopify.yml`) or where an attacker otherwise possesses/derives one org's secret. Given that per the documented multi-org config format `webhook_secret:` is commonly left blank during setup, this is a realistic misconfiguration this codebase's own design permits and does not guard against by cross-checking `repository.owner.login` against `repository.full_name`'s owner segment.

### Recommendation
In `Shipit::Webhooks::Handlers::Handler` (or in `WebhooksController#create`), enforce that the organization portion of `repository.full_name` matches `repository.owner.login`/`organization.login` used for signature verification before dispatching to any handler, so the authenticated organization and the repository actually acted upon are provably the same entity.

### Proof of Concept
1. Configure Shipit with two organizations: `victim-org` (has `webhook_secret` set, has a tracked `Stack` for `victim-org/victim-repo`) and `attacker-org` (configured with no `webhook_secret`, per `docs/setup.md`'s documented blank-secret format).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": {"login": "attacker-org"},
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "branches": [{"name": "main"}]
}
```
No `X-Hub-Signature` header is required because `attacker-org` has a blank `webhook_secret`, so `verify_webhook_signature` returns `true` [4](#0-3) .
3. `WebhooksController#verify_signature` passes (organization = `attacker-org`) [9](#0-8) .
4. `StatusHandler#process` looks up commits by `sha` (unscoped by org) and calls `commit.create_status_from_github!(params)` [8](#0-7) , forging a passing CI status on a commit belonging to `victim-org`'s stack, despite the request never being signed by `victim-org`'s secret.
