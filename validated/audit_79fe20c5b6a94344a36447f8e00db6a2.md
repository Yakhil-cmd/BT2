### Title
Webhook signature verified against `repository.owner.login`, but stack routing uses unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate an inbound webhook against based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body. Once the HMAC check passes, the actual side effect of the webhook — which `Stack`/`Repository` gets synced, statused, or has commits appended — is determined by an entirely different, also attacker-supplied field: `repository.full_name`, read in `Handler#repository_name`. Because Shipit supports multiple organizations each with its own GitHub App and `webhook_secret` (as shown in `config/secrets.development.shopify.yml`), an attacker who legitimately controls one configured organization can forge a payload whose `owner.login` matches their own org (so the signature check passes with their own secret) while `full_name` points at a repository belonging to a different, victim organization tracked by the same Shipit instance.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-49` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to fetch the right `github_app`/`webhook_secret` for signature verification: [2](#0-1) 

This binds "authentication" to the *owner* field only. But the event handlers that actually act on the payload resolve the target repository from a *different* field, `full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process`, for example, uses `stacks` (resolved from `full_name`) to enqueue `GithubSyncJob`, which fetches commits and mutates the target stack: [4](#0-3) 

The signature-verification step never checks that `owner.login` is consistent with `full_name`'s owner segment — they are independently attacker-controlled JSON fields in the same unsigned-until-verified payload. Shipit explicitly supports per-organization GitHub App configuration with distinct `webhook_secret`s (`config/secrets.development.shopify.yml` configures `somegithuborg` and `someothergithuborg` separately) and raises `GithubOrganizationUnknown` for orgs it doesn't recognize, confirming that the org key drives credential selection, not repository targeting. [5](#0-4) 

This breaks the intended binding: **organization that authenticated == repository that is written**. The signature only proves "the sender knows organization A's webhook secret," not "the sender is authorized to act on the repository named in `full_name`."

### Impact Explanation
An attacker who is a legitimate admin/owner of one GitHub organization configured in this Shipit instance (and therefore able to trigger real, correctly-signed webhook deliveries for their own org, e.g. by pushing to their own repo, or by directly POSTing a payload signed with the secret they can obtain via their own installed GitHub App delivery) can set `repository.full_name` to `victim-org/victim-repo` while keeping `repository.owner.login` equal to their own org. `verify_signature` succeeds, and downstream handlers (`PushHandler`, status handler, `check_suite` handler, etc.) operate on the victim's tracked `Stack`. This can queue `GithubSyncJob` against the victim's stack with attacker-influenced `expected_head_sha`, and can forge commit statuses (`app/models/shipit/webhooks/handlers/handler.rb`-driven state/status handlers) or check-suite state for the victim repository — effectively an unauthorized cross-repository write into another team's deploy pipeline/queue, without ever needing the victim's webhook secret. This matches the "cross-repository writes" / "unauthorized deploy" Critical/High impact bar, since it can influence which commits are queued for deploy on a stack the attacker does not own.

### Likelihood Explanation
Requires the attacker to control at least one organization already configured as a trusted GitHub App integration on the shared Shipit instance (multi-org setups are explicitly supported and documented), and requires the Shipit deployment to track repositories belonging to more than one organization sharing infrastructure with an org the attacker controls. This is a realistic scenario for shared/internal Shipit deployments serving multiple teams/orgs, but not exploitable against a single-organization Shipit install with only one configured GitHub App.

### Recommendation
When verifying the webhook signature, cross-check that the organization used to select the `webhook_secret` matches the owner segment of `repository.full_name` (and `organization.login` for org-level events), rejecting the webhook if they diverge. Alternatively, derive the signing/verification organization strictly from `full_name`'s owner segment rather than the separate `owner.login` field, so a single trusted field drives both authentication and repository resolution.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.shopify.yml` pattern).
2. `victim-org/tracked-repo` has a `Stack` in Shipit.
3. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/tracked-repo"
  }
}
```
4. Attacker signs it with `attacker-org`'s legitimately-known `webhook_secret` and sets `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, which succeeds because the signature matches `attacker-org`'s secret.
6. `Shipit::Webhooks.for_event('push')` runs `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/tracked-repo")` — the victim's stack — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, causing `GithubSyncJob` to run against the victim's stack based on attacker-supplied input.
