### Title
Webhook `repository_owner` used only to pick the HMAC secret, never bound to the `repository.full_name` that handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the request against using the `organization`/`repository.owner.login` field taken from the *same untrusted JSON body* it is about to validate, but nothing ever asserts that this organization matches the `repository.full_name` that the event handlers subsequently use to look up and mutate a `Repository`/`Stack`. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
Shipit supports being configured with multiple independent GitHub App installations, one per GitHub organization, each with its own `webhook_secret` [1](#0-0) , and looked up via `Shipit.github(organization:)` / `github_app_config` [2](#0-1) .

`WebhooksController#verify_signature` picks which secret to check the signature with, based on `repository_owner`, which itself is read straight out of the still-unverified JSON payload: [3](#0-2) 

Because the attacker who owns/controls a legitimate GitHub App installation on their **own** organization (e.g. an org that also uses this Shipit instance, or any org configured in the `github:` secrets map) knows that org's `webhook_secret`, they can craft an arbitrary JSON body, compute a valid `X-Hub-Signature` for their own org, and set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` selects and successfully checks their own secret), while independently setting `repository.full_name` (or other repository identifiers inside `pull_request`, `push`, `status`, etc. payload) to name a repository belonging to a **different**, victim organization tracked by the same Shipit instance.

Every handler resolves the target `Repository`/`Stack` purely from `repository.full_name` in the body, with no re-check that it belongs to the org whose secret validated the signature, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

`Repository#from_github_repo_name`/`Stack.from_param!`-style lookups only match on owner/name strings taken from the payload, with no correlation back to the authenticating installation. This is exactly the class of TOCTOU/binding bug described in the analog report: the field the signature check keys off of (`repository_owner`) is never contractually the same field the write path trusts (`repository.full_name`), even though both come from the same attacker-controlled JSON body.

### Impact Explanation
An attacker who legitimately controls one GitHub organization/app installation registered with this Shipit instance can forge webhook events (`pull_request` labeled/opened/closed, `push`, `status`, `check_suite`, `membership`, etc.) that are accepted as valid and then processed **as if they came from a different organization's repository**. Depending on the handler this can: archive/unarchive review stacks, create/delete team memberships, create commit statuses, or otherwise mutate stack/task state for a repository the attacker does not own — a cross-repository/cross-organization write performed using someone else's org's trust, satisfying the "cross-repository writes" impact bar.

### Likelihood Explanation
Requires the attacker to control (or have compromised) at least one GitHub App installation/organization already registered in this Shipit deployment's `github:` secrets, which is a normal, unprivileged-relative-to-other-tenants scenario for any multi-org Shipit installation (a documented, supported configuration). No GitHub write access to the victim repository, no Shipit session, and no `api_clients_secret`/`webhook_secret` of the victim org are needed — only the attacker's own org's webhook secret, which they legitimately possess.

### Recommendation
After verifying the signature, re-derive/validate that the `repository`/`organization` object embedded in the payload actually belongs to the same organization whose secret was used to authenticate the request (i.e. compare `repository.owner.login` == the resolved `Repository#owner` for the `full_name` used downstream, and reject/422 on mismatch), rather than trusting `repository.full_name` independently in each handler.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (supported multi-tenant configuration, see `docs/setup.md` "Using Multiple Github Applications").
2. As the owner/admin of `attacker-org`'s GitHub App, know `attacker-org`'s `webhook_secret`.
3. Build a `pull_request` (or `push`/`status`) webhook JSON body where `repository.full_name` = `"victim-org/some-repo"` but `repository.owner.login`/`organization.login` = `"attacker-org"`.
4. Compute `X-Hub-Signature` over this body using `attacker-org`'s webhook secret, per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` semantics.
5. POST to `/github/auth/.../webhooks` (or the mounted webhooks endpoint) with that body and signature. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature check passes.
6. `Shipit::Webhooks.for_event(event)` handlers then process the body and resolve the `Repository`/`Stack` for `victim-org/some-repo` using `Repository.from_github_repo_name(params.repository.full_name)`, mutating victim-org state despite the signature only proving authenticity for `attacker-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
