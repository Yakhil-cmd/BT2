### Title
Attacker-controlled route hop executes arbitrary `token.transfer` under the caller's signed auth tree in router strategies - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller's router strategies (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, `flash_position`) accept fully user-supplied `swap_xdr` route payloads. The swap aggregator keeps no allowlist of pool or token addresses: it calls whatever contract the payload names. This is the on-chain analog of SSRF — the protocol performs an external call to an attacker-chosen address in a privileged context. Here the privileged context is the caller's `require_auth` tree: any `token.transfer(victim, attacker, x)` executed by a rogue hop pool is recorded by `simulateTransaction` as a child of the caller's authorization entry, and executes on submission if the caller signs the returned tree, draining the caller's wallet — not just the routed amount.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes exactly one `token_in.transfer(controller, router, amount_in)` and invokes `router.execute_strategy(controller, amount_in, swap)` on the caller-provided route bytes [1](#0-0) . Inside the aggregator, venue adapters invoke `ctx.hop.pool` and transfer `ctx.hop.token_in` — addresses taken from the payload's `assets` registry with no allowlist [2](#0-1) . The threat model states this explicitly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount" [3](#0-2) .

The test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves it end to end: a rogue "pool" named by the route executes `token.transfer(alice, attacker, WALLET_BALANCE)` mid-swap; recording-mode simulation attaches that transfer as a sub-invocation of Alice's `swap_collateral` auth entry, and once the poisoned tree is signed, the transfer succeeds while the swap itself still settles at a fair output [4](#0-3) .

### Impact Explanation
Theft of user funds exceeding the routed amount: any token the victim holds — including assets never listed on the protocol — can be swept if the victim signs the simulated authorization tree, which embeds the rogue transfer invisibly beneath a legitimate-looking `swap_collateral` root. In the PoC Alice's entire 77,770-unit wallet balance of an unrelated token moves to the attacker while she receives a fair 2.5 ETH swap output.

### Likelihood Explanation
Medium-to-low. Exploitation requires the victim to sign a poisoned authorization tree — either blindly, via a wallet that does not render nested sub-invocations, or because the tree is only inspected at the root. The attacker is otherwise a fully unprivileged address supplying route bytes to a public entrypoint. The protocol mitigates nothing on-chain: the only defense is client-side route/auth-tree decoding, which the threat model itself notes must be enforced by the client [5](#0-4) .

### Recommendation
Maintain a governance-approved allowlist of venue pool contracts (and optionally token pairs) and reject routes naming unlisted addresses, analogous to Mastodon's disallowed-IP list. At minimum, have the controller verify that the signed authorization tree beneath each strategy root contains exactly the one expected `token_in.transfer` child and nothing else is not possible on-chain — so enforcement must live in the SDK/wallet layer, plus an on-chain venue registry for defense in depth.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies 10,000 USDC and holds `WALLET_BALANCE` of an unlisted token. Attacker deploys `RogueHopPool` whose `swap()` calls `token.transfer(alice, attacker, WALLET_BALANCE)` [6](#0-5) .
2. Attacker serves Alice a `swap_collateral(alice, account_id, USDC, 5_000e7, ETH, route)` quote whose route names `RogueHopPool` as the hop [7](#0-6) .
3. Simulation records the wallet-draining `transfer` as a child of Alice's `swap_collateral` auth entry; if Alice signs that tree, the host authorizes the transfer, `alice` balance → 0, `attacker` → `WALLET_BALANCE`, and Alice still receives her fair swap output [8](#0-7) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
