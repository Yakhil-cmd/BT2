### Title
Webhook signature is verified against `repository.owner.login` while event handlers act on `repository.full_name`, letting an attacker spoof CI status / trigger syncs for a repo whose organization never configured a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using `repository_owner`, taken from `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) . The event is then dispatched to handlers that instead resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` [2](#0-1) . These are two independent, attacker-controlled fields in the same unauthenticated JSON body; nothing ties `owner.login` to `full_name`.

### Finding Description
`Shipit.github(organization:)` returns a `GitHubApp` for the organization named in `repository_owner`, and `verify_webhook_signature` is a no-op that returns `true` whenever that organization's `webhook_secret` is blank/unconfigured [3](#0-2) . `webhook_secret` is documented as optional per GitHub App [4](#0-3)  and multi-org configs allow a mix of orgs, each independently keyed [5](#0-4) .

Because `repository_owner` (used to pick the verification key) and `repository.full_name` (used by every handler to find the target `Stack`) are read from separate, unrelated keys of the same POST body, an attacker can craft a payload where:
- `repository.owner.login` = an organization with no `webhook_secret` configured (or one they control the secret for), so `verify_webhook_signature` trivially passes,
- `repository.full_name` = `victim-org/victim-repo`, an entirely different, legitimately configured stack.

The equality that should hold — "organization whose signature authenticated the request" == "repository whose state the handler mutates" — is never checked, so the two can diverge.

### Impact Explanation
With signature verification bypassed this way, an unauthenticated attacker can drive any registered `Webhooks.handlers` (from `app/models/shipit/webhooks/handlers/`) against a victim stack:
- `StatusHandler#process` creates a `Status` on any commit matching an attacker-chosen `sha` via `Commit.create_status_from_github!`, letting the attacker forge CI status for a victim's commit [6](#0-5) . Forged green/success statuses on a stack that gates deploys on required statuses can be used to make an otherwise-blocked commit appear deployable/mergeable.
- `PushHandler#process` and `CheckSuiteHandler#process` similarly act on `stacks` resolved through `Repository.from_github_repo_name(repository_name)` using the spoofable `full_name`, forcing `sync_github` or check-run refreshes on a victim stack [7](#0-6) [8](#0-7) .

This crosses the "organization authenticated versus the repository that is written" trust boundary called out as in-scope, and forged statuses feeding merge/deploy gating meets the High-severity bar (escalation enabling an unauthorized deploy/merge decision) without any Shipit session, API token, or GitHub write access.

### Likelihood Explanation
Exploitability only requires: (1) the target Shipit instance is configured for multiple GitHub organizations (documented, supported feature) or has at least one onboarded organization without a `webhook_secret` (documented as optional), and (2) the attacker can reach `/webhooks` unauthenticated, which is the public, documented endpoint for this controller. No credentials, sessions, or GitHub write access to the victim repository are needed — only knowledge of the victim's `owner/repo` and a target commit `sha` (both public information for public repos, or guessable/observable in many deployments).

### Recommendation
In `WebhooksController#verify_signature`, and in `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, enforce that the organization whose secret validated the signature matches the owner embedded in `repository.full_name` (or better, always derive the verification key strictly from `repository.full_name`'s owner segment, not from a separately-trusted `repository.owner.login`/`organization.login` field). Reject the webhook if these disagree, and consider making `webhook_secret` mandatory for all configured organizations instead of allowing a silent no-op verification path.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` (no `webhook_secret` set) and `victim-org` (webhook configured, has a stack tracking `victim-org/victim-repo` and a known commit `sha`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature [3](#0-2) .
4. `StatusHandler` resolves `stacks` via `full_name = "victim-org/victim-repo"` and creates a forged "success" `Status` on the victim's commit [2](#0-1) [6](#0-5) .

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post

      Rails.logger.info([
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
