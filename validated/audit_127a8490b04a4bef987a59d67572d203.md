### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while stack mutation keys off `repository.full_name`, allowing an attacker with a validly-signed webhook for their own org to archive a victim org's review stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using `params.dig('repository','owner','login')` (or `organization.login`), while `ClosedHandler#repository` resolves the actual `Shipit::Repository`/`ReviewStack` to mutate using the independent `params.repository.full_name` field. Nothing in the request schema or controller enforces that these two fields describe the same organization, so a payload signed with an attacker's own org secret can name a victim org's repo in `full_name` and archive the victim's review stack.

### Finding Description
The binding the code should enforce is: `organization used to verify HMAC(repository_owner) == organization owning repository.full_name`. Tracing the path:

- `WebhooksController#verify_signature` computes the signing organization purely from `repository.owner.login`/`organization.login`: [1](#0-0) [2](#0-1) 
and looks up that org's app/secret via `Shipit.github(organization:)` → `github_app_config`, which is a distinct per-organization config keyed only by that login string: [3](#0-2) 

- `ClosedHandler`'s `ExplicitParameters` schema only `requires :repository do requires :full_name, String end` - it does not require, read, or cross-check `repository.owner.login`: [4](#0-3) 

- The actual repository/stack that gets mutated is resolved solely from `params.repository.full_name`: [5](#0-4) 

- `ReviewStackAdapter#archive!` looks the stack up by `environment` (derived from `params.number`) within `repository.review_stacks`, and unconditionally decommissions it: [6](#0-5) 

Root cause: the JSON body is entirely attacker-controlled, and GitHub's real webhook payloads happen to keep `repository.owner.login` and the owner segment of `repository.full_name` consistent, but nothing in this engine enforces that invariant. An attacker who legitimately owns/administers "attacker-org" (and thus can produce a validly-signed webhook using attacker-org's configured `webhook_secret`) can craft a `pull_request`/`closed` payload with:
- `repository.owner.login` (or `organization.login`) = `"attacker-org"` → causes `verify_signature` to check the signature against attacker-org's own secret, which the attacker knows and can compute correctly.
- `repository.full_name` = `"victim-org/repo"` → causes `ClosedHandler#repository` to resolve to the victim's `Repository`.
- `number` = `7` → matches the victim's real PR/environment, resolving to the victim's live `ReviewStack`.

Since `verify_signature` passes (attacker signed with their own valid secret) and `drop_unhandled_event`/schema validation only checks presence of fields, not cross-field consistency, `ClosedHandler#process` proceeds to call `review_stack.archive!`, tearing down the victim's stack: `stack.remove_from_provisioning_queue`, `stack.deprovision`, `stack.archive!`.

Existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) do not prevent this because none of them ties the field used for signature verification (`repository.owner.login`/`organization.login`) to the field used for resource resolution (`repository.full_name`).

### Impact Explanation
A payload signed by any organization onboarded to this Shipit instance can force teardown (deprovision + archive) of an arbitrary victim organization's review stack, as long as the attacker knows the victim's real PR number (easily observable on public/private repos they have any visibility into, or simply guessable/brute-forceable since PR numbers are small sequential integers). This is a cross-tenant unauthorized write/mutation of another repository's/organization's resource triggered by a payload that authenticated only for the attacker's own tenant - matching the "payload for one repository mutating another's stack" Critical impact category. It is repeatable against any victim repository/PR number combination known to the attacker, for every org configured in this Shipit instance's multi-tenant `secrets.github` config.

### Likelihood Explanation
Preconditions: Shipit must be configured with the multi-organization GitHub App schema (`secrets.github` keyed by multiple org logins), which is a documented supported deployment mode (`test/dummy/config/secrets_double_github_app.yml`). The attacker needs only their own org's webhook_secret (which they are entitled to since it's their own GitHub App installation) and the victim's real PR number - no victim secrets, sessions, or tokens are required. Cost is a single crafted HTTP POST to `/webhooks`. This is highly feasible and fully repeatable.

### Recommendation
In `ClosedHandler` (and all `PullRequest` handlers), require and validate `repository.owner.login`/`organization.login` as part of the schema, and assert it matches the `repository_owner` value that `WebhooksController#verify_signature` used to select the signing organization (e.g., pass the verified organization into the handler and check `repository.full_name.split('/').first == verified_organization`) before performing any lookup/mutation. Reject the event (204/422) on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "cross-tenant pull_request closed event archives victim stack signed with attacker org secret" do
  # Setup: victim-org repository + review stack for PR #7
  victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "repo", review_stacks_enabled: true, provisioning_behavior: :allow_all)
  victim_stack = create_review_stack_for(victim_repo, pr_number: 7) # existing test helper pattern from closed_handler_test.rb
  assert_not victim_stack.archived?

  # Attacker owns "attacker-org", configured in secrets.github with a known webhook_secret
  payload = payload_parsed(:pull_request_closed).merge(
    "number" => 7,
    "repository" => { "full_name" => "victim-org/repo", "owner" => { "login" => "attacker-org" } }
  ).to_json

  signature = Shipit::Hook::DeliverySigner.new(attacker_org_webhook_secret).sign(payload)
  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  # BEFORE: binding claim - organization verifying webhook ("attacker-org") == organization owning mutated stack ("victim-org")? false
  assert_not_equal "attacker-org", victim_repo.owner

  post :create, body: payload, as: :json
  assert_response :ok

  # AFTER: victim's stack was archived despite signature belonging to attacker-org, not victim-org
  assert victim_stack.reload.archived?, "victim stack should NOT have been archived by an attacker-org-signed payload"
end
```
The assertion `assert victim_stack.reload.archived?` demonstrates the unauthorized cross-tenant mutation; a fixed implementation should instead reject the request (422/204) and leave `victim_stack.archived?` `false`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
