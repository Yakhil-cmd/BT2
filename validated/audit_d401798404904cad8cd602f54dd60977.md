### Title
Webhook signature is verified against `repository.owner.login`, but events are dispatched using the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), then verifies the HMAC over the *entire* raw request body using that organization's secret. [1](#0-0)  Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that resolve the target `Repository`/`Stack` from a *different* field in the same body: `payload.dig('repository', 'full_name')`. [2](#0-1)  `Repository.from_github_repo_name` then does a raw lookup by owner/name split from that string. [3](#0-2) 

### Finding Description
Shipit explicitly supports multi-tenant configuration where multiple, independent GitHub organizations are each configured with their own `webhook_secret`, `app_id`, `private_key`, etc, as shown in `test/dummy/config/secrets_double_github_app.yml`. [4](#0-3)  Each organization's admin legitimately possesses their own org's `webhook_secret` (they configure it on the GitHub App settings page for their own org), and this is not a privileged secret with respect to *other* tenants on the same Shipit instance.

The binding that should hold is:
`organization that authenticated the request (repository.owner.login, verified via HMAC)` == `repository that the request is allowed to write to (repository.full_name, used to resolve the target Stack)`

Because the HMAC only proves the bytes of the payload weren't tampered with by a third party relative to *some* known secret — it does not prove any semantic relationship between `owner.login` and `full_name` inside that payload. An attacker who legitimately administers Org A's GitHub App (and thus knows Org A's `webhook_secret`) can craft an arbitrary JSON body where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` selects Org A's secret and the HMAC computed by the attacker over their own forged body validates successfully)
- `repository.full_name` = `"OrgB/victim-repo"` (an entirely different tenant's repository that Shipit also manages)

Since `verify_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner segment, and handlers trust `full_name` to resolve the target `Stack`, the forged event is processed as if it legitimately originated from Org B's repository/webhook — even though the attacker has no access to Org B's `webhook_secret`, GitHub App, or repository.

The `status` webhook handler demonstrates the real-world reachable impact: it creates a `Status` record for a specific commit sha using attacker-controlled `state`/`context`/`target_url` fields straight from the payload. [5](#0-4)  Shipit's deploy safety mechanism (`ci.require`) gates deploys on these `Status` records showing `success` for required contexts. By forging a `status` webhook (signed with Org A's secret, but with a `full_name`/sha belonging to Org B's stack), an attacker can inject a fake "success" status for a commit they want deployed in Org B's stack, satisfying `ci.require` without any real CI having run, and without ever possessing Org B's credentials.

### Impact Explanation
This breaks the cross-tenant repository-write boundary explicitly called out in scope: "an organization that authenticated versus the repository that is written." A holder of one organization's legitimate `webhook_secret` can inject/forge webhook-driven state (fabricated commit statuses, spurious `GithubSyncJob`/`RefreshCheckRunsJob` triggers, membership/team mutations, etc.) against a *different* organization's stacks that Shipit also serves. Concretely, forging a fake passing CI status can circumvent `ci.require` safety checks and enable an unauthorized deploy of a commit in a different organization's stack, meeting the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Exploitation requires only: (1) the target Shipit instance to be configured for multiple GitHub organizations (a supported, documented configuration — see `secrets_double_github_app.yml`), and (2) the attacker to control (as an unprivileged, non-Shipit-session, non-API-token actor) any one of those organizations' GitHub App webhook secrets, which is normal, expected access for an org admin who is *not* a Shipit privileged user and has no access to other tenants. No Shipit session, API token, or GitHub write access to the victim repository is required — only knowledge of a sibling tenant's webhook secret, which the attacker legitimately possesses for their own tenant.

### Recommendation
In `WebhooksController#verify_signature`, after locating `github_app = Shipit.github(organization: repository_owner)` and verifying the signature, additionally assert that every repository-identifying field consumed by downstream handlers (`repository.full_name`, `organization.login`) is consistent with `repository_owner`/the resolved `github_app`'s organization before dispatching to handlers. Reject (422) any payload where `repository.full_name`'s owner segment does not match `repository.owner.login`/`organization.login` used to select the verifying secret.

### Proof of Concept
1. Configure Shipit with two tenants, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `secrets_double_github_app.yml`).
2. As an attacker who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha-in-OrgB-repo>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://ci.example.com/fake",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates the HMAC successfully against the attacker's own known secret. [6](#0-5) 
5. The `status` handler processes the payload using `repository.full_name = "OrgB/victim-repo"`, creating/updating a `Status` on `OrgB`'s commit as though verified CI passed — satisfying `ci.require` for a deploy the attacker does not otherwise have permission to approve.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
