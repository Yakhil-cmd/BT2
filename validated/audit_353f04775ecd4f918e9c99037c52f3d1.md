## Analysis

The audit finding describes a griefing pattern: a loop that processes multiple independent recipients atomically, where **one malicious/reverting recipient causes the entire batch to fail**, permanently blocking funds meant for unrelated, legitimate parties.

Ocore's Autonomous Agent (AA) engine has a structurally identical pattern in the **secondary-trigger cascade**. When a primary AA response contains payment outputs to other AA addresses, `handleSecondaryTriggers()` invokes each destination AA in sequence with `async.eachSeries`, and if **any single secondary AA bounces**, the error propagates and the *entire* primary trigger (including all previously-successful secondary AA calls and the primary AA's own state changes) is unwound via `revert()`, which performs `ROLLBACK TO SAVEPOINT initial_balances` and then bounces the whole trigger back to the original sender. [1](#0-0) [2](#0-1) 

Since the savepoint `initial_balances` is set once at the very start of the primary trigger's processing, `ROLLBACK TO SAVEPOINT initial_balances` discards *all* effects accumulated across *all* secondary AAs called in that fan-out, not just the failing one: [3](#0-2) 

### Title
Single reverting secondary AA in a fan-out permanently blocks and rolls back state/fund updates for all unrelated AAs in the same trigger cascade - (File: aa_composer.js)

### Summary
`handleSecondaryTriggers()` calls out to every destination AA address referenced in a primary AA response's payment outputs, in series. Any AA author can design (or an existing AA may already contain logic that, under some inputs) causes their AA to always `bounce()`. Whenever a hub/distributor AA's single trigger fans out payments to multiple destination AAs in one response — a common "multi-send"/"router"/reward-distribution pattern — and one of those destinations is such a reverting AA, the failure aborts the *whole* trigger tree via `revert()`, rolling back the balances/state of every other AA that was already successfully updated in the same cascade.

### Finding Description
In `handleSecondaryTriggers()`, the array of destination AAs (derived from the primary response's output addresses) is processed with `async.eachSeries`. Each secondary AA is run through `handleTrigger()`, and its outcome is reported back via the `onDone` callback: if the secondary AA bounces, `cb(bounce_message)` is called, which stops the `async.eachSeries` iteration and propagates the error to the final callback. [4](#0-3) 

For a primary (non-secondary) trigger, that final callback calls `revert()`: [5](#0-4) 

`revert()` clears all responses accumulated so far (including successful ones from other secondary AAs already processed earlier in the same `async.eachSeries` loop), clears the kvstore batch, and rolls the DB back to the single savepoint taken at the very beginning of trigger processing, before finally calling `bounce()` on the *primary* trigger: [2](#0-1) 

This means the design is "all-or-nothing" across an entire tree of secondary AA calls stemming from one trigger: any single AA in that tree that reverts (whether due to a legitimate bug, an edge case, or a deliberately crafted "always bounce" AA controlled by an attacker) discards the successful work done for every *other* AA and every *other* user whose balances were touched earlier in that same cascade. This is exactly analogous to the `withdrawTaxes()` loop in the report, where one malicious `transfer()` in the loop caused `require(success)` to revert the whole batch and lock funds meant for the (unrelated) global beneficiary.

### Impact Explanation
Any application built on top of ocore's AA layer that implements a fan-out/distribution pattern — e.g., a hub AA that on a single trigger forwards commissions, yields, or payouts to several sub-AAs (staking pools, sibling contracts, oracle-fee recipients, etc.) in one response — is vulnerable to permanent denial of that distribution round if any one of the destination AAs can be made to bounce. An attacker who controls (or can influence the logic of) just one of the N destination AAs in the fan-out can force the entire round's payments/state updates to roll back every time, freezing funds and state updates intended for the other, unrelated legitimate AAs and their users. Because the failure is deterministic and repeatable, this is not a one-off griefing but a persistent freeze reachable by any AA author who is one of several fan-out destinations.

### Likelihood Explanation
Reachability requires only that an attacker deploy or control an AA address that legitimately becomes one of several secondary-trigger destinations of a widely used hub/distributor AA (a common composition pattern, since AAs can call other AAs by including payment outputs to them). No special privileges beyond being an ordinary AA author are needed; the attacker's AA merely needs a `bounce()` call that reliably triggers whenever it is invoked as part of the batch.

### Recommendation
Do not let a single failing secondary AA invalidate the entire fan-out. Options:
- Isolate each secondary AA call in its own sub-transaction/savepoint so a failure in one only rolls back that specific branch (and its own bounce fee), rather than the entire primary-trigger's accumulated effects.
- Track and skip/soft-fail an unresponsive or reverting secondary AA (e.g., record the failure, continue processing the remaining destinations) instead of aborting the whole cascade.
- Document and, where practical, enforce limits so hub AA authors are aware that fan-out to attacker-influenceable AA addresses creates this systemic revert risk, and provide primitives (e.g., per-destination try/catch-like isolation in oscript) to mitigate it.

### Proof of Concept
1. Deploy `AA_HUB`, which upon receiving a trigger sends payment outputs to `AA_A`, `AA_B`, and `AA_C` (three sub-AAs) in a single response, and also updates its own state (e.g., incrementing a distributed-rewards counter).
2. Deploy `AA_C` as a malicious/faulty secondary AA whose only logic is `bounce('always fail')`.
3. Any user sends a trigger to `AA_HUB`. `handleTrigger()` produces a primary response with outputs to `AA_A`, `AA_B`, `AA_C`; `handleSecondaryTriggers()` processes them via `async.eachSeries` (aa_composer.js:1720-1741).
4. `AA_A` and `AA_B` process successfully and update their balances/state; when `AA_C` is processed it bounces.
5. The `async.eachSeries` final callback observes the error and calls `revert()` (aa_composer.js:1743-1750), which rolls back to the `initial_balances` savepoint (aa_composer.js:528-529) — undoing `AA_A`'s and `AA_B`'s successful state/balance updates as well as `AA_HUB`'s own state change — and then bounces the entire trigger back to the user.
6. Every subsequent trigger to `AA_HUB` that includes `AA_C` in the fan-out repeats this outcome, permanently preventing `AA_A` and `AA_B` (and their users) from ever receiving their share of the distribution while `AA_C` remains part of the routing.
