### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` triggers unauthorized merge queue advancement - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by bare SHA (`Commit.where(sha: params.sha)`) instead of using the `Handler#stacks`/`repository_name` scoping that every other handler in `app/models/shipit/webhooks/handlers/` relies on. Because GitHub webhook signature verification only proves that the payload's `repository.owner.login` matches the app/organization that signed it — not that the `sha` field belongs to that repository — an attacker who owns a repository sharing commit history with a victim stack (a fork, a mirrored repo, or any Shipit `Repository`/`Stack` tracking the same git objects) can write a `success` status for `context: ci/build` onto the victim's `Commit` record, and if `merge_queue_enabled` is `true` on the victim stack this directly triggers `Stack#schedule_merges` → `MergeRequest#merge!`.

### Finding Description
The broken binding: the code implicitly assumes `Commit(sha: params.sha).stack == Repository(repository_owner_from_signed_payload).stacks`, but nothing enforces this equality.

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the HMAC signature is valid for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body (`params.dig('repository','owner','login')`, line 61). This proves the payload was signed by *some* GitHub App belonging to the org that owns *the repository named in the payload* — it says nothing about which SHAs that repository is allowed to reference.
- Every other handler scopes its side effects through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), i.e., it binds writes to the repository that authenticated the request.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) never calls `stacks` or checks `repository_name`. It does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This matches **every** `Commit` row across **every** stack/repository in the installation that happens to share that 40-character SHA — a certainty for forks/mirrors sharing history, and possible for any repository containing identical commit objects.
- `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:366-386`) writes the new status and, when `new_status.success?`, calls `stack.schedule_merges` (line 383).
- If the victim stack has `merge_queue_enabled: true`, `MergeRequest.schedule_merges` (`app/models/shipit/merge_request.rb:109-111`) enumerates such stacks and advances the queue; a head commit whose statuses now include a forged `ci/build success` can satisfy `MergeRequest#all_status_checks_passed?`/`any_status_checks_missing?` (lines 193-206), letting `MergeRequest#merge!` (lines 164-191) call `stack.github_api.merge_pull_request` against the victim's real GitHub repository.

Attacker's request: a signed `status` webhook (`X-Github-Event: status`) with `repository.owner.login` = attacker's own org/user (so `verify_signature` passes with the attacker's legitimately-owned app secret), body `{"sha": "<shared-sha>", "state": "success", "context": "ci/build", "repository": {"owner": {"login": "attacker"}, ...}}`. No Shipit session, API token, or victim secret is required.

Existing guards do not stop this: `verify_signature` validates signer identity, not SHA ownership; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `StatusHandler` only validates types, not repository scope; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant since webhooks bypass session auth entirely.

### Impact Explanation
An attacker who controls (or forks) a repository whose commit history overlaps with a victim's Shipit-tracked repository can forge a `ci/build success` status that lands on the victim's `Commit` record instead of their own. On a stack with `merge_queue_enabled: true` and `ci/build` in its required statuses, this can push a pull request through `MergeRequest#merge!`, causing GitHub to merge attacker-influenced or unvetted code, or block a legitimate deploy by corrupting the commit's status timeline — this is a payload for one repository mutating another repository's commit/merge-queue state, matching the Critical "unauthorized deploy, rollback or merge" / "payload for one repository mutating another's stack, commit, task or team" category.

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled: true` and requires `ci/build`; a SHA collision exists between an attacker-owned repository and the victim's tracked repository (trivially achievable via forking, since forks retain identical SHAs for all commits up to the fork point, and many organizations' Shipit-tracked repos have forks or mirrors). Attacker cost is a single HTTP POST to `/webhooks`, signed with a secret the attacker legitimately possesses for their own registered repository/org — no privileged Shipit role or secret needed. The action is repeatable against any SHA shared with any victim stack, so blast radius scales with however many repositories in the installation share git history.

### Recommendation
Scope `StatusHandler#process` (and `create_status_from_github!`) to the repository that authenticated the webhook, mirroring `Handler#stacks`: restrict the `Commit.where(sha: params.sha)` lookup to `stacks.flat_map(&:commits)` (i.e., commits belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), rather than a bare cross-tenant SHA match.

### Proof of Concept
minitest plan (no live GitHub):
```ruby
test "status webhook from unrelated repo cannot flip status of a shared-SHA commit on a merge_queue_enabled victim stack" do
  victim_repo  = shipit_repositories(:shipit) # owner/name = "shopify/shipit-engine"
  victim_stack = create_stack(repository: victim_repo, merge_queue_enabled: true)
  shared_sha   = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared history commit")

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/build',
    'repository' => { 'full_name' => 'attacker/forked-repo', 'owner' => { 'login' => 'attacker' } }
  }

  # binding under test: commit's stack must equal the stack of the repository that authenticated the payload
  assert_not_equal victim_stack.repository.full_name, attacker_payload['repository']['full_name']

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  # currently FAILS: victim_commit.status flips to success even though 'attacker/forked-repo' never
  # authenticated a status for 'shopify/shipit-engine'
  assert_not_equal 'success', victim_commit.status.state
end
```
