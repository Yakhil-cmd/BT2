### Title
Membership webhook forgery via cross-organization webhook-secret mismatch escalates arbitrary GitHub identities into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using the organization derived from the *payload itself* (`repository.owner.login` or `organization.login`), but the handler that actually grants team membership (`MembershipHandler`) trusts a **separately-read** field of that same payload (`params.organization.login` / `params.team.id`) to decide which `Team` a `member` is added to. Because both fields are attacker-controlled body content and neither is cross-checked against the other, an attacker who legitimately owns/administers **any one** of the organizations configured in Shipit's multi-org `github:` config can sign a payload with their own `webhook_secret` while making the payload claim to be a `membership` event for a **different, victim organization's team** — including a team that is a member of `Shipit.github_teams` and thus gates authentication/authorization (`User#authorized?`).

### Finding Description
`Shipit.github(organization:)` is a per-organization registry of GitHub Apps, each with its own `webhook_secret` (multi-org config documented in `config/secrets.development.example.yml:18-38`). The signature check is: [1](#0-0) [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read straight out of the untrusted JSON body, so the attacker fully controls which organization's `webhook_secret` (`lib/shipit/github_app.rb:76-83`, `verify_webhook_signature`) is used to validate their own signature. Since they only need to know *their own* organization's secret (the one they legitimately administer), the signature check passes for a payload they crafted.

Downstream, `MembershipHandler` performs the actual authorization-affecting mutation, and it reads the organization/team binding from **the same payload**, independently of `repository_owner`: [2](#0-1) 

```ruby
class MembershipHandler < Handler
  params do
    requires :action, String
    requires :team do
      requires :id, Integer
      ...
    end
    requires :organization do
      requires :login, String
    end
    requires :member do
      requires :login, String
    end
  end
  def process
    team = find_or_create_team!
    member = User.find_or_create_by_login!(params.member.login)
    case params.action
    when 'added'
      team.add_member(member)
    ...
    end
  end

  private

  def find_or_create_team!
    Team.find_or_create_by!(github_id: params.team.id) do |team|
      team.github_team = params.team
      team.organization = params.organization.login
    end
  end
end
```

`Team.find_or_create_by!(github_id: params.team.id)` binds purely on the numeric `team.id` (a GitHub team ID, which is discoverable/enumerable, not secret), not on which org's secret validated the request. If that `github_id` already matches an existing `Team` record that is part of `Shipit.github_teams` (`lib/shipit.rb:256-258`, `github_teams` maps `github.oauth_teams` handles to `Team` rows), `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) unconditionally appends the attacker-chosen `member` (any GitHub login, auto-vivified via `User.find_or_create_by_login!`) to that team.

This breaks exactly the trust binding the rules call out: **the organization that authenticated (via `repository_owner`/its `webhook_secret`) is not the organization actually written (`params.organization.login`, and more importantly the `github_id`-keyed `Team` that is mutated)**. The signature only proves "a holder of org A's secret sent this", but the mutation is applied to org B's team.

`User#authorized?` (`app/models/shipit/user.rb:80-82`) is:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
```
So once the forged membership is created, any GitHub login the attacker names in `member.login` becomes `authorized?` on the next login through `GithubAuthenticationController#callback` → `User.find_or_create_from_github` (`app/controllers/shipit/github_authentication_controller.rb:30-34`), bypassing the team-based access gate enforced in `Authentication#force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`).

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization achieved purely by forging a webhook payload using a secret the attacker legitimately possesses for an *unrelated* organization configured on the same Shipit instance. It grants access to the full authenticated Shipit UI/API (stacks, deploys, rollbacks, API client management) for an arbitrary GitHub identity chosen by the attacker, without any repository write access or privileged credential to the victim organization. This matches the specified High-severity bucket: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-org `github:` schema (documented and supported feature), (2) the attacker legitimately controls at least one of the configured organizations/GitHub Apps (and thus its `webhook_secret`), and (3) knowledge of the target team's numeric GitHub `id` (discoverable via the GitHub API/UI for any team, not a secret). Given these are realistic conditions for a multi-tenant Shipit deployment, likelihood is moderate to high in that specific deployment shape; it does not apply to single-org Shipit installs where only one `webhook_secret`/organization exists.

### Recommendation
In `WebhooksController#verify_signature`, after determining `github_app` from `repository_owner`, re-validate that every organization-identifying field actually used by handlers (`repository.full_name`'s owner, `organization.login`, `team`'s parent org) is consistent with `repository_owner`/the app that validated the signature, and reject mismatches. Additionally, in `MembershipHandler#find_or_create_team!`, scope the `find_or_create_by!` lookup/creation by both `github_id` **and** `organization` (verified against the authenticating app's organization), and reject processing if `params.organization.login` does not match the organization whose secret validated the webhook.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` (attacker is an org owner, knows its `webhook_secret`) and `victim-org` (contains a team `victim-org/admins` with GitHub team id `999`, already synced into Shipit as a `Team` and referenced in `Shipit.github_teams`).
2. Attacker crafts a JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` and sets `X-Hub-Signature` and `X-Github-Event: membership`, then POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s app, and successfully verifies the signature (`lib/shipit/github_app.rb:76-83`).
5. `MembershipHandler#process` runs, finds `Team` with `github_id: 999` (the victim admins team), and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, adding the attacker's GitHub identity to the victim's authorized team.
6. Attacker logs into Shipit via GitHub OAuth with `attacker-github-login`; `User#authorized?` now returns true because `teams` includes the victim's admin team, granting full authenticated access.

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login

        end
