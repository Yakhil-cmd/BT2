### Title
Cross-tenant Team hijack via `MembershipHandler#find_or_create_team!` looking up `Team` by unscoped `github_id` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves and mutates a `Team` purely by `params.team.id` (`github_id`), with no binding to the organization whose secret actually verified the webhook. Any organization configured as a legitimate multi-tenant GitHub App in Shipit (each with its own `webhook_secret`, per `docs/setup.md` "Using Multiple Github Applications") can sign a `membership` webhook naming a `team.id` that belongs to a *different* org, and get itself added as a member of that pre-existing `Team` record, which can escalate to `Shipit.github_teams` authorization.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`Team(github_id = X).organization` (real GitHub owner of team X) `==` `organization.login of the webhook signer whose secret verified this request`

`WebhooksController#verify_signature` selects which `GitHubApp`/secret to verify with, from the very same untrusted payload field: [1](#0-0) [2](#0-1) 

This only proves the request was signed by *whatever org's secret is named in `organization.login`* - it says nothing about which real GitHub team `params.team.id` belongs to. `MembershipHandler` then trusts `params.team.id` alone to resolve/create the `Team`, and only sets `team.organization` on first creation (skipped entirely if the row already exists): [3](#0-2) 

The `teams` table enforces uniqueness only on `(organization, slug)`, not on `github_id`: [4](#0-3) 

So if a `Team` row for `github_id = X` already exists (e.g. created earlier for the victim org via `Team.find_or_create_by_handle`, which is how `Shipit.github_teams` entries are populated): [5](#0-4) [6](#0-5) 

...an attacker who legitimately administers a *different*, Shipit-configured GitHub App installation (`attacker-org`, with its own real `webhook_secret`) can send a `membership` "added" event whose `team.id` equals the victim team's `github_id` and whose `member.login` is the attacker's own login. `verify_signature` succeeds (the signature genuinely matches attacker-org's secret), `find_or_create_by!(github_id: X)` finds the pre-existing victim `Team`, and `team.add_member(member)` adds the attacker as a member: [7](#0-6) [8](#0-7) 

`User#authorized?` checks membership purely through this `Team`/`Membership` association against `Shipit.github_teams.map(&:id)`, with no re-verification against GitHub of who is actually on the real team: [9](#0-8) 

No existing guard closes this gap: `verify_signature` only proves "this org's secret signed this body," `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields (`requires :id, Integer`, etc.), and there is no cross-check that `params.team.id` is actually owned by `params.organization.login`, nor that the resolved `Team.organization` matches `repository_owner`/the org that signed the request.

### Impact Explanation
An attacker who legitimately controls one Shipit-configured GitHub App tenant can add their own GitHub login as a "member" of a `Team` record belonging to a different tenant, without ever touching the victim org's real GitHub team membership. If that `Team` is referenced by `Shipit.github_teams` (i.e., listed in `github.oauth.teams`), the attacker gains `User#authorized?` == true and full access to the Shipit UI/app as an "authorized" user — an escalation into `Shipit.github_teams` authorization (High per the rubric), and depending on downstream permission checks tied to team membership, potentially broader. This is repeatable for any `github_id` the attacker can guess or discover (team IDs are small sequential integers, and often visible via GitHub's public API), against any tenant sharing the same Shipit instance.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations, each with a real `webhook_secret` (a documented, supported configuration per `docs/setup.md`), and the attacker being a legitimate operator/admin of one of those secondary orgs' GitHub App installations; (2) knowledge or a guess of a victim team's `github_id` referenced in `Shipit.github_teams`. Given GitHub team IDs are low-entropy sequential integers and often discoverable, and the attacker needs no Shipit credentials, session, or the victim org's secret at all, this is feasible and cheaply repeatable once the multi-tenant precondition holds.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the `Team` lookup by both `github_id` and `organization` (i.e. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` matches `repository_owner`/the org whose secret verified the webhook (already computed in `WebhooksController`) before mutating any `Team`. Consider also enforcing a unique index on `(organization, github_id)` and rejecting membership events where an existing `Team` with that `github_id` has a different `organization`.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new membership-specific test), configuring two orgs each with a real `webhook_secret` (mirroring `test/dummy/config/secrets_double_github_app.yml`):
1. Seed victim `Team` fixture with `organization: 'victim-org'`, `github_id: 999`, included in `Shipit.stubs(:github_teams).returns([victim_team])`.
2. Compute a valid `X-Hub-Signature` using `attacker-org`'s configured `webhook_secret` over a `membership` payload: `{ action: 'added', team: { id: 999, name: 'Victim Team', slug: 'victim', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'attacker' }, repository: { owner: { login: 'attacker-org' } } }`.
3. POST to `/webhooks` with `X-Github-Event: membership` and that signature; assert `response.status == 200`.
4. Assert `Membership.exists?(team: victim_team, user: User.find_by(login: 'attacker'))` is true, and `attacker_user.authorized?` (with `Shipit.github_teams` including `victim_team`) is `true` — proving cross-tenant `Team` mutation and authorization escalation from a payload the victim org never signed.
