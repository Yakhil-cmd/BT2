### Title
Second-Preimage / Node-as-Leaf Attack in Merkle Proof Verification Enables Forged Membership Proofs - (File: merkle.js)

### Summary
`merkle.js` builds Merkle trees and verifies proofs using the same `hash()` function for both leaf hashing and internal-node hashing, with no domain-separation prefix distinguishing leaves from internal nodes. This is the exact "second-preimage"/"node-as-leaf" weakness referenced in the external report: an attacker who knows two sibling hashes at any level of the tree can submit their concatenation as a forged "leaf" element and produce a valid Merkle proof for it, even though that value was never one of the original committed elements.

### Finding Description
`getMerkleRoot`/`getMerkleProof` hash leaves with `hash(element)` and hash internal nodes with `hash(left_hash + right_hash)`, using the identical `hash()` primitive for both: [1](#0-0) [2](#0-1) 

`verifyMerkleProof` starts from `hash(element)` and repeatedly combines it with the supplied siblings up to the root, comparing the final value to `proof.root`. The developers' own comment flags the exact issue: "Node-as-Leaf issue might matter in some cases": [3](#0-2) 

Because there is no leaf/node prefix (e.g., `0x00` for leaves, `0x01` for internal nodes as recommended in the referenced OpenZeppelin standard), any two adjacent hash values `h1`, `h2` inside the tree can be concatenated into a string `h1+h2`. Submitting `element = h1+h2` together with the sibling path starting one level above `h1`/`h2` will pass `verifyMerkleProof`, because `hash(element)` equals the internal node hash that would have been computed from `h1` and `h2` during normal tree construction. This lets an attacker construct a valid Merkle inclusion proof for a value that was never one of the tree's original leaves.

This primitive is reachable from two independent, permissionless surfaces:
1. The `'in merkle'` address-definition authentifier, which any unit poster satisfies by supplying a serialized proof as an authentifier; the proof is deserialized and verified with the same vulnerable function, and if valid, its root is checked against a published `data_feed` value: [4](#0-3) 
2. The `is_valid_merkle_proof(element, proof)` oscript/AA function, callable by any AA trigger sender with attacker-controlled `element` and `proof` arguments, which similarly calls `merkle.verifyMerkleProof`: [5](#0-4) 

### Impact Explanation
Both the `'in merkle'` authentifier (used in address definitions to gate spending authority, e.g., membership/whitelist/attestation lists published via data feeds) and `is_valid_merkle_proof` (used inside AA oscript logic to gate fund release, e.g., whitelists, allocation lists, claim lists) rely on the assumption that only the originally committed leaves can produce a valid proof. The second-preimage weakness breaks that assumption: an attacker can forge a "member" value equal to the concatenation of two known internal hashes and obtain a valid proof for it. Depending on how the AA or address-definition author intends to use the tree (e.g., "is this address/claim-index/amount combination in the whitelist"), this can let an unauthorized party satisfy the `'in merkle'`/`is_valid_merkle_proof` condition and unlock address-controlled funds or AA-held funds that should have been restricted to genuine leaves — i.e., unauthorized spending or AA fund loss.

### Likelihood Explanation
The tree's sibling hashes needed to mount the forgery are exactly the data an honest prover must reveal as part of any legitimate Merkle proof for elements near the target node, and Merkle roots/trees are commonly published in full or partially inspectable form (e.g., IPFS/data feeds) for whitelist verification use cases. Any unprivileged unit poster or AA trigger sender can attempt the forgery without any special privileges — they only need to know two adjacent hash values, which are visible in any other party's legitimate proof or in a full tree dump. The likelihood scales with how the merkle tree/root is used by application authors (address definitions, AAs) which is out of ocore's control, but the primitive itself is exploitable by design without protocol-level restriction.

### Recommendation
Add domain separation between leaf and internal-node hashing in `merkle.js`, e.g.:
```js
function hashLeaf(str){ return crypto.createHash("sha256").update("\x00"+str, "utf8").digest("base64"); }
function hashNode(left, right){ return crypto.createHash("sha256").update("\x01"+left+right, "utf8").digest("base64"); }
```
Use `hashLeaf` when hashing `arrElements` in `getMerkleRoot`/`getMerkleProof`, and `hashNode` for combining child hashes in both tree construction and `verifyMerkleProof`. This prevents an internal node's hash from ever being reachable via `hashLeaf(element)` for any attacker-chosen `element`, closing the second-preimage/node-as-leaf attack for both the `'in merkle'` authentifier and `is_valid_merkle_proof`.

### Proof of Concept
1. Build a tree with `merkle.getMerkleRoot(arrElements)` where `arrElements.length >= 4` (to guarantee an internal level exists below the root).
2. Compute `h1 = hash(arrElements[0])`, `h2 = hash(arrElements[1])` (the same `hash` primitive as in `merkle.js`).
3. Construct a forged proof: `{ index: 0, siblings: [<sibling(s) of the parent node at higher levels>], root: <actual tree root> }`.
4. Call `merkle.verifyMerkleProof(h1 + h2, forgedProof)`.
5. The function returns `true`, i.e., proves membership for the string `h1+h2`, which is not a member of the original `arrElements` set — demonstrating the second-preimage forgery reachable via `definition.js`'s `'in merkle'` op and via oscript's `is_valid_merkle_proof`.

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
