Cross-repository/cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the commit's `stack`/repository matches the `repository` named in the inbound webhook payload. In a multi-organization Shipit deployment (the documented "Using Multiple Github Applications" mode), any of the several distinct, independently-signing GitHub orgs configured on the instance can post a validly-signed `status` webhook whose `sha` happens to also exist as a commit in a *different* org's stack, and that other stack's commit will silently receive the forged `Status` row.

### Finding Description
The claimed binding is: `CI provider authorized for victim repo's stack == org whose webhook_secret signed the stored Status`. Tracing the code shows this binding is **not enforced** at the commit-resolution step.

- `WebhooksController#verify_signature` at [1](#0-0)  resolves `Shipit.github(organization: repository_owner)` from the **payload's own** `repository.owner.login` field [2](#0-1)  and checks the signature against that org's `webhook_secret`. This only proves the payload was signed by *some* org configured in this Shipit instance — the one the payload itself claims to be from. It does not bind the request to the repository of the commit that ends up being mutated.
- `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This query is **global across all stacks/repositories** — it is not scoped to the repository named in the payload, nor to the org whose secret validated the signature.
- `Commit#create_status_from_github!` then persists the state using the **found commit's own** `stack_id`, not any org/repo derived from the payload:
```
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 
`Status.replicate_from_github!` writes `stack_id:, state:, description:, target_url:, context:, created_at:` [5](#0-4)  with no repository/org validation at all.
- `Commit#status` computes state via `Status::Group.compact` over `statuses_and_check_runs` [6](#0-5) , and with zero prior statuses `Status::Group.compact` returns `Status::Unknown.new(commit)` [7](#0-6) . A single forged `success` row flips this to `success?` true.
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [8](#0-7) , so a fresh victim commit with zero real CI signal becomes deployable purely from the forged cross-repo status.

**Exploit path**: In a shared Shipit instance configured for multiple GitHub organizations (per `docs/setup.md` "Using Multiple Github Applications" and the schema in `lib/shipit.rb` `github_app_config`), an attacker who controls/administers a distinct, unrelated org "OrgAttacker" that is legitimately onboarded to the same Shipit instance (with its own `webhook_secret` known to the attacker for their own org's app) can send `POST /webhooks` with `X-Github-Event: status`, a validly-computed `X-Hub-Signature` for OrgAttacker's secret, and a payload whose `sha` matches a commit sha that also exists in a victim's (OrgVictim's) stack — for example a commit shared via a fork of a public repo, cherry-picked/rebased history producing an identical content-addressed SHA, or simply a commit sha collision engineered by controlling the exact tree/parent/author/committer/message/timestamps of a commit pushed to the attacker's own repo. `verify_signature` passes (the signature is valid for OrgAttacker), but `StatusHandler#process` looks up `Commit.where(sha: ...)` globally and applies the forged `success` status to the victim's `Commit` row belonging to OrgVictim's stack.

No existing guard prevents this: `verify_signature` only authenticates that the payload came from *an* org configured on the instance, not that it applies to a commit within that org's own stacks; `drop_unhandled_event` and `ExplicitParameters` schema on `StatusHandler` only validate shape (`sha`, `state`, etc.), not ownership; there is no `stack_id`/`repository.full_name` filter anywhere in the lookup or write path.

### Impact Explanation
An attacker with a legitimately-provisioned, unrelated tenant/org on a shared Shipit instance can write a `Status` record for a repository/commit they did not authenticate for, turning an unreviewed, CI-less commit into `deployable?`, which — combined with continuous deployment (`stack.continuous_deployment?`) or an operator triggering deploy — leads to an unauthorized deploy of code that never passed the victim's actual CI. This matches "Critical: a payload for one repository mutating another's stack/commit... or an unauthorized deploy." Blast radius is any stack in the same Shipit instance sharing the target sha; the attacker's cost is a single signed HTTP request per target commit, fully repeatable.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured in multi-org mode with the attacker owning/administering one of the configured orgs (a documented, supported configuration for organizations that host multiple tenants on one Shipit instance) — a real but non-default precondition; (2) a sha collision between the attacker's own repository and the victim's, which is feasible via forks of public repos sharing history, or by crafting a commit object with identical content/metadata. In single-org Shipit deployments this specific vector does not apply since there's only one webhook secret and one authorized org, though the unscoped `Commit.where(sha:)` lookup remains a latent design weakness that this multi-tenant misconfiguration turns into an exploitable cross-tenant primitive.

### Recommendation
Scope the commit lookup and status application to the repository named in the payload: resolve the target repository from the webhook's `repository.full_name` (already validated via `verify_signature`'s organization derivation) and restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository` matches that `full_name`/org, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })`, before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, illustrative — actual file under `test/**` is out of scope for remediation but described here for validation):
1. Create two stacks/orgs, `victim_stack` (org "Victim") and `attacker_stack` (org "Attacker"), both configured in `secrets.github` multi-org style with distinct `webhook_secret`s.
2. Create `victim_commit` in `victim_stack` with sha `S`, zero `Status` rows.
   - `assert_equal 'unknown', victim_commit.status.state`
   - `refute victim_commit.deployable?`
3. Create a second commit row with the same sha `S` under `attacker_stack` (simulating shared history/sha collision), or directly craft a `status` webhook payload with `sha: S`, `repository.full_name: "attacker/repo"`, `repository.owner.login: "Attacker"`, `state: "success"`.
4. Compute `X-Hub-Signature` using Attacker's own `webhook_secret` (attacker's legitimately-known secret for their own org).
5. `post :create` to `/webhooks` with `X-Github-Event: status`, the signature header, and the payload.
6. Assert response is `:ok`/`:no_content` (signature verification passes for Attacker org).
7. Reload `victim_commit`:
   - `assert_equal 'success', victim_commit.reload.status.state` (forged cross-org status applied)
   - `assert victim_commit.deployable?`

This demonstrates the binding "CI provider authorized for victim's repo == org whose secret signed the stored Status" does **not** hold: the Status was signed and authorized only for Attacker's org, yet stored against Victim's stack/commit.
