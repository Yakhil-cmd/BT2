### Title
Signed order-book packages are not bound to the deploying AA address, enabling cross-instance signature replay — (File: `test/samples/order_book_exchange.oscript`, `formula/evaluation.js`, `signed_message.js`)

### Summary
The `is_valid_signed_package` opcode [1](#0-0)  and the underlying `signed_message.js` validation logic [2](#0-1)  verify only that a `signed_message` package was signed by a given address — they never bind the package to the specific AA address (`this_address`) that is consuming it. The shipped `order_book_exchange.oscript` template relies on this primitive to authorize trades but never includes `this_address` (or any other contract-identifying value) in the signed order fields or in the `if` condition that validates the order [3](#0-2) . As a result, a signed order intended for one deployment of this AA template can be replayed against any other deployment of the same template, exactly mirroring the `AffiliateValidator.addKey` issue where a signature meant for one contract instance could be reused on another because the contract address was not part of the signed hash.

### Finding Description
`is_valid_signed_package(package, address)` only checks:
1. that `package` is a well-formed signed-message object,
2. that it was signed by `address`,
3. that its `last_ball_unit` (if present) is stable at or before the current mci.

It performs no check that the package was created for the AA instance now evaluating it. The AA author is expected to embed an instance identifier (typically `this_address`) inside `signed_message` and check it explicitly — this is exactly what the sibling sample `payment_channels.oscript` does:
```
if (trigger.data.sentByPeer.signed_message.channel != this_address)
    bounce('signed for another channel');
``` [4](#0-3) 

The `order_book_exchange.oscript` template omits this protection entirely. The order identifier and validity checks are:
```
$id1 = sha256($order1.address || $order1.sell_asset || $order1.buy_asset || $order1.sell_amount || $order1.price || trigger.data.order1.last_ball_unit);
...
if (!is_valid_signed_package(trigger.data.order1, $order1.address)
    OR !is_valid_signed_package(trigger.data.order2, $order2.address))
    return false;
``` [5](#0-4) 

None of `$order1.address`, `sell_asset`, `buy_asset`, `sell_amount`, `price`, or `last_ball_unit` is specific to a particular AA deployment — a user who signs an order for one order-book AA instance produces a signature that is equally valid input for `is_valid_signed_package` in any other AA instance built from the same template, because `signMessage`/`validateSignedMessage` hash only the message content and author info, never the verifying AA's own address [6](#0-5) .

### Impact Explanation
Any trader who deposits balance and signs an order for one deployed order-book AA can have that exact signed order re-submitted as a counter-order against a different deployment of the same order-book template in which the trader also holds a balance in the same asset pair. Because the AA's internal state (`var[$sell_key]`, `var[$buy_key]`) is looked up per-deployment but the signature says nothing about which deployment it authorizes, the trade executes against the victim's balance in the second AA without the victim ever intending or re-signing an order for that market. This causes unauthorized spending of the victim's on-chain balance held by the AA (loss of funds) — directly analogous to the "obtain valid keys without going through the mandatory KYC process" impact in the original report, here manifesting as "execute a trade the user never authorized for that specific market/instance."

### Likelihood Explanation
The `order_book_exchange.oscript` file is a shipped sample template, so any deployer instantiating multiple copies of it (e.g., for different fee tiers, different UIs, or accidental re-deployment) recreates the vulnerable condition with no additional attacker effort beyond obtaining a previously broadcast/negotiated signed order (orders are typically exchanged off-chain between counterparties before being submitted on-chain, making capture straightforward for a counterparty or anyone the order was shared with).

### Recommendation
Bind every `signed_message` package consumed by an AA to that AA's own address by requiring `this_address` (or another AA/session-specific identifier) inside the signed fields, and check it explicitly before accepting the order — the same pattern already used in `payment_channels.oscript`'s `channel != this_address` check. More robustly, consider extending `signed_message`'s canonical hash (`getSignedPackageHashToSign` in `object_hash.js`) or the `is_valid_signed_package` opcode itself to optionally take/require a domain-separation value bound to the verifying address, so templates cannot omit this protection by omission.

### Proof of Concept
1. Deploy the `order_book_exchange.oscript` template twice, as AA₁ and AA₂ (identical bytecode, different addresses), both trading asset X/Y.
2. Trader Alice deposits balance of asset X into both AA₁ and AA₂ (e.g., via the "silently accept coins" case) [7](#0-6) .
3. Alice signs an order `{address: Alice, sell_asset: X, buy_asset: Y, sell_amount: N, price: P}` together with a `last_ball_unit`, intending it to be filled only on AA₁, and sends the signed package to a market maker Bob.
4. Bob submits Alice's exact signed package as `trigger.data.order1` to AA₂ paired with his own counter-order.
5. AA₂'s `is_valid_signed_package(trigger.data.order1, $order1.address)` passes because the signature is valid and the address matches — nothing in the check references AA₂ specifically [8](#0-7) .
6. The trade executes against Alice's balance in AA₂, which she never authorized for that market/instance, resulting in unauthorized spending of her deposited funds.
