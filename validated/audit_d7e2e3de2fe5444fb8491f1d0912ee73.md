### Title
`NonTransfer` proxy can escalate to `SudoBalances` via broken `ProxyType::is_superset`/`filter` lattice, bypassing the "Sudo pallet omitted" restriction - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
On Polkadot Westend (and the identical staking-async RC test runtime), `ProxyType::NonTransfer` explicitly excludes `pallet_sudo` and `pallet_balances` from its `filter`, but `is_superset` unconditionally claims `NonTransfer` is a superset of every other `ProxyType` (including `SudoBalances`). Because `pallet_proxy::do_proxy` authorizes `add_proxy`/`remove_proxy` purely via `is_superset` (not `filter`), a `NonTransfer` delegate can grant itself (or an accomplice) a `SudoBalances` proxy over the delegator, then use that new proxy to invoke `Sudo::sudo{ call: Balances(..) }` on the delegator's behalf — exactly the class of bug already identified and fixed for `NonTransfer`→`Governance` in [1](#0-0)  but left unfixed for `SudoBalances`.

### Finding Description
`pallet_proxy::Pallet::do_proxy` gates the ability of a proxy to add/remove another proxy on `is_superset`, independent of `filter`: [2](#0-1) 

On Westend, the `ProxyType` enum and its `InstanceFilter` impl are: [3](#0-2) 

`NonTransfer`'s filter deliberately omits Sudo and Balances: [4](#0-3) 

`SudoBalances`'s filter admits `Sudo::sudo{ call: Balances(..) }` and `Utility`: [5](#0-4) 

But `is_superset` collapses to "`NonTransfer` is a superset of everything except `Any`": [6](#0-5) 

This is the identical bug pattern that was found and fixed for `NonTransfer` vs `Governance` on Asset Hub Westend, where the fix comment explains the invariant that must hold: a proxy type declaring itself a superset of another must actually admit every call that the other type admits, otherwise "the smaller type is reachable as an escalation" via `add_proxy`: [7](#0-6) [8](#0-7) 

That fix (`is_superset(NonTransfer, Governance) = false`) was applied on Asset Hub, but the identical `NonTransfer`/`SudoBalances` lattice violation on the relay-chain Westend runtime (and the equivalent staking-async `rc` test runtime) was never addressed — there is no `SudoBalances`-specific carve-out in `is_superset`, and no regression test exists for it (confirmed absent via search of `polkadot/runtime/westend` and `substrate/frame/staking-async/runtimes/rc`).

The attack path, mirroring the CVE-2021-43858 pattern (a restricted API call being used to grant broader policy than intended because the authorization check doesn't match the actual capability being requested):
1. The Sudo key holder ("real") grants a `NonTransfer` proxy to a delegate for routine, restricted tasks (identity, vesting, staking, etc.), explicitly *not* including Balances or Sudo.
2. The `NonTransfer` delegate calls `Proxy::proxy(real, None, Proxy::add_proxy{ delegate: attacker, proxy_type: SudoBalances, delay: 0 })`. This inner call is filtered by `do_proxy`'s closure: since `Call::add_proxy{ proxy_type: SudoBalances }` matches, the guard checks `!def.proxy_type.is_superset(&SudoBalances)`, which is `!true = false`, so the call is **not** filtered out and is admitted (`NonTransfer.filter` itself also independently allows `RuntimeCall::Proxy(..)` in full).
3. `attacker` now holds a `SudoBalances` proxy over `real`.
4. `attacker` calls `Proxy::proxy(real, None, Sudo::sudo{ call: Balances::force_set_balance/transfer_allow_death(..) })`. `SudoBalances.filter` admits this call, so `do_proxy` dispatches `Sudo::sudo{..}` with `origin = Signed(real)`.
5. Inside `pallet_sudo::sudo`, the origin check succeeds because the signer *is* `real`, and `real == Self::key()` (the sudo key holder), per the pallet's documented behavior: it only checks the caller matches the stored key, then bypasses all further origin/filter checks via `dispatch_bypass_filter`.
6. The `Balances` call executes with `Root` origin, letting `attacker` move/mint/burn `real`'s (or anyone's) funds — capabilities the `NonTransfer` proxy relationship was explicitly designed to deny. [9](#0-8) 

### Impact Explanation
If the account that holds the Westend Sudo key ever grants a `NonTransfer` proxy (a normal, "restricted/low-trust" delegation intended to exclude fund movement and privileged pallets), the delegate can silently escalate to full `Root`-level `Balances` control over the sudo key's funds via the `SudoBalances` proxy type — theft/unbacked movement of funds and a clear violation of the delegation's documented trust boundary ("Specifically omitting Sudo pallet" / "Specifically omitting the entire Balances pallet"). This is the same bug class Parity already classified as worth a runtime patch for the `Governance` case (PR referenced by `prdoc/pr_12769.prdoc`), just left open for `SudoBalances`.

### Likelihood Explanation
Requires only that: (a) the Sudo-key-holding account has, or ever will, grant a `NonTransfer` proxy to some delegate — a normal, expected administrative pattern on a testnet like Westend where the sudo key is actively used for governance/maintenance actions — and (b) the delegate is malicious or compromised. No governance, root, or validator/collator compromise is needed; the delegate uses only its already-granted (lower-trust) proxy permission through the public, permissionless `pallet_proxy::proxy` extrinsic.

### Recommendation
Mirror the fix already applied for `NonTransfer` vs `Governance` (`prdoc/pr_12769.prdoc`): make `ProxyType::is_superset` for Westend (and the `rc` staking-async test runtime) consistent with `filter` — i.e., `NonTransfer.is_superset(SudoBalances)` must be `false`, since `NonTransfer.filter` does not admit the `Sudo`/`Balances` calls that `SudoBalances.filter` admits. More generally, add (or extend) the whole-lattice regression test (`proxy_type_superset_relation_matches_call_filters`) from `asset-hub-westend`'s test suite to `polkadot/runtime/westend` and `substrate/frame/staking-async/runtimes/rc` to prevent this class of bug from recurring for any `ProxyType` pair.

### Proof of Concept
Not executed against a live network. A minimal FRAME integration reproduction would use `polkadot/runtime/westend`'s mock/test harness (or a `hypothetically!`/`ExtBuilder` pattern as used in the sibling `asset-hub-westend` regression tests) to:
1. Set `real` as the account with `pallet_sudo::Key = real`.
2. `Proxy::add_proxy(real, attacker, ProxyType::NonTransfer, 0)`.
3. `Proxy::proxy(attacker, real, None, Proxy::add_proxy{ delegate: attacker2, proxy_type: SudoBalances, delay: 0 })` and assert it succeeds (`ProxyExecuted{ result: Ok(()) }`), demonstrating the escalation guard is bypassed.
4. `Proxy::proxy(attacker2, real, None, Sudo::sudo{ call: Balances::force_set_balance{ who: attacker2, new_free: X } })` and assert the balance change occurs.

This reproduction was not executed in this session; it is derived purely from static analysis of `pallet_proxy::do_proxy`, the Westend `ProxyType` implementation, and `pallet_sudo`'s origin check, following the exact precedent/pattern of the already-fixed `NonTransfer`↔`Governance` escalation. I could not verify at this time whether Westend's current live Sudo key holder is a single externally-controlled key, a multisig, or already `Root`-restricted in practice (governance-only), which would affect real-world exploitability; this would need confirmation against live chain state/genesis config, which is outside the scope of static code search.

```rust
/// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `ProxyType::is_superset`, so a
/// proxy type that *declares* itself a superset of another must also *admit* every call that other
/// type admits. Otherwise the "smaller" type is reachable as an escalation: the declared superset
/// can grant itself the subset proxy and thereby gain permissions its own filter denies.
///
/// This checks that property across the whole lattice rather than a single pair, so the class of
/// bug cannot silently reappear on another edge.
#[test]
fn proxy_type_superset_relation_matches_call_filters() {
	use frame_support::traits::InstanceFilter;

	let calls = representative_proxy_calls();

	for superset in all_proxy_types() {
		for subset in all_proxy_types() {
			if !superset.is_superset(&subset) {
				continue;
			}

			for call in calls.iter() {
				if subset.filter(call) {
					assert!(
						superset.filter(call),
						"lattice violated: {superset:?} declares itself a superset of {subset:?}, \
						 but rejects {call:?} which {subset:?} admits",
					);
				}
			}
		}
	}
}
```

```rust
/// Regression test for <https://github.com/paritytech/polkadot-sdk/issues/12724>.
///
/// `NonTransfer` used to claim `Governance` as a subset while denying the `Treasury`,
/// `ConvictionVoting`, `Referenda` and `Whitelist` calls that `Governance` admits, which let a
/// `NonTransfer` proxy add a `Governance` proxy and widen its own permissions.
#[test]
fn non_transfer_proxy_is_not_a_superset_of_governance() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// `NonTransfer` denies every governance call family that `Governance` admits, except `Utility`.
	for call in [
		RuntimeCall::Treasury(pallet_treasury::Call::void_spend { index: 0 }),
		RuntimeCall::ConvictionVoting(pallet_conviction_voting::Call::remove_vote {
			class: None,
			index: 0,
		}),
		RuntimeCall::Referenda(pallet_referenda::Call::refund_decision_deposit { index: 0 }),
		RuntimeCall::Whitelist(pallet_whitelist::Call::remove_whitelisted_call {
			call_hash: Default::default(),
		}),
	] {
		assert!(ProxyType::Governance.filter(&call), "Governance must admit {call:?}");
		assert!(!ProxyType::NonTransfer.filter(&call), "NonTransfer must deny {call:?}");
	}

	// So it must not declare itself a superset of it. This is what stops a `NonTransfer` proxy
	// from granting itself a `Governance` proxy: `pallet_proxy` gates `add_proxy`/`remove_proxy`
	// on `is_superset` before it ever consults `filter`, which by itself does not deny `Proxy`
	// calls.
	assert!(!ProxyType::NonTransfer.is_superset(&ProxyType::Governance));
```
