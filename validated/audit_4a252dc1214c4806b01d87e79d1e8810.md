### Title
Uncaught exception (crash) in chash validation on malformed 288-bit c-hash input — ([File: chash.js])

### Summary
`chash.js`'s `isChashValid()` function contains an unguarded `throw` inside `separateIntoCleanDataAndChecksum()` / `mixChecksumIntoCleanData()` that is reachable when a caller passes a 48-character string (the base64-encoded, chash288/288-bit format) whose decoded byte length does not equal exactly 288 bits. Unlike RDesktop's C-level out-of-bounds array reads (CVE-2019-15682), this is a JavaScript analog: a length-mismatch condition that is not validated/caught before the decoded buffer is consumed, producing an uncaught `Error` that can crash the Node process — the network-facing `uncaughtException` handler explicitly re-throws to kill the process. [1](#0-0) 

### Finding Description
`isChashValid(encoded)` only wraps the raw decode step (`base32.decode` for 32-char input, or `Buffer.from(encoded, 'base64')` for 48-char input) in a `try/catch`: [2](#0-1) 

The subsequent calls — `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` — are **outside** that `try/catch` block: [3](#0-2) 

`separateIntoCleanDataAndChecksum` performs a strict length check and `throw`s a plain `Error` for any length other than 160 or 288 bits: [4](#0-3) 

For the 32-character (base32/chash160) branch this is not exploitable, because a 32-character string over the required `[A-Z2-7]` alphabet always decodes to exactly 160 bits — there is no way to produce a mismatched length. However, for the 48-character (base64/chash288) branch, the length gate in `isValidChash`/`isChashValid` only checks the JS string length (`isStringOfLength(str, 48)`), not that every character is valid base64: [5](#0-4) 

Node's `Buffer.from(str, 'base64')` decoder is lenient: it silently skips characters outside the base64 alphabet rather than throwing. A 48-character string containing a mix of valid and invalid base64 characters can therefore decode to a buffer whose length is *not* exactly 36 bytes (288 bits). When that malformed-length buffer reaches `separateIntoCleanDataAndChecksum`, the length check fails and the function `throw`s an `Error` that is never caught by the (too narrowly scoped) `try/catch` in `isChashValid`, propagating up through `isValidChash`/`isValidAddressAnyCase` as an uncaught exception.

This mirrors the CVE-2019-15682 bug class: a parser assumes a fixed decoded length from otherwise-loosely-validated attacker input, and processes it without validating the actual decoded size, leading to an unhandled fault condition instead of a clean input-validation rejection.

### Impact Explanation
An uncaught exception thrown deep inside address/c-hash validation code is not something ordinary `ifUnitError`/`ifJointError` callback-based validation logic is designed to catch (those paths return errors via callbacks, not via native JS exceptions). If such an exception escapes the synchronous call stack during processing of an incoming joint/unit, it can surface as an uncaught exception at the top level. `network.js` installs a global handler that explicitly re-throws to crash the process: [6](#0-5) 

A crash of a full node/hub process during unit validation is a "network unable to confirm new units" condition if triggered broadly, satisfying the required impact bar for this class of report.

### Likelihood Explanation
Likelihood is **uncertain and should be treated as low-to-medium** without further confirmation: I was able to confirm the code-level defect (missing try/catch scope, throw on length mismatch, lenient base64 decoding) with high confidence, but I could not fully trace, within the available search budget, a live, currently-reachable call site that invokes `isValidChash(str, 48)` / the chash288 (48-character) branch with attacker-controlled unit/AA/asset data. In this codebase, addresses are exclusively validated via `isValidAddress` (32-character chash160, which is not exploitable due to the fixed-length base32 alphabet), and it is unclear whether the chash288/48-character code path is still exercised by any currently attacker-reachable field (e.g., a legacy shared-address or definition-hash format) or is effectively dead code retained in `chash.js`. This should be verified against the actual call graph before treating this as confirmed-exploitable.

### Recommendation
- Move the length-validation logic (or a `try/catch`) so that it wraps the entire `isChashValid` body, not just the initial decode step, and return `false` instead of throwing on any internal length mismatch.
- Reject 48-character inputs at `isValidChash`/`isStringOfLength` time unless they are valid base64 (mirroring the strict alphabet check already used for `isValidAddress`'s 32-character/base32 case).
- Audit whether the chash288 (48-character) code path is still used by any attacker-reachable validation route (asset/definition/shared-address logic); if it is dead code, remove it to reduce attack surface.

### Proof of Concept
Conceptual (not fully verified as network-reachable given the caveat above):
```js
const chash = require('./chash.js');
// 48 chars, mixture of valid base64 chars and characters outside the base64 alphabet (e.g. '!', '@')
const malformed = "AAAA!!!!BBBB@@@@CCCCDDDDEEEEFFFFGGGGHHHH"; // length must be 48
console.log(malformed.length); // 48 -> passes isStringOfLength(str,48)
chash.isChashValid(malformed); // Buffer.from(malformed,'base64') silently drops invalid chars,
                                // producing a buffer whose bit length != 288,
                                // causing separateIntoCleanDataAndChecksum to throw an uncaught Error
```
This throw is not caught inside `isChashValid`, and if this function is reached from a synchronous, attacker-triggered validation path without an enclosing `try/catch`, it becomes an uncaught exception that the process-level handler in `network.js` turns into a fatal crash.
