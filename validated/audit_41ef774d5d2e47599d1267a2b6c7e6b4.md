### Title
PR labels unfiltered into deploy/task command env, allowing `RUBYLIB` (and arbitrary env var) injection into `PTY.spawn` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every GitHub PR label name (upcased) as an environment variable set to `"true"` with no allow-list check, and this hash flows unfiltered through `TaskCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn` for every ruby/shell step executed for that review stack's tasks. An attacker who can label their own PR (e.g. with `RUBYLIB`) can inject that variable into the deploy host's process environment for any task run against that review stack.

### Finding Description
The broken binding: the codebase's own trust model (`EnvironmentVariables#permit`, used via `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` and `TaskDefinition#filter_envs`) asserts `env_reaching_command.keys ⊆ machine_env.keys ∪ VariableDefinition-declared keys`. This equality/subset property is what should hold for any env hash reaching `Command`/`PTY.spawn`.

Trace:
- `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` — every PR label becomes an env var unconditionally, no allow-list. [1](#0-0) 
- `PullRequest#github_pull_request=` sets `self.labels = github_pull_request.labels.map(&:name)` directly from the GitHub webhook/API payload — labels are attacker-controlled text with no format validation. [2](#0-1) 
- `TaskCommands#env` (lib/shipit/task_commands.rb:33-48) merges `@stack.env` (which for a `ReviewStack` includes the label-derived vars) into the hash that becomes each step's `Command.new(command_line, env:, ...)`. There is no call to `EnvironmentVariables#permit`/`filter_envs` anywhere in this method — that filtering machinery (`DeploySpec#filter_deploy_envs`, `#filter_rollback_envs`, `TaskDefinition#filter_envs`) is used elsewhere (for user-supplied deploy/rollback form variables), not on the full `TaskCommands#env`/`Stack#env` hash. [3](#0-2) 
- `Command#unbundled_env` (lib/shipit/command.rb:103-105) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` with no key filtering, and `#start` passes this directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (lib/shipit/command.rb:92). [4](#0-3) [5](#0-4) 

Attacker's exact request: open a pull request against a repository with review stacks enabled, add a label named `RUBYLIB` (or `rubylib`, case-insensitively normalized by `.upcase`) via the GitHub UI/API on their own PR/fork — no Shipit credentials needed, only GitHub PR/label permissions on their own PR, which GitHub grants to any contributor with write access to labels on their PR or via GitHub's default label webhooks relayed through `POST /webhooks`. When Shipit syncs the PR (via webhook `pull_request` event), `PullRequest#github_pull_request=` stores the label; subsequent deploy/rollback/task execution on that review stack computes `env['RUBYLIB'] = 'true'`, which is injected into every step's process environment on the deploy host.

Existing guards do not close this gap: `EnvironmentVariables#permit` exists and enforces exactly this invariant, but it is never invoked on `Stack#env`/`ReviewStack#env`/`TaskCommands#env` — it only guards `deploy_variables`/`rollback_variables` (user-facing form-selected variables), a structurally separate code path. No model validation restricts `PullRequest#labels` format/content, and no allow-list exists for which label names are safe to promote to env vars.

### Impact Explanation
Any environment variable name is a candidate for injection (not limited to `RUBYLIB`), since the merge is completely unrestricted — an attacker can inject `RUBYLIB`, `BUNDLE_GEMFILE`, `LD_PRELOAD` (if inherited/passed to a spawned process that respects it), `GIT_SSH_COMMAND`, or any similarly-named variable that a ruby/git/shell step in that stack's `shipit.yml` steps might honor, achieving code execution or `$LOAD_PATH`/require-path corruption on the deploy host for any task (deploy, rollback, dependency install) run against that review stack. This is repeatable per-PR and confined to review stacks tied to that repository/PR, but any repository owner/contributor who can label their own PR can affect their own review stack's execution — matching "Critical: RCE on the deploy host via `Command`/`PTY.spawn`" if the injected variable is leveraged by any of the executed steps (e.g. a ruby interpreter step honoring `RUBYLIB`, or `RUBYOPT`).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`ProvisioningHandler`/review-stack feature configured) and Shipit must sync PR labels via the standard `pull_request` webhook (default behavior, no special Shipit config required). Attacker cost is trivial: open a PR from a fork and add a label — both actions require no privileged Shipit role, no secrets, and are available to any GitHub user able to interact with the repo's PRs. This is fully repeatable and requires no race conditions or timing.

### Recommendation
Filter the label-derived environment in `ReviewStack#env` through an explicit allow-list (e.g. `EnvironmentVariables.with(...).permit(...)`) restricted to variable names declared safe by the repository's `shipit.yml` (similar to `deploy_variables`/`machine_env`), or drop the raw label-to-env-var promotion entirely in favor of an explicit, deploy-spec-declared mapping from labels to env vars. At minimum, reject label names colliding with security-sensitive variable names (`RUBYLIB`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`, `PATH`, etc.) before merging into `Stack#env`.

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (new test)
test "PR labels cannot inject unsanctioned env vars like RUBYLIB into TaskCommands#env" do
  stack = shipit_review_stacks(:some_review_stack) # a Shipit::ReviewStack fixture
  stack.pull_request.update!(labels: ['RUBYLIB'])
  task = shipit_deploys(:some_review_stack_deploy) # task belonging to that stack

  commands = Shipit::TaskCommands.new(task)

  declared_keys = commands.deploy_spec.machine_env.keys
  refute_includes commands.env.keys, 'RUBYLIB',
    "PR label promoted 'RUBYLIB' into env reaching Command/PTY.spawn without being declared in machine_env: #{declared_keys.inspect}"
end
```
Before the fix, `commands.env['RUBYLIB']` equals `"true"` even though `'RUBYLIB'` is absent from `deploy_spec.machine_env` and from any `VariableDefinition`-declared variable, demonstrating the broken binding `env_reaching_command.keys ⊆ machine_env.keys ∪ declared_variable_names` fails.
