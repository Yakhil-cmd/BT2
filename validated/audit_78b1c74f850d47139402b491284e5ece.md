### Title
Unscoped `Stack.from_param!` in `Api::CCMenuController#stack` allows a token scoped to one stack to read any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` overrides the base controller's stack-scoping logic and calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is never applied. `require_permission :read, :stack` only checks that the client's `permissions` array contains the literal string `"read:stack"` and does not verify that the requested stack matches the client's bound `stack_id`, so any client holding a `read:stack`-permissioned token (even one issued for a single specific stack) can retrieve CCMenu XML for an arbitrary stack.

### Finding Description
The broken binding: for the base API endpoints, `current_api_client.stack_id == stack.id` is enforced via `Api::BaseController#stacks` (`Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true) before `from_param!` resolves the record [1](#0-0) . `Api::CCMenuController` redefines `stack` to bypass this scope entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Authorization is enforced only via `require_permission :read, :stack` [3](#0-2) , which calls `current_api_client.check_permissions!(:read, :stack)` [4](#0-3) . `ApiClient#check_permissions!` only checks whether the literal string `"read:stack"` is present in the `permissions` array - it performs no comparison against `stack_id` or the requested stack at all:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [5](#0-4) 

So the equality the system is supposed to preserve, `current_api_client.stack_id == stack.id` (the id of the record actually rendered), holds for `#index`/other endpoints using `stacks.from_param!`, but does **not** hold for `CCMenuController#show`: `stack.id` can be any stack in the database regardless of `current_api_client.stack_id`.

Exploit: attacker has (or obtains) a legitimate `ApiClient` token created for stack A with `permissions` including `read:stack` (e.g., an `ApiClient` created by a maintainer of stack A and handed to a CI dashboard). Attacker sends `GET /api/stacks/<stack-B-slug>/ccmenu.xml?token=<A's token>`. `authenticate_api_client` in `CCMenuController` authenticates the token successfully (`ApiClient.authenticate(params[:token])`) [6](#0-5) , `require_permission!` passes because `read:stack` is in the permission list, and `stack` resolves stack B unscoped, leaking B's `deploys_and_rollbacks.last` (deploy status, lock state, revision) in the rendered XML [7](#0-6) .

The existing test suite only exercises same-stack requests (`stack_id: @stack.to_param` with `@client` bound to the same stack) [8](#0-7) , so this cross-stack divergence is not covered or prevented by any existing guard (`verify_signature`, `require_permission!`, model validations - none of these touch stack-id scoping for this action).

### Impact Explanation
A holder of any `read:stack`-permissioned API token - even one deliberately restricted to a single stack via `ApiClient#stack_id` - can enumerate and read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, activity) of any other stack in the Shipit instance by simply changing the `stack_id` route parameter. This is a cross-tenant/cross-repository unauthorized read of stack state, matching the High-severity category "unauthenticated/unauthorized read of stack state... deploy output." It is fully repeatable against any stack slug the attacker can guess or enumerate, with no additional privilege required beyond a valid-but-narrowly-scoped token.

### Likelihood Explanation
Preconditions: attacker must already possess one valid `ApiClient` token with `read:stack` permission (e.g., leaked from a CI status widget, monitoring dashboard, or a legitimately shared CCMenu URL for stack A - CCMenu tokens are commonly embedded in build-status dashboard configs and are lower-trust credentials than session/OAuth tokens). No GitHub secrets, session, or operator privileges are needed. Cost is a single HTTP GET with a modified path parameter; fully repeatable and scriptable across all stack ids/slugs.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from the base controller instead of overriding it with an unscoped query:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that `current_api_client.stack_id` scoping (enforced by `Api::BaseController#stacks`) applies uniformly to CCMenu requests, or alternatively add an explicit check in `show` that `stack.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` is true.

### Proof of Concept
Minitest plan (add to `test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a token scoped to stack A cannot read stack B's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")
  Deploy.create!(stack: stack_b, until_commit: stack_b.commits.create!(sha: "a" * 40), since_commit: stack_b.commits.create!(sha: "b" * 40))

  scoped_client = ApiClient.create!(creator: @user, name: "scoped", permissions: %w[read:stack], stack_id: stack_a.id)

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Binding under test: current_api_client.stack_id (stack_a.id) should equal stack.id (rendered stack)
  assert_not_equal scoped_client.stack_id, stack_b.id
  # Expected secure behavior: request should be rejected (404/403), not render stack B's data
  assert_response :not_found # or :forbidden, per fix
  refute_includes response.body, stack_b.to_param
end
```
This demonstrates that, prior to the fix, the request succeeds (`200 OK`) and returns stack B's `lastBuildStatus`/`activity`, even though `scoped_client.stack_id` (bound to stack A) never equals `stack_b.id`.
