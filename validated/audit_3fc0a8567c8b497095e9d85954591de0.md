### Title
Stack-scoped API token can read CCMenu status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` lookup method inherited from `Api::BaseController` and drops the per-token stack-scoping enforcement, letting a token that is authorized only for one stack read build/deploy status of **any** stack in the installation.

### Finding Description
`Api::BaseController` enforces that a stack-scoped `ApiClient` can only see the stack it is bound to: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` builds on top of that scoped relation via `stacks.from_param!(...)`. Every other API controller (`TasksController`, `MergeRequestsController`, `StacksController`, etc.) relies on this `stack`/`stacks` method to bind lookups to the token's authorized stack.

`Api::CCMenuController`, however, defines its own private `stack` method that bypasses `stacks` entirely and queries the global `Stack` model directly: [2](#0-1) 

The only authorization check performed is `require_permission :read, :stack`, which merely verifies the token's permission *list* contains `read:stack` — it does not check which specific `stack_id` the token is scoped to: [3](#0-2) 

This breaks the binding: **the stack a token authorizes vs. the stack the request actually touches**. A token created with `stack_id` set (a legitimate, supported feature — see `test "an api client scoped to a stack will only see that one stack"` in `test/controllers/api/stacks_controller_test.rb` and the `here_come_the_walrus` fixture in `test/fixtures/shipit/api_clients.yml`) is meant to be confined to that one stack. `CCMenuController#stack` ignores that scoping and resolves `params[:stack_id]` against the entire `Stack` table.

Note that `Api::CCMenuController` also overrides `authenticate_api_client` to allow authentication via a `token` query parameter (in addition to Basic Auth) — this is how CCMenu clients (e.g. CCTray/CI monitors) are normally used, and it does not itself introduce the bug, but it does make the endpoint reachable with just a URL containing a token, increasing the practical exposure of the missing scope check.

### Impact Explanation
Any holder of a stack-scoped `read:stack` API token (an unprivileged actor with legitimate, narrow access to exactly one stack) can query `GET /api/stacks/:stack_id/ccmenu.xml?token=...` for any other `stack_id` in the Shipit instance and obtain that stack's name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — i.e., unauthorized read of stack/deploy state belonging to repositories the token was never granted access to. This matches the High-severity category "unauthenticated/unauthorized read of stack state, task streams or deploy output" from an authorization-boundary perspective, since the actor is authenticated but is reading state entirely outside their token's authorized scope.

### Likelihood Explanation
Likelihood is high: stack-scoped tokens are a documented, supported feature (`CCMenuUrlController` itself is one place that mints such tokens for individual stacks), the endpoint is reachable with a simple GET request plus a query-string token, and no other check in `CCMenuController` compensates for the missing scoping. Any legitimate consumer of a scoped CCMenu token can trivially enumerate other `stack_id`s and pull their status.

### Recommendation
Have `Api::CCMenuController#stack` reuse the inherited, scope-aware `stack`/`stacks` method from `Api::BaseController` instead of querying `Stack.from_param!` directly, e.g.:
```diff
- def stack
-   @stack ||= Stack.from_param!(params[:stack_id])
- end
+ # remove this override entirely and inherit BaseController#stack,
+ # which respects current_api_client.stack_id scoping
```

### Proof of Concept
1. Create a stack-scoped `ApiClient` bound to Stack A with `permissions: ['read:stack']` (this is exactly how `CCMenuUrlController#client`/tokens minted for a specific stack work).
2. Using that token, send `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<token>` where Stack B is a different, unrelated stack the token was never granted.
3. Observe HTTP 200 with Stack B's CCMenu XML (name, `lastBuildStatus`, etc.), even though the token is only authorized for Stack A — confirmed by comparing against `Api::BaseController#stack`, which would have raised a 404/`from_param!` failure by limiting the queryable relation to `Stack.where(id: current_api_client.stack_id)`.
