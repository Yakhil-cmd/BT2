### Title
Unallowlisted swap-route contracts can append unauthorized wallet-token transfers to the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller correctly limits its own router payment to one exact input-token transfer, but it does not prevent route-selected downstream contracts from placing additional `transfer` calls beneath the user’s root authorization. An attacker can therefore provide a route that simultaneously produces enough output to satisfy the strategy and invokes an unrelated token transfer from the caller to the attacker. Transaction simulation records that rogue transfer as an additional child authorization, and enforcement accepts it if the caller signs the expanded tree.

### Finding Description
`swap_collateral` authorizes `caller` and permits the caller to supply arbitrary strategy bytes for conversion between different collateral assets. [1](#0-0) 

The shared strategy path sends those bytes to the configured router. Before invocation, the controller authorizes only `token_in.transfer(controller, router, amount_in)` with no nested invocations. [2](#0-1) 

That authorization protects only the controller’s declared input transfer. The router remains free to invoke contract addresses encoded in the route, and the controller does not restrict, decode, or independently validate those downstream calls. [3](#0-2) 

The repository’s dedicated authorization test demonstrates the boundary: a router calls a route-selected `hop_pool`, and that pool directly calls `wallet_token.transfer(victim, attacker, amount)`. [4](#0-3) [5](#0-4) 

In simulation, the rogue token transfer is recorded as a child of Alice’s `swap_collateral` authorization, and execution moves her entire unrelated wallet-token balance to the attacker while still crediting the expected swap output. [6](#0-5) 

With an honest authorization tree, enforcement rejects the rogue transfer and rolls back the transaction. If Alice signs the simulation-generated tree containing the added child, enforcement accepts it and the attacker receives the unrelated token. [7](#0-6) 

This is analogous to the Helm issue because authority intended for one integration boundary—the swap input transfer—is attached to a caller-selected downstream domain. Unlike Helm’s silent HTTP credential forwarding, Soroban exposes the added transfer in the signed authorization tree; the vulnerability therefore requires the victim to sign that poisoned tree.

### Impact Explanation
A malicious route can steal any token balance for which the victim’s signed authorization tree gains a rogue child invocation. The loss is not limited to the lending position, swap input, or route output: the demonstrated theft drains a token that was never listed by the protocol. [8](#0-7) [9](#0-8) 

This qualifies as theft of user funds and is medium severity because exploitation requires a malicious route and a victim signature covering the expanded authorization tree.

### Likelihood Explanation
The affected entrypoints are permissionless for account owners and delegates, and route bytes are supplied by the caller rather than constrained to an on-chain venue allowlist. [10](#0-9) [11](#0-10) 

The same root authorization pattern is reachable through other strategy flows that call `swap_tokens`, including `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [12](#0-11) [13](#0-12) [14](#0-13) 

The principal mitigating factor is that an honest wallet or client can reject an authorization tree containing an unexpected token transfer. The repository’s threat model also explicitly relies on clients decoding signed routes and refusing unexpected child authorizations. [15](#0-14) 

### Recommendation
Do not allow arbitrary downstream contracts to execute beneath the user’s root authorization for a strategy swap.

Preferred mitigations are to:

1. Execute swaps through a strictly allowlisted set of venue contracts, or constrain decoded route hops to those venues.
2. Isolate user authorization from route execution by requiring the router to spend only protocol-held input and never invoke venue code in a context where a `require_auth` from the caller can attach to the user’s authorization tree.
3. Make the expected authorization tree part of the request and reject execution paths that would require additional user-authenticated calls.
4. Until an on-chain fix exists, require clients to reject any simulated authorization tree containing children other than the exact expected strategy transfer.

### Proof of Concept
The repository already contains a working harness in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice supplies 10,000 USDC and holds an unrelated wallet token. The test registers a router and an attacker-controlled `RogueHopPool`. [16](#0-15) 
2. Alice calls `swap_collateral` with a route naming the rogue pool. [17](#0-16) 
3. The router pulls the declared input and invokes the route-selected pool. [4](#0-3) 
4. The rogue pool invokes `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`. [5](#0-4) 
5. Recording mode attaches that transfer beneath Alice’s `swap_collateral` authorization and drains her wallet token. [6](#0-5) 
6. Enforcement rejects the transfer when Alice signs only the honest root, but accepts it when the poisoned child is included in her signed tree. [7](#0-6)

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
```

```rust
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
