## Title
Untrusted, attacker-issued assets with unsatisfiable `transfer_condition`/`issue_condition` can permanently freeze funds held by an AA that accepts arbitrary trigger assets - (File: `validation.js`, `definition.js`)

### Summary
The Putty finding shows that allowing a counterparty to freely choose an ERC20/ERC721 contract address that is later called via untrusted external calls lets an attacker plant a "poison" token that reverts on demand, permanently locking `exercise()`/`withdraw()` and any assets held for the other party. Obyte has an analogous trust boundary: any address can define a custom asset with an arbitrary `issue_condition`/`transfer_condition`, and many Autonomous Agents (AAs), by design, accept "any asset the trigger sends" (see the shipped sample AAs `uniswap_like_market_maker.oscript`, `sell_asset_for_bytes.oscript`, `order_book_exchange.oscript`). Once such an asset is deposited into the AA's balance, every subsequent attempt by the AA to pay it back out is itself a "transfer" and is checked against that asset's `transfer_condition` at validation time, exactly like Putty's `_transferERC20sOut`/`_transferERC721sOut` calls into attacker-controlled code.

### Finding Description
`validatePaymentInputsAndOutputs()` in `validation.js` evaluates the asset's `issue_condition` (on issue) or `transfer_condition` (on transfer) for *every* payment of that asset, including payments made by an AA when it tries to send the asset back to a user: [1](#0-0) 

The condition itself is an arbitrary oscript boolean expression supplied entirely by the asset's definer at asset-creation time and is only restricted by generic structural checks (must be a 2-element array) in `validateAssetDefinition`: [2](#0-1) [3](#0-2) 

Nothing prevents the definer from writing a condition that is permanently unsatisfiable for a specific address (e.g. requiring the sender/receiver to not equal the AA's own address, or requiring an attestation from an attestor list controlled by the attacker that will never attest the AA, or referencing a data feed value the attacker will never publish). Because the AA cannot alter its own address or bypass the condition, once it holds a balance of such an asset it can never satisfy `Definition.evaluateAssetCondition` for that asset, so any `payment` message it tries to send with that asset will fail validation and the whole AA response bounces (the AA logic is atomic per trigger — see `revert()`/`bounce()` handling in `aa_composer.js`).

Many AA design patterns explicitly accept "any asset sent by the trigger" without any whitelist, exactly mirroring Putty's design of accepting arbitrary `baseAsset`/`erc20Assets`/`erc721Assets` fields chosen by the counterparty:
- Uniswap-like market maker AA blindly trades and holds whatever `$asset` is configured/deposited: [4](#0-3) 
- Generic bank/order-book AAs track balances keyed by `trigger.output[[asset!=base]].asset` for arbitrary assets and later attempt to pay them back out on withdrawal: [5](#0-4) 

In all of these, if a user deposits an asset whose `transfer_condition` is crafted to always fail when the AA is the sender, the withdrawal/payout message for that asset will always fail validation, the AA response bounces every time, and the balance recorded in the AA's `balance_<address>_<asset>` state variable (or the AA's on-chain asset balance) becomes permanently unspendable — the funds are locked in the AA forever, and any other legitimate depositors of that same asset (e.g. liquidity providers in the same pool) are similarly frozen out, just as Putty's other party could never claim the NFTs/tokens they were owed.

### Impact Explanation
This is directly analogous to the Putty "Malicious Token Contracts May Lead To Locking Orders" bug class translated to Obyte's asset system: an unprivileged asset issuer plants a booby-trapped asset (its `transfer_condition`/`issue_condition`), gets it accepted into an AA that doesn't whitelist assets, and the AA — and any counterparties relying on that asset balance — can never move the asset out again. This is AA fund freezing (funds permanently locked/inaccessible), which matches the "AA fund loss or freezing" acceptance criterion. Severity depends on the specific AA's design (whether it silently accepts arbitrary assets), but for widely-used, publicly documented AA patterns shipped as reference examples in this codebase, the impact is a straightforward permanent DoS/freeze of any legitimate funds co-mingled with the poisoned asset.

### Likelihood Explanation
No special privileges are required: any address can issue a custom asset (`app: 'asset'`) with an attacker-chosen `transfer_condition`, and can then post a trigger unit sending that asset to a target AA. Many AA templates (market makers, banks, order books) are intentionally generic and accept any asset a trigger sends without a whitelist, exactly the condition the Putty report calls out ("any of the transfers... make external calls to untrusted [conditions]"). The only "external requirement" is that a victim AA/dev chooses not to whitelist accepted assets — the same caveat noted by the C4 judge for the original Putty finding.

### Recommendation
- AA authors should whitelist the specific assets they intend to hold/trade (`trigger.output[[asset=<specific asset id>]]`) rather than accepting `trigger.output[[asset!=base]].asset` generically, mirroring the recommended Putty mitigation of whitelisting approved token contracts.
- Consider documenting/warning (as ocore does not currently do, unlike the Putty UI mitigation) that assets with `issue_condition`/`transfer_condition` can be crafted to be permanently unspendable by a specific address, and that AAs accepting arbitrary assets are exposed to this griefing/freezing vector.
- Optionally, at the protocol level, evaluate whether `transfer_condition` should be prevented from referencing filters that can deterministically discriminate against a single fixed address across all future transactions (similar in spirit to disallowing self-referential private-asset conditions already enforced in `validateDefinition`), though this carries the same centralization/complexity tradeoffs noted in the original report.

### Proof of Concept
1. Attacker issues asset `X` via a `payment`+`asset` message with:
   ```
   {
     app: 'asset',
     payload: {
       is_private: false,
       is_transferrable: true,
       auto_destroy: false,
       fixed_denominations: false,
       issued_by_definer_only: true,
       cosigned_by_definer: false,
       spender_attested: false,
       transfer_condition: ["not", [["address", {address: "<victim AA address>"}]]]  // schematic: fails whenever the AA is a party to the transfer
     }
   }
   ```
   (validated only for array-of-2 structure per [2](#0-1) )
2. Attacker deposits asset `X` into a generic AA that accepts arbitrary assets, e.g. the shipped `uniswap_like_market_maker.oscript` pattern (`trigger.output[[asset=$asset]]`) or a bank/order-book AA tracking `balance_<address>_<asset>`.
3. The AA credits the deposit to its state/balance for asset `X`.
4. When the depositor (or any user) tries to withdraw/trade out of asset `X`, the AA's outgoing `payment` message for asset `X` is validated via `validatePaymentInputsAndOutputs` → `Definition.evaluateAssetCondition` against `transfer_condition`: [1](#0-0) . Because the condition is designed to always fail when the AA address is involved, the condition evaluates to false, validation fails ("transfer or issue condition not satisfied"), and the AA response bounces.
5. Every subsequent attempt to move asset `X` out of the AA fails identically — the deposited funds (and, in a pooled AA, other users' co-mingled funds tied to that asset) remain permanently frozen inside the AA.
