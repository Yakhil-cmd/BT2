### Title
Webhook signature validated against `repository.owner.login` while dispatched handlers act on the (unverified) `repository.full_name` - allows cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the still-unverified JSON body. Once the signature check passes, `WebhooksController#create` dispatches the *same raw payload* to event handlers, which instead resolve the target `Repository`/`Stack` using a completely different field: `repository.full_name`. Because the signing key is chosen by one field and the mutating action is keyed by another field inside the same signed blob, an attacker who legitimately owns (or fully controls the webhook secret of) any one organization onboarded in Shipit can forge a payload whose `repository.owner.login` points to their own org (so the signature check passes with their own secret) while `repository.full_name` points to an arbitrary victim repository/stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the authenticating organization purely from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/`webhook_secret` configured for that organization, and `verify_webhook_signature` performs a straightforward HMAC comparison over the raw body using that secret: [3](#0-2) 

This design is correct *only if* the field used to select the secret (`repository.owner.login`) is the same field later trusted to determine which repository/stack is acted upon. It is not: every event `Handler` resolves the target `Repository` using `repository.full_name`, a distinct JSON field that is never cross-checked against `repository.owner.login`: [4](#0-3) 

`create` dispatches the parsed body verbatim to these handlers after the signature check succeeds: [5](#0-4) 

Concretely, an attacker who is a legitimate GitHub org admin/owner able to configure a webhook secret for their own organization "attacker-org" in this Shipit instance can send:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
signed with `attacker-org`'s own `webhook_secret`. `repository_owner` resolves to `"attacker-org"`, `Shipit.github(organization: "attacker-org")` returns the attacker's own `GitHubApp` config, and `verify_webhook_signature` succeeds because the attacker legitimately knows that secret. `PushHandler#stacks` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — an action the attacker was never authorized to trigger for that repository: [6](#0-5) 

This breaks the binding: `organization authenticated (repository.owner.login) == repository written (repository.full_name)`. The signature only proves "this request is authentic for `attacker-org`," not "this request is authentic for the repository it claims to act on."

### Impact Explanation
This lets an attacker who controls webhook credentials for any one organization hosted on a shared/multi-tenant Shipit instance forge verified webhook events (push, status, pull_request, check_suite, membership, etc.) that are dispatched against an arbitrary victim repository/stack tracked by the same instance. Depending on the handler, this can trigger unauthorized `GithubSyncJob` runs, fabricate commit statuses, or manipulate merge/review-stack state for repositories the attacker does not own — i.e., cross-repository writes / unauthorized state changes driven by a forged, "verified" webhook. This matches the High-severity class of "escalation into cross-repository writes" via a trust-boundary confusion, analogous to the reported oracle unit-mismatch bug where one part of the code assumes a value is in units (here: "owner") the other part never actually checked (here: "full_name").

### Likelihood Explanation
Exploitability requires the attacker to control (or know) the `webhook_secret` for at least one organization configured in the same Shipit deployment — a realistic condition on any Shipit instance that onboards multiple independent GitHub organizations (a documented, intended multi-tenant use case, evidenced by `Shipit.github(organization:)` and `GithubOrganizationUnknown` handling for unmapped orgs). No `ApiClient` token, `webhook_secret` of the *victim*, or repository write access to the victim repo is required — only ownership of one's own organization's webhook secret, which is a normal, unprivileged onboarding credential.

### Recommendation
Do not select the verification secret from the same untrusted field independently interpreted later. Bind the verifying organization to the repository actually acted upon: after selecting `github_app` by `repository_owner`, additionally require that `repository.full_name`'s owner segment matches `repository_owner` (or, better, resolve the target `Repository` first and verify using the secret configured for that specific repository's known GitHub App/installation, rejecting the webhook if it disagrees with the claimed `repository.owner.login`).

### Proof of Concept
1. Attacker legitimately controls organization `attacker-org`, which is configured in this Shipit instance with `webhook_secret = S`.
2. Attacker crafts JSON body:
   ```json
   {"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/master","after":"<sha>"}
   ```
3. Attacker computes `sha1=HMAC-SHA1(S, body)` and POSTs to `/webhooks` with header `X-Hub-Signature: sha1=<...>`, `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and `verify_webhook_signature` succeeds (attacker knows `S`).
5. `create` dispatches to `PushHandler`, whose `repository_name` reads `"victim-org/victim-repo"` from `payload.dig('repository','full_name')`, resolving stacks belonging to the victim repository and calling `stack.sync_github(expected_head_sha: params.after)` on them — an action never authorized by the victim organization's own webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
