### Title
Stop-hook / commit-review dedup keys on `(filePath, category)` allow a new, distinct dangerous change to be silently suppressed - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_stop_hook`, `handle_commit_review_posttooluse`, and `handle_push_sweep_posttooluse` all dedup LLM-found vulnerabilities against session state using the key `(filePath, category)` rather than the actual vulnerable code or line range. Once any finding for a given file+category has been shown once in a session, any subsequent — and materially different — dangerous change to that same file in the same category is treated as "already reported" and never resurfaces a warning or rewake.

### Finding Description
`_record_fire` in `handle_stop_hook` records shown findings keyed only by `(filePath, category)`: [1](#0-0) 

The comment explicitly documents that this is deliberate, because `vulnerableCode` bytes drift between fires as diff context lines shift: [2](#0-1) 

The same `previous_findings` state and the same `(filePath, category)` key scheme is shared and consulted by `handle_commit_review_posttooluse`'s `_dedup_against_state` call: [3](#0-2) 

and by `handle_push_sweep_posttooluse`, which records into the same `previous_findings` bucket with an identical `(filePath, category)` set membership check: [4](#0-3) 

Because `previous_findings` is stored under `session_id` and persists across Stop-hook fires, commits, and pushes within that session (it is only pruned/rewritten, never invalidated per-file-content), an attacker who fully controls diff content (via normal edits and `git commit`/`git push`) can:
1. Introduce a vulnerability of category `C` in file `F` (e.g., a trivial/low-severity instance) so it gets flagged once and recorded into `previous_findings` as `("F", "C")`.
2. Later replace it with a substantively different and more dangerous vulnerability of the *same category* `C` in the *same file* `F` (different sink, different payload, different line).
3. Because the dedup key only compares `(filePath, category)` and not the code/location, `_dedup_against_state` treats the new, different, more dangerous finding as already-known and drops it from `new_vulns`, so `handle_stop_hook`/commit-review/push-sweep exit without warning or rewake (`sys.exit(0)` path when `new_vulns` is empty).

This lets a single already-surfaced (and possibly already "fixed" or low-risk) finding of a given file+category act as a standing suppressor for any future, unrelated dangerous change of the same category in that file, across retries, amends, and pushes — directly matching the invariant under test.

### Impact Explanation
This is a security-control bypass: it silently disables the review/warning/rewake mechanism for genuinely new dangerous code, without any explicit user action or approval. An attacker-controlled diff (or an LLM-driven edit trying to sneak in a vulnerability) can exploit the coarse dedup key to make later dangerous changes invisible to the Stop-hook, commit-review, and push-sweep surfaces, defeating the "dangerous edits/commands must stay reviewable and blockable across retries/amends/pushes" invariant. This matches the "Security-control bypass that silently disables or routes around blocking/review" impact category, though the severity is bounded because it requires a same-category, same-file "seed" finding to already exist and only suppresses the guidance mechanism — it does not disable other repo protections.

### Likelihood Explanation
This is a low-effort, fully repeatable scenario for anyone who can shape their own diffs (i.e., every ordinary user/session, since the attacker model here is a normal editing/commit workflow, not privilege escalation). No credentials, admin rights, or state tampering are needed — a two-step edit sequence (seed finding, then swap in a different dangerous finding of the same category/file) reliably reproduces the suppression, and it persists across Stop-hook retries, commit-review, and push-sweep because they all read/write the same `previous_findings` state keyed the same coarse way.

### Recommendation
Tighten the dedup key so it can distinguish genuinely different vulnerabilities in the same file/category, e.g. include a normalized code fingerprint (hash of the vulnerable snippet with surrounding-context stripped, or the changed line range) in addition to `(filePath, category)`, or expire/invalidate a `previous_findings` entry once the underlying line range it referenced is edited again. At minimum, re-verify (as `sweep_pending_warnings` already does for pattern-based rules) that the previously-flagged code is still present before treating a same-key finding as "already shown"; if the specific vulnerable code has changed since the last recorded fire, treat it as a new finding regardless of category/file match.

### Proof of Concept
Integration test outline for `security_reminder_hook.py`:
1. Initialize a git repo and a session state file with `session_id="s1"`.
2. Turn 1: Edit `app.py` introducing vulnerability A (category `"SQL Injection"`), commit. Invoke `handle_commit_review_posttooluse`/`handle_stop_hook` with a mocked LLM response returning `[{"filePath": "app.py", "category": "SQL Injection", "vulnerableCode": "query A"}]`. Assert `sys.exit(2)` is raised (warning surfaced) and `previous_findings` now contains `{"filePath": "app.py", "category": "SQL Injection", ...}`.
3. Turn 2: Replace the code in `app.py` with a different, unrelated SQL-injection sink at a different line (vulnerability B), commit again. Mock the LLM to return `[{"filePath": "app.py", "category": "SQL Injection", "vulnerableCode": "query B"}]`.
4. Invoke `handle_stop_hook`/`handle_commit_review_posttooluse` again and assert that `_dedup_against_state` drops finding B (since `(filePath, category)` already matches), causing `sys.exit(0)` with no stderr guidance and no rewake — demonstrating that a distinct, newly-introduced dangerous change is never surfaced to the user, violating the "must stay reviewable across retries/amends" invariant.
