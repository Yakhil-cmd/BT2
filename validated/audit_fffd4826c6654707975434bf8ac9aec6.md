### Title
`MembershipHandler#process` writes `Team`/`Membership` rows with no repository/organization scoping check, allowing a webhook verified for one organization to add/remove a user from *another* organization's Shipit team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` never calls `stacks` or `repository_name`, and its team lookup (`Team.find_or_create_by!(github_id: params.team.id)`) is keyed only on the attacker-supplied `team.id`, not on the verified organization. Because `github_id` is not unique-scoped to `organization` (only `organization+slug` is), an attacker whose own org's webhook signature validates can forge a `membership` event whose `team.id` collides with an existing `Team` belonging to a completely different organization, causing `team.add_member`/`team.members.delete` to mutate that unrelated team's roster.

### Finding Description
The broken binding is: **verified organization (`params.organization.login`, the org whose secret validated the signature) == organization that owns the `Team` row mutated by the handler**. `MembershipHandler#process` breaks this binding because it never checks it.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) . This only proves the request was signed with the secret belonging to the organization *named in the attacker's own payload* - i.e., an org the attacker legitimately controls (owns the GitHub App/webhook for). It says nothing about any other org.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) do |team| ... end` [3](#0-2) . The block (which sets `team.organization = params.organization.login`) only runs when the record is *created*; if a `Team` with that `github_id` already exists (belonging to a different organization), `find_or_create_by!` simply returns the existing record unmodified.
3. `process` then calls `team.add_member(member)` or `team.members.delete(member)` [4](#0-3)  on whichever `Team` was returned - potentially a team belonging to an org unrelated to the attacker's verified org.
4. Unlike `PushHandler`/`StatusHandler`, which scope their effect via `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`) [5](#0-4) , `MembershipHandler` never calls `stacks` or `repository_name` anywhere, so there is no mechanism tying the mutation to the org that was actually authenticated.

Attacker request: Attacker owns/controls an org (`attacker-org`) with a Shipit GitHub App/webhook installed (so `Shipit.github(organization: 'attacker-org')` has a real secret they know, satisfying "genuinely verifiable webhook"). They send a `membership` webhook, `action: 'added'`, `organization: {login: 'attacker-org'}`, `team: {id: <github_id of a victim org's existing Shipit Team>, name, slug, url}`, `member: {login: 'attacker-controlled-or-arbitrary-login'}`, signed with `attacker-org`'s secret. `verify_signature` passes because it only checks the `attacker-org` secret. `find_or_create_team!` finds the pre-existing victim `Team` row by `github_id` and returns it untouched (its `organization` stays the victim's). `team.add_member(member)` then adds the attacker's chosen `User` to that victim team's `Membership` list.

Existing guards do not stop this: `verify_signature` only authenticates the org named in the attacker's own payload, not the org owning the targeted `Team` row [6](#0-5) ; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not org linkage [7](#0-6) ; `Team`'s only DB-level uniqueness constraint is `(organization, slug)`, not `github_id` [8](#0-7) , so a `github_id` collision across orgs is not prevented at the model layer either.

### Impact Explanation
If the attacker can predict or discover the `github_id` of a `Team` belonging to another org (team IDs are visible via GitHub's public/organization APIs, or via `Shipit.github_teams`/team listing endpoints, or simply guessed as small sequential integers as seeded in fixtures), they can add an arbitrary GitHub login as a member of that team via forged webhooks from their own, unrelated org. Since `User#authorized?` grants Shipit application access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) , and `force_github_authentication` uses `current_user.authorized?` to gate access to the entire app [10](#0-9) , this is an escalation into `Shipit.github_teams` authorization for an attacker-chosen GitHub account - matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any organization/team whose `github_id` the attacker can learn, and the write is fully cross-tenant (attacker's own verified org has zero relationship to the victim org whose `Membership` table is mutated).

### Likelihood Explanation
Preconditions: attacker needs an org with a Shipit-integrated GitHub App/webhook they control (to pass `verify_signature`), and needs to know/guess the `github_id` of a target `Team` in another organization (team IDs are numeric and often discoverable via GitHub's API or UI, or brute-forceable given the modest ID space). No Shipit session, API token, or GitHub App private key is required for the target org - only for the attacker's own org, which they already control. This is a low-cost, fully repeatable attack once the target `github_id` is known.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` **and** `organization` (matching the verified `params.organization.login`), and reject/raise if a `Team` with that `github_id` already exists under a different `organization` rather than silently reusing it. Additionally, since `Team.organization` is only set on creation, add validation/lookup logic that treats `(github_id, organization)` as the true identity key, or add a uniqueness constraint on `github_id` scoped appropriately, and verify that `params.organization.login` matches `repository_owner`/the org that validated the webhook signature before mutating any `Team`.

require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerCrossOrgTest < ActiveSupport::TestCase
        test "membership event verified for org A mutates a Team belonging to org B" do
          victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'
          assert_equal 'shopify', victim_team.organization

          payload = {
            'action' => 'added',
            'team' => {
              'id' => victim_team.github_id, # attacker guesses/knows this
              'name' => victim_team.name,
              'slug' => victim_team.slug,
              'url' => victim_team.api_url,
            },
            'organization' => { 'login' => 'attacker-org' }, # org attacker actually controls & signs with
            'member' => { 'login' => 'attacker-picked-user' },
          }

          User.stubs(:find_or_create_by_login!).with('attacker-picked-user').returns(shipit_users(:walrus))

          assert_no_difference -> { Team.count } do
            assert_difference -> { victim_team.memberships.count }, 1 do
              MembershipHandler.call(payload)
            end
          end

          victim_team.reload
          assert_equal 'shopify', victim_team.organization # untouched, proves lookup ignored the mismatch
          assert_includes victim_team.members, shipit_users(:walrus)
        end

        test "MembershipHandler never scopes by repository/organization" do
          handler = MembershipHandler.new(
            'action' => 'added',
            'team' => { 'id' => 1, 'name' => 'x', 'slug' => 'x', 'url' => 'http://x' },
            'organization' => { 'login' => 'attacker-org' },
            'member' => { 'login' => 'someone' },
          )
          handler.stubs(:stacks).raises('should never be called')
          handler.stubs(:repository_name).raises('should never be called')
          User.stubs(:find_or_create_by_login!).returns(shipit_users(:walrus))
          Team.stubs(:find_or_create_by!).returns(shipit_teams(:shopify_developers))

          assert_nothing_raised { handler.process }
        end
      end
    end
  end
end
