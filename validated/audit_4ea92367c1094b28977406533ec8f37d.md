### Title
Unsanitized `Viewer.Login` from GraphQL response is persisted as `hosts.<host>.user` via `migrateConfig`/`getUsername` and later reflected unescaped to the terminal - (File: internal/config/migration/multi_account.go)

### Summary
`getUsername` takes the `Viewer.Login` field directly from a `CurrentUser` GraphQL query and passes it, without any sanitization, into `migrateConfig`, which persists it as `hosts.<host>.user` in `hosts.yml`. Commands that later print this stored username (e.g. `gh auth logout`, `gh auth switch`, and the login-flow success message) do so via plain `fmt.Fprintf`/`cs.Bold(username)`, not through the codebase's dedicated `iostreams.Untrusted` sanitizing wrapper, so ANSI escape sequences embedded in the login value would reach the terminal unescaped.

### Finding Description
`getUsername` queries `Viewer.Login` from the configured host's GraphQL endpoint and returns it verbatim: [1](#0-0) . `MultiAccount.Do` then passes this value straight into `migrateConfig`, which writes it into `hosts.<hostname>.user` and `hosts.<hostname>.users.<username>` via `c.Set` with no validation or escaping: [2](#0-1) [3](#0-2) .

Once stored, this username is read back by other commands and printed to the terminal using plain string interpolation rather than the `iostreams.Untrusted` type that the codebase built specifically to neutralize ANSI escapes in untrusted content (`pkg/iostreams/untrusted.go`, which sanitizes via `asciisanitizer.Sanitizer` on every `String()`/fmt path): [4](#0-3) . For example, `gh auth logout` prints the username with `fmt.Fprintf(opts.IO.ErrOut, "... %s\n", cs.Bold(username))` [5](#0-4) , `gh auth switch` does the same [6](#0-5) , and the login-flow success message does likewise [7](#0-6) . None of these wrap `username` in `Untrusted`, so no sanitization occurs between the GraphQL response and terminal output.

Preconditions per the allowed threat model: the attacker controls the responses of a host the victim points `gh` at (a GHES-style host with a stored OAuth token but no `hosts.<host>.user` set, e.g. because the token was originally issued as `x-access-token` or a pre-multi-account config). In that case `getUsername` falls through to the GraphQL query (the config lookup `username != "" && username != "x-access-token"` short-circuit fails) [8](#0-7) , and the attacker-controlled server can return an arbitrary `Viewer.Login` string containing ANSI escape bytes, since normal GitHub.com username character restrictions do not apply to a server the attacker fully controls.

### Impact Explanation
This enables terminal escape-sequence injection: a forged username containing ANSI/OSC/CSI sequences can rewrite terminal titles, hide or spoof text (e.g., fake "Logged in as" banners), or otherwise manipulate what the victim sees when running ordinary commands like `gh auth logout`, `gh auth switch`, or after a fresh login against the attacker's host. This matches the "spoofed/forged CLI output via terminal escape injection" impact class; it does not by itself achieve code execution or credential exfiltration.

### Likelihood Explanation
Requires the victim to have (or be establishing) an authenticated session against a host fully controlled by the attacker (e.g., a GHES instance or `--hostname` pointed at attacker infrastructure) — an explicitly allowed precondition in this audit's threat model. Given that, the exploit is fully attacker-driven (the attacker's server simply returns a crafted `Login` value) and deterministic/repeatable on every migration or fresh login against that host.

### Recommendation
Wrap any GraphQL/API-derived username fields in `iostreams.Untrusted` (or run them through `asciisanitizer`) before storing and, more importantly, before every terminal print site (`auth logout`, `auth switch`, `auth status`, `login_flow` success messages, etc.). Additionally, consider validating that `Viewer.Login` conforms to expected GitHub username syntax (alphanumeric and hyphens) before accepting it in `getUsername`/`migrateConfig`.

### Proof of Concept
```go
// internal/config/migration/multi_account_test.go (new test)
func TestMigrateConfig_PersistsUnsanitizedUsername(t *testing.T) {
    cfg := config.NewFromString(heredoc.Doc(`
        hosts:
          github.localhost:
            oauth_token: TOKEN
    `))
    maliciousLogin := "\x1b[31mFAKE PROMPT\x1b[0m"

    err := migrateConfig(cfg, "github.localhost", maliciousLogin)
    require.NoError(t, err)

    stored, err := cfg.Get([]string{"hosts", "github.localhost", "user"})
    require.NoError(t, err)
    // Demonstrates raw ESC bytes are persisted unsanitized.
    require.Contains(t, stored, "\x1b")
}
```
Follow-up: assert that `pkg/cmd/auth/logout` / `pkg/cmd/auth/switch` print this stored `user` value to `opts.IO.ErrOut` and that the captured output still contains `\x1b`, confirming it is not passed through `iostreams.Untrusted` before being written to the terminal.

	// Set the user key in case it was previously an anonymous user.
	c.Set(append(hostsKey, hostname, "user"), username)
	// Create the username key with an empty value so it will be
	// written even if there are no keys set under it.
	c.Set(append(hostsKey, hostname, "users", username), "")

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
