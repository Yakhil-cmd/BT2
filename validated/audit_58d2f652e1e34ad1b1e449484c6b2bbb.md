This confirms the filtering (`filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs`) is only applied to user/API-supplied `env` params in the controllers, via `EnvironmentVariables#permit` against an explicit variable whitelist. Unfiltered pull request label names inject arbitrary environment variables (e.g. `LD_LIBRARY_PATH`) into `Command#start`'s `PTY.spawn` for shell-interpreted `shipit.yml` steps - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (upcased) as an environment-variable key set to `"true"`, with no allowlist, and `TaskCommands#env`/`DeployCommands#env` merge `@stack.env` straight into the environment passed to `Command`, which `Command#start` feeds unfiltered into `PTY.spawn`. An unprivileged PR author can therefore set arbitrary environment-variable *names* (e.g. `LD_LIBRARY_PATH`, `LD_PRELOAD`, `BASH_ENV`, `PATH`) on the shell-interpreted `shipit.yml` step for their own review-stack, something the existing `EnvironmentVariables#permit` allowlist mechanism is never applied to.

### Finding Description
The broken binding: it should hold that `keys(env reaching PTY.spawn) ⊆ allowlisted_variable_names` (as enforced for user/API-submitted `env` via `EnvironmentVariables#permit` in `TaskDefinition#filter_envs` / `DeploySpec#filter_deploy_envs` / `#filter_rollback_envs`, invoked only in `app/controllers/shipit/{tasks,deploys,rollbacks}_controller.rb`). In fact, for review-stack-derived env this does not hold: `Shipit::ReviewStack#env` [1](#0-0) 
merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` with **no key allowlist at all**. Labels are populated straight from webhook payload names by `LabelCapturingHandler#capture_labels` [2](#0-1) 
with the params schema only requiring `labels: Array of {name: String}` [3](#0-2) 
— any label name a PR author can attach to their own PR (including `LD_LIBRARY_PATH`, case-insensitively) is captured and later upcased/merged verbatim into the env.

This unfiltered `@stack.env` is then merged into `TaskCommands#env` (used by `DeployCommands`, `RollbackCommands`, restart tasks, etc.): [4](#0-3) 
Note only `@task.env` (the very last merge) passes through the controller-side `EnvironmentVariables#permit` allowlist; `@stack.env` never does.

Finally, `Command#start` builds the process environment via `unbundled_env` (`BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)`) and spawns it with `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`: [5](#0-4) 
Because `parse_arguments` keeps a `shipit.yml` step (e.g. `"bundle exec rake db:migrate:status"`) as a single string argument, `PTY.spawn` executes it via `/bin/sh -c`, so the attacker-controlled env (including `LD_LIBRARY_PATH`) is applied to that shell and every binary it forks.

Existing guards do not stop this: `verify_signature`/webhook auth only ensures the payload comes from GitHub for a repo that has installed the app — it does not restrict *what* an authorized repository's own PR author can name a label; `drop_unhandled_event`, `ExplicitParameters` schema, and model validations only constrain shape/type, not env-variable-name safety; `EnvironmentVariables#permit` exists precisely for this purpose but is wired only into the API/controller-submitted `env` path, never into `Stack#env`/`ReviewStack#env`.

Exploit flow: attacker opens/owns a PR against a repository with review stacks enabled (any `provisioning_behavior`, including `prevent_with_label` as long as the label used is not the configured provisioning label so the stack is not archived) and adds a label named `ld_library_path` (case-insensitive, upcased by the code) to their own PR. Webhook `pull_request` events (`opened`/`labeled`/`reopened`) cause `LabelCapturingHandler` to persist that label on the stack's `pull_request.labels`. Any subsequent task/deploy/review-check step defined in `shipit.yml` for that review stack then executes with `LD_LIBRARY_PATH=true` in its process environment. Combined with attacker-controlled repository content (their own fork, which is checked out into the task's working/chdir directory), placing a directory/library named to match the dynamic loader's relative-path search under that value lets the attacker redirect library resolution for binaries invoked by the shell step, achieving code execution in the context of the Shipit worker.

### Impact Explanation
Any binary invoked from a shell-interpreted `shipit.yml` step for a review stack (review checks, restart tasks, deploy hooks) runs with attacker-chosen environment-variable keys forced to `"true"`. This is a control-plane violation: values reaching `PTY.spawn`'s process environment are supposed to be restricted to whitelisted variable names when attacker-influenced, but for review-stack pull-request labels there is no such restriction. This matches the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category, since dynamic-linking-influencing variables (`LD_LIBRARY_PATH`, potentially `LD_PRELOAD`, or execution-altering ones like `BASH_ENV`/`ENV`/`PATH`) can be injected into any binary spawned during that stack's task execution, and this is repeatable for every PR/label event on any repository that has review stacks enabled — the blast radius is any tenant repository configured for review stacks.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (a common Shipit feature) and use a shell-interpreted step somewhere in its `shipit.yml` (deploy/review/task steps, which is the default execution model for all such steps). No Shipit session, API token, or GitHub secret is needed — the attacker only needs to open a PR (or already control one) and apply/create a label with a chosen name, both of which are actions available to any unprivileged contributor able to label their own PR (or, for public repos, potentially triggerable via `labeled`/`opened` events depending on org permission settings). This is low-cost and fully repeatable/idempotent by re-labeling.

### Recommendation
Apply an explicit allowlist to `ReviewStack#env`'s label-derived keys (and any other pull-request-controlled data merged into `Stack#env`), e.g. reject/skip label names colliding with security-sensitive environment variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, `BASH_ENV`, `ENV`, `IFS`, etc.) or run all label-derived keys through the same `EnvironmentVariables#permit` mechanism used for user/API-submitted env, requiring an explicit per-repository allowlist of permitted label-derived variable names before merging them into `TaskCommands#env`/`DeployCommands#env`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin

        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES

      end
      @started = true
      self
    end
