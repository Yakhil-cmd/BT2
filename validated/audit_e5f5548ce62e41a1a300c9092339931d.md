### Title
`provision?` operator precedence bug bypasses `review_stacks_enabled: false` for `prevent_with_label` repositories - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` gates only the `provisioning_behavior_allow_all?` disjunct with `repository.review_stacks_enabled` due to Ruby `&&`/`||` precedence, leaving the `allow_with_label` and `prevent_with_label` disjuncts unconditional. An attacker who opens a pull request without the configured provisioning label against a repository with `review_stacks_enabled: false, provisioning_behavior: :prevent_with_label` still causes `ReviewStack.create!`, which unconditionally enqueues provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`, eventually running `shipit.yml` from the attacker-controlled branch.

### Finding Description
The binding the code intends to enforce is: `stack gets created` == `review_stacks_enabled == true AND (per-behavior label rule satisfied)`. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is ANDed only into the first clause, so when `provisioning_behavior` is `prevent_with_label` and the PR carries no provisioning label, the third disjunct evaluates to `true` regardless of `review_stacks_enabled`. `respond_to_pull_request_opened?` then returns true and `process` calls `ReviewStackAdapter#find_or_create!`, which calls `create!` [2](#0-1) , creating a `Shipit::ReviewStack` for the attacker's `branch` (`params.pull_request.head.ref`) and enqueuing it for provisioning unconditionally — there is no re-check of `review_stacks_enabled` at this stage.

Contrast with `LabeledHandler#respond_to_label_change?`, which correctly ANDs `repository.review_stacks_enabled` against the whole `(archive? || unarchive?)` expression [3](#0-2) , confirming the intended design is that `review_stacks_enabled` should gate all provisioning behaviors, not just `allow_all`. `ReopenedHandler#unarchive?` has the identical precedence bug [4](#0-3) .

No other guard intervenes: `respond_to_pull_request_opened?` only checks `params.action == "opened"` [5](#0-4) , and the `params` schema validates payload shape only, not authorization [6](#0-5) . The existing test suite never exercises `review_stacks_enabled: false` combined with `prevent_with_label`, which is why the gap went undetected; the only "disabled" test uses `behavior: :allow_all` [7](#0-6) .

### Impact Explanation
Any GitHub user able to open a PR against a tracked repository (no maintainer/Shipit privileges required) can force `Shipit::ReviewStack` creation and queue it for provisioning even though the repository operator explicitly disabled review stacks (`review_stacks_enabled: false`). Once queued, the review stack's `shipit.yml`/deploy steps from the attacker's branch are eventually executed via the standard provisioning/deploy `Command`/`PTY.spawn` pipeline, matching the Critical impact category (RCE on the deploy host, unauthorized stack creation for a tenant repo whose operator opted out). This is repeatable against every repository configured with `prevent_with_label` regardless of `review_stacks_enabled`, and also affects `ReopenedHandler`, widening blast radius across any tenant using this specific (common, "safe-by-default" intended) configuration.

### Likelihood Explanation
Preconditions: the target repository must exist in Shipit's tracked repositories with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false` — a configuration an operator would reasonably choose to fully disable review stacks while keeping the label rule for defense-in-depth. Attacker cost is trivial: open a PR without the provisioning label from any branch/fork they control; no secrets, tokens, or team membership required, and the webhook payload only needs the standard PR-opened fields. This is fully deterministic and reproducible.

### Recommendation
Fix operator precedence by explicitly parenthesizing so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for repos with review_stacks disabled even under prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, `assert_no_difference` fails because `Shipit::Stack.count` increases by 1 — `provision?` returns `true` even though `review_stacks_enabled` is `false`, demonstrating the binding `stack created == review_stacks_enabled` is broken.
