### Title
Pool creation via `initialize`/`initialize_with_permission` can be frontrun, stealing the `pool_creator` role and its permanent creator-fee stream - ([File: programs/cp-swap/src/instructions/initialize.rs])

### Summary
`initialize` (and `initialize_with_permission`) let *anyone* create a pool for a given token pair, and whoever's transaction lands first is permanently recorded as `pool_creator` in `PoolState`, entitling them to collect all future creator fees from that pool. Because the pool address is deterministic and the caller supplies the initial deposit ratio, a project's legitimate pool-creation transaction can be observed in the mempool and frontrun by an attacker, who claims the creator role and dictates the opening price, exactly analogous to the referenced Aave-Lens `createProfile` handle-squatting issue but with a direct financial payoff.

### Finding Description
`Initialize` accepts `creator: Signer<'info>` with no whitelist/permission check [1](#0-0) , and the pool PDA is fully determined by `amm_config`, `token_0_mint`, and `token_1_mint`: [2](#0-1) 

The caller-supplied `init_amount_0`/`init_amount_1` set the initial reserve ratio, and the same signer is recorded as `pool_creator`, which is permanent for the lifetime of the pool: [3](#0-2) [4](#0-3) 

`pool_creator` is not just informational — it is the sole authority allowed to withdraw the accumulated `creator_fees_token_0`/`creator_fees_token_1` via `CollectCreatorFee`, and even `collect_creator_fee_permissionless` still routes all proceeds to whatever `pool_creator` was recorded at pool-creation time: [5](#0-4) [6](#0-5) 

Because the pool PDA and vaults are derived only from `(amm_config, token_0_mint, token_1_mint)`, once any account has successfully called `initialize` for that pair, every subsequent legitimate `initialize` for the same pair simply fails (`create_or_allocate_account` will find the PDA already owned by the program), so the original creator can never re-claim the role. Meanwhile the attacker who won the race:
1. Is permanently recorded as `pool_creator` and collects all creator-fee revenue from that point on.
2. Chooses `init_amount_0`/`init_amount_1` arbitrarily, letting them set a manipulated opening price/ratio for the pool before the legitimate deposits/swaps occur.

### Impact Explanation
This is a direct, unrecoverable diversion of protocol value: the legitimate token/project deployer loses the `pool_creator` designation and, with it, all future creator-fee income from that pool for its entire lifetime; there is no mechanism in the program to reassign or reclaim `pool_creator`. Additionally, the attacker can seed the pool with a skewed reserve ratio purely under their control, harming subsequent swappers/depositors who assume the deployer set the price. This satisfies the "unauthorized privileged effect" / "insolvent accounting for the intended creator" bar, warranting Medium severity.

### Likelihood Explanation
Any pending `initialize`/`initialize_with_permission` transaction is visible in the mempool before confirmation. An attacker only needs to submit their own `initialize` call for the same `(amm_config, token_0_mint, token_1_mint)` triple with a higher priority fee/compute unit price to land first — no special privileges beyond being a normal, permissionless caller are required (for `initialize`; `initialize_with_permission` requires the `Permission` PDA, but any of the whitelisted permissioned creators, or a compromised/observing one, is equally able to race a competing pool creator).

### Recommendation
- Require that the intended `pool_creator`/fee recipient be pre-committed via a separate, protected step (e.g., a commit-reveal for the token pair, or requiring the pool address to be pre-registered/reserved by an authorized deployer before `initialize` is callable), so a racing transaction cannot silently capture the creator-fee role.
- Alternatively, decouple `pool_creator` fee rights from "whoever calls `initialize` first" by allowing the `amm_config` owner/admin to designate or update the `pool_creator` for newly created pools, or by making the initial price ratio validated against an expected/oracle value rather than fully attacker-controlled.

### Proof of Concept
1. Project deployer builds and signs an `initialize` transaction for mint pair `(TOKEN, USDC)` under `amm_config` index 0, intending to become `pool_creator` and later collect creator fees via `collect_creator_fee`.
2. Attacker monitors the mempool, observes the pending transaction (mints, amm_config, and hence the deterministic pool PDA per `create_pool` in `programs/cp-swap/src/instructions/initialize.rs` lines 364-388), and submits their own `initialize` call for the identical `(amm_config, TOKEN, USDC)` triple with a higher fee, choosing a self-favorable `init_amount_0`/`init_amount_1` ratio.
3. Attacker's transaction lands first; `pool_state.initialize(...)` records `pool_creator = attacker` (`programs/cp-swap/src/states/pool.rs` lines 134-152).
4. The deployer's original transaction now fails because the pool PDA already exists and is owned by the program (`create_pool`, lines 372-388).
5. From then on, only the attacker can call `collect_creator_fee` (`programs/cp-swap/src/instructions/collect_creator_fee.rs` line 12: `address = pool_state.load()?.pool_creator`) to withdraw all accumulated creator fees, and `collect_creator_fee_permissionless` still pays out exclusively to the attacker's address, permanently diverting the intended project's creator-fee revenue.
