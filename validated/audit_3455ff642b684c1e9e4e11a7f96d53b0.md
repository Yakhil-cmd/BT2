### Title
Uncaught exceptions from oscript formula evaluation crash the node process on all validators processing an AA trigger - (File: formula/evaluation.js)

### Summary
The Stellar report fixes a defect where invoking a native contract inside `try_call` could panic and crash the host instead of being caught and converted into a recoverable error. `ocore`'s AA (Autonomous Agent) formula interpreter has an analogous gap: the `evaluate()` function inside `formula/evaluation.js` is expected to route every failure through `setFatalError()`, which formats the error and invokes the callback so the caller (`aa_composer.js`) can gracefully bounce the AA response. However, several code paths inside `evaluate()` use bare `throw Error(...)` instead of `setFatalError()`, so a crafted/edge-case AA formula can throw a synchronous JS exception deep inside nested, asynchronous callback chains (`async.eachSeries`, `evaluate()` recursion) with no enclosing `try/catch`, propagating up to the event loop and crashing the Node.js process.

### Finding Description
`exports.evaluate` in [1](#0-0)  begins with direct `throw Error(...)` calls for malformed validation-state/opts, and internal helper branches such as `parse_date` also `throw Error("non-integer seconds")` directly rather than calling `setFatalError` [2](#0-1) .

All of the "normal" failure handling in `evaluate()` is designed to funnel through `setFatalError()`, which wraps error formatting in its own `try/catch` and always invokes the callback so callers never see a thrown exception [3](#0-2) . This is what allows `aa_composer.js`'s `evaluateAA`/`replace`/`executeStateUpdateFormula` to treat formula failures as ordinary bounce conditions [4](#0-3) [5](#0-4) .

But the code paths that instead use a raw `throw` bypass this design: because `evaluate()` is invoked recursively through nested callbacks and `async.eachSeries` (e.g. inside arithmetic operators, `func_call`, `remote_func_call`, `log`) rather than through a single synchronous call stack with a top-level `try/catch`, a `throw` fired deep inside one of these callback chains is not caught by anything in `formula/evaluation.js`, `aa_composer.js`, `handlePrimaryAATrigger`, or `handleAATriggers` [6](#0-5) [7](#0-6) . There is no global `process.on('uncaughtException', ...)` handler restoring safety net for the writer/AA-execution code path (the only `uncaughtException` references in the codebase are unrelated to AA execution). The exception therefore propagates out of the event loop and terminates the Node.js process.

### Impact Explanation
Because AA trigger processing (`handleAATriggers` → `handlePrimaryAATrigger` → `handleTrigger` → `evaluateAA`/formula evaluation) runs deterministically and identically on every full node that processes the same stabilized unit, an attacker who posts a single unit that triggers an AA whose (attacker-controlled or edge-case) formula reaches one of these bare `throw` sites will cause every full node that stabilizes and executes that trigger to crash simultaneously. This halts stabilization/AA-processing network-wide until node operators intervene, i.e., the network becomes unable to confirm new units that depend on stabilizing past this AA trigger. This differs from a p2p/network-flooding DoS: it is a deterministic crash induced purely by posting one properly-formed unit and having it reach main-chain stability, reachable by any unprivileged AA trigger sender.

### Likelihood Explanation
Reachability requires crafting a formula/trigger combination that survives `formula/validation.js`'s static checks yet exercises one of the un-guarded `throw` branches during actual evaluation (e.g. a `parse_date` argument that validates as a date string but produces non-integer milliseconds, or corrupted `objValidationState` state feeding the top-of-function guards). This is plausible but requires precise crafting of edge-case inputs; exploitability depends on whether such a formula can pass `formula/validation.js`'s pre-checks, which was not directly confirmed against every `throw Error` call site in `formula/evaluation.js` (49 occurrences found in total).

### Recommendation
Replace every raw `throw Error(...)` inside `formula/evaluation.js`'s `evaluate()`/helper functions (and any function reachable from formula evaluation of untrusted AA formulas) with calls to `setFatalError()`, so all failure paths are funneled through the callback-based error protocol instead of throwing. Additionally, wrap the top-level dispatch in `exports.evaluate`, `evaluateAA`, and `handleTrigger`/`handlePrimaryAATrigger` with a defensive `try/catch` that converts any escaped exception into a bounce/error response rather than letting it terminate the process, mirroring the "catch panics and convert to HostError" fix applied in the referenced Stellar commit.

### Proof of Concept
Not independently verified against live grammar/validation constraints from the index; a concrete PoC would require confirming that `formula/validation.js` allows a formula reaching, e.g., the `parse_date` branch at [8](#0-7)  with a date string producing non-integer seconds (`ts % 1000 !== 0`), which triggers `throw Error("non-integer seconds")` uncaught by any surrounding handler in `aa_composer.js`.
