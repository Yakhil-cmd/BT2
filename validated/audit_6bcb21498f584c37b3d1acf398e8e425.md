### Title
API client scoped to a single stack can read any stack's CCMenu status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single `Stack` via the `stack` association (`ApiClient#stack_id?`), and every scope-aware controller enforces that binding through `BaseController#stacks`/`#stack`, which filters `Stack.where(id: current_api_client.stack_id)` before resolving `params[:stack_id]`. `Api::CCMenuController` bypasses this entirely: it redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` relation, and redefines `authenticate_api_client` to also accept a plain `params[:token]`. The only remaining check, `require_permission :read, :stack`, only verifies the client's permission list contains `read:stack`; it never compares the target stack to `current_api_client.stack_id`.

### Finding Description
`ApiClient#check_permissions!` is a pure string-membership check on `permissions` and has no notion of which stack it's being invoked for: [3](#0-2) 

Stack scoping is enforced only in `BaseController#stacks`/`#stack`: [1](#0-0) 

`Api::CCMenuController` overrides both the authentication path and the stack lookup, dropping the scoping: [2](#0-1) 

The equality that should hold is: *stack the token authorises* (`current_api_client.stack_id`, when present) `==` *stack the request actually touches* (`params[:stack_id]` resolved). For every other API endpoint (`StacksController`, `TasksController`, `HooksController`, etc.) this holds because they resolve through `stacks.from_param!`. For `CCMenuController#show` it does not: `stack` is resolved from the global `Stack` relation, so a token created with `stack: <stack A>` and `permissions: [read:stack]` can fetch CCMenu status for any other stack B in the installation, as long as B's id/param resolves. This mirrors the reported `isIncreasing` flaw's structure: a narrower/local check (`sizeDelta` sign locally, or `read:stack` permission locally) is substituted for the check that actually matters (`self.size + sizeDelta` direction, or "is this the stack the client is bound to"), allowing the guarded action to succeed on an unintended target.

### Impact Explanation
This is an authorization-scope violation: a credential deliberately restricted to one stack (`ApiClient.stack_id` set) can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock status, etc., via `deploys_and_rollbacks.last`) for arbitrary other stacks in the Shipit installation, which is unauthorized read of stack/deploy state — matching the "unauthenticated/unauthorized read of stack state ... or deploy output" High-impact category, since the credential was never authorized to read that stack's state at all.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a routine, lower-trust credential intentionally restricted to one stack) can exploit this with a single authenticated GET request by substituting a different `stack_id` in the URL; the `here_come_the_walrus` fixture in the test suite already demonstrates this exact scoping pattern is otherwise relied upon elsewhere. [4](#0-3) 

### Recommendation
Remove the `stack`/`authenticate_api_client` overrides in `Api::CCMenuController`, or make `stack` resolve through the inherited `stacks.from_param!` (which honors `current_api_client.stack_id?`), so CCMenu status lookups are constrained to the same scope enforced everywhere else in the API.

### Proof of Concept
1. Create an `ApiClient` scoped to stack A (`stack: stack_a`, `permissions: ['read:stack']`), analogous to the `here_come_the_walrus` fixture.
2. Authenticate as that client and call `GET /api/stacks/<owner_b>/<repo_b>/<env_b>/ccmenu`, i.e. `Api::CCMenuController#show` with `params[:stack_id]` pointing at stack B, which the client is not scoped to.
3. Observe `stack` resolves via `Stack.from_param!(params[:stack_id])` (bypassing `stacks`), `require_permission :read, :stack` passes because the client's permission list contains `read:stack`, and the response renders stack B's CCMenu status/deploy data — data the client was never authorized to access.
