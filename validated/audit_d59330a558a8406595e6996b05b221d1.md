### Title
Cross-organization/cross-stack status forgery advances victim's merge queue - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no scoping to the organization/repository that authenticated the incoming webhook, and applies the forged GitHub status to every matching `Commit` row regardless of which `Stack` (and therefore which org) it belongs to. Because the `commits` table's uniqueness constraint is `(sha, stack_id)` rather than `sha` alone, the same sha can legitimately exist in multiple stacks/orgs (confirmed by fixtures where sha `367578b362bf2b4df5903e1c7960929361c39074` exists both in stack `shipit` and stack `shipit_canaries`), so an attacker who can produce a validly-signed webhook for their own org/repo can flip the status of a commit belonging to a completely different stack and trigger that victim stack's merge-queue processing.

### Finding Description
Binding claimed broken (before any check): `stack.organization_that_schedules_merges == organization_that_authenticated_webhook_signature`.

Trace:
- `Shipit::WebhooksController#verify_signature` derives `repository_owner` from the inbound JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and validates the HMAC signature against `Shipit.github(organization: repository_owner).webhook_secret` [1](#0-0) . This only proves the payload was signed by *some* organization's configured secret — it never associates that organization with the specific commit/stack the handler will subsequently mutate.
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . There is no filter on `commit.stack.repository.owner`, `commit.stack_id`, or any equivalent tie-back to `repository_owner` from the verified payload.
- The `commits` table enforces uniqueness only on the composite `(sha, stack_id)` index [3](#0-2) , and the same sha value is present across different stacks in the fixtures (`third`/`canaries_third` both use sha `367578b362bf2b4df5903e1c7960929361c39074` for stacks `shipit` and `shipit_canaries`) [4](#0-3) , demonstrating this is an expected, supported condition, not a theoretical edge case.
- `Commit#create_status_from_github!` calls `add_status`, which — on a transition to `pending` or `success` — invokes `stack.schedule_merges` [5](#0-4) , enqueuing `ProcessMergeRequestsJob` for that stack (confirmed by test `#add_status schedule a MergeMergeRequests job...`) [6](#0-5) .

Exploit flow: an attacker who controls (or is onboarded onto) their own repository/org authenticated against this Shipit instance sends (or triggers GitHub to send) a `status` webhook whose `sha` matches a commit sha that also exists in the victim's stack (e.g. via a shared/forked commit history, cherry-pick, or coincidentally identical content commit) with `state: "success"`. `verify_signature` passes because it only checks that the payload's declared org matches a legitimate webhook secret — the attacker's own. `StatusHandler#process` then updates the status on **every** `Commit` row with that sha, including the one in the victim's unrelated stack, and `Commit#add_status` fires `stack.schedule_merges` for the victim stack even though the victim's organization never authenticated or was even referenced in the signature check.

Existing guards do not catch this: `verify_signature` only checks the webhook signature against the org named in the payload, not against the stack ultimately mutated; the `ExplicitParameters` schema for `StatusHandler` only validates `sha`/`state`/etc. types, not ownership; there is no `require_permission!` or stack/org equality check anywhere in the `status` webhook path.

### Impact Explanation
A payload authenticated for organization/repository A causes a real, unauthorized side effect (merge-queue re-evaluation via `ProcessMergeRequestsJob`) on stack/organization B, whose secret was never used and whose maintainers never granted the attacker any permission. This is a cross-tenant write: a Shipit hosting instance backing multiple GitHub orgs/repos allows one tenant's webhook traffic to mutate another tenant's commit `Status` records and trigger merge-queue advancement for stacks it doesn't own. It matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "unauthorized merge."

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must serve multiple orgs/repos (single-tenant deployments are unaffected since `repository_owner` would then always match); (2) a sha collision must exist between the attacker's authenticated stack and the victim's stack — realistic for forked repositories, shared submodule/vendor commits, or mono-repo mirrors, and can also be engineered by an attacker who forks the victim's public repo (preserving upstream commit shas) into their own onboarded org. Attacker cost is low (one crafted/replayed `status` event); the action is repeatable against any sha shared across stacks. Feasibility depends on the multi-tenant sha-collision precondition, which is plausible but not universal.

### Recommendation
In `StatusHandler#process` (and any other sha-keyed handler), scope the `Commit` lookup to stacks belonging to the authenticated organization, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner })`, or pass `repository_owner`/`repository.full_name` from the controller into the handler and assert it against `commit.stack.repository.owner` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status webhook from org A must not schedule merges for a same-sha commit in org B's stack" do
  attacker_owned_stack = shipit_stacks(:shipit)          # authenticated org ("shopify")
  victim_stack         = shipit_stacks(:shipit_canaries) # unrelated stack/org
  shared_sha = 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'

  attacker_owned_stack.commits.create!(sha: shared_sha, ...)
  victim_stack.commits.create!(sha: shared_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  body = { 'sha' => shared_sha, 'state' => 'success' }.merge(repository_params).to_json # repository_params -> attacker's org

  Shipit::Stack.any_instance.expects(:schedule_merges).never.with { |s| s == victim_stack }
  # or explicitly:
  victim_stack.expects(:schedule_merges).never

  post :create, body: body, as: :json
end
```
This test, run with WebMock disabled (no live network) and `GithubHook`/`Hook.emit` stubbed as in the existing suite, currently fails (`schedule_merges` is invoked on `victim_stack`), demonstrating the cross-stack write.
