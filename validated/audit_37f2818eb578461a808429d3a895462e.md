### Title
API token stack-scope bypass in `CCMenuController` allows cross-stack read of deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`) can only see the single `Stack` it was bound to, by routing all stack lookups through the `stacks` helper, which filters by `current_api_client.stack_id`. `Shipit::Api::CCMenuController` breaks this binding: it overrides `stack` to look the record up directly via `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping helper, so any authenticated token with `read:stack` permission — even one explicitly scoped to a single stack — can fetch CCMenu status data for any stack in the Shipit instance.

### Finding Description
`ApiClient` supports scoping a token to one stack via `belongs_to :stack, optional: true` [1](#0-0) . `BaseController` implements that scoping via the `stacks`/`stack` helpers:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every other API controller (e.g. `StacksController#stack`) relies on this scoped helper, so a token whose `stack_id` is set can only resolve to the bound stack [3](#0-2) . Test fixtures explicitly document and test this invariant: the `here_come_the_walrus` client is scoped to the `shipit` stack with only `read:stack` [4](#0-3) , and `StacksControllerTest` asserts "an api client scoped to a stack will only see that one stack" [5](#0-4) .

`CCMenuController`, however, defines its own `stack` method that ignores the scoping entirely:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 
It only declares `require_permission :read, :stack` [7](#0-6) , which checks the permission list on the token (`check_permissions!`) [8](#0-7)  but never checks whether `params[:stack_id]` matches the `stack_id` the token was bound to. The equality that should hold — `stack the token authorizes == stack the token can touch` — is broken specifically for this controller because it never calls the shared `stacks` scoping helper.

`CCMenuController#show` then renders build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity, etc.) for whatever `stack_id` is supplied in the request, regardless of the token's actual binding [9](#0-8) .

### Impact Explanation
This is an authorization boundary break: a token deliberately scoped by an administrator to expose read access to a single stack (a common pattern, exemplified by the CCMenu URL feature itself, which auto-creates single-purpose `read:stack` clients) can be used to read deploy/task/CI status of any other stack managed by the same Shipit instance. This is an unauthorized cross-stack read of stack state / deploy output, matching the High-severity class described in the rules ("escalation into ... unauthenticated/unauthorized read of stack state, task streams or deploy output").

### Likelihood Explanation
Any holder of a valid, even narrowly-scoped, `read:stack` API token (e.g. one distributed for a single project's CI badge/CCMenu integration) can immediately exploit this by supplying a different `stack_id` in the request — no additional privilege, secret guessing, or race condition is required. The attack is a single unauthenticated (from the app's perspective, unauthorized) API call.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot resolve stacks outside their bound `stack_id`.

### Proof of Concept
1. As an administrator, create an `ApiClient` scoped to `stack_id = A` with only the `read:stack` permission (as done automatically by `CCMenuUrlController#client`, or via the `ApiClients` admin UI).
2. Using that client's `authentication_token`, issue:
   `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu.xml` (i.e., pass a `stack_id` for stack `B`, not `A`), authenticating with Basic auth using the token.
3. `CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])` [10](#0-9) , `require_permission :read, :stack` succeeds because the token has `read:stack`, and `stack` resolves `Stack.from_param!(params[:stack_id])` for stack `B` with no ownership check — returning full CCMenu status (build/deploy status) for stack `B`, a stack the token was never authorized to see.
