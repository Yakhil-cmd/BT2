### Title
Session Fixation in OAuth Callback via Missing `reset_session` - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`Shipit::GithubAuthenticationController#callback` sets `session[:user_id]` and `session[:authenticated]` on the pre-existing session after a successful GitHub OAuth exchange, but never calls `reset_session` to rotate the session identifier. With Rails' default cookie-store session, this allows an attacker who pre-establishes a session id in the victim's browser to inherit full authentication once the victim completes the OAuth flow in that same session.

### Finding Description
The broken binding is: `session_id_before_login == session_id_after_login`, i.e. the session identifier issued before `#request`/`#callback` is invoked is identical to the one used to authenticate the freshly-signed-in user afterward.

Tracing `app/controllers/shipit/github_authentication_controller.rb`:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```
There is no `reset_session` call anywhere in `#callback` (confirmed by grep — the only `reset_session` calls in this controller are in `#logout` and in `Shipit::Authentication#force_github_authentication` for stale/fresh-login expiry, at `app/controllers/concerns/shipit/authentication.rb:23`). The routes at `config/routes.rb:70-75` expose `GET /github/auth/github` (`:request`, unauthenticated omniauth entry) and `GET/POST /github/auth/github/callback` (`:callback`), both reachable without any prior session.

Exploit flow: the attacker visits `GET /github/auth/github` (or otherwise causes a session cookie to be set for the victim's browser, e.g. handing them a pre-set cookie via a shared kiosk or a response the attacker controls) and records the resulting session id/cookie. The attacker then causes the victim to complete the GitHub OAuth flow using that same session (e.g. by luring them to `/github/auth/github` from the fixed session). Because `#callback` writes `session[:user_id]` into the existing session object rather than issuing a new one, the session id known to the attacker now maps to the victim's authenticated identity — including access to `current_user`, which is loaded from `session[:user_id]` in `find_current_user` (`app/controllers/concerns/shipit/authentication.rb:40-42`), and whose `github_access_token` was just set to the victim's real OAuth token (`sign_in_github`, line 30-34).

None of the existing guards prevent this: `force_github_authentication` only calls `reset_session` on stale/expired logins, not on fresh sign-in; `current_user.authorized?` checks team membership, not session provenance; there is no CSRF/session-binding check on the callback route since OAuth callbacks are inherently a GET/POST from a redirect. This is a classic session-fixation flaw independent of any GitHub-side protections.

### Impact Explanation
Once fixation succeeds, the attacker holds a session cookie that Rails recognizes as an authenticated session for the victim's `User` record, with `current_user.github_access_token` equal to the victim's live GitHub token. Using that session, the attacker can perform any action the victim is authorized to do in Shipit — trigger deploys, rollbacks, merge requests, or read task output — as the victim, and could exfiltrate the victim's GitHub OAuth token through any Shipit feature that surfaces it. This matches "authentication bypass (session fixation)" / unauthorized deploy or rollback, Critical/High per the given severity taxonomy.

### Likelihood Explanation
Requires: (1) default cookie-store sessions with a stable session id across the OAuth handshake (default Rails config, no `expire_after`/rotation logic added by this engine), (2) attacker's ability to get a fixed session id into the victim's browser and get the victim to complete OAuth in that same browser session — realistic in shared-computer/kiosk scenarios, or via any mechanism that lets the attacker set a cookie for the Shipit domain before redirecting the victim to `/github/auth/github`. No Shipit secrets, GitHub App keys, or privileged roles are needed. This is a well-known, low-cost attack pattern when `reset_session` is omitted after privilege elevation.

### Recommendation
Call `reset_session` in `#callback` before writing `session[:user_id]`/`session[:authenticated]`, re-establishing `return_url`/`omniauth.origin` handling afterward (since `reset_session` clears the session hash), e.g.:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  user_id = sign_in_github(auth)
  reset_session
  session[:user_id] = user_id
  session[:authenticated] = true
  redirect_to(return_url)
end
```

### Proof of Concept
`ActionDispatch::IntegrationTest` under `test/controllers/github_authentication_controller_test.rb`:
1. `get shipit.github_authentication_path` to establish a session; capture `session_id_before = @request.session.id` (or cookie jar's session cookie value).
2. Stub `request.env['omniauth.auth']` via `OmniAuth.config.mock_auth[:github]` / `env: { 'omniauth.auth' => ... }` as done elsewhere in the test suite.
3. `get shipit.github_authentication_callback_path`.
4. Assert `session[:user_id]` is now present and equals the mocked user's id.
5. Assert `session_id_after = @request.session.id` (or the session cookie) — with the current code, `session_id_after == session_id_before` (vulnerable); after the fix, they must differ.
