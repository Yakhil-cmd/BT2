## Title
Stale reward-calculation snapshot vs. live `StakesCache` in `build_updated_stake_reward` can panic every node during epoch-boundary reward distribution - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
`build_updated_stake_reward` compares a stake's *current* delegation (fetched live from `stakes_cache_accounts` at distribution time) against the delegation baked into `partitioned_stake_reward.inflation.stake`, which was computed from an earlier snapshot of the stake account. If a staker's own `Split`/`Withdraw`/`Deactivate`/`Merge` mutates `delegation.stake` between when that reward entry was computed and when `store_stake_accounts_in_partition` runs on it, the `assert_eq!` at [1](#0-0)  fires and panics.

## Finding Description
`build_updated_stake_reward` fetches the account's *live* state from `stakes_cache_accounts` (the current `StakesCache`, not a frozen calculation-time copy) via `stakes_cache_accounts.get(&partitioned_stake_reward.stake_pubkey)` [2](#0-1) . It then computes `expected_delegation = stake.delegation.stake (current) + stake_reward` and asserts it equals `new_stake.delegation.stake`, which is the delegation value baked into the `PartitionedStakeReward` from an earlier reward computation pass [3](#0-2) .

The mitigating mechanism is `recalculate_partitioned_rewards_if_active`/`recalculate_stake_rewards`, which is meant to re-derive `all_stake_rewards` from the *current* `StakesCache` on every new block during the reward window, keeping the "current" and "baked-in" delegation values consistent [4](#0-3) [5](#0-4) . However this recalculation happens at the *start* of block construction (when the new bank is created, before that block's own transactions execute). `store_stake_accounts_in_partition`/`build_updated_stake_reward`, by contrast, run when the block is finalized (in `distribute_partitioned_epoch_rewards`, invoked at freeze time) and read the stakes cache *after* the block's transactions have executed and updated it via `update_stakes_cache`/`check_and_store` [6](#0-5) [7](#0-6) . Any transaction included in that same distribution block that mutates the target stake account's `delegation.stake` (e.g. `Split`, partial `Withdraw` combined with `DeactivateDelinquent`, `Merge`) will be reflected in the live `StakesCache` read by `store_stake_accounts_in_partition`, while the reward entry for that pubkey still carries the pre-transaction delegation amount computed at the start of the block. This produces `expected_delegation != new_stake.delegation.stake`, tripping the `assert_eq!` in `build_updated_stake_reward` and panicking the bank-processing thread deterministically on every validator that processes the block, since it is triggered purely by the block's transaction data rather than validator-local state.

The `AccountNotFound` (removed via `Withdraw`-to-zero) and `ArithmeticOverflow` paths are already handled gracefully as `Result::Err` and do not panic [8](#0-7) ; the vulnerable path is specifically the `assert_eq!` for a stake account whose delegation amount changed but is still present in `stakes_cache_accounts`. Note this assert only executes when `adjust_delegations_for_rent` (the `relax_post_exec_min_balance_check` feature) is `false`; when that feature is active the code instead calls `adjust_delegation_for_rent`, which does not assert (a different, non-panicking code path) [9](#0-8) . I was unable to determine from the available index content whether `relax_post_exec_min_balance_check` is currently activated on mainnet-beta; if it is fully activated everywhere the assert branch may be dead code in production, which would eliminate this specific panic path (though the underlying "current vs. calculation-time delegation" mismatch concept would still be latent). This is a material open question for exploitability that could not be resolved with the tools available.

## Impact Explanation
If reachable, this is a network-wide, deterministic panic triggered by a single unprivileged user's normal stake instruction landing in the same block as that user's own reward-distribution partition entry — i.e., a liveness/consensus halt at every epoch boundary distribution block, matching Agave's highest-severity "network crash / consensus halt" bounty category. It requires no validator control, no leaked keys, and no mocked paths — only ordinary `Split`/`Withdraw`/`Deactivate` instructions signed by the staker's own withdraw authority.

## Likelihood Explanation
Feasibility depends on:
1. Confirming `relax_post_exec_min_balance_check` (the `adjust_delegations_for_rent` feature) is not universally active for the assert branch to be live — unresolved from available context.
2. The attacker must get a stake-mutating transaction for their own stake account included in the exact block that also contains their reward-distribution entry, requiring some knowledge or control of block timing/hashing to land in the right partition and block (the partition assignment is a hash of stake pubkeys against `parent_blockhash`, and the distribution window spans multiple blocks (~432 blocks per the given scope), so an attacker could simply attempt this every block their pubkey is assigned to; this is a feasible but not guaranteed single-attempt condition — repeatable since the attacker can retry across epochs).

Given the unresolved feature-activation state and the need to land the mutating transaction in the exact distribution block, likelihood is plausible but not fully confirmed without further validation (e.g., checking mainnet feature-gate activation status and precisely which block `recalculate_partitioned_rewards_if_active` executes relative to transaction execution in that same block).

## Recommendation
- Re-validate/re-derive `partitioned_stake_reward.inflation.stake` from the live `stakes_cache_accounts` snapshot at the exact point `store_stake_accounts_in_partition` reads it (i.e., recompute the expected delegation using the same live snapshot rather than an earlier-computed value), or
- Replace the `assert_eq!` with a `DistributionError` variant (analogous to `AccountNotFound`/`ArithmeticOverflow`) so a mismatch safely no-ops/burns that stake's reward instead of panicking, and
- Ensure `recalculate_partitioned_rewards_if_active` is invoked after the block's transactions have been applied to the `StakesCache` (or otherwise guarantee no attacker-controlled transaction can execute between the recalculation snapshot and the `store_stake_accounts_in_partition` read within the same block).

## Proof of Concept
```rust
// runtime/src/bank/partitioned_epoch_rewards/distribution.rs (test module)
//
// Goal: show that mutating a stake account's delegation (via a normal Split)
// between the reward-calculation snapshot (baked into PartitionedStakeReward)
// and the distribution-time read of the live StakesCache triggers the
// assert_eq! panic in build_updated_stake_reward, instead of a graceful
// DistributionError.

#[test]
#[should_panic(expected = "stake reward delegation must be consistent")]
fn test_build_updated_stake_reward_panics_on_stale_delegation_after_split() {
    let (genesis_config, _mint_keypair) = create_genesis_config(1_000_000 * LAMPORTS_PER_SOL);
    let bank = Bank::new_for_tests(&genesis_config);
    let stake_history = StakeHistory::default();
    let distribution_epoch = bank.epoch + 1;
    let new_warmup_cooldown_rate_epoch = bank.new_warmup_cooldown_rate_epoch();
    let rent = bank.rent_collector.rent.clone();
    let rent_exempt_reserve = rent.minimum_balance(StakeStateV2::size_of());

    let voter_pubkey = Pubkey::new_unique();
    let stake_pubkey = Pubkey::new_unique();

    // Delegation as it existed at reward-calculation time: stake = 1_000_000
    let original_stake = Stake {
        delegation: Delegation { voter_pubkey, stake: 1_000_000, ..Delegation::default() },
        credits_observed: 10,
    };
    let starting_lamports = rent_exempt_reserve + 1_000_000;
    let mut stake_account = AccountSharedData::new(
        starting_lamports, StakeStateV2::size_of(), &solana_stake_interface::program::id());
    stake_account.set_state(&StakeStateV2::Stake(Meta::default(), original_stake, StakeFlags::default())).unwrap();
    bank.store_account(&stake_pubkey, &stake_account);

    // Reward entry computed from the ORIGINAL (pre-mutation) delegation:
    // new_stake.delegation.stake == original_stake + stake_reward
    let stake_reward = 100;
    let mut new_stake = original_stake;
    new_stake.delegation.stake += stake_reward; // baked-in "expected" value from calculation phase

    let partitioned_stake_reward = PartitionedStakeReward {
        stake_pubkey,
        inflation: InflationReward { stake: new_stake, stake_reward, commission_bps: Some(0) },
        block_reward: 0,
    };

    // ATTACKER ACTION: within the same distribution block, the staker
    // Splits/reduces their own stake, mutating delegation.stake in the
    // live StakesCache to a value that no longer matches the baked-in reward.
    let mut mutated_account = stake_account.clone();
    let mut mutated_stake = original_stake;
    mutated_stake.delegation.stake = 500_000; // reduced via Split
    mutated_account.set_lamports(rent_exempt_reserve + 500_000);
    mutated_account.set_state(&StakeStateV2::Stake(Meta::default(), mutated_stake, StakeFlags::default())).unwrap();
    bank.store_account(&stake_pubkey, &mutated_account); // reflects in StakesCache via check_and_store

    let stakes_cache = bank.stakes_cache.stakes();
    let stakes_cache_accounts = stakes_cache.stake_delegations();

    // This should panic via assert_eq! instead of returning a safe DistributionError.
    let _ = Bank::build_updated_stake_reward(
        distribution_epoch,
        &stake_history,
        new_warmup_cooldown_rate_epoch,
        stakes_cache_accounts,
        &partitioned_stake_reward,
        &rent,
        /* adjust_delegations_for_rent */ false,
        true,
    );
}
```
Expected (buggy) behavior: the test panics with `"stake reward delegation must be consistent with the updated stake account lamport balance"`, demonstrating the crash. Expected (fixed) behavior: `build_updated_stake_reward` should return `Err(DistributionError::...)` (a new, non-panicking variant) instead of panicking, and the outer integration-level test should assert `distribute_partitioned_epoch_rewards` never panics regardless of concurrent staker-initiated account mutations within the reward window.

**Caveat:** I could not confirm from the available indexed code whether `relax_post_exec_min_balance_check` is fully activated on mainnet-beta (which would make the `assert_eq!` branch unreachable in production), nor pin down the exact ordering guarantee between `recalculate_partitioned_rewards_if_active` and transaction execution within the same block. These points should be verified in a full checkout/Devin session before treating this as a confirmed, exploitable finding.

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
        drop(stakes);
        let partition_indices = hash_rewards_into_partitions(
            &stake_rewards,
            &epoch_rewards_sysvar.parent_blockhash,
            epoch_rewards_sysvar.num_partitions as usize,

    fn update_stakes_cache(
        &self,
        txs: &[impl SVMMessage],
        processing_results: &[TransactionProcessingResult],
    ) {
        debug_assert_eq!(txs.len(), processing_results.len());
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        txs.iter()
            .zip(processing_results)
            .filter_map(|(tx, processing_result)| {
                processing_result
                    .processed_transaction()
                    .map(|processed_tx| (tx, processed_tx))
            })
            .filter_map(|(tx, processed_tx)| {
                processed_tx
                    .executed_transaction()
                    .map(|executed_tx| (tx, executed_tx))
            })
            .filter(|(_, executed_tx)| executed_tx.was_successful())
            .flat_map(|(tx, executed_tx)| {
                let num_account_keys = tx.account_keys().len();
                let loaded_tx = &executed_tx.loaded_transaction;
                loaded_tx.accounts.iter().take(num_account_keys)
            })
            .for_each(|(pubkey, account)| {
                // note that this could get timed to: self.rc.accounts.accounts_db.stats.stakes_cache_check_and_store_us,

                self.stakes_cache.check_and_store(
                    pubkey,
                    account,
                    new_warmup_cooldown_rate_epoch,
                    use_fixed_point_stake_math,
                );
