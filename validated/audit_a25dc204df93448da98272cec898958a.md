Cross-tenant `Status` forgery via SHA-only lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, filtering only by the git SHA and never by the organization/repository that authenticated the webhook. Because `WebhooksController#verify_signature` verifies the payload against the org named in the attacker-controlled `repository.owner.login` field, an attacker who owns any GitHub repo (with its own webhook secret) can forge a `status` event that writes a `Status` row onto any commit in the DB whose SHA happens to match — including a commit belonging to a completely unrelated stack/org.

### Finding Description
The claimed binding is: `organization_that_signed_the_webhook (== params.dig('repository','owner','login'), verified via Shipit.github(organization: repository_owner))` **should equal** `organization_owning_every_Commit_row_mutated_by_StatusHandler#process (commit.stack.repository.owner)`.

Tracing the path:
- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` purely from the JSON body: [1](#0-0) . It then fetches `Shipit.github(organization: repository_owner)` and checks the HMAC signature against **that org's own secret**. This only proves the request was signed by whoever owns the org named in the payload — i.e., the attacker's own org, since the attacker chooses `repository.owner.login` and signs with their own secret.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) then does: [2](#0-1) . Note there is no `.joins(:stack)` / no filter on `stack.repository`/organization at all — it is a global, unscoped lookup keyed only by `sha`.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) unconditionally calls `statuses.replicate_from_github!(stack_id, github_status)`, writing a `Status` record tied to `commit.stack_id`, whatever stack that commit belongs to: [3](#0-2) .

So the two sides of the equality diverge: the signature only proves attacker controls org `attacker`, but the write lands on any `Commit` row across the entire table matching the SHA, regardless of which stack/org it belongs to.

Existing guards do not close this gap:
- `verify_signature` only checks the payload's self-declared owner against that owner's own secret — it never cross-checks against the commit(s) actually being mutated.
- `drop_unhandled_event` and the `ExplicitParameters` schema (`params do ... end` in `StatusHandler`) validate shape, not ownership.
- There is no model-level validation in `Commit`/`Status`/`Stack` that ties a `create_status_from_github!` call back to the org that authenticated the webhook.

The existing test `":state create a Status for the specific commit"` in test/controllers/webhooks_controller_test.rb:42-59 demonstrates the normal, intra-tenant flow works via bare SHA match with no repository check, confirming the lack of scoping is exactly the code path in production, not test-only behavior.

SHA collision across repos is achievable without a cryptographic break: git SHAs are content-addressed, so an attacker can produce a commit in their own repo with byte-identical tree/parent/author/committer/message/timestamps to an existing victim commit (e.g., by cherry-picking or fetching the victim's public commit and re-pushing it into their own repo/branch) — no genuine SHA-1 collision (Shattered-style) needed, just a duplicate commit object, which is trivial when victim commits are public or being copied intentionally.

### Impact Explanation
The attacker forges a `success` (or any) CI status onto a commit belonging to a stack they do not own and never authenticated for (e.g. `victim/prod`). Since `Commit#deployable?` and `Stack#schedule_merges`/continuous delivery checks rely on aggregated `Status`/`status` state (see `add_status` in app/models/shipit/commit.rb:366-386, which calls `stack.schedule_merges` and `ContinuousDeliveryJob` triggers on success), this can push a merge/deploy decision for `victim/prod` that depends on a fabricated green status the attacker fully controls the content and timing of. This is a payload for one repository (attacker's) mutating another repository's (victim's) `Commit`/`Status` state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It's repeatable against any stack whose tracked commit SHA the attacker can reproduce/copy, and the attacker needs no privilege beyond owning any GitHub repo with a Shipit App install (or any org registered with `Shipit.github`).

### Likelihood Explanation
Preconditions: attacker must have (a) their own GitHub org/repo registered in Shipit with a `webhook_secret` they control (a normal, low-privilege GitHub App install available to any repo owner using Shipit), and (b) knowledge of a SHA tracked by the victim stack, which is typically public information (commit SHAs are visible on GitHub, in PRs, CI logs, Shipit's own UI, etc.) and can be reproduced by copying the exact commit content into their own repo. No secrets, sessions, or elevated roles are needed — only a POST to the public `/webhooks` endpoint. This is highly feasible and repeatable per-commit.

### Recommendation
Scope `StatusHandler#process` (and other webhook handlers using bare `Commit.where(sha: ...)` such as any similarly structured handler) to only match commits whose `stack.repository` corresponds to the authenticated `repository_owner`/`repository.full_name` from the verified payload, e.g. join through `Stack`/`Repository` and filter by `owner` and `name` matching the webhook payload before calling `create_status_from_github!`. Alternatively, pass the verified repository context from the controller into the handler and enforce `commit.stack.repository.full_name == payload_repository_full_name` before mutating any `Status`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from an unrelated org must not write a Status for a commit owned by another stack" do
  request.headers['X-Github-Event'] = 'status'

  victim_commit = shipit_commits(:first) # belongs to stack `shipit`, org `shopify`
  colliding_sha = victim_commit.sha

  attacker_payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'owner' => { 'login' => 'attacker' } }
  }.to_json

  # Attacker's own org has its own registered webhook_secret they control
  Shipit.stubs(:github).with(organization: 'attacker').returns(
    stub(verify_webhook_signature: true)
  )

  assert_no_difference 'victim_commit.statuses.count' do
    post :create, body: attacker_payload, as: :json
  end
  # Currently FAILS: statuses.count increases by 1 because
  # Commit.where(sha: colliding_sha) matches victim_commit regardless of
  # the org that signed the request.
end
```
Binding assertions to make explicit in the test:
- Left side: `Shipit.github(organization: 'attacker').verify_webhook_signature(...)` returns `true` (attacker authenticated only as `attacker`).
- Right side (should hold but doesn't): `victim_commit.stack.repository.owner == 'attacker'` — this is `false` (it's `'shopify'`/`victim`), yet the write still occurs, proving the binding failure.
