### Title
Webhook organization used for HMAC signature verification is not bound to the repository the payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/organization configuration (and therefore which `webhook_secret`) to use for HMAC verification purely from an attacker-supplied JSON field: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```

`repository_owner` is derived from the raw, unauthenticated request body itself: [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Separately, every `Handler` resolves *which repository/stack is actually acted upon* from a different, independent field of the same payload: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Shipit.github(organization:)` supports per-organization configuration, each with its own `webhook_secret` (documented in `config/secrets.development.example.yml` and `docs/setup.md`), which is the entire reason `verify_signature` needs to pick the correct secret based on `repository_owner`. However, nothing anywhere cross-checks that `repository.owner.login` (used to pick the verification secret) matches `repository.full_name` (used to pick the target `Repository`/`Stack`). These are two independent leaves of the same JSON body, and the signature only proves the *body as a whole* was signed with the secret belonging to whatever organization the attacker declared in `repository.owner.login` — it proves nothing about which repository the handlers subsequently act on.

This is structurally the same bug class as the reported `_updateMultiDeposit` flaw: a secondary field (`retainERC4626` / here, `repository.full_name`) is used downstream without being re-validated against the value that was authorized/verified (`superformIds` / here, `repository.owner.login`), breaking the intended binding `authenticated_organization == target_repository_owner`.

### Impact Explanation
An attacker who legitimately controls their own GitHub organization/repository with the Shipit GitHub App installed (and therefore legitimately knows or can trigger requests signed with their own org's `webhook_secret`) can construct a raw HTTP POST to `/webhooks` where:
- `repository.owner.login` (or `organization.login`) = the attacker's own organization (so `verify_signature` selects and validates against the attacker's own known secret and passes), and
- `repository.full_name` = a victim repository already registered in Shipit under a different organization.

Because `Repository.from_github_repo_name` is looked up globally, without any check that its owner equals the organization whose secret authenticated the request, all downstream handlers act on the victim's stacks:
- `PushHandler` invokes `stack.sync_github(expected_head_sha: params.after)` on the victim's stacks with an attacker-chosen `after` SHA.
- `StatusHandler`/`CheckSuiteHandler` can write forged CI status/check results against victim commits, which the merge queue and continuous-delivery logic use to decide whether to trigger deploys.

This is a cross-organization/cross-repository write achieved with a validly-verified signature belonging to a different (attacker-controlled) organization — directly matching the "Critical: cross-repository writes / unauthorized deploy" impact bar, since forged CI status combined with continuous deployment can result in an unauthorized deploy being triggered on a repository the attacker does not own.

### Likelihood Explanation
Exploitation requires only that the attacker operate their own GitHub organization/repository with the Shipit app installed (a normal, unprivileged setup step available to anyone who can install a GitHub App on their own org) and the ability to send a raw HTTP request with a custom body/signature to Shipit's public `/webhooks` endpoint — no Shipit session, API token, or privileged GitHub role on the victim repository is required. The only non-trivial requirement is that the deployment uses (or can be made to use) a multi-organization GitHub App configuration with distinct webhook secrets per organization, which is an explicitly documented and supported configuration in this engine (`docs/setup.md`, `config/secrets.development.example.yml`).

### Recommendation
In `Shipit::Webhooks::Handlers::Handler`, verify that the resolved `Repository`'s owner/organization matches the organization used to authenticate the webhook (i.e., pass the verified `repository_owner`/organization from the controller into the handler and assert equality against `repository.full_name`'s owner segment, or against the `Repository#owner` used for scoping the App installation) before performing any lookup or write. Reject the payload if they don't match.

### Proof of Concept
1. Attacker installs the Shipit GitHub App on their own org `attacker-org`, obtaining a legitimate installation whose webhook deliveries are signed with `attacker-org`'s `webhook_secret` (multi-org config as documented in `docs/setup.md`).
2. Attacker computes `sha1=HMAC(attacker-org secret, body)` for a crafted body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker POSTs this body with header `X-Github-Event: push` and the computed `X-Hub-Signature` to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret [4](#0-3) .
5. `PushHandler#process` then resolves stacks via `repository_name = "victim-org/victim-repo"` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack, despite the request never having been signed by victim-org's credentials.
