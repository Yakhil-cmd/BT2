### Title
Unvalidated `creator` address in `initialize_with_permission` permanently locks pool creator fees - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
In `InitializeWithPermission`, the `creator` account is declared as a bare `UncheckedAccount` with no signer requirement, no `address` constraint, and no check that it is a valid/controllable address [1](#0-0) . Its key is stored permanently into `PoolState.pool_creator` via `pool_state.initialize(...)`, and this value later gates all creator-fee withdrawal paths. Because the value is never validated (e.g., against the default `Pubkey::default()`, the payer, or any other sane fallback), the `payer` calling this permissioned instruction can set `creator` to an arbitrary, uncontrollable pubkey, permanently freezing all creator fees the pool will ever accrue — directly analogous to the reported "no validation of the address parameter value in the constructor" bug class in `LidoMevTxFeeVault.sol`.

### Finding Description
`PoolState::initialize` writes whatever pubkey is supplied as `pool_creator` with no sanity check [2](#0-1) . In the permissionless-swapper-facing `initialize` instruction the equivalent field is a `Signer<'info>` (`creator`), which at least proves the caller controls the key [3](#0-2) . However, `initialize_with_permission` deliberately decouples payer and creator, making `creator` only an `UncheckedAccount` with a doc-comment claiming it is "creator of pool" but enforcing nothing about it [4](#0-3) . The instruction handler passes `ctx.accounts.creator.key()` straight into `pool_state.initialize(...)` without any zero-address, PDA-ownership, or reachability check.

Downstream, both fee-collection code paths trust this stored value absolutely:
- `CollectCreatorFee` requires the `creator` account to be a `Signer` whose key equals `pool_state.pool_creator` [5](#0-4) .
- `CollectCreatorFeePermissionless` allows anyone to trigger the transfer, but the destination ATA authority is still fixed to `pool_state.pool_creator` [6](#0-5) .

If `pool_creator` is set to a pubkey with no known private key (e.g., `Pubkey::default()`, a random unowned address, or an address that happens to collide with a PDA from an unrelated program that cannot sign), then:
- `CollectCreatorFee` can never succeed because no one can produce a valid signature for that key.
- `CollectCreatorFeePermissionless` will still succeed in moving tokens, but into an ATA owned by an address nobody controls — the funds are irrecoverably stranded there.

### Impact Explanation
This results in permanent freezing of the pool's accrued creator fees, one of the four accepted impact categories (permanent freezing of user/LP funds). Every swap on the pool accrues `creator_fees_token_0` / `creator_fees_token_1` in `PoolState` [7](#0-6) , and once `pool_creator` is bricked, those balances (and all future accruals) are permanently unreachable by anyone, with no admin or governance path to reset `pool_creator` after pool creation.

### Likelihood Explanation
The `initialize_with_permission` instruction is gated by a `Permission` PDA check on the `payer`, so only accounts with permission can create such pools [8](#0-7) . However, within that instruction, the `payer` fully controls the `creator` field with zero constraints — no signer requirement, no default-address check — making the misconfiguration trivial to trigger either accidentally (e.g., passing an unrelated PDA or a placeholder key) or maliciously by a permissioned pool creator wanting to grief a pool's creator-fee accounting. No additional privilege beyond what is already required to call the instruction is needed to hit the bug.

### Recommendation
Add validation on `creator` in `InitializeWithPermission`, e.g.:
- Reject `Pubkey::default()` / the System Program ID.
- Consider requiring `creator` to at least be distinct from `authority`/`pool_state`/other program-owned PDAs that could never sign.
- Optionally, provide a permissioned admin instruction to update `pool_creator` for pools created via `initialize_with_permission`, so a misconfigured value doesn't require a pool redeploy (mirroring the original report's redeploy concern).

### Proof of Concept
1. A permissioned `payer` calls `initialize_with_permission`, supplying `creator = Pubkey::default()` (or any pubkey with no known keypair) along with legitimate token mints and initial liquidity.
2. The instruction succeeds; `pool_state.pool_creator` is now set to that unreachable pubkey [9](#0-8) .
3. Users perform swaps on the pool; `creator_fees_token_0/1` accrue in `PoolState`.
4. `collect_creator_fee` can never be called because no signer can match `pool_state.pool_creator` [5](#0-4) .
5. `collect_creator_fee_permissionless` can be called by anyone, but funds are sent to an ATA owned by the unreachable `creator` address [10](#0-9) , permanently locking the accumulated creator fees.
