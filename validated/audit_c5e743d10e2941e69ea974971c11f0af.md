### Title
Integer overflow in fixed-denomination asset cap validation allows supply-inflation bypass - ([File: validation.js])

### Summary
`validateAssetDefinition()` in `validation.js` sums `denomInfo.count_coins * denomInfo.denomination` for every denomination entry of a fixed-denomination asset to cross-check against the declared `cap`. Both operands are only checked to be positive integers with `isPositiveInteger`, but `count_coins` has no upper bound at all, and `denomination` is bounded by `MAX_CAP` only under a version/mci gate. Their product is accumulated in a plain JS `number`, which silently loses precision once it exceeds `Number.MAX_SAFE_INTEGER` (2^53-1), exactly the integer-overflow bug class described in the gawk `builtin.c` report (arithmetic overflow used to corrupt a downstream size/consistency check). Here the corrupted value is `total_cap_from_denominations`, which is the sole self-consistency check tying an asset's advertised `cap` to its `denominations` array. [1](#0-0) 

### Finding Description
When an author posts an `asset` definition message with `fixed_denominations: true`, each entry of `payload.denominations` is validated independently:
- `denomInfo.denomination` must be a positive integer, and only checked against `constants.MAX_CAP` when a particular upgrade MCI has passed [2](#0-1) 
- `denomInfo.count_coins` must be a positive integer with **no upper bound check whatsoever** [3](#0-2) 

The code then computes `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;` [4](#0-3) , and later requires this running total to exactly equal the previously-declared `payload.cap` (`payload.cap <= constants.MAX_CAP`) [5](#0-4) [6](#0-5) .

Since `count_coins` is unbounded and JS numbers are IEEE-754 doubles, an attacker can choose a `count_coins` value large enough that the product `count_coins * denomination` overflows the 53-bit safe-integer range. In that regime the multiplication result is rounded to a nearby representable double, which can be engineered (by choosing `count_coins` and `denomination` precisely) to equal a small, attacker-chosen `cap` (≤ `MAX_CAP`) that passes the `payload.cap !== total_cap_from_denominations` equality check, while the *true* mathematical product (i.e., the actual number of coin units this denomination structure permits to be issued: `count_coins` individual indivisible coins each worth `denomination`) is far larger than the advertised `cap`.

This is directly analogous to the reported gawk bug: an integer-overflowed intermediate value bypasses an internal consistency/size check that other code relies on for safety.

### Impact Explanation
The `denominations` array and the declared `cap` are the fields other consensus-critical code paths (asset issuance validation, per-denomination issue amount checks in `indivisible_asset.js`/payment validation) rely on to bound the total possible issuance of the asset. If the cap-vs-denominations cross-check can be spoofed via overflow, a malicious asset issuer can define an asset whose declared `cap` looks small/consistent, while the `count_coins` for one or more denominations is effectively unbounded, letting the issuer mint indivisible coins in that denomination without the network-wide total ever being flagged as exceeding the "capped" total. This is a supply-inflation vector for fixed-denomination (typically privacy) assets — a concrete, medium/high severity impact matching the accepted impact classes (supply inflation) for this analog scan.

### Likelihood Explanation
The attacker only needs to be the author of an `asset` definition message (any unprivileged unit poster can define an asset), plus control over `payload.denominations` entries — fields that are entirely attacker-supplied and not sanitized for magnitude other than `isPositiveInteger` and the version-gated `MAX_CAP` check on `denomination` (not on `count_coins`). No privileged role, coordination with other nodes, or race condition is required; a single, syntactically valid `define asset` message is enough to construct the overflow. Likelihood is high given how directly reachable the vulnerable arithmetic is from unit content.

### Recommendation
- Bound `count_coins` explicitly (e.g., `count_coins <= constants.MAX_CAP` or `count_coins * denomInfo.denomination <= constants.MAX_CAP` computed safely) before accumulating.
- Perform the multiplication/accumulation using a big-integer-safe method (e.g., `BigInt`) and only convert back to `Number` after confirming the value is within `Number.MAX_SAFE_INTEGER` and `<= constants.MAX_CAP`; reject the unit otherwise.
- Remove/backdate the version gate on the `denomination > MAX_CAP` check so it always applies, and add an equivalent unconditional bound for `count_coins`.
- Add a regression test that defines an asset whose `count_coins`/`denomination` pair overflows `Number.MAX_SAFE_INTEGER` but whose rounded product coincidentally equals a small `cap`, asserting that validation rejects it.

### Proof of Concept
1. Choose `denomination = D` (a moderate positive integer ≤ `MAX_CAP`).
2. Choose `count_coins = C` such that `C * D` exceeds `2^53` and, due to double rounding, equals exactly some small target `cap = K` (attacker can brute-force nearby `C` values off-chain until the IEEE-754 product rounds to `K`).
3. Submit an `asset` definition message:
```json
{
  "app": "asset",
  "payload": {
    "cap": K,
    "is_private": true,
    "is_transferrable": false,
    "auto_destroy": true,
    "fixed_denominations": true,
    "issued_by_definer_only": true,
    "cosigned_by_definer": false,
    "spender_attested": false,
    "denominations": [ { "denomination": D, "count_coins": C } ]
  }
}
```
4. `validateAssetDefinition()` computes `total_cap_from_denominations = C * D`, which — due to floating point overflow — evaluates to `K`, matching `payload.cap`, so the unit passes validation despite the asset structurally permitting issuance of `C` coins of denomination `D` (mathematically far exceeding `K`). [7](#0-6) 

Note: I was not able to retrieve `constants.MAX_CAP`'s exact numeric value or the exact implementation of `isPositiveInteger`/`isNonnegativeInteger` in `validation_utils.js` before running out of tool iterations, so the precise numeric bounds needed to construct a concrete `C`/`D`/`K` triple for a working exploit could not be fully verified here — this should be confirmed by a Devin session with full file access before finalizing severity/exploit parameters.
