### Title
`ProxyType::NonTransfer` fails open and permits value-moving calls on Asset Hub Rococo - ([File: cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs])

### Summary
The CVE report describes a fail-open access-control defect: Monitorix's `hosts_deny` allow/deny list bypassed Basic Auth on any installation that did not explicitly configure it, because the feature was a deny-list that defaults to allow. The direct Polkadot SDK analog is `ProxyType::NonTransfer` in `pallet_proxy` configurations, which is likewise implemented as a deny-list that fails open: any pallet added to the runtime is reachable by a `NonTransfer` proxy delegate unless explicitly denied. This exact bug class was already identified and fixed for the Asset Hub Westend runtime (pr_12771) and the `staking-async` parachain runtime (pr_12922), but the `asset-hub-rococo` runtime in this codebase still uses the unpatched, narrower deny-list.

### Finding Description
`InstanceFilter<RuntimeCall>::filter` for `ProxyType::NonTransfer` on Asset Hub Rococo only denies: [1](#0-0) 

```
ProxyType::NonTransfer => !matches!(
    c,
    RuntimeCall::Balances { .. } |
        RuntimeCall::Assets { .. } |
        RuntimeCall::NftFractionalization { .. } |
        RuntimeCall::Nfts { .. } |
        RuntimeCall::Uniques { .. }
),
```

This is documented elsewhere in the same codebase as an explicitly fail-open pattern ("a pallet added to the runtime is reachable by a `NonTransfer` proxy unless it is listed here"), as annotated on the fixed Westend version: [2](#0-1) 

The runtime confirms that `ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, `Revive`, and `Indices` pallets are present and wired in `asset-hub-rococo/src/lib.rs` (config impls and call-variant references found via search), yet none of them are denied to `NonTransfer`. By contrast, the Westend and `staking-async` runtimes were patched by pr_12771 and pr_12922 specifically because these same call families move the delegator's funds/assets and were "not listed, contradicting the documented policy that this proxy type can only execute calls that do not transfer funds or assets": [3](#0-2) [4](#0-3) 

A regression test exists confirming the intent and prior vulnerability of this exact fail-open pattern on the Westend sibling runtime: [5](#0-4) 

`pallet_proxy::do_proxy` dispatches the wrapped call under the real account's origin filtered only by `ProxyType::filter`, so any call this filter admits is fully authorized to move the delegator's funds: [6](#0-5) 

### Impact Explanation
A user who grants a `NonTransfer` proxy — believing (per the pallet's own naming/documentation intent) that the delegate cannot move funds or assets — actually grants the delegate the ability to:
- Transfer `ForeignAssets`/`PoolAssets` (fungible instances parallel to `Assets`)
- Execute `AssetConversion` swaps/liquidity withdrawals that move the caller's assets
- Execute `PolkadotXcm::transfer_assets`/`teleport_assets`/`send`/`execute`, moving assets off-chain
- Execute value-bearing `Revive` (contract) calls
- Execute `Indices::transfer`/`force_transfer`, repatriating a reserved deposit

This is an authorization bypass causing unauthorized dispatch and theft of delegator funds/assets by an intentionally lower-privileged proxy account, on the analogous root cause to CVE-2021-3325 (deny-list access control silently failing open for anything not explicitly enumerated).

### Likelihood Explanation
No privileged role or governance action is required. The only prerequisite is that a victim has created (or will create) a `NonTransfer` proxy relationship for any delegate — an extremely common, ordinary, documented usage pattern of `pallet_proxy` intended specifically to limit a delegate's power. The delegate (attacker) needs no special permission beyond being an authorized `NonTransfer` proxy, which by design is meant to be a low-trust grant.

### Recommendation
Apply the same fix used for Asset Hub Westend (pr_12771) and the `staking-async` parachain (pr_12922) to `asset-hub-rococo`: extend the `ProxyType::NonTransfer` deny-list to explicitly deny `ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, `Revive`, and `Indices::transfer`/`force_transfer` (and any other value-moving call families present in the runtime), matching the documented "does not transfer funds or assets" policy. Add the same regression test pattern (`non_transfer_proxy_rejects_value_moving_calls`) to asset-hub-rococo's test suite to prevent recurrence.

### Proof of Concept
Evidence collected via static analysis of `asset-hub-rococo/src/lib.rs` confirms: (1) the `NonTransfer` filter only lists `Balances`, `Assets`, `NftFractionalization`, `Nfts`, `Uniques`; (2) `ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, `Revive`, `Indices` pallets are configured and reachable `RuntimeCall` variants in this runtime (confirmed via grep matches for `impl pallet_asset_conversion::Config`, `impl pallet_xcm::Config`, `impl pallet_revive::Config`, `impl pallet_indices::Config`, `ForeignAssetsInstance`, `PoolAssetsInstance`). A concrete integration reproduction analogous to the existing Westend regression test (`value_moving_calls()` / `non_transfer_proxy_rejects_value_moving_calls`) would need to be adapted and executed against the `asset-hub-rococo-runtime` crate to assert `ProxyType::NonTransfer.filter(&RuntimeCall::ForeignAssets(pallet_assets::Call::transfer{..}))` returns `true` (leak) rather than `false`. This adapted test was not executed in this session — the finding rests on direct code comparison between the unpatched `asset-hub-rococo` filter and the patched `asset-hub-westend`/`staking-async` filters plus the corresponding prdocs describing the exact same root cause as a fixed vulnerability elsewhere in the same codebase.

/// Regression test for <https://github.com/paritytech/polkadot-sdk/issues/12466>.
///
/// `ProxyType::NonTransfer` is documented as permitting "any call that does not transfer funds or
/// assets", but it is implemented as a deny-list and so fails open. `ForeignAssets` and
/// `PoolAssets` transfers were reachable, as were swaps, XCM transfers, contract calls carrying a
/// value, and index transfers (which repatriate the reserved deposit).
#[test]
fn non_transfer_proxy_rejects_value_moving_calls() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// Collected rather than asserted one by one, so a regression reports every call that slipped
	// through instead of only the first.
	let mut leaked = Vec::new();
	for (name, call) in value_moving_calls() {
		if ProxyType::NonTransfer.filter(&call) {
			leaked.push(name);
		}
		// The call is otherwise well-formed and reachable by a fully permissioned proxy.
		assert!(ProxyType::Any.filter(&call), "Any must permit {name}");
	}

	assert!(
		leaked.is_empty(),
		"NonTransfer must reject calls that move funds or assets, but permitted: {leaked:?}",
	);
}
