### Title
Cross-repository commit status forgery in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook handler authenticates the *sender organization* via `WebhooksController#verify_signature`, but the actual database write it performs (`Commit.where(sha: params.sha)`) is not scoped to that organization's repository at all. Any GitHub organization onboarded into a multi-tenant Shipit instance can therefore forge a CI status for a commit belonging to a completely different, unrelated repository/stack, as long as it can produce (or replay) a commit whose SHA-1 matches a commit tracked by that other repository.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/organization signed the request from the payload itself and checks the signature against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

This authenticates "this payload genuinely comes from organization X's installed GitHub App," but says nothing about which *repository* the payload's fields are allowed to affect. Once verified, the whole raw payload is dispatched unmodified to the matching handler: [3](#0-2) 

Every other handler re-establishes the repository binding by scoping through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any record: [4](#0-3) 
e.g. `PushHandler` and `CheckSuiteHandler` both operate only on `stacks.where(...)`: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, ignores `repository` entirely and looks the target commit up **globally by SHA only**: [7](#0-6) 

Because commit SHA-1 values are content-derived and not secret (they are visible in public git history, PRs, and CI logs), an attacker who controls (or has push access to) any organization onboarded to this Shipit instance can construct a commit with byte-identical content (same tree, parents, author/committer metadata, timestamps, message) to a target commit that lives in a different, unrelated repository/stack tracked by Shipit — producing the same SHA-1. Posting/receiving a `status` event for that SHA from the attacker's own (validly signed) organization will cause `StatusHandler` to write the forged status onto the commit record of the *victim* repository, because the lookup is `Commit.where(sha: params.sha)` with no repository/organization filter.

This is the exact bug class from the reference report: `msg.value` is checked (`>= sellOrder.price`) but the *excess* amount is still forwarded to the maker unconditionally — a value acted upon that is not fully constrained by the check that authorized the operation. Here, the webhook signature check constrains "which organization sent this," but the code then acts on a `sha` field with no corresponding constraint tying it to that organization's own repositories.

### Impact Explanation
Commit statuses recorded via `Commit#create_status_from_github!` feed into Shipit's CI/status aggregation used for deploy/merge gating (referenced by `Status::Group`, `MergeRequest`, and `Stack`) as observed in `app/models/shipit/status/group.rb`, `app/models/shipit/merge_request.rb`, and `app/models/shipit/stack.rb`. Forging a "success" status onto a victim commit from an unrelated, low-trust onboarded organization can cause that commit to be treated as CI-green by Shipit's merge-on-green / deploy-readiness logic in the victim repository/stack — enabling an unauthorized merge or deploy decision on a commit whose real CI state was never verified by the victim's own checks. This crosses the "unauthorized deploy, rollback or merge" impact bar via a cross-tenant/cross-repository write that should have been confined by the per-organization signature-verification boundary.

### Likelihood Explanation
Requires: (1) the target Shipit instance to be multi-tenant (multiple GitHub orgs configured, as shown by `config/secrets.development.shopify.yml`), (2) attacker control of at least one onboarded, legitimately-signing organization, and (3) the ability to reconstruct a byte-identical commit to a target commit in the victim repo (straightforward when the victim repository/commit is public, since all commit fields needed to reproduce the SHA are public). No Shipit session, API token, or webhook secret of the victim organization is needed — only the attacker's own organization's legitimate webhook delivery, which they already control.

### Recommendation
Scope `StatusHandler#process` by repository, mirroring `Handler#stacks`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` (or join commits through the stack/repository resolved from `payload.dig('repository','full_name')`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own installed GitHub App / `webhook_secret` (per `config/secrets.*.yml` multi-org support).
2. Attacker identifies a public commit `C` (sha `abc123...`) in a repository tracked by Shipit under `victim-org`.
3. Attacker reproduces commit `C` byte-for-byte (same tree/parent/author/committer/timestamps/message) inside a repository they control under `attacker-org`, yielding the identical SHA-1 `abc123...`.
4. Attacker sets a commit status (e.g. via GitHub's Statuses API, which they can legitimately call for their own repo) on `abc123...` with state `success`.
5. GitHub delivers a `status` webhook to Shipit, signed with `attacker-org`'s `webhook_secret`; `WebhooksController#verify_signature` passes because the signature is valid for `attacker-org`.
6. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which matches the commit tracked under `victim-org`'s stack, and records the forged `success` status on it via `commit.create_status_from_github!(params)`, independent of the fact that the request was authenticated for `attacker-org`, not `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
