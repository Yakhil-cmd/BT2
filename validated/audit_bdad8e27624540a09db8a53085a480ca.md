### Title
Webhook signature verification is bound to the wrong organization, allowing any onboarded org to forge commit statuses (and repository events) for stacks belonging to other organizations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` used to validate an inbound webhook based on a repository/organization field taken from the *unverified* JSON payload, then the individual event handlers act on data (a commit `sha`, a `repository.full_name`, etc.) that is never re-checked against the organization whose secret actually signed the request. This breaks the intended binding "organization that authenticated == repository/record that gets written."

### Finding Description
`WebhooksController#verify_signature` looks up the signing app via `repository_owner`, which is read straight out of the JSON body: [1](#0-0) [2](#0-1) 

Because Shipit supports multiple installed GitHub Apps, one per organization (`docs/setup.md` "Using Multiple Github Applications"), each organization has its own `webhook_secret`. The signature check only proves the payload was signed by *whichever* organization's app the attacker names in `repository.owner.login` — it says nothing about the record the handler subsequently mutates.

`Shipit::Webhooks::Handlers::Handler#stacks` / `#repository_name` scope work off a *different* payload field, `repository.full_name`: [3](#0-2) 

Most severely, `StatusHandler` doesn't even scope by repository — it looks up commits purely by `sha`, globally, across every stack Shipit manages: [4](#0-3) 

So the equality that should hold — `organization that authenticated the signature == repository/commit being written` — is never enforced. An attacker only needs to control (or be an admin of) **any** GitHub organization/app that Shipit is configured to trust; they can then sign a `status` webhook with *their own* valid `webhook_secret`, but set `sha` to the HEAD commit sha of a pull request/stack belonging to a **completely different** organization also hosted on the same Shipit instance.

### Impact Explanation
Commit statuses drive Shipit's merge-queue safety gate (`ci.require` / `required_statuses`, referenced in `DeploySpec::FileSystem#cacheable_config`): [5](#0-4) 

By forging a `success` status with the matching `context` for a target repo's commit, an attacker who only controls an unrelated onboarded organization can make Shipit believe CI passed on a foreign repository's commit, enabling that commit to satisfy merge-queue requirements and proceed to an **unauthorized merge/deploy** — without ever having write access, a Shipit session, or credentials for the target organization/repository. This matches the Critical impact category ("unauthorized deploy, rollback, or merge").

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured for multiple GitHub organizations (documented supported deployment mode), and (2) the attacker controls/administers one of those organizations' GitHub App installs (their own `webhook_secret`, no privileged Shipit account or `GITHUB_TOKEN` needed). This is a realistic multi-tenant scenario explicitly documented in `docs/setup.md`, and the request is a plain unauthenticated HTTP POST to `/webhooks` crafted with a signature computed from the attacker's own known secret.

### Recommendation
Bind the payload's target repository to the organization that produced a valid signature: after `verify_signature` resolves `repository_owner`, propagate/enforce that same organization when resolving `stacks`/`repository` in `Shipit::Webhooks::Handlers::Handler`, and reject events whose `repository.full_name` owner does not match the authenticating organization. For `StatusHandler`, scope the `Commit.where(sha:)` lookup to commits belonging to stacks/repositories owned by the verified organization instead of a global sha lookup.

### Proof of Concept
1. Shipit is configured with two GitHub App organizations, `attacker-org` (attacker controls installation/`webhook_secret`) and `victim-org` (hosts a stack with a pull request awaiting a required `ci/tests` status to merge).
2. Attacker computes `HMAC-SHA1(attacker_org_webhook_secret, body)` over a payload:
```json
{
  "sha": "<head sha of victim PR>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, and the signature verifies successfully (it was legitimately signed by the attacker's own secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — with no repository scoping — finds the victim's commit and calls `create_status_from_github!`, marking the required CI context as passed on `victim-org`'s stack, potentially unblocking an unauthorized merge/deploy.
