### Title
Webhook signature verification is bound to `repository.owner.login`, not to `repository.full_name` acted upon — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App/organization secret to use for HMAC signature verification from the `repository.owner.login` (or `organization.login`) field of the *same, attacker-supplied* JSON body it is about to trust, but every event handler subsequently looks up the target `Repository`/`Stack` using a *different* field of that same body — `repository.full_name`. Because these two fields are never cross-checked, a party who legitimately controls a GitHub App/webhook secret for one organization configured in Shipit can forge a payload whose `repository.owner.login` matches their own org (so it passes signature verification) while `repository.full_name` names a completely different organization's repository, causing Shipit to act on that unrelated repository.

### Finding Description
`Shipit::WebhooksController#verify_signature` resolves the GitHub App/webhook secret to validate against using: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```

with: [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — a field inside the very JSON body being verified.

Once the signature check passes, `create` blindly dispatches the parsed body to all registered handlers for the event: [3](#0-2) 

Every handler (`PushHandler`, pull-request handlers, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, etc.) resolves the target repository/stack from a *different* field of the payload — `repository.full_name` — via the shared base class: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, for example, uses this to select stacks and trigger a GitHub sync: [5](#0-4) 

Since `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon repository) are independent, unrelated JSON fields inside the same attacker-controlled body, nothing forces them to refer to the same repository/organization. Shipit's config explicitly supports multiple, independently-secreted GitHub orgs/apps in a single instance (see `config/secrets.development.shopify.yml` listing `somegithuborg` / `someothergithuborg` each with their own `webhook_secret`), so this is a real multi-tenancy boundary, not a theoretical one.

**Binding broken:** `organization authenticated (repository.owner.login/organization.login, secret-verified)` == `repository written (repository.full_name, used to locate Stack/Repository)`. Before the attack these are supposed to be the same GitHub repository; after a forged request they can diverge, letting an org-A webhook secret authorize writes against org-B's repositories.

### Impact Explanation
An entity that legitimately administers a GitHub App/webhook integration for one organization configured in Shipit (org A) can forge webhook deliveries that are processed as if they originated from any other organization's repository (org B) that is also configured in the same Shipit instance, without needing org B's webhook secret at all. Depending on which event handler is targeted this can:
- Trigger `sync_github`/`RefreshCheckRunsJob`/`RefreshStatusesJob` on org B's stacks (`PushHandler`, `check_suite`, `status` handlers), corrupting CI/commit-status state that stacks rely on to gate deploys.
- Create/close/label review-stack pull requests belonging to org B (`pull_request/*` handlers), since those also key off `repository.full_name`.
- Because commit statuses/checks feed directly into Shipit's deploy-safety logic (CI must be green before a commit becomes deployable), an attacker able to inject arbitrary `status`/`check_suite` events for org B's repository can manufacture false "green" CI states for org B's commits, undermining the safety gate that prevents unvetted/unsafe commits from being deployed.

This crosses the exact organization/repository trust boundary the engine is meant to enforce per-tenant, and can lead toward an unauthorized deploy path by falsifying the CI signals Shipit uses to decide deployability.

### Likelihood Explanation
Requires the attacker to control at least one organization/GitHub App entry configured in the same Shipit instance (i.e., they know that org's `webhook_secret`, which they legitimately possess as the owner of their own integration) — this is not a privileged Shipit account, `ApiClient` token, or `api_clients_secret`; it only requires knowledge of a secret the attacker themselves configured for their own org's GitHub App. Any Shipit deployment onboarding more than one organization (a documented, supported configuration per `config/secrets.development.shopify.yml`) is exposed. No GitHub-side privilege over the victim org is needed, and the crafted request is a single unauthenticated HTTP POST to `/webhooks`.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: derive the organization/secret to verify against from `repository.full_name`'s owner segment (or otherwise ensure `repository.owner.login`/`organization.login` is verified to equal the owner segment of `repository.full_name`) before dispatching to handlers. Additionally, handlers should confirm that the resolved `Repository` actually belongs to the organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` (attacker-controlled, webhook secret known to attacker) and `org-b` (victim), per `config/secrets.yml`.
2. Attacker computes `sha1=HMAC-SHA1(org-a_webhook_secret, body)` for a crafted `push` (or `status`) payload where:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
   - `ref`, `after` set to attacker-chosen values.
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature` set to the computed signature.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against org-a's secret.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on org-b's stack — despite the request never being signed by org-b.
