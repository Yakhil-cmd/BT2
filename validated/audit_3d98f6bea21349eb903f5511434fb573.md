### Title
Cross-tenant webhook forgery: signature verified against `repository.owner.login`'s GitHub App secret, but the stack lookup and status/CI mutation act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC `webhook_secret`) to verify a webhook against using `repository.owner.login` from the JSON body, while `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target `Repository`/`Stack` using the independent `repository.full_name` field from the same body. Nothing binds these two fields together, so in a multi-organization Shipit deployment, a party who legitimately controls one onboarded GitHub organization (and therefore knows that organization's own `webhook_secret`) can sign an arbitrary payload and make it act on a *different* organization's repository/stack.

### Finding Description
`verify_signature` computes the signing organization purely from the payload, not from any authenticated channel: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization GitHub App config (each with its own `webhook_secret`, as documented for the "Multiple Github Applications" setup): [3](#0-2) 

Once the signature check passes, the actual event handlers determine *what* to mutate using a **different** field of the same JSON body — `repository.full_name` — via the base `Handler` class: [4](#0-3) 
resolved to a `Repository`/`Stack` record with: [5](#0-4) 

There is no validation anywhere that `repository.full_name` belongs to the same organization as `repository.owner.login`. Concretely, an attacker who is a legitimate admin of Org A (onboarded into the same shared Shipit instance, e.g. as a self-service tenant with their own GitHub App and their own known `webhook_secret`) can POST a hand-crafted JSON body to `/webhooks` where:
- `repository.owner.login = "org-a"` (used only for `verify_signature`, so the request validates using Org A's own secret, which the attacker legitimately knows), and
- `repository.full_name = "org-b/victim-repo"` (used by `Handler#stacks` / `Repository.from_github_repo_name` to pick the target Stack).

This breaks the binding: **organization that authenticated (Org A) ≠ repository that is written (Org B)**.

Depending on the event type, this can:
- `PushHandler`: force `stack.sync_github(expected_head_sha: params.after)` on an arbitrary victim stack, causing Shipit to resync a victim's branch state. [6](#0-5) 
- `StatusHandler`: forge a passing/failing CI status (`create_status_from_github!`) on a victim commit purely by SHA match (no stack-scoping at all in this handler — even worse, it operates directly on any `Commit` matching the SHA across the whole instance), which can flip whether a commit is `deployable?` and gate merge/deploy decisions. [7](#0-6) 
- `CheckSuiteHandler`: schedule check-run refreshes on a victim stack's commits. [8](#0-7) 

The most impactful is `StatusHandler`, since Shipit uses commit statuses to gate whether a commit is safe to deploy; forging a green/passing status on a victim's commit that hasn't actually passed CI can lead to an **unauthorized deploy** being triggered by a legitimate victim user relying on Shipit's UI/CI gate.

### Impact Explanation
This crosses the exact boundary called out in scope: "an organization that authenticated versus the repository that is written." An attacker who is unprivileged with respect to the victim organization (no GitHub write access, no Shipit session, no `ApiClient` token, no knowledge of the victim's `webhook_secret`) can nonetheless cause writes against the victim's stack/commit records by exploiting their own, legitimately-known organization credentials against a shared multi-tenant Shipit instance. The `StatusHandler` path can corrupt a commit's CI-gating state and enable an **unauthorized deploy** through Shipit's normal deploy flow, which matches the Critical impact bucket ("an unauthorized deploy").

### Likelihood Explanation
This requires that the Shipit deployment be configured for multiple GitHub organizations (the documented "Using Multiple Github Applications" setup), and that the attacker controls/administers one of the onboarded orgs (so they know that org's `webhook_secret`, which they themselves configured when installing their GitHub App). In such shared/multi-tenant deployments this is straightforward to exploit — it only requires crafting one raw HTTP POST to `/webhooks` with a correctly computed HMAC using the attacker's own known secret; no interaction with GitHub's actual webhook delivery mechanism is needed since the secret and payload are both attacker-controlled. In a single-organization deployment this analog does not apply, since the attacker would need the victim's own `webhook_secret`.

### Recommendation
Bind the verified organization to the resource being mutated: after computing `repository_owner` for signature verification, re-derive the target repository from that same field (or validate that `repository.full_name.split('/').first == repository_owner`) before dispatching to handlers, rather than trusting an independent `full_name` field. Additionally, `StatusHandler` should scope status creation to commits belonging to a stack whose repository matches the authenticated organization, not merely match by `sha` globally.

### Proof of Concept
1. Configure/assume a shared Shipit instance with two onboarded GitHub organizations, `org-a` (attacker-controlled) and `org-b` (victim), each with a distinct `webhook_secret` per `docs/setup.md`'s multiple-app configuration.
2. Attacker (an admin of `org-a`) knows `org-a`'s `webhook_secret` (they configured it themselves).
3. Attacker crafts a JSON body for the `status` event:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner => "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature verifies successfully (attacker used the correct secret for `org-a`).
6. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — the victim's commit in `org-b/victim-repo` — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status despite the attacker having no access to `org-b`.
