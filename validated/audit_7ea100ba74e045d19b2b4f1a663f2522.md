### Title
Unvalidated caller-supplied `swap` route executes arbitrary contracts under the caller's authorization tree, enabling wallet-draining child invocations — ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Analogous to CVE-2015-8612 — where Blueman passed the attacker-controlled `dhcp_handler` argument into a privileged execution path — the controller passes a fully caller-controlled opaque `swap: Bytes` route blob into `router.execute_strategy`. Neither the controller nor the router validates or allowlists the venue addresses encoded inside the route, so a crafted route places attacker-deployed code on the call stack *below the caller's own `require_auth` entry*. Soroban's recording-mode simulation then attaches the rogue contract's `token.transfer(victim, attacker, ...)` as a child of the caller's signed authorization tree; if the caller signs the simulated tree, the theft executes for the full wallet balance, unbounded by the routed amount.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` reads the router from storage, grants one exact `token_in.transfer(controller, router, amount_in)` authorization, and calls `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is raw caller-supplied bytes (line 37). The controller only checks measured input spend (`RouterOverspend`) and positive measured output (`NoSwapOutput`) — it never inspects the route contents.

This is reachable via `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, all of which a caller invokes on its own account with an arbitrary route payload. The threat model itself confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them" (`docs/explanation/threat-model.md:154-165`), and the dedicated test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the primitive end-to-end: a `RogueHopPool` contract named in the route performs `token.transfer(victim, attacker, WALLET_BALANCE)` (line 69), simulation records it under the caller's `swap_collateral` auth entry (lines 206-222), and enforcing mode executes it when the signed tree contains that child (lines 259-268).

### Impact Explanation
Theft of user funds exceeding the routed amount. The rogue venue's transfer drains any token the victim holds — including tokens the protocol never listed — because the child invocation executes under the victim's signature, not under the controller's scoped `authorize_transfer_as_current` grant. The victim's signed authorization tree is the only bound; nothing in the controller's `RouterOverspend`/`NoSwapOutput` measurement constrains child transfers sourced from the caller's wallet rather than the controller.

### Likelihood Explanation
Medium. Exploitation requires a crafted route payload that the victim signs — realistically delivered through a malicious/compromised frontend or SDK that supplies the `swap` bytes and presents the poisoned auth tree. An unprivileged attacker cannot reach a foreign account (the account guard pins `account_id` to owner/delegate), so this is a user-targeting phishing-style vector, not a permissionless drain of the protocol. However, every swap user of `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` and direct `execute_strategy` callers is exposed, and the loss is the victim's whole wallet rather than the trade size.

### Recommendation
Bind the route to the authorization it requires. Options in increasing strength: (1) have the router pre-declare every contract the route will invoke as a typed `Vec<Address>` argument so the client can diff the simulated auth tree against declared venues before signing; (2) enforce in the router that venue contracts must come from a governance/operator-managed allowlist (mirroring `INV-STRAT-03`'s approved-Blend-pool pattern); (3) at minimum, document and enforce a client-side rule — already hinted in `threat-model.md` — that any signed tree containing a child `transfer` from the caller other than the single declared input transfer must be rejected.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC:

1. Deploy `RogueHopPool` storing `(victim=Alice, wallet_token, to=attacker, amount=77_770_000_000)` (lines 56-71); its `swap()` performs `token.transfer(victim, attacker, amount)` on an unlisted token.
2. Build a `RoutedSwap` route naming `hop_pool = RogueHopPool` with a fair `min_out` so the swap passes `verify_router_output`.
3. Alice calls `controller.swap_collateral(route)`; simulation records the auth tree with the stolen transfer nested under her `swap_collateral` entry (assertion at lines 206-222).
4. Alice signs the recorded tree; enforcing mode executes and `assert_eq!(s.wallet(&s.alice), 0)` while `s.wallet(&s.attacker) == WALLET_BALANCE` (lines 265-268) — the wallet is drained while she receives fair swap output.
