### Title
`gh skill install` re-resolves the source ref independently of `gh skill preview`, allowing installed content to diverge from reviewed content - (File: pkg/cmd/skills/install/install.go)

### Summary
The GitHub CLI's Agent Skills feature explicitly tells users to review skill content with `gh skill preview` before trusting it with `gh skill install`, because skills "may contain prompt injections, hidden instructions, or malicious scripts." However, `preview` and `install` are separate commands that each independently resolve the source repository's ref to a SHA at the moment they run. Unless the user explicitly pins with `--pin <ref>`, nothing binds the SHA the user reviewed to the SHA that gets installed. An unprivileged attacker who controls (or has push access to) the source skill repository can rewrite the default branch between the user's `preview` and `install` invocations, so the content that is actually written to disk and later executed by an agent differs from what was reviewed — the exact "propose vs. execute" gap described in the zkSync `diamondCut` report, where the reviewed/committed payload is not the same as the payload ultimately executed.

### Finding Description
The documented, recommended workflow is: [1](#0-0) 

`gh skill preview <owner>/<repo> <skill-name>` and `gh skill install <owner>/<repo> <skill-name>` are independent commands. `preview` resolves the ref/SHA for display, and separately `install` calls its own ref resolution and file-fetch/install path: [2](#0-1) 

The tool itself acknowledges the trust gap by warning the user twice — once before installing, and again after, urging a *post-install* review: [3](#0-2) 

The suggested review command embeds the SHA that was *actually installed* (`gh skill preview %s %s@%s`), which is only knowable *after* install completes — meaning the intended safety pattern is "install, then verify," not "verify, then install." If a user instead follows the documented "preview, then install" order (as the skill's own self-management guidance recommends: "preview... to inspect the SKILL.md" then "install... for a reproducible install"), there is no mechanism carrying the reviewed SHA from `preview` into the subsequent `install` call unless the user manually supplies `--pin <ref>`. `gh skill update` demonstrates the same unpinned-ref-resolution pattern used at a different time than discovery: [4](#0-3) 

This mirrors the zkSync finding precisely: the "proposal" (`preview`) does not commit to specific content; the "execution" (`install`) independently re-fetches from a mutable reference (a branch), so an attacker who controls the source repo can swap in malicious content between the two steps.

### Impact Explanation
If exploited, a remote attacker (the owner of, or a contributor with push rights to, an untrusted third-party skill repository referenced by a `gh skill install owner/repo skill` command) can serve benign content to `gh skill preview` and then push malicious content (e.g., a script under `scripts/` or malicious instructions in `SKILL.md`) to the same branch before the user runs `gh skill install`. The user, believing they reviewed the content, unknowingly installs and later has their coding agent execute or follow attacker-controlled instructions/scripts — a form of verification bypass leading to arbitrary command execution or prompt injection in the user's agent environment, without any MITM or local-attacker capability required.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to explicitly install a skill from a repository not under their control, and requires an attacker who controls that repository's default branch to change its contents in the window between the victim's `preview` and `install` invocations (or between separate discovery calls during `update`). This is a realistic workflow given the CLI itself instructs users to "preview" then "install" for review purposes, and skill repos are explicitly untrusted, third-party sources by design (per the CLI's own disclaimer).

### Recommendation
Bind `install` to the exact SHA the user reviewed: have `gh skill preview` optionally emit/require a `--pin <SHA>` (or automatically pin) so `gh skill install` accepts and enforces installing the identical tree SHA that was previewed, refusing to silently re-resolve to a newer/mutated ref. Alternatively, always print the resolved SHA at `preview` time and require the corresponding `install --pin <SHA>` invocation to complete the documented review-then-install workflow, so the reviewed and installed content are cryptographically identical by content-addressed SHA rather than by a re-resolved mutable ref.

### Proof of Concept
1. Attacker publishes a benign `SKILL.md` and scripts under `owner/attacker-skills` on the default branch.
2. Victim runs `gh skill preview owner/attacker-skills useful-skill` and reviews benign content, per the documented self-management pattern in `skills/gh-skill/SKILL.md`.
3. Before the victim runs the follow-up install command, the attacker pushes a new commit to the same branch replacing `scripts/setup.sh` with a malicious payload.
4. Victim runs `gh skill install owner/attacker-skills useful-skill` (without `--pin`); `installSkill` resolves the ref fresh and fetches the now-malicious blob content via `discovery.FetchBlob`, writing it verbatim to disk: [5](#0-4) 
5. The victim, having already "reviewed" the skill in step 2, proceeds to use/execute it, running the attacker's payload instead of the reviewed content.

func installSkill(opts *Options, skill discovery.Skill, baseDir string) error {
	// Use skill.Name (not InstallName) for a flat directory layout.
	skillDir := filepath.Join(baseDir, skill.Name)
	if err := os.MkdirAll(skillDir, 0o755); err != nil {
		return fmt.Errorf("could not create directory %s: %w", skillDir, err)
	}

	files, err := discovery.DiscoverSkillFiles(opts.Client, opts.Host, opts.Owner, opts.Repo, skill.TreeSHA, skill.Path)
	if err != nil {
		return fmt.Errorf("could not list skill files: %w", err)
	}

	safeSkillDir, err := safepaths.ParseAbsolute(skillDir)
	if err != nil {
		return fmt.Errorf("could not resolve skill directory path: %w", err)
	}

func printPreInstallDisclaimer(w io.Writer, cs *iostreams.ColorScheme) {
	fmt.Fprintf(w, "\n%s Skills are not verified by GitHub and may contain prompt injections, hidden instructions, or malicious scripts. Always review skill contents before use.\n\n", cs.WarningIcon())
}

// printReviewHint warns the user to review installed skills and suggests preview commands.
// When sha is non-empty the suggested commands include @SHA so the user previews
// exactly the version that was installed. When allowHiddenDirs is true, the
// suggested commands include --allow-hidden-dirs so previewing hidden-dir
// skills works without an extra manual step.
func printReviewHint(w io.Writer, cs *iostreams.ColorScheme, repo, sha string, skillNames []string, allowHiddenDirs bool) {
	if len(skillNames) == 0 {
		return
	}
	fmt.Fprintf(w, "\n%s Skills may contain prompt injections or malicious scripts.\n", cs.WarningIcon())
	if repo == "" {
		fmt.Fprintln(w, "  Review the installed files before use.")
		return
	}
	fmt.Fprintln(w, "  Review installed content before use:")
	fmt.Fprintln(w)
	hiddenFlag := ""
	if allowHiddenDirs {
		hiddenFlag = " --allow-hidden-dirs"
	}
	for _, name := range skillNames {
		if sha != "" {
			fmt.Fprintf(w, "    gh skill preview %s %s@%s%s\n", repo, name, sha, hiddenFlag)
		} else {
			fmt.Fprintf(w, "    gh skill preview %s %s%s\n", repo, name, hiddenFlag)
		}
	}
	fmt.Fprintln(w)
}
