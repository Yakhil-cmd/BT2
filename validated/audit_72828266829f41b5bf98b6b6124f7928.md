### Title
Unauthenticated cross-organization webhook forgery via `webhook_secret`-less GitHub app in multi-org config - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, the webhook signature check is scoped to whichever GitHub organization the *attacker-supplied* `repository.owner.login` field names, not to the organization that owns the repository the payload actually mutates. If that named organization has no `webhook_secret` configured, signature verification is unconditionally skipped, letting an unauthenticated caller submit a forged webhook whose `repository.full_name` targets a stack belonging to a completely different, fully-secured organization.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` used to validate the request purely from the payload itself: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [2](#0-1) 

`repository_owner` is read straight from the untrusted body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

`GitHubApp#verify_webhook_signature` bypasses HMAC validation entirely when the resolved organization has no configured secret: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Shipit explicitly supports mounting multiple GitHub organizations behind one engine instance, each with its own `webhook_secret`, exactly as documented and tested: [4](#0-3) [5](#0-4) 

After signature verification passes (or is skipped), the controller dispatches the *entire, attacker-controlled* payload to handlers: [6](#0-5) 

Handlers resolve the target `Repository`/`Stack` using a *different* field of the same payload, `repository.full_name`, with no cross-check that it belongs to the same organization used for authentication: [7](#0-6) 

The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login) == organization owning the repository actually written (repository.full_name)`

Because both fields are attacker-controlled JSON keys read independently, and because the security-relevant one (`repository.owner.login`) merely selects *which* organization's secret is checked (and is skipped entirely if that organization has no secret set), an attacker can satisfy the "authenticated organization" side with a secret-less/no-webhook-secret org while pointing `repository.full_name` at a stack owned by any other organization tracked by the same Shipit instance. This is the direct analog of the underlying report: one code path (`_swap`/`_lpTokenSpecified` there, `verify_signature` here) enforces the invariant/authentication, while a second path that consumes the same input (`_reserveTokenSpecified` there, the handler's `repository_name` lookup here) does not re-validate it against the same binding, letting the untrusted data reach state-mutating logic unchecked.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding called out in scope. Concretely, an unauthenticated attacker can trigger, for a repository/stack they do not control:
- `PushHandler` → enqueues `GithubSyncJob` for another org's tracked repository (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`).
- `StatusHandler` → injects fabricated CI statuses on real commits via `Commit#create_status_from_github!`, which is used elsewhere by Shipit to decide whether a commit is `deployable?` — this can be leveraged to make an otherwise CI-failing commit appear green and unlock deploy safety checks.
- `PullRequest::*Handlers` → open/close/label/reopen review-stack-triggering pull request events, and `MembershipHandler` creates/adds `Team`/`User` records.

This is a cross-repository/cross-organization write achieved with no valid credentials for the targeted organization, satisfying the "cross-repository writes" / "unauthorized deploy" bar for Critical, contingent on at least one configured organization lacking a `webhook_secret` (a state the engine itself permits and documents as valid, e.g. `webhook_secret: # nil` in the shipped example configs).

### Likelihood Explanation
Likelihood depends on operational configuration: it requires a multi-org Shipit deployment (explicitly supported and documented) where at least one configured organization was set up without a `webhook_secret`. The shipped example config files (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`) all default `webhook_secret` to nil/blank, so this is a very plausible default/misconfiguration state rather than an exotic one, and once present it requires zero credentials to exploit — the attacker only needs to know the engine's public webhook URL and the target repo's `full_name`, both of which are typically public knowledge.

### Recommendation
Bind the signature-verification organization to the same identity used for repository resolution, or reject the request if they disagree: e.g., look up the `Repository`/`Stack` first from `repository.full_name`, derive its true owning organization from that record (not from the attacker-supplied `repository.owner.login`), and use that to select the `GitHubApp`/secret. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in a multi-organization configuration — either require a secret per organization or fail closed instead of open when the environment declares more than one organization.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (attacker-controlled or simply left with `webhook_secret: nil`) and `OrgB` (victim org, `webhook_secret` set, with a tracked stack for `OrgB/victim-repo`), matching `test/dummy/config/secrets_double_github_app.yml`.
2. POST directly to `/github/webhooks` (or the engine's mounted webhook path) with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
No `X-Hub-Signature` header is required (or any arbitrary value works) because `Shipit.github(organization: "OrgA")` resolves an app whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `WebhooksController#create` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`) and enqueues a `GithubSyncJob` for `OrgB`'s stack — despite never presenting any valid credential for `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
