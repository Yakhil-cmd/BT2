### Title
Borrow-index accrual overflows `i128` before `MAX_BORROW_INDEX_RAY` engages, permanently freezing the market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
`update_borrow_index` multiplies `old_index * interest_factor` via `Ray::mul`, which panics with `GenericError::MathOverflow` when the quotient exceeds `i128::MAX`. The panic fires before the `MAX_BORROW_INDEX_RAY` clamp is ever checked, and since every controller verb accrues the index first, the entire market becomes permanently frozen once scaled debt crosses the `i128::MAX` RAY-value ceiling.

### Finding Description
The bug class in CVE-2017-12086 — an integer overflow in a size/index computation — maps onto XOXNO's RAY index accrual.

`update_borrow_index` grows the index and intends to clamp it at `MAX_BORROW_INDEX_RAY` (1e36 raw, in `common/src/constants/pool.rs:19`): [1](#0-0) 

But `Ray::mul` → `fp_core::mul_div_half_up` computes `x * y / d` with an exact `I256` intermediate and then `.to_i128()` — the result-overflow path panics rather than saturating: [2](#0-1) 

`i128::MAX` ≈ 1.7e38 is ~170× larger than `MAX_BORROW_INDEX_RAY` = 1e36. The panic therefore triggers not on `old_index` alone but on the *unscale products* — `scaled_to_original(scaled, index)` = `scaled * index / RAY` — used pervasively in `calculate_utilization`, `unscale_supply`, `unscale_borrow`, `resolve_repay`, `resolve_withdrawal`, and `update_supply_index`/`calculate_supplier_rewards` (`supplied.mul(old_index)`, `borrowed.mul(new_borrow_index)`): [3](#0-2) [4](#0-3) [5](#0-4) 

When `supplied * supply_index` (or `borrowed * borrow_index`, or `old_index * interest_factor`) exceeds `i128::MAX`, the multiply panics with `MathOverflow` (error #33). Because index accrual runs at the top of `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `update_indexes`, `clean_bad_debt`, `recapitalize`, etc., every subsequent call to the market reverts. There is no recovery path: `update_supply_index` and the write-down clamp only bound `grown`/`new_index` *after* a successful multiply, so no verb can reduce `scaled` or roll back the index. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: accrual panics, `borrow_index` is still below `MAX_BORROW_INDEX_RAY`, and both `withdraw` and `repay` fail with `MATH_OVERFLOW` thereafter: [6](#0-5) 

### Impact Explanation
Permanent freezing of all funds in the affected market. Suppliers cannot `withdraw`, borrowers cannot `repay`, liquidators cannot `liquidate`, and `clean_bad_debt`/`recapitalize`/`update_indexes` all revert on the same panic inside accrual. Every token locked in the pool book for that `(hub, token)` market is bricked forever.

### Likelihood Explanation
An unprivileged attacker (or natural market growth) can reach it without admin cooperation beyond what listing already permits: supply a very large amount of a high-decimal asset, drive utilization high via `borrow`, and let the millisecond-chunked accrual compound. The harness test shows the cliff is hit with `borrow_index` still under the cap — i.e., on a steep rate curve the *value* ceiling (`scaled × index > i128::MAX`) binds before the index clamp. It requires a whale-scale position (order ~10²⁷ token units at 18 decimals, ~98% utilization sustained for years at the XLM-style curve), so likelihood is low and depends on supply/borrow caps being set generously — but caps up to the asset domain are an intended configuration, and no privileged action is needed once the market exists. Impact: permanent freeze; Likelihood: low → **Medium**.

### Recommendation
Make index growth and unscaling saturating or capped *before* the overflow, not after:
- In `update_borrow_index`, use a saturating/widened multiply and clamp `new_index` to `MAX_BORROW_INDEX_RAY` as the code intends (e.g., `mul_div_floor_saturating` semantics or `try_mul` → cap on `None`).
- In `update_supply_index` and `calculate_supplier_rewards`, compute `supplied * index` via `mul_div_floor_saturating` or compare `scaled` against `i128::MAX / index` before multiplying, so accrual can degrade (cap index, shortfall to fees) instead of panicking.
- Alternatively, enforce at borrow/deposit time an invariant `scaled ≤ i128::MAX / MAX_BORROW_INDEX_RAY` so the value product can never exceed `i128::MAX`, turning the freeze into a reject-new-growth bound.

### Proof of Concept
Reproduced by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
// Attacker (unprivileged): supply whale principal into an 18-decimal market
t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18));
// Supply collateral, borrow to ~98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// Advance time; eventually update_indexes panics inside scaled_to_original /
// index mul with MathOverflow while borrow_index < MAX_BORROW_INDEX_RAY.
// Thereafter every verb reverts:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `update_borrow_index` / `update_supply_index` / `calculate_utilization` → `Ray::mul` → `mul_div_half_up` → `I256` quotient `.to_i128()` → `None` → `panic_with_error!(MathOverflow)`, with the `MAX_BORROW_INDEX_RAY` clamp checked only on a value that can never be produced once the product overflows.

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {

    if new_index.raw() > MAX_BORROW_INDEX_RAY {

    }

}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
