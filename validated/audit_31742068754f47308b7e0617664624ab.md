### Title
Webhook signature verified against `repository.owner.login` while handlers act on `repository.full_name`, allowing cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using one field of the JSON payload (`repository.owner.login`, or `organization.login`), but the event handlers that subsequently act on the *same, already-verified* payload key off a completely different field (`repository.full_name`). Because GitHub payload fields are attacker-controlled data (the whole point of the signature is to prove the payload came from *a* trusted source, not that its internal fields are mutually consistent), nothing in this engine binds "the org whose secret validated this HTTP request" to "the repository whose stacks get mutated."

### Finding Description
`verify_signature` computes the app/secret from `repository_owner`: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` and used solely to pick the `GitHubApp`/`webhook_secret` for `verify_webhook_signature`.

Once the signature check passes, `create` dispatches the same raw payload to handlers: [3](#0-2) 

Every handler resolves the target repository/stacks from a *different* payload field, `repository.full_name`: [4](#0-3) 

`Repository.from_github_repo_name` then splits that string on `/` to find the `owner`/`name` row, with no cross-check against `repository.owner.login`: [5](#0-4) 

`PushHandler#process`, for example, uses the resolved stacks to trigger `sync_github`, which fetches commits and can enqueue deploy-relevant state changes: [6](#0-5) 

Under Shipit's documented multi-organization configuration, each org has its own GitHub App and its own `webhook_secret`: [7](#0-6) 

This is exactly the binding the report's bug class targets: "an organization that authenticated versus the repository that is written." An attacker who legitimately controls one onboarded organization (e.g. `attacker-org`, with its own GitHub App and webhook secret known to them because they administer that App) can send Shipit a webhook whose signature is computed with `attacker-org`'s secret, but whose payload sets `repository.owner.login = "attacker-org"` (so `verify_signature` picks and validates against the correct secret) while `repository.full_name = "victim-org/victim-repo"` (an entirely different, unrelated organization/repository also tracked by the same Shipit instance). `verify_signature` succeeds because it only checks the owner-login field; the `PushHandler`/`StatusHandler`/etc. then act on `victim-org/victim-repo`'s stacks using `full_name`, which is never validated against the field the signature was checked against.

### Impact Explanation
This breaks the trust boundary between organizations hosted on the same Shipit instance: possession of a valid webhook secret for organization A is sufficient to forge webhook events (push, status, check_suite, pull_request, membership) for any other organization/repository B configured on the same Shipit instance, as long as B's `Repository` row and full_name are known or guessable (they are visible in Shipit's own UI/API for any stack). This enables cross-repository writes — e.g. forcing `sync_github` on victim stacks, injecting fabricated commit statuses via `StatusHandler`, or manipulating `MembershipHandler`/`CheckSuiteHandler` state for a repo/org the attacker does not control and has no legitimate relationship to. This matches the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires the attacker to control at least one organization/App already onboarded to the target Shipit instance (i.e., know a valid webhook secret for *some* org, not necessarily the victim's) — a realistic scenario for any Shipit deployment serving multiple independent orgs/teams, which is the exact configuration `docs/setup.md`'s "Using Multiple Github Applications" section describes as supported. No Shipit session, `ApiClient` token, or GitHub write access to the victim repo is needed.

### Recommendation
In `verify_signature`, after selecting the app/secret via `repository_owner`, enforce that the resolved app/organization is consistent with any repository the payload claims to affect — e.g., validate that `repository_owner` matches the owner segment of `repository.full_name` (and of `organization.login` if both present) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Shipit is configured with two orgs in `config/secrets.yml`: `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with their own Stack(s), per the multi-org config format in `docs/setup.md`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using their own known secret `S_A`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully against `S_A`. [8](#0-7) 
5. `create` dispatches to `Handlers::PushHandler`, which computes `repository_name` from `full_name` = `"victim-org/victim-repo"`, resolves `victim-org`'s stacks, and calls `stack.sync_github(expected_head_sha: "deadbeef")` — a write against a repository/org the attacker never authenticated for. [6](#0-5)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
