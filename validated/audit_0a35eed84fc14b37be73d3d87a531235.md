### Title
Reward misattribution via unchecked commission-collector aliasing in `update_commission_collector` / `initialize_account_v2` - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The SIMD-0232/SIMD-0464 commission-collector feature lets any vote account's authorized withdrawer point its `inflation_rewards_collector` / `block_revenue_collector` to an arbitrary system-owned, rent-exempt, writable account via `update_commission_collector` and `NewCommissionCollector::validate_and_resolve_key` [1](#0-0) . Unlike the Linea `setCustomContract` bug, where the bridge owner could point a new native token at a target contract already bound to a different native token, here nothing prevents two independent, unprivileged vote accounts (or a vote account and any regular system account that may later be turned into a different vote account) from designating the *same* collector pubkey. This is the same missing "already-bound" check that the report flags: a shared destination identity is accepted without verifying it isn't already entangled with another accounting relationship.

### Finding Description
`NewCommissionCollector::validate_and_resolve_key` only checks that the proposed collector is system-owned, rent-exempt, and writable — it never checks whether that pubkey is already used as a collector by another vote account, nor does it lock in whether the pubkey will remain a plain system account for the life of the relationship [2](#0-1) . `update_commission_collector` then simply writes the resolved key into the vote state after verifying only that the *calling* vote account's withdrawer signed [3](#0-2) ; `initialize_account_v2` performs the identical unchecked resolution during vote-account creation [4](#0-3) .

The reward-calculation code in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` explicitly documents the resulting hazard in `accumulate_lamports`: if vote account A designates system account B as its collector, and B is later allocated/initialized as vote account B which designates itself (`is_vote_account = true`) as its own collector, "the rewards for vote account A will get burned, but the rewards for vote account B will not" [5](#0-4) . More generally, when two different vote accounts both alias the same non-vote-account collector, their commission lamports are silently merged into a single destination without any check that this aliasing was intended, and a repository-level regression test (`test_repeated_inflation_rewards_collector`) exercises exactly this scenario — two distinct vote accounts (`vote1_address`, `vote2_address`) set the identical `collector_address` as their `inflation_rewards_collector`, and the test explicitly notes the collector receives a "double reward" [6](#0-5) .

Because `validate_and_resolve_key` never checks pre-existing usage of the destination pubkey (analogous to Linea's missing `isNewToken(_targetContract)` check on `setCustomContract`), any account controller can pick a collector pubkey that another (unrelated) vote account already uses, causing that other party's commission to be redirected/merged into a destination it does not control the semantics of, or — per the documented A/B collision — causing a legitimate party's commission to be burned instead of paid out.

### Impact Explanation
This produces misattributed and/or destroyed reward lamports at epoch-boundary reward distribution: one validator's commission can be silently combined with, or effectively donated/burned in favor of, another's collector account depending on ordering and whether the shared pubkey is later turned into a vote account. This matches the "misattributed or duplicated rewards" / lamport-loss impact class called out in the validation criteria, occurring purely through normal instruction handlers (`UpdateCommissionCollector`, vote-account initialization) with no special validator/operator privilege beyond being the withdrawer of one's own vote account, which any staking-service or self-custody user can be.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) coincidental/adversarial selection of an already-used collector pubkey, which is easy to do deliberately since collector pubkeys are freely chosen by each withdrawer with no on-chain registry check, or (b) the documented reallocate-as-vote-account race, which needs the collector account to later become a vote account. Case (a) is trivially triggerable by any account owner at will and requires no cooperation from the victim, making front-running/targeting straightforward once an attacker observes a victim's chosen collector address in a pending or historical `UpdateCommissionCollector`/init transaction.

### Recommendation
Add a check in `NewCommissionCollector::validate_and_resolve_key` (or in `update_commission_collector`/`initialize_account_v2`) that rejects a proposed collector pubkey if it is already recorded as the `inflation_rewards_collector` or `block_revenue_collector` of a different, existing vote account, mirroring the `isNewToken` fix pattern from the report. At minimum, the reward-calculation merge logic (`accumulate_lamports`) should not silently combine commissions from two distinct vote accounts under a shared collector without an explicit intent marker, and the vote-account-collision case documented in the code comment should be made a hard error rather than a documented "expected" burn.

### Proof of Concept
The repository's own test demonstrates the aliasing: [7](#0-6) 
Two unrelated vote accounts (`vote1_address`, `vote2_address`) each independently set `new_inflation_rewards_collector: Some(collector_address)` to the same pubkey via ordinary `UpdateCommissionCollector`-style operations, with no rejection at the `validate_and_resolve_key` stage [2](#0-1) ; the following epoch's reward distribution then merges both commissions into the single `collector_address`, as flagged by the test name and comment "get double reward into collector."

impl NewCommissionCollector<'_, '_> {
    /// Validates the collector per SIMD-0232 and returns its pubkey.
    ///
    /// The designated commission collector must either be equal to the vote
    /// account's address OR satisfy ALL of the following constraints:
    ///
    /// 1. Must be a system program owned account.
    /// 2. Must be rent-exempt.
    /// 3. Must not be a reserved account (checked via writable flag).
    pub fn validate_and_resolve_key(
        &self,
        vote_account: &BorrowedInstructionAccount,
        rent: &Rent,
    ) -> Result<Pubkey, InstructionError> {
        match self {
            NewCommissionCollector::VoteAccount => Ok(*vote_account.get_key()),
            NewCommissionCollector::NewAccount(collector_account) => {
                // 1. Must be a system program owned account.
                if collector_account.get_owner() != &system_program::id() {
                    return Err(InstructionError::InvalidAccountOwner);
                }

                // 2. Must be rent-exempt.
                if !rent.is_exempt(
                    collector_account.get_lamports(),
                    collector_account.get_data().len(),
                ) {
                    return Err(InstructionError::InsufficientFunds);
                }

                // 3. Must not be a reserved account (checked via writable flag).
                if !collector_account.is_writable() {
                    return Err(InstructionError::InvalidArgument);
                }

                Ok(*collector_account.get_key())
            }
        }
    }
}

pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Merge the lamport and `is_vote_account` fields of two `RewardCommission`s
///
/// This pays special attention to the case where `is_vote_account` does not
/// match, which can happen in the following situation:
///
/// * a vote account A sets the inflation collector to valid system account B
/// * at some point in the future, that system account B gets allocated and
///   initialized as a vote account B
/// * vote account B sets itself as the inflation reward collector
///
/// In that situation, the rewards for vote account A will get burned, but the
/// rewards for vote account B will not. According to the rules of SIMD-0232,
/// a collector account must either be the vote account itself or a system
/// account that fulfills certain criteria. In the case of vote account A, we
/// are already sure that the collector account is invalid.
///
/// NOTE: if vote account B sets a system account as its inflation collector,
/// then the commission lamports for vote account A will NOT get burned here,
/// but will get burned during `load_and_reward_commission_accounts`
fn accumulate_lamports(src: &RewardCommission, dst: &mut RewardCommission) {
    match (src.is_vote_account, dst.is_vote_account) {
        (false, true) => {
            // Don't accumulate, burn everything in the source
            // reward commission entry.
            //
            // NOTE: There shouldn't be any burned lamports in the
            // source entry, but we're defensive
            dst.burned_lamports = dst
                .burned_lamports
                .saturating_add(src.commission_lamports)
                .saturating_add(src.burned_lamports);
