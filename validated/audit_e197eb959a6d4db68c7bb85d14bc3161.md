### Title
Webhook signature verified against `repository.owner.login`, but pull-request handlers resolve the target `Repository`/`Stack` from independent `repository.full_name` — cross-tenant PR/label state mutation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the GitHub App/secret for `repository.owner.login` and checking the HMAC over the raw body [1](#0-0) . Once verified, `create` dispatches the entire, attacker-controlled JSON body to the registered handlers [2](#0-1) , and `PullRequest::OpenedHandler`/`LabeledHandler` resolve the `Repository` (and thus the `Stack`/`PullRequest` to mutate) purely from `params.repository.full_name`, a field never checked against the org whose secret verified the signature [3](#0-2) .

### Finding Description
The binding the code implicitly relies on is: `org(webhook_secret used to verify signature) == owner(Repository/Stack mutated)`. In fact the controller computes `repository_owner` from `params.dig('repository','owner','login')` solely to select which `Shipit.github(organization: ...)` app/secret to verify against [4](#0-3) . Signature verification only proves "the sender knows the secret configured for that `organization`" — it says nothing about which repository's data is inside the body. Once `head(422)` isn't triggered, `create` parses the raw body again and calls every handler registered for the event with the full, untouched payload [2](#0-1) .

For `pull_request` events, `Shipit::Webhooks.default_handlers` includes `OpenedHandler` and `LabeledHandler` [5](#0-4) . Both resolve their target repository independently via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) [6](#0-5) , and `from_github_repo_name` does a plain DB lookup by `owner/name` parsed from that string [7](#0-6) , with no cross-check against `repository_owner`/the signing organization. The base `Handler#stacks` helper used by other PR handlers has the same pattern: it derives the repository from `payload.dig('repository','full_name')` alone [8](#0-7) .

Exploit flow: an attacker who owns GitHub org `attacker-org` (installed with a real Shipit GitHub App and thus a real, attacker-known `webhook_secret`) crafts a `pull_request`/`opened` (or `labeled`) JSON payload where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`. They sign the raw body with `attacker-org`'s real webhook secret and POST to `/webhooks` with `X-Github-Event: pull_request`. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature, since it was actually computed with that org's secret [1](#0-0) . `drop_unhandled_event`/`check_if_ping` don't block `pull_request`. `create` then invokes `OpenedHandler.call(params)`, which resolves `repository` from `victim-org/victim-repo`'s full name, and if that repository has review-stacks provisioning enabled with `allow_all` (or the attacker also forges a matching label to satisfy `allow_with_label`/`prevent_with_label`), it calls `ReviewStackAdapter#find_or_create!`, creating/mutating a `Stack`/`PullRequest` tied to the victim's repository [9](#0-8) . For `LabeledHandler`, this can archive/unarchive an existing victim review stack [10](#0-9) .

None of the existing guards close this gap: `verify_signature` authenticates the org, not the repository named inside the body; `drop_unhandled_event` only checks event type, not payload contents; the `ExplicitParameters` schema (`params do ... end` blocks) only validates shape/types of fields like `repository.full_name`, not that it matches `repository_owner` [11](#0-10) ; and `Repository.from_github_repo_name` performs an unscoped lookup with no owner cross-check [7](#0-6) .

### Impact Explanation
This is a payload for one repository (`attacker-org/*`, whose secret verified the request) mutating another repository's/tenant's `Stack`/`PullRequest` state (`victim-org/victim-repo`) — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely, an attacker can force-create a review stack, attach a forged `PullRequest` record, or archive/unarchive an existing review stack belonging to a victim tenant they do not control, without ever needing the victim's webhook secret. This is a precursor to unauthorized deploys/merges if review-stack provisioning subsequently drives automated CI/build/merge behavior tied to that stack.

### Likelihood Explanation
Preconditions: the attacker must control at least one GitHub org that is legitimately installed/connected to this Shipit instance (so `Shipit.github(organization: "attacker-org")` resolves to a real, known-to-the-attacker `webhook_secret`), and the victim repository must have review-stack provisioning enabled (`review_stacks_enabled` + a `provisioning_behavior` that the attacker can satisfy, e.g. `allow_all`, or `allow_with_label`/`prevent_with_label` combined with a forged label array in the JSON body). No GitHub-side interaction with the victim repo is required — the attacker constructs the entire JSON body and signs it locally with their own secret. This is a single crafted HTTP request, fully repeatable against any repository whose full name the attacker can guess/enumerate, and works across different attacker-owned orgs. This is a realistic and low-cost attack for any multi-tenant Shipit deployment with review stacks enabled on some repos.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#stacks` / the individual PR handlers), enforce that the repository resolved from `repository.full_name` in the payload actually belongs to the organization that was authenticated (`repository_owner`), e.g. require `Repository.from_github_repo_name(full_name).owner == repository_owner` (case-insensitively) before allowing any handler to act, rejecting the request (422) otherwise.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style):
1. Create two repositories: `victim_repo` (owner: `"victim-org"`, review_stacks_enabled: true, provisioning_behavior: `allow_all`) and configure `Shipit.github(organization: "attacker-org")` with a known test `webhook_secret`.
2. Build a `pull_request`/`opened` JSON payload with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, plus valid `pull_request` sub-fields required by the `params` schema.
3. Compute `X-Hub-Signature` with `attacker-org`'s webhook secret over the raw JSON body, matching `DeliverySigner`'s HMAC-SHA1/SHA256 scheme used by `GithubApp#verify_webhook_signature`.
4. `POST :create` with headers `X-Github-Event: pull_request` and the computed signature.
5. Assert both sides of the binding: **before** — `repository_owner` (`"attacker-org"`) ≠ owner of `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` (`"victim-org"`); **after** — assert `Shipit::Stack.count` increased for `victim_repo.stacks`/`review_stacks` (or `Shipit::PullRequest.count` increased tied to `victim_repo`), and `assert_response :ok`, proving the mutation happened against the victim's repository despite the signature having been verified only for `attacker-org`.
