## Title
Redemption/mint math in the AMM-vault AA sample uses `outstanding == 0` as a silent divide/round-to-zero case, permanently freezing later depositors' funds - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The Thetanuts incident stemmed from a redemption-math/integer-calculation flaw that miscalculated mint/claim amounts once a token's outstanding supply was driven to (near) zero, letting the attacker mint disproportionate shares against real collateral. The ocore repository ships an analogous AMM/vault-style Autonomous Agent template, `test/samples/uniswap_like_market_maker.oscript`, whose mint (“invest”) and redeem (“divest”) branches perform the exact same class of supply-dependent proportional math with no floor/guard for an `outstanding == 0` state, so once the sole liquidity-share holder fully divests, the share-token supply variable legitimately reaches `0` while dust base/asset balance remains in the AA. Any subsequent depositor's funds get accepted into the AA balance but mint `0` shares (`round(share * 0) == 0`), so their funds are permanently unclaimable/frozen since no shares exist to redeem them.

### Finding Description
The "invest" case computes an issuance amount proportional to the current outstanding share supply: [1](#0-0) 
It only treats state as an "initial deposit" (bypassing the outstanding-based math and setting `$issue_amount = balance[base]`) when `$asset_balance == 0 OR $bytes_balance == 0`, i.e. when *asset/byte reserves* are exactly zero - not when `var['mm_asset_outstanding']` (the actual share supply) is zero.

The "divest" case symmetrically computes redemption proportionally to `var['mm_asset_outstanding']`: [2](#0-1) 

Because of integer rounding via `round()` (`formula/evaluation.js` `case 'ceil'/'floor'/'round'`, using `Decimal.ROUND_HALF_EVEN`) [3](#0-2) , a legitimate sequence of operations can drive `var['mm_asset_outstanding']` to exactly `0` while `balance[base]`/`balance[$asset]` retain nonzero dust (the last divesting holder's `round($investor_share * balance[...])` payouts can leave a small remainder due to rounding). At that point:
- Reserve balances (`$asset_balance`, `$bytes_balance`) are non-zero, so the "initial deposit" branch is *not* taken.
- The normal branch executes `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`, and since `var['mm_asset_outstanding'] == 0`, this always evaluates to `0`, regardless of how much the depositor actually contributes.
- The deposit's `payment` message still only sends `$issue_amount` (0) shares back to the depositor, while their real bytes/asset are already consumed as trigger inputs into the AA's balance (the AA keeps them).
- No mechanism exists to redeem funds once `mm_asset_outstanding == 0`, because the "divest" case requires holding `$mm_asset`, none of which exists.

This exactly mirrors the reported bug class: a redemption-math/integer-calculation flaw tied to token supply approaching zero causes value to be extracted or trapped disproportionately to what participants deposited.

### Impact Explanation
Any unprivileged AA trigger sender who deposits into this AA after the share supply has been fully divested to zero permanently loses their contributed bytes and asset tokens - they are absorbed into the AA's balance with no corresponding shares minted and no way to reach them again (the AA has no owner/withdraw case; the only path is via `mm_asset`, whose supply is `0`). This is a concrete AA fund loss/freezing scenario, an accepted impact category for this analysis.

### Likelihood Explanation
No malicious privileges are required. This can occur through completely ordinary usage: a single liquidity provider fully divesting their whole `mm_asset` position (a normal, encouraged action in this AA's design) legitimately zeroes `var['mm_asset_outstanding']`, and any later good-faith depositor triggers the loss. An attacker could also intentionally engineer this state (become sole holder, then fully divest) to grief subsequent users or to trap "donated" funds sent by mistake.

### Recommendation
Guard the mint path so that when `var['mm_asset_outstanding'] == 0` the deposit is treated as a fresh "initial deposit" (reset pricing / require the reserves to also be swept to zero atomically with the last divest, or re-mint proportional to a fixed initial-mint rule) rather than falling through to `round(share * 0)`. Additionally, ensure the "divest" case fully zeroes reserve balances whenever it detects it is paying out the entirety of `mm_asset_outstanding` (i.e., burn-to-zero should also zero remaining dust, or route dust to the last redeemer) so `outstanding == 0` always coincides with `balance == 0`, preventing orphaned/undercollateralized deposits.

### Proof of Concept
1. Deploy the AA from `test/samples/uniswap_like_market_maker.oscript`; trigger `{define: true}` to create `$mm_asset`.
2. Address A sends `trigger.output[[asset=base]] > 1e5` and `trigger.output[[asset=$asset]] > 0` to invest; since both reserves are initially `0`, the "initial deposit" branch fires and A receives `mm_asset_outstanding = balance[base]` shares (case at [4](#0-3) ).
3. A sends all of their `mm_asset` back in a "divest" trigger; `$investor_share = 1`, so A receives (via rounding) almost the entirety of `balance[$asset]`/`balance[base]`, leaving small rounding dust in the AA and `var['mm_asset_outstanding'] = 0` (case at [5](#0-4) ).
4. Address B, unaware of the drained state, sends a normal "invest" trigger (>1e5 bytes + some asset). Since dust reserves are nonzero, the initial-deposit branch is skipped; `$issue_amount = round($investor_share_of_prev_balance * 0) = 0` (line 47). B's funds are added to the AA's balance but B receives `0` `mm_asset` shares.
5. B (and everyone else) can never redeem these funds: the only redemption path requires holding `mm_asset`, whose total supply is `0`.
