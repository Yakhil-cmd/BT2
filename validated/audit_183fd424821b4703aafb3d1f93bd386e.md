### Title
Cross-Repository Commit Status Forgery via Unscoped SHA Lookup in StatusHandler - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely by `sha` across the *entire* `Commit` table, with no scoping to the repository that the incoming webhook's verified signature actually authenticates. This breaks the trust binding "the GitHub organization/repository whose webhook signature is verified" == "the repository whose commit state is mutated," allowing a `status` event that is validly signed for one organization/repository to alter commit statuses belonging to a completely unrelated stack/repository, provided the SHAs coincide (a realistic pre-image, since collaborators, forks, and cherry-picks routinely produce identical SHAs across repos, and SHAs are public information).

### Finding Description
Webhook authenticity is established in `app/controllers/shipit/webhooks_controller.rb#verify_signature`, which selects the `GitHubApp` to verify against using the **unverified** `repository.owner.login` (or `organization.login`) field of the payload: [1](#0-0) 
This only proves the payload was signed by *some* organization's configured `webhook_secret` — it does not constrain which repository's data may be mutated by the handler that subsequently runs.

Every other handler in `app/models/shipit/webhooks/handlers/` scopes its side effects through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` (i.e., the `repository.full_name` field of the *same, signed* payload) before touching any records: [2](#0-1) 
`CheckSuiteHandler` and `PushHandler` correctly follow this pattern: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, ignores the `repository`/`stacks` scoping entirely and looks up commits purely by SHA, globally: [5](#0-4) 

Because `Commit.sha` is not globally unique across `Stack`s/repositories (two different repositories can legitimately contain a commit with the identical SHA — via forks, subtree merges, cherry-picks, or repository renames/migrations that Shipit tracks as separate `Stack` records), a `status` webhook that is validly signed for Organization/Repository A can create or overwrite the GitHub status of a commit that actually belongs to Stack/Repository B, as long as any `Commit` row in the database shares that `sha`. The equality the engine implicitly (but incorrectly) relies on is:

`organization whose webhook_secret signed the event == repository/stack whose Commit rows may be mutated`

This does not hold, because `StatusHandler` never checks `repository_name`/`stacks` before calling `commit.create_status_from_github!(params)`.

### Impact Explanation
`create_status_from_github!` feeds directly into `Commit#status`/`Commit#deployable?` and `Commit#add_status`, which drives production-affecting automation: `Commit#deployable?` gates whether continuous delivery may deploy a commit (`schedule_continuous_delivery` → `ContinuousDeliveryJob`), and `blocked?`/`success?` gate whether other commits can be shipped: [6](#0-5) [7](#0-6) 
An attacker who controls (or has push/status-creation rights on) any single repository whose GitHub App is registered in Shipit's `config/secrets.yml` (a normal, legitimate installation, not a Shipit account) can forge a `status` webhook that is properly signed for their own org, but targets a SHA belonging to another team's stack. If that SHA happens to also exist in the victim stack (e.g. via a shared upstream commit, cherry-pick, or a rebased/duplicated history), the attacker can force a `success` status onto it, unblocking `continuous_deployment?` and triggering an unauthorized deploy — this maps to the report's core bug class ("a single validator can vote on data it doesn't own to force a state transition it isn't authorized to force") and satisfies the "unauthorized deploy" Critical-impact criterion in this engine's context.

### Likelihood Explanation
Exploitation requires: (1) the target Shipit deployment configured with more than one GitHub organization/app (`docs/setup.md`'s documented "Using Multiple Github Applications" feature), and (2) a SHA collision between the attacker-controlled repository and the victim stack's repository. SHA collisions are not cryptographic-collision-hard in this scenario — they occur naturally in real-world Git workflows (forks, monorepo splits, repository migrations tracked as separate `Stack`s, shared vendor commits). No Shipit credentials, `ApiClient` token, or session are required — only a legitimately signed webhook from any configured GitHub App installation, which any repository owner/collaborator/CI integration can trigger by posting a commit status to their own repo. This is a real, currently-shipped code path (not test/docs) with no additional gating.

### Recommendation
Scope `StatusHandler#process` the same way every other handler is scoped — via `stacks` (derived from the verified payload's `repository.full_name`) — before resolving commits:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the invariant that a webhook's verified organization/repository is the only repository whose commit state that webhook can mutate.

### Proof of Concept
1. Shipit is configured with two organizations/apps, `org-attacker` and `org-victim`, per `docs/setup.md`'s multi-app setup, each with a distinct `webhook_secret`.
2. `Stack` "org-victim/prod" has a `Commit` with `sha = "abc123...”` (e.g., a shared upstream/vendored commit also present in `org-attacker/repo`'s history).
3. Attacker (owner/collaborator of `org-attacker/repo`) posts a commit status (`state: success`) to their own repository/commit via the GitHub API — this is a normal action within their own repo permissions.
4. GitHub delivers a `status` webhook to Shipit's `/webhooks` endpoint, signed with `org-attacker`'s `webhook_secret`. `WebhooksController#verify_signature` succeeds because it only checks that org-attacker's secret matches.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matching the victim's commit in "org-victim/prod" (no repository check performed), and calls `create_status_from_github!`, marking it `success`.
6. If `org-victim/prod` has `continuous_deployment?` enabled and no other blocking status, `Commit#schedule_continuous_delivery` triggers `ContinuousDeliveryJob`, resulting in an unauthorized deploy of a commit the attacker never had permission to affect.
