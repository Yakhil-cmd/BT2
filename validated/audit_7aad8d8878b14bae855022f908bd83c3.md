### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up which `Commit` a GitHub `status` webhook applies to using only the commit's `sha`, globally across the entire database, instead of scoping the lookup to the repository the webhook was actually verified for. [1](#0-0) 

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook against the GitHub App/organization derived from `repository_owner` in the payload (or the org fallback), and only that organization's `webhook_secret` is checked with an HMAC over the raw payload. [2](#0-1) 

The base `Handler` class does provide a repository-scoped helper, `stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from the payload before touching any records — and other handlers such as `CheckSuiteHandler` correctly use it (`stacks.where(branch: ...)`). [3](#0-2) [4](#0-3) 

`StatusHandler`, however, ignores `stacks`/`repository_name` entirely and instead does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This finds every `Commit` row across *every* stack/repository in the Shipit instance whose `sha` matches the payload's `sha`, and writes the incoming status to all of them. [1](#0-0) 

This breaks the binding "the repository/organization whose webhook signature was verified == the repository whose commit status is written." Any organization with a legitimate, signed GitHub App installation on Shipit can send a `status` event referencing a `sha` that is also tracked under a completely different organization/repository's stack (e.g. a shared git ancestor commit from a fork, a monorepo split into multiple stacks, or any coincidentally-identical SHA across repos tracked by the same Shipit instance) and have that status applied to the unrelated stack's commit.

Writing a `Status` record triggers real side effects on the *unrelated* stack:
- `enable_ci_on_stack` marks CI as enabled for that stack.
- `schedule_continuous_delivery` calls `commit.schedule_continuous_delivery`, which — if that stack has continuous deployment enabled — enqueues `ContinuousDeliveryJob`, potentially triggering an actual deploy.
- `add_status` also calls `stack.schedule_merges` (queues `ProcessMergeRequestsJob`) when the new status is `pending` or `success`. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who controls (or compromises) any single organization/repo already onboarded onto the Shipit instance can, using only their own legitimately-signed webhook, forge CI status ("success") for a commit belonging to an unrelated organization/repository's stack, as long as that stack tracks a commit with the same `sha`. If that unrelated stack has `continuous_deployment` enabled and the forged "success" status satisfies its deploy-readiness checks, this can trigger `ContinuousDeliveryJob`, an unauthorized deploy of code the attacker never legitimately validated with CI — matching the "unauthorized deploy" Critical impact category. Even short of triggering a deploy, it silently pollutes another repository's CI/commit history state and can advance its merge queue (`ProcessMergeRequestsJob`), an authorization boundary that should be scoped per-repository/organization.

### Likelihood Explanation
Exploitability depends on a `sha` collision between the attacker-controlled repository and the target stack's tracked commits. This is not adversarially forgeable in the general case (SHA-1 preimage is computationally infeasible), but it is realistically achievable in common Shipit deployment patterns: monorepos split into multiple Shipit stacks that share commit history, forked repositories deployed as separate stacks, or repositories imported/rebased from a shared upstream — all of which legitimately share identical commit SHAs across stacks tracked by the same Shipit instance. Given that requirement, likelihood is Low but the missing repository scoping is a clear code defect independent of how often the precondition is met, and every other webhook handler in the codebase (`CheckSuiteHandler`, `Handler#stacks`) demonstrates that the repository-scoping mechanism was intended to be used here as well.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository derived from the webhook payload, mirroring the pattern already used in `CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring statuses can only be written for commits belonging to the repository whose signature was actually verified.

### Proof of Concept
1. Organization A installs the Shipit GitHub App and has a valid `webhook_secret` for repo `orgA/app`. A stack for `orgA/app` (environment `production`) is configured in Shipit with `continuous_deployment: true`.
2. Organization B also has a stack in the same Shipit instance for `orgB/app`, tracking commit `sha = C` (e.g., because `orgB/app` was forked from `orgA/app` and shares history, or the repos happen to have re-based/synced content producing the same commit hash).
3. Attacker, who only controls org A (and thus can send a validly signed webhook for `orgA/app`), sends a `status` webhook to `/github/webhooks` with `sha: C`, `state: "success"`, `context: "ci/required-check"`, correctly signed with org A's `webhook_secret`.
4. `WebhooksController#verify_signature` succeeds (it only checks org A's secret against the raw payload). [8](#0-7) 
5. `StatusHandler#process` runs `Commit.where(sha: 'C')`, which matches the commit in **both** stacks (org A's and org B's), and calls `create_status_from_github!` on each — writing a forged "success" status onto org B's commit despite the webhook never being signed by org B's secret. [1](#0-0) 
6. If org B's stack has `continuous_deployment: true` and this status satisfies its deploy readiness checks, `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, deploying org B's stack without org B ever having produced or approved that status. [6](#0-5)
