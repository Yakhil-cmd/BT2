### Title
Sustained high-utilization whale market overflows i128 in accrual and permanently freezes the market - (File: common/src/rates/simulate.rs)

### Summary
The analog of CVE-2014-3647 — a state transition that an ordinary, unprivileged input can drive into an unrecoverable crash — maps onto XOXNO Lending's interest accrual: `accrue_step` values scaled debt as `borrowed * borrow_index` in `i128`, and the market-level value can overflow that domain well before the borrow-index cap (`MAX_BORROW_INDEX_RAY = 1e36`) ever engages. Every pool mutation calls `interest::global_sync` first, so once the value product overflows, `MathOverflow` traps every subsequent entrypoint touching that market: no withdraw, repay, liquidate, or `update_indexes`. Funds in the market are permanently frozen.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-61` computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` and `supplied_original = scaled_to_original(env, supplied, supply_index)`, both of which are `scaled.mul(env, index)` — an `i128` RAY multiply that panics with `GenericError::MathOverflow` on overflow (`common/src/rates/scaling.rs:14`, `common/src/math/fp.rs:12-16`). The same product is recomputed in `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`). `update_borrow_index` caps the *index* at `1e36`, but nothing caps the *value* `borrowed × index`, which overflows `i128` (~1.7e38) when scaled debt is large — e.g. a market holding on the order of a billion whole 18-decimal tokens (scaled ~1e45 at index RAY) needs only a ~170x index growth, reachable at the steep end of the utilization curve over a few years.

`global_sync` in `contracts/pool/src/interest.rs:20-33` runs this accrual unconditionally at the head of every market mutation (`Cache::load → interest::global_sync → mutate`, per `contracts/pool/README.md:159-168`). Once the product overflows, the panic is deterministic and unrecoverable — the index cap never engages because accrual traps before storing anything. The codebase's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`) demonstrates exactly this: after the cliff, `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW`, and the test asserts the index cap did not engage. Docs acknowledge the gap: "valid caps and bounded indexes do not guarantee that future accrual fits. Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first" (`docs/reference/formulas.md:432-437`).

### Impact Explanation
Permanent freezing of all user funds in the affected market — suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate (liquidation withdrawals also pass through the pool's accrual path). Because the freeze happens inside accrual rather than in a discretionary guard, there is no code path that skips it; even `clean_bad_debt`-style cleanup runs `global_sync` first. This is permanent freezing of funds, a Medium-severity impact consistent with the source advisory.

### Likelihood Explanation
A single unprivileged address can put the market on this trajectory: `supply` a very large amount and `borrow` near the utilization maximum via the controller, then simply let time pass — the index growth is driven by `update_indexes`/any touch and requires no further attacker action. Practical constraints keep it Medium rather than High: it needs a whale-scale position (the test uses ~1e9 whole tokens at 18 decimals), sustained high utilization on a steep curve segment, and multi-year horizons (the test asserts the cliff within 40 years). No privileged role, bad parameter, or oracle manipulation is required — only legitimate `supply`/`borrow` calls and elapsed time.

### Recommendation
Bound the value domain, not just the index domain:
- In `accrue_step`/`update_borrow_index`, detect when `borrowed × new_index` or `supplied × new_index` would exceed `i128` and stop accruing (clamp the index to the largest value that keeps products representable), so the market degrades to zero interest rather than a hard trap on every entrypoint.
- Alternatively, make accrual saturating at the value ceiling and emit an event when the clamp engages, since `docs/reference/formulas.md:437` already notes "no dedicated ceiling alarm is emitted."
- As a secondary mitigation, enforce a scaled-debt ceiling at `borrow`/`create_strategy` time (checked `borrowed + delta` against `i128::MAX / MAX_BORROW_INDEX_RAY`) so a market can never enter the region where accrual can trap.

### Proof of Concept
The scenario is already exercised by the in-repo test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`: create an 18-decimal market with the XLM borrow curve, `supply` ~`BILLION * 1e18` units, `borrow` 98% of it, then advance time in one-year steps calling `update_indexes`. Once `borrowed × borrow_index` exceeds `i128`, `try_update_indexes_for` reverts with `MathOverflow` (error 33), and both `try_withdraw_raw` and `try_repay` revert with the same error because each runs `global_sync` first — the market is permanently frozen while `borrow_index < MAX_BORROW_INDEX_RAY`.
