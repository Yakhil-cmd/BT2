### Title
Cross-organization Team membership mutation via mismatched `repository.owner.login` / `organization.login` in membership webhook - ([File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` selects the organization used for HMAC signature verification from `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')` only when the former is absent. `MembershipHandler#find_or_create_team!`, however, always reads `params.organization.login` regardless of what org's key verified the signature, and only assigns `team.organization` on record *creation* — an existing `Team` row (matched purely by `params.team.id`, i.e. GitHub's numeric team id) is mutated without any recheck that the signing organization owns that team.

### Finding Description
The broken binding is: `organization whose webhook_secret verified the HMAC signature (repository_owner)` **should equal** `organization that legitimately owns the Team record mutated by MembershipHandler (params.organization.login / team.organization)`.

Code path:
- `Shipit::WebhooksController#verify_signature` picks the signing org via `repository_owner`: [1](#0-0) [2](#0-1) 

- `MembershipHandler` independently reads only the top-level `organization.login`, and looks up the team solely by `github_id`, only assigning `organization` inside the create block (a no-op for pre-existing teams): [3](#0-2) 

In a multi-organization Shipit deployment (`github_app_config(organization)` keyed per-org, as documented), each org has its own `webhook_secret` — legitimately known to that org's own operator, who is otherwise an "unprivileged" party with respect to other tenants' orgs/teams: [4](#0-3) [5](#0-4) 

Exploit flow: an attacker who controls org `attacker-org` (registered in Shipit with its own `webhook_secret`) crafts a raw POST to `/webhooks` with `X-Github-Event: membership`:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "http://x" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
signed with `attacker-org`'s own `webhook_secret`. `repository_owner` resolves to `attacker-org` (because `repository.owner.login` is present and checked first), so `verify_signature` passes using the attacker's own legitimately-known secret. `MembershipHandler#process` then reads `params.organization.login` = `victim-org` and `params.team.id` = the real GitHub id of a `Team` already persisted for `victim-org` (created earlier by a genuine webhook). `Team.find_or_create_by!(github_id:)` finds the existing row and the block (which would set `organization`) is skipped, so `team.add_member(User.find_or_create_by_login!('attacker-login'))` executes against `victim-org`'s real team — with no check that the signing org matches the team's `organization`.

Existing guards fail because: `verify_signature` and `drop_unhandled_event` only gate on event type/signature validity, not on cross-consistency between the signing org and the payload's business data; the `ExplicitParameters` schema on `MembershipHandler` validates types/presence of `organization.login`, `team.id`, etc., but not that they are internally consistent with `repository_owner`; there is no model-level validation tying `Membership`/`Team` mutation to the authenticated org.

### Impact Explanation
If the targeted `Team` is one of `Shipit.github_teams` (used by `User#authorized?` to gate access to the whole app): [6](#0-5) 
then the attacker can add an arbitrary (attacker-controlled or fabricated) login into that team's membership, flipping `authorized?` to true for that `User` row and granting them access to another tenant's Shipit instance/stacks — an escalation into `Shipit.github_teams` authorization for a foreign org, matching the High-severity category defined in the rules. The action is repeatable against any known/guessable `team.id` and is not limited to a single team or org; the attacker only needs to learn a target team's numeric GitHub id (which may be discoverable/enumerable) and one existing `Team` record already synced into Shipit's database.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured for multiple GitHub organizations (`github_app_config` keyed per-org), a documented and supported deployment mode; (2) attacker must control/operate at least one org registered in that Shipit instance (own webhook_secret, which they legitimately possess as that org's admin — not a Shipit secret); (3) attacker needs the numeric `github_id` of a target team belonging to a different org already present in Shipit's `teams` table. Given these, the attack is a single crafted HTTP POST, fully repeatable, requiring no session, API token, or Shipit-side secret. In the common single-org config this specific divergence is less relevant to gain (both sides need the shared global secret which the attacker doesn't have), so this is significant primarily for multi-tenant deployments, which is an explicitly supported and documented configuration.

### Recommendation
In `MembershipHandler`, verify `params.organization.login` matches an already-known/expected organization when the `Team` record already exists (reject or ignore the mutation on mismatch), and/or have `WebhooksController#repository_owner` prefer `organization.login` for organization-scoped events like `membership` regardless of an attacker-supplied `repository` key, and validate `team.organization == params.organization.login` before applying `add_member`/`members.delete`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), no live GitHub:
1. Configure two `GithubHook::Organization`-style fixtures / stub `Shipit.github_app_config` so `Shipit.github(organization: 'attacker-org')` and `Shipit.github(organization: 'victim-org')` return distinct `GitHubApp` instances with distinct `webhook_secret`s.
2. Create `shipit_teams(:shopify_developers)` (organization: `'shopify'`, known `github_id`) and add it to `Shipit.github_teams` stub.
3. Build a membership payload: `organization.login = 'shopify'`, `team.id = shipit_teams(:shopify_developers).github_id`, `member.login = 'attacker'`, `repository.owner.login = 'attacker-org'`.
4. Sign the raw JSON body with `attacker-org`'s webhook secret and set `X-Hub-Signature` accordingly; set `X-Github-Event: membership`.
5. POST to `/webhooks`.
6. Assert binding before: `repository_owner (== 'attacker-org') != team.organization (== 'shopify')`.
7. Assert response is `:ok` (signature accepted) — proving verification passed on the wrong org's secret.
8. Assert `shipit_teams(:shopify_developers).members.reload.map(&:login)` now includes `'attacker'` — proving the foreign org's team membership was mutated by a request signed with a different org's secret, i.e. the binding is violated after the request as well as before.

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     someothergithuborg:

        id:
