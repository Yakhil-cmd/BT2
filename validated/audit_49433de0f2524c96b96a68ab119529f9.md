### Title
Webhook signature verification silently no-ops for GitHub orgs configured without a `webhook_secret`, allowing unauthenticated forgery of `membership` events that grant `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
The Art Gobblers bug allowed an attacker to "revive" a burnt token because a security-relevant check (`ownerOf`/approval clearing) was skipped after a privileged action, letting an attacker replay state that should have been invalidated. The analogous binding break here is: `Shipit::WebhooksController#verify_signature` selects *which* GitHub App configuration (and thus which `webhook_secret`) to verify a webhook against using an **unverified, attacker-controlled** payload field (`repository.owner.login` / `organization.login`), and the underlying verifier treats a missing secret as automatic success. The equality that should hold — "the organization whose credential authenticated the request equals the organization whose data is written" — is broken whenever a configured GitHub org has no `webhook_secret`, because in that case *no* cryptographic check binds the payload to GitHub at all.

### Finding Description
`WebhooksController#verify_signature` derives the org to verify against directly from the JSON body, before any authentication has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GithubApp`/`GithubOAuthApp` instance built from that organization's config, whose `verify_webhook_signature` is: [3](#0-2) [4](#0-3) 

`return true unless webhook_secret` means that for any configured organization whose `webhook_secret` is blank/nil, **every** request claiming to be from that org is accepted as verified, regardless of the `X-Hub-Signature` header content. The shipped sample configuration explicitly ships this pattern (`webhook_secret: # nil`): [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the fully attacker-controlled payload straight to the registered event handlers: [6](#0-5) 

For the `membership` event, handlers create/attach `Team`, `User`, and `Membership` records purely from payload content, with no re-verification of the actor's real GitHub membership - confirmed by the test suite driving this behavior end-to-end from an HTTP POST: [7](#0-6) 

Because `User#authorized?` gates access to privileged UI/API surfaces (e.g. `ApiClientsController`) purely on DB team membership, a forged `membership` webhook that inserts a `Membership` row for the attacker's own GitHub account into an org listed in `Shipit.github_teams` is sufficient to satisfy that authorization check: [8](#0-7) 

The binding broken, expressed as an equality that should hold but doesn't:
`organization that cryptographically authenticated the webhook == organization whose Team/Membership/User records are written`, which fails whenever the resolved org's `webhook_secret` is blank, because in that branch **no organization is actually authenticated at all**.

### Impact Explanation
This directly matches the specified High-severity criterion "escalation into `Shipit.github_teams` authorization" and, depending on registered handlers, can also forge `push`/`status`/`check_suite` events that enqueue `GithubSyncJob`/`RefreshCheckRunsJob` against arbitrary tracked stacks - all reachable by an anonymous, unauthenticated internet client with zero prior access (no Shipit session, no ApiClient token, no GitHub credentials), since `WebhooksController` has no authentication requirement other than `verify_signature` itself.

### Likelihood Explanation
This requires no privileged access, no social engineering, and no host-application misconfiguration beyond a normal, engine-documented deployment shape (multi-organization GitHub App config, one of which has not yet had a `webhook_secret` provisioned - exactly the state the shipped sample config represents). The webhook endpoint is intentionally public and unauthenticated by design (`skip_before_action :verify_authenticity_token`), so the only gate is `verify_signature`, and that gate's own logic (`return true unless webhook_secret`) fails open rather than closed.

### Recommendation
- Change `verify_webhook_signature` to fail closed: if `webhook_secret` is blank for the resolved organization, reject the request (`return false`) instead of returning `true`.
- Do not select the verification key using data taken from the unverified request body; require an explicit, out-of-band identifier for routing (e.g. a per-org path segment or a header the app itself controls), or verify against all configured secrets and only proceed if at least one matches.
- Require `Shipit.github` org configs used with `WebhooksController` to have a non-blank `webhook_secret` at boot (fail fast / raise on missing secret) rather than allowing a silently-open configuration to be deployed.

### Proof of Concept
1. Deploy Shipit with two GitHub App orgs configured, where org `someothergithuborg` has `webhook_secret: nil` (as in the shipped `config/secrets.development.shopify.yml` template) while at least one org is present in `Shipit.github_teams`.
2. As an anonymous attacker with no Shipit account and no GitHub App credentials, send:
```
POST /github/webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything-or-empty
Content-Type: application/json

{
  "action": "added",
  "organization": { "login": "someothergithuborg" },
  "team": { "id": 1, "name": "Fake Team", "slug": "fake-team", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
3. Because `someothergithuborg` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb` line 77), `verify_signature` passes, and the membership handler creates a `Team`/`User`/`Membership` row for `attacker-github-login` exactly as demonstrated by the existing test `":membership creates the mentioned team on the fly"` / `":membership creates the mentioned user on the fly"`.
4. If `attacker-github-login`'s corresponding `Shipit::User` later authenticates via OmniAuth (`GithubAuthenticationController#callback`), `User#authorized?` now returns `true` because the forged `Membership` satisfies `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, granting access to privileged pages such as `ApiClientsController` without ever having real GitHub team membership.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
