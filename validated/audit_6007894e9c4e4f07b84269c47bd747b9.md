### Title
Reentrancy protection for EVM value-transfer calls is applied to the wrong branch, leaving `.transfer()`/`.send()`-style stipend calls unprotected - (File: substrate/frame/revive/src/vm/evm/instructions/contract.rs)

### Summary
The original report flags Solidity's `.transfer()` as bad practice because its fixed 2300-gas stipend can silently break, and recommends explicit reentrancy checks when moving value. `pallet-revive`'s EVM-compatibility layer already implements a deliberate analog defense for this exact pattern: a `ReentrancyProtection::AllowNext` mode intended for "calls that transfer value but restrict gas so that the callee only has a stipend gas amount," because (per the code's own comment) PVM's gas/weight scale does not guarantee that a stipend-sized budget is insufficient for a reentrant call the way Ethereum's 2300 gas does. However, the dispatch logic in `run_call` appears to apply this explicit protection to the wrong case.

### Finding Description
In `substrate/frame/revive/src/vm/evm/instructions/contract.rs`, `run_call` decides the reentrancy mode from a match on `(value.is_zero(), gas_limit == CALL_STIPEND)`: [1](#0-0) 

- Arm `(false, _)` matches whenever `value != 0`, **regardless of `gas_limit`**, and yields `ReentrancyProtection::AllowReentry` (no explicit protection).
- Arm `(_, true)` — reachable only when `value == 0` (since the first arm already consumes all `value != 0` cases) — yields `ReentrancyProtection::AllowNext` (the strict, explicit stipend protection).

Per the accompanying prdoc documenting solc's actual codegen (`prdoc/stable2603/pr_11227.prdoc`), the common real-world pattern `target.transfer(amount)`/`target.send(amount)` with `amount > 0` is compiled with `gas_limit = 0` on the stack, relying on the EVM's automatic "add 2300 stipend when value > 0" rule — it is *not* the literal `gas_limit == 2300` case. Only the atypical `transfer(0)`/`send(0)` case has the compiler literally push `2300`.

The `ReentrancyProtection::AllowNext` doc comment in `exec.rs` states the protection exists precisely because "due to gas scale differences that guarantee does not automatically hold in revive," an explicit reentrancy block is required for calls that transfer value under a stipend: [2](#0-1) 

Yet the actual value-transferring case (`value != 0`, the scenario this comment describes) is routed to `AllowReentry` by the first match arm, while `AllowNext` is applied only to the zero-value literal-stipend case — which is not "a call that transfers value" at all. This suggests the intended protection is applied to the wrong branch, contradicting the documented purpose of the `AllowNext` mode.

The gap is also visible by contrast with the PVM-native host function `call_evm`, which computes the stipend condition without inverting value/zero priority: `add_stipend = !value.is_zero() || gas == CALL_STIPEND` [3](#0-2) . This function does not appear to select a `ReentrancyProtection` mode at all in the excerpt seen, so I could not compare its reentrancy handling directly.

### Impact Explanation
If `AllowReentry` truly grants unrestricted re-entry (rather than merely relying on weight exhaustion to organically prevent it, which the code comments say cannot be relied upon), then a malicious contract receiving value via the EVM-emulated `.transfer(amount)`/`.send(amount)` opcode sequence (`CALL` with `value != 0`, `gas_limit = 0`) would not get the explicit `AllowNext` reentrancy guard that pallet-revive's own design intends for this exact scenario. Combined with a classic checks-effects-interactions violation in a target contract's withdrawal logic, this could enable value-draining reentrancy — the exact class of bug the original `.transfer`/reentrancy report warns about, and one `pallet-revive` explicitly tried to close.

### Likelihood Explanation
The reachable entry point is a normal, unprivileged, permitted contract call (`pallet_revive::Pallet::call`/`eth_transact`), executing attacker-supplied EVM bytecode that receives a value transfer and calls back — no privileged role, governance, or validator/collator control is required. The triggering condition (`value != 0`, `gas_limit == 0`) is exactly what solc emits for ordinary `.transfer()`/`.send()` calls, so it is the common case, not an edge case.

### Recommendation
Verify (and if necessary, fix) the match-arm logic in `run_call` so that `AllowNext` is applied whenever a call is stipend-limited due to a value transfer (i.e., also cover `value != 0` combined with `gas_limit == 0`/insufficient-gas heuristics consistent with solc codegen), not only the literal `gas_limit == 2300`, zero-value case. Add differential tests mirroring `evm_call_stipend_prevents_transfer_reentrancy` that assert `AllowNext` (not `AllowReentry`) is selected and enforced for the `value > 0`, `gas_limit == 0` code path that solc actually emits for `.transfer(amount)`/`.send(amount)`.
