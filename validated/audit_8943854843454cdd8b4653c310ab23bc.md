### Title
Webhook signature verifier is selected from `repository.owner.login` while the acted-upon repository/stack is selected from a separate, unvalidated `repository.full_name` field, allowing cross-tenant forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to verify the signature against using `repository.owner.login` from the untrusted JSON body, but `Handler#stacks` (used by `CheckSuiteHandler#process`) resolves the target repository/stack using the independent `repository.full_name` field via `Repository.from_github_repo_name`. Nothing binds these two attacker-controlled fields together, so a payload verified under one organization's key/secret can act on any other organization's stack and commits.

### Finding Description
The intended binding is: **verifying org (used to select the webhook secret) == owning org of the repository/stack that the handler subsequently mutates**. In code these are two independently-read, attacker-controlled JSON fields:

- Verification key selection: `repository_owner = params.dig('repository', 'owner', 'login')`, used in `verify_signature` to call `Shipit.github(organization: repository_owner)` and check `verify_webhook_signature` against that org's `webhook_secret`. [1](#0-0) [2](#0-1) 

- Target-record selection: `CheckSuiteHandler#process` calls `stacks`, which is built from `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a completely separate field from `repository.owner.login`. [3](#0-2) [4](#0-3) [5](#0-4) 

Root cause: `verify_webhook_signature` in `GithubApp` also returns `true` unconditionally when the selected org has no `webhook_secret` configured (`return true unless webhook_secret`), so if the org named in `repository.owner.login` is configured with a blank secret, the request bypasses verification entirely, regardless of what `repository.full_name` names. [6](#0-5) 

Exploit flow: an attacker who can deliver a webhook attributed to an organization onboarded into Shipit (`repository.owner.login = attacker-org`, e.g. one configured with `webhook_secret: nil` as shown in the sample config) crafts a `check_suite` payload where `repository.full_name = "victim-org/victim-repo"` and `check_suite.head_sha` / `head_branch` are attacker-chosen values matching an existing victim `Stack`/`Commit`. The signature check passes against `attacker-org`'s (blank) secret, but `CheckSuiteHandler#process` looks up stacks under `victim-org/victim-repo` and calls `stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!)`, which will use the app's installation token (for whatever org owns that commit) to call the GitHub API against the victim's commit — a credential-scoped action triggered by an unauthenticated cross-tenant party.

None of the existing guards close this gap: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schema only validates presence/type of `check_suite.head_sha`/`head_branch`, not repository ownership; there is no check anywhere that the owner segment of `repository.full_name` matches `repository.owner.login`.

### Impact Explanation
A successful forged request causes `schedule_refresh_check_runs!`/`RefreshCheckRunsJob` to run against a victim organization's `Commit`, triggering GitHub API calls using the app's installation token for the victim, for a request that never authenticated as the victim. This is a payload for one repository (tenant) mutating another tenant's stack/commit state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any victim stack/branch/commit combination known to the attacker (branch names and commit SHAs are often publicly visible via GitHub), as long as attacker controls or can name one onboarded organization whose verification passes (blank secret, or a secret they know).

### Likelihood Explanation
Exploitability depends on a specific precondition: the attacker must be able to have a request verified as some organization configured in `Shipit.github` — either because that org has no `webhook_secret` set (as shown as a placeholder in `config/secrets.development.shopify.yml`) or because the attacker knows/controls that org's secret. If every onboarded organization has a properly random, secret `webhook_secret` unknown to the attacker, this specific bypass is blocked for that step; however, the underlying design flaw — that `repository.full_name` used for record lookup is never cross-checked against the verified `repository.owner.login` — remains present in all deployments and is the true root cause. Given the sample/blank secret configuration pattern committed in the repo and the multi-tenant `github:` config keyed per-organization, this is a realistic misconfiguration risk in production multi-org Shipit deployments.

### Recommendation
In `Handler#repository_name` / `stacks`, and in `WebhooksController`, require that the owner segment parsed from `repository.full_name` equals `repository.owner.login` (the value used to select the verifying `GithubApp`), rejecting the payload otherwise. Additionally, never allow `verify_webhook_signature` to silently return `true` for orgs with blank `webhook_secret` in non-test environments; treat a missing secret as a hard configuration error rather than "verification not required."

### Proof of Concept
```ruby
test ":check_suite with mismatched repository.owner.login and repository.full_name does not schedule refresh for victim stack" do
  victim_stack = shipit_stacks(:shipit) # owns repository "shopify/shipit-engine" with commit fixture
  victim_commit = shipit_commits(:first)

  # attacker-org configured with no webhook_secret in Shipit.github
  request.headers['X-Github-Event'] = 'check_suite'
  payload = JSON.parse(payload(:check_suite_master))
  payload['repository'] ||= {}
  payload['repository']['owner'] = { 'login' => 'attacker-org' } # verifies with blank secret
  payload['repository']['full_name'] = victim_stack.repository.full_name # points at victim
  payload['check_suite']['head_sha'] = victim_commit.sha
  payload['check_suite']['head_branch'] = victim_stack.branch

  assert_no_enqueued_jobs do
    post :create, body: payload.to_json, as: :json
  end
  # Binding check: verifying org ('attacker-org') != owning org of victim_commit.stack ('shopify')
  refute_equal 'attacker-org', victim_stack.repository.owner
end
```
This demonstrates that absent an owner/full_name consistency check, `schedule_refresh_check_runs!` would be enqueued for the victim's commit purely because `repository.full_name` names it, even though verification was performed against an unrelated (`attacker-org`) organization's key.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'
