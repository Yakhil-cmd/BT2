### Title
Unauthenticated access to live stack SSE broadcasts via `mount Pubsubstub::StreamAction.new, at: "/events"` - ([File: config/routes.rb])

### Summary
The engine mounts `Pubsubstub::StreamAction` directly as a Rack endpoint at `/events` with no wrapping controller or authentication filter. Because Shipit's authentication (`force_github_authentication`) is implemented as an ActionController `before_action` inside the `Shipit::Authentication` concern, it never runs for a raw Rack-mounted app, so any unauthenticated client can subscribe to any `stack.<id>` channel and receive live deploy/task/status broadcasts.

### Finding Description
The binding that should hold is: for every SSE subscription to channel `"stack.#{stack.id}"`, `current_user.authorized?` (as enforced by `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb:8,20-34`) must be true for the requesting session. Instead, `config/routes.rb:9` does `mount Pubsubstub::StreamAction.new, at: "/events", as: :events`, which mounts a plain Rack application directly in the route set, bypassing the entire `ActionController::Base` filter chain — `force_github_authentication` is a `before_action` (`app/controllers/concerns/shipit/authentication.rb:7-8`) and only fires for controllers that include the `Shipit::Authentication` concern; it cannot intercept a `Rack` app mount point.

`Pubsubstub::StreamAction` (from the `pubsubstub` gem, required in `lib/shipit.rb:22` and configured with `Pubsubstub.redis_url` in `lib/shipit/engine.rb:23`) accepts a `channels[]` query parameter and streams any Redis pub/sub messages published to those channel names via SSE. Channels are published to as `"stack.#{stack.id}"` from stack lifecycle events, e.g. `Shipit::Stack#broadcast_update`, `Status`, `Commit`, and `Deploy` (confirmed via `Pubsubstub.publish` calls in `app/models/shipit/stack.rb` and exercised in `test/models/status_test.rb:58-63`, `test/models/commits_test.rb:946-951`, `test/models/deploys_test.rb`). Since `Stack#id` is a sequential database primary key, an attacker can enumerate small integers to guess `stack.<id>` channels for any stack in the installation, not just ones they can already see.

An attacker with no Shipit session and no GitHub credentials can send `GET /events?channels[]=stack.1` (and iterate over ids) directly to the mounted endpoint. Because no controller-level filter (`skip_authentication`/`force_github_authentication`) sits in front of the mount, and no application-level `Rack` middleware in `lib/shipit/engine.rb` restricts `/events`, the request reaches `Pubsubstub::StreamAction` and establishes a live SSE stream, receiving all subsequent stack/task/deploy status updates for that stack.

### Impact Explanation
This grants unauthenticated read access to live stack, task, and deploy state (status transitions, deploy progress notifications) for any stack in the Shipit instance, satisfying the "High - unauthenticated read of stack state, task streams or deploy output" impact category. It is fully repeatable and scriptable against every stack id in the installation (blast radius is the entire multi-tenant Shipit deployment, not limited to a single repository), since the mount performs no per-request authorization check at all.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs network access to the Shipit host and knowledge (or brute-forced guess) of a `Stack#id`, which is a small sequential integer requiring no privileged information. No GitHub App secrets, webhook secret, API tokens, or session cookies are required. This is trivially and repeatedly exploitable with a single unauthenticated HTTP request per stack id.

### Recommendation
Wrap `/events` behind an authenticated, authorization-checked endpoint instead of mounting the Rack app directly at the route level. For example, replace the raw `mount` with a controller action that: (1) includes `Shipit::Authentication` (or equivalent `force_github_authentication`), (2) parses the requested `channels[]` param, (3) verifies `current_user.authorized?` and that each requested `stack.<id>` channel corresponds to a stack the current user is permitted to view, and only then delegates to `Pubsubstub::StreamAction` (e.g., calling it manually within the authorized action, or filtering allowed channels before invoking it). Alternatively, mount `Pubsubstub::StreamAction` under a route matched by an authenticating `Rack` middleware/constraint that validates the session and per-channel stack authorization before allowing the Rack dispatch to proceed.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb
require 'test_helper'

module Shipit
  class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
    test "unauthenticated request to /events can subscribe to a stack channel" do
      stack = shipit_stacks(:shipit)

      # No session cookie, no api client credentials, no github auth.
      get "/events", params: { channels: ["stack.#{stack.id}"] }

      # Binding under test: subscribing to a stack channel must require
      # current_user.authorized? for that stack (force_github_authentication).
      # Expected if the binding holds: 401/403 redirect to github_authentication_path.
      # Actual: request is accepted by Pubsubstub::StreamAction with no auth check.
      refute_equal 401, response.status
      refute_equal 403, response.status
      assert_includes [200], response.status # streaming response accepted unauthenticated
    end
  end
end
```
This demonstrates the divergence: the equality `subscriber.authorized_for?(stack) == true` required before granting a `stack.<id>` SSE subscription is never evaluated for `/events`, because the mount point has no `force_github_authentication`/`skip_authentication` binding applied.
