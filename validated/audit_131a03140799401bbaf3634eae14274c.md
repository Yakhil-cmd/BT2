Based on my research, I found a plausible analog to the HTTP response-splitting bug class: **delimiter injection in Obyte's data-feed KV-store keys**, where an unprivileged unit poster's `feed_name` / string value data is concatenated with an unescaped `\n` delimiter used to compose and later re-parse a composite key.

### Title
Delimiter Injection in Data Feed KV-Store Keys via Unsanitized `feed_name`/Value Strings - (File: `data_feeds.js`, `main_chain.js`, `string_utils.js`)

### Summary
Data feed messages (`app: "data_feed"`) can be posted by any unit author. The `feed_name` and string `value` fields from this attacker-controlled payload are directly concatenated with the literal `\n` character to build KV-store keys such as `'df\n'+address+'\n'+feed_name+'\ns\n'+strValue+'\n'+strMci` [1](#0-0) , and equivalently in `data_feeds.js` for querying [2](#0-1) . These keys are later split back apart with `key.split('\n')` in `getMciFromDataFeedKey` and `getValueFromDataFeedKey`, which assume the `\n`-delimited fields land in fixed positions (`m.length !== 6` check) [3](#0-2) .

### Finding Description
This mirrors the CGI report's root cause: user-controlled input is inserted into a delimiter-based serialization format without escaping or rejecting the delimiter character itself, so an attacker who controls one field can inject additional "fields" that get misinterpreted downstream. Here, the delimiter is `\n` instead of `\r\n`, and the "protocol" is the composite KV-store key rather than an HTTP header block.

Notably, ocore already treats this class of bug seriously elsewhere: `getSourceString` (used for unit/message hashing) explicitly throws if any string or object key contains the join character `STRING_JOIN_CHAR` (`\x00`) [4](#0-3) . This shows the codebase is aware that unescaped delimiters in attacker-supplied strings are dangerous — but this same discipline does not appear to be applied to the `\n`-delimited data-feed key format built in `data_feeds.js`/`main_chain.js`.

If `feed_name` (or a string `value`) supplied in a `data_feed` message payload is allowed to contain `\n`, an attacker can inject extra pseudo-fields into the key namespace, potentially:
- Causing `getValueFromDataFeedKey`'s `m.length !== 6` assumption to break (throwing, or in the worst case, being parsed with shifted indices if a variant permits variable-length splits elsewhere).
- Crafting a `feed_name` that itself embeds a fake `type`/`value`/`mci` suffix, so that queries by a *different*, legitimate `feed_name` (e.g., via prefix range scans in `dataFeedByAddressExists`, which use `key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value`) match or fail to match unexpectedly, since RocksDB key ordering/prefix logic in `data_feeds.js` (`options.gte/lt` bounds using `'\r'` as "next after `\n`") assumes `feed_name` cannot itself contain `\n`/`\r` [5](#0-4) .
- Feeding into `oscript`'s `data_feed()` function in AA formulas, which trusts `readDataFeedValue`/`dataFeedExists` results to drive AA logic (payouts, conditions) [6](#0-5) .

### Impact Explanation
If the key/prefix confusion allows an attacker-controlled data feed write to be read back as a *different* feed_name/address's value (or to desynchronize the boundary logic used in range queries), an AA relying on `data_feed()` for oracle-driven decisions (e.g., price feeds gating fund release) could be tricked into reading attacker-injected data as if it were a legitimate oracle's feed, leading to AA fund loss, or into failing to find/finding phantom values leading to node disagreement about a data feed lookup outcome across full nodes vs. light clients that reconstruct these keys differently.

### Likelihood Explanation
I was not able to fully confirm within this session whether `validation.js`'s payload validation for `data_feed` messages already rejects `\n` (or non-printable/control characters in general) inside `feed_name` or string values before they reach `main_chain.js`/`data_feeds.js`. My tool access ended before I could inspect the relevant `data_feed`-related validation block in `validation.js` (grep found 5 matches there but I could not read the specific lines). If such a check already exists (e.g., string well-formedness checks like `isObjectWellFormed` in `string_utils.js` which check for the null byte, or a dedicated printable-ASCII/length constraint on data feed keys), this analog would be mitigated and the bug would not be exploitable as described.

### Recommendation
Explicitly reject (or escape) `\n`/`\r` characters in `feed_name` and any string values used to build data-feed KV-store keys in `data_feeds.js` and `main_chain.js`'s `addDataFeeds`, mirroring the existing `STRING_JOIN_CHAR` check pattern already used in `string_utils.js`'s `getSourceString`. Additionally, harden `getValueFromDataFeedKey`/`getMciFromDataFeedKey` to fail safe (rather than silently misparse) when unexpected delimiter counts are encountered.

### Proof of Concept
Conceptual PoC (unverified against current validation.js):
```
// attacker posts a unit with a data_feed message:
{
  "app": "data_feed",
  "payload": {
    "price\ns\n999999\n00000000": "1"   // feed_name embeds fake type/value/mci suffix
  }
}
```
If `validation.js` does not reject `\n` in the payload key, `main_chain.js`'s `addDataFeeds` will write this as a KV key containing attacker-chosen extra `\n`-delimited segments, potentially colliding with or corrupting range-query boundaries used by `dataFeedByAddressExists`/`readDataFeedByAddress` for a different, legitimately-named feed.

**Caveat:** I could not verify within the available tool budget whether `validation.js` already sanitizes `feed_name`/value strings against `\n` before this point — if it does, this finding does not hold. A background Devin session with full file access to `validation.js` (data_feed payload checks) would be needed to conclusively confirm or refute this.

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}

// df:address:feed_name:type:value:strReversedMci
function getValueFromDataFeedKey(key){
	var m = key.split('\n');
	if (m.length !== 6)
		throw Error("wrong number of elements in data feed "+key);
	var type = m[3];
	var value = m[4];
	return (type === 's') ? value : decodeLexicographicToDouble(value);
}
