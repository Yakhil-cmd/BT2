### Title
XCM `ERC20Transactor` credits the full requested amount to `AssetsInHolding` without verifying actual ERC20 balance moved, unbacked by fee-on-transfer/non-standard tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens by calling the token contract's `IERC20::transfer`/equivalent and only check the boolean success return value, then credit or debit the XCM `AssetsInHolding` register with the exact `amount` that was *requested*, never verifying via balance-before/balance-after checks how many tokens the checking account or beneficiary actually received. [2](#0-1) [3](#0-2) 

### Finding Description
This is the FRAME analog of the Cooler bug: the Cooler contract assumed `transferFrom` moved exactly the requested `amount` of an ERC20 token, ignoring that some ERC20 tokens deduct a transfer fee, so tokens recorded in `Request.amount` diverge from tokens actually held by the contract.

`ERC20Transactor` has the identical violated invariant. On `withdraw_asset_with_surplus`, it calls `IERC20::transfer{to: checking_account, value: amount}` against an arbitrary `asset_id` (any contract address encoded as an `AccountKey20` XCM location) via `pallet_revive::Pallet::<T>::bare_call`, and — as long as the boolean return decodes to `true` — unconditionally creates `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))`, crediting the *requested* `amount` into the XCM holding register, not the amount actually received by the checking account: [4](#0-3) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` out of the checking account to the beneficiary and treats a `true` return as fully depositing `amount`, again without checking actual balance delta: [5](#0-4) 

Per the PR that introduced this feature, this transactor matches **any** ERC20-shaped location (`AccountKey20` interior junction), i.e. any contract deployed via `pallet-revive`, and dispatches `transfer` on it — there is no registry/allow-list check inside the transactor itself gating which token contracts can be used this way: [1](#0-0) 

If such a contract implements a transfer fee (deflationary/fee-on-transfer token, fully legal, standard-compliant ERC20 behavior — e.g. returns `true` but moves `amount - fee`), then:
- `withdraw_asset_with_surplus` credits `AssetsInHolding` with the full nominal `amount`, while the checking account actually received less. Any XCM `DepositAsset`/`InitiateReserveWithdraw`/forwarding instruction operating on that holding then treats the under-collateralized amount as fully backed.
- `deposit_asset_with_surplus` transfers `amount` from the checking account (which may itself hold less than `amount` if it was under-credited on a prior fee-on-transfer withdraw), and if that transfer also incurs a fee, the beneficiary receives less than `amount` while the executor's XCM program logic (weight, subsequent `ExchangeAsset`, cross-chain forwarding, refunds) assumes exactly `amount` was delivered.

Compounded over repeated withdraw/deposit round-trips, the `TransfersCheckingAccount`'s real ERC20 balance drains relative to the nominal amount the runtime believes it holds, breaking the accounting invariant that XCM holding-register credits are 1:1 backed by real token balance. This is directly analogous to the Cooler pattern: `n` requested vs `n-1` (or less) actually moved, with the deficit compounding on every hop.

### Impact Explanation
Impact severity depends on how far the under-collateralized `AssetsInHolding` credit propagates. In the worst case (an XCM program that reserve-transfers/bridges the ERC20 out to another chain, or mints a wrapped/foreign-asset representation elsewhere based on the reported `amount`), this can cause an **unbacked issuance** on the destination side — value is recorded/forwarded that was never actually collected from the fee-on-transfer contract, i.e., a theft/insolvency vector against the `TransfersCheckingAccount` and any downstream systems that trust the reported amount. Even limited to a same-chain hop, it silently drains the checking account's real ERC20 balance relative to what the runtime's XCM accounting assumes, eventually causing deposit failures (checking account insufficient balance) or, depending on `Matcher`/downstream logic, allowing an attacker to extract more value than they contributed.

### Likelihood Explanation
No privileged role is required: `pallet-revive` allows any signed account to deploy an arbitrary ERC20 contract, and per the PRDoc, `ERC20Transactor` matches contract addresses generically without requiring separate registration in the transactor itself. Any signed user can then submit a `pallet_xcm::execute` extrinsic containing `WithdrawAsset`/`DepositAsset` instructions referencing that self-deployed fee-on-transfer contract as the asset location. Whether this is exploitable end-to-end depends on the specific `Matcher: MatchesFungibles<H160, u128>` configuration wired into a concrete runtime (e.g. Asset Hub Westend), which may impose an additional allow-list before matching — this was not fully verifiable from the indexed snippets available, since the runtime-level `Matcher`/`AccountIdConverter` instantiation for `ERC20Transactor` was not located in this pass. This uncertainty should be resolved by inspecting the concrete `xcm_config.rs` wiring of `ERC20Transactor` in `asset-hub-westend-runtime` (and any other runtimes using it) before treating this as conclusively exploitable in a live deployed configuration.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the ERC20 balance of the relevant account (checking account or beneficiary) immediately before and after the `bare_call` to `transfer`, and use the observed balance delta — not the nominal `amount` — when constructing `AssetsInHolding::new_from_fungible_credit` (withdraw) or when deciding how much was successfully deposited. If the observed delta is less than requested, either fail the operation (`XcmError::FailedToTransactAsset`) or credit only the actual delta, consistent with how FRAME's own `fungible`/`fungibles::transfer` implementations return the *actual* amount moved rather than assuming success implies exact transfer.

### Proof of Concept
Not executed against a live network. A concrete Rust/FRAME integration reproduction would require: (1) a `pallet-revive`-enabled runtime with `ERC20Transactor` wired into its `XcmConfig` (e.g. Asset Hub Westend), (2) deploying a minimal ERC20 contract compiled to PolkaVM bytecode via `pallet_revive::Pallet::instantiate_with_code` that implements a fee-on-transfer `_update`/`transfer` (returns `true` but moves less than `value`), (3) a `pallet_xcm::execute` call with a `WithdrawAsset`/`DepositAsset` program referencing that contract's address as an `AccountKey20` asset location, and (4) asserting `TransfersCheckingAccount`'s real ERC20 balance after the round-trip is less than the `AssetsInHolding`/ledger amount the XCM program believed was moved. This reproduction was not built or run in this pass; the finding is based on static code-path analysis of the guard checks (`is_success` boolean check only, no balance delta) in `erc20_transactor.rs` and the PRDoc describing unrestricted contract-address matching. The runtime-level `Matcher` configuration that would confirm/deny reachability by an unprivileged signed user was not located and remains unverified.
