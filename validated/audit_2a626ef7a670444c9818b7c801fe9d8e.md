This confirms the binding break: `WebhooksController#verify_signature` authenticates the webhook against the GitHub App config selected by `repository_owner` (falling back to `organization.login` when `repository.owner.login` is absent) <cite repo="Jortegata/shipit-engine--025" path="app/controllers/shipit/webhooks_controller.rb" start="24,59" end="30,62" />, while the actual write target used by every handler is `payload.dig('repository', 'full_name')`, an independent field never covered by that authentication decision <cite repo="Jortegata/shipit-engine--025" path="app/models/shipit/webhooks/handlers/handler.rb" start="32,36" end="34,38" />. Additionally, `verify_webhook_signature` treats an org with no configured `webhook_secret` as automatically verified (`return true unless webhook_secret`) <cite repo="Jortegata/shipit-engine--025" path="lib/shipit/github_app.rb" start="76,77" end="76,77" />.

### Title
Webhook authenticates the organization but writes to a `repository.full_name` never bound to that signature check - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, which is derived from `params.dig('repository','owner','login') || params.dig('organization','login')` <cite repo="Jortegata/shipit-engine--025" path="app/controllers/shipit/webhooks_controller.rb" start="59,62" end="61,62" />. However, none of the event handlers use `repository.owner.login` or `organization.login` to decide which `Stack`/`Repository` to mutate — they all resolve the target strictly from `payload.dig('repository', 'full_name')` via `Handler#repository_name` [1](#0-0) . These two fields are never cryptographically bound together by the signature check: the HMAC only proves that *some* configured organization's secret produced a valid signature for the raw body, not that the authenticated organization is the owner of the repository being acted on.

### Finding Description
The binding that should hold is: `organization authenticated == organization owning repository.full_name acted on`. In `verify_signature`, `Shipit.github(organization: repository_owner)` looks up per-organization config (including `webhook_secret`) purely from the `owner.login`/`organization.login` fields <cite repo="Jortegata/shipit-engine--025" path="app/controllers/shipit/webhooks_controller.rb" start="24,26" end="29,29" />. Because GitHub Apps/webhooks in Shipit are configured per top-level org (`Shipit.github_teams`/per-org `webhook_secret` in `config/secrets.yml`) <cite repo="Jortegata/shipit-engine--025" path="lib/shipit.rb" start="62,63" end="63,63" />, any organization onboarded onto the same Shipit instance can craft a JSON payload where:
- `organization.login` (or `repository.owner.login`) is set to their own, legitimately-configured org name (so the HMAC computed with their own real `webhook_secret` passes `verify_webhook_signature`), and
- `repository.full_name` is set to `"other-org/other-repo"`, a repository belonging to a *different* organization tracked by the same Shipit instance.

Because `Handler#repository_name` only reads `repository.full_name` and never cross-checks it against the authenticated `repository_owner`, `create` will dispatch this payload to handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, etc.) which will locate the `Stack` for `other-org/other-repo` via `Repository.from_github_repo_name` and act on it — e.g., `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` <cite repo="Jortegata/shipit-engine--025" path="app/models/shipit/webhooks/handlers/push_handler.rb" start="12,16" end="12,16" /> for a repository the attacker's org never controls.

This is compounded by `verify_webhook_signature` short-circuiting to `true` when `webhook_secret` is blank for the resolved org <cite repo="Jortegata/shipit-engine--025" path="lib/shipit/github_app.rb" start="76,77" end="76,77" /> — if any onboarded org is configured without a `webhook_secret` (a supported, documented configuration, see `template.rb`/`secrets.*.yml` samples showing `webhook_secret:` blank) [2](#0-1) , an attacker only needs to pick that org's name for `organization.login`/`repository.owner.login` to bypass signature verification entirely while targeting any other repository's `full_name`.

### Impact Explanation
This lets an unprivileged external actor (anyone who can reach the public `/webhooks` endpoint, no Shipit session or API token required) trigger state-changing webhook events — `push` (queues `GithubSyncJob`/`sync_github`), `status`, `check_suite` (`RefreshCheckRunsJob`), `pull_request` (opens/closes/labels review stacks) — against a `Stack` belonging to a different, unrelated repository than the one whose credentials authenticated the request. This is a cross-repository write / unauthorized state-modification primitive, matching the "High" bucket (escalation across the repository authorization boundary) and, depending on which handler's side effects are abused (e.g., forcing a resync/rollback trigger, spoofing PR/label state that downstream automation trusts), can rise to an unauthorized deploy/rollback trigger for a repo the attacker does not control.

### Likelihood Explanation
Requires only that the target Shipit instance is multi-tenant (serves more than one GitHub organization), which is an explicitly supported and documented deployment pattern (`Shipit.github(organization:)`, per-org `webhook_secret` config keys) <cite repo="Jortegata/shipit-engine--025" path="lib/shipit.rb" start="62,63" end="63,63" />. No secret material or privileged access is needed for the org the attacker already legitimately owns/administers on that shared instance; they merely need to author a payload with mismatched `organization.login` vs `repository.full_name`, which the controller layer does nothing to prevent.

### Recommendation
After signature verification, enforce that `repository_owner` (or `organization.login`) actually matches the owner segment of `payload.dig('repository', 'full_name')` before dispatching to handlers, rejecting (422) any payload where they diverge. Alternatively, resolve the target `Repository`/`Stack` first and require its associated GitHub organization to equal the organization whose `webhook_secret` validated the signature, closing the gap between the authenticated organization and the repository actually written to.

### Proof of Concept
1. Attacker controls (or is a legitimate member configuring) organization `attacker-org` on a shared Shipit instance that also tracks `victim-org/victim-repo`.
2. Attacker computes a valid `X-Hub-Signature` for a JSON body using `attacker-org`'s known `webhook_secret` (or relies on `attacker-org` having no `webhook_secret` configured, in which case `verify_webhook_signature` returns `true` unconditionally).
3. Attacker sets the JSON body's `organization.login` to `"attacker-org"` and `repository.full_name` to `"victim-org/victim-repo"`, and sends it as a `push` event with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `attacker-org`'s webhook config, and the signature check passes <cite repo="Jortegata/shipit-engine--025" path="app/controllers/shipit/webhooks_controller.rb" start="24,30" end="29,30" />.
5. `create` dispatches to `PushHandler`, which resolves the target stack from `repository.full_name = "victim-org/victim-repo"` [1](#0-0)  and calls `stack.sync_github` on it, even though the signature only proved knowledge of `attacker-org`'s secret, not any relationship to `victim-org`.
