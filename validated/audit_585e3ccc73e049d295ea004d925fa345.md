### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository filter, unlike every other webhook handler in this engine which resolves the owning `Repository` via `params.repository.full_name` before acting. Any commit-status webhook whose signature verifies for *some* GitHub organization/repo known to Shipit can therefore write a status onto a `Commit` row belonging to a completely different stack/repository that happens to share the same SHA, flipping `blocked?`/`deployable?` for that unrelated stack.

### Finding Description
The broken binding, stated explicitly, is:

`status_payload.repository.full_name == commit.stack.repository.full_name`

This equality is enforced in every other handler (e.g. `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`, which resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before mutating anything), but it is never checked in `StatusHandler`: [1](#0-0) 

The handler's `params` schema doesn't even `requires :repository`, and `process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This matches **every** `Commit` record across **every** `Stack`/repository in the Shipit instance that shares that SHA — not just commits belonging to the repository that produced the webhook.

`create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` persists the status against that commit's `stack_id` [2](#0-1) [3](#0-2) . If the victim stack configures `blocking_statuses` (e.g. requiring `ci/e2e`), then `Commit#blocked?` re-evaluates using `stack.commits.reachable...any?(&:blocking?)` [4](#0-3) , and `deployable?` is directly gated by `blocked?` and `success?` [5](#0-4) . A forged `failure` status for `ci/e2e` thus can flip `blocked?`/`deployable?` for a stack the attacker never authenticated against.

`verify_signature` in `WebhooksController` only checks that the payload's signature matches the secret for `repository_owner` (the GitHub org named in the attacker's own payload) [6](#0-5) . It validates that the request came from *a* legitimate GitHub organization/app installation that Shipit trusts — it does not, and cannot, validate that the `sha` referenced belongs to the repository that signed the request, because `StatusHandler` never consults `params.repository` at all. Since GitHub App webhook secrets are typically shared across all repositories under one org/installation, any repository under that org that legitimately triggers a `status` event (including one an unprivileged contributor can trigger by pushing a commit/PR that gets a CI status) can produce a validly-signed payload for a SHA that collides with a commit tracked by a *different* stack in the same Shipit instance (e.g., a shared vendored/cherry-picked commit, a monorepo split into multiple Shipit stacks, or a forked stack pointing at the same upstream history).

### Impact Explanation
A payload signed for one repository can write a `Status` record onto a `Commit` belonging to a different repository's `Stack`, altering that victim stack's `blocked?`/`deployable?` computation and hence its continuous-delivery gate (`schedule_continuous_delivery`, `ContinuousDeliveryJob`) and merge scheduling (`stack.schedule_merges`) [7](#0-6) [8](#0-7) . This is a cross-tenant state mutation (one repository's authenticated payload writing another repository's records), matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any commit SHA shared between stacks and is not rate-limited beyond normal webhook delivery.

### Likelihood Explanation
Exploitability depends on SHA collision between the attacker's authenticated repository and the victim stack's commit history — this is not a hash collision requirement but a realistic operational scenario (shared/forked repositories, monorepo-derived stacks, mirrored histories, or vendored commits imported into multiple stacks under the same GitHub org/installation). The attacker needs only to be able to trigger a legitimately-signed `status` webhook (e.g., by having CI configured on any repo under an org that shares the webhook secret with the victim's org/installation) — no Shipit session, API token, or elevated GitHub role is required. Given the stated fast-validation invariant, exploitation reduces to reusing/re-pushing a commit SHA that's shared across two stacks.

### Recommendation
Require and validate `repository.full_name` in `StatusHandler#params` (mirroring the pull-request handlers), then scope the commit lookup: `Repository.from_github_repo_name(params.repository.full_name)&.stacks&.commits&.where(sha: params.sha)` instead of a bare `Commit.where(sha: params.sha)`. Apply the same repository-scoping fix to any other handler doing sha-only lookups (e.g., check-run/check-suite handlers) to enforce the invariant that a status only affects the repository that authenticated it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "a status for repo A cannot alter deployability for stack of repo B sharing the SHA" do
  sha = "deadbeef" * 5

  stack_a = shipit_stacks(:shipit)                    # repo: "shopify/shipit-engine"
  stack_b = create_stack(repository: create(:repository, name: "other-repo", owner: "shopify"))
  stack_b.update!(deploy_spec_overrides: { "ci" => { "blocking" => ["ci/e2e"] } }) # blocking_statuses = ["ci/e2e"]

  commit_a = create_commit(stack: stack_a, sha: sha)
  commit_b = create_commit(stack: stack_b, sha: sha)

  before = commit_b.blocked?   # e.g. false, no blocking statuses recorded yet

  # Payload signed for repo A's org/installation, referencing the shared SHA:
  payload = {
    'sha' => sha,
    'state' => 'failure',
    'context' => 'ci/e2e',
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => 'shopify' } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  after = commit_b.reload.blocked?
  refute_equal before, after   # FAILS today: repo A's payload flipped repo B's stack state
end
```
This demonstrates that `StatusHandler#process`'s repository-unscoped `Commit.where(sha: ...)` lookup lets a payload authenticated for one repository mutate `blocked?`/`deployable?` state for an unrelated stack, confirming the vulnerability.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
