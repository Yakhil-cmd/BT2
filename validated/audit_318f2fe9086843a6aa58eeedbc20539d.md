### Title
Webhook signature verification is scoped to an attacker-chosen organization while `StatusHandler` writes state for any commit SHA in the installation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the shipit-engine analog of the GroupBuy priority-queue bug: a security invariant ("the entity that authenticated == the entity being written") is violated because two different code paths derive their authorization/target identity from two independently-controllable pieces of the same unauthenticated JSON body. In `WebhooksController`, the *organization used to select and verify the HMAC signature* is taken from `repository.owner.login` (or `organization.login`), but the *record actually mutated* by `Shipit::Webhooks::Handlers::StatusHandler` is selected purely by `sha`, with no relationship at all to the repository/organization that was authenticated.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using an attacker-controlled field of the raw JSON body: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` deliberately treats an organization with no configured `webhook_secret` as authenticated for *any* payload/signature combination: [3](#0-2) 

This is a documented, supported configuration state (`webhook_secret: # nil`), used across the codebase's own multi-org example config: [4](#0-3) 

Meanwhile, `StatusHandler#process` — unlike `PushHandler`, which scopes to `stacks` derived from `repository.full_name` — does not use `repository_name`/`stacks` at all. It matches purely on `sha` across the entire `Commit` table of the whole Shipit installation: [5](#0-4) [6](#0-5) 

The equality that should hold is: `organization authenticated by verify_signature == organization/repository whose commit is mutated`. It does not hold, because:
1. `repository_owner` (used only for picking the HMAC secret) is read from `repository.owner.login`, an attacker-supplied JSON field.
2. `StatusHandler` ignores `repository` entirely and updates `Status` records for whatever `Commit` rows match `sha`, regardless of which stack/repository/organization they belong to.

### Impact Explanation
In any multi-organization Shipit deployment where at least one configured GitHub organization has no `webhook_secret` set (a supported, documented configuration), an unauthenticated attacker can:
1. Send a POST to `/webhooks` with `X-Github-Event: status`, and a JSON body whose `repository.owner.login`/`organization.login` names the unsecured organization.
2. `verify_webhook_signature` returns `true` unconditionally for that organization (no secret to check against), so the request passes signature verification with no knowledge of any secret.
3. `StatusHandler.process` looks up `Commit.where(sha: params.sha)` with an attacker-supplied `sha` — a commit belonging to a completely different, secured organization's repository/stack — and writes an arbitrary `state`/`context`/`description` `Status` for it via `commit.create_status_from_github!`.

Because Shipit's merge queue and deploy gating use `Status` records to determine `all_status_checks_passed?`/mergeability, this can be used to forge a passing CI status on a commit in a repository the attacker has no write access to, enabling an unauthorized merge or deploy — meeting the "unauthorized deploy, rollback or merge" Critical-impact bar.

### Likelihood Explanation
Requires only: (a) knowledge that the target Shipit instance hosts multiple GitHub organizations, (b) one configured organization lacking a `webhook_secret` (a state the project's own setup docs present as normal/acceptable), and (c) the target commit `sha` of a real commit tracked by another stack (obtainable from GitHub, which is typically public or at least externally observable). No session, API token, or repository write access is needed — matching the "unprivileged attacker" threat model in scope.

### Recommendation
Bind webhook authentication and payload routing to the *same* identity: derive the authenticating organization from the same repository/organization value that handlers use to select records, and have handlers (in particular `StatusHandler`) validate that the `Commit`'s owning `Stack`/`Repository` matches the `repository.full_name` (and therefore the organization) that was actually verified in `verify_signature`, rather than matching globally by `sha` alone. Additionally, consider disallowing organizations with unset `webhook_secret` from authenticating events for repositories that belong to other organizations, or require a `webhook_secret` per organization.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgWithSecret` (has `webhook_secret` set, hosts the victim stack/repo) and `OrgNoSecret` (no `webhook_secret` configured, e.g. `# nil`), as shown in `docs/setup.md` — both installed on the same Shipit instance.
2. Attacker finds a real commit SHA belonging to a stack under `OrgWithSecret/victim-repo` (e.g. from public GitHub history).
3. Attacker sends:
```
POST /webhooks
X-Github-Event: status
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "required-ci-context",
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgNoSecret/whatever" }
}
```
(No `X-Hub-Signature` header needed, or any arbitrary value.)
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgNoSecret")`, whose `verify_webhook_signature` returns `true` immediately since `webhook_secret` is blank — request is accepted.
5. `Shipit::Webhooks::Handlers::StatusHandler.call(params)` runs `Commit.where(sha: params.sha)` and creates a `success` `Status` for the victim commit belonging to `OrgWithSecret`'s stack, even though the attacker never authenticated against `OrgWithSecret`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
