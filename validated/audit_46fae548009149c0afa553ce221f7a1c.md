### Title
Cross-org spoofing via divergent `repository.owner.login`/`organization.login` fields lets an attacker's own webhook secret authenticate a privileged org's team write - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the request against using `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. `MembershipHandler#find_or_create_team!` instead trusts `params.organization.login` when creating/tagging a `Team`. Because the raw JSON body is attacker-controlled and `ExplicitParameters` only validates the presence/shape of required keys (it does not forbid extra top-level keys), an attacker can inject a `repository.owner.login` pointing at an org they control (and whose `webhook_secret` they know) while setting `organization.login` to a victim org name, causing the victim org's name to be written into `Team#organization` under signature verification performed with the attacker's own secret.

### Finding Description
The broken binding: `organization_that_verified_signature == organization_written_to_Team#organization` is expected to hold, i.e. `Shipit.github(organization: repository_owner)` (the org whose `webhook_secret` validated `X-Hub-Signature`) must equal `params.organization.login` (the value persisted via `team.organization = params.organization.login`).

Code path:
- `WebhooksController#repository_owner` [1](#0-0)  reads `repository.owner.login` first, falling back to `organization.login`.
- `verify_signature` uses that value to pick the app/secret: `Shipit.github(organization: repository_owner)` then calls `verify_webhook_signature` [2](#0-1) .
- `Shipit.github` resolves per-organization config from `secrets.github` keyed by org name when multiple orgs are configured (`TOP_LEVEL_GH_KEYS` are the single-org marker keys) [3](#0-2) .
- Once verified, `create` parses the same raw body and dispatches to handlers [4](#0-3) .
- `MembershipHandler` requires `organization.login` and `team.id`/`team.name`/etc, but does not require/forbid a `repository` key [5](#0-4) , and on team creation writes `team.organization = params.organization.login` [6](#0-5) .
- `Handler#initialize` parses the payload via `ExplicitParameters::Parameters.define(&block).parse!(payload)` [7](#0-6) , which only validates the declared required fields; it does not strip or reject unrelated top-level keys such as an injected `repository` object.

Attacker request: a real GitHub `membership` event payload normally has no `repository` key at all. The attacker crafts a raw JSON body containing:
- `"organization": {"login": "victim-org"}` (target to spoof)
- `"repository": {"owner": {"login": "attacker-org"}}` (injected, extra key, used only by the controller's `repository_owner`)
- `"team": {...}`, `"member": {...}`, `"action": "added"`

and signs it with `attacker-org`'s own `webhook_secret` (which the attacker knows because it is their own onboarded GitHub App/org, per the "unprivileged attacker" definition allowing them to own/control a repository/org and configure its webhook). `repository_owner` resolves to `attacker-org`, `verify_signature` validates successfully against the attacker's own secret, and the request passes. `MembershipHandler` then creates `Team.find_or_create_by!(github_id: ...) { team.organization = "victim-org" }`, binding the spoofed victim org name to a new `Team` record despite the request never being authenticated by `victim-org`'s secret.

Existing guards do not catch this: `drop_unhandled_event` only checks the event is registered; `ExplicitParameters` schema for `MembershipHandler` requires `organization.login` but places no constraint on the presence/absence of a `repository` key or on cross-field consistency between `repository.owner.login` and `organization.login`; there is no code anywhere that asserts `repository_owner == organization.login` before trusting either.

### Impact Explanation
A `Shipit::Team` record can be created and tagged with an arbitrary organization name (`Team#organization`) despite being authenticated only by an org the attacker fully controls. If `Team#organization` is used elsewhere for authorization/oauth-team scoping (e.g., `Shipit.github_teams`, team-to-org membership checks), this is a path to inject a team record falsely associated with a privileged org, which could later be leveraged for escalation once that team's membership is populated (`team.add_member(member)` in the same handler adds the attacker's own GitHub user as a member of the newly created, victim-org-tagged team). This is repeatable per attacker-chosen `team.id`/org combination and only requires the deployment to have more than one organization configured in `Shipit.github` (multi-tenant setups), which is an explicitly supported configuration path (`TOP_LEVEL_GH_KEYS`, `github_app_config`).

### Likelihood Explanation
Requires: (1) the Shipit deployment configured with multiple orgs under `secrets.github` (a supported, documented multi-org mode), (2) the attacker owning/operating at least one of the onboarded orgs (and thus knowing its own `webhook_secret`) — consistent with the "unprivileged attacker who can emit webhooks from a repository/org they own" threat model, (3) no live GitHub interaction needed — the attacker sends a crafted HTTP POST to `/webhooks` directly with a body they fully control and sign themselves. This is fully attacker-cost-free beyond needing to be onboarded as one tenant among several, and is repeatable against any victim org name known to the attacker.

### Recommendation
In `WebhooksController#repository_owner`, do not silently prefer `repository.owner.login`; require the value used to select the verifying app/secret to be internally consistent with any `organization.login` present in the same payload (reject the request with 422 if both are present and differ). More robustly, `MembershipHandler` (and any other org-event handler that writes to a `Team`/model based on `params.organization.login`) should re-derive/assert that the organization used to authenticate the signature is exactly the organization value being persisted, rather than trusting `params.organization.login` independently after verification. Additionally, tighten the `ExplicitParameters` schema for `MembershipHandler` to forbid unexpected top-level keys such as `repository` where the real GitHub payload for `membership` events never includes one.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (extension)
test "membership webhook cannot bind an org authenticated by another org's secret" do
  # Configure two orgs, org_a (victim) and org_b (attacker), each with distinct webhook_secret
  with_rails_credentials(github: {
    org_a: { webhook_secret: 'secret_a', app_id: 1, installation_id: 1, private_key: TEST_PRIVATE_KEY, oauth: {}, domain: 'github.com' },
    org_b: { webhook_secret: 'secret_b', app_id: 2, installation_id: 2, private_key: TEST_PRIVATE_KEY, oauth: {}, domain: 'github.com' },
  }) do
    payload = {
      action: 'added',
      team: { id: 4242, name: 'core', slug: 'core', url: 'https://api.github.com/teams/4242' },
      organization: { login: 'org_a' }, # victim org being spoofed
      repository: { owner: { login: 'org_b' } }, # injected key, attacker-controlled org
      member: { login: 'attacker' },
    }.to_json

    signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'secret_b', payload) # signed with attacker's own secret

    post shipit.github_webhooks_path,
      params: payload,
      headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }

    assert_response :ok

    team = Shipit::Team.find_by(github_id: 4242)
    refute_nil team
    # BROKEN BINDING: team.organization ends up as 'org_a' though verification used org_b's secret
    assert_equal 'org_a', team.organization
  end
end
```
This demonstrates the equality `verifying_org ('org_b') != Team#organization ('org_a')`, confirming the binding is broken.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
