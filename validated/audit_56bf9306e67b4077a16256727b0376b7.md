### Title
Webhook signature verification authenticates the GitHub organization from `repository.owner.login`, but handlers act on a different, unverified field (`sha` / `repository.full_name`), allowing cross-repository status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC `webhook_secret`) to validate against using `repository_owner`, which is read from the attacker-controlled JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes, the handlers dispatched by `Shipit::Webhooks.for_event(event)` act on *other* fields of the same body — most notably `StatusHandler`, which updates commit statuses using nothing but `Commit.where(sha: params.sha)`, with no repository/organization scoping at all. The signature therefore authenticates "which organization's secret matches" but never binds that organization to the repository or commit actually written to.

**The broken binding as an equality:**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository/commit actually mutated by the handler (repository.full_name for most handlers, or nothing at all for StatusHandler, which uses only sha)`.

This equality is never enforced anywhere in the controller or in `StatusHandler`.

**Attack scenario (multi-org Shipit deployment, which the engine explicitly supports per `docs/setup.md`):**
1. Attacker administers their own GitHub organization "attacker-org", which has been configured (by themselves, as an org admin) as one of the multiple organizations in Shipit's `config/secrets.yml`. They therefore know the `webhook_secret` for `attacker-org`.
2. Attacker crafts a `status` event payload where `repository.owner.login` (or `organization.login`) = `"attacker-org"` (so `verify_signature` resolves and validates against the secret they know), but `sha` is set to the SHA of a commit belonging to a *victim* stack tracked by a completely different, unrelated organization on the same Shipit instance (SHAs are public, discoverable via GitHub's public API/commit pages or Shipit's own commit/task pages).
3. Attacker computes `sha1=HMAC(attacker-org secret, raw_body)` and POSTs it to `/github/webhooks` (or the mounted webhook route) with `X-Github-Event: status`.
4. `verify_signature` passes because the org named in the body genuinely matches the secret used. `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — writing an attacker-controlled status (e.g. `state: "success"`, arbitrary `context`) onto the victim's commit, with no verification that "attacker-org" has anything to do with that repository.

### Impact Explanation
Commit statuses gate deployability checks in Shipit (`deployable_status` events, required-status logic). By forging a `success` status on a victim commit that the attacker does not own or control, an unprivileged party (someone who merely administers a different, unrelated org configured on the same Shipit instance) can make a commit appear deployable when it isn't, or otherwise write fabricated CI signal onto a repository they have no authorization over. This crosses the "cross-repository writes" / "unauthorized deploy" boundary called out as Critical impact, because the write path (`StatusHandler`) performs no per-repository authorization check at all — it is bound only to a `sha`, not to any authenticated organization or repository.

### Likelihood Explanation
Exploitability requires only that the attacker control (as a legitimate admin) one organization onboarded to the same multi-tenant Shipit instance — a realistic deployment topology explicitly documented in `docs/setup.md`'s "Using Multiple Github Applications" section. No token, no session, no repository write access to the victim repo is required; only knowledge of a target commit SHA, which is routinely public.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, enforce that the organization used to select the `GitHubApp`/secret matches the actual owner of the `repository.full_name` (or equivalent) that each handler will act upon. In `StatusHandler` (and any handler that does not call the shared `Handler#stacks`/`repository_name` scoping), add explicit repository scoping — e.g. join through the repository/stack that owns `params.sha` and confirm its owning organization equals `repository_owner` verified by the controller — before mutating any `Commit`.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org schema).
2. As the admin of `attacker-org`, obtain its `webhook_secret`.
3. Find a public commit SHA belonging to a stack owned by `victim-org` (e.g. from GitHub's public commits API).
4. Build a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
5. Compute `X-Hub-Signature: sha1=` HMAC-SHA1 of the raw body using `attacker-org`'s `webhook_secret`.
6. POST to the Shipit webhook endpoint with `X-Github-Event: status`.
7. Observe `verify_signature` passes (org `attacker-org`'s secret matches), and `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) creates a forged `success` status on the victim's commit, since `Commit.where(sha: params.sha)` performs no ownership check.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
