### Title
`StatusHandler#process` mutates commits across tenants without repository/organization scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` never uses the inherited `Handler#stacks` repository-scoping helper and its `params do` block does not declare `requires :repository`, so `process` looks up commits purely by `sha` across the entire `Commit` table. Any org registered in `Shipit.github` config can therefore sign a `status` webhook with its own legitimate `webhook_secret` and mutate the commit-status state of a commit belonging to a completely different org's stack, as long as the `sha` value collides with a commit tracked anywhere on the instance.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`organization that produced a valid HMAC signature == organization owning the stack/repository whose Commit row gets mutated`.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks the GitHub App/org to verify against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (line 59-62). This value is fully attacker-controlled in the JSON body — it is only used to *select which registered org's `webhook_secret` to HMAC-verify with*, not to scope what gets mutated.
2. `Shipit::Webhooks::Handlers::Handler` defines a repository-scoping helper, `stacks`, based on `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and sibling handlers like `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), `OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, and `ClosedHandler` all resolve a `repository` from `params.repository.full_name` (each declares `requires :repository { requires :full_name, String }` in their `params` block) before touching any `Stack`/`ReviewStack`.
3. `StatusHandler`'s own `params` block (`app/models/shipit/webhooks/handlers/status_handler.rb:7-18`) requires only `sha`, `state`, and optional fields (`description`, `target_url`, `context`, `created_at`, `branches`) — there is no `requires :repository` at all.
4. `StatusHandler#process` (lines 20-24) runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-tenant lookup by `sha` with zero repository/stack scoping.
5. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) unconditionally calls `statuses.replicate_from_github!(stack_id, github_status)`, creating a `Status` row and firing `commit_status`/`deployable_status` hooks and `stack.schedule_merges` based on the state transition (`app/models/shipit/commit.rb:366-386`), i.e., it directly affects the deployability judgement of whatever stack owns that commit.

Exploit flow: an attacker who legitimately controls Org A (registered in Shipit with a real `webhook_secret`) sends `POST /webhooks` with header `X-Github-Event: status` and a body such as `{"sha": "<known-sha-of-victim-org-B-commit>", "state": "success", "organization": {"login": "OrgA"}}`, signed with Org A's `webhook_secret`. `verify_signature` succeeds because it only checks that OrgA's key matches OrgA's signature — it never checks that the `sha` actually belongs to a repository owned by OrgA. `StatusHandler` then finds and mutates any `Commit` row across the whole instance whose `sha` matches, including ones belonging to Org B's stack.

Existing guards do not prevent this: `verify_signature` authenticates the sender's identity/org, not the object being mutated; `ExplicitParameters` only validates types/presence of declared fields (and `repository` isn't declared for this handler); `Handler#stacks` exists precisely to enforce repository scoping but `StatusHandler` doesn't call it.

### Impact Explanation
An attacker in control of any org registered on the Shipit instance can forge a `success`/`failure`/`pending` `Status` for a commit belonging to an unrelated org's `Stack`, provided they know a tracked `sha`. Since `Status` updates drive `deployable?`/CI-gating and `schedule_merges`/continuous-delivery scheduling (`app/models/shipit/commit.rb:281-287`, `366-386`), this can unblock or block deploys for repositories the attacker does not own — this is a payload for one repository mutating another's stack/commit, matching the "Critical" category explicitly called out in the rules. It is fully repeatable for any known `sha` and requires no elevated Shipit privilege beyond owning one legitimately-registered org's webhook secret.

### Likelihood Explanation
Preconditions: Shipit must be configured (as documented) to serve multiple GitHub orgs/apps sharing one instance (a supported, common multi-tenant setup per `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, which show multiple orgs configured side by side). The attacker needs their own legitimately-issued `webhook_secret` (trivial if they can register any org/app on the shared instance) and a `sha` value tracked by another org's stack — commit SHAs are routinely public (GitHub UI, PR pages, CI logs), so this is a low-cost, highly feasible, and repeatable attack against any multi-tenant Shipit deployment.

### Recommendation
Require `repository` (or `organization`) in `StatusHandler`'s `params` block and scope the commit lookup through the inherited `stacks` helper, e.g. `commit.stack_id.in?(stacks.pluck(:id))`, or otherwise resolve `Repository.from_github_repo_name(params.repository.full_name)` and restrict `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))`, exactly as the sibling handlers already do.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, not currently covering this):
```ruby
test "status payload without repository can mutate a commit belonging to a different org's stack" do
  victim_stack = shipit_stacks(:cyclimse) # belongs to org "cyclimse"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)

  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "organization" => { "login" => "shopify" } # attacker's own registered org
  }

  # left-hand side: org that signs == "shopify"
  # right-hand side: org owning mutated commit's stack == "cyclimse"
  assert_not_equal "shopify", victim_stack.repository.owner

  assert_difference "victim_commit.statuses.count", 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
This demonstrates the two sides of the equality diverge (signing org ≠ mutated-commit's owning org) while the mutation still succeeds, confirming the structural bypass.
