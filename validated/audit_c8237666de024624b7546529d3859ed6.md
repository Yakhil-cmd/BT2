### Title
Webhook signature is verified against `repository.owner.login`, but event handlers act on the unauthenticated `repository.full_name` field, letting an org that owns one repo forge sync/state events for a different tracked repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an incoming webhook with, based on `repository.owner.login` from the JSON body. However, once the signature check passes, every event `Handler` (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolves the target `Repository`/`Stack` using a *different* field of the same untrusted body: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Nothing cryptographically binds `owner.login` to `full_name` - the HMAC covers the raw JSON body as a whole, but the verifier only reads one sub-field to pick the secret, while the business logic reads another sub-field to pick the target. This breaks the intended binding: "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

In a multi-organization Shipit deployment (`config/secrets.development.shopify.yml` shows the `github: { org1: {...webhook_secret...}, org2: {...} }` schema), each organization has its own `webhook_secret`. `verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for whichever organization `repository.owner.login` names - it never checks that this org actually owns the repository the payload claims to describe.

Once verification passes, `Handler#stacks` resolves the target repository from a completely different JSON path:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [2](#0-1) 

`PushHandler#process` then acts on whatever stacks match, calling `stack.sync_github(expected_head_sha: params.after)` for every not-archived stack on the matching branch: [3](#0-2) 

Because the two fields (`repository.owner.login` used for auth, `repository.full_name` used for target resolution) are read independently from the same attacker-controlled JSON body, and are not cross-validated anywhere in the request path, a user who legitimately administers a repository/org tracked by Shipit (and therefore knows or controls that org's `webhook_secret`, e.g. via the GitHub App webhook settings on their own installation) can craft a POST directly to `/webhooks` (bypassing GitHub) with:
- `repository.owner.login` = their own organization (so the HMAC validates with their own known/controlled secret)
- `repository.full_name` = `"victim-org/victim-repo"` (some other repository/stack tracked by the same Shipit instance under a different `github` config entry)

The push handler will then resolve `Repository.from_github_repo_name("victim-org/victim-repo")` and trigger `sync_github(expected_head_sha: ...)` for that stack — an operation that updates the stack's known/deployable commit state and can flow into automatic/continuous deployment (`continuous_deployment` schedules a deploy of the newly-synced commit) without ever having a valid signature from `victim-org`'s own webhook secret.

### Impact Explanation
This crosses the "unauthorized deploy"/"cross-repository writes" boundary called out in scope: an attacker who is only authorized (holds a valid webhook secret) for repository/org A can inject state-changing webhook events (push/status/check_suite/membership) against a stack that belongs to a completely different, unrelated repository/org B, because the signing/authorization check and the target-selection check are decoupled onto different, independently-controlled fields of the same unauthenticated JSON body. Depending on `continuous_deployment` settings on the target stack, this can result in an unauthorized deploy being triggered for `expected_head_sha` values the attacker chooses, on a stack the attacker has no legitimate access to.

### Likelihood Explanation
Requires the attacker to control (or know) at least one organization's `webhook_secret` configured in this Shipit instance — i.e., be a legitimate admin of any one tracked GitHub org/repository — and to know the `owner/name` of another tracked repository (repository names/stacks are visible in Shipit's own UI/API to any Shipit user, per `Stack.from_param!` and the public stacks listing). No GitHub App private key, `api_clients_secret`, or session is needed; only a valid per-organization webhook secret for one of potentially many configured organizations. This is realistic in the documented multi-org deployment model shown in `config/secrets.development.shopify.yml`.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, derive the organization used to select the `webhook_secret` from the same field used to resolve the target repository (`repository.full_name`, splitting on `/`), or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before any handler dispatch, rejecting mismatched payloads with 422.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` (webhook_secret `S1`, known to the attacker as its GitHub App/webhook admin) and `victim-org` (webhook_secret `S2`, unknown to attacker), each with at least one repository/stack tracked.
2. Attacker crafts a push payload body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>` using `S1` (their own known secret) and POSTs directly to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates successfully against `S1`. [4](#0-3) 
5. `PushHandler` is dispatched with the same payload; `repository_name` reads `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, resolving `victim-org`'s stack and invoking `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`. [2](#0-1) [3](#0-2)
