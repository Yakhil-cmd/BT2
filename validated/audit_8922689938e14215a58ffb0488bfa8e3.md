### Title
Hookify PreToolUse/PostToolUse rule engine fails open (silently allows) on rule-file parse or evaluation errors - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The `hookify` plugin implements a user-configurable security-guard hook (`PreToolUse`) meant to block dangerous `Bash`/`Edit`/`Write` operations based on rules defined in `.claude/hookify.*.local.md` files. Every error path in the rule-loading and rule-evaluation pipeline — malformed YAML frontmatter, unreadable files, unicode errors, unexpected exceptions, or even a Python import failure — is caught and converted into a benign `systemMessage`, and the hook process always exits with code `0`. Since Claude Code's `PreToolUse` hook contract treats exit `0` (and the absence of an explicit `"permissionDecision": "deny"`) as an implicit allow, any rule-file corruption or evaluation bug causes the intended block/deny protection to silently disappear rather than fail safe.

### Finding Description
`load_rules()`/`load_rule_file()` in `plugins/hookify/core/config_loader.py` wrap file reads and frontmatter parsing in broad `except` blocks (`IOError`, `ValueError`, `UnicodeDecodeError`, bare `Exception`) that print a warning to stderr and simply skip the offending rule file, continuing on to return whatever rules did parse successfully [1](#0-0) . In `plugins/hookify/hooks/pretooluse.py`, the top-level `try/except Exception` around the entire rule-load-and-evaluate sequence, plus the `finally: sys.exit(0)`, guarantees the hook process always reports success even when the rule engine crashed and no rules were actually evaluated [2](#0-1) . The same fail-open pattern is duplicated in `plugins/hookify/hooks/posttooluse.py` [3](#0-2) . Additionally, if the Python import of the rule engine itself fails (e.g., due to a `CLAUDE_PLUGIN_ROOT` path issue or missing module), the script prints an error message and exits `0` before ever attempting to load or evaluate any rule [4](#0-3) . In `rule_engine.py`, `evaluate_rules()` returns an empty dict `{}` (meaning "no matches — allow operation") whenever no blocking rule matched, including scenarios where all rules failed to load or were filtered out due to a parsing bug in `_check_condition`'s silent `return False` fallback for unknown operators [5](#0-4) [6](#0-5) .

This is directly analogous to the Illuminate `Lender.mint()` bug: there, an uninitialized/zero-value state (`markets[u][m][p] == address(0)`) combined with a default-allow guard (`unpaused(u, m, p)` being `true` by default) let a caller bypass the market's real access boundary and mint value for free. Here, an uninitialized/malformed rule-file state (frontmatter parse failure, unexpected exception, import failure) combined with the hook framework's default-allow behavior on exit code `0` lets a caller (any user or, more critically, the LLM agent itself acting on attacker-influenced content) bypass the intended `Bash`/`Edit`/`Write` block guard.

### Impact Explanation
A user who relies on `hookify` rules to block dangerous commands (`rm -rf`, `chmod 777`, edits to `.env`/credential files, etc., per the documented use cases in `plugins/hookify/commands/hookify.md`) has no visible indication that their protection silently stopped working when a rule file becomes malformed (e.g., through a bad edit, encoding issue, or a future rule schema change). Because the hook always reports "allow" on error instead of "deny," any tool call that should have been blocked instead proceeds unblocked — this is a direct approval-bypass in the command/hook trust boundary, not merely a usability bug, since the entire purpose of `hookify` is to act as a `PreToolUse` gate on potentially destructive Bash/file operations.

### Likelihood Explanation
Triggering this requires only that a `.claude/hookify.*.local.md` rule file becomes unparseable or that the rule evaluation encounters an unexpected exception (e.g., a `Condition` field lookup that raises `AttributeError`/`TypeError` on unusual `tool_input` shapes, or an encoding issue in a rule file). Given the custom hand-rolled YAML-subset parser in `extract_frontmatter()` (not a real YAML parser) handling arbitrary user-authored markdown, malformed frontmatter is a realistic occurrence, and the fail-open design guarantees it degrades to full bypass rather than a safe denial.

### Recommendation
Change the default posture from fail-open to fail-closed for any hook whose stated purpose is a security gate: on any rule-load or rule-evaluation error, the hook should emit `"hookSpecificOutput": {"permissionDecision": "deny"}` (or at minimum surface a prominent, non-silent warning distinguishable from normal operation) rather than exiting `0` with only an informational `systemMessage`. At minimum, distinguish "no rules matched" (`{}`) from "rules failed to load/evaluate" so callers/users can detect degraded protection instead of assuming full coverage.
