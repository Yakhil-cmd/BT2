### Title
Inadequate Cross-Parameter Consistency Check in `checkConsistency` Allows `LowerBoundBaseFee > UpperBoundBaseFee` via Same-Epoch Votes — (File: `kaiax/gov/headergov/impl/header.go`)

---

### Summary

The `checkConsistency` function validates each governance vote independently against the **current** parameter set, without accounting for other pending votes in the same epoch. In `none` governance mode, a single GC member can cast two votes in the same epoch — one raising `LowerBoundBaseFee` and one lowering `UpperBoundBaseFee` — each of which passes the per-vote guard, but whose combined ratification produces the invalid invariant `LowerBoundBaseFee > UpperBoundBaseFee`. This corrupted governance state persists for the entire following epoch and is applied to every block's base-fee calculation during that period.

---

### Finding Description

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` enforces the cross-parameter bound:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads CURRENT epoch params
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads CURRENT epoch params
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
```

`GetParamSet(blockNum)` returns the **effective** parameter set for the current block — it does not include any votes that have already been cast in the same epoch but not yet ratified. Therefore, the two checks are blind to each other.

**Attack path (none mode, single actor):**

| Step | Action | Guard evaluated | Result |
|------|--------|-----------------|--------|
| 1 | Current state: `Lower=100`, `Upper=200` | — | — |
| 2 | Vote `LowerBoundBaseFee = 150` at block N | `150 ≤ currentUpper(200)` → **pass** | vote recorded |
| 3 | Vote `UpperBoundBaseFee = 120` at block N+k | `120 ≥ currentLower(100)` → **pass** | vote recorded |
| 4 | Epoch ratification | `getExpectedGovernance` collects last vote per key, no cross-check | `Lower=150, Upper=120` written |

`getExpectedGovernance` simply collects the last vote per parameter name and emits them as `GovData` with no post-collection consistency validation:

```go
for _, voteBlock := range sortedVoteBlocks {
    vote := prevEpochVotes[voteBlock]
    govs.Add(string(vote.Name()), vote.Value())   // no cross-param check
}
return headergov.NewGovData(govs)
```

`VerifyGov` only checks that the proposer's `header.Governance` matches the locally derived `expected` value — it does not validate that the resulting parameter set is internally consistent.

The corrupted `Lower > Upper` state is then persisted and returned by every subsequent `GetParamSet` call for the next epoch.

---

### Impact Explanation

`LowerBoundBaseFee` and `UpperBoundBaseFee` are the hard floor and ceiling used by the KIP-71 dynamic base-fee algorithm. When `Lower > Upper`, the clamping expression `clamp(computedFee, Lower, Upper)` is undefined and implementations typically resolve it by returning `Lower` (the larger value), forcing every block's base fee to the artificially elevated floor for the entire epoch. Consequences:

- **Unauthorized fee overcharge**: every transaction sender pays a base fee higher than the protocol intends, constituting an unauthorized fee charge on KAIA.
- **Excess burn**: since Magma, half the base fee is burnt; an inflated base fee increases the burn rate beyond governance intent, permanently destroying KAIA.
- **Reward distortion**: the deferred-fee reward path distributes `F/2` to validators; an inflated `F` shifts reward amounts away from the ratified `reward.ratio` split.

All three effects fall within the allowed impact gate ("unauthorized fee charge / reward distribution affecting KAIA").

---

### Likelihood Explanation

- **Trigger**: a single GC member in `none` governance mode; no collusion required.
- **Barrier**: the attacker must be a registered council member (semi-trusted, not fully unprivileged), but no key compromise or majority collusion is needed.
- **Detectability**: both votes appear individually valid; no existing on-chain or off-chain check flags the combined outcome before ratification.
- **Mainnet note**: Kaia Mainnet and Kairos operate in `single` mode, where only the governing node can vote, making exploitation require that node's cooperation. Deployments or testnets using `none` mode are directly exposed to a single-actor attack.

---

### Recommendation

Add a cross-parameter consistency check **at ratification time** inside `getExpectedGovernance` (or equivalently in `VerifyGov`) after all votes for the epoch have been merged:

```go
// After collecting all ratified params for the epoch:
lower, hasLower := govs[string(gov.Kip71LowerBoundBaseFee)]
upper, hasUpper := govs[string(gov.Kip71UpperBoundBaseFee)]
if hasLower && hasUpper {
    if lower.(uint64) > upper.(uint64) {
        return headergov.GovData{}, ErrLowerBoundBaseFee
    }
}
// Also cross-check against the surviving (non-voted) counterpart:
if hasLower && !hasUpper {
    if lower.(uint64) > currentParams.UpperBoundBaseFee { ... }
}
```

Alternatively, `checkConsistency` should also scan the in-memory pending votes for the current epoch and validate the new value against any already-pending vote for the counterpart parameter.

### Proof of Concept

```
Epoch = 1000 blocks. Current params: LowerBoundBaseFee=25_000_000_000, UpperBoundBaseFee=750_000_000_000.

Block 1001: GC member A calls governance_vote("kip71.lowerboundbasefee", 500_000_000_000)
  → checkConsistency: 500e9 ≤ currentUpper(750e9) → PASS, vote recorded.

Block 1500: GC member A calls governance_vote("kip71.upperboundbasefee", 300_000_000_000)
  → checkConsistency: 300e9 ≥ currentLower(25e9) → PASS, vote recorded.

Block 2000 (epoch boundary):
  getExpectedGovernance collects: {lower: 500e9, upper: 300e9}
  VerifyGov: proposer writes header.Governance = {lower:500e9, upper:300e9} → matches expected → PASS.

Blocks 2001–3000: GetParamSet returns Lower=500e9, Upper=300e9.
  Every block's base fee is clamped to 500e9 (Lower > Upper → clamp returns Lower).
  All transaction senders pay 500 Gkei base fee instead of the intended ≤300 Gkei.
```
