### Title
Global unit-cache arrays (`assocUnstableUnits`, `assocStableUnits`, `assocStableUnitsByMci`, `assocBestChildren`) are cleared and asynchronously rebuilt while producer/consumer code assumes atomic, lock-protected mutation - ([File: storage.js])

### Summary
`storage.js` maintains several process-wide caches (`assocUnstableUnits`, `assocStableUnits`, `assocStableUnitsByMci`, `assocBestChildren`, `assocUnstableMessages`) that mirror the `units` table and are consulted synchronously by validation, main-chain stabilization, paid-witnessing and TPS-fee code without any locking of their own — they rely entirely on the caller already holding the `["write"]` mutex from `mutex.js`. `storage.resetMemory()` (via `resetUnstableUnits()`/`resetStableUnits()`) deletes every key from these live objects synchronously and then repopulates them via asynchronous DB queries (`initUnstableUnits`/`initStableUnits`), leaving a window where the caches are empty or partially filled. `writer.saveJoint()` invokes this reset on its error/rollback path, but `saveJoint()` only takes the `"write"` mutex itself when `objValidationState.bUnderWriteLock` is falsy (`writer.js:34`); when `bUnderWriteLock` is true it trusts that some caller already holds the lock instead of acquiring it again. This is structurally the same bug class as CVE-2026-46317: a shared array that is torn down/rebuilt is protected by a *different, narrower* lock than the one relied upon by concurrent readers, so a reader can observe the array mid-mutation.

### Finding Description
- `resetUnstableUnits()` at [1](#0-0)  deletes every key of `assocUnstableUnits` and `assocBestChildren` synchronously, then calls `initUnstableUnits(conn, onDone)`, which repopulates them only after an async `conn.query(...)` callback returns.
- `resetStableUnits()` at [2](#0-1)  does the same for `assocStableUnits`/`assocStableUnitsByMci`, calling `initStableUnits`, itself async (`storage.js:2339-2382`).
- `resetMemory()` chains both operations sequentially: [3](#0-2) .
- `writer.saveJoint()` calls `await storage.resetMemory(conn)` on its rollback/error path: [4](#0-3) .
- Critically, `saveJoint()` only acquires the `"write"` mutex conditionally: `const unlock = objValidationState.bUnderWriteLock ? () => {} : await mutex.lock(["write"]);` [5](#0-4) . When `bUnderWriteLock` is true, `saveJoint()` (and by extension the `resetMemory()` call inside it) executes its cache-clearing/rebuilding logic without independently establishing that it, in fact, has exclusive access — it depends entirely on an external invariant holding true.
- Meanwhile, numerous readers treat these caches as always-consistent, lock-free-readable snapshots: e.g. `main_chain.js` iterates `storage.assocUnstableUnits` and indexes `storage.assocStableUnitsByMci[mci]` directly while stabilizing the DAG ( [6](#0-5) ), `paid_witnessing.js` reads `storage.assocStableUnitsByMci[main_chain_index]` ( [7](#0-6) ) and `storage.assocStableUnits[v.unit]` ( [8](#0-7) ), and `storage.getCurrentTps()`/`getFinalTps()` walk `assocUnstableUnits`/`assocStableUnitsByMci` directly ( [9](#0-8) , [10](#0-9) ). None of these readers acquire the `"write"` mutex themselves; they assume the invariant that mutation of these globals only happens under that lock.

If the `bUnderWriteLock` invariant is ever violated — i.e., `saveJoint()` is invoked with `bUnderWriteLock: true` from a code path that does not actually hold `mutex.lock(["write"])` for the duration of the reset — a concurrently running unit-poster's validation (`validation.js`) or main-chain stabilization (`main_chain.js`) can execute while `assocUnstableUnits`/`assocStableUnitsByMci`/`assocBestChildren` have already had their keys deleted but not yet repopulated (the repopulation is gated on an async DB round-trip). During that window:
- `assocStableUnitsByMci[mci]` can be `undefined` where code assumes an array (e.g. `storage.js:1170`, `paid_witnessing.js:135`), causing a crash, or
- `assocUnstableUnits` can appear to no longer contain a genuinely-unstable, conflicting unit, so double-spend/conflict detection logic that walks this cache (used pervasively in `main_chain.js` stabilization and TPS calculations) can conclude a competing unit does not exist, mirroring the "walker references torn-down state" failure mode of the kernel CVE.

### Impact Explanation
If the missing-lock window is reachable, the practical consequences are:
- Nodes stabilizing the DAG concurrently with the reset can compute inconsistent `is_stable`/`sequence`/main-chain membership for units, since `markMcIndexStable()` relies on `assocUnstableUnits`/`assocStableUnitsByMci` being complete (`main_chain.js:1288-1307`). Divergent nodes disagreeing on stability of the same MCI is one of the accepted high-impact outcomes.
- A transiently empty `assocUnstableUnits` could cause conflicting-unit detection to miss a competitor, mirroring conditions that can lead to acceptance of what should be a non-serial (double-spend) unit.
- Crashes/throws on `undefined` array access (`storage.js:1170`, `paid_witnessing.js:135`) in the write/stabilization path could halt or degrade a node's ability to process and confirm new units.

### Likelihood Explanation
The precondition — `saveJoint()` being invoked with `objValidationState.bUnderWriteLock === true` from a context that does not already own the `"write"` mutex for the whole duration of `resetMemory()` — could not be fully enumerated within the available search budget; I found the mechanism (`writer.js:34`) but did not exhaustively verify every call site that sets `bUnderWriteLock`. This is the main source of uncertainty: if all current callers of `saveJoint(..., {bUnderWriteLock: true})` are strictly nested inside an already-held `"write"` lock for their entire lifetime (including the async `resetMemory` chain), the race is not currently reachable through any code path I confirmed, even though the design pattern (lock-optional mutation of shared global caches, with async rebuild steps) is inherently fragile and matches the CVE's root cause exactly.

### Recommendation
- Make `resetMemory()`/`resetUnstableUnits()`/`resetStableUnits()` always acquire `mutex.lock(["write"])` internally regardless of `bUnderWriteLock`, or assert/enforce (e.g., via `mutex.isAnyOfKeysLocked(["write"])`) that the lock is actually held before mutating the caches, instead of trusting caller discipline.
- Populate replacement caches into local objects first (fully rebuilding them via the async DB queries), and only atomically swap them into `storage.assocUnstableUnits`/`assocStableUnits`/`assocStableUnitsByMci`/`assocBestChildren` once population is complete and while still holding the lock — analogous to the kernel fix's "build outside the lock, swap the pointer while holding the lock" pattern.
- Audit every call site that sets `bUnderWriteLock: true` to confirm the `"write"` mutex is held for the entire synchronous+asynchronous duration of the nested `saveJoint()`/`resetMemory()` call, not just at the moment of invocation.

### Proof of Concept
Not constructed — a concrete PoC would require confirming a real call site where `saveJoint(objJoint, {..., bUnderWriteLock: true}, ...)` is reached without the `"write"` mutex being held for the full duration of the subsequent `resetMemory()` error path, which was not verified within the available investigation. This should be validated with the full codebase (e.g., via a Devin session) before treating this as a confirmed, exploitable vulnerability rather than a structural risk analogous to the reported CVE.
