## Confirmation

I found a concrete analog: the field used to select the HMAC verification key (`repository.owner.login` / `organization.login`) is disjoint from the field used to resolve which `Repository`/`Stack` a handler mutates (`repository.full_name`), and both are attacker-controlled JSON body content in a multi-org deployment.

### Title
Webhook signature key selected by `repository.owner.login`/`organization.login` is decoupled from `repository.full_name` used to resolve the mutated Stack, enabling cross-organization webhook forgery in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret used to verify `X-Hub-Signature` via `repository_owner`, an org name that is read directly out of the untrusted, attacker-controlled JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). All downstream handlers (`PushHandler`, `PullRequest::*Handler`) instead resolve the target `Repository`/`Stack` using a *different* field of that same untrusted body: `repository.full_name`, via `Repository.from_github_repo_name`. In a single-org Shipit deployment this doesn't matter, but the engine explicitly supports and documents multiple, independently-configured GitHub Apps/orgs, each with its own `webhook_secret` (see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). An attacker who legitimately controls (or has compromised) one configured org's GitHub App webhook secret can craft a payload where `repository.owner.login` names their own org (satisfying signature verification with a secret they know) while `repository.full_name` names a repository belonging to a *different* configured org, causing handlers to act on that other org's Stack.

### Finding Description [1](#0-0) 
`verify_signature` picks the `GitHubApp` (and thus the webhook secret) using `repository_owner`: [2](#0-1) 
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This is looked up via `Shipit.github(organization: ...)`, which in multi-org mode indexes into a per-org config table keyed by organization name: [3](#0-2) 

Meanwhile, every default event handler resolves the actual `Repository`/`Stack` acted upon from a *different* JSON field, `repository.full_name`: [4](#0-3) [5](#0-4) [6](#0-5) 

The binding that should hold is: `organization whose secret verified the payload == organization owning the repository the handler mutates`. Nothing in `verify_signature` or in `Repository.from_github_repo_name` enforces that `repository.owner.login` (used for key selection) matches the owner embedded in `repository.full_name` (used for handler dispatch) — they are two independent reads of the same untrusted JSON body, and HMAC coverage of the whole body does not restore this binding because *both* fields are attacker-authored content signed with whichever key the attacker chooses to use.

This mirrors the ECDSA report's root cause class: a verification routine accepts multiple representations/fields of the "same" authenticated fact, and downstream logic keys off a different representation than the one actually checked, breaking the intended equality between "who is authenticated" and "what is acted upon."

### Impact Explanation
The engine explicitly documents and ships fixtures for multi-organization deployments (`docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`, `test/unit/shipit_test.rb`), so this is a supported, in-scope configuration, not a misuse of the engine. In that configuration, an actor who can produce a validly-signed webhook for *one* configured organization (e.g., they administer that org's GitHub App, or that org's secret has leaked — a lower bar than compromising the target org) can forge events (`push`, `pull_request` opened/closed/labeled, etc.) that reference a repository belonging to a *different* configured org, because the secret used for verification is selected from a field independent of the field used to pick the mutated `Stack`. This can trigger unauthorized `sync_github` on another org's stack, or create/archive PR-based review stacks for another org's repository, i.e. writes/state changes across a repository trust boundary the operator did not intend to share — matching the "cross-repository writes" / "unauthorized ...deploy" high-impact class in the rules, in a multi-org install.

### Likelihood Explanation
Requires: (a) a Shipit deployment configured with multiple GitHub organizations (documented, supported feature), and (b) the attacker possessing a valid webhook secret for at least one of those configured orgs (their own app's secret, which they administer, or a leaked one) — not the target org's secret. No session, `ApiClient` token, or `api_clients_secret` is needed; only knowledge of one legitimate org's HMAC secret in the shared deployment. Given the rules exclude findings that require possessing `webhook_secret` outright as the sole crossed boundary, this finding is borderline: the exploit is enabled by having *a* configured secret (for org A) and using it to affect org B — the crossed boundary is the org-to-org isolation promised by "Using Multiple GitHub Applications," not merely possessing a webhook secret in the abstract.

### Recommendation
In `Shipit::Repository.from_github_repo_name`/handler resolution, or in `WebhooksController#verify_signature`, enforce that the organization used to select the verifying `GitHubApp`/secret equals the owner of the resolved `Repository` (i.e., re-check `repository.owner.login == resolved_repository.owner` post-verification, or resolve the target strictly from the same organization namespace that produced a valid signature) before dispatching to handlers.

### Proof of Concept
In a multi-org config with `OrgA` (attacker-controlled/known secret) and `OrgB` (victim), attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already present on OrgB stack>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
`verify_signature` selects `Shipit.github(organization: "OrgA")`, verifies successfully with the attacker-known secret, then `PushHandler` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim org's stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
