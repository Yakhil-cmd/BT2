### Title
Dust flooding of a custom asset lets an attacker permanently freeze an AA's asset payout logic - (File: aa_composer.js)

### Summary
`aa_composer.js`'s unspent-output selection for AA-generated payment messages applies a minimum-amount ("dust") filter only for the base asset, not for custom assets. `validation.js` also explicitly exempts AA-generated payment messages from the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap. Together, this lets any unprivileged unit poster flood an AA's address with an unbounded number of tiny-amount outputs of a custom asset, forcing every subsequent AA response that needs to pay out that asset to walk through and consume all of them as inputs, exactly mirroring the reported "flood the array" pattern that causes an operation to become impossible to complete.

### Finding Description
When an AA needs to pay out in a payment message, `completePaymentPayload()` in `aa_composer.js` selects unspent outputs to use as inputs via `readStableOutputs()` and `readUnstableOutputsSentByAAs()`: [1](#0-0) 

The WHERE clause explicitly applies a minimum-amount dust filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) only when the asset is the base asset (`asset IS NULL`). When `asset` is a custom asset, the condition reduces to plain `asset=<escaped>` with **no lower bound on amount** at all: [2](#0-1) 

The same asymmetry exists for outputs sent by other AAs: [3](#0-2) 

The developers' own comment on line 1144 acknowledges the underlying threat model explicitly for bytes ("spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond"), but the mitigation was never extended to custom assets.

`iterateUnspentOutputs()` then loops over *every* row returned and unconditionally pushes each one into `payload.inputs` until the accumulated amount reaches the target: [4](#0-3) 

Normally, `payload.inputs.length` is capped for ordinary payment messages, but this cap is explicitly bypassed for AA-authored units: [5](#0-4) 

This means there is no consensus-level upper bound stopping an AA-authored payment message from accumulating an unbounded number of inputs when paying out a custom asset.

Any unprivileged user can post an ordinary `payment` message sending a custom asset (e.g., an asset the AA is known to hold/manage, or one the AA is programmed to forward/pay back) to the AA's address in many tiny-amount outputs (1 unit of the asset each), each posted in a separate transfer. Since `outputs` are ordered `ORDER BY main_chain_index, unit, output_index` (oldest first), the attacker's early, tiny-amount dust outputs are always selected first by the AA's coin-selection logic and consumed before any legitimate larger balance, guaranteeing the AA must gather all the dust before it can even start counting toward the real payout target.

### Impact Explanation
Once flooded, every future AA response that must pay any amount of that asset will attempt to select from the flooded output set. As the required number of dust inputs grows, the resulting payment message/unit grows without the size protection that exists for base-asset transfers, and without the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap that protects ordinary payments. This can push the generated unit past size/oversize-fee economics or otherwise make the AA response fail to be composed/validated successfully on an ongoing basis, effectively freezing the AA's ability to pay out that asset to anyone — an AA fund-freezing condition reachable purely by posting ordinary payment units to the AA's address, with no privileged access required. This matches the accepted impact class of "AA fund loss or freezing."

### Likelihood Explanation
Likelihood is high: sending many small-amount custom-asset outputs to a known AA address only requires ordinary `payment` messages authored by the attacker, well within normal validation rules (there is no minimum-amount rule for asset outputs at the protocol level, unlike the special-cased AA-side dust filter for bytes). No cooperation from the victim AA or node operators is needed, and the cost to the attacker is limited to standard transaction fees for however many dust units they choose to send — cheap relative to the DoS it inflicts on the AA's future payouts.

### Recommendation
Extend the dust-amount filtering already applied to base-asset outputs in `readStableOutputs()`/`readUnstableOutputsSentByAAs()` to custom assets as well (e.g., require the accumulated fee-equivalent value of an asset output to exceed some minimum before it is eligible as an input), and/or enforce `MAX_INPUTS_PER_PAYMENT_MESSAGE` (or an asset-specific cap) for AA-generated payment messages instead of exempting `objValidationState.bAA` from that check in `validatePaymentInputsAndOutputs()`.

### Proof of Concept
1. Deploy or identify an AA that holds/manages a custom, transferable asset and can be triggered to pay out that asset to a target address.
2. As an unprivileged attacker, repeatedly post ordinary `payment` units transferring 1 unit of that custom asset to the AA's address, each in its own unit, over many blocks — no admin/AA/oracle privileges required.
3. Because `readStableOutputs()`'s WHERE clause for a non-base asset has no `amount>=X` floor (`aa_composer.js:1149`), and because these outputs are consumed oldest-first (`ORDER BY main_chain_index, unit, output_index`), every future AA response requiring a payout in that asset must include all of the attacker's dust outputs as inputs.
4. Trigger the AA to pay out the asset. Observe `payload.inputs` in `completePaymentPayload()` growing unboundedly as `iterateUnspentOutputs()` walks the flooded set, unconstrained by `MAX_INPUTS_PER_PAYMENT_MESSAGE` since `objValidationState.bAA` is true (`validation.js:2137`).
5. As the number of dust outputs grows large enough, the AA's payout attempts fail to complete successfully on an ongoing basis, freezing its ability to pay out that asset.

I was not able to fully verify from the available index whether some additional unit-size/oversize-fee cap independently rejects the oversized AA response unit before it reaches this failure state (e.g., an explicit `MAX_MESSAGES_PER_UNIT`/size bounce check elsewhere in `aa_composer.js`) — this would need to be confirmed in a full checkout of the repository, since the indexed portions of `aa_composer.js` I could inspect show no such guard specific to this input-accumulation path.
