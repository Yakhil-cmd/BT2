No vulnerability found for this question.

**Rationale:**

The Chakra report describes a signature that omits `from_chain`, letting a griefer front-run the callback with a mismatched (but signature-valid) `from_chain` so that `is_valid_handler` fails downstream and the transaction status flips to `Failed`. Two elements make this non-transferable to `polkadot-sdk`:

1. **No equivalent unbound field exists in the bridges pallet.** In `pallet-bridge-messages`, the analogous "route" identifier is the `lane_id`, but it is not a free-form parameter accompanying an independently-signed message hash — it is embedded in the `MessageKey { lane_id, nonce }` used to derive the storage proof key, and the proof is verified against the bridged chain's finalized header root via `verify_messages_proof`/`verify_messages_delivery_proof`. [1](#0-0)  There is no scenario where a third party can supply a different `lane_id`/`from_chain`-equivalent value while reusing a signature/proof computed over a different one, because the lane id is part of what is cryptographically committed to, not appended alongside a hash that omits it.

2. **Nonce-based ordering already prevents the "poison the status" replay.** `InboundLane::receive_message` strictly rejects any nonce that isn't `last_delivered_nonce + 1`, so a front-run message with attacker-chosen parameters cannot be slotted in ahead of the legitimate one to consume/desync the state as in the Solidity case. [2](#0-1)  The dispatch result is tied to `MessageDispatch::dispatch` outcome per exact nonce/lane, not a mutable global `status` field keyed only by an externally-supplied `txid` decoupled from origin-chain binding.

3. Even setting aside the structural difference, the underlying bug class here is a **front-running griefing attack** against a callback's terminal status, which the scan method explicitly instructs to reject ("Reject ... pure front-running/economic attacks"), and which the original judge only upheld as a status-griefing issue in the Solidity contract's specific (and different) trust model.

No FRAME/XCM/bridges entry point in this codebase exposes an unauthenticated, attacker-supplied field that get omitted from a signature/proof check in a way that lets a non-privileged actor redirect or invalidate a cross-chain settlement's final status.

pub fn verify_messages_proof<T: Config<I>, I: 'static>(
	proof: FromBridgedChainMessagesProof<HashOf<BridgedChainOf<T, I>>, T::LaneId>,
	messages_count: u32,
) -> Result<ProvedMessages<T::LaneId, Message<T::LaneId>>, VerificationError> {
	let FromBridgedChainMessagesProof {
		bridged_header_hash,
		storage_proof,
		lane,
		nonces_start,
		nonces_end,
	} = proof;
	let mut parser: MessagesStorageProofAdapter<T, I> =
		MessagesStorageProofAdapter::try_new_with_verified_storage_proof(
			bridged_header_hash,
			storage_proof,
		)
		.map_err(VerificationError::HeaderChain)?;
	let nonces_range = nonces_start..=nonces_end;

	// receiving proofs where end < begin is ok (if proof includes outbound lane state)
	let messages_in_the_proof = nonces_range.saturating_len();
	if messages_in_the_proof != MessageNonce::from(messages_count) {
		return Err(VerificationError::MessagesCountMismatch);
	}

	// Read messages first. All messages that are claimed to be in the proof must
	// be in the proof. So any error in `read_value`, or even missing value is fatal.
	//
	// Mind that we allow proofs with no messages if outbound lane state is proved.
	let mut messages = Vec::with_capacity(messages_in_the_proof as _);
	for nonce in nonces_range {
		let message_key = MessageKey { lane_id: lane, nonce };
		let message_payload = parser
			.read_and_decode_message_payload(&message_key)
			.map_err(VerificationError::MessageStorage)?;
		messages.push(Message { key: message_key, payload: message_payload });
	}
