I found a directly relevant analog: an uncaught JavaScript exception thrown during processing of an attacker-crafted, otherwise-syntactically-valid unit crashes the full node process, because `network.js` installs a fatal `process.on('uncaughtException', ...)` handler that re-throws to kill the process.

### Title
Attacker-triggerable synchronous `throw Error` in oscript/AA formula evaluation crashes full nodes via the global `uncaughtException` handler - (File: formula/evaluation.js, network.js)

### Summary
Ocore's full node deliberately crashes the process on any uncaught exception: `process.on('uncaughtException', ...)` logs the error and then `throw err` to "crash the process to avoid ending up in an inconsistent state." [1](#0-0) 
This is the direct network-facing analog of the OpenVPN control-channel DoS: a small, crafted piece of attacker-controlled input (there: a "crafted reset packet"; here: a crafted unit/AA trigger whose oscript formula reaches an unguarded `throw Error(...)`) causes an unhandled fault that terminates the process that is supposed to keep validating/confirming the network.

### Finding Description
`formula/evaluation.js`'s `evaluate()` function is the interpreter used for AA `state`/`getters`/`init`/`if` formulas that any unprivileged unit poster can trigger by simply sending a payment/trigger to an Autonomous Agent address, or that any AA author can put in an AA definition that will later be executed against attacker-influenced `trigger.data`. The interpreter uses `setFatalError(...)` almost everywhere to safely convert bad values into a controlled error return, but a few branches use a raw synchronous `throw Error(...)` instead, e.g.:
- `throw Error("test evaluated to object " + res);` when a ternary/if condition evaluates to an object [2](#0-1) 
- `throw Error("args is not an array");` in `callGetter` [3](#0-2) 
- `throw Error("unknown field requested: "+arr[2]);` in the `input`/`output` field accessor [4](#0-3) 

Unlike the `setFatalError` path, these `throw` statements are synchronous JS exceptions that unwind the call stack instead of being funneled through the `cb`/`callback` error-handling convention used everywhere else in the async evaluator. Because `evaluate()` is invoked from deep, nested `async.eachSeries`/`async.eachOfSeries` callback chains inside `aa_composer.js` (`replace()`, `evaluateAA()`, `executeStateUpdateFormula()`, etc.) which do not wrap the call in `try/catch`, [5](#0-4) [6](#0-5)  a thrown exception from deep inside `evaluate` propagates up through `async`'s internal iterator machinery and out to the top of the event loop, where it becomes an `uncaughtException` and, per `network.js`, kills the whole node process. [1](#0-0) 

This class of bug — “malformed-but-superficially-valid input reaches an unguarded fault path in message/control processing and kills the peer” — is exactly the bug class in CVE-2020-20813 (a crafted control-channel reset packet causing OpenVPN to crash/DoS).

### Impact Explanation
If a single crafted AA-trigger unit (payment to an AA address plus `data` payload) can drive an AA formula into one of the raw `throw` branches, every full node that executes that AA's response formula (i.e., every full node that has stabilized the MC index containing the trigger, since AA execution is deterministic and mandatory consensus logic run by all nodes) hits the same `uncaughtException` and crashes simultaneously. Because AA execution is not sandboxed with a defensive `try/catch` at its outer async boundary, this is a synchronized, network-wide crash rather than a single-node failure — matching the "network unable to confirm new units" bar in the validation criteria, since AA trigger processing gates MC stabilization and blocks subsequent unit confirmation until restarted.

### Likelihood Explanation
Reaching most of these `throw` sites requires the interpreter to be coaxed into a state that the author of `evaluate()` believed was unreachable given prior validation in `aa_validation.js`/`validation.js` (e.g., ternary condition somehow evaluating to a raw object, or `args` to a getter call not being an array). Whether an attacker can actually construct oscript that reaches these "should never happen" branches (as opposed to being fully blocked by AA definition-time validation) requires deeper live testing of the formula grammar/validator than is verifiable from static reading alone. I was not able to conclusively construct or confirm a specific formula that reaches one of these unguarded `throw` sites past the AA-definition-time `aa_validation.js` checks; this remains an unverified likelihood and should be treated as **medium-confidence** rather than proven.

### Recommendation
- Wrap every `formulaParser.evaluate(...)` call site in `aa_composer.js` (and any other caller) in a `try/catch` that converts unexpected synchronous exceptions into a bounce/error response instead of letting them propagate to `uncaughtException`.
- Replace the remaining raw `throw Error(...)` statements inside `formula/evaluation.js`'s `evaluate()`/`callGetter()` with the existing `setFatalError(...)` convention so all error conditions—including "impossible" ones—are converted into controlled formula failures/bounces rather than process-fatal exceptions.
- Add fuzz/property tests that specifically try to drive `evaluate()` into each `throw Error` branch via attacker-controlled `trigger.data`/`oscript` to confirm reachability and regression-guard the fix.

### Proof of Concept
Not constructed/verified — reaching the vulnerable `throw` branches (e.g. producing a ternary/if test that evaluates to a raw JS object, or a getter call whose `args` are non-array) requires bypassing `aa_validation.js`'s static AA-definition checks, which I could not confirm from static analysis alone. A concrete PoC would need to be built and executed against a live/test ocore node to confirm the crash, which is outside what I can verify with read-only code inspection.
