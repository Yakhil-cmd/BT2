## Title
Cosigner-ownership check for "sign" requests is disabled, allowing any paired device to trigger unauthorized signing prompts for shared/multisig addresses it does not co-sign - ([File: wallet.js])

### Summary
This is analogous to the ActiveMQ bug: the broker only relied on client-side enforcement to keep temporary destinations isolated to their owning connection, so another connection could consume from a destination it didn't own. In `wallet.js`, the `"sign"` device-message handler is supposed to verify that the device sending a signing request is actually a registered cosigner (via `extended_pubkeys`) of the local shared/multisig address before accepting the request and firing the `signing_request` event to the end user. That server-side ownership check is explicitly commented out, so the check is effectively absent, and any correspondent (paired) device can address a signing request to any local address it can guess/learn, relying only on the requester having behaved correctly (client-side assumption) rather than on the node enforcing cosigner membership.

The comment itself acknowledges that this ownership check exists in intent but was removed to support "multilateral signing" (different addresses signing the same message, e.g. dumb contracts), where the sender is legitimately *not* a cosigner of `body.address` but of a different author address in the same unit. However, the removal is unconditional: it applies identically to the true multisig case (case 1 in the code comment) where the same address is hosted across multiple devices and the sender genuinely must be a registered co-key-holder of that specific address/wallet.

As a result, once past `findAddress`'s `ifLocal` branch (i.e., once the target `body.address` is confirmed to be a locally-known address, e.g. one of the user's own multisig addresses), the node does not verify that the sending device (`from_address`, derived from `device_pubkey`, itself cryptographically authenticated per-message) has any legitimate signing_path/extended_pubkey relationship to that address's wallet. It unconditionally calls `callbacks.ifOk()` and proceeds to validate the passed unsigned unit and then emit the `signing_request` event, or forward the unsigned joint through `network.handleOnlineJoint`: [2](#0-1) 

This is the "isolation checked only in the client" failure mode: the multisig protocol relies on cosigner devices trusting that only real cosigners will send `"sign"` requests, but the enforcement point on the receiving node — which is the only place that can actually validate wallet membership via `extended_pubkeys`/`shared_address_signing_paths` — has had its check disabled.

### Impact Explanation
Any paired correspondent device (an "unprivileged" but paired counterparty, satisfying the "paired device" reachability requirement) can send a `"sign"` device message naming any of the victim's locally known addresses (shared/multisig addresses are often shared out-of-band, e.g. displayed to arbiter counterparties, textcoin recipients, or third parties during shared-address setup flows) together with an attacker-crafted unsigned unit. Because the cosigner-membership check is disabled, the node will:
- accept the message (`callbacks.ifOk()`), silencing any protocol-level rejection that would otherwise flag the sender as unauthorized,
- validate/store the attacker-supplied unsigned joint via `network.handleOnlineJoint`,
- fire the `signing_request` event, causing the wallet UI to prompt the real owner to sign a transaction they never initiated.

If the user is tricked (social engineering, contract confusion, or automated signing flows in bots/services) into approving, this leads to unauthorized spending from a shared/multisig address (fund loss), because the device that is not a genuine cosigner successfully drove the signing flow for that specific address. Even absent user approval, it allows an unauthorized entity to flood/spam signing prompts for addresses on victims' devices and to fingerprint/probe whether a wallet locally controls given multisig addresses (an oracle for `ifLocal` vs `ifUnknownAddress`/`ifRemote` responses), which undermines the shared/multisig authorization model relied on for correct spending intent.

### Likelihood Explanation
Reachable directly from any correspondent (paired) device without needing to compromise a hub, node, or perform any p2p/network-level attack — pairing with a victim is a normal, low-friction wallet operation (e.g., accepting a chat/textcoin/arbiter-contract pairing). Constructing a valid `"sign"` body only requires knowledge of a target multisig address (often not secret — shared in shared-address setup handshakes, arbiter contracts, or public spending history) and a syntactically valid unsigned unit satisfying the other validations in the same handler (`hasValidPayloadHashes`, output/input shape checks). The missing check is a straight comment-out with no compensating control elsewhere in this code path, so likelihood of successful message delivery and event emission is high; the residual risk is bounded by whether the wallet UI provides sufficiently strong context in the `signing_request` confirmation dialog to let the user detect the request is illegitimate (a UI mitigation, not a protocol one).

### Recommendation
Restore and unconditionally enforce a cosigner-membership check in the `ifLocal` branch of the `"sign"` handler for the true multisig case (address hosted on multiple devices under the same wallet), i.e., verify that `from_address` is registered as a `device_address` for the wallet owning `body.address` via `extended_pubkeys`/`shared_address_signing_paths` before calling `callbacks.ifOk()` and emitting `signing_request`. For the legitimate "multilateral signing" case (different addresses cosigning the same unit), scope the exemption narrowly: only skip the same-address cosigner check when the sender is verified to be an author of a *different* address in the same unit that the sender does legitimately control, rather than removing the check entirely for all `"sign"` requests targeting locally-hosted addresses.

### Proof of Concept
1. Device B pairs with Device A (normal pairing flow, requires no special privilege).
2. Device A creates or is part of a multisig/shared address `ADDR_M` whose definition lives across multiple devices (Device A plus a real cosigner Device C), recorded in Device A's `extended_pubkeys` for Device C's `device_address`, not Device B's.
3. Device B (attacker), which knows `ADDR_M` (e.g., learned from a shared address setup broadcast or public unit history) and can supply a syntactically valid unsigned unit spending from `ADDR_M`, sends Device A a `"sign"` message:
   ```json
   { "subject": "sign", "body": { "address": "ADDR_M", "signing_path": "r", "unsigned_unit": { ... authors: [{address: "ADDR_M", ...}], messages: [...] } } }
   ```
4. On Device A, `findAddress` resolves `ADDR_M` as `ifLocal`. Because the cosigner check is commented out, Device A immediately calls `callbacks.ifOk()` and proceeds to validate the joint and emit `signing_request(objAddress, "ADDR_M", objUnit, ..., from_address=Device B, "r")`, prompting Device A's user to sign — despite Device B never being registered as a legitimate signer for `ADDR_M`.
