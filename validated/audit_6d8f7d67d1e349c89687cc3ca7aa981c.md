### Title
`StatusHandler#process` applies GitHub status updates to `Commit` rows across all stacks sharing a sha, without verifying the payload's `repository.full_name` matches `commit.stack.repository` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, never checking that the webhook's `repository.full_name` corresponds to the stack that owns the matched commit. Because `verify_signature` in `WebhooksController` only authenticates that the payload came from *some* organization the attacker controls (via `Shipit.github(organization: repository_owner)`), a validly-signed status event for repo B can silently mutate a `Status` row belonging to a `Commit` on victim stack A whenever the same sha exists in both stacks' `commits` tables.

### Finding Description
Broken binding: `payload.repository.full_name` ('attacker/B') should equal `commit.stack.repository.full_name` ('victim-org/A') before a status derived from that payload is written to `commit`, but `StatusHandler#process` never enforces this: [1](#0-0) 

Compare with the base `Handler` class, which *does* provide a `stacks`/`repository_name` scoping helper used by other handlers (e.g. `push_handler.rb`, `check_suite_handler.rb`, `membership_handler.rb`) but is not used here: [2](#0-1) 

`WebhooksController#verify_signature` only authenticates the request against the GitHub App/secret configured for `repository_owner` (the org in the payload), it does not (and cannot) verify that the `sha` inside the payload actually belongs to that repository: [3](#0-2) 

`Commit.where(sha: ...)` is a global, unscoped query across every stack in the Shipit instance, and `create_status_from_github!` mutates the `statuses` association directly: [4](#0-3) 

Exploit path: two Shipit stacks exist for repo A and repo B. If B is a fork of A (a very realistic and low-cost way to obtain a genuinely identical sha, since forks share git objects — no cryptographic collision is required, the byte-for-byte identical commit is trivially inherited), the same commit sha exists in both repos' git history. The attacker sends `POST /webhooks` with `X-GitHub-Event: status`, signed with their own org/app secret for repo B, and `payload.repository.full_name = 'attacker/B'`, `payload.sha = SHA` (a sha shared with upstream A), `payload.state = 'success'`. `StatusHandler.process` finds the `Commit` row for stack A with that sha and calls `create_status_from_github!`, writing a new `Status` and potentially flipping `deployable?`/triggering `schedule_continuous_delivery` for stack A — despite the request never having been authenticated for repo A.

None of the existing guards prevent this: `verify_signature` authenticates the org, not the sha-to-repo binding; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/shape of fields, not cross-repo ownership; there is no model validation tying `Status#sha`/`Commit#sha` uniqueness to a particular repository across stacks.

### Impact Explanation
An attacker who controls any repository that happens to share a commit sha with a target repository (trivially achievable via forking) can write arbitrary `Status` rows (state, description, target_url, context) onto a victim's `Commit`. Since `Commit#status` drives `deployable?`, `blocked?`, and `schedule_continuous_delivery`, this can cause a stack to become artificially "green" and trigger continuous deployment, or artificially blocked, purely from an event authenticated for a different, attacker-controlled repository. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and can lead to an unauthorized deploy via the continuous-delivery scheduling path.

### Likelihood Explanation
Preconditions: both repo A and repo B must be registered as Shipit stacks, and a `Commit` row with the shared sha must already exist for stack A (created via normal push/sync). The easiest way to satisfy "byte-for-byte identical sha" is forking repo A (or otherwise sharing history/cherry-picks) rather than a true SHA-1 collision, which is realistic for public/open-source repos that are commonly forked and where forks are independently onboarded as Shipit stacks (e.g., CI testing on personal forks). The attacker only needs the ability to push to their own repo and trigger a CI status webhook on it — capabilities explicitly available to an unprivileged GitHub user. This is a straightforward, repeatable attack requiring no secrets.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks matching `repository_name` from the payload (mirroring the `stacks` helper already defined on `Handler`), e.g. filter `Commit.where(sha: params.sha, stack: stacks)` instead of an unscoped `Commit.where(sha: params.sha)`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status payload for repo B does not mutate commit belonging to stack A" do
  stack_a = shipit_stacks(:shipit)              # repo: victim-org/A
  stack_b = create_stack(repository_owner: 'attacker', repository_name: 'B')

  shared_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'shared commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/B' }
  }

  assert_no_difference -> { commit_a.reload.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # Binding under test: payload['repository']['full_name'] ('attacker/B')
  #   != commit_a.stack.repository.full_name ('victim-org/A')
  # yet before the fix, commit_a.statuses.count would increase.
end
```
