### Title
Membership webhook trusts attacker-controlled `organization` field to write team membership, allowing cross-organization escalation into `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The `membership` webhook handler resolves the target `Team` purely by the numeric GitHub `team.id` in the payload, without verifying that the `organization` field of the *same, correctly-signed* payload actually matches the organization already recorded on that `Team`. Because the webhook signature is only proof that the sending organization's secret was used — not that the org is authorized to write to a `Team` record belonging to a *different* organization — an org admin who legitimately controls one onboarded GitHub organization (and hence its webhook secret) can forge a `membership` event that adds an arbitrary GitHub login to a `Team` belonging to a different organization tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects the signing key for `Shipit.github(organization: repository_owner)` where `repository_owner` is taken straight from the untrusted JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`): [1](#0-0) [2](#0-1) 

This only proves the request was signed with *that organization's* webhook secret — it says nothing about which `Team` record the payload is allowed to mutate.

`MembershipHandler#find_or_create_team!` then looks up (or creates) a `Team` solely by the GitHub `team.id`, and only sets `organization` when the record is first created — it never re-validates `organization` against an existing `Team`: [3](#0-2) 

`Team#add_member` then unconditionally appends the resolved `User` (itself auto-created/looked-up purely from an attacker-supplied `login` string) to that team's `memberships`: [4](#0-3) 

The binding that should hold is: *organization that authenticated the webhook* == *organization owning the `Team` being mutated*. The code only checks the former (via HMAC) and blindly trusts the payload for the latter. Once a `Team` for organization B has been created (a normal event, since Shipit auto-creates teams from real GitHub `membership` events), an attacker who administers organization A (which is also configured/onboarded in this Shipit instance, or whose org triggers a real `membership` event they can fabricate/replay) can send:

```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "https://example.com" },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker-login" }
}
```

signed with organization A's real webhook secret. `verify_signature` passes (org A's secret matches), `find_or_create_team!` finds the pre-existing `Team` for victim org B by `github_id` and ignores the `organization` field, and `attacker-login` is added as a member of that team.

`Team#members` directly backs `User#authorized?`: [5](#0-4) 

so membership in this `Team` is exactly the authorization gate used to restrict access to a private Shipit installation via `Shipit.github_teams`.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization: an attacker who only controls a lesser-privileged, onboarded organization's webhook (not any Shipit session, `ApiClient` token, or GitHub App private key) can grant an arbitrary GitHub login membership in a security-gating `Team` belonging to a different, more privileged organization, bypassing the intended "you must actually be a member of this GitHub team" invariant. Combined with `User#authorized?`, this can let an unauthorized identity gain full authenticated access to a Shipit instance meant to be restricted to a different organization's team members.

### Likelihood Explanation
Requires (a) a Shipit deployment configured with multiple organizations sharing one instance (a documented, supported configuration — see `docs/setup.md`'s multi-org discussion and `Shipit.github(organization:)` lookup), (b) the attacker to control webhook delivery for at least one onboarded organization (e.g., as an org owner able to trigger/replay a real `membership` webhook, without needing any Shipit credentials), and (c) knowledge of the victim `Team`'s numeric GitHub team ID, which is often discoverable via the GitHub API/UI. This is a plausible but not trivially-scriptable path, so likelihood is moderate rather than high.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, verify that the `organization` in the payload matches the existing `Team#organization` before performing any membership mutation, and reject/log the event otherwise (mirroring the `repository_owner` used for signature verification). Consider scoping the `Team.find_or_create_by!` lookup by both `github_id` and `organization`.

### Proof of Concept
1. Shipit instance is configured with two organizations, `org-a` and `org-b`, each with its own GitHub App/webhook secret via `Shipit.github(organization:)`.
2. A legitimate `membership` webhook from `org-b` previously created `Team` record with `github_id: 999, organization: "org-b"` (e.g., team "org-b/admins", which is listed in `Shipit.github_teams` for authorization).
3. Attacker, an owner of `org-a`, sends (or replays) a `membership` webhook to Shipit signed with `org-a`'s webhook secret:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker" }
}
```
4. `verify_signature` succeeds because it validates against `org-a`'s secret. `MembershipHandler#find_or_create_team!` finds the existing `Team(id=999, organization="org-b")` by `github_id` alone and calls `team.add_member(User.find_or_create_by_login!("attacker"))`, silently ignoring that the payload's `organization` is `org-a`.
5. `attacker`'s Shipit `User` is now a member of the `org-b/admins` `Team`, and `User#authorized?` returns true if `org-b/admins` is included in `Shipit.github_teams`, granting authenticated access intended only for `org-b` team members.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
