### Title
`StackStxOp::check` fails to reject `num_cycles == 0` (missing `return Err`) - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::check()` validates `num_cycles` with `if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES { warn!(...) }` but never returns an error from that branch, unlike the `stacked_ustx == 0` check two lines above which does `return Err(op_error::StackStxMustBePositive)`. This lets a burnchain `StackStxOp` with `num_cycles = 0` (or `> POX_MAX_NUM_CYCLES`) pass validation and be forwarded to the PoX locking logic.

### Finding Description
The broken equality: an accepted `StackStxOp.num_cycles` should always satisfy `1 <= num_cycles <= POX_MAX_NUM_CYCLES`, but the code allows `num_cycles == 0` (or values above the max) to pass `check()` unmodified.

Code path:
- `StackStxOp::parse_from_tx` -> `StackStxOp::parse_data` reads `num_cycles` from byte 16 of the op-return payload with no range validation: [1](#0-0) 
- `SortitionHandleTx::check_transaction` calls `op.check()` for `BlockstackOperationType::StackStx`, treating a non-`Err` result as "valid, proceed": [2](#0-1) 
- `StackStxOp::check` itself: the `stacked_ustx == 0` branch correctly returns an error, but the `num_cycles` branch only logs a warning and falls through to `Ok(())`: [3](#0-2) 

Attacker action: craft a Bitcoin `StackStxOp` op-return payload (following a valid `PreStxOp`) with `stacked_ustx` set to any positive amount and byte 16 (`num_cycles`) set to `0`. `parse_data` accepts it with no bound check, `check()` warns but returns `Ok(())`, and `process_checked_block_ops` will accept the op and pass it through to the PoX-4/PoX-5 stacking logic that consumes `num_cycles` to compute lock/unlock cycle counts.

Existing guards that fail: the only guard is the `check()` function itself, and it is missing the `return` statement, so there is no other validation layer (parse_data has no bound check either) that would block `num_cycles = 0` from reaching the reward-cycle/unlock-height computation in the PoX contracts.

### Impact Explanation
If a lock computed from `num_cycles = 0` reaches the contract layer with a zero-cycle commitment, it could either produce a no-op/zero-duration lock that still claims reward-cycle participation (unbacked commitment for zero duration), or corrupt unlock-height arithmetic (`current_cycle + num_cycles`) such that STX is locked but never scheduled to unlock — a permanent freeze of the sender's own STX. Both map to the Critical category ("permanent freezing of staked STX" / "unbacked... reward" per the rules). This affects only the sender's own funds (self-inflicted or attacker choosing to grief their own single stacking action) unless the resulting reward-slot claim over-counts relative to actual committed duration, which would need to be confirmed against the pox-4/pox-5 Clarity logic that consumes this value.

### Likelihood Explanation
Preconditions are minimal: any account with STX can send a `PreStxOp` followed by a `StackStxOp` with a hand-crafted op-return payload setting `num_cycles` to `0`. No privileged role, no contract deployment, and no reentrancy conditions are required. The cost is a Bitcoin transaction fee, and the bug is deterministic and repeatable per StackStxOp submitted.

### Recommendation
Add the missing `return Err(op_error::StackStxInvalidCycles)` (or equivalent existing error variant) in the `num_cycles` branch of `StackStxOp::check`, mirroring the `stacked_ustx == 0` branch, so that `num_cycles == 0 || num_cycles > POX_MAX_NUM_CYCLES` is rejected before the op is accepted into a block.

### Proof of Concept
Rust unit test in `stackslib/src/chainstate/burn/operations/stack_stx.rs`:
```rust
#[test]
fn test_check_rejects_zero_num_cycles() {
    let sender = StacksAddress::new(0, Hash160([0;20])).unwrap();
    let reward_addr = PoxAddress::Standard(sender.clone(), None);
    let op = StackStxOp::new(&sender, &reward_addr, 1000, 0, None, None, None);
    let res = op.check();
    assert!(res.is_err(), "num_cycles=0 must be rejected by check(), got {:?}", res);
}
```
Currently this assertion fails because `check()` returns `Ok(())`, confirming the missing `return`. A follow-up integration test would apply this op through the sortition DB (`check_transaction` in `processing.rs`) and then trace the corresponding `stack-stx` call into `pox-4.clar`/`pox-5.clar` to assert whether the resulting unlock-height equals or precedes the lock height, confirming the downstream freeze/zero-duration-commit impact — this downstream Clarity-side confirmation was not verified in this pass due to tool-call limits and would need a dedicated chainstate test.

    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
