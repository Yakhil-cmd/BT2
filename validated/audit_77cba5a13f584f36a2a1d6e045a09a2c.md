### Title
Stale liquidation-threshold snapshot keeps underwater accounts artificially solvent after governance tightens risk params - (File: contracts/controller/src/risk/params.rs)

### Summary
`AccountPosition` snapshots `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` at supply time, and the only resync path — `update_account_threshold` → `apply_gated_liquidation_params` — refuses to apply a liquidation-favoring update whenever the account's debt is non-zero and the new threshold would leave HF < 1.05. This mirrors the vesting-escrow bug class: a claim (here, solvency weight rather than voting weight) is computed from a stale balance/parameter snapshot that nothing can force to re-sync once the account deteriorates.

### Finding Description
Each supply position stores its own copy of the risk tuple. `refresh_supply_risk_params` always restamps `loan_to_value`, but the liquidation tuple only updates via `apply_gated_liquidation_params`, which returns early when `favors_liquidator(...)` is true, the account has debt, and `clears_min_hf` fails (`hf >= 1.05` under the *new* threshold).

Sequence an unprivileged borrower can ride:

1. Borrower supplies collateral and borrows; `position.liquidation_threshold` is snapshotted at, say, 80%.
2. Governance lowers the market's `liquidation_threshold` to 70% (ready-operation execute).
3. The borrower's real HF under the live 70% threshold drops below 1.0 — the position is economically liquidatable — but under the stale stored 80% threshold its computed HF sits in the band [1.0, 1.05).
4. Anyone (keeper, liquidator) calls `controller::update_account_threshold(caller, has_risks=true, [account_id])`. `apply_gated_liquidation_params` sees the change favors liquidators, `clears_min_hf` fails, and the stale tuple is kept. The final `hf >= 1.05` assert still passes because HF is computed *with the stale threshold*.
5. `liquidate` reads the stored `position.liquidation_threshold` in `calculate_account_risk_totals`, so the account reports HF ≥ 1.0 and liquidation reverts — indefinitely, since the only restamp path is self-blocking at exactly the HF band where it matters.

The escrow analog is direct: `stakedBalance` is never reduced after `recallUnvestedTokens` because the only correction runs on unstake; here `liquidation_threshold` is never reduced after a param tightening because the only correction gates itself on the very solvency metric it would change.

### Impact Explanation
Positions that are insolvent under current protocol risk parameters cannot be liquidated and continue to report a healthy HF. Borrowers retain borrowing capacity against a threshold governance explicitly removed, interest keeps accruing on uncollectible debt, and eventual `clean_bad_debt` socializes the enlarged loss across suppliers via the supply-index write-down. This is protocol-insolvency-adjacent value leakage borne by honest suppliers — the same "dishonest party keeps inflated weight at the community's expense" shape as the source report.

### Likelihood Explanation
Medium. Requires governance to tighten a listed asset's liquidation parameters *and* an account to sit in the HF band where the gate blocks the restamp — which is precisely the population of accounts such tightening is meant to reach. Once entered, the stuck state is permanent without further governance action, since `update_account_threshold` is permissionless yet self-defeating for these accounts.

### Recommendation
Split the gate so a *lowering* of `liquidation_threshold` can always be applied (it only makes the stored value more accurate), while keeping the HF ≥ 1.05 gate for changes that raise the threshold, raise fees, or lower the bonus. Alternatively, have liquidation and HF reads consume the live listed `liquidation_threshold` (with the stored tuple retained only as a borrower-protective ceiling), so no account can carry a permanently stale solvency snapshot.

### Proof of Concept
1. Alice supplies USDC and borrows so that HF = 1.04 under the stored `liquidation_threshold` of 8000 bps.
2. Governance executes a ready operation lowering USDC `liquidation_threshold` to 7000 bps; Alice's true HF becomes < 1.0.
3. Keeper calls `update_account_threshold(keeper, true, [alice_id])` → `apply_gated_liquidation_params` detects `favors_liquidator` (7000 < 8000), `clears_min_hf` computes HF with the 7000-bps hypothetical, gets < 1.05, returns early — stale 8000 bps persists; final HF assert passes against stale params.
4. Liquidator calls `liquidate(alice_id, ...)` → `calculate_account_risk_totals` uses stored 8000 bps → HF = 1.04 ≥ 1.0 → revert. Repeatable forever; the debt accrues into bad debt that `clean_bad_debt` later socializes onto USDC suppliers.

Note on confidence: this gating is deliberate in the code (documented as protecting borrowers from being pushed into liquidation by parameter changes), so a reviewer may classify it as an accepted design trade-off rather than a defect; the enduring, unrecoverable nature of the stale-threshold solvency inflation — and the fact the gate blocks *tightening* updates, not just loosening ones — is what makes it a credible analog worth reporting.
