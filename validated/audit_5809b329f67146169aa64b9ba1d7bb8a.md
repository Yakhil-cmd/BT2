### Title
Attacker-controlled `sender.login` is recorded as the actor archiving a victim's `ReviewStack` with no repository-permission check - ([File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb])

### Summary
`ClosedHandler#process` resolves the target repository/stack strictly from `params.repository.full_name`, but the "acting user" recorded on the archive transition comes from `params.sender.login` in the very same, single JSON body [1](#0-0) . Nothing binds `sender.login` to any authenticated GitHub identity or to the repository being mutated, so if a request is accepted at all (per the separately-assumed signature/provenance precondition), the archive is attributed to a completely attacker-chosen login. This is a real gap, but it is only reachable if the precondition ("attacker's org is validly signed") from the referenced provenance issue actually holds, which requires the attacker to know a `webhook_secret` accepted by this Shipit instance.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`archived_stack.audits.last.user.login == <a GitHub identity with authenticated write/collaborator rights on that stack's repository>` — but the code instead guarantees `archived_stack.audits.last.user.login == params.sender['login']` (attacker-controlled, unauthenticated, unrelated to the victim repository).

Path: `ClosedHandler#process` calls `review_stack.archive!` [2](#0-1) , `review_stack` is built by scoping `ReviewStackAdapter` to `repository.review_stacks`, where `repository` is looked up strictly via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) . `ReviewStackAdapter#archive!` then calls `stack.archive!(user)`, where `user` is lazily memoized as `Shipit::User.find_or_create_by_login!(params.sender["login"])` [4](#0-3) . There is no code anywhere in this path that checks `sender.login` against GitHub collaborator/team membership for the resolved `repository`, nor any correlation between `repository.full_name` and `sender.login`/`repository.owner.login`.

The only gate in front of this handler is `WebhooksController#verify_signature`, which selects the HMAC secret to validate against using `repository_owner` (`params.dig('repository','owner','login')`) [5](#0-4) [6](#0-5) , while the handler's repository resolution instead uses `params.repository.full_name` [3](#0-2) . Nothing in `verify_signature`, `GitHubApp#verify_webhook_signature` [7](#0-6) , or `ExplicitParameters` schema in `ClosedHandler` cross-checks that `repository.owner.login` (used to pick the secret) is consistent with `repository.full_name` (used to pick the stack to mutate) or with `sender.login`. If an attacker legitimately controls an organization/repo onboarded into this Shipit instance and therefore knows the webhook secret configured for their own org, they can craft a single POST body where `repository.owner.login` = their own org (so signature verification passes with a secret they know) but `repository.full_name` = a victim's repo/stack, and `sender.login` = any arbitrary string. This is exactly the "provenance bug" precondition assumed by the question. Given that precondition, this handler layer adds no further identity check, so the fabricated `sender.login` is what gets persisted as the actor on the victim's `Shipit::ReviewStack#archive!` transition.

### Impact Explanation
If the precondition holds, an attacker can archive (deprovision) any `ReviewStack` belonging to any repository configured in the same Shipit instance, with the audit/actor attribution poisoned to an attacker-chosen, fabricated `Shipit::User` login that has no relationship to the victim organization. This is a cross-tenant state mutation ("a payload for one repository mutating another's stack") attributed to a forged identity, matching the Critical impact category. The action is repeatable against any repository/environment name the attacker can guess or enumerate (`pr#{number}`), for as long as the attacker's own onboarded org/webhook credential remains valid.

### Likelihood Explanation
This finding's reachability is entirely contingent on the previously-identified provenance bug: the attacker must be an onboarded Shipit customer/org owner who legitimately knows their own org's `webhook_secret`, and must be able to send an HTTP POST directly to `/webhooks` (bypassing GitHub's actual webhook relay) with a crafted body whose `repository.owner.login` differs from `repository.full_name`. Without that precondition (i.e., if signature verification and repository resolution are ever made consistent, or if webhook secrets are never known to any org owner), this specific identity-binding issue is not independently reachable — the "attacker" in that case would be a legitimate, already-authorized sender for their own repository, and `sender.login` would correctly reflect a real GitHub actor on that repo. Given the audit's stated precondition, likelihood is high (single crafted HTTP request, no live GitHub interaction, no secrets beyond what the attacker already legitimately possesses for their own org).

### Recommendation
Enforce identity/repository binding at the handler level, not just the raw-body HMAC level:
1. Validate that `params.repository.full_name`'s owner matches `params.repository.owner.login` (and thus the org whose secret validated the signature) before doing any lookup or mutation.
2. Do not trust `sender.login` to create/attribute a `Shipit::User` without verifying repository-level authorization (e.g., check organization/team membership or collaborator status via the GitHub API for the resolved `repository`, or at minimum enforce equality between the org that signed the webhook and the org owning the resolved repository/stack).
3. Consider signing/verifying webhooks per-repository (not per-organization) if multiple orgs' secrets are shared within a single Shipit deployment scope.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/closed_handler_test.rb`) — cannot be fully written without confirming the provenance-bug precondition's exact reproduction path (which repo/config fixtures wire org→secret in this test suite), but the shape is:
```ruby
test "closed webhook attributes archive to attacker-controlled sender.login on a victim repo" do
  victim_repo = shipit_repositories(:shipit) # some existing victim repository fixture
  victim_stack = create_review_stack_for(victim_repo, pr_number: 42)

  attacker_org = "attacker-org"          # onboarded org whose secret the attacker knows
  # Precondition from the referenced provenance bug: signature computed with attacker_org's secret
  payload = {
    action: "closed",
    number: 42,
    pull_request: { ... head: { ref: "attacker-branch" } ... },
    repository: { full_name: victim_repo.github_repo_name, owner: { login: attacker_org } },
    sender: { login: "totally-fabricated-user" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", known_attacker_secret, payload)

  post "/webhooks", params: payload, headers: {
    "X-Github-Event" => "pull_request",
    "X-Hub-Signature" => signature,
    "Content-Type" => "application/json"
  }

  assert_response :ok
  victim_stack.reload
  assert victim_stack.archived?
  assert_equal "totally-fabricated-user", victim_stack.transitions.last.author&.login
end
```
Both sides of the equality to assert: expected `victim_stack.transitions.last.author.login` should equal a real, authorized GitHub identity for `victim_repo`; actual value equals the attacker-supplied `"totally-fabricated-user"`, confirming the identity-binding break — contingent on the provenance-bug precondition being independently demonstrated (cross-org signature/repo mismatch acceptance in `WebhooksController#verify_signature`).

          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do
              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end

          def user
            @user ||= Shipit::User.find_or_create_by_login!(params.sender["login"])
          end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
