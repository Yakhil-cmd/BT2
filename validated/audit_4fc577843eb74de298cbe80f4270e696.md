Based on my research, I found a plausible analog to the libcue-style out-of-bounds/unchecked structural array access. The bug class in the report is: **trusting an externally-supplied file/structure to have a specific shape and indexing deep into it without validating that shape first**, causing an out-of-bounds/undefined access. The closest reachable analog in ocore is in the arbiter-contract payout logic, which deep-indexes into a shared-address definition supplied by a paired peer device without verifying the peer's definition actually has that shape.

### Title
Unchecked deep array indexing into peer-supplied shared address definition causes fund freezing - ([File: arbiter_contract.js])

### Summary
`complete()` in `arbiter_contract.js` computes the final payout split for an arbiter contract by indexing several levels deep into the shared address definition object returned by `readSharedAddressDefinition`, assuming a fixed shape (`arrDefinition[1][index][1][1][1].amount`, `arrDefinition[1][index][1][2]`) that was only produced by the wallet's own composer at the time of contract creation. That shared address definition, however, is itself accepted from and can be shaped by the peer device via the generic shared-address protocol, and is only validated generically (as any legal boolean/signature address definition) by `definition.js`, not against this specific nested shape.

### Finding Description
`complete()` reads the shared multisig address definition and reaches into it with fixed offsets: [1](#0-0) 

This assumes the shared address was created exactly the way the local wallet's own contract-composer builds it (an `and`/`or` structure with a `has`/amount filter at a specific nested position). The shared address and its definition, however, originate from `wallet_defined_by_addresses.js`, which accepts and stores a `new_shared_address` definition sent by a paired peer device: [2](#0-1) . The only structural check performed on such a definition before use is the generic op-based validator in `definition.js`, which permits any well-formed boolean/signature/filter tree (`or`, `and`, `r of set`, `sig`, `has`, `sum`, `formula`, etc.) — it does not enforce that a `has`/amount clause exists at the exact nested position `[1][index][1][1][1]` that `complete()` assumes: [3](#0-2) .

Because a peer counterparty controls what definition is shared for the joint address that will hold the escrowed contract funds, a peer can supply an address definition that is fully valid per `definition.js` but has a different tree shape (e.g., a different number/order of `and`/`or`/`has` branches, or omits the `has` filter). When the local wallet later calls `complete()` to release funds, the fixed-offset indexing (`arrDefinition[1][index][1][1][1].amount`) will read `undefined` properties or throw a `TypeError`, and the subsequent `throw new Error(...)` for invalid amounts is thrown inside an asynchronous DB-row callback outside the enclosing `Promise`'s synchronous execution, so it becomes an unhandled exception rather than being caught by the `.catch()` at line 791: [4](#0-3) .

### Impact Explanation
An unhandled exception here crashes/aborts the payer's wallet process precisely at the moment it attempts to release the escrowed funds held in the peer-influenced shared address. Because `complete()` is the only code path that computes and sends the final split payment for a non-refund arbiter contract, a peer who supplies a definition of unexpected shape can permanently prevent the payer from ever completing the contract, freezing the funds held in the shared address (they can never be spent through the normal multisig-payout logic the wallet UI relies on). This matches the "AA/contract fund loss or freezing" impact class analogous to the memory-corruption/crash impact of the original libcue bug, translated to this codebase's payment-completion logic.

### Likelihood Explanation
Likelihood is moderate: it requires a device pairing and an active arbiter-contract negotiation with the victim, and the attacking peer must supply a shared-address definition whose top-level shape differs from what the wallet composer normally generates while still passing the generic `definition.js` validation (straightforward, since that validator is intentionally generic and permits many equivalent-looking boolean structures). No hub/node compromise or protocol-level exploit is needed — only participation as the counterparty in a private arbiter-contract flow.

### Recommendation
Before indexing into `arrDefinition` in `complete()`, explicitly validate that the shared address definition matches the exact expected shape produced by the wallet's own composer (verify each expected op at each nested position, e.g. that `arrDefinition[1][index][1][1][0] === 'has'` and that `.amount` fields exist) and reject/handle gracefully (return an error to the caller) rather than assuming the shape and letting a `TypeError`/thrown `Error` escape uncaught in an async callback. Additionally, wrap the definition-shape assumption check earlier in the contract flow (at shared-address creation/acceptance time) so a malformed contract shared address is rejected long before a payout is attempted.

### Proof of Concept
1. Peer device (attacker) negotiates an arbiter contract with victim wallet and, during shared-address setup, sends a `new_shared_address` definition whose `and`/`or` tree structurally differs from the standard 2-branch `[peer_output, arbstore_output]` layout the composer expects (e.g., reorders/removes the `has` amount filter) while still passing generic `definition.js` validation.
2. Victim wallet stores this shared address via `handleNewSharedAddress` (`wallet_defined_by_addresses.js:417-437`).
3. Contract proceeds to `paid` status; victim calls `complete()` in `arbiter_contract.js`.
4. `readSharedAddressDefinition` returns the peer-shaped definition; the fixed-offset access `arrDefinition[1][index][1][1][1].amount` (`arbiter_contract.js:755`) either yields `undefined` (causing the `throw new Error("invalid amounts...")` at line 757) or throws a `TypeError` directly — both escape the enclosing async DB callback uncaught, and the funds in the shared address are never released.
