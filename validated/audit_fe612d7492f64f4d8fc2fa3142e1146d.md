### Title
Webhook signature is verified against the GitHub organization named in `repository.owner.login`, but every event handler acts on the unrelated `repository.full_name` field of the same untrusted payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* per-organization `webhook_secret` to check the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body. [1](#0-0) [2](#0-1)  Once that org's secret happens to validate the signature (which it will, trivially, if the attacker is the one who *generated* the whole payload and signed it with a secret they legitimately know), the controller dispatches the full payload to the event handlers unchanged. [3](#0-2)  The handlers, however, never look at `repository.owner.login` again — they resolve the target `Stack`/`Repository` from a *different* field, `repository.full_name`, via `Handler#repository_name`. [4](#0-3)  Because the HMAC covers the raw body as a whole, the signature is technically "valid" for that body, but the value used to select the trust anchor (`owner.login`) and the value used to select the write target (`full_name`) are never cross-checked against each other, so the org whose secret authenticated the request and the repository actually acted upon can be made to diverge.

### Finding Description
Shipit explicitly supports being configured with multiple GitHub Apps/organizations in one deployment (`config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml` both document/exercise a `github: { OrgOne: {...}, OrgTwo: {...} }` layout, each org with its own `webhook_secret`). [5](#0-4) [6](#0-5) 

For every inbound webhook, `verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1)  Both values come straight from the attacker-controlled JSON body being verified — there is nothing external (e.g. a per-org URL/route or a fixed installation binding) tying the request to a specific org before the secret is chosen.

`verify_webhook_signature` is a straightforward HMAC-SHA1 comparison over `request.raw_post` using whatever secret was selected: `SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest('sha1', webhook_secret, message))`. [7](#0-6)  This means: if an actor legitimately controls one configured organization (e.g. they installed the shared Shipit GitHub App on their own org and thus know that org's `webhook_secret` — a normal, unprivileged administrative action on their own org, not a Shipit credential), they can construct an *arbitrary* JSON body, set `repository.owner.login` to their own org (so the signature-selection logic picks their known secret), sign the whole body with that secret, and set every other field — crucially `repository.full_name` — to point at a completely different, victim organization's repository that is also configured in the same Shipit instance.

Once `verify_signature` passes, `WebhooksController#create` does:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [3](#0-2) 

Handlers resolve their target purely from `repository.full_name`, ignoring `repository.owner.login` entirely:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler`, for example, then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack under that forged `full_name`/branch — with `after` (the SHA to sync to) also taken verbatim from the attacker's body. [8](#0-7)  `CheckSuiteHandler` similarly schedules check-run refreshes for commits on a victim stack chosen only via `full_name`/`head_branch`. [9](#0-8) 

**Binding broken (as equality):** the request is trusted to speak *for* `organization = repository.owner.login` (because that's the org whose secret validated the HMAC), but the engine actually performs writes/reads *for* `organization = owner(repository.full_name)`. Before the attack, these two are assumed equal by design (a webhook from OrgOne always describes an OrgOne repo). The attacker's crafted request breaks that equality: `repository.owner.login = "attacker-org"` (authenticates) while `repository.full_name = "victim-org/victim-repo"` (is written/acted upon), and nothing in the controller or in `Handler` re-validates that `full_name` actually belongs to the org that authenticated the request.

### Impact Explanation
This lets an actor who only administers one of several GitHub organizations configured on a shared Shipit instance trigger unauthorized actions against stacks/repositories belonging to a *different* organization they do not control, using Shipit's own GitHub App credentials for that victim org (Shipit's stored `installation_id`/private key for `victim-org`, not the attacker's). Concretely this can force `GithubSyncJob`/`stack.sync_github` to run with an attacker-chosen `expected_head_sha`, and can trigger `RefreshCheckRunsJob` and other org-scoped webhook side effects against the victim's stacks — an unauthorized cross-repository/cross-organization write path driven entirely by an unprivileged actor's control of an unrelated organization's webhook secret. This matches the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Requires: (1) the Shipit deployment to be configured for more than one GitHub organization (an explicitly documented and tested configuration shape), and (2) the attacker to control (as an ordinary GitHub org admin, not a Shipit credential holder) one of those organizations with the Shipit GitHub App installed, which is a normal, low-privilege action available to anyone who can create/administer a GitHub org and install a public/organization GitHub App. No Shipit session, `ApiClient` token, or GitHub App private key is needed — only knowledge of the webhook secret for the attacker's own org, which they legitimately possess. This is a realistic multi-tenant deployment scenario, not a theoretical one.

### Recommendation
After selecting the webhook secret via `repository_owner`, re-validate that every organization-identifying field actually used by the downstream handlers (`repository.full_name`'s owner segment, `organization.login` for org-level events, etc.) is consistent with the organization whose secret validated the signature, and reject the webhook (422) on mismatch. Alternatively, bind webhook verification to a per-organization route/endpoint (e.g. `/webhooks/:organization`) rather than deriving the trust anchor from a field inside the very payload being authenticated.

### Proof of Concept
1. Deploy Shipit with `github: { OrgOne: { webhook_secret: S1, ... }, OrgTwo: { webhook_secret: S2, ... } }`, mirroring the supported multi-org config. [5](#0-4) 
2. As an ordinary administrator, install the shared Shipit GitHub App on your own org `OrgOne` and obtain/know `S1` (a normal admin action on your own org).
3. Craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker_chosen_sha>",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
   }
   ```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(S1, body)` and POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` selects `Shipit.github(organization: "OrgOne")`, verifies successfully against `S1`, and the request is dispatched. [1](#0-0) 
6. `PushHandler#process` resolves stacks via `repository.full_name = "OrgTwo/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker_chosen_sha>")` on OrgTwo's stack, even though the signing organization was OrgOne. [8](#0-7) [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
