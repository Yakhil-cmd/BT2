The ALPINE-CVE-2019-8324 report describes a Ruby-specific flaw where RubyGems `eval`s a crafted gemspec "stub" line extracted from a maliciously crafted multi-line gem name during `ensure_loadable_spec`'s preinstall check — i.e., an interpreter `eval`ing attacker-controlled string data as code. Polkadot SDK has no equivalent code path: chain-spec/genesis parsing uses `serde_json` deserialization rather than any `eval`-like mechanism [1](#0-0) , and metadata/name resolution in the omni-node runtime inspector only does SCALE decoding and string comparisons, never code evaluation [2](#0-1) . Untrusted code execution paths that do exist (PVF WASM execution, contracts/revive bytecode) are handled through sandboxed, verified-bytecode execution models with explicit unsafe-contract documentation and pre-execution validation, not string-to-code evaluation of user-supplied names [3](#0-2) [4](#0-3) . Since Rust/FRAME extrinsic dispatch, XCM, and contract call paths never `eval` attacker-supplied identifiers/strings as executable code, there is no demonstrable analog to the RubyGems gemspec-stub `eval` injection in this codebase.

///   2) was not modified,

pub unsafe fn execute_artifact(
	compiled_artifact_blob: &[u8],
	executor_params: &ExecutorParams,
	params: &[u8],
) -> Result<Vec<u8>, ExecuteError> {
	let mut extensions = sp_externalities::Extensions::new();

	extensions.register(sp_core::traits::ReadRuntimeVersionExt::new(ReadRuntimeVersion));

	let mut ext = ValidationExternalities(extensions);

	match sc_executor::with_externalities_safe(&mut ext, || {
		let (semantics, _) = params_to_wasmtime_semantics(executor_params);
		let runtime = create_runtime_from_artifact_bytes(compiled_artifact_blob, executor_params)?;
		runtime
			.new_instance(semantics.heap_alloc_strategy)?
			.call("validate_block", params)
	}) {
		Ok(Ok(ok)) => Ok(ok),
		Ok(Err(err)) | Err(err) => Err(err),
	}
}
