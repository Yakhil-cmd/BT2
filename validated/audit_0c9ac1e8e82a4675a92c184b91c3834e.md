### Title
Denial of Service via uncaught exception in address checksum validation - (File: chash.js)

### Summary
`chash.isChashValid()` is called by `validation_utils.isValidChash()` / `isValidAddress()` on every attacker-controlled address string that appears in a posted unit (author addresses, output addresses, definition addresses, data-feed oracle addresses, AA trigger/definition addresses, etc.). For 32-character candidates it base32-decodes the string and then processes the result without validating that the decoded buffer actually has the expected bit-length, so a crafted address string can make an internal helper throw an uncaught `Error` instead of returning `false`.

### Finding Description
`isChashValid(encoded)` only wraps the `base32.decode(encoded)` / `Buffer.from(encoded,'base64')` call in a `try/catch`: [1](#0-0) 

After decoding, it calls `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` outside of any exception handling: [2](#0-1) 

`separateIntoCleanDataAndChecksum` explicitly `throw`s when the decoded bit-length is not exactly 160 or 288: [3](#0-2) 

The `thirty-two` base32 decoder does not guarantee that every 32-character input string decodes to exactly 20 bytes (160 bits) — inputs using characters outside the strict base32 alphabet, unusual padding, or edge-case lengths can decode to a buffer of a different byte length without the earlier `try/catch` catching anything (decode itself doesn't throw, it just returns an oddly-sized buffer). When that happens, `buffer2bin` produces a bit string whose length is not 160/288, and `separateIntoCleanDataAndChecksum` throws `"bad length=..."`. This exception is never caught by `isChashValid`, `isValidChash`, or `isValidAddress`, so it propagates up through `validation.js`'s address checks during unit validation — an unhandled exception in the node process during processing of an untrusted, attacker-supplied unit.

This is directly analogous to CVE-2019-5020: a specially crafted input drives an internal invariant/assert-like check (`separateIntoCleanDataAndChecksum`'s length check) into a state its author assumed could never occur, and the resulting `throw`/assert failure is not gracefully handled, causing a crash/DoS rather than a controlled validation failure.

### Impact Explanation
`isValidAddress`/`isValidChash` is invoked pervasively during unit and AA validation wherever an address-shaped string appears (authors, outputs, definitions, `in data feed`/`in_data_feed` oracle lists, etc.), all of which are populated directly from attacker-controlled joint/unit content. An uncaught exception thrown mid-validation of a broadcast unit can crash the validating process (full node, hub, or AA-processing node) rather than simply rejecting the unit, i.e., a network unable to confirm new units / node crash DoS from a single posted, unprivileged unit.

### Likelihood Explanation
Reachable trivially by any unprivileged party who can post a unit or joint containing a 32-character address-like field. No special privileges, MITM, or hub compromise are required — this is a pure input-validation gap in a hot, universally-invoked address-format checker.

### Recommendation
Wrap the entire body of `isChashValid` (not just the decode step) in a `try/catch`, returning `false` on any exception (including the "bad length" throws from `separateIntoCleanDataAndChecksum`/`mixChecksumIntoCleanData`), so that malformed but structurally valid base32/base64 strings are treated as an invalid c-hash instead of crashing validation. Alternatively, explicitly verify `chash.length` equals the expected byte count (20 for 160-bit, 36 for 288-bit) immediately after decoding and return `false` early if not.

### Proof of Concept
Conceptual PoC (cannot execute code in this environment, so this is a description of the expected crash path rather than a verified run):
1. Construct a 32-character string that is accepted by the `thirty-two` library's decoder but does not decode to exactly 20 bytes (e.g., a string using lower-case/mixed characters or trailing characters the decoder tolerates loosely, producing a truncated or padded output buffer).
2. Call `chash.isChashValid(payload)` directly, or embed the string as an `address` field of a unit's `authors`/`outputs`/definition and submit it to `validation.js` for processing.
3. Because `separateIntoCleanDataAndChecksum` receives a bit-string whose length is not 160, it throws `Error("bad length=...")`, which is not caught anywhere in the `isChashValid` → `isValidChash` → `isValidAddress` → unit-validation call chain, resulting in an uncaught exception during validation of the untrusted unit.

Note: I was not able to fully verify the exact byte-length tolerance/lenience of the vendored `thirty-two` decoder implementation within the indexed codebase (its source was not returned by search), so the precise malformed-string construction needed to trigger the mismatched decode length is unconfirmed and would need to be validated experimentally (e.g., via a Devin session with full repo/dependency access) before treating this as a confirmed exploit rather than a code-path analysis.
