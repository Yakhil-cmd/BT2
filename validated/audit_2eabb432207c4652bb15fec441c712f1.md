### Title
Silent floating-point overflow in `total_cap_from_denominations` check allows fixed-denomination assets to declare a false `cap` - (File: validation.js)

### Summary
`validateAssetDefinition()` computes the total capped supply of a fixed-denomination asset by summing `count_coins * denomination` for every declared denomination and comparing the result against the asset's declared `cap`. Both operands of the multiplication are validated only with `isPositiveInteger()`, which does not bound the values to a range safe for JavaScript's IEEE-754 double arithmetic. An attacker can choose `denomination` and `count_coins` pairs whose product exceeds `Number.MAX_SAFE_INTEGER`, causing the running sum `total_cap_from_denominations` to silently lose precision, exactly analogous to the unsafe `uint256`→`int256` cast described in the reference report: the check `payload.cap !== total_cap_from_denominations` can pass even though the true mathematical total of mintable coins is completely different from the declared `cap`.

### Finding Description
In `validation.js` (`validateAssetDefinition`), the per-denomination cap accumulation is: [1](#0-0) 

`denomInfo.denomination` and `denomInfo.count_coins` are only checked with `isPositiveInteger()`, which enforces integrality and positivity but not an upper bound tied to `Number.MAX_SAFE_INTEGER` (2^53−1). The `denomination > constants.MAX_CAP` bound is even conditionally skipped when the asset is not yet past the `pemCurvesFixMci`/retrievable-mci window: [2](#0-1) 

Critically, `count_coins` is never bounded by `MAX_CAP` at all. Because JavaScript numbers use double-precision floats, `count_coins * denomination` and its running sum in `total_cap_from_denominations` silently round once results exceed `Number.MAX_SAFE_INTEGER` — there is no exception, no wraparound detection, just rounding to the nearest representable double. This mirrors the C4 report's root cause: a value that legitimately doesn't fit the target numeric representation is used in an arithmetic/comparison operation without a safety check, producing a "different value than what should really be."

The `count_coins` per denomination is the actual enforced supply limit at issuance time — `validateIndivisibleIssue()` requires `input.amount === denomination * count_coins` for each capped denomination row stored in `asset_denominations`: [3](#0-2) 

So the real maximum issuable supply of the asset is the (unrounded) sum of `denomination_i * count_coins_i` across all denominations, independent of what `payload.cap` claims.

### Impact Explanation
An asset definer (an unprivileged unit poster who defines an asset — squarely in the reachable "asset issuance and transfer conditions" surface) can craft a `denominations` array where individual `denomination * count_coins` products, and/or their running sum, overflow double precision such that the rounded `total_cap_from_denominations` collides with an attacker-chosen `payload.cap` value, even though the real, per-denomination-enforced maximum supply (checked later via `asset_denominations.count_coins` at issue time) is vastly larger or otherwise inconsistent with the declared cap.

This deceives every downstream consumer of the `cap` field — wallets, exchanges, and AAs that read `asset[asset_id].cap` via the oscript/AA formula engine to reason about total supply — while the true mintable total (bounded only by the sum of `denomination * count_coins`, honored at issuance) can be effectively unbounded. This is a supply-integrity/asset-definition-forgery bug: it lets the definer make the network's own consensus-validated cap accounting internally inconsistent, which can be leveraged to mislead counterparties trusting the declared cap (e.g., in AA-based trading, DEX, or accounting logic keyed off `cap`), a concrete supply-inflation-style deception reachable purely from posting an ordinary `asset` definition unit.

### Likelihood Explanation
Triggering this requires only posting a standard `asset` definition message with `fixed_denominations: true` and a handful of `denominations` entries — an action any regular user (unprivileged unit poster / asset issuer) can perform without special privileges. Constructing colliding float products (`denomination * count_coins`) that sum to a chosen `cap` after IEEE-754 rounding is a solvable numerical search problem, well within reach of an attacker with off-chain computation. No node collusion, timing, or race condition is needed — the flaw is a straightforward validation-logic defect. Likelihood is Medium: it requires deliberate construction of specific numeric values but no other constraint.

### Recommendation
- Bound `denomInfo.count_coins` (not just `denomination`) by `constants.MAX_CAP` unconditionally (not gated behind the `pemCurvesFixMci` legacy compatibility branch), consistent with how `payload.cap` itself is bounded.
- Perform the `count_coins * denomination` multiplication and the running sum using an overflow-safe arithmetic path (e.g., `Decimal.js`, as already used elsewhere in the formula evaluator with explicit `isFinite`/precision checks), or explicitly verify `total_cap_from_denominations <= Number.MAX_SAFE_INTEGER` after each addition and reject the unit if it is exceeded.
- Reuse the existing `isFiniteDecimal`/`toDoubleRange` safety pattern from `formula/evaluation.js` for this consensus-critical accumulation rather than raw JS arithmetic.

### Proof of Concept
1. Craft an `asset` definition message with `fixed_denominations: true` and `denominations` containing entries, e.g., `{denomination: d1, count_coins: c1}`, `{denomination: d2, count_coins: c2}`, where `d1*c1` and `d2*c2` are each below `MAX_CAP` individually (passing the per-field `isPositiveInteger`/`MAX_CAP` checks that only apply to `denomination`, not `count_coins`), but chosen such that their exact sum computed in double precision rounds to a value equal to an attacker-chosen `payload.cap` (e.g., using values near `2^53` where adding two large near-equal numbers loses low-order bits).
2. Set `payload.cap` to that rounded value; the check at [4](#0-3)  passes because `total_cap_from_denominations === payload.cap` in floating point, even though the mathematically exact total (and thus the true maximum issuable supply per [5](#0-4) ) differs from `payload.cap`.
3. The asset is accepted by consensus with a `cap` field that misrepresents the true enforced supply ceiling from the per-denomination `count_coins` rows, which is what actually gates issuance.
