### Title
Unbounded synchronous recursion in address/asset definition evaluation causes stack-overflow DoS - (File: definition.js)

### Summary
`validateDefinition()`/`evaluate()` in `definition.js` recursively walks an address or asset spending-condition definition (`and`, `or`, `r of set`, `weighted and`, `address`) using plain synchronous JS recursion (`async.eachSeries` with synchronous callbacks), guarding only against total node *complexity*/`count_ops`, never against recursion *depth*. This is the same bug class as CVE-2024-37280 (Elasticsearch passthrough mapping): a deeply nested/self-referential structure walked with unbounded recursion causes a native stack overflow before any resource limiter fires. [1](#0-0) [2](#0-1) 

### Finding Description
`evaluate(arr, path, bInNegation, cb)` increments `complexity`/`count_ops` and checks them against `constants.MAX_COMPLEXITY`/`constants.MAX_OPS`, but it never tracks or bounds the *depth* of the call stack the way sibling validators do:
- `formula/validation.js`'s `evaluate()` explicitly tracks `depth`, rejects with `"maximum depth exceeded"` past 100, and periodically calls `setImmediate` every 100 iterations specifically "to avoid extra long call stacks to prevent Maximum call stack size exceeded". [3](#0-2) 
- `aa_validation.js`'s `validate()` similarly enforces `MAX_DEPTH = 100` and interrupts every 100 calls with `setImmediate`. [4](#0-3) 

`definition.js`'s `evaluate()` (used for ordinary address definitions, asset issue/transfer conditions, and re-evaluated on every spend via `validateAuthentifiers`) has neither protection — it only checks `complexity`/`count_ops`, which are node counters, not depth counters: [5](#0-4) 

A chain such as `['and', [ ['sig', {...}], ['and', [ ['sig', {...}], ['and', [...]] ] ] ] ]` nested to depth *N* increments `complexity` by roughly 1 per level (well within `MAX_COMPLEXITY`), while it consumes *N* real JS stack frames of `evaluate` plus the enclosing `async.eachSeries` iterator closures — a strictly deeper/heavier call chain per unit of `complexity` than what triggered the explicit interrupt-every-100 protections added to the formula and AA-definition validators. Because `evaluate` here is invoked directly (not deferred through `setImmediate`), the whole chain unwinds synchronously in one native stack, and can be built well past whatever depth the runtime's stack can hold, since `MAX_COMPLEXITY` bounds *total ops*, not the shape/depth of the tree.

This same unguarded recursive-`evaluate` pattern is re-entered every time an address/asset condition is checked against signed inputs via `validateAuthentifiers`, meaning the crash is triggered not just at definition-time but on every future spend from that address/asset. [6](#0-5) 

### Impact Explanation
An attacker can post a single unit that defines a new address (or an asset issue/transfer condition) with a deeply/linearly nested `and`/`or`/`r of set` boolean tree. When any full node validates this unit — and again every time a spend from that address/asset is subsequently validated — the recursive, depth-unbounded `evaluate()` walk can exhaust the V8 call stack and crash the node process (`RangeError: Maximum call stack size exceeded`), which in Node.js is typically unrecoverable for the process. Because every node in the network independently validates the same unit and the address's subsequent spends, this is a network-wide denial-of-service: nodes crash while attempting to confirm the unit, preventing confirmation/validation of new units referencing the malicious address.

### Likelihood Explanation
The attack requires only posting a normal unit containing a new address definition or an asset definition with a crafted, deeply nested boolean-condition tree — reachable by any unprivileged unit poster / address owner / asset issuer, with no special privileges, hub cooperation, or peer compromise needed. The size of a single unit's `definition` payload only needs to encode a chain of two-element `and`/`or` arrays, which is compact (a handful of bytes per nesting level), so building enough depth to overflow the stack within normal message-size limits is plausible.

### Recommendation
Add an explicit depth counter to `evaluate()` in `definition.js` (mirroring `MAX_DEPTH` in `aa_validation.js`) and reject definitions/conditions once a fixed depth (e.g., 100) is exceeded, independent of the complexity/op counters. Alternatively/additionally, interrupt the recursion periodically (e.g., every N calls) via `setImmediate`/`process.nextTick` as already done in `formula/validation.js` and `aa_validation.js`, so a long, thin chain cannot consume the native call stack in one synchronous burst.

### Proof of Concept
Construct an address definition (or asset `issue_condition`/`transfer_condition`) as a linear chain of nested `and` operators, e.g. (conceptually):
```
["and", [
  ["sig", {"pubkey": "<32-byte base64 pubkey>"}],
  ["and", [
    ["sig", {"pubkey": "<32-byte base64 pubkey>"}],
    ["and", [ ... repeated to depth N ... ]]
  ]]
]]
```
Post a unit defining a new address with this definition (or an asset with this as its `issue_condition`). `validateDefinition()`'s `evaluate()` in `definition.js` will recurse synchronously to depth *N* while `complexity`/`count_ops` stay low; choosing *N* large enough (well below `MAX_COMPLEXITY`/`MAX_OPS`, but beyond the JS engine's stack-frame budget for this closure-heavy recursive function) crashes the validating node's process with a stack overflow.
