## Analog Found

### Title
Missing bound on the number of inputs collected by an AA when spending funds - ([File: aa_composer.js])

### Summary
The reported bug is a **missing sanity check on an array/loop length that is populated from externally-controlled data**, causing a downstream operation (the VRF callback loop) to become unboundedly expensive and fail, permanently blocking the intended fund transfer. The same bug class exists in ocore's Autonomous Agent (AA) payment-composition logic: the routine that gathers unspent outputs to use as payment inputs for an AA-generated unit has no upper bound on how many outputs/inputs it may accumulate, because the two safety limits that normally prevent this (`MAX_INPUTS_PER_PAYMENT_MESSAGE` and the unit-size cap) are explicitly disabled for AA units.

### Finding Description
When validating a payment message, ocore normally rejects a payload whose `inputs` array exceeds `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128). However, this check is explicitly skipped for AA-generated units: [1](#0-0) 

Likewise, the overall unit-size cap (`MAX_UNIT_LENGTH`) is bypassed for AA units in the general unit-structure check: [2](#0-1) 

and again, with only a time-boxed (mci-gated) re-introduction, in the parent-validation path: [3](#0-2) 

The actual loop that gathers inputs for an AA-composed payment is `iterateUnspentOutputs`, invoked from `completePaymentPayload` inside `sendUnit` in the AA composer. It walks every row returned from `readStableOutputs`/`readUnstableOutputsSentByAAs` (i.e., every unspent output previously sent to the AA address) and keeps pushing them into `payload.inputs` until the target amount is reached, with **no cap on the number of iterations/inputs**: [4](#0-3) 

This is called for every payment message the AA composes when it needs to spend or return funds (bounce, regular response, or `send_all` output): [5](#0-4) 

Because any unprivileged unit poster can send arbitrarily many tiny-value ("dust") payments to an AA address (payments are normal unit messages, subject only to the ordinary per-unit output limits, not to any limit on the total number of *distinct* payments an address may receive over time), an attacker can inflate the count of unspent outputs belonging to that AA to an arbitrary size. When the AA subsequently needs to construct a response that spends (or sends-all) its balance, `iterateUnspentOutputs`/`completePaymentPayload` will attempt to consume all of these dust outputs as inputs, producing a payload with a number of inputs far beyond `MAX_INPUTS_PER_PAYMENT_MESSAGE` and a unit size far beyond `MAX_UNIT_LENGTH` — checks that would reject such a unit for an ordinary wallet-composed unit, but are silently skipped here because `objValidationState.bAA` is true.

This mirrors exactly the missing-sanity-check root cause of the external report: an array whose length is driven by attacker-supplied data is processed in a loop that is not gated by an appropriate limit, causing a downstream operation (union: forming/validating/executing the response unit) to become excessively expensive or to fail outright.

### Impact Explanation
An attacker can trigger this from a single posted unit (or a burst of them) that pays dust amounts to a target AA address, with no privileged access required. The resulting oversized response unit:
- Incurs an exponentially growing oversize fee (`storage.getOversizeFee`), which can exceed the AA's actual balance and force a `bounce`, meaning legitimate triggers can no longer be serviced (denial of funds availability / AA operation), and
- Even where it does not bounce, produces the AA response as an abnormally large unit that skips the standard anti-spam sizing safeguards, degrading node processing and potentially breaking downstream assumptions that rely on `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_UNIT_LENGTH` bounds for AA-authored units.

This falls squarely under "AA fund loss or freezing" — users interacting with the affected AA can have their triggers permanently unable to be honored, analogous to the original report where users' card NFTs could never be delivered.

### Likelihood Explanation
Likelihood is medium: any address can send funds to any AA address at will and cheaply (small dust payments cost little), so building up a large number of unspent outputs against a target AA is inexpensive and requires no special permission — it can be done incrementally over time by any unit-posting party, matching the "unprivileged unit poster" reachability constraint.

### Recommendation
Enforce a bound on the number of inputs (and/or a running size cap) that `completePaymentPayload`/`iterateUnspentOutputs` in `aa_composer.js` is allowed to accumulate for AA-generated payment messages, instead of only relying on the post-hoc oversize fee. Equivalently, do not exempt AA units from `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_UNIT_LENGTH` validation in `validation.js` (lines 2137, 267, 744) without an actively enforced alternative cap at input-selection time in `aa_composer.js`, so dust-flooding an AA address cannot force it into unserviceable, oversized response units.

### Proof of Concept
1. Attacker repeatedly posts minimal-value `payment` units sending dust (e.g., 1–1000 bytes) to a target AA address `A`, accumulating thousands of tiny unspent outputs owned by `A`.
2. A legitimate user sends a trigger to `A` that causes it to send a `send_all`/full-balance response (or any payment whose amount forces consumption of many small inputs).
3. `sendUnit` → `completePaymentPayload` → `iterateUnspentOutputs` (`aa_composer.js:1102-1137`) walks and consumes all the dust outputs as inputs, since the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check is bypassed for AA units (`validation.js:2137`).
4. The resulting response unit is abnormally large; its `oversize_fee` may exceed the AA's balance, causing the AA to `bounce` and fail to service the trigger, or the unit construction/propagation degrades due to its size — reproducing the "unable to receive intended asset due to unbounded loop lacking a sanity check" failure mode of the original report.
