### Title
Webhook signature verification authenticates by `repository.owner.login` but stack resolution uses the unrelated `repository.full_name` field, letting a payload signed for one org inject an arbitrary `after` SHA into another org's stack via `PushHandler` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `params.dig('repository','owner','login')`, an attacker-controlled JSON field, while every handler (including `PushHandler`) resolves the target stack using a completely separate field, `payload.dig('repository','full_name')`. Because nothing ties these two fields together, a request that is validly signed for "org A" can carry a `full_name` naming "org B/victim-repo," causing `PushHandler#process` to call `stack.sync_github(expected_head_sha: params.after)` on a stack that does not belong to the authenticating organization.

### Finding Description
Broken binding (stated as an equality that should hold but doesn't):
`repository_owner (used to pick webhook_secret in verify_signature)` MUST equal `owner segment of repository.full_name (used to resolve the target Repository/Stack in Handler#stacks)`. In this codebase they are read from two independent, both attacker-controlled, JSON fields with no cross-validation.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from the raw JSON body and looks up the secret for that org: `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that org's `webhook_secret`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` performs a plain HMAC comparison over the *entire* raw body using that org's secret; it does not (and cannot) check that any other field of the same body actually belongs to that org. Notably it also unconditionally passes when the org has no `webhook_secret` configured: `return true unless webhook_secret`. [3](#0-2) 
3. `Shipit.github` supports multiple independently configured organizations (each with its own secret), confirming a multi-tenant deployment model is a first-class, supported configuration. [4](#0-3) 
4. Once the signature is accepted, `Handler#stacks` resolves the target stack from a *different* field of the same payload: `payload.dig('repository', 'full_name')`, fed into `Repository.from_github_repo_name`. [5](#0-4) [6](#0-5) 
5. `PushHandler#process` uses that resolved stack scope, filters by `branch` (also attacker-controlled via `ref`), and calls `stack.sync_github(expected_head_sha: params.after)` where `after` is a fully attacker-controlled SHA with no relation to any commit approved for that repository. [7](#0-6) 

Exploit: An attacker who legitimately controls (or onboarded) some org "attacker-org" known to this Shipit instance — and therefore knows or can trivially satisfy its `webhook_secret` (including the case where that org's secret is unset, which auto-passes verification) — crafts a raw JSON body:
```json
{
  "ref": "refs/heads/<victim-branch>",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
and POSTs it to `/webhooks` with `X-Github-Event: push` and a valid `X-Hub-Signature` computed with `attacker-org`'s secret. `verify_signature` passes because it only checks the signature against `attacker-org`'s secret over this exact body — it never checks that `attacker-org` actually owns `victim-org/victim-repo`. `PushHandler#process` then resolves the real victim stack via `full_name` and invokes `sync_github(expected_head_sha: params.after)` with the attacker's SHA.

Why existing guards fail: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate "this body was signed with org X's secret" — they never scope which repositories the body is allowed to reference. `drop_unhandled_event`, `ExplicitParameters` schema (`requires :ref, :after`, both permissive `String` types), and `Repository.from_github_repo_name` perform no ownership cross-check against the signing org. `force_github_authentication`/`User#authorized?`/`require_permission!` are session/API-token controls that don't apply to the unauthenticated `/webhooks` endpoint at all.

### Impact Explanation
A forged/crafted webhook validly signed for one organization can cause `sync_github` to run against a completely unrelated victim organization's stack with an attacker-chosen `expected_head_sha`, seeding downstream sync/deploy logic with data the victim organization never approved. This is exactly the listed Critical impact category: "a payload for one repository mutating another's stack." It is repeatable against any stack whose repository/branch name the attacker can guess or discover, for every push received, and the blast radius spans all tenants/organizations configured on a shared Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must control (or have legitimately onboarded) at least one organization known to this Shipit instance's `github` config, or that organization's `webhook_secret` must be unset (auto-pass path in `GitHubApp#verify_webhook_signature`). In a single-tenant deployment with one org and a properly set webhook secret, this is not directly exploitable by an outsider since they'd need that org's secret. In any multi-tenant/multi-org deployment (explicitly supported per `lib/shipit.rb#github_app_config` and `test/dummy/config/secrets_double_github_app.yml`), a legitimate but unprivileged tenant admin can carry out this attack against any other tenant's stack at will, at zero marginal cost per request, fully repeatable.

### Recommendation
After successfully verifying the signature for `repository_owner`, additionally verify that the owner segment of `payload.dig('repository','full_name')` (and/or `organization.login`) matches `repository_owner` before dispatching to any handler; reject the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` strictly through the same organization key that was used to select the verifying secret, rather than trusting `full_name` independently.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest)
test "push webhook signed for org A cannot sync a stack under org B" do
  # victim stack belongs to "victim-org/victim-repo"
  victim_stack = shipit_stacks(:shipit) # repository.full_name == "victim-org/victim-repo", branch == "master"

  forged_payload = {
    "ref" => "refs/heads/#{victim_stack.branch}",
    "after" => "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef", # attacker-chosen, unrelated SHA
    "repository" => {
      "owner" => { "login" => "attacker-org" },       # used by verify_signature
      "full_name" => "victim-org/victim-repo"          # used by Handler#stacks / PushHandler
    }
  }.to_json

  # Simulate attacker knowing (or bypassing, if unset) attacker-org's webhook secret
  Shipit.stubs(:github).with(organization: "attacker-org")
        .returns(stub(verify_webhook_signature: true))

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = 'sha1=whatever-matches-attacker-org-secret'

  Shipit::Stack.any_instance.expects(:sync_github)
    .with(expected_head_sha: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef")

  post :create, body: forged_payload, as: :json
  assert_response :ok
end
```
Equality asserted before: `repository_owner ("attacker-org")` != `owner segment of repository.full_name ("victim-org")`. Equality asserted after: the code proceeds to call `sync_github` on `victim_stack` anyway, proving the binding is never enforced.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
