## Finding: Reused L1 lockup proofs let a staker register the same Bitcoin UTXO for multiple pox-5 bonds without ever re-locking BTC

### Title
Missing global replay protection and liveness check for L1 lockup outpoints lets a staker double-credit the same BTC lock across `register-for-bond` calls - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 path (`verify-l1-lockups` → `validate-l1-lockup`) credits `sats-total` for a Bitcoin output purely from a Merkle-inclusion proof, header check, and script-hash match. Deduplication of `(txid, output-index)` pairs (`seen-outpoints`) is only tracked *within a single fold call*, never persisted in contract state, and there is no check that the timelock's `unlock-burn-height` is still in the future (i.e., that the BTC is still actually locked). This allows the same already-spent/expired L1 lockup proof to be resubmitted in a later `register-for-bond` call to fabricate `sats-total` with no new BTC ever being locked.

### Finding Description
`register-for-bond` computes the sats amount for the L1 path via: [1](#0-0) 

which dispatches to `verify-l1-lockups`, which folds over the caller-supplied outputs using `validate-l1-lockup`: [2](#0-1) 

`validate-l1-lockup` checks the block header, script hash, output amount, an *in-call-only* `seen-outpoints` list for duplicates within the same list of outputs, and a Merkle proof of inclusion — but it never checks against any persisted contract state for outpoints used in *previous* transactions, and it never asserts that `unlock-burn-height` (or the current burn height vs. it) implies the BTC is still time-locked as of *now*: [3](#0-2) 

Grepping the whole contract confirms there is no map persisting used L1 outpoints (e.g., `used-l1-outpoints`) anywhere in `pox-5.clar` — the only outpoint tracking is the transient `seen-outpoints` accumulator reset on every call.

The sats credited by this proof directly drives `sats-total`, which becomes both `amount-sats` in `protocol-bond-memberships`, the per-cycle bond/signer share totals, and the minimum required STX lock: [4](#0-3) 

Because `roll-sbtc` only moves actual sBTC token balance and is a no-op on the L1 path (`new-sbtc` is `u0`), no real value transfer ever validates that the Bitcoin is still locked — the sole "backing" for `sats-total` is the same replayable Merkle proof: [5](#0-4) 

The repository's own integration tests demonstrate the exact scenario that breaks the equality: a staker locks BTC via a timelock P2WSH, later sweeps it back off the timelock once `unlock-burn-height` passes, and the same lockup proof material remains structurally valid (correct header, correct Merkle path, correct script) forever after — nothing in `validate-l1-lockup` ties validity to whether the coins are still actually locked: [6](#0-5) 

### Impact Explanation
An unprivileged staker can:
1. Lock BTC once into a valid timelock output and call `register-for-bond` for bond N, crediting `sats-total` sats.
2. Wait for the bond to reach its L1 unlock window and sweep the real BTC out of the timelock back to themselves (a normal, permitted action).
3. Later call `register-for-bond` again for a new bond M with the *same* Merkle proof for the same (already-spent) output — the proof still verifies (block header/Merkle inclusion/script hash are all historical facts that don't change), so `sats-total` is credited again with zero new BTC actually locked.

This produces `protocol-bonds-total-staked`/`total-sbtc-staked`-equivalent sats accounting, signer delegation weight, and reward shares that exceed the BTC genuinely locked, letting the staker earn sBTC rewards and pox-5 signing weight backed by nothing. This is a double-counting of a stacking commitment and an unbacked reward/signing-weight condition — matching the "High: signing weight or reward slots exceeding locked value" / "double-counting a commitment" categories.

### Likelihood Explanation
Likelihood is Medium-to-High: it requires no privileged role, no signer/bond-admin/pause key, and no exploitation of Clarity-VM or secp256k1 internals — only a normal staker replaying a proof they already legitimately obtained once, after the natural sweep step that other tests in this same file explicitly exercise and document as expected behavior. It's reachable purely through the public `register-for-bond` entrypoint.

### Recommendation
Persist a durable record of consumed L1 outpoints (e.g., a `define-map used-l1-outpoints {txid, output-index} bool`) that `validate-l1-lockup` checks and updates on every successful credit, independent of any single call's transient list, so the same physical BTC output can never be credited more than once across the contract's lifetime. Additionally, consider requiring proof that the output is still unspent as of the current burn height (or bounding validity to `unlock-burn-height` not yet reached) rather than relying solely on historical inclusion proofs.

### Proof of Concept
1. Staker locks 1,000,000 sats into a valid pox-5 timelock P2WSH script for bond 0 and calls `register-for-bond(0, ..., Ok(outputs=[proof_for_utxo_A]), ...)`. `sats-total = 1,000,000` is credited, and the corresponding STX minimum is locked.
2. Mine past bond 0's `unlock-burn-height`; the staker submits the OP_IF sweep transaction (as in `check_pox_5_register_for_bond_l1_early_unlock_lifecycle`/the `sweep_info` test) and recovers the 1,000,000 sats to a wallet-controlled address on Bitcoin — the L1 collateral is gone.
3. A new bond (say bond 7) opens its setup window. The staker calls `register-for-bond(7, ..., Ok(outputs=[proof_for_utxo_A]) /* identical Merkle proof from step 1 */, ...)`.
4. `validate-l1-lockup` re-verifies the (still historically valid) header/Merkle proof/script hash for `proof_for_utxo_A` and credits `sats-total = 1,000,000` again — with no new BTC locked anywhere — since `seen-outpoints` only guards duplicates within this one call's output list, and no contract-level map rejects an outpoint already used in the prior call for bond 0.
