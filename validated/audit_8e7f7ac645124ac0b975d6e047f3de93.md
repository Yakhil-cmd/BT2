### Title
Forged `pull_request` webhook via organization fallback + blank `webhook_secret` bypasses signature verification and lets `LabelCapturingHandler` mutate an arbitrary repository's `PullRequest` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization used to validate `X-Hub-Signature` from `repository_owner`, which falls back to `params.dig('organization','login')` whenever the payload's `repository.owner.login` is absent, while `LabelCapturingHandler` independently derives the repository to mutate from `params.repository.full_name`. Because `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected organization has no `webhook_secret` configured, an attacker who knows of any configured-but-secretless (or attacker-controlled-secret) organization can point `organization.login` at it while pointing `repository.full_name` at a victim repo, causing the request to pass verification and mutate the victim's `PullRequest` labels.

### Finding Description
The broken binding is: *the organization whose credentials verified the request* (`repository_owner` in [1](#0-0)  used inside `verify_signature` at [2](#0-1) ) *must equal* the organization that owns the repository the handler writes to (`params.repository.full_name`, read at [3](#0-2) ).

`repository_owner` reads `params.dig('repository','owner','login')` first, but falls back to `params.dig('organization','login')` whenever that path is missing — the comment explicitly states this is meant for payloads where `repository` isn't included at all, but the code only checks the `owner.login` sub-path, not whether `repository` itself is present. An attacker can therefore supply a payload that has a `repository` object (required by the handler's `ExplicitParameters` schema, `requires :repository do requires :full_name, String end`) but omits `repository.owner`, plus a separate top-level `organization.login` naming a different org.

`Shipit.github(organization: repository_owner)` then resolves the GitHub App config for whatever organization the attacker named in `organization.login` (`lib/shipit.rb#github` / `#github_app_config`), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unset (`return true unless webhook_secret`, [4](#0-3) ). Multi-org deployments are documented as normal and webhook_secret is explicitly optional/nil per `docs/setup.md` and `config/secrets.development.example.yml`.

Once verification passes, `Shipit::Webhooks.for_event('pull_request')` dispatches to handlers including `LabelCapturingHandler`, which resolves `repository` purely from `params.repository.full_name` (independent of `repository_owner`), looks up the `stack`/`review_stack` for that repo, and on `unlabeled_active_stack?` calls `capture_labels`, persisting `pull_request.update!(labels: params.pull_request.labels.map(&:name))` — mutating a `PullRequest` record belonging to whatever repo `repository.full_name` names, regardless of which org's key verified the signature.

Existing guards fail to prevent this because: `verify_signature` never cross-checks that `repository_owner` matches `repository.full_name`'s owner; `drop_unhandled_event` only checks the event type is handled, not the payload's internal consistency; the `ExplicitParameters` schema for the handler validates types/presence, not owner consistency with the organization used for signing; and `GithubOrganizationUnknown` is only raised if the named organization isn't configured at all, not if its `webhook_secret` is blank.

### Impact Explanation
An attacker who can identify any Shipit-configured GitHub organization with a blank/unset `webhook_secret` (a documented, supported configuration state) can forge a `pull_request`/`unlabeled` (or `labeled`/`reopened`) webhook naming an arbitrary victim repository in `repository.full_name`, causing `LabelCapturingHandler` to overwrite that repository's review-stack `PullRequest#labels`. Since `ReviewStack#env` uppercases label names into environment variables consumed at deploy/build time, this is a cross-tenant/cross-repository write into another team's stack state without holding that org's `webhook_secret` — matching the "payload for one repository mutating another's stack/commit/task" Critical impact category. The attack is repeatable against any repository/stack as long as such an org exists in the deployment's `secrets.github` config.

### Likelihood Explanation
This requires a specific but plausible operator misconfiguration: a multi-organization Shipit deployment (`github_default_organization` non-nil) where at least one configured organization has no `webhook_secret` set, as shown to be a supported/example configuration in `docs/setup.md` and `config/secrets.development.example.yml`/`config/secrets.development.shopify.yml`. If Shipit runs in single-org mode (`github_default_organization` nil), `repository_owner`'s value is irrelevant to which config is used (`@github[organization] ||= GitHubApp.new(organization, config)` always uses the single `secrets.github` config), so the divergence has no verification-bypass effect in that mode — the vulnerability is specific to the multi-org configuration path with a secretless org. Attacker cost is a single crafted HTTP POST with no valid signature required against the secretless org's path.

### Recommendation
In `WebhooksController#verify_signature`, require that `repository.owner.login` (or an equivalent authoritative owner field checked against `repository.full_name`) be used for signature-organization selection, and reject payloads where `repository` is present but `repository.owner.login` is missing rather than silently falling back to `organization.login`. Additionally, require `webhook_secret` to be non-blank for all configured organizations (or fail verification rather than bypassing it) in `GitHubApp#verify_webhook_signature`. Finally, have handlers verify that the repository they act on belongs to the same organization/login that was used to authenticate the request.

### Proof of Concept
minitest plan (`ActionDispatch::IntegrationTest` or controller test, no live GitHub):
1. Configure `secrets.github` with two orgs: `"attacker-org"` with `webhook_secret: nil`, and `"victim-org"` with a real `webhook_secret`.
2. Create fixtures: a `Shipit::Stack`/review stack under `victim-org/repo` with an associated `PullRequest` whose `labels` are `[]`.
3. Build a JSON body for a `pull_request` event, `action: "unlabeled"`, with:
   - `organization: { login: "attacker-org" }`
   - `repository: { full_name: "victim-org/repo" }` (no `owner` key)
   - `pull_request: { ..., labels: [{ name: "malicious-label" }] }`
4. POST to `/webhooks` with `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature` (no valid HMAC for either org's secret).
5. Assert response is `200 OK` (not `422`), proving `verify_signature` accepted the request via the `attacker-org` (secretless) path — i.e., assert `repository_owner` resolved to `"attacker-org"` while `params.repository.full_name` is `"victim-org/repo"` (the two values differ, breaking the claimed invariant).
6. Assert `victim_pull_request.reload.labels == ["malicious-label"]`, proving the handler mutated the victim org's record despite the request being authenticated (trivially, due to blank secret) against a different, attacker-named organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
