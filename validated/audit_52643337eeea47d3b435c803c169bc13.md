## Title
Final-bad unit propagation never resets `outputs.is_spent`, permanently freezing/losing the original owner's stable balance - (File: `main_chain.js`)

### Summary
When a spending unit is later found to be a losing side of a double-spend and gets `sequence='final-bad'`, the stabilization code in `main_chain.js` clears the input's uniqueness flag but never resets `outputs.is_spent` back to `0` on the output that unit had (invalidly) claimed to spend. The output row is left permanently marked as spent even though its only claimed spender no longer exists as a valid transaction, exactly mirroring the H-22 pattern where a per-key state flag (`_isLiquidation`) set during one lifecycle event is never cleared when that lifecycle event is invalidated/reversed, causing the legitimate owner to lose access to funds/refunds that should be theirs.

### Finding Description
In `markMcIndexStable()` → `propagateFinalBad()`, once a unit is determined to be `final-bad` (e.g. the losing side of a serial/nonserial conflict resolved at stabilization), the code cascades this status to any descendant unit that spent an output of the final-bad unit: [1](#0-0) 

This block updates `units.sequence='final-bad'` and sets `inputs.is_unique=NULL` for the descendant spending units so that they are "treated as non-existent competitors from now on." However, it never issues a corresponding `UPDATE outputs SET is_spent=0` for the outputs that these now-invalidated spending units had marked as spent when they were first written by `saveJoint()`: [2](#0-1) 

Because `outputs.is_spent` is only ever set to `1` when a unit is saved (never conditioned on that spender's eventual `sequence`), and `propagateFinalBad` only touches `units.sequence` and `inputs.is_unique`, the `is_spent=1` flag on the original output becomes permanently stale/incorrect once its only spender is retroactively invalidated. Any code that queries balances via `is_spent=0 AND sequence='good' AND is_stable=1` (the standard, most common balance-calculation pattern used throughout the codebase, e.g. `aa_composer.js`'s `checkBalances()` and the voting balance logic) will silently omit these outputs forever, even though no valid unit actually spends them.

This is exactly the H-22 root cause pattern: a boolean/flag tied to a specific instance (`is_spent` tied to a specific claimed spend) is set during one lifecycle event but is never cleared when that lifecycle event is subsequently invalidated (the spender becomes `final-bad`), so future logic keyed on that flag makes the wrong decision and the rightful owner loses access to value that should be theirs.

The bug class is independently confirmed by an internal diagnostic tool that was added specifically to detect this discrepancy: [3](#0-2) [4](#0-3) 

The tool's own comments state plainly: "A difference means the OLD method undercounts a voter's balance because a future unstable unit spent their stable output and was later propagated to final-bad, leaving is_spent=1 on the output while no good unit claims it in spent_rows."

### Impact Explanation
Any address whose stable output is spent by a unit that later turns out to be the losing side of a double-spend (a normal, reachable DAG event — any user can post a conflicting/nonserial unit) will have that output permanently marked `is_spent=1` in the database, even though the "spend" is void. Every downstream consumer that relies on the standard `is_spent=0`-based balance query (wallet balances, `system_vote`/governance vote-weight calculations, and potentially AA-adjacent balance checks) will undercount or entirely omit that output, i.e., the legitimate owner's funds become effectively frozen/lost from their computed balance, without any way for the owner to recover recognition of that value through normal wallet flows. This is a concrete funds-freezing condition arising from node disagreement between the DB-persisted `is_spent` flag and the true, current validity state of the unit graph.

### Likelihood Explanation
Double-spends (a unit spending an output that is also spent by a conflicting unit) are a normal, permissionless part of the protocol — any single user can trigger this path by posting two conflicting units from an address they control (or by a light client re-sending an existing chain), so no privileged network position is required. The condition triggers deterministically whenever main-chain stabilization resolves such a conflict and the losing unit is propagated to `final-bad`.

### Recommendation
In `propagateFinalBad()` (and the analogous unstable-unit handling), whenever a spending unit is set to `sequence='final-bad'`, also reset `is_spent=0` on the outputs it (invalidly) claimed via its `inputs.src_unit/src_message_index/src_output_index` — mirroring the `is_unique=NULL` reset that is already performed on the `inputs` side — so the original output again reflects the correct, unspent state usable by balance and voting calculations.

### Proof of Concept
1. Address A receives a stable output O (`is_stable=1`, `sequence='good'`, `is_spent=0`).
2. A posts two conflicting units, U1 and U2, both spending O (a double-spend fork). Whichever is initially accepted marks O as `is_spent=1` on write (per `writer.js` addInlinePaymentQueries logic).
3. During main-chain stabilization, `findStableConflictingUnits`/`handleNonserialUnits` determines U1 is the loser and sets its `sequence='final-bad'`; if any further descendant unit had spent U1's own (invalid) outputs, `propagateFinalBad()` cascades `final-bad` to it and clears `inputs.is_unique`, but O's `outputs.is_spent` row (set to `1` when U1 was originally saved) is never reset to `0`.
4. Any subsequent balance query using the standard pattern `SELECT SUM(amount) FROM outputs ... WHERE is_spent=0 AND is_stable=1 AND sequence='good'` permanently excludes O from address A's balance, even though U1 is void — as demonstrated by the discrepancy the `tools/compare_vote_balances.js` script was written to detect between the old (`is_spent`-based) and new (existence-of-good-spender-based) balance calculation methods.

	const bal_rows = await db.query(`
		SELECT address, SUM(amount) AS balance
		FROM outputs
		LEFT JOIN units USING(unit)
		WHERE address IN(${strAddresses}) AND is_spent=0 AND asset IS NULL AND is_stable=1 AND sequence='good'
		GROUP BY address`);

	const balances = {};
	for (const { address, balance } of bal_rows)
		balances[address] = balance || 0;

	const spent_rows = await db.query(`
		SELECT inputs.address, SUM(outputs.amount) AS spent_balance
		FROM units
		CROSS JOIN inputs USING(unit)
		CROSS JOIN outputs ON src_unit=outputs.unit AND src_message_index=outputs.message_index AND src_output_index=outputs.output_index
		CROSS JOIN units AS output_units ON outputs.unit=output_units.unit
		WHERE units.is_stable=0 AND +units.sequence='good'
			AND +output_units.is_stable=1 AND +output_units.sequence='good'
			AND inputs.address IN(${strAddresses}) AND type='transfer' AND inputs.asset IS NULL
		GROUP BY inputs.address`);

	for (const { address, spent_balance } of spent_rows) {
		if (balances[address])
			balances[address] += spent_balance;
		else
			balances[address] = spent_balance;
	}

	return balances;
}
