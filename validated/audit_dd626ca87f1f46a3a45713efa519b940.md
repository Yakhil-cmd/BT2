### Title
`pending_delegator_rewards` on vote accounts is never decremented after block-reward distribution, causing repeated over-distribution of the same reward pool - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The vote program's `pending_delegator_rewards` field (SIMD-0123) tracks fees owed to delegators that a vote account has collected but not yet distributed. This field is incremented every time a fee is deposited to the vote account (via `deposit_fees`/`deposit_delegator_fees`), and is used every epoch as the numerator to calculate each staker's share of the block reward. However, no code path in the codebase ever decrements or resets `pending_delegator_rewards` after it has been distributed to stakers, which is structurally identical to the reported `vault.move` bug: a counter that grows on issuance but is never adjusted when the corresponding claim is consumed/paid out, producing a permanent and compounding accounting mismatch.

### Finding Description
`pending_delegator_rewards` is incremented in two places when fees/deposits arrive at a vote account: [1](#0-0) [2](#0-1) 

Every epoch, `calculate_block_reward` reads the vote account's *current* `pending_delegator_rewards()` value and uses it as the numerator to compute each delegator/staker's proportional share of the reward, minted directly into the staker's stake account: [3](#0-2) 

This computed `block_reward` is then added to the staker's account balance during distribution: [4](#0-3) 

A grep across the entire codebase for any function that subtracts, resets, or clears `pending_delegator_rewards` (e.g. `decrement_pending_delegator_rewards`, `sub_pending_delegator_rewards`, `clear_pending_delegator`) returns **zero matches**. The only mutator found is `add_pending_delegator_rewards`: [5](#0-4) 

This mirrors the reported bug exactly: `share_to_creator` shares were minted to the creator's `Position` without incrementing `vault.total_shares`, permanently inflating the share/asset ratio. Here, `pending_delegator_rewards` is the "claim pool" that vote-account fee deposits create, and it is read every epoch as the basis for minting new staker rewards, but the pool itself is never reduced by the amount already paid out. Each subsequent epoch's `calculate_block_reward` call re-uses the *same, undiminished* `pending_delegator_rewards` value (plus any newly accrued deposits) as the reward numerator, so the same funds get counted — and minted as new stake-account lamports — repeatedly across epochs.

### Impact Explanation
Because `calculate_block_reward` mints new lamports into stake accounts (`checked_add_lamports(block_reward)`) based on a `pending_delegator_rewards` value that is never reduced, the protocol will re-distribute (and effectively re-mint) rewards derived from the same fee pool epoch after epoch. This is unsigned/uncollateralized fund creation: stakers receive lamports that are not backed by a corresponding one-time debit from the vote account or a decrement of the pool that justified them. Over time this compounds, corrupting stake/reward accounting cluster-wide and diverging real vote-account lamports from the rewards being paid — the same insolvency mechanism described in the reference report, but manifesting as unauthorized reward inflation rather than vault underfunding.

### Likelihood Explanation
`pending_delegator_rewards` accrues automatically from ordinary transaction fee flow (`custom_commission_collector`/`block_revenue_sharing` features) and from the `DepositDelegatorRewards` vote instruction, both of which are reachable by any unprivileged transaction sender paying fees or depositing to a vote account. The reward-calculation path (`calculate_block_reward` → `redeem_delegation_rewards`) runs automatically every epoch for every active vote account with delegators, so the missing-decrement condition is triggered continuously and deterministically by normal cluster operation, not by a rare or adversarial sequence.

### Recommendation
After `calculate_block_reward` is used to compute and distribute a delegator's share, decrement the source vote account's `pending_delegator_rewards` by the amount actually distributed (mirroring how `distributed_rewards` is tracked in the `EpochRewards` sysvar), so that the pool used for reward accrual reflects only funds that have not yet been paid out.

### Proof of Concept
1. A vote account accrues `pending_delegator_rewards = 1000` from deposited fees (`deposit_delegator_fees`, `runtime/src/bank/fee_distribution.rs:296-326`).
2. At epoch N, `calculate_block_reward` computes and distributes rewards to stakers proportional to `pending_delegator_rewards = 1000` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:172-228`), minting lamports into stake accounts (`distribution.rs:262-267`).
3. No code anywhere decrements `vote_state.pending_delegator_rewards` (confirmed via exhaustive grep for decrement/reset/clear functions — zero matches).
4. At epoch N+1, if no new fees are deposited, `calculate_block_reward` reads the *same* `pending_delegator_rewards = 1000` from the vote account and distributes another full round of rewards to stakers, minting additional lamports not backed by any new fee collection — repeating indefinitely every epoch the vote account remains active.

**Uncertainty:** I was unable to fully confirm, within available search iterations, whether some other mechanism (e.g., a separate lamport debit from the vote account tied to `block_reward_lamports_distributed`) implicitly caps or reconciles this pool elsewhere in the reward-distribution pipeline. The absence of any explicit decrement/reset function for `pending_delegator_rewards` across the entire codebase is the strongest available evidence for this finding, but a full trace of every lamport movement in `distribute_epoch_rewards_in_partition` and related sysvar bookkeeping could not be completed in the remaining iterations.

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {
        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
