### Title
Unchecked `P2PStakingInfo.BlockNum` in `commitFastSyncData` Allows Remote Peer to Corrupt Staking DB at Arbitrary Block — (`datasync/downloader/downloader.go`)

### Summary
During fast sync, a malicious P2P peer can supply a `P2PStakingInfo` whose `BlockNum` field is set to any arbitrary value `M`, while the corresponding header has `Number = N`. `commitFastSyncData` blindly uses `result.StakingInfo.BlockNum` as the DB write key, so `PutStakingInfoToDB(M, ...)` writes attacker-controlled staking data to DB slot `M`, not `N`.

### Finding Description [5](#0-4) 

There is no assertion that `result.StakingInfo.BlockNum == result.Header.Number` (or equals the expected staking-update block for that header). The same flaw exists in `commitPivotBlock`: [6](#0-5) 

`stakingInfoPack` carries a raw list of `*staking.P2PStakingInfo` from the peer: [7](#0-6) 

`DeliverStakingInfos` accepts these from any connected peer without authenticating the `BlockNum` field: [8](#0-7) 

### Impact Explanation
The staking DB is the authoritative source for validator sets and reward distribution. `ReadStakingInfo(M)` is called by the staking module to determine which validators are active and what their staking amounts are for epoch calculations. Writing attacker-controlled node addresses, staking amounts, and reward addresses to an arbitrary historic block `M` corrupts validator selection and reward accounting for that epoch. If `M` is a currently-active staking epoch block, the synced node will use wrong validator/reward data going forward — constituting consensus divergence and corrupted reward distribution.

### Likelihood Explanation
Any node that connects as a P2P peer during fast sync can trigger this. Fast sync accepts staking info from any peer. No special privileges, keys, or majority collusion are required — just a crafted RLP-encoded `P2PStakingInfo` message with a chosen `BlockNum`.

### Recommendation
Before calling `PutStakingInfoToDB`, validate that `result.StakingInfo.BlockNum` equals the expected staking-update block number for `result.Header.Number` (i.e., the last staking interval boundary ≤ `Header.Number`). If they do not match, drop the peer and skip the write.

### Proof of Concept
1. Craft a `fetchResult` where `Header.Number = N` but `StakingInfo.BlockNum = M` (M ≠ N, e.g., a past staking epoch block).
2. Populate `StakingInfo` with attacker-controlled `CouncilNodeAddrs`, `CouncilStakingAmounts`, `CouncilRewardAddrs`.
3. Pass this `fetchResult` to `commitFastSyncData`.
4. Assert `ReadStakingInfo(db, M)` returns the attacker-controlled data.
5. Assert `ReadStakingInfo(db, N)` is empty (the legitimate entry was never written).

The staking module will subsequently use the corrupted entry at `M` for validator set and reward calculations for that epoch.
