### Title
Cross-tenant `Status` write via global (non-repository-scoped) `Commit.where(sha:)` lookup enables unauthorized `Stack#trigger_continuous_delivery` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves commits solely by `sha`, with no scoping to the repository that authenticated the webhook, then calls `commit.create_status_from_github!` on every match. A legitimately signed `status` webhook from an attacker-owned repository (Org B) can therefore write a `Status` onto a `Commit` belonging to a completely unrelated stack (Org A) whenever the two commits share a SHA, which then flips `deployable?` and drives `ContinuousDeliveryJob` to call `Stack#trigger_continuous_delivery` on Org A's stack.

### Finding Description
The broken binding: `commit.stack.repository == payload['repository']` (i.e., "the status only applies to the commit belonging to the repo that sent the webhook") is claimed to hold, but it does **not**.

Code path:
1. `WebhooksController#verify_signature` at `app/controllers/shipit/webhooks_controller.rb:24-38` only verifies that the payload is genuinely signed by the GitHub organization named in `params['repository']['owner']['login']` (`repository_owner`, line 59-62). It never checks that the SHA in the payload actually belongs to that repository — it can't, because GitHub's signature only proves "this org sent this payload," not "this SHA lives only in this org's repo."
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries the `Commit` table by `sha` alone, across **all stacks/tenants**, with no `stack_id`/repository filter. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then writes a real `Status` row scoped to `commit.stack_id` — i.e., Org A's stack — using data taken from Org B's webhook payload.
3. `Commit` has no uniqueness constraint or repository binding on `sha` (`app/models/shipit/commit.rb:1-90`); the `by_sha`/`by_sha!` scope (`app/models/shipit/commit.rb:92-103`) even raises `AmbiguousRevision` if two commits share a SHA, confirming SHA collisions across stacks are an anticipated (if rare) possibility, not defended against here.
4. If the resulting status makes the shared commit `deployable?` (`app/models/shipit/commit.rb:227-229`), the existing `ProcessMergeRequestsJob`/`schedule_continuous_delivery` flow and `ContinuousDeliveryJob#perform` → `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`) will pick `next_commit_to_deploy` for Org A and call `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)`, ultimately spawning a real deploy task for Org A with no Org A actor involved.

The attacker's action: repeatedly push deterministic no-op/empty commits to their own repo (identical tree, parents, author/committer identity and timestamp) until one collides in SHA with the specific commit Org A's stack is waiting on, then let GitHub emit a genuine, correctly signed `status` webhook for that push. This requires zero Shipit credentials — only ownership of a GitHub repo whose webhook is configured to notify the shared Shipit host (the attacker's own, legitimately configured repo/App installation).

Existing guards fail because:
- `verify_signature` validates the sender's organization identity, not the SHA-to-repository binding.
- `drop_unhandled_event`/`ExplicitParameters` schema (`requires :sha`, `:state`, etc.) validate shape, not tenant scope.
- No model validation ties `Commit#sha` uniqueness or the incoming status event to `commit.stack.repository`.

### Impact Explanation
An attacker-controlled, cross-tenant write lands on Org A's `Commit`/`Status` records and can flip `deployable?` for a commit Org A did not yet approve for deploy, causing `Stack#trigger_continuous_delivery` to invoke `trigger_deploy` → `Command#start`/`PTY.spawn` for Org A's deploy pipeline, entirely from a webhook authenticated only for Org B. This is an unauthorized deploy execution driven by a payload from one repository mutating another repository's stack/commit state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The blast radius extends to any Shipit stack whose pending commit's SHA the attacker manages to collide with, and is repeatable per target commit.

### Likelihood Explanation
Preconditions: Org A's stack must have `cached_deploy_spec` present and a specific commit pending deployment; that exact commit content (tree/parents/author/committer/date/message) must be reproducible by the attacker in their own repository to get an identical SHA (feasible for deterministic/no-op commits, e.g., automated merge or empty commits with fixed metadata — explicitly called out as "reproducible deterministically, not requiring a cryptographic break"). The attacker needs their own GitHub repo with a webhook pointed at the shared Shipit host — a normal, unprivileged setup. No Shipit secrets, sessions, or API tokens are required. Feasibility depends heavily on how deterministic and predictable Org A's next commit's exact metadata is to an outside attacker; in the generic case this is a targeted, non-trivial precondition, but the code path itself has no defense once the SHA collision exists.

### Recommendation
Scope the status lookup to the reporting repository, not just SHA: in `StatusHandler#process`, join/filter `Commit` through `stack.repository` matching `params['repository']['full_name']` (or the equivalent field already available in the webhook envelope) before calling `create_status_from_github!`. More generally, any handler that resolves records purely by `sha` (`status_handler.rb`, `check_run` handlers, etc.) should also constrain by the repository identity asserted in the payload, since `sha` alone is not a reliable tenant boundary.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_tenant_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "a status webhook only updates commits belonging to the reporting repository" do
          org_a_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
          colliding_sha = "deadbeef" * 5

          org_a_commit = org_a_stack.commits.create!(
            sha: colliding_sha,
            message: "no-op",
            author: shipit_users(:shipit),
            committer: shipit_users(:shipit),
            authored_at: Time.now,
            committed_at: Time.now
          )

          # Payload as if it came from an attacker's own repository (Org B),
          # correctly signed for Org B, referencing the colliding SHA.
          params = ActionController::Parameters.new(
            sha: colliding_sha,
            state: 'success',
            context: 'ci/attacker',
            repository: { full_name: 'attacker/evil-repo', owner: { login: 'attacker' } }
          )

          assert_no_difference -> { org_a_commit.statuses.count } do
            Shipit::Webhooks::Handlers::StatusHandler.new(params).process
          end
          # FAILS today: StatusHandler.process finds org_a_commit purely by sha
          # and writes an attacker-controlled Status onto it, with
          # commit.stack == org_a_stack proving the cross-tenant write, even
          # though params[:repository][:full_name] != org_a_stack.repository.full_name.
        end
      end
    end
  end
end
```
Binding under test, before/after: `commit.stack.repository.full_name` (expected `"shopify/shipit-engine"`) vs `params['repository']['full_name']` (`"attacker/evil-repo"`) — they differ, yet `StatusHandler#process` still writes the status, proving the tenant boundary is not enforced.     def self.by_sha(sha)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (too short)" if sha.to_s.size < 6

      commits = where('sha like ?', "#{sha}%").take(2)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (matches multiple commits)" if commits.size > 1

      commits.first
    end

    def self.by_sha!(sha)
      by_sha(sha) || raise(ActiveRecord::RecordNotFound, "Couldn't find commit with sha #{sha}")
    end
