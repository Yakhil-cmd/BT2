### Title
Reused Bitcoin L1 lockup outpoints can double-count `sats` in bond stake shares — (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s `verify-l1-lockups` / `validate-l1-lockup` functions credit a staker with `amount-sats` for every Bitcoin UTXO lockup output supplied in a `register-for-bond` call, after checking a Merkle proof and timelock script. Duplicate-outpoint protection (`seen-outpoints`) is implemented as a **fold accumulator that is re-initialized to an empty list on every call** [1](#0-0) , rather than being checked against a contract-persisted set of previously-consumed outpoints. A repo-wide search for any global "consumed"/"used" lockup registry (`consumed-lockup`, `used-lockup`, `l1-lockup-registry`, `outpoint-consumed`) returned no matches in `pox-5.clar`, indicating no cross-call persistence of spent outpoints exists.

### Finding Description
`validate-l1-lockup` verifies, for a single Bitcoin output: the timelock script matches the staker/unlock height, the Merkle proof is valid, and the outpoint hasn't been seen **within the current call's list** [2](#0-1) . The `sum` of validated `amount` fields is returned as the total sats credited to the staker for that bond registration [3](#0-2) .

Because the dedup set (`seen-outpoints`) is created fresh in `verify-l1-lockups`'s initial fold accumulator and never intersected with any contract-stored, cross-transaction record of previously-credited outpoints, the same Bitcoin lockup transaction/output can be re-submitted as proof in a **second, independent call** to `register-for-bond` (e.g. for a different `bond-index`, or after `unstake`/rollover into a new bond period) and will pass all `asserts!` checks again, crediting `amount-sats` a second time. This breaks the equality that bond/staker sats-share accounting (`total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`, `staker-shares-staked-for-cycle` — all keyed by `bond-index`, see `add-staker-to-bond-for-cycle` at [4](#0-3) ) should equal actual BTC locked on-chain.

### Impact Explanation
Bond sats-shares (`total-sats`) directly drive `calculate-bond-rewards`'s `target-yield = (total-sats * target-rate) / 10000 / 50`, which is paid out of the contract's real sBTC reward pool [5](#0-4) . If a staker can re-present the same L1 lockup output to register into a second bond slot, they double their credited `amount-sats` without a matching second BTC lockup, letting them draw a disproportionate, unbacked share of `sBTC` bond rewards from the reward pool that legitimate bond participants would otherwise receive — a double-counting of a Bitcoin-lockup commitment. This is a Critical-class impact under the given rubric ("double-counting a commitment or reward").

### Likelihood Explanation
Exploitability depends only on the attacker controlling a valid, timelocked BTC UTXO once and being able to invoke `register-for-bond` twice (different bond indices, or via `unstake`+re-register with different `bond-index` while presenting the same historical proof) before I could confirm the full `register-for-bond` public entrypoint's guard logic. I was not able to fully read that entrypoint within the available iterations to rule out an additional, higher-level check (e.g., a per-outpoint global map maintained outside `pox-5.clar`, in `pox-locking/src/pox_5.rs`, or an implicit restriction tying a lockup script to exactly one bond via the `staker-unlock-bytes`/`early-unlock-bytes` construction). This is a material gap in verification.

### Recommendation
Persist consumed outpoints in a contract-level map (e.g., `l1-lockup-consumed { txid, output-index } -> bool`) that is checked and set inside `validate-l1-lockup` regardless of which call or bond the proof is submitted under, so the same Bitcoin lockup output can never be credited more than once across the contract's lifetime.

### Proof of Concept
Not independently executed; based on static review of `verify-l1-lockups`/`validate-l1-lockup` showing the dedup accumulator is local to a single call, and the absence of any repo-wide persisted "used lockup" registry. A concrete PoC would require confirming `register-for-bond`'s full body (not fully retrieved) and demonstrating two separate transactions submitting the identical `{tx, output-index, header, leaf-hashes, ...}` lockup tuple, each successfully incrementing `total-shares-staked-for-cycle`/`staker-shares-staked-for-cycle` for a bond.

**Caveat:** Due to tool/iteration limits, I could not retrieve and verify the complete `register-for-bond` public function body or the `pox-locking/src/pox_5.rs` glue code, which may contain an additional guard not visible in the excerpts reviewed. This finding should be treated as a lead requiring confirmation against those files before being considered conclusively proven.

;; Verify l1 lockup information for a staker. This asserts that each lockup
;; corresponds to the right timelock script for this staker, and that the lockup
;; occurred on-chain. If everything is valid, this returns the sum of all lockups in sats.
(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)

        (accumulator-res (response {

            last-bond-stx-value-ratio: (optional uint),
            ;; Used as a tie-breaker in the case of bonds with the same
            ;; stx-value-ratio
            last-bond-index: (optional uint),
            ;; How much rewards are available to be distributed
            available-rewards: uint,
            calculation-height: uint,
            reward-cycle: uint,
        }
            uint
        ))
    )
    (let (
            (accumulator (try! accumulator-res))

            (total-sats (get-total-shares-staked-for-cycle reward-cycle (some bond-index)))
            (available-rewards (get available-rewards accumulator))
            ;; How much sBTC the bond is supposed to earn per calculation,
            ;; which is (totalSats * apy) / 50
            (target-yield (/ (/ (* total-sats (get target-rate bond)) u10000) u50))

            ;; this bond gets the remaining rewards.
