## Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-App configurations, `WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`), but every event handler that acts on the payload resolves the target `Stack`/`Repository` from the independent, unchecked `repository.full_name` field. Nothing binds these two fields together, so a party who legitimately controls one onboarded organization's webhook secret can forge a validly-signed payload whose `owner.login` matches their own org while `full_name` points at a completely different (victim) org's repository.

### Finding Description
`WebhooksController#verify_signature` derives the GitHub App/secret to check against solely from the requester-controlled payload: [1](#0-0) [2](#0-1) 

`Shipit.github_app_config` looks the secret up per-organization key in a multi-org secrets schema: [3](#0-2) 

Once `verify_signature` succeeds (HMAC(secret_for_orgA, raw_body) is valid because the attacker legitimately owns orgA's webhook secret), the event is dispatched to handlers. However, `Handlers::Handler` (the base class used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves which `Stack`s to act on purely from `repository.full_name`, with no re-validation that this repository belongs to the organization whose secret validated the signature: [4](#0-3) [5](#0-4) 

So the equality that should hold — `organization authenticated by verify_signature == organization owning repository.full_name acted on by the handler` — is never enforced. An attacker only needs to be a legitimate admin of *any* organization already configured in Shipit's multi-org `secrets.github` block (i.e., they can obtain that org's own GitHub App webhook secret through entirely legitimate means, without any Shipit session, API token, or access to the victim organization) to sign an arbitrary payload whose `repository.full_name` field targets a *different*, victim organization's stack.

### Impact Explanation
This breaks a cross-tenant trust boundary in a multi-org Shipit deployment:
- Forging a `push` event lets the attacker trigger `stack.sync_github(expected_head_sha:)` for a victim org's `Stack`, an operation reserved for GitHub's own delivery for that org — this is a cross-repository write into state owned by a different, unrelated organization.
- Forging a `status`/`check_suite` event lets the attacker inject fabricated commit statuses/check results for a victim org's commits (recorded straight from payload data), which is exactly the signal Shipit's `ci.require`/continuous-delivery gating uses to decide whether a real, already-approved commit is auto-deployed. Falsifying that state for a repository the attacker does not own can unlock an unauthorized deploy of the victim stack.

This lands squarely in the Critical/High bucket defined by the rules ("cross-repository writes" / "unauthorized deploy") because it lets one tenant's legitimately-issued webhook secret be replayed against another tenant's repository state.

### Likelihood Explanation
Requires only that Shipit is configured with the multi-organization GitHub App schema (documented and supported, see `config/secrets.development.example.yml` lines 18-38) and that the attacker administers one of the onboarded orgs (a low bar compared to compromising the victim org). No Shipit session, ApiClient token, or victim webhook secret is needed — only a correctly-signed raw body, which the attacker can compute themselves using their own secret.

### Recommendation
In `Handlers::Handler` (and any handler using `repository_name`/`stacks`), verify that the `repository.owner.login` (or `organization.login`) used to select the signing secret in `WebhooksController#verify_signature` matches the owner segment of `repository.full_name` before resolving/acting on any `Stack`. Reject the event (422) on mismatch. Equivalently, pass the verified organization through to handlers and constrain `Repository.from_github_repo_name` lookups to stacks belonging to that verified organization only.

### Proof of Concept
1. Shipit is configured with multi-org GitHub Apps for `OrgA` (attacker-administered) and `OrgB` (victim), each with its own `webhook_secret`, per `config/secrets.development.example.yml`.
2. Victim `OrgB` has a Shipit `Stack` tracking `OrgB/victim-repo`.
3. Attacker, as an admin of `OrgA`, retrieves `OrgA`'s webhook secret from their own GitHub App settings (no interaction with `OrgB` or Shipit required).
4. Attacker crafts a `push` webhook JSON body with:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha-that-exists-in-OrgB/victim-repo>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
5. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
6. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app/secret, and the signature validates successfully.
7. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` from `repository.full_name` = `"OrgB/victim-repo"`, and calls `stack.sync_github(expected_head_sha:)` on the victim's stack — an action the attacker was never authorized to trigger for `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
