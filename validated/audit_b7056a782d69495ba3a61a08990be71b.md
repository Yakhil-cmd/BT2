### Title
Cross-organization webhook forgery via `repository.owner.login` vs `repository.full_name` binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook's HMAC signature using the `repository.owner.login` (or `organization.login`) field from the JSON body, but every event `Handler` (`PushHandler`, `StatusHandler`, `MembershipHandler`, PR handlers, etc.) resolves the actual `Stack`/`Repository`/`Commit` to mutate using the independent `repository.full_name` field from the same body. Because the two fields are read from attacker-controlled JSON and are never cross-checked against each other, a party who legitimately controls the webhook secret for one organization configured in Shipit can forge a signed payload whose `owner.login` matches their own org (so signature verification passes) while `repository.full_name` points at a stack belonging to a *different* organization/tenant.

### Finding Description
In a multi-tenant Shipit deployment, `Shipit.github(organization:)` supports per-organization GitHub App configs, each with its own `webhook_secret` set by whoever administers that org's GitHub App installation [1](#0-0) .

`WebhooksController#verify_signature` picks which organization's secret to verify against purely from the JSON body itself:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire* parsed body to the registered handler(s) unchanged [3](#0-2) .

Every handler, however, resolves the target repository/stack from a **different** field of the same body — `repository.full_name` — via the shared `Handler#stacks`/`#repository_name` helper:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` uses this to enqueue a sync against whichever stack matches `full_name` and the pushed branch: `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` [5](#0-4) . `StatusHandler` writes a commit status for *any* `Commit` matching the given `sha`, independent of organization: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) . PR handlers resolve `repository` the same way via `params.repository.full_name` [7](#0-6) .

The binding that should hold — `verified_organization == organization_of(repository_written_to)` — is broken: the field authenticated (`repository.owner.login`) and the field acted on (`repository.full_name`) are never checked for consistency, and both are attacker-controlled inside the signed body. Anyone who legitimately knows one organization's `webhook_secret` (they set it themselves when creating that org's GitHub App, per `docs/setup.md`) can compute a valid HMAC over a payload of their choosing, then set `repository.owner.login` to their own org (so `Shipit.github(organization: repository_owner)` resolves to the secret they know and the signature check passes) while setting `repository.full_name` to `"other-org/other-repo"`.

### Impact Explanation
This breaks the tenant isolation boundary Shipit's per-organization GitHub App/webhook_secret model is meant to enforce. A holder of any one organization's webhook secret can:
- Forge `push` events that queue `stack.sync_github` for another organization's stack.
- Forge `status` events that write arbitrary commit statuses on another organization's commits via `Commit.where(sha: ...)` (not even scoped by repository, only by SHA), which can flip CI-check-based gating (`ci.require`) used to allow deploys/continuous delivery on that stack.
- Forge `membership`/PR events against repositories they have no relationship to, since `full_name` lookups are unauthenticated relative to the verified organization.

If a targeted stack has continuous deployment enabled and relies on GitHub commit statuses to gate auto-deploys, forging a passing `status` webhook for that stack's commit can enable an **unauthorized deploy** to be triggered for a stack outside the attacker's own organization — a cross-tenant, cross-repository write achieved purely through a signature/target-field mismatch, without needing an `ApiClient` token, session, or the victim organization's secret.

### Likelihood Explanation
Requires the attacker to control (know) the `webhook_secret` for at least one organization configured on the shared Shipit instance — realistic in any multi-tenant/self-service Shipit deployment where each customer organization creates and knows its own GitHub App's webhook secret, per the documented setup flow. No other privilege (no Shipit session, no `ApiClient`, no GitHub write access to the victim repo) is required to reach the vulnerable code path, since the webhooks endpoint is unauthenticated aside from the HMAC check.

### Recommendation
Bind signature verification to the exact repository the handlers act upon rather than a loosely related field:
- Derive `repository_owner` (and the organization used for `Shipit.github`) from the same value used by `Handler#repository_name` (`repository.full_name`), and additionally verify that `repository.owner.login`, if present, is a prefix of `repository.full_name` before trusting either.
- In `Handler#stacks`/`#repository_name`, cross-check that the resolved `Repository`'s owner matches the organization whose secret validated the signature (e.g., pass the verified organization down from the controller into the handler and reject if it disagrees with `repository.full_name`'s owner segment).
- Consider scoping look-ups (`Commit.where(sha:)`, `Repository.from_github_repo_name`) to only repositories belonging to the verified organization.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with their own GitHub App and `webhook_secret` (a normal multi-tenant setup per `docs/setup.md`), where the attacker administers `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`.
2. `org-b` has a Shipit stack `org-b/victim-repo` with continuous deployment enabled, gated by a required CI status context (`ci.require`), and a pending commit `SHA_X` awaiting a passing status.
3. Attacker crafts a JSON body:
```json
{
  "sha": "SHA_X",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Attacker computes `sha1=HMAC(org-a_webhook_secret, body)` and sends it as `X-Hub-Signature` with `X-Github-Event: status` to `POST /webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")`, whose secret matches the attacker-computed HMAC, so `verified` is `true` and the request proceeds.
6. `StatusHandler#process` executes `Commit.where(sha: "SHA_X").each { |commit| commit.create_status_from_github!(params) }`, creating a passing status on `org-b`'s commit — a commit the attacker has no legitimate relationship to — potentially unblocking or triggering an unauthorized deploy on `org-b`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
