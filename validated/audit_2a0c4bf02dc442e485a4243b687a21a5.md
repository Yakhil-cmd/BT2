### Title
API Client stack-scope bypass in `CCMenuController#stack` grants cross-stack read access - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient` token and the stack(s) it is authorized for: `stacks` returns `Stack.where(id: current_api_client.stack_id)` whenever the token is scoped to a specific stack, and `stack` resolves the requested `:stack_id` param through that scoped relation (`stacks.from_param!`). `Shipit::Api::CCMenuController` breaks this binding: it overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id`.

### Finding Description
`ApiClient` records can be created scoped to a single stack (`belongs_to :stack, optional: true`), and the intended trust binding is "the stack the token authorizes == the stack the request is allowed to touch," enforced in `BaseController#stacks`: [1](#0-0) 

Every other API controller (e.g. `DeploysController`, `RollbacksController`) inherits `stack` unmodified and therefore is restricted to `current_api_client.stack_id` when the token is stack-scoped: [2](#0-1) 

`CCMenuController`, however, redefines `stack` to bypass the scoped `stacks` relation entirely and resolve any `stack_id` param against the full `Stack` table: [3](#0-2) 

`require_permission :read, :stack` only checks that the token has the `read:stack` permission bit — it does not check *which* stack the token's permission applies to: [4](#0-3) 

So a token created with `stack_id` set to Stack A (e.g. via the CCMenu "Get URL" flow, `CCMenuUrlController#client`, which creates/reuses a per-user `read:stack`-scoped `ApiClient`) can be replayed with an arbitrary `stack_id` param and will render CI/build state for any other stack in the installation: [5](#0-4) 

This is the direct analog of the reported bug class: a binding that should hold — "the stack a token authorizes == the stack it touches" — is broken because the enforcement path (`stacks`/`stacks.from_param!`) is not used on this particular controller; the check performed (permission bit) and the object acted on (`Stack.from_param!(params[:stack_id])`) are decoupled, exactly as `HandleReply` decoupled "handling a reply" from "generating a new one" in the original report.

### Impact Explanation
An `ApiClient` token intentionally minted for exactly one stack (least-privilege usage, e.g. embedding in a CI status widget/URL as done by `CCMenuUrlController`) can be used to obtain an unauthenticated read of any other stack's task/deploy state (lock status, last build status/label/time, deploy URL) via `GET /api/:stack_id/ccmenu`. This matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output," since the token is authorized for a narrower scope than what it can actually read.

### Likelihood Explanation
Exploitation only requires possession of any valid, stack-scoped `read:stack` API token (these tokens are routinely generated and embedded in low-trust contexts such as CCMenu URLs handed to CI dashboard tools) and knowledge/guessing of another stack's `stack_id` (stack ids/params are not secret — they are visible in the Shipit UI/URLs). No privileged account, webhook secret, or GitHub credentials are required, satisfying the "unprivileged attacker" constraint.

### Recommendation
Remove the custom `stack` override in `CCMenuController`, or reimplement it to go through the scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) exactly like `BaseController#stack`, so that a stack-scoped `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. As any user, use the "Get CCMenu URL" feature for Stack A to obtain a token via `CCMenuUrlController#fetch`, which creates a `read:stack`-scoped `ApiClient` tied to Stack A (`app/controllers/shipit/ccmenu_url_controller.rb:14-18`).
2. Send `GET /api/:stack_b_id/ccmenu?token=<token>` where `stack_b_id` is any other stack the requester was never granted access to.
3. `authenticate_api_client` authenticates the token successfully (it's valid, just scoped to Stack A) (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`).
4. `require_permission :read, :stack` passes because the token has the `read:stack` permission bit, irrespective of which stack (`app/models/shipit/api_client.rb:38-45`).
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` against Stack B directly, bypassing the `current_api_client.stack_id` restriction that would apply on every other controller (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`).
6. `show` renders Stack B's `lastBuildStatus`, lock state, and deploy URL to the holder of a Stack-A-only token.
