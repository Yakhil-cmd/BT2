### Title
Automatic post-abort rollback forwards a deploy's environment variables into task execution without re-validating them against the stack's `rollback_variables` whitelist - ([File: app/models/shipit/deploy.rb])

### Summary
When a deploy is created, its `env` hash is validated once against `deploy_variables` via `Stack#filter_deploy_envs`. [1](#0-0)  When a rollback is created through the normal UI/API flow, the equivalent gate is `Stack#filter_rollback_envs`, which validates against the separate `rollback_variables` whitelist and is called explicitly by both controllers before `trigger_rollback` is invoked. [2](#0-1) [3](#0-2) 

However, the automatic rollback path triggered when a running deploy is aborted (`rollback_once_aborted: true`) bypasses this gate entirely: `trigger_revert_if_required` forwards the aborted deploy's own already-permitted `env` (validated only against `deploy_variables`) straight into `trigger_rollback`/`trigger_revert`, and neither `build_rollback` nor `trigger_revert` re-filters it against `rollback_variables` before the `Rollback` (a `Task` subclass) is persisted and later spawned as a shell process. [4](#0-3) [5](#0-4) 

### Finding Description
This is the direct analog of the Sherlock report: a value ("debt"/here, the environment map) is checked/whitelisted against one policy at one point in time (deploy creation, `deploy_variables`), but the action that actually matters (spawning the rollback task's shell process with that environment) relies on stale/uncoupled state instead of re-deriving the check against the policy that is actually supposed to govern it (`rollback_variables`).

Concretely:
- `Stack#filter_deploy_envs` gates deploy creation using `deploy_variables`. [6](#0-5) 
- `Stack#filter_rollback_envs` is the intended gate for rollback creation, using the potentially different (and possibly more restrictive) `rollback_variables` list. [7](#0-6) 
- `build_rollback` builds the `Rollback` record with `env: env.to_h` verbatim, performing no whitelist check of its own. [8](#0-7) 
- `trigger_revert_if_required`, invoked automatically `after_transition to: :aborted`, calls `trigger_rollback`/`trigger_revert` passing `env:` (the deploy's own `env` attribute, i.e. the value already approved under `deploy_variables`) with no call to `filter_rollback_envs`. [9](#0-8) [4](#0-3) 
- The existing test suite confirms this behavior is exactly what happens: a deploy's custom `env` (`{'CUSTOM_VAR' => 'value'}`) is carried unchanged into the automatically-created rollback. [10](#0-9) 

The equality that should hold is:
`env keys permitted for the executed task type == env keys the whitelist for that task type (rollback_variables) allows`

Before the attacker's action, for a manually-triggered rollback this equality holds because controllers explicitly call `filter_rollback_envs`. After the deploy aborts and the automatic-rollback code path runs, the equality is broken: the env keys that actually reach `Command#unbundled_env`/process spawn (via `TaskCommands#env`, which merges `@task.env` unfiltered into the spawned shell environment) [11](#0-10) [12](#0-11)  are governed by `deploy_variables`, not `rollback_variables`.

### Impact Explanation
If a repository operator intentionally defines `rollback_variables` more restrictively than `deploy_variables` (e.g., to forbid a destructive/administrative variable such as `RUN_MIGRATIONS` or a variable that toggles a dangerous script branch during rollback specifically, while allowing it for normal forward deploys), a user with only `deploy:stack` permission can:
1. Trigger a deploy with `env` containing a variable that is legal for deploy but excluded from `rollback_variables`.
2. Cause (or wait for) that deploy to be aborted with `rollback_once_aborted: true` (a parameter the same authenticated caller controls via the API/UI abort action).
3. Have the resulting automatic rollback task execute shell commands with that variable present in its process environment, even though the `.shipit/*.yml` config explicitly excludes it from rollback executions.

This results in execution of the deploy/rollback shell scripts with environment variables never sanctioned for that specific code path, i.e. unauthorized control over what gets executed/how the rollback shell scripts behave — a variant of unauthorized deploy/rollback behavior. Because both deploy and rollback controllers currently require the same `deploy:stack` permission scope, this is not a cross-privilege escalation between distinct API-client permission scopes, but it is a genuine breach of the repo owner's `shipit.yml`-declared execution-time environment contract for rollbacks, which the engine is supposed to enforce identically to how it enforces it for manual rollbacks and deploys.

### Likelihood Explanation
Requires: (a) the target stack's `shipit.yml` to define `rollback.variables` more restrictively than `deploy.variables` (a supported, documented feature — see README's "Allow explicit configuration of rollback variables"), and (b) an actor able to trigger a deploy and its abort with `rollback_once_aborted: true`. Both conditions are realistic for any authenticated deploy-permission holder and require no elevated privileges, credential theft, or infrastructure access — only ordinary use of the documented API.

### Recommendation
In `Deploy#trigger_revert_if_required` (or more robustly, inside `build_rollback`/`trigger_revert` themselves), re-filter the forwarded `env` through `stack.filter_rollback_envs(env)` before constructing the `Rollback` record, so the same `rollback_variables` whitelist that governs manually-triggered rollbacks also governs automatically-triggered ones.

### Proof of Concept
1. Configure `shipit.yml` with:
```yaml
deploy:
  variables:
    - name: DANGEROUS_VAR
rollback:
  variables: []   # DANGEROUS_VAR intentionally excluded from rollback
```
2. As a user holding only `deploy:stack` permission, `POST /api/stacks/:id/deploys` with `env: { "DANGEROUS_VAR": "1" }`. This passes `filter_deploy_envs` (allowed for deploy).
3. Abort the running deploy with `rollback_once_aborted: true` (e.g. via the abort endpoint/UI action) which calls `Deploy#abort!` → `after_transition to: :aborted` → `trigger_revert_if_required`. [9](#0-8) 
4. Confirm (as already demonstrated in `test/models/deploys_test.rb:436-451`) that the resulting `Rollback.env` contains `DANGEROUS_VAR`, even though `rollback_variables` is empty and `filter_rollback_envs` would have rejected it had it been passed through the normal rollback-creation path. [10](#0-9) 
5. The rollback task subsequently spawns its shell commands with `DANGEROUS_VAR` present in the process environment via `TaskCommands#env`/`Command#unbundled_env`. [11](#0-10) [12](#0-11)

    def build_rollback(user = nil, env: nil, force: false)
      Rollback.new(
        user_id: user&.id,
        stack_id:,
        parent_id: id,
        since_commit: stack.last_deployed_commit,
        until_commit:,
        env: env.to_h,
        allow_concurrency: force,
        ignored_safeties: force,
        max_retries: stack.retries_on_rollback
      )
    end

    # Rolls the stack back to this deploy
    def trigger_rollback(user = AnonymousUser.new, env: nil, force: false, lock: true)
      rollback = build_rollback(user, env:, force:)
      rollback.save!
      rollback.enqueue

      if lock
        lock_reason = "A rollback for #{rollback.since_commit.sha} has been triggered. " \
          "Please make sure the reason for the rollback has been addressed before deploying again."
        stack.update!(lock_reason:, lock_author_id: user.id)
      end

      rollback
    end

    # Rolls the stack back to the most recent **previous** successful deploy
    def trigger_revert(force: false, rollback_to: nil, env: nil)
      previous_successful_commit = rollback_to&.until_commit || commit_to_rollback_to

      rollback = Rollback.create!(
        user_id:,
        stack_id:,
        parent_id: id,
        since_commit: until_commit,
        until_commit: previous_successful_commit,
        env: env || self.env,
        allow_concurrency: force
      )

      rollback.enqueue
      lock_reason = "A rollback for #{until_commit.sha} has been triggered. " \
        "Please make sure the reason for the rollback has been addressed before deploying again."
      stack.update!(lock_reason:, lock_author_id: user_id)
      stack.emit_lock_hooks
      rollback
    end
