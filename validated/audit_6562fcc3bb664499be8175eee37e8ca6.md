### Title
Path traversal via `inherit_from` in `shipit.yml` allows reading files outside the checked-out repository - (File: `app/models/shipit/deploy_spec/file_system.rb`)

### Summary
`DeploySpec::FileSystem#build_config` resolves the user-supplied `inherit_from` value with plain `Pathname#join` and only checks `.exist?` before reading and YAML-parsing it, with no containment check against `@app_dir`. Since `@app_dir` for a review stack is a checkout of the attacker's own branch, an attacker can supply `inherit_from: ../../<sibling-stack>/shipit.yml` (or any other relative traversal) to make Shipit read and deep-merge the contents of an arbitrary file on the deploy host into the review stack's effective config.

### Finding Description
The intended binding is that any file read by `DeploySpec::FileSystem` must remain inside the ref-checkout directory the reviewer approved, i.e. `inherits_from_path` should satisfy `inherits_from_path.to_s.start_with?(@app_dir.to_s)`. That binding is never enforced: [1](#0-0) 

`build_config` computes `inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))`. `Pathname#join` does not sanitize `..` segments, so a value like `../../other-repo/other-env/shipit.yml` walks the resulting path outside `@app_dir`. `read_config` then does `SafeYAML.load(path.read) if path.exist?` — the only gate is filesystem existence, not membership under `@app_dir`.

`config_file_path` itself is derived the same way (`file(filename, root: true)` → `@app_dir.join(path)`), but `build_config`'s recursive `inherit_from` resolution is the actual escape point because its base is not re-clamped to `@app_dir` on each hop, and it recurses (`build_config(path, config_obj)`) so a chain of `inherit_from` values can walk arbitrarily far from the original checkout.

Exploit flow for a review stack (attacker fully controls `stack.branch` via their own PR/fork):
1. Attacker opens a PR against a repo with review stacks enabled ("Allow All" behavior requires no special permission).
2. In their branch, they add `shipit.yml` containing `inherit_from: ../../<known-sibling-stack-dir>/<env>/shipit.yml` (or a `../../../..` chain), relying on Shipit's documented, predictable on-disk checkout layout for stacks.
3. When the stack's `DeploySpec` is loaded, `load_config` → `build_config` follows the traversal, reads the target file's YAML, and `deep_merge`s it into the attacker's own config (attacker's keys win on conflicts, but any keys not defined in their file are inherited from the read target).
4. If the target file happens to contain a `machine.environment` map, `review.checklist`, `links`, or other rendered fields, that content is exposed through the deploy page or is merged into the environment consumed by `Command`/`PTY.spawn` for that stack's tasks.

None of `verify_signature`, `force_github_authentication`, `require_permission!`, or the `ExplicitParameters` schema apply here — this is a pure filesystem-path bug inside `DeploySpec::FileSystem`, downstream of webhook/authorization checks that only gate whether a review stack gets created, not what its `shipit.yml` is allowed to reference.

### Impact Explanation
Practical impact is constrained by two factors that must be weighed honestly:
- Review stacks are a documented design where the PR author's own branch already fully controls `deploy`, `rollback`, and `tasks` steps executed by `Command`; this bug does not grant new *command execution* capability beyond what review-stack authors already have by design.
- `deep_merge` requires the target file's YAML to parse to a Hash; if the target does not parse as a Hash, Ruby raises `NoMethodError` (denial, out of scope) rather than leaking data.

Within those constraints, the concrete new capability is: an attacker can force Shipit to read and merge the contents of *another* on-disk file (most plausibly another stack's `shipit.yml`, since it is guaranteed to be a well-formed Hash with the exact schema fields Shipit consumes) into their own review stack's config. If that sibling `shipit.yml` embeds secrets in `machine.environment` (a discouraged but real-world pattern) or custom deploy commands, those values become visible to the attacker (via the rendered review page fields such as `links`/`review.checklist`/`review.monitoring`) or get folded into environment variables passed to `Command`/`PTY.spawn` for the attacker's own task. This is a cross-tenant information leak (one repository's config data reaching another repository's stack), matching the "exfiltration of deploy-time secrets" / cross-tenant impact categories, though it is conditional on directory layout guessability and the target file happening to expose sensitive data through a schema field Shipit actually reads.

### Likelihood Explanation
- Requires `review_stacks_enabled` with a provisioning behavior that lets an unprivileged fork's PR create a review stack (e.g., "Allow All", which the docs call the most likely configuration).
- Requires the attacker to correctly guess the relative filesystem layout between their stack's checkout directory and the target file (Shipit's stack checkout layout is a fixed, discoverable convention, making educated guesses for sibling stacks under the same host feasible, though not certain).
- No secrets, tokens, or elevated GitHub roles are needed — only the ability to open a PR/push a branch, which matches the stated attacker capability.
- Repeatable: the attacker can iterate `inherit_from` values across many candidate relative paths at low cost, since a failed guess only produces a config-load error for their own review stack.

### Recommendation
In `build_config`/`read_config`, resolve `inherits_from_path` with `File.expand_path` (or `Pathname#realpath` when the file exists) and explicitly verify the resolved path is a descendant of `@app_dir` (e.g., `inherits_from_path.expand_path.to_s.start_with?("#{@app_dir.expand_path}/")`) before calling `.exist?`/`.read`. Reject or ignore `inherit_from` values that escape `@app_dir`, and apply the same containment check to every recursive hop, not just the initial one.

### Proof of Concept
```ruby
# test/models/shipit/deploy_spec/file_system_test.rb
test '#load_config does not allow inherit_from to escape @app_dir' do
  Dir.mktmpdir do |root|
    app_dir = File.join(root, 'checkout')
    secret_dir = File.join(root, 'outside')
    FileUtils.mkdir_p(app_dir)
    FileUtils.mkdir_p(secret_dir)

    # a file outside the checkout that looks like a valid shipit config
    File.write(File.join(secret_dir, 'secret.yml'), <<~YAML)
      machine:
        environment:
          LEAKED_SECRET: "should-not-be-readable"
    YAML

    File.write(File.join(app_dir, 'shipit.yml'), <<~YAML)
      inherit_from: "../../outside/secret.yml"
      deploy:
        override:
          - echo hi
    YAML

    stack = shipit_stacks(:shipit)
    deploy_spec = Shipit::DeploySpec::FileSystem.new(app_dir, stack)

    loaded_config = deploy_spec.send(:load_config)

    # Binding under test: inherits_from_path must stay within @app_dir.
    # i.e. inherits_from_path.to_s.start_with?(Pathname.new(app_dir).to_s) must be true.
    refute loaded_config.dig('machine', 'environment', 'LEAKED_SECRET'),
      "shipit.yml inherit_from escaped @app_dir and leaked outside file content"
  end
end
```
This test currently fails against the code at [1](#0-0) , demonstrating that `inherits_from_path` is not confined to `@app_dir` and its content is merged into the deploy config.

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end

      def read_config(path)
        SafeYAML.load(path.read) if path.exist?
      end
