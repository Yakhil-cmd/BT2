### Title
Uncaught `throw Error` on missing base AA during parameterized-AA trigger redirection permanently traps trigger funds - ([File: aa_composer.js])

### Summary
`ocore` handles AA trigger failures by design through a `bounce()` mechanism that returns received funds to the sender when an AA's execution fails [1](#0-0) . However, the parameterized-AA redirection path in `handleTrigger()` does not go through `bounce()` at all: if the base AA definition cannot be read, the code throws an uncaught `Error` instead of gracefully failing the trigger [2](#0-1) . This is the same bug class as the Stargate `sgReceive()` report: an external/dynamic address reference (there, the Stargate router; here, `template.base_aa`) is trusted to always resolve, and when it unexpectedly doesn't, the code reverts/throws instead of returning the already-received funds, leaving them stuck.

### Finding Description
When an AA trigger unit is processed, `handleTrigger()` first checks whether the AA definition is a "parameterized AA" (`template.base_aa`) and, if so, looks up the base AA's definition via `storage.readAADefinition(conn, template.base_aa, mci, ...)`: [2](#0-1) 

If `arrBaseDefinition` comes back falsy, the code does `throw Error("base AA not found: " + template.base_aa)` rather than calling `bounce()`. Every other failure condition in `handleTrigger` (insufficient bounce fees, max responses exceeded, formula evaluation errors, `evaluateAA` failures, empty messages, etc.) is routed through `bounce()`, which returns the trigger's payment (minus `bounce_fees`) back to `trigger.address` [3](#0-2) . The base-AA-not-found path is the one place that bypasses this safety net.

The same unprotected pattern also exists in the getter/remote-call resolution helper `readBaseAADefinitionAndParams()`, used when one AA calls a getter on another parameterized AA: [4](#0-3) 

Normally `base_aa` cannot "disappear" because ocore's DAG is append-only and the AA definition validation step already confirms the base AA exists at definition time [5](#0-4) . But the `mci` used at *trigger-processing* time is not necessarily the same as the `mci` used at *definition-validation* time, and the codebase's own comments/constants (`testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci`) show that historically there were real mci-ordering edge cases around AA definitions created by other AAs (secondary triggers) not being immediately "active" or visible for lookups at a given mci [6](#0-5) . Any future edge case, timing bug, or upgrade-related mismatch in mci handling that causes `readAADefinition`/`readAAGetterProps` to return null for a `base_aa` that legitimately exists produces an uncaught exception in the middle of AA trigger processing — after the trigger payment has already been recorded as belonging to that AA address.

### Impact Explanation
The trigger unit's payment output is already written to the `outputs` table for the parameterized AA's address as part of normal unit validation/saving, independent of whether `handleTrigger` succeeds. If `handleTrigger` throws before reaching `bounce()`, no AA response unit is ever produced and the funds are never returned to the sender. Because AA addresses can only be spent from via a successful AA response computed by this exact code path, those bytes/assets become permanently unspendable — functionally identical to the Stargate case where tokens are "left in the contract" with no path to recovery, except here they may not even be recoverable by an attacker (worse: fully frozen, not merely at-risk of theft). An uncaught exception during unit processing on a full node is also process-fatal in Node.js, meaning it can crash the node processing that trigger, which is an availability concern beyond just the frozen funds.

### Likelihood Explanation
Likelihood is low-to-moderate and analogous to the original report's own admission that redeployment likelihood is hard to estimate. It requires a scenario where `template.base_aa` genuinely fails to resolve at the mci used for lookup despite having passed validation — e.g., an mci-boundary/upgrade timing bug, a light-client mci mismatch, or a future protocol change to AA definition rules. The codebase's existing testnet-only compatibility shim for AAs-defined-by-AAs demonstrates that such mci-lookup edge cases have occurred in practice.

### Recommendation
Route the "base AA not found" failure in `handleTrigger()` through `bounce()` instead of `throw Error(...)`, so that if the base AA definition cannot be resolved, the trigger payment is returned to the sender like any other AA execution failure. Similarly, harden `readBaseAADefinitionAndParams()` and its callers (e.g., the getter-call flow in `formula/evaluation.js`) to propagate a normal error to the caller (which already bounces on getter errors) rather than throwing, ensuring no code path can leave AA-received funds permanently stranded due to an unhandled exception.

### Proof of Concept
Not applicable without reproducing an actual mci-lookup inconsistency; no external report or observed defect confirms `readAADefinition`/`readAAGetterProps` currently returns null for a genuinely-existing `base_aa`. This is a structural/defense-in-depth gap (missing `bounce()` on an error branch) rather than a demonstrated exploit today — flagged because it is the closest reachable analog in `ocore` to the reported bug class (a trusted external/dynamic address reference failing to resolve and causing an uncaught revert instead of fund return).
