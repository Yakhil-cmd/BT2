### Title
Missing WebAuthn ceremony-type check allows registration (`Create`) client data to satisfy assertion verification - (File: `types/src/transaction/webauthn.rs`)

### Summary
`PartialAuthenticatorAssertionResponse::verify()` and `verify_arbitrary_msg()` never inspect the `type` field of the parsed `CollectedClientData` (i.e. `ClientDataType::Get` vs `ClientDataType::Create`). Verification succeeds purely based on challenge-byte equality and raw signature validity, so a WebAuthn "registration" (`webauthn.create`) client-data blob can be admitted as a valid transaction "assertion" (`webauthn.get`) signature, as long as an attacker can produce a signature over `authenticator_data || SHA-256(client_data_json)` that verifies against the account's bound public key.

### Finding Description
`PartialAuthenticatorAssertionResponse::verify` in `types/src/transaction/webauthn.rs` performs the following steps:
1. Deserializes `client_data_json` into a `passkey_types::webauthn::CollectedClientData` [1](#0-0) .
2. Extracts `challenge` and compares it against the expected SHA3-256 digest of the signing message, ignoring the `ty` field entirely [2](#0-1) .
3. Builds `verification_data = authenticator_data || SHA-256(client_data_json)` and validates the raw ECDSA signature against the bound `AnyPublicKey::Secp256r1Ecdsa` public key [3](#0-2) .

At no point does the function check `collected_client_data.ty == ClientDataType::Get`, which the WebAuthn spec (§6.3.3, referenced in the doc comment on lines 124-133) requires as step 3 of assertion verification (`response.type` must be `"webauthn.get"`). The same omission exists in `verify_arbitrary_msg` (lines 177-208). No caller elsewhere in the codebase enforces this check either — a search across `types/src/transaction/authenticator.rs` and the API layer (`api/types/src/transaction.rs`, `api/src/tests/webauthn_secp256r1_ecdsa.rs`) turned up no additional `ClientDataType`/ceremony-type validation on the verification path. Because of this, a `client_data_json` produced during a `create()` (registration) ceremony with `ty = ClientDataType::Create`, whose `challenge` happens to equal the SHA3-256 digest of the target `RawTransaction`'s signing message, and whose accompanying signature validates over `authenticator_data || SHA-256(client_data_json)`, will pass `verify()`.

### Impact Explanation
This breaks the intended WebAuthn ceremony-type invariant: registration signatures are meant to attest to key creation, not transaction authorization, and browsers/authenticators apply different UI/consent flows and semantics to `create` vs `get` ceremonies. Admitting a `Create`-typed response as a valid `Get` assertion corrupts that invariant at the authenticator-parsing/binding layer described in the review's Admission Pivots (WebAuthn checks must bind to the intended account set and intended ceremony). However, actually leveraging this to admit an unauthorized transaction still requires the attacker to control (or coerce) a signature over `authenticator_data || SHA-256(client_data_json)` from the private key bound to the target account — the exploit does not by itself let an attacker forge a signature from an unprivileged position; it only removes one binding check (ceremony type) that legitimate flows rely on for defense-in-depth.

### Likelihood Explanation
The missing check is deterministic and trivially demonstrated by constructing a `PartialAuthenticatorAssertionResponse` with `ClientDataType::Create` client data (as long as challenge/signature match) — this requires no privileged access, only ordinary transaction-submission input (BCS `TransactionAuthenticator` bytes). It is a genuine code-level omission versus the WebAuthn spec, confirmed by direct reading of the `verify`/`verify_arbitrary_msg` implementations.

### Recommendation
Add an explicit check in both `verify()` and `verify_arbitrary_msg()` that `collected_client_data.ty == ClientDataType::Get` before proceeding to challenge/signature validation, returning an error otherwise, matching WebAuthn §6.3.3 step 3.

### Proof of Concept
Using the existing test harness in `types/src/transaction/webauthn.rs`, run `registration_helper()` (which produces a `CredentialCreationOptions`/`create()` response with `ty = "webauthn.create"`) instead of the `authenticate()` assertion response, but with `challenge` set to `SHA3_256(signing_message(raw_txn))`. Sign `authenticator_data || SHA-256(client_data_json)` with the credential's private key, build `PartialAuthenticatorAssertionResponse::new(signature, authenticator_data, client_data_json)` from the *registration* response fields, and call `.verify(&raw_txn, &any_public_key)`. Per the current code (lines 139-164), this call returns `Ok(())` because only `challenge` and the raw signature are checked — no assertion of `ty == ClientDataType::Get` is made. Note: producing a genuinely valid signature still requires possessing the credential's private key; the vulnerability lies specifically in the absent ceremony-type binding, not in bypassing signature verification itself.     pub fn verify<T: Serialize + CryptoHash>(
        &self,
        message: &T,
        public_key: &AnyPublicKey,
    ) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        verify_expected_challenge_from_message_matches_actual(message, challenge_bytes.as_slice())?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }
