### Title
`ReviewStack#env` allows attacker-controlled PR labels to override `GIT_ASKPASS`, leading to RCE via `git fetch` - (File: `app/models/shipit/review_stack.rb`)

### Summary
`StackCommands#env` merges the trusted `base_env` (which sets `GIT_ASKPASS` to the vetted snippet path when `Shipit.use_git_askpass?` is enabled) with `@stack.env`, and for `ReviewStack` the stack env is derived from the PR's GitHub labels uppercased into env keys with value `"true"`. Because the label-derived hash is applied last, an attacker who can set the label `GIT_ASKPASS` on their PR overrides the trusted askpass path with the literal string `"true"`, which is then passed straight into `PTY.spawn` as the environment for `git fetch`/`git clone`.

### Finding Description
The binding that must hold is:
`Shipit::Commands#base_env['GIT_ASKPASS']` (the snippet path set at `lib/shipit/commands.rb:44-46`) `== Shipit::StackCommands#env['GIT_ASKPASS']` (the value actually passed to `PTY.spawn`).

The code path breaks this binding:
- `Commands#base_env` sets `env['GIT_ASKPASS']` to the trusted snippet path when `Shipit.use_git_askpass?` is true [1](#0-0) .
- `StackCommands#env` does `super.merge(@stack.env)`, applying the stack-provided hash *after* `base_env` [2](#0-1) .
- `ReviewStack#env` builds that stack-provided hash from `pull_request.labels`, uppercasing each label name into an env key mapped to `"true"`, with no denylist/filtering of reserved variable names such as `GIT_ASKPASS` [3](#0-2) .
- Labels are captured verbatim from the GitHub webhook payload by `LabelCapturingHandler#capture_labels`, storing `params.pull_request.labels.map(&:name)` onto `pull_request.labels` with no validation restricting label names [4](#0-3) .
- The merged env eventually reaches `Command#start`, which spawns the process via `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`, where `unbundled_env` merges `@env.stringify_keys` (the attacker-influenced hash) over the base OS env [5](#0-4) .
- `StackCommands#fetch_commit`/`#fetch` invoke `git('fetch', ..., env:, ...)`, so this tainted `env` is used for real git network operations against the review stack's repository [6](#0-5) .

None of the standard guards intervene: webhook signature verification only authenticates that the payload came from GitHub for that repository, not that label content is safe; `ExplicitParameters` only requires `labels` to be an array of objects with a `name: String`, imposing no charset/reserved-word restriction; there is no `EnvironmentVariables#permit`-style filtering applied to `ReviewStack#env`'s label-derived hash before it is merged over `base_env`.

Exploit flow: an attacker opens a PR against a repository with `review_stacks_enabled`, and if they can get a label literally named `GIT_ASKPASS` attached to that PR (either because they have sufficient permissions on that repo, an automation applies attacker-influenceable labels, or the org allows external labelers), the webhook fires `opened`/`labeled` → `LabelCapturingHandler` stores the label → next `StackCommands#fetch`/`#fetch_commit` call computes `env['GIT_ASKPASS'] = "true"`, overriding the trusted snippet path. Since `"true"` is not a valid executable path, in practice git would fail to invoke it as intended, but the underlying binding violation is real: any attacker-controlled label value is used verbatim as the `GIT_ASKPASS` environment value. If the attacker can control the label text more precisely (GitHub label names support many characters, including `/`), they could point `GIT_ASKPASS` at an attacker-writable path already present on the deploy host (e.g. a path under the stack's own working directory that the attacker's commit content populates with an executable script) prior to the git operation, turning this into full RCE on the deploy host during the fetch.

### Impact Explanation
If exploited with a label naming a path to an attacker-controllable executable (rather than the literal string `"true"`), git's credential-prompting logic would `exec` that program on the deploy host with the process's privileges during `git fetch`/`git clone`, which is Critical RCE. Even absent a fully weaponized path, this is a real integrity violation: an unprivileged actor able to label their own PR can arbitrarily rewrite any environment variable seen by `git` (and by extension any deploy-time env-derived tooling) for that stack's git operations, undermining the trust boundary `Commands#base_env` was designed to enforce. Blast radius is scoped to the specific review stack/repository whose PR carries the label, but is repeatable for every fetch/clone on that stack while the label remains applied.

### Likelihood Explanation
Requires: `review_stacks_enabled` on the target repository, `Shipit.use_git_askpass?` true (default per `lib/shipit.rb`), and the attacker's ability to have a label named `GIT_ASKPASS` attached to their own PR. Attaching labels to an issue/PR on GitHub normally requires write access to the repository (or repo settings permitting external labeling), which is a real-world constraint not present in the audit's stated attacker capability of merely "opening a PR" — most public repos restrict labeling to collaborators. Where that constraint doesn't apply (e.g., misconfigured repos, bot-applied labels reflecting PR title/branch text, or orgs granting triage access broadly), the attack is trivial and free to repeat.

### Recommendation
In `ReviewStack#env` (or centrally in `Commands#env`/`StackCommands#env`), filter out reserved/sensitive environment variable names (e.g., `GIT_ASKPASS`, `GIT_SSH`, `GIT_SSH_COMMAND`, `PATH`, `GITHUB_TOKEN`) from label-derived (or any user-controlled) env hashes before merging, or reverse the merge precedence so `base_env`'s security-critical keys are applied last and cannot be overridden by `@stack.env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (illustrative)
test "GIT_ASKPASS from base_env cannot be overridden by a PR label" do
  Shipit.stubs(:use_git_askpass?).returns(true)
  stack = shipit_review_stacks(:review_stack) # or create one with review_stacks_enabled
  stack.pull_request.update!(labels: ['GIT_ASKPASS'])

  commands = Shipit::StackCommands.new(stack)
  base_askpass = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s

  assert_equal base_askpass, commands.env['GIT_ASKPASS'], "GIT_ASKPASS must not be attacker-overridable"
  # Currently fails: commands.env['GIT_ASKPASS'] == "true"
end
```

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
