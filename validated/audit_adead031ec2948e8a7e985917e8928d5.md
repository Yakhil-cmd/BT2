### Title
Uncaught Decimal.js exception on `ln()` of a negative base in fractional-exponent `pow` evaluation - (File: formula/evaluation.js)

### Summary
The oscript `^` (power) operator handler in `formula/evaluation.js` defends against overflow (`too large exponent`) and non-finite results (`not finite in ^`), but for non-integer exponents applied to a negative base it calls `prevV.ln()` without first checking `prevV.isNegative()`.

### Finding Description
In the `^`/`pow` branch of `evaluate()`, integer exponents are handled safely via `prevV.pow(res)` after an overflow guard on the exponent size: [1](#0-0) 

For fractional exponents, the code falls through to a logarithm-based computation without verifying the sign of the base: [2](#0-1) 

`decimal.js`'s `Decimal.prototype.ln()` throws a `DecimalError` ("Ln argument must be positive") when called on a negative value, rather than returning `NaN` or an `Infinity`-flavored `Decimal`. Every other numeric-safety check in this function (`isFiniteDecimal`, `setFatalError`, `toDoubleRange`) is designed to intercept bad *results*, not to prevent a *thrown exception* originating mid-computation. Unlike the `sqrt`/`ln` unary operators, which explicitly check `res.isNegative()` before calling `.sqrt()`/`.ln()`: [3](#0-2) 
the binary `^` operator's fractional-exponent path has no equivalent negativity check on `prevV` before calling `.ln()`.

This directly mirrors the Chainflip bug class: an unguarded exponentiation/root routine that can be driven into an invalid mathematical domain (negative base to fractional/root power) and panics instead of returning a safe error.

### Impact Explanation
Oscript formulas are evaluated in multiple security-critical, attacker-reachable contexts: unit `authentifiers` (`['formula', ...]`), AA trigger-driven state formulas, and bounce-fee/definition formulas. A formula such as `-2 ^ 1.5` (or any expression producing a negative decimal raised to a non-integer power) reaches the vulnerable code path. If the exception is not caught by an outer handler, it manifests as an uncaught exception during unit/AA validation on every node evaluating the formula, which is a shared deterministic input — potentially crashing the validating process or, if only some nodes crash/others don't (e.g., depending on Node/decimal.js version), causing nodes to disagree on unit validity, which is one of the accepted-impact categories (node disagreement on validity or a network unable to confirm new units).

### Likelihood Explanation
The triggering input is a simple oscript formula with a negative base and non-integer exponent (e.g. `-2^1.5`), easily embeddable by any unprivileged unit poster in a formula-based authentifier or by any AA definer/trigger sender in an AA formula. No special privileges, timing, or race conditions are required — likelihood is high if the exception is not caught elsewhere in the call stack.

### Recommendation
Add a negativity check on `prevV` (analogous to the `sqrt`/`ln` unary handling) before entering the fractional-power branch in `formula/evaluation.js`, returning a `setFatalError` (e.g. "negative base with fractional exponent") instead of calling `.ln()` on a negative value.

### Proof of Concept
Evaluate the oscript formula `-2 ^ 1.5` (or any `negative_decimal ^ non_integer_decimal`) through `formula/evaluation.js`'s `evaluate()` — for example via `definition.validateAuthentifiers(..., ['formula', "-2 ^ 1.5 == -2"], ...)` as used in the existing test harness (`test/formulas_in_contracts.test.js`), and observe whether it throws a `DecimalError` instead of returning `false`/`null`.

**Caveat**: I could not conclusively determine, within the scope of this investigation, whether an outer `try/catch` elsewhere in the evaluation/validation call chain (there are 39 `try`/`catch` occurrences in `formula/evaluation.js` alone) intercepts this specific thrown `DecimalError` before it becomes a true uncaught exception. This should be verified with a live reproduction (e.g., a Devin session) before treating this as a confirmed crash/DoS rather than a caught, non-impactful error.
