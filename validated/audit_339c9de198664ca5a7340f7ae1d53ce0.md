### Title
Webhook signature is verified against the organization named in the untrusted payload, not the organization that owns the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects *which* organization's secret to verify the incoming signature against by reading `repository_owner`, a field taken straight from the same untrusted JSON body it is trying to authenticate. The resulting handler dispatch then processes the entire raw payload — including whatever `repository.full_name` / other repo-identifying fields it contains — without re-checking that the repository being mutated actually belongs to the organization whose secret was used to validate the signature.

### Finding Description
`verify_signature` does: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

The chosen `github_app` (and thus its `webhook_secret`) comes from `Shipit.github(organization: repository_owner)`, and `GitHubApp#verify_webhook_signature` simply HMACs the raw body with that org's configured secret: [3](#0-2) 

Each organization can be configured with an independent `webhook_secret`, as documented for multi-tenant setups: [4](#0-3) 

Once `verify_signature` passes, the full, attacker-controlled `params` hash (not scoped to the verified organization) is dispatched to every registered handler for the event: [5](#0-4) 

The binding the code implicitly assumes but never enforces is:
`organization(secret used to verify signature) == organization(repository actually mutated by the handler)`

Because `repository_owner` (used to pick the verification secret) and the repository/stack fields consumed later by handlers (e.g. `repository.full_name`, used to look up the target `Stack`) are both attacker-supplied fields inside the same JSON body, nothing stops them from diverging. An attacker who knows (or is issued) the `webhook_secret` for *one* configured organization can sign a payload whose `repository.owner.login` matches that organization (so the signature check for that organization's secret passes) while other repository fields consumed by handlers reference a stack belonging to a *different* configured organization on the same Shipit instance.

### Impact Explanation
This breaks organization-to-repository trust isolation in multi-org Shipit deployments: possession of a single organization's webhook secret is sufficient to inject forged, signed-looking webhook events (`push`, `status`, `pull_request`, `check_suite`, etc.) that get routed to handlers touching stacks/commits belonging to a different organization the attacker has no legitimate access to. Depending on the handler reached, this can trigger unwanted `GithubSyncJob`s, forge commit statuses, or manipulate merge/review-stack state for a repository outside the credential's intended scope — a cross-organization/cross-repository write performed with credentials that should only authorize one organization's data.

### Likelihood Explanation
This requires the deployment to use the documented multi-organization configuration and requires the attacker to have obtained (or been legitimately issued, e.g. as a maintainer of one org) the `webhook_secret` for at least one of the configured organizations — this is not a fully unauthenticated attack, but it does cross a trust boundary the engine is supposed to enforce (isolation between tenants/organizations sharing one Shipit instance). Single-organization deployments (the common case) are not affected since there is only one secret to check against.

### Recommendation
After verifying the HMAC signature, cross-check that the organization whose secret validated the signature actually matches the organization owning every repository referenced in the payload that a handler will act upon (e.g., compare `repository_owner` against the owner segment of `repository.full_name` before dispatch, and have handlers reject/ignore repositories outside that verified organization).

### Proof of Concept
Not applicable in the traditional sense (no test files may be added per scope rules); the vulnerable flow is fully demonstrated by tracing:
1. Attacker holding `webhook_secret` for `org-A` crafts a payload with `"repository": {"owner": {"login": "org-A"}, "full_name": "org-B/private-stack", ...}`.
2. `verify_signature` calls `Shipit.github(organization: "org-A")` and validates the HMAC using `org-A`'s secret — succeeds because the attacker legitimately knows that secret. [1](#0-0) 
3. `create` dispatches the same raw `params` (containing `full_name: "org-B/private-stack"`) to the matching handlers, which act on the `org-B` stack despite the signature only proving knowledge of `org-A`'s secret. [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
