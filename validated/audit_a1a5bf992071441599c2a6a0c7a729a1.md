### Title
Non-output_index-scoped duplicate check for divisible private payments crashes the node on legitimate re-delivery - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` uses an aggregate SQL check against the `outputs` table, keyed only by `unit`, `asset`, `message_index`, to decide whether an incoming private payment element is a duplicate. For divisible (non-fixed-denomination) private assets this query intentionally omits `output_index` because "divisible outputs are never hidden individually." But a divisible private payment message routinely has more than one output (recipient output + change output), and once the first of these has been saved, the very same query returns more than one row for any later chain referencing the same `unit/message_index` — including a benign retransmission that the code is explicitly designed to tolerate. The code throws an unhandled `Error` in that case instead of proceeding to the intended duplicate-detection logic, which is only reached when `rows.length <= 1`.

### Finding Description
`validateAndSavePrivatePaymentChain()` builds a duplicate-detection query: [1](#0-0) 

For fixed-denomination (indivisible) assets, `output_index` is appended to the `WHERE` clause, correctly scoping the lookup to exactly one output row. For divisible assets, the comment explains the rationale for omitting it: [2](#0-1) 

However, the very next check runs **before** the duplicate-matching logic and asserts that at most one row can exist for a given `unit/asset/message_index`: [3](#0-2) 

This assumption is false. `validateAndSaveDivisiblePrivatePayment()` inserts one row into `outputs` **for every output in `payload.outputs`** of the message, not just the output belonging to the chain being processed: [4](#0-3) 

Divisible private payments virtually always carry at least two outputs (the recipient's payment output and the sender's change output), and both are inserted together in one call. Consequently, after the *first* successful processing of a private chain for a given `unit/message_index`, the `outputs` table already contains 2+ rows matching the duplicate-check `WHERE` clause. Any subsequent invocation of `validateAndSavePrivatePaymentChain()` for that same `unit/message_index` — even a byte-for-byte identical resend that the surrounding protocol is explicitly designed to swallow — hits `rows.length > 1` and executes `throw Error("more than one output " + sql + ...)` instead of reaching the intended `bDuplicate` comparison.

This is architecturally the same defect class as the reported ERC1155 escrow bug: a validity/duplicate check is implemented as an aggregate query over a shared resource (here, all outputs sharing a `message_index`) instead of tracking state precisely per logical entity (here, a single specific output/chain). When more than one legitimate record shares that aggregate key — exactly as designed — the check breaks and produces a hard failure instead of the intended behavior.

### Impact Explanation
The `throw Error(...)` occurs synchronously inside a `db.query` result callback with no surrounding `try/catch` at any level of the call chain (`network.js:handleOnlinePrivatePayment` → `wallet.js:handlePrivatePaymentChains` → `private_payment.js:validateAndSavePrivatePaymentChain`). In Node.js, an exception thrown inside an asynchronous callback that is not caught anywhere in the stack results in an unhandled exception that crashes the process, unless a global `uncaughtException` handler exists to absorb it and it is safe to continue (which, for a thrown error occurring mid-transaction with an open `BEGIN` and an unreleased DB connection, it is not — the DB connection leaks and the transaction is left open).

Any wallet (full node or light client) that legitimately participates in private (blackbytes-style) divisible-asset payments is affected: a normal retransmission of a private chain (which the network layer explicitly anticipates — see the `INSERT ... IGNORE` comment about receiving the same unit/message_index/output_index twice as cosigner and recipient) will crash the node, denying it the ability to process any further private payments (and, if the crash occurs mid-transaction, potentially leaving corrupted DB state). This is a real, protocol-level denial-of-service against private-payment processing, reachable by any private-payment counterparty simply by re-delivering (or a network retry mechanism re-delivering) a chain that was already accepted.

### Likelihood Explanation
High likelihood of accidental triggering: re-delivery of private payment chains is a normal, expected occurrence in ocore's private-payment protocol (light clients retry `requestUnfinishedPastUnitsOfSavedPrivateElements` on 12-second intervals, `handleSavedPrivatePayments` retries every 5 seconds, and the hub-forwarding/cosigner-forwarding logic in `wallet.js` deliberately re-sends the same chains to multiple parties). It is also trivially triggerable by a malicious private-payment counterparty who simply re-sends the same chain a second time after it has already been accepted once. No special privilege beyond being a normal private-payment counterparty is required.

### Recommendation
Scope the divisible-asset duplicate-detection query correctly:
- Only consider it a pre-existing "same output" candidate for the specific output(s) claimed in the incoming payload (e.g., match address/amount/blinding directly instead of using `rows.length > 1` as a hard assertion), or
- Track a per-chain/per-output "already processed" state (analogous to the recommended fix in the reference report — an explicit flag rather than inferring validity/duplication from an aggregate count over a value shared by multiple legitimate records), or
- At minimum, move the `bDuplicate` comparison ahead of the `rows.length > 1` assertion so that a matching duplicate is detected and short-circuited before the assertion can fire, and replace the `throw Error` with a graceful `transaction_callbacks.ifError(...)` (or continue further validation) instead of crashing the process.

### Proof of Concept
1. Wallet A composes and sends a private divisible-asset payment to Wallet B, where the payment message has two outputs: the payment output to B and the change output back to A (the normal case for any divisible payment that doesn't spend an exact-amount coin).
2. Wallet B receives the private chain via `handleOnlinePrivatePayment` → `validateAndSavePrivatePaymentChain`. Since no prior record exists, the duplicate query at `private_payment.js:70-73` returns 0 rows, so processing proceeds to `divisibleAsset.validateAndSavePrivatePaymentChain`, which inserts rows into `outputs` for **both** outputs of the message (`divisible_asset.js:32-38`).
3. Wallet A (or the hub, or a light-vendor retry loop, or Wallet B's own retry logic after a disconnect) re-sends the identical private chain to Wallet B a second time — a scenario the protocol explicitly anticipates (see the `INSERT ... IGNORE` comment in `network.js` around `handleOnlinePrivatePayment`).
4. Wallet B processes the chain again. The duplicate query now matches the 2 rows already inserted in step 2 (`unit`, `asset`, `message_index` unchanged, no `output_index` filter for divisible assets), so `rows.length === 2`.
5. `private_payment.js:74-75` executes `throw Error("more than one output " + sql + ...)` inside the DB callback, which is not caught anywhere in the stack, crashing Wallet B's node process before it ever reaches the intended duplicate-match logic.
