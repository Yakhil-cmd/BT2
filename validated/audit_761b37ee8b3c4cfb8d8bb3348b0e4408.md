### Title
`StatusHandler#process` updates commits across all repositories/stacks by SHA with no repository ownership check, allowing a status forged from repo B to make a commit in victim stack A `deployable?` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha).each`, with no filter tying the webhook's `repository`/`organization` to the `stack`/`repository` that owns the matched `Commit` row. Any commit row across the entire installation that happens to share the reported SHA — which is common when a stack tracks a fork or shares git history with another repository — receives the attacker-controlled status, corrupting `Commit#status`/`#deployable?` for a repository that never authenticated it.

### Finding Description
The broken binding: `commit.stack.repository.full_name == webhook.payload['repository']['full_name']` is assumed but never checked. In reality, `StatusHandler#process` does: [1](#0-0) 

This iterates every `Commit` row in the database whose `sha` column matches the payload, irrespective of which `stack`/repository owns it, and calls `commit.create_status_from_github!(params)` on each, which in turn calls `add_status`/`statuses.replicate_from_github!` and recomputes `Commit#status`: [2](#0-1) [3](#0-2) 

Contrast this with `PushHandler#process`, which correctly scopes to `stacks` (repository-scoped) before mutating anything: [4](#0-3) 

`WebhooksController#verify_signature` only proves that the payload's `repository.owner.login` legitimately controls that org's webhook secret — it says nothing about which `Commit`/`stack` the payload is allowed to affect: [5](#0-4) 

Because git SHAs are content-addressed, two different repositories can legitimately contain a `Commit` row with the identical `sha` (e.g., stack A tracks upstream `victim-org/A`, and the attacker owns a fork `attacker/B` sharing history with `A`, or any other repository whose history intersects `A`'s at some commit already recorded by stack A). The attacker fully controls repo B and can freely emit a validly-signed `status` webhook for it (per the threat model, "emit webhooks from a repository they own"). Since `StatusHandler` never checks that the matched `Commit`'s `stack.repository` matches the payload's repository, the forged `success` status for repo B is written onto the same-SHA `Commit` row belonging to stack A, flipping `Commit#status`/`#deployable?` to green for the victim stack with zero interaction with `victim-org/A`'s real CI or GitHub App installation.

`Commit#deployable?`/`#status` is exactly what the Shipit UI/API surfaces to a maintainer deciding to click "Deploy", and it is what `Stack`'s deploy-eligibility checks consult — none of `force_github_authentication`, `User#authorized?`, `require_permission!`, or the `stacks` scope apply here because `StatusHandler` never invokes any repository-scoping helper at all; it operates directly on the global `Commit` table by `sha`.

### Impact Explanation
This lets an unprivileged GitHub user (who merely owns/controls some repository B integrated with the same Shipit instance) forge the CI status of an arbitrary commit in an unrelated victim stack A, as long as that commit's SHA also exists as a `Commit` row for stack A (trivially true for forks/shared history, or any repo pair that happens to reference a shared commit, e.g. via a submodule bump, cherry-pick, or shared base branch). This corrupts the general trust signal (`Commit#status`, `#deployable?`) consulted by every deploy path, not just `continuous_deployment`, and can cause a human maintainer to manually deploy code that never actually passed CI for their own repository, executing `Command#start` with `victim-org/A`'s `GITHUB_TOKEN`. This is a payload-for-one-repository-mutating-another's-commit/stack scenario, matching the "Critical" impact category explicitly listed in the rules (a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy). The attack is repeatable against any stack that shares a commit SHA with an attacker-controlled repository.

### Likelihood Explanation
Preconditions: (1) attacker controls a repository B that is wired to the same Shipit instance with a valid GitHub App/webhook installation (achievable via legitimate onboarding, e.g. as a normal contributor/org member with their own project, per the threat model's granted capability to "emit webhooks from a repository they own"); (2) a `Commit` row for stack A exists with a SHA that also appears in repo B's history — realistic for forks, shared upstream commits, or cherry-picked/rebased commits. No Shipit secrets, sessions, or privileged roles are required. Attacker cost is a single webhook delivery from their own repo (e.g., set a commit status via the GitHub API on their own repo), which GitHub signs legitimately. The exploit is deterministic and repeatable.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving commits/stacks purely by `sha`) to the repository that emitted the webhook. Concretely, join through `stack.repository` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })` (or equivalent), mirroring the repository-scoped `stacks` helper already used by `PushHandler`, before calling `create_status_from_github!`.

### Proof of Concept
Minitest (new file, e.g. `test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb`, or added to `test/controllers/webhooks_controller_test.rb`):

1. Create `stack_a` bound to repository `victim-org/A` (fixture), with a `Commit` `commit_a` whose `state` is `pending` and `sha = 'deadbeef...'`.
2. Create `stack_b` bound to repository `attacker/B` (fixture, different `Repository` record), with a `Commit` `commit_b` sharing the identical `sha = 'deadbeef...'` (simulating shared git history from a fork), also `pending`.
3. Build a `status` webhook payload whose `repository.full_name == 'attacker/B'` and `sha == 'deadbeef...'`, `state == 'success'`.
4. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (attacker legitimately signs their own repo's webhook — no Shipit secret needed).
5. POST the payload to `/webhooks` with `X-Github-Event: status`.
6. Assert the broken binding directly:
   - Before: `assert_equal 'pending', commit_a.reload.state` and `refute commit_a.deployable?`.
   - After posting: `assert_equal 'success', commit_a.reload.state` and `assert commit_a.deployable?` — proving stack A's commit became deployable purely from repo B's payload.
   - Contrast: `assert_equal 'success', commit_b.reload.state` (the intended target), showing `commit_a` was mutated even though its `stack.repository.full_name` (`victim-org/A`) never matches the payload's `repository.full_name` (`attacker/B`).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
