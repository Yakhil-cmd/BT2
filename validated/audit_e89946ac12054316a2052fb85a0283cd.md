### Title
Webhook signature verification is keyed off the wrong organization, allowing forged writes into a *different* repository's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body. All of the actual event handlers, however, resolve the target `Stack`/`Commit` to mutate using a completely different field of the same unverified body: `repository.full_name`. These two fields are never cross-checked, so the "organization whose secret authenticated the request" and "the repository that gets written to" are two independent, attacker-controlled values.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
``` [1](#0-0) 
where `repository_owner` is read straight from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` is a no-op when the selected organization has no configured secret:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Meanwhile every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target repository/stack from a *different* field, `repository.full_name`, via `Handler#stacks`/`#repository_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Because `webhook_secret` is documented as optional per organization (`docs/setup.md`: "Webhook secret (optional)") [5](#0-4)  and Shipit supports multiple simultaneously configured organizations, each with independent secrets, resolved through `Shipit.github_app_config`/`Shipit.github` [6](#0-5) , an attacker only needs to know or guess that *any one* configured organization on the instance has no `webhook_secret` set. They can then send an unsigned (or arbitrarily signed) webhook whose `repository.owner.login`/`organization.login` names that unprotected org (satisfying `verify_signature`), while `repository.full_name` names a repository belonging to a *different, protected* organization whose stacks they want to tamper with. `Handler#stacks` and downstream handlers never re-check that `repository.full_name`'s owner matches the organization that was actually authenticated.

This breaks the binding: `organization that authenticated == repository that is written`. Before the fix, both sides collapse to the same trust domain only if operators configure `webhook_secret` uniformly and if handlers happened to reuse `repository_owner` — neither is enforced by the code. After an attacker's crafted request, the left side (`repository_owner`, used to pick the verification secret) is fully decoupled from the right side (`repository.full_name`, used to pick the mutated `Repository`/`Stack`).

### Impact Explanation
With `StatusHandler`, an attacker can inject a forged CI status (`success`) for an arbitrary `sha` on a commit belonging to any repository configured in the Shipit instance, without needing that repository's own webhook secret:
```ruby
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [7](#0-6)  Status checks are typically consulted by deploy-safety gating in Shipit, so forging a passing status can help satisfy pre-deploy checks. With `PushHandler`/`CheckSuiteHandler`, an attacker can trigger `GithubSyncJob` or `schedule_refresh_check_runs!` against any stack in the instance, causing the app to fetch attacker-influenced GitHub state and act on it as if it came from the legitimate, verified organization [8](#0-7) [9](#0-8) . This is a cross-repository/cross-organization write achieved without holding any credential for the targeted organization — satisfying the "unauthorized deploy/cross-repository writes" bar, contingent on at least one configured organization lacking a `webhook_secret`, which the setup docs explicitly present as a supported, optional configuration.

### Likelihood Explanation
Requires: (a) the Shipit deployment configures more than one GitHub organization (a documented, supported multi-tenant setup), and (b) at least one of those organizations has left `webhook_secret` unset (explicitly documented as optional). Given both, exploitation requires no credentials, no session, and no prior access — only knowledge of the unprotected org's login and the target repository's `full_name`, both of which are typically public information (GitHub org/repo names).

### Recommendation
Cross-validate that the organization used to select/verify the webhook signature (`repository.owner.login`/`organization.login`) matches the owner of `repository.full_name` used by handlers before processing, and reject events where they diverge. Consider also making `webhook_secret` mandatory for every configured organization when multiple organizations are configured, to prevent one weak/absent secret from providing an authentication bypass usable against sibling organizations.

### Proof of Concept
1. Configure Shipit with two organizations: `org-a` (no `webhook_secret`) and `org-b` (has `webhook_secret`, protecting `org-b/protected-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/protected-repo" },
  "sha": "<known-sha-of-protected-repo-commit>",
  "state": "success"
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'org-a')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/arbitrary) `X-Hub-Signature` header.
4. `StatusHandler#process` looks up the commit by `sha` (matched against `org-b/protected-repo`'s commit) and creates a forged successful `Status`, even though the request was never authenticated for `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
