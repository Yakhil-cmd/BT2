This confirms the multi-tenant design: multiple organizations (`OrgOne`, `OrgTwo`) can each have their own `webhook_secret` under `secrets.github`, selected at verification time via `Shipit.github(organization: repository_owner)`. This validates the confused-deputy pattern I identified.

### Title
Webhook signature verified against organization derived from `repository.owner.login`/`organization.login`, but event processing acts on repository from unvalidated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full raw payload to handlers, which independently resolve the target repository via `payload.dig('repository', 'full_name')` in `Handler#repository_name`. Nothing binds the `repository.owner.login` value used for signature/secret selection to the `repository.full_name` value used to pick the `Repository`/`Stack` to mutate.

### Finding Description
Shipit supports multi-tenant GitHub App configuration, where `secrets.github` contains one config block per organization, each with its own `webhook_secret` [1](#0-0) . `Shipit.github(organization:)` looks up the config keyed by the organization name and instantiates a `GitHubApp` scoped to that org's secret [2](#0-1) .

In `WebhooksController`, `verify_signature` picks the organization purely from the JSON body itself, not from any authenticated channel identity: `repository_owner` returns `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and this drives which `GitHubApp`/secret is used for HMAC verification [3](#0-2) .

Once `verify_signature` passes, the same raw JSON body is parsed and dispatched to handlers unmodified via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . Handlers independently derive which `Repository`/`Stack` to act on using `payload.dig('repository', 'full_name')` [5](#0-4) .

Because HMAC-SHA1 verification only proves "this body was signed with organization X's secret" — it does not constrain the *content* of the body beyond that — an attacker who legitimately controls (or has been granted, e.g. as an org admin) a GitHub App installation for one org tracked by this Shipit instance (org X, with a known webhook secret) can freely craft a payload where `repository.owner.login` (or `organization.login`) is set to `X` (satisfying `verify_signature`'s org/secret lookup) while `repository.full_name` is set to any other repository tracked by the same Shipit instance, e.g. `victim-org/victim-repo`. The signature will validate because it is computed by the attacker over their own crafted body using the secret they legitimately possess for org X, and the downstream handler will act on the victim repository named in `full_name`, which was never covered by the org-selection check.

This breaks the equality: `organization authenticated by verify_signature` ⇒ `repository acted on by handlers`. The two are read from different JSON fields of the same untrusted body with no cross-check.

### Impact Explanation
Depending on the event/handler, this allows an attacker who controls a webhook secret for any one onboarded organization to forge state-changing GitHub events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against a stack belonging to a *different* organization tracked by the same Shipit instance. For example, a forged `push` payload enqueues `GithubSyncJob` against the victim's stack [6](#0-5) , and a forged `status`/`check_suite` event can inject fabricated commit statuses/check-run refresh triggers that influence deployability and the merge queue for a repository the attacker does not own. This is a cross-repository/cross-organization write achieved without ever needing the victim org's webhook secret, GitHub App credentials, or Shipit session.

### Likelihood Explanation
Requires the attacker to already administer one legitimate GitHub App installation onto a Shipit instance shared across multiple organizations (a supported, documented configuration per `secrets_double_github_app.yml`/multi-org `github_organizations` support) [7](#0-6) . In any multi-tenant Shipit deployment onboarding more than one organization, this is directly reachable by any org that can add the Shipit GitHub App / configure its own webhook, without any other privilege.

### Recommendation
Bind the organization used for signature verification to the actual repository the payload claims to mutate: after selecting the `GitHubApp` for verification, re-derive the "owning organization" from the same `repository.full_name` (or `organization.login`) field the handlers use, and reject the webhook if they diverge. Alternatively, verify that the resolved `Repository`/`Stack` in `handler.rb`'s `stacks` actually belongs to the organization whose secret validated the signature, before invoking any state-changing logic.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with distinct `webhook_secret`s (supported schema, see `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers the Shipit GitHub App on `OrgOne` and knows `OrgOne`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>"
   }
   ```
4. Attacker computes `X-Hub-Signature` with `OrgOne`'s webhook secret over this exact body and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the signature validates [8](#0-7) .
6. The push handler resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and processes the forged push against `OrgTwo`'s stack [5](#0-4) , despite the attacker having no relationship to `OrgTwo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

    github_config[github_organization]
  end

      verified = github_app.verify_webhook_signature(
