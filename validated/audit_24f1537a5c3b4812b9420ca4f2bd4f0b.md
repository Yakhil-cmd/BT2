### Title
Self-service `ApiClient` creation allows unprivileged users to mint globally-scoped `deploy:stack` tokens - (File: `app/controllers/shipit/api_clients_controller.rb`, `app/models/shipit/api_client.rb`, `app/controllers/shipit/api/base_controller.rb`)

### Summary
`ApiClientsController#create_params` permits any authenticated user to set an `ApiClient`'s `permissions` array to arbitrary values (including `deploy:stack`) but never permits or requires a `:stack` association. Because `Api::BaseController#stacks` treats a `nil` `stack_id` as "all stacks", a self-issued token with `deploy:stack` permission is granted deploy rights over every stack in the installation, not just stacks the creator controls.

### Finding Description
The broken binding is: `api_client.stack_id.nil?` should imply `api_client` has **no** deploy authority over any stack, but the code implements `api_client.stack_id.nil? => authority over Stack.all`.

Code path:
- `ApiClientsController#create_params` only permits `:name` and `permissions: []`, with no `:stack` parameter at all: [1](#0-0) 
- `create` builds the record directly from these params for any user hitting the action: [2](#0-1) 
- `ApiClient` validates `permissions` only against the full `PERMISSIONS` whitelist (`subset` validator), not against any per-user or per-stack restriction, and `stack` is `optional: true`: [3](#0-2) 
- `check_permissions!` only checks whether the string `"deploy:stack"` is present in `permissions`, with no stack-scoping logic at all: [4](#0-3) 
- `Api::BaseController#stacks` resolves to `Stack.all` whenever `current_api_client.stack_id` is falsy: [5](#0-4) 
- `Api::DeploysController` requires only the `deploy:stack` permission and then resolves the target stack via `stacks.from_param!`, i.e. from the unscoped `Stack.all`: [6](#0-5) 
- `stack` helper composes `stacks.from_param!(params[:stack_id])`: [7](#0-6) 

Exploit flow: an authenticated (but otherwise unprivileged) user submits `POST /api_clients` with `permissions: ['deploy:stack']` and no stack. The resulting `ApiClient` has `stack_id = nil`. Using its Basic-Auth token, the attacker sends `POST /api/{any_org}/{any_repo}/stacks/{any_env}/deploys` with a valid `sha`. `require_permission!(:deploy, :stack)` succeeds because the token has `deploy:stack`. `stacks` resolves to `Stack.all` because `stack_id` is `nil`, so `stacks.from_param!` finds and returns the arbitrary target stack, and `stack.trigger_deploy` fires — a real deploy on a repository the attacker does not own or administer.

No existing guard prevents this: `require_permission!`/`check_permissions!` is permission-name matching only, and `stacks` explicitly treats `nil` stack scope as "everything," which is the opposite of least-privilege and is not offset by any ownership check in `ApiClientsController`.

### Impact Explanation
An unprivileged, logged-in Shipit user can escalate to unauthorized deploy capability across every repository/stack managed by the Shipit installation, purely through the self-service `/api_clients` UI. This is a cross-tenant "unauthorized deploy" per the Critical impact category — the attacker can trigger `stack.trigger_deploy` (and, by the same token, other `*:stack` permissions such as `write:stack`, `lock:stack`) against stacks belonging to other teams/repositories, with no per-stack authorization check anywhere in the mint or check path. The action is fully repeatable: one token can be reused indefinitely against any/all stacks.

### Likelihood Explanation
Preconditions are minimal: any account able to authenticate to the Shipit web UI and reach `/api_clients` (no team/admin/ownership check is present in the shown `ApiClientsController` code) can perform this in a single form submission, then a single authenticated API call. No GitHub secrets, webhook signatures, or session hijacking are required — it's entirely first-party, self-service functionality being misused as designed by the code. This makes exploitation trivial and highly feasible, contingent on the (stated) precondition that `/api_clients` has no owner/team gate — nothing in the reviewed files (`ApiClientsController`, `ApiClient`, `ShipitController` inheritance) contradicts that.

### Recommendation
- Require `:stack` to be present/permitted for self-service token creation, or restrict which `permissions` a non-operator user may select (e.g., disallow `deploy:stack`/`write:stack`/`lock:stack` without an explicit, authorized stack).
- Change `Api::BaseController#stacks` semantics so a `nil` `stack_id` does not implicitly grant `Stack.all` for tokens created by non-operators — reserve "all stacks" for a distinct, explicitly-flagged admin/global client type (e.g. `UnlimitedApiClient`), not as a side effect of an unset foreign key.
- Add authorization in `ApiClientsController` restricting who may create clients and validate that `stack` is required whenever a stack-scoped permission (`*:stack`) is requested.

# test/controllers/api/deploys_controller_test.rb (conceptual)
test "unscoped self-service api client can deploy to a stack it does not own" do
  attacker = shipit_users(:walrus)
  victim_stack = shipit_stacks(:shipit)
  commit = victim_stack.commits.last

  api_client = ApiClient.create!(name: 'x', permissions: ['deploy:stack'], creator_id: attacker.id)

  authorization = ActionController::HttpAuthentication::Basic.encode_credentials(api_client.id, api_client.authentication_token)

  post "/api/#{victim_stack.repository.owner}/#{victim_stack.repository.name}/stacks/#{victim_stack.environment}/deploys",
       params: { sha: commit.sha },
       headers: { 'Authorization' => authorization }

  assert_response :accepted # demonstrates unauthorized deploy is accepted, not :forbidden/:not_found
end
