### Title
Denial of Service via unbounded alt-branch graph traversal during main-chain stability determination - (File: main_chain.js)

### Summary
Obyte's `ocore` determines when a unit becomes stable by repeatedly walking the DAG of "alt branches" (non-main-chain competing units) every time a new unit is added. Any unprivileged network participant can post ordinary units whose `parent_units` deliberately avoid extending the current best-parent chain, creating many parallel alt branches under the same ancestor. Each subsequent unit addition then re-triggers `main_chain.js`'s stability check, which must recursively walk every uncollapsed alt branch (`createListOfBestChildrenIncludedByLaterUnits`) and, for every branch tip, perform an additional unbounded BFS-style inclusion check (`graph.determineIfIncludedOrEqual`). This is structurally analogous to Synapse's auth-chain cover index weakness (CVE-2024-31208), where crafted events forced expensive recomputation on an index that grows with attacker-controlled branching, causing CPU exhaustion and DoS.

### Finding Description
Stability advancement is driven by `updateStableMcFlag`/`advanceMcStability`, which is invoked on every unit write [1](#0-0) . When there are alt branches competing with the main chain (`arrAltRows`), the code calls `createListOfBestChildrenIncludedByLaterUnits`, which is also reached from `determineIfStableInLaterUnits`, itself invoked from unit validation on every posted unit via `validateParents` [2](#0-1) .

Inside `createListOfBestChildrenIncludedByLaterUnits`, the code must first filter and then walk down every alt-branch root with `goDownAndCollectBestChildrenFast`, following each alt-branch subtree until it hits free units or a "tip" is not conclusively includable, in which case it is pushed to `arrNotIncludedTips` [3](#0-2) . For every such tip, `findBestChildrenNotIncludedInLaterUnits` invokes `graph.determineIfIncludedOrEqual`, an independent recursive BFS over the parenthood graph that itself walks upward/downward through ancestors until resolution [4](#0-3) [5](#0-4) . When no resolution is reached at a tip, `goUp` climbs to `best_parent_unit` and the whole descent-and-inclusion-check cycle repeats (`findBestChildrenNotIncludedInLaterUnits` → `goUp` → recurse) [6](#0-5) .

The cost of this combined traversal scales with the number of alt branches and their depth/breadth, and each of those branches can be created cheaply by any unit-posting party by choosing `parent_units` that intentionally diverge from the current best-parent tip (a decision entirely under the poster's control, validated only by ordinary structural/fee rules, not by any cap on the number of concurrent alt branches). Because this stability check re-runs on every newly-received unit until the contested MC index actually stabilizes, an attacker who continuously seeds new alt branches faster than they can be resolved keeps forcing every node to repeat the expensive nested traversal (`goDownAndCollectBestChildrenFast` × `determineIfIncludedOrEqual` for each tip), analogous to Synapse recomputing its auth-chain cover index on crafted events.

### Impact Explanation
This does not require any special privilege — a single ordinary user issuing a stream of units with cheap byte fees can grow the number of unresolved alt branches faster than they collapse. Since the stability-check code path is on the critical path for `advanceMcStability`/`updateStableMcFlag` (called from `writer.js` for every unit write) and for `validateParents` (called for every incoming unit), sustained growth of unresolved alt branches causes escalating CPU and DB query load across all full nodes processing the DAG. If the traversal cost grows faster than nodes can keep up, main-chain stabilization stalls, meaning newly posted units — including payments — cannot be confirmed as stable network-wide, which is the same "unable to confirm new units" outcome flagged as impactful in the validation rules.

### Likelihood Explanation
Any node in a public, permissionless Obyte network can post units and choose which parents to build on, so creating divergent alt branches requires no elevated access — only paying the standard headers/payload fee per unit, which is cheap relative to the CPU/DB cost imposed on every other node re-running the nested traversal. The stability-check logic is unconditionally exercised on every unit addition whenever alt branches exist, so the attack surface is continuously reachable without any special timing or race condition.

### Recommendation
Bound the cost of alt-branch stability resolution: cap the number of concurrently tracked alt-branch roots/tips processed per stability check, memoize/cache `determineIfIncludedOrEqual` results across repeated calls within the same stabilization pass, and/or charge higher effective fees for units that create new alt branches (deepen the retreating-witnessed-level and best-parent selection penalties) so that sustained divergence is economically discouraged. Additionally, consider adding a hard iteration/time budget to `createListOfBestChildrenIncludedByLaterUnits`/`findBestChildrenNotIncludedInLaterUnits` with graceful fallback (defer stabilization) rather than unbounded recursive re-computation.

### Proof of Concept
1. As an ordinary unprivileged user, continuously author and broadcast units whose `parent_units` are chosen to *not* follow the network's current best-parent tip (e.g., by parenting on slightly older free units or units with lower witnessed level, exploiting `parent_composer.js`'s parent-selection tolerance) so that each new unit creates a new alt branch instead of extending the main chain.
2. Keep the rate of newly created alt branches higher than the rate at which `determineIfStableInLaterUnits`/`createListOfBestChildrenIncludedByLaterUnits` can resolve them, ensuring `arrAltBranchRootUnits` passed into `main_chain.js` line 838/945 keeps growing.
3. Observe that every subsequent legitimate unit submission now triggers `validateParents` → `determineIfStableInLaterUnitsAndUpdateStableMcFlag` (`validation.js:803`) which re-walks all pending alt branches via `createListOfBestChildrenIncludedByLaterUnits`/`graph.determineIfIncludedOrEqual`, causing CPU and DB load to grow with the number of open alt branches, and MC stabilization (and thus confirmation of new units, including payments) to stall network-wide.
