### Title
`GIT_PROXY_COMMAND` and other arbitrary env vars propagate from PR labels into git subprocess env - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment variable key with value `"true"`, with no allowlist, and that hash flows through `StackCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn` for `git clone --recursive` and other git invocations. This means a PR label literally named `git_proxy_command` (or `GIT_PROXY_COMMAND`) becomes `ENV['GIT_PROXY_COMMAND'] = "true"` in the git subprocess's environment.

### Finding Description
The broken binding: `stack.env.keys` is claimed to be a fixed, sanitized set (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`, plus deploy-spec-declared variables filtered by `EnvironmentVariables#permit`), but for `ReviewStack` it is actually `Stack#env.keys ∪ pull_request.labels.map(&:upcase)` with **no allowlist applied**: [1](#0-0) 

`LabelCapturingHandler#capture_labels` persists label names taken verbatim from the webhook JSON body (`params.pull_request.labels.map(&:name)`) with no filtering of the string content: [2](#0-1) 

`StackCommands#env` merges `@stack.env` unmodified into the git command environment, and `git_clone`/`fetch` pass this `env:` straight to `Command.new`: [3](#0-2) [4](#0-3) 

`Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV`/PATH with no key filtering, and this exact hash is handed to `PTY.spawn`: [5](#0-4) [6](#0-5) 

By contrast, `EnvironmentVariables#permit` shows the codebase *does* have an allowlist mechanism elsewhere (used for deploy-spec-declared variables), but it is never applied to `ReviewStack#env`'s label-derived keys: [7](#0-6) 

This is confirmed as intended/tested behavior — the test suite explicitly asserts labels flow into `env` unfiltered: [8](#0-7) [9](#0-8) 

I was unable to fully verify, within the remaining budget, whether `POST /webhooks` requires a valid HMAC signature (`verify_webhook_signature`) before `LabelCapturingHandler` runs — I located `app/controllers/shipit/webhooks_controller.rb` but did not get to read its signature-verification logic before running out of iterations. If signature verification is enforced (which is standard practice and referenced in the audit's own "Validate" checklist), then the attacker must actually control a repository whose webhook is already configured to point at this Shipit instance with the correct `webhook_secret`/GitHub App credentials — i.e., an attacker who owns their own repo and has legitimately connected it to this Shipit instance (a "self-service" registered repo), not an arbitrary internet user forging webhooks against someone else's stack. In that scenario the attacker is only attacking their own review-stack/environment, not another tenant's — but that review-stack's git clone still runs on the shared Shipit host process, so `GIT_PROXY_COMMAND` (or more directly usable vars like `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_EXTERNAL_DIFF`, `GIT_PAGER`) executing arbitrary commands during `git clone --recursive`/`git fetch` on the shared deploy host constitutes host-level RCE, not merely PR-scoped impact.

### Impact Explanation
If an attacker can get an arbitrary label name onto their own PR (which — for repos where they have write/triage permission on their own fork/repo connected to Shipit — is fully within their control), they can set `GIT_PROXY_COMMAND` (or other `GIT_*` execution-hook variables) which git subprocesses will honor while cloning/fetching that stack's repository on the shared Shipit deploy host. This is Critical: arbitrary command execution on the deploy host, matching the "RCE on the deploy host via `Command`/`PTY.spawn`" impact category. The blast radius is the shared Shipit process/host (not isolated per repo), so this is not confined to the attacker's own data.

### Likelihood Explanation
Preconditions: the attacker's repository must have Shipit review-stacks enabled and connected via webhook (a legitimate, expected configuration for any Shipit customer using review apps), and the attacker must be able to add a label with the exact target variable name to their own PR — something a repo owner/collaborator on their own repository can trivially do. No secrets, no privileged Shipit role, and no bypass of webhook signature verification are required beyond normal usage of an already-configured integration. This is highly likely/feasible and repeatable on every clone/fetch of that review stack.

### Recommendation
Restrict `ReviewStack#env`'s label-derived keys with a strict allowlist/denylist (e.g., reject or drop keys matching `GIT_`, or any key not matching a benign application-defined pattern), or refuse to merge attacker-controlled keys directly into the git-subprocess environment at all — route them only into deploy-script-visible variables, never into `Command#unbundled_env` used for the internal `git`/`Commands#git` invocations. At minimum, apply `EnvironmentVariables#permit`-style sanitization to `pull_request.labels` before merging in `app/models/shipit/review_stack.rb`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb
test "#env does not allow labels to inject GIT_PROXY_COMMAND" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_proxy_command"]

  refute stack.env.key?("GIT_PROXY_COMMAND"),
    "PR label should not be able to set GIT_PROXY_COMMAND for git subprocess env"
end

# test/lib/shipit/stack_commands_test.rb (or deploy_commands_test.rb)
test "git_clone command env does not inherit GIT_PROXY_COMMAND from PR labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_proxy_command"]
  commands = Shipit::StackCommands.new(stack)

  command = commands.fetch  # triggers git_clone with env: commands.env
  assert_nil command.env["GIT_PROXY_COMMAND"], "git subprocess env leaked attacker-controlled GIT_PROXY_COMMAND"
end
```
Both assertions currently fail against the code as shown in `app/models/shipit/review_stack.rb:84-93`, `lib/shipit/stack_commands.rb:13-15`, and `lib/shipit/command.rb:103-105`, confirming the equality `stack.env.keys == allowlisted_keys` is broken (it actually equals `allowlisted_keys ∪ upcased_label_names`).
