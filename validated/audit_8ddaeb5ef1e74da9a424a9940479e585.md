### Title
`status` webhook cross-repository commit-status pollution via unscoped `Commit.where(sha:)` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository or stack scoping, and the `commits` table's unique index is `(sha, stack_id)` rather than a global unique on `sha` alone, meaning the same SHA can legitimately exist as separate `Commit` rows belonging to different stacks/repositories. An attacker who controls a `status` webhook payload for a SHA that coincidentally (or intentionally, via a forked/duplicated commit) matches a commit on an unrelated victim stack can flip that victim's commit status, and consequently the stack's `deployable?`/merge/block behavior.

### Finding Description
The broken binding: the code should guarantee `commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` mutated by a `status` webhook, but instead the actual guarantee is only `commit.sha == params.sha`.

Path:
- `Shipit::WebhooksController#create` dispatches the payload to `StatusHandler.call(payload)` (verified signature only proves *a* GitHub source sent it, not which repository's status it legitimately describes for commits shared across stacks).
- `StatusHandler#process` executes: [1](#0-0) 
This iterates over **every** `Commit` row across **all stacks** whose `sha` column matches, and calls `commit.create_status_from_github!(params)` on each — there is no `repository_name`/`stacks` scoping used here (unlike other handlers in this codebase that use the base class's `stacks` helper: `Repository.from_github_repo_name(repository_name)&.stacks`, see `app/models/shipit/webhooks/handlers/handler.rb` lines 32-38).
- The DB schema permits this cross-stack collision: the unique index on `commits` is on `(sha, stack_id)`, not `sha` alone: [2](#0-1) 
This is a deliberate design point (the same commit SHA can be tracked independently by multiple stacks — e.g. shared base branches, forks/review-stacks, or a monorepo with multiple stacks tracking the same underlying commits), confirmed by comments/tests such as `.create_from_github handle PRs merged by another Shipit stacks` in `test/models/commits_test.rb`.
- `create_status_from_github!` then calls `add_status`, which recomputes `status`, fires `deployable_status` hooks, and calls `stack.schedule_merges` on success/pending transitions: [3](#0-2) [4](#0-3) 
- `Commit#deployable?` and `#blocked?` directly gate deploy/merge behavior for the owning stack: [5](#0-4) 

Exploit flow: attacker sends `POST /webhooks` with a `status` event (`context: ci/e2e`, `state: failure`, `sha: <shared-sha>`). If any commit row on a victim stack (which requires `ci/e2e`, has `review_stacks_enabled: true`, `allow_all`) shares that SHA — plausible when the SHA originates from a shared upstream branch/base commit that both the attacker's fork/PR and the victim repository's commit history reference, or via `pull_request_head_sha`/base-commit tracking that creates cross-stack `Commit` rows for identical upstream SHAs — the handler mutates the victim's `Commit` status, flipping `deployable?`/`blocked?` for a stack the attacker's webhook never authenticated against.

Existing guards do not prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` only proves the payload came from *a* legitimate GitHub source (the attacker's own repo, to which they can freely push and receive real signed webhooks), not that the `context`/`sha` pertains to the victim's repository. `ExplicitParameters` only validates types (`sha: String`, `state: String`), not repository ownership. No `repository_name`/`stacks` scoping is applied in `StatusHandler#process`, unlike the base class's built-in `stacks` helper that other handlers use for scoping to `Repository.from_github_repo_name(repository_name)`.

### Impact Explanation
A `status` webhook that legitimately originates from and is signed for the attacker's own repository can flip the CI/status state (and thus `deployable?`/`blocked?`/merge eligibility) of an unrelated stack/repository's commit — a payload for one repository mutating another's commit/stack state, which is a Critical-class "cross-tenant record write" per the stated impact categories. Combined with `review_stacks_enabled: true, allow_all` (auto-provisioned review stacks execute the repository's `shipit.yml`), a `failure` status forcing `blocked?`/`deployable?` to flip can block or unblock deploys/merges that execute arbitrary `shipit.yml`-defined commands, escalating the blast radius toward command execution on the deploy host under specific configuration.

### Likelihood Explanation
This requires: (1) a target commit SHA that is present as a `Commit` row in more than one stack (achievable when stacks track shared upstream commits, PR base commits, or forked commits with identical SHAs — a scenario the codebase itself explicitly anticipates via the `(sha, stack_id)` unique index and the "PRs merged by another Shipit stack" test), and (2) knowledge of that SHA (visible to the attacker if they can see the shared commit, e.g. a public open-source base branch). The attacker's cost is a single unauthenticated `POST /webhooks` request signed with their own repository's webhook secret (which they legitimately possess since they control that repository). This is repeatable against any stack sharing a SHA with an attacker-controlled repository — I could not fully verify from the available index the exact GitHub sync/PR flow that produces such shared-SHA `Commit` rows across repositories owned by different parties without deeper tracing of `GithubSyncJob`/`MergeRequest#find_or_create_commit_from_github_by_sha!` in a live environment, which limits certainty on the practical frequency of SHA collisions across distinct GitHub repositories versus only within forks/branches of the same repository.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the `Handler#stacks` helper: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the `Commit` lookup to `stacks.flat_map(&:commits)` (or a `Commit.joins(:stack).merge(stacks).where(sha: params.sha)` scoped query) instead of a bare `Commit.where(sha: params.sha)`.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "a status webhook for repo A must not affect a commit belonging to repo B's stack" do
  attacker_repo = shipit_repositories(:attacker_repo) # owned/authenticated by attacker
  victim_stack = shipit_stacks(:shipit) # review_stacks_enabled: true, allow_all, requires ci/e2e
  shared_sha = "a" * 40

  # victim's commit row, currently passing
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")
  victim_commit.statuses.create!(stack_id: victim_stack.id, state: 'success', context: 'ci/e2e')
  assert_predicate victim_commit.reload, :deployable?

  payload = {
    'repository' => { 'full_name' => attacker_repo.full_name },
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/e2e'
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  # BROKEN BINDING: commit.stack.repository.full_name should equal payload['repository']['full_name']
  # before the write is applied. It does not — the victim's commit is mutated by a status
  # authenticated only for the attacker's own repository.
  refute_predicate victim_commit.reload, :deployable?, "victim stack's commit flipped by an unrelated repository's webhook"
end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
