### Title
Webhook signature verification binds only to the "organization" secret, not to the "repository" that handlers act on - cross-tenant status/deploy forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check based on `repository_owner`, a value read out of the *same untrusted JSON body* it is about to verify, and then the individual `Shipit::Webhooks::Handlers` act on a *different* field of that same body (`repository.full_name`, or in the case of `StatusHandler`, no repository scoping at all) to decide what gets written. The signature only proves "the sender knows the webhook secret configured for the organization named in this payload" — it proves nothing about the repository/commit fields the handlers subsequently trust and act on.

### Finding Description
`verify_signature` computes which secret to check against using a value taken from inside the very payload being verified: [1](#0-0) [2](#0-1) 

The HMAC (`verify_webhook_signature`) is computed over the entire raw body using the secret for whichever organization name the attacker put in `repository.owner.login` (or `organization.login`): [3](#0-2) 

Because the attacker chooses and signs the *entire* JSON body themselves (using a webhook secret they legitimately possess for their own organization/stack on a multi-tenant Shipit install), nothing stops them from putting an unrelated value in `repository.full_name` — the field the event handlers actually trust to select the target repository/stack: [4](#0-3) 

`PushHandler` uses this untrusted `repository.full_name` to look up the `Repository`/`Stack` to sync: [5](#0-4) 

`StatusHandler` is worse: it never resolves a repository at all — it selects `Commit` records purely by `sha`, globally across every repository/stack managed by the Shipit instance, and applies the attacker-supplied `state`/`context`/`description`/`target_url` to them: [6](#0-5) 

This is the same class of bug as the reported Weiroll issue: a signature/authorization check is bound to one identifier ("organization" whose secret was used, analogous to `idx`), while the code that performs writes trusts a different, unchecked identifier from the same payload ("repository"/"commit", analogous to the out-of-bounds pointer that ends up writing to unrelated state). The equality the code implicitly (and wrongly) assumes is:
`organization authenticated by signature == repository/commit actually written`
but nothing enforces this equality — the attacker fully controls both sides of the payload.

### Impact Explanation
On any Shipit deployment configured with more than one GitHub organization (`Shipit.github_organizations`/multi-org config, as documented in `config/secrets.development.shopify.yml`), a party who is a legitimate owner/administrator of *one* onboarded organization (and thus knows that organization's `webhook_secret`) can forge a validly-signed webhook whose `repository.owner.login`/`organization.login` names their own org, while embedding a `sha`/`context`/`state`/`repository.full_name` belonging to a completely different, victim organization's stack. Via `StatusHandler`, this lets the attacker inject a forged "success" CI status for an arbitrary commit SHA of a victim stack they have no access to — this is the same mechanism `Stack`/`DeploySpec` use to gate `deployable_status`/merge/continuous-deployment decisions. This crosses the "unauthorized deploy"/cross-tenant-write boundary called out as in-scope Critical/High impact. I was not able to fully trace, within the tool budget, the exact `DeploySpec`/`Stack#deployable_status` code path that consumes these forged `Status` rows to confirm it directly unblocks an actual deploy versus only affecting a UI status indicator — this would need to be verified by reading `app/models/shipit/status/group.rb` and `app/models/shipit/stack.rb`'s deployable-status logic in full before treating this as certain Critical impact rather than High.

### Likelihood Explanation
Requires the attacker to already be a legitimate onboarded tenant (owner of one org/stack) on a multi-tenant Shipit install — this is an "unprivileged" attacker relative to the victim organization's resources, satisfying the required trust-boundary crossing (their own credentials give them no rights over another org's repos/stacks). No GitHub App private key, `ApiClient` token, or session is required — only knowledge of their own webhook secret, which they are entitled to and can freely craft raw HTTP requests with.

### Recommendation
Do not select the verification secret from an attacker-controlled field inside the same payload being verified. Alternatives:
- Bind the webhook endpoint/secret to a specific, pre-registered repository/stack (route- or path-scoped) rather than trusting `repository.owner.login`/`organization.login` from the body.
- After signature verification, cross-check that the resolved `Stack`/`Repository`'s configured owning organization matches the organization whose secret validated the signature, rejecting the event otherwise.
- In `StatusHandler`, scope the `Commit` lookup by the repository referenced in the same signed payload (and verify that repository actually belongs to the verified organization) instead of matching `sha` globally across all repositories.

### Proof of Concept
1. Operate/administer Organization A on a shared Shipit instance, with a known `webhook_secret_A`.
2. Identify a target commit `sha` on victim Organization B's stack (commit SHAs are often knowable/public).
3. Build a JSON body:
```json
{
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/some-repo"},
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Sign it with `webhook_secret_A` and send it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves the secret via `repository_owner` = `"org-a"`, validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `commit.create_status_from_github!(params)`, injecting a forged status onto Organization B's commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
