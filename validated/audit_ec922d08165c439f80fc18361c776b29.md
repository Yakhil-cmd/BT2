### Title
Cross-record identity forgery via unauthenticated PR-number collision in `Commit#identify_merge_request` - (File: app/models/shipit/commit.rb)

### Summary
`Commit#identify_merge_request` binds a newly synced commit's `author` to an unrelated `MergeRequest#merge_requested_by` purely based on a numeric PR id parsed out of the commit's free-text message, with no check that the commit is actually that `MergeRequest`'s `merge_commit`/head SHA. Because the number is taken from attacker-authored commit text, an attacker who gets any commit onto the tracked branch (e.g., via a rebase-merged PR, where original commit messages are preserved verbatim as first-parent commits) can make Shipit attribute their commit to an arbitrary, unrelated user who requested a real, different merge.

### Finding Description
The broken binding is: `message_parser.pull_request_number == merge_request.number` is treated as equivalent to `commit.sha == merge_request.merge_commit.sha`, which is false in general.

Trace:
- `Commit.from_github` builds a new `Commit` from a GitHub commit object and lets `before_create :identify_merge_request` run [1](#0-0) .
- `identify_merge_request` parses the commit message via `CommitMessage`, looks up `stack.merge_requests.find_by(number: message_parser.pull_request_number)`, and if found sets `self.merge_request`, `self.pull_request_number`, `self.pull_request_title`, and critically `self.author = merge_request.merge_requested_by` — solely keyed off the numeric match, with no verification against `merge_request.merge_commit.sha`, `merge_request.head.sha`, or any SHA/authorship check [2](#0-1) .
- The number is extracted from raw commit message text using `CommitMessage::GITHUB_MERGE_COMMIT_PATTERN = /\AMerge pull request #(?<pr_id>\d+) from \S+\n\n(?<pr_title>.*)/` [3](#0-2) .
- Commits reach this code via `GithubSyncJob#append_commit` → `Commit.create_from_github!` → `from_github`, fed by `fetch_missing_commits` which walks `Shipit::FirstParentCommitsIterator` over `stack.github_commits` [4](#0-3) .

Exploit path: an attacker (no privileges) opens a PR against the target repo from their own fork and authors the commit(s) in their branch with arbitrary text, e.g. crafting a commit whose message is exactly `Merge pull request #<N> from foo/bar\n\n<title>`, where `<N>` is the number of an existing, unrelated `MergeRequest` row already present for that stack (created earlier through a legitimate `MergeRequest.request_merge!`/merge-queue flow, so `merge_requested_by` is a real trusted user). If a repository maintainer merges the attacker's PR using "rebase and merge" (or the commit otherwise lands as a first-parent, non-synthesized commit on the tracked branch — e.g. via fast-forward/rebase workflows), the attacker's own commit — with its attacker-controlled message — is synced by `GithubSyncJob` as a first-parent commit of the branch. `identify_merge_request` then matches on `pull_request_number == N` and sets the attacker's commit's `author` to `merge_request.merge_requested_by`, an unrelated legitimate user, and links `self.merge_request = merge_request` even though this commit is not that merge request's actual merge/head commit.

None of the existing guards apply here: this path does not go through `POST /webhooks` (so `verify_signature`/HMAC checks are irrelevant to the trust decision being made), does not require an `ApiClient` token or session, and the vulnerable code performs no comparison between the commit's `sha`/`parents` and `merge_request.merge_commit`/`head` before trusting the author binding.

### Impact Explanation
The record actually mutated is a `Shipit::Commit` row for the target repository's stack: its `author`, `merge_request_id`, `pull_request_number`, and `pull_request_title` are set based on attacker-supplied text, misattributing authorship/merge-request identity to an unrelated trusted user. This corrupts `deploy_requested_at` (which relies on `merge_request.merged?`) and any downstream logic/UI/serializers that trust `commit.author` or `commit.merge_request` (e.g. `CommitSerializer`, `merge_status_controller`, deploy history, audit trails). It does not by itself grant deploy/merge authorization or leak credentials, but it lets an outside contributor forge the recorded identity behind a commit/merge-request association on a stack they don't own — a data-integrity/identity-forgery issue scoped to the target stack's commit and merge-request records.

### Likelihood Explanation
Exploitation requires: (1) the target repository accepts PRs from forks, (2) an existing `MergeRequest` with a colliding number already exists for the stack (a very common condition on any actively used merge-queue-enabled stack), and (3) a maintainer merges the attacker's PR using a merge strategy (rebase, or fast-forward) that preserves the attacker's original commit message verbatim as a first-parent commit rather than generating a fresh synthetic merge-commit message. This depends on repository/merge-method configuration and normal maintainer action rather than any additional attacker privilege — the attacker only needs to write a commit message in their own fork, which is fully within an "unprivileged PR author" capability. Feasibility is moderate-to-high on repos configured to allow rebase/squash-with-custom-message merges, and repeatable against any stack where a matching `MergeRequest` number can be found or predicted (numbers are sequential/enumerable via the public GitHub PR list).

### Recommendation
In `Shipit::Commit#identify_merge_request`, do not trust the parsed PR number alone to bind `merge_request`/`author`. Only associate a `MergeRequest` and inherit its `merge_requested_by` when the commit is verified to be that merge request's actual merge commit — e.g., require `merge_request.merge_commit_sha == sha` (or verify the commit's parent SHAs correspond to `merge_request.head.sha` and `merge_request.base_commit.sha`) before setting `self.author = merge_request.merge_requested_by` and `self.merge_request = merge_request`. Falling back to the parsed `pull_request_number`/`pull_request_title` for display purposes can remain, but the trust-bearing `author` assignment must depend on cryptographic/SHA identity, not free-text pattern matching.

### Proof of Concept
Minitest plan (`test/models/commits_test.rb`, no live GitHub, uses existing fixtures under `test/fixtures/shipit/merge_requests.yml`):

```ruby
test "identify_merge_request binds author from an unrelated merge request via crafted commit message" do
  stack = shipit_stacks(:shipit)
  unrelated_merge_request = shipit_merge_requests(:shipit) # has a real merge_requested_by, e.g. user "walrus"
  trusted_user = unrelated_merge_request.merge_requested_by
  refute_nil trusted_user

  attacker_message = "Merge pull request ##{unrelated_merge_request.number} from attacker/evil-fork\n\nlooks legit"

  commit = Shipit::Commit.create!(
    stack: stack,
    sha: '0' * 40, # attacker-controlled sha, NOT unrelated_merge_request.merge_commit&.sha
    message: attacker_message,
    author: nil,
    committer: nil,
    committed_at: Time.now,
    authored_at: Time.now
  )

  # BROKEN BINDING under test:
  # commit.sha != unrelated_merge_request.merge_commit&.sha  (commit is NOT that MR's real merge commit)
  # yet commit.author ends up == unrelated_merge_request.merge_requested_by
  refute_equal unrelated_merge_request.merge_commit&.sha, commit.sha
  assert_equal trusted_user, commit.author
  assert_equal unrelated_merge_request, commit.merge_request
end
```

This demonstrates that `commit.sha == merge_request.merge_commit.sha` is false while `commit.author == merge_request.merge_requested_by` is true, proving the identity-binding is forgeable from attacker-controlled commit text alone.

    def identify_merge_request
      return unless message_parser.pull_request?

      if merge_request = stack.merge_requests.find_by(number: message_parser.pull_request_number)
        self.merge_request = merge_request
        self.pull_request_number = merge_request.number
        self.pull_request_title = merge_request.title
