### Title
`StatusHandler#process` writes `Status` records for commits belonging to any repository, not just the reporting one - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commits with `Commit.where(sha: params.sha)`, a global lookup with no repository/stack scoping, unlike `CheckSuiteHandler#process` which correctly restricts mutation to `stacks.where(branch: ...)` derived from `payload['repository']['full_name']`. Any commit sha that exists in more than one Shipit-tracked `Stack` (e.g., a shared ancestor commit between an upstream repository and a fork that is separately tracked, or a repository added twice under different names) will have its `Status` mutated by a `status` webhook delivered for either repository, regardless of which repository actually reported it.

### Finding Description
The broken binding is:
`commit.stack.repository.full_name == payload['repository']['full_name']` — this is required for a status update to be authorized to that repository's stack, but it does not hold in `StatusHandler#process`.

Code path:
- `app/models/shipit/webhooks/handlers/handler.rb` defines `stacks` as `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, i.e. the set of stacks that belong to the repository named in the incoming payload [1](#0-0) .
- `CheckSuiteHandler#process` uses this correctly: `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...) }`, so a `check_suite` event for repo A can only touch commits belonging to stacks of repo A [2](#0-1) .
- `StatusHandler#process` instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query over the entire `commits` table, with no reference to `stacks`, `repository_name`, or `payload['repository']` at all [3](#0-2) .
- `create_status_from_github!` on `Commit` unconditionally writes a new `Status` row and can trigger `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` — real side effects on whatever stack the matched commit happens to belong to [4](#0-3) [5](#0-4) .

Existing guards do not close this gap:
- `WebhooksController#verify_signature` verifies the payload was really sent by GitHub for the organization named in `payload['repository']['owner']['login']` via `Shipit.github(organization: repository_owner).verify_webhook_signature`, and `drop_unhandled_event`/`check_if_ping` only filter by event type, not by repository identity relative to the commit being mutated [6](#0-5) . None of these bind the reported `sha` to the reporting repository — that binding is only enforced by handlers that consult `stacks`, and `StatusHandler` doesn't.
- `ExplicitParameters` schema in `StatusHandler` only validates the shape of `sha`, `state`, etc.; it performs no ownership check [7](#0-6) .

Exploit flow: if the attacker controls (owns/administers) a repository that is itself tracked by Shipit as a `Stack`, and that repository shares any commit sha with a `Stack` belonging to a different repository (realistic via forks or repositories that share history, since git commit ids are content-addressed and identical for shared ancestor commits), the attacker can cause GitHub to deliver — or can otherwise produce — a validly signed `status` event for their own repository whose `sha` matches a commit in the *other* stack. `StatusHandler#process` will then create/replicate a `Status` on that foreign commit, affecting the foreign stack's deployability/merge state, even though `Handler#stacks` for the attacker's own repository would correctly resolve to only the attacker's own stack.

### Impact Explanation
The unscoped `Commit.where(sha:)` lookup allows a signed webhook for repository A to write `Status` rows on commits that belong to repository B's `Stack`, and those writes have real effects: they change `commit.status`/`deployable?`, can flip `blocked?`/CI gating for unrelated stacks, and trigger `stack.schedule_merges` for the victim stack, potentially unblocking automatic merges or continuous delivery on a repository the attacker does not control. This matches the "payload for one repository mutating another's stack/commit" Critical category. The blast radius is bounded by the precondition that the sha actually appears in more than one tracked stack (shared history, e.g., forks or repos added under multiple names), so it is repeatable specifically against any pair of stacks that share commit history, not against arbitrary unrelated repositories.

### Likelihood Explanation
Exploitation requires: (1) the attacker to own/administer a repository that is itself registered as a Shipit `Stack` (so a legitimately signed webhook for it can be delivered/produced without any Shipit secret), and (2) that repository to share at least one commit sha with a different tracked stack (realistic for forks of a tracked repo, or repositories that were both derived from common history) — no SHA1 collision is required, only shared git history. Given those two preconditions, the attack costs nothing beyond normal GitHub repository operations (setting a commit status via the GitHub API on a commit that exists in the attacker's own repo history) and is fully repeatable. The signature check in `WebhooksController#verify_signature` is satisfied normally because the event is genuinely signed by GitHub for the attacker's own repository/organization — it does not, and cannot, verify that the `sha` inside the payload belongs to that same repository.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler#process` is scoped: restrict the `Commit` lookup to commits within `stacks` (i.e., `stacks.flat_map(&:commits)` or an equivalent `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) so only commits belonging to a stack of the repository named in `payload['repository']['full_name']` can be updated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, not shown/created here per scope, but illustrating the binding):
1. Create `repo_a = Repository` with `Stack stack_a` and `repo_b = Repository` (different `github_repo_name`) with `Stack stack_b`.
2. Create `commit_b = Commit.create!(stack: stack_b, sha: 'deadbeef...')`.
3. Assert precondition equality fails: `Handler.new({'repository' => {'full_name' => repo_a.github_repo_name}}).send(:stacks)` returns `Stack.none` and does not include `stack_b` — i.e. `repo_a.github_repo_name != stack_b.repository.github_repo_name`.
4. Build payload: `{'repository' => {'full_name' => repo_a.github_repo_name}, 'sha' => commit_b.sha, 'state' => 'success'}`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
6. Assert `commit_b.reload.statuses.count == 1` and `commit_b.status.success?` — proving a `Status` was written to repo B's commit from a payload claiming to be repo A, despite `stacks` for repo A never resolving to `stack_b`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
