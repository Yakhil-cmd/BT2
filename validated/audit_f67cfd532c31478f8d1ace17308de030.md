Based on my investigation, I found a plausible analog to CVE-2017-14518's floating point exception pattern in the oscript formula evaluator, but I was not able to confirm whether it is exploitable to crash the node process (as opposed to being caught/turned into a soft AA-bounce), since I could not find a wrapping `try/catch` around the whole `exports.evaluate` call chain in `aa_composer.js` before running out of iterations.

### Title
Potential uncaught exception from `ln()` of a negative number in fractional power (`^`) formula evaluation - (File: formula/evaluation.js)

### Summary
In the `'^'` (pow) case of the oscript arithmetic evaluator, when the exponent is a non-integer, the code unconditionally computes `prevV.ln()` on the base regardless of its sign, in order to implement fractional exponentiation via `exp(ln(base) * exponent)`.

### Finding Description [1](#0-0)  shows the `pow` branch: for `e^x` and integer exponents it takes fast paths, but for any other case (fractional exponent) it falls through to `prevV.ln()` without first validating that `prevV` (the base) is non-negative. Mathematically, the natural logarithm of a negative number is undefined, and depending on the `decimal.js` library's behavior this either returns `NaN` (which would be caught downstream by `isFiniteDecimal` checks such as [2](#0-1)  and `formula/common.js` `isFiniteDecimal`) or throws a library-level error. I was unable to confirm which behavior the vendored `decimal.js` exhibits, nor whether the call is wrapped in a try/catch anywhere up the call chain in `aa_composer.js` (11 references to the evaluate function were found there, but I did not have iterations left to inspect them).

### Impact Explanation
If `Decimal.prototype.ln()` throws on a negative input rather than returning `NaN`, and if that exception is not caught somewhere in the AA trigger-processing pipeline (`aa_composer.js`), any unprivileged unit poster could crash node processing by sending an AA trigger where an oscript formula evaluates something like `(-2) ^ 0.5`. This would match the report's floating point exception bug class: an arithmetic edge case reachable via untrusted input causing an unhandled runtime fault, potentially producing a network-wide inability to process AA triggers if all/most full nodes crash simultaneously on the same malicious trigger.

### Likelihood Explanation
Uncertain — the surrounding code shows a general pattern of defensive `isFiniteDecimal`/`isFinite` checks after nearly every arithmetic operation elsewhere in `formula/evaluation.js` (e.g. [3](#0-2)  `containsNonFiniteNumber`, and repeated `setFatalError` guards), suggesting the maintainers are aware of and defend against non-finite results. It's plausible this specific `ln()` call is already safe because `decimal.js` returns `NaN` for `ln` of a negative number (matching the finite-decimal check style used throughout the file), in which case this would not be a crash but a normal fatal-error/bounce path.

### Recommendation
This requires confirmation before treating as a real, exploitable vulnerability:
1. Determine experimentally/from `decimal.js` source whether `Decimal.prototype.ln()` throws a `RangeError`/`DecimalError` on negative input or returns `NaN`.
2. If it throws, either guard the fractional-power branch with an explicit sign check on `prevV` (returning a formula fatal error via `setFatalError` for negative base with fractional exponent, consistent with the rest of the file), or wrap the `prevV.ln()` call in a try/catch that funnels into `setFatalError`.
3. Audit all other direct `decimal.js` method calls in `formula/evaluation.js` (e.g. `sqrt`, `ln` as first-class formula operators around line 243) for the same negative-input exception risk, since `sqrt`/`ln` of negative numbers have the identical mathematical edge case.

### Proof of Concept
Not able to construct a confirmed PoC without verifying the `decimal.js` throw behavior. The suspected trigger would be an AA formula such as:
```
$x = (-2) ^ 0.5;
```
posted inside an AA's `init`/`state`/message formula and triggered by any unprivileged unit sender, per the code path shown in [1](#0-0) .

---

**Important caveat**: I could not fully verify this finding within the available tool budget — specifically (a) the exact throw/NaN behavior of the vendored `decimal.js` `ln()` on negative numbers, and (b) whether `aa_composer.js`'s calls into `evaluate()` (11 call sites) wrap execution in a try/catch that would turn any such exception into a safe bounce rather than a process crash. Given the pervasive defensive `isFiniteDecimal` checks elsewhere in the same file, it is equally plausible that this is already safely handled and **not exploitable**. I am reporting this with explicit uncertainty rather than asserting it as a confirmed vulnerability, per the instruction to avoid guessing.
