### Title
Attacker-controlled `ft_on_transfer` `msg` array drives unbounded, ungas-metered trie prefetching in `prefetch_kaiching` - (File: `runtime/runtime/src/prefetch.rs`)

### Summary
`TriePrefetcher::prefetch_kaiching` unconditionally parses the `msg` field of a `FunctionCall` receipt matching a hardcoded `(sender, receiver, method_name)` triple and issues two `prefetch_trie_key` DB lookups per entry of an attacker-controlled `rewards` array, with no cap on array length. Because this triple (`wallet.kaiching` → `earn.kaiching`::`ft_on_transfer`) is exactly the standard, permissionless NEP-141 `ft_transfer_call` callback pattern, any unprivileged holder of the corresponding fungible token can trigger this code path with a fully attacker-crafted `msg`, causing validator nodes to perform disk I/O work that scales with attacker-chosen JSON size rather than with the gas the triggering receipt pays.

### Finding Description
`prefetch_kaiching` is invoked from `prefetch_receipts_data` whenever a `FunctionCall` action on a receipt matches an entry in `PrefetchApi::kaiching_prefetch_config` by exact `(predecessor_id, receiver_id, method_name)` triple: [1](#0-0) 

The default, shipped configuration hardcodes this triple as `sender: "wallet.kaiching"`, `receiver: "earn.kaiching"`, `method_name: "ft_on_transfer"` for every node that has not overridden `StoreConfig`: [2](#0-1) 

`ft_on_transfer` is the standard NEP-141 callback: any account holder can call `wallet.kaiching::ft_transfer_call(receiver_id="earn.kaiching", amount, msg)`, and the token contract forwards the caller-supplied `msg` verbatim into the `earn.kaiching::ft_on_transfer(sender_id, amount, msg)` receipt it creates. This makes the `msg` argument — and therefore the JSON structure `prefetch_kaiching` parses — fully attacker-controlled, without requiring the attacker to own `wallet.kaiching` itself.

Inside `prefetch_kaiching`, the function parses `msg` as JSON, extracts `rewards` as an array, and for every element performs two independent `TrieKey::ContractData` lookups (2 disk-backed prefetch requests per tuple), with no limit on the number of tuples in the array: [3](#0-2) 

The amount of prefetching work is bounded only by the attacker-chosen size of the `rewards` array (constrained only by max transaction/args size limits), not by the gas actually charged for the `FunctionCall` receipt, which the caller (the token contract) budgets essentially as a linear byte-cost of the promise's `args`. The design doc at the top of the file explicitly acknowledges this class of risk ("an adversary user can look at the prefetcher's heuristics and force it to mispredict... doing (useless) work that is not covered by gas fees") but `prefetch_kaiching` does not implement any cap on the number of array entries processed, unlike the bounded IO-thread/queue limits described generally for the prefetcher.

The only partial mitigation is that `prefetch_trie_key` returns `Err(PrefetchError::QueueFull)` once the shared per-shard prefetch queue is saturated, and `prefetch_kaiching`/`prefetch_receipts_data` propagate this error via `?`, aborting further prefetching for the *rest of the chunk's receipts* as well: [4](#0-3) [5](#0-4) 
This bounds the *maximum* number of enqueued lookups triggered by a single malicious receipt to the queue capacity, but that capacity's worth of speculative disk work is still driven purely by attacker-chosen data, and — more importantly — a single crafted receipt can starve/abort prefetching for all subsequent receipts in the same chunk once the queue fills, degrading prefetching effectiveness network-wide for that block.

### Impact Explanation
This allows an ordinary account holder (any holder of the relevant fungible token, or more generally anyone able to trigger the hardcoded sender/receiver/method triple through the standard NEP-141 callback flow) to force every validator node running the default prefetch configuration to perform disk I/O proportional to an attacker-chosen JSON array size embedded in `ft_transfer_call`'s `msg`, while paying gas only proportional to the (cheap) byte size of that argument. This is an instance of underpriced/free execution: computational (I/O) cost imposed on the network is decoupled from the gas fee paid, matching NEAR's "greatly increasing the computational cost of the network" High-severity impact class. It can also be leveraged to fill the shared prefetch queue and starve prefetching for other receipts in the same chunk, degrading performance across the shard rather than just the attacker's own call.

### Likelihood Explanation
The precondition is that a node runs the default `StoreConfig` (true for essentially all nodes unless explicitly overridden) and that `kaiching_prefetch_config`'s exact triple corresponds to a live, permissionless NEP-141 flow (`ft_transfer_call` → `ft_on_transfer`), which is a standard, publicly callable token-transfer mechanism, not something requiring elevated privilege, a leaked key, or social engineering. Any account holding (or able to acquire) the relevant token can repeatedly submit such calls at will, making this readily reproducible and repeatable. The severity is nevertheless bounded by the prefetch queue's fixed capacity per attempt (not literally unbounded per receipt), which should be factored into an exact quantitative impact assessment.

### Recommendation
Cap the number of `rewards` (and similarly `steps_batch`/`amounts`) entries processed per receipt in `prefetch_kaiching` (and the sibling `prefetch_sweat_record_batch`/`prefetch_claim_sweat_record_batch_for_hold` functions) to a small constant proportional to the gas actually paid for the triggering `FunctionCall`, and make queue-full/error conditions local to the offending receipt only (do not propagate failure via `?` in a way that aborts prefetching for unrelated subsequent receipts in `prefetch_receipts_data`).

N entries ...]}"}` with N chosen near the max allowed args/transaction size.
2. Call `TriePrefetcher::prefetch_receipts_data` (with `kaiching_prefetch_config` set to the default triple) and assert that the number of enqueued `prefetch_trie_key` calls (`prefetch_api.num_prefetched_and_staged()` / `prefetch_enqueued` counter) scales linearly with N and is not bounded by/related to any gas value charged for the receipt.
3. As a multi-shard `test-loop-tests` scenario: deploy a `wallet.kaiching`-analogous FT contract and `earn.kaiching`-analogous receiver on one shard, submit repeated `ft_transfer_call` transactions with maximal `msg` payloads from an unprivileged account, and assert chunk production continues on all shards but observe/log disproportionate I/O counters (`PREFETCH_ENQUEUED`, `PREFETCH_QUEUE_FULL` metrics) relative to gas burnt, confirming the amplification and the queue-starvation side effect on other receipts in the same chunk.

    fn prefetch_trie_key(&self, trie_key: TrieKey) -> Result<(), PrefetchError> {
        let res = self.prefetch_api.prefetch_trie_key(self.trie_root, trie_key);
        match res {
            Err(PrefetchError::QueueFull) => {
                self.prefetch_queue_full.inc();
                tracing::debug!(target: "runtime::prefetch", "IO scheduler input queue is full, dropping prefetch request");
            }
            Err(PrefetchError::QueueDisconnected) => {
                // This shouldn't have happened, hence logging warning here
                tracing::warn!(target: "runtime::prefetch", "IO scheduler input queue is disconnected, dropping prefetch request");
            }
            Ok(()) => self.prefetch_enqueued.inc(),
        };
        res
    }
