### Title
Unchecked division by zero in `token_price_x32` causes an ungraceful panic/revert instead of a clear error on every swap - ([File: programs/cp-swap/src/states/pool.rs])

### Summary
`PoolState::token_price_x32` computes oracle price ratios using raw integer division (`/`) instead of `checked_div`, unlike every other arithmetic path in the program which consistently uses `checked_*` helpers and returns a descriptive `ErrorCode`. If either side of the pool's fee-adjusted vault balance is zero, this function panics with Solana's generic arithmetic-error message rather than reverting with a meaningful custom error, mirroring the reported analog where an unchecked zero denominator produces an unexpected, unhelpful revert.

### Finding Description
`token_price_x32` is called from `PoolState::get_swap_params`, which is invoked on every single `swap_base_input` and `swap_base_output` call: [1](#0-0) 

The two-sided division uses `token_0_amount` and `token_1_amount` (the fee-adjusted vault balances returned from `vault_amount_without_fee`) directly as denominators without any `checked_div`/`ok_or` guard: [2](#0-1) 

This is called from `get_swap_params`, on both trade directions, before the actual swap math is executed: [3](#0-2) 

Every other division/multiplication in the swap/deposit/withdraw code paths is wrapped in `checked_*` combinators and mapped to an explicit `ErrorCode` (e.g. `ZeroTradingTokens`, `MathOverflow`, `InsufficientVault`) so that a malformed state produces an informative revert instead of a raw arithmetic panic: [4](#0-3) [5](#0-4) 

`token_price_x32`, however, is the one place that departs from this convention, using plain `/` on values (`token_0_amount as u128`, `token_1_amount as u128`) that are derived from user/attacker-influenced vault balances minus accumulated fee ledgers (`vault_amount_without_fee`). If the vault's raw token balance (fully attacker-influenced by prior trade activity) equals exactly the accumulated `protocol_fees_token_x + fund_fees_token_x + creator_fees_token_x` for that side, `vault_amount_without_fee` returns `0` for that side, and the subsequent division by that zero value panics.

### Impact Explanation
This is reachable by an ordinary swapper submitting `swap_base_input`/`swap_base_output` once pool state naturally reaches (or is driven toward, over repeated trades) a fee-ledger-equal-to-raw-balance condition on either token side. Instead of returning a clean custom error like `ZeroTradingTokens`/`MathOverflow` (as every analogous arithmetic path does), the transaction panics with Solana's default arithmetic-overflow/divide-by-zero trap. Functionally, this degrades to an uninformative denial-of-service on swaps for that pool state, consistent with the referenced report's classification (unexpected, unhandled revert due to a missing zero-denominator check on a value fully controllable by pool activity) rather than a fund-theft or freezing bug on its own.

### Likelihood Explanation
The condition requires the fee-adjusted vault balance for one side to become exactly zero, which is a narrow edge case reachable only through specific sequences of deposits/withdrawals/fee accrual that drive the tradeable balance to zero while raw vault balance still equals the fee ledger. It is not trivially triggerable in a single attacker transaction with arbitrary chosen amounts, so likelihood is low-to-moderate; the missing `checked_div` is nonetheless a real deviation from the codebase's otherwise consistent checked-arithmetic-with-explicit-error convention.

### Recommendation
Replace the raw divisions in `token_price_x32` with `checked_div` chained via `.ok_or(ErrorCode::...)?` (or an equivalent explicit zero-check before dividing), consistent with `vault_amount_without_fee` and the rest of the curve/calculator code, so that a degenerate zero-balance state returns a descriptive Anchor error instead of an unhandled arithmetic panic.

### Proof of Concept
Not independently constructible from the indexed code alone without full state-transition simulation across deposits/withdrawals/fee accrual to drive one side's `vault_amount_without_fee` to exactly zero; the root-cause code path (`token_price_x32` invoked unconditionally on every swap via `get_swap_params`) is confirmed above.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

    pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
        let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
