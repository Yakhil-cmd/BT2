### Title
Unauthenticated Fast-Sync Peer Can Write Staking Info to Arbitrary DB Slots, Corrupting Validator-Set and Reward-Distribution Epoch Boundaries — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

### Summary
During fast sync, a remote P2P peer supplies `P2PStakingInfo` objects whose `BlockNum` field is fully attacker-controlled. The `DeliverStakingInfos` validation callback is an explicit no-op (marked `TODO`), and `commitFastSyncData` uses `result.StakingInfo.BlockNum` — not `result.Header.Number` — as the database key when calling `PutStakingInfoToDB`. A malicious peer can therefore write staking info for block X into DB slot Y, corrupting the staking epoch boundaries that govern validator-set selection and KAIA reward distribution for all pre-Kaia-hardfork blocks.

### Finding Description

**Step 1 — No validation in `DeliverStakingInfos`.**

`DeliverBodies` validates the transaction root against `header.TxHash`; `DeliverReceipts` validates the receipt root against `header.ReceiptHash`. `DeliverStakingInfos` has an explicit no-op:

```go
// datasync/downloader/queue.go:956-958
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
```

The `reconstruct` closure then blindly assigns the peer-supplied object to the result:

```go
// datasync/downloader/queue.go:961-963
reconstruct := func(index int, result *fetchResult) {
    result.StakingInfo = stakingInfoList[index]
    result.SetStakingInfoDone()
}
```

No check that `stakingInfoList[index].BlockNum == header.Number` is performed anywhere. [1](#0-0) 

**Step 2 — `commitFastSyncData` uses the peer-supplied `BlockNum` as the DB key.**

```go
// datasync/downloader/downloader.go:1881-1883
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
}
```

The key passed to `PutStakingInfoToDB` is `result.StakingInfo.BlockNum` (attacker-controlled), not `result.Header.Number` (the canonical block number the staking info was requested for). [2](#0-1) 

**Step 3 — `PutStakingInfoToDB` is an unconditional overwrite.**

```go
// kaiax/staking/impl/schema.go:73-75
func (s *StakingModule) PutStakingInfoToDB(sourceNum uint64, stakingInfo *staking.StakingInfo) {
    WriteStakingInfo(s.ChainKv, sourceNum, stakingInfo)
}
```

`WriteStakingInfo` calls `db.Put(stakingInfoKey(num), b)` — a plain overwrite with no guard. [3](#0-2) 

**Step 4 — `GetStakingInfo` trusts whatever is in the DB.**

```go
// kaiax/staking/impl/getter.go:58-63
if !isKaia {
    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
        s.stakingInfoCache.Add(sourceNum, si)
        return si, nil
    }
}
```

There is no cross-check that `si.SourceBlockNum == sourceNum`. Whatever the attacker wrote at key `Y` is returned verbatim when `sourceBlockNum(num) == Y`. [4](#0-3) 

### Impact Explanation

The staking info stored at `sourceNum` determines:
- **Validator set / proposer selection** (WeightedRandom mode uses staking amounts from this record).
- **Reward addresses** (`RewardAddrs`, `KEFAddr`, `KIFAddr`, `KPFAddr`) used by the reward module to distribute block rewards.

An attacker who swaps `BlockNum` values across two staking-interval boundaries (e.g., sends `BlockNum=2000` for the block-1000 request and `BlockNum=1000` for the block-2000 request) achieves two simultaneous effects:

1. **DB slot Y overwritten with wrong data** → `GetStakingInfo` for all blocks whose `sourceBlockNum` maps to Y returns attacker-chosen validator addresses and reward addresses, causing unauthorized rerouting of block rewards and potentially excluding honest validators from proposer selection.
2. **DB slot X left empty** → `GetStakingInfo` for blocks whose `sourceBlockNum` maps to X falls back to `getFromStateByNumber`; after fast sync the historical state is unavailable, so this call returns an error, breaking block processing entirely for those epochs.

Both effects are within the allowed impact gate: unauthorized reward distribution and persistent corruption of chain state that breaks canonical execution.

### Likelihood Explanation

- Fast sync is a standard, publicly reachable P2P flow; any node on the network can act as a sync peer.
- The attacker only needs to be selected as the staking-info provider for one sync session — no key compromise, no majority collusion, no governance privilege required.
- The `TODO` comment in the validation callback confirms the guard was intentionally deferred and has never been implemented.
- The same missing check exists in `commitPivotBlock` for the pivot block's staking info. [5](#0-4) 

### Recommendation

1. **In `DeliverStakingInfos`**, replace the no-op `validate` with a check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`, mirroring how `DeliverBodies` validates `TxHash` and `DeliverReceipts` validates `ReceiptHash`.
2. **In `commitFastSyncData` and `commitPivotBlock`**, use `result.Header.Number.Uint64()` as the DB key instead of `result.StakingInfo.BlockNum`, so the write location is always determined by the locally-verified header, not the peer-supplied payload.
3. Optionally add a consistency assertion: `result.StakingInfo.BlockNum == result.Header.Number.Uint64()` before calling `PutStakingInfoToDB`, and drop/penalize the peer on mismatch.

### Proof of Concept

```go
// Construct a fetchResult where StakingInfo.BlockNum != Header.Number
result := &fetchResult{
    Header: &types.Header{Number: big.NewInt(1000)},
    StakingInfo: &staking.P2PStakingInfo{
        BlockNum:         2000,          // attacker-controlled mismatch
        CouncilNodeAddrs: []common.Address{attackerAddr},
        // ... attacker reward addresses ...
    },
}

// commitFastSyncData calls:
//   PutStakingInfoToDB(2000, ...)   ← writes to slot 2000, not 1000
// DB slot 1000 remains empty; slot 2000 is overwritten with attacker data.

// Later, GetStakingInfo(num) where sourceBlockNum(num)==2000
// returns attacker-controlled validator/reward addresses.
// GetStakingInfo(num) where sourceBlockNum(num)==1000
// misses DB, fails state lookup → error → block processing broken.
```

The unit test the question proposes — constructing a `fetchResult` with `StakingInfo.BlockNum != Header.Number` and asserting `PutStakingInfoToDB` is rejected — would currently **fail** (the mismatch is silently accepted), confirming the vulnerability.
