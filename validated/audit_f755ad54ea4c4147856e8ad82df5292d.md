### Title
Cross-organization webhook forgery: signature is verified against the payload's `owner.login`, but handlers act on a different, uncorrelated `repository`/`sha` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC validation based on `repository_owner`, which is read straight out of the untrusted, unsigned-at-that-point JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once that check passes, `create` dispatches the *same raw payload* to handlers (`PushHandler`, `StatusHandler`, `MembershipHandler`, `PullRequest::*`) that resolve the object to mutate from a **different, independent field** of the payload (`payload.dig('repository','full_name')` in `Handler#repository_name`, or in `StatusHandler`'s case, no repository field at all — just `sha`). Nothing cross-checks that the organization whose secret validated the signature is the same organization that owns the repository/commit being written to. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the report's core mismatch: a value that is checked/authenticated under one identity is used unchecked for a materially different purpose downstream. Here the "equality" that is assumed but never enforced is:

`organization whose webhook_secret validated X-Hub-Signature == organization/repository that the handler actually writes to`

Concretely:
- `Shipit.github(organization: repository_owner)` picks a `GitHubApp` (and its `webhook_secret`) using `repository_owner`, computed from `repository.owner.login` (falling back to `organization.login`). [4](#0-3) [5](#0-4) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unset — which the setup docs explicitly document as optional per-organization in the multi-app config (`webhook_secret: # nil`). [6](#0-5) [7](#0-6) 
- After signature verification, `create` re-parses the same raw body and fans it out to every registered handler for the event, unmodified. [8](#0-7) 
- Every handler determines the repository/stack to act on from `payload.dig('repository', 'full_name')` (a field never inspected during signature verification), e.g. `PushHandler` triggers `stack.sync_github` for any stack matching that `full_name` + branch. [9](#0-8) [10](#0-9) 
- `StatusHandler` doesn't even require a `repository` key — it writes a `Status` onto **any** `Commit` in the entire Shipit installation matching `params.sha`, with zero repository scoping at all. [11](#0-10) 

Before the attack: in a multi-organization deployment (`Shipit.github_organizations` > 1, per `docs/setup.md`), organization A (e.g., a low-value/sandbox org onboarded without a `webhook_secret`, or whose secret has otherwise been obtained) authenticates only requests whose `repository.owner.login == "A"`. Organization B is a separately, properly-secured org with tracked repositories/stacks.

After the attacker's request: the attacker crafts one HTTP POST to `/webhooks` with `X-Github-Event: push` (or `status`, `membership`, `pull_request`), sets `repository.owner.login = "A"` (satisfying/bypassing the weak-secret check), but sets `repository.full_name = "B/private-repo"` (or, for `status`, simply supplies the `sha` of a commit belonging to org B's stack). `verify_signature` passes using org A's (blank or attacker-known) secret, and the handler then mutates state belonging to org B — e.g. forcing `stack.sync_github(expected_head_sha: ...)` on a B stack, or writing a fabricated CI `Status` (state `success`) onto a B commit, which is exactly the kind of status Shipit's deploy safety checks (`commit.deployable?`) consult before allowing a deploy.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary called out explicitly in scope, and reaches **High** impact per the rubric: an unauthenticated attacker who controls (or merely knows is unsecured) one configured organization's webhook secret can inject forged, unauthenticated write operations (fabricated commit statuses, forced re-sync, PR/review-stack archival/creation, team membership changes) against **any repository tracked by the Shipit instance**, regardless of that repository's own organization/secret. Forged `success` statuses can directly undermine `commit.deployable?`-gated deploy safety checks, which is a step toward an unauthorized deploy.

### Likelihood Explanation
Requires the operator to run Shipit with the multi-organization GitHub App configuration (explicitly documented and supported) and for at least one configured organization to have a blank/weak `webhook_secret` (explicitly documented as optional) or a leaked one. Given `webhook_secret` optionality is a first-class, documented feature (not a misconfiguration outside the engine's control), and no additional code anywhere cross-validates `repository_owner` against `payload.repository.full_name`, this is a real gap in the engine's own trust model, exploitable with a single crafted, unauthenticated HTTP request — no session, API token, or GitHub credentials required.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, enforce that the organization whose secret validated the signature is the same organization that owns the repository the handler is about to mutate: derive `repository_owner` from the same `full_name` field the handlers use (or vice versa), and reject the payload (422) if `repository.owner.login` and the owner segment of `repository.full_name` diverge. Additionally, `StatusHandler` should require and check a `repository` field and scope its `Commit` lookup to that repository (`stacks_contributed_to`/`Repository.from_github_repo_name`) rather than matching `sha` globally across the whole installation.

### Proof of Concept
Given a Shipit instance configured with the multi-org github schema (`docs/setup.md` "Using Multiple Github Applications") where org `OrgA` has `webhook_secret: nil` and org `OrgB` has a real secret protecting tracked repository `OrgB/service`:

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything     # ignored: OrgA has no secret configured

{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<sha of a real commit belonging to OrgB/service stack>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```

`verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` unconditionally (blank secret), per [6](#0-5) . `StatusHandler#process` then writes a forged `success` status onto the OrgB commit purely by `sha`, with no relation to `OrgA` at all, per [3](#0-2) , satisfying deploy-safety CI checks for a repository the attacker was never authenticated against.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
