Key finding: `StatusHandler#process` matches on commit `sha` alone, across **all stacks** — `Commit.where(sha: params.sha).each`, with no scoping to the `repository.full_name` from the payload. Combined with the fact that signature verification only authenticates *which organization's secret* was used (`repository_owner`, i.e., `repository.owner.login`), never that the org matches the `full_name`/stack the handler actually mutates, and that `webhook_secret` is documented/allowed to be blank (`return true unless webhook_secret` in `lib/shipit/github_app.rb`), an attacker who controls (or is granted, e.g. via a free personal GitHub org with no `webhook_secret` configured in this Shipit instance) an organization with no configured secret can send arbitrary, validly-"verified" webhook deliveries that plant CI `status` records against **any commit sha figure that happens to exist in any other stack/repository** in the whole Shipit instance, since `StatusHandler` never checks `repository.full_name` against the commit's stack.### Title
Cross-stack CI status forgery via organization/repository binding gap in webhook signature verification - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC `webhook_secret`) to use for authenticating an inbound webhook based solely on `repository.owner.login` (or `organization.login`) taken from the unauthenticated JSON body, but the event handlers that actually mutate state (e.g. `StatusHandler`) never re-check that the `repository.full_name` in that same payload belongs to that organization, nor scope their writes to a specific repository/stack at all. This breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` picks a `GitHubApp` instance keyed off `repository_owner`, computed from the raw JSON body itself: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` HMAC-verifies the raw body against that organization's configured secret, but explicitly no-ops if the organization has no secret configured: [3](#0-2) 

This is a documented, supported configuration: `webhook_secret` is optional/nilable per organization in every example config shipped with the engine (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`). [4](#0-3) 

Once `verify_signature` passes (trivially, for any org with no secret), the raw payload is dispatched to handlers keyed only by event type — never re-checked against the org used for authentication: [5](#0-4) 

`StatusHandler#process`, the code that actually writes state (a CI `Status` record) driven by this payload, looks up commits **by SHA alone, across the entire instance**, with no scoping to the `repository.full_name` in the payload and no cross-check against the organization that was authenticated: [6](#0-5) 

Contrast this with `Handler#stacks`/`#repository_name`, which do read `repository.full_name`, showing the payload *contains* the field needed to bind organization-to-repository — it is simply never enforced in `StatusHandler`: [7](#0-6) 

**The equality that should hold but doesn't:** `organization authenticated via verify_signature (repository.owner.login)` == `repository/stack whose Commit rows StatusHandler mutates (derived from sha, with no full_name/org check)`. Because `StatusHandler` performs a global `Commit.where(sha: ...)` instead of scoping to a repository resolved consistently with the authenticated organization, any commit SHA collision across repositories (which is common for identical commits shared between forks, mirrored repos, or simply any repository whose stack happens to contain that specific SHA) lets a payload "authenticated" for org A silently write a `Status` onto a `Commit` belonging to a completely different stack/org B.

### Impact Explanation
`Status#after_create :enable_ci_on_stack` and `Status.after_commit :schedule_continuous_delivery` are triggered on creation: [8](#0-7) 

and `Commit#create_status_from_github!`/`add_status` transitions feed the merge queue (`ProcessMergeRequestsJob`) and deployability checks used to gate deploys/merges, as shown in tests asserting `MergeMergeRequests`/deployable-status side effects fire on status writes: [9](#0-8) 

Forging a `success` status on a commit belonging to a stack the attacker does not control can therefore feed required-status gates or the merge queue for that unrelated stack, contributing to an unauthorized merge/deploy decision on infrastructure the attacker was never authenticated against — this is a cross-repository-write class impact.

### Likelihood Explanation
Exploitation requires (a) the target Shipit deployment to have at least one configured GitHub organization/App with a blank `webhook_secret` — a state explicitly supported and shown as the default in every shipped example config — and (b) a commit SHA collision between the attacker-controlled/no-secret org's repo and the victim stack's repo. SHA collisions are realistic in forked/mirrored repositories or when the same commit is cherry-picked/rebased into multiple tracked repos, but are not guaranteed for arbitrary targets, which somewhat limits reliability. No Shipit credentials, `ApiClient` token, or privileged GitHub role are required — only the ability to make an HTTP POST to the public `WebhooksController#create` endpoint with an organization login that has no configured secret.

### Recommendation
- In `WebhooksController#verify_signature`, require a non-blank `webhook_secret` to be configured for every organization used in production (or fail closed rather than `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`).
- In `StatusHandler#process` (and any other handler using raw SHA lookups), scope `Commit` lookups by the `Repository`/`Stack` resolved from `repository.full_name` in the payload, and additionally assert that `repository.full_name`'s owner matches the organization that was cryptographically verified in `verify_signature`, closing the organization vs. repository binding gap.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (has a stack tracking a repo with a real commit `abc123...`) and `attacker-org` (configured in `Shipit.secrets.github` with `webhook_secret` left blank, per the documented optional multi-org config format).
2. As the (unprivileged, no Shipit credentials) owner of any repo under `attacker-org`, send `POST /webhooks` with header `X-Github-Event: status`, `X-Hub-Signature: sha1=` (or any value — verification short-circuits to `true`), and body:
```json
{
  "sha": "abc123...",       // SHA that also exists in victim-org's tracked stack
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `verify_webhook_secret` returns `true` unconditionally because no secret is configured.
4. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, which matches the commit under `victim-org`'s stack (no `full_name`/org check), creating a forged `success` `Status` on it and triggering `enable_ci_on_stack`/`schedule_continuous_delivery` for a stack the attacker never authenticated against.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
