### Title
Fail-open exception handling in hookify hooks lets malformed `tool_input`/`edits` crash rule evaluation and silently bypass PreToolUse `deny` rules - ([File: plugins/hookify/core/rule_engine.py], [File: plugins/hookify/hooks/pretooluse.py])

### Summary
`RuleEngine._extract_field` assumes `tool_input` is always a `dict` and that `MultiEdit`'s `edits` list always contains dicts with a `new_string` key. When these assumptions are violated (e.g. `tool_input` is `null`, or an `edits` entry is a non-dict/string), `_extract_field`/`_check_condition` raise unhandled exceptions instead of returning `False`/`None`. `pretooluse.py` wraps the whole evaluation in a blanket `try/except Exception` that, on **any** error, prints a bare `{"systemMessage": ...}` (no `permissionDecision: "deny"`) and always `sys.exit(0)`, which Claude Code treats as "allow." This turns a crash in rule evaluation into a full bypass of `block` rules.

### Finding Description
`evaluate_rules` -> `_rule_matches` -> `_check_condition` -> `_extract_field` (plugins/hookify/core/rule_engine.py:182-254) processes `tool_input` fields directly: [1](#0-0) 

If `tool_input` is not a dict (e.g. the hook JSON payload contains `"tool_input": null`), the containment check `field in tool_input` raises `TypeError: argument of type 'NoneType' is not iterable` rather than returning `None`. Note that `input_data.get('tool_input', {})` in `_rule_matches` only supplies the `{}` default when the key is *absent*, not when it is explicitly `null`: [2](#0-1) 

Similarly, for `MultiEdit`, `_extract_field` blindly calls `.get` on every element of `edits` without validating the elements are dicts: [3](#0-2) 

If any `edits` entry is not a dict (e.g. a plain string), `e.get('new_string', '')` raises `AttributeError`, again propagating instead of being handled gracefully.

Both exceptions escape `evaluate_rules` and reach `pretooluse.py`'s top-level handler: [4](#0-3) 

On exception, the hook emits only `{"systemMessage": f"Hookify error: {str(e)}"}` — critically, it never sets `hookSpecificOutput.permissionDecision = "deny"` — and always calls `sys.exit(0)`. Because Claude Code's PreToolUse hook contract only blocks when `permissionDecision: "deny"` is explicitly returned, the crashed evaluation is functionally equivalent to "no rule matched," so the dangerous command/edit is allowed to execute even though a `block` rule targeting it exists and would otherwise have matched.

### Impact Explanation
This is a full bypass of the hookify `PreToolUse` denial mechanism: any `block` rule (e.g., "block `rm -rf`", "block writes to `.env`") can be defeated by supplying a malformed `tool_input`/`edits` shape that triggers a crash before the pattern match runs, letting the actual dangerous `Bash` command or `MultiEdit` content execute unimpeded. This matches a trust-boundary/approval-bypass impact — an enforcement control (hook-based command blocking) is silently disabled instead of failing closed.

### Likelihood Explanation
Feasible and repeatable: no privileged access is required, only the ability to cause a tool call with an atypical `tool_input`/`edits` shape (e.g., via prompt injection content in a repo/issue/PR that persuades the model to structure a `MultiEdit` call with a non-dict edit entry, or a `tool_input: null` payload). The crash path is deterministic given such input, so the bypass is reliably reproducible.

### Recommendation
- In `_extract_field`, validate `tool_input` is a `dict` (and each `edits` element is a `dict`) before indexing/`.get()`; treat anything unexpected as "field not found" (`None`) rather than raising.
- In `pretooluse.py`'s exception handler, fail closed for rule-evaluation errors: return `hookSpecificOutput.permissionDecision = "deny"` (or at minimum log and re-raise/exit non-zero) instead of silently allowing the operation, at least when rules were loaded and matching was attempted.

### Proof of Concept
```python
# test_rule_engine_failopen.py
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-rm-rf",
    enabled=True,
    event="bash",
    conditions=[Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")],
    action="block",
    message="Dangerous rm command!"
)

engine = RuleEngine()

def test_null_tool_input_should_not_bypass_block():
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": None,  # attacker-controlled malformed payload
    }
    # This currently raises TypeError inside evaluate_rules instead of denying
    result = engine.evaluate_rules([rule], input_data)
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

def test_multiedit_non_dict_edit_should_not_bypass_block():
    edit_rule = Rule(
        name="block-secret-write",
        enabled=True,
        event="file",
        conditions=[Condition(field="new_text", operator="contains", pattern="rm -rf /")],
        action="block",
        message="Dangerous edit content!"
    )
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "MultiEdit",
        "tool_input": {
            "file_path": "script.sh",
            "edits": ["rm -rf /"],  # non-dict entry, attacker-controlled shape
        },
    }
    result = engine.evaluate_rules([edit_rule], input_data)
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Expected (current buggy) behavior: both tests fail because `evaluate_rules` raises an unhandled `TypeError`/`AttributeError` (in `pretooluse.py` this is swallowed and converted to an "allow" response with no `permissionDecision`). Expected (fixed) behavior: `_extract_field` returns `None` for malformed input causing `_check_condition` to return `False` gracefully, and separately, the `Bash`/`MultiEdit` payload with the real dangerous command should still be caught by a well-formed variant of the same test to prove the rule itself still functions.
