## Analog Vulnerability Found

### Title
Uncaught assertion `throw Error("nonserial AA")` in AA trigger processing crashes the entire node - (File: `aa_composer.js`)

### Summary
The Node.js HTTP/2 CVE-2024-27983 crashes the whole server process via an internal assertion (`~Http2Session()`) that fires when unexpected internal state is reached while processing attacker-supplied frames, turning a per-connection edge case into full server unavailability. `aa_composer.js`'s `handleTrigger()` contains an analogous hard invariant-check `throw Error(...)` inside the callback chain that processes an externally triggerable AA response unit. Because this throw happens inside nested asynchronous callbacks (not wrapped in a catchable boundary at the top-level event loop), it becomes an uncaught exception that crashes the whole ocore node process, not just the request/trigger being handled.

### Finding Description
`validateAndSaveUnit()`, invoked from `handleTrigger()`, re-validates the response unit that the AA composer itself builds for a trigger, using `validation.validate()`: [1](#0-0) 

Inside the `ifOk` callback, the code assumes the AA's own freshly generated unit must always land in `sequence === 'good'`, and treats any other outcome as an unreachable condition:
```
ifOk: function (objAAValidationState, validation_unlock){
    if (objAAValidationState.sequence !== 'good')
        throw Error("nonserial AA");
    ...
``` [2](#0-1) 

`sequence` is computed by the normal double-spend detection path in `validation.js` (`validatePaymentInputsAndOutputs` / `checkInputDoubleSpend` / `checkForDoublespends`), the same machinery that determines `good`/`temp-bad`/`final-bad` for ordinary units: [3](#0-2) [4](#0-3) 

The AA response unit spends outputs owned by the AA address (its balance UTXOs). An unprivileged attacker fully controls the *trigger* unit(s) sent to the AA (values, timing, and — via double-spending their own trigger inputs — which of two conflicting forks the network ultimately accepts). Because `handleTrigger()`/`handlePrimaryAATrigger()` runs per unstable MC unit during catch-up/stabilization and secondary triggers can chain (`handleSecondaryTriggers`), it is plausible to construct trigger sequences (e.g., a trigger unit that is itself a double-spend, or a race where two competing forks both attempt to spend the same AA balance output before the sequence is finally settled) that leave the freshly composed AA response with `sequence !== 'good'` when this second validation pass runs. This is the exact same bug class as the HackerOne report: an "impossible" internal invariant, reachable with attacker-controlled input, that the implementation treats as unreachable and asserts on instead of handling gracefully.

Unlike ordinary `handleJoint()` validation failures (which are caught by dedicated `ifUnitError`/`ifJointError` callback branches and handled without crashing, e.g. `network.js:1174-1218`), `validateAndSaveUnit()`'s `ifOk` branch has no error path for `sequence !== 'good'` — it only has the `throw`.

### Impact Explanation
An uncaught `Error` thrown inside a database-driven async callback chain in Node.js is not recoverable by the enclosing `try/catch` of the caller (the throw happens on a different tick/stack), so it propagates to `process.on('uncaughtException')` or, if unhandled, crashes the Node.js process entirely. Because AA trigger processing (`handleAATriggers` / `handlePrimaryAATrigger` / `handleTrigger`) runs as part of routine stabilization on every full node that has the triggered AA address, a single crafted trigger unit that reaches this invariant would crash every full node processing AA triggers on the network simultaneously as they advance MC stability — an availability-wide "network unable to confirm new units" condition, matching the required impact bar.

### Likelihood Explanation
Reaching this exact state requires constructing input (trigger unit(s), possibly combined with a double-spend or with concurrent secondary-trigger execution) that causes the response-composing validation pass to disagree with the initial dry-run assumption of `sequence === 'good'`. This requires understanding of the double-spend/sequence state machine and precise MCI/ordering, so it is not trivial to trigger, but it is fully reachable from unprivileged externally-submitted trigger units without any special privilege, hub role, or protocol-level attack — it only requires posting ordinary payment/trigger units to an AA address.

### Recommendation
- Replace the `throw Error("nonserial AA")` (and the sibling `throw` statements in `validateAndSaveUnit`'s other callbacks: `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`) with a graceful `bounce()`/`revert()` path identical to other AA error handling, so that an unexpected sequence outcome causes the trigger to bounce rather than crashing the process.
- Wrap AA-trigger processing in top-level `process.on('uncaughtException')`/domain-style guards that isolate a single trigger's failure so it cannot take down the whole node.
- Add regression tests that simulate a double-spending trigger pair targeting the same AA address balance to confirm the AA response path degrades to a bounce instead of an uncaught throw.

### Proof of Concept
1. Deploy an AA that accepts payments and forwards balance-dependent outputs to the trigger address.
2. Post two trigger units from the same address that double-spend the same input (or arrange for the AA response's spend of AA-owned outputs to collide with a fork/re-org during MC stabilization) so that, when `handleTrigger()` calls `validateAndSaveUnit()` to re-validate its own freshly built response unit, `validation.validate()`'s double-spend detection (`validation.js:2489-2497`, `checkForDoublespends`) returns `objAAValidationState.sequence !== 'good'`.
3. Observe `aa_composer.js:1823-1824`'s `throw Error("nonserial AA")` fire inside the async callback chain, producing an uncaught exception that crashes the ocore node process while it is stabilizing/handling AA triggers.
