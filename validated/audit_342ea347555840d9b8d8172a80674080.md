## Note on `StatusHandler`

`StatusHandler#process` matches by `sha` alone across *all* stacks (`Commit.where(sha: params.sha)`), it does not even key off `repository_owner`/`full_name` [1](#0-0) , so it is not the cleanest example of the field-binding break. The clearest instance of the "verified field vs. acted-upon field" mismatch is in `PushHandler`/`Handler#repository_name`, which I use below.

### Title
Webhook signature is verified against `repository.owner.login` while the target repository is selected from the independent, unverified `repository.full_name` field, allowing a legitimate low-trust org's webhook secret to forge writes against another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` picks the HMAC secret to validate the request via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the JSON body itself (`params.dig('repository','owner','login')`) [2](#0-1) [3](#0-2) . `Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) keyed by that same string [4](#0-3) . However, once the signature is accepted, event handlers determine which `Repository`/`Stack` to act on using a *different* field of the same payload: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [5](#0-4) , and `PushHandler#process` uses that to sync commits/branch state for matching stacks [6](#0-5) . These two fields (`repository.owner.login` vs `repository.full_name`) are never cross-validated against each other.

### Finding Description
The binding that should hold is: `organization_whose_secret_authenticated_the_HMAC == organization_that_owns_the_repository_being_written`. The code breaks this equality because the two values are read from two independent, attacker-controllable JSON fields inside the same webhook body:
- `repository_owner` (drives which `GitHubApp`/`webhook_secret` is used to verify `X-Hub-Signature`): `app/controllers/shipit/webhooks_controller.rb:59-62`.
- `repository_name` (drives which `Repository`/`Stack` records are looked up and mutated): `app/models/shipit/webhooks/handlers/handler.rb:36-38`.

Anyone who legitimately possesses the webhook secret for organization A (e.g., because they administer A's GitHub App/organization webhook that is configured in this Shipit instance for A's own repositories) can compute a valid HMAC-SHA1 signature over an arbitrary JSON body using A's secret, since `verify_webhook_signature` only checks the raw bytes against the secret - it has no knowledge of, or constraint on, the semantic content of the payload [7](#0-6) . That party can craft a body where `repository.owner.login = "OrgA"` (so the correct - and only - secret they hold is selected) but `repository.full_name = "OrgB/victim-repo"`, where OrgB is a different, more trusted organization also configured in the same shared Shipit deployment.

Before the attacker's request: signature verification and target-repository resolution are logically expected to refer to the same organization.
After the attacker's request: the signature is verified against OrgA's secret while `PushHandler`, `Handler#stacks`, etc. resolve and mutate `OrgB/victim-repo`'s `Stack`/`Commit` records - a cross-organization/cross-repository write performed by someone who never authenticated for OrgB at all.

### Impact Explanation
This is a cross-repository write: an actor with only organization A's webhook credentials can inject fabricated push events (arbitrary `after` SHA / branch) for organization B's tracked stacks, causing `GithubSyncJob` to run against a repository the attacker has no authorization over [8](#0-7) . Depending on continuous-deployment configuration on the victim stack, this can influence merge/deploy scheduling for a repository/org the attacker was never authenticated against, which the report's impact bar explicitly recognizes ("cross-repository writes... an unauthorized deploy").

### Likelihood Explanation
Requires the attacker to already hold a legitimate webhook secret for *some* organization configured in the same multi-tenant Shipit instance (i.e., they are a legitimate but low-trust webhook sender for org A) and knowledge that a second, higher-value org/repo (org B) is also configured on the same instance - both facts an org A administrator can plausibly obtain (org B's repo/stack names are visible in Shipit's UI/API to any authenticated org). No compromise of org B's own secret or GitHub credentials is needed, only crafting a raw HTTP POST with a manually computed HMAC using their own, legitimately-held secret.

### Recommendation
Bind the signature-verification identity to the identity used for repository resolution: derive the organization used both for secret selection and for repository/stack lookup from the *same* payload field (e.g., always use `repository.full_name`'s owner segment for `Shipit.github(organization:)`, or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers), and reject the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (multi-org schema per `lib/shipit.rb:170-200`).
2. As an administrator of `OrgA` (who legitimately knows `OrgA`'s `webhook_secret`), build a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
     "owner": { "login": "OrgA" },
     "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "OrgA")` and succeeds because the signature matches `OrgA`'s secret [2](#0-1) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` [5](#0-4)  and enqueues `GithubSyncJob` for OrgB's stack with the attacker-chosen `after` SHA - despite the request never having been authenticated for OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers

        params do
          requires :ref
          requires :after

        end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
