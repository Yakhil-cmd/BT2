### Title
Webhook signature is verified against attacker-chosen `repository.owner.login` while the action targets an unrelated repository resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate the HMAC signature against using `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , but the actual handler (e.g. `OpenedHandler`) resolves the target `Shipit::Repository` from the independent field `repository.full_name` via `Repository.from_github_repo_name` [3](#0-2) . Nothing enforces that these two attacker-controlled fields refer to the same repository/owner, so a request can be "authenticated" against one (unsecured) organization while mutating another organization's tracked repository and stacks.

### Finding Description
The binding the audit claims should hold is:
`repository_owner` (used in `verify_signature` to select the signing secret) == `owner` component of `Repository.from_github_repo_name(payload['repository']['full_name'])` (used to select which `Repository`/stacks get mutated).

These come from two different reads of the same attacker-supplied JSON body:
- `repository_owner` = `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) 
- Target repository owner = `github_repo_name.downcase.split('/')` applied to `payload.dig('repository','full_name')` inside `Handler#repository_name` / `Repository.from_github_repo_name` [4](#0-3) [5](#0-4) 

Since the raw JSON body is entirely attacker-controlled (no session, no prior auth), an attacker can submit a `pull_request` `opened` webhook where `repository.owner.login = "Y"` (some organization configured in `Shipit.github_app_config` with `webhook_secret` blank/nil) but `repository.full_name = "X/some-tracked-repo"` (an existing `Shipit::Repository` row owned by a different, victim organization `X`).

`verify_signature` calls `Shipit.github(organization: "Y")` and then `verify_webhook_signature`, which explicitly returns `true` with **no signature check at all** when the organization's `webhook_secret` is blank: `return true unless webhook_secret` [6](#0-5) . This is not a hypothetical: the shipped multi-org example config leaves `webhook_secret:` empty for both configured orgs [7](#0-6) .

Once past `verify_signature`, `OpenedHandler#repository` resolves the row using `params.repository.full_name` = `"X/some-tracked-repo"`, ignoring the organization used for authentication entirely [3](#0-2) . If that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all?`, `ReviewStackAdapter#find_or_create!` creates a real `ReviewStack`/`Stack` owned by `X`'s repository [8](#0-7)  — despite the request only ever being "authenticated" for org `Y`.

None of the existing guards catch this: `verify_signature` never compares `repository_owner` against `full_name`'s owner; `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema for `OpenedHandler` only requires `repository.full_name` to be a `String`, not that it match `repository.owner.login` [9](#0-8) ; `force_github_authentication`/`User#authorized?` are irrelevant to unauthenticated webhook ingestion.

This is distinct from (and stronger than) the pure `NullRepository` fallback scenario in the prompt: the `NullRepository` path is a safe no-op (`review_stacks_enabled` is `false` and no stack is created) [10](#0-9) . The actual break is that the *signature-verification identity* and the *record-mutation identity* are two independently attacker-controlled values that are never cross-checked, so an attacker can satisfy verification "for free" against an org with no secret while acting on a completely different, secured org's repository.

### Impact Explanation
An attacker who knows (a) the name of any organization configured in the host's Shipit multi-org GitHub config with a blank/unset `webhook_secret`, and (b) the `owner/name` of any tracked `Shipit::Repository` belonging to a different, victim organization, can forge `pull_request.opened`/`labeled`/`closed`/`reopened`/`unlabeled` webhooks that create, archive, unarchive, or otherwise mutate review stacks for the victim organization's repository — with zero valid GitHub signature for that organization. This is a cross-tenant write triggered by an unauthenticated HTTP POST, matching the "payload for one repository mutating another's stack" Critical criterion. It is fully repeatable against any tracked repository as long as one configured org lacks a webhook secret.

### Likelihood Explanation
Requires a multi-org GitHub App configuration (`github_default_organization` present, i.e. `secrets.github` keyed by organization name) with at least one configured organization having no `webhook_secret` — a configuration state present verbatim in this repo's own example dummy config [11](#0-10) . Given that, attacker cost is a single crafted unauthenticated HTTP POST with no secrets, no session, and no GitHub-side privileges — trivially repeatable.

### Recommendation
In `WebhooksController#verify_signature`, or in `Handler#repository`, cross-validate that the owner segment of `payload.dig('repository','full_name')` equals `payload.dig('repository','owner','login')` (and reject/422 on mismatch) before resolving/mutating any `Shipit::Repository`. Additionally, treat a missing `webhook_secret` for a configured organization as a hard misconfiguration (fail closed) rather than silently returning `true` in `GitHubApp#verify_webhook_signature`.

```ruby
# test/controllers/webhooks_controller_cross_tenant_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerCrossTenantTest < ActionController::TestCase
    tests WebhooksController

    setup do
      Shipit.stubs(:github_default_organization).returns('orgY')
      Shipit.stubs(:github_app_config).with('orgY').returns(webhook_secret: nil, app_id: 1, installation_id: 1)
      # victim repo owned by "shopify" already tracked
      @victim_repo = shipit_repositories(:shipit)
      @victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)
    end

    test "signature check against org Y (no secret) must not authorize mutation of org X's repository" do
      payload = payload_parsed(:pull_request_opened)
      payload["repository"]["owner"]["login"] = "orgY"          # authenticated identity
      payload["repository"]["full_name"] = @victim_repo.github_repo_name # mutated identity ("shopify/shipit-engine")

      request.headers['X-Github-Event'] = 'pull_request'
      # no valid X-Hub-Signature provided at all

      assert_no_difference -> { Shipit::Stack.where(repository_id: @victim_repo.id).count } do
        post :create, body: payload.to_json, as: :json
      end
      # Binding assertion: authenticated owner ("orgY") must equal
      # the owner of the Repository row actually mutated ("shopify").
      # Currently this assertion FAILS because a stack IS created under @victim_repo.
    end
  end
end
```
Expected (buggy) behavior: the `assert_no_difference` fails because a `Stack` is created under `@victim_repo` (owner `shopify`) even though the webhook was only verified for `orgY`, proving `repository_owner` (`orgY`) != owner of the mutated `Repository` (`shopify`).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
