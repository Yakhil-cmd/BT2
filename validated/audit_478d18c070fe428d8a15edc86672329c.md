### Title
System-vote weight is recomputed from the voter's *current* balance at tally time instead of being locked at vote-cast time, allowing transient balance manipulation to sway `op_list`/parameter votes - (File: `main_chain.js`)

### Summary
Similar to the reported governance bug where a voter could change their effective voting weight after casting a vote and before finalization (by relinquishing the vote and burning tokens to shrink the denominator), ocore's on-chain "system vote" mechanism for electing order-providers (`op_list`) and numeric network parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) also decouples the recorded vote from the balance used to weigh it. The vote (`system_vote` message) is persisted once, but the balance used to weight it is recomputed from scratch every time `countVotes()` runs, using whatever balance the voting address holds *at counting time*, not the balance it held when the vote was cast.

### Finding Description
Any unprivileged unit poster can send a `system_vote` message, which is recorded into `system_votes` with only `unit, address, subject, value, timestamp` [1](#0-0) . The actual weight of that vote is not stored or locked when the vote is submitted. Instead, every time `countVotes()` executes (triggered by `system_vote_count`), it recomputes each voting address's balance from the current, live `outputs` table at that moment: [2](#0-1) 

This balance is then joined against `op_votes`/`numerical_votes` to rank OP candidates or compute the median parameter value [3](#0-2) . Because the address's balance is free to change between the moment the vote is cast and the moment(s) it is later recounted (the same vote persists and is reused across multiple future `countVotes` invocations as MC indices stabilize), a voter can post a vote once while their balance is small, later fund the same address heavily right before/during a counting MCI to inflate their tallied weight, and withdraw the funds again afterward - all without needing to resubmit or "relinquish" anything, since the stale vote record is automatically re-weighted with the new balance at every subsequent count. This is the same root-cause pattern as the OtterSec-reported bug: the on-chain "weight" input to a governance-style decision is not frozen at the time the participant expresses their choice, so it can be manipulated in the window between casting and tallying.

### Impact Explanation
The `op_list` vote directly determines the witness/order-provider set used by the network for stability determination (`storage.systemVars.op_list`, `COUNT_WITNESSES`) [4](#0-3) . If an attacker can transiently inflate the counted balance behind their address at exactly the MCI when `countVotes` executes, they can bias which addresses are elected as order providers, or bias `threshold_size`/`base_tps_fee`/`tps_interval` medians which govern fee economics and network throughput. Because these witnesses/parameters underpin stability calculation for the whole DAG, a manipulated election can weaken or split the network's confidence in main-chain stability - a High severity network-availability/consensus concern, not merely a "resource" issue.

### Likelihood Explanation
Exploitation requires the attacker to time a large, temporary balance to coincide with the exact MCI/timestamp at which `countVotes` is invoked for the relevant subject, and for that balance shift to be meaningful relative to other votes in the `since_timestamp` window (which expands backward only when total voted balance is below `SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES`) [5](#0-4) . This makes the attack capital-intensive and timing-sensitive, but it does not require any special privilege - any address holder can submit a `system_vote` unit, and the balance recomputation logic is deterministically triggered on every relevant MC stabilization, so the window is repeatedly and predictably available.

### Recommendation
Lock the voter's balance (or weight) at the time the `system_vote` unit becomes stable, rather than recomputing it from the live `outputs` table on every subsequent `countVotes` call. Store the balance-at-vote-time alongside the vote record in `system_votes`, and use that frozen value (optionally re-validated only once at first stabilization) for all future tallies of that vote, so post-vote balance changes cannot retroactively alter already-cast votes' weight.

### Proof of Concept
1. Attacker controls address `A` with a small/zero byte balance.
2. Attacker posts a `system_vote` unit from `A` for `op_list` (or a numeric subject), which is recorded in `system_votes` [1](#0-0) .
3. Shortly before an MCI that will trigger `system_vote_count`/`countVotes` for that subject stabilizes, attacker transfers a large amount of bytes into `A` (from another address they control) so that `A`'s stable, unspent, good-sequence balance is large at count time.
4. `countVotes()` runs, recomputes `A`'s balance from current `outputs` [6](#0-5) , and applies that large weight to `A`'s previously-cast (and otherwise unchanged) vote when ranking `op_list` candidates or computing the numeric median [3](#0-2) .
5. Immediately after the count, attacker moves the funds out of `A` again; the vote's outsized influence on the just-computed `system_vars` entry is already locked in (`system_vars` is only re-evaluated at future counting events), even though `A` no longer holds that balance.
