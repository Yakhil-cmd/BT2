### Title
`Api::CCMenuController#stack` bypasses `ApiClient` stack scoping, letting a stack-scoped token read any stack's build/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be restricted to a single stack via `stack_id`, and every other API endpoint enforces this by resolving the target stack through `Api::BaseController#stacks`/`#stack`, which filters `Stack.where(id: current_api_client.stack_id)` before looking up the requested record. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, completely skipping that scoping filter, so any valid token — even one deliberately restricted to a single stack — can read CCMenu/build-status data for every stack in the installation.

### Finding Description
`Api::BaseController` defines the scoping binding between an `ApiClient` and the stacks it may touch: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` performs the lookup through that restricted relation (`stacks.from_param!`). This is the mechanism the whole API relies on to bind "the stack a token authorizes" to "the stack a request touches."

`Api::CCMenuController` re-implements `#stack` and does not go through `stacks`: [2](#0-1) 

`stack` calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model, and `authenticate_api_client` is also overridden to accept a client via `params[:token]` without any additional stack check. The only authorization performed is `require_permission :read, :stack`, which merely checks that the permission string `"read:stack"` is present on the token — `ApiClient#check_permissions!` never inspects `stack_id` or compares it to the requested `params[:stack_id]`: [3](#0-2) 

So the binding "stack a token authorizes" (`current_api_client.stack_id`) is never checked against "the stack a request touches" (`params[:stack_id]`) in this controller, even though every sibling controller (`Api::StacksController`, `Api::TasksController`, `Api::HooksController`, etc.) enforces it via the shared `stack`/`stacks` helpers.

Concretely, `CCMenuUrlController#fetch` — the normal way a stack-scoped CI/CD dashboard integration is expected to obtain a CCMenu token — creates the `ApiClient` with only `permissions: %w[read:stack]` and no `stack_id`, then embeds the token in a URL scoped by path (`/stacks/<owner>/<repo>/<env>/ccmenu`): [4](#0-3) 

Because the resulting token is not stack-scoped at the model level, and because even a manually-scoped `ApiClient` (one an admin explicitly restricts to a single stack via `stack_id`) is not enforced by `CCMenuController#stack`, holding any `read:stack`-permission token is sufficient to fetch build status (`name`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.) for any stack in the installation, not just the one it was minted/authorized for.

### Impact Explanation
This matches the "High — unauthenticated/escalated read of stack state" impact category: possession of a token intended to be limited to a single stack (or a per-stack CCMenu token) allows enumeration/reading of build and deploy status of every stack managed by the Shipit installation. This is a genuine authorization-scope escape rather than a documented/expected behavior, because the sibling `Api::StacksController#show` and other API endpoints explicitly respect `ApiClient#stack_id` scoping via `Api::BaseController#stacks`.

### Likelihood Explanation
Likely to be exploitable whenever any `ApiClient` token with the `read:stack` permission exists — a very common permission, since it is the default for CCMenu tokens created by `CCMenuUrlController` and any client created for `read:stack` access. No additional privileges beyond holding one such (possibly narrowly-scoped) token are needed; the attacker just changes `params[:stack_id]` to a different stack's identifier when calling `GET /api/stacks/:stack_id/ccmenu`.

### Recommendation
Make `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that `current_api_client.stack_id` scoping is enforced consistently with every other API controller.

### Proof of Concept
1. As an admin, create (or have `CCMenuUrlController#fetch` create) an `ApiClient` scoped to Stack A (`stack_id = A.id`, `permissions: ["read:stack"]`), and obtain its `authentication_token`.
2. Using that token as HTTP Basic auth, issue `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu` for an unrelated Stack B that the token was never authorized for.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing the `stacks` scoping used everywhere else), the request succeeds with `200 OK` and returns Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though `current_api_client.stack_id` is A's id, not B's.
