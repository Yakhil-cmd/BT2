### Title
Unsanitized linked-branch name passed as bare argv to `git checkout` / `git checkout -b` - (File: pkg/cmd/issue/develop/develop.go)

### Finding Description
`checkoutBranch` in `develop.go` takes `branchName`, which originates from `api.ListLinkedBranches` / `api.CreateLinkedBranch` GraphQL responses (`api/queries_branch_issue_reference.go:15-90`), and passes it unmodified as a bare positional argument to `gc.CheckoutBranch` and `gc.CheckoutNewBranch`: [1](#0-0) 

`git.Client.CheckoutBranch` builds `args := []string{"checkout", branch}` and `CheckoutNewBranch` builds `args := []string{"checkout", "-b", branch, "--track", track}` with no `--` separator and no leading-dash rejection: [2](#0-1) 

However, the other call sites in `checkoutBranch` that use the same `branchName` value embed it inside a larger string rather than passing it as a bare arg — `gc.Fetch` uses `fmt.Sprintf("+refs/heads/%[1]s:...", checkoutBranch, ...)` and `gc.HasLocalBranch` uses `"refs/heads/"+branch` — so a leading `-` in those calls does not produce a standalone flag-like argv element: [3](#0-2) [4](#0-3) 

Critically, in a normal `gh issue develop` flow against a real GitHub/GHES host, `branchName` corresponds to an actual git ref (`node.Ref.Name`) resolved via `FindRepoBranchID`'s `ref(qualifiedName: $ref)` GraphQL field or created via `createLinkedBranch`, which operates against a real git object (`Oid`) in the target repository. Git's own `check-ref-format` rules reject ref/branch names beginning with `-`, so a legitimate, git-backed branch named e.g. `--upload-pack=/tmp/evil` cannot exist as an actual git ref in a repository under attacker's (unprivileged, fork-level) control — the git server itself will refuse to create such a branch. This means the primary described exploit path — "an unprivileged attacker who links a branch named like `--upload-pack=/tmp/evil` via a fork with push access" — is not achievable through the normal, git-backed linked-branch creation flow, because the attacker cannot actually create such a ref in git to link.

The only way `branchName` could contain such a hostile string is if the attacker fully controls the GraphQL *response* (i.e., a malicious/compromised GitHub Enterprise host the victim explicitly points `gh` at), bypassing git's ref-name validation entirely since the string is API-supplied, not derived by parsing a real ref. Even in that scenario, the exploitable flags for real argument-injection-via-transport (`--upload-pack=...`, `-oProxyCommand=...`) apply to network-transport-invoking git subcommands (`clone`, `fetch`, `ls-remote`) — not to `git checkout` or `git checkout -b`, which take no such options and do not invoke a remote transport program. `git checkout --upload-pack=x` and `git checkout -b --upload-pack=x --track origin/x` would simply fail with "unknown option" from git's own argument parser, not execute a program. So even under the more permissive "malicious host" attacker capability, the specific sink (`checkout`/`checkout -b`) does not admit code execution via these flags — the vulnerability class (`--upload-pack=` / `-oProxyCommand=` argument injection) requires a transport-invoking subcommand, which is absent here.

### Impact Explanation
No concrete code-execution or credential-exfiltration path exists through `checkoutBranch`/`gc.CheckoutBranch`/`gc.CheckoutNewBranch`, because: (1) an unprivileged forker cannot create a hostile leading-dash branch name as a real git ref for `ListLinkedBranches`/`CreateLinkedBranch` to return, and (2) even a fully spoofed API response reaching this sink lands on `git checkout`/`git checkout -b`, which have no options equivalent to `--upload-pack=`/`-oProxyCommand=` that would trigger process execution.

### Likelihood Explanation
Low/not exploitable as described. The described attacker (unprivileged fork owner linking a branch) cannot get an invalid-per-git-ref-format string into `branchName` through the normal linked-branch API flow, since GitHub's backend validates refs against real git objects at creation/lookup time.

### Recommendation
No code change required to address this specific reported scenario. Defense-in-depth would still be reasonable: reject/validate branch names beginning with `-` before use, or prefix git invocations for `checkout`/`checkout -b` with `--` where the branch name is a bare argv element, consistent with the pattern already used in `ShowRefs`, `WorktreeRemove`, `IsIgnored`, and `RemoteURL` in `git/client.go`.

### Proof of Concept
Not reproducible as scoped: a unit test with a fake `api.ListLinkedBranches`/`CreateLinkedBranch` returning `"-oProxyCommand=..."` would show `git.Client.Command` invoked as `checkout -oProxyCommand=...` or `checkout -b -oProxyCommand=... --track ...`, but since `git checkout` has no such option, the command would exit with a git usage error rather than executing anything — no code execution assertion is achievable.
