### Title
Denial-of-Service via Front-Running `derived_object::claim` in `sui::coin_registry` - (`crates/sui-framework/packages/sui-framework/sources/registries/coin_registry.move`)

### Summary
A vulnerability exists in the `sui::coin_registry` module where a malicious actor can front-run the creation of a `Currency<T>` object by claiming its deterministic address first. Because `coin_registry::new_currency` uses `derived_object::claim` to generate the `Currency` object's UID, and `derived_object::claim` aborts if the address has already been claimed on the parent registry, an attacker can squat on the specific `CurrencyKey<T>` for any coin type `T`. This prevents the legitimate protocol or user from ever registering that currency in the system registry, leading to a permanent Denial-of-Service for that specific coin type's metadata and supply management features.

### Finding Description
The Sui `derived_object` module allows for the creation of objects with deterministic addresses derived from a parent object's `UID` and a key [1](#0-0) . To ensure uniqueness and prevent duplicate object creation at the same address, `derived_object::claim` records a `ClaimedStatus::Reserved` marker as a dynamic field on the parent [2](#0-1) .

In the `sui::coin_registry` module, the `new_currency` function is used to initialize a new coin's metadata and supply state [3](#0-2) . This function calls `derived_object::claim(&mut registry.id, CurrencyKey<T>())` to obtain the `UID` for the new `Currency<T>` object [4](#0-3) . 

However, `new_currency` is a public function that can be called by anyone [5](#0-4) . An attacker can pre-emptively call `new_currency<T>` for a type `T` that has not yet been registered, or simply use a malicious module to call `derived_object::claim` directly on the `CoinRegistry` shared object using the same `CurrencyKey<T>`. Once the `Claimed` marker is added to the `CoinRegistry` for a specific `T`, any subsequent attempt to call `new_currency<T>` (or `finalize_registration<T>` for OTW-based coins) will abort with `EObjectAlreadyExists` (code 0) [6](#0-5) .

This is analogous to the Gearbox vulnerability where an attacker opens a credit account on behalf of the `CreditFacade` to trigger an ownership assertion failure. Here, the attacker "claims" the identity of the currency on behalf of the registry before the legitimate initialization occurs.

### Impact Explanation
The impact is **High**. An attacker can permanently block the registration of any new coin type in the `CoinRegistry`. This prevents the creation of the `Currency<T>` object, which is required for:
1. Managing coin metadata (name, symbol, etc.) via `MetadataCap`.
2. Utilizing advanced supply features like `Fixed` or `BurnOnly` supply states [7](#0-6) .
3. Integration with ecosystem tools that rely on the centralized `CoinRegistry` for authoritative coin data.
Since `derived_object` claims are currently irreversible [8](#0-7) , the DoS is permanent for the affected coin type.

### Likelihood Explanation
The likelihood is **High**. The `CoinRegistry` is a well-known shared object at a fixed address (`0xc`). The `CurrencyKey<phantom T>` is also predictable as it is a public struct with no fields [9](#0-8) . An attacker can monitor the network for new package publishes and front-run the `init` or `new_currency` calls.

### Recommendation
Restrict the `new_currency` function or the ability to claim `CurrencyKey<T>` to only the module that defines the type `T`. This can be achieved by:
1. Using a witness pattern where `new_currency` requires a witness for `T`.
2. Checking that the caller (sender or current module) has the authority to register type `T` (e.g., via `sui::package::Publisher`).
3. Ensuring that `derived_object::claim` is only called within a flow that validates the one-time-witness or publisher of the coin.

### Proof of Concept
1. A developer publishes a new coin module with type `my_coin::MY_COIN`.
2. Before the developer can call `coin_registry::new_currency<MY_COIN>`, an attacker submits a transaction calling a malicious function:
   ```move
   public entry fun attack<T>(registry: &mut CoinRegistry, ctx: &mut TxContext) {
       // Directly claim the key to block the developer
       let dummy_uid = sui::derived_object::claim(registry, my_coin::CurrencyKey<T>());
       sui::test_utils::destroy(dummy_uid);
   }
   ```
3. The developer's transaction to `new_currency<MY_COIN>` now fails because `derived_object::claim` sees the `Claimed(id)` dynamic field already exists on the `CoinRegistry` [6](#0-5) .
