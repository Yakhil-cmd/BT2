### Title
Excess deposit attached to `AddressRegistrar::register` is not refunded to the caller - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
`AddressRegistrar::register` accepts any attached deposit greater than or equal to the computed storage cost (`given_deposit >= required_deposit`), but on the success path it only refunds the deposit when a collision occurs. When registration succeeds (the common, intended path), any excess NEAR above `required_deposit` is silently retained by the contract instead of being refunded to the caller.

### Finding Description
The `register` method computes `required_deposit` from the size of the data to be stored and compares it against `given_deposit = env::attached_deposit()` using a "greater than or equal" check rather than strict equality, because callers cannot know the exact required deposit in advance: [1](#0-0) 

If the entry is vacant, the method inserts the mapping and returns success but never refunds `given_deposit - required_deposit`: [2](#0-1) 

Only in the `Entry::Occupied` (collision) branch does the code issue a refund, and even then it refunds the *entire* deposit rather than just the excess, via a `Transfer` promise back to the predecessor: [3](#0-2) 

This mirrors the reported pattern exactly: a `>=` payment check without refunding the difference between what was paid and what was actually required, leaving the surplus stuck in a contract with no withdrawal mechanism for the account owner.

### Impact Explanation
Any unprivileged account calling `register()` with an over-estimated deposit permanently loses the excess NEAR — the contract has no method to reclaim or redistribute the surplus, so the tokens become effectively locked/unusable. This is an unauthorized, irreversible reduction of a user's balance caused purely by contract logic rather than by protocol design (unlike NEAR's core gas/deposit refund pipeline, which explicitly reserves and returns unused amounts via `Receipt::new_balance_refund`/`refund_unspent_gas_and_deposits`, see `runtime/runtime/src/lib.rs`).

### Likelihood Explanation
Likelihood is high in practice: `required_deposit` depends on `env::storage_byte_cost()` and the exact byte length of `account_id`, values that ordinary callers must estimate off-chain. Any caller who rounds up their attached deposit (a common defensive practice to avoid the `panic_str` failure path) will trigger fund loss on every successful call.

### Recommendation
In the `Entry::Vacant` success branch, refund only the excess (`given_deposit - required_deposit`) to `env::predecessor_account_id()` via a `Transfer` promise, matching the pattern already used in the collision branch, but computing the correct partial-refund amount instead of retaining or fully refunding the deposit.

### Proof of Concept
1. Call `register(account_id)` with `attached_deposit = required_deposit + X` yoctoNEAR, where `X > 0` and `account_id` has no address collision.
2. Observe the call succeeds (`Some(address)` returned, mapping inserted).
3. Query the caller's account balance: it has decreased by `required_deposit + X`, not just `required_deposit`.
4. No subsequent call or admin function exists to recover the excess `X`; it remains permanently locked in the `AddressRegistrar` contract's balance.
