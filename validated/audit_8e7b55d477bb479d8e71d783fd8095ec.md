### Title
Cross-organization webhook forgery via `repository.owner.login`-selected signature verification — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify a webhook against using `repository_owner`, a value read straight out of the *unauthenticated* JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The event is then dispatched to handlers using the *same* body, but the handlers determine which `Repository`/`Stack` to mutate from a **different** field: `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment, this breaks the binding "organization whose secret authenticated the request == repository the handler acts on."

### Finding Description [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization `GitHubApp` instance from `secrets.github`, keyed by the attacker-supplied `repository_owner` string: [2](#0-1) 

Signature verification for that org's app is: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If **any** configured organization has no `webhook_secret` set (documented/supported as an optional, commonly-nil setting — see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, both showing `webhook_secret: # nil`), then choosing that organization's name for `repository.owner.login` makes `verify_webhook_signature` return `true` unconditionally — no valid `X-Hub-Signature` is required at all.

Once the request is "verified," the raw payload is dispatched unchanged to handlers: [4](#0-3) 

Handlers, however, resolve the target repository from a **separate** field of the same body: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

So an attacker can set `repository.owner.login` to the secret-less org (to defeat/bypass signature verification) while setting `repository.full_name` to `any-other-org/any-repo` (the real target), because nothing ties the two fields together or re-validates that `full_name`'s owner matches `repository_owner`. This is the same class of bug as the report: a field that drives a trust/authorization decision (`webhook_secret` lookup key) is decoupled from the field that the sensitive action actually operates on (`repository.full_name`), and the "authenticated identity" (org used to fetch the secret) is never checked for equality against "the repository being written."

Concretely this enables forged `push` webhooks (`Handlers::PushHandler`, using `params.after`) to trigger `stack.sync_github(expected_head_sha:)` for stacks belonging to a different, secret-protected organization/repository, and forged `status` events to inject arbitrary commit statuses (`Handlers::StatusHandler#process` → `commit.create_status_from_github!`), which can influence CI-gated deploy/merge decisions elsewhere in the engine.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope. In a multi-org configuration where at least one org lacks a `webhook_secret` (a supported, documented configuration), an unauthenticated attacker can forge `push`/`status`/`check_suite`/`pull_request` events targeting **any repository configured in Shipit**, not just the secret-less org's own repositories — enabling unauthorized sync/build/status manipulation and, transitively, unauthorized deploy-flow influence (e.g., faking passing CI statuses required for continuous deployment or merge). This aligns with the High-severity bucket ("unauthenticated read/write of stack state via authorization bypass").

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, and (2) at least one configured organization with no `webhook_secret`. Both conditions are explicitly supported/documented (`webhook_secret: # nil` appears as a normal example in `docs/setup.md`, `config/secrets.development.shopify.yml`, and the multi-org test fixture `secrets_double_github_app.yml`), so this is a realistic, not purely theoretical, configuration. No credentials, tokens, or GitHub App private keys are needed — only knowledge that such an org exists in the deployment.

### Recommendation
After selecting the `GitHubApp` via `repository_owner`, re-validate that the same value equals the owner encoded in `repository.full_name` (and any org referenced elsewhere in the payload) before dispatching to handlers, and reject signature verification for organizations without a configured `webhook_secret` (i.e., stop treating "no secret configured" as an automatic pass) unless that org intentionally has zero repositories/stacks registered. At minimum, ensure `repository_owner` used to pick a signing secret is cryptographically tied to `repository.full_name`'s owner before any handler acts on it.

### Proof of Concept
Preconditions: Shipit configured with orgs `secretless-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`, has repo `victim-org/prod-app` registered as a Stack).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "secretless-org" },
    "full_name": "victim-org/prod-app"
  }
}
```

`verify_signature` resolves `repository_owner` = `secretless-org`, calls `Shipit.github(organization: 'secretless-org').verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank for that org — regardless of the (forged/absent) `X-Hub-Signature`. The controller then dispatches the full payload to `PushHandler`, which resolves the target stack via `payload.dig('repository', 'full_name')` = `victim-org/prod-app`, and calls `stack.sync_github(expected_head_sha: 'deadbeef...')` on `victim-org`'s stack — a forged sync/build trigger with no valid signature for `victim-org` ever presented.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
