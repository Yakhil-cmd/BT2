## Analog Found

### Title
Webhook signature verification selects the GitHub App/organization from an attacker-controlled `repository.owner.login` field that is decoupled from the `repository.full_name` used to resolve the stack that is actually written to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This maps to the "propose vs. change" trust-binding bug class from the M-13 report: a value that is checked/authorized (`proposedAdapter`) is later reused/acted upon without re-validating that the authorization still applies to the same target. In Shipit, the equivalent binding is: **organization used to select the webhook secret for HMAC verification == repository whose stacks are mutated by the handler**. The webhook controller breaks this equality because both values are read from the *same attacker-suppliable payload*, but from two different, independently-controllable JSON keys.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration (and therefore the HMAC secret used to validate the payload) using `repository_owner`, which is read straight from the untrusted request body: [1](#0-0) [2](#0-1) 

Downstream, every default handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the repository/stacks to mutate using a *different* field of the same payload, `repository.full_name`, via the shared `Handler#stacks`/`repository_name` helper: [3](#0-2) [4](#0-3) 

Shipit explicitly supports configuring **multiple independent GitHub Apps/organizations**, each with its own `webhook_secret`, keyed by organization name in `secrets.yml`: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick which repository's stacks get processed) are two independent keys inside the same JSON body, an attacker who legitimately controls one configured organization (and therefore knows that organization's `webhook_secret`) can craft an arbitrary payload where:
- `repository.owner.login` = their own organization (so `Shipit.github(organization: ...)` picks their own known secret and `verify_webhook_signature` succeeds), while
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler resolves and mutates the victim's stacks).

`verify_webhook_signature` only checks that the raw body's HMAC matches the secret for the organization *named in the very same forged body*, not that the organization matches the repository the handlers will actually act on: [7](#0-6) 

This is analogous to the vault bug: the value that was "authorized" (adapter/organization) is checked, but the operation is subsequently re-applied to a value (`proposedAdapter`/`repository.full_name`) that isn't re-verified to still correspond to what was authorized.

### Impact Explanation
An attacker who is a legitimate customer/tenant on a multi-org Shipit deployment (i.e., they know their own org's configured `webhook_secret`) can forge signed-looking webhook payloads that are processed as if they originated from a different organization/repository. Depending on which handler is targeted this allows, for example:
- `PushHandler`: trigger `stack.sync_github(expected_head_sha: ...)` against another tenant's stack with an attacker-chosen `after` SHA — [8](#0-7) .
- `PullRequest::OpenedHandler`/`ReopenedHandler`/`ClosedHandler`: create, unarchive, or archive review stacks belonging to another tenant's repository — [9](#0-8) [10](#0-9) .

This crosses a tenant/repository boundary using a signature that was never meant to authorize actions on that repository, which fits "cross-repository writes" / "unauthorized deploy/rollback" impact category.

### Likelihood Explanation
This requires the Shipit operator to have configured **more than one GitHub organization/App** (a documented, supported feature) and requires the attacker to be a legitimate holder of a `webhook_secret` for at least one of those configured organizations (i.e., an org admin able to see/create the webhook secret for their own org's installation). Given that condition, forging the payload is trivial (just compute an HMAC over an arbitrary JSON body with a secret you already know). This is a real but narrower-likelihood scenario — it does not work in the common single-organization deployment, only in explicitly-supported multi-org setups.

### Recommendation
After selecting the GitHub App/organization from `repository.owner.login` for signature verification, re-validate that the `repository.full_name` (or `organization.login` for org-level events) used later by handlers actually belongs to the same organization that was authenticated. Concretely, in `WebhooksController#verify_signature` (or in `Handler#stacks`/`repository_name`), assert that `repository.full_name.split('/').first == repository_owner` before dispatching to handlers, and reject (422) on mismatch.

### Proof of Concept
Conceptual PoC (cannot be executed without running the app, but based on code paths above):
1. Deploy Shipit with `config/secrets.yml` configured for two orgs, `attacker-org` (secret known to attacker) and `victim-org` (unrelated legitimate tenant), per `docs/setup.md` "Using Multiple Github Applications".
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and triggers `sync_github` on the victim's stack, despite the request never being authenticated for `victim-org`.

**Note on limitation:** I was unable to fully trace `Shipit.github(organization:)`'s multi-app lookup implementation (beyond `lib/shipit/github_app.rb`) within the index, so the exact organization-lookup mechanics (e.g., `Shipit::GithubOrganizationUnknown`) are inferred primarily from `webhooks_controller.rb`'s usage and the multi-org secrets documentation; a full Devin session with repo access would be needed to confirm the app-resolution code (`Shipit.github`) precisely and validate the PoC end-to-end.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
