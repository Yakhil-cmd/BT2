### Title
Cross-repository `Status` write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no filter on the repository/stack that emitted the webhook, while `Handler#stacks` (repository-scoped via `Repository.from_github_repo_name(repository_name)`) is never consulted. `verify_signature` in `WebhooksController` only proves the payload was signed for *some* known organization/repository, not that the `sha` in the payload belongs to that repository's commits, so a legitimately-signed status event for repo X can write a `Status` onto a `Commit` row that actually belongs to repo Y if the two shas coincide.

### Finding Description
The binding that should hold is: `StatusHandler#process`'s write scope == `Handler#stacks.flat_map(&:commits)` (i.e., commits belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`). Instead the code is: [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, unscoped query across the entire `commits` table, not filtered by `stack_id`/repository at all. `Handler#stacks` exists and is repository-scoped: [2](#0-1) 

but `StatusHandler` never calls it. `Handler.call` simply does `new(payload).process`: [3](#0-2) 

The controller's signature check is per-organization, and only validates that the payload was genuinely sent by GitHub for that org/app installation — it says nothing about which `sha`s are legitimate for that repo: [4](#0-3) 

Exploit flow: attacker owns/administers repo `attacker/repo`, which is legitimately registered in Shipit (as any repo owner can add their own repo). Attacker pushes a commit whose `sha` collides with a commit already tracked in a victim repo's stack — most practically by pushing the exact same commit object (same tree, parent, author/committer timestamps) that the victim repo also has (e.g., a shared vendored/cherry-picked commit, or common initial/empty commits across many repos). GitHub emits a real, correctly-signed `status` event for `attacker/repo` with that `sha`. `StatusHandler#process` runs `Commit.where(sha: same_sha)`, which returns **all** `Shipit::Commit` rows across all stacks/repos sharing that sha, and calls `commit.create_status_from_github!(params)` on each — including the victim's commit in an unrelated repository/stack, writing a fabricated CI status (success/failure/pending, arbitrary `description`/`target_url`) that can influence `deployable?`, `blocked?`, and `schedule_continuous_delivery`, potentially triggering unintended deploys via continuous delivery.

Existing guards do not prevent this: `verify_signature` validates webhook authenticity per organization, not per-sha ownership; `ExplicitParameters` only validates the shape of the payload, not that `sha` belongs to the sender's repo; and the `stacks` scoping mechanism that exists in `Handler` for exactly this purpose is unused by `StatusHandler`.

### Impact Explanation
A payload legitimately signed for one repository (`attacker/repo`) mutates state (`Status`) belonging to a `Commit` in a different repository's `Stack`. This matches the "payload for one repository mutating another's stack/commit" Critical category: the attacker can inject arbitrary CI status (pass/fail, description, target URL) onto commits they do not control, which feeds directly into deploy-gating logic (`deployable?`, `blocked?`, continuous delivery scheduling), and is repeatable against any victim repository whose commit history happens to share a sha with a commit the attacker can produce or replicate (shared vendored commits, cherry-picks, common empty/initial commits are realistic collision vectors — no cryptographic sha1 break is required).

### Likelihood Explanation
Preconditions: attacker needs a Shipit-registered repository they control (a low bar — repository registration in Shipit is generally self-service for repo owners/admins) and a commit whose sha is shared with a commit that exists in a targeted victim stack. Exact-object sha collisions across independent repos are realistic for shared/vendored commits, common cherry-picks, or trivial commits (e.g., identical empty commits with identical author/committer/timestamp/tree), making this feasible without brute-forcing SHA-1. The attack is fully repeatable per push and does not require any secret, session, or elevated Shipit role — only that the attacker's own repo webhook fires normally.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the requesting repository's stacks, e.g. filter `Commit.where(sha: params.sha)` by `stacks` (as `Handler#stacks` already provides), such as `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the repository-scoping pattern used elsewhere (e.g. `PushHandler`, `CheckSuiteHandler`).

### Proof of Concept
Minitest plan (no live GitHub needed):
1. Create two `Repository`/`Stack` fixtures for `attacker/repo` and `victim/repo`.
2. Create a `Commit` in `victim/repo`'s stack with `sha: "deadbeef..."`.
3. Create a `Commit` in `attacker/repo`'s stack with the same `sha: "deadbeef..."`.
4. Build a `status` webhook payload with `repository.full_name = "attacker/repo"` and `sha: "deadbeef..."`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
6. Assert: `victim_commit.statuses.reload` gained a new `Status` — proving `victim/repo`'s commit (outside `Repository.from_github_repo_name('attacker/repo').stacks`) was mutated by a payload scoped to `attacker/repo`, violating the equality `StatusHandler` write scope == `stacks`-derived commit scope.

      github_app = Shipit.github(organization: repository_owner)
