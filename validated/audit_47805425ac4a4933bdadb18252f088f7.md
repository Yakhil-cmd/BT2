### Title
`ReviewStackProvisioningQueue#provision` provisions stacks without re-checking `repository.review_stacks_enabled`, letting a precedence bug in `OpenedHandler#provision?` enqueue and provision resources for a repo with review stacks disabled - ([File: app/models/shipit/review_stack_provisioning_queue.rb])

### Summary
`ReviewStackProvisioningQueue#provision(stack)` only checks `stack.provisioner.provision?` before calling `stack.provision`, never re-reading `stack.repository.review_stacks_enabled` at provisioning time. Because `OpenedHandler#provision?` (and `ReopenedHandler#unarchive?`) contain an operator-precedence bug where `&&` binds tighter than `||`, a stack can be enqueued for provisioning even when `review_stacks_enabled` is `false`, and the queue will unconditionally provision it.

### Finding Description
Binding claimed: `repository.review_stacks_enabled == true` at the time `stack.provision` executes. In this codebase that binding is never enforced by the queue.

`ReviewStackProvisioningQueue#provision` reads: [1](#0-0) 
It only gates on `stack.provisioner.provision?` (default implementation always returns `true`): [2](#0-1) 
`queued_stacks` scopes purely on `provision_status`/`awaiting_provision`, with no join or filter on the repository's `review_stacks_enabled`: [3](#0-2) 

The enqueue path is `OpenedHandler#process` → `ReviewStackAdapter#find_or_create!` → `ReviewStackProvisioningQueue.add`: [4](#0-3) 
Gated by `respond_to_pull_request_opened?` → `provision?`: [5](#0-4) 

That `provision?` method has a Ruby operator-precedence defect: `&&` binds tighter than `||`, so the expression actually evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. If an operator sets `provisioning_behavior: allow_with_label` (independently of `review_stacks_enabled`), and later sets `review_stacks_enabled: false` intending to fully disable review stacks, any attacker who opens a PR carrying the configured provisioning label still satisfies `allow_with_label? && has_label?`, making `provision?` return `true` regardless of `review_stacks_enabled`. The same precedence bug exists in `ReopenedHandler#unarchive?`. [6](#0-5) 

Once enqueued (`awaiting_provision: true`, `provision_status: deprovisioned`), `ReviewStackProvisioningQueue.work` (run via a scheduled job) picks it up and calls `stack.provision` with no re-check of `review_stacks_enabled`, triggering `after_transition deprovisioned: :provisioning { stack.provisioner.up }`, i.e. real provisioning side effects defined by the custom `ProvisioningHandler`: [7](#0-6) 

By contrast, `LabeledHandler`/`UnlabeledHandler` correctly parenthesize the check (`repository.review_stacks_enabled && (archive? || unarchive?)`), so they are not affected: [8](#0-7) 

No other guard (webhook signature verification, `ExplicitParameters`, permission checks) inspects `review_stacks_enabled` consistency between enqueue-time and provision-time; those guards authenticate the webhook sender/payload shape, not the business-logic precedence bug.

### Impact Explanation
An attacker who can open a pull request and apply a label to their own PR (per the stated attacker capabilities) can cause the engine to provision real infrastructure/resources for a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`). The action executed is whatever the host application's custom `ProvisioningHandler#up` does (cloud resources, DNS, secrets, etc. - implementation-specific, since `Base#up` is a no-op). This is a write/execution divorced from the repository's own authorization flag, matching "a command running / a record written for a repository that did not authenticate it." It is repeatable for every PR the attacker opens against the same misconfigured repository, but requires a specific operator configuration (`provisioning_behavior: allow_with_label` while `review_stacks_enabled: false`) - it does not cross tenant/repository boundaries by itself.

### Likelihood Explanation
Requires: (1) the target repository has `provisioning_behavior: allow_with_label` (or `prevent_with_label`) configured, and (2) `review_stacks_enabled` is `false`. This is a plausible but non-default combination (e.g., an operator temporarily disabling review stacks without also resetting `provisioning_behavior`). Given that state, the attacker cost is trivial: open a PR and add the configured label to it (or, for `prevent_with_label`, simply not add it). No secrets, sessions, or privileged roles are needed, matching the stated attacker model.

### Recommendation
Fix operator precedence in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` by parenthesizing: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`. Additionally, as defense in depth, have `ReviewStackProvisioningQueue#provision` re-check `stack.repository.review_stacks_enabled` before calling `stack.provision`, and drop/skip (or remove from queue) stacks belonging to repositories with review stacks disabled.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_provisioning_queue_test.rb` style):
1. Create a repository fixture with `review_stacks_enabled: false`, `provisioning_behavior: :allow_with_label`, `provisioning_label_name: "deploy-me"`.
2. Assert binding LHS: `repository.review_stacks_enabled == false`.
3. Simulate `pull_request_opened` webhook payload with a label `"deploy-me"` attached, run `OpenedHandler.new(payload).process`.
4. Assert a `ReviewStack` was created and `awaiting_provision? == true`, `provision_status == "deprovisioned"` (demonstrating the precedence bug enqueues despite `review_stacks_enabled == false`).
5. Stub `stack.provisioner.provision?` to return `true`.
6. Call `Shipit::ReviewStackProvisioningQueue.work`.
7. Assert binding RHS: `stack.reload.provision_status == "provisioning"` (i.e. `stack.provision` was invoked) while `stack.repository.review_stacks_enabled == false` still holds - proving the LHS/RHS equality (`review_stacks_enabled == true` required for provisioning) is violated.
