### Title
Webhook signature is verified against the org selected by `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field - cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* GitHub App/`webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body. Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the *entire* payload to handlers, which resolve the target `Repository`/`Stack` using a *different* field: `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing binds these two fields together, so the org whose secret authenticated the request is not guaranteed to be the org whose repository is actually written to.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
```
where `repository_owner` is derived from the payload itself: [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config/secret (`app_id`, `webhook_secret`, etc.) as documented for multi-org deployments in `docs/setup.md` and exercised in `test/dummy/config/secrets_double_github_app.yml`. In this mode each configured GitHub organization has its own independent `webhook_secret`, and `Shipit::GitHubApp#verify_webhook_signature` only proves that *some* known secret (the one belonging to whatever org name is present in the payload) produced the signature over the raw body — it says nothing about which repository the payload actually targets.

After verification, `create` dispatches the same raw payload to handlers: [3](#0-2) 

Handlers such as `PushHandler` resolve the affected stacks using `repository.full_name`, a field that is completely independent of `repository.owner.login`: [4](#0-3) [5](#0-4) 

The same pattern is used by every handler that looks up a repository/stack via `Repository.from_github_repo_name(params.repository.full_name)` (pull-request handlers, status/check_suite handlers, etc.).

**The broken equality:** the engine implicitly assumes
`organization authenticated by signature == organization owning repository.full_name that handlers act on`,
but nothing in the code enforces this. An attacker who legitimately controls a GitHub organization/App that this Shipit instance also trusts (i.e., has a valid `webhook_secret` for *their own* org, "OrgA") can craft an arbitrary JSON body where `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")`'s secret is used and validates) while `repository.full_name = "OrgB/some-repo"` — a repository belonging to a different, unrelated organization ("OrgB") whose secret the attacker never had. The signature check only proves "this body was signed with OrgA's secret"; it never proves "this body's `repository.full_name` belongs to OrgA."

### Impact Explanation
Because handlers key off `repository.full_name`, not `repository.owner.login`, this lets an attacker who only controls one tenant/organization's webhook secret:
- Trigger `GithubSyncJob`/`RefreshCheckRunsJob` for stacks belonging to a completely different organization's repository (`PushHandler`, `CheckSuiteHandler`).
- Forge commit `status`/`deployable_status` on a foreign stack's commits (`status` handler), which is precisely the kind of forged CI signal that `Stack.schedule_continuous_delivery`/`ContinuousDeliveryJob` consult to decide whether to auto-trigger a deploy — i.e. this can lead to an **unauthorized deploy** on a stack the attacker does not control, satisfying the "Critical: unauthorized deploy" bar.
- More generally, it is a **cross-repository write**: state belonging to Org B's `Repository`/`Stack`/`Commit` records is mutated using a signature that only proves possession of Org A's secret.

This is a direct analog of the referenced bug class: a value used to gate/authorize an action (the org whose secret is checked) is not the same value that is actually acted upon (`repository.full_name` used by the handler), exactly like `MochiVault` checking against `cf` for authorization purposes while the actual borrowed amount used in execution silently diverges from what was validated.

### Likelihood Explanation
This requires a Shipit deployment configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" mode in `docs/setup.md`), which is an explicitly supported configuration, not a misconfiguration. Any organization/tenant onboarded into that Shipit instance automatically obtains a valid `webhook_secret` for its own org (this is intended, since GitHub sends real webhooks signed with each org's App secret) and needs no further privilege to exploit — they simply send a crafted HTTP POST to `/github/webhooks` with a body they sign themselves using their own secret, no GitHub interaction required. This is exploitable by any unprivileged party who has been granted webhook credentials for one org in a multi-org Shipit install, without needing repository write access or an API token for the target org.

### Recommendation
After selecting the GitHub App by `repository_owner`/`organization.login` for signature verification, re-validate that the resolved `Repository`/`Stack` (looked up via `repository.full_name`) actually belongs to that same organization (e.g., compare `full_name.split('/').first` against `repository_owner`, or better, look up the app config from the resolved repository's owner rather than from an attacker-controlled field) before dispatching to handlers. Alternatively, verify the signature using the specific `webhook_secret` tied to the repository actually being acted on, derived only after confirming ownership, not from the same untrusted field used for routing.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` and `OrgB`, each having distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker with legitimate access to `OrgA`'s webhook secret (e.g., an admin of the `OrgA` GitHub App installation), construct a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<any sha>",
     "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } }
   }
   ```
3. Compute `X-Hub-Signature` using `OrgA`'s `webhook_secret` over the raw body and POST to the webhooks endpoint with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), and the signature verifies successfully since it was actually signed with `OrgA`'s secret.
5. `PushHandler#process` resolves stacks via `repository.full_name = "OrgB/target-repo"` and enqueues `GithubSyncJob`/updates state for `OrgB`'s stack — despite the request never being authenticated by anything belonging to `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
