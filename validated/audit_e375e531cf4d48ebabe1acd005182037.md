### Title
Cross-organization webhook forgery lets an attacker escalate into `Shipit.github_teams` via `membership` events - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook using the `webhook_secret` of whatever organization the payload *claims* to be from (`repository_owner`/`organization.login`), not the organization that actually owns the `team.id` in the payload. `MembershipHandler#find_or_create_team!` then looks up/mutates the `Team` record purely by the numeric `team.id`, with no check that the authenticating organization matches `team.organization`. An attacker who owns their own GitHub organization (and thus a valid `webhook_secret` for it) can therefore forge a `membership` event naming a victim org's real team id and their own login, causing `team.add_member(member)` to add themselves to that team.

### Finding Description
Binding claimed: `authenticated_organization (repository_owner used in Shipit.github(organization: repository_owner).verify_webhook_signature)` == `owning_organization_of(Team.find_or_create_by!(github_id: params.team.id))`. This binding is **not enforced**.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`). For a `membership` event there is no `repository` key, so `repository_owner` == `params['organization']['login']`, fully attacker-controlled and used only to select which org's `webhook_secret` verifies the HMAC.
2. Signature is checked against that org's `webhook_secret` via `Shipit.github(organization: repository_owner).verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`). An attacker who controls org "ORG_A" (their own GitHub org, with valid `webhook_secret` configured for Shipit) can sign any payload where `organization.login == 'ORG_A'`.
3. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`). This lookup is keyed **only** on the numeric `github_id`, which is independent of `params.organization.login`. If a `Team` row already exists for that `github_id` (e.g. a real team belonging to victim org "ORG_B", already wired into `Shipit.github_teams`), the `find_or_create_by!` block (which would otherwise set `team.organization`) is skipped and the existing victim team record is returned unchanged.
4. `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) is then called with `member = User.find_or_create_by_login!(params.member.login)`, where `params.member.login` is the attacker's own GitHub login. This creates a `Membership` linking the attacker to the victim's `Team`.

No guard rejects this: `verify_signature` only checks that *some* org's secret matches — it never compares the signing org to the team's `organization` column; `ExplicitParameters` schema only validates types/presence, not cross-references; `drop_unhandled_event` and `check_if_ping` are irrelevant to this path.

### Impact Explanation
If the victim team returned by `find_or_create_team!` is one of the teams listed in `Shipit.github_teams` (used by `User#authorized?` at `app/models/shipit/user.rb:80-82` to gate access), the attacker's `User` record gains membership in that team and thus passes `authorized?`, gaining Shipit-wide authorization (deploy/approve rights) without ever being a real member of the victim GitHub organization or team. This is a cross-tenant authorization escalation: an attacker who only controls their own GitHub org can grant themselves privileged access tied to a completely different organization's team. It is repeatable for any team `github_id` the attacker can learn, against any org configured in the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must (a) control a GitHub organization already registered with Shipit with a legitimate `webhook_secret` (i.e., they are able to configure a webhook against their own repo/org — a normal, unprivileged action for organization owners onboarding to Shipit), (b) know the numeric GitHub `id` of the victim team (team ids are opaque integers, not secrets, and can be discovered via GitHub's public/API team listings or previously observed webhook payloads), and (c) know a `Shipit.github_teams` team is in scope (this is host-configured, may not be secret either). Cost is a single crafted HTTP POST to `/webhooks` with a correctly HMAC-signed body using the attacker's own org secret. No GitHub App private key, Shipit session, or victim secret is required.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and the authenticated organization (e.g., require the payload's `organization.login` to match the existing `Team#organization`, or look up by `[organization, slug]`/`[organization, github_id]` instead of `github_id` alone), and reject/raise if the record exists under a different organization than the one that authenticated the webhook. Alternatively, thread the verified `repository_owner`/organization through to the handler and assert `team.organization == verified_organization` before mutating members.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook signed by org A cannot add a member to org B's team" do
  victim_team = shipit_teams(:cyclimse_cooks) # organization: 'cyclimse', github_id: 2
  attacker_login = 'evil-attacker'

  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => victim_team.name,
                'slug' => victim_team.slug, 'url' => victim_team.api_url },
    'organization' => { 'login' => 'org-a' }, # attacker's own org
    'member' => { 'login' => attacker_login }
  }

  # Signature computed with org-a's webhook_secret (attacker-owned), verified via
  # Shipit.github(organization: 'org-a').verify_webhook_signature — passes.

  assert_no_difference -> { Shipit::Team.count } do
    assert_difference -> { Shipit::Membership.count }, 1 do
      Shipit::Webhooks::Handlers::MembershipHandler.call(payload)
    end
  end

  victim_team.reload
  attacker = Shipit::User.find_by(login: attacker_login)
  assert_includes victim_team.members, attacker
  # Equality check that should have held but didn't:
  # authenticated_organization ('org-a') != victim_team.organization ('cyclimse')
  refute_equal 'org-a', victim_team.organization
end
```
This demonstrates that a webhook authenticated for `org-a` mutates a `Team` record scoped to `cyclimse`, confirming the missing binding.
