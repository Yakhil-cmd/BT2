### Title
`status` webhook writes to any commit sharing a `sha`, regardless of repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` and applies the incoming GitHub status to every matching `Commit` row in the database, without checking that the commit's repository/stack matches the repository that authenticated the webhook. This lets an attacker who controls any repository with the Shipit GitHub App installed set a `ci/test` status on an arbitrary SHA string via the (unauthenticated, content-wise) GitHub Status API, and have it silently applied to a victim's commit in a completely different repository/stack, changing that commit's required-status state and `deployable?` outcome.

### Finding Description
The broken binding: the code should enforce
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')`
for every `Commit` mutated by a `status` webhook, but it never checks this at all.

Path:
- `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` only checks the HMAC signature against the GitHub App configured for `repository_owner` (`params.dig('repository','owner','login')`) [2](#0-1) . This proves the request came from *some* org/repo that has the app installed and produced a genuine GitHub delivery — it says nothing about which commit the payload's `sha` may legitimately refer to. GitHub's Statuses API allows creating a status for an arbitrary 40-hex `sha` string on a repository the attacker controls even if that SHA doesn't correspond to a real commit object in that repo; GitHub will still sign and deliver the resulting webhook faithfully.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` [3](#0-2) , which is the pattern other handlers are expected to use to stay within the authenticated repository's tenant boundary.
- `StatusHandler#process` bypasses this scoping entirely and queries commits globally:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
- `create_status_from_github!` then writes the status using the *victim commit's own* `stack_id` [5](#0-4) , and recomputes `status`/`deployable?`, which is derived from `Status::Group.compact` over `statuses_and_check_runs` [6](#0-5)  and gates `deployable?` [7](#0-6) .

Exploit flow: the attacker owns/administers a repository "attacker/evil" that has the Shipit GitHub App installed (satisfying `verify_signature`). Using the GitHub Statuses API (a normal write action on their own repo, no Shipit credentials needed), they create a status with `sha` equal to a known/guessed victim commit SHA (e.g. observed via the victim's public Shipit UI or GitHub history), `context: "ci/test"`, `state: "failure"`. GitHub signs and delivers this as a real `status` webhook, which passes `verify_signature` because it originates from a repo/org the attacker legitimately controls. `StatusHandler` then finds the victim's `Commit` row purely by SHA equality and appends the failing status to it, which can flip `deployable?`/merge eligibility for the victim stack if `ci/test` is in that stack's required contexts.

Existing guards fail specifically because they authenticate the *sender* (the org/app installation) but not the *target record* being mutated; `StatusHandler` never re-derives or checks `payload.dig('repository','full_name')` against the commit's own stack/repository, unlike the `stacks` helper on the base `Handler` class that other handlers rely on.

### Impact Explanation
A payload authenticated for one repository can mutate commit/status state belonging to an unrelated stack/repository, directly matching the "Critical: a payload for one repository mutating another's stack, commit" category. The blast radius is any commit whose SHA the attacker can guess or observe (Shipit exposes commit SHAs in its UI/API), across every stack tracked by that Shipit instance — a genuine cross-tenant write. This can flip `deployable?` (blocking legitimate deploys) or clear a failing required status (enabling unauthorized deploys/merges) for a stack the attacker has no access to.

### Likelihood Explanation
Preconditions: the attacker needs write/status-creation rights on some repository that has the same Shipit GitHub App installed (this is common in a shared Shipit deployment serving many teams/repos under one or a few GitHub orgs), plus knowledge of the victim's commit SHA (commonly visible via Shipit's own UI, GitHub, or CI logs). No Shipit session, API token, or webhook secret is required — the attacker relies on GitHub's own legitimate signing of their own repo's events. This is inexpensive, fully repeatable against any SHA/stack pair, and doesn't require any SHA1 collision — only that the string matches, which the attacker fully controls via the GitHub Status API on their own repo.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler, e.g. check_run handlers) to the repository that authenticated the event, mirroring the base `Handler#stacks` pattern, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures only commits belonging to stacks tracking the authenticated `repository.full_name` can be mutated by the webhook.

### Proof of Concept
minitest plan (no live GitHub required — directly exercise `StatusHandler`):
1. Create `stack_a` for repository `org/repo-a` with `ci.require = ['ci/test']`, and a `commit_a` on it with `sha = "a" * 40`.
2. Create `stack_b` for a different repository `org/repo-b` (attacker-controlled), with a commit sharing the same `sha = "a" * 40` (simulating attacker crafting a status payload with that sha for their own repo).
3. Assert before: `commit_a.reload.deployable?` is `false`/pending as appropriate (no statuses yet), and `commit_a.status.state` differs from `"failure"`.
4. Build a payload: `{ "sha" => "a"*40, "state" => "failure", "context" => "ci/test", "repository" => { "full_name" => "org/repo-b" } }` and call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert after: `commit_a.reload.status.state == "failure"` and `commit_a.deployable?` changed from its pre-state (e.g., from `true`/pending to `false`), even though the payload's `repository.full_name` is `org/repo-b`, not `org/repo-a` — demonstrating the equality `commit.stack.repository.full_name == payload["repository"]["full_name"]` is violated: expected `false` (should be rejected), actual write proceeds.
