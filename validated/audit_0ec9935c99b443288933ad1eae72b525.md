Based on my investigation, I found a strong analog in `pallet-psm` (Peg Stability Module), which is exactly the token-decimals-drift bug class described in the report, and confirmed that the codebase's own documented mitigation is not actually wired into the vulnerable code paths.

### Title
`pallet-psm::mint`/`redeem` use stale registration-time decimal snapshots instead of live token decimals, enabling under-collateralized minting on decimal changes - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` swaps an "internal" stablecoin for approved "external" assets 1:1 (minus fees), using decimal-scaling math to normalize between the two assets' precisions. It snapshots each asset's `decimals` at `create_psm`/`add_external_asset` time into `PsmInfo::internal_decimals` and `ExternalAssetInfo::decimals` [1](#0-0) [2](#0-1) . Both `mint` and `redeem` read these stored snapshots, never the asset's live `decimals()` metadata, to perform the `external_to_internal`/`internal_to_external` conversion [3](#0-2) [4](#0-3) .

### Finding Description
This is precisely the bug class in the report: fixed decimals assumed at creation time can silently diverge from live token decimals, corrupting 1:1 accounting. The `prdoc` for this pallet claims a fix ("Runtime drift guard: `mint`/`redeem` return `DecimalsMismatch` if live metadata diverges from the registration snapshot") [5](#0-4) , but the actual `Error::DecimalsMismatch` variant is explicitly annotated as dead: "Reserved legacy error; retained to preserve error variant indices" [6](#0-5) , and no code path in `mint` or `redeem` calls `T::Fungibles::decimals(...)` to compare against the stored snapshot — both dispatchables only read `info.internal_decimals` and `external.decimals` from storage [7](#0-6) [8](#0-7) . A test even documents that `redeem` intentionally continues to operate on the stale snapshot after a live decimals change (`redeem_uses_snapshot_when_asset_decimals_drift`), confirming the guard is not enforced [9](#0-8) .

Crucially, `mint` (the external → internal path, which is the one an attacker abuses to extract value) uses the same stale-snapshot logic as `redeem`. If any approved external asset's live decimals subsequently increase (via `pallet-assets::set_metadata`, callable by that asset's owner — not the PSM), the PSM's `ext_decimals` snapshot is now smaller than the real precision of the token. A caller can then deposit a much smaller real-value amount of the external asset (in raw base units, at the *old* decimal scale) and have it converted at the stale (lower) decimal count, producing an inflated `internal_equivalent` and minting excess internal stablecoin — the direct analog of the Beanstalk `FundraiserFacet` exploit (fewer real tokens sent, more of the raised asset received).

### Impact Explanation
An attacker (a normal signed account, no privileged role required — the decimals change is performed by the external asset's owner, which per SECURITY assumptions is not modeled as attacker-controlled, but any legitimate metadata update from `pallet-assets` triggers this) can mint internal stablecoin against significantly under-valued external collateral, draining the PSM's peg backing and directly creating unbacked issuance of the internal asset — a Critical/High-severity theft and insolvency vector for any runtime deploying `pallet-psm` (referenced deployment: `asset-hub-westend-runtime`, per `prdoc/stable2606/pr_11819.prdoc` bump) [10](#0-9) .

### Likelihood Explanation
Likely once any approved external asset's decimals are altered — this is a legitimate, non-privileged (from the PSM's perspective) operation on `pallet-assets`, entirely outside of PSM governance's control, and the pallet's own admin has no way to prevent, detect, or react to it before a `mint` extrinsic exploits the stale conversion. The pallet's own test suite proves the stale-snapshot behavior is deliberate and unguarded on at least the redemption path, and no equivalent guard exists in `mint` either.

### Recommendation
Either (a) read live `T::Fungibles::decimals(asset)` at `mint`/`redeem` time and reject (or halt) the swap when it diverges from the stored snapshot — actually wiring up the currently-dead `Error::DecimalsMismatch` as the `prdoc` claims — or (b) provide a governance-gated resynchronization call (analogous to the report's `synchronizeFundraiserDecimals`) that atomically rescales `PsmDebt`, `PsmInfo::internal_decimals`/`ExternalAssetInfo::decimals`, and blocks `mint`/`redeem` until the resync occurs.

### Proof of Concept
Not independently executed against a live/test harness in this session (no filesystem/terminal access available); the finding is derived from static code inspection: the `mint`/`redeem` dispatchables in `substrate/frame/psm/src/lib.rs` (lines ~703-903) only consult `PsmInfo::internal_decimals` and `ExternalAssetInfo::decimals` snapshots, and the existing test `redeem_uses_snapshot_when_asset_decimals_drift` in `substrate/frame/psm/src/tests.rs:3008-3053` empirically demonstrates a successful swap proceeding on stale decimals after `Assets::set_metadata` changes live decimals, confirming the missing guard exists in-repo as executable, passing test coverage (not a mock/config-only artifact).
