### Title
AA-chain payments confuse `trigger.address` (immediate sender) with `trigger.initial_address` (original human user), risking permanent fund loss - (File: `aa_composer.js`)

### Summary
The reported bug class is: code that treats the immediate message sender's address as if it were the address of the actual end-user/controller of funds, without an explicit "destination" concept, causing tokens/funds to be delivered to an address the true owner cannot control. In ocore's Autonomous Agent (AA) engine, the exact same class of mistake is structurally possible because the trigger object exposes **two different addresses** — `trigger.address` (the immediate sender of the current unit, which can be another AA when the trigger is a *secondary* trigger in a chain) and `trigger.initial_address` (the address of the original human author who started the whole AA chain). AA authors who reflexively use `trigger.address` to send funds back — instead of `trigger.initial_address` — will route funds to an intermediate AA address rather than to the human user who actually initiated and controls the transaction, mirroring the "sender address ≠ true recipient address" bug reported for `SecuritizeBridge`.

### Finding Description
`getTrigger()` builds a trigger object using `objUnit.authors[0].address` as `trigger.address` — this is the address of whoever authored the *current* unit, which is the *previous AA* in a chain, not necessarily the original human: [1](#0-0) 

For a **primary** trigger (submitted directly by a human wallet), `trigger.initial_address` is set equal to `trigger.address`: [2](#0-1) 

But for a **secondary** trigger (an AA calling another AA as part of the same DAG chain), `handleSecondaryTriggers` builds a *child* trigger whose `address` is the *calling AA's* address (since it's derived from `getTrigger(objUnit, row.address)`, where `objUnit.authors[0].address` is the previous/calling AA), while `initial_address`/`initial_unit` are explicitly propagated from the very first trigger in the chain: [3](#0-2) 

This means an AA author who writes `{address: "{trigger.address}", ...}` in a payment message, intending to "pay back the sender," will pay back the **immediately preceding AA** rather than the human who ultimately triggered the chain, whenever this AA is reachable as a secondary hop. This is functionally identical to the reported bug: the code assumes "the address that sent me this message" is interchangeable with "the address that should receive the funds," which is false whenever the sending context differs (cross-chain wallet vs. AA-chain hop).

The engine even documents/tests this exact distinction as something AA authors must consciously handle correctly: [4](#0-3) 

and a real-world composability pattern (`fundraising_proxy.oscript`) that forwards funds through multiple AA hops shows the pattern where getting `trigger.address` vs `trigger.initial_address` wrong at any hop misdirects funds: [5](#0-4) 

Because AA addresses are deterministic hashes of AA bytecode (`chash160`) with no owner-controlled private key, any bytes/asset mistakenly sent to an intermediate AA address (instead of `trigger.initial_address`) are only retrievable if that intermediate AA happens to contain logic recognizing and forwarding an unsolicited deposit — which most simple AAs (e.g. bouncer/forwarder AAs used purely as pass-through hops) do not implement, since they are typically written assuming they are only ever invoked as a *primary* trigger where `trigger.address == trigger.initial_address`.

### Impact Explanation
If an AA is composed to be reusable both as a stand-alone (primary-triggered) contract and as one link in a multi-AA call chain (a common and encouraged composability pattern in Obyte/oscript, demonstrated by the "chain of AAs" tests and the `fundraising_proxy` sample), and its author uses `trigger.address` instead of `trigger.initial_address` for the "refund/payout to caller" output, then whenever that AA is invoked as a secondary trigger, real user funds (bytes or any asset) get sent to the calling AA's address rather than back to the human. Since AA addresses have no private key, this results in unauthorized/irrecoverable fund loss for the end user — functionally equivalent to "AA fund loss" from the accepted analog list. This is a High-severity, real fund-loss risk baked directly into the trigger-address semantics of the AA engine, and is exactly the address-confusion class the external report describes (sender identity assumed reusable as recipient identity across execution contexts).

### Likelihood Explanation
Likelihood is high in practice: composability of AAs (one AA calling another, chains of AAs) is a core, encouraged design pattern in oscript, explicitly supported by `trigger.initial_address`/`trigger.initial_unit` propagation machinery in `aa_composer.js`. Any AA author who does not carefully distinguish `trigger.address` from `trigger.initial_address` — an easy and natural mistake, since `trigger.address` is the more commonly used/simpler field in tutorials/samples for "pay back the sender" — will introduce this bug the moment their AA is invoked indirectly through another AA (which they may not control or anticipate, since any AA can send funds to any other AA's address, triggering it as a secondary trigger). No malicious actor coordination is even required; a benign third-party AA forwarding funds through the vulnerable AA is enough to misdirect funds.

### Recommendation
- In the oscript/AA validation layer, add lint/documentation-level warnings (and ideally a `validateAA` check) flagging AAs that use `trigger.address` for payment outputs without also referencing `trigger.initial_address`, when the AA is otherwise composable (no `if` gating restricting it to primary triggers only).
- Strongly recommend (or default to) `trigger.initial_address` semantics for "refund to the ultimate payer" in framework documentation and starter templates.
- Consider adding a state/response field that explicitly marks whether a trigger is primary or secondary (`bSecondary` is already tracked internally in `aa_composer.js` — expose it to oscript, e.g., `trigger.is_secondary`), so AA authors can add defensive checks (`bounce("no secondary triggers supported")`) instead of silently misdirecting funds.

### Proof of Concept
1. AA `Vulnerable` is written to simply refund incoming bytes minus a fee to `trigger.address`, e.g.:
```
messages: [{
  app: 'payment',
  payload: { asset: 'base', outputs: [{ address: "{trigger.address}", amount: "{trigger.output[[asset=base]] - 1000}" }] }
}]
```
2. Human user Alice (address `ALICE...`) does **not** call `Vulnerable` directly. Instead she calls a `Forwarder` AA, sending it bytes; `Forwarder` forwards the bytes on to `Vulnerable` (as shown in `test/aa_composer.test.js:156-252`, "chain of AAs" pattern, and `fundraising_proxy.oscript`).
3. Inside `handleTrigger`, `Vulnerable` is invoked via `handleSecondaryTriggers`, so its `trigger.address` is set to `Forwarder`'s address (author of the unit sending to `Vulnerable`), while `trigger.initial_address` is `ALICE...` [3](#0-2) .
4. `Vulnerable`'s payment message resolves `{trigger.address}` to `Forwarder`'s address, not Alice's, and sends the refund there.
5. `Forwarder`, having no logic to detect and re-forward unsolicited incoming payments from `Vulnerable`, retains the funds forever — Alice's bytes are permanently stuck in `Forwarder`'s balance, analogous to tokens minted to an uncontrollable address in the original report.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
