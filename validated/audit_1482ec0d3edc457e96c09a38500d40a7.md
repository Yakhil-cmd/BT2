### Title
API deploy/task attribution trusts unauthenticated `X-Shipit-User` header, breaking the GitHub-identity-to-`User` binding - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
The external report's root cause is that a user-controlled amount is acted upon by the contract but only the actually-repaid amount is checked/refunded — the *intended* value and the *executed* value diverge, and nothing reconciles them. In `shipit-engine`, the analogous binding break is between "the GitHub identity that actually performed an action" and "the `User` record Shipit attributes the resulting deploy/rollback/task to." The API only cryptographically authenticates the `ApiClient` bearer token; the *acting user* is taken verbatim, unauthenticated, from the `X-Shipit-User` request header and is never verified against the caller's real GitHub identity.

### Finding Description
`Shipit::Api::BaseController#authenticate_api_client` verifies only the `ApiClient` bearer token (an HMAC-signed id) via `ApiClient.authenticate`. [1](#0-0) 

Separately, `current_user`/`identify_user` resolve the acting `User` purely from the client-supplied `X-Shipit-User` header, with no signature, no cross-check against the API client's creator, and no verification that the request truly originates from that GitHub account: [2](#0-1) 

This `current_user` is then passed straight through as the deploy/task "author" of record, e.g. in `Api::DeploysController#create`: [3](#0-2) 

and it is persisted on the `Task`/`Deploy` record via `belongs_to :user` and surfaced as `author`: [4](#0-3) [5](#0-4) 

The tests confirm this behavior is intentional-but-unverified: any caller holding a valid `ApiClient` token can freely set the header to impersonate any existing Shipit `User` login: [6](#0-5) 

Before vs. after equality that is broken:
- Expected binding: `GitHub identity of the actor == User record attributed to the resulting Task/Deploy`.
- Actual binding enforced by the code: `ApiClient token validity == permission to write ANY User login into the `user_id`/author field`, regardless of who is really acting.

This mirrors the WETH report's flaw exactly at the abstraction level required by the rules: the system checks one thing (the token/amount) but silently trusts an unverified, attacker-controlled companion value (the login/refund amount) that ends up baked into a persisted, trust-bearing record.

### Impact Explanation
Any holder of a valid `ApiClient` token with `deploy:stack` (or `write:hook`/task-trigger) permission can attribute deploys, rollbacks, and custom tasks to an arbitrary other Shipit `User` simply by setting `X-Shipit-User`. Because `author`/`user` fields are used throughout the UI, notifications, hooks, and audit trail (`lock_author`, `aborted_by`, `SHIPIT_USER`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` injected into deploy commands, see `lib/shipit/task_commands.rb`), this allows spoofing the identity behind a deploy/rollback/task for audit-log falsification and social-engineering ("this was approved/run by <trusted person>"), while the true actor (the API-token holder) is hidden. This does not itself grant additional deploy permissions beyond what the `ApiClient`'s own `permissions`/`stack_id` scope allow, so it does not rise to full "unauthorized deploy" by itself — but it directly defeats the authenticity guarantee that Shipit's audit trail (who ran/approved a deploy) is meant to provide, which is the same class of "trust silently broken by an unchecked, attacker-supplied value" as the source report.

### Likelihood Explanation
Any party with a legitimately issued `ApiClient` token (which is a lower privilege bar than repository write access or the webhook secret, and explicitly not excluded by the ruleset) can trigger this with a single crafted header on any deploy/task/rollback API call — no timing race, no additional secrets, and it is exercised routinely enough that the test suite documents the header as a supported (if effectively unauthenticated) feature. [7](#0-6) 

### Recommendation
Do not trust `X-Shipit-User` as an unauthenticated identity claim. Either (a) bind the acting user to the `ApiClient#creator` and require it to match, (b) require a signed/verified assertion (e.g., mediated by the actual GitHub OAuth session rather than a raw header) before allowing `X-Shipit-User` to override the attributed author, or (c) restrict the header's use to trusted internal callers only and record the true `ApiClient` identity alongside any claimed user for audit purposes.

### Proof of Concept
1. Obtain any `ApiClient` token with `deploy:stack` permission (e.g., an integration's own low-trust token).
2. `POST /api/stacks/:owner/:repo/:env/deploys` with header `X-Shipit-User: <victim-login>` and a valid `sha`.
3. Observe (per `test/controllers/api/deploys_controller_test.rb:49-61`) that `Deploy.last.user == victim`, i.e., the deploy is permanently attributed to a user who never made the request — confirming the identity binding is unauthenticated and forgeable.
