### Title
Unvalidated swap route lets a rogue hop contract execute arbitrary token transfers under the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) forward attacker/victim-supplied route bytes (`swap: Bytes`) to the swap router without decoding or validating them. The router keeps no allowlist of the pool/token addresses a route names, so a crafted route can place arbitrary third-party contract calls on the stack beneath the caller's signed authorization — mirroring CVE-2024-0333's "insufficient data validation lets a crafted payload trigger an unintended privileged action." A malicious venue contract invoked mid-route can call `token.transfer(victim, attacker, X)` and Soroban records it as a child of the caller's `require_auth` entry; if the caller signs the recorded tree, the transfer executes.

### Finding Description
In `swap_tokens` the controller authorizes exactly one input transfer to the router and then calls `router.execute_strategy(&controller, &amount_in, swap)` — the `swap` bytes are opaque to the controller [1](#0-0) . The router dispatches each hop to a venue adapter keyed only by the payload's `SwapVenue` tag and the pool address embedded in the payload; `dispatch_hop` only measures balance deltas and never checks that the hop's target contract is a genuine venue [2](#0-1) . The threat model explicitly acknowledges that "a route can put third-party code on the call stack below the caller's authorization" and that the resulting wallet drain "is not bounded by the payload minimum nor the final risk gate" [3](#0-2) . The dedicated test registers a `RogueHopPool` that transfers Alice's unrelated `wallet_token` to the attacker during the hop; the swap still delivers the quoted output, the account passes all risk gates, and simulation records the theft as a child invocation of Alice's `swap_collateral` auth entry [4](#0-3) .

### Impact Explanation
Theft of user funds: the entire balance of any token in the victim's wallet can be transferred to the attacker inside an otherwise fully "successful" `swap_collateral`/`swap_debt`/`multiply` call. The stolen transfer is unrelated to the routed amount — the test drains `WALLET_BALANCE` of a token the strategy never touches while the position still receives `FAIR_OUT_ETH` and remains healthy [5](#0-4) .

### Likelihood Explanation
Requires the victim to sign a poisoned authorization tree (the crafted route plays the role of the CVE's "crafted HTML page"; UI:R, matching the Medium rating). Because `simulateTransaction` records the rogue transfer as a normal child auth entry, a non-enforcing signer or a client that does not decode routes — exactly what the threat model warns about — accepts it. Any unprivileged attacker can deploy the rogue pool contract and distribute the route bytes; no privilege, leaked key, or oracle manipulation is needed [6](#0-5) .

### Recommendation
Validate routes instead of treating them as opaque: (a) have the router maintain a venue/pool registry or verified-pool allowlist so hops can only target legitimate adapter contracts; (b) reject hop targets that are arbitrary user-deployed contracts; (c) enforce in the SDK/signing path that the recorded auth tree for a strategy call contains exactly the expected child entries (one token transfer to the router) and refuse anything else. Until (a)/(b) exist, this remains a sign-time trap bounded only by the user's client hygiene.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `Scene::route_through_pool_stealing` builds a `RoutedSwap` whose `hop_pool` is a registered `RogueHopPool` carrying the plan `(alice, wallet_token, attacker, amount)` [7](#0-6) . The test then calls `ctrl.try_swap_collateral(alice, …, route)` in recording mode, asserts the recorded auth tree contains the stolen `wallet_token.transfer(alice → attacker)` as a child of `swap_collateral`, and confirms `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the position still received the fair ETH output [4](#0-3) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
