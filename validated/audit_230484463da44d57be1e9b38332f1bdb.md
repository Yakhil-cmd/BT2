## Title
Webhook signature is verified against an organization derived from an attacker-controlled payload field, while every handler acts on a different, independently-controlled repository field in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects *which organization's* `webhook_secret` to check the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted request body, before any signature has been validated. Every actual webhook handler (status, push, check_suite, pull_request, membership) then re-parses the same body and resolves the target `Stack`/`Repository` via a *different, independent* field (`repository.full_name`), or via `organization.login`/team data for membership events. Because the two fields live in the same attacker-controlled JSON body and are never cross-checked, a party who legitimately owns one Shipit-tracked GitHub organization (and therefore knows/controls a valid `webhook_secret` for that org) can forge a correctly-signed request whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` (or other identifying fields) points at a completely different, unrelated tracked repository.

## Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
before_action :check_if_ping, :drop_unhandled_event, :verify_signature
...
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the very body whose authenticity is about to be checked. `Shipit.github(organization: ...)` looks up a per-organization `webhook_secret` and `verify_webhook_signature` HMACs the *entire raw body* with that secret [2](#0-1) . This proves only that *some* party who knows Org X's secret sent this exact body — it does not prove that the `repository` object embedded in that body actually belongs to Org X.

Once the filter passes, handlers dispatch purely on the body content, resolving the actual target independently of `repository.owner.login`:
- `PullRequest::OpenedHandler#repository` uses `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , a field independent of `repository.owner.login`.
- `MembershipHandler` (per `webhooks_controller_test.rb`) creates/updates `Team`/`User` records purely from the payload's `team`/`member` fields [4](#0-3) .
- Status/push/check_suite handlers similarly key off `repository`/`sha` fields inside the same signed blob, unrelated to the owner field used only for secret selection.

Since `repository.owner.login` and `repository.full_name` (or `organization.login` and `team`/`member` data) are sibling, independently-settable JSON fields inside one HTTP body, an attacker who controls Org A (and thus a real webhook secret Shipit trusts for Org A) can set `repository.owner.login = "OrgA"` to pass `verify_signature`, while setting `repository.full_name = "OrgB/target-repo"` (a repo/stack they have no access to) so the actual handler logic operates on Org B's stack. This breaks the intended binding: **organization authenticated (via HMAC secret lookup) == repository actually written to**.

## Impact Explanation
This allows a party who is not authorized on a target repository to forge Shipit-recognized GitHub events for that repository as long as they control the webhook secret of any other org tracked by the same Shipit instance. Depending on which event/handler is abused this enables, e.g.:
- Forging `commit_status`/`check_suite` results for another repository's commits, letting CI-status-gated merge/deploy logic in `MergeRequest#reject_unless_mergeable!` / `all_status_checks_passed?` be manipulated for a repo the attacker doesn't own [5](#0-4) , which can lead to an unauthorized merge/deploy on that repository.
- Forging `pull_request` events that auto-provision review stacks (`OpenedHandler`) for arbitrary tracked repositories [6](#0-5) , causing cross-repository writes (`Stack`, `PullRequest`, `Commit` records created/mutated for repos the attacker does not control).
- Forging `membership` events that create arbitrary `Team`/`User` records, potentially interacting with `Shipit.github_teams` authorization used by `User#authorized?` [7](#0-6) .

This maps to the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact tiers, satisfying the rules' Critical/High impact bar, and does not require any Shipit session, `ApiClient` token, or repository write access on the *target* repo — only ownership of any one org already configured in Shipit.

## Likelihood Explanation
Requires the attacker to control at least one GitHub organization/repository that is already integrated with the target Shipit instance (and thus knows that org's webhook secret, which they legitimately possess as the org owner). This is a realistic scenario for any multi-tenant/shared Shipit deployment serving multiple organizations, or in the code4rena-style deployment where any team onboarded to Shipit could pivot to attack any other onboarded team's repositories. No social engineering, TLS interception, or privileged Shipit account is required.

## Recommendation
- After computing the verified organization from the (already-verified) request, re-derive the target `Repository`/`Stack` strictly from a field whose *owner* is checked against that same verified organization — reject the request if `repository.full_name`'s owner segment does not match `repository.owner.login`/`organization.login` used for signature selection.
- Alternatively, verify the signature against every organization configured in Shipit rather than trusting an attacker-supplied field to pick which secret to check, and only then trust body-derived identifiers.
- Add a regression test sending a validly-signed-for-OrgA payload whose `repository.full_name` references OrgB's repository and assert it is rejected.

## Proof of Concept
1. Attacker legitimately owns `github.com/OrgA/*`, which is registered in the Shipit instance with webhook secret `S_A` (a webhook Shipit itself configured on OrgA's repos, so the attacker, as an org admin, can view/rotate/know it, or simply replay a signature they can compute because they control OrgA's webhook delivery settings).
2. Attacker crafts a `pull_request` (or `status`/`check_suite`) JSON body where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/private-target"` (a repo/stack OrgA has no access to but which is tracked by the same Shipit instance)
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, raw_body)` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `S_A`, since the body used to compute it is unchanged [8](#0-7) .
5. The `create` action dispatches to the registered handler for the event, which resolves the target using `repository.full_name` = `OrgB/private-target`, e.g. `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , causing Shipit to create/update records for `OrgB/private-target` on the strength of a signature that only proves knowledge of `OrgA`'s secret.

**Note on limitations:** I was unable to fully enumerate every webhook handler's exact field usage (e.g., `status_handler.rb`, `push_handler.rb`, `check_suite_handler.rb` contents were not retrieved due to tool/time limits), so the precise blast radius per event type is not fully confirmed from source, though the pull_request/opened and membership handlers were directly confirmed to use fields independent of the signature-selection field.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      return reject!('merge_conflict') if merge_conflict?

      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

    end

      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)

    end
