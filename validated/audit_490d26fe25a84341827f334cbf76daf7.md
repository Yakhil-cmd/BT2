## Analysis

The Alchemix bug is a **directional rounding-to-zero flaw**: a rate is derived by dividing a small numerator by a large denominator, and when the divisor dominates, the rate truncates to `0`, silently freezing state that other, unrelated parties rely on. The Zest vaults (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) contain a structurally identical pattern in `calc-multiplier-delta` / `next-index` / `next-liquidity-index`, with an added asymmetry that lets one caller freeze another set of users' yield.

### Root cause

`calc-multiplier-delta` computes `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS`, rounded **up** for the borrow index and **down** for the liquidity (depositor) index: [1](#0-0) 

`next-index` (borrower debt index) always rounds up, so any nonzero numerator guarantees the index strictly increases — and, critically, this triggers `last-update` to be reset in `accrue`: [2](#0-1) 

`next-liquidity-index` (depositor share-value index) rounds **down**, so for the same tiny `time-delta` the multiplier can truncate to `INDEX-PRECISION` (i.e., zero growth) whenever `liquidity-rate * time-delta * INDEX-PRECISION < SECONDS-PER-YEAR-BPS`: [3](#0-2) 

`accrue` writes both indexes and only resets `last-update` when either index actually changed: [4](#0-3) 

Because `idx` (borrow index) rounds up and therefore changes on virtually every call where `rate>0`, `last-update` gets reset to `stacks-block-time` on almost every accrual — even in blocks where the liquidity index failed to grow at all due to downward rounding. This means the "clock" that the liquidity-index calculation needs in order to accumulate enough `time-delta` to overcome the rounding floor is perpetually reset before it can do so, while the debt side keeps compounding.

### Attacker / victim / shared state

- **Shared state:** `last-update`, `index` (borrower debt index), `lindex` (depositor liquidity index) — all vault-wide, not per-account.
- **Attacker:** any unprivileged caller of a state-mutating vault entry point that internally calls `accrue()` (e.g., `deposit`, `redeem`, `system-borrow`, `repay`, `set-points-util`), executed once per block/near-continuously.
- **Victim:** all liquidity providers (depositors) of that vault, whose share value is derived from `lindex`.
- **Mechanism:** by repeatedly triggering `accrue()` with only a few seconds between calls (realistic on Stacks Nakamoto's fast block cadence, especially at low utilization where interest curves start near 0%), the attacker keeps `time-delta` small enough that `liquidity-rate * time-delta * INDEX-PRECISION < SECONDS-PER-YEAR-BPS`, so `calc-multiplier-delta` for the liquidity side rounds to `INDEX-PRECISION` (no growth) every single time — yet `next-index` for debt still rounds up and changes, resetting `last-update` and preventing `time-delta` from ever growing large enough to escape the rounding floor.

### Outcome with vs. without the attacker

- **Without attacker:** `accrue()` is called sporadically by normal user activity; `time-delta` accumulates across longer intervals, `liquidity-rate * time-delta` eventually exceeds the rounding threshold, and `lindex` grows to reflect earned interest, correctly increasing depositors' claim on `total-assets`.
- **With attacker:** by front-running/spamming cheap accrual-triggering calls every block, the attacker keeps resetting `last-update` before `lindex` can cross the rounding threshold. `index` (debt) still grows because of round-up protection, so borrowers keep owing more and `total-assets` (which includes `debt - total-borrowed` as "interest") keeps growing, but `lindex` — the value depositors' shares are priced against — never advances. Depositors' shares are permanently undervalued relative to the true earned interest, i.e., yield accrues to the pool's asset side but is never reflected in the index depositors redeem against, freezing that yield indefinitely for as long as the griefing continues.

This matches the report's "no profit motive, damage to protocol/users" griefing pattern and lands squarely on **temporary/permanent freezing of unclaimed yield** for lenders — an in-scope High-severity impact.

### Title
Downward rounding of `next-liquidity-index` combined with `last-update` reset on borrow-index growth freezes depositor yield - (File: `mainnet/contracts/vault/v0-vault-{stx,usdc,sbtc,ststx,ststxbtc,usdh}.clar`)

### Summary
`calc-multiplier-delta` divides `rate * time-delta * INDEX-PRECISION` by `SECONDS-PER-YEAR-BPS`, rounding up for the borrow index (`next-index`) but down for the depositor liquidity index (`next-liquidity-index`). Because `accrue()` resets `last-update` whenever the borrow index changes (which happens on almost every call, since rounding up guarantees growth), the liquidity index's `time-delta` is perpetually reset before it accumulates enough magnitude to escape rounding-to-zero, permanently starving depositors of interest that is nonetheless being charged to borrowers.

### Finding Description
`calc-multiplier-delta` at [1](#0-0)  computes the growth multiplier as `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS`. `next-index` (borrower debt) rounds this **up** at [2](#0-1) , guaranteeing the index strictly increases whenever `rate>0` and `time-delta>0`. `next-liquidity-index` (depositor share pricing) rounds **down** at [3](#0-2) , so it can produce zero growth for the same short `time-delta`/low-`rate` conditions. `accrue()` only advances `last-update` when either index changed [4](#0-3) ; since the borrow index almost always changes, `last-update` is reset before the liquidity index's `time-delta` window can grow large enough to overcome its rounding floor.

### Impact Explanation
Debt owed by borrowers keeps compounding (protected by round-up), while the index depositors use to redeem shares (`lindex`) stalls. `total-assets` grows via the debt-interest term, but depositors' claims priced off `lindex` do not reflect it, so the accrued interest is never credited to lenders — a permanent freezing of unclaimed yield for all depositors in the affected vault, sustainable indefinitely as long as the trigger transactions keep occurring roughly once per block.

### Likelihood Explanation
Any account can call a cheap state-mutating vault function (e.g., a tiny `deposit`/`redeem`/`repay`) every block; no privileges are required. The trigger conditions (low `rate` at low utilization, short `time-delta` from fast Stacks block cadence) are realistic during normal operating conditions, particularly near-zero base interest rates common in typical interest-rate curves.

### Recommendation
Decouple `last-update` resets from the borrow-index change alone; only reset `last-update` when the liquidity index accrual is nonzero, or accumulate a running remainder for `next-liquidity-index` (e.g., store unaccounted micro-time or micro-interest) instead of truncating it away each call, analogous to raising the effective precision so genuine progress isn't repeatedly erased by rounding.

### Proof of Concept
1. Configure the vault's rate curve so that at current utilization the interpolated `liquidity-rate` is low (e.g., near-zero base rate).
2. Have the attacker call any accrue-triggering function (e.g., `deposit` with a minimal amount) once per block.
3. Each call computes `time-delta` ≈ block interval; verify `liquidity-rate * time-delta * INDEX-PRECISION < SECONDS-PER-YEAR-BPS`, so `next-liquidity-index` == `lindex` (no growth), while `next-index` > `index` (debt grows) because `mul-div-up` rounds any positive numerator up to at least `INDEX-PRECISION + 1`.
4. Observe `accrue()` sets `last-update = stacks-block-time` because `idx != next`, resetting the window for the next call.
5. Repeat over many blocks: `index` (debt) compounds upward while `lindex` (depositor value) never advances, demonstrating permanently frozen yield for depositors despite ongoing interest accrual on the debt side.
