### Title
Cross-tenant forged CI status via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using the attacker-controlled `repository.owner.login` (or `organization.login`) field from the JSON body, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization has no `webhook_secret` configured. `StatusHandler#process` then updates commit CI status by looking up `Commit.where(sha: params.sha)` globally, with **no scoping to the repository/organization that was actually verified**. This lets an attacker who controls (or names) any org entry in Shipit's github config that lacks a `webhook_secret` forge a `status` webhook for a commit SHA belonging to a completely different, victim stack.

### Finding Description
The broken binding is: **organization verified in `verify_signature` (`repository_owner` from payload) == organization/repository owning the `Commit` mutated by `StatusHandler#process`**. These are never checked to be equal.

- `Shipit::WebhooksController#verify_signature` picks the app config via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the untrusted payload: `params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` if the resolved org's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
- Multi-org deployments are explicitly documented/exampled with per-org `webhook_secret` entries that can be left `nil` (e.g. `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple Github Applications" section), and `Shipit.github_app_config` resolves any org key case-insensitively from `secrets.github`. [4](#0-3) [5](#0-4) 
- `Shipit::Webhooks::Handlers::Handler` provides a repository-scoped `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers (e.g. push/pull_request handlers) use to constrain their effects to the verified repository. [6](#0-5) 
- `StatusHandler#process`, however, ignores this scoping entirely and queries commits globally by SHA: [7](#0-6) 

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: status` and a body containing `repository.owner.login` (or `organization.login`) set to any org name present in Shipit's `secrets.github` map whose `webhook_secret` is not configured (a documented/valid configuration state for multi-org installs), `sha` set to a real commit SHA belonging to a victim stack (obtainable from the victim's public GitHub repo/PR), and `state` set to `success` or `failure`. `verify_signature` calls `Shipit.github(organization: <attacker-named org>).verify_webhook_signature(...)`, which returns `true` regardless of the (missing/garbage) `X-Hub-Signature` because that org has no secret. `StatusHandler.call` then runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, mutating the victim's `Commit` status even though the verified organization has nothing to do with the victim's repository.

`Commit#add_status` (invoked transitively via status creation) fires `deployable_status` hooks and calls `stack.schedule_merges` on transitions to `pending`/`success`, directly affecting `Stack#deployable?` gating and auto-merge/deploy scheduling for the victim stack. [8](#0-7) 

None of the existing guards prevent this: `verify_signature` only checks a signature against a secret chosen from attacker-controlled payload data, not that the org owns the target repo/commit; `drop_unhandled_event` and `ExplicitParameters` schema only validate structural shape (`sha`, `state`, etc.), not ownership; there is no per-handler check binding `payload['repository']['full_name']`/owner to the commit's actual `stack.repository`.

### Impact Explanation
An attacker can flip the CI status of an arbitrary commit in any stack hosted on the same Shipit instance, as long as they can name a configured-but-secretless org in the verification step and know a target SHA. This can forge `success` to satisfy `required_statuses`/`deployable?` gating and trigger `stack.schedule_merges`, or forge `failure` to block a legitimate deploy/merge for a victim tenant — a cross-tenant integrity violation matching "a payload for one repository mutating another's stack/commit" and "an unauthorized deploy... " in the Critical impact category. It is repeatable against any known commit SHA in any stack on the instance, not limited to a single victim, as long as the vulnerable secretless-org config condition holds.

### Likelihood Explanation
This is not exploitable against every Shipit deployment: it strictly requires that Shipit be configured with the multi-org github schema (`secrets.github` keyed by org name) and that **at least one** configured org key has no `webhook_secret` set — a state the project's own docs and example configs (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`) show as a normal/expected configuration shape for a not-yet-hardened org integration. Given that precondition, the attacker's cost is trivial: no secrets, tokens, or sessions are needed, only knowledge of (a) the secretless org's name and (b) a target commit SHA (public in GitHub for public repos or PRs). Single-org installs (the common default, one top-level `webhook_secret`) are not vulnerable via this exact vector unless that single org's secret itself is left unset, which is a separate, narrower misconfiguration.

### Recommendation
Scope `StatusHandler#process` (and any other handler that mutates records by attacker-supplied identifiers) to the repository verified in the webhook, e.g. restrict the `Commit` lookup to commits belonging to `stacks` (the handler's repository-scoped stacks) rather than a bare `Commit.where(sha: params.sha)`. Additionally, `verify_signature`/`GitHubApp#verify_webhook_signature` should not silently accept unsigned payloads when a `webhook_secret` is unset for an org that has other data-mutating handlers registered; consider requiring a non-blank `webhook_secret` for all configured orgs or rejecting mutation when signature verification is not enforceable.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), using the multi-org secrets fixture:
1. Configure `Shipit.stubs(:secrets)` (or override `secrets.github`) to include two orgs: `victim-org` (real `webhook_secret`) and `attacker-org` (no `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create a victim stack/repository owned by `victim-org` with a commit `victim_commit` (sha `SHA_X`), asserting initial `victim_commit.state == 'pending'` and `stack.deployable?` is `false` (e.g., required status missing).
3. Build a `status` webhook body: `{ "sha" => "SHA_X", "state" => "success", "repository" => { "owner" => { "login" => "attacker-org" } } }`, with an arbitrary/garbage `X-Hub-Signature` header (or none).
4. `POST :create` with `X-Github-Event: status`; assert `response` is `:ok`.
5. Assert `victim_commit.reload.state == 'success'` (equality now holds where before it was `pending`/`failure`) even though the verifying org (`attacker-org`) is not equal to the victim commit's owning org (`victim-org`) — proving the binding "verifying org == commit-owning org" is broken.
6. Assert `stack.reload.deployable?` (or the `deployable_status`/`ProcessMergeRequestsJob` enqueue via `assert_enqueued_with`) changed as a result, demonstrating the deploy/merge-gating impact.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end
