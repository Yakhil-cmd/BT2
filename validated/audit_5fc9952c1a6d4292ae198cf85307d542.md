## Title
Cross-organization webhook signature confusion — authenticated organization does not bind the repository the event writes to - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository.owner.login` (or `organization.login`) from the *unauthenticated* JSON body, but the downstream event handlers resolve the target `Stack`/`Repository` using an entirely different field of the same body — `repository.full_name`. Because Shipit supports multiple onboarded organizations, each with its own `webhook_secret`, an attacker who legitimately controls one onboarded organization can forge a signature that is valid for their own org while pointing `repository.full_name` at a stack belonging to a completely different organization.

### Finding Description
`verify_signature` computes `repository_owner` purely from attacker-controlled JSON and uses it to pick the GitHub App config/secret to verify against: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`webhook_secret`, etc.) from `secrets.github`, confirming that multiple orgs, each with independent secrets, are supported by design: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only checks the HMAC of the raw body against that organization's secret; it has no knowledge of, or binding to, which repository the body actually targets: [4](#0-3) 

After signature verification passes, `create` dispatches the *entire* raw payload to handlers: [5](#0-4) 

But handlers resolve the target repository/stacks using `repository.full_name`, a field that was never covered by, or reconciled with, the org used for signature verification: [6](#0-5) 

The binding broken is:
`organization used to select the verifying secret` ≠ `repository.full_name whose stacks/commits are mutated`.

Before the attack, an attacker who owns/administers organization `attacker-org` in Shipit legitimately knows `attacker-org`'s `webhook_secret` (e.g. because they registered the app installation for their own org, or simply reuse the fact that they can compute a valid signature against their own org's secret). This alone is intended to authorize only webhook traffic for repositories under `attacker-org`. After the attack, by crafting a JSON body where `repository.owner.login` (or `organization.login`) = `"attacker-org"` but `repository.full_name` = `"victim-org/victim-repo"`, the same valid HMAC signature (computed with `attacker-org`'s secret) is accepted by `verify_signature`, and the handler layer then acts on `victim-org/victim-repo`'s stacks using data taken from the request body.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope. Concretely reachable writes to a foreign repository's records include:
- `StatusHandler#process`, which creates a `Status` on any `Commit` matching an attacker-supplied `sha` using attacker-controlled `state`/`description`/`target_url`/`context` — this can flip CI-required statuses (`ci.require`) for a stack the attacker does not own, since `Commit.where(sha: params.sha)` is looked up across the whole database, not scoped by the verified organization: [7](#0-6) 
- `PushHandler#process`, which triggers a `GithubSyncJob` resync for a foreign stack's branch based on attacker-chosen `ref`/`after`: [8](#0-7) 

Falsifying a required CI status can unblock an unauthorized deploy on a stack the attacker does not control (a stack belonging to another organization/repository), which matches the Critical "unauthorized deploy" impact category, and at minimum constitutes cross-repository writes of status/commit state (also a listed Critical impact).

### Likelihood Explanation
Requires only that the attacker control (administer) one legitimate organization already onboarded into the Shipit instance — no privileged Shipit session, `ApiClient` token, or `webhook_secret` of the *target* org is needed, satisfying the "unprivileged attacker" and "not requiring a Shipit session/token/repo write access" constraints (the attacker only needs access to their *own* org's webhook secret, which is a normal, intended capability for any onboarded org admin, not a privileged credential relative to the victim org). The forged HTTP POST to `/webhooks` is otherwise indistinguishable from a legitimate GitHub delivery once the signature check passes.

### Recommendation
Bind the field used for authentication to the field used for authorization: after selecting the organization/secret for signature verification, verify that `params.dig('repository', 'full_name')` (and/or `organization.login`) actually belongs to (starts with) the same `repository_owner` used to select the secret, e.g. reject the request if `repository_name.split('/').first.casecmp(repository_owner) != 0`. Alternatively, resolve the target `Repository`/`Stack` first, derive the organization strictly from `full_name`, and use that single, consistent field for both secret selection and stack lookup.

### Proof of Concept
1. Onboard `attacker-org` in Shipit's `secrets.github` config with its own `app_id`/`installation_id`/`webhook_secret`, as an ordinary onboarded organization (no special privilege).
2. Compute `signature = HMAC-SHA1(attacker-org.webhook_secret, body)` for a crafted JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/circleci"
   }
   ```
3. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<signature>`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s config, and the signature validates successfully: [9](#0-8) 
5. `StatusHandler.call(params)` executes, looking up `Commit.where(sha: ...)` across the entire application (not scoped to `attacker-org`) and writes a forged `success` status onto `victim-org/victim-repo`'s commit, potentially satisfying `ci.require` and unblocking an unauthorized deploy on that foreign stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
