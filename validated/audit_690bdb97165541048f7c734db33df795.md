### Title
Cross-organization forged CI status via unscoped `Commit.where(sha:)` in StatusHandler allows an unauthorized merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies a `status` webhook to every `Commit` row sharing the posted `sha`, regardless of which organization/repository the webhook signature was verified against. Because Git commit objects are content-addressed, an attacker who legitimately owns (or forks) a repository containing the identical commit object as a victim's PR head can trigger a genuine, correctly-signed GitHub `status` webhook for their own org and have it applied to the victim's `Commit` row in a completely different stack, flipping `MergeRequest#all_status_checks_passed?` and preventing `reject_unless_mergeable!` from firing `ci_failing`/`ci_missing`, letting `merge!` proceed.

### Finding Description
The intended binding is: **the `Commit` rows mutated by a webhook must belong to the same stack/organization whose GitHub App secret authenticated the request** — i.e. `commit.stack.repository.owner == repository_owner (verified via HMAC)`. That binding is broken:

- `WebhooksController#verify_signature` ( [1](#0-0) ) verifies the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body ( [2](#0-1) ). This only proves the request was legitimately signed by *some* configured GitHub org/App — it says nothing about which `Commit`/`Stack` the payload should affect.
- `StatusHandler#process` then does a completely global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` ( [3](#0-2) ). There is no join/filter on `stack_id`, `stack.repository`, or the verified `repository_owner`. Contrast this with `CheckSuiteHandler`, which correctly scopes: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` ( [4](#0-3) ).
- Because Git commit SHAs are content-addressed, the exact same commit object (and therefore the exact same `sha`) can legitimately exist in multiple independent repositories/forks — e.g. a public victim repository and any fork of it that an attacker owns. An attacker who owns a fork containing the victim's PR head commit can call GitHub's real `POST /repos/{attacker}/{fork}/statuses/{sha}` API against their own fork. GitHub will deliver a **correctly signed** `status` webhook to Shipit for the attacker's own org (assuming that org has any configured GitHub App/webhook secret in Shipit, satisfying `verify_signature`).
- `MergeRequest#all_status_checks_passed?` / `#any_status_checks_failed?` ( [5](#0-4)  ) build a `StatusChecker` purely from `head.statuses_and_check_runs` — they trust whatever `Status` rows exist against `head`, with no re-validation of provenance. Since `StatusHandler` just wrote a `success` status onto the victim's `head` `Commit` row (which is shared by sha, not by stack), these methods now report success.
- `reject_unless_mergeable!` ( [6](#0-5) ) checks `any_status_checks_missing?`/`any_status_checks_failed?`, both of which are now poisoned, so the merge request is not rejected and `merge!` ( [7](#0-6) ) is allowed to call `stack.github_api.merge_pull_request`.

No existing guard closes this gap: `verify_signature` only authenticates "a request signed by org X", not "this sha belongs to org X's repo"; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` (`params do requires :sha, String; requires :state, String; ... end`, [8](#0-7) ) validate shape only, not ownership; there is no `stacks`/`repository` scoping applied anywhere in the handler.

### Impact Explanation
A single forged/legitimate-but-cross-tenant `status` webhook write can flip CI-gating state (`Status` rows) on a victim `Commit`, causing `MergeRequest#reject_unless_mergeable!` to skip `ci_failing`/`ci_missing` rejection and allowing `merge!` to proceed and call GitHub's merge API on the victim's stack/repository — an unauthorized merge triggered by a party outside that repository's org. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." The attack is repeatable against any repository whose commits are also reachable by a fork or duplicate the attacker controls, and against any stack tracking that commit, since the write is a raw SQL `WHERE sha = ?` with no tenant scoping.

### Likelihood Explanation
Preconditions: (1) the target commit's sha must exist verbatim in a repository/fork the attacker legitimately controls (trivial for any public repository or any PR whose head the attacker can fork/mirror before or after CI runs); (2) the attacker's own org/repo must be registered in Shipit with a configured GitHub App/webhook secret (true for any tenant already onboarded to a shared Shipit instance, which is a normal, unprivileged configuration in multi-tenant deployments); (3) the attacker never needs Shipit's secrets — GitHub itself computes and sends the valid signature for the attacker's own org when the attacker calls the real GitHub statuses API on their own fork. Cost is low: fork the repo, push the identical commit, call the standard GitHub Statuses API. This is realistic in any Shipit deployment that hosts multiple independent orgs/tenants behind one instance (the documented multi-org `github_organizations`/`github_app_config` support in `lib/shipit.rb`, [9](#0-8) ).

### Recommendation
Scope `StatusHandler#process` (and any other handler using a bare `Commit.where(sha:)`) to only the stacks/commits belonging to the verified `repository_owner`/`repository.full_name`, mirroring `CheckSuiteHandler`'s pattern of scoping through `stacks.where(...)`. Concretely, resolve the `Repository` from the verified payload's `repository.full_name`, then update statuses only for `Commit` rows under that repository's stacks: e.g. `Repository.find_by(owner:, name:)&.stacks&.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, rejecting/no-op'ing when the repository in the payload doesn't match any stack.

```ruby
# test/models/webhooks/status_handler_cross_org_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossOrgTest < ActiveSupport::TestCase
        test "a status event does not affect commits belonging to another stack/org" do
          victim_stack = shipit_stacks(:shipit) # owned by org "shopify" per fixtures
          victim_commit = victim_stack.commits.create!(sha: 'a' * 40, author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)
          merge_request = victim_stack.merge_requests.create!(number: 999, head: victim_commit, merge_status: 'pending')

          # Binding under test: commit rows mutated by a status webhook must belong to the
          # SAME repository/org that the webhook signature authenticates.
          # LHS: victim_commit.stack.repository.owner  (the true owner of the mutated Commit)
          # RHS: repository_owner used to verify the signature ("attacker-org")
          # These must be equal for the write to be legitimate.

          attacker_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => 'attacker-org/attacker-fork', 'owner' => { 'login' => 'attacker-org' } }
          }

          assert_not_equal victim_commit.stack.repository.owner, attacker_payload['repository']['owner']['login']

          assert_no_difference -> { victim_commit.statuses.count } do
            StatusHandler.call(attacker_payload) # simulate a correctly-signed webhook for "attacker-org"
          end

          refute merge_request.all_status_checks_passed?, "victim MergeRequest must not see attacker-signed status as passing"
        end
      end
    end
  end
end
```
Currently this test fails: `StatusHandler.call` writes a `success` `Status` onto `victim_commit` regardless of `attacker_payload['repository']`, and `all_status_checks_passed?` returns `true`, demonstrating the cross-tenant status forgery.
