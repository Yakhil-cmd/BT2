### Title
Cross-organization webhook forgery via signature verification keyed on `repository.owner.login` but authorization/state writes keyed on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to verify the HMAC signature using an organization value derived from the payload itself (`repository.owner.login`, falling back to `organization.login`), then hands the *entire* raw JSON payload to the registered event handlers. Those handlers (e.g. `StatusHandler`, `PushHandler` via `Handler#stacks`) independently resolve the target `Repository`/`Stack` using `repository.full_name` from the same attacker-controlled payload, without ever checking that this repository actually belongs to the organization whose secret validated the signature.

### Finding Description
In a multi-organization Shipit deployment, each organization has its own `webhook_secret` configured under `secrets.github[<organization>]` and looked up via `Shipit.github_app_config(organization)`/`Shipit.github(organization:)`. [1](#0-0) 

`WebhooksController#verify_signature` picks the signing organization purely from the payload: [2](#0-1) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

Once verified, `create` dispatches the *raw, unmodified* payload to handlers: [4](#0-3) 

Handlers resolve the affected `Repository`/`Stack` from a **separate** field of the same payload — `repository.full_name` — with no cross-check against the organization used for signature verification: [5](#0-4) 

`StatusHandler` then writes a `Status` for any commit matching `params.sha`, entirely from attacker-supplied payload fields (`state`, `description`, `target_url`, `context`), independent of which repository that commit belongs to: [6](#0-5) 

**The broken binding:** `organization authenticated (repository.owner.login used to pick webhook_secret) == repository written (repository.full_name used to resolve Repository/Stack)`. These two payload fields are never checked to agree.

An org admin who legitimately owns/administers "OrgA" in this shared Shipit instance (and therefore knows OrgA's `webhook_secret`, e.g. by configuring their own webhook delivery to the shared Shipit endpoint) can:
1. Craft a payload with `repository.owner.login = "OrgA"` (so it authenticates against OrgA's secret) and `X-Github-Event: status`.
2. Set `repository.full_name = "OrgB/some-repo"` and `sha` to a real commit SHA belonging to `OrgB/some-repo`'s stack (SHAs are public via GitHub UI/API for any repo they can read).
3. Sign the payload with OrgA's `webhook_secret`.

`verify_signature` succeeds (OrgA's secret validates a payload OrgA legitimately controls), but `StatusHandler` writes a forged CI status onto `OrgB`'s commit, because `Commit.where(sha: params.sha)` is scoped only by SHA/handler logic, not by the authenticated organization. Forged "success" statuses can satisfy deploy-gating checks (`shipit.yml` required statuses) for OrgB's stack, enabling an unauthorized deploy on a repository the attacker does not control.

### Impact Explanation
This crosses an organizational trust boundary: an actor with legitimate control only over Organization A's webhook secret can inject state (fabricated commit statuses) that influences Organization B's deploy pipeline/gating, without ever holding OrgB's `webhook_secret`, an `ApiClient` token, or repository write access to OrgB. Forged passing statuses can unblock `Stack` deploy gating checks, leading to an unauthorized deploy — matching the "Critical: unauthorized deploy" impact bar. `PushHandler`/`GithubSyncJob` are comparatively lower risk since they re-fetch commits from the real GitHub API rather than trusting payload content directly, but `StatusHandler` writes fully payload-derived data with no such secondary verification.

### Likelihood Explanation
Requires the attacker to already administer at least one organization onboarded to the same multi-tenant Shipit instance (so they legitimately know that organization's `webhook_secret`), and knowledge of a target commit SHA in the victim organization's tracked branch (obtainable from GitHub's public commit history/API for any repo they can view). No access to the victim org's secrets, GitHub App credentials, or Shipit `ApiClient` tokens is needed. This is realistic in any Shipit-as-a-service deployment serving multiple independent GitHub organizations.

### Recommendation
Verify that the organization used to select the `webhook_secret` for signature verification is the same organization implied by every payload field the handlers act on (in particular `repository.full_name`'s owner segment). Concretely, in `WebhooksController#verify_signature` (or in `Handler#stacks`), assert `repository_owner == payload.dig('repository', 'full_name')&.split('/')&.first` (case-insensitively) before processing, and reject (422) on mismatch.

### Proof of Concept
1. Deployment configures two orgs, `orga` and `orgb`, each with distinct `webhook_secret`s under `Rails.application.credentials.github`.
2. Attacker controls org `orga` and knows `orga`'s webhook secret (they legitimately set up the webhook pointing at the shared Shipit instance).
3. Attacker finds a public commit SHA `deadbeef` on `orgb/victim-repo`, which is tracked by a Shipit `Stack` and currently blocked from deploy pending a required "ci/tests" status.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
}
```
signed with `X-Hub-Signature: sha1=<hmac using orga's webhook_secret>`.
5. `verify_signature` resolves `Shipit.github(organization: "orga")` and validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef")` — matches the commit belonging to `orgb/victim-repo`'s stack — and creates a forged `success` status for `ci/tests`, satisfying deploy gating on OrgB's stack despite the attacker never possessing OrgB's credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
