Based on the investigation, I've found the clearest analog to the xrdp authentication-bypass bug class in ocore's device-messaging / multisig-signing subsystem.

### Title
Missing cosigner-authentication check in `sign` request handler allows any paired device to trigger blind signing of arbitrary units for a local single-owner address - (File: wallet.js)

### Summary
The xrdp CVE stems from a code path (Xvnc-over-unix-socket) that omits an authentication check that is present and enforced on other code paths (TCP, xorgxrdp), letting one authenticated local principal act within another's session. `wallet.js`'s `"sign"` message handler has an analogous, explicitly-acknowledged gap: when a peer device asks the local wallet to sign a unit for a **local** address, the code that would verify the requesting device is actually a legitimate cosigner of that address is present in the source but deliberately commented out, so it is never executed.

### Finding Description
In the `handleMessageFromHub` dispatcher, the `"sign"` case is meant to serve two legitimate purposes: multisig (same address hosted on several devices) and multilateral signing (different addresses signing the same message, e.g. dumb contracts) [1](#0-0) . After basic structural validation of the unsigned unit, `findAddress` resolves whether the address is `ifLocal` (owned solely by this device) or a shared/remote address [2](#0-1) .

For the `ifLocal` branch, the code that would confirm the sender (`from_address`, derived from the message's device pubkey) is actually a listed cosigner of the address is written but disabled: [3](#0-2) 
The comment states plainly that this check "would make multilateral signing impossible," so it was removed rather than scoped only to genuinely shared/multi-device addresses. As a result, **any paired device** (not just an actual cosigner or contract counterparty) can send a `"sign"` request naming one of the recipient's fully self-owned, single-key addresses together with an attacker-crafted unsigned unit, and the wallet will unconditionally call `callbacks.ifOk()` and forward the request into the `signing_request` event for potential signing [4](#0-3) . This is functionally the same class of defect as the xrdp bug: a check that exists and works on one path (the properly-gated shared/remote address flow via `ifRemote`, which does verify `other_device_addresses.includes(from_address)` [5](#0-4) ) is missing on a parallel path (`ifLocal`) that should logically require the same authorization, breaking the intended isolation between "my private single-sig address" and "a message from an arbitrary paired correspondent."

### Impact Explanation
Any device paired with the victim's wallet (a normal, low-privilege relationship — pairing is intentionally easy and is even offered via public/wildcard pairing secrets, see `handlePairingMessage` in `device.js` [6](#0-5) ) can submit signing requests for the victim's own private addresses. Because the `ifLocal` branch performs no cosigner/ownership authorization of the request's origin, an attacker-controlled peer can attempt to get the wallet layer to sign malicious payment units that redirect funds, subject only to whatever confirmation logic the downstream `signing_request` consumer implements. Any headless/automated consumer of this event that trusts a same-wallet local address to imply a legitimate multisig/contract session (which is exactly the scenario the disabled check was meant to prevent) is exposed to unauthorized fund-signing requests, i.e., potential unauthorized spending analogous to the "unauthorized session access" impact of the xrdp flaw.

### Likelihood Explanation
Reachable trivially by any already-paired device address — no special privilege beyond being a correspondent is required, and the check that would have prevented it exists in the codebase but is intentionally disabled, indicating the developers were aware of and accepted this specific gap for local addresses. `isValidAddress`/`isNonemptyString` checks on `body.address`/`body.signing_path` do not restrict who may issue the request, only its shape.

### Recommendation
Re-enable an authorization check for the `ifLocal` branch of the `"sign"` handler that verifies `from_address` is actually a cosigner of `body.address` (e.g., via `extended_pubkeys`/`wallet_signing_paths` for BIP44 wallets) for genuinely single-device wallets, while preserving a distinct, explicitly-scoped exception path for multilateral/contract signing that already validates counterparties through other means (e.g., `arbiter_contract`/`prosaic_contract` flows). At minimum, ensure any downstream consumer of the `signing_request` event cannot silently auto-approve requests originating from devices that are not verified cosigners.

### Proof of Concept
1. Pair a malicious device B with victim wallet A (trivial, using a normal or wildcard pairing secret).
2. From device B, send a `device` message to A with `subject: "sign"`, `body: {address: <A's own single-key address>, signing_path: "r", unsigned_unit: <attacker-crafted payment unit spending A's funds to attacker>}`.
3. `handleMessageFromHub` dispatches to the `"sign"` case; `findAddress` resolves `ifLocal` since the address belongs to A.
4. Because the cosigner check is commented out, `callbacks.ifOk()` is called and `eventBus.emit("signing_request", ...)` fires unconditionally, exposing the malicious unit to whatever signs/approves signing requests on A's side, without any verification that B had any right to request a signature for A's private address.
