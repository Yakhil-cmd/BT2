Based on my analysis, I found a concrete analog in ocore's AA payment mechanism, where `mergeMessagesAndOutputs` combines multiple separate outputs into a single payment message per asset, and restricted-asset validation requires **all** output addresses in that single message to be attested — a single non-attestable/blacklisted recipient blocks payment to every other recipient in the same message, causing the AA response to bounce and the funds to remain locked in the AA.

### Title
Single non-attested (or otherwise restricted) recipient in a merged multi-output AA payment causes the entire payment message to fail, locking all outputs to other legitimate recipients - (File: aa_composer.js, validation.js)

### Summary
When an Autonomous Agent (AA) sends payments in a restricted (`spender_attested`) asset to multiple addresses in response to a trigger, `mergeMessagesAndOutputs` in `aa_composer.js` merges all outputs paying the same asset into a single payment message. `validatePaymentInputsAndOutputs` in `validation.js` then requires that *all* output addresses of that message be attested before the unit is considered valid. If even one recipient among many is not (or can no longer be) attested, the whole message — and therefore the whole AA response unit — fails validation, causing the AA trigger to bounce and none of the intended recipients (including the otherwise-valid ones) to receive their funds.

### Finding Description
`aa_composer.js`'s `mergeMessagesAndOutputs` explicitly merges payment messages/outputs paying the same asset into one message with multiple outputs: [1](#0-0) 

This merged message is then sent as-is via `sendUnit`, invoked when `mci >= constants.pemCurvesFixMci`: [2](#0-1) 

For a `spender_attested` asset, `validatePaymentInputsAndOutputs` checks all output addresses together and fails the entire payment if any single one is not attested: [3](#0-2) 

The same all-or-nothing pattern applies to `transfer_condition`/`issue_condition`, which is evaluated once for the whole message rather than per-output: [4](#0-3) 

Because validation failure of this generated unit propagates back into `sendUnit`'s error handling, which calls `bounce`, and bouncing reverts all state changes and consumed balances for that trigger: [5](#0-4) [6](#0-5) 

Thus a single address that loses its attestation status (e.g., its attestor revokes attestation, or the attestor's own definition/address changes), or otherwise fails the shared `transfer_condition`, is enough to block the payment message that also includes many other legitimate recipients, since `spender_attested`/`transfer_condition` restrictions are asset-wide policies enforced atomically on the whole set of outputs in a message, exactly as in the reported vault case where one blacklisted pool token blocks withdrawal of all tokens.

### Impact Explanation
An AA that batches payouts to many addresses in a `spender_attested` (or `transfer_condition`-restricted) asset can have its entire distribution bounce because of a single problematic recipient. This causes AA fund freezing for all intended recipients in that trigger response, not just the affected address, since the AA's payout logic (as commonly written, e.g., `messages: [...]` loops generating multiple outputs) has no per-output failure isolation — the failure is all-or-nothing at the message level. Repeated triggering with the same faulty recipient present in the output set will repeatedly bounce, permanently locking funds intended for the healthy addresses unless the AA's oscript logic is specifically designed to detect and exclude the failing address (which base ocore does not provide automatically).

### Likelihood Explanation
This requires an AA definition that (a) sends the same restricted/`spender_attested` asset to multiple addresses derived from state (e.g., a payout/distribution/vault-like AA), and (b) at least one target address becomes unattested or otherwise fails the `transfer_condition` between when the AA computes the payout and when the unit gets validated. Given that attestation lists are attestor-controlled and can be revoked or become out of date, and that AA authors commonly aggregate multiple payouts into loops that get merged by `mergeMessagesAndOutputs`, this is a realistic, moderate-likelihood scenario for any AA that manages a restricted/regulated asset.

### Recommendation
Do not treat multi-recipient restricted-asset payments as strictly atomic at the message level from the AA's perspective. Options: (1) in AA/oscript payout logic, avoid merging payments to many independently-controlled addresses into a single message for `spender_attested`/condition-restricted assets, splitting per-recipient sends into separate response units or performing pre-checks via `in data feed`/`attested` conditions before adding an output; (2) provide an oscript-accessible way to check attestation status of a candidate output address (e.g., an `attested` boolean function usable in AA formulas, mirroring `evaluate`'s `'attested'` case) so the AA can skip failing recipients instead of failing the whole batch; (3) document clearly for AA authors that restricted-asset payments must isolate address-dependent failures.

### Proof of Concept
1. Define asset A with `spender_attested: true` and an attestor address `X`.
2. Deploy an AA that, upon trigger, sends asset A to two addresses, `B1` and `B2`, both currently attested by `X`, using two `payment` messages in the AA `messages` template (both get merged by `mergeMessagesAndOutputs` into one message with two outputs since they share the same asset).
3. Before the AA trigger executes (or in a subsequent trigger cycle), have attestor `X` stop attesting `B2` (or never (re)attest it, e.g., due to revocation or expiry logic modeled via a data feed check outside consensus).
4. Fire the trigger. `sendUnit` builds the merged payment message with outputs to `B1` and `B2`; `validatePaymentInputsAndOutputs`'s `spender_attested` check in `validation.js` (lines 2630-2641) finds `arrAttestedOutputAddresses.length !== arrOutputAddresses.length` and fails validation.
5. `validateAndSaveUnit` returns an error to `sendUnit`, which calls `bounce(err)`; the AA response bounces, `B1` never receives its otherwise fully valid payment, and the AA's balance for asset A remains locked pending manual AA logic changes or attestor cooperation.

	// merges payment messages paying in the same asset into a single message,
	// and merges outputs paying in the same asset to the same address into a single output.
	// send-all outputs (amount === undefined) are left as they are and never merged with anything.
	// non-payment messages are left intact.
	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
