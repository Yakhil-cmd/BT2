### Title
Staking DB Poisoned Before `InsertReceiptChain` Succeeds in Fast-Sync — (`datasync/downloader/downloader.go`)

### Summary

In `commitFastSyncData` and `commitPivotBlock`, `PutStakingInfoToDB` is called unconditionally for every `fetchResult` with staking info **before** `InsertReceiptChain` is called. If `InsertReceiptChain` fails for any reason, the staking DB already contains the peer-supplied entry with no rollback. A malicious fast-sync peer can exploit this ordering to inject arbitrary staking info (fake `RewardAddrs`, `StakingAmounts`, `KEFAddr`/`KIFAddr`) into the persistent staking DB.

### Finding Description

In `commitFastSyncData`:

```go
// datasync/downloader/downloader.go lines 1878–1889
for i, result := range results {
    blocks[i] = types.NewBlockWithHeader(result.Header).WithBody(result.Transactions)
    receipts[i] = result.Receipts
    if result.StakingInfo != nil {
        d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum,
            staking.ToStakingInfo(result.StakingInfo))  // ← written first, no rollback
    }
}
if index, err := d.blockchain.InsertReceiptChain(blocks, receipts); err != nil {
    return fmt.Errorf("%w: %v", errInvalidChain, err)  // ← staking DB already dirty
}
``` [1](#0-0) 

The same pattern exists in `commitPivotBlock`: [2](#0-1) 

`PutStakingInfoToDB` writes directly to the persistent key-value store with no transaction or rollback: [3](#0-2) 

`P2PStakingInfo` carries fully attacker-controlled fields — `CouncilRewardAddrs`, `CouncilStakingAmounts`, `KEFAddr`, `KIFAddr` — and `ToStakingInfo` copies them verbatim with no cryptographic verification against the block state: [4](#0-3) 

`GetStakingInfo` (used during block execution) reads the DB entry first and returns it without re-validating against state, so a poisoned entry is consumed directly: [5](#0-4) 

The DB is only consulted for pre-Kaia-hardfork blocks, but that is exactly the range fast-sync covers for historical chain data.

### Impact Explanation

`StakingInfo` is the primary input to validator set selection and reward distribution. [6](#0-5)  If the DB contains fake `RewardAddrs` or `StakingAmounts` for a staking-interval source block, the node computes different reward distributions when executing subsequent blocks, producing a state root that diverges from the canonical chain. The node then rejects all valid canonical blocks — a persistent consensus divergence and loss of chain functionality.

### Likelihood Explanation

The attack requires the victim to be in fast-sync mode and the attacker to be a connected P2P peer. The attacker must:
1. Provide fake staking info for a staking-interval block N.
2. Cause `InsertReceiptChain` to fail (e.g., supply receipts with a mismatched count vs. transactions, which fails `SetReceiptsData`). [7](#0-6) 

**Key mitigating factor**: If the node retries fast-sync with a correct peer that also provides staking info for block N, `PutStakingInfoToDB` is called again with correct data, overwriting the fake entry. The attack is most reliable when the attacker is the sole fast-sync peer or the node abandons fast-sync and falls back to full-sync (where the DB entry is never overwritten because `GetStakingInfo` returns the cached DB value without re-reading state). [5](#0-4) 

Likelihood is **low-to-moderate**: requires a targeted network position but no cryptographic break or privileged key.

### Recommendation

Move `PutStakingInfoToDB` to after `InsertReceiptChain` succeeds in both `commitFastSyncData` and `commitPivotBlock`. Alternatively, collect all staking info writes in a pending list and flush them only on success:

```go
// After InsertReceiptChain succeeds:
for _, result := range results {
    if result.StakingInfo != nil {
        d.stakingModule.PutStakingInfoToDB(...)
    }
}
```

Additionally, consider verifying the `BlockNum` in the received `P2PStakingInfo` matches the corresponding `fetchResult.Header.Number` before writing.

2. Connect a victim node in fast-sync mode to this peer.
3. `commitFastSyncData` calls `PutStakingInfoToDB` with the fake entry, then `InsertReceiptChain` fails on the bad receipts.
4. Inspect the staking DB: the fake entry for block N is present.
5. Disconnect the malicious peer; let the victim complete

### Title
Staking DB Poisoned Before Receipt Chain Commit Succeeds in `commitFastSyncData` / `commitPivotBlock` — (`datasync/downloader/downloader.go`)

### Summary
In both `commitFastSyncData` and `commitPivotBlock`, `PutStakingInfoToDB` is called unconditionally inside the result-processing loop **before** `InsertReceiptChain` is called. If `InsertReceiptChain` fails for any reason, the staking DB already contains the peer-supplied entry with no rollback path. A malicious fast-sync peer can exploit this ordering to inject arbitrary staking info (fake `RewardAddrs`, `KEFAddr`, `KIFAddr`, `StakingAmounts`) into the persistent staking DB, which is then used verbatim for pre-Kaia reward distribution on the victim node, causing consensus divergence.

### Finding Description

In `commitFastSyncData`:

```go
for i, result := range results {
    blocks[i] = types.NewBlockWithHeader(result.Header).WithBody(result.Transactions)
    receipts[i] = result.Receipts
    if result.StakingInfo != nil {
        d.stakingModule.PutStakingInfoToDB(...)  // ← written first, no rollback
    }
}
if index, err := d.blockchain.InsertReceiptChain(blocks, receipts); err != nil {
    return fmt.Errorf("%w: %v", errInvalidChain, err)  // ← staking DB already dirty
}
``` [1](#0-0) 

The same pattern exists in `commitPivotBlock`: [2](#0-1) 

`PutStakingInfoToDB` writes directly and durably to the chain key-value store with no transactional guard: [3](#0-2) 

`GetStakingInfo` (used during block execution) reads the DB entry first and returns it without re-validating against canonical state: [5](#0-4) 

The staking info controls `RewardAddrs`, `KEFAddr`, `KIFAddr`, and `StakingAmounts` — all inputs to reward distribution: [8](#0-7) 

### Impact Explanation

A malicious fast-sync peer supplies a `P2PStakingInfo` with attacker-controlled `CouncilRewardAddrs` / `KEFAddr` / `KIFAddr` for a staking-interval block N, paired with receipts that fail `SetReceiptsData` (e.g., receipt count mismatches transaction count). `PutStakingInfoToDB` writes the fake entry; `InsertReceiptChain` then fails and returns `errInvalidChain`. The fake entry persists. When the victim node later processes blocks in the epoch `[N+StakingInterval, N+2*StakingInterval)`, `GetStakingInfo` returns the poisoned DB entry, computes different reward distributions, produces a different state root, and rejects valid canonical blocks — **consensus divergence on an honest node**.

### Likelihood Explanation

**Mitigating factor**: If the node retries fast sync with a correct peer that also provides staking info for block N, `PutStakingInfoToDB` is called again with correct data, overwriting the fake entry. This self-healing limits exploitability to scenarios where the attacker is the sole fast-sync peer or the node falls back to full sync after the failed fast sync. The staking DB path is also only active for pre-Kaia hardfork blocks (`!isKaia` guard in `GetStakingInfo`).

**Attack-enabling factor**: Any permissionless P2P node can act as a fast-sync peer. The attacker only needs to serve one batch with fake staking info and deliberately invalid receipts. No cryptographic break or key compromise is required.

### Recommendation

Move `PutStakingInfoToDB` to **after** `InsertReceiptChain` succeeds in both `commitFastSyncData` and `commitPivotBlock`. The staking write should be conditional on successful block commitment:

```go
if index, err := d.blockchain.InsertReceiptChain(blocks, receipts); err != nil {
    return fmt.Errorf("%w: %v", errInvalidChain, err)
}
// Only write staking info after successful commit
for _, result := range results {
    if result.StakingInfo != nil {
        d.stakingModule.PutStakingInfoToDB(...)
    }
}
```

### Proof of Concept

1. Stand up a malicious fast-sync peer that serves valid headers for canonical block N (a staking-interval block) but attaches a `P2PStakingInfo` with attacker-controlled `CouncilRewardAddrs` and provides a receipt list with zero entries for a block that has transactions.
2. Connect a victim node in fast-sync mode to this peer.
3. `commitFastSyncData` calls `PutStakingInfoToDB` with the fake staking info, then `InsertReceiptChain` fails on `SetReceiptsData` (receipt/tx count mismatch).
4. Assert: `stakingModule.GetStakingInfoFromDB(N)` returns the attacker's `CouncilRewardAddrs`.
5. Disconnect the malicious peer; connect a correct peer that does **not** re-serve staking info for block N (or switch to full sync).
6. Assert: the victim node's `GetStakingInfo` for any block in `[N+StakingInterval, N+2*StakingInterval)` returns the poisoned entry, and the node diverges from the canonical chain when processing those blocks.
