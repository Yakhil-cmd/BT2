This confirms the error-file logic itself (`writeContent`, `ExportError`, `DeleteErrorFile`) is safe — it writes to a temp file via `os.CreateTemp` then atomically renames, and never follows a symlink at the target name (`os.Rename` replaces the destination path directly rather than opening/following it). The real issue described is not in `logging.go` but in the readiness latch in `main.go`.

### Title
Readiness endpoint `/` latches permanently true after first successful sync, masking indefinite staleness from subsequent sync failures - (File: main.go)

### Summary
`setRepoReady()` sets a package-level boolean `repoReady` to `true` and it is never reset to `false` anywhere in the codebase. Once a single sync succeeds, the `/` liveness/readiness HTTP handler will return `200 OK` forever, even if every subsequent sync attempt fails indefinitely (e.g., due to a deleted ref, stalled remote, or wedged repo), as long as `--max-failures` is configured to tolerate or ignore failures (e.g., set to a negative value for infinite retries, a documented, non-default but supported flag).

### Finding Description
The readiness state is a simple one-way latch: [1](#0-0) 

```go
var readyLock sync.Mutex
var repoReady = false

func getRepoReady() bool { ... return repoReady }
func setRepoReady() { ... repoReady = true }
```

There is no corresponding "unset" function, and it is called only inside the success branch of the sync loop and inside `SyncRepo` after a successful publish: [2](#0-1) 

The HTTP handler for `/` only checks this latch: [3](#0-2) 

```go
mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
    if !getRepoReady() {
        http.Error(w, "repo is not ready", http.StatusServiceUnavailable)
    }
    // Otherwise success
})
```

In the main sync loop, on failure the code increments `failCount`, and only exits the process if `failCount >= maxFails` (when `maxFails >= 0`): [4](#0-3) 

If `--max-failures` is set to a negative value (a documented, supported setting — "Setting this to a negative value will retry forever"), the process will retry forever without ever calling `os.Exit(1)`, while `repoReady` remains `true` from the earlier successful sync and the published symlink tree stops advancing. The `/` endpoint therefore continues to return `200 OK` indefinitely, and the served data (via `--link`) grows stale without bound, while the readiness probe gives no indication of this. [5](#0-4) 

An attacker controlling only the repo content/refs (e.g., deleting a branch, force-pushing a broken ref, or causing the remote to stall/hang within `--sync-timeout`) can trigger `SyncRepo` to return an error on every subsequent attempt after the first successful sync, thereby freezing `repoReady=true` forever while data staleness accumulates.

`--http-pprof` itself is irrelevant to the vulnerability — it does not affect `repoReady`, `/`, or the sync loop; enabling it does not open any additional path to this staleness. The bug is present under the default `/` handler regardless of `--http-pprof`.

The `pkg/logging/logging.go` `Error`/`writeContent`/`ExportError`/`DeleteErrorFile` functions are unrelated to the readiness latch — they only affect the optional `--error-file`, and their write path is a safe temp-file + atomic rename pattern that does not itself introduce a readiness or freshness bypass.

### Impact Explanation
Consumers and orchestrators (e.g., Kubernetes readiness/liveness probes pointed at `--http-bind`) will continue to see `200 OK` from `/` even though the published tree under `--link` has stopped updating, potentially for an unbounded period. This is a silent-staleness class issue: workloads relying on the sidecar's readiness signal to gate traffic or restarts will keep operating on outdated data, believing it to be current, with no automated remediation (e.g., pod restart) triggered.

### Likelihood Explanation
This requires the operator to have set `--max-failures` (or `--init-max-failures`) to a negative value to tolerate infinite retries — a documented, supported, but non-default configuration. Given that setting, the trigger is trivial and fully within the attacker's described capability (control of repo refs/content, or the ability to stall the remote endpoint used for fetch): delete the ref being tracked, force it into an unfetchable state, or make the remote hang until `--sync-timeout`. Every such failure after the first successful sync reproduces the stale-but-ready condition, and it persists as long as the failure condition persists.

### Recommendation
Track the age or hash of the last successfully published state and reflect it in the `/` handler, e.g., have `setRepoReady()` also record a timestamp/hash, and fail the readiness check if failures have exceeded some threshold or if the last successful sync is older than some multiple of `--period`. Alternatively, expose a distinct "freshness" flag that is cleared when `SyncRepo` returns an error and is only set again upon the next successful sync, so that `/` accurately reflects "the currently published tree corresponds to a recent successful sync" rather than "a sync succeeded at least once."

### Proof of Concept
Unit-level repro sketch (Go, in `main_test.go` or an integration test):
1. Start git-sync against a real (local) bare repo with `--max-failures=-1`, `--period` small, `--http-bind=127.0.0.1:0`.
2. Let the first sync succeed; confirm `GET /` returns 200 and record the published hash/mtime under `--link`.
3. Delete the tracked ref/branch from the origin (or block the remote transport) so every subsequent `git.SyncRepo` call fails.
4. Wait several sync periods; assert:
   - `GET /` still returns 200 (demonstrating the stale-latch bug), and
   - the target of `--link` and its hash have not changed while wall-clock time has advanced well beyond `--period` × N.
5. This demonstrates readiness reflects "synced once", not "data is fresh", confirming the finding.
