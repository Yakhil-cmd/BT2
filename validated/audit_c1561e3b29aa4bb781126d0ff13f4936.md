### Title
CCMenu API endpoint bypasses `ApiClient#stack_id` scoping, letting a stack-scoped token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to load the target `Stack` directly via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` helper used by every other API controller. Because `require_permission` only checks the *permission name* (`read:stack`) and never the *record*, a token that was minted to be scoped to one specific stack can be used to read the CI status (`lastBuildStatus`, `lastBuildLabel`, activity, etc.) of any other stack in the installation simply by changing the `stack_id` URL parameter.

### Finding Description
`ApiClient` supports scoping a token to a single stack via its `stack_id` column: [1](#0-0) . `Api::BaseController` enforces this scope centrally through the `stacks`/`stack` helpers:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`ApiClient#check_permissions!` only validates that the required permission string (e.g. `read:stack`) is present in the client's `permissions` array; it has no knowledge of which stack is being accessed: [3](#0-2) . The stack-level authorization boundary is therefore entirely delegated to the `stacks`/`stack` helper — any controller that bypasses that helper breaks the "token authorizes stack X" ⇔ "code touches stack X" binding.

`CCMenuController` does exactly that:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [4](#0-3) 

`show` then calls `stack.deploys_and_rollbacks.last` and renders it: [5](#0-4) . Since `stack` resolves against the *global* `Stack` table (no `stacks` scoping applied), a stack-scoped token is never restricted to the stack it was issued for.

This is a direct analog of the reported smart-contract bug class: the report's `updateInterestRates` used a value (`poolData.variableBorrowData.interestRate`) that was not the one actually authorized/validated for the current operation (the freshly computed `variableBorrowInterestRate`), breaking the invariant that the rate *used* must equal the rate *just verified*. Here, the invariant that should hold is "stack a token authorizes == stack the controller touches", and `CCMenuController` breaks it by substituting the globally-resolved `Stack` for the token-scoped one.

The primary legitimate consumer of these scoped tokens is `CCMenuUrlController`, which mints an `ApiClient` scoped to a single stack via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `permissions: %w[read:stack]` (no `stack:` scoping is shown being applied there either, but the *general* mechanism supported by the engine for restricting a client to one stack is `ApiClient#stack_id`, exercised by the `here_come_the_walrus` fixture: [6](#0-5) ). Any `ApiClient` record configured with a `stack_id` (the engine's documented/tested mechanism for restricting a client to one stack, verified in `stacks_controller_test.rb`'s "an api client scoped to a stack will only see that one stack" test [7](#0-6) ) is not actually restricted when hitting `Api::CCMenuController#show`.

### Impact Explanation
An attacker in possession of a valid stack-scoped `read:stack` token (e.g., a leaked CCMenu URL/token meant to expose only one stack's build badge to a CI dashboard) can enumerate `stack_id` values and read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) of every stack in the Shipit installation, including private/internal repositories the token holder was never meant to see. This matches the "High — unauthorized read of stack state ... via a credential whose authorization boundary does not match the resource actually accessed" class: the token *authorizes* one stack, but the code *touches* any stack.

### Likelihood Explanation
Exploitation requires only a valid, currently-permitted API token (no privileged account, no webhook secret, no GitHub App key) — the same class of unprivileged-but-authenticated actor targeted by the rules. CCMenu tokens are specifically designed to be embedded in third-party CI dashboard tools/URLs (lower operational secrecy than a full API client), increasing realistic exposure. The bypass requires no additional gadget beyond changing one query/route parameter.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped helper, consistent with every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private `Stack.from_param!` override so the class inherits `Api::BaseController#stack`, restoring the `stack_id?` scoping check against `current_api_client`.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (e.g., analogous to the `here_come_the_walrus` fixture: [6](#0-5) ).
2. Using that token's `authentication_token`, issue: `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<TOKEN>` where `STACK_B_ID` is a *different* stack than the one the token is scoped to.
3. Observe that `Api::CCMenuController#show` returns HTTP 200 with `<Project name="..." lastBuildStatus="..." .../>` for Stack B, even though the token's `stack_id` is Stack A — contrast with `Api::StacksController#index`, which correctly restricts results to the client's scoped stack per the existing test `"an api client scoped to a stack will only see that one stack"` [7](#0-6) .
