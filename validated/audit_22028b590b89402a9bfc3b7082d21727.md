### Title
CR/LF injection in `verifyRun` allows attacker-controlled release tag and Sigstore subject names to spoof gh's trusted "verified" output - ([File: pkg/cmd/release/verify/verify.go])

### Summary
`verifyRun` and its helper `printVerifiedSubjects` print attacker-influenced strings (`tagName`, and each attestation `Subject.Name`/digest from the Sigstore DSSE payload) directly via `fmt.Fprintf`/`table.AddField` without any control-character sanitization. Because these values can contain raw `\r`/`\n` bytes, an attacker who controls a repository's release tag name or the subject names embedded in a release attestation can redraw or reorder lines in the "Release verified!" output.

### Finding Description
In `pkg/cmd/release/verify/verify.go:184-186`, `tagName` (from `opts.TagName` or, when empty, `release.TagName` fetched via `shared.FetchLatestRelease` from the GitHub API) is written straight into the trusted success banner: [1](#0-0) 
No `Untrusted`/`asciisanitizer` wrapping is applied here, unlike other parts of the codebase that explicitly wrap remote-origin strings (e.g. `iostreams.NewUntrusted`, `asciisanitizer.Sanitizer`) before printing them to a terminal, as seen in `pkg/iostreams/untrusted.go`, `pkg/cmd/gist/view/view.go`, `pkg/cmd/skills/list/list.go`, and `pkg/cmd/repo/view/http.go`. [2](#0-1) [3](#0-2) 

Similarly, `printVerifiedSubjects` (`verify.go:196-238`) decodes the attestation's DSSE payload (attacker-supplied Sigstore bundle content for a release the attacker publishes) and writes each subject's `Name` and digest directly into the table: [4](#0-3) 
Neither the tag name nor the subject name/digest strings pass through any sanitizer before hitting `io.Out`/the table printer. `internal/tableprinter` (`internal/tableprinter/table_printer.go`) performs padding/truncation but does not strip control characters.

Crucially, even where this codebase *does* sanitize untrusted content elsewhere, it only targets ANSI escape sequences (`0x1B`) - the shared `asciisanitizer.Sanitizer` and the fallback `stripControl` explicitly preserve `\t`, `\n`, and `\r`: [5](#0-4) 
So even routing this data through the existing `Untrusted`/`asciisanitizer` machinery would **not** close the specific gap the question describes (bare `\r`/`\n` line redraw, without needing full ANSI escapes) - the codebase's sanitization model treats `\r`/`\n` as legitimate formatting, not as spoofing vectors.

This means: (1) `verify.go` doesn't sanitize the attacker-controlled `tagName`/subject fields at all, and (2) even if it reused the shared sanitizer, that sanitizer wouldn't strip `\r`, so a value like `v1.0.0\rgh: ✓ Release verified!` or a crafted subject name containing `\r` could visually overwrite the genuine success line on a raw terminal (no cursor-repositioning ANSI codes needed - a lone `\r` returns the cursor to column 0, and subsequent characters overwrite what's already there on the same terminal line).

### Impact Explanation
This is a terminal output spoofing issue (line-overwrite via bare `\r`), not a credential-prompt-forgery issue - `gh release verify` does not prompt for a token or credentials during this flow, so the "Paste your GitHub token" scenario described in the exploit idea does not apply here. Realistic impact is limited to visually misleading a user who reads the verification output in a raw/non-interactive terminal (e.g., making a name field appear to say `✓ Release verified!` when the attestation actually failed to match, or obscuring a mismatched digest) - this could support a social-engineering step toward the victim trusting an unverified/attacker-modified artifact. This is a real but low-severity terminal spoofing bug (cosmetic misdirection), not code execution, token theft, or verification bypass by itself, since the underlying cryptographic verification result (`config.AttVerifier.VerifyAttestation`) is unaffected - it only fires (and prints) the "Release verified!" banner if verification returned no error.

### Likelihood Explanation
Requires an attacker to control the target repository (to set a release tag containing `\r`/`\n`, or to publish an attestation/bundle whose statement subjects contain such characters) and the victim to run `gh release verify` against that repo. GitHub's tag/ref naming rules may restrict some characters in the ref itself (`shared.FetchRefSHA` resolves `tagName` to a ref), which could limit how much control an attacker actually has over the printed `tagName` value versus `release.TagName` as returned by the API - this wasn't fully verified in the index available. The Sigstore statement subject names, however, come from JSON fields in an attacker-authored DSSE payload and are far more likely to be freely attacker-controlled.

### Recommendation
Wrap `tagName`, subject `Name`, and digest values in `iostreams.NewUntrusted(...)` (or an equivalent stripping function) before printing in `verifyRun`/`printVerifiedSubjects`, and extend the sanitizer (or add a dedicated one for this path) to also neutralize bare `\r` (and excessive `\n`) rather than only ANSI escape bytes, since this data reaches a raw terminal write path rather than a TTY-aware pager/renderer.

```go
// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
```

```go
// stripControl is a defensive fallback used only if the sanitizing transform
// errors, which the asciisanitizer does not do in practice. It drops C0 control
// bytes other than tab, newline, and carriage return so the result can never
// carry an escape sequence.
func stripControl(s string) string {
	return strings.Map(func(r rune) rune {
		if r < 0x20 && r != '\t' && r != '\n' && r != '\r' {
			return -1
		}
		return r
	}, s)
```

```go
// sanitizeForTerminal replaces ASCII control characters in s with inert
// caret-style stand-ins so frontmatter values cannot inject terminal escapes.
func sanitizeForTerminal(s string) string {
	var buf bytes.Buffer
	r := transform.NewReader(bytes.NewReader([]byte(s)), &asciisanitizer.Sanitizer{})
	if _, err := io.Copy(&buf, r); err != nil {
		return "Unknown"
	}
	return buf.String()
}
```
