### Title
Burn-on-Transfer ERC20 Overcredits Bridge Requests, Draining Counterpart Liquidity — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`requestERC20Transfer` and `onERC20Received` in `BridgeTransferERC20.sol` record and relay the caller-supplied `_value` as the bridged amount without verifying the actual tokens received. For a burn-on-transfer ERC20, the bridge receives fewer tokens than `_value`, yet emits `RequestValueTransfer(_value)` and causes the counterpart bridge to release the full `_value` to the recipient. In lock/unlock mode this permanently drains the bridge's token reserves at the expense of other depositors.

---

### Finding Description

`requestERC20Transfer` (2-step path) pulls `_value + _feeLimit` from the caller and immediately forwards the original `_value` to `_requestERC20Transfer`: [1](#0-0) 

No balance snapshot is taken before or after the `safeTransferFrom`. If the token deflates on transfer (burn rate `r`), the bridge receives only `(1 − r) × (_value + _feeLimit)` tokens, but the event is emitted with the full `_value`: [2](#0-1) 

The 1-step path (`onERC20Received`) has the same flaw — it blindly trusts the `_value` argument supplied by the token contract rather than measuring the actual balance delta: [3](#0-2) 

`_payERC20FeeAndRefundChange` then performs additional `safeTransfer` calls (fee to `feeReceiver`, refund to caller) that each trigger another burn, compounding the shortfall: [4](#0-3) 

The counterpart bridge's `handleERC20Transfer` unconditionally releases the full `_value` to the recipient in lock/unlock mode: [5](#0-4) 

---

### Impact Explanation

In **non-mintBurn (lock/unlock) mode**, the source bridge holds deposited tokens as collateral backing counterpart-chain releases. Each bridge request with a burn-on-transfer token causes the counterpart bridge to release `_value` tokens while the source bridge only ever held `(1 − r) × _value` tokens. The deficit `r × _value` is silently absorbed from other depositors' locked funds. Repeated requests drain the pool until `handleERC20Transfer` on the counterpart side reverts for lack of liquidity, permanently locking honest users' funds.

The corrupted protected value is the bridge's ERC20 token balance: it is understated relative to the sum of all outstanding `RequestValueTransfer._value` obligations, constituting an unauthorized transfer of bridged assets belonging to other depositors.

In **mintBurn mode** the `burn(_value)` call at line 94 will revert when the bridge holds fewer than `_value` tokens, so that path results in a DoS rather than a drain — still a broken invariant but with lower asset impact. [6](#0-5) 

---

### Likelihood Explanation

A bridge operator must first register the deflationary token (`registerToken`). Once registered, **any unprivileged user** can call `requestERC20Transfer` or trigger `onERC20Received` with that token. No further privilege is required. The operator registration step is a normal operational action (supporting a new token on the service-chain bridge), not a security control, so the effective trigger is unprivileged.

---

### Recommendation

Capture the bridge's token balance before and after the `safeTransferFrom` and use the measured delta as the canonical bridged amount:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 received = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    // Derive actual _value and _feeLimit proportionally from `received`
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

Apply the same pattern in `onERC20Received`. Alternatively, document that burn-on-transfer tokens are explicitly unsupported and add a token-registration guard that rejects deflationary tokens.

---

### Proof of Concept

Setup: burn-on-transfer ERC20 with 10 % burn rate (`r = 0.1`), registered on the source bridge in lock/unlock mode. Bridge pre-funded with 1 000 tokens from legitimate depositors. `feeOfERC20 = 5`, `_feeLimit = 10`.

1. Attacker calls `requestERC20Transfer(token, victim, 100, 10, "0x")`.
2. `safeTransferFrom(attacker, bridge, 110)` → bridge receives **99** tokens (110 × 0.9).
3. `_payERC20FeeAndRefundChange`: `safeTransfer(feeReceiver, 5)` → bridge loses 5; `safeTransfer(attacker, 5)` → bridge loses 5. Bridge net: **89** tokens added.
4. `RequestValueTransfer` emitted with `_value = 100`.
5. Counterpart bridge operator calls `handleERC20Transfer(…, 100, …)` → releases **100** tokens to attacker's `_to`.
6. Net loss from bridge reserves: **11 tokens** per call (100 released − 89 received).
7. After ~91 such calls the bridge's 1 000-token reserve is exhausted; all legitimate withdrawal attempts via `handleERC20Transfer` revert with insufficient balance. [7](#0-6) [8](#0-7)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
