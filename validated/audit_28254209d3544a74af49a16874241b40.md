### Title
Webhook `status` events are applied to commits by SHA globally, without validating that the event's repository owns that commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the GitHub App secret configured for the organization derived from the payload's `repository.owner.login` (or `organization.login`). That authentication only proves the request came from *some* organization/repository whose secret is configured in Shipit — it says nothing about which `Stack`/`Commit` the payload is allowed to affect. `StatusHandler`, however, ignores the payload's `repository` field entirely and mutates state by SHA alone, breaking the equality that should hold: "organization/repository authenticated by the signature" == "repository whose commit is written."

### Finding Description
The webhook entry point verifies the signature using the organization implied by the payload: [1](#0-0) [2](#0-1) 

Once verification passes, the raw JSON body is dispatched by event type to a handler, and each handler is trusted to scope its own effects to the correct repository: [3](#0-2) 

Most handlers correctly re-derive the target `Repository`/`Stack` from `params.repository.full_name` before mutating anything, e.g. `PushHandler` scopes to `stacks` (which is resolved via `Repository.from_github_repo_name(repository_name)` in the base `Handler`) and filters by branch: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, never uses `repository_name`/`stacks` at all. It looks up commits **globally by SHA** across the entire Shipit installation and writes a status onto every match: [6](#0-5) 

Because the `status` event's `repository` field is not cross-checked, any organization/repository whose GitHub App webhook secret is configured in this Shipit instance can produce a validly-signed `status` payload with an arbitrary attacker-chosen `sha` and `state`. The commit lookup `Commit.where(sha: params.sha)` is not scoped to the authenticated repository, so a forged status for a SHA that happens to also exist in a *different*, unrelated stack tracked by the same Shipit instance will be written to that other stack's commit — even though the authenticated organization has no relationship to that stack.

### Impact Explanation
Commit statuses gate both merge-queue admission and deploy safety checks: [7](#0-6) 

An attacker who controls (or has commit/status-setting rights on) any repository whose org is configured in this Shipit instance can forge a `status` webhook naming the SHA of a commit belonging to a *different*, sensitive stack, and mark it `success`. This lets them satisfy `required_statuses`/CI-passed checks for that unrelated repository's commit, enabling an unauthorized merge or an unauthorized deploy to proceed on a stack they were never authorized to touch. This is a cross-repository write, matching the "unauthorized deploy/merge" and "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability depends on: (1) Shipit being configured for more than one organization or hosting multiple unrelated repositories whose webhook secret the attacker can legitimately obtain a signature for (e.g., a repo the attacker owns/administers within an org that also has other, unrelated tracked repos), and (2) the attacker being able to choose/guess a SHA that also exists as a tracked commit in the victim stack (trivial if commit history is public, since GitHub SHAs are public and deterministic). No `ApiClient` token, session, or GitHub App private key is required — only the ability to trigger (or forge with a legitimately-known org secret) a real `status` webhook event, which is a standard, unprivileged capability for anyone with commit-status-write access to some repository under a Shipit-configured organization.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository asserted (and already authenticated) by the payload, e.g. restrict to `stacks.flat_map(&:commits)` (using the `stacks`/`repository_name` helper already available on `Handler`) instead of a global `Commit.where(sha: params.sha)`, mirroring the scoping already done by `PushHandler` and the `pull_request` handlers.

### Proof of Concept
1. Shipit is configured with GitHub App credentials for `org-attacker` (attacker-controlled/administered organization) and separately tracks `org-victim/critical-repo` as a Stack requiring the `ci/tests` status to pass before merge/deploy.
2. Attacker creates a repository under `org-attacker`, and via a real (or self-signed, since they control `org-attacker`'s webhook secret) `status` event, sends:
```json
{
  "sha": "<sha of org-victim/critical-repo's current HEAD, public via GitHub API>",
  "state": "success",
  "context": "ci/tests",
  "repository": {"owner": {"login": "org-attacker"}, "full_name": "org-attacker/decoy"}
}
```
3. `WebhooksController#verify_signature` succeeds because it only validates against `org-attacker`'s configured secret.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the matching commit belonging to `org-victim/critical-repo`, and calls `create_status_from_github!`, marking that unrelated stack's commit as CI-passed — enabling an unauthorized merge/deploy on `org-victim/critical-repo` despite the attacker having no relationship to that repository.
