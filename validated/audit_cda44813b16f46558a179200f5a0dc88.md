### Title
Missing `return` after exception handler causes double-processing ("double-free") of a private payment chain callback - ([File: network.js])

### Summary
In `handleSavedPrivatePayments()` in `network.js`, the `try/catch` block that computes `json_payload_hash` via `objectHash.getBase64Hash()` fails to `return` after handling the exception in the `catch` branch. As a result, when a private-payment counterparty sends a chain whose head payload cannot be canonically hashed, the row's completion callback (`cb`) is invoked once from the `catch` handler and then again from the subsequent (unconditionally executed) call into `privatePayment.validateAndSavePrivatePaymentChain(...)`. This is the same bug class as CVE-2021-40574 (GPAC `gf_text_get_utf8_line`): a single resource/completion handle is released/consumed twice because an error path does not short-circuit the rest of the function. [1](#0-0) 

### Finding Description
`handleSavedPrivatePayments()` iterates unhandled private payment rows with `async.each`, and for each row defines `validateAndSave`:

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
``` [2](#0-1) 

`arrPrivateElements` and `row` come directly from `unhandled_private_payments`, which is populated by data received from a private-payment counterparty (a device sending a private chain over the wallet/device messaging protocol). `objectHash.getBase64Hash` can throw for payloads that are not valid canonical-hashable structures (e.g. objects with unsupported types, circular structures, or values that violate the hashing library's assumptions) — this is attacker-influenced input since the payload originates from the sender of the private chain.

When the hash computation throws:
1. `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` is called, which will eventually invoke `cb` — the `async.each` iteratee completion callback for this row — once.
2. Execution does **not** `return` from the `catch` block, so control falls through to the next line, which computes `key` using the now-`undefined` `json_payload_hash`, and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same (already "deleted"/handled) chain.
3. `validateAndSavePrivatePaymentChain`'s `ifOk`/`ifError`/`ifWaitingForChain` callbacks each also call `deleteHandledPrivateChain(...)` and `cb` a second time. [3](#0-2) 

This double invocation of the async iteratee's completion callback is analogous to double-freeing the `gf_text_get_utf8_line` line buffer in the CVE: a single logical unit of work (this row's chain) is finalized twice. Effects include:
- The `async.each` completion accounting is corrupted, which can cause the final callback (`unlock()` on the `"saved_private"` mutex) to fire prematurely/inconsistently, releasing the lock before all rows in the batch have actually finished processing.
- The same private payment chain is fed into `validateAndSavePrivatePaymentChain` a second time even though the code already attempted to mark it as handled, and if validation succeeds this path emits `"new_direct_private_chains"`/`key` events and `sendResult` a second time, causing the wallet layer to process/credit the same private chain more than once.

### Impact Explanation
Because `deleteHandledPrivateChain` is called from the `catch` block yet the function still proceeds to run full validation/save logic on the same chain, and because the premature/duplicate `cb()` invocation corrupts the `"saved_private"` mutex release timing, a malicious private-payment counterparty can trigger:
- Double processing of a single private payment chain (duplicate wallet-side event emission / duplicate crediting attempts of the same private output), and/or
- Premature release of the `"saved_private"` lock while other rows in the same batch are still mid-processing, opening a race window where a second, concurrent invocation of `handleSavedPrivatePayments` can process/validate the same `unhandled_private_payments` row again before the first pass's `deleteHandledPrivateChain` completes.

This can lead to inconsistent or duplicated private-payment state in the receiving wallet (a form of double-spend/double-credit within the local private-asset bookkeping), qualifying as High severity under the rules (unauthorized/duplicate credit of a private payment).

### Likelihood Explanation
The trigger condition — the head private element's `payload` causing `objectHash.getBase64Hash` to throw — is controlled by the remote party constructing the private payment chain (a party the recipient wallet is designed to accept unsolicited private payments from, e.g. any device that knows the recipient's address). No special privileges beyond being a private-payment counterparty are required, and the malformed-payload trigger only requires crafting a `payload` object that the hashing/canonicalization logic cannot handle, which is plausible given `objectHash.getBase64Hash` performs strict type/structure assumptions on arbitrary attacker-supplied payloads.

### Recommendation
Add a `return` statement after the error-handling branch in `network.js`:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
This ensures `cb` (and the row's completion) fires exactly once, preventing double invocation of the `async.each` iteratee and duplicate processing/crediting of the same private payment chain. Additionally, review all other `deleteHandledPrivateChain(...)`/`cb(...)` call sites in this function to confirm each logical path terminates with exactly one callback invocation.

### Proof of Concept
1. As a device/counterparty known to the victim wallet, send a `private_payment` chain whose head element's `payload` is crafted so that `objectHash.getBase64Hash(payload, true)` throws (e.g., a payload containing a value type unsupported by the canonical JSON/hash serializer used by `object_hash.js`).
2. The victim node stores it in `unhandled_private_payments` and later calls `handleSavedPrivatePayments()`.
3. In `validateAndSave`, the `try` block throws; the `catch` handler calls `deleteHandledPrivateChain(..., cb)` (first `cb` invocation) but does not return.
4. Execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which — regardless of outcome — calls `deleteHandledPrivateChain(..., cb)` a second time (second `cb` invocation) and, on the `ifOk` path, emits `new_direct_private_chains` and `sendResult('accepted')` again.
5. Observe duplicate event emissions / duplicate wallet crediting attempts for the single malformed chain, and instrument (or race two concurrent private payments to the same recipient) to confirm the `"saved_private"` mutex is released before all rows finish, allowing overlapping processing of the same `unhandled_private_payments` row.
