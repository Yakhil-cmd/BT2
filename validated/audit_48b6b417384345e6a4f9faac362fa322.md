### Title
Global (repository-unscoped) commit status writes break the authenticated-organization vs. written-repository binding, enabling unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit verifies inbound GitHub webhooks by resolving a `github_app`/webhook secret from the *organization* embedded in the payload (`repository.owner.login`), but the `status` event handler that actually mutates state never checks which repository (or organization) the event claims to belong to. It looks up the target `Commit` purely by SHA across the entire installation. This breaks the equality that should hold between "the organization whose secret authenticated this webhook" and "the repository/stack that is actually written to."

### Finding Description
`WebhooksController#verify_signature` derives the signing organization only from the payload and asks for that org's app: [1](#0-0) [2](#0-1) 

This only proves the request was signed with *some organization's* configured `webhook_secret` (`lib/shipit/github_app.rb#verify_webhook_signature`, `app/models/shipit/hook.rb`) — it says nothing about which repository the event is entitled to mutate.

Compare the two downstream handlers:

- `PushHandler` correctly scopes its side effects to stacks whose repository matches the payload's `repository.full_name`, via the base `Handler#stacks`/`#repository_name`: [3](#0-2) [4](#0-3) 

- `StatusHandler`, however, ignores `repository` entirely and resolves its target purely by commit SHA, globally, across every stack/repository/organization tracked by this Shipit instance: [5](#0-4) 

So the binding that should hold — `organization that authenticated == repository/stack that is written` — is violated for `status` events: authentication is verified at the organization granularity (`repository.owner.login`), but the actual mutation (`commit.create_status_from_github!`) is not scoped to that organization or even to the `repository.full_name` claimed in the same payload. `Commit.where(sha: params.sha)` will match any commit in the database sharing that SHA, regardless of which stack/repo/org it belongs to.

Because git commit hashes are content-addressed, an attacker who has legitimate GitHub write access to *any* repository whose webhooks are forwarded into this Shipit instance (their own repo, or a lower-trust repo under the same or a differently-configured org) can reproduce an identical commit (same tree, parents, author/committer metadata) in a repo they control, then use the real GitHub API/UI to set a commit status on that SHA. GitHub will deliver a correctly-signed `status` webhook for the attacker's own repository. `verify_signature` passes because the signature genuinely matches that repository's/organization's configured `webhook_secret`. `StatusHandler#process` then attaches that forged status to *every* `Commit` record sharing the SHA — including one belonging to an unrelated, higher-trust stack that is pending deploy.

### Impact Explanation
If a victim stack's `shipit.yml` uses `ci.require` to gate deploys on a required status context, an attacker can supply the missing "green" status for a commit under review in a stack they have no access to, without ever running real CI, satisfying the deploy checklist and enabling an unauthorized deploy of that commit. This matches the Critical impact category ("an unauthorized deploy") because it lets an attacker manufacture the CI signal Shipit's deploy authorization logic relies on, cross-repository, using only their own repository's legitimate (and correctly signed) webhook traffic.

### Likelihood Explanation
Exploitability requires: (1) the attacker controls or has write/webhook-triggering access to at least one repository whose events reach this Shipit instance (their own repo is sufficient — no privileged access to the victim's repo, GitHub App, or Shipit account is needed), and (2) the attacker can reproduce an identical commit SHA to one currently pending deploy in the target stack (deterministic given identical tree/parents/metadata, and often feasible when commits are cherry-picked, mirrored, or rebased across repos/forks). This is a real, unprivileged-attacker-reachable path, not merely theoretical, since the code path performs zero repository/organization scoping for this event type.

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already do so) to the repository claimed in the payload before mutating any `Commit`, e.g. restrict the lookup to `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { id: repository.id })`, mirroring the pattern already used by `Handler#stacks`/`PushHandler`. Additionally, verify that the `repository.owner.login` used for signature verification actually matches the `repository.full_name` owner in the same payload, so the authenticated organization and the repository being acted upon are provably the same entity.

### Proof of Concept
1. Attacker creates `attacker/dummy-repo`, tracked (or webhook-forwarding) into the target Shipit instance's organization/app.
2. Attacker crafts a commit in `attacker/dummy-repo` with identical tree, parent(s), author, committer, and timestamps as a real pending commit `C` in victim stack `victim-org/victim-repo`, producing an identical SHA.
3. Attacker uses the GitHub API (`POST /repos/attacker/dummy-repo/statuses/{sha}`) to set `state: success`, `context: <required-ci-context>` on that SHA.
4. GitHub delivers a `status` webhook for `attacker/dummy-repo`, correctly signed with that org's/app's `webhook_secret`; `WebhooksController#verify_signature` passes.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this matches commit `C` in `victim-org/victim-repo` too, attaching the forged success status to it.
6. If `victim-org/victim-repo`'s `shipit.yml` requires that CI context via `ci.require`, commit `C` now appears deployable in the deploy checklist despite never having run real CI, enabling an unauthorized deploy.
