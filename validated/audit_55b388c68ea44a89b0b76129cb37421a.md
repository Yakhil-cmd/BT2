### Title
Cross-repository forged `status` webhook flips `Commit#deployable?` on a victim stack, defeating `Stack#build_deploy`'s `ignored_safeties` escape hatch and triggering unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb], [File: app/models/shipit/stack.rb])

### Summary
`StatusHandler#process` resolves the commit to attach a GitHub `status` webhook to by SHA alone, with no check that the webhook's own `repository.full_name` matches the `Commit`'s `stack.repository`. Because git commit SHAs are pure content hashes that are identical across forks/reconstructed commits, an attacker who controls their own repository (and can therefore emit legitimately-signed webhooks for it) can post a `success` status for a SHA that also exists as an undeployed commit in a victim's stack, writing a `Status` row into the victim stack and flipping `Commit#deployable?` to `true` without any CI ever running against the victim repository.

### Finding Description
The intended binding is: `until_commit.deployable? == true` only if every contributing `Status` for that commit originated from a webhook signed for `stack.repository`'s own org/repo. That binding is broken as follows.

`Commit#deployable?` is purely a function of the `Status` rows attached to the commit: [1](#0-0) 

Those `Status` rows are created by `StatusHandler#process`, which looks up commits **globally by SHA**, with no scoping to the repository that sent the webhook: [2](#0-1) 

`Commit#create_status_from_github!` then persists the status using the **commit's own `stack_id`** (i.e. the victim stack), regardless of which repository the webhook actually came from: [3](#0-2) [4](#0-3) 

`WebhooksController#verify_signature` only checks that the HMAC signature matches the GitHub App config resolved for the payload's own `repository_owner`; it never checks that the payload's repository is the same as the target `Commit`'s repository: [5](#0-4) 

**Exploit flow:**
1. Attacker forks (or independently constructs, via GitHub's Git Data API `POST /repos/:owner/:repo/git/commits` using the exact same tree, parent, author/committer, and message as a real commit visible on the victim's public repo) a commit whose SHA1 is byte-identical to a commit sitting in the victim stack's undeployed range. Because SHA1 is a deterministic hash of content, this collision is not a cryptographic break — it's simply reusing/reproducing a real, already-public commit object.
2. Attacker, as owner/admin of their own repository, sets a commit status (`success`) on that SHA via the GitHub Statuses API on their own repo, or via their own CI pushing to that repo.
3. GitHub sends a real, correctly-signed `status` webhook to Shipit's `POST /webhooks` for the attacker's repository. `verify_signature` passes because it is a genuine GitHub-signed webhook (signed with the app config resolved for the attacker's own org, which is a real registered organization/app installation).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter, matches the victim's `Commit` row (same SHA, different `stack_id`), and calls `create_status_from_github!` on it, inserting a `Status` scoped to the victim's own `stack_id`.
5. `Commit#deployable?` on the victim commit now evaluates `success? && !blocked?` as true purely from the forged status.
6. `Status#schedule_continuous_delivery` fires on `after_commit`, calling `commit.schedule_continuous_delivery`, which — if the victim stack has continuous deployment enabled and is otherwise deployable — enqueues `ContinuousDeliveryJob`, which drives `Stack#trigger_deploy`/`Stack#build_deploy`. Since `until_commit.deployable?` is now `true`, `ignored_safeties: force || !until_commit.deployable?` evaluates to `force || false`; with `force` false (the normal/automatic path), `ignored_safeties` is `false`, meaning the system treats this as a normal, safety-checked, CI-approved deploy — while no legitimate CI ever ran against the victim's repository. [6](#0-5) 

None of the existing guards prevent this: `verify_signature` only proves the webhook came from *some* real GitHub org, not that it's the *same* org as the target commit's stack; the `ExplicitParameters` schema for `StatusHandler` only validates field types/presence, not repository identity; there is no `Repository` cross-check anywhere in this path.

### Impact Explanation
A forged status from a repository the attacker fully owns writes a `Status` row into an unrelated victim `Stack`'s commit and can flip `Commit#deployable?`, causing `Stack#build_deploy`'s `ignored_safeties` to be computed as if the commit passed real CI. Combined with `schedule_continuous_delivery`, this can drive an actual unauthorized deploy/rollback task execution (via `Command`/`PTY.spawn`) on the victim stack's infrastructure, using the victim's own deploy commands and secrets, triggered entirely by a cross-tenant payload. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any commit whose SHA the attacker can reproduce and against any stack tracking that SHA.

### Likelihood Explanation
Preconditions: the attacker needs (a) the ability to emit a genuinely GitHub-signed webhook for a repository they control (explicitly listed as an available attacker capability), and (b) a commit SHA colliding with one in the victim's undeployed commit range — achievable via forking public history or reconstructing an identical commit object through GitHub's Git Data API using publicly visible commit metadata. No Shipit secrets, sessions, or privileged roles are required. The attack is fully repeatable and does not require the victim repository to be misconfigured in any special way.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to commits whose `stack.repository` matches the webhook payload's `repository.full_name` (and organization), e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { name: repo_name, owner: repo_owner } )`, and reject/ignore statuses whose repository does not match the target commit's own stack repository before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually, or `test/models/commits_test.rb`):
```ruby
test "forged status from a foreign repository must not make a foreign commit deployable" do
  victim_stack = shipit_stacks(:shipit) # repository foo/bar
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "shared commit")

  # No status has ever come from victim_stack.repository's own org/webhook.
  refute_predicate victim_commit, :deployable?

  # Attacker's payload claims a *different* repository (their own, attacker/evil)
  foreign_status_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "attacker-ci",
    "repository" => { "full_name" => "attacker/evil", "owner" => { "login" => "attacker" } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new.call(foreign_status_payload)

  victim_commit.reload
  assert_equal false, (false || !victim_commit.deployable?) # exposes the broken binding:
  # deployable? became true purely from a same-sha, foreign-repo status
  assert_predicate victim_commit, :deployable?

  built = victim_stack.build_deploy(victim_commit, shipit_users(:walrus), force: false)
  assert_equal false, built.ignored_safeties
  # ignored_safeties is false even though no status from foo/bar's own webhook exists
end
```
This asserts both sides of the binding: `victim_commit.deployable?` should require a status whose webhook repository equals `victim_stack.repository`, but instead becomes `true` from `attacker/evil`'s status, causing `build_deploy(...).ignored_safeties` to be `false` without any real CI on `foo/bar`.
