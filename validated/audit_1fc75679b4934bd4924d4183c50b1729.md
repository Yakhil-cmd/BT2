### Title
Unwrap on Token-2022 transfer-fee calculation can panic and permanently brick swap/deposit/withdraw, freezing LP and user funds - (File: `programs/cp-swap/src/utils/token.rs`)

### Summary
The disclosed OpenZeppelin advisory is about `ERC165Checker.supportsInterface` reverting instead of gracefully returning `false` because it blindly `abi.decode`s untrusted return data. The general bug class is: *code that processes externally-controlled/untrusted data uses an operation that can panic/revert instead of returning a controlled error, and that unexpected revert is reachable from a user-facing entry point.* The `raydium-cp-swap` program has a structurally analogous pattern: `get_transfer_fee` and `get_transfer_inverse_fee` in `programs/cp-swap/src/utils/token.rs` call `.unwrap()` on the result of Token-2022 `TransferFeeConfig` fee-calculation methods, where the `TransferFeeConfig` is read directly from an attacker-supplied/attacker-created mint account rather than being validated to always succeed.

### Finding Description
`get_transfer_fee` and `get_transfer_inverse_fee` unpack the mint's `TransferFeeConfig` extension and then call `.unwrap()` on `calculate_epoch_fee` / `calculate_inverse_epoch_fee`: [1](#0-0) [2](#0-1) 

These helpers are called on every `deposit`, `withdraw`, `swap_base_input`, and `swap_base_output` instruction for whichever mint is the pool's Token-2022 mint, using amounts that are influenced by pool reserves, the constant-product curve output, and the caller-chosen swap/deposit/withdraw amount: [3](#0-2) [4](#0-3) 

An unprivileged pool creator can create a pool through `initialize`/`initialize_with_permission` using an arbitrary Token-2022 mint they control, including one configured with a `TransferFeeConfig` extension (fee basis points and maximum fee are creator-controlled at mint-creation time, before the pool exists, and are never validated by the cp-swap program itself). If the basis points/maximum fee configuration combined with a caller-chosen amount drives `calculate_epoch_fee`/`calculate_inverse_epoch_fee` into returning `None` (e.g., via an internal overflow/edge case in the fee math for extreme configurations), the `.unwrap()` panics instead of the function returning a Solana program error. Just as `ERC165Checker` assumed `abi.decode` of untrusted return data would never fail and instead let a malformed value cause a revert, this code assumes the fee-calculation result is always `Some` for any mint that passes basic unpacking, and panics on the untrusted extension data instead of surfacing a controlled `Result::Err`.

### Impact Explanation
Because `get_transfer_fee` is invoked unconditionally inside `withdraw` for both vault mints, a panic here makes `withdraw` for that specific pool permanently unusable — every future withdrawal instruction for the pool will abort at the same `.unwrap()`. Since `withdraw` is the only in-program mechanism for LPs to redeem LP tokens for underlying vault assets, this permanently freezes all liquidity provider funds deposited into that pool. The same helper is reachable from `swap_base_input`/`swap_base_output`, so the swap path for the pool is likewise permanently disabled, freezing user funds that would otherwise be tradable. This matches the "permanent freezing of user or LP funds" impact class called out for this scan.

### Likelihood Explanation
Likelihood depends on whether a Token-2022 `TransferFeeConfig` configuration and swap/deposit/withdraw amount combination actually exists that drives `calculate_epoch_fee`/`calculate_inverse_epoch_fee` to return `None` given the crate's internal arithmetic; this is a property of the `spl-token-2022` extension implementation that I was not able to verify from within this repository's index (the fee-math internals live in the external `spl-token-2022` crate, not in this codebase). The pool-creation and fee-calculation call paths themselves are fully attacker-reachable with a single transaction and attacker-chosen mint/amount, matching the reachable-path requirement, but confirming an actual overflow/`None` case requires inspecting `spl-token-2022`'s `TransferFeeConfig::calculate_epoch_fee` source, which is outside this repo.

### Recommendation
Replace `.unwrap()` in `get_transfer_fee` and `get_transfer_inverse_fee` (and any other `TransferFeeConfig` calculation call sites) with `.ok_or(ErrorCode::...)?`/`checked_*` patterns that return a graceful `Result::Err` instead of panicking, mirroring the OpenZeppelin fix of validating decoded data rather than assuming success.

### Proof of Concept
Not independently verified beyond the code-level unwrap pattern, since confirming a concrete panicking input requires the external `spl-token-2022` fee-math implementation, which is not present in this repository's indexed content. Conceptually: (1) attacker creates a Token-2022 mint with a `TransferFeeConfig` extension configured at the boundary values that make internal fee math overflow for some later-chosen amount; (2) attacker calls `initialize`/`initialize_with_permission` to create a pool using that mint; (3) attacker or victim LP calls `deposit` to seed the pool; (4) attacker calls `withdraw` or `swap_base_input`/`swap_base_output` with an amount chosen to trigger the overflow condition, causing `.unwrap()` to panic and the pool's swap/withdraw instructions to permanently revert, freezing LP funds in the pool. /// Calculate the fee for input amount
pub fn get_transfer_fee(mint_info: &AccountInfo, pre_fee_amount: u64) -> Result<u64> {
    if *mint_info.owner == Token::id() {
        return Ok(0);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    let fee = if let Ok(transfer_fee_config) = mint.get_extension::<TransferFeeConfig>() {
        transfer_fee_config
            .calculate_epoch_fee(Clock::get()?.epoch, pre_fee_amount)
            .unwrap()
    } else {
        0
    };
    Ok(fee)
}
