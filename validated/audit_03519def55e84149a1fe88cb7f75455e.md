### Title
Attestor list update for `spender_attested` assets can permanently strand already-received funds - (File: `validation.js`, `storage.js`)

### Summary
Assets in ocore can be created with `spender_attested: true`, which requires that any address involved in a transfer or issue of that asset be present in the asset's *current* attestor list (`arrAttestedAddresses`), populated from the asset definer's `asset_attestors` messages. Because the check re-reads the attestor list valid at `last_ball_mci` at spend time — not the list valid when the output was created/received — a definer can post a new `asset_attestors` list at any time and instantly render existing (already validly received) outputs unspendable. This mirrors the reported EigenLayer issue: a privileged, externally/definer-controlled whitelist can be mutated after the fact, stranding funds that were valid when deposited/received.

### Finding Description
When an asset has `spender_attested = true`, `validatePaymentInputsAndOutputs` requires that transfer input owners and output addresses be attested: [1](#0-0) [2](#0-1) 

Attestation status is resolved from the asset's attestor list, which is looked up dynamically for the current `last_ball_mci` via `storage.filterAttestedAddresses`, reading the most recently confirmed `asset_attestors` unit for that asset: [3](#0-2) 

The definer can post an `asset_attestors` message that replaces/updates this list at any time (limited only to one update per asset per unit, with no restriction preventing removal of addresses that currently hold outputs): [4](#0-3) 

Because the "is this address attested" check is evaluated against the *current* list rather than the list in effect when the output was created, an address that legitimately received a `spender_attested` asset output while attested can be later dropped from the attestor list. Any subsequent attempt to spend that output — whether as an input owner or as a payment output recipient — will fail validation ("owner address is not attested" / "some output addresses are not attested"), exactly as in the EigenLayer report where a previously-whitelisted strategy is de-whitelisted and deposits already sitting in the pool can no longer be staked.

### Impact Explanation
Funds held in a `spender_attested` asset can become permanently unspendable if the definer (a party trusted to manage the attestor list, analogous to EigenLayer's strategy whitelister) removes an address from the attestor list after that address has already received/holds the asset. There is no protocol-level recovery path: the holder cannot transfer the coins to any address, including back to the definer, because the transferrable/attested checks are enforced symmetrically on both owner and recipient side. This constitutes a fund-freezing condition for legitimate holders, consistent with the "High" impact bucket used in the source report (funds locked for an arbitrary/indefinite period, controlled by a third party's whitelist decision).

### Likelihood Explanation
This requires an asset explicitly configured with `spender_attested = true` (a supported, documented asset feature) and a definer who updates the attestor list to remove an address that already holds funds — either intentionally (e.g., de-listing a compromised/sanctioned attestor or address) or as an operational mistake. Since asset definers routinely rotate attestor sets (e.g., to add/remove KYC providers or compliance addresses), this is a realistically triggerable scenario, not a purely theoretical one.

### Recommendation
- Snapshot/record the required attestation at the time the output is created (or otherwise grandfather previously-attested addresses) so that later attestor-list changes cannot retroactively invalidate already-existing balances, or
- Provide an explicit protocol-level mechanism allowing holders of stranded `spender_attested` outputs to recover funds (e.g., allow spending to the definer address regardless of current attestation status, similar to the `auto_destroy`/definer-return path already used elsewhere for non-transferrable assets), or
- Require attestor-list updates to be checked against, and disallowed from removing, addresses that currently hold unspent outputs of the asset (impractical at scale, but at minimum should be documented as a governance risk for asset issuers).

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and posts an initial `asset_attestors` list including address `X`.
2. Address `X` receives a payment output of asset `A` while attested (passes `validatePaymentInputsAndOutputs`, see [2](#0-1) ).
3. Definer posts a new `asset_attestors` unit for asset `A` that no longer includes `X` (allowed per [4](#0-3) ; only one update per unit is enforced, not a floor on removable addresses).
4. `X` attempts to spend or transfer its previously received output of asset `A`. `storage.filterAttestedAddresses`/`readAsset` now returns the updated attestor list without `X` ( [3](#0-2) ), so the transfer validation fails at [1](#0-0)  ("owner address is not attested") — the funds held by `X` are permanently stuck with no way to move them.
