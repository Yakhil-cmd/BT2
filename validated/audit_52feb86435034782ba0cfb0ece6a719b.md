### Title
Stack-scoped `ApiClient` tokens can read any stack's build status via `CCMenuController#stack` bypassing the scope binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The engine's `ApiClient` model supports scoping a token to a single `Stack` via `belongs_to :stack, optional: true` [1](#0-0) , and `Api::BaseController` enforces that scope for every normal API action by resolving `stack` through the scoped `stacks` relation: `stacks.from_param!(params[:stack_id])`, where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is set [2](#0-1) . `Api::CCMenuController`, however, overrides this method and resolves the stack unscoped, directly from the request parameter: `Stack.from_param!(params[:stack_id])` [3](#0-2) .

### Finding Description
`require_permission :read, :stack` on `CCMenuController` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`, which never inspects `stack_id` or compares it to the requested resource: `unless permissions.include?(required_permission) ...` [4](#0-3) . The scope restriction to a single stack is implemented only in `BaseController#stacks`/`#stack` [2](#0-1) , and every other API controller (e.g. `Api::StacksController`, `Api::TasksController`) relies on this shared, scoped `stack` helper. `CCMenuController` breaks this pattern by redefining `stack` to call `Stack.from_param!(params[:stack_id])` directly, ignoring `current_api_client.stack_id` entirely [3](#0-2) .

This is exactly the "equality that should hold but doesn't" pattern from the report: the vault's `convertToShares` binds share ownership to a manipulable price instead of a fixed accounting invariant; here, the intended invariant `stack the token authorizes == stack the token can touch` is broken by one controller path that substitutes an attacker-controlled `params[:stack_id]` for the token's bound `stack_id`.

A stack-scoped token is a real, intentionally weaker credential type: the fixture `here_come_the_walrus` demonstrates exactly this pattern — a token restricted to `stack: shipit` with only `read:stack` permission [5](#0-4) , and a dedicated test confirms the intended restriction: "an api client scoped to a stack will only see that one stack" [6](#0-5) . Nothing in `CCMenuController` enforces that guarantee.

### Impact Explanation
An attacker who legitimately holds a stack-scoped `read:stack` token (e.g., a CI system, monitoring tool, or CCMenu client meant to see only build status of stack A) can supply an arbitrary `stack_id` to `GET /api/:stack_id/ccmenu.xml` and read build/deploy status (stack name, activity, last build status/label/time, lock status) for any other stack in the installation, including stacks they were never authorized to see. This matches the "High" impact category of unauthenticated (here: out-of-scope) read of stack state, since the credential was never authorized for the disclosed stack.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped tokens: this is a supported, documented feature of `ApiClient` (`belongs_to :stack, optional: true`, `stack_id?` scoping in `BaseController#stacks`), exercised by shipped tests and fixtures. Exploitation requires no privilege escalation beyond simply changing the URL's `stack_id` parameter on a request the attacker is already authorized to make against the endpoint.

### Recommendation
Make `CCMenuController#stack` reuse the inherited, scoped resolution instead of bypassing it, e.g. remove the private `stack` override and rely on `BaseController#stack` (`stacks.from_param!(params[:stack_id])`), or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id` before rendering.

### Proof of Concept
1. Admin creates (via console/seed, as in the `here_come_the_walrus` fixture) a stack-scoped `ApiClient` with `stack: stack_a`, `permissions: ['read:stack']`.
2. Attacker holding that token's `authentication_token` sends:
   `GET /api/stack_b/ccmenu.xml` with `Authorization: Basic <token>`.
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully [7](#0-6) .
4. `require_permission :read, :stack` passes because the token has `read:stack` regardless of which stack is requested [4](#0-3) .
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` to `stack_b`, unrelated to the token's bound `stack_a` [8](#0-7) .
6. The response discloses `stack_b`'s build/deploy status, which the token was never authorized to see.
