### Title
Ordinary stake-authority instructions (Split/Merge/Redelegate) between reward calculation and a stake account's scheduled distribution partition can panic `Bank::build_updated_stake_reward`'s consistency assertion - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`Bank::build_updated_stake_reward` reads the stake account's *current, live* delegation from `stakes_cache_accounts` at distribution time and asserts it is consistent with the reward amount computed earlier during the calculation phase. Because `StakesCache::check_and_store`/`upsert_stake_delegation` is updated after every committed transaction, any ordinary stake instruction the account's own authority sends between epoch-boundary calculation and that account's scheduled partition (e.g. `Split`, `Merge`, redelegate) changes `delegation.stake` and causes `assert_eq!` at [1](#0-0)  to fail, panicking the bank deterministically for every validator that processes that block.

### Finding Description
During `begin_partitioned_rewards`, the Bank computes `PartitionedStakeReward`s from a point-in-time snapshot of stake delegations and caches them in `Arc<PartitionedStakeRewards>` under `EpochRewardStatus::Active(EpochRewardPhase::Calculation(...))` [2](#0-1) . Distribution happens over subsequent blocks via `distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward` [3](#0-2) .

`store_stake_accounts_in_partition` fetches the *current* `StakesCache` contents fresh for every partition/block it processes: `let stakes_cache = self.stakes_cache.stakes(); let stakes_cache_accounts = stakes_cache.stake_delegations();` [4](#0-3) . This cache is mutated live after every committed transaction touching a stake account, via `update_stakes_cache` → `StakesCache::check_and_store` → `upsert_stake_delegation`, which replaces the cached `StakeAccount` (including `delegation.stake`) for that pubkey [5](#0-4) [6](#0-5) [7](#0-6) .

`build_updated_stake_reward` looks up the account fresh from that live cache (`stakes_cache_accounts.get(&partitioned_stake_reward.stake_pubkey)`), and — when `adjust_delegations_for_rent` (the `relax_post_exec_min_balance_check` feature) is not active — computes `expected_delegation = stake.delegation.stake (LIVE) + partitioned_stake_reward.inflation.stake_reward (computed at calculation time from the OLD delegation)` and asserts it equals `new_stake.delegation.stake` (also computed at calculation time from the OLD delegation) [8](#0-7) . If the account's authority (the ordinary staker themselves) submits a legitimate stake instruction that changes `delegation.stake` between the calculation block and the block that processes this account's partition — e.g. `Split` (moves stake to a new account, reducing the source's `delegation.stake` immediately) or `Merge` (combines two active delegations' stakes immediately) — the live delegation no longer matches the value baked into the pre-computed `PartitionedStakeReward`, and `assert_eq!` fires, causing a Rust panic inside `store_stake_accounts_in_partition`. This panic is *not* caught by the `Result`-based error path (`DistributionError::AccountNotFound` etc. only covers the case where the account is entirely gone from the cache); `assert_eq!` unconditionally aborts the thread/process. Because block processing (and this reward-distribution logic) is deterministic and run by every validator, this crashes the whole cluster at that slot, not just a single node.

The code comment at line 330-332 claims "further state mutation prevents by stake-program restrictions, there should never be rewards burned," but no code was found in the stake program or `Bank` that blocks `Split`/`Merge`/`Redelegate` on accounts pending reward distribution — the assumption underlying the assert is not actually enforced anywhere in the reachable code paths that were inspected.

### Impact Explanation
This is a deterministic, cluster-wide bank panic ("epoch-boundary halt" category) triggerable by an ordinary staker performing legitimate stake-authority operations (`Split`/`Merge`) on their own stake account during the reward distribution window of an epoch in which they have a pending reward. No privileged access, leaked keys, or validator control is required — only ownership of a stake account that is scheduled for a later distribution partition. This matches the in-scope "epoch-boundary halt" impact category.

### Likelihood Explanation
Feasibility depends on the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) not being active — this feature gates whether the vulnerable `assert_eq!` branch is taken at all; when the feature is active, the code instead calls `adjust_delegation_for_rent`, which tolerates mismatches by clamping rather than asserting [9](#0-8) . I was unable to confirm from the index whether this feature is already fully activated on mainnet-beta (its activation status could not be verified with the available tools). If the feature is not yet active on some cluster (e.g. testnet/devnet, or a fresh validator/cluster build using this codebase), the bug is trivially and repeatably reachable: any staker can always find or construct a scenario where their stake account is scheduled into a later partition (partitioning is public/deterministic via `hash_rewards_into_partitions`), then submit `Split`/`Merge` before that partition's block height is reached.

### Recommendation
- Do not rely on a live re-read of `StakesCache` at distribution time combined with a hard `assert_eq!` against calculation-time state. Either capture an immutable snapshot of the exact pre-distribution stake state for each reward at calculation time (so distribution always operates on data consistent with the reward computation, independent of intervening user transactions), or treat any mismatch as a recoverable `DistributionError` (burn/skip that reward, as already done for `AccountNotFound`) instead of asserting and panicking.
- Ensure the `adjust_delegation_for_rent` (feature-gated, mismatch-tolerant) code path is used unconditionally, or add an explicit skip/burn path for delegation mismatches instead of a panicking assertion, regardless of feature activation status.

### Proof of Concept
Rust integration test plan (to be run against the reward-bank test harness used in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, which already provides `create_reward_bank_with_specific_stakes` and epoch-boundary helpers):
1. Create a reward bank with two stake accounts, `A` and `B`, delegated to the same vote account, with a small `partitioned_rewards_stake_account_stores_per_block` so rewards span multiple blocks/partitions.
2. Advance to the epoch boundary so `Bank::epoch_reward_status` becomes `Active(Calculation(...))`, capturing `PartitionedStakeReward`s for `A` and `B`.
3. Before advancing to the block height that processes `A`'s partition (verify via `hash_rewards_into_partitions`/`partition_indices` which block/partition contains `A`), submit a `stake_instruction::split` (or `merge`) transaction from `A`'s stake/withdraw authority moving lamports/stake out of `A` into a new account.
4. Advance the bank to the block height that triggers `distribute_epoch_rewards_in_partition` for `A`'s partition (via `Bank::new_from_parent` up to `distribution_starting_block_height + partition_index`).
5. Assert: with `relax_post_exec_min_balance_check` disabled, the call panics with `"stake reward delegation must be consistent with the updated stake account lamport balance"` (use `#[should_panic(expected = "stake reward delegation must be consistent")]` to prove reachability), demonstrating a consensus-halting bug reachable by an unprivileged staker performing an ordinary Split/Merge instruction on their own account.
6. As a secondary assertion, verify that with `relax_post_exec_min_balance_check` enabled the panic does not occur (confirming the vulnerable path is feature-gated) — this establishes the exact precondition under which the bug is exploitable.
