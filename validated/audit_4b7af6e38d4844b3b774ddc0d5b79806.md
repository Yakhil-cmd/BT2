## Architecture: How `rpcConn` Works

In `remote_backend.go`, `NewRpcClientP2P` creates a `net.Pipe()` pair: [1](#0-0) 

- `p1` is stored as `sb.rpcConn` (the SubBridge's write end)
- `p2` is wrapped as the `rpc.Client`'s codec (the read end)

So **anything written to `rpcConn` is read by the `rpc.Client`** used by `RemoteBackend`.

## The Unvalidated Write

In `sub_bridge_handler.go`, `HandleMainMsg` for `ServiceChainResponse`: [2](#0-1) 

Raw bytes from the P2P peer are decoded and written directly to `rpcConn` with **zero validation** of content, structure, or authenticity.

## What `RemoteBackend` Does With Those Responses

`RemoteBackend` uses the `rpcClient` (reading from `p2`) for all parent-chain queries: [3](#0-2) [4](#0-3) [5](#0-4) 

These include `BalanceAt`, `CallContract`, `TransactionReceipt`, `FilterLogs`, and `SubscribeFilterLogs` — all used by the bridge manager to decide when to release tokens on the child chain.

## Peer Authentication

The bridge P2P server accepts incoming connections from any peer completing the `servicechain` handshake. The handshake checks `ProtocolVersion`, `NetworkId`, and `ChainID` — none of which are secret. A malicious peer can connect, observe the outgoing `ServiceChainCall` (which contains the JSON-RPC request ID), and craft a `ServiceChainResponse` with a matching ID and attacker-controlled result. [6](#0-5) 

## Impact Chain

1. Attacker connects as a bridge peer (no secret required)
2. SubBridge sends `ServiceChainCall` (e.g., `kaia_getLogs` for bridge events)
3. Attacker observes the JSON-RPC `id` in the call
4. Attacker sends `ServiceChainResponse` with a crafted JSON-RPC response containing fake `RequestValueTransfer` log events
5. `RemoteBackend.FilterLogs` returns attacker-controlled events to the bridge manager
6. Bridge manager processes the fake events and releases tokens on the child chain with no real parent-chain deposit

### Title
Unauthenticated P2P Peer Can Inject Arbitrary RPC Responses Into SubBridge, Causing Unauthorized Token Release — (`node/sc/sub_bridge_handler.go`)

### Summary
`SubBridgeHandler.HandleMainMsg` writes raw bytes from any connected bridge peer directly to `rpcConn` when it receives a `ServiceChainResponse` message. Because `rpcConn` is one end of a `net.Pipe()` whose other end is the `rpc.Client` used by `RemoteBackend`, an attacker acting as a bridge peer can inject fake JSON-RPC responses that the bridge manager acts upon to release bridged assets.

### Finding Description
In `sub_bridge_handler.go` lines 233–246, the `ServiceChainResponse` handler decodes the message payload into a raw byte slice and writes it unconditionally to `sbh.subbridge.rpcConn`. There is no:
- Validation that the bytes form a well-structured JSON-RPC response
- Verification that the response corresponds to a request the SubBridge actually sent
- Authentication that the peer is the legitimate parent-chain bridge node

`rpcConn` is `p1` from a `net.Pipe()` created in `NewRpcClientP2P` (`remote_backend.go:50`). The `rpc.Client` reads from `p2`. All `RemoteBackend` methods (`FilterLogs`, `CallContract`, `TransactionReceipt`, `BalanceAt`, etc.) use this client to query parent-chain state.

### Impact Explanation
The bridge manager uses `RemoteBackend.FilterLogs` / `SubscribeFilterLogs` to detect `RequestValueTransfer` events on the parent-chain bridge contract and trigger token releases on the child chain. By injecting a fake `FilterLogs` response containing a crafted `RequestValueTransfer` log (with attacker-controlled recipient and amount), the attacker causes the bridge to mint or unlock tokens on the child chain with no corresponding parent-chain deposit. This is unauthorized token minting/withdrawal of bridged ERC20, ERC721, or KAIA assets.

### Likelihood Explanation
The bridge P2P server accepts incoming connections from any peer that completes the `servicechain` handshake. The handshake parameters (`NetworkId`, `ChainID`) are public. The attacker only needs network access to the bridge port. The JSON-RPC request ID needed to match a response is visible in the outgoing `ServiceChainCall` message the attacker receives as the connected peer.

### Recommendation
- Validate that `ServiceChainResponse` bytes parse as a valid JSON-RPC response before writing to `rpcConn`.
- Implement peer authentication (e.g., allowlist of trusted parent-chain node IDs) so only the configured parent-chain bridge node can send `ServiceChainResponse` messages.
- Consider replacing the `net.Pipe()` / P2P-forwarded RPC architecture with a direct authenticated RPC connection to the parent chain, removing the P2P relay entirely.

### Proof of Concept
1. Connect a mock peer to the SubBridge's bridge P2P port, completing the `servicechain` handshake with the correct `NetworkId` and `ChainID`.
2. Wait to receive a `ServiceChainCall` (0x06) message from the SubBridge — this is the JSON-RPC request forwarded from `RemoteBackend`.
3. Extract the `id` field from the JSON-RPC request.
4. Send a `ServiceChainResponse` (0x07) message containing a crafted JSON-RPC response:
   ```json
   {"jsonrpc":"2.0","id":<extracted_id>,"result":[{"address":"<bridge_contract>","topics":["<RequestValueTransfer_topic>",...],"data":"<crafted_amount_and_recipient>","blockNumber":"0x1",...}]}
   ```
5. Observe that `RemoteBackend.FilterLogs` returns the fake event to the bridge manager, which processes it and submits a `HandleValueTransfer` transaction on the child chain, releasing tokens to the attacker-controlled address. [2](#0-1) [1](#0-0) [5](#0-4)
