### Title
Division-by-zero panic in `token_price_x32` permanently DoSes swaps after a full LP withdrawal drains a pool's non-fee vault balance to zero - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState::token_price_x32` performs raw integer division on the trading-token amounts returned by `vault_amount_without_fee`, without any zero-denominator guard, unlike every other division in the curve math which uses `checked_div`/`checked_ceil_div`. [1](#0-0)  A single unprivileged liquidity provider can legitimately drive one or both trading-token amounts to exactly zero via a full `withdraw`, after which any subsequent `swap_base_input`/`swap_base_output` call will panic and revert, permanently blocking swaps on that pool.

### Finding Description
`vault_amount_without_fee` computes the trading (non-fee) portion of each vault by subtracting accumulated protocol/fund/creator fees from the raw vault balance, and only errors if the subtraction underflows — it does **not** treat a resulting `0` as invalid: [2](#0-1) 

`token_price_x32` then divides `Q32` by these amounts directly with the `/` operator instead of a checked division: [1](#0-0) 

`withdraw` computes `results.token_0_amount`/`token_1_amount` from `lp_tokens_to_trading_tokens` using the *pre-cap* ratio, and only rejects the withdrawal if that ratio result is `0`; when a user withdraws their entire remaining LP balance (`lp_token_amount == lp_supply`), the ratio is `1`, so `results.token_0_amount == total_token_0_amount` and `results.token_1_amount == total_token_1_amount` (non-zero as long as the pool currently holds any trading liquidity), so the zero-check does not trigger and the full trading balance is transferred out: [3](#0-2) 

After this withdrawal, the vault's raw token balance equals only the outstanding, uncollected `protocol_fees`/`fund_fees`/`creator_fees` for that token — i.e. `vault_amount_without_fee` now legitimately returns `0` for that token. Both `swap_base_input` and `swap_base_output` call `pool_state.get_swap_params(...)` (which internally computes `token_price_x32`) using the *current* on-chain vault balances before performing the swap: [4](#0-3) [5](#0-4) 

Any swap attempt against such a pool will therefore trigger a division-by-zero panic before any transfer executes, aborting the transaction.

### Impact Explanation
Because the panic occurs on every future swap attempt against the affected pool (the zero-liquidity state persists on-chain until new liquidity is deposited), this permanently disables the `swap_base_input`/`swap_base_output` instructions for that pool for all users — a Denial of Service on core trading functionality reachable by any unprivileged LP simply withdrawing their full position. This matches the "unhandled exception on effectively-empty data causing a crash" bug class from the referenced advisory, mapped onto the swap price-oracle computation.

I was not able to fully verify within the available context whether a subsequent `deposit` call by another party could restore non-zero vault balances and self-heal the pool (I did not have visibility into `deposit.rs`'s handling of a pool whose `lp_supply` has reached zero after a full drain), so the "permanence" of the freeze is not fully confirmed and should be validated against `programs/cp-swap/src/instructions/deposit.rs`.

### Likelihood Explanation
Reaching this state requires only a single unprivileged LP to hold and fully withdraw 100% of a pool's circulating LP supply (a normal, permitted action via `withdraw`), so likelihood is high for low-liquidity or single-LP pools such as those immediately after `initialize`.

### Recommendation
Replace the raw division in `token_price_x32` with `checked_div`, returning `ErrorCode::ZeroTradingTokens` (or similar) on a zero denominator, consistent with the rest of the curve math, and consider rejecting `swap_base_input`/`swap_base_output` early with a clear error when `vault_amount_without_fee` yields zero for either side.

### Proof of Concept
1. Create a pool via `initialize` with minimal liquidity, so the single creator LP position equals the entire circulating `lp_supply`.
2. Call `withdraw` with `lp_token_amount == pool_state.lp_supply` (the full circulating supply); this succeeds and transfers out the entire trading-token balance, leaving vault balances equal only to unclaimed fee amounts (`vault_amount_without_fee` now returns `0` for one or both tokens).
3. Call `swap_base_input` (or `swap_base_output`): `get_swap_params` invokes `token_price_x32`, which computes `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` (or vice versa) with a zero divisor, causing an integer-division panic that aborts the transaction — reproducible on every subsequent swap attempt.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

    pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
        let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
        Ok((
            token_1_amount as u128 * Q32 as u128 / token_0_amount as u128,
            token_0_amount as u128 * Q32 as u128 / token_1_amount as u128,
        ))
    }
