### Title
Unvalidated strategy route can execute attacker code inside the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` forward caller-supplied route bytes to the configured router. The controller authorizes only the expected input-token transfer, but route-selected venue code still executes inside the transaction beneath the caller’s root authorization. A malicious venue can therefore add an unrelated `token.transfer(victim, attacker, amount)` as a child invocation; if the victim signs the simulated authorization tree, the transfer executes even though the controller’s accounting and risk checks still pass.

### Finding Description
The vulnerable boundary is the controller’s strategy swap helper. `process_swap_collateral` authenticates the account owner or delegate, withdraws collateral, and sends the resulting amount through `withdraw_and_swap_from_supply`. [1](#0-0) 

`swap_tokens` passes the opaque `swap` payload directly to `router.execute_strategy`. Before that call, it creates a narrow contract authorization for only `token_in.transfer(controller, router, amount_in)` and then checks only the controller’s measured input spend and positive output receipt. [2](#0-1) 

The helper grants no token allowance, but it also does not restrict which venue contracts the router may invoke while processing the payload. A venue chosen by route data can call an unrelated token contract from its own frame. Because the transaction’s root caller authorization remains active, that token call is recorded under the caller’s authorization tree and succeeds when the signed tree includes it. The controller cannot distinguish this injected transfer from legitimate route effects because it observes only the configured input and output balances.

### Impact Explanation
An unprivileged attacker can steal arbitrary token balances from a user who submits a crafted strategy transaction and signs the resulting authorization tree. The stolen asset does not need to be listed by the lending protocol, is not bounded by `amount_in`, and is outside the route minimum-output check. The route can still return a fair strategy output, so the account ends solvent while an unrelated wallet asset is drained.

### Likelihood Explanation
The attack requires the victim to use attacker-supplied `swap` bytes and sign the authorization tree produced by simulation. That is realistic when routes are obtained through a UI, quote service, aggregator response, or manager that does not display nested authorization invocations. A wallet that clearly shows the extra child token transfer gives the user a final opportunity to reject it, but the protocol does not prevent the poisoned tree.

### Recommendation
Do not allow route payloads to place arbitrary contract code below the user’s authorization. Governance should maintain an allowlist of venue pool addresses, or the router should require registry entries that resolve only to approved venues. Independently, the transaction-building layer should reject any simulated caller authorization tree containing children other than the protocol’s expected token pull. Where feasible, separate route execution from the lending authorization by using an isolated router-held balance or explicit permit rather than running arbitrary venue calls beneath the account owner’s root authorization.

### Proof of Concept
1. Victim owns a normal account holding USDC collateral and also holds an unrelated token `T`.
2. Attacker deploys a contract exposing the venue call expected by the router. That contract calls `T.transfer(victim, attacker, T.balance(victim))`.
3. Attacker constructs route bytes whose hop uses the malicious venue while still returning enough `token_out` to satisfy the route and lending risk checks.
4. Victim calls:

   `swap_collateral(victim, account_id, usdc_key, amount, eth_key, malicious_swap)`

   The controller withdraws USDC, authorizes only the expected controller-to-router USDC transfer, and invokes the router with `malicious_swap`. [3](#0-2) 
5. During route execution, the malicious venue calls `T.transfer(victim, attacker, amount)`. Simulation records this as an additional child under the victim’s `swap_collateral` authorization.
6. If the victim signs that tree, the strategy can still produce a positive ETH receipt and pass `strategy_finalize`, while the unrelated `T` balance is transferred to the attacker. [4](#0-3)
