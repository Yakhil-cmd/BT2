### Title
Unbounded accumulation of never-completing private-payment chains in `unhandled_private_payments` (light nodes) - ([File: network.js])

### Summary
Analogous to CVE-2024-38534 (Suricata Modbus transactions kept forever when no matching response ever arrives), a light `ocore` node that receives a crafted private-payment chain whose earlier chain elements are deliberately withheld will store the head element in the `unhandled_private_payments` table forever. The cleanup logic that is supposed to reclaim these rows only fires when the *referenced unit itself* never becomes known, not when the unit is known but the *private chain* never completes. An unprivileged private-payment counterparty (or anyone able to send a `private_payments` device message / `hub/deliver` message to a light wallet) can therefore make the victim's local storage grow without bound.

### Finding Description
When a light client receives a private payment chain with more than one element, `network.handleOnlinePrivatePayment` immediately persists the head element to `unhandled_private_payments` and calls `updateLinkProofsOfPrivateChain` / `rerequestLostJointsOfPrivatePayments`: [1](#0-0) 

For single-element or "known" units, the flow instead reaches `privatePayment.validateAndSavePrivatePaymentChain`, which — **only for light nodes** — checks whether any past unit in the chain is still new/unstable and, if so, returns `ifWaitingForChain`, causing the row to be (re-)saved rather than validated: [2](#0-1) [3](#0-2) 

The only two cleanup routines that touch this table are gated so they can never reclaim a chain that references a *legitimate, already-known* unit but is missing an intermediate element the attacker never sends:

1. `cleanBadSavedPrivatePayments` explicitly refuses to run on light nodes (`if (conf.bLight || bCatchingUp) return;`) and only deletes rows whose unit is *absent* from the `units` table after 1 day: [4](#0-3) 

2. `requestUnfinishedPastUnitsOfPrivateChains` (the light-only path) deletes rows only for units that `storage.filterNewOrUnstableUnits` still reports as new/unstable after 1 day: [5](#0-4) 

Neither routine detects or purges the case where the unit referenced by the stored head element is a normal, stable, already-known unit but the private chain simply never becomes complete/valid because the attacker never forwards the earlier (parent) private elements. In that case `findUnfinishedPastUnitsOfPrivateChains`/`filterNewOrUnstableUnits` returns an empty missing-units list, `arrMissingUnits.length === 0` short-circuits to `finish()` with **no deletion**, and the row is never removed: [6](#0-5) 

Because the `unhandled_private_payments` primary key is `(unit, message_index, output_index)`, an attacker who controls the private-payment sender role can generate an unbounded number of distinct crafted head elements — each pointing at any legitimate, already-stable public unit with an output addressed to the victim, and each with a plausible but never-completed private chain — filling the victim's database indefinitely. This is the direct structural analog of the Suricata Modbus bug: entries are created optimistically while “waiting for a response” (in this case, waiting for the rest of the chain), and the only reap logic is keyed on a condition (“unit doesn't exist”) that the attacker trivially avoids by referencing units that do exist.

### Impact Explanation
This is a resource-exhaustion issue confined to light wallet nodes that accept private payments/chats from counterparties (a role explicitly reachable by an unprivileged private-payment counterparty, per scope). Sustained exploitation grows the local `unhandled_private_payments` table without bound, degrading and eventually crashing the affected wallet/light node (disk exhaustion / DB slowdowns), and can be repeated indefinitely at negligible attacker cost, since each poisoned row costs the attacker only a small crafted JSON message referencing a legitimate on-chain unit. It does not directly enable double-spend or fund loss, so severity is capped below the "spending"/"supply inflation" tier, but qualifies as a resource-only DoS that the scan rules classify by bug-class analogy to the reference CVE (unbounded per-flow state that is never freed).

### Likelihood Explanation
Likelihood is moderate-to-high for any light wallet that accepts unsolicited private-payment/chat traffic from correspondents or via a hub, since `handlePrivatePaymentChains` / `handleOnlinePrivatePayment` process private chains from any device that is allowed to message the wallet (including non-correspondents for whitelisted subjects), and no rate limiting or per-sender quota exists on `unhandled_private_payments` inserts.

### Recommendation
- Add a light-node-safe periodic purge for `unhandled_private_payments` rows whose referenced unit is known/stable but whose chain has not completed validation within a bounded time window (e.g., extend `requestUnfinishedPastUnitsOfPrivateChains` to also delete rows when the head unit is known-stable yet the full chain has repeatedly failed `ifWaitingForChain`/validation past a TTL), rather than only when the unit is missing.
- Enable `cleanBadSavedPrivatePayments`-equivalent reaping logic on light nodes as well, not just full nodes.
- Consider capping the number of pending `unhandled_private_payments` rows per sending device/correspondent, and/or requiring proof that intermediate chain elements exist before persisting the head element.

### Proof of Concept
Conceptual (cannot be executed here, no filesystem/runtime access):
1. Attacker becomes a correspondent (or uses a whitelisted subject) of a victim light wallet.
2. Attacker crafts a `private_payments` message whose head private element references message/output indices of a real, stable, unrelated public unit, but supplies a private chain (`arrPrivateElements`) whose earlier link cannot be resolved (attacker never sends the true prior element, or sends one that fails link-proof verification silently retried).
3. `handleOnlinePrivatePayment` → `savePrivatePayment` inserts the row into `unhandled_private_payments`; `validateAndSavePrivatePaymentChain` keeps returning `ifWaitingForChain`.
4. Repeat with a new distinct `(unit, message_index, output_index)` combination (many real stable units exist to pick from) to add unbounded additional rows.
5. Observe `unhandled_private_payments` table size grow monotonically over time with no scheduled cleanup ever removing these specific rows, since `cleanBadSavedPrivatePayments` doesn't run on light nodes and `requestUnfinishedPastUnitsOfPrivateChains` only deletes rows tied to *missing* units.

function requestUnfinishedPastUnitsOfPrivateChains(arrChains, onDone){
	mutex.lock(["private_chains"], function(unlock){
		function finish(){
			unlock();
			if (onDone)
				onDone();
		}
		privatePayment.findUnfinishedPastUnitsOfPrivateChains(arrChains, true, function(arrUnits){
			if (arrUnits.length === 0)
				return finish();
			breadcrumbs.add(arrUnits.length+" unfinished past units of private chains");
			requestHistoryFor(arrUnits, [], err => {
				if (err) {
					console.log(`error getting history for unfinished units of private payments`, err);
					return finish();
				}
				// get units that are still new or unstable after refreshing the history
				storage.filterNewOrUnstableUnits(arrUnits, async arrMissingUnits => {
					if (arrMissingUnits.length === 0) return finish();
					console.log(`will delete unhandled private payments whose units are not known after 1 day`, arrMissingUnits);
					await db.query(`DELETE FROM unhandled_private_payments WHERE unit IN(${arrMissingUnits.map(db.escape).join(', ')}) AND creation_date < ${db.addTime('-1 DAY')}`);
					finish();
				});
			});
		});
	});
}
