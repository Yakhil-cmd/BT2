### Title
Webhook signature is verified against `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, letting a webhook authenticated for one (secret-less) organization write commit statuses and trigger merges/syncs for any other tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate a webhook against using `repository.owner.login` (falling back to `organization.login`), but the handlers that actually act on the webhook body (`Handler#repository_name`, and especially `StatusHandler#process`) resolve the target repository/commit using a completely different, independently-controlled field (`repository.full_name`, or no repository scoping at all for `status` events). Nothing ties these two fields together. In a multi-organization Shipit install, if any one configured GitHub org has no `webhook_secret` set (documented as an optional field), signature verification for that org is a no-op (`return true unless webhook_secret`), letting an unauthenticated caller "authenticate" as that org while the payload body names and mutates state belonging to a completely different, unrelated tracked repository/org.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
```
where `repository_owner` is: [2](#0-1) 
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GitHubApp#verify_webhook_signature` intentionally treats an absent secret as "always verified": [3](#0-2) 

`webhook_secret` is explicitly documented and shipped in fixtures/templates as an optional, nullable per-organization setting for multi-org installs (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Webhook secret (optional)", `template.rb`).

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire* payload to handlers, none of which re-check that the field used to select the secret (`repository.owner.login`) matches the field used to pick the target repository/commit:
- `Handler#stacks` / `#repository_name` resolves the acted-upon repo from `payload.dig('repository', 'full_name')`, an entirely separate JSON field from the one used in `verify_signature`: [4](#0-3) 
- `StatusHandler#process` doesn't even scope by repository - it matches any `Commit` in the entire database by `sha` alone and writes a new `Status`: [5](#0-4) 

That `Status` creation feeds `Commit#add_status`, which schedules merges/continuous delivery once a commit transitions to `pending`/`success`: [6](#0-5) 

**The broken binding, as an equality that should hold but doesn't:**
`organization used to authenticate the webhook (repository.owner.login)` == `organization/repository whose state is mutated (repository.full_name / matched commit's stack)`.

Before the attack: only the GitHub App installed for organization X, holding X's `webhook_secret`, can produce events that mutate stacks/commits belonging to X's repositories.
After a forged request: an attacker who knows (or guesses) that some configured organization X has no `webhook_secret` set can send `X-Github-Event: status` (or `push`) with `repository.owner.login = "X"` (satisfies signature check, trivially "verified" since the secret is blank) and `sha`/`repository.full_name` referencing an entirely different, unrelated tracked repository/org Y. The commit-status/push handlers act on Y's data with no verification that Y's org ever signed anything.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely:
- `StatusHandler` lets an attacker forge a CI `success`/`pending` status for any known commit `sha` in the whole install (not scoped to the authenticated org at all), which can trigger `stack.schedule_merges` (merge queue processing) and `commit.schedule_continuous_delivery` (auto-deploy on continuous-deployment-enabled stacks) - i.e., an **unauthorized merge or unauthorized deploy** without ever compromising the target org's GitHub App or webhook secret.
- `PushHandler` lets an attacker cause `GithubSyncJob` to run against any tracked stack by supplying an arbitrary `repository.full_name`, using Shipit's real installation credentials to sync from GitHub - a controlled but real cross-repository side effect performed under someone else's authentication context.

This satisfies the Critical bar ("unauthorized deploy, rollback or merge" / cross-repository writes) because the mutation lands on a repository/organization that never authorized (or signed) the request.

### Likelihood Explanation
Requires only that one organization configured on the Shipit instance has no `webhook_secret` set - a state the docs (`docs/setup.md`), the Rails template (`template.rb`), and the multi-org test fixtures (`test/dummy/config/secrets_double_github_app.yml`) all treat as normal/optional, not a misconfiguration. No credentials, GitHub App private key, or session are needed; the attacker just needs network access to `POST /webhooks` and knowledge of a tracked org's name and a target commit `sha` (learnable from the public GitHub repo's commit history). This is a design flaw in the correlation (or lack thereof) between the authenticating field and the acted-upon field, not a third-party gem defect or a hypothetical host-misconfiguration scenario.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the app/secret by `repository_owner`, verify that the same owner is consistent across every repository-bearing field consumed downstream (i.e., that `repository.full_name`'s owner segment equals `repository_owner`, and reject events with mismatched owners). Additionally, `StatusHandler#process` should scope `Commit.where(sha:)` to commits whose `stack.repository` matches `repository_owner`/`repository.full_name`, rather than matching by `sha` globally across the whole install. Do not treat a missing `webhook_secret` as an implicit "always verified" for any organization that lacks one; instead require an explicit opt-in to unauthenticated webhooks per org, separate from the org used to route to other organizations' data.

### Proof of Concept
Preconditions: Shipit is configured for two orgs, "orgA" (no `webhook_secret`, i.e., `webhook_secret: nil` as shown in `test/dummy/config/secrets_double_github_app.yml`) and "orgB" (has a stack tracking `orgB/target-repo`, with a known commit `sha` visible in the public GitHub history and `continuous_deployment: true` or a pending merge queue entry).

1. Attacker sends, with no authentication and no valid HMAC:
```
POST /webhooks
X-Github-Event: status
{
  "repository": { "owner": { "login": "orgA" } },
  "sha": "<known sha in orgB/target-repo>",
  "state": "success",
  "context": "ci/forged"
}
```
2. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` -> `GitHubApp#verify_webhook_signature` returns `true` unconditionally because `orgA`'s `webhook_secret` is blank [7](#0-6) .
3. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, creating a `success` status for the commit belonging to `orgB/target-repo`'s stack - an organization that never authenticated this request [5](#0-4) .
4. This triggers `stack.schedule_merges`/`schedule_continuous_delivery` on `orgB`'s stack [8](#0-7) , producing an unauthorized merge/deploy action on a repository the request never had credentials for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
