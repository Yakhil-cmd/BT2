### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets a forged status for one repository flip CI-enablement (`Stack#enable_ci!`) on any other stack sharing that commit sha - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits by `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike the base `Handler#stacks` helper which properly scopes lookups via `Repository.from_github_repo_name(repository_name)`. Because `Status#after_create` calls `commit.stack.enable_ci!` unconditionally [1](#0-0) , a webhook whose signature is only validated against the attacker's own organization can still create a `Status` on a `Commit` belonging to a completely different stack/repository if a `Commit` row with the same `sha` exists there, mutating that foreign stack's CI-enabled cache flag.

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` a `Status` is attached to. Tracing the code shows this binding is never checked.

`WebhooksController#verify_signature` derives `repository_owner` from the attacker-controlled JSON body (`params.dig('repository', 'owner', 'login')`) and verifies the HMAC using `Shipit.github(organization: repository_owner)` [2](#0-1) . This only proves the request was signed with the secret belonging to *some* org the attacker controls (e.g. their own GitHub App installation/org) - it does not bind the `sha` or any other field to that org's repository.

The base `Handler` class provides a properly scoped helper, `stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from the verified payload before touching any records [3](#0-2) . `StatusHandler#process`, however, does not use this helper at all - it queries commits globally:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

`Commit#create_status_from_github!` then creates a `Status` row scoped to `commit.stack_id`, with no re-validation that this stack corresponds to the payload's repository [5](#0-4) . `Status.after_create :enable_ci_on_stack` then calls `commit.stack.enable_ci!`, writing to the cache key `stacks:#{id}:ci_enabled` for whatever stack owns that commit row [6](#0-5) , [7](#0-6) . This flag feeds `Stack#ci_enabled?`/other CI gating logic used throughout deploy eligibility checks.

Exploit flow: an attacker who legitimately controls a GitHub org/repo with a Shipit webhook configured (satisfies signature verification with their own secret) sends `POST /webhooks` with `X-Github-Event: status`, a `repository.full_name` naming their own repo, and a `sha` value equal to the sha of a commit that also exists in a victim stack's `commits` table (e.g. the same upstream commit tracked by two different Shipit stacks/environments for the same or forked repository - `Commit` rows are stack-scoped, so identical shas commonly exist across multiple stacks tracking overlapping git history). The forged, signature-valid webhook then creates a `Status` against the victim's `Commit` row and its `Stack`, silently invoking `enable_ci!` on the victim stack.

None of the existing guards catch this: `verify_signature` validates the signing org, not the target records; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates `sha`/`state`/etc. types, not repository ownership [8](#0-7) ; and `StatusHandler` bypasses the `stacks`/`repository_name` scoping helper that other handlers rely on.

### Impact Explanation
A payload signed for one repository/org can write a `Status` record and mutate `enable_ci!` (the CI-enabled cache flag) on a stack belonging to a different repository/tenant, matching the explicitly listed Critical category "a payload for one repository mutating another's stack, commit, task or team." This is repeatable for every request as long as a matching-sha `Commit` row exists in the victim's stack, and the blast radius spans any Shipit installation where multiple stacks/tenants can end up with overlapping commit shas (e.g. shared upstream history, monorepo splits, or repo forks tracked as separate stacks).

### Likelihood Explanation
The attacker needs: (1) a Shipit-registered GitHub org/repo they control so their own HMAC signature passes `verify_signature`, and (2) a target commit `sha` known to also exist in the victim stack's `commits` table. Since Git commit SHA1s are content-addressed and independent of which repository hosts them, an attacker can reconstruct an identical commit (same tree/parent/author/committer/message/timestamps) in their own controlled repository if the victim commit's content is public or otherwise known, or the sha collision arises naturally when the same upstream history is tracked by multiple stacks. No Shipit secrets, sessions, or privileged roles are required beyond the attacker's own legitimately-configured webhook.

### Recommendation
Scope `StatusHandler#process` (and any other handler bypassing `Handler#stacks`) to only touch commits belonging to stacks whose repository matches the verified payload's `repository.full_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This mirrors the scoping already used by other handlers via `Handler#stacks` and closes the cross-tenant write path.

### Proof of Concept
Minitest plan (no live GitHub, no secrets needed - directly exercises `StatusHandler.process`/model layer):
```ruby
test "status webhook for repo A must not mutate CI state of unrelated stack B with same commit sha" do
  stack_a = shipit_stacks(:shipit) # repository X
  stack_b = shipit_stacks(:cyclimse) # unrelated repository Y

  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared")
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared")

  # binding under test, stated explicitly BEFORE tracing:
  # commit_b.stack.repository.full_name == "repoX/owner" (payload's repo) should be false
  assert_not_equal commit_b.stack.repository.full_name, stack_a.repository.full_name

  Rails.cache.delete("stacks:#{stack_b.id}:ci_enabled")
  before = stack_b.ci_enabled? # false, no statuses/check_runs yet

  payload = {
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => stack_a.repository.owner } },
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci'
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  after = stack_b.reload.ci_enabled?
  assert_not_equal before, after # FAILS the desired invariant: stack B's CI flag flipped from a repo-A-only payload
end
```
This demonstrates that a payload naming only `stack_a`'s repository causes `Status` creation and `enable_ci!` side effects on `stack_b`, purely because `StatusHandler` resolves commits by `sha` alone with no repository binding check.
