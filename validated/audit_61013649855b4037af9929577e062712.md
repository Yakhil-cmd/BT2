### Title
CCMenu token issued by `CCMenuUrlController#fetch` grants `read:stack` on every stack, not just the requested one - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` creates/finds a single `ApiClient` per user scoped only by `creator` + `name`, never setting `stack:`, so its `stack_id` stays `nil` for the life of the record regardless of which stack the URL was requested for. Because `Api::BaseController#stacks` treats a `nil` `stack_id` as "no restriction" (`Stack.all`), the token embedded in every CCMenu URL a user is ever given authenticates `read:stack` access to **all** stacks, and the `Api::CCMenuController#stack` method additionally bypasses the `stacks` scoping helper entirely.

### Finding Description
Broken binding: the claimed invariant is `client(stackX).stack_id == stackX.id`. The actual code: [1](#0-0) 

shows `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `create_with(permissions: %w[read:stack])` — no `stack:` key anywhere. So the first time any user calls `fetch` for any stack, an `ApiClient` row is created with `stack_id = nil`, `creator = current_user`, `permissions = ['read:stack']`. Every subsequent call to `fetch`, for any other stack, resolves to the *same* row via `find_or_create_by!` (matched purely by `creator` + `name`), so `stack_id` remains `nil` forever — it is never `X.id` for any `X`. This directly satisfies the question's claim: `client(stackA).id == client(stackB).id`, and `stack_id` is nil, not scoped to either stack.

The consequence is verified in the API layer: [2](#0-1) 
`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` — a `nil` `stack_id` is treated as unrestricted, granting `Stack.all`. On top of that, `Api::CCMenuController` doesn't even use this scoping helper for its own `stack` lookup: [3](#0-2) 
`stack` there calls `Stack.from_param!(params[:stack_id])` directly, bypassing `stacks` scoping altogether, so even a properly stack-scoped `ApiClient` would not be constrained on this endpoint.

Attack flow: an authenticated Shipit user with no authorization on stack B visits `GET /ccmenu/*stackA` (any stack they can see) once to mint/find their `'CCMenu Client'` `ApiClient` and obtain its `authentication_token`. That same token, embedded as `?token=` in the returned `ccmenu_url`, can then be replayed against `GET /api/stacks/*stackB/ccmenu` (routed via `config/routes.rb` line 28) for *any* stack B, and `ApiClient.authenticate(token)` in `Api::CCMenuController#authenticate_api_client` will accept it because the record exists and passes `check_permissions!(:read, :stack)`.

No existing guard prevents this: `require_permission :read, :stack` only checks the `permissions` array, not stack scope; the `stacks` scoping helper is bypassed on this controller entirely; and there is no validation forcing `stack` to be present on `ApiClient` creation.

### Impact Explanation
Any authenticated Shipit user can, with a single request, obtain a long-lived, replayable bearer token (`?token=` on the CCMenu URL) that grants `read:stack` on every stack in the Shipit instance, not just the one the URL nominally names. This exposes CI/deploy status (`ccmenu#show`) for stacks/repositories the user was never authorized to view, and — because the permission model and scoping bug are generic (`stacks` helper), any other endpoint gated only by `read:stack` and reachable without stricter stack-membership checks is similarly exposed via this same token. This is a cross-tenant unauthorized-read escalation (High: "unauthenticated/unauthorized read of stack state ... across tenants").

### Likelihood Explanation
Preconditions: attacker needs a valid Shipit session (completed GitHub OAuth) — no special role, team membership, or stack authorization is required. Cost is a single unauthenticated-with-respect-to-stack GET request to `/ccmenu/*any_stack_id` to obtain the token, then arbitrary replay against `/api/stacks/*victim_stack/ccmenu`. This is trivially repeatable against every stack in the deployment and requires no GitHub secrets, webhook signatures, or elevated Shipit privileges — only an ordinary authenticated account, which is a materially lower bar than the "no Shipit session" baseline attacker described in the general ruleset, but matches the precondition explicitly stated in the question ("any authenticated Shipit user, regardless of stack authorization").

### Recommendation
Scope the `ApiClient` lookup/creation by stack: `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`, and fix `Api::CCMenuController#stack` to use the inherited `stacks.from_param!` scoping helper instead of `Stack.from_param!` directly, so a stack-scoped `ApiClient.stack_id` is actually enforced.

### Proof of Concept
Minitest sketch under `test/controllers/ccmenu_url_controller_test.rb` (existing test dir):
```ruby
test "ccmenu token for stack A also authorizes reads on stack B" do
  user = shipit_users(:walrus)
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse)

  session_login_as(user) # authenticated Shipit user, no special stack ACL
  get ccmenu_url_url(stack_id: stack_a.to_param)
  token_a = URI(JSON.parse(response.body)['ccmenu_url']).query[/token=([^&]+)/, 1]

  get ccmenu_url_url(stack_id: stack_b.to_param)
  token_b = URI(JSON.parse(response.body)['ccmenu_url']).query[/token=([^&]+)/, 1]

  assert_equal token_a, token_b # same underlying ApiClient, not scoped

  client = ApiClient.find_by(creator: user, name: 'CCMenu Client')
  assert_nil client.stack_id # never set to stack_a.id nor stack_b.id

  get api_stack_ccmenu_url(stack_id: stack_b.to_param, token: token_a)
  assert_response :success # token minted "for" stack A reads stack B
end
```
This demonstrates both halves of the claimed binding fail: `token_a == token_b` (should differ per stack) and `client.stack_id` is `nil` (should equal the requesting stack's id), and that the leaked token authorizes reads on an unrelated stack.
