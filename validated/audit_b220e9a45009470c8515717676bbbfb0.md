### Title
Use-after-free-style stale object reuse when reverting AA response units invalidates `assocBestChildren` references before `fixIsFreeAfterForgettingUnit` runs - (File: aa_composer.js / storage.js)

### Summary
CVE-2022-3545 is a use-after-free in a kernel driver's address-cache lookup (`area_cache_get`): an entry can be freed while another code path still holds and dereferences a pointer to it. The closest reachable analog in `ocore` is the AA-response rollback path, where in-memory unit objects (kept in `storage.assocUnstableUnits`) are deleted via `storage.forgetUnit()` while other caches (`storage.assocBestChildren`) still hold direct object references to the very same unit objects, and the cleanup of those dangling references (`fixIsFreeAfterForgettingUnit`) is a separate, best-effort pass driven by attacker-influenced input (AA trigger processing).

### Finding Description
`storage.assocBestChildren` stores **direct references to the unstable-unit property objects** (not just unit hashes), e.g. `_.pull(assocBestChildren[parent_unit], assocUnstableUnits[unit])` in `forgetUnit()`: [1](#0-0) 

When an AA-response unit chain must be rolled back (e.g. because a 1-witness network rebuilt the main chain to itself, or bounced units are reverted), `aa_composer.js`'s `revertResponsesInCaches()` walks the response units and calls `storage.forgetUnit` for each, then calls `storage.fixIsFreeAfterForgettingUnit(parent_units)`: [2](#0-1) 

`forgetUnit()` deletes the unit from `assocUnstableUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocStableUnits`, `assocUnstableMessages`, `assocBestChildren`, and attempts to remove the freed object from its parents' `assocBestChildren` arrays — but only for the *direct* parents of the single unit being forgotten: [1](#0-0) 

`fixIsFreeAfterForgettingUnit()` is only called once, after the whole batch of `arrResponseUnits.forEach(storage.forgetUnit)` has completed, and only re-derives `is_free` for the *original* parent_units list captured from `objFirstUnit` (the first response unit), not for every intermediate unit forgotten in the loop: [3](#0-2) [4](#0-3) 

Consumers of `assocBestChildren`, such as `main_chain.js`'s `updateMainChain()`/`goUpFromUnit()`, dereference objects retrieved from `storage.assocUnstableUnits`/`storage.assocStableUnits` and compare them against freshly-read DB rows, throwing `Error("unstable unit not found")` or a consistency-check error if the in-memory object is stale, missing, or already forgotten while still referenced elsewhere: [5](#0-4) 

Because `assocBestChildren[parent_unit]` is an array of live JS object references (not re-fetched by key each time), any code path that iterates it (main-chain best-parent selection, stability determination) after a partial/incomplete cleanup of a chain of forgotten AA-response units can end up holding a reference to an object whose backing entry in `assocUnstableUnits` has already been deleted — a heap-object lifetime bug in the same class as the reported UAF: a cached reference outliving the object's "logical" free, then being read again by a different subsystem (main chain / stability logic) that assumes the cache is authoritative.

### Impact Explanation
If an unprivileged AA-trigger sender can drive a chain of chained AA response units (nested/self-triggering) into a state that gets reverted mid-processing — a scenario explicitly anticipated by the comment "this hack is necessary only for 1-witness network where an AA-response unit can rebuild the MC to itself" in the test file — the resulting stale reference in `assocBestChildren` can cause the main-chain/stability logic in `main_chain.js` to compute best-parent/witnessed-level from an object that no longer matches DB state, or to crash the node process via a thrown consistency-check error (`throwError`/`throw Error`) in `goUpFromUnit`. Either outcome is a node-disagreement-on-stability or an availability failure of main-chain advancement, which is the required "network unable to confirm new units" / "node disagreement on validity or stability" impact class.

### Likelihood Explanation
The rollback path is reachable purely from AA trigger/response processing (no privileged network or hub role required) since `revertResponsesInCaches` is invoked from within `handleTrigger`'s processing pipeline in `aa_composer.js`. The test suite itself documents that a single AA trigger on a 1-witness (or low-witness) network can already cause this MC-rebuild-to-self scenario, indicating the code path is genuinely exercised by ordinary trigger posting, not a purely theoretical edge case. However, actually forcing the exact object-staleness window (a reference in `assocBestChildren` surviving a `forgetUnit` call on a unit it points to further down a multi-response chain) requires precise crafting of a multi-hop AA response chain and timing relative to main-chain construction, which is a real but non-trivial precondition.

### Recommendation
Make `fixIsFreeAfterForgettingUnit` (or an equivalent purge) run against the parent_units of *every* forgotten unit in the `arrResponseUnits` loop, not just the first unit's parents, and have `forgetUnit` defensively scrub `assocBestChildren` globally (or assert no dangling references remain) before returning. Alternatively, store unit hashes rather than object references in `assocBestChildren` so a forgotten unit cannot leave a stale object pointer behind, and add an invariant check in `main_chain.js` that treats a missing `assocUnstableUnits`/`assocStableUnits` entry for a best-parent candidate as a recoverable re-fetch rather than a hard `throw Error`.

### Proof of Concept
1. Set up a single/low-witness test network as in `test/aa_composer.test.js` (uses `eventBus.once('caches_ready', ...)` and `fixCache()` to work around exactly this class of divergence). [6](#0-5) 
2. Post an AA trigger whose processing produces a multi-unit AA response chain such that the resulting response unit(s) become the best parent (or contribute to `assocBestChildren`) of another in-flight unit before the whole chain is confirmed.
3. Force a revert of that chain (e.g., by causing `handleTrigger`'s failure/backoff path to invoke `revertResponsesInCaches(arrResponses)`). [2](#0-1) 
4. Observe that `assocBestChildren` for an ancestor unit still contains a reference to an object that was deleted from `assocUnstableUnits` by `forgetUnit` earlier in the same `forEach` loop (before `fixIsFreeAfterForgettingUnit` executes for that unit's own parents), then trigger `updateMainChain` so `goUpFromUnit` dereferences the stale object and throws or diverges from DB state. [5](#0-4)

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
