Confirmed: `Shipit.github_teams` uses `github.oauth_teams` from a **single** default organization's config (`github_default_organization`), and `github_teams` are computed once and memoized. Critically, `github` is always looked up with `organization: github_default_organization`, i.e., only the first configured org's `oauth.teams` list is ever consulted for team-based authorization — but `User#authorized?` and `find_or_create_from_github` operate on a global `User.github_id`, matched irrespective of which configured GitHub org/domain issued that OAuth callback (`app/controllers/shipit/github_authentication_controller.rb`, `app/models/shipit/user.rb`).

### Title
GitHub identity collision across multiple configured GitHub App/Enterprise organizations allows account takeover via OAuth callback - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
When a Shipit instance is configured with multiple GitHub App organizations (the `github: <org>: {...}` multi-org schema supported by `Shipit.github_app_config`), OmniAuth's GitHub strategy can be initialized per-org with distinct `oauth.id`/`oauth.secret` (and potentially distinct `domain` for GitHub Enterprise). `GithubAuthenticationController#sign_in_github` binds the session solely to `User.find_or_create_from_github(auth.extra.raw_info)`, which matches purely on the numeric `github_id` [1](#0-0) [2](#0-1) . Numeric GitHub IDs are only unique within a single GitHub instance (github.com vs. an independent GitHub Enterprise Server) — they are not globally namespaced. `Shipit::User` has no column recording which org/domain the `github_id` was issued by, so an attacker who can authenticate through one configured org/domain with an ID that collides with a real user's ID from a different configured domain will be logged in as, and overwrite the `github_access_token` of, that existing `User` record [1](#0-0) .

### Finding Description
This is the report's analog of "compromised/unverified identity accounted for in a trust decision without invalidating the prior binding": the equality Shipit relies on is `github_id (scoped to the authenticating org/domain)` == `User.github_id (global, unscoped)`. This breaks whenever more than one org/domain is configured, since `find_from_github` performs `find_by(github_id: github_user.id)` with no domain discriminator [3](#0-2) . `Shipit.github` supports exactly this multi-org configuration via `github_app_config`/`github_organizations`, including a per-org `domain` key for GitHub Enterprise [4](#0-3) . Meanwhile, `Shipit.github_teams`, which drives `User#authorized?`, is only ever derived from the single `github_default_organization`'s `oauth.teams` [5](#0-4) [6](#0-5) , so authorization decisions for the whole app hinge on a single org's team roster while identity can be satisfied by any configured org.

### Impact Explanation
An attacker who controls (or can register) an account on any secondary configured GitHub org/Enterprise instance with a numeric ID equal to a legitimate, already-authorized Shipit `User`'s `github_id` can complete the OAuth callback and be signed in as that user (`session[:user_id] = user.id`) [7](#0-6) . Because `sign_in_github` also does `user.update(github_access_token: auth.credentials.token)` [1](#0-0) , this both hijacks the session (inheriting whatever `authorized?`/team membership and stack permissions that account had) and clobbers the legitimate user's stored `github_access_token`, which is subsequently used for API calls made on that user's behalf (`User#github_api`) [8](#0-7) . This is authentication bypass / session identity confusion, potentially enabling unauthorized deploys under a privileged identity.

### Likelihood Explanation
This requires the deployer to have configured Shipit with the multi-org GitHub App schema (more than one org, potentially including a self-hosted GitHub Enterprise instance the attacker administers or where numeric IDs are attacker-influenceable), which is an explicitly documented and supported configuration path (`config/secrets.development.example.yml`, `lib/shipit.rb#github_app_config`) rather than a hypothetical setup. I was not able to fully verify, within the indexing limits of this session, whether `omniauth-github`'s callback strategy is instantiated per-org with independently switchable `domain`/enterprise endpoints at runtime in this engine's routes/initializers, which would materially affect exploitability — this would need to be confirmed by reading the full OmniAuth builder/initializer wiring, which I could not locate in the indexed files.

### Recommendation
Scope `User` identity to `(domain_or_organization, github_id)` instead of `github_id` alone: add an organization/domain column to `shipit_users`, populate it from the authenticating `GitHubApp`'s configured organization/domain during `find_or_create_from_github`, and require it to match on lookup. Additionally, compute `Shipit.github_teams`/`authorized?` per authenticating organization rather than solely from `github_default_organization`, so authorization is consistently scoped to the org the session was actually established against.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`, e.g. `github: acme: {...}` and `github: attacker_org: {oauth: {...}, domain: "ghe.attacker.example"}`, each with its own OAuth credentials.
2. A legitimate user authenticates against `acme` and is persisted as `Shipit::User` with `github_id: 42`, becomes a member of a required `Shipit.github_teams` team, and is fully authorized.
3. On `ghe.attacker.example` (a GitHub Enterprise instance the attacker controls, or via account-ID collision on github.com), the attacker creates/uses an account whose numeric ID is also `42`.
4. Attacker completes `/github/auth/github/callback` using the `attacker_org` OAuth flow; `sign_in_github` finds the existing `User` with `github_id: 42`, overwrites its `github_access_token` with the attacker's token, and sets `session[:user_id]` to that user's ID.
5. Attacker is now signed in as the legitimate, already-authorized user and can trigger deploys/rollbacks under that identity.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
