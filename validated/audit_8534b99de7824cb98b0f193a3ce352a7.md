### Title
AA payouts in custom assets can be permanently blocked by dust-output spam - (File: aa_composer.js)

### Summary
When an Autonomous Agent (AA) needs to compose a payment message in response to a trigger, `aa_composer.js` collects the AA's spendable outputs via `readStableOutputs()` and `readUnstableOutputsSentByAAs()`, then loops over every returned row in `iterateUnspentOutputs()` to build the payment's `inputs` array. For base-byte outputs there is an explicit dust filter, but that filter is not applied when the payment is in a custom asset, so an attacker can spam an AA address with unlimited tiny-amount outputs of an asset to force the AA's coin-selection loop to consume an unbounded number of inputs, producing an invalid (oversized) unit and freezing the AA's ability to pay out that asset.

### Finding Description
In `aa_composer.js`, `readStableOutputs()` builds a query to find the AA's unspent outputs to spend: [1](#0-0) 

The dust-prevention comment and filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) is applied only in the `asset IS NULL` (base bytes) branch of the ternary; when `asset` is truthy (a custom, user-defined asset) the `WHERE` clause becomes simply `asset=<escaped_asset>` with **no minimum amount** and **no row limit**. The same pattern repeats in `readUnstableOutputsSentByAAs()`: [2](#0-1) 

Both result sets are then fed into `iterateUnspentOutputs()`, which iterates every row in a synchronous JS loop, pushing an `input` per output until `target_amount` is reached: [3](#0-2) 

and is invoked unconditionally from `completePaymentPayload()`: [4](#0-3) 

Unlike the equivalent user-wallet coin-selection code in `inputs.js`, which caps the number of rows fetched with `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` [5](#0-4) , the AA composer's queries have no such `LIMIT`, and there is no minimum-dust filter for non-base assets. Any unprivileged unit poster can therefore send many outputs of a custom asset with amounts as low as 1 unit to an AA's address across separate units. When the AA is later triggered to send a payment in that same asset (e.g., forwarding a balance, paying a bounty, refunding a deposit expressed as a custom asset), the composer must accumulate enough of these dust outputs to reach the required payout, pushing an unbounded number of `input` entries into the payment message.

### Impact Explanation
Because the resulting payment message's `inputs` array is built without any cap, it can exceed the protocol-level maximum number of inputs per payment message enforced during unit validation (`constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, checked in `validation.js`). If the AA cannot construct a valid unit for that asset, its scheduled response/payout for that trigger will fail. Since this failure is deterministic across all full nodes (all nodes independently attempt to compose and validate the AA's response), it does not create a consensus split by itself, but it does render the AA permanently or persistently unable to pay out in that asset - constituting freezing of AA funds reachable purely through unprivileged deposits, directly analogous to the referenced OpenQ report where dust deposits blocked refunds by blowing up the loop used to compute available/locked funds.

### Likelihood Explanation
Likelihood is high: creating outputs of a custom asset is a normal, permissionless action available to any unit poster (via a `payment` message with `asset` set), asset issuance/transfer has no attacker cost beyond fees, and the dust filter that exists for base bytes is conspicuously absent for custom assets, showing the protection was implemented for one case but not the other, no special conditions are required beyond an AA that accepts/holds a custom asset and later needs to pay it out.

### Recommendation
- Apply the same dust-amount floor used for base-byte outputs (`FULL_TRANSFER_INPUT_SIZE` equivalent) to the custom-asset branch in both `readStableOutputs()` and `readUnstableOutputsSentByAAs()`, or introduce an asset-aware minimum threshold.
- Add a `LIMIT` clause to these queries bounded by `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (mirroring `inputs.js`'s `pickMultipleCoinsAndContinue`), so the coin-selection loop can never produce an invalid, oversized unit regardless of how many dust outputs an attacker has sent.
- Consider consolidating/aggregating spam dust outputs (e.g., periodic sweep) or charging an oversize-storage fee for tiny custom-asset outputs sent to AA addresses, similar to the treatment of base-byte dust.

### Proof of Concept
1. Attacker issues (or already holds) a divisible custom asset `X`.
2. Attacker sends thousands of separate `payment` messages each containing a 1-output payload of asset `X` with amount `1` to a target AA's address (cost is limited to standard network fees).
3. A legitimate user later sends a trigger to the AA that requires the AA to pay out `N` units of asset `X` (e.g., a bounty payout or balance forward).
4. `sendUnit()` → `completePaymentPayload()` → `readStableOutputs()`/`readUnstableOutputsSentByAAs()` return all of the attacker's dust outputs (no `LIMIT`, no minimum-amount filter for asset `X`), and `iterateUnspentOutputs()` accumulates inputs from all of them to reach `target_amount`.
5. The resulting `payload.inputs` array can exceed `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, causing the composed unit to fail validation, so the AA's payout in asset `X` cannot be completed, freezing those funds for legitimate recipients.
