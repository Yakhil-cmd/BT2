## Title
Block-reward recalculation can over-distribute a vote account's `pending_delegator_rewards` after partial distribution, minting/misattributing lamports across delegators - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward()` computes each stake account's share of a vote account's `pending_delegator_rewards` pool as `pending_delegator_rewards * stake / total_active_stake`, exactly analogous to the reported `Staking.earned()` pattern of computing a proportional share from a stale/mismatched denominator. The code's own comment acknowledges that `stake` (the numerator, taken from the live/mutated delegation at recalculation time) can exceed `total_active_stake` (the denominator, frozen from `RewardEpochDelegatedStakes` at the end of the rewarded epoch), and only clamps the *per-account* result to `min(pending_delegator_rewards)` rather than ensuring the *aggregate* of all per-account shares stays within the pool. [1](#0-0) 

### Finding Description
`calculate_block_reward` is invoked once per stake delegation from `calculate_stake_rewards_and_commissions` whenever `block_revenue_sharing` is active, both during the initial epoch-boundary calculation and during `recalculate_stake_rewards` (used after snapshot restore or reboot mid-distribution): [2](#0-1) [3](#0-2) 

The reward for a given stake account is:
```
(pending_delegator_rewards * stake / total_active_stake).min(pending_delegator_rewards)
```
where `total_active_stake` is fixed to the value recorded in `reward_epoch_delegated_stakes` at the *end of the rewarded epoch* [4](#0-3) , but `stake` is recomputed live via `delegation_effective_stake(delegation, rewarded_epoch, ...)` from the *current* `StakesCache` delegation [5](#0-4) . The function's own comment states:

> "During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`... We can also have individual rewards look greater than the pending rewards. This is harmless in practice, but we clamp it just to be safe" [6](#0-5) 

This is structurally the same defect as the reported `earned()` bug: a ratio-based share is computed against a "total" figure (`info.totalStaked` / `total_active_stake`) that can diverge from the sum backing it (`totalTokenBalance` / actual per-account stake after mutation), and the fix applied (clamping) only bounds a single leg of the calculation rather than the true invariant — that the sum of all individually-computed shares must not exceed the shared pool (`pending_delegator_rewards`). Clamping each stake account's computed reward to `min(pending_delegator_rewards)` prevents any *single* account from taking more than the entire pool, but does not prevent the *sum across all delegators* to that vote account from exceeding the pool, since each delegation's `stake` value can independently grow between the original calculation and a recalculation (e.g., because a previously-run inflation `stake_reward` was added into `stake.delegation.stake`, or because `distribute_epoch_rewards_in_partition`/`store_stake_accounts_in_partition` already mutated some delegations in `StakesCache` for a prior partition, as shown by `build_updated_stake_reward` writing back `new_stake.delegation.stake` including `inflation.stake_reward`) [7](#0-6) . If `recalculate_stake_rewards` runs after such a partial distribution (a scenario the tests explicitly exercise) [8](#0-7) , unpaid stake accounts' `stake` used for the block-reward numerator can be computed against a stale, now-too-small `total_active_stake` denominator, inflating the block-reward share beyond what the vote account's `pending_delegator_rewards` pool can sustain in aggregate.

### Impact Explanation
`calculate_block_reward`'s output (`block_reward`) is directly minted into stake accounts via `checked_add_lamports` in `build_updated_stake_reward`, and increases total capitalization in `distribute_epoch_rewards_in_partition` (`self.capitalization.fetch_add(stake_reward_lamports_minted, ...)`) [9](#0-8) . If the aggregate block rewards distributed across all delegators of a vote account exceed that account's `pending_delegator_rewards`, this results in minting of lamports beyond the intended, vote-account-tracked pool — a direct violation of the reward accounting invariant and a form of protocol-level over-minting/misattributed rewards.

### Likelihood Explanation
The path requires `block_revenue_sharing` (SIMD-0123 / Alpenglow) to be active and requires a `recalculate_stake_rewards` pass to occur after at least one distribution partition has already mutated `StakesCache` delegations for the same vote account within the same epoch's reward distribution — the specific regression test `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` demonstrates the codebase is already aware of and testing exactly this partial-distribution/recalculation interaction for the inflation-reward denominator. The engineers' own inline comment "This is harmless in practice" for the block-reward path indicates the aggregate-sum risk across delegators has not been rigorously verified, only individually clamped — making this a credible latent defect rather than a purely theoretical one, though triggering it in production requires the specific timing of a bank restart/recalculation mid-distribution combined with multiple delegators to the same validator receiving inflation stake rewards in earlier partitions of the same epoch.

### Recommendation
Do not clamp only per-account block-reward shares to `pending_delegator_rewards`; instead, track the vote account's remaining undistributed `pending_delegator_rewards` pool across all stake-reward computations for that vote account within the same calculation/recalculation pass (analogous to decrementing a shared budget), and ensure the total of all block rewards attributed to one vote account never exceeds its recorded `pending_delegator_rewards`, regardless of whether the underlying `stake` values used as numerators have drifted from `total_active_stake` due to partially-applied inflation rewards.

### Proof of Concept
Not independently executable from static analysis; the following code excerpt demonstrates the vulnerable arithmetic and the developers' own acknowledgment of the mismatch condition:

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
