### Title
Webhook signature verified against attacker-controlled organization while payload actions are dispatched using an unrelated repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate the HMAC signature with by reading `repository_owner`, itself parsed straight out of the *unverified* request body. The handlers that actually act on the payload (e.g. `StatusHandler`, `PushHandler`) look up the target `Stack`/`Commit` using a completely different, independently-controlled field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a caller who legitimately knows the webhook secret for *one* configured organization can forge a signature that is "valid" for that organization while directing the handler logic at a repository belonging to a *different* organization.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does: [1](#0-0) 
selecting `github_app = Shipit.github(organization: repository_owner)`, where `repository_owner` is: [2](#0-1) 
i.e. `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, both drawn from the raw, unauthenticated JSON body before the signature has been checked.

`Shipit.github(organization:)` looks up a per-organization config block (and thus a distinct `webhook_secret`) via `github_app_config(organization)`: [3](#0-2) 

Meanwhile, the actual event handlers resolve which `Stack`/`Repository`/`Commit` to mutate using a *different* payload field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

For example `StatusHandler` writes a CI status onto any `Commit` matching `params.sha` regardless of which organization's secret validated the request: [5](#0-4) 
and `PushHandler` triggers a GitHub sync for stacks matching `repository.full_name`/branch: [6](#0-5) 

Because the organization used for signature verification (`repository.owner.login`) and the organization/repository actually acted upon (`repository.full_name`) are two independent, attacker-supplied strings in the same unauthenticated JSON body, an attacker who controls a legitimate GitHub App installation on *their own* organization (`org-attacker`, with its own known `webhook_secret` configured in this Shipit instance) can craft a payload where:
- `repository.owner.login` (and/or top-level `organization.login`) = `org-attacker` → causes `verify_signature` to validate the HMAC using `org-attacker`'s webhook secret, which the attacker knows and can correctly sign.
- `repository.full_name` = `victim-org/victim-repo` → causes the handler to look up and act on a `Stack` belonging to a completely different organization that the attacker has no access to.

This breaks the trust binding: *the organization whose secret authenticated the request* ≠ *the repository the handler subsequently writes to*.

### Impact Explanation
The most severe reachable consequence is via `StatusHandler`: an attacker can forge a `state: "success"` commit status for an arbitrary commit belonging to a victim organization's stack, using only a webhook secret for their own unrelated org. If the victim stack has `continuous_deployment` enabled and its `shipit.yml` gates deploys on a specific CI `status.context`, this forged success status can satisfy the deploy trigger conditions and cause an **unauthorized deploy** of a commit that never actually passed CI — a Critical-tier impact per the rules (unauthorized deploy). It can also corrupt commit status history used for safety checks. `PushHandler`/`CheckSuiteHandler` extend the same primitive to trigger unwarranted `GithubSyncJob`/`RefreshCheckRunsJob` on victim stacks (state confusion, though these ultimately re-derive truth from the real GitHub API and are less directly exploitable for RCE/deploy-forging than the status path).

### Likelihood Explanation
This requires the target Shipit instance to be configured with the multi-organization GitHub config schema (`github: <org>: ...` with distinct `webhook_secret`s per org, as shown in `config/secrets.development.example.yml`), and the attacker must control (or have configured) one such organization's webhook endpoint/secret within the same instance — a realistic scenario for shared/multi-tenant Shipit deployments serving several GitHub orgs. No privileged Shipit session, `ApiClient` token, or `api_clients_secret` is needed; only knowledge of one org's `webhook_secret`, which the rules permit as an attacker capability (it's not `Shipit`'s master secret, but a config value scoped to one org the attacker legitimately administers).

### Recommendation
Bind signature verification to the same identity that is used to resolve the target resource. Concretely, after selecting `github_app` and verifying the HMAC, re-derive `repository_name`/`stacks` and assert that the resolved `Repository#owner` (or the handler's `repository.full_name`'s owner segment) matches the `repository_owner` value that was used to pick the `webhook_secret`. Reject (422) any request where these two identities diverge, instead of trusting two independently-forgeable fields from the same unauthenticated body for two different purposes.

### Proof of Concept
1. Configure Shipit (per `config/secrets.development.example.yml`) with two organizations, `org-attacker` and `org-victim`, each with its own `webhook_secret`.
2. Attacker knows `org-attacker`'s `webhook_secret` (they administer that org's GitHub App/webhook).
3. Attacker builds a `status` event payload:
```json
{
  "sha": "<commit sha of a real commit on org-victim/victim-repo tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "org-victim/victim-repo",
    "owner": { "login": "org-attacker" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_org_attacker, raw_body)` and POSTs it to `/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"org-attacker"` (from `repository.owner.login`), fetches `org-attacker`'s `webhook_secret`, and the signature checks out — request is accepted.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a "success" status on the commit belonging to `org-victim`'s stack, even though the request was never authenticated by `org-victim`'s webhook secret. [5](#0-4)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
