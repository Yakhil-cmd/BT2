### Title
Legacy `pattern:` rules for `file` events silently fail to block `Write` tool calls, letting attackers bypass block rules by using `Write` instead of `Edit` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` converts a legacy `pattern:` frontmatter field into a `Condition` whose `field` is hardcoded based solely on the rule's `event` type, unconditionally mapping `event: file` to `field: 'new_text'`. In `plugins/hookify/core/rule_engine.py`'s `_extract_field`, the `'new_text'`/`'new_string'` field only reads `tool_input['new_string']` (which exists only for `Edit`/`MultiEdit`) and has no fallback to `tool_input['content']` (used by `Write`). As a result, any hookify rule authored using the legacy `pattern:` shorthand for file-content blocking never matches `Write` tool calls, while an equivalent rule written with explicit `conditions: [{field: content, ...}]` correctly matches both `Write` and `Edit`.

### Finding Description
`Rule.from_dict` (`plugins/hookify/core/config_loader.py:44-84`) contains two parsing paths that are supposed to be semantically equivalent:
1. Explicit `conditions:` list → each item passed through `Condition.from_dict`, field name taken verbatim from user input.
2. Legacy `pattern:` shorthand → field name is *inferred* from `event`:
```python
event = frontmatter.get('event', 'all')
if event == 'bash':
    field = 'command'
elif event == 'file':
    field = 'new_text'
else:
    field = 'content'
```
`plugins/hookify/core/config_loader.py:61-67`

For `event: file` this always produces `field='new_text'`, regardless of which tool (`Write`, `Edit`, `MultiEdit`) will trigger the rule.

At enforcement time, `RuleEngine._extract_field` (`plugins/hookify/core/rule_engine.py:182-254`) resolves this field per tool:
```python
elif tool_name in ['Write', 'Edit']:
    if field == 'content':
        return tool_input.get('content') or tool_input.get('new_string', '')
    elif field == 'new_text' or field == 'new_string':
        return tool_input.get('new_string', '')   # no fallback to 'content'
```
`plugins/hookify/core/rule_engine.py:235-244`

`Write` tool calls populate `tool_input['content']`, not `tool_input['new_string']`. So when the rule's field is `'new_text'` (the legacy-inferred value), `_extract_field` returns `tool_input.get('new_string', '')` = `''` for `Write` calls, and `_check_condition` then evaluates the pattern against an empty string — normally causing the condition (and thus the whole rule, since `_rule_matches` requires all conditions to match) to fail to match. In `_rule_matches` (`plugins/hookify/core/rule_engine.py:96-125`) this means the rule silently never fires for `Write` operations.

In contrast, a rule authored with the explicit form (`conditions: [{field: content, operator: regex_match, pattern: ...}]`) hits the `field == 'content'` branch, which correctly reads `tool_input['content']` for `Write` and thus does match.

This is exactly the "legacy vs explicit" differential: two rule authoring styles that a user (or `/hookify rule creation` generation flow) would reasonably expect to produce identical protection produce materially different, and silently weaker, protection when written in the legacy shorthand for `event: file`.

### Impact Explanation
Any hookify "block" rule intended to prevent dangerous file writes (e.g., blocking writing secrets, blocking writing to sensitive paths, blocking injection of malicious code) that is authored using the simple/legacy `pattern:` frontmatter for `event: file` will never trigger for `Write` tool calls — only for `Edit`/`MultiEdit`. An attacker-influenced flow (e.g., a prompt-injected agent, or a repo-shipped rule file meant to look protective) can trivially evade the intended block simply by using `Write` to create/overwrite the target file instead of `Edit`. This is a silent security-control bypass: no error is raised, the operation is not blocked, and the user/operator has no indication the "block" rule is ineffective for an entire class of tool calls.

### Likelihood Explanation
This requires no privilege beyond authoring or influencing a hookify rule file (via `/hookify rule creation`, `/hookify` generation, or a repo-shipped `.claude/hookify.*.local.md` file) and then having Claude Code perform a `Write` operation instead of `Edit`. Both are ordinary, unprivileged actions within normal Claude Code usage; the divergence is deterministic and 100% reproducible given the code above — it does not depend on race conditions or exotic inputs, only on choosing the legacy `pattern:`/`event: file` form and the `Write` tool.

### Recommendation
Make the legacy-pattern-to-condition conversion tool-aware instead of event-only, or have `_extract_field` treat `'new_text'` the same as `'content'` (i.e., fall back to `tool_input.get('content')` when `new_string` is absent) so both legacy and explicit forms produce identical matching semantics across `Write`, `Edit`, and `MultiEdit`. Alternatively, expand the legacy conversion to emit multiple conditions (or an OR condition) covering all field aliases (`content`, `new_string`) for `event: file`, ensuring parity with explicit `conditions:` usage.

### Proof of Concept
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

# Legacy-style block rule: intended to block writing "SECRET_KEY" to any file
legacy_rule = Rule.from_dict(
    {"name": "block-secret", "enabled": True, "event": "file",
     "pattern": "SECRET_KEY", "action": "block"},
    message="Blocked!"
)

# Equivalent explicit-style rule
explicit_rule = Rule.from_dict(
    {"name": "block-secret-explicit", "enabled": True, "event": "file",
     "conditions": [{"field": "content", "operator": "regex_match", "pattern": "SECRET_KEY"}],
     "action": "block"},
    message="Blocked!"
)

engine = RuleEngine()

write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "/tmp/x.py", "content": "SECRET_KEY = 'abc'"}
}

# Expected (and required for invariant): both rules should block the same Write call
legacy_result = engine.evaluate_rules([legacy_rule], write_input)
explicit_result = engine.evaluate_rules([explicit_rule], write_input)

assert explicit_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
# BUG: legacy_result will be {} (no block), demonstrating the evasion
assert legacy_result == {}, "Legacy rule fails to block Write despite matching content"
```
This test demonstrates that the legacy `pattern:` form for `event: file` fails to enforce the identical block rule for `Write` tool calls that the explicit `conditions:` form correctly enforces, confirming the security-semantics divergence and evasion path.
