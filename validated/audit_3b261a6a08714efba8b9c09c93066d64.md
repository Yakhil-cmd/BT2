### Title
Global sha lookup in `StatusHandler#process` lets a status webhook from an unrelated GitHub repository be applied to another tenant's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) by `Commit.where(sha: params.sha)` with no scoping to the repository named in the webhook payload, unlike every other handler (`push`, `check_suite`, etc.) which use the base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`). Because `commits` are only unique per `(sha, stack_id)` and not globally, a `status` event that is legitimately signed for the attacker's own repository can be matched against a `Commit` row belonging to an entirely different stack whenever the sha values coincide (e.g. attacker forks or otherwise reproduces a commit that also exists in the victim's tracked branch history), letting the attacker inject a status/CI result into the victim's stack evaluation.

### Finding Description
The broken binding: the code should enforce `Status(payload).stack_id == Repository.from_github_repo_name(payload.repository.full_name).stacks.map(&:id)` (i.e., a status must only be attributed to a commit belonging to a stack whose repository matches the webhook's `repository.full_name`), but the actual binding realized in code is `Status(payload).stack_id == Commit.where(sha: payload.sha).stack_id`, which is independent of `payload.repository.full_name` entirely.

Code path:
- `app/controllers/shipit/webhooks_controller.rb` verifies the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e. against the organization named in the payload — this correctly proves the payload originates from a real webhook for that org/repo, but does not constrain *which commit sha* the event may reference. ` [1](#0-0) `
- `app/models/shipit/webhooks/handlers/handler.rb` provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)`, which other handlers (e.g. `check_suite_handler.rb`) correctly use to restrict matching to stacks that belong to the payload's repository. ` [2](#0-1) ` ` [3](#0-2) `
- `StatusHandler#process`, however, ignores this helper entirely and looks up commits purely by sha across the whole `commits` table: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. ` [4](#0-3) `
- `create_status_from_github!` then creates the `Status` using the *matched commit's own* `stack_id` (`statuses.replicate_from_github!(stack_id, github_status)`), so whichever stack happens to own a `Commit` with that sha receives the forged status. ` [5](#0-4) ` ` [6](#0-5) `
- The `commits` table's uniqueness constraint is only `(sha, stack_id)`, confirming multiple stacks can independently hold a `Commit` row with an identical sha (e.g., because they are forks/mirrors sharing history). ` [7](#0-6) `
- `MergeRequest#all_status_checks_passed?` then consumes `head.statuses_and_check_runs` (`statuses + check_runs`), which includes the forged `Status` row because it is attached to `commit_id` on the victim's own `Commit`. ` [8](#0-7) ` ` [9](#0-8) `
- `ProcessMergeRequestsJob` revalidates rejected/queued merge requests and, once `all_status_checks_passed?` flips true, calls `merge_request.merge!`, which performs the actual GitHub merge. ` [10](#0-9) ` ` [11](#0-10) `

Attacker exploit flow: the attacker (unprivileged, only controlling a repository whose commit history includes the same sha as the victim's PR head commit — trivially achievable by forking the victim's public repository, since forks preserve commit shas) posts a real `status` API call against that sha within their own repo. GitHub emits a legitimately signed `status` webhook naming the attacker's own repository (`payload.repository.full_name = attacker/fork`), which passes `verify_signature` because it is a genuine webhook for an org/repo the attacker controls. `StatusHandler#process` then finds the pre-existing `Commit` row for that same sha in the *victim's* stack (created earlier when the victim's PR was opened/refreshed) and attaches the forged `success` status to it, mislabeling it under the victim stack's `stack_id`.

Why existing guards fail: `verify_signature` only proves the webhook is authentic *for the attacker's own organization/repo* — it says nothing about which commit/stack the event should be allowed to affect. `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `requires :state`, etc.) validate shape only, not repository ownership of the sha. No model validation ties `Status#stack_id` to the repository named in the payload; `stack_id` is derived entirely from whatever `Commit` row the sha happens to match.

### Impact Explanation
An attacker who controls (or forks) a public repository whose history intersects with a victim's tracked stack can inject arbitrary CI status records (`success`, `failure`, `error`, `pending`) into the victim stack's evaluation for any commit sha they can reproduce, without any privilege in the victim's Shipit instance, GitHub org, team, or repository. Concretely this can flip `MergeRequest#all_status_checks_passed?` from false to true for a previously `ci_failing`-rejected pull request, causing `ProcessMergeRequestsJob` to invoke `merge_request.merge!` and merge unreviewed/unvetted code into the victim's protected branch — an unauthorized merge driven by a payload naming an unrelated repository. This matches "Critical: a payload for one repository mutating another's stack... or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions: the victim stack must already have a `Commit` row for the target sha (created when the PR/commit was first seen by Shipit, e.g., via push/PR sync), and the attacker must be able to produce a repository containing a commit with that exact sha (trivial for public repos via forking, since git commit shas are content-addressed and preserved across forks). No secrets, tokens, or elevated GitHub permissions are required — only the ability to set a commit status on a repository the attacker owns, which any GitHub user has for their own repos/forks. This is fully repeatable against any stack tracking a public/forkable repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks associated with the webhook's own repository, mirroring other handlers: use the `stacks` helper (`Repository.from_github_repo_name(repository_name)`) to restrict `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`, rather than matching by sha alone across all tenants.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from unrelated repository must not affect another stack's commit" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # different repository

  shared_sha = 'deadbeef' * 5

  # Victim already has a tracked Commit + rejected MergeRequest for this sha
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  merge_request = shipit_merge_requests(:shipit_pending)
  merge_request.update!(head: victim_commit)
  merge_request.reject!('ci_failing')
  merge_request.head.statuses.create!(stack: victim_stack, state: 'failure', context: 'ci/circle')

  assert_equal 'ci_failing', merge_request.rejection_reason
  refute_predicate merge_request, :all_status_checks_passed?

  # Attacker's repository (unrelated) also has a Commit with the same sha
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/circle',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repo_owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Equality that should hold but is broken: forged status stack_id must equal
  # attacker_stack.id only, never victim_stack.id
  victim_commit.reload
  assert_not_includes victim_commit.statuses.pluck(:stack_id), victim_stack.id, "victim stack should not receive attacker-forged status"

  merge_request.reload
  refute_predicate merge_request, :all_status_checks_passed?
end
```
This test currently fails on the vulnerable code (the forged status is attached with `stack_id: victim_stack.id`, flipping `all_status_checks_passed?` to true), demonstrating the cross-repository status forgery.

      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

        merge_message,
        sha: head.sha,

      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
