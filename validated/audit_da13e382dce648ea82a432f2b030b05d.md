### Title
`Shipit::Webhooks::Handlers::StatusHandler#process` scopes CI status updates by `sha` alone, allowing cross-repository status corruption - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` with no repository/stack filter and calls `create_status_from_github!` on every match, while every other handler (`check_suite_handler.rb`, `push_handler.rb`, PR handlers) uses the base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) to scope work to the repository named in the webhook payload. Because git commit SHAs are content-addressed and identical commits can exist verbatim in unrelated repositories (e.g., via fork), an attacker controlling a repository with a valid GitHub App/webhook installation can send a signed `status` webhook naming their own repository, with `state` set to whatever they want (`success`, `failure`, `error`, `pending`), and have it applied to a `Commit` row belonging to a completely different tenant's `Stack`.

### Finding Description
The broken binding: `payload['repository']['full_name']` (the repository the webhook signature was verified against) should equal `commit.stack.repository.full_name` for every `Commit` mutated by the request, but in `StatusHandler#process` this equality is never checked.

Code path:
- `Shipit::WebhooksController#create` dispatches by event type only, verifying the HMAC signature for `repository_owner` derived from the payload (`app/controllers/shipit/webhooks_controller.rb:24-49`). This only proves the request came from a GitHub App installed on *some* repository the attacker owns/controls — it says nothing about which `Commit`/`Stack` may be touched.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
  ```
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This is a global, cross-tenant query with no `stack_id`/repository filter, unlike the `Handler` base class's own `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), which every other handler uses to scope to `Repository.from_github_repo_name(repository_name)&.stacks`.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)`, using the *matched commit's own* `stack_id`, not anything derived from the attacker's payload — so the new `Status` row is attributed to whichever stack the colliding-sha commit actually belongs to.
- `Status#state` accepts any of `%w[pending success failure error]` (`app/models/shipit/status.rb:8-16`), and `Commit#state`/`#deployable?`/`#blocked?` are driven directly by the latest status.

Attacker flow: fork or otherwise obtain a repository containing a commit with the same SHA as a commit already tracked in a victim `Stack` (trivial via fork, since SHA is content-derived and independent of remote/owner), install/keep a legitimate webhook on that attacker-controlled repository, then send (or have GitHub send, by pushing a commit and having any CI report a status, or by crafting the POST directly if the attacker can get a validly-signed request from their own app installation) a `status` event with `state: 'failure'` or `state: 'success'` and the colliding `sha`. `verify_signature` passes because the signature matches the attacker's own repository/app; `StatusHandler#process` then updates the victim's `Commit` regardless.

None of the listed guards catch this: `verify_signature` and `drop_unhandled_event` operate at the event/repository-owner level, not at the individual `Commit` row level; the `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/etc., not ownership; there is no `require_permission!`/`stacks` scoping call inside `StatusHandler#process` (unlike sibling handlers).

### Impact Explanation
A single POST to `/webhooks` can flip `Commit#state` for a commit belonging to a repository the attacker does not own, in either direction:
- `state: 'failure'` on a currently green commit can make `Commit#blocked?`/`deployable?` false for a victim stack, blocking releases (griefing / denial of legitimate deploys).
- `state: 'success'` on a currently red/pending commit can make it `deployable?`, potentially causing an unauthorized deploy of a commit that hasn't actually passed CI in the target repository.

This is a cross-repository state write for a repository that never authenticated the mutating request for that specific `Commit`, matching the Critical category ("a payload for one repository mutating another's stack, commit ... or an unauthorized deploy"). It is repeatable against any commit whose SHA the attacker can reproduce in a repo they control (trivial for forks of public repos, or any repo sharing history/cherry-picks).

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository with a working webhook/App installation pointed at the Shipit instance (something any repo owner can set up if the Shipit instance's GitHub App can be installed broadly, or simply craft the payload with a valid signature for their own org since `Shipit.github(organization: repository_owner)` is keyed by the attacker's own organization), and a commit whose SHA collides with one already ingested into a victim `Stack`. SHA collision across repos is not a cryptographic hash collision — it only requires identical commit content/metadata, which is routine for forks, cherry-picks, or shared upstream commits. No Shipit session, API token, or GitHub secret is needed. Cost is low and the action is repeatable per targeted commit.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring the base `Handler#stacks` helper used elsewhere, e.g. restrict the query to `stacks.flat_map(&:commits)` or add `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: stacks... })` so only commits belonging to the repository named in the verified payload are updated.

### Proof of Concept
minitest (outside `test/**` restriction is for citing existing files, but a proof would live in `test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
```ruby
%w[success failure error pending].each do |state|
  test "status webhook with colliding sha mutates cross-repo commit (state=#{state})" do
    stack_a = shipit_stacks(:shipit)               # victim tenant
    stack_b = create_stack_with_own_repository      # attacker-owned tenant
    sha = 'deadbeef' * 5

    commit_a = stack_a.commits.create!(sha: sha, ...)
    commit_b = stack_b.commits.create!(sha: sha, ...)

    payload = {
      'sha' => sha,
      'state' => state,
      'repository' => { 'full_name' => stack_b.repository.full_name, 'owner' => { 'login' => stack_b.repository.owner } },
      'branches' => [{ 'name' => stack_b.branch }],
    }

    Shipit::Webhooks::Handlers::StatusHandler.call(payload)

    assert_equal state, commit_a.reload.state   # <-- victim commit changed by attacker's payload; should be unchanged
    assert_equal state, commit_b.reload.state
  end
end
```
Assertion of the broken binding: `payload['repository']['full_name'] == stack_b.repository.full_name` (true, attacker's own repo) while the mutated record is `commit_a.stack.repository.full_name == stack_a.repository.full_name` (a different repo) — the two sides diverge, proving the cross-tenant write.
```ruby
# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
