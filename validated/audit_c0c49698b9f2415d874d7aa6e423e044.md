### Title
Cross-organization webhook signature confusion allows one authorized GitHub organization to trigger sync/deploy actions on another organization's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to validate a webhook against using the `repository.owner.login` (or `organization.login`) field of the *same attacker-supplied JSON payload* that is later used, via `repository.full_name`, to resolve the `Repository`/`Stack` that the webhook event acts on. These two fields are never cross-checked against each other.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body and fetches the corresponding per-organization `github_app`/`webhook_secret` to validate `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

Once the signature is accepted, the event is dispatched to a `Handler` whose `stacks`/`repository` lookup uses an entirely independent field of the same JSON body, `repository.full_name`, with no re-validation that its owner segment matches the organization whose secret validated the signature: [3](#0-2) [4](#0-3) 

Because the webhook secret is per-organization (each org configures its own `webhook_secret` in `Shipit.github(organization:)` config, e.g. `secrets.development.shopify.yml`) and the whole request body is attacker-controlled JSON signed with that org's own secret, an entity that legitimately knows/controls organization A's `webhook_secret` (i.e., an admin of org A's GitHub webhook configuration) can craft a payload where `repository.owner.login == "orgA"` (so `verify_signature` fetches and validates against orgA's secret) but `repository.full_name == "orgB/private-repo"` (a completely different, unrelated organization/repository tracked by the same Shipit instance). The signature check passes because it only binds to `repository_owner`, not to `repository.full_name`.

This breaks the intended equality: **the organization that authenticated the request (via the webhook secret) must equal the organization owning the repository that is acted upon.** Here, `repository_owner` (used for authentication) and `repository.full_name`'s owner (used for the actual write/lookup) can diverge, exactly analogous to `amount` vs `msg.value` in the referenced report — one value is checked/authenticated while a different value is what is actually acted upon. [5](#0-4) 

### Impact Explanation
With a forged `push` event (`ref`, `after`, and a `repository.full_name` pointing at org B's stack), `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` on a stack that belongs to an unrelated organization/repository the attacker (org A) has no GitHub write access to: [6](#0-5) 

If that target stack has `continuous_deployment` enabled, syncing new commit state can lead to an unauthorized deploy being triggered against org B's infrastructure, purely from a request authenticated with org A's own webhook secret. Other handlers (e.g. `pull_request` opened/labeled handlers that provision or archive review stacks, or state/status handlers) are similarly reachable via the same `repository.full_name`-driven lookup, all authenticated only against `repository.owner.login`. This is a cross-repository/cross-organization write triggered without the attacker ever holding credentials for, or write access to, the targeted organization/repository — matching the "unauthorized deploy" / "cross-repository writes" High/Critical impact bar.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` of at least one organization already configured in the Shipit instance (a realistic scenario in multi-tenant deployments where each customer/org self-configures its GitHub webhook with a secret it was given) — this is not equivalent to holding a Shipit `ApiClient` token, GitHub App private key, or repository write access to the *target* repo, so it isn't excluded by the out-of-scope rules. Given knowledge of any one valid webhook secret, exploitation is a simple, deterministic HTTP POST with a crafted JSON body and a computed HMAC signature — no race conditions, no fuzzing, no additional bypass needed.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook secret (`repository_owner`) matches the owner segment of `repository.full_name` used by handlers to resolve stacks, rejecting (422) the payload otherwise. Alternatively, look up the `Repository`/`Stack` first and verify the signature using the secret associated with that specific repository's known owner, rather than trusting an attacker-suppliable field to select the verification key.

### Proof of Concept
1. Attacker administers GitHub organization `orgA`, which has a Shipit webhook configured with secret `S_A` (as set in `Shipit.github` config for `orgA`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/private-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "orgA"`, fetches `orgA`'s `github_app`, and successfully verifies the signature against `S_A` (`app/controllers/shipit/webhooks_controller.rb:24-38`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("orgB/private-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) — an org the attacker never authenticated for — and calls `stack.sync_github(expected_head_sha:)` on it (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), potentially cascading into an unauthorized deploy if `continuous_deployment` is enabled on that stack.

Note: I was unable to directly inspect `app/models/shipit/stack.rb#sync_github` and `app/jobs/shipit/github_sync_job.rb` internals in full within the available context window to confirm the exact downstream deploy-trigger mechanics beyond what test files (`test/jobs/github_sync_job_test.rb`) and the `push_handler.rb`/`stack.rb` snippets already reviewed indicate; a Devin session with full file access would be needed to fully trace the continuous-deployment cascade if further confirmation is required.
