### Title
Unauthenticated `membership` webhook can write arbitrary team membership into `Shipit.github_teams` authorization, bypassing the org-team access gate - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
The LoopFi finding is a class of bug where a security invariant (min-shares) is enforced only on one side of a state transition while the state that actually gets persisted (share balance) is attacker-influenced. The structural analog here is a binding that Shipit is supposed to enforce end-to-end but only enforces conditionally: "the webhook event was cryptographically verified" versus "the team-membership rows that `Shipit.github_teams` authorization is computed from were actually derived from a verified GitHub event." `GithubApp#verify_webhook_signature` silently treats "no secret configured" as "signature valid," and `MembershipHandler` then writes attacker-supplied `team.id`/`member.login` straight into the `Team`/`Membership` tables that gate application access.

### Finding Description
`WebhooksController#verify_signature` resolves a GitHub App config from the payload and asks it to check `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

The actual verification is: [3](#0-2) 

`return true unless webhook_secret` means that for any organization configuration where `webhook_secret` is left blank — which is exactly the state shipped in every reference config (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `template.rb`, and documented in `docs/setup.md` as "(optional)") — the signature check is a no-op and `head(422)` is never triggered. This is not a case of "requiring the webhook secret" to exploit; it is the opposite — the vulnerability is that its *absence* removes all authentication on `/webhooks`.

Once past `verify_signature`, `Shipit::Webhooks.for_event('membership')` dispatches the fully attacker-controlled JSON body to `MembershipHandler`: [4](#0-3) 

This handler:
- Resolves/creates a `Team` keyed only by the attacker-supplied `team.id` (`params.team.id`), with no cross-check against a real GitHub org/team the app is actually installed on.
- Resolves/creates a `User` for the attacker-supplied `member.login` via `User.find_or_create_by_login!`.
- Adds that `User` to the `Team` when `action == 'added'`.

The application's entire access-control gate is: [5](#0-4) [6](#0-5) 

`authorized?` trusts local `Membership`/`Team` rows exclusively — it never re-verifies against GitHub at login time beyond the OAuth identity itself. So the binding that must hold is: *"a `Team ⟷ User` row exists in Shipit's DB" ⇒ "that membership was actually confirmed by a signature-verified GitHub `membership` event for a real installation."* The optional-secret behavior in `verify_webhook_signature` breaks that equality: an unauthenticated network attacker can synthesize the row without any real GitHub team membership and without any Shipit credential, ApiClient token, or GitHub App private key.

### Impact Explanation
If the attacker learns (or brute-forces, since GitHub team IDs are small sequential integers, often visible via the GitHub API for public/viewable orgs) the `github_id` of one of the teams listed in `Shipit.github_teams`, they can:
1. POST a forged `membership` event (`action: 'added'`, real team `id`, `member.login: <attacker's own GitHub login>`) to `/webhooks`.
2. `MembershipHandler` finds the existing authorized `Team` row (matching `github_id`) and adds the attacker's `User` as a member — persisted entirely in Shipit's own database.
3. The attacker logs in normally via `/github/auth/github` (a completely legitimate OAuth flow using their own real GitHub account) — `GithubAuthenticationController#sign_in_github` creates/finds their `User` record.
4. `current_user.authorized?` now returns `true` because `teams.where(id: Shipit.github_teams.map(&:id)).exists?` matches the forged `Membership` row.

This is a full authentication-bypass into `Shipit.github_teams` authorization (explicitly listed as a valid High-impact category), granting the attacker complete UI/API access to stacks, deploys, rollbacks and API-client management — without ever holding real GitHub team membership, a Shipit session, an `ApiClient` token, `webhook_secret`, or the GitHub App private key.

### Likelihood Explanation
Likelihood is high wherever an operator follows the shipped defaults/documentation, since `webhook_secret` is explicitly optional and blank in every example/template config in this engine. No privileged access, TLS interception, or social engineering is required — only a single unauthenticated HTTP POST plus a normal, legitimate OAuth login by the attacker's own GitHub account.

### Recommendation
- Make `webhook_secret` mandatory in `GithubApp#verify_webhook_signature` (`app/controllers/shipit/webhooks_controller.rb` / `lib/shipit/github_app.rb`) — fail closed instead of `return true unless webhook_secret`.
- In `MembershipHandler`, cross-validate that the event's `organization.login` matches an org Shipit is actually configured/installed for before mutating `Team`/`Membership`, and prefer confirming membership via an authenticated GitHub API call rather than trusting the raw webhook body alone for authorization-relevant state.

### Proof of Concept
1. Deploy Shipit using the documented/shipped config where `github.webhook_secret` is left blank (the default in `config/secrets.development.example.yml` / `template.rb`).
2. Attacker discovers (or guesses) the `github_id` of a team referenced in `Shipit.github_teams` (e.g., via GitHub's public team API, if the org allows it, or brute force of small integers).
3. Attacker sends:
```
POST /webhooks
X-Github-Event: membership
{
  "action": "added",
  "team": {"id": <real_required_team_github_id>, "name": "x", "slug": "x", "url": "https://example.com"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-github-login"}
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank.
4. `MembershipHandler#process` creates/updates the `Team` row and adds a `Membership` for a `User` matching `attacker-github-login`.
5. Attacker completes a normal GitHub OAuth login on Shipit with `attacker-github-login`.
6. `Shipit::Authentication#force_github_authentication` → `current_user.authorized?` now returns `true`, granting full application access despite never having real GitHub team membership.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
```
