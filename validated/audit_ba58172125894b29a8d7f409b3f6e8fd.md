### Title
Epoch-boundary reward-distribution partition count is capped independent of attacker-created stake account count, causing unbounded per-block work - ([File: runtime/src/bank/partitioned_epoch_rewards/mod.rs])

### Summary
The number of reward-distribution blocks (`num_partitions`) is capped at 10% of `slots_per_epoch` in `get_reward_distribution_num_blocks`, but the actual per-partition workload processed in `store_stake_accounts_in_partition` is determined by `hash_rewards_into_partitions`, which simply hashes every rewarded stake account into one of the fixed `num_partitions` buckets. Because the bucket count is capped while the total stake-account count is not, an attacker who delegates a very large number of low-value stake accounts can make each per-block bucket arbitrarily large, defeating the "bounded per-block work" invariant that `stake_account_stores_per_block`/`MAX_PARTITIONED_REWARDS_PER_BLOCK` is intended to enforce.

### Finding Description
`get_reward_distribution_num_blocks` computes the intended number of blocks as `total_stake_accounts.div_ceil(stake_account_stores_per_block)`, then clamps this to `[1, slots_per_epoch / 10]`: [1](#0-0) 

This value (`num_partitions`) is stored into the `EpochRewards` sysvar via `create_epoch_rewards_sysvar` in `begin_partitioned_rewards`: [2](#0-1) 

At distribution time, `distribute_partitioned_epoch_rewards` uses `epoch_rewards_sysvar.num_partitions` to call `hash_rewards_into_partitions`, which deterministically hashes *every* rewarded stake pubkey into one of exactly `num_partitions` buckets — there is no secondary cap on how many accounts land in a single bucket: [3](#0-2) [4](#0-3) 

Each subsequent block then processes exactly one full bucket in `store_stake_accounts_in_partition`, which iterates over every index in `partition_rewards.partition_indices[partition_index]` and performs a `build_updated_stake_reward` + `store_accounts` call for each — with no per-block truncation or additional chunking of an oversized bucket: [5](#0-4) 

The `10% of slots_per_epoch` clamp in `get_reward_distribution_num_blocks` was intended as an upper bound on the *distribution interval length*, but it also caps `num_partitions` from growing further even when `total_stake_accounts` continues to increase without bound. Since `stake_account_stores_per_block` (`MAX_PARTITIONED_REWARDS_PER_BLOCK` = 4096, see `accounts-db/src/partitioned_rewards.rs`) is only used to *compute the divisor* for the initial (pre-clamp) partition count, once `total_stake_accounts / stake_account_stores_per_block` exceeds `slots_per_epoch / 10`, additional stake accounts are absorbed into the same fixed number of partitions rather than causing more blocks to be scheduled. This means average (and worst-case, per-bucket) accounts-per-block grows linearly with `total_stake_accounts` beyond that threshold, with no cap: [6](#0-5) 

The existing tests only validate the clamp of the *block count*, not the resulting per-block workload size, e.g. `test_get_reward_distribution_num_blocks_cap` confirms `num_blocks` saturates at 3 for a 32-slot epoch regardless of how many multiples of `stake_account_stores_per_block` are supplied, but never checks how large each resulting `hash_rewards_into_partitions` bucket becomes: [7](#0-6) 

An unprivileged attacker can create arbitrarily many stake accounts at (or near) the protocol minimum delegation, delegate them all to a single (or attacker-owned) vote account, and let them activate before the epoch boundary. Once they become part of `stake_delegations` used in `calculate_stake_rewards_and_commissions`, they enter `PartitionedStakeRewards`, and `total_stake_accounts` (via `rewards.num_rewards()`) grows with the number of attacker accounts, without any protocol-level cap on the number of stake accounts that can exist and receive a nonzero/zero reward record for a given epoch.

### Impact Explanation
This falls under the in-scope "epoch-boundary divergence/halt risk (liveness)" category. Since `num_partitions` is deterministically computed by all validators from the same on-chain state (total delegated stake accounts, `slots_per_epoch`, `stake_account_stores_per_block`), all honest nodes will compute the same (capped) partition count and thus the same oversized per-block bucket sizes — so it does not cause consensus divergence by itself, but it does cause every node in the cluster to do unboundedly more work in `store_stake_accounts_in_partition` at each of the (capped) number of reward-distribution blocks, directly increasing per-block time at the epoch boundary in proportion to the number of attacker-created stake accounts. If the workload for a single distribution block grows large enough, it risks exceeding the block's `CLUSTER_SLOT_TIME_TARGET`, causing slow block production/verification and potential liveness degradation across the whole network at every epoch boundary going forward (since the extra stake accounts persist once delegated, unless deactivated).

### Likelihood Explanation
Feasible for any funded, unprivileged actor: creating and delegating a stake account only requires funding a system account, issuing `Initialize`/`DelegateStake` (or equivalent CPI) instructions, and paying the minimum delegation + rent-exempt reserve for each account (`stake_utils::get_minimum_delegation` — not fully explored due to index limits, but it is a small, fixed lamport amount, not scaling with cluster size). The number of accounts needed to trigger a materially larger-than-intended per-block bucket only needs to exceed `stake_account_stores_per_block * (slots_per_epoch / 10)`, e.g., with the default `MAX_PARTITIONED_REWARDS_PER_BLOCK = 4096` and a 432,000-slot epoch, the cap is `4096 * 43200 ≈ 177 million` accounts before hitting the block-count clamp — a very large but not unbounded number requiring substantial (though bounded and public) capital outlay; this raises the cost bar but does not eliminate the finding, since the invariant claimed ("epoch-boundary work bounded independent of attacker-controlled account count") is architecturally false regardless of how expensive it is to reach the threshold. Repeatable every epoch as long as the attacker maintains the delegations.

### Recommendation
Decouple the intended per-block store limit from the block-count clamp: either (a) keep `num_partitions` uncapped by `slots_per_epoch/10` and instead cap `stake_account_stores_per_block` as a hard per-block ceiling enforced inside `store_stake_accounts_in_partition` by processing at most `stake_account_stores_per_block` entries per block (spilling any excess into additional, later blocks even beyond the `10%` epoch-length soft cap), or (b) impose a network-level maximum on the total number of live delegated stake accounts (or accounts per vote account) so `total_stake_accounts` itself is provably bounded, matching the SIMD reward partitioning design intent that per-block store operations remain ≤ `stake_account_stores_per_block` regardless of total participation.

### Proof of Concept
```rust
// runtime/src/bank/partitioned_epoch_rewards/mod.rs (test module)
#[test]
fn test_partition_size_grows_unbounded_with_stake_account_count() {
    // Fix a small epoch and small stores_per_block, as in
    // test_get_reward_distribution_num_blocks_cap.
    let slots_per_epoch = 32u64;
    let stake_account_stores_per_block = 10u64;
    let max_blocks = (slots_per_epoch / 10).max(1); // = 3

    // Case 1: accounts near the clamp threshold
    let n1 = max_blocks * stake_account_stores_per_block; // 30
    let rewards1 = (0..n1)
        .map(|_| Some(PartitionedStakeReward::new_random()))
        .collect::<PartitionedStakeRewards>();
    let num_blocks1 = /* bank with above config */
        bank.get_reward_distribution_num_blocks(&rewards1);
    assert_eq!(num_blocks1, max_blocks);
    let avg_per_block1 = n1 as f64 / num_blocks1 as f64; // ~10, matches intended cap

    // Case 2: attacker creates 1000x more stake accounts, delegated to one vote account
    let n2 = n1 * 1000; // 30,000
    let rewards2 = (0..n2)
        .map(|_| Some(PartitionedStakeReward::new_random()))
        .collect::<PartitionedStakeRewards>();
    let num_blocks2 = bank.get_reward_distribution_num_blocks(&rewards2);
    assert_eq!(num_blocks2, max_blocks); // still capped at 3 blocks!

    let avg_per_block2 = n2 as f64 / num_blocks2 as f64; // ~10,000 per block

    // Assert that per-block workload is NOT bounded/capped despite the
    // per-block store limit (stake_account_stores_per_block) being fixed.
    assert!(
        avg_per_block2 > 100.0 * avg_per_block1,
        "per-block reward-store workload should stay bounded near \
         stake_account_stores_per_block ({stake_account_stores_per_block}), \
         but grew to {avg_per_block2} once total account count exceeded the \
         epoch-length block-count clamp, violating the bounded-work invariant"
    );
}
```
Expected result: the assertion fails today's design expectation (per-block work should stay ~`stake_account_stores_per_block`), demonstrating that `avg_per_block2` scales linearly with attacker-controlled `n2` instead of remaining capped, confirming the invariant violation. A full integration-level PoC would additionally measure wall-clock/`store_stake_accounts_us` in `store_stake_accounts_in_partition` for a bucket of ~10,000+ accounts versus the baseline ~10-account bucket to show the concrete compute-time blowup at distribution time.

```rust
    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
```

```rust
    fn store_stake_accounts_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) -> DistributionResults {
        let feature_snapshot = self.feature_set.snapshot();
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;

        let mut stake_reward_lamports_minted = 0;
        let mut stake_reward_lamports_burned = 0;
        let mut block_reward_lamports_distributed = 0;
        let mut block_reward_lamports_burned = 0;
        let indices = partition_rewards
            .partition_indices
            .get(partition_index as usize)
            .unwrap_or_else(|| {
                panic!(
                    "partition index out of bound: {partition_index} >= {}",
                    partition_rewards.partition_indices.len()
                )
            });
        let mut updated_stake_rewards = Vec::with_capacity(indices.len());
        let stakes_cache = self.stakes_cache.stakes();
        let stakes_cache_accounts = stakes_cache.stake_delegations();
        let stake_history = stakes_cache.history();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let rent = &self.rent_collector.rent;
        for index in indices {
            let partitioned_stake_reward = partition_rewards
                .all_stake_rewards
                .get(*index)
                .unwrap_or_else(|| {
                    panic!(
                        "partition reward out of bound: {index} >= {}",
                        partition_rewards.all_stake_rewards.total_len()
                    )
                })
                .as_ref()
                .unwrap_or_else(|| {
                    panic!("partition reward {index} is empty");
                });
            let stake_pubkey = partitioned_stake_reward.stake_pubkey;
            let stake_reward_amount = partitioned_stake_reward.inflation.stake_reward;
            let block_reward_amount = partitioned_stake_reward.block_reward;

            match Self::build_updated_stake_reward(
                self.epoch,
                stake_history,
                new_warmup_cooldown_rate_epoch,
                stakes_cache_accounts,
                partitioned_stake_reward,
                rent,
                adjust_delegations_for_rent,
                use_fixed_point_stake_math,
            ) {
                Ok(stake_reward) => {
                    stake_reward_lamports_minted += stake_reward_amount;
                    block_reward_lamports_distributed += block_reward_amount;
                    updated_stake_rewards.push(stake_reward);
                }
                Err(err) => {
                    error!(
                        "bank::distribution::store_stake_accounts_in_partition() failed for \
                         {stake_pubkey}, {stake_reward_amount} lamports burned: {err:?}"
                    );
                    stake_reward_lamports_burned += stake_reward_amount;
                    block_reward_lamports_burned += block_reward_amount;
                }
            }
        }
        drop(stakes_cache);
        self.store_accounts(
            (self.slot(), &updated_stake_rewards[..]),
            // Reuse the rewards calculation thread pool to parallelize
            // loading the previous versions of the stake accounts.
            Some(crate::bank::rewards_calculation_thread_pool()),
        );
```

```rust
pub(in crate::bank::partitioned_epoch_rewards) fn hash_rewards_into_partitions(
    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.
        // This prevents us from re-hashing the seed each time.
        // The clone is explicit (as opposed to an implicit copy) so it is clear this is intended.
        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}
```
