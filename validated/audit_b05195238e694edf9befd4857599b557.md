### Title
Webhook signature verification can be silently bypassed when a configured GitHub App has no `webhook_secret`, allowing cross-repository forged events - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate an inbound webhook against by reading an **unauthenticated** field straight out of the not-yet-verified JSON body, then delegates the actual pass/fail decision to `GitHubApp#verify_webhook_signature`, which unconditionally returns `true` whenever that app's `webhook_secret` is unset. Since the field used to *pick the verifying key* (`repository.owner.login` / `organization.login`) is independent from the field every downstream handler uses to decide *which repository/stack to mutate* (`repository.full_name`), an attacker can pick an organization whose app has no configured secret to make verification a no-op, then supply a `repository.full_name` pointing at an arbitrary tracked repository to drive pushes, statuses, check-runs, pull-request and merge events against it.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` runs `verify_signature` as a `before_action`: [1](#0-0) 

`repository_owner` is derived purely from the raw, unauthenticated request body: [2](#0-1) 

That attacker-controlled string is used to select which `GitHubApp` config (`app_id`, `webhook_secret`, etc.) performs verification: [3](#0-2) 

`GitHubApp#verify_webhook_signature` then short-circuits to `true` whenever `webhook_secret` is blank for the selected organization — i.e. HMAC verification is entirely skipped: [4](#0-3) 

Both the multi-org secrets schema and the single-org one document `webhook_secret` as an optional value that defaults to `nil`: [5](#0-4) [6](#0-5) 

Meanwhile every webhook handler (push/status/pull_request/etc.) resolves the target `Stack`/`Repository` using a *different* payload field, `repository.full_name`, not the `repository.owner.login` used for signature selection: [7](#0-6) [8](#0-7) 

Because these two fields are independently attacker-controlled inside the same unauthenticated JSON body, and because the field that selects the verifying secret can be steered toward *any* org configured without a `webhook_secret` (a state the documented config templates present as the default/valid value), the equality that must hold — "organization whose secret authenticated this delivery" == "repository the handler subsequently writes to" — is broken. `check_if_ping`/`drop_unhandled_event` do not perform any additional binding, and `create` dispatches the full, forged payload straight to handlers: [9](#0-8) 

### Impact Explanation
An unauthenticated attacker who can reach the `/github/webhooks` endpoint (an unprivileged, external caller — no Shipit session, API token, or repository access required) can:
- Forge `push` events to trigger `GithubSyncJob` for any tracked repository/stack, seeding attacker-chosen commits.
- Forge `status`/`check_suite` events to mark arbitrary commits as CI-green, defeating `ci.require` gating used before deploys/merges.
- Forge `pull_request`/`membership`/`merge` events to manipulate merge-queue state, review-stack provisioning, or team membership for repositories the attacker does not control.

Combined with `continuous_deployment` / merge-queue automation, this can escalate to unauthorized deploys or merges on a repository/stack the attacker has no legitimate access to — satisfying the "cross-repository writes" / "unauthorized deploy, rollback or merge" Critical bar, without needing any Shipit session, API token, webhook secret, or GitHub App key.

### Likelihood Explanation
Any Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration) where at least one configured organization has not set `webhook_secret` (shown as the default `# nil` in the shipped example/config templates) is exploitable by a completely unauthenticated network attacker who only needs to know that organization's name (which is often public) and any tracked target repository's `owner/name`. No secret material is required to exploit — only knowledge of an org name with a blank secret, which the bundled example configs actively demonstrate as an acceptable value.

### Recommendation
- Make `verify_webhook_signature` fail closed (return `false`, not `true`) when `webhook_secret` is blank, or require `webhook_secret` to be present for every configured GitHub App at boot.
- Do not select the verifying organization/app from unauthenticated payload content before signature verification; instead, bind the webhook delivery to a specific configured app (e.g., via a per-app endpoint/token) so the same identity is used both to verify and to authorize the mutation.
- After verification, cross-check that the organization used for signature verification matches the owner embedded in `repository.full_name` before handlers act on it.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgWithSecret` (has `webhook_secret`) and `OrgNoSecret` (no `webhook_secret`, as shown in the shipped example config), and track a repository `OrgWithSecret/victim-repo` as a stack.
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or an arbitrary one), and a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgWithSecret/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `repository_owner` resolves to `"OrgNoSecret"`; `Shipit.github(organization: "OrgNoSecret")` returns an app with `webhook_secret` nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the (invalid) signature header.
4. The `push` handler processes `repository.full_name` = `OrgWithSecret/victim-repo`, enqueuing `GithubSyncJob` for the victim stack with attacker-supplied `after` sha — despite the request never having been genuinely authenticated for `OrgWithSecret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
