### Title
Cross-organization stack mutation via unbound `repository_owner`/`repository.full_name` fields in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`verify_signature` selects which org's `webhook_secret` to validate against using `repository_owner`, which falls back to the top-level `organization.login` field when `repository.owner.login` is absent from the payload. `UnlabeledHandler`'s `params` schema (`app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb`) never requires `repository.owner`, so an attacker can supply `repository.full_name` naming one repo while the signature is verified against a completely different, attacker-controlled organization named in `organization.login`.

### Finding Description
The broken binding: `organization_used_for_signature (params.dig('organization','login'))` should equal `organization_owning(params.dig('repository','full_name'))`, but nothing in the code enforces this equality.

`repository_owner` at [1](#0-0)  falls back to `params.dig('organization', 'login')` whenever `repository.owner.login` is missing. `verify_signature` then does `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature` against that org's configured secret [2](#0-1) . Separately, `UnlabeledHandler#repository` resolves the mutated repository purely from `params.repository.full_name`, and the schema never requires `repository.owner` [3](#0-2) [4](#0-3) . `handle` then calls `stack.archive!`/`stack.unarchive!` on whatever stack matches that `full_name` [5](#0-4) .

Root cause: `verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is blank/unset [6](#0-5) . In a multi-org Shipit deployment (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), if any configured org lacks a `webhook_secret`, an attacker who knows (or omits) that org's name can craft a payload with `organization: {login: 'unsecured-org'}` and `repository: {full_name: 'victim-org/repo'}` (omitting `repository.owner`). `verify_signature` resolves `Shipit.github(organization: 'unsecured-org')`, finds no secret, and accepts the request regardless of signature. The handler then archives/unarchives the `victim-org/repo` stack — a mutation for a repository that never authenticated the request.

None of the existing guards close this gap: `drop_unhandled_event` only checks event-type registration; the `ExplicitParameters` schema only validates types/presence, never organization equality; `force_github_authentication`/`User#authorized?`/`require_permission!` are session/API-token guards not exercised on the unauthenticated `/webhooks` endpoint; `Repository`/`Stack` model validations validate format, not request provenance.

### Impact Explanation
An unprivileged attacker can flip `archive?`/`unarchive?` state (which controls review-stack provisioning) on any repository configured in Shipit, without ever authenticating as that repository's org. This is a cross-tenant mutation triggered by a payload that was never validated for the target repository, matching the "payload for one repository mutating another's stack" Critical category. Blast radius depends on Shipit's org configuration: any repo whose owning org has a webhook secret is safe from this specific vector as the source org (since a correctly-secreted org check would fail), but the *victim* repository can be any repo whose `full_name` the attacker knows, as long as some org in Shipit's config lacks a secret to piggyback signature verification through.

### Likelihood Explanation
Exploitability is conditional, not universal: it requires (a) Shipit configured with multiple GitHub orgs (the multi-org schema keyed by org name), and (b) at least one of those configured orgs having no `webhook_secret` set. Single-org deployments with a `webhook_secret` configured are not exploitable this way, since `repository_owner` resolves to the one and only org key regardless of payload content, and that org's secret would be checked. This is a real, documented supported configuration (nil `webhook_secret` is explicitly shown as valid in `secrets.development.example.yml`/`secrets_double_github_app.yml`), but its presence in any given production deployment cannot be confirmed from this codebase alone — it is an operator configuration choice, not a guaranteed default.

### Recommendation
In `Shipit::WebhooksController`, do not let `repository_owner` silently fall back to an unrelated `organization.login` object when `repository.owner.login` is present in a different form; more importantly, verify that the organization used to select the webhook secret matches the org that actually owns `repository.full_name` before invoking any handler, e.g. re-derive the org from `full_name.split('/').first` and require it to equal `repository_owner`, rejecting mismatches with 422. Additionally, treat orgs with an unset `webhook_secret` as requiring stricter payload consistency (or disallow multi-org configs with any secret-less org).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "cross-org payload mutates a different org's repository" do
  # Shipit configured with multi-org github: {"unsecured-org" => {webhook_secret: nil}, "victim-org" => {webhook_secret: "s3cr3t"}}
  stack = shipit_stacks(:victim_review_stack) # belongs to victim-org/repo, review_stacks_enabled

  @request.headers['X-Github-Event'] = 'pull_request'
  payload = {
    action: 'unlabeled',
    number: stack.pull_request_number,
    pull_request: { id: 1, number: stack.pull_request_number, url: 'x', title: 't',
                     state: 'open', additions: 1, deletions: 1,
                     head: { sha: 'abc', ref: 'branch' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { full_name: 'victim-org/repo' }, # no owner field
    organization: { login: 'unsecured-org' },      # attacker-controlled, secret-less org
    sender: { login: 'attacker' }
  }.to_json

  # no X-Hub-Signature header sent / arbitrary signature

  post :create, body: payload, as: :json

  assert_response :ok
  assert_equal 'unsecured-org', nil # repository_owner resolved to attacker org
  stack.reload
  assert stack.archived? # victim-org's stack mutated by a request never signed by victim-org
end
```
This demonstrates the divergence: signature verification org (`organization.login` = `unsecured-org`) never equals the mutated repository's owning org (`victim-org`, derived from `repository.full_name`), and no code path enforces that equality.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
