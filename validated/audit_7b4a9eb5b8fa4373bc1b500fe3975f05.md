### Title
Credentials Scoped To One Repo URL Are Broadened By Default Git Credential Caching, Allowing Attacker-Controlled Submodule URLs On The Same Host To Exfiltrate Them - (File: main.go)

### Summary
The C4 report describes a residual-authorization bug: a permission (ERC20/721/1155 allowance) that was granted for one specific, trusted transfer context is left broadly usable, and an unprivileged caller supplies the destination/beneficiary parameter to redirect that residual trust to themselves. The closest reachable analog in `git-sync` is in its credential-management code: git-sync stores per-repo credentials (intended to be scoped to a specific "trusted" URL, e.g. the main repo or one particular submodule) via `git credential approve`, but the credential *retrieval* path relies on git's default `credential.helper` caching behavior, which is keyed by protocol+host rather than by full URL/path unless `credential.useHttpPath` is explicitly configured. An attacker who controls repo content that is synced (e.g. a submodule entry) can point a submodule URL at a different path on the *same host* that a trusted credential was scoped to, and git will hand over the residual (cached) credential to that attacker-influenced destination.

### Finding Description
`SetupDefaultGitConfigs` unconditionally sets a global git config of `credential.helper = "cache --timeout 3600"`: [1](#0-0) 

Credentials for the main repo and for individual submodule URLs are stored via `StoreCredentials`, which calls `git credential approve` with a `url=<value>` line built from the caller-specified `--credential` URL (or `--repo`/`--askpass-url` result): [2](#0-1) 

The `--credential` flag is explicitly documented as being for "specific URLs, for example when using submodules," implying the operator's intent is that a credential is scoped narrowly to one repository path: [3](#0-2) 

However, git's `credential.helper cache` — the helper git-sync globally configures — matches credential requests by `protocol://host` by default; it does not distinguish by path unless `credential.useHttpPath` is also set. No such `useHttpPath` configuration is present in `SetupDefaultGitConfigs`, `SetupExtraGitConfigs`, or elsewhere in the credential setup path that was inspected. This means once a credential has been cached for `https://example.com/trusted-repo`, any subsequent git operation to `https://example.com/<any-other-path>` within the 3600-second cache window will transparently receive the same username/password, because the lookup key is only `https://example.com`.

Because git-sync recursively updates submodules (`--submodules recursive`, the default) using URLs taken directly from the synced repository's `.gitmodules` file — untrusted, attacker-influenced content once an attacker can push to (or influence) the synced ref — an attacker who can add or modify a submodule entry pointing to `https://<same-host>/attacker-repo` can trigger git-sync to send the previously-cached, more privileged credential to a server the attacker controls at that same host. This is directly analogous to the residual-allowance bug: a credential ("allowance") granted for one destination gets consumed by an attacker-chosen destination because the enforcement granularity (host-only, not path) is coarser than the operator's intended trust boundary (path-scoped credential).

### Impact Explanation
If exploited, this leads to credential/token disclosure: an attacker-controlled endpoint on a shared host (e.g., a self-hosted git server, or a multi-tenant SaaS git host where the attacker can create a repo path under the same domain) can receive HTTP Basic-Auth credentials or tokens that were intended only for the legitimate, higher-privileged repo/submodule. This matches the "credential or token disclosure" impact category. It does not require a leaked key or a malicious operator — it only requires the attacker to control content merged into the synced repository (a submodule URL) and to control (or register) a repository/path on the same host as a previously-authorized URL.

### Likelihood Explanation
Exploitability depends on operational conditions: (1) the deployment must use `--credential`/`--askpass-url`/`--username`+`--password` for a repo hosted on a host that also permits attacker-controlled paths (e.g. a shared/multi-tenant git server, or a self-service Git hosting provider), and (2) the attacker must be able to introduce a submodule entry (or otherwise cause a fetch) targeting a different path on that same host within the credential-cache TTL (`3600s`). This is a plausible but not universal configuration — it primarily affects setups combining submodules with the built-in credential caching and shared-host git providers. I was not able to fully verify within the available searches whether `credential.useHttpPath` is set anywhere else in the codebase (a targeted grep returned matches in `test_e2e.sh` and one in `main.go`, but I could not inspect that `main.go` match's context before the tool budget was exhausted), so it is possible there is a mitigating configuration I did not fully confirm.

### Recommendation
- Set `credential.useHttpPath = true` globally (or per relevant host) when configuring git-sync's credential helper, so cached credentials are matched by full URL, not just host.
- Consider reducing/eliminating `credential.helper cache`'s TTL when submodules are enabled, or scope credential storage per-submodule using `git config credential.<url>.helper` overrides instead of a single global cache.
- Validate/allow-list submodule URLs (or the hosts they resolve to) before recursively fetching them, rather than blindly trusting `.gitmodules` content from the synced repo.

### Proof of Concept
1. Configure git-sync with `--repo=https://git.example.com/org/trusted-repo` and `--credential='{"url":"https://git.example.com/org/trusted-repo","username":"svc","password-file":"/creds/pw"}'`. This causes `StoreCredentials` to run `git credential approve` for that URL [4](#0-3) , and `SetupDefaultGitConfigs` has globally enabled `credential.helper cache --timeout 3600` [5](#0-4) .
2. An attacker (who can push to `trusted-repo` or a branch/PR that gets synced, or who controls a nested submodule) adds/edits `.gitmodules` to include a submodule URL `https://git.example.com/attacker/evil-repo`, on the same host `git.example.com` but a different, attacker-controlled path.
3. On the next sync, git-sync runs `git submodule update --recursive`, which causes git's HTTP transport to request credentials for `https://git.example.com/attacker/evil-repo`. Because `credential.helper cache` matches by host only (no `useHttpPath`), git returns the previously cached `svc`/password credential for that request.
4. The attacker's server at `evil-repo` receives the `Authorization` header containing the `trusted-repo` credential, achieving credential disclosure.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
}
```
