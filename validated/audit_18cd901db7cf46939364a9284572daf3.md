### Title
Malicious pool creator can freeze a pool's token vault, permanently disabling swap/deposit/withdraw for all users - (File: `programs/cp-swap/src/instructions/initialize.rs`, `programs/cp-swap/src/utils/token.rs`)

### Summary
`initialize` and `initialize_with_permission` accept any SPL Token / Token-2022 mint as `token_0_mint`/`token_1_mint` as long as it passes `is_supported_mint`, which only whitelists a small set of Token-2022 *extensions* and never checks the mint's base `freeze_authority` field. A pool creator can therefore supply a mint whose freeze authority they control, create a pool, and later call `FreezeAccount` on the pool's vault token account (freeze authority can freeze *any* account of that mint, not only accounts the freezer owns). Once the vault is frozen, every instruction that performs a `transfer_checked` against that vault (`deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, `collect_creator_fee(_permissionless)`, `collect_protocol_fee`, `collect_fund_fee`) reverts forever, permanently freezing all liquidity providers' and swappers' funds in that pool.

### Finding Description
`is_supported_mint` in `programs/cp-swap/src/utils/token.rs:335-360` only rejects Token-2022 mints carrying extensions other than `TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, and `ScaledUiAmount`: [1](#0-0) 

The base `Mint` struct's `freeze_authority` field is not part of the extension list and is never inspected anywhere in the initialization or swap/deposit/withdraw paths (no occurrence of `freeze_authority`/`FreezeAccount`/`is_frozen` checks exist in the program).

`Initialize`'s account constraints for `token_0_mint`/`token_1_mint` only validate `mint::token_program` and mint ordering, not freeze authority: [2](#0-1) 

The pool's vault accounts are created as plain token accounts owned by the pool `authority` PDA: [3](#0-2) 

A vault's ownership (`authority`) has no bearing on whether it can be frozen — SPL Token / Token-2022 freeze authority can freeze *any* token account of the mint, regardless of that account's owner/authority. Once frozen, any `transfer_checked` (and `burn`, for LP mint if that mint's used) against the account fails at the SPL Token program level. All of the program's fund-moving paths funnel through `transfer_from_pool_vault_to_user` / `transfer_from_user_to_pool_vault`: [4](#0-3) 

which are called unconditionally by `deposit` [5](#0-4) , `withdraw` [6](#0-5) , and both swap directions [7](#0-6) [8](#0-7) , with no fallback if the CPI reverts.

### Impact Explanation
Once the malicious creator freezes the vault, every instruction touching that vault (`deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, `collect_creator_fee`, `collect_creator_fee_permissionless`, `collect_protocol_fee`, `collect_fund_fee`) permanently reverts. This is not self-DoS: any user who already deposited liquidity or holds tokens routed through that pool loses access to those funds irrevocably, since there is no admin/emergency path in the program to unfreeze an SPL account or migrate the vault. This constitutes permanent freezing of LP and user funds for the affected pool, satisfying the High/Critical bar (concrete permanent freezing of user/LP funds).

### Likelihood Explanation
`initialize`/`initialize_with_permission` are permissionless (any account can call them as `creator`/`payer`), and creating a Token/Token-2022 mint with an attacker-controlled `freeze_authority` is a normal, unrestricted operation outside the program's control. No pre-existing liquidity or cooperation from other users is required — the attacker seeds the pool with their own mint and its own initial liquidity, waits for third parties (LPs/swappers) to interact with the pool, then freezes the vault. Likelihood is high given the ease of constructing the malicious mint and the total lack of a freeze-authority check.

### Recommendation
Extend `is_supported_mint` (or add a dedicated check in `Initialize`/`InitializeWithPermission`) to reject mints whose base `freeze_authority` is `Some(_)`, mirroring how Token-2022 extensions are already whitelisted. Alternatively/additionally, before any vault-touching transfer, verify the vault token account is not frozen and provide a documented rejection path, though disallowing freezable mints at pool-creation time is the more robust fix since it removes the attack vector entirely.

### Proof of Concept
1. Attacker creates an SPL Token or Token-2022 mint `M` and sets `freeze_authority = attacker`.
2. Attacker calls `initialize` (or `initialize_with_permission`) using `M` as `token_0_mint`/`token_1_mint`; `is_supported_mint` passes because it never inspects `freeze_authority`. The pool's `token_0_vault`/`token_1_vault` is created as a normal token account of mint `M`, owned by the pool `authority` PDA.
3. Legitimate LPs call `deposit`, and swappers call `swap_base_input`/`swap_base_output`, funding the vault.
4. Attacker invokes the SPL Token/Token-2022 `FreezeAccount` instruction (signed by their `freeze_authority` key) directly on the pool's vault account for mint `M`.
5. Any subsequent `deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, or fee-collection instruction touching that vault calls `transfer_checked`, which now fails at the SPL Token program level because the vault is frozen, permanently reverting for all users and locking all funds already in the vault.

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
