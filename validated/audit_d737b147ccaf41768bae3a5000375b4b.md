Based on my research, I found a genuine analog to the reorg/double-spend trust-binding break described in the report: a mismatch between **which GitHub organization's secret authenticates the webhook** and **which repository's records the payload is allowed to mutate**.

### Title
Webhook signature is verified against the organization derived from attacker-controlled payload fields, decoupled from the repository actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/`webhook_secret` to check the HMAC against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the **unverified** JSON body, before the signature has been checked. [1](#0-0) [2](#0-1) 

### Finding Description
The controller flow is:
1. `repository_owner` reads `params.dig('repository','owner','login')` from the raw, unauthenticated payload.
2. `Shipit.github(organization: repository_owner)` picks the `GithubApp` config for that org and calls `verify_webhook_signature`, so the HMAC is checked using **that org's** `webhook_secret`.
3. Only after this succeeds does `create` run `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and the handlers (e.g. `StatusHandler`, push handler) act on records looked up from the same payload's `repository`/`sha`/`stack` fields, not from anything tied to the org whose secret validated the request. [3](#0-2) 

Because GitHub computes the HMAC over the exact raw request body, an attacker who legitimately owns/administers Org A (and therefore knows Org A's `webhook_secret`, as any repository admin can view/rotate it) can craft a payload whose `repository.owner.login`/`organization.login` is Org A (so the signature verifies with Org A's secret) while other payload fields (`repository.full_name`, `sha`, branch, etc.) reference a stack that actually belongs to a different, unrelated repository/org B configured on the same Shipit instance. The equality the code implicitly assumes — "the org whose secret authenticated this request" == "the repository the handlers are about to mutate" — is never checked; only the org name (a payload field) is compared, and it is compared against itself, not against the resolved `Repository`/`Stack` that the handler subsequently touches. This is the same class of bug as the reorg report: a value used to satisfy a trust check (block depth / org-derived signature) is not actually bound to the value that gets acted upon later (the deposit / the target stack).

### Impact Explanation
If exploitable, this would let an attacker who controls webhook credentials for one onboarded org inject fabricated `push`/`status`/`check_suite` events that get recorded against another org's stack (e.g., forging CI "success" status on someone else's commit to trigger `deployable_status`/`ProcessMergeRequestsJob`/continuous-delivery paths), i.e., cross-repository writes without holding write access to the victim repository — matching the Critical impact bar in the rules ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
This requires the attacker to already control (be an admin of, or otherwise know the `webhook_secret` for) at least one GitHub organization/repository that is itself registered as a Shipit stack — a real but non-trivial precondition, and multi-tenant Shipit installations (many orgs configured) are exactly where this matters. I was not able to fully verify, within tool budget, whether `Shipit::Webhooks.for_event` handlers additionally re-derive/re-validate the target `Stack`/`Repository` strictly from a value that is cross-checked against `repository_owner` (which would neutralize this) — the `Handler` base class and `Shipit::Webhooks` dispatcher files could not be read before the iteration budget ran out, so this should be confirmed against `app/models/shipit/webhooks/handlers/handler.rb` and `app/models/shipit/webhooks.rb` before treating this as conclusively exploitable.

### Recommendation
After signature verification, re-derive the target `Stack`/`Repository` and assert its owning organization equals `repository_owner` (the value the signature was actually checked against) before any handler is allowed to mutate records; reject the webhook otherwise.

### Proof of Concept
Not constructed — this requires confirming, with the actual `Handler`/`Shipit::Webhooks` dispatch code (not fully retrieved due to tool-call exhaustion), that a handler resolves its target `Stack` from a payload field independent of `repository_owner`. Given the uncertainty flagged above, treat this as an unconfirmed analog pending verification of `app/models/shipit/webhooks/handlers/handler.rb` and the individual handler `process` methods.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
