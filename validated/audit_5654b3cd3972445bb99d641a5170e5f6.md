### Title
Unbounded growth of the `shown_warnings` array in the security-guidance hook's per-session state file — ([File: plugins/security-guidance/hooks/session_state.py])

### Summary
The security-guidance plugin persists hook state (including a `shown_warnings` list) to a JSON file that is read, mutated, and rewritten on every hook invocation via `with_locked_state`/`load_state`/`save_state`. Unlike sibling collections in the same plugin (`touched_paths`, capped at 200 entries; the reviewed-SHA log, capped via `_REVIEWED_SHAS_CAP`), the `shown_warnings` list has no cap or pruning logic — entries are only ever appended, never trimmed. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`atomic_check_and_mark_warning()` reads the `shown_warnings` list out of session state and, whenever a new `warning_key` is encountered, appends it and never removes any prior entry: [1](#0-0) 

This is the same structural pattern as the M-9 finding: an addition-only collection (`withdrawSeq` in the audited contract; `shown_warnings` here) that is used as an invariant check-list on every operation but has no corresponding removal/GC path, so its length is monotonically non-decreasing over the life of the state file.

Critically, the code comments in `session_state.py` explain that for CCR (remote) sessions, the state-file key is pinned to a *stable* remote-session id rather than the per-process session id, specifically so that state "survives" across many CC process restarts: [4](#0-3) 

Combined with `cleanup_old_state_files()` only pruning files that haven't been touched in 30 days, a single state file can be repeatedly loaded/mutated/rewritten across many turns and restarts over a 30-day window, letting `shown_warnings` accumulate indefinitely — mirroring how `withdrawSeq` in the audited contract accumulated indefinitely across `removeAdapter()`/`addAdapter()` cycles because no reduction counterpart existed.

By contrast, the plugin's authors clearly recognized this exact bug class and fixed it for the *other* similar collections in the same file/plugin:
- `touched_paths` is explicitly capped at 200 with a comment calling out the unbounded-growth risk.
- the reviewed-SHA append log is explicitly capped via `_REVIEWED_SHAS_CAP` with GC-on-write. [3](#0-2) [5](#0-4) 

`shown_warnings` is the one collection in this state-management code that was missed.

### Impact Explanation
Every `with_locked_state()` call does a full JSON read, in-memory mutate, and full JSON rewrite of the state file: [6](#0-5) 

As `shown_warnings` grows without bound, each hook invocation (which fires on tool use, e.g. PreToolUse/PostToolUse/Stop events wired to this plugin) does progressively more I/O and JSON (de)serialization work while holding an `flock` exclusive lock. This degrades interactive latency for every tool call in a long-lived/CCR-persisted session, and — since hooks are subject to execution time limits — can eventually cause the security-guidance hook itself to time out or fail, effectively disabling the security warning/review gate it is meant to enforce. This is an availability/DoS-class impact on a security-relevant control path (the hook that reviews diffs/commits for vulnerabilities and blocks/warns the model), analogous to the "operation becomes economically/practically non-viable as the array grows" impact in the original report, but manifesting as hook slowdown/timeout rather than gas cost.

### Likelihood Explanation
This is reachable by any user running Claude Code with the bundled `security-guidance` plugin enabled, with no special privileges required — the growth happens automatically as normal tool-use warnings are surfaced over the life of a session/state file. Likelihood of the state file being long-lived enough to matter is higher specifically for CCR/remote sessions, per the code's own comment about state surviving process restarts across a stable remote-session id, and generally for any developer with a long, active work session in the same repo/session id over the 30-day GC window.

### Recommendation
Add an explicit cap/pruning policy to `shown_warnings` (and audit any other unbounded state fields in `session_state.py`/`security_reminder_hook.py`), mirroring the cap already applied to `touched_paths` and the reviewed-SHA log — e.g., cap it at a fixed size and evict oldest entries (`del warnings[:len(warnings) - CAP]`) inside `atomic_check_and_mark_warning()`.

### Proof of Concept
I was unable to fully trace every call site of `atomic_check_and_mark_warning()`/`atomic_check_counter()` (call sites in `security_reminder_hook.py`) within the available tool budget to enumerate the exact distinct `warning_key` values used in production, so I cannot provide a concrete step-by-step reproduction demonstrating a specific number of turns/keys needed to trigger measurable degradation. The root-cause code path (append-only list, no cap, repeated full-file read/rewrite per hook call, GC only on a 30-day mtime basis) is confirmed directly from the cited files; confirming the real-world growth rate would require running an actual long CCR/session and observing `shown_warnings` length and hook latency over time, which would need a live environment (recommend a Devin session with filesystem/terminal access to instrument and reproduce this empirically).

```python
def atomic_check_and_mark_warning(session_id, warning_key):
    """
    Atomically check if a warning has been shown and mark it as shown if not.
    Returns True if this is the first time seeing this warning (should show it),
    False if it was already shown (should skip it).
    """
    def _check(state):
        warnings = state["shown_warnings"]
        if warning_key in warnings:
            return False
        warnings.append(warning_key)
        return True

    result = with_locked_state(session_id, _check)
    return result if result is not None else True
```

```python
def _state_key(session_id):
    # In CCR each user turn is a new CC process with a fresh session_id; the
    # remote session ID is stable across those restarts. Prefer it so the
    # pending-warnings sweep and any unprocessed touched_paths survive.
    key = os.environ.get("CLAUDE_CODE_REMOTE_SESSION_ID") or session_id
    # The key becomes a filename component under the state dir. CC session ids
    # are UUIDs (sanitization is a no-op for them), but nothing in the hook
    # protocol guarantees that, so strip path separators and anything else
    # that could escape the state dir, and bound the length.
    return re.sub(r"[^A-Za-z0-9._-]", "_", str(key))[:128]
```

```python
def with_locked_state(session_id, callback):
    """
    Execute callback with exclusive access to the state file.
    The callback receives the state dict and can modify it in place.
    State is saved after the callback returns.
    Returns the callback's return value.
    """
    lock_file = get_lock_file(session_id)
    state_dir = os.path.dirname(lock_file)

    try:
        os.makedirs(state_dir, exist_ok=True)
    except OSError:
        pass

    if fcntl is None:
        # No file locking available (Windows) — run without locking
        state = load_state(session_id)
        result = callback(state)
        save_state(session_id, state)
        return result

    lock_fd = None
    try:
        lock_fd = os.open(lock_file, os.O_RDWR | os.O_CREAT)
        fcntl.flock(lock_fd, fcntl.LOCK_EX)

        state = load_state(session_id)
        result = callback(state)
        save_state(session_id, state)
        return result
```

```python
def record_touched_path(session_id, file_path):
    """Append a file path to the touched_paths list (deduped, capped at 200).

    Stop is the consumer and clears under the same lock it reads with; UPS
    no longer wipes. The cap is a defensive bound for sessions where Stop
    never fires (disabled mid-session, abort) — git diff naturally filters
    stale paths so over-retention is harmless, just wasteful.
    """
    def _record(state):
        paths = state.setdefault("touched_paths", [])
        if file_path not in paths:
            paths.append(file_path)
            if len(paths) > 200:
                del paths[:len(paths) - 200]
    with_locked_state(session_id, _record)
```

```python
def _append_reviewed_shas(repo_root, shas, vulns_found=0):
    """Record that `shas` were reviewed. Best-effort; never raises.

    Uses fcntl.flock for the read-gc-write; appends are O_APPEND-atomic but
    GC needs the lock so concurrent CC sessions in the same clone don't race
    each other's truncation.
    """
    p = _reviewed_shas_path(repo_root)
    if not p or not shas:
        return
    import time as _time
    ts = int(_time.time())
    pv = _PV or 0
    lines = [f"{s}\t{ts}\t{pv}\t{int(vulns_found)}\n" for s in shas]
    try:
        import fcntl
        with open(p, "a+") as f:
            fcntl.flock(f.fileno(), fcntl.LOCK_EX)
            try:
                f.seek(0)
                existing = f.read().splitlines(keepends=True)
                # Dedup by sha (first column) — keep newest, then cap.
                seen = set()
                merged = []
                for ln in (existing + lines)[::-1]:
                    sha = ln.split("\t", 1)[0].strip()
                    if sha and sha not in seen:
                        seen.add(sha)
                        merged.append(ln if ln.endswith("\n") else ln + "\n")
                merged = merged[:_REVIEWED_SHAS_CAP][::-1]
                f.seek(0)
                f.truncate()
                f.writelines(merged)
```
