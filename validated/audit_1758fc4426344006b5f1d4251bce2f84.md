### Title
Webhook signature is verified against the sender's own organization, but `StatusHandler` writes GitHub commit statuses matched only by global `sha`, letting any webhook-authenticated org inject CI status onto any other tracked repository's commits — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the inbound HMAC against using a field pulled straight out of the untrusted JSON payload (`repository.owner.login` / `organization.login`). Once the signature check passes for *that* org, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which looks up the target `Commit` **only by `sha`**, with no scoping to the repository/organization that was actually verified. Any party who legitimately controls a GitHub org/repo tracked by the same Shipit instance (and therefore knows that org's `webhook_secret`) can therefore forge a `status` event that is authenticated as "my org" but writes a CI status onto a commit belonging to a completely different, unrelated tracked stack.

### Finding Description
`WebhooksController#verify_signature` derives the org used for signature verification from the payload itself: [1](#0-0) [2](#0-1) 

This means the *only* fact proven by a valid signature is "the sender knows the `webhook_secret` configured for the org named in `repository.owner.login`/`organization.login`". Multiple orgs, each with independent `webhook_secret`s, can be configured simultaneously on one Shipit instance (see `test/dummy/config/secrets_double_github_app.yml`), so this is a supported, realistic multi-tenant configuration, not a hypothetical.

Once signature verification passes, the raw JSON `params` (the entire attacker-controlled payload, not re-validated against the verified org) is dispatched to event handlers: [3](#0-2) 

For the `status` event, `StatusHandler#process` looks up commits purely by the `sha` field from the payload, with **no** repository/org scoping at all — unlike every other handler (`PushHandler`, `PullRequest::*Handler`, etc.), which route through `Handler#stacks`/`Handler#repository_name`, itself keyed on `payload.dig('repository','full_name')`: [4](#0-3) [5](#0-4) 

`Commit#sha` is not unique per-repository in the schema query used here (`Commit.where(sha: params.sha)` matches across **all** stacks/repositories in the Shipit database), and `create_status_from_github!` persists a `Status` row tied to that commit using attacker-controlled `state`/`context`/`description`/`target_url` fields, which directly feed into CI gating logic: [6](#0-5) [7](#0-6) 

**The broken equality:** the trust binding that should hold is
`organization_whose_secret_verified_the_signature == organization_that_owns_the_repository/stack_being_written_to`.
For every other handler this equality is enforced (both sides route through `repository.full_name`). For `status` events it is not enforced at all — the write target is chosen by a value (`sha`) that has zero relationship to the signature-verifying org.

### Impact Explanation
An attacker who administers/controls any GitHub organization tracked by the Shipit instance (i.e., knows that org's legitimate `webhook_secret`, which they configure themselves when wiring up their own repo's webhook) can forge a `status` webhook signed with their own org's secret, but referencing the `sha` of a commit belonging to a victim organization's stack (commit SHAs are visible in GitHub UI/API/PR links and are frequently public). By setting `state: "success"` and `context` equal to a required CI check context (`ci.require`/`ci.blocking`) for the victim stack, the attacker can flip `Commit#deployable?` to `true` for a commit that never actually passed CI in the victim's real GitHub repository, and can also satisfy `blocking_statuses` gates for other undeployed commits ahead of it. This directly enables an **unauthorized deploy** of unreviewed/failing code in a repository/org the attacker has no legitimate access to — matching the "unauthorized deploy" Critical impact criterion, achieved purely through the webhook endpoint with no `ApiClient` token, GitHub App private key, or repository write access to the victim org.

### Likelihood Explanation
Requires only: (1) the attacker's own legitimate, valid `webhook_secret` for any org tracked by the shared Shipit instance (trivial for any onboarded team in a multi-org Shipit deployment), and (2) knowledge of a target commit SHA in the victim's stack, which is typically public/discoverable. No privileged Shipit account, GitHub App credentials, or victim-org access is required — only the ability to send a correctly-signed HTTP POST to `/webhooks`, which is the documented, unauthenticated (session-wise) entry point for GitHub webhook delivery. This makes exploitation straightforward for any multi-tenant Shipit deployment.

### Recommendation
`StatusHandler` (and any other handler) must scope `Commit`/`Stack` lookups by the repository identified in `payload['repository']['full_name']`, cross-checked against the organization actually used to verify the webhook signature, exactly as `Handler#stacks`/`repository_name` already do for other events. Concretely, `StatusHandler#process` should resolve commits via `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` (or equivalent), never via a global `Commit.where(sha:)`, and `WebhooksController` should assert that the resolved repository owner matches the org whose secret validated the signature before allowing any handler to persist writes.

### Proof of Concept
1. Configure Shipit with two orgs, `VictimOrg` and `AttackerOrg`, each with its own `webhook_secret` (as supported by `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls a repo under `AttackerOrg` and therefore knows `AttackerOrg`'s `webhook_secret`.
3. Attacker finds a known commit `sha` in a `VictimOrg` stack tracked by the same Shipit instance (e.g., from a public PR link) that requires CI context `ci/circleci` (`ci.require`).
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, a body:
   ```json
   {
     "sha": "<victim_commit_sha>",
     "state": "success",
     "context": "ci/circleci",
     "repository": { "owner": { "login": "AttackerOrg" } }
   }
   ```
   and `X-Hub-Signature` computed with `AttackerOrg`'s real `webhook_secret`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and the signature validates successfully (it was legitimately signed with that org's secret) — `app/controllers/shipit/webhooks_controller.rb:24-30`.
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: params.sha)` with no org check, finding the `VictimOrg` commit and calling `commit.create_status_from_github!(params)` — `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`.
7. The victim commit now has a spurious `success` status for a required CI context, potentially making `Commit#deployable?` return `true` and enabling an unauthorized deploy in `VictimOrg`'s stack — `app/models/shipit/commit.rb:227-229`.
