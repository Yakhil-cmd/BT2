### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by SHA with `Commit.where(sha: params.sha)`, with no constraint tying the match to the GitHub organization/repository that the webhook signature was verified against. Any org whose GitHub App has a valid `webhook_secret` configured in this Shipit instance (`OrgReal`) can trigger a correctly-signed `status` webhook carrying a SHA that also exists on a commit belonging to a different tenant's stack (`OrgVictim`), causing Shipit to write a forged `Status` onto `OrgVictim`'s commit and potentially flip its `deployable_status`/CI gate.

### Finding Description
The binding that should hold is: `repository_owner` verified in `WebhooksController#verify_signature` (the org whose `webhook_secret` produced a valid HMAC over the raw payload) == the org owning the `Stack`/`Repository` of every `Commit` mutated as a result of that request. Tracing the code:

- `WebhooksController#verify_signature` only checks that the payload's HMAC matches the secret configured for `repository_owner = params.dig('repository','owner','login')`; it never restricts which commits/stacks the handler is allowed to touch: [1](#0-0) 
- `StatusHandler#process` then does a global, unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, with no join/filter on `stack.repository` or `repository_owner`: [2](#0-1) 
- `Commit#create_status_from_github!` delegates to `statuses.replicate_from_github!(stack_id, github_status)`, and `stack_id` here is the commit's *own* `stack_id` (the victim's real stack), not anything derived from the verified org: [3](#0-2) [4](#0-3) 
- `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` then act on the victim's stack, and `Commit#add_status`/`deployable_status` transitions (shown in `test/models/commits_test.rb`) can enqueue `ProcessMergeRequestsJob` for the victim's stack purely from this forged status: [5](#0-4) 

So a request signed by `OrgReal`'s webhook secret, referencing a SHA that collides with a commit under `OrgVictim`'s stack, results in a `Status` row created against `OrgVictim`'s commit/stack — a write to a tenant the request never authenticated to. None of the existing guards close this: `verify_signature` only proves "this org's secret signed this payload," it does not scope subsequent database writes; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate payload shape, not ownership; there is no repository/stack filter anywhere in the `Commit.where(sha:)` query or in `create_status_from_github!`.

The realistic attack path: since git commit SHAs are a hash of tree+parents+author/committer+timestamps+message, an attacker controlling their own repo under `OrgReal` (with a configured Shipit GitHub App/webhook secret) can reproduce an identical SHA to a known/public commit in `OrgVictim`'s repo by replaying identical commit metadata/content, then have GitHub (or, since `verify_webhook_signature` only checks the HMAC and it's `OrgReal`'s own webhook firing for `OrgReal`'s own repo, this is a legitimately-signed event) deliver a `status` event for that SHA.

### Impact Explanation
An attacker who only controls a repository under an org with any configured Shipit webhook secret can, at will, create arbitrary `Status` rows (state, description, context, target_url) on commits belonging to unrelated stacks/orgs, as long as they can produce a colliding SHA. This can flip `deployable?`/CI-gating logic (`deployable_status`, `enable_ci_on_stack`, `schedule_continuous_delivery`, `ProcessMergeRequestsJob`) for `OrgVictim`'s stack, i.e., "a payload for one repository mutating another's stack/commit," which the rules classify as **Critical**. The attack is repeatable against any stack/commit whose SHA can be reproduced or is already known/public, and is not limited to one victim.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one org (`OrgReal`) with a working webhook configuration (common in the documented multi-org `github:` config), and the attacker needs a SHA collision with a target commit in `OrgVictim` — feasible by replaying/copying commit metadata for public or otherwise known commits, since git SHAs are simply content hashes, not secrets. No Shipit credentials, session, or API token are required at any point; only ability to make GitHub emit a `status` event for the attacker's own repo (which the attacker fully controls). This makes the attack low-cost and repeatable.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers, e.g. check-run/check-suite handlers) to only commits belonging to stacks whose `Repository` matches the verified `repository_owner`/`repository.full_name` from the webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repo_name })`, rather than a bare `sha` match across all tenants.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (or a new `status_handler_test.rb`):
1. Create two `Repository`/`Stack`/`Commit` fixtures under different simulated orgs (e.g. `owner: "OrgReal"` and `owner: "OrgVictim"`), both with a `Commit` row sharing the same `sha` value.
2. Stub `Shipit.github(organization: 'OrgReal').verify_webhook_signature` to return `true` (simulating a correctly-signed request from `OrgReal`), and ensure no stub exists that would authorize `OrgVictim`.
3. POST the `status` webhook with `X-Github-Event: status`, a payload whose `repository.owner.login == 'OrgReal'`, and `sha` equal to the shared SHA.
4. Assert `OrgVictim`'s commit's `statuses.count` increased by 1 (`assert_difference 'victim_commit.statuses.count', 1`), proving a write occurred on a tenant the request never authenticated against — violating the stated binding (`repository_owner == org owning mutated Commit`).
5. As the correct/expected behavior, assert that with a proper fix, `OrgVictim`'s commit `statuses.count` remains unchanged (`assert_no_difference`) since only `OrgReal`'s own commit should be affected.
