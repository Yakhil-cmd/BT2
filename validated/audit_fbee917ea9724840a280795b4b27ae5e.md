### Title
Unsanitized attacker-controlled devcontainer port label enables terminal escape sequence injection - (File: pkg/cmd/codespace/ports.go)

### Summary
`(*portInfo).Label` at [1](#0-0)  returns the `portsAttributes.<port>.label` value from `.devcontainer/devcontainer.json` verbatim, with no ANSI/control-character sanitization. This value is fetched from the codespace's repository contents via `getDevContainer` and written directly to the terminal table via `tp.AddField(port.Label())`, allowing an attacker who controls the repo behind a victim's codespace to inject terminal escape sequences.

### Finding Description
`ListPorts` reads the devcontainer file from the codespace's repository using `apiClient.GetCodespaceRepositoryContents(ctx, codespace, ".devcontainer/devcontainer.json")` [2](#0-1) , JSON-unmarshals it into a `devContainer` struct whose `PortAttributes[port].Label` field is a plain `string` (not the codebase's `Untrusted` type) [3](#0-2) , and later `port.Label()` returns `attributes.Label` unmodified [1](#0-0) . This value flows into `tp.AddField(port.Label())` at line 118, and the table printer writes to `ios.Out` — not `ios.ContentOut` [4](#0-3) .

The codebase has an established pattern for exactly this problem: `pkg/iostreams/untrusted.go` provides an `Untrusted` wrapper type whose `String()` method sanitizes ANSI escapes via `asciisanitizer.Sanitizer`, and `IOStreams.ContentOut` is a writer that sanitizes content by default [5](#0-4) . Similar remote/untrusted-text table fields elsewhere in the codebase (e.g. `pkg/cmd/skills/list/list.go`) explicitly call a `sanitizeForTerminal` helper before adding fields to a table [6](#0-5) . `ports.go`'s `Label()` and `ListPorts` do neither — the raw string bypasses both the `Untrusted` wrapper and any sanitizer, and `ios.Out` (used by the table printer) is not itself sanitized.

Note: the `--json` export path (`ExportData`) also returns `pi.Label()` raw, but JSON export is not rendered to a terminal in the same dangerous way, so the primary risk is the default table rendering path.

### Impact Explanation
An attacker who publishes a repository (or a PR/fork of one) containing a crafted `.devcontainer/devcontainer.json` with a `portsAttributes.<port>.label` value containing ANSI/VT100/OSC escape sequences can, when a victim creates or opens a codespace from that repo and runs `gh codespace ports`, have those sequences interpreted by the victim's terminal. This falls into the "terminal escape injection" bounty class: cursor manipulation to hide/spoof output, OSC 8 malicious hyperlinks, or terminal title manipulation. There is no code execution or credential exfiltration directly from this bug — the impact is limited to terminal-rendering manipulation/spoofing, consistent with the "High" severity scope stated in the question rather than critical RCE.

### Likelihood Explanation
This requires the victim to have a codespace whose backing repository is attacker-controlled or attacker-influenced (e.g., the victim opens a codespace on a malicious or compromised repo, or a PR branch with a devcontainer.json under attacker control), and then run `gh codespace ports`. This is a realistic, low-complexity, and repeatable path: no special privileges beyond being able to have the victim create a codespace against attacker content, which matches the "unprivileged attacker publishes repo/fork/PR" precondition. The `.devcontainer/devcontainer.json` file is a normal, expected file in many repos, making it a plausible/legitimate-looking place to plant a payload.

### Recommendation
Sanitize the `Label` value before returning it or before adding it to the table. Concretely:
- Change `portAttribute.Label` to use the existing `iostreams.Untrusted` type (as already used elsewhere for untrusted remote content) so `String()` sanitizes automatically, or
- Apply the same `sanitizeForTerminal`-style ASCII sanitizer (`golang.org/x/text/transform` + `github.com/cli/go-gh/v2/pkg/asciisanitizer.Sanitizer`) to `attributes.Label` inside `(*portInfo).Label()` before returning it, matching the pattern in `pkg/cmd/skills/list/list.go`.
- Apply the same treatment before exposing the value via `ExportData`'s `"label"` case, or accept that JSON output is not rendered to a terminal and is thus lower risk.

		t.Fatalf("expected label to still contain raw escape bytes demonstrating lack of sanitization, got: %q", got)
	}
	// This assertion currently PASSES, proving the escape sequence survives

Expected result on the current code: the raw ESC byte (`\x1b`) is present in the value returned by `Label()`, demonstrating it is not sanitized before being passed to `tp.AddField(port.Label())` and written to the terminal. After applying the recommended fix (wrapping in `iostreams.Untrusted` or running through `asciisanitizer.Sanitizer`), this test should be updated to assert the ESC byte is absent.

// SetContentSanitization toggles ANSI escape sanitization on ContentOut.
// Commands should call this with false when an explicit opt-out flag (e.g.
// --allow-escape-sequences) is set, so subsequent writes of external content
// pass through unmodified.
func (s *IOStreams) SetContentSanitization(enabled bool) {
	s.sanitizeContent = enabled
	s.ContentOut = newContentWriter(s.Out, enabled)
}

// newContentWriter returns the writer to wire up as ContentOut. When
// sanitize is true it inserts an asciisanitizer in front of the underlying
// writer; otherwise it returns the underlying writer directly so writes
// reach stdout unchanged.
func newContentWriter(out io.Writer, sanitize bool) io.Writer {
	if !sanitize {
		return out
	}
	return transform.NewWriter(out, &asciisanitizer.Sanitizer{})
}

// sanitizeForTerminal replaces ASCII control characters in s with inert
// caret-style stand-ins so frontmatter values cannot inject terminal escapes.
func sanitizeForTerminal(s string) string {
	var buf bytes.Buffer
	r := transform.NewReader(bytes.NewReader([]byte(s)), &asciisanitizer.Sanitizer{})
	if _, err := io.Copy(&buf, r); err != nil {
		return "Unknown"
	}
	return buf.String()
}
