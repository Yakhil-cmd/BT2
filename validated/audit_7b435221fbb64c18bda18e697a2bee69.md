### Title
Cross-Organization Webhook Confusion: Signature Verified Against `repository.owner.login`, But Handlers Act On `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) from the JSON body, but the event handlers that actually mutate state (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) resolve the target `Repository`/`Commit`/`Stack` using a *different* field in the same payload — `repository.full_name`. The signature check never binds these two fields together, so a payload that is validly signed for organization A can reference a repository belonging to organization B.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and thus the `webhook_secret`) using: [1](#0-0) [2](#0-1) 

The multi-org configuration is a supported, documented feature where each GitHub organization has its own `app_id`/`webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature passes, the raw parsed body is dispatched to handlers unmodified: [5](#0-4) 

But every handler resolves its target repository/stacks from `repository.full_name`, a field independent of the `repository.owner.login` used for signature-organization selection: [6](#0-5) [7](#0-6) [8](#0-7) 

`StatusHandler` is even worse: it doesn't check the repository at all — it matches purely on commit SHA across the whole Shipit instance: [9](#0-8) 

**The broken equality**: the HMAC verifies `organization-secret-owner == repository.owner.login`, while the mutation performed by the handler is keyed on `repository.full_name` (or bare `sha`, for status). Nothing enforces `repository.owner.login == owner(repository.full_name)`. An attacker who legitimately administers a GitHub App for *their own* organization (Org A, tracked by this Shipit instance) knows Org A's `webhook_secret` (they configured it when creating the App per `docs/setup.md`). They can therefore craft an arbitrary JSON body — signed correctly with Org A's secret — where `repository.owner.login`/`organization.login` = `"OrgA"` (so `verify_signature` selects and passes with Org A's secret) but `repository.full_name` = `"OrgB/victim-repo"` or an arbitrary commit `sha` belonging to Org B's stack, and POST it directly to `/webhooks`.

### Impact Explanation
This breaks the intended binding "the organization that authenticated is the repository that gets written." Concretely, an attacker in control of one tracked organization's GitHub App configuration can:
- Force `StatusHandler#process` to attach an attacker-chosen commit status (e.g., `state: "success"`) to any commit in *any* stack in the instance, purely by guessing/observing a SHA (`Commit.where(sha:)` is unscoped by org/repo).
- Force `CheckSuiteHandler`/`PushHandler` to trigger `sync_github` / `schedule_refresh_check_runs!` against another organization's stacks via `repository.full_name`.

Since `Commit#deployable?` and `Stack#continuous_deployment?`/`schedule_continuous_delivery` gate solely on stored status/check-run state (`success? && !blocked?`), injecting a forged "success" status via `StatusHandler` on a victim commit can make an otherwise-non-deployable commit `deployable?`, and with continuous deployment enabled this can trigger an **unauthorized deploy** — this satisfies the Critical impact bar ("unauthorized deploy") defined by the rules. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
Requires: (1) the Shipit instance configured for multiple GitHub organizations (a documented, supported feature), (2) the attacker legitimately administering one of those organizations' GitHub Apps (so they know its `webhook_secret`, which is standard for any org onboarding to a shared Shipit instance), and (3) the ability to POST directly to the `/webhooks` endpoint (publicly reachable, no session/API-client auth required — it is authenticated solely by the HMAC signature). No privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is needed — only knowledge of one's own org's webhook secret, which every onboarded organization has by design. This is a realistic, unprivileged-attacker cross-tenant scenario in any multi-org Shipit deployment.

### Recommendation
Bind the field used to select the verification secret to the field used to resolve the mutation target. Concretely, after selecting `github_app` via `repository_owner`, verify that `repository.full_name`'s owner segment (and any `sha`/stack lookup) actually belongs to that same `repository_owner` before dispatching to handlers, or resolve the target `Repository` via `Repository.from_github_repo_name(full_name)` and reject the webhook if `repository.owner != repository_owner`. Additionally, scope `StatusHandler`'s `Commit.where(sha:)` lookup by the verified repository, not by bare SHA alone.

### Proof of Concept
1. Deploy Shipit configured with multi-org GitHub Apps for `OrgA` and `OrgB` (per `test/dummy/config/secrets_double_github_app.yml` pattern), both tracked with stacks.
2. As the administrator of `OrgA`'s GitHub App, obtain `OrgA`'s `webhook_secret` (set during app creation).
3. Craft a `status` webhook body:
```json
{
  "sha": "<victim-commit-sha-in-OrgB-stack>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and the signature validates successfully.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!`, attaching a forged "success" status to the victim commit in `OrgB`'s stack — potentially satisfying `Commit#deployable?` and triggering continuous deployment.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
