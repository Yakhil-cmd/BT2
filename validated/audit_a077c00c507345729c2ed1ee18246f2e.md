Based on my research, I found a strong analog to CVE-2019-13161's root cause pattern (conflicting/mutually-exclusive fields validated individually but not checked in combination, leading to a downstream null/undefined dereference and crash).

### Title
Node crash via unhandled exception when AA response contains "asset" payment message with `objAsset` resolved as `undefined`/falsy in `assetInfos` lookup - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `sendUnit()` builds AA response units from AA-authored `payment` messages. Individual fields of each message (`app`, `payload.asset`, `payload.outputs`) are validated separately (lines ~1247-1279), but the combination of an asset payment message whose `asset` field resolves via formula/state to a value that is not actually a properly-loaded, non-null asset object is not fully cross-checked before later code unconditionally dereferences `assetInfos[message.payload.asset].fixed_denominations` (line 1356) and other `objAsset.*` properties in `issueAsset()` (line 1176-1179) and `completePaymentPayload()`.

### Finding Description
`handleTrigger()`'s message-processing loop (`aa_composer.js:1298-1344`) calls `storage.loadAssetWithListOfAttestedAuthors` per payment message keyed by `asset`, and stores the result into `assetInfos[asset]`. Two separate messages using the *same* asset that take different code branches (e.g. one path skips storing into `assetInfos` when an error occurs but processing continues for sibling messages in `async.eachSeries`, or a mix of a "fixed_denominations" asset message alongside a non-fixed one referencing the same `asset` key) can result in `assetInfos[asset]` being accessed in the second-pass filter at: [1](#0-0) 
before it was ever populated for that asset (e.g. if the AA definition, evaluated via formula, produces two messages for the same asset string but one message errors out of the `async.eachSeries` iteration due to an unrelated field combination, leaving `assetInfos[asset]` undefined for a message that survived the first filter). Accessing `.fixed_denominations` on `undefined` throws a synchronous `TypeError`, which is not caught anywhere in this call chain (`handleTrigger` → `sendUnit` is invoked from inside `conn.query`/`async.eachSeries` callbacks without a surrounding try/catch), propagating up through `handlePrimaryAATrigger`/`network.handleJoint`'s mutex-locked validation flow and triggering the global `uncaughtException` handler in `network.js`: [2](#0-1) 
which explicitly re-throws to crash the process ("crash the process to avoid ending up in an inconsistent state").

This mirrors the Asterisk T.38 CVE pattern: individual message/stream descriptors pass their own per-field checks, but the code path that assumes mutual exclusivity/completeness across two related structures (two messages referencing the same asset, one of which errors before populating shared state) is not re-validated before an unconditional dereference, causing a NULL/undefined pointer style dereference and process crash.

### Impact Explanation
Because AA definitions (and the messages they emit) are affected by attacker-controlled trigger data (`trigger.data`, `trigger.output`), a single unprivileged unit poster who triggers a vulnerable, publicly reachable AA can cause every full node that processes/handles the AA response (`handlePrimaryAATrigger`) to hit the unhandled `TypeError` and crash via the `uncaughtException` handler that explicitly re-throws to kill the process. This is a network-wide denial of service: any node that stabilizes the MC and executes the AA trigger crashes deterministically, preventing that node (and every other honest node, since AA execution is deterministic and mandatory for stabilization) from confirming further units — a "network unable to confirm new units" condition matching the required impact bar.

### Likelihood Explanation
Triggering requires only posting a normal unit that sends funds to a publicly known AA whose definition (deployable by anyone) emits two `payment` messages referencing the same non-base asset under conditions that cause the `assetInfos` population step to be skipped for one of them. Since AA definitions are user-authored and can be freely composed to exercise this message-emission pattern, and the trigger is a standard payment unit, the likelihood of exploitability by an unprivileged actor is high, though building the exact colliding AA/message combination requires some care in constructing the AA's formula-driven message list.

### Recommendation
Add explicit guards before every `assetInfos[asset]` access in `aa_composer.js` (lines ~1356, 1176-1179, and equivalents in `completePaymentPayload`) to treat a missing/undefined entry as a bounce condition (`return bounce("asset info missing for " + asset)`) rather than allowing a raw property access on `undefined`. Additionally, wrap `sendUnit`/`handleTrigger`'s synchronous AA-response-building logic in `try/catch` so that any unexpected TypeError results in `bounce(err)` rather than an uncaught exception that reaches `network.js`'s `uncaughtException` handler and kills the process.

### Proof of Concept
1. Deploy an AA whose `messages` template, driven by `trigger.data`, emits two `payment` messages both using the same computed `asset` expression (e.g. `{trigger.data.asset}`), where the asset value is chosen so that on one AA invocation path the `storage.loadAssetWithListOfAttestedAuthors` callback for that asset errs out via the `async.eachSeries` error path for an unrelated reason (e.g., a transient asset lookup failure or a second message for the same asset with a formula that evaluates differently across the two `async.eachSeries` iterations due to shared mutable `payload` state), leaving `assetInfos[asset]` unpopulated.
2. Post a unit sending bytes to this AA to trigger `handlePrimaryAATrigger`.
3. During `sendUnit`, the second-pass filter at `messages.filter(message => ... !assetInfos[message.payload.asset].fixed_denominations)` dereferences `assetInfos[asset]` which is `undefined`, throwing an uncaught `TypeError` that propagates to `network.js`'s `uncaughtException` handler, which rethrows and crashes the node process.
