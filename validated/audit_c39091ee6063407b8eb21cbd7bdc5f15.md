### Title
Arbiter contract hash allows field-boundary cross-linking (hash collision across different contract terms) - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js`'s `getHashSrc()` builds the byte string that is hashed to produce a contract's unique identifier (`objContract.hash`) by naively concatenating variable-length fields with **no delimiter** whenever `contract.creation_date <= exports.NEW_HASH_DATE`. Since `exports.NEW_HASH_DATE = '2026-11-01'` and the current date is 2026-09-15, every contract created today uses this vulnerable, delimiter-less concatenation path. This is structurally identical to the Fabric "cross-linking" bug class: a peer/attacker can shift bytes across adjacent field boundaries so that two semantically different contracts produce byte-identical concatenations and therefore identical hashes.

### Finding Description
`getHashSrc()`: [1](#0-0) 

```
const src = contract.creation_date > exports.NEW_HASH_DATE
     ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
     : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
```

`NEW_HASH_DATE` is set to a future date (`2026-11-01`) [2](#0-1)  and `creation_date` is generated as the actual current timestamp when a contract is composed [3](#0-2) , so **every contract created before Nov 1 2026 goes through the legacy, delimiter-free branch** (`.join("")`).

In the legacy branch, `title`, `text`, `party names`, `amount`, and `asset` are all free-form, variable-length, attacker-controlled strings that are concatenated raw and then SHA-256-hashed via `getHash()`: [4](#0-3) 

Because there is no length-prefixing or separator between fields, a party constructing/forwarding a contract (the contract counterparty, or a device relaying `arbiter_contract_offer` / `arbiter_contract_shared` / `arbiter_contract_update` messages) can move bytes across a field boundary — e.g., append the first few characters of `text` onto the end of `title` — and produce a *different* structured contract object (different title/text split, or different party name split) whose concatenated byte stream, and hence `getHash()` output, is identical to the original. This is exactly the cross-linking primitive described in the reference Fabric advisory: the hash function is supposed to commit to the *parsed* structure, but instead only commits to the flattened concatenation, so distinct field splits collide.

By contrast, the intended-but-currently-inactive fix (`NEW_HASH_DATE` branch) already uses a delimiter (`exports.DELIMITER = "[|#|]"`), showing the maintainers previously recognized concatenation-without-delimiter as unsafe and hardened it — but gated the fix behind a future date, leaving the vulnerable code live today.

### Impact Explanation
The contract `hash` is the primary key/identifier used throughout `arbiter_contract.js` to look up, share, and update contract records across `wallet_arbiter_contracts` and to route/dedupe device messages (`getByHash`, `setField`, `shareUpdateToPeer`, `shareUpdateToCosigners`) [5](#0-4) [6](#0-5) [7](#0-6) . It also determines the shared multisig address that ultimately controls the disputed funds, and it is the datum an arbiter uses to adjudicate. If a malicious counterparty or a compromised relaying device can construct two structurally different contracts (different title/text, different party-name split) that hash identically, they can cause disagreement between the payer, payee, and arbiter about the true terms of the contract while all parties reference "the same" contract by hash — enabling a payer to later dispute or an arbiter to rule based on forged terms, potentially resulting in wrongful release/freezing of the escrowed funds. This falls within the accepted impact categories (AA/contract fund loss or freezing, node/party disagreement on the true content bound to an identifier).

### Likelihood Explanation
Exploitability requires only that the attacker is one of the two contracting parties (or an intermediate device relaying the contract offer) — a normal, unprivileged participant in the wallet's arbiter-contract flow, matching the "paired device / contract counterparty" reachability the scope explicitly allows. No cryptographic break is needed: constructing a byte-identical concatenation with a different field split is a simple string-manipulation exercise (choose a title ending in the same characters that begin the intended forged text, etc.), which is straightforward given usual human-language contract titles/text. The vulnerability is live today because `NEW_HASH_DATE` (2026-11-01) has not yet passed relative to the current date (2026-09-15).

### Recommendation
Change `getHash`/`getHashSrc` to always use an unambiguous encoding (the delimiter-based or, better, a structured/length-prefixed or JSON-canonical encoding such as `objectHash.getBase64Hash` used elsewhere in the codebase) immediately, rather than gating the fix behind a future `NEW_HASH_DATE`. At minimum, move `NEW_HASH_DATE` to a date in the past (or remove the legacy branch entirely) so all currently created contracts use the delimiter-safe hashing, and ensure the delimiter (`"[|#|]"`) itself cannot appear inside `title`/`text`/party name fields (reject or escape it) to fully close the cross-linking gap.

### Proof of Concept
1. Attacker composes contract A with `title = "Pay for car"`, `text = "no refunds"`, other fields fixed, `creation_date` = today (before `NEW_HASH_DATE`).
   `src_A = "Pay for car" + "no refunds" + creation_date + payer_name + arbiter_address + payee_name + amount + asset`
2. Attacker crafts contract B with `title = "Pay for car"+"no"`, `text = " refunds"`, all other fields identical.
   `src_B = "Pay for car" + "no" + " refunds" + creation_date + payer_name + arbiter_address + payee_name + amount + asset`
3. `src_A === src_B` (identical concatenation), so `getHash(A) === getHash(B)` even though contract A and contract B display different title/text to a human reviewing them.
4. Attacker sends contract B (with its more favorable/misleading text) to the counterparty or arbiter while referencing/quoting the hash that was originally agreed for contract A, creating ambiguity about which terms were actually agreed to.
