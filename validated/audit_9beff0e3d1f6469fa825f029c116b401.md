### Title
Cross-tenant commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/commit.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by SHA, with no scoping to the repository/organization that the webhook signature was verified against. Because git SHAs are content-addressed and identical across forks/shared history, an attacker who controls the webhook secret for *any* organization configured in this Shipit instance can forge a `status` event whose `sha` matches a commit tracked by a completely different (victim) stack, causing `Commit#add_status` to fire `Hook.emit(:commit_status/:deployable_status, victim_stack, ...)` with attacker-controlled `target_url`/`description`.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`organization_verified_by_signature (repository_owner from the payload, checked against Shipit.github(organization: repository_owner)) == organization_that_owns_the_stack_whose_commit_is_mutated (commit.stack.repository owner, resolved later by StatusHandler)`

Trace:
1. `Shipit::WebhooksController#verify_signature` reads `repository_owner` straight from the attacker-supplied JSON body (`params.dig('repository','owner','login')`) and looks up the corresponding `GitHubApp` config via `Shipit.github(organization: repository_owner)`, then checks the HMAC signature against `@webhook_secret` for *that org only*. [1](#0-0) 
2. Signature verification is entirely self-referential to the `repository`/`organization` field the attacker put in the body — it never checks that this org actually owns the commit that will be mutated.
3. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a completely global, unscoped-by-repository/stack lookup across the *entire installation*. [2](#0-1) 
4. `Commit#create_status_from_github!` → `add_status` unconditionally emits `Hook.emit(:commit_status, stack, ...)` and `Hook.emit(:deployable_status, stack, ...)` for whatever `stack` owns each matched commit — using the attacker-supplied `state`/`target_url`/`description` fields from `params`, verbatim. [3](#0-2) [4](#0-3) 
5. `Status.replicate_from_github!` persists `target_url`/`description` directly from the payload with no sanitization. [5](#0-4) 

**Attack request**: attacker sends `POST /webhooks` with `X-Github-Event: status`, body:
```json
{"sha":"<victim-commit-sha>","state":"success","target_url":"http://attacker.example/leak","description":"pwned","repository":{"owner":{"login":"<attacker-controlled-org>"}}}
```
signed with the webhook secret of `<attacker-controlled-org>` (an org the attacker legitimately controls/owns on this Shipit instance, or any org whose `webhook_secret` config is blank — `GitHubApp#verify_webhook_signature` returns `true` unconditionally in that case: `return true unless webhook_secret`). [6](#0-5) 

If `<victim-commit-sha>` matches a commit SHA tracked by any *other* stack (trivially achievable via a shared commit history / fork, since SHAs are content-addressed and identical across forks for unmodified commits), the victim stack's `Hook`s fire with attacker content, even though the attacker never authenticated for, and holds no secret belonging to, the victim's organization.

**Why existing guards fail**: `verify_signature` only proves "the sender knows the secret for the org named in the payload"; it never re-derives or checks the org/repo that actually owns the resolved `Commit`/`Stack`. `StatusHandler#process` performs no additional repository/stack scoping — it trusts the global SHA index across all tenants.

### Impact Explanation
An attacker who controls the webhook secret of any single organization onboarded to a shared Shipit instance (or any org configured with no `webhook_secret`) can mutate commit status state and trigger outbound `Hook` deliveries (Slack/webhook notifications, `commit_status`/`deployable_status` events) for a **different tenant's stack**, injecting attacker-controlled `target_url`/`description` text into that victim's integration, and can also flip commit state to `success`, which triggers `stack.schedule_merges` — potentially enabling unauthorized merges via the merge queue for a stack the attacker does not own. This matches the "Critical" category: a payload for one repository mutating another's stack/commit and causing an unauthorized state transition. It is repeatable against any stack whose tracked commits share a SHA with a commit visible to the attacker (public repos, forks, cherry-picks, or shared upstream history), and does not require compromising GitHub or Shipit secrets belonging to the victim.

### Likelihood Explanation
Preconditions: (a) the attacker must know a valid webhook secret for *some* organization known to this Shipit instance — either their own legitimately onboarded org, or any org configured without a `webhook_secret` (accepted by `verify_webhook_signature`'s early-return); (b) the victim stack must contain a commit whose SHA is also reachable/known to the attacker (public repos, forks sharing history, or any coincidental SHA collision across tracked repos). Both preconditions are realistic in any multi-tenant Shipit deployment tracking public/forked GitHub repositories. The attack costs a single crafted HTTP POST with a correctly computed HMAC using a secret the attacker legitimately possesses — no GitHub App private key, no session, and no victim-side credentials are required, and it is fully repeatable/scriptable against arbitrary stacks sharing SHAs.

### Recommendation
Scope the `status` webhook's commit resolution and signature verification to the same repository: `StatusHandler#process` should filter `Commit.where(sha: params.sha)` by the repository declared in the payload (joined through `stack.repository`), and `verify_signature`/`Hook.emit` should only ever affect stacks whose `repository.full_name`/owner matches the organization actually verified by the signature. Additionally, treat organizations without a configured `webhook_secret` as unverifiable (fail closed) rather than defaulting to `true`.

### Proof of Concept
Minitest plan (model or controller level):
```ruby
test "status webhook signed for org A cannot mutate a commit belonging to org B's stack" do
  attacker_stack = shipit_stacks(:cyclimse)   # owned by "attacker-org"
  victim_stack   = shipit_stacks(:shipit)     # owned by "victim-org", has a deployable_status Hook fixture

  shared_sha = "cafebabecafebabecafebabecafebabecafebabe"
  # Simulate the same commit SHA existing in both stacks (fork / shared history)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared", ...)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "shared", ...)

  body = {
    sha: shared_sha,
    state: "success",
    target_url: "http://attacker.example/leak",
    description: "pwned",
    repository: { owner: { login: "attacker-org" } }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_org_webhook_secret, body)

  Hook.expects(:emit).with(:deployable_status, victim_stack, has_entries(deployable_status: instance_of(Status)))

  @request.headers["X-Github-Event"] = "status"
  @request.headers["X-Hub-Signature"] = signature
  post :create, body: body, as: :json

  assert_response :ok
  # equality that should hold but doesn't:
  assert_equal "attacker-org", verified_org_for(signature)
  refute_equal verified_org_for(signature), victim_stack.repository.owner
  assert_equal "http://attacker.example/leak", victim_commit.reload.status.target_url
end
```
This asserts the binding is broken: the org verified via signature (`attacker-org`) differs from the org owning the mutated stack (`victim-org`), yet the victim's `Hook.emit(:deployable_status, ...)` fires with attacker-controlled `target_url`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
