### Title
Unauthorized `repay` on-behalf-of a stranger can force an Efficiency-Group downgrade and trigger premature liquidation - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`repay` accepts an arbitrary `on-behalf-of` principal and only checks `(is-eq contract-caller tx-sender)` — it never checks that the caller is, or is authorized by, the `account` being repaid. [1](#0-0)  An attacker can therefore repay a victim's debt in a specific asset using the attacker's own funds, without the victim's consent, choosing the exact amount needed to fully zero out that one debt asset.

### Finding Description
`repay` resolves `account` from the caller-supplied `on-behalf-of` optional (defaulting to `contract-caller` only if omitted), then calls `market-vault.debt-remove-scaled` on that account: [2](#0-1) 

In `debt-remove-scaled`, when the repayment brings the account's scaled debt for that asset to exactly zero, the account's position `mask` is updated to clear that debt bit via `mask-update`: [3](#0-2) 

This `mask` is the shared state that determines which Efficiency Group (`egroup`) governs the account's LTV-borrow and liquidation thresholds; the protocol's own documentation confirms that changing which assets are present in the mask can change the applicable egroup and can *decrease* the health capacity of a position — this exact risk is why a dedicated "Egroup Transition Protection" postcondition check was added to `collateral-add`: [4](#0-3)  No equivalent protection exists for the debt-removal path exercised by `repay`.

Because `repay` lets any unprivileged caller pick the exact `account` and pay off only one specific debt asset of a multi-asset position, the caller can deliberately strip out the debt bit that was making the account benefit from a favorable, asset-pair-specific Efficiency Group (e.g., a correlated-asset group with a high LTV-liquidation threshold). Once that bit is cleared, the remaining collateral/debt combination falls back to a different, less favorable egroup with a lower liquidation threshold — even though the account's absolute USD debt only decreased. This can push a previously healthy position below its (new) liquidation threshold, making it liquidatable purely as a side effect of a third party's unsolicited partial repayment, with no consent or benefit-check from the victim.

### Impact Explanation
The attacker (or a colluding second address) can then immediately call `liquidate` against the now-liquidatable victim, seizing collateral at the liquidation-penalty discount that the victim would never have been exposed to under their original, correlated-asset egroup. This is a case of a stranger's action (repay) making a victim's position evaluable/liquidatable under worse terms set by an egroup transition the victim never triggered — direct theft of the victim's collateral via a forced liquidation discount.

### Likelihood Explanation
Requires the attacker to hold (or borrow via flashloan strictly as capital, not as the exploit mechanism) the exact token/amount of one of the victim's debt assets and know the victim's position composition and applicable egroup boundaries — both of which are publicly readable on-chain via `market-vault`. No special privileges or DAO/oracle compromise are needed; only knowledge of which egroup transition is unfavorable, which is deterministic given the public egroup registry.

### Recommendation
Apply the same egroup-transition health/capacity postcondition check used in `collateral-add` to the debt-removal path invoked by `repay` (and any other path that can clear a debt bit on behalf of another account), or restrict `on-behalf-of` in `repay` to require the payer to be the account owner or an explicitly approved delegate, verifying that any resulting egroup change does not reduce the account's liquidation-threshold capacity for its remaining position.

### Proof of Concept
1. Victim holds correlated collateral+debt in Assets A and B, currently matched to Egroup G1 (favorable LTV-liq threshold for the A/B combination).
2. Attacker calls `repay(ft-for-asset-A, exact-remaining-debt-of-victim-for-A, (some victim))` using the attacker's own tokens. [2](#0-1) 
3. `debt-remove-scaled` zeroes victim's scaled debt for asset A and clears that bit in the victim's mask. [5](#0-4) 
4. Victim's remaining position (collateral A/B + debt B only) is now evaluated under a different Egroup G2 with a lower liquidation threshold than G1.
5. Victim's health ratio under G2 falls below the liquidation threshold even though nominal debt decreased.
6. Attacker calls `liquidate(victim, ...)` and seizes victim's collateral at the liquidation-penalty discount that would not have applied under G1.

(define-public (repay (ft <ft-trait>) (amount uint) (on-behalf-of (optional principal)))
  (let ((address (contract-of ft))
        (asset (try! (get-asset address)))
        (asset-id (get id asset))
        ;; defaults to payer (contract-caller) if not specified
        (account (match on-behalf-of behalf behalf contract-caller))
        
        ;; Step 1: Get position WITHOUT resolving prices
        (position (try! (get-position account)))
        (mask (get mask position))
        
        ;; Step 2: Accrue user's positions (populates cache for ztokens)
        (u-debt (accrue-user-debts (get debt position)))
        
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        
        ;; Step 3: Get account debt FIRST to enable safe amount capping
        (account-scaled-debt (get-account-scaled-debt account asset-id))
        
        ;; Step 4: Calculate max repayable amount (actual debt in token), mul-div-up for safe upper bound
        (max-repay-tokens (mul-div-up account-scaled-debt borrow-index INDEX-PRECISION))
        
        ;; Step 5: Cap input amount at actual debt - prevents overflow in scaled calculation
        (safe-amount (min amount max-repay-tokens))
        
        ;; Step 6: Convert to scaled debt (amount is bounded)
        (scaled-debt-repayment (mul-div-down safe-amount INDEX-PRECISION borrow-index))

        (repaid-scaled-debt (min account-scaled-debt scaled-debt-repayment))
        (amount-to-repay (mul-div-up repaid-scaled-debt borrow-index INDEX-PRECISION))
        
        ;; Check if repaying ALL debt for this asset
        (repaying-all (is-eq repaid-scaled-debt account-scaled-debt)))

    ;; preconditions
    (asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (> repaid-scaled-debt u0) ERR-INSUFFICIENT-SCALED-DEBT)

(define-public (debt-remove-scaled (account principal) (scaled-amount uint) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-scaled-debt user-id asset-id scaled-amount)))
        (nmask (if (is-eq remaining u0)
                      (mask-update mask asset-id false false) ;; debt, remove
                      mask))
        (updated-entry (merge entry (refresh nmask))))

    (try! (check-impl-auth))
    (asserts! (not (get debt-remove states)) ERR-PAUSED)
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
    
    (print {
      action: "debt-remove-scaled",
      caller: contract-caller,
      data: {
        account: account,
        asset-id: asset-id,
        scaled-amount: scaled-amount,
        updated-scaled-debt: remaining,
        mask-before: mask,
        mask-after: nmask
      }
    })
    
    (ok remaining)))

### Collateral-Add Egroup Transition Protection

**Issue**: Adding new collateral types can change a user's egroup, potentially decreasing their health capacity and making positions liquidatable.

**Protection Mechanism** (Implemented in `collateral-add`):

1. **Egroup Validation (ALL users)**:
   - Validates future mask (after adding collateral) matches an existing egroup
   - Uses subset matching: user's collateral-only mask can match collateral+debt egroups
   - Fails with `ERR-NO-EGROUP-FOUND` if no valid egroup exists

2. **Capacity Protection (Users with debt)**:
   - When adding NEW collateral type AND user has debt
   - Calculates: `current_capacity = collateral_usd × current_ltv`
   - Calculates: `future_capacity = (collateral_usd + new_collateral_usd) × future_ltv`
   - Validates: `future_capacity >= current_capacity`
   - Fails with `ERR-UNHEALTHY` if capacity would decrease

3. **Optimizations**:
   - Existing collateral: Skips all checks (safe to add more)
   - No debt: Skips capacity check (only validates egroup)
   - Minimal gas overhead for common cases

**Attack Scenarios Prevented**:
- Dust collateral poisoning (adding tiny amounts to worsen position)
- Self-liquidation exploits (manipulating egroup to trigger liquidation with penalty)
- Accidental position deterioration (users can't make themselves liquidatable by adding collateral)
