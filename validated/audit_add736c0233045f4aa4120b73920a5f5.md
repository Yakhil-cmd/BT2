### Title
CCMenu endpoint lets a stack-scoped ApiClient token read build status for any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper defined by `Shipit::Api::BaseController` and, in doing so, drops the scoping enforcement that restricts a stack-scoped `ApiClient` token to only the stack it was issued for.

### Finding Description
`BaseController#stack` resolves the requested stack through the `stacks` scope, which is deliberately narrowed to the client's authorized stack when the authenticating `ApiClient` is bound to one: [1](#0-0) 

This is the binding the rest of the API relies on: **stack a token authorizes == stack a token can touch**. It's exercised elsewhere, e.g. `StacksController#index`, where a stack-scoped client only sees its own stack: [2](#0-1) 

`CCMenuController`, however, redefines `stack` to bypass that scope entirely and instead resolve *any* stack directly from the URL parameter: [3](#0-2) 

Because `require_permission :read, :stack` only checks that the `ApiClient` has the `read:stack` permission bit (`ApiClient#check_permissions!`, `app/models/shipit/api_client.rb#L38-L45`) — not that the requested `stack_id` matches the client's `stack` association — any client holding `read:stack` can pass an arbitrary `stack_id` and the controller will happily load and render that unrelated stack's build status, regardless of the `stack_id` the token was scoped to at creation time (see fixture `here_come_the_walrus`, which is scoped to the `shipit` stack: `test/fixtures/shipit/api_clients.yml#L12-L17`).

Equality that should hold but is broken:
`current_api_client.stack_id (token-authorized stack) == params[:stack_id] (stack actually rendered)`

Before the request: a client token is minted scoped to stack A (`stack: shipit` in the fixture) with `read:stack` permission, intended to only ever surface CI status for stack A (this is exactly the intended use of the CCMenu integration, and is how `CCMenuUrlController#client` mints these tokens per-stack: `app/controllers/shipit/ccmenu_url_controller.rb#L15-L18`).

After the attacker's request: the same token, presented with a different `stack_id` in the URL, returns full build/CI status details for stack B (including `lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc.), because `CCMenuController#stack` never checks whether `params[:stack_id]` is the stack the client is scoped to.

### Impact Explanation
This qualifies as "unauthenticated read of stack state" style escalation, but more precisely it's a cross-stack authorization bypass: an `ApiClient` legitimately scoped to a single stack (the design intent of `CCMenuUrlController`, which mints exactly this kind of narrowly-scoped client) escalates to read build/deploy status, lock reason, and webUrl for every other stack in the installation. This is a High-severity authorization boundary break — it violates the "stack a token authorizes vs. stack it touches" binding without any additional privilege being granted to the attacker.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped CCMenu token (which is designed to be embedded in third-party CI dashboard tools, i.e., handed to lower-trust integrations) can trivially exploit this by changing the `stack_id` route segment in the request URL — no other capability is required.

### Recommendation
`CCMenuController#stack` should resolve the requested stack via the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot view stacks outside its authorized scope.

### Proof of Concept
1. Create/receive a CCMenu-scoped `ApiClient` token for stack `org/repoA/production` (as done by `CCMenuUrlController#client`, which creates a client with `permissions: %w[read:stack]` and a `stack:` association).
2. Using that token's `authentication_token`, issue: `GET /api/stacks/org/repoB/production/ccmenu?token=<tokenA>` (or via Basic Auth).
3. Observe the response returns `200 OK` with `<Project name="org/repoB/production" ...>` and full build status for `repoB`, even though the token was only ever authorized for `repoA`. Contrast this with `GET /api/stacks?...` using the same token, which correctly returns only `repoA` per `BaseController#stacks`.
