### Title
Duplicate entries in `r of set` / `weighted and` allow a single key to satisfy a multi-signer quorum - (File: definition.js)

### Summary
`ocore`'s address-definition validator (`validateDefinition` in `definition.js`) accepts `r of set` and `weighted and` definitions without checking that the members of `args.set` are distinct. This mirrors the reported `PortalToken.vestingDeposits` bug class: a list that is expected to represent distinct entities is never checked for duplicates, so a single logical actor can be counted multiple times, defeating the intended threshold/allocation logic.

### Finding Description
`validateDefinition`'s `evaluate()` function validates `r of set` and `weighted and` purely structurally: it requires `args.set.length >= 2`, that `required` is a positive integer not exceeding the set (or total weight), and recursively validates each set member — but it never verifies that the set members (e.g., `["sig", {pubkey: ...}]` leaves, or nested `["address", ADDR]` leaves) are pairwise distinct. [1](#0-0) [2](#0-1) 

At authentication time, `validateAuthentifiers`'s `evaluate()` treats each set element as an independent branch keyed by its own path (`path+'.'+index`), and simply counts how many branches succeed against `required` (or accumulates `weight`): [3](#0-2) [4](#0-3) 

Because paths are structural (`r.0`, `r.1`, …) rather than keyed by pubkey/address, if the set contains the same `sig` leaf (same pubkey) twice (e.g. `["r of set", {required: 2, set: [["sig",{pubkey:P}], ["sig",{pubkey:P}]]}]`), the holder of the single private key `P` can satisfy both branches by supplying the *same* deterministically-computed ECDSA signature (`sign()` in `signature.js` uses `ecdsa.ecdsaSign`, which for secp256k1 with RFC6979 nonce derivation is deterministic for a given message/key) at both paths `r.0` and `r.1`: [5](#0-4) 

This satisfies `count >= args.required` with only one real signer, even though the definition superficially declares a 2-(or N-)of-set multisig. The same applies to nested `["address", ADDR]` members pointing at the same underlying address inside `r of set`/`weighted and`, and to `weighted and` where duplicating a high-weight leaf inflates `weight_of_options_with_sig` well beyond what the distinct-signer count should allow.

The validation for how many authentifiers must be "used" only checks that the number of used paths equals the number of supplied authentifiers (`arrUsedPaths.length !== Object.keys(assocAuthentifiers).length`), not that they correspond to distinct keys: [6](#0-5) 

This is directly analogous to the `PortalToken` bug: a list (`vestingDeposits` / `set`) that the protocol implicitly assumes contains distinct entities is never checked for duplicates, so a duplicated entry lets one entity count twice (double minting there; here, double "signer" credit toward a quorum threshold).

### Impact Explanation
This affects any unprivileged address definition author (anyone composing a unit, an AA definition, or a shared/multisig wallet) reachable via `validateDefinition`/`validateAuthentifiers` in `definition.js`, which is invoked for both address definitions in unit authors and for asset `issue_condition`/`transfer_condition`. A malicious co-signer proposing a "2-of-3" (or higher) shared address (via `wallet_defined_by_addresses.js`'s `handleNewSharedAddress`/`createNewSharedAddress` flow) could construct a definition where two of the three "independent" set members actually resolve to the same key/pubkey they control, while honest co-signers approve the address believing funds require quorum from genuinely distinct parties. The attacker can then unilaterally authorize spends from the shared address using only their own key, resulting in unauthorized spending of funds that other parties believed were protected by a real multi-party quorum. This is a concrete unauthorized-spending / fund-loss impact reachable from a single malicious address-definition author, consistent with the required impact classes (unauthorized spending, AA fund loss).

### Likelihood Explanation
Likelihood is moderate-to-high in specific but realistic scenarios: shared/multisig address setups are a core, commonly used feature (`wallet_defined_by_addresses.js`), and the attacker only needs to control the address-definition template offered to cosigners (or to be one cosigner proposing the definition) and to reuse an already-approved own pubkey/address twice under different, superficially-independent signing paths. No cryptographic weakness beyond deterministic ECDSA signing is required (reusing the identical signature bytes at multiple authentifier paths is sufficient), and no consensus-rule change is needed — the definition and its authentication both pass current validation unmodified.

### Recommendation
In `validateDefinition` (`definition.js`), for `r of set` and `weighted and`, collect the set of resolvable leaf identities (pubkeys for `sig`, hashes for `hash`, target addresses for nested `address`/definition references) across `args.set` and reject the definition if any two members are structurally identical or resolve to the same key/address — analogous to the recommendation of sorting `vestingDeposits` and reverting on duplicates. At minimum, disallow byte-for-byte identical set members, and recursively detect identical nested subtrees that would allow a single authentifier value to double-count toward `required`/`weight`.

### Proof of Concept
1. Attacker (or a colluding cosigner) proposes a shared address definition:
   `["r of set", {required: 2, set: [["sig", {pubkey: P}], ["sig", {pubkey: P}], ["sig", {pubkey: Q}]]}]`
   where `P` is a pubkey controlled solely by the attacker and `Q` belongs to an honest cosigner. `validateDefinition` accepts this (structurally valid, `required <= set.length`). [7](#0-6) 
2. Honest cosigners approve the shared address believing 2 of {P, P, Q} independent signers are required (per `handleNewSharedAddress` flow in `wallet_defined_by_addresses.js`). [8](#0-7) 
3. To spend, the attacker signs the unit hash once with the private key for `P` via `signature.sign()` (deterministic), and submits that identical signature string at authentifier paths `r.0` and `r.1`. [5](#0-4) 
4. `validateAuthentifiers`'s `r of set` handler verifies both `r.0` and `r.1` against pubkey `P` successfully, `count` reaches `2 >= required`, and the unit is accepted — funds move without the honest cosigner `Q` ever signing. [3](#0-2) 

Note: I was unable to execute this scenario end-to-end (no test harness run), so the deterministic-signature reuse step (2) is based on the documented behavior of the `secp256k1` `ecdsaSign` API used in `signature.js`; if the underlying library or a caller adds non-deterministic randomness to signing, the attacker would still trivially satisfy this by signing twice (both signatures valid for the same key satisfy verification independently), so the core duplicate-set flaw is present in `definition.js` regardless.
