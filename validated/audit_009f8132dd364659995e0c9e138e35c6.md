### Title
Webhook signature verification authenticates the payload's declared organization, not the repository the event actually writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate a webhook against using the **unverified** `repository.owner.login` (or `organization.login`) field of the request body, but every event `Handler` subsequently resolves the target `Stack`/`Repository`/`Commit` using the **separate** `repository.full_name` (or bare `sha`) field from that same body. Nothing ties the field used to select the signing secret to the field used to decide what gets written. On a multi-organization Shipit deployment (see `docs/setup.md` "Using Multiple Github Applications"), anyone who obtains the `webhook_secret` for *any one* configured organization can forge a payload whose `repository.owner.login` matches that organization (so signature verification passes) while `repository.full_name`/`sha` references a stack belonging to a *different* tenant organization on the same instance, causing Shipit to act on that unrelated repository.

### Finding Description
`verify_signature` picks the verification key like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once verification passes, `create` re-parses the same raw body and dispatches it, unmodified, to every registered handler for the event:

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Every concrete handler (`PushHandler`, `StatusHandler`, PR handlers, etc.) then resolves the affected repository/stack from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`#repository_name`, or from a bare `sha` with no repository check at all: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` uses this to trigger a real sync against an attacker-chosen SHA: [5](#0-4) 

`StatusHandler#process` is worse: it does not consult `repository.full_name`/owner at all, it looks up commits **globally by `sha`** and writes a CI status onto whatever commit(s) match, across any stack on the instance: [6](#0-5) 

`Shipit.github(organization:)` only checks that the claimed organization name exists in `secrets.github`; it never checks that the organization claimed in the payload actually owns the repository named elsewhere in the same payload: [7](#0-6) 

This is the same class of bug as the `LineaRollup` report: a value used to satisfy an authorization/authentication check (`shnarfFinalBlockNumbers` / here, `repository.owner.login`) is decoupled from the value actually acted upon (`finalBlockInData` / here, `repository.full_name` or bare `sha`), and the code that used to (or should) bind them together is missing. Concretely, the equality that should hold but doesn't is:

`organization used to select/verify the HMAC secret == owner(repository actually mutated by the handler)`

### Impact Explanation
On a Shipit instance hosting multiple GitHub organizations (the documented, supported "Using Multiple Github Applications" configuration), a party who legitimately possesses (or leaks/obtains) the `webhook_secret` for one hosted organization's GitHub App — e.g., an org owner able to view/rotate that org's App secret in GitHub's settings — can forge a POST to `/webhooks` that:
- Passes signature verification (keyed off their own org name).
- Carries a `repository.full_name` pointing at a *different* tenant's stack, forcing `stack.sync_github(expected_head_sha: <attacker chosen sha>)`, effectively directing that other tenant's Stack to sync/deploy against an attacker-chosen commit reference; or
- Carries an arbitrary `sha`/`state` for the `status` event, forging a passing/failing CI status on any commit across the whole instance, which can be used to make an unsafe commit appear deployable (subverting Shipit's CI gating for deploys) — an unauthorized-deploy-adjacent condition.

This crosses a real repository/organization trust boundary and falls under the "cross-repository writes / unauthorized deploy" impact category, since it lets one tenant/organization's credentials cause writes and deploy-relevant state changes on another tenant's repository within the same shared instance.

### Likelihood Explanation
Requires the attacker to already hold a valid `webhook_secret` for at least one organization configured on the shared instance — this is a real but bounded privilege (host of a single GitHub App among several on a multi-tenant Shipit install), not a Shipit session/API token. Multi-organization hosting is an explicitly documented and supported configuration, so this is a realistic deployment shape, not a theoretical one. The likelihood is Medium: it needs one compromised/leaked/insider-held org secret, but no other Shipit-side credential.

### Recommendation
Bind the field used for signature-key selection to the field the handler will act on before dispatching:
- After successfully verifying the signature, re-derive `repository.full_name`'s owner and assert it equals `repository_owner` (case-insensitively) before calling `create`; reject (422) on mismatch.
- In `Handler#stacks`/`repository_name`, additionally verify that the resolved `Repository#owner` matches the organization whose secret validated the request (thread the verified organization through to handlers, e.g., via the payload or a dedicated context object, rather than trusting `repository.full_name` alone).
- For `StatusHandler`, scope the `Commit.where(sha: ...)` lookup to commits belonging to stacks under the verified organization, instead of searching globally by `sha`.

### Proof of Concept
Preconditions: Shipit configured with two organizations, `orgA` (attacker-controlled, secret `S_A` known to attacker) and `orgB` (victim, has stack `orgB/victim-repo`).

1. Attacker crafts a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(S_A, body)>` using `orgA`'s known webhook secret.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` → finds `orgA`'s app → `verify_webhook_signature` succeeds because the body was signed with `S_A`.
5. `create` dispatches the same payload to `PushHandler`, which resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — despite the request never being authenticated by `orgB`'s secret.

I was not able to execute this end-to-end in a running instance (no filesystem/terminal access here); the flow above is derived directly from the cited source, and confirming exact behavior of `Stack#sync_github` for such a forced SHA would benefit from a live/background Devin session with test execution to fully validate the downstream deploy impact.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
