### Title
Accrual reverts on `borrowed * borrow_index` overflow before the index cap engages, permanently freezing every position in a large high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` computes `scaled_to_original(borrowed, borrow_index)` (i.e., `borrowed.mul(env, borrow_index)`) before anything else, and `calculate_supplier_rewards` multiplies `borrowed` by the *new* borrow index again. `Ray::mul` panics with `MathOverflow` when the product exceeds `i128::MAX`. Although `update_borrow_index` clamps the index at `MAX_BORROW_INDEX_RAY` (1e36 raw), the debt *value* multiplication overflows far earlier — a market holding ~1e36 raw units of scaled debt hits the RAY-value ceiling at index ≈170x, well below the 1e9x cap. Because `interest::global_sync` runs `accrue_step` at the top of every pool mutation, once a market crosses this threshold no entrypoint on that market can ever execute again: `supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `claim_revenue`, `recapitalize`, and `flash_loan` all revert with `MathOverflow`. `recapitalize` cannot rescue the market because it too accrues first. All supplier cash in the market is permanently frozen.

### Finding Description
The crash chain:

1. `contracts/pool/src/interest.rs::global_sync` (lines 20-33) unconditionally calls `accrue_chunk` → `accrue_step` before any mutation of an existing market, matching the documented flow in `contracts/pool/README.md` (`Cache::load → global_sync → mutate → guards → commit`).
2. `common/src/rates/simulate.rs::accrue_step` line 60 calls `scaled_to_original(env, borrowed, borrow_index)`, which is `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`) → `fp_core::mul_div_*` → `panic_with_error!(MathOverflow)` when `borrowed * index` exceeds `i128::MAX` (`common/src/math/fp.rs:13-16`, `common/src/math/fp_core.rs`).
3. Even if step 2 survived, `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`) computes `borrowed.mul(new_borrow_index)`, again panicking on the same product once `borrow_index` grows.
4. `update_borrow_index` (`common/src/rates/index.rs:13-19`) only caps the *index* at `MAX_BORROW_INDEX_RAY`; it never bounds `borrowed * index`. The index cap is therefore unreachable protection: the value multiply fails first.

This is the analog of the CVE's untrapped out-of-bounds access on a crafted input: an unhandled arithmetic boundary condition on attacker-influenced state that crashes the only code path able to move funds.

Reachability for an unprivileged address:
- `supply` and `borrow` are permissionless. Caps are checked via `calculate_scaled_cap`, which deliberately *saturates* rather than rejects at `i128::MAX` (`common/src/rates/scaling.rs:26-33`, and `docs/reference/formulas.md` "a saturated scaled cap does not enforce the configured asset-unit limit"), and the admitted maximum is `i128::MAX / 10^(27-d)` ≈ 170 billion whole tokens — large enough to reach the cliff.
- An attacker supplies a whale-sized amount (their own capital or via `flash_position`/`multiply` leverage loops to build scaled debt), borrows to push utilization into the steep segment of the rate curve, then simply does nothing: passive interest accrual pushes `borrow_index` growth until the next touch panics. Any third party calling `update_indexes` triggers the freeze for everyone.
- The repository's own integration test demonstrates exactly this: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360` — a 1-billion-token, 18-decimal market at 98% utilization on the XLM curve panics with `MATH_OVERFLOW` inside `update_indexes` after a few simulated years, `last.borrow_index < MAX_BORROW_INDEX_RAY` ("the index cap did not engage"), and subsequent `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW`. `docs/reference/formulas.md:432-436` concedes "valid caps and bounded indexes do not guarantee that future accrual fits" but prescribes no mitigation or alarm — this is a numeric limit, not a designed fail-closed behavior, and the freeze is permanent rather than a per-call rejection.

### Impact Explanation
Permanent freezing of user funds, protocol-wide for the affected (hub, token) market. Every supplier's deposit and every borrower's collateral-backed position becomes unreachable: withdrawals, repayments, liquidations, revenue claims, and recapitalization all revert at accrual. Unlike a transient DoS, there is no recovery path — no entrypoint can skip `global_sync`, and the stored `borrowed`/`borrow_index` that cause the overflow cannot be rewritten. An attacker can deliberately push a shared market past the cliff, freezing all *other* users' funds in that market at the cost of their own (potentially flash-leveraged) position.

### Likelihood Explanation
No special privileges, keys, or oracle manipulation are needed — only a large position and time. The crash requires a market whose scaled debt is large enough that `borrowed * index` reaches `i128::MAX` before the index hits 1e36; for a saturated-cap 18-decimal market that is index ≈170x, which the XLM-curve steep segment reaches in single-digit years per the in-repo test, faster at sustained near-100% utilization. Smaller decimals raise the cliff but the mechanism is identical. Likelihood is gated by real capital required (borrowing capacity is limited by collateral and caps), which is why this is not guaranteed on thin markets; but on any market that admits whale-scale positions the attacker controls the trigger entirely — supply the principal, borrow the debt, wait, and the next accrual bricks the market for everyone.

### Recommendation
Make the accrual path survive the overflow instead of trapping:

- In `accrue_step`, compute the debt/supply value products through saturating or widened (`I256`) arithmetic — e.g., a `mul_saturating` variant alongside `fp_core::mul_div_floor_saturating` — so utilization and reward splitting clamp rather than panic.
- Engage the index cap *before* the value multiply: short-circuit `accrue_step` when `borrow_index` is already at `MAX_BORROW_INDEX_RAY`, and/or clamp `new_borrow_index` to the largest index for which `borrowed * index` still fits `i128` (analogous to how `update_supply_index` bounds its result and `protocol_fee_shares` caps at share headroom).
- Enforce a *value* ceiling at entry: bound `supplied`/`borrowed` scaled totals so `scaled * MAX_*_INDEX_RAY < i128::MAX` always holds, turning the arithmetic limit in `docs/reference/formulas.md` into a real admission check rather than a documented hazard.
- Add a regression test asserting post-freeze recoverability (repay/withdraw succeed at the index cap) in place of the current freeze-asserting test.

### Proof of Concept
```text
// Mirrors tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

// Attacker supplies ~1e9 whole tokens (within the admitted cap domain)
// and borrows 98% of it using own collateral.
t.supply_raw(ATTACKER, "BIG18", BILLION * 10i128.pow(18));
t.supply_raw(ATTACKER, "COL", collateral);
t.borrow_raw(ATTACKER, "BIG18", debt_at_98pct_util);

// Time passes; each yearly accrual compounds the borrow index.
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } // MathOverflow
}

// Market is bricked: every entrypoint accrues first and panics in
// scaled_to_original (borrowed * borrow_index > i128::MAX).
assert_contract_error(t.try_withdraw_raw(VICTIM, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ATTACKER, "BIG18", 1.0),   errors::MATH_OVERFLOW);
// Index cap never engaged: last.borrow_index < MAX_BORROW_INDEX_RAY.
// All supplier cash in BIG18 is permanently frozen.
```

Key code path: `pool::interest::global_sync` → `common::rates::accrue_step` (`common/src/rates/simulate.rs:60`) → `scaled_to_original` → `Ray::mul` → `panic_with_error!(MathOverflow)` (`common/src/math/fp.rs:13-16`), while `update_borrow_index`'s cap at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`) never gets a chance to fire.
