### Title
Cross-repository commit status injection via unscoped `StatusHandler` webhook processing - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the GitHub App configured for **the organization named in the payload's own `repository.owner.login` field** [1](#0-0) . That verification only proves the request was signed by *some* organization's registered webhook secret — it says nothing about which repository/commit the event is allowed to affect. For the `status` event, `StatusHandler#process` never re-checks the payload's `repository` field: it looks up commits globally by SHA across the entire installation and writes a status to whatever it finds.

### Finding Description
The base `Handler` class exposes a `stacks` helper that scopes work to the repository the webhook actually claims to be about: `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) . Handlers like `PushHandler` and `CheckSuiteHandler` correctly use this scoped `stacks` collection [3](#0-2) [4](#0-3) .

`StatusHandler` breaks this pattern. Its parameter schema only requires `sha`/`state` (no `repository` binding at all), and it queries `Commit` directly with no repository/stack scoping: [5](#0-4) 

This produces the binding break: **organization authenticated (via `repository_owner` used to pick the webhook secret) ≠ repository actually written (any `Commit` row across all stacks whose `sha` matches)**. Signature verification only proves "this HMAC matches organization X's secret"; it never constrains which commit/stack the event content is allowed to mutate. `Commit.create_status_from_github!` then creates a `Status` scoped to the *victim* commit's own `stack_id` [6](#0-5) , and `Status.replicate_from_github!` persists attacker-controlled `state`/`context`/`description`/`target_url` [7](#0-6) .

GitHub's Statuses API does not require the target `sha` to actually belong to the calling repository — any repository with write access can `POST /repos/{owner}/{repo}/statuses/{sha}` for an arbitrary 40-hex-character SHA, including SHAs that belong to a completely different, unrelated repository (commit SHAs are public information visible on GitHub). Because `StatusHandler` never validates that the commit's stack corresponds to the webhook's own `repository` payload field, any organization/repository already onboarded onto the Shipit instance (i.e., an "unprivileged" tenant with no access to the victim's org, secret, or stack) can forge a legitimate, correctly-signed webhook for its **own** repo that targets a **victim's** commit SHA.

### Impact Explanation
`Commit#deployable?` is derived directly from status state (`success? && !blocked?`) [8](#0-7) , and `MergeRequest#reject_unless_mergeable!` / `all_status_checks_passed?` rely on the same `Status`/`StatusChecker` data [9](#0-8) . By injecting a forged `success` status with a required context name into a victim stack's commit, an attacker with no privileges on that stack can satisfy `ci.require`/deployability checks and unblock an unauthorized deploy or PR merge on a repository/stack they do not control. This crosses the "unauthorized deploy" / "cross-repository writes" bar for a High/Critical finding.

### Likelihood Explanation
Requires only: (1) the attacker's own organization/repo is already a legitimate, onboarded Shipit tenant (a normal, unprivileged customer, not the victim's org, no access to victim's `webhook_secret` or repo), and (2) knowledge of a target commit SHA in the victim's repository (public via GitHub). The attacker uses GitHub's own status API on their own repo to have GitHub generate a correctly signed webhook — no forged HMAC or secret compromise is required from the attacker's side.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the same repository-derived `stacks` association the other handlers use (e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of a bare `Commit.where(sha: params.sha)`, so a status can only be attached to a commit belonging to the repository named in the webhook payload.

### Proof of Concept
1. Attacker controls `attacker-org/attacker-repo`, already registered as a Shipit stack with its own valid GitHub App installation/webhook secret (no relationship to the victim).
2. Attacker calls GitHub's REST API: `POST /repos/attacker-org/attacker-repo/statuses/{victim_sha}` with `state=success`, `context=<victim's required CI context>`, where `victim_sha` is a known commit SHA from `victim-org/victim-repo` tracked by the same Shipit instance.
3. GitHub delivers a `status` webhook to Shipit, signed with `attacker-org`'s legitimate webhook secret; `payload.repository.owner.login == "attacker-org"`, so `verify_signature` succeeds [10](#0-9) .
4. `StatusHandler#process` runs `Commit.where(sha: victim_sha)` (no repository check) and finds the victim's `Commit`, creating a `Status` record scoped to the **victim's stack** [11](#0-10) .
5. The victim commit's `deployable?`/merge-readiness state is now influenced by attacker-controlled data, potentially unblocking a deploy/merge the attacker has no authorization over.

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end
