### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event is dispatched against the repository named in `repository.full_name` — allowing cross-repository/cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App config (and thus which `webhook_secret`) to check the HMAC signature against using one attacker-supplied JSON field (`repository.owner.login`), while `Webhooks::Handlers::Handler#stacks` resolves *which repository/stack the event actually mutates* using a second, independent attacker-supplied field (`repository.full_name`). These two fields are never required to match, so an attacker who can satisfy the signature check for any one configured organization can still direct the event payload at a stack belonging to a completely different, unrelated repository.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

`repository_owner` is read straight from the unauthenticated raw body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `GithubApp` config, and `verify_webhook_signature` explicitly treats a blank/unconfigured secret as automatically valid: [3](#0-2) 

Shipit explicitly supports multiple GitHub Apps/organizations configured independently, each with its own (optionally blank) `webhook_secret`, as shown in the documented multi-org secrets format and in the test fixture that configures a second organization with a nil `webhook_secret`: [4](#0-3) 

Once signature verification passes (by claiming `repository.owner.login` to be the org whose secret is blank/known), the actual event handler resolves the target completely independently, via `repository.full_name`: [5](#0-4) 

This is exactly the pattern from the referenced report: a value is checked/verified via one binding, but a *different* value that isn't covered by that check is what actually gets acted on. Here, the "organization that authenticated" (`repository.owner.login`, used to select the app/secret) is never bound to "the repository that is written" (`repository.full_name`, used to resolve `stacks`/`Repository.from_github_repo_name`). Handlers such as `PushHandler` (triggers `GithubSyncJob`), the `status` handler (creates `Commit::Status` records that can gate continuous deployment), and the pull-request handlers (label capture, assign, close) all operate on whatever `repository.full_name` says, with no re-verification tied to the org that was actually authenticated.

### Impact Explanation
An attacker who can pass signature verification for any single configured organization (e.g., one with a blank `webhook_secret`, or one whose secret has otherwise leaked/is known to them) can forge webhook deliveries directed at *any other repository/stack tracked by the same Shipit instance*, including ones belonging to organizations with a properly configured, secret webhook. Concretely this allows:
- Forging `status` webhooks to create a fabricated successful `Commit::Status` for a victim stack's commit, which can drive Shipit's continuous-deployment pipeline into deploying that commit without ever having a genuine, signed CI status from the real repository — an unauthorized deploy.
- Forging `push` webhooks to trigger `GithubSyncJob` against an arbitrary stack.
- Forging `pull_request` events to trigger label-driven actions (assign/close/label-capture) on PRs belonging to a repository the attacker does not control.

This crosses the "an organization that authenticated versus the repository that is written" trust boundary called out in scope, and the worst-case consequence (forged CI status enabling continuous deployment) maps to the "unauthorized deploy" Critical-impact bucket.

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured GitHub organization/App whose `webhook_secret` is blank or otherwise known/guessable to the attacker (a pattern explicitly supported and exercised in `test/dummy/config/secrets_double_github_app.yml`), while other organizations onboarded to the same Shipit instance have properly configured secrets. Given multi-tenant Shipit deployments that track many GitHub organizations, and that this is a documented supported configuration rather than a documented anti-pattern, the likelihood is non-trivial in any installation using the multi-organization `github:` secrets format where not every org key has a webhook secret set.

### Recommendation
Bind signature verification to the repository actually being acted upon, not to an independently-controlled field in the same untrusted payload:
- Require `repository.full_name`'s owner to equal `repository_owner` (or better, derive the app/secret used for both routing and verification from a single, consistent source), and reject the webhook otherwise.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank for any organization that has repositories with other organizations sharing this Shipit instance; require an explicit, deliberate "unauthenticated" opt-in that also restricts the handler from acting on repositories belonging to any other configured organization.

### Proof of Concept
Given a `secrets.yml` with organizations `OrgTwo` (blank `webhook_secret`) and `victim-org` (real, secret `webhook_secret`), both onboarded to the same Shipit instance:
1. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` (or any garbage value).
2. Body:
```json
{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/whatever",
  "target_url": "https://attacker.example/fake",
  "branches": [{ "name": "master" }]
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the header sent.
4. `Handlers::Handler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")`, and the status handler creates a forged successful `Commit::Status` on `victim-org/victim-repo`'s commit — potentially triggering continuous deployment for a repository/organization the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
