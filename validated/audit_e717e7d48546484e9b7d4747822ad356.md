### `scoreCheckpointInterval()` and `calcCheckpointBlock` [1](#0-0) 

With `VRankEpoch = 1001`: `scoreCheckpointInterval() = 1001 / 8 = 125` (integer division). [2](#0-1)

`1000 % 125 == 0`, so a checkpoint containing the full epoch-0 CPMatrix is persisted at block 1000.

### `loadCPMatrixCheckpointInEpoch` has no epoch boundary guard [4](#0-3) 

The function name says "InEpoch" but it never checks that `cpNum >= calcEpochStart(blockNum, vrankEpoch)`. It simply calls `calcCheckpointBlock(blockNum, checkpointInterval)` and reads whatever is stored there.

Contrast this with `lookupCPMatrixCache`, which **does** enforce the epoch boundary: [5](#0-4) 

The cache probe loop is bounded by `epochStart`, but the disk checkpoint load is not.

### The contamination path in `lookupCFSSeed` [6](#0-5) 

On a cold start (empty cache), `lookupCPMatrixCache` misses, then `loadCPMatrixCheckpointInEpoch(1001)` returns `(1000, epoch0_cpMatrix, true)`. The function returns `start=1001, seed=epoch0_cpMatrix`. Back in `getCPMatrix`, since `start(1001) <= blockNum(1001)`, `applyBlocksForCPMatrix` runs block 1001 **on top of the epoch-0 CPMatrix**, permanently contaminating the epoch-1 accumulation.

### The epoch boundary condition

The contamination triggers when `epochStart % checkpointInterval != 0`, i.e., when `VRankEpoch` is not a multiple of 8. With `VRankEpoch = 1001`:
- Epoch 1 starts at block 1001
- `1001 % 125 = 1 ≠ 0` → `calcCheckpointBlock(1001, 125) = 1000` (previous epoch's last checkpoint)

With `VRankEpoch = 1000`:
- `1000 % 125 = 0` → `calcCheckpointBlock(1000, 125) = 1000` (the epoch-start block itself, whose CPMatrix is fresh because `cfReport` returns empty at epoch-start blocks per the guard in `cfReport`) [7](#0-6)

### Title
Cross-Epoch CPMatrix Contamination in `loadCPMatrixCheckpointInEpoch` Corrupts CFS Scores — (`kaiax/vrank/impl/init.go`)

### Summary
`loadCPMatrixCheckpointInEpoch` resolves the checkpoint block number using `calcCheckpointBlock(blockNum, scoreCheckpointInterval())` without verifying that the resolved block falls within the current epoch. When `VRankEpoch` is not divisible by 8, the most recent checkpoint block before the epoch start belongs to the **previous epoch**, and its accumulated CPMatrix is silently loaded as the seed for the new epoch, violating the invariant that CFS accumulation must start fresh at every epoch boundary.

### Finding Description
`scoreCheckpointInterval()` returns `VRankEpoch / 8` (integer division). When `VRankEpoch` is not a multiple of 8, epoch boundaries do not align with checkpoint boundaries. Specifically, `calcCheckpointBlock(epochStart, checkpointInterval)` returns a block number **less than** `epochStart`, which is the last checkpoint of the previous epoch.

`PostInsertBlock` writes a checkpoint at every multiple of `scoreCheckpointInterval()`, so a checkpoint containing the full previous-epoch CPMatrix exists at that block. When `lookupCFSSeed` is called on a cold cache (e.g., after node restart or at the very first block of a new epoch), `lookupCPMatrixCache` misses, and `loadCPMatrixCheckpointInEpoch` loads the previous epoch's CPMatrix without any epoch boundary validation. This CPMatrix — containing all reporter counts from the prior epoch — becomes the seed for the new epoch's accumulation.

The cache lookup (`lookupCPMatrixCache`) correctly enforces the epoch boundary by bounding its probe loop to `epochStart`: [5](#0-4) 

But the disk checkpoint load does not: [4](#0-3) 

### Impact Explanation
The contaminated CPMatrix carries over `map[candidate][reporter]uint64` counts from the previous epoch. `generateCFSFromCPMatrix` then computes CFS scores from this inflated matrix: [8](#0-7) 

Candidates with non-zero prior-epoch reporter counts receive artificially elevated CFS scores in the new epoch. If these scores exceed the exclusion threshold, the affected candidates are unjustly removed from the permissionless validator set, causing them to lose staking rewards they are entitled to. This constitutes incorrect reward distribution affecting KAIA.

### Likelihood Explanation
The bug triggers automatically on any node that:
1. Uses a `VRankEpoch` not divisible by 8 (e.g., 1001, 999, any non-multiple-of-8 value), and
2. Has a persisted checkpoint at the last checkpoint block of the previous epoch (normal operation — `PostInsertBlock` writes this unconditionally).

No attacker action is required. The contamination occurs passively on every cold-cache lookup at the start of a new epoch. The in-memory cache masks the bug during a continuous run, but any node restart exposes it.

### Recommendation
Add an epoch boundary guard in `loadCPMatrixCheckpointInEpoch`:

```go
func (v *VRankModule) loadCPMatrixCheckpointInEpoch(blockNum uint64) (uint64, vrank.CPMatrix, bool) {
    epochStart := calcEpochStart(blockNum, v.vrankEpoch())
    cpNum := calcCheckpointBlock(blockNum, v.scoreCheckpointInterval())
    if cpNum < epochStart {
        return 0, nil, false  // checkpoint belongs to a prior epoch
    }
    cpMatrix := ReadCheckpointCPMatrix(v.ChainKv, cpNum)
    if cpMatrix == nil {
        return 0, nil, false
    }
    return cpNum, cpMatrix, true
}
```

Apply the same fix to `loadPFSCheckpointInEpoch`. Alternatively, ensure `VRankEpoch` is always a multiple of 8 at the configuration level, but a code-level guard is more robust.
