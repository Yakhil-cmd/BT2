### Title
Unvalidated `AllowPermissionsURL` from codespaces API response is passed directly to browser/HTTP without host validation - ([File: pkg/cmd/codespace/create.go])

### Summary
When `CreateCodespace` fails with a permissions-required error, `create.go` extracts `AllowPermissionsURL` from the parsed `api.AcceptPermissionsRequiredError` and passes it unchecked to `a.browser.Browse(allowPermissionsURL)`. There is no validation that the URL points to the expected GitHub host (`githubServer`/`ghinstance`) before it is opened in the victim's browser.

In `pkg/cmd/codespace/create.go`, on a `CreateCodespace` failure the code does: [1](#0-0) 
and then, in `handleAdditionalPermissions`, the URL is used directly for both a non-interactive message and, in the interactive path, opened with `a.browser.Browse(allowPermissionsURL)`: [2](#0-1) 

Neither `create.go` nor `internal/browser/browser.go` performs any host allowlist check on the URL before opening it: [3](#0-2) 

The codebase does contain a host-validation utility (`internal/safeurl`) that is used elsewhere in `internal/codespaces/api/api.go` (e.g. `safeurl.JoinPathWithHostPrefix`) for constructing outbound request URLs to the GitHub API/server, but this safeguard is not applied to `AllowPermissionsURL`, which originates entirely from the JSON body of a 401 response and is treated as trusted output rather than validated input: [4](#0-3) 

I was not able to fully inspect the exact `startCreate`/`AcceptPermissionsRequiredError` unmarshalling code block inside `internal/codespaces/api/api.go` (grep confirmed matches but I could not retrieve the surrounding lines before running out of tool calls), so I cannot confirm from source whether the API layer itself performs any sanity check on the URL's host before returning it in the error struct. Based on the confirmed consumer code in `create.go`, no such check exists at the point of use.

### Impact Explanation
If the codespaces backend for a given repository returns an `allow_permissions_url` value that does not point to the expected GitHub host (e.g., an attacker-influenced string reflecting into a permissions-required response), the CLI will either:
- print the raw URL for the user to open manually (non-interactive path), or
- open it directly in the victim's default browser (interactive path) via `a.browser.Browse`.

If that URL is attacker-controlled and points to a non-GitHub host, this could be used for phishing, or if it points to an internal/authenticated GitHub-adjacent endpoint, could result in unintended requests/redirects using the victim's browser session. This corresponds to a "wrong-host request" / output-safety class issue rather than direct token exfiltration, since the CLI itself does not attach any bearer token to the browser-opened URL — the risk is bounded by what the browser session does (e.g., cookie-based auth) with an unexpected host.

### Likelihood Explanation
Exploitability requires that GitHub's own Codespaces backend (server-side, not attacker-controlled directly) echoes an attacker-influenced value into the `allow_permissions_url` field of the 401 response — this is a strong precondition outside of the CLI's control and not something an unprivileged repo owner can directly demonstrate purely from the `gh` client code. The CLI-side gap (missing host validation before use) is real and confirmed, but whether the backend is actually susceptible to attacker influence over this field is unverified and outside the scope of this repository's code.

### Recommendation
Before displaying or opening `AllowPermissionsURL`, validate that its host matches the configured `githubServer`/`ghinstance` host (using the existing `internal/safeurl` or `ghinstance` helpers) and reject/log an error if it does not, at the point where `AcceptPermissionsRequiredError` is constructed in `internal/codespaces/api/api.go`, and/or as a defense-in-depth check immediately before `a.browser.Browse(allowPermissionsURL)` in `pkg/cmd/codespace/create.go`.
