### Title
Stack-scoped `ApiClient` tokens can create stacks for arbitrary repositories, escaping their `stack_id` binding - ([File: app/controllers/shipit/api/stacks_controller.rb])

### Summary
`ApiClient#check_permissions!` only checks the generic `"#{operation}:#{scope}"` string (e.g. `write:stack`) and never checks *which* stack the operation targets. [1](#0-0)  The `Api::StacksController#create` action builds a brand-new `Stack` from attacker-supplied `repo_owner`/`repo_name` without ever going through the `stacks` scope that restricts a token to its bound `stack_id`. [2](#0-1) 

### Finding Description
`BaseController#stacks` is the mechanism that is supposed to bind a token to a single stack: if `current_api_client.stack_id?` is true, the token may only see/act on `Stack.where(id: current_api_client.stack_id)`; otherwise it can act on `Stack.all`. [3](#0-2)  `show`, `update`, `destroy`, and `refresh` correctly route through `stack`, which is defined as `stacks.from_param!(params[:id])` — i.e. scoped. [4](#0-3) 

However `create` does not use `stack` or `stacks` at all:
```ruby
def create
  stack = Stack.new(create_params)
  stack.repository = repository
  stack.save
  render_resource(stack)
end
``` [2](#0-1) 

The only gate on `create` is `require_permission :write, :stack, only: %i[create update destroy]`, which calls `current_api_client.check_permissions!(:write, :stack)` — a check that is purely string-based and carries no notion of *which* stack is being written. [5](#0-4) [6](#0-5) [1](#0-0) 

This breaks the intended equality:
`stack(s) that ApiClient#stack_id authorises == stack(s) the write:stack action actually touches`

A token whose `stack_id` binds it to Stack A can call `POST /api/stacks` with any `repo_owner`/`repo_name`/`environment`/`branch` and create a brand-new `Stack` for Repository B — a repository the token was never scoped to. `Repository.find_or_create_by(owner:, name:)` will even create the `Repository` record on the fly if it doesn't already exist. [7](#0-6) 

### Impact Explanation
This is a cross-repository write performed by a token that was deliberately restricted to one stack/repository — exactly the "Critical: cross-repository writes" category. A stack-scoped credential (the intended low-privilege use case for `ApiClient.stack_id`) is silently as powerful as an unscoped one for the `create` verb, defeating the entire purpose of stack scoping.

### Likelihood Explanation
Exploitation requires possession of any valid `ApiClient` token that has the `write:stack` permission and a `stack_id` set (i.e., a token meant to be confined to one stack) — this is the standard "least privilege" scoped-token deployment pattern the engine explicitly supports via `stack_id` and `stacks`. No admin session, GitHub App key, or webhook secret is needed; only the already-issued scoped API credential itself, which is the threat model this control exists to defend against.

### Recommendation
In `Api::StacksController#create`, ensure the new stack is only created when the token is unscoped, or, if the token is scoped to a `stack_id`, reject `create` (and any other action that could produce a stack outside that scope) entirely. More generally, `ApiClient#check_permissions!` should accept the target `Stack` (or `nil` for creation) and verify `current_api_client.stack_id.nil? || current_api_client.stack_id == target_stack&.id` before allowing `write:stack` operations, so the permission check enforces the same binding that `stacks`/`stack` enforce for read/update/destroy.

### Proof of Concept
1. An admin issues a token scoped to Stack A only: `ApiClient.create!(name: "ci-bot", stack_id: StackA.id, permissions: ["write:stack"])` (this is the supported `stack_id`-scoped configuration; see the `here_come_the_walrus` fixture pattern). [8](#0-7) 
2. Using that token's Basic-Auth credentials, call:
```
POST /api/stacks
{ "repo_owner": "someorg", "repo_name": "some-other-repo", "environment": "production", "branch": "main" }
```
3. `require_permission :write, :stack` only checks the token has `write:stack` in its permission list, not that it is limited to Stack A. [1](#0-0) 
4. `create` builds and saves a brand-new `Stack` for `someorg/some-other-repo`, a repository entirely outside Stack A's scope, proving the token escaped its `stack_id` binding. [2](#0-1)
