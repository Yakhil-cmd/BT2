### Title
`provision?` operator-precedence bug lets PRs provision ReviewStacks even when `review_stacks_enabled == false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends "review stacks must be enabled AND one of three provisioning policies allows it," but due to Ruby operator precedence (`&&` binds tighter than `||`), `repository.review_stacks_enabled` only gates the first disjunct (`provisioning_behavior_allow_all?`). The second and third disjuncts (`allow_with_label?` and `prevent_with_label?`) are evaluated independently of `review_stacks_enabled`, so a repository with review stacks explicitly disabled but `provisioning_behavior: prevent_with_label` (the enum's behavior when not `allow_all`) will still provision a `ReviewStack` and queue it for provisioning on any opened PR, without any label.

### Finding Description
The broken binding: the operator intends `repository.review_stacks_enabled == true` to gate all three provisioning policies, but as written it only gates policy 1.

Code at [1](#0-0) :
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Due to Ruby precedence this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

For a repository with `review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`, and `provisioning_label_name: nil`:
- Disjunct 1 is `false` (review_stacks_enabled is false).
- Disjunct 2 is `false` (behavior isn't allow_with_label).
- Disjunct 3: `provisioning_behavior_prevent_with_label?` is `true`, and `pull_request_has_provisioning_label?` calls `pull_request_label_names.include?(repository.provisioning_label_name)` which is `[...].include?(nil)` — `false` for any real PR labels — so `!false == true`. Disjunct 3 evaluates to `true`.

`provision?` returns `true`, so `respond_to_pull_request_opened?` returns `true`, and `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!`, which calls `create!` [2](#0-1) , creating a `ReviewStack` and adding it to `Shipit::ReviewStackProvisioningQueue`, all without checking `review_stacks_enabled` anywhere in this path. `ReviewStackAdapter#create!` and `stack_attributes` have no `review_stacks_enabled` check at all [3](#0-2) .

The `provisioning_behavior` enum defaults to `allow_all` at the DB/migration level [4](#0-3) , but any repository administrator who has explicitly set `provisioning_behavior: prevent_with_label` while intending review stacks to remain disabled (`review_stacks_enabled: false`) is affected — this is not a fringe or invalid configuration; it's a legitimate admin action (e.g., disabling the feature while a label policy remains configured, or never having enabled it while a label policy was set by another integration/default).

No other guard exists to prevent this: `NullRepository` (used when the repo record doesn't exist) has `provisioning_behavior_prevent_with_label?` return `false` [5](#0-4) , so that case is safe, but for a real `Repository` record matching the described config, nothing else in the process path re-checks `review_stacks_enabled`.

### Impact Explanation
Opening a pull request (an action any GitHub user with push access to a fork/branch can trigger, and which is forwarded via a legitimately-signed webhook from GitHub for that repository) causes a `ReviewStack` to be created and queued for provisioning against a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`). This leads to `Stack#provision` execution paths downstream (`Command#start` / deploy tooling) running for a feature the operator believed was off. This is a "record written / action taken for a repository whose configuration should have prevented it" — an authorization/config-gate bypass leading to unauthorized provisioning and downstream command execution against that repository's environment. It is repeatable for every opened PR against any repository sharing this `review_stacks_enabled: false` + `provisioning_behavior: prevent_with_label` configuration, but is scoped to the repositories that have that specific configuration; it does not let an attacker target arbitrary unrelated repositories they don't control the PR for.

### Likelihood Explanation
Requires a specific repository configuration: `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (a non-default but plausible admin configuration, e.g. temporarily disabling review stacks without resetting the behavior). Given that configuration, the attacker (anyone able to open a PR against that repo, including from a fork if the app is configured to receive such webhooks) needs zero extra effort — no label required, since the third disjunct is satisfied precisely when no provisioning label is present.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

### Proof of Concept
In a minitest test for `OpenedHandler` (mirroring the structure in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not provision a ReviewStack when review_stacks_enabled is false, even with prevent_with_label behavior and no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :prevent_with_label,
    provisioning_label_name: nil
  )

  params = pull_request_opened_payload(repository: repository, labels: [])

  assert_no_difference -> { Shipit::ReviewStack.count } do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process
  end
end
```
Before the fix: this assertion fails — a `ReviewStack` is created and added to `Shipit::ReviewStackProvisioningQueue` despite `review_stacks_enabled == false`. After applying the parenthesization fix, `provision?` returns `false` and no `ReviewStack` is created, matching the `review_stacks_enabled` binding.
