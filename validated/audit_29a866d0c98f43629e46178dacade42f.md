### Title
Private divisible-asset payment chains are forwarded to unrelated recipients/cosigners without per-address filtering - (File: divisible_asset.js)

### Summary
`getSavingCallbacks()` in `divisible_asset.js` builds a single combined array of all private output "chains" for a divisible-asset payment message and hands that identical, unfiltered array back to the caller as **both** `arrChainsOfRecipientPrivateElements` **and** `arrChainsOfCosignerPrivateElements`, with no per-address (`to_address`) filtering, unlike the indivisible-asset code path which explicitly filters by `to_address`.

### Finding Description
`composeDivisibleAssetPaymentJoint` supports sending a single private-asset payment message with multiple outputs to different addresses at once via `asset_outputs` / `outputs_by_asset` (plus a change output), all built into one `payload.outputs` array for one `message_index` [3](#0-2) . When the payment is private, `getSavingCallbacks().ifOk` reconstructs `arrPrivateElements` for the payload and, critically, passes that single combined list unchanged as both recipient chains and cosigner chains: [4](#0-3) 

In `wallet.js`'s `sendMultiPayment`, these two arrays are then routed to different parties: `arrChainsOfRecipientPrivateElements` is sent directly to `recipient_device_address` via `walletGeneral.sendPrivatePayments`, and `arrChainsOfCosignerPrivateElements` is forwarded to the sender's own wallet/shared-address cosigners via `forwardPrivateChainsToOtherMembersOfWallets` / `forwardPrivateChainsToOtherMembersOfSharedAddresses` [5](#0-4) . Because `divisible_asset.js` never filters by `to_address` (in contrast with `indivisible_asset.js`'s `getSavingCallbacks(to_address, callbacks)`, which builds `arrRecipientChains` only from outputs matching `to_address`) [6](#0-5) , the array sent to `recipient_device_address` as "recipient chains" for a divisible private asset can contain chain elements for outputs addressed to other, unrelated parties in the same message (e.g., a second `asset_outputs` destination, or the sender's own change output), and vice versa for whatever is labeled "cosigner chains".

On the receiving end, `handlePrivatePaymentChains` further propagates whatever it receives to *other members of any wallet owning any of the output addresses* in the whole received `arrChains` batch, again without filtering the batch down to only the chains relevant to that specific wallet: `forwardPrivateChainsToOtherMembersOfOutputAddresses` collects the union of all output addresses across all received chains and forwards the entire unfiltered `arrChains` to cosigners of every wallet that happens to own any single one of those addresses [7](#0-6) .

The net effect: a party who is only entitled to see their own output (amount, address, blinding factor) in a batched private-asset payment can end up receiving — and further re-forwarding to their own unrelated cosigners — private payment metadata (amount, address, blinding) belonging to a different output/recipient in the same message that they have no legitimate need to know. This mirrors the CVE-2023-30611 pattern: private metadata that is supposed to be scoped to one context (a private topic / a specific recipient's output) leaks to a party who is only tangentially connected to the artifact (another reactor in the topic / another cosigner or recipient of the same payment message).

### Impact Explanation
This exposes the address, exact amount, and blinding factor of one user's private-asset payment output to an unrelated third party (another output recipient's device, or an unrelated cosigner reached transitively via `forwardPrivateChainsToOtherMembersOfOutputAddresses`). Since blinding factors and addresses for private assets are meant to be revealed only to the parties directly involved in that specific output/spend chain, this is a confidentiality breach of financial transaction data for private assets (blackbytes-style assets), which was a core design goal of ocore's private-payment mechanism.

### Likelihood Explanation
This triggers whenever an unprivileged user composes a private-asset payment with multiple outputs to distinct addresses in one message (`asset_outputs`/`outputs_by_asset`, which is a normal, user-reachable wallet feature), or when a private-payment batch containing multiple heads is relayed through `handlePrivatePaymentChains`/`forwardPrivateChainsToOtherMembersOfOutputAddresses` on a shared/multisig wallet. No malicious peer, hub, or node behavior is required — a completely honest node performs the over-broad forwarding as designed by this code path.

### Recommendation
In `divisible_asset.js`'s `getSavingCallbacks`, thread a `to_address` (or a set of "my" addresses) parameter through analogous to `indivisible_asset.js`, and split `arrPrivateElements` into a strictly filtered `arrRecipientChains` (only elements whose `output.address === to_address`) and `arrCosignerChains` (elements relevant only to the payer's own shared/multisig addresses), rather than returning the same unfiltered array for both roles. Additionally, `forwardPrivateChainsToOtherMembersOfOutputAddresses` in `wallet.js` should filter the chains sent to each target wallet down to only those chains whose output address belongs to that specific wallet, instead of forwarding the entire received `arrChains` batch to any wallet that owns any one address in it.

### Proof of Concept
1. User A composes a private divisible-asset payment via `sendMultiPayment` with `asset_outputs = [{address: B_address, amount: X}, {address: C_address, amount: Y}]`, where B and C are different, mutually unrelated recipients on different devices/wallets, plus a change output back to A.
2. `composeDivisibleAssetPaymentJoint` places all three outputs (B, C, change) into a single `payload.outputs` array under one `message_index` for the private asset.
3. `getSavingCallbacks().ifOk` (divisible_asset.js:396-404) builds one `arrChains` from all three outputs and returns it unchanged as both `arrChainsOfRecipientPrivateElements` and `arrChainsOfCosignerPrivateElements`.
4. In `wallet.js`'s `preCommitCb` (wallet.js:2402-2437), `sendToRecipients` sends `arrChainsOfRecipientPrivateElements` — containing B's, C's, and the change output's private data — to `recipient_device_address`, revealing C's (and A's change) amount, address, and blinding to B's device even though B has no legitimate need to know about C's or A's private output data. Similarly, `sendToCosigners` forwards the same full set (including B and C's data) to A's own wallet cosigners via `forwardPrivateChainsToOtherMembersOfWallets`/`forwardPrivateChainsToOtherMembersOfSharedAddresses`.

Note: I was not able to fully trace, within the remaining tool budget, whether `sendMultiPayment`'s current input validation (`bTo`/`bAssetOutputs` exclusivity checks) always guarantees that `recipient_device_address` is unambiguous when `asset_outputs`/`outputs_by_asset` target multiple distinct devices in one call, or whether an upstream caller-side restriction prevents mixing unrelated recipients in a single divisible-asset call in practice. This should be verified directly in a full checkout of `wallet.js`'s `sendMultiPayment` argument-validation logic before treating this as fully weaponizable end-to-end, but the root-cause code defect — `divisible_asset.js` returning identical unfiltered chains for both roles, unlike `indivisible_asset.js` — is confirmed directly from the source.
