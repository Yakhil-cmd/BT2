### Title
Webhook signature verification is keyed on `repository.owner.login`, but the event handler acts on the unauthenticated `repository.full_name` field — a cross-organization write bypass - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization (and therefore the `webhook_secret` used for HMAC verification) using `params.dig('repository', 'owner', 'login')`. But the handler that actually mutates state (`Handler#stacks` / `Handler#repository_name`) looks up the target `Repository` using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so a payload can be signed correctly for organization A while directing the write to a repository belonging to organization B.

### Finding Description
The verification step: [1](#0-0) [2](#0-1) 
resolves the `github_app` (and hence the `webhook_secret` HMAC key) purely from `repository.owner.login` (falling back to `organization.login`), and calls `verify_webhook_signature` over the raw body. If verification succeeds, the entire raw JSON `params` (unmodified) is handed to the event handlers: [3](#0-2) 

Handlers, however, do not re-read `repository.owner.login` — they resolve the target `Stack`/`Repository` from a *different* JSON key, `repository.full_name`: [4](#0-3) 
which is passed straight into `Repository.from_github_repo_name`, itself just a `owner/name` split with a DB lookup — no cross-check against which organization's secret validated the request: [5](#0-4) 

The `push` handler then syncs the resolved stacks using attacker-supplied `after` (target SHA): [6](#0-5) 

So the binding that should hold is:
`organization whose webhook_secret verified the signature == organization owning the repository the handler writes to`

but the code only enforces:
`repository.owner.login (used for signature key selection) — independent of — repository.full_name (used for the actual Repository/Stack lookup)`

**Precondition analysis**: A GitHub App installation's `webhook_secret` is configured per-organization in `secrets.yml`/`Shipit.github(organization:)` (confirmed in `lib/shipit/github_app.rb` and `docs/setup.md`). GitHub itself sends webhook deliveries where `repository.owner.login` and `repository.full_name` are always consistent, so under normal GitHub-originated delivery this can't diverge. The divergence is only reachable if an attacker can submit a raw POST to `/webhooks` with a forged body whose `repository.owner.login` differs from its `repository.full_name` owner segment, and can produce a valid `X-Hub-Signature` for *some* organization's secret they know (e.g. because they are an admin/integrator for one low-trust org configured in this multi-tenant Shipit instance) while targeting a `Stack` that belongs to a different, unrelated organization/repository already registered in this Shipit instance.

### Impact Explanation
If exploitable, this would let a party who controls (or has compromised) the webhook secret for one onboarded GitHub organization forge `push`/`status`/`check_suite` events that are attributed and validated against their own org, but that name a `repository.full_name` belonging to a different organization's `Stack`. This can trigger `GithubSyncJob`, `RefreshCheckRunsJob`, or commit-status writes against a repository/stack the attacker's credentials should have no authority over — a cross-repository/cross-organization state manipulation. This matches the "cross-repository writes" Critical impact bucket, but only for Shipit deployments that configure **multiple** GitHub organizations (`Shipit.github(organization: ...)` supports per-org config, see `test/dummy/config/secrets_double_github_app.yml`) sharing the single `/webhooks` endpoint.

### Likelihood Explanation
Low-to-uncertain. This requires: (1) a multi-organization Shipit deployment, (2) the attacker already possessing a valid `webhook_secret` for at least one configured organization (itself a meaningful trust boundary — typically only the org's own GitHub App/webhook config holder has this, not an arbitrary unprivileged user), and (3) a target repository from a different org already present as a `Stack` in the same instance. None of the code paths reachable by a fully unprivileged external actor (no secret at all) are affected, since `verify_webhook_signature` still requires a correct HMAC for *some* configured secret. This is best classified as a design gap/missing cross-field consistency check rather than a bypass reachable by a zero-credential attacker, and I could not find any code path that lets an attacker skip signature verification entirely. Given the rules require excluding findings that "require... a privileged account" and this needs possession of a legitimate org's `webhook_secret`, this sits in a gray area of the specified scope.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature, additionally assert that the organization used to select the signing secret matches the owner segment of `repository.full_name` (or, more robustly, look up `Repository`/`Stack` first and confirm its `owner` matches `repository_owner` before invoking handlers). Alternatively, have `Shipit::Webhooks::Handlers::Handler#repository_name` derive the owner exclusively from the already-authenticated `repository.owner.login`/`organization.login` value rather than re-parsing `repository.full_name`.

### Proof of Concept
Not independently verified against a running multi-org instance — this requires a Shipit deployment configured with ≥2 organizations and possession of one org's `webhook_secret`, which I could not simulate via static analysis alone. Conceptually:
1. Configure Shipit with two orgs, `org-a` (attacker holds `webhook_secret`) and `org-b` (victim, has a `Stack` for `org-b/app`).
2. POST to `/webhooks` with header `X-Github-Event: push`, body `{"repository":{"owner":{"login":"org-a"},"full_name":"org-b/app"},"ref":"refs/heads/main","after":"<attacker-chosen sha>"}`, and `X-Hub-Signature` computed with `org-a`'s `webhook_secret` over that exact body.
3. `verify_signature` resolves `Shipit.github(organization: "org-a")` and successfully verifies the signature.
4. `PushHandler` resolves `Repository.from_github_repo_name("org-b/app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `org-b`'s stack. [7](#0-6) [8](#0-7)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
