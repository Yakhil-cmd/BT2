### Title
`gh skill install` upstream-redirect logic lets an attacker-controlled `SKILL.md` silently redirect installation to an arbitrary repository and strips the user's `--pin` protection - (File: pkg/cmd/skills/install/install.go)

### Summary
`installRun` in `pkg/cmd/skills/install/install.go` trusts unauthenticated `github-repo` frontmatter metadata embedded in the very `SKILL.md` file being installed to decide whether to redirect the installation to a different ("upstream") repository, then recurses into itself with the repository and pin fields overwritten. Because this metadata is fully attacker-controlled content served from the repository the user explicitly asked to install from, an attacker can make `gh skill install` fetch and install skill content from a completely different, attacker-chosen repository while discarding the safety of any `--pin` the user specified — conceptually the same "act-on-stale/attacker-influenced state after an external, attacker-influenced step" pattern as the CEI-violation reentrancy bug in the external report (state that should be fixed at request time is instead recomputed/overwritten based on data obtained during the same operation).

### Finding Description
`checkUpstreamProvenance` (`pkg/cmd/skills/install/install.go:1292-1374`) fetches the `SKILL.md` of the skill the user is installing via the GitHub Contents API and parses its YAML frontmatter for a `metadata.github-repo` key: [1](#0-0) 

If that key names a different repository than the one the user specified, the function treats it as legitimate "upstream provenance" and, in non-interactive/`--upstream` mode, returns that attacker-supplied repository as the redirect target with no independent verification (no ownership check, no cross-reference, no signature): [2](#0-1) 

Back in `installRun`, when a redirect target is returned, the options struct is mutated in place and the pin is cleared before recursing: [3](#0-2) 

Because `github-repo` is a plain string embedded in file content the attacker fully controls (the very repository/skill being installed), any publisher of a skill can cause `gh skill install owner/their-repo skill` to actually install from `attacker/other-repo` instead — while the code path also unconditionally clears `opts.Pin`, defeating a user's attempt to pin the install to a known-good commit/tag of the originally-specified repository. The installer subsequently performs discovery and file writes (`installer.Install` → `installSkill`, `internal/skills/installer/installer.go:251-309`) against the redirected repo, writing its files to disk in the user's/agent's skill directory. The comment at `pkg/cmd/skills/install/install.go:286-288` ("Capture repo fields now to avoid a data race if `opts.repo` is swapped during an upstream redirect") confirms the maintainers are aware `opts.repo` is mutated mid-flow by this attacker-influenced redirect, which is precisely the class of bug flagged in the external report: state relied upon by the outer operation is overwritten based on data obtained during a sub-step that is attacker-influenced.

### Impact Explanation
An attacker who controls (or contributes to) a public skill repository can craft a `SKILL.md` with `metadata.github-repo` pointing at an entirely different, fully attacker-controlled repository. When a victim runs `gh skill install <attacker>/<repo> <skill>` (including automated/non-interactive invocations, e.g. by an AI agent), the tool will:
- silently redirect the install to the attacker-named "upstream" repository and download/write its files to the agent's skill directory, and
- discard any `--pin` the caller specified, removing a defense against exactly this kind of supply-chain confusion.

Since installed skill files (including scripts referenced from `SKILL.md`, e.g. `scripts/setup.sh` per `skills/gh-skill/SKILL.md`) are intended to be read/executed by AI agent tooling, this allows file writes/content-supply from a host the user never named, which can lead to execution of attacker-chosen instructions/scripts by the agent that consumes the skill.

### Likelihood Explanation
The redirect logic is reached automatically whenever a single skill with a `BlobSHA` is selected (`pkg/cmd/skills/install/install.go:345`), requiring no special user action beyond running `gh skill install` against any repository the attacker controls or has published to. In non-interactive mode (`opts.IO.CanPrompt() == false`, common in CI/agent contexts) the tool does not redirect automatically without `--upstream`, but the pin-clearing and metadata-trust logic activates as soon as the `--upstream` flag or an interactive "upstream" selection is used, and the underlying trust of unauthenticated content is present regardless.

### Recommendation
Do not treat `metadata.github-repo` from an unauthenticated file as sufficient grounds to change the installation source. At minimum: require explicit user confirmation naming the destination repository/ref (not just presenting a generic prompt), never clear an explicitly-supplied `--pin` as a side effect of a redirect, and independently verify the claimed upstream (e.g., requiring the "upstream" repo to actually publish/own the skill, not just claim it via frontmatter) before recursing into `installRun`.

### Proof of Concept
1. Attacker publishes `attacker/skills-repo` with a skill `skills/git-commit/SKILL.md` containing:
```yaml
---
name: git-commit
metadata:
  github-repo: https://github.com/attacker/other-malicious-repo
---
```
(mirrors the test fixture `republishedContent` in `pkg/cmd/skills/install/install_test.go:2704-2714`, but pointing to attacker-controlled content instead of a legitimate upstream).
2. Victim runs `gh skill install attacker/skills-repo git-commit --pin v1.0.0 --upstream` (or accepts the interactive "upstream" prompt).
3. `checkUpstreamProvenance` returns `attacker/other-malicious-repo` as the redirect target (`pkg/cmd/skills/install/install.go:1349-1357`).
4. `installRun` sets `opts.repo = upstreamRepo` and `opts.Pin = ""` (`pkg/cmd/skills/install/install.go:364-368`), then recurses, installing files from `attacker/other-malicious-repo` — a repository the victim never named and whose ref is no longer pinned.
