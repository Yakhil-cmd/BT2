## Title
Cross-organization commit-status forgery via organization-scoped webhook secret selection mismatched against the repository actually written - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `webhook_secret` to validate the GitHub `X-Hub-Signature` against based on an attacker-controlled field taken directly from the (still-unverified) request body — `repository.owner.login`/`organization.login` — via `Shipit.github(organization: repository_owner)`. Once that per-organization secret validates the HMAC over the raw body, the event handlers act on a *different* field from the same body, `repository.full_name`, to decide which `Repository`/`Stack`/`Commit` records to mutate. In a multi-organization Shipit deployment, these two fields are never checked for consistency, breaking the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) 

`repository_owner` is read straight out of the JSON body, before any signature has been validated: [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` configuration (including its own `webhook_secret`) per organization key when Shipit is configured for multiple GitHub orgs: [3](#0-2) 

Once the HMAC is confirmed against *that* organization's secret, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that derive the actual repository to act on from a *different* payload field, `repository.full_name`, via `Handler#repository_name`/`Handler#stacks`: [4](#0-3) 

`StatusHandler` writes GitHub-supplied CI status fields (`state`, `description`, `target_url`, `context`) directly onto matching `Commit` records with no additional binding to `repository.owner.login`: [5](#0-4) 

Nothing in `verify_signature` or in `StatusHandler#process` (or `PushHandler`/`CheckSuiteHandler`) checks that `repository.owner.login`/`organization.login` (the value used to pick the HMAC secret) equals the owner encoded in `repository.full_name` (the value used to find the target `Stack`/`Commit`). An entity that legitimately controls (or knows) the `webhook_secret` for Organization B — e.g., because they administer Org B's GitHub App/webhook settings — can produce a validly-signed request whose `repository.full_name` names a repository belonging to unrelated Organization A that is also tracked by the same Shipit instance.

### Impact Explanation
The most direct exploitation path is CI-status forgery: `StatusHandler#process` builds a `Status` record from attacker-supplied `state`/`description`/`context`/`target_url` for any `Commit` matching `params.sha` in the datastore, regardless of which organization the commit belongs to, as long as *some* org's secret validated the envelope. In stacks that gate continuous delivery on `ci.require` statuses, an attacker who only controls Org B's webhook secret could inject a forged "success" status for a commit belonging to Org A's stack, enabling an unauthorized deploy of that commit through Shipit's own CI-gating logic — a deploy that would otherwise be blocked. This crosses the "unauthorized deploy" impact bar defined by the rules, and it is a genuine analog of the MUD `CoreSystem` issue: an access-control decision made against one identity (the org whose secret validated the signature) is silently reused to authorize a write against a different, unrelated resource (a commit/stack under a different org) named elsewhere in the same untrusted payload.

### Likelihood Explanation
Exploitation requires: (1) the Shipit instance configured for **more than one GitHub organization** (the multi-org schema documented in `config/secrets.development.example.yml`), and (2) the attacker controlling/knowing the `webhook_secret` for at least one of those configured organizations (e.g., as an admin of that org's GitHub App) while a *different* tracked organization/repository exists on the same instance. This is a real but non-default configuration (single-org deployments are unaffected, since there's only one secret to select), and the attacker must know a legitimate webhook secret for some org on the instance, not necessarily the target org. Given these preconditions, forging the request is trivial (compute the HMAC with the known secret over an arbitrary crafted body). I was not able to fully verify from static analysis alone whether any additional constraints (e.g., commit SHA collision requirements across repos, or GitHub API validation elsewhere) further narrow this in practice, since that depends on deployment-specific data (which commits/SHAs exist across which stacks) that isn't visible from the code alone.

### Recommendation
Bind the two fields together before dispatching to handlers: after determining `repository_owner` and successfully verifying the signature for that organization, re-derive the repository to act on and assert its owner matches `repository_owner` (or, more robustly, look up the `Repository`/`Stack` first and verify the signature using the webhook secret configured for *that specific repository's* owner, rejecting the request if `repository.full_name`'s owner and `repository.owner.login`/`organization.login` diverge).

### Proof of Concept
Given a Shipit instance configured with two organizations, `orgB` (attacker-controlled webhook secret) and `orgA` (victim, tracked stacks/commits):
1. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a real commit belonging to orgA's tracked stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, orgB_webhook_secret)>` using the secret they legitimately hold for `orgB`.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'orgB')`, which validates successfully against `orgB`'s secret.
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — a commit under `orgA`'s stack — and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled "success" status onto `orgA`'s commit, independent of `orgA`'s actual CI state, potentially unblocking an automated deploy gated on that status.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
