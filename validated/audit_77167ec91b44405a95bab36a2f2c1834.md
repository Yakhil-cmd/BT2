### Title
Unhandled exception in nested address-definition evaluation crashes full/light nodes and AA execution - (File: definition.js)

### Summary
`Definition.validateDefinition()` and `Definition.validateAuthentifiers()` both implement the `'address'` opcode (used when a spending condition references another on-chain address). When the referenced address has no confirmed definition yet, both functions fall back to looking for a definition supplied inline by one of the *current unit's* authors. If more than one author in the same unit matches the referenced address and definition hash, the code does not return a validation error — it throws a bare, unguarded `Error`, which is never caught by any surrounding `try/catch` because it executes inside an asynchronous DB-query callback.

### Finding Description
In `definition.js`, the `'address'` case inside `validateDefinition()`'s `evaluate()` looks for authors of the current unit that provide the missing definition of a referenced address: [1](#0-0) 
If `arrDefiningAuthors.length > 1`, the code executes `throw Error("more than 1 address definition")` instead of calling `cb(...)` with an error, unlike every other invalid-input branch in this function.

The identical unguarded pattern exists again in `validateAuthentifiers()`'s own `evaluate()` for the same `'address'` opcode: [2](#0-1) 

Both throws happen inside the `ifDefinitionNotFound` callback of `storage.readDefinitionByAddress`, which is invoked asynchronously from a DB query callback — i.e., far outside the stack frame of any `try/catch` in `validation.validate()`. `validation.js`'s only relevant `try/catch` wraps just the unit-hash calculation, not the deep definition-evaluation call graph: [3](#0-2) 

Because `validateAuthors`/`validateAuthentifiers` is invoked for every unit a node receives (broadcast units, AA triggers, and AA responses all funnel through `validation.validate`), and `network.js` installs a process-wide handler that deliberately turns any uncaught exception into a process crash "to avoid ending up in an inconsistent state": [4](#0-3) 
an uncaught `throw Error("more than 1 address definition")` triggered while validating an attacker-crafted unit will bring down the entire full/light node process, exactly like the Xen bug where a code path assumed a hardware precondition (`MISC_ENABLE` MSR always present) that a malicious/atypical guest could violate, causing a host crash with no error handling for the failure case.

### Impact Explanation
Any peer can construct and broadcast a single unit that:
- has two or more authors sharing the same `address` field, and
- both authors supply an inline `author.definition` that hashes to the same `definition_chash` referenced via an `['address', other_address]` clause somewhere reachable in an address definition or asset condition being evaluated for that unit (e.g. the unit's own definition, an asset's issue/transfer condition, or an AA's spending condition).

When any node (full node, hub, or light-vendor logic) validates this unit, it hits the unguarded `throw Error("more than 1 address definition")` deep inside an async callback, producing an uncaught exception that crashes the entire node process due to the `process.on('uncaughtException', …)` handler's explicit `throw err`. This is a remotely triggerable denial of service against every node that receives and validates the crafted unit, matching the "network unable to confirm new units" impact category, since all validating nodes can be repeatedly knocked offline by rebroadcasting the same or similarly crafted units.

### Likelihood Explanation
No special privilege is required — this is reachable from a single ordinary posted unit that any unprivileged wallet/unit poster can construct and broadcast; the definition-evaluation path (`'address'` opcode) is a standard oscript feature used for cosigning/nested addresses and is evaluated during normal `validation.validate()` processing of every unit. The only requirement is producing two authors with an identical address/definition pair in the same unit, which is a purely client-side construction step (no server or peer collusion needed).

### Recommendation
Replace both unguarded `throw Error("more than 1 address definition")` statements in `definition.js` (in `validateDefinition()`'s and `validateAuthentifiers()`'s `'address'` opcode handling) with a proper validation failure via the callback (`cb("more than 1 address definition")` / `cb2(false)`), consistent with how every other malformed-input case in these functions is handled, so that a malformed/duplicate-author unit is rejected as a normal `ifUnitError` instead of causing the whole node process to crash.

### Proof of Concept
1. Construct an address `other_address` whose definition is not yet confirmed on the DAG (so `storage.readDefinitionByAddress` returns `ifDefinitionNotFound`).
2. Craft a unit whose spending condition (or an asset's issue/transfer condition) contains `['address', other_address]`.
3. Add two authors to this same unit, both with `author.address === other_address`, each supplying the identical `author.definition` value that hashes (via `objectHash.getChash160`) to the `definition_chash` of `other_address`.
4. Broadcast the unit to the network via `network.js`'s joint-handling path, which calls `validation.validate()`.
5. During evaluation of the `'address'` opcode, `arrDefiningAuthors.length` will be `2`, causing the unguarded `throw Error("more than 1 address definition")` inside the async `ifDefinitionNotFound` callback, which is uncaught and crashes the validating node process via the `process.on('uncaughtException')` handler in `network.js`.
