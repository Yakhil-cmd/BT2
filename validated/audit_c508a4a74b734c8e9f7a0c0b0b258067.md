### Title
Cross-organization team membership forgery via `MembershipHandler` breaks the organization-signature-to-team binding, enabling escalation into `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an incoming webhook based on the organization named in the payload (`repository.owner.login` or `organization.login`), but `MembershipHandler#find_or_create_team!` mutates a `Team` record keyed only by the numeric `params.team.id` (GitHub's global team id), without re-checking that this team actually belongs to the organization that was cryptographically verified for the request. On a multi-organization Shipit deployment (the documented "Using Multiple Github Applications" setup), an actor who legitimately controls one configured organization's GitHub App/webhook secret can forge a `membership` webhook that authenticates as their own org but grants arbitrary GitHub logins membership in a `Team` record belonging to a different, privileged organization — directly satisfying `User#authorized?`'s `Shipit.github_teams` check.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

It uses `Shipit.github(organization: repository_owner)` to pick the correct per-organization `webhook_secret` and HMAC-validate the raw body. This binds "the request is authenticated **as organization X**" to whichever value the payload happens to put in `repository.owner.login`/`organization.login`.

For the `membership` event, `MembershipHandler` reuses `params.organization.login` — a field entirely inside the HMAC-signed body, so it is internally consistent with the org that signed the request — but the record it mutates is looked up by a **different, unrelated key**: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` only assigns `team.organization = params.organization.login` inside the creation block, which ActiveRecord skips entirely when a `Team` with that `github_id` already exists. Since `github_id` is a GitHub-wide, attacker-suppliable integer (not scoped to, or cross-checked against, the organization that authenticated the request), an already-existing `Team` belonging to organization A can be looked up and have members added to it by a webhook that only ever proved it was signed by organization B's secret.

This breaks the intended binding:
`organization authenticated by verify_signature == organization owning the Team record mutated by MembershipHandler`

which is exactly the class of "authenticate one field, act on a different, unchecked field" bug described in the report (there: `unlockPeriod`'s `_SCALER` divisor applied to the wrong term; here: `organization.login` verified but `team.id` used as the unchecked join key that crosses the organization boundary).

`Shipit.github_teams` authorization is downstream of this exact `Team` record: [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who is a legitimate, low-privilege administrator of one GitHub organization configured in a multi-org Shipit instance (a documented, supported configuration) can send a forged `membership` webhook, correctly signed with their own org's `webhook_secret`, that:
- sets `team.id` = the GitHub team id of a privileged team already tracked by Shipit (e.g., one listed in `Shipit.github_teams`) belonging to a *different* organization,
- sets `member.login` = their own (or any) GitHub username,
- sets `action` = `added`.

`MembershipHandler` finds the existing privileged `Team` by `github_id` and calls `team.add_member(member)`, granting that GitHub login membership in the privileged team without ever being a real member on GitHub. Since `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, this grants full access to the Shipit application under that identity — an escalation into `Shipit.github_teams` authorization, one of the explicitly qualifying High-severity impacts.

### Likelihood Explanation
This requires:
1. A multi-organization Shipit deployment (documented feature), and
2. The attacker legitimately controlling one configured org's own GitHub App/webhook secret (not a stolen credential — it's their own tenant), and
3. Knowledge of the target `Team`'s GitHub `github_id` (a small integer, discoverable via GitHub's team API for public orgs/teams, or leaked in other webhook/API payloads referencing teams, e.g. `requested_teams` on pull requests).

Given multi-tenant Shipit installs are an explicitly documented use case, and team ids are not treated as secrets by GitHub, this is a realistic, low-cost attack for anyone with any one org's App credentials in a shared instance.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found (not just newly created) `Team#organization` matches `params.organization.login` before adding/removing members, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "Team #{team.github_id} organization mismatch" unless team.organization == params.organization.login
  team
end
```
More generally, `verify_signature` should re-validate that every organization-scoped identifier used later in a handler (team ids, repository full names, etc.) is consistent with the organization that was cryptographically authenticated for that specific request, rather than trusting unrelated attacker-controlled fields deeper in the payload.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (attacker is admin, controls its `webhook_secret`) and `victim-org` (has team `Victim/admins` with GitHub team id `9999`, listed in `Shipit.github_teams`).
2. Attacker crafts:
```json
{
  "action": "added",
  "team": { "id": 9999, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/9999" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-handle" }
}
```
3. Attacker computes `X-Hub-Signature` with `attacker-org`'s real `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature validates successfully.
5. `MembershipHandler` finds the existing `Team` with `github_id: 9999` (== `Victim/admins`) and calls `team.add_member(User.find_or_create_by_login!("attacker-handle"))`.
6. `attacker-handle` now passes `User#authorized?` via membership in `Victim/admins`, gaining full access to the Shipit instance. [6](#0-5) [7](#0-6)

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
