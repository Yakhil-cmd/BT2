### Title
Accrual-time `i128` overflow permanently freezes an oversized market - (File: common/src/rates/simulate.rs)

### Summary
An unprivileged user can create a sufficiently large supplied/borrowed book, after which ordinary interest growth makes `scaled_position * index` unrepresentable in `i128`. Every subsequent market mutation accrues before acting, so repayment, withdrawal, liquidation, bad-debt cleanup, recapitalization, and index updates all revert.

### Finding Description
`accrue_step` first converts total scaled debt and supply back to RAY-denominated value via `scaled_to_original`, then calculates utilization and interest. [1](#0-0)  `scaled_to_original` is implemented as `scaled.mul(env, index)`, which returns `MathOverflow` when the resulting value does not fit `i128`. [2](#0-1)  It also multiplies debt shares by both the old and newly grown borrow indexes inside `calculate_supplier_rewards`. [3](#0-2) 

The borrow-index ceiling does not prevent this condition. `update_borrow_index` multiplies first and clamps only the resulting index to `MAX_BORROW_INDEX_RAY`. [4](#0-3)  A 1-billion-token, 18-decimal market creates approximately `1e36` scaled shares; once the borrow index exceeds roughly `170 * RAY`, the debt value exceeds `i128::MAX` even though the index remains far below the `1e36` index ceiling. [5](#0-4) 

`interest::global_sync` runs inside `synced_market`, which is the common loader used by repayment, withdrawal, and other market mutations. [6](#0-5)  The public pool `update_indexes` path independently runs the same accrual loop. [7](#0-6)  Consequently, once the value ceiling is crossed, the panic happens before any code can burn debt, burn supply, socialize debt, or change the rate model.

### Impact Explanation
This permanently freezes all funds associated with the affected `(hub_id, asset)` market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, `clean_bad_debt` cannot socialize the position, and `recapitalize` cannot restore operation because each path must first accrue interest. The project’s own regression test demonstrates `MathOverflow` from `update_indexes` and then identical failures for withdrawal and repayment. [8](#0-7) 

### Likelihood Explanation
A single funded user can create the state using only public controller operations:

1. `supply(caller, account_id, spoke_id, [(HubAssetKey{hub_id, large_asset}, principal)])`
2. `supply(caller, account_id, spoke_id, [(HubAssetKey{hub_id, collateral_asset}, collateral)])`
3. `borrow(caller, account_id, spoke_id, [(HubAssetKey{hub_id, large_asset}, debt)])`
4. Later call `update_indexes(caller, [HubAssetKey{hub_id, large_asset}])`, or simply allow the next user operation to perform accrual.

The regression test uses `principal = 1_000_000_000 * 10^18`, debt equal to 98% of principal, and collateral denominated in a second market. [9](#0-8)  The amount is below the protocol’s maximum admitted token-domain cap of about 170.14 billion whole tokens, so the state is arithmetically admissible when governance-configured caps permit it. [10](#0-9) 

### Recommendation
Do not require the full unscaled market debt or supply value to fit `i128` during accrual. At minimum:

- Perform utilization and interest calculations on bounded ratios or widened `I256` values rather than requiring `scaled * index` to fit `i128`.
- Cap the stored debt/supply value or reject new exposure using a shared invariant stricter than the raw token-to-RAY cap, such that every later `scaled * MAX_INDEX / RAY` remains representable.
- Add an explicit pre-accrual circuit breaker that allows repay, withdrawal, liquidation, and bad-debt settlement to proceed using the last committed indexes when projected values become unrepresentable.
- Treat the condition as a market-level safety bound and enforce it at supply/borrow admission rather than documenting it as an eventual fatal arithmetic limit.

### Proof of Concept
The repository already contains a deterministic proof in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
```

The test then advances the ledger and calls `try_update_indexes_for(&["BIG18"])` until accrual returns `MATH_OVERFLOW`. After the first failure, both `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` fail with the same error because they attempt accrual before mutating the position. [11](#0-10)

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
