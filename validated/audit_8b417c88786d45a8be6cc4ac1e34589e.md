### Title
AA bounce mechanism can permanently trap all returned assets in a single failed atomic unit - (File: aa_composer.js)

### Summary
When an AA trigger fails and must be bounced, `bounce()` builds one single unit that attempts to return *every* asset present in `trigger.outputs` (minus configured `bounce_fees`) in one atomic call to `sendUnit`. If composing the payment for any one of these assets fails (for example due to that asset's spending conditions, such as `issued_by_definer_only`/`spender_attested` restrictions, or an inability to cover the output size/fee), the whole bounce is abandoned rather than salvaging the assets that could have been safely returned.

### Finding Description
`bounce(error)` iterates over all assets in `trigger.outputs`, builds one payment message per asset into a single `messages` array, and calls `sendUnit(messages)` once for the combined set: [1](#0-0) 
`sendUnit` composes a single unit containing all of these payment messages together, and if any part of that composition fails (e.g. `completePaymentPayload` cannot find sufficient inputs/covers fees for one particular asset, or validation of the unit fails for one payload), the whole unit construction is aborted and `bounce(err)` is invoked again: [2](#0-1) 
Because `bounce()` guards against re-entry with the `bBouncing` flag, a second invocation of `bounce()` from within the failed `sendUnit` call short-circuits to `finish(null)`: [3](#0-2) 
This means that if any single asset in the trigger's outputs (say, an asset that requires attestor cosigning or definer-only issuance, and that condition can no longer be satisfied) prevents the combined bounce unit from being built, then *none* of the assets — not even plain bytes (`base`), which had no such restriction and could have been trivially returned — get sent back at all. The whole atomic "return everything" strategy has the same root-cause shape as the reported issue: bundling an unrelated, potentially-blocked operation together with a recoverable one causes the entire recovery path to revert, permanently losing funds that could have been recovered independently.

### Impact Explanation
Any base-currency bytes or other well-behaved assets sent to an AA together with a problematic asset (one whose current definition/attestation state makes it unspendable by that AA) become permanently stuck in the AA, because the bounce mechanism never separates "returnable" from "non-returnable" assets — it either sends everything back in one shot or sends nothing. This is a fund-freezing bug from the sender's perspective, consistent with the accepted "AA fund loss or freezing" impact class.

### Likelihood Explanation
This can be triggered whenever a trigger unit sends the AA more than one asset and at least one of those assets is subject to a spending condition the AA cannot currently satisfy (definer-only issuance, attestor-gated spending, or any other transient inability to source inputs for a particular asset in the required unit). This is a realistic scenario for AAs that accept multiple assets and rely on generic bounce-back behavior, and does not require any malicious actor — a legitimate but ill-fated combination of asset conditions and trigger error is sufficient.

### Recommendation
Have `bounce()` attempt to return each asset independently (e.g., by allowing partial bounce units per asset, or by falling back to a reduced set of messages that excludes assets whose payment cannot currently be composed) rather than aborting the entire bounce when any single asset fails, so that at least the base currency and any unaffected assets can still be returned to the trigger address.

### Proof of Concept
1. Deploy an AA with default bounce behavior (no custom `messages` override needed — rely on protocol-level bounce, or include multiple assets in a triggering unit that intentionally causes the AA logic to `bounce(...)`).
2. Send a trigger unit to the AA containing two outputs: (a) `base` bytes above the bounce-fee threshold, and (b) an amount of an asset `X` defined with `issued_by_definer_only: true` where the AA is not the definer (so the AA cannot legitimately re-issue/spend that asset back if its only source is the trigger's own transferred amount and it lacks a compliant input, or where `spender_attested` requires an attestation the sender can no longer satisfy).
3. Trigger a bounce condition (e.g., invalid trigger data) so `bounce()` is invoked.
4. Observe that `sendUnit` fails to compose the combined multi-asset unit due to asset `X`'s constraints, `bounce(err)` re-enters, `bBouncing` is already `true`, and `finish(null)` is called — no unit is sent, and the `base` bytes that could have been safely bounced are instead retained/lost from the sender's perspective.
