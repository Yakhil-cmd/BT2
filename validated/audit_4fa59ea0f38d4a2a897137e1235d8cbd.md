### Title
ReDoS in hookify's `_regex_match` allows catastrophic-backtracking regex rules to bypass PreToolUse `action: block` decisions - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._regex_match` compiles attacker-supplied regex patterns from `.claude/hookify.*.local.md` rule files and calls `regex.search(text)` with no execution-time bound. A catastrophically backtracking pattern (e.g. `(a+)+$`) matched against an attacker-influenced Bash command string can run far beyond the 10-second `PreToolUse` hook timeout configured in `hooks/hooks.json`, and Claude Code's documented hook timeout semantics treat this as a non-blocking (fail-open) outcome, so a rule with `action: block` never returns its deny decision and the dangerous command executes.

### Finding Description
The `PreToolUse` call sequence is `pretooluse.py:main()` → `load_rules()` → `RuleEngine.evaluate_rules()` → `_rule_matches()` → `_check_condition()` → `_regex_match()` → `compile_regex()` → `re.Pattern.search()`. [1](#0-0) 

`compile_regex` only caches compiled patterns; it applies no complexity vetting, and `_regex_match` performs a bare `regex.search(text)` with no per-call timeout or interruption mechanism. [2](#0-1) 

Rule patterns for `bash` events are matched against the field `command`, i.e. the literal Bash tool-input command string that is about to run. [3](#0-2) 

The `hooks/hooks.json` manifest configures a 10-second timeout for the `PreToolUse` command hook that runs `pretooluse.py`. [4](#0-3) 

`pretooluse.py`'s only exception handling is a generic `try/except Exception`, which does not — and cannot — catch a hang inside `re.search` caused by catastrophic backtracking (this is CPU-bound looping, not a raised exception), and the `finally: sys.exit(0)` never executes if the external timeout mechanism kills the process first. [5](#0-4) 

Separately, the plugin-dev hook documentation (shared exit-code contract used across this codebase's hook infrastructure) states that only exit code `0` is success and `2` is a blocking error; any "other" exit code — which is exactly what a killed/timed-out process produces (confirmed as exit code `124` for `timeout`-induced kills in the test harness) — is explicitly documented as a "non-blocking error." [6](#0-5) [7](#0-6) 

So the intended "deny means deny" behavior of `action: block` rules (which normally produce `hookSpecificOutput.permissionDecision: "deny"` from `evaluate_rules`) is defeated: if `_regex_match` never returns because of a ReDoS pattern, the hook process is killed on timeout, produces no JSON decision, and per the documented "other exit code = non-blocking" contract the tool call is allowed to proceed.

### Impact Explanation
This is a deny-bypass / permission-check-bypass: a Bash command that a checked-in `hookify.*.local.md` rule was explicitly configured to `block` (e.g. a rule intended to stop `rm -rf`, `sudo`, or exfiltration commands) executes anyway because the hook enforcing the block hangs past its timeout and is killed, which this codebase's own hook-execution contract treats as non-blocking/allow. This matches a security-control-bypass impact: an unprivileged attacker who can get a crafted rule file and a crafted command into the flow can make an intended security gate silently fail open.

### Likelihood Explanation
Preconditions: (1) a hookify rule file with a catastrophically backtracking pattern (`(a+)+$`, `(x+x+)+y`, etc.) targeting the `command` field of a `bash` event with `action: block` must exist under `.claude/hookify.*.local.md`, and (2) the Bash tool must be invoked with a command string that triggers exponential backtracking against that pattern (e.g. a long run of `a` characters with no trailing terminator). Rule files are intended to be user-authored/git-ignored per the plugin README, but nothing in `config_loader.py` or `rule_engine.py` enforces this, validates pattern complexity, or bounds match time, so any rule file that lands in `.claude/` (via a merged PR, a copied template, or an unreviewed local config) is sufficient. This is deterministic and repeatable: the same pattern/input pair reliably reproduces multi-second-to-unbounded regex execution time regardless of the `lru_cache` on `compile_regex`, since caching the compiled pattern does not bound `search()` time on new attacker-supplied text.

### Recommendation
- Enforce a hard wall-clock/CPU bound on `_regex_match`'s `regex.search()` call (e.g. run in a worker process/thread with `signal.alarm`, `multiprocessing` + timeout, or use a regex engine with linear-time guarantees such as Google's `re2`), and treat a timeout as a rule-evaluation failure that still returns a safe decision rather than silently allowing the tool call.
- Validate/lint regex patterns at rule-load time (`config_loader.py`) to reject or warn on constructs known to cause catastrophic backtracking (nested quantifiers over overlapping character classes).
- For `action: block` rules specifically, make the PreToolUse hook's failure mode explicit and fail closed (return `permissionDecision: "ask"` or `"deny"`) when rule evaluation cannot complete within an internal budget well under the 10s `hooks.json` timeout, so exceeding that internal budget is treated as an error condition rather than being interpreted as "no match."

### Proof of Concept
Unit/fuzz test in `plugins/hookify/core/rule_engine.py` test suite:
```python
import time
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

def test_regex_match_bounded_time():
    engine = RuleEngine()
    rule = Rule(
        name="block-evil",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+$")],
    )
    payload = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "a" * 40 + "!"},  # triggers catastrophic backtracking, never matches
    }
    start = time.monotonic()
    result = engine.evaluate_rules([rule], payload)
    elapsed = time.monotonic() - start
    # Safe bound well under the 10s hooks.json PreToolUse timeout
    assert elapsed < 2.0, f"_regex_match took {elapsed}s, exceeds safe bound"
    # If it were allowed to hang past 10s and get killed, no decision would
    # ever be returned, and the "deny" would never fire — assert it fires
    # promptly instead:
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") in ("deny",)
```
This test should be run with a range of adversarial patterns (`(a+)+$`, `(a|aa)+$`, `(.*)*=`) and payload lengths (e.g. 20–60 repeated characters) to confirm `_regex_match`/`re.search` wall-clock time grows exponentially and exceeds the 10-second `hooks.json` timeout, at which point the hook process is killed and, per this repo's documented "other exit code = non-blocking" hook contract, the `block` decision is lost and the underlying Bash command runs unblocked.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
