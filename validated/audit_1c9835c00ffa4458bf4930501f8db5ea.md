### Title
Bad-debt supply-index floor clamp leaves wiped suppliers with a live claim that drains fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
The kernel bug class is "a companion field is cleared while its paired field stays valid": `cached_table` was nulled but `table_sz` remained nonzero, so a later `memcpy` consumed the stale size. In XOXNO Lending the same shape appears in bad-debt socialization: `apply_bad_debt_to_supply_index` conceptually wipes supplier value (index reduction factor `0`) but instead of zeroing the paired `supplied` scaled-share total it clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW`. The stale scaled shares therefore retain a positive unscaled claim (`scaled × RAY/1000`) even though their backing value was fully written down. Once a fresh deposit credits cash to the market, the wiped position's `resolve_withdrawal` + `require_reserves` path succeeds and pays real tokens, draining the new supplier's principal.

### Finding Description
`apply_bad_debt_to_supply_index` (contracts/pool/src/interest.rs:73-89) computes `remaining = total_supplied_value − min(bad_debt, total_supplied_value)` and multiplies the old index by `remaining / total_supplied_value`. When `bad_debt ≥ total_supplied_value`, `remaining = 0`, so `new_supply_index = 0`, and it is clamped to `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000). The `supplied` scaled-share total is never burned or reset, so every existing supplier's `scaled_amount` still unscale to `scaled × RAY/1000 > 0` via `unscale_supply_floor`. This seize path is reached from the controller's unprivileged `liquidate`/`clean_bad_debt` flows through `ops::seize::apply` (`AccountPositionType::Borrow` branch, contracts/pool/src/ops/seize.rs:24-28).

### Impact Explanation
Theft of user funds / protocol insolvency in the specific market. A wiped supplier (any holder of shares in a fully written-down market, e.g. the attacker self-liquidating dust collateral to create bad debt, or simply an existing supplier) can call `controller.withdraw` with `i128::MAX`/0, which resolves via `cache.resolve_withdrawal` → `unscale_supply_floor`, and `require_reserves` passes once any fresh supplier has deposited cash into the same hub-asset market. The pool pays out real tokens to a position whose backing was fully socialized away, leaving the honest fresh depositor's claim uncovered — exactly what `contracts/pool/tests/interest.rs:372-427` demonstrates: `gross == fresh_cash` and `cache.cash() < fresh_claim`.

### Likelihood Explanation
Requires a market whose bad debt equals or exceeds total supplied value, which occurs whenever a fully wiped borrow position is seized while the market is thin (common for dust-threshold `clean_bad_debt` on small markets, or a collapsed collateral). The attacker can position as both the wiped supplier and the withdrawer; the victim is any subsequent depositor. The only missing verified detail is whether controller-level bad-debt cleanup zeroes the supply position books elsewhere; the pool-level test indicates it does not, but I could not fully trace the controller's account-book update for seized supply shares.

### Recommendation
When the reduction factor reaches zero (full write-down), burn or zero the `supplied` scaled total alongside the index clamp — i.e., clear the "size" companion, not just the value — or mark the market defunct so `resolve_withdrawal` returns zero. At minimum, gate withdrawals on `supply_index > SUPPLY_INDEX_FLOOR_RAW` for positions created before the write-down.

### Proof of Concept
The existing test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (contracts/pool/tests/interest.rs:372-427) is a direct PoC:
1. Market with `supplied = 1000 RAY` scaled, `supply_index = RAY`, `cash = 0`.
2. `apply_bad_debt_to_supply_index(cache, 5000 RAY)` → index clamps to `SUPPLY_INDEX_FLOOR_RAW`, `supplied` unchanged.
3. Fresh supplier deposits `fresh_cash = unscale_supply_floor(old_scaled)`; pool mints shares and credits cash.
4. Old (wiped) position calls `resolve_withdrawal(i128::MAX, old_scaled)` → `require_reserves(gross)` passes → `gross == fresh_cash` paid out; `cash < fresh_claim`, so the fresh depositor's funds are lost.
