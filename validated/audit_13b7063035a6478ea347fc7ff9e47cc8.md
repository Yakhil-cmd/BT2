### Title
Webhook signature verification bound to a different organization than the repository the payload acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / HMAC secret to check against based on `repository.owner.login` (falling back to `organization.login`), but the actual entity operated on by every webhook handler is `repository.full_name` — a separate, attacker-controlled JSON field in the same unsigned-until-verified request body. In multi-organization deployments (a first-class, documented Shipit feature), if any configured organization has no `webhook_secret` set (documented as *optional*), signature verification is unconditionally bypassed for payloads whose `repository.owner.login`/`organization.login` names that org, while the handlers still act on whatever repository `full_name` is present in the body — which can belong to a different, fully-secured organization.

### Finding Description
The controller verifies signatures like this: [1](#0-0) 

`repository_owner` is taken straight from the JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up the corresponding app config (in multi-org mode) and instantiates a `GitHubApp` scoped to that organization's `webhook_secret`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats an absent secret as automatic success: [4](#0-3) 

Multi-organization configuration is a documented feature where `webhook_secret` is set per organization and is optional: [5](#0-4) 

Crucially, once the request passes `verify_signature`, `create` dispatches the *entire* raw payload to handlers unchanged: [6](#0-5) 

But every handler resolves the target repository from a **different** JSON field, `repository.full_name`, not `repository.owner.login`: [7](#0-6) 

For example `PushHandler` uses that repository's stacks and directly triggers a GitHub sync using an attacker-supplied `after` SHA: [8](#0-7) 

`StatusHandler` similarly writes commit statuses purely based on `params.sha`, with no organization/repo cross-check at all: [9](#0-8) 

**The broken binding (equality that should hold but doesn't):**
`organization_used_for_signature_verification (repository.owner.login / organization.login)` **==** `organization_that_owns_the_repository_the_handler_writes_to (repository.full_name)`

Nothing in `WebhooksController` or `Handler` enforces this equality. An attacker who sends a raw POST to `/webhooks` fully controls both fields independently. If the org named by `repository.owner.login` happens to have no `webhook_secret` configured (an explicitly optional and documented setting), `verify_webhook_signature` returns `true` unconditionally — regardless of the value of `X-Hub-Signature` — and the payload is then processed against whatever `repository.full_name` the attacker chose, which can be a stack belonging to a fully-secured sibling organization in the same Shipit installation.

### Impact Explanation
This lets an unauthenticated, unprivileged network attacker (no session, no `ApiClient` token, no `webhook_secret`, no GitHub credentials) forge GitHub webhook events for repositories/stacks that belong to an organization other than the one whose (missing) secret was used to pass verification. Concretely:
- `push` events can force `GithubSyncJob` to run against a target stack with an attacker-chosen `expected_head_sha`, which drives commit ingestion and (if `continuous_deployment` is enabled on that stack) can trigger an **unauthorized deploy** as soon as the referenced SHA is reachable on GitHub.
- `status` events can inject fabricated CI status records for arbitrary commits, corrupting the signals that gate merges/deploys.
- `membership`/`check_suite`/other handlers can similarly be invoked against arbitrary stacks/teams without ever presenting a valid signature for the organization actually being modified.

This matches the "unauthorized deploy" / cross-repository-write class of High/Critical impact called out in the rules, achieved purely by exploiting the mismatch between the field used for authentication (`repository.owner.login`) and the field used for the actual write (`repository.full_name`), with no need to possess any secret at all when at least one configured organization omits `webhook_secret`.

### Likelihood Explanation
Likelihood depends on deployment configuration: the flaw is only reachable in multi-organization Shipit setups where at least one configured GitHub organization has not set a `webhook_secret` — which the official setup docs explicitly present as optional and even ship example configs with `webhook_secret: # nil`. Given that Shipit installations commonly onboard organizations incrementally (and webhook secrets are easy to forget since they are optional), this is a realistic misconfiguration rather than a theoretical one, and the exploit itself requires nothing beyond an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body — no credentials, tokens, or GitHub access of any kind.

### Recommendation
- Require `webhook_secret` to be present for every configured organization in multi-org mode; refuse to boot (or refuse all webhooks for that org) rather than silently trusting unsigned payloads (`return true unless webhook_secret` in `GitHubApp#verify_webhook_signature` should not exist for production/multi-org configurations).
- Enforce that the organization used to select/verify the signature is the same organization that owns the repository being acted upon: derive the org strictly from `repository.full_name`'s owner (or cross-check it against `repository_owner`) before any handler runs, rejecting mismatches with 422.
- Consider requiring a global cross-check inside `Handler` (or the controller) that the verified `repository_owner` equals `payload.dig('repository', 'owner', 'login')` used to resolve `Repository.from_github_repo_name`.

### Proof of Concept
Preconditions: Shipit configured with multi-org `github:` config where org `OrgB` has `webhook_secret` unset/blank, and org `OrgA` (target) has commits/CI configured normally with `continuous_deployment: true` on some stack.

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/garbage)
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<real-existing-sha-on-OrgA/target-repo>",
  "repository": {
    "owner": {"login": "OrgB"},
    "full_name": "OrgA/target-repo"
  }
}
```

1. `repository_owner` resolves to `"OrgB"`.
2. `Shipit.github(organization: "OrgB")` returns a `GitHubApp` whose `webhook_secret` is blank.
3. `verify_webhook_signature` returns `true` immediately (`return true unless webhook_secret`), regardless of the bogus `X-Hub-Signature`.
4. `create` dispatches the parsed JSON to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("OrgA/target-repo")` and calls `stack.sync_github(expected_head_sha: "<real-existing-sha-on-OrgA/target-repo>")`, forcing a sync/deploy trigger on `OrgA`'s stack — despite the attacker never possessing `OrgA`'s (or any) webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
