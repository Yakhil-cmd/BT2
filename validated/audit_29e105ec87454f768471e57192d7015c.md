### Title
Session Fixation on GitHub OAuth Callback Lets an Attacker Hijack an Authenticated Victim Session - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` binds a freshly-authenticated GitHub identity to the *existing* session by writing `session[:user_id]` / `session[:authenticated]` without first calling `reset_session`. `#logout` explicitly calls `reset_session`, showing the omission on the login path is not intentional. This breaks the binding "GitHub identity authenticated == `User` bound to the session" because the session identifier that existed *before* authentication is the same one that is privileged *after* authentication.

### Finding Description [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

Compare with `#logout`, which does rotate the session: [2](#0-1) 

The engine-wide `current_user` lookup trusts whatever `session[:user_id]` is bound to the request's session: [3](#0-2) 

Because `callback` never invalidates the pre-authentication session and issues a new session identifier, any session that existed prior to the OAuth round trip continues to be valid and becomes privileged once `session[:user_id]` is set. If an attacker can get a victim's browser to carry an attacker-known/attacker-chosen session (a "fixated" session — e.g., by placing a cookie for the Shipit host from a sibling page/subdomain the attacker controls, or by capturing a session cookie issued to the victim by the attacker's own request to the site before the victim logs in), the attacker's session becomes bound to the victim's `User` record the moment the victim completes GitHub OAuth. From that point, requests replayed by the attacker using the same session cookie are treated by `Shipit::Authentication#force_github_authentication` as the victim.

This is exactly the deployment-trust binding the report's bug class generalizes to: in the report, an amount computed from `spendLockedAmount` is applied inconsistently depending on *order of operations*, letting the attacker exploit a mismatch between two views of the same state (allocation vs. spent amount) that should have been kept in lockstep. Here, the mismatch is between the session identifier issued before authentication and the identity that becomes authorized to it after authentication — the `User` binding is updated in place on the pre-existing session object instead of being tied to a freshly minted one.

### Impact Explanation
This maps to the explicitly allowed High-impact category "session fixation / forced OAuth completion." If exploited, an attacker gains a session bound to the victim's `Shipit::User`, inheriting whatever `Shipit.github_teams` authorization and stack access the victim has — including the ability to trigger deploys/rollbacks (`Shipit::Deploy`, `Shipit::Rollback`) and read stack/task output as that user, without ever needing the victim's GitHub credentials.

### Likelihood Explanation
Exploitation requires the attacker to fixate a session cookie in the victim's browser prior to the victim completing GitHub login (e.g., by getting a cookie set from a co-hosted/sibling context or by tricking the victim into using an attacker-supplied session), and the victim to actually go on to log in without an intervening reset. This is a known, practical class of web attack, but it depends on the deployment's cookie scoping (`domain`/`path`) and the app not otherwise rotating the session; the code as written provides no server-side mitigation, so the residual risk rests entirely on external factors (cookie scope) rather than on any additional application-level protection.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` immediately before writing `session[:user_id]` / `session[:authenticated]`, mirroring the behavior already present in `#logout`. Re-derive `return_url` (`omniauth.origin`) before resetting the session if the origin value needs to survive the reset, since `reset_session` clears all session data.

### Proof of Concept
1. Attacker obtains any session for `shipit-engine.myshopify.io` (e.g., by visiting the site unauthenticated, or by forcing a known cookie via a shared-domain mechanism) and notes the session cookie value `S`.
2. Attacker delivers cookie `S` to the victim's browser (fixation) and lures the victim to the Shipit login flow.
3. Victim completes GitHub OAuth; `GithubAuthenticationController#callback` writes `session[:user_id] = victim.id` into the *same* session identified by `S` because `reset_session` is never called. [4](#0-3) 
4. Attacker replays cookie `S` and is now recognized as the victim by `Shipit::Authentication#current_user` / `#force_github_authentication`, gaining full access to stacks, deploys, and tasks the victim is authorized for. [5](#0-4)

      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
