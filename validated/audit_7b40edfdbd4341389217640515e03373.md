The bug-class match (synchronous remote-resource access without any timeout, causing a single serialized handler to hang indefinitely) exists in the Obyte arbiter/arbstore integration, and it is reachable through a global, serializing mutex that blocks all further hub-message processing.

### Title
Unbounded HTTP Request to Attacker-Controlled ArbStore URL Freezes Global `from_hub` Mutex - ([File: arbiters.js], [File: wallet.js])

### Summary
`arbiters.js`'s `requestInfoFromArbStore()` issues an `https.get()` request with no socket/response timeout. It is invoked by `getArbstoreInfo()`, which is called synchronously (via `await`) from the `arbiter_dispute_request` handler inside `wallet.js`'s `handleMessageFromHub()`. That handler executes under a single, globally-keyed mutex (`"from_hub"`) that serializes processing of *all* incoming device/hub messages. If the fetched ArbStore URL belongs to an unresponsive or malicious host, the pending HTTP request never resolves and never times out, so the mutex is never released — freezing processing of every subsequent message from the hub (chat, signing requests, private-payment forwarding, contract updates) indefinitely.

### Finding Description
`requestInfoFromArbStore()` performs a plain `http.get(url, ...)` with only an `"error"` handler and no `setTimeout`/`req.setTimeout` call, so a connection that is accepted but never responds (or never completes) will hang forever: [1](#0-0) 

`getArbstoreInfo()` calls `device.requestFromHub("hub/get_arbstore_url", arbiter_address, …)` to resolve the URL, then calls the unbounded `requestInfoFromArbStore` on it: [2](#0-1) 

This function is awaited synchronously inside the `arbiter_dispute_request` case of `handleMessageFromHub`: [3](#0-2) 

That whole `doHandle()` function — including this `await`-blocked call — executes only after acquiring a **global** mutex key `"from_hub"`, and `unlock()` is only invoked from the `ifOk`/`ifError` callback wrappers, which never fire while the HTTP request is stuck: [4](#0-3) 

The `arbiter_address` supplied in `arbiter_dispute_request` only has to correspond to one of the victim's own addresses (`my_addresses`); reaching the arbstore lookup does not require the resolved URL itself to be trustworthy — an attacker who controls (or has compromised/DNS-hijacked) the arbstore endpoint registered for that arbiter address can make the endpoint accept-and-hold the TCP connection without ever completing the HTTP response.

The same missing-timeout pattern also exists in `arbiter_contract.js`'s `httpRequest()` (used by `appeal()`/`getAppealFee()`), reinforcing that no part of this arbiter/arbstore HTTP client code enforces timeouts: [5](#0-4) 

### Impact Explanation
Because the mutex key is the literal string `"from_hub"` (not scoped per-peer or per-message), a single stuck request permanently starves the mutex queue for the entire device/wallet process. All further hub-delivered messages — signing offers/responses needed to complete pending payment units, private-payment chain forwarding, other arbiter-contract lifecycle updates, and pairing/chat — stop being processed. For an arbiter wallet actively co-signing shared/multisig addresses (e.g., arbiter contracts holding funds in `wallet_arbiter_contracts` shared addresses), this can indefinitely freeze the completion of pending signed transactions that depend on further device-message round trips, effectively freezing funds tied up in those flows until the process is manually restarted.

### Likelihood Explanation
Reaching this requires: (1) the attacker to be an already-paired correspondent of the victim (not a bar for anyone who has interacted with the victim, e.g. as a contract counterparty or disputant), and (2) the target address to be genuinely used by the victim as an arbiter (`my_addresses` check). Arbiter wallets are a designed, expected role in the Obyte arbiter/arbstore ecosystem, and the arbstore URL registration for an arbiter is not otherwise validated for liveness/timeout behavior by this client code, so an attacker who runs or hijacks an ArbStore-compatible endpoint can reliably trigger the hang.

### Recommendation
Add explicit timeouts to all outbound HTTP(S) requests in `arbiters.js` (`requestInfoFromArbStore`) and `arbiter_contract.js` (`httpRequest`), e.g. via `req.setTimeout(ms, () => req.destroy())` or an AbortController, and treat a timeout as an error path so pending callbacks (and therefore the `"from_hub"` mutex) are always released. Additionally, avoid holding a global serializing mutex across network calls to remote, non-trusted parties; scope such locks per-device/per-request or move the network fetch outside the critical section.

### Proof of Concept
1. Attacker pairs with the victim's device (or is already a correspondent) and knows/controls an address that the victim's wallet lists in `my_addresses`, and that the hub's `hub/get_arbstore_url` for that address resolves to a URL the attacker controls (attacker can self-register as arbiter with their own ArbStore URL).
2. Attacker's ArbStore server is configured to accept TCP connections on `/api/get_info` but never write a response (or writes partial headers and stalls).
3. Attacker sends the victim an `arbiter_dispute_request` device message referencing that arbiter address plus otherwise well-formed fields to pass the earlier validation steps in `wallet.js`.
4. Victim's `handleMessageFromHub` acquires the `"from_hub"` mutex, reaches `arbiters.getArbstoreInfo(body.arbiter_address)`, which calls `requestInfoFromArbStore` and hangs forever on `https.get` with no timeout.
5. `unlock()` is never called; every subsequent hub message (signing responses, private payments, chats) for the victim's node stops being processed until manual intervention/restart.

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
