### Title
Uncaught exception in `chash.isChashValid()` on malformed address checksum crashes the node - ([File: chash.js])

### Summary
`chash.isChashValid()` decodes an attacker-supplied address string and then runs it through several helper functions that `throw Error(...)` on any length mismatch, but only the initial decode call is wrapped in `try/catch`. Any unit, AA trigger, asset definition, or definition field that carries an address is fed through this function on every validation pass, so a single crafted address string reaching this code can throw an uncaught exception analogous to the GPAC `uncv_parse_config()` heap-overflow DoS: a malformed input to a low-level parsing routine that isn't defensively bounded causes the whole process to crash instead of failing gracefully.

### Finding Description
`isChashValid()` in [1](#0-0)  only guards the decode step:

```
try{
    var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
}
catch(e){
    console.log(e);
    return false;
}
var binChash = buffer2bin(chash);
var separated = separateIntoCleanDataAndChecksum(binChash);
var clean_data = bin2buffer(separated.clean_data);
var checksum = bin2buffer(separated.checksum);
return checksum.equals(getChecksum(clean_data));
```

`separateIntoCleanDataAndChecksum()` unconditionally throws if the decoded bit-length isn't exactly 160 or 288:
```
if (len === 160) ...
else if (len === 288) ...
else
    throw Error("bad length="+len+", bin = "+bin);
``` [2](#0-1) 

The `base32` decoder used (`thirty-two`) can legally return a byte buffer whose length is not exactly 20 bytes for a 32-character input string that still passes `isValidBase64`/charset checks used upstream (e.g. non-canonical padding or partial final group), so `chash.length*8` can differ from 160. Because this second stage is outside the `try/catch`, the `Error` propagates uncaught out of `isChashValid()`.

`isChashValid()` is invoked from `validation_utils.js` as part of `isValidChash`/`isValidAddress`, which is the single choke point used throughout `validation.js`, `definition.js`, and the AA composer to validate every author address, output address, asset attestor/issuer address, and address literal appearing in `oscript`/`ojson` definitions of a posted unit or AA trigger. This makes the vulnerable path reachable by any unprivileged unit poster or AA trigger sender who can place a syntactically-plausible but malformed 32/48-character address string anywhere an address is validated.

### Impact Explanation
If the uncaught `Error` is not caught by an outer `try/catch` in the validation call chain (validation is largely callback/async-driven, and several validation code paths call `isValidAddress` synchronously without wrapping it), it will surface as an uncaught exception in the unit/AA-trigger validation pipeline. In a Node.js process, an uncaught synchronous exception thrown outside of an `async`/promise boundary crashes the process. Since this check fires on ordinary, unprivileged input (any posted unit, trigger, or AA definition containing an address field), a single crafted joint can knock a node offline — a network-reachable denial of service, matching the same bug class as the reported GPAC heap-overflow DoS via a crafted MP4 (malformed input to a low-level format/length parser that isn't defensively bounded, causing a process-wide failure instead of a bounded validation error).

### Likelihood Explanation
Likelihood is limited by how many `isValidAddress`/`isValidChash` call sites in `validation.js`/`definition.js` are actually wrapped by node-level or process-level try/catch versus running inside a bare synchronous call in the request/validation loop, and by whether `base32.decode` from `thirty-two` can actually be coerced into returning a non-20-byte buffer for a 32-character, base32-alphabet-only string (this behavior of the third-party `thirty-two` package could not be independently confirmed in this pass — its source was not present in the indexed codebase). If the decoder strictly enforces canonical output length for any 32-character input, this specific throw path is not reachable and the analog does not hold.

### Recommendation
- Wrap the entire body of `isChashValid()` (not just the decode call) in a single `try/catch`, returning `false` on any thrown error, mirroring the defensive pattern already used for the decode step.
- Similarly harden `buffer2bin`/`bin2buffer`/`separateIntoCleanDataAndChecksum` call sites so that malformed-length inputs return a validation failure rather than throwing, and audit all `isValidAddress`/`isValidChash` call sites in `validation.js`, `definition.js`, and `aa_composer.js` to ensure they are never invoked in a context where an unexpected throw can escape as an uncaught exception.

### Proof of Concept
Conceptual PoC (pending confirmation of `thirty-two`'s exact decode behavior):
1. Construct a 32-character string using only valid base32 alphabet characters but with padding/length characteristics that cause `thirty-two`'s `base32.decode()` to return a buffer whose length is not 20 bytes (e.g. a truncated/padded final group).
2. Use this string as an address field in a unit's `outputs[].address`, an AA trigger's `address`, or an address literal inside an `oscript`/`ojson` definition, and post it to the network.
3. When the node validates the unit (`validation.js` → `validation_utils.isValidAddress` → `chash.isChashValid`), `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")`, which is uncaught by `isChashValid`'s inner try/catch and propagates up the validation call stack, potentially crashing the node process.
