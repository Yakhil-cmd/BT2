Based on the investigation, the closest reachable analog to CVE-2016-8620's root cause pattern (attacker-controlled length/index values that are never bounds-checked before being fed into array/index arithmetic) is the `"in merkle"` address-authentication path in `definition.js`, which parses an **unvalidated, attacker-supplied authentifier string** into merkle-proof internals without any of the length/type sanity checks that a parallel code path (`formula/evaluation.js`'s `is_valid_merkle_proof`) was later hardened with.

### Title
Unvalidated Merkle-proof authentifier (unbounded siblings array, unchecked index type) in `"in merkle"` address definitions - (File: `definition.js`)

### Summary
The `"in merkle"` address-definition operator lets a unit author supply an arbitrary string as the value of the corresponding authentifier. This string is deserialized with `merkle.deserializeMerkleProof` and fed straight into `merkle.verifyMerkleProof` with none of the defensive checks (max length, `siblings` count cap, "must be non-empty strings", numeric `index`) that the sibling `is_valid_merkle_proof` oscript function in `formula/evaluation.js` enforces.

### Finding Description
In `definition.js`, the `'in merkle'` case reads the authentifier directly from the attacker-controlled `assocAuthentifiers[path]` and passes it unchecked: [1](#0-0) 

`merkle.deserializeMerkleProof` performs a naive `split("-")`, `pop()`, `shift()` with no validation of element count, content, or numeric-ness of the index: [2](#0-1) 

`merkle.verifyMerkleProof` then loops over `proof.siblings` — a fully attacker-controlled, unbounded-length array — performing string-coercion arithmetic (`index % 2`, `Math.floor(index / 2)`) on `proof.index`, which is never validated to be an integer or even numeric: [3](#0-2) 

Contrast this with the later-hardened `is_valid_merkle_proof` oscript function, which explicitly caps proof size (`proof.length > 1024`), requires `siblings` to be an array of non-empty strings, and caps `siblings.length` to 50 once `bPostPemCurvesFix` is active: [4](#0-3) 

No equivalent length/type checks were ever added to the `"in merkle"` definition-authentifier path in `definition.js`, meaning any address whose definition includes an `"in merkle"` clause is validated with untrusted, unbounded data during ordinary unit posting/validation — the same "trust user length without bound before doing indexed math" pattern that caused the curl globbing integer-overflow OOB read.

### Impact Explanation
Any unit author who signs with an `authentifiers[path]` value under an address using an `"in merkle"` condition controls the number of siblings (no upper bound, unlike the 50-item cap enforced elsewhere) and the format of `index` (never coerced/validated as an integer). Because `hash()` in `merkle.js` does not domain-separate leaf vs. internal nodes, and the reconstruction loop blindly trusts attacker-chosen sibling ordering/count while `index` type is uncontrolled, this significantly widens the search space compared to the properly-bounded path and increases risk of second-preimage/duplicate-node style forgeries of the merkle root used for `dataFeeds.dataFeedExists` matching, which is the very check that gates whether the authentifier is accepted as satisfying the address's spending condition. A successful forgery would let an attacker satisfy an `"in merkle"` spending condition without possessing a genuine proof against the real data-feed root — i.e., unauthorized spending from that address.

### Likelihood Explanation
Reaching this code only requires posting a unit authored by an address whose definition contains `["in merkle", ...]` and supplying a crafted `authentifiers[path]` string — fully within reach of an unprivileged unit poster, with no special network or node compromise required. However, actually constructing a valid forged proof depends on finding a hash collision/duplicate-node arrangement, which is non-trivial but exactly the class of weakness that unbounded/unchecked-length structures make easier (the missing length caps that were added elsewhere for this exact function are the differentiator).

### Recommendation
Apply the same validation that `formula/evaluation.js`'s `is_valid_merkle_proof` uses to the `"in merkle"` definition path in `definition.js`: bound the serialized-proof string length, require `proof.siblings` to be a reasonably small array (e.g. ≤ 50) of non-empty strings, and require `proof.index` to be parsed and validated as a non-negative integer before use in `merkle.verifyMerkleProof`. Consider also domain-separating leaf and internal-node hashing in `merkle.js` to remove the structural ambiguity that enables duplicate/second-preimage forgeries regardless of length limits.

### Proof of Concept
1. Define an address `A` with definition `["in merkle", [["ORACLE_ADDR"], "feed_name", "expected_value"]]`.
2. Post a unit authored by `A` with `authentifiers: { "r": "<attacker-crafted-index>-<many-attacker-chosen-sibling-hashes>-<target-root>" }`, where the attacker chooses an arbitrarily large number of siblings and a non-validated `index` value.
3. `definition.js`'s `'in merkle'` handler (`definition.js:1004-1020`) calls `merkle.deserializeMerkleProof`/`merkle.verifyMerkleProof` on this string with no length or type checks, unlike the bounded `is_valid_merkle_proof` formula function; craft siblings/index combinations offline until `verifyMerkleProof` returns true for a `root` matching a real `dataFeeds.dataFeedExists` value, thereby satisfying the spending condition without a legitimate proof.

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
