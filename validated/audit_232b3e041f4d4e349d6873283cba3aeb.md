This confirms the multi-organization configuration model: each configured organization gets its own `GitHubApp` instance and, per `TOP_LEVEL_GH_KEYS`, its own `webhook_secret` [1](#0-0) , selected via `github_app_config(organization)` keyed on the organization name [2](#0-1) .

### Title
Webhook signature is verified against `repository.owner.login` but the write target is resolved from the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to check the HMAC against using `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or the `organization` sub-object) [3](#0-2) [4](#0-3) . Once the signature check passes, every downstream `Handler` resolves the `Repository`/`Stack` to mutate using a *different* field from the same payload: `payload.dig('repository','full_name')` [5](#0-4) [6](#0-5) . Nothing binds `repository.owner.login` (the field whose corresponding secret authenticated the request) to `repository.full_name`'s owner segment (the field whose `Repository`/`Stack` actually gets written).

### Finding Description
This is the same class of bug the external report describes: a check is performed on one binding (`rolesManager.isGovernance(msg.sender)` checked, but the action doesn't depend on the value that was checked in a coherent way), while the actual privileged action operates on a value never covered by the check. Here, the equality that must hold for the design to be safe is:

```
organization_that_authenticated (repository.owner.login, used to pick the webhook_secret)
  == organization_of_repository_written (owner segment of repository.full_name, used by Repository.from_github_repo_name)
```

`verify_webhook_signature` only proves that the raw request body was HMAC-signed with the secret configured for whatever organization `repository_owner` claims to be [7](#0-6) . It does not prove, and nothing else in the request pipeline re-verifies, that `repository.full_name`'s owner is the same organization. Handlers such as the push/status/check_suite/membership handlers then look up `Repository.from_github_repo_name(repository_name)` purely from `full_name` and dispatch writes (queued sync jobs, commit statuses, team/membership churn, PR handling) against whatever repository that resolves to [5](#0-4) .

Because Shipit supports one `webhook_secret` per configured organization [8](#0-7) [2](#0-1) , an actor who can produce a validly-signed webhook payload for Organization A (e.g., because they administer a GitHub App/webhook integration installed on Org A's repositories, which does not require any Shipit credential, `ApiClient` token, or Shipit repository write access) can freely set `repository.full_name` inside that same signed payload to `orgB/some-repo` while leaving `repository.owner.login`/`organization.login` as `orgA` so the correct (Org A) secret is used for HMAC verification. `verify_signature` passes because it only checks the org-A secret against the org-A-labeled field; the handler layer then acts on the attacker-chosen `orgB/some-repo` value, causing Shipit to record commit statuses, enqueue `GithubSyncJob`, add/remove `Membership`/`Team` records, or process PR-driven review-stack actions for a stack that Org A's webhook was never entitled to touch.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. Consequences include unauthorized cross-organization/cross-repository writes to Stack state (queued deploy-triggering sync jobs via `GithubSyncJob`, forged commit statuses affecting `merge_status`/branch protection-like decisions, and forged membership/team changes) driven entirely by a payload whose only genuine credential is a *different* organization's webhook secret. This matches the "cross-repository writes" criterion.

### Likelihood Explanation
Exploitability requires the attacker to already control (or be able to trigger) a genuinely-signed webhook delivery for at least one organization configured in the multi-tenant Shipit deployment — e.g., by having admin/webhook-config access on any one GitHub org/repo pointed at this Shipit instance, which is a much weaker bar than obtaining a Shipit session, `ApiClient` token, or `GITHUB_TOKEN`. Any Shipit deployment onboarding more than one organization is affected; the more organizations configured, the larger the blast radius for any single compromised/malicious org integration.

### Recommendation
`verify_signature` should re-derive the repository owner it verifies against and reject (or the handler layer should reject) any payload where `repository.owner.login` (or `organization.login`) does not match the owner segment of `repository.full_name`, so the field the HMAC-authorization decision is based on is provably the same field the write logic operates on.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `github_app_config`) [2](#0-1) .
2. As an entity with legitimate control over Org A's GitHub webhook configuration (not a Shipit user), craft a `push` (or `status`/`check_suite`/`membership`) payload where `repository.owner.login` = `"orgA"` but `repository.full_name` = `"orgB/target-repo"`.
3. Sign the raw body with Org A's `webhook_secret` and send it to `/webhooks` with the correct `X-Hub-Signature` header.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")` from `repository_owner` and successfully verifies the HMAC [9](#0-8) .
5. `Shipit::Webhooks.for_event(event)` handlers run `Repository.from_github_repo_name("orgb/target-repo")` from `full_name`, resolving Org B's `Stack` and performing the corresponding write (e.g., enqueuing `GithubSyncJob`, adding a commit `Status`, or creating/removing a `Membership`), even though the signature never proved anything about Org B [5](#0-4) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
