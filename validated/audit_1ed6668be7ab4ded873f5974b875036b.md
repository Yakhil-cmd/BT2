### Title
StatusHandler#process resolves commits by global sha lookup, letting one repository's signed status webhook mutate every other tenant stack sharing that commit sha - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with an unscoped `Commit.where(sha: params.sha)` instead of scoping through the repository that owns the webhook, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which resolve `stacks` via `Repository.from_github_repo_name(repository_name)`. Because the schema explicitly supports the same sha existing in multiple stacks (`add_index :commits, %i(sha stack_id), unique: true`), a single validly-signed webhook for one repository/org updates the commit status - and can trigger `ContinuousDeliveryJob` - for every unrelated tenant stack that happens to contain a commit with the same sha.

### Finding Description
The broken binding is: number of organizations that authenticated the payload (1, verified by `WebhooksController#verify_signature` against `repository_owner`) should equal the number of distinct tenant stacks mutated by processing that payload. This is violated whenever `Commit.where(sha: params.sha)` in `StatusHandler#process` matches N > 1 stacks.

Code path:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) authenticates the payload only against the GitHub App configured for `repository_owner` derived from `params.dig('repository','owner','login')`. It does not restrict which stacks/commits the handler may touch - it only proves the sender owns that one org's signing secret. [1](#0-0) 
- `StatusHandler` declares only `sha`, `state`, and optional fields - it never requires or reads `repository` at all, and its `process` method queries commits globally: [2](#0-1) 
- Contrast with `CheckSuiteHandler` and `PushHandler`, which scope through `stacks`, itself derived from the payload's `repository.full_name`: [3](#0-2) [4](#0-3) 
- The schema itself acknowledges the same sha can legitimately exist in multiple stacks: the commits table has a composite unique index on `(sha, stack_id)`, not a unique index on `sha` alone. [5](#0-4) 
- `Commit#create_status_from_github!` → `add_status` emits hooks and, on the appropriate state transition, calls `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob.perform_later(stack)` if the commit's stack has `continuous_deployment?` enabled and is deployable: [6](#0-5) [7](#0-6) 

Exploit flow: an attacker who owns/controls repository A (a real Shipit tenant, e.g. any GitHub user whose fork/repo is tracked by Shipit) triggers a normal, validly GitHub-signed `status` webhook for their own repository (e.g. via their own CI reporting a commit status, which is fully within their control as repo owner). If the sha of that commit happens to also exist as a `Commit` row under stacks B and C (different tenants who vendor the same upstream open-source commit, or share history from a common fork point - a scenario the schema explicitly permits), `StatusHandler#process` iterates `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on all three commit rows, one per stack, regardless of which repository actually sent the webhook. If stacks B or C have `continuous_deployment?` enabled and become deployable off this forged/incidental status, `ContinuousDeliveryJob` is enqueued for B and C too - none of which authenticated or authorized this payload.

None of the existing guards catch this: `verify_signature` only proves the sender owns org A's secret, not that the affected stacks belong to org A; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema for `StatusHandler` doesn't require/validate `repository` at all so there's nothing to cross-check against; and there is no `stacks`/`Repository.from_github_repo_name` scoping call anywhere in `StatusHandler`, unlike `PushHandler`/`CheckSuiteHandler`.

### Impact Explanation
A single validly-signed webhook from tenant A causes commit status writes, and potentially `ContinuousDeliveryJob` enqueues (leading to real deploys via `stack.trigger_continuous_delivery`), against stacks B and C that never received or authorized any webhook from their own configured GitHub organization/repository. This is a cross-tenant mutation: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." The blast radius scales with however many tenant stacks share an overlapping commit sha (vendored dependencies, shared monorepo history, common upstream forks are realistic and repeatable sources of such collisions), and is repeatable on every subsequent status webhook from the attacker-controlled repository.

### Likelihood Explanation
Preconditions: (1) the victim stacks must contain a `Commit` row with the same sha as one in the attacker's own repository - realistic in shared vendoring/fork scenarios, not requiring a cryptographic sha collision; (2) the attacker's own repository must be a Shipit-tracked tenant able to emit genuinely GitHub-signed `status` webhooks (trivial - status events are commonly sent by any CI integrated with the attacker's own repo); (3) victim stacks need `continuous_deployment?` enabled for the deploy-trigger portion of the impact, though the commit-status/webhook-mutation across tenants happens regardless. The attacker needs no secrets, no privileged role, and no interaction with the victim - only ordinary control of their own repository's CI/webhooks, matching the described "unprivileged attacker" threat model exactly.

### Recommendation
Scope `StatusHandler#process` (and any other sha-based commit lookups without repository scoping) through the repository asserted in the payload, mirroring `PushHandler`/`CheckSuiteHandler`: require `repository.full_name` in the params schema and replace `Commit.where(sha: params.sha)` with `stacks.commits.where(sha: params.sha)` (using the `stacks` helper resolved from `Repository.from_github_repo_name(repository_name)`), ensuring only stacks belonging to the authenticated repository can have their commit statuses mutated.

### Proof of Concept
Minitest plan (model-level, no live GitHub, mirrors `test/controllers/webhooks_controller_test.rb` conventions):
1. Create three `Repository`/`Stack` fixtures representing three distinct tenants (`repo_a`, `repo_b`, `repo_c`), each with `continuous_deployment: true` and `occupied?` false/deployable.
2. Create one `Commit` per stack, all with the identical `sha: "deadbeef..."`.
3. Build a `status` webhook payload for `repo_a` only (`repository.full_name == "owner/repo_a"`, `sha == "deadbeef..."`, `state: "success"`), sign it validly for `repo_a`'s org (stub `verify_webhook_signature` true).
4. POST to `/webhooks` once.
5. Assert: `commit_a.statuses.count`, `commit_b.statuses.count`, and `commit_c.statuses.count` all increased by 1 (binding LHS = 1 authenticated org vs RHS = 3 mutated stacks - violated).
6. Assert `assert_enqueued_jobs 3, only: ContinuousDeliveryJob` (or `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_a])`, `[stack_b]`, `[stack_c]` each once) after invoking `ContinuousDeliveryJob.new.perform(stack)` for each, demonstrating three separate tenant stacks are enqueued for deploy from a single request that only authenticated for `repo_a`.
