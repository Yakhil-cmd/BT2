### Title
Missing newline-delimiter sanitization for `feed_name`/`value` in the `in data feed` address-definition operator allows key-prefix injection into the data-feed KV-store range query - (File: definition.js)

### Summary
`definition.js`'s `evaluate()` handler for the `'in data feed'` operator (used in address definitions / spending conditions) validates only the *length* of `feed_name` and `value`, but — unlike the equivalent runtime checks in `aa_validation.js` and `validation.js` — never rejects embedded `\n` characters. `\n` is the field delimiter used to build and parse data-feed keys in the KV store (`kvstore`), e.g. `'df\n'+address+'\n'+feed_name+'\n'+prefixed_value` in `data_feeds.js`. Since address definitions are attacker-controlled data supplied by any unit poster/address definer, this is the same bug class as the Helm advisory: unsanitized, attacker-supplied strings are embedded verbatim into a structured, delimiter-based format used for further parsing/matching, and the special delimiter character is not neutralized.

### Finding Description
- `validateDefinition()` → case `'in data feed'` in [1](#0-0)  only checks:
  - `feed_name.length > constants.MAX_DATA_FEED_NAME_LENGTH`
  - `value.length > constants.MAX_DATA_FEED_VALUE_LENGTH`

  It does **not** check `feed_name.indexOf('\n') >= 0` or `value.indexOf('\n') >= 0`.

- Compare this to the two other places in the codebase that validate the *same* kind of feed name/value and *do* reject `\n`:
  - AA definition validation: [2](#0-1) 
  - Unit message validation (`data_feed` app): [3](#0-2) 

  Both of these explicitly guard against `feed_name`/`value` containing `\n` because `\n` is the reserved separator for the on-disk key format.

- The actual data-feed keys stored by `writer`/`main_chain.js` are built as `'df\n'+address+'\n'+feed_name+'\n'+type+'\n'+value+'\n'+strMci` (see `addDataFeeds()` in [4](#0-3) ), and can never contain literal `\n` inside `feed_name`/`value` because those paths enforce the check.

- However, when an address definition's `'in data feed'` condition is *evaluated* against the KV store, `dataFeedByAddressExists()` builds a `key_prefix` and range-query bounds directly from the attacker-supplied `feed_name`/`value` without any delimiter check: [5](#0-4) . If `feed_name` or `value` (as literal, non-formula strings) contains an embedded `\n`, the resulting `key_prefix` and the `gt`/`gte`/`lt`/`lte` bounds passed to `kvstore.createKeyStream()` no longer correspond 1:1 to the fields boundaries used at write time. Because RocksDB/LevelDB key streams operate on raw lexicographic byte ranges, inserting extra `\n` bytes shifts the effective prefix/range boundaries (e.g. widening or narrowing the `>`/`<`/`>=`/`<=` bound computed with the sibling `'\r'`/`'\n'` "next separator" trick at lines 150/154/158/162), which can cause the range scan to match keys it should not match (or fail to match ones it should), silently changing the true/false outcome of `dataFeedExists`/`dataFeedByAddressExists`.

### Impact Explanation
`'in data feed'` conditions are used to gate spending from smart addresses (definitions), e.g. oracle-based escrows, price-triggered payouts, etc. If an attacker who authors/co-authors such an address definition can construct a `feed_name`/`value` containing `\n` that causes the KV range query to (a) match an oracle post that should not satisfy the condition, or (b) fail to match one that should, this is a node-disagreement / condition-evaluation-integrity bug: it can make a smart contract's spending authorization evaluate inconsistently with the documented/intended semantics, potentially allowing unauthorized withdrawal from a shared/oracle-gated address whose owners believed the condition was strict, or freezing legitimate spends by making a supposed-true condition evaluate false everywhere. This maps to the "concrete unauthorized spending" / "AA fund loss or freezing" outcomes required by the validation rubric — the exact analog to Helm's version-field injection letting malicious/malformed data escape its intended structural boundaries and corrupt downstream parsing/decisions.

### Likelihood Explanation
Medium. Exploitation requires:
1. Constructing an address (or AA) definition containing an `'in data feed'` clause with a `feed_name`/`value` embedding `\n` — trivially reachable by any unit poster/address definer since these are only length-checked, not delimiter-checked.
2. Understanding the exact prefix/bound math in `dataFeedByAddressExists()` well enough to shift a range boundary favorably. The `'\r'`/`\n` adjacent-separator trick used for open ranges makes probing this boundary condition feasible but requires careful crafting.
No signing/witness/hub privilege is required — only ordinary ability to post a unit defining or paying to such an address, matching the "unprivileged unit poster / address definer" reachable-actor requirement.

### Recommendation
In `definition.js`'s `'in data feed'` case (and any other place constructing data-feed KV-store keys from literal, non-formula `feed_name`/`value` strings), add the same guard used in `aa_validation.js`/`validation.js`:
```js
if (feed_name.indexOf('\n') >= 0)
    return cb("feed_name contains \\n");
...
if (typeof value === "string" && value.indexOf('\n') >= 0)
    return cb("value contains \\n");
```
Apply this consistently to every code path that builds `'df\n'+...` (or similar `\n`-delimited) kvstore keys from untrusted, non-formula literal strings, so that address-definition-time validation matches the write-time/runtime invariants already enforced elsewhere.

### Proof of Concept
1. Construct an address definition unit with:
   ```json
   ["in data feed", [["ORACLE_ADDRESS"], "feed\nname_with_injected_separator", "=", "expected"]]
   ```
   or with a `value` such as `"x\ny"`. This passes `validateDefinition()` in `definition.js` because only `.length` is checked (lines 425-434), never `indexOf('\n')`.
2. Post the unit defining/using this address as a spending condition (e.g. a shared address requiring `in data feed`).
3. When a payment from that address is validated, `Definition.evaluate()` calls `dataFeeds.dataFeedExists(...)` → `dataFeedByAddressExists()`, which builds `key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value` using the raw, `\n`-containing `feed_name`/`value` (`data_feeds.js` lines 119-163) and issues a `kvstore.createKeyStream()` range query against it.
4. Because the injected `\n` shifts the byte-range boundaries relative to the well-formed keys written by `addDataFeeds()` (which never contain embedded `\n` in any field), the resulting range scan no longer corresponds to "does an oracle-posted value satisfy `feed_name relation value`" as intended — it can be demonstrated (by comparing the constructed `options.gt/gte/lt/lte` strings against actually-stored key strings) that the match set differs from the non-injected case, i.e., the condition's truth value depends on the presence of the smuggled delimiter rather than on legitimate oracle data.

*(Note: I was not able to fully execute this against a live RocksDB instance to observe the concrete `bFound` divergence for a specific chosen boundary case — that would require an interactive test/repro environment. The root-cause gap — the missing `indexOf('\n')` check that exists in the two sibling validators — is confirmed directly from the source.)*
