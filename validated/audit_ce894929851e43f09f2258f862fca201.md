### Title
Unbounded digit-string in `iteration`/`max_iterations` bypasses numeric-safety validation, causing bash arithmetic overflow/crash instead of a fail-closed stop - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
`stop-hook.sh` validates the `iteration` and `max_iterations` YAML frontmatter fields with the bare-digit regex `^[0-9]+$` before using them in bash arithmetic comparisons and increments [1](#0-0) . The regex accepts digit strings of unbounded length/magnitude, so a crafted state file with a huge numeric value (e.g. `> 2^63-1`) passes validation but then feeds bash's 64-bit arithmetic evaluator in `[[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]` and `$((ITERATION + 1))`, which can produce an "value too great for base" arithmetic error or overflow/wraparound instead of the intended graceful "state file corrupted" handling [2](#0-1) [3](#0-2) .

### Finding Description
The state file `.claude/ralph-loop.local.md` is a project-relative file that is normally created by `scripts/setup-ralph-loop.sh` (invoked by `/ralph-loop`), but the stop hook itself does not verify who wrote the file — it simply checks for its existence in the working directory and trusts its contents [4](#0-3) . Because this path lives inside the project tree, it can be committed by an attacker into a repository; if a victim opens that repository with Claude Code and has the `ralph-wiggum` plugin's Stop hook enabled, the hook auto-executes and parses this attacker-supplied file on the very next Stop event, without the victim ever running `/ralph-loop`.

The validation at lines 28 and 39 only checks that the string is composed exclusively of digits (`^[0-9]+$`); it enforces no upper bound [1](#0-0) . A digit string exceeding bash's 64-bit signed integer range (e.g. 20+ digits) satisfies the regex but then breaks the downstream arithmetic contexts:
- `[[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]` — arithmetic evaluation of an out-of-range operand [5](#0-4) .
- `NEXT_ITERATION=$((ITERATION + 1))` — arithmetic expansion of an out-of-range operand [6](#0-5) .

Bash arithmetic errors of this kind ("value too great for base") are not gracefully handled anywhere in this script; the comment "Validate numeric fields before arithmetic operations" signals developer intent to fully sanitize inputs before arithmetic, but the sanitization is incomplete because it checks format, not magnitude. Since `set -euo pipefail` is active, and non-interactive bash treats malformed arithmetic expansions as fatal regardless of `errexit` state, execution can abort before reaching the file cleanup (`rm "$RALPH_STATE_FILE"`) that every other error branch performs. This leaves the corrupted/oversized state file in place and produces an unhandled failure instead of the script's intended fail-closed message-and-cleanup behavior.

### Impact Explanation
Scoped impact is availability/robustness of the ralph-loop stop-guard mechanism: an attacker who can plant repository content reachable by the stop hook can force the hook to hit an uncaught arithmetic error path rather than the intended "corrupted state file → stop and clean up" path. Consequences are (a) hook execution failure/DoS for the Stop event, and (b) loss of the deterministic max-iteration guard behavior that the rest of the script carefully implements (every other malformed-input case explicitly removes the state file and exits 0 cleanly; this case does not). This does not grant code execution or credential/secret disclosure — it is a logic/availability bug in an opt-in plugin's guard rail.

### Likelihood Explanation
Preconditions: (1) the `ralph-wiggum` plugin's Stop hook must be enabled in the victim's Claude Code session, and (2) an attacker-controlled `.claude/ralph-loop.local.md` file with an oversized digit value must exist in the workspace when a Stop event fires (e.g., via a malicious repository the victim opens). Both preconditions are plausible under "ordinary repository content" reachable without special privilege, and no part of the script cross-checks who authored the file or bounds the parsed values before arithmetic use. The bug is deterministic and repeatable given the same oversized input.

### Recommendation
Add an explicit upper-bound check after the regex validation for both `ITERATION` and `MAX_ITERATIONS` (e.g., reject/clamp values greater than a safe threshold such as `2^63-1` or a much smaller practical cap like `1000000`), and treat any out-of-range value the same way the existing "corrupted state file" branches do — emit the warning, `rm` the state file, and `exit 0` — before any arithmetic comparison or expansion is attempted.

### Proof of Concept
Fuzz/integration test plan:
1. Create `.claude/ralph-loop.local.md` with frontmatter `iteration: 1` and `max_iterations: 99999999999999999999999` (25 nines, > 2^63-1), followed by a valid prompt body.
2. Invoke `stop-hook.sh` with a minimal valid JSON `{"transcript_path": "..."}` on stdin.
3. Assert the hook does NOT terminate with an uncaught bash arithmetic error (e.g. stderr containing "value too great for base") and a non-zero/undefined exit status; instead assert it either (a) prints the "state file corrupted"-style message and removes the state file, exiting 0, or (b) safely treats the value as "unlimited/invalid" and stops the loop.
4. Repeat with `iteration` set to the oversized value and `max_iterations` normal (e.g. `10`), asserting `$((ITERATION + 1))` does not crash the script and the loop still terminates deterministically rather than looping via a wrapped/negative iteration count.
5. Repeat with both fields set to boundary values around `9223372036854775807` (`2^63-1`) and `9223372036854775808` to confirm the exact overflow boundary and failure mode.
