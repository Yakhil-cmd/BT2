### Title
Unscoped commit-SHA matching in `StatusHandler` lets a webhook authenticated for one repository forge deploy-gating commit statuses on any other repository's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook against based solely on the payload's `repository.owner.login` (or `organization.login`), i.e. it authenticates *who sent this* at the organization/app level. But `Handlers::StatusHandler#process` never re-checks that binding: it looks up commits to update purely by SHA across the *entire* `commits` table, with no scoping to the repository/organization that was actually authenticated. Because GitHub's Statuses API lets any repository collaborator with push access set a status on an arbitrary SHA string (it does not have to belong to that repository's history), an attacker who legitimately controls one onboarded repository can produce a cryptographically valid, GitHub-signed `status` webhook whose `sha` matches a commit belonging to a completely different stack, and flip that unrelated commit's CI state to `success`.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This picks a per-organization `webhook_secret` (Shipit supports multiple GitHub Apps/orgs, each with its own secret, see `lib/shipit.rb` `github_app_config`) [2](#0-1) [3](#0-2) . The signature check only proves the payload was really sent by GitHub for *that organization's app*; it says nothing about which specific repository/stack the payload's effects should be limited to.

`Handlers::StatusHandler`, however, ignores `repository` entirely:
```ruby
class StatusHandler < Handler
  params do
    requires :sha, String
    requires :state, String
    ...
  end

  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
``` [4](#0-3) 

Unlike every other handler (`Handler#repository_name`/`#stacks`, `PushHandler`, the `pull_request` handlers) which scope lookups via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [5](#0-4) [6](#0-5) , `StatusHandler` matches purely by SHA across the whole installation, then updates the SHA's own `commit.stack_id`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [7](#0-6) 

A commit's `success` status directly affects deployability and continuous delivery:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [8](#0-7) 
and creating a `success` `Status` schedules continuous delivery / merges via `after_commit` callbacks [9](#0-8) , which is exercised in `test "updating state to success triggers new deploy when stack has continuous deployment"` [10](#0-9) .

GitHub's Statuses API (`POST /repos/{owner}/{repo}/statuses/{sha}`) does not require the target `sha` to actually be reachable from that repository's history — any repository collaborator with push access can set a status on an arbitrary SHA string. GitHub will then send a correctly HMAC-signed `status` webhook event, with `repository` reflecting the attacker's own onboarded repo (so `verify_signature` passes using that repo's org secret) but `sha` chosen to collide with a real commit SHA that exists in a *different*, unrelated stack.

**Binding broken:** the organization/app whose `webhook_secret` authenticated the payload (`repository_owner` in `WebhooksController#verify_signature`) ≠ the repository/stack whose commit status is actually mutated by `StatusHandler#process` (looked up by bare SHA with no repository scoping).

### Impact Explanation
An attacker who legitimately controls (or has push access to) any single repository onboarded to a shared Shipit instance can forge a real, correctly-signed webhook that marks an arbitrary commit SHA — which they know belongs to a totally unrelated stack (SHAs are public information, visible via `git log`/GitHub UI/API on the target repo) — as `success`. If that target stack has `continuous_deployment` enabled or is otherwise gated on commit status, this can unblock/trigger an unauthorized deploy of code that never actually passed CI, matching the report's listed Critical impact ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires only:
1. Being a legitimate contributor/collaborator with push access to any one repository already onboarded to the shared Shipit instance (not a Shipit account, no `ApiClient` token, no privileged Shipit role).
2. Knowledge of a target commit SHA in the victim stack's repository (public git metadata).

No secret material needs to be stolen — the attacker rides their own legitimately-signed webhook. This is a low-effort, unprivileged-relative-to-the-victim-stack attack in any multi-stack/multi-tenant Shipit deployment.

### Recommendation
Scope `StatusHandler` (and any other handler that currently ignores the `repository` payload field) to the repository/organization that was actually authenticated: require and validate `payload.dig('repository', 'full_name')`, resolve the `Repository`/`Stack` the same way `Handler#stacks` does, and restrict the `Commit.where(sha: ...)` lookup to commits belonging to that resolved stack (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), so a status for one repository can never mutate commit state belonging to a different repository/stack.

### Proof of Concept
1. Attacker has push access to `attacker-org/repo-a`, which is onboarded to the shared Shipit instance as `stack-a` (attacker-org's GitHub App `webhook_secret` is unknown to the attacker but irrelevant — GitHub computes the signature).
2. Attacker looks up (public) the current HEAD SHA of `victim-org/repo-b`'s tracked branch, onboarded as `stack-b` with `continuous_deployment: true` in the same Shipit instance.
3. Attacker calls GitHub's API: `POST /repos/attacker-org/repo-a/statuses/<victim-sha>` with `{"state":"success", "context":"ci"}`. GitHub accepts this even though `<victim-sha>` isn't in `repo-a`'s history.
4. GitHub sends Shipit a `status` webhook with `repository.full_name = "attacker-org/repo-a"`, `sha = <victim-sha>`, `state = "success"`, signed with `attacker-org`'s webhook secret.
5. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s app and passes.
6. `StatusHandler#process` runs `Commit.where(sha: <victim-sha>)`, which matches the commit belonging to `stack-b` (victim's stack), and calls `create_status_from_github!`, creating a `success` `Status` on that commit — potentially unblocking/triggering an unauthorized deploy of `stack-b`, a stack the attacker has no access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
