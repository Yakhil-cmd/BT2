### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` and calls `create_status_from_github!` on every match, without ever checking that the webhook's `repository.full_name` matches `commit.stack.repository.full_name`. Because signature verification is keyed only to the *organization that owns the webhook* (via `Shipit.github(organization: repository_owner)`), not to any specific commit, an attacker who controls their own GitHub org/repo can send a validly-signed `status` webhook naming their own repo, but with a `sha` that collides with a commit belonging to an unrelated victim stack, and thereby write a forged `Status` row onto that victim's commit.

### Finding Description
The broken binding, stated explicitly: for every `Commit` row mutated by `StatusHandler#process`, the code never enforces `payload.dig('repository','full_name') == commit.stack.repository.full_name`.

Code path:
- `Shipit::WebhooksController#create` parses JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
- `verify_signature` only checks the HMAC against the webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`) [2](#0-1) . This proves the request was signed by *some* org's webhook secret — the attacker's own org — not that the payload's `sha` belongs to that org's repository.
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with no use of `Handler#stacks` or `repository_name` scoping [3](#0-2) . Contrast this with the base `Handler` class, which does provide a `stacks` helper scoped by `Repository.from_github_repo_name(repository_name)` [4](#0-3) , but `StatusHandler` never calls it.
- `Commit#create_status_from_github!` unconditionally creates a `Status` row tied to the commit's actual `stack_id` [5](#0-4) .

Exploit flow: attacker registers/owns `attacker/own-repo` with its own Shipit-configured webhook secret. Attacker crafts or discovers a git object (e.g. the well-known empty tree sha, or any byte-identical content) so their own repo contains a commit with `sha == SHA_X`, where `SHA_X` also exists as a `Commit` row under victim Stack V. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body `{ sha: SHA_X, state: 'success', context: 'ci/travis', repository: { full_name: 'attacker/own-repo' } }`, signed with their own valid webhook secret. Signature check passes (it's a legitimate signature for the attacker's own org). `Commit.where(sha: SHA_X)` matches the victim's commit row (and possibly others sharing that sha), and a forged `success` Status is written onto Stack V's commit, potentially unblocking CI-gated deploy eligibility for a commit the victim never actually built/tested for that context.

Existing guards do not prevent this: `verify_signature` authenticates "an org's webhook", not "this specific sha belongs to this org's repo"; `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` only validates types/presence, not repository ownership; there is no `stacks`/`repository_name` filter applied in `StatusHandler#process`.

### Impact Explanation
A payload legitimately signed for one repository can mutate an unrelated Stack's `Commit` by injecting a forged `Status` record, matching the "payload for one repository mutating another's stack/commit" Critical category. This can be used to mark an unreviewed victim commit as `success` for a required CI context (e.g. `ci/travis`), potentially satisfying `deployable?`/blocking-status checks and enabling an unauthorized deploy of that commit, or conversely to mark a victim's commit as `failure`/`error` to block their deploys (denial of legitimate work, though the primary tracked impact here is the unauthorized write itself). This is repeatable against any sha the attacker can reproduce in a repo they control (well-known shas like the empty tree, empty blob, or any commit whose tree/parents/timestamps the attacker fully controls and can brute-force/reproduce), and works against any tenant/stack in the same Shipit instance regardless of the target's own webhook configuration.

### Likelihood Explanation
Requires: (1) attacker owns/administers a GitHub repo connected to the same Shipit instance with a configured webhook secret for their org (a normal, unprivileged self-service setup in enterprise Shipit deployments with many onboarded repos/orgs); (2) attacker must produce a commit whose sha collides with an existing victim commit — trivial for well-known content-addressed objects (empty tree/blob), and otherwise requires reproducing exact commit content, which is feasible if the attacker forks/copies public repo content but not for arbitrary secret victim commits. Attacker cost is a single signed HTTP POST, fully repeatable, no secrets stolen or session required — matching the threat model given (unprivileged internet attacker with ability to emit webhooks from their own repo).

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the calling repository, e.g. filter to commits whose `stack` belongs to `stacks` (the `Handler#stacks` helper already resolves `Repository.from_github_repo_name(repository_name)`), and only call `create_status_from_github!` for commits under stacks whose repository's `full_name` equals the verified `repository_name` from the payload. Apply the same repository-scoping check to any other handler that queries `Commit` by `sha` without going through `stacks`.

### Proof of Concept
minitest integration test (`test/controllers/webhooks_controller_test.rb` style):
1. Create two fixture stacks: `stack_a` (repo `victim/target`) and `stack_b` (repo `attacker/own-repo`), each with their own webhook secret configured in test config.
2. Create `commit = stack_a.commits.create!(sha: SHA_X, ...)`.
3. POST `/webhooks` with header `X-Github-Event: status`, body `{ sha: SHA_X, state: 'success', context: 'ci/travis', repository: { full_name: 'attacker/own-repo' } }`, signed with `stack_b`'s webhook secret.
4. Assert response is `200 OK`.
5. Assert `commit.reload.statuses.last.state == 'success'` and `commit.stack == stack_a` — i.e., assert `payload['repository']['full_name'] ('attacker/own-repo') != commit.stack.repository.full_name ('victim/target')` while the Status was still created, proving the `REPOSITORY_SCOPE` binding is not enforced.
6. Negative control: after fix, assert the same POST results in no new `Status` on `stack_a`'s commit (since `attacker/own-repo` does not own that commit).
