### Title
Uncaught exception (DoS crash) in address c-hash validation via malformed input to `isValidAddressAnyCase` - (File: chash.js)

### Summary
`chash.isChashValid()` decodes an attacker-supplied string and processes the decoded buffer through bit-manipulation routines that assume a fixed length. A length mismatch raises an `Error` that is not caught, unlike the bounded `base32.decode`/`Buffer.from` call that precedes it. This mirrors the Wireshark HCI_ISO dissector bug class: malformed length-driven parsing of externally supplied data results in an unhandled fault instead of a graceful validation failure.

### Finding Description
`isChashValid()` wraps only the initial decode step in try/catch: [1](#0-0) 
but the functions it calls afterward — `buffer2bin`, `separateIntoCleanDataAndChecksum`, and (transitively via `getChash`) `mixChecksumIntoCleanData` — throw plain `Error` objects when the bit-length of the decoded data does not match the expected 160 or 288 bits: [2](#0-1) [3](#0-2) 

The entry point `isValidAddressAnyCase()` calls `isChashValid()` without first constraining the input to the base32 alphabet (`[A-Z2-7]`), unlike `isValidAddress()` which applies a regex pre-filter: [4](#0-3) 

Because `thirty-two`'s `base32.decode` can, depending on the exact byte content of a 32-character string, produce a decoded buffer whose bit-length diverges from the hard-coded 160-bit expectation used by `separateIntoCleanDataAndChecksum`, a crafted 32-character string reaching `isValidAddressAnyCase` can trigger the uncaught `Error("bad length=...")`, crashing the node process (unhandled exception) rather than returning `false`.

### Impact Explanation
An uncaught exception thrown during unit/AA/trigger validation on a full node is a process-crashing condition — a hard denial of service, since the node stops processing/confirming units until manually restarted. This satisfies the "network unable to confirm new units" bar for validity, if `isValidAddressAnyCase` is reachable from unprivileged, attacker-controlled data (e.g., addresses embedded in oscript/AA definitions, trigger data, or attestation payloads) without the same base32 pre-filtering applied by `isValidAddress`.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to identify a call site that uses `isValidAddressAnyCase` (rather than `isValidAddress`) on unsanitized network-supplied strings, and find a specific 32-character input whose `base32.decode` output has an unexpected bit-length. I was not able to fully trace all callers of `isValidAddressAnyCase` within the available indexed context (e.g., `formula/evaluation.js` references it per grep results but I could not inspect that call site's reachability constraints before running out of iterations), so the exact unauthenticated trigger path is not fully confirmed.

### Recommendation
Move the length/format validation performed inside `separateIntoCleanDataAndChecksum` and `mixChecksumIntoCleanData` inside the existing try/catch in `isChashValid()` (or wrap the whole body of `isChashValid` in try/catch and return `false` on any exception), and audit all callers of `isValidAddressAnyCase` to ensure malformed strings cannot reach unguarded c-hash decoding logic.

### Proof of Concept
Conceptually: call `chash.isChashValid(<crafted 32-char string outside the expected base32 charset but of length 32>)` directly, or via `ValidationUtils.isValidAddressAnyCase(<crafted string>)`, and observe an uncaught `Error("bad length=...")` propagate instead of a `false` return — this could not be dynamically verified since I only have static code access, not a runtime.

**Caveat:** Due to limited remaining tool iterations, I could not fully confirm which specific unauthenticated code path (e.g., formula evaluation, attestation validation) calls `isValidAddressAnyCase` with fully attacker-controlled 32-character strings without prior base32-charset filtering, nor could I empirically determine whether `thirty-two`'s `base32.decode` can actually produce a non-160-bit output for a 32-character input. This should be verified with a running Devin session with full repo/dependency access before treating this as confirmed exploitable.
