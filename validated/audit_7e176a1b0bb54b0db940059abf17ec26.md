### Title
Unauthenticated AA definition cache corruption via in-place mutation of shared unconfirmed-definition object - ([File: storage.js])

### Summary
`storage.getUnconfirmedAADefinition()` [1](#0-0)  returns the exact object stored inside `assocUnstableMessages`, obtained without cloning from `message.payload.definition`. Both `network.js` (`light/new_aa_to_watch`, `light/get_aa_state_vars`, `light/get_definition`) and internal AA-triggering code paths call this and pass the returned array straight into `aa_composer.handleTrigger()`/`evaluateAA()`, which subsequently does `delete arrDefinition[1].getters` [2](#0-1)  to consume the getters formula before evaluating the rest of the definition. Because this is the same object still referenced by `assocUnstableMessages`, the mutation is not local to one evaluation — the AA's `getters` field is permanently stripped from the shared cache entry.

### Finding Description
`getUnconfirmedAADefinition(address)` walks `assocUnstableMessages` and, on finding a `definition` message for the requested address, returns `payload.definition` directly (no `_.cloneDeep`) [1](#0-0) . This same payload object is what got inserted into `assocUnstableMessages[unit]` in `writer.js` when the unit carrying the AA-defining `definition` message was written [3](#0-2) , and it is the very definition later consumed by `insertAADefinitions()`/`evaluateAA()` for real triggers.

`aa_composer.js`'s `evaluateAA()` treats `arrDefinition` as disposable: it deletes `arrDefinition[1].getters` in place before parsing the getters formula (comment: "evaluate getters before everything else... delete... so we don't waste time on it again") [4](#0-3) . `aa_validation.js`'s `validateAADefinition` does the identical in-place `delete arrDefinition[1].getters` [5](#0-4) .

If any code path obtains the *unconfirmed* (not-yet-stable) definition via `getUnconfirmedAADefinition()` and feeds it into `handleTrigger`/`evaluateAA` or `validateAADefinition` (e.g. `network.js`'s `light/dry_run_aa`-adjacent handlers or any secondary/primary trigger dispatch that falls back to the unconfirmed definition before the AA is stable, since `aa_composer.js` also calls `storage.readAADefinition` with fallbacks to unconfirmed sources for freshly-posted AAs), the getters formula is destructively removed from the object that remains cached in `assocUnstableMessages`. Any subsequent evaluation of the same still-unconfirmed AA (e.g. another trigger arriving before the defining unit stabilizes, or `light/get_aa_state_vars`/`light/new_aa_to_watch` being called again) will see an AA definition with `getters` already missing, so getter-dependent formulas silently behave as if the AA declares no getters, changing evaluation semantics (any `$g()`-style getter calls become undefined-function errors, or complexity/getter-defined locals are absent).

This is unauthenticated-input-reachable: any unprivileged user can post a unit that defines a new AA (an AA-posted `definition` message, or a base unit `definition` message) and then immediately send a trigger to that not-yet-stable AA address, forcing two evaluations of the same cached, mutable definition object before it stabilizes and is safely re-parsed via `JSON.parse` from storage (`readAADefinition` always does a fresh `JSON.parse(rows[0].definition)` [6](#0-5) , which is unaffected — the bug is confined to the pre-stabilization window relying on `getUnconfirmedAADefinition`).

### Impact Explanation
If getters silently disappear mid-flight for an AA that is still unconfirmed, two different nodes evaluating the same trigger at different times relative to this mutation could get diverging AA outcomes for getter-dependent logic (one evaluates with getters, one without), which is a node-disagreement-on-validity/consensus risk for AA responses, and can also cause fund-affecting logic that depends on a getter (e.g., a getter computing a payout amount or fee) to fail or compute differently, leading to bounced/failed responses or incorrect payments from the AA — i.e., AA fund loss/freezing or bounce fee loss for a legitimate trigger sender.

### Likelihood Explanation
Requires a race: the same not-yet-stable AA definition object needs to be dereferenced by `getUnconfirmedAADefinition()` and passed into a getters-mutating consumer more than once before stabilization. This is plausible but timing-dependent, and I could not fully confirm within the available context that `handleTrigger`/`evaluateAA` (as opposed to only `light/*` network handlers) actually calls `getUnconfirmedAADefinition()` for the *primary trigger execution path itself* — the citations show `getUnconfirmedAADefinition` used in `network.js` light-request handlers and in `insertAADefinitions`'s existence check, not conclusively in the main trigger-dispatch code that also calls `evaluateAA`. This is a real, low-risk-of-verification limitation given index size constraints — I recommend a Devin session with full repo access to trace all callers of `storage.getUnconfirmedAADefinition` and confirm whether any of them feed the returned object directly into `evaluateAA`/`validateAADefinition` without cloning, and if the same unconfirmed AA can be triggered twice before stabilization.

### Recommendation
`storage.getUnconfirmedAADefinition()` should return `_.cloneDeep(payload.definition)` rather than the live reference, and/or `evaluateAA`/`validateAADefinition`/`validateDefinition` should operate on a cloned copy of `arrDefinition` instead of mutating the object in place with `delete arrDefinition[1].getters`, matching the "copy before mutate" pattern already used elsewhere in the formula evaluator (e.g. `assignObject`/`clearObject` in `formula/common.js`).

### Proof of Concept
Not fully constructible without confirming the exact caller chain (see Likelihood Explanation above); recommend a Devin session with full codebase access to (1) enumerate every caller of `storage.getUnconfirmedAADefinition`, (2) verify whether the object flows into `evaluateAA`/`validateAADefinition`, and (3) craft a two-unit sequence (AA definition unit + immediate trigger unit, sent twice before stabilization) to demonstrate divergent getter availability.

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}
