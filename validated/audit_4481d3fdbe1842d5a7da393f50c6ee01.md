### Title
Unbounded vote-account scan cost at epoch boundary is not limited by `MAX_ALPENGLOW_VOTE_ACCOUNTS` - ([File: runtime/src/stakes.rs, vote/src/vote_account.rs, runtime/src/bank.rs])

### Summary
`MAX_ALPENGLOW_VOTE_ACCOUNTS` only caps the *output* size returned by `VoteAccounts::clone_and_filter_for_vat`, not the *input* it must scan. Both `refresh_vote_accounts` (called every epoch via `Stakes::calculate_activated_stake`) and `VoteAccounts::clone_and_filter_for_vat` (called every epoch via `compute_new_epoch_caches_and_rewards` and `Bank::get_top_epoch_stakes`) iterate over the *entire* `vote_accounts` map cached in `StakesCache`, whose size grows with every distinct vote account ever created and never shrinks unless the account is closed to zero lamports.

### Finding Description
An unprivileged user can call `VoteProgram::initialize_account` (via a normal system+vote instruction sequence) to create arbitrarily many vote accounts. Each one that is a validly-sized, initialized vote account and has non-zero lamports is unconditionally inserted into the bank's `StakesCache` by `StakesCache::check_and_store` -> `Stakes::upsert_vote_account` [1](#0-0) , regardless of whether it has any delegated stake or meets `minimum_vote_account_balance_for_vat`. It is never evicted from the cache until it is closed to zero lamports [2](#0-1) .

Every epoch boundary, two O(V) scans (V = total number of cached vote accounts, i.e. all ever created and not closed, not limited to `MAX_ALPENGLOW_VOTE_ACCOUNTS`) occur:
1. `refresh_vote_accounts` maps over `vote_accounts.iter()` for **every** cached vote account to rebuild the next epoch's vote-account/stake snapshot [3](#0-2) .
2. `VoteAccounts::clone_and_filter_for_vat` iterates `self.vote_accounts.iter()` over the same full set before ever applying `max_vote_accounts` truncation [4](#0-3) . The `MAX_ALPENGLOW_VOTE_ACCOUNTS = 2000` cap is applied only after the full scan, via `select_nth_unstable_by`/`retain` on `entries_to_sort`, which only bounds the **output** size, not the initial O(V) filtering pass [5](#0-4) .

This is invoked from `compute_new_epoch_caches_and_rewards` and `Bank::get_top_epoch_stakes`/`update_epoch_stakes` on every epoch boundary [6](#0-5) [7](#0-6) [8](#0-7) .

No signer/authority/rent-exempt check limits the *number* of vote accounts an attacker may create system-wide — rent-exemption only bounds the cost per account, not the count. `select_nth_unstable_by` (Rust's pattern-defeating quickselect) does guarantee worst-case linear time, so the "hash-collision-adjacent pubkey" premise for super-linear blowup in the selection step specifically is not applicable; however, the unbounded linear scan over V (proportional to attacker-created accounts, not the 2000 cap) is real and unmitigated.

### Impact Explanation
Each epoch boundary, CPU/memory work for stake/vote-account processing scales linearly with the total number of vote accounts an attacker has ever created and kept funded (non-zero lamports), rather than being hard-capped at `MAX_ALPENGLOW_VOTE_ACCOUNTS`. Because this runs synchronously as part of bank epoch-boundary processing (`compute_new_epoch_caches_and_rewards` / `update_epoch_stakes`) on every validator, sufficiently large V degrades or stalls epoch-boundary block production cluster-wide, matching the "epoch-boundary halt" bounty category.

### Likelihood Explanation
Preconditions: attacker must fund and create N vote accounts (rent-exempt minimum required per `VoteStateV4::size_of()`), which is entirely permissionless and requires no delegated stake or privileged config. Feasibility scales with attacker's available SOL — cost is linear in N (no economies of scale reduce attacker cost), so the practical severity depends on how large N an attacker can realistically fund; for very large N the per-account rent cost becomes economically significant, which is the main real-world mitigating factor rather than any protocol-level bound. Repeatable each epoch since created accounts persist in `StakesCache` indefinitely.

### Recommendation
Bound the input-side cost of epoch-boundary vote-account processing, e.g.: maintain the stakes cache's vote-account set already pre-filtered/pre-bounded (evict non-qualifying accounts promptly rather than scanning them every epoch), or maintain an auxiliary sorted/bounded structure (e.g., a size-bounded top-K heap updated incrementally on `upsert_vote_account`/`add_stake`) so `clone_and_filter_for_vat` and `refresh_vote_accounts` do not need a full O(V) scan over all historically-created vote accounts every epoch.

### Proof of Concept
```rust
// runtime/tests/vote_account.rs (extend existing test file)
#[test]
fn test_clone_and_filter_for_vat_scan_cost_scales_with_total_accounts() {
    use std::time::Instant;
    let mut rng = rand::rng();

    // Baseline: only MAX_ALPENGLOW_VOTE_ACCOUNTS accounts, all qualifying.
    let baseline = new_staked_vote_accounts(
        &mut rng, MAX_ALPENGLOW_VOTE_ACCOUNTS, MAX_ALPENGLOW_VOTE_ACCOUNTS,
        None, MIN_STAKE_FOR_STAKED_ACCOUNT, MAX_STAKE_FOR_STAKED_ACCOUNT, |_| 10_000_000_000,
    );
    let start = Instant::now();
    let _ = baseline.clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, MIN_STAKE_FOR_STAKED_ACCOUNT);
    let baseline_time = start.elapsed();

    // Attacker-inflated: 50x MAX_ALPENGLOW_VOTE_ACCOUNTS non-qualifying (zero-stake or
    // below-balance) accounts mixed in with the same qualifying set, simulating
    // spam vote accounts created via VoteProgram::initialize_account.
    let inflated_total = MAX_ALPENGLOW_VOTE_ACCOUNTS * 50;
    let inflated = new_staked_vote_accounts(
        &mut rng, inflated_total, MAX_ALPENGLOW_VOTE_ACCOUNTS,
        None, MIN_STAKE_FOR_STAKED_ACCOUNT, MAX_STAKE_FOR_STAKED_ACCOUNT, |_| 10_000_000_000,
    );
    let start = Instant::now();
    let filtered = inflated.clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, MIN_STAKE_FOR_STAKED_ACCOUNT);
    let inflated_time = start.elapsed();

    assert_eq!(filtered.len(), MAX_ALPENGLOW_VOTE_ACCOUNTS);
    // FAILS current implementation: wall time should be roughly constant
    // (bounded by MAX_ALPENGLOW_VOTE_ACCOUNTS) but instead scales with
    // inflated_total (attacker-controlled input size).
    assert!(
        inflated_time.as_nanos() < baseline_time.as_nanos() * 5,
        "scan cost scaled with attacker-controlled input size: baseline={baseline_time:?}, inflated={inflated_time:?}"
    );
}
```
Expected result on current code: `inflated_time` grows roughly linearly with `inflated_total`, demonstrating that epoch-boundary vote-account processing cost is not bounded by `MAX_ALPENGLOW_VOTE_ACCOUNTS` but by the attacker-controlled total number of live vote accounts.

    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
        }

    fn update_epoch_stakes(
        &mut self,
        leader_schedule_epoch: Epoch,
        prefiltered_distribution_vote_accounts: Option<VoteAccounts>,

        // update epoch_stakes cache
        //  if my parent didn't populate for this staker's epoch, we've
        //  crossed a boundary
        if !self.epoch_stakes.contains_key(&leader_schedule_epoch) {
            self.epoch_stakes.retain(|&epoch, _| {
                // Note the greater-than-or-equal (and the `- 1`) is needed here
                // to ensure we retain the oldest epoch, if that epoch is 0.
                epoch >= leader_schedule_epoch.saturating_sub(MAX_LEADER_SCHEDULE_STAKES - 1)
            });

            // has already produced the VAT-filtered vote-account snapshot;
            // reuse it here instead of re-cloning and re-filtering the
            // `stakes_cache`. Other callers (same-epoch refresh, warps)
            // fall back to `get_top_epoch_stakes`.
            let stakes = match prefiltered_distribution_vote_accounts {
                Some(prefiltered) => Stakes::new(prefiltered, self.epoch()),
                None => self.get_top_epoch_stakes(),
            };
