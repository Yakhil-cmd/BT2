Based on the investigation, the closest analog to CVE-2025-56361's pattern (a state-invariant assertion reachable via a legitimate-looking operation sequence, causing the process to abort/crash) is in `ocore`'s AA (Autonomous Agent) execution engine, specifically the storage-size accounting invariant in `aa_composer.js`.

### Title
Reachable assertion (`throw Error`) in AA storage-size accounting crashes the node - (File: aa_composer.js)

### Summary
The AA trigger-execution engine maintains a running `storage_size` counter for each AA address and enforces the invariant that after applying state-variable deltas from a trigger, the resulting size cannot be negative. This invariant is enforced with a hard `throw Error(...)` rather than a soft validation failure/bounce, mirroring the CVE's pattern where `minLevel < currentLevel` is enforced via an unconditional assert instead of a recoverable error path.

### Finding Description
`updateStorageSize()` in `aa_composer.js` computes `delta_storage_size` from state-variable writes performed during trigger handling, then computes: [1](#0-0) 
```
console.log('storage size = ' + storage_size + ' + ' + delta_storage_size + ', byte_balance = ' + byte_balance);
var new_storage_size = storage_size + delta_storage_size;
if (new_storage_size < 0)
    throw Error("storage size would become negative: " + new_storage_size);
```
Unlike most other invariant checks in this function which return a soft error via `cb(...)` (which triggers `bounce()`), this specific check uses an unconditional `throw`. Because `updateStorageSize` is called from inside the asynchronous `finish()` chain of `handleTrigger()` (used for every AA invocation triggered by an unprivileged user's unit), any state that drives `storage_size + delta_storage_size` negative crashes the enclosing async callback with an uncaught exception, propagating up through `handleTrigger`, `handlePrimaryAATrigger`/`handleSecondaryTriggers`, and ultimately `writer.saveJoint`'s stabilization/AA-trigger-execution flow, which itself throws similar unguarded errors elsewhere in the batch-write and post-stabilization code: [2](#0-1) 

This is structurally identical to the CVE class: a stateful counter (`currentLevel`/`minLevel` in the Matter case, `storage_size` here) that is supposed to only move in valid directions, hardened with a fatal assertion instead of a recoverable check, reachable by supplying attacker-controlled input (state var writes/deletes via AA formulas triggered by payments) that a downstream secondary trigger or state-var deletion sequence can violate.

### Impact Explanation
A crash inside `writer.saveJoint`'s AA-trigger execution path (`aa_composer.handleAATriggers()` is invoked synchronously as part of unit stabilization, see `writer.js:724-727`) halts the entire node process while it is processing newly stabilized units. Because this occurs during stabilization (not just during pre-acceptance validation), a crash here can desynchronize different node builds/versions or halt the affected node's ability to progress the DAG, i.e., "a network unable to confirm new units" for that node, and it is triggered by ordinary AA/trigger traffic, not a malicious peer or hub.

### Likelihood Explanation
Reaching this exact line requires an attacker to define an AA (or reuse an existing complex AA) whose formulas can construct a sequence of state variable insert/update/delete operations across primary and secondary triggers such that `getValueSize` deltas summed against the previously tracked `storage_size` produce a negative total — for example by exploiting `updateOriginalOldValues()`/`state.original_old_value` bookkeeping for secondary AA calls combined with self-referential or bounced calls. This requires careful crafting of an AA definition and a triggering unit, both of which are fully within reach of an unprivileged AA author + trigger sender, with no special network/hub position needed. Exploitability is not proven here since it depends on the achievability of a negative delta sum in practice, but the code path itself is directly reachable.

### Recommendation
Replace the `throw Error("storage size would become negative...")` with a recoverable failure path, e.g., `return cb("storage size would become negative: " + new_storage_size)`, so that the offending trigger execution is bounced instead of crashing the process, consistent with the surrounding checks (e.g., the `byte_balance < new_storage_size` check on the next line already does this correctly).

### Proof of Concept
A concrete PoC requires devising a specific oscript AA whose formula performs enough state-variable deletions across chained secondary AA calls (using `updateOriginalOldValues()`'s `original_old_value` tracking) to drive the computed `delta_storage_size` more negative than the currently tracked `storage_size` for the address. Constructing this precisely (down to `getValueSize` byte counts) requires live experimentation against the AA formula evaluator, which is out of scope for static analysis; the report above documents the exact unguarded invariant and reachable call path rather than a verified end-to-end exploit.
