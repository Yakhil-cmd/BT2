### Title
Missing bounds validation on `UpdateCommissionBps` vote instruction allows commission > 100% - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `EmergencyProposer` bug class is: a numeric configuration parameter (`quorum`, `minimumWaitTime`) is written to state without checking it against a sane bound (token supply / time cap), which can silently corrupt downstream logic that assumes the parameter is within range. The Agave analog is `update_commission_bps`, which writes an unbounded `u16` commission value into vote account state without checking that it does not exceed `10_000` basis points (100%).

### Finding Description
`VoteInstruction::UpdateCommissionBps` is dispatched from `programs/vote/src/vote_processor.rs` to `vote_state::update_commission_bps`: [1](#0-0) 

The handler itself performs a feature-gate check and a signer check, but never validates the numeric range of `commission_bps` before writing it into the vote account state: [2](#0-1) 

Unlike `update_commission` (legacy `u8` commission, semantically 0–100), `commission_bps` is a `u16` (range 0–65535) intended to represent 0–10000 basis points (0%–100%). There is no `if commission_bps > 10_000 { return Err(...) }` guard anywhere in this path — the value is written directly via `vote_state.set_inflation_rewards_commission_bps(commission_bps)` / `set_block_revenue_commission_bps(commission_bps)`.

This is only gated by requiring the vote account's authorized withdrawer to sign — i.e., it is reachable by any account that holds withdraw authority over a vote account, which is an ordinary transaction sender from the runtime's perspective (no special validator/leader privilege is required to submit this instruction).

### Impact Explanation
`commission_bps` is later consumed during epoch reward distribution (`runtime/src/inflation_rewards/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`) to split rewards between the vote account and its delegators. Reward-splitting arithmetic of the form `commission = rewards * commission_bps / 10_000` assumes `commission_bps <= 10_000`. If `commission_bps` can be set arbitrarily up to `65535` (over 6x the intended maximum), the computed "commission" can exceed the total reward amount, which can:
- corrupt stake/vote reward accounting (delegators being shorted or vote account being over/under credited), matching the "stake or reward corruption" impact category, or
- trigger an arithmetic underflow/panic in reward-distribution code if a subtraction of `rewards - commission` is not saturating/checked in all paths, which — because reward distribution runs identically and deterministically on every validator during epoch boundary processing — would either diverge only if code paths differ across validators, or (more likely) cause every validator to panic identically at the same epoch boundary, which is a cluster-wide halt.

I was not able to fully verify from the available index contents whether every consumer of `commission_bps` in `runtime/src/inflation_rewards/mod.rs` and `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` uses saturating arithmetic or unwraps/checked arithmetic that could panic; this determines whether the concrete outcome is "silent reward corruption" (very likely) or "validator panic/halt" (possible, unconfirmed). This should be verified directly against those files, which is beyond what the current index surfaces.

### Likelihood Explanation
Reaching this requires only:
1. Owning (or being the authorized withdrawer of) any vote account.
2. Submitting a single `VoteInstruction::UpdateCommissionBps` instruction with `commission_bps > 10_000`.

There is no `sudo`/admin gate — the feature (`commission_rate_in_basis_points` + `delay_commission_updates`) merely enables the instruction, and the withdrawer signature check is the only access-control gate, which is a normal, expected signer for this instruction type. This makes it trivially reachable by any validator operator who controls their own vote account's withdraw authority — no attacker collusion or elevated privilege needed. Whether this is intentionally exploited or an operator error (mirroring the "misconfiguration bricking" theme from the report) does not change reachability.

### Recommendation
Add an explicit bounds check in `update_commission_bps` (and confirm the same principle for `update_commission`) rejecting any `commission_bps > 10_000` with `InstructionError::InvalidInstructionData` before mutating vote state:
```rust
if commission_bps > 10_000 {
    return Err(InstructionError::InvalidInstructionData);
}
```
Additionally, audit all downstream consumers in `runtime/src/inflation_rewards/mod.rs` and `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` to ensure `rewards.saturating_sub(commission)` (or equivalent checked arithmetic) is used defensively even after adding input validation, to prevent any future regression from becoming a panic/halt.

### Proof of Concept
1. Create/own a vote account with `commission_rate_in_basis_points` and `delay_commission_updates` features active.
2. As the account's authorized withdrawer, submit:
   ```rust
   VoteInstruction::UpdateCommissionBps {
       commission_bps: 65535, // >> 10_000 (100%)
       kind: CommissionKind::InflationRewards,
   }
   ```
3. Observe (per `update_commission_bps` in `programs/vote/src/vote_state/mod.rs:828-859`) that the instruction succeeds and persists `commission_bps = 65535` into `VoteStateV4` with no error, confirmed by the existing test harness pattern in `test_update_commission_bps` (`programs/vote/src/vote_state/mod.rs:1830+`) which never exercises an out-of-range value.
4. At the next epoch boundary, reward distribution for that vote account's delegators will compute commission using this out-of-range value, producing incorrect (over 100%) commission — a corrupted split between validator and delegator rewards. [2](#0-1)

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
