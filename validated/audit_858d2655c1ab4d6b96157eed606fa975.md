### Title
Stack-scoped API token can read CI/build status of any stack via `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the base controller's stack-resolution method with a version that ignores the `ApiClient`'s stack scope, letting a token that was only ever authorised for a single stack read the CI/build status of *any* stack in the installation.

### Finding Description
Shipit's API authorization model binds an `ApiClient` token to (at most) one stack: `ApiClient#stack_id`. The generic scoping is enforced in `Shipit::Api::BaseController`: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]`/`params[:id]` only from that restricted set. `require_permission` (used with `:read, :stack`) only checks that the string `"read:stack"` is present in `ApiClient#permissions` — it never checks which stack the id belongs to: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass the scoped `stacks` helper entirely and resolve directly against the global `Stack` relation: [3](#0-2) 

This is the same bug class as the external report's RocketPool analog: a value the system *authorizes* (the token's bound `stack_id`) is decoupled from the value the code actually *acts on* (`params[:stack_id]` resolved against all stacks). Compare with `Api::StacksController`, which correctly resolves through the scoped helper: [4](#0-3) 

CCMenu tokens are specifically minted as stack-scoped, read-only clients through `CCMenuUrlController`: [5](#0-4) 

The equality that should hold is: `token.stack_id == stack_id acted on by CCMenuController#show`. Before the request, this equality is guaranteed by design (the token is scoped to one stack at creation). After the request, `Api::CCMenuController#stack` breaks it by ignoring `current_api_client.stack_id` and honoring any `params[:stack_id]` supplied by the caller.

### Impact Explanation
Any holder of a valid, stack-scoped `read:stack` CCMenu token (which by design is meant to expose only that single stack's CI status, e.g. embedded in a CI-status widget URL) can enumerate other stacks and read their deploy/build state (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) by simply changing `stack_id` in the request. This is an unauthorized read of stack state across the intended trust boundary, matching the "High: unauthenticated/out-of-scope read of stack state" impact category — a token minted for stack A discloses build status of stack B without ever being granted that scope.

### Likelihood Explanation
Exploitation requires only a previously-issued, low-privilege, stack-scoped CCMenu token (no repository write access, no session, no privileged account) and knowledge/guessing of another stack's `to_param`. Since `to_param` values are typically derived from repository/branch/environment names (not secret), and CCMenu URLs are often shared/embedded in dashboards, this is easily reachable by any party holding one such token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` helper inherited from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the stack-scope binding on the `ApiClient` is enforced consistently across all API controllers.

### Proof of Concept
1. As a legitimate user, visit a stack page to have Shipit mint a stack-scoped CCMenu token (`CCMenuUrlController#fetch` creates an `ApiClient` with `permissions: %w[read:stack]` and `stack: <stack A>`).
2. Extract the `token` query parameter from the returned `ccmenu_url`.
3. Call `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` for a different stack B that the token was never scoped to.
4. `Api::CCMenuController#authenticate_api_client` authenticates the token; `require_permission :read, :stack` passes because the token has the `read:stack` permission string; `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against stack B directly, bypassing the `current_api_client.stack_id` restriction, and returns stack B's CI status XML.
