### Title
Pool funds are permanently locked if a single vault's mint freezes/blocks transfers, because `withdraw` requires both token legs to succeed atomically - ([File: programs/cp-swap/src/instructions/withdraw.rs])

### Summary
`withdraw` unconditionally transfers **both** `token_0` and `token_1` out of the pool vaults in the same instruction. There is no mechanism to withdraw a single side, and no admin/emergency path to recover funds from a vault whose token account has been frozen or whose mint has become non-transferable. If either vault's SPL/Token-2022 mint has a freeze authority (a native field of every SPL/Token-2022 mint, not an "extension" that `is_supported_mint` screens for) and that authority freezes the pool's own vault token account, every `withdraw` call for that pool reverts forever, because Solana instructions are atomic and the `transfer_checked` CPI to the frozen account will always fail.

### Finding Description
In `withdraw`, both transfers must succeed for the instruction to complete: [1](#0-0) 

Both transfers go through `transfer_from_pool_vault_to_user`, which performs a plain `token_2022::transfer_checked` CPI with no fallback or partial-success handling: [2](#0-1) 

The pool's mint-acceptance check, `is_supported_mint`, only restricts which Token-2022 *extensions* are allowed (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) unless the mint is explicitly admin-whitelisted via `SupportMintAssociated`: [3](#0-2) 

Crucially, this check says nothing about a mint's native `freeze_authority`, which exists on both legacy SPL Token and Token-2022 mints regardless of extensions. `initialize` never validates or rejects mints that carry a freeze authority: [4](#0-3) 

There is also no admin instruction anywhere in the program (`programs/cp-swap/src/instructions/admin/`) to thaw a vault, sweep a frozen vault, migrate liquidity, or otherwise allow single-sided/partial withdrawal — the admin module only exposes config/fee/permission management (`create_config`, `update_config`, `collect_protocol_fee`, `collect_fund_fee`, `collect_excess_lamports`, permission PDA management), none of which touch frozen accounts:


If the freeze authority of `token_0_mint` (or `token_1_mint`) freezes the pool's own `token_0_vault` (or `token_1_vault`) token account after the pool is created and has liquidity, every subsequent `withdraw` call (and `swap_base_input`/`swap_base_output`, which also transfer from vaults) reverts with a token-program `AccountFrozen` error, because the frozen leg's `transfer_checked` CPI fails and Anchor/Solana atomicity rolls back the whole transaction — including the otherwise-successful transfer and burn of the healthy leg.

### Impact Explanation
Once one vault is frozen, LPs cannot withdraw **either** token from the pool — not just the frozen one — because `withdraw` is atomic and requires both transfers to succeed. All liquidity in the pool (both `token_0` and `token_1`, contributed by every LP) becomes permanently frozen with no recovery path in the contract, satisfying the "permanent freezing of user or LP funds" criterion. This is reachable by any unprivileged user who deposits into or swaps against a pool created with a freezable mint, and requires no privileged protocol signer — the freeze action is performed by the external token issuer (mint freeze authority), exactly analogous to the cbETH blacklist scenario in the source report.

### Likelihood Explanation
Likelihood depends on the tokens listed: any pool created with a token whose mint retains an unrevoked/non-null `freeze_authority` (common for many SPL tokens, stablecoins, and Token-2022 tokens) is exposed. `initialize` performs no check on `freeze_authority` for either mint, and `is_supported_mint` only restricts Token-2022 extensions, not this native mint attribute, so nothing in the current instructions prevents such a pool from being created and used normally until the freeze event occurs.

### Recommendation
- Reject mints with a non-null `freeze_authority` in `initialize`/`initialize_with_permission`, or at minimum require the deployer to explicitly acknowledge the risk (e.g., via a separate governance-approved list, similar to `SupportMintAssociated`).
- Add an admin/emergency instruction to handle a frozen vault: allow withdrawing the non-frozen leg independently (single-sided emergency withdraw) instead of requiring both `transfer_checked` calls to succeed atomically, so a freeze on one side does not lock the other side's funds.

### Proof of Concept
1. Create mint `M0` with a freeze authority controlled by an external party and a normal mint `M1`. Initialize a cp-swap pool with `token_0_mint = M0`, `token_1_mint = M1` via `initialize` — this succeeds since `is_supported_mint` and `initialize` do not check `freeze_authority`. [5](#0-4) 
2. LPs deposit liquidity normally; `token_0_vault` accumulates `M0` balance.
3. The freeze authority of `M0` calls the SPL `FreezeAccount` instruction on `pool_state.token_0_vault`.
4. Any LP calls `withdraw`; the second CPI transferring `token_0` out of the frozen vault fails with `AccountFrozen`, reverting the whole instruction — including the LP-burn and the `token_1` transfer that would otherwise have succeeded. [6](#0-5) 
5. No instruction in the program can unfreeze the vault or allow single-sided withdrawal, so all LP funds in both `token_0_vault` and `token_1_vault` remain locked indefinitely.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
