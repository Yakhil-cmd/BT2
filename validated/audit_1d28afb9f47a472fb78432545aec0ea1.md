### Title
Signature verification is bound to an attacker-chosen organization while webhook handlers act on a different, attacker-chosen repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the `X-Hub-Signature` against using a field taken directly from the *unverified* JSON body, while the handlers that actually mutate state (create commit statuses, sync branches, archive/unarchive review stacks, add team memberships) select the *target repository/stack* using a different, independent field from that same unverified body. Because these two lookups are never cross-checked, an attacker who can satisfy (or who does not need to satisfy, because it is blank) the signature of any one configured organization can forge webhook payloads that write to any other organization's repositories/stacks.

### Finding Description
`WebhooksController#verify_signature` computes the organization used for HMAC validation purely from the raw request body, before any authentication has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both are attacker-controlled JSON fields, not covered by any signature at the point they are read. This value is passed into `Shipit.github(organization: repository_owner)`, which looks up that organization's config (`app_id`, `webhook_secret`, etc.) and constructs/reuses a `GitHubApp` instance for it: [3](#0-2) 

The signature is then checked with that organization's secret: [4](#0-3) 

Critically, `verify_webhook_signature` returns `true` unconditionally if `webhook_secret` is blank for that organization (`return true unless webhook_secret`). The example multi-org secrets template shows this is an explicitly supported configuration (`webhook_secret: # nil`): [5](#0-4) 

Meanwhile, every webhook handler resolves the *actual* repository/stack to act on from a completely separate JSON field, `repository.full_name`, with no relationship enforced to `repository_owner`/`organization.login` used above: [6](#0-5) 

For example, the push handler triggers a GitHub sync on whatever stack matches `repository.full_name`: [7](#0-6) 

and the status handler writes a `Status` record for any commit matching the attacker-supplied `sha`, entirely independent of which org's secret was checked: [8](#0-7) 

`Status` creation can trigger continuous deployment and merge-request processing: [9](#0-8) 

This is the exact bug-class analog described in the report: the "price" (here, cryptographic trust) is fetched from one part of the system state (`repository_owner`) while the actual action is executed against a different, unchecked part of state (`repository.full_name`/commit `sha`). The equality that should hold — "organization whose secret authenticated the request == organization that owns the repository being written to" — is broken, because both sides are independently attacker-supplied and only one of them is used for cryptographic verification.

### Impact Explanation
In any Shipit instance configured with more than one GitHub organization (the documented multi-org config format in `config/secrets.development.shopify.yml`), if even one configured organization has no `webhook_secret` set (explicitly supported, returns `verified = true`) or if the attacker otherwise knows/derives one organization's secret, they can craft a webhook whose `repository.owner.login`/`organization.login` points at that low-security org (satisfying `verify_signature`) while `repository.full_name` and `sha` point at a stack belonging to a *different, properly-secured* organization. This allows an unauthenticated actor to:
- Forge commit statuses (`status` event) for arbitrary SHAs on arbitrary tracked repositories, which can trigger continuous deployment (`Status#schedule_continuous_delivery`) or bypass CI-based merge/deploy gating — an unauthorized deploy/merge condition.
- Trigger `sync_github`/`GithubSyncJob` on arbitrary stacks.
- Manipulate review-stack lifecycle (archive/unarchive) and team memberships for organizations they were never authenticated against.

This crosses the "unauthorized deploy" / "cross-repository writes" boundary defined as Critical impact.

### Likelihood Explanation
Likelihood depends on the deployment having multiple GitHub organizations configured, and at least one of them either omitting `webhook_secret` or having a weak/known secret — a configuration explicitly documented and supported by the engine (see `TOP_LEVEL_GH_KEYS`/`github_app_config` in `lib/shipit.rb` and the sample multi-org secrets file). No credentials, session, or prior access are required; a single unauthenticated HTTP POST to the public webhook endpoint suffices.

### Recommendation
Bind the authenticated organization to the resource being mutated: after `verify_signature` succeeds, validate that the organization used for signature verification matches the owner segment of `repository.full_name` (and of any `sha`/stack lookups performed downstream) before dispatching to handlers. Alternatively, require every configured organization to have a non-blank `webhook_secret`, and reject payloads where `repository.owner.login` does not match the owner portion of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations: `weak-org` (no `webhook_secret`) and `victim-org` (secured), each with tracked repositories/stacks — as supported by `config/secrets.development.shopify.yml`.
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "weak-org" },
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<sha of a tracked commit in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` header value can even match — but since `weak-org` has no configured `webhook_secret`, `verify_webhook_signature` short-circuits to `true` (`lib/shipit/github_app.rb:76-83`).
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (resolved via `victim-org/victim-repo` through `repository_name`/`Repository.from_github_repo_name`) and creates a forged `success` status, potentially unblocking continuous deployment or merge requirements on `victim-org`'s stack, despite the request never being authenticated against `victim-org`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
