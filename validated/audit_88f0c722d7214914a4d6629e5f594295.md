Confirmed: `Commit#create_status_from_github!` at [1](#0-0)  mutates a commit's status without any repository-scoping check, and `StatusHandler` never calls `stacks` and never requires `repository` in its params schema.

### Title
Cross-tenant commit status forgery via unscoped `StatusHandler#process` bypassing repository binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler` is the only sibling of `Handler` that never calls `stacks`/`repository_name` and never declares `requires :repository` in its `params` block, so it looks up commits globally by `Commit.where(sha: params.sha)` across the entire installation. In a multi-org Shipit deployment (`config/secrets.yml` `github:` keyed by organization, as documented in `docs/setup.md`), any org whose webhook secret validates the raw payload can mutate the GitHub status of any commit row belonging to any other org's stack, as long as it knows/guesses the sha.

### Finding Description
The broken binding: `repository_owner` used by `WebhooksController#verify_signature` to select the signing `GitHubApp` (`Shipit.github(organization: repository_owner)`) should equal the repository that owns the `Commit` row being mutated by `commit.create_status_from_github!`. These are never compared.

Path:
1. `WebhooksController#create` parses the raw JSON body and dispatches to handlers for the `status` event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`).
2. `verify_signature` picks the `GitHubApp` purely from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies HMAC-SHA1 against that org's `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-49, 59-62`). This proves only that *some* registered org's secret matches — it does not bind the payload to a specific repository's data.
3. `StatusHandler.params` only requires `sha`, `state`, and optional fields; it never requires `repository` (`app/models/shipit/webhooks/handlers/status_handler.rb:7-18`), unlike every other handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `LabelCapturingHandler`, `AssignedHandler`, `ReopenedHandler`) which all `requires :repository do requires :full_name, String end`.
4. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) — a global, unscoped lookup across the whole `commits` table, never calling the parent class's `stacks`/`repository_name` helpers (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that every sibling handler relies on to scope to `Repository.from_github_repo_name(repository_name)`.
5. `Commit#create_status_from_github!` performs `add_status { statuses.replicate_from_github!(stack_id, github_status) }` (`app/models/shipit/commit.rb:165-169`) with no check that the calling org/repository matches `commit.stack.repository`.

Exploit: an attacker who legitimately administers their own org's Shipit GitHub App integration (and thus knows that org's `webhook_secret`) sends `POST /webhooks` with header `X-Github-Event: status` and a body such as `{"sha": "<victim sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}}}`. `verify_signature` validates successfully against `attacker-org`'s secret. `StatusHandler` then updates the status of any `Commit` row anywhere in the database whose `sha` matches, regardless of which org/repository it actually belongs to.

Existing guards do not stop this: `verify_signature` only authenticates *a* legitimate sender, not *the* sender for the target repository; `ExplicitParameters` enforces types but StatusHandler's schema has no `repository` requirement to bind against; `Handler#stacks`/`repository_name` are simply never invoked by `StatusHandler`.

### Impact Explanation
An attacker with control of one legitimately-configured org's webhook signing (any tenant sharing this Shipit instance) can inject arbitrary CI/status states (`success`, `failure`, `pending`, with attacker-controlled `description`/`target_url`/`context`) onto commits belonging to unrelated repositories/stacks. Since `Commit#create_status_from_github!` feeds into `deployable?`/`blocked?` and can trigger `stack.schedule_merges` when the new status is `pending` or `success` (`app/models/shipit/commit.rb:379-384`), a forged `success` status on a victim commit could make it appear deployable or trigger auto-merge behavior for that stack, i.e., an unauthorized deploy/merge trigger for a repository the attacker does not own. This matches the Critical category: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires the target Shipit installation to run the multi-organization config (`github:` keyed by org, as in `docs/setup.md:182-209`); a single-org deployment only has one `webhook_secret`, making this equivalent to a legitimate call, though it still shows global commit lookup is a design flaw. In the multi-tenant case, the attacker only needs to be a legitimate admin/maintainer of one onboarded org (unprivileged with respect to the victim org) and a target sha, which is generally public (visible on GitHub commit/PR pages, CI logs, or Shipit's own commit listing). No secrets from the victim org are needed. The request is trivially repeatable against any sha.

### Recommendation
Require `repository.full_name` in `StatusHandler.params` (mirroring the other handlers) and scope the commit lookup through `stacks`/`Repository.from_github_repo_name(repository_name)` before matching by sha, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))`, so a status webhook can only mutate commits belonging to the repository that was actually authenticated for that request.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, extend `test/models/commits_test.rb` or the controller test):
1. Configure two orgs (`OrgOne`, `OrgTwo`) as in `test/dummy/config/secrets_double_github_app.yml`, each with its own stack/repository (`OrgOne/repo`, `OrgTwo/repo`) and a `Commit` fixture belonging to `OrgTwo`'s stack with a known `sha`.
2. Stub/compute a valid HMAC signature using `OrgOne`'s `webhook_secret` only.
3. POST to `/webhooks` with `X-Github-Event: status`, signature header set to the `OrgOne`-signed value, and body `{"sha": "<OrgTwo commit sha>", "state": "success", "repository": {"owner": {"login": "OrgOne"}}}` (no `full_name` for the target repo at all).
4. Assert response is `200 OK` (not `422`).
5. Reload the `OrgTwo` commit and assert `commit.statuses.last.state == "success"` — i.e., assert the left-hand side (`repository_owner` authenticated = `"OrgOne"`) does not equal the right-hand side (`commit.stack.repository.owner` = `"OrgTwo"`), yet the mutation still occurred.
