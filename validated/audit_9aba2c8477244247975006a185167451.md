### Title
Unbounded in-memory buffering of subprocess stdout/stderr in `runWithStdin` allows attacker-inflated git output to OOM the sidecar - (File: pkg/cmd/cmd.go)

### Summary
`runWithStdin` in `pkg/cmd/cmd.go` captures all subprocess stdout/stderr into plain `bytes.Buffer` objects with no size cap, and on error it re-embeds the full captured content into a `fmt.Errorf(...%q...)` string. Every git operation that git-sync performs (fetch, checkout, submodule update, etc.) goes through this function, so an attacker who controls the ref/content set that git-sync fetches (via ordinary push access) can inflate the volume of ref names, submodules, or verbose git chatter to grow these buffers without bound.

### Finding Description
`runWithStdin` wires `cmd.Stdout`/`cmd.Stderr` directly to `bytes.NewBuffer(nil)` instances with no `io.LimitReader`, streaming cap, or max-size guard: [1](#0-0) 

The captured buffers are then fully materialized as strings and, on any command error (including context deadline exceeded), embedded verbatim into the returned error via `%q`, which duplicates the memory footprint again: [2](#0-1) 

All git subprocess invocations by git-sync (fetch, checkout, submodule sync/update, `git show-ref`, etc.) route through `Runner.Run` / `Runner.RunWithStdin`, which forward directly to `runWithStdin`: [3](#0-2) 

An attacker with ordinary push access to the synced repository controls repo content and ref topology (branch/tag names, number of refs, `.gitmodules` entries, commit graph shape). This lets them inflate the volume of output that git itself emits for routine operations (e.g., a very large number of refs increases per-ref lines during fetch/show-ref processing; a large submodule fan-out multiplies per-submodule status/update output). Because none of that output is capped, streamed to disk, or discarded, the in-process buffers grow proportionally to attacker-supplied ref/content volume across repeated sync cycles, with no upper bound enforced in code.

The `exechook.go` path (`Exechook.Do` calling `h.cmdrunner.Run`) is a separate, operator-configured command and is not itself attacker-controlled, so the exploit-relevant path is the git subprocess calls made by the sync engine (in `main.go`) rather than the hook command itself; the attacker's leverage is over the *inputs* those git commands process (refs/content), not over the command line.

### Impact Explanation
Unbounded memory growth per sync cycle for command output can exhaust sidecar memory and trigger an OOM kill by the kubelet, matching the "OOM kill: denial of updates" impact class — the git-sync container is killed and restarted, disrupting continuous synchronization to consumers of the synced worktree until git-sync recovers (and could recur every cycle if the offending refs/content remain in the repo).

### Likelihood Explanation
- No non-default flags are required; the vulnerable code path (`runWithStdin`) is used for every git invocation regardless of configuration.
- The attacker precondition is push access to the source repo/refs that git-sync polls — this is within the stated unprivileged threat model (repo content/ref control).
- Feasibility is bounded by how much ref/content volume the attacker's own git hosting will accept and by memory available to the sidecar; producing gigabytes of output typically requires a correspondingly large number of refs/objects, which is a real but non-trivial amount of attacker-side effort and repeated sync cycles, not a single crafted request.
- Repeatable: since it is a structural lack of bounding in code (no cap, no streaming, no `io.LimitReader`), it will reproduce deterministically whenever output volume is large enough, independent of specific ref names.

### Recommendation
Bound subprocess output capture in `runWithStdin`:
- Wrap `cmd.Stdout`/`cmd.Stderr` with a size-limited writer (e.g., a custom `io.Writer` that truncates after N MB, or `io.LimitReader`/`io.MultiWriter` to a capped buffer) and record truncation in the returned strings.
- Avoid re-embedding full stdout/stderr into error messages via `%q`; truncate before formatting in the `fmt.Errorf` calls at lines 86 and 89.
- Consider streaming very large expected outputs (e.g., `git fetch` progress) to a bounded ring buffer or discarding progress/verbose output entirely unless a debug flag is set.

### Proof of Concept
Unit-test approach targeting `runWithStdin` directly (add to `pkg/cmd/cmd_test.go`):
```go
func TestRunWithStdinUnboundedOutput(t *testing.T) {
    // A command that emits a large but bounded amount of data to simulate
    // attacker-inflated git output (e.g., huge ref listing / verbose fetch).
    r := NewRunner(testLogger)
    stdout, _, err := r.Run(context.Background(), "", nil,
        "bash", "-c", "yes X | head -c 2000000000") // ~2GB of output
    if err != nil {
        t.Fatalf("unexpected error: %v", err)
    }
    if len(stdout) < 1_000_000_000 {
        t.Fatalf("expected buffer to have captured >1GB, got %d bytes", len(stdout))
    }
    // Assert: process RSS grew unbounded proportional to output size,
    // demonstrating no cap exists in runWithStdin's bytes.Buffer usage.
}
```
Expected result: the buffer grows to match the full output size (no truncation), and memory profiling (`runtime.MemStats` before/after) shows heap growth proportional to `stdout` length, confirming the absence of any bound in `runWithStdin` (pkg/cmd/cmd.go:74-78).
