### Title
Webhook signature verification is keyed on `repository.owner.login`, but write actions (push sync, commit status) trust an unrelated `repository.full_name` / commit `sha` field, allowing signature-check bypass for arbitrary repositories - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to check the HMAC against using `repository_owner`, extracted from `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's `webhook_secret` is blank [3](#0-2) , and a blank `webhook_secret` is an explicitly documented, supported configuration (`webhook_secret: # nil`) both in `docs/setup.md` and in the multi-org example secrets files [4](#0-3) . However, the field that actually drives what gets written to the database - `Handler#repository_name` (`payload.dig('repository','full_name')`) for stack/push resolution [5](#0-4) , or the raw commit `sha` for status updates [6](#0-5)  - is never cross-checked against `repository.owner.login`, the field the signature check was actually performed against.

### Finding Description
The binding that should hold is: **the organization whose signature validated the request == the organization/repository that the handler mutates**. In this engine that equality is never enforced.

1. `verify_signature` reads `repository_owner` solely from `params.dig('repository','owner','login')` (or `params.dig('organization','login')`) and uses it to pick a `GitHubApp` config via `Shipit.github(organization: repository_owner)` [7](#0-6) .
2. `GitHubApp#verify_webhook_signature` trivially returns `true` when that particular organization's `webhook_secret` is not configured [3](#0-2) . This is a first-class, documented deployment mode ("Webhook secret (optional)") for both single-org and multi-org (`Shipit.github_app_config`) setups [8](#0-7) .
3. Once `verify_signature` passes (trivially, for the org with the blank secret), the *entire raw JSON body* — including a `repository.full_name` or `sha` field that has no required relationship to `repository.owner.login` — is dispatched to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [9](#0-8) .
4. `Handler#stacks` resolves the target Stack purely from `payload.dig('repository','full_name')` [5](#0-4) , a value entirely independent of `repository.owner.login`. `PushHandler#process` then calls `stack.sync_github` on whatever stacks match that `full_name` [10](#0-9) . `StatusHandler#process` is even less scoped — it matches `Commit.where(sha: params.sha)` with **no repository scoping at all** [6](#0-5) , so it can update the CI status of a commit belonging to any stack/repository configured on the entire Shipit instance.

Consequently, on a multi-organization deployment (`docs/setup.md`, "Using Multiple Github Applications" section) where operators are told `webhook_secret` is optional per-org, if **any one** configured organization omits its `webhook_secret`, an unauthenticated internet client can send a POST to `/webhooks` with `repository.owner.login` set to that unsecured org (to sail through `verify_signature`) while setting `repository.full_name` / `sha` to reference a completely different, secured organization's stack or commit. The equality the code implicitly assumes — `organization that authenticated == repository that is written` — does not hold, and nothing enforces it.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. Concrete exploitation paths:
- **Unauthorized deploy gating bypass**: `StatusHandler` lets an unauthenticated attacker inject an arbitrary GitHub commit-status (e.g., `state: success`) for any commit `sha` in the system via `commit.create_status_from_github!`, regardless of which org's app is actually installed on that commit's real repository. Since Shipit stacks commonly gate deploys on green CI/commit status, this can make an otherwise-unshippable commit appear deployable, enabling an **unauthorized deploy** by a legitimate but lower-privileged user, or masking a compromised/failing build as safe.
- **Cross-repository push confusion**: `PushHandler` can trigger `stack.sync_github` and downstream deploy-eligibility recalculation for a stack in an organization the forged event never actually claims signature authority over.

This satisfies the Critical impact bar ("an unauthorized deploy, rollback or merge") from a purely unauthenticated network position, with no session, `ApiClient` token, GitHub App private key, or webhook secret required — the attacker only needs knowledge (from the documented, common configuration convention) that at least one org on the instance runs with a blank `webhook_secret`.

### Likelihood Explanation
Moderate-to-high. It requires the operator to have configured multiple GitHub Apps (a documented, supported feature) with at least one organization's `webhook_secret` left blank — which the project's own example/dummy secrets files demonstrate as an accepted pattern (`webhook_secret: # nil`) [4](#0-3) . No credentials, tokens, or GitHub write access are needed by the attacker; the `/webhooks` endpoint is publicly reachable and only distinguishes organizations by attacker-controlled JSON fields.

### Recommendation
Bind the two fields together instead of trusting them independently:
- After `verify_signature` succeeds, re-derive/require the acted-upon repository's owner from the same trusted context used for signature selection, and reject the request if `repository.full_name`'s owner segment does not match the `repository_owner` that was used to select the webhook secret.
- In `StatusHandler`, scope the `Commit` lookup by the repository resolved from the verified organization (i.e., reuse `Handler#stacks`/`repository_name`) rather than a bare, cross-repository `Commit.where(sha:)`.
- Consider disallowing (or at least warning loudly and requiring explicit opt-in) a blank `webhook_secret` when multiple GitHub organizations are configured, since it silently disables signature verification for that organization's namespace while still permitting free-form JSON in shared fields.

### Proof of Concept
Preconditions (documented, supported configuration): Shipit is configured with the multi-org secrets format; `OrgTwo` has `webhook_secret:` left blank; `OrgOne` has a real, secret-protected app installed and owns the stack/commit an attacker wants to affect.

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-empty      # ignored: OrgTwo has no secret

{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/irrelevant-repo" },
  "sha": "<sha-of-a-commit-that-belongs-to-OrgOne/target-repo>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```

1. `WebhooksController#verify_signature` resolves `repository_owner == "OrgTwo"`, fetches `Shipit.github(organization: "OrgTwo")`, and `verify_webhook_signature` returns `true` because `OrgTwo`'s `webhook_secret` is blank [3](#0-2) .
2. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the target commit in `OrgOne/target-repo` regardless of the `repository.owner.login` used in step 1 — and calls `create_status_from_github!`, injecting a forged "success" status for a commit the attacker never had any authenticated relationship to [6](#0-5) .
3. If `OrgOne`'s stack's deploy eligibility depends on that status, the attacker has bypassed CI/status gating and can trigger an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
