### Title
Webhook Signature Verification Trusts a Different Payload Field Than the One Used to Select the Target Repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate an inbound webhook against based on `repository.owner.login` (or `organization.login`) read directly from the *unverified* JSON body. Once the signature check passes, every event handler resolves the target `Stack`/`Repository` using a **different** field from that same unverified body — `repository.full_name`. Nothing ties `full_name` back to the `owner.login` that was actually used to pick the signing secret, so on a multi-org Shipit install an attacker who legitimately controls (or knows) one organization's `webhook_secret` can forge a validly-signed webhook whose `repository.full_name` names a repository belonging to a completely different, unrelated organization/tenant configured on the same instance.

### Finding Description
`before_action :verify_signature` runs before `create`, and picks the GitHub App config to verify against like this: [1](#0-0) 

`repository_owner` is derived straight from the raw, not-yet-verified request body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `webhook_secret` (Shipit explicitly supports multiple GitHub orgs/tenants sharing one instance, each with its own `app_id`/`webhook_secret`): [3](#0-2) 

`verify_webhook_signature` only proves the payload bytes were HMAC-signed with *that org's* secret — it says nothing about which repository the event content is allowed to reference: [4](#0-3) 

Once signature verification succeeds, every handler resolves the affected `Stack`(s) using `repository.full_name`, a sibling field of `repository.owner.login` inside the same JSON object, with no re-check that it belongs to the organization whose secret validated the request: [5](#0-4) [6](#0-5) [7](#0-6) 

This mirrors the report's root cause pattern exactly: a value that is *acted upon* (`repository.full_name`, driving which Stack gets synced/archived/unarchived) is never actually covered by the check that is supposed to establish trust (the signature is only proven relative to `repository.owner.login`). Equality that should hold but does not:
`organization authenticated by signature (repository.owner.login) == organization of the repository actually written (repository.full_name)`.

### Impact Explanation
Because GitHub's real webhook delivery always keeps `owner.login` and `full_name` consistent, this is invisible under normal operation. But the attacker here does not need actual GitHub delivery — they only need one valid `webhook_secret` for *any* organization configured on the shared Shipit instance (e.g., because they are a legitimate GitHub App admin/collaborator for that one org) to hand-craft an arbitrary JSON body and a matching HMAC. With that, they can:
- Set `repository.owner.login`/`organization.login` to the org whose secret they hold (passes `verify_signature`), and
- Set `repository.full_name` to any other repository tracked by the Shipit instance, including ones belonging to organizations/tenants they have no legitimate access to.

This lets them trigger `GithubSyncJob`/`stack.sync_github` on an unrelated stack, archive/unarchive PR review stacks (`ClosedHandler`, `ReopenedHandler`), or otherwise mutate state for repositories outside their authorization boundary — i.e., cross-repository/cross-tenant writes performed by an entity whose only credential is a *different* organization's webhook secret.

### Likelihood Explanation
Requires only knowledge of one legitimate `webhook_secret` in a multi-org Shipit deployment (a realistic, documented configuration per `config/secrets.development.shopify.yml`) and the ability to POST a hand-crafted JSON body with a valid `X-Hub-Signature`. No repository write access, session, or `ApiClient` token is needed — the webhook endpoint is unauthenticated apart from the HMAC check.

### Recommendation
After a successful signature check, verify that `repository.full_name` (and any other repository/org identifiers subsequently used by handlers) is consistent with the `repository.owner.login`/`organization.login` used to select the verifying secret — e.g., re-derive/require `full_name.split('/').first == repository_owner` — or better, resolve the target `Repository`/`Stack` scoped to the verified organization rather than trusting an independent field from the same unauthenticated JSON body.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema).
2. Attacker holds `org-a`'s `webhook_secret` (e.g., as an admin of the GitHub App for `org-a`).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/private-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a_webhook_secret, body)` and POSTs to `/webhooks`.
5. `verify_signature` looks up `Shipit.github(organization: "org-a")` and successfully validates the signature.
6. `PushHandler#process` resolves stacks via `repository.full_name` = `"org-b/private-repo"` and calls `stack.sync_github`, acting on a stack the attacker has no legitimate relationship to, using credentials for an entirely different organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
