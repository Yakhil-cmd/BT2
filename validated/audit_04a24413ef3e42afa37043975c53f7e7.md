### Title
Cross-repository CI status forgery via unscoped `StatusHandler` SHA lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization/App installation identified by `repository_owner` in the payload, but `StatusHandler#process` writes commit status data to **any** `Commit` row across the entire installation whose SHA matches, without checking that the commit's repository/stack matches the authenticated organization/repository.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret used for HMAC validation) purely from the unverified JSON body: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . This proves only that the request came from *some* GitHub App/organization installation known to Shipit — it does not bind the verified identity to which specific repository's data may be mutated.

Once verified, the raw `params` (including the attacker's/GitHub's `sha`) are forwarded unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . `StatusHandler#process` then does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [4](#0-3) 

Unlike `PushHandler`, which scopes to `stacks` derived from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`Handler#repository_name` [5](#0-4) , `StatusHandler` never consults the repository field at all — it matches purely by `sha` against the global `commits` table, which spans every stack/repository registered in the Shipit instance.

This breaks the binding: **organization/installation that authenticated the webhook == repository/stack whose commit status is written**. A GitHub App installation on organization A only proves the request originated from A's App, not that the `sha` in the payload belongs to a commit owned by A's repository. Because git commit SHAs are derived from content/history and are frequently shared across forks and mirrors of the same upstream project, an attacker who controls a repository in an org with its own Shipit-connected GitHub App/webhook (i.e., any onboarded org, including one they set up for this purpose, or a fork of a target's public repo) can send a validly-signed `status` webhook whose `sha` coincides with a commit already tracked in a victim stack belonging to a different organization/repository. `StatusHandler` will happily write a fabricated status (`state`, `description`, `target_url`, `context`) onto that commit in the victim stack.

### Impact Explanation
`Commit#create_status_from_github!` feeds directly into `Commit#status`/`Status::Group` and `Commit#deployable?`, and `add_status` triggers `stack.schedule_merges` and `deployable_status`/`commit_status` hooks whenever the status transitions to success [6](#0-5) [7](#0-6) . If the victim stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` will enqueue `ContinuousDeliveryJob` once the commit becomes `deployable?` [8](#0-7) . An attacker who can make an out-of-band, cross-org "success" status land on a shared/forked commit SHA in a target stack can therefore cause an **unauthorized deploy** — matching the "unauthorized deploy" Critical-impact category in scope — without ever having write access, an `ApiClient` token, or the target's webhook secret.

### Likelihood Explanation
The attacker only needs: (1) their own onboarded GitHub organization/App installation (a normal, unprivileged Shipit customer relationship, not a privileged account), and (2) a commit whose SHA is shared with the victim's tracked repository — trivially achievable if the victim repository is public and forked/mirrored (a common real-world scenario for shipit-engine deployments, since forks retain identical SHAs for shared history). No signature forgery, no compromise of the victim's webhook secret, and no GitHub write access to the victim repo are required, making this a High-confidence, low-effort exploitation path once the SHA-sharing precondition is met.

### Recommendation
Scope `StatusHandler` (and any other handler matching purely on `sha`/global identifiers) to the repository identified in the payload, mirroring `Handler#stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
so that a commit is only updated when it belongs to a stack whose repository matches the `full_name` from the same verified payload — closing the gap between "organization that authenticated" and "repository whose commit is written."

### Proof of Concept
1. Attacker's organization `Evil` has a legitimate Shipit GitHub App installation (any onboarded org qualifies; no special privilege needed).
2. Attacker forks or mirrors the victim's public upstream repository into `Evil/fork`, inheriting identical commit SHAs for shared history commits already tracked as `Commit` rows under the victim's Shipit stack.
3. Attacker triggers (or fabricates, since they control their own repo's commit-status API access) a `status` event from `Evil/fork` for a shared SHA with `state: "success"`.
4. GitHub (or the attacker, with legitimate access to set commit statuses on their own fork) delivers the webhook to Shipit, signed with `Evil`'s real webhook secret.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `Evil` and verifies successfully — proving only that the request is from `Evil`'s installation [1](#0-0) .
6. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against the entire `commits` table, finds the victim's commit row, and writes the attacker-supplied "success" status to it [4](#0-3) .
7. If the victim stack is set to continuous deployment, the newly "successful" commit becomes `deployable?` and is auto-deployed [6](#0-5) [8](#0-7) .
