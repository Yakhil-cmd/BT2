### Title
Webhook signature is verified against a GitHub-App secret selected from an unvalidated field, decoupling authenticated organization from acted-upon repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which HMAC secret) to validate a webhook's signature with by reading `repository.owner.login` / `organization.login` straight out of the *unauthenticated* JSON body, before the signature has been checked. Nothing in this flow cross-checks that the selected "verifying organization" is the same entity as the repository the payload actually claims to modify (`repository.full_name`), which is the field downstream handlers (e.g. push/sync handlers) use to resolve the `Stack`/`Repository` record to act on.

### Finding Description
`repository_owner` is computed purely from attacker-suppliable JSON: [1](#0-0) 

and is used before signature verification to choose the `github_app` instance whose secret will validate the request: [2](#0-1) 

`verify_webhook_signature` then computes the HMAC using only that organization's configured `webhook_secret`: [3](#0-2) 

Note also that if the resolved organization has no `webhook_secret` configured at all, verification is skipped entirely (`return true unless webhook_secret`), meaning any request claiming to be from that organization passes unauthenticated.

The invariant the code needs, but never enforces, is:
`organization used to select/verify the signing secret == organization actually referenced by the repository field the handler writes against (repository.full_name)`.

Because `repository.owner.login` (used for verification) and `repository.full_name` (used later by push/sync handlers to resolve the target `Stack`) are two independent, attacker-controlled fields inside the same unauthenticated raw body, an attacker who legitimately knows/controls the webhook secret for *any* organization configured in this Shipit instance (their own onboarded org) can craft a payload where:
- `repository.owner.login` / `organization.login` = their own organization (secret known to them, so the HMAC they compute passes `verify_signature`), while
- `repository.full_name` = a victim organization/repository already tracked by this Shipit instance.

The signature check succeeds (it's being checked against the attacker's own, correctly-known secret), but the event is then dispatched to handlers that key off `repository.full_name`/other repository fields to find and mutate a *different* stack's state (sync commits, trigger continuous deployment, etc.).

### Impact Explanation
This breaks the authentication boundary that a webhook secret is supposed to guarantee: "this payload really originates from organization X's GitHub". Instead, cryptographic proof of organization X's secret is used to authorize state changes claimed for organization Y's repository. Depending on which handlers are wired to the event type (`push`, `status`, `check_suite`, etc.), this can drive `GithubSyncJob`, commit-status writes, or continuous-deployment triggers against a stack the attacker has no legitimate relationship with — i.e., cross-repository writes / an unauthorized deploy, matching the Critical bucket in scope.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate GitHub organization owner/admin whose organization is *also* configured in the same multi-tenant Shipit deployment (a normal situation for a shared Shipit instance serving many teams/orgs), and that they can POST directly to the public `/webhooks` endpoint with a self-computed, valid `X-Hub-Signature` header. No GitHub App private key, `api_clients_secret`, or Shipit session is needed — only knowledge of their own org's webhook secret, which they legitimately possess.

### Recommendation
Do not select the verification key from an attacker-controlled field alone; verify the payload's cryptographic signature and separately validate that the organization/repository the handler will act on (`repository.full_name`, `repository.owner.login`) matches the organization whose secret validated the signature, rejecting the request otherwise. Additionally, remove the `return true unless webhook_secret` fallback in `verify_webhook_signature` so that organizations without a configured secret cannot bypass verification.

### Proof of Concept
1. Attacker legitimately owns/administers GitHub org `attacker-org`, which is configured in this Shipit instance with webhook secret `S`.
2. Attacker crafts a JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` and POSTs directly to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `github_app`, and successfully verifies the signature using secret `S` [4](#0-3) .
5. The event is dispatched to the registered push handler, which resolves the target repository/stack from `repository.full_name` = `"victim-org/victim-repo"`, causing sync/deploy actions to run against a stack the attacker does not own — despite the signature having been verified against an unrelated organization's secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
