Confirmed: `system_vote_count` is unrestricted (any single-authored non-AA unit can post it, validated only in `validation.js:1913-1923`), and it directly triggers `countVotes()` in `main_chain.js`, which weighs OP-list and numerical-parameter votes by **current** byte balance rather than the balance actually held at vote-casting time.

### Title
Governance vote weighting uses current spendable balance instead of a locked/committed amount, enabling flash-style manipulation of OP-list and system-parameter elections - (File: main_chain.js)

### Summary
`countVotes()` computes each voter's influence over `op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` from the voter's *current* stable-good byte balance at the moment counting runs, not the balance they held when they cast the `system_vote`. Because counting can be triggered by anyone at will via an unrestricted `system_vote_count` message, and balance is freely transferable, an attacker can transiently accumulate a large byte balance across previously-cast voter addresses, trigger the count, and immediately move the coins away — the same root-cause pattern as H-27 (using a mutable, freely-transferable balance as a proxy for "committed stake" when computing a weighted outcome).

### Finding Description
`main_chain.js` selects all addresses that ever cast a `system_vote` for a subject [1](#0-0) , and instead of using the amount the address held/committed at vote time, it re-reads their **current** stable-good byte balance right at count time and inserts it into a temporary `voter_balances` table [2](#0-1) . Vote eligibility only checks whether an address voted at any point within a (potentially multi-year) `since_timestamp` window [3](#0-2) ; the *timestamp of the vote* is used only for the eligibility window, while the *weight* used for tallying is the address's balance as of the count moment [4](#0-3) [5](#0-4) .

Counting is not run on a fixed schedule; it is triggered whenever a `system_vote_count` message stabilizes [6](#0-5) [7](#0-6) . `system_vote_count` can be posted by any single non-AA author with no privilege check beyond subject validity [8](#0-7) , and an emergency variant can force an immediate op_list recount after a timeout with no additional balance requirement beyond the elapsed time [9](#0-8) [10](#0-9) .

This is structurally identical to the Sherlock H-27 root cause: a reward/weight computation reads an account's *current, freely-transferable balance* as a proxy for a durable commitment (staked amount / long-term holdings), rather than using an internally-tracked, time-bound record of what was actually held/committed when the decision-relevant action (vote) occurred. Just as the ELFI bug let an attacker move stake tokens into an account right before `updateAccountFeeRewards` runs, here an attacker can move bytes into voter addresses right before `countVotes` (or an emergency count) runs.

### Impact Explanation
`op_list` determines the network's order providers/witnesses, which underlie main-chain stability and unit confirmation; `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` are consensus-relevant network parameters that affect fee calculation and TPS-fee-based validation (`validateTpsFee` in `validation.js`) [11](#0-10) . Manipulating these via transient balance inflation can let an attacker install a favorable/malicious OP list or push extreme fee/interval parameters, risking node disagreement on validity/stability or degraded ability of the network to confirm units — impact categories explicitly in scope.

### Likelihood Explanation
Exploitation requires: (1) casting `system_vote` from one or more addresses (cheap, unrestricted, and durable — the vote counts as long as it falls within the multi-year eligibility window), (2) temporarily accumulating a large byte balance in those addresses (e.g., via short-term loan/exchange transfer or shuffling one's own holdings across many previously-voted addresses) so it becomes stable-good, and (3) posting `system_vote_count` (or waiting for the emergency path) at that moment. Because counting is attacker-triggerable and vote eligibility does not require recent voting activity, the attacker fully controls timing, making this more practical than typical time-locked governance systems.

### Recommendation
Decouple vote weight from current spendable balance:
- Snapshot and store the voter's balance at the time the `system_vote` is cast (or require some minimum holding period/lock before a balance counts toward voting weight), instead of re-querying live balance at count time.
- Alternatively, require re-casting/confirming votes within a bounded recent window whose balance is checked at a fixed, non-attacker-chosen snapshot mci, and/or restrict who may trigger `system_vote_count` (e.g., minimum elapsed time or balance stability period) to prevent an attacker from timing the count to their own transient balance spike.

### Proof of Concept
1. Attacker controls address A with negligible balance. Posts `system_vote {subject: 'op_list', value: <attacker-favorable OP list>}` from A — this is accepted and recorded in `system_votes`/`op_votes` regardless of A's balance [12](#0-11) .
2. Time passes; A remains within the eligibility window (up to multi-year `since_timestamp` expansion) [3](#0-2) .
3. Immediately before triggering the count, attacker moves a large amount of bytes into A (borrowed, or shuffled from other addresses they control) so it becomes a stable-good unspent output.
4. Attacker posts `system_vote_count {payload: 'op_list'}` (or waits for/triggers the emergency path) [8](#0-7) .
5. `countVotes()` reads A's now-inflated current balance into `voter_balances` and tallies it toward A's previously cast (and possibly stale) op_list vote [2](#0-1) [13](#0-12) .
6. Attacker moves the bytes back out after the count is committed to `system_vars` [14](#0-13) , having influenced the OP list (or numerical parameter) disproportionately to any funds actually locked/committed to the vote.
