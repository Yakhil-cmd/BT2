### Title
Arbitrary account takeover in Stack/Delegate/Transfer-STX-via-Bitcoin: `sender` is bound to `PreStxOp.output` (an unauthenticated recipient address), not to the key that authorized any spent input - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` sets `output` from the *first Bitcoin output* of the PreStx transaction, an address the payer chooses freely and never signs for [1](#0-0) . `StackStxOp::get_sender_txid` only requires that the *second* input's spent output (vout 1) of the PreStxOp's own txid be referenced, with no requirement that whoever supplies that input also controls or is the address in vout 0 [2](#0-1) . Because vout 0 (identity) and vout 1 (chaining/spend authorization) are decoupled, an attacker who fully controls both Bitcoin transactions (funding, signing, and spending) can set vout 0 to a victim's derived Stacks address while only ever proving ownership of vout 1.

### Finding Description
The broken equality: **the Stacks principal whose STX gets locked (`op.sender`) must equal the principal whose Bitcoin private key authorized the chained transactions**. The code enforces only that `StackStxOp`'s (or `DelegateStxOp`'s/`TransferStxOp`'s) first input spends vout 1 of a valid `PreStxOp` txid [2](#0-1) ; it never checks that the entity spending vout 1 is also the entity who received (or controls) vout 0, which is what becomes `op.sender` further up the pipeline via `PreStxOp.output` [3](#0-2) .

Exploit flow:
1. Attacker builds `tx1` (the PreStx transaction) spending only their own UTXOs, with `vout[0]` paying (even dust) to victim V's Bitcoin address (whose hash160 equals V's derived StacksAddress), and `vout[1]` paying back to an attacker-controlled address (change).
2. The node parses `tx1` into a `PreStxOp` with `output = V` [4](#0-3) , `txid = tx1.txid()`.
3. Attacker builds `tx2` (StackStx), spending `tx1`'s `vout[1]` (which only the attacker controls/signed originally) as its first input, and encodes `stacked_ustx`, `num_cycles`, `signer_key` in the OP_RETURN payload, plus their own `reward_addr` as `tx2`'s first output.
4. `StackStxOp::get_sender_txid` accepts this because input 0 references `tx1.txid()` at vout 1 [2](#0-1) .
5. The resulting `StackStxOp.sender = V` (bound from the previously-recorded `PreStxOp.output`), while `reward_addr` and `signer_key` are entirely attacker-chosen [5](#0-4) .
6. When applied, PoX locking uses `sender = V` to lock V's real STX balance, sending future PoX BTC rewards to the attacker's `reward_addr`, and granting stacking/signer weight under an attacker-controlled `signer_key` — all without V ever producing a Bitcoin or Stacks signature.

No later guard re-derives or re-validates that `sender` corresponds to the actual signer of the Bitcoin inputs; the mechanism assumes wallets always set `vout[0]` to their own address, but nothing in `parse_from_tx`/`get_sender_txid` enforces it.

### Impact Explanation
Attacker forcibly locks any target address's actual STX balance into stacking for up to the max cycle count, denying the victim use of those funds (freezing) and redirecting all resulting PoX BTC rewards, plus signer-weight/reward-slot control, to attacker-chosen addresses/keys (theft of rewards, unsigned stacking action attributed to the victim). This matches Critical (permanent-freeze / theft of PoX rewards derived from a victim's locked STX) and High (unsigned stacking action, signing weight not backed by attacker's own locked value) categories. The attack is repeatable against any address the attacker can name, each requiring only two attacker-funded, attacker-signed Bitcoin transactions.

### Likelihood Explanation
Preconditions are minimal: attacker needs only enough BTC to fund two chained transactions (dust-level output to V suffices) and one Stacks-adjacent burnchain op parser reachable in any PoX cycle where `StackStxOp` (or `DelegateStxOp`/`TransferStxOp`) processing is active. No privileged role, no cooperation from V, and no compromise of V's keys is required — fully attacker-controlled and cheap, feasible in a single sortition.

### Recommendation
Require that `PreStxOp.output` be cryptographically bound to the signer(s) of `PreStxOp`'s own inputs (e.g., derive/verify `output` against the input's pubkey hash rather than trusting an arbitrary output address), or alternatively require that the address spending vout 1 in the follow-on op (`StackStxOp`/`DelegateStxOp`/`TransferStxOp`) match `PreStxOp.output`'s underlying key/script before accepting `sender`.

### Proof of Concept
Rust integration test (e.g., in `stackslib/src/chainstate/burn/operations/stack_stx.rs` tests or `stackslib/src/burnchains/tests/mod.rs`):
1. Fund attacker-only UTXOs; build `tx1` with `vout[0].address = V` (any address with a known STX balance, e.g. via `StacksAddress::new`), `vout[1].address = attacker`.
2. Parse `tx1` via `PreStxOp::parse_from_tx`; assert `op.output == V`.
3. Build `tx2` spending `tx1`'s vout 1 as input 0, with attacker's `reward_addr` and `signer_key`; parse via `StackStxOp::parse_from_tx(..., sender = op.output /* = V */, ...)`.
4. Apply both ops against a sortition/chainstate fixture where V has a nonzero STX balance and the attacker has none stacked.
5. Assert V's STX balance becomes locked (`STXBalance` locked amount > 0 for V) and that `reward_addr`/`signer_key` equal attacker-controlled values — with zero transactions signed by V's Stacks or Bitcoin key throughout the test.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
