### Title
Hookify `block` Rules Fail Open on Any Parse/Runtime Exception, Silently Allowing the Exact Commands/Edits the User Configured to Block - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The C4 report's root cause is a security-relevant state (`rewardsVestingWallet`) that a critical code path depends on but that has no reliable way of ever being correctly populated, so the enforcement branch (`rewardsVestingWallet.release(...)`) can never execute and the intended protection silently never happens. The `hookify` plugin's `PreToolUse` enforcement has the same structural flaw: the `action: block` guarantee a user configures (e.g. "block `rm -rf`") depends on `RuleEngine.evaluate_rules` successfully returning a `permissionDecision: deny` payload, but the surrounding code has multiple paths where any exception collapses the decision to a bare `systemMessage` and an unconditional `sys.exit(0)` — which Claude Code treats as "no opinion / allow."

### Finding Description
`pretooluse.py` is registered as the `PreToolUse` hook for every tool call [1](#0-0) . Its `main()` function wraps rule loading and evaluation in a single broad `try/except Exception`, and in every failure branch (import failure, JSON decode issues, or any exception raised while loading/evaluating rules) it emits only a `systemMessage` — never `hookSpecificOutput.permissionDecision: "deny"` — and always calls `sys.exit(0)` in the `finally` block: [2](#0-1) 

The `deny` decision is only produced deep inside `RuleEngine.evaluate_rules`, on the successful, blocking-rule-matched path [3](#0-2) . Any exception thrown before that point — for example from the hand-rolled, non-standard YAML "parser" in `extract_frontmatter` (which does manual string splitting/indent tracking with no schema validation) [4](#0-3) , or from `load_rule_file`/`load_rules` themselves — is caught and converted into a rule being silently dropped (`continue`) or, if it escapes to `pretooluse.py`, into an allow-by-default outcome [5](#0-4) .

This mirrors the BathToken bug class: a security control (`action: block`) is documented and configured by the user as an enforced guarantee [6](#0-5) , but the code path required to actually deliver that guarantee (`hookSpecificOutput.permissionDecision: deny`) has no resilient way to be reached whenever rule parsing/evaluation encounters any unexpected input — it fails open instead of fail closed, just as `rewardsVestingWallet` had no way to ever be non-zero.

### Impact Explanation
An unprivileged user (or Claude acting on adversarial/complex input) who configures a `block` rule to prevent destructive operations (e.g. `rm -rf`, `dd`, writes to `.env`/credentials files) receives no actual protection whenever the custom rule file trips any parsing edge case in the ad-hoc frontmatter parser, or any other exception occurs during evaluation — the dangerous `Bash`/`Write`/`Edit` tool call proceeds exactly as if no rule existed, with only a comment in the transcript/stderr (`Hookify error: ...` or `Hookify import error: ...`), which is easy to miss. This is a concrete, silent security-control bypass rather than a cosmetic issue.

### Likelihood Explanation
The frontmatter parser in `config_loader.py` is a manually written mini-YAML implementation (not a real YAML library) with many untested edge cases (multi-line dict continuations, inline comma-separated dicts, indentation tracking) [7](#0-6) . Any rule file with slightly unusual formatting, an edge case in conditions, or an unexpected field type is plausible to trip a `ValueError`/`KeyError`/`AttributeError`/`TypeError` that is caught and converted to "skip this rule" or "allow the operation," making the fail-open condition realistically reachable, not just theoretical. Because `PreToolUse` runs on every tool call, the exposure window is broad.

### Recommendation
Change the design from fail-open to fail-closed for `action: block` semantics:
- When a `block`-configured rule cannot be loaded/evaluated due to an exception, the hook should either surface an explicit `ask`/`deny` decision (forcing user confirmation) rather than silently allowing the tool call, or clearly and loudly report the failure state so the user knows their configured protection did not run.
- Replace the hand-rolled frontmatter parser with a real YAML parser (e.g., `PyYAML`) to eliminate the large surface of parsing edge cases.
- Add tests that assert `action: block` rules are enforced even when adjacent rule files are malformed, and that any unhandled exception during rule loading defaults to the safer/more restrictive outcome for events explicitly marked `block`.

### Proof of Concept
1. Create `.claude/hookify.dangerous-rm.local.md`: 
```markdown
---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm\s+-rf
action: block
---
Blocked!
```
2. Alongside it, create a second rule file with unusual/edge-case frontmatter that the hand-rolled parser mishandles (e.g., a `conditions:` list mixing inline-comma-dict and multi-line-dict styles, or a field containing a raw colon-and-comma combination that `extract_frontmatter`'s heuristics misclassify), causing `load_rule_file`/`extract_frontmatter` to raise inside `load_rules` in a way not covered by the narrow exception types, or causing the whole `main()` `try` block in `pretooluse.py` to raise before `RuleEngine.evaluate_rules` runs.
3. Have Claude run `rm -rf /tmp/testdir`.
4. Because the exception handling in `pretooluse.py` / `config_loader.py` converts any failure into an allow-by-default `sys.exit(0)` with no `permissionDecision: deny`, the destructive command executes despite the `block` rule being `enabled: true` — confirming the fail-open bypass. (Exact minimal malformed-YAML input needed to trigger the specific exception was not verified end-to-end in this analysis; verifying it requires actually running the parser against crafted inputs, which requires code execution outside the scope of this read-only investigation.)

```python
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

```python
def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()

    # Simple YAML parser that handles indented list items
    frontmatter = {}
    lines = frontmatter_text.split('\n')

    current_key = None
    current_list = []
    current_dict = {}
    in_list = False
    in_dict_item = False

    for line in lines:
        # Skip empty lines and comments
        stripped = line.strip()
        if not stripped or stripped.startswith('#'):
            continue

        # Check indentation level
        indent = len(line) - len(line.lstrip())

        # Top-level key (no indentation or minimal)
        if indent == 0 and ':' in line and not line.strip().startswith('-'):
            # Save previous list/dict if any
            if in_list and current_key:
                if in_dict_item and current_dict:
                    current_list.append(current_dict)
                    current_dict = {}
                frontmatter[current_key] = current_list
                in_list = False
                in_dict_item = False
                current_list = []

            key, value = line.split(':', 1)
            key = key.strip()
            value = value.strip()

            if not value:
                # Empty value - list or nested structure follows
                current_key = key
                in_list = True
                current_list = []
            else:
                # Simple key-value pair
                value = value.strip('"').strip("'")
                if value.lower() == 'true':
                    value = True
                elif value.lower() == 'false':
                    value = False
                frontmatter[key] = value

        # List item (starts with -)
        elif stripped.startswith('-') and in_list:
            # Save previous dict item if any
            if in_dict_item and current_dict:
                current_list.append(current_dict)
                current_dict = {}

            item_text = stripped[1:].strip()

            # Check if this is an inline dict (key: value on same line)
            if ':' in item_text and ',' in item_text:
                # Inline comma-separated dict: "- field: command, operator: regex_match"
                item_dict = {}
                for part in item_text.split(','):
                    if ':' in part:
                        k, v = part.split(':', 1)
                        item_dict[k.strip()] = v.strip().strip('"').strip("'")
                current_list.append(item_dict)
                in_dict_item = False
            elif ':' in item_text:
                # Start of multi-line dict item: "- field: command"
                in_dict_item = True
                k, v = item_text.split(':', 1)
                current_dict = {k.strip(): v.strip().strip('"').strip("'")}
            else:
                # Simple list item
                current_list.append(item_text.strip('"').strip("'"))
                in_dict_item = False

        # Continuation of dict item (indented under list item)
        elif indent > 2 and in_dict_item and ':' in line:
            # This is a field of the current dict item
            k, v = stripped.split(':', 1)
            current_dict[k.strip()] = v.strip().strip('"').strip("'")

    # Save final list/dict if any
    if in_list and current_key:
        if in_dict_item and current_dict:
            current_list.append(current_dict)
        frontmatter[current_key] = current_list

    return frontmatter, message
```
