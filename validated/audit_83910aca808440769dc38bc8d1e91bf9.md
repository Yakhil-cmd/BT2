### Title
Webhook signature verified against `repository.owner.login`, but handlers act on a different, unchecked payload field (`repository.full_name` / `sha`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's webhook secret to validate the HMAC signature against using `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature is accepted, the parsed JSON body is handed unmodified to the event handler, which derives the actual object to mutate from a *different, unvalidated* field of the same payload: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`, or, for `StatusHandler`, from `params.sha` alone with no repository scoping at all. Nothing enforces that `repository.owner.login` (the field that picked the trusted secret) is consistent with `repository.full_name` or the commit `sha` (the fields the handler actually acts on).

### Finding Description
This is the exact bug class from the report: a security-relevant check validates one field, while a completely independent field of the same payload is the one actually used for the state-changing operation. In the C4 report, `lastInteractedTimestamp` was checked on `lpTokenETH` while the burn/mutation happened on `_token`. Here:

- Verification binding: `repository_owner` → `Shipit.github(organization: repository_owner)` → HMAC secret used in `verify_webhook_signature`. [1](#0-0) [2](#0-1) 

- Action binding: handlers resolve the target `Repository`/`Stack` from `repository.full_name`, a sibling field never covered by the check above: [3](#0-2) 

- `PushHandler` syncs whatever stacks match that unchecked `repository_name` + branch: [4](#0-3) 

- `StatusHandler` is worse: it doesn't even use `repository_name` — it looks up **any** `Commit` in the entire installation matching `params.sha` and writes a GitHub status onto it, with zero repository scoping: [5](#0-4) 

Because each configured GitHub organization/App installation has its own independent `webhook_secret` (`lib/shipit/github_app.rb`), any actor who legitimately controls a GitHub App installation for *some* organization tracked by this Shipit instance (i.e., can send a validly-signed webhook for their own org) can craft a JSON body where:
- `repository.owner.login` = their own org (so `verify_signature` picks their own secret and their real signature validates), and
- `repository.full_name` / `sha` = a target belonging to a *different* organization/repository tracked by the same Shipit instance.

The equality that should hold is: `organization whose secret authenticated the request == organization of the repository being written`. This finding breaks it: the authenticating organization and the mutated repository/commit are read from unrelated fields of the same untrusted body, with no cross-check.

### Impact Explanation
This directly crosses one of the explicitly listed authorization boundaries: **escalation into cross-repository writes / unauthorized deploy, rollback or merge**.
- Via `StatusHandler`, an attacker who is only authorized to send webhooks for one organization can forge a passing (`state: "success"`) CI status onto an arbitrary commit `sha` belonging to a completely different, victim repository/stack tracked by the same Shipit instance, as long as that sha happens to exist in Shipit's `commits` table (e.g., a commit already synced for the victim stack). Since commit statuses gate blocking-status checks used by the merge queue and continuous deployment logic, this can cause an unauthorized merge/deploy to proceed on a repository the attacker has no legitimate access to.
- Via `PushHandler`, the attacker can force an unrelated stack (belonging to a different org/repo) to enqueue `GithubSyncJob`, causing Shipit to sync unexpected repository state using its own credentials, cross-organization.

### Likelihood Explanation
Requires the attacker to control (or be an admin of) at least one GitHub organization/App installation that is legitimately registered with this Shipit instance — i.e., they can produce a validly-signed webhook for *some* org, but not for the victim org. This is a realistic multi-tenant scenario for any Shipit deployment serving more than one organization/team, and requires no privileged Shipit account, no `ApiClient` token, and no access to the victim's webhook secret — matching the "unprivileged attacker" framing of the source report.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after verifying the signature, assert that the organization used to select the webhook secret matches the organization implied by every field actually consumed by the handler (`repository.full_name`'s owner segment, and for `StatusHandler`, scope the `Commit` lookup to commits belonging to a repository whose owner equals `repository_owner`). Concretely, `Handlers::Handler#stacks`/`repository_name` and `StatusHandler#process` should validate/derive the repository consistently from the same trusted field used during signature verification, rather than trusting an independent field of the same JSON body.

### Proof of Concept
1. Attacker legitimately installs (or otherwise controls) the Shipit GitHub App on `attacker-org`, and knows `attacker-org`'s `webhook_secret`.
2. Attacker sends a `status` event to `/webhooks` with body:
```json
{
  "sha": "<sha-of-a-commit-belonging-to-victim-org/victim-repo-stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
and `X-Hub-Signature` computed with `attacker-org`'s real, known webhook secret.
3. `verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s secret, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb:21-23`), finds the victim's commit (unrelated to `attacker-org`), and creates a forged "success" status on it, potentially unblocking a merge/deploy on the victim's stack that the attacker has no access to.
