### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` in the JSON body, but every event handler acts on a *different*, independently attacker-controlled field (`repository.full_name`) — breaking the "organization that authenticated == repository that is written" binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) used to validate `X-Hub-Signature` based on `repository_owner`, which is read straight out of the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . Once the signature check passes, the dispatched handler (`Handler#stacks`, used by `PushHandler`, `CheckSuiteHandler`, and every `PullRequest::*Handler`) looks up the target `Repository`/`Stack` using an entirely different field of the same body: `payload.dig('repository', 'full_name')` [3](#0-2) [4](#0-3) . Nothing enforces that `repository.owner.login` (the value that selected the secret used to authenticate the request) and `repository.full_name` (the value that determines which Stack/Repository is acted on) refer to the same repository.

### Finding Description
Shipit supports hosting multiple independent GitHub Apps, one per organization, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications") [5](#0-4) . Each org's operator legitimately knows their own app's `webhook_secret` because they created it.

`verify_signature` picks the `GitHubApp` used to verify the signature purely from the `repository.owner.login` (or `organization.login`) fields of the *body being verified* [2](#0-1) . Because HMAC verification is `sign(secret_of(repository_owner_from_body), whole_body)`, an attacker who legitimately controls one configured org (call it `AttackerOrg`, with a known `webhook_secret`) can compute a valid signature for *any* JSON body as long as `repository.owner.login` in that body says `"AttackerOrg"`. The `full_name`, `check_suite.head_sha`, `pull_request.head.sha/ref`, `number`, `sender.login`, etc. fields — used later by the handlers to select the target repository/Stack and drive behavior — are otherwise unconstrained and can name a completely different, victim organization/repository.

`Handler#stacks` (base class for `PushHandler`, `CheckSuiteHandler`) and each `PullRequest::*Handler#repository` resolve the acted-upon repository via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` / `params.repository.full_name` [3](#0-2) [6](#0-5) , with no cross-check against `repository.owner.login` used for signature selection. This is exactly the "organization that authenticated versus the repository that is written" binding called out as an in-scope class of issue: the equality `organization_whose_secret_verified_signature == owner(repository_full_name_acted_on)` is never enforced.

### Impact Explanation
The most damaging reachable handler is `PullRequest::OpenedHandler` combined with `ReviewStackAdapter#create!`. If the victim repository has Review Stacks enabled with "Allow All" provisioning [7](#0-6) , a forged `pull_request` "opened" event naming the victim's `repository.full_name`, but signed with an attacker-controlled org's own `webhook_secret`, passes signature verification and is then dispatched to `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`, which creates a new `ReviewStack` with attacker-chosen `branch`/`environment` and enqueues it for provisioning [8](#0-7) . Provisioning runs `stack.provisioner.up` and eventually pulls/executes the deploy pipeline (checkout + `shipit.yml` steps) for whatever `branch`/SHA is supplied in the forged payload — i.e., a stack acted on is chosen by an org other than the one whose credential authenticated the request, and code execution / deploy pipeline steps are driven from data never bound to that authentication. This can result in unauthorized provisioning/execution against a repository/environment the forging org does not own, using Shipit's own GitHub credentials for the actual victim repo (`stack.github_api`). Lower-impact variants (`PushHandler`, `CheckSuiteHandler`) let an attacker force a resync of a victim Stack's commit history / re-trigger check-run refresh using a fabricated `after`/`head_sha`, without needing any access to the victim repository.

The severity is capped by the precondition that the attacker must control (i.e., know the `webhook_secret` for) at least one org actually configured in this Shipit instance's `github:` section — this is a legitimate but distinct principal from the victim org whose repository gets acted upon, matching the rule's "organization authenticated vs. repository written" boundary rather than requiring a fully anonymous attacker.

### Likelihood Explanation
Exploitability requires a Shipit deployment configured for **multiple GitHub organizations** (each with independently known `webhook_secret`s) per `docs/setup.md`'s multi-org configuration [5](#0-4) , and the victim repository to have Review Stacks / provisioning enabled for the highest-impact path. In single-org deployments this is not exploitable because there is only one org/secret and thus no other legitimate holder of a valid signature.

### Recommendation
`verify_signature` should re-derive/confirm the organization actually acted upon by the handler and require it to match the organization whose secret validated the signature — e.g., compare `repository.owner.login` (or the `organization.login`) used to select the `GitHubApp` against the owner parsed from `repository.full_name` before proceeding to dispatch handlers, rejecting mismatches with a 422. Handlers should not trust `repository.full_name` alone as the sole authorization anchor for locating a `Stack`/`Repository` to act on.

### Proof of Concept
1. Shipit is configured with two GitHub App orgs in `secrets.yml`: `attacker-org` (secret known to the attacker, who legitimately administers that org's GitHub App) and `victim-org` (hosts a tracked repository `victim-org/victim-repo` with review stacks enabled, "Allow All").
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request` and body:
```json
{
  "action": "opened",
  "number": 999,
  "pull_request": {
    "id": 1, "number": 999, "url": "...", "title": "x", "state": "open",
    "additions": 0, "deletions": 0,
    "head": { "sha": "<attacker-chosen-sha>", "ref": "malicious-branch" },
    "user": { "login": "attacker" },
    "assignees": [], "labels": []
  },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` — a signature they can legitimately compute because they own `attacker-org`'s secret.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against the correct (attacker-known) secret [2](#0-1) .
5. The request is dispatched to `PullRequest::OpenedHandler`, which resolves `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` [4](#0-3)  and, if provisioning is allowed, creates and enqueues a `ReviewStack` for `victim-org/victim-repo` using attacker-chosen `branch`/environment [8](#0-7)  — despite the signature having been verified against `attacker-org`'s secret, not `victim-org`'s.
