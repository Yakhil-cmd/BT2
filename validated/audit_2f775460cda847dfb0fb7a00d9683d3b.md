This confirms the pattern: `PushHandler#process` scopes via `stacks.not_archived.where(branch:)` (using `Handler#stacks`, which resolves via `Repository.from_github_repo_name(repository_name)` — i.e., derived from `payload.dig('repository','full_name')`), and `CheckSuiteHandler#process` does `stacks.where(branch: ...)` before touching commits. `StatusHandler#process`, by contrast, does a global, unscoped `Commit.where(sha: params.sha)` query with no reference to `stacks`, `repository_name`, or any comparison against the target commit's `stack.repository`.### Title
StatusHandler#process mutates Commit rows across repository/stack boundaries with no repository check - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by SHA globally (`Commit.where(sha: params.sha)`) and writes a status to every match, without ever comparing `payload.dig('repository', 'full_name')` (the authenticated repository) against the `stack.repository` of the commits being mutated. Every sibling handler (`PushHandler`, `CheckSuiteHandler`, PR handlers) scopes through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)`; `StatusHandler` is the outlier that skips this entirely.

### Finding Description
The binding that should hold is: `payload.dig('repository','full_name') == commit.stack.repository.github_repo_name` for every `Commit` row touched by the handler. Tracing the call chain:

- `Shipit::WebhooksController#create` parses the raw JSON and dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) . The only upstream gate is `verify_signature`, which validates the HMAC against `Shipit.github(organization: repository_owner)`'s `webhook_secret` — it authenticates the *organization*, not the specific repository, and does nothing about which `Commit`/`Stack` rows get touched [2](#0-1) .
- `Handler#initialize` only runs `ExplicitParameters` schema validation/type-coercion via `param_parser.parse!(payload)`; it never resolves or checks `repository_name` unless the subclass calls `stacks` [3](#0-2) .
- `StatusHandler#process` never calls `stacks` or `repository_name` at all. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a table-wide query with no `stack_id`/repository scoping [4](#0-3) .

Contrast with the correctly-scoped siblings: `PushHandler#process` restricts to `stacks.not_archived.where(branch:)` [5](#0-4)  and `CheckSuiteHandler#process` restricts to `stacks.where(branch: ...)` before touching any commit [6](#0-5) . `stacks` is defined on the base `Handler` as `Repository.from_github_repo_name(repository_name)&.stacks` [7](#0-6) , i.e., exactly the repository-vs-stack equality check that is missing from `StatusHandler`.

**Exploit path.** Git commit SHAs are content-addressed and identical across repositories that share ancestry (e.g., a public fork of a tracked repository, or two Shipit-tracked repos with common history/cherry-picked identical commits). An attacker who owns/controls *any* repository under the same GitHub organization/App installation as a victim's tracked repository (a routine, unprivileged condition — GitHub Apps and their `webhook_secret` are typically shared at the org/installation level, not per-repo) can:
1. Push or otherwise cause a commit that shares a SHA with a commit already ingested into the victim Stack (trivial for shared ancestor commits in a fork).
2. Post a commit status on that SHA in their own repository via the GitHub API (something they're fully entitled to do on their own repo).
3. GitHub genuinely signs and delivers the resulting `status` webhook to Shipit using the shared org secret — `verify_signature` passes because it only checks the org-level HMAC, not that `repository.full_name` matches the target stack.
4. `StatusHandler#process` matches the shared-SHA `Commit` row that actually belongs to the *victim's* stack and calls `commit.create_status_from_github!(params)` on it — a real cross-tenant mutation.

`create_status_from_github!` → `add_status` can flip commit state (e.g., to `success`), firing `deployable_status` hooks and enqueuing `ProcessMergeRequestsJob`, which can influence merge-queue/deploy-readiness decisions for a repository the attacker never authenticated against [8](#0-7) .

No layer in the stack — `verify_signature`, `drop_unhandled_event`, `ExplicitParameters`, or `StatusHandler#process` itself — ever compares the authenticated `repository.full_name` to the mutated commit's `stack.repository`.

### Impact Explanation
An attacker with write/API access to one GitHub repository (their own) sharing a GitHub App/webhook secret with a target org can forge a legitimate, correctly-signed `status` webhook that mutates `Commit`/`CommitStatus` rows belonging to an entirely different Stack/repository that the attacker does not control. This can flip a commit's deployable status (`success`/`failure`/`error`), influence `ProcessMergeRequestsJob` merge-queue behavior, and pollute CI/status history for a repository the attacker never authenticated against — matching the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable for any shared SHA and any repository under the same App installation, so blast radius spans every Stack sharing the org-level webhook secret.

### Likelihood Explanation
Preconditions: attacker needs write access to at least one repository under the same GitHub organization/App installation as the target Stack (common in shared-org multi-team setups), and a commit SHA shared between their repository and the victim's tracked history (trivially achievable via forking or shared ancestor commits — no secret-guessing required). Cost is low: standard git/GitHub operations, no Shipit credentials needed. Fully repeatable against any Stack sharing the same webhook secret.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through `stacks` (as `PushHandler`/`CheckSuiteHandler` do), e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring only commits belonging to a Stack whose `Repository` matches `payload.dig('repository','full_name')` can be mutated.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "StatusHandler must not update a Commit belonging to a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # repository github_repo_name e.g. "shopify/shipit-engine"
  shared_sha = "abc123deadbeef"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)

  attacker_repo = Shipit::Repository.create!(owner: "attacker-org", name: "attacker-repo")
  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "full_name" => attacker_repo.github_repo_name },
  }

  assert_no_changes -> { victim_commit.reload.state } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Binding checked on both sides: `payload.dig('repository','full_name')` (`"attacker-org/attacker-repo"`) vs `victim_commit.stack.repository.github_repo_name` (`victim_stack.repository.github_repo_name`) — currently unequal yet the commit is still mutated, proving the missing check. A full end-to-end variant would `post :create` to `Shipit::WebhooksController` with `X-Github-Event: status`, a valid signature for `attacker-org`, and assert `victim_commit.reload.state` changed despite the mismatched `repository.full_name`.
