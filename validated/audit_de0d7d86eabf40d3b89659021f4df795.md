### Title
Cross-organization commit status forgery due to unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook against using the untrusted `repository_owner` field taken from the payload itself, and that verification only proves *some* organization onboarded to this Shipit instance signed the payload [1](#0-0) . However, `Shipit::Webhooks::Handlers::StatusHandler` never re-checks that the commit it mutates actually belongs to the organization/repository that produced the valid signature: it looks up commits globally with `Commit.where(sha: params.sha)` and writes a status to every match [2](#0-1) . This breaks the equality "organization that authenticated == repository that is written" that every other handler enforces through `Handler#stacks`/`Handler#repository_name`, which scope work to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [3](#0-2) .

### Finding Description
The `status` GitHub event is only required to carry `sha`, `state`, and optional descriptive fields [4](#0-3) . Unlike `PushHandler`, which resolves the target `Stack` set through the payload's `repository.full_name` before acting [5](#0-4) , `StatusHandler#process` queries `Commit` directly by `sha` with no repository/owner constraint at all, then calls `commit.create_status_from_github!(params)` on every matching row across the entire installation [2](#0-1) .

Because Shipit supports multiple GitHub organizations configured with independent `webhook_secret`s in the same instance (as shown by `config/secrets.development.shopify.yml` listing `somegithuborg`/`someothergithuborg` each with their own `webhook_secret`) [6](#0-5) , a valid signature only proves the request originated from whichever organization's secret was used — selected via the attacker-controlled `repository_owner` field read straight from the JSON body before verification [7](#0-6) . Nothing after that point re-ties the `sha` in the payload to a commit that actually belongs to the authenticating organization's repositories.

### Impact Explanation
An attacker who controls (or is a legitimate low-privilege member of) any single GitHub organization/repository onboarded to a shared Shipit instance can send a validly-signed `status` webhook — signed with their own org's `webhook_secret` — but specify a `sha` belonging to a commit in a completely unrelated, more sensitive stack/repository. `StatusHandler` will happily create/overwrite a commit status (e.g. `"state": "success"`) on that unrelated commit. Since Shipit's deploy gating relies on commit/status state to determine deployability, this lets an attacker with control of only their own onboarded repository force a fabricated green status onto another team's commit, potentially unblocking an unauthorized deploy for a stack they have no legitimate access to — matching the report's core pattern of "acting on the totality of a resource using data the verifier never actually bound to the intended scope."

### Likelihood Explanation
Any organization/repository that has been onboarded into a shared/multi-tenant Shipit deployment (a supported and documented configuration, per `config/secrets.development.shopify.yml`) can trigger this by simply configuring a GitHub webhook on their own repository pointed at the shared Shipit `/webhooks` endpoint and crafting a `status` payload with an arbitrary target `sha`. No Shipit session, API token, or elevated GitHub permissions are required beyond controlling one onboarded organization's webhook delivery, which GitHub allows any repo admin to configure.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by cross-cutting identifiers like `sha`) to commits whose `Stack`/`Repository` matches the `repository.full_name` (or owner) that was actually verified against the request's signature, mirroring the scoping already done in `Handler#stacks`/`Handler#repository_name`. Reject or ignore any commit match whose repository does not correspond to the authenticated organization.

### Proof of Concept
1. Attacker registers/administers `attacker-org/attacker-repo` as a stack on the shared Shipit instance, obtaining a legitimate `webhook_secret` for `attacker-org`.
2. Attacker configures a webhook on `attacker-repo` (or crafts the HTTP request directly) sending a `status` event to the shared `/webhooks` endpoint, computing a correct `X-Hub-Signature` with `attacker-org`'s `webhook_secret`, but sets `sha` to the HEAD commit SHA of `victim-org/victim-repo`'s pending pull request, and `state: success`.
3. `WebhooksController#verify_signature` resolves `repository_owner` from the payload as `attacker-org`, verifies successfully against `attacker-org`'s secret [1](#0-0) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (unscoped to `attacker-org`), and writes a `success` status to it [2](#0-1) , potentially satisfying deploy-readiness checks for `victim-org/victim-repo`'s stack.
