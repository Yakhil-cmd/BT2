### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` due to `&&`/`||` precedence, allowing PR authors to force review-stack creation on repos that opted out - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` is written as `A && B || (C && D) || (E && F)`, and Ruby's operator precedence binds `&&` tighter than `||`, so only the first disjunct (`allow_all`) is gated by `repository.review_stacks_enabled`. When a repository has `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (or `prevent_with_label`), `provision?` still evaluates to `true` purely based on the PR's labels, letting any fork PR author trigger stack creation.

### Finding Description
The claimed binding is: "`repository.review_stacks_enabled` as set by an authorized Shipit user" == "the value consulted by every truthy branch of `provision?`". Tracing the code shows this binding is **broken**: [1](#0-0) 

Due to Ruby precedence, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

Only the `allow_all?` branch is ANDed with `review_stacks_enabled`. The `allow_with_label?` and `prevent_with_label?` branches are evaluated completely independently of `review_stacks_enabled`. `Repository#provisioning_behavior` is a plain enum with no dependency on `review_stacks_enabled` at the model level: [2](#0-1) .

Path: `WebhooksController#create` dispatches the `pull_request` webhook to handlers [3](#0-2) , `OpenedHandler#process` calls `respond_to_pull_request_opened?` → `provision?` [4](#0-3) , and if true builds `ReviewStackAdapter#find_or_create!` → `create!`, which sets `branch: params.pull_request.head.ref` (attacker's fork branch name) and enqueues provisioning via `Shipit::ReviewStackProvisioningQueue.add` [5](#0-4) .

`verify_signature` only checks that the webhook came from GitHub for the target organization; it does not validate that the sender is a maintainer, and does not enforce `review_stacks_enabled` at all — that's the handler's job, and the handler's logic is buggy. Because the webhook is a genuine GitHub-generated `pull_request.opened` event (any user who can open a PR against a public repo can trigger it), the signature is valid and passes [6](#0-5) . The PR author fully controls `pull_request.labels` (they can apply labels to their own PR if repo settings allow, or in many default GitHub configurations labels can be applied by PR authors with triage-level access, or a maintainer could inadvertently apply the label without knowing it enables provisioning because `review_stacks_enabled` is false in their mental model) and fully controls `pull_request.head.ref` (their fork's branch name).

No existing guard (`ExplicitParameters` schema, `drop_unhandled_event`, model validations) checks the review_stacks_enabled/provisioning_behavior relationship; the existing test suite (`opened_handler_test.rb`) only exercises `allow_with_label` with `provisioning_enabled: true` (the default), never with `review_stacks_enabled: false`, so this gap is untested.

### Impact Explanation
For any repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) while `review_stacks_enabled: false` — an operator's intended "review stacks are off" setting — an unprivileged PR author can still get a `Shipit::ReviewStack` created with `branch` set to their fork's head ref, and get it enqueued in `Shipit::ReviewStackProvisioningQueue`. Provisioning subsequently reads `shipit.yml` from that attacker-controlled branch (via `DeploySpec::FileSystem`) and executes its steps through `Command#start`/`PTY.spawn` on the deploy host — Critical: RCE on the deploy host of a repository that never opted into review stacks. This is repeatable against any repository with this configuration combination.

### Likelihood Explanation
Preconditions: a repository must be configured with `provisioning_behavior` = `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` = false, and a `provisioning_label_name` set (or blank, for `prevent_with_label` where absence of the label is sufficient — even easier). Attacker cost is trivial: open a PR from a fork and (for allow_with_label) apply/have the label applied, or (for prevent_with_label) simply not apply the label, which is the default state of any new PR. No secrets, tokens, or elevated GitHub roles are required. This is a real, reachable code defect, not theoretical — it stems directly from operator precedence in existing, shipped code.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to any sibling handlers with the same pattern (`LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler` — grep shows similar `review_stacks_enabled`/`provisioning_behavior` checks in those files and should be audited for the same precedence bug).

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label and label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertion before fix: `repository.review_stacks_enabled == false` while `provision?` still returns `true` (stack count increases) — demonstrating the two sides of the claimed binding diverge. After applying the recommended fix, `Shipit::Stack.count` does not change, restoring the binding.
