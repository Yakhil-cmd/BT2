### Title
Cross-organization webhook signature confusion allows spoofed GitHub events for arbitrary tracked stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments (`Shipit.github(organization: ...)`), the organization used to select which webhook secret verifies the HMAC signature is derived from `ActionController::Base#params`, while the payload that is actually processed by webhook handlers is derived from a separate, independent parse of the raw request body. Because Rails merges query-string parameters over JSON body parameters at the top-level key, an attacker who knows the webhook secret of any one organization configured on the instance can make the "verified" organization diverge from the organization/repository whose webhook handlers actually execute — the same class of bug as the reported Solidity issue, where the code path used to *decide* differs from the code path used to *act*.

### Finding Description
`WebhooksController` runs `verify_signature` as a `before_action`, before `create`: [1](#0-0) 

The organization used to select the verifying `GitHubApp`/secret is computed by: [2](#0-1) 

`repository_owner` calls `params.dig(...)`. `params` here resolves to `ActionController::Base#params`, which (for `Content-Type: application/json`) Rails builds by merging the auto-parsed JSON body with the query-string parameters — and on Rails' internal `request_parameters.merge(query_parameters)`, top-level keys from the **query string win** over the body-parsed JSON on collision. `repository` is a single top-level key, so a `?repository[owner][login]=X` query parameter fully replaces the JSON body's `repository` hash for the purposes of `params`, even though it has zero effect on `request.raw_post` (the bytes the signature is actually computed over): [3](#0-2) 

Meanwhile, `create` performs its own, independent parse of the untouched raw body and hands it straight to the event handlers, which resolve the affected repository from that body's `repository.full_name`: [4](#0-3) [5](#0-4) 

`Shipit.github(organization:)` looks up the org-specific config (and thus secret) only when the instance is running in multi-organization mode (`github_default_organization` present, i.e. `secrets.github` is keyed by organization login rather than the flat single-app keys): [6](#0-5) 

**Binding broken:** *organization authenticated* (`repository_owner` from query-string-influenced `params`, used to pick the webhook secret for HMAC verification) `≠` *repository/organization actually written to* (parsed from `request.raw_post` and used by every webhook handler, e.g. `push`, `status`, `commit_status`, `deployable_status`, `pull_request`, `merge`, `membership`).

### Impact Explanation
An attacker who legitimately knows the webhook secret of *any single* organization tracked by this Shipit instance (e.g., their own onboarded, low-privilege org) can craft a POST to the shared `/webhooks` endpoint whose query string names their own org (so `verify_signature` checks the HMAC against a secret they know and can compute correctly for the raw body) while the JSON body itself declares an unrelated victim organization/repository. Since the HMAC is computed over `request.raw_post` regardless of which secret is chosen for the check, the forged signature is valid, and `verify_signature` passes. The unmodified raw body is then handed to the real webhook handlers, which act on the victim's stack: this can fabricate `commit_status`/`deployable_status`/CI states that gate merge-queue and deploy safety checks, fake `push`/`pull_request`/`merge` events, or manipulate `membership`/`Team` records — each of which can influence or trigger unauthorized deploys/rollbacks or corrupt state for repositories the attacker has no rights to. This lines up with the "unauthorized deploy/rollback" and "cross-repository writes" impact classes.

### Likelihood Explanation
Requires the attacker to control an organization already configured on the Shipit instance (multi-tenant `github:` config keyed by org) and to know that organization's own webhook secret — a credential they would legitimately possess for their own onboarded org, not a target's secret. No Shipit session, API token, or repository write access on the victim is needed; the webhook endpoint is unauthenticated by design (protected only by the HMAC check). The exploit relies only on standard Rails parameter-merging semantics for JSON+query-string requests, which is deterministic and reproducible.

### Recommendation
Compute `repository_owner` (and any other value used to select the verification secret) exclusively from the same parsed `request.raw_post` payload that is later dispatched to handlers — never from `ActionController::Base#params`/query string. Ideally, parse the raw body once, store it (e.g., in an instance variable or `request.env`), and have both `verify_signature` and `create` consume that single parsed object, eliminating any possibility of divergence between the verified and the acted-upon payload.

### Proof of Concept
1. Configure Shipit in multi-organization mode with at least two orgs: `attacker-org` (secret known to the attacker) and `victim-org` (a real tracked stack).
2. Attacker crafts a JSON body for a `commit_status`/`push`-type event whose `repository` object names `victim-org/victim-repo`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)` — legitimate for their own org's secret.
4. Attacker POSTs to `.../webhooks?repository[owner][login]=attacker-org` with header `X-Github-Event: <event>` and the body from step 2.
5. `verify_signature` computes `repository_owner` from `params`, which — because the query string's `repository` key overrides the body's `repository` key in the merged `params` hash — resolves to `attacker-org`; the app fetches `attacker-org`'s webhook secret and the HMAC check succeeds.
6. `create` re-parses `request.raw_post` (unaffected by the query string) and dispatches it to `Shipit::Webhooks` handlers, which act on `victim-org/victim-repo` using the attacker-supplied payload.

Note: I could not execute this end-to-end in a live environment (no filesystem/terminal access in this session), so the exact behavior of Rails' `ActionDispatch::Http::Parameters#parameters` merge precedence for the specific Rails version pinned by this engine, and the precise route mounted for `WebhooksController` in `config/routes.rb`, should be confirmed by a maintainer/Devin session with code execution before treating this as fully proven.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
