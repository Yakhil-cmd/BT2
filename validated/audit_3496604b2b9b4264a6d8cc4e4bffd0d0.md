Now I have confirmed the key fact: `lindex` (liquidity index) directly determines the on-chain USD price of ztoken collateral used in health checks and liquidations via `get-asset-price`/`resolve-ztoken`, e.g. `mul-div-down stx-price lindex INDEX-PRECISION` in `v0-1-data.clar` and `market.clar`'s `resolve-ztoken`. This is the exact analog to the `FluxToken`/`VotingEscrow` report: a rounding-down multiplier calculation can silently produce zero delta, but the surrounding state-machine (here, `last-update`) is advanced anyway, permanently discarding the unaccrued amount — except here the consequence lands on a *cross-user* shared price feed (the ztoken collateral valuation) rather than on the caller alone.

### Title
Premature `last-update` advance on asymmetric index rounding causes permanent underpricing of ztoken collateral - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
`accrue()` in every `v0-vault-*.clar` contract advances the shared `last-update` timestamp whenever *either* the borrow index (`index`) or the liquidity index (`lindex`) changes, but the two indexes are calculated with asymmetric rounding: the borrow-side multiplier rounds up (`mul-div-up`, virtually always non-zero) while the liquidity-side multiplier rounds down (`mul-div-down`, which truncates to zero for small `rate * time-delta` products). When a small/no-op time window causes `index` to tick but `lindex` to round to zero, `last-update` is reset anyway, and that whole time window's liquidity accrual is permanently lost — it is never revisited because the next call's `time-delta` starts from the new `last-update`.

### Finding Description
`next-index` uses `calc-multiplier-delta rate time-delta true` (round up) while `next-liquidity-index` uses `calc-multiplier-delta liquidity-rate time-delta false` (round down): [1](#0-0) 

`accrue()` only preserves `last-update` (i.e., only avoids losing the elapsed period) when **both** `idx` and `lindex` are unchanged; if either one moved, the timestamp is advanced for both: [2](#0-1) 

Because `liquidity-rate` (`calc-liquidity-rate`) is derived from the borrow rate scaled down by utilization and `(1 - reserve-factor)`, it is materially smaller than the raw borrow rate feeding `index`. Combined with the round-down (`mul-div-down`) in `calc-multiplier-delta` for the liquidity path, there is a realistic band of `time-delta` values where `index` moves (because `mul-div-up` always yields ≥1 unit of growth once `rate*time-delta>0`) but `lindex` computes to exactly the previous value (rounds to zero growth). In that case `accrue()` resets `last-update` to `stacks-block-time`, discarding that window's supplier-side interest permanently — it can never be recovered by a later call because the elapsed-time base has already moved forward.

This directly parallels the reported bug class: a rounding constant/operation causes small quantities to be truncated to zero, and the surrounding bookkeeping (there: `_locked` state consumed later by `getClaimableFlux`; here: `last-update` consumed by subsequent `accrue()` calls) treats the truncated value as final, permanently erasing it rather than deferring it to the next accrual.

The shared state harmed is not the caller's own position: `lindex` is read by every other borrower/liquidator through the market's `get-asset-price`/`resolve-ztoken` callcode transformation to price ztoken collateral (`zSTX`, `zsBTC`, `zstSTX`, `zUSDC`, `zUSDH`), and by `v0-1-data.clar`'s aggregator: [3](#0-2) 

Any principal (e.g., a routine `deposit`/`redeem`/`borrow` call, or even an unrelated `accrue-and-cache` invocation triggered while walking another user's collateral list) can be the one whose transaction happens to fall in the "index ticks, lindex truncates" window and thereby permanently understate `lindex` for every zToken holder using that vault as collateral, while `index` (and thus vault solvency/reserve accounting) continues to grow correctly.

### Impact Explanation
This is a **High** impact: temporary/permanent freezing (understatement) of unclaimed yield for zToken holders who use rehypothecated collateral. Understated `lindex` lowers the USD-value the market assigns to their collateral relative to their true economic claim on vault assets, which can:
- Reduce their effective borrowing capacity/LTV headroom versus what their true share value should allow, and
- In edge cases push a position closer to (or into) liquidation eligibility earlier than warranted, harming the collateral owner to the benefit of a liquidator — i.e., harm flows from one unprivileged principal's ordinary transaction (whichever call happens to trigger the truncating accrual) onto other, unrelated zToken-collateral holders.

Because `lindex` never "catches up" (the elapsed window is gone, not merely delayed), this loss is permanent for that period, matching the report's "fails to deliver promised returns" impact class.

### Likelihood Explanation
Likelihood is moderate: it requires natural, frequent conditions — utilization low enough (or reserve-factor high enough) that `liquidity-rate` is small, and `time-delta` short enough (frequent transactions/blocks) that `liquidity-rate * time-delta * INDEX-PRECISION < SECONDS-PER-YEAR-BPS`, while the plain borrow-side product clears the rounding threshold via `mul-div-up`. Any active vault with frequent low-utilization periods will exhibit this regularly, since `accrue()` is invoked on essentially every deposit/redeem/borrow/repay/collateral-add/collateral-remove call across the protocol.

### Recommendation
In `accrue()`, only advance `last-update` when **both** derived multipliers correspond to a real, captured elapsed-time debt AND liquidity update — or, better, decouple the "time consumed" bookkeeping so each index tracks its own last-applied timestamp, ensuring a truncated-to-zero `lindex` delta does not cause the underlying elapsed seconds to be discarded. Alternatively, always round the liquidity-index multiplier up (or use a shared, sufficiently large precision constant, as in the original report's recommendation) so it never silently truncates to no-op while the borrow index still advances.

### Proof of Concept
Not independently executed in this Clarity codebase (no Foundry/Clarinet run performed here); the mechanism is demonstrated purely via code-path analysis:
1. Set utilization/rate parameters via `set-points-util`/`set-points-rate` such that `liquidity-rate` is small (low utilization or high `fee-reserve`).
2. Trigger `accrue()` (any deposit/borrow) with a short `time-delta` such that `mul-div-down(liquidity-rate * time-delta * INDEX-PRECISION, SECONDS-PER-YEAR-BPS) == 0` while `mul-div-up(rate * time-delta * INDEX-PRECISION, SECONDS-PER-YEAR-BPS) >= 1` for the borrow side.
3. Observe `index` incrementing (`get-index`) while `lindex` (`get-liquidity-index`) stays flat, and `last-update` (`get-last-update`) advancing to `stacks-block-time` — permanently losing that window's supplier yield, verifiable by comparing successive `get-liquidity-index` reads against expected compounding from `get-interest-rate`/`get-utilization`.
