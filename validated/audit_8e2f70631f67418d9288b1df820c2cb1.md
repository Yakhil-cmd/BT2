### Title
Webhook organization used for signature-secret selection is not bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), while the handlers invoked afterwards (e.g. the push/sync handlers) resolve the target `Stack`/`Repository` using the independent `repository.full_name` field from the same JSON body. Nothing in the controller cross-checks that these two fields describe the same repository, so a forged payload can pass signature verification under one organization's secret while acting on a repository belonging to a different organization.

### Finding Description
The signature check is: [1](#0-0) 
where `repository_owner` is derived as: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/webhook secret configured for that organization, and `verify_webhook_signature` HMACs the *entire* raw body with that secret: [3](#0-2) 

Once verified, `params` is dispatched unmodified to all registered handlers: [4](#0-3) 

The push/sync path resolves the target stack from `repository.full_name`, a field entirely independent of `repository.owner.login`/`organization.login` used above — confirmed by the test that mutates only `full_name` (leaving the owner untouched) to redirect a payload to a different repository record: [5](#0-4) 

Because GitHub's own webhook delivery always keeps `owner.login` and `full_name` consistent, this mismatch is invisible in normal operation — exactly like the UniProxy report, where `hypeRatio` and `depositRatio` were each individually clamped/checked but never checked *against the same real quantity* the transaction actually used. Here, the code checks "does this payload carry a valid signature for organization X" but then acts on "whatever repository `full_name` says", without ever asserting `full_name`'s owner segment equals `repository_owner`. Any party in possession of a webhook secret configured for organization X in Shipit (e.g. an org admin who owns their GitHub App/webhook integration) can therefore forge a raw payload whose `repository.owner.login` = X (so `Shipit.github(organization: 'X')`'s secret validates the HMAC) but whose `repository.full_name` = `Y/victim-repo` for a different, unrelated organization/stack that Shipit also manages.

### Impact Explanation
This breaks the binding "organization that authenticated the webhook == repository that is written by the webhook handler." Downstream handlers (push → `GithubSyncJob`, commit `status`, `check_suite`, `merge_status`, etc.) act on the attacker-chosen repository/stack, producing cross-organization state writes (spurious sync jobs, commit status/check updates, continuous-deployment triggers) attributed to a stack the attacker's secret was never meant to control. This matches the "cross-repository writes" Critical-impact category defined in scope.

### Likelihood Explanation
Exploitation requires the attacker to hold a valid webhook secret for at least one organization configured in the multi-tenant Shipit deployment — a credential far weaker than a Shipit session, `ApiClient` token, or GitHub repository write access, and normally under the sole control of that organization's own GitHub App/webhook setup, not of Shipit administrators. Any Shipit installation serving more than one GitHub organization is affected, since nothing enforces that the verified organization's secret can only originate payloads for repositories under that same organization.

### Recommendation
After signature verification, re-derive the expected organization from the field(s) actually used by handlers (e.g. `repository.full_name.split('/').first` or the resolved `Repository`/`Stack` record) and reject the request (422) if it does not match `repository_owner`/the organization whose secret validated the signature.

### Proof of Concept
1. Shipit is configured with GitHub Apps/webhook secrets for organizations `attacker-org` and `victim-org` (multi-tenant deployment), each with its own `webhook_secret` (`lib/shipit/github_app.rb`).
2. Attacker knows `attacker-org`'s webhook secret (they own that GitHub App/organization's webhook config).
3. Attacker crafts a raw JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "after": "<sha>", ...}` and signs it with `attacker-org`'s secret using `Hook::DeliverySigner`-equivalent HMAC-SHA1.
4. POST to `/github/webhooks` with `X-Github-Event: push` and the forged `X-Hub-Signature`.
5. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s secret, and the HMAC validates (attacker knows this secret) — see `app/controllers/shipit/webhooks_controller.rb:24-62`.
6. The push handler processes `params['repository']['full_name'] == "victim-org/victim-repo"`, enqueuing `GithubSyncJob`/updating state for a stack the attacker does not control — cf. the `full_name`-driven repository resolution demonstrated in `test/controllers/webhooks_controller_test.rb:12-21`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
