### Title
`EnvironmentVariables#interpolate` silently falls back to host process `ENV`, leaking un-allowlisted secrets into task output - (File: `lib/shipit/environment_variables.rb`)

### Summary
`Shipit::EnvironmentVariables#interpolate` is used by `Command#interpolate_environment_variables` to substitute `$VAR` references inside deploy/task shell command lines defined in `shipit.yml`. When a referenced variable is absent from the per-task allowlisted `env` hash, it falls back to `ENV[variable]` — the Shipit Rails process's own environment — instead of failing or leaving the reference unresolved, and the substituted value is written verbatim into the task output stream visible in the UI.

### Finding Description
The broken binding: the value substituted for `$VAR` in a `Command`'s interpolated argument should equal a value present in the caller-supplied, allowlisted `env` hash (`value == @env[variable]`, undefined if `variable` is not a key of `@env`). Instead, at [1](#0-0) , the fallback block `@env.fetch(variable) { ENV[variable] }` makes the binding `value == @env[variable] || ENV[variable]`, so any variable name not in the allowlist resolves to the *host process*'s environment variable of the same name.

Code path:
1. `TaskCommands#perform`/`#install_dependencies` build `Command.new(command_line, env:, chdir:)` for each step returned by `deploy_spec.dependencies_steps!` / `@task.definition.steps`, which are sourced from the repository's `shipit.yml` ( [2](#0-1) ). The `env` merges `@stack.env`, fixed metadata, `deploy_spec.machine_env`, and `@task.env` ( [3](#0-2) ) — none of these is a wildcard, so any `$VAR` name in a step that isn't one of these known keys is unresolved by design.
2. `Command#start` calls `interpolated_arguments` → `interpolate_environment_variables(@args)` → `EnvironmentVariables.with(env).interpolate(argument)` for every shell argument ( [4](#0-3)  and [5](#0-4) ).
3. `interpolate` performs the fallback described above and `Shellwords.escape`s whatever it gets — `ENV[variable]` if not allowlisted — then that string becomes part of the argv passed to `PTY.spawn` ( [6](#0-5) ).
4. The spawned command's stdout/stderr is streamed by `Command#stream`/`#read_stream` and forwarded to the task's output writer, i.e. displayed in the Shipit UI ( [7](#0-6) , [8](#0-7) ).

Exploit flow: an attacker who can get a step of `shipit.yml` deployed/run for a stack (e.g. a review-app/PR-triggered task that checks out the PR branch and reads its `shipit.yml`, or any workflow where task/deploy steps are taken from attacker-controlled repository content) adds a step such as `echo $AWS_SECRET_ACCESS_KEY` or `echo $GITHUB_TOKEN`. That variable name is not a key in the merged `env` hash built by `TaskCommands#env`/`Stack#env`, so `interpolate` falls through to `ENV['AWS_SECRET_ACCESS_KEY']`, reading the Shipit Rails server process's real environment, and echoes it into task output that is rendered to any user who can view that task's output (typically the PR/task author, per the review-app model).

Why existing guards don't help: `EnvironmentVariables#permit` (used via `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs`) enforces an allowlist only on the *inbound* env hash supplied via API/UI when starting a deploy; it is never invoked by `interpolate`, which is a completely separate code path used purely for command-line templating and has no allowlist enforcement of its own — it deliberately widens scope to the full host `ENV` on any miss.

### Impact Explanation
Any host process environment variable (deployment credentials, `GITHUB_TOKEN`, database URLs, cloud credentials, etc., commonly exported for the Rails/Shipit process) can be exfiltrated into task output rendered in the UI, readable by whoever can view that task (in review-app / PR-driven deploy configurations, the PR author). This is a credential-exfiltration primitive and matches the Critical impact category ("exfiltration of ... deploy-time secrets"). The blast radius is scoped to whatever secrets are present in the Shipit host process ENV, and it is repeatable on every task run against that host, for every stack/task that executes attacker-influenced shell steps.

### Likelihood Explanation
Exploitability requires: (1) the deploy host process ENV must actually contain a sensitive value, and (2) the attacker must be able to get a shell command line into a task/deploy step that is actually executed by the target stack (i.e., control over `shipit.yml` content that the stack executes, such as via a review-app deploy of a PR branch). Both are plausible operational configurations already anticipated by the question's threat model. Given those preconditions, the attack costs a single PR/branch push and is deterministic and repeatable — no race conditions or guessing required, since env var names for common secrets are highly predictable.

### Recommendation
Remove the silent fallback to the host process `ENV` in `EnvironmentVariables#interpolate`. Unresolved variables should either raise (consistent with `sanitize_env_vars`'s `NotPermitted` behavior) or resolve to an empty string, never to `ENV[variable]`, since `interpolate` has no concept of an allowlist for its lookups today.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (additional test)
test 'interpolate does not leak host ENV for variables outside the allowlisted env' do
  ENV['SECRET_ENV_VAR'] = 'leaked-secret'
  begin
    allowlisted_env = { 'FOO' => '1' } # SECRET_ENV_VAR intentionally absent
    result = EnvironmentVariables.with(allowlisted_env).interpolate('$SECRET_ENV_VAR')
    # Binding under test: result should equal allowlisted_env['SECRET_ENV_VAR'] (nil/undefined),
    # never ENV['SECRET_ENV_VAR'].
    refute_equal 'leaked-secret', result
  ensure
    ENV.delete('SECRET_ENV_VAR')
  end
end

# End-to-end variant using Command, mirroring test/unit/command_test.rb style
test 'Command does not leak host ENV into task output for unallowlisted variables' do
  ENV['SECRET'] = 'leaked'
  begin
    output = Command.new('echo', '$SECRET', chdir: Dir.tmpdir, env: {}).run
    refute_includes output, 'leaked'
  ensure
    ENV.delete('SECRET')
  end
end
```
Both assertions currently fail against the code at [9](#0-8) , confirming the vulnerability: the equality `value == @env.fetch(variable)` is broken by the `{ ENV[variable] }` fallback.
