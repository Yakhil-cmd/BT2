### Title
Argument-smuggling in `scripts/gh.sh` flag parser bypasses the flag allow-list and repository scoping - ([File: scripts/gh.sh])

### Summary
The value-consuming branch of `scripts/gh.sh`'s argument parser (`--state`, `--limit`, `--label`) appends the *next* argument to `FLAGS` unconditionally, without checking it against `ALLOWED_FLAGS`. An attacker who can influence the Claude agent's tool-call arguments (via prompt injection in an issue/PR body processed by `.claude/commands/triage-issue.md` or `.claude/commands/dedupe.md`) can smuggle an arbitrary extra flag — most notably `--repo=<other-repo>` — into the final `gh` invocation, bypassing the wrapper's repo-scoping guarantee and its flag allow-list.

### Finding Description
`scripts/gh.sh` enforces two layers of restriction: (1) the subcommand pair must be exactly `issue view`, `issue list`, `search issues`, or `label list` [1](#0-0) , and (2) any subsequent `-*` argument must match `ALLOWED_FLAGS` [2](#0-1) . The subcommand check is solid — it is an exact string match on the literal `$1 $2`. The flag check, however, has a bypass: when a flag that expects a value (`--state`, `--limit`, `--label`) is matched, `skip_next` is set to `true`, and on the *next* loop iteration the parser blindly appends that argument to `FLAGS` without any validation against `ALLOWED_FLAGS`:

```
if [[ "$skip_next" == true ]]; then
    FLAGS+=("$arg")
    skip_next=false
``` [3](#0-2) 

This means an argument like `--limit --repo=attacker/other-repo` causes `--repo=attacker/other-repo` to be accepted as the "value" of `--limit` and injected into `FLAGS` unchecked. For the `search issues` branch, this flag is appended *after* the wrapper's own explicit `--repo "$REPO"`:

```
gh "$SUB1" "$SUB2" "$QUERY" --repo "$REPO" "${FLAGS[@]}"
``` [4](#0-3) 

Since `gh` (like most Cobra/pflag-based CLIs) takes the last occurrence of a repeated flag, the attacker-supplied `--repo=` value overrides the wrapper's intended repo scope. For `issue view`, `issue list`, and `label list`, there is no explicit `--repo` in the final `gh` call at all (repo scoping relies solely on the `GH_REPO` env var) [5](#0-4) , so a smuggled `--repo=` flag there directly determines which repository `gh` operates against, since CLI flags generally take precedence over the `GH_REPO`/`GH_HOST` env vars.

The attacker-controlled input path is the issue/PR body text that flows into the agent's context via `$ARGUMENTS` in `.claude/commands/triage-issue.md` [6](#0-5)  and the equivalent flow in `.claude/commands/dedupe.md` [7](#0-6) . Both grant `Bash(./scripts/gh.sh:*)`, meaning Claude Code's tool-permission layer allows any argument string after `./scripts/gh.sh`, deferring all argument-level enforcement to the wrapper script itself. If a malicious issue body persuades/injects the agent into emitting an extra `--limit`/`--state`/`--label` flag followed by a `--repo=...` value, the wrapper's own parser — not the Claude tool-permission allow-list — fails to stop it.

### Impact Explanation
This breaks the core security property the wrapper documents in its header ("All commands are scoped to the current repository via `GH_REPO`") [8](#0-7) . An attacker embedding prompt-injection content in a public issue can cause the automation's `gh` token (whatever repos/orgs it has read access to, e.g. via `gh auth` scopes used by the CI/automation identity) to read `issue view`, `issue list`, `search issues`, or `label list` data from a repository other than the one the workflow is scoped to — including potentially private repositories the automation credential has access to. This is unauthorized cross-repository information disclosure reachable purely from untrusted issue/PR text, matching a trust-boundary-bypass / secret-disclosure class impact.

### Likelihood Explanation
- No privileged access is required; only the ability to open/comment on an issue that the triage/dedupe automation processes.
- Exploitation depends on the LLM agent choosing to append an extra value-taking flag with an attacker-suggested value — a realistic outcome of prompt injection since the commands document these exact flags (`--state`, `--limit`, `--label`) as legitimate and the agent has latitude in choosing flag values (e.g., `--limit`) while the smuggled value is attacker-influenced text embedded in issue content.
- The bug is 100% reproducible once the argv reaches the script — it's a deterministic parser flaw, not probabilistic.

### Recommendation
In `scripts/gh.sh`, validate the "value" argument taken during `skip_next` handling — reject it if it starts with `-` (i.e., looks like another flag) instead of unconditionally appending it to `FLAGS`. Additionally, explicitly pass `--repo "$REPO"` as the *last* argument in every `gh` invocation branch (or otherwise ensure no later `--repo` flag can override it), so that even a successfully smuggled `--repo=` value cannot take precedence.

### Proof of Concept
Integration test (bash) plan:
1. Set `GH_REPO=owner/expected-repo`.
2. Stub `gh` as a script that just echoes its received argv to a file.
3. Invoke `./scripts/gh.sh issue list --limit --repo=owner/attacker-repo --state open`.
4. Assert the stubbed `gh` invocation's argv either (a) is rejected by `gh.sh` before reaching `gh`, or (b) does not contain `--repo=owner/attacker-repo` as an effective override of `GH_REPO`.
   - Current (vulnerable) behavior: the stub receives `issue list --limit --repo=owner/attacker-repo --state open`, i.e., the injected `--repo=` flag reaches `gh` unfiltered — test should fail against current code, confirming the bug.
5. Repeat for `search issues "q" --limit --repo=owner/attacker-repo`, asserting that the final `--repo` argument passed to `gh` is not the attacker-controlled repo.
