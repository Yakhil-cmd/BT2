### Title
Webhook signature verification is scoped to a GitHub organization but downstream handlers (`StatusHandler`, `PushHandler`, PR handlers) act on repository/commit data that is never checked against that organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is a direct analog of the discriminator conflict: a partial/weak check (verifying the payload against the wrong or overly permissive scope) is trusted to imply a stronger guarantee (that the entire payload, including unrelated fields, is safe to act on). Here, the "discriminator" is the organization used to select the HMAC secret; the "account data" that gets overwritten is another organization's `Commit`/`Stack` state.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config/secret to verify against using only `repository.owner.login` (or `organization.login`) taken from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` only raises if the organization is entirely unconfigured; if the organization is configured but has no `webhook_secret` set (explicitly documented as optional in `docs/setup.md`), `verify_webhook_signature` returns `true` unconditionally: [3](#0-2) [4](#0-3) 

Once the request passes this org-scoped check, the raw JSON body is dispatched to event handlers that do not re-validate that the acted-upon repository/commit belongs to the same organization that was just verified. Critically, `StatusHandler` finds commits to update purely by SHA, with no repository/organization scoping at all: [5](#0-4) 

This breaks the binding: **organization that authenticated == repository/commit that is written**. An attacker who controls (or is granted installation of the Shipit GitHub App on) any organization configured with no `webhook_secret` can submit an unauthenticated `status` webhook whose `repository.owner.login` matches their own harmless org (satisfying `verify_signature` trivially), while the `sha` field references a commit belonging to an entirely different, victim-controlled `Stack`/`Repository`. `Commit.create_status_from_github!` will then apply a forged "success" status to that unrelated commit, and via `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`, this can trigger `Stack#trigger_continuous_delivery` for any stack with `continuous_deployment: true`, resulting in an unauthorized deploy.

### Impact Explanation
This crosses the "unauthorized deploy" bar explicitly called out in scope: an attacker who never had write access to the victim repository can force a deploy of a victim's stack by forging a commit-status webhook whose organizational signature scope does not match the repository actually mutated. This matches the Critical impact category (unauthorized deploy) defined in scope.

### Likelihood Explanation
Exploitability depends on the deployment having at least one GitHub organization configured with no `webhook_secret` (explicitly supported/documented as optional) or an org the attacker otherwise has legitimate install access to, and on knowing the SHA of a commit tracked by the target stack (SHAs are public information visible via git/GitHub). Given multi-org configurations are an officially supported, documented feature (`docs/setup.md`) and `webhook_secret` is optional per-org, this is a realistic misconfiguration risk rather than a purely theoretical one, though it requires the org-level `webhook_secret` gap to exist.

### Recommendation
Bind the signature-verification scope to the actual entity being mutated: after determining which repository/commit a handler intends to modify, verify that its owning organization matches the organization whose secret validated the incoming signature (not just an org guessed from an attacker-controlled top-level field). Additionally, `StatusHandler` (and any other handler) should scope commit/stack lookups by the verified repository, not by SHA alone, and `verify_webhook_signature` should not silently return `true` when a per-organization secret is unset in multi-org installations - it should require a globally-enforced minimum verification even when optional secrets are blank, analogous to enforcing a minimum discriminator length regardless of configured size.

### Proof of Concept
1. Deploy Shipit with two GitHub orgs configured under `secrets.yml`: `attacker-org` (no `webhook_secret` set) and `victim-org` (has stacks with `continuous_deployment: true`).
2. Attacker (who need only be able to install the Shipit App on `attacker-org`, or exploit any org lacking a secret) sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" },
  "sha": "<sha of a commit belonging to victim-org's tracked stack>",
  "state": "success",
  "context": "ci/forged"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the header value. [1](#0-0) 
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no repository filter and applies the forged "success" status to the victim's commit, potentially triggering `trigger_continuous_delivery` and an unauthorized deploy. [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
