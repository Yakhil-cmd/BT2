### Title
Deterministic panic from unchecked u128 overflow in tower reward-points scaling can crash all validators at epoch boundary - ([File: runtime/src/inflation_rewards/mod.rs])

### Summary
`calculate_stake_rewards` scales `tower_points` by `point_value.rewards` and divides by `point_value.points` using `checked_mul(...).expect(...)` and `.checked_div(...).unwrap()`, panicking rather than saturating or gracefully degrading if the u128 intermediate product overflows.

### Finding Description
In the Tower reward path, `calculate_stake_rewards` computes the final reward for a stake account as:

```
tower_points
    .checked_mul(u128::from(point_value.rewards))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points)
    .unwrap()
``` [1](#0-0) 

The same overflow-prone pattern (`checked_mul(...).expect(...)`) is repeated for the `MigrationEpoch` branch just below it [2](#0-1) .

`tower_points` itself is an accumulation of `stake_amount * earned_credits` (both cast to u128) summed across every un-redeemed epoch of credits for a delegation [3](#0-2) . This value grows with total effective stake and with the number of epochs/credits accumulated (e.g., if reward redemption is skipped for a long period). It is then multiplied again by `point_value.rewards` (the total inflation lamports to be distributed for the epoch, up to a u64) before dividing by `point_value.points` (total network points for the epoch). Unlike the Bancor `calcExpDecayRewards` bug — where an ever-growing `timeElapsed` relative to a fixed `halfLife` eventually pushes the exponent input past a hard-coded bound and reverts a single transaction — here the analog quantity that grows without bound over the life of the network (total stake, cumulative unredeemed credits, and per-epoch inflation lamports as the token supply and stake pool grow) can eventually push the `u128` product of `tower_points * point_value.rewards` past `u128::MAX`.

The critical difference in severity is the failure mode: because this computation happens inside `Bank::calculate_stake_rewards_and_commissions` at epoch-boundary reward processing, a `.expect()`/`.unwrap()` panic here is not a transaction revert that a client can retry — it is a Rust panic in validator/runtime code executed identically and deterministically by every validator processing the same epoch boundary, which will bring down (or fail to advance) every node in the cluster at the same point simultaneously.

### Impact Explanation
If this panic is ever triggered, it will be triggered by all validators identically at the same epoch transition (since epoch-boundary reward calculation is a deterministic, consensus-critical step), producing a full cluster halt at the epoch boundary. This falls squarely into the accepted "epoch-boundary halt" impact category.

### Likelihood Explanation
Likelihood is low under today's stake and supply levels (analogous to the client's original "safe for practical timeframes" assessment of the Bancor bug), because current total network stake and current per-epoch inflation reward amounts keep the u128 product comfortably below `u128::MAX`. However, like the original bug, this is a design landmine rather than a bounded-safe computation: total stake, cumulative supply (inflation-derived lamports), and unredeemed credit accumulation (e.g., due to a period of skipped/delayed reward redemption) are values that grow monotonically over the life of the network and are not hard-capped against this specific arithmetic limit, so the risk increases over time exactly as in the reported analog.

### Recommendation
Replace the `.expect()`/`.unwrap()` panics in the point-value scaling arithmetic with saturating or graceful-degradation logic (e.g., clamp to `u128::MAX` or split the multiply/divide differently to avoid overflow, similar to the recommended fix of returning `totalRewards` directly rather than reverting/panicking in the analog report), so that a large-but-legitimate accumulation of stake/credits/rewards cannot crash validators deterministically.

### Proof of Concept
A conceptual trigger: a delegation with near-maximum effective stake that goes unredeemed across many epochs so that `tower_points` (stake × cumulative earned credits) grows large, combined with a large `point_value.rewards` value for that epoch, causes:
```
tower_points.checked_mul(u128::from(point_value.rewards))
```
at `runtime/src/inflation_rewards/mod.rs:303` to return `None`, triggering the `.expect("Rewards intermediate calculation should fit within u128")` panic [4](#0-3) . The existing unit test `calculate_rewards_tests` already demonstrates this exact panic path is reachable with extreme (but not necessarily impossible in the long run) `stake`/`rewards`/`credits` combinations: `#[test_case(u64::MAX, 1_000, u64::MAX => panics "Rewards intermediate calculation should fit within u128")]` [5](#0-4) .
