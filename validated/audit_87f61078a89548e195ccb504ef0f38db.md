### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while event handlers act on `repository.full_name` — organization authenticated ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on an attacker-controlled field inside the JSON body itself (`repository.owner.login`, falling back to `organization.login`), then uses that organization's `webhook_secret` to validate the whole raw payload. But once the request is accepted, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by `PushHandler` and others to resolve the target `Stack`/`Repository`) reads a *different* field, `repository.full_name`, which is never cross-checked against the organization used for signature selection. [1](#0-0) [2](#0-1) 

### Finding Description
In a multi-organization deployment (the documented config schema supporting several GitHub orgs, each with its own `webhook_secret`, as shown in `config/secrets.development.shopify.yml`), `Shipit.github(organization:)` looks up a distinct `GitHubApp` (and therefore a distinct `webhook_secret`) per organization key. [3](#0-2) 

`WebhooksController#verify_signature` derives the org used to select that secret purely from the JSON body:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that resolved organization:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [5](#0-4) 

However, the field that actually determines *which repository/stack the payload affects* is a completely separate key, read later by the handler base class:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

Nothing in the controller or the handler pipeline asserts that `repository.full_name`'s owner segment equals `repository.owner.login`/`organization.login` used for signature selection. The equality that should hold is:
`organization authenticated (repository.owner.login / organization.login used for secret lookup) == organization that owns the repository actually written (repository.full_name used by PushHandler/etc.)`

This is exactly the deployment-trust binding class called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
If a Shipit instance is configured with multiple GitHub organizations (a documented and supported configuration) and at least one configured organization has no `webhook_secret` set (also a documented, supported configuration — `webhook_secret: # nil` appears in both example secrets files), an unauthenticated attacker can submit a POST to `/webhooks` with `X-Github-Event: push` and a body where `repository.owner.login` is set to the org without a secret (or any org name that resolves to an app with a blank secret) while `repository.full_name` names a different, tracked repository belonging to another (secret-protected) organization. `verify_webhook_signature` returns `true` unconditionally for the secret-less org, `check_if_ping`/`drop_unhandled_event` pass, and `PushHandler` proceeds to call `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching that `repository.full_name` and branch — an unauthenticated write influencing which commit Shipit considers the head of a branch, without ever presenting a valid signature for the organization that actually owns that repository.

This would qualify as "an unauthorized deploy" pathway (continuous-deployment stacks sync/deploy against attacker-chosen `expected_head_sha`) if such a configuration exists, since `GithubSyncJob`/`sync_github` chain into deploy triggering for continuously-deployed stacks.

### Likelihood Explanation
Exploitability is entirely conditional on host configuration: it requires (a) a multi-organization `secrets.github` setup, and (b) at least one configured organization having a blank `webhook_secret`. Both conditions are explicitly presented as supported/example configurations in this engine's own docs and secrets templates, so this is not solely a "host misconfiguration outside documented use" — the engine ships/documents the vulnerable combination itself. Absent a secret-less organization, the bug has no exploitable path (signature check would fail). This bounds likelihood to a specific, but documented-as-valid, deployment topology.

### Recommendation
Bind the organization used for signature verification to the same repository identity used by event handlers: derive both from `repository.full_name`'s owner segment (or require them to match), and reject requests where `repository.owner.login`/`organization.login` disagrees with the owner segment of `repository.full_name`. Additionally, treat a blank `webhook_secret` for an organization as "require explicit opt-in for unsigned webhooks scoped to that organization's own repositories only," rather than a blanket bypass usable to smuggle payloads referencing arbitrary other repositories.

### Proof of Concept
Conceptual request (requires a target instance with org `no-secret-org` configured with a blank `webhook_secret`, and `victim-org/victim-repo` tracked as a Shipit stack):
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature required)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "no-secret-org" }
  }
}
```
`repository_owner` resolves to `no-secret-org` → `verify_webhook_signature` short-circuits to `true` (no secret configured) → `PushHandler` resolves the stack via `repository.full_name = "victim-org/victim-repo"` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")`, entirely unauthenticated with respect to `victim-org`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
