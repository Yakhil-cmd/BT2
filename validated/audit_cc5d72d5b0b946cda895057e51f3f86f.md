Confirmed: `feed_name` and `value` supplied to the oscript `data_feed`/`in_data_feed` formula operators come directly from `evaluate(params[param_name].value, ...)` in `formula/evaluation.js:600-720`, i.e. they can be arbitrary strings built by the AA author's formula (e.g. via `concat()` of `trigger.data.*` fields under an unprivileged trigger sender's control). Unlike the on-chain `data_feed` message payload — which is explicitly checked for `\n` in `validation.js:1936,1943` and `aa_validation.js:100,109` — the formula-side validators `validateDataFeed`/`validateDataFeedExists` in `formula/validation.js:26-129` only check `value.trim() === ''`, never rejecting `\n`. These unsanitized strings are then concatenated directly into `\n`-delimited LevelDB key prefixes in `data_feeds.js` (`dataFeedByAddressExists` line 139, `readDataFeedByAddress` line 292/305), so an attacker-controlled `\n` breaks the intended key-segment boundaries.

### Title
Newline injection in oscript `data_feed`/`in_data_feed` params breaks key-delimiter structure allowing AA data-feed spoofing - (File: data_feeds.js)

### Summary
The oscript `data_feed`/`in_data_feed` formula operators accept a `feed_name` and `value` that are evaluated from arbitrary trigger-controlled expressions and are not checked for embedded `\n` characters before being spliced into `\n`-delimited LevelDB key prefixes used to look up oracle-posted data feeds.

### Finding Description
When an AA formula uses `data_feed[[...]]` or `in_data_feed[[...]]`, the parameter values are computed via `evaluate()` in [1](#0-0) , permitting `feed_name`/`feed_value` to be derived from `trigger.data` (fully attacker-controlled for a trigger sender). Validation of these parameters at formula-compile time is done by `validateDataFeed`/`validateDataFeedExists` in [2](#0-1)  and [3](#0-2) , which check only for empty strings — there is no rejection of `\n` in `feed_name` or `feed_value`, unlike the on-chain `data_feed` message payload validators at [4](#0-3)  and [5](#0-4)  which explicitly reject `\n`.

These unsanitized values flow into `dataFeeds.readDataFeedValue`/`dataFeedExists`, and ultimately into key-prefix construction that uses `\n` as the field delimiter: [6](#0-5)  builds `key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value` and [7](#0-6)  similarly builds `key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value` for existence checks. A `feed_name` (or a value that gets embedded before the type/value fields) containing `\n` inserts extra pseudo-fields into the key, letting the effective LevelDB range scan (`gte`/`lte`/`gt`/`lt` in [8](#0-7) ) span into unintended type/value/mci segments of the keyspace — the same "structural query injection via unescaped delimiter" bug class as the reported LDAP query injection, where an unsanitized filter value breaks out of its intended field boundary and alters query semantics.

### Impact Explanation
This lets an unprivileged AA trigger sender manipulate which data-feed value the AA formula effectively reads (matching a different feed name/type/mci than the AA author intended), since the query's field boundaries are corrupted by the injected delimiter. Because AA logic that depends on `data_feed`/`in_data_feed` results commonly gates fund transfers, price lookups, or conditionals, an attacker able to steer the "matched" oracle value can bias AA execution — this maps to potential AA fund loss/misbehavior, consistent with the class of impacts this scan accepts. It does not directly cause double-spend or consensus divergence, so its severity is bounded by the specific AA's use of the mismatched feed value.

### Likelihood Explanation
Reachable via a completely unprivileged path: any account can send an AA trigger with attacker-chosen `data` fields, and if the target AA's oscript formula builds its `data_feed`/`in_data_feed` `feed_name` or `feed_value` parameter from trigger data (a common and encouraged oscript pattern, e.g. `data_feed[[oracles=..., feed_name=trigger.data.name, ...]]`), the `\n` is never stripped before it reaches the LevelDB key. No special privileges, timing, or race conditions are required.

### Recommendation
Add explicit `\n` rejection for `feed_name` and any string `feed_value`/`oracles` values inside `validateDataFeed` and `validateDataFeedExists` in `formula/validation.js`, mirroring the checks already present in `validation.js` (`indexOf('\n') >= 0`) and `aa_validation.js`, so formula-supplied data-feed lookup parameters cannot contain the LevelDB key delimiter.

### Proof of Concept
1. Deploy an AA whose formula includes something like:
   `data_feed[[oracles="ORACLE_ADDRESS", feed_name=trigger.data.name, feed_value=1, ifnone=0]]`
2. Send a trigger unit to the AA with `data.name` set to a string containing an embedded `\n`, e.g. `"price\nn\n<crafted-encoded-double>\n<crafted-mci>"`.
3. Because `validateDataFeed` (`formula/validation.js`) never rejects `\n`, the formula compiles/executes, and `feed_name` reaches `data_feeds.js`'s key-prefix construction with the injected delimiter, causing the LevelDB range scan to match keys outside the intended `feed_name`/type boundary — returning a value/mci the AA author never intended to be matched, which the AA logic then acts on.

function validateDataFeed(params) {
	var complexity = 1;
	if (params.oracles && params.feed_name) {
		for (var name in params) {
			var operator = params[name].operator;
			var value = params[name].value;
			if (Decimal.isDecimal(value)){
				if (!isFiniteDecimal(value))
					return {error: 'not finite', complexity};
				value = toDoubleRange(value).toString();
			}
			if (operator !== '=') return {error: 'not =', complexity};
			if (['oracles', 'feed_name', 'min_mci', 'feed_value', 'ifseveral', 'ifnone', 'what', 'type'].indexOf(name) === -1)
				return {error: 'unknown df param: ' + name, complexity};
			if (typeof value !== 'string')
				continue;
			switch (name) {
				case 'oracles':
					if (value.trim() === '') return {error: 'empty oracle', complexity};
					var addresses = value.split(':');
					if (addresses.length === 0) return {error: 'empty oracle list', complexity};
				//	complexity += addresses.length;
					if (!addresses.every(ValidationUtils.isValidAddress)) return {error: 'oracle address not valid', complexity};
					break;

				case 'feed_name':
					if (value.trim() === '') return {error: 'empty feed name', complexity};
					break;

				case 'min_mci':
					if (!(/^\d+$/.test(value) && ValidationUtils.isNonnegativeInteger(parseInt(value)))) return {
						error: 'bad min_mci',
						complexity
					};
					break;

				case 'feed_value':
					break;
				case 'ifseveral':
					if (!(value === 'last' || value === 'abort')) return {error: 'bad ifseveral: ' + value, complexity};
					break;
				case 'ifnone':
					break;
				case 'what':
					if (!(value === 'value' || value === 'unit')) return {error: 'bad what: ' + value, complexity};
					break;
				case 'type':
					if (!(value === 'string' || value === 'auto')) return {error: 'bad df type: ' + value, complexity};
					break;
				default:
					throw Error("unrecognized name after checking: "+name);
			}
		}
		return {error: false, complexity};
	} else {
		return {error: 'no oracles or feed name', complexity};
	}
}
