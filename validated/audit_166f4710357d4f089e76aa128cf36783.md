### Title
Webhook signature is verified against an organization derived from the payload while the acted-upon repository is taken from a different, unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the untrusted, attacker-controlled JSON body. Every event handler, however, resolves the `Repository`/`Stack` that will actually be synced or mutated using a *different* field of the same body: `repository.full_name`. Nothing in the code enforces that `repository.owner.login` (used for signature-secret selection) is consistent with `repository.full_name` (used to pick the target repository). In a multi-organization Shipit deployment, this lets a holder of one organization's webhook secret forge a signature that Shipit accepts, while pointing the payload's `full_name` at a stack belonging to a completely different organization.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and uses it to select the signing secret: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That value is fed into `Shipit.github(organization: repository_owner)`, which looks up the per-organization `webhook_secret` from `secrets.github` when Shipit is configured for multiple GitHub organizations: [3](#0-2) 

Once the HMAC check passes, the raw JSON `params` are handed unmodified to every registered handler for the event: [4](#0-3) 

All handlers resolve which `Repository`/`Stack` to act on via `Handler#repository_name`, which reads `repository.full_name` — a separate JSON field from the one used for signature-secret selection: [5](#0-4) 

For example `PushHandler` looks up stacks for that repository and immediately triggers `sync_github`: [6](#0-5) 

The binding the app is implicitly assuming is:
`organization authenticated by verify_signature (repository.owner.login) == organization that owns the repository acted on (prefix of repository.full_name)`

This equality is never checked. Since both fields are attacker-controlled inside the same JSON body (the signature covers the raw body bytes as a whole, but doesn't enforce internal field cross-consistency), an attacker who has legitimately obtained (or brute-forced/leaked) the `webhook_secret` for *any one* configured organization (e.g. a low-trust org they also administer, per the "Using Multiple GitHub Applications" configuration documented in `docs/setup.md`) can craft a payload where:
- `repository.owner.login` = the organization whose secret they hold (so `verify_signature` succeeds), and
- `repository.full_name` = `"other-org/some-other-repo"` (a repository/stack tracked under a different, higher-trust organization).

The handler will act on the second organization's stack despite the signature only proving control of the first organization's secret.

### Impact Explanation
This breaks the trust boundary between separately configured GitHub organizations/webhook secrets in a multi-tenant Shipit deployment. An attacker who compromises or legitimately controls the webhook secret of one onboarded organization can forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that are processed as if they originated from a repository belonging to a different organization. Depending on handler, this can trigger unauthorized `GithubSyncJob` runs, alter commit statuses used as deploy gates, or create/modify pull-request-driven review stacks and `EnvironmentVariables`/membership records tied to another organization's stacks — i.e., cross-repository/cross-organization writes that the per-organization webhook secret isolation was meant to prevent. This matches the "cross-repository writes" / unauthorized-state-change class explicitly listed as in-scope Critical/High impact.

### Likelihood Explanation
Requires the attacker to already hold a valid `webhook_secret` for at least one organization configured in the Shipit deployment (a realistic scenario only when Shipit brokers webhooks for multiple, separately-trusted GitHub organizations, as explicitly supported and documented in `docs/setup.md` "Using Multiple GitHub Applications"). Given that precondition, exploitation is a single crafted HTTP POST with no further privilege needed — likelihood is moderate and entirely dependent on the multi-org deployment model being in use.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after determining the organization used to validate the signature, cross-check it against the organization prefix of `repository.full_name` (and/or the resolved `Repository#owner`) before dispatching to handlers, rejecting the event with 422 if they diverge. Alternatively, resolve the target `Repository` first and derive the signing organization strictly from that repository's known owner rather than from a raw client-supplied field.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `orgA` and `orgB`, each with its own `webhook_secret` per `docs/setup.md`'s multi-app schema.
2. Attacker has (or leaks) `orgA`'s `webhook_secret` (e.g. because they administer a low-trust repo under `orgA` that is also onboarded to this Shipit instance).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/production-repo"
  }
}
```
4. Attacker signs the raw body with `orgA`'s `webhook_secret` and sends it as `X-Hub-Signature`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature.
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` as `"orgB/production-repo"` via `payload.dig('repository', 'full_name')` and calls `stack.sync_github(expected_head_sha: ...)` on `orgB`'s stack — a repository the attacker never had a valid secret for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
