## Title
Off-by-2-bytes AA `storage_size` accounting mismatch between `aa_composer.js:updateStorageSize()` and `aa_composer.js:checkStorageSizes()` crashes all full nodes - (File: aa_composer.js)

### Summary
This is the same bug class as the ZK-EVM `MAXMEM` issue: an internal accounting value (`MAXMEM` in the ROM, `storage_size` in ocore) is updated by one code path using a formula that doesn't match the formula used by a second, independent code path that later audits/asserts on that same value. In the ROM this mismatch broke a plookup range check and halted proving; in ocore the mismatch between the AA state-var write accounting and the periodic storage-size audit deterministically throws an uncaught exception on every full node, crashing the whole network's full-node population.

### Finding Description
When an AA persists a new state variable, it is written to the key-value store with a 2-byte type prefix (`"s\n"`, `"n\n"`, or `"j\n"`) prepended to the value: [1](#0-0) 

The size accounting function used to update the `aa_addresses.storage_size` column, however, computes the size of a *new* value without adding these 2 prefix bytes: [2](#0-1) [3](#0-2) 

For a brand-new state variable (`state.original_old_value === undefined`), the code does:
```
delta_storage_size += var_name.length + newSize;
```
which omits the 2-byte type-prefix that is actually persisted in the key-value store for that key. Deletion of a never-updated variable has the mirror-image omission (missing `-2`). Only in-place *updates* of an already-existing variable cancel the offset correctly (prefix bytes appear on both sides of the subtraction). Consequently, every state variable that is *created and never deleted* — which is the overwhelmingly common pattern for AA storage (counters, per-user balances, order books, etc.) — leaves the recorded `storage_size` permanently 2 bytes lower than the number of bytes actually written to the key-value store.

The independent audit routine, `checkStorageSizes()`, computes the *true* size directly from the key-value store by reading raw key/value byte lengths and subtracting the 2-byte type prefix explicitly: [4](#0-3) 

It then compares this ground-truth size to the `aa_addresses.storage_size` value written by `updateStorageSize()` and calls `throw Error("storage size mismatch on ...")` on any discrepancy — a plain, uncaught `throw` inside an async callback.

This function is scheduled unconditionally on every full node: [5](#0-4) 

An uncaught exception anywhere in the process is intentionally treated as fatal and re-thrown to kill the process: [6](#0-5) 

### Impact Explanation
Because the `storage_size` divergence accumulates deterministically and identically on every node processing the exact same AA state changes (the AA execution engine is meant to be fully deterministic across all full nodes), this is not a data-dependent or peer-dependent fault: as soon as any AA that any unprivileged user has ever triggered creates and keeps at least one persistent state variable, the recorded `storage_size` for that AA's address diverges from the true kv-store size by 2 bytes. The very next scheduled run of `checkStorageSizes()` (every 10 minutes on every full node) detects the divergence and throws, crashing that node process. Since the divergence is produced identically by every node executing the same AA triggers, essentially all full nodes in the network converge on the same crash within one `600s` interval of any AA creating persistent storage — a network-wide denial of service that prevents new units/state transitions from being confirmed, matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
No privileged access is required. Any address (an ordinary AA trigger sender) triggering any AA that stores at least one persistent (never-deleted) state variable — an extremely common and unavoidable AA pattern already present in many deployed AAs (e.g. balance counters in `order_book_exchange.oscript`, `payment_channels.oscript` samples) — is sufficient to introduce the divergence. Full-node crashes then occur automatically and deterministically via the scheduled audit, with no attacker action needed beyond the ordinary use of any stateful AA. Likelihood is effectively certain over time given the number of live AAs that keep persistent state.

### Recommendation
Make `updateStorageSize()`'s per-variable delta calculation consistent with the actual bytes persisted by `getTypeAndValue()`/read back by `checkStorageSizes()`: include the 2-byte type-prefix in the size delta whenever a variable transitions from "does not exist" to "exists" (add `+2`) and whenever a variable transitions from "exists" to "deleted" (subtract the full `var_name.length + getValueSize(...) + 2`). Alternatively, compute `newSize`/`oldSize` directly from `getTypeAndValue(...).length` (the actual serialized byte length) in all three branches of `updateStorageSize()` so a single formula is shared between the write path and `checkStorageSizes()`, eliminating the possibility of the two independently-maintained size formulas drifting apart. Additionally, `checkStorageSizes()`'s `throw Error(...)` on mismatch should not be allowed to crash the full node process outright (e.g. downgrade to a logged alert or a recoverable resync path) so that any future or historical divergence of this kind cannot become a network-wide fatal event.

### Proof of Concept
1. Deploy any AA whose `state` formula sets at least one state variable that is never subsequently deleted, e.g. the pattern used in `test/samples/order_book_exchange.oscript`:
```
var[$base_key] = var[$base_key] + trigger.output[[asset=base]];
``` [7](#0-6) 
2. Send a trigger unit from any unprivileged address to this AA that causes creation of a new state variable key (first time `$base_key` is set for that user/asset).
3. `updateStorageSize()` persists `aa_addresses.storage_size` under-counted by 2 bytes relative to the bytes actually written to the kv-store for that key (`aa_composer.js:1552-1558`).
4. After the next `checkStorageSizes()` run (`setInterval(checkStorageSizes, 600*1000)`), the computed `assocSizes[address]` from the kv-store will not equal `row.storage_size`, triggering `throw Error("storage size mismatch on ...")` (`aa_composer.js:1941`).
5. This uncaught exception propagates to the process-level `uncaughtException` handler in `network.js`, which deliberately re-throws to crash the process (`network.js:4530-4543`), and the same sequence occurs on every full node that has processed the same trigger, since AA execution is deterministic across nodes.

function checkStorageSizes() {
	mutex.lockOrSkip(['checkStorageSizes'], function (unlock) {
		db.takeConnectionFromPool(function (conn) { // block conection for the entire duration of the check
			var options = {};
			options.gte = "st\n";
			options.lte = "st\n\uFFFF";

			var assocSizes = {};
			var handleData = function (data) {
				var address = data.key.substr(3, 32);
				var var_name = data.key.substr(36);
				if (!assocSizes[address])
					assocSizes[address] = 0;
				assocSizes[address] += var_name.length + data.value.length - 2; // -2 for type and \n
			}
			var stream = kvstore.createReadStream(options);
			stream.on('data', handleData)
				.on('end', function () {
					conn.query("SELECT address, storage_size FROM aa_addresses", function (rows) {
						rows.forEach(function (row) {
							if (!assocSizes[row.address])
								assocSizes[row.address] = 0;
							if (row.storage_size !== assocSizes[row.address])
								throw Error("storage size mismatch on " + row.address + ": db=" + row.storage_size + ", kv=" + assocSizes[row.address]);
						});
						conn.release();
						unlock();
					});
				})
				.on('error', function (error) {
					throw Error('error from data stream: ' + error);
				});
		});
	});
}
