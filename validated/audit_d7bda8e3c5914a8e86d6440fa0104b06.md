### Title
Webhook signature verification is bound to `repository.owner.login`, but event processing trusts the independent `repository.full_name` field, allowing cross-organization status/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, a field read from the untrusted, attacker-supplied JSON body itself. [1](#0-0) [2](#0-1)  The actual repository/stack the payload acts on is instead derived from a *different, independently-controlled* field of the same body, `repository.full_name`, read inside `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`. [3](#0-2)  Nothing ties these two fields together, so a webhook whose HMAC is valid for organization A's secret can carry a `repository.full_name` pointing at organization B's repository/stack, and Shipit will process it as if it legitimately originated from B.

### Finding Description
Shipit supports being configured with credentials (including a distinct `webhook_secret`) per GitHub organization, as shown in the multi-org secrets schema and `GitHubApp` model. [4](#0-3) [5](#0-4) 

`WebhooksController#verify_signature` computes `repository_owner` from the JSON payload (`repository.owner.login`, falling back to `organization.login`), looks up the `GitHubApp` config for *that* org, and verifies the HMAC signature against *that org's* secret: [6](#0-5) 

Once the signature is accepted, `WebhooksController#create` dispatches the raw parsed body to the registered handlers for the event, unchanged: [7](#0-6) 

Handlers (e.g. `PushHandler`, and by the shared base class every other handler) resolve the target `Stack`(s) using `repository.full_name`, a completely separate JSON field from the `repository.owner.login` used for signature selection: [3](#0-2) [8](#0-7) 

Because the field used to select the verifying secret (`repository.owner.login`) is never checked for consistency with the field used to pick the target repository/stack (`repository.full_name`), an attacker who legitimately controls a GitHub App installation on their own organization "A" (i.e., they know/receive genuinely-signed webhook deliveries for org A) can send a POST to `/webhooks` with:
- `repository.owner.login` = `"A"` (or `organization.login` = `"A"`) so `Shipit.github(organization: "A")`'s secret is used for verification, and
- `repository.full_name` = `"victim-org/victim-repo"` (a stack tracked under a different, unrelated organization/secret on the same Shipit instance).

The HMAC check only validates that the raw body matches org A's secret — which it trivially does, since the attacker controls org A's webhook and can compute/replay a valid signature for a body they crafted (or replay a captured, legitimately-signed body from org A and simply reuse the same signature scheme because HMAC-SHA1 verification here does not bind specific JSON fields, only the raw byte string signed with a secret the attacker possesses). The forged event is then routed as if it truly came from `victim-org/victim-repo`.

This exactly matches the requested binding-break class: **"an organization that authenticated versus the repository that is written."** The equality that should hold, `verifying_org(repository.owner.login) == target_repo_owner(repository.full_name)`, is never enforced.

### Impact Explanation
The concrete exploitation path depends on which handler is triggered:
- `PushHandler` merely triggers `stack.sync_github(expected_head_sha:)`, which re-fetches real commits from the GitHub API using Shipit's own credentials, so forged pushes alone don't inject fake commit content, but do let an outsider force arbitrary resyncs on stacks they have no relationship to. [9](#0-8) [10](#0-9) 
- More seriously, the `status` event handler creates a `Commit::Status` record directly from attacker-supplied payload fields (`state`, `target_url`, `context`, `description`) for an existing commit matched purely by `sha`, as evidenced by the test asserting the created status's fields are copied verbatim from the payload. [11](#0-10)  If a stack's deploy spec gates deploys on required CI status contexts, an attacker who controls a legitimate GitHub App installation on any org configured in the same Shipit instance can forge a `status` webhook against a victim stack's real commit SHA (visible from that repository's public commit history) with `state: "success"` for whatever context is required — effectively bypassing required-status gating and potentially enabling **an unauthorized deploy**, one of the explicitly accepted "Critical" impacts.

I was not able to re-verify the exact contents of `status_handler.rb` in this session (a tool failure prevented reading it directly), so the precise field mapping/validation inside that handler is inferred from the handler test and the shared `Handler` base class; this should be confirmed against the actual handler source before treating this as fully proven.

### Likelihood Explanation
Requires only that the attacker control (or have registered) at least one GitHub organization/App configured on the same multi-tenant Shipit instance — no privileged Shipit account, `ApiClient` token, or session is needed, since `/webhooks` is an unauthenticated public endpoint gated solely by HMAC. This is realistic for any Shipit deployment serving multiple organizations (the documented multi-org secrets layout exists specifically to support this). [4](#0-3) 

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after determining `repository_owner` for signature selection, re-validate that every repository-scoped field consumed by the dispatched handlers (`repository.full_name`'s owner segment, or any `Repository` resolved by `Handler#stacks`) belongs to that same verified organization before invoking handlers. Alternatively, resolve the target `Stack`/`Repository` first, derive the organization strictly from that resolved repository record (not from raw payload fields), and use that organization's secret for verification — binding the two together at a single trusted source.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with independent `webhook_secret`s (multi-org config as documented). [4](#0-3) 
2. Attacker legitimately controls a GitHub App installation on `attacker-org` and thus knows/can compute a valid `X-Hub-Signature` for `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body with:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `sha` = an existing head commit SHA of a stack tracked under `victim-org/victim-repo`
   - `state = "success"`, `context = "<required-check-context>"`
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known secret over this exact body and POSTs it to `/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully. [1](#0-0) 
6. The status handler creates/updates a `Status` for the victim's commit using the forged `state`/`context`, as confirmed by the handler's field-copy behavior in its test. [12](#0-11) 
7. If `victim-org/victim-repo`'s deploy spec requires that context to be green, the forged status can satisfy the gate for an otherwise non-CI-passing commit, enabling an unauthorized deploy.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
