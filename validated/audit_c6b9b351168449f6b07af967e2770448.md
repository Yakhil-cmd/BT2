Confirmed vulnerability. The critical divergence is in `StatusHandler`, which — unlike every other webhook handler in this codebase — does not scope its lookup by the reporting repository.

### Title
Repository-unscoped status webhook lookup lets a status from any repository configured in Shipit satisfy a MergeRequest's CI gate for a different, unrelated repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table with no repository/stack scoping, then calls `commit.create_status_from_github!(params)` on every match. Every other handler in `app/models/shipit/webhooks/handlers/**` scopes work through `stacks` / `Repository.from_github_repo_name(repository_name)`, but `StatusHandler` never reads `params.dig('repository', ...)` at all, so a validly signed status payload from repository B can create a `Status` on a `Commit` row that belongs to stack A, purely because the sha values collide.

### Finding Description
The binding the question asserts should hold — "repository named in the verified status payload == repository of the MergeRequest whose `all_status_checks_passed?` gates the merge" — is **not enforced anywhere** in this code path: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Compare with `PushHandler`, `OpenedHandler`, `ClosedHandler`, etc., which all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` (or the inherited `stacks` helper) before touching any records: [2](#0-1) [3](#0-2) 

`StatusHandler`'s `params` schema doesn't even require `repository`, only `sha`/`state`/etc: [4](#0-3) 

Signature verification (`WebhooksController#verify_signature`) only proves the payload was signed by the GitHub App/org whose secret matches `payload.dig('repository','owner','login')` — it proves the *sender* repository/org is authentic, but says nothing about which *commit rows* the handler is allowed to touch: [5](#0-4) 

`create_status_from_github!` then unconditionally records the status and triggers cascading effects: [6](#0-5) , including scheduling `ProcessMergeRequestsJob` on success/pending transitions (proven directly in the test suite): [7](#0-6) 

`ProcessMergeRequestsJob` then calls `merge_request.all_status_checks_passed?`, which reads `head.statuses_and_check_runs` with no repository check either — it trusts whatever `Status` rows are attached to `head`: [8](#0-7) [9](#0-8) 

**Exploit flow:** Git commit shas are content-addressed (tree + parents + author/committer + message + timestamps). If an attacker can reproduce byte-identical commit content — e.g., they know the exact head sha of a queued merge request in stack A (visible in the public PR/Shipit UI) and can fetch/push that exact commit object into a repository B they control that is *also configured in Shipit and covered by a webhook whose signing secret validates for `repository_owner` == B's owner* — they can trigger a real, validly-signed `status` event from GitHub for repository B with `sha` equal to A's queued merge-commit head, `state: success`. `StatusHandler` finds the `Commit` row for stack A with that sha (because the lookup is global, not scoped to B) and writes a `success` `Status` against it, satisfying `all_status_checks_passed?` for A's `MergeRequest`, causing `ProcessMergeRequestsJob` to call `merge_request.merge!`, an unauthorized merge into repository A initiated entirely from repository B's authenticated webhook traffic.

None of the listed guards stop this: `verify_signature` only authenticates *which org/repo sent the request*, not *which stack's data may be mutated*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; there is no `force_github_authentication`, `stacks` scope, or model validation anywhere in `StatusHandler`/`Status`/`Commit#create_status_from_github!` that ties the status's originating repository to the commit's owning stack/repository.

### Impact Explanation
A `Status` record is written for a `Commit`/`MergeRequest` belonging to repository/stack A, authenticated only by webhook traffic from an unrelated repository B. This directly enables an unauthorized merge on repository A (`MergeRequest#merge!` invoking `stack.github_api.merge_pull_request`) — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." It is repeatable against any stack/repository whose pending merge-request head sha the attacker can learn (all public in the Shipit UI/GitHub PR) and reproduce as a commit object pushed into any repository B that shares a Shipit-configured webhook scope (e.g., an org-level GitHub App installation covering multiple repos, or any repo B the attacker can get onboarded to Shipit under an org already known to `Shipit.github_app_config`).

### Likelihood Explanation
Preconditions: (1) attacker must know/reproduce the exact target commit sha (feasible since git commits are content-addressed and merge-request heads are public); (2) attacker needs some repository B whose statuses will produce a webhook that passes `verify_signature` for an organization already configured in Shipit's `secrets.github` (this is realistic in org-wide GitHub App installations spanning many repos, a common real-world Shipit deployment pattern, but is an operator/config-dependent precondition, not guaranteed in every deployment). Given that precondition, exploitation cost is low (no secrets needed, just legitimate GitHub actions on a repo the attacker controls) and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, mirroring every other handler: require `repository.full_name` in the params schema, resolve `stacks`/commits only through `Repository.from_github_repo_name(params.repository.full_name)`, and only call `create_status_from_github!` on commits belonging to a stack tied to that repository — never on a global `Commit.where(sha:)` lookup.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `stack_a` (repository `owner-a/repo-a`) with a `Commit` `commit_a` having `sha: "deadbeef..."` and a `MergeRequest` on stack A with `head: commit_a`, `merge_status: 'pending'`, no statuses yet.
2. Create `stack_b` (repository `owner-b/repo-b`) with its own `Commit` row also having `sha: "deadbeef..."` (simulating the colliding/duplicated commit object) belonging to stack B.
3. Assert baseline: `refute merge_request.all_status_checks_passed?` (binding: repo of payload `owner-b/repo-b` != repo of gated MergeRequest `owner-a/repo-a`).
4. POST `/webhooks` with `X-Github-Event: status`, a JSON body `{ sha: "deadbeef...", state: "success", repository: { full_name: "owner-b/repo-b", owner: { login: "owner-b" } }, branches: [...] }`, signed correctly for `owner-b`'s configured webhook secret (stub `Shipit.github(organization: 'owner-b').verify_webhook_signature` to return true, mirroring real signature validity for B).
5. Assert `commit_a.statuses.count` increased and `commit_a.reload.state == 'success'`.
6. Assert `merge_request.reload.all_status_checks_passed?` is now `true`.
7. Run `ProcessMergeRequestsJob.perform(stack_a)` and assert `MergeRequest#merge!` is invoked (e.g., via mocking `stack.github_api.merge_pull_request` and asserting it was called), proving cross-repository forgery drove an unauthorized merge on stack A.
