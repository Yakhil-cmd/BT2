### Title
Commit authorship attribution trusts unauthenticated commit-message text (`Merge-Requested-By:` field) - ([File: app/models/shipit/commit.rb, app/models/shipit/user.rb])

### Summary
`User.find_or_create_author_from_github_commit` extracts a login from the free-text commit message using the `Merge-Requested-By: <login>` pattern and blindly attributes commit authorship to that Shipit `User` via `find_or_create_by_login!`, with no check that the actual git committer/author or GitHub actor is authorized to claim that identity. Any user who can push a commit with an arbitrary message to a tracked branch (a fork PR merge, a direct push, or any commit ingested by `GithubSyncJob`) can impersonate an existing high-privilege Shipit user as the commit's `author`.

### Finding Description
The broken binding, stated as an equality that should hold but does not: `commit.author_id` should equal `User.find_by(github_id: <verified GitHub identity of whoever authored/pushed the commit>).id`, but instead equals `User.find_or_create_by_login!(<attacker-chosen string embedded in commit.commit.message>).id`.

Code path:
- `Commit.from_github` calls `User.find_or_create_author_from_github_commit(commit)` [1](#0-0) 
- That method matches `github_commit.commit.message` against `/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/` (`MERGE_REQUEST_FIELD = 'Merge-Requested-By'`) and, on match, calls `find_or_create_by_login!(match_info[1])`, returning that user as `author` with no fallback verification against the actual GitHub commit author/committer identity [2](#0-1) 
- `find_or_create_by_login!` performs a lookup/creation purely on the extracted string, with no cross-check against `github_commit.author`/`github_commit.commit.author` [3](#0-2) 

Root cause: the `Merge-Requested-By:` marker is intended to be written only by Shipit itself when it performs a queued merge, via `MergeRequest#merge_message` (`"#{title}\n\n#{MERGE_REQUEST_FIELD}: #{merge_requested_by.login}\n"`) [4](#0-3) . However, `Commit.from_github` parses this same marker out of *any* incoming commit message regardless of who wrote it or how the commit reached the repository (direct push, PR merge with arbitrary commit message, etc.), so there is no binding between "wrote this marker" and "is Shipit's own merge action."

Existing guards that don't prevent this: webhook signature verification (`verify_signature`) only authenticates that the payload came from GitHub for the configured repo — it says nothing about who authored the underlying commit content, and commit *messages* are attacker-controlled by design (anyone with push/merge rights to their own branch/fork chooses the message). `ExplicitParameters`, `force_github_authentication`, and `User#authorized?` are unrelated to this ingestion path, which runs asynchronously via `GithubSyncJob`/`Commit.create_from_github!` and never consults session/API-client context.

Attacker flow: attacker opens a PR from their own fork to a tracked repository/branch, or pushes directly if permissions allow, with a commit whose message body contains a line `Merge-Requested-By: victim-login\n` where `victim-login` is an existing Shipit `User#login` (e.g., a maintainer who has previously interacted with Shipit). Once GitHub webhooks/sync ingest this commit, `Commit.from_github` sets `author` to the victim's `User` record.

### Impact Explanation
The impacted `Commit#author` is used downstream: `TaskCommands#env` sets `SHIPIT_USER` and `EMAIL` directly from the task's author record (`"#{@task.author.login} (#{normalized_author_name}) via Shipit"` and `@task.author.email`) [5](#0-4) , which flow into the deploy `Command`'s environment. This misattributes deploy/audit provenance to an arbitrary existing user without their consent, affecting audit trails and any downstream logic keyed on commit/task authorship (e.g., `stacks_contributed_to`, `repositories_contributed_to` in `app/models/shipit/user.rb`). This is a record-integrity/impersonation issue scoped to the repository whose stack ingested the crafted commit; it does not grant cross-tenant access to other repositories' secrets or execute arbitrary attacker-controlled commands beyond what the attacker's own commit content would otherwise trigger.

### Likelihood Explanation
Precondition is low-cost: the attacker only needs the ability to get a commit with a controlled message synced into a Shipit-tracked stack (opening a PR that gets merged, or pushing to a branch with lax permissions) and knowledge of an existing Shipit user's GitHub login (public information). No Shipit secrets, tokens, or elevated GitHub permissions are required. This is repeatable per commit and per stack that tracks attacker-reachable branches.

### Recommendation
Only trust the `Merge-Requested-By:` marker when the commit is the actual merge commit of a `MergeRequest` that Shipit itself created/tracked (i.e., cross-check `merge_request.merge_requested_by` and `merge_request.number`, as `identify_merge_request` already does at `app/models/shipit/commit.rb:316-328`), rather than parsing the marker out of arbitrary incoming commit messages in `User.find_or_create_author_from_github_commit`. Remove or restrict the free-text regex match in `app/models/shipit/user.rb` so it cannot be spoofed by externally-authored commit messages.

### Proof of Concept
In a minitest under `test/models/commits_test.rb` (out of scope per rules, but described conceptually): construct a stubbed `github_commit` Sawyer resource whose `commit.message` is `"commit\n\nMerge-Requested-By: victim_login\n"`, with `github_commit.author`/`commit.author` set to an unrelated attacker identity. Call `Shipit::Commit.from_github(github_commit)` and assert `result.author == Shipit::User.find_by(login: 'victim_login')`, demonstrating the author is bound to the message-embedded login rather than the actual GitHub author metadata.

```ruby
    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
```
