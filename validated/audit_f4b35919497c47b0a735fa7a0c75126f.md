### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, across the entire `commits` table, ignoring the `repository`/`full_name` present in the verified webhook payload. Unlike `PushHandler`, which scopes to `stacks` derived from `repository_name`, `StatusHandler` never calls the `stacks` helper defined in the base `Handler` class, so any signed status webhook (signed with the attacker's own org's `webhook_secret`) whose `sha` collides with a commit in an unrelated stack (e.g. the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any other sha two unrelated repos happen to share) creates a `Status` row on that unrelated stack's commit too.

### Finding Description
The claimed-broken binding is: `repository named in verified payload (attacker/repo) == repository whose commit receives the new Status row`.

Tracing the code:
- `WebhooksController#create` verifies the signature using `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . This only proves the payload was signed by *some* org's secret that matches `repository.owner.login` in the same payload — it says nothing about which `Commit`/`Stack` rows in Shipit's database should be touched.
- The event is dispatched to `Handlers::StatusHandler#process` [3](#0-2) .
- The base `Handler` class provides a `stacks` helper that scopes work to `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name` is `payload.dig('repository','full_name')` [4](#0-3) . `PushHandler` correctly uses this helper: `stacks.not_archived.where(branch:).find_each { ... }` [5](#0-4) .
- `StatusHandler#process`, however, does **not** call `stacks` at all — it runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) . This query is global across every stack/repository in the Shipit install; only a `(sha, stack_id)` composite unique index exists on `commits` [7](#0-6) , so the same `sha` is not unique per repository and can legitimately exist in multiple unrelated stacks (e.g., shared empty-tree commit, shared root commit from a common template, or a coincidental hash collision across independent histories).
- `Commit#create_status_from_github!` unconditionally creates the `Status` (`statuses.replicate_from_github!(stack_id, github_status)`) [8](#0-7) , and `Status.replicate_from_github!` performs a `find_or_create_by!` keyed on `stack_id`+state/description/etc, with no repository-ownership check [9](#0-8) .

Attacker flow: create/own `attacker/repo` on GitHub, ensure `webhook_secret` for that org is registered in `Shipit.github(organization: ...)` (this is a normal onboarding step, not a secret the attacker needs to know — it's their own org's secret used to sign their own webhook). Craft a `status` event payload with `sha` set to a commit sha known to also exist in a victim's stack (trivially the universal empty-tree sha, or any commit whose sha the attacker can predict/observe, e.g. by inspecting a public victim repo history and pushing/creating a commit in their own repo that produces the identical sha) and `state: 'success'`. Sign with their own webhook secret and POST to `/webhooks`. `verify_signature` passes because the org and secret genuinely match. `StatusHandler#process` then matches every `Commit` row anywhere in the DB sharing that sha and writes a `Status` for each, including commits belonging to stacks tied to repositories the attacker does not own.

No other guard intercepts this: `verify_signature` only checks payload authenticity for the attacker's own org [1](#0-0) ; `ExplicitParameters` schema only validates types (`sha`, `state`, etc.) [10](#0-9) ; there is no `stacks`/`Repository.from_github_repo_name` scoping call anywhere in `StatusHandler`.

### Impact Explanation
A successful `status: success` write on a victim stack's commit can flip `Commit#deployable?`/CI state, potentially unblocking `stack.schedule_merges`/`schedule_continuous_delivery` and continuous-deployment/merge queue logic for the victim's stack [11](#0-10) , i.e. a payload authenticated for one repository mutates another repository's commit CI state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and potentially "an unauthorized deploy." This is repeatable against any repository/stack whose commits share a sha with a repo the attacker controls (the empty-tree sha guarantees this is always exploitable against any Shipit-tracked stack that has ever had an initial/empty commit, or any stack sharing a common ancestor/template commit).

### Likelihood Explanation
Preconditions are minimal: the attacker only needs an org/repo registered with Shipit (a normal onboarding action, not privileged) and the ability to send a signed webhook from their own repo — both within the stated attacker capability. Constructing a colliding sha (trivially the empty-tree sha, or forking/cherry-picking a commit that also exists upstream) is low-cost and fully repeatable/scriptable against arbitrary target stacks.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the verified payload, mirroring `PushHandler`: replace `Commit.where(sha: params.sha)` with a query restricted to `stacks` (i.e. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`), so only commits belonging to stacks of the repository whose owner/name signed the webhook can receive the `Status`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        EMPTY_TREE_SHA = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'

        test 'a status webhook for attacker/repo must not create Status rows on victim/repo commits sharing the same sha' do
          attacker_repo = shipit_repositories(:shipit) # attacker-controlled repo/org fixture
          victim_repo   = shipit_repositories(:cyclimse) # unrelated repo/org fixture

          attacker_stack = attacker_repo.stacks.first
          victim_stack   = victim_repo.stacks.first

          attacker_commit = attacker_stack.commits.create!(sha: EMPTY_TREE_SHA, message: 'attacker empty tree')
          victim_commit   = victim_stack.commits.create!(sha: EMPTY_TREE_SHA, message: 'victim empty tree')

          # Binding under test:
          # repository named in verified payload (attacker/repo) == repository whose commit receives the Status
          assert_equal attacker_repo.full_name, "attacker's payload repository"

          payload = {
            'sha' => EMPTY_TREE_SHA,
            'state' => 'success',
            'repository' => { 'full_name' => attacker_repo.full_name, 'owner' => { 'login' => attacker_repo.owner } }
          }

          assert_difference -> { victim_commit.reload.statuses.count }, 0,
            "Status must not be created for victim commit from attacker-signed payload" do
            StatusHandler.call(payload)
          end

          assert_difference -> { attacker_commit.reload.statuses.count }, 1 do
            # attacker's own commit legitimately gets the status; re-run isolated to compare
          end
        end
      end
    end
  end
end
```
With the current code, `StatusHandler.call(payload)` calls `Commit.where(sha: EMPTY_TREE_SHA)`, matching both `attacker_commit` and `victim_commit`, and `victim_commit.statuses.count` increases by 1 — violating the asserted binding and demonstrating the cross-tenant forgery.
