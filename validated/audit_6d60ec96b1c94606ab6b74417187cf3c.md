### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration, where each organization has its own `webhook_secret` looked up via `Shipit.github(organization:)` [1](#0-0) . The webhook controller determines *which* organization's secret to validate the HMAC signature against using `repository_owner`, taken from the same untrusted, attacker-supplied JSON body (`params.dig('repository','owner','login')`) [2](#0-1) . Once the signature check passes, every downstream handler determines which `Stack`/`Repository` to mutate using a *different* field from the very same payload: `payload.dig('repository', 'full_name')` [3](#0-2) .

### Finding Description
The binding that should hold is:
`organization whose webhook_secret authenticated the request == owner of the repository the handler is about to write to`

Before-action order in `WebhooksController` is `check_if_ping, drop_unhandled_event, verify_signature`, and only after `verify_signature` succeeds does `create` dispatch the parsed payload to handlers [4](#0-3) . `verify_signature` computes the expected HMAC using the app configured for `repository_owner`:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

This is an unverified, attacker-chosen field, read straight out of the JSON body before any signature check occurs — the value only determines which secret to test the signature against; it never constrains what the rest of the payload can contain.

Meanwhile, every handler resolves the target `Stack` via a *different* JSON path:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

and similarly `review_stack_adapter.rb`'s `repo_name` reads `params.repository["full_name"]` [6](#0-5) .

Because `repository.owner.login` and `repository.full_name` are two independent keys inside the same attacker-crafted JSON body, a customer/organization who legitimately possesses their **own** valid `webhook_secret` (an unprivileged actor relative to *other* tenants configured on the same Shipit instance) can craft a payload where:
- `repository.owner.login` = their own org (so the HMAC computed with their own secret validates), and
- `repository.full_name` = `"other-org/other-repo"` (any other tenant's repository configured on the instance).

`verify_signature` succeeds (their secret matches their own field), yet the handler acts on the victim organization's repository/stack, because the acted-upon field was never covered by the same trust check as the field used to select the signing key.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding described as in-scope. Depending on which webhook event is replayed this way, an attacker with only a valid webhook secret for their own low-privilege tenant repository can:
- Trigger `PushHandler`/`GithubSyncJob` for another organization's stack with an `expected_head_sha` under attacker control [7](#0-6) , potentially forcing sync against a spoofed head SHA.
- Manipulate `ReviewStackAdapter` operations (`archive!`, `unarchive!`, `create!`) against another org's `ReviewStack`, causing unauthorized stack archival/creation using a forged `sender.login` identity [8](#0-7) .

These are cross-repository/cross-tenant writes originating from a signature that was never actually valid for the target repository, i.e., an authentication-boundary bypass across GitHub organizations hosted on the same Shipit instance.

### Likelihood Explanation
Requires the attacker to control (or have legitimately been issued) at least one organization's `webhook_secret` on a multi-org Shipit deployment (i.e., be a legitimate but lower-trust tenant), and requires the Shipit instance to host multiple GitHub organizations in its config (`github_organizations`) [9](#0-8) . This is a realistic configuration supported explicitly by the codebase's multi-tenant `github_app_config` mechanism. No GitHub App private key, no `api_clients_secret`, and no privileged Shipit account are needed — only a webhook secret for one's own tenant, which the rules permit as it's not `webhook_secret` of the *target* being attacked.

### Recommendation
Verify the webhook signature using the *same* organization key that will subsequently be used to select stacks/repositories, and additionally validate that `repository.owner.login` (used for signature org lookup) matches the owner segment of `repository.full_name` before dispatching to handlers. Reject the payload if these two fields disagree.

### Proof of Concept
1. Attacker is a legitimate tenant admin for GitHub org `attacker-org` on a shared Shipit instance that also hosts `victim-org/victim-repo`.
2. Attacker knows their own `webhook_secret` for `attacker-org` (as configured under `secrets.github[:attacker-org][:webhook_secret]`).
3. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully, since `attacker-org`'s secret matches [10](#0-9) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` [3](#0-2)  and triggers `GithubSyncJob` against `victim-org/victim-repo`'s stack with the attacker-supplied `expected_head_sha`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
