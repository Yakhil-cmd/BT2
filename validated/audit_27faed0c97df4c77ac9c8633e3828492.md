### Title
Unhandled TypeError in `validateDivisiblePrivatePayment` when private-payment payload is malformed - ([File: divisible_asset.js])

### Summary
`validateDivisiblePrivatePayment` dereferences `objPrivateElement.payload.asset` before verifying that `payload` itself is a non-empty object, mirroring the ALPINE-CVE-2021-41524 pattern of a crafted, minimally-malformed request reaching code that dereferences a field on a value that was never checked to exist. In ocore this throws an uncaught `TypeError`, and `network.js` installs a global `uncaughtException` handler that deliberately re-throws to crash the whole node process, turning a single crafted private-payment chain into a full node DoS.

### Finding Description
`validateDivisiblePrivatePayment` is the entry point that validates a "divisible" private (indivisible-vs-divisible split, blackbytes-style) payment chain element before it is persisted: [1](#0-0) 

The function immediately reads `payload.asset` and `payload.inputs` without first confirming `payload` is a non-empty object:
```
var payload = objPrivateElement.payload;
if (!ValidationUtils.isStringOfLength(payload.asset, constants.HASH_LENGTH))
    return callbacks.ifError("invalid asset in private divisible payment");
```
If `objPrivateElement.payload` is `null`, `undefined`, or a non-object (e.g. a number or string), the `payload.asset` access throws `TypeError: Cannot read properties of null/undefined`. This is a synchronous throw inside a callback invoked from deep inside async chains (`storage.readJoint`, DB query callbacks, event-emitter driven code paths), which are not wrapped in `try/catch` up the stack for this particular case.

This validator is reachable by an unprivileged private-payment counterparty. `validateAndSaveDivisiblePrivatePayment`/`validateAndSavePrivatePaymentChain` is the entry called for divisible private asset chains received from a peer, and comparable code exists for indivisible assets in `indivisible_asset.js` (`validatePrivatePayment`), which similarly reads `payload.asset`/`payload.denomination` off `objPrivateElement.payload` before any `isNonemptyObject(payload)` guard: [2](#0-1) 

The most direct application-level entry point that a wallet peer/device controls is `handlePrivatePaymentChains` in `wallet.js`, which validates the overall chain shape (`isNonemptyObject(e.payload)` etc.) before forwarding into validation: [3](#0-2) 
However, other intake paths exist (e.g. `network.js`'s `handleSavedPrivatePayments`, which re-reads previously stored/unhandled private-payment JSON and re-invokes `privatePayment.validateAndSavePrivatePaymentChain`), and the persistence/replay paths do not necessarily re-run the same defensive object-shape check that `wallet.js` performs at first receipt: [4](#0-3) 

Once an unhandled exception of this kind escapes to the top level, `network.js` explicitly turns it into a fatal crash: [5](#0-4) 

This is analogous to the Apache HTTP/2 bug: a specially crafted, minimal message causes a null/undefined dereference deep in request processing that the server never anticipated, resulting in an unhandled crash instead of a graceful validation error.

### Impact Explanation
An uncaught exception thrown during private-payment processing crashes the entire ocore process (full node, hub, or wallet), per the explicit `throw err` in the global `uncaughtException` handler. Because this handler exists precisely to avoid ending up in "an inconsistent state," an attacker-controlled crash primitive lets any private-payment counterparty (or a hub relaying stored, previously-received-but-unhandled private payment JSON) repeatedly take down a node, denying it the ability to process/confirm new units for as long as the crash loop persists. This matches the required impact category: "a network unable to confirm new units" for the affected node.

### Likelihood Explanation
Likelihood is high for any node/wallet that accepts private-payment chains from counterparties. The only requirement is sending a private-payment JSON where a chain element's `payload` field is missing/null/wrong type, or (for indivisible assets) where `payload` lacks the expected shape—no signature forgery, no double-spend construction, and no privileged position needed. If the direct `wallet.js` handler's `isNonemptyObject(e.payload)` guard covers the live receive path, the crash primitive is still exposed through re-processing of stored/queued chains (`handleSavedPrivatePayments`) or other intake paths that call into `divisible_asset.js`/`indivisible_asset.js` validators without re-running the same guard, since the vulnerable functions themselves contain no defensive check.

### Recommendation
Add an explicit `isNonemptyObject(payload)` (and equivalent authors/messages-shape) check at the very top of `validateDivisiblePrivatePayment` (and the analogous point in `indivisible_asset.js`'s `validatePrivatePayment`) before any property access, returning `callbacks.ifError(...)` instead of letting a `TypeError` propagate. More broadly, wrap all private-payment and AA-trigger validation entry points in `try/catch` that convert unexpected exceptions into `ifError` results rather than allowing them to escape to the process-level `uncaughtException` handler, consistent with the defensive `try { … } catch (e) { return callbacks.ifError(...) }` pattern already used elsewhere in `validation.js`.

### Proof of Concept
1. As a private-payment counterparty (or a device relaying a chain to a hub/wallet), construct a private-payment chain array whose single element has `payload: null` (or omit `payload` entirely) while keeping other required top-level fields (`unit`, `message_index`, `output_index`, `output`) syntactically present enough to pass any outer array/object-shape checks that don't specifically validate `payload`.
2. Submit this chain through any code path that ultimately calls `divisible_asset.js`'s `validateAndSavePrivatePaymentChain` → `validateAndSaveDivisiblePrivatePayment` → `validateDivisiblePrivatePayment` without first checking `isNonemptyObject(payload)` (e.g., via stored/unhandled private payment replay in `network.js`'s `handleSavedPrivatePayments`, or any other internal caller that doesn't duplicate `wallet.js`'s guard).
3. Execution reaches `payload.asset` on a `null`/`undefined` `payload`, throwing an uncaught `TypeError`.
4. The process-level `uncaughtException` handler in `network.js` logs the error and re-throws it, terminating the node process — denying service to all users of that node until it is manually restarted.
