### Title
Webhook signature verification authenticates the payload against an attacker-chosen organization while handlers act on an unrelated, unauthenticated repository field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The `redeem` bug lets an untrusted caller pick which contract/amount is trusted for a state-changing action. `WebhooksController` has the same class of flaw: it picks *which* organization's webhook secret to verify the signature against by reading a field out of the very payload it is about to verify, and it never cross-checks that field against the field handlers subsequently use to decide *which repository/stack* to mutate.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to check the HMAC against using a value taken straight from the untrusted JSON body: [1](#0-0) 

That value comes from: [2](#0-1) 

`Shipit.github(organization: repository_owner)` then supplies the secret used by `verify_webhook_signature`, which simply HMACs the raw body with whatever secret was resolved: [3](#0-2) 

Meanwhile, the handlers that actually act on the payload (create commits, sync stacks, record statuses, etc.) resolve the target repository/stack from a *different* field of the same body: [4](#0-3) 

Nothing in `WebhooksController` or `Handler` enforces that `repository.owner.login` (used to choose the signing secret) and `repository.full_name`'s owner segment (used to select which `Repository`/`Stack` is mutated) refer to the same organization/repository.

Shipit explicitly supports multiple GitHub Apps/orgs sharing one instance, each with its own `webhook_secret`: [5](#0-4) 

This is a documented, supported deployment mode, so knowledge of "your own org's" `webhook_secret` by one tenant/org admin is an expected, in-scope condition, not a hypothetical.

**Equality broken:** `organization that authenticated the request` (`repository_owner` picked from the payload, used only to select the HMAC secret) `!=` `repository that is written` (`repository.full_name`, used by every `Handler` subclass to locate the `Stack`/`Repository` to mutate).

### Impact Explanation
An attacker who administers Organization B, one of several organizations legitimately configured in a multi-org Shipit deployment, knows Org B's `webhook_secret` (it is provisioned by/for that org's own GitHub App). They can POST directly to `/webhooks` with a self-crafted body where:
- `repository.owner.login` = `"OrgB"` (so `Shipit.github(organization: 'OrgB')` resolves to the secret they know, and their self-computed HMAC-SHA1 passes `verify_webhook_signature`), and
- `repository.full_name` = `"victim-org/victim-repo"` (or any other repository tracked by the shared Shipit instance).

Because the signature only certifies "this body was produced/known by whoever holds Org B's secret," not "this body concerns Org B's repositories," the request is accepted and dispatched to handlers (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) which operate on the victim repository resolved from `repository.full_name`. Depending on the event, this allows a cross-organization attacker to inject fabricated commit statuses, membership changes, or CI signals for a repository they do not own. Since Shipit's continuous-delivery/CI-gating logic (`ci.require`, deployment checks) can consult commit statuses to decide whether to auto-deploy, a forged `status` event for a victim stack can be used to satisfy deploy gating and contribute to an unauthorized deploy — the required High/Critical impact category.

### Likelihood Explanation
Requires the attacker to be an admin/owner of any one organization that is configured as a tenant of the shared Shipit instance (a supported, documented multi-org configuration) and to be able to craft an arbitrary HTTP POST with a correct HMAC using their own known secret — no GitHub session, no `ApiClient` token, and no access to the victim org's secret is needed. This satisfies the "unprivileged-attacker analog breaking a deployment-trust binding" bar: the attacker is privileged only for their own tenant, not for the victim's.

### Recommendation
- Short term: after signature verification, require that the organization/owner used to select the signing secret matches the owner segment of `repository.full_name` (or `organization.login`) actually used to resolve the target `Stack`/`Repository`; reject mismatches.
- Long term: derive both "who signed this" and "what this payload is about" from the same, single trusted field, and add regression tests simulating a webhook whose declared owner and target repository diverge.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps/orgs per `docs/setup.md`'s "Using Multiple Github Applications" (Org B controlled by attacker, Victim-Org tracked in the same instance).
2. Attacker, knowing `webhook_secret_B` for their own org, builds a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "victim-org/victim-repo" },
  "sha": "...", "state": "success", "target_url": "...", "context": "ci/required", "branches": [{"name": "master"}]
}
```
3. Computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_B, raw_body)>` and sends it with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'OrgB')` and the HMAC checks out, so the request is accepted.
5. `StatusHandler` (via `Handler#repository_name` → `payload.dig('repository','full_name')` = `victim-org/victim-repo`) records the forged `success` status against the victim's stack/commit, independent of the org whose secret actually authenticated the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
