### Title
Unallowlisted swap-route contracts can attach unrelated wallet-draining transfers to a user's authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The swap-routed controller entrypoints accept attacker-controlled route bytes and execute them through the configured router without constraining route-selected pool contracts. A malicious pool invoked during `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` can call `token.transfer(victim, attacker, amount)` for an unrelated wallet token; Soroban simulation records that transfer as a child of the victim's controller authorization, and signing that tree executes the theft even though the protocol only intended to authorize the swap.

### Finding Description
`process_swap_collateral` authenticates `caller`, verifies ownership or delegation, withdraws collateral, and passes caller-supplied `swap` bytes into the router path. [1](#0-0)  The shared router wrapper snapshots only the swap input and output balances, authorizes one exact controller-to-router input transfer, calls `execute_strategy`, and subsequently checks that controller input spending did not exceed `amount_in` and that measured output is positive. [2](#0-1) 

Those measurements do not constrain unrelated calls made by code selected inside the route. The route payload's `assets` registry supplies each hop's `pool`, `token_in`, and `token_out` addresses, and the swap instruction dispatches to the payload-selected pool address. [3](#0-2) [4](#0-3)  For example, the Soroswap adapter invokes `get_reserves` and `swap` on the supplied `hop.pool`, while the Aquarius adapter invokes `swap` on the supplied pool. [5](#0-4) [6](#0-5) 

The repository's focused authorization test demonstrates that a rogue hop contract can hardcode the victim and execute `token.transfer(victim, attacker, amount)` during its route callback. [7](#0-6)  Simulation records that unrelated transfer as a child invocation beneath the victim's `swap_collateral` authorization, and enforcing mode executes it when the returned tree is signed. [8](#0-7) [9](#0-8) 

### Impact Explanation
A victim who submits an attacker-supplied route can lose assets unrelated to the swap, including tokens never supplied to or listed by the lending protocol. The protocol's controller-side checks only bound the routed input and require a positive output; they do not bound transfers from the victim's wallet that are explicitly included in the signed authorization tree. [10](#0-9)  The demonstrated loss is the victim's full unrelated wallet balance while the collateral swap itself completes successfully. [11](#0-10) 

### Likelihood Explanation
Exploitation requires the victim to sign a simulated authorization tree containing the extra transfer, so it is primarily a malicious-route/signing-interface attack rather than a fully unsolicited drain. The route still has to satisfy the router's measured-spend and positive-output requirements, but an attacker can satisfy them by funding or constructing the rogue venue's output. [12](#0-11)  The affected entrypoints are reachable by any account owner or active delegate, and the repository test shows both recording-mode attachment and successful enforced execution after the poisoned tree is signed. [13](#0-12) [14](#0-13) 

### Recommendation
Do not invoke arbitrary pool addresses embedded in route bytes during user-authorized lending operations. Restrict every route pool to a governance-approved venue/pool registry or otherwise bind pool identity to authenticated venue metadata before dispatch. Clients and wallets should additionally decode and display every nested authorization before signing and reject a swap authorization containing unrelated token transfers. [15](#0-14) 

### Proof of Concept
The existing test deploys a rogue route pool configured with `(victim, wallet_token, attacker, amount)` and invokes `token.transfer(victim, attacker, amount)` when the router calls its `swap` function. [7](#0-6)  The victim calls `controller.swap_collateral(victim, account_id, USDC, amount, ETH, route)`, where `route` names the rogue contract as a hop pool. [16](#0-15) 

Simulation produces an authorization whose root is the victim's `swap_collateral` call and whose child is `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`. [17](#0-16)  Signing that tree drains `WALLET_BALANCE` from the victim to the attacker while crediting the expected swap output to the victim's lending position. [11](#0-10)

```rust
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
