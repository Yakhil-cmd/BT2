### Title
Cross-stack authorization bypass in `CCMenuController#stack` breaks the stack-scoping binding of `ApiClient` tokens - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, bypassing the stack-scoping enforcement (`stacks.from_param!`) that every other API controller relies on via `Shipit::Api::BaseController`. This breaks the binding between the stack an `ApiClient` token is authorized for and the stack whose state it can actually read.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-aware accessor: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the token is scoped to a specific stack, and `stack` calls `stacks.from_param!`, which is how every other controller (`CommitsController`, `StacksController`, etc.) enforces the "token authorized for stack X" binding.

`CCMenuController` overrides `stack` with an unscoped lookup and only checks the generic `read:stack` permission, not which stack the token is bound to: [2](#0-1) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which merely checks the token's permission list, not its `stack_id`: [3](#0-2) 

So a token created with `stack_id` set to Stack A (e.g. the `here_come_the_walrus` fixture, `stack: shipit`, permission `read:stack`) — intended to only ever see Stack A via the scoped `stacks` relation — can be used against `GET /api/stacks/:stack_id/cc_menu.xml` with an arbitrary `stack_id` belonging to Stack B, and the request will succeed because `stack` never checks `current_api_client.stack_id`.

### Impact Explanation
This breaks the equality `token.stack_id == stack_being_read`, allowing unauthenticated (relative to the target stack) read access to another stack's deploy/rollback state (last deploy status, timestamps, running state) exposed by the CCTray XML feed. This matches the in-scope High impact category "unauthenticated read of stack state ... task streams or deploy output" for a stack the token was never granted access to.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission (a routine, low-privilege credential type used for CI/CCTray integrations) can trivially trigger this by substituting a different `stack_id` in the URL — no additional secrets, sessions, or elevated access required beyond possessing one legitimately-scoped token.

### Recommendation
Have `CCMenuController#stack` use the scoped `stacks` relation (as `BaseController` does) instead of the unscoped `Stack.from_param!`, e.g. `stacks.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot read state for stacks outside their `stack_id` binding.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` token bound to Stack A with permission `read:stack` (e.g. via `CCMenuUrlController`/`api_client` creation flow, or fixture `here_come_the_walrus`).
2. Send `GET /api/stacks/:stack_B_id/cc_menu.xml?token=<Stack-A-scoped-token>` where `stack_B_id` is any other stack's id/param.
3. Observe the response renders `stack/cc_menu/project` for Stack B (its latest deploy/rollback status), even though the token is only supposed to be authorized for Stack A, because `stack` in `CCMenuController` never checks `current_api_client.stack_id`.
