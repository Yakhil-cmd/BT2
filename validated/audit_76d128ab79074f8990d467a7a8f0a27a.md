### Title
Webhook signature verification is bound to an attacker-controlled `repository.owner.login`/`organization.login` field rather than the repository the payload actually writes to — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC secret) to validate a webhook against using a value read straight out of the **unverified** JSON body, and `GitHubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as an automatic pass. The value used to pick the verifying organization is not the same value the downstream event handlers use to decide which `Repository`/`Stack` the event applies to, so the two are never checked for equality. This mirrors the Real Wagmi bug: a value used to compute/validate one thing (the "fee"/here "org that verifies") is disconnected from the value that actually gets acted upon (the pool that trades/here "repo whose Stack is written to").

### Finding Description
`before_action :verify_signature` computes the organization to authenticate against from the raw JSON body before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` then fetches that organization's `GitHubApp`, and signature verification is delegated to it: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If that org's `webhook_secret` is blank (the setup docs explicitly describe it as **optional**, not mandatory: "Webhook secret (optional)"), verification unconditionally succeeds regardless of the request body: [4](#0-3) 

Once `verify_signature` passes, the full, still-unauthenticated `params` hash is dispatched verbatim to every registered handler for the event: [5](#0-4) 

Handlers (e.g. the pull-request/push/status handlers under `app/models/shipit/webhooks/handlers/`) resolve the target repository/stack from other fields of that same payload, such as `repository.full_name`, independently of the `repository.owner.login` field used purely to pick the verifying secret:



Because these two lookups (which secret authenticates the request vs. which repository/stack the request is applied to) read different, independently attacker-controllable subfields of the same forged JSON body, an attacker does not need to know the secret of the organization that owns the target stack — they only need one configured organization anywhere in the Shipit installation to have a blank `webhook_secret`.

The equality that should hold and is broken:
`organization whose secret authenticated the request == organization that owns the repository/stack the request is applied to`

### Impact Explanation
This lets an unauthenticated internet attacker forge `push`, `status`, `check_suite`, `pull_request`, or `membership` webhook events for **any** stack in the Shipit installation, as long as any one configured GitHub org (which can be the attacker's own, unrelated org, or simply an org whose admin left the optional secret unset) has no `webhook_secret`. By setting `repository.owner.login`/`organization.login` to that unprotected org while pointing `repository.full_name` (and other repo-identifying fields consumed by handlers) at a different, "protected" stack, the attacker can:
- Forge `push` events to change the tracked head SHA, potentially triggering unauthorized/continuous deploys.
- Forge `status`/`check_suite` events to fake CI success and get merge requests through the merge queue.
- Forge `membership` events to create arbitrary teams/users.

This falls under "unauthorized deploy" / "cross-repository writes" — a Critical-severity outcome per the rules, reachable without any Shipit session, API token, or repository write access — only the ability to send an HTTP POST to the public `/webhooks` endpoint.

### Likelihood Explanation
Exploitability hinges entirely on the presence of at least one configured GitHub organization with a blank `webhook_secret`. This is not a hardening failure outside the engine's control: the engine's own setup documentation explicitly marks the field "optional," and both shipped example config files show `webhook_secret: # nil` as a supported value. In multi-org installs (a first-class, documented configuration path per `secrets_double_github_app.yml`), it is plausible that only some orgs have a secret configured (e.g., during onboarding), making this readily triggerable without any special access.

### Recommendation
- Do not select the verifying organization from unauthenticated payload data. Verify the HMAC signature against every configured `webhook_secret` (or, at minimum, cross-check that the resolved verifying organization equals the organization actually referenced by the fields handlers will use, e.g. `repository.full_name`).
- Do not treat a missing `webhook_secret` as automatically valid; require every configured GitHub App to have a webhook secret, or refuse to accept unauthenticated webhooks entirely.
- Make handlers re-validate that the organization used for verification matches the organization of the repository the event claims to modify.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.yml`: `victim-org` (has `webhook_secret` set) and `no-secret-org` (leaves the documented-optional `webhook_secret` blank), each hosting an installed Shipit stack.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo",
    "name": "victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `repository_owner` to `"no-secret-org"`, fetches its `GitHubApp`, and `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank — no valid `X-Hub-Signature` header is required.
4. The push handler then processes the payload using `repository.full_name` ("victim-org/victim-repo"), applying the forged event to the victim stack, e.g. enqueuing `GithubSyncJob` for it as shown in the existing test suite's expectations. [6](#0-5) 

Note: full internal resolution logic of `push_handler.rb` mapping `repository.full_name` to a `Stack` was not directly re-read line-by-line in this session (only located via `grep_search`); the core authentication bypass (steps 2–3, in `webhooks_controller.rb` and `github_app.rb`) is fully confirmed from source.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
