Confirmed: `StatusHandler#process` writes a `CommitStatus` directly from the raw webhook payload (`params.state`, `context`, etc.) to any `Commit` matching `sha`, with no re-verification against GitHub's API — this is the strongest available escalation of the mismatch found in `WebhooksController`.

### Title
Webhook signature is verified against `repository.owner.login` while all event handlers act on the unverified `repository.full_name`, allowing a legitimate webhook secret holder for one GitHub organization to forge events (including fake CI status) for a stack belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which HMAC secret to check against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and validates the raw POST body against that organization's `webhook_secret`. [1](#0-0)  Once the signature passes, `create` dispatches the entire parsed JSON body, unmodified, to every registered handler for the event. [2](#0-1)  Every handler, however, determines which `Stack`/`Repository` to mutate using `payload.dig('repository', 'full_name')` in `Handler#repository_name` / `#stacks`, a completely different JSON field that is never cross-checked against `repository.owner.login`. [3](#0-2) 

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handler acts on`

Concretely: `repository.owner.login` (checked) should equal the owner encoded in `repository.full_name` (used to resolve `stacks`). Nothing in `verify_signature` or `Handler` enforces this equality — HMAC-SHA1 over the raw body only proves *some* org's secret was used to sign *that exact byte string*; it says nothing about internal consistency between two independent JSON fields inside that body.

In a Shipit deployment configured for multiple GitHub organizations (`Shipit.github_organizations`, `github_app_config(organization)` in `lib/shipit.rb`), each organization owner legitimately knows their own `webhook_secret` because they configure it themselves in GitHub's webhook settings for their own org/repo. An attacker who is a legitimate admin of Organization A (and thus knows Org A's `webhook_secret`) can:

1. Craft an arbitrary JSON payload where `repository.owner.login` (or `organization.login`) = `"OrgA"` (so `verify_signature` selects and validates against Org A's secret, which they know) and `X-Github-Event` = `status` (or `push`, `check_suite`, `membership`, `pull_request`, etc.).
2. Set `repository.full_name` = `"OrgB/victim-repo"` — a repository belonging to a completely different, victim organization already tracked by Shipit.
3. Sign the raw body themselves with Org A's known secret and POST it directly to Shipit's `/github/webhooks` endpoint (no GitHub involvement required).
4. `verify_signature` passes (Org A's secret matches Org A's owner login field). `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` using attacker-controlled `state`, `context`, `description`, `target_url` for any commit sha belonging to the victim's stack. [4](#0-3) 

This is not merely a benign echo of GitHub state — Shipit's deploy gating explicitly checks commit statuses (deployability), so forged `success` statuses for victim commits can be used to make undeployable/unreviewed commits appear deployable in another organization's stack.

Other handlers are similarly exposed to the same trust break, e.g. `CheckSuiteHandler` schedules check-run refresh for a victim stack/branch/sha, and `PushHandler`/`MembershipHandler` operate on stacks/teams resolved purely from the unverified `full_name`/`organization.login` fields inside the same signed-by-someone-else payload. [5](#0-4) [6](#0-5) 

### Impact Explanation
Forging a `success` `CommitStatus` on a victim organization's tracked repository can flip Shipit's deployability checks for that commit, enabling an unauthorized deploy on a stack the attacker has no legitimate access to — this is a cross-repository write and unauthorized-deploy primitive, matching the "Critical" impact bar (unauthorized deploy / cross-repository writes) defined for this analog class.

### Likelihood Explanation
Requires the attacker to be a legitimate, credentialed admin/owner of at least one GitHub organization that is already onboarded to the same multi-tenant Shipit instance (so they know that org's `webhook_secret` through GitHub's own webhook configuration UI) and to know or guess the victim's tracked repository full name and a deployable commit sha — no `ApiClient` token, session, or GitHub App private key is needed, and the request bypasses GitHub entirely by hitting the webhook endpoint directly with a self-signed body.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#stacks`, assert that the organization used to select/verify the webhook secret is the same organization encoded in `repository.full_name` (and `organization.login` where present) before dispatching to handlers; reject the request otherwise. Alternatively, resolve the signing organization solely from the `full_name`/repository owner actually used for stack lookup, eliminating the two independent trust anchors.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret`, and a tracked `Stack` for `OrgB/victim-repo` with an undeployed commit `sha=deadbeef`.
2. As the (legitimate) admin of `OrgA`, construct:
```json
{
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/forged",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(OrgA_webhook_secret, body)>` and POST to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` passes because `repository_owner` resolves to `OrgA` and the HMAC matches `OrgA`'s secret. [7](#0-6) 
5. `StatusHandler` writes a forged `success` status onto the victim commit belonging to `OrgB/victim-repo`, resolved purely via `payload.dig('repository', 'full_name')`. [4](#0-3) [3](#0-2)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
