### Title
Webhook signature is verified against the organization in `repository.owner.login`, but event handlers act on the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate `X-Hub-Signature` based solely on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body. The actual webhook handlers that mutate state (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers) resolve the target `Stack`/`Repository` using a *different* field of the same payload: `repository.full_name`. Nothing enforces that these two fields describe the same repository/organization, so a signature that is valid for organization A can be replayed with a `full_name` pointing at organization B's tracked repository.

### Finding Description
Signature verification:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Shipit supports multiple GitHub organizations, each with its own independently configured `webhook_secret` (`lib/shipit.rb#github`, `GitHubApp#initialize`): [2](#0-1) [3](#0-2) 

`verify_webhook_signature` HMACs the raw body with the `webhook_secret` belonging to whichever org `repository_owner` names: [4](#0-3) 

But the handlers that actually process the payload after signature checks pass resolve the target stacks from a **different** field — `repository.full_name` — via `Handler#stacks`/`#repository_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` and `StatusHandler` both rely on this: `PushHandler` finds stacks via `stacks` and triggers `stack.sync_github`, while `StatusHandler` writes a commit status for any `Commit` matching `params.sha` regardless of organization: [6](#0-5) [7](#0-6) 

**Binding broken:** `repository.owner.login` (the field the HMAC-authenticated organization is derived from) ≠ `repository.full_name`'s owner (the field whose repository/stacks are actually written to). The code implicitly assumes these are equal but never checks it, exactly mirroring the reported smart-contract bug class where the wrong field was checked (checking `_totalTournamentEarnings`/`_totalOtherEarnings` instead of the actually-mutated `tournamentDistributionAmount`/`otherDistributionAmount`).

### Impact Explanation
An attacker who legitimately administers **any one** organization configured in Shipit's multi-org `github:` secrets (and therefore knows that org's own `webhook_secret`, which they themselves provisioned when creating their GitHub App) can forge a webhook whose `repository.owner.login`/`organization.login` is their own org (so `verify_signature` picks their own `GitHubApp` and the HMAC check succeeds using their known secret) while `repository.full_name` names a completely different, victim organization's tracked repository.

With a `status` event, this lets the attacker post arbitrary commit statuses (`Commit#create_status_from_github!`) for any commit SHA tracked by Shipit across *any* organization, regardless of which org's secret validated the signature. Because Shipit uses commit statuses/checks to gate deploy eligibility, this can be used to flip required checks to green and enable an **unauthorized deploy** on a repository/organization the attacker does not control — satisfying the Critical/High impact bar ("an unauthorized deploy" / cross-repository writes) defined in scope rules.

### Likelihood Explanation
Requires only that the attacker controls (or can obtain webhook-secret knowledge for) one of the organizations already configured in Shipit's `secrets.github` multi-org map — a scenario explicitly supported and documented in `docs/setup.md`'s "Using Multiple Github Applications" section. No repository write access, Shipit session, or GitHub App private key exfiltration is required — only knowledge of a secret the attacker was legitimately given for their own org. This is a realistic configuration for any Shipit deployment serving more than one GitHub organization.

### Recommendation
After computing the verified organization for the signature, cross-check that the same organization owns the repository being acted upon before dispatching to handlers — e.g., derive the acting organization/repository consistently from a single verified field, or explicitly assert `repository.full_name.split('/').first == repository_owner` (case-insensitively) in `WebhooksController#verify_signature`/`#create`, rejecting the request with 422 otherwise.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `attacker-org` (webhook_secret known to attacker) and `victim-org` (tracks stack for `victim-org/victim-repo`, commit `abc123` exists in Shipit).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org webhook_secret, raw_body)>`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC validates successfully.
5. `StatusHandler#process` runs unconditionally on `Commit.where(sha: "abc123")` — which belongs to `victim-org` — creating a forged "success" status entirely outside of `attacker-org`'s authority, potentially satisfying required-check gating for a `victim-org` deploy.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
