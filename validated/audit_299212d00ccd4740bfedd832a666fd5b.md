### Title
Webhook signature verification keys on `repository.owner.login` while every event handler resolves state from `repository.full_name` / a separate `organization.login` field, letting a holder of *any* configured org's `webhook_secret` forge events for a different org's stacks — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC against using `repository_owner`, a value read straight out of the attacker-controlled JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). But the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, and `MembershipHandler#find_or_create_team!`) key off a *different* field in the same body: `repository.full_name` or `organization.login` used to create/attach a `Team`. Because the whole raw body is attacker-supplied and the signature only proves "whoever crafted this body knows the secret for the org named at `repository.owner.login`", nothing binds that org to the org/repo that the handler subsequently writes to. ### Finding Description
The binding that must hold is:

`org used to select webhook_secret for signature verification == org/repository the handler actually mutates`

Before the attacker's request: for a genuine GitHub webhook, `repository.owner.login`, `repository.full_name`, and `organization.login` are all consistent, because GitHub itself generated the payload and signed it with the secret configured for that specific installation.

After the attacker's request: Shipit supports **multiple GitHub Apps/organizations** in one deployment (see the multi-org config shape in `config/secrets.development.shopify.yml`), each with its own `webhook_secret`. `Shipit.github(organization: repository_owner)` looks up the app config purely by the org name embedded in the JSON, and `verify_webhook_signature` just HMACs the raw POST body with that org's secret: [5](#0-4) 

Since the attacker fully controls the raw body content (they are forging the request, not replaying a real GitHub webhook), they can set `repository.owner.login` = `"org-A"` (an org whose `webhook_secret` they know — e.g. because they administer a repo that Shipit is also configured to receive webhooks from under org A) while setting `repository.full_name` = `"org-B/target-repo"` or `organization.login` = `"org-B"`, a *different* org/repo actually configured as a Shipit stack. The signature check only validates that the signer knows org A's secret; it says nothing about org B. The downstream handler never re-checks which org signed the request — it just does `Repository.from_github_repo_name(repository_name)` off `repository.full_name`, or creates/attaches a `Team` using `params.organization.login`, decoupled from the org that authenticated the request.

Concretely:
- `PushHandler` would call `stack.sync_github(expected_head_sha: params.after)` for any stack matching a forged `repository.full_name`, letting an outsider (who is not authorized on org B at all) trigger sync jobs against org B's stacks.
- `MembershipHandler` is more serious: it does `Team.find_or_create_by!(github_id: ...) { team.organization = params.organization.login }` then `team.add_member(member)` for an arbitrary `member.login`. Since `Shipit.github_teams` (the authorization gate in `app/controllers/concerns/shipit/authentication.rb`, `current_user.authorized?`) is based on `Team` membership rows created exactly this way, an attacker who knows any one configured org's `webhook_secret` can forge a `membership` event naming a *different* org's team id/slug/login and an arbitrary GitHub login as `member`, adding that (attacker-controlled) login into a `Team` that satisfies `Shipit.github_teams`, thereby self-granting authorization once they subsequently log in via OAuth with that GitHub login. ### Impact Explanation
This breaks the "organization that authenticated versus the organization/repository that is written" binding called out in scope. In a multi-org Shipit deployment, an attacker who legitimately obtains (or is issued) a `webhook_secret` for one configured organization can forge events that write state (teams, memberships, triggered syncs) attributed to a completely different organization's resources without ever having credentials for that second organization. The membership-forging path escalates directly into `Shipit.github_teams` authorization — one of the explicitly listed High-severity impacts — because team membership computed this way is the sole gate checked by `User#authorized?`.

### Likelihood Explanation
Requires the attacker to possess a valid `webhook_secret` for *some* organization configured in the same Shipit instance (a precondition allowed by the rules — this is not "requiring an ApiClient token" or "repository write access" on the *target* org, only a secret for an unrelated configured org). Given that is met, forging the HTTP POST is trivial: compute HMAC-SHA1 of a hand-crafted JSON body with the known secret and set `X-Hub-Signature` accordingly — no GitHub interaction needed at all, since `WebhooksController` accepts any POST with a valid signature regardless of source.

### Recommendation
Bind the signature-verification org to the org/repo actually acted upon:
- After verifying the signature, re-derive `repository_owner`/`organization.login` used by handlers and assert it matches the org whose secret validated the signature, rejecting (422) on mismatch.
- In `Handler#repository_name` / `MembershipHandler#find_or_create_team!`, cross-check `payload.dig('repository','owner','login')` (or `organization.login`) equals the org resolved during signature verification before performing any lookups or writes.

### Proof of Concept
1. Shipit configured with two orgs, `org-A` (secret `SECRET_A`, attacker knows it — e.g. it was rotated and leaked, or the attacker is a legitimate but low-trust member of org A's infra) and `org-B` (secret `SECRET_B`, unknown to attacker), both with GitHub Apps pointed at the same `/webhooks` endpoint, and org-B has a Shipit `Team` gating `Shipit.github_teams`.
2. Attacker crafts:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "OrgB Admins", "slug": "org-b-admins", "url": "https://x" },
  "organization": { "login": "org-B" },
  "member": { "login": "attacker-gh-login" },
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/secret-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>` and sends `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-A")` (from `repository.owner.login`) → verifies successfully with `SECRET_A`.
5. `MembershipHandler` runs using `params.organization.login == "org-B"`, creating/attaching team `org-b-admins` and adding `attacker-gh-login` as a member — despite the attacker never having authenticated as, or held any secret for, org B.
6. Attacker then logs into Shipit via GitHub OAuth as `attacker-gh-login`; `User#authorized?` finds the forged `Team` membership matching `Shipit.github_teams` and grants access.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
