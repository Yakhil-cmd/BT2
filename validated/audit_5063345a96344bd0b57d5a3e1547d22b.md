### Title
CCMenu Controller Bypasses ApiClient Stack Scoping, Allowing a Stack-Scoped Token to Read Any Stack's Deploy State - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates callers with a bare query-string token and then resolves the target stack directly from `params[:stack_id]`, without ever checking whether the authenticated `ApiClient` is scoped to that stack. This breaks the same trust binding described in the external report: an authorization artifact (there, a user account balance/ownership; here, an `ApiClient`'s `stack_id` scope) is not consulted when the "acted-upon" resource is selected, so a narrowly-scoped credential can be used to touch a resource it was never authorized for.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id` [1](#0-0) . The generic `Api::BaseController` correctly enforces this scope when resolving stacks: it restricts the queryable set to `current_api_client.stack_id` before looking up the requested stack. [2](#0-1) 

However, `Api::CCMenuController` does not use this scoped `stacks`/`stack` helper. It overrides `authenticate_api_client` to accept a token from `params[:token]` (used for the CCMenu XML feed, which has no way to attach an `Authorization` header) and defines its own `stack` method that resolves the requested stack directly from `params[:stack_id]`, with no reference to `current_api_client.stack_id` at all: [3](#0-2) 

The only authorization check performed is `require_permission :read, :stack`, which merely verifies the client's `permissions` array contains `read:stack` — it says nothing about *which* stack the client is entitled to read. [4](#0-3) [5](#0-4) 

Such stack-scoped tokens are trivially obtainable by any user with read access to a stack via the "CCMenu URL" feature, which creates (or reuses) an `ApiClient` scoped to `read:stack` for the current stack: [6](#0-5) 

The equality that should hold is: `token.stack_id == stack_being_rendered.id` (when `token.stack_id` is present). The controller never checks this — the token only authorizes an *operation class* (`read:stack`), but the code lets it touch **any** `stack_id` supplied in the URL.

### Impact Explanation
This is an authorization-scope escalation: a token minted for stack A can be replayed with a different `stack_id` to read the deploy/build status (last deploy id, running/success/failure state, lock status) of any other stack in the Shipit instance — data intended to be gated by per-stack permission scoping. This matches the "High" impact bucket of unauthorized read of stack state / deploy output via a token that is supposed to be scoped narrowly, since it discloses deploy status and lock state across stacks the token holder was never granted access to.

### Likelihood Explanation
High. Any user who can view a single stack can self-service mint a stack-scoped `read:stack` `ApiClient` via the built-in "CCMenu URL" link, then trivially change the `stack_id` route parameter while keeping the same `token` query parameter to enumerate other stacks. No special privileges, secrets, or GitHub credentials are required beyond ordinary Shipit access to one stack.

### Recommendation
In `Api::CCMenuController#stack`, resolve the stack through the same scoping helper as `Api::BaseController` (i.e., restrict to `current_api_client.stack_id` when present) instead of calling `Stack.from_param!(params[:stack_id])` unconditionally:
```ruby
def stack
  @stack ||= (current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all)
                .from_param!(params[:stack_id])
end
```

### Proof of Concept
1. As User A with read access only to Stack A, visit the CCMenu URL endpoint for Stack A to obtain a stack-scoped token: `GET /stacks/:stack_a_id/ccmenu_url` → returns a `token` bound to an `ApiClient` with `stack_id = stack_a.id`, `permissions = ['read:stack']`. [7](#0-6) 
2. Call `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token_from_step_1>` where Stack B is a different, unauthorized stack.
3. `authenticate_api_client` accepts the token (it only verifies signature/existence, not stack match) [8](#0-7) ; `require_permission :read, :stack` passes because the token carries `read:stack` [9](#0-8) [5](#0-4) ; `stack` resolves Stack B directly from the URL param, ignoring the token's `stack_id = stack_a.id` [10](#0-9) .
4. The response discloses Stack B's last deploy status/lock state, even though the token was only ever authorized for Stack A.
