### Title
Untrusted skill file `Size` metadata used as pre-fetch limit check allows unbounded terminal output during `gh skill preview` - (File: pkg/cmd/skills/preview/preview.go)

### Summary
`renderAllFiles` in `pkg/cmd/skills/preview/preview.go` enforces a `maxTotalBytes` (512 KiB) budget on the total amount of skill-repo content dumped to the terminal, but the check is performed *before* fetching each file, using the attacker-controlled, declared `f.Size` field from the Git tree listing rather than the actual fetched blob size. Analogous to the Rubicon `enforceReserveRatio` bug — where a size/limit invariant is validated only against pre-action state and never re-validated after the action executes — a single file with a small declared size but arbitrarily large real content can pass the check and be streamed to the terminal in full, bypassing the intended cap.

### Finding Description
In `renderAllFiles`:
```go
pkg/cmd/skills/preview/preview.go:292-314
for _, f := range extraFiles {
    if fetched >= maxFiles { ... break }
    if totalBytes+f.Size > maxTotalBytes {
        ...
        break
    }
    fileContent, fetchErr := discovery.FetchBlob(apiClient, hostname, owner, repo, f.SHA)
    ...
    fetched++
    sanitized := fileContent.String()
    totalBytes += len(sanitized)
    fmt.Fprintf(out, "\n%s\n\n", cs.Bold("── "+f.Path+" ──"))
    fmt.Fprint(out, sanitized)
    ...
}
```
`f.Size` originates from `discovery.ListSkillFiles`, which is populated from the Git Trees API response for the attacker-controlled skill repository (`internal/skills/discovery/discovery.go`, `func FetchBlob`). This value is fully under the control of whoever authored the previewed repository. The loop's guard `totalBytes+f.Size > maxTotalBytes` is evaluated using this untrusted, pre-fetch size *before* `discovery.FetchBlob` retrieves the actual content. The real content byte count (`len(sanitized)`) is computed only *after* the fetch has already completed and the content has already been written to `out` (the pager/terminal). There is no post-fetch check that aborts or truncates output if the actual fetched size exceeds the limit — the invariant "total content <= 512 KiB" is enforced only against the stale, attacker-supplied metadata, exactly mirroring the Rubicon pattern of checking a security invariant before an action but never re-checking it afterward.

By crafting a tree entry that reports a small `size` (e.g. a few bytes) for a blob whose actual content is very large (megabytes), the size check passes, `FetchBlob` retrieves and returns the full content, and it is written directly to the user's terminal/pager via `fmt.Fprint(out, sanitized)` before `totalBytes` is ever updated to reflect reality.

### Impact Explanation
`gh skill preview` is explicitly designed to let a user inspect an *untrusted* skill repository before installing it (`internal/skills/discovery`, `source.ValidateSupportedHost`). The `maxTotalBytes`/`maxFiles` guard exists specifically to bound how much attacker-supplied content is dumped to the user's terminal in one command invocation — protecting against resource exhaustion and against flooding a non-TTY/pipe consumer with attacker content. Because the check trusts declared size instead of validating actual size before/while writing, a malicious skill author can:
- Cause unbounded amounts of data to be written to the terminal/pager in a single file entry, defeating the size cap entirely.
- Potentially exhaust memory/disk (pager buffering) or terminal resources with a single oversized "file" that appears to metadata-check as tiny.

This is a moderate-impact, low-complexity DoS/resource-exhaustion issue reachable purely by an attacker who controls a public repository that a victim previews with `gh skill preview owner/repo`; no privileged access or MITM is required.

### Likelihood Explanation
Likelihood is fairly high for triggering the condition: any GitHub repository owner can freely set arbitrary blob content independent of what the Git Trees API reports for `size` is not normally forgeable (`size` in the trees API is server-computed from the actual blob), which is a caveat — **this weakens the finding**: GitHub's Git Trees API computes `size` from the real blob, so under normal use `f.Size` should match the fetched blob length. The exploitability therefore reduces to any client-side/library discrepancy between the declared `size` field and the bytes actually returned by `discovery.FetchBlob` (e.g., truncation/re-encoding differences, or content substitution between listing and fetch calls if the tree and blob are fetched at different times/refs). I was not able to fully verify from the available index whether `discovery.FetchBlob` and `discovery.ListSkillFiles` operate against the exact same immutable commit/tree SHA in all code paths, which is necessary to know whether a genuine metadata/content mismatch is achievable server-side.

### Recommendation
- Do not rely on the pre-fetch declared `f.Size` as the sole gate. Enforce the `maxTotalBytes` budget by bounding the actual read from `discovery.FetchBlob` (e.g., using an `io.LimitReader` sized to the remaining budget) so no single file can write more than the remaining allowance to the terminal, and truncate/abort if the true content exceeds it.
- After fetching, re-validate `totalBytes` (including the just-fetched file) against `maxTotalBytes` before writing to `out`, mirroring the Rubicon fix of re-checking the invariant after the state-changing action rather than only before it.

### Proof of Concept
I could not construct or run an end-to-end PoC without live access to fork a GitHub repository and control raw Git blob contents (this would require write access to a real host repository to test whether the Trees API `size` field can be made to diverge from actual blob content, which the current index/tools do not support). The code-path analysis above is the basis for this finding; a background Devin session with terminal/GitHub access would be needed to confirm exploitability by publishing a test repository and running `gh skill preview` against it.
