### Title
Missing `return` after caught exception in `handleSavedPrivatePayments` causes duplicate/undefined-state processing of a private payment reachable by any private-payment counterparty - ([File: network.js])

### Summary
The PaddlePaddle `paddle.crop` bug is a missing bounds/validity check that leads to a null-pointer dereference and process crash (CWE-476). In `ocore`, the closest reachable analog is in `network.js`'s `handleSavedPrivatePayments()`, where a caught exception from `objectHash.getBase64Hash()` is not followed by a `return`, so the function keeps executing with a `json_payload_hash` variable that was never assigned (`undefined`), and — more importantly — re-invokes `privatePayment.validateAndSavePrivatePaymentChain()` a second time after the `ifError`/cleanup path already ran, using the same `cb` from `async.each`. [1](#0-0) 

### Finding Description
`handleSavedPrivatePayments()` is invoked for every row in `unhandled_private_payments`, i.e. every private payment JSON previously stored for the wallet's own device by a private-payment counterparty (the sender of the private chain to this device). Inside `validateAndSave`:

```
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
``` [2](#0-1) 

`objectHash.getBase64Hash()` throws when `objHeadPrivateElement.payload` contains a malformed structure that `object_hash`'s canonical-JSON/hashing routines cannot process (e.g. non-primitive/invalid types, deeply nested or malformed `outputs`/`inputs` objects supplied by the private-payment sender inside `arrPrivateElements[0].payload`, which is attacker-supplied JSON stored verbatim from the network message in `unhandled_private_payments.json`). When this throws, the `catch` block already calls `deleteHandledPrivateChain(row.unit, ..., cb)`, which invokes `cb()` to signal completion to `async.each`. But execution does **not** stop there: control falls through to the line building `key` (using the now-`undefined` `json_payload_hash`) and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again. That function's callbacks (`ifOk`, `ifError`, `ifWaitingForChain`) each also call `cb()` (directly or via `deleteHandledPrivateChain`), so `cb` for this `async.each` iteration is invoked a second time.

Calling the iteratee callback of `async.each` more than once is undefined behavior in the `async` library and can result in `unlock()` and `eventBus.emit("new_my_transactions", ...)` firing multiple times, `assocNewUnits` mutations across iterations racing, and reentrant execution of `validateAndSavePrivatePaymentChain` on the same private element while the first pass may still be inside its own DB transaction (`BEGIN/COMMIT/ROLLBACK` in `private_payment.js`). This is the structural analog of the PaddlePaddle bug: a code path where an error branch fails to fully bound/stop execution before continuing to use a value that was never properly produced (`json_payload_hash` is `undefined`) and before the object is handed to further processing that assumes single-invocation semantics. [3](#0-2) [4](#0-3) 

### Impact Explanation
Triggering the exception path repeatedly (a private-payment counterparty can control `arrPrivateElements[0].payload` freely, since it is attacker-supplied private-payment content persisted into `unhandled_private_payments`) leads to:
- Double invocation of the `async.each` iteratee callback, which can corrupt the mutex-protected `["saved_private"]` critical section (double `unlock()`), potentially unlocking the mutex prematurely while other private-payment processing is still in flight, and duplicate `eventBus.emit("new_my_transactions", ...)` / `new_direct_private_chains` events.
- Re-entrant calls into `validateAndSavePrivatePaymentChain` -> `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)` which opens a new DB transaction on the same private element concurrently with (or after) the transaction started by the first pass, risking inconsistent private-payment/spend-proof bookkeeping (`spend_proofs`, `outputs.is_spent`) for the node's own wallet.
- This does not directly enable unauthorized spending of others' funds, but it can corrupt/lose track of private payment state for the receiving wallet and destabilize the private-payment processing pipeline for the affected device, which is a node-disagreement/availability-class impact rather than a full nullptr-crash DoS.

### Likelihood Explanation
Any private-payment counterparty who sends a wallet a private payment chain whose head payload cannot be hashed by `objectHash.getBase64Hash` (malformed nested structure, non-canonicalizable values, etc.) reaches this code path automatically the next time `handleSavedPrivatePayments()` runs (it runs on every new private payment and periodically). No special privileges are needed beyond being able to send a private payment/chain to the target device, which is the normal, unauthenticated-by-design private payment flow between wallet counterparties.

### Recommendation
Add a `return;` immediately after the `catch` block's cleanup call in `network.js`'s `validateAndSave` inner function, so that when `getBase64Hash` throws, the function stops and does not fall through to build `key` with an `undefined` hash or re-invoke `validateAndSavePrivatePaymentChain`/`cb` a second time. Additionally, validate/sanitize `objHeadPrivateElement.payload` structurally before calling `getBase64Hash`, and audit all other call sites where `try { ... } catch (e) { ...; someCleanupThatCallsCb(); }` patterns are used without a subsequent `return`, to ensure a single, well-defined completion path per async iteration.

### Proof of Concept
1. As a private-payment counterparty (paired device or asset-issuer wallet peer), construct a private-payment chain whose head element (`arrPrivateElements[0]`) has a `payload` object that causes `objectHash.getBase64Hash` to throw (e.g., a payload with a value type that `object_hash`'s serializer rejects, such as a `Symbol`-like or excessively nested/circular-shaped object smuggled through JSON that nonetheless parses but fails during canonical stringification/hashing).
2. Send this private-payment chain to the victim's device through the normal private-payment/`private_payment` network message flow so it gets persisted into `unhandled_private_payments` and later processed by `handleSavedPrivatePayments()`.
3. Observe that `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws inside `validateAndSave`, the `catch` block calls `deleteHandledPrivateChain(..., cb)` (first `cb()` call), but execution continues to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which itself will invoke a second `cb()` through one of its callbacks — resulting in double-callback behavior on the `async.each` iteratee and reentrant private-payment processing for the same chain.

Note: I was not able to execute this against a live node to confirm the exact downstream `async`-library failure mode (e.g., whether it throws, silently misbehaves, or triggers `unlock()` twice); this is based on static code-path analysis of the missing `return` and the reentrant call structure shown above.
