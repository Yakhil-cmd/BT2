### Title
`sign` handler skips unit/message validation for `signed_message` requests before triggering the signing dialog - (File: ocore--009/wallet.js)

### Summary
In `handleMessageFromHub`'s `"sign"` case, the two branches that lead to the user-facing `signing_request` event are validated very differently. The plain-unit branch runs the full network/consensus validator (`network.handleOnlineJoint`) and only emits `signing_request` after the `"validated-"+unit` event confirms the unit is valid. The `signed_message` branch instead performs only a shallow field-whitelist check and immediately emits `signing_request`, never invoking `signed_message.validateSignedMessage()` or any equivalent deep validation. This mirrors the reported bug class: a newer/alternate code path omits a validation hook (`msgInspector` in the original report) that the "main" path calls.

### Finding Description
`handleMessageFromHub` handles the `"sign"` subject, which is reachable by any paired device (a normal use case for multisig/multilateral signing) [1](#0-0) .

For a normal unsigned unit, before the wallet ever asks the user to approve/sign anything, the code builds a joint and pushes it through `network.handleOnlineJoint`, waiting for the `"validated-"+unit` event to confirm the unit passes the full consensus-level `validation.js` checks (definitions, payment balances, double-spend checks, etc.) before emitting `signing_request`: [2](#0-1) 

However, for the `signed_message` variant of the same `"sign"` request, the code takes a completely different, much weaker path: it only checks that no unexpected top-level fields exist (`hasFieldsExcept(objUnit, ["signed_message", "authors", "version"])`), computes an artificial hash, and immediately fires the `signing_request` event with no call into `signed_message.validateSignedMessage()` (the real validator, which checks authors, definitions, versions, sizes, and other constraints as shown in `signed_message.js`): [3](#0-2) [4](#0-3) 

The pre-validation checks earlier in the `"sign"` handler (`ValidationUtils.isValidAddress`, signing-path regex, payload-hash checks) apply generically to both branches, but they do not perform the structural/semantic validation that `validateSignedMessage` does (e.g., rejecting malformed `authors`, bad/duplicate addresses, oversized/garbage `signed_message` content, disallowed `definition`, etc.) [5](#0-4) . As a result, a malicious pairing peer can send a `"sign"` request with `signed_message` set and a crafted, unvalidated `unsigned_unit`, and it will reach the UI confirmation dialog and the wallet's cosigning device logic without ever passing through the deep validator that the equivalent unit-signing path enforces.

### Impact Explanation
Because the `signed_message` branch bypasses `validateSignedMessage`, malformed or malicious "documents" can be presented to a user for signing that would otherwise have been rejected outright. Depending on how the UI/confirmation-dialog layer downstream treats `objUnit` (display of `authors`, `address`, arbitrary `signed_message` content), this can result in a user being tricked into signing over unvalidated/malformed data structures, potentially producing an authentifier/signature the requester can later replay or misuse in another (validated) context, or in a crash/DoS of the wallet UI/device software when it tries to render or process the unchecked structure. This falls into the "wallet and contract message handling" and "AA/DAG trigger" adjacent category explicitly permitted by the rules (paired device is a legitimate reachable actor).

### Likelihood Explanation
Any paired device (a normal, expected communication partner in the multisig/multilateral cosigning protocol) can send a `"sign"` message with `signed_message` populated; no privileged or malicious-node/hub access is required — this is a standard device-to-device message that `handleMessageFromHub` processes for every incoming `"sign"` subject. The asymmetry between the two branches (full validation via `network.handleOnlineJoint` vs. no validation at all) is directly visible in the code and easily triggered by simply choosing the `signed_message` code path instead of `unsigned_unit`.

### Recommendation
Before emitting `signing_request` for the `signed_message` branch, call `signed_message.validateSignedMessage()` (or an equivalent complete validator) on `objUnit`, exactly as the `unsigned_unit` branch relies on the full unit validator (`network.handleOnlineJoint`) prior to prompting the user. Only proceed to `eventBus.emit("signing_request", ...)` after the deep validation succeeds.

### Proof of Concept
1. Pair with a victim device (legitimate step in the multisig/multilateral protocol).
2. Send a `"sign"` message to the victim's hub with body:
   ```json
   {
     "address": "<victim's own address>",
     "signing_path": "r",
     "unsigned_unit": {
       "signed_message": "<attacker-controlled/malformed content>",
       "authors": [ { "address": "<victim's own address>" } ]
     }
   }
   ```
3. In `wallet.js`, the checks at lines 253–330 pass (they don't inspect `signed_message` content), `findAddress` resolves the address as local, and because `objUnit.signed_message` is truthy and `hasFieldsExcept` passes, the code immediately fires `signing_request` at line 348 without ever invoking `signed_message.validateSignedMessage()`.
4. Compare with sending the same request without `signed_message` (i.e., as a normal unit): this path is routed through `network.handleOnlineJoint` and will be rejected/held pending real validation, demonstrating the discrepancy in the two code paths handling the same "sign" subject.
