### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup triggers unauthorized continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to using only `sha`, with no check that the commit's stack/repository matches the repository that signed the incoming webhook. Because Shipit supports multi-tenant GitHub App configuration (one webhook secret per organization), an attacker who legitimately administers their own org/repo registered with this Shipit instance can send a validly-signed `status` webhook whose `sha` field targets a commit belonging to an unrelated victim stack, flipping that commit to `success` and triggering `Stack#trigger_continuous_delivery` for the victim.

### Finding Description
The broken binding: `signing_repository_owner` (the org whose `webhook_secret` verified the request, checked in `WebhooksController#verify_signature` via `Shipit.github(organization: repository_owner)` [1](#0-0)  ) should equal `target_commit.stack.repository.owner` (the repo whose commit actually gets mutated). It does not, because `StatusHandler#process` resolves target commits purely by `sha`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This is inconsistent with the rest of the webhook handler family: the base `Handler` class provides a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, and every `pull_request/*` handler uses it. `StatusHandler` ignores this scoping entirely. [3](#0-2) 

`Shipit.github(organization:)` and `github_app_config` confirm this engine natively supports per-organization webhook secrets/multi-tenancy, so an attacker can be a legitimate, unprivileged owner of one configured org (org A) while a victim stack lives under an unrelated org B, both hosted by the same Shipit instance. [4](#0-3) 

Attacker request: `POST /webhooks` with `X-Github-Event: status`, `X-Hub-Signature` computed with org A's own known `webhook_secret`, `repository.owner.login = "org-a"` (passes `verify_signature`), but `sha` set to a known/guessed commit SHA belonging to victim stack `org-b/prod`.

Exploit flow: `Status.create!` fires `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` [5](#0-4)  → `Commit#schedule_continuous_delivery` checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob` [6](#0-5)  → `Commit#deployable?` becomes true once a `success` status exists [7](#0-6)  → `Stack#trigger_continuous_delivery` calls `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` [8](#0-7) , ultimately spawning `Task`/`Command` with the victim stack's own `GITHUB_TOKEN`.

Existing guards fail to prevent this because `verify_signature` only authenticates *which organization* sent the payload — it never checks that the payload's declared `repository` matches the commit(s) that `StatusHandler` mutates, and `StatusHandler` is the only handler that skips the `stacks`/`Repository.from_github_repo_name` scoping used elsewhere.

### Impact Explanation
An attacker who controls (or merely is a legitimate non-privileged customer of) any single organization/repo registered with a multi-tenant Shipit instance can, without ever touching the victim's GitHub App, `webhook_secret`, session, or API token, force a `success` status onto an arbitrary commit sha in any other tenant's stack. If that commit is otherwise the next deployable commit and the victim stack has continuous deployment enabled, this triggers an unauthorized deploy using the victim's own `GITHUB_TOKEN`/`GIT_ASKPASS` and deploy credentials — matching "an unauthorized deploy" and "a payload for one repository mutating another's stack, commit, task" in the Critical impact list. This is repeatable against any stack/commit whose sha the attacker can learn (commit shas are not secrets and are routinely observable through public repos, CI logs, PR pages, etc.).

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured multi-tenant (multiple orgs each with their own `webhook_secret` under `secrets.github`), (2) the attacker to legitimately administer at least one such registered org (a realistic scenario for a shared/multi-tenant Shipit deployment), (3) the attacker knowing the target commit's 40-char sha (public/observable for public repos or leaked via CI/PR metadata), and (4) the victim stack having `continuous_deployment` enabled and being otherwise deployable. Given multi-tenancy is a first-class, documented feature of this engine (`github_app_config`, `github_organizations`), this is a realistic, low-cost, repeatable attack once preconditions (2)-(4) hold.

### Recommendation
Scope `StatusHandler#process` to only match commits whose stack's repository corresponds to `payload['repository']['full_name']`, consistent with the `stacks` helper used by other handlers, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or filter `Commit.where(sha: params.sha)` down to commits whose `commit.stack_id` is in `stacks.pluck(:id)`.

### Proof of Concept
In a minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks under different repos/orgs: `stack_a` (`org-a/repo-a`) and `stack_b` (`org-b/prod`, `continuous_deployment: true`), each with a distinct configured `webhook_secret`.
2. Create a commit on `stack_b` with a known sha, no existing status.
3. Build a `status` webhook payload with `repository.full_name = "org-a/repo-a"` and `sha` equal to `stack_b`'s commit sha; sign it with `org-a`'s webhook secret.
4. Assert both sides of the binding before: `commit.stack_id == stack_b.id` and `payload_repository == "org-a/repo-a"` (mismatch already visible).
5. POST to `/webhooks` with valid `X-Hub-Signature` for org-a.
6. Assert `stack_b`'s commit now has a `success` status (`commit.reload.deployable?` is true) despite the request being authenticated for `org-a`.
7. `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b])`.
8. Stub `Command#start`/`PTY.spawn`, run `ContinuousDeliveryJob.new.perform(stack_b)`, and assert a spawn occurred with `stack_b`'s `GITHUB_TOKEN` in the env — proving the attacker-authenticated request (org-a) unlocked a deploy against `stack_b`/victim without victim's own CI or authorization for that commit.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
