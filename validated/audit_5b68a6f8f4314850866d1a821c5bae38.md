### Title
Stack-Scoped API Token Grants Cross-Stack Read Access via CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used by `Shipit::Api::BaseController` to enforce per-`ApiClient` stack scoping, resolving the target stack directly from the raw `stack_id` param instead of through the scoped `stacks` relation. Any `ApiClient` token that has been granted the `read:stack` permission — even one deliberately restricted to a single stack via `ApiClient#stack_id` — can therefore read the CI/build-status feed (`CCMenuController#show`) of any stack in the installation, breaking the intended binding between "the stack a token authorizes" and "the stack it actually touches."

### Finding Description
`Shipit::Api::BaseController` implements stack scoping centrally: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client is scoped to one, and `stack` resolves the requested `stack_id` param only from within that restricted relation via `stacks.from_param!`. This is the mechanism that makes a stack-scoped `ApiClient` (e.g. the `here_come_the_walrus` fixture, which is `stack: shipit`, `permissions: [read:stack]`) safe to hand out — it can only ever resolve to its own stack, confirmed by the existing test "an api client scoped to a stack will only see that one stack".

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely: [2](#0-1) 

It resolves `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, and only relies on `require_permission :read, :stack` (declared at the top of the controller) for authorization: [3](#0-2) 

`ApiClient#check_permissions!` only checks that the client's `permissions` array contains the string `read:stack` — it never checks `stack_id`: [4](#0-3) 

So the equality that should hold — "stack a token authorizes" == "stack it touches" — is broken specifically in `CCMenuController`: a token scoped to stack A satisfies `read:stack` and is then used to fetch stack B's CI status, because `stack` for this one controller does not go through `stacks`.

This is structurally analogous to the reported bug class: a security-relevant binding (there, "address blocked" vs "address paid"; here, "stack authorized" vs "stack served") is checked in one code path but silently skipped in a sibling code path that reimplements the same operation.

### Impact Explanation
This matches the "High" impact bucket defined in scope: unauthenticated (from the perspective of other stacks) read of stack state / task-stream / deploy-output data. A caller holding only a narrowly-scoped `ApiClient` token (intended to expose a single stack's CI badge, e.g. for embedding in an external CI dashboard as documented for the CCMenu integration) can enumerate and read the last build status, activity, and label of every stack managed by the Shipit instance, including stacks it was never granted access to — a cross-tenant information disclosure of deploy/build state.

### Likelihood Explanation
Likelihood is high given the intended distribution model for CCMenu tokens: `CCMenuUrlController#client` mints a `read:stack`-permissioned `ApiClient` (unscoped by `stack_id` in this creation path, but any pre-existing stack-scoped client works identically) specifically to be embedded in a CCMenu URL: [5](#0-4) 

Any holder of such a URL/token — which is explicitly designed to be shared with third-party CI dashboard tools — can simply change the `stack_id` path/query parameter to pull another stack's build status, with no code changes and no additional privilege required beyond possessing one valid `read:stack` token.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., remove the private `stack` override, or reimplement it as `stacks.from_param!(params[:stack_id])`), so cross-controller behavior matches `BaseController`'s intended enforcement of `ApiClient#stack_id` scoping.

### Proof of Concept
1. Create (or reuse) an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: 'ccmenu', stack: stack_a, permissions: ['read:stack'])`, and obtain its `authentication_token`.
2. Issue `GET /api/stacks/:stack_b_id/ccmenu.xml` using HTTP Basic auth with that token (or `?token=` as supported by `CCMenuController#authenticate_api_client`), substituting Stack B's id/param instead of Stack A's.
3. Observe the request succeeds with `200 OK` and returns Stack B's CCMenu XML (build status, last build label, activity) even though the token was only intended to authorize reads of Stack A — confirmed by the absence of any test asserting stack-scoped clients are rejected for other stacks in `test/controllers/api/ccmenu_controller_test.rb`, unlike the equivalent scoping test present for `StacksController`.
