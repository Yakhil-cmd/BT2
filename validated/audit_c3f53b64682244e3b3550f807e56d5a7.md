### Title
Governance vote counting uses current (spot) balances instead of balance-at-vote-time, enabling flash-style vote inflation of `op_list`/system parameters - ([File: main_chain.js])

### Summary
The Atlantis Loans incident was a governance attack where an attacker used a crafted `GovernorBravo` proposal to seize control of the protocol via manipulated voting power. Ocore has an analogous on-chain governance mechanism — the `system_vote` / `system_vote_count` messages that let any unprivileged address vote, with byte-balance-weighted tallying, to change the `op_list` (order providers/witnesses) and other consensus parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`). Any address can post `system_vote_count` at any time [1](#0-0)  to trigger a tally, and the tally (`countVotes`) weighs each voter by their *current* stable base-currency balance rather than the balance held at the time the vote was cast [2](#0-1) .

### Finding Description
`system_vote` lets any single-authored, unprivileged unit set a vote for `op_list` or a numerical system parameter [3](#0-2) ; the address's chosen value is simply recorded (`op_votes`/`numerical_votes`), keyed by address, overwriting any prior vote from that address [4](#0-3) .

Counting is triggered by `system_vote_count`, postable by anyone at any time (once per unit, non-AA) [1](#0-0) . When the triggering unit stabilizes, `countVotes()` runs:
- It collects the set of addresses that have *ever* voted on the subject, and computes each address's balance using a snapshot query executed **at counting time** (i.e., the current stable-good UTXO balance), not the balance held when the vote was originally cast [2](#0-1) .
- The "vote timeframe" expansion loop only filters *which votes* (by timestamp) are eligible, not *what balance* backs them; the weight always comes from the live `voter_balances` snapshot [5](#0-4) .
- For `op_list`, the OPs with the highest summed voter balance win and directly become the new witness/order-provider list stored in `system_vars`/`storage.systemVars.op_list` [6](#0-5) .

Because the weight is a live balance rather than a balance-at-vote-time or time-locked stake, an attacker can:
1. Post a `system_vote` for `op_list` with a set of attacker-controlled OP addresses from a low-balance address (this only needs to happen once, and the vote persists indefinitely since it's not re-validated for balance at cast time).
2. Shortly before triggering the count, move/borrow/consolidate a large amount of bytes into that same voting address (a large legitimate self-transfer, deposit, or short-term loan of funds is sufficient — no smart-contract flash loan is required because ocore has no such re-entrancy barrier).
3. Post `system_vote_count` for `op_list`; when the triggering unit stabilizes, `countVotes` reads the attacker address's freshly-inflated balance and counts it fully toward the vote, potentially outweighing genuine long-term voters.
4. Immediately after the count, move the funds back out — the malicious `op_list` is already committed to `system_vars` and used going forward for witness selection and stability calculations.

This mirrors the "governance attack" bug class in the report: voting power is not bound to genuine long-term economic stake at the time of casting the vote, so it can be transiently inflated to push through a malicious governance outcome.

### Impact Explanation
`op_list` directly determines the set of order providers/witnesses used for main-chain stability determination throughout ocore (see `checkWitnessesKnownAndGood`/`checkNoReferencesInWitnessAddressDefinitions`, called only to validate that candidate OPs are *known, good, stable, reference-free* — but not that the votes electing them are economically durable) [7](#0-6) . An attacker who transiently inflates voting balance to seize control of `op_list` could install colluding or attacker-controlled witnesses, which is the same class of impact as a governance takeover: potential for nodes to disagree on stability/validity of units, and downstream double-spend or network-liveness risk. The `threshold_size`/TPS-fee parameters can similarly be manipulated to alter fee/consensus dynamics network-wide. Given the direct linkage to witness selection (a core consensus input), this qualifies as High impact under the "node disagreement on validity or stability" / "network unable to confirm new units" criteria.

### Likelihood Explanation
The barrier to exploitation is economic rather than cryptographic: the attacker needs temporary access to a large byte balance in a single address at the precise moment a stabilizing unit finalizes the counting unit. Nothing in the code (`countVotes`, `saveSystemVote`, `validateInlinePayload`'s `system_vote`/`system_vote_count` handling) requires the balance to have been held for any duration, nor does it snapshot balance at vote-casting time — the only aging control is on the `timestamp` of the votes themselves used to decide which votes are still eligible, not on the balance backing them [8](#0-7) . Because `system_vote_count` can be posted by anyone, an attacker fully controls the timing of the tally relative to their balance inflation. This makes the attack technically straightforward for anyone able to command a large temporary balance (e.g., via exchange withdrawal/deposit or a large legitimate transfer), though it does require access to substantial capital relative to the total honest voting weight, which limits — but does not eliminate — practical likelihood.

### Recommendation
- Weight votes by the balance held by each voter at (or shortly after) the time their `system_vote` unit was posted/stabilized, not by the balance read live at counting time; e.g., snapshot and store the balance-at-vote-time when saving each `system_votes` row in `saveSystemVote`, or require a minimum holding/lock period before a balance can count toward a vote.
- Consider requiring votes to be re-affirmed periodically and decaying balance contributions that were acquired only immediately before a `system_vote_count` trigger (e.g., ignore balance from outputs created after the vote unit's timestamp, or require the balance to have existed continuously since the vote).
- Add a cooldown/anti-flash check comparing the age of the UTXOs backing the counted balance against the vote's timestamp before permitting them to count in `countVotes`.

### Proof of Concept
1. Attacker address `A` posts a valid `system_vote` unit with `subject: "op_list"` and `value` set to an array of attacker-controlled OP addresses (values must pass `checkNotAAs`, `checkWitnessesKnownAndGood`, `checkNoReferencesInWitnessAddressDefinitions`, all satisfiable by pre-registering ordinary addresses) [9](#0-8) .
2. Attacker leaves address `A` with a small balance initially so the vote is cheap/unsuspicious to cast, satisfied as long as `A` shows up in `system_votes`.
3. Shortly before triggering the count, attacker moves a very large amount of bytes into address `A` (self-transfer, exchange withdrawal, or short-term borrowed capital).
4. Attacker posts a `system_vote_count` unit for `subject: "op_list"` [1](#0-0) .
5. Once that unit stabilizes, `main_chain.js`'s `saveUnstablePayloads`→`countVotes('op_list')` executes, computing `voter_balances` from address `A`'s now-inflated live balance [2](#0-1)  and, if this sum places `A`'s slate of OPs in the top `COUNT_WITNESSES` by summed balance, commits it as the new `op_list` in `system_vars` [6](#0-5) .
6. Attacker immediately transfers the funds out of `A`; the malicious `op_list` remains in effect for subsequent stability calculations.

Note: I was unable to fully verify the exact economic feasibility (i.e., how much total honest voter balance would need to be outweighed in production) since that depends on live network data not present in the indexed code; this analysis is based purely on the vote-counting logic reachable from unprivileged unit posting.
