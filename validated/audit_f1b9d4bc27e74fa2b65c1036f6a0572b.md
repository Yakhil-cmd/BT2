### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the actual write target is taken from the independent `repository.full_name` field, allowing cross-repository forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary

### Finding Description
The external report's bug class is: a value taken directly from an untrusted payload is used to reference/mutate an object without validating that it is bound to the same trust context that was actually verified (`cycleCounter`/`txId` came straight from the request body and were never checked against what the signature/verification step actually covered).

The same class of bug exists in Shipit's webhook trust boundary. `WebhooksController#verify_signature` selects *which organization's* GitHub App/webhook secret to validate the HMAC signature against by reading a value straight out of the untrusted, attacker-supplied JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — again, both are plain fields of the same untrusted JSON body, not the field that is later used to select the actual `Repository`/`Stack` records to mutate.

Once the signature check passes, `WebhooksController#create` hands the *entire raw parsed payload* to the registered handler for the event, unmodified: [3](#0-2) 

Handlers such as `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` resolve the target `Stack`/`Repository` via `Handler#repository_name`, which reads a *different* field of the same payload — `repository.full_name` — rather than the `repository.owner.login`/`organization.login` field that was actually used to pick the webhook secret: [4](#0-3) [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` splits this attacker-controlled `full_name` string on `/` and does a plain `find_by(owner:, name:)` lookup with no further validation that `owner` matches the organization whose secret validated the signature: [7](#0-6) 

Because `repository.owner.login` (used for authentication) and `repository.full_name` (used for the write target) are two independent string fields inside the same signed JSON body, nothing prevents an attacker who possesses a valid webhook secret for *their own* org/app installation from crafting a payload where the signing-relevant field says "attacker-org" but `repository.full_name` says "victim-org/victim-repo". The signature only proves "this body was HMAC-signed with organization X's secret" — it says nothing about which repository the body's other fields are allowed to name.

This is the same equality violation pattern as the report: **organization authenticated (`repository_owner` used to pick the HMAC key) ≠ repository written (`repository.full_name` used to select the DB record to mutate)**, both sourced from attacker-controlled payload fields that are never cross-checked against one another.

### Impact Explanation
An attacker who controls a legitimate webhook secret for one organization/app installation in the Shipit deployment can forge webhook deliveries that are accepted as authentic (signature verifies) but whose `repository.full_name` names an unrelated, victim-owned repository/stack. Depending on handler:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` on the victim stack based on an attacker-chosen SHA/ref.
- `StatusHandler` injects fabricated commit statuses (`create_status_from_github!`) onto victim commits, which downstream deploy-approval logic (`ci.require`/`ci.hide`) may trust.
- `CheckSuiteHandler` forces check-run refresh cycles on victim stacks.

This is a cross-repository write into another organization's Shipit data driven entirely by attacker-controlled payload content, meeting the "cross-repository writes" Critical impact bar in the rules.

### Likelihood Explanation
Requires the attacker to hold a valid webhook signing secret for at least one organization/repository already registered with this Shipit instance (e.g., their own repo/org onboarded to Shipit) — a lesser privilege than access to the victim's repository, GitHub token, or Shipit account. Given that, forging the JSON body and signature for their own secret while altering the unrelated `repository.full_name` field is trivial (no cryptographic barrier), making exploitation likely once the prerequisite (one legitimate but unprivileged webhook secret) is met.

### Recommendation
Bind the field used for signature-key selection and the field used for repository resolution to the same, single source, and reject the request if handler code discovers a resolved `Repository`/`Stack` whose `owner`/`full_name` does not match the organization whose secret validated the signature. Concretely, `WebhooksController#verify_signature` should derive `repository_owner` from the very same value later consumed by `Handler#repository_name`, and/or handlers should assert `repository.full_name.split('/').first == verified_repository_owner` before performing any writes.

### Proof of Concept
1. Attacker registers/owns a repository `attacker-org/attacker-repo` already connected to this Shipit instance, giving them the webhook secret for `attacker-org` (`Shipit.github(organization: 'attacker-org')`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/production",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s known webhook secret and POSTs to `/webhooks`.
4. `verify_signature` computes `repository_owner` = `"attacker-org"` (from `repository.owner.login`), fetches `attacker-org`'s GitHub App config, and the HMAC verifies successfully.
5. `PushHandler#process` calls `Handler#repository_name`, which reads `repository.full_name` = `"victim-org/victim-repo"`, resolves `Repository.from_github_repo_name` to the victim's real repository, and syncs/mutates the victim's stacks — despite the signature only proving knowledge of `attacker-org`'s secret.
