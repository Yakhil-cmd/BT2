I now have enough to write up the finding. The key binding break confirmed: `WebhooksController#repository_owner` (used to select the *verifying* GitHub org/secret) reads `params.dig('repository', 'owner', 'login')`, while every event handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) resolves the target `Repository`/`Stack`/`Commit` from `payload.dig('repository', 'full_name')` — a separate, independently-controlled field in the same JSON body. In a multi-organization deployment (`Shipit.github(organization:)`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), each organization has its own `webhook_secret`. An attacker who legitimately administers one configured organization's GitHub App (and thus legitimately knows *that* organization's `webhook_secret`) can forge a POST to `/webhooks` where `repository.owner.login` names their own org (so `verify_signature` selects and successfully validates against their own known secret) while `repository.full_name` names a repository belonging to a *different* configured organization/stack. Because the two fields are never cross-checked, the forged, validly-signed request is dispatched to handlers that act on the victim org's stack.### Title
Webhook signature verified against `repository.owner.login` while event handlers act on the independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub organization's `webhook_secret` to validate a webhook payload against by reading `repository.owner.login` (or `organization.login`) out of the untrusted JSON body itself. Once verified, the event is dispatched to handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) that resolve the actual `Repository`/`Stack`/`Commit` to mutate using a different field of the same body: `repository.full_name`. Nothing ties these two fields together, so a party who legitimately controls one configured GitHub organization's `webhook_secret` can forge a signed request whose `repository.owner.login` names their own org (so the signature check passes) while `repository.full_name` names a stack belonging to a completely different organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the signing org purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` (and its `webhook_secret`) for whatever organization name is present in the payload: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations, each with its **own** `webhook_secret`, exactly for this multi-tenant scenario: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `create` dispatches the whole payload to the handlers for the declared event: [6](#0-5) 

But every handler resolves its target repository/stack from `repository.full_name`, not from `repository.owner.login`: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

Because `repository.owner.login` and `repository.full_name` are two independent JSON fields inside a body an attacker fully controls (they only need to know the `webhook_secret` of the organization they name in `owner.login`), the equality the system implicitly assumes — "the organization whose secret authenticated the request" == "the repository/stack the request is allowed to act on" — is never enforced or checked. This is the direct analog of the reported bug class: a field (`full_name`, i.e. "PODs"/liquidity target) that is acted upon is never covered by the binding check (`owner.login`, i.e. "stake" verification), letting the two be decoupled.

### Impact Explanation
An attacker who legitimately administers one org's GitHub App installation on a shared, multi-org Shipit instance (knows only their own org's `webhook_secret`, not the victim's) can:
- Send forged `status` events (`StatusHandler`) to inject arbitrary commit statuses (`state`, `context`, `description`) onto a victim org's commits, which can flip CI/deployable-status gating that this platform uses to decide whether a commit is safe to deploy.
- Send forged `push` events (`PushHandler`) to trigger `GithubSyncJob` against a victim stack.
- Send forged `check_suite`/`pull_request` events against victim stacks/pull requests, manipulating review-stack archival/label state.

Faking a `success` CI status on an attacker-chosen victim commit can make an unsafe commit appear deployable, i.e. it can influence which commit an operator subsequently ships — this maps to the "unauthorized deploy"-class impact in scope, achieved purely by breaking the organization-authenticated vs. repository-acted-upon binding, with no Shipit session, ApiClient token, or victim-org secret required.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub organization (an explicitly documented and supported configuration), and (2) the attacker legitimately controls/administers at least one of those configured organizations (and thus knows that org's own `webhook_secret`, which they set themselves during app installation). No access to the victim org's secret, no Shipit account, and no `ApiClient` token is needed — only crafting a raw HTTP POST with a valid HMAC computed over an attacker-chosen JSON body using a secret the attacker already legitimately possesses.

### Recommendation
When resolving the target repository/stack/commit inside every `Webhooks::Handlers::Handler` subclass, require that the resolved repository's owner/organization matches the organization whose `webhook_secret` was used to verify the request (i.e., thread `repository_owner` from the controller into the handler and assert `Repository.from_github_repo_name(full_name).owner == repository_owner`, rejecting on mismatch). Alternatively, verify the signature using the secret bound to the repository actually referenced by `full_name`, not the one implied by `owner.login`, and reject payloads where `full_name`'s owner segment doesn't match `owner.login`/`organization.login`.

### Proof of Concept
1. Deploy Shipit with two configured organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as in `docs/setup.md`'s "Using Multiple Github Applications" / `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately installed/administers the GitHub App on `attacker-org`, so they know `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `attacker-org`'s secret — see `app/controllers/shipit/webhooks_controller.rb` lines 24-30, 59-62.
6. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24) creates a forged `success` status on the victim commit, keyed only by `sha`, with no check that the commit's stack/repository belongs to `attacker-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
