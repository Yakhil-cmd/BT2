### Title
Webhook signature verified against the org named in `repository.owner.login`, while the write target is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from the field `params.dig('repository', 'owner', 'login')` (or `organization.login`), which is itself part of the unauthenticated JSON body being verified. [1](#0-0) [2](#0-1)  Once the signature is accepted, every webhook handler resolves the actual stack/repository to write to using a *different* field of the same body, `repository.full_name`, via `Repository.from_github_repo_name` / `Shipit::Webhooks::Handlers::Handler#stacks`. [3](#0-2) [4](#0-3) [5](#0-4)  These two fields are never cross-checked against each other.

### Finding Description
Shipit supports hosting multiple GitHub organizations, each with its own GitHub App and its own `webhook_secret`, configured under distinct top-level keys in `secrets.yml`. [6](#0-5)  `verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1)  This value comes straight from the raw JSON body — the very thing the signature is meant to authenticate — so the controller trusts an attacker-controlled field to pick *which secret* is used to check the attacker-controlled body.

Because `verify_webhook_signature` only performs `OpenSSL::HMAC.hexdigest` comparison against whatever secret corresponds to `repository_owner`, an attacker who legitimately possesses (or has installed) a GitHub App for **any one** organization configured in Shipit can:

1. Set `repository.owner.login` = `"attacker-org"` (the org they know the secret for) so `verify_signature` fetches and validates against their own known `webhook_secret`.
2. Set `repository.full_name` = `"victim-org/victim-repo"` (an entirely different, unrelated repository/stack they do not control) inside the same signed body.
3. Sign the whole raw body with their own known secret — this signature is valid because `verify_webhook_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner, and it accepts any payload signed with the secret it looked up.

The handler code that actually executes side effects (`PushHandler#process`, `pull_request/*_handler.rb`, etc.) resolves the target purely from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on stacks matching that unrelated repository/branch — the attacker fully controls `after`, effectively forcing Shipit to sync/track an arbitrary attacker-chosen SHA for a completely different organization's stack. [4](#0-3)  Pull-request handlers behave the same way, resolving `repository` via `params.repository.full_name` independently of the signing organization, and can archive/unarchive review stacks or update PR state for a target owned by a different org than the one whose secret authenticated the request. [7](#0-6) [8](#0-7) 

This exactly matches the requested binding class: **"an organization that authenticated versus the repository that is written"** — the organization whose secret authenticated the request (`repository.owner.login`) is never bound to the repository whose stack is mutated (`repository.full_name`).

### Impact Explanation
This allows an unprivileged party who has legitimately registered/installed their own GitHub App organization in a multi-org Shipit deployment to forge webhook events (push, pull_request, membership, etc.) that are accepted as authentic for **any other organization's repositories/stacks** configured on the same Shipit instance. Consequences include:
- Forcing `GithubSyncJob`/`sync_github` calls with an attacker-chosen `expected_head_sha` on victim stacks (poisoning tracked HEAD state used for deploy eligibility, effectively an unauthorized/incorrect deploy state manipulation), which corresponds to the "unauthorized deploy" impact category.
- Archiving/unarchiving review stacks or mutating pull-request metadata belonging to a victim organization's repositories without any access to that organization.

This satisfies the High-impact bar ("escalation into authorization... unauthorized deploy") because the trust boundary between organizations (each with its own GitHub App/secret) is broken by a signature check that authenticates against a field disjoint from the field driving the write.

### Likelihood Explanation
Likelihood is High in any deployment where `Shipit.github` is configured with more than one organization (explicitly documented and supported as "Using Multiple Github Applications"). [6](#0-5)  Any party controlling one configured org's webhook secret (e.g., a legitimate low-trust org that installed the Shipit GitHub App for its own repos) can immediately exploit this — no privileged Shipit credentials, `ApiClient` token, or GitHub write access to the victim repo are required, only knowledge of their own org's `webhook_secret`, satisfying the rules' unprivileged-attacker constraint.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler`, ensure the organization used to select/verify the webhook secret is bound to the same repository used to resolve the target stack — e.g., after verifying the signature, additionally assert that `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner` equals the `repository_owner`/organization that supplied the verified secret, rejecting the webhook otherwise. Alternatively, since GitHub sends one `X-Hub-Signature` per registered app installation, verify against the secret tied to the resolved target repository's installation rather than a value taken from the unauthenticated body.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per documented multi-org setup). [6](#0-5) 
2. As the party controlling `attacker-org`'s installed GitHub App (which they legitimately know the `webhook_secret` for), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POST to `/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (matching `repository.owner.login`), verifies the signature successfully against the attacker's own known secret. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stacks, despite the request never being authenticated by `victim-org`'s installation. [4](#0-3) [3](#0-2)
