### Title
Fee-on-Transfer ERC20 Tokens Cause Inflated `RequestValueTransfer` Events, Draining Counterpart Bridge Liquidity — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and the 1-step `onERC20Received` path both trust the caller-supplied `_value` parameter as the canonical transfer amount. For fee-on-transfer ERC20 tokens, the bridge actually receives fewer tokens than `_value + _feeLimit`, but the `RequestValueTransfer` event is emitted with the full `_value`. The counterpart bridge's relayer reads this event and calls `handleERC20Transfer` with the inflated `_value`, releasing more tokens on the destination chain than were ever locked on the source chain.

---

### Finding Description

In `requestERC20Transfer` (2-step path):

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The bridge pulls `_value + _feeLimit` tokens via `safeTransferFrom`. For a fee-on-transfer token with rate `r`, the bridge actually receives `(_value + _feeLimit) * (1 - r)` tokens. `_payERC20FeeAndRefundChange` then pays out `fee` to the fee receiver and `_feeLimit - fee` back to the user (total outflow: `_feeLimit`), leaving the bridge with `(_value + _feeLimit) * (1 - r) - _feeLimit = _value - _feeLimit * r - _value * r` tokens — strictly less than `_value`.

Despite this, `_requestERC20Transfer` emits:

```solidity
// BridgeTransferERC20.sol L97-106
emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // <-- inflated; actual custody is _value - transfer_fee
    requestNonce,
    fee,
    _extraData
);
``` [1](#0-0) 

The relayer in `node/sc/bridge_manager.go` reads `valueOrTokenId` from this event and submits it verbatim to `handleERC20Transfer` on the counterpart bridge:

```go
// bridge_manager.go L339
handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, ...)
``` [2](#0-1) 

The counterpart bridge then releases `_value` tokens to the recipient — more than were actually locked on the source side.

The same flaw exists in the 1-step path via `onERC20Received`:

```solidity
// ERC20ServiceChain.sol L44-46
function requestValueTransfer(uint256 _amount, address _to, uint256 _feeLimit, bytes calldata _extraData) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
``` [3](#0-2) 

The token's `transfer` delivers fewer tokens to the bridge than `_amount + _feeLimit`, but `onERC20Received` is called with the original `_amount`, which flows into `_requestERC20Transfer` and the inflated event. [4](#0-3) 

---

### Impact Explanation

In **non-mintBurn (lock/unlock) mode**, the source bridge holds fewer tokens than the `RequestValueTransfer` event claims. Each cross-chain transfer of a fee-on-transfer token drains `transfer_fee_amount` from the counterpart bridge's liquidity pool. Repeated transfers eventually exhaust the counterpart bridge's reserves, causing legitimate `handleERC20Transfer` calls to revert (insufficient balance), permanently blocking withdrawals for honest users. This constitutes an **unauthorized transfer of bridged assets** — recipients on the destination chain receive tokens that were never fully deposited on the source chain.

In **mintBurn mode**, the source bridge burns `_value` tokens (line 94) but only received `_value - transfer_fee`. The burn call itself will revert if the bridge balance is insufficient, making the entire transaction revert — so mintBurn mode is self-protecting via revert, but the lock/unlock mode is not. [5](#0-4) 

---

### Likelihood Explanation

- **Trigger**: Any user can call `requestERC20Transfer` or `requestValueTransfer` on a registered fee-on-transfer ERC20 token. No privileged access is required.
- **Token registration**: `registerToken` in `BridgeTokens.sol` imposes no restriction on token type; any ERC20 can be registered by the bridge owner.
- **Likelihood**: Medium — requires a fee-on-transfer token to be registered on the bridge, which is an operator decision, but the bridge contract itself provides no guard against it. [6](#0-5) 

---

### Recommendation

Measure the actual received amount using a balance-before/balance-after pattern in `requestERC20Transfer`, and use the measured amount (not `_value`) in the emitted event and for all subsequent accounting:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    uint256 actualValue = actualReceived > _feeLimit ? actualReceived.sub(_feeLimit) : 0;
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, _feeLimit, _extraData);
}
```

Apply the same fix to `onERC20Received` by measuring the bridge's balance change rather than trusting the caller-supplied `_value`.

---

### Proof of Concept

1. Deploy `Bridge` in non-mintBurn mode. Register a fee-on-transfer ERC20 token (1% fee on every transfer) on both source and counterpart bridges.
2. Fund the counterpart bridge with 1000 tokens as liquidity.
3. User calls `requestERC20Transfer(tokenAddr, recipient, 100, 0, "0x")` on the source bridge.
   - `safeTransferFrom` pulls 100 tokens from user; bridge receives 99 (1 taken as transfer fee).
   - `_payERC20FeeAndRefundChange` pays 0 fee (no fee receiver set), refunds 0 (feeLimit=0).
   - Source bridge now holds 99 tokens.
   - `RequestValueTransfer` emits `valueOrTokenId = 100`.
4. Relayer observes the event, calls `handleERC20Transfer(..., 100, ...)` on counterpart bridge.
   - Counterpart bridge transfers 100 tokens to recipient.
5. Net: source bridge gained 99 tokens, counterpart bridge lost 100 tokens. **1 token deficit per transfer.**
6. After 1000 such transfers, counterpart bridge is drained; all subsequent legitimate withdrawals revert. [6](#0-5) [7](#0-6) [8](#0-7)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)

			return err
		}
		if ctTokenAddr == (common.Address{}) {

		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	defer bridgeAcc.UnLock()

	var handleTx *types.Transaction
	var err error

		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)

		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)

			return err
		}

		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
