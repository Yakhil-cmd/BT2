### Title
Unbounded accrued-debt valuation overflow permanently freezes a market - (File: `common/src/rates/scaling.rs`)

### Summary
A market can reach a state where converting accrued scaled debt back to token units overflows `i128`. Because the pool accrues the market before borrow, supply, withdrawal, repayment, liquidation and bad-debt settlement, that single arithmetic failure permanently blocks every state-changing path for the market. [1](#0-0) [2](#0-1) 

### Finding Description
The pool represents balances as RAY-scaled shares and derives token amounts by multiplying the scaled balance by the current index. The fixed-point arithmetic treats an overflowing result as an unrecoverable contract error rather than clamping the index or preserving an exit path. [3](#0-2) 

An unprivileged user can create a very large market position, maintain high utilization, and later trigger accrual through `Controller::update_indexes`. Once the debt value reaches the `i128` boundary, accrual panics inside `scaled_to_original`. The intended borrow-index cap does not protect the market because the value overflow occurs before that cap is reached. [4](#0-3) [5](#0-4) 

### Impact Explanation
Permanent freezing of user funds. After the overflow, suppliers cannot withdraw, borrowers cannot repay, and liquidations cannot settle because all those controller paths call pool operations that first load or accrue the affected market. [6](#0-5) 

The repository's regression test demonstrates that withdrawal and repayment revert with the same `MathOverflow` error after `update_indexes` reaches the overflow state, while the stored borrow index remains below its configured cap. [7](#0-6) 

### Likelihood Explanation
Likelihood is conditional on a listed market having sufficiently large caps and remaining at high utilization long enough for the accrued debt valuation to approach the `i128` range. The attacker does not need privileged code execution: they can use `supply`, `borrow`, and the permissionless `update_indexes` entrypoint, although the resulting market size must be permitted by the deployed market configuration. [8](#0-7) [4](#0-3) 

### Recommendation
Clamp or bound the index before any share-to-token conversion can overflow `i128`, and enforce a market-level cap based on the maximum representable accrued token value rather than only the raw index value. Preferably, make accrual saturate at a safe terminal state and preserve repayment/withdrawal paths even when additional interest can no longer be represented. [9](#0-8) 

### Proof of Concept
1. Configure or use a high-decimal market whose caps allow a sufficiently large token balance.
2. Supply the large asset and borrow enough to keep utilization near the high-interest region.
3. Let ledger time advance until the scaled-debt valuation approaches the `i128` boundary.
4. Call `Controller::update_indexes(caller, vec![hub_asset])`; accrual panics with `MathOverflow`.
5. Call `withdraw` or `repay` for the same market; both revert with the same accrual-time `MathOverflow`, leaving balances frozen.

The deterministic regression `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` reproduces this sequence and asserts that the index cap never engages before both `withdraw` and `repay` become unusable. [1](#0-0)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
