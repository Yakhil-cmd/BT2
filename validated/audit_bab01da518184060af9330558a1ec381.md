### Title
Unsanitized attacker-controlled repository name printed to terminal enables ANSI escape sequence injection before `Confirm` prompts - ([File: pkg/cmd/repo/fork/fork.go])

### Finding Description
In `forkRun`, the forked repository's owner/name — sourced directly from the `ForkRepo` API JSON response (`api.ForkRepo`, decoded into plain Go strings with no character-set validation) — is written to `stderr` via `fmt.Fprintf(stderr, "%s %s %s\n", cs.Yellow("!"), cs.Bold(ghrepo.FullName(forkedRepo)), "already exists")` and similar calls at [1](#0-0) , immediately before `opts.Prompter.Confirm("Would you like to clone the fork?", false)` reads from the same TTY at [2](#0-1) . `ghrepo.FullName` simply concatenates `RepoOwner()`/`RepoName()` with no sanitization [3](#0-2) , and `ghrepo.NewWithHost`/`ghRepo` store owner/name verbatim with no allow-list or escape-byte filtering [4](#0-3) . On `github.com`, repo/owner names are constrained server-side to a safe charset, but the question's precondition (a non-standard host under attacker control) removes that guarantee, since the CLI performs no client-side validation of these fields before rendering them.

Critically, this codebase already contains a dedicated mitigation for exactly this class of bug: the `iostreams.Untrusted` wrapper, which sanitizes ANSI escape sequences via `asciisanitizer.Sanitizer` on every `fmt` render path [5](#0-4) , plus a general `ContainsEscapeSequence`/`CopyGuardedContent` guard for untrusted external content [6](#0-5) . `NewUntrusted` is applied in gist/skills code paths that render remote content [7](#0-6) [8](#0-7) [9](#0-8) , but `fork.go` never wraps `ghrepo.FullName(forkedRepo)` (or `RepoName()`/`RepoOwner()`) in `iostreams.Untrusted` before printing, leaving this specific output path unsanitized.

### Impact Explanation
An attacker who controls the `ForkRepo` API response fields on a host the victim has configured could embed ANSI/VT100 escape sequences (cursor movement, line-clear, conceal/invert video, terminal title changes) in the returned owner/name. Because these bytes are written to the same TTY immediately before gh's own literal prompt text, a crafted sequence (e.g., ending without a terminating reset, using `\r` plus cursor positioning) could visually overlay, hide, or reposition gh's subsequent `Would you like to clone the fork?` text, creating a terminal UI-spoofing condition that could mislead a user into confirming an unintended clone/remote action. This maps to a low-severity "terminal/output injection" class rather than code execution or credential exposure — no direct RCE or token exfiltration results from this path alone.

### Likelihood Explanation
Exploitability strictly requires the victim to run `gh repo fork` against a non-`github.com` host whose API responses are attacker-controlled (e.g., a malicious/compromised GitHub Enterprise-like endpoint the user has pointed `gh` at). This is a narrower precondition than a standard `github.com` attack, since GitHub's own repo-naming rules would reject escape characters. Given that precondition holds, the injection is straightforward and repeatable — the attacker fully controls the string content of every affected `Fprintf` call.

### Recommendation
Wrap repository names/owners derived from API responses in `iostreams.Untrusted` (or otherwise pass them through the existing `asciisanitizer`) before any `fmt.Fprintf`/`cs.Bold` call in `fork.go`, consistent with how gist content is already handled. Alternatively, apply `iostreams.ContainsEscapeSequence` validation to `RepoName()`/`RepoOwner()` immediately after decoding API responses, rejecting or sanitizing any value containing `0x1B` bytes before it reaches `ghrepo.FullName` or any terminal-bound output.

		return stripControl(u.raw)
	}
	return sanitized
