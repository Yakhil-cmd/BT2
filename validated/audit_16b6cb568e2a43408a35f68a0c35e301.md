### Title
`StatusHandler#process` mutates commits across all organizations regardless of which organization's webhook secret authenticated the request - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook only against the secret of the organization named in `params['repository']['owner']['login']`, then hands the *entire raw, unscoped* payload to `Shipit::Webhooks.for_event('status')`, which resolves to `StatusHandler`. Unlike every other default handler, `StatusHandler#process` never scopes its DB write to the authenticated repository/organization: it runs `Commit.where(sha: params.sha)` against the whole `commits` table and calls `commit.create_status_from_github!(params)` on every match, so a correctly-signed webhook from organization A can write a `Status` row (and cascade side effects) onto a commit that belongs to organization B's stack.

### Finding Description
The binding that should hold is:
`authenticated_organization (from verify_signature via repository_owner) == organization owning the Commit rows mutated by the handler`

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` purely from attacker-supplied JSON (`params.dig('repository','owner','login')`) and fetches that organization's `GitHubApp` via `Shipit.github(organization: repository_owner)` [1](#0-0) [2](#0-1) . This correctly proves "this HMAC was produced with organization X's secret", nothing more.
2. `#create` then does `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`), passing the same raw, global `params` hash - no organization identity, no scoping token, no ivar - is threaded into the handler [3](#0-2) .
3. `Shipit::Webhooks.for_event('status')` returns `[Handlers::StatusHandler]` (`app/models/shipit/webhooks.rb:19`) [4](#0-3) .
4. `Handler.call(params)` does `new(params).process` (`app/models/shipit/webhooks/handlers/handler.rb:15-24`) - the instance only stores `@payload`/`@params`, nothing tying it to an organization [5](#0-4) . The base class does expose a `stacks`/`repository_name`-scoped helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), which `PushHandler` (`stacks.not_archived.where(branch:)...`) and `CheckSuiteHandler` (`stacks.where(branch: ...)`) both use to constrain writes to the authenticated repository's stacks [6](#0-5) [7](#0-6) .
5. `StatusHandler#process`, however, bypasses `stacks`/`repository_name` entirely and queries the global `Commit` table directly: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [8](#0-7) . `commit.create_status_from_github!` creates a `Status`, which in turn triggers `enable_ci_on_stack`, `schedule_continuous_delivery`, `broadcast_update`, and (via `Commit#add_status`) can call `stack.schedule_merges` and enqueue `ProcessMergeRequestsJob` for that commit's *actual* stack [9](#0-8) [10](#0-9)  - none of which is gated on the SHA belonging to the org that produced the valid signature.

So the two sides of the binding diverge: the authenticated organization is A (whichever org's secret validated the HMAC), but the mutated `Commit`/`Status`/`Stack` can belong to any organization B whose commit table happens to contain a row with the same `sha` value, because SHA is looked up globally with no `stack_id`/`repository_id` filter and no cross-check against `payload.dig('repository','full_name')`.

Since git commit hashes are content-addressed (tree + parents + author/committer + timestamps + message), any fork of a public repository retains identical SHAs for all unchanged history. An attacker who has push access to *some* repository whose organization is already configured with a real webhook secret in Shipit (i.e., a legitimate GitHub webhook fires and is correctly HMAC-signed for that org) can fork or otherwise reference a commit SHA that also exists in a victim stack tracked under a different organization/repository, and send (or have GitHub send) a `status` event for that SHA. `verify_signature` passes because the signature genuinely matches the sending org's secret; `StatusHandler` then writes a `Status` onto the victim's `Commit` row regardless of stack/org, because it never checks repository/organization identity beyond the raw SHA match.

None of the existing guards prevent this: `verify_signature` only proves "signed by org X", it does not constrain what data org X's webhook is allowed to reference; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate shape (`sha`, `state`, etc. are present strings), not ownership; there is no `Repository.from_github_repo_name` / `stacks` scoping call anywhere in `StatusHandler`.

### Impact Explanation
A correctly-authenticated webhook from organization/repository A can create a `Status` record attached to a `Commit` belonging to organization/repository B's stack, and can trigger side effects scoped to B's stack: enabling CI on B's stack, scheduling continuous delivery/deploys, scheduling merge processing (`ProcessMergeRequestsJob`) for B's merge requests, and broadcasting fabricated status/state updates to B's dashboard. This is a payload for one repository mutating another repository's/stack's data — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any commit SHA the attacker can reproduce (trivial for forks of public repos, or any commit history the attacker can replicate), and the blast radius spans every stack/organization hosted by the same Shipit instance, since the query is completely global and unscoped.

### Likelihood Explanation
The attacker needs (a) the ability to generate or trigger a correctly-signed `status` webhook for some organization already configured in Shipit (i.e., legitimate push/webhook activity on any repo under that org), and (b) a commit SHA that collides with a commit tracked in a *different* organization's stack — trivially achievable by forking public repositories, since git commit SHAs are preserved across forks/clones for unchanged history. No secrets, no privileged Shipit role, and no cross-organization signature forgery are required — only the ordinary, unprivileged act of pushing/forking. The cost is low and the action is repeatable per request.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` and `CheckSuiteHandler` do: restrict the `Commit` lookup to commits belonging to `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`), for example:
```ruby
def process
  stacks.find_each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the organization/repository that authenticated the webhook is the same one whose commits get mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status payload naming org A's repo mutates org B's commit with the same SHA" do
          org_a_stack = shipit_stacks(:shipit) # belongs to "shopify/shipit-engine" fixture, say org A
          org_b_commit = shipit_commits(:cyclimse_first) # belongs to a different repo/org fixture, org B
          shared_sha = org_b_commit.sha

          # Craft a payload claiming to originate from org A's repository, but containing
          # org B's commit sha (e.g. via a forked history collision).
          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/forged',
            'repository' => { 'full_name' => org_a_stack.github_repo_name, 'owner' => { 'login' => org_a_stack.repo_owner } }
          }

          assert_difference -> { org_b_commit.statuses.count }, 1 do
            StatusHandler.call(payload)
          end

          # Binding check: nothing in the handler instance ties it to org A,
          # yet org B's commit was mutated.
          status = org_b_commit.statuses.last
          assert_equal 'ci/forged', status.context
          assert_equal org_b_commit.stack_id, status.stack_id
          refute_equal org_a_stack.id, status.stack_id
        end
      end
    end
  end
end
```
