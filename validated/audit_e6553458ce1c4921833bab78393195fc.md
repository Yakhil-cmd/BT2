### Title
`dryRunPrimaryAATrigger` fakes `trigger.unit`/MC context, letting simulation diverge from real execution and misleading AA trigger senders - (File: `aa_composer.js`)

### Summary
The report describes Atlas's off-chain simulation not guaranteeing on-chain success because simulated execution context (opcodes, storage) can differ from the real transaction environment. Ocore has a structurally identical gap: the light-client AA preview API `light/dry_run_aa` executes the trigger with a synthetic environment — a fixed `constants.GENESIS_UNIT` as `trigger.unit` and the *current* last-stable MC unit's `timestamp`/`mci` — instead of the values that will actually exist once the real trigger unit is posted and stabilizes. Any AA formula that reads `trigger.unit`, `timestamp`, `mc_unit`, `this_address`, other AAs' state vars, or balances will therefore compute different results in the dry run than in the real execution, so a favorable/successful simulation does not guarantee (or even correlate with) the on-chain outcome for the unprivileged user who posts the real trigger unit.

### Finding Description
`dryRunPrimaryAATrigger` is the function backing the network command `light/dry_run_aa`, which any light-wallet or dApp front-end calls to preview what will happen if a given trigger (payment + data) is sent to an AA: [1](#0-0) 

Key facts about how it fabricates the execution environment:
- `trigger.unit` is hard-coded to `constants.GENESIS_UNIT`, explicitly noted in a comment as a workaround to avoid duplicate trigger rows, not to reflect reality: [2](#0-1) 
- The MC context (`objMcUnit`, hence `mci`, `timestamp`, `mc_unit`) is taken from `readLastStableMcUnit`, i.e. whatever is currently the last stable unit at simulation time — not the MC unit that will actually be `last_ball` when the real trigger stabilizes, which can be many units/blocks later.

The companion function `estimatePrimaryAATrigger` documents this limitation directly: [3](#0-2) 

The AA formula language explicitly allows AA code to branch on these values — `trigger.unit`, `timestamp`, `mci`/`mc_unit`, and `this_address`/remote AA state (`bal`, `ts`, `mci` of other AAs) are all valid, validated opcodes: [4](#0-3) 

Existing tests confirm that a dry run’s `ts`/`mci` values are pinned to whatever `readLastStableMcUnitProps` currently returns, not to the future stabilization point of the real trigger: [5](#0-4) 

Because the real trigger unit posted later by the user has: (a) a genuinely unpredictable unit hash (nothing like `GENESIS_UNIT`), (b) a `last_ball_mci`/`timestamp` that reflects the MC state at the time the unit actually stabilizes (which can differ substantially from the state at simulation time, e.g. if other AA-affecting units, balance changes, or DApp-controlled state updates land in between), any AA logic keyed off these values will produce a different, unpredictable result at real execution time versus what `light/dry_run_aa` reported. This is functionally identical to the Atlas concern: a party (here, the AA/DApp designer) controls execution paths (`if`/`case` branches keyed on `trigger.unit`, `timestamp`, `mci`, or another AA's live state) that are guaranteed to diverge between the off-chain preview and final on-chain execution, while the wallet/dApp UI presents the dry-run response (`bounced`, `response.responseVars`, output `amount`s) as if it were a reliable preview of the real outcome: [6](#0-5) 

### Impact Explanation
A user who relies on `light/dry_run_aa` (the officially provided preview mechanism for wallets/dApps) to decide whether/how much to send to an AA can be misled by a DApp that intentionally (or even accidentally) writes logic keyed on `trigger.unit`, `timestamp`, or `mci`. Because the dry run always evaluates such branches using `GENESIS_UNIT` and the *current* stable-MC snapshot, a hostile AA author can craft a definition that:
- Always shows a favorable payout / no-bounce result in the simulation (since it can special-case the deterministic `GENESIS_UNIT`/current MC values used by every dry run), while
- Executing a materially different, unfavorable branch for the real trigger unit (e.g., sending funds elsewhere, bouncing and keeping bounce fees, or applying a worse distribution formula), causing direct fund loss for the trigger sender.

This is an AA fund-loss vector reachable by any unprivileged AA trigger sender who trusts the standard preview path, matching the “Medium” severity classification given to the analogous Atlas finding (acknowledged by the original team as inherently hard to fully close, only partially mitigable).

### Likelihood Explanation
`light/dry_run_aa` is a standard, documented light-wallet RPC (used by wallets/UIs to show expected AA outcomes before a user signs and broadcasts a real payment), so the divergence is trivially reachable by any user interacting with any AA that a DApp author designs to exploit it. No special privileges are needed — only an AA definition using `trigger.unit`, `timestamp`, `mci`, or remote-AA state in conditional logic, all of which are ordinary, fully-supported oscript features. Because `GENESIS_UNIT` and “current last-stable MC” are always exactly the same, the divergence is *deterministic* and can be engineered by a malicious/careless AA author, not merely a rare-timing coincidence — the underlying code comment ("estimation is not 100% accurate ... unit validation errors are not caught") already acknowledges the mismatch exists.

### Recommendation
- Do not use a globally fixed, guessable value like `constants.GENESIS_UNIT` for `trigger.unit` in dry runs; instead, either disallow (or explicitly flag as unreliable) simulation of AAs whose static analysis shows dependence on `trigger.unit`, or synthesize a random/unpredictable placeholder unit hash each time so a fixed GENESIS_UNIT branch cannot be special-cased by a DApp author.
- Surface a clear warning/flag in the `light/dry_run_aa` response (and to wallet UIs) whenever the AA's evaluated code path reads `trigger.unit`, `timestamp`, `mci`, `mc_unit`, or another AA's live state, so that wallets can tell users the preview is not authoritative for that particular AA.
- Consider re-simulating using the MC state expected at the unit's *likely* stabilization point (or at minimum re-running the dry run immediately before broadcast) rather than only the last-stable snapshot, to reduce (though not eliminate) the time-of-check/time-of-use gap.

### Proof of Concept
1. A DApp publishes an AA whose response logic branches like:
   `if (trigger.unit == '{GENESIS_UNIT_BASE64}') { pay full refund to trigger.address } else { pay refund minus a large fee to trigger.address, or reroute to attacker address }`.
2. A wallet calls `light/dry_run_aa` (`network.js:3939-3963`) which internally calls `dryRunPrimaryAATrigger` (`aa_composer.js:272-306`), which always sets `trigger.unit = constants.GENESIS_UNIT` before evaluating the AA (`aa_composer.js:280`). The dry run therefore always takes the "full refund" branch and reports success/no-bounce to the user.
3. The user, trusting the preview, signs and broadcasts a real trigger unit. Its actual `unit` hash is never `GENESIS_UNIT`, so the real execution takes the "else" branch, resulting in a materially worse payout (fee/loss/rerouting) than the simulation promised — fund loss for the trigger sender with no indication from the simulation that this could happen.
