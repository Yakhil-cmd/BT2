### Title
`OpenedHandler#provision?` provisions a review stack when `review_stacks_enabled` is `false` due to operator-precedence error - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` uses `&&`/`||` in a way that, due to Ruby operator precedence, only guards the `allow_all` branch with `repository.review_stacks_enabled`. The `allow_with_label` and `prevent_with_label` branches never check `review_stacks_enabled`, so a repository administrator's decision to disable dynamic review-stack provisioning is silently bypassed whenever `provisioning_behavior` is `allow_with_label` or `prevent_with_label`.

### Finding Description
The binding required by design is `repository.review_stacks_enabled == true` for provisioning to occur under any behavior. The code is: [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

For `review_stacks_enabled: false`, `provisioning_behavior: 'prevent_with_label'`, and a PR opened with no labels: `allow_all?` is false so the first disjunct is false regardless of `review_stacks_enabled`; `allow_with_label?` is false so the second disjunct is false; but `provisioning_behavior_prevent_with_label?` is true and `!pull_request_has_provisioning_label?` is true (empty labels array), so the third disjunct evaluates to `true`. `provision?` returns `true`, `respond_to_pull_request_opened?` returns `true`, and `process` calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` record, a `PullRequest` record, and enqueues the stack via `Shipit::ReviewStackProvisioningQueue.add(stack)`, leading to real provisioning work. [2](#0-1) [3](#0-2) 

No guard elsewhere in the call chain re-checks `review_stacks_enabled`: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?` itself. [4](#0-3) 

Notably, sibling handlers `LabeledHandler` and `UnlabeledHandler` correctly gate their archive/unarchive logic behind an explicit top-level `repository.review_stacks_enabled &&` check in `respond_to_label_change?` before ever evaluating behavior-specific branches: [5](#0-4) 

`OpenedHandler` and `ReopenedHandler` both lack this outer guard and instead embed the (broken) check inside the disjunction, so the same precedence bug also affects `ReopenedHandler#unarchive?`. [6](#0-5) 

The existing test suite does not cover this combination: the only `provisioning_enabled: false` test in `opened_handler_test.rb` pairs it with `behavior: :allow_all`, not `prevent_with_label`, and the `prevent_with_label` tests all use the default `provisioning_enabled: true`. [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who can open a pull request against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (the default `provisioning_behavior` is `allow_all`, so this requires the repo owner to have explicitly switched to `prevent_with_label` while separately disabling review stacks — an inconsistent but plausible admin configuration) can trigger creation of a `Shipit::ReviewStack`, `Shipit::PullRequest`, and enqueue it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`, even though the repository owner explicitly opted out of dynamic stack provisioning. This is a record-write / provisioning action for a repository whose administrator did not authorize it, repeatable for every PR the attacker opens (one stack per PR number), confined to the targeted repository (blast radius does not cross tenants since `environment` and `full_name` scope the record), matching the "unauthorized deploy/provisioning" style Critical impact category to the extent that stack provisioning executes deployment automation for that repository.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled: false` combined with `provisioning_behavior: prevent_with_label` (or `allow_with_label`, which has the same precedence flaw for its own branch when combined with a matching label). This is not the default configuration and requires deliberate but plausible admin setup (e.g., an operator disabling stacks org-wide while leaving a previously-configured `prevent_with_label` behavior in place). Attacker cost is trivial: opening a PR with no special labels, which any GitHub user with fork/PR access to the tracked repository can do. No secrets, tokens, or privileged roles are needed. The bug is deterministic and repeatable per PR.

### Recommendation
Add explicit parentheses (or an outer guard) so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`, which has the identical precedence bug.

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks for prevent_with_label repos when review stacks are disabled" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertion: with `review_stacks_enabled == false`, expect `Shipit::Stack.count` unchanged (i.e. `provision?` should be `false`). Running this against current code fails because `provision?` returns `true` and a stack is created, demonstrating the divergence between the intended binding (`review_stacks_enabled == true` required) and actual behavior (`review_stacks_enabled` ignored for the `prevent_with_label` branch).
