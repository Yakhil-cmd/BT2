### Title
Indirect (less-trusted) paired-device correspondents are treated as fully-trusted for all wallet message subjects due to a disabled trust check - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` receives a `bIndirectCorrespondent` flag from `device.js` that is supposed to restrict which message `subject`s an indirectly-known (lower-trust) paired device may trigger. The restriction is dead code — it is commented out — so every subject in the switch statement (including `sign`, `create_new_shared_address`, `approve_new_shared_address`, `new_shared_address`, `removed_paired_device`, etc.) is dispatched identically regardless of whether the sender is a fully-trusted direct correspondent or a merely indirect one. [1](#0-0) 

### Finding Description
`device.js` classifies correspondents as direct or indirect (`is_indirect` flag on `correspondent_devices`) and forwards that classification into the message handler via `bIndirectCorrespondent`: [2](#0-1) 

`wallet.js` accepts this flag as a parameter but the enforcement of a reduced trust surface for indirect correspondents has been disabled:
```
//if (bIndirectCorrespondent && ["cancel_new_wallet", "my_xpubkey", "new_wallet_address"].indexOf(subject) === -1)
//    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
``` [3](#0-2) 

Because this line is commented out, an indirect correspondent — a device that was never directly paired by the wallet owner but became "known" through some indirect relaying path — is trusted to invoke every subject in the same `switch(subject)` block that a fully-trusted, directly-paired device can invoke, including shared-address creation/approval flows and cross-device signing requests: [4](#0-3) [5](#0-4) 

This is directly analogous to the reported OpenClaw bug class: a page/origin that should only be treated as a lower-trust context (a generic local-network page / here, an indirect correspondent) is instead granted the same dispatch trust as a fully-verified origin (a trusted canvas / here, a directly-paired device), allowing it to inject actions into the session that the trust model intended to gate behind stricter verification. The impact category matches: unauthorized, non-owner-initiated dispatch of session actions/state changes without owner-only compromise.

### Impact Explanation
An indirect correspondent can inject arbitrary supported subjects into the wallet's message pipeline instead of being restricted to the small originally-intended whitelist (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`). This can pollute wallet/session state — e.g., initiate `create_new_shared_address`/`approve_new_shared_address` flows that add attacker-influenced device addresses as prospective multisig cosigners into local wallet-related tables, or trigger `signing_request` UI events for cross-device co-signing on behalf of an unauthorized actor. This does not directly enable owner-only actions (a legitimate signature or spend authorization is still needed), matching the "no owner-only action, session-state pollution" impact profile described in the reference advisory, but it does weaken the intended defense-in-depth boundary between trusted and merely-known devices for wallet-management flows.

### Likelihood Explanation
Any device that a hub or intermediary path can classify as an indirect correspondent (i.e., `is_indirect=1` in `correspondent_devices`) automatically has this capability the moment it is recognized by `device.js`; no additional exploitation step or race condition is required, since the gating code path is fully disabled rather than partially bypassable.

### Recommendation
Re-enable and enforce the whitelist check for `bIndirectCorrespondent` in `wallet.js` `doHandle()` so that only the originally intended safe subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`, and any other subjects explicitly reviewed as safe for indirect trust) can be processed from indirect correspondents; reject all other subjects from indirect correspondents with `callbacks.ifError(...)`.

### Proof of Concept
1. Get a device recognized as an indirect correspondent (`correspondent_devices.is_indirect = 1`) relative to the victim wallet (e.g., via any flow that populates this indirect relationship in `device.js`).
2. From that device, send a `hub/message` with `subject: "create_new_shared_address"` (or `"sign"`, `"approve_new_shared_address"`, etc.) to the victim.
3. Because the check at `wallet.js:92-93` is commented out, `handleMessageFromHub` dispatches the message through the normal switch-case exactly as if it came from a fully trusted, directly-paired device, emitting `eventBus.emit("create_new_shared_address", ...)` or `eventBus.emit("signing_request", ...)` — actions the trust model intended to gate to a narrow whitelist for indirect correspondents.
