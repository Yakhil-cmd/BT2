### Title
Missing `_to` Zero-Address Validation in `_requestKLAYTransfer` Allows Unprivileged Drain of Destination Bridge KAIA Liquidity — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`_requestKLAYTransfer` and `requestKLAYTransfer` in the Kaia service-chain bridge accept `_to = address(0)` without any guard. Any unprivileged user can call `requestKLAYTransfer(address(0), value, extraData)` with attached KAIA, causing the bridge operators to faithfully relay a `HandleValueTransfer` to the destination bridge that sends KAIA to `address(0)` — permanently burning it from the destination bridge's liquidity pool.

---

### Finding Description

`_requestKLAYTransfer` performs two checks before emitting the cross-chain request event:

```solidity
require(isRunning, "stopped bridge");
require(msg.value > _feeLimit, "insufficient amount");
```

There is no `require(_to != address(0), ...)` guard. [1](#0-0) 

The public entry point `requestKLAYTransfer` passes the caller-supplied `_to` directly into `_requestKLAYTransfer`:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [2](#0-1) 

When `_to = address(0)` is accepted, a `RequestValueTransfer` event is emitted with `to = address(0)` and `requestNonce` is incremented. The Go bridge manager in `node/sc/bridge_manager.go` reads this event and calls `HandleKLAYTransfer` on the destination bridge, faithfully forwarding the zero address as `_to`: [3](#0-2) 

`handleKLAYTransfer` on the destination bridge then executes:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [4](#0-3) 

A low-level `.call.value()` to `address(0)` succeeds in the EVM (address(0) has no code; the call returns `ok = true`). The KAIA is transferred to `address(0)` and permanently burned from the destination bridge's balance.

The same pattern exists in `_requestERC20Transfer` (no `_to != address(0)` check) and `_requestERC721Transfer`: [5](#0-4) [6](#0-5) 

`BridgeOperator.registerOperator` also lacks a zero-address guard, allowing `address(0)` to be registered as an operator (inflating `operatorList.length` and potentially making thresholds unreachable), though this requires owner action: [7](#0-6) 

---

### Impact Explanation

The destination bridge's KAIA liquidity pool is reduced by `_value` for every zero-address request that reaches quorum. The source bridge retains the user's deposited KAIA (it is locked, not returned), so the net effect is:

- **Source bridge**: +`value` KAIA (locked, never claimable by anyone)
- **Destination bridge**: −`value` KAIA (sent to `address(0)`, burned)
- **User/attacker**: −`value` KAIA (sacrificed)

Repeated calls drain the destination bridge's KAIA reserve, eventually making legitimate cross-chain withdrawals impossible. This is an unauthorized burn of bridged KAIA assets from system-managed bridge funds.

---

### Likelihood Explanation

- The trigger is fully unprivileged: any EOA can call `requestKLAYTransfer(address(0), ...)`.
- The attacker must sacrifice their own KAIA (griefing cost), which limits economic incentive for profit-seeking attackers but does not prevent a motivated griefing or denial-of-service attack.
- Bridge operators relay events automatically and have no on-chain mechanism to filter zero-address destinations; the relay logic in `handleRequestValueTransferEvent` forwards the event as-is.
- No existing guard in the contract, the Go relay layer, or the operator voting mechanism rejects a zero-address `_to`.

---

### Recommendation

Add a zero-address guard at the earliest validation point in each request function:

```solidity
// BridgeTransferKLAY._requestKLAYTransfer
require(_to != address(0), "zero recipient address");

// BridgeTransferERC20._requestERC20Transfer
require(_to != address(0), "zero recipient address");

// BridgeTransferERC721._requestERC721Transfer
require(_to != address(0), "zero recipient address");

// BridgeOperator.registerOperator
require(_operator != address(0), "zero operator address");
```

Apply the same guard symmetrically in `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` so that even if a malformed event is relayed, the destination bridge rejects it before consuming the nonce or transferring funds.

---

### Proof of Concept

1. Deploy the bridge pair (source + destination) with KAIA liquidity in the destination bridge.
2. Call on the source bridge:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(address(0), 1 ether, "");
   ```
   This passes all checks (`isRunning`, `msg.value > feeLimit`) and emits `RequestValueTransfer` with `to = address(0)`, incrementing `requestNonce`.
3. Bridge operators observe the event and call on the destination bridge:
   ```solidity
   bridge.handleKLAYTransfer(txHash, from, address(0), 1 ether, nonce, blockNum, "");
   ```
   (repeated by each operator until quorum is reached)
4. After quorum, `address(0).call.value(1 ether)("")` executes and returns `ok = true`; 1 KAIA is burned from the destination bridge's balance.
5. Verify: `address(destinationBridge).balance` decreased by 1 KAIA; `address(0).balance` increased by 1 KAIA.
6. Repeat to drain the destination bridge's entire KAIA reserve.
