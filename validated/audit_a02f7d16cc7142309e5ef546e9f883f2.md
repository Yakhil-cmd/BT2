### Title
Cross-tenant webhook forgery — `repository_owner` (signature selector) diverges from `repository.full_name` (handler target), letting `LabelCapturingHandler` mutate a production stack authenticated by an unrelated organization's secret - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `GitHubApp`/`webhook_secret` to validate the HMAC signature against using `repository_owner`, which falls back from `repository.owner.login` to `organization.login` when the former is absent. `LabelCapturingHandler`, however, resolves its target repository/stack from the independently-controlled `repository.full_name` field, which its `ExplicitParameters` schema requires but does not tie to `repository.owner.login` or `organization.login` in any way. In a multi-organization Shipit deployment (a supported and tested configuration), this lets an attacker who can produce a signature valid for *any one* onboarded organization forge a `pull_request`/`reopened` event whose `repository.full_name` points at a completely different organization's production stack.

### Finding Description
The broken binding, stated as an equality that the code must (but does not) enforce:
`repository_owner` used in `Shipit.github(organization: repository_owner)` == owner of `repository.full_name` used by the handler to locate the target `Stack`.

Trace:
- `app/controllers/shipit/webhooks_controller.rb:59-62` — `repository_owner` is computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. If the attacker omits `repository.owner.login` (while still including `repository.full_name` elsewhere in the same payload, since it's a separate JSON key), the fallback resolves to whatever the attacker puts in `organization.login`. [1](#0-0) 
- `verify_signature` (lines 24-30) then does `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that organization's configured secret. [2](#0-1) 
- `Shipit.github` (`lib/shipit.rb:170-181`) looks up `github_app_config(organization)` per-organization, meaning different organizations can have distinct `webhook_secret`s, confirmed by the existence of a dedicated `secrets_double_github_app.yml` multi-app test fixture and per-org lookup in `github_app_config`. [3](#0-2) 
- `LabelCapturingHandler`'s params schema requires only `repository.full_name`, not `repository.owner.login`, so a payload lacking `repository.owner.login` still parses successfully: [4](#0-3) 
- The handler resolves its target `Repository`/`Stack` purely from `params.repository.full_name`, with no cross-check against `repository_owner` or `organization.login`: [5](#0-4) 
- On `action == "reopened"` for a present, non-archived stack, `capture_labels` persists attacker-supplied label names onto `stack.pull_request`: [6](#0-5) [7](#0-6) 

Exploit flow: attacker crafts a raw POST body with `organization.login` set to an organization whose webhook secret they know or which is configured with no `webhook_secret` (in which case `verify_webhook_signature` returns `true` unconditionally per `return true unless webhook_secret`), omits `repository.owner.login`, and sets `repository.full_name` to the victim's production repository/stack (e.g. `victim-org/prod-repo`). `verify_signature` authenticates the request against the attacker-controlled/lenient organization's secret, passes, and the `pull_request`/`reopened` handler then operates against the victim's stack because it only ever reads `repository.full_name`.

Existing guards fail to close this: `drop_unhandled_event` only checks the event type is handled; `verify_signature` never compares the org used for verification with the org implied by `repository.full_name`; the `ExplicitParameters` schema for `LabelCapturingHandler` never requires or validates `repository.owner.login`; `GithubOrganizationUnknown` only protects against organizations that are not configured at all, not against divergence between two configured organizations.

### Impact Explanation
A payload authenticated under one organization's (or a secret-less organization's) webhook secret can write attacker-controlled label names onto the `PullRequest` of a `Stack` belonging to a different, victim organization/repository. Because `ReviewStack#env` uppercases label names into environment variables (per the target's stated behavior), an attacker can inject arbitrary environment keys/values into a **production** stack's deploy environment without ever authenticating as, or being a collaborator on, that organization/repository. This is a payload for one repository mutating another's stack/record, matching the Critical impact category explicitly listed ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
This requires a **multi-organization** Shipit deployment (`github_default_organization` non-nil, i.e., `secrets.github` keyed by org — a configuration this codebase explicitly supports and tests via `test/dummy/config/secrets_double_github_app.yml`). The attacker must be able to produce a valid signature for at least one onboarded organization — either because that organization's `webhook_secret` is unset/blank (trivially bypassed, `verify_webhook_signature` returns `true`), or because the attacker legitimately owns/administers a low-trust organization also onboarded to the same Shipit instance. Given that, the attack is fully repeatable against any victim repository/stack tracked by the instance, requiring only crafting one raw HTTP POST per attempt — no GitHub session, API token, or Shipit credentials needed.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: derive `repository_owner` strictly from `repository.full_name`'s owner segment (or require `repository.owner.login` to match the owner portion of `repository.full_name`), and reject payloads that fall back to `organization.login` when `repository.full_name` is present and its owner disagrees. At minimum, `LabelCapturingHandler`'s (and all handlers') schemas should require `repository.owner.login` and cross-check it equals the organization used for signature verification before processing.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, under `organization fallback selection`):
```ruby
test "organization fallback selection: pull_request reopened cannot cross-authenticate a different org's production stack" do
  # Setup: two orgs configured, "attacker-org" (webhook_secret known/blank) and "victim-org" (production stack)
  victim_stack = shipit_stacks(:production_review_stack) # environment: "production", repository full_name "victim-org/prod-repo"
  pr = victim_stack.pull_request # existing PullRequest with labels []

  payload = {
    action: "reopened",
    number: pr.number,
    pull_request: { id: 1, number: pr.number, url: "...", title: "x", state: "open",
                     additions: 1, deletions: 0,
                     head: { sha: "a"*40, ref: "attacker-branch" },
                     user: { login: "attacker" },
                     assignees: [],
                     labels: [{ name: "MALICIOUS_ENV=1" }] },
    repository: { full_name: "victim-org/prod-repo" }, # no owner.login -> falls back
    organization: { login: "attacker-org" },            # attacker-controlled/lenient org
    sender: { login: "attacker" }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = sign_with("attacker-org", payload) # attacker knows attacker-org's secret

  # BEFORE: repository_owner used for verification ("attacker-org") != owner of repository.full_name ("victim-org")
  assert_not_equal "attacker-org", "victim-org"

  post :create, body: payload, as: :json
  assert_response :ok

  # AFTER: attacker-authenticated-as-attacker-org request mutated victim-org's production stack's PR labels
  pr.reload
  assert_equal ["MALICIOUS_ENV=1"], pr.labels
end
```
This demonstrates the two named values (`repository_owner` used for signature selection vs. the owner implied by `repository.full_name` used by the handler) diverge, and that divergence is exploitable to mutate a production stack's `PullRequest`/environment without authenticating against the victim organization's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
