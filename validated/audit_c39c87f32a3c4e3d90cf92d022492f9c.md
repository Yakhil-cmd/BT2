### Title
Stack-scoped API token can be used to read status/output of any stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` accessor to resolve the target stack directly from `Stack.from_param!(params[:stack_id])` instead of using the tenant-scoped `stacks` relation that every other API controller relies on. As a result, an `ApiClient` token that is scoped to a single stack (`ApiClient#stack_id`) can be used to read the CI/build status (including deploy activity) of *any* stack in the installation, not just the one it was authorized for.

### Finding Description
Across the API, authorization for a given request is a combination of two independent checks:
1. `require_permission` / `check_permissions!` — verifies the *operation* (`read`, `write`, `deploy`, ...) against the client's `permissions` list.
2. `stacks` — a controller helper that scopes the queryable set of stacks to the ones the client is allowed to touch:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`check_permissions!` only checks the operation/scope string (e.g. `"read:stack"`); it has no knowledge of *which* stack the request targets. The actual per-stack authorization binding — "the stack(s) this token is entitled to touch" — is enforced exclusively by the `stacks` scoping helper.

`Api::CCMenuController`, however, redefines `stack` to bypass that scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This breaks the binding `stack the token authorizes == stack the request touches`. A client whose `stack_id` column restricts it to one stack (e.g. fixture `here_come_the_walrus`, scoped to `shipit`) [3](#0-2) 
still only needs `read:stack` permission — which is satisfied — to call `show` with an arbitrary `stack_id` belonging to a completely different stack, and `Stack.from_param!` will resolve it because it queries the unscoped `Stack` model rather than the client-scoped relation.

This is directly analogous to the JalaSwap bug: the amount authorized for the swap (`amountIn`, pre-wrap) differed from the amount actually acted upon (`wrappedAmount`, post-wrap), letting the mismatch be exploited. Here, the *stack the token is authorized for* (`ApiClient#stack_id`) differs from the *stack the request actually touches* (any `params[:stack_id]`), because the enforcement point (`stacks`) was silently swapped out for an unscoped lookup in one controller.

### Impact Explanation
An attacker in possession of a legitimately-issued, narrowly-scoped API token (scoped to one stack) can query the CCMenu XML endpoint for any other stack in the Shipit installation and obtain:
- the stack's name,
- last build/activity/status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`),
- lock state,
- deploy/rollback history info exposed through `deploys_and_rollbacks`.

This is an unauthorized cross-stack read of stack/task state that the scoping mechanism (`ApiClient#stack_id`) was specifically designed to prevent, matching the "escalation into authorization scope / unauthorized read of stack state, task streams or deploy output" impact class.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a supported, documented feature — see the `stack` association and `stack_id?` scoping in `ApiClient`/`BaseController`) to third parties (e.g. CI dashboards that consume the CCMenu XML feed) expecting them to only see their own stack. No special privileges beyond a valid, low-scope token are required, and the only "attack" is supplying a different `stack_id` parameter — no signature forgery or credential theft needed.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, client-scoped `stacks.from_param!(params[:stack_id])` from `BaseController`, so that stack-scoped tokens cannot resolve stacks outside their authorized scope:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Add a regression test asserting that a token created with `stack:` set to stack A returns 404/forbidden when `stack_id` refers to stack B.

### Proof of Concept
1. Create two stacks, A and B.
2. Create an `ApiClient` scoped to stack A only (`stack: A`, `permissions: ['read:stack']`), as in fixture `here_come_the_walrus`.
3. Authenticate with that client's token and request:
   `GET /api/ccmenu/<stack_B_param>?token=<client_token>`
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks`/`stack_id?` scoping), the request succeeds and returns stack B's build/activity XML, even though the token was only meant to authorize access to stack A. [4](#0-3) [1](#0-0)
