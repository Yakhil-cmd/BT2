## Verdict: Vulnerability confirmed (but the root cause is broader than "read vs. write scoping" — it's a total absence of repository scoping in the write path)

### Title
Forged `status` webhook creates a `Status` on any Commit sharing the same SHA regardless of repository, and firing side effects before any repository-scoped refresh can occur — (`File: app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` selects target commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with **no check that the commit's owning `Stack`/`Repository` corresponds to the webhook's `repository`/`repository_owner`**. `Commit#refresh_statuses!` (`app/models/shipit/commit.rb:156-163`), by contrast, *is* correctly scoped to the commit's own stack via `stack.github_repo_name`/`stack.github_api`, but that scoping is irrelevant to mitigating the write because it runs later, asynchronously, and does not retract the already-persisted forged `Status` or the callbacks it already fired.

### Finding Description
Binding claimed broken: `write_scope(StatusHandler) == read_scope(refresh_statuses!)`, i.e. both paths restrict Status mutation/read to the commit's actual owning repository (`commit.stack.github_repo_name`).

Trace:
- `WebhooksController#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event('status')`, invoking `StatusHandler.call(params)` — no per-commit or per-repository check beyond the top-level `verify_signature`, which validates against `Shipit.github(organization: repository_owner)`'s `webhook_secret` [1](#0-0) .
- `StatusHandler#process` does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this matches **every** `Commit` row in the entire database with that SHA, independent of which repository/organization signed the webhook [2](#0-1) .
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!` creates a `Status` row synchronously [3](#0-2) .
- `Status` has `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery, :broadcast_update, on: :create`, both firing in-request, before any job runs [4](#0-3) .
- By contrast, `Commit#refresh_statuses!` correctly scopes the GitHub read to `stack.github_api.statuses(github_repo_name, sha, ...)`, where `github_repo_name` is delegated to the commit's real `stack` [5](#0-4) [6](#0-5) . This job only runs later, asynchronously (`RefreshStatusesJob`, enqueued via `after_commit :schedule_refresh_statuses!` on Commit creation, or periodically on stack refresh) [7](#0-6) [8](#0-7) .

Root cause: the write path has **no** repository scope check at all (not "a mismatched scope," but a complete absence of one), so the read-path's correct scoping in `refresh_statuses!` can never retroactively undo the forged create nor its already-fired `after_create`/`after_commit` callbacks.

`verify_signature` only proves the payload was signed by the `Shipit.github(organization: repository_owner)` configured for *some* organization known to this Shipit instance; it says nothing about which `Commit`/`Stack` the `sha` in the payload should be applied to. Nothing else in the stack (`ExplicitParameters` schema on `StatusHandler`, `drop_unhandled_event`, model validations) checks that the target `Commit`'s `stack.repository` matches `params.repository`/`repository_owner`.

### Impact Explanation
An attacker who can get one valid, signed `status` webhook accepted by the Shipit host (i.e., control over a repository/org onboarded to Shipit, or exploiting the separate `verify_webhook_signature` no-secret-configured bypass) can inject a forged `Status` (state, description, target_url, context, created_at all attacker-controlled) onto **any** `Commit` row sharing the reused/colliding SHA, across stacks/repositories/tenants, immediately triggering `enable_ci_on_stack` and `schedule_continuous_delivery` for a victim stack that never authenticated this payload. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team," since it can enable/accelerate a deploy pipeline on a stack the attacker does not control. It's repeatable per request and cross-tenant in multi-organization Shipit deployments (`docs/setup.md` documents multiple `github:` orgs each with independent webhook secrets) [9](#0-8) .

### Likelihood Explanation
Requires the attacker to produce a webhook payload that (a) passes `verify_webhook_signature` for some organization known to the Shipit instance, and (b) references a `sha` that collides with a `Commit` already tracked under a different stack/repository. Git SHA1s are content-derived and portable: an attacker can construct a commit object (same tree, parents, author/committer, timestamps, message) reproducing an identical SHA in a repository they control if the victim commit's content is known/public, then trigger a `status` event for it. This is nontrivial but plausible in multi-tenant or open-source-mirroring setups.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the webhook's own `repository.full_name` (matching `commit.stack.repository.github_repo_name`) before calling `create_status_from_github!`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })`, mirroring the scoping already used correctly in `Commit#refresh_statuses!`.

# frozen_string_literal: true

module Shipit
  class RefreshStatusesJob < BackgroundJob
    queue_as :default

    def perform(params)
      if params[:commit_id]
        Commit.find(params[:commit_id]).refresh_statuses!
      else
        stack = Stack.find(params[:stack_id])
        stack.commits.order(id: :desc).limit(30).each(&:refresh_statuses!)
      end
    end
  end
end
