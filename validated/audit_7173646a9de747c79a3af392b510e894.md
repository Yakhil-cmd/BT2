## Analysis

`storage.assocUnstableMessages` is a global, process-wide map keyed by unit hash that accumulates one entry per unstable unit that contains a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message [1](#0-0) . Every unit is added to it when written, and an entry is only deleted once that specific unit's MCI is stabilized [2](#0-1) . This means the map's size scales with the number of currently *unstable* data-feed/definition/vote-carrying units network-wide, not with any bound tied to a single address or asset.

Several hot-path functions do a full, synchronous, O(n) scan over every key in this map on every invocation:
- `dataFeedExists` (used by `in_data_feed` oscript op and `attested`/`in data feed` definition ops) iterates `for (var unit in storage.assocUnstableMessages)` and then iterates every message in each entry, for every AA data-feed lookup that opts into unstable results (`bAA=true`) [3](#0-2) .
- `readDataFeedValue` does the identical full scan when `unstable_opts` is requested [4](#0-3) .
- `getUnconfirmedAADefinition` and `getUnconfirmedAADefinitionsPostedByAAs` in `storage.js` do the same full scan, and are invoked during every secondary AA trigger dispatch to check whether the child AA's definition is still unconfirmed [5](#0-4) , [6](#0-5) .
- `hasUnstableOpVoteCount` similarly walks the whole map [7](#0-6) .

Any user can post ordinary units carrying a `data_feed` message (data feeds are permissionless — any address can post one) and simply not have them confirmed quickly (e.g., post many low-priority units, or exploit normal network latency/backlog), which keeps entries resident in `assocUnstableMessages` for as long as they remain unstable. Because there is no cap on the number of pending (unstable) data-feed-bearing units the map can hold, an attacker can grow it arbitrarily by flooding the DAG with cheap `data_feed` units before they stabilize. Every AA that evaluates `[in_data_feed]`/`data_feed` with `ifseveral`/unstable options, and every secondary AA trigger dispatch, then pays the cost of this unbounded in-memory scan, on every full node, for every relevant trigger — this is directly analogous to the reported `SafeGuard.nonces` issue: an ever-growing array/map that is fully iterated on a hot path with no bound or cleanup mechanism controllable by an unprivileged caller.

## Impact
This does not corrupt consensus data, but it degrades validation/AA-execution performance on every full node proportionally to attacker-controlled backlog size, since the loop runs synchronously inside AA trigger handling (`aa_composer.js`) and formula evaluation used during unit/AA validation. A sufficiently large backlog can meaningfully slow down or stall AA trigger processing and stability advancement across the network — a shared, unbounded resource that is trivial for any unprivileged unit poster to inflate.

## Recommendation
Index `assocUnstableMessages` (or a derived structure) by `app` and by author address so that `dataFeedExists`, `readDataFeedValue`, `getUnconfirmedAADefinition`, `getUnconfirmedAADefinitionsPostedByAAs`, and `hasUnstableOpVoteCount` can look up only the relevant subset instead of scanning every unstable unit in the system. Alternatively, cap/limit the number of concurrently tracked unstable data-feed/definition/vote units per address, or amortize/limit-check pending backlog size before doing the full scan.

## Note on confidence
I could not fully trace how large this backlog can realistically grow in practice (e.g., whether TPS-fee/backlog limits elsewhere in the codebase effectively bound the number of concurrently-unstable units), so the severity depends on how effective those independent throttling mechanisms are at limiting `assocUnstableMessages` size. I was not able to verify this within the current investigation and flag it as an open question — a deeper look at `tps_fee`/mempool backlog limits (outside what I retrieved) would be needed to confirm the practical magnitude of the DoS.

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}

// arrAddresses is an array of AA addresses whose definitions are posted by other AAs
function getUnconfirmedAADefinitionsPostedByAAs(arrAddresses) {
	var payloads = [];
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (!objUnit.bAA)
			continue;
		assocUnstableMessages[unit].forEach(function (message) {
			if (message.app !== 'definition')
				return;
			var payload = message.payload;
			if (arrAddresses.indexOf(payload.address) >= 0)
			payloads.push(payload);
		});
	}
	return payloads;
}
