(accrue)))`. This exactly mirrors the Popcorn bug class: one function in a set of sibling state-mutating functions skips the checkpoint-sync step that all its siblings perform, letting a stale index be used to compute an economic effect (here, loss distribution) that harms other position holders.

### Title
`socialize-debt` skips interest accrual before writing down `lindex`, causing bad-debt losses to be mis-distributed across suppliers - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults)

### Summary
Every state-mutating vault entry point (`deposit`, `redeem`, `system-borrow`, `system-repay`, `set-fee-reserve`, `set-points-util`, `set-points-rate`, `flashloan`) begins with `(u (try! (accrue)))` to bring `index`/`lindex`/`assets` up to date before mutating them. `socialize-debt` is the one exception: it reads `idx`, `current-lindex`, `old-total-assets`, and `total-assets` directly off possibly-stale storage and writes a new `lindex` from them without accruing first.

### Finding Description
`socialize-debt` is called by `market.clar`'s `liquidate` flow (`vault-socialize-debt`) when a borrower's collateral runs out and remaining bad debt must be written off. It computes:
- `debt-reduction = scaled-amount * idx / INDEX-PRECISION` using the **unaccrued** `idx`
- `old-total-assets = total-assets()` where `total-assets()` internally depends on `assets` and the debt computed via the **unaccrued** `index`
- `new-lindex = current-lindex * (old-total-assets - debt-reduction) / old-total-assets` [1](#0-0) 

Because interest that accrued since `last-update` is not folded into `idx`/`lindex`/`assets` first, the socialization math operates on a stale snapshot of `total-assets`, `index`, and `lindex`. Every other vault mutator normalizes state via `accrue` first: [2](#0-1) 

`accrue`'s own logic shows exactly what gets skipped — index/lindex advancement and treasury minting based on time-delta interest: [3](#0-2) 

The victims are the vault's existing LPs (zToken/share holders) whose `lindex`-based redemption value is written down by `socialize-debt`. The attacker/beneficiary is whichever unprivileged party's transaction lands adjacent to (and before) the liquidation call: e.g., a supplier who redeems large shares immediately before the socialize-debt-driven write-down, or a borrower/second liquidator whose earlier same-block `accrue`-triggering call changes `last-update`/`index` in a way that shifts how much of the loss the write-down formula subsequently absorbs. Because `debt-reduction` is computed off the stale `idx` while other suppliers' shares are priced against the correctly-`accrue`d index elsewhere in the same or an adjacent transaction, LPs redeeming around the socialization event get a share value computed from an inconsistent state versus LPs who redeem after a normal `accrue`-first mutator runs — the two paths diverge in which interest layer is folded in before the loss haircut is applied, letting whichever party acts first "beat" the pending write-down while the remaining LPs absorb a disproportionate share of the socialized loss (since the write-down denominator `old-total-assets` is missing not-yet-accrued interest that later redeemers/depositors would still see credited).

### Impact Explanation
This is a temporary freezing/mis-distribution of unclaimed yield: suppliers who interact with the vault around a bad-debt socialization event receive a `lindex` haircut computed from state that omits legitimately accrued-but-not-yet-materialized interest, meaning the loss is not proportionally spread across all suppliers as designed — some absorb more, some (who act in the stale window) effectively dodge part of the loss. This falls under "High – theft of unclaimed yield ... temporary freezing of funds" since supplier redemption values are directly determined by `lindex`, and this miscalculation is caused entirely by protocol code (root cause: a missing `accrue` call), not by third-party oracle data or DAO action.

### Likelihood Explanation
Bad-debt socialization only occurs on liquidations that leave residual unrecoverable debt (`no-collateral-left` in `market.clar`'s `liquidate`), which is not an everyday event but is a designed code path reachable by any liquidator with no special privilege. The staleness window is bounded by how long since the vault's `last-update`, but on a network where multiple transactions can share `stacks-block-time`, and where liquidation itself can be triggered any time debt is unhealthy, the inconsistency is reliably present whenever any accrual-worthy time has elapsed since the vault's last accrual before the liquidation transaction executes.

### Recommendation
Add `(u (try! (accrue)))` as the first binding in `socialize-debt`, matching every other vault mutator, so that `index`, `lindex`, and `assets` are brought current before computing `debt-reduction`, `old-total-assets`, and the write-down of `new-lindex`.

### Proof of Concept
1. Time passes since the vault's `last-update` without any accrual-triggering call (e.g., no deposit/redeem/borrow/repay happens on `vault-stx` for a while).
2. A borrower's position becomes fully unhealthy with no collateral remaining; a liquidator calls `market.clar liquidate`, which triggers `no-collateral-left` bad-debt handling and calls `vault-socialize-debt` → `vault-stx.socialize-debt`.
3. `socialize-debt` reads `idx`, `current-lindex`, and `total-assets()` without first calling `accrue`, so the not-yet-accrued interest for the elapsed time is excluded from `old-total-assets` and from the `idx` used in `debt-reduction`.
4. `new-lindex` is computed from this stale snapshot: `current-lindex * (old-total-assets - debt-reduction) / old-total-assets`, permanently and incorrectly discounting supplier share value relative to what it would be had `accrue` run first (as it does in every sibling mutator such as `deposit`/`redeem`/`system-repay`), producing a mis-distributed loss among LPs versus the party who redeems/deposits immediately before vs. after the socialization transaction in the same window. (define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
