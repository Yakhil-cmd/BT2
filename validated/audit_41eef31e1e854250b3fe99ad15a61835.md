### Title
Webhook signature verification is keyed off an attacker-controlled `repository.owner.login`/`organization.login` field, letting one organization's webhook secret forge events for another organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses **which** GitHub App/organization secret to verify the HMAC signature against by reading an unauthenticated field out of the same JSON body it is trying to authenticate. The handlers that actually act on the payload (creating commits, statuses, review stacks, memberships, etc.) resolve the **target repository/stack** from a *different* field in that same body (`repository.full_name`). Nothing binds these two fields together, so a webhook that is validly signed for organization A can carry a `repository.full_name` pointing at organization B's stack.

### Finding Description
`verify_signature` selects the verifying `GitHubApp` using `repository_owner`, which is derived purely from the untrusted payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) via `github_app_config`, and `GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) [4](#0-3) 

However, every downstream handler determines the *actual* repository/stack to mutate from a completely independent field of the same body, `repository.full_name`, never cross-checked against `repository.owner.login`/`organization.login` used for signature selection: [5](#0-4) [6](#0-5) 

This is the off-by-one bug class analogue described in the report: a value is checked against the wrong reference (here, the wrong "identity") — the engine authenticates the request against organization A's secret (from `repository.owner.login`/`organization.login`) but then acts on organization B's repository (from `repository.full_name`), because the two are never required to match. In a Shipit instance hosting multiple GitHub organizations (`Shipit.github_organizations`), this breaks the binding "organization that authenticated" == "repository that is written." Concretely: if any onboarded organization has no `webhook_secret` configured (a supported, legitimate configuration state per `GitHubApp#initialize`/`verify_webhook_signature`), an unauthenticated attacker can send a payload with `repository.owner.login`/`organization.login` set to that unsecured organization while setting `repository.full_name` to any other organization's repository, and the request sails through `verify_signature` untouched, then drives handlers (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against the victim organization's stack.

### Impact Explanation
This is a confused-deputy/authentication-bypass condition scoped to multi-organization Shipit deployments: any organization admin (or anyone who learns/leaks one organization's `webhook_secret`, or an organization intentionally left without one) can forge signed webhook traffic for repositories belonging to unrelated organizations on the same Shipit instance. Concretely reachable effects include forging `status`/`check_suite` events that fabricate a `success` CI status on an arbitrary commit (`Commit#deployable?` gates deploys on status state), enabling an unauthorized deploy of a commit that never actually passed CI on the victim's repository, and forging `push`/`membership` events that mutate the victim stack's commit history or team membership records maintained purely from webhook data. This lines up with the "unauthorized deploy" and "cross-repository writes" impact tiers.

### Likelihood Explanation
Exploitability is conditioned on the specific deployment configuring more than one GitHub organization (`github_default_organization` present) and at least one of them lacking a `webhook_secret`, or an attacker holding a legitimately-issued secret for one org in a shared multi-tenant instance. Given `webhook_secret` is presence-checked and silently bypassed when absent (`return true unless webhook_secret`), this is a realistic, not merely theoretical, misconfiguration/multi-tenancy scenario that the engine's own code makes exploitable across organizational boundaries rather than confining trust to the matching organization.

### Recommendation
After parsing and verifying the signature, re-derive the organization from the same field the handlers will use (`repository.full_name` owner segment) and require it to match the organization whose secret verified the request; reject the webhook otherwise. Alternatively, verify the signature against the secret of the organization owning the resolved `full_name` repository, not the organization named in a separate, unrelated payload field.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orgA` (no `webhook_secret` set) and `orgB` (has a stack/repository and a secret webhook_secret).
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "after": "<attacker-chosen sha>"
}
```
with any (or no) `X-Hub-Signature` value.
3. `verify_signature` resolves `repository_owner` to `"orgA"`, calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `Shipit::Webhooks.for_event('push')` handlers then run using `repository.full_name = "orgB/victim-repo"`, mutating `orgB`'s stack despite the request never being validated against `orgB`'s secret. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
