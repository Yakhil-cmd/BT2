Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler`, which processes GitHub `status` webhooks, looks up commits by `sha` alone across the **entire Shipit database**, with no filtering by the repository the webhook was actually verified for. Any GitHub organization/repository onboarded to a shared Shipit instance can therefore forge a `success`/`failure`/`pending` commit status onto a commit belonging to a completely different, unrelated stack/repository/organization, breaking the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook only against the organization derived from the payload's own `repository.owner.login`/`organization.login` field [1](#0-0) . This proves the request came from *some* organization connected to the Shipit instance, but says nothing about which repository's commits the handler is allowed to mutate.

`Handler` base class does define a `stacks` helper that scopes to the repository named in the payload via `Repository.from_github_repo_name(repository_name)` [2](#0-1) , and other handlers such as `PushHandler` and `CheckSuiteHandler` correctly use this repository-scoped `stacks`/`Repository` lookup before touching any commit [3](#0-2) [4](#0-3) .

`StatusHandler`, however, never calls `stacks` or checks `repository_name` at all: [5](#0-4) 
It queries `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository/organization sent the (validly signed) webhook.

GitHub's Statuses API (`POST /repos/{owner}/{repo}/statuses/{sha}`) allows a repository admin to set a status on **any** SHA string for their own repository, even one that doesn't correspond to a real commit in that repo. So an attacker who administers any org/repo connected to this multi-tenant Shipit instance (a supported, documented configuration — see `docs/setup.md` "Using Multiple GitHub Applications" [6](#0-5) ) can:
1. Learn the SHA of a target commit tracked by a victim stack in a different organization (commit SHAs are often public).
2. Call GitHub's Statuses API on their own repository with that SHA and `state: success`.
3. GitHub sends a webhook, signed with the attacker's own organization's `webhook_secret`, which correctly passes `verify_webhook_signature` for that organization [7](#0-6) .
4. `StatusHandler` matches the victim's commit purely by `sha` and writes the forged status onto it, with no cross-check against the attacker's own repository.

### Impact Explanation
Commit statuses directly gate deploy and merge decisions:
- `Commit#deployable?` requires `success?` on the current status [8](#0-7) .
- `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?` read `head.statuses_and_check_runs` via `StatusChecker` to decide mergeability [9](#0-8) .
- `ProcessMergeRequestsJob` automatically merges pull requests once `all_status_checks_passed?` is true [10](#0-9) .

By forging a `success` status on a victim commit they don't control, an unprivileged attacker (with only admin/write access to an unrelated repo on the same Shipit instance) can make CI checks appear to have passed on the victim stack, enabling an unauthorized automatic merge or unblocking an unauthorized deploy — a cross-repository write and an unauthorized merge/deploy, matching the Critical impact bar in the rules.

### Likelihood Explanation
Exploitation requires only ordinary access to any onboarded organization's repository (no Shipit session, API token, or webhook secret needs to be stolen — the attacker uses their own legitimate GitHub credentials/webhook), and knowledge of a target commit SHA, which is frequently public. This is realistic in any deployment using Shipit's documented multi-organization configuration.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook was actually signed for, mirroring `PushHandler`/`CheckSuiteHandler`: restrict the `Commit` lookup to `stacks` (i.e., commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`) instead of a bare global `Commit.where(sha:)`.

### Proof of Concept
1. Onboard/administer Organization A on a shared Shipit instance (multi-org `secrets.yml` configuration).
2. Identify a commit SHA `X` tracked by a stack belonging to Organization B (a different tenant) — e.g., from a public repository's commit history.
3. As an admin of Organization A's repo `repoA`, call `POST /repos/OrgA/repoA/statuses/X` with `{"state":"success","context":"ci/forged"}`.
4. GitHub delivers a `status` webhook to Shipit, signed with OrgA's real `webhook_secret`; `WebhooksController#verify_signature` passes.
5. `StatusHandler.process` executes `Commit.where(sha: "X")`, finds the commit in Organization B's stack, and calls `create_status_from_github!`, writing a forged `success` status that Organization B's stack now uses to gate deploy/merge decisions — despite the attacker having no access to Organization B.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
