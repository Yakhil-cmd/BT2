### Title
Stack-scoped `ApiClient` tokens can read any stack's CCMenu status, bypassing stack authorization - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column [1](#0-0) . The generic `Api::BaseController` enforces this scoping consistently: `#stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `#stack` resolves the requested `stack_id` param only within that scoped relation via `stacks.from_param!` [2](#0-1) . This is the authorization binding: `ApiClient#stack_id` (what the token is authorized to touch) must equal the `stack_id` param the request resolves to.

`Api::CcmenuController`, however, overrides `#stack` to bypass this scoping entirely, resolving the stack directly and globally: `Stack.from_param!(params[:stack_id])` [3](#0-2) . It only enforces the coarse `require_permission :read, :stack` permission bit via `before_action` [4](#0-3) , which is satisfied by any client holding the `read:stack` permission string, regardless of which specific `stack_id` it was scoped to [5](#0-4) . As a result, a token that is authorized (`stack_id`) for stack A can be used to fetch CCMenu status/output for any other stack B in the installation, because the controller never checks that `params[:stack_id]` matches `current_api_client.stack_id`.

This breaks the binding "a stack a token authorises versus a stack it touches" explicitly called out in scope.

### Impact Explanation
An attacker holding any valid `read:stack`-permissioned API token (e.g. one intentionally scoped narrowly to a single low-sensitivity stack) can use it to read deploy/rollback status, output link, and build state (`last_deployed_at`-equivalent info exposed in the CCMenu XML) for every other stack managed by the Shipit installation, including stacks the token was never meant to see. This is an unauthenticated (with respect to the intended scope) read of stack state across repositories, which the rules classify as High severity ("unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
Exploitation requires only possession of any `ApiClient` token bearing `read:stack` — no admin/session access, no webhook secret, no GitHub credentials. Stack-scoped tokens are a documented, supported feature (`ApiClient belongs_to :stack, optional: true`), and the vulnerable endpoint is a standard, unauthenticated-except-for-basic-token API route (`Api::CcmenuController#show`), reachable simply by supplying a different `stack_id` in the URL param.

### Recommendation
Change `Api::CcmenuController#stack` to reuse the scoped resolution from `BaseController`, i.e. `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped token can only resolve the stack it is authorized for.

### Proof of Concept
1. An admin creates a stack-scoped `ApiClient` (`stack_id` = Stack A's id) with `permissions: ['read:stack']` (supported via the `ApiClient` model/UI, and exemplified by `CCMenuUrlController#client`) and hands out its `authentication_token`.
2. The attacker (holder of this token, with no rights to Stack B) issues:
   `GET /api/stacks/<StackB-repo_owner>/<StackB-repo_name>/<StackB-environment>/ccmenu.xml` with `Authorization: Basic <token>--`.
3. `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` passes because the client's `permissions` array includes `read:stack` [5](#0-4) .
4. `#stack` resolves via `Stack.from_param!(params[:stack_id])` [6](#0-5) , unscoped by `current_api_client.stack_id`, returning Stack B and rendering its CCMenu status/output — despite the token only being authorized for Stack A.
