### Title
Malicious Fast-Sync Peer Can Overwrite Arbitrary Staking DB Entries via Unvalidated `P2PStakingInfo.BlockNum` — (`datasync/downloader/downloader.go`, `datasync/downloader/queue.go`)

---

### Summary

During fast sync, `commitFastSyncData` writes staking info to the DB using `result.StakingInfo.BlockNum` as the key. Because the `DeliverStakingInfos` validation function is an acknowledged no-op (`// TODO-Kaia-Snapsync update validation logic`), a malicious sync peer can return a `P2PStakingInfo` with `BlockNum` set to any arbitrary staking-interval block number, causing the node to overwrite the staking DB entry at that block with attacker-controlled `RewardAddrs`, `KEFAddr`, and `KIFAddr`.

---

### Finding Description

**Step 1 — No-op validation in `queue.DeliverStakingInfos`:** [1](#0-0) 

The `validate` closure is explicitly a TODO and always returns `nil`. No check is made that `stakingInfoList[i].BlockNum` matches `header.Number`.

**Step 2 — Index-based assignment, not BlockNum-based:**

The `deliver` function iterates `request.Headers` and calls `reconstruct(accepted, res)`, which assigns `result.StakingInfo = stakingInfoList[index]` purely by position. [2](#0-1) 

**Step 3 — `commitFastSyncData` uses the peer-supplied `BlockNum` as the DB key:** [3](#0-2) 

`result.StakingInfo.BlockNum` — fully attacker-controlled — is passed directly to `PutStakingInfoToDB` as the storage key, not `result.Header.Number`.

**Step 4 — `PutStakingInfoToDB` writes unconditionally:** [4](#0-3) 

No bounds check, no cross-reference against the canonical chain.

**Step 5 — The staking DB is the authoritative source for pre-Kaia reward distribution:** [5](#0-4) 

Before the Kaia fork, `GetStakingInfo` reads the DB first and returns immediately if an entry exists — bypassing state-derived values. A corrupted DB entry therefore takes precedence over the correct on-chain state.

**Contrast with `SyncStakingInfo`**, which does validate: [6](#0-5) 

The recovery path checks `stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum` and aborts on mismatch. The fast-sync path has no equivalent guard.

---

### Impact Explanation

A malicious peer connected during fast sync can overwrite `RewardAddrs`, `KEFAddr`, and `KIFAddr` at any historic staking-interval block number. Because the staking DB is the primary source for pre-Kaia reward distribution, this directly reroutes block rewards and treasury fund flows to attacker-controlled addresses for the corrupted epochs. This satisfies the "unauthorized reward distribution / reroutes treasury or block-reward value" impact gate.

---

### Likelihood Explanation

Fast sync is a standard, permissionless P2P flow. Any peer that the syncing node connects to can serve staking info responses. No privileged access, governance key, or validator collusion is required — only the ability to be a connected P2P peer during fast sync.

---

### Recommendation

In `queue.DeliverStakingInfos`, replace the TODO with a real validation:

```go
validate := func(index int, header *types.Header) error {
    if stakingInfoList[index].BlockNum != header.Number.Uint64() {
        return errInvalidStakingInfo
    }
    return nil
}
```

Additionally, in `commitFastSyncData`, use `result.Header.Number.Uint64()` as the DB key rather than `result.StakingInfo.BlockNum`, so the write location is always determined by the locally-verified header, not the peer-supplied field.

---

### Proof of Concept

1. During fast sync, the downloader requests staking info for block hash `H` (header number `N`).
2. The malicious peer responds with a `P2PStakingInfo{BlockNum: N-86400, RewardAddrs: [attacker], KEFAddr: attacker, KIFAddr: attacker}`.
3. `queue.DeliverStakingInfos` accepts it (validate is a no-op).
4. `commitFastSyncData` calls `PutStakingInfoToDB(N-86400, attackerInfo)`.
5. `GetStakingInfo(N-86400)` now returns the attacker-supplied info from DB, bypassing state.
6. Block rewards for epoch `N-86400` are distributed to attacker addresses.
