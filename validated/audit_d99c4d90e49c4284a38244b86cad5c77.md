### Title
Membership webhook signature is verified against `repository.owner.login` but the `Team` row is scoped by the independent `organization.login` field, allowing a payload verified under one org's (weak/nil) secret to write a `Team` under an unrelated org - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` picks `params.dig('repository','owner','login')` to select which org's `GitHubApp`/`webhook_secret` is used for `verify_signature`, while `MembershipHandler#find_or_create_team!` scopes the created `Team.organization` from the independent `organization.login` field of the same body. Because these two attacker-controlled JSON fields are never cross-checked, a payload that verifies against one (weakly/unauthenticated) organization can create a `Team` row attributed to a completely different organization.

### Finding Description
The broken binding: `repository_owner` (used to select the signing secret) should equal `organization.login` (used to scope the mutated `Team`), i.e. `params['repository']['owner']['login'] == params['organization']['login']`. Nothing in the code enforces this.

- `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and this value alone selects the `GitHubApp` instance (`Shipit.github(organization: repository_owner)`) used in `verify_signature`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/nil: `return true unless webhook_secret`. [3](#0-2) 
- `MembershipHandler#find_or_create_team!` builds/looks up a `Team` keyed on `params.team.id` and sets `team.organization = params.organization.login` on creation — a value taken from a different, independently-controlled part of the same JSON body. [4](#0-3) 

Exploit flow: In a multi-org Shipit deployment (`secrets.github` keyed by multiple orgs), assume org `weak-org` is misconfigured with no `webhook_secret` while org `victim-org` is properly secured. The attacker (who controls no privileged repo/org, only sends an arbitrary HTTP POST to `/webhooks`) sends a `membership` event body with `repository.owner.login = "weak-org"` and `organization.login = "victim-org"`. `repository_owner` resolves to `weak-org`, `Shipit.github(organization: "weak-org")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header. `drop_unhandled_event`/`check_if_ping` do not block a `membership` event since a handler is registered. The `MembershipHandler` then executes and, if no `Team` yet exists for the given `team.id`, creates a new `Team` with `organization = "victim-org"`, and adds an attacker-chosen `member` (`User.find_or_create_by_login!(params.member.login)`) to it via `team.add_member(member)`.

Existing guards do not prevent this: `verify_signature` only proves the body was accepted for whatever org `repository_owner` names — it does not validate that other fields inside the same body (`organization.login`) also belong to that org. The `ExplicitParameters` schema for `MembershipHandler` only requires the presence/type of `organization.login`, `team.*`, and `member.login`; it performs no cross-field consistency check.

### Impact Explanation
An attacker with no privileges on `victim-org` can cause Shipit to create/populate a `Team` row (and associated `Membership`) tagged as belonging to `victim-org`, provided (a) `victim-org` isn't already tracked with the same `team.id`, and (b) some other org configured in Shipit (`weak-org`) has a missing/blank `webhook_secret`. This is a cross-tenant write: a payload nominally verified for one org mutates another org's `Team`/`Membership` state. If `Team` membership feeds into `Shipit.github_teams`-based authorization (`oauth_teams`), this could escalate into unauthorized access to stacks gated by `victim-org` team membership — matching the "escalation into `Shipit.github_teams` authorization" / cross-tenant mutation impact category. Repeatable for any `team.id` not already claimed under `victim-org`, and for any org named in `organization.login`.

### Likelihood Explanation
This requires a genuine operator misconfiguration precondition: at least one org configured in `secrets.github` with a blank/nil `webhook_secret`, coexisting with other properly-secured orgs (multi-org deployment). This is not a default/guaranteed state — a single-org deployment with `github_default_organization` nil uses one global secret for everything, in which case a missing secret disables verification globally (a different, already-known issue) rather than enabling cross-tenant confusion. The cross-tenant scenario specifically needs multi-org config with inconsistent secret hygiene across orgs. Given that precondition, attacker cost is trivial (one unauthenticated HTTP POST, no GitHub access needed at all).

### Recommendation
Cross-validate that `organization.login` (and any other embedded org/repo identifiers) matches `repository_owner`/the org whose secret validated the signature before trusting body-supplied scoping fields in handlers. Additionally, do not allow `verify_webhook_signature` to silently return `true` for orgs with a blank secret in multi-org configurations; require an explicit secret per configured org or fail closed.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Stub `Shipit.github(organization: 'weak-org')` to return a `GitHubApp` whose `webhook_secret` is nil (or stub `verify_webhook_signature` to return `true` unconditionally to simulate the nil-secret path), and leave `Shipit.github(organization: 'victim-org')` untouched/unstubbed to show it's never consulted.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
   `{ "action": "added", "team": { "id": 999, "name": "T", "slug": "t", "url": "http://x" }, "organization": { "login": "victim-org" }, "member": { "login": "attacker-controlled" }, "repository": { "owner": { "login": "weak-org" } } }`
3. Assert response is `:ok` (not `:unprocessable_entity`), proving `verify_signature` passed using `weak-org`'s config.
4. Assert `Team.find_by(github_id: 999).organization == "victim-org"`, i.e. `repository.owner.login` ("weak-org", used for verification) != `Team#organization` ("victim-org", the value actually persisted) — demonstrating the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
