### Title
Direct token transfers to the pool become unrecoverable donations - (File: contracts/pool/src/lib.rs)

### Summary
An unprivileged user who transfers a listed token directly to the pool address receives no supply shares, debt repayment, cash-book credit, or refund, and has no public path to recover the transfer. This is a Medium-severity user-funds-loss issue.

### Finding Description
The pool treats token custody and its accounting book separately. Supply credits the caller-specified `amount` to `cash`, but the controller first measures only the balance increase produced by the current `caller -> pool` transfer. [1](#0-0) [2](#0-1) 

`transfer_amount_measured` snapshots the pool balance before the transfer and returns `post - pre`, so a token sent before calling `supply`, `repay`, or `recapitalize` is included in `pre` and is excluded from the credited amount. [3](#0-2) 

The same pattern applies to debt repayment: the controller measures a new `payer -> pool` transfer and passes only that receipt to the pool. [4](#0-3)  Recapitalization likewise measures a fresh inbound transfer before invoking the pool. [5](#0-4) 

A direct transfer therefore increases only `token.balance(pool)`, not market `cash`, user supply shares, or debt repayment. Pool mutators that can transfer tokens out—`borrow`, `withdraw`, `repay`, `recapitalize`, `flash_loan`, `create_strategy`, and `claim_revenue`—are owner-only and driven by controller accounting rather than donor claims. [6](#0-5) [7](#0-6)  `transfer_out` sends assets to an operation-selected recipient and does not provide a donor recovery path. [8](#0-7) 

### Impact Explanation
The sender permanently loses control of the donated tokens. They may remain as unbooked pool balance or later fund withdrawals, refunds, borrows, or revenue payments for other parties, but the sender has no shares, credit, or authentication-based claim through the public ABI. This directly maps the reported bug class: sending an asset to the protocol contract instead of invoking the intended operation forfeits the funds.

### Likelihood Explanation
Exploitation requires no attacker action, but loss requires a user or integration to call the token contract directly instead of using a controller entrypoint. The pool address is publicly discoverable through `get_pool_address`, and prefunding a contract before a call is a plausible integration mistake. Because the mistake is irreversible and affects the full transferred amount, this is appropriately Medium severity.

### Recommendation
Add an explicit governance-controlled rescue or sweep mechanism for unbooked balances, bounded by the physical token balance minus the sum of booked `cash` across every market sharing that token. Until such accounting exists, prominently expose this behavior and ensure clients always route deposits and repayments through the controller rather than transferring directly to the pool.

### Proof of Concept
Let `asset` be a listed token, `pool` the deployed pool address, and `user` an unprivileged token holder:

```rust
let amount = 1_000_000;
let token = token::Client::new(&env, &asset);

let reserves_before = pool_client.get_reserves(&hub_asset);
let pool_before = token.balance(&pool);

// Direct token-contract call; no controller entrypoint is invoked.
token.transfer(&user, &pool, &amount);

assert_eq!(token.balance(&pool), pool_before + amount);
assert_eq!(pool_client.get_reserves(&hub_asset), reserves_before);
```

If the user then calls `controller.supply(user, account_id, spoke_id, [(hub_asset, amount)])`, `transfer_amount_measured` uses the already-increased pool balance as `pre`, pulls another `amount`, and credits only that second receipt. [1](#0-0)  The original `amount` remains unbooked and cannot be reclaimed by the user through a public pool endpoint because the outbound operations are restricted to the controller owner. [6](#0-5)
