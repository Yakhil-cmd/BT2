### Title
Unhandled exception in dry-run AA trigger execution crashes the entire node process — ([File: network.js])

### Summary
`ocore`'s `bDryRunNewTriggers` feature (analogous to the "high-performance mode" mentioned in the ManageSieve advisory) executes AA trigger logic synchronously inside the unit-validation success path for *every incoming unit that pays a known AA address*, without any surrounding `try/catch`. Any exception thrown deep inside AA-trigger execution for a still-unstable, attacker-crafted unit is not caught locally; it propagates as an uncaught exception and is handled by the node's global `process.on('uncaughtException')` handler, which deliberately re-throws to crash the whole Node.js process. This kills every connection the node is currently serving — the same "all connections handled by the same process are terminated" behavior described in the ALPINE-CVE-2026-33605 advisory for dovecot's high-performance mode.

### Finding Description
When a node processes an incoming unit and validation succeeds, `handleJoint()`'s `ifOk` callback runs a "dry run" of any AA trigger the unit contains, *before* the unit is even saved, specifically so a crash "happens now" instead of later: [1](#0-0) 

This block is reached for any unit posted by an unprivileged party — as long as it has a payment output to an address that `validateAATrigger()` recognizes as a registered AA (a purely structural, attacker-controllable condition checked earlier in the same validation pass): [2](#0-1) 

`aa_composer.getTrigger()` and `aa_composer.dryRunPrimaryAATrigger()` are called with **no try/catch**. Both functions, and the formula-evaluation machinery they invoke, contain numerous `throw Error(...)` statements that are meant to guard "should never happen" invariants but are reachable through attacker-influenced trigger/AA-definition combinations (e.g. `getTrigger()`'s `throw Error("no outputs to " + receiving_address)`, `handleTrigger()`'s `throw Error("assocBalances and bAir do not match")` / `throw Error('bad AA definition ' + arrDefinition)` / `throw Error("base AA not found: " + template.base_aa)`, and `AA not found` and `AA not found?` throws in `estimatePrimaryAATrigger`/`updateInitialAABalances`): [3](#0-2) [4](#0-3) [5](#0-4) 

Because this code executes inside an `async` callback (`ifOk: async function(...)`), any synchronous `throw` becomes an unhandled promise rejection / uncaught exception, which is picked up by the process-wide handler in `network.js`: [6](#0-5) 

The comment on line 4530-4543, `throw err; // crash the process to avoid ending up in an inconsistent state`, shows this is an intentional, blanket kill-the-process policy — exactly mirroring the advisory's "high-performance mode" behavior where a crash in one connection's handling brings down the whole process serving multiple clients, rather than being isolated ("high-security mode" would only drop the single connection).

### Impact Explanation
A single unprivileged unit poster can craft a unit that:
1. Pays a small amount to a real, already-defined AA address (satisfying `count_primary_aa_triggers`), and
2. Is otherwise unit-valid so it passes `validation.js`'s checks and reaches `ifOk`.

If the referenced AA's definition/state, combined with the trigger content, drives execution into one of the un-caught `throw Error(...)` invariant checks in `aa_composer.js`/`formula/evaluation.js`, the entire node process crashes via the global `uncaughtException` handler. This is not limited to the attacker's own connection: **every** peer, light client and hub-connected wallet served by that process is disconnected simultaneously, and the node stops validating/relaying/confirming any units until it is restarted — satisfying the "network unable to confirm new units" impact criterion for the affected node. The attack is repeatable at low cost (one small transaction per crash), producing sustained denial of service, analogous to the advisory's "repeating the attack can cause denial of service."

### Likelihood Explanation
The feature is gated behind `conf.bDryRunNewTriggers`, so it is not universally enabled on all nodes by default — mirroring the advisory's own severity split between "community" and "Pro/high-performance" configurations. On nodes/hubs that do enable it (as the code comment implies is intentional for fail-fast behavior), the trigger condition (paying an existing AA) is trivially reachable by any unprivileged sender who can construct and broadcast a standard payment unit; no special network position, peer trust, or authentication is required.

### Recommendation
Wrap the dry-run trigger execution block in `network.js` (`aa_composer.getTrigger` / `aa_composer.dryRunPrimaryAATrigger` calls) in a `try/catch`, treat any thrown/rejected error as a normal unit/joint validation failure (or simply skip the dry run and log), and avoid using process-crashing invariant `throw`s for conditions that can be influenced by external, unvalidated trigger/AA-definition data. Also audit `aa_composer.js` and `formula/evaluation.js` for `throw Error(...)` statements reachable from trigger execution paths and convert genuinely attacker-reachable ones into regular bounce/error callbacks instead of process-level throws.

### Proof of Concept
Conceptual PoC (exact minimal formula/definition combination reaching one of the internal invariant throws was not fully enumerated within the scope of this analysis — this is a structural/architectural finding, not a fully worked exploit):
1. Enable/target a node running with `bDryRunNewTriggers` enabled.
2. Define (or reuse an existing) AA whose getters/state formulas, when evaluated against attacker-controlled `trigger.data`/`params`, drive `handleTrigger()`/`evaluateAA()` into one of the un-guarded `throw Error(...)` paths identified above (e.g. a `base_aa` template pointing to a not-yet-visible base AA definition to hit `"base AA not found"`, or manipulating outputs so `getTrigger()`'s post-filter output map becomes empty to hit `"no outputs to " + receiving_address`).
3. Post a small payment unit to that AA address from an unprivileged wallet.
4. Observe the targeted node's process crash via the `uncaughtException` handler in `network.js`, dropping all its current connections. [1](#0-0) [6](#0-5)
