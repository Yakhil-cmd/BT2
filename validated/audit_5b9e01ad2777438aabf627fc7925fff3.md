### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook is authenticated only against the organization/repository named in the payload's `repository.owner.login` field, but the handler that processes the event resolves the target `Commit` purely by SHA, with no check that the commit actually belongs to the repository that was authenticated. This breaks the binding "organization that authenticated == repository that is written," allowing an attacker who controls a legitimately-configured (or unconfigured/secret-less) organization's webhook to forge a passing CI status on a commit belonging to an unrelated, victim stack/repository, which can unblock and trigger an unauthorized deploy.

### Finding Description
Webhook authenticity is checked in `Shipit::WebhooksController#verify_signature`, which derives the organization solely from the request payload (`repository_owner`, i.e. `params.dig('repository','owner','login')`) and validates the HMAC using that organization's `webhook_secret` via `Shipit.github(organization: repository_owner).verify_webhook_signature`: [1](#0-0) 

Its `process` method does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This queries `Commit` **globally by SHA across all stacks/repositories** — it never calls `stacks` (which is scoped by `payload.dig('repository','full_name')`, as used correctly by `PushHandler` and `CheckSuiteHandler` via `Handler#stacks`/`Handler#repository_name`): [2](#0-1) [3](#0-2) [4](#0-3) 

Because commit SHAs are 40-hex-character git hashes that are often identical across forks/mirrors, and because an attacker can also freely fabricate the `sha` field in the JSON body they send (the signature only proves the whole payload came from *their* organization, not that the `sha` is truthful), an attacker who runs their own GitHub App installation and repository under Shipit (or any org with `webhook_secret: nil`, which makes `verify_webhook_signature` return `true` unconditionally — see `lib/shipit/github_app.rb`, `verify_webhook_signature`) can send a `status` webhook whose `sha` matches a real commit belonging to a completely different, unrelated stack, and have `StatusHandler` write a fabricated passing status to that victim commit via `commit.create_status_from_github!` / `add_status`: [5](#0-4) [6](#0-5) 

The equality that should hold is:
`organization authenticated by verify_signature == repository owning the Commit row that gets mutated`

`StatusHandler` breaks this by never re-deriving or checking the owning repository/stack of the matched `Commit` against the payload's `repository`/`repository_owner`.

### Impact Explanation
Commit statuses directly gate deployability: `Commit#deployable?` requires `success?` (derived from `statuses`) unless CI is ignored, and `schedule_continuous_delivery` triggers `ContinuousDeliveryJob` once a commit becomes `deployable?`: [7](#0-6) [8](#0-7) 

An attacker able to inject a forged "success" status for a victim commit can therefore make an otherwise CI-blocked commit `deployable?`, and — combined with `continuous_deployment` — cause an **unauthorized deploy** on a stack the attacker has no legitimate access to. This satisfies the Critical-tier "unauthorized deploy" impact bar, achieved purely through a cross-repository write that the webhook signature check was supposed to prevent.

### Likelihood Explanation
The attacker only needs the ability to send an authenticated `status` webhook for *some* organization tracked by the Shipit instance — this can be their own low-privilege repository/org (or any org configured without a `webhook_secret`, which is explicitly supported and bypasses verification entirely). No access to the victim's GitHub organization, repository, or Shipit session is required. The only additional requirement is guessing/knowing a target commit SHA belonging to the victim stack (visible on the public Shipit UI or via GitHub itself), which is not a meaningful barrier.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records by content rather than repository) to the repository authenticated for the request, e.g. restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.joins(:stack).where(stacks: { repository_id: repository.id }, sha: params.sha)`, mirroring the pattern already used correctly in `Handler#stacks` for `PushHandler` and `CheckSuiteHandler`.

### Proof of Concept
1. Attacker registers/owns organization `attacker-org` with its own GitHub App installed on the shared Shipit instance (or targets any configured org with `webhook_secret: nil`).
2. Attacker discovers a commit SHA `abc123...` belonging to victim stack `victim-org/victim-repo` (e.g. from the public Shipit stack page).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `attacker-org`'s webhook secret (or none, if the org is unconfigured), and body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"},
  "sha": "abc123...",
  "state": "success",
  "context": "ci/forged",
  "target_url": "https://example.com"
}
```
4. `verify_signature` in `Shipit::WebhooksController` validates successfully against `attacker-org`.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the victim's commit (belonging to `victim-org/victim-repo`), and calls `create_status_from_github!`, writing a forged "success" status to it.
6. If `victim-org/victim-repo`'s stack has `continuous_deployment` enabled and this was the last required status, `schedule_continuous_delivery` fires and the commit is deployed without any legitimate CI or authorization from the victim organization.

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      end
