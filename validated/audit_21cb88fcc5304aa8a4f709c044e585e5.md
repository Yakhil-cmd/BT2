## Title
Webhook signature verification is keyed on `repository.owner.login` while all event handlers act on `repository.full_name` — cross-organization/cross-repository forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook against based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Repository`/`Stack` to act on using a *different* field of the very same JSON body: `payload.dig('repository','full_name')`. Because these two fields are never cross-checked, a party who legitimately knows the `webhook_secret` for one configured GitHub organization in a multi-org Shipit deployment can forge a signed webhook whose `owner.login` matches their own org (so signature verification passes with their own secret) while `full_name` names a repository belonging to a *different* organization configured on the same instance. The handler will act on the victim repository's stacks despite the signature only proving authenticity for the attacker's own organization.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This picks a `GitHubApp` (and hence a `webhook_secret`) solely from `repository.owner.login`/`organization.login`, and validates only that the raw request body matches the HMAC computed with that org's secret — it does not bind the signature to any other field of the payload, in particular not to `repository.full_name`.

Every downstream handler, however, resolves which `Repository`/`Stack` to mutate using `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

For example, `PushHandler#process` triggers `stack.sync_github(expected_head_sha: ...)` for every stack matching `repository_name`'s branch [3](#0-2) , `CheckSuiteHandler#process` schedules a check-run refresh for commits of `stacks` matching `full_name` [4](#0-3) , and `PullRequest::ClosedHandler` looks up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` independently to archive a review stack [5](#0-4) .

**The binding that should hold:**
`organization that authenticated the signature (repository.owner.login → webhook_secret)` == `organization that owns the repository being acted on (repository.full_name)`

**Before the attack:** In the legitimate flow, GitHub itself generates the payload, so `owner.login` and `full_name`'s namespace always match, and the signature computed with that org's `webhook_secret` legitimately proves the event originated from that org's repo.

**After the attack:** An attacker who administers/controls org `attacker-org` (already configured with its own `webhook_secret` in `Shipit.github`, see the multi-org config shape in `test/dummy/config/secrets_double_github_app.yml`/`config/secrets.development.shopify.yml`) can directly POST to `/webhooks` with:
- `X-Hub-Signature` = HMAC-SHA1(`attacker-org`'s webhook_secret, raw_body)
- `repository.owner.login = "attacker-org"` (drives which secret is used to verify)
- `repository.full_name = "victim-org/victim-repo"` (drives which `Repository`/`Stack` is mutated)

`verify_signature` succeeds because the body genuinely matches the HMAC for `attacker-org`. The handler then acts on `victim-org/victim-repo`'s stacks.

### Impact Explanation
This breaks the trust boundary that a webhook can be trusted as originating from the organization owning the repository it claims to describe. Concrete unauthorized effects on a victim stack the attacker has no legitimate relationship to:
- `push` events can force `GithubSyncJob`/`sync_github` to run against victim stacks with an attacker-chosen `expected_head_sha`, influencing what Shipit believes is the head of a branch.
- `check_suite`/`status` events can be forged to inject arbitrary commit statuses on victim commits via `Commit#create_status_from_github!`, which in turn calls `add_status`, which can flip a commit's deployable state and call `stack.schedule_merges` [6](#0-5) , feeding into `ProcessMergeRequestsJob`'s automatic merge queue (`merge_request.merge!` calls `stack.github_api.merge_pull_request`) [7](#0-6) [8](#0-7) . Forging a passing CI status for a victim's PR can therefore contribute to an unauthorized merge in that victim's repository — matching the "unauthorized deploy, rollback, or merge" Critical-impact criterion.
- `pull_request` closed events can force `review_stack.archive!` on victim review stacks.

This qualifies as a cross-repository-write class issue since the org that authenticated (`attacker-org`) does not equal the org whose repository is written (`victim-org`).

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for at least one organization configured in the same multi-tenant Shipit instance (i.e., they administer that org's GitHub App/webhook config) — this is not "no credential" as it requires control of *some* org's secret, but it is *not* the victim org's secret, and Shipit's documented design supports hosting multiple independent GitHub orgs off a single instance (see `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`). Any organization admin onboarded to a shared Shipit deployment can attack any other organization's repositories on that same instance without further privileges, session, or API token. This is a realistic misuse scenario for any Shipit deployment serving more than one GitHub organization.

### Recommendation
After verifying the HMAC signature in `WebhooksController#verify_signature`, cross-validate that the organization derived from `repository.full_name` (i.e., its owner segment) matches `repository_owner`/`organization.login` used to select the `webhook_secret`. Reject the webhook (422) if they diverge. Ideally, bind the signature check itself to the specific repository/org pairing rather than relying on an implicit assumption that GitHub always sends consistent payloads.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S1`) and `victim-org` (secret `S2`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Have a `victim-org/victim-repo` stack already tracked by Shipit with an open, otherwise-unmergeable PR.
3. As an admin of `attacker-org` (who legitimately knows `S1`), craft a `push` (or `status`) JSON payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim PR head sha>",
  "state": "success",
  ...
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S1, raw_body)>` and POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb`) selects `Shipit.github(organization: "attacker-org")` and validates successfully against `S1`.
6. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb`) creates a forged `success` status on the victim's commit purely from `params.sha`, with no organization ownership check, potentially unblocking that PR's merge queue processing in `victim-org`.
