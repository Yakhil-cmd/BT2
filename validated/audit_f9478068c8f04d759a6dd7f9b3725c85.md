### Title
Cross-repository Status forgery via unscoped SHA lookup allows unauthorized CI-passed marking and continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no verification that the `sha` belongs to the repository that produced and signed the webhook. An attacker who controls any Shipit-tracked repository (or can produce a commit whose sha collides/matches a victim commit's sha, e.g. by replicating identical commit content into their own history) can send a validly-signed webhook from their own GitHub organization that creates a `success` `Status` row on a victim commit belonging to a completely different repository/stack.

### Finding Description
Binding claimed by the question: `UndeployedCommit#deploy_state == 'allowed'` should hold **iff** all `Status` rows on the commit trace back to webhooks verified for the victim repository itself, i.e. `status.repository_owner == commit.stack.repository.owner && status.repository_full_name == commit.stack.repo_name`.

This binding is broken in code. `StatusHandler#process`: [1](#0-0) 
does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global, unscoped** lookup across every stack/repository tracked by the Shipit install. This is inconsistent with sibling handlers such as `CheckSuiteHandler`, which explicitly scope to `Repository.from_github_repo_name(repository_name)` before touching any commit: [2](#0-1) [3](#0-2) 

`WebhooksController#verify_signature` only proves that the request signature matches the secret of the GitHub organization named in `payload['repository']['owner']['login']` — i.e. it authenticates *who sent the webhook*, not *which commit/repository the sha actually belongs to*: [4](#0-3) 

Exploit flow: the attacker owns (or controls webhooks for) some GitHub repository/organization tracked by Shipit. They obtain a commit object with an identical sha to the victim's undeployed commit (trivial if they replicate the exact same tree/parent/author/committer/message/timestamps into their own history — this yields a bit-for-bit identical commit and therefore an identical sha, not a cryptographic collision) and fire a `status` event for that sha with `state: success` from their own repository. The webhook is signed with the attacker's own valid organization secret, so `verify_signature` passes. `StatusHandler` then finds **every** `Commit` row across the DB with that sha — including the victim's — and calls `create_status_from_github!` on it, writing a `Status` row keyed to the **victim's** `stack_id`: [5](#0-4) [6](#0-5) 

Downstream, `Commit#deployable?` and `#status` aggregate all `statuses` regardless of provenance: [7](#0-6) [8](#0-7) 
so the forged `success` status makes the victim commit `deployable?`. `UndeployedCommit#deploy_state` then reports `'allowed'`: [9](#0-8) 

More severely, `Status#after_commit :schedule_continuous_delivery` calls `commit.schedule_continuous_delivery`, which — if the victim stack has `continuous_deployment` enabled and is otherwise deployable — enqueues `ContinuousDeliveryJob` **without any human click at all**: [10](#0-9) [11](#0-10) 

No existing guard prevents this: `verify_signature` checks only the sender org, not the sha-to-repository binding; `ExplicitParameters` in `StatusHandler` validates types only (`sha`, `state`, etc.), not repository ownership; `Repository` format/`Stack` validators don't apply to `Status` creation at all.

### Impact Explanation
This allows a payload received for one (attacker-controlled) repository to mutate a *different* repository's stack/commit state — writing a `Status` row that makes `Commit#deployable?`/`UndeployedCommit#deploy_state` return `'allowed'` for a commit that never had valid CI in its own repository. When the victim stack has `continuous_deployment` enabled, this results in an **automated, unauthorized deploy** with no human interaction, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy." Even without continuous deployment, it produces a false "CI passed / allowed" UI state that a human operator would rely on before manually deploying. This is repeatable against any stack/commit whose sha the attacker can reproduce, and is not limited to a single tenant — any repository tracked by the same Shipit instance is affected because `Commit.where(sha:)` has no tenant boundary.

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository (their own, or any repo) wired to send `status` webhooks to the shared Shipit instance (this is standard/expected setup for any tracked repo, no special privilege needed on the victim's side), and the ability to reproduce a commit with an identical sha to a target commit. This is feasible for the common case of shared/forked history: e.g. an attacker forks a public repo, and any commit already merged into the base repo appears identically in the fork's history with the same sha; pushing/re-notifying status for that sha from the fork's own CI/webhook satisfies this exactly — no hash preimage attack needed. Attacker cost is low: no secrets, no privileged role, just ownership of a tracked repository and standard GitHub CI/webhook usage.

### Recommendation
Scope `StatusHandler#process` (and `Status.replicate_from_github!`) by the repository named in the payload, mirroring `CheckSuiteHandler`/`Handler#stacks`: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, restrict the `Commit` lookup to `repository.stacks.commits.where(sha: params.sha)` (or equivalently verify `commit.stack.repository == repository` before calling `create_status_from_github!`), and drop/ignore statuses for shas that don't belong to the reporting repository's own commits.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, conceptual — file itself is out of scope for delivery but describes the exact assertion):
```ruby
victim_stack = shipit_stacks(:shipit)              # repo: shopify/shipit-engine
attacker_stack = shipit_stacks(:cyclimse)           # repo: some-other/other-repo, different tenant

victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)  # no statuses -> not deployable

# Attacker's payload references the SAME sha but repository = attacker's own repo
payload = {
  "sha" => victim_commit.sha,
  "state" => "success",
  "context" => "ci/attacker",
  "repository" => { "full_name" => attacker_stack.repository.github_repo_name, "owner" => { "login" => attacker_stack.repository.owner } }
}

before = UndeployedCommit.new(victim_commit, index: 0).deploy_state
assert_not_equal 'allowed', before

Shipit::Webhooks::Handlers::StatusHandler.call(payload)  # simulates a validly-signed webhook from attacker's own org

victim_commit.reload
after = UndeployedCommit.new(victim_commit, index: 0).deploy_state
assert_equal 'allowed', after   # BUG: forged cross-repo status made victim commit deployable
assert_equal attacker_stack.id, nil # sanity: no attacker-stack status should exist on victim_commit
refute_equal victim_stack.id, Shipit::Status.where(commit: victim_commit).last.stack_id rescue nil
```
The core assertion is: `UndeployedCommit.new(victim_commit, index: 0).deploy_state` transitions to `'allowed'` purely from calling `StatusHandler.call` with a payload whose `repository.full_name` differs from the victim commit's actual `stack.repository.github_repo_name`, proving the binding "deploy_state == allowed only if all Status rows trace back to the victim repository's own verified webhooks" is violated by `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`.
