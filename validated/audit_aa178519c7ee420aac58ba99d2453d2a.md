### Title
Fork-controlled `PATH` via `machine.environment` in `shipit.yml` overrides safe `PATH` and hijacks `ruby`/`bundle` dependency step execution - (File: `lib/shipit/command.rb`)

### Summary
`Command#unbundled_env` builds the child process environment by merging the caller-supplied `@env` hash *after* setting a safe, hardcoded `PATH`, and `TaskCommands#env` merges `deploy_spec.machine_env` — which is `config('machine', 'environment')` read verbatim from the `shipit.yml` on the review-stack's checked-out branch — into that same hash with no whitelist filtering. A PR author who owns the fork branch of an `allow_with_label` review stack can therefore set `machine.environment.PATH` in their `shipit.yml`, prepend an attacker-controlled directory, and have the bare `bundle`/`ruby` invocations in `TaskCommands#install_dependencies` resolve to an attacker binary, achieving remote code execution on the Shipit host.

### Finding Description
The broken binding is:

`Command#unbundled_env`'s resulting `PATH` == `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` (the safe path)

but the actual code produces:

`Command#unbundled_env`'s resulting `PATH` == attacker's `PATH` value, because the untrusted hash is merged last. [1](#0-0) 

```
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end
```

`@env.stringify_keys` is merged in *last*, so any `PATH` key present in `@env` completely overwrites the safe `PATH` that was just constructed.

`@env` for a task/dependency-install step comes from `TaskCommands#env`: [2](#0-1) 

which merges `deploy_spec.machine_env` into the environment hash. `DeploySpec#machine_env` is: [3](#0-2) 

```
def machine_env
  config('machine', 'environment') || {}
end
```

This reads directly from the parsed `shipit.yml` config with **no whitelist/sanitization** — unlike `deploy_variables`/`rollback_variables`/`task variables`, which are all passed through `EnvironmentVariables#permit` (a strict allow-list, see `filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`). `machine_env` has no equivalent guard.

`TaskCommands#install_dependencies` builds the dependency-install `Command` objects using this same `env`: [4](#0-3) 

The dependency steps themselves are typically bare commands like `bundle install --jobs 4 --retry 2`, `bundle config set --local path ...`, etc., produced by `BundlerDiscovery#bundle_install`: [5](#0-4) 

Since these are unqualified executable names (`bundle`, `sed`, etc.), the child process (spawned via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` in `Command#start`) resolves them using the `PATH` in the environment hash passed to `PTY.spawn` — the attacker-controlled one.

**Exploit flow:**
1. Attacker forks the target repo, opens a PR from a branch they control, and — because the repository is configured with `provisioning_behavior = allow_with_label` — adds the configured provisioning label to their own PR (an action any PR author can perform on their own PR).
2. `OpenedHandler`/`LabeledHandler` create a `ReviewStack` whose `branch` is `params.pull_request.head.ref` — the attacker's fork branch: [6](#0-5) 
3. When the stack's tasks/deploys run, `DeploySpec::FileSystem` loads `shipit.yml` from that checked-out branch (attacker-controlled), including a `machine: { environment: { PATH: "/tmp/evil:$PATH" } }` entry plus a malicious `/tmp/evil/bundle` executable planted by an earlier `dependencies.pre` step or another mechanism reachable within the same fork.
4. `TaskCommands#install_dependencies` builds `Command.new('bundle install ...', env:, ...)` where `env['PATH']` is now attacker-controlled.
5. `Command#start` → `unbundled_env` merges this hostile `PATH` last, and `PTY.spawn` executes `/tmp/evil/bundle` instead of the real `bundle`, achieving code execution as the Shipit process user on the Shipit host.

Existing guards do not stop this: `EnvironmentVariables#permit` is never invoked on `machine_env` (only on deploy/rollback/task variables), and no repository/stack validation restricts the content of `machine.environment`.

### Impact Explanation
Full remote code execution on the Shipit deploy host under the identity of the Shipit worker process, triggered purely by content in a fork's `shipit.yml` combined with adding a label to the attacker's own PR. Because this executes in `Command#start`/`PTY.spawn`, it directly matches the "Critical - RCE on the deploy host via `Command`/`PTY.spawn`" impact category. The blast radius extends beyond the attacker's own repository: the compromised host process typically holds the app's `GITHUB_TOKEN`/GitHub App credentials and can act on other stacks/repositories managed by the same Shipit instance, and the attack is repeatable on demand (re-trigger by re-labeling or re-opening the PR).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior = allow_with_label` (a documented, supported, non-default-safe configuration) and a `provisioning_label_name` the attacker can apply to their own PR — labeling your own PR requires no special repo permission beyond opening the PR in many GitHub configurations, and even if label application is restricted, this is a config the maintainer explicitly designed to let unprivileged fork PRs provision review stacks. No secrets, sessions, or elevated GitHub permissions are required. The only artifact needed is control over the fork's `shipit.yml`, which the PR author fully controls.

### Recommendation
Sanitize `machine_env` in `DeploySpec#machine_env` (or in `TaskCommands#env`) by rejecting or filtering dangerous overrides such as `PATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GEM_HOME`, `GEM_PATH`, etc., or route `machine_env` through an allow-list mechanism similar to `EnvironmentVariables#permit`. Additionally, in `Command#unbundled_env`, force `PATH` to always be the last, non-overridable key (`.merge(@env.stringify_keys).merge('PATH' => safe_path)`), so that untrusted env cannot influence executable resolution regardless of source.

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (illustrative)
test "PATH from shipit.yml machine.environment overrides the safe PATH used for bundle/ruby dependency steps" do
  stack = shipit_stacks(:review_stack) # allow_with_label review stack
  task = shipit_deploys(:pending)      # or create a Task tied to `stack`
  commands = Shipit::TaskCommands.new(task)

  commands.stubs(:deploy_spec).returns(
    stub(
      dependencies_steps!: ['bundle install --some-args'],
      machine_env: { 'PATH' => '/tmp/evil:/usr/bin' },
      clear_working_directory?: true
    )
  )

  install_cmd = commands.install_dependencies.first

  # Binding under test: env['PATH'] should remain the safe Shipit-controlled path
  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"

  # BEFORE fix: attacker value wins
  assert_equal '/tmp/evil:/usr/bin', install_cmd.send(:unbundled_env)['PATH']
  refute_equal safe_path, install_cmd.send(:unbundled_env)['PATH']

  # EXPECTED (invariant that should hold, currently violated):
  # assert_equal safe_path, install_cmd.send(:unbundled_env)['PATH']
end
```
This test demonstrates that a `machine.environment.PATH` entry from `shipit.yml` reaches the process environment used by `PTY.spawn` for the `bundle install` dependency step, proving the safe `PATH` invariant is broken.
