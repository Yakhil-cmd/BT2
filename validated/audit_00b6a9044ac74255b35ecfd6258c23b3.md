The data race is real and demonstrable. Here is the precise analysis:

**Race anatomy in `RemoveVotesAfter`** (`kaiax/gov/headergov/impl/rewind.go`):

- Line 20: `for epochIdxIter, votes := range h.groupedVotes` — the range expression reads `h.groupedVotes` **without holding `h.mu`**.
- Lines 24–31: `h.mu.Lock()` is acquired only inside the inner conditional, and released with `h.mu.Unlock()` after each deletion — so the lock is **not held for the duration of the outer iteration**.

**Concurrent writer**: `AddVote` (`kaiax/gov/headergov/impl/execution.go`, lines 73–83) acquires `h.mu.Lock()` and writes to `h.groupedVotes` (both adding new epoch keys and writing inner map entries).

**Always-running concurrent caller**: The `migrate()` goroutine (`kaiax/gov/headergov/impl/init.go`, lines 151–177) is started unconditionally in `Start()` and loops calling `accumulateVotesInEpoch` → `AddVote`. It runs in the background throughout node operation, not just during block insertion.

**The race**: `migrate()` calls `AddVote` (writes `h.groupedVotes[epochIdx]` under lock) while `RemoveVotesAfter` is ranging over `h.groupedVotes` without the lock. This is a concurrent map read and map write — undefined behavior in Go, detectable by `-race`, and capable of triggering a runtime panic ("concurrent map read and map write") or silent map corruption.

**Secondary race within the loop**: Even if the initial range start is not concurrent, the lock is dropped between each inner-loop deletion (`h.mu.Unlock()` at line 31), so `AddVote` can interleave between deletions while the outer range is still in progress — a second race window.

### Title
Unsynchronized concurrent map iteration in `RemoveVotesAfter` races with `AddVote` / background `migrate()` goroutine, corrupting governance vote cache — (`kaiax/gov/headergov/impl/rewind.go`)

### Summary

`RemoveVotesAfter` iterates `h.groupedVotes` without holding `h.mu`, while the always-running `migrate()` background goroutine concurrently writes to the same map via `AddVote` under `h.mu`. This is a Go data race that can crash the node or silently corrupt the in-memory governance vote cache, causing incorrect vote tallying and wrong ratified parameter sets (block rewards, validator sets).

### Finding Description

In `RemoveVotesAfter`:

```go
// rewind.go:20 — range starts WITHOUT holding h.mu
for epochIdxIter, votes := range h.groupedVotes {
    for blockNumIter := range votes {
        if blockNumIter > blockNum {
            dirty = true
            h.mu.Lock()                                      // lock acquired INSIDE loop
            delete(h.groupedVotes[epochIdxIter], blockNumIter)
            if len(h.groupedVotes[epochIdxIter]) == 0 {
                delete(h.groupedVotes, epochIdxIter)
            }
            h.mu.Unlock()                                    // lock released between iterations
        }
    }
}
``` [1](#0-0) 

Concurrently, `AddVote` writes to `h.groupedVotes` under `h.mu`:

```go
func (h *headerGovModule) AddVote(blockNum uint64, vote headergov.VoteData) {
    h.mu.Lock()
    defer h.mu.Unlock()
    ...
    h.groupedVotes[epochIdx][blockNum] = vote
}
``` [2](#0-1) 

The `migrate()` goroutine is started unconditionally and calls `AddVote` in a loop throughout node lifetime: [3](#0-2) 

`RewindDelete` (called during any chain rewind/reorganization) calls `RemoveVotesAfter` directly: [4](#0-3) 

There are **two race windows**:
1. The `range h.groupedVotes` expression at line 20 reads the map header without the lock — concurrent with `AddVote`'s write.
2. Between each inner-loop iteration, `h.mu.Unlock()` is called at line 31, releasing the lock while the outer range is still in progress — `AddVote` can interleave here too.

`RemoveGovAfter` has the identical pattern for `h.governances`: [5](#0-4) 

### Impact Explanation

A Go data race on a map causes **undefined behavior**. The two concrete outcomes are:

1. **Runtime panic** ("concurrent map read and map write") — crashes the node, a persistent DoS until restart.
2. **Silent map corruption** — `h.groupedVotes` entries are lost, duplicated, or point to wrong inner maps. Since `groupedVotes` is the authoritative in-memory source for governance vote tallying (used by `VoteBlockNums`, `GetVotes`, and epoch-boundary ratification), corruption causes incorrect governance parameter ratification — wrong block-reward ratios, wrong validator-set parameters, or wrong staking thresholds — for the duration of the node's uptime.

### Likelihood Explanation

The `migrate()` goroutine is **always running** after `Start()` is called, continuously calling `AddVote`. A chain rewind (`RewindDelete`) is triggered by any reorganization or `SetHead` operation, which can be caused by receiving a longer competing chain over P2P — a permissionless network event. The two goroutines have no mutual exclusion at the call-site level, so the race window is open whenever a rewind coincides with an active migration scan (common during node startup on a long chain).

### Recommendation

Hold `h.mu` for the **entire duration** of the outer iteration in both `RemoveVotesAfter` and `RemoveGovAfter`. Acquire the lock once before the `range` loop and release it after:

```go
func (h *headerGovModule) RemoveVotesAfter(blockNum uint64) {
    h.mu.Lock()
    defer h.mu.Unlock()

    dirty := false
    for epochIdxIter, votes := range h.groupedVotes {
        for blockNumIter := range votes {
            if blockNumIter > blockNum {
                dirty = true
                delete(h.groupedVotes[epochIdxIter], blockNumIter)
                if len(h.groupedVotes[epochIdxIter]) == 0 {
                    delete(h.groupedVotes, epochIdxIter)
                }
            }
        }
    }

    if dirty {
        WriteVoteDataBlockNums(h.ChainKv, h.VoteBlockNums())
    }
}
```

Apply the same fix to `RemoveGovAfter`. Note that `VoteBlockNums()` and `GovBlockNums()` must not re-acquire `h.mu` if called under the lock (use unlocked internal helpers instead).

func (h *headerGovModule) migrate() {
	defer h.wg.Done()

	// Scan all epochs in the background including 0th epoch
	pBorder := ReadLowestVoteScannedEpochIdx(h.ChainKv)
	if pBorder == nil {
		logger.Crit("Unexpected nil: lowest vote scanned epoch index")
		return
	}

	border := *pBorder

	for int64(border) > 0 {
		if h.quit.Load() == 1 {
			return
		}

		time.Sleep(migrationThrottlingDelay)

		border -= 1
		h.accumulateVotesInEpoch(border)
	}

	if border == 0 {
		logger.Info("HeaderGovModule migrate complete")
	}
}
