### Title
Merkle proof verification lacks domain separation between leaf and internal-node hashing, enabling forged membership proofs - (File: merkle.js)

### Summary
`merkle.js`'s `getMerkleRoot`/`getMerkleProof`/`verifyMerkleProof` hash leaves and internal nodes with the exact same function and no distinguishing prefix/domain tag. This is the classic Merkle "second-preimage"/node-as-leaf weakness: anyone who knows two adjacent hash values from the tree (siblings that are routinely exposed by any valid proof) can present their concatenation as if it were the SHA-256 pre-image of a genuine leaf element, and successfully "prove" that fabricated element is a member of the committed set at a shallower depth in the tree. The verifier (`verifyMerkleProof`, used via `is_valid_merkle_proof` in oscript/AA formulas and `in merkle` address-definition conditions) cannot detect this because it has no way to tell node-hashes from leaf-hashes.

### Finding Description
`hash()` is a single undifferentiated function applied both to raw elements (leaves) and to concatenations of child hashes (internal nodes): [1](#0-0) 

`verifyMerkleProof` walks the supplied `siblings` starting from `hash(element)` and repeatedly re-hashes with each provided sibling, checking only that the final value equals `proof.root`; it never validates the claimed tree depth/leaf count against anything independent of the proof itself: [2](#0-1) 

Because leaf-hashing and node-hashing share the same primitive with no prefix/tag distinguishing them, if an attacker knows any two hash strings that are actual sibling hashes at some level of a real committed tree (`h_L`, `h_R`), they can set `element := h_L + h_R` (as UTF-8 string concatenation, exactly as `getMerkleRoot`/`getMerkleProof` do internally), because `hash(h_L + h_R)` is by construction identical to the tree's real internal-node hash at that position. The attacker then submits a proof that starts one level higher (using the *parent's* siblings, omitting the leaf-level pair), which will verify successfully — even though `h_L + h_R` was never a genuine leaf/data-feed element the tree's creator committed to.

Both `siblings`, `index`, and the target `element` are fully attacker-controlled inputs reachable from an unprivileged unit or AA trigger sender:
- `in merkle` address-definition condition deserializes an attacker-supplied `assocAuthentifiers[path]` string and checks it against `dataFeedExists` for the recovered root: [3](#0-2) 
- `is_valid_merkle_proof(element, proof)` in oscript/AA formula evaluation accepts an object or serialized string proof directly from trigger/message data and calls `merkle.verifyMerkleProof`: [4](#0-3) 

Any of the hash values needed to mount this attack (the siblings of a real tree) are ordinarily public — they are exactly the values published inside any legitimate proof for a real member of the set, or inside the definition/trigger data itself once someone uses the set once.

### Impact Explanation
Both `in merkle` and `is_valid_merkle_proof` are designed to gate authorization: `in merkle` is used as an authentifier condition inside address definitions (so it can gate spending from an address, exactly like `sig` or `hash`), and `is_valid_merkle_proof` is used inside AA/oscript logic to check set membership (e.g., whitelists, allow-lists, claim eligibility) before releasing funds or state changes. Because the verification primitive cannot distinguish a genuine leaf from a forged "leaf" built out of two known internal hashes, an attacker can satisfy either check for a value that the set's creator never actually included, without needing any private key or trust relationship with the data-feed oracle. Depending on how the checked "element" is subsequently used by the AA/definition (as an address, an amount, an authorization flag, etc.), this can lead to unauthorized spending from an address protected by an `in merkle` clause, or an AA incorrectly releasing funds/state based on a bogus membership claim — i.e., concrete unauthorized fund movement/loss, matching the "malicious prover convinces honest verifier of a false statement" pattern in the referenced Plonky2 advisory.

### Likelihood Explanation
The attacker only needs: (1) knowledge of any two adjacent hash values from a tree whose root is committed via a data feed (trivially obtained from any single legitimate proof that was ever published/shared, since proofs directly list sibling hashes), and (2) the ability to submit a unit or AA trigger with a crafted `element`/`proof` pair, which is exactly the capability of a normal unprivileged user. No control over the oracle, no cryptographic break of SHA-256 is required — this is a pure protocol/domain-separation defect, making exploitation realistic wherever `in merkle` or `is_valid_merkle_proof` gates something of value.

### Recommendation
Add domain separation between leaf hashing and internal-node hashing, e.g. `hash('leaf:' + str)` vs `hash('node:' + left + right)` (or a fixed-length prefix byte), in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js`. This must be a coordinated protocol change (old proofs/roots would need versioning) since it changes root/proof serialization semantics used on-chain via `in merkle` and `is_valid_merkle_proof`.

### Proof of Concept
1. A data-feed oracle builds a Merkle tree over legitimate elements `[e0, e1, e2, e3]` and publishes `root = getMerkleRoot([e0,e1,e2,e3])` as a data feed value.
2. Anyone requests/observes a legitimate proof for `e0`, revealing `sibling0 = hash(e1)` and `sibling1 = hash(hash(e2)+hash(e3))` (the two levels of siblings for a 4-leaf tree), per `getMerkleProof` in `merkle.js` lines 22-55.
3. Attacker computes `fake_element = hash(e0) + hash(e1)` (the actual left-child hash at the internal-node level) and crafts `proof = { index: 0, siblings: [sibling1], root }` — one level shallower than a real leaf proof.
4. Attacker submits `is_valid_merkle_proof(fake_element, proof)` in an AA trigger's formula, or uses the equivalent serialized form as the authentifier for an `in merkle` address-definition clause; `verifyMerkleProof` (merkle.js lines 84-102) computes `hash(fake_element + sibling1)` which equals the real `root`, so it returns `true`, even though `fake_element` was never one of `e0..e3`.
5. Whatever authorization/state action was gated on that membership check (fund release, whitelist admission, AA state transition) is incorrectly approved for the attacker's forged value.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
