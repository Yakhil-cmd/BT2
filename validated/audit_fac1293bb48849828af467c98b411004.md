### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, letting a stack-restricted token read state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to fetch the target stack directly by param, instead of going through the base controller's stack-scoped lookup. This breaks the binding between "the stack an `ApiClient` token is authorized for" and "the stack whose state the request actually touches," letting a token scoped to one stack read deploy/lock state of every stack in the installation.

### Finding Description
`Shipit::ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . `Api::BaseController` enforces this scope centrally: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` only from that pre-filtered relation: [2](#0-1) 

`Api::StacksController` follows this pattern correctly (`stacks.from_param!(params[:id])`) [3](#0-2) .

`Api::CCMenuController`, however, redefines `stack` to resolve directly against the global `Stack` relation, discarding the scoping entirely: [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [5](#0-4) ; it never checks whether the requested `stack_id` matches the token's bound `stack_id`. Because `CCMenuController#stack` calls `Stack.from_param!` instead of `stacks.from_param!`, that permission check is the only gate, and any `stack_id` in the request is honored.

**Binding broken:** `current_api_client.stack_id == requested_stack.id` (enforced everywhere else via `stacks`) is not enforced in `CCMenuController`; the token authorizes stack A, but the controller lets it touch stack B.

### Impact Explanation
An attacker holding a legitimate but narrowly-scoped `ApiClient` token (e.g., a CCMenu token auto-created by `CCMenuUrlController` and scoped with `permissions: %w[read:stack]` to a single stack, see [6](#0-5) ) can pass any other `stack_id` to `GET /api/stacks/:stack_id/ccmenu.xml` and get back that other stack's deploy/rollback status, lock state, and last build info — an unauthenticated read of stack state belonging to repositories the token was never meant to see. This matches the "unauthenticated read of stack state" High-impact bucket: the token only proves possession of a read-scoped credential for stack A, but the response discloses stack B's deployment activity/lock reason/author across the whole Shipit installation.

### Likelihood Explanation
High likelihood: exploitation requires only a valid stack-scoped `ApiClient` token (which is intentionally distributed to lower-privileged consumers such as CI dashboards/CCMenu clients) and a single unauthenticated GET request with a different `stack_id` — no session, no GitHub credentials, no privileged account needed beyond the token itself.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation, matching `BaseController`/`StacksController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and remove the private override entirely so the inherited, scope-respecting implementation is used.

### Proof of Concept
1. Create (or observe) a stack-scoped `ApiClient` bound to `stack_a` with `permissions: ['read:stack']` (as done automatically by `CCMenuUrlController#client`) [6](#0-5) .
2. Using that client's `authentication_token`, issue `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b` is any other stack in the installation.
3. `authenticate_api_client` succeeds because the token is valid [7](#0-6) ; `require_permission :read, :stack` succeeds because the client has `read:stack` [5](#0-4) ; `stack` resolves `stack_b` directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction [8](#0-7) .
4. Response renders `stack_b`'s CCMenu XML (name, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl) even though the token was only ever authorized to read `stack_a`.
