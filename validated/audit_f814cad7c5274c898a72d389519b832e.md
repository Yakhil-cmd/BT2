### Title
Webhook signature verification keys on `repository.owner.login` while all handlers (including `LabeledHandler`) resolve the mutated repository/stack from `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret used to verify `X-Hub-Signature`) using `repository_owner`, which is derived solely from `params.dig('repository','owner','login')`. Every downstream handler, including `LabeledHandler`, resolves the actual `Repository`/`Stack` to mutate from the independent `repository.full_name` field. Because nothing binds these two fields together, and because `GitHubApp#verify_webhook_signature` trivially returns `true` when an org has no `webhook_secret` configured, an attacker can pick an org with no secret for `owner.login` while pointing `full_name` at a repository belonging to a different, secret-protected org.

### Finding Description
The broken binding is: `repository_owner (params.dig('repository','owner','login'))` should equal the owner encoded in `repository.full_name.split('/').first`, but the code never enforces this equality.

- `app/controllers/shipit/webhooks_controller.rb:24-30` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` reads only `repository.owner.login` (or `organization.login`), never `repository.full_name`. [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when the selected org's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
- `LabeledHandler#repository` resolves the mutated `Repository` from `params.repository.full_name`, completely independent of `repository.owner.login`. [4](#0-3) 
- The resolved review stack, and the `archive!`/`unarchive!` calls that follow, operate on `repository.review_stacks`, scoped by the repository resolved from `full_name`. [5](#0-4) [6](#0-5) 

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body `action=labeled`, `repository.owner.login = "org-with-no-secret"`, `repository.full_name = "victim-org/victim-repo"`. The controller picks `Shipit.github(organization: "org-with-no-secret")`; if that org is configured with `webhook_secret` blank, signature verification passes unconditionally regardless of the actual `X-Hub-Signature` value or absence thereof. Control then flows into `LabeledHandler`, which resolves `victim-org/victim-repo`'s `Repository` and its `review_stacks`, and calls `stack.archive!`/`stack.unarchive!` based on the (also attacker-controlled) pull-request labels — a mutation on a repository/stack that never validated a signature tied to its own org's secret.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered; `verify_signature` never cross-checks `full_name` against `repository_owner`; `ExplicitParameters` in `LabeledHandler.params` only validates presence/type of `repository.full_name`, not its relationship to the org used for signature verification; there is no `Repository`-level or model validation enforcing that a webhook's authenticated org matches the repository being written to.

### Impact Explanation
This is "a payload for one repository mutating another's stack" (Critical) as long as at least one configured GitHub org in `Shipit.secrets.github` has a blank `webhook_secret`. In that condition, the attacker can archive or unarchive review stacks belonging to any tracked repository under a different, properly-secured org, purely by naming the no-secret org as `repository.owner.login` while pointing `full_name` at the victim repo. The blast radius extends to every repository/stack served by the same Shipit instance, not just the no-secret org's own repositories — this is a cross-tenant break of the "each webhook only affects its authenticating repository" invariant.

The claimed amplification via `ContinuousDeliveryJob` on a `continuous_deployment`-enabled stack is not directly supported by the code I could inspect: `ReviewStackAdapter#create!` explicitly sets `continuous_deployment: false` for any review stack it newly creates (`stack_attributes` in `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:87-94`), so a freshly-provisioned review stack from this flow starts with continuous_deployment disabled. The amplification would only materialize if a pre-existing review stack had been manually configured with `continuous_deployment: true`; I was not able to confirm within the available context whether that configuration is possible or common for review stacks specifically, since the "Rakefile"/settings form. Absent that confirmation, I treat the continuous-deployment amplification as unverified, while the core signature/repository-mismatch finding stands independently as Critical.

### Likelihood Explanation
Preconditions: (1) at least one org configured under `Shipit.secrets.github` must have a blank/unset `webhook_secret` — this is a valid, non-error configuration per `GitHubApp#initialize` (`@webhook_secret = @config[:webhook_secret].presence`) and per the documented multi-org config format, so it's a realistic deployment mistake, not a theoretical one. (2) the attacker must know or guess the name of that no-secret org. (3) the victim repository must exist as a tracked `Shipit::Repository` with `review_stacks_enabled` and an active PR/review stack. Attacker cost is a single crafted HTTP POST with no authentication, no session, and no valid signature required against the victim's actual secret. The attack is fully repeatable against any repository/stack visible via `full_name` in the same Shipit instance. [7](#0-6) 

### Recommendation
Bind webhook signature verification to the same repository identity the handlers act on: derive the verifying org from `repository.full_name`'s owner segment (not `repository.owner.login`), or explicitly validate that `repository.owner.login == repository.full_name.split('/').first` before proceeding. Additionally, make `webhook_secret` mandatory (fail closed) for every configured GitHub org rather than defaulting to `return true unless webhook_secret`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in test secrets: `no-secret-org` (webhook_secret blank) and `victim-org` (webhook_secret set), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create a `Shipit::Repository` for `victim-org/victim-repo` with `review_stacks_enabled: true`, and a `Shipit::ReviewStack` under it in an archived state matching `pr<N>`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` for `victim-org`'s secret, body: `action: "labeled"`, `repository: { owner: { login: "no-secret-org" }, full_name: "victim-org/victim-repo" }`, `pull_request` with the provisioning label and PR number `N`.
4. Assert response is `:ok` (not `:unprocessable_entity`), i.e., signature check passed via the no-secret org.
5. Assert the `ReviewStack` for `victim-org/victim-repo` transitioned state (`unarchived?`) even though the request never carried a signature valid for `victim-org`'s configured `webhook_secret` — demonstrating `repository_owner` ("no-secret-org") diverged from the actually-mutated repository's owner ("victim-org") while the request was still accepted.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
