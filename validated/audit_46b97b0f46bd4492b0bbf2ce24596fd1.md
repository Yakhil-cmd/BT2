### Title
Reentrant `register-for-bond` via attacker-controlled `signer-manager-trait` callback double-refunds custodied sBTC through stale `old-sbtc` - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` computes `old-sbtc` (the staker's currently custodied sBTC) once at the top of its `let` binding, then later invokes the caller-supplied, untrusted `signer-manager-validate-stake` trait callback **before** it asserts the non-overlap invariant and **before** it calls `roll-sbtc`/updates `protocol-bond-memberships`. Because the external call happens before the state-mutating effects, a staker-deployed `signer-manager` contract can re-enter `register-for-bond` and drive a second `roll-sbtc` computation off the same stale `old-sbtc`, causing the contract to refund the same custodied sBTC balance twice.

### Finding Description
The invariant that must hold is: `total-sbtc-staked` (and the contract's actual sBTC balance) reflects each staker's custodied amount refunded/netted **exactly once** per underlying custody balance. `roll-sbtc` is designed to enforce this by netting `old-sbtc` against `new-sbtc` and adjusting `total-sbtc-staked`/transferring only the delta: [1](#0-0) 

In `register-for-bond`, `old-sbtc` is captured once via `get-staker-custodied-sbtc` at the very start of the `let`: [2](#0-1) 

The function then performs a series of `asserts!` and, critically, calls the attacker-supplied `signer-manager-validate-stake` trait function **before** the non-overlap check on `existing-membership` and before `roll-sbtc`/`map-set protocol-bond-memberships` are executed: [3](#0-2) 

Because `signer-manager` is a caller-chosen `<signer-manager-trait>` contract, its `signer-manager-validate-stake` implementation can itself `contract-call?` back into pox-5's `register-for-bond` for the same `tx-sender` (Clarity preserves `tx-sender` across nested `contract-call?`s). At that point neither `existing-membership`/`old-sbtc` in the outer frame, nor the map entries backing them, have been written yet — the reentrant call re-reads the identical pre-mutation state and executes its own `roll-sbtc(tx-sender, old-sbtc, new-sbtc_inner)`, which (if `new-sbtc_inner < old-sbtc`) issues a real sBTC refund transfer from the contract to the staker and decrements `total-sbtc-staked`. Control then returns to the outer call, which resumes with its still-stale, un-refreshed `old-sbtc` and stale `existing-membership`, passes the `bond-overlaps-new-position?` assertion against that stale membership, and calls `roll-sbtc(tx-sender, old-sbtc, new-sbtc_outer)` again — issuing a **second** refund computed against the same `old-sbtc` that was already consumed/refunded once by the nested call. Both `roll-sbtc` calls succeed and both decrement `total-sbtc-staked` and transfer real sats out of the contract, even though the staker's custody balance was only ever `old-sbtc` once.

I did not find any reentrancy guard (e.g., a `signer-manager-call-active` boolean checked/set around the `signer-manager-validate-stake` call) in the reviewed code path between the checks (lines 710–782) and the effects (`roll-sbtc`, `map-set protocol-bond-memberships`); the external, attacker-controlled call at lines 753–756 precedes all of the state-mutating logic. This is a checks-effects-interactions ordering violation: the untrusted external call happens strictly before the invariant-guarding assert (`bond-overlaps-new-position?`) and before the effect (`roll-sbtc`) that the assert is supposed to protect.

### Impact Explanation
Each successful reentrant pair of `register-for-bond` calls can extract one extra net refund of sBTC (up to `old-sbtc`) from the contract's shared custody pool beyond what the staker's real custodied balance supports, i.e., theft of sBTC belonging to the shared pool backing other bond participants, and a double-counted decrement of `total-sbtc-staked` against a single underlying custody balance. This is repeatable per staker who has an existing rollover-eligible bond position (`old-sbtc > 0`) and matches the Critical category: "theft ... of locked STX or sBTC rewards" / "double-counting a commitment."

### Likelihood Explanation
Preconditions: attacker must (1) already hold a bond membership with nonzero custodied sBTC (`old-sbtc > 0`, i.e., have completed one legitimate `register-for-bond` sBTC-path registration), (2) be allowlisted for a second bond they can roll into, (3) be within the L1/rollover window checks (`verify-bond-rollover-window`, `bond-overlaps-new-position?`) for both the outer and inner calls, and (4) deploy their own `signer-manager` contract implementing `signer-manager-trait` that re-enters `register-for-bond` from inside `signer-manager-validate-stake`. All of these are within reach of an unprivileged staker who is a legitimate allowlisted participant — deploying a contract and crafting a callback requires no privileged role. The attack is a single self-contained transaction and can be repeated across bond rollover windows.

### Recommendation
Move the `signer-manager-validate-stake` external call to occur only after all invariant checks and after `roll-sbtc`/`map-set protocol-bond-memberships` have committed (checks-effects-interactions ordering), or add an explicit reentrancy guard (e.g., a contract-level boolean set before the external call and asserted/cleared around it) so a nested `register-for-bond` call from within the callback is rejected. Additionally, re-read `old-sbtc`/`existing-membership` immediately before `roll-sbtc` rather than relying on values captured at the top of the `let`, so any state mutated by a reentrant call is reflected before the second `roll-sbtc` net computation.

### Proof of Concept
Rust/Clarinet integration test plan:
1. Deploy `pox-5` and a malicious `signer-manager` contract implementing `signer-manager-trait`, whose `signer-manager-validate-stake` calls back into `pox-5.register-for-bond` with a second bond index for the same `tx-sender`.
2. Set up two bonds (`bond-0`, `bond-1`) both allowlisting `alice` with sBTC amounts such that `bond-0`'s custody is large (e.g. 8,000,000 sats) and both `bond-1`/rollover targets request smaller amounts (e.g. 1 sat each), maximizing refund per call.
3. `alice` registers for `bond-0` normally (establishes `old-sbtc = 8,000,000`).
4. Advance to `bond-0`'s rollover window; `alice` calls `register-for-bond(bond-1, malicious-signer-manager, ...)`. During `signer-manager-validate-stake`, the malicious contract re-enters `register-for-bond(bond-2, ...)` for `alice`.
5. Assert: total sBTC transferred out of `pox-5` to `alice` across both `roll-sbtc` calls exceeds `old-sbtc` (i.e., `contract_sbtc_balance_before - contract_sbtc_balance_after > 8,000,000 - final_new_sbtc`), and/or `total-sbtc-staked` decreases by more than the actual custodied amount, violating `sum(custodied sBTC per staker) == total-sbtc-staked == contract sbtc-token balance`.
6. Confirm no assertion in `register-for-bond` (`bond-overlaps-new-position?`, `verify-bond-rollover-window`) rejects the nested call, proving the absence of a reentrancy guard.

;; Move a staker's custodied sBTC from `old-sbtc` to `new-sbtc`, transferring
;; only the net difference: pull the increase from the staker, or refund the
;; decrease. `total-sbtc-staked` is updated by the net change. A registration
;; with no rollover passes `old-sbtc` of `u0`, which transfers the full amount.
;; A no-op when the two are equal.
(define-private (roll-sbtc
        (staker principal)
        (old-sbtc uint)
        (new-sbtc uint)
    )
    (begin
        (if (> new-sbtc old-sbtc)
            (let ((delta (- new-sbtc old-sbtc)))
                (try! (contract-call?
                    'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
                    transfer delta tx-sender current-contract none
                ))
                (var-set total-sbtc-staked (+ (var-get total-sbtc-staked) delta))
            )
            (if (< new-sbtc old-sbtc)
                (let ((delta (- old-sbtc new-sbtc)))
                    (try! (as-contract?
                        ((with-ft
                            'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
                            "sbtc-token" delta
                        ))
                        (try! (contract-call?
                            'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
                            transfer delta tx-sender staker none
                        ))
                    ))
                    (var-set total-sbtc-staked
                        (- (var-get total-sbtc-staked) delta)
                    )
                )
                ;; new-sbtc == old-sbtc, no transfer needed
                true
            )
        )
        (ok true)
    )
)
