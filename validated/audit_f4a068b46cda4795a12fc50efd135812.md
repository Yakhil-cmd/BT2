### Title
Stale `Account.owner` keeps spending authority after the position NFT is transferred, so the previous owner retains authentication to borrow and withdraw against an account they no longer hold - (`contracts/controller/src/account.rs`)

### Summary
The Auth0 advisory is about authentication material that remains valid when it should not — session cookie tags that can be forged to impersonate a user. The XOXNO Lending analog is a stored credential that outlives the transfer of ownership: `Account.owner` is fixed at account creation from the caller's address, while actual ownership is the transferable position NFT. The account-spending guards (`borrow`, `withdraw`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) authenticate `caller` against the stale `account.owner` field — not the live NFT owner — so after a victim sells/transfers their position NFT, the previous owner's "session" remains valid and they can drain the position.

### Finding Description
`create_account` writes `owner: owner.clone()` into the `Account` struct at mint time, where it stays in persistent storage (`contracts/controller/src/account.rs:64-65`). The spending authority check used by the sensitive entrypoints is `require_owner_or_delegate`, which grants access when `caller == *owner` — i.e., when the caller equals the *stored* owner (`contracts/controller/src/account.rs:121-122,130-140`). `load_or_create_account` passes `&account.owner` — the stored field — into that guard for `Migrate` and `Multiply` (`contracts/controller/src/account.rs:102,106`), and `debt.rs`/`supply.rs`/`strategies/*` apply the same guard to `borrow`, `withdraw`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` (per the permissionless-entrypoints ledger: "require_owner_or_delegate pins account_id to its owner").

By contrast, `require_account_owner` reads `storage::account_owner(env, account_id)` — the live NFT owner — and compares it to `caller` (`contracts/controller/src/account.rs:143-147`). The codebase therefore maintains two notions of "owner": the live NFT owner and the frozen `Account.owner`. The position NFT is a stock OpenZeppelin `transfer`/`transfer_from` token (per `permissionless_entrypoints.txt`: "each one moves or delegates control of a whole lending account; delegate grants from the previous owner go inactive"), which implies the intent that ownership moves with the NFT. But nothing in `transfer` calls back into the controller to rewrite `Account.owner`, so after a transfer:

- The new NFT owner fails `require_owner_or_delegate` on `account.owner`-guarded paths (`caller != stored owner`, and they hold no delegate grant) — they cannot `withdraw` their own collateral or `borrow` against it.
- The previous owner still satisfies `caller == account.owner` and retains full spending authority, including `borrow` to the threshold and `withdraw` of collateral.

This is the exact shape of the referenced bug class: an authentication token (here, the stored `owner` field) that remains valid after the real credential (NFT ownership) has changed hands.

### Impact Explanation
Theft of user funds. An attacker sells or transfers a leveraged/collateralized position NFT to a victim (e.g., via a secondary-market sale where the NFT confers the lending account). Once the victim owns the NFT — and has likely added collateral or the account holds supplied assets — the attacker calls `controller::withdraw(account_id, ...)` and `controller::borrow(account_id, ...)` as the stale `account.owner`, pulling out collateral up to the solvency limit. The victim cannot stop this: they are the live NFT owner but not the stored `account.owner`, and `remove_delegate`/`renew_account`-style owner-only paths check the live NFT owner while the spending paths check the stale one. All losses are borne by the NFT purchaser; this requires no privileged access and satisfies the "theft of user funds" acceptance bar.

### Likelihood Explanation
High. The trigger is a routine `position-nft::transfer`/`transfer_from` — an explicitly in-scope unprivileged action ("position-nft transfer/approve"). Secondary-market trading or OTC sale of positions is a natural use of an NFT-collateralized account design, and the attacker needs only to have been the owner at mint time. Caveat: within the limited analysis window I could not exhaustively confirm that no code path resynchronizes `Account.owner` on NFT transfer (e.g., a controller-side hook invoked during `supply`/`withdraw` that refreshes `account.owner` from `storage::account_owner`). The guards I inspected all consume `account.owner` directly, and the deliberate coexistence of `storage::account_owner` (live read) alongside the stored field suggests the staleness is real, but a storage-level resync that I did not observe would invalidate this finding.

### Recommendation
Authenticate spending authority against the live NFT owner, not the stored field. Concretely, in `require_owner_or_delegate` (or at each call site in `debt.rs`, `supply.rs`, `strategies/*`), resolve the current owner via `storage::account_owner(env, account_id)` and compare `caller` to that value — and key delegate lookups to the live owner as well (delegates are already stored under `(account_id, owner)`). Alternatively, update `Account.owner` inside the position-NFT `transfer`/`transfer_from` path via a controller hook so the stored field can never diverge. The `is_owner_or_delegate` fast path at `account.rs:121-122` is the single point to fix.

### Proof of Concept
1. Alice calls `controller::supply(account_id = 0, ...)` — `load_or_create_account` mints NFT `N` to Alice and stores `Account { owner: alice, ... }` (`account.rs:63-70`).
2. Alice adds collateral (e.g., supplies USDC, borrows ETH up to near-threshold).
3. Alice calls `position-nft::transfer(alice → bob, N)` (or Bob buys `N` via `transfer_from`). `Account.owner` is unchanged — it still reads `alice`.
4. Bob (new NFT owner) calls `controller::supply(account_id = N, ...)` or `withdraw`: `require_owner_or_delegate` compares `bob != account.owner (alice)`, Bob has no delegate entry → `NotAuthorized` (`account.rs:121-139`). Bob is locked out of managing the account he owns.
5. Alice calls `controller::withdraw(account_id = N, ...)` and `controller::borrow(account_id = N, ...)`: `caller == account.owner` passes the guard, solvency is re-proven against Alice's credentials, and funds leave to Alice — the previous holder's "authentication" still works on an account she no longer holds.
