### Title
Address definition change accepts an unreachable `definition_chash`, permanently freezing the address and any AA/shared-wallet funds controlled by it — ([File: validation.js])

### Summary
The Timelock report describes an "admin" state variable that can legitimately be updated (via `setPendingAdmin`/`acceptAdmin`) to a value that no longer matches the expected controller, permanently blocking all `queue`/`cancel`/`execute` functions that gate on `msg.sender == admin`. In ocore, the analogous "controller pointer" is an address's `definition_chash`, which is updated through the `address_definition_change` message. The gate `validateInlinePayload` applies to this message only checks that the new value is *syntactically* a valid address/chash — it never checks that the new `definition_chash` corresponds to a definition that is or will ever be disclosed. Once such a change becomes stable, the address is bricked: it can no longer author any future unit (payment, AA trigger, etc.), exactly like Timelock's queue functions reverting forever once `admin` no longer matches `governorBravoDelegator`.

### Finding Description
`validateInlinePayload` validates the `address_definition_change` payload with only a format check: [1](#0-0) 

No check is performed that `payload.definition_chash` is a chash of a definition that the sender can or ever will supply. The core definition-evaluation code itself documents this exact risk: [2](#0-1) 

Once the `address_definition_change` unit becomes stable (`address_definition_changes` table updated, see `writer.js`): [3](#0-2) 

all subsequent authoring from that address is validated against the new `definition_chash` via `storage.readDefinitionByAddress` in `validateAuthor`: [4](#0-3) 

If the new `definition_chash` never matches any definition that is disclosed (typo, wrong hash, or deliberately set to an unreachable value), `ifDefinitionNotFound` is hit on every future attempt to spend from or sign with that address, and unless the signer can supply a definition whose `getChash160` equals the stored `definition_chash`, `validateDefinition` in `validation.js:1464-1483` will always reject the unit ("wrong definition: ... !== ..."). The address is then permanently unable to produce a valid signed unit — analogous to Timelock's `queueTransaction`/`cancelTransaction`/`executeTransaction` reverting forever once `admin` diverges from `governorBravoDelegator`.

This is especially damaging for shared/multisig addresses (`wallet_defined_by_addresses.js`) where a `definition_chash` change is a legitimate, cooperatively-composed action controlled by one or more of the co-signers, and for addresses referenced from AA definitions via `['address', 'BASE32']` (`definition.js` case `'address'`), where the inner address's definition is re-evaluated on every use — if a referenced address is redefined to an unreachable chash, `evaluate` at `definition.js:774-800` cannot resolve the inner definition, and every dependent AA signature check that traverses that path will permanently fail.

### Impact Explanation
Once an address's definition is changed to an unreachable `definition_chash`, that address can never again author a valid unit. For a shared address used to hold AA-related or multi-party funds, this freezes those funds irrecoverably (no future payment/AA trigger unit from that address can ever validate). This matches the accepted impact category "AA fund loss or freezing" — the address's coins remain forever unspendable, and any AA logic gated on `['address', ...]` referencing this address becomes permanently non-functional, mirroring the reported Timelock queue-processing freeze.

### Likelihood Explanation
The change is reachable by any address owner (or any co-signer authorized to trigger a definition change on a shared address) through the normal `address_definition_change` message — no special privilege beyond being a legitimate signer/poster of a unit is required, satisfying the "unprivileged unit poster" reachability bar. A single mistake (wrong chash) or a malicious co-signer intentionally setting an unreachable chash is sufficient to trigger the freeze; there is no validation-time safeguard preventing it.

### Recommendation
Consider requiring that the new `definition_chash` either equal an address for which a corresponding definition can plausibly be supplied later, or require the new definition to be attached to the same unit (as already supported for the very first message from an address), removing the ability to point to an entirely unknown chash. At minimum, document/require wallet software to always co-supply the new definition in the same or a closely-following unit, and consider adding a recovery path (e.g., allowing the address to be redefined again by a fallback branch of the *previous* definition) so a bad `definition_chash` cannot be a permanent dead-end for shared/multisig addresses.

### Proof of Concept
1. Address `A` (single-signature or a shared address with definition `D_old`) posts a unit with an inline `address_definition_change` message setting `payload.definition_chash = X`, where `X` is a syntactically valid chash for which no one holds/knows a matching definition (e.g., a randomly generated 32-byte base32 string, or a hash of a definition that was never disclosed and never will be).
2. `validateInlinePayload` accepts this because it only checks `isValidAddress(payload.definition_chash)` (`validation.js:1743-1744`).
3. Once the unit is stable, `address_definition_changes` records `X` as the active `definition_chash` for `A` (`writer.js:186-191`).
4. Any subsequent unit authored by `A` is checked via `storage.readDefinitionByAddress` / `validateDefinition` (`validation.js:1464-1483`); since no definition hashing to `X` can ever be produced, every future unit from `A` is rejected with `"wrong definition: ... !== X"`.
5. `A`'s balance (and any AA logic that reaches `A` via `['address', 'A']` in a definition) is now permanently frozen/unusable, with no on-chain recovery path.
