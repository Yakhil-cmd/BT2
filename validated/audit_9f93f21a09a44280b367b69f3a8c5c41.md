### Title
Missing Recipient Address Validation in `_requestERC20Transfer` and `_requestERC721Transfer` Causes Permanent Token Loss in Mint-Burn Mode — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`_requestERC20Transfer` and `_requestERC721Transfer` do not validate that the `_to` recipient address is non-zero. In mint-burn mode, tokens are irreversibly burned on the source chain before the bridge event is emitted. When `_to = address(0)`, the counterpart bridge's handle function always reverts (ERC20/ERC721 standards reject minting to `address(0)`), leaving the tokens permanently destroyed with no corresponding mint on the destination chain.

---

### Finding Description

In `_requestERC20Transfer`, there is no `require(_to != address(0))` guard:

```solidity
function _requestERC20Transfer(
    address _tokenAddress,
    address _from,
    address _to,       // ← never validated
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    internal
    onlyRegisteredToken(_tokenAddress)
    onlyUnlockedToken(_tokenAddress)
{
    require(isRunning, "stopped bridge");
    require(_value > 0, "zero ERC20 token amount");

    uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

    if (modeMintBurn) {
        ERC20Burnable(_tokenAddress).burn(_value);  // ← tokens destroyed here
    }

    emit RequestValueTransfer(
        TokenType.ERC20,
        _from,
        _to,            // ← address(0) propagated to event
        ...
    );
    requestNonce++;
}
``` [1](#0-0) 

The same pattern exists in `_requestERC721Transfer`:

```solidity
if (modeMintBurn) {
    ERC721Burnable(_tokenAddress).burn(_tokenId);  // ← NFT destroyed
}
emit RequestValueTransferEncoded(..., _to, ...);   // ← address(0) in event
``` [2](#0-1) 

On the counterpart chain, bridge operators observe the `RequestValueTransfer` event and call `handleERC20Transfer`, which attempts:

```solidity
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
}
``` [3](#0-2) 

The OpenZeppelin ERC20 `_mint` function unconditionally reverts when `account == address(0)`:

```solidity
require(account != address(0), "ERC20: mint to the zero address");
``` [4](#0-3) 

Because the entire `handleERC20Transfer` transaction reverts, the nonce-tracking state (`handleNoncesToBlockNums[nonce]`, `closedValueTransferVotes[nonce]`) is never committed. The `_updateHandleNonce` loop advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    ...
}
lowerHandleNonce = i;
``` [5](#0-4) 

Since the stuck nonce's entry is never set, `lowerHandleNonce` is permanently frozen at that nonce, breaking the bridge's recovery-block tracking.

The public entry points that accept a caller-controlled `_to` are:

- `requestERC20Transfer(address _tokenAddress, address _to, ...)` — any user can pass `address(0)` as `_to`
- `onERC20Received(address _from, address _to, ...)` — called by the token contract with caller-supplied `_to`
- `requestERC721Transfer(address _tokenAddress, address _to, ...)` — same issue for NFTs [6](#0-5) [7](#0-6) 

---

### Impact Explanation

In mint-burn mode, the source-chain tokens are burned atomically and unconditionally before the bridge event is emitted. There is no rollback path. The counterpart bridge's handle transaction always reverts for `_to = address(0)`, so no tokens are ever minted on the destination chain. The user's tokens are permanently destroyed. Additionally, `lowerHandleNonce` and `recoveryBlockNumber` are frozen at the bad nonce, corrupting the bridge's recovery state.

---

### Likelihood Explanation

Any user who calls `requestERC20Transfer` or `requestERC721Transfer` directly (or triggers `onERC20Received` / `onERC721Received`) can supply `address(0)` as `_to`, either accidentally or maliciously. No special privilege is required. The bridge is a public-facing contract. The only prerequisite is that the token is registered and the bridge is running, both of which are normal operating conditions.

---

### Recommendation

Add a zero-address check at the top of `_requestERC20Transfer` and `_requestERC721Transfer`:

```solidity
require(_to != address(0), "zero recipient address");
```

Apply the same guard to `_requestKLAYTransfer` in `BridgeTransferKLAY.sol`, where a zero `_to` causes KLAY to be sent to `address(0)` on the counterpart chain (the EVM does not block this, so KLAY is silently destroyed). [8](#0-7) 

---

### Proof of Concept

1. Deploy the bridge in mint-burn mode (`modeMintBurn = true`).
2. Register a token.
3. Call `requestERC20Transfer(tokenAddress, address(0), 1000e18, 0, "")` from any user account.
4. Observe: tokens are burned from the bridge (`ERC20Burnable.burn` succeeds), `RequestValueTransfer` is emitted with `to = address(0)`, `requestNonce` increments.
5. Bridge operators observe the event and call `handleERC20Transfer(..., address(0), ..., value, nonce, ...)` on the counterpart chain.
6. `_voteValueTransfer` reaches threshold; execution proceeds to `ERC20Mintable.mint(address(0), value)`.
7. The mint reverts with `"ERC20: mint to the zero address"` — the entire handle transaction reverts.
8. Operators retry indefinitely; every attempt reverts. `lowerHandleNonce` never advances past this nonce.
9. The burned tokens are permanently lost with no recovery path.
