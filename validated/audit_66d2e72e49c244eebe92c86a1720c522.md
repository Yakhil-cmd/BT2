### Title
Stakers cannot redirect sBTC withdrawals in `unstake-sbtc`/`roll-sbtc`, permanently freezing bonded sBTC if the staker is blacklisted by the sBTC token contract - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s sBTC-bond withdrawal paths (`unstake-sbtc`, and the internal `roll-sbtc` helper used during bond rollover) always send the sBTC back to the hardcoded `staker` principal (`tx-sender`) via `contract-call? ... sbtc-token transfer ... tx-sender staker none`, with no parameter allowing the staker to designate an alternate recipient. This mirrors the Beedle `repay`/`seizeLoan` bug class: if the sBTC-token issuer (an external, admin-governed SIP-010 contract) ever revokes/blacklists the staker's principal, every call path that would return their locked sBTC reverts, and the staker has no way to move the funds to a different address.

### Finding Description
`unstake-sbtc` (stackslib/src/chainstate/stacks/boot/pox-5.clar:1261-1342) locks in all state mutations (map-set of `protocol-bond-memberships`, `protocol-bonds-total-staked`, and `var-set total-sbtc-staked`) and then performs the sBTC payout: [1](#0-0) 

Because this is a Clarity `try!` inside a public function, if the `transfer` call fails (e.g., because the sBTC-token contract's `transfer` function rejects the `staker` recipient/sender due to an issuer-side blacklist), the entire transaction — including the state updates that would have reduced the staker's bonded amount — is rolled back atomically. The result is that the staker's `amount-sats` in `protocol-bond-memberships` remains unchanged and their sBTC remains custodied by `pox-5` forever, with **no function anywhere in the contract that lets the staker (or anyone) specify an alternate recipient** for this payout.

The same pattern exists in the internal `roll-sbtc` helper, which is invoked during bond registration/rollover to refund the delta when a staker's custodied sBTC decreases; it also hardcodes the refund recipient to `staker`: [2](#0-1) 

The only functions that can move sBTC out of `pox-5` to an arbitrary `recipient` are `transfer-from-reserve` and `transfer-stranded-rewards`, both `define-private` and only reachable "as part of consensus (via the SIP process)" — i.e., a privileged/administrative path, not something the affected staker can trigger themselves: [3](#0-2) 

There is therefore no unprivileged, staker-driven way to recover bonded sBTC once the staker's principal is rejected by the sBTC-token contract's `transfer` logic.

### Impact Explanation
This breaks the invariant that locked/staked sBTC is always eventually redeemable by its owner. If the sBTC token issuer revokes the staker's principal, the staker's bonded sBTC becomes **permanently frozen** inside `pox-5` — the exact "permanent freezing of staked... sBTC" impact category called out as Critical, since the funds are unrecoverable by the account that put them at stake and there is no unprivileged recovery path.

### Likelihood Explanation
Low-to-medium likelihood: it requires the staker's principal to be rejected by the sBTC token contract's `transfer` function (e.g., via an issuer-level blacklist or freeze, analogous to how centralized-issuer wrapped-asset contracts such as USDC support blacklisting). This is an external precondition rather than something an attacker can trigger unilaterally against another user, but it is a realistic operational risk for any SIP-010 asset that supports compliance-driven transfer restrictions, and once triggered the resulting freeze is permanent and irreversible through any public entry point.

### Recommendation
Add a `recipient` parameter to `unstake-sbtc` (and to the bond registration/rollover paths that invoke `roll-sbtc`), allowing the staker (`tx-sender`) to designate the address that should receive the returned sBTC, e.g.:
```clarity
(define-public (unstake-sbtc
        (signer-manager <signer-manager-trait>)
        (amount-to-withdrawal-sats uint)
        (recipient principal)
    )
    ...
    (try! (as-contract?
        ((with-ft 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
            "sbtc-token" amount-to-withdrawal-sats
        ))
        (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
            transfer amount-to-withdrawal-sats tx-sender recipient none
        ))
    ))
    ...
)
```
Similarly parameterize `roll-sbtc`'s refund path (or add an alternate unprivileged "sweep to recipient" entry point gated on `tx-sender == staker`) so that a staker whose own principal is rejected by the sBTC contract can still redirect funds to an address the token contract will accept.

### Proof of Concept
1. Alice registers for an sBTC-backed bond via `register-for-bond`/`stake`, custodying `N` sats of sBTC in `pox-5` under her principal.
2. The sBTC-token contract's operator blacklists Alice's principal (analogous to a USDC-style freeze), causing any `(contract-call? sbtc-token transfer amount sender ALICE memo)` to return `(err ...)`.
3. Alice calls `unstake-sbtc` to withdraw her sBTC: [4](#0-3) 
4. The internal `transfer` at line 1326-1328 fails because `staker` (Alice) is blacklisted; the surrounding `try!` propagates the error, aborting the entire transaction and reverting all the bond-accounting state changes made earlier in the function.
5. Alice's `N` sats remain locked in `protocol-bond-memberships`/`total-sbtc-staked`, with no alternate function to redirect the payout to a non-blacklisted address — the sBTC is permanently frozen in `pox-5`.
