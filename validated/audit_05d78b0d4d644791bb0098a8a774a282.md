### Title
Webhook signature verified against the payload's `repository.owner.login`, but events act on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Every event handler (`PushHandler`, `StatusHandler`, the `PullRequest::*` handlers, etc.), however, resolves the target `Stack`/`Repository` using a completely different payload field: `payload.dig('repository', 'full_name')`. The HMAC only covers the raw request body as a whole, but the *authorization decision* ("which org's secret proves this request is legitimate") is bound to `owner.login`, while the *authorization target* ("which repository/stack gets mutated") is bound to `full_name`. Nothing ties these two fields together, so in a multi-organization Shipit deployment an attacker who legitimately controls the webhook secret for **one** onboarded organization can forge a payload that authenticates as that organization while acting on a stack that belongs to a **different** onboarded organization/repository.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) via `github_app_config`, meaning each org onboarded to this Shipit instance can have its own, independently-known secret: [2](#0-1) 

Once the signature check passes (using the secret belonging to `repository.owner.login`), the full, attacker-controlled `params` object is dispatched unmodified to the handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers, however, resolve the acted-upon repository using `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process` uses this `stacks` scope to trigger a `sync_github` against any matching (non-archived) stack: [5](#0-4) 

`StatusHandler#process` similarly finds commits purely by `sha` (a value fully controlled by the attacker) and writes a commit status, independent of `repository.owner.login`: [6](#0-5) 

The trust binding that should hold is:
`org whose webhook_secret authenticated the request == org that owns the repository/stack being mutated`

The code instead enforces:
`org whose webhook_secret authenticated the request == params['repository']['owner']['login']` (an attacker-supplied string used only for signature-key selection)
`repository/stack acted upon == params['repository']['full_name']` (a different attacker-supplied string, never cross-checked against the first)

Because `repository.owner.login` and `repository.full_name` are independent JSON fields inside the same signed body, and the signature only proves "this exact byte string was HMAC'd with organization X's secret," an attacker who knows organization X's `webhook_secret` (which is a config value they legitimately possess for *their own* onboarded org — not a Shipit credential) can set `repository.owner.login: "X"` (to pass verification) while setting `repository.full_name: "Y/some-repo"` for an entirely different onboarded organization `Y`.

### Impact Explanation
This breaks the deployment-trust binding between "the GitHub organization that authenticated the webhook" and "the repository that gets written to," which is explicitly listed as an in-scope analog class. Concretely, in a Shipit instance configured with `github:` entries for multiple organizations (as documented in `docs/setup.md` and `config/secrets.development.example.yml`), an attacker who is a legitimate administrator of org X's GitHub App/webhook (and thus knows X's `webhook_secret`) can:
- Forge a `push` event with `repository.owner.login = "X"` and `repository.full_name = "Y/target-repo"`, causing Shipit to queue a `GithubSyncJob`/`sync_github` for a stack under organization Y that the attacker has no access to.
- Forge a `status` event the same way to inject a fabricated commit status (`state`, `context`, `target_url`) for any commit SHA known to the attacker in org Y's stacks, which can be used to satisfy `ci.require` checks and enable an otherwise-blocked deploy — an unauthorized deploy/CI-bypass on a repository the attacker doesn't control.

This corresponds to "cross-repository writes" and "an unauthorized deploy" impact tiers.

### Likelihood Explanation
Requires the host application to run multiple GitHub organizations behind one Shipit instance (a documented, supported configuration — `docs/setup.md` shows the multi-org `github:` schema) and for the attacker to be an administrator of at least one onboarded, lower-trust organization while targeting a higher-trust one. This is a realistic scenario for shared/multi-tenant Shipit deployments (e.g., an internal platform team onboarding many company GitHub orgs), where possessing one org's webhook secret is not equivalent to having any privilege over other orgs' repositories.

### Recommendation
Bind the signature-verifying key to the same repository identity that handlers act on. Concretely:
- Derive `repository_owner` from the *same* field used by handlers (`repository.full_name`'s owner segment), or better, verify that `params.dig('repository', 'owner', 'login')` matches the owner segment of `params.dig('repository', 'full_name')` before proceeding, rejecting the request (422) on mismatch.
- Alternatively, once `github_app` is resolved, re-validate that the resolved `Repository`/`Stack` the handler will mutate actually belongs to `repository_owner`, and drop the event otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `X` and `Y`, each with a distinct `webhook_secret` (per `docs/setup.md`'s multi-org schema).
2. As an attacker who administers org `X`'s webhook (knows `secret_X`), craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "X" },
    "full_name": "Y/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(secret_X, raw_body)>` and POST to `/github/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner => "X"`, loads `Shipit.github(organization: "X")`, and verifies successfully using `secret_X`.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("Y/victim-repo")` and calls `sync_github` on Y's stack — despite the request never being authenticated by Y's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
