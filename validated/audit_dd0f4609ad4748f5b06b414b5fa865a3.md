### Title
Cross-user oracle price griefing via shared, unversioned `last-update` monotonic-timestamp map - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `last-update` map that gates oracle price acceptance is a single, protocol-wide cache keyed only by `{ type, ident }` (the feed identifier), shared by every user and every operation that touches that asset's price. Any unprivileged caller who is first to land a transaction that resolves a price for a given feed advances this shared "high-water mark," and any other unprivileged caller whose transaction carries a (still valid, non-stale) but older price update for the same feed will have their transaction revert, exactly the same bug class as the reported GovernorAlpha issue where one caller's queued state (keyed only by shared parameters, with no per-caller/per-proposal nonce) blocks a different caller's otherwise-legitimate transaction in the same window.

`price-resolve` checks freshness and monotonicity against this shared map and then advances it if the new timestamp is newer: [2](#0-1) 

The key `{ type, ident }` identifies only the oracle feed itself — it carries no information about which user, which proposal/operation, or which transaction is consuming it, exactly analogous to the GovernorAlpha `Timelock` transaction hash that identified only `(target, value, signature, data, eta)` with no proposal nonce. Because `oracle-timestamp-fresh` requires `(>= ts prev)`, once one caller's transaction advances `last-update` for a feed to timestamp `T2`, any other caller in the same or a following block who submits a legitimately fresh (within `max-staleness`) but slightly older price update (timestamp `T1 < T2`, e.g. because their VAA was relayed/fetched earlier, or because their transaction landed after a fresher one in the same block) has their transaction revert with `ERR-ORACLE-INVARIANT`, even though their own price data would have been perfectly acceptable in isolation.

`price-resolve` is invoked (via `price-multi-resolve`/`iter-price-multi`) for every borrow, repay, withdraw, deposit-driven health check, and liquidation, so this shared state is written and consumed by unrelated, unprivileged callers on every price-sensitive operation for a given asset.

### Impact Explanation
An attacker can weaponize this ordering dependence between two unprivileged users touching the same feed in the same block: front-run a victim's time-sensitive transaction (most impactfully a liquidation, or a repay/withdraw racing a health-check window) with a transaction that resolves the same price feed using a fractionally newer valid timestamp, advancing the shared `last-update` high-water mark. The victim's otherwise valid, in-flight transaction — built with a VAA/timestamp fetched slightly earlier — then reverts against `ERR-ORACLE-INVARIANT` purely because of shared global state, not because of any fault in the victim's own data. This can be used to grief/DoS a specific liquidator out of a liquidation opportunity in a given block, or to block a borrower's timely repay/withdraw, causing temporary freezing of funds/operations for the victim until they resubmit with a fresher feed. This lands in the in-scope "temporary freezing of funds" bucket.

### Likelihood Explanation
Any address can trigger `price-resolve` for a given feed simply by performing an ordinary market operation (borrow/repay/deposit/withdraw/liquidate) that touches that asset — no privileged role is required. Because Pyth/DIA price updates are public and broadcastable, an attacker can cheaply obtain a marginally newer valid update and race it against a known pending victim transaction (e.g., observed in the mempool) that references the same feed, making this an ordering/MEV-adjacent but code-rooted (not miner-privileged) griefing vector reachable by any unprivileged actor.

### Recommendation
Do not use a single global "last accepted timestamp" per feed to gate correctness for unrelated callers. Either: (a) drop the strict cross-caller monotonicity requirement and rely solely on the `max-staleness` freshness check relative to `stacks-block-time` (each caller's own price data should only need to be "fresh enough," not "fresher than whatever anyone else already submitted"), or (b) scope any monotonic tracking to be informational/telemetry only rather than a hard revert condition affecting other users' transactions.

### Proof of Concept
1. Block N: User A (attacker or unrelated party) submits a transaction touching the STX/USD feed with Pyth VAA timestamp `T2`, calling any market operation; `price-resolve` executes, passes freshness/monotonicity, and sets `last-update[{type:PYTH, ident:STX_FEED}] = T2`. [3](#0-2) 
2. In the same block N, victim (e.g., a liquidator) submits a liquidation transaction carrying a valid, non-stale VAA for the same feed with timestamp `T1 < T2` (fetched/signed slightly earlier, still within `max-staleness` of `stacks-block-time`).
3. Victim's call reaches `price-resolve`; `oracle-timestamp-fresh(T1, T2, max-staleness)` evaluates `(>= T1 T2)` as false, causing `asserts!` to fail with `ERR-ORACLE-INVARIANT`. [4](#0-3) 
4. The victim's entire transaction (liquidation, repay, or withdraw) reverts, despite carrying legitimately fresh price data, purely because an unrelated user's transaction already advanced the shared `last-update` marker for that feed in the same block.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
