### Title
Unbounded scan of all unstable DAG units in `dataFeedExists`/`readDataFeedValue` causes O(n) CPU cost per AA data-feed lookup, enabling AA-processing DoS - ([File: data_feeds.js])

### Summary
`data_feeds.js` implements the same unbounded-loop pattern flagged in the external report's `_previewWithdraw` finding: when an AA formula uses `data_feed`/`in_data_feed`, the in-memory branch of `dataFeedExists` and `readDataFeedValue` iterates over **every currently-unstable unit in the DAG** (`storage.assocUnstableMessages`), and for each one iterates over all of that unit's messages, with no upper bound on the number of unstable units scanned.

### Finding Description
`dataFeedExists` (called from `in data feed`/`in_data_feed` formula evaluation) contains:
```
for (var unit in storage.assocUnstableMessages) {
    ...
    storage.assocUnstableMessages[unit].forEach(function (message) { ... });
}
``` [1](#0-0) 

and the equivalent unstable-scan branch in `readDataFeedValue`: [2](#0-1) 

`storage.assocUnstableMessages` holds the messages of **every unit that is not yet stable** (i.e., not yet included in the main chain with enough confirmations), and is populated as new units are accepted/written and cleared only when units become stable (`writer.js`, `main_chain.js`). Any unprivileged unit poster/AA trigger sender can increase the number of unstable units simply by posting many units (or by posting units whose parents are chosen so they linger unstable), since stabilization depends on witnessed confirmations across the whole network and is not something a single poster controls or is rate-limited against. There is no cap analogous to `MAX_MESSAGES_PER_UNIT`, `MAX_OPS`, or `MAX_COMPLEXITY` limiting how many unstable units/messages this loop may traverse.

This is invoked synchronously from `formula/evaluation.js`'s `data_feed`/`in_data_feed` opcode handling during AA trigger processing: [3](#0-2) [4](#0-3) 

AA trigger handling (`handleTrigger` in `aa_composer.js`) runs under the `write` mutex/serialized validation pipeline while processing incoming units, so a slow formula evaluation blocks subsequent unit/AA validation for the whole node - directly analogous to the `_previewWithdraw` report, where an unbounded loop reachable from a normal user action (withdraw) could exhaust gas/time and block processing.

### Impact Explanation
Any unprivileged unit poster can trigger an AA (or is itself the AA author placing a `data_feed`/`in_data_feed` lookup) whose evaluation cost scales linearly with the total number of unstable units network-wide at that moment. Under normal/heavy network load (many pending, not-yet-stable units — which is a state achievable by ordinary usage or by an attacker who posts many units without cooperating to stabilize them), each AA trigger that performs a data-feed lookup forces the local node to iterate the full unstable-unit set and all messages therein. Repeated triggers (each poster can post many trigger units) amplify this into a CPU/time DoS on AA processing, slowing or stalling the node's ability to validate/confirm new units in a timely manner — a network-availability impact in the same class the report calls out (a party being blocked from performing an intended, permitted operation due to unbounded work in a loop it does not control).

### Likelihood Explanation
Likelihood is moderate-to-high: no special privileges are required, only the ability to author/trigger AAs that use `in data feed`/`data feed` formulas and to grow the pool of unstable units (which any active user of the network naturally does, and which an adversary can deliberately inflate). No configuration limit was found capping `storage.assocUnstableMessages` size or the loop's iteration count.

### Recommendation
- Bound the in-memory unstable-unit scan: cap the number of unstable units/messages inspected per data-feed lookup (or maintain a size-limited index of unstable data-feed messages by `(address, feed_name)` instead of scanning the full unstable set).
- Fail/short-circuit early once a match is found per address in the outer loop rather than continuing to iterate the entire `assocUnstableMessages` map for every trigger evaluation.
- Consider charging AA formula complexity/ops proportional to the number of unstable units scanned, consistent with existing `MAX_COMPLEXITY`/`MAX_OPS` protections used elsewhere in `definition.js`/`formula/validation.js`.

### Proof of Concept
Not independently reproduced against a live network; the finding is based on static analysis of `data_feeds.js:13-97` and `data_feeds.js:205-274`, cross-referenced with `formula/evaluation.js` call sites at lines 646 and 745, showing the loop is reachable through ordinary AA `data_feed`/`in_data_feed` formula evaluation with no bound on `storage.assocUnstableMessages` size. Confirming the real-world severity (i.e., how large `assocUnstableMessages` can practically grow and the resulting wall-clock cost) would require running the code against a node with a large unstable-unit backlog, which was not available in this analysis — flagged here as unverified.
