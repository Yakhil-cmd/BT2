### Title
Cross-organization webhook signature confusion: `repository_owner` fallback to `organization.login` lets an attacker who controls one org's webhook secret sign payloads that mutate a different org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the `webhook_secret`) used to validate the HMAC based on `repository_owner`, which falls back to the payload's top-level `organization.login` whenever `repository.owner.login` is absent from the same request body. Because pull-request handlers such as `OpenedHandler` independently trust the payload's top-level `repository.full_name` (a sibling field, unrelated to `repository.owner.login`) to decide which `Shipit::Repository`/stack to mutate, an attacker who legitimately controls org A's webhook integration (and therefore knows org A's `webhook_secret`) can sign a crafted payload naming org A in `organization.login` while pointing `repository.full_name` at an unrelated, already-tracked `org-b/repo`.

### Finding Description
The broken binding: "the organization whose `webhook_secret` verified the HMAC" == "the organization owning the repository the handler mutates." The controller computes: [1](#0-0) 
`repository_owner` prefers `repository.owner.login`, but falls back to `organization.login` if that path is nil - and `Hash#dig` silently returns `nil` for a `repository` hash that exists but simply lacks an `owner` sub-key, not just when `repository` itself is absent. This value is used only to select the verifying app/secret: [2](#0-1) 
and `verify_webhook_signature` performs only an HMAC comparison against that org's secret, with no cross-check against any other field in the payload: [3](#0-2) 

Once verified, `Shipit::Webhooks.for_event('pull_request')` handlers are invoked with the raw, attacker-controlled `params` hash. `Handler#initialize` only parses/validates shape via `ExplicitParameters`, it does not re-derive or compare `repository_owner`: [4](#0-3) 
`OpenedHandler` requires a top-level `repository.full_name` (a field completely independent of `repository.owner.login` used for signature selection) and resolves/mutates that repository's stacks directly: [5](#0-4) [6](#0-5) 

Exploit flow: attacker crafts a POST to `/webhooks` with `X-Github-Event: pull_request`, body `{"action":"opened","number":..., "pull_request": {...}, "repository": {"full_name": "org-b/repo"}, "organization": {"login": "org-a"}, "sender": {"login": "..."}}` (note: `repository.owner.login` is omitted, `organization.login` = "org-a"), and signs `X-Hub-Signature` using org-a's `webhook_secret` (which the attacker legitimately knows because they control org-a's own Shipit/GitHub App integration). `repository_owner` resolves to `"org-a"`, verification succeeds against org-a's secret, but `OpenedHandler` then looks up and creates/mutates a stack for `org-b/repo` - a repository the attacker never authenticated against.

No existing guard prevents this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` only validates payload *shape*, not organizational consistency; there is no code anywhere that compares `repository_owner` (used for verification) against `params.repository.full_name`'s owner before dispatching to handlers.

### Impact Explanation
This is a cross-tenant forged-webhook write: a request whose HMAC only proves knowledge of org-a's secret results in a stack being created/mutated for `org-b/repo`, which the attacker never authenticated against. This matches the Critical category "a payload for one repository mutating another's stack" and effectively an authentication-bypass for org-b's webhook trust boundary. It is repeatable against any repository already tracked by Shipit (`Repository.from_github_repo_name` must resolve) and any pull-request event type Shipit handles (opened, labeled, edited, closed, reopened, etc. - all of these handlers use the same top-level `repository.full_name` pattern), since none of them re-verify the owner.

### Likelihood Explanation
Requires the attacker to control at least one organization's own webhook integration with Shipit (i.e., they know their own org's `webhook_secret`, which is expected of any onboarded org, not a privileged Shipit role) and requires the target `org-b/repo` to already be tracked as a `Shipit::Repository`. No Shipit session, API token, or GitHub credentials for org-b are needed. This is a low-cost, fully scriptable, repeatable attack (single crafted HTTP POST) once the attacker has any one org's secret.

### Recommendation
After successful signature verification, cross-check that the organization used for verification matches the owner implied by every repository reference the handler will act on (e.g., require `repository.owner.login` explicitly rather than falling back silently to `organization.login`, or verify `repository.full_name.split('/').first == repository_owner` before dispatching to handlers). Consider rejecting payloads where `repository` is present but `owner.login` is missing, and only using the `organization` fallback for genuinely organization-scoped events (e.g., `membership`) that have no repository payload at all.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb` (or a new pull-request handler test), construct:
```ruby
test "cross-org signature confusion mutates unrelated repository" do
  # org-a is the attacker's own configured org; org-b/repo is a pre-existing tracked Shipit::Repository
  payload = {
    "action" => "opened",
    "number" => 999,
    "pull_request" => { ... valid pull_request fields ... },
    "repository" => { "full_name" => "org-b/repo" }, # note: no "owner" key
    "organization" => { "login" => "org-a" },
    "sender" => { "login" => "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_webhook_secret, payload)
  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  assert_difference -> { Shipit::Stack.where(repository: org_b_repository).count }, 1 do
    post :create, body: payload, as: :json
  end
  # Assert: signature verified using org-a's secret (repository_owner == "org-a")
  # but the mutated stack's repository owner == "org-b" (repository.full_name.split('/').first)
  assert_response :ok
end
```
Both sides of the equality diverge (`repository_owner` = `"org-a"` for verification vs. actual mutated repository owner = `"org-b"`), and no code path forces them to match.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
