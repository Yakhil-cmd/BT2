**Rationale:** The WeKnora advisory describes a command-injection bug class (CWE-77/78): a Go web server accepts JSON from an authenticated HTTP caller, stores attacker-controlled `command`/`args` fields unsanitized, and later passes them straight into `exec.Command`-style subprocess spawning (`client.NewStdioMCPClientWithOptions` → `client.Start`) when a `/test` endpoint is hit.

Polkadot SDK has no structurally equivalent sink reachable from an unprivileged user entry point:

- The only places where `std::process::Command` (or shell scripts) is invoked are build tooling, CI/test harnesses, benchmarking CLIs, chain-spec builders, and node CLI test helpers — e.g. [1](#0-0)  and [2](#0-1) . None of these are reachable via a signed extrinsic, XCM message, contract call, or any other on-chain user-controlled entry point; they execute only in local developer/CI/node-operator contexts, not as part of runtime state transition logic triggered by untrusted transactions.
- `do_apply_extrinsic` in the executive pallet [3](#0-2)  — the actual dispatch path for user-submitted extrinsics — only decodes, validates, and dispatches calls into pallet logic; there is no code path from a dispatched call into OS-level process spawning.
- PVF worker processes in `polkadot/node/core/pvf` are spawned by validator/node infrastructure using fixed validator-controlled paths and WASM blobs subject to the PVF validation/preparation pipeline, not raw attacker-supplied `command`/`args` strings, and are not triggered per-extrinsic by an ordinary user; this is a fundamentally different trust model than "store attacker JSON, later `exec` it."

Because Polkadot SDK's runtime execution model (WASM state transition function dispatched deterministically on-chain) has no notion of "stored service configuration" that gets fed into a host-side subprocess spawn reachable by an unprivileged signed extrinsic, XCM message, or contract call, there is no demonstrable analog of this command-injection bug class in the provided scope.

	fn do_apply_extrinsic(
		uxt: Block::Extrinsic,
		is_inherent: bool,
		check: impl FnOnce(
			Block::Extrinsic,
			&Context,
		) -> Result<CheckedOf<Block::Extrinsic, Context>, TransactionValidityError>,
	) -> ApplyExtrinsicResult {
		sp_io::init_tracing();
		let encoded = uxt.encode();
		let encoded_len = encoded.len();
		sp_tracing::enter_span!(sp_tracing::info_span!(
			"apply_extrinsic",
			ext=?sp_core::hexdisplay::HexDisplay::from(&encoded)
		));

		let uxt = <Block::Extrinsic as codec::DecodeLimit>::decode_all_with_depth_limit(
			MAX_EXTRINSIC_DEPTH,
			&mut &encoded[..],
		)
		.map_err(|_| InvalidTransaction::Call)?;

		// Verify that the signature is good.
		let xt = check(uxt, &Context::default())?;

		let dispatch_info = xt.get_dispatch_info();

		if !is_inherent && !<frame_system::Pallet<System>>::inherents_applied() {
			Self::inherents_applied();
		}

		// We don't need to make sure to `note_extrinsic` only after we know it's going to be
		// executed to prevent it from leaking in storage since at this point, it will either
		// execute or panic (and revert storage changes).
		<frame_system::Pallet<System>>::note_extrinsic(encoded);

		// AUDIT: Under no circumstances may this function panic from here onwards.

		let r = Applyable::apply::<UnsignedValidator>(xt, &dispatch_info, encoded_len)?;

		// Mandatory(inherents) are not allowed to fail.
		//
		// The entire block should be discarded if an inherent fails to apply. Otherwise
		// it may open an attack vector.
		if r.is_err() && dispatch_info.class == DispatchClass::Mandatory {
			return Err(InvalidTransaction::BadMandatory.into());
		}

		<frame_system::Pallet<System>>::note_applied_extrinsic(&r, dispatch_info);

		Ok(r.map(|_| ()).map_err(|e| e.error))
	}
