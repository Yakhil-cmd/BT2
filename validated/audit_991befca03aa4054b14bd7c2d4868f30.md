### Title
Signed order/price messages validated via `validateSignedMessage` have no deadline/expiry enforcement, enabling stale-priced trade execution - ([File: signed_message.js], [File: test/samples/order_book_exchange.oscript])

### Summary
Obyte's off-chain signed-message primitive (`signed_message.signMessage`/`validateSignedMessage`, exposed to oscript via `is_valid_signed_package`) is the building block that AA authors use to implement price-carrying orders that get matched on-chain by an AA trigger, analogous to Uniswap's `exactInput` swap call in the reported USSD bug. Just like the reported `UniV3SwapInput` function that commented out `deadline`, the core signed-message validator never checks any time-based expiry on the message, so a stale, previously-signed order (fixing a price) can be posted and executed long after it was created, at a price that no longer reflects the market.

### Finding Description
`validateSignedMessage` in [1](#0-0)  accepts an optional `timestamp` field in the signed-message envelope (`ValidationUtils.hasFieldsExcept(objSignedMessage, ["signed_message", "authors", "last_ball_unit", "timestamp", "version"])`), but that field is never read or compared against the current time anywhere in the function. The only "freshness" anchor available is `last_ball_unit`, which is used solely to fetch the signer's definition and MCI, not to bound how long a signed message remains valid: [2](#0-1) .

The shipped `order_book_exchange.oscript` sample demonstrates exactly this pattern being used to build an on-chain limit-order exchange: users off-chain sign `order1`/`order2` messages containing `sell_asset`, `buy_asset`, `sell_amount` and `price`, and the AA validates them purely with `is_valid_signed_package(...)` before executing the trade, with an explicit comment acknowledging the missing check: `// to do check expiry` [3](#0-2) . There is no oscript primitive or core check that rejects an order whose `price` was fixed at a stale point in time; any address can trigger execution of an old, still-validly-signed order at any point in the future, as long as the signer's balance (`var[$sell_key]`) still covers it.

### Impact Explanation
Because the fixed `price` in the signed order is never bound to a deadline, an old counter-order can be matched long after market conditions changed, forcing the signer to sell an asset far below (or buy far above) its current value — the same "undesirable swap / undervalued rebalancing" impact described in the original report. Any user who deposits balance and posts a signed order into such an AA is exposed to indefinite exploitation of that order at an outdated price, i.e., concrete unauthorized-value extraction/fund loss for the order's signer.

### Likelihood Explanation
Likelihood is elevated by the fact that this pattern is not an isolated user mistake but the officially provided reference implementation and template for building order-book/exchange AAs on Obyte, and the core signed-message validator provides no built-in guardrail (no mandatory or default expiry check) that would prevent this class of AA from being deployed and exploited as-is.

### Recommendation
- Add explicit support for an expiry/deadline in the signed-message schema (e.g., a required `timestamp` or `expiry_mci` field) and have `validateSignedMessage` reject messages whose declared timestamp/MCI is older than a caller-specified bound, similar to `min_mci`/`max_mci` bounds already used for data feeds in `readDataFeedValueByParams` [4](#0-3) .
- Update the reference `order_book_exchange.oscript` template to implement the "to do check expiry" comment, comparing `trigger.data.order.expiry` (or similar) against `timestamp`/`this_address`'s MCI before executing a match, so downstream integrators copying this template are not exposed to stale-price execution.

### Proof of Concept
1. Alice signs an order (`price = P0`, `sell_amount = X`) at time T0 using `signMessage`, deposits `X` of the sell asset into the order-book AA balance.
2. Market price of the asset moves substantially after T0.
3. At time T1 (much later), Bob crafts a matching counter-order with a favorable price relative to `P0` and posts both signed packages as `trigger.data.order1`/`order2`.
4. The AA's `if` condition only checks `is_valid_signed_package` (signature/definition validity) and available balance — never checks how old the order is — so the trade executes at the stale `P0`, letting Bob buy Alice's asset far below current market value.
