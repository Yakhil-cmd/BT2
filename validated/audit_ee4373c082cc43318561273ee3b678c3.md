### Title
Stack-scoped `ApiClient` tokens can read CCMenu status for any stack, bypassing the token's stack scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` implements a scoping invariant: an `ApiClient` token that is bound to a single stack (`current_api_client.stack_id?`) must only be able to touch that stack. `Shipit::Api::CCMenuController` re-implements its own `stack` lookup that ignores this scoping entirely, breaking the binding "a stack a token authorises versus a stack it touches," analogous to the PoolTogether report's core defect: a code path that checks one condition (permission bit) while skipping the other condition (actual scope/ownership match) that the security model assumes always holds together.

### Finding Description
`BaseController` defines the canonical, scope-respecting lookup: [1](#0-0) 

Every other API controller (stacks, tasks, deploys, rollbacks, etc.) resolves `stack` through this `stacks.from_param!` helper, so a token created with `stack_id` set can only resolve stacks matching that ID.

`CCMenuController`, however, overrides `stack` with a direct, unscoped lookup: [2](#0-1) 

The only authorization gate applied is `require_permission :read, :stack`, which is implemented purely as a permission-bit check with no relation to the specific stack being requested: [3](#0-2) 

So the invariant "`token.stack_id == requested_stack.id` (or token is unscoped)" — enforced everywhere else via `BaseController#stacks` — is silently dropped in this one controller. Any valid token carrying `read:stack` permission, regardless of the `stack_id` it was created with, can fetch CI/build status (`show` action) for any stack in the Shipit installation by simply supplying a different `stack_id` in the URL, exactly the way the TWAB report's `_toDelegate != SPONSORSHIP_ADDRESS` branch skip let one code path diverge from the invariant that the rest of the system depended on.

### Impact Explanation
This is an unauthenticated-boundary-scoped read of stack state: a token intentionally minted for one stack (e.g. embedded in a third-party CI dashboard widget, as created by `CCMenuUrlController`, or any admin-issued stack-scoped `read:stack` token) can be replayed against `/api/<other_stack>/ccmenu.xml?token=...` to read deploy/build status of stacks the token holder was never meant to access. This matches the in-scope "High" impact category: unauthenticated read of stack state / deploy output, since the requested stack was never authorized for that specific token.

### Likelihood Explanation
Any party who has captured a legitimate `read:stack`-scoped CCMenu token (these are embedded in query strings, sent to third-party CI aggregators, logged in server access logs, etc., by design of `CCMenuUrlController`) can trivially probe other stack IDs/slugs with no additional privileges — no session, no GitHub credentials, and no elevated permission needed beyond the one already-issued token.

### Recommendation
Make `CCMenuController#stack` go through the same scoped lookup as every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it inherits `BaseController#stacks`, which restricts resolution to `current_api_client.stack_id` when the token is stack-scoped.

### Proof of Concept
1. An administrator visits stack A's page, which via `CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` with `permissions: %w[read:stack]` and exposes its `authentication_token` in a CCMenu URL: [4](#0-3) 
2. Assume (as the scoping mechanism in `BaseController` implies is supported elsewhere in the app) that a token is also created/available with `stack_id` bound specifically to stack A.
3. An attacker who obtains this token (e.g., from a third-party CI-status page, logs, or Referer header) issues:
   `GET /api/stack-b/ccmenu.xml?token=<stolen_token>`
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the lookup succeeds for stack B even though the token was only ever authorized for stack A, and the attacker receives stack B's deploy/build status in the XML response — data they were never granted `read:stack` access to for that specific stack.
