### Title
Malicious asset definer can permanently freeze all holders' funds of a `cosigned_by_definer` asset by self-redefining an unsatisfiable address definition - (File: `validation.js`, `divisible_asset.js`, `definition.js`)

### Summary
An asset can be created with `cosigned_by_definer=true`, which forces the `definer_address` to be a co-signing author on *every* future transfer of that asset, forever. Address definitions in Obyte can be freely changed by their owner at any time via an `address_definition_change` message, with no restriction preventing the new definition from being permanently unsatisfiable (e.g. a `sig` clause referencing a pubkey the definer does not control). Since nothing forces the definer to keep a usable definition, the definer can unilaterally and permanently brick their own signing capability, which — because of the `cosigned_by_definer` requirement — permanently freezes every other holder's balance of that asset with no recovery path. This mirrors the referenced report's root cause: a single counterparty's unilateral, irreversible action against an object they control breaks a mandatory verification step that all other users' fund-recovery paths depend on.

### Finding Description
When an asset is defined with `cosigned_by_definer: true`, every payment message transferring that asset must include the `definer_address` as one of the authors, both at validation time and at composition time: [1](#0-0) [2](#0-1) 

This requirement is permanent — there is no expiry, no fallback, and no alternate spending path that bypasses it. It relies implicitly on the definer_address always being able to produce a valid signature satisfying its own address definition.

However, address definitions are mutable by their owner at any point via an `address_definition_change` message, which is validated purely syntactically (a valid chash/valid address), with no check on whether the new definition is actually satisfiable by anyone: [3](#0-2) 

The new definition is written to storage unconditionally once stable: [4](#0-3) 

There is nothing stopping the definer from changing their address's definition to something they cannot satisfy (e.g. a `sig` clause with a pubkey whose private key they discard, or a definition referencing a nonexistent/unreachable inner address). Once that new definition is stable, `validateAuthentifiers`/`validateAuthor` will simply reject every future unit signed by that address because no valid signature can ever be produced: [5](#0-4) 

Because `cosigned_by_definer` unconditionally requires this now-permanently-unusable address as co-author on every transfer, **all** holders of the asset — not just the definer — lose the ability to move their balances, exactly as in the referenced report where a single party's irreversible self-inflicted action (burning the NFT) broke a mandatory ownership check relied upon by every other participant's exit path.

### Impact Explanation
This permanently freezes every holder's balance of the affected asset. There is no emergency/alternate transfer path in `validatePaymentInputsAndOutputs` that omits the `cosigned_by_definer` check, and no mechanism to force a definer to restore a usable definition. This is a permanent, protocol-level fund-freezing griefing vector reachable by the asset issuer/definer — a party explicitly listed as an unprivileged actor in scope, matching the "AA fund loss or freezing" / permanent lock impact class of the original finding.

### Likelihood Explanation
Any asset issuer can set `cosigned_by_definer: true` when defining an asset (a normal, supported configuration), and can trivially self-destruct their own signing capability at any later time by posting a syntactically valid but unsatisfiable `address_definition_change`. No special privileges beyond being the asset's own definer are required, and the action is irreversible once the definition-change unit becomes stable. This makes the attack straightforward to execute by a malicious or careless definer against all other holders of the asset.

### Recommendation
- Disallow (or specially handle) `address_definition_change` for addresses that are the `definer_address` of any `cosigned_by_definer` asset, or
- Add an escape hatch to the `cosigned_by_definer` check (e.g., allow transfers without the definer's co-signature after the definer's address definition is proven permanently unusable / after a timeout), or
- Require `cosigned_by_definer` assets to reference the definer via a construct that supports guardianship/recovery, so a self-inflicted or malicious definition change cannot permanently block all holders.

### Proof of Concept
1. Definer issues asset `A` with `cosigned_by_definer: true`, `is_transferrable: true`, `issued_by_definer_only: false` (see field checks in `validation.js` `validateAssetDefinition`, lines 2725-2827).
2. Holders `H1`, `H2`, ... receive units of asset `A` in normal transfers, each validated per [1](#0-0) , requiring the definer as co-author.
3. Definer posts an `address_definition_change` message for their own address (`validation.js` lines 1719-1746) setting a new `definition_chash` corresponding to a definition such as `['sig', {pubkey: <random_unowned_pubkey>}]` (or any construct the definer cannot satisfy). This passes validation since only syntactic checks are performed.
4. Once this unit is stable, `storage.readDefinitionByAddress` returns the new, unsatisfiable definition for the definer's address; any future unit purporting to be authored by the definer will fail signature verification in `validateAuthentifiers` (`validation.js` lines 1190-1208), so the definer can never again act as a valid author.
5. Any holder `Hn` attempting to transfer asset `A` must include the definer as co-author (`validation.js` lines 2112-2113, `divisible_asset.js` lines 247-248); this is now permanently impossible, so no `A` balance can ever be transferred again by anyone.
