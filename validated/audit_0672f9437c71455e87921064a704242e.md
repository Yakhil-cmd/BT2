### Title
Unauthenticated cross-organization webhook forgery bypasses signature verification and forges CI/push status for arbitrary repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate the HMAC **using an unverified field from the request body** (`repository.owner.login` / `organization.login`), while the handlers that actually act on the webhook (`StatusHandler`, `PushHandler`, pull-request handlers) use a **different, equally unverified field** (`repository.full_name`/`sha`) to decide what to write. Because `verify_webhook_signature` returns `true` unconditionally when the selected organization's `webhook_secret` is blank/nil (a documented, optional setting), an attacker can pick any configured organization that has no webhook secret to skip signature verification entirely, then forge a payload whose `repository.full_name`/`sha` targets a completely different, unrelated (and properly secured) repository/stack.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration purely from the JSON body, before any authentication occurs: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` bypasses verification entirely if that organization's `webhook_secret` is not configured: [3](#0-2) 

The `webhook_secret` is explicitly documented as optional in a multi-organization deployment (`docs/setup.md`, "Using Multiple Github Applications" section, and `config/secrets.development.example.yml`), meaning real deployments plausibly have at least one configured organization with `webhook_secret: nil`.

Once `verify_signature` passes (`head(422)` only fires when `verified` is false), the raw body is re-parsed and dispatched to handlers, which key off **different** fields than the one used to select the verifying secret: [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler` is even more permissive: it does not check the repository at all, only the commit `sha`, meaning it will update the status of any matching commit across every stack/repository tracked by the Shipit instance: [7](#0-6) 

`create_status_from_github!` feeds into `Commit#add_status`, which schedules the merge queue processing (`stack.schedule_merges`) whenever the new status is `pending` or `success`: [8](#0-7) 

This is the binding break: **the organization that authenticated the request (via `repository.owner.login` selecting a `webhook_secret`, which may be absent) ≠ the repository/commit actually written to (via `repository.full_name`/`sha`, taken from the same unauthenticated body)**. Signing/verification is scoped per-organization but the write target is scoped by an independent, unverified field, so any organization lacking a secret becomes an unauthenticated proxy to inject events for any other organization's repositories/commits.

### Impact Explanation
An unauthenticated attacker who knows (a) that at least one organization configured on the Shipit instance has no `webhook_secret`, and (b) the SHA of a commit belonging to a victim stack, can POST a forged `status` (or `push`) webhook that:
- Bypasses signature verification entirely (`verify_webhook_signature` short-circuits to `true`).
- Creates a fabricated successful CI status on an arbitrary victim commit (`StatusHandler` has no repository scoping at all).
- Triggers `stack.schedule_merges` → `ProcessMergeRequestsJob`, which can cause the merge queue to merge pull requests believing CI has passed — an **unauthorized merge**, matching the Critical impact bar defined by the rules ("unauthorized deploy, rollback or merge").
- Alternatively (via `push`), triggers `GithubSyncJob`/`stack.sync_github` for an arbitrary tracked repository, using Shipit's own GitHub App credentials to sync/act on that repo's data without the caller having any legitimate relationship to it.

### Likelihood Explanation
Likelihood is Medium: it requires (1) the operator to run Shipit in the documented multi-organization mode with at least one organization missing a `webhook_secret` (an explicitly supported, optional configuration), and (2) the attacker to know or guess a target commit SHA on a tracked stack (SHAs are often public, e.g., visible in a public GitHub repo or Shipit's own UI). No credentials, session, or `ApiClient` token are required — the endpoint is unauthenticated by design (`/webhooks`), and the identity check is entirely payload-driven and thus attacker-controlled.

### Recommendation
- Do not let an attacker-supplied field select which secret/config is used to authenticate the message. Verify the signature against every configured organization's secret (or otherwise ensure the payload cannot self-select a "no-secret" bypass), and reject the request unless a secret-backed verification succeeds.
- If an organization is configured without a `webhook_secret`, treat webhooks attributed to it as untrusted for cross-repository or cross-stack effects: `StatusHandler` and `PushHandler` should verify that the resolved repository/stack actually belongs to the organization whose credentials verified the signature, not merely match a `sha` or `full_name` string taken from the same unauthenticated body.
- Consider requiring `webhook_secret` to be mandatory (fail configuration validation) rather than optional when running in multi-organization mode.

### Proof of Concept
Given a Shipit deployment configured with two orgs, e.g. per `test/dummy/config/secrets_double_github_app.yml`-style config, where `OrgNoSecret` has `webhook_secret: nil` and `VictimOrg` has a real secret and owns `VictimOrg/victim-repo` (tracked stack with commit `sha=<victim_sha>` currently pending in the merge queue):

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgNoSecret/whatever" },
  "sha": "<victim_sha>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```

- `repository_owner` resolves to `"OrgNoSecret"` → `Shipit.github(organization: "OrgNoSecret")` → `webhook_secret` is blank → `verify_webhook_signature` returns `true` regardless of the (absent/garbage) `X-Hub-Signature` header.
- `StatusHandler` looks up `Commit.where(sha: "<victim_sha>")` — with no repository restriction — and marks it as `success`, potentially unblocking `VictimOrg/victim-repo`'s merge queue with a forged status, without ever touching `VictimOrg`'s real webhook secret.

Note: I was unable to fully trace `ProcessMergeRequestsJob`'s exact merge-execution code path within the available indexed context (the tool budget was exhausted before reading `app/jobs/shipit/process_merge_requests_job.rb`), so the precise mechanics of the merge action itself (e.g., additional gating checks before an actual GitHub merge API call) could not be independently confirmed; this should be verified in a live session before treating the "unauthorized merge" consequence as fully proven end-to-end.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
