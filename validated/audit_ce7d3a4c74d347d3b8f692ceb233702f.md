### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method inherited from `Shipit::Api::BaseController` in a way that removes the scoping check that binds an `ApiClient` token to the single stack it was authorized for. This lets any valid API token (including CCMenu tokens auto-created for a specific stack) read deploy status for arbitrary stacks by simply changing the `stack_id` in the request path, breaking the "stack a token authorizes" vs "stack it touches" binding.

### Finding Description
`BaseController` establishes the authorization boundary between a token and the stacks it may act on: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the client is scoped to a stack, and `stack` resolves the requested id only within that restricted relation, i.e. `stacks.from_param!(params[:stack_id])`.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves against the full, unscoped `Stack` collection: [2](#0-1) 

It also overrides `authenticate_api_client` to authenticate solely via a `token` query parameter instead of Basic Auth: [3](#0-2) 

The `show` action uses this unscoped `stack` to render deploy state: [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string; it does not re-validate that the requested `stack_id` matches the token's `stack_id`, because the scoping enforcement lives entirely inside `BaseController#stacks`/`#stack`, which `CCMenuController` bypasses.

`ApiClient` tokens are commonly created pre-scoped to one stack, most visibly by `CCMenuUrlController`, whose generated URL embeds the token as a query parameter exactly in the form the (overridden) `authenticate_api_client` expects: [5](#0-4) 

This binding break is directly analogous to the report's root cause: a value meant to gate/limit an operation (`highWaterMark`, here the token's `stack_id`) is not correctly enforced at the point the operation is performed, silently expanding what the caller can touch relative to what it was authorized for.

### Impact Explanation
Any holder of a valid, even narrowly stack-scoped, `ApiClient` token (e.g. a CCMenu URL leaked or shared for one stack, or any token with `read:stack` permission created for a single stack) can query `/api/<other_stack>/ccmenu.xml?token=<their_token>` and read deploy status (last deploy id, running state, ended_at) for every other stack managed by the Shipit instance, not just the one it was issued for. This is an unauthorized read of stack/task state outside the token's granted scope, matching the "High - ... unauthenticated read of stack state, task streams or deploy output" impact category, since the disclosure occurs despite an intended per-stack authorization boundary.

### Likelihood Explanation
High. No special privileges, session, or webhook secret are required — only possession of any valid `ApiClient` authentication token, including ones that are routinely generated and embedded in plaintext CCMenu URLs by `CCMenuUrlController`. The attack is a single unauthenticated-boundary GET request differing only in the `stack_id` path segment.

### Recommendation
Make `CCMenuController#stack` honor the same scoping as `BaseController`, e.g. reuse `stacks.from_param!(params[:stack_id])` (or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`) instead of calling `Stack.from_param!` directly, so a stack-scoped token can never resolve a stack outside its `stack_id`.

### Proof of Concept
1. Have a user visit a stack's CCMenu URL, which creates a stack-scoped `ApiClient` (`stack: <stack A>` is implied only by usage context, permission `read:stack`) and returns a token embedded in the URL query string, per `CCMenuUrlController#client`/`#fetch`.
2. As an attacker in possession of that token (e.g. intercepted URL, shared CI dashboard, etc.), send:
   `GET /api/<stack-B-id>/ccmenu.xml?token=<token-issued-for-stack-A>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate(params[:token])`).
4. `CCMenuController#stack` resolves `stack-B` via unscoped `Stack.from_param!`, ignoring that the token's `stack_id` corresponds to stack A.
5. The response renders stack B's `deploys_and_rollbacks.last` deploy status, disclosing deploy state for a stack the token was never authorized to see.
