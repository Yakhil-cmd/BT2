### Title
Unbounded access-key iteration in `ViewAccessKeyList` RPC query, no pagination unlike `ViewState` - ([File: runtime/runtime/src/state_viewer/mod.rs])

### Summary
The `view_access_key_list` / `EXPERIMENTAL_view_access_key_list` JSON-RPC query path is served by `TrieViewer::view_access_keys`, which iterates and collects **every** access key of the target account into a `Vec` with no page-size or byte-size cap, unlike the analogous `view_state` code path which enforces `MAX_VIEW_STATE_PAGE_ITEMS`/`MAX_VIEW_STATE_PAGE_BYTES` limits. An attacker who controls (or creates) an account with a very large number of access keys can make a single unauthenticated RPC query force the node to iterate and materialize the full key set, consuming unbounded CPU/memory per request.

### Finding Description
The RPC handler `view_access_key_list_local` in `chain/jsonrpc/src/lib.rs` forwards `QueryRequest::ViewAccessKeyList { account_id }` to the view client/runtime: [1](#0-0) 

That request is handled in `chain/chain/src/runtime/mod.rs`, which calls `self.view_access_keys(...)` and collects the full result into `AccessKeyInfoView`s with no limit or pagination parameters: [2](#0-1) 

The actual trie work happens in `TrieViewer::view_access_keys`, which does a raw prefix iteration over the account's access-key trie subtree and `.collect::<Vec<_>>()`s every entry, with no `limit`, `after_key`, or item/byte caps of any kind: [3](#0-2) 

This is in stark contrast to the sibling `view_state` implementation in the same file, which explicitly introduces pagination parameters (`limit`, `after_key`) and hard per-page caps (`MAX_VIEW_STATE_PAGE_ITEMS = 10_000`, `MAX_VIEW_STATE_PAGE_BYTES = 50_000`) specifically to bound work per RPC call: [4](#0-3) 

There is no equivalent cap for access keys, and the `RpcViewAccessKeyListRequest`/`RpcViewAccessKeyListResponse` types carry no pagination fields at all: [5](#0-4) 

An unprivileged attacker can grow an account's key count arbitrarily by repeatedly submitting `AddKeyAction` transactions. `action_add_key` in `runtime/runtime/src/access_keys.rs` only rejects duplicate public keys; it enforces no maximum number of keys per account, only charging incremental storage cost (i.e., the attacker just needs enough balance to cover storage rent for however many keys they want to add): [6](#0-5) [7](#0-6) 

Once such an account exists (e.g., with hundreds of thousands of keys), any unauthenticated caller can send a single `view_access_key_list`/`EXPERIMENTAL_view_access_key_list` query against a public RPC node naming that account, causing the node to perform a full unbounded trie iteration and heap-allocate a `Vec` sized to the entire key set for that single request — turning one query into unbounded work, exactly the invariant violation the target describes (listing endpoints should paginate/bound work, as `view_state` does, but `view_access_keys` does not).

Note: the literal function named in the prompt, `start_http_for_readonly_debug_querying`, exists in `chain/jsonrpc/src/lib.rs` but is unrelated to access-key listing — access-key listing is served through the `view_access_key_list_local` handler and `TrieViewer::view_access_keys`, which is the actual vulnerable code path traced above.

### Impact Explanation
Each such query drives disk/trie iteration and in-memory `Vec` growth proportional to the number of keys on the targeted account, with no per-request cap. A modest number of concurrent requests against a large-key account can cause excessive CPU usage, large heap allocations, and slow/blocked RPC worker threads, degrading or crashing the public RPC node (or causing memory pressure across shared services). This matches the "High – RPC node crash or unavailability" impact class: an unbounded, attacker-triggerable resource-consumption primitive reachable by any unauthenticated caller.

### Likelihood Explanation
- No special privileges are needed: any funded account can call `AddKey` repeatedly to accumulate a very large key set (bounded only by their willingness to pay incremental storage cost, not by any protocol-enforced maximum).
- Once the account exists, the query itself is unauthenticated and requires no fees, and can be repeated indefinitely.
- The lack of pagination is a straightforward code-path gap (contrasted directly with the paginated `view_state` sibling in the same file), making this reliably reproducible rather than probabilistic.

### Recommendation
Add pagination/limits to `TrieViewer::view_access_keys` (and the `ViewAccessKeyList` request/response types) analogous to `view_state`'s `limit`/`after_key`/`MAX_VIEW_STATE_PAGE_ITEMS`/`MAX_VIEW_STATE_PAGE_BYTES` mechanism: cap the number of keys and/or bytes returned per call, support a resumption cursor (`after_key`), and/or enforce a protocol-level maximum number of access keys per account to bound worst-case iteration cost regardless of RPC parameters.

### Proof of Concept
Integration test plan (e.g., in `chain/jsonrpc/jsonrpc-tests/tests/rpc_query.rs`):
1. In a test genesis/runtime, create an account and issue N `AddKeyAction` transactions (e.g., N = 200,000) to accumulate a very large number of access keys, or directly seed the test store with that many access-key trie entries to avoid excessive test runtime.
2. Send an unauthenticated `view_access_key_list` / `EXPERIMENTAL_view_access_key_list` RPC query for that account.
3. Assert that the response either returns within a bounded time/memory envelope (paginated) or that the server returns a typed error (e.g., a new `TooManyKeys`/`InternalError` variant) rather than allocating a `Vec` sized to all N keys in one call.
4. As a regression guard, assert CPU/time bound (e.g., request must complete under a fixed millisecond budget) and that memory allocation for the response is bounded independent of N.

    pub fn view_access_keys(
        &self,
        state_update: &TrieUpdate,
        account_id: &AccountId,
    ) -> Result<Vec<(PublicKeyHandle, AccessKey)>, errors::ViewAccessKeyError> {
        let prefix = trie_key_parsers::get_raw_prefix_for_access_keys(account_id);
        let access_keys =
            state_update
                .iter(&prefix)?
                .map(|key| {
                    let key = key?;
                    let key_handle = parse_key_handle_from_access_key_key(&key, account_id)
                        .map_err(|_| errors::ViewAccessKeyError::InternalError {
                            error_message: "Unexpected invalid access key from iterator"
                                .to_string(),
                        })?;
                    if let Some(_index) =
                        parse_nonce_index_from_gas_key_key(&key, account_id, &key_handle).map_err(
                            |_| errors::ViewAccessKeyError::InternalError {
                                error_message: "could not parse nonce index".to_string(),
                            },
                        )?
                    {
                        // This is a gas key nonce, skip it.
                        return Ok(None);
                    }
                    let access_key = near_store::get_access_key_by_handle(
                        state_update,
                        account_id,
                        &key_handle,
                    )?
                    .ok_or_else(|| {
                        near_primitives::errors::StorageError::StorageInconsistentState(format!(
                            "iterator yielded an access-key trie key with no value: {key_handle}"
                        ))
                    })?;

                    Ok(Some((key_handle, access_key)))
                })
                .filter_map_ok(|x| x)
                .collect::<Result<Vec<_>, errors::ViewAccessKeyError>>();
        access_keys
    }

    account: &mut Account,

    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),

        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {

            fee_config,

            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;

        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())

fn add_regular_key(

    state_update: &mut TrieUpdate,

    public_key: &PublicKey,

    let mut access_key = access_key.clone();

    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
