### Title
Cross-organization webhook confusion — signature verified against payload-declared organization while the affected stack is resolved from a different payload-declared repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Multi-tenant Shipit deployments configure one `webhook_secret` per GitHub organization [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against by reading `repository_owner`, itself derived from the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) . Once the signature passes, the actual event-processing code (e.g. `PushHandler`) resolves the target `Repository`/`Stack` from a *different* field of the same payload: `repository.full_name` [3](#0-2) [4](#0-3) .

### Finding Description
The equality that should hold is:

`organization used to verify the HMAC signature == organization that owns the repository whose stacks get mutated`

Nothing in the controller enforces this. `repository_owner` (used to pick `Shipit.github(organization: repository_owner)` and thus the HMAC secret) and `repository.full_name` (used later by `Handler#repository_name`/`Repository.from_github_repo_name` to find the `Stack`) are two independent fields read from the same attacker-controlled JSON body, and are never cross-checked against each other [5](#0-4) [6](#0-5) .

A tenant that legitimately owns a Shipit-configured GitHub organization (and therefore legitimately possesses that organization's own `webhook_secret`, configured server-side per `TOP_LEVEL_GH_KEYS`/`github_app_config` [7](#0-6) [8](#0-7) ) can sign a payload with `repository.owner.login`/`organization.login` set to their own org (so `verify_signature` succeeds using their own secret), while setting `repository.full_name` to a *different* organization's repository. `PushHandler#process` will then call `stack.sync_github(expected_head_sha: params.after)` on the victim organization's stack [9](#0-8) , and other handlers (pull request opened/closed/labeled, etc.) similarly resolve `repository` from `params.repository.full_name` independent of the org used for signature verification [10](#0-9) .

This is a direct analog of the reported bug class: the report flags a missing invariant check between a value that is trusted/fixed (the immutable `zapTreasury`/token addresses) and one that is used elsewhere without re-validation. Here the trust anchor is "the organization whose secret validated this request," and the value acted upon without re-validation is "the repository/stack the request is allowed to mutate" — exactly the binding class called out in the rules ("an organization that authenticated versus the repository that is written").

### Impact Explanation
This allows any organization onboarded to a shared/multi-tenant Shipit instance to forge webhook events (push syncs, PR-driven review-stack creation/archival, label-based provisioning) against stacks belonging to a different organization it has no legitimate access to, i.e. cross-repository/cross-tenant writes triggered by data outside the authenticated organization's own boundary. That matches the "Critical … cross-repository writes" impact bucket.

### Likelihood Explanation
Requires only that the attacker be a legitimate customer/organization of a multi-organization Shipit deployment (has their own valid `webhook_secret`), which is a realistic and commonly supported configuration (`github_organizations`, `github_app_config` explicitly support multiple orgs sharing one Shipit instance) [11](#0-10) . No GitHub App private key, `ApiClient` token, or victim's secret is needed — only the attacker's own, unprivileged webhook credentials for their own org, which they are meant to have.

### Recommendation
After verifying the signature against `repository_owner`, re-derive/validate that any repository the handler will act on (`repository.full_name`, `organization.login`) belongs to the same organization that was used to select the webhook secret, rejecting (422) any payload where these disagree. Alternatively, resolve the `Repository`/`Stack` first and use the repository's own persisted `owner` (not payload-controlled data) to pick the `GitHubApp`/secret for verification, ensuring authentication and the acted-upon resource are always bound to the same organization.

### Proof of Concept
1. Shipit instance configured for two tenants, `orgA` and `orgB`, each with their own `webhook_secret` (multi-org config) [8](#0-7) .
2. Attacker controls `orgA` and knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
   - `repository.owner.login` = `"orgA"` (so `repository_owner` resolves to `orgA`, and the HMAC is computed/verified with `orgA`'s secret) [5](#0-4) 
   - `repository.full_name` = `"orgB/victim-repo"`, `ref` = `refs/heads/master`, `after` = attacker-chosen SHA.
4. Attacker computes `X-Hub-Signature` with `orgA`'s secret and POSTs to `/github/webhooks`.
5. `verify_signature` passes because it only checks the signature against `orgA` [12](#0-11) .
6. `PushHandler#process` looks up `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github(expected_head_sha: ...)` on `orgB`'s stack, even though the request was never authenticated as coming from `orgB` [9](#0-8) .

Note: I could not fully trace whether `GithubSyncJob`/`sync_github` performs any additional, independent authorization check that might mitigate impact (e.g., re-fetching from GitHub API using the correct org's credentials and failing safely) — this would need to be confirmed by reviewing `app/jobs/shipit/github_sync_job.rb` and `Stack#sync_github` in full, which the index did not surface in this session.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
