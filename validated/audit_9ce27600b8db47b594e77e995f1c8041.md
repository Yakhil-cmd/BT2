### Title
AA/definition `timestamp` and `mci` builtins are derived from an attacker-chosen `last_ball_unit`, letting a trigger sender fabricate a favorable past execution time - ([File: formula/evaluation.js])

### Summary
Obyte AA formulas and address-definition conditions expose `timestamp` and `mci` builtins that resolve to `objValidationState.last_ball_timestamp` / `last_ball_mci`, which are simply the timestamp/MCI of whatever `last_ball_unit` the *author of the triggering unit* declares in the unit header [1](#0-0) . Validation only requires that this value not "retreat" relative to the values already implied by the parent units the same author chose to reference [2](#0-1) [3](#0-2) . Nothing in `validate()` requires `last_ball_mci`/`last_ball_timestamp` to be close to the network's actual current MC tip or to wall-clock time. A user who builds parent selection differently from the reference composer (which normally always tries to reference the freshest free units, see `parent_composer.js`) can therefore choose an old, still-valid, already-stable `last_ball_unit`, and thereby make an AA see an arbitrarily old `timestamp`/`mci` while their own unit's `timestamp` field is set to the real current time (which only has an upper-bound "not too far in the future" check) [4](#0-3) .

### Finding Description
The bug class in the external report is: a value used to compute a financial payoff is claimed by an interested party and never checked against the real current time, so the party can pick a historically favorable value.

In ocore, `timestamp` and `mci` are first-class oscript primitives usable both in AA formulas and in address-definition spending conditions:
- In AA formula evaluation, `timestamp` returns `new Decimal(objValidationState.last_ball_timestamp)` and `mci` returns `objValidationState.last_ball_mci` [1](#0-0) .
- `data_feed[[...]]` lookups performed from within an AA also use `mci` (i.e., the same `last_ball_mci`) as the upper bound for which oracle-posted feed values are visible: `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, objValidationState.last_ball_timestamp, ...)` [5](#0-4) .
- The same `timestamp`/`mci` operators are also available in address-definition authentifiers (spending conditions) and resolve identically to `last_ball_timestamp`/`last_ball_mci` [6](#0-5) .

`last_ball_timestamp`/`last_ball_mci` are set during validation purely from the `last_ball_unit` field the unit's author put in the unit:
```
objValidationState.last_ball_mci = objLastBallUnitProps.main_chain_index;
objValidationState.last_ball_timestamp = objLastBallUnitProps.timestamp;
``` [3](#0-2) 

The only constraint imposed on this value is a monotonicity check against the author's own chosen parents:
```
function readMaxParentLastBallMci(handleResult){
    storage.readMaxLastBallMci(conn, objUnit.parent_units, function(max_parent_last_ball_mci) {
        if (max_parent_last_ball_mci > objValidationState.last_ball_mci)
            return callback("last ball mci must not retreat, parents: "+objUnit.parent_units.join(', '));
        handleResult(max_parent_last_ball_mci);
    });
}
``` [2](#0-1) 

This check only compares against the `last_ball_mci` *implied by the parent units the composer itself picked* — it does not compare against the network's actual current main-chain tip or against wall-clock time. The unit's own `timestamp` field is checked only for an upper bound ("not too far into the future") and for monotonic non-decrease versus its DAG parents' own timestamps [4](#0-3) [7](#0-6)  — there is no check tying `objUnit.timestamp` (or the current wall clock) to `last_ball_timestamp`.

The standard composer (`composer.js`/`parent_composer.js`) always tries to pick the freshest free parent units and thus a fresh `last_ball_unit` [8](#0-7) , but this is composer *policy*, not a validation *rule*. Any unit author bypassing the reference composer (a custom wallet, script, or hand-crafted joint) can instead choose old, stable, still-existing DAG parent units and a correspondingly old `last_ball_unit`, as long as it does not retreat relative to those (also old) chosen parents.

This directly enables AA logic that relies on `timestamp`/`mci`/`data_feed` for time-sensitive settlement to be manipulated, e.g., in the shipped sample oscripts:
```
{ // record blackswan event
  if: `{ trigger.data.blackswan AND !var['blackswan'] AND data_feed[[oracles=... feed_name='GBYTE_USD_MA']] < 25 AND timestamp < 1556668800 }`,
  ...
}
...
if (timestamp < 1556668800)
    bounce('wait for maturity date');
``` [9](#0-8) 

and the option contract sample which decides the winning outcome based on `data_feed[...]` and `timestamp` at trigger time [10](#0-9) .

### Impact Explanation
An attacker who trigers such an AA (or spends via a definition using `timestamp`/`mci` timelocks) can manufacture a unit whose `last_ball_unit` points to an old, already-stable point in DAG history where a data feed value or elapsed time window was favorable to them (e.g., before a maturity date, or before an unfavorable price update was published), and submit it "now." Because ocore only checks that the chosen `last_ball_mci` doesn't retreat relative to the chosen (also old) parents — not that it reflects real, current network state — the AA/definition will evaluate as if it were executing at that earlier point in time, even though real-world time and on-chain data have since moved past it. This can:
- Freeze or lock AA funds in a wrong permanent state (e.g., incorrectly setting a `blackswan`/`winner` state variable based on stale conditions, permanently affecting all future users of the AA).
- Allow unauthorized/early spending under `timestamp`/`mci` address-definition conditions intended to enforce vesting or time-locks.
- Cause AA fund loss for other legitimate participants who relied on the AA's time-based logic reflecting real elapsed time.

This matches the "AA fund loss or freezing" and "unauthorized spending" impact categories.

### Likelihood Explanation
Exploitation requires only that the attacker construct a unit outside of the standard composer's automatic parent/last-ball selection (a single custom-composed unit, no special privileges, no reliance on a malicious node/hub) and that suitable old, valid, still-referenceable parent/last-ball units exist in DAG history (which they always do, since stable history is retained). No cooperation from witnesses, oracles, or other participants is required beyond the historical data already existing on the DAG. This is reachable directly by any unprivileged AA trigger sender or asset spender, matching the "AA trigger sender" actor class permitted by the rules.

### Recommendation
- Add an explicit bound in `validateParents`/`validate()` requiring the chosen `last_ball_mci` (and/or `last_ball_timestamp`) to be within some acceptable distance of the network's actual best/current main-chain tip (e.g., compare against `objValidationState.max_known_mci`, which is already computed at [11](#0-10) , similar to how unit timestamps are checked against wall-clock in [12](#0-11) ).
- Alternatively/additionally, document and enforce that AAs relying on `timestamp`/`mci` for time-sensitive financial logic cannot assume these reflect "current" time, and provide a safer primitive that is bound to the actual current tip rather than the trigger-composer's chosen `last_ball_unit`.

### Proof of Concept
1. An attacker deploys or targets an existing AA using time-sensitive logic like the sample futures/option contracts, which gate financial outcomes on `timestamp < X` / `data_feed[...] < Y` combinations [13](#0-12) .
2. Instead of using the standard composer (`composer.js`, which always fetches the current freshest free parent units and last ball [14](#0-13) ), the attacker crafts a unit by hand, selecting DAG parent units and a `last_ball_unit` that are already stable but correspond to an earlier historical MCI/timestamp — from a period when the relevant `data_feed` value or elapsed-time condition was favorable to them.
3. During validation, `readMaxParentLastBallMci` only rejects the unit if the chosen `last_ball_mci` retreats relative to the (also old) chosen parents' own last-ball mci [2](#0-1) ; since the attacker's parents are self-consistent and old, this check passes.
4. `objValidationState.last_ball_mci`/`last_ball_timestamp` get set from this old `last_ball_unit` [3](#0-2) , and the AA formula's `timestamp`/`mci`/`data_feed[...]` calls evaluate against this stale state [1](#0-0) [5](#0-4) , producing a payoff/state-change decision based on a historical (favorable) condition rather than the true current state — exactly analogous to exercising the Buffer option using a past, unvalidated timestamp.

Note: I was unable to fully verify within the available index whether any additional, less-visible validation elsewhere in the AA-trigger-specific path (`validateAATrigger`) imposes a freshness bound on `last_ball_mci`; a full read of that function (not fully retrievable via the index) would be needed to rule out an additional safeguard. If a Devin session is available, this function should be inspected in full to confirm no such check exists before treating this as fully confirmed.
