### Title
Unfiltered `ENV` fallback in `EnvironmentVariables#interpolate` leaks deploy-host process environment variables into task output - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate` substitutes `$VAR` tokens found in shipit.yml step strings using `@env.fetch(variable) { ENV[variable] }`, falling back to the Shipit deploy host's raw process `ENV` for any variable not present in the stack/task's own hash, with no whitelist check at all. Since shipit.yml steps are attacker-controlled content in a PR, any repository contributor can write a step referencing `$HOME`, `$SSH_AUTH_SOCK`, or any other host env var and have its live value shell-escaped and printed/executed in the task log.

### Finding Description
The intended binding is: *the bytes handed to the shell == the step string as written in shipit.yml with every interpolated value drawn only from the repository's declared `env`/`variable_definitions`*. This is broken because `interpolate` never consults `permit`/`variable_definitions` at all: [1](#0-0) 

`permit` (the whitelist enforcement) is a completely separate method used only to filter the *task-level* `env` hash passed in by a user triggering a deploy/task (`Stack#trigger_task`/`build_deploy` → `definition.filter_envs(env)` → `EnvironmentVariables#permit`, see `app/models/shipit/task_definition.rb:63-65`). It is never invoked on the command-line interpolation path. The command interpolation path is:

- `Command#interpolate_environment_variables` calls `EnvironmentVariables.with(env).interpolate(argument)` for each argument/step string, where `env` is `Command#env` (the merged, already-whitelisted task env plus stack defaults) — see [2](#0-1) .
- `interpolate` is applied per `$word` token found anywhere in the step, and for any token not present as a key in that merged env hash, it silently falls through to the real process `ENV` of the Shipit worker/host and Shellwords-escapes whatever it finds there before splicing it into `@args`, which are then passed to `PTY.spawn` — [3](#0-2) .

Attack flow: an attacker opens a PR to a repository already onboarded to Shipit, adding/editing `shipit.yml` to include a step like `echo $SSH_AUTH_SOCK` or `echo $HOME`. Once merged (or during a task/step definition that a maintainer runs, e.g. custom task definitions, deploy steps, or `links`), when that step is executed by `Command#start`, `$SSH_AUTH_SOCK` is not a key in `Command#env` (it's not declared in `variable_definitions`, not part of `Stack#env`), so `interpolate` reads it straight from the deploy host's `ENV` and echoes the escaped value into the task's terminal output, which is visible to anyone who can view that task's log.

None of the existing guards intercept this: `permit`/`sanitize_env_vars` is not on this call path at all; `filter_task_envs`/`filter_deploy_envs`/`filter_envs` only restrict the env hash a *task-triggering user* supplies, not the literal command-line text baked into `shipit.yml`; there is no sanitization between `steps` text and `interpolate`.

### Impact Explanation
Any host-side environment variable (e.g. `$HOME`, `$SSH_AUTH_SOCK`, `$PATH`, any leftover credential-looking var not scrubbed from the worker's environment) that is not deliberately shadowed by the stack/task env can be exfiltrated into task output, which is readable by whoever has access to that stack's tasks. This is filesystem-path/socket-path disclosure aiding host reconnaissance — it does not directly grant RCE, secret exfiltration of Shipit's own application secrets, or cross-tenant writes by itself. This matches an informational/host-reconnaissance leak rather than the Critical/High categories defined (RCE, forged auth, GITHUB_TOKEN/api_clients_secret exfiltration, cross-repository writes, or unauthenticated read of task streams) — the underlying task stream read access itself is already authenticated/authorized by Shipit's existing controllers; this bug only affects *what value* gets echoed into an already-visible stream. Impact is bounded to the specific repository/stack whose `shipit.yml` was modified.

### Likelihood Explanation
Preconditions: the attacker needs a shipit.yml step to actually run, which generally requires the change to be merged and deployed, or a maintainer/CI to execute a task definition sourced from the PR branch (depending on how `cached_deploy_spec` is refreshed and which branch is used to build task definitions in this deployment). This engine's tests/design otherwise assume `shipit.yml` step content is trusted operator-authored config, not equivalent to a fully public unauthenticated write. Reaching execution as an "attacker who only controls a PR branch" without any merge or maintainer action is not demonstrated here — `cached_deploy_spec` is refreshed from the deployed/target branch, not arbitrary PR branches, for stacks with the deployed branch already configured, so the "unprivileged PR opener" alone cannot trigger execution without further privilege (a merge, or a maintainer explicitly running a task off that branch).

### Recommendation
Remove the implicit `ENV[variable]` fallback in `EnvironmentVariables#interpolate` (`lib/shipit/environment_variables.rb:23-26`), or make it opt-in and only apply to whitelisted variable names by threading `variable_definitions`/`permit` results into `interpolate` before executing the step. Unrecognized `$VAR` tokens should be preserved literally or raise, not fall back to the raw process environment of the Shipit host.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb
test 'interpolate leaks unwhitelisted host ENV var' do
  ENV['SSH_AUTH_SOCK'] = '/tmp/ssh-agent.sock'
  interpolated = EnvironmentVariables.with({}).interpolate('$SSH_AUTH_SOCK')
  assert_equal Shellwords.escape('/tmp/ssh-agent.sock'), interpolated
ensure
  ENV.delete('SSH_AUTH_SOCK')
end
```
This demonstrates `permit`'s whitelist check is never invoked on the `interpolate` path, and the deploy host's `SSH_AUTH_SOCK` value is substituted verbatim (Shellwords-escaped) despite no matching `variable_definitions` entry and no key in the stack's own `env`.     def permit(variable_definitions)
      return {} unless @env

    end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
