`initialize_nonce_account` never receives or checks a `signers: &HashSet<Pubkey>` set, unlike its sibling functions `withdraw_nonce_account` and `authorize_nonce_account` in the same file, which both explicitly call `check_signer` against the account/authority before mutating state. [3](#0-2) [4](#0-3) 

So any unprivileged party can submit an `InitializeNonceAccount` instruction naming an arbitrary `nonce_authority` for *any* system-owned, rent-exempt, still-`Uninitialized` account — without that account ever needing to sign the transaction, and without being the account's creator. The only gate is "state == Uninitialized"; whoever's `InitializeNonceAccount` lands first wins.

This is exactly the front-running/init-hijack pattern in the report, but the practical impact is bounded: since nonce accounts are normally created and initialized atomically in a single transaction via the `create_nonce_account` instruction builder used by the CLI (`cli/src/nonce.rs`) and tests, there is only a race window if a caller splits `CreateAccount` and `InitializeNonceAccount` into separate transactions. [5](#0-4) 

### Title
Front-runnable `InitializeNonceAccount` allows hijacking nonce authority on any uninitialized system-owned account - (File: programs/system/src/system_instruction.rs)

### Summary
`initialize_nonce_account` sets the nonce account's `authority` field to an attacker-controlled `nonce_authority` value without requiring any signature from the account being initialized (unlike `withdraw_nonce_account`/`authorize_nonce_account`, which both call `check_signer`). Any account left in `State::Uninitialized` after `CreateAccount` but before the intended `InitializeNonceAccount` call is processed can have its nonce authority claimed by any third party.

### Finding Description
`SystemInstruction::InitializeNonceAccount` is dispatched from `system_processor.rs` directly into `initialize_nonce_account` with no signer-set argument at all, and the function's only guard is `account.is_writable()` plus the `State::Uninitialized` state check. There is no requirement that the account key be a transaction signer, nor that the caller be related to the account's original creator. Consequently, whoever's `InitializeNonceAccount` transaction lands first (while the account is still `Uninitialized`) becomes the permanent `nonce_authority`, since a second call transitions to `Err(InstructionError::InvalidAccountData)` once `State::Initialized` is set.

### Impact Explanation
If a wallet/integrator creates a nonce account (`CreateAccount`, funding it with rent-exempt lamports) and submits `InitializeNonceAccount` as a *separate* transaction rather than atomically bundling them, an attacker monitoring the ledger for the freshly created, still-uninitialized, system-owned account can race an `InitializeNonceAccount` naming themselves as authority. Once set, only the attacker can subsequently `AuthorizeNonceAccount`/`WithdrawNonceAccount` the deposited rent-exempt lamports, effectively stealing control of the funded nonce account from the legitimate owner.

### Likelihood Explanation
Likelihood is limited because the standard tooling (`create_nonce_account`/`create_nonce_account_with_seed` used throughout `cli/src/nonce.rs`, tests, and `runtime/src/bank/tests.rs`) bundles `CreateAccount` and `InitializeNonceAccount` into one atomic transaction precisely to avoid this window, so well-behaved clients aren't exposed. Exposure only arises if a caller deliberately or accidentally separates these two instructions into different transactions, leaving a race window an attacker's transaction can win.

### Recommendation
Require the nonce account itself (or a designated deposit/creation signer) to sign `InitializeNonceAccount`, mirroring the signer checks already present in `withdraw_nonce_account` and `authorize_nonce_account`, so that only the account's rightful controller can set the initial `nonce_authority`.

### Proof of Concept
1. Victim submits a `CreateAccount` transaction assigning a fresh pubkey `N` to the System Program with rent-exempt lamports, intending to call `InitializeNonceAccount(N, victim_authority)` in a follow-up transaction.
2. Before the victim's follow-up transaction lands, an attacker submits their own transaction containing `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` with account `N` listed as writable (non-signer).
3. `initialize_nonce_account` observes `State::Uninitialized`, checks only `is_writable()` and the rent-exemption balance, and sets `authority = attacker_pubkey`.
4. Victim's subsequent `InitializeNonceAccount` call now fails with `InstructionError::InvalidAccountData` (state already `Initialized`).
5. Attacker calls `WithdrawNonceAccount` (or `AuthorizeNonceAccount`) signing as `attacker_pubkey`, draining/controlling the lamports the victim deposited into `N`.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
