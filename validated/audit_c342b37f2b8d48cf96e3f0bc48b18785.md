### Title
Session Fixation on OAuth Login - `GithubAuthenticationController#callback` never rotates the session ID before authenticating - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` writes `session[:user_id]` and `session[:authenticated] = true` directly into whatever session the incoming request already carries, without ever calling `reset_session`. If an attacker can plant a known session cookie in a victim's browser before the victim completes GitHub OAuth, that same session ID becomes authenticated as the victim, and the attacker can then replay it to inherit the victim's identity.

### Finding Description
Broken binding: `session_id_before_oauth == session_id_after_oauth` (should not hold; a fresh, unpredictable session ID should be issued at the authentication boundary).

Code path: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

Contrast with `logout`, which correctly calls `reset_session`: [2](#0-1) . No such call exists in `callback`.

Exploit flow: attacker sets `_shipit_session=X` in the victim's browser (e.g., via a sibling subdomain that shares the cookie domain, or any mechanism that lets the attacker fix a cookie value in the victim's browser for this host). Victim visits Shipit, is redirected to GitHub, authorizes, and is redirected back to `/github/auth/github/callback` still carrying session `X`. `callback` sets `session[:user_id]` and `session[:authenticated] = true` inside session `X` without rotating the ID. The attacker, who already knows `X`, now presents cookie `X` and is treated as the authenticated victim by `Shipit::Authentication` (`current_user`/`session[:user_id]`) and can perform any action the victim's account is authorized for (deploys, rollbacks, merges), per `app/controllers/concerns/shipit/authentication.rb`.

None of the existing guards address this: `verify_signature`/`GitHubApp#verify_webhook_signature` apply to webhook payloads, not browser session handling; `force_github_authentication` and `User#authorized?`/`require_permission!` only check whether *a* session is authenticated, not whether the session ID was rotated at the authentication boundary; OmniAuth's `state` parameter defends CSRF on the OAuth callback request itself but does nothing to change the underlying Rack session ID that Rails already had before the OAuth dance began.

### Impact Explanation
A successful fixation grants the attacker the victim's full authenticated identity within Shipit for as long as the session remains valid - the attacker can trigger deploys, rollbacks, or merges on any stack the victim is authorized for, and can repeat the attack against any victim who can be induced to complete OAuth login while holding the attacker-fixed cookie. This matches the "authentication bypass" Critical category (forged/hijacked session accepted as an authenticated user) since it is a full identity-binding break between pre- and post-login session state, not merely a High-severity fixation precursor.

### Likelihood Explanation
Preconditions: the attacker needs a way to set a cookie for the Shipit host in the victim's browser before the victim completes the OAuth flow (e.g., cookie scoping across subdomains, an open redirect, or any session-fixation delivery vector). No Shipit secrets, GitHub App credentials, or privileged roles are required. Given such a delivery vector exists, exploitation is deterministic and repeatable for every victim login, since `callback` unconditionally reuses the existing session without rotation.

### Recommendation
Call `reset_session` in `callback` immediately before establishing the new authenticated session state, mirroring the pattern in `logout`:
```ruby
def callback
  ...
  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```
Ensure any pre-authentication state needed after `reset_session` (e.g., `return_url` from `omniauth.origin`) is captured into local variables before the reset, as done above.

### Proof of Concept
Minitest plan (ActionDispatch::IntegrationTest) under `test/controllers/github_authentication_controller_test.rb`:
1. Perform a request to establish an initial (unauthenticated) session and capture `session.id` (e.g., via `cookies[Rails.application.config.session_options[:key]]` or `request.session.id` in a controller test hook) - call it `id_before`.
2. Mock `request.env['omniauth.auth']` as in existing tests and drive a request to `/github/auth/github/callback` with the session cookie from step 1 attached.
3. Capture the session id/cookie after the callback response - call it `id_after`.
4. Assert `refute_equal id_before, id_after` (session ID must have been rotated).
5. This assertion fails today because `callback` never calls `reset_session`, demonstrating that the pre-login session ID survives OAuth completion and remains replayable by anyone who fixed it.
