### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled` for `prevent_with_label` and `allow_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Repository#review_stacks_enabled` is intended to be a master switch gating all dynamic review-stack provisioning, per the UI/docs ("Dynamically provision stacks for Pull Requests?"). Due to Ruby `&&`/`||` operator precedence in `provision?`, that flag is only ANDed into the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`, so an attacker's unlabeled PR can trigger stack creation even when the operator has disabled review stacks.

### Finding Description
The broken binding: the operator sets `repository.review_stacks_enabled == false`, intending "no review stack provisioning for this repo," but `provision?` never consults that value on the `prevent_with_label`/`allow_with_label` paths: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When `provisioning_behavior == prevent_with_label` and no provisioning label is present on the PR, the third disjunct evaluates to `true` regardless of `review_stacks_enabled`.

`process` calls this predicate directly and, if true, invokes `ReviewStackAdapter#find_or_create!`, which will create a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` — a branch name fully controlled by the PR author's fork: [2](#0-1) 

Attacker request: open a GitHub pull request (webhook `action: "opened"`) against a repository configured with `review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`, and no matching label on the PR. `respond_to_pull_request_opened?` checks only `params.action == "opened" && provision?`, so this passes: [3](#0-2) 

Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) validate webhook authenticity/shape but do not enforce the `review_stacks_enabled` invariant — that check is purely a logic bug internal to `provision?`. This exact gap is not covered by the test suite: `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` has a test for `provisioning_enabled: false` only combined with `behavior: :allow_all` (lines 96-107) and a separate test for `prevent_with_label` with label absent (lines 159-172) that leaves `provisioning_enabled` at its default `true`. No test combines `review_stacks_enabled: false` with `prevent_with_label`/`allow_with_label`, meaning the divergence was never exercised.

The same flawed predicate pattern is duplicated in `ReopenedHandler#unarchive?`, `LabeledHandler`, and `UnlabeledHandler` handlers (per the earlier grep matches on `provisioning_behavior`/`review_stacks_enabled` in those files), so the same bypass likely applies to those flows as well, though this question is scoped to `OpenedHandler#provision?`.

### Impact Explanation
An attacker who can open a pull request on a repository they don't control the settings of can force creation of a `Shipit::ReviewStack` (a `Shipit::Stack` subtype) bound to their fork's branch, on a repository whose operator explicitly disabled dynamic review-stack provisioning. This is an unauthorized record write for a repository that did not opt into automatic provisioning. Downstream, review stacks proceed through the provisioning queue/task pipeline that ultimately executes deploy/provision commands against the configured deploy host using the attacker-controlled branch — the stack-creation step itself is the entry point into the `EXECUTION_TRUST` chain that the operator believed was closed by setting `review_stacks_enabled = false`. This matches "a record written for a repository that did not authenticate it" and sets up unauthorized command execution against the deploy host per the engine's documented threat model. It is repeatable against any repository configured with `prevent_with_label` (or `allow_with_label` with a self-applied label) and `review_stacks_enabled: false`, requiring only that the attacker be able to open PRs against that repo (e.g., a public repo accepting PRs from forks).

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`) with `review_stacks_enabled` set to `false` by the operator — a configuration explicitly exposed and independently settable in the settings UI (`f.check_box :review_stacks_enabled` and `f.select :provisioning_behavior` are two separate, uncoupled form fields). No validation ties the two together. Attacker cost is minimal: open a PR (or omit a label) against a public repo they can fork/PR into; no secrets, tokens, or privileged roles required. This is fully repeatable per PR/branch name.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to the duplicated predicate in `ReopenedHandler#unarchive?` and the analogous logic in `LabeledHandler`/`UnlabeledHandler`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (minitest, `ActiveSupport::TestCase`):
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding to assert before fix: `repository.review_stacks_enabled == false` (operator config) vs. actual behavior consulted by `provision?` for this branch = "never checked" → `Shipit::Stack.count` increases by 1 and the created stack's `branch` equals `payload["pull_request"]["head"]["ref"]`, demonstrating the two sides diverge. After the fix, `assert_no_difference` on `Shipit::Stack.count` passes, confirming the binding holds.
