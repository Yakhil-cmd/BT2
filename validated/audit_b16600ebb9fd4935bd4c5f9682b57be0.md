### Title
Unscoped commit-status webhook write allows cross-repository CI status forgery bypassing merge-queue checks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub `status` webhook payload to using a global, unscoped query (`Commit.where(sha: params.sha)`), instead of scoping the lookup to the repository that the webhook signature actually authenticates. This breaks the binding: `repository whose webhook signature is verified` == `repository whose commit status record is written`.

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook using the GitHub App's `webhook_secret` selected by `repository_owner`, which is derived from the payload's own `repository.owner.login` (or `organization.login`) field: [5](#0-4) 

The signature covers the entire raw payload body, so the `repository` field itself cannot be tampered with by a third party — but it only proves the request originated from a repository/org whose webhook secret matches. It does **not** prove that the commit-status write that follows is scoped to that same repository.

Every other stateful handler enforces that binding explicitly through the `stacks` helper on the base `Handler` class, which filters by `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [2](#0-1) 

For example `PushHandler` and `CheckSuiteHandler` both restrict their writes through `stacks`: [6](#0-5) [7](#0-6) 

`StatusHandler`, however, ignores `repository_name`/`stacks` entirely and writes to any commit in the entire Shipit installation sharing the given `sha`, regardless of which repository the webhook came from: [8](#0-7) 

`Commit#create_status_from_github!` unconditionally records the forged status against whatever `Commit` record(s) matched: [9](#0-8) 

Because git commit SHAs are shared across forks, mirrors, and any repository whose history includes the same commit (a common occurrence for shared/forked upstream repositories, or repositories tracked under multiple stacks/environments), an attacker who legitimately controls a webhook-emitting event for **one** repository/stack tracked by Shipit (e.g., a low-value fork or a repository they have push/CI access to) can send a genuinely GitHub-signed `status` event containing an arbitrary `sha` that also exists in a completely different, more sensitive stack's commit history. `StatusHandler` will happily attach that forged status to the unrelated commit.

### Impact Explanation
Commit statuses gate the merge queue and deploy safety checks via `MergeRequest::StatusChecker`/`all_status_checks_passed?` and `Commit#deployable?`-style checks: [10](#0-9) 

A forged `success` status injected via this cross-repository write can make `all_status_checks_passed?` return true for a commit belonging to a stack the attacker has no authorization over, causing `ProcessMergeRequestsJob` to auto-merge/ship a change whose real CI never passed: [11](#0-10) 

This is an unauthorized merge / bypass of a security control (required CI checks) across a repository boundary the attacker does not control — matching the High-severity criteria (escalation of authorization; effectively an unauthorized ship for the target repository).

### Likelihood Explanation
Exploitation requires: (1) Shipit tracks at least two stacks/repositories whose commit histories can share a SHA (forks, repo migrations, monorepo splits, or multiple environments of the same upstream), and (2) the attacker can trigger a legitimate, correctly-signed `status` webhook for the repository they control that references a SHA also present in the victim stack. Both conditions are realistic in organizations using forks or shared history, and require no privileged Shipit session, API token, or webhook secret — only ordinary push/CI access to one tracked repository, satisfying the "unprivileged attacker" bar.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`, by restricting the `Commit` lookup to the commits belonging to `stacks` (i.e. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), so a status can only be attached to a commit within a stack whose repository matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
1. Shipit tracks `stack_A` (repository `org/victim-repo`) and `stack_B` (repository `org/attacker-fork`, a fork of `org/victim-repo` sharing commit history), both under the same GitHub App/webhook secret.
2. Attacker has push/CI access to `org/attacker-fork` and knows (from the public upstream history) the SHA of a commit `C` that exists in `org/victim-repo`'s pending merge request, which also exists in the fork's shared history.
3. Attacker uses the GitHub Status API (`POST /repos/org/attacker-fork/statuses/C`) to set `state: success, context: <required-context>` for commit `C` on their fork.
4. GitHub delivers a genuinely signed `status` webhook event for `org/attacker-fork` to `/webhooks`. `WebhooksController#verify_signature` passes because the signature is valid for the org's `webhook_secret`.
5. `StatusHandler#process` runs `Commit.where(sha: 'C')`, matching the `Commit` row belonging to `stack_A` (`org/victim-repo`) as well, and writes the forged `success` status onto it.
6. `ProcessMergeRequestsJob` for `stack_A` observes `all_status_checks_passed?` become true and merges/deploys the pull request in `org/victim-repo`, even though its actual required CI never passed.
