### Title
Oversized `max_iterations`/`iteration` digit strings bypass ralph-loop safety cap via bash arithmetic overflow - (File: `plugins/ralph-wiggum/hooks/stop-hook.sh`)

### Summary
The regex checks at lines 28 and 39 only validate that `ITERATION`/`MAX_ITERATIONS` consist of digits (`^[0-9]+$`), with no bound on digit-string length. When either value exceeds bash's signed 64-bit integer range, subsequent arithmetic operations at lines 51 and 131 either silently fail the comparison (defeating the max-iterations cap) or abort the script mid-execution under `set -euo pipefail`, instead of triggering the explicit "state file corrupted" fail-safe path used for non-numeric input.

### Finding Description
`stop-hook.sh` reads `iteration` and `max_iterations` from `.claude/ralph-loop.local.md` and validates them only with a digit-only regex: [1](#0-0) 

This regex accepts arbitrarily long digit strings (e.g. `999999999999999999999`, 21 digits), which exceeds bash's internal 64-bit signed integer range (`LONG_MAX` = 9223372036854775807, 19 digits). The value is then used directly in arithmetic contexts:

- Line 51: `if [[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]` — when `MAX_ITERATIONS` overflows, bash's `[[ ]]` arithmetic evaluation raises "value too great for base", causing the test to return non-zero (false). Because this failure occurs inside the condition of an `if`, `set -e` does not apply, so the script silently continues past line 51 as though the cap were not reached — the max-iterations safety check is defeated rather than firing the corrupted-state fail-safe used elsewhere in the file. [2](#0-1) 

- Line 131: `NEXT_ITERATION=$((ITERATION + 1))` — if `ITERATION` itself overflows, this arithmetic expansion is not guarded by an `if`, so under `set -euo pipefail` the overflow error terminates the script immediately, leaving the state file un-updated and no JSON decision emitted (crash mid-iteration) instead of the graceful "state file corrupted" cleanup path used for other malformed fields. [3](#0-2) 

Unlike the explicit handling for non-digit values (which removes the state file and stops the loop with a clear message), oversized-but-all-digit values pass the regex and reach unguarded arithmetic, producing undefined behavior instead of the intended fail-safe.

### Impact Explanation
An attacker who can get a crafted `.claude/ralph-loop.local.md` into a shared repository (e.g., via a merged PR, since this file is not gitignored by name alone) can set `max_iterations` to an oversized digit string. Any user who then runs the ralph-loop automation in that workspace will have the max-iterations safety net silently disabled: the intended cap ("stop after N iterations") never triggers, so the loop continues feeding the same prompt/state back to the model on every `Stop` event beyond the user's approved iteration budget, until a completion promise, external interruption, or crash occurs. This is a safety-control bypass of a documented safety mechanism (the max-iterations bound), causing unbounded repeated automation and repo/file re-exposure to the model beyond user consent.

### Likelihood Explanation
Exploitation only requires the attacker to have the ability to introduce or modify `.claude/ralph-loop.local.md` in a shared repository that a victim later checks out and runs `/ralph-loop` against — no special privilege, secret, or social engineering beyond ordinary repo content contribution is needed. The regex flaw is deterministic and always reproducible with any all-digit string beyond 19 digits.

### Recommendation
Bound the accepted numeric range explicitly, e.g. change the regex to also reject numbers exceeding a sane maximum (`^[0-9]{1,9}$` or an explicit numeric range check), or validate with `[[ "$MAX_ITERATIONS" =~ ^[0-9]+$ ]] && (( MAX_ITERATIONS <= 2**31-1 ))` before use, falling back to the existing "state file corrupted" cleanup path (remove state file, stop loop) for out-of-range values just as is already done for non-numeric ones.

### Proof of Concept
Unit test plan for `stop-hook.sh`:
1. Create `.claude/ralph-loop.local.md` with frontmatter `iteration: 0` and `max_iterations: 999999999999999999999` (21 digits) plus a valid prompt body and no `completion_promise`.
2. Provide a minimal `transcript_path` JSONL file with one assistant message lacking `<promise>` tags, and pipe `{"transcript_path": "<path>"}` into the hook via stdin.
3. Run `bash plugins/ralph-wiggum/hooks/stop-hook.sh` and assert:
   - Expected (safe) behavior: hook prints a "state file corrupted"/"value out of range" message, removes the state file, and exits 0 (loop stops).
   - Observed (buggy) behavior: hook either (a) skips the max-iterations check and emits a `"decision": "block"` JSON continuing the loop (cap bypassed), or (b) crashes with bash's "value too great for base" error and non-zero exit status without cleaning up the state file, when `iteration` itself is set to an oversized value instead.
4. Repeat with `iteration: 999999999999999999999`, `max_iterations: 5` to confirm the crash path at line 131.
