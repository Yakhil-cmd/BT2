### Title
Global `authorized?` gate ignores per-organization team scoping in multi-organization deployments - ([File: lib/shipit.rb])

### Summary
In a Shipit instance configured with multiple GitHub organizations (as documented for "Using Multiple GitHub Applications"), the only authorization gate a logged-in user must pass, `User#authorized?`, checks membership against `Shipit.github_teams`, which is always derived from a single, hard-coded "default" organization rather than the organization that actually owns the stack/repository being accessed. This breaks the invariant that *the organization whose GitHub team grants access* should equal *the organization that owns the repository being deployed*.

### Finding Description
`Shipit.github_teams` is defined as: [1](#0-0) 

The bare `github` call inside it resolves to `github(organization: github_default_organization)`, and `github_default_organization` always returns the *first key* in the configured `github` secrets hash: [2](#0-1) 

This means `Shipit.github_teams` — and therefore the OAuth team list used for authorization — is permanently bound to whichever organization happens to be listed first in `secrets.github`, regardless of which organization's stack a request concerns.

The only place this list is consulted is the global authentication gate: [3](#0-2) 

and: [4](#0-3) 

`authorized?` does not take into account which stack, repository, or organization the current request is scoped to — it is a single boolean gate applied engine-wide. Once a user passes this one check (by being a member of the *first* configured org's team), they are treated as authorized to browse, view output for, and trigger deploys/rollbacks on stacks belonging to *any* other configured organization, since no other per-stack/per-organization membership check was found in the controllers (`StacksController`, `TasksController`, etc.) reachable from this session.

This is the same bug class as the reserve-price report: a value that should participate in a validation/authorization decision (here, "which organization does this stack belong to") is silently dropped, and a single global surrogate value (here, "the first configured organization") is substituted in its place — exactly analogous to a check being satisfied by an unrelated field never covered by the intended binding.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" boundary explicitly listed as a High-impact outcome. A user who is legitimately a member of Organization A's designated Shipit team (and thus passes `authorized?`) gains read/deploy access to stacks belonging to Organization B, C, etc. configured on the same Shipit instance, despite having no GitHub-side membership or write access to those other organizations. This defeats the entire purpose of the multi-organization isolation feature documented in `docs/setup.md`.

### Likelihood Explanation
Any Shipit deployment that follows the documented multi-organization setup (multiple GitHub Apps in `secrets.github`) is affected. No special privileges beyond being a member of the first-configured org's designated team are required — this is a standard, unprivileged authenticated user path (login is the intended entry point, not a privileged one).

### Recommendation
Scope `authorized?` (and the underlying team list) per-organization/per-repository rather than deriving it from a single "default" organization. `Shipit.github_teams` should be resolved per the organization that owns the stack/repository being accessed, and controllers should verify team membership against that specific organization's OAuth teams instead of a single global list.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `oauth.teams` restricting access to their respective GitHub teams (per `docs/setup.md` multi-org example).
2. A user who is a member of `org-a`'s designated team (but not a member of any `org-b` team, and has no access to `org-b` repositories on GitHub) logs in via the single configured OmniAuth GitHub app.
3. `User#authorized?` passes because `Shipit.github_teams` resolves to `org-a`'s teams (the first key in the `github` config hash) and the user is a member of one of them.
4. The user navigates to a stack whose repository belongs to `org-b`. No further per-organization check exists, so `force_github_authentication` permits the request, and the user can view task output or trigger a deploy/rollback for `org-b`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
```

```ruby
      if current_user.logged_in? && current_user.requires_fresh_login?

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))

        end

      end
    end
```
