### Title
Payload-owner / signature-owner divergence lets an attacker's own webhook mutate a victim repository's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the signing organization's `GitHubApp` using `repository.owner.login` (or `organization.login`) from the request body, while every handler (via `Handler#repository_name`) resolves the target `Repository`/`Stack` using the *separate* `repository.full_name` field from the same body. Because these are two independent, attacker-controlled JSON fields inside a single request whose signature the attacker legitimately computes with their own `webhook_secret`, the two values can be made to name different organizations, breaking the implicit binding that "the org that signed the webhook == the org whose stack gets mutated."

### Finding Description
The claimed binding is: `organization_owning(webhook_secret_used_for_verification) == organization_owning(repository.full_name_used_by_handlers)`.

Trace:
- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` (fallback `organization.login`). [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` HMACs the whole raw request body with that organization's `webhook_secret`, so the attacker, using their own valid `attacker-org` webhook secret, can sign *any* raw JSON body they construct — nothing ties the HMAC to any particular field inside the JSON other than the whole byte string. [3](#0-2) 
- Once signature verification passes, `WebhooksController#create` dispatches to handlers with the parsed `params` (the full payload). [4](#0-3) 
- `Handler#stacks` / `Handler#repository_name` resolve the acted-upon repository from `payload.dig('repository', 'full_name')` — a field completely independent of `repository.owner.login` used for signature routing. [5](#0-4) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack of the resolved repository whose branch matches, with `after` taken directly from the attacker-supplied payload. [6](#0-5) 
- `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a DB lookup with no ownership/authentication check tied back to `repository_owner`. [7](#0-6) 

Exploit: the attacker owns `attacker-org` and has a legitimate `webhook_secret` for it (a normal, unprivileged prerequisite — any org admin can install/configure their own webhook against the Shipit host). They construct a raw JSON push payload where `repository.owner.login = "attacker-org"` (so `verify_signature` selects and successfully validates against `attacker-org`'s secret) but `repository.full_name = "victim-org/victim-repo"` and `after = <attacker-chosen SHA>`. They compute `HMAC-SHA1(attacker_webhook_secret, raw_body)` and POST it to `/webhooks` with header `X-Github-Event: push`. The controller verifies the signature successfully (since it's checking against `attacker-org`'s own secret over the attacker's own bytes), then `PushHandler` resolves `victim-org/victim-repo`'s stacks and calls `sync_github(expected_head_sha: attacker_after)` — a cross-tenant, unauthenticated write triggered entirely by attacker-controlled data.

No existing guard prevents this: `drop_unhandled_event` only checks the event type exists; `verify_signature` never cross-checks `repository.owner.login` against `repository.full_name`; there's no `ExplicitParameters` validation tying the two; `Repository.from_github_repo_name` performs no ownership check against the verifying organization.

### Impact Explanation
This is a payload for one organization's webhook mutating another organization's `Stack`: the attacker triggers `GithubSyncJob`/`sync_github` on the victim's stack with an attacker-chosen `expected_head_sha`, purely by sending a request signed with credentials the attacker legitimately controls. It is repeatable against arbitrary target repositories known to the attacker (any `owner/repo` string) and, depending on downstream `sync_github`/`GithubSyncJob` behavior, can affect commit state, task scheduling, or deploy-eligible commit tracking on the victim stack without any interaction from the victim. This matches "a payload for one repository mutating another's stack" — Critical severity.

### Likelihood Explanation
Preconditions are minimal and match the stated attacker capability set: the attacker only needs to own any GitHub organization/repo configured in `Shipit.github_teams`/`Shipit.github` mapping (i.e., any org onboarded to this Shipit instance with its own webhook secret) and knowledge of the victim's `owner/repo` string (public information). No GitHub secrets, no Shipit session, and no privileged role are required — the attacker uses only their own legitimately-issued webhook secret. Crafting the payload is trivial (just set an unrelated `full_name` field) and can be repeated at will against any known repository hosted on the same Shipit instance.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization used to verify the signature is the same organization as the one being acted upon: compare `repository_owner` (used for `Shipit.github(organization: ...)`) against the owner segment of `payload.dig('repository', 'full_name')` (and `organization.login` where applicable), and reject the request (422) if they diverge. Alternatively, resolve the target `Repository` using `repository_owner` (the verified organization) rather than trusting the independent `full_name` field, or verify signatures per-repository using the resolved `Repository#owner` rather than a payload-supplied field.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` pattern) — no live GitHub:
1. Stub `Shipit.github(organization: 'attacker-org')` so `verify_webhook_signature` returns `true` for any signature/body.
2. Create fixture stacks: one for `victim-org/victim-repo` (existing `Repository`/`Stack`), none for `attacker-org`.
3. Build raw JSON body: `{"ref": "refs/heads/master", "after": "<attacker_sha>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}}`.
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', raw_body)` (any value works since the signature check is stubbed to `true`, isolating the test to the routing/binding bug).
5. `post shipit_engine.webhooks_path, params: raw_body, headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => sig, 'Content-Type' => 'application/json' }`.
6. Assert (before/after the equality): `repository_owner` extracted equals `'attacker-org'`, while the resolved `Repository.from_github_repo_name(payload.dig('repository','full_name'))` equals the victim's `Repository` (owner `'victim-org'`) — i.e. the two owners diverge.
7. Assert `Shipit::GithubSyncJob`/`stack.sync_github` was enqueued/invoked on **victim's** stack with `expected_head_sha == attacker_sha`, proving cross-tenant mutation triggered by attacker-controlled, attacker-signed data.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
