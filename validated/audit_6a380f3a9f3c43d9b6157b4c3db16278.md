## Finding: `MultiKey` accounts allow duplicate public keys, letting one private key satisfy multiple threshold slots

### Title
K-of-N multisig threshold in `MultiKeyAuthenticator`/`MultiKey` can be satisfied by a single private key when duplicate public keys are present - (File: `types/src/transaction/authenticator.rs`)

### Summary
Aptos' native "MultiKey" authentication scheme (the successor to `MultiEd25519`, usable for arbitrary key-type K-of-N accounts) does not enforce that the `N` public keys registered for an account are distinct. Because signature verification is performed per-index against whatever key sits at that index, a single physical private key that appears more than once in the key list can independently satisfy more than one of the required `K` signature slots. This silently converts an advertised "K-of-N distinct signer" authentication policy into a materially weaker one, exactly analogous to the reported bug class: unsynchronized/unvalidated configuration input (here, the key set) is accepted without any invariant check, causing the object (a multisig account) to behave in a way its other stakeholders do not expect.

### Finding Description
`MultiKey::new` in [1](#0-0)  only validates `signatures_required > 0`, `public_keys.len() <= MAX_NUM_OF_SIGS`, and `public_keys.len() >= signatures_required`. It never checks that the `public_keys` vector contains unique entries.

`MultiKeyAuthenticator::new` and `to_single_key_authenticators` in [2](#0-1)  only prevent a duplicate *signature index*, not a duplicate *public key value*. Verification walks the signature bitmap, and for each set index looks up `self.public_keys.public_keys[idx]` and verifies the (single) signature against that specific key — it has no notion of "this key already contributed a signature elsewhere in the set."

Consequently, if an account's authentication key is derived from a `MultiKey` where the same public key occupies two (or more) of the `N` slots, one holder of that one private key can produce two independently-verifying `(idx, signature)` pairs (the identical signature bytes, submitted under two different indices), satisfying two of the `K` required approvals. The on-chain prologue check that gates admission (`fee_payer_public_key_hash == account::get_authentication_key(...)` / `signer_public_key_hash == option::some(account::get_authentication_key(...))` in [3](#0-2)  and the fee-payer equivalent) only checks that the authentication key hash matches; it has no way to know that the "K distinct signers" property has been violated at account-creation/key-rotation time.

The repository's own unit test proves this: `verify_multi_key_auth` builds a 2-of-3 `MultiKey` where index 1 and index 2 point to the *same* secp256k1 public key (`any_sender1_pub`), then reuses the single signature `signature1` for both indices and shows the resulting `SignedTransaction` passes full signature verification: [4](#0-3) 

The same one-key holder can single-handedly authorize any transaction from this "2-of-3" account — the second required approval slot is filled by reusing their own key/signature, not by an independent co-signer.

### Impact Explanation
Multi-key accounts are the recommended mechanism for shared custody / K-of-N approval on Aptos (successor to `MultiEd25519`, used by wallets, custodians, DAOs, and the framework itself, e.g. `upsert_ed25519_backup_key_on_keyless_account` builds `MultiKey` policies via `multi_key::new_multi_key_from_single_keys`, see [5](#0-4) ). Other approvers of a shared/custodial `MultiKey` account trust that `signatures_required` distinct keyholders must cooperate. If duplicate keys can be inserted into the key list (by the account creator, a compromised co-signer, or a wallet bug that fails to de-duplicate), the effective security threshold silently drops (e.g., a "2-of-3" collapses to "1-of-3" if one key is duplicated once). This is exactly the "authenticator/multisig validation accepting the wrong approval set" scenario the admission gate targets: transactions execute and commit under a signer set that does not reflect the intended K independent approvers, letting an unprivileged single-key holder unilaterally move funds or execute governance actions that were meant to require multiple independent parties.

### Likelihood Explanation
Exploitation requires only that the multi-key account was set up (at key-rotation or account-creation time) with a non-unique key list — there is no on-chain or in-crate validation preventing this, and nothing surfaces the duplication to co-signers inspecting only `signatures_required` and key count. This can happen via: (a) a malicious or compromised account setup where the attacker controls creation of the `MultiKey` list and inserts their key twice while the display/UX layer shows "N distinct owners", or (b) any wallet/SDK bug that fails to reject duplicate keys client-side. Since the vulnerability is proven by the codebase's own passing test rather than requiring speculative conditions, it is a concrete, low-effort admission-time bypass once such an account exists.

### Recommendation
Enforce uniqueness of public keys in `MultiKey::new` (reject construction if any two entries are byte-identical), and add the same check to the Move-side `multi_key` module and the API's `MultiKeySignature::verify`/`TryFrom` conversion (`api/types/src/transaction.rs`) so malformed/duplicate-key multi-key authenticators and authentication-key rotations are rejected before admission, not just documented as a caller responsibility.

### Proof of Concept
1. Generate two independent keys: `sender0` (Ed25519) and `sender1` (secp256k1).
2. Construct `MultiKey::new(vec![any_sender0_pub, any_sender1_pub, any_sender1_pub], 2)` — a nominal "2-of-3" policy where index 1 and 2 are the *same* secp256k1 key.
3. Derive the account address from `AuthenticationKey::multi_key(multi_key)` and fund it.
4. Sign the transaction once with `sender1`'s private key to get `signature1`.
5. Build `MultiKeyAuthenticator::new(multi_key, vec![(1, signature1.clone()), (2, signature1.clone())])` and wrap it as `AccountAuthenticator::multi_key(...)` / `SignedTransaction::new_single_sender(...)`.
6. `signed_txn.verify_signature()` succeeds — reproduced verbatim by the existing repo test `verify_multi_key_auth` at [4](#0-3) , meaning `sender1` alone (without `sender0`'s cooperation) satisfies the "2-of-3" admission requirement and the transaction is admitted/executed under a signer set weaker than the account's declared policy.

impl MultiKeyAuthenticator {
    pub fn new(public_keys: MultiKey, signatures: Vec<(u8, AnySignature)>) -> Result<Self> {
        ensure!(
            public_keys.len() < (u8::MAX as usize),
            "Too many public keys, {}, in MultiKeyAuthenticator.",
            public_keys.len(),
        );

        let mut signatures_bitmap = aptos_bitvec::BitVec::with_num_bits(public_keys.len() as u16);
        let mut any_signatures = vec![];

        for (idx, signature) in signatures {
            ensure!(
                (idx as usize) < public_keys.len(),
                "Signature index is out of public key range, {} < {}.",
                idx,
                public_keys.len(),
            );
            ensure!(
                !signatures_bitmap.is_set(idx as u16),
                "Duplicate signature index, {}.",
                idx
            );
            signatures_bitmap.set(idx as u16);
            any_signatures.push(signature);
        }

        Ok(MultiKeyAuthenticator {
            public_keys,
            signatures: any_signatures,
            signatures_bitmap,
        })
    }

    pub fn public_keys(&self) -> &MultiKey {
        &self.public_keys
    }

    pub fn signatures(&self) -> Vec<(u8, &AnySignature)> {
        let mut values = vec![];
        for (idx, signature) in
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
        {
            values.push((idx as u8, signature));
        }
        values
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }
