### Title
Stack-Scoped API Client Token Can Read CI Status of Any Stack via CCMenu Endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base class's stack-scoping logic with a private `stack` method that resolves `params[:stack_id]` against *all* stacks, unconditionally, instead of the scoped `stacks` relation that every other API controller uses. This breaks the binding: **stack a token authorizes == stack the endpoint touches**.

### Finding Description
`Shipit::Api::BaseController` establishes the trust boundary for stack-scoped `ApiClient` tokens: `stacks` is filtered to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested `params[:stack_id]` only within that scoped relation: [1](#0-0) 

`require_permission` only checks the *generic* permission string (`read:stack`), it never checks which specific stack the token is bound to: [2](#0-1) 

So the *only* place the per-stack scope is enforced is inside the `stack`/`stacks` helper methods. `CCMenuController` re-declares `stack` and bypasses that scoping entirely, resolving directly against the global `Stack` relation: [3](#0-2) 

The `show` action uses this unscoped `stack` to render deploy/build status: [4](#0-3) 

`ApiClient` itself supports being scoped to a single stack via `belongs_to :stack, optional: true` and `stack_id?`: [5](#0-4) 

The fixture `here_come_the_walrus` demonstrates the intended usage pattern — a token restricted to one stack with `read:stack` permission — and other API controllers (e.g. `StacksController#index`) correctly honor that restriction, only returning the client's assigned stack: [6](#0-5) [7](#0-6) 

Before the attacker's action: a stack-scoped `ApiClient` token with `read:stack` can only fetch data for the one `Stack` it is bound to (`current_api_client.stack_id == accessible_stack.id`), as enforced through every controller that uses the base `stack`/`stacks` helpers. After: hitting `Api::CCMenuController#show` with that same token but an arbitrary `stack_id` param resolves and renders build/deploy status for *any* stack in the installation, because `CCMenuController#stack` never consults `current_api_client.stack_id`. The equality `token.authorized_stack == stack_touched_by_endpoint` is broken specifically for this controller.

### Impact Explanation
This is an unauthenticated-scope escalation into stack state: a token deliberately restricted to one stack (as configured by an administrator, e.g. to hand out to a CI dashboard integration scoped to a single project) can read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, lock state) of every other stack managed by the Shipit instance. This matches the in-scope High-impact category of "unauthenticated read of stack state," since access is granted outside the credential's intended authorization scope.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token (which is a normal, unprivileged credential handed out for narrow integrations such as CI badges) can trivially exploit this by changing the `stack_id` route/query parameter on the CCMenu XML endpoint — no additional privilege, repository write access, or session is required beyond possessing that one scoped token.

### Recommendation
Remove `CCMenuController`'s private `stack` override, or reimplement it to resolve against the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so that scoped tokens cannot resolve stacks outside their `stack_id` binding.

### Proof of Concept
1. As an admin, create a stack-scoped `ApiClient` bound to `stack_id = A` with permission `read:stack` (as in the `here_come_the_walrus` fixture).
2. Using that client's `authentication_token`, call `GET /api/stacks/:stack_id/ccmenu` (per `config/routes.rb`) with `params[:stack_id]` set to a *different* stack `B` that the client is not scoped to.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (client has `read:stack` permission generically), and `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly to stack `B`, returning `B`'s deploy/build status in the XML response — despite the token being scoped only to stack `A`. # frozen_string_literal: true

```ruby
module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
