## Analog Found

### Title
Externally Burned LP Tokens Are Not Reflected in `PoolState.lp_supply`, Permanently Distorting Withdraw/Deposit Accounting - (File: `programs/cp-swap/src/instructions/deposit.rs`, `programs/cp-swap/src/instructions/withdraw.rs`, `programs/cp-swap/src/states/pool.rs`)

### Summary
The Linea report describes a case where tokens can be burned on a "downstream" ledger (L2) without that burn ever being reflected in the "authoritative" total-supply accounting (L1), permanently overstating the recognized supply and stranding the corresponding backing value. The analogous flaw in this program is that `PoolState.lp_supply` — the field used as the sole denominator for all deposit/withdraw pricing math — is a hand-maintained counter, updated only inside this program's `deposit`/`withdraw` instructions, and is never reconciled with the real circulating supply of the `lp_mint` token account that anyone can query or affect directly via the standard SPL Token program.

### Finding Description
`PoolState.lp_supply` is documented as "True circulating supply" [1](#0-0)  and is exclusively updated by `+=`/`-=` inside `deposit()` and `withdraw()`: [2](#0-1) [3](#0-2) 

The `lp_mint` created in `initialize` sets only a mint authority (the pool PDA); no freeze authority is configured, and LP tokens are minted into the depositor's own associated token account: [4](#0-3) . Because these are ordinary, freely-held SPL tokens, any LP holder can invoke the standard SPL Token `Burn` instruction directly on their own `owner_lp_token` account, completely bypassing the cp-swap program's `withdraw` instruction. This directly reduces the real supply of `lp_mint` (queryable on-chain via the mint account) but leaves `pool_state.lp_supply` unchanged, since that counter is only touched by this program's own code paths.

`lp_supply` is then used as the denominator for computing every subsequent depositor's/withdrawer's share of the pool via `CurveCalculator::lp_tokens_to_trading_tokens`, both in `deposit()` [5](#0-4)  and `withdraw()` [6](#0-5) . Once `lp_supply` is inflated relative to the real outstanding LP token count, every remaining legitimate LP's `withdraw` call computes a payout proportionally smaller than their true share of the vaults (`token_i_amount = lp_token_amount * vault_amount / lp_supply`, with `lp_supply` artificially too large). The residual value that should have accrued to the burned tokens' fair share becomes permanently stuck in `token_0_vault`/`token_1_vault`, unreachable by any LP token holder, exactly mirroring the reported bug class: an out-of-band burn that is invisible to the ledger used to size claims against the backing pool.

### Impact Explanation
This causes a lasting accounting desync between recognized LP supply and the funds actually claimable against the vaults, permanently under-paying legitimate LPs and stranding pool funds — an insolvency/frozen-funds condition in the pool's fee/value ledger, reachable without any privileged role.

### Likelihood Explanation
Any user who has ever deposited into a pool (an ordinary LP, no special privilege) can trigger this with a single standard SPL Token `Burn` instruction against their own `lp_mint` token account — no interaction with the cp-swap program is even required to cause the desync, and no protections (freeze authority, non-transferable extension, program-only burn enforcement) prevent it.

### Recommendation
Do not maintain `lp_supply` as an independently-tracked, program-only counter that can silently diverge from the mint's real supply. Either (a) always read the LP mint's actual `supply` field on-chain in `deposit`/`withdraw`/valuation logic instead of trusting `pool_state.lp_supply`, or (b) prevent LP tokens from being burned/moved outside protocol-controlled paths (e.g., by using a token extension or an escrow/authority model that disallows direct holder-initiated burns), analogous to removing `ERC20BurnableUpgradeable` from the L2 token in the referenced fix.

### Proof of Concept
1. LP `A` deposits into a pool via `deposit`, receiving `X` LP tokens; `pool_state.lp_supply` increases by `X`.
2. LP `A` sends a plain SPL Token Program `Burn` instruction against their own `owner_lp_token` account for amount `Y` (< `X`), burning `Y` LP tokens directly — this does not touch the cp-swap program at all, so `pool_state.lp_supply` is untouched.
3. `lp_mint`'s actual total supply is now `pool_state.lp_supply - Y`, but `pool_state.lp_supply` still reports the old, larger value.
4. Any other LP `B` calls `withdraw`; the payout formula in `withdraw.rs` divides by the stale, inflated `pool_state.lp_supply`, systematically under-paying `B` relative to their true share of `token_0_vault`/`token_1_vault`.
5. The gap (`Y`'s worth of pool share) remains permanently locked in the vaults, unclaimable by any remaining LP token holder.
