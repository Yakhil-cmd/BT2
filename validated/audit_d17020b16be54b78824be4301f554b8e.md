### Title
`Api::CCMenuController#stack` bypasses the `current_api_client.stack_id` scope enforced by `Api::BaseController#stack`, letting a stack-A-scoped API client read any stack via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController#stacks` restricts the visible stack set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `#stack` resolves through that scoped relation. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, so a stack-scoped `ApiClient` that is denied access to stack B via `Api::StacksController#show` is granted access to stack B via `Api::CCMenuController#show` using the same credentials.

### Finding Description
Binding claimed: for a fixed `current_api_client`, the reachable stack set must be identical across all `Api::*` controllers, i.e. `stacks_visible_via(StacksController) == stacks_visible_via(CCMenuController)` for the same client.

- `Api::BaseController#stacks` (app/controllers/shipit/api/base_controller.rb:74-76): `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`.
- `Api::BaseController#stack` (app/controllers/shipit/api/base_controller.rb:78-80): `@stack ||= stacks.from_param!(params[:stack_id])` — resolves through the scoped relation, so `Api::StacksController#show` (inherits `#stack` unmodified apart from using `params[:id]`) enforces the client's `stack_id` binding; a client scoped to stack A requesting stack B raises `ActiveRecord::RecordNotFound` and the controller's `not_found` rescue returns 404.
- `Api::CCMenuController#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) overrides this with `@stack ||= Stack.from_param!(params[:stack_id])`, calling `from_param!` on the bare `Stack` class instead of the scoped `stacks` relation. This completely drops the `current_api_client.stack_id` restriction.
- `require_permission :read, :stack` (ccmenu_controller.rb:6) only calls `ApiClient#check_permissions!` (app/models/shipit/api_client.rb:38-45), which checks the string `"read:stack"` against the client's `permissions` array — it has no notion of *which* stack, so it does not compensate for the missing scoping.
- `Api::CCMenuController#authenticate_api_client` (ccmenu_controller.rb:33-36) tries `params[:token]` first, then falls back to `super`, which is `Api::BaseController#authenticate_api_client`'s Basic-Auth path. So the exact same Basic-Auth header used against `Api::StacksController` resolves to the exact same `current_api_client` (with the same `stack_id = A`) when replayed against `Api::CCMenuController`.

Attacker flow: an operator issues a stack-scoped `ApiClient` for stack A (a normal, legitimate credential, not a secret the attacker needs to steal — this is exactly the credential meant to be confined to stack A). Using that credential's Basic-Auth header verbatim:
1. `GET /api/stacks/B` → `Api::StacksController#show` → `stack` → `stacks.from_param!(B)` → `Stack.where(id: A).from_param!(B)` → not found → 404.
2. `GET /api/stacks/B/cc.xml` (or equivalent CCMenu route with `stack_id=B`) → `Api::CCMenuController#show` → `stack` → `Stack.from_param!(B)` (unscoped) → succeeds → renders stack B's latest deploy/rollback status via the `shipit/ccmenu/project` template.

The `require_permission :read, :stack` guard does not fail because the client does have `"read:stack"` permission — the check is scope-name based, not stack-instance based. No other guard (`verify_signature`, `force_github_authentication`, model validations) sits between `stack` resolution and rendering in this controller.

### Impact Explanation
A credential intentionally scoped to a single stack (stack A) can read deploy/rollback status (latest deploy id, end time, running state) for any other stack (B) in the installation via `Api::CCMenuController#show`, an unauthenticated-by-design read of stack state that should have been denied. This is a controller-specific authorization scope bypass: the same `ApiClient` yields different, inconsistent authorization decisions for stack B depending only on which controller endpoint is hit, which is a broken access-control invariant across the `Api::*` namespace. It is fully repeatable against arbitrary stack IDs in the same request, using nothing but the pre-issued Basic-Auth header. This matches "High — unauthenticated/under-scoped read of stack state" (task streams/deploy output are not exposed here, only summary CCMenu status, but it is cross-stack data leakage of deploy status not authorized for that credential).

### Likelihood Explanation
Precondition: the attacker must already hold a legitimately-issued, stack-scoped `ApiClient` Basic-Auth credential (e.g. a client meant only for stack A, given to a low-trust integration). No secrets, GitHub tokens, or webhook signing keys are needed. Given that precondition, exploitation is a single unauthenticated-by-scope GET request with the existing header — trivial and deterministic, requiring no race conditions or timing.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation, matching `Api::BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
or simply remove the override entirely so it inherits `Api::BaseController#stack` (adjusting only the param name if `:id` vs `:stack_id` differs), ensuring all `Api::*` controllers share one code path for stack resolution.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_scope_test.rb
require 'test_helper'

module Shipit
  module Api
    class CcmenuScopeBypassTest < ActionController::TestCase
      setup do
        @stack_a = shipit_stacks(:shipit)
        @stack_b = create_stack(repository: create_repository(name: 'other-repo'))
        @client = ApiClient.create!(
          creator: shipit_users(:walrus),
          name: 'scoped-client',
          stack: @stack_a,
          permissions: ['read:stack']
        )
        @credentials = ActionController::HttpAuthentication::Basic
          .encode_credentials(@client.authentication_token, '')
      end

      test 'StacksController denies the scoped client access to stack B' do
        @controller = Shipit::Api::StacksController.new
        get :show, params: { id: @stack_b.to_param }, headers: { 'Authorization' => @credentials }
        assert_response :not_found
      end

      test 'CCMenuController must ALSO deny the scoped client access to stack B (currently fails)' do
        @controller = Shipit::Api::CcmenuController.new
        get :show, params: { stack_id: @stack_b.to_param }, headers: { 'Authorization' => @credentials }
        # Binding: same client, same stack B => same decision as StacksController#show
        assert_response :not_found, 'CCMenuController leaked stack B status to a stack-A-scoped client'
      end
    end
  end
end
```
Before the fix, the second test fails (returns `200 OK` with stack B's CCMenu XML), proving the divergence; after applying the recommended change to use `stacks.from_param!`, both assertions pass identically.
