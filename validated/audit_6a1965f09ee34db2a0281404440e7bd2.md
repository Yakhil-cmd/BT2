## Title
CCMenu API endpoint lets a stack-scoped API token read any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` tokens can be scoped to a single `Stack` via `stack_id`, and every other API controller enforces that scope by resolving stacks through `BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` to bypass that scoping entirely, resolving the `stack_id` param against the global `Stack` relation instead of the client's authorized scope. This is the same class of bug as the Receiver report: a credential is verified for one identity (the `ApiClient` bound to stack A), but the data it is allowed to act on (`stack_id` in the request) is never checked against that verified identity before being used.

### Finding Description
`ApiClient#stack_id` is meant to be an authorization boundary: `Api::BaseController` computes accessible stacks as [1](#0-0) 
so any controller resolving `stack` through `stacks.from_param!` can only ever reach the stack the token was scoped to (or raises `RecordNotFound`).

`Api::CCMenuController`, however, defines its own `authenticate_api_client` (accepting the token from a query string param instead of Basic Auth) and its own `stack` method that talks to `Stack` directly, not through `current_api_client`'s scoped `stacks`: [2](#0-1) 

The only authorization gate left is `require_permission :read, :stack`, which delegates to `ApiClient#check_permissions!`: [3](#0-2) 

This check only verifies that the string `"read:stack"` is present in the client's `permissions` array — it has no notion of *which* stack the client is scoped to. So the binding that should hold, `current_api_client.stack_id == stack.id` (when the client is stack-scoped), is enforced everywhere in the API except here.

Tokens with this exact shape — scoped to one stack, granted only `read:stack` — are created and exposed by design as a URL query parameter for embedding in third-party CI dashboards: [4](#0-3) 

Because this token is meant to be pasted into external tools (CCMenu-compatible clients), it is far more likely to leak (via logs, referrer headers, screenshots, shared dashboards) than a Basic-Auth API token. Whoever obtains it can use it against **any** stack, not just the one it was minted for.

### Impact Explanation
Before the request: `current_api_client.stack_id == A`, and by design the client should only ever resolve `stack == A` (as every other API endpoint enforces via `BaseController#stacks`). After an attacker's request `GET /api/stacks/:B/ccmenu.xml?token=<A's token>`, `stack == B` is resolved and rendered, even though the token's `stack_id` is `A`. This is an unauthenticated-scope read of another stack's state — `stack` name, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` (see the CCMenu template used) — for a stack the token was never authorized to access, matching the "unauthorized read of stack state" High-impact category.

### Likelihood Explanation
Exploitation requires only possession of any valid stack-scoped `read:stack` CCMenu token (no privileged account, no session, no GitHub credentials) and knowledge/guessing of another stack's `to_param` (slug), which is not secret. Because these tokens are specifically designed to be embedded in URLs for external CI dashboard tools, they are the API-client credential most likely to leak outside of Shipit's trusted UI, making this a realistic scenario rather than a purely theoretical one.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same scoped relation as every other API controller, e.g. `stacks.from_param!(params[:stack_id])` (using the inherited `stacks` scoping from `BaseController`), instead of calling `Stack.from_param!` directly. This restores the `current_api_client.stack_id == stack.id` binding that the rest of the API relies on.

### Proof of Concept
1. As a legitimate Shipit user, visit `CCMenuUrlController#fetch` for stack A to obtain a `read:stack`-only, stack-A-scoped token (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` per `app/controllers/shipit/ccmenu_url_controller.rb`).
2. That token URL (`.../api/stacks/A/ccmenu.xml?token=T`) is pasted into a third-party CI aggregator, as intended.
3. An attacker who obtains `T` (e.g., from logs/referrers of the third-party tool) sends `GET /api/stacks/B/ccmenu.xml?token=T` for an unrelated stack B.
4. `authenticate_api_client` succeeds (`ApiClient.authenticate(T)` is valid), `require_permission :read, :stack` passes (`T` has `read:stack`), and `stack` resolves to `Stack.from_param!('B')` — bypassing the intended `stack_id` scope — returning stack B's build/deploy status in the XML response.
