### Title
User-controlled deploy/task variables can override Shipit's trusted environment keys (`GITHUB_TOKEN`, `SHIPIT_USER`, `IGNORED_SAFETIES`, `GIT_COMMITTER_*`) because the "permitted variable" whitelist and the actual environment merge order are not the same binding - (File: `lib/shipit/task_commands.rb`)

### Summary
`shipit.yml` lets a repository maintainer declare a set of *permitted* deploy/task variable names (`deploy.variables` / `tasks.<name>.variables`). `EnvironmentVariables#permit` only checks that a user-supplied variable's **name** is in that whitelist [1](#0-0) . The value that ends up in the actual spawned process environment, however, is produced by `TaskCommands#env`, which merges the user-supplied `@task.env` **last**, after Shipit's own trusted/reserved keys (`SHIPIT_USER`, `EMAIL`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`) and even after the base environment that carries `GITHUB_TOKEN`/`GITHUB_DOMAIN` [2](#0-1) [3](#0-2) [4](#0-3) .

The "permitted" set (what a stack admin allowed via `shipit.yml`) and the "spawned" set (what actually lands in the child process env, and with what precedence) are two different bindings: the whitelist check only validates key *names* against `variable_definitions`, but the merge order lets any permitted name silently overwrite Shipit's own trust-critical keys instead of only adding application-level variables.

### Finding Description
- A stack maintainer defines `deploy.variables` or `tasks.<id>.variables` in `shipit.yml`, e.g. a variable named `RUN_MIGRATIONS`. Defining these variables requires repository write access.
- Triggering a deploy/task with a value for that variable requires only deploy/task trigger authorization (a logged in Shipit user in `Shipit.github_teams`, or an `ApiClient` with `deploy:stack` permission) - a materially lower trust level than repository push access.
- `Stack#trigger_task` / `Stack#build_deploy` sanitize the caller-supplied `env` hash through `TaskDefinition#filter_envs` / `DeploySpec#filter_deploy_envs`, both of which call `EnvironmentVariables#permit(variable_definitions)` [5](#0-4) [6](#0-5) . This check only rejects env keys that are *not* in the whitelist; it does not reject whitelisted keys that collide with Shipit's own reserved keys.
- At execution time, `TaskCommands#env` builds the process environment as:
  `base_env (incl. GITHUB_TOKEN, GITHUB_DOMAIN) → @stack.env → {SHIPIT_USER, EMAIL, BUNDLE_PATH, SHIPIT_LINK, TASK_ID, IGNORED_SAFETIES, GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL} → deploy_spec.machine_env → @task.env`
  with `@task.env` merged last [2](#0-1) . `DeployCommands#env` only re-asserts `SHA`, `REVISION`, `DIFF_LINK` after `super`, leaving every other reserved key overridable by `@task.env` [7](#0-6) .
- If a `shipit.yml` variable name happens to equal one of these reserved keys (`SHIPIT_USER`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `EMAIL`, `TASK_ID`, `BUNDLE_PATH`, `SHIPIT_LINK`, or even `GITHUB_TOKEN`/`GITHUB_DOMAIN` from `base_env`), any caller permitted to supply that variable's value can overwrite Shipit's own trusted metadata in the environment the deploy/task script sees.

### Impact Explanation
This breaks the "environment key permitted vs. environment key spawned" binding: the trust boundary intended by the whitelist (repo admin controls which *application* variables end up in the script env) is not the trust boundary actually enforced (a deploy-trigger-level user can shadow *Shipit's own* audit/safety/credential keys). Concretely, a deploy-trigger user (not necessarily a repo committer) could:
- Overwrite `SHIPIT_USER` / `GIT_COMMITTER_NAME` / `GIT_COMMITTER_EMAIL`, corrupting the deploy audit trail and any commits made by deploy scripts under a forged identity.
- Overwrite `IGNORED_SAFETIES`, changing script behavior that gates dangerous operations.
- Overwrite `GITHUB_TOKEN`/`GITHUB_DOMAIN`, causing deploy scripts that call GitHub APIs using `$GITHUB_TOKEN` to use an attacker-supplied token/endpoint instead of the app's installation token, which can be leveraged for SSRF-style credential substitution against the app's own GitHub-authenticated workflow.

The actual severity is gated on the stack's `shipit.yml` happening to declare a variable whose name collides with a Shipit reserved key - this makes it configuration-dependent rather than universally exploitable, but the underlying merge-order design provides no defense-in-depth (no reserved-key blocklist) once that collision exists.

### Likelihood Explanation
Requires: (1) a stack admin (privileged, has repo write) to define a `deploy.variables`/`tasks.variables` entry whose `name` matches a Shipit-reserved env key, and (2) any deploy/task-trigger-permitted caller (lower privilege) to supply a value for it. Condition (1) is plausible because reserved key names like `EMAIL`, `TASK_ID`, or `GITHUB_TOKEN` are generic and not documented as forbidden variable names anywhere in `README.md`'s variables/environment sections, so an admin could pick one unintentionally. This is a genuine reachable path but is conditional rather than unconditionally exploitable against every Shipit deployment.

### Recommendation
In `lib/shipit/environment_variables.rb`, reject variable definitions/user-supplied env whose names collide with Shipit's reserved keys (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, `SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `SHA`, `REVISION`, `DIFF_LINK`, `ENVIRONMENT`, `BRANCH`, `LAST_DEPLOYED_SHA`), and/or change the merge order in `TaskCommands#env`/`DeployCommands#env` so reserved/trusted keys are always merged **after** `@task.env`, guaranteeing they cannot be shadowed by user- or config-supplied values.

### Proof of Concept
1. Stack admin adds to `shipit.yml`:
```yaml
tasks:
  restart:
    action: "Restart Application"
    steps:
      - ./script/restart
    variables:
      - name: SHIPIT_USER
```
2. A user who only has deploy/task-trigger permission (e.g. `deploy:stack` on an `ApiClient`, or team membership) triggers the task supplying `env: { SHIPIT_USER: "root (forged) via Shipit" }`, matching the pattern already exercised in `test/controllers/api/tasks_controller_test.rb` for whitelisted variables [8](#0-7) .
3. `EnvironmentVariables#permit` accepts it because `SHIPIT_USER` is in the declared whitelist [1](#0-0) .
4. `TaskCommands#env` merges `@task.env` last, so the script executed for this task sees the attacker-chosen `SHIPIT_USER` value instead of the real triggering user's identity [2](#0-1) .

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
