### Title
Unvalidated `burnt_gas_reward` protocol ratio parameter can panic the runtime during normal receipt processing - (File: `runtime/runtime/src/lib.rs`)

### Summary
`RuntimeFeesConfig::burnt_gas_reward` is a `Rational32` numerator/denominator parameter (analogous to `royaltyRate_`/`BPS` in the reported Solidity bug) that is used unchecked to compute a reward paid to a contract account out of the gas burnt for its execution. Neither `core/chain-configs/src/genesis_validate.rs` nor `nearcore/src/config_validate.rs` validate that its numerator is `<=` its denominator (i.e., that the ratio is `<= 1`), unlike the analogous `gas_price_adjustment_rate` and `online_max_threshold`/`online_min_threshold` fractions, which are explicitly bounds-checked.

### Finding Description
`RuntimeFeesConfig::gas_penalty_for_gas_refund` and the receipt-processing code in `apply_action_receipt`/successor logic compute:
```
receiver_gas_reward = gas_burnt_for_function_call * burnt_gas_reward.numer() / burnt_gas_reward.denom()
``` [1](#0-0) 
and then subtract the resulting `receiver_reward` from `tx_burnt_amount` using an unchecked `unwrap()`:
```
tx_burnt_amount = tx_burnt_amount.checked_sub(receiver_reward).unwrap();
``` [2](#0-1) 

If `burnt_gas_reward.numer() > burnt_gas_reward.denom()` (ratio > 1), `receiver_gas_reward` can exceed `gas_burnt_for_function_call`, making `receiver_reward` larger than `tx_burnt_amount`, so `checked_sub` returns `None` and the subsequent `.unwrap()` panics.

Unlike other fraction-typed protocol parameters, this ratio is never bounds-checked. `genesis_validate.rs` explicitly validates that `online_max_threshold`/`online_min_threshold` are `<= 1` and that `gas_price_adjustment_rate < 1`, but performs no equivalent check for `burnt_gas_reward` (or `gas_refund_penalty`/`pessimistic_gas_price_inflation_ratio`): [3](#0-2) 

`nearcore/src/config_validate.rs` similarly validates unrelated `config.json` fields (block delays, gc, tracked shards) but never touches `RuntimeFeesConfig` fraction parameters: [4](#0-3) 

This mirrors the reported Solidity issue exactly: a ratio-typed fee parameter (`royaltyRate_` vs `BPS` ↔ `burnt_gas_reward.numer()` vs `.denom()`) is used in a division/subtraction without validating that the ratio stays within the intended `[0,1]` bound, and an out-of-range value causes the code path to abort (revert in Solidity, `unwrap()` panic in nearcore) whenever normal, unprivileged activity (a function-call transaction) exercises it.

### Impact Explanation
If `burnt_gas_reward` were ever configured (via genesis or a future protocol-upgrade parameter change) with numerator greater than denominator, every function-call receipt that burns gas would trigger the unchecked `unwrap()` panic in `apply_action_receipt`, crashing the validating/executing node process. Because this code runs on the hot path for any function call receipt, this is a chain-halting node panic reachable from ordinary, unprivileged transaction execution once the parameter is misconfigured - not a validator/malicious-node-only condition; the trigger is a normal transaction, only the misconfiguration vector is a protocol/genesis parameter.

### Likelihood Explanation
Likelihood is currently low in practice because current mainnet/testnet values for `burnt_gas_reward` keep numerator ≤ denominator, and changing this parameter requires a protocol-config change (genesis at chain start, or a future protocol upgrade). However, the missing validation is a real gap: nothing in the codebase enforces the invariant, so a single mistaken parameter definition (e.g., in a future `res/runtime_configs/*.yaml` diff or a testnet/custom-chain genesis) would silently pass all existing validation code and only fail at runtime with a panic during normal chunk application.

### Recommendation
Add an explicit validation check (mirroring the existing `gas_price_adjustment_rate < 1` check in `genesis_validate.rs`, and ideally also in the protocol parameter-table/config-store validation) asserting `burnt_gas_reward.numer() <= burnt_gas_reward.denom()` and that both numerator and denominator are non-zero/positive, rejecting genesis or config changes that violate the invariant. Additionally, replace the unchecked `.unwrap()` at `runtime/runtime/src/lib.rs:999` with a saturating/clamped operation (e.g., `min(receiver_reward, tx_burnt_amount)`) as defense-in-depth against future unvalidated protocol parameters.

### Proof of Concept
1. In a test/private-chain genesis or `RuntimeFeesConfig` construction, set `burnt_gas_reward = Rational32::new(2, 1)` (i.e., 200%), which passes both `validate_genesis` and `validate_config` unchanged since neither checks this field. [5](#0-4) 
2. Submit any `FunctionCall` transaction that burns gas.
3. During `apply_action_receipt`, `receiver_gas_reward` computed from the misconfigured ratio exceeds `gas_burnt_for_function_call`/`tx_burnt_amount`, and `tx_burnt_amount.checked_sub(receiver_reward).unwrap()` panics, crashing the node applying the chunk. [6](#0-5)
