### Title
Cross-tenant membership webhook allows an attacker with only their own org's webhook_secret to add an arbitrary GitHub user to another organization's `Team` and gain `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` only checks that the request is validly signed for the organization named in `repository_owner` (derived from the same payload), then dispatches to `MembershipHandler#process` which resolves the target `Team` purely by `params.team.id` via `Team.find_or_create_by!(github_id: params.team.id)`. Because the signing organization is never compared against the organization that actually owns the referenced `team.id`, an attacker who legitimately controls org A's `webhook_secret` can send a `membership` event whose `team.id` matches a pre-existing `Team` belonging to org B, causing Shipit to add an attacker-chosen user as a member of org B's team.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `Shipit.github(organization: repository_owner).webhook_secret` (the key used to accept the request in `verify_signature`, [1](#0-0) ) must equal the `webhook_secret` of the organization that actually owns `Team#github_id == params.team.id` before that team's membership is mutated - and nothing in the code enforces this.

Path:
1. `WebhooksController#create` runs `before_action :verify_signature`, which computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and validates the raw request signature against `Shipit.github(organization: repository_owner)`'s app secret. [2](#0-1) 
2. Since a `membership` payload's `organization.login` is attacker-controlled and equal to the attacker's own org A, this check passes using org A's legitimately-known `webhook_secret` - no cross-org validation occurs.
3. `create` then dispatches unconditionally to every registered handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
4. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }`. [4](#0-3)  If a `Team` row with that `github_id` already exists (belonging to org B), `find_or_create_by!` returns the existing record and the block (which would set `team.organization = params.organization.login`) never runs - the pre-existing org B team is used as-is.
5. `process` then does `team.add_member(User.find_or_create_by_login!(params.member.login))`, appending the attacker-named GitHub login as a member of org B's team. [5](#0-4) 

Root cause: `repository_owner` is used only to pick the signing key, and is never re-derived or cross-checked inside the handler against the organization that actually owns the numeric `team.id` being mutated. The `organization.login` in the payload is attacker-supplied and used purely for signature-org lookup, not for authorizing which `Team` row can be touched.

Why existing guards don't help: `verify_signature` validates payload authenticity for org A only; it says nothing about whether the referenced `team.id` belongs to org A. The `ExplicitParameters` schema in `MembershipHandler` only enforces types/presence, not cross-organization consistency. `Team.find_or_create_by!` keys strictly on `github_id`, silently reusing any existing team regardless of the requesting org.

### Impact Explanation
The attacker can make Shipit believe an arbitrary GitHub user is a member of any pre-existing `Team` whose numeric `github_id` they can guess or learn (team IDs are visible via GitHub's public API), including teams referenced by `Shipit.github_teams`, which directly gate authorization: `User#authorized?` returns true if `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. [6](#0-5)  This is a genuine cross-tenant write: a payload signed for org A mutates a `Team` (and via it, effective authorization) belonging to org B. This is repeatable against any known/guessable `team.id` and any GitHub login, and matches "High - escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: attacker needs their own valid `webhook_secret`-signed `membership` webhook (trivial - they own org A and can configure/trigger a webhook there or fabricate a matching signature using their own known secret), and needs the numeric `github_id` of the target org B's Shipit-authorizing team (obtainable from GitHub's public teams API if the team/org is discoverable, or already known if attacker previously was briefly a member). No Shipit session, API token, or GitHub App private key is required - only the attacker's own legitimately-provisioned org secret. This is a low-cost, repeatable attack limited to organizations already onboarded into Shipit (i.e., a `GithubApp`/`Team` record exists), which is a realistic multi-tenant Shipit deployment scenario.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found/created `Team#organization` matches `params.organization.login` (or better, matches the signature-verified `repository_owner`/organization passed down from the controller) before mutating membership; raise/reject if they differ instead of silently reusing an existing cross-tenant team. More generally, thread the signature-verified organization from `WebhooksController` into every handler and have handlers assert it against every organization-scoped record they touch.

### Proof of Concept
Minitest `ActionDispatch::IntegrationTest` under `test/controllers/webhooks_controller_test.rb` (existing suite):
1. Create `GithubApp` fixture for org A with a known `webhook_secret`.
2. Create a pre-existing `Team` fixture with `organization: 'org-b'`, `github_id: 999`.
3. Build a `membership` JSON payload with `organization.login = 'org-a'`, `team.id = 999`, `team.name/slug/url` arbitrary, `action: 'added'`, `member.login: 'attacker-controlled-user'`.
4. Compute `X-Hub-Signature` using org A's `webhook_secret` over the raw payload.
5. POST to `/webhooks` with `X-Github-Event: membership` and the computed signature.
6. Assert before: `Team.find(org_b_team.id).members.exclude?(User.find_by(login: 'attacker-controlled-user'))`.
7. Assert after: response is `200 OK`, and `Team.find(org_b_team.id).members.include?(User.find_by(login: 'attacker-controlled-user'))` — proving org A's signature caused a membership mutation on org B's team, i.e., `Shipit.github(organization: 'org-a').webhook_secret` (used to accept) `!=` the binding required to mutate `Team#organization == 'org-b'`.
