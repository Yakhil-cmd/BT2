### Title
Cross-repository status forgery via unscoped commit SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the **organization** named in the payload (via `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature`), but `Handlers::StatusHandler#process` writes a `Status` to **every** `Commit` row that matches the payload's `sha`, regardless of which repository/organization that commit belongs to. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
The controller resolves which GitHub App/organization's secret to use for HMAC verification purely from the payload's `repository.owner.login` (or `organization.login`) field: [1](#0-0) [2](#0-1) 

Once the signature is verified for that organization, the raw JSON is dispatched to `Shipit::Webhooks.for_event(event)` handlers with no further scoping: [3](#0-2) 

Every other handler (`PushHandler`, `PullRequest::*Handler`) scopes its side effects through `Handler#stacks`/`#repository_name`, which filters by `payload.dig('repository', 'full_name')`: [4](#0-3) 

`StatusHandler`, however, does not use this scoping at all. It looks up commits **globally by SHA** and applies the status to any matching row: [5](#0-4) 

Git commit SHAs are content-addressed and are identical across forks/mirrors of a repository (same tree, same parent, same author/committer timestamps). If Shipit is configured with multiple GitHub Apps/organizations (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications"), or if the attacker's own org/repo is legitimately configured on the same Shipit instance, an attacker who controls a fork of the target repository can:
1. Push a commit to their own fork that is byte-for-byte identical (and thus has the identical SHA) to a commit already tracked in the victim stack (this SHA is public/known via GitHub).
2. Send a legitimately-signed `status` webhook from their own org/repo (signed with their own org's `webhook_secret`, satisfying `verify_webhook_signature` for their own organization).
3. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against the victim's `Commit` row (belonging to a different stack/repository) and calls `commit.create_status_from_github!(params)` on it, injecting a forged CI status (e.g. `success`) for a commit the attacker does not control in the target repository.

The equality that should hold but doesn't: `organization that signed the webhook == owner of the repository whose Commit row is mutated`. The verified side is the attacker's own organization/app; the mutated side is any repository's commit row that happens to share the SHA.

### Impact Explanation
Shipit's continuous-deployment and merge-queue logic depends on commit statuses to decide whether a commit is safe to deploy or merge (`Commit#create_status_from_github!` → `add_status` → triggers `ProcessMergeRequestsJob`, deployability checks, etc., per `test/models/commits_test.rb`). Forging a `success` status on a target repository's commit that never actually passed the target's CI can cause an unauthorized deploy or an unauthorized merge-queue advance — this satisfies the "Critical: unauthorized deploy/merge" bar since it lets an attacker manufacture the CI signal Shipit trusts to gate deploys/merges, without needing write access to the target repository itself.

### Likelihood Explanation
Requires: (a) the target commit's SHA to be known (public on GitHub) and (b) the attacker to control some repository/org configured with a GitHub App on the same Shipit instance (their own account, or a multi-tenant Shipit install where any team can install the app on their own org — a documented supported configuration). Producing a colliding SHA is trivial since SHAs are simply copied via `git fetch`/fork — the attacker doesn't need to reproduce the commit, only to have that same commit object reachable in a repo they control (e.g., fork the target repo, or if the target commit is already public, host it in any repo they control) and then emit a `status` event referencing it. No cryptographic collision is needed. This makes the likelihood realistic in shared/multi-org Shipit deployments.

### Recommendation
Scope `StatusHandler#process` (and any other handler that mutates cross-tenant state) to the repository named in the payload, consistent with the base `Handler` class's `stacks`/`repository_name` pattern, e.g. restrict the `Commit` lookup to `stack.repository` matching `payload.dig('repository', 'full_name')` before applying the status, rather than a bare `Commit.where(sha:)`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: one for `victim-org` (tracking `victim-org/app`) and one for `attacker-org` (attacker owns this org and its webhook secret).
2. Attacker forks `victim-org/app` into `attacker-org/app-fork`, ensuring their fork contains the exact same commit object (SHA `abc123`) as the commit currently tracked/pending in the `victim-org/app` Shipit stack.
3. Attacker sends a `status` webhook to Shipit, signed with `attacker-org`'s webhook secret, with `repository.full_name = "attacker-org/app-fork"` and `sha = "abc123"`, `state = "success"`, `context = "<the release_status_context configured for victim-org/app>"`.
4. `WebhooksController#verify_signature` succeeds (signature valid for `attacker-org`).
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the victim's `Commit` row, and calls `create_status_from_github!`, marking the victim's commit as passing — potentially unblocking deploy/merge queue actions in `victim-org/app`'s stack despite the attacker never having write access to it.
