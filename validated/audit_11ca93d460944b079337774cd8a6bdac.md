### Title
Non-reward-asset tokens sent to an `asset-rewards` pool account become permanently unrecoverable after `cleanup_pool` - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards` derives a deterministic, keyless pool account for every reward pool via `Pallet::pool_account_id` (`PalletId::into_sub_account_truncating(pool_id)`) [1](#0-0)  and only ever moves the pool's designated `reward_asset_id` out of that account, via `harvest_rewards` and `cleanup_pool` [2](#0-1) [3](#0-2) . Because the pool account is a plain, publicly-computable `AccountId`, any signed user can send an arbitrary, unrelated asset to it using the ordinary `pallet-assets` `transfer` extrinsic. There is no pallet call capable of moving any asset other than `reward_asset_id` out of that account, and `cleanup_pool` deletes the `Pools` entry (`Pools::<T>::remove(pool_id)`) once the reward asset is swept, permanently severing the only authorization path (`pool_info.admin == who`) that any future call could use to reference that account for that pool id [4](#0-3) . This mirrors the reported Solidity bug class: a vault/pool `withdraw`/cleanup routine hard-coded to a single token, leaving any other token that reaches the vault stuck with no recovery mechanism.

### Finding Description
- `PoolInfoFor<T>` stores a `staked_asset_id`, `reward_asset_id`, and an `account` field that is the pool's dedicated, keyless holding account [5](#0-4) .
- `deposit_reward_tokens` is explicitly documented as "not strictly necessary (tokens could be transferred directly to the pool pot address)" [6](#0-5) , confirming that arbitrary direct transfers to the pool account by any signed account is an expected, reachable interaction surface, not merely a theoretical corner case.
- The only functions that move funds out of `pool_info.account` are:
  - `harvest_rewards`, which only transfers `pool_info.reward_asset_id` [2](#0-1) .
  - `cleanup_pool`, which computes `reducible_balance` and transfers only `pool_info.reward_asset_id`, then deletes the pool's storage record and drops its `PoolCost` consideration [7](#0-6) .
- Neither function (nor any other extrinsic in the pallet) is parameterized to sweep an arbitrary asset id from the pool account, unlike the `withdraw` fix recommended in the source report (`withdraw(address token, uint256 amount)`).
- Once `cleanup_pool` executes, `Pools::<T>::get(pool_id)` returns `None` for all future calls, so every remaining call in the pallet that needs `pool_info.admin` authorization (`stake`, `unstake`, `harvest_rewards`, `set_pool_*`, `cleanup_pool` itself) fails with `Error::<T>::NonExistentPool` — there is no path, privileged or not, to move any asset other than the original `reward_asset_id` out of that now-orphaned account ever again.
- The codebase itself already recognizes third parties can pre-fund a deterministically-derived pallet pot account with arbitrary assets: `pallet-asset-conversion`'s `cannot_block_pool_creation` test has an "attacker" account computing a not-yet-existing pool account and sending 14 different unrelated asset ids to it before pool creation [8](#0-7) , confirming this "any signed user can pre-fund a derived pot account with any asset" pattern is a realized, exercised code path in this codebase family, not a hypothetical.
- `pallet-asset-rewards` is wired into shipped reference runtimes (`asset-hub-westend`, `asset-hub-rococo`, `substrate/bin/node/runtime`, `staking-async` parachain runtime), so the pallet's public calls and the pool account derivation are real, deployed, user-reachable surfaces, not test-only code.

### Impact Explanation
Any tokens of an asset other than the pool's configured `reward_asset_id` that end up in the pool account (whether via `deposit_reward_tokens`-style direct transfer by mistake, or a third party deliberately sending an unrelated/valueless-looking asset there) are permanently frozen once the admin calls `cleanup_pool`, since the account is keyless (derived, no private key) and the only pallet-level authorization path to move funds from it is deleted along with `Pools::<T>::remove(pool_id)`. This is an irreversible freezing of funds with no admin, root, or governance recovery mechanism inside the pallet, matching a Medium-severity "fund recovery mechanism is broken" class of finding, analogous to the reported Allo `DonationVotingMerkleDistributionBaseStrategy.withdraw` issue.

### Likelihood Explanation
Likelihood is realistic but requires either (a) a mistaken transfer of the wrong asset id to the well-known, publicly-derivable pool account (a routine user error given `deposit_reward_tokens`'s documented equivalence to a raw transfer), or (b) a third party deliberately pre-funding/griefing the account with an unrelated asset before or after `cleanup_pool`. No privileged role, governance, or stolen keys are required — only a standard signed `pallet-assets::transfer` extrinsic targeting a publicly computable `AccountId`.

### Recommendation
Add a permissioned (pool-admin-gated, or root-gated post-cleanup) extrinsic that can sweep an arbitrary caller-specified `asset_id` balance out of a pool's account, similar to the source report's recommended `withdraw(address token, uint256 amount)` fix — i.e., decouple the swept asset id from the hard-coded `reward_asset_id`, and/or refuse to remove `Pools::<T>` (or retain a minimal recovery mapping) until any non-reward-asset balance on the pool account has been confirmed to be zero or explicitly swept.

### Proof of Concept
Not executed. Guard status: `cleanup_pool`'s only sweep targets `pool_info.reward_asset_id` and unconditionally removes the pool record afterward with no other recovery call in the pallet (verified by reading `substrate/frame/asset-rewards/src/lib.rs` calls `stake`/`unstake`/`harvest_rewards`/`deposit_reward_tokens`/`cleanup_pool`, all gated on `Pools::<T>::get(pool_id)`). A concrete Rust integration reproduction (mock runtime, mint a second asset, `Assets::transfer` it to `AssetRewards::pool_account_id(pool_id)`, call `cleanup_pool`, then assert the second asset balance remains non-zero and unrecoverable via any exposed call) was not run in this session; this would be the recommended next step to obtain empirical confirmation before filing.

		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

fn cannot_block_pool_creation() {

		let attacker = 2;
