Confirmed: this codebase's multi-tenant GitHub App configuration keys the webhook signature secret purely off the org name embedded in the payload, while every event handler that actually mutates state re-derives the target repository from a *different* field (`repository.full_name`) of the same unverified-at-parse-time JSON body, with no cross-check that the two agree.

### Title
Webhook signature is validated against the org named in the payload, not the repository the handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App (and therefore which `webhook_secret`) to validate `X-Hub-Signature` against using `repository_owner`, computed as `params.dig('repository','owner','login')` (fallback `organization.login`). Every handler that performs the actual write (creates teams/users/memberships, syncs stacks, closes/merges review stacks, updates PR state) instead resolves its target strictly from `payload.dig('repository','full_name')` via `Shipit::Repository.from_github_repo_name` [1](#0-0) [2](#0-1) . Nothing in the controller or in `Shipit.github_app_config` enforces that the owner used to select the signing secret is the same tenant that owns the repository the handlers subsequently act on [3](#0-2) .

### Finding Description
In the multi-org configuration schema, each GitHub organization has its own `webhook_secret` under `secrets.github[org]` [4](#0-3) . `verify_signature` selects the app/secret with:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [5](#0-4) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 
This value comes straight from the (not-yet-verified) request body, before any signature has been validated. Once `head(422) unless verified` passes, the raw body is handed unmodified to every registered handler for the event [7](#0-6) .

Handlers never re-check `repository.owner.login`; they instead derive the acted-upon repository from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [1](#0-0) 
and PR handlers do the same via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) [8](#0-7) .

`owner.login` and `full_name`'s owner segment are two independently attacker-controlled JSON fields inside the same signed HTTP body — the HMAC covers the raw bytes, but covering the bytes says nothing about whether the *semantic* field the controller uses to pick the secret (`owner.login`) is the same tenant as the *semantic* field the handler uses to pick the target (`full_name`). Because `Shipit.github_app_config` does a case-insensitive keyed lookup purely on the caller-supplied `organization` string [4](#0-3) , any org that (a) is configured as a tenant on this Shipit instance and (b) knows/controls its own `webhook_secret` can sign a payload where `repository.owner.login` equals its own org (so verification succeeds against its own legitimate secret) while `repository.full_name` names a repository belonging to a *different* configured org/tenant. The equality the system implicitly relies on — "the org whose secret authenticated this request" == "the org whose repository is written by the handler" — is never enforced.

This is the same class of bug as the referenced report: `OmoAgent.sol`'s `onlyAgent` modifier checks `msg.sender` against a stored per-id agent, but the report's underlying concern is that a privileged binding (EntryPoint-only calls) can be routed around because the check is keyed on a value the caller controls without tying it to the actual op being executed. Here, the binding "signing tenant" ⇔ "repository written" is likewise never cross-validated, even though both values live in the same attacker-supplied JSON.

### Impact Explanation
In a Shipit deployment configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" schema [9](#0-8) ), an attacker who controls the webhook secret for organization A (e.g., because they administer that GitHub App, or the secret leaked for that one tenant) can forge a `push`, `pull_request`, `status`, `check_suite`, or `membership` event whose `repository.owner.login` is A but whose `repository.full_name` names a repository under tenant B. The signature check passes (it's validated against A's real secret over the real raw bytes), but the handler acts on B's stack/repository — triggering an unauthorized deploy trigger (`GithubSyncJob`), archiving/unarchiving B's review stacks, mutating B's PR state, or creating/removing team memberships scoped to B's `Shipit.github_teams` authorization. This crosses a cross-tenant/cross-repository write boundary using credentials that were never authorized for that repository.

### Likelihood Explanation
Requires the attacker to control a legitimate webhook secret for *any one* configured tenant on a multi-org Shipit instance (a lower bar than compromising the specific target tenant's secret), and requires the deployment to use the multi-org config schema. This is a realistic operational configuration explicitly documented and supported by the engine.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, assert that `repository_owner` (the org whose secret validated the request) matches the owner segment of `repository.full_name` (the org whose repository the handlers will act on) before dispatching to handlers; reject with 422 on mismatch. Alternatively, have `Shipit::Webhooks::Handlers::Handler` accept the verified `organization` from the controller and require `Repository.from_github_repo_name` to belong to that same organization, refusing to act otherwise.

### Proof of Concept
1. Configure Shipit with two tenants, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org schema).
2. As an operator/attacker with knowledge of `org-a`'s `webhook_secret` (e.g., a compromised or malicious GitHub App owner for org-a), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=` HMAC-SHA1 of the raw body using `org-a`'s `webhook_secret`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` computes `repository_owner == "org-a"`, fetches `org-a`'s `GitHubApp`, and `verify_webhook_signature` succeeds against `org-a`'s real secret over the real body [5](#0-4) .
5. `PushHandler#process` resolves `stacks` from `payload.dig('repository','full_name')` = `"org-b/target-repo"` [1](#0-0) [10](#0-9) , enqueuing a `GithubSyncJob`/deploy-trigger sync against `org-b`'s stack despite the request never being authenticated by `org-b`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
