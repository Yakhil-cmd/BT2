This confirms Shipit's multi-tenant architecture: `Shipit.github(organization:)` supports multiple GitHub App configs keyed per organization, each with its own `webhook_secret`, `app_id`, `installation_id` [1](#0-0) , and `WebhooksController#verify_signature` selects the app config purely based on `repository_owner` derived from the untrusted JSON payload (`params.dig('repository','owner','login')`) [2](#0-1) . This is exactly the multi-tenant setup the question describes: tenant A (owning repo A, with a legitimately configured webhook secret for their org) is cryptographically isolated only at the signature layer, not at the data layer.

### Title
Cross-repository Status forgery via global SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` across the entire `commits` table, without ever restricting the query to the repository named in the signed webhook payload via `Handler#stacks`/`repository_name`. Because Git commit SHAs are content-addressed and identical commits legitimately exist across independent repositories (forks, cherry-picks, mirrors), a tenant who owns repository A can trigger a validly-signed `status` webhook for A and cause a `Status` row to be written onto a commit belonging to an entirely unrelated tenant B's stack.

### Finding Description
The broken binding: `repository_of(status_written) == repository_named_in(verified_payload)` must hold for the status webhook to be tenant-scoped, but it does not.

Code path:
1. `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [3](#0-2) .
2. `verify_signature` only proves the payload was signed by the app config for whichever organization is `params.dig('repository','owner','login')` — i.e., it authenticates "this payload really came from GitHub for org A", not "this payload authorizes changes limited to org A's repositories" [4](#0-3) .
3. `Handler#stacks`/`repository_name` exist precisely to scope handler logic to the repository named in the payload, and are used by `PushHandler`, `CheckSuiteHandler`, and all `PullRequest::*Handler`s [5](#0-4) [6](#0-5) [7](#0-6) .
4. `StatusHandler#process`, however, never calls `stacks` or checks `repository_name`; it queries `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match, regardless of which stack/repository owns that commit [8](#0-7) .
5. `Commit#create_status_from_github!` unconditionally persists a `Status` record tied to `stack_id` derived from the commit's own stack — it performs no cross-check against the webhook's originating repository [9](#0-8) .

Exploit flow: Attacker owns repository A, onboarded to the same Shipit instance (with a legitimate `webhook_secret` for A's organization configured under `Shipit.github_app_config`). Attacker crafts or force-pushes a commit into repo A whose SHA collides with a commit already present in tenant B's `Commit` table (git commit objects are content-addressed SHA-1 hashes of tree+parents+author+committer+message+timestamps; identical commits legitimately recur across forks/cherry-picks/mirrors, and an attacker who can view B's public commit metadata, or who forked B's repo, can reproduce an identical commit object with an identical SHA in A). Attacker then triggers (or has GitHub trigger) a `status` event for repository A with that `sha` and `state: success`, correctly signed with A's webhook secret. `WebhooksController#verify_signature` passes (signature is valid for org A). `StatusHandler#process` finds the row(s) in `shipit_commits` with that SHA — which include B's commit — and writes a fabricated `success` Status against B's commit, bypassing any relationship to A's `stacks`.

Existing guards do not stop this: `verify_signature` only proves the payload's authenticity for organization A, not that the affected data belongs to A; `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`/`state`, not repository ownership; there is no `stacks`/`repository_name` check anywhere in `StatusHandler`.

### Impact Explanation
A `Status` row is written to `shipit_statuses` against a commit belonging to a different tenant's stack, which can flip that commit's CI state to `success` (`Status.replicate_from_github!` creates the row, and `Commit#create_status_from_github!` recomputes commit state via `add_status`) [10](#0-9) . Because `deployable?` gates on `success? && !blocked?` [11](#0-10) , and `Status#after_commit` schedules `schedule_continuous_delivery` [12](#0-11) , a forged "success" status on tenant B's commit can make that commit eligible for automatic deploy under a `continuous_deployment`-enabled stack B — an unauthorized deploy triggered by a payload for repository A. This matches the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable against any commit SHA the attacker can reproduce, across any tenant sharing the Shipit instance.

### Likelihood Explanation
Preconditions: multi-tenant Shipit deployment where multiple organizations/repos share one instance (supported natively via `Shipit.github_app_config` per-organization secrets) [1](#0-0) ; attacker must own/administer a repository (A) already registered with that Shipit instance and control (or be able to trigger) a `status` event for it with an attacker-chosen `sha`; attacker must be able to produce a commit whose SHA-1 matches a target commit in tenant B (trivial for forks/mirrors/cherry-picks of public commits, harder but not impossible for private repos whose commit metadata the attacker can observe by other means). No Shipit secrets, sessions, or API tokens are required beyond the ordinary ability to sign webhooks for A, which repo/org admins possess by design. This is straightforward to reproduce with a minitest integration test.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring `PushHandler`/`CheckSuiteHandler`: restrict the commit lookup to `stacks.flat_map(&:commits)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status from repo A writes a Status onto a commit belonging to a different stack/repo (cross-tenant)" do
  request.headers['X-Github-Event'] = 'status'

  commit_b = shipit_commits(:cyclimse_first) # belongs to a different stack/repo than :shipit
  stack_b_repo_full_name = commit_b.stack.repository.full_name
  payload_repo_full_name = 'shopify/shipit-engine' # repo A, unrelated to stack_b

  refute_equal stack_b_repo_full_name, payload_repo_full_name

  body = {
    'sha' => commit_b.sha,
    'state' => 'success',
    'repository' => { 'full_name' => payload_repo_full_name, 'owner' => { 'login' => 'shopify' } }
  }.to_json

  assert_difference -> { commit_b.statuses.count }, 1 do
    post :create, body:, as: :json
  end

  status = commit_b.statuses.last
  assert_equal 'success', status.state
  assert_not_equal payload_repo_full_name, commit_b.stack.repository.full_name
end
```
This demonstrates `repository_of(status_written)` (=`commit_b.stack.repository.full_name`) diverging from `repository_named_in(verified_payload)` (=`payload_repo_full_name`), proving the cross-tenant write.
