### Title
Stack-scoped `ApiClient` can create arbitrary stacks outside its authorized `stack_id` scope - (File: app/controllers/shipit/api/stacks_controller.rb)

### Summary
`Shipit::Api::StacksController#create` never restricts stack creation to the requesting `ApiClient`'s bound `stack_id`, breaking the binding: `ApiClient.stack_id (the stack a token authorises)` == `Stack the action can touch`.

### Finding Description
`ApiClient` supports an optional `belongs_to :stack` scope [1](#0-0) . Every read/write/update/destroy action in the API is expected to be constrained to that scope through the `stacks`/`stack` helpers in `BaseController`: [2](#0-1) 

`StacksController#index`, `#show`, `#update`, `#destroy`, `#refresh` all resolve the target through `stack`/`stacks`, which filters by `current_api_client.stack_id` when the client is scoped [3](#0-2) . However `#create` builds a brand-new `Stack` directly from client-supplied `repo_owner`/`repo_name` params and never consults `current_api_client.stack_id` at all: [4](#0-3) 

The only gate on `create` is the coarse `write:stack` permission check [5](#0-4)  via `ApiClient#check_permissions!`, which only checks the permission string, not the `stack_id` binding [6](#0-5) . As a result, a token that is scoped (`stack_id` set) to authorize writes for one specific stack/repository can create entirely new `Stack` records for any other repository the GitHub App has access to, because `create` performs no equivalence check between `current_api_client.stack_id` and the stack it is acting on — mirroring the reported bug class where `invest()` never checked the invariant (`endTime`) that was supposed to gate the action, allowing the operation to proceed outside its intended scope.

### Impact Explanation
This is a cross-repository write: an `ApiClient` intended to be confined to a single stack (e.g., an integration token for repo A) can provision new `Stack` records — and thus deployment pipelines — for arbitrary other repositories the GitHub App is installed on, which is an unauthorized action outside the credential's authorized scope. This matches the "cross-repository writes" Critical-impact category defined in scope.

### Likelihood Explanation
Exploitation requires possession of a valid, stack-scoped `ApiClient` token that has been granted `write:stack` permission. This is a legitimate configuration supported by the data model (`stack_id` + `permissions` are independent, orthogonal fields with no validation tying them together), so any deployment consumer who provisions a scoped token with write permission for automation purposes is silently exposed to this over-broad capability. It does not require any additional privilege beyond what the token already holds.

### Recommendation
In `StacksController#create`, reject the request (403) when `current_api_client.stack_id?` is true, since a stack-scoped client should never be able to create a *new* stack outside — or even inside — its own singular scope. Alternatively, enforce that `create_params`/`repository` resolve to the exact `repo_owner`/`repo_name` of `current_api_client.stack`, and update `ApiClient#check_permissions!` (or add a dedicated check) to validate the `stack_id` binding for every stack-mutating action, not just those that already route through `stack`/`stacks`.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack_id: shipit-repo-A` with permission `write:stack` (supported combination; nothing in the model/UI prevents it).
2. Using that client's `authentication_token`, attacker calls:
   `POST /api/stacks?repo_owner=other-org&repo_name=other-repo&environment=production&branch=main`
3. `StacksController#create` only checks `write:stack` permission [5](#0-4)  and never checks `current_api_client.stack_id`, so `Stack.new(create_params)` succeeds for the unrelated repository [4](#0-3) , creating a stack the token was never authorized to touch.
