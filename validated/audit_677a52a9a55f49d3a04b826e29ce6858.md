### Title
Cross-repository status forgery in `StatusHandler#process` lets an attacker mark a victim's commit `success`, causing `Stack#next_commit_to_deploy` to select it for deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by `sha`, with no scoping to the repository/organization that authenticated the incoming webhook. An attacker who controls a repository whose commit history intersects with the victim's (e.g., a shared/forked commit object with an identical SHA) can send a legitimately-signed `status` webhook for their own org and have it update the status of a `Commit` row belonging to a completely different stack, feeding directly into `Commit#deployable?` and `Stack#next_commit_to_deploy`.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`organization_that_signed(request) == commit.stack.repository.owner` for every `Commit` mutated by the handler.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes from the **attacker's own payload** (`params.dig('repository','owner','login')`), and verifies the HMAC signature against **that same organization's** `webhook_secret`. This correctly proves "this request really came from GitHub for org X," but X is the attacker's own org, not the victim's.
- The verified payload is then dispatched to `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This query has **no repository/stack scoping** - it matches any `Commit` row in the entire database with the given SHA, regardless of which org's webhook secret verified the request.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes a new `Status` bound to `commit.stack_id` - i.e., the **victim's** stack - using the state from the attacker-controlled `params`.
- `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `success?` is derived from the just-forged `status`.
- `Stack#next_commit_to_deploy`/`deployable_commits` (`app/models/shipit/stack.rb`) call `.detect(&:deployable?)` over undeployed commits, so once the forged `success` status lands, the victim commit becomes eligible and, on a continuous-deployment-enabled stack, `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) is triggered by the `add_status` callback path, queuing `ContinuousDeliveryJob` against the victim's stack.

Why existing guards fail: `verify_signature` only proves message authenticity for the org named in the payload; it never checks that the resolved `Commit`/`Stack` records actually belong to that org. `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha, String`) validate shape only, not ownership. There is no `repository.full_name` check tying `params.sha` lookups to `repository_owner`.

Attacker's exact request: a `status` webhook (`X-Github-Event: status`) POSTed to `/webhooks`, signed with the attacker's own org's `webhook_secret` (which the attacker legitimately possesses because they configured the webhook on their own GitHub repo/org), with `sha` set to a SHA that also exists as a `Shipit::Commit` row on the victim's stack (achievable by forking the victim's repo so identical commit objects, and therefore identical SHA1s, exist in both repositories) and `state: "success"`.

### Impact Explanation
A payload authenticated for repository/org A mutates a `Commit`/`Stack` belonging to org B - this is exactly the "payload for one repository mutating another's stack/commit" Critical category, and can lead to an unauthorized deploy being scheduled via continuous delivery on the victim's stack. Blast radius: any Shipit-managed stack whose commit SHAs can be reproduced in an attacker-controlled repository (trivial via forking, since forks share git objects and therefore SHAs for identical commits) is at risk, repeatable per-commit/per-status-context.

### Likelihood Explanation
Preconditions: the attacker needs (1) their own GitHub org/repo registered in Shipit's multi-org config (or any org configured in the host's `Shipit.github` setup) so their webhook is genuinely signed and passes `verify_signature`, and (2) a commit SHA collision with the victim, trivially obtained by forking the victim's public repository (fork commits retain identical SHAs for unmodified history) or by knowing/guessing a SHA already present in the victim's stack. No victim secrets, sessions, or API tokens are required at any point - the attacker only uses their own legitimate webhook signature. This is a low-cost, repeatable exploit for any attacker with a GitHub account able to create a repo and register/point a webhook at the Shipit host.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and the analogous `CheckRunHandler`/other SHA-keyed handlers) to only the repository that authenticated the webhook, e.g. join through `Stack -> Repository` and filter `where(stacks: { repository_id: repository_from_verified_payload.id })`, or pass the verified `repository_owner`/`repository_name` from the controller into the handler and require `commit.stack.repository.owner == repository_owner && commit.stack.repository.name == repository_name` before creating the status.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "a status webhook verified for org A cannot mark a commit belonging to org B's stack as deployable" do
  victim_stack  = shipit_stacks(:shipit)          # belongs to org "victim-org"
  attacker_org  = "attacker-org"
  shared_sha    = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")

  assert_nil victim_stack.next_commit_to_deploy # before: no success status

  # Simulate a status webhook whose signature verifies for `attacker_org`
  # (i.e. WebhooksController#verify_signature passes because it checks
  # Shipit.github(organization: 'attacker-org').verify_webhook_signature)
  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: 'success', context: 'ci/attacker'
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.call(params)

  victim_commit.reload
  assert victim_commit.deployable?
  assert_equal victim_commit, victim_stack.next_commit_to_deploy # after: forged success selected the victim's commit
end
```
This demonstrates the equality `organization_that_signed(request) == commit.stack.repository.owner` is violated: the handler never checks it, and `next_commit_to_deploy` changes from `nil`/unrelated to `victim_commit` solely because of a status forged via an unrelated, attacker-controlled org's webhook.
