### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository/stack scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) via `Commit.where(sha: params.sha)` with no repository, org, or stack filter, unlike sibling handlers (e.g. `CheckSuiteHandler`) which scope through `Handler#stacks` (itself derived from `Repository.from_github_repo_name(repository_name)`). Because Shipit stores one `Commit` row per `(stack_id, sha)`, any status webhook whose `sha` collides with a commit tracked by an unrelated stack updates that unrelated stack's commit state too.

### Finding Description
The broken binding: the code implicitly assumes `Commit.where(sha: params.sha) == {commits belonging to the repository that authenticated this webhook}`, but the actual query is `Commit.where(sha: params.sha) == {every commit row in the whole database with that sha, across every stack/repo/org}` [1](#0-0) .

`WebhooksController#verify_signature` only proves that the webhook was really sent by GitHub for the organization named in `payload['repository']['owner']['login']` (via `Shipit.github(organization: repository_owner)`); it says nothing about which `Stack`/`Commit` rows the event is allowed to touch [2](#0-1) . `Handler#stacks`/`Handler#repository_name` exist precisely to scope processing to `Repository.from_github_repo_name(repository_name)`, and `CheckSuiteHandler` uses that scoping [3](#0-2) [4](#0-3) . `StatusHandler` does not use this scoping at all — it queries `Commit` directly by SHA and calls `commit.create_status_from_github!(params)` for every match, and `create_status_from_github!` delegates to `add_status`/`statuses.replicate_from_github!` which drives the commit's `state`, `deployable?`, and `blocked?` computations that gate ship/rollback/merge decisions [5](#0-4) [6](#0-5) .

Because git commit hashes (SHA-1 over tree, parents, author/committer, message/timestamps) are content-addressed and not scoped to a repository, an attacker can reproduce a byte-identical commit object (same SHA) in a repository they fully control, then legitimately trigger a real, GitHub-signed `status` webhook for `ci/lint` on that SHA from their own repo/org. `verify_signature` will pass because it only checks the signature against the attacker's own org's webhook secret, not against the target stack's repository. `StatusHandler#process` will then match and update any `Commit` row elsewhere in the database that happens to carry the same SHA — including a review-stack commit auto-provisioned for an external PR when `review_stacks_enabled true, allow_all` is set on the victim repository (per `app/models/shipit/repository.rb`'s `provision_pr_stacks`/`allow_all` fields flagged in `db/migrate/20201001125502_add_provision_pr_stacks_flag_to_repositories.rb`).

### Impact Explanation
A single unauthenticated/attacker-controlled `status` webhook can flip the CI/lint status of a commit belonging to a stack the attacker has no relationship with, forcing that stack's `deployable?`/`blocked?` state and, in a `review_stacks_enabled` + `allow_all` configuration, driving an unauthorized ship/merge/block decision on infrastructure the attacker does not control. This is a payload for one repository mutating another repository's/stack's commit state — matching the "Critical: payload for one repository mutating another's stack/commit" impact category. The practical blast radius depends entirely on the attacker's ability to make a colliding SHA appear as a real, GitHub-authenticated status event, which requires either a genuine SHA collision (not offered by SHA-1 in practice for arbitrary chosen content) or reproducing an already-public commit's exact object bytes in a repository they control and then generating a real status event for it — this is possible in principle (git hashing is not repo-scoped) but requires the attacker to already know the exact commit metadata of the victim's tracked commit.

### Likelihood Explanation
Preconditions are significant: (1) the attacker must control a GitHub repository/org onboarded to the same Shipit instance (so `verify_signature` succeeds for their own org's secret) — this is a normal, low-privilege precondition for the multitenant Shipit case; (2) the attacker must produce a `Commit` row with an identical SHA to one tracked in the victim's stack, which requires the victim's target commit's exact content to be known/public and reproducible (typical only for forks/mirrors of the same public commit history, not for arbitrary unrelated repositories); (3) the victim stack must have `review_stacks_enabled true, allow_all` so a matching stack/commit actually exists for an external PR. Given these constraints, the attack is feasible but non-trivial to stage against an arbitrary unrelated victim; it is most directly exploitable when attacker and victim share overlapping commit history (fork scenarios), which is a realistic occurrence in the described PR/review-stack workflow.

### Recommendation
Scope `StatusHandler#process` (and any other bare `Commit.where(sha: ...)`/cross-stack lookups) to the repository that authenticated the webhook, e.g. resolve via `stacks` (as `CheckSuiteHandler` does) or `Repository.from_github_repo_name(repository_name)` before touching `Commit` rows, so a status only ever updates commits belonging to the repository that sent it.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` style):
1. Create two `Stack`s for two different `Repository` full_names (`victim/repo`, `attacker/repo`).
2. Create a `Commit` with the same `sha` (e.g. `"deadbeef" * 5`) under each stack.
3. Build a `status` payload with `repository.full_name = "attacker/repo"`, `sha` = the shared SHA, `context: "ci/lint"`, `state: "success"` (or `"failure"`).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `victim_commit.reload.state` changed to the attacker-supplied state (binding broken: `Commit.where(sha:)` touched a commit outside `attacker/repo`) — i.e., assert `victim_commit.state == "success"` even though the webhook only authenticated `attacker/repo`; the finding is proven if this assertion passes while `victim_commit.stack.repository.full_name != "attacker/repo"`.

      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified

      ].join(' '))

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
