Investigation notes: I searched the codebase for the underlying bug class in CVE-2018-7039 — a signed/unsigned integer type mismatch producing a negative length argument passed into a length-based copy routine (`ccnl_ndntlv_prependBlob`) — and looked for analogous length-prefix/TLV decoding paths reachable from real extrinsic/XCM entry points.

The relevant Rust decode paths in this codebase consistently use unsigned `usize`/`u32` arithmetic with explicit bounds/consistency checks rather than signed lengths that could go negative:

- `UncheckedExtrinsic::decode`/`decode_with_len` verifies the actual consumed byte count against the `Compact<u32>` length prefix and rejects mismatches with `"Invalid length prefix"` rather than trusting an unchecked length. [1](#0-0) 
- The legacy `UncheckedExtrinsicV4::decode` performs the same before/after `remaining_len` comparison against the declared length. [2](#0-1) 
- Trie node header size decoding (`decode_size`) accumulates length using `usize` with a `read_byte()`-driven loop, never taking an attacker-controlled negative or unchecked subtraction into an allocation/copy size. [3](#0-2) 
- Storage stream decoding explicitly guards `into.len() + self.buffer_pos > self.buffer.len()` before any `copy_from_slice`, returning an error instead of performing an out-of-bounds copy. [4](#0-3) 

The one function resembling an unchecked, attacker-length-driven copy — `decode_bytes` in `substrate/frame/revive/uapi/src/precompiles/utils.rs` (lines 138-151), which slices `input[32+offset..32+offset+bytes_len]` without a prior bounds check — is only referenced from a test fixture (`substrate/frame/revive/fixtures/sol_utils.rs`), not from any production precompile or contract-facing code path, so it is not attacker-reachable in a live runtime and is excluded per the report's own rules on test/fixture-only findings.

No production, attacker-reachable decode path was found where an integer type/sign mismatch produces a negative or wrapped length fed into a raw memory copy, which is the specific invariant violated by CVE-2018-7039. Rust's memory-safe slicing means the closest analogous mistakes would panic (denial of service via a controlled panic) rather than corrupt memory, and no such reachable panic-inducing path meeting the report's severity/reachability bar was identified within scope.

```rust
fn decode_size(
	first: u8,
	input: &mut impl Input,
	prefix_mask: usize,
) -> Result<usize, codec::Error> {
	let max_value = 255u8 >> prefix_mask;
	let mut result = (first & max_value) as usize;
	if result < max_value as usize {
		return Ok(result);
	}
	result -= 1;
	loop {
		let n = input.read_byte()? as usize;
		if n < 255 {
			return Ok(result + n + 1);
		}
		result += 255;
	}
}
```
