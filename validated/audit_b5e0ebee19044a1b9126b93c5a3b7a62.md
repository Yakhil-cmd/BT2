### Title
Reused Bitcoin L1 lockup outpoint across multiple `register-for-bond` calls credits sats/STX-lock that were never separately locked on Bitcoin - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 lockup path validates each submitted Bitcoin lockup output via `verify-l1-lockups` → `validate-l1-lockup`, which checks script correctness, amount, block header, and merkle proof, and rejects an outpoint that is duplicated *within the same call* using the `seen-outpoints` accumulator. However, this dedup list is a transient fold accumulator, re-initialized to `(list)` on every call, and there is no persistent contract map recording previously-consumed `(txid, output-index)` outpoints across separate `register-for-bond` invocations. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the DittoETH bug class: a value-crediting operation (`fillShortRecord`/minting DUSD) trusted a collateral amount that had already been consumed/reduced by an earlier caller action, letting the protocol credit more than what was actually backed. Here, the "credited backing" is sats/BTC locked on Bitcoin, and the "crediting operation" is `register-for-bond`'s L1 branch, which turns a verified Bitcoin lockup into `sats-total` and, subsequently, locked STX / bond-membership / signer weight in PoX-5.

`validate-l1-lockup` proves only that:
1. The output script matches the deterministic `construct-lockup-output-script` derived from `(staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes)` [3](#0-2) 
2. The output amount and Bitcoin header/merkle proof are valid [4](#0-3) 
3. The outpoint is not repeated *within this one call's output list* [2](#0-1) 

None of these checks establish that the outpoint has not already been consumed by a prior, separate `register-for-bond` call (by the same staker or, since the script only commits to the `staker` principal and not to a bond-index/nonce, potentially reused for a different bond period). Since PoX-5 stakers can roll over out of a bond and register again (as documented for `register-for-bond`'s roll-over handling), a staker could:
1. Perform one genuine Bitcoin lockup transaction and use it to `register-for-bond` for bond period N, receiving STX lock / signer weight for `sats-total`.
2. Later, unstake/roll over (or simply let the bond end) and call `register-for-bond` again for bond period N+2 (or any bond that accepts the same `unlock-burn-height` ≥ the new bond's minimum), submitting the exact same `(tx, output-index, header, leaf-hashes, ...)` lockup proof.
3. Because there's no persistent "used outpoint" set, `validate-l1-lockup` re-validates successfully (the merkle proof and script check are re-derivable deterministically), and PoX-5 credits `sats-total` again for the new bond, minting a second STX lock / signer commitment backed by the same, single BTC UTXO.

This breaks the equality that "sats credited by an L1 proof" must correspond 1:1 to sats actually locked on Bitcoin — the same locked BTC output is double-counted across bond periods, analogous to DittoETH crediting DUSD (collateral-backed debt) without correspondingly-locked collateral.

### Impact Explanation
This falls under "sats credited by an L1 proof that were never locked on Bitcoin" / "double-counting a commitment or reward" (Critical), since the same physical BTC lockup can back more than one PoX-5 bond membership/STX lock, inflating a staker's effective locked stake and signer weight without new BTC ever being locked, and potentially allowing that inflated weight to earn duplicated sBTC rewards across bond periods.

### Likelihood Explanation
Exploitability requires no privileged role — any unprivileged staker who can obtain approval to `register-for-bond` (subject to allowlist admission, which is a protocol-level gate, not a security boundary preventing this specific reuse) can replay their own previously-submitted, publicly-visible Bitcoin lockup transaction data (header, merkle proof, tx bytes) since these are all public once the original lockup transaction confirms. No secret material or another party's key is required, and the flaw is directly reachable via the exposed `register-for-bond` entry point in pox-5.clar.

### Recommendation
Persist a record (e.g., a `define-map used-l1-lockup-outpoints { txid: (buff 32), output-index: uint } bool`) of every outpoint that has ever been credited via `validate-l1-lockup`, checked and set across all `register-for-bond` calls (not just within a single call's fold), so a given Bitcoin lockup output can only ever be consumed once for the entire lifetime of the contract, mirroring how `used-signer-key-authorizations` prevents replay of signer authorizations in pox-4.clar.

### Proof of Concept
Not independently executed against a running node (no filesystem/terminal access in this session); the above is derived from static analysis of `validate-l1-lockup`/`verify-l1-lockups` and `register-for-bond` in `stackslib/src/chainstate/stacks/boot/pox-5.clar`. I was unable to fully read the entire `register-for-bond` body (lines ~636-900) in the final iteration due to a tool error, so I could not confirm whether some other mechanism outside `verify-l1-lockups` (e.g., a check tying the lockup's `unlock-burn-height` uniquely to one bond, or an implicit nonce embedded in `staker-unlock-bytes`) independently prevents this reuse. This should be verified by a Devin session with full repository and test-harness access, and by tracing whether `register-for-bond` or any caller-side logic records consumed outpoints elsewhere before treating this as production-confirmed.
