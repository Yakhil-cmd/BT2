## Analysis

The binding at risk here is: **the organization whose webhook secret authenticates the request** vs **the repository whose stacks are actually mutated by the handler**. In multi-org Shipit deployments (`Shipit.github_organizations`, `config/secrets.yml` keyed by org), each org has its own `webhook_secret` [1](#0-0) . The DHT analog is exact: GitHub's Sybil peers manipulate which node "owns" content resolution for an ID; here an attacker manipulates which org "owns" signature verification for a payload whose *content* (repository) is different from the *verifying identity* (org).

`WebhooksController#verify_signature` derives the signing org purely from attacker-controlled payload fields and looks up the matching `GitHubApp`/secret to verify against: [2](#0-1) [3](#0-2) 

Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3)  dispatches to handlers that resolve the target repository/stacks from a **separate, independently-controlled** field, `payload.dig('repository', 'full_name')`: [5](#0-4) 

`repository.owner.login` (used for signature routing) and `repository.full_name` (used for stack resolution) are never cross-checked. An attacker who legitimately controls a repository/webhook in Org A (and thus knows Org A's `webhook_secret`) can send a signed payload where `repository.owner.login = "orgA"` (so the signature check passes against Org A's secret) while `repository.full_name = "orgB/some-repo"`. `PushHandler#process` would then call `stack.sync_github(expected_head_sha:)` on Org B's stacks [6](#0-5) , and PR handlers would archive/unarchive or capture labels on Org B's review stacks [7](#0-6) .

This is entirely within the engine's own webhook trust logic (no GitHub App private key, no session, no `ApiClient` token needed), and breaks the "organization that authenticated == repository that is written" binding required by the rules. Whether this rises to "cross-repository writes" depends on whether `sync_github`/label handlers can trigger consequential state changes (e.g., queuing deploys) purely from webhook-driven sync — that needs to be validated against `Stack#sync_github` and downstream deploy-trigger logic before calling it a confirmed cross-org write.

### Title
Cross-Organization Webhook Signature/Target Mismatch Allows Acting on Another Org's Stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify a webhook against using `repository_owner`, derived from `payload.dig('repository','owner','login')` or `payload.dig('organization','login')` [3](#0-2) . After verification succeeds, handlers resolve the actual repository/stack to act on using a different, unrelated field: `payload.dig('repository', 'full_name')` [8](#0-7) . Because these two fields are never checked for consistency, a payload signed with one organization's secret can name a repository belonging to a completely different organization configured on the same Shipit instance.

### Finding Description
In the multi-org configuration schema, `Shipit.github(organization:)` returns a distinct `GitHubApp` (and `webhook_secret`) per organization [9](#0-8) . The controller uses `repository_owner` solely to pick which secret to verify with, then hands the raw, unvalidated JSON payload to every registered handler for the event [4](#0-3) . Handlers such as `PushHandler`, `PullRequest::ClosedHandler`, `PullRequest::ReopenedHandler`, and `LabelCapturingHandler` all resolve their target `Repository`/`Stack` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [10](#0-9) , a field completely independent from the one used for signature routing. There is no check that the signing organization matches the owner segment of `full_name`.

### Impact Explanation
An attacker who controls a webhook trigger for Organization A (e.g. is able to push to or open PRs against a repo in Org A configured on the same Shipit instance) can forge `repository.full_name` to point at an Organization B repository while keeping `repository.owner.login`/`organization.login` set to Org A so the HMAC check passes with Org A's known-to-the-attacker secret context. This causes handlers to run stack-mutating logic (`sync_github`, review-stack `archive!`/`unarchive!`, label capture) against Org B's stacks — a cross-organization/cross-repository action the attacker should not be authorized to trigger.

### Likelihood Explanation
This requires the deployment to use the multi-organization `github:` secrets schema and requires the attacker to have legitimate webhook-triggering ability (e.g. push/PR access) in at least one configured organization — no session, `ApiClient` token, or private key is needed. This is plausible for organizations that host many teams/orgs on a shared Shipit instance.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret matches the owner of `payload.dig('repository', 'full_name')` (and `organization.login`) before dispatching to handlers; reject the request if they differ.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own `webhook_secret`.
2. As a user with push access to a repo in `orgA`, craft a webhook payload:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/main",
  "after": "<sha>"
}
```
3. Sign the raw body with `orgA`'s `webhook_secret` and send as `X-Hub-Signature` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")` and verifies successfully [2](#0-1) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/target-repo")` and calls `sync_github` on `orgB`'s stacks [6](#0-5) , despite the attacker having no relationship to `orgB`.
