### Title
Api::CCMenuController#show bypasses `ApiClient#stack_id` scoping, leaking arbitrary stacks' deploy history - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` defines its own private `stack` method that resolves `params[:stack_id]` via `Stack.from_param!` directly on the `Stack` class, instead of using the `stacks` scope inherited from `Api::BaseController`, which restricts lookups to `current_api_client.stack_id` when the token is scoped to a single stack. `#show` then renders `stack.deploys_and_rollbacks.last`, exposing the target stack's latest deploy/rollback sha, status and timing to any caller holding a valid token — even one explicitly scoped to a different stack.

### Finding Description
The binding that should hold is: `stack returned by CCMenuController#show == the stack authorised by current_api_client.stack_id` (when the token has a non-null `stack_id`). In practice this equality is broken.

`Api::BaseController` defines the scoping guard: [1](#0-0) 

This means for a token whose `ApiClient#stack_id` is set to stack A, `stacks` (and therefore the default `stack` method) is limited to `Stack.where(id: current_api_client.stack_id)` — requesting any other stack's param raises `RecordNotFound`.

However, `Api::CCMenuController` overrides `stack` and does not go through `stacks` at all: [2](#0-1) 

`Stack.from_param!` is called on the unscoped `Stack` class model, not on the `stacks` (already-scoped) relation, so any `stack_id`/slug is resolvable regardless of the authenticated token's stack scope.

The only authorization check performed is `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!`: [3](#0-2) 

This check only verifies that the token's `permissions` array contains `"read:stack"` — it never checks which stack the permission applies to. It is completely orthogonal to the `stack_id` scoping enforced by the `stacks` method in the base controller. Any token with `read:stack` permission and *any* `stack_id` (even a stack-scoped one) passes this check for *every* stack, because `check_permissions!` never references `operation`/`scope` against a specific record.

`#show` then does: [4](#0-3) 

renders `stack.deploys_and_rollbacks.last`, which is the target stack's latest `Deploy`/`Rollback` record — leaking its sha, status, and build timing in the CCTray XML.

Attacker exploit flow: attacker (or any legitimate customer of the Shipit instance) holds a token for stack A that is scoped by `ApiClient#stack_id = A` and has `read:stack` permission (a normal, low-privilege configuration intended to restrict the token to stack A only). They send `GET /api/stacks/:unused/deploys` — actually `GET` to the ccmenu route with `params[:stack_id]` set to stack B's identifier (`owner/repo/branch` or similar) instead of A, along with their valid token. `authenticate_api_client` succeeds (token is valid), `require_permission!(:read, :stack)` succeeds (token has `read:stack` in its permissions list, unrelated to which stack), and `stack` resolves stack B via unscoped `Stack.from_param!`, returning stack B's data.

None of the listed guards (`verify_signature`, `force_github_authentication`, `require_permission!`, model validations) prevent this, because the divergence is a controller-level scoping bug specific to `CCMenuController`'s override of `stack`, not a validation or signature issue.

### Impact Explanation
An attacker who possesses one valid but narrowly-scoped API token (scoped to a single stack via `ApiClient#stack_id`) can enumerate/guess other stacks' `stack_id`/slug params and read their latest deploy/rollback sha, status, and timing — cross-tenant/cross-repository deploy history disclosure. This matches "High - unauthenticated read of stack state" category adapted to unauthorized (out-of-scope) read of stack state via a validly-authenticated but improperly-scoped token. The attack is repeatable against any stack whose param is known or guessable, with no rate limiting relevant to this specific bug's exploitation cost.

### Likelihood Explanation
Preconditions: the Shipit operator must have issued at least one `ApiClient` token scoped to a specific stack (`stack_id` set, which is a supported and documented feature for restricting third-party integrations, e.g. CI dashboards) with `read:stack` permission. Given such a token, exploiting this requires only a single unauthenticated-scope HTTP GET to the ccmenu endpoint with a different `stack_id` — no additional secrets, no privilege escalation, trivially repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from the base controller (i.e., remove the override, or replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])`) so that `ApiClient#stack_id` scoping is honored for CCMenu requests exactly as it is for other API controllers.

### Proof of Concept
minitest plan (add to `test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b` with distinct repositories, each with at least one completed `Deploy` (`stack_b`'s deploy having a distinctive `sha`, e.g. `"b" * 40`).
2. Create an `ApiClient` `@client_a` with `stack_id: stack_a.id` and `permissions: ['read:stack']`; authenticate as `@client_a`.
3. `get :show, params: { stack_id: stack_b.to_param }`.
4. Assert `response.status == 200` and that the returned XML's `lastBuildLabel`/label attribute equals `stack_b`'s deploy sha (proving stack B's data was disclosed despite the token being scoped only to stack A) — i.e., assert equality between `Hash.from_xml(response.body)['Projects']['Project']['lastBuildLabel']` and `stack_b.last_deployed_commit.sha`, which should never match given the token's `stack_id == stack_a.id` binding.
