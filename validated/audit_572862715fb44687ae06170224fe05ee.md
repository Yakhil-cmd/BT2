### Title
Refute-stage diff truncation to 8000 bytes causes cross-stage diff-baseline mismatch, enabling attacker-controlled hunk positioning to defeat PRE-EXISTING/anchor checks - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_investigate_prompt` builds candidate findings against the full (per-file/total-capped) diff, but `build_refute_prompt` re-slices that same diff text with a hard `diff_text[:8000]` head-truncation before handing it to the adversarial refute stage. If a candidate's `vulnerableCode` originates from a hunk positioned after byte 8000 of the concatenated diff, the refute LLM is instructed to check "PRE-EXISTING: the cited vulnerableCode does NOT appear on any + line in the DIFF block above" against a DIFF block that never contained that hunk at all.

### Finding Description
`build_investigate_prompt` (review_api.py:156-176) concatenates all touched files' diffs via `cap_diff_for_prompt` (capped at 80KB/file, 400KB total) and passes the *entire* `diff_text` to the investigate-stage LLM, which emits `candidates` referencing `vulnerableCode` anywhere in that full text.

`build_refute_prompt` (review_api.py:210-283) is then called with those same `candidates` and the same `diff_text`, but truncates it with `diff_text[:8000]` (line 214) before embedding it in the refute prompt. The refute system prompt explicitly instructs the model to REFUTE a candidate under the PRE-EXISTING rule when "the cited vulnerableCode does NOT appear on any + line in the DIFF block above" (lines 234-236). If the diff exceeds 8000 bytes and the flagged hunk sits past that offset, the DIFF block shown to the refute model simply never contains it — the model cannot distinguish "removed by truncation" from "pre-existing, not actually a diff addition," and the KEEP/REFUTE bar and DIFF-ANCHOR in_diff/off_diff logic (lines 222-231, based on `tag_diff_anchor`, which itself scans the *full* `diff_text` for +/- line intersection at review_api.py:291-344) become unreliable for stage 2 because stage 2 is working from a different (truncated) diff scope than the tagging step and stage 1.

Since file order in the concatenated diff is driven by the order files appear in the commit/PR diff (attacker-controlled when authoring the change, e.g. via file naming or diff ordering), an attacker can prepend large, benign-looking diff content (e.g., a big generated/vendored/whitespace-heavy file) ahead of the file containing their injected vulnerability, pushing the real hunk past the 8000-byte cutoff used only in the refute stage. This does not require any privilege beyond authoring the diff/PR that the security-guidance review processes.

### Impact Explanation
This causes the adversarial refute stage to systematically apply the PRE-EXISTING (and other DIFF-ANCHOR-dependent) refutation rules to a truncated, effectively different diff than the one actually reviewed in stage 1, letting an attacker suppress detection of a real vulnerability they introduced. The scoped impact is a security-review bypass: malicious or vulnerable code intentionally positioned past the 8000-byte offset in a padded diff can be nudged from an initially-flagged candidate to a REFUTE/no-finding outcome, defeating the review/export logic's intended detection of the introduced vulnerability.

### Likelihood Explanation
Requires only: (1) a diff/commit exceeding 8000 bytes when concatenated across touched files, and (2) the ability to control ordering/padding of that diff (trivial for any PR author/committer, e.g., adding unrelated large files or reordering changes). No special privilege, key leakage, or social engineering needed — fully reachable via ordinary repository content submitted for review. This makes the issue readily and repeatably triggerable.

### Recommendation
Do not blind head-truncate the diff independently in `build_refute_prompt`. Instead, either (a) reuse the exact same `diff_text` passed to `build_investigate_prompt` without re-truncating in refute (rely on the existing per-file/total caps already applied once), or (b) if a smaller refute-stage budget is required, build a targeted excerpt around each candidate's cited `filePath`/`vulnerableCode` (and its surrounding hunk) rather than truncating from byte 0, ensuring every candidate's evidence region is always present in the diff block the refute stage evaluates.

### Proof of Concept
Unit test in the spirit of `review_api.py`'s existing helpers:
1. Construct `diff_files` such that file `a.py` alone (or several dummy files) produces >8000 bytes of `+`-only filler content, followed by `b.py` containing a single `+`-line with a clearly vulnerable pattern (e.g. `subprocess.run(user_input, shell=True)`).
2. Call `cap_diff_for_prompt`/`build_investigate_prompt` to get the full `diff_text`, and construct a `candidates` list with one entry whose `vulnerableCode` is the `b.py` line (positioned past offset 8000 in the concatenated text).
3. Call `build_refute_prompt(candidates, diff_text)` and assert that the returned prompt's `"DIFF:\n" + diff_text[:8000]` still contains the candidate's `vulnerableCode` substring — expected to FAIL with the current implementation, demonstrating the candidate's evidence is absent from the DIFF block shown to the refute model.
4. Assert (documenting the fix) that after excerpting/removing the blind truncation, the vulnerable line is always included in the refute-stage diff regardless of its offset in the full concatenated diff.
