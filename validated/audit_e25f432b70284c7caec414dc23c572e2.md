### Title
Bypass of AA definition sandboxing via skipped recursive validation of nested `definition` messages - ([File: aa_validation.js])

### Summary
`validateAADefinition()` in `aa_validation.js` enforces all of the AA sandbox's structural safety checks (allowed `app` values, `hasFieldsExcept` field whitelists, output/asset/attestor structure, etc.) through the `case` handlers of `validatePayload()`. When an AA message has `app === 'definition'` (i.e. the AA is programmatically deploying a *nested* AA), the code that would recursively re-run `validateAADefinition` on that nested definition is commented out, so none of those structural sandbox checks are ever applied to the nested AA body.

### Finding Description
In `aa_validation.js`, the `'definition'` case is: [1](#0-0) 

The line that would recursively validate the nested definition's structure is disabled:
```js
//	(typeof setImmediate === 'function') ? setImmediate(validateAADefinition, payload.definition, cb2) : setTimeout(validateAADefinition, 0, payload.definition, cb2);
```
Instead, the code only checks `isNonemptyObject(payload.definition[1])` and calls `cb2()` — it never re-enters `validateAADefinition` for the nested body.

Separately, `validateDefinition`/`validate()` in the same file performs a generic recursive walk of the *entire* top-level `arrDefinition` object tree, calling `validateFormula` on any string value that looks like a formula: [2](#0-1) 

This generic walk only checks whether individual string leaves parse/validate as formulas — with permission flags (`bStatementsOnly`, `bStateVarAssignmentAllowed`) derived purely from `path === '/messages/state'` string matching. It performs none of the `validatePayload` structural checks (allowed `app` types from `exports.aaApps`, field whitelists via `hasFieldsExcept`, output count/shape rules, asset field rules, attestor rules, etc.) that are the actual "sandbox" guarding what an AA-deployed nested AA is allowed to contain.

Because the dedicated recursive `validateAADefinition` call on `payload.definition` is commented out, a nested AA definition created by another AA (`app: 'definition'`) skips those structural sandbox checks entirely — analogous to how the Twig sandbox in October CMS failed to re-apply its restriction policy on a nested/indirect code path, letting an authenticated-but-restricted user (here: any AA/unit author able to submit a `definition` message) smuggle disallowed content past the sandbox because the *specific* enforcement function was bypassed while a *generic*, weaker pass-through check silently accepted the payload.

### Impact Explanation
An AA author (an "authenticated" but supposed to be constrained unit poster under `cms.enableSafeMode`-style structural guarantees) can construct a nested AA `definition` message whose messages/payloads violate the structural invariants normally enforced by `validatePayload` (e.g., unknown `app` values, disallowed extra fields in `payment`/`asset`/`data_feed` payloads, malformed `outputs`, or malformed `asset`/`attestors` fields) yet still pass overall validation via the generic formula-only walk. Because the nested definition subsequently becomes a real, on-chain AA definition (deployed by the parent AA), this can lead to an AA whose message/payload semantics were never checked against the invariants the rest of the codebase (asset issuance, payment output construction, `state` variable protection) assumes to hold, risking node disagreement on the validity of consequent triggers/units built against that malformed nested AA, or unintended state/fund handling once such an AA is triggered.

### Likelihood Explanation
Likelihood is limited by the fact that: (1) most string-typed leaves are still checked as syntactically valid formulas by the generic walk, and (2) I could not fully trace, within tool budget, all downstream consumers (`writer.js`, `aa_composer.js`) to confirm that a specific malformed nested-definition field (e.g., an invalid `app`, or extra fields on `payment`/`asset`) is actually exploited at execution time to produce concrete fund loss, double-spend, or consensus disagreement, versus being caught by unrelated checks elsewhere (e.g. in `writer.js` when saving the AA or in `aa_composer.js` when executing it). This is a real gap in the intended defense-in-depth structural sandbox (the dedicated recursive call is explicitly commented out), but I was not able to verify with certainty a concrete unauthorized-spending/double-spend/consensus-divergence path within the exploration performed, so confidence in real-world exploitability of this specific gap is moderate rather than confirmed.

### Recommendation
Re-enable full recursive structural validation of nested AA `definition` payloads by calling `validateAADefinition` (with proper call-stack-depth protection, as the removed `setImmediate`/`setTimeout` comment suggests) on `payload.definition` before accepting the message, rather than relying solely on the generic formula-string walk in `validate()`. Ensure `hasFieldsExcept`, `aaApps` whitelist checks, and all payload-shape checks are applied to nested definitions identically to top-level AA definitions, and add regression tests deploying nested AAs with structurally invalid inner messages to confirm rejection.

2. Submit a unit triggering `A` so it emits this nested AA definition; per current code, `validateAADefinition`'s `'definition'` case only checks `isNonemptyObject(payload.definition[1])` and returns success without recursing into structural validation, while the generic `validate()` walk only checks that any embedded strings look like formulas.
3. Confirm (in a Devin session, via `aa_composer.js`/`writer.js` trace) whether the resulting nested AA definition with the extra/invalid field is persisted and later triggerable, producing behavior inconsistent with the structural guarantees enforced on ordinary top-level AA definitions.
