## Valid Finding

### Title
Missing length-equality check in `TransactionAuthenticator::verify()` (`MultiAgent`/`FeePayer` branches) allows unsigned secondary-signer addresses to reach execution - (File: `types/src/transaction/authenticator.rs`)

### Summary
`TransactionAuthenticator::verify()` for the `MultiAgent` (and structurally identical `FeePayer`) variant never asserts that `secondary_signer_addresses.len() == secondary_signers.len()` before verifying signatures. It only loops over the `secondary_signers` vector, so any address present in `secondary_signer_addresses` beyond the length of `secondary_signers` is never checked against any authenticator at all.

### Finding Description
The `MultiAgent` arm of `verify()` builds the signing message from `secondary_signer_addresses` (the full intended set of participating accounts) and then iterates only `secondary_signers` (the supplied authenticators) to check signatures: [1](#0-0) 

There is no `ensure!(secondary_signer_addresses.len() == secondary_signers.len())` guard anywhere in this match arm (nor in the analogous `FeePayer` arm at lines 179-224). Both `secondary_signer_addresses: Vec<AccountAddress>` and `secondary_signers: Vec<AccountAuthenticator>` are independent, unconstrained BCS-deserialized vectors on the wire — an attacker fully controls both lengths when constructing the `TransactionAuthenticator::MultiAgent` value at the API/mempool ingress boundary: [2](#0-1) 

If `secondary_signer_addresses` contains `N` addresses but `secondary_signers` contains fewer than `N` authenticators, the `for signer in secondary_signers` loop simply verifies the shorter list and returns `Ok(())` — it never rejects the transaction, and it never checks that every address in `secondary_signer_addresses` has a matching verified authenticator. Downstream, the VM (in `TransactionMetadata`) constructs the `&signer` capabilities for the entry function using `secondary_signer_addresses` (the full address list from the authenticator), not the count of verified `secondary_signers`. This means an address can be granted a `&signer` capability in the executed Move function despite never having produced (or having a checked) signature.

### Impact Explanation
This breaks the core multi-agent invariant that every account listed as a co-signer must have cryptographically approved the transaction. An unprivileged attacker who knows a victim's address (no key material needed) can submit a multi-agent transaction listing the victim as a secondary signer while supplying zero or fewer authenticators than addresses, and `verify()` will still return `Ok(())` for the subset it does check. This is an authenticator/approval-set validation issue that fits the "wrong approval set" and "unauthorized execution under the wrong signer set" impact categories from the admission gate.

### Likelihood Explanation
The `TransactionAuthenticator::MultiAgent`/`FeePayer` variants are directly constructible from unprivileged, unsigned wire input (BCS deserialization of a `SignedTransaction`) at the mempool/API admission boundary — no privileged signer or leaked key is required to build a mismatched-length authenticator. The only barrier is whether the constructed authenticator can otherwise be considered "well-formed" prior to `verify()` being called; there is no length-equality assertion present in this file to stop it before signature checking.

### Recommendation
Add an explicit invariant check at the start of the `MultiAgent` and `FeePayer` verify arms:
```rust
ensure!(
    secondary_signer_addresses.len() == secondary_signers.len(),
    "Number of secondary signer addresses does not match number of secondary signers"
);
```
This should also be verified (or re-verified) at the point where `TransactionMetadata`/execution derives the `&signer` list for secondary accounts, so the two lists can never diverge between admission-time verification and execution-time signer construction.

### Proof of Concept
Conceptually:
1. Attacker knows victim address `V` (public information).
2. Attacker (sender `S`) constructs `TransactionAuthenticator::MultiAgent { sender: sig_over_full_msg, secondary_signer_addresses: vec![V], secondary_signers: vec![] }`.
3. `verify()` computes `message = RawTransactionWithData::new_multi_agent(raw_txn, vec![V])`, verifies only `sender.verify(&message)`, and the `for signer in secondary_signers` loop is a no-op over an empty vector — `verify()` returns `Ok(())` even though `V` never authenticated anything.
4. This should be asserted to fail (`verify()` should return `Err`), but based on the code shown it succeeds.

I was not able to independently trace the exact downstream VM code (`aptos-vm`'s `TransactionMetadata`/prologue) in this pass to confirm the precise mechanism by which the mismatched address is turned into an executable `&signer` capability — that part of the claim is based on my recollection of how `secondary_signer_addresses` is consumed by the VM rather than a citation I verified in this session. The core defect — the missing length-equality check inside `verify()` itself — is directly confirmed in the cited code.
