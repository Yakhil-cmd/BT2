### Title
Attacker-Controlled Submodule Fan-out/Nesting Causes Unbounded Resource Consumption and Persistent Sync Denial - (File: main.go)

### Summary
`WinnablesTicketManager`/`WinnablesTicket` allowed an attacker to buy an unbounded (`uint16.max`) number of tickets, causing the `ownerOf()` linear-scan loop to exceed the block gas limit and permanently DoS the winner-propagation step. The analogous condition in `git-sync` is that `configureWorktree` runs `git submodule update --init --recursive` on every sync, where the number and nesting depth of submodules is fully attacker-controlled content coming from the tracked remote repository (via `.gitmodules` files, including in nested submodules). There is no cap on submodule count/depth, so a repo owner (or anyone who can push a ref/tag/commit that git-sync tracks) can make this single git invocation arbitrarily expensive in CPU, network I/O, and disk, in a way structurally identical to the "unbounded loop driven by attacker-supplied quantity" root cause from the Sherlock finding.

### Finding Description
In `configureWorktree`, after checking out the worktree, git-sync unconditionally shells out to git submodule handling when `git.submodules != submodulesOff` (the default is `submodulesRecursive`): [1](#0-0) 

The `submodulesArgs` are built from a fixed template (`submodule update --init [--recursive] [--depth N]`) and executed via `git.Run(ctx, worktree.Path(), submodulesArgs...)`. Crucially, **the actual number of submodules, and how deeply they nest, is not controlled by git-sync flags at all — it is 100% determined by content the upstream repository owner commits** (`.gitmodules` entries, and `.gitmodules` files inside nested submodules when `--recursive` is used). This is directly analogous to the Sherlock bug where the number of loop iterations in `ownerOf()` was determined by an untrusted quantity (`ticketCount`) rather than being bounded by the protocol.

Default `--submodules` behavior is `recursive`, meaning an attacker who controls (or compromises, or is simply the operator of) the tracked remote repository can add:
- an extremely large number of top-level submodules, or
- a long/deep chain of nested submodules (submodule-of-a-submodule, repeated many levels), or a submodule reference cycle across independently-hosted repos,

and each of these will be walked by `git submodule update --init --recursive` on every single sync attempt, since the loop in `main.go` (the outer sync loop) calls `SyncRepo` → `configureWorktree` every period: [2](#0-1) 

There is no limit on submodule fan-out or recursion depth anywhere in the flag parsing or `repoSync` struct: [3](#0-2) [4](#0-3) 

The only bound on the operation's duration is `--sync-timeout` (default 120s), applied via `context.WithTimeout` around the whole sync attempt: [5](#0-4) 

I was not able to fully confirm within this session whether `git.Run`'s underlying `cmd.Runner` (in `pkg/cmd/cmd.go`) properly propagates `ctx` cancellation to kill the `git submodule update` child process on timeout (i.e., whether it uses `exec.CommandContext` all the way through, or spawns the process in a way that survives context cancellation, e.g. via new process groups for signal handling). This detail affects whether the impact is "sync attempt fails after 120s and retries forever" (persistent sync denial) versus "child process leaks and accumulates, exhausting host resources across repeated timeouts" (more severe resource exhaustion). Either way, the operation is fully attacker-shaped and repeats on every sync period, which is the analog of "DoS them and the protocol" from the source finding.

### Impact Explanation
- **Persistent sync denial**: If each sync attempt times out (or takes excessively long) due to the submodule graph, `git-sync` will never successfully publish an update; `failCount` increments and, unless `--max-failures` allows indefinite retries, git-sync eventually calls `os.Exit(1)`, terminating the sidecar entirely: [6](#0-5) 
This denies the intended atomic-publish contract to downstream consumers indefinitely — the direct analog of "loss of funds for the winner and protocol" (a definite, repeatable denial-of-service triggered purely by content the attacker controls, without requiring any special external condition).
- **Resource exhaustion on host/node**: Even absent a hard timeout kill, unbounded submodule counts/depth can consume large amounts of CPU, disk (each submodule clone), and network bandwidth on every sync cycle, potentially affecting co-located workloads in the Kubernetes sidecar deployment model described in the docs.

### Likelihood Explanation
Likelihood is high for any deployment where `git-sync` tracks a repository not fully trusted/controlled by the operator (e.g., syncing configuration from a repo where multiple parties can open PRs/merge, or where the tracked ref/tag can be influenced by outside contributors), and default `--submodules=recursive` is in effect. No special privilege is needed beyond the ability to add commits/submodule entries that eventually get merged onto the tracked ref — exactly mirroring the "no external pre-conditions" characterization in the source finding, with the only "admin responsibility" argument being an operator explicitly setting `--submodules=off` (the analog of "admin sets a reasonable cap"), which was exactly the mitigating control debated as insufficient in the original Sherlock discussion.

### Recommendation
- Add explicit limits: a `--submodule-max-count` and/or `--submodule-max-depth` flag (or hard-coded sane defaults) enforced before/while running `git submodule update --init --recursive`, e.g. by first running `git submodule status --recursive` (or parsing `.gitmodules`) to count/measure depth and aborting the sync with a clear error if limits are exceeded, rather than unconditionally recursing.
- Ensure `git.Run`'s command execution reliably kills the child process tree on `ctx` timeout (verify/fix in `pkg/cmd/cmd.go`) so a runaway submodule operation cannot leak processes or resources across repeated timed-out sync attempts.
- Document that `--submodules=recursive` combined with an untrusted/multi-party-writable tracked repo is a DoS risk, and recommend `--submodules=off` or `shallow` plus depth caps for such deployments.

### Proof of Concept
Conceptual PoC (mirrors the structure of the Solidity PoC, replacing "buy 4000 tickets" with "commit N submodules / deep submodule chain"):
1. Attacker (or anyone able to merge into the tracked ref) adds a large number of submodule entries to `.gitmodules` (e.g. thousands), or nests submodules many levels deep, each pointing to a real reachable git remote.
2. `git-sync` is running with default flags (`--submodules=recursive`) tracking that ref.
3. On the next sync, `main.go`'s loop calls `SyncRepo` → `configureWorktree`, which executes:
   `git submodule update --init --recursive [--depth N]` [7](#0-6) 
4. This single git invocation must clone/update every submodule in the (attacker-defined) graph; with enough submodules/depth this exceeds `--sync-timeout` (default 120s).
5. The sync attempt fails repeatedly (`SyncRepo` returns an error), `failCount` increments each cycle: [6](#0-5) 
6. If `--max-failures` is at its default (0), git-sync exits after the very first failed attempt, denying the publish contract entirely — a persistent, repeatable sync denial triggered purely by attacker-controlled repository content.
