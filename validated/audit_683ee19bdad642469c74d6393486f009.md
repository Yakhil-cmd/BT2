This confirms the finding. `Handler#stacks` scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, and other handlers like `CheckSuiteHandler` use `stacks.where(branch: ...)` before touching commits. `StatusHandler#process`, however, calls `Commit.where(sha: params.sha)` directly on the unscoped model, never referencing `stacks` or `repository_name` at all.

Also relevant: `verify_signature` in `WebhooksController` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC signature against the `webhook_secret` configured for the **organization** (`repository_owner`, i.e. `params.dig('repository','owner','login')`), not per-repository. So the signature check does not bind the payload to a specific `Repository#full_name` in the first place — it only proves the payload came from something possessing that org's shared webhook secret. `StatusHandler` then never re-derives or checks `repository.full_name` against the commit's owning stack.### Title
`StatusHandler#process` writes commit statuses cross-tenant via unscoped `Commit.where(sha:)` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone with `Commit.where(sha: params.sha)`, with no `stack_id`/`repository_id` filter tying the lookup to the webhook's originating repository. Combined with the fact that webhook signature verification is scoped to the GitHub *organization* rather than the specific `Repository#full_name`, any commit sha collision across stacks (shared ancestor commit, empty-tree commit, etc.) causes a `status` webhook for one repository to write a `Status` row onto commits belonging to a completely different stack.

### Finding Description
The broken binding, stated explicitly: the code should enforce
`Commit.where(sha: params.sha, stack_id: stacks.commits.select(:id))` == `Commit.where(sha: params.sha)`
but it does not — `stacks` (from `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) is never referenced in `StatusHandler#process`: [1](#0-0) 

Contrast with the sibling `CheckSuiteHandler`, which correctly scopes through `stacks` before touching any commit: [2](#0-1) 

and with `Handler#stacks`/`#repository_name`, which is the scoping mechanism that `StatusHandler` skips entirely: [3](#0-2) 

Root cause: `StatusHandler` queries the global `Commit` table by `sha` with no tenant boundary. Any `Commit` row in the entire installation whose `sha` matches `params.sha` receives the status via `commit.create_status_from_github!(params)`.

Attacker's exact request: an unprivileged GitHub user who owns/administers a repository that is itself onboarded as a Shipit stack (or who can get a `status` webhook fired for a sha that also exists in a victim stack) pushes/creates a commit whose sha collides with a commit already tracked in a victim's stack — trivially achievable for the well-known empty-tree/empty-repo initial commit sha, or any commit sha inherited from a shared public upstream/fork point before divergence, since git commit shas are content-addressed and identical parents/trees/authorship/timestamps/messages produce identical shas. They then trigger (or wait for) a `status` event on their own repository for that sha. GitHub's webhook fires with the attacker's own repository/organization signature, which passes `verify_signature` because that check only verifies the payload was signed with the sending organization's `webhook_secret` — it never checks that the sha it names actually belongs to that organization's repository: [4](#0-3) [5](#0-4) 

`StatusHandler#process` then finds *all* `Commit` rows across the entire installation with that sha — including the victim's — and writes a status onto each: [1](#0-0) 

Why existing guards fail: `verify_signature`/`GitHubApp#verify_webhook_signature` only prove the HMAC matches the sending organization's secret — they do not bind the payload's `sha` to that organization's own commits: [6](#0-5) 

`ExplicitParameters` only validates the shape/types of `sha`, `state`, `branches`, etc., not ownership: [7](#0-6) 

There is no `require_permission!`/`User#authorized?` check applicable to webhook ingestion at all (webhooks bypass session/API-token auth by design), and `Handler#stacks` — the one mechanism that would scope the write to the correct tenant — is simply unused in this handler.

### Impact Explanation
A payload from one repository can flip the CI status of a commit belonging to an entirely different, unrelated stack/tenant, and `create_status_from_github!` feeds `Commit#status`, which drives `deployable?` and `schedule_continuous_delivery`: [8](#0-7) [9](#0-8) 

If the victim stack has `continuous_deployment` enabled and the poisoned commit is its latest undeployed commit, forging a `success` status can trigger an unauthorized deploy of that victim stack — this matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any stack whose head commit sha the attacker can predict/collide (most reliably the empty-tree/initial-commit sha, or any commit shared from a public upstream before fork divergence — both are attacker-controllable/discoverable without any secret).

### Likelihood Explanation
Preconditions: the attacker needs a repository onboarded into the same Shipit instance (or any repository under an organization Shipit trusts) to receive genuine, validly-signed `status` webhooks, and needs a commit sha that also exists in a victim stack's `commits` table. Colliding on the empty-tree commit sha or a shared fork-point commit requires zero cryptographic effort — git commit shas are deterministic from parent+tree+author/committer+timestamps+message, so an attacker with a fork of the victim's public repo, or simply the well-known empty-tree sha, can generate a collision without brute force. This is fully unauthenticated with respect to Shipit itself (no session, token, or Shipit secret needed) — only ability to have a repository under any org configured in Shipit, or to control which shas appear in status events sent to Shipit. Feasibility is high and the exploit is repeatable per matching sha.

### Recommendation
Scope `StatusHandler#process` to the requesting repository's stacks, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.commits.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the existing `Handler#stacks` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) so a `status` payload can only affect commits belonging to the stack(s) tied to the repository named in that payload. Additionally consider validating `repository.full_name` against `Repository#full_name` on signature verification rather than only the organization, to prevent same-org cross-repo spoofing.

### Proof of Concept
Minitest plan (test/models/shipit/webhooks/handlers/status_handler_test.rb):
```ruby
test "process does not leak statuses across unrelated stacks with colliding sha" do
  shared_sha = "4b825dc642cb6eb9a060e54bf8d69288fbee4904" # git empty-tree sha

  repo_a = Shipit::Repository.create!(owner: "tenant-a", name: "app")
  repo_b = Shipit::Repository.create!(owner: "tenant-b", name: "app")
  stack_a = Shipit::Stack.create!(repository: repo_a, environment: "production")
  stack_b = Shipit::Stack.create!(repository: repo_b, environment: "production")

  commit_a = stack_a.commits.create!(sha: shared_sha, message: "init", author: Shipit::AnonymousUser.new)
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "init", author: Shipit::AnonymousUser.new)

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => repo_a.full_name, "owner" => { "login" => "tenant-a" } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert commit_a.statuses.reload.exists?(context: "ci/attacker"),
    "expected the originating repository's commit to receive the status"
  refute commit_b.statuses.reload.exists?(context: "ci/attacker"),
    "commit belonging to an unrelated stack (tenant-b) must NOT receive the status"
end
```
Before the fix, both assertions on `commit_a` and `commit_b` pass true (both get the status) — demonstrating the equality `Commit.where(sha:...) == Commit.where(sha:..., stack_id: stacks.commits.select(:id))` does not hold. After scoping via `stacks.commits.where(sha:...)`, only `commit_a` is updated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret
