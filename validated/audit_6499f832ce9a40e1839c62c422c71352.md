### Title
Cross-organization commit status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only authenticates that the inbound webhook belongs to a given GitHub organization (looked up via `repository_owner`, i.e. `params.dig('repository','owner','login')` or `organization.login`), and picks the corresponding `GitHubApp` secret to validate the HMAC signature. [1](#0-0) 
Once the signature is valid for *that* org, the `status` event handler (`StatusHandler#process`) resolves the commit to update purely by `sha`, with **no scoping to the repository or organization that was actually authenticated**: [2](#0-1) 

This differs from every other handler in the same hierarchy, all of which scope through `Repository.from_github_repo_name(...)`/`stacks` before touching any data — e.g. `CheckSuiteHandler` filters by `stacks.where(branch: ...)`. [3](#0-2) [4](#0-3) 

### Finding Description
Shipit supports multi-organization deployments where each organization has an independent `webhook_secret` (documented in `docs/setup.md`). [5](#0-4) 
The binding the system relies on is: *"the organization whose webhook secret verified this request" == "the repository/stack whose data gets mutated."* `StatusHandler` breaks this binding: it queries `Commit.where(sha: params.sha)` globally across the entire Shipit database, then calls `commit.create_status_from_github!(params)`, regardless of which org's secret validated the request. [2](#0-1) 

Since git commit SHA-1 IDs are a hash purely of the commit's *content* (tree, parents, author, committer, timestamps, message) and not of any particular hosting repository, it is possible to reproduce an existing commit with an identical SHA inside a completely different, attacker-controlled repository (e.g. by fast-forwarding/cherry-picking the exact same commit metadata into a repo the attacker owns in a different, less-trusted organization that is also configured in Shipit). Pushing that commit (or any action generating a `status` event, e.g. a CI run tagging that SHA) causes GitHub to deliver a correctly-signed `status` webhook — signed with the attacker's own organization's legitimate `webhook_secret` — carrying an attacker-chosen `state`, `context`, `description`, and `target_url` for that SHA.

`WebhooksController#verify_signature` succeeds because the request truly is authentic for the attacker's own org. [6](#0-5) 
`StatusHandler`, however, applies the resulting status to **any** `Commit` record in the whole install matching that SHA — including one belonging to a completely different, victim organization's stack that the attacker was never authenticated for. [2](#0-1) 

### Impact Explanation
Commit statuses are consumed by `ci.require`, a documented `shipit.yml` mechanism which "disallow[s] deploys if any of [the required contexts] is missing on the commit being deployed." [7](#0-6) 
By forging a "success" status with the exact `context` a victim stack requires (e.g. `ci/tests`), an attacker who only controls a repository/organization boundary elsewhere in the same Shipit installation can make a victim's commit appear CI-green, unblocking or accelerating an unauthorized deploy of that commit for continuous-deployment-enabled stacks — without ever holding credentials, GitHub App access, or write permission to the victim organization/repository. This falls under the "High" impact category (escalation crossing an authorization boundary leading to an unauthorized deploy).

### Likelihood Explanation
Exploitation requires: (1) the target Shipit instance configured with multiple GitHub organizations (a documented, supported configuration), (2) the attacker controlling any repository in one of those organizations (even an unrelated, low-trust org), and (3) the ability to recreate a commit with an identical SHA to the victim's commit and get GitHub to fire a `status` event referencing it (trivial, since git objects are fully reproducible from known metadata, and status events can even be self-reported via the Statuses API from the attacker's own repo's CI). No secrets, tokens, or victim-org access are required, making this a realistic and moderately easy-to-execute attack once multi-org mode is in use.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries global models by attacker-supplied identifiers) through the same repository-derived `stacks`/`Repository.from_github_repo_name(repository_name)` path used elsewhere in the handler hierarchy, ensuring the commit being updated actually belongs to the same repository (and by extension, the same authenticated organization) as the verified webhook, e.g. joining through `stacks.joins(:commits).where(commits: { sha: params.sha })` instead of an unscoped `Commit.where(sha: ...)`.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` (hosting the target stack requiring `ci.require: ["ci/tests"]`) and `attacker-org` (attacker has push access), each with distinct `webhook_secret`s, per the documented multi-org setup.
2. Attacker identifies the SHA of a pending commit on `victim-org/app` (visible via Shipit's public-ish stack UI or GitHub).
3. Attacker reconstructs an identical commit (same tree, parents, author/committer name/email/timestamps, message) inside `attacker-org/decoy`, producing the exact same SHA-1.
4. Attacker triggers (or GitHub CI reports) a `status` event on that commit in `attacker-org/decoy` with `state: success`, `context: ci/tests`.
5. GitHub signs and delivers the webhook using `attacker-org`'s real `webhook_secret`; `WebhooksController#verify_signature` validates it successfully because it is genuinely from `attacker-org`.
6. `StatusHandler#process` executes `Commit.where(sha: <shared sha>)`, matches the victim's commit record (unscoped to repository), and calls `create_status_from_github!`, marking the victim commit's `ci/tests` context as green — bypassing the CI gate for `victim-org/app`'s deploy.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
