### Title
Malformed (non-canonical-length) `signer-key` bypasses signature verification and is defaulted to a zero-value key, permanently absorbing signing weight and threatening a chain-wide freeze of staked STX - (File: stackslib/src/chainstate/stacks/boot/pox-4.clar / stackslib/src/chainstate/nakamoto/signer_set.rs)

### Summary
The `signer-key` parameter accepted throughout pox-4/pox-5 (`stack-stx`, `stack-extend`, `stack-increase`, `set-signer-key-authorization`, `verify-signer-key-sig`, etc.) is typed as `(buff 33)`, which in Clarity only enforces a *maximum* length, not an exact one. When a stacker uses the pre-authorization path (`signer-sig-opt` is `none`), `verify-signer-key-sig` never derives `signer-key` from a signature recovery — it is accepted as an opaque, unvalidated byte string of any length ≤ 33. This is directly analogous to the reported circuit bug: a value that is supposed to represent a canonical cryptographic object (a compressed secp256k1 point) is accepted without checking it is in canonical form, and a downstream component silently reinterprets the malformed value rather than rejecting it.

### Finding Description
`verify-signer-key-sig`/`set-signer-key-authorization` in `pox-4.clar` (and the equivalent pox-5 logic) accept `signer-key (buff 33)` with no length or curve-validity check: [1](#0-0) 

When `signer-sig-opt` is `none`, the function simply checks a previously stored authorization keyed by the raw `signer-key` bytes — no ECDSA recovery, hence no guarantee the bytes decode to exactly 33 bytes or a valid curve point: [2](#0-1) 

`set-signer-key-authorization` itself performs no length/format validation on `signer-key` before storing the authorization: [3](#0-2) 

Downstream, when the node reads the committed reward-set/signer entries back out of the contract at the Rust layer, `RawRewardSetEntry::from_pox_4_tuple` explicitly acknowledges the `(buff 33)` type does not enforce a minimum length, and instead of rejecting a short buffer it **silently substitutes an all-zero 33-byte key**: [4](#0-3) 

This all-zero (or any other non-canonical, sub-length) `signer-key` becomes a `NakamotoSignerEntry.signing_key` entry in the reward/signer set with real STX weight attached, exactly as the circuit's non-reduced `Y` becomes a validly-committed-but-wrong-sign public key. No private key can ever produce an ECDSA signature that recovers to this degenerate 33-byte value, so during block signature verification: [5](#0-4) 
that reward-set slot's weight can never be counted toward `total_weight_signed`, because no signature will ever recover to the zero-filled `signing_key`. Multiple such malformed registrations (or one large one) permanently remove voting weight from the achievable pool used against `compute_voting_weight_threshold`, without reducing the `total_weight` denominator — mirroring the report's "prover commits an invalid, unusable value which future provers cannot work around."

### Impact Explanation
If the aggregate un-signable weight (from one or more stackers submitting a short/degenerate `signer-key` via the un-signed authorization path) is large enough, the 70%-style voting-weight threshold in `verify_signer_signatures` can become unreachable for the affected reward cycle, since the denominator (`total_weight`) still counts the phantom slot but the numerator can never include it: [6](#0-5) 
This halts Nakamoto block production/finalization for that cycle, which is the same class of outcome as the reported bug ("halt the LightClient, trapping user funds") — here, halting block signing traps every honestly-locked stacker's STX until the network can intervene (hard fork / patch), a **temporary-to-permanent freezing of staked STX belonging to other, honest participants**, triggered by a single unprivileged staker's malformed transaction rather than any admin/miner action.

### Likelihood Explanation
Likelihood is moderate: exploiting it requires using the *authorization* path (`signer-sig-opt = none`) rather than the signature-recovery path, and requires accumulating enough "dead" weight relative to the reward-cycle's total participation to push the achievable signed weight below threshold. A well-resourced or colluding set of malicious stackers (each individually only "wasting" their own weight, but collectively denying block production to everyone) could realistically reach this bar in cycles with modest total participation. The core defect — accepting and silently mangling a non-canonical-length key instead of erroring — is unconditionally present and requires no special access.

### Recommendation
- In `pox-4.clar`/`pox-5.clar`, assert `(is-eq (len signer-key) u33)` in `set-signer-key-authorization` (and anywhere else `signer-key` is accepted without signature-derived provenance), rejecting non-canonical lengths at the point of entry rather than downstream.
- In `RawRewardSetEntry::from_pox_4_tuple` (`stackslib/src/chainstate/nakamoto/signer_set.rs`), replace the silent `[0; SIGNERS_PK_LEN]` fallback with a hard error (`Error::BadSignerPublicKey`) so malformed entries are rejected/skipped rather than silently converted into a phantom, unusable, but weight-bearing signer slot.
- Additionally validate that `signer-key` decodes to an on-curve, properly-prefixed (`0x02`/`0x03`) compressed secp256k1 public key before it is trusted anywhere weight or signature-matching depends on it, consistent with the long-term recommendation in the referenced report to constrain witnessed values to canonical form before use.

### Proof of Concept
1. Stacker `A` calls `set-signer-key-authorization` with a `signer-key` buffer shorter than 33 bytes (e.g., 1 byte), satisfying the `(buff 33)` type but not a valid compressed pubkey; the contract stores the authorization keyed on those raw bytes without validation (`stackslib/src/chainstate/stacks/boot/pox-4.clar:1431-1440`).
2. Stacker `A` calls `stack-stx`/`stack-extend` with `signer-sig-opt = none` and the same malformed `signer-key`; `verify-signer-key-sig` finds the stored authorization and returns `(ok true)` without ever performing `secp256k1-recover?` (`pox-4.clar:749-762`).
3. At the next reward-cycle boundary, the node reads back the PoX reward-set tuple; `signer.len() != 33` triggers the silent fallback to `[0; SIGNERS_PK_LEN]` (`signer_set.rs:310-317`), inserting a weighted `NakamotoSignerEntry` with `signing_key = [0u8; 33]`.
4. During Nakamoto block signature verification, no signature can ever recover to `[0u8; 33]`, so that slot's weight is permanently excluded from `total_weight_signed` while still counting toward `total_weight` in the threshold calculation (`nakamoto/mod.rs:1122-1189`), reducing the achievable signed-weight ceiling for the cycle. Enough such registrations push the achievable ceiling below `compute_voting_weight_threshold`, halting block production/finalization and freezing all stackers' locked STX for that cycle.
