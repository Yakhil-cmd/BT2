### Title
Stale delegate grant silently re-arms when the position NFT returns to the granting owner, letting a previously-registered delegate drain the reacquired account - (File: contracts/controller/src/storage/account.rs)

### Summary
The Cilium bug class is *identity asserted by a shared label rather than membership*: `fromNodes`/`toNodes` matched on labels that non-node endpoints could also carry, so label equality was treated as node identity. The controller's delegate mechanism has the same shape: a `DelegateGrant` is stamped only with `granted_by` (the owner's address at grant time), and `get_delegates` re-activates the stored list whenever `granted_by == current owner`. There is no transfer epoch, nonce, or per-ownership generation counter. A grant made by a previous ownership stint is therefore indistinguishable from a grant the current owner just made, and it silently re-arms if the NFT ever returns to that address — even though the owner never authorized the delegate during this ownership.

### Finding Description
`DelegateGrant` stores `granted_by: Address` plus the delegate list (`common/src/types/controller.rs`, `set_delegates` at `contracts/controller/src/storage/account.rs:185-199`). Authorization resolves delegates via:

```rust
// contracts/controller/src/storage/account.rs:176-181
get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
    .filter(|grant| grant.granted_by == *owner)
```

`owner` is the *live* NFT holder (`account_owner`, line 41). The match is a bare address equality — the "label" — not proof of a grant in the current ownership. `remove_delegate` (lines 226-247) shows the developers know reactivation is dangerous: when a new owner removes a delegate from a stale grant, it deletes the whole entry "preventing those grants from reactivating if the NFT returns to their original owner" (comment, line 224-225). But that cleanup only runs if an intervening owner calls `remove_delegate`. If the NFT passes through a holder who never touches delegates (e.g., a marketplace purchase-and-flip, or a transfer used for collateral management), the grant survives intact and reactivates the moment `owner_of(token_id)` returns the original `granted_by` address.

Delegates additionally need active global position-manager registration, but a delegate that was legitimate when granted (e.g., a trading bot / automation service the user once enabled) remains registered unless governance deactivates the manager globally. Per the threat model, "Delegates can borrow/withdraw to their chosen recipient within account gates" — the delegate is not economically aligned with the owner.

### Impact Explanation
Concrete scenario reachable by a single unprivileged address:

1. Alice owns `account_id = 42`, calls `add_delegate` granting `manager M` (a registered position manager).
2. Alice transfers the NFT (token_id 42) to Bob — e.g., sells the leveraged position, since positions are ordinary transferable NFTs. M's grant goes dormant.
3. Bob never calls `remove_delegate` (he has no reason to; `get_delegates` returns empty for him).
4. Alice later reacquires NFT 42 — buys it back on a marketplace, or receives it via `transfer`/`transfer_from`. The instant `owner_of(42) == alice`, M's stale grant is live again with no fresh authorization from Alice.
5. M calls `borrow` (or `withdraw` in EMode/multiply modes) on account 42 with `to = M`, drawing debt up to the account's LTV headroom and sending proceeds to itself.

This is theft of user funds: the collateral value backing Alice's reacquired position is converted into debt owed by the account while the borrowed assets go to M. It maps the Cilium class exactly — authority inferred from a label match (`granted_by == owner`) rather than scoped to the actual grant relationship, so an entity that merely shares the label inherits permissions meant for a different epoch.

### Likelihood Explanation
Medium. Two conditions must hold: the NFT must return to a previous `granted_by` address, and a stale delegate must still be an active position manager. Both are plausible — positions are deliberately standard NFTs so they trade freely on marketplaces (a user may repurchase a position they once owned), and interim holders have no on-chain prompt to scrub stale grants. The attacker (M) is unprivileged and uses only `controller::borrow`/`withdraw`. The mitigation is that the attack requires the victim to reacquire the specific account, which is opportunistic rather than freely initiatable.

Note: this behavior is documented in `contracts/position-nft/README.md` ("The stale grant stays in storage and re-arms if the token returns to `granted_by`") and `docs/explanation/threat-model.md`, so it may be a consciously accepted trade-off; if the audit program treats documented ADR choices as out of scope, this finding should be downgraded accordingly. However, the `remove_delegate` cleanup comment demonstrates the protocol treats reactivation as a hazard it actively prevents on one path while leaving it open on another.

### Recommendation
Stamp each `DelegateGrant` with an ownership epoch that changes on every NFT transfer — e.g., store a per-account `transfer_count` (incremented via a controller hook the NFT calls on `transfer`/`transfer_from`, or derived from a monotonic sequence) and require `grant.epoch == current_epoch` in `get_delegates`. Alternatively, have the controller burn/clear `ControllerKey::Delegates(account_id)` on the next owner-resolved operation after detecting an owner change, or key the grant by `(granted_by, mint/first-owner nonce)` that cannot recur. Absent a protocol change, `transfer`-return reactivation should be blocked by clearing the grant on any owner transition rather than only on `remove_delegate`.

### Proof of Concept
```rust
// Conceptual; assumes LendingTest harness primitives.
// 1. Alice creates an account, supplies USDC, registers+grants delegate M.
let acct = t.create_account_full(ALICE, HARNESS_SPOKE, PositionMode::Multiply);
t.supply_to(ALICE, acct, "USDC", 10_000.0);
t.register_position_manager(MANAGER);          // manager M is active
t.ctrl_client().add_delegate(&alice, &acct, &manager);

// 2. Alice transfers NFT `acct` to Bob. Grant is dormant for Bob.
t.nft_client().transfer(&alice, &bob, &(acct as u32));
assert!(t.ctrl_client().get_delegates(&acct).is_empty());

// 3. Bob never calls remove_delegate. NFT returns to Alice (buy-back).
t.nft_client().transfer(&bob, &alice, &(acct as u32));

// 4. Stale grant is live again: delegates list is non-empty for Alice.
assert_eq!(t.ctrl_client().get_delegates(&acct), vec![manager]);

// 5. M borrows against Alice's collateral to itself — no fresh consent.
let borrows = vec![&t.env, (hub_asset(usdc), amount_raw(5_000.0, 7))];
t.ctrl_client().borrow(&manager, &acct, &borrows, &Some(manager));
// token.balance(manager) increased by ~5_000 USDC; account 42 owes the debt.
```

Root cause: `get_delegates` at `contracts/controller/src/storage/account.rs:176-181` authorizes delegates by address-label match (`granted_by == owner`) with no per-ownership scoping; `remove_delegate` (lines 236-238) acknowledges and partially mitigates the same reactivation hazard, confirming the unscoped match is the defect rather than the transfer itself.
