## Title
Multisig transaction execution can silently bypass the on-chain payload-match check, allowing execution of an unapproved payload - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

## Summary
`validate_multisig_transaction()` — the Move prologue function invoked by the VM as part of multisig-transaction admission (called from `run_multisig_prologue()` in the VM) — only verifies that the payload supplied at execution time matches the payload that owners actually approved when the feature flag `abort_if_multisig_payload_mismatch_enabled()` is turned on. This mirrors the external report's bug class exactly: a security-critical field ("does the executed payload equal what was approved?") is checked *conditionally* rather than unconditionally, so when the condition is false the admission logic silently accepts a transaction it should reject.

## Finding Description
When a multisig transaction is created with `create_transaction` (as opposed to `create_transaction_with_hash`), the *full* payload is stored on-chain in `transaction.payload` (an `Option<vector<u8>>`), and `transaction.payload_hash` is `None`. [1](#0-0) 

At execution time, the VM computes `provided_payload` from whatever `TransactionExecutable` the *caller* (any owner who can produce enough approvals) actually submits — not from the stored transaction: [2](#0-1) 

This `provided_payload` is passed into `validate_multisig_transaction(owner, multisig_account, payload)`. The function has two separate checks:
1. If `transaction.payload_hash.is_some()`, it hashes `payload` and compares to the stored hash — this always runs. [3](#0-2) 
2. If the full `transaction.payload` was stored (the more common `create_transaction` path), the match check is gated behind `features::abort_if_multisig_payload_mismatch_enabled()`:
```move
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [4](#0-3) 

The feature's own doc comment confirms this is a known correctness gap being patched behind a flag rather than fixed unconditionally: *"Whether the multisig v2 fix is enabled. Once enabled, the multisig transaction execution will explicitly abort if the provided payload does not match the payload stored on-chain."* [5](#0-4) 

When `abort_if_multisig_payload_mismatch_enabled()` is `false`, the second check never fires, regardless of whether the caller-provided `payload` matches `transaction.payload`. Admission (mempool validation and prologue) and execution both call the exact same code path — `run_multisig_prologue()` is used for both `validate_transaction` and `execute_transaction` — so there is no independent layer that re-validates the payload. Consequently, once a multisig transaction has collected enough owner approvals for a stored payload A, any owner (not necessarily the same approvers, since implicit self-approval is counted) can submit a *different* payload B as the `TransactionExecutableRef::EntryFunction`/`Script` at execution time, and it will pass `validate_multisig_transaction` and be executed under the multisig account's signer authority — because the approval-vs-execution binding is never enforced.

## Impact Explanation
This breaks the core multisig invariant: "the payload that gets executed on behalf of the multisig account must be the payload the required threshold of owners approved." An owner (or colluding minority of owners with less than quorum, but enough to reach the "1-more-signature" implicit-approval bump) who has enough real approvals for transaction A can substitute an entirely different entry function / arguments (transaction B) at submission time and have it execute with the multisig account's authority — effectively bypassing the approval set for the actual code that runs. This is exactly the class of impact called out in the Admission Impact Gate: *"Authenticator, WebAuthn, multisig, or approval validation accepting the wrong signing material or wrong approval set"* and *"Pre-validation mismatch that causes a transaction which should fail admission to execute and commit."* Funds held by or controlled through the multisig account, or any privileged action gated by it, could be misused without the approvers' actual consent for that specific payload.

## Likelihood Explanation
This depends entirely on whether `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` (feature id 70) is enabled on the target network. I was unable to conclusively determine the default/genesis feature-flag state for this repository from the available index (I could not find the genesis feature-list defaults in `vm-genesis` within the indexed content) — this is a material unknown. If the flag is disabled (which the doc's phrasing "once enabled" suggests is not automatically the case, since it reads as an opt-in fix rather than a default-on protection), the flaw is exploitable by any account owner with the ability to create and partially approve multisig transactions, with no privileged access required. If the flag is already enabled network-wide, this is not currently exploitable, but the vulnerable code path still exists and would resurface on any environment where the flag is off (e.g., new devnets/testnets, or if the flag were ever rolled back).

## Recommendation
Remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate from the payload-match check in `validate_multisig_transaction()` and make the comparison between the provided execution payload and the on-chain stored payload unconditional whenever `transaction.payload.is_some()`. If backward compatibility with in-flight transactions submitted before this fix is a concern, resolve it via a one-time migration rather than a permanent feature-flagged bypass, since a "sometimes-enforced" invariant is inherently unsafe for a security-critical binding check.

## Proof of Concept
1. Ensure `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is disabled (or not yet enabled on the target network).
2. Owner creates a multisig account with owners `{A, B, C}`, `num_signatures_required = 2`.
3. Owner A calls `create_transaction(A, multisig_addr, payload_A)` — this stores the **full** `payload_A` on-chain (`transaction.payload = Some(payload_A)`, `payload_hash = None`) and auto-approves as A.
4. Owner B calls `approve_transaction` — quorum (2) is now met for `payload_A`.
5. Owner A (or B) submits the actual multisig-execution transaction to the VM but with a `TransactionExecutable` (EntryFunction/Script) equal to `payload_B` — a completely different, unapproved call (e.g., transferring funds to an unauthorized address).
6. `run_multisig_prologue()` computes `provided_payload = bcs(payload_B)` and calls `validate_multisig_transaction(A, multisig_addr, payload_B)`.
7. Since `payload_hash` is `None`, check (1) is skipped; since `abort_if_multisig_payload_mismatch_enabled()` is `false`, check (2) is skipped entirely — `payload_B != payload_A` is never compared.
8. Transaction passes both mempool admission and prologue validation, and `payload_B` executes with the multisig account's authority despite never having been approved by 2 owners.

**Uncertainty note:** I could not verify from the indexed codebase content whether `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled by default at genesis/mainnet in this repository snapshot (the `vm-genesis` default feature list was not found in the index). This should be confirmed before treating this as exploitable in production; if it is confirmed enabled by default everywhere the multisig module is deployed, the practical severity is reduced to "latent design flaw" rather than an active exploit path. Given the index size limits, a full Devin session with direct repository access would be needed to authoritatively confirm the genesis default feature set.
