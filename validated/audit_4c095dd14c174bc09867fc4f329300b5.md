### Title
Webhook signature verification key is selected from an unverified field, decoupling the authenticated GitHub organization from the repository the payload is allowed to mutate - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to validate a payload against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body, before the HMAC signature has been checked. [1](#0-0) [2](#0-1) 

Once the signature is accepted, every event handler independently re-derives the target repository from the same untrusted payload, using `payload.dig('repository', 'full_name')` to look up the `Repository`/`Stack` to act on: [3](#0-2) 

There is no requirement that `repository.full_name`'s owner segment match `repository.owner.login`/`organization.login` used to select the verification secret. In a multi-organization Shipit deployment (`config/secrets.yml` `github:` keyed by org, each with its own `webhook_secret`), this breaks the intended binding: **"the organization whose secret authenticated the request" == "the repository the handlers are permitted to write to."** [4](#0-3) 

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unverified JSON body and uses it to fetch the corresponding `GitHubApp`/secret:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`verify_webhook_signature` is a plain HMAC-SHA1 check over `request.raw_post` using that organization's `webhook_secret`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [6](#0-5) 

Critically, the signature only proves *the request was signed by the org identified in the payload*, not that every field inside the payload (in particular `repository.full_name`, which is the field actually used by handlers) is consistent with that org. Since the whole `raw_post` is attacker-controlled prior to signing (an attacker who legitimately owns an installation for Org A and therefore possesses Org A's `webhook_secret` can craft arbitrary JSON), they can set:
- `repository.owner.login` = `"org-a"` (or `organization.login` = `"org-a"`) → selects Org A's secret for verification, which the attacker can compute correctly.
- `repository.full_name` = `"org-b/target-repo"` → the value every downstream handler actually keys off of via `Handler#repository_name`/`Repository.from_github_repo_name`. [3](#0-2) [7](#0-6) 

Because `verify_signature` never checks that `repository.full_name`'s owner segment equals `repository_owner`, a payload signed with Org A's secret is accepted, and then `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `pull_request/*` handlers will happily operate on Org B's tracked `Stack`/`Repository`/`Commit` records — e.g. queuing `GithubSyncJob` for Org B's stack, or writing fabricated commit statuses: [8](#0-7) [9](#0-8) 

This is the direct analog of the reported bug class: the check that gates the action (`verify_signature`, keyed on `repository.owner.login`) is not enforced against the same field the subsequent logic actually consumes (`repository.full_name`), exactly like the Solidity report where the auction-cancel guard checked `listing.end` window instead of the actual `listing.start`/bid state that should have gated it.

### Impact Explanation
This allows cross-repository/cross-organization writes: an actor who controls a legitimate, low-privilege GitHub App installation (and thus knows only their own org's `webhook_secret`) can forge webhook deliveries that are processed as if they came from a different, unrelated organization/repository tracked by the same Shipit instance. Concretely this can:
- Force `GithubSyncJob` to run against another org's `Stack` with an attacker-chosen `expected_head_sha` [8](#0-7) 
- Inject fabricated commit statuses (`state`, `context`, `target_url`) onto commits belonging to another org's repository, which can influence CI-gated deploy decisions [9](#0-8) 
- Manipulate `check_suite`/`pull_request` derived state for a repository the attacker does not own.

This matches the "cross-repository writes" / "unauthorized deploy" impact tier because it lets an attacker influence deploy-gating data for a repository they were never granted GitHub write access to, purely by exploiting the mismatch between the org whose secret validated the signature and the org whose repository is actually mutated.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with **multiple** GitHub App organizations (the `github: { org_a: {...}, org_b: {...} }` schema shown in `config/secrets.development.shopify.yml`), each with its own `webhook_secret`, and the attacker must control (or have compromised) one of those orgs' Apps well enough to know its `webhook_secret` — which is a normal, expected credential for a legitimate multi-tenant installation owner, not a privileged Shipit account. Under the single-org config (`github_default_organization` nil), `repository_owner` is effectively ignored and this specific analog does not apply as cleanly, so likelihood is contingent on the multi-org deployment mode. Given multi-org support is a documented, first-class configuration, likelihood is realistic wherever that mode is used.

### Recommendation
In `WebhooksController#verify_signature`, after locating the `github_app` by `repository_owner`, verify that `repository_owner` is consistent with every repository reference the payload will later be used for — most directly, assert that `repository.full_name`'s owner segment equals `repository_owner` (and `organization.login` if present) before dispatching to handlers. Equivalently, bind the verified organization into the handler dispatch path (e.g., pass `repository_owner` into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }`) and have `Handler#repository_name`/`stacks` reject any payload whose repository owner does not match the organization whose secret validated the HMAC.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with a distinct `webhook_secret` (per `config/secrets.development.shopify.yml` schema).
2. As an entity that legitimately controls the `org-a` GitHub App (and thus knows `org-a`'s `webhook_secret`), craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `GitHubApp`, and the HMAC check passes because it was correctly signed with `org-a`'s secret [1](#0-0) .
5. `PushHandler#process` calls `stacks` → `Handler#repository_name` returns `"org-b/target-repo"` → `Repository.from_github_repo_name("org-b/target-repo")` resolves Org B's actual tracked repository, and `sync_github(expected_head_sha: "deadbeef...")` is invoked on Org B's `Stack`, despite the request never being signed by Org B [8](#0-7) [7](#0-6) .
