### Title
Ambiguous flat-string canonicalization in `getSourceString` lets differently-structured units/definitions collide to the same hash - (File: `string_utils.js`)

### Summary
`getSourceString()` in [1](#0-0)  is the canonicalization routine used to compute the hash that underlies unit hashes, signing hashes, and address `chash160` definitions in `object_hash.js` (`getUnitHash`, `getUnitHashToSign`, `getChash160`) [2](#0-1) [3](#0-2) . Similar to the Varnish bug where ambiguous chunk-boundary parsing (CRLF could be "skipped") let a byte stream be interpreted two different ways by different components, `getSourceString` flattens nested structures into a single `\x00`-joined token stream where **object boundaries have no delimiter at all** (only arrays get `'['`/`']'` markers) and where string values/object keys are only checked for containing the literal `\x00` separator — not for colliding with the reserved single-character type tags (`"s"`, `"n"`, `"b"`) or the array markers (`"["`, `"]"`) themselves.

### Finding Description
In `extractComponents`, strings are serialized as two array slots `["s", value]`, numbers as `["n", value.toString()]`, booleans as `["b", value.toString()]`, and arrays get bracket tokens `'['`/`']'` around their flattened children [4](#0-3) . Object values, however, receive **no wrapper token whatsoever** — only the sorted keys are pushed inline as bare tokens before the recursively-flattened value [5](#0-4) . All these heterogeneous tokens are ultimately concatenated with the single-byte separator `\x00` [6](#0-5) [7](#0-6) .

The only sanitation performed is:
- string values must not contain `\x00` [8](#0-7) 
- object keys must not contain `\x00` [9](#0-8) 

Nothing prevents an attacker-controlled string value or object key from being exactly one of the reserved framing tokens `s`, `n`, `b`, `[`, `]`. Because objects are not fenced by any bracket (unlike arrays), an object `{"s":"xyz"}` flattens to the token sequence `["s","s","xyz"]` — indistinguishable, once joined, from a differently-shaped structure that happens to emit the same three tokens in the same order (e.g. an array element that is the plain string `"s"` followed by a sibling string `"xyz"` at the right nesting level, or a key literally named `"s"` nested one level deeper). This is structurally the same class of bug as the CRLF/chunk-boundary confusion in the report: the serializer relies on an implicit, unframed boundary convention that a crafted input can violate, so two semantically different inputs can canonicalize to the identical wire representation and therefore the identical hash.

The impact channel is `object_hash.getChash160` / `getBase64Hash`, which drives:
- Address definitions (`getChash160(arrDefinition)`) used to derive a payment address (analogous to "address definitions and authentifiers" in scope).
- Unit hash / to-be-signed hash (`getUnitHash`, `getUnitHashToSign`), which every node computes independently to agree on unit identity [10](#0-9) [3](#0-2) .

If two structurally distinct definitions/units can be engineered to serialize identically, this becomes a second-preimage-style collision in ocore's canonical hashing, which is the trust anchor for address ownership and unit identity — i.e., exactly the kind of "node disagreement on validity" / spoofed-definition primitive the validation rules in this analog scan are meant to guard against.

### Impact Explanation
If exploitable, an attacker could craft an alternate address definition (`arrDefinition`) that hashes (via `getChash160`) to the same address as a legitimate, previously-published definition, while encoding different spending conditions (e.g. a different `pubkey`). Since address ownership and authorization in ocore is entirely determined by whichever definition hashes to the claimed address (`chash160`), a colliding definition would let an attacker later reveal/attach the colliding definition and attempt to authorize spends from that address under conditions the original owner never agreed to — unauthorized spending. A collision in `getUnitHash`/`getUnitHashToSign` would let two nodes compute different validation outcomes for what they believe is "the same" unit content, causing consensus/validity disagreement.

### Likelihood Explanation
I was **not able to fully construct a concrete colliding pair** within the scope of this investigation — doing so requires finding two distinct JSON shapes (respecting all of `validateDefinition`'s field-name/type constraints in `definition.js`, which I began but did not finish reviewing) that (a) are each independently valid per `definition.js`/`validation.js` schema checks, and (b) still emit byte-identical `\x00`-joined token streams despite the schema differences. The building blocks — unframed objects, un-reserved single-character tokens as legal string values/object keys, and reliance purely on the join character for delimiting — are confirmed in the code, but whether any *validation-legal* field (e.g., a data-feed name, an oracle address, a `case` value in `definition.js`) can actually take on the literal value `"s"`/`"n"`/`"b"`/`"["`/`"]"` and be positioned to produce a genuine ambiguous flattening needs further, deeper enumeration of `definition.js`'s accepted definition templates than I completed.

### Recommendation
Add unambiguous framing to `getSourceString`: wrap object values with a delimiter pair (mirroring the array `'['`/`']'` treatment) instead of leaving them unfenced, and additionally reject string values or object keys whose value exactly equals any of the reserved single-character tokens (`s`, `n`, `b`, `[`, `]`), or switch the tag encoding to length-prefixed tokens (as is already done in `getJsonSourceString`'s length-implicit JSON-based scheme) so that no valid input can mimic a structural marker.

### Proof of Concept
Not conclusively constructed — see Likelihood Explanation. A follow-up engineer with access to run `string_utils.getSourceString()` directly (outside this read-only investigation) should test candidate pairs such as:
```js
getSourceString({ s: "xyz" })      // -> "s\x00s\x00xyz"
getSourceString("s") // top-level string "s" alone -> "s\x00s"  (not colliding, but illustrates the ambiguity)
```
and search for a schema-legal `arrDefinition`/message-payload pair (per `definition.js` validation rules) that collides under this scheme.

```javascript
function getSourceString(obj) {
	var arrComponents = [];
	function extractComponents(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				if (variable.includes(STRING_JOIN_CHAR))
					throw Error("00 byte in string value in " + JSON.stringify(obj));
				arrComponents.push("s", variable);
				break;
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
				arrComponents.push("n", variable.toString());
				break;
			case "boolean":
				arrComponents.push("b", variable.toString());
				break;
			case "object":
				if (Array.isArray(variable)){
					if (variable.length === 0)
						throw Error("empty array in "+JSON.stringify(obj));
					arrComponents.push('[');
					for (var i=0; i<variable.length; i++)
						extractComponents(variable[i]);
					arrComponents.push(']');
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0)
						throw Error("empty object in "+JSON.stringify(obj));
					keys.forEach(function(key){
						if (typeof variable[key] === "undefined")
							throw Error("undefined at "+key+" of "+JSON.stringify(obj));
						if (key.includes(STRING_JOIN_CHAR))
							throw Error("00 byte in object key in " + JSON.stringify(obj));
						arrComponents.push(key);
						extractComponents(variable[key]);
					});
				}
				break;
			default:
				throw Error("getSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	extractComponents(obj);
	return arrComponents.join(STRING_JOIN_CHAR);
}
```

```javascript
function getUnitHashToSign(objUnit) {
	var objNakedUnit = getNakedUnit(objUnit);
	for (var i=0; i<objNakedUnit.authors.length; i++)
		delete objNakedUnit.authors[i].authentifiers;
	var sourceString = (typeof objUnit.version === 'undefined' || objUnit.version === constants.versionWithoutTimestamp) ? getSourceString(objNakedUnit) : getJsonSourceString(objNakedUnit);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
```
