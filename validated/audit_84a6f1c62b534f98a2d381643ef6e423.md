## Analysis: Cross-organization webhook event forgery via signature/target binding mismatch in `WebhooksController`

### Title
Webhook signature verification keys off `repository.owner.login` while all event handlers act on `repository.full_name`, allowing cross-organization webhook forgery — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which configured GitHub App/`webhook_secret` to validate the signature against using the attacker-supplied field `repository.owner.login` (or `organization.login`) taken from the still-unverified JSON body [1](#0-0) . However, every webhook `Handler` resolves the actual `Repository`/`Stack` to act on using a *different* field of the same payload, `repository.full_name` [2](#0-1) . Because the whole raw body is attacker-controlled JSON (the signature only proves it was signed with *some* configured org's secret), these two fields never need to agree, breaking the equality `organization-that-authenticated == repository-that-is-written`.

### Finding Description
`repository_owner` is computed purely from body content before any cryptographic check occurs: [3](#0-2) 

That value is fed into `Shipit.github(organization: repository_owner)` to pick the `GitHubApp` instance (and thus the `webhook_secret`) used to verify `X-Hub-Signature`: [1](#0-0) 

`GitHubApp#verify_webhook_signature` additionally auto-approves any payload when the selected org has no `webhook_secret` configured: `return true unless webhook_secret` [4](#0-3) . Multi-org Shipit deployments are documented to have per-organization secrets that may be blank in examples [5](#0-4)  and [6](#0-5) .

Once verification passes (either via a leaked/known secret for *any one* configured organization, or via an organization that has no secret configured), the raw params are dispatched to handlers unmodified: [7](#0-6) . Every handler, however, resolves the target `Stack`/`Repository` via `repository.full_name`, not `repository.owner.login`: [2](#0-1) 

This is used identically by `PushHandler` [8](#0-7) , `PullRequest::OpenedHandler` [9](#0-8) , and the status/commit_status handler, which is confirmed by tests to write real `Status` records straight from the webhook body onto an existing commit: [10](#0-9) .

Nothing in the request pipeline asserts that `repository.owner.login` (used to pick the signing secret) is a prefix of `repository.full_name` (used to pick the write target). An attacker who can get one signed/unsigned-org payload accepted (via a leaked/known secret for a minor org on the instance, or an org configured with no secret) can set `repository.full_name` to point at an entirely unrelated organization's repository/stack.

### Impact Explanation
By forging a `status` event whose `repository.full_name` targets another organization's stack, an attacker can inject arbitrary commit `Status` rows (`state`, `context`, `description`) for any commit sha of that stack. Since `Commit#deployable?`/`MergeRequest#reject_unless_mergeable!` gate deploys and merge-queue auto-merges on required status contexts [11](#0-10) , this can be used to fabricate a passing CI status for a required context and trigger an **unauthorized deploy** (via continuous delivery) or an **unauthorized auto-merge** of a pull request on a repository the attacker has no legitimate access to — without ever needing that target organization's real webhook secret, `ApiClient` token, or GitHub credentials. This satisfies the "unauthorized deploy, rollback or merge" High-impact bucket.

### Likelihood Explanation
Any Shipit instance configured with multiple GitHub organizations (a documented, supported configuration) is exposed as soon as one organization either omits a webhook secret (shown as a valid example config) or its secret is otherwise known/leaked to the attacker. No special access to the target organization/repository is required — only knowledge of one signing secret (or the absence of one) somewhere in the instance's multi-org configuration.

### Recommendation
- Verify the webhook signature using the `GitHubApp` configuration determined by the same repository field that handlers subsequently use to resolve the target (`repository.full_name`), not `repository.owner.login`/`organization.login`.
- After signature verification, assert that the resolved `Repository#owner` (from `full_name`) matches the organization whose secret validated the signature; reject the request otherwise.
- Do not silently treat a missing `webhook_secret` as "always verified" in multi-organization configurations; require an explicit opt-in or fail closed.

### Proof of Concept
Given a Shipit instance configured with two orgs, `UnsecuredOrg` (no `webhook_secret` set) and `TargetOrg` (the real victim stack), an unauthenticated attacker sends:

```
POST /webhooks
X-Github-Event: status

{
  "repository": {
    "owner": { "login": "UnsecuredOrg" },
    "full_name": "TargetOrg/target-repo"
  },
  "sha": "<existing deployable commit sha in TargetOrg/target-repo>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://example.com",
  "created_at": "2026-09-02T00:00:00Z"
}
```

`verify_signature` selects `Shipit.github(organization: "UnsecuredOrg")`, whose `verify_webhook_signature` returns `true` unconditionally because no secret is configured [12](#0-11) . The status handler then resolves `TargetOrg/target-repo` via `full_name` [13](#0-12)  and creates a genuine `Status` row for that commit, exactly as demonstrated by the existing test for the status event [10](#0-9) , which can then satisfy `required_statuses` and unlock deploy/merge for `TargetOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

    end

    end
