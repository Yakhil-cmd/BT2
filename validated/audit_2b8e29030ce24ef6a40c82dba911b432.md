### Title
Null Pointer/Type Dereference on Malformed Private-Payment `inputs[0]` Crashes Node in `validatePayment` - (File: validation.js)

### Summary
`validation.js`'s `validatePayment()` is shared between fully-validated public units and the separate, lighter-weight private-payment validation path (`private_payment.js` → `divisible_asset.js`/`indivisible_asset.js`). For public units, `validate()` pre-checks that every payment input is a non-empty object (`validation.js:245-255`). Private payments never go through that check, so a malicious private-payment counterparty can send a payload whose `inputs[0]` is `null`, a number, or a string, causing an unguarded `payload.inputs[0].type` access to throw a `TypeError` from inside an asynchronous DB-query callback, uncaught by any try/catch in the call chain.

### Finding Description
`validatePayment()` only validates that `payload.inputs` is a non-empty array: [1](#0-0) 

For asset payments it then reads the asset info and dereferences `payload.inputs[0]` directly: [2](#0-1) 

There is no check anywhere in `validatePayment()` that `payload.inputs[0]` (or other input elements) is a non-empty object. For unit-level (network) validation, this is safe because `validate()` performs that check earlier for every message in the unit: [3](#0-2) 

However, private payments bypass `validate()`'s message-array checks entirely. The private-payment entry points only validate array-level shape, not element types: [4](#0-3) [5](#0-4) 

These call directly into `validation.initPrivatePaymentValidationState` and then `validation.validatePayment`, never passing through the `objUnit.messages.every(...)` guard that exists in `validate()`: [6](#0-5) 

Consequently, a crafted private-payment element with `payload.inputs: [null]` (or `[42]`, `["x"]`, `[[]]`) reaches `payload.inputs[0].type` inside the `storage.loadAssetWithListOfAttestedAuthors` callback, throwing `TypeError: Cannot read properties of null (reading 'type')`. This happens inside a database-query callback with no surrounding `try/catch`, so the exception is not converted into an `ifError` callback — it propagates as an unhandled exception.

### Impact Explanation
An unhandled exception thrown from inside an asynchronous DB callback in a Node.js process typically escapes any `try/catch` in the synchronous call stack and becomes an uncaught exception on the event loop, crashing the process (unless a top-level `process.on('uncaughtException')` handler exists to catch it defensively — none was found guarding this specific call path in `validation.js`, `private_payment.js`, `divisible_asset.js`, or `indivisible_asset.js`). This is directly analogous to CVE-2017-13768: a crafted, attacker-controlled input causes a null/undefined dereference that crashes the process handling it — here the counterparty-controlled private-payment JSON crashes the receiving wallet/hub. Repeated delivery of such payloads by any private-payment counterparty causes a persistent denial of service against the victim's node (inability to process further payments/units while crashing/restarting), which is impact-generating (a node unable to confirm/process new units) and is in scope as it's triggered by an unprivileged private-payment counterparty message, not a network/p2p/node-operator exploit.

### Likelihood Explanation
Likelihood is high for the specific trigger: any device/wallet that can send a private payment (a normal, unprivileged capability of any correspondent in the network) can supply this malformed payload without needing special permissions, keys, or timing. The check gap is a simple, deterministic omission (`isNonemptyArray` without per-element `isNonemptyObject`), reliably reached on the very first message processed.

### Recommendation
In `validatePayment()` (validation.js), validate that every element of `payload.inputs` (and `payload.outputs`) is a non-empty object with expected shape before any property access, mirroring the check already present in `validate()`:
```js
if (!payload.inputs.every(i => isNonemptyObject(i) && (!("type" in i) || ["issue","headers_commission","witnessing"].includes(i.type))))
    return callback("bad input in payment");
```
Apply the same object-shape guard at the very top of `validatePayment()` so both the public-unit and private-payment code paths are protected uniformly, and audit other private-payment entry points (`indivisible_asset.js`, `divisible_asset.js`) for similar unguarded array-element access.

### Proof of Concept
1. Attacker (a normal wallet correspondent) sends a private payment chain via `handlePrivatePaymentChains` / `handleOnlinePrivatePayment` with a head element like:
```json
{
  "unit": "<valid unit>",
  "message_index": 0,
  "payload": {
    "asset": "<valid existing asset id>",
    "inputs": [null],
    "outputs": [{"address":"<addr>","amount":100}]
  }
}
```
2. This flows through `private_payment.js:validateAndSavePrivatePaymentChain` → `divisible_asset.js:validateAndSaveDivisiblePrivatePayment` → `validation.js:validatePayment`.
3. Execution reaches `var bIssue = (payload.inputs[0].type === "issue");` with `payload.inputs[0] === null`, throwing `TypeError: Cannot read properties of null (reading 'type')` inside the `storage.loadAssetWithListOfAttestedAuthors` DB callback, with no enclosing `try/catch`, crashing the receiving node process.

*Note: I was unable to fully verify at what layer (if any) a generic Node `uncaughtException`/`unhandledRejection` handler intercepts this specific throw across all deployment configurations (full node vs. light wallet vs. hub), since global handlers are defined in `network.js` but their exact scope/behavior for this call path was not fully traced within the available search budget. This should be confirmed by a live reproduction.*
