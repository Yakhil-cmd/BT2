### Title
Webhook signature is verified against `repository.owner.login`'s secret while the acted-upon repository is taken from the unverified `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate a request against using `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body, while the handlers that actually act on the payload (`Handler#repository_name`) resolve the target `Repository`/`Stack` using a *different* field in the same body, `repository.full_name`. Because both fields are attacker-controlled and Shipit supports multiple independently-configured GitHub organizations (each with its own, sometimes absent, webhook secret), an attacker who controls the webhook secret for any one configured organization (or one with no secret configured, which is always "verified") can forge a signed payload that names their own org for signature selection but names a victim org/repo's `full_name` for the actual stack lookup.

### Finding Description
`verify_signature` selects the verification key by: [1](#0-0) 
using `repository_owner`, defined as: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization configuration (including a per-org `webhook_secret`) when Shipit is set up with the documented multi-organization schema: [3](#0-2) 

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever the selected organization has no `webhook_secret` configured, and otherwise validates the HMAC over the *entire* raw request body using that organization's secret: [4](#0-3) 

Once the request passes this check, `WebhooksController#create` dispatches the whole (still attacker-controlled) parsed JSON to the registered handlers: [5](#0-4) 

Every handler resolves which `Repository`/`Stack` to operate on via `Handler#repository_name`, which reads `repository.full_name` — a field completely independent from the `repository.owner.login`/`organization.login` field used for signature-key selection: [6](#0-5) 

Nothing ties `repository.owner.login` (used to pick the HMAC secret) to `repository.full_name` (used to pick the acted-upon stack) — they are simply two independent keys inside the same attacker-supplied JSON body. This is the same class of bug as the reported analog: the field that is cryptographically bound/checked (`repository.owner.login`) is not the field that is actually acted upon (`repository.full_name`), i.e. `verified_organization == acted_upon_repository_owner` is assumed but never enforced.

### Impact Explanation
In a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), an attacker who is a legitimate, unprivileged member/admin of any one of those configured organizations (or where any configured org has no `webhook_secret` set) can:
- Set `repository.owner.login` (or `organization.login`) to their own/known org so `verify_signature` selects a secret they control (or none at all).
- Set `repository.full_name` to `victim-org/victim-repo`, a stack belonging to a completely different, unrelated tenant of the same Shipit instance.

This lets the attacker drive `PushHandler` to enqueue `GithubSyncJob` for the victim's stack with an arbitrary `expected_head_sha`: [7](#0-6) 

or drive `StatusHandler` to fabricate a passing CI status on an arbitrary commit of the victim stack: [8](#0-7) 

A forged "success" status can flip a commit's deployable state and trigger continuous deployment/merge scheduling on the victim's stack: [9](#0-8) 

This is a cross-tenant/cross-repository write and can result in an unauthorized deploy/merge on a repository the attacker has no legitimate access to — a Critical-severity outcome per the defined impact criteria.

### Likelihood Explanation
Exploitation requires only:
1. Shipit configured for multiple GitHub organizations (explicitly documented and supported), and
2. The attacker having legitimate access to any one of those configured organizations (to know/set its webhook secret) or any configured org lacking a webhook secret.

No privileged Shipit session, API token, or victim credentials are needed — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted body and a signature computed with a secret the attacker legitimately controls. This is a realistic, unprivileged-attacker scenario in any multi-tenant Shipit deployment.

### Recommendation
Bind the field used to select the verification secret to the same field used to resolve the acted-upon repository/stack: verify signatures per-request using the organization implied by `repository.full_name`'s owner (the same value handlers use), and reject requests where `repository.owner.login`/`organization.login` and the owner portion of `repository.full_name` diverge. Alternatively, after selecting the GitHub App by whatever key is used for the secret, re-derive `repository_owner` strictly from that same source consistently used by the handlers, and fail closed if it cannot be verified against a per-organization secret (do not allow an "unset secret ⇒ verified" bypass in multi-org mode).

### Proof of Concept
Given a Shipit instance configured with two GitHub organizations, `attacker-org` (webhook secret known to/controlled by the attacker, or unset) and `victim-org` (hosts a tracked stack `victim-org/victim-repo`):

1. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s webhook secret (or sends any value if `attacker-org` has no secret configured).
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
4. `WebhooksController#create` dispatches the full payload to `PushHandler`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues `GithubSyncJob` for the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the request was never signed by `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
