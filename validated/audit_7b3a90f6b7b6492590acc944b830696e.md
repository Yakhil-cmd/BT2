### Title
Cross-organization webhook confusion: signature is verified against the `repository.owner.login` org's secret, but stack/commit lookups act on the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`). But once the signature check passes, the actual event handlers (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, and `StatusHandler#process`) resolve which `Stack`/`Commit` records to mutate using a *different* field: `repository.full_name` (for push/check_suite/pull_request handlers) or a global `sha` lookup with no repository/organization scoping at all (`StatusHandler`). Because HMAC verification only proves "this body was signed with organization X's webhook secret," not "this body's repository/full_name belongs to organization X," a party who legitimately possesses an onboarded organization's webhook secret can forge a delivery whose `repository.owner.login` matches their own org (so it passes `verify_signature`) while `repository.full_name` (or `sha`) targets a completely different, victim organization's repository/stack.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This binds trust to `repository.owner.login`. But `app/models/shipit/webhooks/handlers/handler.rb` uses an entirely separate field to decide *what gets written*:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`CheckSuiteHandler`, `PushHandler`, and PR handlers key off `stacks`/`repository_name` (i.e., `repository.full_name`), not `repository.owner.login`. `StatusHandler` is even looser - it does `Commit.where(sha: params.sha)` with no repository scoping whatsoever, meaning any org's signed webhook can create a CI status for a commit sha belonging to any tracked stack across the entire Shipit instance.

Because Shipit explicitly supports "Using Multiple Github Applications" (`docs/setup.md`), each configured organization has its own `webhook_secret` that the admin/owner of that org's GitHub App knows (they created it under their own org's GitHub settings). The equality the code implicitly (and incorrectly) assumes is:

`organization that signed the webhook == organization whose repository/commit is mutated`

but the code only checks:

`repository.owner.login (used to pick the verification secret) == repository.owner.login`

while performing the mutation against `repository.full_name` (or a bare `sha`), which is never cross-checked against the verified organization. An attacker who administers Org A (onboarded into Shipit's multi-org config, with a known webhook secret for Org A) can sign a payload with `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"` (or a `sha` value copied from Org B's public commit history) to affect Org B's stack.

### Impact Explanation
This crosses a credential/organization boundary that Shipit is designed to enforce (`Shipit.github(organization: ...)` selecting per-tenant secrets specifically to isolate orgs from one another). Concretely, an attacker controlling Org A's webhook secret can, against a victim Org B's stack tracked by the same Shipit instance:
- Forge CI status webhooks (`StatusHandler`) to mark arbitrary commits on Org B's stacks as green/`success`, defeating required-status checks and enabling an unauthorized deploy/merge of unreviewed or malicious code.
- Trigger `sync_github`/`RefreshCheckRunsJob` against Org B's stacks via forged `push`/`check_suite` events.
This can escalate into an unauthorized deploy (the report's severity bar: "Critical - ... an unauthorized deploy, rollback or merge"), since falsified commit statuses are consumed by Shipit's deployability checks used to gate deploys/merges.

### Likelihood Explanation
Exploitation requires the attacker to control (or be the legitimate admin of) at least one GitHub organization/app that has been onboarded into this Shipit instance's multi-org `github:` config, which is a realistic multi-tenant deployment scenario explicitly documented in `docs/setup.md`. No Shipit session, `ApiClient` token, or write access to the *victim* repository is needed - only knowledge of a valid webhook secret for any org configured in the instance, which is by-design known to that org's own admin. This is a lower bar than compromising the victim org directly, and it directly exploits a verification/authorization mismatch in first-party engine code (`webhooks_controller.rb` + `handler.rb`), not a third-party gem defect or DoS.

### Recommendation
After `verify_signature` succeeds, cross-check that the resource being mutated actually belongs to the verified organization:
- In `Handler#stacks`/`#repository_name`, verify that `repository.owner.login` (the field used for authentication) matches the owner segment of `repository.full_name` before resolving stacks.
- In `StatusHandler#process`, scope `Commit.where(sha: params.sha)` to commits whose stack's repository owner equals the verified `repository_owner`, rather than searching globally across all tracked repositories.
- More generally, pass the verified organization down into each handler and require handlers to assert `record.repository.owner == verified_organization` before performing any mutation.

### Proof of Concept
1. Shipit instance is configured (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs: `OrgA` (attacker-administered) and `OrgB` (victim, with a Shipit stack tracking `OrgB/victim-repo` and commit `deadbeef123...`).
2. Attacker knows `OrgA`'s `webhook_secret` (they created OrgA's GitHub App).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "deadbeef123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully (the signature does match OrgA's secret for this exact body).
6. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha)` — since `sha` is a global lookup with no organization scoping, it matches OrgB's tracked commit and creates a forged successful status on it, even though the request was never signed by OrgB's webhook secret.
