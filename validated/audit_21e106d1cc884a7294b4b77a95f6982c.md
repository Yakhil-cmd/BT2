This confirms the escalation path: `User#authorized?` checks membership in `Shipit.github_teams` [1](#0-0) , meaning a forged membership webhook against a shared `Team` row can grant an attacker-controlled user authorization into the Shipit application itself, not merely writing a team row.

### Title
Cross-organization `Team` membership forgery via `MembershipHandler#find_or_create_team!` matching on `github_id` alone - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#repository_owner` falls back to `params.dig('organization','login')` for events (like `membership`) that carry no `repository` key, so `verify_signature` authenticates the payload against whatever organization the attacker names in the JSON body [2](#0-1) . `MembershipHandler#find_or_create_team!` then looks up the `Team` purely by `github_id: params.team.id`, and the `organization=` assignment inside the block only executes on row creation, never on an existing match [3](#0-2) . An attacker who controls the webhook secret for their own configured GitHub organization can therefore forge a signed `membership` webhook naming a foreign team's `github_id`, causing `team.add_member(member)` to mutate that foreign team's membership `Shipit::Webhooks::Handlers::MembershipHandler#process` [4](#0-3) .

### Finding Description
The broken binding: `Team#organization` stored on the row should equal `params.organization.login` of the *verified* payload for every write that touches that row. Trace:

1. Attacker POSTs `/webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":<shopify_developers.github_id>,...},"organization":{"login":"not-shopify"},"member":{"login":"walrus-clone"}}`, signed with the webhook secret configured for `not-shopify` (an org the attacker legitimately controls in a multi-org Shipit config, see `docs/setup.md` for the multi-org `secrets.github` schema).
2. `WebhooksController#repository_owner` returns `params.dig('organization','login')` = `'not-shopify'` because membership payloads have no `'repository'` key [5](#0-4) .
3. `verify_signature` calls `Shipit.github(organization: 'not-shopify').verify_webhook_signature(...)`, which succeeds because the attacker owns that org's secret [6](#0-5) .
4. `MembershipHandler#find_or_create_team!` runs `Team.find_or_create_by!(github_id: params.team.id)`; since a `Team` row with that `github_id` already exists (owned by `shopify`), it is found, and the block that sets `team.organization` never executes [3](#0-2) .
5. `process` then calls `team.add_member(User.find_or_create_by_login!('walrus-clone'))`, inserting a `Membership` row linking the attacker-controlled user to the `shopify_developers` team, despite the request being authenticated for `not-shopify` [7](#0-6) .

Existing guards do not prevent this: `verify_signature` only checks the signature matches *some* org's secret, and never cross-checks that the resolved `repository_owner`/`organization.login` equals the `organization` column already stored on the `Team` row being mutated. `ExplicitParameters` (`params do ... end`) only validates shape/types, not cross-tenant ownership [8](#0-7) .

### Impact Explanation
The attacker gains write access to `Membership` rows for any `Team` whose `github_id` they can learn (GitHub team IDs are discoverable via the GitHub API by anyone who can see the org, or simply guessable as small sequential integers), from an organization they legitimately control in the same Shipit deployment. This is a cross-tenant mutation of another organization's `Team` record — explicitly one of the listed Critical categories ("a payload for one repository mutating another's stack, commit, task or team"). Further, `User#authorized?` grants Shipit authorization to any user in `Shipit.github_teams` [1](#0-0) , so if `shopify_developers` is configured as one of `Shipit.github_teams`, this forged membership can escalate an attacker-controlled account into an authorized Shipit user for the victim organization's stacks — matching the High "escalation into `Shipit.github_teams` authorization" category as well. The attack is repeatable against any team whose `github_id` is known and works from any org the attacker controls within the same multi-org Shipit install.

### Likelihood Explanation
Preconditions: the Shipit deployment must be configured for multiple GitHub organizations (per `docs/setup.md`'s multi-org `secrets.github` format) and the attacker must control at least one such organization with its own `webhook_secret` — a realistic scenario for hosted/shared Shipit instances serving several tenants. No Shipit session, API token, or victim-org secret is required; the attacker only needs their own org's webhook secret (which they own) and the numeric `github_id` of the target team (obtainable via public/organization GitHub API). The request is a single unauthenticated-to-Shipit HTTP POST, fully repeatable.

### Recommendation
In `find_or_create_team!`, verify that the found (or created) team's `organization` matches `params.organization.login` (the org the signature was verified against) before proceeding, e.g. raise/drop the event if `team.organization != params.organization.login`, and/or scope the `find_or_create_by!` lookup by both `github_id` and `organization` instead of `github_id` alone.

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb` (not to be created, only described per scope rules — but included here for completeness of the audit):
1. Configure two orgs in test secrets: `shopify` (existing) and `not-shopify` with its own `webhook_secret`.
2. Assert precondition: `shipit_teams(:shopify_developers).organization == 'shopify'` and `shipit_teams(:shopify_developers).members.exclude?` the attacker user.
3. POST `/webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":shipit_teams(:shopify_developers).github_id,"slug":"ouiche","name":"Ouiche","url":"x"},"organization":{"login":"not-shopify"},"member":{"login":"walrus-clone"}}`, signed with `not-shopify`'s webhook secret.
4. Assert `response.status == 200`.
5. Assert violated binding: `shipit_teams(:shopify_developers).reload.organization == 'shopify'` still, but `shipit_teams(:shopify_developers).members.map(&:login)` now includes `'walrus-clone'`, proving a `not-shopify`-authenticated payload mutated `shopify`'s team.
