### Title
StatusHandler updates CI status for every `Commit` sharing a `sha` regardless of the payload's repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike its sibling `CheckSuiteHandler` which scopes lookups via `stacks.where(...)`. Any verified `status` webhook whose `sha` collides with a commit belonging to an unrelated `Stack`/`Repository` will mutate that unrelated commit's CI status too.

### Finding Description
Binding that should hold: `status_update.repository == payload.dig('repository', 'full_name')`, i.e. the set of `Commit` rows mutated by a given `status` webhook should be exactly `stacks_for(payload.repository).commits.where(sha: params.sha)`.

Actual code: [1](#0-0) 
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This performs a global, unscoped `Commit` lookup across the entire database — there is no `.stacks`/`Repository.from_github_repo_name(repository_name)` filter as used in `CheckSuiteHandler`: [2](#0-1) 

The webhook controller's signature check only verifies that the request was signed with the GitHub App credentials configured for the organization named in the payload (`repository_owner`), not that the `sha` in the payload actually belongs to that repository: [3](#0-2) 
This check confirms *who sent* the webhook, but places no constraint on which `Commit` rows the handler is allowed to touch. `Handler#stacks`/`repository_name` exist and are used by other handlers (`CheckSuiteHandler`), but `StatusHandler` doesn't call them at all — it never even reads `payload['repository']`.

Exploit flow: An attacker who owns a GitHub repository/organization "attacker-org" (with Shipit-configured GitHub App credentials, since they are a legitimate onboarded tenant/organization able to send real, correctly-signed webhooks for their own repo) creates a commit whose sha collides with (or is identical to) a commit that already exists in another tenant's `Stack` (an empty/no-op commit or a cherry-picked/merged commit sharing a sha across forks is a realistic occurrence). The attacker sends a `status` webhook for their own repository with `repository.owner.login = attacker-org`. `verify_signature` in `WebhooksController` succeeds because it validates against `attacker-org`'s own legitimate GitHub App config — this is not a forged-signature bypass, it's a valid signature for the attacker's own org. `StatusHandler#process` then updates **every** `Commit` in the database with that sha, including the one belonging to the victim's unrelated `Stack`.

### Impact Explanation
A single valid webhook from one tenant's own repository can flip CI status (`success`/`failure`/`pending`, `create_status_from_github!`) on commits belonging to a completely different `Stack`/`Repository`/tenant. Since Shipit stacks commonly gate continuous deployment (`schedule_continuous_delivery`, `ProcessMergeRequestsJob`) on commit status/state transitions, this can trigger unwanted continuous deployment or unblock merges in a stack that never authenticated the payload — this is a payload for one repository mutating another repository's commit/stack state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any repository whose commits happen to share a sha with the attacker's chosen commit (achievable deliberately via empty/no-op commits or shared upstream history/forks), and can affect multiple stacks/tenants simultaneously in one request.

### Likelihood Explanation
The attacker needs their own repository onboarded with a working GitHub webhook secret for their own org (which any onboarded, unprivileged GitHub org/repo owner has) — no Shipit secrets, tokens, or privileged roles are required. The only extra requirement is a sha collision, which is trivially engineerable: empty commits, cherry-picks, or a shared ancestor commit across forked/mirrored repositories all naturally produce identical shas across different `Stack`s tracked by the same Shipit instance. This is a realistic and reproducible condition, not merely theoretical.

### Recommendation
Scope `StatusHandler#process` to the payload's own repository, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently, join through `Repository.from_github_repo_name(repository_name)&.stacks&.commits&.where(sha: params.sha)`.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repo_a = shipit_repositories(:...)` with a `Stack` `stack_a`, and `repo_b` with `Stack` `stack_b` (different `github_repo_name`s / owners).
2. Create `commit_a = stack_a.commits.create!(sha: 'deadbeef'*5, ...)` and `commit_b = stack_b.commits.create!(sha: 'deadbeef'*5, ...)` — identical sha, different stacks/repos.
3. Stub `GithubHook#verify_signature` to return true (simulating a validly-signed webhook from `repo_a`'s org).
4. POST a `status` webhook payload with `sha: 'deadbeef'*5`, `state: 'success'`, and `repository.full_name` set to `repo_a`'s name only.
5. Assert: `commit_a.reload.state == 'success'` AND `commit_b.reload.state == 'success'` — proving the payload scoped to `repo_a` mutated `commit_b` in an unrelated `stack_b`/`repo_b`, violating `status_update.repository == payload.repository`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
