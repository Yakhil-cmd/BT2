### Title
Unbounded rule-file enumeration in the hookify PreToolUse hook enables approval-pipeline DoS - (File: plugins/hookify/core/config_loader.py)

### Summary
The reported Canto issue is a classic "unbounded attacker-controlled collection processed on every privileged operation" DoS: `GetPoolBalances` iterates every token balance in a pool on each `AddLiquidity`/`RemoveLiquidity` call, and an attacker can inflate that collection to exhaust gas and break the pool for everyone. The closest analog in this repository is the `hookify` plugin's `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` hooks, which re-glob and re-parse **every** `.claude/hookify.*.local.md` rule file from disk on **every single tool call**, with no cap on file count, file size, or total parse time.

### Finding Description
`load_rules()` globs all matching files unconditionally and parses each one on every invocation: [1](#0-0) 

There is no limit on:
- The number of `hookify.*.local.md` files matched by the glob.
- The size of each file's content that gets fed into `extract_frontmatter`.
- The total time spent parsing before the calling hook must return a decision.

`extract_frontmatter` performs a line-by-line hand-rolled YAML-ish parse over the file content: [2](#0-1) 

Crucially, this loading happens synchronously inside `PreToolUse`, which gates **every** Bash/Edit/Write/MultiEdit tool call in the session: [3](#0-2) 

The resulting rule list is then evaluated against the tool call by `RuleEngine.evaluate_rules`, which loops over the full rule set again for every condition check: [4](#0-3) 

If an attacker (via prompt injection, a malicious skill, a compromised dependency, or simply a poisoned/untrusted repository checked out into the workspace) can get many `hookify.*.local.md` files written under `.claude/`, every subsequent tool call in the session pays the full cost of re-reading and re-parsing all of them from scratch — there is no caching, no size cap, and no count cap. This is structurally identical to the Canto bug: an attacker inflates an unbounded, attacker-influenceable collection that a privileged/gating code path iterates on every operation, and the gating path has a hard resource/time budget (gas in Canto; hook execution timeout in Claude Code — hook scripts are documented elsewhere as expected to "complete quickly (< 60s)").

### Impact Explanation
If the per-tool-call rule loading/parsing exceeds the hook timeout, the `PreToolUse` hook fails to return a timely decision. Depending on how Claude Code treats hook timeouts/errors, this either:
- Silently fails open (the `except Exception` in `pretooluse.py` catches only parse-time exceptions inside `main()`, not glob/read latency, so a hang would exceed the hook's timeout budget rather than raising a catchable exception), causing tool-call gating (including block/warn rules meant to catch dangerous `rm -rf`, `eval(`, etc.) to be bypassed — a hook-bypass condition, or
- Causes every tool call in the session to stall/timeout, degrading or freezing the session (denial of service against the user's own workflow).

This is a real, unprivileged-reachable trust-boundary issue (hook bypass / tool authorization gating), matching the accepted analog categories in scope.

### Likelihood Explanation
Medium. It requires an attacker to get a large number of files matching `.claude/hookify.*.local.md` created in the project directory — plausible via prompt injection against Claude while it has file-write access, via a malicious skill/plugin that writes such files, or via checking out a repository that already contains many such files (since these are typically gitignored `*.local.md` files but nothing prevents committing look-alikes or having Claude itself be tricked into generating them). No special privilege is required beyond ordinary file-write capability that Claude Code sessions already have.

### Recommendation
- Cap the number of `hookify.*.local.md` files processed per event (e.g., first N by mtime/name) and log/warn when the cap is exceeded, mirroring the `MAX_DIFF_FILES` / pathological-bailout pattern already used elsewhere in this codebase (`plugins/security-guidance/hooks/security_reminder_hook.py`).
- Cap the size of each rule file read (skip or truncate files above a small threshold, e.g. a few KB, since rule files are expected to be short).
- Cache parsed rules keyed by file path + mtime/hash for the life of the session instead of re-globbing and re-parsing on every tool call.
- Enforce and measure a hard wall-clock budget inside `load_rules()`/`main()` (not just around parsing) so a large/slow filesystem enumeration cannot silently exceed the hook timeout.
- Apply the same caps to `PostToolUse`, `Stop`, and `UserPromptSubmit` hook entry points, which share the identical `load_rules()` call pattern.

### Proof of Concept
1. In a project directory, create a large number of minimally-valid rule files, e.g. for `i` in `1..5000`: write `.claude/hookify.rule_$i.local.md` each containing a `---\nname: r$i\nevent: bash\npattern: x\n---\nmsg`.
2. Trigger any `Bash` tool call in a Claude Code session in that directory.
3. Observe `plugins/hookify/hooks/pretooluse.py` invoking `load_rules(event='bash')`, which globs and fully parses all 5000 files via `extract_frontmatter` before returning a permission decision — as file count/size scales up, this delay grows until it approaches or exceeds the hook execution timeout, blocking or bypassing the permission-check gate for that and subsequent tool calls. def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)
