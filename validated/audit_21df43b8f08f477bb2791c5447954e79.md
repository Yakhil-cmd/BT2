### Title
Webhook signature is verified against `repository.owner.login`, but events are dispatched based on `repository.full_name` — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects the GitHub App / HMAC secret used to verify an incoming webhook based on `repository.owner.login`, but the handlers that actually act on the payload (create statuses, trigger `GithubSyncJob`, etc.) resolve the target `Stack` using a completely different field, `repository.full_name`. Because both fields come from the same attacker-suppliable JSON body and are never cross-checked against each other, an attacker who knows the webhook secret for *any one* organization configured on a multi-org Shipit instance can forge a signed payload whose `owner.login` matches that known secret while its `full_name` points at a stack that belongs to a completely different, victim organization.

### Finding Description
`WebhooksController#verify_signature` picks the per-organization `GitHubApp`/secret purely from an attacker-controlled JSON field: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the secret purely by that same organization key, with no relation to which repository will ultimately be affected: [3](#0-2) 

Once the signature check passes (using the secret selected by `owner.login`), the full raw JSON is dispatched to every matching handler: [4](#0-3) 

But handlers resolve which `Stack`/`Repository` to operate on from a *different* JSON key, `repository.full_name`: [5](#0-4) 

Nothing enforces that `full_name`'s owner segment equals `owner.login`. This breaks the intended trust binding: `organization whose secret authenticated the request == organization that owns the repository being written to`. In a multi-tenant Shipit deployment (multiple GitHub orgs configured, as shown in `config/secrets.development.shopify.yml`), an attacker who legitimately controls (or has previously configured) a webhook for their own org — and therefore knows that org's `webhook_secret` — can:
1. Set `repository.owner.login` = "attacker-org" (or `organization.login` in the fallback case) so `verify_signature` selects and validates against the attacker's known secret.
2. Set `repository.full_name` = "victim-org/victim-repo", pointing at any stack tracked by the Shipit instance under a completely different organization.

Because `Handler#stacks` resolves purely from `full_name`, the forged payload is processed as if it legitimately originated from the victim organization's GitHub App/webhook, e.g. triggering `PushHandler#process`, which enqueues `stack.sync_github` for the victim's stacks: [6](#0-5) 

Other handlers (e.g. the `status` event handler tested in `test/controllers/webhooks_controller_test.rb`) create/overwrite commit `Status` records for arbitrary commits based on attacker-supplied `sha`/`state`, again scoped only by the forgeable `repository`/`sha` fields.

### Impact Explanation
This is a High-severity authentication-boundary break: an entity that is only authenticated as "org A" (via a webhook secret it legitimately possesses) can inject events that are processed as if they came from "org B," any other organization tracked by the same multi-tenant Shipit instance. Concretely this allows an attacker to:
- Forge commit `status`/`check_suite` events for a victim's tracked commits, spoofing CI results (e.g., faking a passing status), which can satisfy deploy-readiness checks gating an unauthorized deploy.
- Force arbitrary `GithubSyncJob` executions against victim stacks.

This matches the "authorization escalation across organizations resulting in an unauthorized deploy" class of impact called out as in-scope.

### Likelihood Explanation
Requires the attacker to know a `webhook_secret` for at least one organization configured on the shared Shipit instance — attainable by anyone who legitimately administers (or previously administered, and secrets weren't rotated) a repository/organization onboarded to that Shipit deployment. No GitHub App private key, `Shipit` session, or `ApiClient` token is needed, and no host-application misconfiguration is required — this is the documented multi-org webhook flow (`WebhooksController#verify_signature` + `Shipit.github(organization:)`).

### Recommendation
After verifying the HMAC signature, re-derive the "authenticated organization" and cross-check it against the organization implied by `repository.full_name` (and by the `Repository`/`Stack` actually resolved by the handler) before processing the event; reject the request if they don't match. Alternatively, resolve the target `Stack`/`Repository` first, and verify the signature using the secret configured for *that* repository's organization rather than trusting `repository.owner.login`/`organization.login` from the unauthenticated payload.

### Proof of Concept
1. Attacker administers `attacker-org`, which is configured in Shipit's `secrets.github` (or previously was), and knows `webhook_secret` for `attacker-org`.
2. Attacker crafts a JSON body: `{"ref":"refs/heads/main","after":"<sha>","repository":{"full_name":"victim-org/victim-repo","owner":{"login":"attacker-org"}}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to the shared `/webhooks` endpoint with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own known secret (`lib/shipit/github_app.rb#verify_webhook_signature`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), triggering a sync (or status/check-run injection) against the victim's stack — despite the request never having been authenticated by the victim organization's own webhook secret.

    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

    @github[organization] ||= GitHubApp.new(organization, config)
  end
