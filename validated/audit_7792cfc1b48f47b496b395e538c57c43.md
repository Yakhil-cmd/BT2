Based on my investigation, I've confirmed the vulnerability. This maps cleanly to the report's "safe-approve blocks on the wrong bound value" class: a field used to select an authenticator is not the same field acted upon downstream, and there is no cryptographic binding between them.

### Title
Webhook signature verification authenticates the `repository.owner.login` organization while event handlers act on the independent, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` taken directly from the unauthenticated request body, then verifies the signature against that secret. Once verification "passes," `create` re-parses the same raw body and dispatches it to handlers (`PushHandler`, `ClosedHandler`, `OpenedHandler`, etc.) which resolve the target repository/stack using a *different* field from the same JSON object: `repository.full_name`. Nothing binds these two fields together, and nothing prevents an organization whose GitHub App is configured with no `webhook_secret` from being used to authenticate a payload whose `repository.full_name` points at a completely different, secret-protected organization/repository tracked by the same Shipit instance.

The equality that should hold, and does not:
`organization authenticated by verify_signature (repository.owner.login) == organization/repository actually acted upon by the handler (repository.full_name)`.

Because both fields live in the same attacker-controlled JSON body and are never cross-checked, an attacker can craft a single payload where `repository.owner.login` names an organization configured in Shipit with no `webhook_secret` (satisfying `verify_webhook_signature`'s trivial `return true unless webhook_secret`), while `repository.full_name` names an entirely different, secret-protected organization/repository that is actually tracked by Shipit and has stacks configured. No knowledge of any `webhook_secret` is required — the exploit relies purely on the org-selection/repo-selection field mismatch and the documented "optional" secret feature.

### Impact Explanation
An unauthenticated attacker can forge GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) for any repository/stack tracked by the Shipit instance, as long as any one configured GitHub organization lacks a `webhook_secret` (an explicitly supported, documented configuration). This lets the attacker, for example, forge `push` events to trigger `stack.sync_github` on a victim stack, or forge `status`/`check_suite` events to fabricate green CI signals for an arbitrary commit SHA, undermining Shipit's build/checks-based deploy gating — a cross-repository trust bypass and precursor to unauthorized deploys.

### Likelihood Explanation
High: the request requires no credentials, secrets, or GitHub App access — only that the deployment has at least one GitHub organization configured without a `webhook_secret`, which the setup docs explicitly present as an optional, valid configuration choice. Any internet-reachable `/webhooks` endpoint (the documented Webhook URL) is exploitable.

### Recommendation
Cryptographically bind the authenticated organization to the repository actually processed: after verifying the signature for `repository_owner`, additionally verify that `repository.full_name`'s owner matches `repository_owner` (or, better, resolve the `GitHubApp`/secret via the specific `Repository` record already registered for `repository.full_name`, not from an unauthenticated field in the same payload). Additionally, warn or refuse to boot when a multi-org configuration mixes organizations with and without `webhook_secret`, since GitHub itself does not require globally distinct secrets, this is a Shipit-specific trust boundary.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `OrgWithoutSecret` (no `webhook_secret`) and `VictimOrg` (has `webhook_secret` set, tracks stack `VictimOrg/victim-repo`) — matching the supported schema in `docs/setup.md` "Using Multiple Github Applications".
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgWithoutSecret" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
No `X-Hub-Signature` header is required to match anything real, since `Shipit.github(organization: "OrgWithoutSecret")` resolves a `GitHubApp` whose `verify_webhook_signature` returns `true` unconditionally.
3. `verify_signature` passes; `create` dispatches the payload to `PushHandler`, which resolves `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — despite the request never being authenticated for `VictimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
