## Title
Independent `has`/`has one` clauses in address/asset spending conditions can be satisfied by a single reused output — ([File: definition.js])

## Summary
Obyte's authentication-condition language (used both for address definitions and for asset `issue_condition`/`transfer_condition`) lets a definer combine multiple `has`/`has one`/`has equal` clauses with `and`/`or` to require that the spending unit contain certain payments (e.g. "must pay fee A to address X" and, separately, "must pay fee B to address Y" or even two distinct qualifying outputs to the same filter). Each `has`/`has one` clause is evaluated independently by re-scanning `objUnit.messages` from scratch and simply checking whether *any* (or *exactly one*) matching output/input exists anywhere in the unit. There is no bookkeeping that marks an output as "already consumed" by a previous clause, so the very same, single output can satisfy two (or more) logically distinct `has` requirements in the same `and` combination. This mirrors the H-03 pattern in the external report: a check verifies a coarse, shared/global condition ("this state/resource is present") instead of confirming a fresh, dedicated instance was provided for each individual requirement, allowing one real payment to be counted twice.

## Finding Description
The `has`/`has one` opcode is implemented in `augmentMessagesAndEvaluateFilter`/`evaluateFilter`, which walks every payment message of the unit and collects all outputs/inputs matching the filter (`asset`, `address`, `amount`/`amount_at_least`/`amount_at_most`, `type`) into `arrFoundObjects`, then returns true if the count is non-zero (`has`) or exactly one (`has one`): [1](#0-0) [2](#0-1) 

These clauses are typically combined with `and`/`or`, which just calls `evaluate` on each sub-clause independently and ANDs/ORs the boolean results: [3](#0-2) 

Because each `has`/`has one` clause re-scans the full, unmodified `objUnit.messages` array, nothing prevents the exact same output object from being the one that satisfies clause #1 *and* the one that satisfies clause #2. A definer who writes something like:
```
['and', [
  ['has', {what:'output', address:'FEE_ADDR', amount_at_least: 1000}],
  ['has', {what:'output', address:'FEE_ADDR', amount_at_least: 2000}]
]]
```
intending "two separate qualifying payments must be present," is actually satisfied by a **single** output of amount 2000 to `FEE_ADDR`, since that one output independently matches both filters. The same applies to asset `issue_condition`/`transfer_condition`, which are evaluated through the identical `evaluate`/`evaluateFilter` machinery via `evaluateAssetCondition`: [4](#0-3) [5](#0-4) 

This is directly reachable by any unprivileged unit poster who authors an address using such a definition, or by any asset issuer who defines an `issue_condition`/`transfer_condition` with multiple `has`/`has one` requirements intended to enforce distinct qualifying payments.

## Impact Explanation
Any address/asset spending condition that relies on multiple independent `has`/`has one` clauses to require what the definer believes are *separate* qualifying payments can be bypassed with a single payment that happens to satisfy all of the filters simultaneously. Depending on how the condition is used (e.g., "N-of-N fee payments to different oracle/beneficiary addresses required to unlock funds," or "issue is only allowed once a co-payment output to a specific address is present, and it must be at least two different amounts/tiers to unlock progressively larger issue amounts"), this can let an attacker unlock spending, issue an asset, or transfer restricted funds while paying less than intended — a concrete case of unauthorized spending / bypass of an asset's or address's designed spending condition.

## Likelihood Explanation
Exploitability depends entirely on how definers write their conditions, but the vulnerability is a language-level (not application-level) gap: any definer who is not aware that `has` clauses are not mutually exclusive across the same unit's messages can unintentionally create such a bypassable condition. Since asset issue/transfer conditions and address definitions are core, widely-used building blocks (multi-sig-like fee/authorization schemes are a natural use case), the likelihood of this pattern being used — and exploited once discovered — is moderate to high for any asset/address relying on multiple `has`-style requirements instead of a single combined filter (e.g. `sum`, or `has equal` tying inputs to outputs).

## Recommendation
Track which outputs/inputs have already been "consumed" by a prior `has`/`has one` match within the same unit evaluation context (e.g., pass a shared "already used" index set through the `evaluate` recursion for a given unit), and exclude already-matched objects when evaluating subsequent `has`/`has one` clauses in the same `and`/`or` tree. Alternatively, document this limitation explicitly and steer definers toward `sum`/`has equal` constructs that already tie amounts together, and audit widely used asset templates for definitions combining multiple independent `has` clauses that assume mutual exclusivity.

## Proof of Concept
1. Define an asset with:
```
transfer_condition: ['and', [
  ['has', {what:'output', address:'BENEFICIARY', amount_at_least: 1000}],
  ['has', {what:'output', address:'BENEFICIARY', amount_at_least: 5000}]
]]
```
   intending that a transfer must include two distinct qualifying payments (e.g. a base fee and a premium fee) to `BENEFICIARY`.
2. Construct a unit transferring the asset that includes only **one** base-asset output of amount 5000 to `BENEFICIARY`.
3. `evaluateAssetCondition` → `validateAuthentifiers` → `evaluate(['and', ...])` calls `evaluate` on each `has` clause; `evaluateFilter` re-scans `objUnit.messages` for each clause and finds the same 5000-byte output satisfies both `amount_at_least: 1000` and `amount_at_least: 5000` filters independently.
4. Both `has` sub-results are `true`, so the `and` condition is satisfied with a single payment instead of the two independent payments the condition author intended, allowing the transfer to proceed while underpaying the intended combined fee.
