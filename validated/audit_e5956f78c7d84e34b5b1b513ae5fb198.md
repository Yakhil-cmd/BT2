### Title
CCMenu API endpoint leaks repository/environment identifiers for stacks outside a token's authorized `stack_id` scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#show` overrides the `stack` lookup method to use `Stack.from_param!(params[:stack_id])` directly instead of the base controller's `stacks.from_param!`, which is the only place that enforces the `current_api_client.stack_id` scoping. As a result, any valid CCMenu token with `read:stack` permission can fetch the CCTray XML for *any* stack, not just the one it was issued for, leaking `stack.to_param` (owner/repo/environment) and `webUrl` (full stack URL) for unauthorized repositories.

### Finding Description
The claimed binding is: `repository info disclosed == repositories current_api_client.stack_id authorises`. Tracing the code shows this binding is broken:

- `Shipit::Api::BaseController#stacks` restricts the queryable set: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` uses `stacks.from_param!(params[:stack_id])` [1](#0-0) .
- `Shipit::Api::CCMenuController` however overrides `stack` to bypass that scoping entirely: `@stack ||= Stack.from_param!(params[:stack_id])`, querying across all stacks with no reference to `current_api_client.stack_id` [2](#0-1) .
- The only authorization gate on this controller is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!(operation, scope)` [3](#0-2) . `ApiClient#check_permissions!` only checks that the string `"read:stack"` is present in the client's `permissions` array; it never compares `stack_id` to the requested stack [4](#0-3) .
- `show` then renders `shipit/ccmenu/project` with the unscoped `stack`, and the view exposes `name: stack.to_param` (which is `repo_owner/repo_name/environment`, see `Stack#to_param` [5](#0-4) ) and `webUrl: stack_url(stack)` [6](#0-5) .

Attack: an attacker who holds any valid CCMenu/API token with `read:stack` permission (e.g. one legitimately issued to them for their own repository via `CCMenuUrlController#fetch`, which creates a client with `permissions: %w[read:stack]` [7](#0-6) ) sends `GET /stacks/*any_other_stack_id/ccmenu?token=<their_token>`. Because `CCMenuController#stack` ignores `current_api_client.stack_id`, the controller looks up and returns the target stack's `Project` XML regardless of the token's actual scope, disclosing that stack's owner/name/environment and web URL.

Existing guards do not prevent this: `require_permission` only checks the permission string, not per-record scoping; `authenticate_api_client` only verifies the token signature, not the stack; there is no `require_permission!(operation, scope, resource:)` variant tying the check to `current_api_client.stack_id` for this controller.

### Impact Explanation
Exposure of `stack.to_param` (organization/repository name and environment) and the CCMenu build URL for a stack outside the token holder's authorized scope constitutes unauthenticated/unauthorized read of stack existence and identity — matching the "High: unauthenticated read of stack state" category. It confirms the existence, naming, and CI/CD environment structure of private repositories/organizations using Shipit, to a party who should only see their own. The attack is repeatable against arbitrary `stack_id` values (enumerable via the predictable `owner/repo/environment` URL format) for any holder of a valid, even narrowly-scoped, CCMenu token.

### Likelihood Explanation
Preconditions: attacker must possess *any* valid CCMenu API token (readily obtainable for their own stack via the normal "Fetch URL" CCMenu button in the settings UI, requiring only that they be a Shipit user with access to at least one stack). No GitHub secrets, webhook secrets, or Shipit operator privileges are needed. Given a valid token, guessing or enumerating other `owner/repo/environment` triples is straightforward since the format is public (`stack.to_param`) and mirrors GitHub repo naming. This makes the issue cheap and highly repeatable.

### Recommendation
In `Shipit::Api::CCMenuController`, remove the `stack` override and use the inherited `stacks.from_param!(params[:stack_id])` (or explicitly check `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering) so that stack-scoped tokens cannot access stacks outside their `stack_id`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot view another stack's CCMenu XML" do
  scoped_client = ApiClient.create!(
    creator: @user,
    name: "scoped",
    permissions: %w[read:stack],
    stack_id: @stack.id
  )
  other_stack = Stack.create!(repository: Repository.new(owner: "secret-org", name: "secret-repo"), branch: "main")

  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  assert_response :ok # currently succeeds - should be :forbidden or :not_found
  refute_includes response.body, other_stack.repository.full_name # currently FAILS: body includes it
end
```
Binding under test: `repository info disclosed (other_stack.repository.full_name in response.body) == repositories current_api_client.stack_id (== @stack.id) authorises (only @stack)`. The proof shows the equality is violated: the unauthorized `other_stack`'s identity is disclosed even though `current_api_client.stack_id` only authorizes `@stack`.
