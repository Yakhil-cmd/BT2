### Title
Webhook signature scoped by `repository.owner.login` does not bind the repository actually mutated (`repository.full_name`) - cross-repository/cross-organization write ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` is used to HMAC-verify an inbound webhook by reading `repository.owner.login` (or `organization.login`) out of the very same JSON body it is about to verify. Once the signature check passes, the event is dispatched to a handler that resolves the target `Stack`/`Repository` using a *different* field of the same payload, `repository.full_name`. Nothing ties these two fields together, so the "organization whose secret authenticated the request" is not equal to the "repository that gets written to."

### Finding Description
`verify_signature` computes the signing organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

The base `Handler` class, used by `PushHandler` and others, resolves the actual `Stack`/`Repository` to mutate using a *separate* field, `repository.full_name`: [3](#0-2) [4](#0-3) 

Since `repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/target-selection) are two independent, attacker-controlled fields inside the same signed JSON body, an attacker who can produce a valid signature for *one* organization (`org-A`) can still forge a payload whose `repository.full_name` points at a stack belonging to an entirely different, unrelated organization/repository (`org-B/victim-repo`). The HMAC only proves "this byte sequence was signed with org-A's secret" - it says nothing about which repository the payload is permitted to reference, because Shipit itself does not cross-check `repository.owner.login` against `repository.full_name`'s owner segment, nor does it verify that the resolved `Stack`'s repository belongs to the organization identified by `repository_owner`.

This is compounded by `GithubApp#verify_webhook_signature`, which treats an org configured with a blank `webhook_secret` as an automatic pass: [5](#0-4) 
If any organization managed by this Shipit instance is configured without a `webhook_secret` (the documented sample config even ships with `webhook_secret: # nil`), an attacker just needs to set `repository.owner.login` to that organization to skip verification entirely, then set `repository.full_name` to any other tracked repository (e.g. a high-value `org-B/prod-repo`) to trigger `stack.sync_github`, forged commit statuses (`StatusHandler`), or team/membership mutations (`MembershipHandler`) against a stack it has no legitimate relationship to.

This is the exact bug class from the ERC20 report generalized: the verified authority (`ERC20(token).symbol()` assumed correct/consistent) does not actually cover the field that downstream logic trusts (`principalSymbol`/`collateralSymbol` used blindly). Here, the verified authority ("this JSON is signed by org-A") does not cover the field downstream logic trusts to select which repository/stack gets mutated (`repository.full_name`).

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." Successful exploitation lets an attacker with only a webhook-signing credential for one (possibly secret-less) organization trigger unauthorized state changes — forced re-sync (`PushHandler` → `stack.sync_github`), forged CI/commit statuses (`StatusHandler` → `commit.create_status_from_github!`), or team membership changes (`MembershipHandler`) — against stacks and repositories belonging to a different organization. This matches the "cross-repository writes" / "unauthorized deploy" Critical bucket, since `sync_github` and forged statuses can influence what gets merged/deployed for a repository the attacker does not control.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a payload that verifies for *some* configured organization while referencing a *different* organization's repository in `repository.full_name`. This is trivially possible if any tenant organization is configured with no `webhook_secret` (an explicitly supported, documented configuration in `config/secrets.development.shopify.yml`), requiring zero attacker credentials. In multi-tenant setups where every org does have a distinct, secret webhook secret, exploitation would additionally require possession of one org's `webhook_secret`, which is a lower bar than compromising the target org's own secret, GitHub App key, or `GITHUB_TOKEN`.

### Recommendation
Cross-validate that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to a handler, and reject the request otherwise. Do not allow `verify_webhook_signature` to silently return `true` for organizations with a blank `webhook_secret` unless that behavior is an explicit, documented single-tenant-only fallback; for multi-tenant deployments, require every configured organization to have a webhook secret before webhooks are accepted.

### Proof of Concept
1. Configure Shipit with two organizations, `org-A` (no `webhook_secret`, or a secret known to the attacker) and `org-B` (tracked stack `org-B/prod`).
2. POST to `/hooks` (via the `webhooks#create` route) with `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha already merged upstream>",
  "repository": {
    "owner": { "login": "org-A" },
    "full_name": "org-B/prod"
  }
}
```
3. `repository_owner` resolves to `org-A`; `Shipit.github(organization: 'org-A').verify_webhook_signature` passes (secret is blank, or attacker signs with known `org-A` secret) per [5](#0-4) .
4. `create` dispatches to `PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"org-B/prod"` per [6](#0-5) , triggering `stack.sync_github` on a stack the attacker never authenticated for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
