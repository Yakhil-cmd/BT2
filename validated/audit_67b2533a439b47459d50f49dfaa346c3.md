### Title
`recapitalize` refunds the undeployed portion of a declared amount that was never received, draining pool custody while the cash book still reports it - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The CVE class is an error/edge path that completes only part of a multi-step operation, leaving allocated-but-untracked state behind. The analog in `LiquidityPool::recapitalize` is worse than a leak: the pool trusts the *declared* `amount` passed by the caller path, computes `refund = amount - min(amount, backing_shortfall)`, and transfers that refund out of real pool custody without ever verifying that `amount` tokens were actually transferred in. When the inbound transfer is short or absent, the refund leg still executes — the "excess return" step completes while the "receive funds" precondition was never met — so custody leaves the contract while `cash` keeps claiming the market is backed.

### Finding Description
`recapitalize` is documented as: the controller transfers `amount` into the pool, then the pool credits `min(amount, backing_shortfall)` to cash and refunds the remainder. The refund leg is a pure function of the declared `amount`:

- `applied = amount.min(guards::backing_shortfall(&cache))` — `contracts/pool/src/ops/recapitalize.rs:52`
- `refund = amount - applied` — `contracts/pool/src/ops/recapitalize.rs:53-55`
- `outcome.cache.transfer_out(&payer, outcome.refund)` — `contracts/pool/src/ops/recapitalize.rs:34`

There is no balance-delta measurement of what the pool actually received — unlike the repo's own convention elsewhere (router strategies measure output by balance delta). The pool book (`cash`) is credited only by `applied`, but the token transfer out is sized by the declared `amount`. If the declared `amount` exceeds what actually arrived — or nothing arrived at all — `transfer_out` pays the payer from the suppliers' custody. The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3483`) demonstrates exactly this: calling `recapitalize` with the full custody balance and no funding leaves the pool balance at 0 while `cash` still covers the supplier's deposit, and a subsequent `withdraw` passes the pool's own `require_reserves`/solvency guards and fails inside the SAC transfer.

This mirrors the CVE shape: the teardown/error-side leg (return the unused portion) runs unconditionally while the setup leg (receive the declared funds) is merely assumed. State is left "half destroyed" — the token balance is gone but the accounting record of it survives.

### Impact Explanation
Two compounding impacts, both in the accepted classes:

1. **Theft of user funds**: a caller can declare an `amount` larger than the market's `backing_shortfall` — trivially so when the shortfall is 0, making the *entire* `amount` refundable — and have the pool pay that "refund" out of suppliers' real token custody without having funded it.
2. **Protocol insolvency / frozen funds**: after the drain, `cash` overstates custody. `require_reserves` reads the book, not the balance, so exits clear the pool's liquidity guards and then revert inside the SAC transfer — suppliers' withdrawals permanently fail once the shortfall equals or exceeds their claims.

`recapitalize` is reachable by an unprivileged address through the controller's public `recapitalize` entrypoint (listed among the permissionless controller verbs), making this a single-address attack.

### Likelihood Explanation
The exploit requires no privileged role, no oracle manipulation, and no price condition. The attacker picks a market where `backing_shortfall < declared amount` — which includes any healthy market where the shortfall is zero — calls `recapitalize(hub_asset, payer, amount)` with `payer` as their own address, funds the pool with less than `amount` (or nothing, depending on how the controller leg is invoked), and collects `amount - shortfall` from custody. The only uncertainty is the exact funding step in `contracts/controller/src/markets.rs` (not fully read in this analysis); the pool-side defect — trusting declared `amount` for the refund without measuring the received balance — is unambiguous and confirmed by the repo's own test, which asserts the drain succeeds and the book ends up overstating custody.

### Recommendation
- Measure the actual received balance in `recapitalize` (balance delta of the pool's SAC balance before/after the controller's inbound leg), or have the controller pull `amount` via `transfer_from` inside the same call so a short inbound transfer reverts atomically.
- Alternatively, cap `refund` by custody: `refund = min(amount - applied, pool_balance - cash_committed)`.
- Keep the existing test as a regression spec and flip its assertions: an unfunded recapitalize must refund nothing and leave `cash == balance`.

### Proof of Concept
The existing test `contracts/pool/tests/flows.rs:3408-3483` is the PoC:

```rust
// custody is 10_000_000_000; caller declares that as `amount` with no funding
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);            // custody drained via "refund"
assert!(t.state_snapshot().cash >= deposit);      // book still claims backing

// a supplier's exit clears the pool's own guards and fails in the SAC transfer
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
// outcome is SAC BalanceError(10) — not InsufficientLiquidity, not PoolInsolvent
```

On-chain reproduction: as an unprivileged address, call the controller's `recapitalize` for a market with `backing_shortfall == 0`, declaring `amount` equal to the pool's token balance, with `payer` set to the attacker. `ops::recapitalize::accounting` computes `applied = 0`, `refund = amount`, and `transfer_out(&payer, amount)` pays the full custody to the attacker — while the market's `cash` book is left claiming the funds are present, making subsequent supplier withdrawals unpayable.
