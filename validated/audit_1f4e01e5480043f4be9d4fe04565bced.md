### Title
Unauthenticated stack/branch enumeration via `MergeStatusController#check` and the referrer-based `#stack` fallback lookup - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController#check` is listed in `skip_authentication` alongside `#show`, but unlike `#show` it never calls `current_user.logged_in?` before rendering `stack_status`. Combined with the `#stack` fallback lookup, which resolves a `Stack` purely from the attacker-supplied `referrer` (repo owner/name) and `params[:branch]` with no ownership or membership check, an unauthenticated caller can probe arbitrary `owner/repo` + `branch` combinations and learn whether a matching stack exists and its merge status.

### Finding Description
The broken binding: `authentication_required_to_read_stack_state == true` for every path that discloses `stack.merge_status`, is violated for the `check` action.

Code path:
- `skip_authentication only: %i[check show]` [1](#0-0) 
- `#show` guards disclosure with `return render('logged_out') unless current_user.logged_in?` [2](#0-1) 
- `#check` has **no** such guard and directly renders `stack_status` (HTML "ok"/error-string with a 503, or JSON `{ stack_status: }`) for any request: [3](#0-2) 
- `stack_status` calls `stack.merge_status`: [4](#0-3) 
- `#stack`'s fallback resolves the record solely from `referrer_parser.repo_owner`/`repo_name` (parsed from the attacker-controlled `referrer` param) and either `params[:branch]` verbatim or `environment: 'production'` — no check that the caller has any relationship to that repository: [5](#0-4) 
- `ReferrerParser` only validates the URL shape (`https://github.com/<owner>/<repo>/pull/<n>`), not that the caller is entitled to see that repo's Shipit data: [6](#0-5) 

Exploit: an unauthenticated attacker sends `GET /merge_status/check.json?referrer=https://github.com/victim-org/victim-repo/pull/1&branch=<guessed-staging-branch>`. If a stack with that `(owner, name, branch)` exists, `#check` returns `stack_status` (e.g. `"success"`, `"pending_checks"`, `"behind"`, etc.) or a 503 with the status string; if no such stack/branch exists, `stack` is `nil` and `stack.merge_status` raises, producing a distinguishable error response. This gives the attacker a binary oracle to enumerate the existence and health of internal/non-production branches for any GitHub repo tracked by the Shipit instance, with zero authentication, zero rate limiting on this endpoint, and no logging of the probing pattern beyond normal request logs.

No existing guard prevents this: `skip_authentication` deliberately bypasses `Shipit::Authentication`; there is no `require_permission!`/`authorized?` check inside `#check`; `ExplicitParameters`/model validations don't apply here since this is a read path with a raw `where` filter, not a write; and the `ArgumentError` rescue only exists in `#show`, not `#check`.

### Impact Explanation
The attacker obtains unauthenticated read access to stack state (merge/CI status) for a `Stack` scoped to a repository they don't control and for branches they merely guess, which falls under the High-impact category "unauthenticated read of stack state." It discloses internal branch/stack topology (existence of staging/internal branches, their queue/merge health) for any repository configured on the instance, and is fully repeatable across arbitrary repositories and branch-name guesses since the only cost is an HTTP request.

### Likelihood Explanation
Preconditions are minimal: the target repository must have a Shipit stack configured, and the attacker needs to guess or otherwise learn a branch name (e.g., via GitHub UI, common naming conventions like `staging`, `release-*`, etc.) — no Shipit credentials, GitHub App keys, or team membership are required. The `check` action is explicitly unauthenticated (`skip_authentication`), so this is trivially and repeatedly exploitable at zero cost.

### Recommendation
Require `current_user.logged_in?` (or equivalent authorization) in `#check` just as `#show` does before calling `stack_status`, or remove `check` from `skip_authentication` and gate it behind normal Shipit authentication/authorization. Additionally, handle a `nil` stack explicitly in `#check` (mirroring the `rescue ArgumentError` / `render(html: '')` pattern in `#show`) so a missing/inaccessible stack does not raise an unhandled exception that itself acts as an enumeration oracle.

### Proof of Concept
Minitest plan (`test/controllers/shipit/merge_status_controller_test.rb`):
1. Create two stacks for the same repository `victim-org/victim-repo`: one `environment: 'production'`, `branch: 'master'`; one `environment: 'staging'`, `branch: 'internal-staging-branch'`.
2. Without logging in / setting `session[:user_id]`, issue `get :check, params: { referrer: 'https://github.com/victim-org/victim-repo/pull/1', branch: 'internal-staging-branch' }, format: :json`.
3. Assert `response.status` is `200` or `503` (not a redirect/401/403) and the JSON body contains a `stack_status` key with a real value (not empty), proving the staging stack was read.
4. Assert equality-violation explicitly: `assert_not_equal current_user.logged_in?, true` while `assert_includes response.parsed_body, "stack_status"` — i.e., disclosure occurred despite `current_user.logged_in?` being `false`, breaking the binding that stack-state reads require authentication.
5. Contrast with `get :show` under the same params/session and assert it renders `'logged_out'` (guard present there), highlighting the inconsistency that `#check` lacks the same guard.

    class ReferrerParser
      URL_PATTERN = %r{\Ahttps://github\.com/([^/]+)/([^/]+)/pull/(\d+)}

      attr_reader :repo_owner, :repo_name, :pull_request_number

      def initialize(referrer)
        unless (match_info = URL_PATTERN.match(referrer.to_s))
          raise ArgumentError, "Invalid referrer: #{referrer.inspect}"
        end

        @repo_owner = match_info[1].downcase
        @repo_name = match_info[2].downcase
        @pull_request_number = match_info[3].to_i
      end
    end
