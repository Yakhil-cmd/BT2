### Title
GitHub `status` webhook forges CI status on commits belonging to any repository/organization, not just the one whose signature authenticated the request - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` applies an incoming `status` webhook to **every** `Commit` row in the entire Shipit installation whose `sha` matches `params.sha`, with no scoping to the repository/organization that the webhook payload claims to be from and whose secret was used to authenticate it. [1](#0-0) 

### Finding Description
Shipit's webhook signature check verifies the payload using the secret configured for `repository_owner` derived from the payload itself, then simply dispatches the parsed JSON to the handler for the event type. [2](#0-1) 

Most handlers scope their side effects to the stacks belonging to the `repository.full_name` in the payload, via the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) — e.g. `PushHandler` and `CheckSuiteHandler`. [3](#0-2) [4](#0-3) 

`StatusHandler`, however, ignores the `repository` field entirely and looks the commit up **globally** by `sha` across the whole `commits` table, then writes a `Status` for every matching commit, regardless of which stack/repository it belongs to:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This breaks the binding: **organization that authenticated the webhook == repository whose data is written**. The signature only proves the payload originated from GitHub for the organization named in `repository.owner.login`/`organization.login`, but the actual write (`Commit#create_status_from_github!` → `Status.replicate_from_github!`) is not constrained to that organization's stacks at all: [5](#0-4) [6](#0-5) 

The resulting `Status` directly affects `Commit#deployable?` and CI-gating logic used to decide whether a commit can be deployed: [7](#0-6) 

### Impact Explanation
An attacker who controls (or can register a webhook on) **any** GitHub organization/repository already connected to the Shipit instance can forge a `status` event whose `sha` matches a commit that exists in a **different** organization's stack (git commit SHAs are content-derived and can be reproduced by an attacker who knows/copies the exact commit metadata of a target, e.g. from a public repo, and pushes it into their own attacker-controlled repository). Because `StatusHandler` matches by SHA globally, the forged "success" status is applied to the victim stack's commit, potentially satisfying required CI checks (`stack.required_statuses`) and making an otherwise CI-failing/pending commit appear `deployable?`. This can enable an **unauthorized deploy** of a commit that never actually passed the real CI/checks of the target repository — a cross-organization write with deploy-authorization impact.

### Likelihood Explanation
Requires the attacker to control any org/repo already onboarded to the Shipit instance (a realistic scenario in multi-tenant Shipit deployments where many teams/orgs share one instance) and to know/reproduce a target commit SHA (feasible for public repos or leaked SHAs). No privileged Shipit account, `ApiClient` token, or `webhook_secret` disclosure is needed beyond the attacker's own legitimately-issued organization secret.

### Recommendation
Scope `StatusHandler#process` to commits belonging to the repository named in the webhook payload, mirroring `Handler#stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
and require/validate the `repository` field in `params` for the `status` event.

### Proof of Concept
1. Attacker registers Organization B (with its own valid `webhook_secret`) on the shared Shipit instance and configures a `status` webhook.
2. Attacker discovers/reproduces a commit SHA `X` that exists in a stack belonging to Organization A (target), e.g. by cloning A's public repo commit metadata into a repo they control in Org B (or simply knowing the SHA from a public PR).
3. Attacker triggers a GitHub `status` event from Org B (e.g. via their own CI/webhook) with `sha: X, state: "success", context: "<required-context-of-A's-stack>"`.
4. `WebhooksController#verify_signature` validates the signature using Org B's secret (valid, since it is B's own webhook) and passes.
5. `StatusHandler#process` executes `Commit.where(sha: X)`, finds the commit belonging to Org A's stack, and creates a `success` `Status` for it — bypassing Org A's actual CI, potentially unlocking `deployable?` and an unauthorized deploy of that commit.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
