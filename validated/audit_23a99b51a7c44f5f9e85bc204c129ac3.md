### Title
Webhook signature verified against the payload's `repository.owner.login`, but every handler dispatches on the same payload's `repository.full_name` with no re-check that they identify the same organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate the request against based on `repository_owner` (`params.dig('repository','owner','login')` or the `organization.login` fallback) [1](#0-0) [2](#0-1) . Once the signature check passes, the raw parsed body is handed unmodified to every registered handler [3](#0-2) . Handlers, however, resolve which `Repository`/`Stack` to act on using a *different* field of the same payload: `payload.dig('repository', 'full_name')` in the base `Handler#repository_name` (used by `PushHandler`) and `params.repository.full_name` in every pull-request handler [4](#0-3) [5](#0-4) . Shipit explicitly supports mounting multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, on the same instance [6](#0-5) .

### Finding Description
The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository being written to**. Nothing in the controller enforces this. `verify_signature` derives the org solely from `repository.owner.login`/`organization.login` and looks up the matching `Shipit.github(organization:)` app config to validate `X-Hub-Signature` [7](#0-6) . The subsequent handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) passes the *entire* parsed JSON body straight through, and each handler independently re-reads `repository.full_name` to locate the target `Repository`/`Stack` [3](#0-2) [4](#0-3) . In a single-tenant deployment `owner.login` and `full_name`'s prefix always match because GitHub itself constructs the payload for one specific repo. But in the documented multi-organization configuration, an operator/attacker who legitimately administers GitHub App "A" (and therefore knows/controls App A's `webhook_secret`, since they configure it when installing the app) can send a POST directly to the shared `/github/webhooks` endpoint with `repository.owner.login`/`organization.login` set to organization A (so `verify_signature` selects and validates against App A's secret) while `repository.full_name` is set to `"org-B/victim-repo"` — an unrelated organization/repository that is also configured on the same Shipit instance. `PushHandler` and the pull-request handlers will happily resolve `org-B/victim-repo`'s `Stack`/`Repository` via `Repository.from_github_repo_name(...)` and act on it [8](#0-7) [9](#0-8) , even though the request was authenticated for org A only.

### Impact Explanation
For `push` events, an attacker-forged event naming an arbitrary victim stack/branch and an arbitrary `after` SHA causes `stack.sync_github(expected_head_sha:)` to be enqueued via `GithubSyncJob` for the victim's stack [8](#0-7) . `GithubSyncJob` fetches commits with the victim stack's own `github_api` (so it cannot fabricate content), but it can force a resync/re-detach of the victim stack's commit graph and, if `expected_head_sha` matches an older, already-known commit, contributes to `next_commit_to_deploy`/continuous-delivery scheduling logic that can trigger an unwanted deploy via `ContinuousDeliveryJob` on stacks with `continuous_deployment?` enabled [10](#0-9) [11](#0-10) . For the pull-request family of handlers, this allows an attacker who only controls org A's webhook secret to create/close/archive/unarchive review stacks or mutate `PullRequest` records belonging to an unrelated victim organization's repository (`ReviewStackAdapter`, `LabelCapturingHandler`, `LabeledHandler`, etc.) [9](#0-8) [12](#0-11) . This is a cross-repository/cross-organization write triggered by a request authenticated for a different organization — matching the "cross-repository writes" / "unauthorized deploy or rollback" impact class.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured with more than one GitHub organization (an explicitly documented, supported configuration) [6](#0-5) , and (2) the attacker is a legitimate administrator/installer of one of those less-trusted organizations' GitHub Apps (so they know that org's `webhook_secret`), which is not "privileged" with respect to any other tenant organization on the same Shipit instance. No GitHub App private key, `ApiClient` token, or Shipit session is needed — only an HTTP POST to the public webhook endpoint with a validly-signed body for the attacker's own org, but forged `repository.full_name` pointing to another tenant.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after signature verification in `#create`), require that every field used later for repository/stack resolution (`repository.full_name`, and any `organization`/`repository.owner.login` used by handlers) is consistently derived from, and cross-checked against, the same organization that authenticated the signature. Concretely: after computing `repository_owner`, also compute the owner implied by `repository.full_name` (i.e., `full_name.split('/').first`) and reject the webhook (422) if it doesn't match `repository_owner`/`organization.login`. Alternatively, resolve the target `Repository` by organization-scoped lookup (`Repository.where(owner: repository_owner).from_github_repo_name(...)`) instead of a global `full_name` lookup in `Handler#repository_name`.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.yml`: `org-a` (attacker-administered app, secret known to attacker) and `org-b` (victim, has a stack `org-b/victim-repo` with `continuous_deployment: true`).
2. Attacker computes `sha256=...` (or `sha1=...` per `verify_webhook_signature`) over a crafted JSON body using org-a's `webhook_secret`:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha of an older commit on org-b/victim-repo>",
  "repository": {
    "full_name": "org-b/victim-repo",
    "owner": { "login": "org-a" }
  }
}
```
3. POST to `/github/webhooks` with header `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully because it was signed with org-a's secret [1](#0-0) .
5. `PushHandler#process` resolves the target via `payload.dig('repository','full_name')` = `"org-b/victim-repo"`, finds the victim stack, and enqueues `stack.sync_github(expected_head_sha: ...)` — a write against org-b's stack triggered by a request authenticated only for org-a [4](#0-3) [8](#0-7) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  class ContinuousDeliveryJob < BackgroundJob
    include BackgroundJob::Unique

    queue_as :deploys
    on_duplicate :drop

    def perform(stack)
      return unless stack.continuous_deployment?

      # If there is a schedule defined for this stack, make sure we are within a
      # deployment window before proceeding.
      return if stack.continuous_delivery_schedule && !stack.continuous_delivery_schedule.can_deploy?

      # checks if there are any tasks running, including concurrent tasks
      return if stack.occupied?

      stack.trigger_continuous_delivery
    end
