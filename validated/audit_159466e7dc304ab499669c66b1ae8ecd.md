### Title
`membership` webhook handler binds team membership writes to a client-supplied `team.id`, not to the organization whose secret verified the signature - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against a payload-derived organization (`repository.owner.login`, falling back to `organization.login`), and only enforces that this *named* organization's secret produced a valid signature. [1](#0-0) [2](#0-1)  Once verified, the `membership` event is processed by `MembershipHandler`, which resolves the `Team` to mutate purely by the client-supplied `team.id` field - with no check that this team actually belongs to the organization that authenticated the request - and then adds an arbitrary `member.login` to it. [3](#0-2) 

### Finding Description
Shipit is explicitly designed to be multi-tenant: a single instance can be configured with several independent GitHub organizations, each with its own App, `webhook_secret`, and `oauth.teams` restricting Shipit application access. [4](#0-3) 

For every inbound webhook, `WebhooksController#verify_signature` computes `repository_owner` from the untrusted JSON body itself:
```
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
and uses that value to look up which org's `github_app`/secret to validate the HMAC signature against. [1](#0-0) [2](#0-1)  For a `membership` event, there is no `repository` key, so this resolves to `organization.login`. This means the only cryptographic guarantee provided by signature verification is "this payload was produced by whichever org is *named inside the payload*, using that org's `webhook_secret`" - it says nothing about the *content* of other fields in the same payload (e.g. `team.id`).

`MembershipHandler#find_or_create_team!` then looks up (or creates) the `Team` record purely by the numeric `github_id` taken from the payload's `team.id`, with the `organization` attribute only used when the row does not already exist:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
`process` then calls `team.add_member(member)` (or removes a member), where `member` is a `User` created/found purely from the payload's `member.login` string. [5](#0-4) 

Because `github_id` is a globally unique GitHub team identifier that is *not* re-validated against the `organization.login` that just authenticated the webhook, an attacker who legitimately controls their own onboarded GitHub organization ("Org A", with a real GitHub App and `webhook_secret` they know because it is their own integration) can send a validly-signed `membership` webhook to the shared endpoint whose body claims `organization.login = "Org A"` (matching the org whose secret produced the signature) but sets `team.id` to the numeric GitHub ID of a `Team` row that actually belongs to a different, privileged organization ("Org B") already present in Shipit's database - e.g. one of the teams listed in `Shipit.github_teams`, which gates access to the whole application via `User#authorized?`. [6](#0-5) 

Because `Team.find_or_create_by!(github_id:)` matches on `github_id` alone, it resolves to Org B's existing `Team` row instead of creating a new one, and `team.add_member(member)` adds the attacker's own (real, freely-chosen) GitHub login to that privileged Team's `memberships`. [5](#0-4) 

The binding that is broken is: *the GitHub organization whose secret cryptographically authenticated the webhook* vs. *the Team record that is actually written to by the handler*. The report's inflation-attack analog is "a value acted upon (the exchange index) is derived from data that isn't bound to the correct scope of the operation (the correct depositor's contribution)"; here, the acted-upon value (`team.id`) is likewise never bound to the scope that was actually authenticated (`organization.login`).

### Impact Explanation
Successful exploitation lets an unprivileged attacker - who only needs to control their own, separately onboarded GitHub organization on a shared Shipit instance - add their own GitHub account as a member of a `Team` belonging to a *different* organization, including one listed in `Shipit.github_teams`. Since `User#authorized?` is satisfied by any membership in `Shipit.github_teams`, this grants the attacker full authenticated access to the Shipit web UI and API-backed actions (deploys, rollbacks, locks, API client management) scoped to stacks/repositories they were never authorized for. This is an escalation into `Shipit.github_teams` authorization, one of the explicitly enumerated High-severity impacts.

### Likelihood Explanation
This requires the attacker to run their own legitimate, separately-configured GitHub organization/App integrated with the same shared Shipit instance (a supported, documented multi-tenant deployment pattern), and to know or guess the numeric `github_id` of a privileged team belonging to another tenant organization - team IDs are small sequential integers that are often discoverable via the GitHub API/UI for teams the attacker can view. No repository write access, Shipit session, or Shipit-issued secret is needed; the attacker only needs their own org's genuine `webhook_secret`, which they legitimately possess.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that any *existing* `Team` matched by `github_id` has an `organization` equal to `params.organization.login` before mutating its membership; reject (or no-op) the event otherwise. More generally, `Team` lookups/writes driven by webhook payloads should be scoped by the organization that was cryptographically verified in `WebhooksController#verify_signature`, not solely by attacker-controlled numeric identifiers echoed back in the same payload.

### Proof of Concept
1. Attacker controls "Org A", onboarded to the shared Shipit instance with a genuine GitHub App and known `webhook_secret_A`.
2. Shipit's database already has a `Team` row for "Org B/privileged-team" (`github_id = 999`), which is one of `Shipit.github_teams` used to authorize UI access.
3. Attacker crafts and sends a `membership` webhook body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "privileged-team", "slug": "privileged-team", "url": "https://example.com" },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker-github-login" }
}
```
4. Attacker signs it with `webhook_secret_A` (their genuine secret) and sets `X-Github-Event: membership`, `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and successfully verifies the signature (it is genuinely signed with Org A's secret). [1](#0-0) 
6. `MembershipHandler#process` runs, `find_or_create_team!` matches the existing Org B team by `github_id: 999`, and `team.add_member(member)` adds `attacker-github-login`'s `User` row to that team. [3](#0-2) 
7. Attacker logs in to Shipit via their real GitHub OAuth account; `User#authorized?` now returns true because they are a member of a `Shipit.github_teams` team, granting full access. [6](#0-5)
