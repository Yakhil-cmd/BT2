Based on my review, the Apache Struts issue describes an unbounded read of an HTTP request body into memory (a generic resource-exhaustion pattern) at an application-level endpoint that has no built-in size limit. The scan rules explicitly instruct to reject "oversized-input/flooding/generic resource-exhaustion claims" and "unbounded-loop or memory/storage-growth scenarios" as out of scope.

Searching the codebase for analogous "unbounded read into memory" patterns shows the opposite: Polkadot SDK's equivalent boundaries already enforce explicit size limits before allocating buffers:

- The libp2p request-response codec bounds both request and response sizes before allocating the read buffer: `GenericCodec::read_request`/`read_response` check `length > self.max_request_size` (or `max_response_size`) and return an error before calling `vec![0; length]` and `read_exact`. [1](#0-0) 
- Extrinsic decoding enforces a `MAX_CALL_SIZE`/`DEFAULT_MAX_CALL_SIZE` (16 MiB) heap memory limit via `DecodeWithMemLimit`/`decode_with_mem_limit` when decoding an `UncheckedExtrinsic`, rejecting oversized calls before they consume unbounded memory. [2](#0-1) [3](#0-2) 
- Block/extrinsic length is explicitly checked against `BlockLength`/`max_extrinsic` bounds by `CheckWeight`, and integration tests confirm oversized payloads are rejected before inclusion. [4](#0-3) [5](#0-4) 

No user-facing entry point (extrinsic, contract call, XCM message, or P2P request/response) was found that reads an attacker-supplied payload into memory without a pre-established size bound analogous to the Struts CSP-report endpoint. Any remaining unbounded-memory concern would fall under the excluded "generic resource-exhaustion" category per the scan's rejection criteria, so no analog finding is reported.
