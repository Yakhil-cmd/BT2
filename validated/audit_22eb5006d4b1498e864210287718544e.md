### Title
Uncaught exception from unvalidated base64-decoded length in `isChashValid` causes node crash on malformed address strings - ([File: chash.js])

### Summary
`chash.isChashValid()` (used by `validation_utils.isValidAddress()` for every address string in every unit, AA trigger, payment output, and asset definition) assumes that a base64-decoded 48-character c-hash always yields exactly 36 bytes (288 bits). It never checks the decoded buffer length before feeding it into `buffer2bin()`/`separateIntoCleanDataAndChecksum()`. Node's `Buffer.from(str, 'base64')` silently truncates on invalid characters instead of throwing, so a crafted 48-character string can produce a buffer whose bit-length is neither 160 nor 288. `separateIntoCleanDataAndChecksum()` then throws `Error("bad length=...")` **outside** the only `try/catch` in `isChashValid`, propagating an uncaught exception into address validation that any unprivileged unit/AA-trigger author can trigger.

### Finding Description
`isChashValid()` in [1](#0-0)  only wraps the `base32.decode`/`Buffer.from` call in a `try/catch`:
```
try{
    var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
}
catch(e){
    console.log(e);
    return false;
}
var binChash = buffer2bin(chash);
var separated = separateIntoCleanDataAndChecksum(binChash);
```
For the 48-character (base64) branch, `Buffer.from(encoded, 'base64')` does **not** validate that `encoded` is well-formed base64: Node's decoder stops/skips at invalid characters and returns a buffer of whatever length it managed to decode, without throwing. This means `chash.length` is not guaranteed to be 36 bytes just because `encoded.length === 48`.

`separateIntoCleanDataAndChecksum()` [2](#0-1)  unconditionally throws when the resulting bit-length isn't exactly 160 or 288:
```
var len = bin.length;
var arrOffsets;
if (len === 160) arrOffsets = arrOffsets160;
else if (len === 288) arrOffsets = arrOffsets288;
else throw Error("bad length="+len+", bin = "+bin);
```
This throw happens *after* the try/catch block in `isChashValid`, so it becomes an uncaught exception in the caller's stack. This is the same bug class as CVE-2024-38538: code assumes a fixed minimum/exact structural length ("at least ETH header len bytes") without validating it before parsing, and the resulting mis-sized buffer is processed as if it had the expected shape, producing undefined/error behavior instead of a safe, handled rejection.

`isChashValid` is invoked from `validation_utils.js` (confirmed via grep match) as part of address-format validation (`isValidAddress`), which is used pervasively for unit author addresses, payment output addresses, AA definitions such as `sig`/`in merkle` address lists, and asset/definition validation — i.e., attacker-controlled data arriving from a single posted unit or AA trigger reaches this code path.

### Impact Explanation
An uncaught exception thrown mid-validation of a unit/trigger (rather than a clean `false` return) can propagate up through the synchronous validation call stack. Depending on where the calling code lacks a wrapping try/catch (validation is largely callback-driven, and synchronous throws inside these callbacks are not always caught), this can crash the Node.js process performing validation. If triggered on stability-relevant paths (main validation of incoming units), this can cause a node to be unable to validate/confirm new units — i.e., a network-availability/consensus-processing impact reachable by any unprivileged party who can post a unit or AA trigger containing a malformed 48-character "address" field.

### Likelihood Explanation
High likelihood of reachability: address-format strings appear in virtually every unit (author addresses, output addresses) and every AA trigger/definition. Constructing a 48-character string with an invalid base64 character that causes `Buffer.from` to truncate to an unexpected length requires no special privileges — any unit poster or AA trigger sender can supply it.

### Recommendation
- In `isChashValid()` (`chash.js`), validate `chash.length` immediately after decoding (must be exactly 20 bytes for 160-bit chash or 36 bytes for 288-bit chash) and return `false` if not, before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`.
- Alternatively, wrap the entire body of `isChashValid` (including `buffer2bin` and `separateIntoCleanDataAndChecksum`) in the existing `try/catch` so any length-mismatch throw is converted into a safe `false` return.
- Consider validating base64 strictness (e.g., via `ValidationUtils.isValidBase64`) prior to decoding, consistent with how `signature.js` validates PEM base64 content before use.

### Proof of Concept
```js
const chash = require('./chash.js');

// 48-character string that Buffer.from(..., 'base64') will truncate
// due to an invalid character, so the decoded buffer is not 36 bytes.
const malformed_encoded_288 = 'AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA!'; // 48 chars incl. invalid '!'

try {
    chash.isChashValid(malformed_encoded_288);
    console.log('no crash (unexpected)');
} catch (e) {
    console.log('Uncaught exception (as predicted):', e.message);
}
```
Feeding such a string as an `address` field in a unit's author/output, or inside an AA definition/trigger (`sig`, `in merkle` addresses list, etc.), routes through `validation_utils.isValidAddress` → `chash.isChashValid`, triggering the unhandled `Error("bad length=...")` from `separateIntoCleanDataAndChecksum` during validation of attacker-supplied data.

**Note on confidence:** I was unable to view the exact body of `validation_utils.js` around the `isChashValid` call (only confirmed via grep that it is referenced there) and could not trace every downstream caller of `isValidAddress` to confirm whether all invocation sites wrap it in try/catch. A Devin session with full repository access would be needed to confirm the exact crash propagation path and any existing outer-level catch blocks that might already mitigate this.
