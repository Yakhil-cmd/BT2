### Title
Malicious AA can force revert of an unrelated primary AA trigger by bouncing as an automatically-invoked secondary trigger, causing DoS/fund-lock for legitimate parties bundled in the same trigger cascade - (File: aa_composer.js)

### Summary
Any address that receives a payment output from an AA's response message is automatically and unconditionally treated as a secondary AA trigger if that address happens to be an AA (`handleSecondaryTriggers`). If that secondary AA "bounces" (reverts), the entire primary trigger — including all other legitimate payments and side effects bundled in the same response — is rolled back to the savepoint taken before execution. Because deploying an AA is a completely permissionless, unprivileged action (just posting a `definition` message), an attacker can create an AA that always bounces and get it invoked as an unintended payment recipient inside any protocol AA (auction/lending/marketplace-style AA) whose logic pays out to a caller/attacker-supplied address, analogous to the `buyoutLien` arbitrary receiver in the Astaria report.

### Finding Description
`handleTrigger` in `aa_composer.js` collects every output address touched by a primary AA's response messages (`addOutputAddresses`) and, once the response unit is validated and saved, unconditionally calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)`: [1](#0-0) 

`handleSecondaryTriggers` queries `aa_addresses` for any of those output addresses and, for every AA address found, invokes `handleTrigger` again with `bSecondary: true`: [2](#0-1) 

If any secondary AA in the chain bounces, the error propagates up and the *entire* cascade — not just the malicious secondary AA — is unwound: [3](#0-2) 

The unwind mechanism (`revert`) rolls the database transaction back to a savepoint taken at the start of the primary trigger and clears all accumulated `stateVars`/`batch` writes, discarding every legitimate side effect (payments to other addresses, state updates, etc.) that were part of the same trigger execution, and finally bounces the primary AA as well: [4](#0-3) 

There is no allow-list, no isolation, and no way for the primary AA to "try/catch" a failed payment to a secondary AA and continue — a bounce anywhere in the secondary chain unconditionally reverts the whole primary response. Deploying an AA is fully permissionless (posting a `definition` message that only needs to pass `validateAADefinition` in `aa_validation.js`), so any user can create an "always bounce" AA and get themselves specified/selected as a payout recipient in a target protocol AA (e.g., an auction/lending/marketplace AA built on top of ocore that pays winners, liquidators, or lien holders to an address supplied at trigger time) — this mirrors the Astaria `buyoutLien` pattern of delivering a token/callback to an attacker-controlled receiver that then reverts core operations (`endAuction`, `liquidate`, `_payment`).

### Impact Explanation
Because the whole trigger cascade (not just the malicious leaf) is reverted, an attacker who gets included as (or tricks a protocol into paying) a secondary-AA payee can:
- Force any settlement AA (auction end, liquidation, multi-party payout) built on ocore's AA layer to permanently fail every time it is triggered, since the same malicious AA will be re-invoked and re-bounce on every retry.
- Cause loss/lock of funds and state for all other legitimate parties whose payments/state updates were bundled into the same trigger response, since `revert()` discards everything, not just the offending sub-payment.
- This is a fund-freezing/DoS condition reachable purely from posting standard, permissionless entities (an AA definition unit plus becoming a payee address) with no elevated privileges, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is high for any dApp/AA built on ocore that lets a trigger-time parameter or another party control a payout address (very common pattern: bidder address, liquidator address, referral address, arbitrary recipient chosen by a formula from trigger data). The attacker only needs to (1) deploy a trivial bouncing AA (`bounce($x)` always) and (2) get that address used as a payment recipient of the target AA within a shared trigger execution. No special permissions, timing races, or resource exhaustion are required — it is a deterministic, repeatable griefing vector.

### Recommendation
- Do not allow a single failing secondary AA to unwind unrelated side effects of sibling secondary AAs or the primary AA's other outputs; consider isolating each secondary-trigger sub-transaction so a bounce there only reverts that recipient's payment, not the whole cascade.
- Alternatively/additionally, document and strongly enforce at the AA-formula level that any address used as a payment destination which is *user/trigger supplied* should be treated as untrusted, and encourage/require patterns (e.g., pull-payments, `bounce_fees` sized to make griefing costly, or explicit `if` guards rejecting AA-address destinations) — mirroring the "mapping of active/trusted receivers" and "reentrancy guard" recommendations from the original report, adapted to the AA secondary-trigger cascade.
- Consider capping/charging the primary AA's response for secondary AA bounces (cost attribution) so that repeatedly minting bounce-only AAs to grief a specific protocol has an economic disincentive, rather than only being paid for by the bounce_fees of the immediate secondary call.

### Proof of Concept
1. Attacker deploys AA `M` with `messages: [{app:'data', payload:{x:1}}]` guarded by an `if` that is always false / or explicit `bounce("griefed")` in its formula, so `M` always bounces on any trigger (any unit sending money to `M`'s address).
2. Attacker interacts with (or is a legitimate counterparty of) a protocol AA `P` built on ocore whose response logic pays out to a trigger-supplied or state-tracked "receiver"/"winner"/"liquidator" address (analogous to `buyoutLien`'s arbitrary receiver), and gets `M`'s address set/used as that receiver — e.g., by placing the highest bid, being selected as liquidator, or by directly triggering `P` with `trigger.data.receiver = M`.
3. When `P`'s response includes a payment output to `M`, `aa_composer.handleTrigger` → `handleSecondaryTriggers` (aa_composer.js:1702-1741) automatically triggers `M`.
4. `M` bounces; per aa_composer.js:1743-1757 and 1759-1783, the error propagates and the *entire* primary trigger from `P` (including any other legitimate outputs/state changes bundled in that same response) is rolled back via `ROLLBACK TO SAVEPOINT initial_balances`, and `P` itself ends up bounced.
5. Because this can be repeated on every retriggering of `P` involving `M`, the attacker can indefinitely DoS `P`'s settlement functionality for all other users whose funds/state are processed in the same trigger, achieving fund loss/lock analogous to the reported Astaria issue.
