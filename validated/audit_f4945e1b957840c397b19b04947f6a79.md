## Analog Found

### Title
Private textcoin payload (mnemonic + private chains) is written to disk with default, world-readable permissions - (File: wallet.js)

### Summary
`storePrivateAssetPayload()` in `wallet.js` persists the mnemonic and the chains of private elements for a private-asset textcoin payment into a zip file on disk using `fs.writeFile(fullPath, zipFile, cb)` without ever specifying a restrictive file mode. On POSIX systems, `fs.writeFile` without an explicit `mode` defaults to `0o666` masked by the process umask (commonly `0o644`), making the file readable by any other local OS user for as long as it exists — not just during a short creation window as in the DIRAC advisory, but persistently until it is deleted. [1](#0-0) 

### Finding Description
When a private (non-public) asset is sent as a textcoin, `sendMultiPayment()`'s `preCommitCb` invokes `opts.getPrivateAssetPayloadSavePath`, and once the caller supplies a path, `storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, arrChainsOfRecipientPrivateElements, cb)` is called to serialize `{mnemonic, chains}` into a zip and write it with `fs.writeFile`: [2](#0-1) [1](#0-0) 

The `mnemonic` here is the seed that derives the private key controlling the textcoin address (see `expandMnemonic`, which turns the mnemonic directly into an `xPrivKey`/`address`): [3](#0-2) 

Because the mnemonic is equivalent to a bearer private key for the asset value locked in the textcoin address, and the private chains contain the blinding data needed to spend the private payload, this file is exactly as security-critical as an X.509 proxy in the DIRAC advisory — whoever reads it can redeem the funds. No `mode` option is passed to `fs.writeFile`, so the file inherits default, group/world-readable permissions on typical POSIX configurations, and no subsequent `fs.chmod` is performed to restrict it.

### Impact Explanation
Any other unprivileged local user or process on the same machine (a common deployment scenario for desktop/headless Obyte wallets and multi-tenant hosts) can read the file the instant it is created and extract the mnemonic before the intended recipient claims it. Because textcoins are bearer instruments, this allows the local reader to claim/spend the asset themselves — a concrete unauthorized-spending / double-spend-race condition directly analogous to "unauthorized users can read proxy contents ... perform any action possible with the original proxy" in the DIRAC report, except the exposure window here is unbounded (any time before the file is removed) rather than sub-millisecond.

### Likelihood Explanation
Exploitation requires local co-residency (shared filesystem access with the wallet process), which mirrors the DIRAC threat model exactly ("unauthorized users on the same machine"). Given that `getPrivateAssetPayloadSavePath` is a normal, documented flow for private-asset textcoins (not an edge case), and the file is written with no hardening at all, likelihood is high whenever the wallet process runs on a shared or multi-user host.

### Recommendation
Create the file with restrictive permissions from the start (e.g., pass `{ mode: 0o600 }` to `fs.writeFile`, or open with `fs.open(path, 'wx', 0o600)` and write via the resulting file descriptor) instead of relying on default umask-derived permissions. Where possible, also `fs.chmod` the destination path to `0o600` immediately after creation as a defense-in-depth measure, and document that `getPrivateAssetPayloadSavePath` implementations should target directories not readable by other local users.

### Proof of Concept
1. Configure a wallet consumer that supplies `opts.getPrivateAssetPayloadSavePath` to save private textcoins to a shared directory (e.g., `/tmp/...`).
2. Call `wallet.sendMultiPayment` with a private asset output targeting a `textcoin:` address; this triggers `storePrivateAssetPayload` at [4](#0-3) .
3. On the same host, as a different OS user, `stat`/`cat` the resulting zip file immediately after creation — because `fs.writeFile` used no restrictive mode, the file is readable (commonly `0644`).
4. Unzip and read `private_textcoin` JSON to obtain `mnemonic` and `chains`; derive the private key via `expandMnemonic` and claim the textcoin before the legitimate recipient, achieving unauthorized spending.
