Based on my investigation, I found the strongest analog to the reported bug class in ocore's AA (Autonomous Agent) execution model, specifically in the way secondary AA triggers are chained and any single failure reverts the entire response tree, including unrelated successful transfers.

### Title
Single secondary AA bounce reverts entire primary AA trigger response and grants a griefing vector against unrelated AA recipients - (File: aa_composer.js)

### Summary
`handleTrigger()` in [1](#0-0)  processes secondary AA triggers with `async.eachSeries`. If any single secondary AA in the chain bounces, the entire primary trigger's response — including payments to other, unrelated, well-behaved addresses processed in the same response unit — is reverted via `revert()`, which performs `ROLLBACK TO SAVEPOINT initial_balances` and clears the batch, discarding all state changes and forcing the whole primary trigger to bounce instead.

### Finding Description
When a primary AA trigger's response messages contain outputs to other AA addresses, `handleSecondaryTriggers()` automatically re-invokes `handleTrigger()` for each of those addresses as "secondary" triggers [2](#0-1) . This is analogous to the CrabNetting bug where independently-controlled sub-operations (market maker orders) are batched into a single all-or-nothing execution.

`revert()` rolls back *all* balance/state changes accumulated by the primary trigger and every secondary AA invoked so far in the chain — not just the one that bounced — and then bounces the primary trigger entirely. Since anyone can permissionlessly define an AA (an "AA author" is an unprivileged actor per the analysis scope), an attacker can deploy a malicious AA that always bounces (e.g., an AA with an `if` condition or state formula guaranteed to fail, or that intentionally exceeds `MAX_RESPONSES_PER_PRIMARY_TRIGGER` or triggers a “balance overflow”/“max_aa_responses exceeded” condition). If a legitimate/victim primary AA — as part of its normal, otherwise-successful logic — sends any payment output to this malicious address (e.g., paying multiple recipients including one adversary-controlled AA address among many), the entire calling chain’s work is discarded, and *all* of the primary AA's intended payments (to the malicious address's uninvolved co-recipients) are wiped out and replaced with a bounce.

### Impact Explanation
This constitutes AA fund freezing/denial-of-execution: a single malicious or intentionally-failing secondary AA can force complete reversal of a batch of otherwise valid, unrelated payments/state changes made by a primary AA, and the bounce fee is consumed instead of the intended payouts reaching their destinations. Any protocol built on top of AAs that fans out payments to multiple AA addresses in one response (e.g., DEX/auction/distribution AAs) is exposed to griefing by any third party who can get themselves (or induce another actor) included as one of the payment recipients, matching the "repeated griefing causing legitimate batch operations to fail" impact described in the source report.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a victim AA design that pays out to multiple addresses (some of which may not be pre-vetted, e.g., addresses supplied via trigger data or state), and (2) an attacker being able to insert/become one of those payout addresses as an AA that predictably bounces. This is a known and partially-intentional design characteristic of Obyte's atomic AA execution model (similar to the Sherlock report's acknowledgment that "market makers/auction participants don't grief" in practice), so it is primarily exploitable in application-level AAs that pay third-party-supplied addresses without checking that they aren't AAs (`checkNotAAs` exists for this purpose in some payment paths but is not universally applied) [5](#0-4) .

### Recommendation
- For protocols (and potentially base AA semantics) that fan out payments to a list of externally-influenced addresses, use `checkNotAAs`-style filtering, or make secondary AA calls independent/isolated (e.g., catch a bounce from one secondary AA without reverting the balance changes already committed for the primary trigger and other secondary AAs), similar to the fix recommended in the report: skip failing sub-operations instead of reverting the whole batch.
- At minimum, document this atomicity clearly for AA authors so that AAs performing multi-recipient payouts either avoid paying to addresses that could be AAs, or use `checkNotAAs`/definition checks before including an address in the payout list.

### Proof of Concept
1. Attacker defines a malicious secondary AA `M` whose logic deterministically causes a bounce (e.g., it always evaluates a state formula that fails, per `bounce()` semantics in [6](#0-5) ).
2. A victim primary AA `V` — as normal, legitimate behavior — sends a multi-output payment message in its response, including an output to `M`'s address (e.g., paying multiple market participants, one of which happens to be `M`, whether accidentally or via attacker-supplied address input).
3. `handleSecondaryTriggers()` automatically invokes `M`'s trigger as a secondary AA [2](#0-1) .
4. `M` bounces, causing the `async.eachSeries` final callback to call `revert()` for the whole chain [3](#0-2) .
5. All balance changes and outputs from `V`'s response (including payments to legitimate, uninvolved recipients) are rolled back via `ROLLBACK TO SAVEPOINT initial_balances`, and `V`'s trigger bounces instead of completing successfully — demonstrating that a single unprivileged attacker-controlled AA can force reversal/freezing of an otherwise-valid batch of AA payments.
