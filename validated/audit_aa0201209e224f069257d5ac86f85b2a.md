### Title
AA trigger identity collapses multi-authored units to a single address, enabling bypass of per-address restrictions and misdirected refunds - ([File: aa_composer.js])

### Summary
`aa_composer.getTrigger()` derives the entire identity of an AA trigger — `trigger.address` — from a single element of an array that can legitimately contain multiple, independent entries: `objUnit.authors[0].address`. [1](#0-0) 
This mirrors the reported SponsorPaymaster flaw exactly: a protocol object designed to hold *several* addresses (Kinto's `dest[]` array / ocore's `authors[]` array) is collapsed to "the first one" for a security-relevant decision, even though ocore units can be multi-authored and `authors` is not sorted by contribution or intent — it is sorted purely by address value (ascending) as enforced by unit validation, e.g. in `signed_message.js`: `if (author.address <= prev_address) return handleResult("author addresses not sorted");` [2](#0-1) 

### Finding Description
Autonomous Agents (AAs) receive a `trigger` object built once per triggering unit by `getTrigger(objUnit, receiving_address)`:
```
var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
``` [3](#0-2) 

`trigger.address` is subsequently exposed to oscript/AA definitions via the formula-evaluation engine (`case 'trigger.address': cb(trigger.address);`) and is the standard mechanism AA authors use to identify "who sent this trigger" for authorization checks, refunds, and per-address bookkeeping. [4](#0-3) 

Real-world AA templates in this codebase rely on `trigger.address` being *the* unique, trustworthy identity of the caller for privileged branches, e.g. `trigger.data.finish AND (trigger.address == $control_address OR timestamp > $expiry_ts)` and milestone-release gated by `trigger.address == $auditor_address`. [5](#0-4) 

However, ocore units are explicitly allowed to have **multiple, independent authors** (funded by different addresses in the same joint), up to `MAX_AUTHORS_PER_UNIT`, and validation code throughout the payment/input logic (`validatePaymentInputsAndOutputs`, `writer.js`) treats `arrAuthorAddresses` as a genuine array of potentially-many distinct payer identities:
```
if (arrAuthorAddresses.length === 1){ ... }
else{
    if (typeof input.address !== "string")
        return cb("when multi-authored, must put address in issue input");
    ...
}
``` [6](#0-5) 

Despite this, `getTrigger()` never inspects more than `authors[0]` — the other author(s) of a multi-authored trigger unit are completely invisible to the AA's oscript logic. Because `authors[]` in a unit is required to be sorted ascending by address (not by "who is the primary caller"), whichever address happens to sort first lexicographically becomes `trigger.address`, regardless of actual roles or fund contribution. [2](#0-1) 

This is structurally identical to the reported bug class: a caller can construct a message that legitimately carries several addresses (multiple co-authors, each independently signing/funding the unit), but the downstream consumer (SponsorPaymaster / `getTrigger`) picks only the first element as "the" address relevant to a security decision, silently discarding the rest.

### Impact Explanation
Any AA design pattern that uses `trigger.address` for per-address rate limiting, anti-spam/anti-Sybil bookkeeping, or "one action per address" accounting can be defeated by an attacker who is willing to add a throwaway self-owned second author to their trigger unit. Since `authors[]` is sorted purely by address string value, the attacker can pre-generate an address that sorts before their "real" address (trivial and free — address generation costs nothing), include it as a second author/co-signer of the trigger unit (funding it with a negligible/zero-relevant amount as required by multi-author input rules), and thereby force `trigger.address` in the AA evaluation to be a fresh, unique address on every single trigger — even though the actual acting party and funding source is the same person. Any AA that keys state (`var[trigger.address]`) or gating logic off `trigger.address` for the purpose of restricting repeated interactions per real-world actor (faucets, giveaways, per-user allowances, KYC/attestation-linked control addresses, etc.) can have that restriction bypassed, leading to AA fund drain/loss beyond the intended per-address caps. Conversely, legitimate multi-author cooperative triggers (e.g., dual-signed transactions meant to represent joint authorization by two specific control addresses) cannot be correctly represented at all — the AA can only "see" one of the two co-signers, silently dropping the other's identity from all authorization decisions.

### Likelihood Explanation
The exploit path requires only: (1) knowledge that multi-authored units are permitted by the protocol (documented, widely used feature — shared addresses/multi-sig, joint payments), and (2) the ability to generate arbitrary new addresses and co-sign a unit with them, both of which are trivially available to any unprivileged wallet user posting an AA trigger. No cooperation from third parties or special privileges are required for the "self-sybil per trigger" bypass scenario. The likelihood of an AA actually depending on `trigger.address` for per-address uniqueness/restriction is high, since this is the only per-caller identity primitive exposed by the language (`trigger.address`, `trigger.initial_address`), and the official oscript samples in this repo demonstrate exactly this trust pattern (`trigger.address == $control_address`, `== $auditor_address`).

### Recommendation
Either (a) disallow multi-authored units from being valid primary/secondary AA triggers (reject in `validateAATriggerObject`/`validateAATrigger` if `objUnit.authors.length > 1`), forcing a 1:1 mapping between "unit" and "trigger address," or (b) rework `getTrigger()` and the oscript surface (`trigger.address`) to expose the full list of authors (e.g., `trigger.addresses` array) so AA authors can make an explicit, informed decision about how to treat multi-authored triggers instead of silently defaulting to `authors[0]`. At minimum, document clearly that `trigger.address` is not a reliable unique-caller identity when multiple authors are permitted, and audit existing AA templates (like the ICO/milestone samples in this repo) that assume otherwise.

### Proof of Concept
1. Attacker generates a throwaway keypair/address `Z` such that `Z < <attacker's real address A>` lexicographically (cheap, brute-forceable in seconds).
2. Attacker composes a payment unit funding an AA, listing authors `[Z, A]` (sorted ascending as required), with `A` providing the actual payment/output funds relevant to the AA's per-address bookkeeping, and `Z` co-signing with a trivial/zero-effect input (or another minor contribution satisfying multi-author input rules in `validation.js`).
3. `getTrigger()` sets `trigger.address = Z` (the first/lexicographically-smallest author) rather than `A`. [3](#0-2) 
4. Any AA logic keyed on `trigger.address` (e.g., `var[trigger.address]`-based per-user limits, or `if (trigger.address == $control_address)`-style gating) evaluates against the throwaway `Z`, not the attacker's persistent identity `A` — allowing repeated triggering under a fresh identity each time (bypassing per-address limits) or causing legitimate multi-party authorization checks to silently fail/misfire depending on address sort order.
