### Title
`reward_per_token()` integer-division truncation permanently forfeits staker rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards`'s `reward_per_token()` computes the reward accrued per staked token using a fixed, small `PRECISION_SCALING_FACTOR` (4096) instead of a high-precision fixed-point/rational type. When `reward_rate_per_block * rewardable_blocks_elapsed * 4096` is smaller than `total_tokens_staked`, integer division truncates the increment to zero, yet `update_pool_rewards()` unconditionally advances `last_update_block` to the current block. This is analogous to the Surge Protocol `getCurrentState()` bug: the "time window" for which zero reward was calculated is discarded forever, because the next call recomputes `rewardable_blocks_elapsed` starting from the just-advanced `last_update_block`.

### Finding Description
`reward_per_token()`:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [1](#0-0) 

`PRECISION_SCALING_FACTOR` is only `4096` (a `u16`), far smaller than the 1e18 scale typically used for such accumulators: [2](#0-1) 

`update_pool_rewards()` unconditionally sets `last_update_block = current_block_number()` and stores whatever `reward_per_token` was computed — including zero-increment results — with no guard comparable to the recommended "don't update last accrual time when interest is 0":
```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
``` [3](#0-2) 

Every user-facing extrinsic (`stake`, `unstake`, `harvest_rewards`) triggers this update path via `update_pool_and_staker_rewards` -> `reward_per_token` -> `update_pool_rewards`, and these are ordinary signed extrinsics callable by any staker with no privileged role required: [4](#0-3) [5](#0-4) [6](#0-5) 

If reward-token or staked-token decimals are large (18 decimals is common for `pallet-assets`/fungible tokens), and a modest `reward_rate_per_block` is chosen relative to `total_tokens_staked`, the numerator `reward_rate_per_block * rewardable_blocks_elapsed * 4096` can be smaller than `total_tokens_staked`, so `ensure_div` yields `0` (division truncation, not an error — `ensure_div` only errors on div-by-zero, not on truncation to zero). Any staker (or third party via `harvest_rewards`/`unstake` after expiry) can trigger `update_pool_rewards` every block, keeping `rewardable_blocks_elapsed` pinned at `1` and the increment pinned at `0` indefinitely, permanently forfeiting reward accrual for that pool despite reward tokens sitting in (and admin continuing to fund) the pool account.

This differs from the Surge report only in the specific arithmetic constants; the violated invariant is identical: a scale-factor too small for the token's actual decimal range causes legitimate accrual to silently round to zero, and the code advances the "last accrual" checkpoint anyway, making the loss unrecoverable rather than merely deferred.

### Impact Explanation
Stakers who deposit real value (LP/staked tokens) into a pool with a sufficiently small `reward_rate_per_block` relative to `total_tokens_staked` and normal (e.g., 18-decimal) token precision receive zero rewards forever, even though the pool admin funds the reward account and intends for rewards to accrue. This is a fund-loss / broken-accounting issue (rewards effectively stranded/undistributable), matching the "Medium" class of the original Sherlock report (interest/reward silently zeroed due to decimal/precision mismatch). It does not enable outright fund theft or unauthorized dispatch, so it falls short of Critical/High severity used for unbacked issuance or unauthorized transfers.

### Likelihood Explanation
Reachable by any signed account with no privileged role: `stake`/`unstake`/`harvest_rewards` are ordinary user extrinsics, and `harvest_rewards`/`unstake` can even be called by third parties once a pool has expired. The trigger condition (small `PRECISION_SCALING_FACTOR`=4096 relative to typical 18-decimal token supplies and modest reward rates) is plausible for realistic pool parameterizations chosen by a pool admin — it is not attacker-privileged, but it depends on pool configuration (reward rate vs. staked supply magnitude), so likelihood is configuration-dependent rather than universal.

### Recommendation
- Increase `PRECISION_SCALING_FACTOR` to a much larger constant (e.g., 1e18-scale, consistent with `FixedU128`/`Perquintill`-style precision used elsewhere in the codebase such as `nomination-pools`' `RewardCounter` (`T::RewardCounter::checked_from_rational`), rather than a raw `u16` multiplier.
- Alternatively/complementarily, avoid updating `last_update_block` (i.e., avoid discarding `rewardable_blocks_elapsed`) when the computed reward increment truncates to zero, so unaccounted blocks are carried forward to a future computation instead of being permanently lost — mirroring the report's own recommendation of not updating `lastAccrueInterestTime` when computed interest is zero.
- Use a checked-rational/fixed-point type (as done in `pallet-nomination-pools`'s `current_reward_counter`) instead of raw integer multiply-then-divide to bound worst-case precision loss.

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
