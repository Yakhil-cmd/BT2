### Title
Global 15-significant-digit arithmetic precision in oscript formulas can silently truncate large intermediate products, allowing rounding-driven fund extraction from AAs - (File: formula/common.js, formula/evaluation.js)

### Summary
Oscript's arithmetic engine, used by every Autonomous Agent (AA) to compute payment amounts, is globally configured to only 15 significant digits of precision via `decimal.js`, applied uniformly to every operation regardless of the magnitude of the operands. Because asset amounts and balances can legitimately reach up to `MAX_CAP`/`TOTAL_WHITEBYTES` scale (~9×10^15), any formula that multiplies two large balances together (a pattern explicitly used in AMM/bonding-curve AA templates shipped with the codebase) produces an intermediate result whose exact integer value requires far more than 15 significant digits, so the true value is silently rounded/truncated before the final `round()`/`floor()` division is applied.

### Finding Description
The Decimal engine used for all oscript formula evaluation is configured once, globally, with a fixed precision: [1](#0-0) 

This precision setting is applied indiscriminately to every arithmetic operator (`+ - * / % ^`) evaluated for any AA formula, with no relation to the actual scale of the token amounts being computed: [2](#0-1) [3](#0-2) 

An unprivileged trigger sender who posts a payment message to any deployed AA using a bonding-curve / constant-product style formula (a documented, shipped pattern) can hit this: the AA computes `$p = $asset_balance * $bytes_balance` and then `round($p / balance[...])` to decide payout, exactly as in the shipped sample: [4](#0-3) [5](#0-4) 

When `$asset_balance` and `$bytes_balance` are both large (approaching realistic on-chain balances of ~10^9–10^15 raw units, which is normal since 1 GByte = 10^9 bytes and assets can have caps up to `constants.MAX_CAP`), their product can reach ~10^18–10^30, i.e. it needs 19–31 significant digits to be represented exactly. The fixed 15-digit precision (`Decimal.set({ precision: 15, ... })`) then forces a rounding of the product itself, before the subsequent division/`round()` step ever runs. This is structurally the same bug class as the reported "PRECISION should be 1e6 not 1e3" issue: a single, coarse, fixed precision constant is used uniformly for quantities that legitimately span many orders of magnitude, so the smaller/finer-grained side of the calculation loses correctness.

Unlike the Solidity report (where PRECISION governs decimal scaling explicitly), here the precision constant governs the number of significant digits retained by every Decimal operation in the interpreter that every AA's payout formula relies on – so the "AURA suffers precision loss" analog becomes "any AA computing a payout as a function of two large balances multiplied together suffers precision loss," with attacker-controllable inputs (trigger outputs) directly influencing which side of the rounding the error falls on.

### Impact Explanation
Because the truncation happens on an intermediate value that directly feeds the payout `amount` for a `payment` message, an attacker can craft trigger amounts that push the multiplication result just past a precision boundary, causing the computed `round()`/`floor()` result to be rounded in the attacker's favor. Repeated triggers exploiting this bias let an attacker extract more of the pooled asset/bytes from the AA's balance than they contributed, directly draining AA-held funds — a concrete fund-loss scenario reachable from a single unprivileged trigger sender, matching the "AA fund loss" impact category.

### Likelihood Explanation
Any AA using multiplication of two balances/amounts before division (a pattern explicitly documented and shipped as `uniswap_like_market_maker.oscript`) is affected, and no special privilege is needed — an ordinary user simply sends payment triggers with amounts chosen to land near a rounding boundary. The precision configuration is global and cannot be adjusted per-AA, so any AA author relying on default oscript arithmetic for such formulas is exposed without being aware of it, making this both easily reachable and repeatable.

### Recommendation
Increase (or make configurable per computation) the `decimal.js` precision used by the oscript evaluator so it comfortably covers the full range of products of two `MAX_CAP`-scale integers (i.e., at least ~32 significant digits, ideally higher with headroom), or restructure formula evaluation for multiplicative payout calculations to preserve full integer precision (e.g., using arbitrary-precision integer arithmetic for products of on-chain balances/amounts before any final scaling/rounding step) rather than relying on a fixed low-digit floating precision shared by all magnitudes of value.

### Proof of Concept
Not directly executable without a deployed AA instance and unit posting infrastructure, but the exploitable path is:
1. Deploy (or use an existing) AA implementing the shipped constant-product formula pattern: [4](#0-3) 
2. Grow `$asset_balance` and `$bytes_balance` (via normal deposits) until their product exceeds ~10^15 (comfortably reachable given `MAX_CAP`-scale balances), pushing the Decimal computation of `$p = $asset_balance * $bytes_balance` past the 15-significant-digit precision boundary configured in: [6](#0-5) 
3. Post a trigger `payment` with an `amount` chosen so that `round($p / balance[...])` rounds down/up in the attacker's favor due to the lost low-order digits of `$p`, extracting slightly more of the pooled asset than deposited.
4. Repeat across many triggers to accumulate a meaningful drain of AA-held funds.
