### Title
Webhook signature verification is bound to the wrong field — `repository.owner.login` selects the verifying app while `repository.full_name` selects the mutated stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to verify the incoming signature against using `repository.owner.login` from the *unverified* JSON body, and `GitHubApp#verify_webhook_signature` trivially returns `true` when that particular organization has no `webhook_secret` configured. The actual state-mutating operation (which `Stack` gets synced/updated) is later selected by handlers using other unverified payload fields (e.g. `repository.full_name`, `ref`, `after`), which are never required to match the organization that was actually verified. This breaks the equality `{organization authenticated by verify_signature} == {repository whose Stack is mutated}` in exactly the same way the go-ethereum bug broke `{bytes covered by the key computation} == {bytes actually used at the preimage level}`: one field is checked, a different, unbound field is acted upon.

### Finding Description
`verify_signature` derives `repository_owner` directly from the raw, unauthenticated request body before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

That value is used only to select which `GitHubApp` instance (and its `webhook_secret`) to check the signature against: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured — a state explicitly documented and shown as the default in every multi-org configuration example (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) [6](#0-5) 

Once `verify_signature` passes (either because it matched a secret for the claimed org, or trivially because that org has no secret), `create` dispatches the entire event body — unfiltered by `repository_owner` — to per-event handlers: [7](#0-6) 

The `push` handler, for example, only validates `ref` and `after`, and resolves target `Stack`s via `stacks` (inherited from the base `Handler`, not shown to take `repository.owner.login` into account) and syncs them via `GithubSyncJob`: [8](#0-7) [9](#0-8) 

In a multi-organization installation (explicitly supported per `docs/setup.md:181-209`), the field checked for authentication (`repository.owner.login`) and the field/entity actually acted upon (the `Stack`, resolved independently of that owner check) are not bound together. An attacker who knows (or guesses) that *any one* configured organization in the install has no `webhook_secret` set can craft a webhook payload where `repository.owner.login` names that unsecured organization (satisfying `verify_signature` trivially) while the rest of the payload (ref/sha/full_name used by the handler) targets a `Stack` belonging to a different, properly-secured organization. This is the same class of defect as the referenced go-ethereum bug: a boundary check is performed on one representation of the identity while the actual operation is keyed off a different, unguarded representation, letting the two diverge.

### Impact Explanation
This allows an unauthenticated attacker to inject a spoofed `push` event that queues `GithubSyncJob` for a `Stack` outside the organization whose (lack of) secret was used to pass verification, causing the sync job to fetch commits and append them to that stack's history, or to spoof `status`/`check_suite`/`membership` events that mutate `Status`, `CheckRun`, `Team`, and `Membership` records tied to stacks/teams outside the "verified" organization. Depending on downstream deploy conditions (auto-deploy triggers, merge queues gated on statuses), this can lead to an unauthorized deploy being triggered on a stack the attacker has no legitimate relationship to — satisfying the "unauthorized deploy" bar for High/Critical impact.

### Likelihood Explanation
Exploitability depends entirely on at least one organization in a multi-org Shipit install having no `webhook_secret` configured — a state the project's own setup documentation shows as the default/example value (`webhook_secret: # nil`) for each org entry, making it a plausible real-world configuration rather than a contrived edge case. No session, API token, or GitHub write access is required — only knowledge (or successful guessing) of one org name without a secret in a shared install.

### Recommendation
Bind the verified identity to the entity being mutated: after selecting the `GitHubApp` via `repository_owner`, require that every handler's target `Stack`/`Repository` actually belongs to that same verified organization (e.g., compare `repository.full_name`'s owner segment against the already-verified `repository_owner`, or resolve the `Stack` by `(owner, repo)` pair matching the value used to select the signing secret) and reject the event otherwise. Additionally, consider requiring `webhook_secret` to be present for all configured organizations, or refusing verification (422) rather than allowing a bypass when it is absent.

### Proof of Concept
1. Deploy Shipit with two GitHub Apps configured per `docs/setup.md`'s multi-org example: `org-unsecured` (no `webhook_secret`) and `org-secured` (with `webhook_secret` set), each with at least one `Stack` tracked.
2. Send `POST /github_authentication`-mounted webhook endpoint (`WebhooksController#create`) with header `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-unsecured" },
    "full_name": "org-secured/victim-repo"
  }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `verify_signature` resolves `Shipit.github(organization: "org-unsecured")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the signature header.
4. `create` dispatches to `PushHandler`, which resolves stacks matching `branch: "master"` independent of `org-unsecured`, potentially matching the `org-secured/victim-repo` stack, and enqueues `GithubSyncJob` for it — mutating state in an organization whose secret was never checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
