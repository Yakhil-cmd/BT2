### Title
Custom asset with `spender_attested`/`transfer_condition` restrictions can permanently freeze user funds held by an AA when the recipient loses eligibility - ([File: aa_composer.js], [File: validation.js])

### Summary
Obyte custom assets can define `spender_attested` (attestor allow-list) or `transfer_condition` restrictions that behave like an ERC20 blacklist/whitelist: an output can only be spent to an address that satisfies these conditions at validation time. An AA (Autonomous Agent) that holds and later needs to return such an asset to a specific user (e.g., a vault/lending-style AA returning "collateral" or deposit shares) has no way to redirect the payment to a different address if that check fails — the entire response unit fails validation and the whole trigger bounces, leaving the asset stuck inside the AA. This mirrors the `Pool.removeCollateral()` issue where a blacklisted recipient causes an unconditional revert with no recovery path.

### Finding Description
When an AA sends a payment message for a custom asset, `aa_composer.js`'s `sendUnit()` builds the response unit and hands it to `validateAndSaveUnit()`, which runs full `validation.validate()`: [1](#0-0) 

Inside standard payment validation, for divisible/indivisible assets, `validatePaymentInputsAndOutputs()` enforces two recipient-side conditions that can permanently deny a specific output address:

- `spender_attested`: every output address must be attested by one of the asset's attestors, checked via `storage.filterAttestedAddresses()`. If any output address is not attested, the whole payment (and thus the whole unit) is rejected with `"some output addresses are not attested"`.
- `transfer_condition`: an arbitrary boolean expression (`Definition.evaluateAssetCondition`) that must evaluate true for the payment; if not, `"transfer or issue condition not satisfied"`. [2](#0-1) 

The attestor filtering itself is a simple SQL membership check against the `attestations` table, so an attestor (which can be the asset definer or any address the definer trusts) can freely stop attesting a given address at any time, instantly making that address's outputs unspendable for that asset: [3](#0-2) 

When `validateAndSaveUnit()`'s `ifUnitError` fires with this validation error, it propagates back through the `sendUnit()` callback chain and triggers `bounce(err)`: [4](#0-3) 

`bounce()` discards the AA's intended response messages and state changes entirely (via `revert()`, which rolls back to the savepoint and clears state vars), refunding only the trigger's bytes minus bounce fees — the custom asset that was supposed to be paid out to the user is never sent and remains trapped in the AA's balance: [5](#0-4) 

Critically, there is no oscript-level getter that lets an AA author check `spender_attested`/attestation status or evaluate `transfer_condition` for a specific address before attempting the payment, so the AA logic cannot branch to an alternate recipient or defer/queue the payout — the failure is unconditional and unrecoverable from within the AA's own logic, exactly like `Pool.removeCollateral()`'s unconditional `safeTransfer` to `msg.sender` with no alternate `recipient` parameter.

### Impact Explanation
Any AA that custodies a `spender_attested` or `transfer_condition`-restricted asset on behalf of users (e.g., a vault, lending pool, staking/collateral contract, or wrapped-asset bridge built as an AA) can have specific users' withdrawable balances permanently frozen the moment an attestor (which could be the asset issuer, or even the AA's own definer in some designs) revokes that user's attestation or the transfer condition is engineered to exclude them. Every subsequent attempt by the AA to pay that asset to the now-ineligible address bounces the entire trigger, so:
- The user cannot ever retrieve their share of the asset from the AA (permanent freezing of AA-held funds).
- Depending on AA logic, this can also block unrelated state transitions bundled in the same response (e.g., debt/interest accounting, liquidation bookkeeping), amplifying the freeze to the whole contract's operation for that user.

This matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
This requires an asset with `spender_attested: true` or a nontrivial `transfer_condition` to be used as the AA's payout asset, and an entity controlling the attestor list (or the condition's underlying data feed/address) to deny/blacklist a specific user. This is a realistic and even intended use case for compliance-oriented tokens on Obyte (analogous to USDC/USDT blacklists), and the AA composer code offers no defensive path (no partial success, no alternate-recipient fallback, no pre-check getter) — so once the condition changes, the freeze is deterministic and permanent for that recipient, not merely probabilistic.

### Recommendation
- Provide AA authors with a way to react gracefully to such payment failures instead of unconditionally bouncing the whole trigger — e.g., a getter to check `is_attested(asset, address)` / evaluate transfer conditions from within oscript before composing the payment, so the AA can hold the funds in an internal, address-keyed state variable and let the user (or any address) later claim/redirect to an eligible address instead of attempting to force-send.
- Alternatively, document this risk prominently for AA authors that plan to use `spender_attested`/`transfer_condition` assets as payout mechanisms, recommending a pull-based withdrawal pattern (user calls a separate "claim" trigger providing an eligible destination address) rather than push-based automatic payments so that a revoked/blacklisted primary address does not brick the whole payout logic.
- Consider not bouncing the entire response purely because one payment message among several fails an asset-specific condition, if the AA logic can be restructured to isolate failures per-message (would require deeper protocol changes and careful review of atomicity guarantees).

### Proof of Concept
1. Definer issues asset `X` with `spender_attested: true` and attestor list `[Attestor]` (or a `transfer_condition` referencing a mutable state, e.g. a data feed the attestor controls).
2. An AA (e.g., "VaultAA") accepts deposits of asset `X` from users and tracks each depositor's balance in a state variable; on a "withdraw" trigger it composes `{app: 'payment', payload: {asset: 'X', outputs: [{address: trigger.address, amount: userBalance}]}}`.
3. `Attestor` (which could be the asset definer, or colludes with them) stops attesting `trigger.address` (removes/never grants attestation for that address), or the `transfer_condition` referencing state controlled by a counterparty evaluates to false for that address.
4. User sends a withdraw trigger to VaultAA. `aa_composer.js`'s `sendUnit()` composes the payment and calls `validateAndSaveUnit()`; `validatePaymentInputsAndOutputs()` in `validation.js` rejects the unit with `"some output addresses are not attested"` (or `"transfer or issue condition not satisfied"`).
5. `bounce()`/`revert()` fires: all VaultAA state changes for this trigger are rolled back, no asset is sent to the user, and the user's `X` balance remains locked inside VaultAA indefinitely — with no alternate code path in VaultAA (or in ocore's AA composer) to redirect the payout to a different address.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
