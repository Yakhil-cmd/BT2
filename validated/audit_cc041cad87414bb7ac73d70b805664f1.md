### Title
Webhook signature is verified against `repository.owner.login`, but the target Stack is resolved from the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on one JSON field (`repository.owner.login` / `organization.login`), while the handlers that actually mutate data (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`) resolve the target `Stack`/`Repository` using a completely different field (`repository.full_name`) that is never cross-checked against the field used for authentication. This is the same class of bug as the reported issue: a credential/authority ("the organization whose secret validated the signature") is checked once at one point, but a different, unguarded value ("the repository actually written to") is trusted for the effectful operation, breaking the intended binding `authenticated_org == written_repository_org`.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used to validate `X-Hub-Signature`) using: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). In a multi-organization Shipit deployment, each organization has its own `webhook_secret` (see `Shipit.github_app_config`, `test/dummy/config/secrets_double_github_app.yml`), so this method effectively decides *whose* secret is used to validate the signature.

Once the signature check passes, `create` dispatches the raw JSON body to handlers: [3](#0-2) 

Every handler inherits stack/repository resolution from `Handler`, which uses a **different** field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler#process` and `CheckSuiteHandler#process` then act on whatever `Stack`s that lookup returns: [5](#0-4) [6](#0-5) 

Nothing in `verify_signature`, `Handler`, or any of the handlers verifies that the owner segment of `repository.full_name` matches `repository.owner.login`/`organization.login` used for authentication. An attacker who legitimately controls (or has learned) the `webhook_secret` for one configured organization (`OrgA`) can therefore forge a JSON body where:
- `repository.owner.login` = `"OrgA"` / `organization.login` = `"OrgA"` (used only to pick the secret to verify against — attacker signs the body with `OrgA`'s real secret), while
- `repository.full_name` = `"OrgB/some-repo"` (used to resolve which `Stack` actually gets acted upon).

The HMAC check succeeds because the attacker knows `OrgA`'s secret and can sign an arbitrary raw body, and the handler happily operates on `OrgB`'s `Stack` because it never re-derives or validates the organization from the same field that was authenticated.

### Impact Explanation
This breaks the equality `organization_that_authenticated == organization_whose_repository_is_written`, matching the required analog class directly. Concretely, an operator with only `OrgA`'s webhook secret can:
- Trigger `PushHandler` → `stack.sync_github(expected_head_sha: ...)` on any `OrgB` stack, forcing an out-of-band GitHub sync/commit-fetch cycle on a repository they have no legitimate relationship to.
- Trigger `CheckSuiteHandler` → `schedule_refresh_check_runs!` on `OrgB` commits.
- Trigger `StatusHandler` → `commit.create_status_from_github!` writes on `OrgB`'s commits (matched purely by `sha`, with no organization scoping at all).

This is a cross-organization write into another tenant's `Stack`/`Commit` records driven entirely by attacker-supplied JSON, satisfying the "cross-repository writes" Critical-impact bucket, and it only requires knowledge of one organization's own configured `webhook_secret` — not any Shipit session, `ApiClient` token, GitHub App private key, or `api_clients_secret`.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (`Shipit.github_organizations` with more than one entry, a documented and supported configuration — see `docs/setup.md` "Using Multiple Github Applications"), and (2) the attacker knowing/controlling the `webhook_secret` of at least one configured organization, which is a routine, unprivileged capability for anyone who administers that organization's GitHub App/webhook settings. No GitHub App private key, Shipit session, or API token for the *target* organization is needed. Given multi-tenant Shipit setups are an intended and documented feature, this is a realistic likelihood whenever more than one organization is configured.

### Recommendation
In `Shipit::WebhooksController#verify_signature`/`Handler`, derive the organization used to locate the target `Stack`/`Repository` from the same authenticated value (`repository_owner`) that was used to select the signing secret, and reject the payload if the owner segment of `repository.full_name` (or the resolved `Repository#owner`) does not match `repository_owner`. Alternatively, have `Handler#repository_name`/`stacks` be scoped by the already-verified organization rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows `OrgA`'s `webhook_secret` (e.g., an `OrgA` admin), craft a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`) and the signature validates successfully.
5. `PushHandler` resolves `repository_name` as `"OrgB/target-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stacks — an action performed on `OrgB`'s data using only `OrgA`'s credential.
