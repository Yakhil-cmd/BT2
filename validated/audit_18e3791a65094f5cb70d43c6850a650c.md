### Title
Cross-stack status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit(s) to update purely by SHA, with no repository/stack scoping, and applies the incoming GitHub `status` payload to every matching `Commit` record found. Because the `commits` table's uniqueness constraint on `sha` is scoped `(sha, stack_id)` rather than globally unique, the same SHA can legitimately exist as separate `Commit` rows belonging to different stacks (e.g., an attacker's own fork/stack and a victim's stack sharing history), letting an attacker's own authenticated webhook (for their own repo) forge a `ci/circleci` `failure` status onto a victim stack's commit, which can flip deployability and, if `merge_queue_enabled` is true, affect the merge queue's `merge!`/reject decision.

### Finding Description
The broken binding: the code should enforce `commit.stack.repository == payload.repository` (i.e., only commits belonging to the stack that authenticated the webhook for its own repository should be updated), but the actual binding enforced is only `commit.sha == params.sha`, with no repository check at all: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This has no filter on `repository`, `stack`, or any authentication-bound identifier — it iterates over *every* `Commit` row across *every* stack in the installation whose `sha` matches the attacker-supplied string.

The uniqueness constraint backing the `commits` table confirms rows are not globally unique by SHA — they are unique per `(sha, stack_id)`: [2](#0-1) 

So the same SHA value can exist as distinct `Commit` records tied to different `stack_id`s/repositories (e.g., a shared history point between a fork and upstream, or any accidental/engineered SHA collision across two independently configured stacks). Because webhook signature verification is performed per-repository against the repository that is presumably targeted, but `StatusHandler#process` never consults `params.repository` (the handler's `params` schema doesn't even require/use it — only `sha`, `state`, `context`, etc.), the write fans out to any stack holding a `Commit` with that SHA, regardless of which repository's secret validated the payload.

Once `create_status_from_github!` runs on the victim's commit, `Commit#add_status` recomputes `status` from `statuses_and_check_runs` and, on a state transition, calls `stack.schedule_merges` when the new status is `pending` or `success`: [3](#0-2) 

For a `merge_queue_enabled: true` stack, `MergeRequest#any_status_checks_failed?`/`reject_unless_mergeable!` reads the head commit's `statuses_and_check_runs` through `StatusChecker`, so a forged `failure` for the required `ci/circleci` context on the merge request's head commit will cause `reject!('ci_failing')` instead of proceeding to `merge!`: [4](#0-3) [5](#0-4) 

This is exactly the "block" side of the exploit idea; conversely, a forged `success`/passing state on a commit that otherwise lacks CI evidence could clear `any_status_checks_missing?`/`any_status_checks_failed?` and let `merge!` be attempted.

Why existing guards don't catch this: signature verification (`verify_signature`) validates that the payload originated from *some* GitHub repository configured with a matching secret — it does not, and cannot by itself, prevent the handler from writing to a different stack's commit once the payload is accepted. The `ExplicitParameters` schema on `StatusHandler` only requires `sha`/`state`/etc. and never binds the write to `params.repository`'s identity. No other guard (`force_github_authentication`, `User#authorized?`, `require_permission!`) applies to unauthenticated webhook processing.

Attacker's exact request: attacker owns/configures their own Shipit stack (repository they control) and pushes a commit whose SHA is shared with a victim's stack's commit (trivially achievable if the attacker's fork/stack tracks a commit that is also present, unmodified, in the victim's repository history — e.g., a commit merged upstream and also present on the fork before/after rebase, or any other shared-SHA scenario across two Stack records). Attacker then triggers (or crafts, if their own repo's secret is known to them, which it is since it's their own GitHub App/webhook config) a `status` event with `context: ci/circleci`, `state: failure`, `sha: <shared-sha>`. `StatusHandler#process` updates **all** `Commit` rows with that SHA, including the victim's, not just the attacker's own stack's commit.

### Impact Explanation
A payload legitimately authenticated for the attacker's own repository mutates a *different* stack's commit status record, which is squarely the "payload for one repository mutating another's stack/commit" category (Critical). On a `merge_queue_enabled` victim stack requiring `ci/circleci`, this can force `reject!('ci_failing')` on a pending merge request (denial/block of a legitimate merge) or, in the success-forging direction, help satisfy status requirements that clear the way for `merge!` to be attempted — i.e., unauthorized block or merge of code the attacker does not own. The blast radius spans every stack in the installation, since the lookup has no tenant boundary; it is repeatable against arbitrary stacks as long as a shared-SHA condition is achievable.

### Likelihood Explanation
Preconditions: (1) attacker needs a stack of their own (or any means to author a `status` event whose signature is validated by the Shipit instance) — this is satisfiable by any user for whom a stack/webhook exists for a repo they control; (2) a victim stack with `merge_queue_enabled: true` requiring `ci/circleci`; (3) a shared SHA between attacker's and victim's `Commit` rows. This third condition is the main constraint — it requires the same git commit SHA to be recorded under both stacks (a real-world condition e.g., for forks tracking the same upstream history, cherry-picked/rebase-preserved SHAs, or common ancestor commits recorded via PR base/head resolution in `MergeRequest#github_pull_request=`). Given that, the attack is a single unauthenticated `POST /webhooks` request with no privileged token needed, fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run handler, if it has the same pattern) to only update commits belonging to the stack(s) whose repository matches the authenticated webhook's repository — i.e., join through `Stack` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: matching_repository_id })`, deriving the repository identity from the webhook delivery context (the repo that owns the validated signature), not from attacker-controlled payload fields alone.

### Proof of Concept
minitest plan (no live GitHub):
1. Create two `Stack` fixtures, `stack_a` (attacker-controlled, arbitrary repo) and `stack_b` (victim, `merge_queue_enabled: true`, deploy spec requiring `ci/circleci`).
2. Create `Commit` `commit_a` under `stack_a` and `Commit` `commit_b` under `stack_b` with the **same** `sha` value (this is permitted because uniqueness is `(sha, stack_id)`, not global — see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`).
3. Create a `MergeRequest` on `stack_b` whose `head` is `commit_b`, in `pending` merge_status, with the deploy spec's `merge_request_required_statuses` including `ci/circleci`.
4. Assert baseline binding: `commit_b.deployable?` reflects no failing status, and `merge_request.any_status_checks_failed?` is `false`.
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(...).process` (or POST to `/webhooks` with a validly-signed payload for `stack_a`'s repository) with `sha: <shared sha>, context: 'ci/circleci', state: 'failure'`.
6. Assert `commit_b.reload.status.failure?` is `true` and `merge_request.reload.any_status_checks_failed?` is `true` (or, after invoking `reject_unless_mergeable!`, `merge_request.rejected?` is `true` with `rejection_reason == 'ci_failing'`) — proving that a payload authenticated for `stack_a` mutated `stack_b`'s commit/merge state, violating the invariant "a `ci/circleci` status affects only the repository that authenticated it."
