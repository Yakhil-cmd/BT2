### Title
Webhook org used for signature verification diverges from org written to `Team.organization` in `MembershipHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the webhook secret to verify against using `repository_owner`, which prefers `params['repository']['owner']['login']` over `params['organization']['login']`. `MembershipHandler#find_or_create_team!` instead always uses `params.organization.login` to populate `Team.organization`. Because these are two independent fields in an attacker-fully-controlled JSON body, an attacker who administers one onboarded org (and thus knows its `webhook_secret`) can make the signature verify against their own org while attributing the resulting `Team`/`Membership` rows to a completely different, victim org.

### Finding Description
The binding that must hold is: `org_used_to_select_webhook_secret == org_attributed_in_Team.organization`.

- `WebhooksController#repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`):
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) calls `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that org's `webhook_secret`.

- `MembershipHandler` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) never reads `repository.owner.login`; it exclusively uses `params.organization.login` to set `team.organization`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
The `ExplicitParameters` schema on `MembershipHandler` (`params do ... end`, lines 7-21) requires `action`, `team`, `organization`, `member`, but does not forbid extra top-level keys such as `repository` — so an attacker can freely add a `repository` object to the body purely to steer signature verification, while the handler ignores it entirely.

Exploit flow: attacker administers org A (knows its `webhook_secret`). They craft a body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "n", "slug": "n", "url": "u"},
  "organization": {"login": "victim-org-B"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "org-A"}}
}
```
`X-Github-Event: membership`, signed with org A's secret. `verify_signature` computes `repository_owner = "org-A"` (from the injected `repository` key), fetches `Shipit.github(organization: "org-A")`, and the HMAC matches — verification succeeds. `MembershipHandler#process` then runs and creates/updates `Team` with `organization = "victim-org-B"`, adding `attacker` as a member, entirely without org B ever authenticating or being involved.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type is handled; `verify_signature` only checks the HMAC against whichever org it derives from `repository_owner`; the `ExplicitParameters` schema for `MembershipHandler` validates presence/type of fields but performs no cross-field consistency check between `repository.owner.login` and `organization.login`, and does not reject unexpected keys.

### Impact Explanation
An attacker who administers only one onboarded org can create/mutate `Team` and `Membership` rows attributed to any other org name of their choosing — including a real, unrelated victim org already onboarded in Shipit. If `Shipit.github_teams` authorization or any downstream logic keys off `Team.organization`/`Team` membership (e.g., granting deploy/session privileges based on team membership under a given org), this becomes a cross-tenant privilege-escalation primitive: the attacker can insert themselves as a "member" of a team nominally belonging to org B. This matches the "escalation into `Shipit.github_teams` authorization" / cross-tenant data-mutation impact categories, and is repeatable against arbitrary target org names since `organization.login` is a free-form string with no validation against the actual verifying org.

### Likelihood Explanation
Preconditions: attacker must administer at least one org already configured in Shipit (to know a valid `webhook_secret` and be able to compute a passing `X-Hub-Signature`). No knowledge of the victim org's secret, session, or API token is required — the victim org name is simply a string in the JSON body. This is a low-cost, fully repeatable attack: a single crafted HTTP POST per exploitation attempt, no timing constraints, no race conditions.

### Recommendation
In `MembershipHandler` (and any other handler that writes an org-scoped record), use the same org value that was authenticated in `WebhooksController#verify_signature` rather than trusting `params.organization.login` independently. Concretely: pass the verified `repository_owner`/organization into the handler (e.g., as a required context value) and assert `params.organization.login == verified_organization` before writing `Team.organization`, rejecting the webhook (422) on mismatch. More generally, `WebhooksController#repository_owner` should not silently accept two different possible provenance fields (`repository.owner.login` vs `organization.login`) without cross-checking that they agree when both are present.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "membership event can attribute Team to an org that never authenticated" do
  org_a_app = stub(verify_webhook_signature: true)
  Shipit.stubs(:github).with(organization: 'org-A').returns(org_a_app)

  body = {
    action: 'added',
    team: { id: 1, name: 'Foo', slug: 'foo', url: 'http://x' },
    organization: { login: 'victim-org-B' }, # attacker-chosen, never verified
    member: { login: 'attacker' },
    repository: { owner: { login: 'org-A' } } # steers signature check to org-A
  }.to_json

  post shipit.hooks_path, params: body,
       headers: {
         'X-Github-Event' => 'membership',
         'X-Hub-Signature' => 'sha1=validForOrgA',
         'Content-Type' => 'application/json'
       }

  team = Shipit::Team.find_by(github_id: 1)
  assert_equal 'victim-org-B', team.organization
  # No assertion anywhere ties team.organization back to the org ("org-A")
  # whose secret actually verified the signature.
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
