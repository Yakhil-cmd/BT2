### Title
Author-controlled `earned_headers_commission_recipients` share manipulation distorts per-address TPS-fee accounting, allowing later units to evade the anti-spam `tps_fee` requirement - (File: `validation.js`, `storage.js`)

### Summary
The TPS-fee anti-spam mechanism accumulates a running `tps_fees_balance` per address and later "cashes it in" by dividing it by that address's *current* commission `share` to recover an equivalent full fee. Because the `share` assigned to an address is not fixed but is freely re-declared unit-by-unit through `earned_headers_commission_recipients`, an author can change the share used for the same address between units, breaking the implicit invariant that `balance` was accumulated under a constant `share`. This mirrors the reported bug class: a per-unit "share" is divided against a value (`underlying`/`tps_fees_balance`) that changes independently of the share used to build it, producing inconsistent, exploitable accounting where late transactions can be charged far less (or a victim address far more) than intended.

### Finding Description
`getTpsFeeRecipients()` computes each unit's fee recipients and their `share` from `assocEarnedHeadersCommissionRecipients`, defaulting to `{author: 100}` but allowing any split among authors that sums to 100: [1](#0-0) 

`validateHeadersCommissionRecipients()` only requires the shares to sum to 100 and be sorted/positive — it places no restriction on an author using a *different* split for the same addresses in consecutive units: [2](#0-1) 

`updateTpsFees()` accumulates a per-address, per-mci `tps_fees_balance` by splitting each unit's `total_tps_fees_delta` according to that unit's own (possibly different) `share`: [3](#0-2) 

Both `getPaidTpsFee()` (light client / wallet path) and `validateTpsFee()` (full validation path) then reconstruct an "equivalent full tps_fee" for each recipient by dividing the accumulated `tps_fees_balance` by the **current unit's** `share` for that address: [4](#0-3) [5](#0-4) 

This `balance / share` reconstruction is only correct if `share` for that address has been constant across all units that contributed to `balance`. Since `share` is attacker-chosen per unit (subject only to summing to 100 across authors), an author fully controls this divisor independently of how the balance was built up — exactly analogous to the reported bug where `depositShares = depositAmount * share / underlying` distorts the pool once `share/underlying` moves, because `share` and `underlying` are not kept in lockstep.

Concretely: an author (with a co-author) can post an early unit specifying a very small `earned_headers_commission_recipients` share (e.g. 1%) for their own address while paying a large `tps_fee`, causing a disproportionately large `tps_fees_balance` credit to build for a low-share address (per `updateTpsFees`'s `Math.floor(total_tps_fees_delta * share / 100)` logic feeding back through subsequent stabilizations). The author then posts follow-up units declaring a much larger `share` (e.g. 99%) for the same address. `tps_fees_balance / share` for that unit now divides a balance built at a very different (larger, low-share) rate by a much larger `share`, producing an artificially small "equivalent full fee," letting `validateTpsFee` accept an underpriced unit (`objUnit.tps_fee` far below what `min_tps_fee` should demand) while still passing the `tps_fees_balance + objUnit.tps_fee*share >= min_tps_fee*share` and `tps_fee < min_acceptable_tps_fee` checks: [6](#0-5) 

### Impact Explanation
The `tps_fee` mechanism is the network's anti-spam / congestion-pricing invariant introduced at `constants.v4UpgradeMci`. By manipulating the per-unit `share` split (a value entirely controlled by the posting author via `earned_headers_commission_recipients`), an attacker can distort the `balance/share` reconstruction so that a unit is accepted with an effective fee lower than what `getLocalTpsFee`/`min_acceptable_tps_fee` actually requires. This lets an attacker systematically underpay the throughput fee designed to price and limit unit flooding, degrading the network's ability to confirm units at the intended congestion price and undermining the fee-based spam protection for all other users, similar to how late depositors in the original report bore losses the accounting model failed to distribute fairly.

### Likelihood Explanation
The attacker only needs multiple authors of a single address's unit (a standard multi-authored/AA-shared-address unit) and full control over the `earned_headers_commission_recipients` field, which `composer.js` and `validateHeadersCommissionRecipients` permit to vary freely unit-to-unit as long as it sums to 100 and lists only authors. No special privileges (validators, hubs, witnesses) are required — this is reachable by any ordinary multi-author unit poster, matching the allowed "unprivileged unit poster" actor class.

### Recommendation
Track `tps_fees_balance` per `(address, share-context)` rather than per address alone, or require that an address's `earned_headers_commission_recipients` share remain stable while it holds a nonzero `tps_fees_balance`, so the `balance/share` reconstruction in `getPaidTpsFee` and `validateTpsFee` is only ever performed against the same share that generated the balance. Alternatively, do not reconstruct an "equivalent full fee" via division at all — instead track the accumulated deficit/surplus directly in fee units (independent of `share`) so a change in `share` between units cannot rescale historical contributions.

### Proof of Concept
1. Address `A` and `A2` jointly author units from a shared multi-sig address.
2. Unit U1 sets `earned_headers_commission_recipients = [{A: 1%}, {A2: 99%}]` and pays a large `tps_fee`. Per `updateTpsFees`, `A`'s `tps_fees_balance` grows by `1% * total_tps_fees_delta`, i.e. a large absolute number relative to its 1% share.
3. Unit U2 (built on top of U1) sets `earned_headers_commission_recipients = [{A: 99%}, {A2: 1%}]`.
4. In `validateTpsFee`, `share = 0.99` for `A`; `tps_fee = tps_fees_balance / 0.99 + objUnit.tps_fee` computes a deceptively small "equivalent full tps_fee" relative to the actual balance built while `A`'s share was only 1%, allowing U2 to be posted with `objUnit.tps_fee` far below `min_tps_fee`, bypassing the intended anti-spam pricing check at [7](#0-6) .

		let bHasExternalRecipients = false;

			if (!author_addresses.includes(address))
				bHasExternalRecipients = true;
		}
		if (bHasExternalRecipients) // override, non-authors won't pay for our tps fee
			recipients = { [author_addresses[0]]: 100 };
	}
	return recipients;

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
