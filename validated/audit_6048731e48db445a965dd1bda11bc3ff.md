### Title
`Team.find_or_create_by!(github_id:)` does not scope lookup by `organization`, allowing a webhook validly signed by any configured GitHub organization to add arbitrary members to another organization's team - (`app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up existing `Team` records solely by `params.team.id` (GitHub's numeric team ID), never by `params.organization.login`. Because the `organization` field is only used when *creating* a new `Team`, an attacker who controls a validly-signed webhook from *any* organization configured in Shipit can supply a `team.id` belonging to a *different* organization's already-existing team and get an arbitrary GitHub login added as a member of that team via `team.add_member(member)`.

### Finding Description
The claimed broken binding, stated as an equality: `Team.find(github_id: params.team.id).organization == params.organization.login` must hold, but nothing enforces it.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from the payload (`params.dig('repository','owner','login') || params.dig('organization','login')`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, using that organization's configured `webhook_secret`. [1](#0-0) 
- In a multi-org configuration (`docs/setup.md`, "Using Multiple Github Applications"), each organization has its own `app_id`/`webhook_secret`, and `Shipit.github_app_config(organization)` looks the secret up strictly by the `organization` key present in the payload. [2](#0-1) 
- `MembershipHandler`'s `params do ... end` block only validates shape (String/Integer presence), never that `team.id` belongs to `organization.login`. [3](#0-2) 
- `process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login ... }`. The block that assigns `organization` only executes when a **new** record is being initialized; if a `Team` with that `github_id` already exists (belonging to some other org), it is simply returned unmodified, and its `organization` is never checked against `params.organization.login`. [4](#0-3) 
- `process` then unconditionally does `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` — the attacker's own GitHub login. [5](#0-4) [6](#0-5) 

Exploit flow: attacker administers (or otherwise knows the webhook secret of) an org, `evil-corp`, that is a legitimately configured tenant in Shipit's multi-org `github:` config. They POST a `membership` event to `/webhooks` with `X-Github-Event: membership`, a signature computed with `evil-corp`'s own webhook secret, `action: 'added'`, `organization.login: 'evil-corp'`, `member.login: 'attacker'`, and `team.id` set to the numeric GitHub team ID of a team owned by a *different* organization (e.g., `shopify_developers`, `github_id: 1` per fixtures). `verify_signature` succeeds because it only checks that the signature matches `evil-corp`'s secret — it never checks that `evil-corp` actually owns `team.id`. `MembershipHandler#process` then finds the pre-existing `shopify_developers` team and adds the attacker as a member.

Existing guards do not stop this: `verify_signature`/`verify_webhook_signature` only prove the payload was signed by *some* configured organization's secret, not that that organization owns the referenced team; `ExplicitParameters` only checks shape (String/Integer), never relational integrity; there is no `Team#organization` re-check in `find_or_create_by!`'s lookup path.

### Impact Explanation
A successful call results in `Membership.create!` linking an attacker-controlled GitHub user to a `Team` belonging to a completely different organization. If that team's `handle` (`organization/slug`) is present in `Shipit.github_teams` (`Shipit.oauth_teams`, i.e. the set of teams authorized for Shipit access), the attacker gains membership in an authorization-relevant team without ever being a real member on GitHub, matching the "High - escalation into `Shipit.github_teams` authorization" category. This is repeatable against any organization's team whose numeric `github_id` the attacker can learn or guess, and is cross-tenant: an attacker's own legitimately-configured tenant can be used to escalate into a completely unrelated tenant's team.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment where the attacker controls or knows the webhook secret for at least one configured tenant organization (plausible if that org's own admins configured their own GitHub App, per `docs/setup.md`'s multi-org instructions); (2) the target team must already exist in Shipit's database (i.e., some prior legitimate membership webhook created it) with a `github_id` the attacker can learn (GitHub team IDs are not secrets but are also not trivially public for teams the attacker isn't in, so this depends on exposure via other channels, e.g., cached webhook deliveries, prior events, or enumeration). In a single-org deployment this specific cross-tenant escalation is moot since there is only one trusted organization, so the practical exploitability is confined to genuinely multi-tenant Shipit installs.

### Recommendation
Scope the team lookup by both `github_id` and `organization`: e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally raise/reject if a `Team` with that `github_id` already exists under a *different* `organization` value rather than silently reusing it.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/membership_handler_test.rb`, new):
```ruby
test "process refuses to mutate a team owned by a different organization" do
  existing_team = Shipit::Team.create!(github_id: 999, organization: 'shopify', name: 'Real Team', slug: 'real-team')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Fake', 'slug' => 'fake', 'url' => 'http://example.com' },
    'organization' => { 'login' => 'evil-corp' }, # attacker's own org, distinct from existing_team.organization
    'member' => { 'login' => 'attacker' },
  }

  handler = Shipit::Webhooks::Handlers::MembershipHandler.new(payload)

  assert_equal existing_team.organization, 'shopify'
  assert_not_equal payload['organization']['login'], existing_team.organization  # binding is broken before fix

  assert_no_difference -> { existing_team.members.count } do
    assert_raises(ArgumentError) { handler.process } # after fix: should reject, not silently add member
  end
end
```
Before the fix, `handler.process` succeeds and `existing_team.members` gains the attacker's user despite `payload['organization']['login']` ('evil-corp') never matching `existing_team.organization` ('shopify'), demonstrating the broken webhook-provenance binding.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
