### Title
Attacker-labeled PR injects `BUNDLE_GEMFILE` into the dependency-install `Command` env, enabling Bundler-driven RCE - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges every PR label (upcased, unfiltered) as an environment variable onto the stack env, and `Shipit::TaskCommands#env` merges that unfiltered `@stack.env` into the environment passed to every `Command`, including the one built by `install_dependencies` for `bundle install`. A PR labeled `bundle_gemfile` therefore causes `BUNDLE_GEMFILE=true` to reach `Command#unbundled_env` and `PTY.spawn`, letting Bundler load an attacker-supplied file named `true` from the checked-out branch as the Gemfile, executing arbitrary Ruby during dependency installation.

### Finding Description
The safety property that should hold is: `TaskCommands#install_dependencies`'s `Command#env`'s keys ⊆ `BASE_ENV ∪ Shipit.env ∪ deploy_spec.machine_env ∪ VariableDefinition names`. Instead:

- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `super.merge(pull_request.labels.each_with_object({}) { |l, h| h[l.upcase] = "true" })` — every label name becomes an env var with no allow-list.
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) does `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` — `@stack.env` (which for a `ReviewStack` includes the label-derived keys) is merged in unfiltered, and none of the later merges strip or filter `BUNDLE_GEMFILE`.
- `install_dependencies` (`lib/shipit/task_commands.rb:17-21`) builds `Command.new(command_line, env:, chdir: steps_directory)` using this same unfiltered `env`.
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, so `BUNDLE_GEMFILE` from `@env` survives into the process passed to `PTY.spawn` (`lib/shipit/command.rb:92`).

Exploit flow: an attacker opens a PR against a repository whose `deploy_spec` runs `bundle install` as a dependency step (Bundler auto-discovery, `app/models/shipit/deploy_spec/bundler_discovery.rb`), commits a file named `true` in their branch containing a malicious Gemfile (e.g. with `eval_gemfile`, a crafted `source`, or a `gemspec` pointing at attacker code), and labels the PR `bundle_gemfile` (`LabelCapturingHandler#capture_labels`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`, persists `pull_request.labels`). When the review stack's dependency-install step runs, Bundler honors `BUNDLE_GEMFILE=true` and loads the attacker's file from the working directory, executing arbitrary Ruby on the deploy host.

No existing guard filters this: there is no allow-list check on label names in `ReviewStack#env`, no key-based filtering in `TaskCommands#env`, and `Command#unbundled_env` merges `@env` verbatim over `BASE_ENV`. `EnvironmentVariables#permit` is not invoked on this path.

### Impact Explanation
This is a Critical finding: arbitrary Ruby code execution on the deploy host (RCE) via `PTY.spawn`, triggered during the dependency-installation phase of a review-stack build. Because review stacks are created for attacker-controlled forks/branches per the review-stack workflow, this is repeatable against any repository that uses review stacks with Bundler dependency discovery — the attacker fully controls both the malicious file content and the label, with no need for elevated permissions beyond opening/labeling their own PR.

### Likelihood Explanation
Preconditions: (1) the target repository has review stacks enabled and its `deploy_spec` results in a Bundler `dependencies_steps` (auto-discovered via `Gemfile`/`gemspec` presence, per `deploy_spec/bundler_discovery.rb`), (2) the attacker can open a PR and label it (per the audit's stated attacker capability), (3) the attacker commits a file literally named `true` to their own branch. All of this is within the reach of an unprivileged contributor to a public/fork-based repo, and the exploit is deterministic and repeatable once conditions are met — no timing races, no secrets required.

### Recommendation
Do not let arbitrary PR label names become raw environment variable keys. Either:
- Restrict `ReviewStack#env`'s label-derived variables to a fixed, safe prefix (e.g. only allow `SHIPIT_LABEL_<NAME>` style keys) instead of using the raw upcased label as the key, or
- Maintain an explicit deny-list/allow-list intersecting with `BASE_ENV`, `Shipit.env`, `deploy_spec.machine_env`, and `VariableDefinition` names before merging into `TaskCommands#env`, explicitly rejecting keys like `BUNDLE_GEMFILE`, `BUNDLE_PATH`, `RUBYOPT`, `LD_PRELOAD`, `PATH`, etc.
- Additionally, `Command#unbundled_env` could refuse to let `@env` override a small set of security-sensitive keys (`BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD`) regardless of source.

```ruby
# shown here only to state the exact binding/assertions)
test "review stack labels leak BUNDLE_GEMFILE into dependency install command env" do
  stack = shipit_stacks(:review_stack) # a ReviewStack fixture with bundler deploy spec
  stack.pull_request.update!(labels: ['bundle_gemfile'])

  task = shipit_tasks(:review_stack_deploy) # associated task
  commands = Shipit::TaskCommands.new(task)

  install_command = commands.install_dependencies.first

  # Binding under test: env['BUNDLE_GEMFILE'] must never be attacker-reachable via labels.
  assert_nil install_command.env['BUNDLE_GEMFILE'], 
    "expected BUNDLE_GEMFILE to be filtered, but label injection set it to #{install_command.env['BUNDLE_GEMFILE'].inspect}"
end
```
