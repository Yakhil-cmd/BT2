### Title
Unauthenticated GitHub-identity spoofing via forged `Merge-Requested-By` commit trailer bypasses author-identity binding - (File: `app/models/shipit/user.rb`)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` extracts a login from the `Merge-Requested-By:` trailer in a commit message and calls `find_or_create_by_login!` on it without ever comparing that extracted login to the GitHub-signed `commit.author`/`commit.commit.author` identity of the same commit. Because the commit message is attacker-controllable content that ships to GitHub in the attacker's own fork/PR, any commit message reaching Shipit's ingestion path (`Commit.from_github`) with a crafted trailer will have its `Commit#author` attribute forged to an arbitrary existing (or newly-created) GitHub login.

### Finding Description
The binding that should hold is:
`commit_message_asserted_author (match_info[1]) == commit.author.login (or commit.commit.author.login)`

In practice it does not: [1](#0-0) 

The regex `/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/` is matched against `github_commit.commit.message` (raw, attacker-influenced git commit message text), and on a match the code immediately trusts `match_info[1]` as the merge requester's login and calls `find_or_create_by_login!(match_info[1])` — this creates/looks up a `Shipit::User` by that login and returns it as the commit's `author`, with no comparison against the commit's actual GitHub-verified author (`github_commit.author` / `github_commit.commit.author`).

This trailer is only meant to be trustworthy when it is generated by Shipit's own merge-queue flow: `MergeRequest#merge_message` builds `"#{title}\n\n#{MERGE_REQUEST_FIELD}: #{merge_requested_by.login}\n"` from a `merge_requested_by` value that was set via `MergeRequest.request_merge!(stack, number, user)` [2](#0-1) [3](#0-2) , where `user` is the actually-authenticated Shipit user who invoked the merge. That value is legitimate because it originates from Shipit's server-side session, not from the commit itself.

However, `User.find_or_create_author_from_github_commit` is invoked on every ingested commit via `Commit.from_github` [4](#0-3) , regardless of whether that commit's message trailer was produced by Shipit's own merge flow or crafted by an external actor. Git commit messages are plain text supplied by whoever authors/merges the commit on GitHub (e.g., PR title/body text used as the default squash-merge message, or any commit an attacker pushes to their own fork branch that later lands on the tracked branch via a normal GitHub merge). An attacker who controls the text of a commit that ultimately reaches the tracked branch can embed `Merge-Requested-By: victim-admin-login` in that text. When Shipit syncs/ingests that commit, `find_or_create_author_from_github_commit` matches the trailer and binds `Commit#author` to `victim-admin-login`'s `Shipit::User` record — a record that may already exist (an actual Shipit admin) or gets freshly created via `Shipit.github.api.user(login)` — with no verification that this matches the commit's real GitHub author/committer identity.

### Impact Explanation
The direct effect is a forged `Commit#author` association: `Shipit::User.find_or_create_by_login!` creates/attaches a real GitHub user record as the "author" of a commit that user never wrote, corrupting `has_many :authored_commits`, `User#repositories_contributed_to`, and `User#stacks_contributed_to` [5](#0-4) , and whatever UI surfaces commit authorship (audit trail forgery).

I searched the authorization-relevant code paths (`Stack`, `Deploy`, and the controllers gating deploys/rollbacks/locks) and found that request-level authorization is keyed off `current_user`/session and API client scopes, not off `Commit#author` [6](#0-5) . I could not find a concrete downstream authorization check in this engine that grants deploy/merge/rollback capability based on `Commit#author`, so I cannot confirm the "inherits arbitrary victim's authority" escalation claimed in the prompt — that part is speculative and unproven in this codebase. What is proven is the identity-binding defect itself: a forged authorship record is written for a commit whose real GitHub identity was never checked, which is a data-integrity/audit-trail forgery, not a demonstrated authentication bypass or unauthorized-deploy primitive.

### Likelihood Explanation
Exploitability of the *binding defect* itself is high and requires no privileges beyond writing a commit message, which is squarely available to any external contributor. However, turning this into the "critical" impact described (forged authority inherited by an attacker's deploy) requires an additional, unverified downstream dependency on `Commit#author` for an authorization decision, which I could not locate in this engine.

### Recommendation
In `Shipit::User.find_or_create_author_from_github_commit` (`app/models/shipit/user.rb`), do not trust the `Merge-Requested-By` trailer parsed from arbitrary commit message text as an authorization-equivalent signal. If this attribution feature must be kept, only honor it when the commit is verified to originate from Shipit's own merge-queue flow (e.g., match on `merge_request.merge_requested_by` already stored server-side, as `Commit#identify_merge_request` does at [7](#0-6)  via `self.author = merge_request.merge_requested_by`), and remove/ignore the free-text regex match against `github_commit.commit.message` for author attribution, or at minimum reject the trailer when the extracted login differs from `github_commit.author&.login`.

### Proof of Concept
minitest plan for `test/models/users_test.rb` (already contains related coverage of `find_or_create_author_from_github_commit` per grep, to be extended):
1. Build a stub GitHub commit resource where `commit.commit.message` = `"Some PR title\n\nMerge-Requested-By: victim-admin-login\n"` and `commit.author.login` / `commit.commit.author.login` = `"attacker-login"`.
2. Call `Shipit::User.find_or_create_author_from_github_commit(stub_commit)`.
3. Assert `result.login == "victim-admin-login"` while `stub_commit.author.login == "attacker-login"`, demonstrating `match_info[1] != commit.author.login` yet the mismatched (victim) user is returned unchallenged — i.e., the code never asserts `match_info[1] == commit.author.login` before calling `find_or_create_by_login!`.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
