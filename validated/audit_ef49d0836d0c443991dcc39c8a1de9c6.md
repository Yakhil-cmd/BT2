### Title
Missing `onlyRegisteredToken` Validation in `handleERC20Transfer` and `handleERC721Transfer` Allows Operators to Drain Unregistered Bridge-Held Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge contracts enforce token registration on the **outbound** (request) path but not on the **inbound** (handle) path. `handleERC20Transfer` and `handleERC721Transfer` accept any caller-supplied `_tokenAddress` without checking `registeredTokens[_tokenAddress]`, allowing a bridge operator to transfer any ERC20/ERC721 tokens held by the bridge — including deregistered, accidentally deposited, or otherwise unregistered tokens — to an arbitrary recipient.

---

### Finding Description

`BridgeTokens` defines the `onlyRegisteredToken` modifier:

```solidity
modifier onlyRegisteredToken(address _token) {
    require(registeredTokens[_token] != address(0), "not allowed token");
    _;
}
``` [1](#0-0) 

The **outbound** path `_requestERC20Transfer` correctly applies both `onlyRegisteredToken` and `onlyUnlockedToken`:

```solidity
function _requestERC20Transfer(...) internal
    onlyRegisteredToken(_tokenAddress)
    onlyUnlockedToken(_tokenAddress)
``` [2](#0-1) 

However, the **inbound** path `handleERC20Transfer` only checks `onlyOperators` — there is no `onlyRegisteredToken` guard:

```solidity
function handleERC20Transfer(...) public onlyOperators {
    ...
    if (modeMintBurn) {
        require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
    } else {
        IERC20(_tokenAddress).safeTransfer(_to, _value);
    }
}
``` [3](#0-2) 

The same asymmetry exists in `handleERC721Transfer`:

```solidity
function handleERC721Transfer(...) public onlyOperators {
    ...
    if (modeMintBurn) {
        require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...), "mint failed");
    } else {
        IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
    }
}
``` [4](#0-3) 

The off-chain relay (`handleRequestValueTransferEvent` in `bridge_manager.go`) does resolve the counterpart token address before calling the on-chain function, but this is a Go-layer convention — the on-chain contract itself imposes no such constraint. [5](#0-4) 

---

### Impact Explanation

In **lock/unlock mode** (`modeMintBurn == false`): any bridge operator can call `handleERC20Transfer` (or `handleERC721Transfer`) with an arbitrary `_tokenAddress` that is not in `registeredTokens`. The contract will execute `IERC20(_tokenAddress).safeTransfer(_to, _value)` (or `IERC721.transferFrom`) against the bridge's own balance. This drains any ERC20/ERC721 tokens the bridge holds that are not registered — including tokens that were deregistered but not withdrawn, tokens accidentally sent directly to the bridge address, or tokens whose registration was removed after deposit.

In **mint/burn mode** (`modeMintBurn == true`): the call would attempt to mint on an arbitrary contract. This would fail unless the bridge has the minter role on that contract, limiting the impact in this mode.

The corrupted value is the bridge's ERC20/ERC721 token balance: tokens are transferred out to an attacker-controlled `_to` address without any legitimate cross-chain request backing the transfer. The handle nonce is also consumed and advanced, which can desynchronize the bridge's nonce accounting with the counterpart chain. [6](#0-5) 

---

### Likelihood Explanation

The trigger requires `onlyOperators` — operators are semi-trusted relayers registered by the bridge owner. A single compromised or malicious operator (below the voting threshold if threshold > 1) can vote for a fraudulent handle; once the threshold is met, the transfer executes. With a threshold of 1 (the default at deployment), a single operator is sufficient. The attack requires no external contract deployment and no user interaction beyond submitting a transaction. [7](#0-6) 

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` to both `handleERC20Transfer` and `handleERC721Transfer`, mirroring the protection already present on the outbound path:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD THIS
{
    ...
}
```

Apply the same fix to `handleERC721Transfer`. This ensures the inbound path enforces the same token-registry invariant as the outbound path. [1](#0-0) 

---

### Proof of Concept

1. Bridge is deployed in lock/unlock mode (`modeMintBurn = false`) with operator threshold = 1.
2. Token `T` (registered) and token `U` (unregistered, e.g. accidentally sent to the bridge) are both held in the bridge's ERC20 balance.
3. Attacker controls one operator account `op`.
4. `op` calls:
   ```solidity
   bridge.handleERC20Transfer(
       bytes32(0),          // arbitrary requestTxHash
       op,                  // _from
       attacker,            // _to
       address(U),          // _tokenAddress — UNREGISTERED token
       bridgeBalanceOfU,    // _value
       freshNonce,          // _requestedNonce
       currentBlock,        // _requestedBlockNumber
       ""                   // _extraData
   );
   ```
5. The contract passes `onlyOperators`, skips `onlyRegisteredToken` (absent), votes pass (threshold = 1), and executes `IERC20(U).safeTransfer(attacker, bridgeBalanceOfU)`.
6. All of token `U` held by the bridge is transferred to the attacker. No legitimate cross-chain request existed for this transfer. [8](#0-7)
