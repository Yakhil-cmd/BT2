### Title
Lock Bypass in Bridge Handle Functions Allows Asset Drain When Bridge Is Locked — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`)

---

### Summary

The `lockKLAY()` and `lockToken()` mechanisms in the Kaia service-chain bridge are intended to act as emergency stops that prevent KAIA and ERC20 tokens from being transferred. However, the lock state is only enforced on the **request** path (`_requestKLAYTransfer`, `_requestERC20Transfer`) and is completely absent from the **handle** path (`handleKLAYTransfer`, `handleERC20Transfer`). Bridge operators can therefore drain KAIA or bridged ERC20 tokens from a locked bridge, defeating the purpose of the lock.

---

### Finding Description

`BridgeTransferKLAY.sol` defines a lock flag and two modifiers:

```solidity
bool public isLockedKLAY;

modifier lockedKLAY   { require( isLockedKLAY, "unlocked"); _; }
modifier unlockedKLAY { require(!isLockedKLAY, "locked");   _; }
```

The request path correctly enforces the lock:

```solidity
function _requestKLAYTransfer(...) internal unlockedKLAY nonReentrant { ... }
```

But the handle path — which actually moves KAIA out of the bridge — carries **no lock check**:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    // No unlockedKLAY modifier
    ...
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
```

The same asymmetry exists for ERC20 tokens. `BridgeTokens.sol` defines per-token locking:

```solidity
mapping(address => bool) public lockedTokens;
modifier onlyUnlockedToken(address _token) { require(!lockedTokens[_token], "locked token"); _; }
```

`_requestERC20Transfer` enforces it:

```solidity
function _requestERC20Transfer(...) internal onlyRegisteredToken(_tokenAddress) onlyUnlockedToken(_tokenAddress) { ... }
```

But `handleERC20Transfer` does not:

```solidity
function handleERC20Transfer(...) public onlyOperators {
    // No onlyUnlockedToken check
    ...
    IERC20(_tokenAddress).safeTransfer(_to, _value);   // or mint
}
```

---

### Impact Explanation

When the bridge owner calls `lockKLAY()` or `lockToken()` — typically in response to a security incident, a suspicious cross-chain request, or a regulatory requirement — the expectation is that no assets leave the bridge. Because `handleKLAYTransfer` and `handleERC20Transfer` ignore the lock state, any bridge operator (or an automated relayer) can continue to call these functions and transfer KAIA or bridged ERC20 tokens to arbitrary `_to` addresses. This constitutes an **unauthorized transfer of KAIA and bridged assets** from a system-managed contract, directly matching the allowed impact gate.

---

### Likelihood Explanation

Bridge operators are semi-trusted: they are authorized to relay legitimate cross-chain requests. In practice, operators are often automated relayers that process every pending `RequestValueTransfer` event. When the owner locks the bridge, the automated relayer has no on-chain signal to stop; it will continue calling `handleKLAYTransfer`/`handleERC20Transfer` for every queued event, draining the bridge. No attacker capability beyond being a registered operator is required.

---

### Recommendation

Add the `unlockedKLAY` modifier to `handleKLAYTransfer` and the `onlyUnlockedToken` modifier to `handleERC20Transfer` (and `handleERC721Transfer` if the same pattern exists there):

```solidity
function handleKLAYTransfer(...) public onlyOperators unlockedKLAY nonReentrant { ... }

function handleERC20Transfer(...) public onlyOperators onlyUnlockedToken(_tokenAddress) { ... }
```

This ensures the lock is enforced symmetrically on both the request and handle paths, matching the stated intent of `lockKLAY()` and `lockToken()`.

---

### Proof of Concept

1. Owner deploys bridge with KAIA liquidity (`chargeWithoutEvent`).
2. User on the counterpart chain calls `requestKLAYTransfer`, emitting `RequestValueTransfer` with nonce 0.
3. Owner detects suspicious activity and calls `lockKLAY()` → `isLockedKLAY = true`.
4. Owner verifies: `requestKLAYTransfer` now reverts with `"locked"`. ✓
5. Operator (or automated relayer) calls `handleKLAYTransfer(txHash, from, attacker, 1 ether, 0, blockNum, "")`.
6. The call succeeds — no `unlockedKLAY` check — and `1 ether` is transferred to `attacker`.
7. The bridge is drained despite being locked.
