### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act on `repository.full_name` (Same-Payload Field Split) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`) taken from the *unauthenticated* JSON body, then, once the signature is accepted, every `Handler` subclass (`Handler#repository_name`, `PullRequest::ClosedHandler#repository`, etc.) resolves the target `Stack`/`Repository` using a *different* field from that same body: `repository.full_name`. Nothing binds these two fields together, so the "organization whose secret authenticated the request" is never checked to equal "the repository that gets written to."

### Finding Description
`verify_signature` picks the GitHub App/secret to check the signature against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) *before* the signature is verified, and is used only to select which per-organization `webhook_secret` (`Shipit.github(organization:)`) to HMAC-check the raw body against, per `GithubApp#verify_webhook_signature`: [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the full, attacker-controlled body to the matching handler: [4](#0-3) 

Handlers never re-check `repository.owner.login`; they resolve the target repository/stack from `repository.full_name`, an independent field in the same payload: [5](#0-4) [6](#0-5) 

In a multi-tenant Shipit deployment (the engine explicitly supports multiple GitHub orgs, each with its own `app_id`/`installation_id`/`webhook_secret`, as shown in `config/secrets.development.shopify.yml`), an entity that controls (or is the legitimate installer/owner of) *one* configured organization's GitHub App — and therefore knows that org's `webhook_secret` — can craft a POST to `/webhooks` where:
- `repository.owner.login` = "orgA" (their own org → makes `verify_signature` pick `orgA`'s secret, which they can correctly HMAC-sign)
- `repository.full_name` = "orgB/some-repo" (a *different* tenant's repository)

The signature check passes because it only validates that the body was signed by orgA's known secret; it never asserts `repository.owner.login == repository.full_name.split('/').first`. The handler then acts on `orgB/some-repo` using data fully controlled by the orgA-secret holder.

This is the direct analog of the reported flashloan bug class: a value that is checked/authenticated (`repository.owner.login`, analogous to the debt/collateral field verified before closure) is not the same value that is subsequently acted upon (`repository.full_name`, analogous to the account actually closed/transferred). The verification and the mutation are decoupled across two different fields of the same untrusted input, breaking the intended binding "organization that authenticated == repository that is written."

### Impact Explanation
Depending on which webhook event/handler is invoked, this allows an attacker who legitimately controls one org's GitHub App (a low-privilege position relative to any *other* tenant on the shared Shipit instance) to forge events against another org's `Repository`/`Stack`:
- `PullRequest::ClosedHandler` can archive another org's review stacks.
- `push`/`GithubSyncJob`-triggering events can force syncs and, via existing stack automation (continuous deployment, merge queue processing), influence deploy/merge state of a repository the attacker does not own.
- `membership_handler` can create teams/users tied to another org's team-authorization checks (`Shipit.github_teams`), which is used for the app's own authorization boundary (`User#authorized?`).

This is a cross-repository/cross-tenant write performed without any credential tied to the victim organization, satisfying the "cross-repository writes" / escalation-into-`Shipit.github_teams`-authorization impact categories.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator of at least one GitHub organization/App that is configured in the same shared Shipit instance (multi-org config is a documented, supported deployment mode). No access to the victim org's secrets, no privileged Shipit account, and no GitHub write access to the victim repo is needed — only the ability to sign an arbitrary HTTP POST with a secret the attacker legitimately possesses for their own org. This matches the "no privileged keys for the target" bar required by the rules.

### Recommendation
Bind the field used for signature-secret selection to the field used for repository resolution: after verifying the signature, re-derive `repository_owner` from `repository.full_name` (or vice versa) and reject the request (422) if they don't match. Alternatively, resolve the target `Repository`/`Stack` strictly by `repository.owner.login` (the value that gated secret selection) rather than by the separate `full_name` field, so the same trust anchor is used end-to-end.

### Proof of Concept
1. Attacker legitimately owns/administers `orgA`, which is configured in Shipit's multi-org `github:` secrets with `webhook_secret = S_A`.
2. Attacker crafts a `pull_request` closed-event JSON body with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/victim-repo"`
   - `action = "closed"`, valid nested `pull_request` fields.
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_A, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and `verify_webhook_signature` succeeds (correct secret for the chosen org).
5. `PullRequest::ClosedHandler` resolves `Shipit::Repository.from_github_repo_name("orgB/victim-repo")` and calls `review_stack.archive!`, mutating a stack that belongs to `orgB`, an organization the attacker has no relationship with.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
