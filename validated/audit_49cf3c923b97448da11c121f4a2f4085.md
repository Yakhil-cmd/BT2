### Title
Unaccounted "eat-the-coins" AA deposits allow reserve-ratio manipulation in balance[]-based AMM/oscript logic - ([File: aa_composer.js], [File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The MBC/ZZSH exploit worked because the vulnerable contracts computed swap/liquify amounts from raw token `balanceOf()` deltas that could be inflated by a direct, unaccounted transfer before the swap-triggering call, letting the attacker distort the pool's price ratio and profit on the round trip. The Obyte/ocore analog is any AA that reads `balance[asset]` (the AA's live on-chain balance) to compute investment/exchange ratios, combined with a documented ocore platform behavior: when a trigger unit's payment does not match any `case` (or produces no messages), the AA still permanently absorbs the received coins into its balance with **no state-variable accounting** of the deposit ("eat the received coins and send no response, state changes are still performed").

### Finding Description
`aa_composer.js` explicitly handles the case where an incoming trigger's data does not satisfy any `if` condition (or all messages get filtered out) by silently keeping the money and doing nothing else: [1](#0-0) 
This means **any unprivileged unit poster can send coins directly to an AA's address with a trigger payload that matches none of the AA's `if` branches**, and those coins become part of `balance[asset]` / `balance[base]` forever, without the AA's own state variables (e.g. `var['mm_asset_outstanding']`) being updated to reflect it.

The reference/example AMM shipped with ocore, `test/samples/uniswap_like_market_maker.oscript`, computes swap and investment amounts directly from `balance[$asset]` and `balance[base]` minus the current trigger's own outputs: [2](#0-1) [3](#0-2) 
Because `balance[]` reflects the AA's *actual* accumulated on-chain balance (read straight from `aa_balances`/live formula state) rather than an internally tracked reserve variable, and because the platform allows unaccounted deposits to silently inflate that balance (as shown above), an attacker can:
1. Send a "dust" unit to the AA with `data` that satisfies none of the `if` cases (e.g. omit `trigger.data.define`, don't cross the `1e5` threshold, etc.), donating extra base/asset balance that is absorbed with no state update.
2. Immediately follow with a real trigger unit that hits the `exchange bytes to asset` / `exchange asset to bytes` branches, where `$asset_balance`/`$bytes_balance` (and thus `$p`, `$new_asset_balance`, `$amount`) are computed straight from the now-inflated `balance[...]`.
3. Extract a distorted amount of the other asset because the constant-product formula is evaluated against a reserve value the attacker just skewed, exactly mirroring how the MBC/ZZSH attacker donated tokens to the pair before calling `swap`, letting `swapAndLiquifyStepv1` and the subsequent swap operate on manipulated reserves.

This is a business-logic flaw class, not a memory-safety bug: the ocore engine correctly executes the oscript as written, but the platform's "silently keep unmatched deposits" semantics (`aa_composer.js:1873-1877`) makes any `balance[]`-driven pricing formula unsafe unless the AA author tracks reserves in dedicated state variables (as `var['mm_asset_outstanding']` partially does for share accounting, but the underlying `asset`/`base` reserves used for the constant-product price are never independently tracked).

### Impact Explanation
Any AA implementing an AMM/bonding-curve/liquidity-pool pattern using `balance[asset]` directly (matching the pattern shown in ocore's own reference sample) is exposed to a donation-based price-manipulation attack. This allows an attacker to extract funds at a manipulated exchange rate from the pool, resulting in direct fund loss for other liquidity providers/traders interacting with the AA — a concrete "AA fund loss" impact reachable by an unprivileged trigger sender, consistent with Medium/High severity.

### Likelihood Explanation
High likelihood for any AA author who follows the documented/sample pattern of using `balance[asset]` for AMM pricing: the attack requires only two ordinary trigger units from an unprivileged address (a "donation" unit whose data matches no case, followed by a swap-triggering unit), no privileged access, no protocol bug beyond the intentional-but-unsafe "eat the coins" semantics.

### Recommendation
- AA authors implementing AMM-style pricing must never derive swap/exchange amounts directly from `balance[asset]`/`balance[base]`; instead they should maintain and update dedicated state variables (e.g. `var['reserve_base']`, `var['reserve_asset']`) on every deposit/withdrawal path, and explicitly bounce/reject any trigger whose payment doesn't match a known case rather than silently absorbing it.
- Consider updating the ocore documentation/reference sample (`test/samples/uniswap_like_market_maker.oscript`) to warn against or fix this pattern, since it is likely to be copied by real-world AA authors.
- Alternatively, ocore could offer/encourage a mechanism to make unmatched-case deposits bounce back to the sender rather than being permanently absorbed into `balance[]`, closing the donation vector at the platform level.

### Proof of Concept
1. Deploy an AA based on `test/samples/uniswap_like_market_maker.oscript`; define the MM asset and seed it with an initial deposit (case 2, `$asset_balance == 0 OR $bytes_balance == 0`).
2. Attacker sends a trigger unit paying, say, 10,000,000 bytes and some `asset` tokens to the AA's address with `data` that satisfies none of the `if` conditions (e.g., large base payment but also `trigger.data.define` unset and asset output not exactly `0`/`>0` matching thresholds, or crafted to fail every guard) — per `aa_composer.js:1873-1877` this unit is accepted, funds are kept, but no `messages`/state updates occur.
3. Attacker immediately sends a second trigger unit hitting the "exchange bytes to asset" case (`trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] == 0`); `$bytes_balance`/`$asset_balance` are now computed from the balance inflated in step 2, producing a skewed `$amount` of `asset` paid out to the attacker.
4. Attacker performs the reverse trade in a third unit to convert back to bytes, realizing profit from the manipulated ratio — mirroring the reserve-manipulation round trip in the MBC/ZZSH exploit.
