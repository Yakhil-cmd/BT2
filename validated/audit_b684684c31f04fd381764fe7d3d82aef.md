### Title
ERC20Transactor trusts an attacker-deployed contract's fabricated `transfer()` boolean return instead of verifying actual balance movement - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`assets_common::ERC20Transactor` implements `TransactAsset::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` by calling `IERC20::transfer` on the contract address that is encoded in the XCM `Asset` location, then treats the operation as "successful token movement" purely based on the ABI-decoded boolean return value of that call.

### Finding Description
Any signed account can submit `pallet_xcm::execute` with an XCM program that names an arbitrary `AccountKey20` contract address as the asset id (as demonstrated by the runtime's own tests `smart_contract_not_erc20_will_error` and `smart_contract_does_not_return_bool_fails` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1978-2081`, which build `withdraw_asset((AccountKey20 { key: <arbitrary address> }, amount))` XCM instructions). `ERC20Transactor` is wired into `AssetTransactors` for asset-hub-westend at `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:240-246`, and its `Matcher` (`assets_common::ERC20Matcher`) maps any `AccountKey20` location to the corresponding contract address with no allow-list/registration check visible in the reviewed matcher wiring.

In `withdraw_asset_with_surplus` (erc20_transactor.rs:150-216) and `deposit_asset_with_surplus` (erc20_transactor.rs:225-306), the transactor:
1. Calls `bare_call` against the attacker-supplied contract's `transfer(address,uint256)`.
2. Only checks `return_value.did_revert()` and then ABI-decodes the return data as a `bool` via `IERC20::transferCall::abi_decode_returns_validate`.
3. If the decoded value is (or casts to) `true`, it unconditionally credits `AssetsInHolding` with an `Erc20Credit(amount)` imbalance (a "trust me" imbalance type, see `struct Erc20Credit` at erc20_transactor.rs:79-107) — with **no verification that the checking account's real token balance actually decreased/increased by `amount`** (no `balanceOf` diff check before/after the call).

This is structurally identical to the report's root cause: trusting a claimed "transfer succeeded" signal (a fabricated notification/return value from an untrusted, attacker-controlled contract) instead of verifying the real, on-chain state change of the token balance — exactly the bug class in the nkpaymentcap incident, where the DApp trusted a spoofed transfer notification instead of validating the real inline action/contract that produced it.

The runtime authors were partially aware of the return-value spoofing risk — the test `smart_contract_does_not_return_bool_fails` at `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2026-2081` documents that a fake ERC20 contract returning a non-bool `uint256` value can still be cast to `true` and succeed, i.e., is explicitly *not* rejected.

### Impact Explanation
Because the credited amount is purely a claim made by an attacker-controlled contract, the executor's `AssetsInHolding` can be populated with a completely fabricated `Erc20Credit` that is not backed by any real balance movement of a real, trusted asset. This holding is otherwise treated by the XCM executor identically to any legitimately-matched fungible asset for the remainder of the program (e.g., it could in principle be routed through `DepositAsset`, or exchanged via `AssetExchanger`/`SingleAssetExchangeAdapter` against a pool if a pool exists for that asset). Whether this leads to extraction of *real* backed value (e.g., WND) depends on whether a liquidity pool or other trust boundary treats this fake asset as convertible — I was not able to fully verify within the available context whether `PoolAssetsExchanger`/`AssetConversion` would allow such a pool to be paired against a real asset without the attacker independently funding both sides, which would make exploitation partially/fully an economic/social (rug-pull) scenario rather than a pure protocol invariant violation. This uncertainty is a real limitation of this analysis.

### Likelihood Explanation
Reaching this code requires only a signed extrinsic (`pallet_xcm::execute`) and a self-deployed `pallet_revive` contract exposing a `transfer(address,uint256)` selector that always returns `true` — both are ordinary, unprivileged user actions with no governance, stolen keys, or malicious external chain/collator involved. The runtime's own test suite (`smart_contract_does_not_return_bool_fails`, `smart_contract_not_erc20_will_error`) confirms this path is directly reachable and that spoofed return values are not fully rejected.

### Recommendation
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` should independently verify the real balance delta of the checking account / beneficiary (e.g., via `balanceOf` before and after the `transfer` call, or by requiring the contract to be a pre-registered/allow-listed asset with known-safe semantics) rather than trusting the contract's self-reported boolean return value alone. Additionally, any code path that could later treat this `Erc20Credit` as fungible with real backed assets (pool creation/exchange) should be reviewed to ensure a fabricated credit cannot be laundered into real value.

### Proof of Concept
No independent PoC execution was performed. The reasoning above is derived from the existing runtime test suite (`cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1978-2081`), which already demonstrates the "arbitrary attacker contract as ERC20 asset" path is reachable and that non-standard/fabricated return values are not conclusively rejected (`smart_contract_does_not_return_bool_fails`). I was not able to trace, within available tool budget, a concrete end-to-end path from this fabricated credit to extraction of real backed assets (e.g., via `AssetConversion`/`SingleAssetExchangeAdapter`), so the "measurable loss" leg of the required chain (checks → mutation → cross-pallet effect → loss) remains unverified. This should be explicitly validated (or refuted) with a local integration test before treating this as bounty-eligible; I flag it as a plausible analog rather than a fully proven exploit. /// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}

#[test]
fn smart_contract_not_erc20_will_error() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 10_000_000_000_000u128;

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let (code, _) = compile_module("dummy").unwrap();

		let Contract { addr: non_erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.build_and_unwrap_contract();

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: non_erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.build();
		// Execution fails but doesn't panic.
		assert!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(2_500_000_000, 120_000),
		)
		.is_err());
	});
}
