This confirms the exploit chain: `Handler#stacks` resolves via `Repository.from_github_repo_name(repository_name)` using `payload.dig('repository', 'full_name')` [1](#0-0) , and `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on every matching stack's branch [2](#0-1) , with no re-check that `full_name`'s owner matches the organization used for the signature.

### Title
Cross-organization webhook forgery via mismatched signature-verification organization and acted-upon repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/webhook secret to validate the HMAC using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [3](#0-2) . Once the signature is accepted, the raw JSON body is dispatched unchanged to event handlers, which independently resolve the target repository from a *different* field of the same payload: `payload.dig('repository', 'full_name')` [1](#0-0) . Nothing enforces that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same organization, so a valid signature computed with one organization's `webhook_secret` can be paired with a `full_name` pointing at a stack belonging to a completely different, unrelated organization in the same Shipit installation.

### Finding Description
Shipit supports hosting multiple GitHub organizations from one instance, each with its own `webhook_secret`, selected via `Shipit.github(organization:)` [4](#0-3) , as documented for multi-org setups [5](#0-4) .

The binding that should hold is:
`organization used to select the webhook_secret that authenticates the payload == organization that owns the repository the payload causes Shipit to act on`

In `WebhooksController#verify_signature`, the organization is derived from `repository_owner` (`params.dig('repository','owner','login')`) [6](#0-5) , and only that value is used to fetch the `GitHubApp` and its secret before calling `verify_webhook_signature` [7](#0-6) . But the HMAC covers only `request.raw_post` bytes — it does not semantically pin `repository.owner.login` to any other field. The handler layer then reads `repository.full_name` independently to look up the `Repository`/`Stack` to operate on [1](#0-0)  via `Repository.from_github_repo_name` [8](#0-7) .

Because `owner.login` and `full_name` are two independent, attacker-controlled JSON fields inside the same signed body, an attacker who legitimately possesses the `webhook_secret` for *any one* organization configured in the multi-org Shipit instance (e.g., their own org "OrgOne", which they administer and can read the webhook secret for from their own GitHub App settings) can craft a payload where:
- `repository.owner.login = "OrgOne"` (used only for HMAC-organization selection, verifies successfully with OrgOne's secret)
- `repository.full_name = "OrgTwo/victim-repo"` (used by the handler to pick the actual Stack to act on)

This breaks the binding: the organization that authenticated the payload is not the organization/repository the engine writes to.

### Impact Explanation
Depending on event type, this allows an attacker who only knows one organization's `webhook_secret` to forge webhook effects against stacks belonging to a different organization tracked by the same Shipit instance:
- `push` events trigger `PushHandler#process`, which calls `stack.sync_github(expected_head_sha:)` on stacks of the victim repo/branch [2](#0-1) , forcing an unauthorized sync using an attacker-chosen `after` SHA.
- `status` events let the attacker inject arbitrary commit statuses via `Commit#create_status_from_github!` for any commit `sha` in the system, since `StatusHandler` doesn't scope to a specific repository/stack at all [9](#0-8)  — this can manipulate CI-gated deploy checks (`ci.require`) for an unrelated org's stack.
- `check_suite` events can force `schedule_refresh_check_runs!` on victim-org commits [10](#0-9) .

This crosses a repository/organization trust boundary and can influence deploy-gating state (CI status, check runs, sync) for a stack the attacker does not own or have credentials for, meeting the "cross-repository writes" / unauthorized deploy-adjacent impact bar.

### Likelihood Explanation
Requires the attacker to control (or have legitimate access to) at least one organization's `webhook_secret` in a Shipit deployment configured with multiple GitHub organizations (an explicitly documented and supported configuration, see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`). This is a realistic scenario for shared/multi-tenant Shipit installations where different teams/orgs each control their own GitHub App and secret but share one Shipit instance — one org's legitimate secret holder can forge events against another org's stacks.

### Recommendation
After selecting the `GitHubApp` for signature verification, re-derive `repository_owner`/`organization` strictly from the same field used later by handlers (`repository.full_name`'s owner segment), or better, have handlers re-validate that the resolved `Repository#owner` matches the organization whose secret verified the signature before acting on any stack.

### Proof of Concept
1. Attacker administers "OrgOne" (a legitimate customer org on a shared Shipit instance) and knows OrgOne's GitHub App `webhook_secret`.
2. Attacker crafts a JSON payload for `X-Github-Event: push`:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, body)>` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches OrgOne's `GitHubApp`, and the signature verifies successfully [7](#0-6) .
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` [1](#0-0)  and calls `sync_github(expected_head_sha: "deadbeef...")` on OrgTwo's stack, even though the request was never authenticated for OrgTwo.
