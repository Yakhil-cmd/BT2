The DODO report describes a DeFi lending/liquidation contract omitting `accrueInterests()` before `liquidateByDODO`. There is no analogous "interest accrual" concept tied to a liquidation-like operation in this codebase's FRAME pallets. The closest conceptual parallel — snapshotting a rate (reward pool) before a state-mutating action — exists in `pallet-nomination-pools`' commission handling, but that exact bug class was already identified and fixed (`set_commission_max` now calls `update_records` before lowering `commission.current`), as documented in [1](#0-0)  and verified by the regression test [2](#0-1) .

For staking/pool slashing, which is the nearest FRAME analog to "liquidation," the pending slash is always applied (`do_apply_slash`) before withdrawal in `withdraw_unbonded`, so state is up to date before funds move: [3](#0-2) . No unpatched, reachable code path was found where a signed extrinsic permits liquidation/withdrawal/slash-application to proceed against stale interest/reward/exchange-rate state. Forcing the EVM lending-protocol bug class onto this codebase's staking/pools primitives does not produce a demonstrable, currently-exploitable analog.

	fn set_commission_max_snapshots_rewards_before_lowering_current() {
		// `set_commission_max` force-lowers `current` when the new max is below it. Rewards that

			let payee = 900;
			let _ = Currency::set_balance(&payee, 5);

				pool_id,
				Some((Perbill::from_percent(50), payee))
			));
			// ...and 100 of rewards accrue with no intervening snapshot (no claim/bond happens).
			deposit_rewards(100);
			assert_eq!(RewardPool::<Runtime>::current_balance(pool_id), 100);

			assert_eq!(RewardPools::<Runtime>::get(pool_id).unwrap().total_commission_pending, 50);
