### Title
Webhook signature is validated against the org derived from `repository.owner.login`, while the acted-upon repository is taken from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org (and therefore which `webhook_secret`) to validate the inbound signature against based on `repository.owner.login` (or `organization.login`) pulled straight out of the untrusted JSON body. Once the signature check passes, the actual event-processing code path (`PushHandler`, `StatusHandler`, etc., via `Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target repository/stack from a **different** field of the same untrusted payload: `repository.full_name`. Nothing binds these two fields together.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
using [2](#0-1) 
to pick `repository_owner` purely from the JSON body, then fetches that organization's `GitHubApp` (and thus its `webhook_secret`) via `Shipit.github(organization: repository_owner)`, and validates `X-Hub-Signature` with `verify_webhook_signature`: [3](#0-2) 

Once validated, `create` dispatches the same raw parsed JSON to handlers: [4](#0-3) 

Handlers resolve the stack to act on via `repository_name`, which reads `repository.full_name` — a separate JSON key from `repository.owner.login`: [5](#0-4) [6](#0-5) 

Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, as shown in the multi-org secrets fixture: [7](#0-6) 

Because the signature is HMAC'd only over the raw body and the `webhook_secret` selection depends on an unauthenticated field (`repository.owner.login`) that is never cross-checked against `repository.full_name`, an attacker who legitimately knows (or controls) the `webhook_secret` for **one** onboarded organization (OrgA) can craft an HTTP POST to `/webhooks` where:
- `repository.owner.login = "OrgA"` (so `verify_signature` looks up OrgA's `GitHubApp`/secret and the HMAC computed with OrgA's `webhook_secret` validates), while
- `repository.full_name = "OrgB/some-onboarded-repo"` (so the handler processes the event as if it originated from OrgB's repository).

This breaks the intended binding: *the organization whose credential authenticated the request* ≠ *the repository the code subsequently writes to / acts upon*. This is a direct analog of the "authenticated identity vs. acted-upon target" bug class from the referenced report (there, an SCP node's asserted parameters were not the ones actually enforced; here, the org whose secret authenticated the webhook is not the org/repo the handler subsequently trusts and mutates).

### Impact Explanation
Handlers keyed off `repository.full_name` can perform state-changing, cross-repository actions once "authenticated" this way:
- `PushHandler#process` enqueues a `GithubSyncJob` / calls `stack.sync_github(expected_head_sha:)` for the target stack resolved from the forged `full_name`. [8](#0-7) 
- `StatusHandler#process` creates a commit status (`create_status_from_github!`) on commits belonging to a different repository's stack. [9](#0-8) 

This is a cross-repository write achievable by anyone who holds a valid webhook secret for *any single* org configured in the same Shipit instance, letting them inject synthetic push/status events attributed to a completely different, unrelated repository they do not control on GitHub. In a multi-tenant/multi-org Shipit deployment this crosses the documented "cross-repository writes" Critical-impact bucket.

### Likelihood Explanation
Requires the attacker to know one org's `webhook_secret` in a multi-org Shipit deployment — this is explicitly a supported configuration (`secrets_double_github_app.yml`), and organizations onboarded to a shared Shipit instance are not necessarily mutually trusting. No repository write access, `ApiClient` token, or session is needed — only the ability to send a raw HTTP POST to the public `/webhooks` endpoint with a correctly-signed body using a secret they legitimately possess for their own org.

### Recommendation
- In `verify_signature`, ensure the organization used to select the `webhook_secret` is derived the same way, and is cross-validated against, the organization/repository that handlers will subsequently act on (i.e., validate that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching).
- Alternatively, have handlers use the already-verified `repository_owner` (not `full_name` alone) to scope repository/stack lookup, so the field trusted for authorization is the same field trusted for target resolution.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`), and onboard a stack for `OrgB/target-repo`.
2. As an attacker who only knows `OrgA`'s `webhook_secret` (e.g., because they administer an OrgA-side integration), build a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner => "OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature validates successfully.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/target-repo")` from `full_name` and enqueues a sync against `OrgB`'s stack — despite the request never being signed by `OrgB`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
