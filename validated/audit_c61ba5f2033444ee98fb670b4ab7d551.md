### Title
Webhook signature verification org (`repository.owner.login`) is decoupled from the target repository org (`repository.full_name`) used by all event handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check using `repository.owner.login`, while `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (used by `CheckSuiteHandler#process` and every other handler) resolves the target `Repository`/`Stack`/`Commit` using the independent `repository.full_name` field of the same attacker-controlled JSON body. Because these two fields are never cross-validated, in a multi-org Shipit deployment an attacker who names an org with no `webhook_secret` configured in `repository.owner.login` can forge a `check_suite` payload whose `repository.full_name` points at a victim repository in a *different, properly-secured* org, causing `schedule_refresh_check_runs!`/`RefreshCheckRunsJob` to run against the victim's commit.

### Finding Description
Claimed binding: `repository.owner.login` (the org used to select the verifying `GitHubApp`/secret in `WebhooksController#verify_signature`) should equal the owner segment of `repository.full_name` (the org that actually owns the `Stack`/`Commit` being mutated). The code never enforces this.

- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then checks `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- In a multi-org config (`secrets.github` keyed by org name, `github_default_organization` non-nil), `Shipit.github` looks up `github_app_config(organization)` per-org and instantiates a `GitHubApp` scoped to *that org's own* `webhook_secret`. [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` — i.e., if that org's secret is blank/unset, ANY signature (or none) is accepted. [3](#0-2) 
- Every handler, including `CheckSuiteHandler`, resolves the target repo/stack purely from `payload.dig('repository','full_name')` via `Handler#stacks`/`#repository_name`, with no relation to `repository_owner`. [4](#0-3) 
- `CheckSuiteHandler#process` then walks `stacks.where(branch: head_branch)` and calls `schedule_refresh_check_runs!` on any matching commit by `sha`. [5](#0-4) 
- `Repository.from_github_repo_name` splits `full_name` and does a plain `find_by(owner:, name:)` — no check that this owner matches the org that verified the signature. [6](#0-5) 

Attacker request: POST `/webhooks` with header `X-Github-Event: check_suite` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org-with-no-secret" }, "full_name": "victim-org/victim-repo" },
  "check_suite": { "head_branch": "master", "head_sha": "<existing victim commit sha>" }
}
```
If `attacker-org-with-no-secret` is one of the orgs configured in Shipit's multi-org `secrets.github` with `webhook_secret` unset (a configuration the project's own docs/fixtures show as valid/default, e.g. `test/dummy/config/secrets_double_github_app.yml`), signature verification trivially passes regardless of the `X-Hub-Signature` header. The `Handler#stacks` lookup then uses `repository.full_name`'s "victim-org", finds the real victim `Stack`/`Commit`, and schedules `RefreshCheckRunsJob`, which calls `Commit#refresh_check_runs!`/uses the victim org's own GitHub credentials against the victim's real GitHub repo.

None of the existing guards prevent this: `verify_signature` only checks a signature scoped to `repository.owner.login`; it never compares that value to `repository.full_name`'s owner. `drop_unhandled_event` and `check_if_ping` are unrelated. The `ExplicitParameters` schema for `CheckSuiteHandler` only requires `head_sha`/`head_branch` types, not repository consistency.

### Impact Explanation
An attacker with no relationship to the victim org can cause the app to enqueue `RefreshCheckRunsJob` for a victim's commit, forcing Shipit to make authenticated GitHub API calls (`check_runs`) against the victim repo using the victim org's own stored GitHub App credentials, entirely on the say of an unrelated attacker-controlled/named org. This is a cross-tenant confused-deputy: a payload nominally "authenticated" for one org (or not authenticated at all, if that org has no secret) mutates another org's Shipit state (queues a job touching commit/check-run records for a repo the attacker never proved control of). The same root cause (`Handler#repository_name` divorced from `verify_signature`'s org) affects all other handlers (`push`, `status`, `pull_request`, etc.), so the blast radius extends beyond `check_suite` to any handler reachable through `/webhooks`. This matches "a payload for one repository mutating another's stack/commit" — Critical per the rubric, though the concrete `check_suite` action itself only queues a check-run refresh (a read against GitHub), not a deploy/merge.

### Likelihood Explanation
This only manifests in **multi-org** Shipit deployments (`secrets.github` keyed by multiple org names) where at least one configured org has no `webhook_secret` set — a state the project's own setup docs and multi-org test fixture (`secrets_double_github_app.yml`) present as an acceptable/default configuration. In a single-org deployment, `Shipit.github` ignores the `organization:` argument entirely and always uses the one top-level secret, so the org-name spoof described here has no effect there (single-org deployments are only vulnerable if the sole configured secret is itself blank, which is a separate, non-org-confusable issue). Given the multi-org precondition, attacker cost is trivial: no session, no token, no knowledge of any real secret — just knowledge/guess of one org name in the deployment's config that lacks a secret, and the target repo's `full_name`/branch/commit sha, all of which are typically discoverable from public GitHub activity or the Shipit UI. The attack is fully repeatable and requires no live GitHub interaction to reproduce.

### Recommendation
In `WebhooksController#verify_signature`, require that `repository.owner.login` matches the owner segment of `repository.full_name` before proceeding, or better, derive the verifying org strictly from `repository.full_name` (the same field every handler uses to resolve state) rather than from a separate, independently-controlled `repository.owner.login`/`organization.login` field. Additionally, treat an org with a blank `webhook_secret` in a multi-org config as a hard misconfiguration (refuse to process webhooks, or fail closed) instead of silently returning `true` from `verify_webhook_signature`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), multi-org secrets fixture:
1. Configure `secrets.github` as multi-org (`OrgOne` with no `webhook_secret`, `OrgTwo` with a real `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create victim `Stack` (`OrgTwo/victim-repo`, branch `master`) and `Commit` (`sha: "victimsha123"`).
3. POST to `/webhooks` with `X-Github-Event: check_suite`, no valid `X-Hub-Signature` for `OrgTwo`, and body:
   `{"repository": {"owner": {"login": "OrgOne"}, "full_name": "OrgTwo/victim-repo"}, "check_suite": {"head_branch": "master", "head_sha": "victimsha123"}}`.
4. Assert `response` is `:ok` (not `422`) — proving verification against `OrgOne` (no secret) trivially passed.
5. Assert `assert_enqueued_with(job: RefreshCheckRunsJob)` (or that `commit.reload` scheduling occurred) for the `victimsha123` commit belonging to `OrgTwo`, demonstrating that a signature verified only against `OrgOne` triggered action on `OrgTwo`'s commit — i.e., `repository_owner` used for verification (`OrgOne`) ≠ the org that actually owns the affected commit (`OrgTwo`), yet the action was permitted.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
