### Title
Read-after-write race between in-memory unit-props cache and DB triggers assertion crash - (File: storage.js)

### Summary
`storage.readUnitProps()` first checks the in-memory caches `assocStableUnits`/`assocUnstableUnits`, and if the unit is not yet cached, issues an async DB query and re-validates the freshly read row against whatever is now in the in-memory caches. Because unit processing (`writer.js` `saveJoint`, `main_chain.js` `markMcIndexStable`) mutates these same in-memory caches asynchronously while other `readUnitProps()` calls are in flight for different units/authors, the two views can diverge between the moment the SQL callback fires and the moment the in-memory cache was captured, hitting one of several unconditional `throw Error(...)` assertions.

### Finding Description
`readUnitProps(conn, unit, handleProps)` is used throughout validation and main-chain code to fetch a unit's properties, e.g. from `validateParents`, `main_chain.updateMainChain` (`goUpFromUnit`), and `paid_witnessing.js`. Its fast path returns directly from `assocStableUnits`/`assocUnstableUnits` [2](#0-1) . If the unit isn't cached, it runs a DB `SELECT ... FROM units JOIN unit_authors ...` and, once the callback fires, re-checks the caches:

- If the DB row shows `is_stable=1` but the unit was *just* promoted to `assocStableUnits` between the initial check and the callback, the code compares the freshly read DB row against the racily-populated cache entry and throws `"different props: assocStableUnits[unit]=..., props=..."` if they don't deep-equal [3](#0-2) .
- If the DB row shows `is_stable=0` but the unit has meanwhile been forgotten from `assocUnstableUnits` (e.g. via `forgetUnit()` after stabilization/rewrite of unstable state), the code unconditionally throws `"no unstable props of "+unit"` [4](#0-3) .
- Even when both entries exist, any transient mismatch between DB and in-memory shadow props (which are mutated piecemeal by `writer.js` and `main_chain.js` while units are validated/stabilized concurrently) throws `"different props of "+unit+..."` [5](#0-4) .

This is structurally the same bug class as CVE-2024-23850: an object (`unit` row/props) is inserted/mutated in one code path (`writer.js` `saveJoint`, `main_chain.js` `markMcIndexStable`) while it is concurrently looked up in another (`readUnitProps`), and the lookup path enforces an invariant with a hard assertion instead of tolerating the timing window, crashing the whole node process. The same pattern of "fetch stale snapshot then hard-assert equality with concurrently-mutated in-memory state" recurs in `main_chain.js`'s `goUpFromUnit` (`throwError("different props, db: ...")`) [6](#0-5)  and in `readPropsOfUnits` [7](#0-6) , and in `readBestChildrenProps` [8](#0-7) , all reachable purely from posting units into an otherwise honest DAG (no privileged access required) once enough concurrent unit submissions create the race window.

### Impact Explanation
Hitting any of these `throw Error(...)` assertions is an uncaught exception inside the unit-validation/main-chain-update pipeline, which is not guarded by a try/catch at these call sites, crashing the full node process. A crashed full node stops confirming/relaying units for as long as it remains down, matching the "network unable to confirm new units" acceptance criterion, and is the direct analog of the "assertion failure and crash" impact described in CVE-2024-23850 (CVSS A:H).

### Likelihood Explanation
Triggering the exact interleaving requires two units (or a unit and a stabilization event) to race such that the SQL callback for `readUnitProps` resolves in the narrow window between an in-memory cache mutation in `writer.js`/`main_chain.js` and the completion of an unrelated async DB read for the same unit. This is timing-dependent and not attacker-controlled with the same precision as choosing exact byte offsets, but an attacker who can flood the node with many units concurrently (which is a normal, unprivileged operation — anyone can post units) increases the probability of hitting the race, especially under load or on slower storage backends (e.g. MySQL network latency vs. local caches), making repeated crash-inducing attempts realistic over time even though a single attempt isn't deterministic.

### Recommendation
Replace the hard `throw Error(...)` assertions in `readUnitProps`, `readPropsOfUnits`, `goUpFromUnit`, and `readBestChildrenProps` with re-fetch/retry logic (or a `throwError()`-only non-fatal emit path as already used elsewhere in the codebase, e.g. `storage.throwError`) so a detected cache/DB divergence does not crash the node but instead safely serves the freshest value (or retries after the write lock is released). At minimum, ensure that these debug-consistency checks are only enabled when `conf.bFaster` is false in the test/dev configuration and cannot fire in production configurations exposed to the network.

### Proof of Concept
1. Run a full node with `conf.bFaster` disabled (default consistency-check mode).
2. From several independent processes/wallets, concurrently post many valid units authored by different addresses that reference each other as parents/last-ball around the same main-chain-index boundary, so that some units are actively being validated (`validateParents` → `readUnitProps`) at the same moment others are being written (`writer.js saveJoint`) or a main-chain-index is being marked stable (`main_chain.js markMcIndexStable`, which mutates `storage.assocStableUnits`/`assocUnstableUnits` and calls `forgetUnit`).
3. Repeat under load; when a `readUnitProps` DB callback resolves after a concurrent in-memory cache mutation for the same unit, the node throws `"different props of ..."` or `"no unstable props of ..."` and crashes, taking the node offline.
