### Title
Cross-AA data-feed and pool-balance oracle reads are unstable and manipulable within a single atomic unit, enabling flash-loan-style price attacks — ([File: formula/evaluation.js], [File: data_feeds.js])

### Summary
The `data_feed[[...]]` / `in_data_feed[[...]]` oscript primitives, when evaluated inside an AA (`bAA=true`), read data feed values not only from finalized/stable units but also from **unstable messages**, including responses of other AAs that were just produced earlier in the same trigger-processing chain (secondary triggers), before that chain’s outer unit is even validated/stabilized. Likewise, `balance[asset]` reads of an AA's own or another AA's live balance reflect the instantaneous, unconfirmed state produced mid-chain. This is functionally identical in root cause to the reported Curve issue: a price source is read directly from mutable, not-yet-finalized on-chain state within one atomic execution, with no TWAP or staleness/stability guard, letting an attacker manipulate the "oracle" and the price consumer in the same atomic operation.

### Finding Description
The `data_feed` opcode is evaluated in `formula/evaluation.js` and delegates to `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ...)`, passing the AA-evaluation flag `bAA` as the `unstable_opts` parameter: [1](#0-0) 

Inside `readDataFeedValue`, when `bIncludeUnstableAAs` (i.e. `bAA`) is truthy, the function additionally scans `storage.assocUnstableMessages` for `data_feed` messages authored by the oracle address(es), with no requirement that the authoring unit be stable or even fully validated yet — only that it is in the designated oracle list and passes basic sequence checks: [2](#0-1) 

This is intentional so that an AA acting as its own "oracle" can post a price via a `data_feed` message and have a *different* AA consume that same value later in the same secondary-trigger cascade — all before the encompassing unit is stabilized on the DAG. `aa_composer.js`'s `handleSecondaryTriggers` explicitly supports arbitrarily deep chains of AA-to-AA calls triggered from outputs of a single unit, executed synchronously and atomically as part of processing that one unit: [3](#0-2) 

If an "oracle AA" in this chain derives its posted price from mutable state that the attacker can shift within the same chain (e.g., its own or another AA's `balance[asset]` — the same pattern ocore's own shipped sample `uniswap_like_market_maker.oscript` uses: `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]`), then a single crafted unit can:
1. Send a large swap/deposit to the AMM/oracle-producing AA to skew its balance ratio.
2. Have that AA (or a chained AA) post the skewed ratio as a `data_feed` value or expose it via `balance[]`/getter reads.
3. Trigger, in the same unit's secondary-trigger cascade (still unstable, still uncommitted to the DAG), a second AA (e.g., a lending/liquidation/valuation AA) that consumes this manipulated, momentary price via `data_feed[[...]]` or `balance[...]` to mint, lend, or liquidate at an incorrect valuation.
4. Unwind the initial swap in the same or a follow-up secondary trigger, restoring the pool to its original state.

Because steps 1–4 all execute atomically within `handleTrigger`/`handleSecondaryTriggers` for one posted unit (or are rolled back together via `revert()` on any failure), this is architecturally the same atomicity primitive that a flash loan provides on EVM chains: manipulate → exploit → restore, all-or-nothing, in one transaction, with no intervening stabilization or TWAP smoothing.

### Impact Explanation
Any AA design that uses another AA's live `balance[]` ratio or a same-chain `data_feed` post as a price oracle (a pattern ocore's own documentation/sample AAs, e.g. `uniswap_like_market_maker.oscript`, `sell_asset_for_bytes.oscript`, `futures_contract.oscript`, encourage) inherits an intra-unit price-manipulation surface. This can lead to AA fund loss (mispriced issuance/redemption, wrongful liquidation, under-collateralized minting) — a concrete, unauthorized-spending/fund-loss outcome reachable by any unprivileged unit poster who funds the attack unit, matching the accepted impact classes (AA fund loss).

### Likelihood Explanation
Likelihood is Low-to-Medium and conditional: it requires an AA design that (a) chains a price-producing AA and a price-consuming AA within one unit's secondary-trigger cascade, and (b) the price-producing AA derives its value from within-chain mutable balance/state rather than only from previously-stabilized, externally-attested data. Ocore's own sample AAs demonstrate exactly this at-risk pattern, so it is a realistic design an unsophisticated AA author could deploy; funds are then reachable by any unprivileged unit poster who can afford the bounce fees and the swap capital for one unit.

### Recommendation
- Document explicitly (and where possible enforce/lint at `aa_validation.js` time) that `data_feed[[...]]` values sourced from unstable/unconfirmed AA-authored messages (`bIncludeUnstableAAs` path in `data_feeds.js`) must not be treated as manipulation-resistant price oracles, and that consumer AAs should prefer stable (`min_mci`-gated, already-stabilized) data feeds for financial decisions.
- Consider adding an oscript-level primitivive or guidance for time-weighted/multi-sample price reads (analogous to TWAP) when a price is derived from another AA's `balance[]`/state within the same DAG, rather than a single instantaneous read.
- For AMM-style reference AAs shipped with ocore (`test/samples/uniswap_like_market_maker.oscript`), add an explicit warning comment that other AAs must not treat its `balance[]` ratio as a manipulation-safe oracle without external stabilization/averaging.

### Proof of Concept
Conceptual sequence (cannot be fully executed without a live oscript AA pair, but each step is grounded in code referenced above):
1. Deploy `OracleAA`, whose response reports `price = balance[$asset] / balance[base]` of itself (or an AMM AA) via a `data_feed`-style `state`/`data` message, with `OracleAA` set as the `oracles` param of `ConsumerAA`.
2. Deploy `ConsumerAA`, which on trigger reads `data_feed[[oracles=OracleAA, feed_name='price', ...]]` (evaluated with `bAA=true`, hitting the unstable-message branch in `data_feeds.js:211-249`) to mint/lend/liquidate.
3. Attacker composes a single unit with outputs: (a) a large payment to `OracleAA` skewing its balance ratio, chained via secondary trigger to (b) a payment to `ConsumerAA`, which immediately reads the now-skewed price mid-chain (all within `handleSecondaryTriggers`, `aa_composer.js:1702-1756`, before the unit itself is stable), then (c) a follow-up trigger unwinding the initial swap back through `OracleAA`.
4. All operations commit atomically for the one posted unit (or all roll back together via `revert()`), giving the attacker an all-or-nothing manipulate-and-exploit primitive equivalent to a flash loan attack.
