### Title
CCMenuController bypasses stack-scoped ApiClient authorization, allowing cross-tenant stack read - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping via `#stacks` (`Stack.where(id: current_api_client.stack_id)`), which every properly scoped controller must resolve `params[:stack_id]` through. `Shipit::Api::CCMenuController#stack` instead resolves `Stack.from_param!(params[:stack_id])` directly against the unrestricted `Stack` relation, so any valid token (even one scoped to a single, attacker-owned stack) can read the CCTray status XML of any stack on the instance.

### Finding Description
The intended binding is: for a stack-scoped `ApiClient`, `requested_stack ∈ Stack.where(id: current_api_client.stack_id)` must hold before any stack data is rendered. `BaseController#stacks`/`#stack` implement exactly this: [1](#0-0) .

`CCMenuController` overrides `#stack` and does not call `stacks.from_param!`; it calls `Stack.from_param!(params[:stack_id])` on the entire `Stack` table: [2](#0-1) .

`require_permission :read, :stack` only checks that the token's `permissions` array contains the string `"read:stack"` — it never checks `stack_id` at all: [3](#0-2) . Authentication for this controller is also overridden to accept the token via the `token` query param instead of Basic Auth, but this still resolves the same `ApiClient` record with its `stack_id`: [4](#0-3) .

Exploit flow: attacker legitimately creates/obtains an `ApiClient` token scoped to their own stack with `read:stack` permission (this is the standard, supported way to get a CCMenu URL for a stack, per `app/controllers/shipit/ccmenu_url_controller.rb` / stack settings UI). They then send `GET /api/stacks/:victim_stack/cc_menu.xml?token=<their_token>`. `authenticate_api_client` succeeds (token is valid, sets `@current_api_client` with `stack_id = attacker_stack.id`). `require_permission!(:read, :stack)` passes because the token has `read:stack`. `#show` calls `#stack`, which resolves `victim_stack` directly, ignoring `current_api_client.stack_id`. The response renders `victim_stack`'s deploy/task status via the `shipit/ccmenu/project` XML view. Existing guards (`require_permission!`, `ExplicitParameters`, model validations) do not check stack ownership; only `BaseController#stacks` does, and this controller does not use it.

### Impact Explanation
An attacker with any legitimately-issued, stack-scoped CCMenu token can enumerate/read build and deploy status (stack name, latest deploy/rollback id, running/success/failure state, timestamps) for any stack on the Shipit instance, including private repositories/orgs they have no access to. This is repeatable for arbitrary `stack_id`/`repo/env` combinations by simply changing the URL path, with no additional secrets required. This matches the "High - unauthorized read of stack state" impact category (deploy/task status disclosure across tenants), not full RCE or write access, since CCMenu is read-only status XML.

### Likelihood Explanation
Preconditions are trivial to satisfy: an attacker needs a Shipit account/permission to create one stack-scoped CCMenu token for a repository they legitimately administer (a normal, supported workflow via the stack settings CCMenu URL). No GitHub secrets, `api_clients_secret`, or elevated Shipit role is required beyond owning one stack. The victim stack ID is guessable/enumerable (sequential integer or known slug from `owner/repo/environment`). This is a low-cost, fully repeatable attack against any target stack.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped relation, e.g. `@stack ||= stacks.from_param!(params[:stack_id])` (using the inherited `#stacks` method), so stack-scoped tokens can only ever resolve their own stack, consistent with `StacksController` and other API controllers.

### Proof of Concept
Minitest controller test plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create `attacker_stack` and `victim_stack` (different repositories).
2. Create an `ApiClient` with `stack_id: attacker_stack.id`, `permissions: ['read:stack']`.
3. Assert the binding before the request: `assert_not_includes Stack.where(id: api_client.stack_id), victim_stack`.
4. `get shipit.api_stack_cc_menu_path(victim_stack), params: { token: api_client.authentication_token, format: :xml }`.
5. Assert `response.status == 200` and response body contains `victim_stack.repository.full_name` / deploy info — demonstrating the scoped token read a stack outside `Stack.where(id: current_api_client.stack_id)`, proving the authorization bypass.
