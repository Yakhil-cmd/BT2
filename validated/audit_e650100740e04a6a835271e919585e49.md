### Title
Cross-organization webhook forgery via mismatched signature-selection key and processing key - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In the multi-GitHub-app configuration (`github: { OrgOne: {...}, OrgTwo: {...} }`), each organization has its own `webhook_secret` used to verify inbound webhook HMAC signatures [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to check against using a value taken directly from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`), not from any value bound cryptographically to the signature itself: [2](#0-1) . Once the signature is accepted, the actual event handlers (e.g. `PushHandler`, `StatusHandler`) resolve the target `Repository`/`Stack`/`Commit` using a *different* field of the same attacker-controlled body: `repository.full_name` [3](#0-2) , and `Commit.where(sha: params.sha)` matched across all stacks [4](#0-3) .

### Finding Description
The trust binding that should hold is: **organization whose secret authenticated the HMAC == organization/repository whose state is mutated by the handler**. Because the HMAC is computed over the *entire raw body* with a per-organization secret, anyone who legitimately possesses one organization's `webhook_secret` (e.g. an org admin installing their own GitHub App integration, or a webhook secret leak scoped to org A) can construct an arbitrary JSON payload, sign it with org A's secret, and set:
- `repository.owner.login` = `"OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` selects `Shipit.github(organization: "OrgA")` and the HMAC check passes, and
- `repository.full_name` = `"OrgB/victim-repo"` (any other org's repo actually configured in Shipit) so the handler processes state changes for a repository/stack the attacker has no relationship to.

`verify_signature` never checks that `repository.owner.login`/`organization.login` matches `repository.full_name`'s owner segment, and `Handler#repository_name` never checks it against the org whose secret validated the request [5](#0-4) [6](#0-5) . This is exactly the "organization that authenticated versus the repository that is written" mismatch.

Concretely, `StatusHandler` writes a `CommitStatus` for any `Commit` matching `params.sha` regardless of which stack/repo it belongs to [4](#0-3) , and commit statuses feed into deployability checks used to gate deploys/merges. `PushHandler` triggers `stack.sync_github` for any stack matching the forged `repository.full_name`/branch [7](#0-6) .

### Impact Explanation
An attacker who controls (or has leaked) org A's `webhook_secret` can forge signed webhook deliveries that are processed as if they originated from org B, letting them inject fabricated commit statuses (potentially marking unreviewed/malicious commits as passing checks) for any stack configured in the same Shipit instance, and trigger `sync_github` for other organizations' stacks. Forged/forced "success" commit statuses can enable an unauthorized deploy of code that has not actually passed CI/review, matching the "unauthorized deploy" Critical/High impact category.

### Likelihood Explanation
Requires possession of a legitimate `webhook_secret` for at least one configured GitHub organization on a multi-org Shipit deployment — this is a real deployment configuration documented in `docs/setup.md`, and having one org's secret (e.g. via an org admin who is not fully trusted, or leaked configuration) is a materially weaker requirement than compromising the target org's own secret. No `ApiClient` token, GitHub App private key, or `github_access_token` is needed.

### Recommendation
Bind the signature-verification key deterministically to the value used by handlers to select the target repository: verify the webhook using the organization derived from the same `repository.full_name` owner segment that `Handler#repository_name` uses, and reject if `repository.owner.login`/`organization.login` doesn't match the owner encoded in `repository.full_name`. Alternatively, look up the `Repository` record first (by `full_name`), derive its configured GitHub App/secret from `Repository#owner`, and verify against that — never let an attacker-chosen field pick which secret authenticates a request whose effects target a different attacker-chosen field.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s [8](#0-7) .
2. As someone who knows `OrgA`'s `webhook_secret` only, craft a `status` webhook JSON body: `{"sha": "<victim-commit-sha-in-OrgB-repo>", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, body)`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature check succeeds because it was signed with `OrgA`'s secret [9](#0-8) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit belonging to `OrgB/victim-repo` — and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `"success"` status for an `OrgB` commit despite never having `OrgB`'s webhook secret [4](#0-3) .

**File:** app/controllers/shipit/webhooks_controller.rb (L24-62)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
