### Title
`OpenedHandler#provision?` skips the `review_stacks_enabled` check for the `prevent_with_label` branch, allowing unauthorized ReviewStack provisioning - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` in `OpenedHandler` uses Ruby operator precedence (`&&` binds tighter than `||`) so `repository.review_stacks_enabled` is only ANDed with the first `allow_all?` disjunct, not with the `allow_with_label?` or `prevent_with_label?` disjuncts. As a result, a repository configured with `provisioning_behavior: :prevent_with_label` and `review_stacks_enabled: false` will still provision a `ReviewStack` for any PR opened without the provisioning label.

### Finding Description
The claimed binding is: the operator-set flag `repository.review_stacks_enabled` (intended to gate all provisioning behaviors) should equal the flag actually consulted for the `prevent_with_label` branch of `provision?`. Tracing the code: [1](#0-0) 

Due to Ruby precedence this evaluates as:
```
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
The third disjunct — the `prevent_with_label` branch — never references `review_stacks_enabled`. So for a repo with `provisioning_behavior: :prevent_with_label` and `review_stacks_enabled: false`, if a PR is opened without the provisioning label, `provision?` still returns `true`. The two sides of the binding (operator's intended gate vs. code's actual gate) diverge for this specific behavior.

`process` then calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which calls `create!`, persisting `stack_attributes[:branch] = params.pull_request.head.ref` (the attacker's own branch name, fully attacker-controlled) and `environment: "pr#{params.number}"`, then enqueues the stack via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

Existing guards do not prevent this: `params` schema validation only checks payload shape, not authorization; `review_stacks_enabled` is intended as the master on/off switch per `docs/review_stacks.md` and the settings UI (`app/views/shipit/repositories/settings.html.erb`), but the code never applies it to the `prevent_with_label` (or `allow_with_label`) branches. There is no separate check downstream in `ReviewStackAdapter` or `Repository` that re-verifies `review_stacks_enabled` before creating the stack.

The attacker's request: open (or push to) a pull request on a public/tracked repository configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`, without adding the provisioning label, then have the resulting `pull_request.opened` GitHub webhook delivered to `POST /webhooks` (a normal, unprivileged action any PR author can trigger — no forged signature needed since it's a genuine GitHub-originated event).

### Impact Explanation
This creates a `Shipit::ReviewStack`/`Shipit::Stack` record for a repository whose operator explicitly disabled review-stack provisioning (`review_stacks_enabled: false`), with `branch` set to the attacker's PR head ref. The stack is queued via `ReviewStackProvisioningQueue`, which subsequently drives `Command#start`-based provisioning steps (e.g., running `shipit.yml` provision steps) against attacker-controlled branch content. This matches the "unauthorized deploy" class of Critical impact: a record/command execution triggered for a repository that opted out, using unvalidated attacker-supplied branch data. It is repeatable against any repository configured with `prevent_with_label` + `review_stacks_enabled: false`, and, notably, also silently breaks the `allow_with_label` branch in the opposite direction (that branch too ignores `review_stacks_enabled`).

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false` — a plausible, even intuitive, misconfiguration for an operator who wants "prevent unless labeled" semantics while nominally believing the master toggle is off. Attacker cost is trivial: open a normal PR without the label. No secrets, sessions, or elevated GitHub permissions are needed — any external contributor who can open a PR against the repo satisfies this.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every disjunct:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (out of scope per rules for modification, but proof plan):
```ruby
test "does not create stacks when review_stacks_enabled is false even for prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # no provisioning label

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Given the current implementation, this assertion fails: `Shipit::Stack.count` increases by 1, proving `provision?` returns `true` despite `repository.review_stacks_enabled == false`, confirming the binding divergence.
