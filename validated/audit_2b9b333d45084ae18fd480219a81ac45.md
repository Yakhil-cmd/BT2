### Title
Api::CCMenuController bypasses ApiClient stack scoping, allowing a stack-scoped token to read the state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The reported MagicLP bug is a mismatch between the amount a user authorized (`baseInAmount`/`quoteInAmount`) and the amount actually spent, because the code that recomputed the "adjusted" amount used the wrong operands. The analogous binding in shipit-engine is: **the stack an `ApiClient` token is authorized for (`ApiClient#stack_id`) must equal the stack whose state is actually returned**. `Api::CCMenuController` breaks this equality by resolving the target stack directly from client-supplied params instead of through the scoped lookup used everywhere else in the API.

### Finding Description
`Shipit::Api::BaseController` implements permission checks (`check_permissions!`) which only verify that a permission string like `"read:stack"` is present on the token — they never verify which stack the permission applies to. The actual per-stack restriction is enforced by a separate mechanism, the `stacks` scope: [1](#0-0) [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Every other API controller that resolves a stack from `stack_id` relies on this `stacks`-scoped lookup, e.g. `Api::StacksController#stack` uses `stacks.from_param!(params[:id])`: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass the `stacks` scope entirely and looks the record up directly from the unscoped `Stack` model using the raw `params[:stack_id]`: [3](#0-2) 

```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` only checks that the permission string is present: [4](#0-3) 

An `ApiClient` can be scoped to a single stack via `ApiClient#stack_id` (e.g. tokens created through `Shipit::CCMenuUrlController#client`, which is explicitly created with `permissions: %w[read:stack]` and scoped to one stack): [5](#0-4) 

Because `CCMenuController#show` calls the overridden `stack` method instead of the scoped one, a token that is only supposed to authorize reading one stack's state can be presented with a *different* `stack_id` in the URL and will still succeed, since nothing checks `current_api_client.stack_id == stack.id`.

### Impact Explanation
This is the "stack a token authorizes versus a stack it touches" binding break called out in scope. It grants **unauthenticated/unauthorized read of stack state** (last deploy status, label, timestamp, web URL) for stacks the token holder was never granted access to — the exact "High" impact category defined for this analog (`escalation into ... unauthenticated read of stack state`). Any holder of a stack-scoped, `read:stack`-only CCMenu token (which are routinely embedded in third-party CI-status dashboards/tools, since that is the entire purpose of the CCMenu XML endpoint) can enumerate other stacks' build/deploy status by simply changing `stack_id` in the request path, without needing write access, a session, or any other privilege elevation.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API clients (as `CCMenuUrlController` does by default for every user who fetches the CCMenu widget URL). Exploitation requires only a valid, low-privilege token (already obtainable through the documented "fetch CCMenu URL" feature) and knowledge/guessing of another stack's `stack_id`/slug — both of which are normal, unprivileged capabilities within the app; no session, GITHUB_TOKEN, or admin access is needed.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, properly-scoped `stack` method from `BaseController` (`stacks.from_param!(params[:stack_id])`), so the stack lookup is restricted to `current_api_client.stack_id` when the client is stack-scoped, consistent with every other API controller.

### Proof of Concept
1. `CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` scoped to `stack: shipit_prod`, with `permissions: %w[read:stack]`, and returns its `authentication_token`.
2. An attacker who obtains this token (e.g. it is embedded in a publicly reachable CI dashboard widget, which is the documented use case for this token) issues:
   `GET /api/other-org/other-secret-stack/ccmenu.xml?token=<the scoped token>`
3. `authenticate_api_client` (CCMenuController's override) accepts the token via query string and sets `@current_api_client`.
4. `require_permission :read, :stack` passes because the token has the `read:stack` string, regardless of which stack.
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks` scoping), returning `other-secret-stack` even though the token is scoped to `shipit_prod`.
6. The response renders `latest_deploy` and stack metadata for `other-secret-stack`, which the token was never authorized to read.
