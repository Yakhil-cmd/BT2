### Title
Unauthenticated forged `membership` webhook lets an attacker plant a fake `Team` that hijacks `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The `amAmm::cancelNextBid` bug binds a validity check (`topBid.deposit/topBid.rent`) to a completely different quantity than the one actually enforced against the caller (`nextBid`'s ability to cancel). The same class of "checked-field vs. acted-on-field" mismatch exists in Shipit's webhook trust boundary: `WebhooksController#verify_signature` selects *which* GitHub App/secret to authenticate against using `repository.owner.login` / `organization.login` (an attacker-supplied JSON field), while the business logic that actually creates/writes persistent authorization state (`Shipit::Webhooks::Handlers::MembershipHandler`) trusts a *different*, unverified field — the numeric `team.id` and `member.login` in the same payload — to create or reuse a `Team` row that later becomes an authorization decision in `Shipit.github_teams`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to check the signature with, based on attacker-controlled payload data: [1](#0-0) [2](#0-1) 

That verification is not a proof that the payload's contents actually originate from GitHub for any particular organization/team when the `webhook_secret` for the selected app is left blank — a state explicitly documented and shipped as the default in Shipit's own example configs: [3](#0-2) [4](#0-3) 

When `webhook_secret` is unset, `verify_webhook_signature` returns `true` unconditionally, regardless of the `X-Hub-Signature` header or body content — i.e., no credential is required at all to reach `Webhooks.for_event(event).each { |handler| handler.call(params) }`.

The `membership` event is dispatched to `MembershipHandler`, which trusts entirely attacker-controlled fields (`team.id`, `team.name`, `team.slug`, `organization.login`, `member.login`) to find-or-create a `Team` record and add a member to it, with **no cross-check against GitHub**: [5](#0-4) 

Crucially, `Team.find_or_create_by!(github_id: params.team.id)` keys off an attacker-chosen `github_id` — a number that has no verified relationship to the `organization`/`slug` the attacker also supplies. Meanwhile, the actual authorization gate — `Shipit.github_teams` — resolves each configured team **by `organization` + `slug`**, not by `github_id`: [6](#0-5) [7](#0-6) 

And `User#authorized?` checks team membership purely by the `Team` row's DB id: [8](#0-7) 

This is the exact binding mismatch called out in the report's rule set: the field used to authenticate the webhook (`organization.login` used to pick the app/secret) is disjoint from the field that is actually written and later trusted for a security decision (`team.id`, `slug`, membership rows created via `team.add_member(member)`), analogous to how `topBid.deposit/topBid.rent` was checked while `nextBid`'s own deposit was the thing actually needed to enforce the invariant.

### Impact Explanation
If `Shipit.github_teams` has not yet memoized the real `Team` for a configured handle (e.g. right after a deploy/restart, before `teams:fetch` or any legitimate `membership`/OAuth flow has run), an attacker can:
1. POST a forged `membership` webhook (`action: "added"`) with `organization.login` matching a configured org whose `webhook_secret` is unset/blank, `team = {id: <arbitrary>, slug: <slug of a team listed in Shipit's `oauth.teams` config>, name: ..., url: ...}`, and `member.login` = the attacker's own GitHub login.
2. `MembershipHandler#process` creates a `Team` row with the attacker-chosen `github_id` but real-looking `organization`/`slug`, and immediately adds the attacker as a `Membership`.
3. When `Shipit.github_teams` is later computed, `Team.find_or_create_by_handle` resolves the configured handle via `find_by(organization:, slug:)` and returns this attacker-created row (since it already matches on `organization`+`slug`) instead of fetching the genuine team from GitHub.
4. The attacker completes a normal GitHub OAuth login (with their real GitHub identity) and passes `current_user.authorized?`, because their `User` row is a member of the `Team` id that now backs `Shipit.github_teams`.

This is an escalation into `Shipit.github_teams` authorization performed by an unprivileged, unauthenticated party — one of the explicitly in-scope High-impact categories. It grants access to the entire Shipit UI/API (stacks, deploys, tasks, rollbacks) that is otherwise gated behind GitHub-team membership, without any credential, without repository write access, and without a Shipit session.

### Likelihood Explanation
Likelihood is Medium: the primary exploitation path depends on winning a timing/ordering race — the attacker's forged `Team` row must be the first row Shipit resolves for a given `organization`/`slug` handle (i.e., before the real GitHub-backed team has been fetched via `teams:fetch` or via a genuine `membership` webhook). This window realistically exists after deploys/restarts of long-lived Rails processes (since `Shipit.github_teams` memoizes via `@github_teams ||=` for the life of the process) and in any environment where `webhook_secret` is left blank — which is the exact configuration shown in Shipit's own shipped example secrets files. No attacker credentials, GitHub App keys, or Shipit sessions are required to send the forged webhook itself.

### Recommendation
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank; require an explicit, documented opt-in (and log/alert loudly) for unauthenticated webhook ingestion, or refuse to process security-sensitive events (`membership`) without a configured secret.
- In `MembershipHandler#find_or_create_team!`, do not trust the attacker-supplied `team.id`/`organization`/`slug` triple as sufficient to create or reuse authorization-relevant `Team` records; verify team/organization membership against the GitHub API (as `Team.refresh_members!` and `fetch_and_create_from_github` already do) rather than trusting webhook payload fields directly.
- Add a uniqueness constraint on `(organization, slug)` for `Team` so a forged `github_id` cannot create a colliding, attacker-controlled row that shadows a real team.

### Proof of Concept
1. Deploy Shipit with a config where one configured GitHub org's `webhook_secret` is left blank (the shipped default, e.g. `config/secrets.development.example.yml`), and `oauth.teams` includes `"someorg/admins"`.
2. Before any real membership sync has occurred for `someorg/admins` in this process's lifetime, POST to the webhooks endpoint with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 999999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999999"},
  "organization": {"login": "someorg"},
  "member": {"login": "attacker-github-login"}
}
```
No valid `X-Hub-Signature` header is required because `webhook_secret` is blank for `someorg`, so `verify_webhook_signature` short-circuits to `true` (`lib/shipit/github_app.rb:77`).
3. `MembershipHandler#process` creates `Team(github_id: 999999, organization: "someorg", slug: "admins")` and adds `User(login: "attacker-github-login")` as a member.
4. Attacker logs into Shipit via the normal GitHub OAuth flow using their real `attacker-github-login` account.
5. `Shipit.github_teams` resolves `"someorg/admins"` via `find_by(organization: "someorg", slug: "admins")`, returning the attacker-planted `Team`; `current_user.authorized?` returns `true`, granting the attacker full access to Shipit despite never having been a genuine member of the real `someorg/admins` GitHub team.

      return true unless webhook_secret

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
