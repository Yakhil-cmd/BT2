### Title
Cross-organization forged commit status bypasses per-org webhook signing and can trigger unauthorized PR merges - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against using an *organization* value taken from the unverified JSON body (`repository.owner.login`, falling back to `organization.login`), while the actual write performed by `StatusHandler` is scoped only by commit `sha` — with no repository or organization check at all. This breaks the intended binding "GitHub App/organization that authenticated the request" == "repository/stack that gets written to."

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the attacker-supplied payload and uses it to pick which per-organization `webhook_secret` to verify the HMAC signature against: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple independent GitHub Apps/organizations sharing one Shipit instance, each with its own `webhook_secret`, as documented and tested: [3](#0-2) [4](#0-3) 

Once the signature check passes (using whichever org's secret matches the attacker-chosen `repository_owner` field), the whole raw JSON body is dispatched to handlers: [5](#0-4) 

`StatusHandler#process`, however, does **not** consult `repository`/organization at all. It looks up commits purely by `sha` across the entire database, with no scoping to the repository or organization that was actually authenticated: [6](#0-5) 

This directly breaks the equality the engine should enforce: `organization authenticated by verify_signature` == `organization/repository whose commit is written by StatusHandler`. Since `sha` is an attacker-controlled string field in the JSON payload (not cryptographically tied to the signed organization), an attacker who merely knows/owns the webhook secret for **any one** organization configured in the shared Shipit instance can forge a `status` event that is validly signed for their own org, but whose `sha` names a commit belonging to a completely different (victim) organization's stack.

`Commit#create_status_from_github!` → `add_status` then applies the forged status to that commit and, on `success`/`pending`, schedules merges for the stack that actually owns that commit: [7](#0-6) 

`ProcessMergeRequestsJob` then evaluates `all_status_checks_passed?` using the (forged) status and calls `merge_request.merge!`, which invokes GitHub's merge API using the **victim stack's own** GitHub App credentials: [8](#0-7) [9](#0-8) [10](#0-9) 

This is the same bug class as the Sherlock report: a value used to satisfy an authorization/verification gate (the `totalCollateral` used for the fee check vs. the actual current balance; here, the organization used to select the signing secret) is not the same value that is ultimately acted upon (the actual repository/stack whose state is mutated), so the check silently applies to the wrong scope.

### Impact Explanation
An attacker who controls (or has legitimately obtained webhook credentials for) any single organization hosted on a multi-organization Shipit deployment can forge commit statuses for arbitrary commits belonging to any other organization/stack in the same instance. Because Shipit's merge queue treats a forged "success" status as satisfying CI requirements, this can cause `MergeRequest#merge!` to merge a pull request in a victim repository the attacker has no legitimate access to, using Shipit's own privileged GitHub App token for that org. This is an unauthorized merge / cross-repository write, matching the Critical impact bar ("cross-repository writes ... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented and supported) and requires the attacker to know/guess a target commit's SHA in the victim's stack, which is typically public GitHub information (visible via PRs/commits on GitHub.com) even though the attacker has no write access to that repository. No GitHub App private key, `api_clients_secret`, or Shipit session is required — only a valid webhook secret for any one configured (potentially low-trust) organization.

### Recommendation
Bind the verified organization to the data being written: after `verify_signature` resolves `repository_owner`, pass that resolved organization/repository context into the handler dispatch, and have `StatusHandler` (and any other handler that looks up records independent of `repository.full_name`) scope its `Commit`/`Stack` lookup to repositories belonging to the verified organization only, rejecting or ignoring any match outside that scope.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` (attacker-controlled) and `OrgB` (victim), per the documented multi-org config.
2. Attacker discovers, via GitHub.com, the SHA of the head commit of an open pull request tracked by a Shipit stack under `OrgB` that has `merge_queue_enabled: true`.
3. Attacker crafts a `status` webhook JSON body: `{"sha": "<OrgB commit sha>", "state": "success", "context": "<OrgB's required CI context>"}` and signs it with `OrgA`'s `webhook_secret` (computed via `OpenSSL::HMAC.hexdigest('sha1', orgA_secret, body)`), setting `X-Github-Event: status` and (optionally) `repository.owner.login = "OrgA"` so `verify_signature` resolves and validates against `OrgA`'s secret.
4. POST to the webhooks endpoint. `verify_signature` passes (OrgA's secret matches OrgA's signature). `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgB commit, and applies the forged "success" status via `create_status_from_github!`.
5. `add_status` calls `stack.schedule_merges`, enqueuing `ProcessMergeRequestsJob` for the OrgB stack; if other required checks are already satisfied, `merge_request.merge!` merges the PR in OrgB's repository using Shipit's OrgB GitHub App credentials — an unauthorized cross-org merge triggered entirely by an OrgA-signed webhook.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
  end
```

```ruby
    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
```

```ruby
    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
```
