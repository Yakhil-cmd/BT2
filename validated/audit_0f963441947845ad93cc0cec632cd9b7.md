### Title
Webhook signature verified against the payload's `repository.owner.login` while the acted-upon Stack is selected via `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or the top-level `organization.login`) from the untrusted JSON body, while `Shipit::Webhooks::Handlers::Handler#repository_name` — used by every handler (e.g. `PushHandler`) to look up the `Stack`/`Repository` to mutate — reads a *different*, independently-attacker-controlled field of the same body: `repository.full_name`. Nothing enforces that `repository.full_name` actually belongs to `repository.owner.login`. This mirrors the StrongBlock pattern of "authority checked against one identity, action performed against another": the org whose secret authenticates the payload is never bound to the repository the payload is used to act on.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
```
`repository_owner` is derived purely from the JSON body: [2](#0-1) 

Shipit natively supports one distinct GitHub App / `webhook_secret` per organization (`lib/shipit/github_app.rb` initializes each `GitHubApp` from a per-organization config block including `webhook_secret`), so `repository_owner` selects *which secret* is checked against the HMAC: [3](#0-2) 

Once the signature is accepted, `create` dispatches the *entire raw payload* to handlers: [4](#0-3) 

But every handler resolves the target `Stack`(s) via `repository.full_name`, an entirely separate field of the same payload, with no re-validation that it corresponds to the organization used above: [5](#0-4) 

`PushHandler` then uses this unchecked lookup to enqueue writes against the resolved stacks: [6](#0-5) 

`GithubSyncJob` performs real database writes on the target stack — creating `Commit` rows, toggling `mark_as_accessible!`/`mark_as_inaccessible!`, and invoking `lock_reverted_commits!` — based solely on this cross-tenant, unauthenticated-for-that-repo lookup: [7](#0-6) 

**The binding that is broken:** `organization authenticated by verify_webhook_signature (repository.owner.login) == organization/repository the handler acts on (repository.full_name)`. Nothing in the codebase enforces this equality; the two fields are read independently from the same untrusted body.

### Impact Explanation
In a multi-organization Shipit deployment (explicitly documented and supported via `lib/shipit/github_app.rb`'s per-organization config), an entity that legitimately owns/administers **its own** organization's GitHub App (and therefore genuinely knows that org's `webhook_secret`) can POST a self-crafted payload to the shared `/webhooks` endpoint with:
- `repository.owner.login` / `organization.login` = their own org (so `verify_webhook_signature` succeeds using the secret they legitimately possess), and
- `repository.full_name` = a **different** organization's repository that Shipit also tracks.

Because `Handler#repository_name` trusts `repository.full_name` unconditionally, this forges cross-tenant actions against a `Stack` belonging to an organization the attacker has no relationship or credentials for: forced `GithubSyncJob` runs, `Commit` record creation, accessibility-state flips, and reverted-commit locking on someone else's stack. This is a cross-repository write performed by an entity with no access to the victim organization at all, matching the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Any tenant configured under Shipit's documented multi-organization GitHub App support already possesses everything required (their own genuine `webhook_secret`) and needs only to send one crafted HTTP POST with mismatched `owner.login`/`full_name` fields — no stolen credentials, no privileged Shipit account, and no interaction with the victim organization. The disconnect between `verify_signature`'s org selection and `Handler#repository_name`'s repository selection is a straightforward code-level oversight, not a race condition or theoretical edge case.

### Recommendation
After computing `repository_owner` for signature verification, thread that same verified organization value into the handler dispatch and require `Handler#repository_name`'s owner segment to equal it before resolving `Repository.from_github_repo_name`. Concretely, `WebhooksController#create` should pass `repository_owner` alongside `params` to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_owner: repository_owner) }`, and `Handler#repository_name`/`#stacks` should reject (or scope the lookup) unless `payload.dig('repository', 'owner', 'login') == verified_owner`.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App / `webhook_secret` (per documented multi-org support in `lib/shipit/github_app.rb`).
2. As the legitimate owner/admin of `attacker-org`'s GitHub App, compute a valid `X-Hub-Signature` HMAC over a crafted JSON body using `attacker-org`'s real `webhook_secret`:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. POST this to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and succeeds (attacker's own secret matches).
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and enqueues `GithubSyncJob` against `victim-org`'s stack, writing `Commit` rows and mutating stack accessibility state — despite the attacker having no relationship with `victim-org`.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
