### Title
`review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning due to `&&`/`||` operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends to require `repository.review_stacks_enabled == true` for all auto-provisioning paths, but Ruby's operator precedence makes `&&` bind tighter than `||`, so `review_stacks_enabled` only gates the `allow_all` branch. An attacker who can add a label matching `repository.provisioning_label_name` to their own PR (per the stated threat model) can get a `ReviewStack` created even when the repository owner has disabled `review_stacks_enabled`.

### Finding Description
The intended invariant is: `provision? == true` **iff** `repository.review_stacks_enabled == true AND <behavior-specific condition>`. The actual code in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

is parsed as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is only ANDed into the first disjunct; the second and third disjuncts (`allow_with_label` and `prevent_with_label`) are entirely independent of `review_stacks_enabled`. `respond_to_pull_request_opened?` calls only `provision?` with no separate top-level `review_stacks_enabled` check [2](#0-1) , unlike `LabeledHandler#respond_to_label_change?`, which correctly ANDs `repository.review_stacks_enabled` at the top level before delegating to `archive?`/`unarchive?` [3](#0-2) . The same precedence bug is duplicated in `ReopenedHandler#unarchive?` [4](#0-3) .

`pull_request_has_provisioning_label?` reads `pull_request_label_names.include?(repository.provisioning_label_name)`, where the label names come straight from the webhook payload's `pull_request.labels[].name` [5](#0-4) , and the label name attacker input is not otherwise validated against `review_stacks_enabled`.

Attack flow: repository owner sets `provisioning_behavior = allow_with_label` (or `prevent_with_label`) with a known/public `provisioning_label_name`, but sets `review_stacks_enabled = false` to disable auto-provisioning entirely. An attacker opens a PR from their fork and applies the matching label (label name is either public in `shipit.yml`/repo settings or guessable/enumerable). The `opened` webhook fires; `respond_to_pull_request_opened?` → `provision?` evaluates true via the second disjunct regardless of `review_stacks_enabled`, and `ReviewStackAdapter#find_or_create!` creates a `ReviewStack` for the attacker's branch/PR.

None of the existing guards catch this: `params` schema validation only validates payload shape, not authorization; `drop_unhandled_event`/signature verification only ensure the webhook is a legitimate GitHub event for that repo, not that provisioning is enabled; there is no model validation tying `provisioning_behavior` to `review_stacks_enabled`.

### Impact Explanation
A `ReviewStack` is created and provisioned for the attacker's branch on a repository whose owner explicitly disabled review-stack provisioning (`review_stacks_enabled = false`). Since provisioned stacks run Shipit tasks (checks/provision/deploy hooks) against the attacker-controlled branch/commit, this can lead to execution of attacker-influenced task/CI configuration on the deploy host, i.e., an unauthorized provisioning/deploy action the repository owner explicitly opted out of. This is repeatable against any repository configured with `allow_with_label` or `prevent_with_label` and `review_stacks_enabled: false`, and does not require any privileged credential — only the ability to label one's own PR, which is granted by the stated threat model.

### Likelihood Explanation
Preconditions: the target repository must use `provisioning_behavior: allow_with_label` (attacker needs to know/match the label) or `provisioning_behavior: prevent_with_label` (works with zero preconditions on labels, since absence of the label is the default state for an unlabeled fork PR) while `review_stacks_enabled` is `false`. The `prevent_with_label` case requires no special knowledge at all — a normal PR with no matching label already satisfies `!pull_request_has_provisioning_label?`, so bypass is essentially free whenever a repo is configured this way. Attacker cost is minimal (open a PR from a fork, optionally add a label) and the action is repeatable per PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`, and add a regression test asserting no stack/unarchive occurs when `review_stacks_enabled: false` regardless of behavior/label state.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` add:
```ruby
test "does not create stacks for allow_with_label when review_stacks_enabled is false, even with matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository: repository,
    provisioning_enabled: false,      # review_stacks_enabled = false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not create stacks for prevent_with_label when review_stacks_enabled is false, even without label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository: repository,
    provisioning_enabled: false,      # review_stacks_enabled = false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Against current code, both assertions fail (`Shipit::Stack.count` increases by 1), proving `review_stacks_enabled == false` does not prevent provisioning in the `allow_with_label`/`prevent_with_label` branches, contradicting the intended equality `provision? == (review_stacks_enabled && <behavior condition>)`.
