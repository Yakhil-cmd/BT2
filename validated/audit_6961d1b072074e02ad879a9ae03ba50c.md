### Title
Data-feed value/unit corruption via embedded delimiter breaks round-trip integrity of KV-stored feeds - (File: `data_feeds.js`, `main_chain.js`)

### Summary
`ocore` stores stable data-feed values in the key-value store as a single delimiter-joined string (`value + '\n' + unit`) and later reconstructs the value and its source unit by splitting on the same `'\n'` delimiter. Because a data-feed value is an attacker-controlled string that is never checked for embedded `'\n'` characters, an unprivileged unit poster can craft a data-feed value containing newline(s) so that when the record is re-parsed it splits into more parts than expected. This silently truncates the reported *value* and replaces the reported *unit* with an unrelated fragment — a structural round-trip instability conceptually equivalent to the REXML bug (data that is validated as one structure is reconstituted into a different structure on the next read), but here manifesting in the oracle/data-feed subsystem that AAs use to make trust decisions.

### Finding Description
When an MCI becomes stable, `addDataFeeds()` writes each data-feed's value into RocksDB with the unit hash appended after a `\n` separator: [1](#0-0) 

On read, `readDataFeedByAddress()` retrieves that raw string and blindly splits it on `'\n'`, taking `arrParts[0]` as the value and `arrParts[1]` as the unit: [2](#0-1) 

This function backs `readDataFeedValue()` / `readDataFeedValueByParams()`, which are the functions the `data_feed[[...]]` oscript operator (in `formula/evaluation.js`) and the `light/get_data_feed` network command use to fetch a data feed's `value` or its originating `unit`: [3](#0-2) [4](#0-3) 

Nowhere in the data-feed message validation path is the feed value checked for embedded `'\n'` (unlike `getSourceString`, which explicitly rejects strings containing the `STRING_JOIN_CHAR` `"\x00"` used as its own join delimiter): [5](#0-4) 

Because the data-feed value has no such restriction, a value like `"legit\nFAKE_UNIT_HASH_OR_GARBAGE"` will be stored verbatim as `"legit\nFAKE_UNIT_HASH_OR_GARBAGE\n<real_unit>"`. On read-back, `data.value.split('\n')` yields `["legit", "FAKE_UNIT_HASH_OR_GARBAGE", "<real_unit>"]`, so:
- `objResult.value` becomes only `"legit"` (silently truncated/altered from what was actually posted and hashed into the unit), and
- `objResult.unit` becomes `"FAKE_UNIT_HASH_OR_GARBAGE"` instead of the real unit that published the feed.

This is exactly the "round-trip instability" bug class from the report: the on-chain, validated/hashed representation of the data (the full string value inside the signed unit's `data_feed` message) differs from what is reconstructed after being serialized into and re-parsed out of the storage layer.

### Impact Explanation
AAs commonly use `data_feed[[oracles=X, feed_name=Y, what='unit']]` to fetch the unit that published an assertion, then cross-check that unit's contents (e.g., to build trustless bridges/oracles, verify signed statements, or gate payouts). If the returned `unit` can be corrupted to an attacker-chosen bogus value by embedding `'\n'` in a data-feed value, an AA's unit-based verification logic can be fed a wrong unit hash, and/or the reported `value` can silently differ from what was actually signed by the oracle. Any address (an unprivileged unit poster acting as its own or a colluding "oracle") can trigger this by simply posting a `data_feed` message with a value containing a newline. Depending on how the consuming AA uses the (`value`, `unit`) pair, this can lead to AA fund loss/misdirection or node disagreement between clients that read the raw DB record differently from what the original poster intended — a Medium-severity data-integrity defect in a component (`data_feed`) explicitly in scope.

### Likelihood Explanation
Any account can post a `data_feed` message inline in a unit; feed values are free-form strings with (per the reviewed validation code) no restriction against embedded `\n`. The corrupting condition triggers automatically the next time any node (light or full) queries that stable feed by unit or long-form value through `readDataFeedValueByParams`/`data_feed[[...]] what='unit'`, requiring no special timing or race — only that an AA or client relies on the `unit` (or full multi-line `value`) returned from this API.

### Recommendation
- Reject (during message/data-feed validation) any data-feed value string containing the `'\n'` (and ideally any control) character, mirroring the existing `"\x00"` rejection in `getSourceString`.
- Alternatively, change the KV storage format in `main_chain.js`/`data_feeds.js` to use a length-prefixed or otherwise unambiguous encoding for `value` + `unit` instead of a bare `'\n'`-joined string, so no legal value can shift the parse boundary.
- Add regression tests verifying that a data-feed value containing `\n` cannot alter the `unit` returned by `readDataFeedValueByParams`.

### Proof of Concept
1. Post a unit containing a `data_feed` message whose payload is `{ "myfeed": "legit\nDEADBEEF..." }` (a string value containing an embedded newline), signed by address `A`.
2. Wait for the unit to stabilize; `addBalls()`/`addDataFeeds()` in `main_chain.js` writes key `dfv\nA\nmyfeed\n<mci>` with value `"legit\nDEADBEEF...\n<real_unit>"`.
3. Call `data_feeds.readDataFeedValueByParams({oracles:[A], feed_name:"myfeed", what:"unit"}, ...)` (e.g., via `light/get_data_feed` or from an AA formula `data_feed[[oracles=A, feed_name='myfeed', what='unit']]`).
4. Observe that `readDataFeedByAddress` splits the stored string on `'\n'` and returns `objResult.unit = "DEADBEEF..."` instead of `<real_unit>`, and `objResult.value = "legit"` instead of the full posted string — demonstrating the round-trip corruption.

*Note: I was unable to fully trace the exact data-feed message validation function in `validation.js`/`formula/validation.js` that checks value contents (e.g., `isNonemptyString`/length limits) within the tool-call budget available, so I cannot 100% rule out an existing implicit restriction on `\n` in feed values elsewhere in the codebase. If such a restriction exists, this specific PoC would need to be re-verified against it; I recommend confirming this in a Devin session with full repository access before treating this as conclusively exploitable.*
