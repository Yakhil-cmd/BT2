### Title
Webhook signature is verified against an attacker-selectable organization while the mutated `Commit`/`Stack` is selected from a different field in the same unverified-for-consistency payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate the `X-Hub-Signature` against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the attacker-supplied JSON body, then hands the very same JSON body to the event handlers, which independently resolve the target `Repository`/`Commit`/`Stack` from `repository.full_name`. Nothing ties the "owner" used for authentication to the "full_name" used for the write.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
`verify_signature` computes `repository_owner` from the raw JSON (`params.dig('repository','owner','login') || params.dig('organization','login')`), fetches `Shipit.github(organization: repository_owner)`, and verifies the HMAC using that org's `webhook_secret`: [2](#0-1) 

Shipit explicitly supports one distinct GitHub App / `webhook_secret` **per organization** in a shared, multi-tenant deployment: [3](#0-2) 
and `Shipit.github_app_config` looks up the config purely by the organization name string: [4](#0-3) 

After the signature check passes, `create` parses the body and dispatches to handlers using the same JSON, unconstrained by which organization was authenticated: [5](#0-4) 

Every handler resolves the affected repository independently, from `repository.full_name`, via `Handler#stacks`: [6](#0-5) 

`StatusHandler` uses this to look up `Commit` **by SHA alone**, with no scoping to the authenticated organization, and writes a GitHub commit status directly from attacker-controlled fields (`state`, `description`, `context`, `target_url`): [7](#0-6) 

`PushHandler` similarly resolves stacks from `repository.full_name` and triggers a sync for any matching branch: [8](#0-7) 

**Broken equality:** organization authenticated by `verify_signature` (`repository.owner.login`/`organization.login`, checked against org **A**'s `webhook_secret`) ≠ organization/repository actually mutated (`repository.full_name`, resolved to org **B**'s `Repository`/`Stack`/`Commit`). Because both fields live in the same attacker-controlled JSON body and are never cross-checked, an attacker who legitimately administers org A's GitHub App on a shared multi-tenant Shipit instance (and therefore knows org A's `webhook_secret`, which is chosen and configured by the org admin in GitHub's own webhook UI) can self-sign an arbitrary payload with org A's secret while setting `repository.full_name` (and, for `StatusHandler`, `sha`) to point at org B's repository/commits.

### Impact Explanation
This crosses the `Shipit.github_teams`/organization authorization boundary and enables cross-repository writes: an attacker who is a legitimate admin of *one* tenant organization on a shared Shipit instance can forge commit statuses (`StatusHandler`) or push/sync events (`PushHandler`) against any *other* tenant's tracked repository, without ever having credentials or the `webhook_secret` for that other organization. Forged statuses can satisfy `required_statuses`/`blocking_statuses` merge/deploy gates defined in another team's `shipit.yml`, leading to an unauthorized deploy or merge on a repository the attacker does not control - meeting the "escalation into `Shipit.github_teams` authorization" / "unauthorized deploy, rollback or merge" bar.

### Likelihood Explanation
Requires the Shipit installation to be configured in the documented multi-tenant "Using Multiple Github Applications" mode (multiple orgs each with independent app_id/webhook_secret), and requires the attacker to be a legitimate GitHub organization admin/owner for at least one tenant org on that shared instance (able to set that org's webhook secret in the GitHub App settings). No repository write access, `ApiClient` token, or Shipit session is required — only knowledge of one's own org's webhook secret, which every onboarded tenant necessarily has. This is a realistic multi-tenant threat model explicitly documented and supported by the engine, not a theoretical one.

### Recommendation
- After signature verification, re-derive the organization/repository from the verified request context and reject/ignore any handler processing where `repository.full_name`'s owner segment does not match the organization whose secret validated the signature.
- In `Handler#stacks`/`StatusHandler#process`, scope `Commit`/`Repository` lookups to the authenticated organization (pass it down from the controller) instead of trusting `repository.full_name`/`sha` alone.
- Consider using per-organization webhook URLs (`/webhooks/:organization`) so the organization is bound by routing rather than by a field inside the signed-but-unchecked payload body.

### Proof of Concept
1. Configure Shipit in multi-tenant mode with `OrgA` (attacker-administered, `webhook_secret: secretA`) and `OrgB` (victim, tracked stack with `shipit.yml` requiring CI status `ci/tests`).
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<victim's blocked commit sha, e.g. leaked from OrgB's public PR/commit page>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(secretA, body)` — attacker legitimately knows `secretA`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, validates successfully against `secretA` ( [9](#0-8) ).
6. `StatusHandler#process` looks up `Commit.where(sha: ...)` — matching OrgB's commit — and writes a forged `success` status ( [7](#0-6) ), satisfying OrgB's merge/deploy safety check despite the attacker never authenticating as, or holding credentials for, OrgB.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
