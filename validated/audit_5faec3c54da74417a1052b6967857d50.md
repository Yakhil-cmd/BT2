### Title
Third-party dust supply bypasses the health-factor floor on risk-parameter restamping, enabling forced liquidation - (File: contracts/controller/src/positions/supply.rs)

### Summary
`controller::supply` intentionally grants third parties a grace path: any caller may top up a foreign account's *existing* supply position without being owner or delegate (`require_third_party_existing_supply`). That grace path reaches `merge_supply_leg`, which unconditionally calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, restamping the position's cached LTV/liquidation threshold to the currently listed values. The permissionless restamp entrypoint `update_account_threshold` explicitly guards this exact effect — it reverts unless the account clears an update health-factor floor when `has_risks` is set — but the equivalent state change via a stranger's dust supply skips that check entirely. This is the same bug class as the reference report: a permission/solvency check that is enforced on the direct path is inadvertently skipped on a second, grace-period-style path.

### Finding Description
- `process_supply` only verifies `caller.require_auth()` and then, for a non-owner/non-delegate caller, requires each supplied `hub_asset` to already exist in `account.supply_positions` (`require_third_party_existing_supply`, contracts/controller/src/positions/supply.rs:78-97).
- Every supplied leg flows through `process_deposit` → `merge_supply_leg`, which calls `refresh_supply_risk_params(env, cache, account, hub_asset, &mut position, &asset_config, RiskRefreshScope::FullTuple)` (supply.rs:288-296). This restamps the position's cached risk parameters — including the liquidation threshold that the health factor reads — to whatever governance currently lists, on both owner's and strangers' supplies.
- Contrast with the declared guarantee for `controller::update_account_threshold` in `scripts/permissionless_entrypoints.txt:76`: "with has_risks set it reverts unless the account clears the update health-factor floor, so it cannot be used to push an account into liquidation." The protocol explicitly recognizes that an unguarded restamp after a parameter decrease is a liquidation weapon, and gates the dedicated entrypoint — but the same restamp is reachable, ungated, through `supply` by any address.
- When governance lowers a market's `liquidation_threshold` (or LTV tuple) between the victim's last touch and now, an attacker supplies a minimal dust amount of that same asset to the victim's `account_id`. The victim's cached threshold drops to the new value without any solvency floor being enforced, the health factor recomputes below WAD on the next risk read, and the attacker immediately calls `controller::liquidate` (`process_liquidation`, liquidation/mod.rs:36-138), earning the HF-based bonus on seized collateral.

### Impact Explanation
Theft of user funds: the attacker converts a healthy-or-marginal account into a liquidatable one using only their own dust deposit, then liquidates it and captures the liquidation bonus and collateral spread. The impact is bounded to accounts that hold a supply position in a market whose risk parameters were tightened and whose pre-restamp health factor sits between the old and new thresholds — but the loss to the victim is real (seized collateral at bonus pricing).

### Likelihood Explanation
- Preconditions: governance reduces an asset's liquidation threshold (a routine risk-management action), and a target account's HF is above 1 under the stale cached params but at or below 1 under the new params. This window persists until the account's next owner-initiated touch or a `update_account_threshold` call — which itself is the guarded path the attacker is bypassing.
- Cost to attacker: a dust supply of an asset the victim already holds, plus liquidation capital. No privileged role, no leaked key, no flash loan required; a single unprivileged address executes `supply(account_id=victim, [(hub_asset, dust)])` then `liquidate`.
- Analogous to the CVE's requirement ("attacker must be a meeting participant" → here "attacker must hold dust of one of the victim's supply assets"), this is a medium-severity conditional access-control gap.

### Recommendation
Apply the same health-factor floor used by `update_account_threshold` whenever `refresh_supply_risk_params` restamps risk parameters on behalf of a caller that is not the account's owner or an active delegate. Concretely: in `process_supply`, when `require_third_party_existing_supply` admits a stranger, either (a) skip the `FullTuple` restamp in `merge_supply_leg` for third-party supplies (keep the stored tuple), or (b) after restamping, enforce the same post-restamp solvency check `update_account_threshold` uses for `has_risks`, reverting the whole call if the account would fail the floor. Option (a) is the smaller change: a third party's top-up should credit shares without re-signing the account onto new risk terms.

### Proof of Concept
1. Governance lists USDC in hub with `liquidation_threshold = 8000` bps. Victim supplies USDC and borrows to HF = 1.05 under cached threshold 8000.
2. Governance updates the listing to `liquidation_threshold = 7000` bps. Victim's cached position still reads 8000; `update_account_threshold(victim, has_risks=true)` correctly reverts because restamping would breach the HF floor.
3. Attacker (holds dust USDC) calls `controller::supply(attacker, victim_account_id, spoke_id, [(USDC_key, 1)])`. `require_third_party_existing_supply` passes because the victim already holds a USDC supply position. `merge_supply_leg` restamps the position to threshold 7000 — no floor check.
4. `get_health_factor(victim_account_id)` now returns < WAD.
5. Attacker calls `controller::liquidate(attacker, victim_account_id, debt_payments, SeizeMode::Transfer)`; `build_liquidation_plan` admits the account and the attacker seizes collateral at the HF-curve bonus.

Uncertainty note: I did not verify whether `refresh_supply_risk_params` on supply touch is an explicitly documented ADR decision (e.g., in `docs/`); if the design mandates restamping on every position touch, this reduces to an inconsistency between two permissionless restamp paths rather than an outright bug — though the security consequence for the victim is identical and the floor check should still apply to third-party callers.
