### Title
CCMenuController ignores ApiClient stack scoping, allowing any CCMenu token to read the deploy status of every stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces a binding: `ApiClient#stack_id` (the stack the token is authorised for) must equal the stack that is actually queried, via the `stacks`/`stack` helpers [1](#0-0) . `Api::CCMenuController` re-implements its own `stack` accessor that bypasses this scoping entirely and resolves the stack directly from `params[:stack_id]` with no relation to the authenticated client's `stack_id` [2](#0-1) .

### Finding Description
`ApiClient` records can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [3](#0-2) . `BaseController#stacks` is supposed to enforce that scoping for every request: if the authenticated client has a `stack_id`, only that stack is queryable; otherwise all stacks are queryable [1](#0-0) . All other API controllers (e.g. `StacksController`) rely on this inherited `stack`/`stacks` helper, so the token-to-stack binding holds: `stack_the_token_authorizes == stack_the_request_touches`.

`Api::CCMenuController`, however, overrides `stack` with:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 
This performs a direct, unscoped lookup of any stack by its param, completely ignoring `current_api_client.stack_id`. The controller still calls `require_permission :read, :stack`, which only checks that the token carries the generic `read:stack` permission string — it never checks which stack the permission applies to [5](#0-4) , [6](#0-5) .

This is exactly the reported bug class transposed onto an authorization binding: the "amount" that is verified (the scoping check performed once in `stacks`) is never re-applied at the point the value is actually used (the `stack` resolution in `CCMenuController`), so the two independently-derived values (`current_api_client.stack_id` vs. the stack actually rendered) diverge.

The severity is amplified by how these tokens are provisioned. `CCMenuUrlController#client` creates or reuses an `ApiClient` scoped only by `permissions: %w[read:stack]`, with **no `stack:` attribute set**, and returns a URL containing the raw `authentication_token` in the query string, intended for use by external CI-status tools/dashboards (CCMenu clients) [7](#0-6) . These URLs are designed to be shared/embedded outside of an authenticated Shipit session (build monitors, dashboards, Slack, etc.), and their `authentication_token` is a bearer credential with no further binding to the specific stack it was generated for once `Stack.from_param!` is invoked. Since the token itself never enforces a per-stack restriction (client's `stack_id` is nil in the default flow, and even when a client's `stack_id` is set for other purposes, `CCMenuController` ignores it), the same token/URL pattern can be replayed against `api_stack_ccmenu_url(stack_id: <any_other_stack>)` to read that other stack's latest deploy/rollback status.

### Impact Explanation
This breaks the "stack a token authorises vs. stack it touches" binding. A holder of any CCMenu token — a low-privilege, often externally-shared credential meant to expose only a single stack's build/deploy status — can enumerate `stack_id` values and read the latest deploy/rollback status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for every stack in the Shipit installation, not just the one the URL was generated for. This is an unauthenticated (relative to the target stack) read of stack state, matching the High-severity criterion "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High. No special privilege is needed beyond possessing any single valid CCMenu token — which by design is meant to be distributed to external tooling with restricted scope. The `stack_id` parameter is a simple integer/slug in the URL path, trivially enumerable, and `Stack.from_param!` performs no ownership check against the token.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped `stacks`/`stack` helper from `BaseController` (i.e., remove the private `stack` override and let `stacks.from_param!(params[:stack_id])` enforce `current_api_client.stack_id` scoping), or explicitly verify `stack.id == current_api_client.stack_id` when the client is scoped. Additionally, consider always scoping CCMenu tokens created by `CCMenuUrlController` to the specific stack (`stack: stack`) rather than leaving `stack_id` nil, so unscoped/generic `read:stack` tokens are not usable for cross-stack reads even outside the CCMenu controller path.

### Proof of Concept
1. As a user with read access to Stack A, visit `GET /:stack_id_A/ccmenu_url` (routed to `CCMenuUrlController#fetch`), obtaining a URL like `.../api/1/ccmenu.xml?stack_id=A&token=<TOKEN>` [8](#0-7) .
2. Share/leak `TOKEN` (as intended, e.g. embedded in an external CI dashboard).
3. An attacker who obtains `TOKEN` (or any other CCMenu token from any stack) requests `.../api/1/ccmenu.xml?stack_id=B&token=<TOKEN>` for an arbitrary Stack B they were never authorized to view.
4. `CCMenuController#authenticate_api_client` successfully authenticates the token via `ApiClient.authenticate(params[:token])` [9](#0-8) ; `require_permission :read, :stack` passes because the token carries `read:stack` generically [6](#0-5) ; and `stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, bypassing any scoping check [4](#0-3) .
5. The response renders Stack B's latest deploy/rollback status, which the attacker was never authorized to see.
