## Title
CCMenu API endpoint bypasses per-stack API client scoping, allowing a token authorized for one stack to read the status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` reimplements both `#stack` and `#authenticate_api_client` instead of using the versions inherited from `Shipit::Api::BaseController`. In doing so it drops the scoping logic that restricts a stack-scoped `ApiClient` token to only the `Stack` it was issued for, letting any holder of a valid, stack-scoped, `read:stack` token read the CI/deploy status of an arbitrary stack by simply changing the `stack_id` in the URL.

### Finding Description
`Shipit::Api::BaseController` binds an `ApiClient`'s authorization to a specific stack via the `stacks`/`stack` helpers: [1](#0-0) 
`current_api_client.stack_id?` restricts the visible/queryable stacks to the one the client is `belongs_to :stack` bound to. [2](#0-1) 
This scoping is exercised and tested elsewhere in the API (e.g. `Api::StacksController`), where a client scoped to a stack "will only see that one stack": [3](#0-2) 

`Shipit::Api::CCMenuController`, however, overrides `#stack` to bypass the `stacks` scope entirely, resolving directly from the global `Stack` table: [4](#0-3) 
It also overrides `#authenticate_api_client` to authenticate purely from a `token` query-string parameter (rather than HTTP Basic Auth used by the base controller), which is how `CCMenuUrlController` mints and hands out these tokens for embedding in third-party CI status tools: [5](#0-4) 

The only remaining check is `require_permission :read, :stack`, which merely verifies the `read:stack` string is present in the client's `permissions` array — it does **not** verify which stack the client is bound to: [6](#0-5) [7](#0-6) 

The equality that should hold is: *stack authorized by token == stack touched by the request*. Before the exploit, a stack-scoped token (`ApiClient#stack_id` set to Stack A) can only ever resolve `stack` to Stack A through the inherited `stacks` helper used throughout the rest of the API. After the exploit, because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly, the same token can resolve `stack` to any Stack B/C/... in the installation just by changing the `stack_id` route parameter — breaking that binding.

### Impact Explanation
This is an authorization scope bypass allowing an attacker who has obtained (or been legitimately given, e.g. embedded in a public CI-status badge/widget URL) a token scoped to a single stack to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status, etc.) for every other stack in the Shipit installation, including private/production stacks the token holder was never meant to have visibility into. This matches the "unauthenticated/unauthorized read of stack state" High-impact category, since the CCMenu token mechanism is specifically designed to be a narrowly-scoped, low-trust credential (handed out for embedding in unrelated tools), and this bug removes that scoping.

### Likelihood Explanation
Likelihood is moderate-to-high in any installation that uses stack-scoped API clients together with the CCMenu feature: an attacker only needs one leaked or legitimately-obtained CCMenu/API token with `read:stack` permission (these tokens are designed to be embedded in third-party CI dashboards, i.e., lower-trust contexts) and can immediately probe other `stack_id` values, since stack ids are just `owner/repo/environment` strings that are often guessable or discoverable from the GitHub org's repository/stack list.

### Recommendation
Have `CCMenuController#stack` use the inherited scoped `stacks`/`stack` helper from `BaseController` (i.e., remove the private `#stack` override, or reimplement it as `stacks.from_param!(params[:stack_id])`) so a stack-scoped `ApiClient` can only ever resolve to the stack it is bound to, consistent with every other API endpoint.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A (`stack_id` = A, `permissions` includes `read:stack`), e.g. via the CCMenu URL flow (`GET /ccmenu/*stack_id`) or an admin-configured scoped client.
2. As the holder of that token (no further privileges), request:
   `GET /api/stacks/<STACK_B_OWNER>/<STACK_B_NAME>/<STACK_B_ENV>/ccmenu?token=<TOKEN_FOR_STACK_A>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully; `#stack` resolves Stack B directly via `Stack.from_param!`, bypassing the scoping check that would otherwise raise `ActiveRecord::RecordNotFound` for a client scoped to Stack A.
4. The response renders Stack B's CCMenu XML status, disclosing build/deploy state the token was never authorized to see.
