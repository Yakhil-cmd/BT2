Based on my investigation, I found a concrete authentication gap in the shared-address / wallet message handling code that is analogous to the account-takeover class of bug in the report (an entity's identity/ownership claim is accepted without verifying it actually comes from an authorized party).

### Title
Unauthenticated cosigner registration in shared multisig address creation allows funds to be permanently frozen - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` in [1](#0-0)  accepts a `new_shared_address` device message and persists the shared address definition and every claimed `signers` entry (including the `device_address` that should be asked to co-sign in the future) — but it never verifies that the message actually originated from one of the parties named in `body.signers`. This is unlike the sibling flow `handleOfferToCreateNewWallet()`, which explicitly checks `arrDeviceAddresses.indexOf(from_address) === -1` to make sure the sender is one of the legitimate cosigners [2](#0-1) .

### Finding Description
`wallet.js`'s `new_shared_address` handler calls straight into `handleNewSharedAddress(body, ...)` without ever passing or checking `from_address`: [3](#0-2) .

Inside `handleNewSharedAddress`, the only checks performed are:
- the definition hashes to the claimed address,
- each `signers[path].address` is a syntactically valid address,
- the addresses in `signers` match the `address` leaves extracted from the definition,
- every `address`-leaf path has a corresponding signer entry. [4](#0-3) 

None of these checks establish that the sending device is actually one of the parties who should be co-signing this address. `determineIfIncludesMeAndRewriteDeviceAddress()` only rewrites the `device_address` for signing paths whose `address` is verifiably present in the *local* `my_addresses` table — i.e., it protects the local user's own slot — but it leaves the `device_address` for every *other* signer's path exactly as supplied by the (unauthenticated) sender [5](#0-4) . The address itself and other cosigners' addresses can be learned by any correspondent by simply observing chain data (a shared address is public once used), so an attacker with a device pairing to the victim can freely re-send a `new_shared_address` message for a genuine multisig address the victim is part of, substituting the attacker's own `device_address` for the real second cosigner's slot in `shared_address_signing_paths`.

Because `addNewSharedAddress()` uses `INSERT … IGNORE` for both `shared_addresses` and `shared_address_signing_paths` [6](#0-5) , whichever `new_shared_address` message the victim's node processes *first* wins and cannot be overwritten by the legitimate cosigner's later, authentic message for the same `(shared_address, signing_path)` key. This lets any paired correspondent race the real cosigner and permanently plant a bogus `device_address` for the co-signing role.

### Impact Explanation
Once the attacker's device_address is recorded for a genuine cosigner's signing path, the victim's wallet software, when later composing a payment from that shared/multisig address, will direct signing requests for that path to the attacker's device rather than to the real cosigner. Since the attacker does not hold the real cosigner's private key, they cannot forge a valid signature (so this is not direct fund theft), but the legitimate cosigner is permanently excluded from the signing workflow for that address — funds controlled by that shared address can become unspendable, i.e. AA/wallet fund freezing, until the corrupted `shared_address_signing_paths` row is manually corrected. This also enables a denial-of-service against the intended multisig-approval process (attacker learns of pending/likely shared addresses via correspondence and squats on them).

### Likelihood Explanation
Reachable by any device that is a paired correspondent of the victim (a common trust level in ocore chat wallets, e.g. through a group/multisig setup or a merchant "arbiter" flow) — no special network position or victim‑side mistake is required beyond having exchanged pairing at some point. The race is timing-dependent (attacker must send before the legitimate co-signer's message is processed), which lowers but does not eliminate practical likelihood.

### Recommendation
Add sender authentication analogous to `handleOfferToCreateNewWallet`: `handleNewSharedAddress` (and the `new_shared_address` case in `wallet.js`) should require and verify that `from_address` is one of the `device_address` values named in `body.signers`, and should not blindly trust/overwrite/insert-ignore `device_address` values for cosigners that don't match the sender or previously-confirmed values.

### Proof of Concept
1. Attacker device D_A is a paired correspondent of victim device D_V.
2. D_V is (or will be) a genuine cosigner of shared address `S` with real second cosigner D_B, definition `["and",[["address","V_ADDR"],["address","B_ADDR"]]]` (address/definition publicly derivable once used on-chain, or guessable ahead of the real setup handshake).
3. D_A sends a `new_shared_address` message to D_V with `address: S`, the correct `definition`, but `signers["r.1"] = {address: "B_ADDR", device_address: D_A}` (attacker's own device address instead of D_B's).
4. D_V's `wallet.js` handler invokes `handleNewSharedAddress` with no `from_address` check [3](#0-2) ; `determineIfIncludesMeAndRewriteDeviceAddress` only fixes the row for `V_ADDR` (D_V's own address) and leaves the `B_ADDR` row's `device_address` as `D_A` [5](#0-4) .
5. `addNewSharedAddress` performs `INSERT IGNORE`, permanently locking in the malicious `device_address` for that signing path if it arrives before D_B's own legitimate `new_shared_address` message [6](#0-5) .
6. When D_V later tries to spend from `S`, the wallet will request the co-signature from D_A (attacker) instead of D_B, and D_B is never contacted, permanently freezing spending from `S` unless manually fixed.

**Note on verification limits:** I was unable to inspect `composer.js`'s exact logic for how `shared_address_signing_paths.device_address` is consumed at payment-composition time (no direct references were found in that file within the indexed context), so I could not fully trace end-to-end how the signing request is dispatched using this table. This limits full certainty on the precise mechanics of the freeze, though the missing sender-authentication check itself is confirmed directly in the source. Given the size limits on the indexed codebase, a full Devin session with complete file access is recommended to confirm the exact downstream consumption of `shared_address_signing_paths` in the signing/payment-composition flow before treating this as fully proven.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
