### Title
Cross-organization webhook confusion: signature verified against `repository.owner.login`, but repository acted upon resolved from unvalidated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC signature against using a field pulled directly out of the unauthenticated request body, while every event `Handler` resolves which `Repository`/`Stack` to mutate using a *different, uncorrelated* field from the same body. Nothing ties these two fields together, so a party who legitimately controls one configured organization's webhook secret can produce a validly-signed request that is routed, by the handler, to act on a stack belonging to an entirely different organization/repository.

### Finding Description
Multi-organization Shipit deployments configure a separate GitHub App / `webhook_secret` per organization (`lib/shipit/github_app.rb:44-57`, `lib/shipit.rb:170-200`, `config/secrets.development.shopify.yml`). Signature verification in the controller derives the organization to check against solely from the JSON body: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` then picks that organization's configured secret to verify the `X-Hub-Signature` HMAC over the raw body [1](#0-0) . Once verification passes, the event is dispatched to handlers with the *entire attacker-controlled* `params` object [3](#0-2) .

Every handler, however, determines which `Stack`/`Repository` to act on from a *separate* field, `repository.full_name`, with no check that it is consistent with `repository.owner.login`: [4](#0-3) 

Because both `repository.owner.login` and `repository.full_name` are simple JSON keys inside the same signed payload, and the *organization selection for verification* uses only the former while the *repository selection for the actual write* uses only the latter, an attacker who legitimately owns/administers one configured organization (say `orgA`, with its own valid `webhook_secret`) can:

1. Compute a valid HMAC signature over a crafted JSON body using `orgA`'s own secret (which they legitimately possess, since they installed/configured their own GitHub App tenant on this shared Shipit instance).
2. Set `repository.owner.login` (and/or `organization.login`) to `"orgA"` so `verify_signature` selects `orgA`'s secret and passes.
3. Set `repository.full_name` to `"orgB/some-repo"` — a repository belonging to a different tenant organization `orgB` that has stacks configured on this same Shipit instance.
4. `PushHandler` (or `StatusHandler`, etc.) resolves stacks via `Repository.from_github_repo_name(repository_name)` using this forged `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack [5](#0-4) , even though the signature only proved knowledge of `orgA`'s secret, not any credential relating to `orgB`.

This breaks the intended binding: *the organization whose credential authenticated the request* ≠ *the repository/stack the handler actually writes to*. The docs explicitly describe support for "multiple GitHub organisations" as a supported multi-tenant feature (`CHANGELOG.md:132`), so `orgA` and `orgB` are meant to be mutually untrusted tenants sharing one Shipit instance — exactly the unprivileged-attacker boundary the rules describe ("an organization that authenticated versus the repository that is written").

### Impact Explanation
An attacker who controls (or has compromised) one tenant organization's webhook secret in a multi-org Shipit deployment can forge webhook deliveries that are attributed to their own org for signature purposes, but that cause Shipit to sync GitHub state, create commits/statuses, or otherwise mutate stacks belonging to a completely different, unrelated organization's repositories. Depending on handler (`push`, `status`, `check_suite`, `membership`), this can trigger unauthorized GitHub sync operations, spoofed commit statuses, or team/membership changes cross-tenant — a cross-repository/cross-organization write performed with a credential that was never authorized for that target repository.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple organizations (an explicitly supported and documented configuration), and (b) the attacker to possess a valid `webhook_secret` for at least one configured organization — which is the case for any legitimate but malicious/compromised tenant admin of that org. No GitHub repository write access, Shipit session, or API token to the *target* org/repo is required, satisfying the "unprivileged attacker" bar for the victim organization.

### Recommendation
Bind the signature-verification identity and the write-target identity to the same, single source of truth. When resolving which organization's secret to use for verification, and when resolving which `Repository`/stack a handler should mutate, both should derive from the same normalized field (e.g., `repository.full_name`'s owner segment), and the controller should additionally assert that the resolved `Repository#owner` for the target stack matches the organization whose secret verified the signature before dispatching to any handler. Reject events where `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret`, per `docs/setup.md` multi-org instructions.
2. As an operator of `orgA` (who legitimately knows `orgA`'s `webhook_secret`), craft a `push` event JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `GitHubApp`, and the HMAC verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `repository.full_name = "orgB/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: ...)` on `orgB`'s stack — despite the signature only proving possession of `orgA`'s secret.
