## Analysis Result [1](#0-0) 

I found a demonstrable analog in `pallet-asset-rewards`, which explicitly implements the same Synthetix `StakingRewards.sol`-style "reward-per-token accumulator" pattern referenced by the report.

### Title
Integer-division rounding in `reward_per_token()` permanently freezes reward-per-token accumulation while `last_update_block` keeps advancing - (File: substrate/frame/asset-rewards/src/lib.rs)

### Summary
`Pallet::reward_per_token` computes the incremental reward-per-token as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, using plain integer division with a scaling factor of only `4096` (vs. the `1e18` scaling used in the Solidity contract this report was originally filed against). Any signed, unprivileged account can trigger this recomputation with a minimal `blocks_elapsed` (as little as 1 block) simply by calling the permissionless `stake`, `unstake`, or `harvest_rewards` extrinsics repeatedly. When `reward_rate_per_block * blocks_elapsed * 4096 < total_tokens_staked`, the increment rounds down to zero every single call, yet `last_update_block` is unconditionally advanced to the current block, permanently discarding that period's rewards for the whole pool.

### Finding Description
`reward_per_token` is:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [2](#0-1) 

`PRECISION_SCALING_FACTOR` is a constant `4096` [3](#0-2) , far smaller than the `1e18` scale used in the original ERC20Rewards analog, which itself was shown by the report to be too small when the staked-asset total supply is large.

`update_pool_rewards` unconditionally sets `last_update_block = current_block_number()` regardless of whether `reward_per_token_stored` actually changed:
```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
``` [4](#0-3) 

This is called from every real user entry point that touches the pool:
- `stake` (call index 1) — any signed account, no privilege required [5](#0-4) 
- `unstake` (call index 2) — staker or anyone post-expiry [6](#0-5) 
- `harvest_rewards` (call index 3) — staker themselves before expiry [7](#0-6) 

Each of these calls `update_pool_and_staker_rewards` -> `reward_per_token` -> `update_pool_rewards`, so `last_update_block` moves forward on every call, but `reward_per_token_stored` only increases if the rounded division is nonzero.

Because a staker can call `harvest_rewards`/`stake` in every block (paying only ordinary transaction fees, no privileged origin, no governance, no forged inherents), they can keep `rewardable_blocks_elapsed` at `1` indefinitely. If `reward_rate_per_block * 4096 < total_tokens_staked` (a condition that is very easy to satisfy with realistic token decimals/supplies, since the scaling factor is a mere `4096` rather than `1e18`), every such call rounds the increment to `0`. The accumulator `reward_per_token_stored` then never advances although `last_update_block` is dragged forward every block, so the reward period for that stretch of time is permanently lost — it can never be recovered on a later, larger-elapsed-time call because the "lost" blocks are excluded from all future `rewardable_blocks_elapsed` computations (the subtraction is always `now - last_update_block`).

### Impact Explanation
Any single staker (with only a minimal, non-privileged stake sufficient to have a `PoolStakers` entry) can, by simply calling `harvest_rewards` (or `stake`) once per block, permanently zero out reward distribution to every staker in the pool for as long as they keep doing so. This is a pool-wide state (`reward_per_token_stored`, `last_update_block` on `PoolInfoFor<T>`), so the griefing affects all other stakers in the pool, not just the caller. The reward tokens already deposited into the pool's account remain stuck without being credited to `reward_per_token_stored`, effectively freezing the intended reward emission for that pool. This matches the report's core invariant violation: "accumulated" reward-per-token can stay constant while the "lastUpdated" timestamp keeps moving forward, defeating the purpose of the rewards program.

### Likelihood Explanation
The trigger requires no attacker sophistication beyond calling a normal permissionless extrinsic (`harvest_rewards` or `stake`) every block, which is well within reach of any account holding trivial funds for fees. It also does not require malicious intent: any actively-used pool with frequent staking/unstaking/harvesting activity and a reward rate/token-supply ratio under the `4096` scaling threshold will naturally suffer eaten rewards, exactly as the original report notes about "naturally liquid tokens where lots of transfer, mint or burn events occur."

### Recommendation
As suggested in the original report, only update `last_update_block` when `reward_per_token_stored` actually changes (or, better, increase `PRECISION_SCALING_FACTOR` substantially, e.g. to `1e18`/a `FixedU128`-based computation as `pallet-nomination-pools` does via `T::RewardCounter::checked_from_rational` [8](#0-7) , which avoids this rounding-to-zero-while-time-advances failure mode entirely).

### Proof of Concept
- Reachable entry point confirmed: `stake`/`unstake`/`harvest_rewards` are ordinary signed extrinsics with no privileged origin check beyond `ensure_signed`/self-caller equality [9](#0-8) .
- Root-cause math confirmed at `reward_per_token` (lines 794-810) and unconditional timestamp bump at `update_pool_rewards` (lines 775-784), both cited above.
- No local Rust/FRAME test was executed against this repository as part of this analysis; this is a static-code-trace finding, not a report of an executed reproduction. A concrete integration test (e.g., extending `substrate/frame/asset-rewards/src/tests.rs`) driving repeated `harvest_rewards` calls with 1-block spacing and asserting `reward_per_token_stored` stays constant while `last_update_block` advances would be needed to obtain executed PoC evidence.

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}
