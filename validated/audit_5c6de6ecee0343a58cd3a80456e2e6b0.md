### Title
Stack-scoped API client authorization bypass in CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack via the global `Stack.from_param!(params[:stack_id])` instead of the stack-scoped `stacks.from_param!` helper defined in `BaseController`, breaking the binding between the stack an `ApiClient` token is authorized for and the stack whose data is actually returned.

### Finding Description
`Shipit::Api::BaseController` establishes a trust binding: when an `ApiClient` is scoped to a single stack (`current_api_client.stack_id?`), the `stacks` helper restricts the visible collection to `Stack.where(id: current_api_client.stack_id)`, and the generic `stack` method looks up the requested stack only within that scoped collection via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`CCMenuController` overrides this `stack` method and instead calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely bypassing the `current_api_client.stack_id` restriction, even though it still declares `require_permission :read, :stack`. [2](#0-1) 

Since `require_permission!` only checks the *permission list* on the client (`check_permissions!` checks whether `"read:stack"` is in `permissions`) and never checks `stack_id` scoping, a stack-scoped token still passes the `require_permission :read, :stack` filter. [3](#0-2) 

The `ApiClient` model itself supports (and the fixtures demonstrate) scoping a client to exactly one stack via the `stack` association/`stack_id` column, precisely for this "authorized only for one stack" use case. [4](#0-3) [5](#0-4) 

The `Api::StacksController#index` test suite explicitly documents and enforces the expected invariant — "an api client scoped to a stack will only see that one stack" — confirming this is the intended security boundary elsewhere in the same namespace. [6](#0-5) 

The route for this endpoint accepts an arbitrary `stack_id` path segment for any stack in the installation. [7](#0-6) 

The binding that should hold is: `stack authorized by token == stack touched by the request`. After this bug, for the CCMenu endpoint specifically, `stack touched` can be any stack in the system regardless of the token's `stack_id`, breaking the equality.

### Impact Explanation
This falls under "High — unauthenticated/unauthorized read of stack state, task streams or deploy output" from the accepted impact list: a token deliberately restricted to one stack (e.g. the token an org gives to a low-trust integration, or the `ccmenu_url` self-service token) can be used to read the latest deploy/rollback status (`stack.deploys_and_rollbacks.last`) of any other stack in the Shipit installation, cross-repository, without needing broader permissions. This is a genuine escalation across the stack-authorization boundary that other controllers in the same namespace correctly enforce.

### Likelihood Explanation
Exploitation only requires possession of any valid API token that has the `read:stack` permission and is scoped to a single stack — no privileged account or session is needed beyond having been issued such a token (which is the standard, lower-trust use case for `ApiClient.stack_id` scoping, e.g. tokens generated by `CCMenuUrlController` for a specific stack's CI badge). The attacker only needs to change the `stack_id` route segment in the request URL; no signature or extra secret needs to be forged.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` collection from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so that `current_api_client.stack_id` scoping is enforced consistently with the rest of the `Api::BaseController` subclasses.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id` = Stack A, with permission `read:stack` (as done by `CCMenuUrlController#client`, or via the `api_clients` admin UI plus manually setting `stack_id`).
2. Authenticate to `GET /api/stacks/:other_org/:other_repo/:other_env/ccmenu` (Stack B, a different stack the client was never authorized for) using this token, either via Basic Auth or the `?token=` query parameter supported by `CCMenuController#authenticate_api_client`.
3. Observe that `require_permission :read, :stack` passes (because the client has `read:stack` in its `permissions` list) and the response renders Stack B's CCMenu XML (build status, last build label, etc.), even though the token is scoped only to Stack A — contrast with `Api::StacksController#index`, which correctly restricts results to the client's `stack_id`.
