### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is resolved from `repository.full_name` — breaking the org-authentication binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC secret) to verify the inbound webhook against using `repository_owner`, a field read straight out of the attacker-suppliable JSON body. Every event handler, however, resolves the `Repository`/`Stack` to act on using a *different* field from the same body: `repository.full_name`. Because both fields live inside the same payload that the attacker fully controls before signing it with their own known secret, nothing forces `repository.owner.login` to match the owner encoded in `repository.full_name`. An attacker who legitimately controls one Shipit-configured GitHub organization (and therefore knows *that org's* webhook secret) can sign a payload as their own org while pointing the `repository.full_name` at a completely different, victim-owned repository/stack.

### Finding Description
`verify_signature` picks the GitHub App/secret using the payload-controlled `repository_owner`: [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` dispatches the entire raw JSON to the handler for the event, unmodified: [3](#0-2) 

Every concrete handler (e.g. `PushHandler`) resolves the target `Repository`/`Stack` from a *different* JSON field, `repository.full_name`, via the base `Handler#stacks`/`#repository_name`: [4](#0-3) [5](#0-4) 

This is structurally identical to the referenced report: the field that is checked/authorized (`repository_owner`, used to pick the signing secret) is not the same field that is acted upon (`repository.full_name`, used to pick the `Repository`/`Stack`). The binding that should hold is:

`organization_used_for_signature_verification == owner_encoded_in(repository.full_name)`

but nothing in `verify_signature` or `create` enforces this equality. Shipit explicitly supports multiple, independently configured GitHub organizations, each with its own `webhook_secret` set by that organization's own admins: [6](#0-5) [7](#0-6) 

So an org admin of one onboarded organization (who necessarily knows their own org's `webhook_secret`, since they configured the GitHub App and secret themselves) can compute a valid `X-Hub-Signature` for a payload whose `repository.owner.login`/`organization.login` is their own org (satisfying `verify_signature`), while its `repository.full_name` names a stack belonging to a different organization they have no legitimate access to.

### Impact Explanation
This breaks the intended authentication boundary of the multi-tenant webhook endpoint: a signature that is only supposed to authorize events for one organization's repositories is treated as sufficient to authorize handler actions on any repository named anywhere else in the same payload. Concretely with `PushHandler`, the attacker can force `stack.sync_github(expected_head_sha: params.after)` to run against a victim's `Stack` they do not own/administer, for any branch and `after` SHA of their choosing: [8](#0-7) 
This crosses an authentication boundary the report rules consider in-scope ("an organization that authenticated versus the repository that is written"), and can drive unscheduled syncs/deploy triggers on a stack the attacker has no relationship to — an unauthorized action against another tenant's repository, satisfying the "unauthorized deploy" / cross-tenant write class of impact. Other handlers (status, check_suite, membership, pull_request) follow the same `Handler#repository_name` pattern, so the same organization/repository mismatch is reachable through multiple event types, not just `push`.

### Likelihood Explanation
Exploitability requires the attacker to be an org admin of at least one GitHub organization independently onboarded into the same Shipit instance (a normal, unprivileged position relative to the *victim* organization/stack — no Shipit session, API token, or victim-org credentials are needed). Forging the JSON body and computing the HMAC with their own known secret is trivial once they control their own org's webhook secret. The multi-org configuration is an explicitly documented and supported deployment mode, so this is realistically reachable wherever more than one organization is configured on a shared Shipit instance.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), require that the organization used to select the verifying `GitHub App`/secret matches the owner encoded in the `repository.full_name` (or `organization.login`) actually used to resolve the target `Repository`/`Stack`, rejecting the webhook (422) on mismatch. This mirrors the recommended fix pattern of pinning the verified/authorized field to the field that is actually acted upon.

### Proof of Concept
1. Shipit is configured with multiple GitHub organizations, e.g. `AttackerOrg` (attacker is admin, knows `webhook_secret_A`) and `VictimOrg` (victim's stack, unrelated to attacker), per the supported multi-org config: [9](#0-8) 
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")` (from `repository_owner`), which succeeds because the signature was computed with `AttackerOrg`'s own secret [1](#0-0) .
5. `PushHandler` then resolves `repository_name = "VictimOrg/victim-repo"` and calls `sync_github` on the matching, non-archived `VictimOrg` stacks on branch `master` [4](#0-3) [8](#0-7) , an action the attacker has no legitimate authority to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
