### Title
Pull-request label names flow unfiltered into `TaskCommands#env`/`DeployCommands#env`, bypassing the `deploy.variables` allowlist and letting a fork PR inject arbitrary env vars such as `LD_LIBRARY_PATH` into `Command#start` - ([File: lib/shipit/task_commands.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's env hash with no key allowlist. `TaskCommands#env` (and by inheritance `DeployCommands#env`) merges `@stack.env` directly into the command environment, and only the *explicitly-submitted* `env` parameter (`@task.env`) is ever passed through `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit`. This means the `deploy.variables` allowlist never sees or filters label-derived keys, so a fork PR labeled `LD_LIBRARY_PATH` reaches `Command#unbundled_env` and `PTY.spawn` unfiltered.

### Finding Description
The broken binding: for any deploy/task step, every key in `Command#env` reaching `PTY.spawn` should be an element of `deploy_variables.map(&:name)` (as enforced by `DeploySpec#filter_deploy_envs` / `EnvironmentVariables#permit`). In practice this is false whenever a `ReviewStack` has a `pull_request` with labels.

Trace:
1. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```ruby
super.merge(pull_request.labels.each_with_object({}) { |n, h| h[n.upcase] = "true" })
```
with no key allowlist — any label name becomes an env var. [1](#0-0) 

2. `LabelCapturingHandler#capture_labels` persists label names straight from the webhook `pull_request.labels[].name` field with no sanitization beyond string presence:
```ruby
pull_request.update!(labels: params.pull_request.labels.map(&:name))
``` [2](#0-1) 

3. `TaskCommands#env` (used by `DeployCommands#env` via inheritance) merges `@stack.env` (the unfiltered, label-derived hash) directly, and only merges the *filtered* `@task.env` afterward:
```ruby
def env
  super
    .merge(@stack.env)                 # <-- unfiltered, includes label-derived keys
    .merge('SHIPIT_USER' => ..., ...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)                  # <-- only this went through filter_deploy_envs
end
``` [3](#0-2) 

4. The allowlist (`EnvironmentVariables#permit`, called from `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`) is only invoked on the explicit API-submitted `env` parameter at `Stack#build_deploy` (`env: filter_deploy_envs(env.to_h)`), never on `@stack.env`: [4](#0-3) [5](#0-4) [6](#0-5) 

5. `Command#start`/`unbundled_env` merges `@env` (built from the above chain) directly on top of `BASE_ENV`/`PATH` and spawns the process with it:
```ruby
def unbundled_env
  BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)
end
...
@out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
``` [7](#0-6) 

Existing repository tests confirm this is exactly how labels flow, unfiltered, into the command environment: [8](#0-7) [9](#0-8) 

Attacker's exact request/PR: open a pull request against a repository configured with `provisioning_behavior = allow_all` and review stacks enabled, then apply (or have applied, per the audit's attacker model) a label literally named `LD_LIBRARY_PATH` (case-insensitive since it's `.upcase`'d) to that PR. `LabelCapturingHandler` persists the label; every subsequent deploy/task for the resulting `ReviewStack` will carry `LD_LIBRARY_PATH=true` in its environment. If any attacker-influenced binary/library path already exists on disk under the deploy's working directory (which the attacker fully controls via the PR contents), dynamic linking for spawned binaries in the `deploy`/`deploy.variables` phase is redirected to attacker-supplied `.so` files, achieving code execution as the Shipit deploy user.

Existing guards do not stop this: `EnvironmentVariables#permit` only filters the API-submitted `env` param at deploy-creation time (`Stack#build_deploy`), not the `@stack.env` merged inside `TaskCommands#env`/`DeployCommands#env`. There is no allowlist check anywhere on `ReviewStack#env`'s label-derived keys before they reach `Command`.

### Impact Explanation
Any environment key the attacker chooses (via label name) is injected into every deploy/task/rollback command run against that review stack, including `deploy.variables`, `deploy.override`, and `dependencies` steps. `LD_LIBRARY_PATH` (or `RUBYOPT`, `BUNDLE_GEMFILE`, `PYTHONPATH`, etc., depending on the deploy tech stack) can be used to redirect dynamic linking/interpreter behavior for any subprocess spawned by `PTY.spawn`, i.e., Critical — Remote Code Execution on the Shipit deploy host, matching the "Critical - RCE on the deploy host via Command/PTY.spawn" category. This is repeatable on every review-stack deploy/task for the affected PR and requires no elevated Shipit privileges — only the ability to attach a label to one's own PR (as defined by the attacker model in this audit) against a repo with `provisioning_behavior=allow_all` review stacks enabled.

### Likelihood Explanation
Preconditions: target repository has review stacks enabled with `provisioning_behavior: allow_all` (or `allow_with_label`/`prevent_with_label` where labeling is otherwise achievable), and the attacker can open a PR and have a label named after a dangerous env var (e.g. `LD_LIBRARY_PATH`) attached to it. No Shipit credentials, GitHub App keys, or webhook secrets are required — GitHub itself signs and sends the legitimate webhook for actions on the upstream repo. Cost is minimal (open a PR + label). This is a real, demonstrated code path (not theoretical) confirmed by existing repo tests showing labels flow unfiltered into `env`.

### Recommendation
Apply the `deploy.variables`/`rollback.variables`/task-variable allowlist (`EnvironmentVariables#permit`) to `@stack.env` (and specifically to the label-derived portion of `ReviewStack#env`) before merging it into `TaskCommands#env`/`DeployCommands#env`, or exclude dangerous/reserved variable names (e.g. `LD_LIBRARY_PATH`, `LD_PRELOAD`, `DYLD_*`, `PATH`, `RUBYOPT`, `BUNDLE_*`, `PYTHONPATH`) from ever being derived from PR label names. At minimum, `ReviewStack#env`'s label-injected keys must pass through the same `filter_deploy_envs`/`filter_rollback_envs`/`filter_task_envs` allowlists that `@task.env` already goes through, so only names explicitly declared in `shipit.yml`'s `variables` sections can reach `Command`.

### Proof of Concept
minitest plan (add to `test/lib/shipit/deploy_commands_test.rb` or `test/models/shipit/review_stack_test.rb`):
```ruby
test "#env does NOT let pull request labels inject LD_LIBRARY_PATH into deploy commands" do
  stack = shipit_stacks(:review_stack)
  stack.update!(cached_deploy_spec: DeploySpec.new(
    'deploy' => { 'variables' => [{ 'name' => 'ENVIRONMENT' }] } # explicit allowlist, no LD_LIBRARY_PATH
  ))
  deploy = stack.trigger_continuous_delivery
  stack.pull_request.labels = ["ld_library_path"] # attacker-controlled label name

  env = Shipit::DeployCommands.new(deploy).env

  # Binding under test: only allowlisted deploy.variables names should reach the command env
  refute_includes env.keys, "LD_LIBRARY_PATH",
    "label-derived LD_LIBRARY_PATH bypassed deploy.variables allowlist and reached Command#env"
end
```
Expected (current, vulnerable) result: `env["LD_LIBRARY_PATH"] == "true"` even though `deploy.variables` never declared `LD_LIBRARY_PATH`, proving the allowlist is bypassed via `@stack.env` in `TaskCommands#env`.

    def start(&block)
      return if @started

      @control_block = block

      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT

      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
