### Title
`register-for-bond`'s L1 Bitcoin-lockup proof can be replayed across separate bond registrations, letting a staker double-count one BTC lock into multiple pox-5 bonds — (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 path credits `sats-total` STX-backing weight to a bond based solely on a Bitcoin merkle-proof of a timelocked P2WSH output (`verify-l1-lockups` / `validate-l1-lockup`). The only replay protection (`seen-outpoints`) is scoped to the single fold call, not to the lifetime of the underlying Bitcoin UTXO. Once a staker's bond membership ends (e.g. via `unstake-sbtc`/expiry, which deletes `protocol-bond-memberships`), nothing stops the staker from calling `register-for-bond` again with the exact same historical BTC lockup proof to open a brand-new bond and lock a fresh batch of STX "backed" by BTC that was never re-locked.

### Finding Description
`verify-l1-lockups` initializes a *fresh, empty* `seen-outpoints` list every call: [1](#0-0) 

and the fold helper `validate-l1-lockup` explicitly documents that de-duplication is scoped "in this call": [2](#0-1) 

`validate-l1-lockup` checks the unlock height, the script hash, the amount, the intra-call outpoint dedup, the Bitcoin block header, and the merkle inclusion proof — but it never checks the outpoint against a persistent, cross-call/cross-bond map of already-consumed BTC lockups: [3](#0-2) 

`register-for-bond` uses this `sats-total` figure to size the STX that the staker is permitted/required to lock for a new bond: [4](#0-3) 

The contract does prevent a staker from registering a *second, concurrent* bond while an existing membership is active (`ERR_ALREADY_REGISTERED`), as exercised in the integration test: [5](#0-4) 

However, this check only blocks concurrent double-registration by the same staker. It does not, and cannot, prevent a staker from unstaking/closing a bond and then submitting the *same* previously-used BTC lockup merkle proof again to open a subsequent bond. A single real Bitcoin timelock output only proves the BTC was locked once at that block height/output — Bitcoin's own timelock mechanics govern spendability after maturity — but pox-5 never records that this specific outpoint has already been "spent" as collateral inside pox-5's own bond-registration bookkeeping.

### Impact Explanation
This breaks the intended equality that pox-5 relies on: 1 BTC lockup commitment == 1 backing of locked STX/bond membership. By reusing the same BTC proof across sequential bond lifecycles, a staker can back multiple independent STX lock periods (and the signer-weight / reward eligibility that comes with an active bond) with a single BTC commitment that was locked (and possibly later reclaimed on Bitcoin) only once. This is a double-counting of a commitment, which the rubric classifies as Critical impact (double-counting a commitment or reward, exceeding signing weight/reward slots relative to locked value).

### Likelihood Explanation
The attack requires no privileged role — any staker who has completed one L1-backed bond cycle (or otherwise regains the ability to call `register-for-bond` again, e.g. after `unstake-sbtc`/expiry clears their `protocol-bond-memberships` entry) can resubmit the identical lockup proof bytes used previously. No new Bitcoin transaction, signature, or admin action is needed — the exploit only needs the staker's own historical proof data, which is public on the Bitcoin chain and was already broadcast once in a prior transaction.

### Recommendation
Persist consumed L1 outpoints in a durable map (e.g. `used-l1-outpoints: {txid, output-index} -> bool`) that is checked and set across all calls/bonds, not just within a single `verify-l1-lockups` invocation, so that any given Bitcoin lockup output can back at most one pox-5 bond registration for its entire lifetime (or until the staker proves, via a corresponding spend/withdrawal proof, that the BTC was released and a new lock was created).

### Proof of Concept
1. Staker locks BTC into the canonical P2WSH timelock script, gets it mined, and calls `register-for-bond` with the merkle proof (`l1-lockups`) — bond #1 is created, `sats-total` sats credited, STX locked accordingly.
2. Bond #1 matures/staker calls `unstake-sbtc` (or otherwise the membership entry is cleared) — `protocol-bond-memberships` no longer contains the staker.
3. Staker calls `register-for-bond` again for a new bond, passing the identical `l1-lockups` tuple (same `tx`, `header`, `output-index`, `leaf-hashes` used in step 1).
4. `verify-l1-lockups`/`validate-l1-lockup` re-validate successfully because `seen-outpoints` starts empty each call and there is no cross-call persistent record of previously consumed outpoints — the same BTC lock now backs bond #2 with no new BTC ever having been re-locked.
