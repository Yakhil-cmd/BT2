Interesting: `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) doesn't even scope by repository at all — it matches purely on `Commit.where(sha: params.sha)`, which is a global lookup across all stacks/repositories. Combined with the signature-verification design, this produces a genuine cross-organization trust-binding break.

### Title
Webhook signature verified against `repository.owner.login`/`organization.login`, while every handler acts on data unbound to that identity - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner`, a field read out of the *same* untrusted JSON body it's about to validate [1](#0-0) . Shipit explicitly supports "Using Multiple Github Applications", where each organization can have its own `webhook_secret`, and that secret is optional (`nil` is allowed) per app [2](#0-1) . When an organization's `webhook_secret` is unset, `verify_webhook_signature` short-circuits to `true` unconditionally [3](#0-2) . Every event handler, however, resolves the target `Repository`/`Stack`/`Commit` from a *different* field of the same JSON body — `repository.full_name` (or, for `status` events, a global `sha` lookup with no repository scoping at all) [4](#0-3) [5](#0-4) . Because `repository.owner.login` (used to pick/validate the secret) and `repository.full_name` / global `sha` (used to select what gets mutated) are never checked to be consistent with each other, an unprivileged attacker who can reach `/webhooks` can craft a payload that authenticates as an organization with no configured secret while writing state for a completely unrelated, fully-secured organization's stacks and commits.

### Finding Description
The equality that should hold is: `organization whose secret validated this signature == organization that owns the repository being mutated`. In this codebase that equality is never enforced.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and uses it solely to pick a `GitHubApp` config via `Shipit.github(organization: repository_owner)`, then checks the signature against that org's secret [6](#0-5) .
- `Shipit.github` supports per-organization configuration and each entry's `webhook_secret` is documented as optional [7](#0-6) [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` with no HMAC check at all when `webhook_secret` is blank [3](#0-2) .
- All webhook handlers derive the actual target repository from `payload.dig('repository', 'full_name')` [4](#0-3)  — a field that is entirely independent of `repository.owner.login`/`organization.login` used above. `StatusHandler` goes further and doesn't even use the repository field; it does a bare `Commit.where(sha: params.sha)` across the whole database [8](#0-7) .

Before the attack: signature check is bound to `repository.owner.login` = Org-with-no-secret; data mutation is bound to `repository.full_name`/`sha` = any tracked repo/commit, with no cross-check between the two fields. An attacker can therefore submit a self-consistent-looking JSON body where `repository.owner.login` names an org that has `webhook_secret: nil` (satisfying `verify_signature`, which bypasses HMAC entirely for that org) while `repository.full_name` (or `sha`) refers to a repository/commit belonging to a different, fully-secured organization tracked by the same Shipit instance.

### Impact Explanation
This breaks the "GitHub App authenticated org vs. repository actually written" binding required by the rules. Concretely, an unprivileged external attacker (no Shipit session, no GitHub App key, no webhook secret) can:
- Forge `status`/`check_suite` events to fabricate a `success` CI status on an arbitrary commit SHA of any stack Shipit tracks (via `StatusHandler`/`create_status_from_github!`), which can flip a commit to "deployable" and trigger continuous-deployment auto-deploys or unblock the merge queue to auto-merge pull requests (`Commit#add_status` schedules `ContinuousDeliveryJob`/`ProcessMergeRequestsJob` on transition to success) [9](#0-8) .
- Forge `push` events to trigger `GithubSyncJob`/`sync_github` for any stack under the spoofed `repository.full_name`, and forge `pull_request` events to create/archive review stacks for repositories it doesn't own [10](#0-9) [11](#0-10) .

The end result is an unauthorized deploy/merge triggered against a repository the attacker never had write or webhook access to, satisfying the Critical/High impact bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires the operator to run Shipit's documented multi-organization configuration with at least one organization configured with `webhook_secret: nil` (explicitly supported/documented as optional) while other tracked organizations have real secrets — a realistic, supported deployment pattern, not a misconfiguration outside the engine's design. No credentials, no GitHub App key, and no prior Shipit access are required; only knowledge (or a guess) of which configured organization has no secret and the target repo's `full_name`/commit SHA.

### Recommendation
Bind the signature verification to the same identity used to select and mutate data: after choosing the GitHub App config, re-derive the repository/organization actually referenced by `repository.full_name` and verify it belongs to the organization that was used to select the (possibly-secretless) app config, before dispatching to handlers. At minimum, refuse to process events for any organization with `webhook_secret` unset unless that organization actually owns the repository named in `repository.full_name`; better, always require a configured secret and reject requests where `repository.owner.login` doesn't match `repository.full_name`'s owner segment.

### Proof of Concept
1. Configure Shipit with two orgs per the documented multi-app layout: `OrgWithoutSecret` (`webhook_secret: nil`) and `OrgSecured` (`webhook_secret: <real secret>`), and track a stack for `OrgSecured/target-repo`.
2. As an anonymous attacker, `POST /webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, and body:
```json
{
  "sha": "<sha of a commit on OrgSecured/target-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgWithoutSecret" }, "full_name": "OrgSecured/target-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the signature header [3](#0-2) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `success` status on the targeted commit belonging to `OrgSecured/target-repo`, potentially triggering an unauthorized deploy or unblocking a merge, despite the attacker never having any credential for `OrgSecured`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
