### Title
Overflow in `update_supply_index` / `calculate_supplier_rewards` bricks an entire market once `supplied * index` exceeds `i128` — (File: common/src/rates/index.rs)

### Summary
The vesting-contract bug class — an unbounded `amount * factor` multiplication reverting under checked math — maps onto XOXNO Lending's interest accrual. `update_supply_index` computes `supplied.mul(env, old_index)` (a `scaled_to_original`-style `RAY` rescale) and `calculate_supplier_rewards` computes `borrowed * old/new_borrow_index`. All `Ray`/`Wad` multiplication goes through `fp_core::mul_div_*`, which panics with `GenericError::MathOverflow` when the exact result cannot fit `i128`. Because accrual runs at the head of every market verb, once the product crosses the `i128` ceiling the market is permanently frozen — the intended index caps never get a chance to engage.

### Finding Description
- `common/src/rates/index.rs:34` — `update_supply_index` multiplies `supplied` (scaled supply, RAY) by `old_index` (RAY). `supplied.mul` → `fp_core::mul_div_half_up` → `try_mul_div_half_up`, which returns `None` when the quotient leaves `i128` and panics with `MathOverflow` (`common/src/math/fp_core.rs:108-143`). `Ray::mul` does not saturate; only `calculate_scaled_cap`, `protocol_fee_shares`, and the `_saturating` helpers clamp.
- `common/src/rates/index.rs:80-81` — `calculate_supplier_rewards` multiplies `borrowed` by both borrow indexes with the same panicking path, so a large-debt market overflows even before the supply side does.
- `common/src/rates/scaling.rs:14-16` — `scaled_to_original` (`scaled * index`) is used by every position unscale (`unscale_supply`, `unscale_borrow_ceil`), so even the per-position path panics for a whale whose scaled balance times the index overflows.
- The index caps in `update_borrow_index`/`update_supply_index` (`MAX_BORROW_INDEX_RAY`, `MAX_SUPPLY_INDEX_RAY`, `index.rs:15-17, 43-44`) bound the *index*, not the `supplied * index` product, so they cannot prevent the overflow.
- This is demonstrated by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`), which shows `update_indexes` failing with `MATH_OVERFLOW` at borrow index ~170x — well below the cap — and then `withdraw` and `repay` failing with the same error because every verb accrues first. The test comment explicitly notes "the bound in docs/reference/formulas.md is wrong", so this is not an acknowledged documented limit.
- The Certora spec independently flags the same hole: `update_supply_index` "panics with `MathOverflow` once `supplied * old_index / RAY` leaves `i128`" (`certora/common/spec/rates_rules.rs:316-320`).

### Impact Explanation
Permanent freezing of funds / contract unable to operate. Once `supplied * supply_index` (or `borrowed * borrow_index`) crosses `i128::MAX`, `update_indexes` reverts, and since accrual precedes `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan` and every other controller verb touching that market, all user funds in the market are frozen with no recovery path — the panic is a function of stored state (`supplied`, monotonically growing `index`), not of caller input, so no argument choice avoids it.

### Likelihood Explanation
A single unprivileged address can put the market on the path: `supply(asset, amount)` up to the market cap, then `borrow` to drive utilization onto the steep segment of the interest-rate curve so the index compounds. Anyone can then call `update_indexes` permissionlessly to execute the accrual that trips the overflow. The ceiling is `i128::MAX / RAY ≈ 1.7e11` whole tokens of supplied/debt value; for an 18-decimal market with a high cap this is within the permitted cap domain (`require_cap_within_asset_domain` admits up to `max_cap_for_decimals`, `common/tests/validation.rs:349-371`). It requires a whale-scale balance and index growth, so it is a Medium-severity edge rather than a trivially triggered bug, matching the source report's severity.

### Recommendation
- Make the accrual-time products saturating or widened rather than panicking: use `mul_div_floor_saturating`/`I256` math for `supplied * old_index` in `update_supply_index` and for `borrowed * index` in `calculate_supplier_rewards`, or clamp `total_supplied_value`/`total_debt` at `i128::MAX` before the reward math.
- Alternatively enforce an on-chain invariant linking cap to the index headroom: derive the effective supply cap as `min(configured_cap, i128::MAX / index_unit_headroom)` and re-check it inside `supply`/`calculate_scaled_supply` so `supplied * index` is provably in range for the index's entire capped lifetime.
- Correct the numeric-limits bound in `docs/reference/formulas.md`, which the harness test shows does not hold before the freeze.

### Proof of Concept
Already encoded in the repo (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply up to lifted cap
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);             // ~98% utilization on the steep curve
// advance years; each call to update_indexes accrues:
//   update_supply_index: supplied.mul(old_index)  -> MathOverflow
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
// market permanently frozen — every verb accrues first:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
assert!(book(&t, "BIG18").borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged
```

The panic originates at `supplied.mul(env, old_index)` in `update_supply_index` (`common/src/rates/index.rs:34`) via `fp_core::mul_div_half_up`'s `MathOverflow` path (`common/src/math/fp_core.rs:116-117`), with the debt-side equivalent at `index.rs:80-81`.
