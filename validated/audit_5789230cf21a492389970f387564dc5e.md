### Title
Webhook Signature Verified Against One Organization While Commit Statuses Are Written Cross-Tenant By SHA - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook by HMAC-verifying the raw body against the `webhook_secret` belonging to whichever GitHub organization is named in `repository.owner.login` (or `organization.login`) inside that same body. [1](#0-0)  Shipit supports hosting multiple independent GitHub organizations in one instance, each with its own `webhook_secret`, looked up via `Shipit.github_app_config(organization)`. [2](#0-1)  Once the signature is accepted, the raw JSON is dispatched to event handlers that trust *other* fields of the same payload without re-validating them against the organization whose secret produced the signature. `StatusHandler` in particular applies the status update to every `Commit` in the entire database matching the supplied `sha`, with no scoping to the organization or repository that was authenticated. [3](#0-2) 

### Finding Description
The equality that should hold is:
`organization whose webhook_secret authenticated the request == organization/repository whose state is mutated by the handler`

`verify_signature` derives the authenticating organization strictly from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), and fetches that organization's `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`. [4](#0-3) [5](#0-4) 

The `create` action then hands the entire raw `params` hash to every registered handler for the event, unmodified: [6](#0-5) 

`StatusHandler#process` never consults `repository`/`organization` at all — it looks up every `Commit` row across the whole install whose `sha` matches the attacker-chosen value and writes a GitHub-style status onto it: [7](#0-6) 

Because Shipit's documented multi-tenant configuration keys `secrets.github` by organization, each with its own independently-known `webhook_secret` (an operator/administrator of one onboarded org knows their own secret) [8](#0-7) [9](#0-8) , anyone who administers organization "OrgX" in such a deployment can compute a valid `X-Hub-Signature` over an arbitrary raw body using `OrgX`'s secret. They then set `repository.owner.login: "OrgX"` (to satisfy `verify_signature`) while setting `sha`, `state`, and `context` to target a commit that actually belongs to an unrelated tenant/organization "OrgY" tracked by the same Shipit instance. The signature check passes because it only inspects `repository.owner.login`, but `StatusHandler` applies the forged status to `OrgY`'s commit, since it queries `Commit` globally by `sha` with no ownership check.

This same "authenticated org field vs. handler's target field" split exists more broadly: other handlers key their target lookup off `repository.full_name` (a sibling field never checked by `verify_signature`), e.g. `Handler#repository_name` and its many subclasses (`PushHandler`, the `PullRequest::*Handler`s). [10](#0-9) [11](#0-10)  `StatusHandler` is the most severe instance because it performs no repository binding whatsoever.

### Impact Explanation
A forged, cross-tenant commit status is used directly by the merge queue to decide whether a pull request is safe to merge and by deploy readiness checks. `MergeRequest#all_status_checks_passed?` / `#any_status_checks_failed?` / `#any_status_checks_missing?` all evaluate `StatusChecker` against the commit's statuses, which the attacker just controls. [12](#0-11)  When the merge queue subsequently believes the required CI checks succeeded, `MergeRequest#merge!` calls `stack.github_api.merge_pull_request(...)`, i.e. Shipit's own GitHub App credentials perform the merge on the victim's real repository. [13](#0-12)  This is an unauthorized cross-organization merge/deploy triggered purely by an attacker who only controls credentials for a different, unrelated tenant organization in the same Shipit instance — matching the Critical impact category (unauthorized merge/deploy, cross-repository writes) defined in scope.

### Likelihood Explanation
Exploitation requires: (1) a Shipit deployment configured for multiple GitHub organizations (an explicitly documented and supported configuration in `docs/setup.md`), and (2) the attacker administering/onboarding at least one of those organizations (and thus knowing its `webhook_secret`), and (3) knowledge of a target commit SHA belonging to another tenant (git SHAs are not secret — they are routinely visible in PR pages, CI logs, chat notifications, or even Shipit's own public UI/API for that other stack). No Shipit session, API token, or GitHub push access to the victim's repository is required. This is a realistic scenario for any organization operating Shipit as a shared/internal platform across several teams or subsidiaries.

### Recommendation
`WebhooksController#verify_signature` should bind the verified organization to every downstream identifier the handler will act on, not just to `repository.owner.login`. Concretely: after verifying the signature for the derived `repository_owner`, `StatusHandler` (and other handlers) must additionally confirm that the `Commit`/`Repository`/`Stack` they are about to mutate actually belongs to that same verified organization (e.g., scope `Commit.where(sha: params.sha)` through `joins(:stack => :repository).where(repositories: { owner: repository_owner })`), rejecting or ignoring any status/push/pull_request update whose target repository owner does not match the organization whose secret authenticated the request.

### Proof of Concept
1. Operate (or be granted admin rights to configure) organization `OrgX` in a Shipit instance configured with the multi-org `github:` schema, and note `OrgX`'s `webhook_secret`.
2. Identify the SHA of a commit belonging to a stack of a different tenant, `OrgY/critical-repo`, e.g. `abc123...` (visible via that stack's public Shipit page or GitHub PR).
3. Build the payload:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgX" } }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgX_webhook_secret, body)>` and POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` to `"OrgX"`, fetches `OrgX`'s app/secret, and the signature validates. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the commit belonging to `OrgY/critical-repo`, and creates a forged "success" status on it, with no organization/repository check performed. [3](#0-2) 
7. If that commit is head of a queued `MergeRequest` on `OrgY`'s stack waiting on that CI context, Shipit's merge queue will subsequently consider it mergeable and merge it via `OrgY`'s stack's real GitHub credentials. [13](#0-12) 

Note: I was unable to fully verify at what SHA-collision granularity `StatusHandler` is exercised in production (i.e., whether operators commonly run true multi-org configurations), since that is a deployment-time choice; the code path itself, however, contains no repository/organization check and is confirmed directly from the cited files.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
