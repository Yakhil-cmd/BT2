### Title
Webhook signature verification is keyed on an attacker-controlled organization field that is decoupled from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate an inbound webhook's HMAC against using a field taken from the *unauthenticated* JSON body itself, while every downstream event handler resolves the *target* repository/stack from a different field in that same body. In a Shipit installation configured with multiple GitHub Apps (one per organization, as documented for multi-org setups), this breaks the binding "organization that authenticated == repository that is written," analogous to the reported `aggregator::remove_job` bug where a value used for one purpose (lookup/validation) silently diverges from the value actually mutated.

### Finding Description
`verify_signature` picks the app config used to validate `X-Hub-Signature` like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted, attacker-supplied request body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and it is used to look up `Shipit.github(organization: repository_owner)` — i.e., which of possibly several configured `webhook_secret`s to verify the HMAC against.

Every downstream handler, however, resolves the actual repository/stack to mutate using a **different field**, `repository.full_name`: [3](#0-2) [4](#0-3) 

Because HMAC verification only checks that the raw POST body matches a signature computed with *some* configured secret — it never asserts that the org whose secret was used for verification is the same org that owns the repository named in `full_name` — an attacker who possesses the `webhook_secret` for one configured GitHub App (organization "OrgA") can forge a fully valid signature over a payload where `repository.owner.login` (or `organization.login`) is `"OrgA"` (to select OrgA's secret) but `repository.full_name` is `"OrgB/some-tracked-repo"`. The signature check passes because it only verifies "this body was signed with OrgA's secret," not "this body's referenced repository belongs to OrgA." Documentation confirms multi-org configurations exist with independent secrets per org: [5](#0-4) 

This exactly matches the reported bug class: a value ("organization" used to authenticate) is checked/consumed for one purpose while a *different*, unguarded value ("repository" actually written) drives the real mutation — the equivalent of `remove_job`'s `job_ref_count` being decremented for a job whose actual removal check silently used a different, unvalidated code path.

### Impact Explanation
With a forged-but-validly-signed `push`, `status`, or `check_suite` event targeting `OrgB/some-tracked-repo`, an attacker who only knows OrgA's webhook secret can:
- Force `Shipit::Webhooks::Handlers::PushHandler` to enqueue `GithubSyncJob` for OrgB's stack with an attacker-chosen `expected_head_sha` [4](#0-3) .
- Potentially forge commit/check-run status transitions to `success` for OrgB's stack via the `status`/`check_suite` handlers, which — combined with `continuous_deployment?` — triggers a real, unauthorized deploy: `Commit#schedule_continuous_delivery` fires `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery`, ultimately calling `trigger_deploy` [6](#0-5) [7](#0-6) [8](#0-7) .

This crosses an organizational trust boundary: only OrgA's webhook secret is needed to influence deploy state for any other organization's repositories tracked by the same Shipit instance, meeting the "unauthorized deploy" Critical-impact bar in scope.

### Likelihood Explanation
This requires (a) a multi-GitHub-App Shipit deployment (explicitly documented and supported) and (b) possession of one configured organization's `webhook_secret` (e.g., an org admin/insider of a lower-trust org onboarded to the same Shipit instance, or a leaked secret for one org). Given that per-org webhook secrets are exactly the mechanism meant to keep tenants isolated, this is a realistic multi-tenant scenario where the org boundary is expected to hold but does not.

### Recommendation
Bind signature verification to the same repository identity used for routing. Concretely, resolve the target repository via `repository.full_name` (or an explicit, trusted mapping of tracked `Repository` → its owning GitHub App/organization) *before* selecting which webhook secret to verify against, rather than trusting `repository.owner.login`/`organization.login` from the unauthenticated payload. Reject the webhook if the app selected for verification does not match the app configured for the resolved repository's actual organization.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with distinct `github.webhook_secret`s, and both track repositories (e.g., `OrgB/prod-app` has `continuous_deployment: true`).
2. Attacker has `OrgA`'s webhook secret.
3. Attacker crafts a `push` (or `status`) JSON body with:
   - `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`)
   - `repository.full_name = "OrgB/prod-app"`
   - forged `ref`/`after` (or CI `state: "success"`) fields.
4. Attacker computes `X-Hub-Signature` using OrgA's `webhook_secret` over this exact raw body and POSTs it to `/webhooks` with header `X-Github-Event: push` (or `status`).
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully since the signature matches OrgA's secret over the exact bytes sent.
6. `Shipit::Webhooks.for_event('push').each { |h| h.call(params) }` runs `PushHandler`, which resolves the target stack via `repository.full_name = "OrgB/prod-app"` and enqueues `GithubSyncJob`/commit-state updates for OrgB's stack — despite the request never being authenticated by OrgB's secret.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end
