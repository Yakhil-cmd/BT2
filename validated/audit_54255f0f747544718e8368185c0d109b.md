Confirmed: `GET /stacks/*stack_id/ccmenu` is routed to `Api::CCMenuController#show` [1](#0-0)  and the `stack_id` path segment is completely attacker-controlled while authentication happens via a raw token param, independent of that path segment [2](#0-1) .

### Title
Stack-scoped ApiClient tokens bypass their `stack_id` scope in `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController` is supposed to enforce that scope on every request by resolving the target stack through the `stacks`/`stack` helpers [3](#0-2) . `Api::CCMenuController` overrides `stack` to resolve the target directly from `params[:stack_id]` via `Stack.from_param!`, bypassing the scoping entirely [4](#0-3) . This is the same class of bug as the Union `debtWriteOff` finding: the resource used to authorize the token (the `stack` a token is bound to via `ApiClient#stack_id`) is not the same as the resource the operation actually acts on (the `stack_id` supplied in the request), even though the permission check (`require_permission :read, :stack`) only validates the permission string, not the identity of the stack.

### Finding Description
`ApiClient#check_permissions!` only checks that the required permission string (`"read:stack"`) is present in the client's `permissions` array; it never compares the client's `stack_id` to the stack being accessed [5](#0-4) . The stack-scope enforcement is supposed to happen in `Api::BaseController#stacks`, which restricts the queryable set of stacks to `Stack.where(id: current_api_client.stack_id)` when the client is scoped [6](#0-5) , and `#stack` (used by e.g. `Api::HooksController`) resolves through that scoped `stacks` relation [7](#0-6) .

`Api::CCMenuController`, however, redefines `#stack` to bypass this scoping: `@stack ||= Stack.from_param!(params[:stack_id])` reads directly from the unscoped `Stack` model using the attacker-supplied `stack_id` path segment [8](#0-7) . The route `GET /stacks/*stack_id/ccmenu` accepts an arbitrary `stack_id` [1](#0-0) , and this controller also allows authenticating solely via a `token` query-string param instead of the `Authorization` header [2](#0-1) , which is exactly the credential distributed by `CCMenuUrlController#fetch`/`ccmenu_url` links embedded in the stack settings page [9](#0-8) .

The binding that should hold is: `stack a token authorizes == stack a token touches`, i.e. `current_api_client.stack_id == stack.id` for any scoped `ApiClient`. Because `Api::CCMenuController#stack` never consults `current_api_client.stack_id`, this equality is broken: a token scoped to Stack A (`current_api_client.stack_id == A.id`) can be replayed against `/stacks/*B/ccmenu` for any other Stack B (`stack.id == B.id`), and the request still passes `require_permission :read, :stack` because the client does hold the `read:stack` permission string, just not for that stack.

The `test/fixtures/shipit/api_clients.yml` fixture `here_come_the_walrus` demonstrates that scoped clients are a first-class, expected configuration (`stack: shipit`, `permissions: ['read:stack']`) [10](#0-9) , and `Api::StacksControllerTest` explicitly verifies that such a scoped client sees only its own stack through the properly-scoped `#index`/`#stack` path [11](#0-10) . No equivalent scoping test exists for `Api::CCMenuController`, and the code path confirms none would pass.

### Impact Explanation
This is an unauthorized cross-stack read: a token that was only ever meant to authorize CCMenu polling for one stack (often distributed as a bare URL/token via `ccmenu_url`, intended for CI-dashboard tools) can be used to read build/deploy status (`deploys_and_rollbacks`, lock state, last build label/time) of any other stack in the installation, including private/internal stacks the token holder was never granted access to. This crosses the "unauthenticated read of stack state" boundary defined as a valid High-impact class for this engine, since the credential holder is authenticated as *some* client but reads state of a repository/stack outside its granted scope.

### Likelihood Explanation
Likelihood is high for any deployment that issues scoped `ApiClient` tokens (a documented, supported feature, exercised by the `stack:` fixture) and exposes CCMenu URLs, since exploitation requires only swapping the `stack_id` segment of a known/leaked CCMenu URL — no additional privilege, session, or secret is needed beyond the token itself, which is exactly the credential this scoping mechanism is meant to constrain.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the same scoped lookup used elsewhere, e.g. `stacks.from_param!(params[:stack_id])` (reusing `Api::BaseController#stacks`), so a stack-scoped `ApiClient` can only ever resolve its own bound stack, matching the enforcement already relied upon by `Api::HooksController` and `Api::StacksController`.

### Proof of Concept
1. Create two stacks, A and B.
2. Create a scoped `ApiClient` bound to stack A with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`).
3. Obtain/derive its `authentication_token`.
4. Issue `GET /stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token>`.
5. Observe `Api::CCMenuController#authenticate_api_client` succeeds via the token, `require_permission :read, :stack` passes because the permission string is present, and `#stack` resolves stack B directly via `Stack.from_param!`, returning stack B's CCMenu XML (deploy/build status) — despite the client being scoped exclusively to stack A.
