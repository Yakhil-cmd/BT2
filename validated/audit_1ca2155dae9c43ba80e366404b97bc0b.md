### Title
Webhook Signature Verified Against Requesting Organization's Secret, But Handlers Act on an Unverified `repository.full_name` Field, Enabling Cross-Organization Forged Push Events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate `X-Hub-Signature` using `repository_owner`, which is parsed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [2](#0-1)  Once the HMAC verifies against *that* organization's secret, the raw JSON body is handed unmodified to event handlers, which instead trust `payload.dig('repository', 'full_name')` to resolve which `Repository`/`Stack` to act on. [3](#0-2) [4](#0-3)  Nothing ties `repository.owner.login` (the field whose value drove secret selection) to `repository.full_name` (the field whose value drives which stack gets updated). This is analogous to the `GaugeExtraRewarder` bug: a value used for accounting/authorization (`lastRewardTime`, here the "authenticated organization") diverges from the value actually acted upon (accrued rewards, here the "written repository").

### Finding Description
- `Shipit.github(organization:)` looks up a per-organization config block (`secrets.github[org]`), each with its own independent `webhook_secret`, when the multi-org schema is used. [1](#0-0) 
- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and validates the signature solely against that organization's secret. [5](#0-4) 
- `repository_owner` is read from `params.dig('repository', 'owner', 'login')` — attacker-controlled JSON, not itself covered by any additional binding to the rest of the payload. [6](#0-5) 
- After the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` passes the *entire* parsed body — including `repository.full_name` — to handlers. [7](#0-6) 
- `Handler#stacks` / `Handler#repository_name` resolve the target `Repository` via `payload.dig('repository', 'full_name')`, a completely separate field from the one used for signature-org selection. [3](#0-2) 
- `Repository.from_github_repo_name` splits this `full_name` on `/` and looks up any repository in the database by `owner`/`name`, with no re-check that it matches `repository_owner`. [8](#0-7) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the resolved branch, which enqueues `GithubSyncJob`. [9](#0-8) 
- `GithubSyncJob` fetches new commits from GitHub (using that *stack's own* configured GitHub App/API client, not the attacker's) and appends them, and can trigger continuous deployment for the targeted stack. [10](#0-9) 

**Binding broken:** the organization whose `webhook_secret` authenticated the request (`repository.owner.login`) ≠ the repository whose stacks are looked up and synced (`repository.full_name`). The verified field and the acted-upon field are disjoint attacker-controlled JSON keys in the same payload.

### Impact Explanation
An attacker who legitimately controls (or has compromised) the webhook secret for **one** organization configured in a multi-org Shipit deployment (e.g., an organization admin who installed their own GitHub App pointed at the shared Shipit instance, per the documented multi-org setup) can forge a signed webhook whose `repository.owner.login` matches their own org (so it passes `verify_signature` with their own secret) but whose `repository.full_name` names a *different* organization's tracked repository/stack. This forged event will be processed as genuine for that unrelated stack, causing Shipit to sync github state and, depending on `continuous_deployment` settings, cascade toward an unauthorized deploy of that other organization's stack — a cross-repository/cross-organization trust violation. This satisfies the "unauthorized deploy" / "cross-repository writes" High/Critical bar.

### Likelihood Explanation
Requires: (1) the deployment to use the multi-organization GitHub config schema documented in `docs/setup.md`/`config/secrets.development.example.yml`, and (2) the attacker to control a valid webhook secret for at least one configured organization (a realistic scenario for shared, multi-tenant Shipit installations where different teams/orgs each install their own GitHub App). No GitHub OAuth session, `ApiClient` token, or direct database access is required — only knowledge of one org's `webhook_secret`, which by design many separate parties hold in a multi-org setup.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that `payload.dig('repository', 'full_name')`'s owner matches `repository_owner` (the organization whose secret validated the signature) before dispatching to handlers. Reject the webhook (422) if the two disagree, closing the gap between the authenticated identity and the entity being written.

### Proof of Concept
1. Deploy Shipit with the multi-org config schema: org `attacker-org` and org `victim-org`, each with distinct `webhook_secret`s, both tracked as repositories/stacks in the same Shipit instance.
2. Attacker (who controls/knows `attacker-org`'s webhook secret) crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-reachable-on-victim-org-repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact raw body and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature against `attacker-org`'s secret. [5](#0-4) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, matching real `victim-org` stacks, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` for the victim's stack. [9](#0-8) [11](#0-10)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
