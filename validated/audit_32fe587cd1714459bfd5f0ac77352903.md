Confirmed: `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) bypasses the stack-scoping enforced everywhere else in the API, and the route at `config/routes.rb:27-28` reaches it via a `stack_id` URL segment that is fully attacker-controlled while the `token` is looked up independently.### Title
CCMenu API token scope bypass allows reading any stack's build/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `Api::CCMenuController` overrides the shared `stack` lookup method used by every other API controller and drops the `ApiClient#stack_id` scoping check, so a token that was only authorized (`stack_id` bound) for one stack can be replayed against any other stack in the installation.

### Finding Description
Shipit's normal API stack lookup enforces token scope in `Api::BaseController`: [1](#0-0) 

`stacks` filters to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that filtered relation. This is the binding: "stack a token authorises" (`current_api_client.stack_id`) MUST equal "stack it touches" (`stack` resolved from `params[:stack_id]`).

`Api::CCMenuController`, however, defines its own `stack` private method that ignores the client's scope entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

It resolves directly against `Stack.from_param!(params[:stack_id])` — the full `Stack` relation, not `stacks` (the scoped relation from the base controller). The only guard is `require_permission :read, :stack`, which is a permission-bit check, not a scope check: [3](#0-2) 

`check_permissions!` only verifies the client has the `read:stack` bit; it never compares `stack_id` against the requested resource.

The token itself is provisioned scoped to exactly one stack via `CCMenuUrlController`: [4](#0-3) 

`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` is created without a `stack:` association in this snippet's visible code, but the CCMenu URL itself is stack-specific (`api_stack_ccmenu_url(stack_id: stack.to_param)`), and the route is scoped per-stack: [5](#0-4) 

Regardless of whether the produced token is globally scoped or stack-scoped, any `ApiClient` record anywhere in the system that carries `read:stack` permission and has a non-nil `stack_id` (the documented/expected scoping mechanism, enforced by `Api::BaseController#stacks`) can be used to bypass that scoping specifically on the CCMenu endpoint, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
This breaks the "stack a token authorises versus stack it touches" trust binding described in the analog bug class. A CCMenu token minted/leaked for stack A (e.g., embedded in a CI dashboard URL, browser extension, or a locked-down deploy dashboard) can be used to read build/deploy/lock status of any other stack B by simply changing the `stack_id` path segment, per `app/views/shipit/ccmenu/project.xml.builder`, which exposes `lastBuildStatus`, `activity`, `lastBuildTime`, `lastBuildLabel`, and `webUrl` for the targeted stack. This matches the "High - unauthenticated read of stack state ... deploy output" impact bucket: an attacker holding a token meant to be restricted to one stack gains read access to state of stacks it was never authorized for.

### Likelihood Explanation
Likelihood is significant among holders of any valid CCMenu-style API token (which by design is meant to be narrowly scoped and is often embedded in low-security contexts like CI dashboards, IRC/RSS integrations, or browser bookmarks). No additional privilege escalation, session, or GitHub credential is required — only a query-string token that is already intentionally distributed for read-only monitoring purposes, plus knowledge/guessing of another stack's identifier (`owner/repo/branch`), which is often discoverable (stack names are visible in the Shipit UI to any authenticated user, or guessable from repository names).

### Recommendation
Make `Api::CCMenuController#stack` respect the API client scope like every other API controller, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
reusing (not overriding) the `stacks`/`stack` scoping helpers already defined in `Api::BaseController`. Additionally, consider always minting CCMenu tokens with an explicit `stack:` association (never `nil`) so the base-controller scoping in `app/controllers/shipit/api/base_controller.rb:74-80` is guaranteed to apply.

### Proof of Concept
1. As a Shipit user, obtain a CCMenu URL/token for Stack A via the UI, which internally calls `CCMenuUrlController#fetch` → `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`), yielding `?token=<TOKEN>` for `api_stack_ccmenu_url(stack_id: "org/repoA/branch")`.
2. Send: `GET /api/stacks/org/repoB/otherbranch/ccmenu?token=<TOKEN>` (a stack the token was never meant to access).
3. `Api::BaseController#authenticate_api_client` (overridden in `CCMenuController` to accept `params[:token]`, `app/controllers/shipit/api/ccmenu_controller.rb:33-36`) successfully authenticates the client.
4. `require_permission :read, :stack` passes because the client has the `read:stack` bit (`app/models/shipit/api_client.rb:38-45`), regardless of which stack is targeted.
5. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), ignoring `current_api_client.stack_id`, and returns Stack B's XML status — successfully reading Stack B's build/deploy state using a token only ever authorized for Stack A.
