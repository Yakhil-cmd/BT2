## Analog Vulnerability Found

The Discourse Calendar bug is a classic "missing invitation/membership check on a state-mutating message" — a client can send an update (attendance) for a resource (an event) without the server ever verifying that the sender was actually invited to interact with it. The closest reachable analog in `ocore` is the handling of the `new_shared_address` device message.

### Title
Uninvited correspondent device can register itself as a cosigner of another user's shared (multisig) address - (File: `wallet_defined_by_addresses.js`)

### Summary
`handleNewSharedAddress()`, invoked from the `new_shared_address` device-message handler in `wallet.js`, accepts and persists an entire multi-party address definition and its cosigner list from any already-paired correspondent, without ever checking that the sender (`from_address`) is one of the parties actually referenced in `body.signers`. It only checks that *one of the recipient's own addresses* is present in the definition.

### Finding Description
The `new_shared_address` case in `wallet.js` is dispatched to `walletDefinedByAddresses.handleNewSharedAddress`: [1](#0-0) 

`handleNewSharedAddress` performs structural validation (definition hash matches c-hash, signer addresses match definition paths) and calls `determineIfIncludesMeAndRewriteDeviceAddress`, which only verifies that one of the recipient's own or shared addresses appears somewhere in the definition — it never checks that the message actually originated from one of the declared signers/cosigners: [2](#0-1) [3](#0-2) 

Contrast this with the legitimate multi-step negotiation flow (`create_new_shared_address` → `validateAddressDefinitionTemplate`, which explicitly checks `arrDeviceAddresses.indexOf(from_address) === -1` to ensure the sender is a declared member) and `approve_new_shared_address`, which only updates rows keyed by the requesting `from_address`: [4](#0-3) 

`new_shared_address`, however, bypasses that entire pending-approval negotiation (`pending_shared_addresses` / `pending_shared_address_signing_paths`) and is accepted directly, as long as the recipient is already a paired correspondent of the sender (device message delivery requires a known correspondent, per the check in `device.js`): [5](#0-4) 

Once accepted, `addNewSharedAddress` unconditionally writes the attacker-supplied definition and signer map into `shared_addresses` / `shared_address_signing_paths`, and — for light clients — starts watching the address and forwards it to the victim's other cosigning devices: [6](#0-5) 

This is the same bug class as the CVE: a state-changing action (joining/being registered as a party to a shared entity) is accepted from an actor who was never invited into that specific relationship, because the check only validates "does this touch me" rather than "did the claimed party actually agree to this."

### Impact Explanation
An already-paired correspondent (e.g., a merchant, service bot, or any device the victim has paired with for an unrelated purpose) can craft a `new_shared_address` message naming the victim's real address plus an attacker-controlled address in an `["and", ...]` or `["or", ...]` definition. The victim's wallet will silently record this as a legitimate shared address and cosigner relationship, without any confirmation dialog corresponding to the actual negotiation flow, and will forward/propagate it to the victim's other cosigning devices and correspondents (`forwardNewSharedAddressToCosignersOfMyMemberAddresses`). This can be leveraged to trick the victim's wallet into treating attacker-chosen addresses as "my"/shared addresses (subject to signing requests, private-payment forwarding, and light-wallet watching), enabling social-engineering-driven fund-loss scenarios (e.g., the victim being prompted to sign a transaction moving funds into or via a bogus shared address) or wallet-state pollution that can lead to accepting private payments/outputs tied to an address the victim never agreed to share.

### Likelihood Explanation
Requires only that the attacker be a paired correspondent of the victim — a low bar, since pairing is commonly done via one-time codes/QR shared broadly (e.g., wallet support bots, merchants, exchanges). No cryptographic proof of the other cosigner's consent is required; only definition self-consistency (chash match) is checked.

### Recommendation
In `handleNewSharedAddress` (`wallet_defined_by_addresses.js`), require that `from_address` matches the `device_address` of at least one of the non-self signers declared in `body.signers` before accepting and persisting the shared address, similar to the `from_address` membership check already performed in `validateAddressDefinitionTemplate`. Alternatively, route `new_shared_address` through the same pending-approval bookkeeping (`pending_shared_addresses`) so that a shared address is only finalized after having been previously offered and explicitly approved by the local device.

### Proof of Concept
1. Attacker device `D_a` pairs with victim device `D_v` (e.g., posing as a merchant/support chat).
2. Attacker crafts `arrDefinition = ["and", [["address", VICTIM_ADDR], ["address", ATTACKER_ADDR]]]`, computes `shared_address = chash160(arrDefinition)`.
3. Attacker sends a device message with `subject: "new_shared_address"`, `body: {address: shared_address, definition: arrDefinition, signers: {"r.0": {address: VICTIM_ADDR, device_address: D_v}, "r.1": {address: ATTACKER_ADDR, device_address: D_a}}}`.
4. `wallet.js`'s `new_shared_address` case calls `handleNewSharedAddress`, which passes all structural checks (chash match, signer/definition path match) and `determineIfIncludesMeAndRewriteDeviceAddress` succeeds because `VICTIM_ADDR` is one of the victim's own addresses — with no check that `D_a` was ever invited to form this relationship.
5. `addNewSharedAddress` persists the shared address on the victim's node and propagates it further, without any confirmation flow matching the intended `create_new_shared_address` → `approve_new_shared_address` negotiation.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function validateAddressDefinitionTemplate(arrDefinitionTemplate, from_address, handleResult){
	try{
		var assocMemberDeviceAddressesBySigningPaths = getMemberDeviceAddressesBySigningPaths(arrDefinitionTemplate);
	}
	catch (e) {
		return handleResult("failed to get member device addresses of new shared address: " + e.toString());
	}
	var arrDeviceAddresses = _.uniq(_.values(assocMemberDeviceAddressesBySigningPaths));
	if (arrDeviceAddresses.length < 2)
		return handleResult("less than 2 member devices");
	if (arrDeviceAddresses.indexOf(device.getMyDeviceAddress()) === - 1)
		return handleResult("my device address not mentioned in the definition");
	if (arrDeviceAddresses.indexOf(from_address) === - 1)
		return handleResult("sender device address not mentioned in the definition");
