### Title
Authorization token re-attached on cross-scheme (HTTPS→HTTP) redirects due to hostname-only same-origin check - (File: `api/http_client.go`)

### Summary
`AddAuthTokenHeader` in `api/http_client.go` decides whether to re-attach the GitHub OAuth token to a redirected request by comparing only the hostname (`getHost(req)`) of the original and redirect-target requests. It never compares URL scheme. A redirect from `https://` to `http://` on the *same host* is therefore treated as "same origin" and the token is reattached, causing an authenticated bearer token to be transmitted in plaintext.

### Finding Description
This is the closest present-tense analog to the reported "incomplete state-transition check" bug class (in the original report, `getTotalRewards`/eligibility checks failed to account for the imminent reward-period transition, letting an attacker exploit an incomplete verification window). Here, the analogous incomplete check is in the redirect/host-trust guard that gates whether the `Authorization` header is resent: [1](#0-0) 

```go
func AddAuthTokenHeader(rt http.RoundTripper, cfg tokenGetter) http.RoundTripper {
	return &funcTripper{roundTrip: func(req *http.Request) (*http.Response, error) {
		if req.Header.Get(authorization) == "" {
			var redirectHostnameChange bool
			if req.Response != nil && req.Response.Request != nil {
				redirectHostnameChange = getHost(req) != getHost(req.Response.Request)
			}
			// Only set header if an initial request or redirect request to the same host as the initial request.
			if !redirectHostnameChange {
				...
				req.Header.Set(authorization, fmt.Sprintf("token %s", token))
			}
		}
		return rt.RoundTrip(req)
	}}
}

`getHost` only returns `r.Host` or `r.URL.Host`, which never includes the scheme:
```go
func getHost(r *http.Request) string {
	if r.Host != "" {
		return r.Host
	}
	return r.URL.Host
}
```

The existing regression test only validates the intended (host-changed) case, and does not test a same-host scheme downgrade: [3](#0-2) 

Because Go's `net/http` client follows redirects transparently (including cross-scheme ones by default, since no `CheckRedirect` policy is set in `NewHTTPClient`), if a GitHub Enterprise Server (or any host `gh` is configured to talk to) issues a `30x` redirect from `https://host/...` to `http://host/...`, the `redirectHostnameChange` check evaluates to `false` (same `Host` value), and the CLI will reattach the user's OAuth token in the `Authorization` header on the follow-up plaintext HTTP request.

### Impact Explanation
An attacker who controls (or has compromised/can influence) a configured GitHub Enterprise Server host, or who can inject a redirect response for a `gh`-issued request (e.g., a malicious/compromised on-path proxy on the enterprise network, or a GHES admin panel/webhook misconfiguration returning a scheme-changing redirect), can force the CLI to disclose the live OAuth/PAT token over unencrypted HTTP. That token could then be observed by anyone able to see the plaintext traffic (e.g., shared corporate network, ISP-level intermediaries, misconfigured proxies) — effectively converting a same-host redirect into a credential-exfiltration primitive, without requiring the attacker to defeat TLS or perform a true MITM against the HTTPS leg of the connection.

### Likelihood Explanation
Requires a redirect response to be attacker-influenced — realistic to reach through:
- A compromised or malicious GHES/GHE instance the user is authenticated against.
- A misbehaving/compromised reverse proxy or load balancer in front of a legitimate GitHub Enterprise deployment that the CLI trusts.
This does not require MITM on the HTTPS connection itself; the "attacker-controlled host" only needs to issue a same-hostname, scheme-downgrading `Location` header, which `net/http`'s default redirect handling in Go will follow automatically since `NewHTTPClient` sets no `CheckRedirect` policy restricting scheme.

### Recommendation
Update the redirect same-origin check in `AddAuthTokenHeader` to compare full origin (scheme + host), not just host, e.g. compare `req.URL.Scheme + "://" + getHost(req)` against the original request's scheme+host, and additionally consider setting an explicit `CheckRedirect` policy on the client that refuses to downgrade from HTTPS to HTTP across redirects.

### Proof of Concept
1. Configure `gh` against a host (e.g. `ghe.internal.example`) with an active OAuth token.
2. From that host (attacker-controlled or compromised), respond to any authenticated `gh` API request with a `302 Found` and `Location: http://ghe.internal.example/<same-path>`.
3. Observe (via network capture or a test harness modeled on `TestHTTPClientRedirectAuthenticationHeaderHandling` but using an `http://` redirect target with the identical host) that `AddAuthTokenHeader` reattaches `Authorization: token <TOKEN>` to the follow-up plaintext `http://` request because `getHost(req) == getHost(req.Response.Request)` evaluates true despite the scheme downgrade. [3](#0-2) 

Note: I could not find any additional `CheckRedirect` hardening elsewhere in `api/http_client.go` or `ghAPI.NewHTTPClient` (external dependency `github.com/cli/go-gh/v2/pkg/api`) that would prevent the scheme downgrade before `AddAuthTokenHeader` is invoked; that library's internals were not indexed in this codebase and could not be verified further.

// AddAuthTokenHeader adds an authentication token header for the host specified by the request.
func AddAuthTokenHeader(rt http.RoundTripper, cfg tokenGetter) http.RoundTripper {
	return &funcTripper{roundTrip: func(req *http.Request) (*http.Response, error) {
		// If the header is already set in the request, don't overwrite it.
		if req.Header.Get(authorization) == "" {
			var redirectHostnameChange bool
			if req.Response != nil && req.Response.Request != nil {
				redirectHostnameChange = getHost(req) != getHost(req.Response.Request)
			}
			// Only set header if an initial request or redirect request to the same host as the initial request.
			// If the host has changed during a redirect do not add the authentication token header.
			if !redirectHostnameChange {
				hostname := ghauth.NormalizeHostname(getHost(req))
				if token, _ := cfg.ActiveToken(hostname); token != "" {
					req.Header.Set(authorization, fmt.Sprintf("token %s", token))
				}
			}
		}
		return rt.RoundTrip(req)
	}}
}
```

func TestHTTPClientRedirectAuthenticationHeaderHandling(t *testing.T) {
	var request *http.Request
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		request = r
		w.WriteHeader(http.StatusNoContent)
	}))
	defer server.Close()

	var redirectRequest *http.Request
	redirectServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		redirectRequest = r
		http.Redirect(w, r, server.URL, http.StatusFound)
	}))
	defer redirectServer.Close()

	client, err := NewHTTPClient(HTTPClientOptions{
		Config: tinyConfig{
			fmt.Sprintf("%s:oauth_token", strings.TrimPrefix(redirectServer.URL, "http://")): "REDIRECT-TOKEN",
			fmt.Sprintf("%s:oauth_token", strings.TrimPrefix(server.URL, "http://")):         "TOKEN",
		},
	})
	require.NoError(t, err)

	req, err := http.NewRequest("GET", redirectServer.URL, nil)
	require.NoError(t, err)

	res, err := client.Do(req)
	require.NoError(t, err)

	assert.Equal(t, "token REDIRECT-TOKEN", redirectRequest.Header.Get(authorization))
	assert.Equal(t, "", request.Header.Get(authorization))
	assert.Equal(t, 204, res.StatusCode)
}
