### Title
Stale `Account.owner` retains old owner's delegates after NFT transfer, letting them borrow against the new owner's collateral - ([File: contracts/controller/src/account.rs](contracts/controller/src/account.rs))

### Summary
The account struct stores `owner` at creation (`account.rs:64-70`) and it is never resynchronized when the position NFT is transferred. `require_owner_or_delegate` / `is_owner_or_delegate` (account.rs:115-140) authorize against this stale `account.owner`, while `require_account_owner` (account.rs:143-148) checks the live NFT owner via `storage::account_owner`. This mirrors the reported class: protocol logic assumes a stored privileged identity equals the current effective owner, and an ownership transfer silently invalidates that assumption.

### Finding Description
- `create_account` sets `Account.owner = owner` once at mint time (account.rs:64).
- `is_owner_or_delegate` returns true when `caller == owner` **or** when `caller` is an active manager listed in `storage::get_delegates(env, account_id, owner)` — keyed on the *stale* stored owner (account.rs:121-127).
- `load_or_create_account` applies this stale check for `AccountGuard::Migrate` and `AccountGuard::Multiply` (account.rs:101-109), which gate `migrate_from_blend` and `multiply` — both unprivileged entrypoints in scope.
- `set_account_delegate` (account.rs:242-275) authenticates the *current NFT owner* (`require_account_owner`) and mutates the delegate list keyed under `caller`. Delegates granted by a previous owner live under the previous owner's key and are never purged on transfer; `permissionless_entrypoints.txt` only notes that manager grants "go inactive" implicitly, but nothing removes existing `delegates` entries or updates `account.owner`.

Concretely: Alice owns account N, grants delegate D (an active position manager), then transfers NFT N to Bob (or Bob buys it). `account.owner` is still Alice. D remains in `get_delegates(N, Alice)` with an active manager registration, so `is_owner_or_delegate(N, D, Alice)` is still true. D can now call `multiply` (or `migrate_from_blend`) on Bob's account — opening/managing borrow positions backed by Bob's collateral — while Bob cannot revoke D, because `remove_delegate` writes under `get_delegates(N, Bob)`, not `(N, Alice)`. Alice herself can also still pass the owner check for Multiply/Migrate paths.

### Impact Explanation
Theft of user funds: a stale delegate (or the previous owner) can invoke `multiply`/`migrate_from_blend` on an account whose NFT they no longer hold, taking on debt and routing borrowed/swap proceeds per the strategy path, leaving the new owner with the liability. This is reachable entirely by an unprivileged address once it holds an active-manager delegate grant under the previous owner.

### Likelihood Explanation
Likelihood is moderate: it requires an account with an existing delegate grant to change hands via `position-nft::transfer`/`transfer_from`/`approve`-driven moves — a supported, documented flow (NFTs represent whole accounts). No privileged action is needed to exploit; the stale check is deterministic.

### Recommendation
Do not trust `Account.owner` after mint. Either resolve the effective owner via `storage::account_owner` (NFT owner) inside `is_owner_or_delegate`/`require_owner_or_delegate` for every authorization decision, or resynchronize `account.owner` and clear/re-key delegate entries whenever the NFT transfers (e.g., a controller hook invoked on transfer, or a lazy check in `load_or_create_account` that rewrites the stored owner and drops delegates keyed under the old owner).

### Proof of Concept
1. Alice calls `controller::supply` with `account_id = 0`, creating account N owned by Alice; adds delegate D (active manager) via `add_delegate`.
2. Alice transfers NFT N to Bob (`position-nft::transfer`). `Account.owner` still reads Alice; `get_delegates(N, Alice)` still contains D.
3. D calls `controller::multiply(account_id = N, ...)`. `require_owner_or_delegate(N, D, account.owner = Alice)` passes because `D ∈ delegates(N, Alice)` and D is an active manager.
4. Debt is minted against Bob's collateral; Bob cannot remove D (`remove_delegate` keys under Bob). Alternatively, Alice retains authority over Multiply/Migrate on an account she no longer owns.

Uncertainty noted: I could not fully verify within the iteration budget whether some other path (e.g., an NFT-transfer hook or `storage::account_owner` refresh inside `get_account`) already clears stale `account.owner`/delegates. If such synchronization exists elsewhere, the finding downgrades to a latent inconsistency rather than an exploitable authorization gap.
