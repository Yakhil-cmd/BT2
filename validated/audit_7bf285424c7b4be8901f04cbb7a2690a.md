This is a real, exploitable divergence: `WebhooksController#repository_owner` (used for signature verification) and `AssignedHandler#repository` (used for the actual DB mutation) read independent, attacker-controlled fields.

### Title
`repository_owner` fallback to `organization.login` diverges from `AssignedHandler`'s `repository.full_name`, allowing cross-tenant PullRequest mutation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) used to authenticate a request based on `repository_owner`, which falls back to `params.dig('organization','login')` whenever `repository.owner.login` is absent from the payload. `AssignedHandler` (and all `pull_request` handlers) never look at `repository.owner`/`organization` — they only require `repository.full_name` for locating and mutating the `PullRequest`/`Stack`. An attacker who controls a repository/organization with no (or a known) `webhook_secret` can pick that organization for signature verification while pointing `repository.full_name` at an unrelated, properly-secured victim stack.

### Finding Description
The binding the code implicitly assumes is: `verifier_org(repository_owner) == mutation_target_org(repository.full_name)`. This is false. `repository_owner` is computed as: [1](#0-0) 
while the mutating handler resolves the target repository independently from `params.repository.full_name`: [2](#0-1) 

`AssignedHandler`'s `ExplicitParameters` schema only `requires :repository do requires :full_name, String end` — it does **not** require `repository.owner`: [3](#0-2) 

So a payload can supply `repository.full_name` (satisfying the handler schema and pointing at the victim's tracked repo) while omitting `repository.owner.login`, causing `repository_owner` in the controller to fall back to `organization.login` — a field entirely independent of `repository.full_name` and not validated against it anywhere: [4](#0-3) 

`verify_signature` then does `Shipit.github(organization: repository_owner)`, which looks up per-organization config (multi-org deployments configure a `GitHubApp` — including `webhook_secret` and `bot_login` — per organization key): [5](#0-4) 

If the attacker names an organization that is configured in Shipit with a blank/`nil` `webhook_secret` (a supported and documented configuration, as shown in the dummy multi-org fixture), `verify_webhook_signature` trivially returns `true` regardless of the actual signature header: [6](#0-5) [7](#0-6) 

Once signature verification passes (against the attacker-chosen lenient organization), the raw payload is dispatched unchanged to every registered `pull_request` handler: [8](#0-7) 

`AssignedHandler#process` then runs against `repository.full_name`, which the attacker set to the victim's repo, and mutates the persisted `PullRequest` record for that repo/stack regardless of which organization's secret authenticated the request: [9](#0-8) 

No existing guard catches this: `drop_unhandled_event` only checks the event type, `verify_signature` never cross-checks its selected organization against `repository.full_name`, and `ExplicitParameters` for `AssignedHandler` never requires or validates `repository.owner`/`organization` at all.

### Impact Explanation
The attacker can write to the `PullRequest` record (`github_pull_request` JSON blob) of a stack belonging to a repository/organization whose webhook secret they never possessed, using only the credentials of a *different*, weakly-configured organization. Because Shipit auto-triggers behavior (e.g., review-stack provisioning/deploys keyed off PR state, and deploys running as the stack's configured `bot_login`/`Shipit.user`) from this same class of `pull_request` handlers, corrupting the cached PR state (assignees, labels, head sha reflected in `github_pull_request`) for an arbitrary tracked stack is a cross-tenant "payload for one repository mutating another's stack" — matching the Critical category. This is repeatable against any repository tracked by any Shipit-configured organization, as long as at least one organization configured on the instance uses a blank/weak `webhook_secret`, and blast radius spans every stack whose `repository.full_name` the attacker can guess (repo names are public GitHub data).

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (`github_default_organization` non-nil, i.e., `secrets.github` keyed by org), and (2) at least one configured organization with an empty/guessable `webhook_secret` (documented as valid, e.g. `webhook_secret: # nil` in `test/dummy/config/secrets_double_github_app.yml`). No authentication, GitHub App keys, or victim-org secrets are needed — only knowledge of the lenient org's name and the target repo's `full_name`, both discoverable via public GitHub/Shipit UI. This is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
Bind signature verification to the same repository that handlers act on: derive `repository_owner` strictly from `params.dig('repository','owner','login')` when `repository` is present, and separately validate that the resolved organization matches the owner segment of `repository.full_name` before dispatching to handlers. Reject any `pull_request`/`repository`-scoped payload where `repository.owner.login` is absent but `repository.full_name` is present, instead of silently falling back to `organization.login`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs via `secrets_double_github_app.yml`-style fixture: `LenientOrg` (blank `webhook_secret`) and `VictimOrg` (real `webhook_secret`, `bot_login` set).
2. Create `shipit_repositories(:victim)` under `VictimOrg/victim-repo` with a `Stack` and a `PullRequest` fixture (number: 42, differing `github_pull_request` state).
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no `X-Hub-Signature` (or garbage signature), and body:
   `{ "action":"unassigned","number":42,"pull_request":{...valid...},"repository":{"full_name":"VictimOrg/victim-repo"},"sender":{"login":"attacker"},"organization":{"login":"LenientOrg"} }`
4. Assert `response.status == 200` (signature bypass succeeded via `LenientOrg`).
5. Assert `Shipit::PullRequest.find_by(number: 42, ...).github_pull_request` changed to reflect the forged payload — i.e., `pull_request.reload.github_pull_request['assignees'] != original_assignees` — proving a write occurred on `VictimOrg`'s stack authenticated only by `LenientOrg`'s (weak) secret, violating the stated invariant that "a `pull_request` event only affects the repository/stack whose secret authenticated it."

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
