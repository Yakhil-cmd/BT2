### Title
Integer Overflow in Asset Denomination Cap Validation Bypasses Bounds Checking - (File: validation.js)

### Summary
`validateAssetDefinition()` in `validation.js` computes the declared total supply of a divisible asset with fixed denominations by summing `count_coins * denomination` for every entry in `payload.denominations`, then compares that sum against the asset's declared `cap`. Neither `denomInfo.count_coins` nor the product is bounded to stay within `Number.MAX_SAFE_INTEGER` (2^53-1), so, just like the Lua `struct` library integer overflow in CVE-2018-11219 that defeated the library's bounds check, the multiplication/summation in JS floating point silently loses precision once the true mathematical value exceeds the safe-integer range, letting an attacker craft a denomination table whose real sum is far larger (or different) than what the bounds check computes.

### Finding Description
`isPositiveInteger` is the only constraint placed on `count_coins`: [1](#0-0) 
There is no `MAX_CAP`-style upper bound on `count_coins` itself (only `denomInfo.denomination` gets an explicit `MAX_CAP` ceiling, and only conditionally after `pemCurvesFixMci`): [2](#0-1) 
The running total is accumulated with plain JS number arithmetic: [3](#0-2) 
and later compared for exact equality against the declared cap: [4](#0-3) 

Because `count_coins` can be any positive integer up to `Number.MAX_SAFE_INTEGER` and `denomination` up to `MAX_CAP` (9e15), the product `count_coins * denomination` for a single denomination entry — or the cumulative sum across up to `MAX_DENOMINATIONS_PER_ASSET_DEFINITION` (64) entries — can exceed `Number.MAX_SAFE_INTEGER`. Once that happens, IEEE-754 double rounding silently changes the represented value (rounding to the nearest representable double, potentially by large margins), exactly analogous to the Redis Lua `struct` bug where an integer overflow defeated the library's size/bounds check. An attacker (any unprivileged unit poster defining an asset, or an AA author whose formula computes `cap`/`count_coins`, see `aa_validation.js`) can choose `count_coins`/`denomination` pairs such that the rounded `total_cap_from_denominations` happens to equal the attacker-chosen `payload.cap`, even though the true, un-rounded sum of coins issuable across all denominations is different from (and can be made to look consistent with, while actually diverging from) the declared cap.

Because per-denomination issuance is independently enforced later (in `indivisible_asset.js` / `writer.js`) based on the raw stored `count_coins` and `denomination` for each row — not by re-deriving from `payload.cap` — the cap-vs-denominations consistency check in `validateAssetDefinition` is the only guard tying the user-facing `cap` value to the actual maximum issuable supply. Defeating that guard via float overflow lets a malicious asset definer publish a `cap` that does not truthfully bound the real total that can ever be issued through the denomination table, undermining every downstream assumption (wallets, other validators, AA logic) that `cap` represents the true maximum supply of the asset.

### Impact Explanation
This breaks the integrity guarantee that an asset's declared `cap` equals the true maximum number of coins mintable through its `denominations` table. Since every full node performs the same (overflowing) JS-number check during validation, all nodes agree the corrupted definition is valid — this is not a transient/DoS issue but a genuine protocol-level supply-inflation vector: the attacker can under/over-state `cap` relative to what the denomination table actually allows to be issued over time, deceiving asset holders and any AA or contract logic that trusts `cap` as the total-supply ceiling for the custom asset. This matches the "asset issuance and transfer conditions" analog class and results in concrete supply inflation for the affected asset.

### Likelihood Explanation
Any user can post a unit defining a new asset (`validateAssetDefinition` is reached by an ordinary "asset" message from an unprivileged unit poster), or an AA author can define an asset whose `cap`/`count_coins`/`denomination` are computed by AA formulas (`aa_validation.js` lines 233-292 impose the same unbounded `isPositiveInteger` check on `count_coins`). No special privileges, timing, or race conditions are required — only picking large integers for `count_coins`/`denomination`, making this trivially reachable and deterministic.

### Recommendation
- Bound `denomInfo.count_coins` (and the cap computed from it) to a safe value, e.g. reject `count_coins` or `denomInfo.denomination * denomInfo.count_coins` whenever it exceeds `Number.MAX_SAFE_INTEGER` or `constants.MAX_CAP`.
- Perform the sum-of-denominations check using an overflow-safe arithmetic (e.g. `BigInt`) instead of native JS numbers, and reject the asset definition if any intermediate product/sum exceeds `Number.MAX_SAFE_INTEGER`.
- Apply the same fix to the equivalent AA-definition validation path in `aa_validation.js`.

### Proof of Concept
1. Craft an "asset" message with `fixed_denominations: true` and a `denominations` array containing an entry such as `{ denomination: 100000000, count_coins: 90071992547409 }` (both individually pass `isPositiveInteger` and the conditional `MAX_CAP` check on `denomination`).
2. The true product `100000000 * 90071992547409 = 9007199254740900000000` vastly exceeds `Number.MAX_SAFE_INTEGER` (9007199254740991); JS float arithmetic rounds this to an imprecise double.
3. Choose a second denomination entry whose value, when added, makes `total_cap_from_denominations` (as computed with rounded doubles) equal an attacker-chosen `payload.cap` at line 2790 of `validation.js`, even though the mathematically true achievable total via full issuance of all denominations differs from `cap`.
4. The unit passes `validateAssetDefinition` on every node identically (deterministic float rounding), establishing an asset definition whose declared `cap` does not truthfully bound the real maximum issuable supply through the stored `asset_denominations` rows.
