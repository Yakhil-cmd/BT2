### Title
`handleSecondaryTriggers` aborts all sibling AA responses when one secondary AA bounces - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `handleSecondaryTriggers` iterates over every AA that receives an output from the current response unit using `async.eachSeries`, invoking `handleTrigger` for each one as an independent secondary trigger. [1](#0-0)  If any single secondary AA in that batch bounces (returns an error via its `onDone` callback), the entire `async.eachSeries` short-circuits and the outer trigger chain is unwound with `revert(...)` (or `bounce(err)` if already inside a secondary), unwinding/discarding the effects of *all* the other, unrelated secondary AAs that were successfully processed in the same batch. [2](#0-1) 

### Finding Description
When a primary or secondary AA trigger unit sends outputs to multiple independent AA addresses in one response unit, `handleSecondaryTriggers` fetches all of them and processes each with `handleTrigger` in series. [3](#0-2)  Each child trigger's completion callback treats *any* bounce message from that single secondary AA as a fatal error for the whole `async.eachSeries` run: `if (bounce_message) return cb(bounce_message);`. [4](#0-3)  Once `async.eachSeries` sees this error, it stops iterating (any subsequent unrelated AAs in `rows` are never even invoked) and calls the final handler with `err` set, which either calls `bounce(err)` (if this whole group was itself a secondary trigger) or `revert({...})` at the top level — explicitly labeled "one of secondary AAs bounced with error". [5](#0-4) 

This mirrors the reported pattern: a single failing "call" (here, one AA's bounce) inside a loop over several independent downstream endpoints (here, sibling AAs) is allowed to abort/roll back the processing of all the others, rather than the bounce being isolated to just the AA that failed. The AA that triggered this chain reaches this code path merely by posting a normal payment/trigger unit that fans out balances to multiple AA addresses — something any unprivileged unit poster or AA (as an intermediate hop) can construct, since `handleSecondaryTriggers` is invoked automatically whenever a response unit's outputs land on registered `aa_addresses`. [6](#0-5) 

### Impact Explanation
A user/attacker can craft (or cause) one AA response unit whose outputs go to several independent secondary AAs, where at least one of those secondary AAs is engineered (or naturally likely) to bounce (e.g., insufficient balance, a state precondition failure, or a deliberately malicious/buggy target AA). Because the bounce of that single secondary AA reverts the entire trigger chain, every other secondary AA that would otherwise have succeeded independently is also rolled back/bounced, its state changes and payments undone. [7](#0-6)  This can be used to:
- Grief/lock funds or block state updates in unrelated third-party AAs that happen to receive outputs in the same response unit as a failing AA.
- Force bounce fees to be charged to victims for AAs that would otherwise have executed successfully, since bouncing reverts execution back to the bounce_fees deduction.
- In aggregate, this is an AA fund-loss/freezing and correctness-of-execution issue reachable purely by an AA trigger sender (unprivileged), matching the “fail-safe propagate” bug class from the source report where one failing sub-call breaks processing for all others.

### Likelihood Explanation
Any address (or upstream AA) can trigger an AA whose logic (defined in oscript by the AA author) sends outputs to multiple sibling AAs in one message set; this is a normal, supported multi-AA-fan-out pattern exercised in the test suite (`test/aa_composer.test.js` "chain of AAs" and related tests) confirming that arrays of secondary triggers are routinely processed together. [8](#0-7)  Because bounces are a normal/expected AA behavior (e.g. insufficient balance conditions), triggering one bounce among several sibling AAs requires no privileged access, only crafting inputs/state that cause one of the fan-out AAs to fail its own preconditions.

### Recommendation
`handleSecondaryTriggers` should not treat a bounce from one secondary AA as a fatal error for the entire `async.eachSeries` loop. Each secondary AA already has its own bounce/rollback semantics (bounce fees, revert of its own balance changes) — that isolation should not be escalated to abort or revert the other, independent secondary AAs in the same batch. Refactor the `cb(bounce_message)` / final `err` handling in `handleSecondaryTriggers` (aa_composer.js, roughly lines 1736–1750) so that a bounced secondary AA is recorded (e.g., in `arrResponses` with `bounced: true`) without calling `cb(bounce_message)`, allowing `async.eachSeries` (or better, `async.each`) to continue processing sibling AAs, and only proceed to `saveStateVars()`/`addUpdatedStateVarsIntoPrimaryResponse()`/`onDone(...)` normally rather than unwinding the whole chain via `revert`/`bounce`.

### Proof of Concept
1. Deploy AA `Factory` whose response unit, in a single trigger execution, sends outputs to two independent AAs, `GoodAA` and `BadAA`.
2. `GoodAA` has trivial logic that always succeeds (e.g., forwards remaining balance).
3. `BadAA` is written (or naturally happens) to always bounce, e.g., by requiring a state precondition that is false (`bounce("always bounce")`).
4. Post a normal payment unit that triggers `Factory`.
5. Observe via `handleSecondaryTriggers` in `aa_composer.js` that because `BadAA`'s trigger returns a bounce, `async.eachSeries`'s final callback receives `err`, and `revert({message: "one of secondary AAs bounced with error: ", ...})` is invoked, discarding `GoodAA`'s otherwise-successful execution and state changes. [5](#0-4) 
6. Compare against the expected fail-safe behavior: `GoodAA`'s response should have been recorded as bounced=false with its effects preserved, independent of `BadAA`'s bounce.
