## Analog Found

### Title
AA internal balance ledger is decremented even when the accompanying payment message is silently dropped for fixed-denomination (indivisible) assets - ([File: aa_composer.js])

### Summary
In Obyte AAs (Autonomous Agents), an AA definition can respond to a trigger with several messages in the same response, typically a `payment` message that pays out funds and a `state` message that updates the AA's own bookkeeping (e.g., decrementing a user's tracked balance in a `var[...]` state variable), following the common "internal ledger" pattern seen throughout the codebase's own sample scripts (`a_bank_without_percent.oscript`, `order_book_exchange.oscript`, `fundraising_proxy.oscript`, `payment_channels.oscript`). This mirrors exactly the `usdBalance[msg.sender]` bookkeeping pattern in the reported `CrabNetting.withdrawUSDC()` bug: state is updated unconditionally, while the actual transfer of value can silently fail/not-happen.

### Finding Description
When `handleTrigger` -> `sendUnit` assembles the AA's response unit, it iterates the `payment` messages and, for any payment whose asset is `fixed_denominations` (an indivisible/textcoin-style asset), it silently strips out that entire `payment` message from the response: [1](#0-0) 

Crucially, this filter only removes `app: 'payment'` messages — it does **not** touch any other message in the same response, such as an `app: 'state'` message that was written by the AA author to decrement an internal balance variable in lockstep with the (now-removed) payment. The overall "are there any messages left" check only bounces the whole trigger if **all** messages end up empty: [2](#0-1) 

If there are other messages left (e.g., the `state` message), execution proceeds normally: the (already-filtered) message list is used to build `objUnit`, and then `executeStateUpdateFormula(objUnit, ...)` is invoked on that same filtered message list to actually apply/persist the state variable formulas: [3](#0-2) 

Because the state-decrement formula (e.g. `var[$key] = var[$key] - trigger.data.amount;`) is not conditioned on whether the sibling payment message survived filtering, it executes and is committed via `fixStateVars()`/`updateFinalAABalances`, permanently reducing the user's tracked balance — even though the corresponding `payment` output for that indivisible asset was dropped and no coins were actually sent to the user. This is the exact analog of `CrabNetting.withdrawUSDC()`: the ledger entry (`usdBalance[msg.sender] -= _amount`) is committed unconditionally while the real transfer (`IERC20(usdc).transfer(...)`) can silently not happen.

The canonical AA pattern that is vulnerable to this is demonstrated by the project's own sample oscript files, e.g. the withdraw case: [4](#0-3) 
and [5](#0-4) 

If an AA author (following this documented/idiomatic pattern) allows `trigger.data.asset` to be any user-supplied asset (as in `a_bank_without_percent.oscript`, where `asset: "{trigger.data.asset}"` is taken directly from `trigger.data`), and that asset happens to be `fixed_denominations`, the `payment` message for that asset is dropped by `aa_composer.js` while the `state` message still executes, decrementing the user's balance without ever paying them.

### Impact Explanation
Any AA that maintains a per-user internal balance for an asset and pays it out via a `payment` message paired with a `state` decrement (a widely-used, idiomatic AA pattern) is at risk: if the withdrawn asset is (or can be) fixed-denomination, the user's tracked balance is silently burned/lost while no real funds are transferred. This is a direct, unauthorized loss of AA-held user funds — funds become permanently stuck/unspendable by the rightful owner (their ledger entry is gone, and there's no other mechanism to reclaim it), matching the "AA fund loss or freezing" impact bar.

### Likelihood Explanation
Likelihood depends on whether an AA's oscript logic lets a `trigger.data.asset` (or otherwise attacker/user-influenced asset) resolve to a fixed-denomination asset when computing a payout that is paired with a state-ledger decrement. This is plausible for generic multi-asset AAs (banks, exchanges, escrows) that accept `trigger.data.asset` as a parameter rather than hardcoding a specific divisible asset — a pattern explicitly present in the repo's own sample AA (`a_bank_without_percent.oscript`). The trigger condition doesn't validate that the asset is divisible before allowing the withdraw case to fire.

### Recommendation
In `aa_composer.js`, when a `payment` message is removed because its asset is `fixed_denominations` (or removed for any other reason at this filtering stage), any correlated `state` message(s) in the same response should either: (1) also be removed/bounced (fail the whole trigger with an explicit error, similar to how `messages.length === 0` triggers `handleSuccessfulEmptyResponseUnit`), or (2) the AA formula engine should expose a way to detect that a sibling payment failed so authors can guard the state decrement. At minimum, AA authors should be warned/documented that payments of indivisible assets from AAs are unsupported and silently dropped, and the AA validation (`aa_validation.js`) should reject/flag AAs whose `payment` messages could target `fixed_denominations` assets paired with unconditional state mutations.

### Proof of Concept
1. Deploy an AA equivalent to `test/samples/a_bank_without_percent.oscript`, where `trigger.data.asset` is used both in the `payment` message's `asset` field and in the `state` message's `var[$key] -= trigger.data.amount`.
2. A user deposits some divisible-looking `asset` into the AA (silently accepted, ledger incremented) — but this asset is actually created with `fixed_denominations: true` (an indivisible/textcoin asset).
3. The user later triggers a withdraw for `trigger.data.amount` of that asset.
4. In `aa_composer.js`, the withdrawal condition passes (balance check on `var[$key]` succeeds), so the case's messages (`payment` + `state`) are queued.
5. During message finalization, the filter at aa_composer.js removes the `payment` message because `assetInfos[asset].fixed_denominations` is true: [6](#0-5) 
6. Since the `state` message remains, `messages.length !== 0`, so execution proceeds to `executeStateUpdateFormula`, which decrements `var[$key]` by `trigger.data.amount` and commits it via `updateFinalAABalances`/`fixStateVars`.
7. Result: the user's tracked balance is reduced, a response unit is produced, but no asset output was ever sent to the user — the funds are permanently stuck in the AA with no ledger entry left to reclaim them.
