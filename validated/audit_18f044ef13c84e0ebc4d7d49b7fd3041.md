### Title
Uncaught Assertion Throw on Stable "temp-bad" Input Crashes Node During Payment Validation - ([File: validation.js])

### Summary
The CVE describes a Xen host crash triggered by an *incorrect assertion* (`ASSERT` in the M2P/log-dirty code) that a guest OS can hit and bring down the whole hypervisor host — i.e., an invariant the developer believed could never be violated, encoded as a fatal assertion, but which is in fact reachable by an unprivileged party under specific timing/state conditions. The analogous bug class in `ocore` is the use of hard `throw Error(...)` "assertions" inside the payment-input validation path that are meant to encode invariants about unit stabilization, but which run inside a payment-input DB-row callback with no surrounding `try/catch`, so hitting them terminates the node process instead of failing validation gracefully.

### Finding Description
In `validation.js`, the code that validates a `transfer` payment input queries the referenced source output and enforces the invariant that a *stable* output can never have `sequence === 'temp-bad'` — stable units are supposed to have already been resolved to `good` or `final-bad` by `markMcIndexStable()`'s `handleNonserialUnits()` step in `main_chain.js`. This invariant is enforced with a hard `throw`, not a graceful validation error: [1](#0-0) 

```

2456: if (bStableInParents) {
2457:     if (src_output.sequence === 'temp-bad')
2458:         throw Error("spending a stable temp-bad output " + input.unit);
```

This throw fires synchronously inside a `conn.query(...)` result callback, called from `validatePaymentInputsAndOutputs`, which is itself reached from `validateMessages` inside `validation.validate()` — the single, unauthenticated entry point that processes every unit posted by any peer or light client (`network.js`'s `handleJoint`/`handlePostedJoint`, `divisible_asset.js`, `indivisible_asset.js`, `aa_composer.js`). None of these callers wrap `validation.validate()` in a `try/catch` that can safely absorb an unexpected synchronous throw from deep inside a DB callback; an uncaught exception thrown from inside a `sqlite3`/`mysql` row-callback in Node.js is not caught by the caller's stack and results in an `uncaughtException`, crashing the node process — the same "host crash from an incorrect assertion" pattern as the CVE, except the "guest" here is any peer able to submit a unit and the "host" is the full node process.

The invariant itself ("stable ⇒ sequence != temp-bad") depends on stabilization always fully resolving sequence before `is_stable=1` is set and before validation of a spending unit can see it. `markMcIndexStable()` sets `is_stable=1` via one `UPDATE units SET is_stable=1 ...` query and only afterward resolves `sequence` for `temp-bad` rows in a separate, later step (`handleNonserialUnits`): [2](#0-1) 

Because these are two separate sequential steps (mark stable, then resolve sequence) rather than one atomic update, and because `objValidationState.last_ball_mci` is derived from parent last-ball state rather than the live `is_stable` flag, a validation running concurrently, or against a slightly different view of stabilization progress (e.g., via `determineIfStableInLaterUnitsAndUpdateStableMcFlag` advancing the stability point mid-validation, as seen in `validateParents`), can observe a source output that is stable-in-parents but whose `sequence` column has not yet been flipped away from `temp-bad`: [3](#0-2) 

### Impact Explanation
Hitting this uncaught throw during ordinary payment-input validation crashes the node's process (denial of service), matching the CVE's Availability-only impact (`C:N/I:N/A:H`). Because `validation.validate()` is the mandatory choke point for every unit accepted from the network — normal payments, private payment chains, AA triggers, and asset transfers all funnel through `validatePaymentInputsAndOutputs` — any full node (and light/hub-adjacent full nodes) processing a unit that spends such an input becomes vulnerable simultaneously, which can knock multiple/most nodes offline at once and stop the network from confirming new units, the same class of concrete harm the validation rules call out.

### Likelihood Explanation
This requires no special privilege: any unit poster can spend any output, including near-the-edge-of-stabilization ones, in normal operation — the only requirement is timing/state such that the two-phase stabilize-then-resolve-sequence process in `markMcIndexStable` is observed mid-transition by a concurrently validating unit. This mirrors the CVE's own high attack-complexity rating (`AC:H`) — a real but narrow, timing-dependent race — while remaining reachable purely through unit posting, without needing hub, peer, or key compromise.

### Recommendation
- Replace the hard `throw Error(...)` at `validation.js:2458` (and the sibling `throw Error("more than 1 src output")` at line 2451, and `throw Error("spending a stable final-bad output "...)`-style peers) with a soft validation failure (`return cb(...)`) so that hitting an unexpected/racy state degrades to "reject this unit" rather than crashing the process.
- Make the transition from `is_stable=1` to a resolved `sequence` atomic within `markMcIndexStable` (single transaction/update ordering) so no validator can observe the intermediate state.
- Add a top-level `try/catch` around `validation.validate()`'s async pipeline in `network.js`/`writer.js` callers that converts unexpected internal assertion failures into `ifTransientError`/`ifUnitError` instead of letting them propagate to `uncaughtException`.

### Proof of Concept
A concrete PoC requires reproducing the specific interleaving where: (1) a unit `U1` with a payment output ends up marked `is_stable=1` for its MCI in `markMcIndexStable` before `handleNonserialUnits` has updated its `sequence` from `temp-bad`, and (2) a second unit `U2` that spends that output is validated with `last_ball_mci >= U1.main_chain_index` in that same narrow window. Because this depends on internal DB timing/locking behavior across `main_chain.js` and `validation.js` that isn't fully visible from the code alone, exact reproduction steps should be confirmed by instrumenting `markMcIndexStable`/`validatePaymentInputsAndOutputs` in a test node rather than asserted here without execution.
